# 模块面试题 · Coding Agent（Claude Code / Codex）

> 岗位设定：**AI 编码工具工程师（使用者视角）**——不要求你训练模型或写 Agent 框架，要求你能把 Claude Code / Codex 这类终端编码 Agent 用对、用稳、用便宜，并能在一个团队里把它落地成规范。
> 题目按「通用问题 → 专业能力问题 → 行为面试问题 → 评估要点」四段组织，专业能力段按知识章节分组，每题作答走「判断 → 展开 → 佐证 → 边界」四槽，便于模拟面试时照着追问。

---

## 一、通用问题（角色认知与协作方式）

### Q1（通用）｜ 这个岗位的价值是"写得更快"吗？
- **判断**：不是。价值在**把不确定性前移**——把「需求澄清、上下文收集、验证闭环」这些本来靠人脑扛的环节，变成可复现的流程。
- **展开**：写代码的耗时只占交付的一小部分，真正吃时间的是「不知道改哪里」「改完不知道对不对」「别人不敢接」。Agent 在这三处的杠杆远大于补全速度。
- **边界**：只谈提速的候选人，通常没经历过 AI 改动引入线上问题的复盘；追问他「你最快的一次和最慢的一次差在哪」。

### Q2（通用）｜ 你会用哪些指标衡量引入 AI 编码工具的收益？
- **判断**：不能只看「代码行数 / 提交数」，要看**周期时间与返工率**。
- **展开**：
  | 层级 | 指标 | 说明 |
  | ---- | ---- | ---- |
  | 交付 | 需求从开工到合并的时长 | 直观但受需求粒度干扰 |
  | 质量 | 回滚率、hotfix 率、CR 一次通过率 | 提速是否以质量为代价 |
  | 成本 | 人均 token 花费 / 单需求花费 | 直接决定能不能规模化 |
  | 采纳 | 周活跃使用人数、人均会话数 | 工具是否被真正用起来 |
- **边界**：「代码生成占比」这类指标容易造假且鼓励堆量，作为主指标会把团队带偏。

### Q3（通用）｜ 你怎么建立对 AI 产出代码的信任？
- **判断**：靠**可验证性**而不是靠"看起来对"——测试、类型检查、diff 规模三道闸门。
- **展开**：让 Agent 自己跑测试只是底线；更关键的是把任务切到「一次 diff 能被人在 10 分钟内读完」的粒度，并要求它给出验证命令与结果。
- **边界**：没有测试覆盖的仓库，AI 的收益会明显打折，此时先补测试而非先上 Agent。

### Q4（通用）｜ 你的日常工具组合是什么，怎么分工？
- **判断**：按**任务形态**分工，而不是按喜好——终端 Agent 管跨文件重构与排障，IDE 补全管行内编写，对话式工具管方案预研。
- **展开**：Claude Code / Codex 这类终端 Agent 的优势是能跑命令、能读整个仓库、能反复验证；劣势是上下文成本高、单次改动粒度大。小改动用补全更快更省。
- **边界**：把一切都丢给终端 Agent 是新人的典型误区，表现为「改一行字也开一个会话」。

### Q5（通用）｜ 安全与合规上你守哪几条线？
- **判断**：三条线——**密钥不进上下文、私有代码不外流、改动可审计**。
- **展开**：密钥走环境变量与配置文件的本地覆盖（如 `settings.local.json` 不入库）；接第三方模型时确认数据出境与留存策略；Agent 的所有改动必须落在 git 里，禁止绕过提交直接推。
- **边界**：为了省事开「不询问直接执行」的权限模式，等于把安全边界交给模型判断，是团队推广阶段最常见的事故源。

### Q6（通用）｜ 你要在一个 20 人团队推广，第一步做什么？
- **判断**：先做**一个标杆仓库的配置沉淀**，再做推广，而不是先发一份使用规范文档。
- **展开**：配置沉淀（指令文件、规则、常用技能、格式化钩子）能让第二个人直接复用；文档在没有人验证过的仓库里往往写不出来。
- **边界**：上来就全员铺开会导致「每人一套配置」，后续无法收敛，也无法度量。

## 二、专业能力问题（按知识章节）

### 2.1 安装、接入与模型选择

#### Q1（2.1）｜ 国内网络/模型怎么接入 Claude Code？
- **判断**：不改代码，改**环境变量**——用兼容 Anthropic 协议的网关地址 + 模型名，写进 settings 的 `env`。
- **展开**：核心四个变量：`ANTHROPIC_AUTH_TOKEN`、`ANTHROPIC_BASE_URL`、`ANTHROPIC_MODEL`、`ANTHROPIC_SMALL_FAST_MODEL`；前两个决定"发给谁"，后两个决定"用哪个模型干活 / 用哪个模型做轻量任务"。
- **佐证**（示意片段）：
  ```json
  // .claude/settings.json
  {
    "env": {
      "ANTHROPIC_AUTH_TOKEN": "xxxxxx",
      "ANTHROPIC_BASE_URL": "https://open.bigmodel.cn/api/anthropic",
      "ANTHROPIC_MODEL": "glm-4.7",
      "ANTHROPIC_SMALL_FAST_MODEL": "glm-4.5-air"
    }
  }
  ```
- **边界**：各厂商的兼容路径与模型名会变，`SMALL_FAST_MODEL` 常被漏配导致轻量任务也走大模型；多模型切换用 cc-switch 之类的工具管理，而不是手改文件。

#### Q2（2.1）｜ 项目级、本地级、全局级配置分别放哪，怎么取舍？
- **判断**：**团队共享**的进项目级 `settings.json`，**个人/含密钥**的进 `settings.local.json`（不入库），**跨项目习惯**的进 `~/.claude/settings.json`。
- **展开**：判断标准是「这条配置换个人还成不成立」——权限白名单、钩子属于团队共识，模型与密钥属于个人环境。
- **边界**：把密钥写进项目级配置并提交，是这类工具最典型的泄露方式；反过来把团队钩子只写在本地，会导致别人跑不出同样结果。

#### Q3（2.1）｜ 环境"看起来能跑"但结果不对，你怎么排查？
- **判断**：先用工具自带的体检入口确认**装了什么、连到哪、上下文占了多少**，再怀疑模型能力。
- **展开**：`claude --version` 确认版本，`/doctor` 查安装与配置，`/context` 看当前上下文占用；多数"变笨了"其实是上下文被塞满或模型被切走了。
- **边界**：不要一上来换模型——先排除上下文与配置问题，否则会把两件事的归因混在一起。

### 2.2 核心工作原理与权限模式

#### Q1（2.2）｜ Agent 一轮任务到底在跑什么？
- **判断**：一个循环——**收集上下文 → 采取行动 → 验证结果**，不通过就继续收集，直到满足停止条件。
- **展开**：三类阶段各对应一组能力：收集靠搜索与读取工具，行动靠文件编辑与命令执行，验证靠测试/类型检查与报错信息。工具大致五类：文件操作、搜索、执行、网络、代码智能。
- **边界**：候选人若只答"它会自动改代码"，通常没意识到**验证阶段是 Agent 与补全工具的分水岭**——能跑测试才有闭环。

#### Q2（2.2）｜ 四种权限模式怎么选？
- **判断**：按**改动风险**选，不按熟练度选——`plan`（只出计划不动文件）用于不熟悉/高风险，`manual`（动手前问）用于默认，`acceptEdits`（常规命令免确认）用于高频低危，`auto`（带安全检查自动执行）只用于隔离环境。
- **展开**：模式是运行时可切换的（`Shift + Tab` / `Alt + M`），所以正确用法是**一个会话内分段切换**：探查阶段用 plan，执行阶段放宽。
- **边界**：一整场会话都开着最高权限，等于放弃了人工闸门；追问候选人「你会在哪一步切回来」。

#### Q3（2.2）｜ Agent 到底能看到什么？
- **判断**：它能看到**当前工作目录及许可文件、终端信息、git 状态、指令文件与记忆、以及 MCP/技能/子代理等扩展**，看不到你没给它的东西。
- **展开**：这条决定了「上下文工程」的全部工作——你想让它知道什么，就得有一条路径把它送进上下文（文件、规则、记忆、MCP、命令输出）。
- **边界**：很多人以为它能看到整个磁盘或别的项目；实际会话**与启动目录绑定**，换个目录就是另一个会话。

### 2.3 上下文工程（指令文件、规则与记忆）

#### Q1（2.3）｜ 为什么指令文件建议控制在 200 行以内？
- **判断**：因为它**每次会话都全量加载**，行数是固定成本，直接挤占真正干活的上下文。
- **展开**：取舍规则是「每个会话都需要的才留，按需的挪走」——语言/包管理器/测试命令留下，某类文件的详细规范挪到 `rules/`，长篇参考挪到 skills。
- **边界**：`@file` 导入的内容**同样计入这 200 行**；以为用导入就能"无限扩展"是常见误解。

#### Q2（2.3）｜ 带 `paths` 的规则和不带 `paths` 的规则有什么区别？
- **判断**：不带 `paths` 的规则**会话开始即加载**（等同指令文件），带 `paths` 的规则**碰到匹配文件时才加载**。
- **展开**（示意片段）：
  ```
  // .claude/rules/testing.md
  ---
  paths:
    - "**/*.test.ts"
  ---
  - 测试名写成 should [expected] when [condition]
  - 只 mock 外部依赖，不 mock 内部模块
  ```
- **边界**：把高频规范写成带 paths 的规则会让它在需要时不生效（文件没被打开就不加载），这是「规则写了没用」的头号原因。

#### Q3（2.3）｜ 记忆文件与指令文件的加载差异是什么？
- **判断**：记忆 `MEMORY.md` **有上限、会被截断**（200 行 / 25KB，先到先算），指令文件**没有上限、全量加载**。
- **展开**：记忆是跨会话沉淀的，超限时工具会提醒精简，超限部分下次加载被丢弃；指令文件则是越短越好但一定完整。自动记忆默认开启，可关。
- **边界**：把项目规范塞进记忆文件是不可靠的——它会被截断；规范应放在指令文件或规则里。

#### Q4（2.3）｜ 会话、目录与上下文清理怎么配合？
- **判断**：**会话绑定目录**，同目录可恢复、跨目录不互通；上下文靠 `/context` 观察、靠 `/compact` 压缩、靠 `/clear` 重置。
- **展开**：使用顺序是——看着涨到高位先 `/compact`（保留语义、腾出空间），主题切换用 `/clear`，换目录直接新开；历史会话落在本地，可 `/resume` 恢复。
- **边界**：`/compact` 会丢细节，压缩前确认关键结论已经落到文件或提交里；中途打断了方向可以直接中断重新引导，不必硬等它跑完。

### 2.4 扩展机制选型

#### Q1（2.4）｜ Skill / Command / Subagent / MCP / Hook 怎么选？
- **判断**：按**"要不要模型判断"和"要不要独立上下文"**两个维度选。
- **展开**：
  | 机制 | 谁触发 | 是否占用主上下文 | 适用 |
  | ---- | ---- | ---- | ---- |
  | Skill | 模型按描述匹配或 `/name` | 用时才加载全文 | 可复用的流程与知识 |
  | Command | 用户显式调用 | 用时加载 | 人手触发的固定动作 |
  | Subagent | 模型委派或点名 | 独立上下文，只回传总结 | 上下文隔离、并行、专精 |
  | MCP | 模型调用工具 | 会话加载工具名，用时加载 schema | 接外部服务与数据 |
  | Hook | 事件触发 | 不占上下文 | 确定性的自动化 |
- **边界**：能用 Hook 做的事（改完文件格式化）不要用 Skill 做——Hook 是确定性的，不烧 token 也不会被模型"忘记"。

#### Q2（2.4）｜ 这些机制的加载时机分别是什么？
- **判断**：**会话开始**加载的是指令文件与规则、MCP 工具名、Skill 描述；**用时**加载的是 Skill 全文与 MCP 的完整 schema；**事件时**加载的是 Hook（且它在主对话之外）；**委派时**才有 Subagent 的独立上下文。
- **展开**：这套"延迟加载"是上下文预算的核心——所以 Skill 的**描述**写得好不好，直接决定它会不会被选中。
- **边界**：限定为仅用户调用的技能（`disable-model-invocation: true`）在主动调用前完全不加载，常被误认为"技能没装好"。

#### Q3（2.4）｜ 技能自动触发为什么难做对？
- **判断**：因为模型只看**描述**来决定用不用，描述写得像标题就永远不会被选中。
- **展开**：有效的描述要写清「做什么 + 什么时候用 + 用户会怎么说」三件事，例如把适用场景与用户原话（"帮我 review 这段代码"）都写进去。
- **边界**：描述过宽会导致误触发、过窄会导致不触发；落地方式是用真实需求语料反复试，而不是一次写完。

### 2.5 子代理与多会话协作

#### Q1（2.5）｜ 子代理和主对话的差别在哪几个维度？
- **判断**：三个维度——**上下文（空白，只拿到任务交代）、人设（专属 system 提示）、工具与权限（可单独裁剪）**。
- **展开**：这三维决定了它的用途：上下文隔离（脏活不污染主线）、专精人设（只挑刺的审查员）、限权（只准读不准写）。
- **边界**：子代理看不到你和主对话聊过什么，「交代不清就返工」是使用它的主要成本。

#### Q2（2.5）｜ 什么时候不该拆子代理？
- **判断**：**简单活儿直接干更快更省**——拆得多不等于更专业。
- **展开**：四项代价——启动开销（从白纸开始摸上下文）、沟通返工（看不到主对话）、多烧 token、结果回灌（每个都把详细结果塞回主线，开多了反而把上下文堆回去）。
- **边界**：判断标准是「这个子任务是否需要自己收集大量上下文且主线不需要这些细节」；并发写类任务还会放大冲突。

#### Q3（2.5）｜ 子代理怎么建、怎么触发？
- **判断**：建 = 写一个带 frontmatter 的 Markdown；触发 = 自动委派、点名、或 `@名称`。
- **展开**：关键字段是 `name`、`description`（决定委派准不准）、`tools`（省略即继承，列出即限权）、`model`、`permissionMode`。
- **边界**：早期 `/agents` 命令已废弃，现在推荐用提示词让工具生成再人工改；`description` 写含糊会导致"该派不派、不该派乱派"。

### 2.6 钩子与确定性自动化

#### Q1（2.6）｜ 钩子的时机有哪些，哪个能拦住操作？
- **判断**：`PreToolUse` 是唯一能**阻止**工具执行的时机，`PostToolUse` 只做事后处理。
- **展开**：完整链路是 `SessionStart → UserPromptSubmit → Pre/Post 工具循环 → Stop → SessionEnd`；典型用法分别是注入项目状态、校验提示、拦截危险命令、改完自动格式化与 lint、答完提醒收尾。
- **边界**：把"检查并阻止"写在 `PostToolUse` 上是无效设计——那时改动已经落盘。

#### Q2（2.6）｜ 钩子为什么必须用 matcher 收窄？
- **判断**：不收窄就**每个工具调用都跑一遍**，噪声和延迟都会失控。
- **展开**（示意片段）：
  ```json
  {
    "hooks": {
      "PostToolUse": [
        {
          "matcher": "Edit|Write",
          "hooks": [
            { "type": "command", "command": "jq -r '.tool_input.file_path' | xargs npx prettier --write" }
          ]
        }
      ]
    }
  }
  ```
- **边界**：钩子跑在主对话之外、不占上下文，这是它相对技能的优势；代价是它不理解语义，只能按规则机械执行。

#### Q3（2.6）｜ 钩子和技能的分工边界在哪？
- **判断**：**确定性的、每次都要发生的 → 钩子；需要理解语义、按需发生的 → 技能**。
- **展开**：判断依据是"这件事会不会因为模型心情不好而漏做"——格式化、lint、保护敏感文件不该有这种不确定性。
- **边界**：反过来，把需要判断的业务校验（比如"这段改动是否破坏兼容"）塞进钩子，会得到大量误报。

### 2.7 插件、市场与分发

#### Q1（2.7）｜ 插件是什么，装进来后各组件怎么用？
- **判断**：插件是**打包与分发层**——把技能、子代理、钩子、命令、MCP 捆成一个可安装单元。
- **展开**：装进来后——技能/命令变成带命名空间的 `/插件名:skill名`；子代理进列表可被自动派；钩子按事件自动触发；MCP 自动启动并混入工具箱；LSP 需另装语言服务器二进制。
- **边界**：**插件不是纯提示词**，它可能带可执行钩子与外部访问，装之前要看清单与权限。

#### Q2（2.7）｜ 装很多插件有什么代价？
- **判断**：**还没干活，上下文就被技能说明和 MCP 工具占掉了**。
- **展开**：插件加载的东西是会话级固定成本，装得越多，"可用 token" 越少；分发时优先项目级安装，只把个人通用工具装到全局。
- **边界**：判断标准是「这个插件的能力是否每周都用」；一次性插件装完即用即卸。

#### Q3（2.7）｜ 自定义插件的最小结构是什么？
- **判断**：一个 `.claude-plugin/` 描述文件 + 若干能力目录。
- **展开**：`plugin.json` 管插件自身元信息（name/description/version/author），`marketplace.json` 管市场与插件清单（含 `source`）；能力分别放 `skills/`、`agents/`、`hooks/hooks.json`。
- **边界**：两个 json 的 `name` 与 `source` 不一致会导致市场里能看到但装不上；分发用 git 链接即可。

### 2.8 成本、性能与排障

#### Q1（2.8）｜ 上下文污染的典型表现与处置？
- **判断**：表现为**变慢、变笨、开始引用早已无关的文件**；处置顺序是 `/context` 看占用 → `/compact` 压缩 → 换主题就 `/clear`。
- **展开**：污染来源通常是大段搜索结果、失败的尝试、以及多个子代理回灌的详细结果。
- **边界**：压缩会丢细节，所以关键结论要先落到文件或提交里；这题的加分项是"我会在任务中途主动开新会话，而不是等它变慢"。

#### Q2（2.8）｜ 成本怎么控？
- **判断**：控**上下文体积**和**并行度**，不是控对话轮数。
- **展开**：上下文是每轮都要重付的费用——少塞无关文件、及时压缩、能用钩子就别用技能；并行度上，子代理每多开一个就多一份上下文开销。
- **边界**：轻量任务走小模型（配 `SMALL_FAST_MODEL`）是常被忽略的一项；反过来为了省钱把所有任务压到一个长会话里，会同时损失质量。

#### Q3（2.8）｜ 常见"不生效"怎么定位？
- **判断**：按**加载链路**逐段排除——装了吗、加载了吗、匹配到了吗。
- **展开**：技能不触发 → 看描述是否写清场景；钩子不跑 → 看 matcher 是否匹配、配置层级是否生效；MCP 连不上 → 看作用域（项目级需 `--scope project`）与传输方式（如 `--transport http`）。
- **边界**：权限弹窗反复出现通常不是"工具坏了"，而是白名单写在了错误的层级（本地 vs 项目）。

### 2.9 跨工具：Codex 与其他终端 Agent

#### Q1（2.9）｜ Codex 与 Claude Code 的核心差异是什么？
- **判断**：理念相近（都是终端 Agent、都读 Markdown 指令、都沙箱化、都接 MCP），差异在**指令文件、配置形态、模型生态与非交互能力**。
- **展开**：
  | 维度 | Codex CLI | Claude Code |
  | ---- | ---- | ---- |
  | 指令文件 | `AGENTS.md` | `CLAUDE.md`（也能通过 `@AGENTS.md` 读同一份） |
  | 配置 | `~/.codex/config.toml`（项目级 `.codex/config.toml`） | `settings.json` 层级体系 |
  | 默认模型 | GPT-5.x 系列 | Opus / Sonnet |
  | 实现 | Rust 单二进制 | Node.js |
  | 非交互 | `codex exec`（CI 友好） | headless 模式 |
- **边界**：不要按"谁更强"选型，按**团队已有的订阅与模型偏好**选型；重度用户通常两个都装，按任务路由。

#### Q2（2.9）｜ Codex 的沙箱与审批为什么是两条独立的轴？
- **判断**：**沙箱决定"能碰多远"，审批决定"越界时问不问人"**——两者组合才是完整的安全模型。
- **展开**：沙箱有 `read-only` / `workspace-write` / `danger-full-access`，审批有 `untrusted` / `on-request` / `never`；日常推荐 `workspace-write + on-request`，CI 推荐 `workspace-write + never`，`danger-full-access` 与绕过沙箱的开关只用于一次性环境。
- **佐证**（示意片段）：
  ```toml
  # ~/.codex/config.toml
  model = "gpt-5.x"
  sandbox_mode = "workspace-write"
  approval_policy = "on-request"

  [profiles.ci]
  approval_policy = "never"
  ```
- **边界**：`--full-auto` 这类笼统开关已被显式的沙箱/审批配置取代；把 `never` 用在没有沙箱的交互场景是最危险的组合。

#### Q3（2.9）｜ 同一个仓库要同时支持两个工具，配置怎么复用？
- **判断**：**指令文件复用一份，工具配置各写各的**。
- **展开**：以 `AGENTS.md` 为源，指令文件里用 `@AGENTS.md` 引入（或做软链），避免两边规范漂移；MCP 这类工具配置无法通用，需要分别写在 `.mcp.json` 与 `.codex/config.toml` 的 `[mcp_servers.*]`。
- **边界**：指令文件有体积上限（Codex 侧默认 32KiB 量级的项目文档上限），超出会被截断——所以共用文件更要保持精简。

### 2.10 场景设计题

#### Q1（2.10）｜ 给一个中型仓库做 Agent 落地，你怎么划分配置？
- **判断**：按**加载时机**划分——每次都要的进指令文件，按文件类型生效的进 `rules/`，可复用流程进 `skills/`，确定性动作进 `hooks/`。
- **展开**：指令文件只放包管理器、测试命令、目录约定（控制在 200 行内）；`rules/` 放测试规范、API 设计等带 `paths` 的规则；`skills/` 放发布检查表、排障流程；`hooks/` 放改完文件格式化与敏感文件保护。
- **边界**：把所有规范堆进指令文件是最常见的错误答案——它既超长又无法按需加载。

#### Q2（2.10）｜ 要把 Agent 接进 CI，你怎么设计？
- **判断**：**最小权限 + 非交互 + 可审查**——只读或工作区写权限、不询问、输出结构化结果。
- **展开**：Codex 侧用 `codex exec` 配 `workspace-write + never`，需要结构化输出就加 `--json`；执行前让 git 处于干净状态或先建检查点，产出以 diff/PR 形式交付而不是直接推。
- **边界**：CI 里给"完全访问 + 不询问"等于给流水线里的任意代码执行权限；追问候选人「如果 Agent 在 CI 里被注入恶意提示，你的边界在哪」。

#### Q3（2.10）｜ 团队推广到一半，有人说"AI 写的代码不敢合"，你怎么处理？
- **判断**：把**信任问题拆成流程问题**——不是"敢不敢"，而是"合并前有哪些闸门"。
- **展开**：三件事——缩小单次 diff 粒度、强制验证命令与结果进 PR 描述、把高频返工点沉淀成规则/技能，让同类错误不再出现第二次。
- **边界**：用"多 review 几遍"来回应是不可规模化的；这题看的是候选人会不会把一次性质疑转成可执行的机制。

## 三、行为面试问题（STAR）

每题按「题面 → 考察点 → 追问 → 回答质量信号」使用。

### Q1（行为）｜ 讲一次你把 AI 编码工具引入团队/项目的完整经历。
- **考察点**：推动路径是否从标杆场景切入、是否有度量、是否处理了阻力。
- **追问**：第一个接入的是哪个仓库，为什么选它？第二个人是怎么上手的？三个月后还在用的人有几个？
- **信号**：好回答能给出"先沉淀配置再推广"的顺序和具体数字；差回答只讲"我演示了一次大家觉得好用"。

### Q2（行为）｜ 讲一次 AI 生成的代码差点或已经造成问题的经历。
- **考察点**：是否有验证闭环、是否做复盘并沉淀成机制。
- **追问**：问题是什么时候发现的（上线前/后）？之后你改了哪条配置或流程来避免复发？
- **信号**：好回答会把一次事故转成一条规则/钩子/检查表；差回答停留在"以后我更仔细看"。

### Q3（行为）｜ 讲一次你与同事在"要不要用 AI"上产生分歧的经历。
- **考察点**：说服方式是讲道理还是拿证据。
- **追问**：对方的具体顾虑是什么？你用什么数据或试点回应？最后结论是什么？
- **信号**：好回答会用试点结果（耗时、返工率）说话，并接受"部分场景不用"的结论；差回答是立场之争。

### Q4（行为）｜ 讲一次你在完全陌生的仓库里用 Agent 快速上手的经历。
- **考察点**：上下文收集策略——先问什么、先看什么、怎么验证理解正确。
- **追问**：你第一步让它做什么？你怎么确认它对架构的理解是对的？用了多久？
- **信号**：好回答会先做只读探查（结构、入口、测试、约定）并交叉验证，再动手；差回答直接让它改。

### Q5（行为）｜ 讲一次你在成本或安全上踩的坑。
- **考察点**：是否意识到上下文即成本、配置即权限边界。
- **追问**：是怎么发现账单/权限异常的？改了什么配置？有没有推广给其他人？
- **信号**：好回答能说清"哪一类操作最烧钱""哪一类配置最危险"；差回答完全没有成本与安全维度。

### Q6（行为）｜ 你如何保持对这类快速变化工具的更新？
- **考察点**：信息源质量与验证习惯（这类工具官方文档改动频繁）。
- **追问**：上一次你发现"我之前用错了"是什么时候？你怎么验证一个新特性真的可用？
- **信号**：好回答有一手验证习惯（小仓库试跑、看 `/status`、看官方 changelog）；差回答只转述二手文章。

## 四、评估要点

### 4.1 评分维度与权重

| 维度 | 权重 | 看什么 | 主要题源 |
| ---- | ---- | ---- | ---- |
| 工具熟练度 | 30% | 安装接入、权限模式、会话与上下文命令是否形成肌肉记忆 | 2.1 · 2.2 |
| 上下文工程 | 25% | 指令文件/规则/记忆的取舍，能否按加载时机组织配置 | 2.3 |
| 扩展机制选型 | 20% | 技能/子代理/钩子/MCP/插件的分工与代价判断 | 2.4 · 2.5 · 2.6 · 2.7 |
| 成本与安全 | 15% | token 成本结构、沙箱与审批组合、CI 最小权限 | 2.8 · 2.9 |
| 协作与度量 | 10% | 团队落地路径、指标设计、质疑的应对方式 | 一 · 2.10 · 三 |

### 4.2 分级标准

| 等级 | 画像 |
| ---- | ---- |
| **优秀（A）** | 每个选型都能说出"代价"和"什么时候不用"；能把一次事故沉淀成配置；谈推广时自带指标 |
| **合格（B）** | 常用功能熟练、能独立完成配置；取舍主要凭经验，说不出量化理由 |
| **待提升（C）** | 只会"装插件、写指令文件、让它跑"；上下文与成本没有概念，安全边界依赖默认配置 |
| **不通过（D）** | 把 Agent 当补全工具用；对权限与密钥风险无感知；无法讲清一次完整落地经历 |

### 4.3 红线信号（出现即降一档）

- 为了省事长期开最高权限/绕过沙箱，且说不出适用场景。
- 把密钥或私有代码配置提交到仓库。
- 说不出任何一次"AI 改动引入了问题"的经历——通常意味着没有验证闭环。
- 认为"上下文越多越好"，从不压缩、从不清理会话。

### 4.4 通用追问链（把"会用"问到"懂取舍"）

1. 你这么做的原因是什么？→ 2. 换一种做法（技能/钩子/子代理）会怎样？→ 3. 什么情况下你会推翻自己刚才的选择？→ 4. 这个选择在多人和 CI 场景下还成立吗？

### 4.5 45 分钟模拟面试流程建议

| 时段 | 内容 | 目的 |
| ---- | ---- | ---- |
| 0–5 min | 自我介绍 + 常用工具组合（通用 Q4） | 定位层级 |
| 5–20 min | 专业能力：2.1 接入 → 2.3 上下文 → 2.4 选型，各抽 1–2 题 | 看技术底盘 |
| 20–30 min | 场景设计：2.10 选一题，要求现场给出目录与配置划分 | 看工程化能力 |
| 30–40 min | 行为题选 2 题（建议 Q2 + Q5） | 看复盘与风险意识 |
| 40–45 min | 反问 + 按 4.1 权重现场评级 | 收敛结论 |

> 追问优先走 4.4 的四步链；候选人卡住时，退到更具体的子问题（"那你说说 matcher 写过什么"），不要直接给答案。
