## 1. Agent 是什么与 LLM 接入

### 1.1 Agent 与 LLM 的本质区别

普通大模型应用是"用户 → LLM → 答案"的单向链路；Agent 多出一条"LLM 决策 → 选工具 → 执行 → 结果回灌 → 再判断"的循环。核心差异是：**LLM 不再只回答，而开始参与决定程序下一步做什么**——这一步让"调用什么工具、传什么参数"由模型在运行时决定，而非程序员写死的 `if/else`。

```
普通应用：  User → 程序(if/else) → 结果
Agent：     User → LLM → 决策 → Tool → 执行 → Observation → LLM → ...
```

### 1.2 接入大模型：NestJS + OpenAI 兼容 SDK

Agent 本质是一个真实运行在服务端的软件系统，仍然需要 API、数据库、鉴权、部署。先用 NestJS 把"调用模型"这一层独立成 `LlmModule`（依赖注入、`exports` 暴露 `LlmService`），再把"Agent 行为"放在 `AgentModule`，做到**模型厂商与 Agent 解耦**：换 DeepSeek / OpenAI / Claude 不推倒重写。Key 走环境变量（如 `DEEPSEEK_API_KEY`），不进代码、不提交 Git；用 OpenAI SDK + `baseURL` 指向兼容网关，零成本切换厂商。

### 1.3 messages 与 Context：多轮对话的本质

`messages` 就是模型这一次能看到的对话上下文，常见角色有 `system / user / assistant / tool`。所谓"多轮对话"首先是 **Context 管理问题**：API 每次调用都是无状态的，上一轮对话不会自动保留，必须把历史消息重新放进 `messages` 才能"记住"。而 `Context Window` 有上限，一轮调用到底放什么进 Context（System + Tool 定义 + 历史 + 记忆 + RAG 文档 + 工具结果 + 当前消息）正是后续 Context Engineering 要解决的。

### 1.4 Structured Output：让自然语言进入程序逻辑

自然语言 → LLM → 自然语言，程序很难直接行动；Structured Output 把链路变成 自然语言 → LLM → JSON → 程序对象 → 行为。优先用模型 API 自带的 `response_format: { type: 'json_object' }` 约束输出，而不是只靠 Prompt 说"请返回 JSON"——后者模型可能包一层"好的，结果是：{...}"导致 `JSON.parse` 报错。

### 1.5 运行时校验：合法 JSON ≠ 正确 Schema

模型返回的 `content` 本质还是字符串，`JSON.parse` 后只是 JavaScript 对象；但"JSON 格式正确"不等于"结构正确"（字段名、类型可能错）。所以 Structured Output 之后还要做 **Runtime Validation**（如 Zod），形成 `LLM → Structured Output → JSON → Zod Schema → 校验 → TS 对象 → Agent`。注意 `as IntentResult` 只是编译期断言，运行时没有任何检查，类型与校验必须分开。

## 2. Tool Calling：让 LLM 直接调用程序

### 2.1 工具 schema 与"模型选工具"

Tool Calling 不是告诉模型"用户问天气时返回 weather"，而是告诉它"这里有一个真正可调用工具 `getWeather(city)`"，由模型**自己决定要不要调用、传什么参数**。工具以 OpenAI 兼容的 `function` schema 描述：`name / description / parameters(JSON Schema)`。`description` 是 Agent Prompt 的一部分，模型据此选工具，所以写得准不准直接决定调用质量。

### 2.2 解析 `tool_calls` 与执行

模型返回的不再是纯文本，而是 `tool_calls: [{ name, arguments(JSON 字符串) }]`。程序要取出 `toolCall.function.name` 与 `JSON.parse(arguments)`，分发到真实实现执行，再把结果放回 Context 让 LLM 继续。关键点：真正该解析的是 `toolCall.function.arguments`，不是 `content`；模型不一定每次都调用工具（无 tool_calls 时直接当答案返回）。

### 2.3 与 Structured Output 的本质区别

Structured Output 是"模型描述用户意图（intent），程序根据 intent 决定下一步"；Tool Calling 是"模型直接选择程序能力并生成参数，程序直接执行"。后者让 Agent 第一次真正产生行动——模型负责"调用什么"，真正执行代码的仍然是应用程序。两者不要混用：用了 `tools` 就不要再带 `response_format: json_object` 做意图解析。

## 3. Agent Loop：会循环的运行时

### 3.1 Loop 的执行机制

一个最基础的 Agent = **LLM + Tools + Context + Agent Loop + Stop Condition**。Loop 就是把"模型决策 → 执行工具 → 结果回灌上下文 → 再调模型"循环到模型不再返回 `tool_calls`。

```
while (未达上限) {
  const r = await llm()
  if (!r.tool_calls?.length) return r.content
  await executeTools()   // 执行并把结果放回 messages
}
```

### 3.2 统一工具协议 `AgentTool`

所有工具遵循统一接口：`name / description / schema / execute()`。再配一个 `ToolRegistry` 管理工具集合，职责分离、便于注入。`AgentTool` 把"工具定义"和"工具实现"彻底分开——schema 给模型看，execute 给程序跑。

### 3.3 一轮多工具与"错误即观察"

`while` 管"多轮"，`for` 管"一轮里的多个 Tool"：一轮里模型可能一次请求多个工具，要逐个执行。工具的**错误同样可以作为 Observation 回灌给模型**，让模型重新决策——这是 Agent 与传统后端程序的重要区别：失败不一定等于 Agent 失败。

### 3.4 LLM 输出不可信：必须校验

LLM 输出永远属于不可信外部数据，无论 Structured Output 还是 Tool 参数，都必须经过 `JSON.parse` + Schema 校验才能真正进入业务系统。没有校验就信任模型输出，是 Agent 落地的头号风险。

## 4. 上下文与记忆：让 Agent 记住对话

### 4.1 多轮对话 = Context 管理

短期靠把历史 `messages` 重新塞回请求；但历史不可能无限增长，必须主动管理。Context 管理的目标是：在 `Context Window` 内保留"对当前任务有用的信息"，丢掉的用别的方式补回。

### 4.2 按对话轮次裁剪历史

最朴素的裁剪按 token 截断会切坏一条完整交互。更合理的是**按"对话轮次（Round）"裁剪**：一次 `user` 触发的连续交互（含中间的 `assistant(tool_calls) / tool / assistant`）算一轮，保留最近 N 轮。`trimMessages(messages, maxRounds)` 的核心是"遇到 `user` 就开新轮"。

### 4.3 Rolling Summary 压缩历史

当轮次也装不下时，把较早的历史压缩成一段摘要（Rolling Summary）注入 System Context，腾出空间。摘要的质量决定了 Agent 长期对话的连贯性。

### 4.4 短期记忆 vs 长期记忆

- **短期记忆**：当前会话的 `messages` + 裁剪 + 摘要，随会话结束而消失。
- **长期记忆**：跨会话沉淀的用户偏好、事实，需要持久化存储（见第 5 篇 Embedding + 向量库），并在每轮按需检索注入。

```
架构演进：  LLM → +Tool → +AgentLoop → +ContextManager → +Memory(短期/长期)
```

## 5. Embedding 与向量检索：长期记忆的持久化

### 5.1 Embedding 与语义向量

Embedding 把文本语义转成数字向量：语义越近，向量空间距离越近。这是长期记忆"语义检索"的基础——用户问"登录凭证多久失效"，也能召回"Refresh Token 有效期 30 天"（关键词并不一致）。

### 5.2 余弦相似度

用余弦相似度衡量两个向量的接近程度：越接近 1 越相似，越接近 0 越不相关。`cosineSimilarity(a, b) = dot / (|a|·|b|)`，维度必须一致。

### 5.3 向量库与 TopK

内存向量库负责写入向量并按余弦相似度取 TopK。生产环境用 PostgreSQL + `pgvector`（`vector(n)` 类型），用 `<=>` 计算余弦距离（`1 - distance` 即相似度），重启不丢、可并发。

```
SELECT content, 1 - (embedding <=> $1::vector) AS similarity
FROM "DocumentChunk" WHERE embedding IS NOT NULL
ORDER BY embedding <=> $1::vector LIMIT $2;
```

### 5.4 pgvector 持久化

Embedding 模型凭证（如 OpenAI）与推理模型（如 DeepSeek）**独立**，不要混用 Key。维度需实测（OpenAI `text-embedding-3-small` 默认 1536）。用 Prisma 管理：模型里 embedding 列映射为 `Unsupported("vector")`，写入与检索走 `$queryRaw`。允许 embedding 为 `NULL` 给 API 临时故障留容错。

### 5.5 语义检索与 Context 层级

一轮 Agent Context 的层级通常是：`System + 相关记忆 + 摘要 + 近期 + 当前`。长期记忆从"全量塞入"升级为"语义检索 TopK 注入"，避免把无关记忆撑爆 Context。

## 6. RAG：从 0 手写企业级知识库

### 6.1 RAG 是什么

RAG = Retrieval-Augmented Generation（检索增强生成）：用户问题 → 从知识库检索相关资料 → 作为 Context 交给 LLM → 基于资料回答。让模型"基于企业资料回答"，而不是凭自己记忆瞎编。

### 6.2 RAG 与 Tool 的关系

RAG 是一种能力，不一定非要是 Tool；但在 Agent 里，常把知识库检索包装成 `search_knowledge` 这样的 Tool 交给 Agent 自主调用。RAG ≠ Tool，但 RAG Retrieval 可以作为 Tool 提供给 Agent。

### 6.3 文档入库流水线

企业 RAG 的真正工程量在"数据工程"：

```
Document → Loader → Parser → Chunking → Metadata → Embedding → pgvector(存储)
查询： Query → QueryEmbedding → Vector Retrieval → TopK → Context → LLM → Answer+Sources
```

真实知识库不能手工写 Chunk，要有 Ingestion Pipeline 自动读取/解析/切片/入库；还要处理去重、事务、文档版本（同一 `documentKey` 多 `version`，`isActive` 标记生效版）。

### 6.4 向量检索、阈值与评估

相似度阈值（如 `similarity > 0.6`）不能拍脑袋，要靠 **Retrieval Evaluation** 得出合适值。注意 `0.618` 不是"模型 61.8% 把握"，只是向量距离算出来的分数。后续还有 Hybrid Search（向量 + BM25）、Rerank、Metadata Filter、Permission Filter、异步队列、PDF/DOCX/HTML 解析等。

### 6.5 进阶方向

RAG Generation（答案+来源）、Context Assembly、Prompt Engineering、Metadata 过滤、混合检索、重排、邻居召回、权限过滤、RAG 评估、异步 Ingestion、多格式解析。先做透底层，再用 LangChain 重构，能清楚框架到底封装了什么。

## 7. LangChain：用框架重写一遍 Agent

### 7.1 手写组件 → 框架抽象对应

先手写 Agent 底层，再学框架，才能把框架当"工程抽象"而非黑盒。手写组件与 LangChain 的对应：`LlmService`→`ChatOpenAI`、`AgentTool`→`tool()`、`ToolRegistry`→继续保留、`EmbeddingProvider`→`Embeddings`、`VectorStore`→`VectorStore`、`Retriever`→`Retriever`。

### 7.2 `ChatOpenAI` / Message / `tool()`

`ChatOpenAI` 封装 DeepSeek 等兼容端点；消息统一为 `SystemMessage / HumanMessage / AIMessage / ToolMessage`；`tool()` 把"name/description/schema/execute"统一成一个工具定义，并继续用 `ToolRegistry` 管理。

### 7.3 `bindTools()` 与 Agent Loop

`bindTools(tools)` 只是把工具描述提供给模型，**不自动执行**。真正的 Loop 仍要手写：`modelWithTools.invoke(messages)` → 拿到 `tool_calls` → 逐个执行 → 用 `ToolMessage`（带 `tool_call_id`）回灌 → 再 `invoke`，直到无 `tool_calls`。保留模型返回的完整消息、正确对应 `tool_call_id` 是循环跑通的关键。

### 7.4 RAG 集成与"不是所有都交 LLM"

RAG 作为知识 Tool 接入 Agent；System Prompt 要约束 Agent"不要乱判"（如 Android 安全分析里不能仅凭 `exported` 判漏洞）。重要原则：**确定性逻辑交 Tool，知识交 RAG，决策交 LLM**——不要把所有事都丢给模型。结构化报告（`withStructuredOutput()` + Zod）放在"调查阶段之后"单独整理，不要直接替换 Agent Loop。

## 8. LangGraph：有状态的流程编排

### 8.1 LangChain 与 LangGraph 的分工

LangChain 的 `createAgent()` 本身构建在 LangGraph 之上。LangChain 适合"模型、工具、提示词 + 现成流程扩展"；当任务需要"先做什么、何时重试、在哪等人确认、退出后怎么继续"这类**明确的有状态流程**时，直接用 LangGraph 设计 State / 节点 / 边 / 暂停 / 恢复。

### 8.2 State / Node / Edge

- **State**：当前任务保存了哪些数据（类比 Store，但更新要遵循图的合并规则）。
- **Node**：这一步做什么（读取状态、执行、返回要更新的字段）。
- **Edge**：执行完去哪（`addEdge` 固定边 / `addConditionalEdges` 条件边）。

真正决定执行顺序的是边的连接；`.addNode().addEdge()...compile()` 只是组装图，`invoke()/stream()` 才启动。

### 8.3 条件边与业务流程

`Conditional Edge` 按当前状态选下一步。例如"生成报告 → 校验 → 通过则成功 / 失败则带错误重生成 / 超限则失败"。判断顺序：先判是否通过，再判修改次数是否耗尽；最后一次修改若已合格应成功结束。

### 8.4 并行执行与 Reducer

互不依赖的节点可并行（如两份资料同时获取再汇总）。多个节点写**不同字段**可各自更新；同一步写**同一字段**需定义合并规则（Reducer，如把新数组追加到已有数组）。并行节点读的是该步开始时的状态，不能把 State 当实时全局变量。消息可用 `MessagesValue`（内置追加/按 ID 更新）。

### 8.5 Checkpoint 持久化

`Checkpoint / Checkpointer` 记录与恢复执行状态，`thread_id` 标识一段会话/任务上下文。先用 `MemorySaver` 理解延续，再换 PostgreSQL 保存器实现"程序退出后数据仍在、不同会话不串"。

### 8.6 Human-in-the-loop

`interrupt()` 在指定位置暂停等人输入，`Command({ resume })` 提交后从检查点恢复。恢复时相关节点会从函数开头重跑，因此**幂等性**很关键：已成功的操作（如保存报告）重复恢复不应再产生一次。

### 8.7 多 Agent 与子图

职责需要独立模型决策/工具/上下文时才拆 Agent（如研究 Agent 与写作 Agent），简单数据校验保留为普通函数节点即可。`Subgraph` 把一段完整流程作为另一张图的节点，父子图通过共享字段或包装节点通信。

## 9. MCP：把工具标准化暴露给 Agent 与外界

### 9.1 MCP 解决什么：站在 Tool Calling 上一层

MCP（Model Context Protocol，模型上下文协议）为"应用与外部工具、数据之间的交互"提供统一约定。它不替你写业务逻辑，只负责让调用方以统一方式发现能力、调用能力、交换上下文。与 Tool Calling 的区别：Tool Calling 解决"模型怎么表达要用的工具和参数"，MCP 解决"应用怎么发现、调用外部能力并交换上下文"——后者站在前者上一层。

### 9.2 Host / Client / Server 三角色

Host 承载对话和模型调用并决定如何使用工具结果；Client 连接服务、发现并调用工具；Server 提供 `get_weather` 这类能力。接入 Agent 时，Host 是 NestJS 应用，MCP Client 是其组件，天气 Server 是独立程序。模型只负责"调什么、传什么"，真正发送调用、接收结果并放回对话的是应用程序。

### 9.3 三类能力：Tools / Resources / Prompts

MCP 服务可提供三类能力：Tools 是可执行操作（调用 `get_weather`）；Resources 是应用可读取的上下文数据（读取 `weather://supported-cities`）；Prompts 是可复用消息模板。Resources 需应用读取并按需加入上下文，Prompts 不会自动调用模型。

### 9.4 两种传输：stdio 与 Streamable HTTP

MCP 把消息约定（JSON-RPC 2.0）与传输分离。stdio 让客户端启动子进程、通过输入输出流交换消息，适合本地工具与调试；Streamable HTTP 适合远程部署、供多应用访问。本文用 stdio，不需要 Express、不监听端口。

### 9.5 写 Server：registerTool + stdio

`server.registerTool(name, meta, impl)` 注册工具名称、说明、参数（`inputSchema` 用 `z.enum` 限定城市，SDK 据此生成 JSON Schema 并在执行前校验）。业务函数 `getWeather(city)` 仍是普通函数，换提供方主要改它，对外保持 `get_weather` 接口。通过 `StdioServerTransport` 通信；`console.error` 写日志、`console.log` 会破坏协议流；`AbortSignal.timeout` 防无限等待；失败返回 `isError: true`。

### 9.6 用 Inspector 做 Tool Discovery / Tool Call

官方 MCP Inspector 可在无模型密钥下验证工具：`tools/list` 做 Tool Discovery（结果含 `get_weather` 及说明/参数），`tools/call` 调西安天气。先 `pnpm run build` 生成 `dist/server.js`。

### 9.7 写 Client：connect / listTools / callTool

`client.connect(transport)` 启动 Server 子进程并建立通信；`listTools()` 取工具清单；`callTool(...)` 调用并取结果；`finally` 中 `close()` 释放连接与子进程。`process.execPath` + 相对路径计算避免依赖终端目录。

### 9.8 接到 Agent：MCP Client 放在调用工具的节点

接入模型后，城市与调用时机由模型提出，应用检查并执行：获取工具列表 → 转成模型工具定义 → 交模型 → 模型提 `get_weather` → 应用经 MCP Client 执行取结果 → 作为工具消息回灌 → 模型继续。LangGraph 组织步骤，MCP Client 放在调用工具的节点；循环次数、超时、成本、人工审核仍由应用控制。Server 不调模型、不需要密钥，密钥在 Host 配。
