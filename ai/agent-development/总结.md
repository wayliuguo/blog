## 1. Agent 是什么与 LLM 接入

### 1.1 Agent 到底是什么：LLM 参与决策

普通大模型应用是「程序员写规则」：`if/else` 决定程序走向；Agent 的分界线是 **LLM 开始参与决定程序下一步做什么**。一个最基础的 Agent = LLM + Tools + Context + Agent Loop + Stop Condition。

```
普通应用：  User → 程序(if/else) → 结果
Agent：     User → LLM → 决策 → Tool → 执行 → Observation → LLM → ...
```

### 1.2 架构决策：把 Agent 和 LLM 拆开

Agent 本质是运行在服务端的软件系统。第一步把「调用模型」独立成 `LlmModule`（依赖注入、`exports` 暴露 `LlmService`），Agent 行为放 `AgentModule`，做到模型厂商与 Agent 解耦：OpenAI SDK + `baseURL` 指向兼容网关，换 DeepSeek / OpenAI 不推倒重写；Key 走环境变量，不进代码。

### 1.3 messages 与 Context：多轮对话的本质

`messages` 就是模型这一次能看到的 Context，角色有 `system / user / assistant / tool`。API 每次调用无状态——「多轮对话」首先是 Context 管理问题：历史必须重新放进 `messages`。Context Window 有上限，一轮放什么（System + Tool 定义 + 历史 + 记忆 + 当前消息）是后续所有 Context 工程的起点。

### 1.4 Structured Output：让自然语言进入程序逻辑

链路：自然语言 → LLM → JSON → 程序对象 → 行为。优先用 API 自带 `response_format: { type: 'json_object' }`。三个坑：① JSON String 不是 JavaScript Object（`content` 本质是字符串）；② 只靠 Prompt 要求「请返回 JSON」不可靠（模型会包一层「好的，结果是：」）；③ 合法 JSON ≠ Schema 正确，`as` 断言只是编译期把戏。

### 1.5 用 Zod 收口：运行时校验才是底线

类型（`type`）与校验（`parse`）必须分开：`JSON.parse(content) as IntentResult` 运行时零检查。正确链路是 `LLM → Structured Output → JSON → Zod Schema → 校验 → TS 对象`。LLM 输出永远按不可信外部数据处理。

### 1.6 第一次让 LLM 参与程序决策，以及 switch 的天花板

用 Structured Output 解析出 `intent`，`switch (intent)` 分发到不同行为——这是 LLM 第一次参与决策。但加一个意图就要加一个 case，扩展性受限；要让模型直接选择「程序能力」，就进入下一篇 Tool Calling。

## 2. Tool Calling：让 LLM 直接调用程序

### 2.1 为什么有了 Structured Output 还要 Tool Calling

Structured Output 是「模型描述意图，程序决定下一步」；Tool Calling 是「模型直接选择程序能力 + 生成参数，程序直接执行」。两者必须彻底分开：用了 `tools` 就不要再带 `response_format: json_object`。

### 2.2 Tool Schema：模型怎么知道有哪些 Tool

工具以 OpenAI 兼容的 `function` schema 描述：`name / description / parameters(JSON Schema)`。请求里带 `tools` 数组 + `tool_choice: 'auto'`；`description` 是模型选工具的依据，写得准不准直接决定调用质量。

### 2.3 解析与执行：tool_calls、Type Narrowing 与「不一定调用」

模型返回 `tool_calls: [{ name, arguments(JSON 字符串) }]`——该解析的是 `toolCall.function.arguments`，不是 `content`（后者 `JSON.parse` 会报 `Unexpected token '我'`）。模型不一定每次都调用工具：无 `tool_calls` 时 content 直接当答案。SDK 类型需要 Type Narrowing 判空。

### 2.4 Tool Result 回灌 Context：assistant 与 tool 两条消息

执行完工具后要回灌两条消息：**assistant 消息（原样保留，含 tool_calls）+ tool 消息（带 `tool_call_id` 对应结果）**，再发起第二次调用，模型综合结果给出最终回答——单轮闭环完成。

### 2.5 十步链路：单轮撑不起依赖链

完整链路：定义 Tool → 随请求下发 schema → 模型选工具 → 解析 `tool_calls` → 执行 → 回灌 assistant + tool 两条消息 → 二次调用 → 得到答案。但一轮只够「问一句答一句」，「查 A 的结果拿去查 B」这类依赖链需要循环——进入 Agent Loop。

## 3. Agent Loop：会循环的运行时

### 3.1 Agent Loop 的本质：一个循环 + 最大次数

Tool Calling ≠ Agent。Loop 就是把「模型决策 → 执行工具 → 结果回灌 → 再调模型」循环到模型不再返回 `tool_calls`。必须设 `MAX_ITERATIONS`：防模型无限循环调用（死循环烧钱）。

```
while (未达上限) {
  const r = await llm()
  if (!r.tool_calls?.length) return r.content
  await executeTools()   // 执行并把结果放回 messages
}
```

### 3.2 while 管多轮、for 管一轮：第一版 Loop 与两个坑

`while` 管「多轮循环」，内层 `for` 管「一轮里的多个 tool_call」。两个坑：① Tool 一定要 `await`（漏了会把 Promise 当结果回灌）；② `assistantMessage` 必须先入栈再执行工具——回灌时 assistant 消息缺失，API 直接报错。

### 3.3 统一 AgentTool 协议与 Tool Registry

工具一多 `if` 分发失控。统一协议四要素：`name / description / schema / execute()`；Registry 是一张 `Map<string, AgentTool>` + `invoke(name, args)`。工具定义（schema 给模型看）与实现（execute 给程序跑）彻底分开。

### 3.4 Zod 校验：一份 Schema 两处用

LLM 参数是运行时数据，TS 类型管不住。用 zod 定义参数 schema：转 JSON Schema 给模型、`parse` 校验入参，Single Source of Truth。Registry 的 invoke 收口四步：查表 → 校验 → 执行 → 格式化结果。

### 3.5 错误即观察：Action 与 Observation

工具执行失败不抛 HTTP 500——把错误文本作为 Observation 回灌给模型，让它重试、换参数或放弃。失败不等于 Agent 失败，这是 Agent 与传统后端的核心区别。

### 3.6 手写组件对应框架的什么概念

`LlmService` → LangChain `ChatOpenAI`；`AgentTool` → `tool()`；Registry → 保留；`MAX_ITERATIONS` 循环 → LangGraph 的图循环。先手写再学框架，框架才不是黑盒。下一步：让 Agent 拥有 Memory。

## 4. 上下文与记忆：让 Agent 记住对话

### 4.1 为什么不能全量发送：`slice(-20)` 会切断消息链

历史无限增长会撑爆窗口、烧钱、降质。第一直觉 `messages.slice(-20)` 是错的：它按条数切，会把一条交互拦腰斩断（assistant 带 tool_calls 进来了，对应的 tool 结果被切掉），API 报错。

### 4.2 按 Conversation Round 裁剪：Safe Trimming

一次 `user` 触发的连续交互（含中间 `assistant(tool_calls) / tool / assistant`）算一轮。`trimMessages(messages, maxRounds)` 的核心是「遇到 `user` 就开新轮」，从后往前保留最近 N 轮——保证任何轮内部完整。

### 4.3 ConversationStore 与 ContextManager 分层

**Store 负责「保存完整对话」，Manager 负责「这次给 LLM 看什么」**。调用链恒定：`Store(完整历史) → Manager(筛选组装) → LLM`。以后加摘要、加记忆、加 RAG，都只是给 Manager 增加新的组装来源。

### 4.4 Rolling Summary：旧历史压摘要，近期留原文

Trimming 的残留问题：早期轮次里的约束（「项目用 pnpm」「别用 any」）被裁掉后模型就忘了。Rolling Summary 把被裁的旧历史交给 LLM 压成一段摘要注入 System，近期轮留原文；随对话推进摘要「滚动」更新。Summary 与 Trimming 互补而非二选一。

### 4.5 Summary 不等于 Memory：MemoryExtractor 与 upsert

换一个会话 Summary 就没了——跨会话沉淀靠 Memory。但不是所有聊天都值得记（全存=垃圾场）。MemoryExtractor 在每轮回答后跑一次（本质是 Structured Output：返回 `{ memories: [...] }`），值得记的走 `MemoryStore.upsert()`——同一类记忆会变（用户换了主力语言），按 key 覆盖而不是无限追加。

### 4.6 Memory Injection 与跨会话验证

存了不用等于没做：每轮组装 Context 时把相关 Memory 注入 System。验证方式：换一个 `conversationId` 继续对话，上一会话沉淀的偏好仍然生效。

### 4.7 四个概念：History / Context / Summary / Memory

History 是完整原始消息（Store 里）；Context 是这一轮实际发送的（Manager 组装）；Summary 是 History 的压缩替身；Memory 是跨会话的结构化沉淀。短期记忆（History+Trimming+Summary）随会话消失，长期记忆（Memory+向量库）跨会话存活。

## 5. Embedding 与向量检索：长期记忆的持久化

### 5.1 Embedding 是什么：把语义变成一组数字

旧方案把用户全部 Memory 塞进上下文——撑爆窗口。Embedding 把文本语义映射为向量：语义越近，向量越近。字符串匹配不行：「登录凭证多久失效」与「Refresh Token 有效期 30 天」没有共同关键词但语义相近。

### 5.2 手写余弦相似度与内存 VectorStore

`cosineSimilarity(a, b) = dot / (|a|·|b|)`，越接近 1 越相似。内存 VectorStore = 数组 + 全量遍历取 TopK——暴力但包含向量检索的全部思想。

### 5.3 EmbeddingProvider 抽象与真实 Provider

业务依赖 `EmbeddingProvider` 抽象而非具体模型。推理模型与 Embedding 模型是两回事：DeepSeek 只管对话、不做 Embedding；Embedding 要单独的模型与**独立的凭证**——两套 Key 混用报 `Missing credentials`。

### 5.4 pgvector 持久化：建表、检索与三个坑

进程一死内存库全丢，生产用 PostgreSQL + pgvector（`vector(n)` 类型）。三个坑：① `5432/tcp` 是容器暴露端口不是宿主映射；② SQL 里 `<=>` 算的是余弦**距离**，`1 - distance` 才是相似度，方向相反；③ 连不上时错误码从 P1013（认证）变 P1001（不可达），错误码变化就是排查进度。检索 SQL：

```
SELECT content, 1 - (embedding <=> $1::vector) AS similarity
FROM "UserMemory" WHERE embedding IS NOT NULL
ORDER BY embedding <=> $1::vector LIMIT $2;
```

### 5.5 MemoryRepository / MemoryService：语义检索接入 Agent

Repository 收口参数化 Raw SQL（存文本 + 回写向量）；Service 组合 Embedding + Repository。Agent 每轮注入的从「全部记忆」升级为「相关记忆 TopK」：`System + 相关记忆 TopK + 摘要 + 近期 + 当前`。

## 6. RAG：从 0 手写企业级知识库

### 6.1 RAG 是什么：先检索、后生成

RAG = Retrieval-Augmented Generation：用户问题 → 检索相关资料 → 作为 Context 交给 LLM → 基于资料回答。RAG 是能力不是调用形式：可独立成链路，也可包装成 `search_knowledge` Tool 交给 Agent 自主调用。

### 6.2 数据模型与向量写入：Document / Chunk / `::vector`

Document（文档级，含状态/版本/校验和）与 DocumentChunk（片段级，含向量）两级模型。pgvector 写入：向量以 `'[0.1,0.2,...]'` 字符串形式传参、`::vector` 显式转型。检索分数 `0.6184` 不是「61.84% 的把握」，只是距离算出的分数。

### 6.3 Ingestion Pipeline：Loader 与 Parser 分离

企业知识库不能手工建 Chunk。Loader 做「文件 → 文本」（`supports()` 判断格式 + `load()` 读内容，插件式扩展）；Parser 做「文本 → 结构」（Markdown 标题层级 → sections）。分开后换格式只加 Loader、换解析策略只动 Parser。

### 6.4 Token-aware 切块：标题路径 + 逐级降级 + 硬切兜底

`maxChunkLength = 500` 按字符切是错的：500 characters ≠ 500 tokens。按 Token 计数切块（近似：中文 ≈ 1 token/字，英文 ≈ 0.25 token/字符）；超限时逐级降级「段落 → 句子 → 字符硬切」；每个 Chunk 拼上标题路径（`# 手册 → ## 制度 → 内容`），离开原文仍是可独立理解的语义单元。

### 6.5 Chunk 字段与完整入库：checksum 去重 + 事务

`content` 供 Embedding、`heading/section` 供上下文、`chunkIndex` 支撑 Neighbor Retrieval、`tokenCount` 算 Budget、`metadata` 供 Filter/Debug。入库流水线用 checksum 判断内容是否变化（没变就跳过）；写入包在事务里——Embedding 在事务外（API 慢且幂等），**数据库写入在事务内**：100 个 Chunk 嵌到第 57 个失败就整体 ROLLBACK，不留半成品。只有 `COMPLETED` 状态的文档才参与检索。

### 6.6 文档版本管理：isActive 与版本切换事务

Checksum 解决不了「同一 documentKey 的文档内容合法更新」：靠 `version` 递增 + `isActive` 标记生效版。切换必须放进事务：先建新版本（COMPLETED），再下线旧版本——新旧两版绝不能同时参与检索。

### 6.7 向量检索、阈值与进阶方向

相似度阈值（如 `> 0.6`）不能拍脑袋，要靠 Retrieval Evaluation 得出。进阶：Hybrid Search（向量 + BM25）、Rerank、Metadata Filter、权限过滤、Neighbor Retrieval、异步 Ingestion、PDF/DOCX 解析。手写完再看 LangChain 的 `asRetriever()`——背后没有魔法。

## 7. LangChain：用框架重写一遍 Agent

### 7.1 为什么先手写再学框架：映射表

不先手写，框架的每个抽象都会变成「答不上来为什么」。映射：`LlmService`→`ChatOpenAI`、裸 messages→`SystemMessage/HumanMessage/AIMessage/ToolMessage`、`AgentTool`→`tool()`、`EmbeddingProvider`→`Embeddings`、`VectorStore/Retriever`→同名抽象。

### 7.2 封装 LLM / Message / tool()

`chat.completions.create()` → `model.invoke()`；消息从裸对象升级成类但本质没变；`tool()` 把 `name / description / schema / execute` 统一封装，ToolRegistry 继续保留管理工具集合。

### 7.3 bindTools 不自动执行：Loop 还是要自己写

全篇最大误解：`bindTools(tools)` 只是把工具描述提供给模型，**不自动执行**。Loop 仍要手写：`invoke` → 解析 `tool_calls` → 逐个执行 → 带 `tool_call_id` 的 `ToolMessage` 回灌 → 再 `invoke`。未知工具与执行异常都必须作为 ToolMessage 回填，不能只走成功分支。Tool 执行外部进程不要拼 shell 命令——用 `execFile` + `promisify` + `timeout`，参数数组化天然避开注入。

### 7.4 RAG 作为 Tool：确定性逻辑交 Tool，知识交 RAG，决策交 LLM

`retriever.invoke()` 背后就是我们手写的向量检索。System Prompt 是执行规则不是人设（如安全分析场景要明确「不能仅凭 exported 判漏洞」）——不要把所有判断都丢给模型。

### 7.5 Structured Output 与最重要的坑

`withStructuredOutput(zodSchema)` 一行顶「构造请求 + JSON.parse + 校验」三步。最重要的坑：**不要用它直接替换 Agent Loop**——结构化报告放在调查阶段之后单独整理，Loop 的多轮工具调用不能省。

## 8. LangGraph：有状态的流程编排

### 8.1 LangChain 与 LangGraph 的关系：配合，不是二选一

LangChain 的 `createAgent()` 本身构建在 LangGraph 之上。现成流程用 LangChain；需要明确的有状态流程（先做什么、何时重试、在哪等人、退出后怎么继续）直接用 LangGraph。

### 8.2 State / Node / Edge：组装顺序 ≠ 执行顺序

State 是任务数据（更新遵循图规则）；Node 读状态、执行、返回要更新的字段；Edge 决定去哪（固定边 / 条件边）。**真正决定执行顺序的是边的连接**，`.addNode().addEdge()...compile()` 只是组装，`invoke()/stream()` 才启动。

### 8.3 把 Agent Loop 放进图里：双节点循环与三个限制

Agent Loop 变成「model 节点 ↔ tools 节点」的图循环 + 条件边出口。三个易混的限制：**自维护工具轮数**（业务允许几轮）、**`recursionLimit`**（图运行的超级步数上限）、**`maxRetries`**（模型请求失败自动重试）——约束不同层次，不能互相替代。

### 8.4 条件边与并行 Reducer

条件边按状态选下一步（校验通过 → 成功；失败且未超限 → 修改重生成；超限 → 失败终态）。互不依赖的节点可并行；写**同一字段**需定义 Reducer 合并规则（如数组追加）；并行节点读的是该步开始时的状态快照。

### 8.5 interrupt / Checkpoint / 恢复：HITL 完整时序

实战主线「生成计划 → 校验分支 → `interrupt()` 暂停人工审核 → `Command({ resume })` 恢复」。Checkpointer 每步存状态（先 `MemorySaver` 理解、后 Postgres 持久化），`thread_id` 标识任务——程序退出后凭同 `thread_id` 恢复，不同 `thread_id` 不串。恢复时节点从函数开头重跑，**写操作必须幂等**。

### 8.6 流式输出与学习路线

`streamMode` 三种：`values`（每步后全量状态）/ `updates`（每步增量）/ `messages`（token 级流式）。学习路线按小闭环推进：图基础 → Agent 循环 → 业务流程 → 并行 → 持久化 → 人工参与 → 多 Agent → 调试 → 工程验证。

### 8.7 多 Agent 与子图：什么时候才拆

职责需要独立的模型决策/工具/上下文时才拆 Agent（研究 Agent 与写作 Agent）；简单校验保留为普通函数节点。Subgraph 把一段完整流程作为另一张图的节点，父子图通过共享字段通信。

## 9. MCP：把工具标准化暴露给 Agent 与外界

### 9.1 M×N 困境与 MCP 是什么：AI 应用的 USB-C

M 个应用 × N 个工具 = M×N 份接入胶水代码。MCP（Model Context Protocol）把工具实现一次成 Server，任何支持协议的应用即插即用，M×N 变 M+N；协议基于 JSON-RPC 2.0。

### 9.2 Host / Client / Server 三角色与三类能力

Host 承载对话与模型调用；Client 与 Server 保持 1:1 连接；Server 声明并执行能力。Server 不接触 LLM，「要不要调、怎么拼进 Context」是 Host 的事。三类能力：Tools（模型触发）/ Resources（应用拉取）/ Prompts（用户选择）。

### 9.3 stdio 传输与踩坑：console.log 会破坏协议流

本地工具选 stdio（子进程 + 标准输入输出，零网络配置）；远程共享选 Streamable HTTP。**stdio 管道上禁止 `console.log()`**——会混入 JSON-RPC 消息流破坏通信，普通日志一律 `console.error`。

### 9.4 写 Server：registerTool + zod 校验

`McpServer.registerTool(name, { description, inputSchema }, handler)` 三步把普通函数变协议工具；zod schema 转 JSON Schema 下发并自动校验入参（`z.enum` 收敛合法城市）。工具失败返回 `isError: true` + 文本原因，让模型把失败当观察；外部调用加 `AbortSignal.timeout` 兜底。

### 9.5 写 Client：connect / listTools / callTool

四步：构造 `Client` → `connect(transport)` 拉起 Server 子进程并握手 → `listTools()` 发现工具（返回的描述就是给 LLM 的 Function 定义）→ `callTool()` 调用。`finally` 里 `close()` 释放连接与子进程。

### 9.6 Inspector 调试与接入 Agent

`npx @modelcontextprotocol/inspector` 免写 Client 即可图形化验证工具发现与调用。接入真 Agent：`listTools()` 结果转成模型工具定义，模型回 `tool_calls` 后由 Host 执行——MCP 没有替代 Function Calling，替换的是**工具的分发与接入层**。
