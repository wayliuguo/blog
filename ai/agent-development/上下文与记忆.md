# 上下文与记忆：让 Agent 记住对话

## 为什么不能把所有聊天记录都发送给 LLM

上一篇的 Agent 已经能多轮对话了，但实现方式很朴素：维护一个 `messages` 数组，每次用户提问时「读取全部历史 → 追加新的 user 消息 → 全部发给 LLM」。短对话没问题；对话增长到 100 轮、1000 轮时，三个问题同时爆发：

```
Token 消耗越来越高 → 请求越来越慢 → 最终超过模型上下文窗口
```

这里要建立本篇第一个架构思想：

> **Conversation History ≠ LLM Context**——数据库里可以保存完整聊天记录（Storage），但不意味着每次调用 LLM 都要发送全部记录（Context）。

## 第一直觉是错的：`slice(-20)` 会切断消息链

最直接的裁剪方案是 `messages.slice(-20)`——只保留最后 20 条。看起来合理，实际上有致命缺陷：Agent 的 Tool Calling 消息存在**配对关系**，不能从中间切断：

```
assistant（tool_calls: id=call_001, get_weather）
tool（tool_call_id: call_001）        ← slice 恰好从这里截断
assistant（最终回答）
```

如果 `slice` 的起点落在 `tool` 消息上，前面的 `assistant(tool_calls)` 已被删除——模型收到一条「没有来源的结果」，消息链不完整。**裁剪单位必须从「消息条数」升级为「对话轮次」。**

## 按 Conversation Round 裁剪：Safe Trimming

先定义什么算「一轮」（Round）：

```
普通对话：        user → assistant
有 Tool Calling： user → assistant(tool_calls) → tool → assistant
一次调多个工具：  user → assistant(tool_calls) → tool → tool → assistant
```

核心判定思想：**遇到 user 消息，就开启一个新 Round**。裁剪时整轮整轮地丢，永远不会从 tool 消息中间断开：

> 摘自 `code/context-memory/context-manager.ts`

```ts
// 按"完整对话轮次"裁剪历史：一轮 = 一次 user 触发的连续交互。
export function trimMessages(messages: Message[], maxRounds = 5): Message[] {
  const rounds: Message[][] = []
  let current: Message[] = []
  for (const message of messages) {
    if (message.role === 'user') {
      if (current.length > 0) rounds.push(current)
      current = [message]
      continue
    }
    current.push(message)
  }
  if (current.length > 0) rounds.push(current)
  return rounds.slice(-maxRounds).flat()
}
```

`rounds.slice(-maxRounds)` 保留最近几轮时，**一定从完整的 user 消息开始**——这就是 Safe Context Trimming。

## ConversationStore 和 ContextManager 必须分开

功能变多之后，职责必须分层：

- **ConversationStore** 负责「保存 Conversation」——完整历史，一条不丢；
- **ContextManager** 负责「决定这次到底给 LLM 看什么」——筛选、裁剪、拼装。

调用链固定为：

```
ConversationStore → 完整 Conversation History → ContextManager → 筛选后的 Context → LLM
```

如果把「存历史」和「筛上下文」混在一个模块里，后面加 Summary、Memory、Token Budget、RAG Context 时就没法扩展了。ContextManager 未来就是**唯一的上下文构建入口**，最终产出 Final LLM Context。

## 只做 Trimming 还是有问题：旧约束会被裁掉

用具体场景制造矛盾：第一轮用户说「我要带一个 6 岁的小朋友去西安玩」，连续聊了 20 轮之后问「那你最终推荐哪个地方？」。

只保留最近 5 轮的话，「6 岁的小朋友」这条关键约束早被裁掉了——模型可能推荐不适合儿童的地点。结论：**旧消息不能全部保留，也不能简单全部删除**。答案是第三条路：**Conversation Summary**——把被裁掉的旧历史压缩成摘要，继续放进 Context。

## Rolling Conversation Summary：旧历史压摘要，近期留原文

Summary 方案把历史分成两部分：

- **旧历史** → 压缩成 Summary；
- **最近几轮** → 保留原始 Messages。

最终给 LLM 的 Context 变成：`System Prompt + Conversation Summary + Recent Messages + Current User Message`。用 6 轮对话、`KEEP_RECENT_ROUNDS = 3` 演算：

```
Round 1~3 → 压缩成摘要：「用户正在计划西安亲子旅行，同行有一名 6 岁儿童……」
Round 4~6 → 原文保留
```

配套脚本实现了这个流程（摘要器注入，mock 脱离 API 运行）：

> 摘自 `code/context-memory/rolling-summary.ts`

```ts
// Rolling Summary：把装不下的旧轮次压成一段摘要注入 System，
// 与保留的近期轮次拼回，构成「System + 摘要 + 近期」的 Context。
export async function buildContextWithSummary(
    messages: Message[],
    keepRounds: number,
    summarize: Summarizer,
    systemPrompt = '你是一个专业的 AI Agent 助手。'
): Promise<Message[]> {
    const rounds = splitRounds(messages)
    if (rounds.length <= keepRounds) {
        return [{ role: 'system', content: systemPrompt }, ...messages]
    }
    const oldRounds = rounds.slice(0, rounds.length - keepRounds)
    const recent = rounds.slice(-keepRounds).flat()
    const summary = await summarize(oldRounds.flat())
    return [{ role: 'system', content: `${systemPrompt}\n\n已知背景摘要：\n${summary}` }, ...recent]
}
```

`Summary + Recent Messages` 同时兼顾了长期上下文与近期精确细节。

## 为什么叫「Rolling」（滚动式）摘要

对话继续增长怎么办？关键约束：**不能每次重新总结全部历史**——否则 Summary 这一步自己会越来越贵，机制失效。正确做法是增量滚动：

```
第一次：        Round 1~3 → Summary A
对话增长后：    Summary A + 新的旧历史 → Summary B
（而不是）      Round 1~100 → 全量重总结
```

正确结构是 `Old Summary + New Old Messages → New Summary`——摘要滚动更新，成本恒定。

## ConversationState 也要升级：给 summary 一个位置

功能变了，数据结构必须跟着升级。以前 ConversationState 只有 `messages`，现在要加 `summary` 字段：

> 示意片段（无配套脚本）

```ts
interface ConversationState {
  messages: ChatCompletionMessageParam[]
  summary?: string    // 新增：被压缩的旧历史
}
```

历史达到阈值后的完整维护流程：

```
Old Messages → LLM Summary → 更新 summary → 删除已被压缩的原始历史 → 只保留 Recent Messages
```

这样 Conversation 本身就不会无限增长。

## Summary 和 Trimming 是互补关系，不是二选一

这两个概念很容易被当成互相替代的方案，实际是同时存在、各管一段：

| 机制 | 负责什么 |
| ---- | ---- |
| Trimming | 决定哪些**最近的原始消息**继续保留 |
| Summary | 决定**被裁掉的旧消息**里，有哪些重要信息不能忘 |

`Summary + Recent Messages` 才是比较完整的 Context Management。

## Summary 不等于 Memory：换一个会话就失效

第三层矛盾来了。用户说「以后给我写 TypeScript 代码不要使用 any」——当前 Conversation 靠 Summary 能记住；但一旦新开会话（`conversationId` 从 001 换成 002），**新 Conversation 没有之前的 Summary**，长期偏好又丢了。

一句话区分两个绑定维度：

> **Conversation 绑定 `conversationId`，Memory 绑定 `userId`。**

```
User
├── Conversation A（Summary + Messages）
├── Conversation B（Summary + Messages）
└── Long-term Memory（Preferences / Profile / Projects）
```

请求体从此要带两个 ID，职责严格区分：`conversationId` 找当前聊天上下文；`userId` 找用户长期 Memory。

## Memory 不能直接保存所有聊天记录：垃圾场问题

提前踩坑预警：错误做法是「所有 User Message → 全部存 Memory」。很快会变成垃圾场——「你好」「西安今天多少度？」「谢谢」这类内容没有长期保存价值。真正值得进 Memory 的是：

```
「以后 TypeScript 不要使用 any」
「我后端主要使用 NestJS」
「我现在长期在做 Agent 开发项目」
```

所以定义是：**Memory 是从 Conversation 中提取出来的长期有价值信息**——需要一个专门的提取环节：**Memory Extractor**。配套脚本用规则 mock 演示提取逻辑：

> 摘自 `code/context-memory/memory-extractor.ts`

```ts
// mock 版提取器：只有带「以后 / 不要 / 喜欢 / 记住」等信号词的用户输入才值得提取；
// 「西安今天多少度」这类即时问题返回空数组——不是所有对话都有长期价值。
export function extractMemories(userMessage: string): ExtractedMemory[] {
    const memories: ExtractedMemory[] = []
    if (/以后.*(不要|要|用)/.test(userMessage) || /(喜欢|记住)/.test(userMessage)) {
        memories.push({
            type: 'preference',
            key: `pref_${userMessage.length}`,
            value: userMessage
        })
    }
    return memories
}
```

真实实现由 LLM 担任「是否有长期价值」的判断者，返回 `{ memories: [...] }` 结构，`type / key / value` 是记忆的三元组；无价值时返回空数组。

## 用 Zod 约束提取结果：模型输出依然是不可信输入

模型返回的是字符串，直接用会绕过类型安全。用 Zod 做运行时校验，并让类型从 Schema 推导：

> 示意片段（无配套脚本）

```ts
const ExtractedMemorySchema = z.object({
  type: z.enum(['preference', 'profile', 'project']),
  key: z.string().min(1),
  value: z.string().min(1),
})
const MemoryExtractionSchema = z.object({
  memories: z.array(ExtractedMemorySchema),
})
export type MemoryExtractionResult = z.infer<typeof MemoryExtractionSchema>
```

`z.infer` 保证运行时校验与编译期类型来自同一份定义——运行时、编译时双重约束。

这条「Prompt 约定 → JSON.parse → Zod 校验」是第一版提取链路，能用但不健壮——JSON.parse 挡不住模型偶尔夹带的自然语言。更稳的做法是第 1 篇用过的 Structured Output（`response_format: json_object`）：在协议层强制模型只返回 JSON，Zod 再做最后一道校验。

## MemoryStore 为什么需要 upsert：同一类记忆会变

Memory 与聊天记录最大的区别之一：**Memory 会变化**。用户先说「后端主要使用 NestJS」，后来改口「这个项目改用 Fastify」——此时不能同时存在两条互相冲突的记忆。所以写入用 **upsert**：以 `type + key` 判定同一类记忆，存在则 UPDATE，不存在则 INSERT。简单 append 会让同一 key 的新旧记忆冲突共存。配套脚本用内存 Map 演示：

> 摘自 `code/context-memory/memory-extractor.ts`

```ts
// MemoryStore：长期记忆的落点。真实实现用 upsert（type+key 唯一）写入
// user_memory 表并生成 embedding（见第 5 篇）；这里用内存 Map 演示。
export class MemoryStore {
  private items = new Map<string, ExtractedMemory>()

  upsert(memory: ExtractedMemory): void {
    // Map 键用 type:key 复合——不同 type 的同 key 记忆互不覆盖，
    // 与真实表的 @@unique([userId, type, key]) 唯一约束对齐。
    this.items.set(`${memory.type}:${memory.key}`, memory)
  }

  all(): ExtractedMemory[] {
    return [...this.items.values()]
  }
}
```

## Memory Injection：存了不用等于没做

最后一块拼图：即使 MemoryStore 里已经存了 `typescript_no_any`，**如果下次调用 LLM 时没放进 Context，LLM 还是不知道**。每次 Agent 执行前读取该用户的 Memory，构造 Long-term Memory Context 注入。至此最终的五层 Context 成型：

```
System Prompt
→ Long-term Memory
→ Conversation Summary
→ Recent Messages
→ Current User Message
→ LLM
```

## 跨会话验证：换了 conversationId，记忆还在

端到端验证整条链路，用两个不同的 conversationId：

```
第一次：conversation-001「以后给我写 TypeScript 代码时不要使用 any」
        → Extractor 提取出一条 preference 记忆（key 形如 pref_25，见 `npm run memory-extract` 实跑读数）
第二次：conversation-002（新会话）「帮我写一个 NestJS Tool」
        → 根据 userId 加载 Memory → 注入 Context → LLM 遵守旧偏好
```

验证要点：`conversationId` 已变化，但 `userId` 没变。**Memory 的生命周期由 userId 决定，与 conversationId 无关**——会话换了、记忆还在，才算真正打通。

## 四个最容易混的概念：History / Context / Summary / Memory

本篇最大的收获不是多写了几个 Service，而是区分开四个特别容易混淆的概念：

| 概念 | 是什么 | 生命周期 |
| ---- | ---- | ---- |
| Conversation History | 当前会话的原始聊天记录 | 绑定 conversationId，永久保存 |
| Context | 这一次真正发送给 LLM 的信息 | 每次调用现拼 |
| Summary | 当前会话被压缩后的旧历史 | 绑定 conversationId |
| Memory | 跨会话的长期重要信息 | 绑定 userId |

正确的关系链：

```
Conversation History → Trimming + Summary ┐
                                          ├→ ContextManager → Final LLM Context
Long-term Memory     → Memory Retrieval   ┘
```

## 架构演进总图

从第 1 篇到现在，Agent 的完整架构已经长成这样：

```
User Request → AgentService
                 │
        ┌────────┼──────────────┐
        ▼        ▼              ▼
ConversationStore  MemoryStore  MemoryExtractor
 Summary+Messages   Long-term Memory（提取自对话）
        └────────┬──────────────┘
                 ▼
           ContextManager（唯一入口）
                 │ Final LLM Context
                 ▼
               LLM ⇄ Tools（Tool Result 回流）
                 │
          Final Answer → Memory Extractor 写回 MemoryStore
```

Agent 开发远远不只是「让大模型调用几个函数」——Tool Calling 只是其中一个能力。状态怎么保存、上下文怎么控制、旧历史怎么压缩、什么值得长期记、跨会话怎么共享、哪些记忆进本次 Context——每一个都是独立的工程问题。
## 下一步：让记忆可被语义检索

现在的 Memory Injection 是「取出该用户的全部记忆注入」——记忆少时够用，多了就会撑爆 Context。让 Agent 只拿到「与当前问题相关的记忆」，需要把 Memory 文本变成向量、按语义相似度检索——这正是下一篇 Embedding 与向量检索要解决的问题。
