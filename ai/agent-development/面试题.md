# 模块面试题 · Agent 开发

> 岗位设定：**Agent 开发工程师（后端 / 应用视角）**——不要求你训练模型，要求你能把"LLM + 工具 + 循环 + 记忆 + 检索"用对、用稳，并能在一个项目里把它落地成可维护的系统。
> 题目按知识体系章节分组，每题走「判断 → 展开 → 佐证 → 边界」四槽，便于模拟面试时照着追问。

---

## 1. Agent 是什么与 LLM 接入

### Q1（1.1）｜ Agent 和 LLM 是什么关系？
- **判断**：LLM 是 Agent 的核心组件，但 LLM 本身不等于 Agent。一个最基础的 Agent = **LLM + Tools + Context + Agent Loop + Stop Condition**。
- **展开**：普通 LLM 应用是"用户 → LLM → 答案"单向链路；Agent 多出"LLM 决策 → 选工具 → 执行 → 结果回灌 → 再判断"的循环，让"调用什么、传什么参数"由模型在运行时决定。
- **佐证**：`User → LLM → 决策 → Tool → 执行 → Observation → LLM → ...`
- **边界**：只调一次模型 API、没有工具循环，那只是 LLM 应用，不是 Agent。

### Q2（1.4）｜ 为什么不能只靠 Prompt 让模型返回 JSON？
- **判断**：模型可能包一层"好的，结果是：{...}"，导致 `JSON.parse` 报错；应优先用 API 自带的 `response_format: { type: 'json_object' }` 约束。
- **展开**：Prompt 约束是软的，框架约束是硬的；Structured Output 的价值就是让"自然语言 → 程序对象"这一步可靠。
- **边界**：即使返回合法 JSON，也不代表结构正确（字段名/类型可能错），还要运行时校验。

### Q3（1.5）｜ `as IntentResult` 能代替运行时校验吗？
- **判断**：不能。`as X` 只是 TypeScript 编译期断言，运行时零检查。
- **展开**：类型（`type`）与校验（`parse`）必须分开；正确链路是 `LLM → Structured Output → JSON → Zod Schema → 校验 → TS 对象`。
- **边界**：把 `JSON.parse(content) as X` 当校验用，是 Agent 落地最常见的隐蔽 bug。

## 2. Tool Calling

### Q1（2.1）｜ Tool Calling 和 Structured Output 的本质区别是什么？
- **判断**：Structured Output 是"模型描述用户意图（intent），程序决定下一步"；Tool Calling 是"模型直接选择工具 + 生成参数，程序直接执行"。
- **展开**：前者输出 `response_format → JSON → intent`；后者输出 `tools → tool_calls → Function`。
- **边界**：两者不要混用——用了 `tools` 就不要再带 `response_format: json_object` 做意图解析。

### Q2（2.2）｜ 解析工具调用最容易踩的坑是什么？
- **判断**：真正该解析的是 `toolCall.function.arguments`，不是 `content`；且模型不一定每次都调用工具。
- **展开**：必须有"无 `tool_calls` → 直接返回答案"的分支；新版 SDK 的 Tool Call 类型需 Type Narrowing。
- **边界**：`Tool Definition`（schema）和 `Tool Implementation`（execute）是完全不同的东西，别混为一谈。

## 3. Agent Loop

### Q1（3.1）｜ 一个最基础的 Agent 由哪几部分组成？
- **判断**：**LLM + Tools + Context + Agent Loop + Stop Condition**；缺了循环就只是单次 Tool Calling。
- **展开**：Loop 把"模型决策 → 执行工具 → 结果回灌 Context → 再调模型"循环到模型不再返回 `tool_calls`。
- **佐证**：`while(未达上限){ r=llm(); if(!r.tool_calls) return r.content; executeTools(); }`
- **边界**：真正执行 Tool、管理上下文、决定继续与否的是 Agent Runtime，不是模型。

### Q2（3.3）｜ 工具执行报错应该直接让 Agent 失败吗？
- **判断**：不应该。工具错误同样可以作为 Observation 回灌给模型，让它重新决策。
- **展开**：`while` 管多轮、`for` 管一轮多个工具；失败≠Agent 失败，是 Agent 与传统后端程序的重要区别。
- **边界**：无限重试才是风险，所以要配 `maxIterations` 停止条件。

### Q3（3.4）｜ 为什么 LLM 输出必须校验？
- **判断**：LLM 输出永远是不可信外部数据，无论 Structured Output 还是 Tool 参数，都要 `JSON.parse` + Schema 校验后才进业务。
- **展开**：没有校验就信任模型输出，是 Agent 落地的头号风险。
- **边界**：校验失败要有兜底（重试 / 报错 Observation / 终止），而不是静默继续。

## 4. 上下文与记忆

### Q1（4.2）｜ 按 token 截断和按轮次裁剪历史，哪个更合理？
- **判断**：按"对话轮次（Round）"裁剪更合理——一次 `user` 触发的连续交互算一轮。
- **展开**：按 token 截断会切坏一条完整交互；`trimMessages` 的核心是"遇到 `user` 就开新轮"。
- **边界**：轮次也装不下时，再用 Rolling Summary 压缩更早的历史。

### Q2（4.4）｜ 短期记忆和长期记忆怎么分工？
- **判断**：短期记忆管当前会话的 `messages` + 裁剪 + 摘要（随会话结束消失）；长期记忆跨会话沉淀，靠 Embedding + 向量库持久化、按需检索注入。
- **展开**：长期记忆不能"全量塞入 Context"——撑爆窗口又浪费 token。
- **边界**：检索注入的是"相关记忆 TopK"，不是全部历史。

## 5. Embedding 与向量检索

### Q1（5.2）｜ 余弦相似度 0.618 代表模型有 61.8% 把握吗？
- **判断**：不代表。那只是基于向量距离算出来的分数，不是置信度。
- **展开**：余弦相似度衡量语义接近程度，越接近 1 越相似；阈值要靠 Retrieval Evaluation 定。
- **边界**：相似度阈值不能拍脑袋（如 `> 0.6`），必须评估得出。

### Q2（5.4）｜ pgvector 里 embedding 列为什么允许 NULL？
- **判断**：给 Embedding API 临时故障留容错空间——某条写入失败不至于整条记忆丢失。
- **展开**：检索时 `WHERE embedding IS NOT NULL` 跳过空值即可。
- **边界**：Embedding 模型凭证与推理模型凭证独立，不要混用 Key。

## 6. RAG

### Q1（6.2）｜ RAG 一定要做成 Agent 的 Tool 吗？
- **判断**：不必须。RAG 是一种能力，可独立成"检索 → 生成"链路；在 Agent 里才常包装成 `search_knowledge` 这样的 Tool。
- **展开**：RAG ≠ Tool，但 RAG Retrieval 可以作为 Tool 提供给 Agent。
- **边界**：企业 RAG 真正的工程量在"数据工程"（入库流水线、去重、版本、权限），不止调一次 Embedding。

### Q2（6.4）｜ 相似度阈值怎么定？0.6 合理吗？
- **判断**：不能拍脑袋定，要靠 Retrieval Evaluation 得出合适值。
- **展开**：阈值影响召回质量；太低召回噪声、太高漏召回。
- **边界**：评估要同时看"召回的相关片段是否够、无关片段是否少"，而非单一分数。

## 7. LangChain

### Q1（7.3）｜ `bindTools(tools)` 会自动执行工具吗？
- **判断**：不会。它只把工具描述提供给模型，执行仍需手写 Loop + `ToolMessage` 回灌。
- **展开**：`invoke` 拿到 `tool_calls` → 逐个执行 → 用带 `tool_call_id` 的 `ToolMessage` 回灌 → 再 `invoke`。
- **边界**：保留模型返回的完整消息、正确对应 `tool_call_id` 是循环跑通的关键。

### Q2（7.4）｜ 什么不该交给 LLM 决定？
- **判断**：确定性逻辑交 Tool，知识交 RAG，只有"决策"交 LLM。
- **展开**：不要把所有事都丢给模型；System Prompt 要约束 Agent 不乱判。
- **边界**：结构化报告（`withStructuredOutput`）放在调查之后单独整理，不要直接替换 Agent Loop。

## 8. LangGraph

### Q1（8.2）｜ StateGraph 里真正决定执行顺序的是什么？
- **判断**：是**边的连接关系**，不是 `.addNode().addEdge()` 链式调用的书写顺序。
- **展开**：`addNode` 注册步骤、`addConditionalEdges` 按状态选下一步、`compile()` 检查、`invoke()/stream()` 才启动。
- **边界**：把"链式书写顺序=执行顺序"是初学最常见的误解。

### Q2（8.5）｜ 用 PostgreSQL 做 Checkpoint 解决什么问题？
- **判断**：解决"程序退出后任务状态仍在、不同会话不串"——`thread_id` 标识一段任务上下文。
- **展开**：先用 `MemorySaver` 理解延续，再换 Postgres 保存器做持久化。
- **边界**：Checkpoint 只存状态，不替代你的业务数据库。

### Q3（8.6）｜ 中断恢复时为什么要保证幂等？
- **判断**：恢复时相关节点会从函数开头重跑，已成功的操作（如保存报告）重复恢复不应再产生一次结果。
- **展开**：`interrupt()` 暂停、`Command({ resume })` 恢复；幂等性防止重复副作用。
- **边界**：涉及写库 / 发消息 / 计费等副作用的节点，都要做幂等保护。

## 9. MCP

### Q1（9.2）｜ MCP 的 Host / Client / Server 各负责什么？
- **判断**：Host 承载对话与模型调用、决定如何使用工具结果；Client 连接服务、发现并调用工具；Server 提供 `get_weather` 这类能力。
- **展开**：接入 Agent 时，Host 是 NestJS 应用，MCP Client 是其组件，天气 Server 是独立程序。模型只负责"调什么、传什么"，真正发调用、收结果并放回对话的是应用。
- **边界**：Server 本身不调用模型，所以不需要模型密钥；密钥在 Host 配。

### Q2（9.1 / 9.4）｜ MCP 和 Tool Calling 是同一层吗？stdio 和 HTTP 怎么选？
- **判断**：不是同一层。Tool Calling 解决"模型怎么表达要用的工具和参数"；MCP 解决"应用怎么发现、调用外部能力并交换上下文"——MCP 站在 Tool Calling 上一层。
- **展开**：传输上，stdio 让客户端启动子进程、通过标准输入输出交换消息，适合本地工具与调试；Streamable HTTP 适合远程部署、供多应用访问。
- **边界**：stdio 下 Server 的普通日志要写 `console.error()`，`console.log()` 会混入协议消息流破坏通信。

### Q3（9.8）｜ 把 MCP 工具接入 Agent 时，MCP Client 应该放在哪？
- **判断**：放在"调用工具的节点"里；循环次数、超时、成本、人工审核仍由应用控制。
- **展开**：流程是：获取工具列表 → 转成模型工具定义 → 交模型 → 模型提 `get_weather` → 应用经 MCP Client 执行取结果 → 作为工具消息回灌 → 模型继续。
- **边界**：Server 只把"能力"标准化暴露，不调模型；真正把 MCP 工具接入 Agent 的是 Host，模型密钥在 Host 配。
