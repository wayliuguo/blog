# 日常使用总结

## 在工作中如何使用AI

主要是跟随工作流，需求理解/澄清 => 技术方案 => 编码实现 => 质量评审 => 监控运维

- 需求理解/澄清，产出技术方案，使用到技术方案生成skill
  - 轻量勘察，对项目代码进行勘察
  - 需求澄清 => 落 spec
  - 深度勘察，定位改动点
  - 图形设计，结合 archify 对架构图/流程图进行生成
  - 按照技术方案模板进行产生文档
    - 名词解析
    - 整体流程、架构改动评估
    - 关键实现
    - 风险点及后续规划
    - 上线策略
    - 数据监控
    - 回归要求
- 编码实现，使用方案喂给AI 进行实现
- 质量评审，使用AI 对生成的代码或CR清单进行评审，按p0、p1等进行标记，给出问题及修复方案
- 监控运维，先用监控skill 扫描代码得出配置，然后通过在脚手架使用配置进行自动生成

## 使用AI 遇到的问题

- 代码规范类
  - 表现
    - 生成的代码不符合已有配置的eslint 规范
    - ts 类型不符合规范
  - 解决方案
    - 规范添加上代码规范文档
    - 添加agent 钩子搭配代码格式化或push 进行代码格式化
- 质量类
  - 表现
    - 模板逻辑复杂、变量语义、变量冗余
    - 组件提取、逻辑提取复用、类型提取复用
    - 改动引起其他模块的失败
  - 解决方案
    - 引入对应的框架最佳实践 skill
    - 定义相关变量规范文档，按需引入
    - 严格使用SDD，先方案再确认执行
    - 引入自动化测试，执行完成或push执行用例
- 协作类
  - 表现
    - spec kit 太重了，前置的流程很多，要看的文档太多了
    - 频繁触发权限，无法做到【全天候工作】，不注意会被打断
    - 对于内部组件库等私有库，不会去使用
  - 解决
    - 使用更轻量的工作流，如CE\superpowers
    - 项目定义好权限
    - 构建好 readme，进行链接，及时提醒
- 工程类
  - 表现
    - 多 agent，规范不好统一
    - skill 等团队的沉淀，跨工程、个人没有做好积累共享
  - 解决
    - 前期手工定制过，后面可以看看腾讯 team AI
    - 进行插件化构建

## 为什么需要重构？遇到什么问题？

- 背景
  - 技术债务蔓延：历史业务下线代码没回收，冗余分支、失效代码、废止配置散落各处。改代码时容易踩到废弃配置，认知负担持续膨胀。 => 下线代码
  - 结构分层缺失：主组件同时承担初始化、要素联动、试算、校验 四份职责。任何一个改动都有横跨"启动→联动→计算→校验"的影响面， 改一点就要通读整个组件 ，风险面巨大。 => 组件合理拆分，单向数据流
  - 复用与回归丧失：金融要素联动（还款方式→计息→分期数→试算）在页面中 分散实现、没有封装复用 ，既导致"改一处未必同步别处"，又 没有测试回归能力 ——它就是"改 A 坏 B、回归才暴露"的温床。 =>金融要素拆解为纯函数，引入自动化测试
- 问题
  - 澄清阶段
    - 和各方明确已有逻辑，改动范围，工作量巨大
  - 方案阶段
    - 如何解耦、设计
  - 开发阶段
    - 并行两套，双倍资源消耗
  - 度量阶段
    - 如何减少风险=>引入测试
  - 监控阶段
    - 灰度发布
    - 主动监控
