# 日常使用总结

## 在工作中如何使用AI？
- 三个发展阶段
  - 第一个阶段是工具期，使用claude code、codex这类工具做编码提效
  - 第二个阶段是工程期，对上下文进行约束。
  - 第三个阶段是沉资产期，把重复劳动沉淀成skill。
- 在工作流上的体现：需求理解/澄清 => 技术方案 => 编码实现 => 质量评审 => 监控运维
  - 需求理解/澄清：需求澄清是通用能力，开源社区比较成熟（基于superpowers 的头脑风暴工作流/ grill-me），提炼需求点、歧义、未覆盖场景；和产品确认后落到澄清文档中。
  - 技术方案：把团队的方案结构沉淀为技术方案生成skill，基于澄清内容作为输入，产出颗粒度统一的技术方案。
    - 名词解析
    - 整体流程、架构改动评估（结合 archify 对架构图/流程图进行生成）
    - 关键实现
    - 风险点及后续规划
    - 上线策略
    - 数据监控
    - 回归要求
- 编码实现，使用方案喂给AI 进行实现，在这个环节的工程期，做了以下约束：
  - claude.md 简写了工程架构、常用命令、相关规范索引。
  - 规范索引放在 rules 进行按需约束，包含：
    - 代码规范
    - 注释规范
    - 最佳实践skill 索引
- 质量评审，使用AI 对生成的代码或CR清单进行评审
  - 审查维度：正确性、安全性、规范合规、可维护性、性能、配置等
  - 问题分级：按照严重、建议、提示进行
  - 输出：按照文件格式输出到对应的文件中
- 监控运维
  - 埋点与指标口径生成skill，确认事件清单、命名口径、指标口径、取数 sql
  - 监控配置skill，根据指标口径，生成监控配置，结合脚手架进行自动生成

## 使用AI 遇到的问题

- 代码规范类
  - 表现
    - 生成的代码不符合已有配置的eslint 规范
    - ts 类型不符合规范
  - 解决方案
    - 规范添加上代码规范文档
    - 添加agent 钩子搭配代码格式化或push 进行代码格式化
- 质量类
  - 表现
    - 模板逻辑复杂、变量语义、变量冗余
    - 组件提取、逻辑提取复用、类型提取复用
    - 改动引起其他模块的失败
  - 解决方案
    - 引入对应的框架最佳实践 skill
    - 定义相关变量规范文档，按需引入
    - 严格使用SDD，先方案再确认执行
    - 引入自动化测试，执行完成或push执行用例
- 协作类
  - 表现
    - spec kit 太重了，前置的流程很多，要看的文档太多了
    - 频繁触发权限，无法做到【全天候工作】，不注意会被打断
    - 对于内部组件库等私有库，不会去使用
  - 解决
    - 使用更轻量的工作流，如CE\superpowers
    - 项目定义好权限
    - 构建好 readme，进行链接，及时提醒
- 工程类
  - 表现
    - 多 agent，规范不好统一
    - skill 等团队的沉淀，跨工程、个人没有做好积累共享
  - 解决
    - 前期手工定制过，后面可以看看腾讯 team AI
    - 进行插件化构建
