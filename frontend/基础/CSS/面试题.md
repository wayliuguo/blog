# 模块面试题 · CSS

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。

> 题目来源：由本模块各篇正文的高频知识点整理，仅保留概念 / 机制 / 对比 / 场景四类重难点，精简掉低频与重复覆盖的题。

## 一、基础概念

### Q1: `box-sizing` 两种模型的区别？为什么推荐 `border-box`？

- **结论**：`content-box` 的 width 不含 padding/border，`border-box` 含；全局推荐 border-box。
- **原理**：`content-box` 下 `width: 100px + padding: 20px` 实际占 140px，百分比布局极易溢出；`border-box` 把 padding/border 算进 width，百分比与 flex 分配更可预期。
- **边界**：`box-sizing` 不继承，需 `* { box-sizing: border-box }` 显式设置；border-box 会改变对 width 的直觉，老项目改造需全量回归。

### Q2: 选择器权重怎么计算？`!important` 与内联谁高？

- **结论**：权重 = 行内样式 > ID > 类/属性/伪类 > 类型/伪元素；`!important` 反转该规则，但同为 important 时仍按权重比较。
- **原理**：按 `(a, b, c)` 计权——a 个 ID、b 个类/属性/伪类、c 个类型/伪元素；`!important` 提到最高优先组，冲突时再比权重。
- **边界**：`!important` 会让覆盖成本指数上升，是"最后的武器"；内联样式高于普通选择器，但低于 `!important`。

### Q3: `display:none` / `visibility:hidden` / `opacity:0` 的差异？

- **结论**：三者"看不见"的层度不同——`display:none` 移除文档流，`visibility:hidden` 占位隐藏，`opacity:0` 保留且可交互。
- **原理**：`display:none` 触发重排且不渲染；`visibility:hidden` 只触发重绘、占位保留；`opacity:0` 走合成层、元素仍在、点击事件仍触发（可配合 `pointer-events: none`）。
- **边界**：`visibility:hidden` 的子孙可用 `visibility: visible` 恢复显示，`display:none` 不能；`opacity:0` 不隐藏语义，读屏器仍会读出。

### Q4: `link` 引入 CSS 和 `@import` 有什么区别？为什么建议用 link？

- **结论**：`link` 是 HTML 标签、并行下载不阻塞渲染；`@import` 是 CSS 内部导入、串行且可能被忽略，建议用 `link`。
- **原理**：`link` 样式与页面并行加载；`@import` 必须等引用它的样式表**加载解析完**才继续下载，且 @import 必须写在样式表最前面、JS 动态创建的 `@import` 会被浏览器忽略。
- **边界**：多级 `@import` 会产生串行请求链，明显拖慢首屏；现代构建产物里 `@import` 会被打包器预处理合并，但手写样式仍以 `link` 为准。

## 二、机制与原理（布局）

### Q5: 什么是 BFC？怎么触发？有什么用？

- **结论**：BFC 是块级格式化上下文，内部布局不影响外部、外部不影响内部。
- **原理**：BFC 内浮动与边距被隔离——浮动元素不会溢出 BFC、margin 不会穿透折叠；触发方式有 `overflow`（非 visible）、`display: flow-root`、`float`、`position: absolute/fixed`、flex/grid 容器等。
- **边界**：`overflow: hidden` 清浮动有裁切副作用，推荐 `display: flow-root`（无副作用）；BFC 是布局隔离，不同于层叠上下文的绘制层级。

### Q6: `position` 各取值分别相对谁定位？

- **结论**：`static` 无定位、`relative` 相对自身、`absolute` 相对最近非 static 祖先、`fixed` 相对视口、`sticky` 滚动吸附。
- **原理**：`relative` 保留占位只做偏移；`absolute`/`fixed` 脱离文档流，参照系分别由包含块与视口决定；`sticky` 是 relative + 视口吸附的合体。
- **边界**：`absolute` 无非 static 祖先时相对初始包含块；祖先有 `transform`/`filter` 时 `fixed` 参照会被改掉（见 Q13）。

### Q7: 水平垂直居中有哪几种方案？

- **结论**：按"是否定宽高"分——不定尺寸用 flex/grid + margin auto，定尺寸用绝对定位 + 负 margin 或 `inset: 0; margin: auto`。
- **原理**：`display: flex; justify-content: center; align-items: center` 与 Grid 的 `place-items: center` 是最通用的；`position: absolute + inset: 0 + margin: auto` 依赖居中元素尺寸已知或内容自撑。
- **边界**：`transform: translate(-50%, -50%)` 会创建层叠上下文并影响 1px 精度；老方案各有坑，新代码一律优先 flex/grid。

### Q8: `flex: 1` 的 `min-width: 0` 陷阱？

- **结论**：flex 子项默认 `min-width: auto` 不收缩到内容以下，长文本会撑破布局；加 `min-width: 0` 恢复收缩。
- **原理**：flex 子项的隐式最小尺寸是内容最小宽度，当内容是不可断行字符串时，子项宁肯溢出也不压缩；`flex: 1` 即 `flex: 1 1 0%`，伸缩基数为 0，收缩与否仍受 min 约束。
- **边界**：`overflow: hidden` 也能间接解除，但语义不如 `min-width: 0` 清晰；垂直方向同理——`min-height: 0` 解决滚动容器内子项被撑高的问题。

### Q9: 层叠上下文导致 z-index 失效？

- **结论**：z-index 只在同一层叠上下文内比较，跨上下文比较的是各自祖先的层级。
- **原理**：`opacity < 1`、`transform`、`filter`、`will-change`、`position: fixed`、flex/grid 子项 + z-index 都会创建层叠上下文；一旦创建，内部的 z-index 就出不去。
- **边界**：弹窗被盖住先检查祖先链是否有元素创建了上下文；正确做法是分层管理上下文，而非大数值比高。

### Q10: Flex 与 Grid 怎么选？

- **结论**：一维布局用 Flex，二维布局用 Grid；"排列"用 Flex，"布局骨架"用 Grid。
- **原理**：Flex 是单轴模型（main/cross 轴），擅长内容驱动的排列与均分；Grid 是双轴（行列网格）布局，擅长容器驱动的骨架划分，还能 `grid-area` 区域命名。
- **边界**：Flex 做二维要 wrap + 计算宽度，Grid 一行搞定；两者可嵌套——外 Grid 定骨架、内 Flex 排工具栏是常见分层用法。

## 三、移动端与响应式

### Q11: px→vw 与 px→rem 怎么选？项目为什么用 vw？

- **结论**：px→vw 是编译期纯 CSS 方案，px→rem 是运行期 JS 设根字号方案；项目选 vw 是因为零 JS、随视口天然等比。
- **原理**：`postcss-px-to-viewport-8-plugin` 在构建期把 px 编译成 vw（`viewportWidth: 375`），随视口等比缩放；rem 依赖 JS 设根字号，有 FOUC 风险且需处理横竖屏。
- **边界**：vw 在大屏（iPad/PC）会按比例放大，需 `max-width` 容器兜底；`minPixelValue: 1` 保护真实 1px 描边不转 vw。

### Q12: `1px` 物理像素边框为什么变粗？怎么解决？

- **结论**：DPR ≥ 2 时 1 CSS px = 2+ 物理像素，视觉上"变粗"；用伪元素 + `scaleY(0.5)` 模拟。
- **原理**：CSS px 是逻辑单位，高 DPR 下渲染成多个物理像素；`minPixelValue: 1` 保留真实 1px 不参与 vw 转换，避免缩放出小数。
- **边界**：`border-width: 0.5px` 部分老 Android 不支持，需兼容写法；`scaleY(0.5)` 只适合水平线，四条边要 `scale(0.5)` + 放大补偿。

### Q13: 移动端安全区 `env(safe-area-inset-*)` 怎么用？`fixed` 为何会"变绝对"？

- **结论**：`viewport-fit=cover` 让布局延伸到刘海屏之下，用 `env(safe-area-inset-*)` 避让；`transform` 祖先会让 `fixed` 参照从视口变成该祖先（表现等同 absolute）。
- **原理**：`env()` 返回安全区距离，需 `viewport-fit=cover` 才非零，`constant()` 是旧 iOS 11 前缀可双写兼容；`transform`/`filter` 等会作为 `fixed` 与 `absolute` 的包含块。
- **边界**：排查"fixed 弹窗没贴住视口"先查祖先链有无 transform/filter；App 内动态状态栏用 JS 写 CSS 变量兜底，与 `env()` 互补。

## 四、现代 CSS 与渲染

### Q14: `@layer` 的层叠顺序是怎样的？为什么说它终结了"优先级战争"？

- **结论**：层叠排序是"来源与重要性 → 层 → 特异性 → 源码顺序"——层与层之间先比层序，同层之内才比特异性与源码顺序。
- **原理**：`@layer reset, components, utilities;` 先声明层序，普通声明里**越靠后的层越强**，与规则写在源码哪个位置无关；未分层的样式处在"隐式的最后一层"，普通声明里最强。`!important` 会把层序反转。
- **边界**：层序声明只认第一次出现的 `@layer a, b;`；工程落地是固定第一行声明层序，第三方库进 vendor、业务进 components、工具类进 utilities，从此不靠权重加码比大小。

### Q15: `:is()` 和 `:where()` 的特异性有什么差别？

- **结论**：`:is()` 取括号内**最高**特异性，`:where()` 恒为 `0`。
- **原理**：`:is(#ghost, .probe)` 会把 ID 权重带进来，压过单独的 `.probe`；`:where(#ghost, .probe)` 权重是 `0,0,0`，任何一条类选择器都能覆盖它。
- **边界**：`:is()` 括号里混进一个 ID 权重就暴涨；`:where()` 只适合承担"默认值"角色——重置/基础样式用 `:where()` 包裹，业务选择器用 `:is()` 缩短列表。

### Q16: 容器查询和媒体查询的本质区别？

- **结论**：媒体查询参照物是**视口**，容器查询参照物是**容器自身的宽度**；组件级适配用容器查询，设备级决策用媒体查询。
- **原理**：容器声明 `container-type: inline-size` 后，后代可 `@container (min-width: X)` 按容器宽度匹配；同一个卡片放进 280px 侧栏与 520px 主区、视口不变时，媒体查询给一个答案、容器查询给两个——这就是它存在的理由。
- **边界**：`inline-size` containment 让容器行内尺寸不再由内容决定，必须有确定宽度来源，否则内容被压扁；嵌套要 `container-name` 限定，否则匹配最近的祖先查询容器。

### Q17: 动画只用 `transform`/`opacity` 的原理（合成层）？

- **结论**：动画只改 `transform`/`opacity` 走合成线程、不触发重排重绘，成本最低。
- **原理**：渲染管线是 Layout → Paint → Composite；改 `transform`/`opacity` 时浏览器把元素提升到合成层，由 GPU 合成，主线程不参与每一帧。
- **边界**：合成层是双刃剑——层多了 GPU 内存与合成开销上升；动画结束后应移除 `will-change` 避免常驻。

## 五、场景设计题

### Q18: H5 在 375 手机、iPad 与 PC 都要好看，适配方案怎么定？

- **结论**：分三层——手机用 vw 等比缩放、平板用断点切列数、桌面用 `max-width` 容器锁死上限，不做"全端等比"。
- **原理**：vw 的语义就是随视口等比缩放，到 iPad/PC 会失真（1920 视口下 14px 被放大到 71px）；所以按视口区间分段——`≤768px` 走 vw 等比 + `viewportWidth: 375`；`768~1200px` 媒体查询切列数；`≥1200px` `max-width` 锁死居中。
- **边界**：`max-width` 兜底时 `1px` 与 `border-radius` 不能参与 vw 转换；`position: fixed` 底部栏大屏上要对齐内容区而非视口；iOS 安全区 `env()` 大屏下返回 0，不冲突。

### Q19: 浅色 / 深色 / 品牌色三套主题 + 运行时换色，怎么设计？

- **结论**：用 CSS 自定义属性搭"设计令牌三层结构"——原始令牌 → 语义令牌 → 组件消费，换主题只改 `:root` 上一组语义变量，组件一行不动。
- **原理**：原始令牌 `--color-brand-500` 描述调色板；语义令牌在 `:root` 映射 `--color-primary: var(--color-brand-500)`；组件只消费语义令牌。换主题 = 切 `data-theme`，运行时换色 = `setProperty('--color-brand-500', hex)` 改一个原始令牌全部自动跟随。
- **边界**：`getComputedStyle` 读 `--x` 只能拿到字符串，JS 做颜色运算要靠自己维护原始值或 `color-mix()`；CSS 变量按 DOM 继承，子树覆盖形成"局部主题"；微前端/iframe 下变量不穿透，需显式注入。

### Q20: 多人协作的覆盖战争（改一处影响另页）怎么治理？

- **结论**：先止血（收敛全局与超高权重选择器）→ 再隔离（组件级作用域）→ 后立规（命名与层级规范），不要一上来就换工具。
- **原理**：根因是"全局选择器 + 权重不断加码"和"样式归属无边界"。止血——把长链选择器与散落 `!important` 换回类名直选；隔离——CSS Module 或 `<style scoped>` 编译成哈希类名；立规——全局只留 reset 与设计令牌，业务走 BEM/`@layer` 分层，跨组件覆写必须走 props 或 CSS 变量。
- **边界**：`scoped` 的 `:deep()` 是逃生口，用多了等于没隔离；存量页面无法一次改造，按"新代码先立规、老代码随需求迁移"渐进推进；`@layer` 有"未分层样式优先级最高随后调整"的反直觉规则，迁移时需集中梳理。
