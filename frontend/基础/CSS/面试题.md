# 模块面试题 · CSS

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../../进阶/面试方法论.md)的四步答题法——结论/原理/边界/追问。
> 题目来源：由本模块各篇正文的知识点整理，每题在标题后标注出处（第 N 篇 / 场景综合）。

## 一、基础概念

### Q1: `box-sizing` 两种模型的区别？为什么推荐 border-box？（第 1 篇）

- **结论**：`content-box` 的 width 不含 padding/border，`border-box` 含；全局推荐 border-box。
- **原理**：`content-box` 下 `width: 100px + padding: 20px` 实际占 140px，百分比布局极易溢出；`border-box` 把 padding/border 算进 width，百分比与 flex 分配更可预期。
- **边界**：`box-sizing` 不继承，需 `* { box-sizing: border-box }` 显式设置；border-box 会改变对 width 的直觉，老项目改造需全量回归。
- **追问**：reset 里用 `*` 通配会全量生效，新项目直接全局 border-box，老项目逐模块迁移。

### Q2: `display:none` / `visibility:hidden` / `opacity:0` 的差异？（第 2 篇）

- **结论**：三者"看不见"的层度不同——`display:none` 移除文档流，`visibility:hidden` 占位隐藏，`opacity:0` 保留且可交互。
- **原理**：`display:none` 触发重排且不渲染；`visibility:hidden` 只触发重绘、占位保留；`opacity:0` 走合成层、元素仍在、点击事件仍触发（可配合 `pointer-events: none`）。
- **边界**：`visibility:hidden` 的子孙可用 `visibility: visible` 恢复显示，`display:none` 不能；`opacity:0` 不隐藏语义，读屏器仍会读出。
- **追问**：性能上 `opacity` 走合成层最便宜，动画过渡用它；真正"移除"用 `display:none`。

### Q3: 什么是 BFC？怎么触发？有什么用？（第 2 篇）

- **结论**：BFC 是块级格式化上下文，内部布局不影响外部、外部不影响内部。
- **原理**：BFC 内浮动与边距被隔离——浮动元素不会溢出 BFC、margin 不会穿透折叠；触发方式有 `overflow`（非 visible）、`display: flow-root`、`float`、`position: absolute/fixed`、flex/grid 容器等。
- **边界**：`overflow: hidden` 清浮动有裁切副作用，推荐 `display: flow-root`（无副作用）；`display: inline-block` 也能触发但会有基线空隙。
- **追问**：BFC 与层叠上下文不是一回事——前者管布局隔离，后者管绘制层级。

### Q4: 选择器权重怎么计算？`!important` 与内联谁高？（第 1 篇）

- **结论**：权重 = 行内样式 > ID > 类/属性/伪类 > 类型/伪元素；`!important` 反转该规则但同为 important 时仍按权重比较。
- **原理**：按 (a, b, c) 计权——a 个 ID、b 个类/属性/伪类、c 个类型/伪元素；`!important` 声明提到最高优先组，两个 `!important` 冲突时再比权重。
- **边界**：`!important` 会让覆盖成本指数上升，是"最后的武器"；内联样式高于普通选择器，但低于 `!important`。
- **追问**：`0,0,0,0` 的 `*` 通配符权重最低，任何选择器都盖过它。

### Q5: `position` 各取值分别相对谁定位？（第 2 篇）

- **结论**：`static` 无定位、`relative` 相对自身、`absolute` 相对最近非 static 祖先、`fixed` 相对视口、`sticky` 滚动吸附。
- **原理**：`relative` 保留占位只做偏移；`absolute`/`fixed` 脱离文档流，参照系分别由祖先链（包含块）与视口决定；`sticky` 是 relative + 视口吸附的合体，受滚动容器约束。
- **边界**：`absolute` 无任何非 static 祖先时相对 `body`/初始包含块；祖先有 `transform`/`filter` 时 `fixed` 参照会被改掉（见 Q12）。
- **追问**：`relative` 常被当作 `absolute` 的定位锚点，且不脱离文档流，是"父 relative + 子 absolute"套路的地基。

### Q6: 什么是 CSS 预处理器（Less/Sass/Stylus）？它的主要作用有哪些？（第 5 篇）

- **结论**：预处理器在 CSS 之上加编程能力（变量/嵌套/混合/函数/运算），编译后仍是标准 CSS。
- **原理**：Sass/Less 提供变量、嵌套规则、`@mixin`（混合宏）、循环与函数，解决"重复颜色值""层级冗长""媒体查询难复用"三大痛点；产物可被浏览器直接解析。
- **边界**：预处理器不是标准，引入编译环节与依赖；嵌套过深会放大选择器权重与生成体积，需配合 BEM/命名规范约束。
- **追问**：现代 CSS 已原生支持 `--var` 变量、嵌套（部分浏览器）——简单项目可先用原生，但 mixin/函数等能力仍是预处理器的优势。

## 二、机制与原理

### Q7: 水平垂直居中有哪几种方案？（第 2 篇）

- **结论**：按"是否定宽高"分——不定尺寸用 flex/grid + margin auto，定尺寸用绝对定位 + 负 margin 或 `inset: 0; margin: auto`。
- **原理**：`display: flex; justify-content: center; align-items: center` 与 Grid 的 `place-items: center` 是最通用的；`position: absolute + inset: 0 + margin: auto` 依赖"居中元素尺寸已知"或内容自撑。
- **边界**：`transform: translate(-50%, -50%)` 会创建层叠上下文并影响 1px 精度；老方案各有坑，新代码一律优先 flex/grid。
- **追问**：`text-align: center + line-height` 只对单行文本有效，多行文本会错位。

### Q8: `flex: 1` 的 `min-width: 0` 陷阱？（第 2 篇）

- **结论**：flex 子项默认 `min-width: auto` 不收缩到内容以下，长文本会撑破布局；加 `min-width: 0` 恢复收缩。
- **原理**：flex 子项的隐式最小尺寸是内容最小宽度（`min-width: auto`），当内容是不可断行字符串或长单词时，子项宁肯溢出也不压缩。
- **边界**：`overflow: hidden` 也能间接解除，但语义不如 `min-width: 0` 清晰；`flex: 1` 表示 `flex: 1 1 0%`，伸缩基数为 0，收缩与否仍受 min 约束。
- **追问**：垂直方向同理——`min-height: 0` 解决滚动容器内子项被撑高的问题。

### Q9: 层叠上下文导致 z-index 失效？（第 1 篇）

- **结论**：z-index 只在同一层叠上下文内比较，跨上下文比较的是各自祖先的层级。
- **原理**：`opacity < 1`、`transform`、`filter`、`will-change`、`position: fixed`、flex/grid 子项 + z-index 都会创建层叠上下文——一旦创建，内部的 z-index 就出不去。
- **边界**：弹窗被盖住先检查祖先链是否有元素创建了上下文；大 z-index 数值是"权重战争"，正确做法是分层管理上下文。
- **追问**：`transform` 不写 z-index 也创建上下文吗？→ 会，`transform: none` 之外的值都创建。

### Q10: `1px` 物理像素边框为什么变粗？怎么解决？（第 3 篇）

- **结论**：DPR ≥ 2 时 1 CSS px = 2+ 物理像素，视觉上"变粗"；用伪元素 + `scaleY(0.5)` 模拟。
- **原理**：CSS px 是逻辑单位，高 DPR 下渲染成多个物理像素；`minPixelValue: 1` 保留真实 1px 不参与 vw 转换，避免被缩放出小数。
- **边界**：`border-width: 0.5px` 部分浏览器（老 Android）不支持，需兼容写法；`scaleY(0.5)` 只适合水平线，四条边要 `scale(0.5)` + 放大补偿。
- **追问**：`minPixelValue: 1` 的副作用？→ 小于 1px 的设计间距不参与适配，通常可接受。

### Q11: 移动端安全区 `env(safe-area-inset-*)` 怎么用？（第 3 篇）

- **结论**：`viewport-fit=cover` 让布局延伸到刘海屏之下，用 `env(safe-area-inset-*)` 避让。
- **原理**：`env()` 返回安全区距离，需 `viewport-fit=cover` 才非零；`constant()` 是旧 iOS 11 前缀，可双写兼容。
- **边界**：未设 `viewport-fit=cover` 时 `env()` 恒为 0；`env()` 管系统级安全区，App 内动态状态栏用 JS 写 CSS 变量（`--phone-state-bar-height`），两者互补。
- **追问**：Android 的 `env()` 需要除以 `devicePixelRatio` 换算，直接引用可能偏大。

### Q12: `fixed` 在 `transform` 祖先下为何"变成 absolute"？（第 4 篇）

- **结论**：`transform`（非 none）祖先会创建"包含块"，`fixed` 的参照从视口变成该祖先——表现等同于 absolute。
- **原理**：规范规定 `transform`/`perspective`/`filter`/`will-change` 等会作为 `fixed` 与 `absolute` 的包含块；浏览器据此把 fixed 元素定位到该祖先的坐标体系。
- **边界**：祖先 `transform: none` 则不影响；`transform: translateZ(0)` 这类"空变换"也会触发——为了提升合成层常被误用。
- **追问**：排查"fixed 弹窗没贴住视口"先检查祖先链有没有 transform/filter。

### Q13: 动画只用 `transform`/`opacity` 的原理（合成层）？（第 4 篇）

- **结论**：动画只改 `transform`/`opacity` 走合成线程、不触发重排重绘，成本最低。
- **原理**：渲染管线是 Layout → Paint → Composite；改 `transform`/`opacity` 时浏览器把元素提升到合成层，由 GPU 合成，主线程不参与每一帧。
- **边界**：合成层是双刃剑——层多了 GPU 内存与合成开销上升；动画结束后应移除 `will-change` 避免常驻。
- **追问**：`contain: layout paint` 与 `will-change` 区别？→ contain 限制重排范围，不是提升合成层。

### Q14: `will-change` 的收益与滥用代价？（第 4 篇）

- **结论**：`will-change: transform` 提前把元素提升为合成层、减少动画首帧卡顿；滥用会占用 GPU 内存、增加合成层管理开销，反而更卡。
- **原理**：它只是"提前提示"浏览器做优化（创建合成层），不是动画加速器；多个元素同时 `will-change` 会耗尽低端机 GPU 资源。
- **边界**：用完要移除（或动画后置为 `auto`）；低端机上一个页面超过十几个合成层就明显掉帧。
- **追问**：优先考虑 `transform`/`opacity` 本身成本低，`will-change` 是"值得才用"的补充。

### Q15: `link` 引入 CSS 和 `@import` 有什么区别？为什么建议用 link？（第 1 篇）

- **结论**：`link` 是 HTML 标签、并行下载不阻塞渲染；`@import` 是 CSS 内部导入、串行且可能被忽略，建议用 `link`。
- **原理**：`link` 样式与页面并行加载；`@import` 必须等引用它的样式表**加载解析完**才继续下载，且 @import 必须写在样式表最前面、JS 动态创建的 `@import` 会被浏览器忽略。
- **边界**：`@import` 在 `<style>` 内或外链 CSS 里都可用，但多级 `@import` 会产生串行请求链，明显拖慢首屏。
- **追问**：现代构建（Vite/Webpack）的产物里 `@import` 会被打包器预处理合并，生产环境看不到差异，但手写样式仍以 `link` 为准。

### Q16: `backdrop-filter` 与 `filter` 的区别及兼容？（第 4 篇）

- **结论**：`filter` 作用于元素自身，`backdrop-filter` 作用于元素背后的区域（毛玻璃）。
- **原理**：`backdrop-filter` 对"背景"做模糊/变色处理，需要元素本身透明部分才能看到效果；两者都可能创建层叠上下文与包含块。
- **边界**：`backdrop-filter` 兼容性弱（iOS Safari 需 `-webkit-` 前缀），且与 `overflow` 裁剪、合成层提升互有影响；性能开销高于 filter，页面多毛玻璃会卡。
- **追问**：毛玻璃底部导航若不设 `backdrop-filter`，内容滚动会"透"过半透明背景，效果明显不同。

### Q17: 为什么 `selectorBlackList` 要排除 Vant？（第 3 篇）

- **结论**：Vant 组件库基于自身设计稿适配，若再按 375 二次转 vw 会尺寸错乱——所以用 `selectorBlackList: ['.van-']` 排除。
- **原理**：px→vw 转换会对**所有** px 生效，Vant 的样式基于 375 基准，被转 vw 后在不同屏宽被二次缩放，间距与字号比例失真。
- **边界**：黑名单按选择器前缀匹配，`.van-` 覆盖全部 Vant 类名；自定义 `ignore-` 前缀用于业务侧手动豁免。
- **追问**：排除后 Vant 组件用 rem？→ 不，排除的类名保持 px 原样，靠 Vant 自带的设计与媒体适配。

### Q18: `@layer` 的层叠顺序是怎样的？为什么说它终结了"优先级战争"？（第 6 篇）

- **结论**：层叠排序是"来源与重要性 → 层 → 特异性 → 源码顺序"——层与层之间先比层序，同层之内才比特异性与源码顺序。
- **原理**：`@layer reset, components, utilities;` 先声明层序，普通声明里**越靠后的层越强**，与规则写在源码哪个位置无关；没写进任何层的样式处在"隐式的最后一层"，普通声明里最强。`!important` 会把层序反转：最早声明的层最强，未分层的 `!important` 反而最弱。
- **边界**：`@layer` 改的是覆盖排序，不是代码组织的分组，同层内规则照样互相覆盖；未分层样式压过所有分层样式，这既是渐进迁移的便利，也是"我明明进了层怎么还被覆盖"的原因；层序声明只认第一次出现的 `@layer a, b;`，之后同名 `@layer x {}` 只是往里追加规则。
- **追问**：工程上怎么落地？→ 固定第一行 `@layer reset, vendor, components, utilities;`，第三方库进 vendor、业务进 components、工具类与局部覆写进 utilities，从此不靠引入顺序与权重加码比大小。

### Q19: `:is()` 和 `:where()` 的特异性有什么差别？各自该用在哪？（第 6 篇）

- **结论**：`:is()` 取括号内**最高**特异性，`:where()` 恒为 `0`。
- **原理**：`:is(#ghost, .probe)` 会把 `#ghost` 的 ID 权重带进来（`1,0,0`），所以压过单独的 `.probe`；`:where(#ghost, .probe)` 权重是 `0,0,0`，任何一条类选择器都能覆盖它。两者都能解决"一长串选择器写三遍"的重复。
- **边界**：`:is()` 只要括号里混进一个 ID，整体权重就暴涨，容易造成"引了别人的样式就改不动"；`:where()` 权重为零，连标签选择器都压不过，只适合承担"默认值"角色。
- **追问**：实际怎么分工？→ 重置样式、基础样式用 `:where()` 包裹（保证业务侧随便一条规则都能覆盖）；业务选择器用 `:is()` 缩短列表，但要清楚它继承了哪个权重。

### Q20: 容器查询和媒体查询的本质区别是什么？用之前有哪些前提？（第 6 篇）

- **结论**：媒体查询的参照物是**视口**，容器查询的参照物是**容器自身的宽度**；组件级适配用容器查询，设备级决策用媒体查询。
- **原理**：容器声明 `container-type: inline-size`（可用 `container-name` 起名）后，后代就能用 `@container [name] (min-width: X)` 按容器宽度匹配。同一个卡片放进 280px 的侧栏与 520px 的主区、视口完全不变时，媒体查询给出同一个答案、容器查询给出两个不同答案——这就是它存在的理由。
- **边界**：`inline-size` containment 让容器的行内尺寸不再由内容决定，所以容器必须有确定的宽度来源（父容器、显式 `width`、flex/grid 分配），否则内容被压扁；高度仍由内容决定；不带容器名时会匹配最近的祖先查询容器，多层嵌套要显式命名避免误匹配。
- **追问**：什么时候还必须用媒体查询？→ 栅格列数、字号体系、侧栏显隐这类跟设备/视口走、且发生在组件外部的决策；容器查询解决不了"容器自己还没有宽度"的问题。

## 三、排障与选型

### Q21: Flex 与 Grid 怎么选？（第 2 篇）

- **结论**：一维布局用 Flex，二维布局用 Grid；"排列"用 Flex，"布局骨架"用 Grid。
- **原理**：Flex 是单轴布局模型（main/cross 轴），擅长"内容驱动"的排列与均分；Grid 是双轴（行列网格）布局，擅长"容器驱动"的骨架划分，还能 `grid-area` 做区域命名。
- **边界**：Flex 做二维（多行等宽卡片）要靠 wrap + 计算宽度，Grid 一行搞定；Grid 子项默认拉伸填满轨道，与 Flex 的 `align-items` 行为不同。
- **追问**：两者可嵌套——外 Grid 定骨架、内 Flex 排工具栏，是常见的分层用法。

### Q22: px→vw 与 px→rem 怎么选？项目为什么用 vw？（第 3 篇）

- **结论**：px→vw 是编译期纯 CSS 方案，px→rem 是运行期 JS 设根字号方案；项目选 vw 是因为零 JS、随视口天然等比。
- **原理**：`postcss-px-to-viewport-8-plugin` 在构建期把 px 编译成 vw（`viewportWidth: 375`），随视口等比缩放；rem 依赖 JS 设 `html` 根字号，有 FOUC 风险且需处理横竖屏。
- **边界**：vw 在大屏（iPad/PC）会按比例放大，需 `max-width` 容器兜底；`minPixelValue: 1` 保护真实 1px 描边不转 vw。
- **追问**：为什么 `selectorBlackList` 要排除 Vant？→ Vant 基于自身设计稿，若按 375 二次缩放会尺寸错乱（详见 Q17）。

### Q23: H5 页面在 iPhone 刘海屏上底部按钮被 Home 条遮挡，怎么修？（第 3 篇）

- **结论**：修法分三层——`viewport-fit=cover`（HTML 层）→ `padding-bottom: env(safe-area-inset-bottom)`（CSS 层）→ App 内动态状态栏用 JS 写 CSS 变量兜底。
- **原理**：`cover` 让页面铺满安全区外区域，`env()` 读出底部 inset 做 padding；App 内状态栏高度不固定，`setProperty('--phone-state-bar-height', ...)` 运行时写入，CSS 用 `var()` 消费。
- **边界**：兼容顺序是 `constant()`（旧 iOS）→ `env()`（新标准）→ 默认值兜底；Android 端需处理 DPR 换算。
- **追问**：加分点是主动说明"`env()` 需 `viewport-fit=cover` 才非零"，否则排查半天以为是 CSS 写错。

### Q24: `position: sticky` 失效的常见原因？（第 2 篇）

- **结论**：sticky 失效的排查顺序是——父容器 `overflow` 非 visible、父容器高度不足、未设 top/bottom 阈值、祖先有 `transform`。
- **原理**：sticky 是"相对定位 + 视口吸附"，但吸附范围被最近的滚动祖先与父容器高度约束；`overflow: hidden/auto/scroll` 会把它变成"在该容器内滚动"，`transform` 祖先会把视口参照系改掉。
- **边界**：父容器必须比 sticky 元素高才有滚动空间；设了 `top: 0` 但不滚到边界就不会"粘"。
- **追问**：`position: sticky` 在 `display: flex` 父容器里要配合 `align-self: flex-start`，否则被拉伸。

## 四、场景设计题

### Q25: 场景：同一套 H5 要在 375 手机、iPad 与 PC 桌面浏览器都好看，适配方案怎么定？（场景综合）

- **结论**：分三层——手机用 vw 等比缩放、平板用断点切列数、桌面用 `max-width` 容器锁死上限，不做"全端等比"。
- **原理**：vw 的语义就是"随视口等比缩放"，这在手机上正是想要的；但到 iPad/PC 会立刻失真（1920 视口下，375 设计稿的 14px 字号会被放大到 71px）。所以适配必须按视口区间分段：`≤768px` 走 vw 等比 + `postcss-px-to-viewport` 的 `viewportWidth: 375`；`768~1200px` 用媒体查询把布局从 1 列切到 2 列；`≥1200px` 用 `max-width: 750px` 把内容区锁死并居中，两侧留白。
- **边界**：`max-width` 兜底时，`1px` 描边与 `border-radius` 不能参与 vw 转换（靠 `minPixelValue: 1` 保护）；`position: fixed` 的底部操作栏默认相对视口，大屏上会贴到浏览器最底部远离内容——要么随内容容器改成 `absolute`，要么加 `max-width` + `left/right: auto` + `margin: auto` 对齐内容区；iOS 安全区的 `env(safe-area-inset-bottom)` 在大屏下返回 0，不会与 `max-width` 冲突。
- **追问**：为什么不用现成响应式框架直接解决？→ 框架给的是栅格与组件断点，解决不了"vw 在哪个区间该停下"这个策略问题；适配方案是策略层决定，框架只是执行层。

### Q26: 场景：中后台要支持浅色 / 深色 / 品牌色三套主题，还要支持运行时动态换色，怎么设计？（场景综合）

- **结论**：用 CSS 自定义属性搭"设计令牌三层结构"——原始令牌 → 语义令牌 → 组件消费，换主题只改 `:root` 上一组语义变量，组件样式一行不动。
- **原理**：第一层原始令牌 `--color-brand-500: #1677ff` 描述调色板；第二层语义令牌在 `:root` 上做映射 `--color-primary: var(--color-brand-500)`、`--color-bg: #fff`；第三层组件只消费语义令牌（`color: var(--color-text)`）。换主题 = 在 `html` 上切 `data-theme`，由 `[data-theme='dark'] { --color-bg: #141414 }` 覆盖语义层；运行时换品牌色 = `document.documentElement.style.setProperty('--color-brand-500', hex)` 只改一个原始令牌，全部下游自动跟随；深色模式还能用 `@media (prefers-color-scheme: dark)` 让系统偏好当默认值。
- **边界**：`getComputedStyle` 读 `--x` 只能拿到解析后的字符串，JS 里做颜色运算要在自己这侧维护原始值或改用 `color-mix()`；CSS 变量按 DOM 继承、有作用域，在某个子树里覆盖会形成"局部主题"（既是能力也是坑）；微前端 / iframe 下变量不会穿透，需要显式注入；旧浏览器需 `@supports` 兜底。
- **追问**：为什么不做"多份构建产物 + 构建时换色"？→ 运行时换色只需改一个变量、零重新构建，还能支持用户自定义品牌色；多份产物要构建 N 次、且无法覆盖"用户在设置页选了个颜色"这类运行时需求。

### Q27: 场景：多人协作的中后台出现"改一处样式影响另一个页面"的覆盖战争，怎么治理？（场景综合）

- **结论**：先止血（收敛全局与超高权重选择器）→ 再隔离（组件级作用域）→ 后立规（命名与层级规范），不要一上来就换工具。
- **原理**：覆盖战争的两个根因是"全局选择器 + 权重不断加码"和"样式属于谁没有边界"。止血——把 `body .page .list li a` 这类长链与散落的 `!important` 逐个换回类名直选；隔离——组件样式走 CSS Module 或 Vue 的 `<style scoped>`，编译成哈希类名实现作用域；立规——全局只留 reset、设计令牌与少量工具类，业务样式一律走块级命名（BEM），跨组件覆写必须通过组件暴露的 props 或 CSS 变量，而不是直接选内部类名。现代 CSS 的 `@layer` 是这条路的终点：把第三方库放进 `layer(vendor)`、业务放进 `layer(app)`，从此靠层级而不是靠权重与 `!important` 比大小。
- **边界**：`scoped` 的 `:deep()` / `>>>` 是逃生口，用多了等于没隔离；CSS Module 的哈希类名调试不直观，要配 sourcemap；存量页面无法一次改造，按"新代码先立规、老代码随需求迁移"渐进推进；`@layer` 需要浏览器支持且有"未分层的样式优先级高于所有分层"这条反直觉规则，迁移时要集中梳理。
- **追问**：怎么证明治理有成效？→ 用一个可量化指标——统计 `!important` 出现次数、单条选择器最大长度与"改一个文件影响的页面数"，治理前后对比，而不是凭感觉说"好维护多了"。

### Q28: 场景：一个卡片组件要同时用在 280px 侧栏、520px 主区和弹窗里，它的响应式怎么设计？（场景综合）

- **结论**：不再按视口断点写三套样式，而是让容器声明 `container-type: inline-size`，组件按容器宽度自己换形；视口级布局仍交给媒体查询。
- **原理**：侧栏、主区、弹窗都是"宽度来源明确的一层"，组件只声明"容器 ≥ 360px 时横排、否则竖排"这类规则，用 `@container`（可带容器名）匹配。同一份 CSS 在三个场景自动给出正确形态，既不需要父组件传 `size` 类名，也不需要 `:deep()` 之类的外部覆写；容器宽度变化（侧栏折叠、弹窗拖拽）时组件实时跟随。
- **边界**：`container-type: inline-size` 引入行内尺寸 containment，容器必须有确定宽度——弹窗里若写 `width: fit-content` 会直接塌掉；多容器嵌套要用 `container-name` 限定，否则会匹配到外层的查询容器；内嵌 WebView、老安卓机型不支持 `@container`，需要 `@supports` 兜底或保留一套媒体查询降级写法；容器查询只解决"容器内怎么排"，弹窗在小屏上是否改成全屏抽屉这件事仍属视口级决策。
- **追问**：和"父组件传 props 控制形态"相比优势在哪？→ 形态直接绑定容器可用宽度，父组件改布局时组件自动跟随，不会出现"props 说的 size 与实际宽度不一致"的错配，也省掉了每个父级都要记得传参的心智负担。
