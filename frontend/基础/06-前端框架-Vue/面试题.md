## 一、基础与差异

### Q1: Vue3 与 Vue2 的核心差异？（第 01 篇）

- **结论**：三大核心差异——响应式换 Proxy、组合式 API、编译优化（更快更小）；另加 TypeScript 一等公民。
- **原理**：Vue2 用 `Object.defineProperty` 逐属性劫持，新增/删除属性不响应；Vue3 用 Proxy 整对象代理，天然拦截动态属性与数组索引。模板编译加 patchFlag 静态提升，运行时 diff 更省。
- **边界**：Vue3 仍是"响应式 + 模板编译 + 虚拟 DOM"，不是重写；选项式 API 仍可用。
- **追问**：为什么要换 Proxy？→ 补齐 Vue2 的响应式盲区（新增属性、数组下标），且一次代理整个对象、无递归 defineProperty 的逐属性开销。
- **场景**：Vue3.5 项目里 `reactive` 直接覆盖动态表单字段，不再需要 `Vue.set`。

### Q2: `v-if` 与 `v-show` 的区别？（第 01 篇）

- **结论**：`v-if` 条件不成立时不渲染节点（销毁/创建），`v-show` 始终渲染只是 `display: none`。
- **原理**：`v-if` 走"增删 DOM"，切换有重建成本、也触发销毁钩子；`v-show` 只切 display，代价是元素常驻。
- **边界**：高频切换用 `v-show`，低频/首屏不展示用 `v-if`（省初始渲染）；`v-if` 与 `v-for` 同元素时 `v-if` 优先（Vue3 编译告警，应拆开）。
- **追问**：`v-show` 对 `display` 有特殊处理——切到 `!important` 的 display 会失效。
- **场景**：Tab 切换面板用 `v-show`；登录后才能看到的区块用 `v-if`。

### Q3: `v-for` 的 `key` 作用？（第 01 篇）

- **结论**：`key` 是 diff 时识别节点身份的依据，让复用走"移动"而非"删除重建"。
- **原理**：`v-for` 渲染的列表在数据重排/增删时靠 key 配对新旧节点；用 index 作 key 在中间插入时，后续节点被错位复用，输入框状态错乱。
- **边界**：key 在兄弟间唯一即可；整组重排（拖拽排序）更依赖稳定 key。
- **追问**：key 应该用什么？→ 业务 id（唯一且稳定），不是 index、不是随机数。
- **场景**：审核列表 `:key="item.id"`；拖拽排序后 DOM 正确复用。

### Q4: Vue 生命周期有哪些？（第 01 篇）

- **结论**：创建（setup/onBeforeMount/onMounted）、更新（onBeforeUpdate/onUpdated）、卸载（onBeforeUnmount/onUnmounted）三段，组合式 API 用 `onXxx` 钩子注册。
- **原理**：`setup` 在组件实例创建前执行（拿不到 this）；`onMounted` 在 DOM 挂载后（可读 DOM/发请求）；`onUnmounted` 做清理（定时器、监听器、订阅）。
- **边界**：`onBeforeUnmount` 里必须清理副作用，否则内存泄漏；`onErrorCaptured` 捕获后代组件错误。
- **追问**：`onMounted` 里发请求为什么常见？→ DOM 就绪 + 避免请求回调写未挂载组件。
- **场景**：页面进入 `onMounted` 拉列表、`onBeforeUnmount` 清定时器。

## 二、模板与组件

### Q5: 组件通信方式？（第 02 篇）

- **结论**：props 下行、emit 上行、v-model 双向、provide/inject 跨层、事件总线兜底；就近选择、避免滥用。
- **原理**：单向数据流下 props 只读、emit 通知父级改数据；provide/inject 跨多层传递（不经过中间层）；`defineExpose` + ref 暴露子组件方法。
- **边界**：provide/inject 是"非响应式透传"？→ 传 ref/reactive 才保持响应式；事件总线无类型约束、难追踪，能不用就不用。
- **追问**：兄弟组件通信？→ 状态提升到公共父组件，或上 Pinia。
- **场景**：表格行组件 props 收数据、emit 行点击；登录态 provide 给所有后代。

### Q6: `v-model` 的本质？（第 02 篇）

- **结论**：`v-model` 是 `:modelValue` + `@update:modelValue` 的语法糖（表单元素上是 value + input）。
- **原理**：模板编译展开成 prop 绑定 + 事件监听；子组件 `defineModel()`（Vue3.4+）声明双向绑定模型。
- **边界**：Vue3 支持多个 `v-model:name` / `v-model:age`；Vue2 的 `.sync` 在 Vue3 统一为 v-model 多参数。
- **追问**：`v-model` 与手动 `:value + @input` 的区别？→ 语法糖等价，v-model 更简洁且语义化。
- **场景**：自定义金额输入组件用 `defineModel()` 双向绑定，父组件 `v-model="amount"` 直接使用。

### Q7: `computed` 与 `watch` 的区别？（第 01 篇）

- **结论**：computed 是"派生值"（有缓存、响应式依赖），watch 是"副作用监听"（数据变化时执行逻辑）。
- **原理**：computed 惰性求值 + dirty 标记，依赖不变直接返回缓存；watch 显式监听源，变化回调可做请求/埋点/异步。
- **边界**：能在 computed 表达的不要用 watch（声明式优于命令式）；watch 默认浅监听，深对象要 `{ deep: true }`。
- **追问**：computed 里能改数据吗？→ 不能——computed 应保持纯，否则派生生源混淆。
- **场景**：试算结果用 computed（输入要素变 → 结果自动重算）；切换还款方式触发的请求用 watch。

## 三、响应式原理

### Q8: Vue3 响应式原理？（第 01 篇）

- **结论**：`reactive` 用 Proxy 拦截 get/set——get 时收集依赖（effect），set 时触发更新。
- **原理**：渲染函数作为 effect 执行，读取响应式属性即建立"属性 → effect"依赖；数据变化把 effect 加入调度队列（`queueJob`）在微任务中批量执行。
- **边界**：深度响应式递归代理有初始化成本，可用 `shallowReactive`/`shallowRef` 降级；Map/Set 走专用 handlers；`ref` 用对象包装值（`.value`）。
- **追问**：为什么用 Proxy 不用 defineProperty？→ 可拦截动态新增属性与数组索引，且一次性代理整个对象。
- **场景**：页面依赖 `loanForm.amount`，改 amount 只重渲染依赖它的组件，不是全页重绘。

### Q9: 依赖收集与触发更新的完整链路？（第 01 篇）

- **结论**：effect 执行 → 读取属性 → 属性对应的 dep 收集该 effect → 属性变化 → dep 触发 effect。
- **原理**：数据结构是 `targetMap: WeakMap<对象, Map<key, Set<effect>>>`；`ref` 的 `.value` 读写同样走 getter/setter；computed 是惰性 effect（缓存），watch 是显式收集目标。
- **边界**：在 effect 外读取不收集；Vue2 用 `Vue.set` 解决"新增属性不响应"，Vue3 Proxy 下不存在此痛点。
- **追问**：computed 为什么能缓存？→ 惰性求值 + dirty 标记，依赖不变直接返回缓存值。
- **场景**：改 `loanForm.amount` → 试算 computed 标记 dirty → 视图 effect 重新执行，链路环环相扣。

### Q10: 批量更新：为什么连续改数据只渲染一次？（第 01 篇）

- **结论**：effect 触发进 `queueJob` 去重 + 微任务调度，多次同步改数据只执行一次渲染。
- **原理**：同一 effect 被多次触发只入队一次（去重）；渲染在微任务中批量执行，当前宏任务内的所有修改合并到一次更新。
- **边界**：`flushSync`（Vue3.5 起）可强制同步渲染，但牺牲批处理收益、尽量不用。
- **追问**：为什么用微任务不用同步？→ 同步多次改数据会多次渲染，微任务合并为一次。
- **场景**：循环里改 100 次列表数据 → 只渲染一次，不卡主线程。

### Q11: `nextTick` 的原理？（第 01 篇）

- **结论**：nextTick 在"本次更新批处理完成后"执行回调，用于拿最新 DOM。
- **原理**：渲染队列在微任务中 flush，`nextTick` 把回调排到同一批微任务之后；Vue3 返回 Promise，可 `await nextTick()`。
- **边界**：nextTick 保证的是"DOM 已更新"，不是"布局已稳定"（要读尺寸仍需在回调里等渲染完）。
- **追问**：为什么组件内直接读 DOM 尺寸是旧的？→ 数据变更后 DOM 更新是异步的，同步读的是旧 DOM。
- **场景**：修改数据后 `await nextTick()` 再读列表滚动高度，做"滚动到底部"。

## 四、编译与 diff

### Q12: 编译优化：patchFlag / 静态提升 / Block Tree？（第 01 篇）

- **结论**：编译期标记动态节点（patchFlag），diff 只对比动态部分；静态子树提升出渲染函数；Block Tree 把动态子节点收成扁平数组。
- **原理**：模板编译把"哪些部分是动态的"编码进标志位（TEXT/CLASS/PROPS 等）；静态节点创建一次、重复复用；`v-for` 等动态结构用 Block 收集动态子节点，diff 直接遍历。
- **边界**：手写渲染函数没有编译优化收益——这是"模板优先"的原因之一。
- **追问**：Block Tree 解决什么？→ 不再深度对比静态结构，diff 复杂度从整树降到动态节点数。
- **场景**：`<div>{{ msg }}</div>` 只标记 text 动态；大列表模板按 v-for Block 收集，更新只 diff 变化行。

### Q13: Vue3 的 diff 为什么比 Vue2 快？（第 01 篇）

- **结论**：快在"对比范围更小"——编译期 patchFlag 缩小动态范围 + 双端 diff 优化，而不是算法本身突破。
- **原理**：Vue2 全量 patch 整棵 vnode 树；Vue3 静态提升免重建、patchFlag 跳过静态比较、Block Tree 扁平遍历；同层 diff 也做了双端/最长递增子序列优化。
- **边界**："快"是相对静态内容多的模板；动态内容密集的列表提升有限，仍要按需优化（虚拟滚动、memo）。
- **追问**：手写渲染函数 + 无编译优化时，Vue3 与 Vue2 差距缩小。
- **场景**：运营后台大量静态模板页面，Vue3 编译优化收益明显。

## 五、组合式 API 与工程

### Q14: 组合式 API 与选项式 API 的取舍？（第 02 篇）

- **结论**：组合式按"逻辑"组织（相关代码聚在一起、可复用），选项式按"类型"组织（data/methods 分块）；新代码用组合式。
- **原理**：组合式靠函数作用域复用逻辑（自定义 Hook）；选项式靠 mixin 复用，有命名冲突与来源不明问题。
- **边界**：组合式更灵活也更容易写乱，需要分层规范约束（api/hooks/utils/views）。
- **追问**：自定义 Hook 与 mixin 的区别？→ Hook 是普通函数（显式传参、无命名冲突），mixin 隐式合并、来源难查。
- **场景**：`useLoanFlow` 把级联试算链路收敛在一个 Hook，页面组件只做编排与渲染。

### Q15: 自定义指令 / Teleport / Suspense？（第 02 篇）

- **结论**：自定义指令封装 DOM 操作（聚焦、权限、埋点），Teleport 把内容传送到指定 DOM 节点，Suspense 处理异步依赖的加载态。
- **原理**：`v-focus` 之类指令在 mounted 钩子操作元素；Teleport 用 `to` 指定目标（弹窗挂 body 避免遮挡裁剪）；Suspense 配合异步组件/`async setup` 显示 fallback。
- **边界**：能用组件做的别用指令（指令难测试、难约束）；Suspense 在 SSR 下需谨慎；Teleport 目标要存在且同文档。
- **追问**：`<Teleport to="body">` 常用于弹窗，避免父级 `overflow: hidden` 裁剪。
- **场景**：全局弹窗组件 Teleport 到 body；按钮权限用自定义指令 `v-permission` 控制显隐。

### Q16: 响应式数据在"大数据 + 复杂联动"场景怎么设计？（附录）

- **结论**：试算/派生逻辑用纯函数 + 单向数据流，响应式只负责视图层派生——可枚举、可单测、可复用、可回归。
- **原理**：纯函数"输入决定输出"无副作用，摆脱响应式依赖追踪的隐式耦合；视图只消费纯函数的输出（computed/ref 派生状态）。
- **边界**：纯函数要可缓存（相同输入直接取上次结果）；不要用 watch 链式改数据（命令式易失控），用派生式表达。
- **追问**：响应式计算 vs 纯函数怎么分工？→ 响应式管"视图依赖派生"，纯函数管"业务计算"，各自可测。
- **场景**：借款要素（还款方式/计息方式/分期数/金额）→ 纯函数试算 → UI 消费派生状态，单测覆盖试算函数。

### Q17: 从 Vue2 迁 Vue3 的坑？（附录）

- **结论**：迁移坑集中在——响应式差异（新增属性/数组下标）、`this` 与 setup、v-model/`$listeners` 移除、全局 API 改具名导入。
- **原理**：Vue2 的 `Vue.set`/`$set` 在 Vue3 不需要（Proxy）；`this.$emit`/`$attrs` 语义变化；`Vue.nextTick` 改具名导出；过滤器 filter 移除。
- **边界**：选项式可平滑迁移（兼容层），组合式迁移要重写组件逻辑；第三方库生态需查兼容。
- **追问**：Weex（Vue2）转 Vue3 MPA 的迁移？→ 组件/路由/状态逐层替换，先跑通兼容层再按模块改组合式。
- **场景**：老项目迁移先跑"迁移构建版"看告警，再按模块逐个改造，避免大爆炸式重写。

## 六、实战场景

### Q18: 借款页切换还款方式/计息方式/分期数会级联触发试算，怎么用 Vue3 实现才不卡、不乱、可测？（附录）

- **结论**：金融要素 → 纯函数试算（无副作用）→ 试算结果作派生状态 → 视图只消费派生状态 + 相同输入缓存 + 请求标记位防竞态。
- **原理**：级联逻辑散在 data/watch/事件里会隐式耦合、难测难回归；收敛为纯函数后"输入决定输出"，computed 自动缓存，缓存 key 覆盖全部输入要素。
- **边界**：并发切换试算用请求标记位保证最后一次生效；缓存命中要覆盖全部要素，否则脏缓存。
- **追问**：为什么不用 watch 链？→ watch 改数据会级联触发、顺序难控，纯函数单向数据流可枚举可单测。
- **场景**：主组件职责从"视图+数据+请求+校验+埋点混写"收敛为"编排 + 渲染"，`useLoanFlow` Hook 持有要素与派生结果。
