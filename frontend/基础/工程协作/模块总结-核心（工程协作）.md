## 高频核心点

### 01 Git 与协作

**撤销与回退**

- **`reset` vs `revert`**：`reset` 改写历史（移动 HEAD）、`revert` 新建相反提交不改写历史；已推共享分支用 `revert`
- **`reset` 三模式**：`--soft` 只动 HEAD、改动留暂存区；`--mixed`（默认）更新暂存区、工作区不动；`--hard` 连工作区一起重置，未提交改动全丢、慎用
- **`revert commitId`**：新建内容正好抵消目标提交的提交，原历史不变，适合已推送场景

**远程仓库与分支协作**

- **`remote` 换源**：`git remote -v` 查看、`remote rm` + `remote add` 换源、`push -u origin main` 首次指定上游；换源不影响本地历史与分支
- **功能分支流程**：`checkout -b feature/xxx` → 提交 → 推远程发 PR/MR → 评审合入 → 其他人 `pull` 同步；分支宜短命，防与主干差异拉大
- **合并冲突**：同一区域两边都改才冲突；`<<<<<<<`/`=======`/`>>>>>>>` 标记区选留，`add` + `commit` 解决；提前 `pull`、提交粒度单一可减少冲突
- **`pull` 合并式 vs `pull --rebase`**：后者把本地提交变基到远端最新之后、历史更线性；已推共享提交不要 rebase

**Gitee / GitHub 镜像同步**

- **Push 方向镜像**：Gitee「仓库镜像管理」加镜像，令牌含 `repo` 权限；提交到 Gitee 自动同步分支/标签/提交，最短间隔 5 分钟
- **方向限制**：Push 只自动同步"提交到 Gitee"这一向；反向自动同步需另配 Pull 方向镜像；建议 Gitee 作提交主力、GitHub 作联动镜像

**Monorepo 与 pnpm（速览）**

- **Monorepo**：单仓库多模块，相同依赖提升到顶层只装一次省磁盘、工程配置一致；代价是无项目级权限管控、体积可达数 G
- **pnpm**：严格 `node_modules` 结构根治幽灵依赖，`workspace:` 协议子包间互链、避免手写 `npm link`；完整工程化见[前端工程化 / Monorepo 工程化](../../进阶/前端工程化/Monorepo工程化.md)
