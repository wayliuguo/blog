## 1. 基础命令与提交历史

### 1.1 常用命令速览

每个 Git 仓库从 `init` 开始，之后几乎每天都在"写提交 / 看历史 / 回退"。常用命令：

| 命令 | 作用 |
| ---- | ---- |
| `git init` | 在当前目录初始化一个空仓库 |
| `git add <file>` | 把改动加入暂存区 |
| `git commit -m "说明"` | 把暂存区固化成一个提交 |
| `git status` | 查看工作区 / 暂存区 / 分支状态 |
| `git log` | 查看提交历史；`--oneline` 紧凑单行、`--graph` 用 ASCII 显示分支图 |

撤销回退的两条主线在 1.2 展开。

### 1.2 撤销与回退：reset 与 revert

撤销历史有两条哲学不同的路：**`reset` 改写历史**、**`revert` 不改写历史**。核心抉择点是"这条提交推到共享分支没有"。

**`reset`：改写历史**。本质是**移动分支指针**，把 HEAD 指回旧提交，中间的提交从本地历史消失。三种模式由浅入深：

| 模式 | 移动 HEAD | 暂存区 | 工作区 | 后果 |
| ---- | ---- | ---- | ---- | ---- |
| `--soft` | ✅ | 保持 | 保持 | 改动留在暂存区 |
| `--mixed`（默认） | ✅ | 重置 | 保持 | 改动回到工作区，等同未 `add` |
| `--hard` | ✅ | 重置 | 重置 | **未提交改动全丢，慎用** |

`reset` 会**改写历史**：已推送到远程共享分支的提交不要 `reset` 后再 `--force`，那会改掉别人已基于其开发的历史、造成他们本地与远端冲突。此时改用 `revert`。

**`revert`：新建一个相反的提交抵消目标**。`git revert commitId` 生成的新提交内容正好抵消目标提交，原提交链原样保留；因为历史不变，其他人 `pull` 无碍——适合已推送场景。

> 改提交信息时常进 vim。小抄：`:wq` 保存退出、`:q!` 强制丢弃退出；命令模式 / 插入模式（`i`）/ 普通模式是 vim 的三模式切换。

## 2. 分支协作与远程仓库

### 2.1 远程仓库管理

`remote` 只记录"远程地址映射"，本地历史与分支不受影响：

```
git remote -v                查看已关联的远程（url）
git remote rm origin         移除旧的远程关联
git remote add origin <url>  添加新的远程（换 Gitee/GitHub 源）
git push -u origin main      首次推送：-u 建立本地与远程分支关联，之后可省参数
```

换源后首次推送要用 `-u` 或明确指定远程分支，否则分支关联可能仍是旧地址。

### 2.2 功能分支工作流

团队协作的标准姿势是**功能分支**：从主分支拉一条只属于自己的分支开发，合入前过评审，保证主分支始终可发布。

```
git checkout -b feature/xxx   从当前分支拉功能分支并切过去
→ 开发并多次提交
→ git push 推远程，发 PR / MR
→ 评审合入 → 其他人 git pull 同步
```

- **不直接往主分支乱推**；一个功能一条分支、生命周期宜短，长期不合并的分支与主干差异越大、合并越痛。
- 分支管理：`git branch -vv` 看本地分支与远程的关联，`git merge` 合并分支。
- PR/MR 顺带提供评审与 CI 卡点，合入后再统一同步。

### 2.3 合并冲突与解决

**冲突怎么产生**：同一文件**同一区域**被两个分支各自修改、Git 无法自动合并时产生冲突。冲突文件在 `git status` 里标 `both modified`，文件内出现三行标记：

```
<<<<<<< HEAD
当前分支保留的内容
=======
另一分支的内容
>>>>>>> feature/xxx
```

- 手动决定保留哪一边（可全删标记、按需选留），删掉 `<<<<<<<` / `=======` / `>>>>>>>` 标记后 `git add` + `commit` 就完成解决。
- 冲突只发生在「双方都改了的重叠区间」；**提前 `pull`、提交粒度单一**（一个提交只做一件事）能显著减少冲突。

### 2.4 同步策略：merge 与 rebase

`git pull` 默认是 `fetch` + `merge`，会产生分叉的合并提交；`git pull --rebase` 把本地提交"挪"到远端最新之后，历史更线性：

```
pull 默认      fetch + merge → 主干出现分叉合并点
pull --rebase  fetch 后把本地未推送提交逐个重放到远端最新之后 → 一条直线
```

- 本地有未推送提交时 `rebase` 更清爽；**已推送过的共享提交不要 rebase**——等同改写他人已见的历史。

## 3. 跨仓库同步与多包工程

### 3.1 Gitee / GitHub 镜像同步

在 Gitee 配镜像，让提交自动联动到 GitHub，不用手动两边推：

```
Gitee「管理 → 仓库镜像管理 → 添加镜像」
  选 Push 方向 → 填目标仓库地址与私人令牌（令牌需含 repo 权限）
  提交到 Gitee → 自动同步到 GitHub（最短间隔 5 分钟）
```

- Push 方向只自动同步"提交到 Gitee"这一向，GitHub 上的改动要回推 Gitee 需另配 Pull 方向镜像。
- Push 方向会自动同步分支 / 标签 / 提交。建议统一以 Gitee 为提交主力、GitHub 作联动镜像。

### 3.2 Monorepo 与 pnpm 速览

**Monorepo**：把一个工程的多个模块放进**同一个仓库**管理。收益与代价：

```
收益   相同依赖提升到顶层只装一次，省磁盘；多个包工程配置一致，改一处全局生效
代价   没有项目级权限管控（所有人能看全量代码）；仓库体积大、git clone 慢
```

**pnpm**：用**内容寻址存储 + 严格 `node_modules` 结构**根治了 npm 扁平结构的「幽灵依赖」——npm3 把依赖提到顶层，导致未声明却可访问的包出现；pnpm 只在根目录放显式声明的包、其余放 `.pnpm` 下。子包间用 `workspace:` 协议互链，避免手写 `npm link`。完整工程化（workspace 配置、增量构建、任务编排、幽灵依赖治理）见进阶·前端工程化模块的「Monorepo 工程化」。
