# 模块面试题 · 工程协作

## 1. 基础命令与提交历史

### Q1（1.2）｜ `git reset` 和 `git revert` 的区别？什么时候用哪个？

- **判断**：`reset` 改写历史（移动 HEAD）、`revert` 不改写历史（新建一个相反的提交）；已推送到共享分支就只用 `revert`。
- **展开**：`reset --hard commitId` 把 HEAD 及暂存区/工作区都指回旧提交、之后的提交从本地历史消失；`revert commitId` 生成的新提交内容正好抵消目标提交、原提交链保留。
- **佐证**：
```
reset   移动分支指针、抹掉中间提交   → 改写历史
revert  新增相反提交抵消目标提交      → 保留历史
```
- **边界**：`reset` 改写了别人已基于其开发的远端历史，强推 `--force` 会让他人本地冲突；`revert` 因为历史不变、其他人 `pull` 无碍。追问：已推送的分支想回退会选哪个？——revert。

### Q2（1.2）｜ `reset` 的 `--soft` / `--mixed` / `--hard` 三种模式差别？

- **判断**：由浅入深——`--soft` 只移动 HEAD、`--mixed`（默认）重置暂存区、`--hard` 连工作区一起重置（未提交改动全丢）。
- **展开**：`reset` 本质是移动分支指针，三模式的区别在于"指针移动后，是否把暂存区、工作区也回退到目标提交状态"。
- **佐证**：
```
--soft     仅 HEAD 回退，改动留暂存区
--mixed    默认，HEAD + 暂存区回退，改动回工作区
--hard     HEAD + 暂存区 + 工作区全部回退
```
- **边界**：`--hard` 会丢弃所有未提交改动，慎用；`reset` 改写历史，用于已推共享分支前一定要想清楚。追问：只想改 commit message 且不想丢改动？——`--soft` 退回后重新 `commit`。

## 2. 分支协作与远程仓库

### Q3（2.1）｜ 仓库地址变了（换 Gitee/GitHub 源）怎么改远程？`remote` 相关命令各干什么？

- **判断**：`git remote -v` 查看关联、`remote rm` + `remote add` 换源、`push -u origin main` 首次指定上游。
- **展开**：`remote` 只记录远程地址映射，删 `origin` 再 `add` 换个地址即可，本地历史与分支不受影响；`-u` 把本地分支与远程分支关联，之后可省参数直接 `push`。
- **边界**：换源后首次推送到新地址要用 `-u` 或明确指定远程分支，否则分支关联可能仍是旧地址。追问：想同时保留旧链接再加一个新源？——用第二个名字 `git remote add github <url>`。

### Q4（2.2）｜ 功能分支工作流长什么样？

- **判断**：从主分支拉功能分支开发 → 推远程发 PR/MR → 评审合入 → 其他人 `pull` 同步；不直接往主分支乱推。
- **展开**：`git checkout -b feature/xxx` 建分支隔离改动，PR 提供评审与 CI 卡点，合入后再统一同步，保证主分支始终可发布。
- **边界**：分支生命周期宜短，长期不合并的分支与主干差异越大、合并越痛。追问：功能开发到一半想切回主分支看东西？——先 `commit` 或 `stash`，再切回。

### Q5（2.3）｜ 合并冲突怎么产生的、怎么解决？

- **判断**：同一文件的同一区域被两个分支各自修改、Git 无法自动合并时产生冲突；手动在标记区选留后 `add` + `commit` 即解决。
- **展开**：冲突文件标 `both modified`，体内 `<<<<<<< HEAD` 到 `=======` 是当前分支内容、`=======` 到 `>>>>>>> branch` 是另一分支内容，删掉标记并保留正确代码即可。
- **佐证**：
```
<<<<<<< HEAD
保留当前分支的这版
=======
另一分支的改动
>>>>>>> feature/xxx
```
- **边界**：冲突只发生在「双方都改了的重叠区间」；提前 `pull`、提交粒度单一（一个提交只做一件事）能显著减少冲突。追问：多个文件冲突怎么办？——按文件逐个处理并 `add` 标记已解决。

### Q6（2.4）｜ `git pull`（默认合并式）和 `git pull --rebase` 有什么区别？

- **判断**：默认 `pull` 走 merge、产生分叉的合并提交；`pull --rebase` 把本地提交"挪"到远端最新之后，历史更线性。
- **展开**：`pull` = `fetch` + `merge`；`--rebase` 用变基方式把本地优于远端的提交逐个重放到远端提交之后，主干保持一条直线。
- **边界**：本地有未推送提交时 rebase 更清爽；已推送过的共享提交不要 rebase，等同改写他人已见的提交。追问：rebase 途中出现冲突？——解完后 `git rebase --continue`，不想继续用 `--abort`。

## 3. 跨仓库同步与多包工程

### Q7（3.1）｜ Gitee 镜像到 GitHub 是怎么配的、有什么限制？

- **判断**：在 Gitee「仓库镜像管理」加 Push 方向镜像到 GitHub，提交到 Gitee 自动同步；最短间隔 5 分钟。
- **展开**：镜像按方向同步分支/标签/提交，私人令牌需含 `repo` 权限否则镜像不可用。
- **边界**：Push 方向只自动同步"提交到 Gitee"这一向；GitHub 上的改动要回推 Gitee 需另配 Pull 方向镜像；建议统一以 Gitee 为提交主力、GitHub 作联动镜像。追问：同步失败的可能原因？——令牌权限不足（需 `repo` 全权限）。

### Q8（3.2）｜ 什么是 Monorepo？pnpm 相比 npm 扁平结构解决了什么问题？

- **判断**：Monorepo 是单仓库管理多模块；pnpm 用内容寻址存储 + 严格 `node_modules` 结构，根治了 npm 扁平结构的「幽灵依赖」。
- **展开**：npm3 扁平化把依赖提到顶层，未声明却可访问的包叫幽灵依赖；pnpm 只在根目录放显式声明的包、其余在 `.pnpm` 下，子包间用 `workspace:` 协议互链，避免手写 `npm link`。
- **边界**：Monorepo 代价是无项目级权限管控、仓库体积可达数 G、`git clone` 慢；完整工程化（workspace 配置、增量构建、任务编排、幽灵依赖治理）见进阶·前端工程化模块的「Monorepo 工程化」。追问：pnpm 子包互相依赖怎么装？——用 `workspace:*` 协议指向本仓内的子包。
