## 一、撤销与回退

### Q1: `git reset` 和 `git revert` 的区别？什么时候用哪个？

- **结论**：`reset` 改写历史（移动 HEAD）、`revert` 不改写历史（新建一个相反提交）；已推送到共享分支就只用 `revert`。
- **原理**：`reset --hard commitId` 把 HEAD 及工作区/暂存区都指回旧提交，之后的提交从本地历史消失；`revert commitId` 生成的提交内容正好抵消目标提交，原提交链保留。
- **边界**：`reset` 改写了别人已基于其开发的远端历史，强推 `--force` 会让他们本地历史与远端冲突；`revert` 因为历史不变，其他人 `pull` 无碍。

### Q2: `reset` 的 `--soft` / `--mixed` / `--hard` 三种模式差别？

- **结论**：三者都由浅入深——`--soft` 只移动 HEAD（改动留暂存区）、`--mixed`（默认）更新暂存区、`--hard` 连工作区一起重置（未提交改动全丢）。
- **原理**：`reset` 本质是移动分支指针；三模式区别在于"指针移动后，是否把暂存区、工作区也回退到目标提交状态"。
- **边界**：`--hard` 会丢弃所有未提交改动，慎用；`reset` 改写历史，用于已推共享分支前一定要想清楚。

## 二、分支与协作

### Q3: 功能分支工作流长什么样？

- **结论**：从主分支拉功能分支开发 → 推远程发 PR/MR → 评审合入 → 其他人 `pull` 同步；不直接往主分支乱推。
- **原理**：`git checkout -b feature/xxx` 建分支隔离改动，PR 提供评审与 CI 卡点，合入后再统一同步，保证主分支始终可发布。
- **边界**：分支生命周期宜短，长期不合并的分支与主干差异越大、合并越痛。

### Q4: `git pull`（默认合并式）和 `git pull --rebase` 有什么区别？

- **结论**：默认 `pull` 走 merge、产生分叉的合并提交；`pull --rebase` 把本地提交"挪"到远端最新之后，历史更线性。
- **原理**：`pull` = `fetch` + `merge`；`--rebase` 用变基方式把本地优于远端的提交逐个重放到远端提交之后，主干保持一条直线。
- **边界**：本地有未推送提交时 rebase 更清爽；已推送过的共享提交不要 rebase，等同改写他人已见的提交。

### Q5: 合并冲突怎么产生的、怎么解决？

- **结论**：同一文件的同一区域被两个分支各自修改，Git 无法自动合并时产生冲突；手动在标记区选留后 `add` + `commit` 即解决。
- **原理**：冲突文件里 `<<<<<<< HEAD` 到 `=======` 是当前分支内容，`=======` 到 `>>>>>>> branch` 是另一分支内容，删掉标记并保留正确代码即可。
- **边界**：冲突只发生在「双方都改了的重叠区间」；提前 `pull`、提交粒度单一（一个提交只做一件事）能显著减少冲突。

## 三、远程仓库

### Q6: 仓库地址变了（换 Gitee/GitHub 源）怎么改远程？`remote` 相关命令各干什么？

- **结论**：`git remote -v` 查看关联、`remote rm` + `remote add` 换源、`push -u origin main` 首次指定上游。
- **原理**：`remote` 只记录远程地址映射，删 `origin` 再 `add` 换个地址即可，本地历史与分支不受影响；`-u` 把本地分支与远程分支关联，之后可省参数。
- **边界**：换源后首次推送到新地址要用 `-u` 或明确指定远程分支，否则分支关联可能仍是旧地址。

## 四、镜像同步

### Q7: Gitee 镜像到 GitHub 是怎么配的、有什么限制？

- **结论**：在 Gitee「仓库镜像管理」加 Push 方向镜像到 GitHub，提交到 Gitee 自动同步；最短间隔 5 分钟。
- **原理**：镜像按方向同步分支/标签/提交，私人令牌需含 `repo` 权限否则镜像不可用。
- **边界**：Push 方向只自动同步"提交到 Gitee"这一向；GitHub 上的改动要回推 Gitee 需另配 Pull 方向镜像；建议统一以 Gitee 为提交主力、GitHub 作联动镜像。

## 五、Monorepo 与 pnpm

### Q8: 什么是 Monorepo？pnpm 相比 npm 扁平结构解决了什么问题？

- **结论**：Monorepo 是单仓库管理多模块；pnpm 用内容寻址存储 + 严格 `node_modules` 结构，根治了 npm 扁平结构的「幽灵依赖」。
- **原理**：npm3 扁平化把依赖提到顶层，未声明却可访问的包叫幽灵依赖；pnpm 只在根目录放显式声明的包，其余在 `.pnpm` 下，子包间用 `workspace:` 协议互链，避免手写 `npm link`。
- **边界**：Monorepo 代价是无项目级权限管控、仓库体积可达数 G、`git clone` 慢；完整工程化（workspace 配置、增量构建、任务编排、幽灵依赖治理）在[前端工程化 / Monorepo 工程化](../../进阶/前端工程化/Monorepo工程化.md)。
