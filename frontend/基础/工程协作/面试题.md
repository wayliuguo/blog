## 一、基础概念

### Q1: `git reset` 和 `git revert` 的区别？什么时候用哪个？（正文）

- **结论**：`reset` 改写历史（移动 HEAD）、`revert` 不改写历史（新建一个相反提交）。已推送到共享分支就只用 `revert`。
- **原理**：`reset --hard commitId` 把 HEAD 及工作区/暂存区都指回旧提交，之后的提交从本地历史消失；`revert commitId` 生成的提交内容正好抵消目标提交，原提交链保留。
- **边界**：`reset` 改写了别人已基于其开发的远端历史，强推 `--force` 会让他们本地历史与远端冲突；`revert` 因为历史不变，其他人 `pull` 无碍。
- **追问**：`reset --soft` 和 `--mixed` 差在哪？→ `--soft` 只动 HEAD、改动留在暂存区；`--mixed`（默认）额外更新暂存区、工作区不动。

### Q2: 合并冲突怎么产生的、怎么解决？（正文）

- **结论**：同一文件的同一区域被两个分支各自修改，Git 无法自动合并时产生冲突；手动在标记区选留后 `add` + `commit` 即解决。
- **原理**：冲突文件里 `<<<<<<< HEAD` 到 `=======` 是当前分支内容，`=======` 到 `>>>>>>> branch` 是另一分支内容，删掉标记并保留正确代码即可。
- **边界**：冲突只发生在「双方都改了的重叠区间」；提前 `pull`、提交粒度单一（一个提交只做一件事）能显著减少冲突。
- **追问**：`git pull --rebase` 和 `git pull` 合并式有什么区别？→ 前者把本地提交"挪"到远端最新之后，历史线性；后者产生一个 merge 提交，历史分叉。

### Q3: 功能分支工作流长什么样？（正文）

- **结论**：从主分支拉功能分支开发 → 推远程发 PR/MR → 评审合入 → 其他人 `pull` 同步；不直接往主分支乱推。
- **原理**：`git checkout -b feature/xxx` 建分支隔离改动，PR 提供评审与 CI 卡点，合入后再统一同步，保证主分支始终可发布。
- **边界**：分支生命周期宜短，长期不合并的分支与主干差异越大、合并越痛。
- **追问**：`branch -vv` 看什么？→ 看每个本地分支与哪个远程分支关联、领先/落后几个提交。

### Q4: Gitee 镜像到 GitHub 是怎么配的、有什么限制？（正文）

- **结论**：在 Gitee「仓库镜像管理」加 Push 方向镜像到 GitHub，提交到 Gitee 自动同步；最短间隔 5 分钟。
- **原理**：镜像按方向同步分支/标签/提交，私人令牌需含 `repo` 权限否则镜像不可用。
- **边界**：Push 方向只自动同步"提交到 Gitee"这一向；GitHub 上的改动要回推 Gitee需另配 Pull 方向镜像。
- **追问**：为什么建议以 Gitee 为提交主力？→ 国内访问快，GitHub 作联动镜像，避免两边手动提交。

### Q5: 什么是 Monorepo？pnpm 相比 npm 扁平结构解决了什么问题？（正文）

- **结论**：Monorepo 是单仓库管理多模块；pnpm 用内容寻址存储 + 严格 `node_modules` 结构，根治了 npm 扁平结构的「幽灵依赖」。
- **原理**：npm3 扁平化把依赖提到顶层，未声明却可访问的包叫幽灵依赖；pnpm 只在根目录放显式声明的包，其余在 `.pnpm` 下，子包间用 `workspace:` 协议互链，避免手写 `npm link`。
- **边界**：Monorepo 代价是无项目级权限管控、仓库体积可达数 G、`git clone` 慢。
