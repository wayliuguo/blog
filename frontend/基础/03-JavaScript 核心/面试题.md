# 模块面试题 · JavaScript 核心

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。

## 一、类型与比较

### Q1: `==` 与 `===` 的区别？类型转换规则？（第 01 篇）

- **结论**：`===` 不转类型，`==` 会先做类型转换再比较；业务代码一律用 `===`。
- **原理**：`==` 的转换规则有陷阱——`null == undefined` 为 true，`'0' == 0` 为 true，`[] == false` 为 true；`===` 只在"类型相同且值相同（或同为 NaN 之外的引用同一对象）"时为 true。
- **边界**：`NaN` 连 `===` 自己都 false，判断用 `Number.isNaN`；`Object.is` 是更严格的 `===`（能区分 `-0` 与 `+0`）。
- **追问**：`==` 唯一的合理用法是 `x == null` 同时判断 `null` 与 `undefined`，但团队规范通常禁止。
- **场景**：表单校验判空、if 分支判断一律 `===`，避免 `'0'` 这类字符串意外通过。

### Q2: 数据类型有哪些？怎么准确判断类型？（第 01 篇）

- **结论**：7+1 种——原始类型（string/number/boolean/null/undefined/symbol/bigint）+ 对象类型；准确判断用 `Object.prototype.toString.call`。
- **原理**：`typeof` 对 null 返回 `'object'`（历史 bug）、对函数返回 `'function'`，无法细分数组/日期等；`Object.prototype.toString.call(x)` 返回 `[object Array]` 这类精确标签。
- **边界**：`Array.isArray` 比 toString 更轻、且对跨 iframe 的数组仍可靠；`instanceof` 判断类实例受原型链与跨 realm 影响。
- **追问**：`typeof Symbol()` 返回 `'symbol'`、`typeof 1n` 返回 `'bigint'`，原始类型只有这些，其余都是 object。
- **场景**：埋点上报前 `toString` 判断参数类型，避免把 `Date` 误当普通对象序列化。

### Q3: 深浅拷贝的区别？怎么实现？（第 01 篇）

- **结论**：浅拷贝只复制一层引用，深拷贝递归复制全部层级；默认场景用浅拷贝，数据要独立才用深拷贝。
- **原理**：浅拷贝（`{...obj}` / `Object.assign`）共享内层引用，改内层会互相影响；深拷贝要递归遍历，`WeakMap` 缓存已拷贝对象防循环引用。
- **边界**：`JSON.parse(JSON.stringify(x))` 有先天缺陷——丢 undefined/Symbol/函数、Date 变字符串、BigInt 报错、循环引用抛错；`structuredClone` 是原生替代，但函数仍不支持。
- **追问**：原型链不被深拷贝保留；拷贝成本与数据规模成正比，大对象慎用。
- **场景**：表单提交前 `structuredClone` 一份做对比；组件 props 派生 state 用浅拷贝 + 不可变更新即可。

## 二、作用域与闭包

### Q4: `var` / `let` / `const` 的区别？暂时性死区？（第 02 篇）

- **结论**：`var` 函数级作用域且可重复声明，`let`/`const` 块级作用域且不可重复声明；`const` 绑定不可变（引用不可变，内容可变）。
- **原理**：`var` 声明提升到函数顶部但赋值不提升；`let`/`const` 也存在提升但被"暂时性死区"（TDZ）保护——声明前访问直接 `ReferenceError`。
- **边界**：`const` 保证的是"绑定不可变"不是"对象不可变"，`const a = {x:1}; a.x = 2` 合法。
- **追问**：TDZ 让"提升"不再是"undefined 可用"，是 ES6 之后作用域语义最大的变化。
- **场景**：`for` 循环计数器用 `let`，每次迭代独立绑定，配合闭包不再需要 IIFE 包一层。

### Q5: 什么是闭包？实际用来做什么？（第 02 篇）

- **结论**：闭包 = 函数 + 其词法作用域引用，让内层函数能访问外层函数的变量，即使外层已经执行完。
- **原理**：函数定义时把当前作用域链记进 `[[Environment]]`，执行时沿链查找变量；外层活动对象只要还被闭包引用就不会被回收。
- **边界**：过度闭包会让变量常驻、造成内存泄漏（大对象被闭包引用、事件监听器未解绑）；用完的引用置 null。
- **追问**：闭包捕获的是变量引用不是值拷贝——经典 `var` + 循环全输出最后一个值，`let` 每次迭代独立绑定才救回来。
- **场景**：模块化私有变量、防抖节流保存 timer、接口竞态的"请求标记位"（保存当前最新标记）。

### Q6: `this` 的指向规则？箭头函数为什么特殊？（第 02 篇）

- **结论**：`this` 在**调用时**决定，按优先级从低到高是 普通调用（window/undefined）→ 方法调用（对象）→ `call`/`apply`/`bind` 显式绑定 → `new`。
- **原理**：函数执行时引擎按调用形态决定 `this`；箭头函数**没有自己的 this**，捕获定义时外层词法作用域的 `this`，也不受 call/apply/bind/new 影响，且不能 `new`、没有 `arguments`。
- **边界**：把 `obj.fn` 单独取出来调用，`this` 就变回普通调用（window/undefined）——这是输出题最常见的陷阱；严格模式下普通调用 `this` 是 `undefined`。
- **追问**：`arguments` 是类数组（有 length、无数组方法），转真数组用 `Array.from(arguments)`；箭头函数内没有自己的 `arguments`。
- **场景**：回调里 `this` 丢失（`setTimeout`、事件监听）统一用箭头函数或显式 `bind` 修复；Vue/React 组件方法绑定同理。

## 三、原型与继承

### Q7: 原型链与继承？`class` 与 `new` 的本质？（第 03 篇）

- **结论**：对象通过 `[[Prototype]]` 链式查找属性，继承的本质是"沿链查找"；`class` 是构造函数的语法糖。
- **原理**：`Object.create` 显式建链，`class extends` 编译成原型链 + 静态继承；属性查找沿原型链直到 `null`。
- **边界**：链过长影响查找性能；原型上共享引用型属性会被所有实例共享（要放实例上）；`class` 与旧式构造函数的 `new` 行为一致。
- **追问**：`A instanceof B` 判断的是 `A` 的原型链上是否存在 `B.prototype`，不是"构造自"。
- **场景**：业务错误类继承 `Error` 保持 `instanceof` 语义；组件基类抽公共方法。

### Q8: 手写 `new` 与 `instanceof`？（第 06 篇）

- **结论**：`new` 做四件事——建对象、链原型、绑 this 执行、返回；`instanceof` 沿原型链找 prototype。
- **原理**：`obj = Object.create(ctor.prototype)`；`ret = ctor.call(obj, ...args)`；`ret` 是对象则返回 `ret`，否则返回 `obj`。`instanceof` 循环 `obj = Object.getPrototypeOf(obj)` 比对 `ctor.prototype`。
- **边界**：构造函数显式返回原始值会被忽略、返回对象则覆盖新对象；箭头函数没有 prototype，不能被 `new`。
- **追问**：`Object.create(null)` 造出的对象没有原型链，`instanceof` 恒 false、也没有 `toString`。
- **场景**：面试手写题标配，同时考察对原型链、this 绑定的理解。

### Q9: `call` / `apply` / `bind` 的区别？怎么手写？（第 06 篇）

- **结论**：三者都用于显式绑定 `this`；`call` 参数逐个传、`apply` 参数数组传、`bind` 返回新函数（不立即执行）。
- **原理**：手写 `call` 的思路是"把函数临时挂到目标对象上调用"（`target.fn = this; target.fn(...)`），`apply` 同理会展开数组，`bind` 用闭包保存 `this` 与部分参数、返回包装函数。
- **边界**：`bind` 返回的函数 `this` 已固化，后续 `call`/`apply` 无法再改（new 除外）；箭头函数没有自己的 `this`，`call`/`apply`/`bind` 对它无效。
- **追问**：`bind` 还能做"偏函数"（预置参数）；`fn.bind(null, i)` 在循环里会立刻固化 `i` 的值。
- **场景**：事件处理器传参 `fn.bind(null, id)`、借用方法 `Array.prototype.slice.call(arguments)`、类组件方法绑定。

## 四、异步与事件循环

### Q10: 事件循环中宏任务与微任务的执行顺序？（第 04 篇）

- **结论**：每轮先执行一个宏任务，再清空整个微任务队列，然后才进入下一轮。
- **原理**：执行顺序是 同步代码 → 微任务（`Promise.then` / `queueMicrotask` / `MutationObserver`）→ 宏任务（`setTimeout` / I/O / 渲染）；微任务里再产生的微任务会继续执行完。
- **边界**：`requestAnimationFrame` 在渲染前执行，渲染时机在宏任务之间；`setTimeout(0)` 并不保证 0ms，前面有微任务就插队，嵌套时最小延迟 4ms。
- **追问**：`queueMicrotask` 与 `Promise.then` 机制相同，但前者不产生 Promise 包装、更轻。
- **场景**：React/Vue 的批量更新依赖微任务合并多次状态变更；上报放在微任务里不阻塞主流程。

### Q11: Promise 的状态机？`all` / `race` / `allSettled` 的区别？（第 04 篇）

- **结论**：Promise 三态——pending → fulfilled / rejected，状态一经落定不可逆；选型看"一个失败怎么算"。
- **原理**：`all` 一败俱败（短路）、`allSettled` 等全部落定、`any` 取首个成功、`race` 取首个落定；`then` 返回新 Promise 实现链式。
- **边界**：`all` 的空数组立即 fulfilled；`race` 常用于超时控制（配合 `setTimeout` reject）；忘记 `catch` 会产生 `unhandledrejection`。
- **追问**：`await` 就是 `then` 的语法糖，`async` 函数返回值会被包装成 Promise。
- **场景**：并行请求三个接口全要 → `Promise.all`；埋点批量上报不互相影响 → `allSettled`。

### Q12: `async/await` 的原理？（第 04 篇）

- **结论**：`async/await` 是 Generator + Promise 的语法糖，本质还是事件循环里的异步回调。
- **原理**：`await` 把后续代码放进 `then` 回调，挂起当前 async 函数、不阻塞主线程；编译为状态机（类似 Generator 的 yield/resume）。
- **边界**：`await` 只挂起"当前 async 函数的后半段"，从不阻塞事件循环；`for` 循环里逐个 `await` 是串行，要并发用 `Promise.all(items.map(...))`。
- **追问**：忘了 `await` 会拿到 Promise 对象，异常变 `unhandledrejection`；`try/catch` 只在 async 函数内有效。
- **场景**：接口串行依赖用 `await` 顺序写（语义清晰），无依赖的多请求用 `Promise.all` 并发。

### Q13: 微任务（`queueMicrotask`）为什么能"上报不阻塞渲染"？（第 04 篇）

- **结论**：微任务在当前宏任务结束后、渲染前执行——上报早于渲染完成，又不阻塞主流程。
- **原理**：事件循环的检查点是"每个宏任务之后清空微任务队列"，渲染在其后；把上报放微任务里，既保证及时（不拖到下一帧）又不打断渲染。
- **边界**：微任务里做重活同样会卡渲染（清空队列是同步的）；递归微任务会饿死宏任务。
- **追问**：相比 `setTimeout` 上报，微任务更早、且不受宏任务调度延迟影响。
- **场景**：`requestReport` 用 `queueMicrotask` 批量上报性能/错误数据，不阻塞首屏渲染。

## 五、性能、内存与工程

### Q14: 防抖与节流的区别与实现？（第 06 篇）

- **结论**：防抖是"停止触发后等 N 秒再执行一次"，节流是"固定间隔内最多执行一次"；防抖适合"最后一次算数"，节流适合"定期执行"。
- **原理**：防抖每次触发重置定时器；节流用时间戳或定时器做闸门（leading/trailing 两种模式）。
- **边界**：防抖会让高频操作"迟迟不执行"（如搜索建议延迟感），节流保证频率上限但可能丢弃尾部触发。
- **追问**：`lodash.debounce` 支持 `immediate` 参数做首触即执行，滚动监听配 `{ leading: true, trailing: true }` 的节流。
- **场景**：搜索框输入防抖（300ms）、窗口 resize 节流、滚动加载节流。

### Q15: 垃圾回收：标记清除、引用计数与内存泄漏场景？（第 05 篇）

- **结论**：V8 主用标记-清除（分代收集），引用计数只是概念补充；泄漏多是"可达但不需要"的引用。
- **原理**：GC 从根（全局、调用栈）出发标记可达对象，清除不可达；新生代（Scavenge 复制）与老生代（标记-整理）分代处理。
- **边界**：闭包长引用、全局变量、未清理的定时器/事件监听器、分离 DOM（节点已移除仍被变量引用）是四大泄漏场景。
- **追问**：`WeakMap`/`WeakSet` 的键是弱引用，不阻止回收——缓存用 WeakMap 不会造成泄漏。
- **场景**：页面长驻 + 内存只增不减，先查全局变量与未解绑监听器，再用 Chrome Performance 堆快照按 Retained Size 排序定位。

### Q16: 接口竞态怎么用"请求标记位"解决？（附录）

- **结论**：用"请求标记位 + 最新一次生效"，比取消请求更稳——旧响应回来直接丢弃。
- **原理**：每次发起冲突请求前更新递增标记；响应回来比对当前标记，不一致则丢弃，保证展示的是最新请求结果。
- **边界**：为什么不用 AbortController？→ 取消要在请求层统一改造且容器内 fetch/XHR 行为不一致；标记位只丢弃结果、不中断请求，对"连续触发试算"这类场景足够。
- **追问**：丢弃次数要埋点吗？→ 要，计入埋点观测切换频率与冗余请求规模。
- **场景**：用户快速切换分期数/计息方式并发触发试算，网络乱序会让旧响应覆盖新结果——标记位保证最后一次生效。

### Q17: 含 50+ 字段、带级联校验与实时试算的借款表单卡顿，怎么优化？（附录）

- **结论**：把"计算"从"渲染"里拆出来——校验纯函数化、试算纯函数化、派生结果缓存，再解决输入与竞态。
- **原理**：卡顿根因是每次输入都触发全量校验与试算、且试算结果驱动大量受控组件重渲染；纯函数 + 单向数据流让计算可单测、可缓存、可回归。
- **边界**：派生结果缓存（相同输入直接取上次）要保证 key 覆盖全部输入要素，否则脏缓存；受控组件收敛到"需要实时受控的字段"。
- **追问**：长列表用虚拟滚动；输入防抖只对"非实时反馈"的字段用，试算字段要即时。
- **场景**：金融要素（还款方式/计息方式/分期数/金额）级联流转 → 纯函数试算 → UI 只消费派生状态；并发试算用请求标记位保证最后一次生效。
