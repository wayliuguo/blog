# 模块面试题 · React

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../../进阶/面试方法论.md)的五步答题法——结论/原理/边界/追问/场景。
> 题目来源：各篇正文原有 `## 面试题`（口径与新版正文一致）与原附录题库去重合并。

## 一、JSX 与组件基础

### Q1: JSX 的本质是什么？（第 01 篇）

- **结论**：JSX 是 `React.createElement` 的语法糖，产出 React 元素（普通对象）。
- **原理**：`<div className="x">hi</div>` → `createElement('div', { className: 'x' }, 'hi')` → `{ type, props, children }`；自定义组件首字母大写是因为 `type` 要指到函数/类。
- **边界**：JSX 不是模板字符串、不执行任意代码，注入安全由转义保证；JSX 里不能用 if/for 直接写，因为是表达式求值。
- **追问**：React 元素与 DOM 节点的区别？→ 元素是描述对象，DOM 是浏览器真实节点。
- **场景**：理解"列表要 `map` 返回 JSX"的本质——它是在构造元素数组，不是渲染模板。

### Q2: 函数组件与类组件的区别？（第 01 篇）

- **结论**：函数组件是"props 进、JSX 出"的纯函数，类组件用实例方法承载生命周期；现代写法一律函数组件 + Hooks。
- **原理**：函数组件每次渲染重新调用，状态由 Hooks 在调用顺序上存取；类组件有 `this` 与实例，生命周期方法（`componentDidMount` 等）被 `useEffect` 取代。
- **边界**：类组件需要 `this` 绑定、`constructor` 初始化，样板多；错误边界（Error Boundary）目前仍需类组件实现。
- **追问**：为什么 Hooks 时代函数组件更优？→ 逻辑可抽自定义 Hook 复用，无 `this` 指向问题。
- **场景**：React 19 管理后台全部函数组件 + Hooks，错误边界单独抽一个类组件兜底。

### Q3: props 与 state 的区别？（第 01 篇）

- **结论**：props 是父传子的外部数据（只读），state 是组件内部可变状态；props 变化或 setState 都会触发重渲染。
- **原理**：props 由父组件传入，子组件修改无效（单向数据流）；state 由 `useState` 管理，`setState` 触发重渲染并产出新渲染快照。
- **边界**：state 提升到公共父组件即"状态提升"，兄弟组件共享数据靠它；props 是引用，父级原地修改子级看不到变化（不可变更新）。
- **追问**：派生 state（props 变化重新计算）用"渲染期间计算"而非在 effect 里 setState。
- **场景**：表单组件内部值用 state，外部回填用 props；跨层传参用 Context 避免逐层透传。

### Q4: 受控组件与非受控组件？（第 01 篇）

- **结论**：受控组件的值由 state 持有（value + onChange），非受控由 DOM 自己持有（ref 读取）；需要校验/联动用受控。
- **原理**：受控把 DOM 输入"提升"进 React 状态，单向数据流闭环；非受控用 `defaultValue` + `ref`，DOM 是唯一事实源。
- **边界**：受控组件每个输入都触发重渲染，大表单要收敛受控字段；非受控无法做实时校验与联动。
- **追问**：中间态（indeterminate）checkbox 只能非受控（ref 设属性），受控表达不了。
- **场景**：借款表单的金额/计息方式要联动试算 → 受控；长表单里纯展示的备注输入 → 非受控。

### Q5: `key` 的作用与选择原则？（第 01 篇）

- **结论**：`key` 是节点身份标识，让 diff 复用走"移动"而非"删除重建"；用稳定唯一 id，别用 index。
- **原理**：diff 在同层按 key 匹配节点；中间插入/删除时，index 会让后续节点对错位复用，输入框状态、动画被错误迁移。
- **边界**：key 只在兄弟间唯一即可；数组整体重排（拖拽排序）更依赖 key 正确，否则整列状态错乱。
- **追问**：key 变了会怎样？→ 该节点被当"新节点"整棵重建，状态丢失、代价大。
- **场景**：审核列表用业务 id 作 key；拖拽排序后列表重排，key 稳定才能正确复用 DOM。

## 二、渲染与 diff

### Q6: 虚拟 DOM 与 diff 算法？（第 01 篇）

- **结论**：虚拟 DOM 是 UI 的 JS 描述，diff 对比新旧元素树、最小化真实 DOM 变更。
- **原理**：同层 diff（不跨层比较）、`key` 识别节点身份、`type` 不同直接重建子树、props 变化只更新属性。
- **边界**：diff 只是策略不是银弹——大规模列表仍需虚拟滚动 / memo；"虚拟 DOM 快"的说法不准确，快的是"可控的更新范围 + 声明式编程模型"。
- **追问**：React 为什么不直接操作 DOM？→ 声明式、可预测、跨平台（同构渲染到 Native）。
- **场景**：频繁更新的动态表单只改变化的字段节点，而不是整页重绘。

### Q7: React 渲染流程：render → reconcile → commit？（第 01 篇）

- **结论**：render 生成新元素树 → reconcile 对比找差异 → commit 把差异应用到 DOM 并执行副作用。
- **原理**：render 是纯计算（可中断），reconcile 产出变更清单（workInProgress），commit 一次性同步提交（不可中断）并触发 `useEffect`。
- **边界**：render 阶段不要有副作用（会被多次调用）；commit 是同步的，大更新会卡住主线程，所以有并发特性调度。
- **追问**：为什么分成两个阶段？→ render 可中断/可丢弃让出主线程，commit 必须一次完成保证一致性。
- **场景**：`startTransition` 把非紧急更新标记为可中断，后台列表同步不卡输入框。

### Q8: Fiber 是什么？为什么需要可中断渲染？（第 01 篇）

- **结论**：Fiber 是 React 的"工作单元"链表结构，把渲染拆成可中断的小任务，实现并发调度。
- **原理**：每个组件对应一个 Fiber 节点，连接成树；渲染在空闲时间片里分片推进（时间切片），高优先级更新（输入）可打断低优先级（列表）。
- **边界**：中断只发生在 render/reconcile 阶段，commit 仍同步；`useState` 基于优先级可被打断丢弃旧结果。
- **追问**：为什么以前会卡？→ 旧架构递归渲染整树不可中断，一帧内做不完就掉帧。
- **场景**：大列表首次渲染 + 用户同时输入——Fiber 让输入优先，列表后台分批完成。

### Q9: 渲染性能优化：并发特性、`startTransition`、懒加载？（附录）

- **结论**：优化三板斧——`startTransition` 降级非紧急更新、`React.lazy` + `Suspense` 按需加载、`memo`/`useMemo` 控制重渲染范围。
- **原理**：`startTransition` 标记的更新可被紧急更新打断；懒加载把大 chunk 拆到路由级；`memo` 对 props 浅比较跳过无变化子树的渲染。
- **边界**：缓存不是越多越好——`useMemo` 本身有开销，仅当计算昂贵或依赖引用稳定时用；过渡更新有延迟感知。
- **追问**：`useDeferredValue` 与 `startTransition` 区别？→ 前者处理"值"（搜索框），后者处理"更新"（setState 包层）。
- **场景**：搜索筛选大列表——输入用紧急更新，筛选结果 `useDeferredValue` 降级渲染。

## 三、Hooks

### Q10: Hooks 的规则？为什么不能条件调用？（第 02 篇）

- **结论**：只在顶层调用、只在函数组件（或自定义 Hook）调用；Hooks 按调用顺序存储状态。
- **原理**：React 用链表按顺序保存每个 hook 的 state；条件/循环里调用会让顺序错位，前后两次渲染读到的不是同一个 hook。
- **边界**：依赖数组需要稳定引用；`useEffect` 空依赖 + 引用外部变量就是闭包陷阱。
- **追问**：为什么依赖数组里写 setState 函数没事？→ setter 是稳定引用，不会触发重复执行。
- **场景**：自定义 Hook（`useAuth`/`useDebounce`）内部可以放心调 Hooks，只要不在 if 里调。

### Q11: `useEffect` 与 `useLayoutEffect` 的区别？（第 02 篇）

- **结论**：useEffect 在绘制后异步执行，useLayoutEffect 在绘制前同步执行；多数场景用 useEffect。
- **原理**：useLayoutEffect 在浏览器 paint 前同步运行，适合测量 DOM 与避免闪烁；useEffect 不阻塞渲染。
- **边界**：useLayoutEffect 在服务端渲染会警告（SSR 无布局时机）；需要同步读布局再改 UI 才用它。
- **追问**：什么时候必须 useLayoutEffect？→ 读 DOM 尺寸并据此改样式，用 useEffect 会闪一下。
- **场景**：请求数据、订阅、防抖副作用用 useEffect；拖拽中读元素尺寸设定位用 useLayoutEffect。

### Q12: `useMemo` / `useCallback` / `memo` 怎么用？什么时候不需要？（第 02 篇）

- **结论**：三者都控制"计算/渲染/引用"的重复成本——memo 拦组件渲染，useMemo 缓存计算值，useCallback 缓存函数引用；别默认全用。
- **原理**：`memo` 对 props 浅比较，无变化跳过渲染；`useMemo` 依赖不变返回上次结果；`useCallback` 保持函数引用稳定，配合 memo 的子组件 props 比较。
- **边界**：缓存有开销（比较 + 内存）；计算不昂贵、引用不敏感就不需要；滥用会让依赖分析更难。
- **追问**：React Compiler 出现后这些会被自动记忆化，手写 memo 逐步可省。
- **场景**：列表项组件 `memo` + `useCallback` 稳定回调；昂贵派生（大数组过滤）用 `useMemo`。

### Q13: Hooks 闭包陷阱（stale closure）怎么解决？（第 02 篇）

- **结论**：回调/effect 捕获了旧渲染的 state，读到的是旧值；用函数式更新或 ref 保存最新值。
- **原理**：每次渲染是独立闭包，state 是常量；依赖数组不变则回调不重建，内部引用的旧值不更新。
- **边界**：函数式更新（`setCount(c => c + 1)`）解决"基于旧值的更新"，但不解决"读取最新值"——读场景用 ref。
- **追问**：为什么每次渲染都是独立闭包？→ state 不可变，重渲染 = 新作用域 + 新值。
- **场景**：`setInterval` 里读 count 一直拿 0——用 `countRef` 同步最新值，或依赖数组加 count 重建定时器。

## 四、组件通信与状态管理

### Q14: 组件通信的方式？（第 04 篇）

- **结论**：props 自上而下、回调向上、Context 跨层、事件总线 / 状态库做无关系通信；按层级就近选。
- **原理**：单向数据流下，"向下传 props、向上传回调"覆盖父子；Context 避免逐层透传（但有整棵子树重渲染成本）；全局状态库（Redux/Zustand）管理跨模块共享状态。
- **边界**：Context 值变了订阅者全重渲染——拆 Context 或配 selector；事件总线无类型约束、难追踪，能不用就不用。
- **追问**：状态提升 vs Context 怎么选？→ 只升一层用状态提升，跨很多层才上 Context/状态库。
- **场景**：审核列表项 → 父组件回调；主题/登录态 → Context；跨页面缓存 → Zustand。

### Q15: 状态管理选型：Context / Redux / Zustand 怎么取舍？（第 04 篇）

- **结论**：局部状态用 useState；跨层少量共享用 Context；复杂全局状态（缓存、派生、跨模块）用 Zustand（轻）或 Redux（重）。
- **原理**：Context 无 selector 会整树重渲染；Redux 强调单向流 + 中间件（redux-thunk/saga）+ DevTools，样板多；Zustand 基于外部 store + selector 订阅，最小重渲染。
- **边界**：选型看团队与规模——小项目 Zustand 够用，中后台强规范用 Redux Toolkit；别为"流行"上重型方案。
- **追问**：服务端状态（接口数据）和客户端状态（UI）分开管，缓存用 React Query/SWR 更合适。
- **场景**：运营后台登录态 + 主题用 Context，审核流与权限缓存用 Zustand。

## 五、React 19 与实战

### Q16: React 19 的新特性？（附录）

- **结论**：Actions（表单动作）、`use()`（读 Promise/Context）、React Compiler（自动记忆化）。
- **原理**：Actions 让表单提交自动管理 pending/error 状态；`use()` 可在条件中调用、读资源；编译器自动做 memo 替代手写 useMemo/useCallback。
- **边界**：新特性需配套生态（Router 7 / antd 兼容版本）；`use()` 与 Suspense 配合读异步资源。
- **追问**：React Compiler 解决了什么？→ 自动记忆化，减少"该不该 memo"的心智负担。
- **场景**：管理后台表单提交用 Actions 简化 pending 与错误处理，配合 `useActionState`。

### Q17: 可拖拽排序 + 实时搜索 + 分页的审核列表，怎么设计才能不卡？（附录）

- **结论**：分页 + 搜索防抖 + 列表项 memo + 拖拽最小变更 + 大列表虚拟滚动 + 状态收敛。
- **原理**：卡顿来自整树重渲染与每帧重排——列表项 memo 拦无关渲染，拖拽只更新排序字段（变更最小化），行多时虚拟滚动只渲染可见行。
- **边界**：拖拽态与列表数据分离——本地只存拖拽中间态，提交后才改服务端数据，避免拖动过程全列表重排。
- **追问**：性能度量用 React Profiler / DevTools 定位是"哪一层重渲染"，别凭感觉优化。
- **场景**：React 19 管理后台审核流——dnd-kit 拖拽只改排序字段 + 提交后刷新，搜索 300ms 防抖，列表项 memo。
