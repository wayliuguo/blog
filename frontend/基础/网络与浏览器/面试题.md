## 一、HTTP 与 HTTPS

### Q1: HTTP 与 HTTPS 的区别？混合加密是怎么工作的？

- **结论**：HTTPS = HTTP + TLS，在 TCP 之上补上加密、身份认证与完整性校验；安全核心是"混合加密"。
- **原理**：非对称加密只用于协商会话密钥，大量数据用对称加密（如 AES）传输，兼顾安全与性能；服务器向 CA 申请证书、客户端用内置根证书验证签名，防止中间人冒充。HTTPS 增加一次往返（TLS 握手）与计算开销，但能防窃听、篡改、伪装。
- **边界**：证书过期 / 自签会告警或阻断；`HSTS` 强制跳转可防降级攻击；HTTPS 页面加载 HTTP 子资源即"混合内容"，现代浏览器直接阻止脚本类子资源。

### Q2: TCP 三次握手与四次挥手的过程和意义？

- **结论**：三次握手建连（SYN → SYN+ACK → ACK），四次挥手断连（FIN → ACK → FIN → ACK）。
- **原理**：握手是为了双方确认收发能力并就初始序号（ISN）达成一致，防止历史报文串扰；挥手因为连接是全双工的，两端各自关闭、各需一次 FIN/ACK。
- **边界**：主动关闭方进入 `TIME_WAIT` 等待 2MSL，防止旧报文到达；大量短连接会堆积 `TIME_WAIT` 是服务端调优常见点；HTTPS 首次连接在 TCP 之后还要叠加 TLS 握手。

### Q3: HTTP 状态码分哪五类？常见状态码分别代表什么？

- **结论**：2xx 成功 / 3xx 重定向 / 4xx 客户端错误 / 5xx 服务端错误。
- **原理**：2xx——200 正常、201 已创建（POST 常用）、204 成功无内容；3xx——301 永久、302 临时、304 协商缓存命中（资源未变用缓存）；4xx——401 未认证 vs 403 无权限、404 不存在、405 方法不允许、429 限流；5xx——500 内部错误、502 网关收到无效响应、503 暂时不可用、504 网关超时。
- **边界**：401 与 403 一个"没认证"一个"没权限"最容易混；排查先看 4xx/5xx 归属客户端还是服务端问题。

### Q4: GET 与 POST 的本质区别？什么是幂等？

- **结论**：GET 与 POST 唯一本质差异是**语义**——GET 取数据、无请求体、幂等；POST 提交数据、有请求体、非幂等。
- **原理**：GET 可缓存、可收藏、可被预加载，参数放 URL；POST 参数放进请求体避免进 URL 与日志泄漏——两者传输是否安全取决于是否走 HTTPS，GET 明文参数并不"更不安全"。
- **边界**：GET 参数放 URL 有长度限制（服务器/代理限制，非协议规定）且会进访问日志；重试与用户重复点击依靠幂等性做正确决策——`PUT` 才是语义上幂等的方法，重复 POST 可能重复创建资源。

### Q5: 强缓存与协商缓存的区别？发版时缓存怎么做？

- **结论**：强缓存命中直接读本地、不发请求；协商缓存需一次往返拿 304 再复用。
- **原理**：强缓存看 `Cache-Control: max-age`（相对时间，优先）与 `Expires`（绝对时间、依赖客户端时钟），命中返回 200（from cache）；协商缓存带 `If-None-Match`（ETag，内容指纹，优先）或 `If-Modified-Since`（Last-Modified），服务器回 304。
- **边界**：`no-store` 完全放弃缓存，`no-cache` 是每次都要协商而非不缓存；HTML 不宜长缓存——内容更新用户看不到、发版失效困难；静态资源用"内容指纹文件名 + 长缓存"，内容变则文件名变、缓存自动失效，发版只换变了的那批文件。

### Q6: HTTP/1.1 的队头阻塞，HTTP/2、HTTP/3 分别怎么解决？

- **结论**：HTTP/1.1 同连接串行请求有队头阻塞；HTTP/2 用多路复用解决应用层，HTTP/3 用 QUIC（基于 UDP）解决传输层。
- **原理**：HTTP/1.1 一个连接同时只能一个请求，靠多连接（约 6 个）缓解；HTTP/2 二进制分帧 + 单连接多路复用 + 头部压缩（HPACK）+ 服务端推送；HTTP/3 把可靠传输挪到用户态 QUIC，内置 TLS 1.3、0-RTT、连接迁移，一个流丢包不影响其他流。
- **边界**：HTTP/2 的 TCP 层队头阻塞仍存在（一个 TCP 连接共享拥塞窗口）；服务端推送易浪费带宽、慎用。

### Q7: TCP 与 UDP 的区别？各自应用场景？

- **结论**：TCP 面向连接、可靠、有流量/拥塞控制；UDP 无连接、不可靠但快——"要可靠选 TCP，要低延迟选 UDP"。
- **原理**：TCP 三次握手建连，靠确认应答、超时重传、乱序重排保证可靠；UDP 直接发数据报、无握手无确认、丢包不重传。
- **边界**：TCP 面向字节流会粘包、要封包/拆包，UDP 面向报文、自带消息边界不会粘包；HTTP/HTTPS/WebSocket/文件传输走 TCP，实时音视频/直播/DNS/游戏走 UDP，QUIC 是"在 UDP 上自建可靠性"的折中。

### Q8: WebSocket 与 HTTP 的区别？即时通信方案怎么选？

- **结论**：WebSocket 是复用 HTTP 握手的全双工持久连接，服务器能主动推送；HTTP 是半双工请求-响应，服务器无法主动推送。
- **原理**：一次握手（HTTP Upgrade 101）后连接长驻、双方随时互发，数据帧轻量；HTTP 每次请求都带头部、只能客户端发起。
- **边界**：WebSocket 没有同源限制，服务端必须校验 `Origin` 防跨站连接；断线要自己重连（退避），空闲要心跳保活（代理会掐空闲连接），用 `wss://` 加密；即时通信性能 WebSocket > SSE > 长轮询 > 短轮询，兼容性反之——SSE 是单向流式 HTTP、实现简单且自动重连，但客户端不能推。

## 二、浏览器渲染原理

### Q9: 从输入 URL 到页面渲染，完整链路是什么？

- **结论**：URL → DNS → TCP（HTTPS 加 TLS）→ 请求 HTML → 解析构建 DOM/CSSOM → 渲染树 → 布局 → 绘制 → 合成。
- **原理**：每段都是关键渲染路径的一部分；DNS 走"浏览器/系统缓存 → 本地 DNS 递归 → 根/顶级/权威迭代"把域名换成 IP，可用 `dns-prefetch`/`preconnect` 预解析预热。
- **边界**：命中强缓存则完全跳过网络请求，301/302 会跟随 `Location` 重新请求；优化抓手对应每一段——`preconnect`/`dns-prefetch` 缩短连接、关键 CSS 内联、脚本 `defer`/module、资源 hash 长缓存。

### Q10: 哪些资源会阻塞解析或渲染？`defer` 与 `async` 有什么区别？

- **结论**：CSS 是渲染阻塞资源、必须全部拿到才能渲染；普通同步脚本阻塞解析，`defer` 在解析完后按序执行、`async` 下载完立即执行。
- **原理**：渲染要等 CSSOM 就绪，构造样式必须先拿到全部 CSS；`<script>` 遇到会暂停 HTML 解析先执行。
- **边界**：脚本放底部或加 `defer`/module 可避免阻塞首屏，`async` 适合互不依赖的独立脚本；减少关键资源数量与体积是让关键渲染路径变短的根本。

### Q11: 重排 / 重绘 / 合成什么区别？怎么减少？

- **结论**：重排（Layout）代价最高、必然伴随重绘；重绘（Paint）其次；合成（Composite）走 GPU 最廉价。
- **原理**：改几何属性（宽高、margin、增删节点）触发重排，读 `offsetWidth` 等会触发强制同步布局；只改颜色/背景触发重绘；`transform`/`opacity` 走合成层、不触及前两者。
- **边界**：动画只用 `transform`/`opacity` 是性能铁律；批量读写 DOM 避免"读-写"交替、`will-change` 适度（滥用占 GPU 内存）、`content-visibility` 跳过屏外渲染。

### Q12: DOM 事件流三个阶段？事件委托的原理与局限？

- **结论**：事件按 捕获 → 目标 → 冒泡 三阶段传播；事件委托 = 把子元素监听绑到公共祖先，利用冒泡统一处理。
- **原理**：`addEventListener(type, fn, useCapture)` 第三参 `true` 在捕获阶段触发、默认冒泡阶段，`onclick` 只能监听冒泡；委托回调里用 `e.target.closest(selector)` 定位真实目标。
- **边界**：委托省内存（N→1）且动态节点免重新绑定；`focus`/`blur`/`scroll`/`mouseenter`/`mouseleave` 不冒泡无法委托（`focus` 用 `focusin`），`mousemove` 高频事件在父级统一处理反而费计算；`stopPropagation` 阻止传播与 `preventDefault` 阻止默认行为互不相干。

### Q13: Cookie / localStorage / sessionStorage / IndexedDB 的区别与选型？

- **结论**：Cookie 随请求自动携带且容量最小（约 4KB），localStorage 同步持久（约 5MB），sessionStorage 标签页级，IndexedDB 是异步大容量数据库。
- **原理**：Cookie 由服务端 `Set-Cookie` 下发、请求自动带（也因此有 CSRF 面）；localStorage 同源持久、同步 API；sessionStorage 随标签页关闭清空；IndexedDB 是内置 NoSQL 事务型数据库，百 MB~GB 级，适合大量结构化数据。
- **边界**：会话态 / 随请求携带 → Cookie（HttpOnly + SameSite）；复杂大数据 → IndexedDB；跨标签页持久 → localStorage；关页即清临时态 → sessionStorage；localStorage 同步写大对象会卡主线程、容量满抛 `QuotaExceededError` 需 try/catch。

## 三、浏览器存储与本地缓存

### Q14: Cookie 的核心属性？SameSite 三种取值分别防什么？

- **结论**：Cookie 靠 `Expires/Max-Age`、`Path`、`Domain`、`Secure`、`HttpOnly`、`SameSite` 等属性控制过期、作用域与携带条件。
- **原理**：`Secure` 仅 HTTPS 传、`HttpOnly` 禁 JS 读（防 XSS 盗 Cookie）、`Domain` 可含子域共享；`SameSite` 三种取值——`Strict` 完全不带、`Lax` 跨站 POST 不带但顶导航 GET 会带（现代浏览器默认最优解）、`None` 全部带（最危险须配额外校验）。
- **边界**：凭证 Cookie 必须三件套 `HttpOnly + Secure + SameSite`，防 XSS 读走、防 CSRF 自动携带；`localStorage` 放凭证会被 XSS 一把读走，别存。

### Q15: Service Worker 的缓存策略怎么选？

- **结论**：SW 是运行在独立线程的网络代理，可拦截请求实现离线访问；以 Cache Storage（请求-响应）为单位缓存资源。
- **原理**：`caches.open`/`addAll`/`match` 读写；四种策略——Cache First（静态资源）、Network First（需较新又需离线）、Stale-While-Revalidate（先旧后新、后台更新）、Network Only（实时强一致）。
- **边界**：SW 必须在 HTTPS（或 localhost）下；升级要小心旧缓存不更新（配版本号清缓存）。

## 四、前端安全

### Q16: 什么是同源？CORS 的预检请求什么时候触发？

- **结论**：同源 = 协议 + 域名 + 端口三者全同；CORS 是浏览器基于响应头的跨源放行机制，预检（`OPTIONS`）只在"非简单请求"时触发。
- **原理**：简单请求（`GET`/`HEAD`/`POST` + 安全头 + `Content-Type` 只能是表单三类之一）直接发，靠响应 `Access-Control-Allow-Origin` 决定 JS 能否读；自定义头、非简单方法、`application/json` 会先 `OPTIONS` 预检，服务端回 `Allow-Methods`/`Allow-Headers`。
- **边界**：两条硬规则——`Allow-Credentials: true` 时 `Allow-Origin` 不能是 `*`（须回显具体源）；自定义响应头默认对 JS 不可见、必须列进 `Access-Control-Expose-Headers`。被拦时 JS 只拿到 `Failed to fetch`，但请求其实到了服务端也返回了——所以 CORS 挡不住攻击、不能当鉴权；工程首选同域部署或 dev server 代理，从架构上消灭跨源。

### Q17: XSS 的三种形态？怎么防御？

- **结论**：XSS 分 反射型（URL 注入）、存储型（入库持久化、危害最大可横向传播）、DOM 型（前端 JS 操作 DOM 时注入）；防御核心是"输入白名单 + 输出按上下文编码 + CSP 纵深"。
- **原理**：用户输入未转义进入 HTML/JS 执行；`innerHTML`/`v-html` 是高发点，`textContent` 只当文本；DOM 型危险入口是 `innerHTML`、`document.write`、`eval`、`location.hash`。
- **边界**：仅前端转义不够，需 CSP 与后端校验双层；富文本只能白名单（DOMPurify）净化，不能靠黑名单；Cookie 加 HttpOnly 防被盗。

### Q18: CSRF 怎么防御？`SameSite=Lax` 能防住什么、防不住什么？

- **结论**：CSRF 是"借用户凭证发起非预期请求"；防御三板斧是 SameSite Cookie、CSRF Token、Origin/Referer 校验。
- **原理**：浏览器自动携带 Cookie 的特点被利用——已登录 A 时访问恶意站 B，B 发出自动带 Cookie 的请求；`SameSite=Lax` 从根上阻断跨站 POST 携带，但跨站链接跳转触发的 GET 仍会带。
- **边界**：SameSite 防不住"同站子域"与"GET 副作用"，它只约束"浏览器带不带 Cookie"，Token/Origin 校验才是业务侧主动防御；Token 需防 XSS 窃取（配合 HttpOnly/CSP）；敏感操作加二次验证（验证码）。

### Q19: CSP 的 nonce / hash 原理与局限？

- **结论**：CSP 用白名单限制资源来源（核心指令 `default-src`/`script-src`/`style-src`/`img-src`/`connect-src`）；`nonce`/`hash` 是"动态内联脚本放行"方案，精确到单条脚本。
- **原理**：`Content-Security-Policy: script-src 'nonce-xxx'`——服务器给合法脚本标签加 `nonce` 属性，浏览器只执行 nonce 匹配的脚本；`'sha256-...'` 按内容哈希放行；配 `report-uri` 上报可及时发现真实攻击。
- **边界**：nonce 每次响应要随机、写死等于没设；hash 每次改动都要重算、适合静态页面；CSP 只管"来源"，不防 DOM 型 XSS 把恶意脚本挂进已被信任的标签；防点击劫持用 `frame-ancestors`（现代首选）或 `X-Frame-Options`。

## 五、场景设计题

### Q20: 数据实时性要求高的接口，缓存策略怎么定？

- **结论**：按数据时效性分级——资金/强实时类绝不缓存，配置/字典类可长缓存，用户资料类短缓存；缓存 key、TTL、清 key 策略要配套。
- **原理**：缓存 key = URL + 序列化入参，key 必须含用户标识；TTL 过期或写操作后主动清 key；缓存放进程内内存（模块级 Map）不落盘。
- **边界**：金额、额度、费率、还款计划错一次就是资金错误，必须实时；TTL 加随机抖动防雪崩；写操作后清相关 key，否则串数据。
