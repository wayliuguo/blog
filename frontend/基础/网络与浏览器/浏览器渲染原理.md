# 浏览器渲染原理

当你在地址栏输入一个 URL 按下回车，浏览器在幕后要完成从"网络抓取"到"像素上屏"的一整套流水线。这个过程涉及多进程调度、HTML/CSS 解析、布局计算、绘制与合成。理解浏览器渲染原理，是前端工程师排查性能问题、写出流畅页面的必修课。

这篇文章我们按"架构 → 导航 → 解析 → 布局 → 绘制 → 优化"的脉络展开，最后给出可落地的优化策略清单。

## 一、浏览器的多进程架构

### 1. 为什么需要多进程

如果把浏览器比作工厂，那么"渲染引擎"（如 Chrome 的 Blink）单线程跑所有页面，任何一个页面崩溃或卡顿都会拖垮整个浏览器。多进程架构的价值在于**隔离与稳定**：某个标签页崩溃不会导致整个浏览器瘫痪，同时天然提供安全沙箱。

### 2. Chrome 的主要进程

| 进程 | 职责 |
| --- | --- |
| **浏览器主进程（Browser）** | 管理 UI、地址栏、书签、网络、文件访问、以及其他进程的调度 |
| **渲染进程（Renderer）** | 每个标签页一个进程，负责页面解析、布局、绘制、脚本执行 |
| **GPU 进程（GPU Process）** | 负责图形合成与硬件加速绘制（Compositing 与光栅化） |
| **网络进程（Network）** | 统一处理网络请求 |
| **辅助进程** | 扩展、插件、音视频工具等独立进程 |

### 3. 渲染进程内的线程分工

渲染进程内部通常包含以下线程（不同浏览器实现略有差异）：

- **主线程（Main Thread）**：执行 JavaScript、解析 HTML/CSS、计算样式、布局、绘制——**大多数渲染工作都在这里**，是性能的"主战场"。
- **合成器线程（Compositor Thread）**：负责把已栅格化的图层合成到屏幕，理解何为"合成（Composite）"。
- **光栅线程 / 栅格化（Raster Threads）**：把绘制指令转换成像素位图。
- **事件处理器线程**：接收输入事件（点击、滚轮、键盘）。
- **网络线程 / 定时器线程 / Worker**：分别处理网络、`setTimeout`、`Web Worker` 等，避免阻塞主线程。

> 关键结论：浏览器渲染相关的绝大部分 CPU 工作集中在**渲染进程的主线程**，因此"减少主线程工作"几乎等价于"提升渲染性能"。

## 二、导航流程：从输入 URL 到页面

一次完整的页面访问，从键入地址到首屏出现，大致经历如下步骤（可结合前一篇《HTTP 与 HTTPS》理解网络部分）：

> 示意片段（无配套脚本）

```
① 输入 URL → 浏览器校验、补全协议
② DNS 解析出 IP（本地缓存 → 本地 DNS → 迭代查询）
③ 建立 TCP 连接（三次握手）→ 如为 HTTPS 再做 TLS 握手
④ 发送 HTTP 请求 → 服务器返回 HTML 响应
⑤ 网络进程把收到的 HTML 交给渲染进程
⑥ 渲染进程解析 HTML/CSS，构建 DOM 与样式
⑦ 计算布局 → 绘制 → 合成 → 显示到屏幕
```

补充：如果响应是 `301/302` 重定向，浏览器会跟随 `Location` 重新请求；如果命中强缓存，则完全跳过网络请求。

## 三、HTML 解析与 DOM 构建

### 1. HTML 解析算法

浏览器从服务端收到一串 HTML 字节流，主线程开始解析。**字节流 → 字符 → Token（标记）→ 节点 → DOM 树**。

大致引擎流程：

> 示意片段（无配套脚本）

```
Bytes(字节) → Characters(字符) → Tokens(标记) → Nodes(节点) → DOM 树
```

- **标记化（Tokenization）**：把 HTML 字符串切分成一个个标签标记（`<html>`、`<div>`、文本等）。
- **树构建（Tree Construction）**：根据标记嵌套关系，构建一棵 **DOM（Document Object Model）树**，其中的每个节点对应一个对象（元素、文本、注释等）。
- DOM 是一棵**可被 JavaScript 操作**的动态结构；而 HTML 文本只是一串字符串，二者通过解析建立连接。

### 2. 阻塞问题

- **CSS 会阻塞渲染树构建**：浏览器在构造样式时必须先拿到所有 CSS，确保样式结果正确，因此 CSS 是"渲染阻塞资源"。
- **普通 `<script>` 会阻塞 HTML 解析**：因为脚本可能通过 `document.write` 修改正在解析的 HTML，所以遇到同步脚本会停下来先执行。
- 解决方式：
  - `async`：脚本下载异步，下载完立即执行（不保证执行顺序）。
  - `defer`：脚本下载异步，等待 HTML 解析完成后按顺序执行。

> 示意片段（无配套脚本）

```html
<script src="a.js" defer></script>
<script src="b.js" defer></script>
```

### 3. HTML 解析出现 `<script>` 时的时序

> 示意片段（无配套脚本）

```
HTML 解析
   │
   ▼
遇到同步 <script>
   │
   ▼
暂停解析 → 下载并执行脚本 → 继续解析
   │
   ▼
遇到 <link rel="stylesheet">
   │
   ▼
样式可能阻塞后续脚本执行（脚本需要等待 CSS）
```

所以实践上：把 `<script>` 放在 `<body>` 底部，或用 `defer/async`，把 `<link rel="stylesheet">` 放在 `<head>`。

## 四、CSS 解析与 CSSOM 构建

### 1. CSSOM 是什么

CSS 解析构建出 **CSSOM（CSS Object Model）**，与 DOM 对应，但它具有**树形级联结构**：一个元素最终的样式由选择器匹配 + 层叠（Cascade）+ 继承共同决定。

> 示意片段（无配套脚本）

```css
body { font-size: 16px; color: #333; }
.container { padding: 20px; }
```

浏览器读取样式规则、根据选择器匹配元素、应用层叠规则与继承，最终为每个可见元素算出"计算样式（Computed Style）"。

### 2. 解析时的特点

- CSS 规则是**右往左匹配**的（浏览器从选择器最右侧的选择子开始匹配），所以过度写深层的后代/通配选择器会拖慢匹配。
- CSSOM 构建期间，页面**不能进行渲染**，这是"渲染阻塞资源"的由来。

## 五、渲染树（Render Tree）

把 **DOM** 与 **CSSOM** 合并，就得到**渲染树（Render Tree）**。渲染树只包含**可见**节点：

- 剔除 `display: none` 的节点（`visibility: hidden` 仍会占据布局，所以保留）；
- 剔除 `<head>`、`<meta>`、`<script>` 等不可见元素；
- 为每个节点附加计算好的样式信息。

> 示意片段（无配套脚本）

```
DOM树 + CSSOM树 → 渲染树(Render Tree) → 每个节点含布局信息 → 屏幕
```

注意区分：**DOM 树**管"结构"，**CSSOM 树**管"样式"，**渲染树**是两者结合后"用来绘制"的中间产物。

## 六、布局（Layout / 回流）

有了渲染树，浏览器需要为每个可见元素计算它**在页面中的几何位置与尺寸**（宽、高、x/y 坐标）。这个阶段叫 **Layout**，也叫 **Reflow（回流/重排）**。

### 1. 布局的要点

- 布局根据**视口尺寸**与样式，计算出节点盒模型（margin、border、padding、content）的位置。
- 布局通常是**从根节点自上而下、自左向右**递归进行的。
- 因为一个元素的尺寸可能依赖其子元素或后续元素，布局往往需要"逐步收敛"。

> 参考资料：像 `offsetWidth`、`getBoundingClientRect()`、`scrollTop` 这些"读取布局信息"的 API，会**强制触发同步布局（Forced Synchronous Layout）**，引起意外开销。

### 2. 什么是回流（Reflow）

**回流**指浏览器**重新计算布局**的过程。当元素的**几何属性**（尺寸、位置、隐藏显示）或**页面结构**改变，且影响了其他元素的位置时，就会触发回流。

常见触发回流的操作：

- 增删或移动 DOM 节点；
- 修改 width / height / margin / padding / top / left 等几何样式；
- 改变窗口尺寸（resize）；
- 读取 `offsetWidth` / `getClientRects()` 等布局强相关的值；
- 改变字体大小、内容变化（如文字增多导致高度变化）。

## 七、绘制（Paint / 重绘）

回流完成后，浏览器要把每个节点绘制出来，这一阶段叫 **Paint（绘制）** 或 **Raster（栅格化）**，也叫**重绘（Repaint）**。

### 1. 回流 vs 重绘（关键区分）

| 对比 | 回流（Reflow / Layout） | 重绘（Repaint / Paint） |
| --- | --- | --- |
| 触发 | 几何属性、结构、位置改变 | 仅外观/颜色改变，不影响几何 |
| 成本 | **更高**（重新计算整个受影响区域的布局） | 相对较低（只重新绘制像素） |
| 示例 | 改宽高、增删元素、改 padding | 改 color、background-color、box-shadow |
| 关系 | **回流必然导致重绘** | 重绘不一定会回流 |

一句话：**凡是改变几何位置/尺寸的操作，必然触发回流；而回流之后必然跟着一次重绘。** 改颜色等纯外观变化通常只触发重绘。

> 回流为什么贵：它可能需要从根部重新计算整个或大部分渲染树，而重绘只是把已有布局结果重新上色。

## 八、合成（Compositing）与合成层

### 1. 为什么要引入合成

上述"布局→绘制"都是基于主线程 + 渲染树的同步过程，非常昂贵。而**合成（Compositing）**是现代浏览器引入的一大优化：把页面按内容划分成若干**合成层（Compositing Layer）**，各层独立栅格化，最后由合成器把它们**拼合（Composite）**到屏幕上。

关键收益：如果某个层的内容不改变，那么只是这一层的变化（如 `transform`、`opacity` 动画）无需重新布局、无需重绘整层，只需合成器移动/叠加位图即可——**合成动画可以跑在合成器线程、不占主线程**。

### 2. 触发合成层的方式

以下属性/操作常会**promote（提升）**元素成为独立合成层：

- `transform`、`opacity`、`will-change`、`filter` 等；
- 显式设置 `will-change: transform`（或 `opacity`）；
- 使用 `translateZ/translate3d` 强制开启硬件加速；
- 有 `animation`/`transition` 涉及合成属性；
- 元素覆盖关系复杂、有 `fixed` 定位等。

> 示意片段（无配套脚本）

```css
.card {
  /* 把动画放在独立合成层，避免影响整页布局/绘制 */
  will-change: transform;
}
.card {
  transform: translate3d(0, 0, 0); /* 传统上用于强制开启 GPU 合成层 */
}
```

### 3. GPU 合成 / 硬件加速

浏览器在合成阶段会把位图交给 **GPU 进程** 处理。**GPU 合成（硬件加速渲染）** 能利用显卡并行能力对图层进行高速变换、缩放、透明叠加，让动画流畅且不阻塞主线程。

适用且高效的合成属性主要是：`transform` 与 `opacity`——因为它们不触发布局与绘制，可由 GPU 直接处理。

## 九、关键渲染路径（Critical Rendering Path）

我们把"从 HTML/CSS 到首屏像素"这条必经之路统称为**关键渲染路径**：

> 示意片段（无配套脚本）

```
HTML → 解析 → DOM ─┐
                 ├→ Render Tree → Layout → Paint → Composite → 像素
CSS  → 解析 → CSSOM┘
```

路径上的任何一步变慢，都会推迟首屏可见内容（可量化为 FCP / LCP 等指标）。因此优化的核心思想就是：**让关键路径更短、让阻塞更少**。

## 十、如何减少回流与重绘

### 1. 合并 DOM 操作（Batch）

减少"读-写-读-写"的交替，因为浏览器会**缓存**布局值，一旦读到强制刷新就立即重新布局。将多次修改合并为一次，让浏览器统一处理：

> 示意片段（无配套脚本）

```js
// 不推荐：循环内读写交替，强制多次同步布局
for (let i = 0; i < items.length; i++) {
  const h = list.offsetHeight; // 读
  item.style.top = h + i * 10 + "px"; // 写
}

// 推荐：先批量读，再批量写（或改用 DocumentFragment + 一次性插入）
```

### 2. 用现代属性替代昂贵操作

- 动画尽量用 **`transform` + `opacity`**，而非修改 `top/left/width/height`（触发回流）。
- 一次性改变多个样式，可用**修改 class** 而非逐个改 style，或用 **CSS Variables**。

> 示意片段（无配套脚本）

```js
// 不推荐：多次回流
el.style.width = "100px";
el.style.height = "200px";

// 推荐：合并为一次覆盖，或改 className
el.style.cssText = "width:100px;height:200px;";
```

### 3. 使用离屏 / 隐藏节点操作

- 把要大量修改的元素先 `display: none`，改完再 `display: block`，避免过程中的多次回流。
- 或使用 `DocumentFragment` 在文档外构建片段再一次性插入。

### 4. 请求动画帧优化

避免使用 `setTimeout` 做动画（节流不准、易抖动），改用 `requestAnimationFrame`，它会在下一次绘制前统一执行，与浏览器的绘制节奏对齐：

> 示意片段（无配套脚本）

```js
function update() {
  // 只改 transform，触发 GPU 合成，避免回流重绘
  el.style.transform = `translateX(${x}px)`;
  requestAnimationFrame(update);
}
```

### 5. 减少布局读取触发

避免在同一批操作中用 `offsetWidth/offsetHeight/getBoundingClientRect()` 强制同步布局；确需测量时，先取出值再统一修改。

## 十一、触发层级视角的优化策略

结合前面的渲染管线，整理出一张"优化策略 → 对应阶段"的对照表：

| 优化策略 | 作用阶段 |
| --- | --- |
| 精简/合并 JS，使用 `defer`/`async` 或放底部 | 解析（HTML） |
| 精简/合并 CSS，尽早放 `head`，减少阻塞 | 解析（CSSOM） |
| 避免深层/复杂 CSS 选择器 | CSSOM 匹配 |
| 减少 DOM 规模、避免大规模节点操作 | DOM/Layout |
| 动画使用 `transform`/`opacity` + GPU 合成 | Paint/Composite |
| 减少强制同步布局（批量读写） | Layout |
| 使用 `content-visibility`/懒渲染隐藏屏外内容 | 全部 |
| CSS 属性避免逐帧触发布局 | Layout |

### 1. 总体优化清单（落地）

> 示意片段（无配套脚本）

```markdown
1. 减少关键资源数量与体积（压缩、合并、按需加载）
2. 关键路径资源按顺序优化：优先 HTML，其次关键 CSS/JS
3. 用 transform/opacity 做动画，减少回流重绘
4. 批量读写 DOM，避免强制同步布局
5. 用 GPU 合成层处理高频动画（will-change 适度使用，勿滥用）
6. 减少 DOM 深度与规模，避免昂贵的重排范围
7. 利用缓存放行重复资源，配合 HTTP 缓存
8. 用 内容可见性(content-visibility) 跳过屏外渲染
```

### 2. MVP 首屏性能速查

> 示意片段（无配套脚本）

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head>
  <meta charset="UTF-8" />
  <title>性能友好页面</title>
  <!-- 早期、小体量的关键 CSS 尽量放这里并精简 -->
  <link rel="stylesheet" href="/critical.css" />
  <!-- 非关键脚本延迟解析，避免阻塞 -->
  <script src="/defer.js" defer></script>
</head>
<body>
  <!-- 主体内容 -->
  <!-- 非关键脚本放底部或 async -->
</body>
</html>
```

## 十二、DOM 事件流与事件委托

页面渲染出来之后，用户交互靠的是 DOM 事件。DOM 事件在文档中的传播有固定顺序，理解它是"为什么事件委托能省内存"的前提。

### 1. 事件流的三个阶段

一次事件从发生到处理完，按顺序经过三个阶段：

> 示意片段（无配套脚本）

```
捕获阶段（capture）→ 目标阶段（target）→ 冒泡阶段（bubble）
```

- **捕获阶段**：事件从 `document`（顶层）向下传播到目标元素，逐层经过祖先节点。
- **目标阶段**：事件到达目标元素本身。
- **冒泡阶段**：事件从目标元素向上冒泡回 `document`，逐层经过祖先节点。

监听事件用 `addEventListener(type, fn, useCapture)`：第三个参数为 `true` 在捕获阶段触发，`false`（默认）在冒泡阶段触发。`onclick` 等属性赋值方式只能监听**冒泡阶段**，且一个元素同一事件只能绑一个回调；`addEventListener` 可以绑多个、可精确移除（`removeEventListener` 需传同一函数引用）、还能监听捕获阶段——所以**一律用 `addEventListener`**。

### 2. 阻止传播与默认行为

- `e.stopPropagation()`：阻止事件继续向上（冒泡）或向下（捕获）传播，但不影响同元素上其他监听器。
- `e.stopImmediatePropagation()`：连当前元素上后续的同事件监听器也阻止。
- `e.preventDefault()`：阻止默认行为（如 `<a>` 跳转、表单提交），但**不阻止传播**。

注意区分：`stopPropagation` 管"传播"，`preventDefault` 管"默认行为"，两者互不相干。

### 3. 事件委托（事件代理）

**事件委托 = 把子元素的事件监听绑在共同的祖先元素上，利用冒泡机制统一处理。**

> 示意片段（无配套脚本）

```js
// 普通做法：每个 li 绑一个监听（1000 个 li = 1000 个回调）
// 委托做法：只给 ul 绑一个
document.getElementById("list").addEventListener("click", (e) => {
  const target = e.target.closest("li"); // 找到真正被点击的 li
  if (target) console.log("点击了", target.dataset.id);
});
```

好处：

- **省内存**：事件回调从 N 个变成 1 个，尤其适合列表、表格这类大量同类元素。
- **动态元素免绑定**：新增的子节点天然被父级监听覆盖，不需要重新绑定（适合"增删改查列表""懒加载追加"场景）。
- 内部用 `e.target` 拿到真实目标、`closest()` 向上找匹配节点，配合 `data-*` 属性分发逻辑。

局限：

- **不冒泡的事件无法委托**：`focus`/`blur`（可用 `focusin`/`focusout` 代替）、`scroll`、`mouseenter`/`mouseleave`（不冒泡）、`resize`。
- **高频位置事件慎用**：`mousemove`/`mouseout` 冒泡但高频触发，在父级统一处理反而加大计算量，通常直接绑在目标上。
- 要避免在"已经绑了事件委托的祖先内部"再嵌套一层无关委托，层级越深、每次事件的查找成本越高——委托次数与层级需克制。
