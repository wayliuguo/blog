# 模块总结 · 网络与浏览器

## 知识主线

四篇不是并列的知识点，而是一条有依赖关系的链，每一篇都在回答上一篇留下的问题：

```
01 HTTP 与 HTTPS（浏览器和服务器怎么说话）
        │  资源通过网络拿到了，浏览器下一步怎么把它变成页面？
        ▼
02 浏览器渲染原理（页面怎么画出来）  ★主轴
        │  页面画出来了，登录态、偏好这些状态该存在哪？
        ▼
03 浏览器存储与本地缓存（数据放在哪）
        │  数据都放进浏览器了，怎么防止被别人偷走？
        ▼
04 前端安全（怎么守住信任边界）
```

本模块的主轴是**浏览器渲染原理**：01 讲页面资源怎么从服务器传过来（HTTP/HTTPS/DNS/缓存），02 讲资源到了之后如何走完"解析 → 布局 → 绘制 → 合成"变成像素（多进程、DOM/CSSOM、回流重绘、关键渲染路径），03 讲页面运行中产生的数据存到哪里（Cookie/Web Storage/IndexedDB/Cache Storage），04 把前面所有环节放回"信任边界"的视角，讲 XSS/CSRF/CSP 等攻击与防御。串起来正好是"输入 URL → 页面渲染完成 → 数据持久化 → 安全防护"的完整链路。

## 分篇知识点

### 01-HTTP 与 HTTPS

- **HTTP 是无状态的应用层协议**
  - **无状态与身份模拟**：每个请求独立、服务器不记忆客户端，靠 Cookie/Session/Token 显式携带身份来模拟"有状态"
  - **报文结构**：请求/响应行 + 头 + 空行 + 体组成；请求行是 METHOD + 路径 + 版本，响应行是版本 + 状态码 + 描述
  - **请求-响应模型**：客户端发起请求、服务端返回响应；明文传输是早期版本被窃听篡改的根源（HTTPS 的由来）
- **方法语义与幂等性**
  - **GET**：取数据、无请求体、幂等
  - **POST**：提交/创建资源、有请求体、非幂等
  - **PUT**：整体替换资源、幂等
  - **PATCH**：局部更新资源、通常视为非幂等
  - **DELETE**：删除资源、幂等
  - **幂等性的价值**：网络超时重试/用户重复点击时靠幂等性做正确决策；GET/POST 唯一本质差异是语义，安全性由 HTTPS 提供
- **状态码五类**
  - **2xx 成功**：200 正常返回、201 已创建（POST 常用）、204 成功无内容（DELETE 成功）
  - **3xx 重定向**：301 永久 / 302 临时 / 304 协商缓存命中（资源未变用缓存）
  - **4xx 客户端错误**：401 未认证 vs 403 无权限、404 不存在、405 方法不允许、429 限流
  - **5xx 服务端错误**：500 内部错误 / 502 网关收到无效响应 / 503 暂时不可用 / 504 网关超时
- **强缓存 vs 协商缓存**
  - **强缓存**：`Cache-Control`（相对时间，优先）vs `Expires`（绝对时间、依赖客户端时钟），命中不发请求直接用本地副本
  - **协商缓存**：带 `If-None-Match`/`If-Modified-Since` 条件请求，304 确认后复用；ETag（内容指纹）优先于 Last-Modified（秒级时间）
  - **开发实践**：静态资源用内容指纹文件名（`app-5f8c2a.js`）+ 长 `max-age`，HTML 用 `no-cache` 保证拿最新
- **HTTP 版本演进：消除队头阻塞**
  - **HTTP/1.1**：Keep-Alive 持久连接 + 管线化，但一个连接同时只能处理一个请求，队头阻塞靠并发多连接（约 6 个）缓解
  - **HTTP/2**：二进制分帧 + 多路复用，一个 TCP 连接多个流交错传输，解决 HTTP 层队头阻塞；配 HPACK 头部压缩
  - **HTTP/3**：传输层换 QUIC（基于 UDP），内置 TLS 1.3、0-RTT 握手、连接迁移，一个流丢包不影响其他流，彻底解决 TCP 层队头阻塞
- **HTTPS 与 DNS**
  - **混合加密**：非对称加密协商会话密钥 + 对称加密（如 AES）传大流量数据，兼顾安全与性能
  - **CA 证书体系**：服务器向 CA 申请证书，客户端用内置根证书验证签名，防中间人冒充
  - **DNS 解析**：走"浏览器/系统缓存 → 本地 DNS 递归 → 根/顶级/权威迭代查询"把域名换成 IP，可用 `dns-prefetch`/`preconnect` 预解析预热
- **TCP 与 UDP**
  - **核心区别**：TCP 面向连接、可靠（确认应答/超时重传/乱序重排）、有流量与拥塞控制；UDP 无连接、不可靠但快
  - **粘包问题**：TCP 面向字节流、多条消息黏连要封包/拆包；UDP 面向报文、自带消息边界不会粘包
  - **选型**：HTTP/HTTPS/WebSocket/文件传输走 TCP；实时音视频/直播/DNS/游戏走 UDP；QUIC 是"在 UDP 上自建可靠性"的折中
- **WebSocket**
  - **定位**：复用 HTTP 握手（Upgrade 101）的全双工持久连接，服务器可主动推送，无同源限制但服务端要校验 `Origin`
  - **四种即时通信对比**：性能 WebSocket > SSE > 长轮询 > 短轮询，兼容性反之；SSE 是单向流式 HTTP（客户端不能推）
  - **工程要点**：断线重连（退避策略）、心跳保活防代理掐连接、`wss://` 加密、`Origin` 白名单
- **同源策略**
  - **同源三要素**：协议 + 域名 + 端口三者全同；`localhost` 与 `127.0.0.1`、`5177` 与 `5178` 都不同源
  - **管的是"读"不是"发"**：跨源的 `<script>`/`<img>` 可以正常加载执行，跨源 `fetch` 的请求也会真的发出去、服务端照常处理，被拦的只是"把响应交给 JS"
  - **保护对象**：另一源的响应内容、跨源 iframe 的 DOM、按源隔离的存储与 Cookie
- **CORS**
  - **简单请求**：方法限 `GET`/`HEAD`/`POST`、请求头限安全列表、`Content-Type` 只能是表单三类之一；直接发真实请求，靠响应头决定 JS 能否读
  - **预检请求**：非简单请求（自定义头、`PUT`/`DELETE`、`application/json`）先自动发 `OPTIONS`，通过后才发真实请求；页面只写一次 `fetch` 却产生两次请求
  - **六个响应头**：`Allow-Origin`（必填）/ `Allow-Methods` / `Allow-Headers` / `Allow-Credentials` / `Max-Age` / `Expose-Headers`
  - **两条硬规则**：`Allow-Credentials: true` 与 `Allow-Origin: *` 互斥；自定义响应头默认对 JS 不可见，必须 `Expose-Headers` 放行
  - **失败表现**：JS 只拿到 `TypeError: Failed to fetch`（无状态码、无原因），定位靠 Network 面板与 Console；服务端其实收到了那次请求，所以 CORS 不能当鉴权
  - **工程首选**：同域部署或 dev server 代理，从架构上消灭跨源；必须跨源时按"是否带凭据"选 `*` 还是回显白名单 Origin

### 02-浏览器渲染原理

- **多进程架构**
  - **四大进程分工**：浏览器主进程（UI/网络/调度）/ 渲染进程（每标签页一个，负责解析、布局、绘制、脚本）/ GPU 进程（合成与硬件加速）/ 网络进程
  - **价值**：隔离与稳定——某个标签页崩溃不会拖垮整个浏览器，并提供安全沙箱
  - **性能主线**：渲染相关的 CPU 工作集中在渲染进程主线程，"减少主线程工作 ≈ 提升渲染性能"
- **导航流程**
  - **网络阶段**：输入 URL → DNS 解析出 IP → TCP 三次握手（HTTPS 加 TLS 握手）→ HTTP 请求拿到 HTML
  - **渲染阶段**：网络进程把 HTML 交给渲染进程 → 解析 → 布局 → 绘制 → 合成 → 显示到屏幕
  - **分支**：命中强缓存则完全跳过网络请求，301/302 会跟随 Location 重新请求
- **解析与阻塞**
  - **HTML 解析五步**：字节流 → 字符 → Token（标记化）→ 节点（树构建）→ DOM 树
  - **CSS 阻塞渲染**：构造样式必须先拿到全部 CSS，是"渲染阻塞资源"，CSSOM 构建期间不能渲染
  - **`<script>` 阻塞解析**：普通同步脚本会暂停 HTML 解析先执行；`defer` 解析完按序执行、`async` 下载完立即执行
- **DOM/CSSOM/Render Tree**
  - **DOM**：管结构，可被 JS 操作的动态树；CSSOM 管样式，由选择器匹配 + 层叠 + 继承算出计算样式
  - **Render Tree**：DOM + CSSOM 合并的"可绘制"中间产物
  - **可见性过滤**：渲染树只含可见节点，剔除 `display:none` 与 `<head>`/`<meta>`/`<script>` 等
- **回流 vs 重绘 vs 合成**
  - **回流（Layout）**：改几何（宽高、位置、增删节点）重新计算布局，最贵、必然伴随重绘
  - **重绘（Paint）**：只改外观（颜色、背景、box-shadow），不触发回流时相对便宜
  - **合成（Composite）**：只拼合已栅格化的图层位图，最廉价；`transform`/`opacity` 动画可跑在合成器线程、不占主线程
- **优化清单**
  - **减少关键资源**：压缩、合并、按需加载，让关键渲染路径更短
  - **脚本与样式调度**：`defer`/`async` 或放底部，CSS 尽早放 head 并精简
  - **批量读写 DOM**：避免"读-写"交替触发强制同步布局（`offsetWidth` 等读取会强制刷新）
  - **动画用合成属性**：`transform`/`opacity` + GPU 合成，不触发布局与绘制
  - **`will-change` 适度使用**：提示浏览器提升合成层，滥用反而占内存
  - **`content-visibility`**：跳过屏外内容的渲染
- **DOM 事件流与事件委托**
  - **事件流三阶段**：捕获（document 向下）→ 目标 → 冒泡（向上到 document）；`addEventListener` 第三参 `true` 捕获阶段触发、默认冒泡阶段，`onclick` 只能监听冒泡
  - **阻止 API**：`stopPropagation` 阻止传播、`stopImmediatePropagation` 连后续监听器一起阻止、`preventDefault` 阻止默认行为——传播与默认行为互不相干
  - **事件委托**：子元素监听绑到公共祖先利用冒泡统一处理，省内存（N→1）、动态节点免绑定；`focus`/`blur`/`scroll`/`mouseenter` 等不冒泡事件无法委托，`mousemove` 高频事件慎用

### 03-浏览器存储与本地缓存

- **Cookie**
  - **下发与携带机制**：服务端 `Set-Cookie` 下发、浏览器随同源请求自动携带，容量约 4KB/条、每次请求都带上浪费带宽，只承载会话标识
  - **核心属性**：Expires/Max-Age 过期、Path 生效路径、Domain 域名（含子域共享）、Secure 仅 HTTPS 传、HttpOnly 禁 JS 读（防 XSS 盗 Cookie）、SameSite（Strict/Lax/None，Lax 是默认最优解）
  - **JS 侧读写**：`document.cookie` 可读写非 HttpOnly 部分，一次只能写一个
- **localStorage vs sessionStorage**
  - **共同点**：同步 API、约 5MB、只存字符串（对象要 JSON 序列化）、不随请求发送
  - **区别**：生命周期（持久 vs 关标签页即清）与作用域（同源所有标签页共享 vs 同一标签页内共享）
  - **限制与坑**：同步写大数据阻塞主线程、容量满或隐私模式抛 `QuotaExceededError`（要 try/catch）、无法做复杂查询
- **IndexedDB**
  - **定位**：浏览器内置的 NoSQL 事务型数据库，支持对象仓库/索引/事务/异步读写，容量百 MB~GB 级
  - **用法**：`indexedDB.open` 建库、事务包裹 `add`/`put`/`delete`/`get`，索引用 `idx.getAll` 高效查询
  - **适用与封装**：适合大量结构化数据（离线笔记、聊天记录）；原生 API 繁琐，常用 Dexie.js / idb 封装
- **Web SQL 已废弃**
  - **历史定位**：基于 SQLite 的浏览器关系型数据库规范，语法类似 SQL
  - **现状**：已被 W3C 正式废弃、主流浏览器逐渐移除，新项目用 IndexedDB 替代
- **Service Worker + Cache Storage**
  - **SW 定位**：运行在独立线程的网络代理，可拦截页面请求实现离线访问与后台同步，必须在 HTTPS（或 localhost）下
  - **Cache Storage**：以"请求-响应"为单位缓存网络资源，`caches.open`/`addAll`/`match` 读写
  - **四种缓存策略**：Cache First（静态资源）/ Network First（需较新又需离线）/ Stale-While-Revalidate（先旧后新后台更新）/ Network Only（实时强一致）
- **选型流程**
  - **会话态 / 随请求携带** → Cookie（尽量 HttpOnly + SameSite=Lax）
  - **复杂大数据** → IndexedDB（离线笔记、本地数据仓库）
  - **跨标签页持久** → localStorage（偏好、字典、皮肤）
  - **关页即清的临时态** → sessionStorage（表单草稿）

### 04-前端安全

- **XSS 三类**
  - **反射型（非持久）**：恶意脚本在请求 URL 中、服务器渲染后立即反射回页面，典型触发点是搜索框、错误提示、URL 参数回显
  - **存储型（持久）**：恶意脚本入库持久化，所有访问该页面的用户都会中招，评论区/留言/昵称是重灾区，危害最大、可横向传播
  - **DOM 型**：恶意脚本经前端 JS 操作 DOM 时注入、不经过服务端，`innerHTML`、`document.write`、`eval`、`location.hash` 是危险入口
  - **防御手段**：输入白名单校验 + 输出上下文编码，用 `textContent`/DOMPurify 安全渲染富文本，Cookie 加 HttpOnly，配合 CSP 纵深防御
- **CSRF**
  - **攻击原理**：用户已登录 A 站时访问恶意站 B，浏览器自动带上 A 的 Cookie 发请求，服务端无法辨别是否用户本意，从而执行转账、改密等危险操作
  - **SameSite 首选防御**：现代浏览器默认 `SameSite=Lax` 使跨站 POST 不再自动带 Cookie，从根上阻断大部分 CSRF；`None` 最危险、必须配合 Token 等额外校验
  - **辅助防御**：CSRF Token（请求头/体携带一次性随机凭证）、校验 Origin/Referer、敏感操作二次验证（验证码/二次确认）
- **CSP**
  - **指令白名单**：通过响应头或 `<meta>` 声明允许的资源来源，核心指令 `default-src`/`script-src`/`style-src`/`img-src`/`connect-src`
  - **内联放行**：内联脚本用 `nonce`（随机数）或 `hash` 方式放行，避免完全禁止导致功能可用性问题；配 `report-uri` 上报可及时发现真实攻击
  - **防点击劫持**：`frame-ancestors` 限定哪些站点能以 iframe 嵌入本页（现代首选），老方案 `X-Frame-Options: DENY/SAMEORIGIN` 兼容旧浏览器
- **SQL 注入与上传安全**
  - **SQL 注入**：根治在服务端参数化查询/预编译语句、禁止拼接 SQL 字符串；前端校验可被绕过不能作安全边界，只能预校验明显恶意输入并做错误脱敏与异常上报
  - **上传安全**：类型白名单 + 魔数校验（不信任扩展名）、限制大小，重命名后存到非 web 可执行目录，不允许上传文件被当作脚本执行
  - **SVG 风险**：SVG 可能内嵌脚本，非必要时禁止上传 SVG，若需支持必须做内容净化
- **纵深防御模型**
  - **传输层**：HTTPS + HSTS 保证机密性、完整性与身份认证，也是 Secure Cookie、CSP、Service Worker 等能力的前提
  - **输入输出层**：白名单优先的输入校验 + 按上下文（HTML/属性/JS/URL）输出编码，敏感信息最小化返回、日志与存储脱敏
  - **会话层**：Cookie 三件套 `HttpOnly`/`Secure`/`SameSite`，防 XSS 盗取与 CSRF 自动携带
  - **策略层**：CSP 白名单约束资源来源，`frame-ancestors`/`X-Frame-Options` 防点击劫持
  - **服务端层**：参数化查询根治 SQL 注入、上传文件非可执行目录存储、接口鉴权
  - **兜底层**：监控风控（CSP report-uri、异常上报）及时发现攻击，前端校验被绕过时仍有最后防线
