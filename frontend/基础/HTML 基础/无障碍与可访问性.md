# 无障碍与可访问性

无障碍（Accessibility，常缩写为 a11y）经常被当成"给少数用户的额外功能"：等业务做完、再补一堆 `aria-*`。这个印象是反的。无障碍做的绝大部分事情是**把标签用对**——`<button>` 而不是 `<div onclick>`、`<label for>` 而不是 placeholder、`alt` 而不是不写、标题一级一级往下走。这些标签本来就该这么写，它们顺带带来的收益是：键盘用户能用、读屏用户能听、搜索引擎能懂、自动化测试能定位。

前面两篇讲了标签的语义与表单的用法，这一篇讲的是**怎么验证它们真的生效**。关键在一个平时看不见的结构：浏览器会把 DOM 翻译成一棵**无障碍树（accessibility tree）**，每个节点带 `role`（这是什么）、`name`（怎么念它）、`state`（当前什么状态）。读屏软件、语音控制、部分自动化工具读的都是这棵树——**你写的是标签，它们看到的是树**。

所以本篇的结论全部用两种真实输出佐证：页面内自己实现的检查器（跑在配套 demo 上），以及用 CDP 读出的**浏览器自己算的无障碍树**。两块内容的 HTML 差别只有几行，树的差别可以逐条对比。

## 无障碍树：从标签到 role 与 name

同一组控件写两遍，一遍故意写坏（`#bad-zone`）、一遍是改对之后的版本（`#good-zone`）：

> 摘自 `./code/site/a11y/index.html`（运行：`npm start`）

```html
            <div class="row">
                <div class="fake-btn" id="bad-fake-btn">提交</div>
                <span class="note">用 <code>div</code> 装的按钮</span>
            </div>
            <div class="row">
                <button class="icon-btn" type="button">
                    <svg width="16" height="16" viewBox="0 0 24 24" aria-hidden="true">
                        <circle cx="11" cy="11" r="7" fill="none" stroke="#374151" stroke-width="2" />
                        <line x1="16" y1="16" x2="21" y2="21" stroke="#374151" stroke-width="2" />
                    </svg>
                </button>
                <span class="note">只有图标、没写任何名字的按钮</span>
            </div>
```

对照区的对应部分只改了三处：

> 摘自 `./code/site/a11y/index.html`（运行：`npm start`）

```html
            <div class="row">
                <button class="btn" type="button" id="good-real-btn">提交</button>
                <span class="note">直接用 <code>button</code></span>
            </div>
            <div class="row">
                <button class="icon-btn" type="button" aria-label="搜索">
                    <svg width="16" height="16" viewBox="0 0 24 24" aria-hidden="true">
                        <circle cx="11" cy="11" r="7" fill="none" stroke="#374151" stroke-width="2" />
                        <line x1="16" y1="16" x2="21" y2="21" stroke="#374151" stroke-width="2" />
                    </svg>
                </button>
                <span class="note">图标按钮用 <code>aria-label</code> 给出名字</span>
            </div>
```

看起来两块几乎一样——都是蓝底白字的"提交"、都是一个圆形加一条线的搜索图标。但把两块分别丢给浏览器的无障碍树：

> 实测（`node code/ax-tree.mjs <页面地址> "#bad-zone"`，仅摘录有语义的节点）

```
role = "generic"  name = ""
role = "StaticText"  name = "提交"
role = "button"  name = ""
```

> 实测（同一条命令，`#good-zone`）

```
role = "button"  name = "提交"
role = "button"  name = "搜索"
```

差别一下子清楚了：

- **`div` 假按钮的 role 是 `generic`**，不是 `button`。它里面那串文字"提交"只是树里一个独立的文本节点，两者之间没有任何关系。读屏用户按"按钮"跳转时**根本跳不到它**，也不知道它可点。
- **真 `<button>` 的 role 是 `button`**，里面的文字自动成为它的 `name`——不需要额外写任何东西。
- **纯图标按钮的 role 是 `button`，但 `name` 是空字符串**。它是个"没有名字的按钮"，读屏只会念成"按钮"，用户完全不知道点了会发生什么。补一个 `aria-label="搜索"`，树里就变成 `name = "搜索"`。

这就是"无障碍树"的价值：**`<div>` 装得像按钮、看得像按钮，但树里它永远不是按钮**。外观骗得过人眼，骗不过树。

## 能用原生标签就别用 ARIA

ARIA（`role` / `aria-*`）是**语义补丁**，不是行为补丁。规范里的第一条规则就是：如果一个原生标签能做到，就优先用它。

原因看上面那组对比就明白了。把 `div` 硬改成 `role="button"` 之后，还得自己补上：

| 原生 `<button>` 免费给你的 | `<div role="button">` 要自己补的 |
| --- | --- |
| role 是 `button` | `role="button"` |
| 能 Tab 聚焦 | `tabindex="0"` |
| 回车 / 空格触发 click | 监听 `keydown` 判断 `key === 'Enter'` / `' '`（还要 `preventDefault` 防滚动） |
| 禁用态 | `aria-disabled` 或 `disabled`（前者还要自己拦 click） |
| 读屏报"按钮" | 同上，靠 role |
| 表单里参与提交 | 自己处理 |

漏任何一条，就得到一个"看起来能用、用键盘或读屏时坏掉"的控件。所以顺序永远是：**先选对标签 → 确实没有原生方案时（比如自绘的下拉、树、标签页）再用 ARIA 补语义**，并且补语义的同时要把键盘行为也补齐。

配套 demo 的扫描器同样能看出这个差别——它对"能不能真的聚焦"的判定很直接：`focus()` 对不可聚焦的元素是空操作，所以比对 `document.activeElement` 就行了。

> 摘自 `./code/site/a11y/audit.js`（运行：`npm start`）

```js
/** focus() 对"不可聚焦"的元素是空操作，所以比对 activeElement 就能看出它能不能拿到焦点 */
const checkFocus = id => {
    const el = document.getElementById(id)
    el.focus()
    const focused = document.activeElement === el
    const outline = focused ? getComputedStyle(el).outlineStyle : '(未聚焦)'
    el.blur()
    return { focused, tabIndex: el.tabIndex, outline }
}
```

同一个检查跑在真假按钮上：

> 实测（`chrome --headless=new --dump-dom` 读页面内探针，摘录「键盘可达」两行）

```
  键盘可达（div 假按钮）：focus() 后 activeElement 仍是 body → 不可聚焦，tabIndex = -1，聚焦时 outline-style = (未聚焦)
  键盘可达（真 button）：focus() 后 activeElement 就是它自己 → 可聚焦，tabIndex = 0，聚焦时 outline-style = auto
```

`div.focus()` 什么也没发生——`activeElement` 还是 `body`，`tabIndex` 是 `-1`。这就是"键盘用户 Tab 不到它"的机器可读证据。

## 可访问名：读屏怎么念这个控件

`name` 是无障碍树里第二个关键字段。它的计算有明确的优先级，简化后大致是：

1. `aria-labelledby` 指向的元素文本（最高优先，可以跨元素拼接）
2. `aria-label` 属性
3. 原生关联的 `<label for="...">` / `<label>` 包裹 / `<caption>` 等
4. 元素自己的文本内容（按钮、链接）
5. 内部 `img` 的 `alt`、`title` 等兜底

demo 里的检查器实现的是这个规则的简化版（够用，但不如浏览器精确——所以关键结论以无障碍树的输出为准）：

> 摘自 `./code/site/a11y/audit.js`（运行：`npm start`）

```js
function accessibleName(el) {
    const ariaLabel = el.getAttribute('aria-label')
    if (ariaLabel && ariaLabel.trim()) return ariaLabel.trim()
    const labelledBy = el.getAttribute('aria-labelledby')
    if (labelledBy) {
        const target = document.getElementById(labelledBy)
        if (target) return flat(target)
    }
    const own = flat(el)
    if (own) return own
    const img = el.querySelector('img[alt]')
    if (img && img.getAttribute('alt').trim()) return img.getAttribute('alt').trim()
    const title = el.getAttribute('title')
    return title ? title.trim() : ''
}
```

三个实用要点：

- **图标按钮必须显式给名字**。`<button>` 里只有一个 `<svg>`（再标上 `aria-hidden="true"`），树里的 `name` 就是空。用 `aria-label`（或视觉隐藏的文字）补上。
- **`title` 是最后的兜底，不可靠**：它要鼠标悬停才显示、移动端基本没有、触屏和键盘用户都拿不到。能用 label 就别用 title。
- **`aria-label` 会覆盖可见文本**。给"提交"按钮写 `aria-label="提交订单"`，用户看到的是"提交"、读屏听到的是"提交订单"——语音控制用户喊"点击提交"可能就点不中了。可见文本与可访问名尽量一致。

## 图片：`alt` 的三种写法

图片的 `alt` 不是"有或没有"，而是三种：

| 写法 | 含义 | 无障碍树里 |
| --- | --- | --- |
| `alt="示例站点图标"` | **有信息**：把图里的信息说出来 | `role = "image"  name = "示例站点图标"` |
| `alt=""` | **纯装饰**：明确告诉辅助技术跳过我 | 不作为 image 出现（被标成 presentational，整棵树里都找不到它） |
| 不写 `alt` | **不知道**：读屏只能念"图像"或者念文件名 | `role = "image"  name = ""` |

第三行是关键：**"不写 alt" 与 `alt=""` 不是一回事**。前者是"我忘了"，后者是"我确认它是装饰"。demo 的两个区域正好各有一个缺 `alt` 的图和一对写对的图：

> 实测（`node code/ax-tree.mjs <页面地址> "#bad-zone"` / `"#good-zone"`，摘录 image 节点）

```
# 坏例子：一张没写 alt 的图
role = "image"  name = ""

# 改对之后：有信息的图 + 一张 alt="" 的装饰图
role = "image"  name = "示例站点图标"
```

改对之后的区域里有**两张**图，但树里只出现**一张**——那张 `alt=""` 的装饰图被正确地从无障碍树里拿掉了。这就是"装饰图写 `alt=""`"的目的：不是省事，而是让读屏跳过它、不要把噪音念给用户。

页面内的检查器按同一口径统计（缺 `alt` 才算问题，`alt=""` 不算）：

> 实测（`chrome --headless=new --dump-dom` 读页面内探针，摘录「图片 alt」两行）

```
  图片 alt：1 张图，缺 alt 1 张
  图片 alt：2 张图，缺 alt 0 张
```

## 对比度：可读性的下限

WCAG 给出的阈值是硬指标：**正文 4.5:1**、大字（≥ 24px，或 ≥ 18.66px 加粗）3:1、图标/边框这类非文本内容 3:1。

对比度 = `(亮色 + 0.05) / (暗色 + 0.05)`，其中"亮度"不是颜色的平均值，而是按相对亮度公式算的（先做 sRGB 反伽马，再按人眼对三种原色的敏感度加权）：

> 摘自 `./code/site/a11y/audit.js`（运行：`npm start`）

```js
const toLinear = c => {
    const v = c / 255
    return v <= 0.03928 ? v / 12.92 : Math.pow((v + 0.055) / 1.055, 2.4)
}
const luminance = rgb => 0.2126 * toLinear(rgb[0]) + 0.7152 * toLinear(rgb[1]) + 0.0722 * toLinear(rgb[2])

// …

/** 对比度 = (亮色 + 0.05) / (暗色 + 0.05)，正文要求 ≥ 4.5:1 */
function contrastRatio(fg, bg) {
    const sorted = [luminance(fg), luminance(bg)].sort((a, b) => b - a)
    return (sorted[0] + 0.05) / (sorted[1] + 0.05)
}
```

两队灰字白底的文本，靠公式算出来：

> 实测（`chrome --headless=new --dump-dom` 读页面内探针，摘录「对比度」两行）

```
  对比度：检查 9 处文本，不达标 1 处（最低 2.85:1，正文要求 ≥ 4.5:1） → 「这行字的对比度不足（灰字白底」2.85:1
  对比度：检查 11 处文本，不达标 0 处（最低 4.63:1，正文要求 ≥ 4.5:1）
```

`#999999` 在白底上只有 **2.85:1**（远低于 4.5:1，看起来"灰得挺清楚"但机器判定不合格）；换成 `#4b5563` 就是 **7.56:1**。两个颜色在肉眼看来差别不大，判定结果却是"不达标"与"远远达标"。

实践里的做法：**不要靠眼睛估**。Chrome DevTools 的颜色选择器会直接显示对比度并标出达到的等级；设计稿阶段的灰色尽量直接用一套过了阈值的色阶（比如 `#4b5563` / `#6b7280` 这一档），而不是随手填 `#999`。要和主题色配套生成深浅灰时，可以用 [`现代 CSS`](../CSS/现代%20CSS.md) 里的 `oklch()`——它按感知亮度调，比在 sRGB 里手动试色更接近对比度公式的感受。

## 键盘可达与焦点可见

三条规则，按重要性排列：

1. **所有交互都能用键盘完成**。Tab 走一遍能不能提交表单、能不能关掉弹窗、下拉能不能展开，是比任何静态检查都更有效的验收方式。
2. **Tab 顺序就是 DOM 顺序**。所以不要用 CSS 把视觉顺序和 DOM 顺序调成两回事（`flex-direction: row-reverse` 配上不同的 DOM 顺序，会让键盘顺序和眼睛看到的顺序对不上）。`tabindex` 只有两个值该用：`0`（进入 Tab 序）和 `-1`（可以被 `focus()` 聚焦、但不在 Tab 序里，适合模态框与错误跳转）；**正值（`tabindex="1"`）会插队打乱整页顺序，不要用**。
3. **焦点必须可见**。`:focus` 样式是键盘用户唯一的"我现在在哪"的指示器——`outline: none` 把它删掉，等于让键盘用户盲操作。

第 3 条在 demo 里也能直接量出来——聚焦后读计算样式，看轮廓还在不在：

> 实测（`chrome --headless=new --dump-dom` 读页面内探针，摘录「焦点轮廓」两行）

```
  键盘可达（链接是否保留焦点轮廓）：focus() 后 activeElement 就是它自己 → 可聚焦，tabIndex = 0，聚焦时 outline-style = none
  键盘可达（链接是否保留焦点轮廓）：focus() 后 activeElement 就是它自己 → 可聚焦，tabIndex = 0，聚焦时 outline-style = solid
```

两行都"可聚焦"，差别只在 `outline-style`：坏例子的链接被判成 `none`（键盘 Tab 到它身上，页面上没有任何视觉变化），对照区是 `solid`。要自定义焦点样式完全可以，但**替换而不是删除**——比如 `outline: 2px solid #2563eb; outline-offset: 2px`。另外 `:focus-visible` 比 `:focus` 更精细：它只在"用户可能需要知道焦点在哪"时匹配（键盘导航匹配、鼠标点击不匹配），可以做到"键盘用户看得到、鼠标用户不被打扰"。

焦点还有两处需要主动管理：

- **模态框**：打开时把焦点移进去、并把 Tab 限制在框内（焦点陷阱），关闭后把焦点**还给触发它的那个元素**。
- **单页应用的路由切换**：整体替换内容后，焦点会留在原地或掉回 `body`，读屏用户不知道页面变了。切完之后把焦点移到新页面的 `<h1>`（给它 `tabindex="-1"`）是最省事的做法。

## 结构与状态：让读屏能"跳读"

**标题层级**是读屏用户最常用的导航手段之一，用来"跳读"整页结构。规则是只能一级一级往下走：`h1 → h2 → h3`，不能 `h2` 直接跳 `h4`。

值得注意的是：**层级问题不会体现在 role 上**——无障碍树里 `h4` 和 `h3` 的 role 都是 `heading`，靠树本身看不出跳级，必须单独查文档结构。所以这件事交给检查器做：

> 实测（`chrome --headless=new --dump-dom` 读页面内探针，摘录「标题层级」两行）

```
  标题层级：全页共 6 个标题，跳级 1 处 → h2 -> h4（这级标题跳过了 h3）
  标题层级：全页共 6 个标题，跳级 1 处 → h2 -> h4（这级标题跳过了 h3）
```

两行一样是有意的：**标题层级是整篇文档的结构，必须扫全页**，所以两块内容共用同一个结果——坏例子里那个 `h4` 把整页的结构都带坏了。这也是本篇里唯一"一处错误污染全局"的检查项。

**地标（landmark）**让读屏用户能整块跳转：`header` / `nav` / `main` / `aside` / `footer` 各自对应一个 landmark，读屏可以直接"跳到主内容"。一个页面只应有一个 `main`，它包住该页独有的内容。

**状态与实时更新**靠 ARIA 补充，常用的几个：

| 属性 | 用在哪 | 效果 |
| --- | --- | --- |
| `aria-expanded` | 折叠面板、下拉的触发按钮 | 读屏会念"已展开 / 已折叠" |
| `aria-current="page"` | 导航里当前页那一项 | 读屏会念"当前页"，不必只靠高亮色 |
| `aria-live="polite"` | 表单提示、异步结果区 | 内容变化时读屏主动播报（不打断用户） |
| `aria-live="assertive"` / `role="alert"` | 错误提示 | 立刻打断播报 |
| `aria-hidden="true"` | 纯装饰的图标、重复文本 | 从无障碍树里隐藏 |

两个容易踩的坑：

- **`aria-hidden="true"` 不要用在可聚焦元素上**。读屏会忽略它，键盘却还能 Tab 到它，形成"看得见但听不见"的幽灵焦点。真正的做法是同时把它移出 Tab 序。
- **ARIA 写错不报错**。`aria-lable`、`aria-live="assertive"` 拼错、把只该用于某种 role 的属性乱放，浏览器一律静默忽略——树里就是没效果，开发者控制台也没有任何提示。所以改完 ARIA 一定要回到无障碍树里确认。

## 别只用颜色传达信息

错误提示画成红色、必填项标成红色星号、图表靠颜色区分系列——这些对色盲用户（男性中约 8%）是无效信息。任何时候都要有第二个通道：错误用**文字**写出来（不只是一圈红边），必填项在 label 里写明，图表加线型或标记。

表单场景最典型的组合是：

> 示意片段（无配套脚本）

```html
<!-- 错误提示：文字 + aria-describedby 关联 + aria-invalid + role="alert" 立刻播报 -->
<label for="phone">手机号</label>
<input id="phone" aria-invalid="true" aria-describedby="phone-err" />
<p id="phone-err" role="alert">手机号需要 11 位数字</p>
```

`aria-describedby` 把错误文本挂到控件上，读屏聚焦到这个输入框时会把错误一起念出来——这是"红框"永远做不到的。另外 `placeholder` **不能替代 `<label>`**，这点在无障碍树里能看出一个很有趣的细节：

> 实测（`node code/ax-tree.mjs <页面地址> "#bad-zone"`，摘录表单节点）

```
role = "textbox"  name = "手机号"
```

坏例子里的输入框只写了 `placeholder="手机号"`，树里却**有名字**——浏览器把 placeholder 当作可访问名的兜底了。但这不意味着"用 placeholder 当标签"是合格的：placeholder 在用户开始输入后就消失了，认知障碍用户无法回头确认这一栏要填什么；它也经常与真实标签的措辞不一致（"请输入手机号" vs "手机号"）。改对之后的区域里，除了 textbox 之外还多出一个 `LabelText` 节点——那才是真正被关联上的 `<label>`：

> 实测（`node code/ax-tree.mjs <页面地址> "#good-zone"`，摘录表单节点）

```
role = "LabelText"  name = ""
role = "textbox"  name = "手机号"
```

`<label for="a11y-phone">手机号</label>` + `<input id="a11y-phone">` 的收益是双份的：读屏能念出标签，**鼠标用户点标签文字也能聚焦输入框**（点击热区从一个小方块变成一个词组）。单选/多选组则用 `fieldset` + `legend` 把"这是哪一组"包进去，否则读屏只会念出一串孤立的选项。

## 一份可执行的清单

不想记那么多概念的话，先记住这几条——它们覆盖了实际项目里 90% 的无障碍问题：

1. 能用原生标签就用原生标签（`button` / `a` / `input` / `label` / `details`…）。
2. 每张图都要有 `alt`：有信息就描述，纯装饰写 `alt=""`。
3. 每个表单控件都有 `<label>`；`placeholder` 只是提示，不是标签。
4. 标题一级一级往下走，`h1` 每页一个。
5. 焦点永远可见；要用 `:focus-visible` 自定义，不要 `outline: none`。
6. 键盘（Tab + Enter + 空格 + Esc）能走完全部流程。
7. 正文对比度 ≥ 4.5:1，大字与非文本内容 ≥ 3:1。
8. 不用颜色单独传达信息。
9. 需要动效时尊重 `prefers-reduced-motion`（见 [`现代 CSS`](../CSS/现代%20CSS.md)）。
10. 用真读屏跑一遍：Windows 讲述人（`Win` + `Ctrl` + `Enter`）、macOS VoiceOver（`Cmd` + `F5`）。

自动化工具能覆盖前 8 条的相当一部分——DevTools 的 Lighthouse 无障碍审计、axe DevTools 插件、以及本模块的示例检查器都属这一类。但要注意：**自动化检查通常只能发现 30%～40% 的问题**，它擅长"属性写没写"（alt、label、对比度），不擅长"顺序对不对、读起来顺不顺"。第 6 条与第 10 条只能人工验。
