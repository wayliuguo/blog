# 原生小程序与跨端框架差异

## 一、原生小程序的特点

原生开发直接使用小程序自身的技术栈：

- **WXML**（模板）+ **WXSS**（样式）+ **JS/TS**（逻辑）+ 组件/API，全部由微信运行时直接支持。
- 运行在双线程架构上（渲染层 WebView + 逻辑层 JS 引擎，详见《双线程架构与渲染机制》），数据更新走 `setData` 跨线程通信。
- 能力最全：所有小程序 API、组件、平台特性（分包、插件、云开发）第一时间支持，**无桥接层损耗**。

## 二、跨端框架的特点

跨端框架把"写一套代码"编译成各平台的小程序产物：

- **Taro**（京东）：React / Vue 语法写代码，编译到多端小程序 + H5 + React Native。
- **uni-app**（DCloud）：Vue 语法，编译到多端小程序 + H5 + App。
- 共同点：**开发层用 Web 技术栈（组件化、状态管理、路由）**，编译期把代码转成各端可运行的形态。

**收益**：一套代码多端跑、Web 生态（npm 库、组件库）可复用、开发效率高；框架层还内置了常用的 UI 组件、请求封装、状态管理。

**代价**：多一层编译与运行时桥接；平台特有能力要"条件编译"或走框架提供的 API 透传；长列表、复杂动画等极致性能场景可能被框架的抽象拖累；框架版本迭代要先于小程序新特性。

## 三、关键差异对比

| 维度 | 原生小程序 | 跨端框架（Taro / uni-app） |
| --- | --- | --- |
| 开发效率 | 每端写一套，模板/样式/逻辑分开 | 一套代码多端编译，Web 语法复用 |
| 性能 | 直接跑小程序运行时，无中间层 | 多一层编译产物与桥接，复杂场景有损耗 |
| 平台能力 | API/组件/新特性第一时间可用 | 依赖框架适配，特殊能力需透传/条件编译 |
| 多端覆盖 | 只覆盖目标平台 | 一套代码覆盖多端小程序 + H5 + App |
| 团队技术栈 | 需掌握小程序特有语法 | 复用团队已有的 React/Vue 经验 |
| 调试排错 | 官方工具直接调试原生产物 | 先查编译产物，多一层排错成本 |

### 1. 双线程架构在两边的不同体现

- 原生小程序：逻辑在 JS 引擎、视图在 WebView，`setData` 走 Native 中转——这是平台**硬约束**。
- 跨端框架：框架把"组件树 → 数据 → 视图更新"翻译成目标端的 `setData` 调用。也就是说 **Taro/uni-app 在微信小程序里最终也是靠 setData 更新视图**，性能上界的决定权仍在小程序运行时；框架要做的只是**减少不必要的 setData**（自动合并、diff）。

### 2. 为什么"框架写 H5 很顺，写小程序要小心"

H5 里框架直接操作 DOM、更新几乎没有跨线程成本；小程序里所有视图更新都收敛到 `setData` 这条跨线程通道。所以跨端框架的面试题常落在："框架给你抽象掉了跨端差异，但你要清楚它在小程序端最终生成了什么"——长列表、高频更新、大数据量这些场景，靠框架"无脑 diff"不一定够，还是要按小程序的原生优化思路（虚拟列表、合并 setData、WXS）去压。

## 四、怎么选

- **只做微信端、性能敏感、要第一时间用平台新能力** → 原生。
- **多端都要、团队有 Web 技术栈积累、开发效率优先** → 跨端框架（选 Taro 还是 uni-app 看团队是 React 还是 Vue）。
- **混合策略**：核心性能页用原生，外围业务页用框架（同一小程序里原生与框架编译产物可以共存，但成本高，慎用）。
