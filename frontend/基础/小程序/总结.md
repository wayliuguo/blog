## 1. WXML 与 WXSS 基础

### 1.1 插值表达式

WXML 里用 `<code v-pre>{{ }}</code>` 插入数据，它**只求值、不执行代码**：运算 / 三元 / 成员访问 / 方法调用是表达式可以写；`var` / `if` / 分号 / 赋值号等语句会在编译期被拦下。插值语义是"求一个值填进模板"，没有语句的位置。

- 判断逻辑放逻辑层算好再 `setData` 过去，纯展示加工交给 WXS。
- 访问 `data` 里**不存在的字段得到 `undefined`**（渲染成空串）而不是报错——字段拼错会静默空白，排查要靠对照 `data` 定义。

### 1.2 列表渲染

`wx:for` 渲染数组，默认变量是 `item` 与 `index`（从 0 起），重命名用 `wx:for-item` / `wx:for-index`。

**`wx:key` 是列表项的稳定唯一标识**，渲染层靠它认出"哪两个节点是同一个"，把重排退化成移动而不是整段重建：

```
对象数组     wx:key="id"       取元素上稳定的字段做 key
基本类型数组  wx:key="*this"    没有字段，用值本身做 key
不写 wx:key  告警，且重排时整段重建，带输入框 / 展开态 / 动画的项状态会丢
```

- 用 `index` 当 key 在中间插入时会错位复用、状态串位。
- `wx:for` 的值**不是数组 → 编译期报错**，不是渲染空白。

### 1.3 条件渲染

`wx:if` / `wx:elif` / `wx:else` 是**连写**的一组，未命中的分支不产出节点；`hidden` 只是给节点加 `display:none`（节点还在渲染树里，状态得以保留）。

| 场景 | 用哪个 |
| ---- | ---- |
| 切换频繁、要保留状态（表单输入、滚动位置、`<video>`、地图） | `hidden` |
| 节点较重、初始不需要、只在少数条件下出现 | `wx:if` |

注意：`wx:if` 隐藏的节点 `createSelectorQuery` 查不到。

### 1.4 模板复用

- `template` 是带参片段，`data` 必须显式传；`import` 有作用域、只导入 `template`。
- `include` 是文本级拷贝，忽略被包含文件里的 `template` 与 `wxs`。

### 1.5 WXSS：rpx 与选择器与作用域

**rpx**：基准是 **`750rpx` = 屏幕宽度**，`px = rpx × 屏宽 / 750`。设计稿按 750 宽出图、照抄数字即可免费等比缩放。代价是会算出小数：`2rpx` 在 375 屏宽上是 1px、320 上只有 0.85px——**"一像素细线"要么写死 `1px`、要么用 `transform: scaleY()`**，别用 rpx 算。

**选择器清单很短**：`.class` / `#id` / `element` / `element, element` / `::after` / `::before`；通配符与属性选择器不在内，状态要用类名表达（`.btn--loading`）。

**作用域三层**：`app.wxss` 全局、页面 `.wxss` 作用于本页、组件样式默认隔离；跨文件用 `@import`。

### 1.6 事件绑定

`bind*` 冒泡、`catch*` 阻止冒泡；`data-*` 传进 `dataset` 的**都是字符串**（数字也会被译成字符串）；读触点用 `currentTarget` 而不是 `target`。回调在逻辑层执行、事件对象由渲染层序列化跨线程传过来。

给超长列表每一项都绑 `bindtap` 常规但有成本——把监听器收到容器上、用 `data-*` 区分项，能省一批跨线程通信。

## 2. 生命周期与路由

### 2.1 应用生命周期（app.js）

| 钩子 | 时机 | 用途 |
| ---- | ---- | ---- |
| `onLaunch` | 初始化完成，全局只触发一次 | 做初始化 |
| `onShow` / `onHide` | 前台 / 后台切换 | 做刷新与暂停 |
| `onError` / `onPageNotFound` / `onUnhandledRejection` | 异常兜底 | 上报与恢复 |

- `globalData`：跨页面共享数据，但**非响应式**，简单场景兜底。

### 2.2 页面生命周期（Page）

| 钩子 | 时机 | 用途 |
| ---- | ---- | ---- |
| `onLoad` | 创建时一次、最早 | 发请求取数据、读参数 |
| `onShow` | 每次到前台都触发 | "返回刷新" |
| `onReady` | 首次渲染完 | 取页面元素 |
| `onHide` / `onUnload` | 终止任务、释放资源会话末尾 | 释放资源 |

请求放 `onLoad` 而非 `onReady`，能提前一个渲染周期发起、首屏更快。

### 2.3 组件生命周期（Component）

`created` 时组件实例刚创建、还没进入页面节点树，视图层没有对应节点——**`created` 不能 `setData`**，只能做数据初始化。之后：

```
created    实例刚建，不能 setData
attached   进入节点树，可拿到页面数据
ready      视图布局完成，才能取组件内部节点
detached   从节点树移除
```

组件取节点必须等 `ready`，页面取节点在页面 `onReady`。

### 2.4 页面路由

| 方式 | 行为 | 限制 |
| ---- | ---- | ---- |
| `navigateTo` | 开新页保留当前页 | 只能开非 tabBar 页；栈最多 10 层 |
| `redirectTo` | 关闭当前页重定向 | 只能开非 tabBar 页 |
| `navigateBack` | 返回上一页 | 触发上一页 `onShow`（"返回刷新"的实现依据） |
| `switchTab` | 切 tab | 只能开 tabBar 页 |
| `reLaunch` | 关闭全部重开 | 任意页 |

## 3. 双线程架构与渲染机制

### 3.1 双线程架构

```
渲染层   WebView：只画视图（WXML/WXSS），无业务 JS、无 DOM
逻辑层   JS 引擎：跑业务代码，无 DOM、不能直接操作视图
Native   中转通信 / 数据传递 / 网络请求
```

- 逻辑与视图**完全隔离**：逻辑层不能直接操作视图，只能走 `setData`。
- 多页面 = 多 WebView；页面栈加深内存增长，长流程页面要及时 `navigateBack`。

### 3.2 setData 跨线程通信

`setData` 是**跨线程通信**，链条是：

```
逻辑层 setData → 序列化 → Native 转发 → 渲染层反序列化 → 更新节点
```

开销与数据量正相关：数据量大、调用频繁都会线性放大成本，且视图更新会**阻塞用户交互**。减少开销的四条原则：

```
少调用      同一轮逻辑里的多次 setData 收敛成一次
批量更新    一次回调合并多次更新（合并相邻字段）
只传要用的  不渲染的字段别放 data
路径更新    setData('list[0].name', v) 只传变化的最小切片
```

路径更新的 key 必须与实际层级**逐字一致**，拼错会静默不生效、极难排查。

### 3.3 WXS 渲染层脚本

WXS 是运行在**渲染层**的小程序脚本语言，把"展示前的数据加工"（格式化金额、过滤列表）放到视图层本地算，数据变化不必再走 setData 跨线程传输。

- 不支持 ES6+ 与部分 API，**只适合纯展示计算**；业务逻辑与网络请求必须在逻辑层。

## 4. 启动优化与性能优化

### 4.1 启动流程与启动优化

启动 = **固定启动界面 + 下载/加载代码包 + 初始化首页**。启动耗时 = 主包下载/加载 + 首页初始化，优化从"包瘦身 + 分包 + 预下载"入手：

| 手段 | 做法 | 注意 |
| ---- | ---- | ---- |
| 控制包体积 | 压缩、清理无用代码、图片上 CDN、生产关 sourcemap | 用量化看构成（开发者工具"代码依赖分析"） |
| 分包加载 | 主包只留核心，分包按需下载 | 有硬限制：主包约 2MB、总包约 20MB；切换有延迟 |
| 预下载 | `preloadRule` 进入触发页时提前下载分包 | 抵消分包切换延迟；可限 `network: wifi` 防耗流量 |

tabBar 页面必须在主包，首页跑不掉分包。

### 4.2 首屏渲染优化

三个抓手：

```
请求前置   请求放 onLoad（而非 onReady）提前发起
data 精简  data 只放视图要用的数据（无关字段参与 setData 传输与 diff，拖慢首帧）
不阻塞     onLoad 不做同步阻塞操作（wx.getStorageSync 大对象、耗时同步计算都是阻塞源）
```

同步操作卡住逻辑层主线程，渲染指令无法及时下发。

### 4.3 渲染性能优化

```
setData 治理  少调用、数据量小、路径更新
wx:key       精确识别列表节点，把重排退化成移动
长列表        虚拟列表只渲染可视区附近数据，官方方案 recycle-view
展示加工      用 WXS 在渲染层算，避免跨线程传输
```

长列表整段渲染会让 WebView 节点爆炸；虚拟列表切片渲染 + 占位撑高 + 滚动复用，上千条级列表才流畅；小列表（几十条）不必上虚拟列表。

## 5. 原生与跨端框架差异

### 5.1 原生方案的特点

直接跑小程序运行时，能力最全、新能力第一时间可用、无桥接损耗；代价是**每端一套代码**。

### 5.2 跨端框架方案的特点

Taro（React/Vue）/ uni-app（Vue）一套代码编译多端，覆盖多端 + 复用 Web 生态与团队积累，效率高；代价是多一层编译与桥接，性能与排错有成本。落地把"平台差异"收敛到两层：**能力层**（条件编译或适配器封装登录 / 支付 / 分享 / 存储）、**UI 层**（跨端组件库），业务层不感知平台。

### 5.3 关键差异与选型

```
性能   原生更直接；框架最终也靠 setData 更新视图，性能上界仍由小程序运行时决定
能力   原生第一时间可用；框架依赖适配（平台特有组件要透传 / 条件编译兜底）
选型   单端性能敏感用原生；多端 + Web 栈积累用框架
```

跨端框架在微信端最终仍靠 `setData` 更新视图，**不会让它更快**；三端且样式逻辑高度一致时收益最大，一端或各端差异极大时适配层会变成负担。
