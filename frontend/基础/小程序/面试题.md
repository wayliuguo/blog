# 模块面试题 · 小程序

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../../进阶/面试方法论.md)的四步答题法——结论/原理/边界/追问。
> 题目来源：本模块五篇正文（WXML/WXSS 与基础语法、生命周期与路由、双线程架构、启动与性能优化、原生与跨端框架）。

## 一、基础概念

### Q1: WXML 的 <code v-pre>{{ }}</code> 里能写什么、不能写什么？（第 1 篇）

- **结论**：只能写**一个表达式**——运算、三元、成员访问、方法调用都行；语句（`var` / `if` / `for`）与分号、赋值号都会被编译期拦下。
- **原理**：WXML 由渲染层的编译器处理，<code v-pre>{{ }}</code> 的语义是"求一个值填进模板"，不是"执行一段代码"，所以它没有语句的位置。需要中间量就先在逻辑层算好、再 `setData` 过去；纯展示加工交给 WXS。
- **边界**：访问 `data` 里不存在的字段得到 `undefined`（渲染成空串）而不是报错，所以拼错字段名不会崩、只会静默空白，排查要靠对照 `data` 定义。
- **追问**：<code v-pre>{{ items.length === 0 }}</code> 这种写法可以吗？→ 可以。比较、`&&` / `||`、三元、`item.name.toUpperCase()` 都是表达式，不会被拦。

### Q2: 小程序的生命周期分哪几层？各有哪些钩子？（第 2 篇）

- **结论**：分三层——应用（app.js）、页面（Page）、组件（Component），各管一段启停时机。
- **原理**：应用层 `onLaunch`（全局一次）/`onShow`/`onHide`/`onError` 等；页面层 `onLoad`/`onShow`/`onReady`/`onHide`/`onUnload`；组件层 `created`/`attached`/`ready`/`moved`/`detached`/`error`。
- **边界**：`onLaunch` 全局只触发一次；`onShow` 可能多次（每次回前台）；页面栈最多 10 层。
- **追问**：返回上一页会触发什么？→ 上一页的 `onShow`（不会重新 `onLoad`）。

### Q3: 页面生命周期的 onLoad / onShow / onReady 分别适合做什么？（第 2 篇）

- **结论**：`onLoad` 发请求取数据、`onShow` 每次回前台刷新、`onReady` 首次渲染后取元素。
- **原理**：`onLoad` 只执行一次且最早，适合初始化与拉首屏数据；`onShow` 每次出现在前台都触发，适合"返回刷新"；`onReady` 保证视图已渲染完，才能 `createSelectorQuery` 操作节点。
- **边界**：请求放 `onLoad` 而非 `onReady`，能提前一个渲染周期发起。
- **追问**：为什么不用 onReady 发请求？→ onReady 在渲染完成之后才触发，请求晚一轮，首屏更慢。

### Q4: 小程序路由有哪几种跳转方式？各自限制？（第 2 篇）

- **结论**：五种——`navigateTo`/`redirectTo`/`navigateBack`/`switchTab`/`reLaunch`，限制落在 tabBar 页与非 tabBar 页的划分上。
- **原理**：`navigateTo` 开新页保留当前页（栈最多 10 层）、`redirectTo` 关闭当前页重定向、`navigateBack` 返回、`switchTab` 切 tab、`reLaunch` 关闭全部重开。
- **边界**：`navigateTo`/`redirectTo` 只能开非 tabBar 页面，`switchTab` 只能开 tabBar 页面，`reLaunch` 任意。
- **追问**：栈顶页面状态？→ 永远处于 `onShow`，返回时上一页 `onShow` 再次触发。

### Q5: WXS 是什么？解决什么问题？（第 3 篇）

- **结论**：WXS 是运行在渲染层的小程序脚本语言，把"展示前的数据加工"放到视图层本地算，避免跨线程传输。
- **原理**：格式化金额、过滤列表这类纯展示计算写在 WXS 模块里，在渲染层执行，数据变化不必再走 setData 跨线程。
- **边界**：WXS 不支持 ES6+ 与部分 API，只适合纯展示计算；业务逻辑与网络请求必须在逻辑层。
- **追问**：WXS 和普通 JS 什么关系？→ 语法接近 ES5 子集，独立运行于渲染层。

### Q6: `wx:key` 解决什么问题？基本类型数组为什么必须写 `*this`？（第 1 篇）

- **结论**：`wx:key` 是列表项的稳定唯一标识，渲染层靠它认出"哪两个节点是同一个"，从而把重排退化成移动而不是整段重建。
- **原理**：`wx:for` 更新时要对比新旧列表。有 key 就能按 key 匹配节点、只做移动与增删；没有 key 只能按位置对比，插入一项就会让后面所有项都被判定为"内容变了"，整段重建——列表项里如果有输入框内容、展开态、动画，都会一起丢。
- **边界**：key 必须是**元素上存在的稳定字段**。对象数组用 `wx:key="id"`；基本类型数组（`['a','b']`）没有字段，要用 `wx:key="*this"`；用 `index` 当 key 在中间插入时会错位复用，状态会串位。
- **追问**：不写 `wx:key` 会报错吗？→ 不报错，但编译期会警告（实测 `wx:for 缺少 wx:key：列表重排时无法复用节点，会整段重建`），运行时表现为"插入一项后整列表闪一下"。

## 二、机制与原理

### Q7: 组件生命周期里为什么 created 不能调用 setData？（第 2 篇）

- **结论**：`created` 时组件实例刚创建、还没进入页面节点树，视图层没有对应节点，`setData` 没有意义。
- **原理**：`created` 只能做数据初始化（不能 setData）；`attached` 时组件进入节点树、可拿到页面数据；`ready` 时视图布局完成、才能取组件内部节点。
- **边界**：组件取节点必须等 `ready`，页面取节点在页面 `onReady`。
- **追问**：组件进入节点树是哪个钩子？→ `attached`。

### Q8: 小程序双线程架构是怎样的？为什么这么设计？（第 3 篇）

- **结论**：渲染层 WebView 画视图、逻辑层 JS 引擎跑业务，两层通过 Native 层中转通信——逻辑与视图完全隔离。
- **原理**：渲染层只含视图（WXML/WXSS）无业务 JS；逻辑层跑业务代码但无 DOM；通信、数据传递、网络请求统一由 Native 层转发。
- **边界**：多个页面 = 多个 WebView，页面栈加深内存增长；逻辑层没有 DOM，不能直接操作视图。
- **追问**：没有这套隔离会怎样？→ 逻辑错误直接挂掉渲染、Web 的 DOM 能力也带来安全与性能风险；隔离换来稳定与安全，代价是通信成本。

### Q9: setData 为什么"贵"？怎么减少它的开销？（第 3 篇）

- **结论**：`setData` 是跨线程通信，数据要序列化传输且会触发视图更新，开销与数据量正相关。
- **原理**：逻辑层 setData → 序列化 → Native 转发 → 渲染层反序列化 → 更新节点；数据量大、调用频繁都会放大成本，且视图更新会阻塞用户交互。
- **边界**：只传视图要用的数据（不渲染的字段别放 data）、一次回调合并多次更新、用路径更新 `list[0].name` 避免整对象重传。
- **追问**：路径更新怎么用？→ <code v-pre>this.setData({ 'list[0].name': 'xx' })</code> 只更新局部节点。

## 三、排障与选型

### Q10: 小程序启动慢，从哪些方向优化？（第 4 篇）

- **结论**：启动 = 下载/加载代码包 + 初始化首页，优化方向是"包瘦身 + 分包 + 预下载 + 首屏请求前置"。
- **原理**：包越小下载越快；主包只留核心页面、不常用页面放分包按需加载；`preloadRule` 提前下载分包抵消切换延迟；首屏接口放 `onLoad` 提前发起。
- **边界**：分包有体积限制（主包约 2MB、总包约 20MB）；分包切换有下载注入延迟，要配预下载。
- **追问**：图片放哪里？→ 静态资源上 CDN，不进代码包。

### Q11: 分包加载（subpackages）与预下载（preloadRule）怎么配合？（第 4 篇）

- **结论**：分包按需下载省首启体积，预下载在进入触发页时提前拉取分包，两者抵消分包的切换延迟。
- **原理**：`subpackages` 把不常用页面拆分到分包、主包只留核心；`preloadRule` 配置"进入某页时预载哪些分包"，可限定 `network: wifi` 防耗流量。
- **边界**：预下载会占网络与存储，只对"下一步很可能进入"的分包配置；包体积限制是硬门槛，超限必须分包。
- **追问**：preloadRule 的 network 有什么用？→ 限制仅在 WiFi 下预载，避免消耗用户移动流量。

### Q12: 小程序首屏渲染怎么优化？（第 4 篇）

- **结论**：三个抓手——请求提前到 onLoad、data 只放渲染要用的数据、onLoad 不做同步阻塞操作。
- **原理**：请求发得越早数据回得越早；data 里无关字段都参与 setData 传输与 diff，拖慢首帧；同步操作卡住逻辑层主线程，渲染指令无法及时下发。
- **边界**：`wx.getStorageSync` 大对象、耗时同步计算都算阻塞源。
- **追问**：为什么 onLoad 比 onReady 更适合发请求？→ onLoad 先于 onReady，早一个渲染周期。

### Q13: 长列表渲染怎么优化？（第 4 篇）

- **结论**：虚拟列表只渲染可视区附近的数据，配 `wx:key` 精确识别节点；官方方案是 recycle-view。
- **原理**：长列表整段渲染会让 WebView 节点爆炸；虚拟列表切片渲染 + 占位撑高 + 滚动复用，上千条级列表才流畅。
- **边界**：`wx:for` 必须给稳定 `wx:key`，否则更新范围放大；小列表（几十条）不必上虚拟列表。
- **追问**：recycle-view 是什么？→ 微信官方维护的长列表组件，数据切片 + 滚动复用。

### Q14: 原生小程序和跨端框架（Taro / uni-app）怎么选？（第 5 篇）

- **结论**：单端、性能敏感、要第一时间用平台能力选原生；多端覆盖 + Web 栈积累选跨端框架。
- **原理**：原生直接跑小程序运行时、无桥接损耗、能力最全；框架一套代码多端编译、Web 生态复用、效率高，但多一层编译与桥接，复杂场景有损耗。
- **边界**：框架在微信端最终也靠 setData 更新视图，性能上界仍由小程序运行时决定；平台特殊能力需透传/条件编译。
- **追问**：Taro 和 uni-app 怎么选？→ 团队是 React 用 Taro，是 Vue 用 uni-app。

### Q15: `hidden` 和 `wx:if` 有什么区别？什么时候必须用 `hidden`？（第 1 篇）

- **结论**：`hidden` 给节点加 `display:none`（**节点还在渲染树里**），`wx:if` 未命中时**根本不产出节点**。
- **原理**：`hidden` 是样式层面的隐藏，节点、状态、事件都还在；`wx:if` 是编译/运行时的结构切换，命中才创建节点。同一份模板换数据实测：<code v-pre>hidden="{{ !visible }}"</code> 在 `visible=false` 时产物是 `<div class="tip" style="display:none">`，而 `wx:if` / `wx:elif` 没命中的分支在产物里直接消失。
- **边界**：切换频繁、需要保留状态的用 `hidden`（表单输入、滚动位置、`<video>` 实例、第三方地图）；初始就不需要、节点较重或只在少数条件下出现的用 `wx:if`；`wx:if` / `wx:elif` / `wx:else` 必须连写，中间不能插别的节点。
- **追问**：`wx:if` 隐藏的节点还能拿到吗？→ 拿不到，节点不存在，`createSelectorQuery` 查不到；需要"藏起来但仍可操作"只能用 `hidden`。

### Q16: rpx 是怎么换算的？为什么"1px 细线"不能用 rpx 算？（第 1 篇）

- **结论**：**750rpx 恒等于屏幕宽度**，`px = rpx × 屏宽 / 750`；rpx 的代价是会算出小数，要精确一像素就别用它。
- **原理**：按 750 宽的设计稿出图、直接照抄数字，等比缩放在小程序里是自动的：690rpx 在 320 / 375 / 430 屏宽上分别是 294.4 / 345 / 395.6px，都正好占住屏宽减边距的比例。
- **边界**：`28rpx` 在 320 屏宽上是 11.9467px，`2rpx` 在 375 上是 1px、在 320 上只有 0.8533px。所以"一像素细线"这种要求精确的场景要么写死 `1px`，要么用 `transform: scaleY()` 那套方案。另外 WXSS 支持的选择器清单只有 `.class` / `#id` / `element` / `element, element` / `::after` / `::before`，通配符与属性选择器都不在内。
- **追问**：为什么小程序不直接用 vw？→ 逻辑等价（100vw 对 750rpx），但 rpx 是按设计稿宽度约定的领域单位，社区素材与组件库都按 750 出图；两者混用容易在计算上打架。

## 四、场景设计题

### Q17: 场景：小程序主包体积超限、首启白屏 3 秒，怎么设计一套"包瘦身 + 首屏加速"方案？（场景综合）

- **结论**：按"量化体积 → 减体积 → 挪出主包 → 提前下载 → 首屏请求前置"五步走，而不是只盯着压缩图片。
- **原理**：启动耗时 = 主包下载/加载 + 首页初始化，所以先量化再动手（开发者工具的"代码依赖分析"看主包体积构成）。减体积——静态资源全部上 CDN 不进包、删未引用文件与重复依赖、生产构建关 sourcemap；挪出主包——用 `subpackages` 把非首屏页面拆到分包，主包只留 tabBar 页与首屏链路；提前下载——用 `preloadRule` 在进入某个触发页时预载"下一步很可能进"的分包，并配 `network: wifi` 避免消耗移动流量；首屏请求前置——接口在 `onLoad`（而非 `onReady`）发起，`onLoad` 里不做 `wx.getStorageSync` 大对象这类同步阻塞。
- **边界**：分包是硬限制（主包约 2MB、总包约 20MB），超限直接上传失败；分包切换本身有"下载 + 注入"延迟，不配 `preloadRule` 只是把首启问题变成切页问题；`preloadRule` 只对"确定会去"的分包配置，乱配会浪费用户流量与存储；tabBar 页面必须在主包，首页跑不掉。
- **追问**：为什么"把首页做成分包"这条路走不通？→ 分包解决的是"非首屏页面不阻塞首启"，而 tabBar 页强制在主包内；首屏要变快只能靠"主包更小 + 请求更早"，这是两件事。

### Q18: 场景：一个长列表页滚动越来越卡，怎么确认是 `setData` 的问题、又怎么治理？（场景综合）

- **结论**：先用"`setData` 数据量 + 调用次数"两个指标确认，再按"少传、合并、路径更新、切片渲染"四招治理。
- **原理**：`setData` 的代价来自三段——逻辑层序列化、Native 转发、渲染层反序列化并更新节点，数据量与调用次数都会线性放大成本。对应四招：① **少传**——`data` 里只放渲染要用的字段，接口返回的冗余字段不入 `data`；② **合并**——同一轮逻辑里的多次 `setData` 收敛成一次；③ **路径更新**——<code v-pre>this.setData({ 'list[3].name': 'x' })</code> 只传变化的最小切片，配稳定 `wx:key` 让 diff 精确到节点；④ **切片渲染**——长列表只渲染可视区附近数据（虚拟列表或官方 `recycle-view`）。
- **边界**：路径更新的 key 必须与实际层级逐字一致，拼错会静默不生效、极难排查；虚拟列表的滚动容器高度与占位必须精确，否则滚动条跳动；`wx:key` 用 index 在中间插入时会错位复用，状态（输入内容、展开态）会串位；小列表（几十条）上虚拟列表反而更慢。
- **追问**：怎么把"卡"量化成可对比的数字？→ 开发者工具性能面板看每次 `setData` 的数据量（KB）与耗时，优化前后对比"同一次滚动的 `setData` 次数与总数据量"，而不是凭手感说流畅了。

### Q19: 场景：一套业务要同时上微信小程序、支付宝小程序和 App 内嵌 H5，怎么选型与落地？（场景综合）

- **结论**：按"端数量 × 团队技术栈"选——只上一两家平台且性能敏感选原生，三端以上且团队有 Web 栈选跨端框架，H5 单独维护。
- **原理**：原生直接用平台运行时、无桥接损耗、平台新能力第一时间可用，代价是每端一套代码；Taro（React 系）/ uni-app（Vue 系）一套代码编译多端，Web 生态与团队积累可复用，代价是多一层编译与桥接。落地时把"平台差异"收敛到两层：**能力层**用条件编译或适配器封装各端不同的登录、支付、分享、存储；**UI 层**用跨端组件库；业务层完全不感知平台。H5 因为运行环境差异太大（没有小程序 API、没有分包机制、没有 `setData`），通常单独维护，只共享纯逻辑与样式令牌。
- **边界**：跨端框架在微信端最终仍靠 `setData` 更新视图，性能上界仍由小程序运行时决定，框架不会让它更快；平台特有组件与原生能力（地图、`open-data`）要靠透传或条件编译兜底；框架升级时多端回归成本高于单端；`rpx` 这类平台单位在 H5 端需要换算，别直接照搬。
- **追问**：怎么判断"该不该上跨端"？→ 看"多端差异有多大 + 迭代有多快"：三端且样式逻辑高度一致时收益最大；只有一端、或各端差异极大时，适配层会反过来变成负担。
