# 模块面试题 · 小程序

## 1. WXML 与 WXSS 基础

### Q1（1.1）｜ `{{ }}` 里只能放表达式，为什么？

- **判断**：`{{ }}` 只求一个值、不执行代码——表达式可写，语句会被编译期拦下。
- **展开**：WXML 插值的语义是"求一个值填进模板"，没有语句的位置；需要中间量就先在逻辑层算好再 `setData` 过去，纯展示加工交给 WXS。
- **边界**：访问 `data` 里不存在的字段得到 `undefined`（渲染成空串）而不是报错，字段拼错会静默空白，排查要靠对照 `data` 定义。

### Q2（1.2）｜ `wx:key` 是干什么的？基本类型数组为什么必须写 `*this`？

- **判断**：`wx:key` 是列表项的稳定唯一标识，渲染层靠它认出"哪两个节点是同一个"，把重排退化成移动而不是整段重建。
- **展开**：没有 key 只能按位置对比，插入一项就让后面所有项都被判为"内容变化"而整段重建，带输入框 / 展开态 / 动画的列表项状态会一起丢。key 必须是元素上存在的稳定字段。
- **佐证**：

```
对象数组      wx:key="id"      取元素上稳定的字段
基本类型数组   wx:key="*this"   没有字段，用值本身
不写 wx:key  告警，重排时整段重建
```

- **边界**：用 `index` 当 key 在中间插入时会错位复用、状态串位。

### Q3（1.3）｜ `hidden` 与 `wx:if` 有什么区别？什么时候必须用 `hidden`？

- **判断**：`hidden` 只是加 `display:none`（节点还在渲染树里），`wx:if` 未命中时根本不产出节点。
- **展开**：`hidden` 是样式层面的隐藏，节点 / 状态 / 事件都还在；`wx:if` 是结构切换，命中才创建节点，`wx:if` / `wx:elif` / `wx:else` 必须连写、中间不能插别的节点。切换频繁、要保留状态用 `hidden`；节点较重、初始不需要、少数条件才出现用 `wx:if`。
- **边界**：`wx:if` 隐藏的节点 `createSelectorQuery` 查不到。

### Q4（1.5）｜ rpx 是怎么换算的？"1px 细线"为什么不能用 rpx 算？

- **判断**：`750rpx` 恒等于屏幕宽度，`px = rpx × 屏宽 / 750`；rpx 的代价是会算出小数，要精确一像素就别用它。
- **展开**：设计稿按 750 宽出图、照抄数字即可免费等比缩放，但 `2rpx` 在 375 屏宽上是 1px、在 320 上只有 0.85px，所以"一像素细线"要么写死 `1px`、要么用 `transform: scaleY()`。
- **边界**：WXSS 支持的选择器清单很短（`.class` / `#id` / `element` / `element, element` / `::after` / `::before`），通配符与属性选择器不在内，状态要用类名表达（`.btn--loading`）。

### Q5（1.6）｜ 小程序事件绑定有哪些坑？（bind/catch、dataset、currentTarget）

- **判断**：`bind*` 冒泡、`catch*` 阻止冒泡；`data-*` 传进 `dataset` 的都是字符串；读触点用 `currentTarget` 而不是 `target`。
- **展开**：事件回调在逻辑层执行、事件对象由渲染层序列化跨线程传过来；`data-id` 传数字进来，`dataset.id` 拿到的是 `'1001'`；`target` 是真正被点中的子节点、`currentTarget` 才是绑定了事件的节点。
- **边界**：回调跨线程执行，给超长列表的每一项都绑 `bindtap` 有成本——把监听器收到容器上、用 `data-*` 区分项能省一批跨线程通信。

## 2. 生命周期与路由

### Q6（2.1/2.2/2.3）｜ 小程序的生命周期分哪几层？各有哪些钩子？

- **判断**：分三层——应用（app.js）、页面（Page）、组件（Component），各管一段启动停止时机。
- **展开**：应用层 `onLaunch` / `onShow` / `onHide` / `onError` 等；页面层 `onLoad` / `onShow` / `onReady` / `onHide` / `onUnload`；组件层 `created` / `attached` / `ready` / `moved` / `detached` / `error`。
- **边界**：`onLaunch` 全局只触发一次；`onShow` 可能多次（每次回前台）；页面栈最多 10 层，栈溢出新页面无法打开。

### Q7（2.2）｜ onLoad / onShow / onReady 各适合做什么？

- **判断**：`onLoad` 发请求取数据、`onShow` 每次回前台刷新、`onReady` 首次渲染后取元素。
- **展开**：`onLoad` 只执行一次且最早，适合初始化与拉首屏数据；`onShow` 每次出现在前台都触发，适合"返回刷新"；`onReady` 保证视图已渲染完才能 `createSelectorQuery` 操作节点。
- **边界**：请求放 `onLoad` 而非 `onReady`，能提前一个渲染周期发起、首屏更快。

### Q8（2.3）｜ 组件生命周期里为什么 created 不能调用 setData？

- **判断**：`created` 时组件实例刚创建、还没进入页面节点树，视图层没有对应节点，`setData` 没有意义。
- **展开**：`created` 只能做数据初始化；`attached` 时组件进入节点树、可拿到页面数据；`ready` 时视图布局完成、才能取组件内部节点。
- **边界**：组件取节点必须等 `ready`，页面取节点在页面 `onReady`。

### Q9（2.4）｜ 五种路由跳转方式各自的限制？

- **判断**：`navigateTo` / `redirectTo` / `navigateBack` / `switchTab` / `reLaunch` 五种，限制落在 tabBar 页与非 tabBar 页的划分上。
- **展开**：`navigateTo` 开新页保留当前页（栈最多 10 层）、`redirectTo` 关闭当前页重定向、`navigateBack` 返回、`switchTab` 切 tab、`reLaunch` 关闭全部重开。
- **佐证**：

```
navigateTo / redirectTo   只能开非 tabBar 页面
switchTab                 只能开 tabBar 页面
reLaunch                  任意
navigateBack              返回，上一页 onShow 再次触发
```

- **边界**：返回触发上一页 `onShow`（"返回刷新"的实现依据）。

## 3. 双线程架构与渲染机制

### Q10（3.1）｜ 小程序双线程架构是怎样的？为什么这么设计？

- **判断**：渲染层 WebView 画视图、逻辑层 JS 引擎跑业务，两层通过 Native 层中转通信——逻辑与视图完全隔离。
- **展开**：渲染层只有视图（WXML/WXSS）无业务 JS；逻辑层跑业务代码但无 DOM；通信 / 数据传递 / 网络请求统一由 Native 层转发；多个页面 = 多个 WebView。
- **边界**：逻辑层没有 DOM 不能直接操作视图；页面栈加深内存增长，长流程页面要及时 `navigateBack`。

### Q11（3.2）｜ setData 为什么"贵"？怎么减少它的开销？

- **判断**：`setData` 是跨线程通信，数据要序列化传输且会触发视图更新，开销与数据量正相关。
- **展开**：逻辑层 setData → 序列化 → Native 转发 → 渲染层反序列化 → 更新节点；数据量大、调用频繁都会线性放大成本，且视图更新会阻塞用户交互。减少开销的四招——少传、合并、只传视图要用的、路径更新。
- **佐证**：

```
少调用      同一轮逻辑里的多次 setData 收敛成一次
只传要用的  不渲染的字段别放 data
路径更新    setData('list[0].name', v) 只传变化的最小切片
```

- **边界**：路径更新的 key 必须与实际层级逐字一致，拼错会静默不生效、极难排查。

### Q12（3.3）｜ WXS 是什么？解决什么问题？

- **判断**：WXS 是运行在渲染层的小程序脚本语言，把"展示前的数据加工"放到视图层本地算，避免跨线程传输。
- **展开**：格式化金额、过滤列表这类纯展示计算写在 WXS 模块里、在渲染层执行，数据变化不必再走 setData 跨线程。
- **边界**：WXS 不支持 ES6+ 与部分 API，只适合纯展示计算；业务逻辑与网络请求必须在逻辑层。

## 4. 启动优化与性能优化

### Q13（4.1）｜ 小程序启动慢，从哪些方向优化？

- **判断**：启动 = 下载 / 加载代码包 + 初始化首页，优化方向是"包瘦身 + 分包 + 预下载 + 首屏请求前置"。
- **展开**：包越小下载越快；主包只留核心页面、不常用页面放分包按需加载；`preloadRule` 提前下载分包抵消切换延迟；首屏接口放 `onLoad` 提前发起。
- **边界**：分包有硬性体积限制（主包约 2MB、总包约 20MB）；分包切换有下载注入延迟，要配预下载。

### Q14（4.1）｜ 分包加载（subpackages）与预下载（preloadRule）怎么配合？

- **判断**：分包按需下载省首启体积，预下载在进入触发页时提前拉取分包，两者抵消分包的切换延迟。
- **展开**：`subpackages` 把不常用页面拆分到分包、主包只留核心；`preloadRule` 配置"进入某页时预载哪些分包"，可限定 `network: wifi` 防耗流量。
- **边界**：预下载会占网络与存储，只对"下一步很可能进入"的分包配置；tabBar 页面必须在主包，首页跑不掉分包。

### Q15（4.2）｜ 小程序首屏渲染怎么优化？

- **判断**：三个抓手——请求提前到 onLoad、data 只放渲染要用的数据、onLoad 不做同步阻塞操作。
- **展开**：请求发得越早数据回得越早；data 里无关字段都参与 setData 传输与 diff，拖慢首帧；同步操作卡住逻辑层主线程，渲染指令无法及时下发。
- **边界**：`wx.getStorageSync` 大对象、耗时同步计算都算阻塞源。

### Q16（4.3）｜ 长列表渲染怎么优化？

- **判断**：虚拟列表只渲染可视区附近的数据，配 `wx:key` 精确识别节点；官方方案是 recycle-view。
- **展开**：长列表整段渲染会让 WebView 节点爆炸；虚拟列表切片渲染 + 占位撑高 + 滚动复用，上千条级列表才流畅。
- **边界**：`wx:for` 必须给稳定 `wx:key`，否则更新范围放大；小列表（几十条）不必上虚拟列表。

## 5. 原生与跨端框架差异

### Q17（5.1/5.2/5.3）｜ 场景：一套业务要同时上微信小程序、支付宝小程序和 App 内嵌 H5，怎么选型与落地？

- **判断**：按"端数量 × 团队技术栈"选——只上一两家平台且性能敏感选原生，三端以上且团队有 Web 栈选跨端框架，H5 单独维护。
- **展开**：原生直接用平台运行时、无桥接损耗、平台新能力第一时间可用，代价是每端一套代码；Taro（React 系）/ uni-app（Vue 系）一套代码编译多端、复用 Web 生态与团队积累，代价是多一层编译与桥接。落地把"平台差异"收敛到两层：能力层用条件编译或适配器封装登录 / 支付 / 分享 / 存储，UI 层用跨端组件库，业务层不感知平台；H5 环境差异大（无小程序 API、无分包、无 setData），单独维护、只共享纯逻辑与样式令牌。
- **边界**：跨端框架在微信端最终仍靠 `setData` 更新视图，性能上界仍由小程序运行时决定，框架不会让它更快；平台特有组件与原生能力（地图、`open-data`）要靠透传或条件编译兜底；三端且样式逻辑高度一致时收益最大，一端或各端差异极大时适配层会变成负担。

### Q18（4.1）｜ 场景：小程序主包体积超限、首启白屏 3 秒，怎么设计一套"包瘦身 + 首屏加速"方案？

- **判断**：按"量化体积 → 减体积 → 挪出主包 → 提前下载 → 首屏请求前置"五步走，而不是只盯着压缩图片。
- **展开**：启动耗时 = 主包下载 / 加载 + 首页初始化，所以先量化（开发者工具"代码依赖分析"看主包构成）；减体积——静态资源全部上 CDN 不进包、删未引用文件与重复依赖、生产构建关 sourcemap；挪出主包——用 `subpackages` 把非首屏页面拆到分包、主包只留 tabBar 页与首屏链路；提前下载——用 `preloadRule` 在进入触发页时预载"下一步很可能进"的分包，并配 `network: wifi`；请求前置——接口在 `onLoad`（而非 `onReady`）发起，`onLoad` 里不做 `wx.getStorageSync` 大对象这类同步阻塞。
- **边界**：分包是硬限制（主包约 2MB、总包约 20MB），超限直接上传失败；分包切换本身有"下载 + 注入"延迟，不配 `preloadRule` 只是把首启问题变成切页问题；首页作为 tabBar 页必须在主包，跑不掉分包，首屏变快只能靠"主包更小 + 请求更早"。

### Q19（4.3）｜ 场景：一个长列表页滚动越来越卡，怎么确认是 `setData` 的问题、又怎么治理？

- **判断**：先用"`setData` 数据量 + 调用次数"两个指标确认，再按"少传、合并、路径更新、切片渲染"四招治理。
- **展开**：`setData` 的代价来自三段——逻辑层序列化、Native 转发、渲染层反序列化并更新节点，数据量与调用次数都会线性放大成本。对应四招：① 少传——data 只放渲染要用的字段，接口冗余字段不入 data；② 合并——同一轮逻辑里的多次 `setData` 收敛成一次；③ 路径更新——`'list[3].name'` 只传变化的最小切片，配稳定 `wx:key` 让 diff 精确到节点；④ 切片渲染——长列表只渲染可视区附近数据（虚拟列表或官方 `recycle-view`）。
- **边界**：路径更新的 key 必须与实际层级逐字一致，拼错会静默不生效、极难排查；虚拟列表的滚动容器高度与占位必须精确，否则滚动条跳动；`wx:key` 用 index 在中间插入状态会串位；确认问题用开发者工具性能面板量化"同一次滚动的 setData 次数与总数据量"，对比优化前后，而不是凭手感。
