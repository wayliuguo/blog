## 一、基础概念

### Q1: 小程序的生命周期分哪几层？各有哪些钩子？（第 1 篇）

- **结论**：分三层——应用（app.js）、页面（Page）、组件（Component），各管一段启停时机。
- **原理**：应用层 `onLaunch`（全局一次）/`onShow`/`onHide`/`onError` 等；页面层 `onLoad`/`onShow`/`onReady`/`onHide`/`onUnload`；组件层 `created`/`attached`/`ready`/`moved`/`detached`/`error`。
- **边界**：`onLaunch` 全局只触发一次；`onShow` 可能多次（每次回前台）；页面栈最多 10 层。
- **追问**：返回上一页会触发什么？→ 上一页的 `onShow`（不会重新 `onLoad`）。

### Q2: 页面生命周期的 onLoad / onShow / onReady 分别适合做什么？（第 1 篇）

- **结论**：`onLoad` 发请求取数据、`onShow` 每次回前台刷新、`onReady` 首次渲染后取元素。
- **原理**：`onLoad` 只执行一次且最早，适合初始化与拉首屏数据；`onShow` 每次出现在前台都触发，适合"返回刷新"；`onReady` 保证视图已渲染完，才能 `createSelectorQuery` 操作节点。
- **边界**：请求放 `onLoad` 而非 `onReady`，能提前一个渲染周期发起。
- **追问**：为什么不用 onReady 发请求？→ onReady 在渲染完成之后才触发，请求晚一轮，首屏更慢。

### Q4: 小程序路由有哪几种跳转方式？各自限制？（第 1 篇）

- **结论**：五种——`navigateTo`/`redirectTo`/`navigateBack`/`switchTab`/`reLaunch`，限制落在 tabBar 页与非 tabBar 页的划分上。
- **原理**：`navigateTo` 开新页保留当前页（栈最多 10 层）、`redirectTo` 关闭当前页重定向、`navigateBack` 返回、`switchTab` 切 tab、`reLaunch` 关闭全部重开。
- **边界**：`navigateTo`/`redirectTo` 只能开非 tabBar 页面，`switchTab` 只能开 tabBar 页面，`reLaunch` 任意。
- **追问**：栈顶页面状态？→ 永远处于 `onShow`，返回时上一页 `onShow` 再次触发。

### Q7: WXS 是什么？解决什么问题？（第 2 篇）

- **结论**：WXS 是运行在渲染层的小程序脚本语言，把"展示前的数据加工"放到视图层本地算，避免跨线程传输。
- **原理**：格式化金额、过滤列表这类纯展示计算写在 WXS 模块里，在渲染层执行，数据变化不必再走 setData 跨线程。
- **边界**：WXS 不支持 ES6+ 与部分 API，只适合纯展示计算；业务逻辑与网络请求必须在逻辑层。
- **追问**：WXS 和普通 JS 什么关系？→ 语法接近 ES5 子集，独立运行于渲染层。

## 二、机制与原理

### Q3: 组件生命周期里为什么 created 不能调用 setData？（第 1 篇）

- **结论**：`created` 时组件实例刚创建、还没进入页面节点树，视图层没有对应节点，`setData` 没有意义。
- **原理**：`created` 只能做数据初始化（不能 setData）；`attached` 时组件进入节点树、可拿到页面数据；`ready` 时视图布局完成、才能取组件内部节点。
- **边界**：组件取节点必须等 `ready`，页面取节点在页面 `onReady`。
- **追问**：组件进入节点树是哪个钩子？→ `attached`。

### Q5: 小程序双线程架构是怎样的？为什么这么设计？（第 2 篇）

- **结论**：渲染层 WebView 画视图、逻辑层 JS 引擎跑业务，两层通过 Native 层中转通信——逻辑与视图完全隔离。
- **原理**：渲染层只含视图（WXML/WXSS）无业务 JS；逻辑层跑业务代码但无 DOM；通信、数据传递、网络请求统一由 Native 层转发。
- **边界**：多个页面 = 多个 WebView，页面栈加深内存增长；逻辑层没有 DOM，不能直接操作视图。
- **追问**：没有这套隔离会怎样？→ 逻辑错误直接挂掉渲染、Web 的 DOM 能力也带来安全与性能风险；隔离换来稳定与安全，代价是通信成本。

### Q6: setData 为什么"贵"？怎么减少它的开销？（第 2 篇）

- **结论**：`setData` 是跨线程通信，数据要序列化传输且会触发视图更新，开销与数据量正相关。
- **原理**：逻辑层 setData → 序列化 → Native 转发 → 渲染层反序列化 → 更新节点；数据量大、调用频繁都会放大成本，且视图更新会阻塞用户交互。
- **边界**：只传视图要用的数据（不渲染的字段别放 data）、一次回调合并多次更新、用路径更新 `list[0].name` 避免整对象重传。
- **追问**：路径更新怎么用？→ `this.setData({ 'list[0].name': 'xx' })` 只更新局部节点。

## 三、排障与选型

### Q8: 小程序启动慢，从哪些方向优化？（第 3 篇）

- **结论**：启动 = 下载/加载代码包 + 初始化首页，优化方向是"包瘦身 + 分包 + 预下载 + 首屏请求前置"。
- **原理**：包越小下载越快；主包只留核心页面、不常用页面放分包按需加载；`preloadRule` 提前下载分包抵消切换延迟；首屏接口放 `onLoad` 提前发起。
- **边界**：分包有体积限制（主包约 2MB、总包约 20MB）；分包切换有下载注入延迟，要配预下载。
- **追问**：图片放哪里？→ 静态资源上 CDN，不进代码包。

### Q9: 分包加载（subpackages）与预下载（preloadRule）怎么配合？（第 3 篇）

- **结论**：分包按需下载省首启体积，预下载在进入触发页时提前拉取分包，两者抵消分包的切换延迟。
- **原理**：`subpackages` 把不常用页面拆分到分包、主包只留核心；`preloadRule` 配置"进入某页时预载哪些分包"，可限定 `network: wifi` 防耗流量。
- **边界**：预下载会占网络与存储，只对"下一步很可能进入"的分包配置；包体积限制是硬门槛，超限必须分包。
- **追问**：preloadRule 的 network 有什么用？→ 限制仅在 WiFi 下预载，避免消耗用户移动流量。

### Q10: 小程序首屏渲染怎么优化？（第 3 篇）

- **结论**：三个抓手——请求提前到 onLoad、data 只放渲染要用的数据、onLoad 不做同步阻塞操作。
- **原理**：请求发得越早数据回得越早；data 里无关字段都参与 setData 传输与 diff，拖慢首帧；同步操作卡住逻辑层主线程，渲染指令无法及时下发。
- **边界**：`wx.getStorageSync` 大对象、耗时同步计算都算阻塞源。
- **追问**：为什么 onLoad 比 onReady 更适合发请求？→ onLoad 先于 onReady，早一个渲染周期。

### Q11: 长列表渲染怎么优化？（第 3 篇）

- **结论**：虚拟列表只渲染可视区附近的数据，配 `wx:key` 精确识别节点；官方方案是 recycle-view。
- **原理**：长列表整段渲染会让 WebView 节点爆炸；虚拟列表切片渲染 + 占位撑高 + 滚动复用，上千条级列表才流畅。
- **边界**：`wx:for` 必须给稳定 `wx:key`，否则更新范围放大；小列表（几十条）不必上虚拟列表。
- **追问**：recycle-view 是什么？→ 微信官方维护的长列表组件，数据切片 + 滚动复用。

### Q12: 原生小程序和跨端框架（Taro / uni-app）怎么选？（第 4 篇）

- **结论**：单端、性能敏感、要第一时间用平台能力选原生；多端覆盖 + Web 栈积累选跨端框架。
- **原理**：原生直接跑小程序运行时、无桥接损耗、能力最全；框架一套代码多端编译、Web 生态复用、效率高，但多一层编译与桥接，复杂场景有损耗。
- **边界**：框架在微信端最终也靠 setData 更新视图，性能上界仍由小程序运行时决定；平台特殊能力需透传/条件编译。
- **追问**：Taro 和 uni-app 怎么选？→ 团队是 React 用 Taro，是 Vue 用 uni-app。
