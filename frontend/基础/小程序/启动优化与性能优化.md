# 小程序启动优化与性能优化

小程序打开时的体验 = **启动快不快** + **页面流畅不流畅**。启动阶段微信要下载代码包、加载代码包、初始化首页，这个阶段用户只能看到一个固定的启动界面；启动之后，页面渲染与交互又受 `setData` 通信成本影响。小程序性能优化的主线就是两条：**让启动更快**（包体积、分包、预下载）与**让渲染更省**（少 setData、列表优化、WXS）。

这篇文章按「启动流程 → 启动优化 → 首屏渲染优化 → 渲染性能优化」的脉络展开。

## 一、启动流程：用户看到了什么

用户点开小程序，先看到的是一个固定的**启动界面**（小程序的图标、名称、加载提示图标），微信在背后完成几项工作：

> 示意片段（无配套脚本）

```
① 展示启动界面（图标 + 名称 + 加载提示）
② 下载小程序代码包
③ 加载小程序代码包
④ 初始化小程序首页
```

启动耗时主要花在 ②③④ 三步：**包越大下载越慢，逻辑越重初始化越慢**。所以启动优化的第一刀永远是"代码包瘦身"。

## 二、启动优化

### 1. 控制代码包大小

- **上传代码时启用压缩**：开发者工具勾选"上传时压缩代码"，去除注释与冗余空白。
- **清理无用代码与资源**：删除不再引用的页面、组件、图片；被 `tree-shaking` 无法覆盖的（小程序没有完整 tree-shaking）要靠人工检查。
- **图片等资源放到 CDN**：静态资源不进代码包，改为网络地址，包体积立刻瘦一大圈。

> 微信对主包有体积限制（当前约 2MB，总包约 20MB），超过必须用分包——包体积不只是体验问题，还是硬性门槛。

### 2. 分包加载 `subpackages`

把小程序中**不经常使用**的页面放到多个分包，主包只保留核心页面（首页 + 常用流程）：

> 示意片段（无配套脚本）

```json
{
  "subpackages": [
    {
      "root": "pages/order/",
      "name": "orderPage",
      "pages": ["page1", "page2"]
    }
  ]
}
```

**收益**：用户打开小程序只需下载主包，分包按需下载，首启更快。

**代价**：进入分包页面需要**下载和注入分包**，会有一次页面切换延迟——这就是为什么需要预下载。

### 3. 预下载 `preloadRule`

在进入某个页面时，提前把指定的分包下载好，用户跳进分包时"秒开"：

> 示意片段（无配套脚本）

```json
{
  "preloadRule": {
    "pages/start/index": {
      "network": "all",
      "packages": ["orderPage"]
    }
  }
}
```

`preloadRule` 的 key 是"触发预下载的页面路径"，`packages` 声明要预载的分包名，`network` 可以限定网络条件（`all` 全部网络 / `wifi` 仅 WiFi，防止消耗用户流量）。

## 三、首屏渲染优化

启动之后、首页第一次画出来，还有一次渲染过程。首屏优化的三个抓手：

- **提前首屏数据请求**：把接口请求放在 `onLoad` 而不是 `onReady`——`onLoad` 先于 `onReady`，请求发出越早、数据回来越早；放 `onReady` 意味着渲染完成后才开始请求，白白多等一轮。
- **精简首屏数据**：与视图渲染无关的数据尽量不要放在 `data`——`data` 里的每个字段都要参与 `setData` 传输与 diff，无关数据只会拖慢首帧。
- **避免阻塞渲染**：在 `onLoad` 里不要使用同步操作（如同步的 `wx.getStorageSync` 大对象、耗时的同步计算），同步任务卡住逻辑层主线程，渲染指令就无法及时下发。

## 四、渲染性能优化

### 1. 避免不当使用 setData

setData 是跨线程通信，前面已讲过链路。落到实践：

- **每次 `setData` 都是一次进程间通信**，通信开销与 `setData` 数据量正相关。
- **`setData` 会引发视图层面内容更新，阻塞用户交互**。
- 不要频繁调用 `setData`；每次 `setData` 不要塞太多数量数据。

### 2. 列表渲染中合理使用 key

`wx:for` 给列表项加 `wx:key`，渲染层才能精确识别"哪个节点是同一个"，避免整列表重渲染：

> 示意片段（无配套脚本）

```html
<view wx:for="{{list}}" wx:key="id">{{item.name}}</view>
```

不加 key（或 key 不稳定），列表数据变化时渲染层只能按索引对号入座，更新范围被放大。

### 3. 长列表渲染优化

长列表（消息记录、订单列表）如果整段渲染，WebView 的节点数会爆炸。方案：

- **虚拟列表**：只渲染可视区附近的一小段，滚动时替换内容（自己实现，或直接用微信官方的 [recycle-view](https://github.com/wechat-miniprogram/recycle-view)）。
- recycle-view 是官方维护的长列表组件，核心是"数据切片 + 占位撑高 + 滚动复用"，适合上千条级的列表。

### 4. 使用 WXS 直接操作视图数据

需要"展示前加工"的数据（格式化、过滤）用 WXS 在渲染层处理，避免每次数据变化都走一次跨线程 setData（详见《双线程架构与渲染机制》）。

## 小结

- 小程序启动优化与性能优化
  - 启动流程
    - 固定启动界面 + 下载/加载代码包 + 初始化首页
  - 启动优化
    - 控制代码包大小：压缩、清理无用代码、图片上 CDN
    - 分包加载：主包只留核心，分包按需下载
    - 预下载：进某页提前下载分包，抵消分包切换延迟
  - 首屏渲染优化
    - 请求放 onLoad 提前发
    - data 只放视图要用的数据
    - onLoad 不做同步阻塞操作
  - 渲染性能优化
    - setData 少调用、数据量小
    - wx:key 精确识别列表节点
    - 长列表用虚拟列表 / recycle-view
    - 展示加工用 WXS 在渲染层算
