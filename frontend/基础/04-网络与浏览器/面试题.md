## 一、链路与协议

### Q1: 从输入 URL 到页面渲染的完整链路？（第 02 篇）

- **结论**：URL → DNS → TCP/TLS → 请求 HTML → 解析构建 DOM/CSSOM → 渲染树 → 布局 → 绘制 → 合成。
- **原理**：每段都是关键路径的一部分；同步脚本阻塞解析，CSS 阻塞渲染，渲染要等 CSSOM 就绪但不一定等所有图片。
- **边界**：同步脚本阻塞解析、CSS 阻塞渲染与后续脚本执行——"放哪"直接决定首屏快慢。
- **追问**：优化抓手对应每一段——`dns-prefetch`/`preconnect` 缩短连接、关键 CSS 内联、脚本 `defer`/module、资源 hash 长缓存。
- **场景**：H5 首屏优化就是逐段压缩这条链路：DNS 预解析 + 预连接 + 非阻塞脚本 + 图片懒加载。

### Q2: HTTP 与 HTTPS 的区别？（第 01 篇）

- **结论**：HTTPS = HTTP + TLS，在 TCP 之上加加密、身份认证与完整性校验。
- **原理**：TLS 握手协商密钥（非对称交换密钥、对称加密传输），证书校验防中间人；HTTP 明文，可被窃听、篡改、伪装。
- **边界**：HTTPS 增加一次 RTT 与计算开销；证书过期 / 自签会告警或阻断；HSTS 强制跳转能防降级攻击。
- **追问**：混合内容（Mixed Content）是"页面 HTTPS、子资源 HTTP"——现代浏览器直接阻止该子资源加载。
- **场景**：登录、支付、Cookie 传输必须 HTTPS；静态资源站全站 HTTPS + HSTS。

### Q3: TCP 三次握手与四次挥手？（第 01 篇）

- **结论**：三次握手建连（SYN → SYN+ACK → ACK），四次挥手断连（FIN → ACK → FIN → ACK）。
- **原理**：握手是为了双方确认收发能力与初始序号（ISN），防止历史报文串扰；挥手因为连接是双工的，两端各自关闭、各需一次 FIN/ACK。
- **边界**：`TIME_WAIT` 是主动关闭方等待 2MSL，防旧报文到达；大量短连接会堆积 `TIME_WAIT`，是服务端调优常见点。
- **追问**：TLS 在 TCP 握手之后，所以 HTTPS 首次连接是 3（TCP）+ 若干（TLS）次往返。
- **场景**：弱网下每多一次 RTT 都更慢——`preconnect` 提前做完 DNS+TCP+TLS，正是把握手成本移到空闲期。

### Q4: HTTP/1.1 队头阻塞？HTTP/2 怎么解决？HTTP/3（QUIC）呢？（第 01 篇）

- **结论**：HTTP/1.1 同连接串行请求有队头阻塞；HTTP/2 多路复用解决应用层；HTTP/3 用 QUIC（UDP）解决传输层。
- **原理**：HTTP/1.1 一个连接同时一个请求，前面的慢响应堵住后面的；HTTP/2 二进制分帧 + 单连接多路复用 + 头部压缩（HPACK）+ 服务端推送；HTTP/3 把可靠传输挪到用户态 QUIC，丢包只影响单条流。
- **边界**：HTTP/2 的 TCP 层队头阻塞仍存在（一个 TCP 连接共享拥塞窗口）；服务端推送易浪费带宽、慎用。
- **追问**：HTTP/3 为什么用 UDP？→ 在用户态实现可靠传输与流复用，才能摆脱 TCP 的全局队头阻塞。
- **场景**：移动弱网下 QUIC 减少建连与丢包重传成本；HTTP/2 部署简单（TLS 1.3 上），先于 HTTP/3 普及。

### Q19: GET 与 POST 的区别？（第 01 篇）

- **结论**：GET 取数据、参数在 URL、幂等；POST 提交数据、参数在请求体、非幂等——本质差异是**语义**，安全性由 HTTPS 保证。
- **原理**：GET 无请求体、可缓存、可收藏书签、可被预加载（`<link rel="prefetch">`）；POST 有请求体、数据放在体里避免进 URL（也避免日志泄漏）；两者传输安全与否取决于是否走 HTTPS，GET 明文参数并不比 POST"更不安全"。
- **边界**：GET 参数放 URL 有长度限制（服务器/代理限制，非协议规定）且会进访问日志；POST 幂等性看实现——`PUT` 才是语义上幂等的方法，重复 POST 可能重复创建资源。
- **追问**：既然语义不同，为什么有人用 POST 传查询参数？→ 参数复杂（对象/数组）或过长时 URL 放不下，只能用体传输。
- **场景**：列表查询/详情用 GET（可缓存可分享链接），创建订单/提交表单/上传用 POST，删除用 DELETE、整体更新用 PUT。

### Q20: TCP 与 UDP 的区别？各自应用场景？（第 01 篇）

- **结论**：TCP 面向连接、可靠、有流量/拥塞控制；UDP 无连接、不可靠、快——"要可靠选 TCP，要低延迟选 UDP"。
- **原理**：TCP 三次握手建连、确认应答 + 超时重传 + 乱序重排保证可靠，滑动窗口做流量控制、慢启动/拥塞避免控制发送速率；UDP 直接发数据报，无握手无确认，丢包不重传。
- **边界**：TCP 是面向字节流、有粘包问题（要封包/拆包），UDP 面向报文、自带消息边界不会粘包；TCP 队头阻塞（一个包丢了后面的全等），UDP 无此问题。
- **追问**：HTTP/3 为什么基于 UDP？→ QUIC 在 UDP 上自己实现可靠性与多路复用，丢掉 TCP 的全局队头阻塞，兼顾快与可靠。
- **场景**：HTTP/HTTPS、WebSocket、文件传输走 TCP；实时音视频、直播、DNS 查询、游戏对战走 UDP（丢几帧可接受、延迟敏感）。

### Q21: WebSocket 与 HTTP 的区别？即时通信方案怎么选？（第 01 篇）

- **结论**：WebSocket 是复用 HTTP 握手的全双工持久连接协议，服务器能主动推送；HTTP 是半双工请求-响应，服务器无法主动推送。
- **原理**：一次握手（HTTP Upgrade 101）后连接长驻，双方随时互发，数据帧轻量（二进制/文本）；HTTP 每次请求都要带头部、且只能客户端发起。
- **边界**：WebSocket 没有同源限制，服务端必须校验 `Origin` 防跨站连接；断线要自己重连、空闲要心跳保活（代理会掐空闲连接）。
- **追问**：SSE 呢？→ SSE 是单向（服务器→客户端）的流式 HTTP，实现简单、自动重连，但客户端不能推；性能上 WebSocket > SSE > 长轮询 > 短轮询，兼容性反之。
- **场景**：聊天、行情推送、协同编辑用 WebSocket；服务端单向推送（通知、日志流）SSE 更省事；低频场景短轮询够用。

## 二、缓存与存储

### Q5: 强缓存与协商缓存的区别？（第 03 篇）

- **结论**：强缓存命中直接读本地不发请求；协商缓存需一次往返拿 304。
- **原理**：强缓存看 `Cache-Control: max-age` / `Expires`，命中返回 200（from cache）；协商缓存带 `If-None-Match`（`ETag`，内容哈希，优先）/ `If-Modified-Since`（`Last-Modified`），服务器回 304 复用本地。
- **边界**：`no-store` 完全放弃缓存；`no-cache` 不是不缓存，而是每次都要协商；HTML 不宜长缓存——内容更新用户看不到、发版失效困难。
- **追问**：资源 hash 文件名 + 长缓存是标准做法——内容变 → 文件名变 → 缓存自动失效，发版只换变了的那批文件。
- **场景**：`index.html` 走 `no-cache`，`app.8f3a.js` / 图片走 `max-age=31536000, immutable`。

### Q6: `Cookie` / `localStorage` / `sessionStorage` / `IndexedDB` 的区别与选型？（第 03 篇）

- **结论**：Cookie 随请求自动携带且容量最小（4KB），localStorage 持久 5MB+，sessionStorage 标签页级，IndexedDB 是异步大容量数据库。
- **原理**：Cookie 由服务端 `Set-Cookie` 下发、请求自动带（也因此有 CSRF 面）；localStorage 同源持久、同步 API；sessionStorage 随标签页关闭清空；IndexedDB 存储结构化数据、事务与索引，适合离线 / 大数据量。
- **边界**：Cookie 放凭证要 `HttpOnly` + `SameSite`；localStorage 同步读写大对象会卡主线程；IndexedDB API 繁琐，通常用库（Dexie）。
- **追问**：登录态凭证放哪？→ Cookie（HttpOnly）由浏览器管理，别落进 localStorage——localStorage 被 XSS 一读就走。
- **场景**：主题 / 草稿用 localStorage；购物车 / 离线缓存用 IndexedDB；会话标识用 Cookie。

### Q7: 接口缓存与实时性冲突怎么处理（金融场景）？（第 03 篇）

- **结论**：按数据时效性分级——资金类绝不缓存，配置/字典类可长缓存，用户资料类短缓存。
- **原理**：缓存 key = URL + 序列化入参；TTL 过期或写操作后主动清 key；缓存放内存（模块级 Map）不落盘。
- **边界**：金额、可用额度、费率、还款计划必须实时——错一次就是资金错误；TTL 加随机抖动防雪崩；key 必须含用户标识，写操作后清相关 key，否则串数据。
- **追问**：为什么不持久化？→ 金融数据落盘是风险，内存缓存进程内即生命周期内有效即可。
- **场景**：项目接口工具层逐接口声明缓存策略：运营位文案 / 协议文本缓存 5 分钟，额度接口不缓存。

## 三、渲染机制

### Q8: 重排 / 重绘 / 合成的触发条件？（第 02 篇）

- **结论**：重排（Layout）代价最高、必带重绘；重绘（Paint）其次；合成（Composite）走 GPU 最便宜。
- **原理**：改几何属性（宽高、margin、增删节点）、读 `offsetWidth` 等强制同步布局都触发重排；只改颜色 / 背景触发重绘；`transform` / `opacity` 走合成层不触发前两者。
- **边界**：`display:none` 触发重排，`visibility:hidden` 只触发重绘；渲染不在每帧都发生，受 JS 执行与帧调度影响。
- **追问**：`will-change` 提前提升合成层，滥用会占 GPU 内存反而更卡。
- **场景**：列表滚动 + 动画全用 `transform`；图片声明尺寸防 CLS；批量 DOM 操作合并、读写分离。

### Q22: DOM 事件流三个阶段？事件委托的原理与局限？（第 02 篇）

- **结论**：事件按 捕获 → 目标 → 冒泡 三个阶段传播；事件委托 = 把子元素监听绑到公共祖先，利用冒泡统一处理。
- **原理**：`addEventListener(type, fn, useCapture)` 第三个参数 `true` 在捕获阶段触发、`false`（默认）在冒泡阶段触发，`onclick` 只能监听冒泡阶段；委托回调里用 `e.target.closest(selector)` 找到真实目标再分发逻辑。
- **边界**：`e.stopPropagation()` 阻止传播、`e.preventDefault()` 阻止默认行为，两者互不相干；不冒泡的事件（`focus`/`blur`/`scroll`/`mouseenter`/`mouseleave`/`resize`）无法委托——`focus` 用 `focusin` 代替。
- **追问**：委托为什么省内存？→ N 个子元素的回调收敛成 1 个，且新增动态节点免重新绑定；但 `mousemove` 这类高频事件在父级统一处理反而费计算、委托层级过深查找成本高。
- **场景**：长列表点击（li 上千个只绑 ul 一个监听）、动态增删的表格/菜单、全局事件埋点（统一在 document 捕获阶段监听上报）。

## 四、跨域与通信

### Q9: CORS 跨域？预检请求什么时候触发？（第 01 篇）

- **结论**：CORS 是浏览器基于响应头的跨域放行机制；预检（OPTIONS）只在"非简单请求"时触发。
- **原理**：简单请求（GET/POST + 简单头 + `text/plain` 等）直接发，响应带 `Access-Control-Allow-Origin` 才放行；自定义头、非简单方法、`application/json` 会先 OPTIONS 预检，服务端回 `Allow-Methods` / `Allow-Headers`。
- **边界**：`credentials: 'include'` 携带 Cookie 需服务端 `Access-Control-Allow-Credentials: true` 且 `Allow-Origin` 不能是 `*`；预检不通过请求根本不会发出。
- **追问**：后端网关统一加 CORS 头可免预检负担；同源部署（Nginx 反代）是最省事的规避。
- **场景**：H5 调接口域名不同 → 网关配 `Access-Control-Allow-Origin`，POST `application/json` 的预检由网关统一应答。

### Q10: `postMessage` 为什么要校验 `origin`？（第 02 篇）

- **结论**：不校验 `origin`，任何页面都能向你的窗口发消息，伪造指令 / 窃取数据。
- **原理**：`window.postMessage` 是跨窗口 / 跨 iframe 通信通道；`message` 事件的 `event.origin` 是可信来源标记，必须先白名单比对再处理 `event.data`，`event.source` 也要校验。
- **边界**：只校验 `data` 不校验 `origin` 等于没防——攻击者可以从任意源发同结构数据；监听器用完要移除防泄漏。
- **追问**：`targetOrigin` 参数写 `'*'` 会把消息发给任何同域 / 跨域窗口，应写具体源。
- **场景**：H5 与 App 原生桥通信、与第三方 SDK iframe 通信，一律先 `if (event.origin !== EXPECTED) return`。

### Q11: `window.opener` 与 `rel="noopener"` 的风险？（第 04 篇）

- **结论**：`target="_blank"` 打开的页面能通过 `window.opener` 反向操作原页面，`rel="noopener"` 切断这条链。
- **原理**：`window.opener` 是"反向引用"，新页面（甚至恶意页面）可 `opener.location = ...` 把原页面跳走（反向 tabnabbing）或读取原页面对象。
- **边界**：`rel="noreferrer"` 隐含 noopener 且不传 Referer；现代浏览器 `target="_blank"` 已默认 noopener，但老内核仍要显式写。
- **追问**：外链、第三方跳转页全部加 `rel="noopener noreferrer"` 是安全基线。
- **场景**：活动页外链落地页 `target="_blank" rel="noopener noreferrer"`，防止恶意落地页劫持活动页跳转钓鱼。

## 五、安全

### Q12: XSS 的三种形态与防御？（第 04 篇）

- **结论**：存储型（持久化）、反射型（URL 注入）、DOM 型（前端渲染注入）；防御核心是输出转义 + CSP + 输入校验。
- **原理**：用户输入未转义进入 HTML / JS 执行；`innerHTML` / `v-html` 是高发点；`textContent` 只当文本。
- **边界**：仅前端转义不够，需 CSP 与后端校验双层；富文本只能白名单（DOMPurify），不能靠黑名单。
- **追问**：`meta charset` 与 XSS 的关系？→ 编码声明被绕过（如早期 UTF-7 攻击）是历史漏洞，现代主防线是 CSP + 转义。
- **场景**：评论 / 昵称展示用 `textContent` 或框架转义；第三方富文本编辑器内容用 DOMPurify 过滤后再 `v-html`。

### Q13: CSRF 怎么防御？`SameSite=Lax` 能防住什么、防不住什么？（第 04 篇）

- **结论**：CSRF 是"借用户凭证发起非预期请求"；防御三板斧是 SameSite Cookie、Token 校验、Referer/Origin 校验。
- **原理**：浏览器自动携带 Cookie 的特点被利用；`SameSite=Lax` 阻止跨站 POST 携带，但跨站链接跳转触发的 GET 仍会带——接口若用 GET 改数据就有风险。
- **边界**：SameSite 防不住"同站子域"与"GET 副作用"；Token 需防 XSS 窃取（配合 HttpOnly / CSP）。
- **追问**：为什么 SameSite 不是银弹？→ 它只约束"浏览器带不带 Cookie"，Token / Origin 校验才是业务侧主动防御。
- **场景**：登录态 Cookie 设 `SameSite=Lax` + `HttpOnly`；关键写接口加自定义请求头 / Token 校验。

### Q14: CSP 的 nonce/hash 原理与局限？（第 04 篇）

- **结论**：CSP 白名单限制脚本来源；`nonce`/`hash` 是"动态脚本放行"方案，精确到单条脚本。
- **原理**：`Content-Security-Policy: script-src 'nonce-xxx'`——服务器给合法脚本标签加 `nonce` 属性，浏览器只执行 nonce 匹配的内联/外链脚本；`'sha256-...'` 则按内容哈希放行。
- **边界**：nonce 每次响应要随机，写死等于没设；hash 对每次改动都要重算，适合静态页面；CSP 只管"来源"，不防 DOM 型 XSS 把恶意脚本挂进已被信任的标签。
- **追问**：`strict-dynamic` 让 nonce 链传播——被信任脚本动态创建的脚本也继承信任，同时要求移除白名单兜底。
- **场景**：活动页内联监控脚本 + 上报脚本，用 nonce 放行并配 `object-src 'none'` 收紧。

### Q15: HTTPS 下的混合内容（Mixed Content）风险？（第 01 篇）

- **结论**：HTTPS 页面加载 HTTP 子资源即混合内容；现代浏览器直接阻止 HTTP 脚本 / 图片等子资源。
- **原理**：混合内容会让"页面加密、部分资源明文"，中间人能篡改插入恶意代码；浏览器分级——主动内容（脚本）直接 block，被动内容（图片）先降级后全面阻止。
- **边界**：升级到 HTTPS 后遗留的 HTTP 引用（CDN、图片、iframe）是常见来源；用 `block-all-mixed-content` 强制。
- **追问**：排查方式是 DevTools Console 的 Mixed Content 提示 + Network 面板按协议过滤。
- **场景**：老项目全站 HTTPS 化后，残留 http 图片导致页脚图挂掉——把 CDN 域名统一 https + CSP `upgrade-insecure-requests`。

### Q16: 金融 H5 接入第三方 SDK（埋点/推广），要求不影响主流程且不泄露凭证，怎么设计？（第 04 篇）

- **结论**：按"信任边界"设计——CSP 限制来源 + SRI 防篡改，脚本异步加载，通信校验 origin，凭证最小化，异常隔离。
- **原理**：第三方脚本默认拥有当前页的全部权限，必须显式圈定其能力：`script-src` 只放行可信 CDN + `integrity`（SRI）防内容被篡改；`async` 加载不阻塞主流程；`postMessage` 通信必须校验 `event.origin`。
- **边界**：接口鉴权不依赖前端可读凭证——"前端拿不到、不该拿到的凭证就不落地到前端"；第三方异常单独捕获上报，不打断主流程。
- **追问**：Cookie 最小化——第三方域名的 Cookie 用 `SameSite` + `HttpOnly`，能不放凭证就不放。
- **场景**：埋点 SDK 用 `<script async crossorigin integrity=...>` 注入，App 桥通信 `postMessage` 双端校验 origin，SDK 报错走独立通道。

## 六、工程与监控

### Q17: App 预取（端能力）怎么设计降级？（附录）

- **结论**：预取 = Native 在 WebView 打开前请求数据并缓存，H5 用端能力直接取；必须带超时降级。
- **原理**：`getPrefetchData` 省掉首屏一次网络往返；取数失败 / 未命中走标准请求，等待预取设上限（如 500ms）超时立即降级——绝不能让"等预取"变白屏。
- **边界**：预取失败与真实接口失败在监控上必须分开埋点，否则把预取问题误判为接口问题。
- **追问**：预取命中但数据过期怎么办？→ 由缓存策略的 TTL 判定，过期按未命中处理走标准请求。
- **场景**：金融 H5 首页额度展示——App 预取额度数据，H5 打开直接渲染，500ms 未等到就发标准请求，用户无感。

### Q18: 错误分级（network-error / logic-error）决定什么？（附录）

- **结论**：错误分级决定"谁来看、怎么处置"——网络错误找运维/网关，逻辑错误找前端。
- **原理**：`network-error`（超时、404、5xx、CORS 失败）反映链路与后端问题，`logic-error`（JS 异常、数据格式不符）反映前端问题；分级后告警路由与责任人明确。
- **边界**：资源加载错误不冒泡，必须捕获阶段监听（`window.addEventListener('error', fn, true)`）；上报多通道按环境分流——容器内走原生桥、H5 外跳走 HTTP。
- **追问**：异常监控五维（JS 错误 / 白屏 / 资源加载 / 接口成功率耗时 / 初始化健康度）是金融项目的完整口径。
- **场景**：监控平台按 `errorType` 分组告警——`network-error` 升到网关团队，`logic-error` 升到前端，避免"都在看、都没人负责"。
