## 2. 重点题精答（五步法）

### Q1：从输入 URL 到页面渲染的完整链路？

- **结论**：URL → DNS → TCP/TLS → 请求 HTML → 解析构建 DOM/CSSOM → 渲染树 → 布局 → 绘制 → 合成。
- **原理**：每段都是关键路径的一部分；同步脚本阻塞解析，CSS 阻塞渲染。
- **场景**：优化抓手 = dns-prefetch/preconnect 缩短连接、关键 CSS 内联、脚本 defer/module、资源 hash 长缓存。
- **边界**：渲染不一定等所有资源（图片异步），但等 CSSOM。
- **追问**：CSS 会阻塞 DOM 解析吗？→ 不阻塞解析，但阻塞渲染与后续脚本执行。

### Q2：强缓存与协商缓存？

- **结论**：强缓存命中直接读本地不发请求；协商缓存 304 需一次往返。
- **原理**：强缓存看 `Cache-Control: max-age` / `Expires`；协商缓存看 `ETag`（内容哈希，优先）与 `Last-Modified`（时间）。
- **场景**：HTML `no-cache`/短缓存；静态资源（hash 文件名）长缓存——发版只失效内容变化的文件。
- **边界**：`no-store` 完全放弃缓存；`no-cache` 不是不缓存，而是每次协商。
- **追问**：为什么 HTML 不宜长缓存？→ 内容更新用户看不到，发版失效困难。

### Q3：HTTP/1.1 队头阻塞与 HTTP/2 / HTTP/3？

- **结论**：HTTP/1.1 同连接串行请求有队头阻塞；HTTP/2 多路复用解决应用层；HTTP/3 用 QUIC（UDP）解决传输层。
- **原理**：HTTP/1.1 一个连接一个请求；HTTP/2 二进制分帧 + 多路复用 + 头部压缩 + 服务端推送；HTTP/3 丢包不再阻塞整条流。
- **场景**：移动端弱网下 QUIC 减少 RTT；HTTP/2 仍需考虑连接数上限。
- **边界**：HTTP/2 的 TCP 层队头阻塞仍存在；服务端推送慎用。
- **追问**：HTTP/3 为什么用 UDP？→ 在用户态实现可靠传输与流复用，摆脱 TCP 队头阻塞。

### Q4：XSS 的三种形态与防御？

- **结论**：存储型（持久化）、反射型（URL 注入）、DOM 型（前端渲染注入）；核心防御是输出转义 + CSP + 输入校验。
- **原理**：用户输入未转义进入 HTML 执行；`innerHTML`/`v-html` 是高发点。
- **场景**：`textContent` 比 `innerHTML` 安全；框架默认转义；第三方富文本需白名单过滤（DOMPurify）。
- **边界**：仅前端转义不够，需 CSP 与后端校验双层。
- **追问**：`meta charset` 与 XSS 的关系？→ 编码声明被绕过（如早期 UTF-7 攻击）是历史漏洞，现代主防线是 CSP + 转义。

### Q5：CSRF 与 SameSite？

- **结论**：CSRF 是"借用户凭证发起非预期请求"；防御三板斧：SameSite Cookie、Token 校验、Referer/Origin 校验。
- **原理**：浏览器自动携带 Cookie 的特点被利用；`SameSite=Lax` 阻止跨站 POST 携带，但 GET 导航（链接跳转）仍会带。
- **场景**：登录态 Cookie 设 `SameSite=Lax/Strict`；关键写接口加自定义 Token。
- **边界**：SameSite 防不住"同站子域"与"GET 副作用"；Token 需防 XSS 窃取。
- **追问**：SameSite=Lax 防不住什么？→ 跨站链接跳转触发 GET 请求仍携带 Cookie，若接口用 GET 改数据就有风险。

### Q6：接口缓存与实时性冲突？（简历核心）

- **结论**：按数据时效性分级——资金类绝不缓存，配置/字典类可长缓存，用户资料类短缓存。
- **原理**：缓存 key = URL + 序列化入参；TTL 过期或写操作后主动清 key。
- **场景**：项目接口工具层：运营位文案/协议文本可缓存；金额、可用额度、费率、还款计划必须实时（错一次就是资金错误）。
- **边界**：缓存放内存（模块级 Map）不做持久化——金融数据落盘是风险；TTL 加随机抖动防雪崩。
- **追问**：怎么避免缓存串数据？→ key 必须含用户标识与关键入参；写操作后清相关 key。

### Q7：App 预取怎么设计降级？（简历核心）

- **结论**：预取 = Native 在 WebView 打开前请求数据并缓存，H5 用端能力直接取；必须有超时降级。
- **原理**：`getPrefetchData` 省掉首屏一次网络往返。
- **场景**：取数失败/未命中走标准请求；等待预取设上限（如 500ms）超时立即走标准请求——绝不能让"等预取"变白屏。
- **边界**：预取与真实接口失败在监控上必须分开（埋点区分），否则把预取问题误判为接口问题。
- **追问**：预取失败会怎样？→ 降级为标准请求，用户无感。

## 3. 追问链

1. "跨域资源怎么带上 Cookie？" → `credentials: 'include'` + 服务端 `Access-Control-Allow-Credentials`。
2. "CORS 预检什么时候触发？" → 非简单请求（自定义头、非简单方法、application/json）。
3. "错误分级有什么价值？" → 决定谁来看：network-error 找运维/网关，logic-error 找前端。
4. "上报为什么多通道分流？" → 容器内走原生桥、H5 外跳走 HTTP，同一份上报代码运行时判定环境。

## 4. 场景设计题

**场景：金融 H5 接入一个第三方 SDK（埋点/推广），要求不影响主流程且不泄露凭证，怎么设计？**
- 答题骨架：信任边界（CSP 限制脚本来源 + SRI 防篡改）→ 第三方脚本 async 加载不阻塞 → postMessage 通信必须校验 origin → Cookie 最小化（SameSite + HttpOnly）→ 接口鉴权不依赖前端可读凭证 → 错误隔离（第三方异常捕获上报不打断主流程）。
- 加分点：说明"前端拿不到、不该拿到的凭证就不落地到前端"的边界思维，呼应简历金融安全边界。

## 5. 面试口径（简历项目如何表达）

- **项目证据**：接口工具层缓存（URL+入参为 key、逐接口声明策略、时效性分级）、App 预取 `getPrefetchData` + 500ms 超时降级、错误分级 `network-error`/`logic-error`、上报多通道按环境分流（容器内原生桥 / 外跳 HTTP）、埋点区分"预取超时降级"与"真实接口失败"。
- **表达句式**："接口缓存按数据时效性分级，资金类绝不缓存；App 预取做了超时降级，绝不让等预取变白屏，并且预取失败与真实接口失败在监控上分开统计，避免误判。"
- **加分表达**：异常监控五维（JS 错误 / 白屏 / 资源加载 / 接口成功率耗时 / 初始化健康度）——"资源加载错误必须用捕获阶段监听，因为 error 事件不冒泡"。
