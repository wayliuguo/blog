# 模块总结 · 网络与浏览器

## 知识主线

四篇不是并列的知识点，而是一条有依赖关系的链，每一篇都在回答上一篇留下的问题：

```
01 HTTP 与 HTTPS（浏览器和服务器怎么说话）
        │  资源通过网络拿到了，浏览器下一步怎么把它变成页面？
        ▼
02 浏览器渲染原理（页面怎么画出来）  ★主轴
        │  页面画出来了，登录态、偏好这些状态该存在哪？
        ▼
03 浏览器存储与本地缓存（数据放在哪）
        │  数据都放进浏览器了，怎么防止被别人偷走？
        ▼
04 前端安全（怎么守住信任边界）
```

本模块的主轴是**浏览器渲染原理**：01 讲页面资源怎么从服务器传过来（HTTP/HTTPS/DNS/缓存），02 讲资源到了之后如何走完"解析 → 布局 → 绘制 → 合成"变成像素（多进程、DOM/CSSOM、回流重绘、关键渲染路径），03 讲页面运行中产生的数据存到哪里（Cookie/Web Storage/IndexedDB/Cache Storage），04 把前面所有环节放回"信任边界"的视角，讲 XSS/CSRF/CSP 等攻击与防御。串起来正好是"输入 URL → 页面渲染完成 → 数据持久化 → 安全防护"的完整链路。

## 分篇知识点

### 01-HTTP 与 HTTPS

- **HTTP 是无状态的应用层协议**：每个请求独立，服务器不记忆客户端，靠 Cookie/Session/Token 显式携带身份来模拟"有状态"；报文由请求/响应行 + 头 + 空行 + 体组成
- **方法语义与幂等性**：GET 取数据（幂等）、POST 提交（非幂等）、PUT 整体替换（幂等）、PATCH 局部更新、DELETE（幂等）；网络超时重试时靠幂等性做正确决策；GET/POST 唯一本质差异是语义，安全性由 HTTPS 提供
- **状态码五类**：2xx 成功、3xx 重定向（301 永久 / 302 临时 / 304 协商缓存命中）、4xx 客户端错误（401 未认证 vs 403 无权限）、5xx 服务端错误（500/502/503/504）
- **强缓存 vs 协商缓存**：强缓存（Cache-Control 优先于 Expires）命中不发请求直接用副本；协商缓存带 If-None-Match/If-Modified-Since 条件请求，304 确认后复用（ETag 优先于 Last-Modified）；静态资源用内容指纹文件名 + 长 max-age
- **HTTP/1.1 → 2 → 3 的演进主线是"消除队头阻塞"**：HTTP/2 用二进制分帧 + 多路复用解决 HTTP 层阻塞（一个 TCP 连接多个流），HTTP/3 换 QUIC（基于 UDP）彻底解决 TCP 层队头阻塞
- **HTTPS = HTTP + TLS 混合加密**：非对称加密协商会话密钥 + 对称加密传数据，CA 证书体系防中间人冒充；DNS 走"浏览器/系统缓存 → 本地 DNS 递归 → 根/顶级/权威迭代查询"把域名换成 IP

### 02-浏览器渲染原理

- **多进程架构**：浏览器主进程 / 渲染进程（每标签页一个）/ GPU 进程 / 网络进程，价值在隔离与稳定；渲染相关的 CPU 工作集中在渲染进程主线程，"减少主线程工作 ≈ 提升渲染性能"
- **导航流程**：输入 URL → DNS → TCP/TLS → HTTP 请求 → 网络进程把 HTML 交给渲染进程 → 解析 → 布局 → 绘制 → 合成
- **解析与阻塞**：HTML 字节流 → 字符 → Token → 节点 → DOM 树；CSS 是渲染阻塞资源，普通 `<script>` 阻塞 HTML 解析，用 `defer`（解析完按序执行）/ `async`（下载完立即执行）解决
- **DOM/CSSOM/Render Tree**：结构 / 样式 / 可绘制中间产物；渲染树只含可见节点，剔除 `display:none` 与 `<head>` 等
- **回流 vs 重绘 vs 合成**：回流（Layout）改几何最贵、必然伴随重绘；重绘（Paint）只改外观；合成（Composite）只拼合图层位图最廉价，`transform`/`opacity` 动画可跑在合成器线程不占主线程
- **优化清单**：减少关键资源体积、defer/async、批量读写 DOM 避免强制同步布局（offsetWidth 等会强制刷新）、动画用 transform/opacity + GPU 合成、`will-change` 适度使用、`content-visibility` 跳过屏外渲染

### 03-浏览器存储与本地缓存

- **Cookie**：服务端 Set-Cookie 下发、随同源请求自动携带，容量约 4KB/条；核心属性 Expires/Max-Age、Path、Domain、Secure、HttpOnly（防 XSS 读）、SameSite（Strict/Lax/None，Lax 是默认最优解）
- **localStorage vs sessionStorage**：同步、约 5MB、只存字符串（对象要 JSON 序列化）、不随请求发送；区别只在生命周期（持久 vs 关标签页即清）与作用域（同源全标签页 vs 同一标签页）；同步写大数据会阻塞主线程，隐私模式可能抛 QuotaExceededError
- **IndexedDB**：浏览器内置的 NoSQL 事务型数据库，支持索引、事务、异步读写，容量百 MB~GB 级，适合大量结构化数据（离线笔记、聊天记录）；原生 API 繁琐，常用 Dexie.js / idb 封装
- **Web SQL 已废弃**：基于 SQLite 的关系型规范，W3C 正式废弃，新项目用 IndexedDB 替代
- **Service Worker + Cache Storage**：SW 是独立线程的网络代理，须 HTTPS；以"请求-响应"为单位缓存；策略按数据新鲜度选：Cache First / Network First / Stale-While-Revalidate / Network Only
- **选型流程**：要随请求自动携带或用会话态 → Cookie；复杂大数据 → IndexedDB；需跨标签页持久 → localStorage；关页即清的临时态 → sessionStorage

### 04-前端安全

- **XSS 三类**：反射型（URL 注入非持久）、存储型（入库持久、危害最大、横向传播）、DOM 型（前端 innerHTML/eval 注入）；防御 = 输入白名单校验 + 输出上下文编码 + `textContent`/DOMPurify + Cookie HttpOnly + CSP 纵深防御
- **CSRF**：利用浏览器自动带 Cookie 发请求；首选 `SameSite=Lax` 从根上阻断跨站携带，再辅以 CSRF Token、校验 Origin/Referer、敏感操作二次验证
- **CSP**：白名单约束资源来源（script-src/connect-src/frame-ancestors 等），内联脚本用 nonce/hash 放行；`frame-ancestors` / `X-Frame-Options` 直接防御点击劫持
- **SQL 注入与上传安全**：SQL 注入根治在服务端参数化查询，前端校验可被绕过不能作安全边界；上传做类型白名单 + 魔数校验 + 重命名非可执行目录存储，SVG 可能内嵌脚本需净化
- **纵深防御模型**：传输层 HTTPS+HSTS → 输入输出编码 → 会话 Cookie 三件套（HttpOnly/Secure/SameSite）→ 策略层 CSP → 服务端参数化查询与鉴权 → 监控风控

## 代码与自测入口

配套代码项目：`./code`，零依赖静态服务器，启动 `node server.js` 后打开 `http://localhost:5177/` 。site 目录下的代表 demo：

- `fetch-status.html`：Fetch 发起请求，回显状态码并演示 Promise resolve/reject 时序（对应 01 篇）
- `promise-order.html`：极简 fetch 封装 + Promise 微任务/宏任务执行顺序（对应 01 篇）
- `block-render.html`：同步 while 空转把主线程"冻住"，直观看到渲染被卡（对应 02 篇）
- `storage-demo.html`：写读 localStorage / sessionStorage / Cookie，刷新与关页后观察各自生命周期与作用域（对应 03/04 篇）
