## 1. React 核心概念

### 1.1 一切皆组件：组件、依赖与 JSX 根节点

六篇不是并列知识点，而是一条有依赖关系的链：**掌握 React 的完整路线是"用 React 写出一个可维护的 SPA"**。

```
01 React 核心概念（界面怎么描述、组件怎么写）
        │  组件会写了，但数据一变界面怎么跟着变、副作用放哪？
        ▼
02 React Hooks（状态与副作用）  ★主轴
        │  组件多了、页面多了，怎么在页面之间切换？
        ▼
03 React 路由（URL ↔ 组件）
        │  跨组件、跨页面共享的数据越来越多，放哪统一管？
        ▼
04 React 状态管理（全局状态）
        │  项目变大，怎么让组件不出错、可维护？
        ▼
05 React 使用 TS（类型约束）
        │  组件逻辑清楚了，样式怎么写、怎么隔离？
        ▼
06 React 使用 CSS（样式方案）
```

**React 一切皆组件**：

- **组件的定义**：一块拥有自身逻辑与外观的 UI，小到按钮大到整个页面，可嵌套组合；组件拆分利于代码组织与维护，尤其适合大型软件。
- **组件就是一个函数**：输入 props、返回一段 JSX，可用 TS 定义 props 类型与泛型（`interface` 描述结构、`type` 做类型编程）。

**核心依赖分工**：

| 依赖 | 职责 |
| ---- | ---- |
| `react` | 定义组件、管理状态与生命周期 |
| `react-dom` | 把 JSX 渲染成 Web 真实 DOM 或 Native 原生控件 |
| `babel` | 把 JSX 转成 React 代码（用 `React.createElement` 手写源码时可不依赖） |

**JSX 的根节点约束**：JSX 是 JS 的语法扩展，一段 JSX 只能有一个根节点（外层包 `div` 或 `<></>` Fragment），标签必须闭合（`<input/>`、`<br/>`），常在外层包小括号便于阅读。

### 1.2 标签规则与 JSX 表达式

**标签首字母规则**：

```
小写开头  视为 HTML 原生元素，若 HTML 中没有同名元素则报错
大写开头  React 渲染对应组件，组件未定义则报错
          <input/> 与 <Input/> 含义完全不同
```

标签可像 HTML 一样进行嵌套。

**JSX 表达式 `{xxx}`**：

- **嵌入表达式**：可嵌变量、表达式、属性值与注释；`number/string/array` 直接显示，`null/undefined/boolean` 渲染为空（可用 `toString()`、字符串拼接、`String()` 转成字符串显示），**对象类型不能作为子元素**。
- **判断**：`if...else` 不能直接放进 `{xxx}`，用逻辑运算符 `&&`、三元 `a ? b : c`、函数封装三种方式。
- **循环与 key**：用 `map` 生成列表，每项必须给唯一且稳定的 `key`（用业务 ID，不用 index、不用随机数），帮助 React 识别元素增删、优化 VDOM diff。
- **绑定属性**：`className` 对应 HTML 的 `class`、`for` 改为 `htmlFor`、内联 `style` 必须是驼峰键的 JS 对象（不能是字符串）。
- **显示 HTML**：JSX 默认防 XSS 注入，确需渲染 HTML 时用 `dangerouslySetInnerHTML={ { __html: 'xxx' } }`。

### 1.3 事件绑定与合成事件

- **合成事件与事件委托**：React 用自定义合成事件而非原生 DOM 事件，通过事件委托处理（委托给组件最外层元素）。
- **传引用而非调用**：`onClick={handleClick}` 而不是 `onClick={handleClick()}`，否则函数在渲染时立即执行。
- **传参与引用稳定**：需要传参时包一层箭头函数 `onClick={() => handleClick(id)}`，代价是每次渲染生成新函数，配合 `memo` 子组件时用 `useCallback` 稳定引用。
- **event 对象**：回调里通过 `event.target` 拿到发生事件的 DOM 元素对象，阻止默认行为用 `preventDefault()`、阻止冒泡用 `stopPropagation()`。

### 1.4 props 单向数据流与 Vue 对比

- **单向数据流**：父组件通过 props 向子组件传数据，子组件只能读取、不能直接修改 props；要改数据由父组件把处理函数一起传下来。
- **默认值**：用解构默认参数（如 `{ name, sex = '女' }`），`defaultProps` 已废弃。
- **类型校验**：用 TypeScript 做编译期检查；`prop-types` 已不再维护，React 19 移除了对函数组件 `propTypes` 的支持。

**与 Vue 模板的理念对比**：

| 维度 | React | Vue |
| ---- | ---- | ---- |
| 判断 | `&&` / 三元 | `v-if` |
| 循环 | `map` | `v-for` |
| 表达式 | `{xxx}` | 模板里全是 `"xxx"` |
| 设计理念 | "JS 能实现的都交给 JS、不重复定义指令"、要求 JS 熟练 | 自定义很多指令与写法、初学者更好理解好记忆，但这些写法需要记忆、查文档 |

- **Vue3 对 JSX 的态度**：Vue3 也能友好地支持 JSX（从最初抨击到最终接纳）。

## 2. React Hooks

### 2.1 useState 与不可变更新

**Hooks 让函数组件具备状态与副作用能力**：

- **解决的问题**：函数组件原本无法管理内部状态、无法执行副作用；两个核心特点是简化逻辑复用与关注分离（按功能而非生命周期组织代码）。
- **useState 基本用法**：参数是初始化值（任意类型、默认 undefined），返回 `[当前值, 更新函数]` 数组、通常解构取值。

**两种更新方式与异步更新**：

```
setCount(count + 1)        直接传新值
setCount(c => c + 1)       传函数接收旧值（更可靠）
异步更新    日志打印的不一定是最新值，简单数据直接传值还可能被合并
```

- **不可变数据是核心**：不能直接修改 state、而要 setState 一个"新"的值；更新机制是对引用地址做浅对比，地址没变就不触发重渲染；对象更新用扩展运算符创建新对象。
- **immer 简化不可变更新**：`produce(draft => { ... })` 代理 draft、用"可变"写法直接改 draft 生成不可变的新数据，避免手写扩展运算出错。
- **ESLint 约束**：安装 `eslint-plugin-react-hooks`，配置 `rules-of-hooks`（error）与 `exhaustive-deps`（warn）。

### 2.2 useEffect：三个生命周期的合一

**回调与依赖数组**：`useEffect(callBack, deps)` 的回调在挂载、更新、卸载时执行；`[]` 只挂载执行一次、有依赖则依赖变化时执行、不传第二个参数则每次渲染后都执行。

| 依赖写法 | 执行时机 |
| ---- | ---- |
| `[]` | 只在挂载执行一次 |
| `[dep]` | 挂载 + 依赖变化时执行 |
| 不传第二参 | 每次渲染后都执行 |

- **卸载清理**：回调 `return` 返回的函数在组件销毁时执行，用于解绑定时器与 DOM 事件、防止内存泄漏。
- **React 18 开发环境执行两次**：用于模拟组件创建→销毁→再创建流程、及早暴露问题（如弹窗重复、事件重复绑定），生产环境不会执行两次。

### 2.3 useRef

- **基本特性**：返回可变 ref 对象、`.current` 初始化为传入参数；值变化不会触发组件重新渲染，这是与 useState 的本质区别。
- **绑定 DOM**：`useRef<HTMLInputElement>(null)` + `<input ref={inputRef}>`，取值需判空（`inputRef.current?.focus()`）。
- **保存共享数据**：只适合保存不需要驱动 UI 的共享数据；update 结果不用于页面渲染时就不要用 useState、改用 useRef，避免无谓重渲染。

### 2.4 useMemo / useCallback

- **useMemo 缓存计算结果**：依赖项不变就不重新执行计算，适合计算量较大的场景做性能优化。
- **useCallback 缓存函数引用**：useMemo 的语法糖，依赖不变不生成新函数，避免子组件因父组件每次渲染传入新函数引用而无效重渲染。
- **官方定位**：都是性能优化手段，但"不要把它当成语义上的保证"——执行控制权在 React、不一定保证每个都缓存。

### 2.5 自定义 Hook：逻辑复用正解

- **与 HOC 对比**：高阶组件（HOC）存在组件嵌套地狱、props 透传、命名冲突；自定义 Hook 直接回到组件内部使用，复用逻辑的同时保持组件树扁平。
- **开发三步走**：先在组件内直接写、再抽成函数、最后抽到独立文件（`src/hooks/useXxx.ts`）复用。
- **常见实现**：`useTitle` 修改网页标题、`useMouse` 返回鼠标位置、`useGetInfo` 按依赖变更重新请求数据（返回 `{ loading, info }`）。
- **第三方库**：成熟 Hook 可发布 npm 沉淀为库——ahooks（国内流行、功能全面、文档清晰）、react-use（国外流行、英文文档）。

### 2.6 三条规则与闭包陷阱

```
命名规则   Hook 必须使用 useXxx 格式命名
调用位置   只能在组件内部与其他 Hook 内部调用，组件外部或普通函数中不能调用
顺序一致   每次渲染都必须按相同顺序调用，Hook 必须是组件"第一层代码"，
          不能放 if（前面有 return 也算条件）与 for 循环里
```

- **闭包陷阱**：异步回调里读 state 可能拿到旧值（闭包捕获了旧快照），因为 useState 是值类型、每次渲染快照独立。
- **useRef 解法**：useRef 是引用类型、跨渲染共享同一对象，用 `countRef.current = count` 同步最新值；原则是 useState 存驱动 UI 的值、useRef 存给异步闭包读取的最新值。

## 3. React 路由

### 3.1 前端路由的本质

**前端路由 vs 后端路由**：

| 类型 | 方式 | 特点 |
| ---- | ---- | ---- |
| 后端路由 | 服务器按路径返回不同页面 | 触发整页刷新 |
| 前端路由 | JS 拦截并响应路径变化、只替换部分内容 | 体验更流畅 |

```
hash 路由    URL 形如 http://xxx/#/about，改变 # 后的 hash 不触发浏览器发请求，
             兼容性最好（老旧浏览器也能用）
History 路由 URL 形如 http://xxx/about，基于 HTML5 History API
             （pushState/replaceState/popstate），URL 更美观，
             但刷新时需服务端把请求回落到入口页、否则 404
```

- **react-router-dom 的职责**：根据 URL 渲染对应组件、在组件间跳转并传递参数、支持嵌套路由与动态路由，是 React 生态最主流的路由方案。

### 3.2 V5 vs V6 关键差异

**Router 种类**：

| Router | 用途 |
| ---- | ---- |
| `BrowserRouter` | History 模式、URL 干净、需服务端配合 |
| `HashRouter` | 兼容最好、无需服务端配置 |
| `MemoryRouter` | 路由保存在内存、适合 React Native |
| `NativeRouter` | 配合 React Native |
| `StaticRouter` | 服务端渲染 SSR |

| 维度 | V5 | V6 |
| ---- | ---- | ---- |
| 匹配顺序 | `<Switch>` 需手动排序（否则 `/product/new` 会先匹配到 `/product/:id`） | `<Routes>` 按路径优先级自动选最具体匹配、定义顺序无关 |
| 路由组件 props | 自动注入 `history`/`location`/`match` 三个固定属性 | 不再自动注入，改用 `useParams`/`useLocation`/`useNavigate` 等 Hook |
| Route 写法 | `component={X}` | `element={<X />}` |

### 3.3 传参三种方式

```
params 传参   参数拼进 URL 路径，须在 Route 声明 :id/:title
              V5 用 props.match.params 读取、V6 用 useParams
search 传参   参数拼在 URL 查询串（?id=1&title=x），无需在 Route 声明
              V6 用 useSearchParams（用法类似 useState）
state 传参    参数放在 state 对象里、不在 URL 上体现，同样无需声明
              V6 用 useLocation 读取 location.state
```

- **V6 携带方式**：`Link`/`Navigate` 组件与 `useNavigate` 钩子都可通过 `to` 对象或参数携带 state。

### 3.4 编程式导航

- **V5 方式**：`history.push` 压入新记录可返回、`replace` 替换当前记录不新增历史；`goBack`/`goForward`/`go(n)` 回退、前进、跳转 n 步。
- **V6 统一 useNavigate**：`const nav = useNavigate()`，支持字符串路径或 `{ pathname, search, state }` 对象，适合"点击后先处理再跳转"的场景。
- **声明式导航**：`Link` 相当于 `a` 标签；`NavLink` 是升级版、带 active 激活状态（可指定激活类名），常用于导航栏高亮当前菜单。

### 3.5 路由守卫

- **无内建守卫**：React Router 没有像 Vue Router 那样的内置守卫钩子，用"条件渲染 + 高阶组件或自定义 Hook"实现权限校验。
- **RequireAuth 模式**：封装守卫组件，未登录则 `navigate('/login', { replace: true })` 重定向并返回 null，已登录才渲染 children；受保护页面用 `<RequireAuth>` 包裹。
- **工程要点**：守卫产物是"跳转逻辑 + 条件渲染"、可抽成独立 Hook（如 `useNavPage`）复用；守卫逻辑收敛到路由配置层、避免业务组件各写各的。

### 3.6 懒加载与代码分割

- **React.lazy + Suspense**：`lazy(() => import('./pages/Home'))` 动态 import 返回组件，构建工具会将其拆分成独立 chunk。
- **Suspense fallback**：chunk 未加载完成时显示兜底内容（如 loading 态）。
- **收益**：按路由拆包、按需加载，首屏只加载真正访问到的页面、减小首屏体积。

## 4. React 状态管理

### 4.1 为何需要状态管理

- **状态提升的局限**：页面拆成多个 UI 组件后数据保存在顶级组件、靠 props 层层传递，页面越复杂传递链越长、中途组件被迫"接盘"自己不关心的数据，同级或深层组件读写别扭，跨页面共享数据（如登录用户信息）根本无法实现。
- **状态管理的定义**：把数据放到一个集中的第三方 Store（单一数据源），任何组件都能读取与更新，且保持数据流清晰可控。
- **常见方案**：React 自带的 Context、useReducer，第三方库 Redux、MobX、Zustand。

### 4.2 Context

- **createContext 与 Provider 注入**：`createContext` 创建 context 对象，在组件上方用 `Context.Provider value={...}` 指定注入的值。
- **useContext 读取**：深层组件通过 `useContext(Context)` 拿到注入的值，中间组件完全不需要知道数据存在、体现跨层级优势（类似 Vue 的 provide/inject）。
- **适用边界**：适合主题、语言这类"低频、全局"的数据；数据更新会让所有消费该 context 的组件重渲染，因此不适合频繁变化的大数据，也不具备跨模块的组织能力。

### 4.3 useReducer

- **定位**：useState 的代替方案（数据结构较复杂时考虑）、参考 Redux 设计的"简化版 Redux"。
- **四个核心概念**：`state` 存储数据、`action` 动作（`{ type: 'xxx', ... }`）、`reducer` 根据 action 生成新 state（不可变、必须返回新对象）、`dispatch` 触发 action（唯一更新 state 的方式）。
- **局限**：state 与 dispatch 没有模块化、数据混在一起难以组织；需结合 useContext 才能跨组件通信；但简单项目用它处理复杂一点的组件状态完全够用。

### 4.4 Redux

**核心概念与单向数据流**：把 useReducer 的 state/action/reducer/dispatch 思想推广到全局。

```
组件 dispatch(action) → store 把 state 与 action 交给对应 reducer 算新 state
      → 新 state 派发给订阅组件重渲染
```

- **相对 useReducer 的增强**：store 可拆分模块、不同领域数据各自独立；通过 Hook（`useSelector`/`useDispatch`）在任意组件取用；Redux DevTools 可回放每一步 dispatch、时间旅行式调试。
- **核心组成**：Action 是描述"发生了什么事"的普通对象；Reducer 是返回新 state 的纯函数（绝不能 `push`、`arr[i] = x`，必须构造新对象/数组）；Store 用 `configureStore`（RTK）或 `createStore` 创建、支持中间件处理异步。
- **RTK 与 TS 结合**：`configureStore` 组合模块化 reducer，`createSlice` + `PayloadAction` 自动生成 reducer 与 action、配合 TS 样板更少。
- **实战**：用 Redux 管理用户信息——创建 store/reducer 收敛读写、对外封装 `useGetUserInfo`/`useLoadUserData` Hook、组件消费、与路由权限联动（呼应路由守卫）。

### 4.5 MobX 与 Zustand

- **MobX 理念**：声明式直接修改数据、像 Vue，不需要像 React + Redux 那样用纯函数和不可变值。
- **MobX 三要素**：`state` 数据（可观察对象）、`action` 动作（允许 `arr.push` 这种直接修改）、`derivation` 派生（`computed` 根据 state 算派生值、`observer` 包裹组件使 state 变了自动重渲染、`autorun` 监听变化执行副作用类似 Vue 的 watch）。
- **MobX 使用建议**：`makeAutoObservable` 自动标记可观察（v6 默认去掉装饰器语法）；需要基于 state 生成值时总用 `computed`、computed 必须纯函数且惰性求值缓存。
- **Zustand**：极简 API——`create` 直接创建 store 并返回一个 Hook；无需 Provider 包裹、自带订阅机制；支持选择器避免多余重渲染、天然契合并发特性；适合中小型项目。

### 4.6 选型

| 方案 | 适用 | 特点 |
| ---- | ---- | ---- |
| Context | 低频全局少量数据 | 内置无依赖但高频更新性能差 |
| useReducer + Context | 组件内状态复杂 | 无依赖但不支持模块化 |
| Redux | 大型复杂应用 | 生态成熟、DevTools 强大、样板多 |
| MobX | 偏好声明式、像 Vue 直接改数据 | 上手快但约束少 |
| Zustand | 中小项目轻量少样板 | API 极简、体积小、性能好 |

- **选型建议**：简单页面优先 useState/Context；共享复杂业务状态考虑 Redux（规范可预测）或 Zustand（轻量）；喜欢 Vue 式响应式体验选 MobX。
- **不变原则**：无论哪种都要牢记不可变数据与单一数据源（Single Source of Truth）。

## 5. React 使用 TS

### 5.1 组件类型定义

- **函数组件为基准写法**：输入 props、返回一段 JSX；组件标签首字母必须大写以与原生 HTML 标签区分。
- **props 类型两种写法**：直接给函数参数标注 props 类型，或用 `FC<IProps>` 泛型（自动补全 props、children 等类型，社区主流写法）。
- **泛型组件**：`function FunctionTs<P>(props: P)` 声明，props 类型由调用方传入。

### 5.2 事件与 ref 泛型

- **事件对象类型**：命名规律是"场景名 + `Event<T>`"（`ChangeEvent`、`MouseEvent`、`KeyboardEvent`、`FormEvent`、`DragEvent`、`TouchEvent`），泛型参数传绑定事件的标签元素类型，它决定 `event.target` 能取到什么。
- **事件处理函数类型**：`ChangeEventHandler<T>`、`MouseEventHandler<T>` 等 `*EventHandler<T>` 系列，同样传入元素类型（如 `React.ChangeEventHandler<HTMLInputElement>`）。
- **ref 类型**：`useRef<HTMLInputElement>(null)`，泛型参数为目标标签元素类型，`current` 可能是 `null`，取值时需判空。
- **标签元素与属性类型**：命名规律是 `HTML` + 标签名 + `Element` / `Attributes`（`HTMLDivElement`、`HTMLInputElement`、`ButtonHTMLAttributes<T>`）；透传原生属性时与自定义 props 交叉组合。

### 5.3 泛型组件与 hooks 泛型

**泛型组件与 .tsx 歧义**：

```
function FunctionTs<P>(props: P) 声明，props 类型由调用方传入
  （<FunctionTs<IProps> name='well' />）
.tsx 的解析歧义   箭头函数泛型 <P extends any> 可能与 JSX 标签解析歧义而报错，
                  定义泛型组件推荐用 function 声明
```

**hooks 泛型**：

```
useState<number>(0)                                   数值状态
useRef<HTMLInputElement>(null)                        DOM ref
useContext<MyCtxType>(MyContext)                      context 值
useReducer<MyReducer, MyState>(reducer, initState)    reducer
```

- **自定义 hooks 的类型处理**：入参与返回值各定义一个类型并随 hook 一起导出，调用方解构出来的值因此都有确定类型。

### 5.4 type vs interface

- **差异在扩展方式**：`interface` 支持声明合并与 `extends`，适合描述对象结构与对外暴露的类型；`type` 支持联合、交叉、条件类型，适合做组合与工具类型。
- **"类型即文档"**：结合 TS 的编译期检查，传错形状的错误在编译期就被拦住。

## 6. React 使用 CSS

### 6.1 普通 CSS

- **内联 style**：必须是 JS 对象形式（不能是字符串），属性名用驼峰写法（如 `fontSize`）。
- **className**：与 HTML 的 class 作用一致，因与 JS 的 class 关键字重复而改名；动态拼接用 `classnames` 或 `clsx`，支持对象/数组多种写法、可读性好（对比手动拼字符串）。
- **尽量少用内联 style**：代码量大、性能较差、不利于复用；用 className 外链样式可复用、性能更好。

### 6.2 CSS Module

- **解决的问题**：组件化开发下多个 CSS 文件容易类名重复、互相覆盖、难以管理。
- **原理**：`xxx.module.css` 把每个 CSS 文件当作独立模块，`className` 自动加不重复后缀实现隔离，CRA 原生支持。
- **结合 classnames**：先取出模块化后的类名再用 classnames 组合，利用对象字面量中括号取值特性（`styles['list-item']`）。
- **使用 Sass**：CSS 写法较原始可用 Sass/Less 增强能力，CRA 支持 Sass Module（`.module.scss`）。

### 6.3 CSS-in-JS

- **是什么**：一种解决方案（不是某个工具的名字），在 JS（组件代码）中写 CSS，不用担心类名重名、动态样式更灵活。
- **关键认知**：不是内联 style——会经过工具编译处理、最终生成真实的 CSS class 形式。
- **styled-components**：代表实现，通过带样式的标签模板字符串快速创建组件（`styled.button<Props>`），支持 props 动态样式。
- **styled-jsx**：另一种方案（Next.js 内置），用 `<style jsx>` 包裹样式、默认作用域局部。

### 6.4 Tailwind

- **Utility-first 原子化**：把常用 CSS 样式细分成一个个小工具类，开发者自由组合搭配。
- **用法**：无需编写大量 CSS，直接用 `text-3xl font-bold` 这类工具类堆叠样式。
- **定位**：适合追求开发效率、风格统一的场景。

### 6.5 选型

| 方案 | 隔离 | 特点与适用 |
| ---- | ---- | ---- |
| 普通 CSS + className | 无类名隔离 | 动态需配合 classnames、学习成本低、适合小项目与全局样式 |
| CSS Module | 自动加后缀隔离 | 适合 CRA 与中大型项目 |
| CSS-in-JS | 编译为 class | 动态样式强、适合高度动态样式与组件库 |
| Tailwind | 工具类灵活组合 | 适合追求效率与风格统一 |

**选型建议**：小项目普通 CSS + className；中大型要隔离用 CSS Module；高度动态用 CSS-in-JS；追求效率统一用 Tailwind。
