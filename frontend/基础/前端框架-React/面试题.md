## 一、基础概念

### Q1: JSX 的本质是什么？

- **结论**：JSX 是 `React.createElement` 的语法糖，产出 React 元素（描述 UI 的普通对象）。
- **原理**：`<div className="x">hi</div>` 编译为 `createElement('div', { className: 'x' }, 'hi')` → `{ type, props, children }`；组件首字母必须大写，因 `type` 需指到函数/类。
- **边界**：JSX 是表达式而非模板字符串、不执行任意代码，注入安全由默认转义保证；`if/for` 不能直接写进 `{}`，要用 `&&`/三元/`map`。

### Q2: 为什么函数组件 + Hooks 成为默认写法？

- **结论**：函数组件是"props 进、JSX 出"的纯函数，配 Hooks 管理状态与副作用，按功能而非生命周期组织代码、逻辑复用内置。
- **原理**：函数组件每次渲染重新调用，状态由 Hooks 按调用顺序存取；`useEffect` 按依赖组织副作用，多份副作用各自独立声明；逻辑抽自定义 Hook 复用，避免 HOC 的嵌套地狱与 props 透传。
- **边界**：类组件有 `this` 绑定与 `constructor` 样板；错误边界（Error Boundary）目前仍需类组件或 `react-error-boundary` 封装。

### Q3: props 与 state 的区别？

- **结论**：props 是父传子的外部只读数据，state 是组件内部可变状态；两者任一变化都会触发重渲染。
- **原理**：props 单向数据流、子组件修改无效；state 由 `useState` 管理、setState 触发重渲染并产出新快照；props 变化重新计算派生值用"渲染期间计算"而非 effect 里 setState。
- **边界**：兄弟共享数据靠"状态提升"到公共父组件；props 是引用，父级应不可变更新，否则子组件看不到变化。

### Q4: 受控组件与非受控组件怎么选？

- **结论**：受控组件值由 state 持有（value + onChange）、非受控由 DOM 持有（ref 读取）；需要校验/联动用受控。
- **原理**：受控把 DOM 输入"提升"进 React 状态、单向数据流闭环；非受控用 `defaultValue` + ref、DOM 是唯一事实源。
- **边界**：受控每个输入都触发重渲染，大表单需收敛受控字段；非受控无法实时校验；`indeterminate` 中间态 checkbox 只能非受控实现。

### Q5: `key` 的作用是什么？为什么别用 index？

- **结论**：`key` 是节点身份标识，让 diff 走"移动"而非"删除重建"；用稳定唯一 id，别用 index。
- **原理**：diff 在同层按 key 匹配节点；中间插入/删除时 index 会让后续节点错位复用，输入框状态、动画被错误迁移。
- **边界**：key 只在兄弟间唯一即可；数组重排（拖拽排序）更依赖 key 正确，否则整列状态错乱。

### Q6: React 19 有哪些新特性？

- **结论**：Actions（表单动作）、`use()`（读资源）、React Compiler（自动记忆化）。
- **原理**：Actions 让表单提交自动管理 pending/error 状态；`use()` 可在条件中调用、配合 Suspense 读异步资源；编译器自动 memo，替代手写 useMemo/useCallback。
- **边界**：新特性需配套生态（Router 7 / antd 兼容版本）；React Compiler 减少"该不该 memo"的心智负担。

## 二、机制与原理

### Q7: 虚拟 DOM 与 diff 机制是什么？

- **结论**：虚拟 DOM 是 UI 的 JS 描述，diff 对比新旧元素树、只做最小的真实 DOM 变更。
- **原理**：同层 diff（不跨层比较）、`key` 识别节点身份、`type` 不同直接重建子树、props 变化只更新属性。
- **边界**：diff 只是策略——大列表仍需虚拟滚动/memo；"虚拟 DOM 快"的说法不准，快的其实是声明式编程模型下的可控更新范围。

### Q8: React 渲染流程 render → reconcile → commit？

- **结论**：render 生成新元素树 → reconcile 对比找差异 → commit 把差异同步到 DOM 并执行副作用。
- **原理**：render 是纯计算、可中断；reconcile 产出变更清单（workInProgress）；commit 一次性同步提交、不可中断，并触发 `useEffect`。
- **边界**：render 阶段禁止副作用（会被多次调用）；commit 同步会卡主线程，故引入并发特性调度。

### Q9: Fiber 为什么能实现可中断渲染？

- **结论**：Fiber 是"工作单元"链表结构，把渲染拆成可中断的小任务，支撑并发调度。
- **原理**：每个组件对应一个 Fiber 节点组成树；渲染在空闲时间片分片推进（时间切片），高优先级更新（输入）可打断低优先级（列表）。
- **边界**：中断只发生在 render/reconcile 阶段、commit 仍同步；旧架构递归渲染整树不可中断，一帧做不完就掉帧。

### Q10: Hooks 的规则有哪些？为什么不能条件调用？

- **结论**：Hooks 只在顶层调用、只在组件/自定义 Hook 内调用；按调用顺序存储状态。
- **原理**：React 用链表按顺序保存每个 hook 的 state；条件/循环调用会让顺序错位，两次渲染读到的不是同一个 hook。
- **边界**：依赖数组需稳定引用，闭包陷阱见 Q14；setter 是稳定引用，写进依赖不会触发重复执行。

### Q11: `useEffect` 与 `useLayoutEffect` 的区别？

- **结论**：`useEffect` 在绘制后异步执行，`useLayoutEffect` 在绘制前同步执行；多数场景用前者。
- **原理**：`useLayoutEffect` 在 paint 前同步跑，适合测量 DOM 并避免闪烁；`useEffect` 不阻塞渲染。
- **边界**：需同步读布局再改 UI 才用 `useLayoutEffect`，否则 useEffect 会闪一下；它在 SSR 下会警告。

### Q12: 函数组件里"挂载 / 更新 / 卸载"怎么在 `useEffect` 里区分？

- **结论**：`useEffect` 一个 API 覆盖三个时机——依赖数组区分执行时机，返回的清理函数处理卸载。
- **原理**：`[]` 只在挂载执行一次、`[count]` 挂载加 count 变化时执行、不传则每次渲染后执行；清理函数在下一次执行前与卸载时各跑一次，防止订阅/定时器泄漏。
- **边界**：React 18 开发环境 effect 执行两次，用于暴露订阅重复绑定等问题、生产不执行两次。

## 三、渲染性能与状态

### Q13: 渲染性能三板斧——`startTransition`、懒加载、`memo`？

- **结论**：`startTransition` 降级非紧急更新、`React.lazy`+`Suspense` 按需拆包、`memo`/`useMemo` 控制重渲染范围。
- **原理**：`startTransition` 标记的更新可被紧急更新打断；懒加载把大 chunk 拆到路由级、首屏只加载访问到的页面；`memo` 对 props 浅比较跳过无关子树渲染。
- **边界**：缓存不是越多越好——`useMemo` 本身有开销，仅计算昂贵或引用需稳定时用；`useDeferredValue` 处理"值"（搜索）、`startTransition` 处理"更新"。

### Q14: Hooks 闭包陷阱（stale closure）怎么解决？

- **结论**：回调/effect 捕获旧渲染的 state、读到旧值；用函数式更新或 ref 保存最新值。
- **原理**：每次渲染是独立闭包、state 是不可变常量；依赖不变则回调不重建、内部旧引用不更新。
- **边界**：函数式更新 `setCount(c => c+1)` 解决"基于旧值的更新"；"读取最新值"的场景用 ref（useState 存驱动 UI 的值、ref 存异步闭包读取的最新值）。

### Q15: 状态管理 Context / Redux / Zustand 怎么取舍？

- **结论**：局部状态用 useState；跨层少量共享用 Context；复杂全局状态中小项目用 Zustand、大型用 Redux。
- **原理**：Context 无 selector、值变了订阅者全重渲染，只适合低频全局数据；Redux 单向流 + 中间件 + DevTools 时间旅行、样板多；Zustand 基于外部 store + selector 订阅、最小重渲染、无需 Provider。
- **边界**：state 与派生数据不混——接口缓存等服务端状态用 React Query/SWR 更合适；无论哪种都坚持不可变与单一数据源。

## 四、路由与场景设计

### Q16: 前端路由两种模式 hash 与 history 怎么选？

- **结论**：hash 改 `#` 后不请求服务器、兼容性最好、无需服务端配置；history 用 History API、URL 美观、但刷新时需服务端回落、否则 404。
- **原理**：hash 兼容老浏览器但 URL 带 `#` 不美观；history 基于 `pushState`/`popstate`、需要服务端把所有路径回落到入口页。
- **边界**：生产选 BrowserRouter 需服务端配合；Memory/StaticRouter 分别用于 RN 与 SSR。

### Q17: React Router 的嵌套路由与路由守卫怎么实现？

- **结论**：嵌套路由用 `<Outlet>` 渲染子路由；React Router 无内置守卫，用"条件渲染 + 封装守卫组件"实现权限校验。
- **原理**：守卫组件未登录则 `navigate('/login', { replace: true })` 并返回 null、已登录才渲染 children；被保护页面用守卫组件包裹。
- **边界**：守卫逻辑收敛到路由配置层，可抽成自定义 Hook（如 `useNavPage`）复用。
