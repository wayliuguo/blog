# 小程序双线程架构与渲染机制

小程序与普通 H5 最大的不同是它跑在**双线程架构**里：界面由渲染层的 WebView 画，逻辑由逻辑层的 JS 引擎跑，两层之间通过 Native 层中转通信。理解这套架构，才能解释"为什么 `setData` 那么贵""为什么数据要小""为什么会有 `WXS`"这一串小程序特有的性能问题。

这篇文章按「架构 → 通信 → WXS」的脉络展开。

## 一、双线程架构

小程序的运行环境被拆成两层：

```text
┌─────────────────────────────────────────────┐
│                  逻辑层                        │
│   每个小程序一个 JS 引擎（iOS: JSCore / Android: V8）│
│   负责：数据、业务逻辑、网络请求、生命周期         │
└───────────────────┬─────────────────────────┘
                    │ setData / 事件 经 Native 转发
┌───────────────────▼─────────────────────────┐
│                Native 层（微信客户端）           │
│   统一处理线程间通信、数据传递、网络请求转发        │
└───────────────────┬─────────────────────────┘
                    │ 渲染指令 下发
┌───────────────────▼─────────────────────────┐
│                  渲染层                        │
│   多个 WebView（每个页面一个）负责视图渲染         │
│   只有视图与 WXML/WXSS，没有 DOM 与业务逻辑      │
└─────────────────────────────────────────────┘
```

- **渲染层**：使用 WebView 渲染，小程序有几个页面就有几个 WebView；渲染层里只有视图（WXML / WXSS）与渲染相关的脚本，**不运行业务 JS**，也没有完整的 DOM。
- **逻辑层**：用 JS 引擎（iOS 上是 JavaScriptCore，Android 上是 V8）运行 JS 代码，业务逻辑、数据、网络请求都在这层；逻辑层没有 DOM，不能直接操作视图。
- **Native 层**：两个线程之间的通信、数据传递、网络请求，**统一由 Native 层中转转发**，不直接互相访问。

> 关键结论：小程序里"逻辑"和"视图"是隔离的两个世界，页面想要展示数据，必须走 `setData` 把数据从逻辑层"传"到渲染层——这是一次跨线程通信，不是一次本地赋值。

## 二、双线程之间的通信：setData

### 1. setData 的完整链路

`this.setData({ key: value })` 的执行链路：

```text
逻辑层 setData
  → 把数据序列化（字符串）
  → 经 Native 层转发（进程间通信）
  → 渲染层 WebView 收到，解析反序列化
  → 驱动 WXML 更新对应的节点
```

因为要跨线程，数据要**序列化传输**——所以 `setData` 的开销与**数据量正相关**：塞的数据越大、字段越多，序列化和传输越贵。

### 2. 为什么 setData 会阻塞交互

- 每次 `setData` 都是一次进程间通信过程，通信开销与 `setData` 数据量正相关。
- `setData` 会引发视图层面内容更新（渲染层要重新计算、更新节点），这个更新过程会阻塞用户交互。
- 所以实践上有两条铁律：**不要频繁调用 setData**，**每次 setData 不要塞太多数据**。

典型反例：

```js
// 反例：一次 setData 塞了整个大对象，或循环里反复 setData
for (let i = 0; i < 100; i++) {
  this.setData({ [`item${i}`]: list[i] }) // 100 次跨线程通信
}

// 正确：一次 setData 批量更新，且只传视图要用的字段
this.setData({ list: visibleList })
```

### 3. 减少 setData 的原则

- **只传视图用到的数据**：与渲染无关的数据不要放进 `data`（避免"改了不渲染的数据也要跨线程传一遍"）。
- **合并多次更新**：一次回调里的多次修改合并成一次 `setData`。
- **路径更新**：`this.setData({ 'list[0].name': 'xx' })` 只更新局部，避免整对象重传。

## 三、WXS：让视图层自己算

`WXS`（WeiXin Script）是小程序的一套脚本语言，运行在**渲染层**，语法上接近 ES5 的一个子集。

```html
<wxs module="fmt">
  module.exports = {
    format: function (n) {
      return n.toFixed(2)
    }
  }
</wxs>

<view>{{ fmt.format(price) }}</view>
```

**价值**：某些"展示前的数据加工"（格式化金额、过滤列表）如果写在逻辑层，改一次数据就要跨线程传一次；用 WXS 把计算挪到渲染层本地执行，**避免跨线程开销**，视图渲染不再依赖逻辑层反复 setData。

**边界**：WXS 不支持 ES6+ 语法与部分 API，只适合纯展示计算；业务逻辑、网络请求仍然必须在逻辑层。

## 四、多页面与多 WebView

渲染层每个页面对应一个 WebView，所以：

- 页面切换（`navigateTo`）是**新建 WebView**，不是 DOM 切换——这也是为什么页面栈深度有限制（最多 10 层）、以及 `onHide`/`onUnload` 要主动清理定时器与播放器等资源。
- 多个 WebView 常驻意味着**内存占用随页面栈增长**，长流程页面（列表 → 详情 → 订单）要注意及时 `navigateBack`，避免栈堆深后内存吃紧。

## 总结

- 小程序双线程架构与渲染机制
  - 双线程架构
    - 渲染层 WebView 只负责视图，逻辑层 JS 引擎负责业务
    - 通信/数据/网络请求统一由 Native 层中转
    - 多个页面 = 多个 WebView，页面栈加深内存增长
  - setData 通信
    - setData 是跨线程序列化传输，开销与数据量正相关
    - 会引发视图更新并阻塞交互
    - 原则：少调用、批量更新、只传视图要用的数据、用路径更新
  - WXS
    - 运行在渲染层，做纯展示计算
    - 避免数据加工跨线程传输的开销
    - 不支持 ES6+/部分 API，只适合展示计算
