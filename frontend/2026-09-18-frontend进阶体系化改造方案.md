### 3.1 D1 为什么要把工程化与构建拆开

两者解决的是不同层次的问题，混在一个模块里导致：构建内容被压缩成一节（Vite 870 字符、Rollup 594 字符），工程化内容又只有概念没有落点。

- **前端工程化**：研发流程与协作体系 —— 全景与成熟度、模块化与包管理语义、脚手架、Monorepo、基建串联
- **构建体系**：把源码变成产物的工具链 —— 编译与 AST、打包器、插件机制、产物优化、最小实现

### 3.2 D3 交付与质量的去留判定

| 篇 | 判定 | 理由与处理 |
|---|---|---|
| Git 与协作 (6.8K) | **下沉基础** | 内容是命令速览 / reset-revert / 远程管理 / Gitee 镜像，属工具使用，非进阶能力。移入基础新建模块「工程协作」 |
| 调试技巧 (5.1K) | **重写** | 主体是 VS Code `launch.json` 配置教程。重写为「排障方法论」：DevTools 定位链路 + 线上问题复现与定位 |
| 代码规范 (11.3K) | **重写** | 保留 ESLint/Prettier/husky/commitlint，删除与基础 CSS 重复的 BEM 节，升级为"质量门禁设计"视角 |
| 质量体系与测试 (6.4K) | **保留扩写** | 补视觉回归、契约测试、覆盖率门禁 |
| CI/CD 自动化 (6.2K) | **保留扩写** | 补缓存策略、产物校验、多环境 |
| 发布、灰度与监控 (5.1K) | **拆** | 监控部分并入监控模块，本篇聚焦发布策略 / 灰度 / 回滚 / 发布视角的可观测 |

### 11.3 TypeScript 类型系统：冗余分布错位，需重构

**现状实测**：27.7K 字符，**95 个代码块全部是 `> 示意片段（无配套脚本）`**，而 `TypeScript/code/check.ts` 本就是为该篇准备的类型校验脚本，却一次都没被引用——整篇零可验证内容。

**重构后骨架**（9 节，场景驱动）：

1. 类型系统的心智模型（结构类型 vs 名义类型、类型即集合、可赋值性、鸭子类型）← 新增，最重要
2. TS 相对 JS 多了什么（一张表讲清 `enum`/`tuple`/`never`/`unknown`/`void`/`any`/字面量/联合/交叉）← 压缩原基础类型
3. 类型是怎么推出来的（推断、上下文、`as const`、`satisfies`、收窄）← 扩写
4. 描述结构的两种方式（`interface` vs `type` 给**明确结论**，不是"都行"）
5. 泛型：参数化类型（约束、默认、推断、映射）
6. 类型编程（条件类型、`infer`、模板字面量、递归）
7. 工具类型与它们的实现（逐行实现 `Partial`/`Pick`/`Omit`/`Record`/`ReturnType`/`Awaited`）
8. 类型边界与逃生舱（`any`/`unknown`/`never`、断言、声明合并、`@ts-ignore` 的代价）
9. 类：只讲"作为类型用"

**配套同步**：`code/check.ts` 扩为 `code/type-lab/`（`inference.ts` / `generics.ts` / `conditional.ts` / `utils.ts`），所有代码块摘自脚本并贴 `npx tsc --noEmit xxx.ts` 的**真实报错输出**——把 95 个示意片段变成可验证内容。
