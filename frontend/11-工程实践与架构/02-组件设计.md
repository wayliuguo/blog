# 组件设计

> 级别：高级

组件化是前端工程化的核心命题：它把"界面"拆解成可组合、可复用、可测试的单元。React 与 Vue 都提供了组件的定义、渲染与通信机制，但"能不能把组件写好"取决于设计方法论，而不只是框架 API。本章从设计原则出发，系统讲解组件划分、API 设计、复用手段、跨框架抽象与选型，帮助你在 2 年以上经验水平建立起可落地的组件设计能力。

本章按四层推进：入门（组件设计原则与划分策略）→ 进阶（props 设计、API 演进、复用手段对比）→ 实战（抽象层级与技术选型清单落地）→ 最小实现（用事件中心与单例 store 演示"跨组件通信与状态共享"的最小骨架，对应本节的 Context / 状态库思想）。原理均在章内自足。

---

## 一、组件设计原则

好的组件不是"能用就行"，而是要在生命周期内的每一次变更、每个新需求、每次接手重构中都能保持清晰。以下原则是判断组件设计优劣的度量衡。

### 1.1 单一职责原则（SRP）

一个组件只做一件事，并且把事情做完。判断标准：当你要向别人解释"这个组件是干什么的"时，如果要用到"并且"、"还有"这类连接词，就说明职责过重。

> 反面示例：一个 `UserCard` 同时负责拉取用户数据、渲染信息、点赞、编辑资料、上报埋点。它既是容器又是展示组件，既管数据又管交互，改动任何一个需求都会影响其他功能。

```jsx
// 拆分前的"上帝组件"，职责过多
function UserCard({ userId }) {
  const [user, setUser] = useState(null);
  useEffect(() => { fetchUser(userId).then(setUser); }, [userId]);
  const handleLike = () => api.like(user.id);
  return (
    <div>
      <Avatar url={user.avatar} />
      <p>{user.name}</p>
      <button onClick={handleLike}>点赞</button>
    </div>
  );
}
```

```jsx
// 拆分后：负责"获取数据"与"埋点"的逻辑放到容器层
function UserCardContainer({ userId }) {
  const user = useUser(userId);              // 自定义 hook 承担数据职责
  return <UserCard user={user} />;           // 纯展示组件只负责渲染
}
```

拆分粒度不是越细越好。真正的目标不是"一定拆开"，而是"单个组件的变更原因唯一"。一个组件如果有多个互不相干的改动理由，才需要拆分。

### 1.2 SOLID 在前端的应用

SOLID 是面向对象设计原则，前端虽然通常不使用传统的继承层次，但它背后的思想可以直接迁移到组件与模块层面。

| 原则 | 前端对应实践 |
|------|--------------|
| S 单一职责 | 一个组件 / hook / 模块只承担一种职责 |
| O 开闭原则 | 通过 props / slots 扩展能力，而不是改组件内部源码来加需求 |
| L 里氏替换 | 复合组件 / 接口约定保证子组件可被替换而不破坏父组件逻辑 |
| I 接口隔离 | 不要设计一个大而全的 props 对象，按用途拆分组合 |
| D 依赖倒置 | 组件依赖"数据契约 / 接口"而非具体实现，便于 mock 与替换 |

开闭原则在组件层面最具指导性：**对扩展开放、对修改关闭**。一个成熟的第三方组件库组件，应当允许用户通过自定义渲染（render / slots）、样式覆盖、附加钩子等方式扩展，而不是被迫去改动框架源码。

```jsx
// 开闭原则示例：允许调用方注入自定义渲染，而不是写死在组件内
function Tooltip({ content, renderContent }) {
  return (
    <div className="tooltip">
      {renderContent ? renderContent(content) : <span>{content}</span>}
    </div>
  );
}
```

### 1.3 可复用性与可维护性

这是两个需要平衡的目标：

- **可维护性**：组件容易被读懂、被修改、被测试、被信任。追求的是"低耦合、内聚清晰、变更影响范围小"。
- **可复用性**：组件能被多次、跨项目复用。适度抽象能提升复用，但过度抽象会牺牲可读性与可维护性。

**著名的"复用诅咒"**：为了"预判未来"而抽象出来的组件，往往和实际需求对不上，最终既不能复用，又增加了维护负担。更稳妥的做法是 **"三次法则"（Rule of Three）**：同一个逻辑出现第一次先写在原地，第二次出现再抽出来，第三次出现时才真正抽象成可复用单元。

```js
// 第一次：以内联方式书写，不急着抽象
// 第二次：抽成函数
// 第三次：封装成 hook / 组件库成员并补充文档与测试
```

**可维护性的可观测信号**：

- 一个组件文件超过 300 行是否可控？很大程度取决于职责是否单一。
- 修改一个需求，是否需要同时改动多个无关组件？
- 新同事能否在不读源码、只看 props 文档的情况下正确使用该组件？

## 二、组件划分策略

### 2.1 原子设计（Atomic Design）

由 Brad Frost 提出，把界面拆成五个层级：

```
atoms（原子）→ molecules（分子）→ organisms（有机体）→ templates（模板）→ pages（页面）
```

| 层级 | 含义 | 示例 | 说明 |
|------|------|------|------|
| 原子 | 不可拆分的元素 | Button、Input、Icon | 只负责基本渲染，不携带业务 |
| 分子 | 原子组合 | SearchBar（Input + Button） | 有明确交互意图的小单元 |
| 有机体 | 分子组合成区块 | Header、CardList | 开始出现数据驱动 |
| 模板 | 布局结构 | 详情页框架 | 只定结构，不定具体数据 |
| 页面 | 模板实例 | 用户管理页 | 填充真实数据与业务 |

原子设计最大的价值是**提供了一种团队统一的命名与分工语言**：设计师、前端、产品都能用同一套词汇对齐。但它也容易陷入"为了拆分而拆分"，建议只在真正有复用诉求处坚持原子化。

### 2.2 容器组件 vs 展示组件

- **容器组件（Container / Smart）**：负责数据获取、状态管理、业务逻辑与埋点，通常没有或少有样式，往往对应一个页面或区块。
- **展示组件（Presentational / Dumb）**：只负责接收 props 并渲染，不关心数据从哪来，可随意替换与复用。

这种划分的价值在于**关心点分离**：展示组件可在无后端接入的情况下开发与测试（通过传入静态 props），容器组件则专注数据流。

```jsx
// 展示组件：纯函数，不关心数据来源
function TodoList({ todos, onToggle }) {
  return (
    <ul>
      {todos.map((t) => (
        <li key={t.id} onClick={() => onToggle(t.id)}>{t.text}</li>
      ))}
    </ul>
  );
}

// 容器组件：负责数据与状态
function TodosPage() {
  const [todos, setTodos] = useTodoStore();   // 状态管理
  const handleToggle = (id) => setTodos(toggleTodo(id));
  return <TodoList todos={todos} onToggle={handleToggle} />;
}
```

在前端状态管理（Redux / Pinia / React Query 等）出现之后，"容器"的职责进一步被数据 hooks 与数据层消化，展示组件可以通过自定义 hook 保持简洁。

### 2.3 受控组件 vs 非受控组件

指南针式的经典概念：**数据由谁拥有关键。**

- **非受控（Uncontrolled）**：组件内部自己维护状态，父组件不介入值的读写，只在需要时通过 `ref` 读取。
- **受控（Controlled）**：值由父组件通过 props 提供，变化通过事件回调反馈给父组件，组件本身不持有状态。

```jsx
// 非受控：用户输入由组件内部 state 管理
function UncontrolledInput() {
  return <input defaultValue="init" />;
}

// 受控：值来自 props，通过 onChange 上抛
function ControlledInput({ value, onChange }) {
  return <input value={value} onChange={(e) => onChange(e.target.value)} />;
}
```

两者的取舍：

- 组件要做成可被外部验证、重置、与其他组件联动 → 用受控。
- 组件本地自洽、父组件不关心具体值 → 用非受控，简化父组件代码。
- 业界成熟方案是**同时支持两者**：未传 `value` 时内部自管（非受控），传了则走受控路径。这是 Ant Design、arco-design 等大量组件库的实际做法。

```js
// 可切换受控/非受控的典型实现思路（以 React 为例）
function useControlled({ controlledValue, defaultValue }) {
  const { current: isControlled } = useRef(controlledValue !== undefined);
  const [value, setValue] = useState(defaultValue);
  return [
    isControlled ? controlledValue : value,
    setValue,
  ];
}
```

## 三、props 设计

props 是组件的公共 API，其设计质量直接决定组件的可用性。

### 3.1 props 设计要点

- **收窄职责**：props 只暴露与组件职责相关的属性，不要把业务数据大对象整个塞进去，宁可传明确的字段。
- **合理默认值**：可选 props 必须有语义明确的默认值，且必须说明默认值的含义。
- **单向数据流**：数据从父到子单向流动，子组件只读，如需改变需通过回调由父组件完成。
- **类型约束与文档**：TS 泛型 + props 类型定义 + 注释，让调用方在 IDE 里就能看清每个属性的用途、类型与默认值。

```ts
// props 类型约束：类型即文档（React 示例）
interface ButtonProps {
  /** 按钮语义变体 */
  type?: 'primary' | 'default' | 'danger';
  /** 是否禁用 */
  disabled?: boolean;
  /** 点击回调 */
  onClick?: (e: MouseEvent) => void;
  /** 前置图标 */
  icon?: React.ReactNode;
}
```

```ts
// Vue 3 的 props 定义也自带类型与校验
defineProps<{
  type?: 'primary' | 'default' | 'danger'
  disabled?: boolean
}>()
```

### 3.2 事件通信

"子传父"在 React 中用**回调 props**，在 Vue 中用 **emits**。

```jsx
// React：事件即回调 prop
<Modal visible={open} onClose={() => setOpen(false)} />
```

```vue
<!-- Vue：使用 emits 声明事件，便于可读与文档化 -->
<script setup lang="ts">
const emit = defineEmits<{ close: [void] }>()
</script>
```

深层的、跨多层的通信不建议层层透传，后面会用 Context / provide-inject / 状态库解决。事件命名保持简洁一致：统一动词如 `onChange` / `onSelect` / `onSubmit`，复数的回调总是以 `on` 开头，这是 React 生态约定。

### 3.3 组合 vs 继承

**组合优于继承**是前端组件设计的铁律。继承会形成脆弱的基类层级，难以理解和维护；组合则通过 props 传子组件、插槽、children、自定义渲染实现灵活装配。

```jsx
// 组合：子组件作为 children 注入
function Layout({ header, sidebar, children }) {
  return (
    <div className="layout">
      <header>{header}</header>
      <aside>{sidebar}</aside>
      <main>{children}</main>
    </div>
  );
}

<Layout header={<Header />} sidebar={<Sidebar />}>
  <Content />
</Layout>
```

```vue
<!-- Vue 组合：借助 slot 分发 -->
<Layout>
  <template #header><Header /></template>
  <template #sidebar><Sidebar /></template>
  <Content />
</Layout>
```

业务逻辑层面同理：要复用一段带状态的逻辑，React 用自定义 Hook，Vue 用组合式函数（Composable），而不是把逻辑塞进父类继承。

## 四、组件 API 设计

组件 API 是开发者的"用户体验"，好的 API 应该在语义、默认值与演化上都很友好。

### 4.1 语义化命名

- 组件名用大驼峰，用途明确的单词组合，如 `DateRangePicker` 而非 `DRP`。
- props 名尽量选用框架社区通用语义：`value`、`onChange`、`placeholder`、`disabled`、`size`、`variant`。
- 字段避免含糊命名如 `flag`、`data`、`obj`。

```jsx
// 反例：语义模糊
<Switch flag={true} opt="123" />

// 正例：语义清晰、遵循社区约定
<Switch checked={checked} size="small" onChange={setChecked} />
```

### 4.2 默认值策略

- 所有可选 props 都应提供安全、合理的默认值，避免调用方漏传导致崩溃或行为异常。
- 默认值要符合直觉：例如 `Button` 的 `type` 默认 `default`，App 级主题通过全局配置覆盖。
- 慎重使用默认值掩盖缺陷——如果一个功能必须有值才能正确，宁可设为必填并让 TS 报错，而不是悄悄给一个"假默认值"。

```jsx
// 默认值收敛到一个常量对象，便于统一维护（React 默认参数方式）
function Button({
  type = 'default',
  size = 'middle',
  disabled = false,
  children,
}) { /* ... */ }
```

### 4.3 向前兼容（API 演进）

当组件面向真实用户（尤其是组件库）时，破坏性变更代价极高。原则：

- **新增属性用可选 + 默认关闭**，不要"默认开启新行为"，避免老调用方行为突变。
- **弃用先标记（deprecated）**，保留旧写法 N 个大版本再移除。
- **用邮政语义版本（semver）**约束：`major` 允许破坏性变更，`minor` 向后兼容新增，`patch` 修 bug。
- 对外文档与 `CHANGELOG` 清楚记录每个版本的破坏点与迁移路径。

一个典型做法：新增特性通过 `variant` 或 `props` 提供，老用法行为完全不变，仅在文档提示已弃用，交由调用方按节奏迁移。

## 五、组件复用手段

同一段"界面 + 逻辑"，在不同框架 / 时代有不同的复用载体。理解它们的演进与取舍，能帮你在合适场景用对工具。

### 5.1 HOC（高阶组件）

HOC 是一个函数，接收一个组件、返回一个增强后的组件，本质是"包装"。

```jsx
// 一个给组件注入 loading 能力的 HOC
function withLoading(Wrapped) {
  return function Enhanced({ loading, ...rest }) {
    if (loading) return <Spinner />;
    return <Wrapped {...rest} />;
  };
}

const UserPanelWithLoading = withLoading(UserPanel);
```

**优点**：历史悠久、复用方便。**缺点**：props 来源混乱（不知道某个 props 来自哪层）、多次包装形成"包装地狱"、类型到 TS 里会变得复杂、难以在逻辑层复用（只能包装组件）。HOC 在 React 类组件时代是主流，如今更推荐 Hook。

### 5.2 Render Props

一个组件接收一个"返回 JSX / VNode"的 `render` 函数或 `children` 函数，把内部状态透传给调用方去渲染。

```jsx
function Mouse({ render }) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  // 监听 mouse move 更新 pos...
  return render(pos);
}

<Mouse render={(pos) => <Cir cursorPosition={pos} />} />
```

**优点**：数据来源清晰、类型更好。**缺点**：多层 render prop 嵌套会导致回调地狱式的复杂度；React 函数组件 + hooks 出现后，多数场景已被自定义 hook 替代。

### 5.3 Hooks / 组合式

当今前端复用的**首选载体**：把"有状态逻辑"抽成独立函数，不依赖 UI 结构，可自由组合，可测试。

```jsx
// React：自定义 Hook 承载有状态逻辑
function useOnlineStatus() {
  const [isOnline, setIsOnline] = useState(navigator.onLine);
  useEffect(() => {
    const handler = () => setIsOnline(navigator.onLine);
    window.addEventListener('online', handler);
    window.addEventListener('offline', handler);
    return () => {
      window.removeEventListener('online', handler);
      window.removeEventListener('offline', handler);
    };
  }, []);
  return isOnline;
}

function Status() {
  const online = useOnlineStatus();
  return <div>{online ? '在线' : '离线'}</div>;
}
```

```ts
// Vue：组合式函数（Composable），逻辑与 UI 彻底解耦
export function useOnlineStatus() {
  const isOnline = ref(navigator.onLine)
  const update = () => { isOnline.value = navigator.onLine }
  onMounted(() => {
    window.addEventListener('online', update)
    window.addEventListener('offline', update)
  })
  onBeforeUnmount(() => {
    window.removeEventListener('online', update)
    window.removeEventListener('offline', update)
  })
  return { isOnline }
}
```

**对比小结**：

| 手段 | 复用单元 | 是否耦合 UI | 适合场景 |
|------|---------|-------------|----------|
| HOC | 组件包装 | 是 | 透传式增强、老代码迁移 |
| Render Props | 渲染函数 | 是 | 需要把状态暴露给渲染 |
| Hooks / Composable | 逻辑函数 | 否 | 有状态逻辑复用的首选 |
| 组合/插槽 | 子组件 | 否 | 布局、可定制内容区域 |

## 六、跨框架 / 跨端组件与技术选型

### 6.1 跨框架的动因与现状

团队内部往往并存 React 与 Vue，或者历史原因存在多套框架；再加上小程序、RN、移动 H5 等多端诉求，"写一份、处处跑"极具吸引力。跨框架方案通常从"渲染层解耦"入手：

- **无框架底层 + 各自适配层**：核心逻辑用原生 JS / 自定义 renderer 实现，React / Vue 各写一个薄薄的壳组件调用它。
- **Web Components**：用标准的 Custom Elements 定义，任何框架都能通过普通 DOM 标签使用（React 19 / Vue 对自定义元素的互操作已日趋成熟）。适合降级互操作，但对框架内状态管理、事件绑定仍是约束。

```html
<!-- Web Components：独立于框架的封装 -->
<my-dialog open></my-dialog>
```

- **JSDK / 头less（headless）模式**：组件拆成"无样式逻辑核心" + "框架绑定层"，如 TanStack（React/Vue/Solid 各一套名下的 headless 库）。
- **统一运行时**：如 Solid、Svelte 通过编译期优化实现跨语言（但仍是各自框架），并非真正的跨框架复用。

### 6.2 框架无关 vs 框架先行的权衡

| 维度 | 跨框架封装 | 框架原生组件 |
|------|-----------|--------------|
| 复用范围 | 一套逻辑服务多框架/多端 | 局限于当前框架内 |
| 性能 | 多一层抽象，可能有运行时开销 | 最少间接层，性能最优 |
| 开发体验 | 需维护多套适配层与文档 | 直接使用框架能力，体验最顺 |
| 适配成本 | 高（维护成本、调试成本） | 低 |

**决策建议**：如果只有单一框架，不跨框架也不跨端，优先框架原生组件，不要为"理论上可能复用"而引入抽象层。"跨端复用"要评估各端（Web/H5/小程序/RN）的渲染能力差异——真正能跨端的往往是**业务领域层逻辑**（数据、状态、规则）而非 UI 层。

### 6.3 组件技术选型清单

选型成熟组件库时，建议从这些维度评估：

1. **功能覆盖**：是否满足产品需要的组件（表单、表格、弹层、日期、上传等）。
2. **质量与定制能力**：设计规范是否完善、支持主题定制/样式覆盖程度。
3. **可维护性与社区活跃度**：维护频率、issue 反馈速度、周边生态。
4. **兼容性**：浏览器目标、React/Vue 版本、SSR 支持。
5. **体积与性能**：按需加载（tree-shaking / babel-plugin-import）能力。
6. **许可证与可持续性**：开源许可、背后的公司或作者、长期维护承诺。

> 常用参照：React 生态 Ant Design、Arco Design、MUI、Headless UI、Radix；Vue 生态 Element Plus、Arco Design Vue、Naive UI、Varlet。

## 七、抽象层级

从"基础可复用单元"到"完整业务系统"，优秀的前端项目会在不同抽象层级上设计，每层解决不同问题。理解这些层级，是架构设计的关键。

### 7.1 复合组件（Compound Components）

**复合组件**是一个"家族"组件：父组件提供上下文，多个子组件共享该上下文，从而自由排列布局。

```jsx
// React Context 实现复合组件
const TabsContext = createContext(null);

function Tabs({ defaultValue }) {
  const [value, setValue] = useState(defaultValue);
  const tabsCtx = { value, setValue };
  return (
    <TabsContext.Provider value={tabsCtx}>
      {children}
    </TabsContext.Provider>
  );
}

function TabList({ children }) { return <div role="tablist">{children}</div>; }
function Tab({ value, children }) {
  const { value: current, setValue } = useContext(TabsContext);
  return (
    <button role="tab" aria-selected={value === current}
            onClick={() => setValue(value)}>{children}</button>
  );
}
```

```vue
<!-- Vue 复合组件：借助 provide / inject 共享上下文 -->
<script setup lang="ts">
const tabs = ref(null)
provide('tabsCtx', { value: tabs })
</script>
```

**价值**：允许调用方自定义嵌套顺序与布局，而内部状态仍由父组件统一管理。React 的 `<Select></Select>` 复合组件、Vue 的 `ElTabs/ElTabPane` 都是典型代表。

### 7.2 高阶抽象：render engine / 配置化渲染

当组件数量与页面结构重复度极高的场景（如低代码、表单引擎、可视化搭建），可引入**配置化渲染**或**数据驱动的渲染引擎**：用一个 schema 描述组件树与 props，由运行时统一渲染。

```ts
// 简单 schema 驱动渲染（React 示例）
const pageSchema = [
  { type: 'input', props: { label: '姓名', name: 'name' } },
  { type: 'select', props: { label: '城市', name: 'city', options: [] } },
  { type: 'button', props: { children: '提交' } },
];

function SchemaRenderer({ schema }) {
  return schema.map((node) => componentMap[node.type]({ ...node.props }));
}
```

**价值**：界面结构数据化，可实现配置化、可持久化、可校验。**代价**：过于灵活导致性能与调试成本上升、类型安全保障更难，仅在确有动态渲染/低代码诉求时引入。

### 7.3 头部库模式（Header-driven Library）

**头部（headless）库**指把"行为与状态逻辑"与样式彻底分离的组件库。这类库通常提供可复用的逻辑/hooks（如 `useTab`、`useAccordion`）以及无样式的结构组件，样式完全由使用方决定，常见的前后端领域通常配合 CSS 方案（Tailwind、CSS Module 等）落地。

```jsx
// headless 思路：组件只负责行为，类名与样式交给使用方
function Tab({ selected, onClick, className }) {
  return <button onClick={onClick} className={className} role="tab">{children}</button>;
}
```

**价值**：极致灵活、不受品牌样式约束、便于适配设计系统。**典型代表**：Radix UI、Headless UI、TanStack、React Aria。它是"组件库 + 设计系统"时代的重要趋势——组件托管行为，品牌样式由团队掌控。

## 八、总结与落地清单

组件设计的本质，是**在正确层次上做出正确的解耦**。最后给你一张可执行的落地检查单：

- [ ] 组件是否满足单一职责？能否只用一句话说明它的作用？
- [ ] 是否把"数据/逻辑"与"展示"分离（容器 vs 展示，或逻辑进 hook）？
- [ ] 数据是否单向流动？子传父是否都用回调/事件清晰表达？
- [ ] props 是否收窄、命名语义化、必填项有预期默认值、有 TS 类型？
- [ ] 是通过组合/插槽而非继承实现扩展？
- [ ] 复用的"有状态逻辑"是否已抽成 hook / composable，而不是重复粘贴？
- [ ] 是否确认当前项目确实需要跨框架/跨端抽象，而非仅为"假设的未来"付出成本？
- [ ] 抽象层级是否明确：基础组件、复合组件、业务组件、页面组件各归其位？

带着这份清单做一次自查，往往就能发现组件库里"长歪"的抽象，进而在下一次搭建或重构时做出更清晰的设计。
