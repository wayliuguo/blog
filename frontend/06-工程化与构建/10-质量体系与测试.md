# 质量体系与测试

> 级别：高级

按本书四层推进：

- **入门使用**：看懂规范治理工具链（ESLint / Prettier / husky / lint-staged / commitlint）的分工与执行时机；
- **进阶**：掌握自定义 ESLint 规则、单测/组件/E2E 测试分层，以及覆盖率门禁；
- **实战**：把 lint + 覆盖率阈值固化进 CI，让"质量不达标就不让合入"成为硬约束；
- **最小实现掌握原理**：到 `code/frontend/14-infra` 运行 `lint-demo.html`，手写一个用"规则数组逐条正则"给代码打分、报错的极简 lint，认清"代码规范工具"的本质。

代码写得对不止靠"细心"，更要靠一套从"写代码之前"到"合并之前"的质量治理体系。它由静态治理（ESLint 自定义规则 / Prettier / husky / commitlint）和多层测试（单测 / 组件测试 / E2E）交织而成，并以覆盖率和质量门禁把"质量不达标就不让合入"变成硬约束。本文构建一套可落地的前端质量体系。

## 一、代码规范治理

### 1. 分层治理工具链

| 工具 | 治理对象 | 时机 |
| ---- | ---- | ---- |
| ESLint | 代码质量与潜在问题 | 编辑器 + 提交前 |
| Prettier | 代码格式 | 编辑器 + 提交前 |
| lint-staged | 只检查本次改动的文件 | git 提交前 |
| husky | 注入 git hook | git 事件触发 |
| commitlint | commit message 规范 | git commit 前 |

### 2. husky + lint-staged 接入示例

在较新的 husky 中，用 `husky init` 初始化并创建 hook 文件：

```bash
npx husky init
```

生成 `.husky/pre-commit`：

```sh
npx lint-staged
```

`package.json` 中声明：

```json
{
  "lint-staged": {
    "*.{ts,tsx,js,vue}": ["eslint --fix", "prettier --write"],
    "*.{css,json,md}": ["prettier --write"]
  }
}
```

### 3. ESLint 自定义规则

内置规则不足以表达团队约束时，可写"自定义规则"。规则本质是一个返回 `meta` 与 `create` 的对象：

```js
// rules/no-console-errors.js
module.exports = {
  meta: {
    type: 'problem',
    docs: { description: 'Disallow console.error in production code' },
    messages: { avoid: '避免在业务代码中使用 console.error' },
    fixable: 'code',
  },
  create(context) {
    return {
      CallExpression(node) {
        if (isConsoleErrorCall(node)) {
          context.report({
            node,
            messageId: 'avoid',
            fix(fixer) {
              return fixer.remove(node);
            },
          });
        }
      },
    };
  },
};
```

```js
function isConsoleErrorCall(node) {
  return (
    node.callee &&
    node.callee.type === 'MemberExpression' &&
    node.callee.object &&
    node.callee.object.type === 'Identifier' &&
    node.callee.object.name === 'console' &&
    node.callee.property &&
    node.callee.property.name === 'error'
  );
}
```

### 4. commitlint 规范提交

使用 Conventional Commits 风格约定：`type(scope): subject`。

```bash
echo "feat: add login page" > commit-msg
# commitlint 校验通过

# 错误示例(会被拦截):
#   "add stuff"  -> 缺少 type
#   "fix bug"    -> 缺 scope 可选，可接受，但需遵守规则
```

配置 `.commitlintrc.json`：

```json
{
  "extends": ["@commitlint/config-conventional"]
}
```

常用 type：`feat` `fix` `docs` `style` `refactor` `perf` `test` `chore` `ci` `revert`。

## 二、单元测试：Vitest / Jest

### 1. 选型对比

| 维度 | Jest | Vitest |
| ---- | ---- | ---- |
| 生态 | 非常成熟 | 与 Vite 原生集成，配置极简 |
| 性能 | 一般 | 利用 Vite + esbuild，快速 |
| 配置成本 | 需配 babel/ts-jest | 继承 Vite 配置，几乎零成本 |
| 适用 | 老项目、重型环境 | 新项目、Vite 项目优先 |

### 2. Vitest 基础示例

```ts
// utils/math.ts
export function add(a: number, b: number) {
  return a + b;
}
```

```ts
// __tests__/math.test.ts
import { describe, it, expect } from 'vitest';
import { add } from '../utils/math';

describe('add', () => {
  it('adds two numbers', () => {
    expect(add(1, 2)).toBe(3);
  });
});
```

### 3. Mock 与断言技巧

```ts
import { expect, vi } from 'vitest';

const mockFn = vi.fn().mockReturnValue(42);
mockFn();

expect(mockFn).toHaveBeenCalled();
expect(mockFn).toHaveBeenCalledTimes(1);
expect(mockFn.mock.results[0].value).toBe(42);
```

## 三、组件测试

组件测试检测"给定 props/交互后，组件是否正确渲染与响应事件"。在 Vue3 上常用 `@vue/test-utils`。

```ts
// Button.test.ts
import { mount } from '@vue/test-utils';
import { describe, it, expect, vi } from 'vitest';
import Button from '../Button.vue';

describe('Button', () => {
  it('emits click with count when clicked', async () => {
    const wrapper = mount(Button, {
      props: { label: 'confirm' },
    });
    const btn = wrapper.find('button');
    await btn.trigger('click');

    expect(wrapper.emitted('click')).toBeTruthy();
    expect(wrapper.emitted('click')![0]).toEqual([{ count: 1 }]);
  });
});
```

### 组件测试关注点

| 测什么 | 不测什么 |
| ---- | ---- |
| props 渲染差异 | 真实后端请求 |
| 事件/named emit | 浏览器级交互(留给 E2E) |
| 条件渲染/插槽 | 样式与视觉细节 |
| 状态变更 | 网络依赖 |

## 四、E2E：Playwright / Cypress

E2E 以真实浏览器验证**用户完整路径**，是对 UI 交互的最终兜底。

### 1. 选型对比

| 维度 | Playwright | Cypress |
| ---- | ---- | ---- |
| 浏览器支持 | 多浏览器(Chromium/Firefox/WebKit) | 主流 Chromium/WebKit 有限 |
| 并行 | 原生多 worker 并行 | 需额外配置/企业版 |
| 网络拦截 | 灵活 | 支持 |
| 上手 | 现代 API、自动等待 | 生态丰富、文档友好 |
| 内置报告 | 生成 Trace/视频 | 截图/视频 |

### 2. Playwright 示例

```ts
// e2e/login.spec.ts
import { test, expect } from '@playwright/test';

test('user can log in', async ({ page }) => {
  await page.goto('/login');
  await page.fill('input[name="username"]', 'demo');
  await page.fill('input[name="password"]', 'secret');
  await page.click('button[type="submit"]');
  await expect(page).toHaveURL(/\/dashboard/);
  await expect(page.locator('.welcome')).toContainText('欢迎回来');
});
```

## 五、覆盖率与质量门禁

### 1. 覆盖率指标

| 指标 | 含义 |
| ---- | ---- |
| 行覆盖率(Statements) | 被执行过的代码行占比 |
| 分支覆盖率(Branches) | 被覆盖的 if/switch 分支占比 |
| 函数覆盖率(Functions) | 被调用过的函数占比 |

### 2. 覆盖率配置与门槛

```ts
// vitest.config.ts
export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      include: ['src/**/*.{ts,vue}'],
      thresholds: {
        lines: 80,
        functions: 80,
        branches: 70,
        statements: 80,
      },
    },
  },
});
```

### 3. 质量门禁在 CI 中的落地

```
<push / pull_request>
      │
      ▼
  lint(ESLint+Prettier+commitlint) ──失败→ 拒绝
      │成功
      ▼
  单测 + 覆盖率阈值           ──失败/不达标→ 拒绝
      │成功
      ▼
  组件测试 + E2E            ──失败→ 拒绝
      │成功
      ▼
  gate 全绿 → 允许合并 / 进入需要审批的部署流程
```

在 CI 中直接失败退出码即"门禁"：

```bash
pnpm lint && pnpm test:coverage   # 任一失败，命令退出码非 0，pipeline 红
```

### 4. 覆盖率之外的"质量信号"

质量门禁不止覆盖率：

| 信号 | 工具 |
| ---- | ---- |
| 同质重复代码 | SonarQube / kodethon / CodeQL |
| 依赖漏洞 | `npm audit` / Dependabot |
| SLO 回归 | 性能/错误率监控(见《06-发布、灰度与监控》) |
| 复杂度 | ESLint `complexity` 规则 |

## 最小实现：手写一个极简 lint 看清"规范工具"的本质

到 `code/frontend/14-infra` 运行 `lint-demo.html`：它定义一个"规则数组"，每条含匹配正则、严重度与提示，对一段示例代码逐行扫描并报错/警告、扣分，最终给出门禁结论。原理一句话：ESLint/Prettier 与它同源——本质都是"把约定转成能逐条执行的规则，再对源码文本或 AST 做判定"；规则是否可执行，决定了规范是否真正落地。
