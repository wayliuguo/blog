# 调试技巧

"写代码"与"排错"是开发者的两项核心能力。本文围绕 VS Code 调试展开，覆盖 `launch.json` 配置项的逐个说明、普通入口文件与 npm 脚本的调试方式、debugger 断点的几种类型，以及 Node.js 项目的浏览器（Chrome DevTools）调试技巧，帮助你从"打 `console.log`"升级到真正的断点调试。

> 级别：初级→中级

按本书四层推进：

- **入门使用**：会配 `.vscode/launch.json`，能断点调试普通入口与 npm 脚本；
- **进阶**：理解 `launch` / `attach` 两种请求、各断点类型与 source map 映射；
- **实战**：把 VS Code 与浏览器 DevTools 对接，对真实 Node 项目做断点与性能定位；
- **最小实现掌握原理**：到 `code/frontend/06-engineering` 运行 `mini-dev-hmr.html`，体会"在程序运行中持续观察其状态"的最小形态。

## 一、launch.json：调试配置核心

调试配置写在项目的 `.vscode/launch.json` 中，其中最核心的字段说明如下：

- **`type`**：调试器类型，如 `node`（Node.js）、`google-chrome`（浏览器）、`python`、`java` 等。
- **`request`**：请求类型，`launch`（启动一个新进程）或 `attach`（附加到已运行进程）。
- **`name`**：为配置提供友好名称，便于识别与切换。
- **`runtimeExecutable`**：程序运行所需可执行文件的路径，如 `"npm"`。
- **`program`**：程序入口文件路径，绝对路径或相对工作目录。
- **`cwd`**：程序工作目录。
- **`args`**：命令行参数，数组形式。
- **`env`**：程序运行环境变量，对象形式。
- **`stopOnEntry`**：`true` 时启动后在入口处停下，等待调试器连接。
- **`console` / `externalConsole`**：`externalConsole` 为 `true` 时在外部控制台运行；多用于设置输出位置，如 `"console": "integratedTerminal"`。
- **`internalConsoleOptions`**：内部控制台显示方式，`neverOpen` / `openOnSessionStart` / `openOnFirstSessionStart`。
- **`showAsyncStacks`**：`true` 时在堆栈跟踪中显示异步调用信息。
- **`smartStep`**：`true` 时跳过无需调试的代码。
- **`skipFiles`**：指定不需要调试的文件或文件夹，如 `<node_internals>/**`（跳过 Node 内置模块）。
- **`justMyCode`**：`true` 时只调试自己的代码。
- **`preLaunchTask`**：启动调试前运行的**编译任务**。
- **`postDebugTask`**：调试结束后运行的任务，如清理。
- **`outFiles`**：输出文件路径，用于映射源码与编译后的文件。
- **`sourceMaps`**：是否启用 source map，`inline` / `both` / `false`。
- **`sourceMapPathOverrides`**：根据 source map 调整文件路径。

## 二、调试普通入口文件

假设入口文件是 `bin/index.js`，配置如下：

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "type": "node",
            "request": "launch",
            "name": "启动程序",
            "skipFiles": [
                "<node_internals>/**"
            ],
            "program": "${workspaceFolder}\\bin\\index.js",
            "args": [
                "V"
            ]
        }
    ]
}
```

- `${workspaceFolder}` 是 VS Code 提供的变量，指向当前打开的工作区（根）目录。
- 在调试面板选择「启动程序」后按 F5，即可断点调试。

## 三、调试 npm 脚本入口

与上面唯一区别在于引入 `runtimeExecutable: "npm"`，并把 `args` 改为脚本命令：

```json
{
    "version": "0.2.0",
    "configurations": [
        {
            "type": "node",
            "request": "launch",
            "name": "debug nest",
            "runtimeExecutable": "npm",
            "args": ["run", "start:dev"],
            "skipFiles": ["<node_internals>/**"],
            "console": "integratedTerminal"
        }
    ]
}
```

这种方式非常适用于需要经过构建/启动脚本的框架项目（如 Nest、Express 脚手架）。

### 快捷方式：直接调试 package.json 中的 scripts

1. 在 `package.json` 里命令行 `scripts` 旁边会出现 Debug 入口，直接点击并选择需要调试的脚本。
2. 或者在调试界面选择 Node.js 类型，然后同样选取 `package.json` 中配置的脚本。

两种方式都不用手写 `runtimeExecutable`，由 VS Code 自动生成配置。

## 四、断点类型

在行号左侧点击即可添加断点，右键可选择不同类型：

1. **Add Breakpoint**：普通断点，执行到这里停住。
2. **Add Conditional Breakpoint**：条件断点，**表达式成立时才停住**，适合循环中带条件过滤。
3. **Add Logpoint**：日志点，**避免写 `console.log`**，在表达式处用 `{}` 包裹要打印的变量（如 `{user.id}`），不停顿只输出日志。
4. **Add Triggered Breakpoint**：触发断点，与条件断点功能接近。

| 类型 | 是否会停住 | 典型用途 |
| --- | --- | --- |
| Breakpoint | 会 | 定位到某行就中断 |
| Conditional | 条件满足时 | 循环/特定场景过滤 |
| Logpoint | 不会（只打日志） | 快速看变量且不打断流程 |

## 五、前端（浏览器）调试

前端代码既可以在浏览器 DevTools 中调试，也可以通过 VS Code 的 debugger + `attach` 连接已启动的页面。

### Chrome DevTools 断点调试

打开开发者工具（F12）→ Sources（源代码）面板：

- 在源码行号处点击添加断点。
- 使用调试控制栏暂停 / 单步 / 进入、跳出函数。
- **Console** 面板可在断点暂停时用 **Evaluate in console** 实时计算变量。
- 用 **watch**（监视）面板观察指定表达式的值变化。

### 性能分析（Performance 面板）

当页面卡顿、加载慢时，使用 **Performance** 面板：

- 点击录制（Record）后刷新/操作页面，再停止录制。
- 观察 **主线程时间线（Main）**，找出耗时任务（长任务 / 脚本执行 / 布局重排）。
- 结合 **Network** 面板定位慢请求、过大资源，进而针对性优化。

## 六、Node.js 调试（浏览器连调试）

Node.js 也支持通过调试协议把断点暴露给浏览器 DevTools：

```js
// index.js
const os = require('os');
const homedir = os.homedir();
console.log(homedir);
```

**1. 以调试模式启动：**

```bash
node --inspect-brk index.js
```

`--inspect-brk` 启动后会**停在入口等待调试器连接**，并起一个 ws（WebSocket）调试服务。

**2. 连接调试：**

打开 `chrome://inspect/`，即可看到可调试的目标（页面 / Node 进程），点击即可进入 DevTools 调试。

**3. 检查配置：**

如果 `chrome://inspect/` 里没有出现调试目标，点击「Configure…」添加上 `localhost:9229`（默认调试端口）。

### 调试 Nest 项目（浏览器方式）

若项目提供了 `start:debug` 脚本：

```bash
npm run start:debug
```

它会以调试端口启动应用，然后在 `chrome://inspect/` 连接到对应进程即可使用 DevTools 断点调试。

### 调试模型的统一认识

无论浏览器还是 Node，"断点调试"的本质都是：**调试客户端（VS Code / DevTools）通过调试协议连接到一个可中断执行的运行环境，在命中断点处暂停，供你查看调用栈与变量、单步执行**。掌握 launch.json 的 `launch` 与 `attach` 两种请求，就能把这条链路套用到任意运行时上。

## 最小实现：用 Demo 验证原理

到 `code/frontend/06-engineering` 运行 `mini-dev-hmr.html`：它每隔 2 秒轮询本地信号，并把"同步 / 变更 / 新版本"每一步都持续输出到页面。原理一句话：调试 = 在程序的关键节点停下或记录，观察当时的内部状态——断点调试是"暂停后看"，而轮询日志是"持续输出看"，二者源自同一个本质。
