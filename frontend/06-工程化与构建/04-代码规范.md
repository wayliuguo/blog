# 代码规范

在团队协作中，"能跑"只是底线，"好维护"才是追求。一套约定统一的代码规范，包括静态检查（ESLint）、格式化（Prettier）、提交前的 Git 钩子校验（husky + lint-staged + commitlint）、以及命名与样式约定（BEM），能把大量潜在的风格争争吵、低级错误在进入代码库之前就拦截下来。本文从工具的安装、配置、常见报错排查到 VS Code 落地实践，梳理一整套代码规范方案。

> 级别：初级→中级

按本书四层推进：

- **入门使用**：会装能用 ESLint 与 Prettier，配置"保存即格式化、保存即修复"；
- **进阶**：理解 ESLint 的规则 / 插件 / 继承，以及它和 Prettier 的角色分工与解冲突；
- **实战**：用 husky + lint-staged + commitlint 把校验固化进提交链路，让规范成为团队流程而非个人自觉；
- **最小实现掌握原理**：到 `code/frontend/06-engineering` 运行 `semver.html`，从依赖版本字段的解析体会"规范被解析器逐条执行"这件事。

## 一、ESLint：静态代码检查

ESLint 是一个代码检测工具，用于检测代码中潜在的问题和错误，作用是**提高代码质量、约束代码规范**。

### 安装

```bash
npm install eslint
```

### 初始化配置文件

```bash
npm init @eslint/config
```

初始化时会交互式询问你的模块风格、框架等，自动生成 `.eslintrc.*` 配置文件。

若项目同时使用了 Prettier 做格式化，两者可能产生冲突（如引号、缩进风格不一致），建议安装互补包消除冲突：

```bash
npm i eslint-config-prettier eslint-plugin-prettier -D
```

### .eslintrc.js 示例

```js
module.exports = {
    env: {
        browser: true,
        es2021: true,
        node: true
    },
    extends: ['eslint:recommended', 'prettier'],
    overrides: [
        {
            env: {
                node: true
            },
            files: ['.eslintrc.{js,cjs}'],
            parserOptions: {
                sourceType: 'script'
            }
        }
    ],
    plugins: ['prettier'],
    parserOptions: {
        ecmaVersion: 'latest',
        sourceType: 'module'
    },
    rules: {
        indent: ['error', 4] // 指定代码缩进方式，这里为使用四个空格缩进
    }
}
```

要点说明：

- `env`：声明代码运行环境，避免误报 `process`、`window` 等未定义。
- `extends`：继承规则集，`prettier` 用于与 Prettier 解冲突。
- `plugins`：注册可用的规则插件，`prettier` 让 ESLint 也能按 Prettier 规则检查。
- `rules`：具体规则的细粒度开关，可参照[官方文档](https://github.com/eslint/eslint)配置。

## 二、Prettier：代码格式化

Prettier 负责**代码格式化**，统一引号、缩进、分号、换行等风格，让团队代码长成一个样。

### 安装

```bash
npm install prettier --save-dev
```

> 注意使用场景的差异：通过 **vsCode 插件**安装时，保存文件即可自动格式化；通过 **npm** 安装时，只能通过命令行使用（常用于配合 git hooks 在提交前强制格式化）。

### 配置

`.prettierrc.js`：

```js
module.exports = {
    semi: false,             // 语句末尾不使用分号
    trailingComma: 'none',   // 多行结构末位不加逗号
    singleQuote: true,       // 使用单引号
    printWidth: 120,         // 单行最大宽度，超出换行
    tabWidth: 4,             // 一个 Tab 等于 4 个空格
    arrowParens: 'avoid',    // 箭头函数参数括号
    endOfLine: 'auto',       // 结尾换行自动（兼容各操作系统）
    jsxBracketSameLine: true // JSX 右括号是否跟随末行
}
```

`.prettierignore`（忽略无需格式化的文件）：

```
node_modules
dist
package.json
```

## 三、husky + lint-staged：提交前强制校验

**ESLint / Prettier 只能在你主动运行或编辑器保存时生效**，无法保证成员都遵守。husky 通过 Git 钩子，能在指定 Git 事件发生前强制执行脚本（如格式化、检查、测试），从源头保证代码库风格统一。

### 常见 Git 钩子

- `pre-commit`：执行 `git commit` 之前触发，用于提交前的检查、格式化、测试。
- `commit-msg`：提交消息（commit message）被创建后、提交完成前触发，用于校验提交消息格式。
- `pre-push`：执行 `git push` 之前触发，用于推送前的额外检查、测试。

### husky V6.0 之后的使用方式

husky 从 V6 开始采用更轻量的目录式配置。安装并启用：

```bash
npm install -D husky
```

在 `package.json` 中加 `prepare` 脚本（`npm install` 不带参数时会自动执行，从而创建 `.husky/` 目录并指定其为 git hooks 目录）：

```bash
npm pkg set scripts.prepare="husky install"
```

```json
{
    "scripts": {
        "prepare": "husky install"
    }
}
```

创建钩子文件：

```bash
# 校验暂存区代码
npx husky add .husky/pre-commit 'npx lint-staged'

# 校验提交信息
npx husky add .husky/commit-msg 'npx commitlint --edit ${1}'
```

执行成功后在 `.husky` 目录会多出 `pre-commit` 和 `commit-msg` 两个文件。

### lint-staged：仅对暂存区执行脚本

lint-staged 能在 **git 暂存（staged）区域**中的文件上运行脚本，通常配合 husky 钩子在提交前完成格式化与静态检查，避免对全库进行无谓检查。

```bash
npm install lint-staged --save-dev
```

在 `package.json` 中添加配置：

```json
{
    "lint-staged": {
        "src/**/*.{js,jsx,ts,tsx}": [
            "prettier --write",
            "eslint --fix"
        ]
    }
}
```

- `"src/**/*.{js,jsx,ts,tsx}"`：指定要针对的暂存文件模式，可按项目需求调整。
- `["prettier --write", "eslint --fix"]`：提交前依次执行的校验命令。
- 配置后，`commit` 前就会对暂存文件自动执行 `prettier` 与 `eslint`。

> 补充（husky V6.0 前的老写法，供旧项目参考）：在 `package.json` 中通过 `"husky": { "hooks": { "pre-commit": "...", "commit-msg": "..." } }` 声明钩子。

## 四、commitlint + Commitizen：规范提交信息

提交信息同样需要规范，便于回溯与自动生成 changelog。

### commitlint：校验提交信息格式

上面 `commit-msg` 钩子里的 `npx commitlint --edit ${1}`，就是读取暂存的提交信息并按约定规则校验。安装：

```bash
npm install -D @commitlint/cli @commitlint/config-conventional
```

配置 `commitlint.config.js`：

```js
module.exports = {
    extends: ['@commitlint/config-conventional']
}
```

`config-conventional` 支持的类型包括 `feat`（新功能）、`fix`（修复）、`docs`（文档）、`style`（样式/格式）、`refactor`（重构）、`perf`（性能）、`test`（测试）等。

### Commitizen：引导式提交

Commitizen 是一个命令行工具，用于以一致的方式编写规范的提交消息。它通过交互式问答引导你填写 type、scope、description 等。

```bash
npm install --save-dev commitizen cz-conventional-changelog
```

`cz-conventional-changelog` 是 Commitizen 的一个适配器，实现了符合 Conventional Commits 规范的提交消息。在 `package.json` 中配置：

```json
{
    "config": {
        "commitizen": {
            "path": "cz-conventional-changelog"
        }
    },
    "scripts": {
        "commit": "git-cz"
    }
}
```

使用：

```bash
git add .
npm run commit
```

交互式选择提交类型并填写内容：

```
? Select the type of change that you're committing: (Use arrow keys)
> feat:     A new feature        // 新功能
  fix:      A bug fix            // 错误修复
  docs:     Documentation only changes
  style:    Changes that do not affect the meaning of the code
  refactor: A code change that neither fixes a bug nor adds a feature
  perf:     A code change that improves performance
  test:     Adding missing tests or correcting existing tests

? What is the scope of this change        // 此更改的范围
? Write a short, imperative tense description of the change //【必填】简短描述
? Provide a longer description of the change                // 详细说明
? Are there any breaking changes?        // 是否有破坏性变更
? Does this change affect any open issues? (y/N)
```

完成提交后输出日志：

```
[master 2cf55e0] docs: 修改commitzen文档
 1 file changed, 2 insertions(+), 2 deletions(-)
```

## 五、团队命名规范：BEM

除了工具层面，命名本身也要有约定。**BEM** 是 CSS/类名命名中广泛采用的一种规范，由三部分组成：

1. **Block（块）**：一个独立、可重用的组件或模块，是页面上的高级元素。
2. **Element（元素）**：块的组成部分，不能独立存在，位于块内部；用**双下划线** `__` 连接块和元素。
3. **Modifier（修饰符）**：修改块或元素的外观、状态或行为；用**单个连字符 / 双连字符** `--` 连接。

```css
.header__logo--hidden
/* Block=header  Element=logo  Modifier=hidden */
```

### 推荐 CSS 属性书写顺序

1. **定位属性**：`position display float left top right bottom overflow clear z-index`
2. **自身属性**：`width height margin padding border background`
3. **文字样式**：`font-family font-size font-style font-weight font-varient`
4. **文本属性**：`text-align vertical-align text-wrap text-transform text-indent text-decoration letter-spacing word-spacing white-space text-overflow`
5. **CSS3 新增属性**：`content box-shadow border-radius transform`

### 用 JS 实现 BEM（类名前缀生成器）

先实现字符串拼接的 `_bem`：

```ts
function _bem(
  prefixName: string,
  blockSuffix: string,
  element: string,
  modifier: string | number
) {
  if (blockSuffix) {
    prefixName += `-${blockSuffix}`
  }
  if (element) {
    prefixName += `__${element}`
  }
  if (modifier) {
    prefixName += `--${modifier}`
  }
  return prefixName
}
```

再封装 `createBEM`，导出 `b`、`e`、`m`、`be`、`bm`、`em`、`bem` 等便捷函数：

```ts
function createBEM(prefixName: string) {
  const b = (blockSuffix = '') => _bem(prefixName, blockSuffix, '', '')
  const e = (element = '') => (element ? _bem(prefixName, '', element, '') : '')
  const m = (modifier = '') =>
    modifier ? _bem(prefixName, '', '', modifier) : ''

  const be = (blockSuffix = '', element = '') =>
    blockSuffix && element ? _bem(prefixName, blockSuffix, element, '') : ''
  const bm = (blockSuffix = '', modifier = '') =>
    blockSuffix && modifier ? _bem(prefixName, blockSuffix, '', modifier) : ''
  const em = (element = '', modifier: string | number = '') =>
    element && modifier ? _bem(prefixName, '', element, modifier) : ''
  const bem = (blockSuffix = '', element = '', modifier = '') =>
    blockSuffix && element && modifier
      ? _bem(prefixName, blockSuffix, element, modifier)
      : ''

  const is = (name: string, state: string | boolean) =>
    state ? `is-${name}` : ''
  return { b, e, m, be, bm, em, bem, is }
}

export function createNamespace(name: string) {
  const prefixName = `van-${name}`
  return createBEM(prefixName)
}
```

生成如 `van-button__icon--small` 这类符合 BEM 且带前缀的类名，是组件库 / 业务组件命名时常用的小工具。

## 六、常见错误排查

### 换行符格式不一致（Delete `␍` prettier/prettier）

**表现：** 编辑器 / ESLint 提示 `Delete '␍'`，这是因为 Windows 默认使用 `CRLF` 换行，而项目统一为 `LF`（或反之）。

#### 方法 1：用 VS Code 转换

- 打开存在问题的文件。
- 查看编辑器底部状态栏、点击显示的 `CRLF`。
- 从弹出菜单中选择 `LF`。
- 保存文件。

#### 方法 2：让 Prettier 支持 CRLF

```json
// .prettierrc
{
    "singleQuote": true,
    "trailingComma": "all",
    "endOfLine": "crlf"  // 新增这一行
}
```

#### 方法 3：配置 ESLint 忽略换行符检查（推荐）

```js
// .eslintrc.js
rules: {
    // 其他规则保持不变
    "prettier/prettier": ["error", { "endOfLine": 0 }] // 新增这一行，忽略换行符
}
```

### 其他常见问题排查思路

- **ESLint / Prettier 规则互相报冲突**：确认 `extends` 与 `plugins` 中已引入 `prettier` 相关配置，并集中调整 `rules`。
- **钩子未触发**：确认 `husky install` 已执行、`.husky/` 目录存在，且对应 `pre-commit` / `commit-msg` 文件内容正确。
- **`npx husky add` 后文件无执行权限（macOS/Linux）**：使用 `chmod +x .husky/pre-commit` 赋予执行权限。

## 七、VS Code 落地配置

通过项目的 `.vscode/settings.json`，可以把上述规范在编辑器层面固化，达到"保存即格式化、保存即修复"的效果。

### 作用

`.vscode/settings.json` 用于覆盖 VS Code 默认全局配置，或添加项目专属设置。

### 参考配置

```json
{
    "editor.fontSize": 14,
    "editor.formatOnSave": true,   // 开启保存时自动格式化

    // 对于 JavaScript，使用 Prettier 作为默认格式化器
    "[javascript]": {
        "editor.defaultFormatter": "esbenp.prettier-vscode"
    },

    // 对于 JSON，也可以使用 Prettier
    "[json]": {
        "editor.defaultFormatter": "esbenp.prettier-vscode"
    },

    "security.workspace.trust.untrustedFiles": "open",

    // 保存时触发的代码操作，例如 ESLint 的自动修复
    "editor.codeActionsOnSave": {
        "source.fixAll.eslint": true
    },

    // ESLint 相关设置（需安装 ESLint 插件）
    "eslint.codeActionsOnSave.rules": null,
    "eslint.execArgv": null
}
```

> 拓展阅读：结合 `husky + eslint + prettier`，可以做到"编辑器层自动格式化 + 提交前强制校验"双保险，从而在多人协作中保证代码仓库的风格始终统一。

## 最小实现：用 Demo 验证原理

到 `code/frontend/06-engineering` 运行 `semver.html`：它用一段 JS 逐条解析 `^1.2.3`、`~1.2.3` 等依赖版本范围。原理一句话：工程化的"规范"最终都落到可被工具逐条执行的约定——正如依赖版本由解析器决定能装哪个，代码风格由 ESLint/Prettier 的规则逐条判定，口头约定只有"可执行"才算落地。
