# 脚手架的诞生

> 级别：中级→高级

按本书四层推进：

- **入门使用**：看懂脚手架"收集信息 → 选模板 → 渲染生成 → 收尾"四件事，以及它替人省下了什么；
- **进阶**：掌握 commander/yargs 的命令与参数解析、模板引擎插值原理；
- **实战**：参考 create-vite 的生成器架构，设计并实现一个会"解析 CLI 参数、按参数选模板"的私有脚手架；
- **最小实现掌握原理**：到 `code/frontend/14-infra` 运行 `scaffold-cli.html`，用一段 JS 把 `my-create app -t vue --force` 解析成结构化选项，看"CLI 参数解析"这件事的本质。

"npm create vite@latest my-app" 一键就能生成一个可运行的项目，这门"黑魔法"背后是一项基础工程能力：脚手架(Scaffold / CLI)。脚手架的本质是把"创建项目的知识"沉淀为可复用的代码，让工程师从重复初始化中解放出来。本文从脚手架职责出发，讲解 CLI 设计、模板引擎，并从 create-app 这类知名项目源码中提炼出通用生成器架构，最终延伸到私有脚手架平台的建设。

## 一、脚手架的核心职责

### 1. 脚手架解决什么

| 问题 | 手动做法 | 脚手架做法 |
| ---- | ---- | ---- |
| 项目初始化 | 复制旧项目然后删删改改 | 一条命令生成结构 |
| 依赖版本漂移 | 各自装，版本不一致 | 锁定模板内统一版本 |
| 规范不一致 | 各写各的配置 | 内置统一 ESLint/tsconfig/prettier |
| 升级困难 | 想升级没头绪 | 重新生成或 codemod |

### 2. 脚手架要做的四件事

```
输入(选项/参数)
    │
    ▼
确定模板与配置 ──▶ 生成/拷贝文件 ──▶ 安装依赖 ──▶ 输出总结
    │                  │              │
    │ 用户交互          │ 模板渲染      │ 包管理器调用
    ▼                  ▼              ▼
  询问选项           ejs/handlebars    npm/pnpm/yarn
```

1. **收集信息**：交互式提问（项目名、框架、要不要 TS/路由/状态管理等）。
2. **选择模板**：根据答案匹配对应模板或动态生成配置。
3. **渲染生成**：把模板内容渲染成目标项目文件。
4. **收尾**：安装依赖、初始化 git、输出下一步操作指引。

## 二、CLI 设计：commander / yargs

一个 Node CLI 程序通常以这样的入口开始：

```js
#!/usr/bin/env node   // shebang，让系统用 Node 执行

const { Command } = require('commander');
const program = new Command();
```

### 1. commander 设计一个命令

```js
// bin/index.js
#!/usr/bin/env node
const { program } = require('commander');
const packageJSON = require('../package.json');
const create = require('../lib/create');

program
  .version(packageJSON.version)          // --version
  .name('my-scaffold')
  .usage('<command> [options]');         // 帮助信息

program
  .command('create <projectName>')        // create my-app 必选项目名
  .description('create a new project')
  .option('-t, --template <template>', 'specify template', 'vue') // 默认 vue
  .option('-f, --force', 'force overwrite directory')
  .action((projectName, options) => {
    create(projectName, options);
  });

program.parse(process.argv);
```

### 2. 常用 API 对照

| 能力 | commander | yargs |
| ---- | ---- | ---- |
| 定义命令 | `program.command()` | `yargs.command()` |
| 可选参数 | `.option()` | `.option()` |
| 必填参数 | `<param>` | `positional` |
| 帮助信息 | 自动生成 | 自动生成，可自定义 |
| 交互式 | 需配合 prompts/inquirer | 需配合 inquirer |
| 定位 | 命令式，直观易读 | 参数解析更强，历史悠久 |

### 3. 错误处理与健壮性

```js
// 捕获未知命令
const { Option, Command } = require('commander');

// 参数校验：目录已存在且未加 --force
const fs = require('fs');
const path = require('path');

function create(projectName, options) {
  const target = path.resolve(process.cwd(), projectName);
  if (fs.existsSync(target) && !options.force) {
    console.error(`目标目录 ${projectName} 已存在，请使用 --force 覆盖`);
    process.exit(1);
  }
  // ... 后续
}
```

## 三、模板引擎

模板引擎解决"同样的骨架，不同项目有细微差异"的问题。核心逻辑是：**用占位符 + 条件 + 循环，把配置注入模板文件**。

### 1. 常用模板引擎对比

| 引擎 | 语法特点 | 使用场景 |
| ---- | ---- | ---- |
| Handlebars | `&#123;&#123;name&#125;&#125;` 逻辑少，偏纯文本 | 通用文件模板 |
| EJS | `<% %>` 支持 JS 逻辑 | 需要条件/循环的配置模板 |
| Mustache | 无逻辑，最简 | 简单替换 |
| Liquid | 模板标签丰富 | Ruby 生态、主题 |
| JSON 合并 / 直接 JS 生成 | 用函数动态拼对象 | 需要强逻辑时更灵活 |

> **构建坑提醒**：若脚手架最终生成的是 Vue/React 项目，而模板文件又是 `.vue`/`.jsx` 后缀，模板引擎的插值语法 `&#123;&#123;var&#125;&#125;` 可能与 Vue 模板插值或框架语法冲突，因此很多脚手架选择**在生成时完成渲染，而不是运行时渲染**，避免二义性。

### 2. EJS 渲染 package.json 示例

`templates/package.json.ejs`：

```ejs
{
  "name": "<%= projectName %>",
  "version": "0.1.0",
  "type": "module",
  "scripts": {
    <% if (features.includes('vue')) { %>
    "dev": "vite",
    "build": "vite build"
    <% } else { %>
    "dev": "vite --type=react",
    "build": "vite build"
    <% } %>
  },
  "dependencies": {
    "vue": "^3.4.0"<% if (features.includes('router')) { %>,
    "vue-router": "^4.3.0"<% } %>
  }
}
```

## 四、从 create-app 源码看生成器架构

以 `create-vite`（Vite 官方脚手架）为范例，理解真实脚手架的代码组织与流程。

### 1. 整体状态机

```
start ──────────────▶ 解析参数 ──▶ 询问缺省信息 ──▶ 确定模板
                                                       │
   选用定制的构建工具 / 非 JavaScript 项目 ◀── 再次询问 ──┤
                                                       ▼
                                                     拷贝/写入
                                                       │
                                                       ▼
                                          安装依赖 ──▶ 下一步指引
```

### 2. 模板的组织方式

`create-vite` 把模板按"框架 × 变体"组织在 `playground` 目录：

```
templates/
  vanilla/           # 纯 JS/TS
  vanilla-ts/
  vue/               # Vue3
  vue-ts/
  react/
  react-ts/
  ...
```

生成时通过一个 `FRAMEWORKS` 数组记录每个模板的元信息与变体：

```js
const FRAMEWORKS = [
  {
    name: 'vanilla',
    color: 36,
    variants: [
      { name: 'vanilla', display: 'JavaScript', color: 36 },
      { name: 'vanilla-ts', display: 'TypeScript', color: 360 },
    ],
  },
  {
    name: 'vue',
    color: 32,
    variants: [
      { name: 'vue', display: 'JavaScript', color: 32 },
      { name: 'vue-ts', display: 'TypeScript', color: 35 },
    ],
  },
];
```

### 3. 核心渲染函数 getTemplateDir

```js
function getTemplateDir(targetDir, template) {
  const cwd = process.cwd();
  const root = path.resolve(cwd, targetDir);
  const templateDir = path.resolve(__dirname, `template-${template}`);

  fs.mkdirSync(root, { recursive: true });

  // 使用 writeFile 逐个写入文件，而非简单的 cp -r
  // 好处：可以针对每个文件做条件处理、过滤、保留空目录等
  const files = fs.readdirSync(templateDir);
  for (const file of files.filter((f) => f !== 'package.json')) {
    write(file, ...);
  }

  // package.json 单独做「改写」，保留用户选择的 name 等信息
  const pkg = JSON.parse(fs.readFileSync(path.join(templateDir, 'package.json'), 'utf-8'));
  editFile(path.join(root, 'package.json'), (content) =>
    content.replace(`"name": "${npmName}"`, `"name": "${projectName}"`),
  );
}
```

### 4. 从源码中提炼的通用生成器架构

任何 create-app 类工具都可以抽象为这样一个分层的生成器架构：

```
┌─────────────────────────────────────────────┐
│            CLI 入口 (bin/index.js)          │
│  解析参数 → 交互提问 → 协调调用             │
└─────────────────────────────────────────────┘
                    │
┌───────────────────▼─────────────────────────┐
│             Generator 核心控制器             │
│  getTemplateDir / 模板解析 / 文件渲染        │
│  条件合并、过滤、覆盖保护、冲突处理          │
└─────────────────────────────────────────────┘
                    │
┌───────────────────▼─────────────────────────┐
│              Template 仓库层                │
│  官方模板 / 私有模板 / 远端模板下载          │
└─────────────────────────────────────────────┘
```

## 五、私有脚手架平台

当团队变大，光靠"复制 create-vite"是不够的，还要**把团队自己的约定、内部能力沉淀进模板**。

### 1. 为什么需要私有脚手架

- 官方脚手架只给通用骨架，不含团队的企业级能力（登录态、埋点、组件库、请求封装、权限路由）。
- 团队规范（ESLint 规则集、tsconfig、发布脚本）想统一导入。
- 模板需要跟随团队约定持续迭代并发布版本。

### 2. 私有脚手架平台的构成

```
私有 CLI (脚手架客户端)
    │  拉取模板元信息
    ▼
模板仓库 / 模板中心 (可发布、可版本化)
    │  按所选模板生成 + 注入
    ▼
企业级基础模板(含:布局/请求/埋点/权限/组件库)
```

典型实现方案：

```
npm 私服(package.json 模板包)
       + 模板中心后台(模板列表、版本、变更日志)
       + 版本化发布(模板 v1.0.0 / v1.1.0)
```

### 3. 私有模板版本化发布命令示例

```bash
# 发布一个模板版本
npm run release:template --r 1.2.0

# CLI 可指定要用的模板版本
my-fw create app --template enterprise@1.2.0

# 查看可用模板列表（私下或公司后台）
my-fw list
```

### 4. 建设要点

| 要点 | 说明 |
| ---- | ---- |
| 模板迭代与灰度 | 新模板先在试点团队用，全面铺开前保证稳定 |
| 埋点统计 | 记录"哪些模板被谁用、用了什么变体"，指导模板进化 |
| 可升级性 | 提供 `upgrade` 命令或 codemod，老项目能跟进新基建 |
| 文档与示例 | 模板自带 README 与 demo，降低使用门槛 |
| 权限与审计 | 谁发布、谁使用、版本变更记录可追溯 |

## 最小实现：用手写参数解析看到一个 CLI 的本质

到 `code/frontend/14-infra` 运行 `scaffold-cli.html`：它用一段 JS 把 `my-create app -t vue --force` 这类命令解析成结构化对象（command、positional、options、flags），并据此决定"用哪个模板"，还模拟了 workspace 本地包解析。原理一句话：所有脚手架 CLI 的本质都是"解析参数 + 按参数拼装输出"，commander/yargs 只是把这一步规则封装好——参数解析清楚了，脚手架一半的工作就有了答案。
