# 浏览器存储与本地缓存

> 级别：中级

按本书四层推进：

- **入门使用**：Cookie 的基本读写、localStorage/sessionStorage 的存取、IndexedDB 的增删改查；
- **进阶**：SameSite、HttpOnly、行为规范冲突、Service Worker + Cache Storage 离线缓存策略；
- **实战**：结合本章 `04-前端安全`，你会在 XSS/CSRF 的背景下重新审视每种存储的取舍；
- **最小实现掌握原理**：到 `code/frontend/04-network-browser` 运行 `storage-demo.html`，亲手写读 localStorage / sessionStorage / Cookie 并观察生命周期与作用域。

浏览器本身就是一个"小型的持久化数据库"。登录态要记住、购物车要保留、图片要复用、离线要可用——这些需求都依赖浏览器端的数据保存能力。但`Cookie`、`localStorage`、`sessionStorage`、`IndexedDB`、`Cache Storage`五花八门，各自的能力边界、容量、同步/异步、作用域都不同，选错了轻则白占内存，重则带来安全隐患。

这篇文章我们把这些存储机制逐一拆解：Cookie 从属性到作用域、localStorage/sessionStorage 的区别与限制、IndexedDB 的进阶用法、已被废弃的 Web SQL，最后用一张对比表收尾，并给出清晰的适用场景选择思路。

## 一、Cookie：最早的服务端会话载体

### 1. 什么是 Cookie

Cookie 是服务器通过 `Set-Cookie` 响应头发送给浏览器、浏览器随后存储的一小段文本。它的初衷是"以键值对的形式帮服务端记住客户端状态"，因为 HTTP 本身是无状态的。

```http
HTTP/1.1 200 OK
Set-Cookie: sessionId=abc123; Path=/; HttpOnly; SameSite=Lax
Set-Cookie: theme=dark; Max-Age=2592000
```

此后浏览器在同源且符合 `Path` 的请求中，会通过 `Cookie` 请求头自动带上这些数据：

```http
GET /profile HTTP/1.1
Cookie: sessionId=abc123; theme=dark
```

### 2. Cookie 的核心属性

| 属性 | 作用 |
| --- | --- |
| `Expires` / `Max-Age` | 过期时间。不设置则为**会话级 Cookie**，关闭浏览器即失效 |
| `Path` | 生效路径，如 `/` 全站生效，`/admin` 仅后台生效 |
| `Domain` | 指定哪些域名可携带，含子域共享 |
| `Secure` | 仅在 HTTPS 连接下传输 |
| `HttpOnly` | 禁止 JS 读取（`document.cookie` 访问不到），是抵御 XSS 盗 Cookie 的关键 |
| `SameSite` | 控制跨站请求是否携带（见下） |
| `Priority` | 设置优先级（低/中/高），用于淘汰时的保留顺序 |

### 3. Cookie 的作用域

Cookie 的作用域由 **`Domain` + `Path`** 共同决定：

```js
// 响应头：Domain=.example.com; Path=/
// 则对 www.example.com、api.example.com、blog.example.com 都生效
```

- 未指定 `Domain` 时，默认只对该**设置它的父域**及子路径有效，不跨子域共享。
- 浏览器遵循**同站（Same-Site）**与**同源（Same-Origin）**规则决定是否发送。
  - **同源** = 协议 + 域名 + 端口 都相同。
  - **同站** = 仅要求**有效注册域 + 协议**相同（端口不参与）。

### 4. SameSite 的三种取值

`SameSite` 是前端安全里极其重要的一环，也是防御 CSRF 的重要手段：

| 值 | 行为 |
| --- | --- |
| `Strict` | 完全禁止第三方上下文携带 Cookie（跨站请求一律不带，最安全但体验可能受损） |
| `Lax` | 默认值。跨站**子资源或跨站表单 GET 提交**可带，跨站点 POST/iframe 不带。日常使用的最优解 |
| `None` | 允许跨站携带，**必须配合 `Secure`**（HTTPS）。第三方登录、SSO 场景才会用到 |

```http
Set-Cookie: session=xxx; SameSite=None; Secure
```

### 5. JS 侧读写与注意点

服务端设 `HttpOnly` 后，JS 无法读写该 Cookie。可写的部分可以通过 `document.cookie` 读写：

```js
// 读取（返回所有可读 Cookie 拼接成的字符串）
console.log(document.cookie);

// 写入（一次只能写一个，多个用分号隔开传参无效）
document.cookie = "theme=dark; Max-Age=2592000; Path=/";
```

> ⚠️ Cookie 容量非常小（**单条约 4KB，一个站点总量通常几十条**），且每次请求都会带上，浪费带宽。**不要用 Cookie 存大数据**，它只该承载会话标识这类短小数据。

## 二、localStorage 与 sessionStorage：同步的键值存储

### 1. 共同点

二者都属于 **Web Storage**，API 完全一致，都以**字符串键值对**方式存储，且只能存字符串（对象需序列化）：

```js
// 写入
localStorage.setItem("name", "张三");
localStorage.setItem("user", JSON.stringify({ id: 1, role: "admin" }));

// 读取
localStorage.getItem("name"); // "张三"
JSON.parse(localStorage.getItem("user")); // { id: 1, role: "admin" }

// 删除
localStorage.removeItem("name");
localStorage.clear();
```

还可以绑定事件监听跨标签页的变化（注意：只在本标签页打开时不会触发）：

```js
window.addEventListener("storage", (e) => {
  console.log(e.key, e.oldValue, e.newValue);
});
```

### 2. 区别

| 对比项 | localStorage | sessionStorage |
| --- | --- | --- |
| 生命周期 | 持久保存，除非手动清除或清浏览器缓存 | 生命周期限于**当前标签页/会话**，标签页关闭即消失 |
| 作用域 | 同源下所有标签页共享 | 同源且**同一标签页**内共享，新开标签页复制不出数据 |
| 是否随请求发送 | 不发送给服务端 | 不发送给服务端 |
| 典型场景 | 记住偏好、缓存业务字典 | 表单草稿、标签页内临时状态 |

### 3. 使用的常见限制与坑

- **同步阻塞**：`getItem`/`setItem` 是同步的，写入大量数据会阻塞主线程。
- **仅字符串**：存对象必须手动 `JSON.stringify` / `JSON.parse`，存在"存的是 `{}` 还是 `undefined`"的判断陷阱。
- **容量小且固定**：约 **5MB**（各浏览器略有差异），超出会抛 `QuotaExceededError`。
- **同步写入需要 try/catch**：隐私模式下可能被禁用而抛异常。
- **无法承载复杂查询**：只能按 key 读整条，不适合做结构化数据。

```js
try {
  localStorage.setItem("big", JSON.stringify(bigData));
} catch (err) {
  // QuotaExceededError：容量满了或隐私模式禁用
  console.error("存储失败", err);
}
```

## 三、IndexedDB：浏览器内置的事务型数据库

### 1. 它是什么

IndexedDB 是一个运行在浏览器里的**非关系型（NoSQL）对象数据库**，支持事务、索引、游标、异步读写，容量远大于前两者（通常可达几百 MB 到几 GB）。

核心概念：
- **数据库（Database）** → 一个域名下可建多个。
- **对象仓库（Object Store）** → 类比"表"，存放对象。
- **索引（Index）** → 为某个字段建立索引实现高效查询。
- **事务（Transaction）** → 读写的原子性单元。

### 2. 基本使用：打开数据库

```js
const request = indexedDB.open("my-db", 1);

request.onupgradeneeded = (event) => {
  const db = event.target.result;
  // 不存在则创建对象仓库，并指定主键与索引
  if (!db.objectStoreNames.contains("users")) {
    const store = db.createObjectStore("users", { keyPath: "id" });
    store.createIndex("byName", "name", { unique: false });
  }
};

request.onsuccess = (event) => {
  const db = event.target.result;
  console.log("数据库打开成功", db);
};
```

### 3. 增删改查

用事务包裹，基于主键或索引异步 CRUD：

```js
function addUser(db, user) {
  return new Promise((resolve, reject) => {
    const tx = db.transaction("users", "readwrite");
    const store = tx.objectStore("users");
    const req = store.add(user); // 新增
    // store.put(user);        // 更新或新增
    // store.delete(id);       // 删除
    // store.get(id);          // 按主键读取
    req.onsuccess = () => resolve(req.result);
    req.onerror = () => reject(req.error);
  });
}
```

按索引查询：

```js
function findByName(db, name) {
  return new Promise((resolve, reject) => {
    const tx = db.transaction("users", "readonly");
    const idx = tx.objectStore("users").index("byName");
    const req = idx.getAll(name); // 按索引取所有匹配项
    req.onsuccess = () => resolve(req.result);
    req.onerror = () => reject(req.error);
  });
}
```

### 4. 使用建议

- 原生 API 较繁琐，生产环境常用封装库：**Dexie.js**、**idb**。
- 适合存储**大量结构化数据**：离线笔记、聊天记录、音视频元数据、需要本地搜索的大字典。
- 结合其他存储一起用：本地缓存的"最后一层兜底"。

## 四、Web SQL：已被废弃的技术

**Web SQL** 是基于 SQLite 的浏览器关系型数据库规范，语法类似 SQL：

```sql
CREATE TABLE IF NOT EXISTS users (id INTEGER PRIMARY KEY, name TEXT);
INSERT INTO users (name) VALUES ('张三');
SELECT * FROM users;
```

但浏览器需要宿主内置 SQLite 才能实现，且规范存在严重分歧，早已被 **W3C 正式废弃（deprecated）**。主流浏览器均不再支持或逐渐移除。**新项目请勿使用，用 IndexedDB 替代。** 它只能作为历史知识，出现在面试或老项目迁移中。

## 五、各存储机制对比总表

| 维度 | Cookie | localStorage | sessionStorage | IndexedDB | Cache Storage | Web SQL |
| --- | --- | --- | --- | --- | --- | --- |
| 用途 | 会话标识 | 键值缓存 | 标签页内临时 | 结构化大数据 | 网络资源缓存 | 已废弃的关系型 |
| 容量 | ~4KB/条 | ~5MB | ~5MB | 百 MB~GB 级 | 较大 | — |
| 存储类型 | 字符串 | 字符串 | 字符串 | 对象/键值 | 请求-响应 | 表 |
| 同步/异步 | 同步 | 同步 | 同步 | **异步** | 异步 | 同步 |
| 是否随请求发送 | **是** | 否 | 否 | 否 | 否 | 否 |
| 事务支持 | 无 | 无 | 无 | **有** | 无 | 有 |
| 生命周期 | 按 Expires / 会话 | 持久 | 标签页关闭即清 | 持久 | 持久（受配额管理） | 持久 |
| 服务端可读 | 可 | 否 | 否 | 否 | 否 | 否 |
| 安全性 | 有 HttpOnly 等 | 可被 XSS 读 | 可被 XSS 读 | XSS 时相对安全 | 无针对 XSS 的访问控制 | — |
| 现状 | 活跃 | 活跃 | 活跃 | 活跃 | 活跃 | **废弃** |

## 六、适用场景怎么选

按需分层，给出一个直观的选择流程：

```text
需要服务端会话（登录态）？
  ├─ 是 → Cookie（尽量 HttpOnly + SameSite）
  └─ 否
需要随请求自动携带？
  ├─ 是 → Cookie
  └─ 否 ↓
数据结构是否复杂 / 数据量大？
  ├─ 是 → IndexedDB
  └─ 否 ↓
是否需要在标签页关闭后保留？
  ├─ 是 → localStorage
  └─ 否 → sessionStorage
```

配套的典型组合：

- **登录态**：`HttpOnly + SameSite=Lax` 的 Cookie（或短生命周期的 httpOnly token）。
- **用户偏好 / 字典 / 皮肤**：localStorage。
- **编辑中的表单草稿**：sessionStorage（关页即清，避免残留）。
- **离线笔记、缓存到本地的数据仓库**：IndexedDB。
- **静态资源/接口响应的缓存**：Cache Storage（配合 Service Worker）。

## 七、Service Worker 与网络缓存

### 1. Service Worker 是什么

**Service Worker（SW）** 是运行在浏览器独立线程里的**网络代理脚本**，能拦截页面的所有请求、自定义缓存策略，并实现**离线访问**与**后台同步**。

它的几个前提：
- 必须在 **HTTPS**（或 localhost）下运行。
- 从属一定的**作用域**（scope）。
- 生命周期独立于页面，`install` → `activate` → `fetch` 监听。

### 2. Cache Storage 缓存接口

配套的 `Cache Storage` 以"请求-响应"为单位缓存网络资源，与 localStorage/IndexedDB 都不同。

```js
// 打开一个名为 "static-v1" 的缓存
const cache = await caches.open("static-v1");

// 缓存一个或多个请求
await cache.addAll(["/", "/style.css", "/app.js"]);

// 匹配请求是否命中缓存
const response = await cache.match("/style.css");
```

### 3. 一个最简单的离线缓存 SW

```js
// sw.js
const CACHE_NAME = "blog-v1";
const PRECACHE = ["/", "/index.css", "/app.js"];

self.addEventListener("install", (event) => {
  // 预缓存静态资源
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => cache.addAll(PRECACHE))
  );
  // 新 SW 激活后接管页面
  self.skipWaiting();
});

self.addEventListener("activate", (event) => {
  // 清理旧版本缓存
  event.waitUntil(
    caches.keys().then((keys) =>
      Promise.all(
        keys.filter((k) => k !== CACHE_NAME).map((k) => caches.delete(k))
      )
    )
  );
  self.clients.claim();
});

// 拦截请求：命中缓存则返回，未命中再走网络并回填缓存
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      return (
        cached ||
        fetch(event.request).then((response) => {
          const clone = response.clone();
          caches.open(CACHE_NAME).then((cache) => cache.put(event.request, clone));
          return response;
        })
      );
    })
  );
});
```

### 4. 常见缓存策略

| 策略 | 含义 | 适用资源 |
| --- | --- | --- |
| **Cache First** | 有缓存用缓存，否则走网络 | 长期不变的静态资源（图片、字体） |
| **Network First** | 先网络，失败回退缓存 | 数据要求较新又需离线的页面 |
| **Stale-While-Revalidate** | 先返回旧缓存，后台静默更新 | 列表、次要接口 |
| **Network Only** | 只用网络 | 实时强一致数据 |

```js
// Stale-While-Revalidate 示例
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => {
      const network = fetch(event.request).then((resp) => {
        if (resp.ok) {
          const clone = resp.clone();
          caches.open(CACHE_NAME).then((c) => c.put(event.request, clone));
        }
        return resp;
      });
      return cached || network;
    })
  );
});
```

### 5. SW 的升级与注意事项

- SW 拥有独立的更新机制：浏览器检测到新 sw.js 时会触发新的 `install`，需配合 `activate` 里清理旧缓存并 `clients.claim()` 完成接管。
- 谨慎使用，**千万不要把敏感/个性化数据缓存成全体可见**。
- SW 还能做**消息推送（Push）**、**后台同步（BackgroundSync）**、**Web Push 通知**。

## 小结

- **Cookie** 适合"要随请求自动发送的短小会话数据"，注意 `HttpOnly`、`SameSite`。
- **localStorage / sessionStorage** 提供同步、约 5MB 的键值缓存，区别仅在**生命周期与作用域**。
- **IndexedDB** 是异步、支持索引与事务的结构化数据库，承载大数据量；前端用它做离线数据仓库。
- **Web SQL 已废弃**，不要在新项目中使用。
- **Service Worker + Cache Storage** 让前端具备离线能力，策略选择（Cache/Network First 等）取决于数据新鲜度要求。
