## 1. pnpm

### 1.1 npm 平坦树的两个后果

- npm 的平坦树按"每个包名一份顶层实体"摆放：同名包出现两个版本时，另一份嵌进依赖方自己的 `node_modules`；同一句 `require` 在根目录与嵌套处会命中不同版本。
- npm 还把传递依赖提升到顶层，未声明的 `is-number` 也能 `require` 成功。
- 危险不在"当前能跑"，而在依赖别人的安装结果：换个包管理器、升级上游、或顶层恰好换成别的版本，同一段代码就可能解析失败。

### 1.2 安装模型：全局 store、硬链接与符号链接

```
registry → 全局 store（内容寻址，一份文件） ──硬链接──> 项目 node_modules/.pnpm/<包>@<版本>/node_modules/<包>
                                                              ▲ 符号链接（Windows 是 junction）
                                                       node_modules/<包>
```

- 同一个包在磁盘上只存一份：多个项目的实体文件指向**同一 inode**，`nlink` 反映共享份数（store 一份 + 每个装过它的工程各一份）。
- `.pnpm` 目录名带版本，包自己的依赖挂在它旁边的 `node_modules`，所以不同版本可以并存、各自解析。
- 顶层 `node_modules/<包>` 只是链接，只有直接声明的依赖才会出现。
- store 与项目必须同盘才能硬链接，跨盘会退化为复制；`package-import-method` 可显式指定。

### 1.3 严格 node_modules 与幽灵依赖

- pnpm 顶层只放直接依赖；传递依赖在 `.pnpm` 私有区，源码解析不到，报 `MODULE_NOT_FOUND`，补上声明后恢复。
- 默认 `hoist=true` 只把依赖提升到 `.pnpm/node_modules` 私有区；`public-hoist-pattern` / `shamefully-hoist` / `node-linker=hoisted` 是三档逐级放宽的开关。
- pnpm 10+ 默认不执行依赖的生命周期脚本，靠 `onlyBuiltDependencies` 白名单放行。
- 判断严格性时工程要放在没有父级 `node_modules` 的干净路径，否则上层项目会把依赖"喂"进来。

### 1.4 构建 monorepo

- `pnpm-workspace.yaml` 声明 `packages/*`、`apps/*`；根 `package.json` 标 `private` 并写 `packageManager` 锁 pnpm 版本。
- 包间依赖写 `workspace:*`，安装后变成指向本地目录的符号链接，锁文件里是 `link:../utils`；本地改完即生效，不用发版。
- `--filter @lab/web...` 选中 web 及其全部依赖，按拓扑序执行（`utils → ui → web`）；`--filter ...@lab/utils` 反向选使用方；`-r` 全量执行，`--parallel` 放弃顺序。
- 日常管理都用 `--filter`：加依赖、删依赖、跑脚本、`pnpm why` 查来源；发布时 `workspace:*` 自动替换成真实版本号。

## 2. Vite

### 2.1 核心设计思想：dev 与 build 两套链路

```
dev   浏览器 import ──请求──> Vite Server ──转译──> 返回 ESM 源码（不打包）
build 从 index.html 入口 ──全量解析──> 依赖图 ──打包 / 分割 / 压缩──> dist
```

- **dev 处理"被请求到的模块"，build 处理"整个依赖图"**。dev 引擎是 esbuild（单文件转换）+ 依赖预构建；build 引擎是 Rolldown（8.x 起，兼容 Rollup 配置）。
- dev 侧维护**模块图**：一个 URL ↔ 一个模块节点，节点挂 `importers` / `importedModules`。它解释了冷启动快、HMR 快、`optimizeDeps.exclude` 的坑、以及"源码必须是 ESM"。
- 还有一个容易被忽略的约定：**Vite 的入口写在 `index.html` 里**，那句 `<script type="module" src="/src/main.ts">` 就是 entry；HTML 是构建起点，不是产物模板。

### 2.2 基础使用：配置 / 环境变量 / 资源 / CSS / 框架模板

- 五类配置：`root` + HTML（入口）/ `build.outDir` + `*FileNames`（出口）/ 内置 + 官方插件（转换）/ `plugins`（扩展）/ `manualChunks` + `minify`（优化）。
- 五个路径：`root`（默认 cwd）、`base`（默认 `/`，部署子目录要改）、`publicDir`（原样复制）、`build.outDir`（默认 `dist`）、`build.rollupOptions`（透传 Rollup / Rolldown）。`define` 替换代码文本，值必须 `JSON.stringify`。
- **环境变量**：`.env` / `.env.[mode]` / `.env.[mode].local` 按优先级叠加；`import.meta.env` 是**编译期静态替换**，只有 `VITE_` 前缀（`envPrefix` 可改）会暴露；不能动态拼 key。dev 下注入一行环境对象，build 后变成字面量。`h5-vite` 把读取收口到 `src/env.ts`，token 只从 `.env.local` 读（仓库只提交 `.env.local.example`）。
- 静态资源：默认按 `assetsInlineLimit` 决定内联；`?url` 强制 URL、`?raw` 取文本、`?inline` 强制内联、`?no-inline` 强制出文件；`public/` 下的文件原样复制、用 `/xxx` 引用。
- CSS：`import './a.css'` 抽成独立文件；`*.module.css` 是 Modules；装 `sass` / `less` 后直接 import；PostCSS 走 `postcss.config.js`；`?inline` 返回 CSS 文本；`cssCodeSplit` 让异步 chunk 的 CSS 随 chunk 加载。
- `.vue` 的编译只能靠官方 `@vitejs/plugin-vue`——"配置全手写"针对产物收尾，不是语言编译。
- **框架模板**：`create-vite` 每个框架一个模板族（vanilla / vue / react / preact / svelte / lit，各带 TS 变体）；差异在**各家的语言插件**——`@vitejs/plugin-vue` 编译 SFC 并生成 HMR accept 边，`@vitejs/plugin-react` 转译 JSX 并注入 Fast Refresh。语言编译是框架语义，交给官方插件，Vite 核心保持中立。

### 2.3 工程化与性能：预构建与缓存 / HMR / 分割压缩 / 产物分析

- **预构建**（`optimizeDeps`）：第三方包多是 CJS、且可能碎成几百个文件；提前转成单个 ESM 放进 `node_modules/.vite/deps`，一次解决"浏览器不认 CJS"与"请求瀑布"。`include` 显式声明扫不到的依赖，`exclude` 排除本地 workspace 包，`force` 忽略缓存重建。
- **依赖缓存两层别混**：server 侧在 `node_modules/.vite/deps`（hash 由 lockfile / patches / 配置依赖字段 / NODE_ENV 算出，任一变了才重新预构建）；浏览器侧靠 `?v=hash` 缓存戳 + `max-age=31536000, immutable`。排查旧依赖：删 `.vite` 再 `--force`。
- **HMR**：服务端只重转变更模块，通过 WebSocket 通知浏览器重新请求，耗时与项目规模无关；`import.meta.hot.accept` 声明边界，没有边界就向上冒泡，冒泡不到整页刷新；`dispose` 负责清理。
- **代码分割**：`manualChunks` 按模块 id 分组；路由 `() => import()` 自动切 chunk。**8.x 的坑：Rolldown 下 `manualChunks` 只接受函数形式**，写对象会报错。
- **压缩与兼容**：`build.minify` 默认 `'esbuild'`；`build.target` 默认按浏览器基线；tree-shaking 由 Rollup / Rolldown 完成，前提是 ESM + 包的 `sideEffects` 声明。
- 实测（`h5-vite`，五页 H5 接真实后端）：452 个模块、1.02 s，产物按来源拆 `vant` / `axios` / `vue` / 路由页面 / 入口，整包 gzip ≈ 147.1 kB，首屏 ≈ 135.5 kB；`vant` 一组占一半以上，是组件库的固定成本。注意分组以打包器的实际归属为准：Vue 运行时被归进了 `vant` chunk，`vue` chunk 里只有 `vue-router` 与 `pinia`。
- 四条命令：`dev`（默认 5173，按请求转换 + `/api` 代理）/ `build`（类型检查 + 写盘 `dist/`）/ `build:only` / `preview`（先 `build` 再托管真实产物，默认 4173，携带 `preview.proxy`）。
- **产物分析**：增量对比用 `rollup-plugin-visualizer`——构建后生成 treemap（`stats.html`），矩形面积即体积，可按 gzip 计算；面积大的包先看"用到了多少"，组件库该优化的是按需引入；持续盯增量把"量 gzip + 阈值告警"做成构建门禁（见 2.5 的 mini-size-gate）。

### 2.4 插件结构与排序

- 插件就是一个对象，唯一必填 `name`；钩子分**通用**（Rollup / Rolldown 兼容：`resolveId` / `load` / `transform` / `renderChunk` / `generateBundle`）与 **Vite 专有**（`configureServer` / `transformIndexHtml` / `hotUpdate` / `configurePreviewServer`）。
- **两条正交的轴**：归属决定"能不能换个工具复用"，生效端决定"什么时候触发"。`resolveId` / `load` / `transform` 两端都跑但含义不同——dev 只处理被请求的模块，build 处理整张图。
- 排序三层且只有中间一层跨插件：跨钩子天然有序；`enforce: 'pre' | 'normal' | 'post'` 跨插件排同一钩子；`order` 排同插件同一钩子的多个 handler。官方链：`alias → pre → vite core → normal → vite build → post → vite build post`。
- 门禁一律用 `apply: 'serve' | 'build'`，不要在钩子体内判 `command`——否则插件在另一端仍会被加载、`config` 仍会被调用。
- build 侧分工纪律：改 chunk 代码用 `renderChunk`；增删产物 / 出清单用 `generateBundle`；改 HTML 用 `transformIndexHtml`。**改代码在 `renderChunk`，动产物结构在 `generateBundle`**。

### 2.5 插件实战：四个钩子

- **mini-virtual**（`resolveId` + `load`）：认领 `virtual:build-info` 并提供源码。虚拟 id 用 `\0` 打头；`resolveId` 返回 `null` 表示"我不处理"；`configResolved` 缓存 `mode`，`load` 时内联成字面量。
- **mini-mock**（`configureServer`，`apply: 'serve'`）：中间件直接应答 `/api/*`。直接 `server.middlewares.use()` 是立刻挂（抢在内置中间件之前）；`return () => {...}` 是等内置中间件装完再调用——`/api/*` 的 404 必须放在靠前那个，否则会被 HTML 回退吞成 200。
- **mini-html**（`transformIndexHtml`，`apply: 'build'` + `order: 'post'`）：`ctx.bundle` 只有构建期才有，现读带 hash 的入口文件名补 `modulepreload`，**必须查重**——Vite 默认已注入，实测"补 0 条"；同时给 `<script>` 加 `nonce`。
- **mini-size-gate**（`generateBundle`）：按 **gzip** 称重、`emitFile` 出 `build-manifest.json`、`this.error` 超预算中断。清单进 CI 产物可 diff，`this.error` 让插件从"报告"变"门禁"。
- 四条插件与生态插件（`vite-plugin-virtual` / `vite-plugin-mock` / `vite-plugin-html` / `size-limit`）一一对应；语言编译用官方，产物收尾才值得自己写。

## 3. Webpack

### 3.1 核心概念：八个名词、五对象、Loader vs Plugin

```
入口 ──递归解析 import──> 模块图 ──按规则分 chunk──> 每个 chunk 包一层运行时 ──> assets
```

```
Compiler     一次 webpack 进程的入口，持有配置与钩子（只创建一次）
  └─ Compilation   一次具体编译的产物容器，模块、chunk、产物都挂在它上面
       ├─ Module   一个源文件（经过 loader 处理后的结果）
       ├─ Chunk    一组模块的集合（决定"哪些模块进哪个文件"）
       └─ Asset    最终写盘的文件（chunk 渲染后的结果）
```

- webpack 从始至终只做一件事：**先把整张图打进 bundle，再给浏览器**；dev server 只是把产物放在内存里，编译流程与生产一致。
- 八个名词各就各位：Entry（建图起点）/ Output（写到哪、叫什么）/ Module（loader 处理后的源文件）/ Chunk（模块集合）/ Bundle（chunk 渲染出的产物）/ Loader（转换单个文件的函数）/ Plugin（介入打包生命周期的对象）/ Mode（一组默认配置开关）。
- 这解释三个困惑：`stats` 模块数与文件数对不上（中间隔着 Chunk 分组）；改一个文件会重编译很多文件（模块变则所属 Chunk 全部重渲染）；plugin 能改什么（Compiler 钩子拿配置与整次编译，Compilation 钩子拿模块 / chunk / 产物）。
- 高频考点：**loader 管单个模块的源码，plugin 管整次编译的流程与产物**；loader 不能跨文件，plugin 能读写 `compilation.assets`。

### 3.2 基础配置：配置 / 环境变量 / 资源 / CSS

- 五类配置：`entry` / `output`（`path` / `filename` / `chunkFilename` / `publicPath`）/ `module.rules` + loader / `plugins` / `optimization`（splitChunks / minimize / runtimeChunk）。
- `mode` 不是"环境名"，是**一组默认配置的开关**：`production` 默认开压缩、作用域提升、`sideEffects` 分析，并通过内置 `DefinePlugin` 把 `process.env.NODE_ENV` 定成 `'production'`。
- 出口项决定长缓存：`[contenthash:8]` 内容变文件名才变；`chunkFilename` 管懒加载 chunk；`clean: true` 先清 `dist/`。
- **环境变量**：`process.env.NODE_ENV` 由 `mode` 自动注入；自定义变量必须用 `DefinePlugin`（值要 `JSON.stringify`，没有前缀闸门，不能动态拼 key）。`h5-webpack` 自己写 `loadEnvFiles(mode)` 读 `.env` / `.env.<mode>` / `.env.local`（只取 `VITE_`），再注入**一个** `__ENV__` 对象；业务侧 `src/env.ts` 是唯一读取点。
- 静态资源用 asset modules：`asset/resource`（出文件）/ `asset/inline`（data URL）/ `asset/source`（原文本）/ `asset`（按 `maxSize` 自动二选一），分别对应旧的 `file-loader` / `url-loader` / `raw-loader`。
- CSS：`MiniCssExtractPlugin.loader` + `css-loader` 抽离（生产推荐）、`style-loader` 运行时注入；`css-loader` 的 `modules: true` 开 CSS Modules；`sass-loader` / `less-loader` / `postcss-loader` 依次加在 `use` 链尾。Vant 的函数式组件样式（toast / dialog）要手动 import。
- Vue + TS 五处必配：`resolve.extensions` 加 `.mjs`（Vant 的 ESM 入口）与 `.vue`、`vue-loader` 编译 SFC、`ts-loader` 开 `transpileOnly` + `appendTsSuffixTo`（类型检查交给 `vue-tsc`）、`VueLoaderPlugin` 把 `.css` 规则克隆到 `<style>` 请求、`DefinePlugin` 把 `__VUE_OPTIONS_API__` 等开关定成字面量。
- 三个命令：`dev`（5185，内存产物 + HMR + `/api` 代理）/ `build`（类型检查 + 写盘 `dist/`）/ `preview`（同 5185，仍是内存产物；验证真实 `dist/` 用任意静态服务器）。

### 3.3 性能优化：分割 / 缓存策略 / tree-shaking / devServer 与 HMR

- `runtimeChunk: 'single'` 把运行时单独成文件，业务 chunk 的 hash 不因运行时变化而全部失效。
- `cacheGroups` 按来源切四组：`vant`（priority 30）/ `axios`（20）/ `vue`（`vue|@vue|pinia|vue-router`，10）/ `vendor`（兜底，1），`chunks: 'all'` 保证懒加载里的依赖也被抽出；**最终归属由打包器决定**，cacheGroup 表达的是"我希望怎么分"。
- 分割点三处：cacheGroup、动态 `import()`、魔法注释——`webpackPrefetch: true` 面向"将来"（空闲时预取，下次导航秒开），`webpackPreload: true` 面向"现在"（当前导航立即并行下载）。
- 路由 chunk 名靠 `/* webpackChunkName: "list" */`：不加是 `100.js` 这类数字名，加了就是 `list.js` / `detail.js` / `stats.js` / `mine.js` / `edit.js`（新增与编辑共用一个 chunk）。
- **三种 hash 粒度**：`[hash]` 整次构建全局同（改一个文件全废）> `[chunkhash]` chunk 内共享 > `[contenthash]` 只看文件自身内容（产物命名的正确选择）；配 `runtimeChunk: 'single'` 让业务 chunk 与运行时解耦。
- **持久化缓存**：`cache: { type: 'filesystem', buildDependencies: { config: [__filename] } }`，production 要显式开；命中后只重建变更模块，二次构建快一个数量级。webpack 4 时代的 `cache-loader` / DllPlugin 由此退场。
- tree-shaking 三个条件同时成立：**ESM**、包的 **`sideEffects` 声明**、**`minimize: true`**（`usedExports` 只标记，真正删除靠压缩器）；纯函数调用加 `/*#__PURE__*/`。
- 其他优化：`externals` + CDN 排除大依赖（失去按需引入，慎用）；`devtool` 生产 `false`、dev `eval-cheap-module-source-map`；`performance.hints: false` 关 244KB 告警——关提示不等于没体积问题，应用门禁。
- **HMR 是模块粒度热替换，不是全量刷新**：watch 重编译受影响模块 → WebSocket 推 manifest（新 hash）→ runtime 用 JSONP 拉更新 chunk → 沿模块图找 `module.hot.accept` 边界执行替换，找不到就 `location.reload()`。
- 实测（`h5-webpack`，五页 H5 接真实后端）：18 个产物 / 708 个模块 / ≈ 7 s，整包 gzip ≈ 158.7 kB、首屏 ≈ 123 kB；`vue` 组 111.6 kB 是因为 Vue 运行时与 `vue-router` / `pinia` 同组，`vant` 是组件库的固定成本。

### 3.4 版本差异：webpack4 vs webpack5

- **持久化缓存**：webpack 4 靠 `cache-loader` / `hard-source-webpack-plugin` 民间方案，webpack 5 内置 `cache.type: 'filesystem'`——"老项目构建慢"的标准答案从 DllPlugin 变成开缓存。
- **Asset Modules**：webpack 4 要 `file-loader` / `url-loader` / `raw-loader` 三件套，webpack 5 内置四种 `type`。
- **移除 Node polyfill**：webpack 4 自动注入 `crypto` / `process` / `buffer`（node-libs-browser），webpack 5 不再自动——前端用到要在 `resolve.fallback` 显式给包，升级后报 `Can't resolve 'crypto'` 先查这里。
- 其他：tree-shaking 更强（嵌套属性、CommonJS 部分）、Module Federation（跨应用模块共享）。

### 3.5 Loader 原理：本质 / pitch / loader-runner / 手写

- loader 的全部秘密一句话：**输入源码字符串，输出代码字符串**——返回的是代码文本不是值，想导出字符串要自己 `JSON.stringify` 拼进代码。分类：**同步**（直接 `return` 或 `this.callback`）、**异步**（`this.async()` + `callback`，适合 IO）、**pitch**。
- 两个阶段方向相反：**pitch 从左往右**先跑，**normal 从右往左**执行；`use: [extract, css]` 里 `css` 先执行 normal，`extract` 后执行。pitch 返回了值会**跳过剩余链**直接回卷。
- **loader-runner**：webpack 执行 loader 的逻辑被单独抽成的包，可脱离 webpack 单独跑——写 loader 调试器、做 loader 单测、研究 pitch 顺序都用它。
- **手写最简同步 loader：markdown-loader**——`.md` 编译成 `export default 'HTML 字符串'` 的 JS 模块；三个要点：输出必须是 JS 代码文本不是渲染结果、先 escape 再匹配、用 `JSON.stringify` 生成合法字符串字面量。
- **css-loader** 做两件事：递归内联 `@import`（并 `ctx.addDependency` 登记依赖）、把相对 `url()` 改写成 `require()`（保留 `url(...)` 包装，只把资源地址换成运行时插值）。
- **extract-css-loader 必须用 pitch**：轮到 normal 阶段时 `source` 已是 css-loader 产出的 JS 代码；pitch 用 `this.importModule('!!' + remainingRequest)` 在构建期跑后面那条链、拿回 CSS 导出，登记到 `compilation.__miniCss`，再返回占位模块 `export default undefined`。
- 生产为什么"抽离"不"注入"：抽离的 `.css` 随 HTML 并行加载无 FOUC、有独立 `contenthash` 单独命中缓存；注入要等 JS 执行完、CSS 变了 JS 文件名也变。
- SFC 的 `<style>` 变成带 `?vue&type=style` 的请求，匹配不上 `test: /\.css$/`——`VueLoaderPlugin` 把每条规则克隆成带 `?vue` 的版本，SFC 样式自动走同一条手写链（实测汇总 3 个模块）。

### 3.6 Plugin 原理：Tapable / Compiler / stage / 手写最简插件

- plugin 是带 `apply(compiler)` 的对象；钩子由独立的 **Tapable** 库提供，类型决定多回调怎么执行：`SyncHook`（按序）、`SyncBailHook`（返回非 `undefined` 停）、`SyncWaterfallHook`（返回值传下一个）、`AsyncSeriesHook`（异步串行）、`AsyncParallelHook`（异步并行）。
- `compiler.hooks.*` 覆盖整个进程，`compilation.hooks.*` 覆盖一次编译。时间线口诀：**先配入口（entryOption），再开始编译（compile），从入口长出依赖图（make），长完封包（seal），定稿写盘（emit），写完收工（done）**。
- 产物阶段几乎都挂 `processAssets`，靠 `stage` 排队：`ADDITIONS(-100)` 产出 CSS → `OPTIMIZE_SIZE(400)` 压缩 → `SUMMARIZE(1000)` 生成 HTML；顺序即依赖关系，填错会出现"HTML 引用压缩前的旧文件名"。
- **MiniCssExtractPlugin**：读 `compilation.__miniCss` 拼成 `.css`，手算 md5 填 `[contenthash:8]`，`emitAsset` 产出——**loader + plugin 两段式**（loader 管单模块登记，plugin 管跨文件汇总）。
- **MiniTerserPlugin**：`OPTIMIZE_SIZE` 阶段过 terser 再 `updateAsset`；此时文件名按压缩前内容算，最终名以 stats 为准。
- **MiniHtmlPlugin**：`SUMMARIZE` 阶段从 `entrypoint.getFiles()` / `compilation.assets` 现读带 hash 的最终文件名拼进模板；JS 顺序取自 entrypoint（保证 `runtime` 在 `main` 之前），CSS 从 assets 筛。
- **手写最简插件 · 清目录（MiniCleanPlugin）**：挂 `compiler.hooks.emit`——产物已定稿未写盘的窗口；拿 `compilation.assets` 的 key 做白名单，把输出目录里不在清单上的旧 hash 文件删掉再收缩空目录。本 lab 故意 `clean: false` 用它验证机制。
- **手写最简插件 · 注入全局变量（MiniDefinePlugin）**：往每个 `.js` 产物头部插一行 `window.__APP_VERSION__ = "1.0.0"`。灵魂是同时 tap **`chunkHash`**——contenthash 在 processAssets 前就算完了，只改内容文件名 hash 不变，必须把注入内容算进 hash 才能触发缓存更新（官方 BannerPlugin 同款解法）。
- 纪律：新增产物用 `emitAsset`、覆盖已有产物用 `updateAsset`，不要 `fs.writeFileSync`——否则不参与 `output.clean`、不进 stats、不跟随 watch。
