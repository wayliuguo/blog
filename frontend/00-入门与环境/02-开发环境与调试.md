# 开发环境与调试（入门→进阶→实战→最小实现原理）

> 级别：初级（含进阶）

工欲善其事，必先利其器。本章是整套体系的「工具起点」，按本书主线四层组织：

- **入门使用**：把浏览器、编辑器、Node、Git、包管理器装好，会开 DevTools 六个面板；
- **进阶**：调试、Git、包管理三块往深走一层，跨过「会用」；
- **实战**：串一条完整闭环——从零搭环境 → 建 Vite 项目 → Git 分支协作 → 用 DevTools 定位并修复一个真实 Bug；
- **最小实现掌握原理**：手写最小 DevServer、理解 HMR、认清 Git 提交本质与包解析原理，并对应 90-附录面试自测。

读完全章，你的电脑就是一台「能跑、能查、能协作、懂原理」的前端开发机。

# 第一层 · 入门使用

先把环境跑起来。目标：**能创建项目、能启动、能看报错**即可。

## 1. 浏览器：第一前线

前端代码最终在浏览器运行。选择标准：

- **Chrome**：市场占有率最高、DevTools 最成熟，前端事实标准，主用。
- **Microsoft Edge**：同为 Chromium 内核，能力基本一致，国内访问更方便，可作备用。
- **Firefox**：性能与 DevTools 优秀，偶用于跨浏览器兼容校验。

```text
配置建议
- 默认用无痕窗口开发（避免缓存干扰调试）。
- 记住打开 DevTools 快捷键：F12 / Ctrl+Shift+I（Mac 为 Cmd+Option+I）。
```

核心概念：同一款浏览器在不同系统/版本渲染可能有差异，发布前记得做常见浏览器与移动端兼容检查。

## 3. Node.js + 版本管理器 nvm

前端依赖构建工具、脚本、SSR 都需要 Node。**推荐用 nvm 管理，可随项目切换版本，避免冲突**：

```bash
# Windows 用 nvm-windows；以下命令通用
nvm install 20      # 安装 Node 20
nvm use 20          # 切换使用
nvm use --lts       # 切到长期支持版

node -v            # 验证：打印 Node 版本
npm -v             # 验证：打印 npm 版本
```

打开终端输入 `node` 进入 REPL，这是你第一个可交互的 JS 运行环境，随手敲两句感受一下。

## 4. Git：版本与协作基石

核心概念一句话表：

| 概念 | 一句话解释 |
| --- | --- |
| 工作区 | 你当前能看到、在改动的文件 |
| 暂存区（index） | 通过 `git add` 把改动暂存 |
| 本地仓库 | 通过 `git commit` 提交为版本快照 |
| 远程仓库 | GitHub / GitLab 上共享的仓库 |
| 分支（branch） | 并行开发的线，`main` 为主分支 |

最常用命令：

```bash
git init                            # 初始化仓库
git status                          # 查看状态
git add .                           # 暂存所有改动
git commit -m "feat: 新增登录功能"    # 提交（message 写清做了什么）
git branch                          # 查看分支
git checkout -b feature/login       # 新建并切到分支
git merge feature/login             # 合并分支到当前
git push origin main                # 推到远程
git pull                            # 拉取远程最新
git log --oneline                   # 查看提交历史
git clone <仓库地址>                  # 克隆远程到本地
```

> 常用提交前缀：`feat` 新功能、`fix` 修复、`docs` 文档、`style` 样式、`refactor` 重构、`chore` 杂项、`test` 测试。规范提交信息也是专业素养。

## 5. 包管理器：npm / yarn / pnpm

负责下载、管理、共享依赖：

- `npm`：Node 自带，最基础。
- `yarn`：早期为性能和确定性而生。
- `pnpm`：性能与磁盘最优，硬链节空间、依赖隔离更安全，**新项目推荐**。

```bash
# npm
npm install          # 装 package.json 依赖
npm install axios    # 装某个包
npm run dev          # 运行 dev 脚本

# pnpm（推荐）
pnpm add axios
pnpm run dev
```

用 Vite 脚手架秒建一个项目，验证环境是否就绪：

```bash
pnpm create vite my-app --template vue
cd my-app
pnpm install
pnpm dev            # 启动，浏览器打开终端打印的地址即成功
```

## 6. DevTools 六个面板（第一遍）

快捷同上。先知道每个面板干嘛，进阶层再深挖：

| 面板 | 用途 |
| --- | --- |

> **入门验收**：能用 Vite 新建并启动一个项目；能在 Console 打印日志、在 Elements 改一个样式、在 Network 看到请求。

# 第二层 · 进阶

把「会用」升级成「会查、会协作、会不踩坑」。三块各往深一步。

## 7. 调试进阶

### 7.1 断点的三种「瞄准镜」

入门只会打断点暂停。进阶要能**在正确的位置命中**：

- **条件断点**：只在满足条件时暂停，避免无效断点。在断点上右键 → Add conditional breakpoint，例如 `idx === 5`。
- **DOM 断点（Break on）**：在 Elements 选中元素 → 右键 → Break on → 子树修改 / 属性修改 / 节点移除。适合排查「谁偷偷改了这个节点」。
- **XHR/fetch 断点**：在 Sources → XHR/fetch breakpoints 添加 URL 片段，命中后再看调用栈。

### 7.2 逐步执行四键 + 观察变量

```text
Step Over（F10） 执行当前行，不进内部函数
Step Into（F11） 进入函数内部
Step Out（Shift+F11） 跳出当前函数
Resume（F8）    继续到下一个断点
```

在 **Scope** 看作用域变量、**Watch** 添加想持续观察的表达式；在 **Call Stack** 从「被调用的函数回到调用处」，这是看懂报错堆栈的关键动作。

### 7.3 console 高阶 API

```js
console.log("普通")
console.warn("警告")                // 黄色
console.error("报错")               // 红色，样式可自定义
console.table(users)                // 表格展示数组/对象
console.time("loop"); /* ... */ console.timeEnd("loop")  // 统计耗时
console.trace("栈")                 // 打印调用栈，排查“谁调用的我”
```

## 8. Git 进阶

### 8.1 撤销的三种「后悔药」（务必分清）

| 你指的命令 | 撤销对象 | 结果 |
| --- | --- | --- |
| `git restore <file>` | 工作区改动 | 放弃未暂存改动（不碰提交历史） |
| `git restore --staged <file>` | 暂存区 | 已 `add` 的移出暂存，文件不变 |
| `git reset --soft HEAD~1` | 最近一次提交 | 撤销提交但保留改动在暂存区 |
| `git revert <commit>` | 已推送到远端的提交 | 新增一个反向提交，**不改历史，协作安全** |

> 经验法则：**本地未推送**用 `reset`（清爽）；**已推送到远端**用 `revert`（不破坏他人历史）。

### 8.2 分支与合并：解决冲突

```bash
git checkout -b feature/a     # 新建分支
# ... 与 main 都改了同一处，merge 时会冲突
git checkout main
git merge feature/a
# CONFLICT：编辑器里保留两个版本中你要的部分，删掉 <<<<<<< ======= >>>>>>> 标记
git add . && git commit       # 解决后提交即完成合并
```

冲突本质：**两个分支都改了同一行/同一文件**，Git 不知道留哪个，交给你裁决。这不恐怖，是协作常态。

### 8.3 stash 与 rebase

```bash
git stash            # 临时保存未提交改动，让工作区干净
git stash list       # 查看
git stash pop        # 恢复最近一次
git rebase main      # 把当前分支的提交“重放”到 main 最新之上，线性历史
```

`rebase` 让历史更线性（好看易读），但**不要对已推送到远端的提交 rebase**。

## 9. 包管理进阶

### 9.1 语义化版本与 lock 文件

版本号 `主版本.次版本.修订号`：

```text
"^3.4.0"  允许补丁+次版本（不跨主版本）   （pnpm install 后生成 lock）
"~3.4.0"  仅允许补丁
"3.4.0"   精确锁定
```

`package-lock.json` / `pnpm-lock.yaml` 记录**精确地依赖树**，保证同一份代码在任何人机器上装出相同版本（可复现性）。所以 **lock 文件必须提交到 Git**。

### 9.2 为什么 pnpm 更省空间、更安全

- **省空间**：所有包放进一个全局 store，靠**硬链接**被多个项目共享，不重复下载；
- **更安全**：默认「符号链接隔离」——你只能直接引用 `package.json` 里声明的包，装 `a` 时不会意外撞上 `a` 的依赖 `b`（避免幽灵依赖）。

# 第三层 · 实战：一条完整闭环

把前面拆开的能力，串成一个真实场景：**从零搭环境 → 建项目 → 首次分支协作 → 用 DevTools 定位并修复一个真实 Bug**。

### 场景设定

你在第一阶段（纯 HTML/CSS/JS）做的一个「待办列表」页面，部署后发现「点击删除按钮没反应」，同事说他也复现了，怀疑是某处报错。你需要在分支上定位并修复，提交后合回主分支。

**第 1 步：确认环境就绪**
开 VS Code，用 Live Server 打开页面；打开 DevTools（F12）。

**第 2 步：看 Console 定位现象**
Console 出现 `Uncaught TypeError: removeTodo is not a function`，对应一句代码。点右侧文件名/行号跳转到 Sources。

**第 3 步：打断点逐步执行**
在调用处打断点 → 刷新 → 单步进入，观察 `this` 上下文。发现 `removeTodo` 定义在闭包内另一个作用域，`onclick` 里 `this` 被指向了按钮元素——**经典 this 丢失问题**。

**第 4 步：用最小改动修复并验证**
把 `onclick="removeTodo(1)"` 改为 `onclick="btnRemove(1)"`（或绑定正确的引用），刷新确认删除正常。Console 无报错，Network 中能对应到数据请求。

**第 5 步：Git 分支协作闭环**
```bash
git checkout -b fix/remove-todo     # 不在 main 主干上直接改
git add .
git commit -m "fix: 修复待办删除 this 丢失问题"
git checkout main
git merge fix/remove-todo           # 无冲突（单提交小改动）
```

> **本轮实战验收**：你能独立完成「报错阅读 → 断点定位 → 最小修复 → 分支提交合并」的完整链路。这已经是不少初级岗位的日常了。

# 第四层 · 最小实现掌握原理

光会点「pnpm dev」还不够。用几十行手写一个最小版，真正理解它后台在干什么。

## 10. 手写一个「最小 DevServer」：它到底做了什么

`pnpm dev` 背后的 Vite 本质是一个 **HTTP 静态文件服务器 + 文件监听刷新**。我们手写一个看懂核心：

```js
// dev-server.js —— 最小实现：静态服务 + 改动后通知浏览器刷新
const http = require("http");
const fs = require("fs");
const path = require("path");

const ROOT = process.cwd();

http.createServer((req, res) => {
  if (req.url === "/") {                       // 首页返回 index.html
    res.setHeader("Content-Type", "text/html");
    res.end(fs.readFileSync(path.join(ROOT, "index.html")));
    return;
  }
  const file = path.join(ROOT, req.url);        // 其他路径按文件返回
  res.end(fs.readFileSync(file));
}).listen(3000, () => console.log("serving on :3000"));

// 文件变化时向浏览器发一个 SSE 事件，浏览器收到就 location.reload()
const es = require("events");
const bus = new es.EventEmitter();
fs.watch(ROOT, (_, name) => bus.emit("change", name));
// 结合 <script> 里 new EventSource('/__reload') 监听即可实现“保存即刷新”
```

**一句话原理**：DevServer = 「把文件按 URL 发出去」的 HTTP 服务 + 「文件变了通知浏览器重取」的文件监听。所谓 HMR（热替换）只比这个更进一步：浏览器收到变化后**只替换变更的模块、保留页面状态**，而不是整页刷新。

## 11. 认清 Git 提交的本质：快照 + 指针

很多人以为 Git 存的是「差异」，其实 Git 每次提交存的是 **整个项目的快照**，再用指针串成时间线：

```
       快照A(old)          快照B           快照C(new)
main  o ---------------> o ---------------> o
      ^ HEAD             （每个快照存全部文件的实际内容，重复文件用哈希去重）
```

- `git commit` 生成了一个指向新快照的提交对象；
- `branch` 只是一个「指向某次提交的移动指针」；
- `HEAD` 是「当前你在哪个分支」的指针。

所以 `git reset` 只是**把某个指针往回移**，快照对象没删——这也是「后悔药」能救回的根本原因。

## 12. 手写一个包解析最小实现：包管理器装的是什么

`node_modules` 里无非是「把一个包名解析成真实文件，再拿给代码 require」。最小理解：

```js
// 最小“安装器”：把 index.js 内容复制到 node_modules 下，实现‘装包’
// my-lib/index.js
const hello = () => "hello from lib";
module.exports = { hello };

// 消费方
const { hello } = require("./node_modules/my-lib/index.js");
console.log(hello()); // hello from lib
```

真实 npm/pnpm 做的三件事在这之上：
1. **解析**：把 `my-lib` 映射到 `node_modules/my-lib/index.js`（package.json 的 `main` 字段）；
2. **下载与缓存**：去 registry 拉包，全局 store 缓存，硬链接共享（pnpm 省空间的由来）；
3. **依赖树**：按 lock 文件装出**完全相同**的一棵树，保证可复现。

## 小结

- 环境 = 浏览器(Chrome/Edge) + VS Code + Node(nvm) + Git + 包管理器(pnpm)。
- DevTools 六大面板中，Elements / Console / Sources / Network 是日常主力。
- 调试核心 = 打断点 + 逐步执行 + 观察变量；进阶用条件/DOM/XHR 断点精准命中。
- Git 冲突 = 双方改同一处，交给人工裁决；本地用 reset、已推送用 revert。
- pnpm 省空间因全局 store + 硬链接；lock 文件必须进仓库保证可复现。
- 手写最小 DevServer 后你会明白：dev 服务 = 静态 HTTP 服务 + 文件变更通知，HMR 只是模块级热更。
