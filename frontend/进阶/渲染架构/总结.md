# 模块总结 · 渲染架构

## 知识主线

三篇是一条从「坐标系」到「机制」再到「新范式」的链：

```
01 渲染方案全景（同一份页面代码的五种交付方式：CSR / SSR / SSG / ISR / 流式 + 选型决策树）
        │  先建立坐标系：差别不在"渲染"，而在"字符串在哪一刻生成、何时交给浏览器"
        ▼
02 SSR 与同构实现（同构的三条约束 / 服务端那份账 / 注水数据 / hydrate 的失配代价 / 流式的边界）
        │  把坐标系里最常用的那个点拆开：它耗在哪、交接要赔多少、流式提前了什么又没提前什么
        ▼
03 新兴渲染范式（Islands / RSC / 选择性注水与 PPR / 边缘渲染）
           拆掉前两篇的默认值：整页接管、整棵树注水
```

本模块的主轴是**同一个页面的代价分配**。01 给出完整坐标系——首屏要等几条腿、服务端背多少账、客户端下载多少 JS；02 把「SSR + 同构」这条主流路径拆到机制层，并把每一笔代价量化（服务端 266ms 每次都逃不掉、注水数据占 HTML 的 22.3%、一处文本失配静默改写 8 个节点）；03 则是四个**拆默认值**的方向：岛化拆掉「客户端要认识整棵树」（实测少下载 42.8% 的客户端 JS），RSC 拆掉「整棵树的 props 都要下发」，选择性注水拆掉「注水必须一次完成」，边缘渲染拆掉「渲染必须在源站」。

本模块与其它模块的分工：**指标口径与测量工具见性能优化模块**（本篇只解释数字怎么来的）；**HTTP/2、HTTP/3、CDN 与缓存的协议层细节见网络与协议进阶模块**（本篇只在「边缘渲染」一节引用它的结论）；**虚拟 DOM、diff 与更新的实现见前端框架原理模块**（本篇只用最小 vdom 支撑实验，不展开算法）；**浏览器从 HTML 到首个像素的完整流程见基础板块的网络与浏览器模块**。

全部数字来自 `frontend/进阶/渲染架构/code/render-lab`：零依赖、手写最小 vdom 与三套渲染出口，用无头 Chrome 与原生 `http` 客户端现场测量，七个 mode（`csr` / `ssr` / `ssg` / `isr` / `stream` / `island` / `hydrate`）共用同一份路由表，`npm run all` 可一次跑完并校验。

## 分篇知识点

### 01-渲染方案全景

- 交付方式的差别不在渲染，在「字符串何时生成、何时交给浏览器」
  - CSR：浏览器渲染，内容靠 JS 拉；SSR：每次请求服务端渲染；SSG：构建时渲染一次
  - ISR：SSG + 过期时间 + 后台重建；流式：已就绪的部分先发
  - 实测（`jslag=300`）FCP：CSR 2192ms · SSR 504ms · SSG 404ms · 流式 388ms
- CSR 的首屏由网络与解析决定，不由渲染决定
  - 首屏四段：HTML 到达 → JS 下载解析 → 接口往返 → 建 DOM；实测建 DOM 只占个位数毫秒
  - 网络条件从 `jslag=0` 换成 `jslag=300`，CSR 的 FCP 从 640ms 涨到 2192ms，其它三种基本不动
  - 骨架屏只把 FCP 提前，不改变内容到达的时刻
- SSR 的代价在服务端，不在浏览器
  - 连发三次响应头到达 273/279/278ms，一次都没省下
  - 整页耗时绑定最慢的接口（`loadAll` 并发后取更慢的那个，260ms）
  - 产物体积：标记 4.1KB + 注水数据 1.2KB，数据占 22.3%
- SSG 与 ISR 是把渲染挪到请求路径之外
  - SSG 响应头 3~4ms（本机导航固定开销约 100ms 之外近乎为 0）
  - ISR 四态实测：回源 266ms · 命中 2ms · 过期返回旧内容 4ms（后台重建）· 重建后命中 1ms
  - ISR 的取舍问两句：内容错了有没有损失、旧内容能忍受多旧
- 流式把「看得见」提前，不把「点得动」提前
  - 壳 17ms 发出、整页 290ms 完成；浏览器侧 FCP 340ms vs 非流式 508ms
  - 代价：HTML 从 5.3KB 涨到 6.5KB
  - 入口模块执行时刻几乎不变（1650ms vs 1679ms）—— 注水数据要等最后一个边界
  - 补位顺序由「谁先好」决定：推荐位 130ms 先于评价 260ms 补位
- 选型按四个问题走
  - 要不要被抓 → 要就打掉 CSR；内容变不变 → 不变就 SSG；能不能旧 → 能就 ISR
  - 有没有慢数据源 → 有且区块多就流式；只有一小块动态就 PPR / 岛化
  - 交互密度高不高 → 高就接受全量注水，低就岛化

### 02-SSR 与同构实现

- 同构是「一份页面树两端渲染」，前提是树必须是纯描述
  - 组件两端可跑、渲染期无副作用；数据必须先于渲染就位；客户端要能重建出完全相同的树
  - 收益是结构只写一次，代价是上述三条约束贯穿整个工程
- SSR 的耗时绑定最慢的数据源，服务端反而更累
  - 实测连发三次响应头到达 266 / 275 / 275 ms，一次都没省下（渲染只占个位数毫秒）
  - `Promise.all` 并发取数，整体耗时等于更慢的那个（评价 260ms 决定一切）
  - SSG 服务端耗时 0ms、ISR 命中 1~2ms —— 省掉的正是 SSR 每次都逃不掉的那一段
- SSR 的产物是 HTML + 数据，注水数据是隐性成本
  - 实测标记 4.1KB + 数据 1.2KB，数据占 22.3%，同标记下发数据后体积涨 29.5%
  - 数据与入口模块都放在文档尾：内容先到、脚本后到
  - `renderToString` 产物里没有任何事件监听器，事件是客户端接管时挂的
- hydrate 的成本由失配决定，且失配不一定报错
  - 四种情形的（复用/新建/丢弃/改写/失配）实测：一致 97/0/0/0/0 · 价格口径 97/0/0/8/0 · 标签不一致 83/2/14/2/1 · 直接重建 0/97/97/57/0
  - 文本不一致只静默改写（`characterData` 8 次），标签不一致才整段重建（丢弃 14）
  - 真实 DOM 突变次数：一致 0 次，这才是要卡的硬指标
  - 对齐单位是容器的 `childNodes`，不是容器自己 —— 少这一层会导致整棵树从根错位
  - 经典失配来源：时区、货币与数字格式化、日期格式、随机数、不稳定排序
- 流式把「看得见」提前，不把「点得动」提前
  - 服务端壳 3ms 发出、整页 266ms 完成；首个内容字节比非流式早 261ms
  - 浏览器侧 FCP 340ms vs 508ms，商品列表 235ms vs 399ms
  - 代价是 HTML 从 5.3KB 涨到 6.5KB（占位、template、补位脚本、运行时）
  - 入口模块执行时刻几乎不变（1650ms vs 1679ms）—— 注水数据要等最后一个边界
  - 补位顺序由「谁先好」决定（推荐位 130ms 先于评价 260ms）
  - 分段边界画在数据来源上，不画在组件层级上

### 03-新兴渲染范式

- 岛化拆掉的是「客户端要认识整棵树」这个默认值
  - 全量 hydration 实测：14 文件 16.4KB，97 个节点，但只挂 1 个监听器 —— 96 个节点的代码在陪跑
  - 岛激活：6 文件 9.4KB，少下载 7.0KB（整份客户端的 42.8%），监听器数量与按钮行为完全相同
  - 省的是业务代码，不是运行时：`vdom` + `hydrate` 共 5.5KB 的地板价岛化省不掉
  - 入口开始执行 1643ms vs 1631ms —— `jslag` 下模块并发下载，决定时刻的是依赖链段数而非总字节；字节优势要等带宽成瓶颈才变成时间优势
- 岛的实现有两个必须做对的地方
  - 标记落在子树**自己的根元素**上，多套一层会导致整棵子树失配重建
  - 注册表只放交互组件：页面里没有的组件不进图谱，代码也就不下载
  - props 序列化进属性时 `<` 要转义成 `\u003c`，防 `</script>` 提前闭合
- RSC 改的是「组件在哪一侧求值」（原理，无实测）
  - SSR 下发整棵树的 props；RSC 只下发客户端组件那部分，服务端组件代码不进客户端包
  - 解决的是注水数据随组件树增长的成本（第 2 篇实测占比 22.3%）
  - 代价是「两类组件」的写法与心智负担；交互密集页面无收益；不替代 SSR
- 选择性注水与 PPR 补的是流式留下的缺口（原理，无实测）
  - 流式把 FCP 提前 168ms，但 TTI 几乎不动（1650ms vs 1679ms）
  - 选择性注水按交互意图给区域插队，把 TTI 与「最后一个慢区块」解耦
  - PPR：静态骨架构建时生成、动态洞流式补，TTFB 走 SSG、完整性走 SSR
- 边缘渲染缩短的是传输，不是计算（原理，无实测）
  - 计算与取数照旧，若数据仍要回中心查，省下的只是传输那段
  - 与 SSG / PPR 天然搭配：能在边缘渲染的前提是不依赖只能在中心访问的数据
  - 边缘渲染 ≠ CDN 缓存：前者在边缘执行逻辑、可按请求差异化，后者是共享同一份产物
