## 1. 渲染方案全景与选型

### 1.1 同一问题的取值：HTML 何时生成、何时交给浏览器

CSR / SSR / SSG / ISR / 流式 / RSC / 岛化 / PPR / 边缘渲染不是九种技术，而是同一个问题「HTML 字符串在哪一刻生成、何时交给浏览器」的九个取值。想清楚时间轴，就不需要死记方案清单。

### 1.2 主轴与增强：前四行是交付方式，后五行是增强

对比表的前四行（CSR/SSR/SSG/ISR）是交付方式的主轴；后五行全是主轴上的增强——流式改交付节奏、RSC 改求值位置、岛化改注水粒度、PPR 组合 SSG 与流式、边缘改传输距离。读表先定「HTML 何时生成」，再看「服务端每次成本」。

### 1.3 选型决策树与实测基线

四个问题走到底：要不要被抓 → 内容变不变 → 能不能旧 → 有没有慢数据源。实测基线（render-lab）：FCP（jslag=300）CSR 2192ms · SSR 504ms · SSG 404ms · 流式 388ms；SSR 连发三次一次没省（273/279/278ms）；ISR 四态命中 2ms。「注水期零 DOM 写入」是注水失配的硬指标。

## 2. Next.js：把渲染范式的选择权交给文件

### 2.1 心智模型迁移：术语对照与两个不对应

Next 与 Nuxt 术语几乎一一对应（文件路由、layout、useFetch≈RSC await、routeRules≈dynamic/revalidate）。两个不对应：① Next 默认所有组件是 Server Component，交互要显式 `'use client'`，Nuxt 正好相反；② Next 15 的动态路由 params 是 Promise，必须 await。

### 2.2 App Router：路由表是文件树，外壳是 layout

目录名是路径段、`page.tsx` 使路径可访问、`[id]` 是动态段；`layout.tsx` 导航切换不重渲染，`loading.tsx`/`error.tsx`/`not-found.tsx` 把加载态与错误态变成路由树上的节点——放得越深，作用范围越小。

### 2.3 Next 15 的 params 是 Promise

页面组件可以是 async 函数，组件体里直接 await 取数（RSC 的核心形态变化）；代价是 params 从对象变成 Promise（静态化构建时逐路径求值，动态化请求时求值）。迁移老代码直接点 `.id` 会拿到 Promise。

## 3. 渲染范式的一行切换

### 3.1 默认即 SSG

不写声明的页面构建时渲染一次。判据沿用决策树：内容变化频率低于构建频率，请求路径零渲染就是净收益。实测构建输出里首页是 `○ (Static)`。

### 3.2 force-dynamic：数据被写操作改写时不能静态化

列表页数据会被 Server Action 新增，构建期 HTML 立刻过期，`export const dynamic = 'force-dynamic'` 切成每请求 SSR。代价仍是渲染架构篇那笔账：每次重渲染、重等慢数据源——能静态的别 dynamic。

### 3.3 revalidate：ISR 就是一个数字

`export const revalidate = 10` + `generateStaticParams`：已知 id 构建期预渲染（实测 1001~1005 五条），其余请求时动态渲染。ISR 四态原样成立，实测构建后首请求详情页 `x-nextjs-cache: STALE`——命中旧 HTML、同时后台重建，「用户永远不等重建」在真实框架里就是这一个响应头。

### 3.4 RSC 边界：'use client' 不等于不预渲染

实测构建输出里 `'use client'` 的表单页仍是 `○ (Static)`——HTML 壳照样构建期生成，JS 只负责交互。RSC 的判据是「组件需不需要浏览器能力」，不是「要不要下发 HTML」。

## 4. Server Action 与写操作实战

### 4.1 写操作不需要手写接口

`app/actions.ts` 整文件 `'use server'`，表单 action 直接调服务端函数：校验失败返回错误对象、成功 redirect 跳详情。「表单 → 服务端校验 → 落库 → 跳转」整条链不需要 API 路由；生产把内存存储换成数据库调用，范式不变。

### 4.2 流式交付下 notFound() 换不了状态码

实测 `GET /orders/9999` 返回 **200 但内容是 404 页**：流式交付下响应头已随壳发出，notFound() 只能换内容、换不了状态码。状态码监控要配合内容判断，别只盯 4xx 比例。

## 5. mini-next：手写文件路由 + SSR + hydration

### 5.1 文件路由 = 构建期生成的 import 映射

扫描 pages/ 把文件名翻译成 pattern，生成 `routes.gen.ts` 静态 import 列表——实测输出 `routes = /about, , /order/:id`，与 Next 的 `Route (app)` 表是同一件事的最小形态。「约定优于配置」的落地物就是这段生成代码，没有任何运行时扫描。

### 5.2 SSR：数据先于渲染就位

`load()` 是 getServerSideProps 的最小对应物：只在服务端执行、await 完才渲染、props 随 HTML 下发。服务本身是三十行原生 node:http，响应头记 `X-Render-Ms` 实测 0.7~6.1ms。

### 5.3 注水数据下发与转义

SSR 产物 = HTML + `window.__PROPS__`；props 里的 `<` 转义成 `\u003c` 防 `</script>` 提前闭合——渲染架构篇「SSR 的产物是 HTML + 注水数据」在最小实现里就是模板里的一个 script。

### 5.4 hydration：React 的注释锚点

`hydrateRoot` 用同一份路由表与数据认领已有 DOM。实测 React 18 的 SSR 字符串里相邻文本节点之间有 `<!-- -->` 注释——没有它两个文本节点会被 HTML 解析合并、客户端对齐就乱。渲染架构篇「对齐单位是 childNodes 下标」的结论，React 用注释锚点来守。

## 6. Nuxt：混合渲染与 Nitro

### 6.1 routeRules：渲染范式的中心化路径表

`routeRules: { '/client-only': { ssr: false }, '/orders/**': { swr: 10 } }`——Next 是每页一行导出，Nuxt 是中心化一张规则表，粒度相同、组织方式不同，按目录自治时后者更好收敛。

### 6.2 useFetch：数据先于渲染就位的默认化

`await useFetch(...)` 顶部直接等：服务端取数、payload 随 HTML 下发、客户端 hydration 认领、不再发第二次请求。传统 Vue SSR 的「手动预取 + 注水对齐」整套手工程序被做成了默认行为。composables/ 目录免 import 全局可用，收益是少样板、代价是来源不可见。

### 6.3 server/api 与 Nitro 运行时

`defineEventHandler` 文件即接口，与页面同一份工程同构部署；server/utils 自动导入共享数据层。「前后端同一工程」是 Nuxt 核心卖点，Next 要 route.ts + Server Action 两套形态才凑齐。

### 6.4 ssr:false 的边界：整页文案都不在 HTML 里

实测 `GET /client-only` 返回 200，HTML **不含页面标题文案**——只有 app.vue 布局壳。「不服务端渲染」不是「少渲染一段」，是整个页面组件都不参与；这正是「CSR 首屏由网络与解析决定」在框架层的直接体现。

## 7. mini-nuxt：SFC 双遍编译与 Vue SSR

### 7.1 SFC 双遍编译：ssrRender 与 render

SSR 构建不是「同一份产物跑两端」，是同一个 SFC 编译两遍：server 遍 `compileTemplate({ ssr: true })` 产出直拼字符串的 ssrRender（不建 vdom），client 遍产出标准 render。Nuxt 的双产物构建就是 mini-nuxt 那个 46 行 esbuild 插件的工业版。

### 7.2 每请求新建应用实例

三个实测踩过的坑：asyncData 挂在组件对象（default 导出）上不在模块命名空间上；每请求必须新建 createSSRApp（实例持有状态，复用会串单）；`h(comp, props)` 传的 props 要在组件里声明 `props: [...]` 才进实例，否则落进 $attrs 模板取不到。

### 7.3 hydration：createApp 与 createSSRApp 的分野

Vue 把「SSR 还是 CSR」编码在创建应用的 API 上：`createApp().mount()` 直接重建，`createSSRApp().mount()` 先复用已有 DOM——与 React 用 render/hydrateRoot 两个 API 编码同一个区别异曲同工。两端锚点对照：React 用 `<!-- -->` 分隔文本节点，Vue 用 `<!--[-->`/`<!--]-->` 包住列表段。

## 8. 综合收口：框架选型与边界

### 8.1 Next 与 Nuxt 的架构差异：有没有 RSC

Nuxt 没有 RSC——所有组件默认客户端组件、代码包照发；Next 服务端组件代码不进客户端包。内容型大站里注水数据随树增长的成本，RSC 是真实解法。偏向 Nuxt 的信号：Vue 栈、前后端同工程同部署（Nitro）、中心化规则表；偏向 Next 的信号：页面树深、注水数据占比高。

### 8.2 什么时候不该上 SSR 框架

全交互密集的后台工作台（SSR 只增加服务端成本，CSR 即可）；内容不需要被抓且用户有明确预期的壳内页。要 SEO 又不想每次重渲染 → SSG/ISR/页面缓存。SSR 只保证内容先到，不保证点得动——「上了 SSR 框架就等于首屏快」仍是常见误判。
