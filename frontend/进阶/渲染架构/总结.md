## 1. 渲染方案总览

### 1.1 交付方式的本质：字符串何时生成、何时交给浏览器

CSR / SSR / SSG / ISR 不是四种技术，而是同一个问题「HTML 字符串在哪一刻生成、何时交给浏览器」的四个取值：

```
CSR    浏览器端渲染，内容靠 JS 拉取（JS 下载解析 + 接口往返后重建 DOM）
SSR    每次请求，服务端渲染一次
SSG    构建时渲染一次（构建后内容固定）
ISR    SSG + 过期时间 + 后台重建
流式   同一份 SSR，已就绪的部分先发
```

实测（`jslag=300`）FCP：CSR 2192ms · SSR 504ms · SSG 404ms · 流式 388ms。

> 全部数字来自 `frontend/进阶/渲染架构/code/render-lab`：零依赖、手写最小 vdom 与三套渲染出口，用无头 Chrome 与原生 `http` 客户端现场测量，七个 mode（`csr` / `ssr` / `ssg` / `isr` / `stream` / `island` / `hydrate`）共用同一份路由表，`npm run all` 可一次跑完并校验。

### 1.2 首屏指标口径：TTFB、FCP、TTI 与内容出现时刻

- **TTFB**：第一个字节到达的时刻。
- **FCP**：第一个像素画出来的时刻。
- **TTI**：页面可交互的时刻，需要事件挂到 DOM 上。
- **内容出现时刻**：用户真正看到内容的那一列，与 FCP 不是一回事。

SSR 的 FCP 紧贴 TTFB，因为**内容随 HTML 一起来**：SSR 的 HTML 里已有完整内容，浏览器解析到就能画，中间只隔着一次解析（实测 TTFB 374ms、FCP 504ms，差 130ms）。CSR 则要等「HTML 到达 → JS 下载解析 → 接口往返 → 建 DOM」四条腿走完。

> 读表口径要先说清：无头环境里 `load` 与首帧的先后不严格（CSR 那行 FCP 甚至比 `load` 晚），判断「用户什么时候看到内容」要看 FCP 与「内容出现时刻」两列。

**SSR 的 FCP 好，不代表体验好**：服务端渲染先到的是内容，事件要等客户端运行时下载解析完才挂上——还要看 TTI。

### 1.3 渲染方案选型决策树

选型按四个问题走：

```
要不要被抓      → 要，打掉 CSR；不要，CSR 可用
内容变不变      → 不变，SSG；会变，看下一问
内容能不能旧    → 能，ISR（TTL 换「用户不等重建」）；不能，SSR
有没有慢数据源  → 有且区块多，流式；只有一小块动态，PPR / 岛化
交互密度高不高  → 高，接受全量注水；低，岛化
```

ISR 的取舍问两句：内容错了有没有损失、旧内容能忍受多旧。价格、库存、余额这类数据不适合 ISR。

## 2. CSR 客户端渲染

### 2.1 首屏由网络与解析决定，不由渲染决定

CSR 首屏分四段：HTML 到达 → JS 下载解析 → 接口往返 → 建 DOM。实测建 DOM 只占个位数毫秒。

网络条件从 `jslag=0` 换成 `jslag=300`，CSR 的 FCP 从 640ms 涨到 2192ms（3.4 倍），而 SSR / SSG / 流式基本不动（500ms 左右 → 400~500ms）。同一份代码，渲染耗时始终是个位数毫秒。

### 2.2 骨架屏只提前 FCP，不改变内容到达时刻

骨架屏把 FCP 提前，但只解决「看起来在加载」，不解决「内容什么时候到」——LCP 与内容出现时刻依然压在最后。

### 2.3 CSR 的适用场景

内容不需要被爬虫抓、不被社交卡片引用、用户对「先加载再出现」有明确预期的场景（后台工作台、登录后仪表盘、桌面端壳内页面），CSR 换来的构建简单与缓存粒度清晰是净收益。

## 3. SSR 与同构实现

### 3.1 同构的三条约束

同构 = 「一份页面树两端渲染」，前提是**页面树必须是纯描述**——`App()` 返回的是一棵由 `h()` 组成的普通对象树，不含任何 DOM 引用或浏览器 API，服务端能直接 `renderToString` 它。

收益是结构只写一次，代价是三条约束要贯穿整个工程：

```
① 组件两端可跑、渲染期无副作用（不碰 window / localStorage）
② 数据必须先于渲染就位
③ 客户端要能重建出完全相同的树
```

任何一条破了，要么报错，要么静默失配。

### 3.2 服务端侧：耗时绑定最慢的数据源

- 实测 SSR 连发三次，响应头到达 273 / 279 / 278ms，**一次都没省下**（服务端自己记的 `X-Render-Ms` 是 266 / 275 / 275ms）；渲染本身只占个位数毫秒，其余全是等待。
- `await Promise.all` 的语义是「全部就绪才继续」，整体耗时等于**更慢的那个**——实验台两个慢接口并发（评价 260ms、推荐 130ms），整页绑定在 260ms 上。
- 对照 SSG 服务端耗时 **0ms**、ISR 命中 1~2ms——省掉的正是 SSR 每次都逃不掉的那一段。

> 这就是「一个慢区块拖垮整页」的根因：页面只要有一个慢数据源，哪怕其余 90% 的内容本机立即可得，也发不出去。破法见第 5 章流式渲染。

### 3.3 产物：HTML + 注水数据

- SSR 的产物是 HTML + 数据：实测标记 4.1KB + 注水数据 1.2KB，数据占 HTML 的 22.3%；同标记下发数据后体积涨 29.5%。
- 数据与入口模块都放在文档尾：内容先到、脚本后到。
- `renderToString` 产物里**没有任何事件监听器**，事件是客户端接管时挂的。

### 3.4 hydrate：注水机制与成本

注水（hydration）不是「把 HTML 再渲染一遍」，而是**把事件监听器与状态接到已经存在的 DOM 上**。

```
renderToString  树 → 字符串（服务端，产物里没有事件）
renderDOM       树 → 新建 DOM（客户端，创建节点 + replaceChildren 到容器）
hydrate         树 → 认领已有 DOM（客户端，挂事件的唯一处）
```

`hydrate` 按容器 `childNodes` 下标对齐：第 i 个虚拟子节点对第 i 个真实子节点，标签一致就复用并补属性（这里是挂事件的地方），不一致才整棵重建。

**理想形态是一次 DOM 写入都不发生**——实测两端一致时 97 个节点全部复用、真实 DOM 突变 0 次。反过来说，注水期一旦出现 DOM 突变，就说明前面白渲染了。「注水期零 DOM 写入」是钉死失配的硬指标。

成本由失配决定：失配不一定报错（见 3.5）。若不做注水直接重建也行，但实测丢弃 97 个节点、重建 97 个，服务端那份 HTML 就只剩「用户先看一眼」的价值。

> 实现细节：三者共用的那步是「把 `children` 塞进 `props`」（函数组件拿子节点的唯一通路）；自己实现渲染器时漏掉这一步，所有带子节点的组件都会渲染成空。

### 3.5 注水失配：形态、上报与对齐单位

**三种失配形态**（只有标签不一致这类严重情形才会被注意到）：

```
文本不一致   静默改写（characterData 突变 8 次）——只是白干，连警告都没有
标签不一致   整段重建（丢弃 14 个节点、重建 2 个）
结构多节点   删除（否则成为幽灵节点，下次更新错位）
```

实测四个变体：两端一致 97 / 0 / 0 / 0 / 0（复用 / 新建 / 丢弃 / 改写 / 失配）；价格口径不一致 97 / 0 / 0 / 8 / 0；标签不一致 83 / 2 / 14 / 2 / 1；直接重建 0 / 97 / 97 / 57 / 0。真实 DOM 突变次数：一致 0 次，这才是要卡的硬指标。

**经典失配来源**：时区、货币与数字格式化、日期格式、随机数、不稳定排序——共同特征是「同一份数据在两端算出不同结果」。

**对齐单位是容器的 `childNodes`，不是容器自己**。两个推论：① 服务端渲染子树时子节点之间不能插入空白，多一个换行文本节点就会让后续下标全部错位；② 任何一层多余的包裹（比如给岛再套一个 `div`）都会让子树失去复用资格。少这一层会导致整棵树从根错位。

排查手段：用 `MutationObserver` 量三个计数——`characterData` 有值 → 格式口径不一致（数据问题）；`childList` 有值 → 结构不一致（结构问题）。两者一分开，方向就定了。

## 4. SSG 与 ISR

### 4.1 SSG：构建时渲染一次

- 构建时把渲染挪到请求路径之外，响应头 3~4ms（本机导航固定开销约 100ms 之外近乎为 0），服务端耗时 0ms。
- 内容变化频率低于构建频率是 SSG 的判据：内容不随请求变化，SSR 每次都重渲染是纯浪费；且 SSR 的响应时间绑定最慢的数据源。
- HTML 自带完整内容，爬虫能直接抓，SEO 友好。

### 4.2 ISR：过期时间与后台重建

ISR = SSG + 过期时间 + 后台重建，用的是 `stale-while-revalidate` 在页面层的版本。

**四态实测**：回源 266ms · 命中 2ms · 过期返回旧内容 4ms（后台重建）· 重建后命中 1ms。用户永远不等重建。

```
首次请求   回源渲染 0ms流量？ 否，回源 266ms
之后命中   2ms
过 TTL 那次 仍只花 4ms —— 返回旧内容，同时后台开始重建
重建完     命中 1ms
```

> 与「CDN 缓存页面」的区别：ISR 是应用层的一份带 TTL 的缓存 + 后台重建，可进行按路径的参数化生成；CDN 缓存是同一份产物发给所有人，失效靠手动或 TTL。

ISR 的取舍问两句：内容错了有没有损失、旧内容能忍受多旧。价格、库存、余额这类数据不适合。

## 5. 流式渲染

### 5.1 边界画在数据来源上

流式渲染不改变「服务端渲染」这件事，只改变**什么时候把已经渲染好的部分交出去**——能发的先发。

遇到「边界」节点时不阻塞：先写一段兜底（骨架）占住位置，把取数 Promise 登记下来，继续渲染后面的内容；数据到齐后把真内容装进 `<template>` 发过去，用一段自删脚本原位替换。

**分段的边界画在数据来源上，不画在组件层级上**：按组件树层级切会切出几十个几百字节的碎片，每片都带自己的占位与模板，TCP 效率被拖垮。评价接口一段、推荐接口一段正合适。

> 标记用自删的 `<script>` 做：它在浏览器侧往 `window.__chunks` 记一笔时间，同时给 Node 侧的解析提供切分位置。

### 5.2 补位顺序由谁先好决定

补位顺序由**谁先好**决定，不是由谁在页面里靠前决定。实现上对所有边界任务的 promise 做 `Promise.race`，先完成的先产出补位段。

实测顺序是 `shell → recommend:fill → reviews:fill`——推荐位在页面里排在评价**之后**，但它 130ms 就好了、评价要 260ms，所以它先补位。

### 5.3 看得见不点得动：与全量注水的矛盾

- 服务端壳 3ms 发出、整页 266ms 完成；首个内容字节比非流式 SSR 早 261ms；浏览器侧 FCP 340ms vs 508ms、商品列表 235ms vs 399ms。
- 代价：HTML 从 5.3KB 涨到 6.5KB（占位、template、补位脚本、运行时）。
- **入口模块执行时刻几乎不变**（1650ms vs 1679ms）——全量注水需要一份完整数据对象去重建整棵树，而这份数据要等最后一个边界之后才凑齐，文档尾（注水数据 + 入口模块）被那句 `await reviewsPromise` 压到了最后。
- 一句话：**它把「看得见」的边界提前了很多，没有把「点得动」提前**。流式与全量注水「天然别扭」——前者希望尽早交付片段，后者必须等全部数据，两个目标在时间轴上相反。

要连 TTI 也提前有三条路：① 分段下发注水数据（每个边界把这段 props 一起塞进去，客户端接受数据分批到达）；② 改成岛化（交互点自带 props，激活不必等任何东西）；③ 接受「先看见后点得动」，用骨架或 `aria-busy` 把等待表达清楚。

## 6. 新兴渲染范式

### 6.1 岛化 Islands

岛化拆掉的是「客户端要认识整棵树」这个默认值：把整页划成「静态的海」与「需要 JavaScript 的岛」——服务端渲染完整页面但只给岛打标记，客户端入口只认识那些标记，于是静态组件的代码根本不用下载。

**实测收益**：全量 hydration 要 14 个模块 16.4KB，岛激活只要 6 个模块 9.4KB，**少下载 7.0KB，是整份客户端的 42.8%**，而挂上的监听器数量与按钮行为完全相同。

**两个必须做对的地方**：

```
① 标记落在子树自己的根元素上——多套一层会导致整棵子树失配重建
② 注册表只放交互组件——页面里没有的组件不进图谱，代码也就不下载
③（细节）props 序列化进属性时 < 要转义成 \u003c，防 </script> 提前闭合
```

**省的是业务代码，不是运行时**：`vdom` + `hydrate` 共 5.5KB 是框架的地板价，只要还有一处交互就得下载。「页面很小、只有一两个交互点」时，岛化的绝对收益可能还不如换一套更轻的框架。

**一个心智补丁**：入口开始执行时刻实测 1643ms vs 1631ms，岛化甚至还略晚一点——`jslag` 下模块是并发下载的，决定入口开始时刻的是依赖链的**段数**，不是总字节数；省下的字节要等带宽或解析成为瓶颈时才变成时间收益。

**隐性成本**：岛之间无法直接共享状态，需显式通过属性或全局事件通信，这会改变组件的写法。岛的粒度不是「组件」，而是「需要 JavaScript 的区域」（一个筛选器、一个图表）。

### 6.2 React Server Component（RSC）

RSC 改的是「组件在哪一侧求值」（原理，无实测）：

- SSR 下发整棵树的 props；RSC 只下发**客户端组件**那部分，服务端组件的代码**完全不进客户端包**，还能直接查库、读文件、调内部服务。
- 解决的是注水数据随组件树增长的成本（上一篇实测占 HTML 22.3%）——树越深、数据越多，整份 props 下发越不划算。
- 代价是「两类组件」的写法与心智负担（哪些能用 `useState`、数据怎么往下传都要按类别判断）；交互密集页面所有组件都是客户端组件，RSC 就退化成普通 SSR。**它是架构级选择，不是性能开关，也不替代 SSR。**

### 6.3 选择性注水与 PPR

两者都补流式留下的那个缺口——**内容看得见了，但点不动**（原理，无实测）。

```
选择性注水   把「注水顺序」变得可干预：先只给用户正要交互那一段注水，其余延后
             于是 TTI 不再由「最后一个慢区块」决定，而由「用户想看哪里」决定
PPR          把静态与动态分开：静态骨架构建时生成（等同 SSG），动态的洞请求时用流式补
             于是第一个字节可立刻从 CDN 边缘出去，TTFB 走 SSG、内容完整性走 SSR
```

- 选择性注水的前提是渲染器支持**按标记粒度注水**（就是岛化那套机制在更大范围内的版本）。
- PPR 要求页面能被可靠地切成「静态骨架 + 动态洞」两半，切得不好会出现骨架与真内容布局跳动。

### 6.4 边缘渲染

边缘渲染动的是 **传输**，不是**计算**（原理，无实测）：

```
SSR 耗时 = 计算（渲染 + 取数）+ 传输（用户 → 服务端 → 用户）
边缘渲染  把服务端渲染放到离用户最近的城市节点，省的是第二块——传输
它不减少计算：若 260ms 的慢接口还得回中心机房查，边缘只是把传输那段省下来
```

- 与 SSG / PPR 天然搭配：能在边缘渲染的前提就是「不依赖只能在中心查的数据」，静态骨架正好满足这一点。
- **边缘渲染 ≠ CDN 缓存**：前者在边缘**执行**渲染逻辑、可按请求头与地理位置产出不同结果；后者是共享同一份产物。
- 运行时约束：冷启动更敏感、包体积有上限、可用 API 是子集（通常没有完整文件系统）、不能直连内网。

## 7. 综合实战收口

### 7.1 渲染方案选型全景

把第 1 章的决策树落到四个典型场景：

| 场景 | 方案 | 理由 |
| ---- | ---- | ---- |
| 内容站，每天更新几次、要 SEO、几乎没有交互 | SSG（构建时生成）+ 增量更新，更新频繁到构建跟不上时用 ISR | 内容变化低于构建频率是 SSG 判据；实测 SSG 服务端耗时 0ms、请求路径零渲染，HTML 自带完整内容报爬虫直接抓 |
| 电商首页，主体就绪快、有个 300ms 个性化推荐接口 | SSR + 流式渲染，把推荐位切成独立边界 | 壳 3ms 发出、推荐 141ms 补位、评价 265ms 补位，用户先拿到 90% 内容；边界画在数据来源上 |
| 老项目 CSR 迁移 SSR 的注水排查 | 「注水期零 DOM 写入」当验收指标 | 用 `MutationObserver` 分 children / attributes / characterData 三档量化（详见 3.5、7.2） |
| 文档站，只有搜索框与折叠需交互 | 岛化 | 静态内容占绝对多数、交互点只有两三个，实测少下载 42.8% 客户端 JS，行为完全不变 |
| 全球营销页，TTFB 高 | 先拆构成再决定：服务端占大头先静态化（SSG/PPR），传输占大头先上边缘 | 用 `Server-Timing` / `X-Render-Ms` 拆服务端处理时间占比 |

某场景入口（文中不重复展开的细节）：

- 岛化落地：给两个子树打 `data-island` + `data-props` 标记，客户端入口从注册表取这两个组件逐个 `activate`（本质是对每个标记调一次 `hydrate`）。搜索框要拿全量索引数据时，不要塞进 `data-props`——把它放在岛内部（激活后再 fetch），`data-props` 只放启动必需的小配置。

### 7.2 迁移排查与回归验收

老项目从 CSR 迁移到 SSR，系统排查注水失配（对应 3.5）：

```
① 在 hydrate 前后挂 MutationObserver，分别统计三类突变次数
② characterData 有值 → 找两端格式口径不一致（时区、货币、日期、随机数、排序）
                       实测这类静默改写 8 处文本、不报错
③ childList 有值 → 查结构对齐（childNodes 下标、空白节点、多余包裹）
                    实测标签不一致丢弃 14 个节点
④ 用「复用数 / 丢弃数」判断严重程度，理想是复用 N、丢弃 0
```

迁移期最常见的三类改动会引入失配：把服务端能访问的全局状态（登录态、时区）直接读进组件；把 `Math.random()` 或用当前时间当 key；列表排序不稳定。隐藏项：服务端拼接时为了可读性插了换行、客户端没有——这类「看起来无害」的空白会让整棵子树重建。

**回归防线**：把「clean 变体 0 突变」写进 CI，像实验台那样把四个失配变体固定下来当回归用例。

**方法论收尾**：SSR 只保证**内容先到**，不保证**点得动**；「上了 SSR 就等于首屏快」是常见误判。既要 SEO 又不想让服务端每次都重渲染 → SSG 或 ISR（内容变化频率低于构建频率时），或用页面缓存把 SSR 的产物缓存起来。
