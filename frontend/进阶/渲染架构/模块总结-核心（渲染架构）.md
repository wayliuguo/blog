## 知识主线（一句话）

本模块的主轴是**同一个页面的代价分配**：差别不在"渲染"而在"字符串在哪一刻生成、何时交给浏览器"。01 给出完整坐标系（CSR/SSR/SSG/ISR/流式 + 选型问题）；02 把「SSR + 同构」拆到机制层并量化每一笔代价（服务端省不掉、注水数据、hydrate 失配）；03 是四个**拆默认值**的方向——岛化 / RSC / 选择性注水与 PPR / 边缘渲染。

## 高频核心点

### 01 渲染方案全景

**交付方式一句话**

- **CSR**：浏览器渲染，首屏由网络与解析决定（HTML 到达→JS 下载→接口往返→建 DOM，实测 jslag=300 时 FCP 2192ms）
- **SSR**：每次请求服务端渲染，代价在服务端不在浏览器（连发三次都省不下）
- **SSG**：构建时渲染一次，请求路径上只剩一次字符串写出（响应头 3~4ms）
- **ISR**：SSG + 过期时间 + 后台重建；取舍问两句：内容错了有没有损失、旧内容能忍多旧
- **流式**：已就绪部分先发，把"看得见"提前、不把"点得动"提前（FCP 基质块不变）

**选型按四问走**：要不要被抓→打掉 CSR；内容变不变→不变就 SSG；能不能旧→能就 ISR；有慢数据源且区块多→流式，只有一小块动态→PPR/岛化；交互密度高→接受全量注水，低→岛化

### 02 SSR 与同构实现

- **同构前提**：树必须是纯描述——组件两端可跑、渲染期无副作用；数据先于渲染就位；客户端能重建完全相同树
- **SSR 耗时绑定最慢的数据源**：`Promise.all` 并发取数、整体等于更慢的那个；服务端每次都逃不掉
- **产物是 HTML + 数据**：注水数据占 22.3%（数据是隐性成本）；`renderToString` 产物无事件监听器、事件客户端接管时挂
- **hydrate 的成本由失配决定**：文本不一致只静默改写、标签不一致才整段重建；真实 DOM 突变次数才是要卡的硬指标；对齐单位是容器的 `childNodes`（少这一层整棵树错位）；经典失配来源：时区、货币/数字/日期格式化、随机数、不稳定排序
- **流式**：分段边界画在**数据来源**上不画在组件层级上；壳先发、注水数据等最后一个边界

### 03 新兴渲染范式

- **岛化（Islands）**：拆掉"客户端要认识整棵树"——全量 hydration 大多节点在陪跑（97 节点只挂 1 监听器）；岛激活实测少下载 42.8% 客户端 JS；标记落在子树自己的根元素（多套一层整棵失配重建）；注册表只放交互组件
- **RSC**：改"组件在哪一侧求值"——只下发客户端组件那部分 props，服务端组件代码不进客户端包；代价是"两类组件"写法；交互密集页面无收益、不替代 SSR
- **选择性注水与 PPR**：按交互意图给区域插队、把 TTI 与"最后一个慢区块"解耦；PPR=静态骨架构建时生成 + 动态洞流式补
- **边缘渲染**：缩短的是传输不是计算——若数据仍回中心查，省下的只是传输那段；边缘渲染 ≠ CDN 缓存（前者按请求差异化、后者共享一份产物）
