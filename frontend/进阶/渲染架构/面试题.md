# 模块面试题 · 渲染架构

## 1. 渲染方案全景与选型

### Q1（1.1）｜ CSR / SSR / SSG / ISR / 流式 / RSC 这些方案的本质区别是什么？

- **判断**：不是九种技术，是同一个问题「HTML 字符串在哪一刻生成、何时交给浏览器」的九个取值。
- **展开**：CSR 在浏览器端（等 JS 下载解析 + 接口往返）；SSR 每次请求；SSG 构建时；ISR 构建时 + TTL 后台重建；流式把「已就绪的部分先发」；RSC 改的是组件在哪一侧求值；岛化改注水粒度；PPR 组合 SSG 与流式；边缘改传输位置。
- **佐证**：实测（render-lab，`jslag=300`）FCP：CSR 2192ms · SSR 504ms · SSG 404ms · 流式 388ms。
- **边界**：读对比表的方法——前四行（CSR/SSR/SSG/ISR）是交付方式主轴，后五行全是主轴上的增强；先定「HTML 何时生成」，再看「服务端每次成本」。追问：SSG 与 ISR 怎么选？→ 内容变化频率低于构建频率用 SSG；能接受 TTL 窗口内的旧内容用 ISR。

### Q2（1.3）｜ 渲染方案选型的决策树怎么走？

- **判断**：四个问题走到底——要不要被抓、内容变不变、能不能旧、有没有慢数据源。
- **展开**：要被爬虫抓/被社交卡片引用 → 打掉 CSR；内容不变 → SSG；能容忍旧内容 → ISR（TTL 换「用户不等重建」）；不能 → SSR；有慢数据源且区块多 → 流式，只有一小块动态 → PPR/岛化；交互密度低 → 岛化。
- **边界**：ISR 的取舍问两句——内容错了有没有损失、旧内容能忍受多旧；价格、库存、余额这类数据不适合 ISR。追问：交互密度高但也要 SEO 怎么办？→ 接受全量注水的 SSR，或 PPR：静态骨架走 SSG 的 TTFB，动态洞流式补。

## 2. Next.js：把渲染范式的选择权交给文件

### Q1（2.1）｜ Next.js 相对于「自己搭 React SSR」解决了什么？

- **判断**：把「渲染方案选型」从架构决策降级成文件约定——四种渲染取值映射成文件系统里的声明，构建器读声明出产物。
- **展开**：`page.tsx` 默认静态（SSG）、`force-dynamic` 切 SSR、`revalidate` 切 ISR、`'use client'` 画 RSC 边界；路由表、layout、数据预取、服务端部署全部约定化。
- **佐证**：实测 `next build` 输出的 Route 表里 `○ /`（Static）、`ƒ /orders`（Dynamic）、`● /orders/[id]`（SSG + Revalidate 10s）三行并存——同一份工程四条交付路径互不干扰。
- **边界**：约定多、黑盒深是代价；深度定制渲染管线到约定装不下时，先读 mini-next 这类最小实现再决定绕不绕框架。追问：Vue 背景怎么快速迁移？→ 术语对照表（文件路由/layout/useAsyncData↔RSC await/routeRules↔导出常量），再记两个不对应：Next 默认 Server Component、params 是 Promise。

### Q2（2.2）｜ App Router 的 layout 和 loading/error 约定带来什么？

- **判断**：路由表由文件树决定；layout 是导航切换不重渲染的共享外壳；loading/error/not-found 把加载态与错误态变成路由树上的节点。
- **展开**：目录名是路径段、`[id]` 是动态段；约定式外壳的价值是加载态与错误态不再是每页手写的样板——放得越深，作用范围越小（根布局的 error.tsx 兜全站，段落里的只兜该段）。
- **边界**：error.tsx 必须是客户端组件（错误边界要在浏览器接住运行时错误）。追问：layout 为什么不重渲染？→ 导航只换 children 对应的子树，layout 这层在客户端是复用的。

### Q3（2.3）｜ Next 15 里动态路由的 params 有什么变化？

- **判断**：params 从对象变成了 Promise，页面组件必须 `await params`。
- **展开**：这是 RSC 异步化的直接后果——页面组件可以是 async 函数，组件体里直接 await 取数；`params` 在静态化构建时按路径逐个求值、动态化请求时才求值，所以把它建模成 Promise。
- **边界**：迁移老代码直接点 `params.id` 会拿到 Promise 对象，取到 undefined。追问：页面组件变 async 意味着什么？→ 「数据先于渲染就位」成了组件写法本身，不再需要 useEffect + loading 三件套。

## 3. 渲染范式的一行切换

### Q1（3.1/3.2）｜ 什么时候用默认的 SSG，什么时候 force-dynamic？

- **判断**：内容变化频率低于构建频率 → 默认 SSG；数据会被写操作改写、构建期 HTML 立刻过期 → `force-dynamic`。
- **展开**：SSG 的请求路径零渲染（实测构建输出里首页 `○ /`）；订单列表页的存储会被 Server Action 新增，静态化后新订单不可见，必须声明 force-dynamic 每请求 SSR。
- **佐证**：实测 `next build` 输出：`○ /` 与 `ƒ /orders` 并存于同一工程。
- **边界**：SSR 的代价仍是渲染架构篇那笔账——每次重渲染、重等慢数据源，响应时间绑最慢数据源；能静态的别 dynamic。追问：中间态呢？→ revalidate 的 ISR（3.3）。

### Q2（3.3）｜ revalidate 和 generateStaticParams 分别做什么？

- **判断**：`generateStaticParams` 决定哪些路径构建期预渲染，`revalidate = N` 给预渲染产物加 TTL 后台重建——两者合起来是完整的 ISR。
- **展开**：详情页返回已知 id 列表（实测 1001~1005 五条全部预渲染），没列出的 id 落到请求时动态渲染；TTL 到期后的请求返回旧内容、同时后台重建。
- **佐证**：实测构建后首请求 `GET /orders/1001` → 200，`x-nextjs-cache: STALE`——命中旧 HTML、同时后台重建，「用户永远不等重建」在真实框架里就是这一个响应头。
- **边界**：ISR 的取舍两问不变：内容错了有没有损失、旧内容能忍多旧。追问：ISR 与 CDN 缓存页面的区别？→ 应用层带 TTL 的缓存 + 后台重建 + 按路径参数化生成；CDN 是同一份产物发所有人。

### Q3（3.4）｜ 'use client' 的页面还会预渲染吗？

- **判断**：会——'use client' 不等于「不预渲染」，它的 HTML 壳照样构建期生成。
- **展开**：实测构建输出里 `'use client'` 的表单页是 `○ /orders/new (Static)`：HTML 壳 SSG，JS 只负责交互。RSC 的判据是「组件需不需要浏览器能力」（useState/事件/浏览器 API），不是「要不要下发 HTML」。
- **边界**：Next 默认所有组件是 Server Component（在服务端求值、代码不进客户端包），与 Nuxt「默认全客户端组件」正好相反——这是两套框架最本质的架构差异。追问：RSC 解决什么成本？→ 注水数据随组件树增长的成本，服务端组件代码完全不进客户端包。

## 4. Server Action 与写操作实战

### Q1（4.1）｜ Server Action 是什么？它取代了什么？

- **判断**：`'use server'` 声明的服务端函数，客户端表单可以直接调用——写操作不再需要手写 API 路由。
- **展开**：表单 `action={async (formData) => ...}` 里直接 await 服务端函数；校验失败返回错误对象、成功 `redirect` 跳转。「表单 → 服务端校验 → 落库 → 跳转」整条链一个 API 路由都不用写。
- **边界**：数据层演示用进程内存储（globalThis），生产换数据库调用范式不变。追问：它和传统 POST 接口的本质区别？→ 调用关系在编译期绑定（RPC 形态），参数校验和类型在两端共享，不用维护接口契约。

### Q2（4.2）｜ notFound() 之后状态码还是 200，为什么？

- **判断**：流式交付下响应头已随壳发出，`notFound()` 只能换内容、换不了状态码。
- **展开**：实测 `GET /orders/9999` 返回 200 但内容是完整 404 页——流式渲染时壳先发（此时还不知道这个 id 有没有数据），响应头定型后只能靠内容表达失败。
- **边界**：这是流式渲染的固有代价，监控要配合内容判断，别只盯 4xx 比例。追问：非流式 SSR 下呢？→ notFound() 在首字节前判定时可以正常返回 404 状态码；关流式（去 suspense 边界/关 PPR）可换回，但失去流式收益。

## 5. mini-next：手写文件路由 + SSR + hydration

### Q1（5.1）｜ 「文件路由」的运行时成本是什么？为什么能做到零扫描？

- **判断**：文件路由的本质是**构建期生成的 import 映射**，运行时零扫描。
- **展开**：构建脚本扫描 pages/ 目录把文件名翻译成 pattern（`index.tsx → /`、`order/[id].tsx → /order/:id`），生成一份静态 import 列表（routes.gen.ts）；实测输出 `routes = /about, , /order/:id`，与 Next 构建输出的 Route 表是同一件事的最小形态。
- **边界**：「约定优于配置」的落地物就是这段生成代码——约定没有魔法，最终都变成构建产物。追问：动态段怎么匹配？→ 运行时逐段比对 `:id` 与实际路径段，非动态段要求全等。

### Q2（5.3）｜ 注水数据下发要注意什么安全问题？

- **判断**：props 序列化后塞进 `<script>` 标签，里面的 `<` 必须转义成 `\u003c`，防止 `</script>` 提前闭合。
- **展开**：实测响应里 `window.__PROPS__={"order":{"id":"1001","title":"机械键盘",...}}` 与内容同到——「内容随 HTML 一起来，中间只隔着一次解析」，这就是 SSR 的 FCP 紧贴 TTFB 的原因。转义是通用要求：只要数据可能含用户输入，JSON 里的 `</script>` 就是 XSS 入口。
- **边界**：数据体积是隐性成本——渲染架构篇实测注水数据占 HTML 22.3%；树越深数据越多，这份成本越大，这正是 RSC 要解决的问题。追问：为什么数据放文档尾？→ 内容先到、脚本后到。

### Q3（5.4）｜ React 的 SSR 字符串里为什么会有 `<!-- -->` 注释？

- **判断**：这是 React 为 hydration 对齐埋的锚点——相邻文本节点不锚定会在 HTML 解析时合并，客户端对齐就乱。
- **展开**：实测 `<h1>订单 <!-- -->1001</h1>`：`订单` 和 `1001` 是两个独立的 React 文本节点，HTML 解析器会把相邻文本合并成一个节点，插入注释把它们隔开。渲染架构篇的结论「对齐单位是容器的 childNodes 下标」，React 用注释锚点来守。
- **佐证**：mini-next 实测 `GET /order/1001`：`X-Render-Ms: 0.7`，HTML 内容与 `__PROPS__` 同到；`GET /` 为 6.1ms（首请求含模块加载）。
- **边界**：对照 Vue 的做法——用 `<!--[-->`/`<!--]-->` 包住列表段。两家都在为 hydration 对齐埋锚点，锚点形态不同。追问：自己写渲染器时对应什么？→ 服务端渲染子树时子节点间不能插空白，任何多余包裹都会让下标错位。

## 6. Nuxt：混合渲染与 Nitro

### Q1（6.1）｜ Nuxt 的 routeRules 与 Next 的页面内导出常量，怎么选？

- **判断**：两种等价的组织方式——Nuxt 中心化一张路径规则表，Next 分散到每个页面文件。
- **展开**：`routeRules: { '/client-only': { ssr: false }, '/orders/**': { swr: 10 } }` 一处声明全站渲染策略；Next 是页面里 `export const dynamic/revalidate`。粒度相同（都到路径级），组织方式不同。
- **边界**：按目录自治、想一眼看全站策略时 Nuxt 的中心表更好收敛；页面级自治、策略跟文件走时 Next 更顺。追问：swr: 10 作用在哪层？→ 页面级渲染产物；接口本身的缓存要另在 Nitro 层配，别把页面规则误当接口缓存。

### Q2（6.2）｜ useFetch 在 SSR 下的数据流是怎么走完整的？

- **判断**：服务端取数 → payload 随 HTML 下发 → 客户端 hydration 认领 → 不发第二次请求。
- **展开**：`await useFetch(...)` 顶部直接等，数据先于渲染就位；传统 Vue SSR 的「beforeMounted 前手动预取 + 注水对齐」整套手工程序被做成默认行为。composables/ 目录的公共取数免 import 全局可用。
- **边界**：自动导入的代价是来源不可见——评审时先确认函数在 composables/ 还是组件内部，避免「魔法名」失控。追问：它与 Next 的 RSC await fetch 对应吗？→ 解决同一个问题（数据先于渲染），但 Nuxt 组件仍是客户端组件、代码包照发，没有 RSC 的「服务端代码不下发」。

### Q3（6.3/6.4）｜ ssr: false 的页面，HTML 里到底有什么？

- **判断**：只有布局壳——整个页面组件都不参与服务端渲染，连页面标题文案都不在 HTML 里。
- **展开**：实测生产构建后 `GET /client-only` 返回 200，HTML 不含「纯 CSR 页」五个字，curl 只拿到 app.vue 的布局壳。「不服务端渲染」不是「少渲染一段」，是整页跳过。
- **佐证**：实测读数（2026-10-13）：`/` 含「订单中心（Nuxt）」（SSR）；`/orders/1001` 含「订单 1001」（SWR 回源）；`/client-only` 不含页面文案。
- **边界**：这正是渲染架构篇「CSR 首屏由网络与解析决定」在框架层的直接体现。追问：要「页面里局部 CSR」怎么办？→ 不是 ssr:false，用 `<ClientOnly>` 组件包住那块。

## 7. mini-nuxt：SFC 双遍编译与 Vue SSR

### Q1（7.1）｜ 为什么说 SSR 构建是「同一个 SFC 编译两遍」？

- **判断**：server 遍 `compileTemplate({ ssr: true })` 产出直拼字符串的 `ssrRender`（不建 vdom），client 遍产出标准 `render`（建 vdom + 挂事件）——两份产物职责不同。
- **展开**：mini-nuxt 的 esbuild 插件（46 行）就是 mini 版 vite vue 插件：解析 SFC → script 转译 → 模板按模式编译 → 合成组件。Nuxt 的双产物构建就是这段逻辑的工业版。
- **佐证**：实测编译产物里同一个页面在 server 包里是 `ssrRender(_ctx, _push, ...)` 直拼 HTML，在 client 包里是 `render(_ctx, _cache)` 返回 vdom。
- **边界**：如果只用 client 版 render 做服务端渲染也能出 HTML（走 vdom 序列化），但放弃了 ssrRender 的字符串直拼优化。追问：Vue 为什么不直接用 vdom 序列化？→ 能，但每节点都要建对象再序列化；ssrRender 跳过建树，这是它的性能来源。

### Q2（7.2）｜ 手写 Vue SSR 最容易踩的三个坑是什么？

- **判断**：asyncData 的挂载位置、应用实例复用、props 未声明。
- **展开**：① asyncData 挂在组件对象（default 导出）上不在模块命名空间上，取错位置拿到 undefined、页面白屏；② 应用实例持有状态，必须每请求 `createSSRApp`，跨请求复用会串单；③ `h(comp, props)` 传的 props 要在组件里声明 `props: ['orders']` 才进实例，否则落进 `$attrs`，模板取不到——实测报 `Property "orders" was accessed during render but is not defined`。
- **边界**：三坑的共同特征是「不报架构错误，报的是渲染期静默异常」。追问：怎么快速定位 props 没进去？→ Vue warn 会点名属性名；先查组件的 props 声明，再查取值路径。

### Q3（7.3）｜ Vue 和 React 分别把「SSR 还是 CSR」编码在哪里？

- **判断**：Vue 编码在创建应用的 API 上（createApp vs createSSRApp），React 编码在挂载 API 上（render vs hydrateRoot）。
- **展开**：`createApp().mount()` 直接整棵重建；`createSSRApp().mount()` 先尝试复用已有 DOM。React 侧 `render` 重建、`hydrateRoot` 认领。两家的分野点不同，语义完全同构。
- **佐证**：两端锚点对照读数：React 的 SSR 字符串用 `<!-- -->` 分隔文本节点，Vue 用 `<!--[-->`/`<!--]-->` 包住列表段——两家都在为 hydration 对齐埋锚点。
- **边界**：锚点形态不同意味着两家的失配模式也不同：React 的失配常来自文本节点合并/错位，Vue 的常来自列表段边界错位。追问：手写渲染器怎么对应？→ 「对齐单位是 childNodes 下标 + 服务端不插空白」这条结论两家通用。

## 8. 综合收口：框架选型与边界

### Q1（8.1）｜ Next 和 Nuxt 怎么选？架构层面的差异是什么？

- **判断**：最本质的差异是**有没有 RSC**：Next 默认 Server Component、服务端组件代码不进客户端包；Nuxt 默认全客户端组件、代码包照发。
- **展开**：内容型大站页面树深、注水数据占比高（实测传统 SSR 注水数据占 HTML 22.3%），RSC 砍客户端代码是真实收益。偏向 Nuxt 的信号：Vue 栈、前后端同工程同部署（Nitro）、想要中心化渲染规则表；偏向 Next 的信号：React 栈、页面树深、注水数据成本高。
- **边界**：RSC 也有代价——「两类组件」的写法与心智负担（哪些能用 useState、数据怎么往下传都按类别判断）；交互密集页面所有组件都是客户端组件，RSC 退化成普通 SSR。追问：两家的渲染范式声明机制等价吗？→ 等价（路径级粒度），只差组织方式（中心表 vs 页内导出）。

### Q2（8.2）｜ 什么场景不该上 SSR 框架？

- **判断**：全交互密集的后台工作台、内容不需要被抓且用户有明确预期的壳内页——SSR 只增加服务端成本，CSR 即可。
- **展开**：SSR 换来的是浏览器视角的快（内容随 HTML 到），代价全在服务端：每次重渲染、重等慢数据源（render-lab 实测连发三次 273/279/278ms 一次没省）。后台工作台不需要为爬虫付这份成本。
- **佐证**：实测 FCP（jslag=300）CSR 2192ms vs SSR 504ms 的差距全部来自网络与解析，渲染本身只占个位数毫秒——内容不需要提前到达时，这份成本白付。
- **边界**：「上了 SSR 框架就等于首屏快」仍是常见误判——SSR 只保证内容先到，不保证点得动（TTI 要等客户端运行时下载解析完）。既要 SEO 又不想每次重渲染 → SSG/ISR/页面缓存。追问：框架选错了怎么退？→ 渲染范式声明都是路径级的，可以从混合渲染起步（列表 SSR + 工作台 ssr:false），不必全有或全无。
