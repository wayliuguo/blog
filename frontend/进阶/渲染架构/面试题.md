# 模块面试题 · 渲染架构

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../面试方法论/面试方法论.md)的四步答题法——结论/原理/边界/追问。
> 题目来源：由本模块各篇正文的知识点整理，每题在标题后标注出处（第 N 篇）。

## 一、基础概念

### Q1: CSR / SSR / SSG / ISR 的区别是什么？（第 1 篇）

- **结论**：它们不是四种技术，而是同一个问题「HTML 字符串在哪一刻生成」的四个取值——CSR 在浏览器、SSR 在每次请求、SSG 在构建时、ISR 在构建时但带过期时间。
- **原理**：渲染的产物都是同一棵页面树的字符串，差别只在生成时刻与缓存策略。浏览器渲染要等 JS 下载解析 + 接口往返（实测 FCP 2192ms）；请求时渲染把等待搬到服务端（FCP 504ms）；构建时渲染让请求路径上只剩一次静态字符串写出（FCP 404ms）。
- **边界**：SSR 的产物是 HTML + 注水数据（数据占 22.3%），服务端每次都要重渲染、重等慢接口；SSG 的内容不随请求变化；ISR 用 TTL 换「用户不等重建」，代价是有人看到旧内容。
- **追问**：内容随请求变化、又不想让用户等，选哪个？→ 流式渲染（同一份 SSR，把已就绪的部分先发）或 PPR（静态骨架 + 动态洞）。

### Q2: 什么是同构？它的前提条件是什么？（第 2 篇）

- **结论**：同构指同一份组件代码既能被服务端渲染成字符串、也能被浏览器渲染成 DOM，前提是页面树必须是**纯描述**。
- **原理**：`App()` 返回的是一棵由 `h()` 组成的普通对象树，不含任何 DOM 引用或浏览器 API，所以服务端可以直接 `renderToString` 它；客户端接管时算出的树来自同一份源码，两端结构天然一致。
- **边界**：三条约束必须守住——组件渲染期不能有副作用（不碰 `window`/`localStorage`）、数据必须**先于**渲染就位、客户端要能重建出**完全相同**的树。任何一条破了，要么报错，要么静默失配。
- **追问**：同构最大的收益是什么？→ 页面结构只写一次，不会出现「两端各写一遍、改一处忘一处」。

### Q3: 注水（hydration）是什么？它到底做了什么？（第 2 篇）

- **结论**：注水不是「把 HTML 再渲染一遍」，而是**把事件监听器与状态接到已经存在的 DOM 上**。
- **原理**：服务端渲染的产物里没有任何事件监听器（实测 `renderToString` 输出 1.8KB，零监听器）。客户端拿同一棵树去「认领」已有 DOM：第 i 个虚拟子节点对第 i 个真实子节点，标签一致就复用并补属性（这里是挂事件的地方）。
- **边界**：理想形态是**一次 DOM 写入都不发生**——实测两端一致时 97 个节点全部复用、真实 DOM 突变 0 次。反过来说，注水期一旦出现 DOM 突变，就说明前面白渲染了。
- **追问**：不做注水直接重建行不行？→ 行，但实测丢弃 97 个节点、重建 97 个，服务端那份 HTML 就只剩「用户先看一眼」的价值。

### Q4: 什么是流式渲染？（第 2 篇）

- **结论**：流式渲染不改变「服务端渲染」这件事，只改变**什么时候把已经渲染好的部分交出去**——能发的先发。
- **原理**：遇到「边界」节点时不阻塞，先写一段兜底（骨架）占住位置，把取数 Promise 登记下来，然后继续渲染后面的内容；数据到齐后把真内容装进 `<template>` 发过去，用一段自删脚本原位替换。
- **边界**：实测壳 3ms 就发出、整页 266ms 才完成，首个内容字节比非流式 SSR 早 261ms；代价是 HTML 从 5.3KB 涨到 6.5KB（占位、template、补位脚本、运行时）。**它把「看得见」提前，不把「点得动」提前**。
- **追问**：为什么流式的入口模块没有更早执行？→ 全量注水需要一份完整数据，而流式的数据要等最后一个边界才凑齐（1650ms vs 1679ms，实测几乎不变）。

### Q5: 什么是岛化（Islands）？（第 3 篇）

- **结论**：岛化把整页重新划成「静态的海」与「需要 JavaScript 的岛」——服务端渲染完整页面但只给岛打标记，客户端入口只认识那些标记。
- **原理**：客户端不再需要算出整棵树，所以静态组件的代码根本不用下载。实测全量 hydration 要 14 个模块 16.4KB，岛激活只要 6 个模块 9.4KB，**少下载 7.0KB，是整份客户端的 42.8%**，而挂上的监听器数量与按钮行为完全相同。
- **边界**：省的是**业务代码，不是运行时**——`vdom` + `hydrate` 共 5.5KB 是框架的地板价，只要还有一处交互就得下载。所以「页面很小、只有一两个交互点」时，岛化的绝对收益可能还不如换一套更轻的框架。
- **追问**：岛化的收益什么时候最大？→ 静态内容多、交互点少的页面（文档站、商详、内容页）；整页都在交互的场景收益接近零。

### Q6: ISR 是什么？它为什么能省掉服务端渲染的耗时？（第 1 篇）

- **结论**：ISR = SSG + 过期时间 + 后台重建，用的是 `stale-while-revalidate` 在页面层的版本。
- **原理**：首次请求回源渲染（实测 266ms），之后命中缓存（2ms）；过了 TTL 的那次请求**仍然只花 4ms**——它返回旧内容，同时后台开始重建；重建完成后又是命中（1ms）。**用户永远不等重建。**
- **边界**：代价是有人会看到旧内容，能旧多久由 TTL 决定。判断能不能接受问两句：内容错了会不会造成损失？旧内容能忍受多旧？价格、库存、余额这类数据不适合。
- **追问**：ISR 与「CDN 缓存页面」的区别？→ ISR 是应用层的一份带 TTL 的缓存 + 后台重建，可以进行按路径的参数化生成；CDN 缓存是同一份产物发给所有人，失效靠手动或 TTL。

### Q7: TTFB 与 FCP 有什么区别？为什么 SSR 的 FCP 紧贴 TTFB？（第 1 篇）

- **结论**：TTFB 是「第一个字节到达」，FCP 是「第一个像素画出来」；SSR 的 FCP 靠 TTFB 是因为**内容随 HTML 一起来**。
- **原理**：SSR 的 HTML 里已经有完整内容，浏览器解析到就能画，中间只隔着一次解析；实测 SSR 的 TTFB 374ms、FCP 504ms，差 130ms。CSR 则要等「HTML 到达 → JS 下载解析 → 接口往返 → 建 DOM」四条腿走完，实测 FCP 2192ms，而建 DOM 本身只占个位数毫秒。
- **边界**：读表口径要先说清——无头环境里 `load` 与首帧的先后不严格（CSR 那行 FCP 甚至比 `load` 晚），判断「用户什么时候看到内容」要看 FCP 与「内容出现时刻」两列。
- **追问**：SSR 的 FCP 好，是不是就代表体验好？→ 不代表，还要看可交互时间（TTI）：服务端渲染先到的是内容，事件要等客户端运行时下载解析完才挂上。

### Q8: RSC 与 SSR 的区别是什么？（第 3 篇）

- **结论**：SSR 是「把同一棵组件树在服务端渲染成 HTML」；RSC 是「在服务端**求值**一部分组件」，产物是一棵已求值的描述树。
- **原理**：SSR 要把整棵树的 props 序列化下发（实测注水数据占 HTML 22.3%）；RSC 里服务端组件的代码**完全不进客户端包**，只有客户端组件那部分需要下发。服务端组件还能直接查库、读文件、调内部服务。
- **边界**：代价是「两类组件」的写法与心智负担（哪些能用 `useState`、数据怎么往下传都要按类别判断）；交互密集的页面所有组件都是客户端组件，RSC 就退化成普通 SSR。**它是架构级选择，不是性能开关，也不替代 SSR。**
- **追问**：RSC 解决的是哪一类成本？→ 注水数据随组件树规模增长的成本——树越深、数据越多，整份 props 下发越不划算。

## 二、机制与原理

### Q9: CSR 的首屏时间由什么决定？（第 1 篇）

- **结论**：由**网络与解析**决定，不由渲染决定。
- **原理**：CSR 首屏 = HTML 到达 + JS 下载解析 + 接口往返 + 建 DOM。实测把 JS 的网络延迟从 0 加到 300ms（`jslag`），CSR 的 FCP 从 640ms 涨到 2192ms（3.4 倍），而 SSR / SSG / 流式基本不动（500ms 左右 → 400~500ms）。同一份代码，渲染耗时始终是个位数毫秒。
- **边界**：骨架屏把 FCP 提前，但只解决「看起来在加载」，不解决「内容什么时候到」——LCP 与内容出现时刻依然压在最后。
- **追问**：那 CSR 还有存在价值吗？→ 有。内容不需要被爬虫抓、不被社交卡片引用、用户有明确预期的场景（后台工作台、登录后仪表盘、桌面端壳内页面），CSR 换来的构建简单与缓存粒度清晰是净收益。

### Q10: 为什么 SSR 每次请求都省不下时间？（第 2 篇）

- **结论**：因为它每次都要把同样的树重渲染一遍、把慢接口重等一遍——SSR 没有「缓存」这个环节。
- **原理**：实测 SSR 连发三次，响应头到达 273 / 279 / 278ms，一次都没省下；服务端自己记的耗时（`X-Render-Ms`）是 266 / 275 / 275ms。对照 SSG 的服务端耗时列是 **0ms**——那 260ms 在 `listen()` 之前就花完了。
- **边界**：SSR 的「快」是**浏览器视角的快**（内容随 HTML 一起来），服务端反而更累：CPU、内存、慢接口等待全压在它身上。SSG 与 ISR 省掉的正是这一段。
- **追问**：想省掉这一段又不能让内容静态化，怎么办？→ 加缓存层（页面级 TTL / CDN / ISR），或在服务端缓存取数结果而不缓存渲染产物。

### Q11: 为什么 SSR 的响应时间会绑定最慢的接口？（第 2 篇）

- **结论**：因为 `await Promise.all` 的语义是「全部就绪才继续」，整体耗时等于**更慢的那个**。
- **原理**：实验台两个慢接口是**并发**发的（评价 260ms、推荐 130ms），但整页 HTML 要等两个都回来才发得出去，所以绑在 260ms 上。这 266ms 里真正属于渲染的只有个位数毫秒，其余全是等待。
- **边界**：这就是「一个慢区块拖垮整页」的根因。页面只要有一个慢数据源（个性化推荐、实时库存、第三方接口），哪怕其余 90% 的内容本机立即可得，也发不出去。
- **追问**：怎么破？→ 流式渲染：把边界画在数据来源上，快的区块先发；或把慢区块降级（先骨架、后补位）。

### Q12: `renderToString` / `renderDOM` / `hydrate` 三者的区别？（第 2 篇）

- **结论**：`renderToString` 树 → 字符串（服务端）；`renderDOM` 树 → 新建 DOM（客户端）；`hydrate` 树 → **认领已有 DOM**（客户端）。
- **原理**：三者都走同一棵页面树，差别在「目标是什么」。`renderToString` 递归拼字符串，产物里没有事件；`renderDOM` 创建节点、`replaceChildren` 到容器；`hydrate` 按 `childNodes` 下标对齐，标签一致就复用、补属性（挂事件），不一致才整棵重建。
- **边界**：`hydrate` 有一个必须记住的坑——对齐单位是**容器的 `childNodes`**，不是容器自己。如果拿 `App` 的根 `div` 去和挂载点 `#app` 认亲，结构会从头错位、整棵树重建。
- **追问**：三者共用的那步是什么？→ 把 `children` 塞进 `props`（函数组件拿子节点的唯一通路）。自己实现渲染器时漏掉这一步，所有带子节点的组件都会渲染成空。

### Q13: hydration 的对齐单位是什么？为什么？（第 2 篇）

- **结论**：**容器的 `childNodes` 下标**——第 i 个虚拟子节点对第 i 个真实子节点。
- **原理**：服务端渲染时 `App` 的根 `div` 挂在 `#app` 里面，所以接管时应该让「`#app` 的第 0 个子节点」去认领「`App` 根的 `div`」。这个细节直接决定了整棵树能不能复用。
- **边界**：两个推论——① 服务端渲染子树时**子节点之间不能插入空白**，多一个换行文本节点就会让后续下标全部错位；② 任何一层多余的包裹（比如给岛再套一个 `div`）都会让那棵子树失去复用资格。实验台两个坑都踩过，症状都是「明明两端一致，却什么都没复用」。
- **追问**：服务端多渲染出来的节点怎么处理？→ 必须删掉，否则它会成为幽灵节点，下次更新时造成错位。

### Q14: 注水失配有哪几种形态？为什么不报错？（第 2 篇）

- **结论**：三种——**文本不一致**（静默改写）、**标签不一致**（整段重建）、**结构多出节点**（删除）；只有标签不一致这类严重情形才会被你注意到。
- **原理**：实测四个变体：「两端一致」复用 97 个、0 次 DOM 突变；「价格口径不一致」复用 97 个但**改写 8 处文本**（`characterData` 突变 8 次）；「标签不一致」丢弃 14 个节点、重建 2 个；「不做注水直接重建」丢弃 97、重建 97。
- **边界**：**失配不一定报错**——文本不一致只是白干（服务端为这 8 个价格做的工作全作废），连一个警告都没有，所以最难发现。经典来源就那几类：时区、货币与数字格式化、日期格式、随机数、不稳定排序，共同特征都是「同一份数据在两端算出不同结果」。
- **追问**：用什么硬指标把失配钉死？→ 「注水期不应有任何 DOM 写入」——用 `MutationObserver` 数真实 DOM 突变次数，clean 变体应该是 0。

### Q15: 流式渲染的补位顺序由什么决定？（第 2 篇）

- **结论**：由**谁先好**决定，不是由谁在页面里靠前决定。
- **原理**：实现上是对所有边界任务的 promise 做 `Promise.race`，先完成的先产出补位段。实测顺序是 `shell → recommend:fill → reviews:fill`——推荐位在页面里排在评价**之后**，但它 130ms 就好了、评价要 260ms，所以它先补位。
- **边界**：这正是流式比「一次发完整 HTML」更复杂的地方：每一段都要能独立定位、独立替换。所以分段的边界应该画在**数据来源**的边界上（评价接口一段、推荐接口一段），而不是画在**组件层级**的边界上——按组件树层级切会切出几十个几百字节的碎片，每片都带自己的占位与模板，TCP 效率被拖垮。
- **追问**：分段的标记怎么做到「既是服务端切分点、又是浏览器到达时间戳」？→ 用一段自删的 `<script>` 做标记：它在浏览器侧往 `window.__chunks` 里记一笔时间，同时给 Node 侧的解析提供切分位置。

### Q16: 流式渲染为什么没能提前可交互时间？（第 2 篇）

- **结论**：因为全量注水需要一份**完整**的数据对象去重建整棵树，而流式下这份数据要等最后一个边界之后才凑齐。
- **原理**：实测流式的入口模块开始执行是 1650ms、非流式 SSR 是 1679ms，几乎不变。文档尾（注水数据 + 入口模块）被那句 `await reviewsPromise` 压到了最后一个慢接口之后。所以流式把「看得见」的边界提前了很多，没有把「点得动」提前。
- **边界**：要连 TTI 也提前有三条路——① 分段下发注水数据（每个边界把这段 props 一起塞进去，客户端要能接受数据分批到达）；② 改成岛化（交互点自带 props，激活不必等任何东西）；③ 接受「先看见后点得动」，用骨架或 `aria-busy` 把等待表达清楚。
- **追问**：为什么说流式和全量注水「天然别扭」？→ 前者希望尽早交付片段，后者必须等全部数据——两个目标在时间轴上是相反的。

### Q17: 岛化为什么能省下这么多 JS？省的是哪一部分？（第 3 篇）

- **结论**：因为客户端不再需要认识整棵树——**只有进注册表的交互组件的代码会被下载**。
- **原理**：全量 hydration 必须能算出整棵树，所以每个组件的代码都得在客户端有一份；岛只按 `data-island` 的名字去注册表取组件，页面里没有的组件根本不进这份图谱。实测被省掉的是 `app.mjs`、`entry-full.mjs`、`lib/cities.mjs`、四个静态组件、`island.mjs`（服务端那一半）、`lib/serialize.mjs`、`lib/price.mjs`。
- **边界**：省不掉的是 `vdom.mjs`（2.8KB）+ `hydrate.mjs`（2.7KB）+ 交互组件本身（694B）——只要还有一处交互，建元素与接管的代码就得在。另外注意入口开始执行时刻实测 1643ms vs 1631ms，**岛化甚至还略晚一点**：`jslag` 下模块是并发下载的，决定入口开始时刻的是依赖链的**段数**，不是总字节数；省下的字节要等带宽或解析成为瓶颈时才变成时间收益。
- **追问**：岛与岛之间怎么通信？→ 无法直接共享状态，需要显式通过属性或全局事件。这会改变组件的写法，是岛化的隐性成本。

### Q18: 选择性注水与 PPR 分别解决什么问题？（第 3 篇）

- **结论**：两者都在补流式留下的那个缺口——**内容看得见了，但点不动**。
- **原理**：选择性注水把「注水顺序」变得可干预：浏览器先只给用户正要交互的那一段注水，其余延后，于是 TTI 不再由「最后一个慢区块」决定，而由「用户想看哪里」决定。PPR 把静态与动态分开：页面的静态骨架在构建时生成（等同 SSG），动态的洞在请求时用流式补上，于是第一个字节可以立刻从 CDN 边缘出去。
- **边界**：选择性注水的前提是渲染器支持**按标记粒度注水**（也就是岛化那套机制在更大范围内的版本）；PPR 要求页面能被可靠地切成「静态骨架 + 动态洞」两半，切得不好会出现骨架与真内容布局跳动。
- **追问**：PPR 与第 1 篇那张表里的哪个方案等价？→ 它是 SSG 与流式两个极限的组合：TTFB 走 SSG（几毫秒），内容完整性走 SSR。

## 三、排障与选型

### Q19: 注水后页面内容「闪」了一下（服务端内容被替换），怎么排查？（第 2 篇）

- **结论**：这是**失配**，先判断是哪一类：文本不一致（只是改写，观感上是一闪）还是标签/结构不一致（整段重建）。
- **原理**：文本不一致的表现是「内容没变多少但闪了一下」——实测 8 个价格被逐个改写，`characterData` 突变 8 次；标签不一致的表现是「一整块被换掉」，实测丢弃 14 个节点、重建 2 个。两者都不报错。
- **边界**：排查手段是量 `MutationObserver` 的三个计数（childList / attributes / characterData）：`characterData` 有值 → 格式口径不一致；`childList` 有值 → 结构不一致。按这个线索去两端找同一份数据的两种算法：时区、货币与数字格式化、日期格式、随机数、不稳定排序。
- **追问**：为什么不直接看控制台警告？→ 因为 hydrate 的失配绝大多数是静默的——它只是「白干」，不会抛错。

### Q20: 「服务端和客户端渲染的树明明一样，hydration 却全量重建了」，怎么查？（第 2 篇）

- **结论**：先查**对齐单位**，再查**空白节点**，最后查**多余的包裹**。
- **原理**：对齐单位是容器的 `childNodes`。三个对应的坑：① 拿 `App` 根 `div` 去和挂载点 `#app` 认亲（少一层容器），整棵树从根错位；② 服务端拼接时子节点之间插了换行文本节点，后续下标全部错位；③ 给可交互子树多套了一层 `div`（岛化里最容易犯），那棵子树失去复用资格。实验台这三个坑都踩过。
- **边界**：症状有共同特征——「复用数是 0 或断崖式下降、丢弃数等于整棵树」。这时不要去调渲染逻辑，先数节点层级。
- **追问**：怎么快速确认是结构问题而不是数据问题？→ 结构问题会让 `childList` 突变，数据问题只会让 `characterData` 突变；两者一分开，方向就定了。

### Q21: 上了流式渲染，HTML 变大了、LCP 也没明显改善，是不是白做了？（第 2 篇）

- **结论**：不一定。先分清你优化的是 FCP 还是 LCP，以及慢的那一段是「等数据」还是「等 JS」。
- **原理**：流式的收益是**让已就绪的部分先走**——实测壳 3ms 发出、首个内容字节比非流式早 261ms，浏览器侧 FCP 340ms vs 508ms、商品列表 235ms vs 399ms。代价是 HTML 从 5.3KB 涨到 6.5KB。如果 LCP 元素本身就在慢区块里（比如页面最大的图或列表在评价接口那一段），流式当然救不了它。
- **边界**：网络越好，这份 1.2KB 的固定开销越不值；网络越差越值。另外注意「流式的评价出现时刻」与「非流式的整页出现时刻」不是同一个东西，别直接对比得出「流式更慢」的结论。
- **追问**：想救 LCP 该做什么？→ 先定位 LCP 元素属于哪一段：在静态壳里就检查资源加载与渲染阻塞；在慢区块里就考虑把这段数据提前（并行预热）或给它更靠前的边界。

### Q22: 什么情况不该上 SSR？（第 1 篇）

- **结论**：内容不需要被抓取/引用、且用户对「先加载再出现」有明确预期的场景，不该上 SSR。
- **原理**：SSR 换来的是**浏览器视角的快**，代价全在服务端——每次请求都要重渲染、重等慢接口（实测连发三次 273/279/278ms 一次没省），而且响应时间绑定最慢的数据源。后台工作台、登录后仪表盘、桌面端壳内页面都不需要为爬虫付这份成本。
- **边界**：另一个误判是「上了 SSR 就等于首屏快」。SSR 只保证**内容先到**，不保证**点得动**：框架运行时若很大，用户在 FCP 之后还要等它下载解析完才能交互。
- **追问**：既要 SEO 又不想让服务端每次都重渲染？→ SSG 或 ISR（内容变化频率低于构建频率时），或用页面缓存把 SSR 的产物缓存起来。

### Q23: 什么情况不该上岛化？（第 3 篇）

- **结论**：**交互密集的页面**不该上岛化——收益接近零，却要付写法一致性与跨岛通信的代价。
- **原理**：岛化的收益来自「静态内容多、交互点少」。实测省下 42.8% 的客户端 JS，但省的是业务代码，`vdom` + `hydrate` 那 5.5KB 的运行时地板价省不掉。整页都要交互时每个组件都是岛，等于没有省。
- **边界**：第二个隐性成本是**状态共享**——岛之间无法直接共享状态，必须显式通过属性或全局事件通信，这会改变组件的写法。第三个是粒度判断：岛的粒度不是「组件」，而是「需要 JavaScript 的区域」（一个筛选器、一个图表）。
- **追问**：怎么判断一个页面值不值得岛化？→ 数一数「需要事件的区域」占多少；如果整个可视区几乎都需要，就直接全量注水。

### Q24: 边缘渲染适合什么业务？（第 3 篇）

- **结论**：适合**用户与源站地理距离大、且渲染逻辑不依赖只能中心访问的数据**的业务。
- **原理**：SSR 的耗时可以拆成计算（渲染 + 取数）与传输（用户 → 服务端 → 用户），边缘渲染动的是第二块——把服务端渲染放到离用户最近的城市节点。**它不减少计算**：如果那 260ms 的慢接口还得回中心机房查，边缘只是把传输那段省下来。
- **边界**：边缘运行时还有额外约束——冷启动更敏感、包体积有上限、可用 API 是子集（通常没有完整文件系统）、不能直连内网。另外要区分：**边缘渲染 ≠ CDN 缓存**，前者在边缘**执行**渲染逻辑、可按请求头与地理位置产出不同结果，后者是共享同一份产物。
- **追问**：为什么它和 SSG / PPR 天然搭配？→ 因为能在边缘完成渲染的前提就是「不依赖只能在中心查的数据」，而静态骨架正好满足这一点。

## 四、场景设计题

### Q25: 场景：一个内容站，文章每天更新几次，要 SEO，页面基本没有交互，怎么选渲染方案？（第 1 篇）

- **结论**：**SSG（构建时生成）+ 增量更新**，或内容更新频繁到构建跟不上时用 ISR。
- **原理**：内容变化频率低于构建频率是 SSG 的判据。实测 SSG 服务端耗时 0ms、响应头 3~4ms——渲染那 260ms 在构建时花掉了，请求路径上一点都不剩，同时 HTML 自带完整内容，爬虫能直接抓。每天更新几次意味着重新构建完全可行。
- **边界**：纯 SSG 在「内容量大 + 更新频繁」时会拖长构建时间，这时改 ISR：TTL 设成可接受的陈旧窗口（实测命中 2ms、过期返回旧内容 4ms 且后台重建）。注意 ISR 的取舍问两句：内容错了有没有损失、旧内容能忍受多旧。
- **追问**：为什么不用 SSR？→ 内容不随请求变化，SSR 每次都重渲染是纯浪费；而且 SSR 的响应时间还绑定最慢的数据源。

### Q26: 场景：电商首页，主体内容很快就绪，但有个 300ms 的个性化推荐接口，怎么设计？（第 1 篇、第 2 篇）

- **结论**：**SSR + 流式渲染**，把推荐位切成一个独立的边界。
- **原理**：实测壳（页头 + 商品列表）在 3ms 就发出去了，推荐位 141ms 补位、评价 265ms 补位，整页 266ms 完成——用户先拿到 90% 的内容。边界要画在**数据来源**上（推荐接口一段），不要按组件层级切。
- **边界**：注意两笔代价——① HTML 从 5.3KB 涨到 6.5KB；② 全量注水的入口要等最后一个边界，可交互时间不会提前（1650ms vs 1679ms）。如果推荐位的交互还很重要，就把推荐位本身改成岛（自带 props、不等全局数据）。
- **追问**：如果推荐接口经常超时怎么兜底？→ 边界处给骨架 + 超时后补一段降级内容（热门商品），保证「这一块永远有东西」，而不是整页等它。

### Q27: 场景：老项目从 CSR 迁移到 SSR，怎么系统地排查注水失配？（第 2 篇）

- **结论**：把「注水期零 DOM 写入」当验收指标，用 `MutationObserver` 分三个维度（childList / attributes / characterData）量化，再按维度定位根因。
- **原理**：① 在 `hydrate` 前后挂观察器，分别统计三类突变次数；② `characterData` 有值 → 找两端格式口径不一致（时区、货币、日期、随机数、排序），实测这类会静默改写 8 处文本、不报错；③ `childList` 有值 → 查结构对齐（`childNodes` 下标、空白节点、多余包裹），实测标签不一致会丢弃 14 个节点；④ 用「复用数 / 丢弃数」判断严重程度，理想是复用 N、丢弃 0。
- **边界**：迁移期最常见的三类改动会引入失配——把服务端能访问的全局状态（登录态、时区）直接读进组件；把 `Math.random()` 或用当前时间当 key；列表排序不稳定。还有一个隐藏项：服务端拼接时为了可读性插了换行，客户端没有——这类「看起来无害」的空白会让整棵子树重建。
- **追问**：怎么防止回归？→ 把「clean 变体 0 突变」写进 CI，像实验台那样把四个变体固定下来当回归用例。

### Q28: 场景：文档站，整页只有搜索框和侧边栏折叠需要交互，客户端 JS 怎么砍？（第 3 篇）

- **结论**：**岛化**，把搜索框与折叠面板各注册成一个岛，其余内容纯静态输出。
- **原理**：文档站是岛化的教科书场景——静态内容占绝对多数、交互点只有两三个。做法是服务端渲染时给这两个子树打 `data-island` + `data-props` 标记，客户端入口只从注册表取这两个组件，逐个 `activate`（本质是对每个标记调一次 `hydrate`）。实测这条路能少下载 42.8% 的客户端 JS，而按钮行为与监听器数量完全不变。
- **边界**：两点必须做对——① 标记落在**子树自己的根元素**上，不能为了打标记再套一层 `div`，否则整棵子树失配重建；② 注册表里只放交互组件，页面里没有的组件不要进图谱。另外 `vdom` + `hydrate` 那 5.5KB 的运行时地板价省不掉，如果连这个都想省，就得放弃手写 vdom、换成更小的方案。
- **追问**：搜索框需要拿到整个文档的索引数据，怎么传？→ 索引数据体积大，不要塞进 `data-props`；把「索引的获取」放在岛内部（激活后再 fetch），`data-props` 只放启动必需的小配置。

### Q29: 场景：面向全球用户的营销页，首屏 TTFB 一直很高，怎么优化？（第 1 篇、第 3 篇）

- **结论**：先拆 TTFB 的构成，再决定是「缩短传输」还是「消掉渲染」——通常两手都要。
- **原理**：① 如果慢在传输（用户离源站远），考虑边缘渲染：把 SSR 放到离用户最近的节点，用户到服务端的往返从跨洋变成城内；② 如果慢在服务端渲染与取数（实测 SSR 每次 266ms，其中慢接口占 260ms），先看内容能不能静态化——营销页内容通常不随请求变，改成 **SSG** 让请求路径上只剩一次静态字符串写出（实测服务端耗时 0ms），或者 **PPR**：静态骨架构建时生成，动态的洞（地区化文案、个性化头图）流式补。
- **边界**：边缘渲染需要改造运行时依赖（可用 API 是子集、不能直连内网数据库），且**边缘渲染 ≠ CDN 缓存**——前者执行渲染逻辑、可按请求差异化，后者共享同一份产物。如果渲染逻辑必须连中心数据库，就不要把它整体搬到边缘。
- **追问**：怎么判断该先做哪一步？→ 先看 TTFB 里「服务端处理时间」占多少（用 `Server-Timing` 或像实验台那样在响应头里记 `X-Render-Ms`）：服务端占大头就先静态化，传输占大头就先上边缘。
