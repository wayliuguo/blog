# 新兴渲染范式

前两篇讲的 CSR / SSR / SSG / ISR / 流式，都建立在同一个默认值上：**客户端要能算出整棵树**，所以整棵树的代码和整份数据都得下发。岛化、RSC、选择性注水、边缘渲染这四件事，做的都是同一个动作 —— 拆掉这个默认值。其中岛化在本实验台有完整实测，RSC 与边缘渲染需要多运行时或跨地区节点，只做原理说明并明确标注。

## 一、整页接管是上一代默认值

全量 hydration 的隐含假设是「客户端必须重建整棵页面树」，于是每个组件的代码都得在客户端有一份。把这份代价量化一下：本实验台的页面很朴素，但它已经要下载 **14 个模块、16.4KB**：

```
| 客户端入口     | JS 文件数 | JS 字节 | 复用节点 | 新建节点 | 挂上的监听器 | 按钮点得动 | 入口开始执行 | FCP    |
|----------------|-----------|---------|----------|----------|--------------|------------|--------------|--------|
| 全量 hydration | 14        | 16.4 KB | 97       | 0        | 1            | true       | 1631 ms      | 512 ms |
| 岛激活         | 6         | 9.4 KB  | 5        | 0        | 1            | true       | 1643 ms      | 520 ms |
```

把两张脸对齐看：97 个节点被接管，但**挂上的监听器只有 1 个**。另外 96 个节点的代码被下载、被解析、被 `hydrate` 走了一遍，最后什么也没做 —— 它们只是「静态内容」，服务端渲染完就再也没有变化。**这就是整页接管的浪费，量化下来是「96 个节点的代码为 1 个交互点陪跑」。**

## 二、Islands：只给交互点下发 JavaScript

岛化的思路是把「组件树」重新划成两块：**静态的岛之间是海，需要有 JavaScript 的区域是岛**。服务端渲染完整页面，但只给岛打标记；客户端入口不再认识整棵树，只认识那些标记。

服务端那一半只做两件事 —— 给可交互子树的根打标记、把 props 序列化进属性：

> 摘自 `./code/render-lab/src/island.mjs`（运行：`npm run island`）

```js
export function Island({ name, props, children }) {
    const child = children.length === 1 ? children[0] : h('div', null, children)
    const root = typeof child.type === 'function' ? resolve(child) : child
    return {
        ...root,
        props: { ...root.props, 'data-island': name, 'data-props': serializeData(props || {}) }
    }
}
```

这段代码里有一句注释值得单独抄出来（原文在文件头上）：

> 标记必须落在**子树自己的根元素**上，不能再套一层 div —— 套了的话激活时组件根会去和外壳认亲，整棵子树被判定为失配、全部重建。

这和第二篇 `hydrateRoot` 那个「对齐单位是容器的子节点」是同一个坑的两张脸：**hydration 靠结构对齐，任何一层多余的包裹都会让整棵子树失去复用资格**。本实验台最初就是在 `Island` 里多套了一个 `div`，症状是「岛激活后 5 个节点全被重建、一个都没复用」。

序列化那一半也是必须的，因为 props 要穿过 HTML 属性：

> 摘自 `./code/render-lab/src/lib/serialize.mjs`（运行：`npm run island`）

```js
export function serializeData(data) {
    return JSON.stringify(data)
        .replace(/</g, '\\u003c') // 防 </script> 提前闭合
        .replace(/\u2028|\u2029/g, (c) => (c === '\u2028' ? '\\u2028' : '\\u2029'))
}
```

`<` 必须转义成 `\u003c`，否则数据里只要出现 `</script>` 就会把外层脚本提前闭合 —— 这是把 JSON 内联进 HTML 的通用规则，服务端那份注水数据用的是同一份实现。

## 三、岛为什么能省下这些：客户端不再需要认识整棵树

浏览器那一半短得出人意料：

> 摘自 `./code/render-lab/src/activate.mjs`（运行：`npm run island`）

```js
export function activate(registry, root) {
    const stats = { islands: 0, missing: 0, reused: 0, created: 0, patched: 0, mismatches: 0, discarded: 0, activated: 0 }
    for (const el of root.querySelectorAll('[data-island]')) {
        const name = el.getAttribute('data-island')
        const factory = registry[name]
        if (typeof factory !== 'function') {
            stats.missing++
            continue
        }
        const props = JSON.parse(el.getAttribute('data-props') || '{}')
        const sub = hydrate(factory(props), el, newStats())
        stats.islands++
        for (const key of ['reused', 'created', 'patched', 'mismatches', 'discarded', 'activated']) stats[key] += sub[key]
    }
    return stats
}
```

它做的其实就是对每个标记调一次 `hydrate` —— 第二篇那套接管逻辑原封不动复用，只是范围从「整页」缩到了「这个标记子树」。所以岛入口也短：

> 摘自 `./code/render-lab/src/entry-islands.mjs`（运行：`npm run island`）

```js
const entryAt = Math.round(performance.now() * 10) / 10
const { value, ...measured } = await Lab.observeMutations('#app', () => activate({ 'like-button': LikeButton }, document))
```

**注册表里只有 `like-button` 一项**，这就是省下字节的全部机制：页面里没有的组件根本不进这份图谱，它们的代码也不用下载。逐个模块看：

```
| 模块                        | 全量 hydration 下载 | 岛化是否下载 | 它服务什么                                     |
|-----------------------------|---------------------|--------------|------------------------------------------------|
| vdom.mjs                    | 2.8 KB              | 仍然要       | 创建元素、挂属性与事件（两端都要）             |
| hydrate.mjs                 | 2.7 KB              | 仍然要       | 接管已有 DOM（全量 hydration 与岛激活共用）    |
| entry-full.mjs              | 1.9 KB              | 不再要       | 全量 hydration 入口                            |
| render-dom.mjs              | 1.4 KB              | 仍然要       | 客户端建 DOM（兜底重建用）                     |
| app.mjs                     | 1.1 KB              | 不再要       | 整棵页面树                                     |
| lib/cities.mjs              | 1.1 KB              | 不再要       | 50 个站点的静态字典                            |
| island.mjs                  | 1.1 KB              | 不再要       | 岛的服务端那一半：给子树打标记（只在服务端用） |
| components/product-list.mjs | 866 B               | 不再要       | 静态商品列表                                   |
| components/reviews.mjs      | 766 B               | 不再要       | 静态评价                                       |
| components/like-button.mjs  | 694 B               | 仍然要       | 唯一的交互点（岛也一样要）                     |
| components/recommend.mjs    | 655 B               | 不再要       | 静态推荐位                                     |
| components/header.mjs       | 570 B               | 不再要       | 静态页头                                       |
| lib/serialize.mjs           | 414 B               | 不再要       | 把 props 序列化到属性里（服务端用）            |
| lib/price.mjs               | 410 B               | 不再要       | 价格格式化                                     |
| activate.mjs                | 不下载              | 仍然要       | 岛激活入口：按标记找组件（只有岛用）           |
| entry-islands.mjs           | 不下载              | 仍然要       | 岛入口                                         |
```

**岛化少下载 7.0KB，是整份客户端的 42.8%**；两者挂上的监听器数量相同、按钮都点得动 —— 省掉的是「不会被用到的那部分代码」，不是功能。表里有三处值得多看一眼：

- **`vdom.mjs` + `hydrate.mjs` 一共 5.5KB，岛化省不掉**。这是框架运行时的地板价：只要还有一处交互，建元素与接管的代码就得在。岛化省的是**业务代码**，不是运行时 —— 所以「页面很小、只有一两个交互点」时，岛化省下的绝对值可能还不如一套轻量框架的自身体积差。
- **`island.mjs` 只在服务端用，岛化后客户端不再下载它**。这是岛化设计上真正讲究的地方：把 `Island`（服务端打标记）与 `activate`（浏览器接管）拆成两个文件，浏览器那份就完全不必包含服务端的逻辑。
- **`lib/serialize.mjs` 两边都被引用**（服务端的注水数据、服务端的岛标记），但在客户端只在「接管时读属性」这条路径上出现 —— 实验台里它确实不再被下载，因为岛激活只 `JSON.parse` 属性、不调用 `serializeData`。

至于「入口什么时候开始执行」：**岛激活是 1643ms，比全量 hydration 的 1631ms 还略晚**。这不是矛盾，而是提醒一件事 —— `jslag` 是按「每个模块的响应 +300ms」模拟的，模块之间**并发**下载，所以决定入口开始时刻的是**依赖链的段数**（两个入口都要 `vdom` + `hydrate`），不是总字节数。**省下的字节要等带宽或解析成本成为瓶颈时，才会变成时间上的收益。** 这也是为什么岛化在弱网、低端设备上收益更明显，在本机理想网络里只体现为「少传了 7KB」。

## 四、RSC：把组件分成两类

> 本节为原理说明。RSC 需要 React 服务端运行时与打包器支持，本实验台没有实测，文中不给出数字。

RSC（React Server Components）与 SSR 的关键区别在于**求值发生在哪一侧、产物是什么**：

| | SSR | RSC |
| --- | --- | --- |
| 服务端做了什么 | 把同一份组件树渲染成 HTML 字符串 | 在服务端**求值一部分组件**，产出一棵「已求值的描述树」 |
| 注水数据 | 整棵树的 props 都要序列化下发 | 只有客户端组件那部分需要下发 |
| 组件代码 | 所有组件都要进客户端包 | 服务端组件的代码**完全不进客户端包** |
| 能力 | 渲染期不能用数据库等只能服务端用的东西 | 服务端组件可以直接查库、读文件、调内部服务 |

它解决的正是第二篇量到的那个隐性成本：**注水数据随组件树规模增长**（22.3%）。一个 CMS 驱动的页面可能有几十层嵌套的数据，如果整棵树的 props 都要序列化下发，HTML 会被数据撑到失去意义的程度。RSC 的做法是让「不需要交互的子树」在服务端就求值完，客户端只收到已经算好的结果，连 props 都不必知道。

代价与边界同样清楚：

- **组件被分成了两类，写法与心智负担都变重**。哪些能用 `useState`、哪些不能、数据怎么往下传，都要按类别判断；这不是「性能开关」，是**架构级的选择**。
- **交互密集的页面没有收益**。如果整页都需要事件与状态，那所有组件都是客户端组件，RSC 就退化成了普通 SSR。
- **它不替代 SSR**。RSC 负责「客户端要下载什么」，HTML 的首屏仍要靠 SSR/SSG 那条路产出，两者是叠加关系。

## 五、Streaming SSR 的进阶：选择性注水与 PPR

> 本节为原理说明，本实验台只实测了基础流式（见第 2 篇第五、六节），**没有实测**选择性注水与 PPR。

第 2 篇量到流式的一个重要边界：**FCP 提前了 168ms，但入口模块开始执行的时刻几乎不动（1650ms vs 1679ms）**。原因是全量注水需要一份完整的数据，而流式的数据要等最后一个边界才凑齐。这留下一个缺口 —— 内容看得见了，但点不动。补这个缺口的两条路：

**选择性注水（Selective Hydration）** 把「注水顺序」变得可干预：浏览器先只给「用户正要交互的那一段」注水，其余部分延后。判据是**真实交互意图** —— 用户点了某块区域、或悬停在上面，那一块就插队。这样 TTI 不再由「最后一个慢区块」决定，而是由「用户想看哪里」决定。它成立的前提是渲染器支持**按标记粒度注水**，也就是岛化的那套机制在更大范围内的版本。

**PPR（Partial Prerendering）** 把静态与动态分开处理：页面的静态骨架在**构建时**生成好（等同 SSG），动态的洞在请求时用流式补上。于是第一个字节可以立刻从 CDN 边缘出去（静态部分无需回源），而个性化的那一小块照旧等待。它是第 1 篇那张「SSG 与流式」表里两个极限的结合：**TTFB 走 SSG 的路子（几毫秒），内容完整性走 SSR 的路子。**

两者共同的思路都是**不再把整页当成一个原子**：注水的原子是「需要交互的区域」，渲染的原子是「数据来源」。第 2 篇给出的分片判据在这里依然适用 —— 边界画在数据来源上，不画在组件层级上。

## 六、边缘渲染：缩短第一段的路程

> 本节为原理说明。边缘渲染需要跨地区的节点网络，本机（单台机器）**无法实测**，与第 1 篇对 HTTP/3 的处理方式一致，不给出数字。

SSR 的耗时可以拆成两块：**计算**（渲染 + 等数据）与**传输**（用户 → 服务端 → 用户）。边缘渲染动的是第二块：把服务端渲染放到离用户最近的那个节点（CDN 边缘），用户到服务端的往返从「跨省/跨洋到源站」变成「到最近的城市节点」。

值得注意的是它**不减少计算**。渲染同样要跑、数据同样要等，如果那 260ms 的慢接口还得回中心机房查，边缘节点只是把传输那段省下来。所以：

- **用户越分散、源站越集中，边缘渲染的收益越大**；用户与源站在同一地区时收益接近零。
- **它与 SSG / PPR 天然搭配**：能在边缘完成渲染的前提是「不依赖只能在中心查的数据」。静态骨架、公开内容、按地区差异化的展示，都适合；需要连内网数据库的个性化数据不适合。
- **边缘运行时有额外约束**：冷启动更敏感、包体积有上限、可用 API 是子集（通常没有完整的 Node 文件系统）、不能直连内网。把一份依赖 `fs` 与本地 SDK 的渲染逻辑部署到边缘，通常要改造。

一个容易混淆的点：**边缘渲染 ≠ CDN 缓存**。CDN 缓存是「同一份产物发给所有人」，边缘渲染是「在边缘**执行**渲染逻辑」，可以按请求头、地理位置、cookie 产出不同结果。前者是存储，后者是计算。

## 七、四种范式怎么选

把这一篇压成一张判断表：

1. **页面交互点密集吗？**
   - 只有零星几处（内容页、商详、文档站） → **岛化**。收益随「静态内容占比」增大。
   - 整页都在交互 → 全量注水反正跑不掉，别为省字节牺牲写法一致性。
2. **组件树很深、props 注水成本高吗？**
   - 是，且大量子树不需要交互 → 值得评估 **RSC**，但先确认团队能接受「两类组件」的写法。
   - 否，注水数据占比在 20% 以下 → 收益有限，第 1 篇的决策树够了。
3. **流式渲染后，TTI 仍是瓶颈吗？**
   - 是（用户抱怨「点了没反应」） → 评估 **选择性注水**；或干脆改成岛化，岛本身不依赖全局数据。
   - 否，用户对「先看见后能点」有预期 → 基础流式足够。
4. **用户与源站地理距离大吗？**
   - 大，且渲染逻辑不依赖只能中心访问的数据 → **边缘渲染**。
   - 小，或渲染必须连内网 → 收益有限，先看传输以外的部分。
5. **静态骨架 + 少量动态洞？**
   - 是 → **PPR**：静态走构建时，动态走流式。

## 小结

- 岛化拆掉的是「客户端要认识整棵树」这个默认值
  - 全量 hydration 实测：14 文件 16.4KB，97 个节点，但只挂 1 个监听器 —— 96 个节点的代码在陪跑
  - 岛激活：6 文件 9.4KB，少下载 7.0KB（整份客户端的 42.8%），监听器数量与按钮行为完全相同
  - 省的是业务代码，不是运行时：`vdom` + `hydrate` 共 5.5KB 的地板价岛化省不掉
  - 入口开始执行 1643ms vs 1631ms —— `jslag` 下模块并发下载，决定时刻的是依赖链段数而非总字节；字节优势要等带宽成瓶颈才变成时间优势
- 岛的实现有两个必须做对的地方
  - 标记落在子树**自己的根元素**上，多套一层会导致整棵子树失配重建
  - 注册表只放交互组件：页面里没有的组件不进图谱，代码也就不下载
  - props 序列化进属性时 `<` 要转义成 `\u003c`，防 `</script>` 提前闭合
- RSC 改的是「组件在哪一侧求值」（原理，无实测）
  - SSR 下发整棵树的 props；RSC 只下发客户端组件那部分，服务端组件代码不进客户端包
  - 解决的是注水数据随组件树增长的成本（第 2 篇实测占比 22.3%）
  - 代价是「两类组件」的写法与心智负担；交互密集页面无收益；不替代 SSR
- 选择性注水与 PPR 补的是流式留下的缺口（原理，无实测）
  - 流式把 FCP 提前 168ms，但 TTI 几乎不动（1650ms vs 1679ms）
  - 选择性注水按交互意图给区域插队，把 TTI 与「最后一个慢区块」解耦
  - PPR：静态骨架构建时生成、动态洞流式补，TTFB 走 SSG、完整性走 SSR
- 边缘渲染缩短的是传输，不是计算（原理，无实测）
  - 计算与取数照旧，若数据仍要回中心查，省下的只是传输那段
  - 与 SSG / PPR 天然搭配：能在边缘渲染的前提是不依赖只能在中心访问的数据
  - 边缘渲染 ≠ CDN 缓存：前者在边缘执行逻辑、可按请求差异化，后者是共享同一份产物
