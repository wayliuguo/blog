# 渲染方案全景

渲染方案不是八种技术，而是**同一个问题的不同取值**：HTML 字符串在哪一刻生成、何时交给浏览器。把这个问题想清楚，CSR / SSR / SSG / ISR / 流式 / RSC / 岛化 / PPR / 边缘渲染就不需要死记——它们全是这张时间轴上的一个位置。

## 一、一张对比表

```
| 方案   | HTML 何时生成               | 内容新鲜度     | 服务端每次成本             | 首屏表现                 | 典型场景               |
|--------|-----------------------------|----------------|----------------------------|--------------------------|------------------------|
| CSR    | 浏览器端（JS 下载解析后）   | 实时           | 0                          | 最差：等 JS + 接口往返   | 后台工作台、登录后页   |
| SSR    | 每次请求                    | 实时           | 渲染 + 取数（绑最慢数据源）| FCP 紧贴 TTFB            | 个性化首页、搜索结果   |
| SSG    | 构建时                      | 构建时         | 0（纯静态）                | 最好                     | 文档站、营销页         |
| ISR    | 构建时 + TTL 后台重建       | TTL 窗口内可旧 | 命中≈0                     | 命中最好，仅回源一次     | 商品页、内容站         |
| 流式   | 请求时分段                  | 实时           | 同 SSR                     | 壳先到，慢洞后补位       | 有慢区块的大页         |
| RSC    | 服务端求值部分组件          | 实时           | 同 SSR                     | 注水数据显著变小         | React 深树应用         |
| 岛化   | 服务端整页 + 局部注水       | 实时           | 同 SSR                     | 静态部分零 JS            | 文档站、内容页         |
| PPR    | 静态骨架构建时 + 动态洞流式 | 同 ISR         | 命中≈0                     | TTFB 走 SSG、完整性走 SSR| 大型电商首页           |
| 边缘   | 不改生成时刻，只改传输位置  | 实时           | 同 SSR（+运行时约束）      | 传输段变短               | 全球分布用户           |
```

读这张表的方法：先定「HTML 何时生成」，再看「服务端每次成本」——**前四行是交付方式的主轴，后五行是主轴上的增强**（流式改交付节奏、RSC 改求值位置、岛化改注水粒度、PPR 组合 SSG 与流式、边缘改传输距离）。

## 二、选型决策树：四个问题走到底

```
要不要被抓      → 要，打掉 CSR；不要，CSR 可用
内容变不变      → 不变，SSG；会变，看下一问
内容能不能旧    → 能，ISR（TTL 换「用户不等重建」）；不能，SSR
有没有慢数据源  → 有且区块多，流式；只有一小块动态，PPR / 岛化
交互密度高不高  → 高，接受全量注水；低，岛化
```

ISR 的取舍问两句：内容错了有没有损失、旧内容能忍受多旧。价格、库存、余额这类数据不适合 ISR。

## 三、实测基线

以下数字来自本板块保留的实验台 `code/render-lab`（零依赖手写 vdom 与渲染出口，无头 Chrome 实测）：

- FCP（`jslag=300`）：CSR 2192ms · SSR 504ms · SSG 404ms · 流式 388ms——**CSR 首屏由网络与解析决定，不由渲染决定**。
- SSR 连发三次 273 / 279 / 278ms 一次没省（`X-Render-Ms` 266 / 275 / 275），响应时间绑最慢数据源。
- ISR 四态：回源 266ms · 命中 2ms · 过期返回旧内容 4ms · 重建后命中 1ms——**用户永远不等重建**。
- 注水失配：「注水期零 DOM 写入」是硬指标，`MutationObserver` 分 childList / attributes / characterData 三档定位（结构问题 vs 格式口径问题）。

这些机制的推导过程与失配排查，沉淀在 `render-lab` 的实验里；本篇不再展开。

## 四、板块地图：接下来读什么

渲染架构只解决「**单应用**怎么交付」；本板块后续两篇把这张表的前四行变成可跑的真实工程，并各自配一个独立的最小实现：

- **Next.js**（React 系）：App Router 把渲染范式做成了文件约定——`page.tsx` 默认 SSG、`force-dynamic` 切 SSR、`revalidate` 切 ISR、`'use client'` 切 RSC 边界；最小实现 `code/mini-next` 手写文件路由 + SSR + hydration。
- **Nuxt**（Vue 系）：`routeRules` 把混合渲染做成路径级声明，Nitro 把 server API 做进同一份工程；最小实现 `code/mini-nuxt` 手写 Vue SSR + SFC 双遍编译。

两个板块与本篇的关系：**微前端**解决「多个应用在运行时怎么组合」（沙箱、通信、资源加载），是渲染架构在应用组合维度的延伸；**跨端与桌面**解决「同一套渲染思路离开浏览器怎么落地」（WebView 容器、JS→Native、自绘引擎）。三条线索合起来，才是「渲染」这件事的完整版图。
