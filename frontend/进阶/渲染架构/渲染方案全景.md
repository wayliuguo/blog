# 渲染方案全景

一个页面「在哪儿被渲染成 HTML」，决定了三件事：首屏要等几条腿、服务端要背多少账、客户端的 JavaScript 要下载多少。这一篇把 CSR / SSR / SSG / ISR / 流式放在同一张表里比 —— 同一份页面代码、同一台机器、同一套接口，数字全部来自配套实验台。注水与同构的细节见第 2 篇，岛化、RSC 这些更细的范式见第 3 篇。

## 一、同一份代码，五种交付方式

实验台的页面是一个商品列表页，数据分两份：**壳数据**（标题、城市、8 件商品）本机立即返回；**评价接口 260ms、推荐接口 130ms**。所有交付方式渲染的都是同一个 `App` 组件树，差别只在「字符串在哪一刻生成、什么时候交给浏览器」。

要看清差别，得把网络成分拉出来。表里两套条件：`jslag=0` 是本机理想网络；`jslag=300` 给每个 JS 模块的响应加 300ms 延迟，模拟「框架运行时在慢网下下载 + 解析」的开销。

`npm run panorama` 在 `jslag=300` 下的真实输出：

```
| 方案           | TTFB   | FCP     | 商品列表出现 | 评价出现 | JS 字节 | load    |
|----------------|--------|---------|--------------|----------|---------|---------|
| CSR 客户端渲染 | 112 ms | 2192 ms | 2085 ms      | 2085 ms  | 12.6 KB | 1805 ms |
| SSR 服务端渲染 | 374 ms | 504 ms  | 388 ms       | 388 ms   | 16.4 KB | 1638 ms |
| SSG 静态生成   | 97 ms  | 404 ms  | 259 ms       | 259 ms   | 16.4 KB | 1506 ms |
| 流式渲染       | 103 ms | 388 ms  | 271 ms       | 380 ms   | 16.4 KB | 1633 ms |
```

同一份代码，把网络条件换成本机理想网络（`jslag=0`）：

```
| 方案           | TTFB   | FCP    | 商品列表出现 | 评价出现 | JS 字节 | load   |
|----------------|--------|--------|--------------|----------|---------|--------|
| CSR 客户端渲染 | 110 ms | 640 ms | 539 ms       | 539 ms   | 12.6 KB | 271 ms |
| SSR 服务端渲染 | 377 ms | 500 ms | 391 ms       | 391 ms   | 16.4 KB | 504 ms |
| SSG 静态生成   | 100 ms | 368 ms | 237 ms       | 237 ms   | 16.4 KB | 368 ms |
| 流式渲染       | 116 ms | 348 ms | 224 ms       | 379 ms   | 16.4 KB | 429 ms |
```

两套条件给出两个不同的结论，这本身就是要读出来的东西：

- **CSR 的 FCP 从 640ms 涨到 2192ms**，涨了 3.4 倍；而其它三种只从 500ms 左右涨到 400~500ms。说明 CSR 的首屏时间主要**由网络与解析决定，不由渲染本身决定** —— 它的渲染是几毫秒的事。
- **SSR 的 TTFB 在两套条件下都是 374~377ms**，因为它等的是服务端的慢接口，跟网络无关；它的 FCP 紧贴 TTFB（差 100ms 左右）。
- **SSG 的 TTFB 是 97~100ms** —— 注意这个数不是「0」，它是这台机器上无头 Chrome 单次导航的固定开销。渲染那 260ms 在构建时就花掉了，请求路径上一点都不剩。
- **流式的「商品列表出现」只有 271ms**，比 SSR 的 388ms 早了 117ms，但它的「评价出现」是 380ms，反而更晚 —— 后一节展开。

一个读表口径要先说清：无头环境里 `load` 与首帧的先后不严格（CSR 那行的 FCP 甚至比 `load` 晚），所以判断「用户什么时候看到内容」请看 **FCP** 与「内容列表出现」两列，`load` 只用来参考资源收尾时间。

## 二、CSR：三条腿都得走完

CSR 的页面壳是一份**没有任何内容**的 HTML，内容全靠这份 JS：

> 摘自 `./code/render-lab/harness/routes.mjs`

```js
if (mode === 'csr') {
    // 壳里什么内容都没有：首屏完全押在这份 JS 上
    return send(docHead({ mode }) + docTail({ entry: '/src/entry-csr.mjs' }), 'csr')
}
```

入口拿到之后要做两件事，缺一不可：

> 摘自 `./code/render-lab/src/entry-csr.mjs`

```js
const fetchedAt = performance.now()
const response = await fetch('/api/data?reviews=1')
const data = await response.json()
const dataAt = performance.now()

renderDOM(App({ data }), root, stats)
const renderedAt = performance.now()
```

于是首屏时间 = **HTML 到达 + JS 下载与解析 + 接口往返 + 建 DOM**，四条腿串起来：

1. HTML 壳 1.7KB，本机 100ms 上下就到了；
2. 入口模块要下载，它又 `import` 了页面树、8 个组件、城市字典……14 个模块（12.6KB），在 `jslag=300` 下这一串就是 1.5 秒量级；
3. 接口 `/api/data?reviews=1` 要等 260ms 的慢数据；
4. 最后才建 DOM、才出现内容。

实测 2085ms 里，建 DOM 只占个位数毫秒。**CSR 的慢不是渲染慢，是它在渲染之前还要跑完前面三件事。**

这也解释了为什么「骨架屏」在 CSR 里几乎是必需的：把第 4 步提前成一次静态的骨架渲染，让 FCP 不必等第 2、3 步。但骨架屏只解决「看起来在加载」，不解决「内容什么时候到」——FCP 早了，LCP 与「内容出现」依然压在最后。

CSR 的合理性只在特定场景成立：内容不需要被爬虫抓、不被社交卡片引用、用户有明确预期（后台工作台、登录后的仪表盘、桌面端壳内页面）。这些场景里，CSR 换来的构建简单、部署简单、缓存粒度清晰，是净收益。

## 三、SSR：内容随 HTML 一起来

SSR 把第 1、4 步合并了：服务端渲染好的 HTML 里**已经有全部内容**，浏览器解析到就能画。实验台的服务端渲染核心就这十几行：

> 摘自 `./code/render-lab/src/render-string.mjs`

```js
export function renderToString(vnode) {
    if (vnode == null || vnode === false) return ''
    if (Array.isArray(vnode)) return vnode.map(renderToString).join('')
    if (typeof vnode === 'string' || typeof vnode === 'number') return escapeHtml(vnode)
    const { type, props } = vnode
    if (typeof type === 'function') return renderToString(resolve(vnode))
    const open = `<${type}${attrsToString(props)}>`
    if (VOID.has(type)) return open
    return `${open}${vnode.children.map(renderToString).join('')}</${type}>`
}
```

两处细节值得记：

- **`children` 得手动塞进 `props`**（`resolve(vnode)` 做的事）。函数组件拿子节点的唯一通路是 `props.children`，自己实现渲染器时漏掉这一步，所有带子节点的组件都会渲染成空 —— 这个坑实验台真的踩了一次。
- **子节点之间不插任何空白**。客户端注水靠 `childNodes` 下标对齐，多一个换行文本节点，整棵子树就开始错位重建（第 2 篇有量化）。

代价在服务端这一侧：

```
| 路径         | X-Render-Mode | 服务端耗时 | 响应头到达 | HTML 字节 |
|--------------|---------------|------------|------------|-----------|
| SSR 第 1 次  | ssr           | 266 ms     | 273 ms     | 5.3 KB    |
| SSR 第 2 次  | ssr           | 275 ms     | 279 ms     | 5.3 KB    |
| SSR 第 3 次  | ssr           | 275 ms     | 278 ms     | 5.3 KB    |
```

连着三次，一次都没省下。因为服务端每次都要把同样的树重渲染一遍、把慢接口重等一遍。**SSR 的快是「浏览器能立刻拿到内容」，不是「服务端更省」。** 服务端反而更累：CPU、内存、慢接口的等待全压在它身上，而且它的响应时间与最慢的那个接口绑定。

绑定的机制在取数形态里：

> 摘自 `./code/render-lab/src/data.mjs`

```js
export async function loadAll(latency = REVIEWS_LATENCY) {
    const [reviews, recommend] = await Promise.all([loadReviews(latency), loadRecommend(Math.round(latency / 2))])
    return { ...loadShell(), reviews, recommend }
}
```

两个接口是并发的，但整体耗时等于**更慢的那个**（260ms）。只要有一个区块的数据慢，整页 HTML 就都发不出去 —— 这是流式渲染要解决的问题。

## 四、SSG 与 ISR：把渲染挪到构建时

SSG 的思路很直接：内容不随请求变，那就渲染一次、存起来。

> 摘自 `./code/render-lab/harness/routes.mjs`

```js
// SSG：构建时渲染一次，运行时零成本 —— 所以在服务开始接客之前就做好了
let ssg = { html: null, data: null }
async function warm() {
    const data = await slow()
    ssg = { html: renderToString(App({ data })), data }
    return ssg.html
}
```

实验台把 `warm()` 放在 `listen()` 之前调用，模拟「构建时完成」。请求路径上只剩一次静态字符串的写出，实测响应头 3~4ms 到达（本机导航开销约 100ms 的那个固定部分之外，服务端部分约等于 0）。

ISR 是 SSG 与 SSR 的折中：**内容有缓存，但带过期时间；过期后先返回旧内容，后台重建。**

```
| 路径                     | X-Render-Mode | 服务端耗时 | 响应头到达 | HTML 字节 |
|--------------------------|---------------|------------|------------|-----------|
| ISR 首次（回源）         | isr-miss      | 263 ms     | 266 ms     | 5.3 KB    |
| ISR 立刻再来（命中）     | isr-hit       | 0 ms       | 2 ms       | 5.3 KB    |
| ISR 过期后（返回旧内容） | isr-stale     | 0 ms       | 4 ms       | 5.3 KB    |
| ISR 后台重建完成后       | isr-hit       | 0 ms       | 1 ms       | 5.3 KB    |
```

四个状态连起来看就是 ISR 的全部行为：第一次回源渲染（266ms），之后命中缓存（2ms）；过了 TTL 之后的那一次请求**仍然只花 4ms** —— 它返回的是旧内容，同时后台开始重建；重建完成后再请求就又是命中（1ms）。

这就是 `stale-while-revalidate` 在页面层的版本：**用户永远不等重建**，代价是有人会看到旧内容，且旧内容能旧多久由 TTL 决定。判断能不能接受，问两个问题：内容错了会不会造成损失？旧内容能忍受多旧？

## 五、流式：能发的先发

流式渲染不改变「服务端渲染」这件事，只改变**什么时候把已经渲染好的部分交出去**。

```
响应头到达 16 ms · 全部完成 290 ms
| 段             | 到达时刻 | 该次写入字节 |
|----------------|----------|--------------|
| shell          | 17 ms    | 1.9 KB       |
| recommend:fill | 151 ms   | 482 B        |
| reviews:fill   | 290 ms   | 776 B        |
```

壳（页头 + 商品列表）在 17ms 就出去了，而整页要 290ms 才结束。中间那 273ms 是**慢接口还没回来，不是服务端在忙** —— 浏览器在这段时间里已经把壳画出来了。浏览器侧的对照更直白：

```
| 交付方式   | FCP    | 商品列表出现 | 评价出现 |
|------------|--------|--------------|----------|
| 非流式 SSR | 508 ms | 399 ms       | 399 ms   |
| 流式渲染   | 340 ms | 235 ms       | 373 ms   |
```

FCP 提前 168ms，商品列表提前 164ms。还有一个反直觉的地方：**流式的「评价出现」比非流式 SSR 还晚**（373ms vs 399ms 看似早，但注意非流式 SSR 那 399ms 是「整页一起出现」，而流式是 235ms 就出现了大部分内容）。真正要小心的是**可交互时间**：

```
| 交付方式   | 入口模块开始执行 |
|------------|------------------|
| 非流式 SSR | 1679 ms          |
| 流式渲染   | 1650 ms          |
```

流式的入口模块**没有更早**。因为全量注水需要完整的数据，而流式的数据要等最后一个边界才凑齐 —— 流式把「看得见」提前了，没有把「点得动」提前。要连可交互时间一起提前，得让注水数据也分段下发，或者干脆改成岛化（见第 3 篇）。

流式还有一笔明账：**HTML 从 5.3KB 涨到 6.5KB**。多出来的是占位节点、装真内容的 `<template>`、补位脚本、以及 head 里那段运行时。网络越差，这份开销越值；网络越好，越不值。

分段的边界应该画在**数据来源**的边界上（评价接口一段、推荐接口一段），而不是「组件层级」的边界上，否则你会得到几十个几百字节的碎片，反而把 TCP 的效率拖下去。实验台里的推荐位（130ms）排在评价（260ms）后面，但它是**先补位**的：

```
实际顺序：shell → recommend:fill → reviews:fill
```

## 六、选型决策树

把上面五节压成一张判断表：

1. **内容需要被爬虫抓、或被社交卡片引用吗？**
   - 不需要 → **CSR**（后台、工作台、桌面壳内页面）。简单是它的主要价值。
   - 需要，且内容变化频率低于构建频率 → **SSG**。
   - 需要，且内容随请求变化 → 下一步。
2. **服务端渲染的耗时里，有没有明显慢的数据源？**
   - 有，且首页有多个数据区块 → **流式**。让快的区块先到。
   - 有，但只有一小块是动态的（登录态、购物车） → **PPR / 岛化**：静态部分走静态，动态部分单独补。
   - 没有，取数都很快 → **SSR**，别提前优化。
3. **内容能接受有多旧？**
   - 几分钟到几小时 → **ISR**（`revalidate` 设成可接受的值），纯静态页优先 SSG。
   - 一秒都不能旧（价格、库存、余额） → SSR 或流式。
4. **交互密度高不高？**
   - 整页都在交互（编辑器、看板、表格） → CSR 或 SSR + 全量注水，注水反正跑不掉。
   - 只有零星交互点（文档站、商详、内容页） → **岛化**，能把客户端 JS 砍掉一大半。

一个常见的误判是「上了 SSR 就等于首屏快」。SSR 只保证**内容先到**，不保证**点得动**：如果框架运行时是 150KB，用户在 FCP 之后还要等它下载解析完才能交互（第 2 篇与第 3 篇分别给出注水与岛化的量化）。

## 小结

- 交付方式的差别不在渲染，在「字符串何时生成、何时交给浏览器」
  - CSR：浏览器渲染，内容靠 JS 拉；SSR：每次请求服务端渲染；SSG：构建时渲染一次
  - ISR：SSG + 过期时间 + 后台重建；流式：已就绪的部分先发
  - 实测（`jslag=300`）FCP：CSR 2192ms · SSR 504ms · SSG 404ms · 流式 388ms
- CSR 的首屏由网络与解析决定，不由渲染决定
  - 首屏四段：HTML 到达 → JS 下载解析 → 接口往返 → 建 DOM；实测建 DOM 只占个位数毫秒
  - 网络条件从 `jslag=0` 换成 `jslag=300`，CSR 的 FCP 从 640ms 涨到 2192ms，其它三种基本不动
  - 骨架屏只把 FCP 提前，不改变内容到达的时刻
- SSR 的代价在服务端，不在浏览器
  - 连发三次响应头到达 273/279/278ms，一次都没省下
  - 整页耗时绑定最慢的接口（`loadAll` 并发后取更慢的那个，260ms）
  - 产物体积：标记 4.1KB + 注水数据 1.2KB，数据占 22.3%
- SSG 与 ISR 是把渲染挪到请求路径之外
  - SSG 响应头 3~4ms（本机导航固定开销约 100ms 之外近乎为 0）
  - ISR 四态实测：回源 266ms · 命中 2ms · 过期返回旧内容 4ms（后台重建）· 重建后命中 1ms
  - ISR 的取舍问两句：内容错了有没有损失、旧内容能忍受多旧
- 流式把「看得见」提前，不把「点得动」提前
  - 壳 17ms 发出、整页 290ms 完成；浏览器侧 FCP 340ms vs 非流式 508ms
  - 代价：HTML 从 5.3KB 涨到 6.5KB
  - 入口模块执行时刻几乎不变（1650ms vs 1679ms）—— 注水数据要等最后一个边界
  - 补位顺序由「谁先好」决定：推荐位 130ms 先于评价 260ms 补位
- 选型按四个问题走
  - 要不要被抓 → 要就打掉 CSR；内容变不变 → 不变就 SSG；能不能旧 → 能就 ISR
  - 有没有慢数据源 → 有且区块多就流式；只有一小块动态就 PPR / 岛化
  - 交互密度高不高 → 高就接受全量注水，低就岛化
