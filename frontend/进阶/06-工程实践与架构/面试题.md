## 一、设计模式

### Q1: 什么是设计模式？前端常用的有哪些？（第 01 篇）

- **结论**：设计模式是"在特定场景下被反复验证的解决方案模板"——不是语法，是可复用的结构约定；前端高频的是单例、观察者/发布订阅、工厂、策略、代理、装饰器。
- **原理**：模式解决"变化点"——单例管唯一实例、观察者管一对多通知、策略管算法替换、装饰器管职责叠加；前端版常见于状态管理、事件通信、配置化渲染。
- **边界**：模式是工具不是目标，为模式而模式增加复杂度；小型场景直接写法更清晰。
- **追问**：什么场景不用模式？→ 只有一处使用、变化频率极低时，直写比抽象更便宜。
- **场景**：Redux/Pinia 单例 store、Vue 响应式观察者、表单校验策略集、请求拦截装饰。

### Q2: 单例模式的适用场景与坑？（第 01 篇）

- **结论**：适用"全局唯一 + 跨处共享"（store、日志、Toast）；坑是隐藏依赖与难测试。
- **原理**：保证一个类只有一个实例并全局可访问；前端典型是单一 store（Redux/Pinia）、事件总线、全局弹窗。
- **边界**：全局单例让依赖不显式、测试难隔离；共享可变状态是 bug 温床。
- **追问**：单例怎么测试？→ 构造函数收依赖 + 提供 reset 方法，避免测试间污染。
- **场景**：Pinia store 单一数据源驱动多个组件；Toast 弹窗单例避免多实例叠层。

### Q3: 观察者模式与发布-订阅模式的区别？（第 01 篇）

- **结论**：观察者是"对象直接通知依赖"；发布-订阅多一层事件中心，发布者与订阅者完全解耦。
- **原理**：观察者 = 目标持有订阅者列表、状态变了直接 notify；pub-sub = 通过事件总线/EventEmitter 转发，双方互不知道对方存在。
- **边界**：事件总线容易失控（事件名无约束、难追踪），大项目慎用。
- **追问**：Vue 响应式属于哪种？→ 观察者模式（依赖收集直连）。
- **场景**：Vue 响应式（effect 直接依赖数据）；跨组件/跨模块通信用事件总线但收敛事件定义。

### Q4: 工厂模式 / 策略模式 / 装饰器模式在前端的体现？（第 01 篇）

- **结论**：工厂管"创建"（按配置产出实例），策略管"算法替换"（组合替代 if/else），装饰器管"职责叠加"（不动原逻辑加能力）。
- **原理**：工厂——统一创建逻辑、隐藏细节；策略——一组可互换算法由上下文选择，新增一种加一个策略对象（开闭原则）；装饰器——HOC/拦截器包一层。
- **边界**：工厂滥用让创建路径变深；策略过多要配注册表管理；装饰器叠加过多难以调试。
- **追问**：策略和 if/else 的本质区别？→ 策略把分支收敛成可组合、可独立测试的对象集合。
- **场景**：表单校验策略集、支付渠道配置；请求拦截器（包装 + 权限校验）、HOC 包装组件。

## 二、组件设计

### Q5: 组件是什么？和普通函数/类的区别？（第 02 篇）

- **结论**：组件是"有状态的渲染单元"——有自己的 props/状态/生命周期，可复用、可组合、可独立测试；普通函数无状态、无生命周期。
- **原理**：组件 = 输入（props/状态）→ 输出（渲染 + 事件）；框架负责调度生命周期与更新；函数是一等公民的纯计算。
- **边界**：无状态纯渲染可用函数组件，有副作用/状态才需要组件心智。
- **追问**：函数组件也算组件吗？→ 算——无状态组件是组件的最小形态，配合 hooks 也可有状态。
- **场景**：把"试算表单"抽成组件（自有状态 + props 契约），按钮等纯展示用函数。

### Q6: 组件边界怎么判断？（第 02 篇）

- **结论**：三点判据——变化频率是否独立、是否有可复用的数据闭环、是否能独立测试。
- **原理**：抽组件是为了隔离变化；频率低的变化不值得抽（过度抽象比重复更贵）。
- **边界**：边界不是越细越好，要看"改一个需求动几个文件"。
- **追问**：组件与主流程的试算联动怎么做？→ 券只产出抵扣结果，试算仍由主流程纯函数完成。
- **场景**：简历项目优惠券模块：券规则变、主流程不变 → 抽组件；组件内聚自己的状态，向父级只暴露结果（选中的券 + 影响金额）。

### Q7: 组件通信方式与取舍？（第 02 篇）

- **结论**：自上而下 props、自下而上事件（emit/回调）、跨层用 provide/inject 或全局状态、无关组件用事件总线——按耦合度递进选择。
- **原理**：props 单向数据流最可预测；事件回调让父子契约显式；provide/inject 解决深层传递；全局状态适合多组件共享；事件总线解耦但难追踪。
- **边界**：优先 props/事件（显式契约），跨层与共享才升级；事件总线是最后手段。
- **追问**：什么时候用全局状态？→ 多组件共享 + 跨页面 + 需持久化，否则本地状态 + props 提升。
- **场景**：父子组件用 props + emit；多页共享用户信息用 Pinia；深层组件用 provide/inject 注入 api。

### Q8: 单向数据流是什么？为什么重要？（第 02 篇）

- **结论**：数据单向流动（状态 → 视图 → 事件 → 状态），可预测、可调试、可单测。
- **原理**：状态唯一来源 + 视图只消费派生 + 修改必须走明确路径。
- **边界**：简单页面套全局状态管理是过度设计；状态本地化优先。
- **追问**：组件状态被父级偷偷改怎么办？→ 组件不暴露内部状态，只暴露结果事件。
- **场景**：简历项目金融要素流转：要素 → 纯函数试算 → 派生结果 → UI 只渲染，四条收益：可枚举、可单测、可复用、可回归。

### Q9: 状态管理：全局状态 vs 组件状态怎么划分？（第 02 篇）

- **结论**：多组件共享 + 跨页面 + 需持久化才全局；否则本地状态 + props 提升。
- **原理**：状态就近原则——单一组件用的状态放本地；多组件共享的向上提升或进 store；派生值不存状态（由源状态计算）。
- **边界**：滥用全局 store 让数据流失控、组件难复用；状态越少越可预测。
- **追问**：派生值为什么不存状态？→ 存了会"双份真相"，改一处忘另一处。
- **场景**：表单输入本地状态；登录用户、字典数据全局 store；金额结果用计算属性派生。

### Q10: 组件库/设计系统的边界怎么划？（第 02 篇）

- **结论**：组件库收"通用原子与复合组件"（不掺业务），业务专属组件留业务层——边界是"是否可跨业务复用"。
- **原理**：通用组件只依赖设计 token 与自身状态，通过 props 扩展；业务组件依赖业务数据与接口，进不了通用库。
- **边界**：过早抽通用组件会做出"四不像"；通用层要防业务渗透（不许 import 业务 api）。
- **追问**：设计 token 怎么用？→ CSS 变量定义色板/间距/圆角，组件全部消费 token 不写死。
- **场景**：vant 类基础组件入库，优惠券/借款流程组件留在业务层，token 统一换肤。

## 三、架构与演进

### Q11: 前端分层架构（api / hooks / utils / views）？（附录）

- **结论**：`api/`（接口与契约）→ `hooks/`（组合逻辑）→ `utils/`（纯函数）→ `views/`（视图），职责单向依赖。
- **原理**：分层让"改一处"（接口变了只动 api 层）与"可测"（纯函数不挂组件）成为可能。
- **边界**：分层要防"层间穿越"（视图直接写业务逻辑）；小项目不必全套分层。
- **追问**：hooks 与 utils 的区别？→ hooks 持有响应式状态与生命周期，utils 是纯函数。
- **场景**：简历项目接口治理：页面只消费 api，不直接碰请求；api 工具层收口缓存/竞态/错误分级。

### Q12: 技术债有哪几种形态？怎么判定可下线？（附录）

- **结论**：下线判据不是"看起来没人用"，而是"消费方不存在"。
- **原理**：四种形态——失效业务分支（接口/配置不存在）、失效埋点（面板不再消费）、历史兼容判断（端版本全覆盖）、废弃配置（无读取方）。
- **边界**：三步判定：找消费方 → 看端版本/接口是否还在 → 灰度或加兜底后再删。
- **追问**：怎么确定一个分支可以删？→ 分支条件对应的接口/配置是否还存在，消费方是否还在用。
- **场景**：简历项目冗余下线：主组件职责从"视图+数据+请求+校验+埋点"混写收敛为"编排+渲染"两类。

### Q13: 纯函数 + 派生状态的架构收益？（附录）

- **结论**：把逻辑收敛成纯函数、派生结果不落状态——可枚举、可单测、可复用、可回归。
- **原理**：纯函数同输入同输出、无副作用，天然可单测；派生状态由源状态计算，单一真相；UI 只消费派生结果。
- **边界**：纯函数只解决"计算"，IO/副作用仍要明确边界（请求放 api 层）。
- **追问**：怎么保证派生不落状态？→ 用计算属性/useMemo 实时派生，不写 set 派生副本。
- **场景**：级联试算重构：要素 → 纯函数 → 结果，测试覆盖所有组合，改规则只动一个函数。

### Q14: 从"视图+数据+请求+校验+埋点混写"重构为"编排+渲染"的价值？（附录）

- **结论**：职责收敛——主组件只管"编排"（拉起数据、串联流程）与"渲染"（展示结果），横切关注点下沉。
- **原理**：混写导致改一个需求动多处、不可测；收敛后数据请求归 api/hooks、校验归纯函数、埋点归统一调用，组件可读可测。
- **边界**：收敛是渐进不是推倒重来——边界先行 + 增量迁移 + 灰度验证。
- **追问**：混写最典型的问题？→ 请求散落在组件里，接口变更动多个页面，且无法单测。
- **场景**：简历项目主组件从"视图+数据+请求+校验+埋点"混写收敛为"编排+渲染"，改接口只动 api 层。

## 四、场景实战

### Q15: 大列表虚拟滚动的实现原理？（附录）

- **结论**：只渲染可视区 + 缓冲区的条目，滚动时用 translateY 平移内容容器。
- **原理**：视口高度 / 行高估算可视条数；内容容器高度撑起总高度；列表项绝对定位或整体平移。
- **边界**：行高不固定需测量或估算（有偏差）；key 必须稳定（复用项状态）。
- **追问**：固定行高 vs 动态行高？→ 固定行高简单，动态需 ResizeObserver + 缓存每项高度。
- **场景**：千条级列表、长表格、聊天记录——DOM 从万级降到几十级。

### Q16: 场景：实现一个支持十万条数据、可滚动可搜索的列表（虚拟滚动），怎么设计？（附录）

- **结论**：固定行高虚拟滚动 + 数据层过滤搜索 + 事件委托 + 性能度量，四件事一起做。
- **原理**：① 固定行高方案（估算 + 可视区渲染 + 总高度撑位 + translateY 平移）；② 稳定 key（复用项状态）；③ 搜索在数据层过滤（纯函数）+ 防抖输入；④ 可视区外不渲染 DOM；⑤ 行内交互用事件委托；⑥ 性能度量（渲染时长/内存）。
- **边界**：动态行高有测量成本，先固定行高起步；"可视区 + 缓冲"提前渲染防白屏。
- **追问**：为什么搜索要在数据层做？→ 过滤是纯计算，不碰 DOM，可单测、不触发重渲染风暴。
- **场景**：十万条借款记录列表，输入防抖搜索、滚动流畅、渲染时长与内存入监控。

### Q17: 前端权限系统怎么设计？（附录）

- **结论**：权限分三层——路由权限（动态路由 + 守卫）、按钮/操作权限（自定义指令）、数据权限；模型上采用 RBAC（用户-角色-权限）。
- **原理**：登录后按角色拉取权限码集合；路由层在 `beforeEach` 里校验 `meta.roles` 并通过 `addRoute` 动态注册可见路由，无权限重定向 403/登录页；按钮层用自定义指令（如 `v-permission`）按权限码控制显隐；菜单树由权限路由表直接派生。
- **边界**：前端权限防君子不防小人——真正的安全靠后端接口鉴权，前端只做体验与菜单收敛；权限码集中管理，避免散落魔法字符串。
- **追问**：动态菜单怎么实现？→ 由过滤后的路由表直接派生菜单树，加一条路由即出一个菜单。
- **场景**：后台管理系统——不同角色登录后菜单/按钮不同，直接访问无权限 URL 被守卫拦到 403。

### Q18: 通用请求层（axios 封装）怎么设计？（附录）

- **结论**：统一实例 + 拦截器分层（请求拦截注入 token/参数、响应拦截统一解包与错误处理）+ 业务码与 HTTP 错误分类处理 + 重试与取消能力。
- **原理**：`create` 统一 baseURL/超时；请求拦截器注入 token 与签名、防重复提交；响应拦截器按 HTTP 状态与业务 `code` 分流——成功解包 `data`、401 跳登录、业务错误统一提示；`AbortController` 支持取消（组件卸载/路由切换），重试用指数退避。
- **边界**：业务码与 HTTP 码要分开处理，不能混为一谈；取消信号要透传给调用方（`AbortSignal`）；错误处理要有"全局兜底 + 局部覆盖"两级。
- **追问**：并发请求怎么控？→ 相同 key 去重（复用同一 Promise）与并发上限队列。
- **场景**：页面卸载时未完成的请求被 abort，避免 setState 泄漏告警与多余流量。

### Q19: 大文件上传（切片/断点续传）怎么设计？（附录）

- **结论**：前端切片 + 并发上传 + 服务端合并；断点续传靠"已传分片哈希"查询，秒传靠文件指纹。
- **原理**：`File.slice` 按固定大小（如 2MB）切分，每片计算 hash（如 SparkMD5）作标识并限制并发数上传；上传前先向服务端查询哪些分片已传（断点续传），全部传完触发合并；整体文件 hash 用于秒传判断；进度 = 已传分片 / 总分片聚合。
- **边界**：大文件 hash 计算耗时长，用 Web Worker 计算不阻塞主线程；并发数要限制避免打满带宽；服务端要校验合并完整性。
- **追问**：秒传怎么实现？→ 上传前按文件 hash 查服务端，已存在直接返回成功、不用传分片。
- **场景**：网盘/后台导入大文件，断网重传只补缺失分片，成功率与体验显著提升。

### Q20: 怎么设计一个组件库（数据结构/样式/主题/文档/规范）？（第 02 篇）

- **结论**：API 与数据模型先行（受控/非受控）、样式主题可配置（CSS 变量/设计令牌）、文档与规范（示例 + 类型 + 变更日志）是组件库的"门面"。
- **原理**：数据结构——props 契约（类型/默认值/受控模式）与内部状态分离；样式——CSS 变量设计令牌实现主题切换、BEM 命名防样式污染；文档——示例站点 + API 表格 + changelog 驱动升级；规范——lint 规则、语义化版本、破坏性变更策略。
- **边界**：headless 是趋势——行为与样式分离（Radix/TanStack），品牌样式交给团队掌控；组件库要控制破坏性变更频率。
- **追问**：组件库和设计系统什么关系？→ 设计系统 = 组件库 + 设计令牌 + 文档 + 规范，组件库是它的实现载体。
- **场景**：团队自建 button/table/form 库，主题切换靠换 CSS 变量、升级靠 changelog + semver 评估破坏性。
