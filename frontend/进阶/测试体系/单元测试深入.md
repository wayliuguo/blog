# 单元测试深入

## 一、用例组织与生命周期

`describe` 把用例分组、`it`（或 `test`）写单条用例、`expect` 做断言——这三样在测试工具上手已经会用了。这里补齐组织方式和四种生命周期钩子。

四种钩子决定了一段准备/还原代码在什么范围跑：

> 示意片段（无配套脚本）

```js
let db
beforeAll(async () => { db = await connect() })   // 整套用例前：连一次库（贵资源只建一次）
beforeEach(() => { db.clear() })                   // 每条用例前：清空，保证用例间隔离
afterEach(() => { cleanup() })                     // 每条用例后：还原全局对象 / 还原间谍
afterAll(async () => { await db.close() })         // 整套用例后：释放资源
```

- `beforeAll` / `afterAll` 在整套 `describe` 的前后各跑一次，适合"建一次、拆一次"的贵资源（数据库连接、起一个服务）。
- `beforeEach` / `afterEach` 在**每条**用例前后跑，是隔离用例、避免串味的主力——绝大多数准备和还原逻辑放这里。
- 钩子按 `beforeAll → beforeEach → 用例 → afterEach → afterAll` 的顺序执行；多个 `beforeEach` 按声明顺序，多个 `afterEach` 按**逆序**。

进阶标记：

- **`it.fails`** 声明"这条预期失败"，用来锁住一个已知 bug 或一个反例（本篇的泄漏实验就用了它）。
- **`it.only` / `it.skip` / `it.todo`**：只跑这一条 / 跳过 / 占位待写，调试时 `it.only` 最省事。

## 二、断言：钉在行为上，而不是实现上

判断一条断言好不好，看它挂掉时你能不能一眼看出哪错了。先从一个反面教材看"钉实现"的代价——同一份结算逻辑，两种写法都能绿，但重构时天差地别。被测代码：

> 摘自 `./code/test-lab/src/strategy/discount.js`

```js
// 被测源码：购物车折扣计算
// 刻意拆成两个文件，方便演示「mock 掉内部依赖」这种测实现细节的写法

export const VIP = { normal: 1, gold: 2, platinum: 3 }

export function discountRate(level, amount) {
    if (level === VIP.platinum) return 0.8
    if (level === VIP.gold && amount >= 200) return 0.85
    if (level === VIP.gold) return 0.9
    return 1
}
```

> 摘自 `./code/test-lab/src/strategy/price.js`

```js
import { discountRate, VIP } from './discount.js'

export { VIP }

export function calcTotal(items, level = VIP.normal) {
    const amount = items.reduce((sum, it) => sum + it.price * it.count, 0)
    const rate = discountRate(level, amount)
    return Math.round(amount * rate * 100) / 100
}
```


### 反模式一：mock 掉内部依赖，断言调用参数

> 摘自 `./code/test-lab/src/strategy/price-impl.test.js`

```js
import { describe, it, expect, vi } from 'vitest'

// 反模式：把内部依赖 mock 掉，断言「它被调用了、参数是啥」
// 这样测的是"实现路径"，不是"算出来的结果"
vi.mock('./discount.js', async () => {
    const actual = await vi.importActual('./discount.js')
    return {
        ...actual,
        discountRate: vi.fn(actual.discountRate)
    }
})

import { discountRate } from './discount.js'
import { calcTotal, VIP } from './price.js'

describe('反模式：测实现细节', () => {
    it('断言 discountRate 被调用且参数正确', () => {
        const total = calcTotal([{ price: 100, count: 3 }], VIP.gold)

        expect(discountRate).toHaveBeenCalledTimes(1)
        expect(discountRate).toHaveBeenCalledWith(VIP.gold, 300)
        expect(total).toBe(255)
    })
})

describe('反模式：重言式断言（把实现抄一遍当期望）', () => {
    it('用同样的算法算一遍期望值', () => {
        const items = [{ price: 100, count: 3 }]
        const expected = items.reduce((s, it) => s + it.price * it.count, 0) * 0.85

        // 期望值与被测代码用的是同一套算法 —— 实现写错了，这里也跟着错
        expect(calcTotal(items, VIP.gold)).toBe(expected)
    })
})
```


这套断言把"内部必须先算总额、再调 `discountRate`"这两步钉死了。哪天有人把折扣改成查表、或把两个函数合并，功能完全没变，用例却红了。更糟的是它给了一种虚假的安全感 —— 断言"调用过"不等于"算对了"。

### 反模式二：重言式断言

期望值是用同一套算法算出来的：实现里把 0.85 写成 0.8，期望值也跟着变成 0.8，用例依然绿。覆盖率 100%，什么都不保障。

### 正模式：表驱动 + 只描述输入输出

> 摘自 `./code/test-lab/src/strategy/price-behavior.test.js`

```js
import { describe, it, expect } from 'vitest'
import { calcTotal, VIP } from './price.js'

// 正模式：只描述「输入 → 期望输出」，不关心内部是 if 链还是查表
// 表驱动：一行一条用例，补用例的成本极低
const cases = [
    { name: '普通用户无折扣', level: VIP.normal, items: [{ price: 100, count: 1 }], expect: 100 },
    { name: '黄金会员未满 200 九折', level: VIP.gold, items: [{ price: 100, count: 1 }], expect: 90 },
    { name: '黄金会员满 200 八五折', level: VIP.gold, items: [{ price: 100, count: 3 }], expect: 255 },
    { name: '铂金会员八折', level: VIP.platinum, items: [{ price: 250, count: 1 }], expect: 200 },
    { name: '空购物车为 0', level: VIP.platinum, items: [], expect: 0 }
]

describe('正模式：测行为', () => {
    it.each(cases)('$name', ({ level, items, expect: want }) => {
        expect(calcTotal(items, level)).toBe(want)
    })
})

// 边界：这些是真正容易出 bug 的地方，值得单独成例
describe('边界与异常', () => {
    it('金额含小数时按分位四舍五入', () => {
        expect(calcTotal([{ price: 33.33, count: 3 }], VIP.platinum)).toBe(79.99)
    })

    it('数量为 0 的商品不影响总额', () => {
        expect(calcTotal([{ price: 100, count: 0 }], VIP.normal)).toBe(0)
    })
})
```


期望值是**手写的常数**，不是算出来的。这样实现改了写法、但结果不变，用例不用动；实现算错了，用例立刻红。区别在重构那天才显现：把 `discountRate` 的 if 链换成查表，第一份用例要改，第二份一行不动。**用例不需要跟着实现改，是判断它是否测在行为上的唯一硬标准。**

进阶断言用法：

| 断言 | 语义 | 什么时候用 |
| --- | --- | --- |
| `toStrictEqual` | 深比较，且检查 `undefined` 属性与原型 | 想连"多出一个字段"也抓出来时 |
| `expect.soft` | 软断言：失败不中断，收集完一起报 | 一个用例里有多条相关断言时 |

## 三、异步：不要等时间，等条件

异步用例有三种写法，可读性依次下降：

> 示意片段（无配套脚本）

```js
// 最推荐：await 拿到结果再直接断言
const user = await fetchProfile('2')
expect(user.name).toBe('小黑')

// 更紧凑：直接断言 promise 的状态
await expect(fetchProfile('2')).resolves.toEqual({ id: '2', name: '小黑' })
```

两条纪律：

1. **不要用 `done` 回调。** 忘了调 `done` 就超时，调了两次就报错，错误栈还难读。返回 Promise 或 `async` 函数即可。
2. **不要用固定 `sleep` 等异步结果。** 这是 flaky 的头号来源。要等"条件成立"，用 `waitFor` / `findBy*`，或者干脆用假定时器把时间拨快。

超时是可配置的：`testTimeout`、`hookTimeout` 控制单条用例与钩子的上限。把超时调大能"治好"偶发失败，但那只是把问题藏起来 —— 正确的做法是找到不稳定的根因。

## 四、时间：用假定时器把"等 300ms"变成"拨表 300ms"

被定时器支配的代码（防抖、节流、轮询、动画）如果靠真等，一个用例几百毫秒，套件很快就跑不动了。假定时器的思路是：**把时钟换成可以手动拨动的假时钟**。

> 摘自 `./code/test-lab/src/unit/timer.js`

```js
// 被测源码：定时器相关的两个经典工具函数

export function debounce(fn, wait = 300) {
    let timer = null
    return function debounced(...args) {
        if (timer) clearTimeout(timer)
        timer = setTimeout(() => {
            timer = null
            fn.apply(this, args)
        }, wait)
    }
}

export function throttle(fn, wait = 300) {
    let last = 0
    let timer = null
    return function throttled(...args) {
        const now = Date.now()
        const remain = wait - (now - last)
        if (remain <= 0) {
            last = now
            fn.apply(this, args)
        } else if (!timer) {
            timer = setTimeout(() => {
                last = Date.now()
                timer = null
                fn.apply(this, args)
            }, remain)
        }
    }
}
```


测试里不需要真的等 300ms：

> 摘自 `./code/test-lab/src/unit/timer.test.js`

```js
import { describe, it, expect, vi, beforeEach, afterEach } from 'vitest'
import { debounce, throttle } from './timer.js'

describe('debounce：用假定时器把"等 300ms"变成"拨表 300ms"', () => {
    beforeEach(() => {
        vi.useFakeTimers()
    })

    afterEach(() => {
        vi.useRealTimers()
    })

    it('wait 毫秒内重复调用，只执行最后一次', () => {
        const fn = vi.fn()
        const debounced = debounce(fn, 300)

        debounced('a')
        vi.advanceTimersByTime(200)
        debounced('b')
        vi.advanceTimersByTime(200)
        debounced('c')
        vi.advanceTimersByTime(299)
        expect(fn).not.toHaveBeenCalled()

        vi.advanceTimersByTime(1)
        expect(fn).toHaveBeenCalledTimes(1)
        expect(fn).toHaveBeenCalledWith('c')
    })

    it('不拨表就永远不触发——证明它是"延迟"而非"节流"', () => {
        const fn = vi.fn()
        debounce(fn, 1000)()
        vi.advanceTimersByTime(999)
        expect(fn).not.toHaveBeenCalled()
    })
})

describe('throttle：依赖 Date.now，假定时器会连系统时间一起冻结', () => {
    beforeEach(() => {
        vi.useFakeTimers()
        vi.setSystemTime(new Date('2026-01-01T00:00:00Z'))
    })

    afterEach(() => {
        vi.useRealTimers()
    })

    it('一个周期内只执行一次', () => {
        const fn = vi.fn()
        const throttled = throttle(fn, 100)

        throttled() // t=0    立即执行
        vi.advanceTimersByTime(50)
        throttled() // t=50   被推迟到 t=100
        vi.advanceTimersByTime(49)
        expect(fn).toHaveBeenCalledTimes(1)

        vi.advanceTimersByTime(1) // t=100
        expect(fn).toHaveBeenCalledTimes(2)
    })
})
```


这条用例不仅快（毫秒级），还顺手锁住了一个容易写错的点：**第 299 毫秒不能触发，第 300 毫秒才触发**。用真定时器你永远测不出这个边界。

假定时器还会连系统时间一起冻结，所以依赖 `Date.now()` 的逻辑也能被精确控制。


### 假定时器的边界

- 它会冻结 `setTimeout` / `setInterval` / `Date` / `performance.now` 等一整组 API。如果被测代码里有 `await` 一个真实 Promise，拨表不会推进它 —— 需要 `await vi.advanceTimersByTimeAsync(...)`。
- 全局单例（比如模块级的 `setInterval`）在拨表后可能留下未清理的状态，`afterEach` 里一定要 `vi.useRealTimers()`。
- 假定时器不是万能的：涉及真实 I/O 节奏（比如上传进度的真实节流）就别用它，那是 E2E 或手工验证的活。

## 五、测试替身：stub / spy / mock / fake 不是一回事

这四个词日常被混着用，但它们的意图不同，选错了就会写出难维护的用例：

| 类型 | 意图 | 是否记录调用 | 是否保留真实实现 | Vitest 写法 |
| --- | --- | --- | --- | --- |
| stub | 只负责给出固定答案 | 否 | 否 | `vi.stubGlobal` / `mockReturnValue` |
| spy | 旁观：真实实现照跑，顺便记录 | 是 | 是 | `vi.spyOn(obj, 'method')` |
| mock | 行为完全由测试指定 | 是 | 否 | `vi.fn()` |
| fake | 能跑的简化实现，有自己的内部状态 | 视情况 | 有自己的逻辑 | 手写一个替身函数/类 |

> 摘自 `./code/test-lab/src/unit/doubles.test.js`

```js
import { describe, it, expect, vi, beforeEach, afterEach } from 'vitest'
import { fetchProfile, findUser } from './user-api.js'
import { loadUserName } from './profile.js'

// 四类测试替身的区别，全在这一个文件里对照：
//   stub  —— 替身只负责"给出固定答案"，不记录调用（vi.stubGlobal / mockReturnValue）
//   spy   —— 保留真实实现，顺便记录调用（vi.spyOn）
//   mock  —— 完全由测试指定行为，并记录调用（vi.fn）
//   fake  —— 能跑的简化实现，有自己的内部状态（下面手写的 fakeFetch）

function fakeFetch(routes) {
    return url => {
        const route = routes[url]
        if (!route) return Promise.resolve({ ok: false, status: 404, json: () => Promise.resolve(null) })
        return Promise.resolve({ ok: true, status: 200, json: () => Promise.resolve(route) })
    }
}

describe('替身家族对照', () => {
    afterEach(() => {
        vi.unstubAllGlobals()
        vi.restoreAllMocks()
    })

    it('stub：只给答案，不关心被调了几次', async () => {
        vi.stubGlobal('fetch', vi.fn(fakeFetch({ '/api/users/1': { id: '1', name: '阿白' } })))

        const user = await fetchProfile('1')
        expect(user.name).toBe('阿白')
        // stub 一般不写这种断言 —— 写了就变成 mock 了
        expect(fetch).toHaveBeenCalledTimes(1)
    })

    it('spy：保留真实实现，只做旁观记录', () => {
        const spy = vi.spyOn(console, 'log').mockImplementation(() => {})
        console.log('hello')
        expect(spy).toHaveBeenCalledWith('hello')
        // restoreAllMocks 负责还原，避免污染后续用例
    })

    it('mock：行为完全由测试指定，包括抛错', async () => {
        vi.stubGlobal(
            'fetch',
            vi.fn().mockResolvedValueOnce({ ok: false, status: 500, json: () => Promise.resolve(null) })
        )

        await expect(fetchProfile('1')).rejects.toThrow('HTTP 500')
    })

    it('fake：内部有状态，能表达"第一次失败第二次成功"', async () => {
        let calls = 0
        vi.stubGlobal(
            'fetch',
            vi.fn(() => {
                calls += 1
                if (calls === 1) return Promise.resolve({ ok: false, status: 503, json: () => Promise.resolve(null) })
                return Promise.resolve({ ok: true, status: 200, json: () => Promise.resolve({ name: '阿白' }) })
            })
        )

        expect(await loadUserName('1')).toBe('未知用户')
        expect(await loadUserName('1')).toBe('阿白')
    })
})

describe('异步断言的三种写法', () => {
    afterEach(() => {
        vi.unstubAllGlobals()
    })

    beforeEach(() => {
        vi.stubGlobal('fetch', vi.fn(fakeFetch({ '/api/users/2': { id: '2', name: '小黑' } })))
    })

    it('await + 直接断言（最推荐，可读性最好）', async () => {
        const user = await fetchProfile('2')
        expect(user.name).toBe('小黑')
    })

    it('resolves / rejects（断言一个 promise 更紧凑）', async () => {
        await expect(fetchProfile('2')).resolves.toEqual({ id: '2', name: '小黑' })
    })

    it('兜底分支也要测：网络失败时返回未知用户', async () => {
        expect(await loadUserName('not-exist')).toBe('未知用户')
    })
})

describe('不替换依赖也能测的部分，就不要替换', () => {
    it('纯函数直接测，零替身', () => {
        expect(findUser('1')).toEqual({ id: '1', name: '阿白' })
        expect(findUser('404')).toBeUndefined()
    })
})
```


最后一条是 fake 的价值所在：**它能表达"状态随时间变化"**，而 `mockReturnValueOnce` 只能表达"第 N 次调用返回什么"。要测重试逻辑、熔断、缓存命中率，fake 比一串 `Once` 清晰得多。

### 替换整个模块：`vi.mock`

当依赖是一个模块（而不只是某个全局函数），用 `vi.mock` 替换整张依赖图里的那个模块：

> 摘自 `./code/test-lab/src/unit/module-mock.test.js`

```js
import { describe, it, expect, vi, beforeEach, afterEach } from 'vitest'

// vi.mock 会被提升到文件顶部：它替换的是"模块依赖图里的那个模块"
// 所有 import 拿到的都是替身，不需要 stubGlobal
vi.mock('./user-api.js', async () => {
    const actual = await vi.importActual('./user-api.js')
    return {
        ...actual,
        fetchProfile: vi.fn()
    }
})

import { fetchProfile } from './user-api.js'
import { loadUserName, loadUserCard } from './profile.js'

beforeEach(() => {
    vi.mocked(fetchProfile).mockReset()
})

describe('整模块替换：把数据层换成 mock', () => {
    it('正常路径', async () => {
        vi.mocked(fetchProfile).mockResolvedValue({ id: '1', name: '阿白' })
        expect(await loadUserName('1')).toBe('阿白')
    })

    it('异常路径：抛错时兜底', async () => {
        vi.mocked(fetchProfile).mockRejectedValue(new Error('HTTP 500'))
        expect(await loadUserName('1')).toBe('未知用户')
    })

    it('一次调用被并发复用时只请求一次', async () => {
        vi.mocked(fetchProfile).mockResolvedValue({ id: '1', name: '阿白' })
        const card = await loadUserCard('1')
        expect(card).toEqual({ name: '阿白', orderCount: 1 })
        expect(fetchProfile).toHaveBeenCalledTimes(1)
    })
})

describe('vi.doMock：只在运行时替换，不受提升影响', () => {
    afterEach(() => {
        vi.doUnmock('./user-api.js')
        vi.resetModules()
    })

    it('同一个文件里可以对不同模块用不同策略', async () => {
        // resetModules 必须在 doMock 之前：先清掉模块缓存，再让新的 import 走替身
        vi.resetModules()
        vi.doMock('./user-api.js', () => ({
            fetchProfile: vi.fn().mockResolvedValue({ name: '动态替身' })
        }))

        const { loadUserName: fresh } = await import('./profile.js')
        expect(await fresh('1')).toBe('动态替身')
    })
})
```


三个要点：

1. **`vi.mock` 会被提升到文件顶部**，所以它写在 `import` 之后也照样生效 —— 这是它最容易让人困惑的地方。
2. 用 `importActual` 展开真实模块再覆盖某一个导出，可以做到"只替换需要替换的部分"。
3. `vi.mocked(fn)` 只是为了拿回类型提示，运行时是透明的。

如果需要在用例运行时动态替换（而不是文件顶部提升），用 `vi.doMock`，但必须配合 `vi.resetModules()`。

## 六、替身的使用纪律

### 只 mock 边界，不 mock 内部

值得替换的通常是这四类"不受你控制"的东西：

- **网络**（`fetch` / XHR / SDK）
- **时间**（`Date`、`setTimeout`、`performance`）
- **随机与 ID**（`Math.random`、`crypto.randomUUID`）
- **全局与环境**（`localStorage`、`window.matchMedia`、环境变量）

反过来，**不要 mock 你自己的被测单元**，也不要 mock 内部函数。判断标准很简单：这个东西的实现由我维护吗？是，就别 mock。

### 必须还原：mock 会泄漏

`vi.spyOn` 默认不会自动还原。下面这个实验直接复现了后果 —— 注意第二个用例用了 `it.fails`，因为它确实是坏的：

> 摘自 `./code/test-lab/src/unit/leak.test.js`

```js
import { describe, it, expect, vi, afterEach } from 'vitest'

// 这个文件的用例必须按顺序跑，用来复现"mock 没还原"的后果
// vitest 默认不会自动还原 spy（restoreMocks 默认 false）

describe('反例：mock 泄漏', () => {
    it('A 用例 spy 了 console.log 且不还原', () => {
        vi.spyOn(console, 'log').mockImplementation(() => {})
        expect(console.log.mock).toBeTruthy()
    })

    it.fails('B 用例拿到的 console.log 已经被换掉了', () => {
        expect(console.log.mock).toBeUndefined()
    })
})

describe('正例：每个用例结束都还原', () => {
    afterEach(() => {
        vi.restoreAllMocks()
    })

    it('A 用例 spy 后由 afterEach 还原', () => {
        vi.spyOn(console, 'log').mockImplementation(() => {})
        expect(console.log.mock).toBeTruthy()
    })

    it('B 用例拿到的是干净的 console.log', () => {
        expect(console.log.mock).toBeUndefined()
    })
})
```


三种还原方式，按粒度从粗到细：

- `vi.restoreAllMocks()` —— 还原所有 `spyOn`；
- `vi.unstubAllGlobals()` —— 还原所有 `stubGlobal`；
- 配置 `restoreMocks: true` / `unstubGlobals: true` —— 全局自动还原，最省心，代价是偶尔会掩盖"谁改了全局"这个问题。

## 七、参数化与数据构造

一个逻辑有多组输入输出时，用 `it.each` 把用例变成一行一条数据，补用例的成本降到几乎为零（见测试工具上手里的表驱动示例）。

数据本身不要手写一堆字面量 —— 做个 factory：

> 示意片段（无配套脚本）

```js
// 只填这次关心的字段，其余给默认值
function makeUser(overrides = {}) {
    return { id: '1', name: '阿白', vip: false, balance: 0, ...overrides }
}
```

factory 的好处是**新增字段时不用改所有用例**，而一堆手写对象字面量会让你在加字段时改到崩溃。
