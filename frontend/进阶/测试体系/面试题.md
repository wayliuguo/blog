# 模块面试题 · 测试体系

## 1.测试工具上手

### Q1（1.1）｜ 为什么前端项目现在更推荐 Vitest 而不是 Jest？

- **判断**：Vite / ESM 技术栈优先 Vitest —— 复用 Vite 的解析与转译，TS/JSX/CSS Modules 零配置，watch 快，配置与 Vite 统一。
- **展开**：Jest 需要 babel/ts-jest 额外配置，且偏 CJS 取向；Vitest 原生 ESM，和源码同一模块系统。两者 API 高度相似（`describe`/`it`/`expect`），迁移主要是配置与 mock 写法的替换。
- **边界**：老 webpack / CJS 项目或已有 Jest 体系可沿用 Jest，不必强迁；后端（Node/NestJS）测试见 `node/进阶主题/测试.md`。

### Q2（1.2）｜ `vitest` 和 `vitest run` 有什么区别？CI 里该用哪个？

- **判断**：`vitest` 进入 watch 模式，改文件自动重跑，本地开发用；`vitest run` 跑一次就退出，CI 必须用。
- **展开**：watch 模式不会自己结束，在 CI 里会卡死流水线导致超时；`run` 一次性退出并带回退出码，门禁靠这个码判断红绿。
- **边界**：只想跑某段时加路径或 `-t` 过滤，如 `vitest run src/hello`。

### Q3（1.3）｜ `globals` 开还是关？为什么本仓库示例都关着？

- **判断**：关。多一行 `import` 换"API 从哪来"永远清楚，也避免和页面全局变量混淆。
- **展开**：开着 `globals` 后 `describe`/`it`/`expect` 变成全局，初看省事，但大项目里分不清是测试 API 还是业务全局，重构时更容易踩坑。
- **边界**：如果团队确实想要全局写法，可在配置里开 `test.globals: true`，但本仓库所有示例保持关闭以统一口径。


## 2.测试策略与分层

### Q4（2.2）｜ 前端测试为什么要分层？单层不行吗？

- **判断**：分层是因为每层的"反馈速度 / 定位精度 / 维护成本"组合不同，单层必然在某处失衡 —— 只有单测测不到渲染与集成，只有 E2E 则慢到没人愿意跑。
- **展开**：静态检查最便宜（秒级、零维护）；单测毫秒级、定位最准；组件测试覆盖渲染与交互、比 E2E 快一个数量级；E2E 覆盖真实浏览器但秒到分钟级、且脆。
- **边界**：前端更贴近"测试奖杯"而非金字塔 —— 中间层（组件/集成）最厚，因为逻辑长在组件里。追问：比例怎么定？→ 不按教条，按改动频率与出错代价：高频模块密度高，钱/权限路径必进 E2E。

### Q5（2.2）｜ 单元测试与组件测试的区别？

- **判断**：单测不挂载组件、面向纯逻辑与数据变换；组件测试挂载到内存 DOM，模拟用户交互，断言渲染结果与事件回调。
- **展开**：组件测试操作的是"契约"—— props 进、渲染/事件出，中间还有异步三态（loading / success / error）。
- **边界**：组件测试不能替代 E2E —— 真实浏览器差异、跨页流程测不到；反之 E2E 已覆盖的长链路不应在组件层重复。追问：组件测试要不要测样式？→ 不测像素与动画，视觉交给截图对比。

### Q6（2.1）｜ 场景：要重构一个核心模块，怎么保证不重构出事故？

- **判断**：先给现有行为补"行为级"用例（表驱动 + 手写常数期望），重构过程中用例一行不改即为成功。
- **展开**：测实现的用例（mock 内部依赖、重言式断言）会在重构时变红，反而掩盖真正的回归；测行为的用例是重构的安全网。
- **边界**：补用例时要覆盖边界（小数、空值、0 值），这些才是真正容易出错的地方。追问：重构完覆盖率掉了怎么办？→ 看掉的是哪几行（报告有 Uncovered Line #s），补用例而不是调阈值。

### Q7（2.4）｜ 场景：一个已有项目要从 0 开始补测试，怎么做才不半途而废？

- **判断**：按"静态检查 → 盘 P0 → 组件测试 → E2E 关键路径 → 单测 → CI 门禁 → 治理 flaky"的顺序推进，覆盖率只做增量阈值。
- **展开**：先上零维护成本的静态检查建立信心；P0 清单决定资源投向；组件测试性价比最高；门禁先只卡"必须全绿"，避免一上来就卡 80% 覆盖率导致所有合并被拒。
- **边界**：测试范围要**由页面配置派生**（新增页面自动进入盘点与回归清单），靠人工清单必然遗漏。追问：老模块覆盖率 30% 怎么办？→ 不设绝对阈值，只要求本次改动的行被覆盖，让数字随改动缓慢上升。

## 3.单元测试

### Q8（3.1）｜ Vitest 还是 Jest？

- **判断**：Vite 技术栈优先 Vitest —— 复用 Vite 配置与转换能力，TS/JSX/CSS Modules 开箱可用，配置成本极低；老项目（尤其非 Vite 构建）迁移成本高时可留 Jest。
- **展开**：Vitest 走 Vite 的解析与 esbuild 转换，速度快；Jest 需要 babel/ts-jest 额外配置。
- **边界**：两者 API 高度相似（`describe`/`it`/`expect`/`vi` vs `jest`），迁移主要是配置与 mock 写法的替换。追问：`globals` 要不要开？→ 建议不开，显式 import 让来源清晰，也避免与页面全局变量混淆。

### Q9（3.4）｜ 假定时器是怎么工作的？为什么它能测出真定时器的边界？

- **判断**：`vi.useFakeTimers()` 把 `setTimeout` / `setInterval` / `Date` 等换成可手动拨动的假时钟，`advanceTimersByTime(n)` 直接把时间推进 n 毫秒。
- **展开**：时间不再由真实时钟决定，所以"第 299 毫秒不触发、第 300 毫秒触发"这类边界可以被精确断言；用例也从等 300ms 变成毫秒级。
- **佐证**：

```
useFakeTimers() + advanceTimersByTime(300)   等 300ms → 拨 300ms
setSystemTime   连 Date 一起冻结，测跨天 / 有效期
假定时器不推进真实 Promise 的 await → 用 advanceTimersByTimeAsync
```

- **边界**：假定时器不会推进真实 Promise 的 await，需要 `advanceTimersByTimeAsync`；用完必须 `useRealTimers`。追问：`setSystemTime` 有什么用？→ 把 `Date` 也冻结，用来测跨天、有效期这类逻辑。

### Q10（3.5）｜ stub、spy、mock、fake 有什么区别？

- **判断**：不是一回事 —— stub 只给固定答案；spy 保留真实实现只做记录；mock 行为完全由测试指定并记录调用；fake 是能跑的简化实现，有自己的内部状态。
- **展开**：区别在于"是否保留真实实现"与"是否记录调用"两个维度。

```
stub   给固定答案，不记录调用
spy    真实实现照跑，只做记录
mock   行为由测试指定，记录调用
fake   有内部状态，能表达"第一次失败第二次成功"这类时序
```

- **边界**：需要表达"第一次失败第二次成功"这类时序时用 fake，比一串 `mockReturnValueOnce` 清晰。追问：哪些东西该替换？→ 边界四件套：网络、时间、随机、全局环境；自己维护的内部函数不要 mock。

### Q11（3.5）｜ `vi.mock` 为什么写在 import 后面也生效？

- **判断**：因为 `vi.mock` 会被提升到文件顶部执行，替换的是模块依赖图里的那个模块，所有 import 拿到的都是替身。
- **展开**：配合 `importActual` 展开真实模块再覆盖个别导出，可以做到只替换需要替换的部分。
- **边界**：需要在运行时动态替换时用 `vi.doMock`，但必须先 `vi.resetModules()` 清掉模块缓存。追问：`vi.mocked()` 是什么？→ 只是拿回类型提示的包装，运行时透明。

## 4.组件测试

### Q12（4.2）｜ 组件测试里为什么要按 role / label 查询，而不是按 class？

- **判断**：按 role / label 查询等价于"用户怎么找到这个元素"，把断言与实现解耦；按 class 或 DOM 结构查，改个标签名就红。
- **展开**：RTL 的查询优先级是 Role → LabelText → Placeholder → Text → DisplayValue → AltText → Title → TestId，`getByTestId` 是兜底。
- **边界**：`getBy*` 查不到会抛错并打印整棵 DOM（很好的调试线索）；`queryBy*` 用于断言"不存在"；`findBy*` 用于"最终会出现"。追问：`fireEvent` 和 `user-event` 用哪个？→ `user-event`，它模拟完整事件序列，能测出逐字符输入、聚焦丢失这类问题。

### Q13（4.4）｜ 断言异步中间态（loading）为什么要用 deferred？

- **判断**：手动控制 Promise 的兑现时机，才能在"请求中"这个瞬间稳定断言按钮禁用与文案变化。
- **展开**：`mockReturnValue(deferred.promise)` 让被测组件停在 pending，断言完再 `resolve`，中间态就被锁住了。
- **佐证**：

```
deferred = 手动控制的 { promise, resolve }
mockReturnValue(deferred.promise)   组件停在 pending，断言 loading
断言完 → resolve()                   走 success 分支
```

- **边界**：失败分支同样要测，而且要断言按钮恢复可用，否则用户卡死在 loading 上。追问：如果一定要等一个不受控的异步过程呢？→ 用 `waitFor` 等条件成立，不要 `sleep` 固定时间。

## 5.E2E 与稳定性

### Q14（5.1）｜ E2E 应该放哪些用例？

- **判断**：只放"挂了就是事故"的关键路径 —— 登录、下单支付、跨页跳转、第三方集成；几十条，不是几百条。
- **展开**：E2E 秒到分钟级、需要真实浏览器与数据准备，成本结构决定了它不能铺开。
- **边界**：组件分支细节、边界值、表单校验组合都不该进 E2E，它们属于单测与组件测试。追问：规模失控了怎么办？→ 并行分片 + 精简路径，而不是无脑加机器。

### Q15（5.2）｜ Playwright 还是 Cypress？

- **判断**：需要多浏览器、原生并行、CI 上大规模跑，选 Playwright；看重交互式调试体验与文档友好度，选 Cypress。
- **展开**：Playwright 原生支持 Chromium/Firefox/WebKit 与多 worker 并行、内置 trace；Cypress 的调试器体验更成熟，并行历史上需要额外方案。
- **边界**：两者都能做网络拦截与自动等待，选型更多取决于团队现有技术栈与 CI 形态。追问：用例多了怎么提速？→ 并行 worker + `--shard` 分片 + 失败才保留 trace。

### Q16（5.3）｜ Playwright 的断言为什么不用写 sleep？

- **判断**：Playwright 的断言是 web-first 的，会**自动重试**直到超时，天然吸收"元素还没渲染"这类时序问题。
- **展开**：`expect(locator).toBeVisible()` 内部轮询；同理导航用 `waitForURL`、请求用 `waitForResponse`。等条件，不等时间。
- **佐证**：

```
expect(page.getByRole('button')).toBeVisible()   自动重试到超时
waitForURL('**/order/**')                         等 URL
waitForResponse('**/api/**')                      等请求
```

- **边界**：自动等待治不了"数据不可控"，数据准备要独立（每用例独立账号、用 API 造前置数据）。追问：写 `waitForTimeout(1000)` 有什么问题？→ 慢机器上不够、快机器上白等，是 flaky 的头号来源。

### Q17（5.5）｜ 一条用例时红时绿（flaky），怎么排查？

- **判断**：按四个根因逐个排除 —— 用 sleep 赌时间、用例间共享可变状态、依赖"现在"、时区。
- **展开**：前两个是时序与顺序依赖，后两个是环境依赖（时间/时区会随运行时刻与机器而变）。

| 根因 | 对策 |
| ---- | ---- |
| sleep 赌时间 | 等条件成立 |
| 用例间共享状态 | beforeEach 重置，用 shuffle 暴露 |
| 依赖"现在" | 时间注入 + `setSystemTime` |
| 时区 | 明确业务口径，固定 `TZ` 或用 UTC 方法 |

- **边界**：加 `waitForTimeout` 或调大超时都只是掩盖；正确做法是等条件、重置状态、注入时间、明确时区口径。追问：怎么让共享状态问题提前暴露？→ 日常用 `--sequence.shuffle` 跑套件，顺序依赖会第一时间翻车。

### Q18（5.7）｜ 场景：团队抱怨"测试红了重跑就好"，怎么重建信任？

- **判断**：把 flaky 治理当成项目做 —— 量化失败率 Top10 → 隔离出主门禁 → 用 trace 定位 → 修根因 → 重复跑验证 → 立规矩。
- **展开**：flaky 的危害不是浪费 CI 时间，而是消耗信任；一旦大家习惯重跑，真 bug 混在里面也没人看。
- **佐证**：

```
量化 Top10 → 隔离 → trace 定位 → 修根因 → 重复跑验证 → 立规矩
```

- **边界**：`retries` 只降噪不治本，必须配"连续 N 次重试才通过就报警"；隔离要有 deadline，否则永远修不完。追问：修不动的用例怎么办？→ 设 deadline，到期就删 —— 一条没人信的测试不如没有。

## 6.测试基建与门禁

### Q19（6.1）｜ 覆盖率分哪几种口径？分支覆盖为什么常低于行覆盖？

- **判断**：四种口径 —— 语句、行、分支、函数；分支覆盖比行覆盖严格：行覆盖只要求"执行到"，分支覆盖要求每条路径都走到。
- **展开**：`if (a && b)` 只要被执行过，行覆盖就是 100%，但 `a` 假、`b` 假、都为真三条路径未必都走过。
- **佐证**：

```
语句   每条语句执行过
行     每行执行过
分支   每个分支都走到   ← 最有信息量
函数   每个函数调用过
```

- **边界**：覆盖率是信号不是目标 —— 80% 覆盖不等于 80% 质量，弱断言能刷出 100% 覆盖却抓不到业务 bug。追问：v8 与 istanbul 怎么选？→ v8 快、istanbul 分支粒度细；选定后不要中途换，否则趋势会断。

### Q20（6.2）｜ 覆盖率 100% 就说明代码没问题吗？

- **判断**：不能。覆盖率只衡量"代码被执行过"，不衡量"结果被验证过"；弱断言（`expect(typeof x).toBe('number')`）能刷出 100% 覆盖。
- **展开**：覆盖率工具不看断言内容。同一份代码把断言换成具体值，立刻暴露业务 bug（实测：期望 81、实际 65）。
- **边界**：反过来，覆盖率低的模块也不能一棍子打死 —— 脚本、配置、一次性代码不该要求覆盖率。追问：那覆盖率该怎么用？→ 存量代码只卡**增量覆盖率**，核心目录设高阈值，阈值只升不降。

### Q21（6.5）｜ CI 上的测试越来越慢，怎么治理？

- **判断**：按性价比依次做 —— 缓存依赖、并行与分片、只跑受影响的部分、减少 worker 启动开销、快慢分层。
- **展开**：Vitest 默认每个测试文件起一个隔离环境，文件多时开销显著，`isolate: false` 复用 worker 能提速（前提是用例之间没有共享状态）。
- **边界**：`isolate: false` 与"用例必须独立"是同一件事的两面 —— 有共享状态的套件不能关。追问：套件慢到什么程度要处理？→ 给团队定一个速度预算（如本地全量 30 秒内），超了就治理。
