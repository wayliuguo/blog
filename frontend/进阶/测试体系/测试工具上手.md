# 测试工具上手

前面几篇会讲"测什么、怎么分层、替身怎么写、覆盖率怎么卡"。但在那之前，得先让你今天就能在本地跑起第一个用例——**把"会不会用工具"和"该怎么测"彻底拆开**。策略与分层解决的是认知问题，替身与定时器解决的是技术深水区，而这一篇只做一件事：带你在零基础下把 Vitest 用起来。

> 本篇是模块入口，纯 Vitest、零 Jest。如果你在 webpack / CJS 老项目里用 Jest，后端测试部分见 `node/进阶主题/测试.md`，本篇不重复。

## 一、为什么这一篇放在最前面

一个能跑的 hello world，比三页"为什么要测试"的哲学更有用：

- 工具是先决条件。后面的策略、替身、覆盖率，全部建立在"你能写一个 `it` 并让它变绿"之上。
- 工具认知和测试认知是两件事。很多人卡住不是因为不懂"该测什么"，而是被"环境配不起来、报错看不懂、不知道怎么只跑一条"劝退。
- 这一篇只覆盖**入门面**：安装、第一个用例、配置最小集、文件约定、常用断言、过滤、覆盖率开关。替身 / 假定时器 / 异步这些"深水分"留给[单元测试深入](./单元测试深入.md)。

## 二、测试运行器是什么，为什么是 Vitest

测试运行器干四件事：

```
发现   按命名规则找出所有测试文件
加载   转译 TS/JSX，准备好运行环境（node 或 DOM）
执行   describe/it 组织用例，expect 做断言
报告   哪些绿、哪些红、挂了为什么
```

Vite 技术栈选 Vitest 的理由全在"复用 Vite"上：

- **零额外转译**：TS、JSX、CSS Modules 直接能吃，不用再配 babel/ts-jest。
- **watch 快**：复用 Vite 的模块图与 HMR 通道，改一个文件只重跑受影响的用例。
- **一份配置**：`test` 字段直接写在 `vite.config` 里，不用维护两套。
- **原生 ESM**：和源码同一个模块系统，没有 CJS/ESM 互转的坑。

一句选型：

| 你的技术栈 | 选什么 |
| --- | --- |
| Vite / ESM 前端项目 | **Vitest** |
| 老 webpack / CJS 项目，已有 Jest 体系 | 沿用 **Jest**（迁移成本低，但本篇不讲） |
| Node / NestJS 后端 | 见 `node/进阶主题/测试.md`（Jest 体系） |

## 三、从 0 跑通：你的第一个用例

最小动作链只有三步。

**1. 装**：`npm i -D vitest`

**2. 写**一个被测函数和一个用例文件（放在 `src/hello/` 下，与源码同级）：

> 摘自 `./code/test-lab/src/hello/sum.test.js`

```js
import { describe, it, expect } from 'vitest'
import { sum } from './sum.js'

describe('sum', () => {
    it('两个正数相加', () => {
        expect(sum(1, 2)).toBe(3)
    })

    it('能处理负数', () => {
        expect(sum(-1, 1)).toBe(0)
    })
})
```

**3. 跑**：

- `vitest`——进入 watch 模式，改文件自动重跑，本地开发用。
- `vitest run`——跑一次就退出，**CI 里必须用这个**（watch 模式不会自己结束，会卡死流水线）。
- 只跑这一个目录：`vitest run src/hello`。

输出里看三件事：

```
 ✓ src/hello/sum.test.js (2 tests) 12ms
 Test Files  1 passed (1)
      Tests  2 passed (2)
   Duration  875ms
```

绿的就是过了；红的会打印**失败信息**——这一行信息本身就是定位线索（[单元测试深入](./单元测试深入.md) 第二章专门讲怎么让失败信息更有用）。

## 四、配置文件的最小集

上面的 hello world **一个配置文件都没写**——Vitest 零配置就能跑，默认 `node` 环境、默认按 `*.test.*` / `*.spec.*` 找文件。只有需要定制时才写配置，最小集就这么大：

> 摘自 `./code/test-lab/hello.config.js`

```js
import { defineConfig } from 'vitest/config'

export default defineConfig({
    test: {
        // 纯逻辑用 node（最快）；需要 DOM 的用例在文件首行加 // @vitest-environment jsdom
        environment: 'node',
        // 决定哪些文件算测试；! 开头的是排除项
        include: ['src/**/*.test.{js,jsx,ts,tsx}']
    }
})
```

三个决定，和后面[单元测试深入](./单元测试深入.md) 的口径一致：

- **`environment`**：纯逻辑用 `node`（最快），要 DOM 的用 `jsdom` / `happy-dom`。**按文件切换优于全局**——在文件首行写 `// @vitest-environment jsdom`，其它文件不必为它付启动成本。
- **`globals`**：默认关闭，`describe`/`it`/`expect` 需要显式 `import`。多敲一行，换来"这些 API 从哪来"永远清楚，也避免和页面全局变量混淆。**本仓库所有示例都保持关闭**。
- **`include`**：决定哪些文件算测试；`!` 开头的是排除项（有些故意留失败的演示用例不该进默认套件）。

配置放哪：直接写在 `vite.config` 的 `test` 字段，或独立成 `vitest.config.js`（如上面这个 `hello.config.js`）。同一个项目只认一个配置入口。

## 五、测试文件约定

- **命名**：`*.test.{js,ts}` 或 `*.spec.{js,ts}`。一眼能认出"这是测试"。
- **位置**：和源码同级（如 `sum.js` + `sum.test.js`），或统一塞进 `__tests__/`。同级最直观，重构时不会"源文件删了测试还在"。
- **一个文件长什么样**：`describe` 分组、`it`（或 `test`）写单条用例、`expect` 做断言。第三篇的 `sum.test.js` 就是完整示例。
- **基本钩子**：`beforeEach` / `afterEach` 等在每条用例前后跑，用来准备 / 还原环境。完整的四种生命周期钩子留到[单元测试深入](./单元测试深入.md) 第二章展开。

## 六、必会的几个断言（常用 20%）

断言就是"我期望这个结果"。最常用的就这么几个，覆盖了日常 80% 的场景：

> 摘自 `./code/test-lab/src/hello/assert.test.js`

```js
import { describe, it, expect } from 'vitest'
import { sum } from './sum.js'

describe('必会的几个断言', () => {
    it('toBe：原始值严格相等（Object.is）', () => {
        expect(sum(1, 2)).toBe(3)
    })

    it('toEqual：对象深比较', () => {
        expect({ a: 1, b: 2 }).toEqual({ a: 1, b: 2 })
    })

    it('toThrow：断言抛出', () => {
        expect(() => {
            throw new Error('boom')
        }).toThrow('boom')
    })

    it('toContain：数组/字符串包含', () => {
        expect([1, 2, 3]).toContain(2)
    })

    it('toMatchObject：部分字段匹配', () => {
        expect({ id: 1, name: '小黑', age: 3 }).toMatchObject({ name: '小黑' })
    })
})
```

一张速查表：

| 断言 | 语义 | 什么时候用 |
| --- | --- | --- |
| `toBe` | `Object.is` 严格相等 | 数字 / 字符串 / 布尔等原始值 |
| `toEqual` | 深比较，忽略 `undefined` 属性 | 对象 / 数组的常规比较 |
| `toStrictEqual` | 深比较，且查 `undefined` 属性和原型 | 想连"多出一个字段"也抓出来 |
| `toThrow` | 断言抛错 | 错误分支；可带参数断言错误信息 |
| `toContain` | 包含 | 数组 / 字符串 |
| `toMatchObject` | 部分字段匹配 | 只关心返回对象里的某几个字段 |

一条贯穿全模块的原则：**写具体值，不要写类型**。

```
// 弱：实现返回 undefined 也过得去，挂了也看不出哪错
expect(typeof result).toBe('number')

// 强：挂掉时直接告诉你"期望 81，实际 65"
expect(calcPay(81, true)).toBe(81)
```

`toStrictEqual`、软断言 `expect.soft` 这类进阶用法，在[单元测试深入](./单元测试深入.md) 第二章。

## 七、只跑你关心的

套件一大，每次全跑很慢。三种最常用的收窄方式：

- **路径过滤**：`vitest run src/hello`——只跑这个目录下的用例。
- **名字过滤**：`vitest run -t "负数"`——只跑用例名含"负数"的（对应 `it` 的标题）。
- **文件内标记**：`it.only('…')` 只跑这一条、`it.skip('…')` 跳过、`it.todo('…')` 占位待写。调试时 `it.only` 最省事。

更细的过滤与生命周期（`beforeAll` / `afterAll`、按 tag 分组）见[单元测试深入](./单元测试深入.md) 第二章。

## 八、覆盖率怎么开

想知道"代码有没有被执行到"，加一个开关就行：

```
vitest run src/hello --coverage
```

Vitest 用 `v8` 作为覆盖率 provider（快、零侵入），报告默认打印在终端，也能输出 html 看每一行有没有跑到。`provider` 写在配置里，本仓库的 `vitest.config.js` 已配好。

覆盖率本身只是"代码被执行过"的信号，衡量不了"结果被验证过"——弱断言照样能刷出 100%。**它真正有用的地方是当门禁**：不达阈值就非零退出，卡住没人维护的盲区。怎么设阈值、怎么增量卡、怎么接 CI，是[测试基建与门禁](./测试基建与门禁.md)（模块第 6 章）的主题。
