# 测试基建与门禁

前面几篇解决了「怎么写测试」，这一篇解决「怎么让测试在团队里长期发挥作用」。核心是两件事：**基建**——让测试「看得见、信得过」（覆盖率能不能代表质量、怎么度量、怎么看趋势）；**门禁**——让「质量不达标就不让合入」变成一个不靠人自觉的机制。本篇按 基建 → 门禁 两部分展开，每部分都从目的出发，落到可执行的拆解：基建讲覆盖率口径、陷阱、阈值与报告；门禁讲落地、提速与落地清单。

## 基建：让测试看得见、信得过

## 一、覆盖率统计的到底是什么

覆盖率工具不检查你的断言对不对，它只记录**哪些代码被执行过**。常见的四种口径：

| 口径 | 统计什么 | 特点 |
| --- | --- | --- |
| 语句覆盖（Statements） | 每条语句是否执行过 | 最粗，`if` 只走一个分支也算覆盖 |
| 行覆盖（Lines） | 每行是否执行过 | 与语句覆盖接近，报表里最常见 |
| 分支覆盖（Branches） | `if` / `switch` / 三元 / 短路的每个分支是否都走到 | 比行覆盖严格，通常更低 |
| 函数覆盖（Functions） | 每个函数是否被调用过 | 只看"调没调"，不看逻辑 |

四种口径里**分支覆盖最有信息量**：一行 `if (a && b)` 只要被执行过，行覆盖就是 100%，但 `a` 为假、`b` 为假、`a&&b` 为真这三条路径未必都走过。

### v8 与 istanbul 两种实现

- **v8**（`@vitest/coverage-v8`）：直接用 V8 引擎的运行时数据，不需要插桩，速度快、和源码映射关系简单；缺点是分支粒度较粗（对某些语法结构的判定与 istanbul 不同）。
- **istanbul**（`@vitest/coverage-istanbul`）：对源码做插桩后再跑，慢一些，但分支统计更细、历史数据可比性更好。

选哪个都行，但**不要中途换** —— 同一个项目换 provider 会出现覆盖率数字整体跳变，趋势图就断了。

## 二、覆盖率 100% 也可能是零保障

看一份被测代码，里面藏着一个业务 bug：VIP 折扣本该"满 100 才生效"，实现里漏了这条判断。

> 摘自 `./code/test-lab/src/coverage-demo/checkout.js`

```js
export function calcPay(amount, isVip) {
    if (amount <= 0) return 0
    const rate = isVip ? 0.8 : 1
    return Math.round(amount * rate)
}

export function canCheckout(user, cart) {
    if (!user) return false
    if (!cart || cart.length === 0) return false
    const total = cart.reduce((sum, item) => sum + item.price * item.count, 0)
    return user.balance >= total
}
```

下面这套用例把每条分支都走了一遍，但断言只说"是个数字"：

> 摘自 `./code/test-lab/src/coverage-demo/checkout.test.js`

```js
describe('弱断言：覆盖率好看，质量没保障', () => {
    it('VIP 有折扣', () => {
        const result = calcPay(81, true)
        expect(typeof result).toBe('number')
    })

    it('非 VIP 不打折', () => {
        expect(typeof calcPay(81, false)).toBe('number')
    })

    it('金额为 0 时返回 0', () => {
        expect(typeof calcPay(0, true)).toBe('number')
    })

    it('未登录不能下单', () => {
        expect(typeof canCheckout(null, [{ price: 10, count: 1 }])).toBe('boolean')
    })

    it('空购物车不能下单', () => {
        expect(typeof canCheckout({ balance: 100 }, [])).toBe('boolean')
    })

    it('余额充足可以下单', () => {
        expect(typeof canCheckout({ balance: 100 }, [{ price: 10, count: 1 }])).toBe('boolean')
    })
})
```

跑出来的报告非常漂亮：

```
> test-lab@1.0.0 coverage
> vitest run src/coverage-demo --coverage

 ✓ src/coverage-demo/checkout.test.js (6 tests) 6ms

 Test Files  1 passed (1)
      Tests  6 passed (6)

 % Coverage report from v8
-------------|---------|----------|---------|---------|-------------------
File         | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s 
-------------|---------|----------|---------|---------|-------------------
All files    |     100 |      100 |     100 |     100 |                   
 checkout.js |     100 |      100 |     100 |     100 |                   
-------------|---------|----------|---------|---------|-------------------
```

四项全 100%，门禁通过。然后把**同一份被测代码**的断言换成具体值：

> 摘自 `./code/test-lab/src/coverage-strict/checkout.test.js`

```js
describe('强断言：覆盖率相同，但能抓到 bug', () => {
    it('未满 100 的 VIP 订单不打折', () => {
        expect(calcPay(81, true)).toBe(81) // 实际拿到 65，用例失败
    })

    it('满 100 的 VIP 订单打八折', () => {
        expect(calcPay(200, true)).toBe(160)
    })

    it('非 VIP 原价', () => {
        expect(calcPay(200, false)).toBe(200)
    })

    it('余额刚好等于总额可以下单', () => {
        expect(canCheckout({ balance: 100 }, [{ price: 50, count: 2 }])).toBe(true)
    })

    it('余额差一分也不能下单', () => {
        expect(canCheckout({ balance: 99.99 }, [{ price: 50, count: 2 }])).toBe(false)
    })
})
```

效果：

```
> test-lab@1.0.0 coverage:strict
> vitest run --config vitest.strict.config.js --coverage

 ❯ src/coverage-strict/checkout.test.js (5 tests | 1 failed) 16ms
   ❯ 强断言：覆盖率相同，但能抓到 bug (5)
     × 未满 100 的 VIP 订单不打折 12ms
     ✓ 满 100 的 VIP 订单打八折 0ms

 FAIL  src/coverage-strict/checkout.test.js > 强断言：覆盖率相同，但能抓到 bug > 未满 100 的 VIP 订单不打折
AssertionError: expected 65 to be 81 // Object.is equality
```

结论很直接：**覆盖率衡量的是"代码被执行"，断言质量衡量的是"结果被验证"，两者是独立维度。** 把覆盖率当 KPI，团队会理性地选择"写能提升覆盖率的弱断言"。

## 三、阈值与增量覆盖率

阈值配置写在测试配置里：

> 摘自 `./code/test-lab/vitest.config.js`（运行：`npm run coverage`）

```js
coverage: {
    provider: 'v8',
    include: ['src/coverage-demo/checkout.js'],
    reporter: ['text'],
    thresholds: {
        lines: 80,
        branches: 70,
        functions: 80,
        statements: 80
    }
}
```

阈值不达标时，命令以非 0 退出码结束 —— 这就是门禁的技术基础。实测（只跑一部分用例，模拟覆盖率下降）：

```
> test-lab@1.0.0 coverage:partial
> vitest run src/coverage-demo --coverage -t VIP

 ✓ src/coverage-demo/checkout.test.js (6 tests | 4 skipped) 6ms
 Tests  2 passed | 4 skipped (6)

 % Coverage report from v8
-------------|---------|----------|---------|---------|-------------------
File         | % Stmts | % Branch | % Funcs | % Lines | Uncovered Line #s 
-------------|---------|----------|---------|---------|-------------------
All files    |   27.27 |       30 |   33.33 |   42.85 |                   
 checkout.js |   27.27 |       30 |   33.33 |   42.85 | 11-14             
-------------|---------|----------|---------|---------|-------------------
ERROR: Coverage for lines (42.85%) does not meet global threshold (80%)
ERROR: Coverage for functions (33.33%) does not meet global threshold (80%)
ERROR: Coverage for statements (27.27%) does not meet global threshold (80%)
ERROR: Coverage for branches (30%) does not meet global threshold (70%)
```

注意这个例子里**行覆盖 42.85% 高于分支覆盖 30%** —— 这正是"分支覆盖通常比行覆盖更难达标"的直观体现。报表最后一列 `Uncovered Line #s` 直接告诉你该补哪几行。

### 三条阈值策略

1. **存量代码用"增量覆盖率"**：老项目整体覆盖率 30%，强行卡 80% 等于禁止所有合并。正确做法是只要求**本次改动的行**被覆盖（很多平台支持按 diff 计算），让覆盖率随改动缓慢上升。
2. **分层设阈值**：核心目录（支付、权限）设 90%，通用组件 70%，脚本与配置不设。一刀切只会逼人造假。
3. **阈值只升不降**：写进配置后用 CODEOWNERS 保护这个文件，避免"先改成 50% 让它绿了再说"。

## 门禁：让质量卡得住

## 四、门禁怎么落地

门禁的本质是：**一条命令的非 0 退出码阻断合并**。所以 CI 里那几行命令就是全部机制：

```
npm run lint && npm run test:coverage && npm run build
```

任何一环失败，后续不执行，流水线红，分支保护规则阻止合并。

一份可落地的准入清单：

| 阶段 | 检查 | 失败后果 |
| --- | --- | --- |
| pre-commit（本地） | lint-staged：只查改动文件的 ESLint / Prettier | 提交被拒 |
| commit-msg | commitlint 校验提交信息 | 提交被拒 |
| CI · 静态 | TypeScript 类型检查、ESLint 全量 | 阻断合并 |
| CI · 测试 | 单测 + 组件测试 + 覆盖率阈值 | 阻断合并 |
| CI · 构建 | 产物构建成功、体积预算 | 阻断合并 |
| CI · E2E | P0 关键路径 | 阻断发布 |
| 发布后 | 错误率 / 性能指标对比基线 | 触发回滚 |

两条容易踩的坑：

- **pre-commit 只做增量、不做全量。** 全量测试放 pre-commit 会让人养成 `--no-verify` 的习惯，门禁就废了。
- **E2E 不要挡在"合并"前面。** 它慢且偶发，放在"发布"前更合适；合并门禁由快反馈的那几层守住。

flaky 与门禁的关系：隔离 + deadline + 修根因，不要让重试次数掩盖问题。

## 五、CI 加速：让套件保持"值得跑"

套件慢了，人就跑得少，反馈就慢，质量就下滑。加速手段按性价比排序：

1. **缓存依赖**：`node_modules` 与构建缓存按 lockfile 哈希缓存，通常省掉大半时间。
2. **并行与分片**：单测/组件测试用多 worker；E2E 用 `--shard=i/n` 切到多台机器。
3. **只跑受影响的部分**：Monorepo 里用变更集（如 `turbo run test --filter=...changed`）只跑被改动影响的包。
4. **减少进程启动开销**：Vitest 默认每个测试文件起一个隔离环境，文件多时开销显著。实测中 vitest 自己会给出提示：

   ```
   Isolate  11 workers spawned · ~3.43s startup each (spawn + environment, per file)
            at least ~1.96s faster with isolate: false — reuses workers across files instead of one per file
   ```

   `isolate: false` 会复用 worker，提速的前提是用例之间没有隐式共享状态 —— 和第 4 篇的"共享状态"根因是同一件事的两面。
5. **把慢的用例分层跑**：组件测试里模拟逐字符输入的部分天然慢（本仓库实测 `LoginForm.test.jsx` 1.5s vs `Counter.test.jsx` 0.4s），把它们和快用例分开，让快反馈先回来。

## 六、报告与趋势

单次结果决定"这次能不能合"，趋势决定"这套体系是不是在变好"。Vitest 可以输出 JSON 报告，再由脚本汇总成两份信息：一份给机器（门禁、趋势），一份给人（最慢用例、失败清单）。

> 摘自 `./code/test-lab/scripts/report.mjs`（运行：`npm run report`）

```js
const res = spawnSync(
    npm,
    ['exec', '--', 'vitest', 'run', '--reporter=json', `--outputFile.json=${outFile}`],
    { encoding: 'utf8', shell: true, stdio: ['ignore', 'pipe', 'pipe'] }
)
```

> 摘自 `./code/test-lab/scripts/report.mjs`

```js
console.log('---- 给机器看（门禁 / 趋势用）----')
console.log(
    JSON.stringify(
        {
            numTotalTests: report.numTotalTests ?? passed + failed + skipped,
            numPassedTests: report.numPassedTests ?? passed,
            numFailedTests: report.numFailedTests ?? failed,
            success: report.success ?? failed === 0,
            durationMs: Math.round(report.runDuration ?? 0)
        },
        null,
        2
    )
)
```

实测输出：

```
---- 给机器看（门禁 / 趋势用）----
{
  "numTotalTests": 52,
  "numPassedTests": 52,
  "numFailedTests": 0,
  "success": true,
  "durationMs": 0
}

---- 给人看（本次最慢的 5 个用例）----
337.03770000000077ms  LoginForm.test.jsx > 空表单提交时给出校验提示，且不调用 onSubmit
324.5678000000007ms  LoginForm.test.jsx > 提交期间按钮禁用且文案变为登录中
319.6445999999996ms  Counter.test.jsx > 渲染初始值，点击后加一并回调
315.93829999999934ms  LoginForm.test.jsx > 等待 DOM 变化而不是睡固定时间
```

值得长期盯的三个趋势指标：**用例总数**（在涨说明覆盖在扩）、**套件耗时**（超过预算就要治理）、**单条用例失败率**（找出 flaky Top10）。这三个指标画成折线，比任何"覆盖率 78%"的快照都有用。

## 七、落地清单

按顺序做，每一步都能独立产生价值：

1. 静态检查进 CI（TS + ESLint），零维护成本。
2. 单测与组件测试接 CI，门禁先只卡"必须全绿"。
3. 覆盖率只加**增量**阈值，只对核心目录加绝对阈值。
4. 报告落库，画出用例数 / 耗时 / 失败率三条趋势线。
5. pre-commit 只做 lint-staged 增量检查。
6. E2E 接发布前门禁，配 trace 与隔离机制。
7. 建立 flaky 治理流程（量化 → 隔离 → 修根因 → 验证）。
8. 每季度回顾：删掉没人信的用例，补上 P0 缺口。
