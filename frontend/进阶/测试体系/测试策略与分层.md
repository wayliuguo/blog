# 测试策略与分层

写测试之前先要回答一个问题：这套测试买的是什么。如果答案是"覆盖率达标"，那大概率会写出一堆跑得飞快、改一行代码就要改三处、却从来没抓到过 bug 的用例。测试真正买到的是三样东西：**防回归**（改坏了能立刻知道）、**设计压力**（不好测的代码往往写得也不好）、**可执行文档**（新人看用例就知道边界在哪）。本篇先把"测什么、分几层、怎么判断好坏"定下来，后面四篇才是具体怎么写。

## 一、测试不是越多越好，而是越准越好

一个团队的测试资产是有限的：写用例的时间、跑用例的时间、用例失败后排查的时间，都要算进去。所以判断要不要写某个测试，用三个问题筛一遍：

1. **它挂了我会不会立刻去修？** 如果答案是"哦，这条又红了，重跑一下"，那这条测试已经在收"信任税"了 —— 它每红一次，团队对整套测试的信任就少一分，真 bug 混在里面时也没人当回事。
2. **它能不能定位到具体位置？** 一条断言 `expect(result).toBeTruthy()` 挂了，你得从头读一遍代码；而 `expect(calcPay(81, true)).toBe(81)` 挂了，报错直接告诉你"期望 81，实际 65"。
3. **重构实现时它要不要跟着改？** 要改，说明它测的是实现；不用改，说明它测的是行为。后者才有长期的防回归价值。

业界常说的"缺陷成本放大规律"（需求阶段 1、编码阶段 10、上线后 100）没有统一的精确口径，但方向是稳定的：发现得越晚，修复链路越长。测试的全部价值，就是把发现时机往前推。

## 二、分层：每一层解决不同的问题

前端的测试通常分成四层，加上静态检查一共五层。分层不是为了凑数量，而是因为**每层的"反馈速度 / 定位精度 / 维护成本"组合不同**：

| 层 | 测什么 | 不测什么 | 典型工具 | 单次耗时量级 | 谁来写 |
| --- | --- | --- | --- | --- | --- |
| 静态检查 | 类型、语法、规范、依赖风险 | 运行时行为 | TypeScript / ESLint / Prettier | 秒级（增量更快） | 所有人 |
| 单元测试 | 纯函数、类、状态机、数据变换 | DOM、网络、跨模块链路 | Vitest / Jest | 毫秒级 | 写这段代码的人 |
| 组件（集成）测试 | 组件的 props / 事件 / 条件渲染 / 异步中间态 | 真实浏览器差异、全流程 | Vitest + RTL / Vue Test Utils | 十到百毫秒 | 写这个组件的人 |
| E2E | 关键用户路径、跨页跳转、真实网络与存储 | 分支细节、边界值 | Playwright / Cypress | 秒到分钟 | 谁改了这条路径 |
| 手工探索 | 新功能的第一轮、视觉与交互体感 | —— | 人 | —— | 所有人 |

静态检查常被忽略，但它是最便宜的一层：类型错误、未使用变量、明显的空值风险，全部在写代码时就标出来了，不需要任何人维护用例。

**金字塔还是奖杯？** 经典金字塔是"单测最多、E2E 最少"。前端更贴近"测试奖杯"（Testing Trophy）：中间那层**集成/组件测试最厚**。理由是前端的绝大部分逻辑都长在组件里 —— 单独测一个纯函数往往测不到真正的风险点（状态没更新、事件没绑上、条件渲染写反），而这些恰好是组件测试的强项；同时它又比 E2E 快一个数量级。

具体比例没有标准答案，可以按这几条来定：

- **改动频率高的模块，测试密度要高。** 半年没人碰的历史代码，补测试收益很低。
- **出错代价高的路径，必须进 E2E。** 登录、下单、支付这类路径，线上出一次事故的代价远大于维护成本。
- **优先补中间层。** 从零开始时，先把组件测试铺开，性价比通常最高。

## 三、测什么：给测试点分级，而不是给代码分级

"覆盖率 80%"是个容易被玩坏的指标 —— 把工具函数写满用例、核心流程一条不测，照样能到 80%。可行的做法是先给**测试点**分级：

| 级别 | 定义 | 例子（购物车结算） | 要求 |
| --- | --- | --- | --- |
| P0 | 主流程 + 钱/权限相关的分支，挂了就是事故 | 下单成功扣款、优惠券互斥、未登录拦截 | 必有自动化用例，进 CI 门禁 |
| P1 | 影响体验但不致命的分支 | 库存不足提示、地址为空的兜底 | 建议有，至少组件测试覆盖 |
| P2 | 边缘场景与兼容细节 | 超长商品名截断、极端折扣组合 | 有空再补，允许手工验证 |

分级的好处是**资源永远往 P0 倾斜**，也让"这个要不要写测试"从争论变成查表。

同样重要的是"不测清单"：

- **不测第三方库和框架本身。** React 的 `useState` 对不对，不是你的测试该操心的。
- **不测样式像素和动画细节。** 这类断言维护成本极高、收益极低，视觉回归交给截图对比（见第 4 篇）。
- **不测实现细节。** 这是最容易踩的一条，下面用实验说明。
- **不穷举环境组合。** 3 个浏览器 × 5 个版本 × 2 个主题 = 30 套，交给 E2E 里的关键路径 + 兼容性矩阵抽样。

## 四、把断言钉在行为上，而不是实现上

同一个"结算金额计算"，两种写法都能让它变成绿色，但重构时的表现天差地别。先看被被测代码：

> 摘自 `./code/test-lab/src/strategy/discount.js`

```js
export const VIP = { normal: 1, gold: 2, platinum: 3 }

export function discountRate(level, amount) {
    if (level === VIP.platinum) return 0.8
    if (level === VIP.gold && amount >= 200) return 0.85
    if (level === VIP.gold) return 0.9
    return 1
}
```

> 摘自 `./code/test-lab/src/strategy/price.js`

```js
export function calcTotal(items, level = VIP.normal) {
    const amount = items.reduce((sum, it) => sum + it.price * it.count, 0)
    const rate = discountRate(level, amount)
    return Math.round(amount * rate * 100) / 100
}
```

### 反模式一：mock 掉内部依赖，断言调用参数

> 摘自 `./code/test-lab/src/strategy/price-impl.test.js`

```js
vi.mock('./discount.js', async () => {
    const actual = await vi.importActual('./discount.js')
    return {
        ...actual,
        discountRate: vi.fn(actual.discountRate)
    }
})
```

> 摘自 `./code/test-lab/src/strategy/price-impl.test.js`

```js
it('断言 discountRate 被调用且参数正确', () => {
    const total = calcTotal([{ price: 100, count: 3 }], VIP.gold)

    expect(discountRate).toHaveBeenCalledTimes(1)
    expect(discountRate).toHaveBeenCalledWith(VIP.gold, 300)
    expect(total).toBe(255)
})
```

这套断言把"内部必须先算总额、再调 `discountRate`"这两步钉死了。哪天有人把折扣改成查表、或把两个函数合并，功能完全没变，用例却红了。更糟的是它给了一种虚假的安全感 —— 断言"调用过"不等于"算对了"。

### 反模式二：重言式断言

> 摘自 `./code/test-lab/src/strategy/price-impl.test.js`

```js
it('用同样的算法算一遍期望值', () => {
    const items = [{ price: 100, count: 3 }]
    const expected = items.reduce((s, it) => s + it.price * it.count, 0) * 0.85

    // 期望值与被测代码用的是同一套算法 —— 实现写错了，这里也跟着错
    expect(calcTotal(items, VIP.gold)).toBe(expected)
})
```

期望值是用同一套算法算出来的：实现里把 0.85 写成 0.8，期望值也跟着变成 0.8，用例依然绿。覆盖率 100%，什么都不保障。

### 正模式：表驱动 + 只描述输入输出

> 摘自 `./code/test-lab/src/strategy/price-behavior.test.js`

```js
const cases = [
    { name: '普通用户无折扣', level: VIP.normal, items: [{ price: 100, count: 1 }], expect: 100 },
    { name: '黄金会员未满 200 九折', level: VIP.gold, items: [{ price: 100, count: 1 }], expect: 90 },
    { name: '黄金会员满 200 八五折', level: VIP.gold, items: [{ price: 100, count: 3 }], expect: 255 },
    { name: '铂金会员八折', level: VIP.platinum, items: [{ price: 250, count: 1 }], expect: 200 },
    { name: '空购物车为 0', level: VIP.platinum, items: [], expect: 0 }
]

describe('正模式：测行为', () => {
    it.each(cases)('$name', ({ level, items, expect: want }) => {
        expect(calcTotal(items, level)).toBe(want)
    })
})
```

期望值是**手写的常数**，不是算出来的。这样实现改了写法、但结果不变，用例不用动；实现算错了，用例立刻红。

边界单独成例，因为它们才是真正容易出问题、且值得被记住的地方：

> 摘自 `./code/test-lab/src/strategy/price-behavior.test.js`

```js
describe('边界与异常', () => {
    it('金额含小数时按分位四舍五入', () => {
        expect(calcTotal([{ price: 33.33, count: 3 }], VIP.platinum)).toBe(79.99)
    })

    it('数量为 0 的商品不影响总额', () => {
        expect(calcTotal([{ price: 100, count: 0 }], VIP.normal)).toBe(0)
    })
})
```

两种写法跑出来都是绿的，这不是它们的区别所在：

```
> test-lab@1.0.0 test:strategy
> vitest run src/strategy

 ✓ src/strategy/price-impl.test.js (2 tests) 8ms
 ✓ src/strategy/price-behavior.test.js (7 tests) 9ms

 Test Files  2 passed (2)
      Tests  9 passed (9)
```

区别在重构那天才显现：把 `discountRate` 的 if 链换成查表，第一份用例要改，第二份一行不动。**用例不需要跟着实现改，是判断它是否测在行为上的唯一硬标准。**

## 五、代价与治理：什么时候该删测试

测试是资产也是负债。负债体现在三处：

- **维护成本**：实现变了要跟着改。测实现的用例，维护成本是测行为的数倍。
- **速度成本**：套件慢了，人就跑得少；跑得少，反馈就慢。给单测套件定一个速度预算（比如"本地全量 30 秒内"），超了就优化或拆分（见第 5 篇）。
- **信任成本**：flaky 用例每红一次都在消耗团队的信任。治理手段见第 4 篇。

该删的测试有三类：

1. **测实现的** —— 重构一次就红一次，且红了不代表功能坏了。
2. **长期 skip 的** —— `.skip` 超过一个迭代还挂着，说明没人真的需要它。
3. **与产品意图不符的** —— 断言的行为已经被产品推翻，留着只是在误导后人。

## 六、从 0 到 1 的落地顺序

在已有项目上补测试，最忌讳"先定个 80% 覆盖率目标"。可行的顺序是：

1. **先上静态检查**：TypeScript strict + ESLint，一次性消灭一大类低级错误，零维护成本。
2. **盘 P0 路径**：按页面/接口列一份 P0 清单（支付、登录、核心表单）。
3. **P0 补组件测试**：这一层性价比最高，覆盖渲染与交互。
4. **P0 中的跨页路径补 E2E**：只放关键路径，控制在几十条以内。
5. **纯函数补单测**：工具函数、金额计算、状态机，通常是顺手的事。
6. **接 CI 门禁**：先卡"必须全绿"，覆盖率只做**增量**阈值（见第 5 篇）。
7. **治理 flaky**：建立"红了必须当天处理"的规矩，否则门禁会变成摆设。

### 测试范围怎么不遗漏

靠人记清单必然会漏。可行的做法是把页面配置当**单一数据源**，让测试范围从配置派生：新增页面只要加一条配置，就自动进入测试盘点与回归清单。这样"有哪些页面要测"这个问题由代码回答，而不是由文档回答 —— 文档会过期，配置不会。

## 小结

- 测试策略与分层
  - 测试买的三样东西
    - **防回归**：改坏了立刻知道，越早发现修复成本越低
    - **设计压力**：不好测的代码通常写得也不好
    - **可执行文档**：新人看用例就知道边界
    - 判断一条测试是否值得留：挂了你会不会立刻修 / 能否定位 / 重构时是否要改
  - 五层分层与各自职责
    - **静态检查**：类型与规范，最便宜的一层，零维护
    - **单元测试**：纯函数与状态机，毫秒级
    - **组件（集成）测试**：props / 事件 / 条件渲染 / 异步中间态
    - **E2E**：关键用户路径与真实浏览器
    - **手工探索**：新功能第一轮与视觉体感
  - 金字塔 vs 奖杯
    - **前端更贴近奖杯**：中间层最厚，因为逻辑长在组件里
    - 比例按"反馈速度 × 定位精度 × 维护成本"定，不按教条
  - 测什么：测试点分级
    - **P0**：主流程与钱/权限分支，进 CI 门禁
    - **P1**：影响体验的分支，建议覆盖
    - **P2**：边缘场景，允许手工
    - **不测清单**：第三方库、样式像素、实现细节、环境穷举
  - 把断言钉在行为上
    - **反模式一**：mock 内部依赖、断言调用参数 —— 重构即红
    - **反模式二**：重言式断言 —— 期望值用同一套算法算出来
    - **正模式**：表驱动 + 手写常数期望 + 边界单独成例
    - 硬标准：实现换了写法，用例一行不改
  - 代价与治理
    - 维护成本、速度成本、信任成本（flaky）
    - 该删的三类：测实现的、长期 skip 的、与产品意图不符的
  - 落地顺序
    - 静态检查 → 盘 P0 → 组件测试 → E2E 关键路径 → 单测 → CI 门禁 → 治理 flaky
    - **测试范围由页面配置派生**，避免人工清单遗漏
