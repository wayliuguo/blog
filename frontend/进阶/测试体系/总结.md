## 1. 测试工具上手

### 1.1 Vitest 是什么，为什么选它

Vite / ESM 技术栈选 Vitest——复用 Vite 转译（TS / JSX / CSS Modules 零配置）、watch 快、与 Vite 共用配置、原生 ESM。本篇是模块入口：先带人零基础上手跑起来，再补齐写测试必备的体系化知识（配置、断言、Mock、过滤、覆盖率），后面的篇章不再重复这些，直接讲「测什么、怎么把测试写深」。

### 1.2 从 0 跑通第一个用例

三步：装 `npm i -D vitest` → 写首个 `*.test.*` → 跑（`vitest` watch 本地用，`vitest run` 一次性、CI 用）。零配置文件即可跑。

### 1.3 配置最小集

只关心三件事：`environment`（按文件切换优于全局）、`globals`（保持关闭，来源清晰、避免与页面全局变量混淆）、`include`（用 `!` 排除目录）。配置写在 `vite.config` 的 `test` 字段或独立 `vitest.config.js`。

### 1.4 测试文件约定

命名 `*.test.*` / `*.spec.*`；与源码同级或 `__tests__`；一个文件由 `describe` / `it` / `expect` 组成；基本钩子 `beforeEach` 等（生命周期详见第三章）。

### 1.5 断言：常用集与怎么选

高频 20%：`toBe` / `toEqual` / `toStrictEqual` / `toThrow` / `toContain` / `toMatchObject`。原则：写具体值而非类型，失败信息即调试线索；一条输入要断言多处时用 `expect.soft`（软断言，收集全部失败而非遇到第一个就停）。

### 1.6 Mock 入门：vi.fn / spyOn / vi.mock

`vi.fn` 造一个可调用的替身（记录调用、可指定返回值）；`spyOn` 给真实对象的方法包一层记录；`vi.mock` 替换整个模块依赖图（会被提升到文件顶部执行）。本篇只做入门，替身的分类、提升陷阱与纪律在第三章展开。

### 1.7 只跑你关心的

路径过滤 `vitest run src/hello`、名字过滤 `-t`、文件内 `it.only` / `it.skip` / `it.todo`。`only` / `skip` 是调试与分批的常用手段。

### 1.8 覆盖率开关

`vitest run --coverage`（v8 provider）。覆盖率只表示「代码被执行」，衡量不了「结果被验证」；真正价值是当门禁——不达标则非零退出。阈值与 CI 落地见第六章。

## 2. 测试策略与分层

### 2.1 目的：测试到底买到什么

测试不是「写代码外的负担」，而是买三样东西：

- **防回归**：改坏了立刻知道；发现越晚修复链路越长。
- **设计压力**：不好测的代码通常写得也不好——测试倒逼你拆出干净的接口。
- **可执行文档**：新人看用例就知道边界在哪。

> 三条筛选题：挂了会不会立刻修？改完能否定位？重构时要不要跟着改？都答「是」才值得写。

### 2.2 分层：每一层解决不同的问题

测试按**反馈速度 × 定位精度 × 维护成本**分成五层，各管一段：

| 层 | 成本 | 覆盖内容 |
| ---- | ---- | ---- |
| 静态检查（TS / ESLint） | 最便宜，零维护 | 类型 / 未使用变量 / 潜在 bug |
| 单元测试 | 毫秒级 | 纯函数与状态机 |
| 组件（集成）测试 | 比 E2E 快一个数量级 | props / 事件 / 条件渲染 / 异步中间态 |
| E2E | 秒到分钟级、脆 | 关键用户路径与真实浏览器 |
| 手工探索 | 新功能第一轮 | 视觉体感、浏览器差异 |

单测测不到渲染与集成，E2E 全铺则慢到没人愿意跑——**分层就是因为每层的成本组合不同，单层必然在某处失衡**。前端更贴近「测试奖杯」：逻辑长在组件里，中间层（组件 / 集成）最厚。

### 2.3 测试点分级：给测试点定级

不按代码分级，按 **P0 / P1 / P2 给「测试点」定级**——同一份代码里的不同测试点，投入不同：

| 级别 | 含义 | 投入 |
| ---- | ---- | ---- |
| **P0** | 主流程与钱 / 权限分支 | 进 CI 门禁 |
| **P1** | 影响体验的分支 | 建议覆盖 |
| **P2** | 边缘场景 | 允许手工 |

**不测清单**：第三方库、样式像素、实现细节、环境穷举。

### 2.4 落地顺序：从 0 到 1

测试既是资产也是负债，落地要讲顺序：

1. 先上零维护成本的静态检查建立信心。
2. 盘 P0 清单决定资源投向；组件测试性价比最高，优先铺。
3. E2E 只进关键路径；单测补纯逻辑深水区。
4. 门禁先只卡「必须全绿」，避免一上来卡 80% 覆盖率导致所有合并被拒。

测试范围由**页面配置派生**，避免人工清单遗漏；老项目覆盖率低时只做增量阈值，让数字随改动缓慢上升。

## 3. 单元测试深入

### 3.1 用例组织与生命周期

- 结构：`describe` / `it` + 四种生命周期钩子：`beforeAll` / `beforeEach` / `afterEach` / `afterAll`，钩子包裹着用例的执行，用来准备 / 还原共享上下文。
- 标记：`only`（只管这条）/ `skip`（跳过）/ `todo`（占位）/ **`fails`**（锁已知 bug 与反例）。
- 过滤：命令行按路径，或 `-t` 按名字过滤。

### 3.2 断言：钉在行为上

断言要钉在「行为」，不要钉在「实现」：

- **反模式一**：mock 内部依赖后断言调用参数——重构即红，掩盖真回归。
- **反模式二**：重言式断言——期望值用同一套算法算出来，等于没说。
- **正模式**：**表驱动 + 手写常数期望 + 边界单独成例**。

> 硬标准：实现换了写法，用例一行不改。`toStrictEqual` 连 `undefined` 属性也查；一处要断言多项用 `expect.soft`。

### 3.3 异步：不要等时间，等条件

- 返回 Promise 或 `async`，**不用 `done` 回调**。
- **不用固定 `sleep` 等结果**——快机器白等、慢机器不够，是 flaky 之源。
- 超时可调，但调大只是掩盖问题，不是修复。

### 3.4 时间：假定时器

用假时钟把「等多久」变成「拨多久 / 拨多少」：

```
useFakeTimers() + advanceTimersByTime(n)
    把 setTimeout / setInterval 换成可手动拨动的假时钟
    等 300ms → 拨 300ms；第 299 不触发、第 300 触发的边界可精确断言
setSystemTime
    连 Date 一起冻结，能锁死毫秒级边界（跨天、有效期）
```

- 涉及 await 真实 Promise 时用 `advanceTimersByTimeAsync`（假定时器不会推进真实 Promise 的 await）。
- 用完必须 `useRealTimers`。

### 3.5 测试替身：stub / spy / mock / fake

四类替身的区别在「是否保留真实实现」与「是否记录调用」两个维度：

| 替身 | 行为 | 记录调用 |
| ---- | ---- | ---- |
| **stub** | 给固定答案 | 不记录 |
| **spy** | 真实实现照跑 | 只做记录 |
| **mock** | 行为完全由测试指定 | 记录调用 |
| **fake** | 有内部状态的简化实现 | 能表达时序变化 |

- 需要表达「第一次失败第二次成功」这类时序时用 **fake**，比一串 `mockReturnValueOnce` 清晰。
- `vi.mock` 会被提升到文件顶部执行，替换模块依赖图里的那个模块；运行时动态替换用 `vi.doMock`（需先 `vi.resetModules()`）。

### 3.6 替身的使用纪律

- **只 mock 边界**：网络 / 时间 / 随机 / 全局；自己维护的内部函数不要 mock。
- **必须还原**：`restoreAllMocks` / `unstubAllGlobals` / 配置全局自动还原，否则用例之间会串味。

### 3.7 参数化与数据构造

- `it.each` 一行一条用例，直接来自参数表。
- 用 factory 造数据（如 `makeUser()`），新增字段不用改所有用例。

## 4. 组件测试

### 4.1 测什么：组件契约

组件测试测的是「契约」，不是组件内部：

```
渲染契约   props → 渲染结果
交互契约   用户操作 → 回调与状态
异步契约   请求三态（loading / success / error）
```

**不测**：样式像素、动画时序、内部变量名、第三方组件内部实现。

### 4.2 怎么找：查询策略

查询优先级（等价于「用户怎么找到这个元素」）：

```
Role → LabelText → Placeholder → Text → DisplayValue → AltText → Title → TestId
```

- `getBy*`（必须存在）/ `queryBy*`（应该不存在）/ `findBy*`（最终会出现）。
- 按 role / label 查把断言与实现解耦——按 class / DOM 结构查，改个标签名就红。
- **查不到时 RTL 打印整棵 DOM**，报错即调试线索。

### 4.3 怎么操作：user-event

- **`user-event` 比 `fireEvent` 真实**：模拟完整事件序列（pointer → focus → click），能测出逐字符输入、聚焦丢失。
- `user.type` 逐字符输入；**每次交互都要 await**，它们内部会推进微任务与定时器。

### 4.4 怎么对付异步：中间态

- **deferred 模式**：手动控制 Promise 的兑现时机，`mockReturnValue(deferred.promise)` 让组件停在 pending，稳定断言 loading。
- 失败分支要断言**按钮恢复可用**，否则用户卡死在 loading 上。
- 等条件（`waitFor` / `findBy*`），**不等时间**；不要 `sleep` 固定时间。

### 4.5 什么不测：反模式与边界

```
container.querySelector   按 DOM 结构查，改结构即红
整树快照                   分不清什么是重要的，噪声淹没信号
测内部 state               耦合实现，违反「测契约」
```

- 何时换层：浏览器差异 / 跨页流程 → E2E；视觉 → 截图对比；**E2E 已覆盖的长链路不在组件层重复**。

### 4.6 怎么组织

- 与组件同级放 `.test.jsx`；用例名写成完整句子（`it('点击提交后发送请求并禁用按钮')`）。
- 抽 `renderXxx` helper，但**不抽断言**（用例可读性全靠断言）。
- `globals: false` 时需显式 `afterEach(cleanup)`，否则 DOM 越堆越多。

## 5. E2E 与稳定性

### 5.1 守什么：关键路径

- 只放**关键路径**：登录 / 支付 / 跨页跳转 / 第三方集成——「挂了就是事故」的路径。
- 规模控制在几十条，不是几百条；组件分支、边界值、表单校验组合都不进 E2E。

### 5.2 怎么写：骨架与定位器

- 定位器语义化：`getByRole` / `getByLabel` / `getByText` 优先，CSS 选择器与 XPath 兜底。
- 每用例自带完整前置（`page` 是全新上下文），**不共享登录态**——那是顺序依赖的开始。
- URL 用正则匹配关键部分，避免 query 参数变化带来的脆弱。

### 5.3 怎么等：自动等待不写 sleep

- Playwright 断言是 **web-first** 的，自动重试到超时，吸收「元素还没渲染」的时序。
- **不写 `waitForTimeout`**——慢机器上不够、快机器上白等，是 flaky 头号来源。
- 等条件：URL（`waitForURL`）/ Response（`waitForResponse`）/ 元素可见（`:toBeVisible`）。

### 5.4 怎么控环境：数据与网络拦截

- 每用例**独立数据**（账号 / 订单号带随机后缀）；前置数据用 API 造，不用 UI 跑一遍注册。
- 第三方依赖用 `page.route` 拦截并返回固定响应；**自己系统的接口不拦**（除非测降级），否则 E2E 退化成组件测试。

### 5.5 为什么 flaky：四个可复现根因

| 根因 | 对策 |
| ---- | ---- |
| **sleep 赌时间** | 等条件成立 |
| **用例间共享状态** | beforeEach 重置，用 `--sequence.shuffle` 暴露 |
| **依赖「现在」** | 时间注入 + `setSystemTime` |
| **时区** | 明确业务口径，固定 `TZ` 或用 UTC 方法 |

- 反例要写成确定性的（`it.fails` 锁住），不能自己也是 flaky。
- `retries` 只降噪，不治本。

### 5.6 怎么规模化：并行、分片与报告

- 并行 worker 的前提是**数据独立**（见 5.4）。
- 分片（`--shard`）按稳定顺序（文件名排序）切，失败才保留 trace / 视频 / 截图。
- 用例多了提速：并行 worker + 分片 + 失败才保留 trace。

### 5.7 怎么治理：flaky 治理流程

flaky 治理当成项目做：**量化 Top10 → 隔离出主门禁 → 用 trace 定位 → 修根因 → 重复跑验证 → 立规矩**。连续失败又修不动的用例，设 deadline，到期就删——一条没人信的测试不如没有。

## 6. 测试基建与门禁

本篇分两块：**基建**——让测试「看得见、信得过」（覆盖率能不能代表质量、怎么度量、怎么看趋势）；**门禁**——让「质量不达标就不让合入」变成不靠人自觉的机制。

### 6.1 覆盖率统计的到底是什么

覆盖率分四种口径：

```
语句   每条语句执行过
行     每行执行过
分支   每个分支都走到   ← 最有信息量
函数   每个函数调用过
```

- v8 快、istanbul 分支粒度细，**中途不要换 provider**，否则趋势会断。

### 6.2 覆盖率 100% 也可能是零保障

- 覆盖率衡量「**代码被执行**」，断言质量衡量「**结果被验证**」，两者独立。
- 弱断言（`expect(typeof x).toBe('number')`）能刷出 100% 覆盖；同份代码换强断言（期望 81 实得 65）立刻暴露 bug。
- 反过来，脚本 / 配置 / 一次性代码不该要求覆盖率。

### 6.3 阈值与增量覆盖率

- 不达标 → **非 0 退出码**，这是门禁的技术基础。
- **存量代码用增量覆盖率**，只卡本次改动的行被覆盖，让数字随改动缓慢上升。
- 分层设阈值（核心目录高、通用组件低）；**阈值只升不降**，用 CODEOWNERS 保护配置。

### 6.4 门禁怎么落地

- 一条 `&&` 命令链就是全部机制（前一步失败即终止，流水线红，分支保护阻止合并）。
- pre-commit 只做增量（lint-staged）；全量与 E2E 放 CI / 发布前，否则逼出 `--no-verify`。
- 准入清单：本地 lint → commit-msg → 静态 → 测试 + 覆盖率 → 构建 → E2E → 发布后监控。

### 6.5 CI 加速：让套件保持「值得跑」

按性价比依次做：缓存依赖、并行分片、只跑受影响的部分、减少 worker 启动开销、快慢分层。

- `isolate: false` 复用 worker（**前提是无共享状态**——与「用例必须独立」是同一件事的两面）。
- 快反馈先回来：模拟逐字符输入的慢用例和快用例分开跑。

### 6.6 报告与趋势

- JSON reporter + 汇总脚本：**一份给机器（门禁 / 趋势）、一份给人（最慢用例 / 失败清单）**。
- 长期盯三个指标：**用例总数**（覆盖在扩）、**套件耗时**（超预算就治理）、**单条用例失败率**（找出 flaky Top10）。

### 6.7 落地清单

```
静态检查 → 测试门禁 → 增量阈值 → 趋势 → pre-commit 增量 → E2E → flaky 治理 → 季度回顾
```
