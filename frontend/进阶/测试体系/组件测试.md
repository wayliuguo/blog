# 组件测试

组件是前端逻辑的主要载体，也是最容易出问题的地方：状态没更新、事件没绑上、条件渲染写反、异步中间态没兜住。这些用单元测试测不到（没有 DOM），用 E2E 测又太慢太脆。组件测试就是专门补这一层的：把组件挂到内存 DOM，**模拟用户操作、断言用户看到的结果**。

本篇按「测什么 → 怎么找 → 怎么操作 → 怎么对付异步 → 什么不测 → 怎么组织」展开：先明确组件契约（这一层测的边界），再落到具体写法——查询策略、user-event、异步中间态，最后讲反模式、换层边界与组织方式。所有用例都来自 `code/test-lab`，可实跑。

## 一、测什么：组件契约

一个组件的契约可以概括成：

```
输入 props / 用户交互 / 外部数据
            │
            ▼
        组件
            │
            ▼
输出 渲染结果 / 事件回调 / 副作用（请求、埋点）
```

所以用例基本就三类：

| 类别 | 断言什么 | 例子 |
| --- | --- | --- |
| 渲染契约 | 给定 props，渲染出什么 | `disabled` 为真时按钮不可点 |
| 交互契约 | 用户操作后，回调/状态怎么变 | 点击 +1 后计数变化且 `onChange` 被调用 |
| 异步契约 | 请求进行中/成功/失败三态 | loading 禁用、成功文案、错误提示 |

**不测的**：样式像素、动画时序、组件内部变量名、第三方组件的内部实现。

## 二、怎么找：查询策略

React Testing Library（RTL）的核心主张是：**你怎么找到页面元素，测试就怎么找**。用户看不到 `class="submit-btn"`，也看不到组件内部叫 `isLoading`，他们看到的是"一个写着登录的按钮"。

> 摘自 `./code/test-lab/src/component/Counter.jsx`

```jsx
export function Counter({ initial = 0, onChange }) {
    const [count, setCount] = useState(initial)

    function increment() {
        const next = count + 1
        setCount(next)
        onChange?.(next)
    }

    return (
        <div>
            <p>
                当前计数：<span>{count}</span>
            </p>
            <button onClick={increment}>+1</button>
        </div>
    )
}
```

按角色和文案查，是最贴近用户的方式：

> 摘自 `./code/test-lab/src/component/Counter.test.jsx`

```jsx
it('渲染初始值，点击后加一并回调', async () => {
    const user = userEvent.setup()
    const onChange = vi.fn()

    render(<Counter initial={5} onChange={onChange} />)

    // getByRole + accessible name：最接近"用户怎么找到这个按钮"
    await user.click(screen.getByRole('button', { name: '+1' }))

    expect(screen.getByText('6')).toBeTruthy()
    expect(onChange).toHaveBeenCalledWith(6)
})
```

### 查询优先级

从上往下选，越靠上越接近真实用户，也越不容易因为重构而失效：

| 优先级 | 查询 | 适用场景 |
| --- | --- | --- |
| 1 | `getByRole` | 按钮、输入框、复选框、对话框等所有有语义角色的元素 |
| 2 | `getByLabelText` | 表单控件（靠 `<label for>` 关联） |
| 3 | `getByPlaceholderText` | 没有 label 的输入框 |
| 4 | `getByText` | 文本、标题、提示语 |
| 5 | `getByDisplayValue` | 受控输入的当前值 |
| 6 | `getByAltText` | 图片 |
| 7 | `getByTitle` | 图标按钮这类只有 title 的元素 |
| 8 | `getByTestId` | 兜底：实在没有语义可依时才用 |

`getByTestId` 之所以排在最后，不是因为它不能用，而是因为它**把测试和实现耦合在了一个对用户毫无意义的标识上**。真正需要它的场景是：元素本身没有可访问语义（比如一个纯装饰性的容器），或者需要在复杂的可视化组件里定位某个区块。

### get / query / find 的语义

- `getBy*`：查不到就抛错 —— 断言"它应该存在"。
- `queryBy*`：查不到返回 `null` —— 断言"它应该不存在"。
- `findBy*`：`getBy*` 的异步版，内部轮询等待 —— 断言"它最终会出现"。

选错会有隐蔽后果：用 `getBy*` 断言"元素消失了"必然报错，用 `queryBy*` 断言"元素存在"则拿到 `null` 后报一条毫无信息量的错。

查不到时的报错本身就是很好的调试线索 —— RTL 会把整棵 DOM 树打印出来：

> 摘自 `./code/test-lab/src/component/Counter.test.jsx`

```jsx
it('getBy 查不到会打印整棵 DOM 树', () => {
    render(<Counter />)
    // 故意查一个不存在的按钮，看报错长什么样（用 try 接住，避免用例失败）
    try {
        screen.getByRole('button', { name: '减一' })
    } catch (e) {
        expect(e.message).toContain('Unable to find')
        expect(e.message).toContain('+1') // 报错里会列出页面上真实的按钮
    }
})
```

## 三、怎么操作：user-event

`fireEvent.click(el)` 只派发一个 `click` 事件；真实用户点一下按钮会依次触发 `pointerover` → `pointerdown` → `focus` → `pointerup` → `click`。`user-event` 模拟的就是后者，因此能测出"输入框没聚焦导致输入丢失""按钮被遮挡点不动"这类问题。

> 摘自 `./code/test-lab/src/component/LoginForm.test.jsx`

```jsx
it('输入后提交，成功后展示欢迎语', async () => {
    const user = userEvent.setup()
    const onSubmit = vi.fn().mockResolvedValue(true)

    render(<LoginForm onSubmit={onSubmit} />)
    // getByLabelText：靠 <label for> 关联，正是无障碍用户找到输入框的方式
    await user.type(screen.getByLabelText('用户名'), '阿白')
    await user.type(screen.getByLabelText('密码'), 'secret')
    await user.click(screen.getByRole('button', { name: '登录' }))

    // findBy* = getBy* + waitFor：只要"最终会出现"，中间几帧不管
    expect(await screen.findByText('欢迎回来，阿白')).toBeTruthy()
    expect(onSubmit).toHaveBeenCalledWith({ name: '阿白', pwd: 'secret' })
})
```

三条要点：

1. `userEvent.setup()` 要在**每次交互前**调用（或每个用例开头调用一次），它返回的对象绑定到当前 document。
2. 所有 `user.*` 操作都要 `await` —— 它们内部会推进微任务与定时器。
3. `user.type` 是逐字符输入的，所以受控组件的状态更新会真实发生；`fireEvent.change` 一次性塞值，可能绕过某些中间逻辑。

## 四、怎么对付异步：中间态

组件最常见的 bug 不在"最终结果"，而在**请求过程中的那几百毫秒**：按钮没禁用导致重复提交、loading 没清除、错误提示没出现。要稳定断言中间态，关键是别让 Promise 自己决定什么时候兑现：

> 摘自 `./code/test-lab/src/component/LoginForm.test.jsx`

```jsx
// 手动控制 Promise 的兑现时机：这样"加载中"这个中间态就能被稳定断言，不用碰真实定时器
function deferred() {
    let resolve
    let reject
    const promise = new Promise((res, rej) => {
        resolve = res
        reject = rej
    })
    return { promise, resolve, reject }
}
```

> 摘自 `./code/test-lab/src/component/LoginForm.test.jsx`

```jsx
it('提交期间按钮禁用且文案变为登录中', async () => {
    const user = userEvent.setup()
    const d = deferred()
    const onSubmit = vi.fn().mockReturnValue(d.promise)

    render(<LoginForm onSubmit={onSubmit} />)
    await user.type(screen.getByLabelText('用户名'), '阿白')
    await user.type(screen.getByLabelText('密码'), 'secret')
    await user.click(screen.getByRole('button', { name: '登录' }))

    expect(screen.getByRole('button', { name: '登录中…' }).disabled).toBe(true)

    d.resolve(true)
    expect(await screen.findByText('欢迎回来，阿白')).toBeTruthy()
})
```

这个 `deferred` 模式比"sleep 100ms 再断言"强在三点：不依赖机器快慢、不拖慢套件、中间态被精确锁定。

失败分支同样要测 —— 而且要注意**按钮必须恢复可用**，否则用户卡死在 loading 上：

> 摘自 `./code/test-lab/src/component/LoginForm.test.jsx`

```jsx
it('请求失败时给出错误提示，按钮恢复可用', async () => {
    const user = userEvent.setup()
    const onSubmit = vi.fn().mockRejectedValue(new Error('500'))

    render(<LoginForm onSubmit={onSubmit} />)
    await user.type(screen.getByLabelText('用户名'), '阿白')
    await user.type(screen.getByLabelText('密码'), 'secret')
    await user.click(screen.getByRole('button', { name: '登录' }))

    expect(await screen.findByRole('alert')).toBeTruthy()
    expect(screen.getByRole('alert').textContent).toBe('网络异常，请重试')
    expect(screen.getByRole('button', { name: '登录' }).disabled).toBe(false)
})
```

如果确实要等一个不受控的异步过程，用 `waitFor` 等条件成立，而不是等时间过去：

> 摘自 `./code/test-lab/src/component/LoginForm.test.jsx`

```jsx
await waitFor(() => {
    expect(screen.getByText('欢迎回来，阿白')).toBeTruthy()
})
```

## 五、什么不测：反模式与边界

组件测试里最常见的三类坏味道，下面这个测试文件把它们和正解放在一起对照：

> 摘自 `./code/test-lab/src/component/query-antipattern.test.jsx`

```jsx
describe('反例一：用 DOM 结构当查询条件', () => {
    it('click 后断言第 N 层子节点', async () => {
        const user = userEvent.setup()
        const { container } = render(<Counter initial={1} onChange={vi.fn()} />)

        await user.click(container.querySelector('button'))

        // 断言写成了"p 里的 span"——把 <p> 换成 <div>，功能没坏，测试却红了
        expect(container.querySelector('p > span').textContent).toBe('2')
    })
})

describe('反例二：整棵 DOM 树拍快照', () => {
    it('把渲染结果整个存下来', () => {
        const { container } = render(<Counter />)
        // 任何样式/class 微调都要 npm test -- -u；而且看快照的人并不知道"什么是重要的"
        expect(container.innerHTML).toMatchSnapshot()
    })
})

describe('正例：只断言用户能感知的东西', () => {
    it('同样的场景，写法与实现解耦', async () => {
        const user = userEvent.setup()
        render(<Counter initial={1} onChange={vi.fn()} />)

        await user.click(screen.getByRole('button', { name: '+1' }))

        // 用户看到的是"数字变成了 2"，不关心它躺在哪个标签里
        expect(screen.getByText('2')).toBeTruthy()
    })
})
```

逐个说清楚问题在哪：

- **`container.querySelector`**：查询条件写成了 DOM 结构。改一个标签名、多包一层 div，用例就红 —— 而这两件事对用户毫无影响。
- **整树快照**：快照最大的问题是"读它的人不知道什么是重要的"。改一个 class 就要 `-u` 更新，久了大家闭着眼更新，快照就退化成形式。快照只在一种场景下有价值：**输出确实是契约的一部分**（比如 error code 文案、序列化结果），这时用 `toMatchInlineSnapshot` 更好，因为它就在用例里，review 时能看到。
- **测内部 state**：直接读组件实例的 state 或调用内部方法，等价于把实现细节钉死。一律通过"用户能看到什么"来断言。


三个文件里 `LoginForm.test.jsx` 明显更慢（1.5s vs 0.4s），因为它要挂载真实 DOM 并模拟逐字符输入。这是组件测试的固有成本 —— 也是为什么套件规模上去之后要做并行与分片。

### 何时换层（边界）

组件测试不是万能的，超出下面这些边界就该换层：

| 场景 | 该用什么 |
| --- | --- |
| 真实浏览器差异（Safari 的日期格式、iOS 的输入法） | E2E / 真机 |
| 跨页面流程（登录 → 跳转 → 下单） | E2E |
| 真实后端联调 | 契约测试 / E2E（少量） |
| 视觉与布局 | 视觉回归（截图对比） |
| 性能（渲染耗时、内存） | 性能专项 |

反过来，**E2E 已覆盖的长链路，不要在组件层再走一遍**，会重复且拖慢套件。

## 六、怎么组织

- 一个组件一个测试文件，放在组件同级（`LoginForm.jsx` / `LoginForm.test.jsx`），改组件时顺手就改到用例。
- 每个用例只验证一个行为，用例名写成一句完整的话（"请求失败时给出错误提示，按钮恢复可用"）。
- 重复的挂载逻辑抽成 `renderXxx(overrides)` helper，但**别把断言也抽进去** —— 用例的可读性全靠断言。
- 记得 cleanup：RTL 在 `globals: false` 时不会自动清理，需要显式 `afterEach(cleanup)`，否则 DOM 会越堆越多。
