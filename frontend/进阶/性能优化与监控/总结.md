# 模块总结 · 性能优化与监控

## 知识主线

四篇不是并列的知识点，而是一条有依赖关系的链，每一篇都在回答上一篇留下的问题：

```
01 性能指标与评估（衡量什么：Core Web Vitals / 辅助指标 / 测量原理 / Lab·Field·RUM） ★主轴
        │  先定下"多快才算快"的标尺，后面优化与监控才都有判据
        ▼
02 性能优化实践（怎么优化：加载 / 运行时 / 分割 / 缓存 / 虚拟滚动 / 资源提示）
        │  它在回答上一篇的什么问题：指标测得慢，具体该改哪里、怎么改
        ▼
03 监控平台（怎么持续看见：错误监控 / 性能采集 / 埋点 / 告警）
        │  它在回答上一篇的什么问题：优化上线后，线上到底好不好、有没有出错
        ▼
04 企业级性能与监控工程实践（怎么焊成工程：Agent SDK → 秒桶聚合 → 分位值 → 告警基线）
        │  它在回答上一篇的什么问题：单点能力都有，怎么落成一条能进生产的闭环
```

本模块的主轴是**性能指标**：01 定下"衡量什么、多快算快"的标尺（LCP / INP / CLS 与 TTFB / FCP / TBT 等），02 的每一种优化都以指标为判据，03 把指标与错误持续采回来看线上真实情况，04 把指标聚合成报表与告警做闭环回归。整章就是围绕"指标"这条线，走完"先测量、再优化、后回归"的完整闭环。

## 分篇知识点

### 01-性能指标与评估

- **三大 Core Web Vitals**
  - **LCP（最大内容绘制）**：衡量最大内容元素（大图、标题文本等）渲染完成的时间，代表"页面主要内容是否加载完成"，Good 目标 ≤2.5s
  - **INP（交互到下次绘制）**：衡量整个生命周期内最具代表性的一次交互延迟，Good 目标 ≤200ms，正在取代只反映首次输入的 FID（≤100ms）
  - **CLS（累积布局偏移）**：意外布局偏移总分 = 位移距离 × 影响比例，Good 目标 ≤0.1；用固定宽高、预留空间、`transform` 动画控制
- **辅助指标沿时间轴排布**
  - **TTFB（首字节时间）**：请求发出到收到响应首字节，受 DNS/TLS/服务器处理影响，目标 ≤800ms，是加载体验的起点
  - **FP / FCP（绘制类）**：FP 首次绘制任意像素，FCP 首次绘制有意义内容，FCP 目标 ≤1.8s
  - **TBT（总阻塞时间）**：FCP→TTI 之间长任务（>50ms）超过 50ms 部分之和，目标 ≤200ms
  - **TTI（可交互时间）**：页面可靠响应用户输入的时间点（FCP 完成 + 主线程空闲 + 无长任务阻塞）
  - **SI（速度指数）**：可见内容填充速度，目标 ≤3.4s；整体时间轴为 TTFB → FP → FCP → TTI → LCP → 稳定（CLS）
- **测量原理**
  - **`performance` 只读缓冲区**：浏览器自动写入的高精度时间数据，`getEntriesByType()` 读历史条目、`now()` 取高精度时间戳
  - **`PerformanceObserver` 异步订阅**：`observe({ type: 'largest-contentful-paint' / 'layout-shift' / 'longtask' / 'paint' })` 持续接收新条目，无需轮询
  - **`mark` / `measure` 手动打点**：`mark('start')` → 执行业务逻辑 → `measure('duration', 'start', 'end')` 计算自定义耗时
- **工具三分工**
  - **Lighthouse**：受控环境（Lab）基准审计，可复现可对比，输出评分与优化建议（Opportunities/Diagnostics），不反映真实用户
  - **Chrome Performance 面板**：录制交互过程看火焰图，定位主线程长任务与渲染瓶颈
  - **RUM（Field）**：在真实用户浏览器中采集，反映真实网络与设备，但样本噪声大；综合用法是 RUM 发现问题、Lab 定位根因
- **RAIL 模型**
  - **Response（响应）**：输入响应 <100ms，交互即时反馈
  - **Animation（动画）**：每帧 <16ms（60fps），帧率不掉
  - **Idle（空闲）**：主线程空闲 >50ms，用空闲时间处理非用户请求
  - **Load（加载）**：首屏 <5s 快速呈现；它决定"优先优化哪一项"的优先级
- **采集与上报**
  - **上报时序**：短时指标（FCP/TTFB）load 后上报；长时指标（LCP/CLS/INP）在 `visibilitychange → hidden` 取最终值
  - **上报方式**：`sendBeacon`（页面卸载也能送达）/ `fetch keepalive` 兜底，合并多条为一次批处理请求
  - **采样率与去重**：按 `sessionId + 页面路径 + 设备类型` 维度去重，用 `Math.random() < SAMPLE_RATE` 控制上报量
  - **附带上下文**：上报网络类型（EffectiveConnectionType）、设备、浏览器版本，便于分维度分析

### 02-性能优化实践

- **五步流程与四个层面**
  - **五步流程**：明确指标 → 量化评估 → 定位原因 → 实施优化 → 迭代回归，先量化再动手、优化后持续回归验证
  - **"性能"的五个层面**：减少整体加载时间、使网站尽快可用、平滑与交互性、感知表现（loading/进度条/骨架屏）、性能测定（指标/测试/监控持续优化）
- **加载性能**
  - **懒加载（按需加载）**：滚动 + `getBoundingClientRect` 兼容好、`IntersectionObserver` 性能优；Vue 指令封装为"收集监听 → 进可视区才替换 src"
  - **图片优化**：能用 CSS 样式代替就不用图片、按 `Accept` 头选 WebP/SVG、HTTP/2 后弃雪碧图、Base64 内联需权衡体积
  - **文件上传**：大文件切片上传 + FileReader 配 SparkMD5 生成 HASH 断点续传 + `/upload_merge` 合并接口，切片天然支持失败重传单个分片
- **运行时性能**
  - **长任务拆分**：>50ms 即长任务、阻塞交互；把任务拆成 <50ms 片段并给耗时操作反馈，符合 RAIL 响应与 Idle 原则
  - **页面流畅度**：rAF 配合滚动监听错峰执行高耗时逻辑、Web Worker 把复杂任务移出主线程、动画用 `transform`/`opacity` 走合成器避免重排重绘
  - **内存管理与泄漏**：警惕六类泄漏——全局变量、闭包持有外部引用、定时器未清除、循环引用、DOM 删除未解绑事件、未清理的 DOM 元素引用，及时销毁不再使用的对象
- **虚拟滚动**
  - **固定高度（定位 + `translate3d`）**：`scroll-bar` 用总高度撑出滚动条，`scroll-list` 用 `translate3d` 跟随偏移，只渲染可视区附近元素
  - **上下 padding 占位**：`getPadFront`/`getPadBehind` 撑起完整数据高度，滚动时按方向复用或重建可视区
  - **动态高度**：元素渲染后收集 `id→height` 映射、平均高度撑滚动条，二分查找在高度累计区间中定位下标
- **代码分割与缓存**
  - **代码分割**：路由/组件懒加载（动态 `import`）+ Tree Shaking 删未引用代码 + 第三方库按需引入，减小首屏体积
  - **强缓存**：`Expires`/`Cache-Control`，命中后不发请求直接使用本地副本
  - **协商缓存**：`ETag`/`If-None-Match`、`Last-Modified`/`If-Modified-Since`，需与服务器验证，命中返回 304
  - **CDN 与 gzip**：CDN 多物理位置部署缩短响应时间，gzip 压缩（打包层预生成 `.gz` 或 Nginx 开启）减小资源体积
- **关键路径与资源提示**
  - **关键渲染路径优化**：CSS 放 `<head>` 避免 FOUC、JS 放底部或 `async`/`defer` 不阻塞 DOM 构建、减少回流重绘、为高构图预留空间降 CLS
  - **`preload`**：提前加载本页即将使用的关键资源（字体/图片/脚本）
  - **`prefetch`**：提前获取后续导航可能需要的资源，低优先级、闲时加载
  - **`preconnect` / `dns-prefetch`**：提前建立跨域连接 / 提前解析 DNS，缩短跨域请求耗时

### 03-监控平台

- **监控三大目标**
  - **稳定性**：监控 JS 错误、资源异常（script/link 加载失败）、接口错误（ajax/fetch 异常）、白屏四类异常，及时定位并解决
  - **用户体验**：监控 TTFB/FP/FCP/FMP/FID/卡顿（>50ms 长任务）等加载与响应指标，识别性能瓶颈
  - **业务**：监控 PV（页面浏览量）、UV（去重后的独立访客数）、页面停留时长，从业务视角看流量与用户行为
- **七步闭环流程**
  - **目标设定与数据采集**：先确定监控指标与目标（加载时间/错误率/用户行为），再用合适技术或自封装函数采集数据
  - **数据传输与存储处理**：经 HTTP 请求、WebSocket 等方式传到后端，用数据库/日志/分析平台存储处理供后续分析
  - **分析与可视化**：转成可视化报表、图表或仪表盘，帮助开发与运营了解系统性能和用户行为
  - **告警预警与定位优化**：数据超限触发告警通知相关人员，结合监控数据与告警信息定位根因、改进优化
- **错误收集方式**
  - **`try/catch` 手动捕获**：业务代码主动包裹可能出错的逻辑，错误信息最全、可控性强，但侵入业务且易遗漏未包裹的错误
  - **`window.onerror`**：捕获未被 `try/catch` 包裹的运行时错误（脚本执行错误）
  - **`unhandledrejection`**：Promise 被 reject 而未处理时兜底捕获，`e.reason` 是被拒绝的原因
  - **资源加载 `error`（捕获阶段）**：`addEventListener('error', fn, true)`——资源错误不冒泡，需在捕获阶段统一拦截
  - **框架专项机制**：Vue `config.errorHandler` / `errorCaptured`，组件渲染、生命周期或事件处理出错时统一上报
- **上报方式**
  - **手动上报**：业务 catch 分支显式调用上报函数，可控、可自定义数据，但对业务代码侵入性强
  - **自动上报**：监听浏览器内置事件（如 `window.onerror`）自动采集，无需侵入业务
  - **1×1 gif 图片打点**：数据拼到图片请求 URL，防跨域、不带 Cookie、不阻塞页面加载，gif 体积最小最轻量
- **性能指标采集**
  - **网络层面**：`getEntriesByType('navigation')[0]` 的时间戳差值算 DNS、TCP、SSL、TTFB、传输耗时
  - **页面展示层面**：`PerformanceObserver` 监听 `paint`/`layout-shift` 拿 FP/FCP/CLS，监听 `longtask` 统计卡顿次数与总阻塞时间
- **埋点与告警**
  - **埋点字段**：用户标识 + 环境信息（OS/浏览器/userAgent）+ 页面地址 + 行为信息（事件类型/元素/时间戳/参数）统一采集
  - **报表产出**：事件委托/全局监听统一采集，按业务维度输出 PV、UV、停留时长、转化漏斗等报表
  - **分级告警**：按严重程度（致命/严重/一般）配置不同通知渠道与响应时效
  - **阈值合理**：结合历史基线动态设置，避免阈值过严频繁误报、过松遗漏问题
  - **去重与抑制**：同一问题聚合、去重、时间窗口抑制，避免短时间内重复轰炸
  - **溯源到人**：告警关联负责模块/团队，附带指标、URL、堆栈、用户信息加速定位

### 04-企业级性能与监控工程实践

- **工程闭环四段**
  - **前端 Agent**：负责采集/传输/治理，埋点 SDK 做采样与脱敏
  - **传输层**：`sendBeacon` / `fetch keepalive`，轻量不阻塞、页面卸载也能送达
  - **接收端聚合**：秒桶聚合 + 分位值 + 去重 + 阈值/基线，把离散上报变成可决策指标
  - **决策端**：报表 / 告警 / 趋势，超阈触发通知、可溯源到人
- **Agent 做成可复用 SDK**
  - **采集层**：定义"报什么"——性能指标（FP/FCP/LCP/TTFB）、接口延迟（包裹 fetch/XHR 读 latency 与 ok）、错误（onerror + unhandledrejection + 框架专项）、行为（事件委托采点击/曝光）
  - **传输层**：优先 `sendBeacon`、兜底 `fetch keepalive`；长时指标（LCP/CLS/INP）在 `visibilitychange → hidden` 上报取最终值
  - **治理层**：采样（`Math.random() < SAMPLE_RATE`，热门页 5%–10%）、脱敏（URL query 密钥、token、userAgent 截断）、频控（按 message+文件+行号聚合，同一错误一段时间只报一次）
- **秒桶聚合**
  - **聚合字段**：按 1 秒一个桶累加 `count / totalLatency / errCount / fpSum / lcpSum`，每来一条上报就更新对应桶
  - **延迟样本**：该秒延迟样本存入 `p95List`，供后续算分位值
  - **价值**：把海量离散上报变成可决策的指标
- **分位值才是体感**
  - **为什么不用 avg**：平均延迟被少数慢请求拉偏，P95/P99 代表"绝大多数用户"的体验，是告警更该关注的判定量
  - **两级聚合**：demo 对每秒钟样本算 P95，再对最近 60 秒做二次聚合
- **告警"准"的三要素**
  - **阈值**：demo 基线 P95 >120ms、错误率 >1% 触发告警
  - **去重**：同一秒同指标准确去重，避免告警轰炸
  - **动态基线**：基于历史数据算动态基线，比固定阈值更抗业务起伏
- **决策端与闭环回归**
  - **监控报表台**：`monitor.html` 每 2s 轮询 `/api/report`——KPI 卡超阈标红、avg/P95 曲线叠加阈值线、告警流含时间/指标/值/阈值可溯源复现
  - **闭环回归**：优化（拆长任务、缩 LCP、补 key 消 CLS）后看曲线是否下降，不以"感觉快了"为止，而以"指标回归到阈值内"为准
