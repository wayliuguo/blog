## 1. 富文本与编辑器架构

### 1.1 编辑的三条路线

做富文本编辑器有三条路线，按可控性与工作量递增：

| 路线 | 形态 | 评价 |
| ---- | ---- | ---- |
| 裸 `contentEditable` | 直接开浏览器编辑 | 产物脏、产物不可控 |
| 受控 `contentEditable` | 自己管数据、浏览器只管输入 | **主流**（ProseMirror / Slate） |
| 完全自绘 | 光标、选区、渲染全自己算 | 可控但工作量最大 |

完全自绘只在有强定制排版需求（在线设计工具、代码块编辑）时才值，工作量最大；做普通富文本应走受控 `contentEditable` + 现成内核。

### 1.2 contentEditable 三个陷阱

为什么不能直接裸用 `contentEditable`？三个陷阱：

```
产物不可控    浏览器往里面塞什么 DOM 完全自己决定（同源操作也可能产生 <span style> 嵌套）
行为不一致    跨浏览器对同一操作的产物各不相同
与框架冲突    框架每次重渲染把 DOM 覆盖回去 → 「打字光标跳到开头」
```

- 第一条它是"脏"源头；第二条让你无法保证所有浏览器出来同样结构；第三条让"编辑 + 框架数据流"直接打架。

### 1.3 选区与光标：位置映射

别人的编辑进来后，光标/选区怎么保持正确？做**位置映射（transform）**：

```
插入    按左右分治：插入点在光标左侧 → 光标右移
                     正好插在光标处 → 光标停在原字符前
删除    按三段：左不动 / 右左移 / 区间内拉回起点
```

- 删除最容易写错的是第三支：光标落在被删区间内要**拉回区间起点**，否则位置会指向一个已经不存在的字符。
- **选区归一化**还要处理反向拖选（从右往左拖）：必须把 anchor/head **整体交换**，而不是只换 offset，并保留 `forward=false` 供方向键使用；越界索引裁剪到合法范围而非抛错。

### 1.4 操作历史合并

逐字符输入会产生海量 op，撤销一次只退一个字符，所以历史要合并：

```
逐字符输入 5 次 → 操作历史只剩 1 条 op
三条合并约束  同类型 / 位置相接 / 同客户端
```

- 跨客户端与不相接位置**不合并**——跨客户端合并会让撤销变成撤销别人的编辑。

### 1.5 躲不掉的三件事与 schema

无论哪条路线，这三件是绕不开的：

```
输入法隔离    compositionstart / compositionend 处理，否则吞字
粘贴白名单   粘贴内容要清洗，只留允许的标签与属性
大文档分块   大文档要分块渲染，避免一次渲染阻塞

schema 必须有   否则只能无限追赶浏览器的脏 DOM
```

- **schema 不是可选优化，而是能不能长期维护的分界线**：没有 schema，你就只能无限追赶浏览器产生的脏 DOM。

## 2. 协同编辑

### 2.1 问题根源：位置失效

多人同时编辑，操作记录的是**位置**，而位置会因为他人编辑失效：

```
操作记录位置 → 位置因他人编辑失效 → 朴素覆盖丢字
```

- 这是协同编辑一切方案的出发点：如何让"位置"在并发下仍然有意义。

### 2.2 OT：变换位置

OT（Operational Transform）选择**变换位置**：把后来的操作按已有操作做一次坐标变换，使到达顺序无关。

```
位置映射：对已有 op 做 transform，让新 op 应用到别人改过的状态也正确
裁定规则必须全局一致：同位置并发插入 A/B，clientId 小的在前
实测：同位置并发插入 A/B，两条到达路径都收敛为 "abxce"
```

- **OT 代价**：变换矩阵随操作类型**平方增长**、需要中心服务定序、正确性难证明。

### 2.3 CRDT：取消位置

CRDT 选择**取消位置**——每个字符带 `left-origin` 引用，靠结构本身保证顺序无关，不需要中心定序。

```
每个字符带 left-origin 引用，互相挂接成链
排序靠 left-origin + clientId
实测：同一位置并发插入，两种到达顺序都为 "bx"
```

- **对比**：OT 要中心服务定序 + 变换矩阵；CRDT 靠结构自身保证顺序无关，代价是元数据更大、文档只增不减。

### 2.4 删除墓碑

CRDT 里删除用**墓碑**而不是真删：

```
真删    并发插入找不到左邻居 → 位置信息丢失 → 发散
墓碑    保留位置锚点，文档只增不减

实测（删 b 与「在 b 后插入 x」并发）
  墓碑版    两种顺序都为 "ax"
  真删版    发散为 "xa" / "ax"
            (并发插入的 findIndex 返回 -1，被塞到文档开头)
```

- 墓碑必须**定期压缩**（服务端合并历史、清理已确认的墓碑），否则长生命周期文档无限膨胀。

### 2.5 收敛性验证

协同算法正确性靠"收敛"验证：任意到达顺序，最终状态一致。

```
实测：3 客户端并发、6 种到达顺序结果唯一，才敢说收敛
验证要穷举而非随机——随机漏掉某条路径可能掩盖发散
```

### 2.6 工程现实：Yjs

- **优先 Yjs**：它是久经验证的 CRDT 实现，自带 awareness、撤销管理、网络层；自研 OT 的正确性成本极高。
- **撤销只撤自己的**：撤销栈记录自己的操作区间，重放前把区间做一次位置映射（文档已被他人改动），直接把旧区间拿来删会删掉别人的字。
- **awareness 不进文档**：光标的在线状态是瞬时的，不属于文档数据。
- **算法不解决语义冲突**：结构层面能收敛，但"两个人同时把标题改成不同主题"这种语义冲突仍要业务层处理。

## 3. 复杂表单引擎

### 3.1 schema 驱动

把「表单是什么」与「怎么渲染」分开：

```
表单是什么          schema + 值 + 规则（纯数据，可单测）
怎么渲染            表单引擎/组件（只消费上面的数据）
```

- schema 驱动让"表单定义"是**纯数据、可单测**，这是复杂表单可维护的前提。

### 3.2 依赖求值与成环

表单里有派生字段，求值顺序怎么保证？

```
显式声明 deps → 求值前拓扑排序
三态访问标记检测成环：未访问 / 访问中 / 已完成

实测：qty 3→10 时 amount 60→200、discount 0→10、payable 60→190
       把 payable 改成依赖自己 → evaluate 立刻抛「字段依赖成环」
```

- **成环必须在求值前抛错**，等到算出 `undefined` 再排查，成本是几十倍。
- 为什么两态标记不够？两态区分不了「已经算完」和「正在算」，后者正是成环信号；三态里的「访问中」就是环检测的依据。

### 3.3 联动传播与互清

改一个字段级联更新其他字段，两条规则：

```
只有值真的变了才往下传    目标已为空时不传播
传播必须有深度上限         兜底赋值型联动的无限打转
```

```
实测：改 province 级联清空 city/district（2 次传播）
      目标已为空时不传播（0 次）
```

- **互清不会死循环**：province↔city 互清时靠「值不再变化」自然收敛，代价是把 `province` 反向抹成空——这是**配置错误而非性能问题**。
- 真正会无限打转的是**赋值型**联动（每次写入的都是新值，如时间戳/自增序号），只能靠深度上限兜底（实测第 6 层被拦下并抛出成环错误）。
- 线上表现为「选了省份它自己变空」，先查联动配置里有没有**反向边**，而不是去查渲染——它不会崩溃，只会安静地写错数据。

### 3.4 异步校验竞态

异步校验做了防抖为什么还出错提示？

```
防抖管请求量，序号管结果归属
只做防抖：先发请求仍可能后到，用旧结果覆盖新输入

实测：连发 a/ab/abc，模拟返回顺序 ab→a→abc
      只有 abc 的结果被采纳（resp.seq === seq），前两次判为过期丢弃
```

- 同一个 seq 机制也要用在**搜索联想、远程选项加载**上；过期请求最好配合 `AbortController` 直接取消，双保险。

### 3.5 订阅粒度与选型边界

大表单卡顿的根因是**订阅粒度**：

```
100 字段改 1 个
  全量订阅唤醒  100 个订阅者
  按字段订阅唤醒 1 个（100× 差距）
写入相同值时应 0 通知
```

- 这是判断表单库是否够用的**分水岭**。
- **选型边界**：字段少别上引擎；schema 需要持久化 / 迁移 / 出码时才值得自研。

## 4. 状态机与流程编排

### 4.1 状态空间与状态机

复杂交互的状态为什么该用状态机而不是一堆布尔量？

```
n 个布尔量       给出 2ⁿ 种组合，绝大多数非法且没人处理过
状态机          收缩成 n 个显式命名状态，不在表里的转移走不到
```

### 4.2 转移表与非法事件

```
转移表    状态 × 事件 → 目标状态（可枚举、可验证、可重放）
非法事件  返回 rejected 且状态不变（绝不静默）
can()     让 UI 能提前禁用按钮

实测：idle 下 send('onSuccess') 返回 rejected 且状态不变
```

三个必备语义：**非法事件返回 `rejected` 绝不静默**、守卫拦下返回 `blocked`、**进入新状态前清掉上一个状态的定时器**。

### 4.3 守卫与幽灵定时器

- **守卫**：区分「没有这条边」（`rejected`）与「有边但被条件拦下」（`blocked`）。
- **幽灵定时器**：`onCancel` 后定时器必须被清（`pending=false`），到点也不再转移；**超时目标必须跟着状态走**而非写死在边上，否则超时永远触发不了。

```
实测：onCancel 后定时器被清，到点也不再转移
```

### 4.4 DAG 编排与补偿逆序

流程里的多步任务编排（有依赖、有重试、有回滚）：

```
能并行就并行    5 节点分层只需 4 轮（串行要 5 步）
失败可重试      pay 失败 2 次后第 3 次成功（attempts=3）
补偿必须逆序    undo:merge → undo:fetchOrder → undo:fetchUser
              补偿本身也要重试与告警
```

- 编排两硬规则：**能并行的按层并行**、**补偿必须按完成顺序的逆序**执行。

### 4.5 事件重放

状态机可重放：把事件序列喂回去，应该得到完全相同的状态。

```
实测：8 个事件里 onRetry 被拒且不入历史，重放 50 次状态恒为 success
用途：崩溃恢复、bug 复现
```

- 重放不一致说明状态机里**混进了隐藏状态**（闭包变量、模块级缓存、时间依赖）——事件重放既能用于恢复与复现，也能暴露这类隐藏状态。

## 5. 最小实现收口

### 5.1 editor-lab 探针实验台

零依赖的探针实验台，`node run.cjs` 依次执行四组探针，`node:assert` 自检全绿：

```
位置映射 / 选区归一化 / 操作合并     （第 1 篇）
OT 变换 / CRDT / 墓碑 / 收敛        （第 2 篇）
依赖求值 / 联动清值 / 异步校验 / 订阅粒度（第 3 篇）
转移表 / 守卫与延迟 / DAG 编排 / 事件重放（第 4 篇）
```

### 5.2 共同底色：隐含状态显式化

四篇的共同底色是同一件事——**把隐含状态显式化**：

```
编辑器的隐含状态是 DOM   → 变成可枚举、可验证、可重放的数据结构
协同的隐含状态是位置      → 用 transform / left-origin 显式建模
表单的隐含状态是组件 state → 用 schema + 依赖关系显式声明
流程的隐含状态是一堆布尔量 → 用状态机表显式命名
```

把它们各自变成**可枚举、可验证、可重放的数据结构**，复杂度才真正可控。
