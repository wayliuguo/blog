# 协同编辑

## 一、问题：朴素覆盖会丢字

假设文档是 `ace`，A 在位置 1 插入 `b`，B 在位置 1 插入 `x`。如果直接按到达顺序覆盖：

- A 先落：`ace → abce`，B 的操作按自己的位置 1 覆盖进来 → `axce`，**A 的 b 没了**。
- B 先落：对称地，**B 的 x 没了**。

问题的根源是：操作记录的是**位置**，而位置会因为别人的编辑而失效。两条路线的分歧就在怎么解决它——OT 选择「变换位置」，CRDT 选择「取消位置」。

## 二、OT：把后到的操作变换到新世界

OT（Operational Transformation）的核心是 `transform(a, b)`：已知 b 已经落地，求 a 在新文档上的等价形式。

> 摘自 `./code/editor-lab/crdt.cjs`

```js
function transformInsert(op, against) {
  // op 是还没落地的操作，against 是已经落地的操作
  let at = op.at
  if (at > against.at) at += against.text.length
  else if (at === against.at && against.client < op.client) at += against.text.length // 同位置：clientId 小的在前
  return { ...op, at }
}
```

> 摘自 `./code/editor-lab/crdt.cjs`

```js
{
  const base = 'ace'
  const A = { type: 'insert', at: 1, text: 'b', client: 'A' }
  const B = { type: 'insert', at: 1, text: 'x', client: 'B' }

  // 路径一：A 先落地
  const p1 = applyInsert(applyInsert(base, A), transformInsert(B, A))
  // 路径二：B 先落地
  const p2 = applyInsert(applyInsert(base, B), transformInsert(A, B))
  assert.equal(p1, p2, '两条路径必须收敛到同一结果')
  assert.equal(p1, 'abxce', '同位置并发插入按 clientId 定序（A 在 B 前）')
  console.log(`[1] OT 变换：同位置并发插入 A/B，两条到达顺序都收敛为 "${p1}"，裁定规则 = clientId 小的在前`)
}
```

关键在 `at === against.at` 这一支：两个人在同一位置插入时，必须有一个**全局一致的裁定**，否则两条路径会算出不同结果（这就是很多自研协同「偶尔不收敛、无法复现」的根因）。裁定规则可以是 clientId、服务端序号，但必须所有人一致。

OT 的代价也随之而来：

- **变换矩阵随操作类型膨胀**：insert/delete/retain/format/移动节点……每加一种操作，就要补齐它与所有已有操作的变换规则（N×N）。
- **必须有中心服务定序**：OT 的变换依赖「谁先落地」，所以需要一个权威顺序（经典做法是服务端给操作编号），离线编辑很别扭。
- **正确性难证明**：收敛性质（TP1/TP2）要逐个操作类型验证，手写实现很容易漏。

## 三、CRDT：取消位置，让字符自带身份

CRDT 换了个思路：字符不按位置插，而是记「**我的左邻居是谁**」。位置因此不再需要变换，到达顺序天然无关。

> 摘自 `./code/editor-lab/crdt.cjs`

```js
let clock = 0
function makeItem(client, ch, afterId) {
  return { id: `${client}:${clock++}`, client, ch, afterId, deleted: false }
}

function insertItem(doc, item) {
  let i = item.afterId === null ? -1 : doc.findIndex(x => x.id === item.afterId)
  let pos = i + 1
  // 与我有同一个左邻居、且 clientId 比我小的并发字符，一律排在我前面（clientId 小的在前，全局一致）
  while (pos < doc.length && doc[pos].afterId === item.afterId && doc[pos].client < item.client) pos++
  doc.splice(pos, 0, item)
  return doc
}
```

实测：同一位置（文档开头）并发插入 A 的 `b` 与 B 的 `x`，两种到达顺序都得到 `bx`——**排序靠 left-origin + clientId，不靠位置**。

删除不能真删。真删会让别人「基于这个字符的插入」失去锚点：

> 摘自 `./code/editor-lab/crdt.cjs`

```js
function deleteItem(doc, id) {
  const it = doc.find(x => x.id === id)
  if (!it) return false
  it.deleted = true
  return true
}
```

实测给出了墓碑版与真删版的直接对比：删 `b` 与「在 `b` 后插入 `x`」并发时，**墓碑版两种顺序都是 `ax`**；而真删版会发散成 `xa` 与 `ax` 两个结果。这就是「协同文档只增不减」说法的来源——墓碑保留位置，代价是文档体积只增不减，需要靠服务端定期压缩（确认所有人已确认后清掉墓碑）。

## 四、收敛性怎么测：穷举到达顺序

协同唯一真正要证明的性质是：**消息乱序不影响最终结果**。测法很朴素——穷举所有到达顺序，比对结果是否唯一。

> 摘自 `./code/editor-lab/crdt.cjs`

```js
function permutations(arr) {
  if (arr.length <= 1) return [arr]
  const out = []
  arr.forEach((x, i) => {
    const rest = [...arr.slice(0, i), ...arr.slice(i + 1)]
    for (const p of permutations(rest)) out.push([x, ...p])
  })
  return out
}
```

> 摘自 `./code/editor-lab/crdt.cjs`

```js
{
  clock = 0
  // 三个人在同一段文字上并发编辑：A/B 插入，C 删除首字符
  const items = [makeItem('A', 'x', null), makeItem('B', 'y', null), makeItem('C', 'z', null)]
  const results = new Set()
  for (const order of permutations([0, 1, 2])) {
    const d = []
    for (const i of order) insertItem(d, { ...items[i] })
    results.add(toText(d))
  }
  assert.equal(results.size, 1, '所有到达顺序必须得到同一结果')
  const final = [...results][0]
  console.log(`[4] 顺序无关：3 个客户端并发插入、全部 ${permutations([0, 1, 2]).length} 种到达顺序，结果唯一："${final}"`)
}
```

实测 3 个客户端并发插入、全部 6 种到达顺序，结果唯一（`xyz`）。这个测试要**用确定性的排列而不是随机重排**——随机测试偶发失败最难查，穷举 + 固定顺序才可复现。

## 五、选型与工程现实

| 维度 | OT | CRDT |
| --- | --- | --- |
| 核心机制 | 变换后到的操作 | 字符自带 id，天然可交换 |
| 中心服务 | 必需（定序 / 编号） | 可选（可 P2P、可离线） |
| 操作类型扩展 | 成本随类型数平方增长 | 相对便宜 |
| 文档体积 | 紧凑 | 有墓碑与元数据开销 |
| 离线编辑 | 别扭 | 天然支持 |
| 成熟实现 | 少量（多自研） | Yjs、Automerge |

工程上最常见的选择是直接用 **Yjs**（CRDT）：它把「文档 = 一组可交换的类型（Y.Text / Y.Array / Y.Map）」做成了库，并配套 `y-websocket`/`y-webrtc` 与 awareness（在线状态）。除非你有强中心化、强审计的特殊要求，自研 OT 的投入产出比通常不划算。

还有三件事和算法无关，但决定协同能不能用：

- **撤销必须是「我的操作的逆」**。协同里按 Ctrl+Z 不能撤销别人的编辑，否则用户会互相破坏。做法是历史栈里只存自己的操作，撤销时把逆操作广播出去；undo 掉的区间如果已被别人改动，要做区间映射（回到第一篇的位置映射）。
- **感知（awareness）**：光标、选区、在线名单属于「不进文档」的临时状态，走独立通道，不能进 CRDT 文档（否则会给每个人都留下墓碑）。
- **权限与冲突的语义层**：算法只保证「不丢字」，不保证「改得对」。真正的业务冲突（两人把同一字段改成不同值）要在业务层给提示或合并策略。

要点：

- 朴素覆盖必丢字：位置会因为别人的编辑失效。
- OT 变换后到的操作，同位置插入要有全局一致的裁定（clientId 或服务端序号）。
- CRDT 取消位置：字符带 id + left-origin，删除用墓碑（真删会发散，实测对比）。
- 收敛性靠穷举到达顺序验证，别用随机测试。
- 撤销只撤销自己的编辑；感知状态不进文档。
