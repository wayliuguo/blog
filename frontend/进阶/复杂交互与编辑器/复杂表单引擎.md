# 复杂表单引擎

表单看起来是最简单的东西：一堆输入框，点提交。但一旦走到「几百个字段、字段之间互相依赖、联动规则几十条、还要异步校验和不卡」这一步，它就会长成项目里最难维护的那一块。这一篇用 `editor-lab` 的 `form.cjs` 把复杂表单的四道坎——**依赖求值、联动传播、异步校验、订阅粒度**——各跑一遍，并给出可落地的结构。

## 一、问题：表单为什么会越做越烂

所有烂掉的表单都倒在同一条路径上：

1. **值散落在组件里**：每个 `Input` 自己 `useState`，提交时再满世界收集。父组件改一个字段要层层传 props。
2. **联动写在 onChange 里**：`onChange={e => { setCity(''); fetchDistrict(...) }}`。规则一多就没法回答「改 A 到底会影响谁」。
3. **校验等到提交才做**：用户填完 200 个字段才发现第 3 个不合法，而且错误提示散落在各组件内部。
4. **任何一次输入都重渲染整个表单**：字段一多就卡，而卡顿又逼着人加 `debounce`，于是出现「输入后 300ms 才出字」这种体验问题。

破局点只有一个：**把「表单是什么」和「表单怎么渲染」分开**。前者是 schema + 值 + 规则（纯数据、可测试），后者是 React/Vue 组件（只负责画）。下面四节逐一拆。

## 二、依赖求值：派生字段必须先定序

表单里总有派生字段：金额 = 单价 × 数量、折扣看金额、应付 = 金额 − 折扣。手写渲染顺序时最容易犯的错是：算 `payable` 的时候 `discount` 还没算出来。

正确做法是**显式声明依赖，在求值前做拓扑排序**：

> 摘自 `./code/editor-lab/form.cjs`

```js
function topo(fields) {
  const mark = {} // 0 未访问 / 1 访问中 / 2 已完成
  const order = []
  const visit = (id, stack) => {
    if (mark[id] === 1) throw new Error(`字段依赖成环：${[...stack, id].join(' -> ')}`)
    if (mark[id] === 2) return
    mark[id] = 1
    for (const dep of fields[id].deps || []) visit(dep, [...stack, id])
    mark[id] = 2
    order.push(id)
  }
  for (const id of Object.keys(fields)) visit(id, [])
  return order
}
```

访问标记用三态而不是两态，是为了区分「已经算完」和「正在算」——后者意味着回到了自己，**成环**。成环必须在求值前抛错，否则你会得到一个 `undefined` 的金额，然后花半天找它从哪来。

> 摘自 `./code/editor-lab/form.cjs`

```js
function evaluate(fields) {
  const values = {}
  for (const id of topo(fields)) {
    const f = fields[id]
    values[id] = f.calc ? f.calc(values) : f.value
  }
  return values
}
```

实测：数量 3、单价 20 时金额 60、未满 100 无折扣、应付 60；数量改成 10 后金额 200、折扣 10、应付 190——**只需要改原始值，派生值自动跟对**。把 `payable` 改成依赖自己，`evaluate` 立刻抛「字段依赖成环」。

## 三、联动：清值、传播收敛，以及互清陷阱

改省份要清空城市，改城市要清空区县。看起来是两行代码的事，但有两个必须处理的细节。

**细节一：只有值真的变了才继续往下传。** 否则每次联动都会把下游全标记为「脏」，触发一堆无意义渲染。

**细节二：传播必须有终止条件。**

> 摘自 `./code/editor-lab/form.cjs`

```js
function applyChange(cascade, values, field, newValue, maxDepth = 5) {
  const next = { ...values }
  next[field] = newValue
  let queue = [field]
  let depth = 0
  let propagations = 0
  while (queue.length) {
    if (++depth > maxDepth) throw new Error(`联动传播超过 ${maxDepth} 层，疑似成环：${queue.join(',')}`)
    const batch = queue
    queue = []
    for (const f of batch) {
      for (const target of cascade[f].onChange || []) {
        const before = next[target]
        next[target] = ''
        if (before === '') continue // 本来就是空的：没真变化，不再往下传播
        propagations++
        queue.push(target)
      }
    }
  }
  return { values: next, propagations }
}
```

实测三种情况：

| 场景 | 传播次数 | 说明 |
| --- | --- | --- |
| province → city → district 正常级联 | 2 | 一次改动清空两级 |
| 目标已是空值 | 0 | 没真变化，一次渲染都不触发 |
| **province ↔ city 互清** | 2，**不会死循环** | 但用户刚选的 province 被反向抹成空 |

最后一行值得单独说：互清配置**不会**栈溢出（「值真变了才传播」这条规则让它自然收敛），它的代价是**用户刚选的值被抹掉**。所以这类错误的表现是「我选了省份，它自己变空了」，而不是崩溃——排查时容易被误判成渲染 bug。真正会无限打转的是「赋值型」联动（每次写入的都是新值，比如时间戳、自增序号），那种只能靠深度上限兜底，实测在第 6 层被拦下并抛出成环错误。

## 四、校验：异步结果必须能丢弃

同步规则（必填、长度、格式）没什么好说的。真正的坑在**异步校验**：用户名是否重复、发票号是否有效，都要问服务端。

用户连打三个字符 `a` → `ab` → `abc`，三个请求发出去，**谁先回来是不确定的**。如果「谁最后回来就用谁」，那么当 `ab` 的请求最后回来时，输入框明明是 `abc`，却显示 `ab` 的校验结果。

解法是给每次请求编号，**只接受最新一次发起的响应**：

> 摘自 `./code/editor-lab/form.cjs`

```js
function createAsyncValidator() {
  let seq = 0
  return {
    send(value) {
      return { seq: ++seq, value }
    },
    // 响应回来时判断：我还是不是最新一次请求
    accept(resp) {
      return resp.seq === seq
    },
    latest: () => seq
  }
}
```

实测：依次发 `a`/`ab`/`abc`，模拟返回顺序为 `ab → a → abc`，最终**只有 `abc` 的结果被采纳**，前两次被判为过期丢弃。

同一套思路也适用于防抖：防抖解决的是「别发那么多请求」，序号解决的是「回来的结果该不该用」——**只做防抖不够**，因为网络抖动下先发的请求完全可能后到。

## 五、性能：订阅粒度决定渲染次数

大表单卡顿的根因几乎总是同一个：任何一个字段变化，都把整个表单重渲染一遍。100 个字段的表单里改 1 个字，唤醒 100 个订阅者——而实际只需要唤醒 1 个。

> 摘自 `./code/editor-lab/form.cjs`

```js
function createStore(values) {
  const all = []
  const byField = {}
  return {
    values,
    subscribeAll(fn) {
      all.push(fn)
    },
    subscribe(k, fn) {
      (byField[k] || (byField[k] = [])).push(fn)
    },
    set(k, v) {
      if (values[k] === v) return { all: 0, field: 0 } // 值没变：谁都别叫醒
      values[k] = v
      all.forEach(fn => fn(k));
      (byField[k] || []).forEach(fn => fn(v))
      return { all: all.length, field: (byField[k] || []).length }
    },
  }
}
```

实测：100 字段表单里改 `f7`，全量订阅唤醒 **100** 个订阅者，按字段订阅只唤醒 **1** 个，相差 100×；写入相同值时两种订阅都是 0 次通知。

这就是 `react-hook-form` 的 `useController`、`Formily` 的响应式字段订阅在做的事。选型的分水岭也在这里：**库是否支持按字段订阅**。不支持的库，几百字段的表单基本必卡。

顺带一提，这套订阅模型与「受控组件」并不冲突：受控解决的是值从哪来，订阅解决的是谁需要被通知。很多团队把两者混为一谈，于是每个输入框都订阅了整个表单。

## 六、选型与工程边界

| 场景 | 推荐做法 | 理由 |
| --- | --- | --- |
| 十几个字段的普通表单 | 原生受控 + 手写校验 | 引入引擎的收益为负 |
| 几十到几百字段、联动多 | schema 驱动引擎（Formily / react-hook-form + zod） | 联动与校验声明化后可测试 |
| 表单即产品（问卷、流程引擎） | 自研 schema + 渲染器 | 需要版本迁移、出码、DSL 等能力 |
| 表单里有大量异步校验 | 引擎 + 请求序号 + 防抖 | 竞态与请求量要同时处理 |

自研之前先确认一件事：**schema 要不要跨版本持久化**。低代码平台里 schema 要存库、要迁移、要出码（见「低代码与搭建体系」模块），这种情况下自研几乎是必然的；只是内部表单，用现成库更划算。
