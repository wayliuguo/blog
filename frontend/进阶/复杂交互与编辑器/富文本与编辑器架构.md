# 富文本与编辑器架构

编辑器是前端里少数几个「自己做不出来，接第三方又接不好」的领域。难点不在渲染，而在三件事：**浏览器给的编辑能力不可控**、**文档变了光标要跟着变**、**历史与协同要求每一次编辑都是可描述的操作**。这一篇用 `editor-lab` 的 `model.cjs` 逐条给出实现与实测。

## 一、三条路线：contentEditable 的三个陷阱

`contentEditable` 让浏览器直接接管编辑，代价是**浏览器写进 DOM 的内容不受你控制**：

1. **产物不可控**：同样的粘贴操作，Chrome 会带 `<span style="...">`、Safari 会带 `<font>`、还会插入 `<b>`/`<i>` 混着用。你拿到的 DOM 是浏览器方言，不是你的数据模型。
2. **行为不一致**：回车是分段还是换行、退格删一个字符还是删一个标签、输入法（IME）组合期间的 DOM 变更，三家浏览器各不相同。
3. **与框架的渲染冲突**：React/Vue 每帧想按自己的虚拟 DOM 更新，浏览器却在你背后改真实 DOM，双方互相覆盖——表现为「打字打着打着光标跳到开头」。

于是工程上有三条路线：

| 路线 | 做法 | 代价 |
| --- | --- | --- |
| 裸用 contentEditable | 直接读 `innerHTML` | 产物脏、行为不一致，只适合极简场景 |
| **受控 contentEditable**（主流） | 让浏览器编辑，但立刻拦截（`beforeinput`）转成自己的操作，再按自己的模型重绘 | 要自己处理 IME、选区恢复 |
| 完全自绘 | 自己画光标、自己处理按键与选区（如 CodeMirror 6、Google Docs） | 工作量最大，但完全可控；输入法的候选框定位是难点 |

ProseMirror、Slate、Lexical、Tiptap 都属于第二条：它们不是「不用 contentEditable」，而是**把它当成输入法前端**，真正的真相是一棵树。

## 二、数据模型：为什么不能直接改字符串

最朴素的想法是「文档就是字符串，改就行了」。问题在于：**别人的编辑进来之后，你的位置全失效了**。协同、撤销重做、甚至一次批量替换，都会让「位置」变成需要映射的东西。

> 摘自 `./code/editor-lab/model.cjs`

```js
function transformPosition(pos, op) {
  if (op.type === 'insert') {
    // 规则：插入点在光标之前（或正好在光标处且光标要留在原字符前）→ 光标右移
    return pos <= op.at ? pos : pos + op.text.length
  }
  // delete：光标在区间左侧不动，右侧左移，区间内被拉到区间起点
  if (pos <= op.at) return pos
  if (pos >= op.at + op.len) return pos - op.len
  return op.at
}
```

> 摘自 `./code/editor-lab/model.cjs`

```js
{
  const doc = 'hello world'
  assert.equal(transformPosition(0, { type: 'insert', at: 0, text: 'x' }), 0, '光标在最左，头部插入不影响它')
  assert.equal(transformPosition(5, { type: 'insert', at: 0, text: 'xy' }), 7, '插入点在光标左侧 → 右移 2')
  assert.equal(transformPosition(5, { type: 'insert', at: 5, text: 'xy' }), 5, '正好插在光标处 → 光标停在原字符前')
  assert.equal(transformPosition(5, { type: 'insert', at: 9, text: 'xy' }), 5, '插入点在光标右侧 → 不动')
  assert.equal(transformPosition(2, { type: 'delete', at: 5, len: 3 }), 2)
  assert.equal(transformPosition(8, { type: 'delete', at: 5, len: 3 }), 5)
  assert.equal(transformPosition(6, { type: 'delete', at: 5, len: 3 }), 5, '光标在被删区间内 → 拉到区间起点')
  console.log('[1] 位置映射：插入按左右分治、删除按三段（左不动 / 右左移 / 区间内拉回起点）')
}
```

删除是三段而不是两段，这点最容易写错：光标落在**被删除区间内部**时，不能按「右侧左移」算（会得到负数或跳到奇怪位置），必须拉回区间起点。

插入那条用了 `pos <= op.at` 而不是 `<`：在光标处插入时，光标应当**停在原字符前面**（用户的心智是「我在这个字前面打字」），而不是被推到新内容之后。

## 三、选区：反向拖选与越界裁剪

用户可以从右往左拖，浏览器给的选区 anchor/head 因此是无序的；而异步更新（协同、批量替换）之后，块索引和 offset 都可能越界。

> 摘自 `./code/editor-lab/model.cjs`

```js
function normalizeSelection(sel, blocks) {
  let { anchorBlock, anchorOffset, headBlock, headOffset } = sel
  anchorBlock = Math.max(0, Math.min(anchorBlock, blocks.length - 1))
  headBlock = Math.max(0, Math.min(headBlock, blocks.length - 1))
  anchorOffset = Math.max(0, Math.min(anchorOffset, blocks[anchorBlock].text.length))
  headOffset = Math.max(0, Math.min(headOffset, blocks[headBlock].text.length))
  let forward = true
  if (anchorBlock > headBlock || (anchorBlock === headBlock && anchorOffset > headOffset)) {
    // 反向拖选：整体交换，而不是只换 offset
    [anchorBlock, headBlock] = [headBlock, anchorBlock];
    [anchorOffset, headOffset] = [headOffset, anchorOffset]
    forward = false
  }
  return { anchorBlock, anchorOffset, headBlock, headOffset, forward }
}
```

实测：反向拖选整体交换并标记 `forward=false`；越界的 offset 与块索引**裁剪到合法范围**而不是抛错。

两个易错点：

- **整体交换**，不是只换 offset。只换 offset 会在跨块选区上得到「起点块 > 终点块」的非法结果，后续所有区间遍历都会算错。
- `forward` 要保留下来。它决定按方向键时光标收在哪一端（Shift+→ 扩展选区的方向），丢了这个标记，反向选区的键盘操作就会反直觉。

## 四、操作与历史：合并规则

如果每个字符都产生一条操作，打一句话就是几十条：撤销要按几十次，协同要传几十条消息。必须合并。

> 摘自 `./code/editor-lab/model.cjs`

```js
function tryMerge(prev, next) {
  if (!prev || !next) return null
  if (prev.type !== 'insert' || next.type !== 'insert') return null
  if (prev.at + prev.text.length !== next.at) return null // 位置必须相接
  if (prev.client !== next.client) return null // 不同人的输入不合并（合并会破坏 OT 的因果）
  return { type: 'insert', at: prev.at, text: prev.text + next.text, client: prev.client }
}
```

> 摘自 `./code/editor-lab/model.cjs`

```js
  // 模拟一次输入：逐字符进来，历史里最终只留 1 条
  let history = []
  for (const ch of ['h', 'e', 'l', 'l', 'o']) {
    const op = { type: 'insert', at: history.length ? history[history.length - 1].at + history[history.length - 1].text.length : 0, text: ch, client: 'A' }
    const merged = tryMerge(history[history.length - 1], op)
    if (merged) history[history.length - 1] = merged
    else history.push(op)
  }
  assert.equal(history.length, 1)
  assert.equal(history[0].text, 'hello')
  console.log('[3] 操作合并：逐字符输入 5 次 → 历史只剩 1 条 op；跨客户端与不相接位置不合并')
```

三条合并约束缺一不可：**同类型**、**位置相接**、**同一客户端**。第三条在有协同时尤其重要——把别人的输入合并进你的历史，会让撤销变成「撤销别人的编辑」，那是协同里最招骂的 bug（撤销的正确语义见下一篇）。

## 五、选型与边界

| 方案 | 数据模型 | 适合 |
| --- | --- | --- |
| ProseMirror | schema 驱动的文档树，位置是数字 + 路径 | 结构严格的富文本（文档、笔记） |
| Slate | 可嵌套的自定义节点树，React 受控 | 需要与业务组件深度混排（卡片、表单块） |
| Lexical | 节点树 + 状态管理，性能优先 | 中轻量编辑器、评论框 |
| CodeMirror 6 | 自绘 + 分块渲染，面向超长文本 | 代码编辑、超大文档 |

共同边界（选哪个都躲不掉）：

- **输入法是最大变量**：组合输入期间 DOM 会被浏览器临时改写，必须靠 `compositionstart/end` 隔离，否则中文输入会吞字或重影。
- **粘贴必须清洗**：把剪贴板 HTML 过一遍白名单（标签 + 属性），否则样式与脚本一起进来。
- **大文档要分块渲染**：一次性渲染几千个块必然卡，按可视区渲染 + 占位高度。
- **不要自己写 schema-less 的编辑器**：没有 schema，你就永远在给「浏览器塞进来的任意 DOM」打补丁。

要点：

- 受控 contentEditable 是主流路线：浏览器负责输入，你负责模型和重绘。
- 文档一变位置就要映射：插入分左右，删除分三段（区间内拉回起点）。
- 选区归一化要整体交换 + 裁剪越界，并保留 `forward` 方向标记。
- 操作要合并（同类型 / 位置相接 / 同客户端），否则历史与网络都会被撑爆。
- schema 必须有：没有 schema，就只能无限追赶浏览器的脏 DOM。
