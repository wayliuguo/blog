# 状态机与流程编排

复杂交互的烂法惊人地一致：一开始只有 `isLoading`，后来加了 `isError`，再后来加了 `isRetrying`、`isSubmitted`、`isEmpty`……很快就有七八个布尔量，而它们的组合数是 2⁷ = 128 种——**其中绝大多数是非法状态**（既在加载又在成功、既出错又在提交）。这一篇用 `editor-lab` 的 `flow.cjs` 说明：把这些布尔量换成一张**状态转移表**之后，哪些 bug 会结构性消失，以及流程编排里的重试与补偿该怎么写。

## 一、问题：布尔标志位为什么必然失控

> 示意片段（无配套脚本）

```js
if (isLoading && !isError && !isSubmitted) { /* ... */ }
```

这种代码的问题不是难读，而是**无法回答「当前到底处于什么状态」**。三个布尔量给出 8 种组合，其中可能只有 3 种合法，剩下的 5 种没人处理过——但它们一定会在某个时序下出现，然后表现为偶发 bug。

状态机换掉的不是写法，是**状态空间**：从 2ⁿ 个组合，变成 n 个显式命名状态，且**不在表里的转移根本走不到**。

## 二、转移表：不该转的时候，转不动

最小实现就是一张「当前状态 + 事件 → 下一个状态」的表：

> 摘自 `./code/editor-lab/flow.cjs`

```js
function createMachine(def) {
  let state = def.initial;
  return {
    get state() {
      return state;
    },
    can: event => Boolean(def.states[state] && def.states[state][event]),
    send(event) {
      const next = def.states[state] && def.states[state][event];
      if (!next) return { changed: false, state, rejected: event };
      state = next;
      return { changed: true, state };
    },
  };
}
```

实测：`idle` 下 `send('onSuccess')` 返回 `{ changed: false, rejected: 'onSuccess' }`，状态纹丝不动；合法路径 `idle → loading → success → idle` 正常。

**关键设计点：非法事件必须返回「被拒绝」这个事实，而不是静默无反应。** 静默是最糟的结果——调用方以为发出去了，状态没变，两边从此各说各话。有了 `rejected`，你可以决定是记日志、抛错，还是忽略；`can(event)` 则让 UI 能提前禁用按钮（这也是状态机在 UI 层的直接收益：按钮可用性不再靠拍脑袋判断）。

## 三、守卫与延迟：条件转移和「幽灵定时器」

真实流程里转移往往要带条件（校验没过不许提交），以及延迟（超时、轮询）。两者各有一个经典 bug。

**守卫（guard）**：条件不满足时转移不该发生，且要能区分「没有这条边」和「有边但被拦下」。

**延迟**：进入某状态后挂一个定时器，用户提前离开了，定时器还活着——它会在一个**已经不是当时那个状态**的上下文里触发转移。这就是「幽灵定时器」，表现为「点了取消之后，页面莫名其妙跳到超时提示」。

> 摘自 `./code/editor-lab/flow.cjs`

```js
    send(event) {
      const edge = def.states[state] && def.states[state][event];
      if (!edge) return { changed: false, rejected: event };
      const e = typeof edge === 'string' ? { target: edge } : edge;
      if (e.guard && !e.guard(ctx)) return { changed: false, blocked: event };
      // 关键：进入新状态前先清掉上一个状态挂的定时器
      if (timer) {
        clearTimeout(timer);
        timer = null;
        timeoutTo = null;
      }
      state = e.target;
      if (e.after) {
        timeoutTo = e.timeoutTo;
        timer = setTimeout(() => {}, e.after); // 真实工程里这里就是 fireTimeout
      }
      return { changed: true, state };
    },
```

实测：`ctx.valid = false` 时 `onSubmit` 被守卫拦下（返回 `blocked`，状态仍是 `editing`）；把 `valid` 改成 `true` 后进入 `loading` 并挂上 3 秒超时；`onCancel` 之后 `pending === false`，**此时即使定时器到点也不会再转移**。反过来，没取消的那一支，超时正常生效转到 `timeout`。

一个容易写错的地方：`timeoutTo` 必须**跟着状态走**，不能写死在某条边上（我第一版就是从一个固定的 `onSubmit` 边上去读目标状态，结果超时永远触发不了——因为那时状态已经是 `loading`，`editing` 上的边查不到）。

## 四、编排：能并行的别串行，失败要有退路

状态机管的是「一个交互的状态」，流程编排管的是「一串有依赖关系的任务」。核心是三件事：**分层并行、失败重试、失败补偿**。

> 摘自 `./code/editor-lab/flow.cjs`

```js
function layers(flow) {
  const done = new Set();
  const out = [];
  while (done.size < Object.keys(flow.nodes).length) {
    const layer = Object.keys(flow.nodes).filter(
      id => !done.has(id) && flow.nodes[id].needs.every(n => done.has(n))
    );
    if (!layer.length) throw new Error('流程存在无法解开的环');
    layer.forEach(id => done.add(id));
    out.push(layer);
  }
  return out;
}
```

按层执行，同一层内的节点没有相互依赖，可以并行。实测一个 5 节点流程（`fetchUser` / `fetchOrder` 无依赖，`merge` 依赖前两者，之后 `pay` → `notify`）：分层只需 **4 轮**，串行要 5 步。节点越多、越「宽」，这个差距越大。

重试与补偿：

> 摘自 `./code/editor-lab/flow.cjs`

```js
      let attempt = 0;
      const maxRetry = (flow.nodes[id].retry || 0) + 1;
      let ok = false;
      while (attempt < maxRetry) {
        attempt++;
        if (!(fail[id] && fail[id] >= attempt)) {
          ok = true;
          break;
        }
      }
```

实测：`pay` 配置 `retry: 2`，前两次失败第三次成功 → `attempts = 3`；三次全失败时，补偿按**已完成节点的逆序**执行 —— `undo:merge → undo:fetchOrder → undo:fetchUser`。

逆序是硬要求：先做的后撤。顺序反了会出现「撤销了订单，但用户的积分已经扣了」这类残留。另外，补偿本身也可能失败，所以它必须有自己的重试与告警，不能假设一定成功。

## 五、事件重放：状态可还原的前提是状态机不藏东西

把事件日志留下来，就能靠重放还原状态——前提是**状态机自己不偷偷保存可变数据**，业务数据放在 `context` 里、由事件驱动变更。

> 摘自 `./code/editor-lab/flow.cjs`

```js
function replay(def, events) {
  const m = createMachine(def);
  const seen = [];
  for (const e of events) {
    const r = m.send(e);
    if (r.changed) seen.push(e); // 被拒绝的事件不进历史
  }
  return { state: m.state, accepted: seen };
}
```

实测：8 个事件里 `onRetry`（在 `success` 状态下无意义）被拒且不入历史，重放 50 次状态恒为 `success`，接受序列完全一致。

这条性质带来两个实用能力：**崩溃恢复**（重新加载后重放日志回到断点）和**可复现的 bug 报告**（用户报 bug 时附上事件序列，本地重放即可复现）。反过来，如果你发现重放得不到同一状态，说明状态机里混进了隐藏状态（闭包变量、模块级缓存、时间依赖）——那正是最难查的那类 bug。

## 六、选型与工程边界

| 场景 | 推荐做法 | 理由 |
| --- | --- | --- |
| 2~3 个状态的简单交互 | `useReducer` + 显式枚举 | 引入状态机库收益为负 |
| 5 个以上状态、有异步和超时 | XState / 自研转移表 | 超时取消、守卫、可视化调试 |
| 多步骤流程（下单、开户） | 状态机 + 事件日志 | 可重放、可恢复、可审计 |
| 任务编排（DAG、批处理） | 分层执行 + 重试 + 补偿 | 并行度与失败退路都要显式设计 |

状态机不是银弹，它的代价是**前期建模成本**：你得先把状态想清楚。但反过来想，如果你说不清有哪些状态，那这本来就是要补的课——状态机只是逼你早一点补。
