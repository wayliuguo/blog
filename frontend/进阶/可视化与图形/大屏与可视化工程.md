# 大屏与可视化工程

> 统一业务场景：实时交易监控大屏（见[全景](./全景.md)）。本篇是板块的实战核心：**`screen-board` 真实工程**（vite + vue3 + echarts，可 `npm run dev` 跑起来）把前几篇的手法全部落进一个项目；`screen-lab` 探针负责量化的部分。

## 一、入门：大屏是三个工程问题

大屏不是「图表多放几个」，它在普通前端技能之外多出三个问题：

| 问题 | 本质 | 本篇落点 |
| --- | --- | --- |
| 分辨率适配 | 4K 拼接墙 / 1080p 投影 / 小显示器要同一份代码 | 等比缩放（第一节） |
| 渲染预算 | 高频数据流 × 有限帧时间 | 时间切片 / 聚合 / 降级（二、三、四节） |
| 7×24 长跑 | 内存泄漏、断线、上下文丢失在长跑里必然出现 | 稳定性清单（第六节） |

实战工程 `code/screen-board/` 对应这四个字：1920×1080 设计稿等比缩放、mock 数据每 2s 推一批、四张图 + 告警列表，`npm run build` 与浏览器实测均通过。

## 二、核心机制：渲染预算

### 2.1 成本模型：重绘 = 重放

大屏卡不卡只看一件事：**每次刷新的实际耗时是否挤进 16.7ms**。Canvas 篇已建立成本模型（显示列表 + 帧合并）：

> 摘自 `./code/viz-lab/render.cjs`

```js
// 迷你「虚拟画布」：只记录绘制指令不真画 —— 用指令数度量渲染成本
class MiniCanvas {
  constructor() {
    this.ops = [] // 显示列表：当前画面由哪些指令构成
    this.clears = 0
    this.executed = 0 // 最近一次重绘真正执行的指令数
  }
  add(op) { this.ops.push(op) return this }
  // 策略 A · 全量重绘：清屏后重放整个显示列表（改 1 根柱子也要付 100 根的代价）
  repaintFull() {
    this.clears++
    this.executed = this.ops.length
  }
  // 策略 B · 增量重绘：只执行受影响的指令（真实实现按脏矩形裁剪）
  repaintIncremental(changed) {
    this.clears++
    this.executed = changed.length
  }
}
```

工程化的增量更新链路是：**数据变更 → 算 diff → 只重算受影响的布局 → 只重放受影响的指令**。ECharts 的增量渲染、自研大屏的脏矩形，都是这条链。

### 2.2 时间切片：别让一次刷新卡死主线程

大屏刷新常伴随批量任务（几十个图表重新布局、表格重渲染）。一次全做就是一根长任务，卡住主线程还吞掉用户输入。做法是把任务按帧预算切片：

> 摘自 `./code/screen-lab/chunk.cjs`

```js
// 时间切片：把任务列表按帧预算切分，单帧放不下的顺延到下一帧
function chunkTasks(costs, budget = 16.7) {
  const frames = []
  let cur = []
  let used = 0
  for (const c of costs) {
    // 当前帧放不下且已有任务 → 收帧开新帧
    if (used + c > budget && cur.length) {
      frames.push(cur)
      cur = []
      used = 0
    }
    cur.push(c)
    used += c
  }
  if (cur.length) frames.push(cur)
  return frames
}
```

实测：10 个 3ms 的任务切成 2 帧执行；单个 20ms 的任务拆不动、独占一帧——**切片的最小粒度是单个任务**，任务本身太大就要先拆任务（`node run.cjs` 场景一）。浏览器侧的对应 API 是 `requestIdleCallback` 与 `scheduler.yield`，React 的并发调度同源。

### 2.3 数据聚合：监控折线的降维

大屏监控折线的原始数据是秒级甚至毫秒级上报，直接画几万个点既费预算又看不出信息。标准做法是**时间桶聚合**：每桶只留 min/max/count——min/max 保住了「尖峰」这个监控最重要的特征：

> 摘自 `./code/screen-lab/aggregate.cjs`

```js
// 滑动窗口聚合：把原始点按时间桶归并，每桶只留 min/max/count（监控折线的降维）
function aggregate(points, bucketMs) {
  const buckets = new Map()
  for (const [t, v] of points) {
    const key = Math.floor(t / bucketMs) * bucketMs
    if (!buckets.has(key)) {
      buckets.set(key, { t: key, min: v, max: v, count: 0 })
    }
    const b = buckets.get(key)
    b.min = Math.min(b.min, v)
    b.max = Math.max(b.max, v)
    b.count++
  }
  return [...buckets.values()].sort((a, b) => a.t - b.t)
}
```

实测：1 万个原始点聚成 17 个分钟桶，每桶只有 min/max/count 三个数（`node run.cjs` 场景三）——**降维 500 倍而监控特征不丢**。聚合放在哪一层做也讲究：能在采集端/Web Worker 里做就别等主线程。

## 三、降级阶梯：从视觉到渲染器逐级加码

数据量超预算时，降级不是一步到位「上 WebGL」，而是**按代价从小到大逐级加码**——先降视觉，再降数据，最后换渲染器：

> 摘自 `./code/screen-lab/chunk.cjs`

```js
// 降级阶梯：视觉 → 数据 → 渲染器逐级加码，取第一个满足帧预算的档位
const LADDER = [
  { level: 'L0 原样', costPerPoint: 0.005 },
  { level: 'L1 去阴影渐变', costPerPoint: 0.0035 },
  { level: 'L2 降采样', costPerPoint: 0.002 },
  { level: 'L3 上 WebGL', costPerPoint: 0.0005 }
]
function pickLevel(count, budget = 16.7) {
  for (const l of LADDER) {
    if (count * l.costPerPoint <= budget) return l.level
  }
  return LADDER[LADDER.length - 1].level // 都超预算就顶格降
}
```

实测（`node run.cjs` 场景二）：

> 摘自 `./code/screen-lab/run.cjs`

```js
// ── 场景二：降级阶梯 ────────────────────────────────────────────
console.log('场景二 · 降级阶梯')
assert.equal(pickLevel(2000), 'L0 原样')      // 10ms < 16.7ms 不降
assert.equal(pickLevel(4000), 'L1 去阴影渐变') // 20ms → 先降视觉
assert.equal(pickLevel(8000), 'L2 降采样')     // 40ms → 再降数据
assert.equal(pickLevel(20000), 'L3 上 WebGL')  // 100ms → 换渲染器
console.log('  ✓ 2k→L0 · 4k→L1 · 8k→L2 · 2w→L3，逐级加码不跳级\n')
```

逐级而不是跳级，是因为**视觉降级用户几乎无感、数据降级用户可感知、换渲染器是工程成本**——能用便宜的手段解决就不动贵的。

## 四、Web Worker 与离屏渲染

把计算挪出主线程的两条路：

> 示意片段（无配套脚本）

```js
// ① Web Worker：布局计算 / 数据聚合 / Socket 解析放进来，主线程只收结果
const worker = new Worker('/workers/layout.worker.js')
worker.postMessage({ type: 'layout', data: rows })
worker.onmessage = (e) => chart.setData(e.data)
```

> 示意片段（无配套脚本）

```js
// ② 离屏渲染（OffscreenCanvas）：连「画」本身都能挪进 Worker
const offscreen = canvas.transferControlToOffscreen()
worker.postMessage({ canvas: offscreen }, [offscreen])
// Worker 里照常 new OffscreenCanvas 的 2d/webgl context 绘制
```

边界要先想清楚：Worker 没有 DOM，图表库要在 Worker 里跑需要其支持（如 ECharts SSR 字符串输出）；`transferControlToOffscreen` 兼容性要按目标环境评估。**多数大屏的卡顿先把主线程的活干干净，轮不到这两条**。

### 5.1 等比缩放（最小实现）

设计稿 1920×1080，运行时算 `scale = min(内宽/1920, 内高/1080)` 等比缩放并居中：

> 摘自 `./code/screen-board/src/utils/useFitScreen.js`

```js
export function useFitScreen(elRef) {
  const fit = () => {
    const sx = window.innerWidth / DESIGN.w
    const sy = window.innerHeight / DESIGN.h
    const s = Math.min(sx, sy)
    // 等比缩放 + 居中。注意 transform-origin 必须用 left top：
    // 若保持默认 center，translate(-50%,-50%) 的位移会被 scale 放大，
    // 视口比例与设计稿不一致时整体会向右下漂移（实测踩坑）。
    elRef.value.style.transformOrigin = 'left top'
    const dx = (window.innerWidth - DESIGN.w * s) / 2
    const dy = (window.innerHeight - DESIGN.h * s) / 2
    elRef.value.style.transform = `translate(${dx}px, ${dy}px) scale(${s})`
  }
```

**这个「实测踩坑」值得单独说**：直觉写法是 `left:50%; top:50%; transform: translate(-50%,-50%) scale(s)`——在视口恰好等于设计稿比例时看不出问题，比例不一致时整屏内容向右下漂移（headless Chrome 1080×608 视口实测复现）。根因：`transform-origin` 默认是元素中心，`scale` 会把 `translate` 的位移一并放大，而 `left:50%` 参照的却是真实视口——两个参照系错位。修法就是 origin 用 `left top`、偏移量按缩放后的实际尺寸手算。

### 5.2 实测读数

工程在本机实测（2026-10-14，Node 22 + vite 5.4）：

- `npm run build`：573 模块，产物 1.1MB（gzip 372KB，echarts 全量引入；生产应按需引入或 manualChunks 拆包）；
- dev server + headless Chrome 起真实页面，7 秒后 DOM 读数：3 个图表 canvas、GMV 数值、2 条告警，无异常；
- 期间修掉的两个 echarts 实战坑（写进团队规范不过分）：
  1. **空系列的初始 option 不能直接 setOption**——`series: []` + category 轴会抛 `getAxesOnZeroOf is not a function`（tooltip `trigger: 'axis'` 时）。首帧数据未到时先不画，等第一笔数据再渲染；
  2. **line/bar 的 option 缺 `yAxis` 定义**会抛 `yAxis "0" not found`——xAxis/yAxis 都要显式给出，别依赖默认。

### 5.3 数据链路

服务端每 2s 推一批 → `mock.js` 帧内合并（Canvas 篇实战）→ `aggregate.js` 时间桶聚合（60 个秒级点 → 12 个 5s 桶）→ ECharts `setOption` 增量更新。消费端 `EPanel.vue` 对 option 整体替换，引擎内部做 diff——「你给全量、引擎做增量」，这正是配置驱动流派（图表引擎篇）的工作方式。

## 六、7×24 稳定性清单

| 项 | 手段 |
| --- | --- |
| 内存泄漏 | 长跑页面重点盯：定时器/监听器/ECharts 实例都要随路由销毁（`EPanel.vue` 的 dispose 即此纪律） |
| 断线恢复 | WebSocket 重连 + 指数退避 + 重连后全量对齐一次数据 |
| 数据错乱 | 消息带版本号/时间戳，乱序到达丢弃旧版本 |
| 渲染兜底 | WebGL 上下文丢失（`webglcontextlost`）监听并自动降级 Canvas |
| 值班观测 | fps/长任务/内存埋点回传，掉帧超阈值告警 |
