## 1. 渲染方式总览

### Q1（1.4）｜ Canvas 和 SVG 怎么选？

- **判断**：看两个变量——图形数量与交互密度。上千图形、逐帧动画、图像处理选 Canvas；几百以内、需要 DOM 事件与可缩放选 SVG。
- **展开**：Canvas 是即时模式，画完就忘、没有对象，任何变化整幅重画，交互要自己算几何命中；SVG 是保留模式，每个图形是 DOM 节点、浏览器托管重绘与事件，但节点多了 DOM 开销失控。
- **佐证**：viz-lab 实测——100 根柱子改 1 根，全量重绘执行 100 条指令、增量重绘只执行 1 条。
- **边界**：两者不互斥——ECharts 默认 Canvas 但支持切 SVG 渲染器；高端大屏常用「静态层 SVG/离屏 Canvas + 动态层 Canvas」混合。追问：为什么 Canvas 没有场景图？→ 即时模式 API 只是一支画笔、画布上只有像素，所以要自己建显示列表记录"画面由哪些指令构成"，重绘即重放。

## 2. Canvas 2D 性能

### Q2（2.2）｜ Canvas 高频更新怎么保证不卡？

- **判断**：三件套——帧内合并、增量重绘、降采样。
- **展开**：一切数据变更只标脏不画，合并到 `requestAnimationFrame` 里一帧一画（实测一帧 3 次 setData 只重绘 1 次）；重绘用脏矩形只画受影响区域；数据量超帧预算（16.7ms ÷ 单点成本）就降采样。
- **边界**：增量重绘要求显示列表可 diff，复杂图形（路径交叉、透明叠加）的脏区域计算成本会上升，得不偿失时退回全量；降采样丢点要在 tooltip 与图例里对用户诚实。追问：离屏 canvas 解决什么？→ 把不变的部分（网格、背景）画一次存成位图，之后每帧一次 `drawImage` 贴上，把"重画背景"的成本变成一次位图拷贝。

## 4. WebGL 与 Three.js

### Q3（4.1）｜ WebGL 为什么快，贵在哪？

- **判断**：快在 GPU 并行——顶点/片元着色器在数千核心上同时执行，一次 draw call 能画几万个三角形；贵在三维素养——相机、光照、矩阵、draw call 合批都是独立知识块。
- **展开**：渲染管线只有两段可编程（顶点着色器算坐标、片元着色器算颜色），中间光栅化固定；GLSL 是「一次只算一个顶点/像素」的纯函数，时间变化靠 uniform 传入。Three.js 的三件套（场景/相机/渲染器）在 WebGL 上重建了保留模式场景图，`renderer.render` 每帧把场景图翻译成 draw call。
- **佐证**：材质链 Basic（不受光）→ Lambert（漫反射）→ Standard（PBR 主流）→ Physical（透射/清漆），最低配是环境光 + 方向光。
- **边界**：普通图表大屏不要上 WebGL——Canvas/SVG 便宜得多；判断信号是「万级图形逐帧动、需要 3D 或特效」。追问：Three.js 改 `cube.rotation.y` 后 GPU 怎么知道的？→ 每帧 `render` 时框架把模型矩阵（含 rotation）与视图、投影矩阵相乘后随顶点数据提交，GPU 端一次乘完——所以"改对象属性"永远优于手动改顶点；z-fighting 这类坑来自裁剪面范围太宽导致深度精度不足。

## 5. 图表引擎原理

### Q4（5.1）｜ ECharts 和 D3 的本质区别？

- **判断**：ECharts 是配置驱动的图表库，D3 是数据驱动的可视化原语库。
- **展开**：ECharts 内部完成「数据 → processor 链 → 布局 → ZRender 渲染 → 事件」全链路，用户只写 option；D3 只提供 selection / join / scale / shape 等模块，五层架构里每一层都由你显式组装。
- **边界**：ECharts 定制受 option 边界限制（可用 registerLayout / registerView 扩展）；D3 学习曲线在概念多，产出依赖开发者对图形学的理解；报表类需求选 ECharts 几乎总是对的，非标准信息图只有 D3 顺手。追问：tooltip 是怎么知道该显示哪条数据的？→ 拾取得到像素坐标后，用比例尺的 `invert` 逆映射回数据域——所以交互能力建立在比例尺抽象上，而不是画图上。

### Q5（5.2）｜ 比例尺是什么，为什么图表引擎离不开它？

- **判断**：比例尺是「数据域 → 像素域」的映射函数，是连接数据与图形的唯一桥。
- **展开**：线性比例尺算斜率 k = 像素跨度 / 数据跨度，`v = r0 + (x - d0) × k`；类目轴用分段比例尺，step 内扣 padding 得柱宽；刻度线步长对齐 1/2/5 × 10ⁿ（nice 算法），实测 `[0,100]` 5 格得到 `[0,20,40,...,100]`。
- **佐证**：5 个类目放 600px、留 20% 间隙 → step = 600 / (5 - 0.2) = 125，柱宽 = 125 × 0.8 = 100（viz-lab 实测）。
- **边界**：数据含异常值时开 clamp 防止出界；对数轴、序数轴、时间轴是同一抽象的不同实现；invert 逆映射是 hover/点击拾取的前提。追问：invert 有什么用？→ 交互层拿像素坐标反查数据域，tooltip 依赖它才能显示正确数据。

### Q6（5.4）｜ 饼图和堆叠图的布局在算什么？

- **判断**：布局层把「值」翻译成「几何」——饼图算弧段角度，堆叠图算 y0/y1 区间。
- **展开**：饼图布局按值占比切总角度：`angle = (v / total) × span`，逐段累加起止角，弧段天然首尾相接（浮点累加需留 1e-9 容差）；堆叠布局逐系列累加，上一段的 y1 就是下一段的 y0。
- **边界**：布局是纯函数，输入不变输出不变——这是图表可以做增量更新与动画插值的前提；堆叠顺序决定读数语义（总量 vs 各自趋势），`series.stack` 同名才堆。追问：为什么说布局与渲染分离是图表引擎的关键设计？→ 布局结果与渲染目标解耦后，同一份布局可以驱动 Canvas/SVG/WebGL 任一渲染器，也才能做「只重算布局、不重放全部指令」的增量更新。

## 7. 大屏与可视化工程

### Q7（7.3）｜ 大屏项目的数据量超预算了怎么降级？

- **判断**：先量化再降级——最大点数 = 帧预算 ÷ 单点绘制成本，超限按策略丢数据，而不是让页面卡着。
- **展开**：60fps 下帧预算 16.7ms；实测单点成本 0.005ms 时上限约 3340 点，1 万点必须降采样。生产策略：趋势图用 LTTB 抽稀保形状、监控折线按窗口聚合、超出 Canvas 能力上移 WebGL。
- **佐证**：降级阶梯逐级不跳级——视觉（去阴影渐变）→ 数据（降采样）→ 渲染器（WebGL），实测 2k→L0 / 4k→L1 / 8k→L2 / 2w→L3。
- **边界**：任何降采样都要在产品层可见，避免用户误读数据；不要跳级——视觉降级用户无感、数据降级可感知、换渲染器是工程成本。追问：怎么验证降级生效了？→ 帧率埋点对比降级前后的长任务与 fps 分布；viz-lab 的 `planSample` 是决策模型，工程里还要加「实测单点成本」的校准环节。

### Q8（7.1）｜ 大屏项目的工程手段有哪些？

- **判断**：五件事——等比缩放适配、渲染预算约束、降级阶梯、时间切片、数据聚合，外加稳定性五件套。
- **展开**：适配用设计稿等比 scale（XY 铺满会拉伸 / 等比留黑边）；一切优化收敛到 16.7ms 帧预算；降级按「视觉→数据→渲染器」逐级加码；批量任务按帧预算切片（10×3ms 实测切 2 帧，最小粒度是单任务）；监控折线按时间桶聚合 min/max/count（1 万点实测降维到 17 桶、约 500 倍）。
- **佐证**：稳定性五件套 = 内存泄漏 / 断线重连（指数退避）/ 乱序丢弃 / WebGL 上下文丢失降级 / fps 长任务埋点。
- **边界**：Canvas 注意 devicePixelRatio——按 1/dpr 设物理宽高再 `ctx.scale(dpr,dpr)` 保持清晰；Worker/OffscreenCanvas 能挪走计算与绘制，但多数卡顿先把主线程干干净——切片的最小粒度是单任务，任务太大先拆任务。追问：7×24 大屏最常出的线上问题是什么？→ 内存泄漏（定时器/监听器/ECharts 实例随路由销毁）与断线恢复（重连指数退避 + 全量对齐一次），加上 WebGL 上下文丢失的自动降级兜底。
