# 模块面试题 · 交付与质量

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../../进阶/面试方法论.md)的五步答题法——结论/原理/边界/追问/场景。
> 题目来源：各篇正文原有 `## 面试题`（口径与新版正文一致）与原附录题库去重合并。

## 一、Git 与协作

### Q1: Git 分支模型？（第 02 篇）

- **结论**：分支模型不是越多越好，是按团队节奏选型——主干开发（Trunk-based）追求持续集成，Git Flow 适合固定版本节奏。
- **原理**：主干开发：所有人短分支快速合并回主干，分支存活短、冲突少、随时可发布；Git Flow：develop/feature/release/hotfix 多线并行，按版本发版；两者的本质区别是"发布节奏"与"分支存活时长"。
- **边界**：Git Flow 在小团队/快节奏迭代里流程重；主干开发要求测试与门禁强，否则主干不稳。
- **追问**：前端项目适合哪种？→ 通常 Trunk-based + 发布分支，配合按页发布。
- **场景**：多人项目走主干开发 + PR 合入，每次合入都过 lint/测试门禁，主干随时可发布。

### Q2: `merge` 与 `rebase` 的区别与取舍？（第 02 篇）

- **结论**：merge 保留历史分叉（记录真实协作），rebase 线性化历史（整洁但改写提交）。
- **原理**：merge 生成一个合并提交、保留两分支历史；rebase 把当前分支提交"重放"到目标分支顶部，历史线性；rebase 的冲突在逐个提交时解决。
- **边界**：rebase 改写已推送提交会破坏他人工作（需 force push）；公共分支禁用 rebase，私有/特性分支可 rebase。
- **追问**：rebase 冲突怎么处理？→ 逐提交解决，解决后 `git rebase --continue`。
- **场景**：特性分支开发完用 rebase 拉平历史再合入；多人共享分支用 merge 保留协作轨迹。

### Q3: commit message 规范的意义？（第 02 篇）

- **结论**：提交信息是"变更的说明书"——让历史可检索、可追溯，可自动生成 changelog 与触发语义化发布。
- **原理**：约定式提交（`feat:`/`fix:`/`refactor:` 等）让 commit 分类可机器识别；配合 commitlint 门禁与 changelog 生成；关联 issue/PR 提供上下文。
- **边界**：规范的价值在可检索与自动化，不是形式主义；描述应说"为什么改"，而不是复述代码。
- **追问**：commitlint 怎么落地？→ husky 的 commit-msg 钩子校验消息格式。
- **场景**：CI 按 `feat/fix` 自动生成版本与 changelog；回溯线上问题靠"按模块搜 commit"定位改动范围。

### Q4: 代码评审（CR）应该关注什么？（第 02 篇）

- **结论**：CR 重点看契约与风险，不是抠代码风格——接口契约（入参/返回/兜底）→ 状态与副作用 → 兼容与降级 → 埋点覆盖新增分支。
- **原理**：契约错是运行期才暴露的错；状态与副作用决定可测性与内存安全；兼容与降级决定存量用户是否受损；埋点保证新增逻辑可观测。
- **边界**：CR 不替代自动化检查——格式、lint 交给机器，人只审逻辑与取舍。
- **追问**：CR 过慢怎么办？→ 小步提交 + 关注点清单（契约/副作用/兼容/埋点），PR 控制在可审规模。
- **场景**：合入前 CR，重点核对接口字段变更是否同步、异常分支是否有兜底。

## 二、代码规范与门禁

### Q5: ESLint 与 Prettier 的分工？（第 01 篇）

- **结论**：ESLint 管"代码质量与规范"（未定义变量、危险 API、风格争议规则），Prettier 管"格式化"（缩进/引号/换行）——两者各司其职不重叠。
- **原理**：ESLint 是规则引擎，能发现逻辑级问题（未使用变量、危险 API、复杂度）；Prettier 是纯格式化器，输出唯一风格；ESLint 的 stylistic 规则与 Prettier 冲突时关闭交给 Prettier。
- **边界**：格式规则放 Prettier、逻辑规则放 ESLint；`eslint-config-prettier` 关闭冲突规则避免打架。
- **追问**：为什么不能只用 Prettier？→ Prettier 不检查逻辑错误，只改排版。
- **场景**：CI 里 `eslint` 检查 + `prettier --check` 校验格式，提交前 lint-staged 同时跑两者。

### Q6: ESLint 9 flat config 相比 `.eslintrc` 的变化？（第 01 篇）

- **结论**：配置从"级联继承"变为"显式数组组合"，配置即数据。
- **原理**：`extends` 的隐式解析与 `overrides` 嵌套被取消；插件要显式 `plugins: { vue }` 声明；`ignores` 替代 `.eslintignore`。
- **边界**：升级成本是旧配置改造；可被程序化组合是最大收益。
- **追问**：flat config 怎么忽略文件？→ `ignores: ['dist/**']` 数组项。
- **场景**：简历项目 `export default [js.recommended, ...tseslint.recommended, vue.flat/recommended, { rules, ignores }]`，配置可拆可组合、可被脚本生成。

### Q7: lint-staged + pre-commit 怎么落地门禁？（第 01 篇）

- **结论**：husky 挂 pre-commit 钩子，lint-staged 只对暂存文件跑格式化与 lint——检查快、门禁在合入前生效。
- **原理**：husky 生成 git 钩子调用 `lint-staged`；lint-staged 拿暂存文件列表按配置执行（`prettier --write`、`eslint --fix`、`git add`）；只查改动文件避免全库检查拖慢提交。
- **边界**：门禁是"提交前"而非"推送前"；pre-commit 慢的解法是只做增量检查，重活（完整测试）放 CI。
- **追问**：pre-commit 太慢怎么办？→ lint-staged 只处理暂存文件 + 只做增量检查。
- **场景**：团队每人提交前自动格式化与 lint，脏代码进不了仓库。

## 三、测试体系

### Q8: 前端自动化测试分哪几层？各自测什么？（第 05 篇）

- **结论**：单元（纯函数）→ 组件（渲染与交互）→ 集成（多组件+数据流）→ E2E（真实浏览器主流程）。
- **原理**：每层工具与判据不同：Vitest + 分支覆盖；@vue/test-utils + props/事件契约；Vitest + mock 请求；Cypress/Playwright + 用户旅程。
- **边界**：覆盖率不是目标，测试点分级（P0/P1/P2）才是；高层慢且脆，放关键路径。
- **追问**：测试范围怎么不遗漏？→ 由页面配置自动生成，新增页面自动纳入。
- **场景**：简历项目按页面盘点测试点分级（P0 主流程 / P1 边界 / P2 异常），91 个测试点落地。

### Q9: 单元测试与组件测试的区别？（第 05 篇）

- **结论**：单元测纯函数（输入输出断言），组件测渲染与交互契约（props/事件）。
- **原理**：单元测试不挂载组件、不 mock 请求；组件测试用挂载器模拟用户交互、断言渲染结果与事件。
- **边界**：组件测试不能替代 E2E——真实浏览器环境的行为差异测不到。
- **追问**：为什么要让业务逻辑是纯函数？→ 不挂载组件、不 mock 请求就能测，是"可测性设计"。
- **场景**：金额计算、校验、格式化走单元；按钮点击触发事件、props 变化重渲染走组件测试。

### Q10: 测试范围怎么随页面配置自动派生？（第 05 篇）

- **结论**：页面注册的唯一来源是页面配置，测试范围由配置自动派生——新增页面自动纳入，不用人补配置。
- **原理**：`pages.config.ts` 是单一数据源，测试盘点按配置遍历页面生成测试点清单；新页面加一条配置即进入测试范围与回归清单。
- **边界**：配置派生的是"范围"不是"断言"——具体断言仍需人工或生成；页面形态差异大时派生规则要兜底。
- **追问**：派生出来的测试点谁写？→ 先 P0 主流程人工或 AI 生成，P1/P2 按优先级补齐。
- **场景**：新增借贷页 = 配置加一条，CI 自动产出该页 P0 测试清单，不会"忘了加测试"。

### Q11: 覆盖率口径：分支覆盖 vs 行覆盖？（第 05 篇）

- **结论**：分支覆盖比行覆盖更严格——行覆盖只看"执行到"，分支覆盖还要"每条路径走到"。
- **原理**：行覆盖统计被执行的语句占比；分支覆盖统计 if/switch 的分支（true/false、case）是否都被走到；分支覆盖达标通常行覆盖也高，反之不然。
- **边界**：覆盖率是"质量信号"不是目标——80% 覆盖率不等于 80% 质量，重点路径的覆盖才有意义。
- **追问**：为什么分支覆盖常低于行覆盖？→ 分支覆盖要求更细的用例组合。
- **场景**：门禁配 `branches: 80` 而非只看 statements，逼着补边界用例。

### Q12: 场景：一个新页面要上线，质量保障怎么做全？（第 05 篇）

- **结论**：从规范到监控形成闭环——生成即合规、分层测试、CR、按页发布 + 灰度、监控与回滚预案。
- **原理**：规范（脚手架/规则文件让代码生成即合规）→ 单测 + 组件测试 + E2E（P0 主流程）→ CR（契约/兜底/埋点）→ 构建产物（单版本 ESM + 按需 polyfill）→ 按页发布 + 灰度 → 监控（错误/白屏/接口）→ 回滚预案。
- **边界**：体系的关键是"自动派生"而非人工清单——新增页面自动纳入测试与回归，否则必然遗漏。
- **追问**：灰度看什么指标？→ 接口成功率、JS 错误率、白屏率、转化漏斗，与发布前同一套埋点口径。
- **场景**：H5 新增页面从配置生成 → 测试点自动纳入 → 灰度放量看错误率平稳 → 异常一键回滚上一版本产物。

## 四、调试

### Q13: 真机调试链怎么搭？（第 03 篇）

- **结论**：真实域名 + whistle 域名代理 + 扫码入口 + vConsole。
- **原理**：导航页链接不能写 `127.0.0.1`（手机上指向手机自己），必须真实域名；whistle 把线上域名代理到本地 dev server；Vite `allowedHosts` 放行（默认拒绝未知 Host 防 DNS Rebinding）。
- **边界**：只配了 dev 没配 preview，构建产物真机预览时找不到页面。
- **追问**：为什么 Vite 默认拒绝未知 Host？→ 防 DNS Rebinding 攻击。
- **场景**：简历项目开发导航插件（`configureServer` + `configurePreviewServer`）——开发态与预览态都有导航页。

## 五、CI/CD 与发布

### Q14: CI/CD 流水线里前端能做什么？（第 04 篇）

- **结论**：代码检查 → 单元/组件测试 → 构建 → E2E → 产物上传 → 按页/按包发布 → 灰度放量 → 监控与回滚。
- **原理**：门禁前置（pre-commit lint-staged / pre-push 测试）、构建产物可追溯（版本/哈希）、发布可灰度可回滚。
- **边界**：E2E 慢且脆，放发布前关键路径即可；别让测试成为发布瓶颈。
- **追问**：测试在 CI 里失败会怎样？→ 阻断合并与发布，质量门禁兜底。
- **场景**：push 触发流水线，并行跑类型检查与构建，测试通过才进发布阶段。

### Q15: `start-server-and-test` 解决什么（flaky）？（第 04 篇）

- **结论**：解决 E2E 的 flaky——先起服务、等端口就绪、再跑测试，把"启动时序竞争"从用例里消除。
- **原理**：`start-server-and-test` 一条命令串起"启动 server → 轮询端口/URL 就绪 → 执行 test → 结束进程"；避免用例因服务未就绪随机失败。
- **边界**：它解决启动时序，不解决用例本身的脆弱（选择器依赖、异步竞态）——后者要靠稳定选择器与等待策略。
- **追问**：还有哪些 flaky 来源？→ 网络延迟、动画时序、测试数据污染。
- **场景**：CI 里 `start-server-and-test preview` 起 preview 服务再跑 Playwright，产物一致且不 flaky。

### Q16: 发布策略：按页发布 / 按包发布 / 灰度放量 / 回滚？（第 06 篇）

- **结论**：发布粒度决定回归成本——MPA 按页构建、按页发布，灰度放量 + 监控指标 + 自动/手动回滚。
- **原理**：按页构建产物独立，单页改动只发布该页；灰度按比例/条件放量观察错误率与成功率；回滚是"回到上一版本产物"。
- **边界**：灰度必须配监控口径（同一套埋点基准），否则放量风险不可观测。
- **追问**：灰度观察哪些指标？→ 接口成功率、JS 错误率、白屏率、转化漏斗（产品视角）。
- **场景**：简历项目"按页构建、按页发布、按页回归"；产物归集插件对接发布系统。

### Q17: 线上问题怎么从监控定位到发布？（第 06 篇）

- **结论**：靠"监控 → 定位 → 回滚"三步——先有错误/白屏/接口监控兜住，再按版本与时间线缩小范围，最后回滚上一版本。
- **原理**：监控埋点（JS 错误、白屏、接口成功率）在发布后对比基线；按"版本号 + 时间窗口 + 影响面"定位是哪个发布引入；回滚是发布系统的标准动作（上一版本产物原地切换）。
- **边界**：监控口径与发布前一致才有可比性；回滚要快，前提是"发布产物可追溯、可一键回退"。
- **追问**：怎么确认是新版本引入的？→ 对比新旧版本的错误率基线，灰度组 vs 对照组。
- **场景**：灰度放量后错误率陡增 → 按时间线定位到本次发布 → 一键回滚上一版本产物 → 保留现场排查根因。
