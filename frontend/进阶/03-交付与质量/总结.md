# 模块总结 · 交付与质量

## 知识主线

六篇不是并列的知识点，而是一条有依赖关系的链，每一篇都在回答上一篇留下的问题：

```
01 代码规范（代码怎么写才一致）
        │  约定有了，改了代码怎么提交、多人怎么协作？
        ▼
02 Git 与协作（历史与协作怎么管）
        │  协作中出了问题，怎么高效定位？
        ▼
03 调试技巧（问题怎么定位）
        │  个人能力齐了，重复的检查/构建/部署怎么变成机器流程？
        ▼
04 CI/CD 自动化（流程怎么自动化）  ★主轴
        │  流水线有了，怎么让「质量不达标就不让合入」成为硬约束？
        ▼
05 质量体系与测试（门禁怎么设）
        │  质量通过了，新版本怎么安全送到用户面前、上线后怎么兜底？
        ▼
06 发布、灰度与监控（怎么安全上线与兜底）
```

本模块的主轴是**交付流水线**：01/02/03 篇是交付前的个人能力与约定——代码规范把风格与低级错误拦在提交前，Git 管好版本与协作，调试负责定位问题；04 篇把流程串成 lint→test→build→deploy 的自动化流水线；05 篇用测试分层与覆盖率门禁给流水线设硬约束；06 篇是流水线末端的发布策略、灰度熔断与可观测性兜底，最终反哺规范。

## 分篇知识点

### 01-代码规范

- **ESLint 静态检查**：检测代码潜在问题、约束规范；`env` 声明运行环境避免误报 `process`/`window`，`extends` 继承规则集、`rules` 做细粒度开关
- **Prettier 格式化**：统一引号/缩进/分号/换行等风格；与 ESLint 用 eslint-config-prettier + eslint-plugin-prettier 解冲突
- **husky + lint-staged 提交前强制校验**：Git 钩子（pre-commit/commit-msg/pre-push）在指定事件前强制执行脚本；lint-staged 只对暂存区文件跑 prettier/eslint，避免全库无谓检查
- **commitlint + Commitizen**：`type(scope): subject` 约定式提交，commit-msg 钩子校验；Commitizen 用交互式问答引导写规范提交信息，便于回溯与自动生成 changelog
- **BEM 命名规范**：Block（块）__Element（元素）--Modifier（修饰符）三段式；可用 createBEM 工具生成 `van-button__icon--small` 这类带前缀的类名
- **常见坑与 VS Code 落地**：Windows CRLF 与 LF 换行符冲突（Delete ␍）的三种解法；`.vscode/settings.json` 实现「保存即格式化、保存即修复」

### 02-Git 与协作

- **reset 三种模式**：`--soft` 只移动 HEAD（撤销提交、改动留暂存区）、`--mixed`（默认）更新暂存区、`--hard` 连工作区一起丢弃（慎用）；reset 会改写历史，已推远程共享分支不要 `--force`
- **revert 安全反做**：新建一个相反的提交抵消目标提交、不改写原有历史，适合已推送远程的场景
- **分支协作工作流**：从主分支拉功能分支 → 开发提交 → 推远程发起 PR/MR → 评审合入；`git pull --rebase` 让历史更线性；冲突通过 `<<<<<<<`/`=======`/`>>>>>>>` 区域手动解决
- **镜像同步**：Gitee/GitHub 配置 Push 方向镜像自动同步分支/标签/提交，令牌需含 `repo` 权限，最短触发间隔 5 分钟
- **Monorepo 与 pnpm**：单仓库多模块统一依赖与配置、一次命令完成部署；pnpm 扁平结构省磁盘但可能带来「幽灵依赖」，建议 `shamefully-hoist` 等 `.npmrc` 配置
- **最小实现**：`mini-dev-hmr.html` 轮询「变更信号」决定取用哪一版，体会协作中「现在该拿哪一版」的通病

### 03-调试技巧

- **launch.json 核心字段**：`type`/`request`（launch 启动新进程 vs attach 附加已运行进程）/`program`/`runtimeExecutable`/`cwd`/`args`/`env`/`skipFiles`/`sourceMaps` 等
- **三种入口调试**：普通入口文件（`program` 指向入口）、npm 脚本（`runtimeExecutable: "npm"` + `args: ["run", "start:dev"]`）、package.json scripts 旁的快捷 Debug 入口
- **断点类型**：普通断点（执行到停住）、条件断点（表达式成立才停，适合循环过滤）、Logpoint 日志点（不停顿只打日志，避免写 console.log）
- **浏览器调试**：Chrome DevTools Sources 断点 + Console 断点暂停时实时求值 + watch 监视；Performance 面板看主线程时间线定位长任务与卡顿
- **Node 浏览器调试**：`node --inspect-brk index.js` 停在入口起 ws 调试服务，`chrome://inspect/` 连接（默认端口 9229）；Nest 等框架走 `start:debug` 脚本
- **统一认识**：断点调试 = 调试客户端通过调试协议连接可中断执行的运行环境，在命中断点处暂停查看调用栈与变量——`launch` 与 `attach` 两种请求可套用到任意运行时

### 04-CI/CD 自动化

- **术语厘清**：CI 持续集成（频繁合并小改动并自动验证，到构建+测试）、CD 交付（随时可发布到生产，到可部署产物）、CD 部署（验证通过自动上线）；生产环境往往保留审批而非全自动部署
- **GitHub Actions 三件套**：workflow → job → step 用 YAML 声明在 `.github/workflows/*.yml`；事件触发（push/pull_request/workflow_dispatch）；`needs` 声明 job 依赖，artifact 传递产物
- **流水线设计**：lint → test → build → deploy 分阶段「尽早失败」——lint/test 便宜且快放最前，构建只依赖质量通过、部署只依赖产物就绪
- **环境管理**：dev/test/pre-production/production 多环境分层；`environment` 为生产配置独立 secrets 与 approvers，实现「生产部署需人工审批」
- **凭据安全**：密钥永不写进代码或 yml 明文、放 secrets 仅运行时注入、`permissions` 收窄最小权限、OIDC 优于长期 token
- **最小实现**：`pipeline-demo.html` 在浏览器里跑 build→test→deploy，每步门禁、任一步失败即终止，含灰度放量与一键回滚

### 05-质量体系与测试

- **规范治理工具链**：ESLint（质量与潜在问题）、Prettier（格式）、lint-staged（只查本次改动文件）、husky（注入 git hook）、commitlint（提交信息）各管一档、时机清晰
- **自定义 ESLint 规则**：规则本质是返回 `meta` 与 `create` 的对象，在 `create` 里监听 AST 节点（如 CallExpression）并 `context.report`
- **测试分层**：单测（Vitest/Jest 验函数逻辑，vi.fn mock）→ 组件测试（@vue/test-utils 验 props/事件/条件渲染，不测真实请求与视觉）→ E2E（Playwright/Cypress 验真实用户完整路径）
- **覆盖率与质量门禁**：行/分支/函数覆盖率，vitest 配 `thresholds`（lines 80 等）；CI 中失败退出码即门禁——`pnpm lint && pnpm test:coverage` 任一失败 pipeline 变红
- **覆盖率之外的信号**：同质重复代码（SonarQube）、依赖漏洞（npm audit/Dependabot）、复杂度（ESLint complexity）、SLO 回归
- **最小实现**：`lint-demo.html` 用「规则数组 + 正则」逐条扫描代码报错/扣分并给出门禁结论，看清规范工具的本质

### 06-发布、灰度与监控

- **四种发布策略**：蓝绿（双环境切换、回滚极快）、滚动（逐台替换）、金丝雀（先小流量试运行再放量）、灰度（按用户/区域/渠道分桶）；前端资源是静态文件，最常用灰度 + 即时可控的 CDN 发布
- **不可变部署**：产物文件名带内容 hash（`main.8f3c12b1.js`），每个版本是独立永不修改的对象；切换版本 = 发布新的 index.html 指向新 hash 资源，不覆盖旧对象
- **CDN 缓存策略**：带 hash 静态资源长缓存（max-age 一年 + immutable），index.html 短缓存/no-cache 回源校验；前端灰度有入口级（网关分流 index.html）、脚本级、路由级（featureFlag）三种手段
- **灰度预案与回滚**：明确比例与分桶口径 → 定义健康指标 → 自动熔断 → 秒级回滚；资源回滚（入口指回旧 hash）/重建回滚/功能开关三种方式，基石是不可变产物 + 版本与入口映射
- **可观测性三大支柱**：Logs（Sentry 错误日志/行为日志）、Metrics（FP/FCP/LCP、JS Error 率、API 错误率、崩溃率）、Traces（与后端 OpenTelemetry 打通 traceId 串联定位慢接口）
- **稳定性保障体系**：预防（lint/测试门禁）→ 抑制（错误边界）→ 兜底（降级/CDN 容灾）→ 恢复（秒级回滚/自动熔断）→ 复盘（SLO/告警分级值班）
