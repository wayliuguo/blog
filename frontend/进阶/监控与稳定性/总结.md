# 模块总结 · 监控与稳定性

> 说明：本模块共 7 篇，已全部落地——监控平台 · 前端监控 SDK 实现 · 错误监控 · 性能与体验监控 · 埋点与行为分析 · 数据管道与告警 · 企业级性能与监控工程实践。本节按阅读顺序收录各篇知识点。

## 知识主线

七篇不是并列的知识点，而是一条从"看得见"到"焊成工程"的链，每一篇都在回答上一篇留下的问题：

```
01 监控平台（看见什么：三大目标 / 七步闭环 / 采集手段 / 告警机制）                    ★主轴
        │  先把"线上到底好不好、用户干了什么"变成看得见、可查询的数据
        ▼
02 前端监控 SDK 实现（怎么组装：四层分工 / 单例 / 攒批采样重试 / 生命周期收口）
        │  单点采集手段都有了，怎么收成一个开销可控、能进业务的 SDK
        ▼
03 错误监控（第一类数据：六类错误的抓法与字段 / 指纹频控 / sourcemap 还原）
        │  采集能力落到最需要真相的一类数据：到底错在哪
        ▼
04 性能与体验监控（第二类数据：RUM 采集的 buffered / 定稿 / cls 双口径 / TBT 换算）
        │  另一类必须持续观测的数据：真实用户的体感
        ▼
05 埋点与行为分析（第三类数据：声明式埋点 / 会话与身份 / 曝光与点击 / 漏斗与归因）
        │  第三类数据：用户究竟在做什么
        ▼
06 数据管道与告警（怎么变成决策：秒桶 → 分位值 → 窗口 → 告警四要素 → 收敛）
        │  三类数据都采回来了，怎么聚合成能判定、能告警、能溯源的东西
        ▼
07 企业级性能与监控工程实践（焊成工程：前端 Agent → 上报 → 聚合 → 告警 的可运行闭环）
```

本模块的主轴是**「把线上状态变成可决策的数据」**：01 定下监控的三个视角（稳定性 / 用户体验 / 业务）与闭环流程；02 把采集收成一个 SDK，解决"怎么装进业务又不拖慢业务"；03~05 分别把错误、性能、行为三类数据的采法与口径讲透；06 解决"采回来之后怎么变成判定与告警"；07 把整条链路装配成能进生产的工程。

与「性能优化」模块的分工是：**优化模块负责把指标改好，监控模块负责持续回答"改完到底有没有变好、有没有变差"**。两边的指标口径必须一致（LCP ≤ 2.5s、CLS ≤ 0.1、P95 而非 avg），否则优化前后不可比。

## 分篇知识点

### 01-监控平台

- **监控三大目标**
  - **稳定性**：监控 JS 错误、资源异常（script/link 加载失败）、接口错误（ajax/fetch 异常）、白屏四类异常，及时定位并解决
  - **用户体验**：监控 TTFB/FP/FCP/FMP/FID/卡顿（>50ms 长任务）等加载与响应指标，识别性能瓶颈
  - **业务**：监控 PV（页面浏览量）、UV（去重后的独立访客数）、页面停留时长，从业务视角看流量与用户行为
- **七步闭环流程**
  - **目标设定与数据采集**：先确定监控指标与目标（加载时间/错误率/用户行为），再用合适技术或自封装函数采集数据
  - **数据传输与存储处理**：经 HTTP 请求、WebSocket 等方式传到后端，用数据库/日志/分析平台存储处理供后续分析
  - **分析与可视化**：转成可视化报表、图表或仪表盘，帮助开发与运营了解系统性能和用户行为
  - **告警预警与定位优化**：数据超限触发告警通知相关人员，结合监控数据与告警信息定位根因、改进优化
- **错误收集方式**
  - **`try/catch` 手动捕获**：业务代码主动包裹可能出错的逻辑，错误信息最全、可控性强，但侵入业务且易遗漏未包裹的错误
  - **`window.onerror`**：捕获未被 `try/catch` 包裹的运行时错误（脚本执行错误）
  - **`unhandledrejection`**：Promise 被 reject 而未处理时兜底捕获，`e.reason` 是被拒绝的原因
  - **资源加载 `error`（捕获阶段）**：`addEventListener('error', fn, true)`——资源错误不冒泡，需在捕获阶段统一拦截
  - **框架专项机制**：Vue `config.errorHandler` / `errorCaptured`，组件渲染、生命周期或事件处理出错时统一上报
- **上报方式**
  - **手动上报**：业务 catch 分支显式调用上报函数，可控、可自定义数据，但对业务代码侵入性强
  - **自动上报**：监听浏览器内置事件（如 `window.onerror`）自动采集，无需侵入业务
  - **1×1 gif 图片打点**：数据拼到图片请求 URL，防跨域、不带 Cookie、不阻塞页面加载，gif 体积最小最轻量
- **性能指标采集**
  - **网络层面**：`getEntriesByType('navigation')[0]` 的时间戳差值算 DNS、TCP、SSL、TTFB、传输耗时
  - **页面展示层面**：`PerformanceObserver` 监听 `paint`/`layout-shift` 拿 FP/FCP/CLS，监听 `longtask` 统计卡顿次数与总阻塞时间
- **埋点与告警**
  - **埋点字段**：用户标识 + 环境信息（OS/浏览器/userAgent）+ 页面地址 + 行为信息（事件类型/元素/时间戳/参数）统一采集
  - **报表产出**：事件委托/全局监听统一采集，按业务维度输出 PV、UV、停留时长、转化漏斗等报表
  - **分级告警**：按严重程度（致命/严重/一般）配置不同通知渠道与响应时效
  - **阈值合理**：结合历史基线动态设置，避免阈值过严频繁误报、过松遗漏问题
  - **去重与抑制**：同一问题聚合、去重、时间窗口抑制，避免短时间内重复轰炸
  - **溯源到人**：告警关联负责模块/团队，附带指标、URL、堆栈、用户信息加速定位

### 02-前端监控 SDK 实现

- **四层分工**
  - **采集层**：错误 / 性能 / 行为三块各自独立成模块，互不感知
  - **传输层**：采样 → 攒批 → 投递 → 重试 → 溢出丢弃
  - **治理层**：采样率在传输层、脱敏与频控在采集层
  - **生命周期**：`init` 时机与页面离开时的收口上报
- **组装方式**
  - **单例**：业务多处 `init` 只返回首个实例，否则重复绑监听、重复上报
  - **插件化**：采集器只共用 `emit(event)` 一个签名，加一类采集不用碰传输与生命周期
- **传输层四个必备机制**
  - **攒批**：同样 12 条事件，逐条发 12 次请求、攒批发 3 次
  - **采样**：放在入队口丢弃，2000 条 @10% 只接受 198 条
  - **重试**：`maxRetry = 2` 即首投 + 2 次重试，耗尽即放弃并计入 `dropped`
  - **溢出**：`maxQueue` 上限内丢最旧的，50 条入队 10 条上限最终只投 10 条
- **投递顺序**
  - **`sendBeacon` 优先**：页面卸载也能送达、不阻塞、但拿不到响应
  - **`fetch + keepalive` 兜底**：有响应、请求体有 64KB 上限
  - **同步 XHR 不可用**：阻塞卸载，浏览器已基本禁用
- **生命周期收口**
  - 用 `visibilitychange → hidden` 而不是 `unload`：`unload` 在移动端常不触发
  - LCP / CLS 是"越晚越准"的收敛值，必须在离开时定稿
- **自身开销约束**
  - 一次 `flushAll` 实测 593B / 4 条，单条约 148B
  - 回调里只累加、不序列化；指标只算一次，避免重复上报
- **治理口径**
  - 错误不采样、埋点可低比例采样、长任务明细 1%~5%
  - URL 只留 path、文本截断 40 字符、表单值不采
  - 频控按指纹（message + 位置 + 行号），不是按 message

### 03-错误监控

- **六类错误与捕获方式**
  - **运行时错误**：`error` 事件，能拿到 message / 文件 / 行列 / stack
  - **未处理 Promise**：`unhandledrejection`，只有 `reason.stack`，无文件名行号
  - **资源加载失败**：同一个 `error` 事件，但必须 `capture = true`
  - **接口错误**：包裹 `fetch`，`!res.ok` 时记录 `status`
  - **网络错误**：包裹 `fetch` 的 `catch` 分支，如 `Failed to fetch`
  - **跨域脚本错误**：只剩 `Script error.`，需 `crossorigin` + CORS 才有细节
- **`window.onerror` 的三个坑**
  - 资源错误不冒泡，必须捕获阶段监听；判据是 `event.target.tagName` 是否存在
  - `Script error.` 是同源策略，不是代码问题
  - 参数是 `(message, source, lineno, colno, error)`，行号是整页行号
- **Promise 拒绝**
  - 不触发 `window.onerror`，必须单独监听
  - `reason` 可能是非 Error（字符串 / `undefined`），必须 `String()` 兜底
  - 实测无 filename / lineno，位置信息不能作为唯一索引
- **接口错误**
  - 包装 `fetch`，业务代码无感
  - `catch` 里上报后必须 `throw`，否则吞掉业务异常
  - 网络错误与 HTTP 错误字段不同，看板上要分开统计
- **指纹与频控**
  - 指纹 = message + 出错位置 + 行号
  - 资源 / 接口错误没有 message，必须把 `src` / `url` 算进指纹，否则所有资源错误塌成一条
  - 被频控拦下的事件仍进 `captured`，只打 `throttled` 标记
  - 实测 6 条捕获 → 4 条出端，拦截 2 条
  - 线上还要带出现次数（count）与指纹复位逻辑
- **sourcemap 还原**
  - 生产栈是压缩后的，必须用 sourcemap 还原
  - 用 `release` 版本号把 map 与代码绑定，否则还原到错误版本
  - 服务端还原优于客户端还原（客户端会暴露 sourcemap）
- **框架层兜底**
  - Vue：`config.errorHandler` / `onErrorCaptured`
  - React：错误边界只覆盖渲染错误，不含事件处理器与异步代码，不能替代全局监听

### 04-性能与体验监控

- **RUM 与 Lab 采集的三个差别**
  - `buffered: true` 补收注册前的历史条目，否则 FCP 恒为 0
  - `visibilitychange → hidden` 时定稿，LCP / CLS 越晚越准
  - 不支持的 entry 类型静默跳过，不能把页面搞崩
- **采集方式**
  - `PerformanceObserver` 事件驱动，优于定时轮询
  - `navigation` entry 用 `getEntriesByType` 读取（TTFB / domReady / load）
  - 回调里只累加，序列化与上报留到 flush
- **指标口径**
  - 实测 TTFB 166ms / FCP 416ms / LCP 1272ms / CLS 0.0116 / TBT 90ms
  - LCP 晚于 FCP 的差值 = 主要内容"白等"的时间
  - **FID 已被 INP 取代**；INP 要按交互分组，不能对全部 `event` 取平均
  - **CLS 豁免"紧跟用户输入"的位移**（`hadRecentInput`），要同时存 `cls` 与 `clsRaw`
  - 位移合并要求：500ms 窗口内、累计不超过 5% 视口高度
  - **TBT = Σ max(0, duration - 50)**，实测 140ms 长任务只贡献 90ms
- **上报字段设计**
  - `appId` / `release`（sourcemap 索引）/ `route`（用模板避免维度爆炸）
  - 设备与网络档位（低端机与弱网是分位值恶化主因）
  - 五个指标 + 端上算好的评级；采样率要让接收端能还原计数
- **采集自身开销**
  - 一次 flush 593B / 4 条
  - 指标只算一次，重复 flush 会造成重复上报
  - 资源明细只报 Top N 或总量，否则随资源数线性增长

### 05-埋点与行为分析

- **三种埋法对比**
  - **代码埋点**：口径最准、参数最全，但每次改动要发版
  - **可视化埋点**：不改代码，但规则随页面改版失效
  - **无埋点（全埋点）**：覆盖最全，但噪声大、元素路径易变、上报量巨大
  - 实践是组合：核心转化路径用代码埋点，长尾用可视化，兜底用无埋点
- **声明式埋点**
  - 业务只写 `data-track` / `data-expose` 属性，采集逻辑集中在 SDK
  - 点击走事件委托，动态插入的 DOM 自动被覆盖
  - 元素标识与 DOM 结构解耦，改版不影响数据
  - 代价：必须靠埋点字典约束命名，否则同义不同名会把一个按钮拆成多个维度
- **身份与会话**
  - 设备 ID / 匿名 ID / 登录 ID 三者生命周期与用途不同
  - 会话按 30 分钟不活跃切分（行业惯例 25~30 分钟）
  - 会话判定放在 `track()` 入口，任何事件都刷新活跃时间
- **指标口径**
  - **PV**：每次页面加载 vs 每次路由切换，SPA 里差数倍
  - **UV**：按匿名 ID / 设备 ID / 登录 ID 去重结果不同
  - **停留**：离开页面时结算，用户直接关页会丢，需 enter/stay 双写兜底
  - **跳出率**：单 PV 会话占比 vs 短停留会话占比
- **曝光埋点**
  - 用 `IntersectionObserver`，不监听 `scroll`（后者每次滚动都要同步读布局）
  - `unobserve` 保证曝光只报一次
  - `entry.time` 是判定进入视口的时刻，不是停留时长
  - 首屏元素注册即回调，不会漏（scroll 监听要等用户先滚）
  - 真实口径还要加可见比例与持续时长阈值
- **点击埋点**
  - 事件委托一次监听覆盖全站
  - 曝光与点击是两套独立锚点，同一元素两个标识分开命名
- **漏斗与归因**
  - 实测事件流 8 条：PV → 2 条首屏曝光 → 2 次委托点击 → 自定义事件 → 滚动后曝光 → 停留 1032ms
  - 漏斗靠统一命名才成立，价值在定位断点
  - UTM 四字段分工：source / medium / campaign / content
  - 首次归因与末次归因要提前定义
- **脱敏与治理**
  - URL 只留 path、文本截断、表单值一律不采
  - 脱敏放在采集口而不是接收端（数据出端就已经泄露）
  - 治理四件套：埋点字典、命名规范、上报校验、超期埋点自动下线

### 06-数据管道与告警

- **四段管道**
  - 采集端 → 传输 → 聚合 → 告警，四段失败模式不同，分开调
  - 采集端故障：采样过高、卸载丢数据；传输故障：批次过大被拒、重试无上限
  - 聚合故障：粒度错、用平均值；告警故障：无收敛、无恢复
- **采集端职责**
  - 先入内存、顺手落盘、再按需计算
  - 落盘（JSONL / Kafka）是唯一能重放历史的手段
  - 生产形态：前端 → 网关（限流鉴权）→ 队列（削峰可重放）→ 消费者
- **秒桶聚合**
  - 按固定桶长归拢，桶内先计数再算分位值
  - 桶长选 1 秒用于故障发现、小时级用于容量趋势
  - 秒级数据短期保留 + 降采样长期保留
- **分位值**
  - 桶内 `floor(n*q)` 取位，是近似值；精确分位值要用直方图 / t-digest
  - 事故秒实测 avg 351ms 而 P95 1119ms（3.19 倍），平均值掩盖长尾
  - 告警主用 P95，P99 追长尾，max 只作排查线索
- **秒桶与滑动窗口的分工**
  - 秒桶用于定位"哪一秒开始坏"，样本少、抖动大
  - 滑动窗口用于告警判定，数值稳但掩盖起止时刻
  - 同一段时间两口径实测差 2.7 倍（窗口 P95 418ms vs 事故秒 1119ms）
- **告警四要素**
  - `threshold` + `op`：判定条件
  - `consecutive`：连续命中几次才推，抑制单点抖动
  - `silenceMs`：同规则最小推送间隔，防轰炸
  - `resolved`：指标回到阈值内要显式推恢复通知
  - `streak` 与 `active` 是两个状态，不能合并；不命中时 `streak` 要清零
  - 告警 `ts` 用桶时间戳而非收包时间；告警值只是触发瞬间的窗口快照
- **收敛**
  - 实测事故秒 8 批 × 3 条规则 = 24 条潜在告警，静默期压成 3 条
  - 手段：连续命中、静默期、聚合、依赖抑制、值班排班
  - 依赖抑制用于避免根因告警被下游告警淹没
- **分级与溯源**
  - 分级的核心是"谁在什么时候必须做什么"
  - 事件带 `release` 关联到发布；规则与看板要有 owner，改阈值要评审
- **成本三旋钮**
  - 采样（在采集端降量）、预聚合（明细短期 + 桶长期）、保留期分层
  - 不要省的三个：错误量、告警判定窗口、恢复通知

### 07-企业级性能与监控工程实践

- **工程闭环四段**
  - **前端 Agent**：负责采集/传输/治理，埋点 SDK 做采样与脱敏
  - **传输层**：`sendBeacon` / `fetch keepalive`，轻量不阻塞、页面卸载也能送达
  - **接收端聚合**：秒桶聚合 + 分位值 + 去重 + 阈值/基线，把离散上报变成可决策指标
  - **决策端**：报表 / 告警 / 趋势，超阈触发通知、可溯源到人
- **Agent 做成可复用 SDK**
  - **采集层**：定义"报什么"——性能指标（FP/FCP/LCP/TTFB）、接口延迟（包裹 fetch/XHR 读 latency 与 ok）、错误（onerror + unhandledrejection + 框架专项）、行为（事件委托采点击/曝光）
  - **传输层**：优先 `sendBeacon`、兜底 `fetch keepalive`；长时指标（LCP/CLS/INP）在 `visibilitychange → hidden` 上报取最终值
  - **治理层**：采样（`Math.random() < SAMPLE_RATE`，热门页 5%–10%）、脱敏（URL query 密钥、token、userAgent 截断）、频控（按 message+文件+行号聚合，同一错误一段时间只报一次）
- **秒桶聚合**
  - **聚合字段**：按 1 秒一个桶累加 `count / totalLatency / errCount / fpSum / lcpSum`，每来一条上报就更新对应桶
  - **延迟样本**：该秒延迟样本存入 `p95List`，供后续算分位值
  - **价值**：把海量离散上报变成可决策的指标
- **分位值才是体感**
  - **为什么不用 avg**：平均延迟被少数慢请求拉偏，P95/P99 代表"绝大多数用户"的体验，是告警更该关注的判定量
  - **两级聚合**：demo 对每秒钟样本算 P95，再对最近 60 秒做二次聚合
- **告警"准"的三要素**
  - **阈值**：demo 基线 P95 >120ms、错误率 >1% 触发告警
  - **去重**：同一秒同指标准确去重，避免告警轰炸
  - **动态基线**：基于历史数据算动态基线，比固定阈值更抗业务起伏
- **决策端与闭环回归**
  - **监控报表台**：`monitor.html` 每 2s 轮询 `/api/report`——KPI 卡超阈标红、avg/P95 曲线叠加阈值线、告警流含时间/指标/值/阈值可溯源复现
  - **闭环回归**：优化（拆长任务、缩 LCP、补 key 消 CLS）后看曲线是否下降，不以"感觉快了"为止，而以"指标回归到阈值内"为准
