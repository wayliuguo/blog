# 监控平台

前端监控（Frontend Monitoring）是一种用于**捕获、分析和报告**网站或应用程序中异常、错误和性能问题的方法体系。通过前端监控，开发团队能够在用户实际使用场景中实时感知问题，从而快速定位、响应和解决，最终提升应用的稳定性与用户体验。

## 监控目标

前端监控围绕三个核心目标展开。

### 1. 稳定性

监测前端应用程序中的异常情况，及时定位并解决问题，提高应用稳定性和用户体验。需要监控的异常类型包括：

- **JS 错误**：JS 执行错误或 Promise 异常。
- **资源异常**：`script`、`link` 等资源加载异常。
- **接口错误**：`ajax` 或 `fetch` 接口请求异常。
- **白屏**：页面完全空白，无任何可交互内容。

### 2. 用户体验

监测性能指标，识别潜在性能瓶颈，优化应用的加载速度和响应时间。常用指标包括：

- **TTFB（Time To First Byte）首字节时间**：发送请求到接收返回首个字节的时间。
- **FP（First Paint）首次绘制**：浏览器首次将像素绘制到屏幕上的时间。
- **FCP（First Contentful Paint）首次内容绘制**：将第一个 DOM 渲染到页面的时间。
- **FMP（First Meaningful Paint）首次有意义绘制**：网页加载过程中能看到"有意义内容"的时间点。
- **FID（First Input Delay）首次输入延迟**：用户首次与页面交互到页面响应的时间。
- **卡顿**：执行时间超过 50ms 的长任务。

### 3. 业务

从业务视角了解流量与用户行为：

- **PV（Page View）**：页面浏览量或点击量。
- **UV（Unique Visitor）**：访问站点的不同用户数（通常按 IP、设备或标识去重）。
- **页面停留时长**：用户在页面/站点内的停留时间。

## 监控流程

一套完整的前端监控平台遵循如下流程：

1. **目标设定**：确定需要监控的指标和目标（如页面加载时间、错误率、用户行为等）。
2. **数据采集**：使用合适的工具或技术收集数据，或自行封装函数采集监控数据。
3. **数据传输**：将采集到的数据通过 HTTP 请求、WebSocket 等方式传输到监控系统或后端服务器。
4. **数据存储和处理**：用数据库、日志文件或数据分析平台存储、处理数据，供后续分析与展示。
5. **数据分析和可视化**：将数据转化为可视化报表、图表或仪表盘，帮助开发与运营人员了解系统性能和用户行为。
6. **告警和预警**：根据设定的指标与阈值，当数据超限时触发告警或预警，通知相关人员处理。
7. **问题定位和优化**：结合监控数据与告警信息，定位问题根因，进行优化改进，提升系统性能与用户体验。

## 错误监控与上报

### 错误收集方式

#### try/catch 手动捕获

在业务代码中主动包裹可能出错的逻辑，捕获异常后手动处理或上报。优点是可捕获的错误信息最丰富、可控性强；缺点是需要侵入业务代码，容易遗漏未包裹的错误。

> 示意片段（无配套脚本）

```js
try {
    // 可能出错的业务逻辑
} catch (error) {
    // 捕获并上报
    monitor.trackError(error)
}
```

#### window.onerror 捕获运行时错误

捕获未被 try/catch 包裹的运行时错误（脚本执行错误）。

> 示意片段（无配套脚本）

```js
window.onerror = function (msg, source, lineno, colno, error) {
    // 上报错误信息
}
```

#### 监听 unhandledrejection 事件

当 Promise 被 reject 而没有得到处理时会触发该事件，用于兜底 Promise 异常。

> 示意片段（无配套脚本）

```js
window.addEventListener('unhandledrejection', (e) => {
    // e.reason 为 Promise 被拒绝的原因
})
```

#### 资源加载错误监听

脚本、样式、图片等资源加载失败会触发 `error` 事件，但不会冒泡（除非设置 `addEventListener('error', ..., true)` 使用捕获阶段）。注意资源加载错误通常在捕获阶段才能统一拦截。

> 示意片段（无配套脚本）

```js
window.addEventListener('error', (event) => {
    // 判断 target 是资源元素，则为资源加载错误
    // 通过事件捕获获取资源加载失败信息
}, true)
```

资源加载错误与 JS 运行错误的捕获方式不同：`window.onerror` 能拿到 JS 运行时错误；而图片、`link`、`script` 等资源加载错误需要通过 `window.addEventListener('error', handler, true)`（捕获阶段）来监听。

#### 各技术栈的专项机制

以 Vue 为例，Vue 项目内置错误捕获机制：`Vue.config.errorHandler` 和 `Vue.config.errorCaptured`。可以劫持这些方法，当组件渲染、生命周期或事件处理出错时统一上报。

> 示意片段（无配套脚本）

```js
Vue.config.errorHandler = function (err, vm, info) {
    // 在错误发生时进行上报
    monitor.trackError(err, vm, info)
}
```

### 错误信息解析

通过 `window.addEventListener('error', handler)` 监听时，`event` 中携带的错误信息可覆盖大多数错误上报指标：

> 示意片段（无配套脚本）

```js
window.addEventListener('error', (event) => {
    // 关键字段：
    // event.message   - 错误消息，如 "Uncaught TypeError: Cannot set properties..."
    // event.filename  - 发生错误的文件名或 URL
    // event.lineno    - 发生错误的行号
    // event.colno     - 发生错误的列号
    // event.error     - 包含类型、消息与 stack 堆栈信息
    // event.type      - 事件类型 "error"
})
```

更多字段可通过 `ErrorEvent` 获得：`bubbles`（是否冒泡）、`cancelable`（是否可取消）、`target`/`srcElement`（触发事件元素）、`timeStamp`（事件时间戳）、`eventPhase`（事件传播阶段）、`composed`（是否可跨 Shadow DOM）等。

### 上报方式

上报方式决定了数据如何从客户端传到服务端，常见方案：

- **手动上报**：在业务代码出错的 catch 分支显式调用上报函数。
  - 优点：可控性强，可自定义上报的数据内容。
  - 缺点：对业务代码侵入性强。
- **自动上报**：通过监听浏览器/应用内置事件自动采集数据，无需侵入业务。

  > 示意片段（无配套脚本）

  ```js
  window.onerror = function () {
      monitor.trackError(...)
  }
  ```
- **使用 1×1 gif（图片打点）上报**：把监控数据拼到图片请求的 URL 上，用 `new Image()` 发出请求，服务端返回一张 1×1 的透明 gif 就算上报完成。
  - 优点：不受同源策略限制、不触发预检；不带当前域名下的 Cookie；相比 png、jpg，gif 体积最小、最轻量。
  - 缺点：**能带的数据很少**——数据只能放在 URL 上，受 URL 长度上限制约（约 2~8 KB，取决于浏览器与服务端、CDN 的配置），长堆栈与批量合并都放不下；只能发 GET，拿不到响应体，无法确认服务端是否入库；数据落在 URL 上会进 access log 与浏览器历史，含用户标识的字段有泄露风险。
  - 定位：这是上一代方案，今天已被 `sendBeacon` 取代——`sendBeacon` 跨域同样不触发预检，却能用请求体带上约 64 KB 数据。
  - 注意它省的是首屏、不是卸载：浏览器会为了加载这张图片而推迟 unload，所以"不阻塞"只说对了一半。

按上面的边界，图片打点只适合字段少、且不追求送达确认的轻量场景：

> 示意片段（无配套脚本）

```js
// 图片打点：数据只能拼在 URL 上，所以每个字段都要先截断
const img = new Image()
img.src =
    '/collect.gif?' +
    new URLSearchParams({
        t: 'error',
        msg: message.slice(0, 100), // 不截断就可能超过 URL 上限，被服务端拒收
        page: location.pathname,
        ts: Date.now() // 带时间戳，避免被浏览器缓存
    }).toString()
```

## 性能监控指标采集

### 性能数据接口（Performance API）

`Performance` 是 Web API 中的一个接口，用于访问和测量网页性能数据。它有两套取数范式，**生产环境不是二选一，而是分工不同**。

**同步快照（拉）**：主动去查，读一条已经写完的记录。适合页面加载过程中「一次写好」的条目：

- `performance.getEntriesByType("navigation")`：页面导航过程的时间戳，可算出 DNS、TCP、TTFB 等各阶段耗时（见下节）。
- `performance.getEntries()` / `performance.getEntriesByName(name, type)`：获取性能条目（导航、资源、标记、测量）。
- `performance.now()`：当前时间相对导航开始的毫秒数，用于测量执行时间。
- `performance.mark(name)` / `performance.measure(name, start, end)`：创建自定义时间戳标记并计算两点间耗时。

**异步订阅（推）**：不主动查，条目产生时被回调。LCP、CLS、长任务这些都是「异步产生、越晚越准」的收敛值，只能这样采：

- `PerformanceObserver`：异步监听性能指标。要带 `buffered: true`，才能补收 SDK 初始化之前已经产生的条目——少这个参数最常见的后果是 FCP 恒为 0；老浏览器不支持某类 entry 时用 `try/catch` 静默跳过，不能把页面搞崩。

真实的采集器里两者是一起用的：动态指标挂观察者，navigation 这类快照读完事。

> 摘自 `./code/monitor-lab/sdk/perf.mjs`

```js
    function observe(type, cb, extra = {}) {
        if (typeof PO !== 'function') return false
        try {
            const po = new PO(list => list.getEntries().forEach(cb))
            po.observe({ type, buffered: true, ...extra })
            observers.push(po)
            return true
        } catch {
            return false // 该 entry 类型不被支持：直接放弃这一类，不抛
        }
    }

    function readNavigation() {
        const nav = perf && perf.getEntriesByType && perf.getEntriesByType('navigation')[0]
        if (!nav) return null
        metrics.ttfb = Math.round(nav.responseStart)
        metrics.domReady = Math.round(nav.domContentLoadedEventEnd)
        metrics.load = Math.round(nav.loadEventEnd)
        return nav
    }
```

生产环境还要避开两种写法：一是轮询 `performance.getEntries()`——要么采到半截的值，要么定时器空转；二是已被规范弃用的 `performance.timing` 与 `performance.navigation`，它们由 `PerformanceNavigationTiming` 取代。

### 网络层面指标采集

基于 `performance.getEntriesByType("navigation")[0]` 的时间戳计算各阶段耗时：

> 示意片段（无配套脚本）

```js
const getEntry = () => performance.getEntriesByType('navigation')[0]

// DNS 解析时间
const { domainLookupEnd, domainLookupStart } = getEntry()
const DNS = domainLookupEnd - domainLookupStart

// TCP 连接时间
const { connectEnd, secureConnectionStart } = getEntry()
const TCP = connectEnd - secureConnectionStart

// SSL 握手时间
const { connectEnd, connectStart } = getEntry()
const SSL = connectEnd - connectStart

// TTFB：请求到收到首个字节的耗时（含网络与服务端处理）
const { responseStart, requestStart } = getEntry()
const TTFB = responseStart - requestStart

// 数据传输耗时
const { responseEnd, responseStart } = getEntry()
const dataResponseTime = responseEnd - responseStart

// 重定向耗时
const { redirectEnd, redirectStart } = getEntry()
const redirect = redirectEnd - redirectStart
```

### 页面展示层面指标采集

页面展示主要指首屏渲染类指标与长任务：

- 通过 `PerformanceObserver` 监听 `paint`（获取 FP/FCP）与 `layout-shift`（获取 CLS）等指标。
- 通过 `PerformanceObserver` 监听 `longtask`，捕捉执行时间超过 50ms 的长任务，统计卡顿次数与总阻塞时间。

## 埋点与用户行为

埋点用于采集用户在页面中的行为数据，支撑业务分析与体验优化。

### 采集完整度：环境信息

- **用户标识**：用户 id 或用户 token。
- **环境信息**：操作系统、浏览器类型与版本，记录 `userAgent`。
- **页面地址**：当前监控页面的 URL。

### 用户行为信息

- **事件类型**：用户进行的具体操作（点击、滚动、输入等）。
- **事件元素（srcElement）**：操作发生在哪个元素上。
- **触发时间（timeStamp）**：操作发生的时间。
- **事件参数**：某些特定事件携带的额外参数（如输入事件的内容）。

通过事件委托 / 全局监听统一采集，再按业务维度输出如 PV、UV、停留时长、转化漏斗等报表。

## 告警

告警是监控体系的"最后一公里"。基于设定的指标与阈值，当监控数据达到或超过预设阈值时，触发告警或预警机制，通过邮件、短信、IM、电话等方式通知相关人员处理。设计告警时需注意：

- **分级告警**：按严重程度（如致命/严重/一般）区分配置不同通知渠道与响应时效。
- **阈值合理**：避免阈值过严频繁误报、过松遗漏问题，可结合历史基线动态设置。
- **去重与抑制**：同一问题避免短时间内重复轰炸，可采用聚合、去重、时间窗口抑制。
- **溯源到人**：告警应能关联到负责的模块/团队，并附带上下文（指标、URL、堆栈、用户信息）以加速定位。

## 配套代码

本篇的可运行示例在仓库 `frontend/进阶/监控与稳定性/code/monitor-lab/`。

| 文件 | 演示什么 | 对应小节 |
| --- | --- | --- |
| `./code/monitor-lab/site/error-report.html` | 错误监控与上报：window.onerror 捕获运行时错误、unhandledrejection 捕获 Promise 拒绝，用 URLSearchParams 模拟发送到服务端 | 错误监控与上报 |
| `./code/monitor-lab/sdk/perf.mjs` | 性能采集：navigation 走同步快照读取，paint / LCP / CLS / longtask 走 PerformanceObserver 订阅 | 性能监控指标采集 |
| `./code/monitor-lab/site/monitor.html` | 监控报表与告警台：KPI 卡超阈标红、avg/P95 曲线叠加阈值线、告警流，轮询 /api/report 拉取聚合快照 | 告警 |
| `./code/monitor-lab/site/agent.html` | 前端埋点 Agent：模拟页面访问/接口调用/JS 错误，采集 FP/FCP/LCP/TTFB 等指标，用 sendBeacon 兜底上报 | 埋点与用户行为 |

启动方式：在 `code/monitor-lab` 目录执行 `npm start`（起采集端，端口 5189，同时把 `site/` 下的页面与 `sdk/` 下的 SDK 模块按 URL 下发，并接收 `POST /collect` 上报）。
或执行 `npm run enterprise` 起完整闭环服务（`http://localhost:5188/agent.html`，埋点 → 上报 → 聚合 → 告警）。
