# 埋点与行为分析

`错误监控` 与 `性能与体验监控` 回答的是"页面好不好"，埋点回答的是"用户干了什么"。两者的采集手法差别很大：错误与性能是**等事件自己发生**，埋点是**主动往业务代码里埋锚点**——所以埋点的问题往往不是技术问题，而是"埋错了、埋漏了、埋重了"。

## 一、三种埋法：代码埋点 / 可视化埋点 / 无埋点

| 维度 | 代码埋点 | 可视化埋点 | 无埋点（全埋点） |
| --- | --- | --- | --- |
| 怎么做 | 业务代码里调 `track('事件名', 参数)` | 运营在管理后台圈选元素，生成配置下发 | SDK 自动采集全部点击 / 曝光，后端再筛选 |
| 覆盖范围 | 想埋什么埋什么 | 只能"圈得出元素"的交互 | 全量点击与页面浏览 |
| 参数丰富度 | 高（可带业务上下文） | 中（依赖元素属性） | 低（只有元素路径与位置） |
| 开发成本 | 高（每次改动都要发版） | 低（不改代码） | 最低（一次接入） |
| 数据质量 | 高（口径明确） | 中 | 低（噪声大，元素路径易变） |
| 典型问题 | 埋点漏埋 / 埋错位置 | 圈选规则随页面改版失效 | 上报量巨大，接收端成为瓶颈 |

实践里通常是**组合**：核心转化路径用代码埋点（口径必须准），运营关心的长尾交互用可视化埋点，兜底用无埋点看"还有哪些没覆盖到的地方"。

本篇的实验台走的是**声明式埋点**——它是代码埋点与无埋点之间的折中：业务只写属性，采集逻辑统一在 SDK 里。

## 二、声明式埋点：业务只写属性，采集逻辑集中在 SDK

页面里不写任何采集代码，只加两个属性：

> 摘自 `./code/monitor-lab/site/track-lab.html`

```html
  <button data-track="cta-hero" data-expose="hero-cta">开始体验</button>
  <div class="card" data-expose="card-intro">首屏可见的卡片（进视口即曝光）</div>
```

SDK 则统一处理"谁被看到了、谁被点了"：

> 摘自 `./code/monitor-lab/sdk/track.mjs`

```js
  // 点击：事件委托，一次监听覆盖全站，新增 DOM 无需重绑
  function listenClicks(root) {
    const doc = root || win.document
    if (!doc) return
    doc.addEventListener('click', (e) => {
      const el = e.target && e.target.closest && e.target.closest('[data-track]')
      if (!el) return
      track('click', { id: el.getAttribute('data-track'), text: sanitizeText(el.textContent) })
    })
  }
```

好处有三条，都是"少出事"：

1. **新增元素不用改采集代码**——事件委托挂在 `document` 上，动态插入的按钮自动被覆盖；
2. **事件名与元素解耦**——`data-track="cta-hero"` 是稳定标识，DOM 结构怎么改都不影响数据；
3. **埋点集中在 SDK 里**，代码评审时只需要看一个文件，不会散落在几十个组件里。

代价是**必须靠埋点字典约束命名**（见第十节），否则 `cta-hero` / `hero-cta` / `btnHero` 三种写法会把同一个按钮拆成三个维度。

## 三、会话与身份：三个 ID 别混用

行为数据必须能回答"这是同一个人的第几次访问"，所以要区分三种身份：

| 标识 | 生成方式 | 生命周期 | 用途 |
| --- | --- | --- | --- |
| 设备 ID | 首次访问生成，存 `localStorage` | 长期（清缓存即失效） | 无登录场景下的"同一台设备" |
| 匿名 ID（`anonId`） | 首次访问生成 | 与设备 ID 同生命周期 | 未登录用户的 PV / UV 去重 |
| 登录 ID（`userId`） | 登录后由后端下发 | 随登录态 | 跨设备、跨会话的行为串联 |

> 摘自 `./code/monitor-lab/sdk/track.mjs`

```js
  function loadIdentity() {
    let anon = store && store.getItem('ml_anon_id')
    if (!anon) { anon = uid('anon'); if (store) store.setItem('ml_anon_id', anon) }
    return anon
  }
```

会话（session）是另一层：**用户不活跃超过 30 分钟就算新会话**。这不是随便定的窗口——搜索、电商、内容类的行业惯例都在 25~30 分钟附近；窗口太短会把"读一半去吃个饭"算成两次访问，太长则把"同一个人下午和晚上各来一次"算成一次。

> 摘自 `./code/monitor-lab/sdk/track.mjs`

```js
  function track(name, payload = {}) {
    const t = now()
    if (t - session.lastAt > SESSION_GAP) {
      session.id = uid('s')
      session.startedAt = t
      session.pageViews = 0
    }
    session.lastAt = t

    const ev = { type: 'track', name, ts: t, sessionId: session.id, anonId, ...payload }
    events.push(ev)
    emit(ev)
    return ev
  }
```

注意**会话判定放在 `track()` 入口**：任何事件都能刷新会话活跃时间，这样"用户在页面上只滚动不点击"也不会被误判为离开。

## 四、PV / UV / 停留 / 跳出：口径先说清楚

这四个词在需求文档里天天出现，但每个都有两三种口径。不上来就定义，报表一定对不上数。

| 指标 | 本实验台口径 | 常见另一种口径 | 差异后果 |
| --- | --- | --- | --- |
| PV | 每次页面加载记 1 次 | 每次路由切换记 1 次 | SPA 里差好几倍 |
| UV | 按 `anonId` 去重 | 按设备 ID 或登录 ID 去重 | 登录用户跨设备会被算成两个人 |
| 停留时长 | 离开页面时结算（`enter + leave`） | 与下一次事件的时间差 | 用户直接关页面时不产生停留数据 |
| 跳出率 | 只有一个 PV 的会话占比 | 停留 < 10s 的会话占比 | 单页应用几乎恒为 100% |

停留时长的实现：

> 摘自 `./code/monitor-lab/sdk/track.mjs`

```js
  // 停留时长：离开页面时结算，用 enterAt 与当前时间差
  function pageLeave() {
    const stay = now() - session.enterAt
    return track('stay', { url: String((win.location && win.location.pathname) || '/'), stay })
  }
```

它的**已知缺口**：用户直接关标签页、或者手机切后台被系统杀掉时，`stay` 事件可能发不出去。工程上的补救是**双写**——进入页面时先发一条 `enter`，离开时再发 `stay`，接收端对"只有 enter 没有 stay"的会话按超时时间兜底估算。

## 五、曝光埋点：用 IntersectionObserver，别监听 scroll

曝光（expose）的语义是"元素进入视口且被用户看到了"。朴素做法是监听 `scroll` 再算 `getBoundingClientRect()`，问题是**每次滚动都要同步读布局**——正是 `性能优化` 模块讲的布局抖动（强制同步布局）。

`IntersectionObserver` 把这件事交给浏览器：

> 摘自 `./code/monitor-lab/sdk/track.mjs`

```js
  // 曝光：IntersectionObserver 比 scroll 监听省得多，且不会漏首屏
  function observeExposure(selector = '[data-expose]') {
    const doc = win.document
    if (!doc || typeof win.IntersectionObserver !== 'function') return 0
    const io = new win.IntersectionObserver((entries) => {
      entries.forEach((entry) => {
        if (!entry.isIntersecting) return
        const el = entry.target
        // entry.time 是「被判定进入视口」的时刻（相对页面开始），不是停留时长
        track('expose', { id: el.getAttribute('data-expose'), at: Math.round(entry.time) })
        io.unobserve(el)   // 曝光只报一次
      })
    })
    const nodes = doc.querySelectorAll(selector)
    nodes.forEach((n) => io.observe(n))
    return nodes.length
  }
```

三个设计点：

- **`io.unobserve(el)` 让曝光只报一次**。不取消观察的话，用户上下滚动会把同一个元素报出几十次曝光。
- **`entry.time` 不是停留时长**，它是"被判定进入视口"的时刻（相对页面开始时间）。想统计"看了多久"要自己记 `intersectionRatio` 变化并累计时长。
- **首屏元素不会漏**：观察者在注册时会立刻对当前已在视口内的元素回调一次——这也是它优于 scroll 监听的地方（scroll 监听要等用户先滚一下）。

真实的曝光口径还会加阈值，比如"可见面积 ≥ 50% 且持续 ≥ 1s 才算曝光"：

> 示意片段（无配套脚本）

```js
io.observe(el)   // 注册时用 threshold 控制触发比例
// new IntersectionObserver(cb, { threshold: 0.5 })
```

## 六、实测：8 条事件串成的用户轨迹

实验页做了一次完整动作：进页面 → 看首屏 → 点两个按钮 → 搜索一次 → 滚到底 → 离开。

> 摘自 `./code/monitor-lab/scenarios/track.mjs`（运行：`npm run track`）

```
---- 事件流：共 8 条（页面注册了 3 个曝光元素） ----
| T+Nms | 事件名 | 标识            | 附加字段         |
|-------|--------|-----------------|------------------|
| +0    | pv     | /track-lab.html | ref=direct       |
| +16   | expose | hero-cta        | at=440ms         |
| +16   | expose | card-intro      | at=440ms         |
| +308  | click  | cta-hero        | —                |
| +308  | click  | cta-card        | —                |
| +309  | search | —               | keyword=性能优化 |
| +525  | expose | footer-banner   | at=949ms         |
| +1032 | stay   | /track-lab.html | stay=1032ms      |
```

对着这张表能读出很多东西：

- **`hero-cta` 与 `card-intro` 的 `at` 都是 440ms**：两个首屏元素是同一次回调里判定的，说明"进页面就有曝光"这条路走通了，不需要用户先滚一下；
- **`footer-banner` 的 `at=949ms`**：它是在滚到底之后才曝光的，说明底部元素没有被漏掉——如果这里没数据，通常就是"只观察了首屏元素"或"scroll 监听没触发"的 bug；
- **同一个元素可以既是曝光锚点又是点击锚点**：按钮上同时写了 `data-track="cta-hero"` 与 `data-expose="hero-cta"`，两个标识分开命名，曝光数与点击数才能各算各的（如果共用一个标识，你会分不清"看到了"和"点了"）。

汇总成看板：

> 摘自 `./code/monitor-lab/scenarios/track.mjs`（运行：`npm run track`）

```
---- 小看板：把事件流汇成可决策的数字 ----
| 口径     | 数值    | 说明                                  |
|----------|---------|---------------------------------------|
| PV       | 1       | 页面浏览量                            |
| UV       | 1       | 按匿名 ID 去重，单机演示恒为 1        |
| 曝光元素 | 3       | hero-cta / card-intro / footer-banner |
| 点击     | 2       | cta-hero / cta-card                   |
```

## 七、漏斗：行为数据真正的用法

单点数字（PV、点击量）只是原料，漏斗才是结论。把上面的事件流按"看没看到 → 点没点"排列：

> 摘自 `./code/monitor-lab/scenarios/track.mjs`（运行：`npm run track`）

```
---- 漏斗：从曝光到点击 ----
| 环节          | 人数 | 转化率 |
|---------------|------|--------|
| 曝光 hero-cta | 1    | —      |
| 点击 cta-hero | 1    | 100.0% |
```

单机演示的转化率恒为 100%，但线上漏斗的价值在**定位断点**：曝光 10000、点击 2000 说明文案或位置有问题；点击 2000、下一步提交只有 100，说明流程中间那一步有硬伤。埋点的意义就在于让每一级都可比。

漏斗要成立，前提是**每一级的事件标识都来自同一套命名**（`cta-hero` 而不是三种写法），也就是第十节的埋点字典。

## 八、归因：`ref` 与 UTM

所有流量都要能回答"从哪来"。标准做法是解析跳转链接上的 UTM 参数：

> 示意片段（无配套脚本）

```js
// 只在这里读取 query，落库前就丢掉，避免把带 token 的完整 URL 存进去
const q = new URLSearchParams(location.search)
const ref = q.get('utm_source') || document.referrer || 'direct'
```

四个 UTM 字段各管一层：`utm_source`（渠道，如 weixin）、`utm_medium`（媒介，如 cpc）、`utm_campaign`（活动名）、`utm_content`（同一活动下的不同素材）。归因规则的坑在于**首次归因 vs 末次归因**：用户先看广告再搜品牌词进来，算广告的功劳还是搜索的功劳？这个必须在需求阶段定，不能留给数据分析师猜。

## 九、脱敏与合规

埋点最容易出的事故不是漏埋，而是**把不该传的东西传了**。三条硬线：

1. **URL 只留 path**，query 里可能有 token、手机号、订单号；
2. **元素文本统一截断**（本实验台 40 字符），因为按钮里可能是用户昵称、手机号；
3. **表单值一律不采**，`input` 的 `value` 永远不上报，密码框更要显式排除。

> 摘自 `./code/monitor-lab/sdk/track.mjs`

```js
export function sanitizeText(text) {
  const s = String(text || '').replace(/\s+/g, ' ').trim()
  return s.length > MAX_TEXT ? s.slice(0, MAX_TEXT) + '…' : s
}

// 脱敏：只留 path，丢掉可能带 token / 手机号的 query
export function sanitizeUrl(url) {
  return String(url).split('?')[0]
}
```

脱敏要放在**采集口**而不是接收端：数据一旦出端就已经泄露了，接收端再过滤只是心理安慰。

## 十、埋点治理：字典 + 校验

埋点最大的长期成本是**口径腐化**：两年后没人知道 `btn_v2_new` 是什么按钮。

| 手段 | 做法 | 解决的问题 |
| --- | --- | --- |
| 埋点字典 | 一张表登记每个 `data-track` 标识、含义、负责人、上线时间 | 标识可解释、责任可追溯 |
| 命名规范 | 统一 `区域-元素-动作`（如 `hero-cta-click`） | 避免同义不同名 |
| 上报校验 | SDK 里 `if (!id) return`；开发环境对未登记标识告警 | 防漏参数、防拼错 |
| 下线机制 | 超过 N 天无数据的埋点自动进入待清理列表 | 防止表无限膨胀 |

最实用的一条是**在开发环境对未登记标识直接告警**：埋点错在编码阶段发现，成本几乎为零；等到报表对不上再回头查，成本是几十倍。
