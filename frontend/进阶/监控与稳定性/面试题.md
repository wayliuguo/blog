# 模块面试题 · 监控与稳定性

## 1. 监控体系与采集手段

### Q1（1.1）｜ 白屏是什么？可能的原因有哪些？

- **判断**：白屏 = 页面完全空白、无任何可交互内容；根因通常是 JS 错误中断渲染、资源加载失败、初始化流程未走完。
- **展开**：SPA 依赖 JS 挂载，脚本执行前或执行出错即白屏；CSS/JS 资源 404 或跨域被拦也白屏；监控要在初始化早期注入才能捕获。
- **边界**：白屏要区分"加载中"与"真白屏"——用页面级埋点（LOAD.ERROR）定时判定；追问：白屏怎么先让错误可见？→ 监控脚本早于 polyfills、捕获阶段监听资源错误。

### Q2（1.1）｜ 前端监控要采哪三类数据？

- **判断**：稳定性（错误 / 资源 / 接口 / 白屏）、用户体验（加载与响应指标、卡顿）、业务（PV / UV / 停留 / 转化）。
- **展开**：三类数据回答三个不同的问题——"有没有坏"、"快不快"、"用户在做什么"，缺任何一类都会导致决策盲区（比如接口全成功但转化率跌了，只监控稳定性就发现不了）。
- **边界**：三类数据的上报量级差很多（业务行为量最大），所以采样策略必须分开定；追问：怎么汇总到一张看板？→ 按 `appId + route + release` 三个维度对齐，同一时间轴叠加。

### Q3（1.1）｜ 异常监控看哪几个维度？

- **判断**：JS 错误率 · 白屏 · 资源加载失败 · 接口成功率与耗时 · 初始化流程健康度。
- **展开**：白屏的直接工具是 LOAD.ERROR（页面级埋点）；资源错误必须用捕获阶段监听（`error` 事件在资源加载失败时不冒泡）；监控脚本要早于 polyfills 执行。
- **边界**：只监控不定位等于白搭；每个维度都要能串到"哪个页面 / 接口 / 版本"；追问：错误分级有什么价值？→ network-error 找运维 / 网关，logic-error 找前端，避免互相甩锅。

### Q4（1.4）｜ 上报方式怎么选？

- **判断**：优先 `navigator.sendBeacon`，兜底 `fetch(..., { keepalive: true })`；页面卸载与隐藏时上报走这条链路，其余场景可批量合并。
- **展开**：`sendBeacon` 由浏览器在后台发送，不阻塞页面卸载、页面关闭也能送达；`keepalive` 让 `fetch` 在页面卸载后继续完成请求。1×1 gif 打点是更老的方案，防跨域、不带 Cookie、不阻塞加载，但只能传很有限的信息。
- **边界**：`sendBeacon` 的 payload 有大小上限（约 64KB），超了要改走 `fetch`；同步 `XMLHttpRequest` 会阻塞卸载，浏览器已基本禁用；上报本身也有体积与开销成本，必须采样与合并；追问：长时指标（LCP/CLS）什么时候上报？→ 等 `visibilitychange → hidden` 取最终值再报。

### Q5（1.6）｜ 监控埋点分哪几层？

- **判断**：页面级（LOAD.*）/ 曝光级（SHOW.*）/ 交互级（CLICK.*）/ 结果级（*_SUC/_FAIL）四层。
- **展开**：页面级管访问与性能；曝光级管元素可见；交互级管点击行为；结果级管业务闭环成败；每层独立成事件、共用口径。
- **边界**：埋点遗漏必然发生——靠"埋点清单随方案生成"兜底，新增分支必须补埋点；追问：怎么防遗漏？→ 清单随方案生成（沉淀为模板），CR 时核对新增分支。

### Q6（1.6）｜ 白屏怎么用数据定位，而不是靠猜？

- **判断**：先让错误可见（早期注入监控）→ 用数据定位（资源加载错误）→ 最小改动修复并留痕。
- **展开**：典型场景是容器多页跳转后白屏——靠捕获阶段的资源错误上报，定位到 modulePreload 预加载失败且没有降级。
- **边界**：预取降级与真实接口失败要在监控上分开打点，否则会误判问题域；追问：为什么资源错误要用捕获阶段？→ `error` 事件在资源加载失败时不冒泡，只有捕获阶段能监听到。

### Q7（1.6）｜ 场景：线上反馈某页面白屏率上升，本地无法复现，怎么排查？

- **判断**：先确认监控覆盖 → 按维度切片 → 区分预取降级与真实失败 → 定位到具体资源/接口 → 修复 + 回归 + 埋点验证。
- **展开**：① 确认 LOAD.ERROR / 资源加载错误 / JS 错误率是否在监控内；② 按版本 / 机型 / 接口维度切片，找出集中分布；③ 区分"预取超时降级"与"真实接口失败"；④ 查初始化流程是否中断（polyfill 之前发生的错误需要最早注入的监控才能捕获）；⑤ 定位到资源或接口 → 修复 + 回归 + 埋点验证。
- **边界**：监控没覆盖的维度只能靠用户反馈补——先补监控再修问题；追问：怎么确认是不是预取导致的？→ 监控里把预取降级与真实失败分开打点，看白屏是否集中在预取路径。

## 2. 前端监控 SDK 实现

### Q8（2.1）｜ 监控 SDK 为什么要做单例和插件化？

- **判断**：单例是为了避免"重复初始化 → 重复绑监听 → 重复上报"，插件化是为了让采集器之间互不感知、传输与生命周期不用改动。
- **展开**：多团队各写一句 `init()` 时，每一类错误会上报 N 遍，看板上的错误数直接乘 N；而错误采集不该知道埋点存在，两者唯一的交集是 `emit(event)` 这个函数签名，加一类采集就是加一个插件。
- **边界**：单例要暴露 `reset()` 供测试与多轮演示重置；插件注册顺序会影响事件顺序，采集类插件之间必须无依赖；追问：插件怎么拿到上报能力？→ 插件 `install` 时注入 `{ track, emit, transport, win, flushAll }`，只调 `emit` 不碰传输细节。

### Q9（2.2）｜ 监控 SDK 的采样、攒批、重试、溢出分别解决什么？

- **判断**：采样控制量、攒批控制请求数、重试兜住偶发失败、溢出保住内存。
- **展开**：采样放在**入队口**，被采样掉的事件尽早消失、不占内存（实测 2000 条 @10% 只接受 198 条）；攒批让 12 条事件从 12 次请求降到 3 次；重试给偶发网络失败 2 次机会；`maxQueue` 防止网络卡死时队列无限增长（实测 50 条入队、上限 10 条，丢弃 40 条）。
- **边界**：重试必须有上限——耗尽就计入 `dropped`；溢出丢的是**最旧**的而不是最新的；采样要按用户维度稳定，否则分位值会失真；追问：哪一类数据不该采样？→ 错误不采样（抽样会漏偶发崩溃），性能指标全量或高比例（分位值需要样本量）。

## 3. 错误监控

### Q10（3.1）｜ 错误的捕获手段有哪几种？

- **判断**：`try/catch`（手动）· `window.onerror`（未捕获的运行时错误）· `unhandledrejection`（Promise 拒绝）· 捕获阶段的资源 `error` 事件 · 包裹 `fetch`/XHR（接口与网络错误）· 框架专项钩子（Vue `config.errorHandler` / `onErrorCaptured`、React 错误边界）。
- **展开**：这几种互相补充，覆盖"同步执行 / 异步执行 / 异步拒绝 / 资源加载 / 网络请求"五条路径；资源错误因为不冒泡只能靠捕获阶段；框架内部错误会先被框架兜住，要用框架钩子接出来。
- **边界**：`try/catch` 信息最全但侵入业务、易漏；React 错误边界**不覆盖事件处理器与异步代码**，不能替代全局监听；跨域脚本的错误信息会被抹成 `Script error.`；追问：判据怎么区分资源错误与脚本错误？→ 看事件对象上有没有 `target.tagName`：有就是资源错误，没有才是脚本错误。

### Q11（3.1）｜ 场景：设计一个错误监控方案，要求"能定位、不轰炸"。

- **判断**：捕获覆盖六类错误 + 结构化字段齐备 + 指纹频控 + sourcemap 还原 + 版本关联。
- **展开**：捕获上分别挂 `error`（含 `capture: true`）、`unhandledrejection`、包裹 `fetch`，框架层再挂 `config.errorHandler` / 错误边界；每条错误上报 `kind / message / filename / lineno / colno / stack / fp / release / route`；接收端按指纹聚合出"出现次数 + 影响用户数 + 首次/末次时间"。
- **边界**：`Script error.` 类拿不到细节的错误要单独归类，不能与"有堆栈的错误"混在同一个指标里；sourcemap 还原依赖 `release`，构建流程必须把 map 与版本一起归档；追问：怎么让错误量下降而不是只看见？→ 按指纹排 Top N，先修影响用户数最多的那几条，修复后用同一指纹的计数曲线验证是否归零。

### Q12（3.2）｜ Promise 拒绝为什么抓不到？怎么抓？

- **判断**：`Promise.reject()` 不触发 `window.onerror`，只在控制台打警告；必须单独监听 `unhandledrejection`。
- **展开**：`onerror` 只接"未捕获的同步抛错"与"脚本执行错误"这条路径，Promise 的未处理拒绝是另一条独立的错误通道，由 `unhandledrejection` 事件承载，`e.reason` 是被拒绝的原因。
- **边界**：`reason` 不一定是 `Error`，可能是字符串、对象甚至 `undefined`（`Promise.reject()`），必须 `String(r)` 兜底；这类错误**没有 filename 与 lineno**，位置不能作唯一索引；追问：为什么不能只上报 `reason.message`？→ 没有 `stack` 就无法定位，`reason.stack` 才是唯一线索。

### Q13（3.2）｜ 跨域脚本错误只能拿到 `Script error.`，怎么办？

- **判断**：这是同源策略在保护跨域脚本，不是代码写错了；要拿到细节必须给 `<script>` 加 `crossorigin`，且 CDN 响应头带 `Access-Control-Allow-Origin`。
- **展开**：不同源的脚本出错时，浏览器不把 message / 文件 / 行号传给页面，只给一句 `Script error.`。
- **边界**：拿不到位置，sourcemap 也还原不了——所以最终解法往往是"把关键脚本自建同源"，而不是指望还原；追问：为什么 `Script error.` 不能忽略？→ 它是真实错误的信号（有错但没细节），要和"无错误"区分开统计。

### Q14（3.3）｜ 错误上报的"指纹"该怎么设计？

- **判断**：指纹 = `message + 出错位置 + 行号`，用于频控去重；**资源与接口错误没有 message，必须把 `src` / `url` 算进指纹**。
- **展开**：一个渲染循环里的报错，message 完全一样，只按 message 去重会把不同的出错点合并；把位置与行号算进去才能既压量又不丢信息。资源错误若不带上 `src`，页面上所有图片加载失败会塌成同一条 `resource@-:0`。
- **边界**：实测 6 条捕获 → 4 条出端，被拦下的 2 条仍进 `captured` 只打 `throttled` 标记（本地调试要看全部、线上要压量）；线上还要带上出现次数 `count`，否则看不出"这条错误每分钟 800 次"；追问：指纹表需要清理吗？→ 需要，长驻页面上要有复位逻辑（如 5 分钟未再出现就清掉），否则同样的错误只报首次那一次。

### Q15（3.3）｜ 线上某条错误量突然暴涨，怎么收敛上报？

- **判断**：按指纹聚合 + 频控 + 带上出现次数，而不是把每条都推上去。
- **展开**：错误量暴涨通常只有一两个指纹在刷（比如渲染循环里每帧报一次），按指纹做短时间窗频控就能把出端量压到与"错误种类数"同量级。
- **边界**：被频控拦下的不能直接丢——要留在本地 `captured` 里并累计 `count`，恢复后把计数一起补报，否则会丢掉"到底发生了多少次"这个关键信息；追问：频控会不会掩盖新问题？→ 不会，只要指纹里含位置与行号：新问题就是新指纹，第一次一定出端。

### Q16（3.4）｜ 生产环境的错误堆栈怎么还原到源码？

- **判断**：用 sourcemap 还原，并且要用 `release`（版本号）把 map 与代码绑定。
- **展开**：生产栈是 `at n (app.a1b2c3.js:1:48213)` 这种压缩后的形式，文件名带哈希、行号列号都在第一行；接收端按事件里带的 `release` 找到对应版本的 map 再解析。
- **边界**：客户端还原会暴露 sourcemap 给用户，且体积大；服务端还原要求每次发布都保存对应的 map 文件——**没有版本号会还原到错误的那一版代码**；追问：为什么一定要保留 sourcemap？→ 不留就没有任何还原手段，线上错误等于只能看到一个哈希文件名。

## 4. 性能与体验监控

### Q17（4.1）｜ 为什么性能采集要用 `PerformanceObserver` 而不是轮询？

- **判断**：因为 `paint` / `largest-contentful-paint` / `layout-shift` / `longtask` 都是**异步产生**的条目，轮询要么采到半截值、要么定时器空转。
- **展开**：观察者是事件驱动，条目产生即回调；而且注册时可带 `buffered: true` 把**缓冲区里已经产生过的历史条目**一次性补给你——SDK 往往是异步加载的，少这个参数最常见的结果就是 **FCP 恒为 0**。
- **边界**：`navigation` entry 是页面加载时就写完的一条记录，仍走 `getEntriesByType` 读取；不支持某类 entry 的旧浏览器要静默跳过（用 `try/catch` 包住 `observe`），不能把页面搞崩；追问：回调里能做什么？→ 只做累加，不做序列化、不做上报；重活留到 flush。

### Q18（4.1）｜ 场景：设计一个 RUM 性能采集方案，覆盖三个核心指标。

- **判断**：用一个 `PerformanceObserver` 采集器覆盖 LCP / INP / CLS，在 `visibilitychange → hidden` 时定稿上报，端上算好评级。
- **展开**：LCP 监听 `largest-contentful-paint` 并保留最后一次值；CLS 累加 `!hadRecentInput` 的 `layout-shift`（同时存 `clsRaw` 供排查）；INP 监听 `event` entry 并按交互分组取分位值。上报带 `appId / release / route / deviceType / networkType / sampleRate`。
- **边界**：必须 `buffered: true`（否则 SDK 晚加载时 FCP/LCP 采不到）；`route` 要用模板而不是带参 URL，否则维度爆炸；资源明细只报 Top N 或总量，不能全量；追问：怎么从数据判断"是网络问题还是渲染问题"？→ 看 TTFB 与 FCP 的差值：TTFB 高说明服务端/网络慢，TTFB 正常但 FCP 高说明渲染被阻塞。

### Q19（4.2）｜ CLS 的口径 `hadRecentInput` 是怎么回事？

- **判断**：规范里 CLS **只统计没有紧跟用户输入的位移**——用户点击后导致的重排是"预期内"的，被规范豁免；所以同一页面会得出 `cls`（规范口径）与 `clsRaw`（含全部位移）两个数。
- **展开**：`layout-shift` 条目带 `hadRecentInput` 标记，采集时 `clsRaw += e.value` 全部累加、`cls += e.value` 只在 `!hadRecentInput` 时累加。
- **边界**：位移还要求"在 500ms 窗口内、且累计不超过 5% 视口高度"才合并成一次 shift；看板与告警用 `cls`（与官方和竞品可比），排查问题要看 `clsRaw`，因为"点击后横幅把内容顶下去"在 `cls` 里被豁免了但用户照样觉得页面在跳；追问：单机实验为什么常常两个值一样？→ 无头浏览器里很难稳定复现"位移紧跟用户输入"这一分支，所以差值常是 0。

### Q20（4.2）｜ TBT 是怎么算出来的？

- **判断**：`TBT = Σ max(0, duration - 50)`——**长任务的门槛是 50ms，但计入 TBT 的是超出部分**。
- **展开**：页面里塞一次 140ms 的同步循环，实测 `longtasks = 1`、`tbt = 90ms`，正是 140 − 50。写错成"累加任务总时长"会让 TBT 虚高。
- **边界**：`longtask` 只在同步阻塞超过 50ms 时产生；一段逻辑被切成很多 40ms 的小块时一次长任务都不会有，但用户仍会感觉"一顿一顿"——这种要看交互延迟（`event` entry / INP）而不是长任务数；追问：TBT 与 INP 什么关系？→ TBT 衡量加载期的阻塞总量（Lab 指标），INP 衡量整页生命周期里真实交互的响应延迟（现场指标），前者是后者的一个弱预测因子。

### Q21（4.2）｜ FID 和 INP 有什么区别？

- **判断**：FID 已被 INP 取代（2024 年 3 月起 Core Web Vitals 不再包含 FID）；FID 只测第一次交互的**输入延迟**，INP 测**所有交互**的响应延迟分位值。
- **展开**：FID 只测"从点击到事件回调开始执行"，不测处理完；INP 覆盖一次交互从输入到下一帧渲染的完整耗时，并取最差的那一段。
- **边界**：INP **不能把所有 `event` 条目的 `duration` 取平均**——规范要求按交互分组（同一轮用户输入引发的多个事件算一次），再取分位值；自己实现容易在分组逻辑上出错，建议直接用官方的 `web-vitals` 库；追问：采集时怎么控制量？→ 观察 `event` entry 时用 `durationThreshold` 过滤掉极短交互，避免上报量爆炸。

### Q22（4.2）｜ 线上 LCP 突然变差，从监控上怎么找原因？

- **判断**：先按维度切片（版本 / 设备 / 网络 / 路由），再看"LCP 晚于 FCP 的差值"与资源明细，最后落到具体元素。
- **展开**：`release` 维度能确认是不是本次发版引入；设备与网络档位能定位是不是低端机/弱网放大；LCP 与 FCP 差值大说明"主要内容来得晚"（多为图片或异步数据），差值小则整体都慢。
- **边界**：LCP 是"越晚越准"的收敛值，必须等 `hidden` 时定稿，中途值会低估；采样率不高时单页样本太少，要看 P75 而不是平均值；追问：怎么验证优化生效？→ 用同一套口径对比优化前后的 P75，而不是"感觉快了"。

## 5. 埋点与行为分析

### Q23（5.1）｜ 埋点有哪三种埋法，怎么选？

- **判断**：代码埋点（口径最准、成本最高）、可视化埋点（不改代码、随改版失效）、无埋点/全埋点（覆盖最全、噪声最大）；实践是**组合使用**。
- **展开**：代码埋点可以在业务上下文里带参数；可视化埋点由运营圈选元素生成配置下发；无埋点由 SDK 自动采集全部点击与页面浏览，后端再筛选。
- **边界**：核心转化路径必须用代码埋点（口径要准），运营关心的长尾交互可以用可视化，无埋点只适合做"还有哪些没覆盖"的兜底补漏；追问：声明式埋点是哪一类？→ 代码埋点与无埋点之间的折中：业务只写 `data-track` / `data-expose` 属性，采集逻辑集中在 SDK；代价是必须靠埋点字典约束命名。

### Q24（5.2）｜ 会话是怎么切分的？为什么是 30 分钟？

- **判断**：用户不活跃超过 30 分钟就算新会话（行业惯例 25~30 分钟）。
- **展开**：窗口太短会把"读一半去吃个饭"算成两次访问，太长则把"下午和晚上各来一次"算成一次。
- **边界**：会话判定要放在**事件入口**（每次 `track` 都检查），这样"只滚动不点击"也不会被误判为离开；任何事件都刷新活跃时间；追问：会话 ID 与用户 ID 的关系？→ 一个用户（匿名 ID / 登录 ID）可以有多个会话，一个会话包含多个 PV 与行为事件。

### Q25（5.3）｜ PV / UV / 停留 / 跳出，各有什么口径陷阱？

- **判断**：四个指标每个都有两三种口径，必须先定义再埋点，否则报表一定对不上数。
- **展开**：PV 有"每次页面加载"与"每次路由切换"两种（SPA 里差数倍）；UV 按匿名 ID / 设备 ID / 登录 ID 去重结果各自不同；停留时长有"离开时结算"与"与下一次事件的时间差"两种；跳出率有"单 PV 会话占比"与"短停留会话占比"两种。
- **边界**：`stay` 事件的已知缺口是**用户直接关标签页时可能发不出去**，工程补救是 `enter` / `stay` 双写，接收端对只有 enter 的会话按超时兜底估算；追问：三个身份 ID 分别什么时候用？→ 设备 ID 用于无登录场景的"同一台设备"，匿名 ID 用于未登录 PV/UV 去重，登录 ID 用于跨设备串联行为。

### Q26（5.4）｜ 曝光埋点为什么用 `IntersectionObserver`，不用监听 `scroll`？

- **判断**：因为 `scroll` 监听方案每次滚动都要同步读布局（`getBoundingClientRect`），正是布局抖动；`IntersectionObserver` 把这件事交给浏览器，省得多且不会漏首屏。
- **展开**：观察者在注册时会立刻对当前已在视口内的元素回调一次，所以"进页面就可见"的元素不需要用户先滚一下；而 `scroll` 监听必须等首次滚动才触发。
- **边界**：必须在回调里 `unobserve` 让曝光**只报一次**，否则用户上下滚动会把同一元素报几十次；`entry.time` 是"被判定进入视口"的时刻，**不是停留时长**；追问：真实口径还要加什么？→ 可见面积比例阈值（`threshold`，如 50%）与持续时长阈值（如 ≥1s），否则"一闪而过"也会被算成曝光。

### Q27（5.5）｜ 场景：给一次营销活动页设计埋点方案。

- **判断**：先定漏斗再定事件，用声明式埋点（`data-track` / `data-expose`）落地，并对齐会话与去重口径。
- **展开**：漏斗通常是"曝光 → 点击 → 填写 → 提交成功"，每一级一个稳定标识（如 `hero-cta` / `form-submit`）；曝光用 `IntersectionObserver` 且只报一次；点击用事件委托；提交结果分 `_suc` / `_fail` 两个事件；渠道归因读 UTM 并在落库前丢掉 query。
- **边界**：曝光不报一次会让数字虚高几十倍；标识不统一（`cta-hero` / `hero-cta` / `btnHero` 混用）会把同一个按钮拆成三个维度；文本要截断、表单值一律不采；追问：活动结束后怎么复盘？→ 用同一套标识算分级转化率与渠道对比，断点最大的一级就是下次优化的重点。

### Q28（5.6）｜ 埋点数据和业务方的数对不上，怎么查？

- **判断**：先对齐口径（PV 按加载还是按路由、UV 按哪个 ID 去重），再查链路（埋点是否漏在分支里、是否被采样、是否被频控拦），最后查去重与补点。
- **展开**：口径不一致造成的差异通常是数倍级的，链路问题造成的差异通常是小比例；所以先问口径能最快定位性质。
- **边界**：埋点漏埋是新需求引入的（新增分支没补埋点），要靠"埋点清单随方案生成 + CR 核对"防；数据延迟会造成"当天数不全"的假差异；追问：怎么从工程上防止口径腐化？→ 埋点字典（登记标识/含义/负责人）+ 命名规范 + 开发环境对未登记标识告警 + 超期无数据埋点自动下线。

## 6. 数据管道与告警

### Q29（6.2）｜ 秒桶聚合是什么？为什么不用平均值？

- **判断**：按固定桶长（如 1 秒）累加计数与延迟样本，桶内再算 P50/P75/P95/P99；告警看 P95 而不是 avg。
- **展开**：平均延迟会被大量快请求稀释——实测事故秒 avg 只有 351ms，但 P95 已经 1119ms（3.19 倍）、P99 1992ms，**每 20 个用户就有 1 个等了 1 秒以上**；用平均值做阈值这一秒根本不会触发。
- **边界**：桶内 `floor(n*q)` 取位只是近似值，要精确分位值得用直方图 / t-digest 这类流式算法；桶越小越准但内存越高；追问：P95 与 P99 分别用在什么场景？→ P95 做告警主口径（覆盖率与稳定性平衡），P99 追长尾，`max` 只作排查线索不做阈值。

### Q30（6.2）｜ 秒桶和滑动窗口各管什么？

- **判断**：秒桶用于**定位**（哪一秒开始坏），滑动窗口用于**判定**（是否触发告警）。
- **展开**：秒桶样本少、抖动大，某一秒恰好来两个慢请求 P95 就爆表；滑动窗口把最近 N 秒样本合起来算，数值稳，但会掩盖起止时刻。
- **边界**：两者口径差异很大——实测同一段时间窗口 P95 是 418ms、事故秒是 1119ms，**差 2.7 倍**。所以"告警按窗口调阈值、排查时盯秒桶"的争论必须先说清口径；追问：为什么要强调这一点？→ 口径不一致会让"告警说没问题、排查说有问题"变成日常扯皮，规则旁边必须写明口径。

### Q31（6.3）｜ 一个合格的告警规则有哪几个要素？

- **判断**：阈值 + 连续命中次数（`consecutive`）+ 静默期（`silenceMs`）+ 恢复通知（`resolved`），四者缺一不可。
- **展开**：只有阈值会因单点抖动频繁误报；没有静默期，持续故障会被每批数据各推一次（实测事故秒 8 批 × 3 条规则 = 24 条潜在告警，收敛后只有 3 条）；没有恢复通知，告警会一直挂着没人销，值班人从此不信任告警。
- **边界**：`streak`（连续命中次数）与 `active`（是否处于触发态）是两个状态不能合并，否则指标在阈值附近抖动会出现"触发-恢复-触发"的锯齿；不命中时 `streak` 必须清零；追问：告警的时间戳该用哪个？→ 用**桶的时间戳**而不是服务器收包时间——告警描述的是数据，补数据或延迟到达时收包时间会挂错时刻。

### Q32（6.3）｜ 阈值怎么设才不是拍脑袋？

- **判断**：基线（近 N 天分位数）+ 波动容忍 + 量与率同看 + 去重抑制 + 分级路由。
- **展开**：只看率会被小样本放大（10 个请求 1 个错 = 10%）；只看量会漏掉转化率下滑；阈值随基线滚动，而不是一个固定数字。去重按"指标 + 维度"聚合，同一问题在时间窗口内只报一次。
- **边界**：阈值过严频繁误报、过松漏问题，最终都导致告警疲劳；动态基线比固定阈值更抗业务起伏（大促期间的量级变化不该触发告警）；追问：一个故障同时打爆多条规则怎么办？→ 用**依赖抑制**（数据库挂了就别再报"接口超时"），只报警最上游的那条，避免根因被下游淹没。

### Q33（6.3）｜ 告警轰炸了，从哪几处下手治？

- **判断**：按顺序上"连续命中 → 静默期 → 聚合 → 依赖抑制 → 分级路由"五层。
- **展开**：连续命中治单点抖动；静默期治持续故障的重复推送（实测 24 条潜在告警压成 3 条）；聚合把一次故障的多条规则合成一条消息；依赖抑制治"根因告警被下游淹没"；分级路由让不同级别走不同渠道。
- **边界**：**不要靠调高阈值来止轰炸**——那只会把真问题一起静默掉；也不要省掉恢复通知，那只是把负担转移给值班人；追问：怎么判断收敛是不是过头了？→ 看"漏报"：如果真实故障没有产生告警，说明连续次数或静默期太长。

### Q34（6.3）｜ 场景：给一个新服务的接口设计告警规则。

- **判断**：按"错误率 + 延迟分位值 + 流量"三类指标配置，每条规则都带连续命中、静默期、恢复通知与级别路由。
- **展开**：错误率用 P1（阈值 1% 上下），延迟用 P95（P2）与 P99（P1）双档，流量用 TPS 走低（P3）做兜底；判定基于滑动窗口而不是单秒桶；告警值的口径必须在规则旁边写明（是触发瞬间快照还是整桶值）。
- **边界**：新服务没有历史基线，先用固定阈值上线，稳定运行两周后再改成动态基线；`streak` 与 `active` 要分开维护，否则阈值附近抖动会推出锯齿状告警；追问：上线后发现告警太吵怎么办？→ 先看是误报（调连续次数/加静默期）还是真问题（修服务），不要一上来就抬高阈值。

## 7. 企业级监控工程实践

### Q35（7.2）｜ 场景：要给一个 SPA 接入前端监控 SDK，你按什么顺序做？

- **判断**：按"采集 → 传输 → 治理 → 聚合 → 告警"五段装配，每段先做最小可用，再补能力。
- **展开**：① 采集层先定义"报什么"——性能指标（FP/FCP/LCP/TTFB）、接口延迟（包裹 fetch/XHR 读 latency 与 ok）、错误（onerror + unhandledrejection + 框架钩子）、行为（事件委托采点击/曝光）；② 传输层用 `sendBeacon` + `keepalive` 兜底，阈值触发或隐藏态上报；③ 治理层加采样（热门页 5%~10%）、脱敏（URL query 里的密钥、token，userAgent 截断）、频控（按 message + 文件 + 行号聚合）；④ 接收端按秒桶聚合出 TPS / P95 / 错误率；⑤ 超阈值产生告警并溯源到人。
- **边界**：SDK 自身的体积与上报开销也要有预算（实测一次 flush 数百字节量级）；采样要按用户维度稳定（同一用户始终进/出样本），否则分位数会失真；脱敏做漏了是安全事故；追问：怎么验证 SDK 真的在收集数据？→ 起一个本地的接收端打开三个实验页，看 `/api/report` 的聚合是否更新、`/api/events` 是否有原始事件。
