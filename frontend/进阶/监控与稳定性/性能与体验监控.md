# 性能与体验监控

`性能优化` 模块讲过指标怎么定义、Lab 端怎么测。但那是在**你自己控制的机器、可控的网络**下测出来的"实验室数据"。本篇讲另一端：**真实用户监控（RUM）**——指标从千奇百怪的设备与网络里采回来，怎么采、在哪采、什么算终值，以及采集口径上最容易出错的两处。

## 一、RUM 采集与 Lab 采集的三个根本差别

同一套指标，在两端采集要处理的问题完全不同：

| 差别 | Lab（性能实验台） | RUM（本篇） |
| --- | --- | --- |
| 数据来源 | 本机无头浏览器，环境可控 | 真实用户，设备与网络不可控 |
| 采集时机 | 页面加载完成后主动读取 | SDK 可能在页面跑了一半才加载 |
| 生命周期 | 测完即取，值一次定 | LCP / CLS 是"越晚越准"的收敛值 |
| 兼容性 | 只跑一个 Chrome 版本 | 要覆盖不支持某个 entry 类型的旧浏览器 |

三个差别对应三个具体设计：**`buffered: true` 补收历史条目**、**`visibilitychange` 时定稿**、**不支持的 entry 静默跳过**。

> 摘自 `./code/monitor-lab/sdk/perf.mjs`

```js
  function observe(type, cb, extra = {}) {
    if (typeof PO !== 'function') return false
    try {
      const po = new PO(list => list.getEntries().forEach(cb))
      po.observe({ type, buffered: true, ...extra })
      observers.push(po)
      return true
    } catch {
      return false   // 该 entry 类型不被支持：直接放弃这一类，不抛
    }
  }
```

### `buffered: true` 到底补了什么

`PerformanceObserver` 默认只收到"注册之后"新产生的条目。而 SDK 往往是异步加载的（甚至用户点了按钮才初始化），等到它注册时，FCP、首次 LCP 已经过去了。

`buffered: true` 让观察者把**缓冲区里已经产生过的历史条目**一次性补给你。少这一个参数，最常见的结果就是**FCP 恒为 0**——指标看起来"很好"，其实是没采到。

### 为什么要在 `hidden` 时定稿

用户滚到页面底部看到的大图会刷新 LCP；用户点了按钮后展开的弹层可能产生新的布局位移。这些都是"页面还在用"的过程中发生的，所以真正的终值只能在用户离开时取。

> 摘自 `./code/monitor-lab/sdk/perf.mjs`

```js
  // 页面隐藏 / 卸载时收口：LCP 与 CLS 都是「越晚越准」
  function finalize() {
    metrics.lcp = Math.round(metrics.lcp)
    metrics.cls = Number(metrics.cls.toFixed(4))
    metrics.clsRaw = Number(metrics.clsRaw.toFixed(4))
    metrics.tbt = Math.round(metrics.tbt)
    return { ...metrics }
  }
```

## 二、采集器挂什么

五类 entry，一次挂完：

> 摘自 `./code/monitor-lab/sdk/perf.mjs`

```js
  function observeAll() {
    observe('paint', e => {
      if (e.name === 'first-paint') metrics.fp = Math.round(e.startTime)
      if (e.name === 'first-contentful-paint') metrics.fcp = Math.round(e.startTime)
    })
    observe('largest-contentful-paint', e => { metrics.lcp = Math.round(e.startTime) })
    observe('layout-shift', e => {
      // 无用户输入时的位移才计入 CLS；带 hadRecentInput 的位移只是「点击后的正常重排」
      metrics.clsRaw += e.value
      if (!e.hadRecentInput) metrics.cls += e.value
    })
    observe('longtask', e => {
      metrics.longtasks++
      metrics.tbt += Math.max(0, e.duration - 50)   // TBT 只算超出 50ms 的部分
    })
    observe('resource', e => {
      metrics.resources++
      metrics.resourceBytes += e.transferSize || 0
    })
    readNavigation()
  }
```

用 `PerformanceObserver` 而不是 `performance.getEntriesByType()` 轮询，理由是**时机**：`paint`、`largest-contentful-paint`、`layout-shift`、`longtask` 都是异步产生的，轮询要么采到半截的值，要么得定时器空转。观察者是事件驱动，条目产生即回调。

导航类指标仍要走 `getEntriesByType('navigation')`，因为它是页面加载时就写完的一条记录：

> 摘自 `./code/monitor-lab/sdk/perf.mjs`

```js
  function readNavigation() {
    const nav = perf && perf.getEntriesByType && perf.getEntriesByType('navigation')[0]
    if (!nav) return null
    metrics.ttfb = Math.round(nav.responseStart)
    metrics.domReady = Math.round(nav.domContentLoadedEventEnd)
    metrics.load = Math.round(nav.loadEventEnd)
    return nav
  }
```

## 三、五个指标的口径与实测

实验页故意制造了三种"坏情况"：一次 140ms 的同步循环（长任务）、一个没有预留高度的横幅（布局位移）、一个最后才出现的大块元素（把 LCP 拖到 FCP 之后）。

> 摘自 `./code/monitor-lab/scenarios/perf.mjs`（运行：`npm run perf`）

```
---- 采集到的指标：值 / 阈值 / 评级（Core Web Vitals 官方口径） ----
| 指标 | 含义                     | 实测值  | 良好阈值  | 评级 |
|------|--------------------------|---------|-----------|------|
| ttfb | 首字节时间               | 166 ms  | ≤ 800 ms  | 良好 |
| fcp  | 首次内容绘制             | 416 ms  | ≤ 1800 ms | 良好 |
| lcp  | 最大内容绘制             | 1272 ms | ≤ 2500 ms | 良好 |
| cls  | 累计布局偏移（规范口径） | 0.0116  | ≤ 0.1     | 良好 |
| tbt  | 总阻塞时间               | 90 ms   | ≤ 200 ms  | 良好 |
```

三个值得单独说的点：

1. **LCP(1272) 明显晚于 FCP(416)**：因为最大的那块内容最后才插进来。LCP 关心的是"主要内容"什么时候可见，FCP 只是"有东西可见"，两者差值就是"白等"的时间。
2. **TTFB(166) 在这台机器上很低**：本地回环没有网络延迟，所以 TTFB 只反映服务端处理时间。线上 TTFB 的大头是 DNS + TCP + TLS。
3. **评级是按官方阈值给的**，不是"我觉着快"：

> 摘自 `./code/monitor-lab/sdk/perf.mjs`

```js
// 按 Core Web Vitals 的官方口径给一次评级，方便看板上直接标色
export function ratePerf(m) {
  const rate = (v, good, poor) => (v <= good ? '良好' : v <= poor ? '需改进' : '差')
  return {
    ttfb: rate(m.ttfb, PERF_THRESHOLDS.ttfb, PERF_THRESHOLDS.ttfb * 2),
    fcp: rate(m.fcp, PERF_THRESHOLDS.fcp, PERF_THRESHOLDS.fcp * 1.8),
    lcp: rate(m.lcp, PERF_THRESHOLDS.lcp, PERF_THRESHOLDS.lcp * 1.6),
    cls: rate(m.cls, PERF_THRESHOLDS.cls, PERF_THRESHOLDS.cls * 2.5),
    tbt: rate(m.tbt, PERF_THRESHOLDS.tbt, PERF_THRESHOLDS.tbt * 3)
  }
}
```

### 关于 FID 与 INP

`FID` 已被 `INP` 取代（2024 年 3 月起 Core Web Vitals 不再包含 FID）。差别在于：

| 指标 | 测什么 | 局限 |
| --- | --- | --- |
| FID | 首次交互的**输入延迟**（从点击到事件回调开始执行） | 只测第一次、只测"开始"，不测"处理完" |
| INP | 整页生命周期内**所有交互**的响应延迟分位值（取最差的那一段） | 需要 `event` entry，且要按交互分组归因 |

采集 INP 要多挂一个观察者：

> 示意片段（无配套脚本）

```js
// 采样时用 durationThreshold 过滤掉极短的交互，避免上报量爆炸
po.observe({ type: 'event', buffered: true, durationThreshold: 40 })
```

注意 INP 不能简单地把所有 `event` 条目的 `duration` 取平均：规范要求**按交互分组**（同一轮用户输入引发的多个事件算一次交互），再取分位值。真要上 INP，建议直接接官方的 `web-vitals` 库，自己实现容易在分组逻辑上出错。

## 四、口径陷阱一：`cls` 与 `clsRaw` 不是同一个数

规范里 CLS 只统计**没有紧跟用户输入**的位移——用户点了按钮导致的重排是"预期内"的，不算布局不稳定。所以同一个页面会得出两个数：

> 摘自 `./code/monitor-lab/scenarios/perf.mjs`（运行：`npm run perf`）

```
---- 口径对照：cls 与 clsRaw 什么时候不一样 ----
| 字段   | 算法                          | 本次实测 | 说明                               |
|--------|-------------------------------|----------|------------------------------------|
| clsRaw | 累加全部 layout-shift         | 0.0116   | 把「用户操作引起的位移」也算进来   |
| cls    | 只累加 !hadRecentInput 的位移 | 0.0116   | Core Web Vitals 的规范口径         |
| 差值   | clsRaw - cls                  | 0.0000   | 本次位移没有紧跟用户输入，两者相同 |
```

采集器要**两个都存**，原因很实际：

- 看板与告警用 `cls`（规范口径），这样才与官方数据、与竞品可比；
- 排查问题时看 `clsRaw`，因为"点击后横幅把内容顶下去"这种体验问题在 `cls` 里被规范豁免了，但用户照样觉得页面在跳。

规范口径还有一个容易被忽略的细节：位移必须**在 500ms 的窗口内、且累计不超过 5% 视口高度**才合并成一次 shift。所以"连续三次小位移"可能被算成一次，而"间隔 600ms 的两次位移"一定算两次。

## 五、口径陷阱二：TBT 只算超出 50ms 的部分

页面里塞了一次 140ms 的同步循环，采到的结果：

> 摘自 `./code/monitor-lab/scenarios/perf.mjs`（运行：`npm run perf`）

```
---- 长任务与 TBT：TBT 只算超出 50ms 的部分 ----
| 指标      | 实测值 | 算法说明                                               |
|-----------|--------|--------------------------------------------------------|
| longtasks | 1      | performance 条目数（页面里塞了 1 次 140ms 的同步循环） |
| tbt       | 90 ms  | Σ max(0, duration - 50)，所以 140ms 的任务贡献约 90ms  |
```

注意：**长任务的门槛是 50ms，但计入 TBT 的是超出部分**。140ms 的任务只贡献 90ms，不是 140ms。这个换算最容易在自研采集里写错，写错的结果是 TBT 虚高。

### 长任务粒度 vs 帧间隔

`longtask` 只在**同步阻塞超过 50ms** 时产生。反过来，如果一段逻辑被切成很多 40ms 的小块，它一次长任务都不会产生，但用户会感觉页面"一顿一顿"——这属于 `性能优化` 模块讲的切片问题，监控侧看的是 `event` entry（交互延迟）而不是长任务数。

## 六、上报字段与体积

一次 `flushAll` 实际发出去的量：

> 摘自 `./code/monitor-lab/scenarios/perf.mjs`（运行：`npm run perf`）

```
---- 上报体积：监控不能自己变成性能问题 ----
| 项           | 数值                                        |
|--------------|---------------------------------------------|
| 事件条数     | 4                                           |
| 批量序列化后 | 593 B                                       |
| 单条平均     | 148 B                                       |
| 说明         | 一次 flush 的体积应该远小于一个业务接口响应 |
```

一次上报的字段设计建议：

| 字段 | 用途 | 注意 |
| --- | --- | --- |
| `appId` / `release` | 区分应用与版本 | 版本号是 sourcemap 还原的索引 |
| `route` | 页面维度聚合 | 用路由模板而不是带参 URL，否则维度爆炸 |
| `deviceType` / `networkType` | 分档看 | 低端机与 4G 是分位值恶化的主要来源 |
| 五个指标 + `rate` | 看板与告警 | 评级在端上算好，省得接收端重复实现阈值 |
| `sampleRate` | 让接收端知道怎么还原 | 采样 10% 上报时，看板要把计数乘回去 |

## 七、采集本身的开销

RUM 采集是"给业务代码旁边装了个长期运行的进程"，三条硬约束：

1. **不在主线程做重活**：`PerformanceObserver` 回调里只做累加，不序列化、不上报。本实验台的序列化发生在 `flush` 时。
2. **指标只算一次**：`finalize()` 之后不再重复计算。同一页面反复 `flush` 时，重复上报相同指标等于把流量翻倍。
3. **资源明细要限流**：`resource` entry 一条不少地全报，会随页面资源数线性增长。真实 SDK 只报 Top N 个大文件，或只报总量。
