# 前端监控实战·单页验证

## 三十秒速览

**结论：`前端监控体系.md` 讲「是什么、为什么」，本篇用一张单页把概念落地成「点了会怎么样」。** 打开 `site/monitor-lab.html`，三个面板正好对应三类数据——错误、性能、埋点，每点一下，SDK 就攒批上报到采集端，右上「刷新聚合」从 `/api/report` 拉回接收端收到的证据。跑法一行：

```
cd code/monitor-lab && npm run site     # 起采集端（端口 5189）
# 浏览器打开 http://localhost:5189/monitor-lab.html
```

## 一、验证台三块面板 = 三类数据

页头到页尾的布局就是「前端监控体系」的主线：

| 面板 | 对应篇目 | 验证什么 |
| --- | --- | --- |
| 稳定性 · 错误 | [前端监控体系](./前端监控体系.md) 第 四 节 | 六类错误六种抓法、指纹频控 |
| 体验 · 性能 | 第 五 节 | RUM 采集、LCP/CLS 越晚越准、指标评级 |
| 业务 · 埋点 | 第 六 节 | 声明式埋点、会话/曝光/点击、脱敏 |

三个面板共用**同一个 SDK 实例**（`sdk/index.mjs` 的 `init` 单例，一次初始化挂上三类采集插件），切身体会「插件只负责采、`emit` 只把事件丢进传输层」的分工。

## 二、稳定性面板：六类错误，六次点击

每一行对应 [前端监控体系](./前端监控体系.md) 第 四 节的一种抓法：

| 按钮 | 触发什么 | 验证的概念 |
| --- | --- | --- |
| 运行时错误 | 读 `undefined` 的属性，冒泡成 `window` 的 `error` | `addEventListener('error')` 兜底同步抛错 |
| Promise 拒绝 | `Promise.reject(...)` 不 catch | **不走 `onerror`**，需单独 `unhandledrejection` |
| 资源加载失败 | 把 `<img src>` 指到不存在的文件 | 资源错误**不冒泡**，只看捕获阶段 + 事件上无 message |
| 接口 404 | `fetch('/definitely-missing')` | SDK 包 `fetch`，`!ok` 记 `http` 错误（status） |
| 网络错误 | 请求 `127.0.0.1:1`（拒绝连接） | 连响应都没有，走 `catch` 记 `network` |
| 跨域脚本 | 派发 `Script error.` 事件 | 同源策略抹平细节，只剩一句 |

```text
-- 点完「一键跑全部」后，采集端 /api/events 实际收到的错误 --   （约）
script   Uncaught TypeError: Cannot read properties of undefined (reading 'foo')   fp=...@monitor-lab.html:N
promise  接口数据解析失败                                                          fp=接口数据解析失败@-:0
resource img@/missing-image.png                                                    fp=resource@/missing-image.png:0
http     /definitely-missing · 404                                                fp=http@/definitely-missing:0
network  http://127.0.0.1:1/nope · Failed to fetch                                 fp=Failed to fetch@...:0
cross    Script error.                                                             fp=Script error.@-:0
```

注意观察两个细节：**六条的错误指纹 `fp` 几乎没有一个是重复的**——即使两个错误都发生在同一页，指纹（`message + 位置 + 行号`）也能把它们分开；本页 SDK 用 `throttleMs: 0` 关掉了频控，是为了让你点一次看全六条。线上把 `throttleMs` 打开，同样的错误连点只会出端第一条。

## 三、体验面板：三类性能降级

| 按钮 | 触发什么 | 验证的概念 |
| --- | --- | --- |
| 长任务 140ms | 一条 `jam(140)` 同步循环 | 生成长任务，**TBT 只算超出 50ms 的部分**（约 90ms） |
| 无预留横幅 | 在 `body.firstChild` 插横幅 | 产生 `layout-shift`，进入 CLS 统计（且 `clsRaw` 与 `cls` 可能不同） |
| 晚到大元素 | 最后插一个占满屏的 hero | 面积最大的内容最后出现，**LCP 被刷新**、直到页面离开才定稿 |

关键：LCP 与 CLS 是**越晚越准**的收敛值。点完「晚到大元素」后如果立刻关页，采集端收到的才是终值；这也是为什么 SDK 在 `visibilitychange → hidden` 时收口上报。想亲眼验证这个时机，可以点「一键跑全部」后不要立刻关，等几秒看聚合——LCP 会比你刚点完时更晚。

## 四、业务面板：声明式埋点，业务只写属性

页面里那几个按钮和卡片**没有一行采集代码**，只写了 `data-track` / `data-expose` 属性：

```html
<button data-expose="hero-cta" data-track="cta-hero">开始体验</button>
<div class="card" data-expose="card-intro">首屏可见的卡片</div>
<button data-track="cta-card">卡片内按钮</button>
<!-- 底部还有 data-expose="footer-banner"，要滚动到才曝光 -->
```

| 触发 | 采集到的事件 | 验证的概念 |
| --- | --- | --- |
| 打开页面/点「PV」 | `pv { ref:'direct' }` | PV 挂会话上，UV 靠 `anonId` 去重 |
| 点「开始体验」 | `click { id:'cta-hero' }` | 事件委托一次监听覆盖全站 |
| 卡片进入视口 | `expose { id:'card-intro' }` | `IntersectionObserver` 采曝光，且**首屏不漏** |
| 滚到底 | `expose { id:'footer-banner' }` | 底部元素不因"滚动"漏采（对照 `scroll` 监听的坑） |
| 点「自定义事件」 | `search { keyword:'性能优化' }` | 埋点字典之外的一次性事件 |

关闭/刷新页面时会结算 `stay`（停留时长）一起上报。页面里给到的日志行和上方的 `/api/report` 能对得上，就完成了「概念 → 上报 → 接收」的闭环验证。

## 五、聚合面板：看接收端怎么把它变成可决策数字

页尾「刷新聚合」拉的是采集端 `/api/report` 的 `snapshot()`，结构大致是：

```json
{
  "kpi": { "ts": ..., "count": ..., "p95": ..., "errorRate": ... },  // 最新 1 秒桶
  "window": { ... },                                                // 最近 60 秒汇总
  "buckets": [ ... ],                                               // 逐秒桶
  "alerts": [ ... ],
  "total": 42
}
```

这个概念就够用了：**浏览器端只负责「采 + 送」，接收端负责「聚合成可决策的指标」**。秒桶、分位值、告警这些服务端聚合不上报也不在这个单页里展开——它们属于模块之外的服务端/数据分析范畴，看 `total` 在涨、`kpi.p95` 有值，就说明前面的概念全链路走通了。

## 六、自动化：三个场景由同单页驱动

为了让 `前端监控体系.md` 里的实测数字可复现，`monitor-lab.html` 支持 `?scenario=` 参数，复刻原三个实验台的自动化序列：

| 命令 | 页面 | 输出对齐 |
| --- | --- | --- |
| `npm run errors` | `/monitor-lab.html?scenario=errors` | 6 类错误字段表、指纹频控 6→4 |
| `npm run perf` | `/monitor-lab.html?scenario=perf` | 5 指标评级、`cls`/`clsRaw` 对照、TBT 90ms、一次 flush 体积 |
| `npm run track` | `/monitor-lab.html?scenario=track` | 8 条事件流、小看板、漏斗 |

三张页面（`errors-lab.html` / `perf-lab.html` / `track-lab.html`）已收拢成这一个 `monitor-lab.html`，框架代码与表单一处维护。

## 配套代码

本篇的验证台就是 `frontend/进阶/监控与稳定性/code/monitor-lab/site/monitor-lab.html`。

| 文件 | 角色 |
| --- | --- |
| `./code/monitor-lab/site/monitor-lab.html` | 单页验证台（三类面板 + 一键跑全部 + /api/report 聚合面板；`?scenario=` 驱动自动化） |
| `./code/monitor-lab/collector.mjs` | 采集端：下发本页、收 `POST /collect`、暴露 `/api/report` / `/api/events` |
| `./code/monitor-lab/sdk/index.mjs` | SDK 入口：单例 init 一次挂上错误 / 性能 / 埋点三类采集 |
| `./code/monitor-lab/scenarios/{errors,perf,track}.mjs` | 无头 Chrome 实跑本篇对齐的数字表（由 `?scenario=` 驱动） |

运行方式：`npm run site` 后浏览器打开 `/monitor-lab.html` 手动点；或 `npm run errors|perf|track` 跑自动化对照表。
