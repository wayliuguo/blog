# 数据管道与告警

前四篇解决的是"采到什么"：SDK 把错误、性能、行为变成一条条事件。本篇解决"采到之后怎么变成决策"——离散事件怎么聚合、聚合出什么数、什么数超了要报警、报了警怎么不把人吵死。

## 一、一条数据要走完四段

```
[A 采集端]            [B 传输]              [C 聚合]                [D 告警]
SDK 采样/攒批    →   批量推送/落盘    →   秒桶 + 分位值     →   阈值判定 + 收敛 + 通知
（前端浏览器）        （HTTP / beacon）     （接收端内存/时序库）    （值班人 / 工单 / 群）
```

四段各有各的失败模式，不要混着调：

| 段 | 典型故障 | 症状 |
| --- | --- | --- |
| A 采集端 | 采样过高、卸载时丢数据 | 数据量少但没有规律 |
| B 传输 | 批次过大被网关拒、重试无上限 | 接收端看到重复批次 |
| C 聚合 | 按错误粒度分桶、用平均值 | 数字看着正常，问题被掩盖 |
| D 告警 | 无收敛、无恢复 | 告警轰炸，或者告警一直挂着不消 |

本篇的采集端在 `collector.mjs`（端口 5189），它同时承担静态下发、接收上报与聚合告警三件事——生产上这三件事会拆成不同进程，但把它们放一起更容易看清数据是怎么流动的。

## 二、采集端只做三件事

接收端最忌讳"来一条就做一堆计算"。正确顺序是：先入内存、顺手落盘、再按需算。

> 摘自 `./code/monitor-lab/collector.mjs`

```js
function ingest(batch) {
  const accepted = []
  for (const raw of batch) {
    const ev = { kind: 'event', ts: raw.ts || Date.now(), ...raw }
    events.push(ev)
    accepted.push(ev)
  }
  persist(accepted)
```

落盘这步容易被省掉，但它是**唯一能重放历史的手段**：聚合逻辑改错了、告警阈值调过头了，只要有原始事件就能重跑。本实验台写 JSONL：

> 摘自 `./code/monitor-lab/collector.mjs`

```js
// 落盘：真实系统这里会是 Kafka / 日志采集器，演示里写 JSONL 足够说明「批次可以落盘重放」
function persist(batch) {
  fs.mkdirSync(DATA, { recursive: true })
  fs.appendFileSync(path.join(DATA, 'events.jsonl'), batch.map(e => JSON.stringify(e)).join('\n') + '\n')
}
```

生产上的对应物：**采集端（前端）→ 网关（限流、鉴权）→ 消息队列（Kafka，天然削峰 + 可重放）→ 消费者（聚合入库）**。队列这一环的价值在于，接收端重启或变慢时，数据不会丢，只是晚到。

## 三、聚合第一步：秒桶

原始事件是"一个时间戳一个点"，没法直接算指标。第一步先按**固定长度的时间桶**归拢——本实验台用 1 秒：

> 摘自 `./code/monitor-lab/aggregate.mjs`

```js
// 秒桶：把事件按 ts 归到 [ts, ts+sizeMs) 的桶里，桶内先算计数，延迟留样本后算
export function bucketize(events, sizeMs = 1000) {
  const map = new Map()
  for (const e of events) {
    const ts = Math.floor(e.ts / sizeMs) * sizeMs
    let b = map.get(ts)
    if (!b) {
      b = { ts, count: 0, errors: 0, pv: 0, byKind: {}, latency: [] }
      map.set(ts, b)
    }
    b.count++
    const kind = e.kind || e.type || 'unknown'
    b.byKind[kind] = (b.byKind[kind] || 0) + 1
    if (kind === 'error' || e.ok === false) b.errors++
    if (e.name === 'pv') b.pv++
    if (typeof e.latency === 'number') b.latency.push(e.latency)
  }
  return [...map.values()].sort((a, b) => a.ts - b.ts)
}
```

**桶长选多长**，取决于你要多快发现问题：

| 桶长 | 适用 | 代价 |
| --- | --- | --- |
| 1 秒 | 故障发现、接口监控 | 存储量大，需要降采样保存 |
| 10 秒 / 1 分钟 | 常规看板、日报 | 突发尖峰被平均掉 |
| 1 小时 | 容量规划、成本趋势 | 完全看不出口径内的抖动 |

真实的时序库通常两者都存：**秒级数据保留几天**（用于事后定位），**小时级数据长期保留**（用于趋势）。这就是"降采样（downsampling）"。

## 四、聚合第二步：分位值，因为平均值会骗人

桶里攒了样本之后，先算出可读指标：

> 摘自 `./code/monitor-lab/aggregate.mjs`

```js
// 桶 → 可读指标：TPS / 平均延迟 / P95 / 错误率
export function summarizeBucket(b) {
  const avg = b.latency.length ? b.latency.reduce((a, c) => a + c, 0) / b.latency.length : 0
  return {
    ts: b.ts,
    count: b.count,
    tps: b.count,
    avg: Math.round(avg),
    p50: percentile(b.latency, 0.5),
    p75: percentile(b.latency, 0.75),
    p95: percentile(b.latency, 0.95),
    p99: percentile(b.latency, 0.99),
    errorRate: b.count ? b.errors / b.count : 0,
    errors: b.errors,
    pv: b.pv,
    max: b.latency.length ? Math.max(...b.latency) : 0
  }
}
```

分位值本身很简单：

> 摘自 `./code/monitor-lab/aggregate.mjs`

```js
// q 取 0.5 / 0.75 / 0.95 / 0.99；样本为空返回 0
export function percentile(values, q) {
  if (!values.length) return 0
  const sorted = [...values].sort((a, b) => a - b)
  const idx = Math.min(sorted.length - 1, Math.floor(sorted.length * q))
  return sorted[idx]
}
```

注意这只是**桶内近似**（`floor(n*q)` 取位，不做线性插值），适合告警判断；要精确分位值得用直方图或 t-digest 这类流式算法，理由是在高基数下没法把所有样本都留在内存里。

为什么必须看分位值，实测最能说明问题：

> 摘自 `./code/monitor-lab/scenarios/pipeline.mjs`（运行：`npm run pipeline`）

```
---- 为什么不能只看平均值：事故那一秒 avg 看着还行，P95/P99 已经爆了 ----
| 指标 | 事故秒的值 | 说明                                      |
|------|------------|-------------------------------------------|
| avg  | 351 ms     | 被大量快请求稀释，看不出问题              |
| P95  | 1119 ms    | 是 avg 的 3.19 倍——慢的那 5% 才是用户痛点 |
| P99  | 1992 ms    | 最慢的 1% 样本                            |
| max  | 2173 ms    | 单个最慢请求                              |
```

事故那一秒里 400 个请求有 65% 还是很快的（基础延迟 180ms 左右），所以 `avg` 只有 351ms；但**每 20 个用户里就有 1 个等了 1 秒以上**。用平均值做告警阈值，这一秒大概率不会触发。

分位值的读法：

| 分位 | 回答的问题 | 适合谁看 |
| --- | --- | --- |
| P50 | 一半人比这快 | 容量规划（典型体验） |
| P75 | 四分之三的人比这快 | 常规看板 |
| P95 | 20 个人里有 1 个比这慢 | **告警主口径** |
| P99 | 100 个人里有 1 个比这慢 | 追查长尾、发现极端个例 |
| max | 最慢的那一个 | 排查问题时的线索，不适合做阈值 |

## 五、秒桶与滑动窗口各管什么

秒桶的缺点是**太灵敏**：某一秒恰好来了两个慢请求，P95 就爆表。所以告警不该直接看单桶，而要看滑动窗口。

> 摘自 `./code/monitor-lab/aggregate.mjs`

```js
// 滑动窗口汇总：把最近 windowMs 的样本合起来算一次全局分位值（告警看的就是这个）
export function rollup(events, windowMs = 60000, now = Date.now()) {
  const from = now - windowMs
  const recent = events.filter(e => e.ts >= from)
  const latency = recent.filter(e => typeof e.latency === 'number').map(e => e.latency)
  const errors = recent.filter(e => (e.kind || e.type) === 'error' || e.ok === false).length
  return {
    window: windowMs,
    samples: recent.length,
    count: recent.length,
    tps: Math.round(recent.length / (windowMs / 1000)),
    avg: latency.length ? Math.round(latency.reduce((a, c) => a + c, 0) / latency.length) : 0,
    p50: percentile(latency, 0.5),
    p75: percentile(latency, 0.75),
    p95: percentile(latency, 0.95),
    p99: percentile(latency, 0.99),
    max: latency.length ? Math.max(...latency) : 0,
    errorRate: recent.length ? errors / recent.length : 0
  }
}
```

两者的分工：

| 口径 | 优点 | 缺点 | 用在哪 |
| --- | --- | --- | --- |
| 秒桶 | 能定位到"哪一秒开始坏的" | 样本少，抖动大 | 看板曲线、事后定位 |
| 滑动窗口 | 数值稳，适合判定 | 掩盖起止时刻 | 告警判定 |

**告警用窗口、定位用秒桶**，这个分工要写进团队约定，否则会出现"告警阈值按窗口调的，但排查的人盯着秒桶说没超"的扯皮。

## 六、告警四要素

一个能进生产的告警规则，光有阈值是不够的：

> 摘自 `./code/monitor-lab/alert.mjs`

```js
export const DEFAULT_RULES = [
  { id: 'latency-p95', level: 'P2', metric: 'p95', op: '>', threshold: 120, consecutive: 2, silenceMs: 5000, title: '接口 P95 延迟超阈，存在变慢风险' },
  { id: 'latency-p99', level: 'P1', metric: 'p99', op: '>', threshold: 400, consecutive: 1, silenceMs: 5000, title: '接口 P99 延迟严重超阈' },
  { id: 'error-rate', level: 'P1', metric: 'errorRate', op: '>', threshold: 0.01, consecutive: 1, silenceMs: 5000, title: '错误率超阈，可能有故障' },
  { id: 'lcp-p75', level: 'P2', metric: 'lcpP75', op: '>', threshold: 2500, consecutive: 2, silenceMs: 30000, title: 'LCP P75 超 2.5s，首屏体验差' },
  { id: 'tps-drop', level: 'P3', metric: 'tps', op: '<', threshold: 5, consecutive: 3, silenceMs: 30000, title: 'TPS 异常走低，疑似流量中断' }
]
```

| 要素 | 作用 | 不写会怎样 |
| --- | --- | --- |
| `threshold` + `op` | 判定条件 | 没有判定就没有告警 |
| `consecutive` | 连续命中几次才推 | 单点抖动就报，误报率高 |
| `silenceMs` | 同一规则最小推送间隔 | 持续故障时重复轰炸 |
| `resolved` | 指标回到阈值内推恢复通知 | 告警挂着没人销，值班人失去信任 |

判定逻辑：

> 摘自 `./code/monitor-lab/alert.mjs`

```js
      if (hit) {
        s.streak++
        const cooled = ts - s.lastFiredAt >= (rule.silenceMs ?? 60000)
        // 连续命中达到门槛、且不在静默期内 → 才真的推一条告警
        if (s.streak >= rule.consecutive && (!s.active || cooled)) {
          const alert = { id: rule.id, level: rule.level, state: 'firing', ts, metric: rule.metric, value, threshold: rule.threshold, consecutive: s.streak, title: rule.title }
          s.active = true
          s.lastFiredAt = ts
          log.push(alert)
          out.push(alert)
        }
      } else if (s.active) {
        // 指标回到阈值内 → 推一条恢复通知，避免「有告警无恢复」
        const alert = { id: rule.id, level: rule.level, state: 'resolved', ts, metric: rule.metric, value, threshold: rule.threshold, title: rule.title }
        s.active = false
        s.streak = 0
        log.push(alert)
        out.push(alert)
      } else {
        s.streak = 0
      }
```

三个容易写错的地方：

1. **`s.active` 与 `s.streak` 是两回事**：`streak` 是"连续命中次数"，`active` 是"这条告警当前是否处于触发态"。少了 `active`，指标在阈值附近抖动时会出现"触发-恢复-触发-恢复"的锯齿。
2. **恢复要显式发**，不能只靠"不再发触发告警"来隐含表达。值班人需要一条明确的"线上已恢复"消息。
3. **`streak` 在不命中时要清零**（`else` 分支），否则"命中一次、隔很久再命中一次"也会凑够连续次数。

造一段"两秒正常 → 一秒事故 → 一秒恢复"的数据，每批 50 条上报，共 32 次 HTTP 请求：

> 摘自 `./code/monitor-lab/scenarios/pipeline.mjs`（运行：`npm run pipeline`）

```
---- 事件流：4 秒共上报 1600 条（每批 50 条，共 32 次 HTTP 请求） ----

---- 秒桶聚合：每秒一个桶，桶内先计数再算分位值 ----
| 桶   | 状态 | 事件数 | TPS | avg    | P50    | P95     | P99     | 错误率 |
|------|------|--------|-----|--------|--------|---------|---------|--------|
| 1 秒 | 正常 | 400    | 400 | 66 ms  | 58 ms  | 69 ms   | 289 ms  | 0.25%  |
| 2 秒 | 正常 | 400    | 400 | 64 ms  | 59 ms  | 69 ms   | 281 ms  | 0.00%  |
| 3 秒 | 事故 | 400    | 400 | 351 ms | 228 ms | 1119 ms | 1992 ms | 7.50%  |
| 4 秒 | 恢复 | 400    | 400 | 70 ms  | 55 ms  | 66 ms   | 357 ms  | 0.25%  |
```

注意 `TPS` 四秒都是 400：**这次故障是"变慢"，不是"挂掉"**。只看 TPS 或只看成功率，这次事故完全不会被发现——它只有延迟指标能揭示。

滑动窗口（最近 60 秒）把两个正常秒、一个事故秒、一个恢复秒合在一起看：

> 摘自 `./code/monitor-lab/scenarios/pipeline.mjs`（运行：`npm run pipeline`）

```
---- 滑动窗口（最近 60s）汇总 ----
| 样本 | TPS | avg    | P50   | P75    | P95    | P99     | max     | 错误率 |
|------|-----|--------|-------|--------|--------|---------|---------|--------|
| 1600 | 27  | 138 ms | 61 ms | 187 ms | 418 ms | 1596 ms | 2173 ms | 2.00%  |
```

窗口的 P95 是 418ms，秒桶事故那秒是 1119ms。**同一段时间，两个口径差了 2.7 倍**，这就是为什么"口径"必须写在告警规则旁边。

读这张表要注意**"指标值"是触发那一刻的快照**：事故秒只收进第一批 50 条时就判定出来了，所以 p99 报的是 2173ms（首批样本里的最慢值），而事故秒整桶跑完后的 P99 是 1992ms。两个数不矛盾，只是口径不同——**告警值回答"触发瞬间有多糟"，桶值回答"这一秒整体有多糟"**。

还有一处设计要说明：告警的 `ts` 用的是**桶的时间戳**，不是服务器收到批次的时间。告警描述的是数据本身，用收包时间会在补数据或延迟到达时把告警挂到错误的时刻上。

> 摘自 `./code/monitor-lab/collector.mjs`

## 九、收敛：24 条重复告警被压成 3 条

事故秒里一共上报了 8 批，每批都会评估一次告警。`consecutive` + `silenceMs` 一起作用的效果：

> 摘自 `./code/monitor-lab/scenarios/pipeline.mjs`（运行：`npm run pipeline`）

```
---- 收敛效果：事故秒内评估了 8 批，静默期把重复告警压掉 ----
| 口径             | firing 条数 | resolved 条数 | 说明                                 |
|------------------|-------------|---------------|--------------------------------------|
| 有静默期（实际） | 3           | 3             | 同一规则在 5000ms 内只推一次         |
| 无静默期（假设） | 24          | 3             | 事故秒 8 批次 × 3 条规则，会各推一次 |
```

8 批 × 3 条命中规则 = 24 条潜在告警，实际只推了 3 条。少了静默期，值班人 1 秒内会收到 24 条消息，然后开始忽略所有告警——**告警轰炸的最终结局一定是"没人看告警"**。

真实的收敛手段比这更丰富：

| 手段 | 做法 | 抑制哪种噪声 |
| --- | --- | --- |
| 连续命中 | 命中 N 次才推 | 单点抖动 |
| 静默期 | 同规则 N 秒内只推一次 | 持续故障的重复推送 |
| 聚合 | 同一次故障的多条规则合成一条消息 | 一个故障引发的告警风暴 |
| 依赖抑制 | 数据库挂了就别再报"接口超时" | 根因告警被下游淹没 |
| 值班排班 | 按级别路由到不同渠道 | 所有事都打扰所有人 |

其中**依赖抑制**最容易被忽略：一次数据库故障能同时打爆"接口错误率""接口延迟""订单量下跌"三条规则，最好的做法是只报警最上游的那条。

## 十、分级、通知与溯源

| 级别 | 判定参考 | 通知方式 | 期望响应 |
| --- | --- | --- | --- |
| P0 | 核心链路不可用 / 影响交易 | 电话 + 群 + 工单 | 立即（分钟级） |
| P1 | 错误率或 P99 严重超阈 | 群 + 工单 | 尽快（半小时内有人接） |
| P2 | P95 超阈 / LCP 恶化 | 群消息 | 工作时间处理 |
| P3 | 趋势类（TPS 走低、容量上升） | 日报 / 看板 | 排期优化 |

分级的关键不是级别名字，而是**"谁在什么时候必须做什么"**。没有明确责任人的告警等于没有告警。

溯源到人包括两层：

1. **事件带上 `release`（版本号）**，能对应到某次发布、某个提交；
2. **规则与看板有 owner 字段**，改阈值要走评审，避免"阈值被悄悄调高，故障被静默"。

## 十一、成本控制：三个旋钮

数据管道最怕的不是技术，是账单。三个旋钮按顺序拧：

1. **采样**：先在**采集端**把量降下来（`前端监控 SDK 实现` 里实测 10% 采样只保留 198/2000 条）。这是唯一能省掉全链路成本的旋钮。
2. **预聚合**：接收端把明细转成秒桶后，**原始明细只保留短期**（比如 3~7 天），桶数据长期保留。查询走桶，追查才去翻明细。
3. **保留期分层**：秒级 7 天、分钟级 90 天、小时级 2 年。这是所有可观测性平台的通用做法。

反过来，有三个旋钮**不要拧**：错误量（本来就不大，采样会漏掉偶发崩溃）、告警判定用的窗口（改窗口等于改口径，会让历史数据不可比）、恢复通知（省掉它只是把负担转移给值班人）。

## 配套代码

本篇的可运行示例在仓库 `frontend/进阶/监控与稳定性/code/monitor-lab/`。

| 文件 | 演示什么 | 对应小节 |
| --- | --- | --- |
| `./code/monitor-lab/collector.mjs` | 采集端：批量接收上报、落盘 JSONL、按最新秒桶评估告警、对外暴露 `/api/report` | 二、采集端只做三件事 |
| `./code/monitor-lab/aggregate.mjs` | 秒桶归并、桶内分位值、滑动窗口汇总 | 三、聚合第一步：秒桶 |
