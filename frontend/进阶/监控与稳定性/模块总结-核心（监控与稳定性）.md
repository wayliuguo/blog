## 知识主线（一句话）

主轴是**「把线上状态变成可决策的数据」**：01 定监控的三大视角（稳定性 / 用户体验 / 业务）与七步闭环，02 把采集收成一个开销可控的 SDK，03~05 分别把错误、性能、行为三类数据的采法与口径讲透，06 解决"采回来后怎么变成判定与告警"（秒桶 → 分位值 → 告警四要素 → 收敛），07 把整条链路装配成能进生产的工程闭环。

## 高频核心点

### 01 监控平台

**监控三大目标**

- **稳定性**：JS 错误、资源异常、接口错误、白屏四类异常
- **用户体验**：TTFB/FP/FCP/FMP/FID、卡顿（>50ms 长任务）等加载与响应指标
- **业务**：PV、UV、页面停留时长；**七步闭环**：定目标 → 采集 → 传输存储 → 分析可视化 → 告警定位优化

**错误收集方式**

- `try/catch` 手动捕获（信息最全但侵入）；`window.onerror` 捕未包裹的运行时错误；`unhandledrejection` 兜底 Promise；资源 error 须捕获阶段监听（资源错误不冒泡）；框架专项 `Vue config.errorHandler`
- **1×1 gif 打点**：防跨域、不带 Cookie、不阻塞页面加载

**性能与告警**

- `getEntriesByType('navigation')` 算网络耗时；`PerformanceObserver` 监听 paint/layout-shift/longtask
- 分级告警按严重程度配渠道；阈值结合基线防误报漏报；去重抑制防短时轰炸；溯源到人

### 02 前端监控 SDK 实现

- **四层分工**：采集层（错误/性能/行为各自独立）、传输层（采样→攒批→投递→重试→溢出丢弃）、治理层（采样在传输层、脱敏与频控在采集层）、生命周期
- **单例**：多处 `init` 只返回首个实例，否则重复绑监听、重复上报；**插件化**：采集器共用 `emit(event)` 一个签名
- **传输四机制**：攒批（12 条 12→3 次请求）、采样（放在入队口丢弃）、重试（maxRetry 耗尽计入 dropped）、溢出（受 maxQueue 限制丢最旧）
- **投递顺序**：`sendBeacon` 优先（卸载可送达、无响应）→ `fetch + keepalive` 兜底（64KB 上限）→ 同步 XHR 不可用
- **生命周期**：用 `visibilitychange → hidden` 而非 unload（移动端 unload 常不触发）；LCP/CLS 越晚越准、离开时定稿
- **治理口径**：错误不采样、埋点可低比例、长任务 1%~5%；URL 只留 path、文本截断、表单值不采；频控按指纹（message+位置+行号）

### 03 错误监控

**六类错误与捕获**

- 运行时（error，有行号 stack）· 未处理 Promise（unhandledrejection，只有 reason.stack）· 资源加载（error + capture）· 接口（`!res.ok` 记 status）· 网络（fetch catch，如 Failed to fetch）· 跨域（只剩 Script error.，需 crossorigin+CORS）

**`window.onerror` 三个坑与 Promise/接口**

- 资源错误不冒泡须捕获阶段、`Script error.` 是同源策略、行号是整页行号
- `unhandledrejection` 不触发 window.onerror 须单列；`reason` 可能非 Error 须 `String()` 兜底
- 网络错误与 HTTP 错误字段不同、看板分开统计；catch 上报后必须 `throw` 否则吞异常

**指纹、频控与 sourcemap**

- **指纹 = message + 出错位置 + 行号**；资源/接口错误没 message，必须把 src/url 算进指纹否则塌成一条
- 被频控拦下的事件仍进 captured、只打 throttled 标记；线上带 count 与指纹复位
- 用 `release` 版本号把 map 与代码绑定；**服务端还原优于客户端**（客户端暴露 sourcemap）
- 框架兜底：Vue `config.errorHandler`；React 错误边界只覆盖渲染错误、不含事件处理器，不能替代全局监听

### 04 性能与体验监控

- **与 Lab 采集三差别**：`buffered: true` 补收历史、`hidden` 时定稿、不支持的 entry 静默跳过
- **指标口径**：`PerformanceObserver` 事件驱动优于轮询；**FID 已被 INP 取代**，INP 按交互分组不能取平均；**CLS 豁免 `hadRecentInput` 的位移**，同时存 cls 与 clsRaw；**TBT = Σ max(0, duration − 50)**
- **上报字段**：`appId` / `release`（sourcemap 索引）/ route（用模板避免维度爆炸）；设备与网络档位
- **自身开销**：指标只算一次防重复 flush；资源明细只报 Top N；低端机与弱网是分位值恶化主因

### 05 埋点与行为分析

- **三种埋法**：代码埋点口径最准要发版 · 可视化不改代码但随改版失效 · 无埋点覆盖全但噪声大；实践是核心路径代码埋点 + 长尾可视化 + 兜底无埋点
- **声明式埋点**：业务只写 `data-track` / 点击走事件委托覆盖动态 DOM、与结构解耦；须靠埋点字典约束命名
- **会话**：按 30 分钟不活跃切分；判定放在 track() 入口、任何事件刷新活跃时间
- **指标口径**：PV 按页面加载 vs 路由切换差数倍；UV 按不同 ID 去重结果不同；停留用 enter/stay 双写兜底关页
- **曝光**：用 `IntersectionObserver` 不监听 scroll、`unobserve` 保证只报一次、entry.time 是进视口时刻
- **漏斗与归因**：靠统一命名才成立；UTM 四字段 source/medium/campaign/content；首次与末次归因提前定义
- **脱敏治理**：URL 只留 path、文本截断、表单值不采；脱敏放采集口而非接收端

### 06 数据管道与告警

- **四段管道分离调**：采集端 · 传输 · 聚合 · 告警，四段失败模式不同；落盘（JSONL/Kafka）是唯一能重放历史的手段
- **秒桶 + 分位值**：按固定桶长归拢、桶内先计数再算分位值（`floor(n*q)` 近似）；**平均值掩盖长尾**（事故秒 avg 351ms vs P95 1119ms）；告警主用 P95、P99 追长尾
- **秒桶 vs 滑动窗口**：秒桶定位"哪一秒开始坏"（样本少抖动大）、滑动窗口判告警（数值稳掩起止）
- **告警四要素**：`threshold` + `op` 判定 · `consecutive` 连续命中抑制抖动 · `silenceMs` 防轰炸 · `resolved` 显式恢复通知；`streak` 不命中要清零；ts 用桶时间戳
- **收敛**：连续命中 / 静默期 / 聚合 / 依赖抑制（避免根因告警被下游淹没）/ 值班排班

### 07 企业级性能与监控工程实践

- **工程闭环四段**：前端 Agent（采集/传输/治理）→ 传输层（sendBeacon / fetch keepalive）→ 接收端聚合（秒桶 + 分位值 + 去重 + 阈值/基线）→ 决策端（报表/告警/趋势，可溯源到人）
- **Agent 做成可复用 SDK**：采集（性能 / 接口延迟包裹 fetch / 错误 / 行为）；传输优先 sendBeacon 兜底 keepalive；治理采样 5%~10%、脱敏、频控聚指纹
- **分位值才是体感**：P95/P99 代表"绝大多数用户"，比 avg 更该作为告警判定量；两级聚合（每秒算 P95 再对最近 60s 二次聚合）
- **告警"准"三要素**：阈值、去重（同一秒同指标去重）、**动态基线**（抗业务起伏）
- **闭环回归**：优化后看曲线是否下降，以"指标回归到阈值内"为准而非"感觉快了"
