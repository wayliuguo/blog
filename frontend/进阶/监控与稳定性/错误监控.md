# 错误监控

## 一、六类错误，六种抓法

先说结论：**没有一个 API 能抓全**，必须按错误来源分别挂监听。

| 类别 | 典型场景 | 捕获方式 | 关键字段 |
| --- | --- | --- | --- |
| 运行时错误 | 读 `undefined` 的属性 | `window.addEventListener('error')` | `message` `filename` `lineno` `colno` `error.stack` |
| 未处理 Promise | `.then` 里抛错、`await` 没 catch | `window.addEventListener('unhandledrejection')` | `reason.message` `reason.stack` |
| 资源加载失败 | img / script / link 挂了 | 同一 `error` 事件，但**必须 `capture = true`** | `event.target.tagName` `src` |
| 接口错误 | 后端 404 / 500 | 包裹 `fetch` / `XMLHttpRequest` | `url` `status` |
| 网络错误 | DNS 失败、连接被拒、断网 | 同上，走 `catch` 分支 | `url` `message`（如 `Failed to fetch`） |
| 跨域脚本错误 | 第三方 CDN 脚本出错 | 只能拿到 `Script error.` | 细节全无，需 `crossorigin` + CORS |

实测一遍，看捕获到的原始事实：

> 摘自 `./code/monitor-lab/scenarios/errors.mjs`（运行：`npm run errors`）

```
---- 真实浏览器捕获到 6 条错误事件，逐条看关键字段 ----
| 捕获方式           | kind         | 关键字段                                                                                                              | 指纹                                                                                                              |
|--------------------|--------------|-----------------------------------------------------------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------|
| unhandledrejection | promise      | 接口数据解析失败 / — / —                                                                                              | 接口数据解析失败@-:0                                                                                              |
| error(capture)     | resource     | img / http://127.0.0.1:51341/missing-image.png                                                                        | resource@http://127.0.0.1:51341/missing-image.png:0                                                               |
| error              | script       | Uncaught TypeError: Cannot read properties of undefined (reading 'foo') / http://127.0.0.1:51341/errors-lab.html / 37 | Uncaught TypeError: Cannot read properties of undefined (reading 'foo')@http://127.0.0.1:51341/errors-lab.html:37 |
| error              | http         | /definitely-missing / 404                                                                                             | http@/definitely-missing:0                                                                                        |
| error              | network      | http://127.0.0.1:1/nope / Failed to fetch                                                                             | Failed to fetch@http://127.0.0.1:1/nope:0                                                                         |
```

（端口是每次运行时随机分配的，你跑出来的端口号会不一样。）

六条里只有一条（`script`）能拿到完整的文件与行号。剩下五条各有各的"缺"：Promise 没有文件名、资源错误没有 message、跨域错误什么都没有。

## 二、`window.onerror` 的三个坑

### 坑 1：资源错误不冒泡，必须在捕获阶段监听

`img`、`script`、`link` 加载失败时触发的是**资源元素的 `error` 事件**，它**不冒泡**。默认的 `addEventListener('error', fn)` 挂在冒泡阶段，永远收不到。

判据是"事件对象上有没有 `target.tagName`"：有则是资源错误，没有则是脚本错误。

> 摘自 `./code/monitor-lab/sdk/errors.mjs`

```js
  // 坑：资源错误不冒泡，必须在捕获阶段监听；此时 event 上没有 message，只有 target
  function onError(ev) {
    const target = ev.target
    if (target && target !== win && target.tagName) {
      return push({ kind: 'resource', tag: String(target.tagName).toLowerCase(), src: target.src || target.href })
    }
```

对应地，监听时要显式传第三参：

> 摘自 `./code/monitor-lab/sdk/errors.mjs`

```js
win.addEventListener('error', onError, true)
```

### 坑 2：`Script error.` 是浏览器在保护跨域脚本

第三方 CDN 的脚本出错时，出于安全考虑浏览器不会把错误细节传给不同源的页面，只给一句 `Script error.`。**这不是代码写错了，是同源策略在生效。**

要拿到细节，两条都得满足：

1. `<script src="..." crossorigin="anonymous">` 带上 `crossorigin`；
2. CDN 响应头带 `Access-Control-Allow-Origin`。

做不到时，退路是**在服务端用 sourcemap 做一次位置还原**——但前提是能拿到位置，而 `Script error.` 连位置都没有，所以最终只能靠"把关键脚本自建同源"来解决。

### 坑 3：三个容易记混的参数

`onerror` 的回调参数是 `(message, source, lineno, colno, error)`：

- `message` 已经被浏览器加了前缀（`Uncaught TypeError: ...`），自己别再拼一次；
- `lineno` 是**整页**的行号（含 HTML 部分），压缩后与源码行号对不上；
- `error` 在现代浏览器里才是真正的 `Error` 对象；老浏览器只有前三个参数，所以要用 `error && error.stack` 兜。

## 三、Promise 拒绝不走 `onerror`

这是最容易漏的一类：`Promise.reject(new Error('接口数据解析失败'))` 不会触发 `window.onerror`，只在控制台打个警告。

> 摘自 `./code/monitor-lab/site/errors-lab.html`

```js
  // 2. Promise 未处理拒绝：不会走 window.onerror，必须单独监听 unhandledrejection
  log('2) 未处理的 Promise 拒绝')
  Promise.reject(new Error('接口数据解析失败'))
```

监听回调里要防两件事：

> 摘自 `./code/monitor-lab/sdk/errors.mjs`

```js
  function onRejection(ev) {
    const r = ev.reason
    return push({ kind: 'promise', message: (r && r.message) || String(r), stack: r && r.stack })
  }
```

- `reason` 不一定是 `Error`，可能是字符串、对象、甚至 `undefined`（如 `Promise.reject()`），必须 `String(r)` 兜底；
- 实测抓到的这条 Promise 错误**没有 `filename` 与 `lineno`**，只有 `reason.stack` 里的栈信息，所以指纹里位置字段是空的（`接口数据解析失败@-:0`）——这也说明**位置信息不能作为唯一索引**。

## 四、接口错误：包一次 `fetch`，业务无感

接口错误属于"业务自己 catch 掉了，但监控必须知道"的类型。做法是包装全局 `fetch`：

> 摘自 `./code/monitor-lab/sdk/errors.mjs`

```js
  // 接口错误：包裹 fetch，业务代码无感
  function wrapFetch(original) {
    return async function patched(input, init) {
      const started = Date.now()
      try {
        const res = await original.call(this, input, init)
        if (!res.ok) push({ kind: 'http', url: String(input), status: res.status, duration: Date.now() - started })
        return res
      } catch (err) {
        push({ kind: 'network', url: String(input), message: err && err.message, duration: Date.now() - started })
        throw err
      }
    }
  }
```

两个细节：

- **`!res.ok` 只覆盖 HTTP 错误**（4xx/5xx）。业务码错误（HTTP 200 但 `{code: 500}`）只在响应体里，需要业务自己调 `report` 上报。
- **`catch` 里上报完要 `throw err`**，否则会把业务的错误处理链条吃掉，变成"监控吞了异常"。
- 实测里 404 报的是 `kind: http, status: 404`，连接被拒报的是 `kind: network, message: Failed to fetch`——两者字段不同，看板上要分开统计。

## 五、指纹与频控：6 条捕获压成 4 条出端

错误量最大的场景不是"错误种类多"，而是"同一个错误被循环触发几千次"（比如渲染循环里每帧报一次）。**全量上报会把接收端和告警系统一起打爆。**

做法是给每条错误算个"指纹"，指纹相同的短时间内只报一次。指纹取 `message + 出错位置 + 行号`：

> 摘自 `./code/monitor-lab/sdk/errors.mjs`

```js
// 指纹 = 错误信息 + 出错位置 + 行号。同一条错误短时间内只应报一次，避免告警轰炸
// 资源/接口错误没有 message，必须把 src / url 算进指纹，否则「所有资源错误」会塌成同一条
export function fingerprintOf(e) {
  const where = e.filename || e.src || e.url || '-'
  return `${e.message || e.kind}@${where}:${e.lineno || 0}`
}
```

注意第二行注释里的坑：**资源错误与接口错误没有 `message`**。如果指纹只取 `message` + `filename`，那么页面上所有图片加载失败会塌成同一条 `resource@-:0`，不同类型、不同资源的错误会被错误地合并。实测把 `src` / `url` 算进去之后：

> 摘自 `./code/monitor-lab/scenarios/errors.mjs`（运行：`npm run errors`）

```
---- 指纹与频控：同一条错误连触发 3 次，只有第一次出端 ----
| 轨迹 | kind     | 指纹                                          | 是否出端   |
|------|----------|-----------------------------------------------|------------|
| #1   | resource | resource@/a.png:0                             | 已上报     |
| #2   | script   | Cannot read properties of undefined@app.js:12 | 已上报     |
| #3   | script   | Cannot read properties of undefined@app.js:12 | 被频控拦下 |
| #4   | script   | Cannot read properties of undefined@app.js:12 | 被频控拦下 |
| #5   | script   | 其他错误@app.js:99                            | 已上报     |
| #6   | promise  | 接口数据解析失败@-:0                          | 已上报     |
| 捕获条数     | 6    |
| 实际上报条数 | 4    |
| 频控拦截     | 2    |
```

被拦下的两条（#3、#4）**仍然进入了 `captured` 列表**，只是打了 `throttled` 标记没有出端。这个区分很重要：本地调试要看到全部，线上要压量，两者用同一个采集器、不同的出口策略。

> 摘自 `./code/monitor-lab/sdk/errors.mjs`

```js
  function push(err) {
    const ev = { type: 'error', ts: Date.now(), ...err }
    ev.fp = fingerprintOf(ev)
    captured.push(ev)

    const last = seen.get(ev.fp)
    if (throttleMs && last && ev.ts - last < throttleMs) {
      ev.throttled = true
      return ev
    }
    seen.set(ev.fp, ev.ts)
    emit(ev)
    return ev
  }
```

线上还有两条必须加的规则：**上报要带出现次数**（`count`），否则你看不出"这条错误其实每分钟发生 800 次"；**要有复位逻辑**，比如 5 分钟没再出现就把指纹从表里清掉，否则长驻页面上同样的错误只会报首次那一次。

## 六、栈对不上源码，靠 sourcemap 还原

生产环境的栈长这样：`at n (app.a1b2c3.js:1:48213)`。文件名带哈希、行号列号都在第一行里。

还原方案有两种，都要求**构建产物里保留 sourcemap**：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| 服务端还原 | 上报原始 `filename/lineno/colno`，接收端用 sourcemap 解析 | 需要保存每次发布对应的 map 文件 |
| 客户端还原 | 错误发生时就 `fetch` map 并解析 | 体积大，且会把 sourcemap 暴露给用户 |

主流做法是服务端还原，并且**把 sourcemap 与代码版本号绑定**：监控事件里带上 `release`（如 git commit），接收端按 `release` 找对应的 map。没有版本号，还原结果会指向错误的那一版代码。

## 七、框架层再兜一层

框架会自己"吃掉"一部分错误，全局监听收不到：

| 框架 | 兜底钩子 | 覆盖范围 |
| --- | --- | --- |
| Vue 2/3 | `app.config.errorHandler` | 组件渲染、生命周期、`watch` 回调 |
| Vue 3 | `app.config.warnHandler` / `onErrorCaptured` | 警告与局部捕获 |
| React | 错误边界组件（`componentDidCatch` / `getDerivedStateFromError`） | 子树渲染错误（**事件处理器与异步代码不在内**） |

注意 React 错误边界**不覆盖事件处理器、异步回调与 SSR**，所以它不能替代全局监听，只能作为补充：渲染期错误交给错误边界（因为只有它能给你"出错的那个组件树"），其他错误交给 `window.onerror`。
