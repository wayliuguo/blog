# 前端监控体系

## 三十秒速览

**结论：前端监控只回答三个问题——稳定性（有没有坏）、体验（快不快）、业务（用户在做什么）。** 所有采集、上报、指标设计都围绕这三类数据展开，缺任何一类都会造成决策盲区。理解本篇，抓住一条主线：**先按「三类数据」分清楚要采什么，再决定「怎么把那点数据安全、轻量地送出去」，最后补上「错误 / 性能 / 埋点」各自的采集手段与口径。**

主线一览（本篇从概念层面串起，抓实现在 [前端监控 SDK 实现](./前端监控%20SDK%20实现.md) 与 [前端监控实战·单页验证](./前端监控实战·单页验证.md)）：

```
三类数据（要采什么）  稳定性：错误 / 资源 / 接口 / 白屏
                      体验：  TTFB / FP / FCP / FMP / FID、卡顿
                      业务：  PV / UV / 停留时长 / 转化

上报方式（怎么送）     手动 / 自动；图片打点 → sendBeacon / fetch keepalive

采集手段（分头抓）     错误：6 类错误 6 种抓法 + 指纹频控
                      性能：PerformanceObserver 订阅 + navigation 快照
                      埋点：声明式 data-track / data-expose + 事件委托 / IntersectionObserver
```

## 一、三类数据，三类视角

监控先要回答"看什么"。三类数据把线上状态拆成三个互不替代的视角，各自独立成一套采集与指标。

| 视角 | 回答的问题 | 采集对象 | 关键指标 / 信号 |
| --- | --- | --- | --- |
| **稳定性** | 有没有坏 | JS 错误、Promise 异常、资源加载失败（script/link）、接口异常（ajax/fetch）、白屏 | 错误率、资源加载失败数、接口成功率 |
| **体验** | 快不快 | 加载与响应指标、长任务卡顿 | TTFB / FP / FCP / FMP / FID、>50ms 长任务 |
| **业务** | 用户在做什么 | 页面访问与行为 | PV、UV、停留时长、转化漏斗 |

> 为什么要按这三类分？因为**张三类的量级和口径完全不同**：错误量小但必须全要，行为数据量最大必须采样，性能指标要足够样本才稳。把三者混在一个采集逻辑里，必然顾此失彼。

## 二、监控闭环：七步，别只看"报了个错"

监控不是一个"报错函数"，是一整套从采集到优化的闭环。

```
目标设定与数据采集 → 数据传输与存储处理 → 分析与可视化 → 告警预警与定位优化
```

1. **目标设定与数据采集**：先定监控指标与目标（加载时间 / 错误率 / 用户行为），再选采集技术或自封装函数采集数据。
2. **数据传输与存储处理**：经 HTTP / WebSocket 等传到后端，用数据库 / 日志 / 分析平台存储处理，供后续分析。
3. **分析与可视化**：转成报表、图表或仪表盘，帮助开发与运营了解系统性能和用户行为。
4. **告警预警与定位优化**：数据超限触发告警通知相关人员，结合告警信息定位根因、改进优化。

本篇只讲前端的"采集—上报"这一段，其余是服务端 / 数据分析的范畴，不在本模块展开。

## 三、上报方式：怎么把那点数据送出去

前端监控的最后一米是"把采集到的事实送到接收端"。两种上报模式、三代手段，关键在**别为了省代码而偷掉可靠性**。

### 3.1 手动上报 vs 自动上报

| 方式 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| 手动上报 | 业务 catch 分支显式调用上报函数 | 可控、可自定义数据内容 | 侵入业务代码，容易漏 |
| 自动上报 | 监听浏览器内置事件（`window.onerror` 等）自动采集 | 无需侵入业务 | 拿不到业务上下文 |

核心转化路径的错误用**自动上报兜底**、关键业务分支用**手动上报补上下文**，两者配合而不是二选一。

### 3.2 三代上报手段：图片打点 → sendBeacon / fetch keepalive

| 手段 | 页面卸载能否送达 | 是否阻塞 | 限制 | 定位 |
| --- | --- | --- | --- | --- |
| `new Image()` 图片打点 | 能，但浏览器为它推迟卸载 | 不阻塞首屏 | 只能 GET、数据受 URL 上限（约 2~8 KB）、拿不到响应 | 上一代方案 |
| 同步 `XMLHttpRequest` | 能 | 阻塞卸载 | 浏览器已基本禁用 | 丢弃 |
| `fetch`（无 keepalive） | 不能，请求被取消 | 不阻塞 | — | 不适用 |
| `fetch + keepalive` | 能 | 不阻塞 | 请求体 64KB 上限 | 兜底（现代） |
| `navigator.sendBeacon` | 能 | 不阻塞 | 无响应回调 | 首选（现代） |

两个关键结论：

- **能带数据量的差别是代际性的**：图片打点只能 GET、数据拼在 URL 上（约 2~8 KB），还受 access log、浏览器历史存储明文 URL 的泄露风险；`sendBeacon` 用请求体承载（约 64 KB），跨域同样不触发预检，还确认能送达一个"至少提交出去了"的信号。**数据一多，图片打点就是死路。**
- **`sendBeacon` 拿不到响应体**，它只能回答"提交出去了没有"；要确认服务端真收到，得靠服务端入库计数。

## 四、错误监控：六类错误，六种抓法

**结论：没有一个 API 能抓全错误，必须按错误来源分别挂监听。** 错误量不大，通常 100% 上报、不采样。

| 类别 | 典型场景 | 捕获方式 | 关键字段 |
| --- | --- | --- | --- |
| 运行时错误 | 读 `undefined` 的属性 | `window.addEventListener('error')` | `message` `filename` `lineno` `colno` `error.stack` |
| 未处理 Promise | `.then` 里抛错、`await` 没 catch | `window.addEventListener('unhandledrejection')` | `reason.message` `reason.stack` |
| 资源加载失败 | img / script / link 挂了 | 同一 `error` 事件，但**必须 `capture = true`** | `event.target.tagName` `src` |
| 接口错误 | 后端 404 / 500 | 包裹 `fetch` / `XMLHttpRequest` | `url` `status` |
| 网络错误 | DNS 失败、连接被拒、断网 | 同上，走 `catch` 分支 | `url` `message`（如 `Failed to fetch`） |
| 跨域脚本错误 | 第三方 CDN 脚本出错 | 只能拿到 `Script error.` | 细节全无，需 `crossorigin` + CORS |

> 实测六条里只有一条（`script`）能拿到完整文件与行号，其余各有各的"缺"：Promise 没有文件名、资源错误没有 message、跨域错误什么都没有。采集器必须接受这种"信息不全"并各自兜底。

### 4.1 `window.onerror` 的三个坑

1. **资源错误不冒泡**：`img/script/link` 加载失败触发的是资源元素的 `error` 事件，**不冒泡**，默认事件冒泡阶段收不到，必须 `addEventListener('error', fn, true)` 用**捕获阶段**监听。判据：事件对象上有 `target.tagName` 就是资源错误，没有才是脚本错误。
2. **`Script error.` 是同源策略在起作用**：跨域脚本出错时浏览器不给细节，只给一句 `Script error.`。要细节得 `<script crossorigin>` + CDN 响应头带 `Access-Control-Allow-Origin` 两条都满足；做不到时退路也难——`Script error.` 连位置都没有，sourcemap 还原也用不上，最终常靠"关键脚本自建同源"。
3. **参数容易记混**：`onerror(msg, source, lineno, colno, error)`——`msg` 已被浏览器加前缀（`Uncaught TypeError: ...`），别自己再拼；`lineno` 是整页行号（含 HTML 部分），压缩后和源码对不上；老浏览器只有前三个参数，要 `error && error.stack` 兜底。

### 4.2 Promise 拒绝不走 `onerror`

`Promise.reject()` 不触发 `window.onerror`，只打控制台警告，必须单独监听 `unhandledrejection`，`e.reason` 是被拒原因。`reason` 不一定是 `Error`（可能是字符串、对象甚至 `undefined`），要 `String(r)` 兜底；这类错误**没有 filename 与 lineno**，位置不能作唯一索引，`reason.stack` 是唯一线索。

### 4.3 接口错误的两分法：网络错误 vs 逻辑错误

包裹 `fetch` 后，`!res.ok`（HTTP 状态码）记 `http` 错误、`catch` 分支（根本没到服务端）记 `network` 错误。**catch 里上报后必须 `throw`**，否则会吞掉业务异常。看板上把两类分开：`network-error` 找运维 / 网关，`logic-error` 找前端，避免互相甩锅。

### 4.4 指纹与频控：既压量又不丢信息

**错误频控的去重键是「指纹」，不是「错误信息」。** 指纹 = `message + 出错位置 + 行号`。同一个函数被循环调用时报错信息一模一样，只按 message 去重会把不同出错点合并成一条，只按指纹去重才既压量又不丢信息。一个细节：**资源 / 接口错误没有 message，必须把 `src` / `url` 算进指纹**，否则页面上所有图片加载失败会塌成同一条。

线上还要带出现次数（`count`）与指纹复位逻辑（如 5 分钟未再出现就清掉），否则同样的错误只报首次那一次，看不出"每分钟 800 次"。

### 4.5 sourcemap 还原：生产栈是压缩后的

生产栈是 `at n (app.a1b2c3.js:1:48213)` 这种压缩形式，必须用 sourcemap 还原。两条约定：

- **用 `release` 版本号把 map 与代码绑定**，否则还原到错误版本；
- 服务端还原优于客户端还原（客户端还原暴露 sourcemap、体积大；服务端要发布时归档 map）。

框架兜底另算：Vue 用 `config.errorHandler` / `onErrorCaptured`；React 错误边界**只覆盖渲染错误，不含事件处理器与异步代码，不能替代全局监听**。

## 五、性能与体验监控：RUM 的三个设计前提

**结论：性能监控是"给业务代码身边装了个长期运行的进程"，前提是采集本身不能是性能问题。** 与 Lab（性能实验台）不同，RUM 面对真实用户，环境不可控，于是有三个必然设计：

| 差别 | 对应设计 | 解决什么 |
| --- | --- | --- |
| SDK 可能跑了一半才加载 | `PerformanceObserver` 带 `buffered: true` | 否则 FCP 恒为 0 |
| LCP / CLS 越晚越准 | `visibilitychange → hidden` 时定稿 | 否则报中途值，低估 |
| 老浏览器不支持某 entry 类型 | `try/catch` 静默跳过 | 不把页面搞崩 |

### 5.1 取数两范式：同步快照 vs 异步订阅

| 范式 | 方式 | 适用 |
| --- | --- | --- |
| 同步快照（拉） | `performance.getEntriesByType("navigation")` 读取 | 导航时间戳（DNS / TTFB / load），一次写好 |
| 异步订阅（推） | `PerformanceObserver` 监听 | LCP / CLS / 长任务，异步产生、越晚越准 |

要用 `PerformanceObserver` 而不是轮询 `performance.getEntries()`：`paint` / `largest-contentful-paint` / `layout-shift` / `longtask` 都是异步产生的，轮询要么采到半截值、要么定时器空转。导航类仍走 `getEntriesByType`，因为它是加载时就写完的一条记录。

### 5.2 五类指标与官方口径

一次实测（无头浏览器，故意制造了长任务 + 无预留横幅 + 晚到大图三种坏情况）：

| 指标 | 含义 | 实测值 | 良好阈值 | 评级 |
| --- | --- | --- | --- | --- |
| ttfb | 首字节时间 | 166 ms | ≤ 800 ms | 良好 |
| fcp | 首次内容绘制 | 416 ms | ≤ 1800 ms | 良好 |
| lcp | 最大内容绘制 | 1272 ms | ≤ 2500 ms | 良好 |
| cls | 累计布局偏移（规范口径） | 0.0116 | ≤ 0.1 | 良好 |
| tbt | 总阻塞时间 | 90 ms | ≤ 200 ms | 良好 |

三个值得单独记的点：

- **LCP 明显晚于 FCP**：最大内容最后才插进来。LCP 关心"主要内容"何时可见，FCP 只是"有东西可见"，差值就是"白等"的时间。
- **FID 已被 INP 取代**（2024 年 3 月起 Core Web Vitals 不再包含 FID）。FID 只测首次交互的输入延迟、只测"开始"；INP 测所有交互的处理完成（取最差分位段），且**必须按交互分组**，不能对所有 `event` 的 `duration` 取平均——真要上 INP 建议直接接官方 `web-vitals` 库。
- **评级按官方阈值给**，不是"我觉着快"。

### 5.3 两个容易写错的指标口径

**CLS 存两个数：`cls` 与 `clsRaw`。** 规范只统计**没有紧跟用户输入的位移**（用户点击导致的重排是"预期内"豁免的），所以 `clsRaw`（累加全部 layout-shift）与 `cls`（只累加 `!hadRecentInput`）可能不同。采集器两个都存：看板告警用 `cls`（与官方/竞品可比），排查用 `clsRaw`（"点击后横幅把内容顶下去"在规范豁免里，但用户照样觉得页面在跳）。规范还要求位移在 500ms 窗口内、累计不超过 5% 视口高度才合并成一次 shift。

**TBT 只算超出 50ms 的部分。** 长任务门槛是 50ms，计入 TBT 的是 `Σ max(0, duration - 50)`。实测一次 140ms 的长任务 `longtasks=1`、`tbt=90ms`。写错成"累加任务总时长"会让 TBT 虚高，这是自研采集最常见的错。

### 5.4 采集自身三条自律

1. **不在主线程做重活**：`PerformanceObserver` 回调里只累加，不序列化、不上报，序列化放 flush。
2. **指标只算一次**：`finalize()` 后不再重复计算，否则同一页面重复 flush 等于流量翻倍。
3. **资源明细要限流**：`resource` entry 全报会随资源数线性增长，真实 SDK 只报 Top N 大文件或总量。

## 六、埋点与行为分析：单点数字是原料，漏斗才是结论

**结论：埋点靠"声明式属性 + 事件委托"把采集逻辑收进 SDK，业务只写 `data-track` / `data-expose`。** 单点 PV / 点击量只是原料，把事件流按环节排成漏斗才能定位转化断点。

### 6.1 三种埋法怎么组合

| 维度 | 代码埋点 | 可视化埋点 | 无埋点（全埋点） |
| --- | --- | --- | --- |
| 怎么做 | 业务里调 `track('事件', 参数)` | 运营后台圈选元素生成配置下发 | SDK 自动采集全部点击 / 曝光 |
| 口径 / 成本 | 口径最准、参数最全，但要发版 | 不改代码，规则随改版失效 | 覆盖最全，噪声大、上报量巨大 |

实践是**组合**：核心转化路径用代码埋点（口径必须准），长尾用可视化，兜底用无埋点看"还有哪些没覆盖"。本模块实验台走**声明式埋点**，是前两者的折中——业务只写属性，采集集中 SDK。

### 6.2 三个 ID 别混用，会话按 30 分钟切

三个身份各管一段生命周期：

- **设备 ID**：首次访问生成、存 `localStorage`，无登录场景的"同一台设备"；
- **匿名 ID（anonId）**：首次访问生成，未登录用户的 PV/UV 去重；
- **登录 ID（userId）**：登录后后端下发，跨设备 / 跨会话串联行为。

**会话按 30 分钟不活跃切分**（行业惯例 25~30 分钟）：窗口太短把"读一半吃饭"算两次、太长把"下午和晚上各来一次"算一次。会话判定放**事件入口**（每次 `track` 都检查），任何事件都刷新活跃时间，"只滚动不点击"也不会被误判离开。

### 6.3 四个指标先定口径再埋点

PV / UV / 停留 / 跳出每个都有两三种口径，不上来定义报表一定对不上数：

- **PV**：每次页面加载 vs 每次路由切换（SPA 里差数倍）；
- **UV**：按匿名 ID / 设备 ID / 登录 ID 去重结果不同；
- **停留**：离开页面时结算；用户直接关标签页会丢 `stay`，工程补救是 **enter / stay 双写**，接收端对"只有 enter 的会话"按超时兜底估算；
- **跳出率**：单 PV 会话占比 vs 短停留会话占比。

### 6.4 曝光用 IntersectionObserver，不监听 scroll

`scroll` 监听方案每次滚动都要同步读布局（`getBoundingClientRect`）——正是布局抖动。`IntersectionObserver` 交给浏览器，且注册时立刻对已在视口内的元素回调一次，**首屏不漏**。三个设计点：

- **`unobserve()` 让曝光只报一次**，否则上下滚动把同一元素报出几十次；
- **`entry.time` 是被判定进入视口的时间，不是停留时长**；
- 真实口径还要加**可见面积阈值（`threshold`）与持续时长阈值（如 ≥1s）**，否则"一闪而过"也算曝光。

点击走**事件委托**（一次监听覆盖全站，动态插入 DOM 自动被覆盖）；曝光与点击是同一元素的**两套独立标识**（如 `data-track="cta-hero"` 与 `data-expose="hero-cta"`），分开命名才能区分"看到了"和"点了"。

### 6.5 脱敏与治理：埋点最大的事故是"把不该传的传了"

三条硬线放在**采集口**（数据出端就已泄露，接收端再过滤只是心理安慰）：

1. URL 只留 path，query 里可能有 token / 手机号 / 订单号；
2. 元素文本截断（本实验台 40 字符）；
3. 表单值一律不采，`input.value` 永不上报。

埋点长期成本是**口径腐化**（两年后没人知道 `btn_v2_new` 是什么）。治理四件套：埋点字典（登记标识 / 含义 / 负责人）、命名规范（统一 `区域-元素-动作`）、上报校验（开发环境对未登记标识告警）、超期埋点自动下线。最实用的一条是**开发环境对未登记标识直接告警**——错在编码阶段发现成本几乎为零。
