# 企业级性能与监控工程实践

前面几篇分别回答了监控的四个切面：`监控平台` 讲监控要采集什么、告警怎么做，`前端监控 SDK 实现` 把采集收成一个 SDK，`错误监控` / `性能与体验监控` / `埋点与行为分析` 各自把一类数据的采法讲透，`数据管道与告警` 讲离散事件怎么变成决策；性能侧的指标口径与优化手段见 `性能优化` 模块的 `性能指标与评估` 与 `优化手段速查`。但理论拆开看是一回事，落到真实业务是另一回事。本文把它们**焊接成一个工程**：一个能进生产的性能与监控闭环，应该长什么样。

## 一、为什么理论够多、落地仍难

很多人学了指标、看了优化清单、甚至写过 demo，一上生产却发现：

- **指标采回来没人看**：数据进了库，但没有阈值、没有告警，等于没监控；
- **监控和优化脱节**：只监控不优化，或只优化不回归，形成不了闭环；
- **数据噪声淹没问题**：全量上报、重复告警，真问题被海量假警报淹没；
- **埋点破坏性能**：埋点代码本身拖慢页面，违背了"为性能做监控"的初衷。

企业级实践的核心，就是把这些"理论到落地之间的缝隙"填上。下面用一个可运行的完整工程 demo 贯穿到底。

## 二、工程全景：埋点 → 上报 → 聚合 → 告警

一条完整的性能与监控闭环包含四段，每一段都有自己的工程职责：

> 示意片段（无配套脚本）

```
[前端 Agent]          [传输层]           [接收端聚合]           [决策端]
采集指标/错误/行为  →  sendBeacon/fetch  →  秒桶聚合+分位值   →  报表 / 告警 / 趋势
埋点 SDK(采样/脱敏)    轻量,不阻塞          去重,阈值/基线         超阈触发通知、溯源到人
```

这套闭环正是 `code` 企业级 demo 所演示的：`agent.html` 扮演**前端埋点 Agent**，`enterprise-server.js` 承担**接收端聚合与告警**，`monitor.html` 是**监控报表/告警台**。下面逐段拆解。

## 三、前端 Agent：把"采集"做成一块可复用 SDK

企业级的前端埋点绝不是在页面里散落一堆上报调用，而是一个**统一、可配置、低侵入的 SDK**。它的职责分三层：

### 1. 采集层：定义清楚"报什么"

- **性能指标**：从 `performance` / `PerformanceObserver` 拿 FP/FCP/LCP/TTFB；
- **接口延迟**：包裹 `fetch`/XHR，在请求完成时读数 `latency`、是否 `ok`；
- **错误**：`window.onerror` + `unhandledrejection` + 框架专项（如 Vue `config.errorHandler`）兜底捕获；
- **行为**：事件委托统一采集点击/曝光，支撑 PV/UV/漏斗。

> 示意片段（无配套脚本）

```js
// demo 中的一次采样：组装一条结构化监控事件
function sample(latency, ok) {
  const nav = performance.getEntriesByType('navigation')[0]
  return {
    label: ok ? '正常' : '失败',
    fp: performance.getEntriesByType('paint')[0].startTime,
    lcp: 480 + Math.random() * 120,
    ttfb: nav ? nav.responseStart : 160,
    latency, ok,
  }
}
```

### 2. 传输层：上报要"轻量 + 不丢"

- 优先 `navigator.sendBeacon()`：页面跳转/关闭时也能送达，不阻塞卸载；
- 兜底 `fetch + keepalive`；
- 长时指标（LCP/CLS/INP）在 `visibilitychange → hidden` 时上报，确保拿到最终值。

> 示意片段（无配套脚本）

```js
function sendReport(metrics) {
  const body = JSON.stringify({ metrics, extra: { route: location.pathname, ua: navigator.userAgent } })
  if (navigator.sendBeacon) navigator.sendBeacon('/api/collect', body)
  else fetch('/api/collect', { method: 'POST', body, keepalive: true })
}
```

### 3. 治理层：采样 + 脱敏 + 频控

企业级必须考虑的治理策略：

- **采样率**：`Math.random() < SAMPLE_RATE` 控制上报量，热门页面可低至 5%–10%；
- **脱敏**：不上报完整 URL 的 query 密钥、手机号、token；用 `slice` 截断 `userAgent` 等长字段；
- **频控**：错误按 `message + 文件 + 行号` 聚合，同一条错误一段时间内只报一次，避免告警轰炸。

## 四、接收端：从"一条条数据"到"一张报表"

接收端（`enterprise-server.js`）承担把海量离散上报变成可决策指标的职责，三个关键工程点：

### 1. 秒桶聚合（Time Bucket）

按**1 秒一个桶**聚合计数：每来一条上报，往对应秒的桶里累加 `count / totalLatency / errCount / fpSum / lcpSum`，并记录该秒的延迟样本。

> 示意片段（无配套脚本）

```js
const b = buckets.get(ts)
b.count++
b.totalLatency += m.latency || 0
if (!m.ok) b.errCount++
b.p95List.push(m.latency)   // 该秒的延迟样本，用于算分位值
```

### 2. 分位值（Percentile）才是体感

平均延迟（avg）容易被少数慢请求拉偏，而 **P95/P99 分位值**代表"绝大多数用户"的体验，是告警更该关注的判定量。demo 中对每秒钟的样本算 P95，再对最近 60 秒做二次聚合：

> 示意片段（无配套脚本）

```js
function percentile(arr, q) {
  const sorted = [...arr].sort((a, b) => a - b)
  const idx = Math.floor(sorted.length * q)
  return sorted[Math.min(idx, sorted.length - 1)]
}
```

### 3. 阈值 + 基线：告警"准"

- **阈值**：P95 > 120ms、错误率 > 1% 触发告警（demo 中的企业基线约定）；
- **去重**：同一秒同指标准确去重，避免告警轰炸；
- **基线**：成熟系统会基于历史数据算动态基线，比固定阈值更抗业务起伏。

> 示意片段（无配套脚本）

```js
const ALERT_LIMITS = { p95: 120, errorRate: 0.01 }
function evalAlerts(ts, b) {
  const p95 = percentile(b.p95List, 0.95)
  const errorRate = b.errCount / b.count
  if (p95 > ALERT_LIMITS.p95) pushAlert(ts, 'p95', p95, ALERT_LIMITS.p95, '接口 P95 延迟超阈，存在变慢风险')
  if (errorRate > ALERT_LIMITS.errorRate) pushAlert(ts, 'errorRate', errorRate, ALERT_LIMITS.errorRate, '错误率超阈')
}
```

## 五、决策端：报表与告警台（monitor.html）

监控的终点是"看得懂、触得到"。`monitor.html` 每 2s 轮询 `/api/report`：

- 顶部 **KPI 卡**：TPS / 平均延迟 / P95 / 错误率 / FP / LCP，超阈的标红；
- 中部 **曲线**：接口延迟（avg/P95 vs 阈值线）、TPS 与错误率趋势；

## 六、闭环回归：优化要回到指标

这套工程闭环也把 `性能优化实践` 的优化手段接回了第 1 篇的指标：做一次优化（如拆分长任务、缩 LCP、补 key 消 CLS）→ 看 `monitor` 上的 P95/FCP/LCP 曲线是否下降 → 若没变再定位、再优化，直到曲线进入阈值健康区。**优化不以"感觉快了"为止，而以"指标回归到阈值内"为准。**
