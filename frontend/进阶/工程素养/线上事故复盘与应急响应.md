# 线上事故复盘与应急响应

事故处理里最贵的不是修 bug，而是**混乱**：不知道该谁来处理、不知道现在该止血还是该查根因、复盘写了但行动项三个月后还在原地。这一篇用 `practice-lab` 的 `incident.cjs` 把三件事做成可判定的规则：**分级**、**时间线拆解**、**行动项闭环**。

## 一、分级：先定级，再决定谁来

「线上有问题」这句话无法行动。定级要同时看**影响面**与**是否有资损/核心功能是否可用**：

> 摘自 `./code/practice-lab/incident.cjs`

```js
function grade(i) {
  // P0：核心功能不可用或资损；P1：核心功能降级或大范围受影响；P2：有一定影响且无绕过；P3：轻微且可绕过
  if (i.coreBroken || i.moneyLoss > 0) return 'P0';
  if (i.affectedUsers >= 10000 || i.coreDegraded) return 'P1';
  if (i.affectedUsers >= 500 || !i.workaround) return 'P2';
  return 'P3';
}
```

实测几条边界：

| 情况 | 级别 | 关键理由 |
| --- | --- | --- |
| 核心功能不可用，只有 50 人受影响 | **P0** | 核心不可用与人数无关 |
| 3 人受影响，但资损 12000 元 | **P0** | 有资损即 P0 |
| 5 万人受影响，有绕过方案 | **P1** | 大范围 |
| 300 人受影响，无绕过方案 | **P2** | 影响小但用户没办法自己解决 |
| 300 人受影响，有绕过方案 | **P3** | 可绕过 → 降级处理 |

**核心不可用 / 有资损 → P0，与影响人数无关**，这是最容易吵的一条。理由很简单：核心功能挂掉时，受影响人数只是「已经被观测到的」，真实规模随时间增长；而资损一旦发生就已经是事实。

定级必须**先于讨论**：级别决定谁被叫起来、多久响应、要不要升级——先讨论再定级，等于每次都从零开始协商。

## 二、时间线：MTTD 与 MTTR 是两个不同的问题

一次事故的总时长拆成两段：

> 摘自 `./code/practice-lab/incident.cjs`

```js
function timeline(ev) {
  const mttd = ev.detectedAt - ev.occurredAt; // 多久被发现
  const mttr = ev.recoveredAt - ev.detectedAt; // 发现后多久恢复
  return { mttd, mttr, total: mttd + mttr };
}
```

实测：01:00 发生、01:35 被**用户投诉**发现、01:50 回滚恢复 → **MTTD 35 分钟、MTTR 15 分钟**，合计 50 分钟，且瓶颈在「发现」而不是「恢复」。补上监控之后：MTTD 降到 5 分钟，MTTR 仍是 15 分钟。

这两段对应完全不同的改进：

| 段 | 慢的原因 | 改什么 |
| --- | --- | --- |
| MTTD（发现慢） | 没监控 / 告警阈值不合理 / 告警没人看 | 核心链路埋点、告警分级、值班响应 |
| MTTR（恢复慢） | 没有预案 / 回滚要重新发版 / 依赖别人 | 一键回滚开关、预案演练、权限前置 |

把两者混在一起说「我们响应太慢」，就会去改错误的地方——本例中如果去优化回滚流程，收益是 0，因为恢复本来就只花 15 分钟。

**响应时的顺序也要固定**：先止血（回滚 / 降级 / 限流），再查根因。在 P0 现场追根因是最常见的失误——用户还在受影响，而你在读日志。

## 三、复盘：产出是关掉的行动项，不是文档

复盘的价值不在于那份文档写得多深刻，而在于**行动项有没有关掉**。每条行动项必须有 owner、截止时间、验收标准：

> 摘自 `./code/practice-lab/incident.cjs`

```js
  for (const a of actions) {
    if (!a.owner) {
      open.push(`${a.id}：缺 owner`);
      continue;
    }
    if (!a.dueDay) {
      open.push(`${a.id}：缺截止时间`);
      continue;
    }
    if (!a.acceptance) {
      open.push(`${a.id}：缺验收标准`);
      continue;
    }
    if (!a.done && a.dueDay < nowDay) open.push(`${a.id}：已逾期 ${nowDay - a.dueDay} 天`);
  }
```

实测 5 条行动项：只有 1 条闭环（**20%**），另外 4 条分别有问题——1 条逾期 8 天、缺 owner、缺截止时间、缺验收标准各一条。

这三要素各自防的是一种典型失败：

- **缺 owner** → 所有人都以为是别人在做。
- **缺截止时间** → 永远排在下个迭代。
- **缺验收标准** → 做完了但说不清做没做完（"加了监控"——加了什么监控？）。

复盘的两个原则：

1. **对事不对人，但要具体到动作**。写"张三操作失误"没有价值；写"发布前缺少二次确认机制"才有。前者的行动项是"张三下次小心"（不可执行），后者是"发布流程加确认步骤"（可执行）。
2. **复盘要有期限**。48 小时内出初版、一周内定稿，超过这个时间，细节就开始丢失，复盘会退化成猜测。

## 四、日常演练：别让第一次实战发生在 P0

| 手段 | 频率 | 练什么 |
| --- | --- | --- |
| 回滚演练 | 每季度 | 开关真的能在分钟级生效吗 |
| 告警有效性检查 | 每月 | 阈值是不是早就该调了、有没有静默告警 |
| 混沌演练 | 每半年 | 依赖挂掉时降级链路通不通 |
| 值班手册走查 | 每季度 | 新人能不能照着手册独立处理 |

演练的意义在于：**降级开关这种东西，只有真的切过才知道它还在不在**。很多团队在 P0 现场第一次按那个开关，才发现它三个月前就被某个重构删掉了。

## 小结

- **分级**：核心不可用或有资损 → P0（与人数无关）；大范围或核心降级 → P1；有绕过方案可降级到 P3；**先定级再讨论**。
- **时间线拆两段**：MTTD（发现）+ MTTR（恢复）；实测 35min + 15min——瓶颈在发现，补监控后 MTTD 5min 而 MTTR 不变，**先分清慢在哪一段**。
- **响应顺序**：先止血（回滚 / 降级 / 限流）再查根因，别在 P0 现场追根因。
- **行动项三要素**：owner / 截止时间 / 验收标准，缺一即判不合规；实测 5 条只闭环 1 条（20%）。
- **复盘原则**：对事不对人但要落到可执行的机制改进；48 小时出初版、一周定稿。
- **演练**：回滚、告警有效性、混沌演练、值班手册——降级开关只有真切过才知道还在不在。
