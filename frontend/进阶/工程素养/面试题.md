# 模块面试题 · 工程素养

## 1. 技术方案写作与架构评审

### Q1（1.1）｜ 一份能过评审的技术方案，至少要有哪些内容？

- **判断**：八块必备——背景 / 目标 / 非目标 / 方案 / 取舍 / 风险 / 回滚 / 验证；缺一大多过不了评审。
- **展开**：这八块按下述分工形成一份可判定、可验收的方案：

```
背景 / 目标    为什么做、要达成什么（目标必须可度量，如"P90 ≤ 2s"）
非目标         明确不做哪些范围
方案 + 取舍    怎么做 + 关键决断的候选对比
风险 + 回滚     会出什么问题 + 出问题怎么退（分钟级开关）
验证           灰度比例、观察时长、验收指标
```

- **佐证**：实测（`practice-lab/proposal.cjs`）——只写「背景/目标/方案/取舍」的方案被报出缺非目标、风险、回滚、验证，完整度不足 60%。
- **边界**：**「非目标」最容易被删也最不该删**——没有它，评审会上每个人对范围的假设都不一样，争论的是各自脑补的版本；「回滚」写"重新发版"不算回滚，那是分钟级和小时级的区别。追问：目标和验证怎么写才算合格？→ 目标必须可度量，验证要写清灰度比例、观察时长、验收指标，而不是"上线观察一下"。

### Q2（1.2）｜ 方案里写了「我们选 SSR」，这算完成取舍论证吗？

- **判断**：不算。取舍要有**至少两个候选**、每个都给出结论与理由；只有一个候选的方案本质是「通知」不是「论证」。
- **展开**：取舍只写结论（如「选 SSR」）会被判弱，必须写被否决的方案与原因（如「CSR+预渲染只能到 2.5s，不达标」「边缘渲染依赖境外节点，合规过不了」）。
- **佐证**：实测（`practice-lab/proposal.cjs`）——单个候选在比例打分上也能拿满分，所以检查器必须**同时看候选数量**。
- **边界**：写清被否决方案有个副作用收益——半年后有人问「当初为什么不用 X」时答案在文档里，不用靠老人回忆。追问：风险那一块怎么写才有用？→ 按 概率×影响 排序讨论（实测 SSR 内存 1.8 > 缓存击穿 1.5），且每条必须带**信号**（怎么知道它要发生）与**兜底**（发生了做什么）；缺任一条即判未就绪。

## 2. 代码评审与技术债治理

### Q3（2.1）｜ 代码评审该看什么？

- **判断**：能自动判的交给规则，人只讨论判断不了的部分；评审真正价值在命名、抽象、边界条件。
- **展开**：四条硬规则——改公共接口要有兼容、新增依赖要说明必要性、动构建配置要本地验证、>50 行改动要有测试。
- **佐证**：实测（`practice-lab/review.cjs`）——一份四项全占的变更被四条 blocker 拦下；这四条背后是四类真实事故：旧调用方拿到 undefined、为 10 行函数引入 300KB 包、全组 CI 卡死、重构后行为变了没人知道。
- **边界**：人的精力要放在**命名、抽象、边界条件**上。追问：评审评论怎么处理才不浪费双方时间？→ 明确区分阻塞意见与建议；否则提交者只能全部照做或全部忽略。

### Q4（2.3）｜ 欠了一堆技术债，先还哪一笔？

- **判断**：按 **影响面 × 恶化速度 ÷ 修复成本** 打分排序，而不是按"看着最难受"排。
- **展开**：公式同时衡量"破坏多大、恶化多快、修起来多贵"，排序结果与直觉常有出入。
- **佐证**：实测（`practice-lab/review.cjs`）评分排序：

```
重复的工具函数散落 8 处   6.0   （影响一般但极便宜且在扩散）
核心模块没有测试         5.0   （影响大但贵，成本 4）
硬编码路径             3.0
遗留 jQuery 插件       0.8   （影响大但很贵且不恶化，垫底）
```

- **边界**：还债要**固定占用产能**（每迭代 15%~20%），靠"有空再说"永远不会发生；更重要的是**新增债要有门槛**——还的速度必须快过欠的速度。追问：影响最大的「核心模块没有测试」为什么不是第一优先？→ 因为它贵（成本 4）而工具函数便宜（成本 1）且在扩散（趋势 3）；先还便宜且在扩散的，能阻止它变成下一笔大债。

### Q5（2.4）｜ 想重构一个老旧模块，先做什么？

- **判断**：先铺安全网——测试 / CI / 回滚 / 监控 四件套，再谈动代码。
- **展开**：四件套各司其职——测试证明行为没变、CI 保证每次都跑同一套检查、回滚要分钟级开关而非重新发版、监控覆盖测试到不了的路径。
- **佐证**：铺网程度决定能改多大——缺 0 项可大改、缺 1 项只做小步改动（重命名、抽函数这一级）、缺 ≥2 项先补网；实测（`practice-lab/review.cjs`）缺「回滚手段」时只能做最小级改动。
- **边界**：**没有网的重构就是赌博**——重构收益是长期隐性的（可维护性），风险是即时显性的（线上故障），时间尺度不对等。追问：回滚手段具体指什么？→ 配置开关 / 灰度比例 / 特性开关，能在分钟级生效；"回退版本重新发版"在 P0 现场太慢。

## 3. 线上事故复盘与应急响应

### Q6（3.1）｜ 线上出问题了，第一步做什么？

- **判断**：**先定级，再响应**；然后先止血（回滚 / 降级 / 限流）再查根因。
- **展开**：级别决定谁被叫起来、多快响应、要不要升级——核心不可用或有资损即 P0，大范围或核心降级为 P1，无绕过为 P2，可绕过为 P3。
- **佐证**：实测（`practice-lab/incident.cjs`）——核心功能不可用只有 50 人受影响也是 P0，3 人受影响但资损 12000 元也是 P0，5 万人受影响有绕过方案则是 P1。
- **边界**：在 P0 现场追根因是最常见的失误——用户还在受影响，而你在读日志；止血与根因是两个阶段，顺序不能颠倒。追问：为什么「核心不可用」与影响人数无关？→ 观测到的人数只是「已被发现的」，真实规模随时间增长；而资损一旦发生就是既成事实。

### Q7（3.2）｜ 事故响应"太慢"，该从哪里改？

- **判断**：先把总时长拆成 **MTTD（多久被发现）+ MTTR（发现后多久恢复）**，再决定改监控还是改预案。
- **展开**：两段对应不同改进——MTTD 靠核心链路埋点、告警分级、值班响应；MTTR 靠一键回滚开关、预案演练、权限前置。
- **佐证**：实测（`practice-lab/incident.cjs`）——01:00 发生、01:35 被用户投诉发现、01:50 回滚恢复：MTTD 35min、MTTR 15min，瓶颈在发现；补监控后 MTTD 降到 5min，MTTR 仍是 15min。
- **边界**：把两者混在一起说"响应太慢"，会去优化本来就只要 15 分钟的回滚流程，收益为 0。追问：演练有什么用？→ 降级开关只有真的切过才知道还在不在；很多团队在 P0 现场第一次按开关，才发现它三个月前被某个重构删掉了。

### Q8（3.4）｜ 复盘会开完了，怎么保证不白开？

- **判断**：产出不是文档，是**关掉的行动项**；每条必须有 owner、截止时间、验收标准，缺一即判不合规。
- **展开**：三要素各防一种失败——缺 owner → 都以为是别人在做；缺截止时间 → 永远排在下个迭代；缺验收标准 → 做完了说不清做没做完。
- **佐证**：实测（`practice-lab/incident.cjs`）——5 条行动项只闭环 1 条（20%），其余分别为逾期 8 天、缺 owner、缺截止时间、缺验收标准。
- **边界**：原则是对事不对人但**要落到可执行的机制**——写"张三操作失误"的行动项是"下次小心"（不可执行），写"发布流程缺二次确认"才有行动项。时间上 48 小时出初版、一周定稿，超期细节就开始丢失。追问：行动项都补齐三要素就一定有效吗？→ 还要跟踪闭环率（本例 20% 明显偏低）并纳入迭代回顾；只写不查的清单会迅速退化成形式。
