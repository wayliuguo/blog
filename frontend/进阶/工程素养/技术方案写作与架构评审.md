# 技术方案写作与架构评审

方案写不好，评审就会退化成一场「各说各话」的会：一半时间在补背景，另一半在争论一个根本没写清楚的点。这篇讲的是**怎么真的做出来**——用 `practice-lab` 的 `proposal.cjs` 把方案的必备项、取舍论证与风险排序做成可自动检查的东西。

## 一、必备项：缺一块，评审就会绕圈子

一份能过评审的方案，八块内容缺一不可：

> 摘自 `./code/practice-lab/proposal.cjs`

```js
const REQUIRED = ['背景', '目标', '非目标', '方案', '取舍', '风险', '回滚', '验证'];
```

实测：一份只写了「背景 / 目标 / 方案 / 取舍」的方案，检查器报出缺 **非目标、风险、回滚、验证** 四项，完整度不足 60%；补齐后满分。

八块各自回答什么问题：

| 块 | 回答的问题 | 最常见的缺失 |
| --- | --- | --- |
| 背景 | 现在有什么问题，数据是多少 | 只写感受（"太慢了"）没有数字 |
| 目标 | 做到什么算成功 | 不可度量（"提升性能"） |
| **非目标** | 这次**不**做什么 | 整块消失——然后评审时反复拉扯范围 |
| 方案 | 具体怎么改 | 写成愿景，没有可执行的步骤 |
| 取舍 | 为什么是它，不是别的 | 只写结论（见第二节） |
| 风险 | 什么可能出错 | 写了风险但没有信号与兜底 |
| 回滚 | 出问题怎么退 | 写"重新发版"——那不叫回滚 |
| 验证 | 怎么证明达标 | 只写"上线观察" |

**「非目标」是被删得最多、也最不该删的一块**。没有它，评审会上每个人对范围的假设都不一样，争论的其实是各自脑补的版本。写清楚「这次不动支付链路」，能省掉的会议时间超乎想象。

## 二、取舍：没有备选方案的方案，本质是通知

「我们选 SSR」不是论证。论证长这样：**至少两个候选，每个都给出结论与理由**。

> 摘自 `./code/practice-lab/proposal.cjs`

```js
function scoreOptions(options) {
  // 每个备选要能给得出：结论 + 至少一条否决理由（或选择理由）
  let ok = 0;
  for (const o of options) {
    if (o.name && o.verdict && (o.verdict === 'selected' ? o.reason : o.rejectReason)) ok++;
  }
  return { total: options.length, argued: ok, ratio: ok / options.length };
}
```

实测：单个候选也能拿满分——所以检查器**不能只看比例，还要看候选数量**。只有一个候选的方案，本质是「通知」而不是「论证」，评审时第一句就该问：**还有别的路吗？**

合格的取舍表里，被否决的方案也要写清楚理由，而且理由要具体：

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| SSR | ✅ 采用 | 首屏可到 1.8s，团队已有 Node 基建 |
| CSR + 预渲染 | ❌ | 只能到 2.5s，不达标 |
| 边缘渲染 | ❌ | 依赖境外节点，合规过不了 |

写清被否决方案还有个副作用收益：**半年后有人问「当初为什么不用 X」时，答案在文档里**，而不是要靠老人回忆。

## 三、风险：先讨论哪一条，要能算出来

评审时间有限，风险不该按书写顺序讨论，而应按 **概率 × 影响** 排序。

> 摘自 `./code/practice-lab/proposal.cjs`

```js
function rankRisks(risks) {
  return risks
    .map(r => ({ ...r, level: r.probability * r.impact, ready: Boolean(r.signal && r.mitigation) }))
    .sort((a, b) => b.level - a.level);
}
```

实测：SSR 内存上涨（0.6×3 = **1.8**）排在缓存击穿（0.3×5 = **1.5**）之前——后者一旦发生更严重，但综合期望损失更低，所以先讨论前者。

检查器还强制每条风险带两样东西：

- **信号**：怎么知道它正在发生（如「容器内存 > 70%」）。
- **兜底**：发生了做什么（如「限流 + 扩容预案」）。

实测中「第三方 SDK 超时」因为两者都缺被标为 **未就绪**，要求补齐后才进评审。没有信号的风险等于不可观测，没有兜底的风险等于只能祈祷——这两类在评审会上都会被反复追问，不如写方案时就补上。

## 四、评审会怎么开：会前、会中、会后

方案质量只解决一半问题，另一半在流程。

**会前（决定成败）**：

- 提前 24 小时发方案，明确「会前必须读完并留评论」。
- 指定 1~2 个**主要评审人**（而不是"大家都看看"）——没有指定人等于没人负责。
- 作者在会前逐条回复已有评论；能达成一致的不要占用会议时间。

**会中**：

- 作者先花 5 分钟讲背景与目标，不要念文档。
- 按风险排序讨论（见第三节），不要按页码。
- 明确区分**阻塞意见**与**建议**：前者必须解决才能上线，后者记录即可。会议结束时要能说出哪些是阻塞项。

**会后**：

- 24 小时内发出结论：通过 / 修改后再审 / 否决，以及每条阻塞意见的处理方式。
- 方案文档本身要跟着改——很多人只改代码不改方案，三个月后文档与实现对不上，下一个人就被误导。

## 五、常见写作毛病

| 毛病 | 表现 | 改法 |
| --- | --- | --- |
| 目标不可度量 | "提升性能" | 首屏 P90 ≤ 2s，跳出率降 5pp |
| 把方案写成愿景 | "建设统一能力" | 拆成可执行步骤与排期 |
| 取舍只写结论 | "选 SSR，因为它好" | 列 ≥2 候选，各给理由 |
| 风险没有兜底 | "可能有性能问题" | 补信号 + 兜底动作 |
| 回滚靠重新发版 | "出问题就回退版本" | 开关 / 配置 / 灰度，分钟级生效 |
| 验证靠感觉 | "上线观察一下" | 灰度比例、观察时长、验收指标 |

## 小结

- **八块必备**：背景 / 目标 / **非目标** / 方案 / 取舍 / 风险 / 回滚 / 验证；实测缺 4 项时完整度不足 60%。
- **非目标最容易被删**，但删了它评审就会反复拉扯范围。
- **取舍要有 ≥2 个候选**，每个给结论 + 理由；只有一个候选的方案是通知不是论证。
- **风险按 概率×影响 排序**讨论（实测 SSR 内存 1.8 > 缓存击穿 1.5）；每条必须带**信号**与**兜底**，缺一即判未就绪。
- **流程三件事**：会前指定主要评审人并预读、会中按风险排序并区分阻塞与建议、会后 24 小时出结论并同步更新文档。
- **六个毛病**：目标不可度量、方案写成愿景、取舍只写结论、风险没兜底、回滚靠发版、验证靠感觉。
