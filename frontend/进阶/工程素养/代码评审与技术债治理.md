# 代码评审与技术债治理

代码评审（CR）最大的敌人不是不认真，而是**注意力不够用**：一个 300 行的 diff，人眼能盯住的重点有限，而最容易出事的往往是最不起眼的那几处。这一篇用 `practice-lab` 的 `review.cjs` 说明：能把「记得看」变成「必须过」的部分尽量自动化，人只讨论判断不了的部分；以及技术债该先还哪一笔、重构前要有几层网。

## 一、CR 检查器：能自动判的，别浪费人力

四类改动几乎每次都要问同样的问题，那就把它们写成规则：

> 摘自 `./code/practice-lab/review.cjs`

```js
const RULES = [
  { id: '改了公共接口', test: d => d.publicApiChanged, require: d => d.compatHandled, msg: '需要兼容处理（旧调用方还在）' },
  { id: '新增依赖', test: d => (d.newDeps || []).length > 0, require: d => d.depJustified, msg: '需要说明为什么不能自己写' },
  { id: '改动构建配置', test: d => d.buildConfigChanged, require: d => d.localVerified, msg: '需要本地验证过（构建配置错了会阻塞所有人）' },
  { id: '新增代码块', test: d => (d.addedLines || 0) > 50, require: d => d.hasTest, msg: '>50 行改动要有测试' },
];
```

实测：一份「改了公共接口 + 加了依赖 + 动了构建配置 + 300 行无测试」的变更，四条规则**全命中**，直接拦下；把这些都处理过（兼容做了、依赖说明了、构建本地验证过、补了测试）就放行。

四条规则背后是四类真实的线上事故：

| 规则 | 它防的事故 |
| --- | --- |
| 改了公共接口要有兼容 | 旧调用方编译不过 / 静默拿到 undefined |
| 新增依赖要说明必要性 | 为一个 10 行函数引入 300KB 包 |
| 动构建配置要本地验证 | 全组人的 CI 卡死半小时 |
| 大改动要有测试 | 重构后行为变了没人知道 |

自动化负责**门槛**，人负责**判断**：命名是否清晰、抽象是否合理、边界条件是否想到——这些机器判不了，也才是评审真正的价值所在。

**评审的体量也有硬规律**：单次 diff 超过 400 行，缺陷发现率会显著下降（不是线性下降，是断崖）。所以规则里那条「>50 行要有测试」之外，还应该有一条不成文约定——**大改动拆成多个小 PR 提**，每个 PR 能独立看懂、独立回滚。

## 二、技术债：先还哪一笔，要能算

「我们欠了很多债」这句话没有信息量。要排优先级，就得把它变成三个可打分的维度：

> 摘自 `./code/practice-lab/review.cjs`

```js
function debtScore(d) {
  // 影响面 1-5、恶化速度 1-5（5 = 正在快速变糟）、修复成本 1-5（5 = 很贵）
  return { id: d.id, score: (d.impact * d.trend) / d.cost, ...d };
}
```

实测四笔债的排序：

| 债 | 影响 | 恶化 | 成本 | 得分 |
| --- | --- | --- | --- | --- |
| 重复的工具函数散落 8 处 | 2 | 3 | 1 | **6.0** ← 先还 |
| 核心模块没有测试 | 5 | 4 | 4 | 5.0 |
| 构建脚本硬编码路径 | 3 | 2 | 2 | 3.0 |
| 遗留 jQuery 插件 | 4 | 1 | 5 | **0.8** ← 最后 |

结论很反直觉：**影响最大的「核心模块没测试」不是第一优先，最不起眼的「工具函数散落」才是**。原因在公式里——后者极便宜（成本 1）且在扩散（趋势 3），现在不还，三个月后就是 20 处；而遗留 jQuery 虽然影响大，但它**不恶化**（趋势 1）且很贵（成本 5），可以一直往后放。

两个实践要点：

1. **还债要占用固定产能**，比如每个迭代留 15%~20%。完全靠"有空再说"的还债计划，永远不会发生。
2. **新增的债必须当下就拦**。存量债可以慢慢还，但新增债要有门槛（见第一节的规则）——否则还的速度永远赶不上欠的速度。

## 三、重构：先铺网，再跳

重构不是「把代码写好看」，而是「在保持行为不变的前提下改结构」。行为变没变，得有东西证明——这就是安全网。

> 摘自 `./code/practice-lab/review.cjs`

```js
function safeToRefactor(ctx) {
  const missing = [];
  if (!ctx.hasTest) missing.push('测试');
  if (!ctx.hasCi) missing.push('CI');
  if (!ctx.hasRollback) missing.push('回滚手段');
  if (!ctx.hasMonitoring) missing.push('监控');
  // 四缺一：只能做重命名级改动；四缺二以上：先补网
  const level = missing.length === 0 ? 'large' : missing.length === 1 ? 'small' : 'blocked';
  return { missing, level };
}
```

实测：四件套齐全 → 可做大规模重构；缺一项（比如没有回滚手段）→ 只做小步改动（重命名、抽函数这一级）；缺两项以上 → **先补网，别动**。

四件套各自的职责：

- **测试**：证明行为没变。没有测试的重构，验证手段是"点一点看起来没问题"。
- **CI**：保证每次改动都被同一套检查跑过，而不是靠人记。
- **回滚**：改错了能退回去。分钟级生效的开关远优于"重新发版"。
- **监控**：线上一出问题能立刻看到——尤其是对那些测试覆盖不到的路径。

**没有网的大重构就是赌博**。这不是保守，而是因为重构的收益是长期且隐性的（可维护性），而它的风险是即时且显性的（线上故障）——两者的时间尺度不对等，所以必须用安全网把风险压下去。

## 四、评审的文化问题

规则能解决一部分，剩下的靠文化，而文化靠几个具体动作建立：

| 动作 | 说明 |
| --- | --- |
| 区分阻塞与建议 | 评论要明确标出哪些必须改、哪些是建议；否则提交者只能全部照做或全部忽略 |
| 对事不对人 | 评论落在代码上（"这个分支在 X 情况下会漏"），不落在人上（"你怎么又忘了"） |
| 作者先自审 | 提交前自己过一遍 diff，能消灭大半的低级问题 |
| 24 小时内响应 | 评审拖三天，上下文就没了，质量与速度一起下降 |
| 小 PR 优先 | 100 行的 PR 得到的有效评论远多于 800 行的 |

最后一条尤其重要：**评审质量与 PR 大小强相关**。如果团队里大 PR 是常态，先解决的是拆分习惯，而不是评审流程。
