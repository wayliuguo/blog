## 1. 技术方案写作与架构评审

### 1.1 方案八块必备项

一份能过评审的技术方案，至少要有**八块必备**内容：

```
1 背景   为什么做、问题的起因
2 目标   要做到什么程度（必须可度量）
3 非目标 明确不做哪些范围
4 方案   具体怎么做
5 取舍   关键决断与候选对比
6 风险   可能出什么问题
7 回滚   出问题怎么退回去
8 验证   如何证明做成了
```

- 实测（`practice-lab/proposal.cjs`）：只写了「背景 / 目标 / 方案 / 取舍」四块时，会被报出缺非目标、风险、回滚、验证，**完整度不足 60%**。
- **「非目标」最容易被删，也最不该删**。没有它，评审会上每个人对范围的假设都不一样，争论的其实是各自脑补的版本。
- **二块硬标准**：目标必须可度量（"首屏 P90 ≤ 2s"而非"提升性能"）；验证要写清**灰度比例、观察时长、验收指标**（而非"上线观察一下"）。

### 1.2 取舍论证与候选方案

**取舍要 ≥2 个候选，每个都给出结论 + 理由**。只有一个候选的方案本质是「通知」不是「论证」。

- 实测（`practice-lab/proposal.cjs`）：单个候选在比例上也能拿满分，所以检查器必须**同时看候选数量**。
- 取舍只写结论（如「选 SSR」）会被判弱——必须写**被否决的方案与为什么**：
  -「CSR + 预渲染只能到 2.5s，不达标」
  -「边缘渲染依赖境外节点，合规过不了」
- **副作用收益**：写清被否决方案后，半年后有人问「当初为什么不用 X」时答案在文档里，不用靠老人回忆。

### 1.3 风险矩阵：概率 × 影响与信号兜底

风险按 **概率 × 影响** 排序讨论，实测排序：

```
SSR 内存上涨   1.8  （高概率 × 影响大）
缓存击穿       1.5  （中概率 × 中影响）
SDK 超时       0.4  （低概率 × 低影响）
```

**每条风险要带信号与兜底**，缺任一条即判未就绪：

```
信号   怎么知道它要发生       没有信号 = 不可观测，只能等它爆
兜底   发生了做什么          没有兜底 = 只能祈祷
```

### 1.4 评审流程三件事与六个毛病

评审流程的**三件事**：

```
会前  指定主要评审人并预读（带着准备来，不临场看图）
会中  按风险排序讨论、区分阻塞意见与建议
会后  24 小时出结论、同步更新文档
```

方案的**六个毛病**（自检清单，摊上任意一个都会让评审退化成"各说各话"的会）：

```
1 目标不可度量          写成"提升性能"，不是"P90 ≤ 2s"
2 方案写成愿景          只有大方向，没有可执行的具体做法
3 取舍只写结论          没写候选、没写被否决的方案与理由
4 风险没兜底            只列了风险，没有信号也没有应对
5 回滚靠发版            重新发版是小时级，不算回滚
6 验证靠感觉            "观察一下"，没有灰度与指标
```

## 2. 代码评审与技术债治理

### 2.1 自动化硬规则与人力分工

**能自动判的交给规则，人只讨论判断不了的部分**。四条硬规则（全命中即被拦下）：

```
改公共接口     要保证向下兼容（否则旧调用方拿到 undefined）
新增依赖       要说明必要性（为 10 行函数引入 300KB 包）
动构建配置     要本地验证（否则全组 CI 卡死）
改动 >50 行   要有测试（否则重构后行为变了没人知道）
```

实测（`practice-lab/review.cjs`）：一份四项全占的变更被这四条 blocker 拦下。四条规则背后各对应一类真实事故。

- **自动化管门槛，人管判断**。人的精力要放在**命名、抽象、边界条件**上——这是规则判不了、才是评审真正的价值。

### 2.2 PR 大小与评审效率

PR 体量有硬规律：**超过 400 行，缺陷发现率断崖下降**。

```
>400 行   缺陷发现率断崖下降，评审流于形式
对策       大改动拆成可独立看懂与回滚的小 PR
```

- 评审评论是否浪费时间，关键看是否**区分阻塞意见与建议**——否则提交者只能全部照做或全部忽略。

### 2.3 技术债打分与还债产能

还债按 **影响面 × 恶化速度 ÷ 修复成本** 打分排序，而不是按"看着最难受"排。实测排序（`practice-lab/review.cjs`）：

| 债项 | 得分 | 原因 |
| ---- | ---- | ---- |
| 重复的工具函数散落 8 处 | 6.0 | 影响一般但极便宜且在扩散（成本 1、趋势 3） |
| 核心模块没有测试 | 5.0 | 影响大但贵（成本 4），不排第一 |
| 硬编码路径 | 3.0 | 中等 |
| 遗留 jQuery 插件 | 0.8 | 影响大但很贵且不恶化，垫底 |

- **还债要固定占用产能**：每迭代留 **15%~20%**，靠"有空再说"永远不会发生。
- **新增债要有门槛**——还的速度必须快过欠的速度，否则永远赶不上欠的速度。

### 2.4 重构安全网四件套

重构前先铺**安全网**，四件套各司其职：

```
测试   证明行为没变
CI     保证每次都跑同一套检查
回滚   分钟级开关，不是重新发版
监控   覆盖测试到不了的路径
```

铺网程度决定能改多大：

```
缺 0 项   可大改
缺 1 项   只做小步改动（重命名、抽函数这一级）
缺 ≥2 项  先补网，否则别动
```

实测（`practice-lab/review.cjs`）：缺「回滚手段」时只能做最小级改动。**没有网的重构就是赌博**——重构收益是长期隐性的（可维护性），风险是即时显性的（线上故障），时间尺度不对等。

> 「回滚手段」具体指配置开关 / 灰度比例 / 特性开关，能在分钟级生效；"回退版本重新发版"在 P0 现场太慢。

## 3. 线上事故复盘与应急响应

### 3.1 事故分级

**先定级，再响应**。级别决定谁被叫起来、多快响应、要不要升级。

| 级别 | 判定 | 说明 |
| ---- | ---- | ---- |
| P0 | 核心不可用 **或** 有资损 | **与影响人数无关**（50 人也 P0、3 人资损 1.2 万也 P0） |
| P1 | 大范围受影响 或 核心降级 | 5 万人受影响但有绕过方案 |
| P2 | 无绕过方案 | — |
| P3 | 可绕过 | — |

- **为什么「核心不可用」与影响人数无关**：观测到的人数只是「已被发现的」，真实规模随时间增长；而资损一旦发生就是既成事实。
- 分级判断第一步是**定级**，不要先追根因。

### 3.2 MTTD 与 MTTR 的时间线两段

把总时长拆成两段，才知道该改监控还是改预案：

```
MTTD   发生 → 被发现   多久才发现（发现）
MTTR   被发现 → 恢复   发现后多久恢复（恢复）
```

实测（`practice-lab/incident.cjs`）：01:00 发生、01:35 被用户投诉发现、01:50 回滚恢复——**MTTD 35min + MTTR 15min = 50min，瓶颈在发现**；补监控后 MTTD 降到 5min，MTTR 仍是 15min。

两段对应**不同的改进**：

```
MTTD   靠核心链路埋点、告警分级、值班响应
MTTR   靠一键回滚开关、预案演练、权限前置
```

- 把两者混在一起说"响应太慢"，会去优化本来就只要 15 分钟的回滚流程，收益为 0。

### 3.3 应急止血与响应顺序

线上出问题的响应顺序铁律：

```
1 先定级    核心不可用 / 有资损 → P0，决定响应规格
2 先止血    回滚 / 降级 / 限流，让用户先恢复
3 再查根因  稳定之后才追根因
```

- **在 P0 现场追根因是最常见的失误**——用户还在受影响，而你在读日志。止血与根因是两个阶段，顺序不能颠倒。

完整案例（下单页白屏 76 分钟）切五段后，「发生 → 发现」占 41%：

```
补告警      省 28 分钟
呼值班      省 12 分钟
一键回滚    省 12 分钟
三个都做    76 分钟 → 24 分钟
```

段还要再拆：「发现慢」可能是没配告警，也可能是告警没人接，改的东西完全不同。

### 3.4 复盘行动项与问责边界

复盘的产出不是文档，是**关掉的行动项**。每条必须有**三要素**，缺一即判不合规：

```
owner       负责的人     缺了 → 都以为是别人在做
截止时间     什么时候做完     缺了 → 永远排在下个迭代
验收标准     怎样算做完     缺了 → 做完了说不清做没做完
```

实测（`practice-lab/incident.cjs`）：5 条行动项只闭环 1 条（20%），其余分别是逾期 8 天、缺 owner、缺截止时间、缺验收标准。

**问责边界**——对事不对人、但要落到可执行的机制：

```
不可执行   "张三操作失误" → "下次小心"
可执行     "发布流程缺二次确认" → 才有行动项
```

- **时间窗**：48 小时出初版、一周定稿，超期细节就开始丢失。
- 行动项补齐三要素也不一定有效：还要**跟踪闭环率**（本例 20% 明显偏低）并纳入迭代回顾——只写不查的清单会迅速退化成形式。

### 3.5 演练与常态机制

再好的预案，不演练都是纸面的。要常态化演练的四类内容：

```
回滚演练      回滚开关是否还能用
告警有效性    告警配了、真出事会不会响、响了有没有人接
混沌演练      故意搞挂组件，验证系统能自愈/降级
值班手册      值班的人手边有没有可执行的步骤
```

**降级开关只有真切过才知道还在不在**——很多团队在 P0 现场第一次按开关，才发现它三个月前被某个重构删掉了。

## 4. 综合实践与最小实现

### 4.1 practice-lab 探针实验台

`practice-lab` 是这个模块三篇的共同方法落地：**把靠人记住的东西变成可判定的规则**。方案八块必备项、CR 四条硬规则、行动项三要素——写成规则之后，它们就不再是"资深工程师的经验"，而是任何人都能执行、任何流程都能检查的东西。

```
零依赖探针实验台，node run.cjs 依次执行三探针：
  技术方案  方案必备项 / 取舍论证 / 风险矩阵
  代码评审  CR 检查器 / 技术债打分 / 重构安全网
  事故复盘  事故分级 / MTTD·MTTR / 行动项闭环 / 完整 P0 案例切段
node:assert 自检全绿
```

上述各章的「实测」数据即来自本实验台各探针，可复现、可改参、可当团队规范检查器复用。
