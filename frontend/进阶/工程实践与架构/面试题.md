# 模块面试题 · 工程实践与架构

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../../进阶/面试方法论/面试方法论.md)的四步答题法——结论/原理/边界/追问。
> 题目来源：由本模块各篇正文的知识点整理，每题在标题后标注出处（第 N 篇）。

## 一、基础概念

### Q1: 什么是设计模式？前端常用的有哪些？（第 1 篇）

- **结论**：设计模式是"在特定场景下被反复验证的解决方案模板"——不是语法，是可复用的结构约定；前端高频的是单例、观察者/发布订阅、工厂、策略、代理、装饰器。
- **原理**：模式解决"变化点"——单例管唯一实例、观察者管一对多通知、策略管算法替换、装饰器管职责叠加；前端版常见于状态管理、事件通信、配置化渲染。
- **边界**：模式是工具不是目标，为模式而模式增加复杂度；小型场景直接写法更清晰。
- **追问**：什么场景不用模式？→ 只有一处使用、变化频率极低时，直写比抽象更便宜。

### Q2: 观察者模式与发布-订阅模式的区别？（第 1 篇）

- **结论**：观察者是"对象直接通知依赖"；发布-订阅多一层事件中心，发布者与订阅者完全解耦。
- **原理**：观察者 = 目标持有订阅者列表、状态变了直接 notify；pub-sub = 通过事件总线/EventEmitter 转发，双方互不知道对方存在。
- **边界**：事件总线容易失控（事件名无约束、难追踪），大项目慎用。
- **追问**：Vue 响应式属于哪种？→ 观察者模式（依赖收集直连）。

### Q3: 组件是什么？和普通函数/类的区别？（第 2 篇）

- **结论**：组件是"有状态的渲染单元"——有自己的 props/状态/生命周期，可复用、可组合、可独立测试；普通函数无状态、无生命周期。
- **原理**：组件 = 输入（props/状态）→ 输出（渲染 + 事件）；框架负责调度生命周期与更新；函数是一等公民的纯计算。
- **边界**：无状态纯渲染可用函数组件，有副作用/状态才需要组件心智。
- **追问**：函数组件也算组件吗？→ 算——无状态组件是组件的最小形态，配合 hooks 也可有状态。

### Q4: 组件通信方式与取舍？（第 2 篇）

- **结论**：自上而下 props、自下而上事件（emit/回调）、跨层用 provide/inject 或全局状态、无关组件用事件总线——按耦合度递进选择。
- **原理**：props 单向数据流最可预测；事件回调让父子契约显式；provide/inject 解决深层传递；全局状态适合多组件共享；事件总线解耦但难追踪。
- **边界**：优先 props/事件（显式契约），跨层与共享才升级；事件总线是最后手段。
- **追问**：什么时候用全局状态？→ 多组件共享 + 跨页面 + 需持久化，否则本地状态 + props 提升。

### Q5: 单向数据流是什么？为什么重要？（第 2 篇）

- **结论**：数据单向流动（状态 → 视图 → 事件 → 状态），可预测、可调试、可单测。
- **原理**：状态唯一来源 + 视图只消费派生 + 修改必须走明确路径。
- **边界**：简单页面套全局状态管理是过度设计；状态本地化优先。
- **追问**：组件状态被父级偷偷改怎么办？→ 组件不暴露内部状态，只暴露结果事件。

### Q6: 前端分层架构（api / hooks / utils / views）？（第 3 篇）

- **结论**：`views/`（视图）→ `hooks/`（组合逻辑）→ `store/`（全局状态）→ `api/`（接口契约）→ `utils/`（纯工具）→ `shared/`（常量纯函数），**依赖只能单向向下**。
- **原理**：分层让"改一处"（接口变了只动 api 层）与"可测"（纯函数不挂组件）成为可能；层序号把违规变成可判定的算术——被引用方的层序号高于引用方即"反向依赖"。
- **边界**：分层要防"层间穿越"（视图直接写 fetch、工具层认识当前用户）；小项目不必全套分层，抽层的信号是"接口被两处调用、逻辑被两个组件需要、工具被三处引用"。
- **追问**：hooks 与 utils 的区别？→ hooks 持有响应式状态与生命周期，utils 是纯函数。

### Q7: 纯函数 + 派生状态的架构收益？（第 3 篇）

- **结论**：把逻辑收敛成纯函数、派生结果不落状态——可枚举、可单测、可复用、可回归。
- **原理**：纯函数同输入同输出、无副作用，天然可单测；派生状态由源状态计算，单一真相；UI 只消费派生结果。
- **边界**：纯函数只解决"计算"，IO/副作用仍要明确边界（请求放 api 层）。
- **追问**：怎么保证派生不落状态？→ 用计算属性/useMemo 实时派生，不写 set 派生副本。

### Q8: RBAC 是什么？为什么前端只该认权限码、不认角色名？（第 4 篇）

- **结论**：RBAC 是「用户 → 角色 → 权限」三层模型；前端只判断"有没有某个权限码"（`资源:动作`），不判断角色名。
- **原理**：用 `role === 'admin'` 做判断会把「角色 × 操作」变成组合爆炸，第二个角色出现就开始漏；权限码是角色配置的唯一出口，新增角色只改后端配置、前端代码不动。
- **边界**：前端拿到的应是权限码数组而非角色名；权限码要集中定义成常量，写魔法字符串拼错会静默失效。
- **追问**：为什么不让前端把角色名映射成权限？→ 映射表会随角色增长而膨胀，且与后端配置重复、容易不一致。

### Q9: 请求层该管什么、不该管什么？（第 5 篇）

- **结论**：只管「怎么发、怎么复用、怎么解析错误」——baseURL/超时/公共头、token 注入、拦截器管道、去重、并发上限、缓存与取消；**不含任何业务语义**。
- **原理**：职责清晰才能独立演进；一旦在拦截器里开始 `if (url === '/api/order')`，说明这段逻辑属于 api 层。
- **边界**：业务规则（"订单只能查 30 天"）、页面 loading/空态/文案、需要跳路由的逻辑都不属于请求层（401 除外）。
- **追问**：HTTP 错误和业务码错误为什么必须分开？→ 前者进 `catch`、后者进 `then`，混在一起会导致"统一错误提示"覆盖掉业务提示。

## 二、机制与原理

### Q10: 工厂模式 / 策略模式 / 装饰器模式在前端的体现？（第 1 篇）

- **结论**：工厂管"创建"（按配置产出实例），策略管"算法替换"（组合替代 if/else），装饰器管"职责叠加"（不动原逻辑加能力）。
- **原理**：工厂——统一创建逻辑、隐藏细节；策略——一组可互换算法由上下文选择，新增一种加一个策略对象（开闭原则）；装饰器——HOC/拦截器包一层。
- **边界**：工厂滥用让创建路径变深；策略过多要配注册表管理；装饰器叠加过多难以调试。
- **追问**：策略和 if/else 的本质区别？→ 策略把分支收敛成可组合、可独立测试的对象集合。

### Q11: 组件边界怎么判断？（第 2 篇）

- **结论**：三点判据——变化频率是否独立、是否有可复用的数据闭环、是否能独立测试。
- **原理**：抽组件是为了隔离变化；频率低的变化不值得抽（过度抽象比重复更贵）。
- **边界**：边界不是越细越好，要看"改一个需求动几个文件"。
- **追问**：组件与主流程的试算联动怎么做？→ 券只产出抵扣结果，试算仍由主流程纯函数完成。

### Q12: 组件库/设计系统的边界怎么划？（第 2 篇）

- **结论**：组件库收"通用原子与复合组件"（不掺业务），业务专属组件留业务层——边界是"是否可跨业务复用"。
- **原理**：通用组件只依赖设计 token 与自身状态，通过 props 扩展；业务组件依赖业务数据与接口，进不了通用库。
- **边界**：过早抽通用组件会做出"四不像"；通用层要防业务渗透（不许 import 业务 api）。
- **追问**：设计 token 怎么用？→ CSS 变量定义色板/间距/圆角，组件全部消费 token 不写死。

### Q13: 技术债有哪几种形态？怎么判定可下线？（第 3 篇）

- **结论**：下线判据不是"看起来没人用"，而是"消费方不存在"。
- **原理**：四种形态——失效业务分支（接口/配置不存在）、失效埋点（面板不再消费）、历史兼容判断（端版本全覆盖）、废弃配置（无读取方）。
- **边界**：三步判定：找消费方 → 看端版本/接口是否还在 → 灰度或加兜底后再删。
- **追问**：怎么确定一个分支可以删？→ 分支条件对应的接口/配置是否还存在，消费方是否还在用。

### Q14: 从"视图+数据+请求+校验+埋点混写"重构为"编排+渲染"的价值？（第 3 篇）

- **结论**：职责收敛——主组件只管"编排"（拉起数据、串联流程）与"渲染"（展示结果），横切关注点下沉。
- **原理**：混写导致改一个需求动多处、不可测；收敛后数据请求归 api/hooks、校验归纯函数、埋点归统一调用，组件可读可测。
- **边界**：收敛是渐进不是推倒重来——边界先行 + 增量迁移 + 灰度验证。
- **追问**：混写最典型的问题？→ 请求散落在组件里，接口变更动多个页面，且无法单测。

### Q15: 权限码通配（`*` / `资源:*`）该怎么用？边界在哪？（第 4 篇）

- **结论**：读动作可以用通配，**写/删动作必须逐个列举**；超管也尽量别用 `*` 走"神模式"。
- **原理**：实测 `operator` 持有 `order:read/write/refund` 三个具体码但没有 `order:*`，新上线的 `order:bulk` 会直接被拦截——这是"新能力默认关闭"的安全默认；反之配了 `order:*` 则新动作自动放行。
- **边界**：`*` 会让"权限码拼错"这类问题永远不暴露，直到新模块上线才一起爆；具体码的代价是每次加动作要同步改后端角色配置。
- **追问**：新增一个危险动作（如 `order:delete`）怎么配才安全？→ 用具体码，并在后端角色配置里显式加给该给的角色——漏配就是"没权限"，比漏拦安全。

### Q16: 拦截器为什么是"洋葱"？注册顺序与执行顺序是什么关系？（第 5 篇）

- **结论**：**请求拦截器后注册的先执行，响应拦截器先注册的先执行**，合起来是一个洋葱：最外层是"最后注册的请求拦截器 + 最先注册的响应拦截器"。
- **原理**：实测注册 A、B、C 三个请求拦截器与三个响应拦截器，执行顺序是 `C → B → A → 网络 → A → B → C`；axios 的实现是 `request` 拦截器用 `unshift` 插入调用链、`response` 用 `push`，所以行为一致。
- **边界**：注册顺序写反会出现"埋点在鉴权之前跑，未登录也上报一次"这类难以从表面看出的 bug；拦截器一旦开始判断 url，就属于 api 层该管的事。
- **追问**：想让埋点包住所有请求，应该注册在哪？→ 请求侧注册在最后、响应侧注册在最前。

### Q17: 大列表虚拟滚动的实现原理？（第 7 篇）

- **结论**：只渲染可视区 + 缓冲区的条目，内容容器高度按 `total × rowH` 撑出滚动条，滚动时用 `translateY` 平移内容容器。
- **原理**：`start = floor(scrollTop / rowH)`、`end = start + ceil(viewportH / rowH)`，边界要 `Math.min(total, ...)` 截断；渲染量与数据量无关，只由"视口高度 ÷ 行高"决定。
- **边界**：行高不固定要用前缀和 + 二分（实测 16 步 vs 线性 50001 步）；key 必须稳定（复用项状态）；虚拟滚动省 DOM 不省内存。
- **追问**：虚拟滚动和"懒加载无限滚动"的区别？→ 懒加载首屏成本随已加载量增长、内存持续增长；虚拟滚动首屏成本与总高度都恒定。

### Q18: 不定高虚拟滚动怎么做？（第 7 篇）

- **结论**：维护前缀和数组 `offsets[i] = 前 i 条总高`，用**二分查找**定位起点。
- **原理**：`offsets` 让"第 i 条起始于哪"变成一次数组读取，"某偏移量落在第几条"变成一次二分；十万条只需约 17 步，实测单次 0.070µs，线性扫描 55.53µs。
- **边界**：前缀和重建实测 736µs（十万条），只在行高集合变化时重建、滚动期间只读；单行高度变化用增量更新；未测量行先估算再回填。
- **追问**：为什么不在每次滚动时重算前缀和？→ 每帧多花 0.7ms 加十万次分配，GC 压力会直接体现为掉帧。

### Q19: 断点续传与秒传的判据分别是什么？（第 6 篇）

- **结论**：断点续传靠「服务端返回已收分片列表」（`init` 返回 `received`，客户端推出 `missing` 补传）；秒传靠「文件内容指纹（sha256）已存在」。
- **原理**：实测掉线时已传 [0,1,2]，重连后只发 2 片（167ms），从头重传要发 5 片；同一文件第二次 `init` 返回 `exists: true`，实际传输 0 B。
- **边界**：`uploadId` 必须按文件指纹复用，否则每次新建会话、`received` 恒为空，断点续传直接失效；指纹判据是内容，改一个字节就变，所以不会误合并。
- **追问**：秒传的风险是什么？→ 指纹可用于探测"某文件是否已上传"；且服务端在 `complete` 阶段仍要校验，不能只信客户端声明的 `fileHash`。

### Q20: 上传进度为什么不可信？该怎么算？（第 6 篇）

- **结论**：`upload.onprogress` 给的是"已交给系统缓冲区的字节数"，不是"服务端已落盘的字节数"，所以进度会先冲到 100% 再卡住。
- **原理**：网络缓冲、网关转发、服务端落盘都可能滞后；按"服务端已确认分片数"聚合，进度只在服务端真正收下一片后前进。
- **边界**：想要既快又准，用两层进度（已发出 = 快、已落盘 = 准），很多网盘就是这么做的。
- **追问**：服务端确认分片后返回什么更有用？→ 返回 `received` 数量或 `missing` 数组，客户端可直接据此补传，不必再来一轮 `status`。

## 三、排障与选型

### Q21: 单例模式的适用场景与坑？（第 1 篇）

- **结论**：适用"全局唯一 + 跨处共享"（store、日志、Toast）；坑是隐藏依赖与难测试。
- **原理**：保证一个类只有一个实例并全局可访问；前端典型是单一 store（Redux/Pinia）、事件总线、全局弹窗。
- **边界**：全局单例让依赖不显式、测试难隔离；共享可变状态是 bug 温床。
- **追问**：单例怎么测试？→ 构造函数收依赖 + 提供 reset 方法，避免测试间污染。

### Q22: 状态管理：全局状态 vs 组件状态怎么划分？（第 2 篇）

- **结论**：多组件共享 + 跨页面 + 需持久化才全局；否则本地状态 + props 提升。
- **原理**：状态就近原则——单一组件用的状态放本地；多组件共享的向上提升或进 store；派生值不存状态（由源状态计算）。
- **边界**：滥用全局 store 让数据流失控、组件难复用；状态越少越可预测。
- **追问**：派生值为什么不存状态？→ 存了会"双份真相"，改一处忘另一处。

### Q23: 请求竞态是怎么产生的？怎么解决？（第 5 篇）

- **结论**：先发出的慢请求后到达，把后发出的快请求结果**覆盖**掉——最终视图停留在用户已经不想要的输入上。
- **原理**：实测输入 A（200ms）后改成 B（50ms），B 先到写入、A 后到覆盖，屏幕停在 A；这不是时序巧合，只要网络抖动或接口变慢就必现。
- **边界**：两种保护——自增令牌比对"我是不是最新"，或 `AbortController` 直接掐断上一条；`AbortError` 是主动取消不是错误，混进错误上报会淹没真实错误。
- **追问**：为什么 AbortController 更彻底？→ 响应根本不会到达，连 `.then` 都不执行，省掉了后续处理逻辑。

### Q24: 请求缓存的失效策略怎么选？（第 5 篇）

- **结论**：按可靠度排——**写操作成功后就地删 key** ＞ 标签失效（一次清一组）＞ 短 TTL 兜底。
- **原理**：TTL 命中实测把 136ms 压到 0.1ms 且不走网络，但只写不删的缓存迟早会把脏数据留在用户屏幕上；`force` 参数是"用户点刷新"必需的出口。
- **边界**：SWR（过期后 1.00ms 交出旧值 + 后台刷新）适合能容忍旧数据的列表与详情，**不适合余额、库存**这类一致性敏感数据。
- **追问**：什么数据不该缓存？→ 会因陈旧导致错误操作的数据（余额、库存、订单状态），以及每次都要求强一致的场景。

### Q25: 上传的分片大小与并发数怎么定？（第 6 篇）

- **结论**：分片 `1~5MB`、并发 `3~4`。
- **原理**：实测 5 片 × 120ms 串行 753ms、并发 3 是 319ms，服务端观测并发峰值与客户端一致；同域 HTTP/1.1 浏览器只有 6 条连接，超过只会在连接层排队，还挤掉页面自身请求。
- **边界**：分片太小（如 64KB）请求数爆炸、协议开销占比过高；太大（如 16MB）单片重传代价高；HTTP/2 下没有连接数限制但共用一条 TCP 的带宽，服务端也有承载上限。
- **追问**：上传时还要注意什么？→ 首屏其他请求的带宽会被抢，重要请求要能插队或走独立通道。

### Q26: 什么情况不该上虚拟滚动？（第 7 篇）

- **结论**：数据量不大（几百条以内）、或者行高极其不定且无法估算、或者需要"整表导出/打印/查找"的场景，虚拟滚动带来的复杂度不划算。
- **原理**：虚拟滚动省 DOM 不省内存，也不解决"我要一次看到全表"的需求；不定高的工程量（前缀和 + 二分 + 高度缓存 + 增量更新）比定高高一个数量级。
- **边界**：还要防"过度虚拟化"——把本来几百条的列表改成虚拟列表，收益是几十毫秒，代价是无法用 `Ctrl+F` 找到屏幕外的内容、测试也变难。
- **追问**：数据量真到百万级怎么办？→ 虚拟滚动 + 数据分片（只保留下载过的窗口）或后端游标分页。

### Q27: 分层结构怎么落地才不会变成一张 PPT？（第 3 篇）

- **结论**：把规约变成可自动检查的规则并跑进 CI——四类可自动化的违规：反向依赖、绕过接口层、跨领域引用、循环依赖。
- **原理**：依赖图能被静态解析出来（正则扫 import + 解析相对路径即可），层序号让"违规"变成算术判定；同一份图上还能算出扇入与影响面（实测 `shared/constants.js` 波及 84% 的文件、`utils/http.js` 63%）。
- **边界**：规则要分级——循环与反向报错，跨领域警告起步；**存量违规冻结增量**（baseline 只许降不许升），不要一次清光，否则重构会被"顺带清架构"绑架。
- **追问**：扇入这个数字有什么用？→ 决定测试策略：扇入高的必须有单测，扇入低的（叶子模块）可以放手重构。

## 四、场景设计题

### Q28: 场景：实现一个支持十万条数据、可滚动可搜索的列表（虚拟滚动），怎么设计？（第 7 篇）

- **结论**：固定行高虚拟滚动 + 数据层过滤搜索 + 事件委托 + 性能度量，四件事一起做。
- **原理**：① 固定行高方案（`start = floor(scrollTop / rowH)`，可视区 + 缓冲区渲染，`total × rowH` 撑总高，`translateY` 平移）；② 稳定 key（用业务主键而非下标，否则输入框内容会串行）；③ 搜索在数据层过滤（纯函数）+ 输入防抖 200~300ms；④ 可视区外不渲染 DOM；⑤ 行内交互用事件委托；⑥ `scroll` 处理放 `requestAnimationFrame`，每帧只算一次；⑦ 性能度量（渲染时长/内存）。
- **边界**：动态行高有测量成本（前缀和 + 二分 + 增量更新），先固定行高起步；"可视区 + 缓冲（overscan 5~10）"提前渲染防白屏；`Math.min(total, ...)` 边界不能漏。
- **追问**：为什么搜索要在数据层做？→ 过滤是纯计算，不碰 DOM，可单测、不触发重渲染风暴；"渲染全部再 CSS 隐藏"会把 DOM 数量退回全量，虚拟滚动的收益全部交出。

### Q29: 前端权限系统怎么设计？（第 4 篇）

- **结论**：权限分三层——路由权限（动态路由 + 守卫）、按钮/操作权限（自定义指令）、数据权限；模型上采用 RBAC（用户-角色-权限码），前端只认权限码。
- **原理**：登录后按角色拉取权限码集合；路由层在 `beforeEach` 里用**同一份过滤函数**筛出可达路由并 `addRoute` 动态注册，无权限重定向 403/登录页；按钮层用自定义指令按权限码控制显隐；菜单树由过滤后的路由表直接派生（叶子按权限码剪、父节点因"子项全被剪"而整枝消失）。
- **边界**：前端权限防君子不防小人——真正的安全靠后端接口鉴权，前端只做体验与菜单收敛；动态路由注册后要重新导航（`return { ...to, replace: true }`），刷新时要有 `routesLoaded` 标记否则详情页会被踢回首页；权限变更后要有独立 refresh 时机。
- **追问**：动态菜单怎么实现？→ 由过滤后的路由表直接派生菜单树，加一条路由即出一个菜单；不要维护两份配置靠人工同步。

### Q30: 通用请求层（axios 封装）怎么设计？（第 5 篇）

- **结论**：统一实例 + 拦截器分层（请求侧注入 token/公共参数、响应侧统一解包与错误分流）+ HTTP 码与业务码分类处理 + 去重/并发上限/缓存/取消四项能力。
- **原理**：`create` 统一 baseURL 与超时；请求拦截器注入 token、加签名、防重复提交；响应拦截器按 HTTP 状态与业务 `code` 分流——成功解包 `data`、401 跳登录并刷新 token、业务错误统一提示；`AbortController` 支持取消（组件卸载/路由切换）；去重靠 in-flight 表复用 Promise（实测 5 次并发同 key 只发 1 次），表要在请求结束后才清。
- **边界**：业务码与 HTTP 码要分开处理（前者进 `then`、后者进 `catch`），不能混为一谈；取消信号要透传给调用方（`AbortSignal`）；错误处理要有"全局兜底 + 局部覆盖"两级；缓存必须有失效策略。
- **追问**：并发请求怎么控？→ 相同 key 去重（复用同一 Promise）+ 并发上限队列（实测 20 个 120ms 请求，串行 2491ms、上限 4 是 694ms、服务端峰值 4）；去重要放在并发控制之前。

### Q31: 大文件上传（切片/断点续传）怎么设计？（第 6 篇）

- **结论**：四个端点——`init`（含秒传判定）/ `part`（幂等接收）/ `status`（查缺片）/ `complete`（校验合并）；前端切片 + 并发上传 + 断点续传靠"已收分片列表"，秒传靠文件指纹。
- **原理**：`File.slice` 按固定大小（1~5MB）切分，每片计算 hash 并限制并发数（3~4）上传；上传前先 `init` 拿到 `uploadId` 与 `received`，只补 `missing`（实测掉线已传 3 片，重连只发 2 片）；整体文件 hash 用于秒传判断（实测第二次上传传输 0 B）；全部传完触发 `complete`，服务端缺片时返回 400 + `missing` 数组；进度 = 已确认分片 / 总分片。
- **边界**：**分片接收必须幂等**（同 index 重复到达只记一次），这是断点续传的地基；`uploadId` 按文件指纹复用、`chunkSize` 一经确定不许改；大文件哈希必须放 Web Worker / `crypto.subtle`（实测同步算 50MB 要 132ms，主线程完全不能交互）；合并后服务端必须重新校验哈希。
- **追问**：秒传怎么实现？→ 上传前按文件 hash 查服务端，已存在直接返回成功；但要注意指纹探测风险，且服务端不能只信客户端声明的 `fileHash`。

### Q32: 怎么设计一个组件库（数据结构/样式/主题/文档/规范）？（第 2 篇）

- **结论**：API 与数据模型先行（受控/非受控）、样式主题可配置（CSS 变量/设计令牌）、文档与规范（示例 + 类型 + 变更日志）是组件库的"门面"。
- **原理**：数据结构——props 契约（类型/默认值/受控模式）与内部状态分离；样式——CSS 变量设计令牌实现主题切换、BEM 命名防样式污染；文档——示例站点 + API 表格 + changelog 驱动升级；规范——lint 规则、语义化版本、破坏性变更策略。
- **边界**：headless 是趋势——行为与样式分离（Radix/TanStack），品牌样式交给团队掌控；组件库要控制破坏性变更频率。
- **追问**：组件库和设计系统什么关系？→ 设计系统 = 组件库 + 设计令牌 + 文档 + 规范，组件库是它的实现载体。

### Q33: 场景：一个 20 人的前端团队，代码越写越乱，怎么治理？（第 3 篇）

- **结论**：先量化再治理——画出依赖图，找出四类违规与高扇入文件，然后用"冻结增量"的方式把规约落进 CI。
- **原理**：① 静态扫描 import 生成层间依赖矩阵，违规分四类（反向依赖/绕过接口层/跨领域/循环依赖）；② 计算扇入与传递影响面，把改动风险量化（哪些文件动一次波及 80% 代码）；③ 定义分层与依赖方向，写进 ESLint 或 `dependency-cruiser`；④ 用 baseline 冻结存量违规，只允许下降；⑤ 补高扇入文件的测试。
- **边界**：不要一次清光存量——会把业务需求排在架构重构后面，工期不可控；跨领域引用这类"看起来能跑"的违规要警告起步；**新代码必须严格**，否则存量清理的速度赶不上新增的速度。
- **追问**：怎么说服团队接受这套规则？→ 把"改一个需求动几个文件""改这个文件波及多少文件"变成数字，用影响面说话，比讲设计原则有效。
