# 虚拟滚动与大数据渲染

## 一、虚拟滚动是一道算术题

十万条数据渲染不出来，不是因为框架慢，而是因为**DOM 节点本身就是成本**：每个列表项少则几个、多则几十个元素，十万行就是几十万到上百万个节点，光是创建与样式计算就要几秒。

虚拟滚动的思路是反直觉的：**列表里那一万行其实一行都不需要真实存在**。用户能看到的最大范围就是一个视口，所以只要"渲染视口内那几条、其余用空白占位"就够了。

于是问题从「怎么渲染十万条」变成一道算术题：**给定滚动位置，算出该渲染哪几条**。

> 摘自 `./code/eng-lab/scenarios/vscroll.mjs`（运行：`npm run vscroll`）

```js
/** 定高：可见区 + 上下缓冲区，返回该渲染的下标区间与内容容器的位移 */
export function rangeOf(scrollTop, { total, rowH, viewport, overscan = 0 }) {
    const visible = Math.ceil(viewport / rowH)
    const start = Math.max(0, Math.floor(scrollTop / rowH) - overscan)
    const end = Math.min(total, Math.floor(scrollTop / rowH) + visible + overscan)
    return { start, end, count: Math.max(0, end - start), offset: start * rowH }
}
```

三个值支撑起整个方案：

- **内容容器高度** = `total × rowH`，它把滚动条撑到正确长度——所以滚动条是"真的"，用户拖动手感与真实列表完全一致；
- **渲染区间** = `[start, end)`，只挂载这一段；
- **位移** = `start × rowH`，用 `translateY` 把这一段平移到视口对应的位置。

拿十万条跑几个典型位置：

```
=== 实验设置 ===
100000 条数据，行高 44px，视口 600px → 一屏能放下 14 条

--- 一、定高方案：滚动位置 → 该渲染哪几条 ---
| scrollTop  | 可见区间      | 渲染条数 | 内容容器高度 | 列表位移 translateY |
|------------|---------------|----------|--------------|---------------------|
| 0 px       | 0 ~ 13        | 14       | 4400000 px   | 0 px                |
| 2200 px    | 50 ~ 63       | 14       | 4400000 px   | 2200 px             |
| 44000 px   | 1000 ~ 1013   | 14       | 4400000 px   | 44000 px            |
| 4399956 px | 99999 ~ 99999 | 1        | 4400000 px   | 4399956 px          |
```

内容容器高度恒定在 4400000px，而渲染条数一直是 14——**这是虚拟滚动最关键的性质：渲染量与数据量无关**。

最后一行滚到底部只剩 1 条，是因为后面没有数据了（`Math.min(total, ...)` 截断）。这是边界处理，容易漏——漏掉就会渲染出不存在的行，或者算出的 `offset` 超出容器高度导致白屏。

## 二、和全量渲染的数量级差

把两个方案摆一起：

```
--- 二、和全量渲染的数量级差 ---
| 方案     | 挂载的列表项 | 相对全量 | 首屏可交互时间 |
|----------|--------------|----------|----------------|
| 全量渲染 | 100000       | 100%     | 随条数线性增长 |
| 虚拟滚动 | 14           | 0.01%    | 与条数无关     |
```

DOM 节点少了 99.99%，而且这个比值**只由「视口高度 ÷ 行高」决定**。把数据从 1 万加到 100 万，挂载的仍然是 14 条——这是虚拟滚动与「分页」「懒加载」最本质的区别：

| 方案 | 首屏成本 | 滚动体验 | 总高度 |
| ---- | ---- | ---- | ---- |
| 分页 | 与页大小相关 | 需要点击，无法连续滚动 | 只有当前页 |
| 懒加载（无限滚动） | 与已加载量相关，越滚越慢 | 连续，但数据量大后内存持续增长 | 持续增长 |
| 虚拟滚动 | 恒定 | 连续 | 恒定（`total × rowH`） |

值得注意的是：虚拟滚动省下的是 DOM 与渲染，**不省内存**。数据列表本身还在，十万条对象该占多少内存还是多少。真正数据量到百万级、且内存也扛不住时，要配合**数据分片**（只保留下载过的窗口）或后端游标分页。

## 三、缓冲区：拿 DOM 换的是什么

只渲染可见区会有一个问题：滚动是连续的，而渲染是原子的。用户快速滚动时，如果渲染只能"刚好覆盖一屏"，就会出现短暂空白。

于是引入 `overscan`——视口上下各多渲染若干条：

```
--- 三、缓冲区：拿 DOM 换的是"快速滚动不白屏" ---
| overscan | 渲染条数 | 多渲染 | 作用                             |
|----------|----------|--------|----------------------------------|
| 0        | 14       | +0     | 刚好一屏，快速滚动时容易看到空白 |
| 5        | 24       | +10    | 上下各预渲染 5 条，覆盖惯性滚动  |
| 10       | 34       | +20    | 覆盖更快的滚动速度               |
| 20       | 54       | +40    | DOM 偏多，收益递减               |
```

`overscan` 的代价是**线性**的（多渲染 `overscan × 2` 条），收益却是**递减**的：`5 → 10` 让缓冲条数翻倍，但实际能多覆盖的滚动速度提升有限。

实用值是 `5~10`。真正需要更快滚动的场景（如表头固定、拖动滚动条），靠加大缓冲不划算，应该改用**空位骨架**：滚动时立即渲染带固定高度的占位块，等滚动停下再换成真实内容。

另一种常见的配套手段是**滚动节流**：把 `scroll` 事件的处理放进 `requestAnimationFrame` 里，每帧只算一次区间。滚动事件一秒能触发上百次，每次都触发框架更新会直接把主线程打满。

## 四、不定高：前缀和加二分

上面的公式有一个前提：**每一行高度相同**。一旦行高不定（评论内容长短不一、图片高度不定），`scrollTop ÷ rowH` 就不再成立。

不定高方案要维护一份**前缀和数组**：`offsets[i]` 表示前 `i` 条的总高度，于是"第 i 条起始于哪里"变成一次数组读取，而"某个偏移量落在第几条"变成一次**二分查找**：

> 摘自 `./code/eng-lab/scenarios/vscroll.mjs`（运行：`npm run vscroll`）

```js
/** 找第一个前缀和 >= 目标偏移的下标（不定高场景的起点定位） */
export function lowerBound(offsets, target) {
    let lo = 0
    let hi = offsets.length - 1
    let steps = 0
    while (lo < hi) {
        steps++
        const mid = (lo + hi) >> 1
        if (offsets[mid] < target) lo = mid + 1
        else hi = mid
    }
    return { index: lo, steps }
}
```

为什么不用线性扫描？因为每次滚动都要定位一次起点，线性扫描的开销会随数据量放大：

```
--- 四、不定高：前缀和 + 二分 vs 线性扫描 ---
| 方案   | 定位方式                     | 单次查找步数 | 单次查找耗时 |
|--------|------------------------------|--------------|--------------|
| 定高   | scrollTop ÷ rowH             | 1            | 常数时间     |
| 不定高 | 二分（100000 条 → 约 17 步） | 17           | 0.070 µs     |
| 不定高 | 线性扫描（对照）             | 50001        | 55.53 µs     |
```

在总高 5605851px 的列表里滚到中线：二分 16 步命中第 50000 条，线性扫描 50001 步才到——**两者结果完全一致（下标 50000），差的是 3 个数量级的步数**，单次耗时相差约 800 倍。滚动是每秒触发上百次的操作，这个差距会直接体现为掉帧。

（定高那格的耗时写"常数时间"而不是具体数字：它是一次除法加几个算术运算，微秒级的测量会受对象分配干扰，测出来的数反而比二分难看——那是测量方式的假象，不是算法事实。）

前缀和本身要重建：

```
前缀和数组本身要重建 100001 个元素，耗时 736.410 µs —— 所以只在行高集合变化时重建，
滚动过程中只读不写；行高变化时用增量更新而不是整表重算。
```

736µs 建一次没问题，但如果每次滚动都重建，就等于每帧多花 0.7ms，再加上十万次的分配，GC 压力会很明显。所以不定高的工程做法是：

- **`offsets` 只在行高集合变化时重建**；滚动过程中只读；
- **单行高度变化**（图片加载完成、文字展开）用**增量更新**：只把 `i` 之后的部分加上高度差，而不是整表重算；
- **未测量过的行先用估算高度**（按内容类型的经验值），测到真实高度后再回填。这就是"估算高度"方案——首次滚动位置有轻微偏差，但避免了预测量全部行的成本。

不定高的复杂度显著高于定高。**能用定高的场景（表格、固定卡片）就不要做不定高**：一行除法与「前缀和 + 二分 + 高度缓存 + 增量更新」之间，是数量级的工程量差。

## 五、滚动锚定：别让内容跳一下

一个容易被忽略、但用户一眼就能看出问题的场景：往列表**顶部**插入数据。

> 摘自 `./code/eng-lab/scenarios/vscroll.mjs`（运行：`npm run vscroll`）

```js
    const anchorIndex = 100
    const inserted = 20
    const insertHeight = inserted * ROW_H
```

```
--- 五、上方插入数据时的滚动锚定 ---
| 处理方式              | 插入前视口首条 | 插入后视口首条 | 视觉位移 |
|-----------------------|----------------|----------------|----------|
| 不动 scrollTop        | 100            | 120            | 880 px   |
| scrollTop += 插入总高 | 100            | 100            | 0 px     |
```

插入 20 条后不补偿 `scrollTop`，用户看到的内容会整体往下跳 880px——他本来在看第 100 条，突然变成在看第 100 条上方的内容（实际是视口首条变成了第 120 条，视觉上内容被顶下去了）。

补偿方式就是一行加法：`scrollTop += insertedCount × rowH`。不定高场景下，就是加上插入行的实际高度和。

同样的现象还有两个触发源：

- **图片加载完成**把上方内容撑高（这是最隐蔽的一种，因为发生在滚动停止之后）；
- **字体切换 / 折叠面板展开**。

现代浏览器提供了 `overflow-anchor`（默认 `auto`）来做**滚动锚定**，能自动处理部分场景（尤其是图片加载）。但它对虚拟列表不适用——虚拟列表的 DOM 在不停替换，浏览器的锚定算法找不到稳定的锚点。所以虚拟列表必须自己做补偿。

## 六、剩下的细节

**key 必须稳定且唯一**。虚拟滚动会复用列表项，框架靠 key 认领哪一项是"原来的谁"。用数组下标当 key，滚动时输入框里的内容会串行到别的行上——这是虚拟列表最经典的 bug。正确做法是用数据的业务主键（`order.id`）。

**行内事件用事件委托**。一万行里每行挂三个监听器，就是三万个函数对象；虚拟列表只渲染 14 行时问题不大，但配合 overscan 与频繁的挂载/卸载，监听器的创建与解绑成本会显出来。把监听器挂在容器上，用 `event.target.closest()` 找到具体行，是更稳的写法。

**搜索与筛选在数据层做**。过滤是纯计算，不碰 DOM：

> 示意片段（无配套脚本）

```js
const filtered = useMemo(() => rows.filter(r => r.no.includes(keyword)), [rows, keyword])
```

把过滤结果喂给虚拟列表，而不是"渲染全部再 CSS 隐藏"。后者看起来实现简单，但它把 DOM 数量退回到全量，虚拟滚动的收益全部交出。搜索框本身要防抖（200~300ms），否则每敲一个字符就重建一次十万条的数组。

**和性能模块的分工**：虚拟滚动相对全量渲染能省下多少首屏时间、内存怎么测、长列表还有哪些优化手段（`content-visibility`、`contain`），属于性能话题，见性能优化模块；本篇只讲实现本身。
