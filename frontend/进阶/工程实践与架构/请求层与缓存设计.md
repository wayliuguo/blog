# 请求层与缓存设计

## 一、请求层管什么、不管什么

每个项目早晚都会长出一个 `utils/request.js`。它变胖的原因通常是职责没划清：一开始只管发请求，后来加了 token 注入、错误提示、loading 状态、重试、缓存、防重复提交，最后连业务判断也搬了进去——于是它变成一个没人敢改的文件。

清晰的边界是：**请求层只管「怎么发、怎么复用、怎么解析错误」，不含任何业务语义**。

```
请求层该管的                          请求层不该管的
  ├─ baseURL / 超时 / 公共头            ├─ "订单列表只能查 30 天" 这类业务规则
  ├─ token 注入与刷新                   ├─ 具体接口的路径与字段拼装（那是 api 层）
  ├─ HTTP 错误与业务码的分流            ├─ 页面 loading / 空态 / 文案
  ├─ 拦截器管道                         ├─ 弹窗提示的样式与位置
  ├─ 请求去重 / 并发上限                 └─ 需要跳路由的逻辑（401 除外）
  ├─ 缓存与失效
  └─ 取消与重试的能力
```

本模块实验台里有一个几十行的精简实现，把请求层常见的四件事（拦截器、去重、缓存、并发上限）摊开：

## 二、拦截器是洋葱

请求拦截器的执行顺序是个高频面试题，也是高频写错的地方。实测最直观——注册三个请求拦截器、三个响应拦截器，看它们按什么顺序跑：

> 摘自 `./code/eng-lab/scenarios/request.mjs`（运行：`npm run request`）

```js
    /** 洋葱：最后注册的请求拦截器在最外层，最先注册的响应拦截器在最外层 */
    function buildChain(path) {
        const steps = [...reqs].reverse().concat([send]).concat(ress)
        return async () => {
            let ctx = { path }
            for (const step of steps) ctx = await step(ctx)
            return ctx
        }
    }
```

```
--- 一、拦截器的执行顺序 ---
1. 请求拦截器 C：埋点开始
2. 请求拦截器 B：加公共参数
3. 请求拦截器 A：注入 token
4. 发请求 /api/list?q=interceptor
5. 响应拦截器 A：解包 data
6. 响应拦截器 B：业务码校验
7. 响应拦截器 C：埋点结束
```

注册顺序 A、B、C，执行顺序 C、B、A → 网络 → A、B、C：

- **请求拦截器后注册的先执行**（新的在外层），这样后注册的埋点能包住先注册的鉴权；
- **响应拦截器先注册的先执行**，于是它和请求侧正好对称；
- 合起来是一个完整的洋葱：**最外层永远是"最后注册的请求拦截器"与"最先注册的响应拦截器"**。

这个顺序和 axios 的实现一致（`request` 拦截器用 `unshift` 插入调用链，`response` 拦截器用 `push`），所以迁移到 axios 时行为不变。

实务含义：想包住所有请求的埋点，**注册在最后**；想最先处理响应体解包，**注册在最前**。写反了就会出现「埋点在鉴权之前跑，用户未登录时也上报了一次」，这种 bug 很难从代码表面看出来。

拦截器的另一个常见错误是把它当业务钩子用：在响应拦截器里 `if (url === '/api/order') {...}`。一旦开始判断 url，说明这段逻辑属于 api 层，不属于请求层。

## 三、竞态：慢请求覆盖掉新结果

搜索框是最容易复现的场景。用户输入 A（服务端 200ms），觉得不对改成 B（服务端 50ms）。B 的响应先到、A 的后到：

```
--- 二、竞态：慢请求后到，把新结果覆盖掉 ---
| 发出的请求 | 服务端耗时 | 到达顺序 | 无保护时对视图的写入 |
|------------|------------|----------|----------------------|
| B          | 50 ms      | 第 1 个  | 写入 B               |
| A          | 200 ms     | 第 2 个  | 写入 A               |
```

最终视图停留在「A」——用户最后输入的是 B，屏幕上却是 A。**这不是时序巧合，只要网络抖动就一定复现**：接口变慢、用户手速快，两个条件满足一个就够了。

两种保护手段，第一种是给请求发号：

```
| 请求 | 是否写入视图 | 原因               |
|------|--------------|--------------------|
| A    | 丢弃         | 已有更新的请求发出 |
| B    | 写入         | 它是最新的一次请求 |
```

实现只需一个自增令牌 + 一次比对：

> 摘自 `./code/eng-lab/scenarios/request.mjs`（运行：`npm run request`）

```js
    let token = 0
    const guardedWrites = []
    async function search(q, latency) {
        const mine = ++token
        const data = await fetch(`${server.base}/api/list?q=${q}&ms=${latency}`).then(r => r.json())
        if (mine !== token) return { q, applied: false, reason: '已有更新的请求发出' }
        guardedWrites.push(q)
        return { q, applied: true, data: data.q }
    }
```

第二种是 `AbortController`：发新请求时直接 `abort()` 掉上一条。它比令牌法更彻底——响应根本不会到达，连 `.then` 都不执行，省掉了处理逻辑。缺点是需要把 `signal` 一路透传到 `fetch`，并且要区分「主动取消」与「真错误」：

> 示意片段（无配套脚本）

```js
catch (err) {
    if (err.name === 'AbortError') return   // 主动取消，不是错误，不要上报
    throw err
}
```

把 `AbortError` 当成错误上报，是监控里最常见的噪声来源之一。它的数量几乎等于用户操作次数，会把真正的错误淹没。

## 四、去重与并发上限

**去重**解决的是「同一时刻多个组件要同一份数据」。一个页面里 Header 和侧边栏同时请求用户信息，不去重就发两次。实现是一张在途表：

> 摘自 `./code/eng-lab/scenarios/request.mjs`（运行：`npm run request`）

```js
    function shared(path, key) {
        let p = inflight.get(key)
        const reused = !!p
        if (!p) {
            p = once(path).then(ctx => {
                cache.set(key, { value: ctx.data, at: Date.now() })
                inflight.delete(key)
                return ctx
            })
            inflight.set(key, p)
        }
        return { promise: p, reused }
    }
```

实测 5 个并发调用同一个 key：

```
--- 三、去重：同一时刻的相同请求只发一次 ---
| 情形         | 并发调用 | 真实发出请求 | 命中去重 | 服务端收到 |
|--------------|----------|--------------|----------|------------|
| 有去重（实跑） | 5        | 1            | 4        | 1          |
| 无去重（推演） | 5        | 5            | 0        | 5          |
```

注意 `inflight.delete(key)` 写在 `.then` 里，而不是请求发出后立刻删——这是去重能不能生效的关键。**表要在请求结束后才清**，否则第二个调用进来时表已经空了。

去重只能防"同时发生"，防不了"前后脚发生"（用户快速切了两个 tab 再切回来）。后者要靠缓存或业务层节流。

**并发上限**解决的是「一次性打出去太多请求」。进入一个页面时有 20 个接口要调，全部同时发出会：占满浏览器连接数、抢带宽、让首屏关键请求排在队尾。

用一个并发池把 20 个请求压进不同数量的通道：

```
--- 四、并发上限：20 个请求压进 4 条通道 ---
| 配置       | 总耗时  | 服务端观测并发峰值 | 服务端收到请求数 |
|------------|---------|--------------------|------------------|
| 并发上限 1 | 2491 ms | 1                  | 20               |
| 并发上限 4 | 694 ms  | 4                  | 20               |
```

20 × 120ms 的串行是 2400ms 量级，压到 4 条通道后变成 6 轮 ≈ 720ms；峰值停在 4 而不是 20——这就是「排队」与「打满」的区别。

池子本身是通用的，串行只是 `limit = 1` 的特例：

> 摘自 `./code/eng-lab/harness/pool.mjs`（运行：`npm run request`）

```js
export function createPool(limit) {
    let active = 0
    let peak = 0
    const queue = []

    function pump() {
        while (active < limit && queue.length) {
            const { task, resolve, reject } = queue.shift()
            active++
            peak = Math.max(peak, active)
            Promise.resolve()
                .then(task)
                .then(
                    value => {
                        active--
                        resolve(value)
                        pump()
                    },
```

重复的请求（相同 key）如果先经过去重表，就不会占用池子的名额——**去重放在并发控制之前**，两条机制才不会互相浪费。

并发数怎么定？不是越大约好：同域 HTTP/1.1 浏览器只有 6 条连接，超过就得排队；HTTP/2 多路复用没有连接数上限，但服务端仍有承载上限，而且所有请求抢同一条 TCP 连接的带宽。`4~6` 是常见的安全区间，同时**首屏关键请求要能插队**（优先级队列，或直接走独立的通道）。

## 五、缓存：TTL 与 stale-while-revalidate

请求层的第三件事是缓存。最基础的 TTL 缓存实测：

```
--- 五、TTL 缓存与 stale-while-revalidate ---
| 第几次取                | 返回值来源 | 耗时     | 缓存年龄 | 是否发请求 |
|-------------------------|------------|----------|----------|------------|
| 第 1 次                 | network    | 136.0 ms | —        | 是         |
| 第 2 次（TTL 300ms 内） | fresh      | 0.1 ms   | 0 ms     | 否         |
```

时延从 136ms 掉到 0.1ms，且完全没有走网络。Hit 判定就是一次时间戳比较：

> 摘自 `./code/eng-lab/scenarios/request.mjs`（运行：`npm run request`）

```js
    async function get(path, { key = path, useCache = false, force = false } = {}) {
        if (useCache && !force) {
            const hit = cache.get(key)
            if (hit) {
                const age = Date.now() - hit.at
                if (age < ttl) return { data: hit.value, from: 'fresh', age, network: false }
                if (swr) {
                    const { promise } = shared(path, key)
                    background.push(promise)
                    return { data: hit.value, from: 'stale', age, network: false }
                }
            }
        }
        const { promise, reused } = shared(path, key)
        const ctx = await promise
        return { data: ctx.data, from: reused ? 'dedup' : 'network', age: 0, network: !reused }
    }
```

`force` 参数（强制绕过缓存）是必须的——没有它，"用户点刷新按钮"这种需求就没法实现。

TTL 缓存的痛点是过期那一刻的等待：用户等了 300ms 缓存过期，第 301ms 进来还是要等一次完整的网络往返。**stale-while-revalidate**（SWR）解决这个：过期后先把旧值交出去，同时在后台刷新。

```
| 阶段           | 返回值来源 | 耗时         | 服务端收到的请求数 |
|----------------|------------|--------------|--------------------|
| 首次           | network    | 135.7 ms     | 1                  |
| 过期后立即返回 | stale      | 1.00 ms      | 2                  |
| 后台刷新完成   | —          | 不阻塞调用方 | 2                  |
```

过期后那一次只用了 1.00ms 就把旧值交出去了，同时后台悄悄补了一次请求。代价是用户这次看到的是「上次的数据」。

所以 SWR 的适用范围很明确：

- **适合**：能容忍旧一点的列表、详情、统计。用户感知到的是"秒开"，而不是"数据晚了 100ms"；
- **不适合**：余额、库存、订单状态、任何会因此产生错误操作的数据。这些应该直接走网络 + loading，甚至每次强制刷新。

缓存还有一个必须配套的东西：**失效策略**。只写不删的缓存迟早会把脏数据留在用户屏幕上。三种失效方式按可靠度排：

| 方式 | 做法 | 适用 |
| ---- | ---- | ---- |
| 主动失效 | 写操作成功后就地 `cache.delete(key)` | 用户自己的增删改 |
| 标签失效 | 按资源打标签，一次清一组（列表 + 详情） | 有关联关系的资源 |
| 短 TTL 兜底 | TTL 取小（如 5s），靠时间自愈 | 拿不准的、别人改的数据 |

最有效的一种是**写操作后清掉相关 key**，成本极低。最不该做的是设一个很长的 TTL 然后指望"反正会过期"。

## 六、错误分类与取消

请求层最后一个容易含糊的地方：错误怎么分。至少要分成四类，处理方式完全不同：

| 类别 | 例子 | 处理 |
| ---- | ---- | ---- |
| 网络/超时 | `TypeError: Failed to fetch`、`AbortError` | 可重试；主动取消不上报 |
| HTTP 错误 | 4xx / 5xx | 401 跳登录并刷新 token；403 提示无权限；5xx 可重试 |
| 业务码错误 | HTTP 200 但 `code !== 0` | 统一提示，具体文案由业务决定 |
| 代码错误 | 响应体结构与预期不符 | 上报监控，不要静默吞掉 |

把前两类塞进 `.catch`、后两类放进 `.then`，是最容易在团队内达成一致的划分。混在一起（例如业务码错误也走 catch）会导致「统一错误提示」把业务提示覆盖掉。

取消还有一处必须做：**透传 `AbortSignal` 给调用方**。

> 示意片段（无配套脚本）

```js
const ac = new AbortController()
onUnmounted(() => ac.abort())
const data = await get('/api/list', { signal: ac.signal })
```

组件卸载时取消请求，收益不只是省流量——更常见的是避免响应回来后 `setState` 落在已卸载的组件上，那会产生一批难以定位的告警。

重试与幂等属于协议与可靠性话题，不在本篇展开：什么时候可以重试、指数退避与抖动怎么算、`Idempotency-Key` 怎么用，见 [网络可靠性与弱网](../网络与协议进阶/网络可靠性与弱网.md)。请求层要做的是把重试能力**做在可配置的开关上**，而不是在业务代码里写 `for` 循环。
