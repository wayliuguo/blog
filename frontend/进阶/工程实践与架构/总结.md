# 模块总结 · 工程实践与架构

## 知识主线

两篇不是并列的知识点，而是一条有依赖关系的链，每一篇都在回答上一篇留下的问题：

```
01 设计模式在前端（模式语言：单例 / 观察者·发布订阅 / 工厂 / 策略 / 代理 / 装饰器 / 适配器 / 组合 / 命令） ★主轴
        │  先掌握"解耦与复用"的通用词汇，读源码不迷路、写代码抗变化
        ▼
02 组件设计（把模式落到界面单元：原则 / 划分 / props·API / 复用手段 / 跨框架 / 抽象层级）
        │  它在回答上一篇的什么问题：有了模式思路，"界面单元"具体怎么拆、怎么对外设计、怎么复用
```

本模块的主轴是**解耦**：01 给出解耦与复用的模式词汇——发布订阅、策略、适配器、代理、装饰器本质上都在"把变化点隔开"；02 把"在正确层次上做出正确的解耦"落到组件设计的每一个环节——单一职责、容器与展示分离、受控与非受控、组合优于继承、Hooks 复用、抽象层级。两篇一篇讲思想、一篇讲落地，主轴始终是解耦。

## 分篇知识点

### 01-设计模式在前端

- **九种高频模式一句话**
  - **单例（Singleton）**：保证一个类全局只有唯一实例（构造器判断已有实例直接返回），用于全局 store、事件总线、Toast 弹窗
  - **观察者 / 发布订阅（Observer / Pub-Sub）**：一方变化、依赖它的多方自动收到通知；Observer 目标直持观察者列表，Pub/Sub 中间加事件中心彻底解耦，如 Vue `reactive`、事件总线 `emit/on`
  - **工厂（Factory）**：把"创建对象"的逻辑集中起来，由传入参数决定返回哪种具体实例，调用方不关心构造细节，用于按类型建组件、按钮、弹窗
  - **策略（Strategy）**：把一组可互相替换的算法各自封装成对象，由上下文选择使用，用组合替代大量 if/else，典型是表单校验
  - **代理（Proxy）**：不改变原对象、通过替身控制访问、在访问前后插入额外逻辑，如防抖节流、`Proxy` 响应式、接口加 token 的拦截器
- **装饰器 / 适配器 / 组合 / 命令**
  - **装饰器（Decorator）**：不修改原函数/类，用"包装"动态叠加新能力，如 React HOC、AOP 埋点/日志/鉴权
  - **适配器（Adapter）**：把不兼容的接口翻译成调用方期望的接口，如统一后端/第三方数据结构、统一浏览器 API 差异
  - **组合（Composite）**：把对象组织成树形结构，"叶子"与"整体"使用一致接口，如组件递归渲染目录树
  - **命令（Command）**：把一个操作封装成对象（含参数与执行），支持延迟执行、排队与撤销/重做，如编辑器历史
- **选型对照表**
  - **创建与结构类**：全局只该有一个→单例；想统一参数化创建→工厂；树形结构→组合
  - **行为与协作类**：一方变多方受影响→观察者/发布订阅；一堆可替换算法想干掉 if/else→策略；想撤销重做/回放→命令
  - **接口与增强类**：想在访问前后插逻辑→代理；不改原对象加能力→装饰器；接口不匹配→适配器
- **实践建议**
  - **别为模式而模式**：先有真实的"变化点"再上模式，否则是过度设计
  - **优先组合而非继承**：模式大多建立在"组合 + 依赖注入"之上
  - **读源码对号入座**：读 Vue / Redux / axios 源码时主动识别其中的模式，是掌握模式最快的方式
- **最小实现**
  - **`pubsub.html`**：手写事件中心（EventHub），两个互不引用的组件通过发布/订阅实现解耦
  - **`store.html`**：手写单例 store + `subscribe` 订阅更新，多个组件被同一 store 驱动
  - **解耦本质**：双方不直接引用对方，只通过一个中间调度者（事件中心 / store）建立发布-订阅关系

### 02-组件设计

- **设计原则**
  - **单一职责（SRP）**：解释组件时用到"并且/还有"即职责过重；拆分目标不是越细越好，而是"单个组件的变更原因唯一"
  - **SOLID 前端化**：开闭原则最具指导性——用 props/slots 扩展能力而非改组件内部源码；接口隔离（props 按用途拆分）、依赖倒置（依赖数据契约而非具体实现）
  - **可复用性与可维护性**：两者需平衡，警惕"复用诅咒"；用"三次法则"——第三次出现才真正抽象成可复用单元，防过度抽象
- **划分策略**
  - **原子设计（Atomic Design）**：atoms → molecules → organisms → templates → pages 五层，提供团队统一的命名与分工语言
  - **容器 vs 展示组件**：容器管数据获取/状态/业务逻辑，展示组件只接收 props 渲染，可在无后端接入下开发测试
  - **受控 vs 非受控**：按"数据由谁拥有"取舍——外部要验证/重置/联动用受控，本地自洽用非受控；成熟组件库同时支持两者（未传 `value` 自管、传了走受控）
- **props 与事件通信**
  - **props 设计要点**：收窄职责（不塞业务大对象）、合理默认值、单向数据流（子组件只读、改由回调上抛）、TS 类型即文档
  - **子传父**：React 用回调 props、Vue 用 emits 声明事件，命名统一为 `onChange`/`onSelect` 等动词
  - **深层跨层通信**：交给 Context / provide-inject / 状态库，而非层层透传
  - **组合优于继承**：前端组件设计的铁律——用 children、插槽、自定义渲染灵活装配，业务逻辑复用走自定义 Hook / Composable 而非父类继承
- **API 设计**
  - **语义化命名**：组件名大驼峰、用途明确（`DateRangePicker`）；props 用社区通用语义（`value`/`onChange`/`disabled`），避免 `flag`/`data` 等含糊命名
  - **默认值策略**：可选 props 给安全合理的默认值；别用"假默认值"掩盖缺陷——功能必须有值时应设为必填让 TS 报错
  - **向前兼容**：新增属性可选 + 默认关闭、弃用先 deprecated 标记保留 N 个大版本、semver 约束（major/minor/patch）+ CHANGELOG 记录迁移路径
- **复用手段演进**
  - **HOC（高阶组件）**：接收组件返回增强组件，历史悠久复用方便，缺点是 props 来源混乱、多次包装成"包装地狱"、难以在逻辑层复用
  - **Render Props**：把内部状态透传给 `render`/children 函数渲染，数据来源清晰，但多层嵌套成回调地狱
  - **Hooks / Composable**：把有状态逻辑抽成独立函数，逻辑与 UI 彻底解耦、可自由组合可测试，是当今复用的首选载体
- **跨框架与抽象层级**
  - **跨框架四条路线**：无框架底层 + 各自适配层、Web Components（标准 Custom Elements，任何框架可用）、headless 模式（无样式逻辑核心 + 框架绑定层）、统一运行时（编译期优化，仍是各自框架）
  - **框架无关 vs 框架先行**：单一框架不跨端时优先框架原生组件，别为"理论上可能复用"引入抽象层；"真正能跨端的是业务领域层逻辑而非 UI 层"
  - **复合组件**：父组件用 Context / provide-inject 提供上下文、多个子组件共享，自由排列布局而状态由父组件统一管理（如 Tabs/TabPane）
  - **配置化渲染引擎**：用 schema 描述组件树与 props 由运行时统一渲染，适合低代码、表单引擎场景，代价是性能与调试成本上升
  - **headless 库**：行为与样式彻底分离（Radix / Headless UI / TanStack / React Aria），样式完全由使用方决定，便于适配设计系统
