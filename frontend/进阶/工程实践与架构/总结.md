## 1. 设计模式在前端

### 1.1 模式的本质与高频六种

设计模式是"在特定场景下被反复验证的解决方案模板"——不是语法，是可复用的结构约定。前端高频的六种一句话：

| 模式 | 一句话 |
| ---- | ---- |
| 单例（Singleton） | 保证一个类全局只有唯一实例（构造器判断已有实例直接返回），用于全局 store、事件总线、Toast 弹窗 |
| 观察者 / 发布订阅 | 一方变化、依赖它的多方自动收到通知，如 Vue `reactive`、事件总线 `emit/on` |
| 工厂（Factory） | 把"创建对象"的逻辑集中起来，由传入参数决定返回哪种具体实例，调用方不关心构造细节 |
| 策略（Strategy） | 把一组可互相替换的算法各自封装成对象，由上下文选择使用，用组合替代大量 if/else，典型是表单校验 |
| 代理（Proxy） | 不改变原对象、通过替身控制访问、在访问前后插入额外逻辑，如防抖节流、`Proxy` 响应式、接口加 token 的拦截器 |
| 装饰器（Decorator） | 不修改原函数/类，用"包装"动态叠加新能力，如 React HOC、AOP 埋点/日志/鉴权 |

**观察者 vs 发布订阅** 是高频辨析点：

```
观察者  目标直持观察者列表，状态变了直接 notify → 双方互相知道对方存在
发布订阅 中间加一个事件中心（EventBus），通过 emit/on 转发 → 发布者与订阅者完全解耦
Vue 响应式属于观察者（依赖收集直连）
```

事件总线解耦但容易失控——事件名无约束、难追踪，大项目慎用。

### 1.2 装饰器 / 适配器 / 组合 / 命令

- **装饰器（Decorator）**：不修改原函数/类，用"包装"动态叠加新能力，如 React HOC、AOP 埋点/日志/鉴权。
- **适配器（Adapter）**：把不兼容的接口翻译成调用方期望的接口，如统一后端/第三方数据结构、统一浏览器 API 差异。
- **组合（Composite）**：把对象组织成树形结构，"叶子"与"整体"使用一致接口，如组件递归渲染目录树。
- **命令（Command）**：把一个操作封装成对象（含参数与执行），支持延迟执行、排队与撤销/重做，如编辑器历史。

### 1.3 选型对照

按要解决的"变化点"选型：

| 类别 | 变化点 | 选什么 |
| ---- | ---- | ---- |
| 创建与结构类 | 全局只该有一个 | 单例 |
| | 想统一参数化创建 | 工厂 |
| | 树形结构 | 组合 |
| 行为与协作类 | 一方变、多方受影响 | 观察者 / 发布订阅 |
| | 一堆可替换算法想干掉 if/else | 策略 |
| | 想撤销重做 / 回放 | 命令 |
| 接口与增强类 | 想在访问前后插逻辑 | 代理 |
| | 不改原对象加能力 | 装饰器 |
| | 接口不匹配 | 适配器 |

**工厂 / 策略 / 装饰器** 前端体现对照：

| 模式 | 管的"变化点" | 机制 | 边界 |
| ---- | ---- | ---- | ---- |
| 工厂 | 创建 | 按配置产出实例、隐藏细节 | 滥用让创建路径变深 |
| 策略 | 算法替换 | 一组可互换算法由上下文选择，组合替代 if/else，新增一种加一个策略对象（开闭原则） | 策略过多要配注册表管理 |
| 装饰器 | 职责叠加 | HOC/拦截器包一层，不动原逻辑加能力 | 叠加过多难以调试 |

### 1.4 实践建议与最小实现

实践建议：

- **别为模式而模式**：先有真实的"变化点"再上模式，否则是过度设计；只有一处使用、变化频率极低时，直写比抽象更便宜。
- **优先组合而非继承**：模式大多建立在"组合 + 依赖注入"之上。策略与 if/else 的本质区别在于：策略把分支收敛成可组合、可独立测试的对象集合。
- **读源码对号入座**：读 Vue / Redux / axios 源码时主动识别其中的模式，是掌握模式最快的方式。

最小实现（两个演示页面）：

- `pubsub.html`：手写事件中心（EventHub），两个互不引用的组件通过发布/订阅实现解耦。
- `store.html`：手写单例 store + `subscribe` 订阅更新，多个组件被同一 store 驱动。
- **解耦本质**：双方不直接引用对方，只通过一个中间调度者（事件中心 / store）建立发布-订阅关系。

单例的坑：全局唯一让依赖不显式、难测试隔离，共享可变状态是 bug 温床——测试要构造函数收依赖 + 提供 `reset` 方法，避免测试间污染。

## 2. 组件设计

### 2.1 设计原则：SOLID 前端化

- **单一职责（SRP）**：解释组件时用到"并且/还有"即职责过重；拆分目标不是越细越好，而是"单个组件的变更原因唯一"。
- **SOLID 前端化**：开闭原则最具指导性——用 props/slots 扩展能力而非改组件内部源码；接口隔离、依赖倒置。
- **可复用性与可维护性**：两者需平衡，警惕"复用诅咒"；用"三次法则"——第三次出现才真正抽象，防过度抽象。

状态管理划分（状态就近原则）：单一组件用的状态放本地；多组件共享 + 跨页面 + 需持久化才进全局 store，否则本地状态 + props 提升；派生值不存状态（由源状态计算），存了会"双份真相"，改一处忘另一处。滥用全局 store 让数据流失控、组件难复用——状态越少越可预测。

### 2.2 划分策略：原子设计 / 容器 vs 展示 / 受控 vs 非受控

- **原子设计（Atomic Design）**：atoms → molecules → organisms → templates → pages 五层，提供团队统一的命名与分工语言。
- **容器 vs 展示组件**：

| 维度 | 容器组件 | 展示组件 |
| ---- | ---- | ---- |
| 数据 | 管数据获取 / 状态 / 业务逻辑 | 只接收 props 渲染 |
| 后端 | 依赖后端接入 | 可在无后端接入下开发测试 |

- **受控 vs 非受控**：按"数据由谁拥有"取舍——外部要验证/重置/联动用受控，本地自洽用非受控；成熟组件库同时支持两者。
- **组件边界三判据**：变化频率是否独立、是否有可复用的数据闭环、是否能独立测试；抽组件是为了隔离变化——频率低的变化不值得抽（过度抽象比重复更贵）。

### 2.3 props 与事件通信

- **props 设计要点**：收窄职责、合理默认值、单向数据流、TS 类型即文档。
- **子传父**：React 用回调 props、Vue 用 emits 声明事件，命名统一为 `onChange`/`onSelect` 等动词。
- **深层跨层通信**：交给 Context / provide-inject / 状态库，而非层层透传。
- **组合优于继承**：用 children、插槽、自定义渲染灵活装配；逻辑复用走自定义 Hook / Composable 而非父类继承。

通信方式按耦合度递进选择：

| 方式 | 方向 / 场景 | 说明 |
| ---- | ---- | ---- |
| props | 自上而下 | 单向数据流最可预测 |
| 事件回调 / emit | 自下而上 | 契约显式 |
| provide / inject 或状态库 | 跨层 | 解决深层传递 |
| 全局状态 | 多组件共享 | 适合共享 + 跨页面 + 需持久化 |
| 事件总线 | 无关组件 | 解耦但难追踪，最后手段 |

**单向数据流**：数据单向流动（状态 → 视图 → 事件 → 状态），状态唯一来源 + 视图只消费派生 + 修改必须走明确路径 → 可预测、可调试、可单测。组件不暴露内部状态，只暴露结果事件——简单页面套全局状态管理是过度设计。

### 2.4 API 设计：命名、默认值与兼容

- **语义化命名**：组件名大驼峰、props 用社区通用语义（`value`/`onChange`/`disabled`），避免 `flag`/`data` 等含糊命名。
- **默认值策略**：可选 props 给安全合理的默认值；别用"假默认值"掩盖缺陷——功能必须有值时应设为必填让 TS 报错。
- **向前兼容**：新增属性可选 + 默认关闭、弃用先 deprecated 标记、semver 约束 + CHANGELOG 记录迁移路径。

### 2.5 复用手段演进：HOC → Render Props → Hooks

| 手段 | 形态 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| HOC | 接收组件返回增强组件 | 早期主流 | props 来源混乱、包装地狱、难以在逻辑层复用 |
| Render Props | 把内部状态透传给 `render`/children 函数渲染 | 数据来源清晰 | 多层嵌套成回调地狱 |
| Hooks / Composable | 把有状态逻辑抽成独立函数 | 逻辑与 UI 彻底解耦、可组合可测试，当代首选 | — |

### 2.6 跨框架与抽象层级

- **跨框架四条路线**：无框架底层 + 各自适配层、Web Components（Custom Elements）、headless 模式、统一运行时。
- **框架无关 vs 框架先行**：单一框架不跨端时优先框架原生组件；"真正能跨端的是业务领域层逻辑而非 UI 层"。
- **复合组件 / 配置化渲染 / headless 库**：Context 共享状态自由排列；schema 描述组件树代价是性能与调试成本；Radix / TanStack 一类行为样式分离。

**组件库边界**：组件库收"通用原子与复合组件"（只依赖设计 token 与自身状态，通过 props 扩展），业务专属组件留业务层——边界是"是否可跨业务复用"；通用层要防业务渗透（不许 import 业务 api），过早抽通用组件会做出"四不像"。**设计系统 = 组件库 + 设计令牌 + 文档 + 规范**，组件库是它的实现载体；设计令牌用 CSS 变量定义色板/间距/圆角，组件全部消费 token 不写死。组件库要控制破坏性变更频率。

## 3. 前端架构与分层

### 3.1 目录结构即架构

- **两种切法**：按类型分横跨多目录、按领域分改动集中，核心差别是**改动半径**。
- **两层结合**：顶层按领域切，领域内部再按类型切，是真实项目的主流形态。
- **前提**：按领域切要求领域之间不互相引用内部文件，否则 features 会变成互相纠缠的大泥球。

### 3.2 依赖方向单向：六层模型

六层单向依赖，上层可依赖下层、反向禁止：

```
views → hooks → store → api → utils → shared
视图    组合逻辑  全局状态 接口契约 纯工具  常量纯函数
```

- **可判定**：层序号让"违规"变成算术——`toLayer > fromLayer` 即反向依赖。
- **视图额外约束**：禁止直连 `utils/http`、`utils/storage` 这类能力层，请求与存储必须走 api。
- **越界的代价**：utils 认识"当前用户"→ 不可复用、不可单测；视图里写 fetch → 契约变更漏改。
- **收益**：分层让"改一处"（接口变了只动 api 层）与"可测"（纯函数不挂组件）成为可能。hooks 与 utils 的区别——hooks 持有响应式状态与生命周期，utils 是纯函数。

**纯函数 + 派生状态**：把逻辑收敛成纯函数、派生结果不落状态（用计算属性/useMemo 实时派生）——可枚举、可单测、可复用、可回归；纯函数只解决"计算"，IO/副作用仍要明确边界（请求放 api 层）。

**职责收敛（编排 + 渲染）**：主组件只管"编排"（拉起数据、串联流程）与"渲染"（展示结果），横切关注点下沉——数据请求归 api/hooks、校验归纯函数、埋点归统一调用；请求散落在组件里 → 接口变更动多个页面且无法单测。收敛是渐进不是推倒重来——边界先行 + 增量迁移 + 灰度验证。

### 3.3 四类可自动检查的违规

| 违规 | 含义 | 后果 |
| ---- | ---- | ---- |
| 反向依赖 | 下层引用上层 | 依赖方向被击穿 |
| 绕过接口层 | 视图里出现接口路径与 fetch 细节 | 契约变更漏改 |
| 跨领域引用 | 伸进别的领域内部文件（应走公共出口 `index.js`） | features 变泥球 |
| 循环依赖 | 初始化顺序不可预测，几乎总是伴随越界 | 项目小时不报错，最危险 |

### 3.4 扇入与影响面

- **传递影响面**：反向可达集（改一个文件会波及其传递可达的所有文件）。实测 `shared/constants.js` 波及 84% 文件、`utils/http.js` 63%、`hooks/useToast.js` 16%。
- **决定测试策略**：扇入高的必须有单测；扇入低的叶子模块可放手重构。
- **架构债判定**：下线判据是"消费方不存在"，不是"看起来没人用"。技术债四种形态——失效业务分支（接口/配置不存在）、失效埋点（面板不再消费）、历史兼容判断（端版本全覆盖）、废弃配置（无读取方）；判定三步：找消费方 → 看端版本/接口是否还在 → 灰度或加兜底后再删。

### 3.5 分层不是越细越好

抽层三个信号：

```
接口被两处调用
逻辑被两个组件需要
工具被三处引用
```

信号没出现就先不分——间接层本身也是成本，修一个 bug 要跳三次文件。

### 3.6 规约落进 CI

- **可用工具**：`no-restricted-imports` / `eslint-plugin-boundaries` / `dependency-cruiser` / 自研扫描器。
- **规则分级**：循环与反向往报错，跨领域警告起步。
- **冻结增量**：baseline 只许降不许升，别一次清光——否则重构会被"顺带清架构"绑架；跨领域引用这类"看起来能跑"的违规要警告起步，**新代码必须严格**，否则存量清理的速度赶不上新增的速度。

治理落地（把规约变 PPT 之外的可检查规则）五步：

1. 静态扫描 import 生成层间依赖矩阵。
2. 计算扇入与传递影响面，把改动风险量化。
3. 定义分层与依赖方向，写进 ESLint 或 `dependency-cruiser`。
4. 用 baseline 冻结存量违规，只允许下降。
5. 补高扇入文件的测试。

说服团队用数字说话——把"改一个需求动几个文件""改这个文件波及多少文件"变成数字，比讲设计原则有效。

## 4. 权限系统设计

### 4.1 模型：只认权限码

- **RBAC**：用户 → 角色 → 权限码（`资源:动作`），前端只判断"有没有这个码"。
- **反例**：`role === 'admin'` 会把「角色 × 操作」变成组合爆炸，第二个角色出现就开始漏；权限码是角色配置的唯一出口，新增角色只改后端配置、前端代码不动。
- **通配两种**：`*`（神模式，慎用）与 `资源:*`；**读动作可用通配，写/删动作逐个列举**。
- **取舍**：具体码的代价是新增动作要同步配（安全默认——实测 `operator` 有 `order:read/write/refund` 但没有 `order:*`，新上线的 `order:bulk` 会被直接拦截）；通配的代价是危险动作自动放行（且让"权限码拼错"这类问题永不暴露，直到新模块上线才一起爆）。

### 4.2 路由级：菜单是过滤的结果

- **单一来源**：路由表自带 `perm`，菜单树由过滤后的路由派生，不维护第二份配置。
- **剪枝两条**：叶子按权限码剪；父节点因"子项全被剪"而**整枝消失**。
- **父节点 perm 语义**：只写"能看这个分组"的码，写高门槛码会出现空分组。
- **实现两个坑**：`addRoute` 后要重新导航（`return { ...to, replace: true }`）；刷新时要有 `routesLoaded` 标记，否则详情页会被踢回首页。
- **动态菜单**：由过滤后的路由表直接派生菜单树，加一条路由即出一个菜单；不要维护两份配置靠人工同步。

### 4.3 按钮级：先看路由可达性

- **实测**：12 个按钮里 7 个是"路由本身就进不去"，大多数按钮走不到权限码判定。
- **与关系**：可达性与权限码缺一个，就会出现"按钮点下去 403"。
- **常量化管理**：权限码写常量不写魔法字符串，否则拼错会静默消失。

### 4.4 数据级：脱敏在下发之前

- **不下发 ≠ 脱敏**：服务端裁剪响应体（抓包也拿不到）≠ 前端打码（只是视觉处理）。
- **分工**：服务端决定下发什么，前端只决定渲染什么。
- **行级与列级**：行级必须服务端注入查询条件；列级可降级为聚合（给不出明细就给汇总）。

### 4.5 契约与边界

- **下发权限码数组**而非角色名；`store.perms` 是单一数据源，菜单/路由/按钮/字段四处派生。
- **前端权限只做体验收敛**，真正的边界是接口鉴权（防君子不防小人）。
- **要有独立 refresh 时机**；403 与 404 语义要定好，别把用户卡在空白页。

权限变更（如退出重登、签到升级）后要有独立刷新权限码的时机，否则 stale 权限会让已渲染的按钮与接口鉴权不一致。

## 5. 请求层与缓存设计

### 5.1 职责边界：该管与不该管

- **该管**：baseURL / 超时 / 公共头、token 注入、拦截器管道、去重、并发上限、缓存、取消与重试能力。
- **不该管**：业务规则（"订单只能查 30 天"）、页面 loading / 空态 / 文案、需要跳路由的逻辑（401 除外）。
- **信号**：拦截器里开始判断 url（`if (url === '/api/order')`），就说明这段逻辑该搬到 api 层。
- **错误分类**：HTTP 码与业务码必须分开——前者进 `catch`、后者进 `then`，混在一起会导致"统一错误提示"覆盖掉业务提示。

通用请求层的整体设计：统一实例 + 拦截器分层（请求侧注入 token/公共参数、响应侧统一解包与错误分流）+ HTTP 码与业务码分类 + 去重 / 并发上限 / 缓存 / 取消四项能力；错误处理要有"全局兜底 + 局部覆盖"两级。

### 5.2 拦截器是洋葱

- **顺序**：请求拦截器**后注册先执行**，响应拦截器**先注册先执行**。
- **实测**：注册 A、B、C → 执行 `C → B → A → 网络 → A → B → C`。
- **与 axios 一致**：`request` 用 `unshift`、`response` 用 `push`，迁移不改变顺序。
- **注册位置**：想包住所有请求的埋点请求侧注册在最后、响应侧注册在最前；想最先解包响应体注册在最前。
- **坑**：注册顺序写反会出现"埋点在鉴权之前跑，未登录也上报一次"，表面看不出。

### 5.3 竞态保护

- **现象**：先发出的慢请求后到达，把后发出的快请求结果**覆盖**掉——实测输入 A（200ms）后改 B（50ms），B 先到写入、A 后到覆盖，屏幕停在 A。
- **两种保护**：

```
自增令牌比对    "我是不是最新"——不是最新则丢弃
AbortController  直接掐断上一条——响应根本不会到达，.then 都不执行，更彻底
```

- **陷阱**：`AbortError` 是主动取消不是错误，混进错误上报会淹没真实错误。

### 5.4 去重与并发上限

- **去重**：in-flight 表复用同一个 Promise，**表要在请求结束后才清**；实测 5 次并发同 key 只发 1 次。
- **局限**：只能防"同时发生"，防不了"前后脚发生"（后者靠缓存或业务节流）。
- **并发上限**：实测 20 个 120ms 请求，串行 2491ms、上限 4 是 694ms，服务端峰值 4。
- **取值**：`4~6` 是安全区间；去重放在并发控制之前；首屏关键请求要能插队。

### 5.5 缓存与失效

- **TTL**：实测命中把 136ms 压到 0.1ms 且不走网络；`force` 参数是"用户点刷新"的出口。
- **SWR**：过期后 1.00ms 交出旧值 + 后台刷新；适合列表详情，**不适合余额、库存**。
- **失效策略**（按可靠度排）：**写操作成功后就地删 key** ＞ 标签失效（一次清一组）＞ 短 TTL 兜底。
- **不该缓存**：会因陈旧导致错误操作的数据（余额、库存、订单状态），以及每次要求强一致的场景。

### 5.6 取消与重试

- **透传 `AbortSignal`**：组件卸载 / 路由切换时取消，避免响应落在已卸载组件上；取消信号要透传给调用方。
- **重试与幂等**属可靠性话题（见网络与协议进阶模块），请求层只提供可配置开关。

## 6. 大文件上传与断点续传

### 6.1 为什么要切片

不切片的四个坑：

```
失败全量重来         一个分片失败，整个文件重传
进度不可信           upload.onprogress 是"已交给系统缓冲区"，不是已落盘
服务端要一次性缓冲    内存被大文件撑爆
无法并发             一条连接串行传完
```

切片解决：一次大请求变 N 次小请求，四个问题一起解决。

### 6.2 协议四端点

| 端点 | 作用 | 要点 |
| ---- | ---- | ---- |
| `init` | 含秒传判定（按指纹查是否已完整存在） | 返回 `uploadId` 与 `received` |
| `part` | 接收分片 | **接收必须幂等**——同 index 重复到达只记一次，这是断点续传的地基 |
| `status` | 查已收与缺失分片 | 返回 `missing` 数组 |
| `complete` | 合并（**校验关不是合并关**） | 缺片返回 400 + `missing` 数组，客户端直接补传 |

### 6.3 串行与并发

- **实测**：5 片 × 120ms，串行 753ms、并发 3 是 319ms；服务端观测并发峰值与客户端一致。
- **并发取值**：`3~4`——同域 HTTP/1.1 只有 6 条连接，超了只会在连接层排队，还挤掉页面自身请求；HTTP/2 下无连接数限制但共用一条 TCP 的带宽，服务端也有承载上限。
- **分片大小**：`1~5MB`——太小（如 64KB）请求数爆炸、协议开销占比高；太大（如 16MB）单片重传代价高。
- **注意**：首屏其他请求的带宽会被抢，重要请求要能插队或走独立通道。

### 6.4 断点续传

- **靠 `init` 返回的 `received`**：客户端不需要记住传到哪，换设备换网络都能续。
- **`uploadId` 按文件指纹复用**：否则每次新建会话、`received` 恒为空，功能直接失效。
- **`chunkSize` 不许改**：一旦确定，改了 index 与偏移量就错乱。
- **会话要过期清理**：否则废弃分片会占满磁盘。

判据复盘：断点续传靠「服务端返回已收分片列表」——`init` 返回 `received`，客户端推出 `missing` 补传；实测掉线时已传 [0,1,2]，重连后只发 2 片（167ms），从头重传要发 5 片。

### 6.5 秒传与文件指纹

- **判据是内容指纹（sha256）**：改一个字节就变，所以不会误合并；同一文件第二次 `init` 返回 `exists: true`，实际传输 0 B（实测）。
- **指纹有成本**：实测同步算 5MB 14ms、50MB 132ms，必须放 Web Worker / `crypto.subtle`——否则主线程完全不能交互。
- **大文件流式 update**：不要整份读进内存。
- **两个风险**：指纹可用于探测"某文件是否已上传"；服务端在 `complete` 阶段仍要校验，不能只信客户端声明的 `fileHash`。

### 6.6 完整性校验与进度

- **合并后必须重算哈希**：截断、代理改写、index 算错都会让文件坏掉，而损坏往往几个月后才发现。
- **进度按已确认分片数**聚合，不按已发出字节数（`upload.onprogress` 给的是缓冲字节数，会先冲到 100% 再卡住）。
- **两层进度**：已发出（快）+ 已落盘（准），网盘的常见做法；服务端确认分片后返回 `received` 数量或 `missing` 数组，客户端可直接据此补传。

## 7. 虚拟滚动与大数据渲染

### 7.1 虚拟滚动是一道算术题

- **三要素**：内容容器高度 `total × rowH` 撑起滚动条、渲染区间 `[start, end)`、`translateY(start × rowH)` 平移。
- **公式**：

```
start = floor(scrollTop / rowH)
end   = start + ceil(viewportH / rowH)
```

- **边界**：`Math.min(total, ...)` 不能漏，否则会渲染出不存在的行或算出越界 offset。
- **性质**：渲染量与数据量无关——十万条与一百万条渲染的都是视口/行高决定的十几条（可视区 + 缓冲区）。
- **key 用业务主键**：用下标当 key 会让输入框内容串行到别的行。

### 7.2 与分页、懒加载的区别

| 方案 | 交互 | 首屏成本 | 内存 |
| ---- | ---- | ---- | ---- |
| 分页 | 需点击、无法连续滚动、只加载当前页 | — | — |
| 懒加载（无限滚动） | 连续 | 随已加载量增长 | 持续增长 |
| 虚拟滚动 | 连续 | 恒定 | 恒定额外开销 |

**省什么不省什么**：省 DOM 与渲染，**不省内存**；百万级要配合数据分片或游标分页。该不该上虚拟滚动——数据量不大（几百条以内）、行高极其不定又无法估算、或需要"整表导出/打印/查找"时，复杂度不划算；还要防"过度虚拟化"——几百条硬改虚拟列表，收益是几十毫秒，代价是 `Ctrl+F` 找不到屏外内容、测试也变难。

### 7.3 缓冲区

- **`overscan`**：多渲染 `overscan × 2` 条（线性代价），收益递减，取值 `5~10`。
- **更快滚动**：靠空位骨架（先占位后替换），不是加大缓冲。
- **滚动节流**：`scroll` 处理放 `requestAnimationFrame`，每帧只算一次。

### 7.4 不定高：前缀和 + 二分

- **`offsets[i]`** = 前 i 条总高；"第 i 条起始于哪"变成数组读取，"某偏移量落在第几条"变成一次二分。
- **定位起点用二分**：实测 16 步 vs 线性 50001 步，单次耗时 0.070µs vs 55.53µs（约 800 倍）。
- **前缀和成本**：重建十万条实测 736µs，只在行高集合变化时重建、滚动期间只读；否则每帧多花 0.7ms 加十万次分配，GC 压力直接体现为掉帧。
- **变化处理**：单行高度变化用增量更新；未测量行先估算再回填。
- **结论**：能定高就别做不定高，两者工程量差一个数量级。

### 7.5 滚动锚定

- **现象**：顶部插入 20 条不补偿 `scrollTop`，内容跳 880px。
- **补偿**：`scrollTop += 插入总高`（不定高就是插入行的实际高度和）。
- **隐蔽触发源**：图片加载完成把上方内容撑高（发生在滚动停止之后）。
- **`overflow-anchor` 对虚拟列表无效**：DOM 在不停替换，浏览器找不到稳定锚点。

### 7.6 剩下的细节

- **key 用业务主键**：用下标当 key 会让输入框内容串行到别的行。
- **行内事件用事件委托**：监听器挂容器，`event.target.closest()` 定位具体行。
- **搜索在数据层做**：过滤是纯计算、不碰 DOM、可单测；不要"渲染全部再 CSS 隐藏"（DOM 数量退回全量，虚拟滚动收益全部交出）；输入防抖 200~300ms。
- **与性能模块的分工**：虚拟滚动省下的首屏时间与内存、长列表其它手段（`content-visibility`、`contain`）见性能优化模块，本篇只讲实现。
