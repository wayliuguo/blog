# 权限系统设计

## 一、模型：前端只认权限码，不认角色名

权限系统的第一道设计决策不是「怎么拦住页面」，而是**前端依据什么做判断**。

最省事的写法是让前端认识角色名：`if (user.role === 'admin') showButton()`。这个写法在第二个角色出现时就开始崩——运营要能退款但不能删单，财务要能导出但不能改，于是判断语句变成：

> 示意片段（无配套脚本）

```js
if (user.role === 'admin' || user.role === 'finance' || (user.role === 'operator' && route !== 'refund')) { ... }
```

角色 × 操作的组合是指数增长的，用 `if` 枚举必然漏。正确的模型是 **RBAC**：用户挂角色，角色挂权限，前端只判断「这个用户有没有某个权限码」。

权限码用 `资源:动作` 两段式命名，例如 `order:read`、`order:refund`、`report:cost`。判断时前端完全不认识角色名：

> 摘自 `./code/eng-lab/scenarios/auth.mjs`（运行：`npm run auth`）

```js
// 权限码 = 资源:动作。后端在登录后下发"这个用户拥有哪些码"，前端不认识角色名
const GRANTS = {
    admin: ['*'],
    operator: ['order:read', 'order:write', 'order:refund', 'coupon:read', 'coupon:write', 'report:read'],
    viewer: ['order:read', 'report:read']
}
```

这里的 `GRANTS` 只是实验台的输入数据——**真实项目里这三个角色不存在于前端代码**，它们在后端，前端拿到的只是一串权限码。

判定函数要支持 `*` 和 `资源:*` 两种通配：

> 摘自 `./code/eng-lab/scenarios/auth.mjs`（运行：`npm run auth`）

```js
/** 单个权限码是否被授予集合覆盖：支持 * 与 resource:* 两种通配 */
export function can(granted, needed) {
    if (!needed) return true
    return granted.some(g => {
        if (g === '*') return true
        if (g.endsWith(':*')) return needed.startsWith(g.slice(0, -1))
        return g === needed
    })
}
```

通配符看起来只是少写几个字符串，但它决定了一个容易踩的坑。实测几组判定：

```
--- 通配符匹配的边界（实测 can() 的判定结果） ---
| 角色     | 校验的权限码  | 判定 |
|----------|---------------|------|
| admin    | order:read    | 通过 |
| admin    | system:manage | 通过 |
| operator | order:write   | 通过 |
| operator | order:bulk    | 拦截 |
| operator | report:cost   | 拦截 |
| viewer   | order:write   | 拦截 |
| viewer   | order:read    | 通过 |
```

- `operator` 持有 `order:read / write / refund` 三个**具体码**，但没有 `order:*`。新上线一个「批量操作」按钮（`order:bulk`）时，运营会直接看不到它——这是**安全的默认**（新能力默认关闭），代价是每次加动作都要同步改后端的角色配置；
- 反过来，如果给运营配 `order:*`，新增动作会自动放行，方便但危险；
- `admin` 的 `*` 能过任何校验，所以这类账号必须有更严的审计，因为它连"忘记配权限码"这种兜底都没有。

选择哪一侧，取决于这个动作的危险程度。**读动作可以给通配，写/删动作一定逐个列举**。

## 二、路由级：菜单树是过滤的结果，不是一份单独维护的配置

菜单与路由是同一份数据的两个视图。常见的坏做法是维护一棵菜单树 + 一份路由表，然后靠人工保持同步——必然对不上。

正确的做法：**路由表自带权限标记，菜单树由过滤后的路由派生**。路由定义里带上 `perm`：

> 摘自 `./code/eng-lab/scenarios/auth.mjs`（运行：`npm run auth`）

```js
    {
        title: '数据',
        path: '/data',
        perm: 'report:read',
        children: [
            { title: '经营报表', path: '/reports', perm: 'report:read' },
            { title: '成本分析', path: '/reports/cost', perm: 'report:cost' }
        ]
    },
```

过滤逻辑有两个容易写漏的细节：**叶子先剪，父节点因为"子项全被剪"而整枝消失**：

> 摘自 `./code/eng-lab/scenarios/auth.mjs`（运行：`npm run auth`）

```js
/** 菜单过滤：叶子先过滤，父节点因"子项全被剪"而一起消失 */
function filterMenu(nodes, granted) {
    const out = []
    for (const node of nodes) {
        if (!can(granted, node.perm)) continue
        if (!node.children) {
            out.push({ ...node })
            continue
        }
        const kids = filterMenu(node.children, granted)
        if (kids.length === 0) continue // 父节点有权限、但没有任何可见子项 → 整枝剪掉
        out.push({ ...node, children: kids })
    }
    return out
}
```

第二种情况（父节点有权、子项全没权）如果漏了，菜单里会出现一个点进去空白的「营销」分组。三个角色跑一遍：

```
[admin] 可见叶子 10 / 10
概览  /dashboard
交易  /trade
  └─ 订单列表  /orders
  └─ 订单详情  /orders/:id
  └─ 退款审批  /orders/refund
营销  /marketing
  └─ 优惠券  /coupons
  └─ 券模板  /coupons/edit
数据  /data
  └─ 经营报表  /reports
  └─ 成本分析  /reports/cost
系统  /system
  └─ 用户管理  /users
  └─ 系统设置  /settings

[operator] 可见叶子 7 / 10
概览  /dashboard
交易  /trade
  └─ 订单列表  /orders
  └─ 订单详情  /orders/:id
  └─ 退款审批  /orders/refund
营销  /marketing
  └─ 优惠券  /coupons
  └─ 券模板  /coupons/edit
数据  /data
  └─ 经营报表  /reports

[viewer] 可见叶子 4 / 10
概览  /dashboard
交易  /trade
  └─ 订单列表  /orders
  └─ 订单详情  /orders/:id
数据  /data
  └─ 经营报表  /reports
```

实测出的三点值得展开：

- `operator` 的「数据」组从 2 个子项掉到 1 个：有 `report:read` 的「经营报表」留下，需要 `report:cost` 的「成本分析」被剪掉，父节点因为还有可见子项而保留。**这是最常见的形态**——分组本身不必须有权限，它只是容器；
- `viewer` 的「系统」「营销」两组**整枝消失**：父节点权限不足时直接剪掉，不在子项上再逐个判断。这一条要注意语义：如果分组权限写成 `user:manage`，那么有 `user:manage` 却没有子项权限的人，会看到一个空分组——所以父节点的 `perm` 只该写"看一眼分组"所需的码，不该写高门槛的码；
- 最终菜单是**张量的形状**：同一份路由表 × 不同的权限集合 = 不同菜单。参数是权限集合，输出才是菜单。

路由层的实现要点：

```
router.beforeEach(async (to) => {
    if (!store.token) return '/login'
    if (!store.routesLoaded) {
        const allowed = filterRoutes(ALL_ROUTES, store.perms)   // 与菜单同一份过滤
        allowed.forEach(r => router.addRoute(r))                // 动态注册
        store.menu = buildMenu(allowed)                         // 菜单同源
        return { ...to, replace: true }                         // 重进一次以命中新路由
    }
})
```

两个坑：**动态路由注册后要重新导航一次**（`return { ...to, replace: true }`），否则本次匹配的还是旧路由表，会落到 404；**刷新页面时权限还没拉到**，所以判断里必须有 `routesLoaded` 标记，否则用户刷新详情页会被踢回首页。

## 三、按钮级：只看权限码是不够的

按钮级权限通常用自定义指令实现（`v-permission="'order:write'"`），它的问题是**孤立地看权限码**。实测一份 12 个按钮的清单：

```
--- 按钮级判定：路由不可见时按钮必须一并不可见 ---
| 所在路由       | 按钮     | 权限码         | admin | operator   | viewer     |
|----------------|----------|----------------|-------|------------|------------|
| /orders        | 新建订单 | order:write    | 显示  | 显示       | 隐藏       |
| /orders        | 导出     | order:export   | 显示  | 隐藏       | 隐藏       |
| /orders        | 批量操作 | order:bulk     | 显示  | 隐藏       | 隐藏       |
| /orders/:id    | 取消订单 | order:cancel   | 显示  | 隐藏       | 隐藏       |
| /orders/refund | 审批通过 | order:refund   | 显示  | 显示       | 路由不可见 |
| /coupons       | 新建券   | coupon:write   | 显示  | 显示       | 路由不可见 |
| /coupons       | 停用券   | coupon:disable | 显示  | 隐藏       | 路由不可见 |
| /reports       | 导出报表 | report:export  | 显示  | 隐藏       | 隐藏       |
| /reports/cost  | 查看成本 | report:cost    | 显示  | 路由不可见 | 路由不可见 |
| /users         | 编辑用户 | user:manage    | 显示  | 路由不可见 | 路由不可见 |
| /users         | 重置密码 | user:resetPwd  | 显示  | 路由不可见 | 路由不可见 |
| /settings      | 保存设置 | system:manage  | 显示  | 路由不可见 | 路由不可见 |

共 12 个按钮，其中 7 个会因为"所在路由本身就进不去"而被前置拦住，
这就是为什么按钮级权限不能只看权限码：路由层才是第一道闸。
```

注意 `operator` 那一列的 `order:refund`：它**通过了权限码校验，却也可能因为路由不可见而显示不出来**。12 个按钮里有 7 个属于这种情况，说明大多数按钮根本走不到权限码判定——路由层已经把它们挡在外面了。

实务上的推论：

- 按钮级判定要**先看路由可达性，再看权限码**。二者与关系，缺一个就会出现「按钮点下去 403」；
- 前端显示的按钮只是体验，**真正决定能不能执行的是后端接口**。所以前端隐藏按钮的收益是"减少误操作与困惑"，不是"安全"；
- 权限码不要散落在模板里的魔法字符串。集中定义并生成常量（`PERM.ORDER_WRITE`），否则拼错一个字符，按钮会静默消失而没有任何报错。

## 四、数据级：脱敏必须在下发之前

同一份数据，不同角色应该看到不同形态。这层最容易被误解为"前端做"，实测一下三种角色的字段视图：

> 摘自 `./code/eng-lab/scenarios/auth.mjs`（运行：`npm run auth`）

```js
// 字段级：public 之外都要求权限码；mask 表示"有权限也脱敏"
const FIELDS = [
    { key: 'id', label: '订单号', perm: null },
    { key: 'amount', label: '金额', perm: null },
    { key: 'phone', label: '手机号', perm: null, mask: 'phone' },
    { key: 'cost', label: '成本', perm: 'report:cost' },
    { key: 'storeNo', label: '门店', perm: 'store:all' }
]
```

跑出来：

```
--- 字段级：同一份数据，三种角色看到的形态 ---
| 字段   | 要求权限    | admin       | operator    | viewer      |
|--------|-------------|-------------|-------------|-------------|
| 订单号 | —           | A20260919   | A20260919   | A20260919   |
| 金额   | —           | 12800       | 12800       | 12800       |
| 手机号 | —           | 138****5678 | 138****5678 | 138****5678 |
| 成本   | report:cost | 8600        | 不下发      | 不下发      |
| 门店   | store:all   | S-021       | 不下发      | 不下发      |
```

关键区别在「不下发」与「脱敏」这两个动作发生在哪一侧：

- **「不下发」**：服务端按权限裁剪响应体。抓包拿不到，前端拿到的就是全部真相；
- **「脱敏」**：手机号打码。如果服务端下发 `13812345678` 再让前端遮成 `138****5678`，那前端代码与网络面板里都是明文——这只是视觉处理，不是权限。

所以字段级权限的正确分工是：**服务端决定下发什么，前端只决定渲染什么**。前端的字段判定（`if (can('report:cost')) 显示成本列`）作用只有一个：避免渲染一列永远是空的值。

数据级还有更细的两层，前端能做的不多但要知道：

- **行级**：只看自己门店 / 自己名下 / 下级部门的。这必须由服务端在查询条件里注入，前端伪造参数毫无意义；
- **列级 + 聚合**：明细不能看但可以看汇总（例如只能看到门店平均毛利，看不到单笔成本）。这类"给不出明细就给聚合"的降级形态，是数据权限里最实用的设计。

## 五、前后端契约与落地顺序

**契约**：登录/刷新用户信息时，接口一次性下发「权限码数组」，而不是角色名。前端 `store.perms` 变化后，菜单、路由、按钮、字段四处都从它派生——**单一数据源**带来一个很实际的收益：权限变更后只要重新拉一次 `perms` 并重新派生，四处自动同步，不用各改一遍。

**落地顺序**：

| 顺序 | 做什么 | 为什么排这里 |
| ---- | ---- | ---- |
| 1 | 后端定义权限码清单与角色映射 | 前端所有判断都依赖它，先定契约 |
| 2 | 前端集中定义权限码常量 | 避免魔法字符串散落 |
| 3 | 路由级（动态路由 + 守卫）+ 菜单派生 | 拦住入口，覆盖面最大 |
| 4 | 按钮级指令 | 在可达路由上做二次收敛 |
| 5 | 服务端字段/行级裁剪 | 真正的安全边界，与前端无关但必须同步上线 |

**几条容易被追问的边界**：

- **前端权限不是安全边界**。有经验的人可以用 DevTools 改 `store.perms`、直接构造请求。前端拦住的是菜单，不是数据——**真正的边界永远在接口鉴权**；
- **权限码要能刷新**。超管给某人加了一个权限，对方不该等到重新登录。让 `perms` 有独立的 refresh 时机（路由切换、窗口 focus、或后端通过推送通知）；
- **超级管理员不要用 `*`** 走"神模式"绕过所有判断。`*` 让"某个权限码拼错了"这种问题永远不会暴露，等到上线一个新模块才一起爆。更稳的做法是给超管也配具体码，只在极少数兜底处使用通配；
- **403 与 404 的语义**。无权限的路由，有些团队返回 404（不暴露资源存在），有些返回 403（明确告知）。前者信息泄露更少，后者排查更方便——但无论哪种，都别把用户卡在一个空白页上。
