# 前端架构与分层

## 一、目录结构是架构的第一份文档

一个项目的架构不写在文档里，写在目录里。新人接手时第一眼看的是目录树，它直接回答了「这个需求该改哪几个文件」。

最常见的两种切法：

```
按类型分（按技术角色）              按领域分（按业务能力）
src/                              src/
  components/  ← 所有组件            features/
  hooks/       ← 所有 hook             order/
  api/         ← 所有接口                components/
  utils/       ← 所有工具                hooks/
  views/       ← 所有页面                api.js
  store/       ← 所有状态                index.js
                                     user/
                                       components/
                                       hooks/
                                       api.js
```

两者的差别在**改动半径**：改「订单」这个需求，按类型分要横跨 5 个目录、按领域分只动 `features/order/` 一个目录。

但按领域分有个前提——领域之间不能互相引用内部文件，否则一个 features 目录会变成 5 个互相纠缠的大泥球。所以真实项目往往是**两层结合**：顶层按领域切，领域内部再按类型（组件/hooks/api）切。

本模块的示例目录 `code/eng-lab/fixtures/shop` 就是这么切的，它同时也是后面所有实测的样本：

```
fixtures/shop/
  views/        视图层：order/ user/ dashboard/ 三个领域
  hooks/        组合逻辑：useOrderList / useUser / useToast
  store/        全局状态：session / cart
  api/          接口层：order / user / coupon
  utils/        纯工具：http / date / storage / validate
  shared/       最底层：constants / format
```

19 个文件、33 条内部 import。这份目录是**故意写坏的**——它看起来很正常，但违反了四条分层规约，后面会用脚本把它们一条条揪出来。

## 二、依赖方向：谁可以引用谁

分层的全部内容就是一句话：**依赖只能单向流动**。

```
       views        ← 页面与视图：只消费 hooks / api / store 暴露的能力
         │
       hooks        ← 组合逻辑：把取数、分页、权限打包成视图能直接用的形状
         │
       store        ← 全局状态：跨组件共享的可变状态
         │
        api         ← 接口层：把后端契约翻译成业务函数
         │
       utils        ← 纯工具：不碰业务语义的通用能力
         │
      shared        ← 叶子：常量与纯函数，不 import 项目内任何文件
```

箭头方向即依赖方向：上层可以 import 下层，下层**不能**回头 import 上层。每一条倒过来的箭头都是一个具体的成本——

- `utils` 认识「当前登录用户」，它就再也不能被别的项目复用，也无法脱离 store 单测；
- `views` 直接写 fetch，后端契约一改，要改的不是一处 api 而是一堆视图；
- `store` 依赖 `hooks`，状态层的初始化顺序就被视图层绑架了。

规约要用代码表达，而不是靠口头约定。示例实验台里它就是两个常量：

> 摘自 `./code/eng-lab/scenarios/layers.mjs`（运行：`npm run layers`）

```js
// 层级：数字越小越底层。规约是"上层可以依赖下层，下层不能回头依赖上层"
const LAYERS = ['shared', 'utils', 'api', 'store', 'hooks', 'views']

// 视图层不允许直连的能力层：发请求、写存储都要走 api，视图只认业务函数
const VIEW_FORBIDDEN = ['utils/http.js', 'utils/storage.js']
```

有了层序号，"违规"就变成一个可判定的算术问题：`toLayer` 的序号大于 `fromLayer` 的序号，就是反向依赖。

扫描器不依赖任何构建工具，只用正则把源码里的 import 抠出来，再把相对路径解析成项目内路径：

> 摘自 `./code/eng-lab/scenarios/layers.mjs`（运行：`npm run layers`）

```js
/** 从源码里抠出所有 import 的目标，把相对路径解析成相对 shop 的路径 */
function importsOf(file) {
    const src = fs.readFileSync(path.join(SHOP, file), 'utf8')
    const re = /import\s+(?:[\s\S]*?)\s*from\s*['"]([^'"]+)['"]|import\s*['"]([^'"]+)['"]/g
    const out = []
    let m
    while ((m = re.exec(src))) {
        const spec = m[1] || m[2]
        if (!spec || !spec.startsWith('.')) continue // 只分析项目内部依赖
        out.push(path.posix.normalize(path.posix.join(path.posix.dirname(file), spec)))
    }
    return out
}
```

跑一遍，得到的是完整的层间依赖矩阵：

```
=== 扫描范围 ===
示例目录：fixtures/shop（19 个文件、33 条内部 import）
规约：上层可依赖下层，下层不得回头依赖上层；视图只通过 api 拿数据；
      领域之间不互相引用内部文件；文件之间不允许成环。

--- 层间依赖矩阵（行 = 引用方，列 = 被引用方，数字 = import 条数） ---
| from \ to | shared | utils | api | store | hooks | views | 出度 |
|-----------|--------|-------|-----|-------|-------|-------|------|
| shared    | 1      |       |     |       |       |       | 1    |
| utils     | 2      |       |     | 1     |       |       | 3    |
| api       | 1      | 4     |     |       |       |       | 5    |
| store     |        | 3     | 2   |       | 1     |       | 6    |
| hooks     | 1      | 3     | 2   |       |       |       | 6    |
| views     | 3      | 1     | 3   | 1     | 3     | 1     | 12   |

右上角应当全空——那里是"下层引用上层"。实际非空的位置：utils→store(1)、store→hooks(1)
```

矩阵比规则更好读的地方在于：**合规的部分有形状**。`views` 行填满左侧五列、`shared` 行只有一个同层引用——这就是一张健康的依赖图长什么样。右上角那两个非零格，就是下一条要处理的问题。

## 三、四条能自动查出来的违规

分层的收益必须能落到"可检查"上，否则它会退化成新人培训 PPT 里的一张图。实践中值得自动化的违规只有四类，因为它们都能从 import 图里算出来：

> 摘自 `./code/eng-lab/scenarios/layers.mjs`（运行：`npm run layers`）

```js
    const violations = []
    for (const [f, t] of edges) {
        const fromLayer = layerOf(f)
        const toLayer = layerOf(t)
        if (LAYERS.indexOf(toLayer) > LAYERS.indexOf(fromLayer)) {
            violations.push(['反向依赖', f, t, `${toLayer} 是下层，不该被 ${fromLayer} 引用`])
        }
        if (fromLayer === 'views' && VIEW_FORBIDDEN.includes(t)) {
            violations.push(['绕过接口层', f, t, '视图直接发请求/写存储，契约变更会漏改'])
        }
        const fa = domainOf(f)
        const fb = domainOf(t)
        if (fa && fb && fa !== fb) {
            violations.push(['跨领域引用', f, t, `${fa} 直接引用了 ${fb} 的内部文件`])
        }
    }
```

第四类「循环依赖」不在这个循环里，它是图算法：用三色标记 DFS 找环，把同一条环上的文件串起来。

四条规则各自的现实形态，在示例目录里都有一份真身：

**反向依赖**——工具层里出现了「当前用户」：

> 摘自 `./code/eng-lab/fixtures/shop/utils/validate.js`

```js
// 校验规则。注意这里 import 了 store/session —— 一个纯工具不该知道"当前登录用户"，
// 这条边就是架构检查里要报的「反向依赖」
import { currentUser } from '../store/session.js'

export function canEdit(order) {
    return currentUser().role !== 'viewer' && order.status !== 'closed'
}
```

**绕过接口层**——视图里出现了接口路径：

> 摘自 `./code/eng-lab/fixtures/shop/views/order/OrderList.js`

```js
import { useOrderList } from '../../hooks/useOrderList.js'
import { money } from '../../shared/format.js'
import { request } from '../../utils/http.js'

export async function OrderList() {
    const { load, rowActions } = useOrderList()
    const rows = await load()
    // 这条 request 绕过了 api 层，前后端契约一变就得回来改视图
    const stat = await request('/api/orders/stat')
    return { rows, stat, text: money(rows.length * 100) }
}
```

**跨领域引用**——订单领域伸手去拿用户领域的内部文件：

> 摘自 `./code/eng-lab/fixtures/shop/views/order/OrderDetail.js`

```js
import { fetchOrders } from '../../api/order.js'
import { useToast } from '../../hooks/useToast.js'
import { UserCard } from '../user/UserCard.js'
```

正确的做法是让 `UserCard` 从 `views/user/index.js` 这类**公共出口**导出，而不是让外面的模块知道它藏在哪个文件里。领域内部的文件结构应当可以随便重构，只要出入口不变。

四类违规一次扫出来：

```
--- 违规清单（共 5 条，按规则分类） ---
| 规则       | 位置                       | 指向                   | 判定                                                                   |
|------------|----------------------------|------------------------|------------------------------------------------------------------------|
| 反向依赖   | store/cart.js              | hooks/useToast.js      | hooks 是下层，不该被 store 引用                                        |
| 反向依赖   | utils/validate.js          | store/session.js       | store 是下层，不该被 utils 引用                                        |
| 跨领域引用 | views/order/OrderDetail.js | views/user/UserCard.js | order 直接引用了 user 的内部文件                                       |
| 绕过接口层 | views/order/OrderList.js   | utils/http.js          | 视图直接发请求/写存储，契约变更会漏改                                  |
| 循环依赖   | utils/validate.js          | store/session.js       | 2 个文件成环：utils/validate.js → store/session.js → utils/validate.js |
```

注意 `utils/validate.js → store/session.js` 这一对同时命中两条规则：它是反向依赖，两文件之间还成了环。这很典型——**循环依赖几乎总是伴随着某一层的越界**，因为只有在某一层抄了近路，两个不相干的模块才会互相认识。

这里有一个值得单独说的坑：项目规模小时，循环依赖「跑得起来」。ESM 与 CJS 都能容忍它，只是模块初始化的顺序变得不可预测，被环包住的模块也无法单独测试。所以它不会以报错的形式暴露，只会在某次重构后表现为「某个变量是 undefined」。

## 四、改动的影响面：扇入决定测试策略

分层图还有第二个用途：算影响面。某个文件被多少文件（直接或间接）依赖，决定了改它需要多大的心理准备。

> 摘自 `./code/eng-lab/scenarios/layers.mjs`（运行：`npm run layers`）

```js
    /** 传递闭包：改了这个文件，哪些文件会受影响 */
    function affected(target) {
        const reverse = {}
        for (const [f, t] of edges) (reverse[t] = reverse[t] || []).push(f)
        const seen = new Set()
        const queue = [target]
        while (queue.length) {
            const cur = queue.shift()
            for (const up of reverse[cur] || []) {
                if (seen.has(up)) continue
                seen.add(up)
                queue.push(up)
            }
        }
        return [...seen].sort()
    }
```

拿几个典型文件跑一遍：

```
--- 影响面：改动一个文件会波及多少文件 ---
| 改动的文件          | 直接引用 | 传递波及 | 占全量 |
|---------------------|----------|----------|--------|
| shared/constants.js | 5        | 16       | 84%    |
| shared/format.js    | 3        | 4        | 21%    |
| utils/http.js       | 4        | 12       | 63%    |
| hooks/useToast.js   | 3        | 3        | 16%    |

改动 shared/format.js 波及的 4 个文件：
  views/dashboard/Overview.js
  views/order/OrderDetail.js
  views/order/OrderList.js
  views/user/UserCard.js
```

这组数字直接翻译成工程决策：

- `shared/constants.js` 波及 84% 的文件，改它等于改整个项目——**这类文件必须有测试**，而且新增字段只能加不能改语义；
- `utils/http.js` 波及 63%，接口层的请求配置改动要连同 API 契约一起评审；
- `hooks/useToast.js` 只波及 3 个文件、自身又不依赖任何项目内文件——这类「叶子模块」才是能放手重构、甚至换实现的。

所以「哪些文件必须有单测」不该拍脑袋，看扇入就够了：扇入高的写测试，扇入低的靠集成测试兜。

## 五、分层不是越细越好

上面这套东西有一个反噬面：**层分得越细，跨层需要绕的路就越长**。

一个只有三个页面的后台，按 `views/hooks/api/utils` 分四层，写一个「获取用户信息」要走 `view → hook → api → utils/http` 四跳，任何一次改动都要动四个文件。这时候正确的做法是**先不分**：`views/User.js` 里直接 `fetch`，等项目长到需要复用的时候再抽。抽出接口层的时机不是"项目启动时"，而是"第二处要发同样的请求时"。

判断要不要分层的三个信号：

1. **同一个接口被两处以上调用** → 抽 `api` 层，否则请求细节会复制两份；
2. **同一段状态逻辑被两个组件需要** → 抽 `hooks`；
3. **某个工具函数被三个以上模块引用**（三次法则） → 抽 `utils`。

反过来，如果这三件事都还没发生，分层带来的只是间接层。**间接层本身也是成本**——它让你在修一个 bug 时要跳三次文件。

## 六、把规约变成 CI 卡口

扫描器可以自己写（本例 100 行不到），但项目里更常见的做法是直接用现成工具：

- **ESLint 的 `no-restricted-imports`**：按路径前缀配置禁配关系，零额外依赖，适合只禁少数几条线；
- **`eslint-plugin-boundaries`**：按目录定义元素类型，声明「谁可以依赖谁」，报错信息直接指出违规的层；
- **`dependency-cruiser`**：把依赖图输出成 SVG，规则可以写成 `.dependency-cruiser.js`，适合需要可视化给团队看场景；
- **自研脚本**：像本例这样，逻辑完全可控，能顺手算出扇入与影响面，跑在 CI 的 lint 阶段。

规则本身也要分等级，不能一律报错：

| 规则 | 建议等级 | 理由 |
| ---- | ---- | ---- |
| 循环依赖 | 报错 | 初始化顺序不可预测，且几乎总是越界的征兆 |
| 反向依赖 | 报错 | 直接破坏可测试性与可复用性 |
| 绕过接口层 | 报错 | 契约散落是后期维护成本最高的形态 |
| 跨领域引用 | 警告起步，新代码报错 | 存量可能很多，先冻结增量 |

最后一条经验：**存量违规要冻结增量，而不是一次清光**。用 `--baseline` 把当前违规数记下来，CI 只允许这个数字下降不允许上升，重构才不会被"顺带清架构"绑架。
