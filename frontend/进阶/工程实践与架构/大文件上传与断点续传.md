# 大文件上传与断点续传

## 一、为什么要切片

一个 2GB 的文件直接 `POST` 上去，会同时踩四个坑：

1. **失败就得重来**。传到 99% 断网，一切归零——而大文件恰恰最容易在长连接上被网络波动打断；
2. **没有可信的进度**。`XMLHttpRequest.upload.onprogress` 给的是「已交给操作系统缓冲区的字节数」，不是「服务端已落盘的字节数」。网卡缓冲时进度会先冲到 100% 再卡住；
3. **服务端要一次性缓冲整个请求体**，内存压力大，且很多网关对请求体大小有硬限制；
4. **无法并发**，一个 TCP 连接的吞吐被 RTT 和窗口大小卡死。

切片把「一次大请求」变成「N 次小请求」，四个问题一起解决：单片失败只重传这一片、进度按已确认分片聚合、服务端流式落盘、多片可以并发。

切片本身只是一行 `subarray`：

> 摘自 `./code/eng-lab/scenarios/upload.mjs`（运行：`npm run upload`）

```js
    const parts = []
    for (let offset = 0; offset < file.length; offset += CHUNK_SIZE) {
        parts.push(file.subarray(offset, offset + CHUNK_SIZE))
    }
```

真正的工作量在协议设计和幂等保证上。

## 二、上传协议：四个端点

一个够用且能支持断点与秒传的协议只需要四个端点：

```
POST /upload/init      { size, chunkSize, fileHash }  → { exists, uploadId, received[] }
POST /upload/part      ?uploadId=&index=  body=分片字节 → { ok, index, received }
GET  /upload/status    ?uploadId=                      → { received[], missing[] }
POST /upload/complete  ?uploadId=                      → { ok, bytes, sha256 }
```

设计要点有三个：

**`init` 同时承担秒传判定**。服务端按文件指纹查一下这个文件是不是已经完整存在，存在就直接返回 `exists: true`，客户端一个字节都不用传：

> 摘自 `./code/eng-lab/scenarios/upload.mjs`（运行：`npm run upload`）

```js
            const known = byHash.get(body.fileHash)
            if (known && jobs.get(known).parts.size === Math.ceil(body.size / body.chunkSize)) {
                return json(res, { exists: true, uploadId: known, received: [...jobs.get(known).parts.keys()] })
            }
```

**分片接收必须幂等**。同一个 `index` 重复到达（网络超时后客户端重传、并发重试）只能记一次：

> 摘自 `./code/eng-lab/scenarios/upload.mjs`（运行：`npm run upload`）

```js
        if (url.pathname === '/api/upload/part') {
            const job = jobs.get(url.searchParams.get('uploadId'))
            const index = Number(url.searchParams.get('index'))
            const buf = await readBody(req)
            stats.active++
            stats.peak = Math.max(stats.peak, stats.active)
            await sleep(PART_LATENCY) // 模拟落盘/转存耗时，让并发在这里体现出来
            if (!job.parts.has(index)) {
                job.parts.set(index, buf)
                stats.parts++
                stats.bytes += buf.length
            }
            stats.active--
            return json(res, { ok: true, index, received: job.parts.size })
        }
```

这条幂等是断点续传的地基：**「客户端不确定服务端收没收到」是常态**，所以协议必须允许无条件重发。如果分片处理不幂等，重复分片会被追加进去，合并后的文件就坏了。

**`complete` 必须是校验关，不能是合并关**。缺片就拒绝，别让服务端产出一个坏文件：

> 摘自 `./code/eng-lab/scenarios/upload.mjs`（运行：`npm run upload`）

```js
            const missing = Array.from({ length: total }, (_, i) => i).filter(i => !job.parts.has(i))
            if (missing.length) return json(res, { ok: false, missing }, 400)
            const hash = crypto.createHash('sha256')
            let size = 0
            for (let i = 0; i < total; i++) {
                hash.update(job.parts.get(i))
                size += job.parts.get(i).length
            }
            stats.merges++
            return json(res, { ok: true, bytes: size, sha256: hash.digest('hex') })
```

`missing` 数组要返回给客户端——它比 400 状态码有用得多，客户端拿到之后可以直接补传这几个 index，不需要再来一轮 `status`。

## 三、串行还是并发

切片之后立刻产生一个问题：一次发几片。实验台里给每个分片加了 120ms 的服务端耗时，把差异放大：

```
=== 实验设置 ===
文件 5.00 MB，切片 1.00 MB → 5 片，每片服务端耗时约 120 ms
文件指纹 sha256=5e7d7dc8135f13c8…

--- 一、串行与并发的对照 ---
| 上传方式     | 客户端耗时 | 客户端并发峰值 | 服务端观测并发峰值 |
|--------------|------------|----------------|--------------------|
| 串行（1 片） | 753 ms     | 1              | 1                  |
| 并发（3 片） | 319 ms     | 3              | 3                  |
```

5 片 × 120ms 顺序执行是 600ms 量级，并发 3 把它压到两轮。服务端观测到的峰值和客户端一致，说明并发是真的并行，而不是客户端"排队等"。

并发数不是越大越好：

- 浏览器对**同域 HTTP/1.1 默认只有 6 条连接**，切片并发超过 6 只会在连接层排队，还挤掉页面自身的请求；
- HTTP/2 下没有连接数上限，但所有分片抢同一条 TCP 连接的带宽，且服务端合并分片时也有限流；
- 经验值是 **3~4**：足够把 RTT 隐藏掉，又留得下带宽给页面里其他请求。

上传与下载抢的是同一条上行/下行管道。真实场景里还要考虑**切片大小**：太小（如 64KB）会导致请求数爆炸、协议开销占比过高；太大（如 16MB）则单片重传代价高。`1~5MB` 是常见区间，配合 `3~4` 的并发。

## 四、断点续传

断点续传的实现依赖前面那条幂等性——它其实是「把已传分片查出来，只补缺的」。实验里模拟了传到一半掉线：

```
--- 二、断点续传：传到一半掉线，重连只补缺的片 ---
掉线时已传 [0, 1, 2]，缺 [3, 4]
重连后 init 返回 received=[0, 1, 2]，按总量 5 片推出还缺 [3, 4]；这一轮只发了 2 片、耗时 167 ms，若从头重传要发 5 片
```

关键信息是**重连时 `init` 返回的 `received` 数组**——客户端不需要知道自己上次传到哪，服务端说了算。这带来一个重要的健壮性：用户在另一台设备、另一个浏览器标签、甚至换了个网络，只要文件指纹一致，就能接着传。

几个容易忽略的细节：

- **`uploadId` 要按文件指纹复用**，不能每次 `init` 都新建。否则同一份文件会生成两个上传会话，`received` 永远是空的，断点续传直接失效；
- **分片大小必须固定**。`init` 时把 `chunkSize` 一起报上去，之后不允许改，否则 index 与偏移量的对应关系错乱；
- **上传会话要有过期时间**。一个被放弃的上传（用户关了页面）如果永久保留分片，磁盘会被垃圾占满。常见做法是 24~48 小时后清理，并让客户端在过期后能重新从头传（`init` 返回新的 `uploadId` + 空 `received`）。

## 五、秒传与文件指纹

同一份文件第二次上传，`init` 直接返回 `exists: true`：

```
--- 三、秒传：同一份文件第二次上传 ---
| 轮次 | init 返回    | 后续要发的分片 | 实际传输字节 |
|------|--------------|----------------|--------------|
| 首次 | exists=false | 5 片           | 5.00 MB      |
| 再次 | exists=true  | 0 片           | 0 B          |
```

指纹用 sha256 而不是文件名 + 大小，因为**改一个字节指纹就变**：

> 摘自 `./code/eng-lab/scenarios/upload.mjs`（运行：`npm run upload`）

```js
const sha256 = buf => crypto.createHash('sha256').update(buf).digest('hex')
```

指纹本身是有成本的，实测同步计算：

```
--- 五、客户端算指纹的代价（为什么要放 Worker） ---
| 文件大小 | 同步计算 sha256 耗时 |
|----------|----------------------|
| 5 MB     | 14 ms                |
| 50 MB    | 132 ms               |
```

主线程一次性算完 50MB 要 132ms，这期间页面完全不能交互（点击无响应、动画卡顿）。所以：

- 浏览器里用 **Web Worker** 计算指纹，主线程只收结果；
- 或者直接用 **`File.prototype.slice` + `crypto.subtle.digest`** 分片摘要再拼（`createHash` 在浏览器不可用，`crypto.subtle` 是异步的，天然不阻塞）；
- Node 侧对应 `worker_threads`。

第二个成本是**大文件全量读进内存**的问题：`crypto.createHash('sha256').update(stream)` 可以流式更新，边读边算，不必把整份文件加载到内存。浏览器里对应 `ReadableStream` 分块喂给 `crypto.subtle`。

秒传的边界也要说清楚：

- **指纹即内容**，所以它不会误合并（不同内容必定不同指纹）；
- 但它带来一个**探测风险**：如果接口允许无条件查"这个指纹存在吗"，别人可以用指纹反查是否上传过某个已知文件。敏感业务要加权限校验，或对指纹做服务端二次确认；
- **不能让客户端只靠指纹跳过校验**。`complete` 阶段服务端仍要按真实收到的分片算一次哈希，与 `init` 时的声明比对（或者直接信任合并结果），否则客户端可以伪造 `fileHash` 去覆盖别人已上传的文件。

## 六、完整性校验与进度聚合

缺片时服务端必须拒绝合并：

```
--- 四、完整性：缺片不许合并，齐了要能验出哈希 ---
只传了 1 片就请求合并 → HTTP 400，服务端返回 missing=[1, 2, 3, 4]
| 校验项              | 值                                |
|---------------------|-----------------------------------|
| 客户端文件 sha256   | 5e7d7dc8135f13c8444002776d7401d5… |
| 服务端合并后 sha256 | 5e7d7dc8135f13c8444002776d7401d5… |
| 是否一致            | 一致                              |
| 合并后字节          | 5.00 MB                           |
```

「合并后重新算哈希」这一步不是可选项：分片在传输途中被截断、被中间代理改写、或者客户端算错了 index，都会让文件坏掉，而这种坏掉的文件往往几个月后才会被发现。**校验成本（一次全量哈希）远低于数据损坏成本**。

进度聚合则有个常被写错的点：

> 示意片段（无配套脚本）

```js
// 错的：按已发出的字节数
onProgress(sentBytes / totalBytes)

// 对的：按服务端已确认的分片数
onProgress(receivedCount / totalChunks)
```

已发出不等于已落盘——请求还在网络里、或者服务端还在处理时，进度条就已经跑满了，用户随后会看到进度条卡在 100% 不动。按「已确认分片」聚合，进度只会在服务端真正收下一片后前进，虽然看起来慢一点，但它是可信的。

如果要更流畅的进度，可以用**两层进度**：一条显示「已发出」（快，随时前进）、一条显示「已落盘」（慢，但准确）。很多网盘就是这么做的。
