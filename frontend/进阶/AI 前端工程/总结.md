## 1. LLM 应用的前端形态

### 1.1 对话式 UI 的三个前提

把 LLM 做进对话式 UI，与传统的请求-响应界面有三个根本差异，是其余一切设计的出发点：

```
响应长度不确定   模型吐多少字，前端事先不知道，布局要能吸收任意长度
时间是流式的    结果不是一次性回来，而是逐 token 到达，天然是异步流
正确性要前端兜底 模型可能出错、胡说，可靠性必须靠前端工程补
```

一句话：**LLM 应用没有"拿一次结果"的说法，只有"管理一条持续到达的流"**。

### 1.2 传输选型：SSE vs WebSocket

纯文本生成场景，首选 SSE 而不是 WebSocket：

| 维度 | SSE | WebSocket |
| ---- | ---- | ---- |
| 方向 | 单向（服务端 → 客户端） | 全双工 |
| 传输层 | 普通 HTTP，过一切网关/代理 | 需要协议升级（upgrade） |
| 重连 | 浏览器自动重连，带 `Last-Event-ID` 续传 | 需手写重连 |
| 数据形态 | `data:` 文本行 | 任意二进制 / 消息帧 |
| 适用 | 打字机式的单向文本推送 | 语音流、实时协同等双向场景 |

打字机只需要服务端到客户端的单向文本推送，SSE 天生就是干这个的；WebSocket 的双向与二进制能力在这里用不上，却要付出协议升级与手写重连的代价。

**`EventSource` vs `fetch + ReadableStream`**：

```
EventSource        只能 GET、不能带自定义 header/body
fetch + stream     能 POST 复杂参数、接 AbortController，工程上更常用
```

### 1.3 SSE 解析：按行分帧

一个重要事实：**一个 chunk 不等于一个事件**。网络按 TCP 报文切分，一个 `data:` 行可能被劈成两半，两个事件也可能挤进同一个 chunk——唯一可靠的分帧依据是换行符。

```
攒 buffer → 见到 \n 才吐出一行 → 没吐完的残行留在缓冲区，等下一个 chunk
```

实测（`ai-lab/sse.cjs`）：逐字节到达、以及把一行从中间劈开，两种恶劣分包都能完整还原 4 个事件。

两个独立的终止条件都要处理：`data: [DONE]` 是协议层结束信号，流关闭（`reader.read()` 返回 `done`）是传输层结束信号。

> 直接按 chunk `JSON.parse` 会怎样？大概率抛 `SyntaxError`，且偶发（取决于分包时机），是最难复现的一类线上 bug。

### 1.4 流式渲染：半开代码块的控制

Markdown 流式渲染时，代码块可能处于"半开"状态：开头 ``` 已到、结尾 ``` 未到。

- **处理**：用 fence 奇偶性判断——奇数个 ``` 意味着存在未闭合代码块，这期间的增量先"按住"不渲染，闭合后整体放行。
- **不做会怎样**：代码会被当作正文渲染出去，页面出现半秒"语法乱码闪烁"，下一个 token 到达后又跳回正常。

实测（`ai-lab/sse.cjs`）：半开期间按住了 2 次增量，闭合后一次性放行。

生产实现还要叠两层：

```
按 rAF 合帧 flush   避免逐 token 重排
闭合后只对块内重新高亮  避免整篇重做
```

### 1.5 中断语义

用户点了「停止」，前端的职责边界要清楚：

```
停止渲染            立即把已收内容上屏
保留已收内容        已收 token 照常保留
丢弃后续            后续 token 全部丢弃
服务端生不停止/计不计费   前端控制不了
```

`AbortController` 让 `fetch` 抛 `AbortError`、reader 立即终止。实测（`ai-lab/sse.cjs`）：第 3 个 token 前 abort，已收 3 个保留、后续 2 个丢弃。

**中断后的 UI** 要给出明确状态（已停止 / 部分结果），不能停在"加载中"；同时把已收内容纳入上下文，避免重新生成时丢上下文。

### 1.6 重试的双重防错

网络错误重试有两个防护，缺一都可能造成重复计费：

```
指数退避        300 → 8000ms 封顶
+ 抖动          随机化退避，避免惊群
幂等键          同一次逻辑请求的所有重试携带同一个幂等键，服务端按键去重
```

## 2. AI 与前端工程结合

### 2.1 三层基建

把 AI 能力做进前端产品，工程上要立三层基建：

```
上下文   检索 + 装配：喂给模型的素材从哪来、怎么凑进窗口
约束     schema + DSL：限制模型只能输出我们能接住的东西
评测     prompt 即隐性发版：改一句提示词就是一次没有任何 diff 的发版
```

尤其 **prompt 改一次就算发版**——且是没有任何 diff 的隐性发版，必须有评测集与 badcase 回归。

### 2.2 结构化输出：四道闸

模型输出的 JSON 常带围栏和客套话，要稳定接住，走四道闸：

```
噪声剥离   抽围栏 / 取首尾花括号
JSON.parse   尝试解析
schema 校验  校验字段
失败重试   带上错误清单回喂重试，而不是原样重发
```

实测（`ai-lab/gen.cjs`）：第 1 次围栏缺右括号解析失败、第 2 次字段类型错误校验失败、第 3 次通过——**错误回喂是修复率的关键**。

> 优先用模型 API 的结构化输出模式（JSON Schema 约束解码）从源头消灭围栏噪声，但校验仍要保留——「格式对」不等于「内容对」。

### 2.3 组件生成与白名单 DSL

为什么不直接让模型写组件代码？

```
直接生成自由代码   每次都不一样（命名/依赖/风格随机），进不了设计系统
输出受约束的 DSL   schema 即文档，渲染交给自己的引擎
```

**组件生成走白名单 DSL**：schema 即文档，坏结果按节点定位；表达力被锁死不是缺陷，而是把"模型会乱来"这个风险关在笼子里。

### 2.4 上下文装配与 token 预算

上下文窗口不够时，按优先级贪心装配：

```
system   永不动（最高优先级）
检索片段  其次
代码上下文  再次
历史对话  最末位，最先丢
```

实测（`ai-lab/gen.cjs`）：预算 1600 时保住 system+检索+代码（1520），丢弃历史对话。

- **token 粗算**：中文按字、英文按 4 字符，留 20% 余量兜底误差。
- **贪心的特性**：装不下的高优先级片段会被跳过、转而装更小的低优先级片段——先保装得下的最重要内容，而不是严格排序后截断；想要严格语义需自行改写为"命中即停"策略。

### 2.5 设计稿转代码的边界

设计稿转代码的自动化程度分两块：

```
布局骨架    高自动化：结构、排布能可靠产出
交互逻辑    仍是人的边界：状态流转、事件
可访问性    仍是人的边界：语义、焦点、对比度
```

结论：**交互逻辑与可访问性仍是人的边界**。

## 3. 端侧推理与 WASM

### 3.1 端侧 vs 云端

端侧推理是"用体积/算力/兼容，换隐私/离线/零边际成本"：

```
端侧收益   隐私不愁、可离线、推理边际成本为零
端侧代价   模型体积大、设备算力有限、兼容性参差
落地形态   不是二选一，而是分层：能端侧就走端侧，重的才上云
```

### 3.2 模型分片加载

大模型整包下载太慢，用分片加载降低峰值内存与首包延迟：

```
80MB 模型分 20 片
完整加载需要 80MB
分片加载峰值缓冲区只有 4MB
```

实测换算成内存收益：整包需 80MB，分片后峰值只需 4MB。

### 3.3 WASM 的性能真相

**WASM 不一定比 JS 快**。反直觉的实测（`ai-lab/wasm.cjs`）：

```
2e7 次紧循环
  WASM   46.6ms
  JS     16.0ms   ← 快约 3×
因为这种循环上 V8 的 JIT 打得比 WASM 更凶
```

- **WASM 真正的价值**：可移植与可预测（无 JIT 预热、无 deopt 悬崖、无 GC 停顿）。
- **真正加速来源**：SIMD / threads 与厂商优化内核（如 XNNPACK），不是"用 WASM 重写一遍"。

### 3.4 内存预算与量化

端侧跑模型，内存大致可按**参数量 × 每参数字节 + KV cache** 估算：

```
参数所占内存 = 参数量 × 每参数字节
  fp16    2B
  int8    1B
  int4    0.5B
KV cache  随上下文线性增长
```

实测（`ai-lab/wasm.cjs`）：

```
1B 参数 fp16    2.0GB
1B 参数 int4    0.50GB  → 量化到 1/4
4k 上下文 KV cache  另需 384MB，且随上下文线性增长
```

**量化就是把每个参数的字节数压下来**（fp16 → int4），是端侧"能不能装下"的决定性手段。

### 3.5 线程模型与降级链

推理放主线程会阻塞 UI：

```
单帧 20ms 的推理 × 3 = 60ms 主线程完全无响应
```

必须在 Worker 中推理，并对 WebGPU → WASM → 云端做降级链——每一档能力递减、但保证能跑。

## 4. AI 应用的性能与体验

### 4.1 TTFT 三段分解

首字延迟（TTFT）拆成三段分别优化：

```
排队段   服务端队列——前端改不动
网络段   连接复用（保持 HTTP 连接、TLS 复用）
prefill  上下文压缩（减前缀 token）
```

实测（`ai-lab/perf.cjs`）：TTFT 从 428ms 降到 342ms——改动的是**连接复用 + 上下文压缩**，排队段前端做不了。

```
感知填充   排队段改不动时，用占位 / 流式 loading 让用户"不觉得等"
```

### 4.2 flush 合帧

逐 token 改 DOM 等于每帧多次重排，用 rAF 合帧把更新合并到一帧：

```
600 token 的 DOM 更新
  不合帧   600 次
  rAF 合帧  150 次   → 降为 25%
```

配合 1.4 的半开代码块控制，流式渲染既正确又流畅。

### 4.3 成本模型

成本优化的三条路径，环环递进：

```
基线单次        0.0390
+ 前缀缓存       0.0228
+ 叠加上下文压缩   0.0185
```

**前缀缓存的前提是前缀字节级稳定**——时间戳、随机 ID 放前面会让整条前缀失效。

### 4.4 降级阶梯

高成本 / 能力不足时的四档降级，逐级递降：

```
full     完整模型
lite     切小模型
short    限制上下文
static   静态兜底 + 重试入口
```

**降级必须对用户可见**，否则会被当成质量问题；每档都保留"重试 / 回到上级"的入口。

### 4.5 观测指标

AI 应用的前端可观测指标，盯这几项：

```
TTFT       看 P90（首字延迟的长尾）
TPOT       每 token 生成耗时
完成率      一次生成完整走完的比例
abort 率    按 prompt 版本分组——是 prompt 质量最敏感的晴雨表
单位成本    一次请求的计价
```

abort 率按 prompt 版本分组，能直接反映哪版提示词在诱导用户中断。
