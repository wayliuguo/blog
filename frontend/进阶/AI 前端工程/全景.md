# AI 前端工程全景

> 本板块统一业务场景：**智能客服助手**——流式对话（chat-ui）、订单/退款工具调用（fn-calling）、用户转化打分（wasm-infer）。四个字：前端怎么在 AI 产品里「接得住、管得住、跑得动、花得起」。

## 一、前端在 AI 应用里的四个角色

大模型能力都在服务端，但用户摸到的每一层都是前端工程。本板块的四个角色与对应篇目：

| 角色 | 要解决的问题 | 一句话判据 | 篇目 |
| --- | --- | --- | --- |
| 对话 UI | token 流变成可靠界面 | 流要「接得住」：分帧、半开代码块、可中断 | [LLM 应用前端形态](./LLM%20应用前端形态.md) |
| 结构化接线 | 模型输出进程序 | 输出要「管得住」：白名单 schema、错误回喂 | [AI 与前端工程结合](./AI%20与前端工程结合.md) |
| 端侧推理 | 隐私/离线/零边际成本 | 任务要「跑得动」：分层、Worker、内存预算 | [端侧推理与 WASM](./端侧推理与%20WASM.md) |
| 性能与成本 | 体验与账单 | 功能要「花得起」：TTFT、合帧、降级 | [AI 应用的性能与体验](./AI%20应用的性能与体验.md) |

## 二、一张图：智能客服的数据流

统一业务场景的完整链路，四个角色各占一段：

```
用户输入
  → [对话 UI] fetch POST + SSE 流式接收（分帧解析 / 半开 fence / rAF 合帧）
  → [服务端 LLM] DeepSeek / 任意 OpenAI 兼容端点
  → [结构化接线] 模型返回 tool_calls → 前端白名单执行（查订单/查政策）→ 结果回喂 → 最终答复
  → [端侧推理] 敏感特征不出设备：本地 wasm 模型打分，只上传概率
  → [性能与体验] TTFT 拆三段优化 + 降级阶梯 + 成本监控
```

- 「接得住」与「管得住」是**确定性对概率**的两道闸：流式层保证渲染确定性，结构化层保证程序消费确定性；
- 「跑得动」与「花得起」是**工程收益**的两本账：端侧把小任务的成本从按 token 计费变成零边际成本，性能层把账单和流失率一起压下来。

## 三、与相邻板块的分工

- **ai/Agent 开发**（ai 板块）：讲 Agent 的**后端编排**——Agent Loop、记忆、RAG、LangGraph、MCP，配套 NestJS 工程；
- **本板块**：讲同样的模型能力**落到前端**——SSE 消费、工具的前端接线、端侧推理、流式体验。两边的 Function Calling 是同一段协议的两个视角：Agent 板块关心循环与决策，本板块关心白名单与回喂的工程化；
- **性能优化**（frontend 板块）：rAF 合帧、长任务、帧预算全部复用，AI 应用只是多了 token 流这一种数据形态。
