# AI 前端工程：面试题

> 格式：结论 → 原理 → 边界/坑 → 追问。标注「第 X 篇」的题目按阅读顺序出题。

### Q1: LLM 应用为什么首选 SSE 而不是 WebSocket？（第 1 篇）

- **结论**：打字机只需要服务端到客户端的单向文本推送，SSE 天生就是干这个的；WebSocket 的双向与二进制能力在这个场景里用不上，却要付出协议升级与手写重连的代价。
- **原理**：SSE 走普通 HTTP，能过一切网关和代理；断线由浏览器自动重连，并带 `Last-Event-ID` 续传；数据就是 `data:` 文本行。WebSocket 是全双工，适合语音流、实时协同这类双向场景。
- **边界**：需要客户端持续上行（如语音实时转写、边说边传音频）时，SSE 不适用，上 WebSocket 或 WebRTC。
- **追问**：`EventSource` 和 `fetch + ReadableStream` 怎么选？→ `EventSource` 只能 GET、不能带自定义 header/body；`fetch` 方案能 POST 复杂参数并接 `AbortController`，工程上更常用。

### Q2: SSE 解析时为什么必须按换行分帧？一个 chunk 不等于一个事件吗？（第 1 篇）

- **结论**：不等于。网络按 TCP 报文切分，一个 `data:` 行可能被劈成两半，两个事件可能挤在同一个 chunk 里，唯一可靠的分帧依据是换行符。
- **原理**：攒 buffer，见到 `\n` 才吐出一行；没吐完的残行留在缓冲区等下一个 chunk。实测（`ai-lab/sse.cjs`）——逐字节到达、以及把一行从中间劈开，两种恶劣分包都能完整还原 4 个事件。
- **边界**：`data: [DONE]` 是协议层的结束信号，与流关闭（`reader.read()` 返回 `done`）是两个独立的终止条件，两者都要处理。
- **追问**：按 `chunk` 直接 `JSON.parse` 会怎样？→ 大概率抛 `SyntaxError`，且偶发（取决于分包时机），是最难复现的一类线上 bug。

### Q3: 流式渲染 Markdown 时半开的代码块怎么处理？（第 1 篇）

- **结论**：用 fence 奇偶性判断——奇数个 ``` 意味着存在未闭合的代码块，这期间的增量先按住不渲染，闭合后整体放行。
- **原理**：不按住的话，代码语法会被当作正文渲染出去，页面出现半秒的「语法乱码闪烁」，下一个 token 到达后又跳回正常。实测（`ai-lab/sse.cjs`）——半开期间按住了 2 次增量，闭合后一次性放行。
- **边界**：生产实现还要叠两层：按 rAF 合帧 flush（避免逐 token 重排）、代码块闭合后只对块内重新做高亮。
- **追问**：rAF 合帧为什么必须做？→ 每秒几十个 token 逐条改 DOM 等于每帧多次重排，实测 600 token 可压到 150 次更新（见第 4 篇）。

### Q4: 用户点了「停止」，前端到底要负责什么？（第 1 篇）

- **结论**：`abort()` 之后立刻停止渲染、保留已收到的内容。服务端是否停止生成、是否计费，前端控制不了。
- **原理**：`AbortController` 让 `fetch` 抛 `AbortError`，reader 立即终止；已收 token 照常上屏，后续全部丢弃。实测（`ai-lab/sse.cjs`）——第 3 个 token 前 abort，已收 3 个保留、后续 2 个丢弃。
- **边界**：中断后的 UI 要给明确状态（已停止 / 部分结果），不能停在「加载中」；同时把已收内容纳入上下文，避免重新生成时丢上下文。
- **追问**：网络错误重试时怎么防止重复计费？→ 同一次逻辑请求的所有重试携带同一个幂等键，服务端按键去重。

### Q5: 模型输出的 JSON 经常带围栏和客套话，怎么稳定接住？（第 2 篇）

- **结论**：四道闸——噪声剥离（抽围栏/取首尾花括号）→ `JSON.parse` → schema 校验 → 失败时**带上错误清单回喂重试**，而不是原样重发。
- **原理**：实测（`ai-lab/gen.cjs`）——第 1 次围栏缺右括号解析失败、第 2 次字段类型错误校验失败、第 3 次通过。错误回喂是修复率的关键。
- **边界**：优先用模型 API 的结构化输出模式（JSON Schema 约束解码）从源头消灭围栏噪声，但校验仍要保留——「格式对」不等于「内容对」。
- **追问**：为什么不直接让模型写组件代码？→ 自由代码每次都不一样（命名/依赖/风格随机），进不了设计系统；应输出受约束的 DSL，渲染交给自己的引擎。

### Q6: 上下文窗口不够时，先丢什么？（第 2 篇）

- **结论**：按优先级贪心装配——system 永不动，其次检索片段、代码上下文，历史对话排最末位最先丢。
- **原理**：实测（`ai-lab/gen.cjs`）——预算 1600 时保住 system+检索+代码（1520），丢弃历史对话。预算靠 token 粗算（中文按字、英文约 4 字符/token）并留 20% 余量。
- **边界**：贪心装配的特性是「装不下的高优先级片段会被跳过，转而装更小的低优先级片段」——先保装得下的最重要内容，而不是严格排序后截断；想要严格语义需自行改写为「命中即停」策略。
- **追问**：prompt 改一次算不算发版？→ 算，且是没有任何 diff 的隐性发版，必须有评测集与 badcase 回归。

### Q7: 端侧跑模型，内存够不够怎么算？WASM 一定比 JS 快吗？（第 3 篇）

- **结论**：内存 = 参数量 × 每参数字节（fp16 2B / int8 1B / int4 0.5B）+ KV cache（随上下文线性增长）；WASM **不一定**更快。
- **原理**：实测（`ai-lab/wasm.cjs`）——1B 参数 fp16 要 2.0GB，int4 量化降到 0.50GB（1/4），4k 上下文 KV cache 另需 384MB；而 2e7 次紧循环 WASM 46.6ms vs JS 16.0ms，WASM 慢约 3×，因为这种循环上 V8 的 JIT 打得更凶。
- **边界**：WASM 的价值是可移植与可预测（无 JIT 预热、无 deopt 悬崖、无 GC 停顿），真正加速来自 SIMD/threads 与厂商优化内核（如 XNNPACK），不是「用 WASM 重写一遍」。
- **追问**：推理放主线程会怎样？→ 单帧 20ms 的推理 ×3 就是 60ms 完全无响应，必须放 Worker，并对 WebGPU→WASM→云端做降级链。

### Q8: 首字迟迟不出、成本一直涨、请求失败——前端各怎么处理？（第 4 篇）

- **结论**：TTFT 拆成排队/网络/prefill 三段分别优化；成本靠前缀缓存 + 上下文压缩；失败走四档降级阶梯。
- **原理**：实测（`ai-lab/perf.cjs`）——TTFT 428ms → 342ms（连接复用 + prompt 压缩，排队段前端改不动）；单次成本 0.0390 → 前缀缓存 0.0228 → 叠加压缩 0.0185；降级 full → lite → short → static。
- **边界**：前缀缓存生效的前提是前缀字节级稳定（时间戳、随机 ID 放前面会全废）；降级必须对用户可见，否则会被当成质量问题。
- **追问**：该盯哪些指标？→ TTFT（看 P90）、TPOT、完成率、abort 率（按 prompt 版本分组，是 prompt 质量最敏感的晴雨表）、单位成本。
