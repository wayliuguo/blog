# 构建平台与产物治理

「交付与质量」那篇讲的是**怎么用**一条流水线；这一篇讲的是**这条流水线本身怎么建**：云端的构建任务怎么缓、改一个文件到底要重建多少东西、线上报错的行号怎么变回源码。这三件事决定了一个构建平台是「能跑」还是「好用」——用 `platform-lab` 的 `build.cjs` 逐一实测。

## 一、缓存键：为什么不能用 mtime

构建缓存的第一原则是**缓存键必须完全由输入内容决定**。听起来理所当然，但最常见的错误就是拿文件修改时间当键：

> 摘自 `./code/platform-lab/build.cjs`

```js
function hash(s) {
  let h = 0x811c9dc5;
  for (let i = 0; i < s.length; i++) {
    h ^= s.charCodeAt(i);
    h = Math.imul(h, 0x01000193);
  }
  return h >>> 0;
}

// ---------- 场景一：缓存键——用 mtime 会白白失效，用内容 hash 才稳 ----------
// 云端构建里 CI 每次都是全新 checkout：所有文件 mtime 都是"刚刚"，内容却一个字没变。
function buildWithCache(files, cache, keyBy) {
  let rebuilt = 0;
  for (const f of files) {
    const key = keyBy === 'hash' ? hash(f.content) : String(f.mtime);
    if (cache[f.name] === key) continue; // 命中缓存，不重建
    cache[f.name] = key;
    rebuilt++;
  }
  return rebuilt;
}
```

实测：3 个文件首次全建；内容一字未改、只把 mtime 从 1000 改到 2000（CI 重新 checkout 就是这个效果），**hash 缓存 0 个重建，mtime 缓存 3 个全重建**。

真实工程里缓存键的构成要比「文件内容」更全：

| 输入项 | 是否入键 | 说明 |
| --- | --- | --- |
| 源文件内容 hash | ✅ | 主体 |
| 依赖版本（lockfile） | ✅ | 依赖变了必须重建 |
| 构建参数（mode / env / target） | ✅ | 同一份源码不同参数产出不同 |
| 工具链版本（Node / 编译器） | ✅ | 升级工具链后旧缓存不可信 |
| 文件 mtime | ❌ | 与内容无关，纯噪声 |
| 构建开始时间 | ❌ | 同上 |

漏掉「工具链版本」是最隐蔽的一类：升级了 Node 或打包器，缓存还命中，产出的却是旧工具链的产物，问题往往要几周后才以奇怪的方式暴露。

## 二、增量构建：改一个文件，到底该重建几个产物

全量重建最省心，也最慢。要快，就得算出**真正脏掉的那一撮**：从被改的文件出发，沿**反向依赖边**传播。

> 摘自 `./code/platform-lab/build.cjs`

```js
function dirtySet(graph, changed) {
  // 反向边：谁依赖我 → 谁也要重建
  const rev = {};
  for (const [id, node] of Object.entries(graph)) {
    for (const dep of node.deps) (rev[dep] || (rev[dep] = [])).push(id);
  }
  const dirty = new Set(changed);
  const queue = [...changed];
  while (queue.length) {
    const cur = queue.shift();
    for (const downstream of rev[cur] || []) {
      if (dirty.has(downstream)) continue;
      dirty.add(downstream);
      queue.push(downstream);
    }
  }
  return dirty;
}
```

实测（4 个源文件，依赖关系 a → b/c → d）：

- 改叶子 `d.js`：只重建 **1** 个
- 改 `c.js`：重建 **2** 个（`c` 与依赖它的 `d`，**不包含不相关的 `b`**）
- 改底层 `a.js`：4 个全脏

两个实现细节：`dirty` 用 Set 防重复入队（菱形依赖会让一个节点被访问多次）；反向图每次重算太浪费，真实平台会维护一份持久化的反向索引，文件变更时增量更新。

增量构建的收益高度依赖**依赖图的精度**：粒度太粗（按目录/包）会过度重建，粒度太细（按语句）则维护成本失控。工程上主流是按模块（文件）级，这也是 Vite/Turbopack 那一类工具的做法。

## 三、产物溯源：线上报错 `app.js:150` 是哪一行源码

压缩混淆之后，线上错误堆栈里的行列号对排查毫无意义，除非你能把它**反查回源码**。

> 摘自 `./code/platform-lab/build.cjs`

```js
function locate(manifest, bundle, line) {
  const entry = manifest[bundle];
  if (!entry) return null;
  for (const s of entry.sources) {
    if (line >= s.startLine && line < s.startLine + s.lines) {
      return { file: s.file, line: line - s.startLine + 1 };
    }
  }
  return null;
}
```

实测：`app.8f3c.js:150` → `src/cart.js:31`；越界行号与查不到的 bundle 都返回 `null` 而不是猜一个。

这里有两个层次的东西，别混为一谈：

- **manifest**：记录「这个版本的包里有哪些源文件、各自的偏移」，负责粗定位与版本治理（哪个版本还在服务、能不能下线）。
- **sourcemap**：用 VLQ 编码做**行列级**映射，能精确到列，是真正的反查主力。

工程上三条必须守住：

1. **sourcemap 不随产物一起发布到公开 CDN**（等于把源码公开），要传到错误监控平台内部，或加访问控制。
2. **版本要一一对应**：线上报错要带上产物 hash，用 hash 找对应版本的 map；map 丢了就只能定位到压缩代码。
3. **构建要可复现**：同样输入产出同样的 hash，否则溯源链路会错位。这要求依赖锁定、构建参数固定、并尽量避免把时间戳/随机值写进产物。

## 四、平台化的边界：什么才值得做成平台

不是所有构建问题都要建平台。判断标准很简单：**这件事是不是每个团队都要重复做一遍，且做错了代价很高**。

| 能力 | 值得平台化吗 | 理由 |
| --- | --- | --- |
| 分布式缓存（远程缓存） | ✅ | 每队自建一遍纯浪费，命中率直接决定 CI 时长 |
| 产物溯源与版本治理 | ✅ | 出错时影响排查速度，且需要集中存储 |
| 依赖图与增量构建 | ✅ | 通用逻辑，且越做越准 |
| 单项目的构建参数调优 | ❌ | 业务相关，平台做不好也管不了 |
| 把构建脚本塞进平台 DSL | ⚠️ | 过度抽象会让「本地能跑、平台跑不了」成为常态 |

最后一行是最常见的坑：平台应该**复用**项目自己的构建脚本（同一份命令跑在本地和 CI），而不是把它翻译成平台的 DSL。两者一旦分叉，就会出现一类极难排查的问题。

## 小结

- **缓存键**：必须由输入内容决定（源码 hash + 依赖版本 + 构建参数 + 工具链版本），**mtime 是纯噪声**——实测只改 mtime，hash 缓存 0 重建 vs mtime 缓存全重建。
- **增量构建**：沿反向依赖边传播脏标记，用 Set 防重复入队；实测改叶子只重建 1 个、改底层才全脏（4 个）。
- **产物溯源**：manifest 管版本与粗定位，sourcemap 管行列级映射；越界与查不到都返回 `null` 而不是猜。
- **sourcemap 安全**：不随产物公开，按 hash 对应版本，构建要可复现。
- **平台化边界**：复用项目自己的构建脚本，别翻译成平台 DSL——本地与 CI 分叉的代价极高。
