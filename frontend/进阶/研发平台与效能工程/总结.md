## 1. 构建平台与产物治理

### 1.1 缓存键：由内容决定

缓存键决定命中率——键错了，缓存永远失效。**缓存键必须完全由输入内容决定**：源码 hash + 依赖版本 + 构建参数 + 工具链版本；mtime 是纯噪声。

实测（`platform-lab/build.cjs`）：

```
内容一字未改，只改 mtime
  hash 缓存    0 重建（全部命中）
  mtime 缓存   3 个全重建
```

云端构建每次都是全新 checkout，所有文件 mtime 都是"刚刚"——用 mtime 等于缓存永远失效。

**最隐蔽的漏项**：工具链版本不入键。升级 Node/打包器后旧缓存仍命中，产出的却是旧工具链的产物——这类问题往往几周后才以奇怪的方式暴露。

构建参数也要入键：同一份源码用 dev / prod 模式产出完全不同，参数不入键会拿到错误模式的产物。

### 1.2 增量构建：依赖图与脏传播

改一个文件，怎么算出该重建哪些产物？从被改文件出发，沿**反向依赖边**传播脏标记：

```
依赖图  a → b / c → d
  改叶子 d.js   重建 1 个
  改     c.js   重建 2 个（不包含不相关的 b）
  改底层 a.js   全脏 4 个
```

**两个实现细节**：

- `dirty` 用 Set 防重复入队——菱形依赖会让同一节点被多次访问，必须去重。
- 反向图要持久化并增量更新，每次重算在大仓里本身就是开销。

依赖图粒度有取舍：按文件是主流，太粗过度重建、太细维护失控。

增量构建与远程缓存的分工：前者决定「本次要建哪些」，后者决定「这些能不能直接拿来用」；两者叠加才把 CI 时长压下去。

### 1.3 产物溯源：manifest 与 sourcemap

线上报 `app.js:150`，怎么定位到源码？**两层配合**：

```
manifest   管版本与粗定位——哪个版本有哪些源文件、各占多少行
sourcemap  管行列级映射——VLQ 编码的精确映射
```

实测（`platform-lab/build.cjs`）：`app.8f3c.js:150` → `src/cart.js:31`；越界行号与查不到的 bundle 都返回 `null` 而不是猜一个。

**三条守线**：

1. sourcemap **不随产物发到公开 CDN**（等于公开源码）。
2. 版本按产物 hash 一一对应，map 丢了就只能定位到压缩代码。
3. **构建要可复现**，否则溯源链路会错位。

### 1.4 平台化边界

不是所有东西都值得做成平台：

```
值得平台化   远程缓存 / 产物治理 / 依赖图
别做         把项目构建脚本翻译成平台 DSL
```

原因：应该复用同一份脚本跑在本地和 CI，分叉之后「本地能跑、平台跑不了」会成为常态且极难排查。

## 2. 实验与增长平台

### 2.1 分桶：稳定性与均匀性

AB 实验的分桶要同时满足**稳定**与**均匀**：`hash(userId + ':' + salt) % n`，**可重算、不能用随机数**；盐里必须带实验名。

实测（`platform-lab/ab.cjs`）：

```
同一用户连续 100 次分桶结果恒定
1 万用户落实验组 49.87%（偏差 < 2%）
```

不带盐的话所有实验对同一用户的分桶完全一致，实验之间产生系统性相关。

**用什么 ID 分桶决定了实验单位**——用设备 ID 是按设备、用账号 ID 才是按人；选错是隐性且致命的（同一个人在手机和电脑上看到不同版本）。

能用 `Math.random()` 吗？绝对不行——用户刷新一次就换组，体验割裂且数据作废。

### 2.2 正交分层：多实验隔离

多个实验同时跑，怎么避免互相污染？**分层**：

```
同层互斥       一个人只进一个实验
跨层不同盐→正交  不同层的分桶互相独立
```

实测（`platform-lab/ab.cjs`）：UI 层与排序层各自分桶，四种命中组合均匀分布在四格，最大偏差 0.53%。

**正交只保证分配独立，不保证效果可加**。一个改按钮颜色、一个改推荐排序，叠加效果可能不是简单相加，所以核心指标要在「只中 A / 只中 B / 都中」三群里分别看。

层不够用了怎么办？加层或把互斥实验排进同一层的流量轮转；但层数越多、单层可用流量越少，样本量压力越大。

### 2.3 SRM：样本比例失衡

实验跑到一半发现两组人数是 5200/4800，能不能继续看指标？**不能**。这是 SRM（样本比例失衡），说明分流或埋点坏了，**结论一律作废**。

```
卡方检验（临界值 3.84）
  4980 / 5020  卡方 0.16   < 3.84  通过
  5200 / 4800  卡方 16.00  > 3.84  判失衡，结论作废
```

**SRM 成因按频率排序**：埋点丢失（某组 SDK 上报被拦截）> 分流时机不一致 > 跳转丢参 > 机器人流量。

SRM 检查必须做成平台**自动巡检**，不能等人看报表。为什么不能"先看看指标，万一结论明显呢"？失衡意味着两组人群本身不可比（可能是某类用户根本没被记进来），任何差异都可能来自这个偏差而非实验效果。

### 2.4 显著性：样本量决定结论

转化率从 5.0% 涨到 5.4%，能上线吗？**看样本量，不看提升幅度**。两比例 z 检验，临界值 1.96。

实测（`platform-lab/ab.cjs`）——**同样的 8% 提升**：

```
每组 2 万样本   z=1.80  不显著
每组 5 万样本   z=2.85  显著
```

样本量决定结论。

**三条纪律**：

1. 实验前先按 MDE 算样本量，不够就别开。
2. **禁止中途偷看**（每天看一次、显著就停，会把假阳性率从 5% 抬到 20%+）。
3. 样本足够大时 0.1% 提升也能"显著"，但**统计显著 ≠ 值得上线**，还要看置信区间与收益量级。

想连续监测？用序贯检验/贝叶斯方法（专门允许连续看），或在实验设计阶段就定好固定周期与停止规则。

## 3. 研发效能度量

### 3.1 DORA 四指标

老板要"提升研发效能"，先从 **DORA 四指标**入手：部署频率、变更前置时间、变更失败率、MTTR。

实测一例（`platform-lab/metrics.cjs`）：

```
部署频率     2 次/天      high
变更前置时间  20h         elite
变更失败率    8.3%        high（离 elite ≤5% 差一档）
MTTR         1h          elite
```

**口径三条**：

1. **用中位数**不用平均值（一次卡两周的发布会把均值拉飞）。
2. **四个指标一起看**（单看部署频率，团队会用质量换速度做坏指标）。
3. 跨行业比意义有限，**跟自己历史比**更有价值。

### 3.2 周期分解与瓶颈定位

拿到四指标后，再把**交付周期拆段**找瓶颈，而不是直接"让大家写快点"。

实测（`platform-lab/metrics.cjs`）——一个 PR 从创建到上线 72h：

```
编码   4h（6%）
等待   62h（86%）  评审排队 60h + 发布窗口 2h
```

瓶颈在评审排队与发布窗口，**不在编码速度**。

**推论**：编码只占 6% 时，把编码效率翻倍的端到端收益仅约 3%——先解决等待，再谈提速。

### 3.3 度量反模式与原则

不能直接用代码行数或部署次数考核：

- **反模式一 · LOC 考核**：一次优秀重构 LOC 300→120（−60%）但前置时间 48h→12h、故障 3→0，LOC 考核会把它判成"产出下降 60%"。
- **反模式二 · 按部署次数考核个人**：同样的 200 行改动拆成 10 个 PR 后指标翻 5 倍。
- **反模式三 · 窗口裁剪**：同一批变更 30 天窗口失败率 10.0%，掐掉最后一周变 5.3%（跨过 elite 门槛只差"从哪天开始算"）——窗口与口径必须固定。

古德哈特定律：**指标一旦成为目标，就不再是好指标**。

**三条原则**：

1. 度量团队，不度量个人。
2. 多指标交叉验证。
3. 度量只用于找瓶颈，不用于排名。

### 3.4 读趋势与难采集指标

看趋势要看信噪比，别被波动带节奏：

```
Q3→Q4  降 0.5h 但波动 4.4h（比值 0.11）  是噪声
Q4→Q5  降 12.3h（比值 2.47）            才是真变化
变异系数 9%~16% → 季度间低于 15% 的变化基本不可信
```

**难采集但重要**：满意度、认知负荷、文档质量——这些靠定期问卷，不靠事件流。
