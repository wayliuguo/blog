# 实验与增长平台

## 一、分桶：稳定与均匀是两个不同要求

**稳定**：同一个用户每次进来都要落在同一个桶。否则他今天看到新版、明天看到旧版，体验割裂，数据也失去意义。
**均匀**：桶之间的人数要符合配置比例，否则两组本来就不可比。

两者都由同一个函数决定——**用户 ID + 实验盐**的哈希取模：

> 摘自 `./code/platform-lab/ab.cjs`

```js
function bucket(userId, salt, buckets = 100) {
  return hash(userId + ':' + salt) % buckets
}
```

实测：同一用户连续 100 次分桶结果恒定；1 万个用户落在实验组（桶号 < 50）的比例是 **49.87%**，偏差 < 2%。

三个必须知道的细节：

1. **盐里要带实验名**。不带盐的话，所有实验对同一个用户的分桶结果完全一样，实验之间产生系统性相关（见第二节）。
2. **用什么 ID 分桶决定实验单位**。用设备 ID 分桶，同一个人在手机和电脑上会看到不同版本；用账号 ID 分桶才是「按人」实验。选错实验单位是隐性且致命的。
3. **不要用随机数**。`Math.random()` 每次结果都不同，用户刷新就换组——这是新手最常踩的坑。

## 二、正交分层：多个实验叠在一个人身上

一个产品同时跑十几个实验是常态。如果所有实验共用一套分桶，那么「被实验 A 选中的人」和「被实验 B 选中的人」会高度重叠，两个实验的效果就纠缠在一起、无法归因。

解法是**分层**：同一层内的实验互斥（一个人只进其中一个），层与层之间用不同的盐 → **正交**。

> 摘自 `./code/platform-lab/ab.cjs`

```js
  const N = 10000
  const quad = [0, 0, 0, 0] // [都不中, 只中A, 只中B, 都中]
  for (let i = 0; i < N; i++) {
    const a = bucket('u-' + i, 'layer-UI') < 50
    const b = bucket('u-' + i, 'layer-rank') < 50
    quad[(a ? 1 : 0) + (b ? 2 : 0)]++
  }
```

实测：UI 层与排序层各自分桶，四种命中组合均匀分布在四格，**最大偏差 0.53%**——这就是正交的含义：你在不在 A 实验里，与你在不在 B 实验里无关。

工程上还要处理**层间交互**：即便正交，一个改按钮颜色、一个改推荐排序，两者叠加的效果也可能不是简单相加。所以核心指标要在「只中 A」「只中 B」「都中」三群里分别看，发现异常交互就手工拆开跑。

## 三、SRM：样本比例失衡时，结论一律作废

配置成 50/50，结果跑出来 5200/4800——这不是「稍微不均匀」，而是**说明分流或埋点坏了**。此时看任何指标都没有意义。这个检查叫 SRM（Sample Ratio Mismatch），用卡方检验做：

> 摘自 `./code/platform-lab/ab.cjs`

```js
function srmChiSquare(observed, expectedRatio) {
  const total = observed.reduce((a, b) => a + b, 0)
  let chi = 0
  for (let i = 0; i < observed.length; i++) {
    const e = total * expectedRatio[i]
    chi += ((observed[i] - e) ** 2) / e;
  }
  return chi // df = 组数 - 1；两组时 3.84 是 p=0.05 的临界值
}
```

实测：4980/5020 的卡方是 **0.16**（远小于 3.84，通过）；5200/4800 的卡方是 **16.00**（远大于 3.84，判定失衡）。

SRM 的常见成因，按出现频率排序：

1. **埋点丢失**：某一组的 SDK 上报被拦截（比如新版页面漏了埋点代码），人进来了但事件没记。
2. **分流时机不一致**：一组在启动时分流、一组在页面可见时才分流，导致进入实验的人数不同。
3. **重定向与跳转丢参**：实验组页面跳转后丢了实验参数，被当成未命中。
4. **机器人流量**：爬虫集中在某一组（尤其是被搜索引擎抓取到的那一个版本）。

SRM 检查必须**做在实验平台的自动巡检里**，而不是等人去看报表——失衡一旦没被发现，后面所有的分析与决策都是建立在错误数据上的。

## 四、显著性：「提升 8%」能不能信

转化率从 5.0% 涨到 5.4%，相对提升 8%，听上去很棒。但**提升幅度本身什么也说明不了**，要看它相对于噪声有多大——这就是 z 检验：

> 摘自 `./code/platform-lab/ab.cjs`

```js
function zTest(convA, nA, convB, nB) {
  const p1 = convA / nA
  const p2 = convB / nB
  const pooled = (convA + convB) / (nA + nB)
  const se = Math.sqrt(pooled * (1 - pooled) * (1 / nA + 1 / nB))
  const z = (p2 - p1) / se
  return { p1, p2, z, lift: (p2 - p1) / p1, significant: Math.abs(z) > 1.96 }
}
```

实测：**同样的 8% 提升**，每组 2 万样本时 `z = 1.80 < 1.96`，**不显著**；每组 5 万样本时 `z = 2.85 > 1.96`，**显著**。

由此得到三条工程纪律：

1. **实验前先算样本量**。按基线转化率与期望的最小可检测提升（MDE）估算需要多少样本，达不到就别开实验——跑不够样本的实验只会产出噪声。
2. **禁止中途偷看（peeking）**。每天看一次结果、看到显著就停手，会把假阳性率从 5% 抬到 20% 以上。要固定实验周期，或用序贯检验（如 Optimizely 的 Stats Engine）这种专门允许连续监测的方法。
3. **区分统计显著与实际显著**。样本足够大时，0.1% 的提升也能"显著"，但它不值得上线的复杂度和维护成本。决策要看置信区间和收益量级，而不是只看一个 p 值。
