> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。

## 一、基础概念

### Q1: 构建缓存的键为什么不能用文件修改时间？（第 1 篇）

- **结论**：缓存键必须完全由**输入内容**决定（源码 hash + 依赖版本 + 构建参数 + 工具链版本），mtime 是纯噪声。
- **原理**：实测（`platform-lab/build.cjs`）——内容一字未改只把 mtime 从 1000 改成 2000，hash 缓存 **0 重建**，mtime 缓存 **3 个全重建**。云端构建每次都是全新 checkout，所有文件 mtime 都是"刚刚"，用 mtime 等于缓存永远失效。
- **边界**：最容易漏的是**工具链版本**（Node、打包器）。它不入键的话，升级工具链后旧缓存照样命中，产出的却是旧工具链的产物——这类问题往往几周后才以奇怪的方式暴露。
- **追问**：为什么构建参数也要入键？→ 同一份源码用 dev / prod 模式产出完全不同；参数不入键会拿到错误模式的产物。

### Q2: 改一个文件，怎么算出该重建哪些产物？（第 1 篇）

- **结论**：从被改文件出发，沿**反向依赖边**传播脏标记，用 Set 防重复入队。
- **原理**：实测（`platform-lab/build.cjs`）——依赖图 a→b/c→d：改叶子 d.js 只重建 1 个、改 c.js 重建 2 个（**不包含不相关的 b**）、改底层 a.js 全脏 4 个。
- **边界**：菱形依赖会让同一节点被访问多次，必须去重；反向图要持久化并增量更新，每次重算在大仓里本身就是开销。依赖图粒度也有取舍——按文件是主流，太粗过度重建、太细维护失控。
- **追问**：增量构建和远程缓存是什么关系？→ 前者决定「本次要建哪些」，后者决定「这些能不能直接拿来用」；两者叠加才把 CI 时长压下去。

### Q3: 线上报 `app.js:150`，怎么定位到源码？（第 1 篇）

- **结论**：两层配合——**manifest** 管版本与粗定位（哪个版本有哪些源文件、各占多少行），**sourcemap**（VLQ 编码）管行列级映射。
- **原理**：实测（`platform-lab/build.cjs`）——`app.8f3c.js:150` → `src/cart.js:31`；越界行号与查不到的 bundle 都返回 `null` 而不是猜一个。
- **边界**：三条守线——① sourcemap **不随产物发到公开 CDN**（等于公开源码）；② 版本按产物 hash 一一对应，map 丢了就只能定位到压缩代码；③ **构建要可复现**，否则溯源链路会错位。
- **追问**：平台该不该把项目的构建脚本翻译成自己的 DSL？→ 不该。应该复用同一份脚本跑在本地和 CI，分叉之后「本地能跑、平台跑不了」会成为常态且极难排查。

### Q4: AB 实验的分桶怎么保证稳定与均匀？（第 2 篇）

- **结论**：`hash(userId + ':' + salt) % n`，**可重算、不能用随机数**；盐里必须带实验名。
- **原理**：实测（`platform-lab/ab.cjs`）——同一用户连续 100 次分桶结果恒定；1 万用户落实验组 49.87%（偏差 < 2%）。不带盐的话所有实验对同一用户的分桶完全一致，实验之间产生系统性相关。
- **边界**：**用什么 ID 分桶决定了实验单位**——用设备 ID 是按设备、用账号 ID 才是按人；选错是隐性且致命的（同一个人在手机和电脑上看到不同版本）。
- **追问**：能用 `Math.random()` 吗？→ 绝对不能，用户刷新一次就换组，体验割裂且数据作废。

### Q5: 多个实验同时跑，怎么避免互相污染？（第 2 篇）

- **结论**：分层——**同层互斥**（一个人只进一个实验），**跨层不同盐 → 正交**。
- **原理**：实测（`platform-lab/ab.cjs`）——UI 层与排序层各自分桶，四种命中组合均匀分布在四格，最大偏差 0.53%。
- **边界**：正交只保证**分配独立**，不保证**效果可加**。一个改按钮颜色、一个改推荐排序，叠加效果可能不是简单相加，所以核心指标要在「只中 A / 只中 B / 都中」三群里分别看。
- **追问**：层不够用了怎么办？→ 加层或把互斥实验排进同一层的流量轮转；但层数越多，单层可用流量越少，样本量压力越大。

## 三、排障与选型

### Q6: 实验跑到一半发现两组人数是 5200/4800，能继续看指标吗？（第 2 篇）

- **结论**：不能。这是 SRM（样本比例失衡），说明分流或埋点坏了，**结论一律作废**。
- **原理**：实测（`platform-lab/ab.cjs`）——卡方检验：4980/5020 得 0.16（< 3.84 通过），5200/4800 得 16.00（> 3.84 判失衡）。
- **边界**：成因按频率排序是**埋点丢失**（某组 SDK 上报被拦截）> 分流时机不一致 > 跳转丢参 > 机器人流量。SRM 检查必须做成平台**自动巡检**，不能等人看报表。
- **追问**：为什么不能"先看看指标，万一结论明显呢"？→ 失衡意味着两组人群本身不可比（可能是某类用户根本没被记进来），任何差异都可能来自这个偏差而非实验效果。

### Q7: 转化率从 5.0% 涨到 5.4%，能上线吗？（第 2 篇）

- **结论**：看样本量，不看提升幅度。两比例 z 检验，临界值 1.96。
- **原理**：实测（`platform-lab/ab.cjs`）——**同样的 8% 提升**，每组 2 万样本时 z=1.80 **不显著**；每组 5 万样本时 z=2.85 **显著**。
- **边界**：三条纪律——① 实验前先按 MDE 算样本量，不够就别开；② **禁止中途偷看**（每天看一次、显著就停，会把假阳性率从 5% 抬到 20%+）；③ 样本足够大时 0.1% 提升也能"显著"，但**统计显著 ≠ 值得上线**，还要看置信区间与收益量级。
- **追问**：想连续监测怎么办？→ 用序贯检验/贝叶斯方法（专门允许连续看），或者在实验设计阶段就定好固定周期与停止规则。

## 四、场景设计题

### Q8: 老板要"提升研发效能"，该从哪下手？（第 3 篇）

- **结论**：先算 DORA 四指标（部署频率、变更前置时间、变更失败率、MTTR），再**把交付周期拆段**找瓶颈，而不是直接"让大家写快点"。
- **原理**：实测（`platform-lab/metrics.cjs`）——一个 PR 从创建到上线 72h 里，编码只占 **6%**（4h），等待占 **86%**（62h：评审排队 60h + 发布窗口 2h）。编码效率翻倍，端到端收益也只有约 3%。
- **边界**：口径三条——用**中位数**不用平均值（一次卡两周的发布会把均值拉飞）；四个指标**一起看**（单看部署频率，团队会用质量换速度）；跨行业比意义有限，跟自己历史比更有价值。
- **追问**：能不能用代码行数或部署次数考核？→ 不能。实测：一次优秀重构 LOC 300→120（−60%）但前置时间 48h→12h、故障 3→0，LOC 考核会把它判成"产出下降"；按部署次数考核个人，同样的 200 行改动拆成 10 个 PR 后指标翻 5 倍——古德哈特定律：**指标一旦成为目标，就不再是好指标**。正确做法是度量团队、多指标交叉验证、只用于找瓶颈不用于排名。
