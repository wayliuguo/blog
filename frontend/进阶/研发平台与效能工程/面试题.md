# 模块面试题 · 研发平台与效能工程

## 1. 构建平台与产物治理

### Q1（1.1）｜ 构建缓存的键为什么不能用文件修改时间？

- **判断**：缓存键必须完全由**输入内容**决定（源码 hash + 依赖版本 + 构建参数 + 工具链版本），mtime 是纯噪声。
- **展开**：mtime 描述"文件何时被写"，与内容是否变化无关；内容一字未改只戳 mtime，hash 缓存 **0 重建**、mtime 缓存 **3 个全重建**。云端构建每次都是全新 checkout，所有文件 mtime 都是"刚刚"，用 mtime 等于缓存永远失效。
- **佐证**：

```
内容一字未改，只把 mtime 从 1000 改成 2000
  hash 缓存    0 重建
  mtime 缓存   3 个全重建
```

- **边界**：最容易漏的是**工具链版本**（Node、打包器）——不入键则升级后旧缓存照样命中、产出旧工具链产物，常几周后才以奇怪方式暴露。追问：构建参数为什么也要入键？→ 同一份源码 dev/prod 产出完全不同，参数不入键会拿到错误模式的产物。

### Q2（1.2）｜ 改一个文件，怎么算出该重建哪些产物？

- **判断**：从被改文件出发，沿**反向依赖边**传播脏标记，用 Set 防重复入队。
- **展开**：依赖图 a→b/c→d：改叶子 d.js 只重建 1 个、改 c.js 重建 2 个（**不包含不相关的 b**）、改底层 a.js 全脏 4 个。`dirty` 用 Set 收集，菱形依赖下同一节点不会被重复处理。
- **佐证**：

```
依赖图  a → b / c → d
  改叶子 d   重建 1 个
  改     c   重建 2 个
  改底层 a   全脏 4 个
```

- **边界**：反向图要持久化并增量更新，每次重算在大仓里本身就是开销；图粒度按文件是主流，太粗过度重建、太细维护失控。追问：增量构建与远程缓存的关系？→ 前者决定「本次要建哪些」，后者决定「这些能不能直接拿来用」；两者叠加才把 CI 时长压下去。

### Q3（1.3）｜ 线上报 `app.js:150`，怎么定位到源码？

- **判断**：两层配合——**manifest** 管版本与粗定位（哪个版本有哪些源文件、各占多少行），**sourcemap**（VLQ 编码）管行列级映射。
- **展开**：实测 `app.8f3c.js:150` → `src/cart.js:31`；越界行号与查不到的 bundle 都返回 `null` 而不是猜一个。守线三条——① sourcemap **不随产物发到公开 CDN**（等于公开源码）；② 版本按产物 hash 一一对应，map 丢了就只能定位到压缩代码；③ **构建要可复现**，否则溯源链路会错位。
- **佐证**：

```
app.8f3c.js:150  →  src/cart.js:31
越界行号 / 查不到 bundle  →  返回 null
```

- **边界**：追问：平台该不该把项目的构建脚本翻译成自己的 DSL？→ 不该，应复用同一份脚本跑在本地和 CI，分叉之后「本地能跑、平台跑不了」会成为常态且极难排查。

## 2. 实验与增长平台

### Q4（2.1）｜ AB 实验的分桶怎么保证稳定与均匀？

- **判断**：`hash(userId + ':' + salt) % n`，**可重算、不能用随机数**；盐里必须带实验名。
- **展开**：分桶要同时满足稳定（同一用户任何时刻都进同一组）与均匀（各组人数接近）。实测同一用户连续 100 次分桶结果恒定；1 万用户落实验组 49.87%（偏差 < 2%）。不带盐则所有实验对同一用户的分桶完全一致，实验之间产生系统性相关。
- **佐证**：

```
同一用户 100 次分桶结果恒定
1 万用户落实验组 49.87%（偏差 < 2%）
```

- **边界**：**用什么 ID 分桶决定实验单位**——设备 ID 是按设备、账号 ID 才是按人，选错隐性且致命（同一个人手机和电脑看到不同版本）。追问：能用 `Math.random()` 吗？→ 绝对不能，用户刷新一次就换组，体验割裂且数据作废。

### Q5（2.2）｜ 多个实验同时跑，怎么避免互相污染？

- **判断**：分层——**同层互斥**（一个人只进一个实验），**跨层不同盐 → 正交**。
- **展开**：UI 层与排序层各自分桶，四种命中组合均匀分布在四格（实测最大偏差 0.53%）。但**正交只保证分配独立，不保证效果可加**——改按钮颜色与改推荐排序的叠加效果未必是简单相加。
- **佐证**：

```
UI 层 / 排序层不同盐，四格命中组合各约 25%，最大偏差 0.53%
```

- **边界**：核心指标要在「只中 A / 只中 B / 都中」三群里分别看。追问：层不够用了怎么办？→ 加层或把互斥实验排进同一层的流量轮转；但层数越多、单层可用流量越少，样本量压力越大。

### Q6（2.3）｜ 实验中途发现两组人数是 5200/4800，能继续看指标吗？

- **判断**：不能。这是 SRM（样本比例失衡），说明分流或埋点坏了，**结论一律作废**。
- **展开**：用卡方检验判失衡：4980/5020 得 0.16（< 3.84 通过）、5200/4800 得 16.00（> 3.84 判失衡）。成因按频率排序是**埋点丢失**（某组 SDK 上报被拦截）> 分流时机不一致 > 跳转丢参 > 机器人流量；SRM 检查必须做成平台**自动巡检**，不能等人看报表。
- **佐证**：

```
卡方检验（临界值 3.84）
  4980 / 5020   卡方 0.16   通过
  5200 / 4800   卡方 16.00  失衡
```

- **边界**：追问：为什么不能"先看看指标，万一结论明显呢"？→ 失衡意味两组人群本身不可比（可能某类用户根本没被记进来），任何差异都可能来自这个偏差而非实验效果。

### Q7（2.4）｜ 转化率从 5.0% 涨到 5.4%，能上线吗？

- **判断**：看**样本量**，不看提升幅度。两比例 z 检验，临界值 1.96。
- **展开**：**同样的 8% 提升**，每组 2 万样本时 z=1.80 **不显著**、每组 5 万样本时 z=2.85 **显著**——样本量决定结论。统计显著 ≠ 值得上线，样本足够大时 0.1% 提升也能"显著"，还要看置信区间与收益量级。
- **佐证**：

```
同样的 8% 提升（5.0% → 5.4%）
  每组 2 万样本   z=1.80   不显著
  每组 5 万样本   z=2.85   显著
```

- **边界**：三条纪律——实验前按 MDE 算样本量、禁止中途偷看（每天看一次显著就停，会把假阳性率从 5% 抬到 20%+）、显著不等于值得上线。追问：想连续监测怎么办？→ 用序贯检验/贝叶斯方法（专门允许连续看），或在设计阶段定好固定周期与停止规则。

## 3. 研发效能度量

### Q8（3.1）｜ 老板要"提升研发效能"，该从哪下手？

- **判断**：先算 **DORA 四指标**（部署频率、变更前置时间、变更失败率、MTTR），再把**交付周期拆段**找瓶颈，而不是直接"让大家写快点"。
- **展开**：一个 PR 从创建到上线 72h 里，编码只占 **6%**（4h），等待占 **86%**（62h：评审排队 60h + 发布窗口 2h）——瓶颈不在编码速度，编码效率翻倍的端到端收益也只约 3%。口径三条：**用中位数**不用平均值、**四个指标一起看**、跨行业比意义有限（**跟自己历史比**更有价值）。
- **佐证**：

```
72h 交付周期拆段
  编码   4h（6%）
  等待   62h（86%）  评审排队 60h + 发布窗口 2h
```

- **边界**：追问：能用代码行数或部署次数考核？→ 不能。一次优秀重构 LOC 300→120（−60%）但前置时间 48h→12h、故障 3→0，LOC 考核会判"产出下降"；同样 200 行改动拆成 10 个 PR 按部署次数考核指标翻 5 倍——古德哈特定律：**指标一旦成为目标，就不再是好指标**。正确做法是度量团队、多指标交叉验证、只用于找瓶颈不用于排名。
