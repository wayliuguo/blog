# 研发效能度量

「我们的研发效能怎么样」是个很难回答的问题——难不在于没数据，而在于**大部分能轻易拿到的数据都是错的**：代码行数、提交次数、故事点、加班时长。这一篇用 `platform-lab` 的 `metrics.cjs` 说明真正被大规模研究验证过的四个指标（DORA）怎么算、交付周期该怎么拆、以及哪些度量一旦用来考核就会立刻失真。

## 一、DORA 四指标：四个数就够了

DORA（DevOps Research and Assessment）多年研究给出的结论是：团队效能可以由四个指标刻画，且它们互相印证。

| 指标 | 定义 | 它衡量什么 |
| --- | --- | --- |
| 部署频率 | 单位时间成功部署的次数 | 交付节奏 |
| 变更前置时间 | 代码提交到跑在生产的中位时长 | 流程效率 |
| 变更失败率 | 导致线上劣化的变更占比 | 质量 |
| 服务恢复时间（MTTR） | 故障从发生到恢复的中位时长 | 韧性 |

> 摘自 `./code/platform-lab/metrics.cjs`

```js
function dora(deploys, changes, incidents, windowDays) {
  const deployPerDay = deploys / windowDays;
  const leadHours = changes.reduce((a, c) => a + c.leadHours, 0) / changes.length;
  const failed = changes.filter(c => c.failed).length;
  const failRate = failed / changes.length;
  const mttr = incidents.length
    ? incidents.reduce((a, i) => a + i.recoverHours, 0) / incidents.length
    : 0;
  return {
    deployPerDay,
    leadHours,
    failRate,
    mttr,
    grades: {
      deployFreq: grade('deployFreq', deployPerDay, false),
      leadTime: grade('leadTime', leadHours),
      failRate: grade('failRate', failRate),
      mttr: grade('mttr', mttr),
    },
  };
}
```

实测（30 天窗口、60 次部署、12 个变更含 1 次失败、2 次故障）：部署 **2 次/天**（high）、前置 **20 小时**（elite）、失败率 **8.3%**（high，离 elite 的 ≤5% 差一档）、MTTR **1 小时**（elite）——下一步该盯的是变更失败率。

三个必须注意的口径：

1. **用中位数而不是平均值**。一次卡了两周的发布会把平均值拉飞，中位数才反映常态。
2. **四个指标要一起看**。单独把部署频率做成 KPI，团队会用「降低质量」换「提高频率」——失败率就是它的刹车。
3. **分档是相对的**。elite/high/medium/low 的分界来自行业分布，跨行业比较意义有限；**跟自己的历史比**更有价值。

## 二、交付周期：慢的不是写代码，是等待

「我们的交付太慢了」——慢在哪？不拆开就永远只能猜。把一次变更从创建到上线切成几段：

> 摘自 `./code/platform-lab/metrics.cjs`

```js
const stages = { 编码: 4, 等待评审: 60, 评审修改: 6, 等待发布: 2 };
```

实测：一个 PR 从创建到上线共 **72 小时**，其中编码 4 小时（**6%**），等待评审 60 小时、等待发布 2 小时，等待合计 **86%**。

这个比例在真实团队里非常典型，它给出两个直接结论：

- **优化编码速度毫无意义**。就算编码时间砍半（4h → 2h），总时长只从 72h 降到 70h。
- **真正的杠杆在排队**：评审响应慢（没人看 PR）、发布窗口稀缺（一天只有一次发车）。对应的改进是评审 SLA、小 PR、按需发布，而不是"写快点"。

同理，**当有人提出"引入 AI 辅助编码提升效能"时，先算一下编码在总周期里的占比**。如果它只有 6%，那么即使编码效率翻倍，端到端收益也就 3%——这不代表不该做，但它不该被当成效能的主线。

## 三、反模式：LOC 与「个人吞吐」为什么不能当指标

度量一旦变成考核目标，人们就会优化指标本身，而不是它想衡量的东西（古德哈特定律）。

> 摘自 `./code/platform-lab/metrics.cjs`

```js
  // 同一次重构：代码变少，价值变高
  const before = { loc: 300, leadHours: 48, incidents: 3 };
  const after = { loc: 120, leadHours: 12, incidents: 0 };
```

实测：一次优秀重构把 LOC 从 300 降到 120（**−60%**），同时前置时间 48h → 12h、故障 3 → 0。用代码行数考核，这次重构会被判成"产出下降 60%"。

第二种失真更隐蔽——按部署次数考核个人：

> 摘自 `./code/platform-lab/metrics.cjs`

```js
  const honest = { prs: 2, deploys: 2, loc: 200 };
  const gaming = { prs: 10, deploys: 10, loc: 200 }; // 同样的改动拆成 10 个 PR
```

实测：同样的 200 行改动，拆成 10 个 PR 后「部署次数」从 2 变成 10，指标翻 5 倍，交付的东西一模一样。

由此得到三条实践原则：

1. **度量团队，不度量个人**。团队指标难被单人操纵，也更符合「软件是集体产出」的事实。
2. **用多个指标交叉验证**。任何单一指标都能被玩坏；DORA 之所以被广泛采用，部分原因就是它的四个指标互相制约。
3. **度量只用于找瓶颈，不用于排名**。一旦排行榜出现，数据就开始失真，而你会失去唯一有价值的那一版真实数据。

另外，还有一类指标是「**不能直接采信但需要人工判断**」的：开发者满意度、认知负荷、文档质量。它们难以自动化采集，但 DORA 的研究表明它们与效能强相关——通常用定期问卷（季度）来做，而不是靠系统里的事件流。

## 小结

- **DORA 四指标**：部署频率、变更前置时间、变更失败率、MTTR；实测一例为「2 次/天 high · 20h elite · 8.3% high · 1h elite」，短板是变更失败率。
- **口径**：用中位数不用平均值；四个指标必须一起看（单指标会被用质量换速度的方式做坏）；跨行业比较意义有限，跟自己历史比更有价值。
- **周期分解**：72h 里编码只占 6%、等待占 86%——**瓶颈在评审排队与发布窗口**，不在编码速度。
- **反模式**：LOC 考核会贬低优秀重构（实测 LOC −60% 但前置时间 48h→12h、故障 3→0）；按部署次数考核个人会导致拆 PR（同样改动指标翻 5 倍）。
- **三条原则**：度量团队不度量个人、多指标交叉验证、度量只用于找瓶颈不用于排名。
