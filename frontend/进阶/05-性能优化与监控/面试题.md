## 一、性能指标与评估

### Q1: 前端性能指标有哪些？（第 01 篇）

- **结论**：FP（首帧）→ FCP（首内容）→ LCP（最大内容，体验关键）→ CLS（布局偏移）→ INP（交互延迟）。
- **原理**：LCP 衡量"页面核心内容可感知"的时间；采集用 PerformanceObserver 而非打点；INP 替代 FID 衡量交互响应。
- **边界**：指标有采集成本（观测器不阻塞，但上报链路要可控）；不同端（H5/小程序）口径不同。
- **追问**：为什么 LCP 比 FCP 更重要？→ FCP 可能只是首块文字，LCP 才代表"主要内容出现"。
- **场景**：指标要能落监控——性能页面按 LCP/CLS/INP 建看板，优化围绕 LCP 展开。

### Q2: `performance.now()` 与 `Date.now()` 的区别？（第 01 篇）

- **结论**：`performance.now()` 是相对导航开始的高精度时间戳（微秒级、单调递增），`Date.now()` 是系统时钟（毫秒、可被修改）。
- **原理**：`performance.now()` 基于高分辨率时间源，单调递增不受系统时间修改影响，适合测执行耗时；`Date.now()` 返回距 1970 的毫秒数，受 NTP 校准/手动改时影响。
- **边界**：性能测量用 `performance.now()`；业务时间戳/日志仍用 `Date`。
- **追问**：为什么测耗时不用 Date.now()？→ 系统时间可能被改，前后差值失真。
- **场景**：埋点里测接口耗时、函数执行时间都用 `performance.now()` 起止差值。

## 二、性能优化实践

### Q3: 首屏优化的三层手段？（第 02 篇）

- **结论**：关键路径（并行化）+ 阻塞（非关键兜底）+ 网络（预取 + 降级），三层一起做。
- **原理**：并行化减少关键路径长度；兜底与增量更新减少阻塞时间；预取省一次网络往返。
- **边界**：比"请求本身更快"更可控的是减少等待与阻塞。
- **追问**：首屏接口哪些必须串行？→ 下游接口依赖上游返回值的才串行，其余并发。
- **场景**：简历项目接口串行改并行（1 个前置依赖 + 4 个并行）；运营位失败按空对象兜底不阻塞首屏；App 预取 + 500ms 超时降级。

### Q4: 打包体积怎么降？（第 02 篇）

- **结论**：按需引入 + manualChunks 分层 + tree-shaking + 压缩，四管齐下。
- **原理**：按需引入（组件库/工具库按模块引）避免整包；分包按变更频率分层吃满浏览器缓存；tree-shaking 剔除未用导出；压缩（JS/CSS/图片）降低传输体积。
- **边界**：降体积要与请求数权衡（切太细反增 HTTP 开销）；无 A/B 度量前不报量化数字。
- **追问**：怎么分析产物？→ rollup-plugin-visualizer 看各 chunk 构成，先打最大头。
- **场景**：首包从全量降到核心业务；图片压缩 + 路由懒加载，产物分析工具定位大块依赖。

### Q5: 图片懒加载怎么实现？（第 02 篇）

- **结论**：核心是"按需加载"——滚动进入可视区才加载真实资源，用 IntersectionObserver 而非 scroll 计算。
- **原理**：IntersectionObserver 监听元素进入视口（isIntersecting）再填充 `src`；原生 `loading="lazy"` 零成本兜底；占位高度避免布局抖动（CLS）。
- **边界**：首屏图片不懒加载（反优化）；观察器要 `disconnect` 防泄漏；低版本浏览器需 polyfill。
- **追问**：为什么不用 scroll 监听？→ scroll 高频触发反复计算，IntersectionObserver 异步批量回调更省。
- **场景**：长列表图片/运营位用懒加载，滚动不卡、流量省、首屏不被非首屏图片拖慢。

### Q6: 长列表性能（虚拟滚动）？（第 02 篇）

- **结论**：虚拟滚动只渲染可视区附近的少量元素，用"占位撑高 + 定位偏移"模拟完整滚动条，是长列表的事实标准。
- **原理**：固定高度实现简单高效（按 index 换算偏移）；动态高度更精准但需收集高度映射；前后置缓冲多渲染上下两屏防快速滚动白屏。
- **边界**：虚拟滚动牺牲"全部 DOM 可检索"（Ctrl+F/滚动条长度失真）；数据量小（几百条）不必上。
- **追问**：怎么保证滚动不白屏？→ 前后缓冲屏 + 稳定 key 复用节点。
- **场景**：万级借款记录/消息列表用虚拟滚动，DOM 从万级降到几十级，滚动帧率稳定。

### Q7: 预取（App 端能力）与超时降级？（第 02 篇）

- **结论**：预取是"用户还没进页面、数据已到"的体验优化；必须有超时降级，否则失败反而拖慢首屏。
- **原理**：App 壳在页面跳转前预取接口数据缓存；前端设超时（如 500ms）——缓存命中直接用、超时走正常请求；降级保证"预取失败 = 没预取"，不阻塞。
- **边界**：预取命中率要监控，否则白做；预取数据要防串页（页面 key 校验）。
- **追问**：预取失败会怎样？→ 超时降级走真实接口，用户无感。
- **场景**：H5 在 App 内跳转秒开——预取借款额度，500ms 超时降级，运营位失败按空对象兜底。

## 三、异常与监控

### Q8: 白屏是什么？可能原因？（第 03 篇）

- **结论**：白屏 = 页面完全空白、无任何可交互内容；根因通常是 JS 错误中断渲染、资源加载失败、初始化流程未走完。
- **原理**：SPA 依赖 JS 挂载，脚本执行前或执行出错即白屏；CSS/JS 资源 404 或跨域被拦也白屏；监控要在初始化早期注入才能捕获。
- **边界**：白屏要区分"加载中"与"真白屏"——用页面级埋点（LOAD.ERROR）定时判定。
- **追问**：白屏怎么先让错误可见？→ 监控脚本早于 polyfills、捕获阶段监听资源错误。
- **场景**：iOS 容器多页跳转后白屏，靠资源错误上报定位到 modulePreload 预加载失败。

### Q9: 监控埋点分哪几层？（第 03 篇）

- **结论**：页面级（LOAD.*）/ 曝光级（SHOW.*）/ 交互级（CLICK.*）/ 结果级（*_SUC/_FAIL）四层。
- **原理**：页面级管访问与性能；曝光级管元素可见；交互级管点击行为；结果级管业务闭环成败；每层独立成事件、共用口径。
- **边界**：埋点遗漏必然发生——靠"埋点清单随方案生成"兜底，新增分支必须补埋点。
- **追问**：埋点怎么防遗漏？→ 埋点清单随方案生成（沉淀为模板），CR 时核对新增分支。
- **场景**：借款流程 LOAD 页面 → SHOW 试算区 → CLICK 提交 → SUBMIT_SUC/FAIL 结果，一条漏斗串起来。

### Q10: 异常监控五维是什么？（第 03 篇）

- **结论**：JS 错误率 · 白屏 · 资源加载失败 · 接口成功率与耗时 · 初始化流程健康度。
- **原理**：白屏直接工具是 LOAD.ERROR（页面级埋点）；资源错误必须捕获阶段监听（error 事件不冒泡）；监控脚本要早于 polyfills 执行。
- **边界**：只监控不定位 = 白搭；要能串到"哪个页面/接口/版本"。
- **追问**：错误分级有什么价值？→ network-error 找运维/网关，logic-error 找前端，避免互相甩锅。
- **场景**：简历项目覆盖五维 + 错误分级（network-error / logic-error）——分级决定谁来看。

### Q11: 白屏怎么用数据定位（而不是猜）？（第 03 篇）

- **结论**：先让错误可见（早期注入监控）→ 用数据定位（资源加载错误）→ 最小改动修复并注释留痕。
- **原理**：iOS 容器多页跳转后白屏，靠捕获阶段资源错误上报定位到 modulePreload 预加载失败且无降级。
- **边界**：预取降级与真实接口失败要在监控上分开，否则误判问题域。
- **追问**：为什么资源错误要用捕获阶段？→ error 事件在资源加载失败时不冒泡，只有捕获阶段能监听到。
- **场景**：修复 = 关闭 `modulePreload` + 配置处写明原因注释（防止后人"优化"改回去）。

## 四、指标与告警工程

### Q12: 双视角指标设计？（第 04 篇）

- **结论**：产品视角看漏斗（进入→试算→提交→授信逐段转化），研发视角看接口（成功率/耗时/健康度），共用同一套埋点口径。
- **原理**：同一份埋点事件派生两套视图——字段命名与口径一致，否则两套账对不上。
- **边界**：口径必须双视角同源，这是设计的关键不是实现细节。
- **追问**：埋点遗漏怎么防？→ 埋点清单随方案生成（模板沉淀），新增分支必须补埋点。
- **场景**：`report_serial_num` 把前后端埋点串成一条链路；页面级（LOAD.*）/ 曝光级（SHOW.*）/ 交互级（CLICK.*）/ 结果级（*_SUC/_FAIL）。

### Q13: 告警阈值怎么设才不是拍脑袋？（第 04 篇）

- **结论**：基线（近 N 天分位数）+ 波动容忍 + 量与率同时看。
- **原理**：只看率被小样本放大；只看量漏掉转化率下滑；阈值随基线滚动，不是固定数字。
- **边界**：阈值不是拍脑袋，要随基线滚动；告警太多会麻木（告警疲劳）。
- **追问**：告警与发版怎么联动？→ 版本维度对齐，发版后指标异常优先查本次改动。
- **场景**：告警图把"哪个接口/页面/版本"对齐到一张图，直接指向问题域。

### Q14: 天表与实时表的分工？（第 04 篇）

- **结论**：实时表管"当下是否出问题"（秒级/分钟级、明细小窗口），天表管"趋势与对账"（离线聚合、全量留存）。
- **原理**：实时表写入高频、保留短，供告警与即时排查；天表每日聚合归档，供周报/趋势/双视角报表；两条链路共用同一埋点口径。
- **边界**：实时表成本高，不能全量长存；趋势分析要天表，实时查明细要实时表。
- **追问**：两张表口径不一致怎么办？→ 埋点字段与聚合口径同源，天表由实时明细归档派生。
- **场景**：白屏率告警走实时表（分钟级），月度趋势与漏斗分析走天表。

## 五、场景实战

### Q15: 场景：线上反馈某页面白屏率上升，本地无法复现，怎么排查？（第 03 篇）

- **结论**：先确认监控是否覆盖 → 按维度切片 → 区分预取降级与真实失败 → 定位到具体资源/接口 → 修复 + 回归 + 埋点验证。
- **原理**：① 确认 LOAD.ERROR / 资源加载错误 / JS 错误率是否在监控内；② 按版本/机型/接口维度切片；③ 区分"预取超时降级"与"真实接口失败"；④ 查初始化流程是否中断（polyfill 前错误需最早注入的监控）；⑤ 定位资源/接口 → 修复 + 回归 + 埋点验证。
- **边界**：监控没覆盖的维度只能靠用户反馈补——先补监控再修问题。
- **追问**：怎么确认是不是预取导致？→ 监控里把预取降级与真实失败分开打点，看白屏是否集中在预取路径。
- **场景**：iOS modulePreload case——捕获阶段资源错误定位到预加载失败，关闭 `modulePreload` + 注释留痕，回归验证白屏率下降。

### Q16: 图片优化有哪些手段？（第 02 篇）

- **结论**：格式选对 + 体积压缩 + 加载策略（懒加载/预载/占位）+ 缓存，四路并进。
- **原理**：格式——图标用 SVG/雪碧图、照片用 JPEG/WebP（按请求头 `Accept` 判断支持，CDN 可自动转 WebP）；体积——压缩与响应式尺寸（srcset）；加载——懒加载（进视口才加载）、`preload` 预载 LCP 关键图；缓存——不可变 hash 长缓存；布局——固定宽高占位防 CLS。
- **边界**：HTTP/2 及以上不建议再用雪碧图（多路复用已降低请求开销）；WebP 不支持的环境要降级回退。
- **追问**：怎么判断浏览器支持 WebP？→ 看请求头 `Accept` 是否含 `image/webp`，或用 canvas `toDataURL('image/webp')` 探测。
- **场景**：首屏 hero 图用 WebP + `preload` + 固定宽高占位，LCP 与 CLS 双双下降。
