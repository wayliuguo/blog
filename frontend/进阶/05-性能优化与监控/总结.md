# 模块总结 · 性能优化与监控

## 知识主线

四篇不是并列的知识点，而是一条有依赖关系的链，每一篇都在回答上一篇留下的问题：

```
01 性能指标与评估（衡量什么：Core Web Vitals / 辅助指标 / 测量原理 / Lab·Field·RUM） ★主轴
        │  先定下"多快才算快"的标尺，后面优化与监控才都有判据
        ▼
02 性能优化实践（怎么优化：加载 / 运行时 / 分割 / 缓存 / 虚拟滚动 / 资源提示）
        │  它在回答上一篇的什么问题：指标测得慢，具体该改哪里、怎么改
        ▼
03 监控平台（怎么持续看见：错误监控 / 性能采集 / 埋点 / 告警）
        │  它在回答上一篇的什么问题：优化上线后，线上到底好不好、有没有出错
        ▼
04 企业级性能与监控工程实践（怎么焊成工程：Agent SDK → 秒桶聚合 → 分位值 → 告警基线）
        │  它在回答上一篇的什么问题：单点能力都有，怎么落成一条能进生产的闭环
```

本模块的主轴是**性能指标**：01 定下"衡量什么、多快算快"的标尺（LCP / INP / CLS 与 TTFB / FCP / TBT 等），02 的每一种优化都以指标为判据，03 把指标与错误持续采回来看线上真实情况，04 把指标聚合成报表与告警做闭环回归。整章就是围绕"指标"这条线，走完"先测量、再优化、后回归"的完整闭环。

## 分篇知识点

### 01-性能指标与评估

- **三大 Core Web Vitals**：LCP（加载，最大内容元素渲染完成，≤2.5s）、INP（交互，生命周期内代表性交互延迟，≤200ms，正在取代只反映首次输入的 FID）、CLS（稳定，意外布局偏移总分 = 位移距离 × 影响比例，≤0.1）
- **辅助指标沿时间轴排布**：TTFB（≤800ms）→ FP → FCP（≤1.8s）→ TBT（FCP→TTI 间长任务超 50ms 部分之和，≤200ms）→ TTI → LCP，另有 SI（可见内容填充速度，≤3.4s）
- **测量原理**：`performance` 是浏览器写入的只读缓冲区——`getEntriesByType()` 读历史条目，`PerformanceObserver` 异步订阅新条目（`largest-contentful-paint` / `layout-shift` / `longtask` / `paint`），`mark`/`measure` 手动打点
- **工具三分工**：Lighthouse 做受控环境基准审计（Lab，可复现可对比），Chrome Performance 面板看火焰图定位主线程热点，RUM 反映真实用户（Field，样本噪声大）
- **RAIL 模型**：以用户为中心排优化优先级——Response 输入响应 <100ms、Animation 每帧 <16ms（60fps）、Idle 主线程空闲 >50ms、Load 首屏 <5s
- **采集与上报**：短时指标（FCP/TTFB）load 后上报，长时指标（LCP/CLS/INP）在 `visibilitychange → hidden` 取最终值；上报用 `sendBeacon` / `fetch keepalive` 批处理 + 采样率控制 + 附带上下文（网络类型/设备/版本）

### 02-性能优化实践

- **五步流程与四个层面**：明确指标 → 量化评估 → 定位原因 → 实施优化 → 迭代回归；"性能"= 减少加载时间、尽快可用、平滑交互、感知表现、持续测定
- **加载性能**：懒加载按需加载（滚动 + getBoundingClientRect 兼容好，IntersectionObserver 性能优，Vue 指令封装"收集监听 → 进可视区才替换 src"）；图片用样式代替、WebP/SVG 选型、HTTP/2 后弃雪碧图、Base64 需权衡；大文件切片上传 + SparkMD5 HASH 断点续传 + 合并接口
- **运行时性能**：长任务 >50ms 阻塞交互——把任务拆成 <50ms 片段、rAF 错峰、Web Worker 移出主线程、动画用 `transform`/`opacity` 走合成器；警惕六类内存泄漏（全局变量/闭包/定时器/循环引用/未解绑事件/未清理 DOM 引用）
- **虚拟滚动**：占位撑高 + 只渲染可视区；固定高度用 `translate3d` 偏移，动态高度收集 `id→height` 映射、平均高度撑滚动条 + 二分查找定位下标
- **代码分割与缓存**：路由/组件懒加载 + Tree Shaking + 第三方按需引入；强缓存（Expires/Cache-Control，命中不发请求）与协商缓存（ETag/Last-Modified，命中返回 304）两级命中，配 CDN 加速与 gzip 压缩
- **关键路径与资源提示**：CSS 放 `<head>` 避免 FOUC、JS 放底部或 `async`/`defer`、减少回流重绘、为高构图预留空间降 CLS；`preload` 本页关键资源、`prefetch` 后续导航、`preconnect`/`dns-prefetch` 提前建立跨域连接

### 03-监控平台

- **监控三大目标**：稳定性（JS 错误、资源异常、接口错误、白屏）、用户体验（TTFB/FP/FCP/FMP/FID/卡顿）、业务（PV/UV/页面停留时长）
- **七步闭环流程**：目标设定 → 数据采集 → 数据传输 → 存储处理 → 分析与可视化 → 告警预警 → 定位优化
- **错误收集四种方式**：`try/catch` 手动捕获（信息最全但侵入业务）、`window.onerror`（未被包裹的运行时错误）、`unhandledrejection`（Promise 异常兜底）、捕获阶段监听资源 `error`（`addEventListener('error', fn, true)`，资源错误不冒泡）；另有框架专项机制（Vue `errorHandler`/`errorCaptured`）
- **上报三方案**：手动上报（可控、侵入）、自动上报（全局监听兜底，不侵入）、1×1 gif 图片打点（防跨域、不带 Cookie、不阻塞页面加载、体积最小最轻量）
- **性能采集**：`navigation` 条目时间戳差算出 DNS/TCP/SSL/TTFB/传输耗时；`PerformanceObserver` 监听 `paint`/`layout-shift`/`longtask` 拿 FP/FCP/CLS 与卡顿统计
- **埋点与告警**：用户标识 + 环境信息 + 页面地址 + 行为信息（事件类型/元素/时间戳/参数）统一采集，出 PV/UV/漏斗等报表；告警要分级（按严重度配渠道与时效）、阈值合理（结合历史基线）、去重抑制、溯源到人

### 04-企业级性能与监控工程实践

- **工程闭环四段**：前端 Agent（采集/传输/治理）→ 传输层（`sendBeacon`/`fetch keepalive`，轻量不丢）→ 接收端聚合（秒桶 + 分位值 + 去重 + 阈值/基线）→ 决策端（报表/告警/趋势）
- **Agent 做成可复用 SDK**：采集层定义"报什么"（性能/接口延迟/错误/行为），传输层"轻量 + 不丢"，治理层采样（热门页 5%–10%）、脱敏（URL query 密钥、token、userAgent 截断）、频控（按 message+文件+行号聚合，同一错误一段时间只报一次）
- **秒桶聚合**：按 1 秒一个桶累加 `count / totalLatency / errCount / fpSum / lcpSum` 并存延迟样本，把海量离散上报变成可决策指标
- **分位值才是体感**：平均延迟（avg）被少数慢请求拉偏，P95/P99 代表"绝大多数用户"的体验；demo 对每秒样本算 P95、再对最近 60 秒二次聚合
- **告警"准"的三要素**：阈值（demo 基线：P95 >120ms、错误率 >1% 触发）、去重防告警轰炸、动态基线比固定阈值更抗业务起伏
- **决策端与闭环回归**：`monitor.html` 每 2s 轮询 `/api/report`——KPI 卡超阈标红、avg/P95 曲线叠加阈值线、告警流可溯源复现；优化不以"感觉快了"为止，而以"指标回归到阈值内"为准
