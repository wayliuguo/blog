# 模块面试题 · 微前端体系

> 体例：判断（一句话结论）→ 展开（原理）→ 边界（适用范围与追问）。带实测的题目引用 `mf-workspace` 的浏览器端到端读数。

## 1. 方案全景与选型

### Q1（1.1）｜ 什么样的团队 / 系统才需要微前端？

- **判断**：只有「多团队 × 多技术栈 × 独立发布」三个条件**同时出现**才值得上微前端；它解决的是组织架构问题，不是代码量问题。
- **展开**：每一条收益（独立发布、技术栈共存、按域划责）都对应一个团队协作痛点；仅"代码多"用模块化 + 代码分割即可。代价五笔：容器基建复杂度上移、公共依赖重复打包、样式/全局一致性变难、跨应用调试链路变长、协议升级的兼容矩阵。
- **边界**：团队只有一两个人时这些全是纯开销。可追问：渐进迁移怎么走？→ 新功能用子应用承载、老代码按域外迁，qiankun 官方路径即此。

### Q2（1.2/1.3）｜ 五种微前端方案（iframe/qiankun/micro-app/wujie/Web Components）怎么选？

- **判断**：彻底防串选 iframe，改造成本最低选 micro-app/wujie，长期标准化选 Web Components，生态成熟度选 qiankun。
- **展开**：iframe 零改造但体验差（整页刷新、弹窗三面墙）；qiankun 靠生命周期协议换性能，但子应用必须导出 UMD + bootstrap/mount/unmount；micro-app 用 `<micro-app>` 标签接入、零协议（元素生命周期接管时序）；wujie 用"真 iframe 跑 JS + shadow DOM 渲染"兼得隔离与体验；WC 方案零运行时但无 JS 隔离、共享全靠约定。
- **边界**：配套统一工程 mf-workspace 把五方案跑在同一业务流上实测：五方案业务闭环全通、通信四方案联动全通（iframe 走 postMessage+src 转发）。可追问：五方案通信语义差异？→ 全部同构（下行 props、上行事件），差异只在载体。

## 2. iframe 方案

### Q3（2.2）｜ iframe 方案里 postMessage 的工程要点？

- **判断**：postMessage 不是"调 API"而是"设计协议"——格式、方向、时序、校验四件事都要自己定。
- **展开**：上行用 postMessage（列表 → 宿主 `{type:'order-select', orderId}`）；下行传参用 **URL 重载**最可靠——postMessage 发给"还没加载完"的 iframe 会丢消息（监听器未就绪），URL + 重载无时序问题但代价是整页刷新；要免刷新就得做"就绪握手"（子应用 ready 后回消息，宿主再发数据）。
- **边界**：origin 校验是底线——收方校验 `e.origin`，发方指定目标 origin，教学代码里的 `'*'` 生产必改。可追问：为什么 iframe 联动是整页刷新？→ 每个 iframe 是完整文档（重新解析 HTML + 执行全部 JS），内存约为同文档方案 2~4 倍，这也是 qiankun 系方案存在的理由。

### Q4（2.3）｜ iframe 方案"处处是墙"具体指什么？

- **判断**：三面墙——弹窗遮罩困在 iframe 视口、路由状态不进宿主地址栏、跨源不共享 Cookie/localStorage。
- **展开**：弹窗 `position:fixed` 只盖住 iframe，盖不住宿主导航与兄弟 iframe（解法是"弹窗请求 postMessage 给宿主代渲染"，状态回传又是一个协议）；子应用内部跳转刷新即丢（要双向路由同步）；登录态要 URL 传递（泄漏风险）或 postMessage 握手。
- **边界**：wujie 意外地解决了第一面墙——它把子应用的 `document.body` 代理到宿主文档，弹窗天然盖满页面。可追问：那为什么还有团队选纯 iframe？→ 安全边界：子应用不可信（三方/遗留系统）时，结构性隔离不可替代。

## 3. qiankun

### Q5（3.1/3.2）｜ qiankun 的生命周期协议和 import-html-entry 加载链路？

- **判断**：协议三函数（bootstrap 一次 / mount 每次挂容器 / unmount 清理）+ 加载五步（fetch html → 摘 script/link → CSS 注入 → JS eval 执行 → 从 exports 找生命周期）。
- **展开**：加载链路解释了两个工程约束——子应用必须 **UMD**（ESM 静态 import 无法在运行时重定向进沙箱）；entry html 内脚本同步串行解析（动态 import 的 chunk 在运行时拉）。mount 时 props 注入 `container/setGlobalState/onGlobalStateChange`。
- **边界**：loadMicroApp 手动加载 vs registerMicroApps 路由激活：前者直观可控、适合先学，后者路由驱动自动 mount/unmount。可追问：手写最小版多长？→ `fetch html → fetch js → new Function 执行 → 找三函数 → 调用`，20 行主干（qiankun.md 4）。

### Q6（3.5）｜ React 子应用接 qiankun 报 "can't detect preamble" 怎么回事？

- **判断**：`@vitejs/plugin-react` 给每个组件模块头部插了"检查 HMR 垫片"的代码，qiankun 沙箱的 eval 环境不满足检查条件——**React 子应用的 qiankun 接线必须走生产产物**，dev server 直连只适用于 Vue 子应用（配 vite-plugin-qiankun useDevMode）。
- **展开**：mf-workspace 实测复现：react-sub dev 接入时报 `Error: @vitejs/plugin-react can't detect preamble. Something is wrong.`，切到 `build:qk` UMD 产物后浏览器端到端 PASS。这也是"子应用产物矩阵"（dev/UMD/元素三形态）存在的现实原因。
- **边界**：Vue 子应用 dev 直连可用的原因是 vue 的 HMR 不做同样的 preamble 硬检查。可追问：生产怎么接？→ UMD 产物 + import-html-entry，dev 只是联调便利。

### Q7（3.5）｜ qiankun 沙箱里报 `process is not defined`，两层修法是什么？

- **判断**：构建层在子应用产物上 `define: { 'process.env.NODE_ENV': '"production"' }` 治本；宿主入口垫片 `window.process = { env: {...} }` 兜底（qiankun 官方 FAQ 方案）。
- **展开**：Vue/React 运行时产物里有 dev 判断 `process.env.NODE_ENV`，浏览器和 qiankun 沙箱都没有 `process` 全局。lib 构建不自动替换依赖内的 process 引用（mf-workspace 实测：产物里 220 处 `process.env.NODE_ENV`），必须在构建配置显式 define。
- **边界**：垫片必须有——生产环境总有你改不了的第三方子应用产物。可追问：为什么 WujieMicro 前端微服务等也常见？→ 同源问题：所有 Proxy 沙箱方案都是 eval 环境执行，`process` 缺失是共性。

## 4. micro-app / wujie / Web Components

### Q8（4.1/4.2）｜ micro-app 为什么能零生命周期协议接入？

- **判断**：它把加载时序交给**自定义元素生命周期**——`connectedCallback` 触发 fetch html → 解析 → 沙箱执行 → 应用自挂载，`disconnectedCallback` 回收。子应用按普通页面写（自 mount 到 #root）。
- **展开**：`microApp.start()` 一次注册，`<micro-app url>` 标签即接入；data 属性下行、`window.microApp.dispatch` 上行、`addDataListener` 推送——组件式通信与 React props/回调同构。样式 scopecss 默认开启（运行时给规则加 `micro-app[name=xxx]` 前缀，弹窗也生效）。
- **边界**：实测坑——micro-app 对 Vite dev 的 ESM module script 路径拼接 bug（`undefined../src/main.ts`），走 UMD 产物最稳。可追问：与 Web Components 方案的关系？→ micro-app 就是 WC 思路的工业化：元素壳 + 补上沙箱与 scopecss。

### Q9（5.1/5.4）｜ wujie 的"iframe 运行时 + 影子渲染"组合怎么理解？

- **判断**：JS 在隐藏 iframe 里执行（结构性隔离，无沙箱代码），DOM 搬运到宿主 shadow DOM 渲染——把 iframe 方案的隔离优势和容器方案的同文档体验拼在一起。
- **展开**：意外收获是弹窗天然逃逸——子应用看到的 `document.body` 被代理到宿主文档，`body.appendChild(modal)` 实际挂到宿主 body，**五方案唯一弹窗开箱即用**。alive 模式 iframe 保活、二次切换秒开（脚本不重执行）。
- **边界**：定价是依赖共享——各 iframe 独立解析，React/Vue 必然各一份（mf-workspace 实测：react-sub UMD 产物 465KB 自包含）。调试也是双层结构（iframe + shadow），排查成本高于单文档。可追问：路由同步？→ iframe 内路由天然隔离，要同步走 bus/自定义协议。

### Q10（6.2/6.3）｜ React 没有 defineCustomElement，怎么把子应用做成自定义元素？

- **判断**：手写 HTMLElement 子类：`connectedCallback` ↔ mount、`disconnectedCallback` ↔ unmount、`attributeChangedCallback` ↔ props 更新，内部 `createRoot(shadow 内容器).render()`。
- **展开**：核心 30 行（wc-entry.tsx）：observedAttributes 声明 `order-id`；首次 connectedCallback `attachShadow` + 注入 inline 样式 + createRoot 挂载；attribute 变化重渲染。**元素生命周期就是微前端生命周期协议的原型**——qiankun/micro-app 的 mount/unmount 都在模仿它。
- **边界**：attribute 传值只能是字符串（复杂对象走 property 或事件回传）；样式必须 `?inline` 字符串注入 shadow（见 Q11）。可追问：Vue 侧呢？→ defineCustomElement 一行变元素，props 自动映射 attribute。

### Q11（6.4）｜ defineCustomElement 构建的元素在页面上"全裸"，什么原因？

- **判断**：lib 构建默认把 `<style>` 抽成独立 css 文件，宿主只加载 js 产物时 shadow DOM 里没有样式——必须 `?inline` 把样式变字符串、经组件 `styles` 选项注入 shadowRoot。
- **展开**：mf-workspace 实测：修复前产物有独立 `style.css`（0.58KB），js 里无样式；用 `import appStyle from './app.css?inline'` + `defineCustomElement({ extends: App, styles: [appStyle] })` 后 js 体积 +0.58KB（样式内联），shadow 内样式生效。
- **边界**：React 手写 wrapper 同理（`style.textContent = appStyle` 注入 shadow）。这个坑出现率极高，因为 lib 构建默认行为与 shadow 隔离直觉相反。

## 5. 沙箱与隔离

### Q12（7.2/7.3）｜ 三种 JS 沙箱的原理与取舍？

- **判断**：快照"激活拍照、失活 diff 还原"；Proxy 单例用 set 陷阱记账代替快照；Proxy 多例一人一份 fakeWindow——**多例是唯一支持多应用并存的方案**（qiankun 2.x/micro-app 现行）。
- **展开**：快照正确但慢且必须单应用交替；Proxy 单例开销与写入次数成正比、与全局大小无关；多例 `fakeWindow = Object.create(sharedGlobal)`，读沿原型链回落、写只落自己那份，天然互不可见无需恢复。
- **边界**：IE11 只能退快照；`in`/`for...in` 穿透原型链，真实实现要对 document/location 做代理白名单；Proxy 沙箱防无意污染不防有意逃逸（window.top 等）——结构性隔离只有 iframe/wujie。可追问：副作用清理？→ 拦截 setInterval/addEventListener 记账，unmount 回滚，同一套记账思路。

### Q13（7.4）｜ 样式隔离三条路线怎么选？

- **判断**：Shadow DOM（强，弹窗逃逸）、选择器前缀（中，运行时改写 CSS 文本）、动态样式表（中，整批启停）。
- **展开**：工程落点——wujie/WC 用 shadow DOM（天然）；micro-app scopecss 默认开（前缀，弹窗也生效）；qiankun strictStyleIsolation 会让弹窗丢样式、experimentalStyleIsolation 有动态样式边界 case，**实践中多数团队不开隔离靠 CSS Modules/命名约定**。
- **边界**：WC 方案的 shadow 隔离有个高频构建坑——lib 构建抽独立 css 导致 shadow 全裸，须 `?inline`（Q11）。可追问：主题穿透？→ CSS 变量可穿 shadow 边界，是 shadow 方案下主题下发的标准姿势。

## 6. 通信与共享

### Q14（8.1/8.4）｜ 五方案的通信通道语义上有什么共同点？initGlobalState 的边界？

- **判断**：全部同构——下行 props、上行事件、共享态 store；initGlobalState 是 qiankun 托管的广播式 shared store。
- **展开**：mf-workspace 同一动作五条通道实测联动全通：qiankun setGlobalState/onGlobalStateChange、micro-app dispatch/addDataListener、wujie bus.$emit/$on、WC CustomEvent/attributeChangedCallback、iframe postMessage/URL 转发。发送端一个 20 行 switch 按环境分流（env.ts）。
- **边界**：initGlobalState 无历史回放、无 selector、无持久化——只放令牌/主题/当前选中类轻状态；业务数据走各子应用 API 层。事件传"发生了什么"、store 存"现在是什么"。可追问：unmount 忘退订会怎样？→ 给已卸载应用发"幽灵回调"，订阅必须进副作用清单。

### Q15（9.3/9.4）｜ Module Federation 的 shared 协商规则？单例语义为什么重要？

- **判断**：从高到低找同时满足所有消费方版本约束的版本——找到全场一份（copies:1），找不到按约束分组 fallback 各带各的（代价是多份副本而非报错）。
- **展开**：构建期把 shared 依赖外置出版本清单，运行期容器协商只加载需要的 chunk。React 这类带全局状态的包必须 `singleton: true`——两份 React 意味着 hooks 状态、Context、事件系统各一套，跨应用 Context 打不通。
- **边界**：requiredVersion 太宽易踩不兼容、太窄频繁 fallback；实践是主应用定基准、子应用 `^` 从宽；上线用产物分析核对 React 出现次数、协商表 copies===1。可追问：qiankun 和 MF 怎么配合？→ qiankun 管应用级隔离调度，MF 管模块级依赖去重，组合使用。

### Q16（9.1）｜ 为什么"三个远程加载方案统一走 UMD 产物"？

- **判断**：qiankun（preamble 冲突）、micro-app（ESM 路径拼接 bug）、wujie（classic script 支持最稳）——实测三家都指向 **classic script 是容器方案最稳的共同消费形态**。
- **展开**：mf-workspace 的产物矩阵：dev server（3031/3032）服务 iframe 与联调；UMD 产物（3033/3034）服务 qiankun/micro-app/wujie；自定义元素产物（3141/3142）服务 WC。UMD 是 classic script，容器 fetch 后直接 eval/执行，无 ESM 静态解析问题。
- **边界**：UMD 的代价是依赖内联（产物大）与无法 tree-shaking 增量；现代演进方向是 ESM 容器（esm 属性、import maps），但兼容性成本当前仍高。可追问：产物怎么和接入协议解耦？→ 同一份 UMD，qiankun 取 lifecycle、micro-app/wujie 无视 lifecycle 自挂载——产物形态与接入姿势正交。

## 7. 手写 mini 框架与综合

### Q17（10.2）｜ 手写 mini 微前端框架，最容易被问到的三行代码？

- **判断**：`with(window){...}`（裸标识符走 Proxy，缺它必逃逸）、`Object.create(sharedGlobal)`（原型链回落，多例基础）、副作用记账（拦截 + unmount 回滚）。
- **展开**：mini-micro 四文件——sandbox.cjs（多例 Proxy + 记账 + cleanup）、entry.cjs（HTML entry 正则解析 + scoped 前缀）、scheduler.cjs（url 缓存/预加载/start/stop）、run.cjs（假 CDN + 四场景自检）。`new Function('window', 'with(window){' + code + '}')(sandbox.proxy)` 让子应用代码的一切裸标识符都经过 Proxy。
- **边界**：从 mini 到生产差的六件事：完整 HTML 解析、document/location 代理白名单、全量副作用覆盖、shadow/运行时样式隔离、路由驱动调度、MF 协商组合。可追问：路由驱动怎么实现？→ 监听 popstate/hashchange 把 start/stop 变成自动副作用，内部仍是这几步。

### Q18（综合）｜ 给你一个"Vue 宿主 + Vue/React 子应用"的中后台需求，你的落地方案？

- **判断**：先跑统一工程验证选型（mf-workspace 五方案实测），默认推荐 micro-app 或 wujie（零改造），子应用团队愿意配合时 qiankun 生态最好。
- **展开**：产物矩阵三形态（dev 联调 / UMD 容器消费 / 元素产物标准化）；通信契约先行（事件名统一、载荷约定、下行 props 清单）；构建层先修 process define；样式上 scss 命名空间 + micro-app scopecss 或 wujie shadow；上线前核对依赖副本数与通信协议兼容矩阵。
- **边界**：实测数据支撑——五方案业务闭环 9/9 通过（五挂载 + 四通信联动，headless Chrome）；已知双坑（React preamble、Vite dev ESM）都已在工程里复现并给出修法。可追问：怎么验证隔离真的生效？→ 沙箱实验台 node run.cjs 四场景（sandbox-lab）+ 产物分析 React 副本数（mf-demo 协商表 copies===1）。
