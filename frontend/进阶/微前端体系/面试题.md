# 模块面试题 · 微前端体系

## 1. 方案全景与选型

### Q1（1.1）｜ 什么样的团队 / 系统才需要微前端？

- **判断**：只有「多团队 × 多技术栈 × 独立发布」三个条件**同时出现**才值得上微前端；它解决的是组织架构问题，不是代码量问题。
- **展开**：微前端把应用按业务域拆成独立开发、独立部署、独立运行的子应用，由容器拼在同一个页面里。它的每一条收益（独立发布、技术栈共存、按域划责）都对应一个团队协作痛点；代码多本身用**模块化 + 代码分割**就能解决，不需要付架构成本。
- **边界**：代价清单有五笔——容器基建的复杂度上移、公共依赖重复打包、样式 / 全局一致性变难、跨应用调试链路变长、容器协议升级的版本兼容矩阵。团队只有一两个人时这些全是纯开销。可追问：巨石应用怎么渐进迁移？→ 新功能用子应用承载、老代码按域逐步外迁；qiankun 官方的渐进式路径即此。

### Q2（1.2）｜ 路由分发式、微件式、容器式三类方案怎么选？

- **判断**：页面级整合选路由分发式，局部组件嵌入选微件式，要"同页面运行 + 共享布局与通信"才上容器式。
- **展开**：路由分发式靠 Nginx 把不同路径转发到各子应用，零侵入但整页刷新；微件式用 Web Components 把子应用做成自定义元素嵌进页面；容器式由容器应用在运行时完成路由分发、生命周期调度、沙箱与通信，qiankun / micro-app / wujie 都属此类。
- **边界**：三类**不是演进关系而是场景关系**——门户聚合老系统用路由分发，嵌一个客服卡片用微件，中后台多团队平台才用容器。可追问：iframe 属于哪类？→ 三类之外的原生硬隔离：任何应用都能丢进去，但 URL 状态易丢、弹窗困在框内、内存开销成倍、只能 postMessage 通信，适合一次性接入第三方异构系统（wujie 用"iframe 管 JS 隔离 + Web Components 管渲染"混合补短板）。

## 2. 容器式框架与生命周期协议

### Q3（2.1）｜ qiankun 和 Module Federation 的定位差别是什么？

- **判断**：qiankun 管的是「隔离与调度」，Module Federation 管的是「依赖共享」，前者无技术栈约束但各带各的依赖，后者要求同一套构建链但能 shared 协商去重。
- **展开**：容器框架在运行时加载子应用、起沙箱、调生命周期，代价是每个子应用把 React 等依赖各打一份；Module Federation 在构建期声明 shared 依赖，运行时按版本协商只加载一份，但它不做任何 JS / 样式隔离——多份代码在同一个全局里执行。
- **边界**：两者可以组合：容器框架做应用级拆分，MF 做模块级共享；MF 单独使用时适合"多个应用共享同一份组件库 / 工具库"的微模块场景。可追问：只想嵌一个卡片该用什么？→ Web Components，浏览器原生、无需框架，别为组件级复用引入容器。

## 3. JS 沙箱隔离与副作用管理

### Q4（3.2）｜ 三种 JS 沙箱方案的原理与取舍？

- **判断**：快照沙箱"激活拍照、失活 diff 还原"；Proxy 单例用 `set` 陷阱记账代替全量快照；Proxy 多例给每个应用一份 `fakeWindow`、写只进自己那份——**多例是唯一支持多应用并存的方案**。
- **展开**：快照方案在激活时对全局做全量记录、失活时遍历 diff 还原，正确但慢且必须单应用交替；Proxy 单例在属性写入时顺手记下"写过什么"，失活只撤销记账的属性，开销与写入次数成正比、与全局大小无关；Proxy 多例让 `fakeWindow = Object.create(sharedGlobal)`，读沿原型链回落原生 API、写永远落在自己那份，天然互不可见、无需恢复（qiankun 2.x / micro-app 采用）。
- **佐证**：

```
fakeWindow = Object.create(sharedGlobal)
读 → 沿原型链回落共享全局；写 → 只落进自己这份 fakeWindow
```

- **边界**：快照方案是 ES5 环境下兼容 IE11 的唯一选择，代价是同时只能跑一个子应用；Proxy 方案 IE11 全军覆没；多例方案还要注意 `in` 与 `for...in` 会穿透原型链，真实实现需对 `document`/`location` 做代理白名单。可追问：副作用（定时器、监听器）怎么清理？→ 与沙箱同一思路：拦截 `setInterval`/`addEventListener` 记账，unmount 时统一回滚。

## 4. 样式隔离

### Q5（4.1）｜ 样式隔离有哪些路线，各牺牲了什么？

- **判断**：三条路线——Shadow DOM 隔离最强但弹窗会逃出 shadow 边界；选择器前缀（scoped）靠构建期约定，`@规则` 与伪元素要特殊处理；动态样式表实现最简单，但应用切走后新弹出的元素会丢样式。
- **展开**：Shadow DOM 用浏览器原生边界让样式天然不外泄；scoped 在构建期（CSS Modules / postcss）给每条规则加 `[data-app=main]` 前缀；动态样式表给每个应用的 style/link 打标记，切换时整批启停。
- **边界**：Shadow DOM 下全局主题样式"进不来"，UI 规范统一反而变难；scoped 前缀会拉高选择器优先级，覆盖关系要小心；动态样式表是 qiankun 默认方案，隔离强度最低。可追问：主子应用要共用一套主题变量怎么办？→ 用 CSS 变量穿透（自定义属性沿 DOM 继承可进 shadow 边界）或在每个子应用构建期注入同一份变量定义。

## 5. 应用通信与状态共享

### Q6（5.1）｜ 主子应用之间有哪些通信方式，分别适合什么场景？

- **判断**：四种——props 透传做一次性单向低频下发，事件总线做通知类交互，shared store 做持续读写的公共状态，路由同步靠主应用路由当唯一真相源。
- **展开**：props 在 mount 时下发（用户、配置、request），双向同步会导致双方各存过期快照；事件总线双方只认事件名不认实例，解耦但要事件名加前缀、unmount 退订、payload 传拷贝；shared store 存"现在是什么"（登录态 / 主题），与事件总线分工为「事件传发生了什么、store 存现在是什么」；路由上主路由管应用级分发、子路由管应用内级。
- **边界**：三个路由坑——子应用直改 `location.href` 触发整页刷新、前进 / 后退主子双跳（只由主应用 popstate 分发）、iframe 刷新丢内部路由需写回主页面 URL 恢复。可追问：生命周期协议在通信里扮演什么角色？→ 它定义通信的时间窗口：bootstrap 只跑一次、mount 每次激活带 props、unmount 必须清干净副作用，否则下次 mount 叠加两份。

## 6. 资源加载与依赖共享（打包）

### Q7（6.4）｜ Module Federation 的 shared 版本协商怎么工作？失败会怎样？

- **判断**：运行时在共享作用域里从高到低找一个同时满足所有消费方 `requiredVersion` 的版本——成功全场共用一份；失败不报错，而是按约束分组 fallback，各组各加载一份副本。
- **展开**：构建期每个应用声明 provides（版本）与 requires（范围），把 shared 依赖外置成独立 chunk + 版本清单；运行期容器拉清单做协商，最高公共版本胜出（实测 appA `^18.0.0` 与 appB `^18.2.0` 共用 18.2.0 一份），React 17/18 大版本冲突时 17 组与 18 组各带各的（copies: 2，内存与体积回到不共享状态）。
- **边界**：React、状态管理这类带全局状态的包必须 `singleton: true`——宁可版本告警也不能加载第二份，否则 hooks 状态、Context 跨应用打不通；`requiredVersion` 填 `*` 省事但易踩不兼容，太窄则频繁 fallback，实践是主应用定基准大版本、子应用 `^` 从宽。可追问：怎么验证共享真的生效了？→ 上线后用产物分析核对 React 出现次数；协商结果的 `copies === 1` 就是这个指标的模型（mf-demo 场景一实测）。

## 7. 手写 mini 微前端框架

### Q8（7.1）｜ 手写一个 mini 微前端框架，最小要实现哪几层？

- **判断**：四层——沙箱层（多例 Proxy + 副作用记账）、解析层（HTML entry 摘 script/style + scoped 样式前缀）、调度层（路由命中 → 沙箱执行 → 生命周期调度 → 卸载清账）、以及一个模拟环境做自检；约 200 行就能跑通主流程。
- **展开**：子应用源码用 `new Function('window','with(window){'+code+'}')` 在沙箱里执行——`with(window)` 让裸标识符也走 Proxy（micro-app 同款），写入落在自己的 `fakeWindow`、读沿原型链回落共享全局；`get` 陷阱拦截 `setInterval`/`addEventListener` 记副作用账，`stop` 时 unmount→cleanup 统一清定时器、撤销沙箱属性。
- **佐证**：

```
with(window){ code }   让裸标识符也走 Proxy，写落 fakeWindow、读回落共享全局
```

- **边界**：实测的三个坑——`new Function` 不闭包外层作用域，公共能力必须放共享全局（子应用沿原型链取）；`with` 之外的裸赋值会逃逸到真实全局；实验台里 mount 申请的真实定时器不清理，进程会挂住——框架本身就要守"卸载清副作用"的规矩。可追问：与生产级框架（qiankun/micro-app）的差距在哪？→ 完整 HTML 解析与资源路径补全、document/location 代理白名单、路由变化自动 mount/unmount 与 keep-alive、Shadow DOM 增强、与 Module Federation 的 shared 依赖协商组合。
