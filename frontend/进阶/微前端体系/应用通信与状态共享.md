# 应用通信与状态共享

沙箱把主子应用隔开了，但业务上它们必须协同：子应用要读登录态、要跟着主应用路由走、要往全局通知条发消息。通信设计的目标恰好与沙箱相反——**在隔离的墙上开尽量少、尽量规矩的门**。本文讲清楚主子应用的生命周期协议、四种通信方式的取舍、跨应用路由同步和版本兼容策略。

## 一、生命周期协议：通信的时间窗口

容器式微前端的通信都发生在约定的生命周期钩子之间，这是主子双方的"合同"：

> 示意片段（无配套脚本）

```
容器（主应用）                          子应用
    │
    ├─ 注册（app: { name, entry, activeRule, container }）
    │
    ├─ 路由命中 activeRule
    │        └─────── 加载资源 ───────▶  bootstrap()   只跑一次：初始化不依赖 DOM 的全局
    │                                    mount(props)  每次激活：渲染进容器，props 里带通信对象
    ├─ 路由离开 activeRule
    │        └────────────────────────▶  unmount()     清理副作用，卸载 DOM，归还沙箱
    │
    └─ （再次命中 → 重新 mount，bootstrap 不再执行）
```

两条纪律：**bootstrap 里只做不依赖运行环境的事**（配置、SDK 初始化），凡是碰 DOM 的都进 mount；**unmount 必须把 mount 期间申请的副作用全部退掉**——定时器、监听器、弹窗，否则下次 mount 会叠加两份。

## 二、props 透传：最朴素的单向下发

容器在 mount 时把数据和方法作为 props 传给子应用，是最不该被滥用的方式：

> 示意片段（无配套脚本）

```js
// 主应用注册时声明要下发的 props
registerMicroApps([{
  name: 'app-orders',
  entry: '//cdn.example.com/orders/',
  activeRule: '/orders',
  container: '#micro-app',
  props: { user: currentUser, request: authedFetch },   // 数据 + 能力
}])

// 子应用 mount 时收到
export function mount(props) {
  const { user, request } = props
  render(user)
}
```

适用边界：**一次性、单向、低频**的下发（当前用户、全局配置、封装好的 request）。一旦主子要"互发"，props 就成了双方各存一份的过期快照，应改用事件或共享 store。

## 三、事件总线：解耦的广播通道

跨应用的通知类交互（子应用改完数据 → 主应用刷新角标）走事件总线，双方只认事件名不认对方实例：

> 示意片段（无配套脚本）

```js
// 主应用提供（或用 SharedCommunicator 之类约定包）
const bus = {
  map: new Map(),
  on(type, handler) {
    if (!this.map.has(type)) this.map.set(type, new Set())
    this.map.get(type).add(handler)
    return () => this.map.get(type).delete(handler)   // 返回退订函数
  },
  emit(type, payload) {
    ;(this.map.get(type) || []).forEach((h) => h(payload))
  },
}

// 子应用 mount 时订阅，unmount 时必须退订
let off
export function mount(props) {
  off = props.bus.on('cart:changed', (n) => updateBadge(n))
}
export function unmount() {
  off()   // 不退订 = 给已卸载的应用发"幽灵回调"
}
```

三条纪律：事件名加应用前缀防撞（`cart:changed` 而不是 `changed`）；**unmount 必须退订**（订阅放进副作用清单统一清理）；payload 走拷贝，避免传大对象引用导致两边共享可变状态。

## 四、shared store：跨应用的状态共享

需要多应用**持续读写**的公共状态（登录态、主题、购物车计数）放 shared store。两种做法：

**1. 主应用下发实例**：主应用把自己的 store（如 Redux/Vuex 实例或一个自建 mini store）通过 props 下发，子应用当外部 store 订阅。优点是主应用完全掌控；缺点是子应用与主应用的技术栈耦合在协议里。

**2. 独立共享包**：把状态做成独立 npm 包（或 Module Federation 的 shared singleton），主子各自 import 同一份模块实例——前提是依赖协商把它变成单例（见下一篇）。这是 Module Federation 体系下的主流做法：

> 示意片段（无配套脚本）

```js
// shared-store 包：纯单例，不关心谁在用
export const store = {
  state: { user: null, theme: 'light' },
  listeners: new Set(),
  set(patch) {
    Object.assign(this.state, patch)
    this.listeners.forEach((l) => l(this.state))
  },
  subscribe(l) {
    this.listeners.add(l)
    return () => this.listeners.delete(l)
  },
}

// 主/子应用代码一致：订阅 + 按需更新，谁写的状态对另一方可见
store.subscribe((s) => renderUser(s.user))
```

与事件总线的分工：**事件总线传"发生了什么"，shared store 存"现在是什么"**。两者并存时，写动作发事件、状态读 store，避免事件里携带大状态快照。

## 五、跨应用路由同步

容器式微前端的路由必须只有一个真相源——**主应用路由器**：

> 示意片段（无配套脚本）

```
地址栏 /orders/list/42
   ├── 主应用路由：匹配 activeRule('/orders') → 决定加载哪个子应用（应用级）
   └── 子应用路由：读路径剩余部分 '/list/42' 渲染内部页面（应用内级）

子应用内部跳转：改自己的 history + 通知主应用同步地址栏
主应用跳转：改地址栏 → 命中某 activeRule → 对应子应用 mount 后自行解析
```

最容易踩的三个坑：子应用直接 `location.href = ...` 触发整页刷新（必须用各自的 Router API 走 history）；浏览器前进/后退时主子路由各动一次导致双跳（约定只由主应用 popstate 做分发）；iframe 方案刷新后 iframe 内路由丢失（需要把 iframe 路由写进主页面 URL 或 sessionStorage 恢复）。

## 六、版本兼容：通信协议也是公共 API

主容器与 N 个子应用**不同时发布**，通信协议的每次变更都要考虑旧子应用还在线：

| 变更类型 | 风险 | 兼容策略 |
|---|---|---|
| 新增 props / 事件 | 低 | 天然向后兼容，子应用按需消费 |
| 删除 / 改名 | 高 | 旧名保留一个版本周期 + 运行时告警 |
| payload 结构变化 | 高 | 版本字段内嵌（`{ v: 2, data }`），消费方按版本分支 |
| 协议大版本升级 | 极高 | 容器同时挂新旧协议层，子应用声明自己说哪个版本 |

实操建议：把"props/事件/store 结构"当成对外 API 写进文档并做兼容测试；容器侧对所有跨应用调用做 try-catch + 上报——某个旧子应用抛错不能拖垮整个主应用。

## 小结

- 应用通信与状态共享
  - 生命周期协议：bootstrap 一次 / mount 每次激活 / unmount 清副作用，通信都发生在这扇时间窗里
  - props 透传：一次性单向低频下发（用户、配置、request），不做双向同步
  - 事件总线：通知类交互，事件名加前缀、unmount 必退订、payload 传拷贝
  - shared store：持续读写的公共状态（登录态/主题），"事件传发生了什么、store 存现在是什么"
  - 路由同步：主应用路由是唯一真相源，应用级/应用内级分工，防双跳与整页刷新
  - 版本兼容：协议是公共 API，新增安全、删除要过渡、结构变化带版本字段、调用侧 try-catch 兜底
