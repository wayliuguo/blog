# 应用通信与状态共享

## 〇、五方案通信矩阵：同一件事五种写法

统一工程 `mf-workspace` 里有一个跨方案的通信契约：点击订单 → 事件名 `order-select`、载荷 `{ orderId }` → 宿主中枢状态更新 → 详情联动。同一个动作在五种接线里的通道：

| 方案 | 上行（列表→宿主） | 下行（宿主→详情） | 对应本文概念 |
|---|---|---|---|
| iframe | `parent.postMessage` | URL 传参 + 重载 / message | 事件总线（手工版） |
| qiankun | `props.setGlobalState` | `props.onGlobalStateChange` | shared store |
| micro-app | `window.microApp.dispatch` | data 属性 / `addDataListener` | props + 事件总线 |
| wujie | `window.$wujie.bus.$emit` | `:props` / `bus.$on` | props + 事件总线 |
| Web Components | `CustomEvent`（bubbles+composed） | attribute + `attributeChangedCallback` | props + 事件总线（标准版） |

子应用侧的分流实现只有 20 行（`vue-sub/src/env.ts`），本章第二节起逐条对照：

> 摘自 `./code/mf-workspace/vue-sub/src/env.ts`

```ts
export function reportSelect(orderId: string) {
    // 一个动作按当前环境选择唯一通道，避免双重上报；事件名统一为 order-select
    const env = detectEnv()
    switch (env) {
        case 'qiankun':
            qiankunStateSetter?.({ selectedId: orderId })
            break
        case 'micro-app':
            window.microApp!.dispatch({ type: 'order-select', orderId })
            break
        case 'wujie':
            window.$wujie!.bus.$emit('order-select', orderId)
            break
        case 'iframe':
            window.parent.postMessage({ type: 'order-select', orderId }, '*')
            break
        default:
            // bubbles + composed：作为自定义元素运行时穿透 shadow DOM 边界冒泡到宿主
            window.dispatchEvent(new CustomEvent('order-select', { detail: { orderId }, bubbles: true, composed: true }))
    }
}
```

实测（headless Chrome）：qiankun/micro-app/wujie/Web Components 四条通道全部跑通"点击 #1002 → 宿主状态变 1002"，iframe 通道同样闭环（postMessage 上行 + src 转发下行）。**五条通道语义完全同构，差异只在载体**——这是本章所有机制的总纲。

## 一、生命周期协议：通信的时间窗口

容器式微前端的通信都发生在约定的生命周期钩子之间，这是主子双方的"合同"：

> 示意片段（无配套脚本）

```
容器（主应用）                          子应用
    │
    ├─ 注册（app: { name, entry, activeRule, container }）
    │
    ├─ 路由命中 activeRule
    │        └─────── 加载资源 ───────▶  bootstrap()   只跑一次：初始化不依赖 DOM 的全局
    │                                    mount(props)  每次激活：渲染进容器，props 里带通信对象
    ├─ 路由离开 activeRule
    │        └────────────────────────▶  unmount()     清理副作用，卸载 DOM，归还沙箱
    │
    └─ （再次命中 → 重新 mount，bootstrap 不再执行）
```

两条纪律：**bootstrap 里只做不依赖运行环境的事**（配置、SDK 初始化），凡是碰 DOM 的都进 mount；**unmount 必须把 mount 期间申请的副作用全部退掉**——定时器、监听器、弹窗，否则下次 mount 会叠加两份。

## 二、props 透传：最朴素的单向下发

容器在 mount 时把数据和方法作为 props 传给子应用，是最不该被滥用的方式：

> 示意片段（无配套脚本）

```js
// 主应用注册时声明要下发的 props
registerMicroApps([{
  name: 'app-orders',
  entry: '//cdn.example.com/orders/',
  activeRule: '/orders',
  container: '#micro-app',
  props: { user: currentUser, request: authedFetch },   // 数据 + 能力
}])

// 子应用 mount 时收到
export function mount(props) {
  const { user, request } = props
  render(user)
}
```

适用边界：**一次性、单向、低频**的下发（当前用户、全局配置、封装好的 request）。一旦主子要"互发"，props 就成了双方各存一份的过期快照，应改用事件或共享 store。

工程落点：wujie 的 `:props="{ orderId: selectedId }"` 和 micro-app 的 `:data="{ orderId: selectedId }"`（见 [wujie](./wujie.md) 1.2 / [micro-app](./micro-app.md) 1.2）都是 props 下行的工业化形态——声明即下发，响应式更新。接收端在 react-sub 的 App.tsx 集中适配五条下行通道：

> 摘自 `./code/mf-workspace/react-sub/src/App.tsx`

```ts
    // 每种方案一条独立的下行通道，onUnmounted 里逐条清理
    useEffect(() => {
        const applyId = (id: string) => {
            const next = orderDetails[id]
            setOrder(next ?? null)
            setNotFound(!next)
        }

        const onMessage = (e: MessageEvent) => {
            if (typeof e.data === 'object' && e.data?.type === 'order-select') applyId(e.data.orderId)
        }
        const onCustom = (e: Event) => applyId((e as CustomEvent<{ orderId: string }>).detail.orderId)
        const onWujie = (id: string) => applyId(id)
        const onMicroData = (data: Record<string, unknown>) => {
            if (typeof data.orderId === 'string') applyId(data.orderId)
        }

        window.addEventListener('message', onMessage)
        window.addEventListener('order-select', onCustom)
        window.$wujie?.bus.$on('order-select', onWujie)
        window.microApp?.addDataListener(onMicroData)
        props.onGlobalStateChange?.((state) => {
            if (state.selectedId) applyId(state.selectedId)
        })

        return () => {
            window.removeEventListener('message', onMessage)
            window.removeEventListener('order-select', onCustom)
            window.$wujie?.bus.$off?.('order-select', onWujie)
            window.microApp?.removeDataListener?.(onMicroData)
        }
        // props.onGlobalStateChange 在 mount 后只注入一次，不进依赖
        // eslint-disable-next-line react-hooks/exhaustive-deps
    }, [])
```

## 三、事件总线：解耦的广播通道

跨应用的通知类交互（子应用改完数据 → 主应用刷新角标）走事件总线，双方只认事件名不认对方实例：

> 示意片段（无配套脚本）

```js
// 主应用提供（或用 SharedCommunicator 之类约定包）
const bus = {
  map: new Map(),
  on(type, handler) {
    if (!this.map.has(type)) this.map.set(type, new Set())
    this.map.get(type).add(handler)
    return () => this.map.get(type).delete(handler)   // 返回退订函数
  },
  emit(type, payload) {
    ;(this.map.get(type) || []).forEach((h) => h(payload))
  },
}

// 子应用 mount 时订阅，unmount 时必须退订
let off
export function mount(props) {
  off = props.bus.on('cart:changed', (n) => updateBadge(n))
}
export function unmount() {
  off()   // 不退订 = 给已卸载的应用发"幽灵回调"
}
```

三条纪律：事件名加应用前缀防撞（`cart:changed` 而不是 `changed`）；**unmount 必须退订**（订阅放进副作用清单统一清理）；payload 走拷贝，避免传大对象引用导致两边共享可变状态。

## 四、shared store：跨应用的状态共享

需要多应用**持续读写**的公共状态（登录态、主题、购物车计数）放 shared store。两种做法：

**1. 主应用下发实例**：主应用把自己的 store（如 Redux/Vuex 实例或一个自建 mini store）通过 props 下发，子应用当外部 store 订阅。优点是主应用完全掌控；缺点是子应用与主应用的技术栈耦合在协议里。

**2. 独立共享包**：把状态做成独立 npm 包（或 Module Federation 的 shared singleton），主子各自 import 同一份模块实例——前提是依赖协商把它变成单例（见下一篇）。这是 Module Federation 体系下的主流做法：

> 示意片段（无配套脚本）

```js
// shared-store 包：纯单例，不关心谁在用
export const store = {
  state: { user: null, theme: 'light' },
  listeners: new Set(),
  set(patch) {
    Object.assign(this.state, patch)
    this.listeners.forEach((l) => l(this.state))
  },
  subscribe(l) {
    this.listeners.add(l)
    return () => this.listeners.delete(l)
  },
}

// 主/子应用代码一致：订阅 + 按需更新，谁写的状态对另一方可见
store.subscribe((s) => renderUser(s.user))
```

与事件总线的分工：**事件总线传"发生了什么"，shared store 存"现在是什么"**。两者并存时，写动作发事件、状态读 store，避免事件里携带大状态快照。

工程落点：qiankun 的 `initGlobalState` 就是内置的 shared store（由 qiankun 托管、双向可写）。宿主侧建立并订阅：

> 摘自 `./code/mf-workspace/host/src/register-micro-apps.ts`

```ts
export const qiankunActions = initGlobalState({ selectedId: hostState.selectedId })

qiankunActions.onGlobalStateChange((state) => {
    if (state.selectedId && state.selectedId !== hostState.selectedId) {
        hostState.selectedId = state.selectedId
        logEvent('qiankun', `onGlobalStateChange → ${state.selectedId}`)
    }
})
```

子应用侧从 mount props 拿到 `setGlobalState`（写入方）——工程里通过注入式 setter 解耦（避免 App.vue 感知插件细节，且 UMD 产物不打包 dev 插件）：

> 摘自 `./code/mf-workspace/vue-sub/src/main-qk.ts`

```ts
let app: VueApp | null = null

export async function bootstrap() {}

export async function mount(props: { container: HTMLElement | string; setGlobalState?: (s: object) => void }) {
    if (props.setGlobalState) setQiankunStateSetter(props.setGlobalState)
    app = createApp(App)
    app.mount(typeof props.container === 'string' ? document.querySelector(props.container)! : props.container)
}
```

注意 initGlobalState 的边界：它是**广播语义**（无历史回放、无 selector、无持久化），只适合轻状态。业务数据的读写走子应用各自的 API 层，共享 store 里只放"令牌、主题、当前选中"这类真正的全局值。

## 五、跨应用路由同步

容器式微前端的路由必须只有一个真相源——**主应用路由器**：

> 示意片段（无配套脚本）

```
地址栏 /orders/list/42
   ├── 主应用路由：匹配 activeRule('/orders') → 决定加载哪个子应用（应用级）
   └── 子应用路由：读路径剩余部分 '/list/42' 渲染内部页面（应用内级）

子应用内部跳转：改自己的 history + 通知主应用同步地址栏
主应用跳转：改地址栏 → 命中某 activeRule → 对应子应用 mount 后自行解析
```

最容易踩的三个坑：子应用直接 `location.href = ...` 触发整页刷新（必须用各自的 Router API 走 history）；浏览器前进/后退时主子路由各动一次导致双跳（约定只由主应用 popstate 做分发）；iframe 方案刷新后 iframe 内路由丢失（需要把 iframe 路由写进主页面 URL 或 sessionStorage 恢复）。

## 六、版本兼容：通信协议也是公共 API

主容器与 N 个子应用**不同时发布**，通信协议的每次变更都要考虑旧子应用还在线：

| 变更类型 | 风险 | 兼容策略 |
|---|---|---|
| 新增 props / 事件 | 低 | 天然向后兼容，子应用按需消费 |
| 删除 / 改名 | 高 | 旧名保留一个版本周期 + 运行时告警 |
| payload 结构变化 | 高 | 版本字段内嵌（`{ v: 2, data }`），消费方按版本分支 |
| 协议大版本升级 | 极高 | 容器同时挂新旧协议层，子应用声明自己说哪个版本 |

实操建议：把"props/事件/store 结构"当成对外 API 写进文档并做兼容测试；容器侧对所有跨应用调用做 try-catch + 上报——某个旧子应用抛错不能拖垮整个主应用。
