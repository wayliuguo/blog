## 1. 方案全景与选型

### 1.1 动机判定：什么时候才该上微前端

「**多团队 × 多技术栈 × 独立发布**」三个条件同时出现才值得上微前端。它解决的是**组织架构问题，不是代码量问题**：

- 每一条收益（独立发布、技术栈共存、按域划责）都对应一个团队协作痛点；
- 仅"代码多"用**模块化 + 代码分割**即可解决（`import()` 按需加载 + 路由懒加载），不需要付架构成本；
- 代价清单有五笔：容器基建复杂度上移、公共依赖重复打包、样式 / 全局一致性变难、跨应用调试链路变长、容器协议升级的版本兼容矩阵。

### 1.2 三类方案：路由分发式 / 微件式 / 容器式

三类不是演进关系而是**场景关系**：

| 方案 | 形态 | 适用 |
| ---- | ---- | ---- |
| 路由分发式 | Nginx 按路由转发到各子应用静态资源，页面级整合、零侵入 | 门户聚合老系统，缺点是切换整页刷新、无局部嵌入 |
| 微件式 | 子应用作为页面局部区块嵌入；Web Components（自定义元素 + Shadow DOM）是原生路径 | 嵌一个客服组件 / 图表卡片 |
| 容器式 | 容器应用负责布局、路由分发、生命周期调度、沙箱与通信 | 中后台多团队、要"同页面运行 + 共享布局与通信" |

容器式框架中，**qiankun / micro-app / wujie 均属此类**，是一套运行时按需加载子应用、起沙箱、调生命周期的完整方案。

### 1.3 iframe 的取舍

iframe 是三类之外的**原生硬隔离**：

```
优点  隔离最强（JS/CSS/DOM 硬隔离）、接入成本最低、任何应用都能丢进去
缺点  URL 状态易丢、弹窗困在框内、内存与首屏开销成倍、只能 postMessage 通信
适用  一次性接入完全不可控的第三方异构系统
```

- wujie 的思路正是"**iframe 管 JS 隔离 + Web Components 管渲染**"——混合两种技术补各自短板。

### 1.4 决策矩阵与代价清单

**决策矩阵**：

```
中后台多团队平台           → qiankun / micro-app 类容器框架
多应用共享依赖且同一构建链 → Module Federation（解决依赖共享而非隔离）
嵌一个卡片 / 组件           → Web Components，别上框架
完全不可控的第三方老系统   → iframe / wujie
```

**代价清单**：复杂度上移（容器基建本身要维护）、公共依赖重复、样式一致性难、调试链路变长、版本兼容矩阵。一句话：**微前端是组织架构问题的技术解**。

## 2. 容器式框架与生命周期协议

### 2.1 容器式框架：single-spa / qiankun / micro-app / wujie

容器式框架的核心职责：**布局、路由分发、生命周期调度、沙箱与通信**。

- **single-spa** 是底层的微前端内核/规范，只定义生命周期协议与路由调度，不管样式、沙箱；
- **qiankun 基于 single-spa** 在上层补齐沙箱、样式隔离、HTML entry、预加载等工程能力；micro-app / wujie 各自再给出不同的技术实现（Custom Element 包装、iframe 沙箱等）；
- 框架之间并非非此即彼，选型看团队技术栈惯性与隔离需求（见 §1.4）。

### 2.2 生命周期协议：bootstrap / mount / unmount

每个子应用向容器暴露一致的生命周期钩子（这也定义了下文通信的时间窗口）：

| 钩子 | 时机 | 契约 |
| ---- | ---- | ---- |
| `bootstrap` | 只跑一次 | 做不碰 DOM 的初始化（创建全局实例） |
| `mount` | 每次激活 | 渲染进容器，`props` 带上通信对象 |
| `unmount` | 切走时 | 清副作用（定时器 / 监听器 / 弹窗全退掉），否则下次 mount 叠加两份 |

### 2.3 版本兼容协议：协议是公共 API

生命周期钩子与 props 结构都是**公共 API**，改动要按版本化纪律走：

- 新增向后兼容；
- 删除 / 改名要保留旧名一个版本周期；
- payload 变化内嵌 `{ v: 2, data }` 版本字段；
- 容器对**所有跨应用调用 try-catch + 上报**——旧子应用抛错不拖垮主应用。

## 3. JS 沙箱隔离与副作用管理

### 3.1 隔离对象；DOM 与副作用重定向

隔离的**对象**是：`window` 运行时、样式表、DOM 查询、定时器 / 监听器 / fetch 劫持等副作用。所以沙箱不止挡 `window`，还要处理：

- `querySelector` / `createElement` **重定向到容器**；
- `setInterval` / `addEventListener` **拦截记账**，unmount 统一回滚——与沙箱的"记账"是同一思路。

### 3.2 三种 JS 沙箱方案对比

| 方案 | 原理 | 是否支持多应用并存 | 代价 |
| ---- | ---- | ---- | ---- |
| 快照沙箱（legacy） | 激活拍全局快照，失活 diff 还原 | 否（只能交替跑一个） | 全量记录，慢 |
| Proxy 单例沙箱 | `set` 陷阱记账，失活只撤销记账属性 | 否 | 开销与写入次数成正比 |
| Proxy 多例沙箱 | 每应用一份 `fakeWindow`，写只进自己那份 | **是**（qiankun 2.x / micro-app 采用） | 真实实现要处理 `in`/`for...in` 穿透 |

### 3.3 快照沙箱

激活时对全局做**全量记录**，失活时 **diff 出新增与修改**并还原全局。

- 优点：实现简单可靠；
- 缺点：激活 / 失活必须**完整交替**，同一时刻只能跑一个应用；是 **ES5 环境下兼容 IE11 的唯一选择**。

### 3.4 Proxy 单例沙箱

`set` 陷阱在属性写入时顺手**记账**（写过什么），失活**只撤销记账的属性**。

- 相比全量快照，开销与写入次数成正比、与全局大小无关；仍是单例交替。

### 3.5 Proxy 多例沙箱与选型

每应用一份 `fakeWindow = Object.create(sharedGlobal)`：读沿原型链回落共享全局、写永远落在自己那份，天然互不可见、无需恢复。

```
fakeWindow = Object.create(sharedGlobal)
读  沿原型链回落原生 API（共享全局）
写  只落进自己这份 fakeWindow，互不可见
```

**选型结论**：新项目一律 **Proxy 多例**；要兼容 IE11 只能退回快照并接受单应用交替。注意多例下 `in` 与 `for...in` 会穿透原型链，真实实现需对 `document`/`location` 做代理白名单。

### 3.6 DOM 与副作用清理的记账思路

副作用（定时器、事件监听、fetch 劫持）与沙箱同一思路：**拦截记账、卸载统一回滚**。unmount/stop 时清定时器、撤销沙箱属性，避免重复 mount 叠加两份副作用。

## 4. 样式隔离

### 4.1 三条路线对比

| 路线 | 隔离强度 | 牺牲 / 代价 |
| ---- | ---- | ---- |
| Shadow DOM | 最强（浏览器原生边界） | 弹窗会逃出 shadow 边界；全局主题样式"进不来" |
| scoped 选择器前缀 | 中 | 靠构建期约定；拉高选择器优先级；`@规则`与伪元素要特殊处理 |
| 动态样式表 | 最弱（qiankun 默认） | 实现最简单；应用切走后新弹出的元素丢样式 |

### 4.2 Shadow DOM

用浏览器**原生边界**让样式天然不外泄。代价是**全局主题样式"进不来"**，UI 规范统一反而变难。

### 4.3 scoped 选择器前缀

构建期（CSS Modules / postcss）给每条规则加前缀，如 `[data-app=main] .card`。

- 优点：跨框架、可控；
- 代价：选择器优先级被拉高，覆盖关系要小心；每条选择器加前缀（`@规则` 除外）。

### 4.4 动态样式表

给每个应用的 style/link **打标记**，切换应用时**整批启停**。

- 实现最简单（qiankun 默认方案），但隔离强度最低：应用切走后，新弹出的元素不再持有对应样式而丢样式。

### 4.5 选型与主题穿透

- **选型分级**：要强边界用 Shadow DOM；要通用可控用 scoped；接入成本优先用动态样式表；
- **主子共用一套主题变量**：用 **CSS 变量穿透**（自定义属性沿 DOM 继承可进 shadow 边界），或在每个子应用构建期注入同一份变量定义。

## 5. 应用通信与状态共享

### 5.1 四种通信方式概览

按"数据的生命周期"划分成四种：

| 方式 | 适合 | 特征 |
| ---- | ---- | ---- |
| props 透传 | 一次性、单向、低频的下发 | 双方各存快照，双向同步必然过期 |
| 事件总线 | 通知类交互 | 双方只认事件名不认实例，解耦 |
| shared store | 持续读写的公共状态 | 存"现在是什么" |
| 路由同步 | 跨应用跳转、状态保留 | 主应用路由当唯一真相源 |

### 5.2 props 透传

主应用在 `mount` 时把一个 `props` 对象下发（当前用户、全局配置、封装好的 request）。

- **一次性、单向、低频**是它的边界：要双向同步就不能用 props——**双方各存一份快照必然过期**。

### 5.3 事件总线

子应用改数据 → 主应用刷角标这类**通知类交互**。纪律三条：

1. 事件名加应用前缀，防撞；
2. **unmount 必须退订**（否则给已卸载应用发幽灵回调）；
3. payload 传**拷贝**，不传引用。

### 5.4 shared store 与「事件 vs store」分工

shared store 承担持续读写的公共状态（登录态 / 主题 / 购物车计数）。两种落地：

- 主应用经 props **下发 store 实例**——主应用掌控、协议耦合栈；
- **独立共享包单例 import**——MF 体系主流。

分工原则一句话：**「事件传发生了什么，store 存现在是什么」**。

### 5.5 路由同步

主应用路由是**唯一真相源**：主路由管应用级（activeRule 分发），子路由管应用内级（剩余路径）。三个坑：

```
子应用直改 location.href    → 整页刷新
前进 / 后退主子双跳          → 只由主应用 popstate 分发
iframe 刷新丢内部路由        → 写回主页面 URL 恢复
```

## 6. 资源加载与依赖共享（打包）

### 6.1 加载链路与 url 级缓存

```
entry(HTML/JS/manifest) → 解析依赖清单 → 逐个拉取 JS/CSS(全生命周期只拉一次)
→ JS 进沙箱、CSS 按隔离策略挂载 → bootstrap → mount
```

- 依赖采用 **url 级缓存**，全生命周期只拉一次网络。

### 6.2 HTML entry vs JS entry

| 方案 | 特点 |
| ---- | ---- |
| HTML entry（qiankun 默认） | 顺带样式与首屏占位、接入成本低 |
| JS entry | 更轻，但样式随行要自己做 |

### 6.3 共享收益的两层

不共享时同一份 React 会各打一份，共享的收益分两层：

```
网络层  公共依赖只下载一次，进 HTTP 缓存
运行层  同一份 React 实例保住 hooks 状态 / Context / 事件系统全局唯一
        ——不共享时跨应用 Context 打不通
```

### 6.4 Module Federation shared 版本协商

运行时在共享作用域里**从高到低找一个同时满足所有消费方 `requiredVersion` 的版本**：

- 成功 → 全场共用一份（`copies: 1`），实测 appA `^18.0.0` 与 appB `^18.2.0` 共用 18.2.0 一份；
- 失败 → **不报错**，按约束分组 fallback，各组各带各的；React 17/18 大版本冲突时两组并存（`copies: 2`），内存与体积回到不共享状态。

### 6.5 构建期与运行期分工

```
构建期  ModuleFederationPlugin 把 shared 依赖外置、产出独立 chunk + 版本清单
运行期  容器拉清单做协商，按结果加载对应版本
```

### 6.6 工程要点与最小实现

**工程要点**：

- React / 状态管理等带全局状态的包必须 `singleton: true`（宁可版本告警，不留第二份）；
- `requiredVersion` 从宽（`^`）+ 主应用定基准大版本；
- 上线用产物分析核对 React 出现次数、协商结果 `copies === 1`。

**最小实现（`mf-demo`）**：零依赖实验台，`node run.cjs` 跑三个场景（协商成功一份 / 失败 fallback 两份 / 远程加载与 url 缓存），`node:assert` 自检全绿。

## 7. 手写 mini 微前端框架

### 7.1 四层结构

`sandbox.cjs`（隔离）/ `entry.cjs`（解析+样式）/ `scheduler.cjs`（调度）/ `run.cjs`（模拟环境自检），约 **200 行零依赖**就能跑通主流程。

### 7.2 沙箱层

- **多例 Proxy**：写落 `fakeWindow`、读沿原型链回落共享全局；
- **`get` 陷阱拦截** `setInterval` / `addEventListener` 记副作用账；
- **`cleanup()`** 清定时器、撤销沙箱属性（仅留 `__MICRO_APP_NAME__`）。

关键一行：`with(window)` 让裸标识符也走 Proxy——没有它子应用直接调 `log()` 会逃逸到真实全局（micro-app 同款实现）。

### 7.3 解析层

正则摘出 `<script src>` 与 `<style>`；scoped 给每条选择器加 `[data-app=xx]` 前缀（`@规则` 除外）。

### 7.4 调度层

url 级缓存（全生命周期一次网络）→ `preload` 只抓不执行 → `start` 里 `new Function('window','with(window){'+code+'}')` 在沙箱执行 → `bootstrap`→`mount`；`stop` 走 `unmount`→`cleanup`。

### 7.5 实测场景、踩坑与生产差距

**实测四场景**：启动顺序与写入隔离 / 样式前缀 / 卸载清账与切换 / 预加载后启动零网络。踩坑记录：

```
new Function 不闭包外层作用域  → 公共能力要放共享全局
with 之外的裸赋值              → 会逃逸到真实全局
mount 里的真实定时器不清理     → 进程挂起（实验台也守"卸载清副作用"）
```

**与生产差距**：完整 HTML 解析、document/location 代理白名单、路由驱动自动调度、keep-alive、Shadow DOM 增强、与 MF shared 组合。
