# 沙箱与隔离机制

沙箱是微前端的技术核心：主应用和多个子应用跑在**同一个浏览器页面**里，却共享同一份 `window`、同一片 DOM、同一张样式表——谁都能改 `window.fetch`、谁都能写全局 CSS。沙箱要回答的问题只有一句话：**怎么让子应用"以为自己拥有全局"，实际上互不污染**。本文用可运行的实验台把三种 JS 沙箱方案和三类样式隔离写清楚。

## 一、为什么微前端的第一难题是"全局"

浏览器给每个页面只准备了一份全局环境：

> 示意片段（无配套脚本）

```
页面全局（主子应用共享）
├── window / document        ← 子应用 A 写 window.userId，B 读到的是 A 的
├── 样式表                    ← A 的 `.card { color: red }` 染红了 B 的卡片
├── localStorage / cookie    ← 按"源"隔离，同域下主子共用
└── 定时器 / 事件监听 / fetch ← 子应用卸载后定时器还在跑（副作用泄漏）
```

这些共享点的危险程度不同：`window` 上的运行时篡改（如 polyfill、重写 `fetch`）最难发现；样式互串最常见；定时器和监听器泄漏最隐蔽。隔离方案要逐一对付它们。

## 二、快照沙箱：激活拍照、失活还原

最早的方案（qiankun legacy）：激活子应用前给全局**拍快照**，失活时把子应用改过的属性记下来、全局还原到快照。

> 摘自 `./code/sandbox-lab/legacy-snapshot.cjs`

```js
class SnapshotSandbox {
  constructor(global) {
    this.global = global
    this.snapshot = new Map()
    this.modify = new Map()
  }

  activate() {
    // 激活：先恢复上次失活时记录的修改，再对当前全局拍新快照
    for (const [k, v] of this.modify) this.global[k] = v
    this.snapshot = new Map(Object.entries(this.global))
  }

  deactivate() {
    // 失活：diff 当前全局与快照，记下本应用的修改，再把全局还原
    this.modify = new Map()
    for (const k of Object.keys(this.global)) {
      if (!this.snapshot.has(k)) {
        // 新增的属性：记下来，然后删掉
        this.modify.set(k, this.global[k])
        delete this.global[k]
      } else if (this.snapshot.get(k) !== this.global[k]) {
        // 改过的属性：记下新值，还原旧值
        this.modify.set(k, this.global[k])
        this.global[k] = this.snapshot.get(k)
      }
    }
  }
}
```

两个应用轮流激活时，全局基线不受污染（`node run.cjs` 场景一实测）：

```
场景一 · 快照沙箱（Snapshot）
A 激活后  : {"api":"appA","extra":"A-only"}
A 失活后  : {"api":"origin"}
B 激活后  : {"api":"appB"}
B 失活后  : {"api":"origin"}
  ✓ 修改被记录并在激活间还原，全局基线不受污染
```

快照方案的局限也在这里暴露了：**激活和失活之间必须完整地"上台—下台"**，同一时刻只能跑一个应用；遍历全局的 diff 在属性很多时也有性能开销。

## 三、Proxy 单例沙箱：记账代替拍照

Proxy 出现后，不再需要全量快照——在 `set` 陷阱里**顺手记账**，失活时只撤销记过的账：

> 摘自 `./code/sandbox-lab/proxy-single.cjs`

```js
class ProxySandbox {
  constructor() {
    this.fakeWindow = Object.create(null)
    this.added = new Map()
    const added = this.added
    this.proxy = new Proxy(this.fakeWindow, {
      set(target, key, value) {
        added.set(key, value)
        target[key] = value
        return true
      },
      deleteProperty(target, key) {
        delete target[key]
        added.delete(key)
        return true
      },
    })
  }

  activate() {
    // 激活：把本应用上次写入的属性恢复到沙箱全局
    for (const [k, v] of this.added) this.fakeWindow[k] = v
  }

  deactivate() {
    // 失活：把本应用写入的属性全部撤销，全局回到干净状态
    for (const k of this.added.keys()) delete this.fakeWindow[k]
  }
}
```

> 摘自 `./code/sandbox-lab/run.cjs`

```js
const box1 = new ProxySandbox()
box1.activate()
box1.proxy.token = 't1'
box1.proxy.theme = 'dark'
console.log('写入后    :', JSON.stringify(box1.fakeWindow))
box1.deactivate()
console.log('失活后    :', JSON.stringify(box1.fakeWindow))
assert.equal(Object.keys(box1.fakeWindow).length, 0)
assert.equal(box1.added.get('token'), 't1')  // 记录还在，可随时恢复
box1.activate()
assert.equal(box1.fakeWindow.token, 't1')    // 激活即恢复
box1.deactivate()
```

记账的开销与子应用写入次数成正比，与全局大小无关——这是它对快照方案的实质改进。但它依然是**单例**：`fakeWindow` 只有一份，还是要靠"同一时刻只有一个应用激活"来保证正确性。

## 四、Proxy 多例沙箱：一人一份 fakeWindow

qiankun 2.x 与 micro-app 的做法：每个应用一份自己的 `fakeWindow`，用原型链挂到共享全局上——读不到时回落原生 API，写永远只写自己那份：

> 摘自 `./code/sandbox-lab/proxy-multi.cjs`

```js
const sharedGlobal = Object.create(globalThis)

function createSandbox(name) {
  const fakeWindow = Object.create(sharedGlobal)
  fakeWindow.__MICRO_APP_NAME__ = name
  return new Proxy(fakeWindow, {
    get(target, key) {
      // 读：优先读自己的，读不到沿原型链回落到共享全局
      return target[key]
    },
    set(target, key, value) {
      // 写：永远只写进自己的 fakeWindow，共享全局不动
      target[key] = value
      return true
    },
  })
}
```

多例沙箱天然支持**多应用同时在线**，不需要激活/失活还原：

```
场景三 · Proxy 多例沙箱
A.count = 1 · B.count = 100
  ✓ 各写各的互不可见，读共享回落原生 API
```

要注意原型链回落的一处坑：`in` 判断与 `for...in` 会穿透到共享全局，真实的 qiankun 还会对 `document`、`location` 这类对象做**代理白名单**，防止子应用绕过沙箱直接摸到真全局。

## 五、样式隔离

JS 沙箱解决了 `window`，样式互串要另想办法，共三条路线：

**1. Shadow DOM**：浏览器原生隔离，样式天然不外泄。代价是弹窗、拖拽层等挂在 `document.body` 上的元素会**逃出** Shadow 边界，需要配合弹窗重挂载：

> 示意片段（无配套脚本）

```html
<!-- 宿主容器 -->
<div id="micro-app"></div>
<script>
  const host = document.getElementById('micro-app')
  const shadow = host.attachShadow({ mode: 'open' })
  shadow.innerHTML = `
    <style>.card { color: red }</style>  <!-- 只作用于 shadow 内部 -->
    <div class="card">子应用内容</div>
  `
</script>
```

**2. 选择器前缀（scoped）**：给每条规则加上应用前缀。真实框架在构建期用 CSS Modules / postcss 做，实验台里有一个运行时教学版：

> 摘自 `./code/sandbox-lab/style-scope.cjs`

```js
function scopeStyle(css, scope) {
  return css.replace(/([^{}]+)\{/g, (m, sel) => {
    const s = sel.trim()
    if (s.startsWith('@')) return m        // @media / @keyframes 不加前缀
    const scoped = s.split(',').map((part) => `${scope} ${part.trim()}`).join(', ')
    return `${scoped} {`
  })
}
```

```
场景四 · 样式隔离（选择器前缀）
[data-app=main] .card { color: red }[data-app=main] .btn, [data-app=main] .link { margin: 0 }
@media (min-width: 768px) {[data-app=main] .card { font-size: 16px } }
  ✓ 普通选择器加前缀，@规则原样保留
```

**3. 动态样式表切换**：给每个应用的 `<style>`/`<link>` 打上应用标记，切换应用时整批启停。实现简单，但切走后弹出的元素会丢样式。

| 方案 | 隔离强度 | 主要代价 | 代表 |
|---|---|---|---|
| Shadow DOM | 强（浏览器级） | 弹窗逃逸、全局样式不可达 | micro-app |
| 选择器前缀 | 中（构建期约定） | 需要处理 `@规则`、伪元素 | qiankun 实验性 |
| 动态样式表 | 中（整批启停） | 卸载后新元素丢样式 | qiankun 默认 |

## 六、DOM 隔离与副作用清理

- **DOM 隔离**：容器式方案要求子应用渲染进指定容器（如 `#micro-app`），查 `document.querySelector` 时应限制在容器内查——qiankun 对 `document` 做代理，把 `querySelector`/`createElement` 重定向到容器或假文档。
- **副作用清理**：子应用挂载期间申请的定时器、事件监听、被劫持的 `fetch` 必须在卸载时撤销。做法是在沙箱里拦截 `setInterval`/`addEventListener` 并记账，`unmount` 时统一回滚——和 Proxy 沙箱"记账"是同一套思路，记的对象从"属性"换成了"副作用"。

## 七、三种 JS 沙箱对比

| 维度 | 快照沙箱 | Proxy 单例 | Proxy 多例 |
|---|---|---|---|
| 兼容性 | ES5 即可 | 需要 Proxy（IE11 不支持） | 需要 Proxy |
| 同一时刻应用数 | 1 个 | 1 个 | 多个 |
| 恢复开销 | 全量 diff | 只撤销写入 | 无需恢复 |
| 全局逃逸风险 | 高（直接写真全局） | 中 | 低（写进自己那份） |
| 代表实现 | qiankun legacy | qiankun 1.x | qiankun 2.x / micro-app |

选型结论：新项目一律用 **Proxy 多例**；需要兼容 IE11 的存量系统只能退回快照，并接受"同时只能跑一个子应用"的限制。

## 小结

- 沙箱与隔离机制
  - 隔离对象：`window` 运行时、样式表、DOM 查询、定时器与监听器等副作用
  - 快照沙箱：激活拍快照、失活 diff 还原；简单可靠，但同时只能跑一个应用
  - Proxy 单例：`set` 陷阱记账代替全量快照，开销与写入次数成正比
  - Proxy 多例：一人一份 `fakeWindow` + 原型链回落共享全局，支持多应用并存
  - 样式隔离：Shadow DOM（强但有弹窗逃逸）、选择器前缀（scoped）、动态样式表（整批启停）
  - 副作用清理：拦截定时器/监听器/劫持并记账，卸载时统一回滚
