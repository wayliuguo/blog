# 微前端方案全景与选型

> 上一站[渲染架构](/frontend/进阶/渲染架构/全景)解决"一个应用怎么渲染"，这一站解决"多个独立交付的应用怎么长成一个页面"。本板块所有实战共用一个统一工程 `mf-workspace`：一个 Vue 宿主 + 一对子应用（Vue 订单列表、React 订单详情），**同一业务场景跑通五种接线**，每章的四层结构（入门/进阶/实战/最小实现）都绑定它。

## 一张对比表定乾坤

五种方案的全部差异，都能从这张表推出来。先记表，后面每章都是在放大其中一列：

| 维度 | iframe | qiankun | micro-app | wujie | Web Components |
|---|---|---|---|---|---|
| 接入形态 | 原生标签 | 生命周期协议 + 容器 div | `<micro-app>` 标签 | `<WujieVue>` 组件 | 自定义元素标签 |
| 子应用改造 | 零 | **必须**导出 bootstrap/mount/unmount | 近零（Vite 加 `esm` 属性） | 零 | 各自构建成元素产物 |
| JS 隔离 | **最强**（独立文档） | Proxy 代理沙箱（可逃逸） | with+Proxy（可逃逸） | **iframe 运行时**（最强） | 无（同文档） |
| 样式隔离 | 天然 | strictStyleIsolation/实验性 | scopecss 自动前缀 | shadow DOM | shadow DOM |
| 通信 | postMessage | initGlobalState | data 属性 + dispatch | props + bus | attribute + CustomEvent |
| 性能 | 差（整页上下文） | 中 | 中 | 好（保活可秒开） | 好 |
| 弹窗/路由穿越 | 处处是墙 | 需逐个修 | 需逐个修 | **天然支持**（iframe 身份） | 在宿主文档内，无墙 |
| 体积负担 | 无 | single-spa ~40KB | ~70KB | ~90KB | 零运行时 |

> 配套工程把五种接线跑在同一条业务流（点订单 → 详情联动）上，你可以逐个页面对比"同一个动作五种写法"：`./code/mf-workspace/` 的 `host/src/views/` 五个视图就是五套接线的全部宿主代码。

## 怎么选：三条硬边界

1. **要"彻底防串"选 iframe**。子应用是三方系统/遗留系统/安全边界严格的系统，不值得为性能冒被污染的险。代价是弹窗遮罩、路由同步、登录态处处要桥接——[iframe 方案](/frontend/进阶/微前端体系/iframe%20方案)一章把这个代价算清楚。
2. **要"改造成本最低"选 micro-app 或 wujie**。子应用团队不愿导出生命周期时（大多数真实团队如此），qiankun 的强制协议是最大阻力。micro-app 用标签化接入、wujie 用 iframe 保活兜底，都接近零改造。
3. **要"长期演进"选 Web Components**。没有框架绑定、产物即标准标签，但生态最薄：弹窗、路由、状态管理全要自己补。它是 micro-app 的原理原型，也常作为"平台级底座"的终态。

**qiankun 的位置**：它是事实标准（生态、文档、坑的资料都最多），适合"子应用团队愿意配合协议"的中大型组织。注意 single-spa 生命周期协议是它的核心资产也是它最大改造成本。

## 统一实战工程怎么用

```cmd
cd code/mf-workspace/host && npm install --ignore-scripts && npm run dev
cd code/mf-workspace/vue-sub && npm install --ignore-scripts && npm run dev
cd code/mf-workspace/react-sub && npm install --ignore-scripts && npm run dev
```

打开 `http://127.0.0.1:3030`，顶部导航在五种方案间切换。事件日志面板会记录每一次跨应用通信走过的通道——五方案共用同一中枢状态 `hostState.selectedId`，谁改了它、通过哪条通道改的，一目了然。

子应用侧有一个跨方案通用的关键文件：环境探测 + 通道切换（同一个点击动作在五种环境下走五条不同通道，但只走一条）：

> 摘自 `./code/mf-workspace/vue-sub/src/env.ts`

```ts
export function reportSelect(orderId: string) {
    // 一个动作按当前环境选择唯一通道，避免双重上报；事件名统一为 order-select
    const env = detectEnv()
    switch (env) {
        case 'qiankun':
            qiankunStateSetter?.({ selectedId: orderId })
            break
        case 'micro-app':
            window.microApp!.dispatch({ type: 'order-select', orderId })
            break
        case 'wujie':
            window.$wujie!.bus.$emit('order-select', orderId)
            break
        case 'iframe':
            window.parent.postMessage({ type: 'order-select', orderId }, '*')
            break
        default:
            // bubbles + composed：作为自定义元素运行时穿透 shadow DOM 边界冒泡到宿主
            window.dispatchEvent(new CustomEvent('order-select', { detail: { orderId }, bubbles: true, composed: true }))
    }
}
```

> 这份 `switch` 就是本板块的目录：五种 case 各展开成一章，每章回答同一个问题——"这条通道的沙箱、通信、资源加载分别怎么实现、代价是什么"。
