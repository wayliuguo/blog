# 微前端方案全景与选型

微前端要解决的问题很具体：一个几十万行的巨石前端应用，多人团队改一处、构建十分钟、上线一锅端，历史包袱永远甩不掉。微前端的做法是把应用**按业务拆成多个独立开发、独立部署、独立运行**的子应用，由一个容器应用把它们拼在同一个浏览器页面里。本文先讲清"为什么需要"，再过一遍三类方案与主流实现的决策矩阵，最后给一份"微前端不是银弹"的代价清单。

## 一、为什么需要微前端

判断要不要上微前端，看的是这四个痛点占了几条：

> 示意片段（无配套脚本）

```
巨石应用之痛                     微前端后的形态
├── 构建 10+ 分钟            →   子应用独立构建，分钟级
├── 一个包改一处发全量        →   子应用独立部署，互不影响
├── 技术栈锁死（不敢升级）    →   Vue / React / Angular 共存
├── 团队职责边界模糊          →   按业务域划仓库与发布节奏
```

注意反过来也成立：如果只是"代码多"，模块化 + 代码分割就能解决；**只有"多团队 × 多技术栈 × 独立发布"同时出现**时，微前端才值得付出它的架构成本。

## 二、三类方案：路由分发式 / 微件式 / 容器式

**1. 路由分发式**：最朴素的做法——不同路由指向不同部署，靠 Nginx 或网关把 `/app-a/**` 转发到 A 的服务。页面级整合，每次跳转都是整页刷新。

> 示意片段（无配套脚本）

```
Nginx
├── /            → 容器/门户
├── /app-a/**    → 子应用 A 的静态资源
└── /app-b/**    → 子应用 B 的静态资源
```

优点是零侵入、天然隔离；缺点是切换体验割裂、无法共享登录态之外的任何东西、没有"应用内嵌页面局部"的能力。

**2. 微件式（Widget）**：子应用作为页面上的**一个局部区块**嵌入，主页面可以混排多个子应用。Web Components（自定义元素 + Shadow DOM）是浏览器原生的实现路径：

> 示意片段（无配套脚本）

```js
// 子应用把自己注册成自定义元素，主页面像用 div 一样用它
customElements.define('user-card', class extends HTMLElement {
  connectedCallback() {
    this.attachShadow({ mode: 'open' })
    this.shadowRoot.innerHTML = '<user-panel></user-panel>'
  }
})
```

适合"把第三方能力嵌进我的页面"（如客服组件、图表卡片），不适合承载完整路由级应用。

**3. 容器式**：当前主流。一个容器应用负责**布局、路由分发、生命周期调度、沙箱与通信**，子应用在运行时被加载进容器的指定区域。qiankun、micro-app、wujie 都属于这一类，也是本模块后面几篇的主角。

## 三、iframe：被低估又被滥用的方案

iframe 是浏览器原生的"微前端"——JS、CSS、DOM 全都硬隔离。但为什么大型方案都不选它？

| 维度 | 表现 |
|---|---|
| 隔离 | ✅ 完全隔离，浏览器级 |
| 接入成本 | ✅ 几乎为零，任何应用都能丢进去 |
| URL 状态 | ❌ 刷新后 iframe 内路由丢失，需手动同步 |
| 弹窗/遮罩 | ❌ `alert`、弹层困在 iframe 里，跨出边界要 `postMessage` 桥 |
| 性能 | ❌ 每个iframe 是独立文档上下文，内存与首屏开销成倍 |
| 通信 | ❌ 只能 `postMessage`，序列化开销大且难调试 |

结论：**一次性接入第三方异构系统时 iframe 依然是最快路径**；但要主子应用协同运作（共享状态、联合路由、统一弹窗），iframe 的"墙"就成了障碍。wujie 的思路正是"iframe 负责 JS 隔离 + web components 负责渲染"，把墙补掉一部分。

## 四、决策矩阵：qiankun vs Module Federation vs Web Components

| 维度 | qiankun | micro-app | wujie | Module Federation | Web Components |
|---|---|---|---|---|---|
| 定位 | 容器式框架 | 容器式（组件化接入） | 容器式（iframe+WC 混合） | 构建期模块共享 | 浏览器原生微件 |
| 技术栈约束 | 无 | 无 | 无 | 需构建工具支持 | 无 |
| JS 隔离 | Proxy 沙箱 | Proxy 沙箱 | iframe 原生 | ❌ 无（同页面执行） | Shadow DOM 天然 |
| 样式隔离 | 动态样式表/前缀 | Shadow DOM 可选 | iframe+WC 原生 | ❌ 无 | Shadow DOM |
| 依赖共享 | ❌ 各带各的 | ❌ | ❌ | ✅ shared 协商 | ❌ |
| 接入成本 | 中（生命周期改造） | 低（类 WebComponent 用法） | 中 | 低（配置声明） | 高（需自己封装） |
| 适用场景 | 多团队中后台平台 | 渐进式接入、组件级复用 | 强隔离诉求+性能敏感 | 多应用共享依赖、微模块 | 嵌入式小组件 |

选型经验法则：

- **中后台多团队平台**（布局 + 权限 + 路由分发）→ qiankun / micro-app 一类容器框架
- **多个应用要共享同一份 React/lodash，且都走同一套构建链** → Module Federation，它解决的是"依赖共享"而不是"隔离"
- **只想嵌一个卡片/组件** → Web Components，别上框架
- **接一个完全不可控的第三方老系统** → iframe / wujie

## 五、微前端不是银弹：代价清单

上微前端前，把这五笔账算清楚：

> 示意片段（无配套脚本）

```
代价清单
├── 复杂度上移     ：容器要管路由分发、生命周期、沙箱、通信——这套基建本身
│                   就是一个需要维护的"中间件层"
├── 公共依赖重复   ：不配共享策略，React 被主应用和 3 个子应用各打一份
├── 样式/全局一致性：隔离做太狠，UI 规范和主题难以统一
├── 调试链路变长   ：问题横跨主应用与子应用，source map 与日志要打通
└── 版本兼容矩阵   ：主容器协议一升级，所有子应用都要回归
```

行业里的共识是：**微前端是组织架构问题的技术解**——团队按业务域拆了，应用才值得拆。只有一两个开发者维护的系统上微前端，得到的是纯开销。
