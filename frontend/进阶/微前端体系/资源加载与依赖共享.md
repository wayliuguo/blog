# 资源加载与依赖共享

容器式微前端在运行时把子应用"拉进"页面，这引出两个工程问题：**怎么加载**（HTML entry 的解析与依赖抓取）和**怎么共享**（React 被主应用和三个子应用用到，凭什么只下载一份）。本文先走通远程加载流程，再深入 Module Federation 的 shared 版本协商——配套实验台 `mf-demo` 用零依赖脚本把协商算法跑给你看。

## 一、远程加载流程：从 entry 到可运行

容器加载一个子应用的完整链路：

> 示意片段（无配套脚本）

```
容器决定加载 appA
   │
   ① 拉 entry（HTML 或 manifest）
   │     HTML entry：拿到完整 HTML，解析出 <script>/<link>/<style>
   │     JS entry ：直接拿 JS，样式需另行打包
   ② 解析依赖清单（import maps / externals / manifest.exposes）
   ③ 逐个拉取 JS 与 CSS（命中缓存则跳过网络）
   ④ 执行：JS 放进沙箱、CSS 按样式隔离策略挂载
   ⑤ 调用生命周期：bootstrap → mount
```

**HTML entry 与 JS entry** 的取舍：HTML entry（qiankun 默认）能顺带把样式、首屏占位一起带来，接入成本低；JS entry（micro-app 部分场景、纯 MF 模块）更轻但要自己解决样式随行。实验台里用 manifest 模拟了这个流程，重点看**缓存**——同一个 url 全生命周期只拉一次：

> 摘自 `./code/mf-demo/loader.cjs`

```js
function loadModule(url) {
  // 先查缓存：同一个 url 全生命周期只拉一次
  if (cache.has(url)) return { url, fromCache: true, code: cache.get(url) }
  const code = fetch(url)
  if (!code) throw new Error(`module not found: ${url}`)
  cache.set(url, code)
  return { url, fromCache: false, code }
}
```

> 摘自 `./code/mf-demo/run.cjs`

```js
const loader = createLoader()
const m1 = loader.loadManifest('appA')
console.log('manifest  :', JSON.stringify(m1))
const btn = loader.loadModule(m1.exposes['./Button'])
console.log('首次加载  :', JSON.stringify(btn))
assert.equal(btn.fromCache, false)
const btn2 = loader.loadModule(m1.exposes['./Button'])
assert.equal(btn2.fromCache, true)
const appB = loader.loadManifest('appB')
loader.loadModule(appB.exposes['./Card'])
const s = loader.stats()
console.log('统计      :', JSON.stringify(s))
assert.equal(s.cached, 2)     // appA-button + appB-card 各缓存一份
assert.equal(s.fetchCount, 4) // 2 次 manifest + 2 次模块首次加载
```

```
场景三 · 远程模块加载流程
manifest  : {"entry":"appA.js","exposes":{"./Button":"appA-button.js"}}
首次加载  : {"url":"appA-button.js","fromCache":false,"code":"define(\"appA/Button\")"}
统计      : {"fetchCount":4,"cached":2}
  ✓ 同 url 只拉一次，缓存命中后 0 网络开销
```

## 二、公共依赖为什么值得共享

不共享时，每个子应用独立打包，`react + react-dom`（约 140KB min+gzip）会被打进每一份产物。主应用 1 份 + 3 个子应用 4 份 = **560KB 的重复下载与 5 份 React 在内存里各持一套 hooks 状态**。共享的收益分两层：

- **网络层**：公共依赖只下载一次，进 HTTP 缓存后所有应用复用
- **运行层**：同一份 React 实例意味着 hooks 状态、Context、事件系统全局唯一——不共享时跨应用的 Context 根本打不通

但共享有前提：**版本必须谈得拢**。这就是 Module Federation 的 shared 协商。

## 三、Module Federation 的 shared 版本协商

MF 构建时每个应用声明两件事：我**提供**哪些共享包（`shared` + 版本），我**需要**哪些共享包（`requiredVersion` 范围）。运行时容器维护一个共享作用域（shared scope），协商规则一句话：**从高到低找一个同时满足所有消费方约束的版本，找到了就全场共用一份；找不到就按约束分组、各组各带各的（fallback）**。

实验台实现了这个协商的最小版本（只支持 `^` 范围与精确版本）：

> 摘自 `./code/mf-demo/negotiate.cjs`

```js
function negotiate(sharedScope, providers, consumers) {
  // sharedScope: { react: ['17.0.2', '18.2.0'] } —— 共享层里实际有哪些版本
  // consumers:   [{ app: 'appA', deps: { react: '^18.0.0' } }, ...]
  const result = {}
  for (const dep of Object.keys(sharedScope)) {
    const ranges = consumers
      .filter(c => c.deps[dep])
      .map(c => ({ app: c.app, range: c.deps[dep] }))
    const versions = sharedScope[dep]
    // 从高到低找一个同时满足所有消费方约束的版本
    const picked = versions
      .slice()
      .sort((a, b) => (a < b ? 1 : -1))
      .find(v => ranges.every(r => satisfies(v, r.range)))
    if (picked) {
      result[dep] = { picked, copies: 1, satisfied: ranges.map(r => r.app) }
    } else {
      // 协商失败：按约束分组，各组各加载一份（fallback）
      const groups = {}
      for (const r of ranges) {
        const ok = versions.filter(v => satisfies(v, r.range)).sort((a, b) => (a < b ? 1 : -1))[0]
        const key = ok || 'none:' + r.range
        ;(groups[key] = groups[key] || { version: ok, apps: [] }).apps.push(r.app)
      }
      result[dep] = { picked: null, copies: Object.keys(groups).length, groups }
    }
  }
  return result
}
```

两组实测（`node run.cjs`）：

```
场景一 · shared 版本协商（成功）
react     : {"picked":"18.2.0","copies":1,"satisfied":["appA","appB"]}
  ✓ 两个消费方共用 18.2.0 一份

场景二 · shared 版本协商（失败 fallback）
react     : {"picked":null,"copies":2,"groups":{"17.0.2":{"version":"17.0.2","apps":["legacy"]},"18.2.0":{"version":"18.2.0","apps":["modern"]}}}
  ✓ 没有公共版本，17/18 各加载一份，互不串用
```

注意协商失败的代价不是报错而是**多份副本**：React 17 和 18 各加载一份，内存与体积回到不共享的状态——所以共享策略要求**公共依赖的大版本尽量对齐**。

## 四、构建期与运行期协同

依赖共享横跨两个阶段，各管一半：

| 阶段 | 做什么 | 谁负责 |
|---|---|---|
| 构建期 | 把 shared 依赖**外置**（不打进业务产物），产出各版本独立 chunk + 版本清单 | Webpack ModuleFederationPlugin / Vite 插件 |
| 运行期 | 容器拉各应用的版本清单，做 shared 协商，按协商结果只加载需要的 chunk | 容器运行时 |

三个工程要点：

- **单例语义**：React、状态管理这类带全局状态的包必须 `singleton: true`——宁可版本不满足也要只留一份（MF 会告警而不是加载第二份）；
- **严格版本 vs 共享**：`requiredVersion` 填太宽（如 `*`）协商省事但容易踩不兼容 bug；太窄则频繁 fallback，共享形同虚设。实践是主应用定基准版本、子应用范围从宽（`^`）；
- **去重的度量**：上线后用构建产物分析（bundle-analyzer）核对"React 出现几次"，协商表里 `copies` 是否为 1——`mf-demo` 场景一的 `copies: 1` 就是这个指标的模型。
