## 1. 跨端框架原理

与基础板块 `浏览器渲染原理` 的边界：基础讲「页面在浏览器里怎么渲染」，本模块讲「**同一套前端代码怎么跑到非浏览器宿主里**，以及宿主差异带来的工程题」。整套跨端技术可归纳为一条知识主线：**三条路线 → 桥的设计 → 桥换到桌面进程 → 进程分工与通信**——任何路线都绕不开同一个问题：**逻辑层与渲染层之间那座桥怎么设计？**

### 1.1 三条渲染路线：UI 由谁画

跨端方案看似繁多，本质区别只有一个问题——**JS（或 Dart）描述的 UI 由谁画出来**：

| 路线 | 代表 | UI 由谁画 | 特点 |
| ---- | ---- | ---- | ---- |
| WebView 容器 | Cordova、小程序 | 系统 WebView | 复用 Web 全生态，受 WebView 性能上限 |
| 原生渲染 | RN、Weex | 映射成原生控件 | 体验接近原生，但要付通信成本 |
| 自绘引擎 | Flutter | 自带渲染管线，不依赖平台控件 | 像素级一致，包体积大、动态化弱 |

选型本质在「生态复用 / 体验上限 / 动态化」三点间权衡：

```
高频交互重体验  → 选 自绘（Flutter）/ 原生渲染（RN）
内容型求迭代    → 选 容器（WebView）
同 App 混用     → 容器 + RN 并存是常态，非全局最优
```

**追问**：Flutter 为什么一致性好但热更新难？——不走 JS 引擎，产物是编译后的机器码，缺 JS 动态下发执行的法律与技术通道。

### 1.2 老架构 Bridge：异步序列化与排队

老架构的 Bridge 是**异步消息 + JSON 序列化**的桥，调用要过完整流水线：

```
JS 调用 → JSON.stringify 编码 → 原生侧解码 → 处理 → 编码回传 → JS 解码 → Promise 落定
        （两次编解码 + Promise 包装 + 消息队列排队）
```

代价有两处：

- **只能异步**：同步拿不到返回值，布局这类需要同步测量的 API 在老架构根本做不出来。
- **序列化有损**（`cross-lab/jsi.cjs` 实测）：`Date` 退化为字符串、**函数被静默丢弃**。

### 1.3 新架构 JSI：同步直通零序列化

新架构的 **JSI** 让 JS 直接持有 Native 对象的引用，同步直通调用、零序列化。实测（`cross-lab/jsi.cjs`，2 万次调用）：

```
bridge  72.6ms
jsi      1.3ms   约 58×
```

关键工程点：

- JSI 是 C++ 层、**JS 引擎无关**（Hermes/JSC/V8 都能接）；
- 配套瘦身：TurboModules 按需加载、Fabric 同步渲染。

**追问**：序列化丢函数意味着什么？→ 回调不能直接过桥，只能靠 `callbackId` 在桥两侧各持半张表关联——这就是 3.3 回调表设计的由来。

### 1.4 小程序双线程与 setData 铁律

小程序采用**双线程**（逻辑层 JS 引擎 + 渲染层 WebView，Native 转发），动机是**安全管控**——渲染层拿不到 BOM/DOM，逻辑层碰不到页面。代价是**过桥数据必须可序列化**，通信成为第一性能瓶颈。

`setData` 三条铁律（`cross-lab/twin.cjs` 实测）：

- **合并成一帧**：同一 tick 的多次 setData 合并，同 key 取最后一次；
- **只传变化**：消息里只有本次传入的数据，路径写法只通信变化的叶子；
- **不可过桥的类型**：函数无法过桥、`Date` 退化为字符串。

边界：`this.data` 是**同步更新**的（本地立即可读），通信是**异步**的——不要连续 setData 依赖「渲染已完成」。长列表优化：分页 append 只传新增段、路径写法更新单叶子、避免把整棵大对象重新 set 上桥。

### 1.5 Flutter 三棵树

```
Widget（配置）       声明要什么、怎么配，轻量、可频繁重建
   └─ 转成 ...
Element（复用/diff） 维护实例与配对，diff 在这里发生
   └─ 挂载到 ...
RenderObject（布局绘制）真正画出来，持有尺寸、布局、绘制
```

三棵树分工：**配置 → 复用/diff → 布局绘制**，做到「声明式写 UI、命令式只改最底层真正变化的部分」。

## 2. Hybrid 与 WebView 深度优化

容器路线的账本：把「白屏」拆成三段独立成本，分别用预热、离线包、预渲染对应消除，**三段优化可叠加**。

### 2.1 白屏时间线：三段独立成本

```
t0 取容器创建起点
  ├─ 容器创建   200~500ms      → 预热消除
  ├─ 网络往返   取决于资源      → 离线包消除
  └─ 首屏渲染   取决于页面      → 预渲染消除
```

三段成本**独立、可叠加**——只优化一段，另两段仍卡住白屏；三段齐做才能系统性提速。

### 2.2 容器预热：空闲换时间

在空闲期把 WebView 容器提前创建好、放进池子，点击时直接取用。实测（`cross-lab/webview.cjs`）：

```
空闲期预创建  付 8 单位（成本先置换）
点击取用      0 单位（几乎瞬时）
池空          冷启动兜底
```

预热工程要点：

- **时机**：首帧渲染完成后才触发，别抢首屏资源；
- **池容量**：2~3 个就够（Android 空 WebView 占 30~50MB，池大就是内存浪费）；
- **复用而非销毁**：页面关闭后把容器归还池中 `release`，避免反复创建。

### 2.3 离线包：可控缓存与安全校验

离线包是「**可控的缓存**」：与 WebView 自管的 HTTP 缓存不同（不可控、可能被逐出），离线包由容器全权管理、随包版本可控失效。

离线包三件配套：

- **拦截点**：Android 是 `shouldInterceptRequest`，iOS 是 `WKURLSchemeHandler`；
- **差量更新**：下发走版本清单 + 差量包（全量的 10%~20%），合成后校验整体 hash 再切换生效；
- **静默下发**：后台静默流水式下发，不阻塞用户。

**安全校验**：每个本地文件带 hash 签名，拦截命中后**先校验再用**；签名不符**拒用本地、回退在线请求**。实测（`cross-lab/webview.cjs`）：篡改包内容但不改签名 → 请求立即回退在线，`networkHits` 加一。注意离线包只解决静态资源，接口数据要走预取。

### 2.4 预渲染与白屏分段监控

预渲染把**壳 + 首屏提前到点击前**：

```
只做高概率入口  避免对所有页面预渲染浪费内存
设超时回收      超过时限强制回收，空转的白屏 WebView 是内存黑洞
```

**白屏分段监控是一切优化的前提**——分段数据都没有就是在猜：t0 取容器创建起点，按容器 / 网络 / 渲染三段上报归因。没有分段数据，无法判断优化到底落在哪一段。

## 3. JSBridge 设计与演进

容器里最核心的基础设施是**桥**本身。JSBridge 是「同步语法与异步执行的矛盾」反复博弈的产物——这句矛盾贯穿三代演进。

### 3.1 三代机制演进

```
第一代  URL Scheme 拦截    把调用编码进 URL 拼给原生，原生解码分发
第二代  原生注入 API       原生往 JS 上下文注入全局方法，JS 直接调
第三代  注入 + 协议化       注入消息通道 + 标准化协议（module/method + callbackId）
```

进化方向是「从协议字符串到真实对象再到标准化协议」，同步语法 (调用时有返回值姿势) 与底层异步执行 (Native 回不去同步) 的矛盾始终要靠回调机制弥合。

### 3.2 通信协议：module / method / callbackId

一条消息的骨架：

```
module/method   命名空间：route 到哪个模块的哪个方法
callbackId      关联异步回复的凭证，随消息带上桥
encodeURIComponent  消息体编码，编解码严格对称（编码端和解码端必须配套）
```

协议的价值在「对称」：只要有 JS 和 Native 两侧同构的编解码，任意调用都能落到同一套契约上展开。

### 3.3 回调表、批量与超时兜底

**回调表**：`callbackId` 关联异步回复，桥两侧各持半张表。铁律是**一次性、用后即清**：

- 正常回复 → 执行回调后从表里删除；
- **重复触发同一 callbackId** → 直接报错（协议被破坏的信号）。

**超时兜底**（`cross-lab/bridge.cjs` 实测）：Native 不回复（崩溃 / 超时 / 丢消息）时回调表只进不出——这就是**桥上的内存泄漏**。兜底是每个 API 设超时，超时 `reject` 并从表里清理该项，实测超时后 `callbacks.size === 0`。超时按 API 类别分级：读配置几百 ms、支付类放宽到数十秒；**超时不等于失败**，回复晚到要能静默丢弃。

**批量合并**（`cross-lab/bridge.cjs` 实测）：高频埋点调用容易拥堵通道——同 tick 入队批量 flush（三次调用一条消息）+ 队列长度阈值 + `visibilitychange` 时强制 flush 防丢尾部数据。

### 3.4 安全边界

```
origin 白名单   拒绝非授权来源调用，白名单外的访问直接拒绝
Native 侧重参数校验  宿主侧对入参做校验，不信任 JS 传来的任何数据
敏感 API 原生确认    涉及系统能力的关键 API 由原生显式弹窗/确认，不静默放行
```

一句话：**JS 侧不可信，所有防线都在 Native 侧重置，敏感操作要真人确认。**

## 4. Electron 与桌面端

桥的思路换到桌面：**两个进程怎么安全地分工与通信**。

### 4.1 进程模型：主 / 渲染分工

```
主进程      单个，跑 Node，拥有完整系统能力，收拢所有系统操作
渲染进程    多个，每个窗口一个，跑 Chromium，承载不可信前端内容
```

分工原则：**系统能力收拢进主进程**，渲染进程只做界面展示、接受受限能力。这样即使渲染层被攻破（XSS），攻击者也没有直接的系统权限。

### 4.2 IPC 与 contextBridge 安全基线

**IPC 走 `invoke` / `handle`**：Promise 往返；未注册的 channel **明确 `reject`，不静默返回 undefined**——静默无响应的 IPC 是排查地狱，开发期炸出来、生产期按 channel 白名单拒绝。

**安全基线**：`contextIsolation: true` + `nodeIntegration: false` + contextBridge 白名单暴露。渲染层看到的**不是整个 Node，而是主进程愿意给的少数几个函数**：

- contextBridge 只把 `expose: true` 的 API 挂上 `window.desktop`；
- **未暴露的能力在渲染层根本不存在**（实测：`exec` 查无此键）；
- 老项目 `nodeIntegration: true` 一次 XSS 就全盘沦陷。

### 4.3 asar 归档与包体积账

- **asar 是归档不是加密**：可被解包，压缩内层还有 unpack 可读区——敏感逻辑放主进程或服务端，不指望 asar 保密；
- **体积来源**：每平台都要捆绑 Chromium + Node，所以单个安装包 80~100MB；
- **应对**：增量更新只下 diff，把包体从 100MB 降到几 MB。

### 4.4 更新状态机与桌面特有账

桌面端不能像 Web 一样「刷新即上线」——代码运行在用户本机磁盘，替换正在运行的程序有**原子性问题**，必须重启生效。更新走状态机（`cross-lab/electron.cjs` 实测）：

```
版本比对 → 下载 → hash 校验 → 校验成功落盘/失败回滚不落盘 → 重启切换入口

正常     新版本正常落盘
up-to-date  版本相同，跳过
verify-failed  校验 hash 不符 → 回滚不落盘，本地保持不变
```

原则：**宁可停在旧版本，不能让损坏 / 被篡改的包污染本机**。边界：双版本目录 + 重启切换入口，失败可回退旧目录。

**桌面特有账**（与纯 Web 不同）：

```
多窗口内存  每个窗口一份渲染进程内存，窗口数即内存账
单实例锁    防止同一 App 启动多份，抢文件/资源
离线可用    桌面天然离线，需设计离线姿态
双端崩溃上报  主进程 + 渲染进程各自崩溃路径都要上报
```

## 5. 最小实现

### 5.1 cross-lab 五探针实验台

**`cross-lab`**：零依赖探针实验台，把本模块每个「结论」都落到可 `node:assert` 自检的实测脚本上，全绿绿灯即证明结论成立。

```
node run.cjs   依次执行五探针，node:assert 自检全绿

探针一  bridge.cjs      Bridge vs JSI 开销与序列化有损（Date 退化、函数丢弃）
探针二  bridge.cjs      桥协议 / 回调表 / 批量合并 / 白名单安全
探针三  webview.cjs     预热池 / 离线包命中与回退
探针四  twin.cjs        双线程 setData 合并与只传变化
探针五  electron.cjs    IPC / contextBridge 白名单 / 更新状态机回滚
```
