# 跨端框架原理

「一套代码跑多端」从来不是免费的：省下的是多团队的人力，付出的是通信层、渲染层与平台能力的折价。这一篇把主流跨端方案放进同一个坐标系里比较，并用 `cross-lab` 的零依赖探针把「Bridge 为什么慢、JSI 快在哪、双线程通信的硬约束是什么」变成可实测的证据。

## 一、跨端的三条技术路线

> 示意片段（无配套脚本）

```
WebView 容器（Cordova / 小程序）     ：原生壳 + WebView 渲染 H5
原生渲染  （React Native / Weex）    ：JS 写逻辑，UI 映射成原生控件
自绘引擎  （Flutter）                ：自带渲染引擎直接画，不依赖平台控件
```

| 路线 | 渲染方式 | 生态/语言 | 体验上限 | 代表代价 |
| --- | --- | --- | --- | --- |
| WebView 容器 | WebView 里的 DOM | Web 全生态 | 受 WebView 性能上限 | 通信桥 + 首屏慢（见下一篇） |
| 原生渲染 | 原生 UI 控件 | JS/React | 接近原生 | JS↔Native 通信成本 |
| 自绘引擎 | 自带引擎直接绘制 | Dart | 最一致（跨平台像素级） | 包体积大、动态化弱 |

三条路线的本质区别只有一个问题：**JS（或 Dart）代码的 UI 描述，最终由谁画出来？** 由 WebView 画、由原生控件画、还是由自己的引擎画。而所有路线共同的难点是——**逻辑层与渲染层不在同一个运行时里，中间必须有一座桥**。

## 二、老架构 Bridge：异步消息 + JSON 序列化

React Native 老架构（0.68 之前）的 Bridge 是典型的「消息总线」：JS 侧拿不到 Native 对象，只能把调用打包成一条**可序列化的消息**丢进队列，Native 侧取出、解析、执行，结果再序列化回来。用探针把这条链路模拟出来：

> 摘自 `./code/cross-lab/jsi.cjs`

```js
// JS 侧拿不到 Native 对象，只能发一条可序列化的消息：
// stringify（JS 出口）→ parse（Native 入口）→ 执行 → 结果再走一遍反方向。
function createLegacyBridge(native) {
  let nextId = 1
  return {
    invoke(module, method, params) {
      const payload = JSON.stringify({ id: nextId++, module, method, params })
      const decoded = JSON.parse(payload) // 模拟 Native 侧反序列化
      const result = native[module][method](decoded.params)
      return Promise.resolve(JSON.parse(JSON.stringify(result))) // 结果回程再编解码
    },
  }
}
```

序列化不只是慢，还会**丢信息**——JSON 只认六种值：

> 摘自 `./code/cross-lab/jsi.cjs`

```js
const src = { when: new Date(0), fn: () => 1, ok: 1 }
const viaBridge = JSON.parse(JSON.stringify(src))
assert.equal(typeof viaBridge.when, 'string', 'Date 经 JSON 退化为字符串')
assert.ok(!('fn' in viaBridge), '函数被 JSON 静默丢弃')
```

这解释了老架构 RN 的一批「做不到」：`measure` 这类需要**同步返回**布局的 API 无法实现（消息是异步的）；回调函数传不过去（序列化丢弃）；大批量数据滚动时通信拥堵（每帧都在排队过桥）。

## 三、新架构 JSI：把「消息」变成「调用」

RN 新架构的 JSI（JavaScript Interface）换了一个思路：不传消息了，让 JS **直接持有 Native 对象的引用**。JSI 是一层 C++ 抽象，向下适配任意 JS 引擎（Hermes / JSC / V8），向上把 Native 能力注册成 host object——JS 侧调用它就是一次同步的 C++ 直通调用，零序列化：

> 摘自 `./code/cross-lab/jsi.cjs`

```js
// JS 侧直接持有 Native 对象的代理（JSI::HostObject），
// 方法调用是同步的 C++ 直通调用，参数按原样传递，零序列化。
function createJsiBinding(native) {
  return new Proxy(native, {
    get(target, module) {
      return target[module] // 直接是 Native 侧函数引用
    },
  })
}
```

两种模型的实测差距（Node 22，`node ./code/cross-lab/jsi.cjs`，2 万次「读设备信息」调用）：

> 摘自 `./code/cross-lab/jsi.cjs`

```js
console.log(`探针二  : ${N} 次调用 —— bridge ${bridgeMs.toFixed(1)}ms vs jsi ${jsiMs.toFixed(1)}ms（${(bridgeMs / jsiMs).toFixed(0)}×）`)
```

实测：bridge 72.6ms vs jsi 1.3ms，**约 58 倍**。差距主要来自三处：两次 JSON 往返、Promise 包装、消息队列排队。JSI 直通后，同步 API（同步测量布局、同步取值）成为可能，列表滚动这类高频通信也不再拥堵。

配套的新架构还有两块：**TurboModules**（Native 模块按需初始化，不再启动时全量注册）与 **Fabric**（渲染器支持同步渲染、优先级调度）。

## 四、小程序：双线程模型的取舍

小程序走了第四条路：**逻辑层与渲染层物理分离**。逻辑层跑在一个独立的 JS 引擎里（iOS JSCore / Android V8），渲染层是多个 WebView，两者之间由 Native 做消息转发。这个设计的动机是**安全管控**：渲染层拿不到 BOM/DOM，逻辑层碰不到页面，运营者的代码被沙箱在一个受控环境里。

代价同样落在通信上——**过桥的数据必须可序列化**：

> 摘自 `./code/cross-lab/twin.cjs`

```js
// 渲染层收到的是 flush 出来的「一帧」消息；过桥必须序列化，
// 所以 flush 里做一次 JSON 往返——这正是双线程通信的硬约束。
class NativeBridge {
  constructor() { this.sent = [] }
  flush(pending) {
    if (pending.size === 0) return
    const data = JSON.parse(JSON.stringify(Object.fromEntries(pending)))
    this.sent.push({ from: 'logic', data })
    pending.clear()
  }
}
```

`setData` 是这套模型的核心 API，两条铁律都能从探针里读出来。第一条：**同一 tick 的多次 setData 合并成一帧**，同 key 取最后一次：

> 摘自 `./code/cross-lab/twin.cjs`

```js
page.setData({ title: 'a' })
page.setData({ count: 1 })
page.setData({ title: 'b' }) // 同 tick 覆盖
page.$applyFrame()

assert.equal(bridge.sent.length, 1, '一帧只发一条消息')
assert.deepEqual(bridge.sent[0].data, { title: 'b', count: 1 })
```

第二条：**消息里只有本次传入的部分**——用路径写法更新一个叶子，未变化的兄弟数据不会跟着过桥：

> 摘自 `./code/cross-lab/twin.cjs`

```js
page.setData({ 'user.name': 'wu' }) // 路径写法：只更新一个叶子
page.$applyFrame()

assert.equal(bridge.sent.length, 1)
assert.deepEqual(bridge.sent[0].data, { 'user.name': 'wu' })
assert.ok(!('list' in bridge.sent[0].data), '未变化的 list 不通信')
```

这就是「少传数据、只传变化」这条小程序性能军规的由来：每次 setData 都是一次序列化 + 一次跨线程转发 + 一次渲染层 diff，传多了全链路都疼。

## 五、Flutter：自绘引擎与三棵树

Flutter 不映射平台控件，而是自带渲染管线（Skia，新版 Impeller）直接绘制，因此能做到跨平台**像素级一致**。它的核心是三棵树：

> 示意片段（无配套脚本）

```
Widget（配置，不可变，每帧可以重建）
  ▼
Element（实例 + 状态，持有生命周期，尽量复用）
  ▼
RenderObject（布局 / 绘制 / 命中测试，最重，跨帧复用）
```

Widget 声明「界面长什么样」，Element 是它在树中的常驻实例（diff 就发生在这里——`runtimeType` 与 `key` 都相同则复用），RenderObject 才真正参与布局绘制。声明式 + 不可变 Widget + Element 复用，让「每帧重建 Widget 树」不会引发昂贵的重排——这与前端虚拟 DOM 的分层思路同构。

对比项上 Flutter 的取舍也很清晰：体验一致性最好、包体积最大（要打一个引擎进去）、动态化最弱（不走 JS 引擎，热更新受平台政策限制）。

## 工程含义清单

| 决策点 | 原理（对应实测/机制） |
| --- | --- |
| 高频通信的数据要精简 | Bridge/双线程每次通信都付序列化成本（§二、§四） |
| 回调、Date 等不可 JSON 化的值别过桥 | 序列化有损：函数丢弃、Date 退化（§二、§四） |
| 连续 setData 合并到一帧 | 消息按 tick flush，同 key 取最后一次（§四） |
| 用路径写法更新叶子 | setData 增量语义：只有传入的数据过桥（§四） |
| 需要同步 Native 能力时选新架构 | JSI 直通调用，同步 API 成为可能（§三） |
| 追求跨平台像素一致选自绘 | Flutter 不依赖平台控件，代价是包体积与动态化（§五） |

## 小结

- 跨端框架原理
  - 三条路线：WebView 容器 / 原生渲染 / 自绘引擎，本质区别是「UI 由谁画」
  - 老架构 Bridge：异步消息 + JSON 序列化，两次编解码 + Promise 包装 + 队列排队
  - 序列化有损实测：Date 退化为字符串、函数被静默丢弃
  - JSI 实测：2 万次调用 bridge 72.6ms vs jsi 1.3ms（约 58×），同步直通零序列化
  - 小程序双线程：逻辑层与渲染层分离，安全管控换来通信成本；setData 合并成一帧、只传变化
  - Flutter 三棵树：Widget（配置）→ Element（复用/diff）→ RenderObject（布局绘制）
