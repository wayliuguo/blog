# 跨端渲染架构全景

> 本篇是板块地图：一张对比表 + 一条决策树，帮你定位到正确的选型章。各路线的机制深化在对应章节完成。

## 一、一张对比表：UI 描述最终由谁画出来？

四条路线的本质区别只有一个问题：**JS（或 Dart）写下的 UI 描述，最终由谁渲染？**

| 路线 | 渲染方式 | 语言/生态 | 体验上限 | 核心代价 | 代表 |
| --- | --- | --- | --- | --- | --- |
| WebView 容器 | WebView 里的 DOM | Web 全生态 | 受 WebView 性能上限 | 通信桥 + 首屏慢 | Hybrid、小程序 |
| 原生渲染 | JS 描述 → 映射成原生控件 | JS/React | 接近原生 | JS↔Native 通信成本 | React Native |
| 自绘引擎 | 自带引擎（Skia/Impeller）直接画 | Dart | 跨平台像素级一致 | 包体积大、动态化弱 | Flutter |
| 桌面双进程 | Chromium 渲染 + Node 主进程 | JS/TS 全栈 | 等同 Web | 内存与包体积（捆绑 Chromium） | Electron |

所有路线共同的难点是同一件事：**逻辑层与渲染层不在同一个运行时里，中间必须有一座桥**。桥的设计（序列化 vs 直通、同步 vs 异步、白名单）决定了每条路线的性能与安全上限——这也是本板块三条主线的交汇点：

- **React Native**：桥从「JSON 消息总线」演进到「JSI 直通调用」，见 [React Native](./React%20Native.md) §2.1
- **Hybrid/JSBridge**：桥是一套完整的调用协议（回调表/超时/批量/白名单），见 [Hybrid 与 JSBridge](./Hybrid%20与%20JSBridge.md)
- **Electron**：桥收拢成 IPC + contextBridge 白名单，见 [Electron](./Electron.md)

## 二、统一业务场景：三端同一个订单工作台

本板块三个实战工程承载**同一个业务**——订单列表 + 详情 + 状态推进，与渲染架构、微前端板块的订单场景同构，方便横向对比同一件事在不同容器里的写法与代价：

| 工程 | 技术栈 | 实跑状态 | 对应章节 |
| --- | --- | --- | --- |
| `code/rn-app` | RN 0.73 + FlatList | ✅ Metro 全量编译（842KB bundle）；设备层需真机 | React Native |
| `code/flutter-app` | Flutter 3.x + ListView.builder | ⚠️ 完整代码交付，未实跑（环境配置见工程 README） | Flutter |
| `code/electron-app` | Electron 33 + IPC | ✅ 烟雾测试全过（真实窗口 + 主进程数据层） | Electron |
| `code/cross-lab` | 零依赖 Node 探针 | ✅ 7 探针全过 | 各章「最小实现」小节 |

## 三、选型决策树

> 示意片段（无配套脚本）

```
要做的东西跑在哪？
├─ 桌面（Windows/macOS）
│   ├─ 团队是 Web 栈，需要系统级能力（托盘/文件/自更新）→ Electron
│   └─ 只要一个"网页套壳"，无系统能力 → 直接发 PWA/链接
├─ 移动 App
│   ├─ 团队是 React 栈 / 需要动态化（热更新）→ React Native
│   ├─ 追求跨平台 UI 像素一致 / 重图形动效 → Flutter
│   └─ 预算只够一套 Web，可接受体验折损 → Hybrid（WebView 容器）
└─ 已有 App 只嵌内容页
    └─ Hybrid + 离线包（成本最低，见 Hybrid 与 JSBridge 篇）
```

两条高频误判：**"性能不够所以上原生"**——多数列表页的性能瓶颈是通信数据量与首屏资源，先看 Hybrid 与 JSBridge 篇的优化清单再决定；**"Flutter 一定能统一三端"**——动态化弱（不走 JS 引擎，热更新受平台政策限制）是硬约束，依赖热更新的业务要避开。
