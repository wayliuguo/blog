## 知识主线（一句话）

本模块回答「同一套前端代码怎么跑到非浏览器宿主里」：从三条跨端路线的取舍（WebView 容器 / 原生渲染 / 自绘引擎），到容器路线绕不开的白屏三段优化（预热 / 离线包 / 预渲染），再到两端之间那座桥的设计（JSBridge 协议与回调表），最后落到桌面端 Electron 的进程分工与安全基线——只要两端之间有通信，桥的性能与安全就是共同主线。

## 高频核心点

### 01 跨端框架原理

**三条路线**

- WebView 容器（Cordova/小程序）/ 原生渲染（RN/Weex）/ 自绘引擎（Flutter）——本质区别是「UI 由谁画」
- 选型在三者间权衡：生态复用 / 体验上限 / 动态化

**老架构 Bridge vs 新架构 JSI**

- 老 Bridge：异步消息 + JSON 序列化，两次编解码 + Promise 包装 + 队列排队
- 序列化有损：Date 退化为字符串、函数被静默丢弃
- JSI 实测：2 万次调用 bridge 72.6ms vs jsi 1.3ms（约 58×），同步直通零序列化

**小程序双线程与 Flutter 三棵树**

- 逻辑层与渲染层分离，安全管控换来通信成本；setData 合并成一帧、只传变化
- Flutter 三棵树：Widget（配置）→ Element（复用/diff）→ RenderObject（布局绘制）

### 02 Hybrid 与 WebView 深度优化

**白屏三段成本**

- 容器创建（200~500ms）/ 网络往返 / 首屏渲染，三段独立可叠加

**预热 / 离线包 / 预渲染**

- 容器预热实测：空闲期预创建付 8 单位、点击取用 0 单位、池空冷启动兜底；预热池 2~3 个、release 复用而非销毁
- 离线包实测：命中 0 网络、未命中在线兜底、签名不符拒用；配套 shouldInterceptRequest / WKURLSchemeHandler + 差量更新 + 静默下发
- 预渲染：只做高概率入口 + 超时回收；白屏分段监控是一切优化的前提

### 03 JSBridge 设计与演进

- 三代机制：URL Scheme 拦截 → 原生注入 API → 注入 + 协议化；同步语法与异步执行的矛盾贯穿始终
- **协议**：module/method 命名空间 + callbackId + encodeURIComponent，编解码严格对称
- **回调表**：callbackId 关联异步回复，一次性用后即清，重复触发报错
- **Promise 化 + 超时兜底**：超时 reject 且回调表清空，防桥上泄漏
- **批量合并**：同 tick 三次调用一条消息，空队列不发
- **安全**：origin 白名单拒绝非授权调用，Native 侧重做参数校验，敏感 API 原生确认

### 04 Electron 与桌面端

**进程模型与安全基线**

- 单主进程（Node，系统能力收拢）+ 多渲染进程（Chromium，不可信内容隔离）
- 安全基线 = contextIsolation + 禁 nodeIntegration + contextBridge 白名单暴露
- invoke/handle 实测：未注册 channel 明确 reject，不静默

**工程账**

- asar 是归档不是加密；体积来源是每平台捆绑的 Chromium + Node（80~100MB）
- 更新状态机实测：版本比对 → 下载 → hash 校验失败回滚不落盘 → 重启切换
- 桌面特有账：多窗口内存、单实例锁、离线可用、双端崩溃上报
