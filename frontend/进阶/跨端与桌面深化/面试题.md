## 一、基础概念

### Q1: 跨端方案三条路线的本质区别是什么？怎么选？（第 1 篇）

- **结论**：WebView 容器、原生渲染、自绘引擎的区别只有一个问题——**JS（或 Dart）描述的 UI 由谁画出来**。选型在「生态复用 / 体验上限 / 动态化」三点之间做权衡。
- **原理**：WebView 容器复用 Web 全生态但受 WebView 性能上限；原生渲染（RN）把 UI 映射成原生控件，体验接近原生但要付通信成本；自绘引擎（Flutter）自带渲染管线不依赖平台控件，像素级一致但包体积大、动态化弱。
- **边界**：没有全局最优——高频交互重体验选自绘/原生渲染，内容型页面求快速迭代选容器；同一 App 内混用（容器 + RN）是常态。
- **追问**：Flutter 为什么一致性好但热更新难？→ 不走 JS 引擎，产物是编译后的机器码，缺 JS 动态下发执行的法律与技术通道。

## 二、机制与原理

### Q2: RN 老 Bridge 为什么慢？新架构 JSI 快在哪？（第 1 篇）

- **结论**：老 Bridge 每次调用都要 JSON 序列化往返 + Promise 包装 + 消息排队，且只能异步；JSI 让 JS 直接持有 Native 对象引用，同步直通调用零序列化。
- **原理**：实测（`cross-lab/jsi.cjs`，2 万次调用）——bridge 72.6ms vs jsi 1.3ms，约 58 倍。序列化还有损：Date 退化为字符串、函数被静默丢弃，所以同步测量布局这类 API 在老架构根本做不出来。
- **边界**：JSI 是 C++ 层、JS 引擎无关（Hermes/JSC/V8 都能接）；配套 TurboModules 按需加载、Fabric 同步渲染。
- **追问**：序列化丢函数意味着什么？→ 回调不能直接过桥，只能靠 callbackId 在桥两侧各持半张表关联——这就是 JSBridge 回调表设计的由来。

### Q3: 小程序为什么用双线程？setData 有什么性能铁律？（第 1 篇）

- **结论**：双线程（逻辑层 JS 引擎 + 渲染层 WebView，Native 转发）的动机是**安全管控**——渲染层拿不到 BOM/DOM，逻辑层碰不到页面。代价是过桥数据必须可序列化，通信成为第一性能瓶颈。
- **原理**：实测（`cross-lab/twin.cjs`）——同一 tick 的多次 setData 合并成一帧、同 key 取最后一次；消息里只有本次传入的数据，路径写法只通信变化的叶子；函数无法过桥、Date 退化为字符串。
- **边界**：`this.data` 是同步更新的（本地立即可读），通信是异步的——不要连续 setData 依赖「渲染已完成」。
- **追问**：长列表怎么优化 setData？→ 分页 append 只传新增段、用路径写法更新单叶子、避免把整棵大对象重新 set 上桥。

### Q5: 离线包怎么保证安全？被篡改了怎么办？（第 2 篇）

- **结论**：每个本地文件带 hash 签名，拦截层命中后**先校验再用**；签名不符拒用本地、回退在线请求。
- **原理**：实测（`cross-lab/webview.cjs`）——篡改包内容但不改签名，请求立即回退在线，networkHits 加一。离线包下发走版本清单 + 差量包（全量的 10%~20%），合成后校验整体 hash 再切换生效。
- **边界**：拦截点 Android 是 `shouldInterceptRequest`，iOS 是 `WKURLSchemeHandler`；离线包只解决静态资源，接口数据要走预取。
- **追问**：离线包和 HTTP 缓存什么关系？→ 缓存由 WebView 自管、不可控且可能被逐出；离线包由容器全权管理、随包版本可控失效——是「可控的缓存」。

### Q7: Electron 的安全基线是什么？（第 4 篇）

- **结论**：`contextIsolation: true` + `nodeIntegration: false` + contextBridge 白名单暴露——渲染层看到的不是「整个 Node」，而是主进程愿意给的少数几个函数。
- **原理**：主进程（Node 完整环境）收拢系统能力，渲染进程跑不可信内容；contextBridge 只把 `expose: true` 的 API 挂上 `window.desktop`，未暴露的能力在渲染层根本不存在（实测：`exec` 查无此键）。IPC 走 invoke/handle，未注册 channel 明确 reject 不静默。
- **边界**：老项目 `nodeIntegration: true` 一次 XSS 就全盘沦陷；asar 是归档不是加密，可被解包——敏感逻辑放主进程或服务端。
- **追问**：为什么未注册的 channel 要报错而不是返回 undefined？→ 静默无响应的 IPC 是排查地狱；开发期炸出来、生产期按 channel 白名单拒绝。

## 三、排障与选型

### Q6: JSBridge 的回调表为什么会泄漏？怎么兜底？（第 3 篇）

- **结论**：Native 不回复（崩溃/超时/丢消息）时回调表只进不出——这就是桥上的内存泄漏；兜底是每个 API 设超时，超时 reject 并从表里清理该项。
- **原理**：实测（`cross-lab/bridge.cjs`）——超时后 `callbacks.size === 0`；正常回复的调用走「用后即清」，重复触发同一 callbackId 直接报错（协议被破坏的信号）。
- **边界**：超时按 API 类别分级——读配置几百 ms，支付类放宽到数十秒；超时不等于失败，回复晚到要能静默丢弃。
- **追问**：高频埋点调用怎么防止通道拥堵？→ 同 tick 入队批量 flush（实测三次调用一条消息）+ 队列长度阈值 + `visibilitychange` 时强制 flush 防丢尾部数据。

## 四、场景设计题

### Q4: H5 页嵌进 App 白屏一秒起步，怎么系统性优化？（第 2 篇）

- **结论**：把白屏拆成三段独立成本——容器创建（200~500ms）、网络往返、首屏渲染——分别对应预热、离线包、预渲染，三段优化可叠加。
- **原理**：实测（`cross-lab/webview.cjs`）——预热池空闲期预创建付 8 单位、点击取用 0 单位、池空冷启动兜底；离线包命中 0 网络、未命中在线兜底。
- **边界**：预热池 2~3 个就够（Android 空 WebView 占 30~50MB）；离线包必须有在线兜底；预渲染只做高概率入口并设超时回收——内存换时间不能无代价。
- **追问**：优化怎么验证有效？→ 白屏分段监控：t0 取容器创建起点，按容器/网络/渲染三段上报归因，没有分段数据就是在猜。

### Q8: 桌面端自动更新怎么做才能不把用户更新坏？（第 4 篇）

- **结论**：状态机四步——检查清单版本比对 → 下载 → **hash/签名校验 → 失败回滚不落盘** → 重启切换入口。宁可停在旧版本，不能让损坏/被篡改的包污染本机。
- **原理**：实测（`cross-lab/electron.cjs`）——新版本正常落盘；版本相同 up-to-date；下载内容与清单 hash 不符时返回 verify-failed，本地版本保持不变。
- **边界**：增量更新（只下 diff）把包体从 100MB 降到几 MB；双版本目录 + 重启切换入口，失败可回退旧目录。
- **追问**：为什么桌面端不能像 Web 一样「刷新即上线」？→ 代码运行在用户本机磁盘上，替换正在运行的程序有原子性问题——所以必须重启生效，且切换入口要可回退。
