# 模块面试题 · 跨端与桌面深化

## 1. 跨端渲染架构全景

### Q1（全景）｜ 跨端四条路线的本质区别是什么？怎么选？

- **判断**：四条路线的区别只有一个问题——**JS（或 Dart）描述的 UI 由谁画出来**；选型在「生态复用 / 体验上限 / 动态化」三点间权衡。
- **展开**：

```
WebView 容器    UI 由系统 WebView 画     → 复用 Web 生态、受 WebView 性能上限
原生渲染 RN      UI 映射成原生控件        → 接近原生、付 JS↔Native 通信成本
自绘引擎 Flutter  UI 由自带渲染管线画      → 像素级一致、包体大、动态化弱
桌面双进程 Electron → Chromium 渲染 + Node 主进程 → 等同 Web、捆绑 Chromium
```

高频交互重体验选自绘/原生；内容型页面求快速迭代选容器；桌面系统级能力选 Electron。所有路线共同的难点：逻辑层与渲染层不在同一运行时，**中间必须有一座桥**。
- **边界**：没有全局最优；追问「Flutter 为什么一致性好但热更新难」→ AOT 产物是编译后机器码，运行时没有 JS 引擎可承载下发逻辑。

### Q2（全景）｜ "性能不够所以上原生"这个判断对吗？

- **判断**：多数情况下不对——列表页的性能瓶颈通常是**通信数据量与首屏资源**，先做容器优化再决定换技术栈。
- **展开**：Hybrid 的三段白屏成本（容器/网络/渲染）各有独立武器（预热/离线包/预渲染），三段叠加后多数内容页够用；换栈的真实理由通常是**体验上限**（复杂手势、动效、原生转场）而非平均性能。
- **佐证**：`cross-lab/webview.cjs` 实测预热池——空闲期付 8 单位、点击取用 0 单位；离线包命中 0 网络。
- **边界**：重交互页面（复杂手势、长列表、动效）WebView 上限确实顶不住，该换就换；判断依据是白屏分段监控的数据，不是感觉。

## 2. React Native

### Q3（RN）｜ 老 Bridge 为什么慢？新架构 JSI 快在哪？

- **判断**：老 Bridge 每次调用 JSON 序列化往返 + Promise 包装 + 消息排队、只能异步；JSI 让 JS 直接持有 Native 对象引用，同步直通调用零序列化。
- **展开**：老桥「JS 编码 → 原生解码 → 处理 → 编码回传 → JS 解码」，两次编解码 + 队列排队；序列化还有损——`Date` 退化字符串、函数被静默丢弃。JSI 是 C++ 层、JS 引擎无关（Hermes/JSC/V8 都能接）；配套 TurboModules 按需加载、Fabric 同步渲染。
- **佐证**：`cross-lab/jsi.cjs` 实测 2 万次调用——bridge 235.4ms vs jsi 2.2ms，约 105 倍（量级稳定在两位数倍）。
- **边界**：追问「序列化丢函数意味着什么」→ 回调不能直接过桥，只能靠 callbackId 在桥两侧各持半张表关联——这正是 JSBridge 回调表的由来。

### Q4（RN）｜ "RN 的 JS 每帧重渲染，原生层会不会跟着重建？"

- **判断**：不会——JS 侧 diff 出**最小指令集**下发给原生层，类型不变的控件只更新变化的 props。
- **展开**：RN 本质是「JS 维护描述树 + Native 持有控件树 + 中间 diff」。同类型走 props 级 diff；类型变化才触发子树 REMOVE + CREATE（React remount 语义）。这也是 FlatList 有效的原理基础——虚拟化在 JS 层裁剪描述树，原生层指令自然最少。
- **佐证**：`cross-lab/mapper.cjs` 实测——首帧 6 条指令（3 CREATE + 3 UPDATE 整树创建），第二帧改一个文字只有 **1 条 UPDATE**，第三帧 Text→Image 触发 REMOVE + CREATE。
- **边界**：追问「diff 在哪一层」→ 新架构在 Fabric 的 C++ 渲染器；老架构在 JS 侧 shadow tree。追问「key 的作用」→ 同层同 type 下的对位凭证，丢了 key 退化成按位对齐。

## 3. Flutter

### Q5（Flutter）｜ 三棵树各自负责什么？为什么每帧重建 Widget 不卡？

- **判断**：Widget 是不可变配置（每帧重建，廉价）；Element 是常驻实例（diff 发生在 `canUpdate`：runtimeType+key 相同即复用）；RenderObject 负责布局绘制（最重，跨帧复用）。
- **展开**：声明式 + 不可变 Widget + Element 复用，让「每帧重建 Widget 树」不会引发昂贵重排——与前端虚拟 DOM 分层同构。RenderObject 只在类型变化时才重建。
- **佐证**：`cross-lab/three-trees.cjs` 实测三帧——同类型换配置：Element 复用、RenderObject 不动；类型变化才整链重建。
- **边界**：追问「和虚拟 DOM diff 的区别」→ Flutter 的 Widget 不可变，比较只需看 type+key 两个判据，比可变对象 diff 简单得多；追问「key 什么时候必须给」→ 列表重排/条件插入时防 Element 错位复用。

### Q6（Flutter）｜ Flutter 动态化弱，"弱"在哪？技术根源是什么？

- **判断**：发布期 AOT 把 Dart 编译成平台机器码，**运行时没有 JS 引擎**可承载下发的逻辑代码——热更新（绕应用商店的代码下发）在 Flutter 上缺乏技术通道，且触碰平台政策红线。
- **展开**：对比 RN 的动态化路线：JS 产物（源码或 Hermes 字节码）由 App 内嵌引擎解释执行，可随包下发替换；Flutter 的 UI 由 AOT 机器码驱动，改代码 = 重新发版。Shorebird 等方案本质是打补丁（patch Dart bytecode），能力边界远小于 RN 的热更新。
- **佐证**：Dart 双编译模式——开发期 JIT（热重载毫秒级）与发布期 AOT 是两套产物，运行时形态不可互换。
- **边界**：依赖热更新的业务（运营活动、AB 实验频繁）要么选 RN/Hybrid，要么把动态部分做成服务端配置驱动；追问「UI 物料化呢」→ 下发配置由固定代码解释是安全的，下发可执行逻辑不是。

## 4. Electron

### Q7（Electron）｜ Electron 的安全基线是什么？

- **判断**：`contextIsolation: true` + `nodeIntegration: false` + contextBridge 白名单暴露——渲染层看到的不是整个 Node，而是主进程愿意给的少数几个函数。
- **展开**：主进程（Node 完整环境）收拢系统能力，渲染进程跑不可信内容；preload 是唯一合法的桥；IPC 走 invoke/handle，未注册 channel **明确 reject 不静默**。
- **佐证**：`cross-lab/electron.cjs` 实测——`expose: false` 的 `exec` 在渲染层查无此键；electron-app 烟雾测试验证真实窗口 + IPC 数据层全链路。
- **边界**：asar 是归档不是加密、可被解包——敏感逻辑放主进程或服务端；追问「为什么未注册 channel 要报错」→ 静默无响应没法排查，宁可开发期炸出。

### Q8（Electron）｜ CI 或沙箱里 electron 命令跑不起来/行为像纯 Node，为什么？

- **判断**：环境里设了 `ELECTRON_RUN_AS_NODE=1`——electron.exe 退化为纯 Node，`require('electron')` 返回的是**路径字符串**而非 API 对象，`ipcMain`/`app` 全是 undefined。
- **展开**：该变量本意是让 Electron 二进制当 Node 用（如运行构建脚本），CI 镜像与沙箱常全局设置。Electron 只检查「变量是否定义」，**置空串无效**，必须从环境里彻底移除（`env -u ELECTRON_RUN_AS_NODE`）。
- **佐证**：本仓库 electron-app 实测——带变量跑烟雾测试直接 `TypeError: Cannot read properties of undefined (reading 'handle')`；`env -u` 后 4/4 通过。
- **边界**：排查口诀——Electron 环境下 `typeof require('electron') === 'object'`，纯 Node 下是 `'string'`；同族坑还有 `ELECTRON_NO_ATTACH_CONSOLE` 等影响输出的变量。

### Q9（Electron）｜ 桌面端自动更新怎么做才能不把用户更新坏？

- **判断**：状态机四步——检查清单版本比对 → 下载 → **hash/签名校验，失败回滚不落盘** → 重启切换入口；宁可停在旧版本，不能让损坏/被篡改的包污染本机。
- **展开**：增量更新（只下 diff）把包体从 100MB 降到几 MB；双版本目录 + 重启切换入口，失败可回退旧目录。桌面代码运行在用户本机磁盘，替换运行中的程序有原子性问题，必须重启生效。
- **佐证**：`cross-lab/electron.cjs` 实测——新版本正常落盘；版本相同 `up-to-date`；hash 不符返回 `verify-failed`，本地版本不变。
- **边界**：连续更新失败要有熔断与回滚预案；追问「为什么不用 Web 那套刷新」→ 渲染层可以热刷新，但主进程与原生模块更新必须重启。

## 5. Hybrid 与 JSBridge

### Q10（Hybrid）｜ H5 页嵌进 App 白屏一秒起步，怎么系统性优化？

- **判断**：把白屏拆成三段独立成本——容器创建（200~500ms）/ 网络往返 / 首屏渲染——分别对应预热、离线包、预渲染，三段可叠加。
- **展开**：预热在空闲期预创建容器进池、点击取用；离线包由容器全权管理、命中零网络；预渲染把壳 + 首屏提前到点击前，只做高概率入口并设超时回收。
- **佐证**：`cross-lab/webview.cjs` 实测——预热付 8 单位、取用 0 单位、池空冷启动兜底；离线包命中 0 网络、未命中在线兜底。
- **边界**：预热池 2~3 个就够（Android 空 WebView 占 30~50MB）；预渲染不设回收就是内存黑洞；追问「怎么验证有效」→ 白屏分段监控，t0 取容器创建起点，按段上报归因。

### Q11（JSBridge）｜ JSBridge 的回调表为什么会泄漏？怎么兜底？

- **判断**：Native 不回复（崩溃 / 超时 / 丢消息）时回调表**只进不出**——这就是桥上的内存泄漏；兜底是每 API 设超时，超时 reject 并从表里清理。
- **展开**：callbackId 关联异步回复、桥两侧各持半张表；铁律是一次性、用后即清——**重复触发同一 callbackId 直接报错**（协议被破坏的信号）。高频埋点防拥堵：同 tick 入队批量 flush + 队列阈值 + `visibilitychange` 强制 flush。
- **佐证**：`cross-lab/bridge.cjs` 实测——超时后 `callbacks.size === 0`；同 tick 三次调用合并一条消息。
- **边界**：超时按 API 类别分级——读配置几百 ms、支付类数十秒；**超时不等于失败**，回复晚到要能静默丢弃。

### Q12（JSBridge）｜ 桥的安全第一道门是什么？小程序双线程为什么也疼在通信上？

- **判断**：**origin 白名单**——Native 收到调用先校验来源域名再入队；小程序双线程的动机是安全管控（渲染层拿不到 BOM/DOM），代价是过桥数据必须可序列化。
- **展开**：桥是原生能力对 WebView 的授权通道，「谁能过桥」比「怎么过桥」更重要——白名单按模块细分（支付 API 只允许收银台域名）、参数 Native 侧重校验、敏感 API 原生二次确认、注入选 postMessage 型杜绝反射攻击。小程序 setData 两条铁律：同 tick 合并一帧同 key 取最后、路径写法只传变化叶子。
- **佐证**：`cross-lab/bridge.cjs` 实测 `evil.example` 被拒；`cross-lab/twin.cjs` 实测同 tick 三次 setData 合并一帧、`{ 'user.name': 'wu' }` 时 list 不通信。
- **边界**：追问「setData 铁律怎么推出来的」→ 每次 setData = 一次序列化 + 一次跨线程转发 + 一次渲染层 diff，合并与增量都是为了少付这三笔；「少传数据、只传变化」军规的由来。
