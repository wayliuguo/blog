# 渲染引擎

## 一、入门：从「写组件」到「解释 schema」

写业务页面时，组件树是你手写的 JSX/模板；低代码渲染引擎把这个动作反过来——**组件树存在 schema 里，你写的是「解释器」**。心智迁移有三条：

- **渲染 = 求值 + 递归**：业务渲染由框架 diff 驱动，引擎渲染是「schema 节点 → 求值表达式 → 递归子树」，条件、循环、插值都是表达式求值的特例；
- **用户的输入不可信**：schema 里的表达式是运营写的，不是你写的——`window`、`process` 一律要挡在沙箱外，这是业务前端没有的攻击面；
- **更新粒度自己负责**：框架 diff 帮业务页面兜底，引擎没有这层兜底——「改一个属性全量重渲染」就是编辑器卡顿的头号原因，按脏子树更新要自己做。

## 二、表达式沙箱：先关住门，再谈能力

低代码里用户一定会写表达式（条件、插值、循环数据源）。表达式一旦能碰到 `window`/`document`/`process`，就等于把站点交给用户——这是搭建平台最典型的安全事故面。做法是用 `with` + `Proxy` 把所有标识符先过一道闸：

> 摘自 `./code/lowcode-lab/render.cjs`

```js
// 低代码里用户会写表达式，而表达式一旦能碰到 window/document，就等于把站点交给用户。
function evaluate(expr, scope) {
  const guard = new Proxy(scope, {
    has: () => true, // 让 with 把所有标识符都交给下面的 get 处理
    get: (t, k) => {
      // with 语句会先查 Symbol.unscopables，symbol 键必须放行，否则连合法表达式都跑不起来
      if (typeof k === 'symbol') return t[k]
      if (!(k in t)) throw new Error(`表达式禁止访问：${String(k)}`)
      return t[k]
    }
  })
  const fn = new Function('__scope', `with (__scope) { return (${expr}); }`)
  return fn(guard)
}

{
  assert.equal(evaluate('state.count > 2', { state: { count: 3 } }), true)
  assert.equal(evaluate('item.name', { item: { name: 'a' } }), 'a')
  assert.throws(() => evaluate('window.location', { state: {} }), /表达式禁止访问/)
  assert.throws(() => evaluate('process.exit(1)', { state: {} }), /表达式禁止访问/)
  console.log('[1] 表达式沙箱：state/item 可用，window 与 process 一律抛错')
}
```

实测 `state`/`item` 可用，`window`、`process` 一律抛错。三个必须知道的细节：

- `with` 在严格模式下禁用，所以这段代码所在文件**不能**声明 `'use strict'`（探针文件顶部已注明）。
- `with` 会先查 `Symbol.unscopables`，symbol 键必须放行，否则连合法表达式都跑不起来——这是实测踩到的坑。
- 这只是**软沙箱**：`({}).constructor.constructor('return process')()` 这类原型链逃逸依然存在。真正的隔离要靠 Web Worker 或 iframe（配合 `sandbox` 属性），软沙箱用于「防误用 + 拦住绝大多数越界」，不用于对抗恶意用户。

## 三、递归渲染：条件、循环与 props 解析

渲染引擎的核心函数就是一次递归：条件决定「有没有」，循环决定「有几份」，props 决定「长什么样」：

> 摘自 `./code/lowcode-lab/render.cjs`

```js
// 渲染引擎的核心就是把 schema 展开成组件树：条件决定有没有，循环决定有几份。
function resolveValue(v, scope) {
  // 约定：以 state./item./index 开头的字符串视为表达式
  if (typeof v === 'string' && /^(state|item|index)\b/.test(v)) return evaluate(v, scope)
  return v
}

function renderNode(node, scope, stats) {
  stats.visited++
  if (node.when !== undefined && !evaluate(node.when, scope)) return null // 条件不成立 → 整棵剪掉
  const props = Object.fromEntries(Object.entries(node.props || {}).map(([k, v]) => [k, resolveValue(v, scope)]))
  if (node.loop !== undefined) {
    // 循环节点本身还是一个组件（容器），展开的是它的子项
    const items = evaluate(node.loop, scope) || []
    return {
      id: node.id,
      type: node.type,
      props,
      children: items.flatMap((item, index) =>
        (node.children || [])
          .map(c => renderNode(c, { ...scope, item, index }, stats))
          .filter(Boolean)
          .flat()
          .map(n => ({ ...n, id: `${n.id}#${index}` })) // 循环项 id 带下标，保证可定位
      )
    }
  }
  return {
    id: node.id,
    type: node.type,
    props,
    children: (node.children || []).map(c => renderNode(c, scope, stats)).filter(Boolean).flat()
  }
}
```

一份带条件节点和循环节点的 schema，在两种状态下渲染：

> 摘自 `./code/lowcode-lab/render.cjs`

```js
const schema = {
  id: 'page',
  type: 'Page',
  props: {},
  children: [
    { id: 'banner', type: 'Banner', props: { title: '大促', vip: 'state.vip' }, when: 'state.vip' },
    {
      id: 'list',
      type: 'List',
      props: {},
      loop: 'state.items',
      children: [{ id: 'item', type: 'Text', props: { text: 'item.name' } }]
    }
  ]
}

{
  const stats = { visited: 0 }
  const tree = renderNode(schema, { state: { vip: true, items: [{ name: 'a' }, { name: 'b' }] } }, stats)
  assert.equal(tree.children.length, 2)
  assert.deepEqual(tree.children[1].children.map(c => c.props.text), ['a', 'b'])

  const stats2 = { visited: 0 }
  const tree2 = renderNode(schema, { state: { vip: false, items: [{ name: 'a' }] } }, stats2)
  assert.equal(tree2.children.length, 1) // banner 被条件剪掉
  assert.equal(tree2.children[0].id, 'list')
  console.log(`[2] 递归渲染：条件开关生效（顶层 2 → 1 个），循环展开 ${tree.children[1].children.length} 份且 item 变量可见`)
}
```

两个容易做错的点：**循环节点本身仍是容器**（它的子项才被展开 N 份，这也是能让 List 自己控制空态/分页的前提）；**循环项 id 要带下标**，否则 N 个同名 id 会让后续的属性面板和局部更新全部定位错误。

## 四、更新粒度：全量重渲染是最常见的性能坑

编辑器里改一个属性就全量重渲染，页面一大就卡。正确做法是按 id 找到脏节点，只重算它的子树，再把结果拼回原树：

> 摘自 `./code/lowcode-lab/render.cjs`

```js
// 编辑器里拖一下就全量重渲染，页面一大就卡；正确做法是按 id 定位脏节点、只重算它的子树。
function buildIndex(root) {
  const index = new Map();
  (function walk(node) {
    index.set(node.id, node);
    (node.children || []).forEach(walk)
  })(root)
  return index
}

{
  const index = buildIndex(schema)
  const state = { state: { vip: true, items: [{ name: 'a' }, { name: 'b' }] } }
  const all = { visited: 0 }
  renderNode(schema, state, all)
  const patch = { visited: 0 }
  renderNode(index.get('list'), state, patch) // 只有 list 变了
  assert.ok(patch.visited < all.visited)
  console.log(
    `[3] 更新粒度：全量渲染访问 ${all.visited} 个节点，只重算脏子树 ${patch.visited} 个（省 ${
      all.visited - patch.visited
    } 个）`
  )
}
```

实测：全量访问 5 个节点，只重算 list 子树访问 3 个。这个例子只有 5 个节点，实际页面几百个节点时差距是指数级的——**更新粒度是低代码编辑器流畅度的第一生产力**。

配套的三件事：

- **依赖收集**：属性里引用了哪些 `state` 字段要能算出来，state 变了才知道哪些节点脏（表达式 AST 扫描即可）。
- **错误边界**：单个节点渲染失败不能整页白屏，用错误边界组件兜住并保留 id 便于定位。
- **key 稳定**：交给框架的 key 必须是 id（含循环下标），不能是数组索引，否则输入框内容会串位。

## 五、渲染引擎的工程边界

| 议题 | 现实约束 |
| --- | --- |
| 跨框架 | 渲染层要绑定具体框架（React/Vue），协议层必须框架无关——用适配器把「组件树描述」翻译成各框架的 render 函数 |
| 服务端渲染 | schema + state 可在服务端直接渲染出 HTML，天然支持 SSR，但要保证表达式求值无副作用 |
| 出码 | 渲染引擎只服务于「运行时渲染」；「出码」是另一条路径（见下一篇），两者共用同一份协议 |
| 大页面性能 | 长列表虚拟滚动、节点懒渲染、表达式求值缓存（同一表达式同一 state 只算一次） |
| 版本兼容 | 渲染器要拒绝自己不认识的 schema 版本，而不是硬着头皮渲染一半 |

一句话总结边界：**渲染引擎负责「把 schema 变成界面」，不负责「把界面变成代码」**——后者是出码器的事，下一篇讲。

## 工程含义清单

- 表达式必须沙箱化：`with` + Proxy 软沙箱挡住 window/process；真隔离用 Worker/iframe。
- 递归渲染三件事：条件剪枝、循环展开（容器保留、子项带下标）、props 表达式解析。
- 更新粒度按脏节点子树算，配合依赖收集；全量重渲染是编辑器卡顿的头号原因。
- 每个节点要能被 id 定位、被错误边界兜住、被 key 稳定标识。
- 协议层框架无关、渲染层框架相关，两者用适配器解耦。

## 实战：活动页渲染在 mini-lowcode 里的完整链路

统一场景「运营活动页」的渲染三要素在真实工程里对应 `mini-lowcode/src/engine.js` 的三个函数（与探针同源）：

- `evaluate`：`state.vip` 这类表达式的软沙箱求值——属性面板、条件 `when`、循环 `loop` 全走这一个入口；
- `renderNode`：Banner 的 `when: 'state.vip'` 条件剪枝、List 的 `loop: 'state.items'` 循环展开（渲染树保留 `_loop` 标记、子项 id 带 `#index` 下标）；
- 标题栏的「N 节点渲染」计数是 `stats.visited`——把 `state.vip` 从 true 改成 false，这个数字从 8 降到 6，就是「条件剪枝发生在求值之后、子树递归之前」的可视化证据。

动手实验：把 `schema.js` 的 `items` 改成 10 个商品，观察画布与出码预览同步展开 10 份、子项 id 变成 `item#0`~`item#9`——这就是「循环项 id 带下标」在生产交互里的样子。
