## 1. 协议与 schema 设计

回答一个问题：**协议怎么定、schema 怎么设计，才能换来一套从此稳定、够快、可迁移的搭建体系。**

### 1.1 协议分层与四层改动代价

搭建体系按「越靠底层越不能动」分层，整条链路改动代价从贵到便宜：

```
协议 > 渲染 > 编辑器 > 物料
```

- **协议（最贵）**：唯一会被持久化、跨版本存在的东西，数据库里躺着几万份 schema。改协议要写迁移链、兼容老数据、保证老页面不崩。
- **渲染**：改了重新发版即可，代价中等。
- **编辑器**：只影响创作体验，改动影响面更窄。
- **物料（最便宜）**：只影响单个组件。

推论：**协议要最先定稳**。协议一变，存量 schema、渲染器、编辑器、物料全要跟着动；而协议又不可能一次定对，所以**一开始就留版本号字段和迁移链机制**，而不是等第一次大改时临时补救。

### 1.2 节点模型与层级解耦

四篇共用一套节点模型，作为平台的“数据 DNA”：

```
node = {
  id,           唯一标识
  type,         物料类型 / 原生元素
  props,        已拍平属性的子物料 + 表达式
  children,     子节点数组
  when,         条件表达式（布尔，false 时整棵剪掉）
  loop,         循环源数据（数组），子项 id 带下标
}
```

协议的上层还牵涉一套解耦约定：

- **协议层框架无关**：schema 本身不绑死任何 UI 框架。
- **渲染层框架相关**：真正跑起来要落到具体框架（React / Vue…）。
- **两者用适配器解耦**：schema → 组件树的转换集中在一个适配层，协议轻易不动、渲染层可替换。

### 1.3 物料协议：注册表与 props 描述

物料不是散落的组件，而是注册进一张**注册表**；每个物料携带一份 `props` 描述，即“一份描述三用”：

```
props 描述  →  校验（运行时拦截非法值）
            →  属性面板（自动生成编辑项）
            →  文档（自动生成说明）
```

- **名利双收**：props 描述写一次，三个消费方共用，避免三处各维护一份而漂移。
- **校验四类**：必填缺失 / 类型不对 / 枚举越界 / 未注册。未知组件直接拒绝，不静默降级。
- 未注册物料**明确抛错**，是逃生舱的一部分（见 5.2）。

### 1.4 schema 版本迁移

schema 会因协议演进而过时，迁移是**逐级链式**执行，每一级只负责自己那一次变更：

```
v1 → v2 → v3
一级只改一件事：补默认值 / 改字段名 / 清理废弃字段
```

- **幂等**：同一份 schema 迁移两次，结果一致。
- **可回滚**：迁移失败要能停在半路并给出明确错误，而不是写坏一半。
- **实测（`lowcode-lab/schema.cjs`）**：v1 → v3 两级迁移，补默认值 `size=md`；旧字段 `visible` 改写为 `when` 且清理干净。
- **为什么不用一把梭的 v1→v3 大迁移**：存量数据版本分布不可控（可能有 v2 的），且大迁移一旦出错无法定位是哪一步；链式迁移每一级都能单独测试。

### 1.5 schema 索引校验与环检测

渲染前必须先建索引并校验，把两类脏数据挡在渲染之前：

- **重复 id**：定位错乱、局部更新失效。
- **循环引用**：递归渲染直接栈爆，且错误现象离根因很远。

```
校验（schema.cjs）
  正常树 4 节点        → 无错通过
  重复 id             → 检出
  循环引用            → 检出（按对象身份）
```

两个关键点：

- **环检测按对象身份**：维护访问过的对象集合，用对象身份判断是否回头；不能用值比较——两个内容相同的节点会被误判成环。
- **索引一份两用**：除拦脏数据外，还承担「按 id 定位脏节点」的职责，服务于渲染层的更新粒度（见 2.5）。

## 2. 渲染引擎

回答一个问题：**一份 schema 怎么稳定、够快、有选择地变成组件树并保持同步。**

### 2.1 渲染引擎框架与适配

渲染引擎接收 schema（已含约束校验），通过适配器把框架无关的节点模型翻译成框架相关的组件树：

```
schema → 适配器 → 组件树 → 挂载 / 更新
```

- 递归遍历节点树，按 `type` 找到已注册组件、按 `props` 灌入属性、按 `children` 向下递归。
- 表达式 / 条件 / 循环在递归过程中求值展开（见 2.2~2.4）。

### 2.2 表达式沙箱

表达式的 `props` 里允许用户写取动态值，必须关进沙箱执行。做法是 `with` + `Proxy` 的**软沙箱**：

```
with + Proxy：所有标识符先过一道 get
  在白名单作用域内（state / item / props…）→ 放行
  不在白名单（window / process…）        → 一律抛错
```

`with` 必须知道的两个坑：

- **严格模式禁用**：`with` 在 `'use strict'` 下直接语法错误，所以承载沙箱的文件**不能写 `'use strict'`**。
- **先查 `Symbol.unscopables`**：`with` 环境会先查对象的 `Symbol.unscopables`，symbol 键必须放行，否则连合法表达式都跑不起来。

**边界**：这只是软沙箱——原型链逃逸（`({}).constructor.constructor('return process')()`）依然存在，**只防误用、不防恶意**；真隔离要靠 Web Worker 或 iframe 的 `sandbox`。

### 2.3 递归渲染与条件剪枝

节点树靠**递归**展开，遇到 `when` / `loop` 就地求值：

- **条件（`when`）剪枝**：`when` 不成立（`false`），整棵子树直接剪掉——`<Page>` 下两个子项，剪掉一个后顶层只渲染 1 个。
- **递归 + 剪枝实测（`lowcode-lab/render.cjs`）**：条件剪枝把顶层 2 → 1 个；`item` 变量在子项作用域内可见。

### 2.4 循环展开与 key

循环节点的展开方式很关键——**不是把自己展开成 N 个兄弟**：

```
循环节点 = 容器（保留自身） + N 个子项
子项 id 带下标，如 item#0 / item#1 …
```

- 若把自己展开成 N 个兄弟，父层节点数失控，且 N 个同名 id 会让定位与局部更新全错。
- **实测**：循环展开 2 份，`item` 变量在子项作用域内可见。
- **`key` 的边界**：要稳定且尽量用业务 id，而不是下标——下标在插入 / 删除时会导致整段重建；出码时探针自动补 `key={index}` 只是兜底，不是最优解。
- **条件 + 循环组合**：先判条件（不成立整棵剪掉），再展开循环；顺序反过来会白算一遍子项。

### 2.5 更新粒度与依赖收集

改一个属性**不需要整棵树重渲染**：按 id 定位脏节点，只重算它的子树。

```
全量渲染   → 访问 5 个节点
只重算脏子树 → 只访问 3 个节点
实测（render.cjs）
```

- **为什么要收集依赖**：把「哪个 `state` 字段 → 哪些节点」记录下来，字段一变只重算关联子树。
- **编辑器卡顿的头号原因**：每拖一下就全量重渲染，页面一大就卡。
- **依赖的运行时性**：表达式依赖是运行时才能确定的（用户写 `state.a.b.c`），所以要么渲染时动态收集依赖，要么静态分析表达式取根字段（保守取 `state.a`）。
- **失效表现**：依赖没收集全时，改了属性页面没反应，或要切换一下面板才刷新。

## 3. 可视化搭建与编辑器

回答一个问题：**怎么让用户把节点拖成页面、又把属性改对，最后带走能跑的源码。**

### 3.1 编辑器整体：画布 / 属性面板 / 出海

编辑器三大件：

- **画布（Canvas）**：预览渲染出的组件树，承载拖拽、选中、缩放。
- **属性面板（Props Panel）**：由物料 `props` 描述自动生成一组编辑项，改一处触发更新与联动。
- **出海（Out-of-Box / 导出）**：把 schema 落成独立源码文件，从此脱离平台可维护。

画布放大缩小时，出码 / 交互坐标必须换算正确（见 3.2 的工程细节）。

### 3.2 拖拽落点判定

拖拽到目标容器时，按目标容器的**上 / 中 / 下三段**判定落点：

```
上 → before（插到该子项之前）
中 → inside（作为该子项的子节点）
下 → after（插到该子项之后）
```

两个必要的工程细节：

- **小容器要给边缘区最小像素值**——否则太小的容器永远塞不进“中间”（`inside`）。
- **画布用 `transform: scale()` 缩放时**，`getBoundingClientRect` 拿到的是缩放后的值，指针坐标要除回缩放比，才算回画布坐标系。

**环检测必须在移动前做**：把节点拖进自己的子孙必须拦，且要在移动前拦。

```
isDescendant(page, 'list', 'item') → true → 拒绝移动
把"自身"也算命中 → 顺带挡掉「拖到自己身上」
```

### 3.3 属性联动与清值

属性面板的字段联动要注意**隐藏不等于清值**：只隐藏不清值，用户会提交一个看不见的旧值（幽灵值）。

- **实测**：切换 `srcType` 后，`url` / `fileId` 互斥字段被连带清空——不可见字段不留旧值。
- **原则**：字段不可见时，若其取值在语义上不再成立，必须连同清空，而不是只做视觉隐藏。

### 3.4 手写区锚点

编辑器的源码视图允许用户在出码产物里**手写一段代码**，这需要锚点机制保真：

```
手写区用锚点注释标记
  二次出码 → 原样搬回手写代码
  锚点被整块删掉 → 降级为注释保留在文件末尾，绝不静默丢弃
```

- **实测（`lowcode-lab/editor.cjs` / `boundary.cjs`）**：锚点健全时二次出码原样搬回；锚点被删时以注释形式保留。
- **意义**：给「用户要的灵活性」一条显式出口，同时保证「不丢用户的任何输入」。

## 4. 出码与双真相治理

回答一个问题：**schema 变成源码之后，两份真相怎么共存、谁来裁决、如何收场。**

### 4.1 schema→源码出码

出码把 schema 翻译成可直接运行的源码文件，是按**节点模型逐条生成**的确定性过程。生成规则按结构形态对齐：

| schema 结构 | 出码结果 |
| ---- | ---- |
| 条件 `when` | 三元表达式，`false` 分支显式 `null` |
| 循环 `loop` | `map`，遍历子项并自动补 `key` |
| 字面量 | 原样写入 |
| 表达式 | 与字面量**分道**，走另一条生成路径 |

- 出码是确定性的：同一份 schema 出码结果稳定可复现，才能被回归测试。

### 4.2 出码的表达式与括号配平

出码时拼表达式字符串，**括号必须配平**：

- 错一个括号，会把语法错误**推迟到编译期**才暴露，而不是出码当下。
- 所以出码末尾要做**括号配平断言**，先查再产出，把错误挡在生成阶段。

### 4.3 双真相与漂移检测

出码那一刻，体系里就同时存在**两份真相**：

```
schema（结构真相）         源码（运行真相）
        └───── 同一页面的两种表述 ─────┘
出码覆盖 ┄┄ 谁改了？┄┄ 手改源码
```

用 **hash 检测漂移**：

```
原样（未手改）  = clean    ← 可安全重新出码覆盖
手改过          = drifted  ← 必须先 diff 或标记「源码优先」
```

- **实测（`lowcode-lab/boundary.cjs`）**：手改一行即判 `drifted`。
- **原则**：`drifted` 时必须先 diff 或标记源码优先，绝不闷头用 schema 覆盖掉用户的手改。

### 4.4 schema 与源码治理

双真相长期共存，靠治理收口，三件事必做：

```
1. schema 与源码一起进版本库（同一提交里保持一致，可回溯）
2. 页面级权限（谁允许出码 / 谁允许发布）
3. 出码产物要有回归测试（防止出码器随物料的增长悄悄回归）
```

## 5. 低代码的边界

回答一个问题：**什么场景不该用低代码，用了之后这份代码归谁、平台该在哪收手。**

### 5.1 适用性打分与短板决定

每个候选页面按交互 / 状态 / 集成 / 性能四维打分，得出“适不适合进平台”的排序：

| 场景 | 总分 | 结论 |
| ---- | ---- | ---- |
| 表单 | 2 | 低代码（纯搭建即够） |
| 看板 | 6 | 低代码 + 扩展点 |
| 画布编辑器 | 单维满分 | 专业开发（出局） |

**短板决定上限**：交互 / 状态 / 集成 / 性能**任一维满分即不宜进平台**——满分意味着该维度低代码的通用抽象盖不住，强行塞入只会逼用户写表达式 / 逃生舱，得不偿失。

### 5.2 逃生舱机制

平台必须有明确的出口，否则用户只能在约束内硬凑。两条关键设计：

- **未注册物料明确抛错，绝不静默降级成 `<div>`**——静默降级会把错误推迟到线上，最后只表现为「这块样式不对」，无从定位。
- **逃生舱是「注册自定义物料」**，不是让用户在表达式里写业务——业务逻辑该由专业开发在真正的代码层写。

### 5.3 成本盈亏分析

搭建不是永远省人工，要算**成本盈亏**：

```
搭建成本         一次搭建 8h   ·  单次变更 2.5h
专业开发         一次开发 24h  ·  单次变更 0.8h
→ 盈亏平衡点在第 9.4 次变更
→ 20 次时 专业开发累计 40h < 低代码累计 58h，反超
```

- **结论**：低频变更页面是低代码主场；**高频演进的核心页面应尽早出码脱离**平台。
- 判断标准不是“搭建当时花了多久”，而是「这个页面日后还要不要频繁改」。

### 5.4 最小实现 lowcode-lab

`lowcode-lab` 是一个**零依赖探针实验台**，把全模块知识点落成可跑的自检：

```
node run.cjs 依次执行四探针
  物料校验 / 版本迁移 / 索引环检测   （schema.cjs）
  表达式沙箱 / 递归渲染 / 更新粒度    （render.cjs）
  拖拽落点 / 出码 / 手写区 / 属性联动 （editor.cjs）
  适用性打分 / 逃逸机制 / 成本盈亏 / 漂移检测（boundary.cjs）
node:assert 自检全绿
```

用它验证本总结里所有「实测」结论，也作为面试 / 复习时的最小复现。
