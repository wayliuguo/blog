# 模块面试题 · 低代码与搭建体系

## 1. 协议与 schema 设计

### Q1（1.1）｜ 搭建平台里，为什么协议（schema）要最先定稳？

- **判断**：四层改动代价排序是**协议 > 渲染 > 编辑器 > 物料**，越靠底层改动越贵；协议一变，存量 schema、渲染器、编辑器、物料全要跟着动。
- **展开**：协议是唯一会被持久化并跨版本存在的东西（数据库里躺着几万份 schema）。渲染器改了重新发版即可，协议改了要写迁移链、要兼容老数据、还要保证老页面不崩。
- **边界**：协议不可能一次定对，所以要**一开始就留版本号字段和迁移链机制**，而不是等第一次大改时临时补救。追问点：有了版本号还需要迁移链吗？→ 需要。版本号只告诉你「从哪来到哪去」，迁移链才定义每一级怎么走；跨多级的老数据要逐级迁移（实测 v1 → v3 走两级）。

### Q2（1.4）｜ schema 版本迁移要注意什么？

- **判断**：迁移是**逐级链式**执行，每一级只负责自己那一次变更；补默认值和清理废弃字段都要在链里完成。
- **展开**：实测（`lowcode-lab/schema.cjs`）——v1 页面经两级迁移到 v3，补上默认值 `size=md`，旧字段 `visible` 改写为 `when` 且被清理干净。
- **佐证**：

```
v1 → v2 → v3   一级只改一件事：补默认值 / 改字段名 / 清理废弃字段
约束            幂等（迁两次结果一致）+ 可回滚（失败停在半路并明确报错）
```

- **边界**：迁移必须**幂等且可回滚**：同一份 schema 迁移两次结果一致；迁移失败要能停在半路并给出明确错误，而不是写坏一半。追问点：为什么不能一次性写个 v1→v3 的大迁移？→ 存量数据版本分布不可控（可能有 v2 的），且大迁移一旦出错无法定位是哪一步；链式迁移每一级都能单独测试。

### Q3（1.5）｜ 渲染前为什么必须先建索引并做校验？

- **判断**：重复 id 与循环引用必须挡在渲染之前，否则定位错乱、递归栈爆掉，且错误现象离根因很远。
- **展开**：实测（`lowcode-lab/schema.cjs`）——正常树 4 节点无错；重复 id 与循环引用都被检出。环检测按**对象身份**做（维护访问过的对象集合），不能用值比较（两个内容相同的节点会被误判）。
- **边界**：索引还承担了「按 id 定位脏节点」的职责（见更新粒度），一份索引两用。追问点：循环引用在什么操作里最容易产生？→ 复制粘贴节点（把父节点粘进子节点）和拖拽，两处都要拦。

## 2. 渲染引擎

### Q4（2.2）｜ 用户写的表达式怎么关进沙箱？`with` 有哪些坑？

- **判断**：`with` + `Proxy` 软沙箱：所有标识符先过一道 `get`，不在白名单作用域里的一律抛错。
- **展开**：实测（`lowcode-lab/render.cjs`）——`state`/`item` 可用，`window`/`process` 一律抛错。两个必须知道的坑：① `with` 在严格模式禁用，所以该文件不能写 `'use strict'`；② `with` 会先查 `Symbol.unscopables`，symbol 键必须放行，否则连合法表达式都跑不起来。
- **边界**：这只是**软沙箱**，原型链逃逸（`({}).constructor.constructor('return process')()`）依然存在，只防误用不防恶意；真隔离靠 Web Worker 或 iframe `sandbox`。追问点：为什么不干脆禁用用户表达式？→ 禁用意味着条件、循环、插值全做不了，平台立刻退化成静态页生成器；正确做法是限制能力 + 隔离执行。

### Q5（2.4）｜ 循环节点展开成什么结构？为什么要带 key？

- **判断**：循环节点**本身保留为容器**，展开的是它的子项，且子项 id 要带下标（如 `item#0`）；列表项必须带稳定 `key`。
- **展开**：把自己展开成 N 个兄弟会让父层节点数失控，且 N 个同名 id 会导致定位与局部更新全错。实测（`lowcode-lab/render.cjs`）——循环展开 2 份且 `item` 变量在子项作用域内可见。
- **边界**：`key` 要稳定且尽量用业务 id 而不是下标（下标在插入 / 删除时会导致整段重建）；出码时探针自动补 `key={index}` 是兜底，不是最优解。追问点：条件节点和循环节点同时存在时怎么展开？→ 先判条件（不成立整棵剪掉），再展开循环；顺序反过来会白算一遍子项。

### Q6（2.5）｜ 改一个属性要整棵树重渲染吗？

- **判断**：不要。按 id 定位脏节点，只重算它的子树；依赖关系要收集到「哪个 state 字段 → 哪些节点」。
- **展开**：实测（`lowcode-lab/render.cjs`）——全量渲染访问 5 个节点，只重算脏子树 3 个。编辑器里每拖一下就全量重渲染，页面一大就卡，这是搭建平台卡顿的头号原因。
- **边界**：表达式依赖是**运行时**才能确定的（用户写 `state.a.b.c`），所以要么在渲染时动态收集依赖，要么静态分析表达式取根字段（保守取 `state.a`）。追问点：局部更新失效时会表现成什么？→ 改了属性页面没反应，或者要切换一下面板才刷新——典型的依赖没收集全。

## 3. 可视化搭建与编辑器

### Q7（3.2）｜ 拖拽落点怎么算？什么操作必须拦？

- **判断**：按目标容器的上 / 中 / 下三段判定 `before` / `inside` / `after`；**把节点拖进自己的子孙必须拦**，且要在移动前拦。
- **展开**：实测（`lowcode-lab/editor.cjs`）——三段判定正确，`isDescendant(page, 'list', 'item')` 为 true 时拒绝移动；该判定把自身也算命中，顺带挡掉「拖到自己身上」。
- **佐证**：

```
上 → before（插到该子项之前）   中 → inside（作为子节点）   下 → after（插之后）
工程细节：小容器给边缘区最小像素；scale 缩放画布须把指针坐标换算回画布坐标
```

- **边界**：两处工程细节——小容器要给边缘区**最小像素值**（否则永远塞不进中间）；画布用了 CSS `transform: scale()` 时，`getBoundingClientRect` 是缩放后的值，指针坐标要除回缩放比。追问点：属性面板的字段联动要注意什么？→ **隐藏不等于清值**：只隐藏不清值，用户会提交一个看不见的旧值。实测切换 `srcType` 后 `url` / `fileId` 互斥字段被连带清空。

### Q8（3.3）｜ 属性面板的字段「隐藏」与「清值」有什么本质区别？

- **判断**：隐藏只是视觉不显示，值还在；清值才把旧值删掉。只隐藏不清值，用户会提交一个看不见的旧值（幽灵值）。
- **展开**：字段不可见时，若其取值在语义上不再成立，必须连同清空。实测（`lowcode-lab/editor.cjs`）——切换 `srcType` 后，`url` / `fileId` 互斥字段被连带清空。
- **边界**：互斥字段（二选一）是幽灵值的重灾区；判断标准是「当前配置下这个值是否还有意义」，而不是「面板上显不显示它」。

## 4. 出码与双真相治理

### Q9（4.3）｜ 出码之后，schema 和源码谁说了算？

- **判断**：出码那一刻就产生两份真相。用 hash 检测漂移：**原样 = clean**（可安全重新出码覆盖），**手改过 = drifted**（必须先 diff 或标记为源码优先）。
- **展开**：手写区用锚点注释标记，二次出码时原样搬回；锚点被整块删掉时**降级为注释保留**在文件末尾，绝不静默丢弃。实测（`lowcode-lab/boundary.cjs`）——手改一行即判 `drifted`。
- **佐证**：

```
原样 = clean      逐一 hash 比对 → 可覆盖
手改 = drifted    必须 diff 或标记「源码优先」→ 绝不闷头覆盖
```

- **边界**：什么时候该彻底脱离平台？看成本账——实测搭建 8h vs 24h、单次变更 2.5h vs 0.8h，**盈亏平衡在第 9.4 次变更**；低频变更页面是低代码主场，高频演进的核心页面应尽早出码脱离。追问点：未注册的物料怎么处理最稳妥？→ **明确抛错**，绝不静默降级成 `<div>`；静默降级会把错误推迟到线上，最后只表现成「这块样式不对」。平台的逃生舱是「注册自定义物料」，不是让用户在表达式里写业务。

### Q10（4.4）｜ 双真相共存，靠什么治理收口？

- **判断**：治理三件事——**schema 与源码一起进版本库、页面级权限、出码产物要有回归测试**。
- **展开**：schema（结构真相）与源码（运行真相）只有在同一提交里保持一致才可回溯；页面级权限解决「谁允许出码 / 谁允许发布」；回归测试防止出码器随物料库增长悄悄回归。
- **边界**：漂移检测是前提——`drifted` 的页面在 diff 或标记源码优先之前，任何自动出码覆盖都是数据丢失风险。

## 5. 低代码的边界

### Q11（5.1）｜ 什么场景适合用低代码？「短板决定上限」怎么理解？

- **判断**：按交互 / 状态 / 集成 / 性能四维打分排序——表单 = 低代码（总分 2）、看板 = 低代码 + 扩展点（6）、画布编辑器 = 专业开发（单维满分出局）。
- **展开**：**短板决定上限**：交互 / 状态 / 集成 / 性能**任一维满分即不宜进平台**——满分意味着该维度的通用抽象盖不住，强行塞入只会逼用户写表达式 / 逃生舱，得不偿失。
- **佐证**：

```
表单            交互低 状态低 集成低 性能低 → 总分 2  → 纯低代码
看板            部分维度需求上升            → 总分 6  → 低代码 + 扩展点
画布编辑器      交互满分                → 单维满分 → 专业开发（出局）
```

- **边界**：满分维度的判断要落到具体页面的真实需求，而不是套模板；判错把专业开发场景塞进平台，最终成本由逃生舱（自定义物料）转移给专业团队。

### Q12（5.2）｜ 未注册的物料该怎么处理？平台的逃生舱是什么？

- **判断**：未注册物料**明确抛错**，绝不静默降级成 `<div>`；逃生舱是「注册自定义物料」，不是让用户在表达式里写业务。
- **展开**：静默降级会把错误推迟到线上，最后只表现成「这块样式不对」，无从定位。逃生舱给用户一条显式出口，但业务逻辑该由专业开发在真正的代码层写。
- **边界**：逃生舱的克制使用边界——它解决「物料库覆盖不到的结构」，不解决「用户想把业务都塞进表达式」；滥用逃生舱会让平台退化成「比手写更绕的姿势」。

### Q13（5.3）｜ 什么时候该「出码脱离」平台？成本账怎么算？

- **判断**：看成本盈亏平衡点——搭建 8h vs 开发 24h、单次变更 2.5h vs 0.8h，**盈亏平衡在第 9.4 次变更**；高频演进的核心页面应尽早出码脱离。
- **展开**：搭建一次便宜、但每次变更更贵；专业开发一次贵、但变更便宜。低频变更页面是低代码主场，高频演进页面随变更次数累计反超。
- **佐证**：

```
一次搭建 8h   ·  单次变更 2.5h       盈亏平衡点 = 第 9.4 次变更
一次开发 24h  ·  单次变更 0.8h       20 次时：专业开发 40h < 低代码 58h，反超
```

- **边界**：判断标准不是「搭建当时花了多久」，而是「这个页面日后还要不要频繁改」；出码脱离的前提是双真相治理到位（见 Q9/Q10），否则脱离即失控。
