# 低代码的边界

前三篇把「怎么做」讲完了，这一篇讲**什么时候不该做**。低代码的失败案例很少是技术做不出来，而是：该用专业开发的需求硬塞进了平台、或者平台没留逃生舱、或者出码之后没人说得清这份代码归谁。这一篇用 `lowcode-lab` 的 `boundary.cjs` 给出可判定的规则与实测。

## 一、适用性：短板决定上限，不是总分决定

判断一个需求该不该进低代码，不要算总分——**任意一维满分就出局**。交互、状态、集成、性能，任何一项到了「必须写代码实现」的程度，平台的抽象就成了阻碍。

> 摘自 `./code/lowcode-lab/boundary.cjs`

```js
function assess(scores) {
  // 每维 0-3 分；任一维度满分即判「不建议」——短板决定上限，不是总分决定
  const total = DIMENSIONS.reduce((s, d) => s + (scores[d.key] || 0), 0)
  const maxDim = Math.max(...DIMENSIONS.map(d => scores[d.key] || 0))
  const verdict = maxDim >= 3 ? '专业开发' : total >= 6 ? '低代码+扩展点' : '低代码'
  return { total, maxDim, verdict }
}
```

> 摘自 `./code/lowcode-lab/boundary.cjs`

```js
{
  const form = assess({ interaction: 0, state: 1, integration: 1, performance: 0 })
  assert.equal(form.verdict, '低代码')

  const dashboard = assess({ interaction: 1, state: 2, integration: 2, performance: 1 })
  assert.equal(dashboard.verdict, '低代码+扩展点')

  const editor = assess({ interaction: 3, state: 2, integration: 1, performance: 2 })
  assert.equal(editor.verdict, '专业开发', '短板维度满分即出局，不看总分')
  console.log(`[1] 适用性：表单=低代码（总分 ${form.total}）、看板=低代码+扩展点（${dashboard.total}）、画布编辑器=专业开发（单维 ${editor.maxDim} 满分出局）`)
}
```

四类典型结论：

| 需求 | 表现 | 结论 |
| --- | --- | --- |
| 后台表单 / 列表页 | 交互简单、状态扁平、接口规整 | 低代码 |
| 运营活动页 | 需要自定义物料、对接埋点与 AB | 低代码 + 扩展点 |
| 数据看板 | 图表多、口径复杂、要联动 | 低代码 + 扩展点（图表走注册物料） |
| 画布编辑器 / 在线文档 | 多步交互、复杂状态机、协同 | 专业开发 |

「中间态」那一类是平台价值最高的地方，也是最容易做砸的：给它扩展点，它就落在平台里；不给，用户就会在表达式框里塞进 200 行逻辑。

## 二、逃生舱：注册物料，而不是在表达式里写业务

平台必须留一个「去写代码的口子」，而且这个口子必须是**受控的**（注册自定义物料），不是放任用户在字符串里写脚本。

> 摘自 `./code/lowcode-lab/boundary.cjs`

```js
const REGISTRY = new Set(['Text', 'List', 'Banner'])

function resolveComponent(type) {
  if (REGISTRY.has(type)) return { source: 'builtin', type }
  // 未注册的类型不静默降级成 div，而是明确要求注册——静默降级会把错误推迟到线上
  throw new Error(`未注册的物料：${type}`)
}
```

> 摘自 `./code/lowcode-lab/boundary.cjs`

```js
{
  assert.deepEqual(resolveComponent('Text'), { source: 'builtin', type: 'Text' })
  assert.throws(() => resolveComponent('Charts'), /未注册的物料/)
  console.log('[4] 逃逸机制：未注册物料明确报错而非静默降级——逃生舱是「注册自定义物料」，不是在表达式里写业务')
}
```

「未注册就降级成 `<div>`」是典型的善意 bug：开发环境下页面能跑，于是问题一路带到线上，最后表现成「这块样式怎么不对」。明确抛错 + 编辑器里高亮，成本极低。

## 三、成本账：搭建便宜，变更贵

低代码的收益集中在首次搭建（8h vs 24h），代价是每次变更都要绕过平台的抽象（2.5h vs 0.8h）。这笔账要算到变更次数上：

> 摘自 `./code/lowcode-lab/boundary.cjs`

```js
function cost({ buildHours, changeHours, changes, proBuildHours, proChangeHours }) {
  return {
    lowcode: buildHours + changeHours * changes,
    pro: proBuildHours + proChangeHours * changes
  }
}
```

实测结论（搭建 8h/24h、单次变更 2.5h/0.8h）：**盈亏平衡在第 9.4 次变更**——1 次变更时 10.5h vs 24.8h，低代码完胜；20 次变更时 58h vs 40h，专业开发反超。

推论很直接：**低频变更的页面（运营页、一次性活动）是低代码的主场；高频演进的核心页面不该长期绑在平台上。** 判断是否该"出码脱离"的信号就是变更次数逼近平衡点，以及需求开始出现「这个平台不支持」的频次。

## 四、治理：schema 与源码的双真相

出码之后存在两份真相。谁改了源码必须可检测，否则下一次出码会静默覆盖别人的工作。

> 摘自 `./code/lowcode-lab/boundary.cjs`

```js
function emit(code) {
  return `/* hash:${crypto.createHash('sha256').update(code).digest('hex').slice(0, 12)} */\n${code}`
}

function detectDrift(emitted) {
  const declared = emitted.match(/hash:(\w{12})/)
  const body = emitted.replace(/^\/\* hash:\w+ \*\/\n/, '')
  const actual = crypto.createHash('sha256').update(body).digest('hex').slice(0, 12)
  return declared && declared[1] === actual ? 'clean' : 'drifted'
}
```

实测：原样输出 = `clean`；手改一行 = `drifted`。据此定规则：

- `clean` → 允许平台重新出码覆盖（源码无人手改，schema 是唯一真相）。
- `drifted` → **必须先 diff 或把该文件标记为「源码优先」**，出码时跳过它并告警。
- 把源码重新变回 schema（反向工程）只在极少数场景可行（纯静态、无手写区），不要作为通用能力承诺。

配套还要有三件事：schema 与源码一起进版本库（且互相关联）、页面级权限（谁能发布谁能改物料）、以及一套回归测试（出码产物跑了才算通过）。

要点：

- 适用性用短板判定：任一维度满分即走专业开发，不看总分。
- 逃生舱是「注册自定义物料」，未注册物料明确报错，绝不静默降级。
- 成本账算到变更次数：低频变更是低代码主场，高频演进的核心页面应尽早出码脱离。
- 出码后有两份真相：用 hash 检测漂移，`drifted` 时必须先 diff 再出码。
- 反向（源码 → schema）只在纯静态场景可行，不要作通用承诺。
