## 分篇知识点

### 01-前端工程化全景

- **工程化解决什么**：把「人的不确定性」转化为「流程的确定性」；核心矛盾是规模越大、协作与稳定的成本越高
- **五大阶段**：开发→测试→构建→发布→监控，每一阶段是一条独立子体系，一环扣一环：规范影响测试通过率、测试门禁决定能否进构建发布、发布可控性决定线上稳定性与监控信号量
- **依赖链**：「规范/脚手架 → 质量门禁/CI-CD → 灰度/发布 → 监控/复盘 → 反哺规范」；链条最短的薄弱环节才是真正的瓶颈
- **基建工程师成长路径**：写页面 → 写组件库 → 写团队脚手架 → 设计整套研发基础设施；抽象能力是分水岭，服务对象从用户变为团队工程师
- **成熟度模型 L1–L5**：原始→逐步→规范→自动→平台；建设遵循「先规范、再自动化、后平台化」，用构建耗时、发布失败率、回归率等指标驱动迭代
- **最小实现**：到 `../03-交付与质量/code` 运行 `pipeline-demo.html`，看 build→test→deploy 最小流水线如何把「人肉接力」变成「机器编排」

### 02-模块化规范

- **为什么模块化**：避免全局变量污染与命名冲突、解决依赖关系混乱与加载顺序难控、提升可维护性与协作效率
- **五种规范**：CommonJS（同步、运行时、Node 服务端）、AMD（异步、浏览器、require.js）、CMD（sea.js，同步/异步兼有）、ES6 Modules（编译时静态、通用）、UMD（带前后端同构思想的封装工具，按环境自适应）
- **CJS vs ESM 的本质差异**：运行时确认依赖 vs 编译时确认依赖；ESM 的静态分析让 tree-shaking 与类型检查成为可能
- **加载与输出细节**：CommonJS 首次加载后缓存、输出 `module.exports` 的值拷贝；AMD 等所有依赖加载完成才执行回调；ESM 的加载都是引用
- **package.json 入口字段**：`main`（JS 通用入口）、`browser`（浏览器环境入口）、`module`（ES Modules 入口），为包体与引用方选对正确入口
- **最小实现**：`mini-bundler.html` 把依赖模块「拼装」成一份可运行产物，直观看见加载顺序如何被固定

### 03-构建工具

- **Webpack 是模块打包器**：从入口递归构建依赖图，把 JS/CSS/图片/字体统一打包；核心配置 entry/output/mode/module/plugins/optimization/devServer/resolve
- **loader 与 plugin 分工**：loader 接收文件内容加工后返回（`use` 数组从右到左执行），负责非 JS 资源；plugin 监听整个构建生命周期，如 html-webpack-plugin
- **代码分割与优化**：splitChunks 权衡「文件体积 vs 请求数」；tree-shaking 靠 `usedExports` + production 剔除未用代码；`[contenthash]` 让文件名带内容指纹避免缓存失效；preload/prefetch 做资源预加载
- **Vite 基于原生 ESM**：开发时让浏览器自己分析模块、省去大量编译，esbuild 快速转译、类型检查交给 tsc；底层仍用 Rollup 完成生产打包，dev server 开箱即用
- **Rollup 专注库打包**：不生成过多运行时代码、产物干净，支持多模块规范输出，tree-shaking 是强项
- **选型对比**：Webpack 生态庞大、可深度定制，适合大型应用；Vite 开发体验优先，适合新一代应用脚手架；Rollup 适合 npm 库/组件/工具发布

### 04-脚手架的诞生

- **脚手架的本质**：把「创建项目的知识」沉淀为可复用代码；核心四件事是收集信息 → 选择模板 → 渲染生成 → 收尾（安装依赖/初始化 git/输出指引）
- **CLI 设计**：`#!/usr/bin/env node` shebang 让系统用 Node 执行；commander/yargs 负责命令与参数解析（`program.command('create <projectName>').option('-t, --template')`），并做目录已存在等健壮性校验
- **模板引擎**：EJS/Handlebars 用占位符 + 条件 + 循环把配置注入模板文件；构建坑：插值语法可能与 Vue/框架语法冲突，应「生成时渲染」而非运行时渲染
- **生成器架构**：任何 create-app 类工具都可抽象为「CLI 入口 → Generator 核心控制器（getTemplateDir/模板解析/文件渲染）→ Template 仓库层」；create-vite 按「框架 × 变体」组织模板、package.json 单独改写保留用户信息
- **私有脚手架平台**：npm 私服模板包 + 模板中心后台 + 版本化发布（`--template enterprise@1.2.0`）；建设要点是模板迭代与灰度、埋点统计、可升级性、权限审计
- **最小实现**：`scaffold-cli.html` 用 JS 把 `my-create app -t vue --force` 解析成结构化选项，看清 CLI 的本质

### 05-Monorepo 工程化

- **Monorepo vs Multi-repo**：单仓库多包以「统一版本 + 统一依赖 + 统一任务编排」换一致性；收益是原子提交、依赖统一、增量构建、基建复用
- **pnpm 依赖管理**：全局内容寻址存储（CAS）+ 硬链接/软链，一份内容多处链接省磁盘；非扁平结构只暴露直接依赖，防住「幽灵依赖」
- **lerna 管版本**：`lerna version/publish` 联动多包发版，`--conventional-commits` 按提交信息自动推导版本（fix→patch、feat→minor、BREAKING→major）
- **turborepo 管编排**：任务依赖图 + 增量缓存（输入文件 hash 命中即复用产物，远程缓存让整个团队共享、CI 大幅提速）；`--filter` 定向构建受影响包
- **大型案例与误区**：Babel 多版本共生、Vue3 按需拆包、Turbo 自举（dogfooding）；落地误区是包太厚、循环依赖、权限全开放、跨包耦合无规约
- **最小实现**：`deps-demo.html` 可视化「内容寻址存储、硬链接/软链、扁平 hoist vs 隔离结构」，看懂幽灵依赖为何产生又为何被防住
