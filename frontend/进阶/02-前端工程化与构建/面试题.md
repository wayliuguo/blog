## 2. 重点题精答（五步法）

### Q1：Vite 为什么快？和 webpack 的差别？

- **结论**：dev 不打包（浏览器直接请求模块），启动耗时近似常数；webpack dev 要全量打包。
- **原理**：依赖预构建（esbuild 转 ESM + 合并请求）+ 源码按需编译（原生 ESM 按路由/import 懒加载）+ 基于 `import.meta.hot` 的 HMR 只更新变更模块。
- **场景**：大项目冷启动秒开，热更新不随文件数线性变慢。
- **边界**：生产构建仍需 Rollup（成熟打包 + 产物优化）；ESM 在旧浏览器需降级。
- **追问**：依赖预构建解决了什么问题？→ ① 几百个依赖模块的请求瀑布流（合并为一个）；② CommonJS 依赖转 ESM；③ 依赖只构建一次。

### Q2：Vite 插件的本质？

- **结论**：插件 = 返回 hooks 对象的函数，遵循 Rollup 插件接口，扩展 Vite 专有钩子。
- **原理**：dev 态不打包 → 需要 dev server 中间件（`configureServer`）；build 态走 Rollup → 需要虚拟模块（`resolveId` + `load`）；`enforce: 'pre'/'post'` 控制执行顺序。
- **场景**：简历项目四个自研插件：虚拟入口（`pre`）、开发导航（`configureServer`）、错误监控注入（`post` + `transformIndexHtml`）、产物归集（`apply:'build'` + `closeBundle`）。
- **边界**：`generateBundle`/`writeBundle` 操作产物对象，文件系统搬运用 `closeBundle`（落盘后最后时机）。
- **追问**：`\0` 前缀是什么？→ Rollup 约定，`\0` 开头表示虚拟模块 id，不参与常规解析。

### Q3：虚拟入口插件怎么实现"一份模板 + 一个配置 = N 个页面"？

- **结论**：`pages.config.ts` 单一数据源，插件按 pageKey 现场拼 HTML / 虚拟模块。
- **原理**：构建态 `resolveId` 把不存在的入口声明为虚拟模块，`load` 返回模板 + 占位符替换的 `main.ts`；开发态 `configureServer` 中间件直接 `res.end(htmlHandle(page))`。
- **场景**：Vite 官方 MPA 要求每页一个物理 HTML，页面上量后模板冗余；插件让它零模板代码。
- **边界**：模板只读一次并缓存在闭包（避免每页重复 IO），`pageKey` 从路径取最后两段兼容简写。
- **追问**：为什么 `enforce: 'pre'`？→ 必须早于 Vite 内置 HTML 处理。

### Q4：tree-shaking 的原理？

- **结论**：基于 ES Module 的静态结构，构建时剔除未使用的导出。
- **原理**：ESM 的 `import/export` 顶层静态可分析；Rollup 依赖图里标记不可达导出；副作用标记（`sideEffects: false`）决定能否安全删除。
- **场景**：只 `import { a } from 'lib'` 时 b/c 不进产物；组件库/工具库需配 `sideEffects`。
- **边界**：CommonJS 动态 require 无法静态分析；具名导出被整体访问（`import * as`）会失效。
- **追问**：函数副作用怎么处理？→ 顶层调用有副作用不删，`/*#__PURE__*/` 注释标记纯函数。

### Q5：MPA vs SPA 的工程取舍？

- **结论**：不是技术优劣，是运维成本——页面上量后发布与回归成本成为主要矛盾时转 MPA。
- **原理**：SPA 整包发布、全量回归；MPA 按页构建、按页发布、按页回归。
- **场景**：借钱业务 H5 从 Weex 转 Vue3 MPA；`pages.config.ts` 唯一配置中心，新增页面 = 加一条配置。
- **边界**：MPA 代价是构建配置复杂度上升、页面间无法共享内存态；公共依赖需构建配置复用（否则重复打包）。
- **追问**：多页的公共依赖怎么切？→ 按变更频率 + 复用范围分层。

### Q6：manualChunks 分包策略？

- **结论**：按变更频率 + 复用范围切分：vendor（框架）→ ui（组件库）→ utils（工具）→ 页面 chunk。
- **原理**：框架/组件库几乎不变 → 单独一层长期命中浏览器缓存；业务代码高频变 → 单独一层发布只失效这一层。
- **场景**：简历项目四层分包：vue/vue-router/pinia、vant、axios/lodash、每页独立 chunk。
- **边界**：切太细导致请求多、缓存碎片化；依赖循环引用会报错。
- **追问**：为什么文件名要扁平化？→ 便于发布系统与 CDN 规则统一。

### Q7：浏览器兼容怎么决策？

- **结论**：基于真实 UA 分布做决策，而不是无脑双包。
- **原理**：目标浏览器（iOS 11+ / Android Chrome 61+）全部支持 ES Module → 不出 legacy 双包，只出单版本 ESM + `modernPolyfills` 按需注入 polyfill。
- **场景**：覆盖率 iOS 11+ 约 99.97%、Android Chrome 61+ 约 99.83%，放弃极低占比的 iOS 10- / Android 8- 为可接受风险。
- **边界**：`renderLegacyChunks: false` 明确关掉 legacy——口径是"单版本 ESM + 按需 polyfill"，别说成"做了 legacy 双包"。
- **追问**：`modulePreload` 踩过什么坑？→ iOS 部分内核预加载失败且无降级导致白屏，关闭 `modulePreload` 并在配置处注释防回改。

## 3. 追问链

1. "为什么自己写插件，不用现成方案？" → 现成方案解决不了"单模板多页 + 零模板代码 + 按页发布"的组合诉求。
2. "依赖预构建会不会导致缓存失效频繁？" → lockfile 变化才重新预构建，用 `node_modules/.vite` 缓存。
3. "monorepo 的依赖提升（hoist）有什么坑？" → 幽灵依赖、版本不统一，用 pnpm 严格依赖隔离 + workspace 协议。
4. "构建慢怎么排查？" → 先看依赖预构建与插件耗时（`vite --debug`），再看是否误打包、sourcemap 是否关闭。

## 4. 场景设计题

**场景：公司想从 webpack 迁移到 Vite，怎么评估与落地？**
- 答题骨架：收益（冷启动/热更新）与风险（插件生态、特殊 loader、老浏览器 target）→ 先小范围试点（新项目/低流量页面）→ 依赖预构建检查 → 构建产物对比（体积/兼容）→ 滚动迁移 + 灰度。
- 加分点：把"兼容决策基于真实 UA 分布"的方法论讲出来，体现"不是无脑迁移而是评估取舍"。

## 5. 面试口径（简历项目如何表达）

- **项目证据**：Vite 7 + Vue 3.5 + TS 5.8；MPA 改造（`pages.config.ts` 单一数据源、新增页面零模板代码）；四个自研 Vite 插件（虚拟入口 / 开发导航 / 错误监控注入 / 产物归集，共享 `entry-path-handler.ts` 公共层）；manualChunks 四层分包；单版本 ESM + 按需 polyfill；iOS `modulePreload` 白屏 case（关 `modulePreload` + 注释留痕）。
- **表达句式**："页面上量后 SPA 整包发布、全量回归成为主要矛盾，我主导把 H5 转成多页应用——一份页面配置派生构建入口、开发导航、测试范围；虚拟入口插件让新增页面零模板代码；四个自研插件共用一套虚空路径解析公共层。"
- **勿说**：兼容策略别说成"做了 legacy 双包"；量化数字（首屏 ms/包体积 MB）无严格度量时宁可不报。
