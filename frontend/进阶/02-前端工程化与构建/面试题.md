## 一、工程化与模块化

### Q1: 为什么需要前端工程化？（第 01 篇）

- **结论**：工程化是把"能跑"变成"可持续交付"——用工具与规范解决规模变大后的可维护性、一致性与性能问题。
- **原理**：模块化（依赖管理）、组件化（复用）、构建（打包/转译/优化）、规范化（lint/commit/CI）、性能监控构成工程化骨架；本质是"把人工约定固化成工具约束"。
- **边界**：工程化解决的是"人一多、页面一多"的协作问题，不是业务正确性；过度工程化（复杂配置、多余抽象）反而拖慢小项目。
- **追问**：没有工程化会怎样？→ 依赖手动管理、全局命名冲突、无统一构建与回归，页面上量后只能全量发布、全量回归。
- **场景**：页面 30+、协作 10+ 人的 H5，靠工程化把"新增页面零模板代码"等约定固化成配置与插件，而不是靠口头约定。

### Q2: CommonJS 与 ES Module 的区别？（第 02 篇）

- **结论**：CJS 是运行时动态、同步加载、值拷贝；ESM 是编译期静态、可异步、引用实时——后者可被静态分析。
- **原理**：CJS 的 `require` 是运行时函数调用、`module.exports` 整体赋值，导出是值拷贝（简单类型）；ESM 的 `import/export` 是顶层声明、静态可分析，导入是活的引用（live binding），天然支持 tree-shaking 与循环依赖处理。
- **边界**：Node 早期是 CJS，现代 Node 与浏览器原生支持 ESM；CJS 在浏览器需要打包；Node 里 `require` ESM 早期受限。
- **追问**：为什么 CJS 不能 tree-shaking？→ 动态 `require` 无法静态分析哪些导出被用到。
- **场景**：浏览器端统一 ESM；Node 工具脚本看生态（多数仍是 CJS）；Vite 预构建把 CJS 依赖转 ESM。

### Q3: 模块化的演进（IIFE → CommonJS → AMD → ESM）？（第 02 篇）

- **结论**：演进主线是"从全局作用域到作用域隔离，再到可静态分析的依赖图"。
- **原理**：IIFE 用函数作用域 + 全局挂载解决命名冲突（手工维护依赖顺序）；CJS 服务端同步模块；AMD 为浏览器异步加载而生（require.js）；ESM 成为标准，编译期依赖图 + 异步加载。
- **边界**：AMD/UMD 已基本退出，UMD 仅用于库的"浏览器 + Node"双环境兼容；演进是叠加不是替代，存量代码仍有 CJS。
- **追问**：ESM 相比 AMD 解决了什么？→ AMD 是运行时注册回调，ESM 静态可分析、可 tree-shaking、可处理循环依赖。
- **场景**：库要同时给浏览器与 Node 用就出 UMD 包；新项目一律 ESM。

### Q4: `dependencies` / `devDependencies` / `peerDependencies` 的区别？（第 02 篇）

- **结论**：dependencies 是运行时必需，devDependencies 仅开发/构建期用，peerDependencies 声明"宿主环境必须提供"的依赖。
- **原理**：npm 默认把 dependencies 装进生产环境，dev 依赖只在本项目安装；peer 依赖不重复安装、由宿主提供（如插件要求宿主已有 React），避免同一库多实例冲突。
- **边界**：把 dev 依赖混进 dependencies 会让生产包变大；peerDependencies 版本不满足时 npm 通常只告警不报错。
- **追问**：`optionalDependencies` 是什么？→ 安装失败不阻塞整体安装，常用于平台相关的二进制包。
- **场景**：组件库把 react/vue 放 peerDependencies；脚手架工具把构建链放 devDependencies。

### Q5: 语义化版本（semver）规则？（第 02 篇）

- **结论**：主版本.次版本.补丁——主版本不兼容、次版本加功能（向后兼容）、补丁修 bug；`^` 允许次版本、`~` 只允许补丁。
- **原理**：`^1.2.3` 允许 1.x（不含 2.0），`~1.2.3` 只允许 1.2.x，裸 `1.2.3` 精确锁定；lockfile 固化实际安装版本。
- **边界**：0.x 主版本语义失效（0.2 对 0.1 不保证兼容，`^0.2.3` 只允许 0.2.x）；语义版本是"约定"，违规发布仍然存在。
- **追问**：应用该用 `^` 还是精确锁？→ 应用锁 lockfile（`npm ci`），库用 `^` 让出兼容范围；升级走 CI 全量回归。
- **场景**：一次"看起来向后兼容"的次版本升级引入破坏——复盘后规范 peer 范围 + 升级必须过回归，防止无声爆炸。

## 二、构建工具

### Q6: webpack / Vite / Rollup / esbuild 的定位与取舍？（第 03 篇）

- **结论**：webpack 是全功能打包器（生态最全），Vite 是"dev 用 esbuild、build 用 Rollup"的次世代方案，Rollup 是库构建优化之王，esbuild 是极速转译器。
- **原理**：webpack 万物皆模块 + 丰富 loader/plugin，dev 全量打包导致大项目慢；Vite dev 用原生 ESM + esbuild 预构建，build 走 Rollup；Rollup 依赖图静态分析、tree-shaking 最强；esbuild 用 Go 并行极速转译，但只转译不优化产物。
- **边界**：esbuild 不是打包器替代品（无 HMR、插件生态弱）；Rollup 的代码分割支持晚于 webpack；webpack 配置重、构建慢。
- **追问**：为什么 Vite build 不用 esbuild？→ esbuild 产物优化弱（无精细 code splitting），Rollup 更成熟，各司其职。
- **场景**：应用开发用 Vite；库/组件发布用 Rollup；esbuild 当转译/压缩加速器（替代 TSC 编译业务代码）。

### Q7: Vite 为什么快？与 webpack 的本质差别？（第 03 篇）

- **结论**：dev 不打包（浏览器直接请求模块），启动耗时近似常数；webpack dev 要全量打包。
- **原理**：依赖预构建（esbuild 转 ESM + 合并请求）+ 源码按需编译（原生 ESM 按路由/import 懒加载）+ 基于 `import.meta.hot` 的 HMR 只更新变更模块。
- **边界**：生产构建仍需 Rollup（成熟打包 + 产物优化）；ESM 在旧浏览器需降级。
- **追问**：依赖预构建解决了什么问题？→ ① 几百个依赖模块的请求瀑布流（合并为一个）；② CommonJS 依赖转 ESM；③ 依赖只构建一次。
- **场景**：大项目冷启动秒开，热更新不随文件数线性变慢。

### Q8: tree-shaking 的原理与生效条件？（第 03 篇）

- **结论**：基于 ES Module 的静态结构，构建时剔除未使用的导出；生效条件是"ESM + 无副作用声明 + 具名导入"。
- **原理**：ESM 的 `import/export` 顶层静态可分析；Rollup 在依赖图里标记不可达导出；`sideEffects: false` 决定能否安全删除；`/*#__PURE__*/` 注释标记纯函数。
- **边界**：CommonJS 动态 `require` 无法静态分析；`import * as` 整体访问会失效；样式/全局初始化这类副作用需显式声明保留。
- **追问**：函数副作用怎么处理？→ 顶层调用有副作用不删，`/*#__PURE__*/` 注释标记纯函数。
- **场景**：只 `import { a } from 'lib'` 时 b/c 不进产物；组件库配 `sideEffects: ['*.css']` 让样式不被误删。

### Q9: 代码分割与动态导入怎么用？（第 03 篇）

- **结论**：代码分割把产物按路由/按需拆成多个 chunk，动态导入（`import()`）是触发拆分的标准手段——首屏只载必要的。
- **原理**：构建工具遇到 `import()` 自动生成独立 chunk；路由级分割（每路由一个 chunk）+ 组件懒加载 + 公共依赖抽 vendor 层；配合 `preload`/`prefetch` 策略。
- **边界**：切太细导致请求数变多、HTTP 开销与缓存碎片化；动态导入有加载时序，SSR 与微前端场景要评估。
- **追问**：分包和动态导入什么关系？→ 动态导入定拆分点，分包定公共依赖分层，两者配合使用。
- **场景**：报表/编辑器这类大页面按需加载，首屏体积从全量降到核心业务，弱网体验明显改善。

### Q10: 场景：从 webpack 迁移到 Vite，怎么评估与落地？（第 03 篇）

- **结论**：不无脑迁移——先量化收益与风险，小范围试点、灰度滚动。
- **原理**：收益是冷启动/热更新速度与配置心智；风险是插件生态缺失、特殊 loader、老浏览器 target、构建产物差异；流程为试点新项目/低流量页 → 依赖预构建检查 → 产物对比（体积/兼容）→ 滚动迁移 + 灰度。
- **边界**：存量复杂 webpack 配置（自定义 loader、动态 `require` 模式）是主要阻力；兼容决策要基于真实 UA 分布，不是拍脑袋双包。
- **追问**：迁移最容易踩什么坑？→ CJS 依赖未预构建、浏览器端引到 Node 内置模块、`__dirname` 等 webpack 注入变量失效。
- **场景**：H5 从 webpack 迁 Vite 后冷启动从十几秒到秒开；评估阶段先做 POC，对比产物体积与目标浏览器兼容性再决定。

## 三、依赖与 Monorepo

### Q11: pnpm 的硬链接/软链与依赖隔离原理？（第 05 篇）

- **结论**：pnpm 用全局内容寻址存储 + 硬链接，配合 `.pnpm` 虚拟 store 的软链，实现"磁盘最省 + 依赖严格隔离"。
- **原理**：所有包版本存全局 store（内容寻址），项目 `node_modules/.pnpm/<name>@<version>/` 用硬链接指向 store；包的真实依赖装在包自己的 `node_modules` 里（软链），消灭幽灵依赖；workspace 内用 `workspace:*` 协议互链。
- **边界**：硬链接跨盘符/跨文件系统受限；少数工具链对 `node_modules` 扁平结构有隐式假设，会踩坑。
- **追问**：为什么能防幽灵依赖？→ 依赖不扁平提升，`require` 解析不到未声明的包，未声明即报错。
- **场景**：Monorepo 10+ 包共享依赖，磁盘占用大降、版本冲突可控，装包速度也更快。

### Q12: Monorepo 的收益与代价？（第 05 篇）

- **结论**：Monorepo 用"一个仓库管理多包"换跨包协作与统一流程；收益在共享与原子变更，代价在规模与构建编排。
- **原理**：收益——依赖统一、跨包改动一次 PR 原子提交、统一 lint/CI/发布、便于重构与代码复用；代价——仓库变大后 git/CI 变慢、权限粒度粗、需要工具链（pnpm workspace / turborepo / changesets）编排。
- **边界**：小团队、产品强独立时 monorepo 反成负担；取舍核心是"共享多还是隔离多"。
- **追问**：什么时候该拆多仓库？→ 团队边界清晰、版本各自演进、故障隔离要求高时。
- **场景**：组件库 + 业务多应用 + 公共工具集一仓管理，pnpm workspace 组织，changesets 统一发版。

## 四、Vite 插件与自研

### Q13: Vite 插件的本质？开发态与构建态为什么两套执行面？（第 04 篇）

- **结论**：插件 = 返回 hooks 对象的函数，遵循 Rollup 插件接口，再扩展 Vite 专有钩子；dev 走 dev server 中间件、build 走 Rollup。
- **原理**：dev 态不打包 → 需要 `configureServer` 中间件处理请求；build 态走 Rollup → 需要虚拟模块（`resolveId` + `load`）；`enforce: 'pre'/'post'` 控制执行顺序，`apply` 限定 dev/build。
- **边界**：`generateBundle`/`writeBundle` 操作产物对象，文件系统搬运用 `closeBundle`（落盘后的最后时机）。
- **追问**：`\0` 前缀是什么？→ Rollup 约定，`\0` 开头表示虚拟模块 id，不参与常规解析。
- **场景**：简历项目四个自研插件：虚拟入口（`pre`）、开发导航（`configureServer`）、错误监控注入（`post` + `transformIndexHtml`）、产物归集（`apply: 'build'` + `closeBundle`）。

### Q14: 自研虚拟入口插件：`resolveId` / `load` / `configureServer` 各干什么？（第 04 篇）

- **结论**：`pages.config.ts` 是单一数据源，插件按 pageKey 现场拼 HTML / 虚拟模块，实现"一份模板 + 一个配置 = N 个页面"。
- **原理**：构建态 `resolveId` 把不存在的入口声明为虚拟模块，`load` 返回模板 + 占位符替换的 `main.ts`；开发态 `configureServer` 中间件直接 `res.end(htmlHandle(page))`。
- **边界**：模板只读一次并缓存在闭包（避免每页重复 IO）；`pageKey` 从路径取最后两段兼容简写；必须 `enforce: 'pre'` 早于 Vite 内置 HTML 处理。
- **追问**：为什么 `enforce: 'pre'`？→ 必须早于 Vite 内置 HTML 处理。
- **场景**：Vite 官方 MPA 要求每页一个物理 HTML，页面上量后模板冗余；插件让它零模板代码。

### Q15: `manualChunks` 怎么按变更频率切分？（第 03 篇）

- **结论**：按变更频率 + 复用范围切分：vendor（框架）→ ui（组件库）→ utils（工具）→ 页面 chunk。
- **原理**：框架/组件库几乎不变 → 单独一层长期命中浏览器缓存；业务代码高频变 → 单独一层发布只失效这一层。
- **边界**：切太细导致请求多、缓存碎片化；依赖循环引用会报错。
- **追问**：为什么文件名要扁平化？→ 便于发布系统与 CDN 规则统一。
- **场景**：简历项目四层分包：vue/vue-router/pinia、vant、axios/lodash、每页独立 chunk。

### Q16: 脚手架/Monorepo 里怎么做到"新增页面零模板代码"？（第 04 篇）

- **结论**：把"新增页面"的模板步骤固化成配置 + 插件，新增页面 = 加一条配置，不用复制粘贴模板。
- **原理**：`pages.config.ts` 单一数据源（页面 key/入口/元信息），虚拟入口插件在 dev/build 现场生成 HTML 与入口；脚手架生成器同样由配置驱动。
- **边界**：零模板的前提是页面形态同构（同一种壳）；差异过大的页面仍需自定义；配置是收敛口，字段缺失要有默认值兜底。
- **追问**：怎么保证新增页面不破坏现有页面？→ 配置校验 + 页面级构建产物隔离（按页构建、按页发布、按页回归）。
- **场景**：借钱业务 H5 从 Weex 转 Vue3 MPA，新增页面 = `pages.config.ts` 加一条，构建入口、开发导航、测试范围全部派生。

## 五、工程选型

### Q17: MPA vs SPA 的工程取舍？页面上量后为什么转 MPA？（附录）

- **结论**：不是技术优劣，是运维成本——页面上量后发布与回归成本成为主要矛盾时转 MPA。
- **原理**：SPA 整包发布、全量回归；MPA 按页构建、按页发布、按页回归。
- **边界**：MPA 代价是构建配置复杂度上升、页面间无法共享内存态；公共依赖需构建配置复用（否则重复打包）。
- **追问**：多页的公共依赖怎么切？→ 按变更频率 + 复用范围分层（manualChunks）。
- **场景**：借钱业务 H5 从 Weex 转 Vue3 MPA；`pages.config.ts` 唯一配置中心，新增页面 = 加一条配置。

### Q18: 浏览器兼容策略怎么基于真实 UA 分布决策？（附录）

- **结论**：基于真实 UA 分布做决策，而不是无脑双包。
- **原理**：目标浏览器（iOS 11+ / Android Chrome 61+）全部支持 ES Module → 不出 legacy 双包，只出单版本 ESM + `modernPolyfills` 按需注入 polyfill。
- **边界**：`renderLegacyChunks: false` 明确关掉 legacy——口径是"单版本 ESM + 按需 polyfill"，别说成"做了 legacy 双包"。
- **追问**：`modulePreload` 踩过什么坑？→ iOS 部分内核预加载失败且无降级导致白屏，关闭 `modulePreload` 并在配置处注释防回改。
- **场景**：覆盖率 iOS 11+ 约 99.97%、Android Chrome 61+ 约 99.83%，放弃极低占比的 iOS 10- / Android 8- 为可接受风险。
