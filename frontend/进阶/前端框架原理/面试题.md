# 模块面试题 · 前端框架原理

## 1. 渲染与更新的双阶段模型

### Q1（1.1）｜ React 的一次更新为什么要分成 render 和 commit 两个阶段？

- **判断**：渲染 = Render（纯计算、可中断）+ Commit（副作用、不可中断）两阶段，前者算差异、后者落地。
- **展开**：Render 阶段是纯函数式的，只构建新的虚拟 DOM / Fiber 树并计算 diff（哪些节点增、删、改），**不修改真实 DOM**，因此可以暂停、恢复、丢弃重做；Commit 阶段把变更一次性应用到真实 DOM，并执行 `useEffect` / `useLayoutEffect`、生命周期、ref 赋值，**必须同步完成**，一旦开始就不能被打断。
- **边界**：两条铁律——Render 阶段不允许有副作用（一律推迟到 Commit）；Commit 阶段是命令式的，绝对不能"半途而废"，否则页面闪现中间态。可追问：把 render 拆成可中断小任务，是为了让高优先级操作（输入、点击）能"插队"执行，这是并发特性的核心价值。

### Q2（1.2）｜ Fiber 是什么？它如何让 React 的渲染变得可中断？

- **判断**：Fiber 是普通 JS 对象、对"一个组件的单元工作"的描述，靠 `child` / `sibling` / `return` 指针构成双向链表树，把大更新拆成可逐个处理的小单元。
- **展开**：React 15 之前的协调是递归遍历整棵组件树，**一旦开始就无法中断**；Fiber 链表可遍历，React 每次只处理一个 Fiber，处理完检查是否有空闲时间（`deadline.timeRemaining()`）与更高优先级任务，再决定继续还是让出主线程——这就是时间切片（Time Slicing）。
- **佐证**：
  ```
  递归遍历组件树    →  无法中断（React 15）
  child/sibling/return 指针链表 →  每次处理一个单元、可检查空闲再继续（Fiber）
  ```
- **边界**：双缓存同时维护 current（屏幕上的树）与 workInProgress（内存中的新树），构建中被打断 current 不受影响，完成后一次性原子切指针，天然满足"Commit 不可中断"。可追问：这是 React 调度器（Scheduler）的雏形，利用类似 `requestIdleCallback` 的机制获取空闲时间片分片执行。

### Q3（1.3）｜ 时间切片会让渲染变得更快吗？

- **判断**：不会。切片不改变工作总量，只把"一次长阻塞"换成"多次短阻塞"——换的是响应性，不是总时长。
- **展开**：mini-react 里 `workLoop(dl)` 每处理一个工作单元就问一次 `dl.timeRemaining()`，<1ms 就让出主线程。实测渲染 4000 项列表（8002 个宿主节点）：
  ```
  一次跑完    18.1 ms   最长阻塞 18.1 ms
  每片 2ms    19.6 ms(+8%)  切 11 片  最长阻塞 5.8 ms
  ```
- **边界**：有两处**根本切不动**——第一片特别长（执行 `List` 组件函数、造 4000 个 vnode 是一整件事），最后一片长（后面紧跟 commit、所有 DOM 写入必须一次做完）。所以"组件自己算得久"时间切片救不了，那是 memo 与虚拟列表要解决的。可追问：它价值场景很具体——让输入、点击这类高优先级操作插进短空隙。

## 2. 虚拟 DOM 与 diff

### Q4（2.1）｜ 虚拟 DOM 是什么？为什么需要它？

- **判断**：虚拟 DOM 是真实 DOM 的内存镜像——由 type / props / children 构成的普通 JS 对象树；更新时先改便宜的虚拟 DOM、diff 出最小操作集再一次性应用到真实 DOM。
- **展开**：React 元素描述 UI 结构；数据变化构建新树与旧树 diff，算出最小 DOM 操作集合后在 commit 阶段统一落地。核心价值不是"比手写 DOM 操作快"，而是**把 UI 变成可编程的数据**，从而支撑声明式更新与跨平台渲染（React Native / 小程序）。
- **边界**：直接手写 DOM 的极端优化场景可能更快；真实收益是批量最小化操作、跨平台能力与声明式心智，性能上限要靠稳定 key 与 memo 等配合。可追问：虚拟 DOM 一定比直接操作 DOM 快吗？→ 不一定——它给的是可维护性与跨平台，diff 保证"以最小代价过渡"。

### Q5（2.2）｜ React 的 diff 算法基于哪些启发式假设？为什么复杂度是 O(n)？

- **判断**：基于三条启发式——不同类型直接重建、同类型只更新 props、同层兄弟用 key 定位，把 diff 从 O(n³) 压到 O(n)。
- **展开**：① 新旧根节点 type 不同（如 `div` 变 `span`）直接销毁旧节点及其整棵子树重建；② type 相同保留原 DOM 节点，只在 props 上做最小更新（只 update 变化的属性）；③ 子元素是数组时，用 key 识别哪些节点是"同一个"，避免不必要的重建（`isSameVNodeType` 只比较 `type` 与 `key`）。
- **边界**：启发式是"假设"，依赖实际项目里树结构稳定、同层移动这一前提，极端情况下会退化为重建；它不是暴力 O(n³) 逐节点比较。可追问：diff 的全部意义是"以最小真实 DOM 操作代价"从旧树过渡到新树——直接重建整棵树正确但代价巨大。

### Q6（2.3）｜ `key` 为什么是节点上的独立字段，而不是放进 `props`？

- **判断**：因为 `key` 只参与"这次更新该复用谁"的匹配，不参与属性更新；把它留在 props 里会让两件事混在一起。
- **展开**：两边的 `createElement` / `createVNode` 都把它摘出来单独存——React 用 `const { key = null, ...props } = config || {}`，Vue 在 `createBaseVNode` 里写成 `key: props && props.key != null ? props.key : null`。之后 diff 只比较 `type` 与 `key`，属性更新那边统一跳过 `key`。
- **佐证**：正因它是"身份"而不是"属性"，值必须归一——`props ? props.key : null` 会让"有 props 但没有 key"的节点拿到 `undefined`，而 `null !== undefined` 会被判成"类型变了"，于是每次更新整棵重建、事件监听全部重挂。这个坑 mini-vue 真实踩到过：只渲染一次的用例全绿，只有"渲染三次、中间摘掉 `onClick`"那条挂了。
- **边界**：可追问：`key` 的取值还会出现在"按下标退化"的分支里——没有 key 时用下标当身份，这正是 index 陷阱的源头。

### Q7（2.3）｜ key 在列表 diff 中起什么作用？为什么不能用 index 当 key？

- **判断**：key 让 React 识别"哪个节点是同一个"，头部插入时只新增缺失项、复用其余 DOM；用 index 当 key 会引发不必要的更新与状态错乱。
- **展开**：有 key 时 React 能识别 a/b/c 是"同一节点被移动"，只新增 x，复用其余三个 DOM；没有 key（或用 index）只能按索引对号入座——index 0 的新元素与旧元素被视为同一个，A/B/C 被依次"更新"、最后删除一个。
- **佐证**：
  ```
  头部插入 x：有 key → 最多 1 次新增（真实 Vue 先算 LIS 更省），复用 a/b/c
              无 key / index → A/B/C 依次就地改写 + 1 次删除
  ```
- **边界**：性能差只是其一，更严重的是状态错乱——复用错误的组件实例会让输入框内容串位。可追问：动态列表务必给稳定且唯一 key；只有列表静态不可变时才可考虑用 index。

### Q8（2.3）｜ 有 key 与无 key 的列表 diff 差异有多大？有 key 的重排是零成本吗？

- **判断**：差异是量级的——实测删首项无 key 要 5 次宿主操作（4 次就地改写 + 1 次删除）、有 key 只需 1 次；但"有 key 的重排"并非零成本。
- **展开**：Vue3 列表 diff 是双端比较——先头部同步、再尾部同步（最便宜最常见），剩下中间乱序段按 `key` 建 `keyToNewIndex` 索引配对：能复用 `patch`、新增 `patch(null, ...)`、多余 `unmount`；无 key 退化成"按下标对应"。纯重排实测：无 key 6 次全是改内容、一个节点没搬；有 key 3 次全是 `insert` 搬移、一次内容没改。
- **边界**：有 key 的重排也要搬节点——真实 Vue 会先算最长递增子序列（LIS）跳过已在正确位置的（三个节点的重排其实只需搬 1 个）；mini-vue 简化为"从后往前逐个插"所以偏多。另外无 key 的 DOM 结果"看起来是对的"（内容按位置重写），真正出事的是节点上有状态时：输入框内容、焦点、组件内部状态都留在原节点。可追问：所以"加 key"买到的不是"更快"，而是"复用的身份是对的"——性能顺带、正确性才是主因。

### Q9（2.4）｜ 怎么证明一个渲染器是"平台无关"的？

- **判断**：让同一份 runtime-core 跑在两个完全不同的宿主上，对比宿主操作的调用次数——次数逐项相同，就说明核心逻辑里没有一行假设过"节点是 DOM"。
- **展开**：`createRenderer(options)` 把 9 个宿主操作（createElement / createText / createComment / setText / setElementText / insert / remove / nextSibling / patchProp）作为参数注入，组件、patch 分发、列表 diff 全在闭包里，只通过这 9 个函数接触平台。宿主 A 用浏览器 `nodeOps`（跑在假 DOM 上），宿主 B 把节点拼成字符串（相当于 SSR 雏形）。
- **佐证**：实测两个宿主调用次数逐项相同——createElement 3 / setElementText 2 / insert 3 / patchProp 1。
- **边界**：两个必要接口细节——`insert(child, parent, anchor)` 在 anchor 为 null 时即 append（所以不需要单独 `appendChild`）；`patchProp` 把"事件 / DOM property / attribute"三种写法收敛成一个函数（字符串宿主里直接实现成写进 `attrs`）。可追问：同一条机制解释了"为什么 Node 里单测不需要 jsdom"（注入一份假 DOM 操作就够了），也解释多端渲染（DOM / SSR / 小程序 / Canvas）为什么只是换一份 `nodeOps`。

## 3. 响应式原理

### Q10（3.1）｜ Vue3 用 Proxy 做响应式，相比 Vue2 的 Object.defineProperty 优势在哪？

- **判断**：Proxy 代理整个对象，天然支持属性新增 / 删除、数组操作、Map / Set 集合类型；Object.defineProperty 只能拦截预先声明的属性。
- **展开**：`reactive` 用 Proxy + Reflect 拦截 `get` / `set` / `deleteProperty` / `has` / `ownKeys`，get 时 `track` 收集依赖、set 时 `trigger` 触发更新；深度响应式在 get 返回对象时自动再代理（按需、惰性）；用 WeakMap 做代理缓存，同一对象只代理一次。
- **边界**：WeakMap 的键必须是对象、是弱引用，正适合"响应式对象 → 依赖"映射——对象不再被引用时可被 GC 自动清理，避免内存泄漏；readonly 不做依赖收集——不可 set 就永远不会触发 trigger，收集没意义。可追问：deleteProperty / has / ownKeys 的拦截让"属性增删、枚举、存在性检测"全部响应式，这是 defineProperty 时代做不到的。

### Q11（3.2）｜ track 和 trigger 是如何完成依赖收集与触发更新的？

- **判断**：依赖结构是 targetMap（WeakMap）→ depsMap（Map）→ dep（Set），get 时 track 把当前 effect 塞进 dep，set 时 trigger 把 dep 里所有 effect 取出来执行。
- **展开**：track 按"找 target 的 depsMap → 找 key 的 dep → trackEffects 加入 activeEffect"走，已收集过则跳过；trigger 取出该 key 的 dep 逐个执行——effect 有 `scheduler` 就调 scheduler（自定义执行时机），否则 `effect.run()`。
- **佐证**：
  ```
  targetMap(WeakMap: 对象) → depsMap(Map: 属性) → dep(Set: effect 集合)
  track(get 时): activeEffect 收进 dep      trigger(set 时): 取 dep 执行全部 effect
  ```
- **边界**：activeEffect 是全局"进行中的副作用"实例，`isTracking()` 判断当前能否收集；scheduler 的意义是让框架自己决定副作用何时执行——Vue 靠它把多次更新合并到下一个微任务，实现 nextTick 异步批量更新。可追问：`effect.stop()` 通过 track 时记录的 `effect.deps` 反向把自己从所有 dep 删除；组件卸载时自动停止相关 effect 防内存泄漏。

## 4. 编译优化与运行时

### Q12（4.2）｜ Vue3 的模板编译做了哪些优化？与运行时 diff 如何配合？

- **判断**：编译期给节点打 PatchFlags 静态标记，运行时只对动态节点做精细 diff，静态节点直接跳过——这是 Vue3 相比 Vue2 在编译层的重要性能优化。
- **展开**：compiler-core 走"解析（模板 → AST）→ 转换（递归遍历节点，标记静态节点、缓存动态绑定）→ 代码生成（AST → render 函数）"；含插值 / 指令 / 绑定的节点标记为动态，纯静态节点不参与更新、甚至只创建一次。
- **佐证**：`<code v-pre>{{ count }}</code>` 编译成 `_createElementVNode("p", null, toDisplayString(count), 1)`——位 1 表示含动态文本。
- **边界**：判断标准是"节点是否动态"——只有动态节点才需要更新时对比；运行时按 VNode 上的 patch flag 决定比对范围，大量静态 DOM 直接跳过。可追问：这是"用编译换说法"的典型——能提前确定的信息在编译期处理，运行时只做不得不做的；官方 `template-explorer` 可直观查看不同模板编译出的 render 与 patchFlags。

### Q13（4.3）｜ 一次同步代码里改了三次状态，为什么最后只渲染一次？

- **判断**：因为组件的渲染函数被包成了一个带 scheduler 的 effect，数据变化时只把同一个 job 推进微任务队列，`queue.includes(job)` 保证去重，所以三次修改换来一次渲染。
- **展开**：`setupRenderEffect` 里 `instance.update = effect(componentUpdateFn, { scheduler: () => queueJob(instance.update) })`；`queueJob` 先判重再 `queueFlush`，后者用 `Promise.resolve().then(flushJobs)` 排到微任务；`flushJobs` 先取队列快照再执行（执行期间新推入的留到下一轮）。`nextTick` 挂在同一个 flush promise 上，所以能等到"DOM 已经最新"。
- **边界**：批处理不是额外实现的功能，而是"把渲染交给调度器"的自然结果；如果绕过调度器同步反复调用渲染函数，就是每次修改渲染一轮（mini-react 的 `sync: true` 模式同理）。实测：三次赋值后立刻读渲染次数 +0、DOM 还是旧文案，`await nextTick()` 之后 +1、DOM 变最终值。可追问：这也是为什么"在框架之外改状态"（原生事件、`setTimeout`）容易出现多次渲染——那时调度器不在同一条微任务链上。

### Q14（4.1）｜ Vue3 的编译、运行时、响应式三大模块如何协作？nextTick 批量更新在其中扮演什么角色？

- **判断**：用编译换说法、用响应式驱动、用运行时落地——编译产出 render 函数，响应式感知数据变化并通知，运行时把 VNode 以最小代价落地到真实 DOM。
- **展开**：compiler-sfc 拆 .vue 三块、compiler-core 把模板编译成 render（含静态标记）；`createApp(App).mount(root)` → `createVNode(App)` 得根 VNode → `render` → `patch(null, vnode, container)` 按 shapeFlag 分发挂载；组件 render 每次执行被一个渲染 effect 包裹，数据变化触发 track / trigger 后经 scheduler 不立即渲染，而是 queueJob 把更新推进队列、下一微任务统一执行。
- **边界**：异步批量更新的价值是合并同一轮内多次数据变更、只渲染一次；nextTick 就是"等这批更新落定后再拿最新 DOM"的机制。运行时核心 runtime-core 平台无关，runtime-dom 通过 `createRenderer` 注入 createElement / insert / remove / patchProp 等宿主操作——所以 Vue 支持 DOM / SSR / 小程序等多端。可追问：理解 reactive（对象代理）与 effect（副作用调度）两根"脊梁"，再顺着 patch 这条"主干"展开运行时，最后接上编译产物（render 函数），整个 Vue3 机制就清晰了。

## 5. Hooks 机制与优化

### Q15（5.1）｜ Hooks 为什么必须按固定顺序在顶层调用？

- **判断**：因为 Hooks 是按调用顺序挂在组件对应 Fiber 节点的链表（`fiber.memoizedState`）上的，顺序一变就会错位。
- **展开**：每个函数组件的 Fiber 节点上有一条 hooks 链表，每个 hook 节点含 `memoizedState`（状态 / deps）、`queue`（更新队列）、`next`（下一节点）；首次渲染依次创建节点，后续渲染沿 `next` 复用旧节点读旧值、把新 setState 入队。
- **边界**：hooks 放 if / 循环里，第二次渲染的读取顺序与上次不一致，状态就错位——这就是"不能条件调用 Hooks"的原因；每个组件各有自己的 Fiber 与链表、互不干扰，React 用 `currentFiber` 全局指针定位"现在处理的是哪个组件"。可追问：`useEffect` 的依赖比较也在链上——deps 存进 hook 节点，渲染时浅比较新旧 deps，不同才在 Commit 阶段执行副作用。

### Q16（5.2）｜ React.memo、useMemo、useCallback 分别优化什么？为什么 memo 有时不生效？

- **判断**：`React.memo` 缓存整个组件、`useMemo` 缓存计算结果、`useCallback` 缓存函数引用；memo 是浅比较，props 引用不稳定就会失效。
- **展开**：父组件 state 变化默认递归渲染所有子组件，`React.memo` 在 props **浅比较相等**时跳过该子组件渲染；`useMemo` 只在依赖项变化时才重新计算、否则返回缓存；`useCallback` 是 `useMemo` 的语法糖（`useMemo(() => fn, deps)` 等价于 `useCallback(fn, deps)`）。
- **边界**：memo 是浅比较——传入 props 若是每次渲染新建的对象 / 内联箭头函数，memo 会失效，必须配合 `useCallback` / `useMemo` 保持引用稳定；官方提醒"可以把 useMemo 作为性能优化手段，但不要当成语义上的保证"，控制权在 React。可追问：减少渲染的综合手段还有状态上移 / 下移、拆分组件、合理分层（Layout、导航用 memo 包裹）、避免内联对象 / 函数作为 props。

## 7. 状态管理

### Q17（7.4）｜ 依赖追踪为什么能把"通知谁"精确到字段？它和"订阅整个 store"差在哪？

- **判断**：因为依赖表记的是「字段 → 读过它的 effect」，订阅单位是字段而不是 store；改一个切片时只有读过它的 effect 被唤醒（实测 1/3）。
- **展开**：`track` 在 `get` 时把 `activeEffect` 收进 `target → key → dep` 三层表的对应集合，`trigger` 在 `set` 时只取这个字段的集合并执行；`effect` 每次重跑前先 `cleanup` 把旧 dep 引用摘掉，再按本次实际读到的字段重新收集——所以依赖是"运行时读出来的"，会随分支变化（实测：`flag` 从 true 切到 false 之后再改 `a`，effect 不再被唤醒）。
- **边界**：精确的代价有三处——`activeEffect` 是全局状态，跨越 `await` / 异步边界后依赖容易丢；追踪本身有开销（每次读写进出依赖表）；省掉的是"叫醒"，但每次 `set` 仍要做一次 `Object.is` 与 Map/Set 查找。实测 reducer + 选择器与依赖追踪的重渲染次数相同（都是 1），差别在被唤醒：3 次 vs 1 次。可追问：这也解释了 `computed` 为什么能"读两次只算一次"——getter 也是 lazy effect，依赖变了只置脏，真重算等到有人读 `value`（实测计算次数依次 1 → 1 → 2 → 2）。

### Q18（7.2）｜ 页面"数据变了但界面没动"，怎么排查？

- **判断**：先确认状态是不是被**原地修改**了——绕过 store 的写入口，订阅者不会收到任何通知，而且不会报错。
- **展开**：三条路线的通知都建立在"引用比较"上——reducer 靠 `combineReducers` 逐片 `Object.is`、`setState` 靠逐键 `Object.is`、依赖追踪靠 `set` 里的 `Object.is`。原地改只动了对象内容、引用没变，判断层认为"什么都没发生"。实测：直接 `store.getState().cart.items = 99`，订阅者被叫醒 **0** 次，但它读到的已是 99。
- **边界**：这类问题在"嵌套对象 + 数组 `push` / `splice`"上最常见，顶层键常被重新赋值（看起来"改了"）、内层却原地改。两个排查手段——① 开发期递归 `Object.freeze`，原地改直接抛错；② 用不可变工具（`immer` / `structuredClone`）替代手写展开。另要区分另一种"界面没动"：选择器返回新对象造成的是**多**渲染，不属于这类。可追问：这也是值得开"状态只读类型"（`Readonly<State>`）的理由——类型层面拦住一部分原地写。

### Q19（7.5）｜ 场景：一次更新之后有 30 个组件重渲染，只有 2 个该动，怎么定位和收敛？

- **判断**：先分清是"被叫醒太多"还是"叫醒之后没拦住"——两个指标要分开数，收敛手段完全不同。
- **展开**：用对照方法把两个量分开——给 store 的 `subscribe` 装计数器数"被唤醒次数"，给每个组件装渲染计数数"重渲染次数"。实测同一次更新：
  ```
  订阅整棵树 reducer    3 被唤醒 / 3 重渲染
  按切片的选择器         3 被唤醒 / 1 重渲染
  依赖追踪路线           1 被唤醒 / 1 重渲染
  ```
- **边界**：三个收敛动作按代价从低到高——① 让选择器返回扁平基本类型（避免 `Object.is` 失守：实测"选择器返回新对象"时无关更新也重渲染 3 次，用 `shallowEqual` 后降到 0）；② 需要返回对象时配记忆化选择器；③ 连"被唤醒"都嫌多，才考虑把订阅单位下沉到字段。别一上来就换库：多数"30 个组件重渲染"是选择器返回值不稳定造成的，换库不解决。可追问：还要查一笔易忽略的成本——选择器每次通知都会跑一遍（实测 2 次通知 = 2 次选择器调用），重选择器要配记忆化；以及一轮连续 `setState` 10 次就是 30 次通知 / 10 次渲染，批处理要靠合并成一次函数式 `setState`，或让调度器把渲染推迟到下一个微任务。
