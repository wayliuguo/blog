# 模块面试题 · 前端框架原理

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../../进阶/面试方法论.md)的四步答题法——结论/原理/边界/追问。
> 题目来源：`React 高级与原理`、`Vue3 原理`、`手写 mini-react`、`手写 mini-vue`四篇正文实际讲到的点，覆盖 React（Fiber 与可中断并发、虚拟 DOM 与 diff、render/commit 两阶段、Hooks 顺序与 Fiber 链表、key 的作用、memo/useMemo/useCallback 优化）与 Vue3（Proxy 响应式、track/trigger、虚拟 DOM diff、模板编译与静态标记、nextTick 批量更新、三大模块协作链路），以及两篇手写实现里实测出来的量（时间切片的阻塞时长、有 / 无 key 的宿主操作次数、两个宿主的调用次数对照）。

## 一、基础概念

### Q1: 虚拟 DOM 是什么？为什么需要它？（第 1 篇）

- **结论**：虚拟 DOM 是真实 DOM 的内存镜像——由 type / props / children 构成的普通 JS 对象树；更新时先改便宜的虚拟 DOM、diff 出最小操作集再一次性应用到真实 DOM。
- **原理**：React 元素描述 UI 结构；数据变化构建新树与旧树 diff，算出最小 DOM 操作集合后在 commit 阶段统一落地；核心价值不是"比手写 DOM 操作快"，而是把 UI 变成可编程的数据，从而支撑声明式更新与跨平台渲染（React Native / 小程序）。
- **边界**：直接手写 DOM 的极端优化场景可能更快；真实收益来自批量最小化操作、跨平台能力与声明式心智，性能上限要靠稳定 key 与 memo 等配合。
- **追问**：虚拟 DOM 一定比直接操作 DOM 快吗？→ 不一定——它提供的是可维护性与跨平台，diff 保证"以最小代价过渡"。

### Q2: `key` 为什么是节点上的独立字段，而不是放进 `props`？（第 3 · 4 篇）

- **结论**：因为 `key` 只参与"这次更新该复用谁"的匹配，不参与属性更新；把它留在 props 里会让两件事混在一起。
- **原理**：两边的 `createElement` / `createVNode` 都把它摘出来单独存——React 用 `const { key = null, ...props } = config || {}`，Vue 在 `createBaseVNode` 里写成 `key: props && props.key != null ? props.key : null`。之后 diff 只需要比较 `type` 与 `key`（`isSameVNodeType`），属性更新那边则统一跳过 `key`。
- **边界**：正因为它是"身份"而不是"属性"，值必须归一——`props ? props.key : null` 这种写法会让"有 props 但没有 key"的节点拿到 `undefined`，而 `null !== undefined` 会被判成"类型变了"，于是每次更新都整棵重建、事件监听器全部重挂。这个坑在 mini-vue 里真实踩到过：只渲染一次的用例全绿，只有"渲染三次、中间摘掉 `onClick`"那条挂了。
- **追问**：`key` 的取值还会出现在"按下标退化"的分支里——没有 key 时用下标当身份，这正是 index 陷阱的源头。

## 二、机制与原理

### Q3: React 的一次更新为什么要分成 render 和 commit 两个阶段？（第 1 篇）

- **结论**：渲染 = Render（纯计算、可中断）+ Commit（副作用、不可中断）两阶段，前者算差异、后者落地。
- **原理**：Render 阶段是纯函数式的，只构建新的虚拟 DOM / Fiber 树并计算 diff（哪些节点增、删、改），**不修改真实 DOM**，因此可以暂停、恢复、丢弃重做；Commit 阶段把变更一次性应用到真实 DOM，并执行 `useEffect` / `useLayoutEffect`、生命周期、ref 赋值，**必须同步完成**，一旦开始就不能被打断。
- **边界**：两条关键原则——Render 阶段不允许有副作用，副作用一律推迟到 Commit；Commit 阶段是命令式的，绝对不能"半途而废"，否则页面会闪现中间态。
- **追问**：把 render 拆成可中断的小任务，是为了让高优先级操作（输入、点击）能"插队"执行，这正是并发特性的核心价值。

### Q4: Fiber 是什么？它如何让 React 的渲染变得可中断？（第 1 篇）

- **结论**：Fiber 是普通 JS 对象、对"一个组件的单元工作"的描述，靠 `child` / `sibling` / `return` 指针构成双向链表树，把大更新拆成可逐个处理的小单元。
- **原理**：React 15 之前的协调是递归遍历整棵组件树，**一旦开始就无法中断**；Fiber 链表可遍历，React 每次只处理一个 Fiber，处理完检查是否有空闲时间（`deadline.timeRemaining()`）与更高优先级任务，再决定继续还是让出主线程——这就是时间切片（Time Slicing）。
- **边界**：双缓存机制同时维护 current（屏幕上的树）与 workInProgress（内存中构建的新树），构建中被打断 current 不受影响，完成后一次性把指针切过去，切换是原子的，天然满足"Commit 不可中断"。
- **追问**：这是 React 调度器（Scheduler）的雏形，利用类似 `requestIdleCallback` 的机制获取空闲时间片分片执行工作。

### Q5: React 的 diff 算法基于哪些启发式假设？为什么复杂度是 O(n)？（第 1 篇）

- **结论**：基于三条启发式——不同类型直接重建、同类型只更新 props、同层兄弟用 key 定位，把 diff 从 O(n³) 压到 O(n)。
- **原理**：① 新旧树根节点 type 不同（如 `div` 变 `span`，或组件类型变化），直接销毁旧节点及其整棵子树重建；② type 相同，保留原 DOM 节点，只在 props 上做最小更新（只 update 变化的属性）；③ 子元素是数组时，用 key 识别哪些节点是"同一个"，避免不必要的重建。
- **边界**：启发式是"假设"，依赖实际项目里树结构稳定、同层移动这一前提，极端情况下会退化为重建；它不是暴力 O(n³) 逐节点比较。
- **追问**：diff 的全部意义是"以最小的真实 DOM 操作代价"从旧树过渡到新树——直接重建整棵树正确但代价巨大。

### Q6: Hooks 为什么必须按固定顺序在顶层调用？（第 1 篇）

- **结论**：因为 Hooks 是按调用顺序挂在组件对应 Fiber 节点的链表（`fiber.memoizedState`）上的，顺序一变就会错位。
- **原理**：每个函数组件的 Fiber 节点上有一条 hooks 链表，每个 hook 节点含 `memoizedState`（状态 / deps）、`queue`（更新队列）、`next`（指向下一个 hook）；首次渲染依次创建节点，后续渲染沿 `next` 复用旧节点读旧值、把新 setState 入队。
- **边界**：hooks 放在 if / 循环里，第二次渲染的读取顺序与上次不一致，状态就会错位——这就是"不能条件调用 Hooks"的原因；每个组件各有自己的 Fiber 与链表，互不干扰，React 用 `currentFiber` 全局指针定位"现在处理的是哪个组件"。
- **追问**：`useEffect` 的依赖比较也在这条链表上——deps 存进 hook 节点，渲染时浅比较新旧 deps，不同才在 Commit 阶段执行副作用。

### Q7: Vue3 用 Proxy 做响应式，相比 Vue2 的 Object.defineProperty 优势在哪？（第 2 篇）

- **结论**：Proxy 代理整个对象，天然支持属性新增 / 删除、数组操作、Map / Set 集合类型；Object.defineProperty 只能拦截预先声明的属性。
- **原理**：`reactive` 用 Proxy + Reflect 拦截 `get` / `set` / `deleteProperty` / `has` / `ownKeys`，get 时 `track` 收集依赖、set 时 `trigger` 触发更新；深度响应式在 get 返回对象时自动再代理（按需、惰性）；用 WeakMap 做代理缓存，同一对象只代理一次。
- **边界**：WeakMap 的键必须是对象、是弱引用，正适合"响应式对象 → 依赖"的映射场景，对象不再被引用时可被 GC 自动清理，避免内存泄漏；readonly 不做依赖收集——不可 set 就永远不会触发 trigger，收集没有意义。
- **追问**：deleteProperty / has / ownKeys 的拦截让"属性的增删、枚举、存在性检测"全部响应式，这是 defineProperty 时代做不到的。

### Q8: track 和 trigger 是如何完成依赖收集与触发更新的？（第 2 篇）

- **结论**：依赖结构是 targetMap（WeakMap）→ depsMap（Map）→ dep（Set），get 时 track 把当前 effect 塞进 dep，set 时 trigger 把 dep 里所有 effect 取出来执行。
- **原理**：track 按"找 target 的 depsMap → 找 key 的 dep → trackEffects 加入 activeEffect"走，已收集过则跳过；trigger 取出该 key 的 dep，逐个执行——effect 有 `scheduler` 就调 scheduler（自定义执行时机），否则 `effect.run()`。
- **边界**：activeEffect 是全局"进行中的副作用"实例，`isTracking()` 判断当前能否收集；scheduler 的意义是让框架自己决定副作用何时执行——Vue 正是靠它把多次更新合并到下一个微任务，实现 nextTick 异步批量更新。
- **追问**：`effect` 的 `.stop()` 通过 track 时记录的 `effect.deps` 反向把自己从所有 dep 中删除；组件卸载时自动停止相关 effect，防止内存泄漏。

### Q9: Vue3 的模板编译做了哪些优化？与运行时 diff 如何配合？（第 2 篇）

- **结论**：编译期给节点打 PatchFlags 静态标记，运行时只对动态节点做精细 diff，静态节点直接跳过——这是 Vue3 相比 Vue2 在编译层的重要性能优化。
- **原理**：compiler-core 走"解析（模板 → AST）→ 转换（递归遍历节点，标记静态节点、缓存动态绑定）→ 代码生成（AST → render 函数）"；含插值 / 指令 / 绑定的节点标记为动态（如 `_createElementVNode("p", null, toDisplayString(count), 1)`，位 1 表示含动态文本），纯静态节点不参与更新、甚至只创建一次。
- **边界**：判断标准是"节点是否动态"——只有动态节点才需要更新时对比；运行时按 VNode 上的 patch flag 决定比对范围，大量静态 DOM 直接跳过。
- **追问**：这是"用编译换说法"的典型——能提前确定的信息在编译期处理，运行时只做不得不做的事；官方 `template-explorer` 可直观查看不同模板编译出的 render 与 patchFlags。

### Q10: 时间切片会让渲染变得更快吗？（第 3 篇）

- **结论**：不会。切片不改变工作总量，只把"一次长阻塞"换成"多次短阻塞"——换的是响应性，不是总时长。
- **原理**：mini-react 里 `workLoop(dl)` 每处理一个工作单元就问一次 `dl.timeRemaining()`，小于 1ms 就把主线程让出去；实测渲染 4000 项列表（8002 个宿主节点），一次跑完 18.1 ms、最长阻塞 18.1 ms；每次只给 2 ms 时间片则是总耗时 19.6 ms（+8%）、切 11 片、最长阻塞 5.8 ms。
- **边界**：有两处**根本切不动**——第一片特别长（6.8 ms），因为它包含执行 `List` 组件函数，造 4000 个 vnode 是一整件事，不可再分；最后一片也长（9.2 ms），因为它后面紧跟 commit，所有 DOM 写入必须一次做完。所以"组件自己算得久"这种问题，时间切片救不了，那是 memo 与虚拟列表要解决的。
- **追问**：既然是"多个短卡顿"，那它的价值场景就很具体——让输入、点击这类高优先级操作有机会插进这些短空隙里。

### Q11: 一次同步代码里改了三次状态，为什么最后只渲染一次？（第 4 篇）

- **结论**：因为组件的渲染函数被包成了一个带 scheduler 的 effect，数据变化时只把同一个 job 推进微任务队列，`queue.includes(job)` 保证去重，所以三次修改换来一次渲染。
- **原理**：`setupRenderEffect` 里 `instance.update = effect(componentUpdateFn, { scheduler: () => queueJob(instance.update) })`；`queueJob` 先判重再 `queueFlush`，后者用 `Promise.resolve().then(flushJobs)` 排到微任务；`flushJobs` 先取队列快照再执行（执行期间新推入的留到下一轮）。`nextTick` 挂在同一个 flush promise 上，所以能等到"DOM 已经最新"。
- **边界**：批处理不是额外实现的功能，而是"把渲染交给调度器"的自然结果；反过来，如果绕过调度器同步地反复调用渲染函数，就是每次修改渲染一轮（mini-react 的 `sync: true` 模式同理）。实测：三次赋值后立刻读渲染次数 +0、DOM 还是旧文案，`await nextTick()` 之后 +1、DOM 变成最终值。
- **追问**：这也是为什么"在框架之外改状态"（原生事件、`setTimeout`）容易出现多次渲染——那时调度器不在同一条微任务链上。

## 三、排障与选型

### Q12: key 在列表 diff 中起什么作用？为什么不能用 index 当 key？（第 1 篇）

- **结论**：key 让 React 识别"哪个节点是同一个"，头部插入时只新增缺失项、复用其余 DOM；用 index 当 key 会引发不必要的更新与状态错乱。
- **原理**：有 key 时 React 能识别 a/b/c 是"同一节点被移动"，只新增 x，复用其余三个 DOM；没有 key（或用 index），React 只能按索引对号入座——index 0 的新元素与旧元素被视为同一个，A/B/C 被依次"更新"、最后删除一个。
- **边界**：性能差只是其一，更严重的是状态错乱——复用错误的组件实例会让输入框内容串位。
- **追问**：动态列表务必给稳定且唯一的 key；只有列表静态不可变时才可考虑用 index。

### Q13: React.memo、useMemo、useCallback 分别优化什么？为什么 memo 有时不生效？（第 1 篇）

- **结论**：`React.memo` 缓存整个组件、`useMemo` 缓存计算结果、`useCallback` 缓存函数引用；memo 是浅比较，props 引用不稳定就会失效。
- **原理**：父组件 state 变化默认会递归渲染所有子组件，`React.memo` 在 props **浅比较相等**时跳过该子组件渲染；`useMemo` 只在依赖项变化时才重新计算，否则返回缓存结果；`useCallback` 是 `useMemo` 的语法糖（`useMemo(() => fn, deps)` 等价于 `useCallback(fn, deps)`），用于缓存函数引用。
- **边界**：memo 是浅比较——传入的 props 若是每次渲染新建的对象 / 内联箭头函数，memo 会失效，必须配合 `useCallback` / `useMemo` 保持引用稳定；官方提醒"可以把 useMemo 作为性能优化的手段，但不要把它当成语义上的保证"，控制权在 React。
- **追问**：除三板斧外，减少渲染的综合手段还有状态上移 / 下移、拆分组件、合理分层（Layout、导航用 memo 包裹）、避免内联对象 / 函数作为 props。

### Q14: 有 key 与无 key 的列表 diff 差异有多大？有 key 的重排是零成本吗？（第 4 篇）

- **结论**：差异是量级的——实测删掉列表第一项，无 key 要 5 次宿主操作（4 次就地改写 + 1 次删除），有 key 只要 1 次；但"有 key 的重排"并非零成本。
- **原理**：Vue3 的列表 diff 是双端比较——先从头部同步、再从尾部同步（这两步最便宜也最常见），剩下的中间乱序段才按 `key` 建 `keyToNewIndex` 索引配对，能复用的 `patch`、新增的 `patch(null, ...)`、多余的 `unmount`；无 key 的节点退化成"按下标对应"。纯重排场景实测：无 key 6 次操作全是改内容、一个节点都没搬；有 key 3 次操作全是 `insert` 搬移、一次内容都没改。
- **边界**：有 key 的重排也要搬节点——真实 Vue 会先算最长递增子序列（LIS），跳过本来就在正确位置的那些，三个节点的重排其实只需搬 1 个；这份实现为了好读简化成"从后往前逐个插"，所以次数偏多。另外无 key 的 DOM 结果"看起来是对的"（内容按位置重写），真正出事的是节点上有状态时：输入框内容、焦点、组件内部状态都留在原节点上。
- **追问**：所以"加 key"买到的不是"更快"，而是"复用的身份是对的"——性能是顺带的，正确性才是主因。

## 四、场景设计题

### Q15: Vue3 的编译、运行时、响应式三大模块如何协作？nextTick 批量更新在其中扮演什么角色？（第 2 篇）

- **结论**：用编译换说法、用响应式驱动、用运行时落地——编译产出 render 函数，响应式感知数据变化并通知，运行时把 VNode 以最小代价落地到真实 DOM。
- **原理**：compiler-sfc 拆 .vue 三块、compiler-core 把模板编译成 render（含静态标记）；`createApp(App).mount(root)` → `createVNode(App)` 得到根 VNode → `render` → `patch(null, vnode, container)` 按 shapeFlag 分发挂载；组件 render 的每次执行被一个渲染 effect 包裹，数据变化触发 track / trigger 后经 scheduler 不立即渲染，而是 queueJob 把更新推进队列、在下一个微任务统一执行。
- **边界**：异步批量更新的价值是合并同一轮内的多次数据变更、只渲染一次；nextTick 就是"等这批更新落定后再拿最新 DOM"的机制。运行时核心 runtime-core 平台无关，runtime-dom 通过 `createRenderer` 注入 createElement / insert / remove / patchProp 等宿主操作——所以 Vue 能支持 DOM / SSR / 小程序等多端。
- **追问**：理解 reactive（对象代理）与 effect（副作用调度）这两根"脊梁"，再顺着 patch 这条"主干"展开运行时，最后接上编译产物（render 函数），整个 Vue3 的运行机制就清晰了。

### Q16: 怎么证明一个渲染器是"平台无关"的？（第 4 篇）

- **结论**：让同一份 runtime-core 跑在两个完全不同的宿主上，对比宿主操作的调用次数——次数逐项相同，就说明核心逻辑里没有一行假设过"节点是 DOM"。
- **原理**：`createRenderer(options)` 把 9 个宿主操作（createElement / createText / createComment / setText / setElementText / insert / remove / nextSibling / patchProp）作为参数注入，组件、patch 分发、列表 diff 全在闭包里，只通过这 9 个函数接触平台。宿主 A 用浏览器 `nodeOps`（跑在假 DOM 上），宿主 B 把节点拼成字符串（相当于 SSR 的雏形）。实测两个宿主：createElement 3 / setElementText 2 / insert 3 / patchProp 1，逐项相同。
- **边界**：两个必要的接口细节——`insert(child, parent, anchor)` 在 anchor 为 null 时就是 append（所以不需要单独的 `appendChild`）；`patchProp` 把"事件 / DOM property / attribute"三种写法收敛成一个函数，字符串宿主里直接把它实现成写进 `attrs` 即可。官方把 runtime-core 与 runtime-dom 拆成两个包，就是这条结论的工程版本。
- **追问**：同一条机制还解释了"为什么 Node 里单测不需要 jsdom"——测试注入一份假 DOM 操作就够了；也解释了多端渲染（DOM / SSR / 小程序 / Canvas）为什么只是换一份 `nodeOps`。
