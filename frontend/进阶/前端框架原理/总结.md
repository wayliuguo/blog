## 1. 渲染与更新的双阶段模型

本模块的主轴是**「状态到界面的最小代价映射」**：状态/数据变了，框架如何以最小代价把界面更新到最新。第一章用 React 建基线——渲染分两阶段、可中断、用链表组织；Vue3 在同一个问题域里走另一条工程路径（编译期优化 + 响应式）；手写实现把结论写成可单测、可计数的代码；最后一章把状态搬出组件，回答「改完通知谁」。

### 1.1 render / commit 两阶段

React 把一次更新拆成两个性质完全不同的阶段：

```
Render  纯计算、可中断：只构建新虚拟 DOM / Fiber 并算 diff（差异），不碰真实 DOM，不允许副作用
Commit  不可中断、一次性：把变更应用到真实 DOM，并执行 useEffect / useLayoutEffect / 生命周期 / ref 赋值
        ——「纯函数在前、命令式在后」
```

- **并发基础**：render 可被高优先级操作（输入、点击）抢占插队；commit 一旦开始不能半途而废，否则页面会闪现中间态（渲染到一半的真实 DOM）。

### 1.2 Fiber 链表与双缓存

- **Fiber 是普通 JS 对象**：靠 `child` / `sibling` / `return` 三个指针构成双向链表树，把大更新拆成小单元逐个处理——解决 React 15 之前递归遍历整棵树、一旦开始就无法中断的问题。
- **双缓存**：同时维护 current（当前展示）与 workInProgress（内存中构建）两棵树，完成后原子切换指针；构建被打断也不影响屏幕。mini-react 里 `alternate` 即双缓存（新树长好才一次切过去），根按容器区分（`roots` 是 Map），换容器就是另一棵新树。

### 1.3 时间切片与并发特性

- **开启方式**：`ReactDOM.createRoot` 渲染即获得并发（可中断渲染 + 时间切片）能力。
- **低优先级更新**：`startTransition` / `useTransition` 把非紧急更新（如切换 tab）标记为低优先级；`useDeferredValue` 延迟某个值的计算，让输入、点击先响应。
- **workLoop 机制**：每个工作单元处理完就检查 `deadline.timeRemaining() < 1`，时间片用完就让出主线程，全部处理完才进入 commit。
- **切片不省时间只换响应性**（mini-react 实测，4000 项 / 8002 节点）：

```
一次跑完    总 18.1 ms  最长阻塞 18.1 ms
每片 2ms    总 19.6 ms  切 11 片   最长阻塞 5.8 ms（+8% 换响应性）
```

- **两处切不动**：组件函数本身（第一个工作单元，一次算完整段逻辑）与 commit 阶段（所有 DOM 写入必须一次做完）——「组件自己算得久」要靠 memo 与虚拟列表，时间切片救不了。

## 2. 虚拟 DOM 与 diff

### 2.1 虚拟 DOM 是什么

- **定义**：React 元素构成的普通 JS 对象树（`type` / `props` / `children`），是真实 DOM 的内存镜像；更新时先改便宜的虚拟 DOM、diff 出最小操作集再一次性应用。
- **核心价值**：把 UI 变成可编程的数据，从而支撑声明式更新与跨平台渲染（React Native / 小程序）；不是"比手写 DOM 快"，至少要快在批量最小化操作上。
- **mini-react 的 createElement**：产物只有 `type` / `key` / `props`，只描述不渲染，children 统一进 `props.children`；文本与数字被包成 `TEXT_ELEMENT`，所以「改文案」在 diff 眼里是「更新一个节点」；`key` 独立成字段，只参与 diff 匹配。

### 2.2 diff 三条启发式

| 启发式 | 规则 |
| ---- | ---- |
| 一：类型不同直接重建 | 新旧根节点 type 不同（如 `div` 变 `span`），销毁旧节点及其整棵子树重建 |
| 二：同类型只更新 props | 保留原 DOM 节点，只 update 变化的属性 |
| 三：同层兄弟用 key 定位 | 用 key 识别「同一节点」，避免不必要重建 |

- **本质**：三条启发式是"假设"，依赖树结构稳定、同层移动这一前提——不是暴力 O(n³) 逐节点比较，把复杂度压到 O(n)。
- **mini-react 的身份判定**：`isSameVNodeType` 只比较 `type` 与 `key`；有 key 用 key，没 key 退化成下标——这是 index 陷阱的源头，不是实现偷懒。

### 2.3 key 与列表 diff

- **key 的意义**：让框架识别「哪个节点是同一个」。有 key：能识别「同一节点被移动」，只新增缺失项、复用其余 DOM；无 key / index：只能按索引对号入座，节点被依次"更新"，动态列表出现状态错乱（输入框内容串位）。
- **key 必须独立成字段**（不是 props）：只参与"该复用谁"的匹配，不参与属性更新；且值必须归一成 `null`——`props ? props.key : null` 会让"有 props 无 key"的节点拿到 `undefined`，而 `null !== undefined` 会把更新误判成整棵重建（mini-vue 曾真实踩到）。
- **有 key 的差异是量级级**（mini-vue 实测，删首项）：

```
删首项    无 key 5 次（4 改写 + 1 删）  有 key 1 次
纯重排    无 key 6 次全改写            有 key 3 次全 insert 搬移
```

- **有 key 的重排不是零成本**：真实 Vue 会先算最长递增子序列（LIS）跳过已在正确位置的节点（三个节点重排只需搬 1 个）；mini-vue 简化为从后往前逐个插，搬移次数偏多。加 key 买到的主因是「复用的身份正确」，性能是顺带。

### 2.4 宿主抽象与多端渲染

- **渲染器只用宿主操作**：核心逻辑不认识 DOM。mini-react 注入 6 个操作、mini-vue 注入 9 个（createElement / createText / createComment / setText / setElementText / insert / remove / nextSibling / patchProp），换一组就换平台——这就是「平台无关」的定义本身。
- **mini-vue 注入 9 个宿主操作**：`createRenderer(options)` 让核心不认识 DOM；`insert(child, parent, anchor)` 在 anchor 为 null 时即 append（所以不需要单独的 appendChild）；`patchProp` 把「事件 / DOM property / attribute」三种写法收敛成一个函数（只 setAttribute 会让受控属性"数据变了但界面不动"）。
- **逻辑节点没有 DOM**：函数组件与 Fragment 不产生节点，找父 DOM 要沿 `parent` 往上找（`domParentOf`）；Vue 的 Fragment 用两个空文本锚点定位插入与删除。

## 3. 响应式原理

### 3.1 Proxy 响应式 vs Object.defineProperty

- **Proxy 代理整个对象**：`reactive` 返回的不是原对象；用 Proxy + Reflect 拦截 `get` / `set` / `deleteProperty` / `has` / `ownKeys`，天然支持属性新增 / 删除、数组操作、Map / Set 集合类型；Object.defineProperty 只能拦截预先声明的属性。
- **深度响应式是惰性的**：get 到对象才继续代理、不预先遍历整棵树；`reactiveMap`（WeakMap）做缓存，同一对象只代理一次。
- **readonly 不做依赖收集**：不可 set 就永远不会触发 trigger，收集没有意义；readonly / shallowReadonly 复用 `createGetter` 闭包区分。

### 3.2 track / trigger 三层依赖表

```
targetMap（WeakMap：对象）
  └─ depsMap（Map：属性）
       └─ dep（Set：effect 集合）
```

- **track（get 时）**：把当前 `activeEffect` 收进对应 dep，按「找 target 的 depsMap → 找 key 的 dep → 加入」走，已收集过则跳过。
- **trigger（set 时）**：取出 dep 里所有 effect 执行；effect 有 `scheduler` 就交用户自定义调度时机（runtime-core 用它实现 nextTick 批量更新），否则 `effect.run()`。
- **mini-vue 细节**：遍历前复制集合（effect 执行中可能增删 dep）、跳过 `activeEffect` 自己（避免自触发死循环）；`activeEffect` 用栈 / 保存-恢复（effect 里可能再跑 effect：computed getter、子组件渲染）；`deps` 是反向索引，支撑 `cleanupEffect`（分支切换清旧依赖）与 `stop`（组件卸载防泄漏）；依赖只认「读过」——没被读到的属性改了也不触发。
- **Why WeakMap**：键必须是对象、是弱引用，正适合「响应式对象 → 依赖」映射——对象不再被引用时可被 GC 自动回收，避免内存泄漏。

### 3.3 ref 与自动解包

- **RefImpl 包装基本类型**：Proxy 代理不了基本类型，所以 `ref` 把值包进对象再代理，`.value` 读写；值为对象自动转 reactive；`__v_isRef` 标记供 `isRef` 判断。
- **unref / proxyRefs**：`unref` 是 ref 返回 `.value`，否则返回本身；`proxyRefs` 用 Proxy 让模板里写 `count` 而非 `count.value`——**只解包第一层**，嵌套 ref 不递归解包。

### 3.4 computed / watch

- **computed 惰性与缓存**：基于 lazy 的 ReactiveEffect，`_dirty` 脏标记控制是否重算——依赖未变直接返回缓存值（实测读两次只算一次），依赖变化经 scheduler 置脏并通知依赖它的渲染 effect，真正重算发生在「有人读 value」时。
- **watch 是 effect 的封装**：对源执行一次读取建立关联，源变化经 scheduler 执行用户回调；支持 immediate / deep / flush 选项。

## 4. 编译优化与运行时

### 4.1 三大模块协作

```
编译模块     @vue/compiler-core(模板→AST→render，平台无关)
             @vue/compiler-dom(浏览器扩展 v-html/v-text/SVG)
             @vue/compiler-sfc(拆 .vue 的 template/script/style，处理 <script setup> 与 scoped)
运行时模块   @vue/runtime-core(平台无关：组件实例化、VNode、生命周期、props/插槽、provide/inject)
             @vue/runtime-dom(浏览器宿主操作、默认 createApp)
响应式模块   @vue/reactivity(独立可脱离 Vue 使用，为数据提供变更追踪)
```

三者关系一句话：**用编译换说法、用响应式驱动、用运行时落地**。

### 4.2 模板编译与静态标记

- **编译三阶段**：解析（模板字符串 → AST）→ 转换（AST 优化：静态节点标记、缓存动态绑定）→ 代码生成（AST → 可执行 render 函数代码）。
- **PatchFlags 静态标记**：编译期给节点打补丁标记，只有含插值 / 指令 / 绑定的动态节点参与更新对比，静态节点直接跳过——Vue3 相比 Vue2 的关键编译期性能优化。例如含动态文本的 `<code v-pre>{{ count }}</code>` 编译成 `_createElementVNode("p", null, toDisplayString(count), 1)`（位 1 表示动态文本），纯静态节点甚至只创建一次。
- **判断标准**：只有动态节点才需要更新时对比；运行时按 VNode 上的 patch flag 决定比对范围，大量静态 DOM 直接跳过。

### 4.3 运行时 patch 与异步批量更新

- **createRenderer 注入宿主操作**：runtime-dom 通过 `createRenderer({ createElement, insert, remove, patchProp... })` 注入浏览器宿主操作，返回 render 与 createApp；平台相关运行时都基于 runtime-core 扩展。
- **shapeFlag 位运算分发**：VNode 形状标记（ELEMENT / COMPONENT / TEXT_CHILDREN / ARRAY_CHILDREN 等），一个整数同时表达「元素还是组件」与「孩子是文本还是数组」，patch 按位与分发到 processElement / processComponent / processText。
- **patch(n1, n2)**：对比新旧 VNode 生成最小补丁（挂载 / 更新 / 卸载）。
- **渲染 effect + scheduler 批量更新**：组件渲染函数被包成 effect，数据变化经 scheduler 把更新推入队列、`queue.includes(job)` 去重，在下一微任务统一执行（nextTick 挂在同一 flush promise 上，能等到"DOM 已最新"）——所以「一轮改三次渲染一次」。

### 4.4 组件运行时能力

- **生命周期钩子**：本质是「特定时机调用的用户函数集合」——onMounted 把回调注册进 `instance.mounted`，挂载完成统一遍历调用；组件卸载时统一 stop 相关 effect 防内存泄漏。
- **props 与插槽**：props 用 `shallowReadonly` 代理防止子组件改父值；插槽是父组件编译出的「返回 VNode 树的函数」，子组件经 slots 渲染（作用域插槽函数接收 props 参数）。
- **provide / inject**：借原型链（`Object.create` 浅拷贝父 provides）实现就近覆盖、沿链向上查找，跳过中间组件跨层级传数据。
- **跳过无意义的子渲染**：父组件重渲染前先比 props 与插槽，都没变就不调子组件的 update。

## 5. Hooks 机制与优化

### 5.1 Hooks 链表与调用顺序

- **链表结构**：每个函数组件的 Fiber 节点（`memoizedState`）上挂 hooks 链表；hook 节点含 `memoizedState`（状态 / deps）、`queue`（更新队列）、`next`（下一节点）。
- **按调用顺序存取**：首次渲染依次创建节点，后续渲染沿 `next` 复用旧节点读旧值、把新 setState 入队。所以必须顶层、固定顺序调用——放 if / 循环里，第二次渲染的读取顺序与上次不一致就会整体错位一格。
- **useEffect 依赖比较**：deps 存在 hook 节点里，每次渲染浅比较新旧 deps，不同才执行副作用并在 Commit 阶段触发；依赖变化先 cleanup 再 effect。
- **mini-react 的 setState 只推队列**：下次渲染按顺序作用到旧状态上，函数式更新读到的是队列里的前一个结果；批处理是调度的自然结果（异步调度下同一轮两次 setState 只渲染一次；同步模式则每次 setState 渲染一轮）；effect 在 commit 之后统一执行，卸载时清理整棵子树。

### 5.2 优化三板斧

- **`React.memo`**：浅比较 props 缓存组件，props 浅比较相等时跳过该子组件渲染。
- **`useMemo`**：缓存计算结果，依赖项不变不重算；它是性能优化手段而非语义上的保证。
- **`useCallback`**：`useMemo(() => fn, deps)` 的语法糖，缓存函数引用，配合 `React.memo` 才能真正跳过渲染。
- **配合要点**：memo 是浅比较，内联对象 / 新建函数会让它失效，需配合引用稳定（`useCallback` / `useMemo`）与状态上移 / 下移、组件拆分、合理分层。

### 5.3 代码分割

- **`lazy` + `Suspense`**：`lazy(() => import(...))` 声明动态加载的组件，`Suspense` 提供加载中 fallback；配合 React Router 实现路由级懒加载。
- **体积优化**：抽离公共依赖（react-dom、antd 等 vendors）成独立 chunk，配合 Gzip 压缩（约再压 1/3）与长缓存命中，减小首屏体积、加快首屏渲染。

## 6. 手写实现验证

### 6.1 骨架分层对照

把 React 与 Vue3 的「说法」写成能跑、能单测、能数出宿主操作次数的代码，凡实测与说法对不上的地方（时间切片并不省时间、有 key 的重排也要搬节点），都以实测为准。

```
mini-react    element(对象树) → host(6 宿主操作) → internal(渲染器状态)
              → reconciler(Fiber/workLoop/diff/commit) → hooks(链表)   每层可单独跑
mini-vue      reactivity(三层依赖表·惰性代理·computed 脏标记)
              → runtime-core(vnode/scheduler/renderer/component)
              → runtime-dom(宿主操作) → fake-dom(单测环境)
```

### 6.2 用宿主操作次数做实测

- **两个宿主的调用次数逐项相同**（mini-vue）：假 DOM 与字符串宿主跑同一份 render，createElement 3 / setElementText 2 / insert 3 / patchProp 1 逐项相同——这就是 runtime-core / runtime-dom 分包的依据（顺带说明 SSR 只需换一份 `nodeOps`）。
- **能数出来的优化事实**：
  - 时间切片：总时长 18.1 → 19.6 ms（+8%），最长阻塞 18.1 → 5.8 ms——换的是响应性不是总时长。
  - 删首项：mini-react 无 key 3 次（1 删 + 2 就地改写）vs 有 key 1 次；mini-vue 无 key 5 次 vs 有 key 1 次。
  - 批处理：同一轮改三次只渲染一次，`await nextTick()` 之后 DOM 才变。

### 6.3 与真实框架的差距

- **mini-react 有意留白**：无事件系统 / Lane 优先级 / Context / ref / memo / 错误边界 / Suspense / SSR。
- **mini-vue 有意留白**：无编译层（模板 / 静态标记 / PatchFlags）、无 LIS 优化、无生命周期 / provide-inject / Teleport / Suspense / SSR 水合。
- **它们都是同一骨架上加的一层，不是新机制**：Lane = 给 `nextUnitOfWork` 排优先级，memo = 更新前加一次浅比较，模板 = render 函数的一种写法。骨架跑通，这些就是顺理成章的增量。

## 7. 状态管理

### 7.1 三个真问题与判断分层

- **状态放哪 / 谁能改 / 改完通知谁**：前两个是「约定」，第三个是「机制」——把状态从组件内部搬到组件之外以后，就得自己回答「改完通知谁」。
- **分野在第三个问题**：各家状态库的实质差别是「这次更新跟我有没有关系」这个判断被放在哪一层——放在订阅者手里（reducer、选择器），还是放在 store 内部（依赖表）。判断越靠前省得越多。

### 7.2 reducer 与不可变更新

- **reducer 必须是纯函数**：只返回新对象、不改入参——不可变是「用引用比较回答变没变」的前提（Redux / Zustand 一类）。
- **没被影响的切片要返回原引用**：`combineReducers` 逐片 `Object.is` 后短路，避免白重建整棵树；`dispatch` 一律通知所有订阅者，不判断「跟谁有关」，收敛责任在订阅者的选择器。
- **原地改的后果**：状态错了但屏幕不变、且不报错——这是不可变真正要防的事故，不是拷贝开销。
- **代价**：路径上每一层都要展开重写；`immer` 用 Proxy 记录改动路径消除它。

### 7.3 setState 与订阅切片

- **浅合并 + 逐键 `Object.is`**：赋同值时连通知都不发（与 `dispatch` 的可观测差异：3 次 vs 0 次）。
- **订阅单位是「组件 × 切片」**：`subscribeWithSelector` 用 `isEqual` 决定要不要重渲染，等价于 `useSelector`。
- **选择器返回新对象就会失守**：`Object.is` 永远不等 → 无关更新也重渲染（实测 3 次）；解法是返回扁平基本类型或换 `shallowEqual`。
- **选择器每次通知都会跑一遍**：重选择器要靠记忆化（reselect 一类）补「输入没变就不重算」。

### 7.4 依赖追踪与精确唤醒

- **三层依赖表 `target → key → dep`**：订阅单位下沉到**字段**，改 `cart.items` 只唤醒读过它的 effect（实测 1/3，signal / Vue 的 reactive）。
- **`cleanup` + `deps` 反向索引**：每次重跑先摘旧依赖，否则分支切换后「读过的字段」只增不减，脏字段也会唤醒它。
- **`activeEffect` 用保存-恢复**：effect 里还会跑 effect（computed getter、子组件渲染）。
- **`computed` = lazy effect + 脏标记 + scheduler**：读两次只算一次、改了没读不算、无关字段不重算。
- **`signal` 与 `reactive` 分工**：`set` 里先 `Object.is` 再 return，压根不进通知流程。

### 7.5 三条路线对照与选型

**被唤醒 ≠ 重渲染**（同一场景实测，只改 `cart.items`）：

```
路线                   被唤醒 / 重渲染
reducer 订阅整棵树      3 / 3
reducer + 选择器         3 / 1
setState + 选择器        3 / 1
signal / 依赖追踪        1 / 1
```

- **「减少叫醒」与「减少渲染」是两条不同的优化路径**：对照里「唤醒」都不同，但「重渲染」可以相同。
- **批处理不是 store 的职责**：一轮 10 次 `setState` = 30 次通知 / 10 次渲染；要么合并成一次函数式 `setState`，要么由调度器把渲染推迟到下一个微任务 / 下一帧。
- **选型与边界**：
  - **服务端状态交给请求库**：请求数据有缓存 / 失效 / 重试 / 竞态，是服务端缓存问题；store 只装客户端自己拥有的跨模块状态。
  - **单一 store vs 按域拆分**：前者换来可调试可回放、后者换来边界清晰——判据是「谁能改」而不是规模。
  - **不需要状态库的信号**：状态只被一个子树用到时就放在最近的公共父组件里。
  - **三条路线的取舍**：可回放可追溯（reducer）/ 上手快但收敛责任在调用方（setState + 选择器）/ 判断最准但依赖是运行时收集的、追踪本身有开销（依赖追踪）。
