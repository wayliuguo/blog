# 模块总结 · 前端框架原理

## 知识主线

五篇不是并列的五堆 API 知识：前两篇围绕同一个问题展开两条实现路径——**"状态/数据变了，框架如何以最小代价把界面更新到最新"**；第三、四篇把前两篇的结论各自落到能跑、有单测的实现上；第五篇再往外扩一层——**状态从组件内部搬到组件之外以后，"改完通知谁"这个判断该放在哪一层**。每一篇都在回答上一篇留下的问题：

```
01 React 高级与原理（组件状态一变，React 怎么知道改哪里）
        │  先建立基线：渲染 = render/commit 两阶段
        │  → 虚拟 DOM + diff 三条启发式求最小变更
        │  → Fiber 链表把大更新拆成可中断小单元
        │  → Hooks 链表按调用顺序在 Fiber 上存状态
        ▼
02 Vue3 原理（同一个问题，另一条工程路径）
        │  编译：模板 → render 函数 + 静态标记（能提前确定的就不进 diff）
        │  → 响应式：Proxy 代理 + track/trigger（数据一变知道通知谁）
        │  → 运行时：createRenderer + patch 按差异落地（scheduler 批量更新）
        ▼
03 手写 mini-react（"可中断到底怎么实现"落到 400 行）
        │  element / host / reconciler（Fiber·workLoop·diff·commit）/ hooks
        │  → 实测：时间切片把最长阻塞 18.1 → 5.8 ms；key 让删首项的宿主操作 3 → 1 次
        ▼
04 手写 mini-vue（"依赖表长什么样、谁在排队"落到 1100 行）
        │  reactivity（三层依赖表 · 惰性代理 · computed 脏标记）
        │  → runtime-core（createRenderer · shapeFlag · 头尾同步 diff · 渲染 effect + scheduler）
        │  → 实测：两个宿主调用次数逐项相同；有 key 重排只搬移不改写内容
        ▼
05 状态管理原理与实现（把状态搬到组件之外，同一个问题的另一半）
        │  三条路线：reducer（dispatch 一律通知，判断在订阅者）
        │  → setState + 选择器（订阅切片，store 先做"同值就不通知"）
        │  → signal（判断在 store 内部的依赖表，订阅单位精确到字段）
        │  → 实测：只改 cart.items，reducer 3/3 · reducer+选择器 3/1 · signal 1/1（被唤醒/重渲染）
        ▼
共同收口：状态变化 → 以最小代价把界面更新到最新
```

本模块的主轴是**"状态到界面的最小代价映射"**：01 篇以 React 为样本建立"渲染分两阶段 + 虚拟 DOM/diff + 链表（Fiber、Hooks）"这条基线，02 篇在同一个问题域里看 Vue3 的另一种实现——用编译期静态标记省掉不必要的 diff，用 Proxy 响应式把更新精确到"哪个数据变了、通知谁"，再交给运行时 patch 落地。03、04 两篇换一条路验证同一批结论：把"可中断渲染""依赖表""批处理"这些说法写成能跑、能单测、能数出宿主操作次数的代码，凡是实测和说法对不上的地方（时间切片并不省时间、有 key 的重排也要搬节点），都以实测为准。05 篇把状态搬出组件：前四篇里"数据一变，框架知道改哪里"，默认状态就长在组件树上；一旦状态要跨模块共享，就得自己回答"改完通知谁"。三条路线的差别不在 API，而在**这个判断被放在哪一层**，而且都能数出来——只改一个切片时，reducer 叫醒了 3 个订阅者、重渲染 3 个；加选择器后叫醒仍是 3 个、重渲染降到 1 个；依赖追踪直接把叫醒降到 1 个。

## 分篇知识点

### 01-React 高级与原理

- **render / commit 两阶段**
  - **Render 阶段**：纯计算、可中断，只构建新虚拟 DOM / Fiber 并算 diff（差异），不碰真实 DOM，不允许副作用
  - **Commit 阶段**：不可中断，一次性把变更应用到真实 DOM 并执行副作用（`useEffect` / `useLayoutEffect` / 生命周期 / ref 赋值）——"纯函数在前、命令式在后"
  - **并发基础**：render 可被高优先级操作（输入、点击）抢占插队，commit 一旦开始不能半途而废，否则页面闪现中间态
- **Fiber 链表与双缓存**
  - **Fiber 是普通 JS 对象**：靠 `child` / `sibling` / `return` 三个指针构成双向链表树，把大更新拆成小单元逐个处理，解决递归不可中断的问题
  - **双缓存**：同时维护 current（当前展示）与 workInProgress（内存中构建）两棵树，完成后原子切换指针；构建被打断也不影响屏幕
  - **时间切片 workLoop**：每处理一个 Fiber 检查 `deadline.timeRemaining()`，时间片用完就让出主线程，全部处理完才进入 commit
- **并发特性**
  - **开启方式**：`ReactDOM.createRoot` 渲染即获得并发（可中断渲染 + 时间切片）能力
  - **低优先级更新**：`startTransition` / `useTransition` 把非紧急更新（如切换 tab）标记为低优先级，`useDeferredValue` 延迟某个值的计算，让输入、点击先响应
- **虚拟 DOM 与 diff 三条启发式**
  - **虚拟 DOM 是什么**：React 元素构成的普通 JS 对象树（type / props / children），是真实 DOM 的内存镜像；先改便宜的虚拟 DOM，diff 出最小操作集，最后一次性应用
  - **启发式一：类型不同直接重建**：新旧根节点 type 不同（如 div 变 span），直接销毁旧节点及其整棵子树重建
  - **启发式二：同类型只更新 props**：保留原 DOM 节点，只 update 变化的属性
  - **启发式三：同层兄弟列表用 key 定位**：用 key 识别"同一节点"，把复杂度从 O(n³) 压到 O(n)
- **key 的真正意义**
  - **有 key**：能识别"同一节点被移动"，只新增缺失项、复用其余 DOM，性能高
  - **无 key / index 陷阱**：只能按索引对号入座，导致节点被依次"更新"、出现状态错乱（如输入框内容串位）；动态列表务必给 key 且不要用 index
- **优化三板斧**
  - **`React.memo`**：浅比较 props 缓存组件，props 浅比较相等时跳过该子组件渲染
  - **`useMemo`**：缓存计算结果，依赖项不变不重算；它是性能优化手段而非语义上的保证
  - **`useCallback`**：`useMemo(() => fn, deps)` 的语法糖，缓存函数引用，配合 `React.memo` 才能真正跳过渲染
  - **配合要点**：memo 是浅比较，内联对象 / 新函数会让它失效，需配合引用稳定与状态上移 / 下移、组件拆分
- **Hooks 是 Fiber 上的链表**
  - **链表结构**：每个函数组件的 Fiber 节点上挂 hooks 链表（`memoizedState`），hook 节点含 `memoizedState`（状态）/ `queue`（更新队列）/ `next`（下一节点）
  - **按调用顺序存取**：每次渲染按同样顺序读取链表节点，所以必须顶层、固定顺序调用，放 if / 循环里就会错位
  - **useEffect 依赖比较**：deps 存在 hook 节点里，每次渲染浅比较新旧 deps，不同才执行副作用并在 Commit 阶段触发回调
- **代码分割**
  - **`lazy` + `Suspense`**：`lazy(() => import(...))` 声明动态加载的组件，`Suspense` 提供加载中 fallback；配合 React Router 实现路由级懒加载
  - **体积优化**：抽离公共依赖（react-dom、antd 等 vendors）成独立 chunk，配合 Gzip 压缩（约再压 1/3）与长缓存命中，减小首屏体积、加快首屏渲染

### 02-Vue3 原理

- **三大模块协作**
  - **编译模块**：`@vue/compiler-core`（模板 → AST → render 函数，平台无关）、`@vue/compiler-dom`（浏览器扩展 v-html / v-text / SVG 等）、`@vue/compiler-sfc`（拆 .vue 的 template / script / style 三块，处理 `<script setup>` 与 scoped 样式）
  - **运行时模块**：`@vue/runtime-core`（平台无关：组件实例化、VNode、生命周期、props / 插槽、provide / inject）+ `@vue/runtime-dom`（浏览器宿主操作、默认 `createApp`）
  - **响应式模块**：`@vue/reactivity` 独立可脱离 Vue 使用，为数据提供变更追踪——三者关系是"用编译换说法、用响应式驱动、用运行时落地"
- **Proxy 响应式 vs Object.defineProperty**
  - **reactive 用 Proxy 代理整个对象**：返回的不是原对象；支持属性增删检测、数组与 Map / Set 集合、深度响应式（访问嵌套对象时自动再代理）
  - **WeakMap 做缓存与依赖存储**：`reactiveMap` 缓存保证同一对象只代理一次；键是对象、弱引用可被 GC 回收避免内存泄漏
  - **readonly 不做依赖收集**：不可 set 就永远不会触发 trigger，收集没有意义；readonly / shallowReadonly 复用 `createGetter` 闭包区分
- **track / trigger 依赖收集**
  - **三层结构**：targetMap（WeakMap：对象）→ depsMap（Map：属性）→ dep（Set：effect 集合）
  - **track（get 时）**：把当前 `activeEffect` 收进对应 dep，避免重复收集
  - **trigger（set 时）**：取出 dep 里所有 effect 执行；effect 有 `scheduler` 就交用户自定义调度时机（runtime-core 用它实现 nextTick 异步批量更新），否则 `effect.run()`
- **ref 与自动解包**
  - **RefImpl 包装基本类型**：把值包进对象再代理，`.value` 读写、值为对象自动转 reactive，`__v_isRef` 标记供 `isRef` 判断
  - **unref / proxyRefs**：unref 是 ref 返回 `.value` 否则返回本身；proxyRefs 用 Proxy 让模板里写 `count` 而非 `count.value`（只解包第一层，嵌套 ref 不递归解包）
- **computed / watch**
  - **computed 惰性与缓存**：基于 lazy 的 ReactiveEffect，`_dirty` 脏标记控制是否重算——依赖未变直接返回缓存值，依赖变化经 scheduler 置脏并通知依赖它的渲染 effect
  - **watch 是 effect 的封装**：对源执行一次读取建立关联，源变化经 scheduler 执行用户回调；支持 immediate / deep / flush 选项
- **模板编译与静态标记**
  - **编译三阶段**：解析（模板字符串 → AST）→ 转换（AST 优化：静态节点标记、缓存动态绑定）→ 代码生成（AST → 可执行 render 函数代码）
  - **PatchFlags 静态标记**：编译期给节点打补丁标记，只有含插值 / 指令 / 绑定的动态节点参与更新对比，静态节点直接跳过——Vue3 相比 Vue2 的关键编译期性能优化
- **运行时与虚拟 DOM diff**
  - **createRenderer 注入宿主操作**：runtime-dom 通过 `createRenderer({ createElement, insert, remove, patchProp... })` 注入浏览器宿主操作，返回 render 与 createApp；平台相关运行时都基于 runtime-core 扩展（多端渲染的基础）
  - **shapeFlag 位运算分发**：VNode 形状标记（ELEMENT / COMPONENT / TEXT_CHILDREN / ARRAY_CHILDREN 等），一个值表达多种组合特征，patch 按位与分发到 processElement / processComponent / processText
  - **patch 与异步批量更新**：patch(n1, n2) 对比新旧 VNode 生成最小补丁（挂载 / 更新 / 卸载）；渲染 effect 包上 scheduler，数据变化后推进队列、在下一微任务统一执行（nextTick）
- **组件运行时能力**
  - **生命周期钩子**：本质是"特定时机调用的用户函数集合"，onMounted 把回调注册进 `instance.mounted`，挂载完成统一遍历调用；组件卸载时统一 stop 相关 effect 防内存泄漏
  - **props 与插槽**：props 用 shallowReadonly 代理防止子组件改父值；插槽是父组件编译出的"返回 VNode 树的函数"，子组件经 slots 渲染（作用域插槽函数接收 props 参数）
  - **provide / inject**：借原型链（`Object.create` 浅拷贝父 provides）实现就近覆盖、沿链向上查找，跳过中间组件跨层级传数据

### 03-手写 mini-react

- **五层骨架**
  - **分层**：element（对象树）→ host（6 个宿主操作）→ internal（渲染器状态）→ reconciler（Fiber / diff / commit）→ hooks（链表），每层都能单独跑
- **createElement 的产物**
  - **只描述不渲染**：产物只有 `type` / `key` / `props`，children 统一进 `props.children`
  - **文本也是节点**：文本与数字被包成 `TEXT_ELEMENT`，所以"改文案"在 diff 眼里是"更新一个节点"
  - **`key` 独立成字段**：只参与 diff 匹配，不参与属性更新
- **宿主抽象**
  - **渲染器只用 6 个操作**：换一组就换平台（浏览器 DOM / Node 假 DOM），这就是平台无关的定义本身
  - **逻辑节点没有 DOM**：函数组件与 Fragment 不产生节点，找父 DOM 要沿 `parent` 往上找（`domParentOf`）
- **Fiber 与时间切片**
  - **三指针换递归**：`child` / `sibling` / `parent` 把整棵树变成可随时打断的循环；"工作单元" = 处理一个 Fiber + 找下一个
  - **每单元问一次 deadline**：`workLoop` 用 `dl.timeRemaining() < 1` 决定是否让出主线程
  - **切片不省时间只换响应性**：实测 4000 项（8002 节点）总耗时 18.1 → 19.6 ms，最长阻塞 18.1 → 5.8 ms
  - **两处不可切分**：组件函数本身（第一个工作单元）、commit 阶段（所有 DOM 写入）
- **diff 与 commit**
  - **身份 = 有 key 用 key，没 key 退化成下标**：这是 index 陷阱的源头，不是实现偷懒
  - **`alternate` 即双缓存**：新树在内存里长好才一次性切过去；根按容器区分（`roots` 是 Map），换容器就是另一棵新树
  - **实测删首项**：无 key 3 次宿主操作（1 删 + 2 就地改写），有 key 1 次
  - **commit 递归且无 deadline**：先处理 deletions、再走树、最后统一跑 effect
- **Hooks**
  - **按调用顺序存链表**：状态挂在 Fiber 的 hooks 数组上，所以顺序必须固定，放进 if 会整体错位一格
  - **setState 只推队列**：下次渲染按顺序作用到旧状态上，函数式更新读到的是队列里的前一个结果
  - **批处理是调度的自然结果**：异步调度下同一轮两次 setState 只渲染一次；同步模式则每次 setState 渲染一轮
  - **effect 在 commit 之后统一执行**：依赖变化先 cleanup 再 effect；卸载时清理整棵子树
- **与真实 React 的差距**
  - **有意留白**：无事件系统 / Lane 优先级 / Context / ref / memo / 错误边界 / Suspense / SSR
  - **它们都是同一骨架上加的一层**，不是新机制（Lane = 给 `nextUnitOfWork` 排优先级，memo = 更新前加一次浅比较）

### 04-手写 mini-vue

- **四层骨架**
  - **分层**：reactivity（依赖表）→ runtime-core（vnode / scheduler / renderer / component）→ runtime-dom（宿主操作）→ fake-dom（单测环境）
- **响应式地基**
  - **三层依赖表**：targetMap（WeakMap: 对象）→ depsMap（Map: 属性）→ dep（Set: effect 集合），`track` 逐级补空
  - **trigger 的两个细节**：遍历前复制集合（effect 执行中可能增删 dep）、跳过 `activeEffect` 自己（避免自触发死循环）
  - **`activeEffect` 用栈**：effect 里可能再跑 effect（computed getter、子组件渲染），必须能恢复外层
  - **`deps` 是反向索引**：支撑 `cleanupEffect`（分支切换清旧依赖）与 `stop`（组件卸载防泄漏）
  - **依赖只认"读过"**：没被读到的属性改了也不触发；`readonly` 读不收集依赖（不会被 set，收集没意义）
- **惰性代理与 ref**
  - **深度响应式是惰性的**：get 到对象才继续代理，不预先遍历整棵树；`reactiveMap` 缓存保证同一对象只代理一次
  - **ref 包基本类型**：Proxy 代理不了基本类型，所以用 `RefImpl` + `.value`，值为对象自动转 reactive
  - **`proxyRefs` 只解包第一层**：让模板里写 `count` 而不是 `count.value`
- **computed**
  - **脏标记 + scheduler**：依赖变化只 `_dirty = true` 并通知，真正重算发生在"有人读 value"时（实测：读两次只算一次，改依赖不重算）
- **宿主抽象与 VNode**
  - **注入 9 个宿主操作**：`createRenderer(options)` 让核心不认识 DOM；`insert` 在 anchor 为 null 时即 append，所以不需要单独的 appendChild
  - **两个宿主调用次数逐项相同**：假 DOM 与字符串跑同一份 render，这就是 runtime-core / runtime-dom 分包的依据（也顺带说明 SSR 只需换一份 `nodeOps`）
  - **shapeFlag 位运算**：一个整数同时表达"元素还是组件"与"孩子是文本还是数组"，patch 按位分发
  - **Fragment 用两个空文本锚点**：自己不产生节点，靠首尾锚点定位插入与删除
  - **key 必须归一成 null**：写 `props ? props.key : null` 时，有 props 无 key 的节点 `key` 是 `undefined`，`null !== undefined` 会让 `isSameVNodeType` 判成不同类型，更新退化为整棵重建
  - **属性分三种写法**：`onXxx` 走事件（换新函数先摘旧的）、`value/checked/...` 走 DOM property、其余走 attribute；只 setAttribute 会让受控属性"数据变了但界面不动"
- **列表 diff**
  - **双端比较**：先从头部、再从尾部同步（这两步最便宜也最常见），剩下中间乱序段按 key 建索引配对
  - **无 key 退化成按下标对应**：实测删首项无 key 5 次操作（4 次改写 + 1 次删）、有 key 1 次；纯重排无 key 6 次全改写、有 key 3 次全搬移
  - **有 key 的重排也不是零成本**：真实 Vue 先算最长递增子序列跳过已在正确位置的节点，本实现简化为从后往前逐个插，搬移次数偏多
- **组件与批量更新**
  - **渲染 effect**：组件 render 被包成 effect，它读到的响应式数据就是依赖；`isMounted` 区分 `patch(null, subTree)` 与 `patch(prev, next)`
  - **scheduler 微任务批处理**：`queue.includes(job)` 保证同一组件一轮只渲染一次，所以"改三次渲染一次"，DOM 在 `nextTick` 之后才变
  - **props 浅只读**：`shallowReadonly` 拦住子组件改父值，又不妨碍 prop 内部对象响应式；`propsRaw` 保留原引用供框架更新
  - **跳过无意义的子渲染**：父组件重渲染前先比 props 与插槽，都没变就不调子组件的 update
  - **卸载要 stop 渲染 effect**：否则组件已不在界面上，更新还会继续来
- **与真实 Vue3 的差距**
  - **有意留白**：无编译层（模板 / 静态标记 / PatchFlags）、无 LIS 优化、无生命周期 / provide-inject / Teleport / Suspense / SSR 水合

### 05-状态管理原理与实现

- **三个真问题**
  - **状态放哪 / 谁能改 / 改完通知谁**：前两个是"约定"，第三个是"机制"
  - **分野在第三个问题上**：各家状态库的实质差别是"这次更新跟我有没有关系"这个判断被放在哪一层——放在订阅者手里（reducer、选择器），还是放在 store 内部（依赖表）
- **reducer 与不可变更新**
  - **reducer 必须是纯函数**：只返回新对象、不改入参——不可变是"用引用比较回答变没变"的前提
  - **没被影响的切片要返回原引用**：`combineReducers` 逐片 `Object.is` 后短路，避免白重建整棵树
  - **`dispatch` 一律通知所有订阅者**：它不判断"这次更新跟谁有关"，收敛责任在订阅者的选择器
  - **原地改的后果**：状态错了但屏幕不变、且不报错——这是不可变真正要防的事故，不是拷贝开销
  - **代价**：路径上每一层都要展开重写；`immer` 用 Proxy 记录改动路径来消除它
- **setState 与订阅切片**
  - **浅合并 + 逐键 `Object.is`**：赋同值时连通知都不发（与 `dispatch` 的可观测差异：3 次 vs 0 次）
  - **订阅单位是"组件 × 切片"**：`subscribeWithSelector` 用 `isEqual` 决定要不要重渲染，等价于 `useSelector`
  - **选择器返回新对象就会失守**：`Object.is` 永远不等 → 无关更新也重渲染（实测 3 次）；解法是返回扁平基本类型或换 `shallowEqual`
  - **选择器每次通知都会跑一遍**：重选择器要靠记忆化（reselect 一类）补"输入没变就不重算"
- **依赖追踪**
  - **三层依赖表 `target → key → dep`**：订阅单位下沉到**字段**，改 `cart.items` 只唤醒读过它的 effect（实测 1/3）
  - **`cleanup` + `deps` 反向索引**：每次重跑先摘旧依赖，否则分支切换后"读过的字段"只增不减，脏字段也会唤醒它
  - **`activeEffect` 用保存-恢复**：effect 里还会跑 effect（computed 的 getter、子组件渲染）
  - **`computed` = lazy effect + 脏标记 + scheduler**：读两次只算一次、改了没读不算、无关字段不重算
  - **`signal` 与 `reactive` 分工**：`set` 里先 `Object.is` 再 return，压根不进通知流程
- **三条路线对照（同一场景实测）**
  - **被唤醒 ≠ 重渲染**：只改一个切片时 reducer 订阅整棵树 3/3、reducer + 选择器 3/1、setState + 选择器 3/1、signal 1/1——**减少叫醒**与**减少渲染**是两条不同的优化路径
  - **判断越靠前省得越多**：同一个"赋同值"，reducer 通知 3 次、setState 0 次、signal 0 次
  - **批处理不是 store 的职责**：一轮 10 次 `setState` = 30 次通知 / 10 次渲染；要么合并成一次函数式 `setState`，要么由调度器把渲染推迟到下一个微任务 / 下一帧
- **选型与边界**
  - **服务端状态交给请求库**：请求数据有缓存 / 失效 / 重试 / 竞态，属于服务端缓存问题；store 只装客户端自己拥有的跨模块状态
  - **单一 store vs 按域拆分**：前者换来可调试可回放，后者换来边界清晰——判据是"谁能改"而不是规模
  - **不需要状态库的信号**：状态只被一个子树用到时就放在最近的公共父组件里
  - **三条路线的取舍**：可回放可追溯（reducer）/ 上手快但收敛责任在调用方（setState + 选择器）/ 判断最准但依赖是运行时收集的、追踪本身有开销（依赖追踪）
