## 1. Chrome 多进程与渲染管线

### 1.1 多进程：谁在跑页面

浏览器用**多进程**分兵把守，各进程职责互不重叠：

| 进程 | 职责 |
| ---- | ---- |
| 浏览器主进程 | UI、进程调度 |
| GPU 进程 | 合成汇总、统一出画面 |
| 网络进程 | 网络请求独立收发 |
| 渲染进程 | 跑页面（JS / 布局 / 绘制）；**站点隔离**，每个站点一个 |
| 插件进程 | 隔离插件 |

进程是**操作系统级隔离**：一个进程崩了不影响另一个（崩溃隔离），恶意站点即使攻破自己进程的沙箱也读不到别的站点——这是 Meltdown/Spectre 后的安全补课。

**进程边界实测（探针）**：

```
崩溃隔离     一个进程崩，另一个进程照常
内存不共享   跨进程传对象走结构化克隆副本，子进程改，父进程不变
序列化成本   按字节付费：1 万条≈20ms、100 万条≈1.3s，比同进程遍历慢 18→200+ 倍
固定开销     每进程≈48MB → 进程要复用且设上限
```

### 1.2 渲染进程四线程

每个渲染进程内部靠四类线程协同：

```
主线程        JS + 样式计算 + 布局 + 绘制记录
合成器线程    接收输入 + 合成出帧
光栅线程池    把图层光栅成位图
Worker        JS 密集计算专用（不占主线程）
```

其中只有**主线程**会成为"事件循环"的宿主——JS 任务、DOM 事件都在它上面排队执行；合成器线程独立于主线程工作，这一分工是后面几节性能结论的根。

### 1.3 渲染管线：像素旅程

一帧画面从 JS 到屏幕走固定管线：

```
JS → 样式计算 → 布局 → 绘制记录 → 分块光栅 → 合成出帧
                         │
                    只产出"怎么画"的指令列表
                    位图由光栅线程池异步生成
```

关键点：**绘制记录（Paint）并不真的画**，只是列出一串"怎么画"的指令；真正的位图由光栅线程池异步生成，合成器线程拿已光栅化的图层做合成。这条分工决定了谁能绕开主线程。

### 1.4 合成器线程与动画加速

合成器线程只做一件事——用现成图层**改变换矩阵出帧**，不需要重跑布局与绘制：

```
transform / opacity    只影响合成阶段，完全绕开主线程，主线程卡死动画照跑
left / top / width 等   走「布局 → 绘制记录 → 光栅 → 合成」全链，且在主线程
代价                  合成层占显存，滥用 will-change 层爆炸
```

所以 **transform/opacity 动画天然流畅**：它不重排、不重绘，纯粹在合成层上变矩阵。

### 1.5 输入流转与事件循环底层

输入事件怎么进入主线程，决定了许多性能结论：

```
用户滚动       合成器线程可独立处理，不需要主线程 → 页面卡也照滚
click / 触摸    必须转发到主线程 JS 处理 → 进主线程事件循环排队
监听器带 preventDefault → 合成器必须先等主线程确认不拦，才敢滚动
```

只有可能 `preventDefault` 的滚动监听器，合成器才需要等主线程；而不需要拦的监听器给出 `{ passive: true }` 就是**免费的性能开关**——它告诉浏览器"我不会阻止默认行为，你可以放心并行滚"。这既是"为什么主线程卡死还能滚动"的答案（滚动归合成器），也是"为什么长任务让点击卡、滚动却不卡"的答案（click 必须进主线程队列，这是 INP 只关注交互延迟的原因）。

## 2. V8 执行与优化

### 2.1 分层编译流水线

V8 不把 JS 一次编译成最优机器码，而是**越跑越快**的分层流水线：

```
AST → Ignition 字节码（收集类型反馈）
        → Sparkplug（快速基准编译）
        → Maglev（中等级优化编译）
        → TurboFan（终极优化编译）
```

真正让 JS 快起来的是**类型反馈**：较底层的解释器先跑、边跑边收集"这个变量的类型是什么"，供上层优化编译器押注更激进的优化。

### 2.2 隐藏类与内联缓存

V8 给每个对象挂一个描述「属性布局」的**隐藏类（map）**，属性访问按"形状偏移"直取，不用查名字：

```
同构造函数 + 同字段顺序   → 共享隐藏类，偏移直取（快）
乱序写属性                → 不同 map，形状不稳
事后加属性                → 过渡到另一种形状，破坏隐藏类
delete 属性               → 推入字典模式，退化为查表
```

**实测（`%HaveSameMap`）**：`new Point(1,2)` 与 `new Point(3,4)` 同构；`{y:2,x:1}` 与构造产物异构；delete 后的对象与同形状字面量异构。保持对象形状稳定，内联缓存才能走最快路径。

### 2.3 tier-up：预热与升级

JIT 的"热"是靠跑出来的。用 `--allow-natives-syntax` 实测 TurboFan 级别的 tier-up：

```
冷（未优化）       status = 262145（含 interpreted + 未优化位）
预热 10 万次       status = 81（optimized + TurboFan）
```

只有被反复执行的热代码，V8 才花成本升级到 TurboFan；冷函数一直停在解释器阶段。

### 2.4 反优化与热路径军规

优化代码基于类型反馈**押注**，一旦押错就回退：

```
用数字预热 10 万次 → 进入 optimized + TurboFan
随后喂一个字符串参数 → optimized 位清零，退回解释器重新收集反馈（status 129）
```

- deopt **不是错误**，是设计的回退路径；热路径上反复触发才要修。
- 反复 deopt 是"隐形杀手"——JIT「先慢后快」与「反复 deopt 拖垮」是同一机制的两面。

**热路径军规**（只在热路径有意义，冷函数真无所谓）：

```
构造函数一次初始化全字段     避免事后加属性破坏隐藏类
调用类型保持一致             同类型、同参数个数
热对象别 delete              避免推入字典模式
字段顺序保持一致             同构对象共享隐藏类
```

## 3. 内存模型与 GC

### 3.1 可达性：泄漏的定义

GC 的判定标准只有一条——**从根出发是否可触达**：从根触达到的对象即活，触达不到即回收。

据此给出泄漏的精确含义：**泄漏 = 你以为丢了、但还能摸得到**。不是 V8 忘了回收，而是你的代码仍持有引用，让对象一直"可达"。

### 3.2 分代收集：Scavenge 与 Mark-Compact

对象按存活时间分两代、各有回收策略：

```
新生代   Scavenge    复制存活对象，快但空间小    → 新对象出生地
老生代   Mark-Compact 标记清扫+压缩，慢但空间大   → 熬过几轮的存活对象
```

**回收实测（`--expose-gc`）**：200 万个作用域垃圾，触发 GC 后堆从峰值回到 4MB 基线——纯粹的作用域临时对象会被干净回收。

### 3.3 增量与并发标记

老生代 Mark-Compact 全量标记会卡顿，用两种手段消停顿：

```
增量标记   把标记切碎穿插执行，摊薄 STW 时间
并发标记   标记过程放到后台线程，与主线程并行，几乎不占主线程
```

一句话：GC 也要"先慢后稳"——新生代快回收照旧，老生代用增量 + 并发标记把长停顿消化掉。

### 3.4 四大持有模式与泄漏定位

**泄漏实测（`--expose-gc`）**：同样的对象被全局数组持有，GC 后仍占 88MB；放开引用，回到 4MB。

**四大持有模式**（各自对应一种"该丢没丢"）：

```
全局缓存只进不出      用 LRU / WeakMap 收敛
定时器没清            清除 setInterval / setTimeout 引用
监听器没退订          移除 addEventListener / 订阅
分离 DOM              卸载后仍被变量引用着
```

> 闭包是隐性持有的主通道：回调会捕获整个外层作用域，看似只用了几个变量，实际整层都被攥住。

**定位套路（快照对比法）**：

```
快照 A → 操作 N 次 → 快照 B → Comparison 找净增长 → Retainers 看谁攥着
```

判断是否泄漏的铁律是看堆是否「楼梯形」**阶梯式增长不回落**，而不是单次内存偏高。

## 4. WebAssembly

### 4.1 定位：沙箱化可移植字节码

wasm 的定位要说准：它**不是更快的 JS，而是"算数字的函数库"**。

```
沙箱化   内存隔离、不能直接碰 DOM/JS 生态
可移植   一份字节码跨平台跑
接近原生  静态确定的指令 + 真正的 32 位整数运算
```

需要 DOM、JS 生态操纵的场景不该用 wasm；只有纯计算/大数的重活才值得请它上场。

### 4.2 模块结构：四节布局

wasm 模块由四节构成，可**手工组装字节码**：

```
类型节   声明函数的签名（参数/返回值类型）
函数节   列出模块里的函数
导出节   把内部函数暴露成可调用入口
代码节   函数体字节码指令
```

实测：**77 字节**即可手工组装一个 `sum` 模块；`Instance.exports` 得到的导出**就是普通 JS 函数**——联调无缝：`const { sum } = instance.exports`。

### 4.3 数字语义分界

wasm 与 JS 的最大差异在数字：

```
i32       真正的 32 位整数，超 2³¹ 回绕   （实测 sum 结果 1784293664）
JS double 浮点，大数不精确
大数      走 i64 / BigInt，绕开两种陷阱
```

这是第一条分界线：**大数计算不要用 i32，也别指望 JS double 精确**。

### 4.4 性能与边界成本

**性能实测**：1 亿次循环累加，wasm 39ms vs JS 145ms（约 **3.7 倍**）。

但性能不是白捡的，**跨调用边界的转换有成本**：

```
跨边界调用     参数转换 + 线性内存复制
结论          一次跨边界调用要干足够的活，摊薄转换开销
             调用频繁但每次极轻的任务，反而被边界成本吃光收益
工程路径      几乎没人手写字节码：Rust/C++ → wasm-pack / Emscripten
```

## 5. 工程落地：探针实验台与边界

### 5.1 v8-lab 探针实验台

`v8-lab` 是配套的**零依赖探针实验台**，把本篇所有实测一键复现：

```
node run.cjs      按所需 flag 分子进程执行三探针
  探针一   分层编译 / 反优化 / 隐藏类     （--allow-natives-syntax）
  探针二   GC 回收与泄漏定位               （--expose-gc）
  探针三   手写字节码 wasm 对比
node:assert 自检全绿                      可当测试跑
```

真去改代码、跑探针，比背结论更能理解"感觉 vs 实测"的差距。

### 5.2 模块边界与面试指路

与基础板块 `浏览器渲染原理` 划分边界：基础讲「页面怎么**渲染出来**」，本模块讲「引擎内部**怎么跑** + 怎么**实测**」。

四篇构成一条依赖链，每篇回答上一篇留下的问题：

```
Chrome 多进程与渲染管线（谁在跑） → V8 执行与优化（怎么跑快）
    → 内存模型与 GC（回收规则） → WebAssembly（最后的底牌）
```

常见面试问题指路见 [面试题](./面试题.md)：多进程与站点隔离、合成器与输入流转、隐藏类与反优化、GC 分代与泄漏定位、wasm 语义边界与适用场景。
