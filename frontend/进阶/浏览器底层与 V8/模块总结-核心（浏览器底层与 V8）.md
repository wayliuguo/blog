## 知识主线（一句话）

本模块回答「引擎内部是怎么跑的，以及怎么用探针把『感觉』变成『实测』」：从 Chrome 的进程/线程模型与像素旅程（谁在跑），到 V8 的分层编译、隐藏类与优化反优化（怎么跑快），再到分代 GC 与泄漏定位（怎么回收），最后落到 wasm 这张「最后的底牌」——四篇串成一条「进程 → 编译 → 内存 → 字节码」的依赖链。

## 高频核心点

### 01 Chrome 多进程与渲染管线

**多进程与站点隔离**

- 进程分工：浏览器主进程（UI/调度）· GPU 进程（合成汇总）· 网络进程 · 渲染进程（**站点隔离**，每站点一个）· 插件进程
- **多进程的价值**：崩溃隔离 + 沙箱安全；站点隔离进一步让每个站点一个渲染进程，防跨站点信息泄露
- **渲染进程四线程**：主线程（JS + 样式 + 布局 + 绘制记录）· 合成器线程（输入 + 合成）· 光栅线程池（位图）· Worker

**渲染管线与合成器**

- 管线：JS → 样式 → 布局 → 绘制记录（只出指令列表）→ 分块光栅 → 合成出帧
- **合成器为什么快**：transform/opacity 只影响合成、绕开主线程，主线程卡死动画照跑；代价是层爆炸占显存
- **输入流转**：合成器可独立滚动；click 必进主线程排队——`passive: true` 是免费的性能开关

**进程边界实测（探针）**

- 崩溃隔离 · 内存不共享（结构化克隆副本，子改父不变）· 序列化按字节付费（1 万条≈20ms、100 万条≈1.3s）· 每进程固定开销≈48MB → 进程要复用且设上限

### 02 V8 执行与优化

**分层执行**

- 分层：AST → Ignition 字节码（收集类型反馈）→ Sparkplug → Maglev → TurboFan

**隐藏类 + 内联缓存**

- 隐藏类（map）：属性按形状偏移直取；同构造函数、同字段顺序 → 共享隐藏类
- **形状要稳定**：乱序、事后加属性、delete 都会产生不同 map 或推入字典模式（实测 `%HaveSameMap`）

**优化与反优化**

- tier-up 实测（`--allow-natives-syntax`）：冷（未优化）→ 预热 10 万次 → optimized + TurboFan（status 81）
- 反优化实测：一个字符串参数让 optimized 位清零
- deopt 是设计的回退路径，热路径上反复触发才要修——保持调用形态一致

**军规（只在热路径有意义）**

- 构造函数一次初始化全字段 / 类型保持一致 / 热对象别 delete / 字段顺序一致

### 03 内存模型与 GC

**可达性与泄漏**

- **可达性定义**：从根触达即活——泄漏 = 你以为丢了但还能摸到

**分代回收**

- 新生代 Scavenge（快、小）· 老生代 Mark-Compact（慢、大）· 增量 + 并发标记消停顿

**四大持有模式（泄漏来源）**

- 全局缓存只进不出 / 定时器没清 / 监听器没退订 / 分离 DOM；闭包是隐性持有的主通道

**定位套路**

- 快照 A → 操作 N 次 → 快照 B → Comparison 找净增长 → Retainers 看谁攥着
- 回收实测（`--expose-gc`）：200 万作用域垃圾 GC 回基线（4MB）；全局持有则 GC 后仍占 88MB，放开引用回落到 4MB

### 04 WebAssembly

**定位**

- 沙箱化的可移植字节码，接近原生速度；「算数字的函数库」而非更快的 JS

**数字语义分界线**

- i32 超 2³¹ 回绕（实测 1784293664）；JS double 精确——大数走 i64/BigInt

**性能与边界成本**

- 实测：1 亿次循环累加 wasm 39ms vs JS 145ms（约 3.7 倍）
- 跨调用边界有参数转换/拷贝开销——一次跨边界调用要干足够多的活
- 工程路径：Rust/C++ → wasm-pack / Emscripten
