# Chrome 多进程与渲染管线

基础篇的「浏览器渲染原理」回答的是*页面怎么渲染出来*；这一篇往里走一层——**哪些进程、哪些线程在跑，事件和像素在它们之间怎么流转**。理解了线程模型，性能优化的很多「为什么」才有答案。

## 一、多进程架构与站点隔离

Chrome 是多进程浏览器，每个进程各司其职：

> 示意片段（无配套脚本）

```
浏览器主进程   —— UI（地址栏/标签页）、网络调度、子进程管理
GPU 进程       —— 所有进程的合成与光栅都汇总到它，统一出画面
网络进程       —— HTTP 请求（独立出来是为了不阻塞且可沙箱）
渲染进程（每站点一个）—— HTML/CSS/JS 解析执行、布局绘制
插件进程       —— 沙箱化的扩展载体
```

**站点隔离（Site Isolation）**让不同站点的渲染进程严格分开：iframe 里的第三方站点跑在自己的进程里。这是 Meltdown/Spectre 漏洞后的安全补课——进程边界是最强的隔离手段，恶意站点即使破了自己的沙箱也读不到别的站点。

> 提示：一个标签页打开同站点的 iframe 共享一个渲染进程；`crossorigin` 的 iframe 则拆出去。这就是「同一页面可能有十几个渲染进程」的原因。

## 二、渲染进程内部：谁在干活

渲染进程里真正关心的是四类线程：

| 线程 | 干什么 | 对你的意义 |
| --- | --- | --- |
| 主线程 | JS 执行、样式计算、布局（Layout）、绘制记录（Paint） | **卡顿的元凶都在这** |
| 合成器线程（compositor） | 接收输入、调度光栅、合成图层 | 可绕过主线程直接滚动 |
| 光栅线程池 | 把绘制记录变成真实位图 | 分块（tile）光栅化 |
| Worker 线程 | Web Worker / Service Worker | 你的逃生通道 |

关键分工：**主线程跑你的 JS 并产出「绘制记录」，光栅线程把记录变成位图，合成器线程把位图拼成最终画面**。三层各管一段，所以「主线程卡住时页面还能滚动」——滚动由合成器线程接管。

## 三、渲染管线：像素的完整旅程

> 示意片段（无配套脚本）

```
主线程                          其他线程
─────────────────────          ─────────────
JS 执行（改了 DOM/样式）
  ↓
样式计算（computedStyle）
  ↓
布局 Layout（几何）
  ↓
绘制记录 Paint（"画什么"的指令列表）
  ↓  —— 提交 ──→  分块 → 光栅化（位图）   [光栅线程池]
                                ↓
                  合成 Layers → 出帧      [合成器线程 → GPU 进程]
```

注意绘制与光栅的分离：**Paint 阶段只产出「怎么画」的指令列表（记录），真正的位图由光栅线程异步生成**。这就是为什么「重排（Layout + 后续全链）」远贵于「重绘（跳过 Layout）」、而「仅合成（transform/opacity）」可以完全不碰主线程。

## 四、合成器为什么快

`transform` 与 `opacity` 动画流畅的秘密：它们的属性变化**只影响合成阶段**——

> 示意片段（无配套脚本）

```css
/* 推荐：只走合成，不进主线程 */
.box { transition: transform 0.3s; }
.box:hover { transform: translateX(100px); }

/* 反例：left 变化触发 Layout → Paint → 光栅 → 合成 全链 */
.bad { position: absolute; left: 0; transition: left 0.3s; }
.bad:hover { left: 100px; }
```

合成器线程拿到已光栅化的图层，改一下变换矩阵就出新帧——主线程哪怕正被长任务卡死，动画照跑。代价是**合成层会占显存**，滥用 `will-change` 让成百上千元素各自成层，就是「层爆炸」。

## 五、输入事件流转

你滚动页面、点击按钮时发生了什么：

> 示意片段（无配套脚本）

```
鼠标/触摸事件
  → 浏览器进程（收到硬件事件）
  → 渲染进程合成器线程（拿到事件坐标）
     ├ 滚动：目标区域无主线程监听 → 合成器直接滚动（主线程卡了也能滚）
     └ 点击：涉及页面元素 → 转发主线程 JS 处理
```

两个工程推论：

1. **滚动监听用 `passive: true`**——告诉浏览器「我不会 preventDefault」，合成器就可以不等主线程直接滚动；
2. **长任务会让点击也变卡**——因为 click 必须进主线程排队，滚动却不用。这就是为什么 INP 关注交互延迟而滚动体验相对独立。

> 提示：触摸/滚轮事件的监听器默认在部分场景被当作「可能阻塞滚动」处理，合成器必须等它执行完才能决定是否滚动——`{ passive: true }` 是免费的性能开关。

## 六、性能含义小结

| 现象 | 线程级解释 |
| --- | --- |
| 长任务卡交互 | JS 在主线程，输入也要进主线程排队 |
| transform 动画不掉帧 | 只走合成器，绕开主线程 |
| 大图滚动掉帧 | 光栅化慢于滚动速度，出「白块」（ checkerboard） |
| 频繁 reflow 卡顿 | Layout 在主线程，挤占了 JS 与事件处理 |
| Worker 优化有效 | 计算挪出主线程，主线程只收结果 |

## 小结

- Chrome 多进程与渲染管线
  - 多进程：浏览器主进程 / GPU / 网络 / 渲染进程（站点隔离，每站点一个）/ 插件
  - 渲染进程四线程：主线程（JS+样式+布局+绘制记录）、合成器（输入+合成）、光栅池（位图）、Worker
  - 管线：JS → 样式 → 布局 → 绘制记录 →（光栅线程池）分块光栅 →（合成器）合成出帧
  - Paint 只出指令列表，位图异步光栅化——重排贵于重绘贵于仅合成
  - transform/opacity 只影响合成，主线程卡死动画照跑；代价是层爆炸占显存
  - 输入流转：合成器可独立滚动；click 必进主线程——passive 监听器是免费开关
