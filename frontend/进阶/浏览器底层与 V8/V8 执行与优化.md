# V8 执行与优化

同一段 JS，为什么「先跑几千次热身」比第一次快几倍？为什么对象属性加的顺序不同也能影响性能？这一篇用 V8 自带的探针指令（`--allow-natives-syntax`）把这些问题变成**可实测的结构证据**，全部结论来自 `v8-lab/opt.cjs` 的真实运行输出。

## 一、一段 JS 在 V8 里的旅程

V8 执行 JS 不是「解释器直接跑」也不是「直接编译机器码」，而是**分层**：

> 示意片段（无配套脚本）

```text
源码 → AST（解析）
     → Ignition 字节码（解释执行，同时收集类型反馈）
     → Sparkplug（快速基线编译，少优化但比解释快）
     → Maglev（中层优化，用类型反馈做假设）
     → TurboFan（顶层优化，激进假设 + 激进回退）
```

类型反馈（feedback）是关键：Ignition 边跑边记录「这个加法的操作数是 int」「这个属性访问的对象是什么形状」，优化编译器据此**押注**——假设接下来类型不变，生成直通机器码；押错了就触发**反优化**退回解释器。

## 二、隐藏类与内联缓存

V8 不用哈希表存对象属性（慢），而是给每个对象挂一个**隐藏类（map）**描述「有哪些属性、在哪个偏移」。属性访问经**内联缓存（IC）**加速：记住上次访问的对象形状，下次形状相同就直接按偏移取。

用 `%HaveSameMap` 可以直接验证两个对象是否共享隐藏类：

> 摘自 `./code/v8-lab/opt.cjs`

```js
// ── 3. 隐藏类：同构与异构 ──────────────────────────────────────
function Point(x, y) { this.x = x; this.y = y }
const p1 = new Point(1, 2)
const p2 = new Point(3, 4)
assert.ok(%HaveSameMap(p1, p2), '同构造函数产出应共享隐藏类')
const diffOrder = { y: 2, x: 1 } // 同字段、不同添加顺序
assert.ok(!%HaveSameMap(p1, diffOrder), '属性顺序不同 → 隐藏类不同')
const g = new Point(1, 2)
g.z = 3 // 事后加属性 → 派生出新的隐藏类
assert.ok(!%HaveSameMap(p1, g))
```

实测输出（`--allow-natives-syntax`）：

> 摘自 `./code/v8-lab/opt.cjs`

```js
console.log('隐藏类  : 同构 true · 乱序 false · 加属性 false · delete 后进入字典模式')
console.log('\n探针一通过 ✓')
```

三个对工程有直接意义的结论：

1. **同构造函数、同顺序 → 同隐藏类**（IC 直通最快路径）；
2. **同字段不同顺序 → 不同隐藏类**—— `{ y, x }` 与 `{ x, y }` 在 V8 眼里是两种形状；
3. **事后加属性会派生新隐藏类**——这就是「在构造函数里一次初始化所有字段」这条优化军规的由来。

delete 更狠——直接把对象推入**慢属性（字典）模式**：

> 摘自 `./code/v8-lab/opt.cjs`

```js
// delete 把对象推入「慢属性（字典）模式」，与同形状字面量也不再同构
function makeXYZ() { const o = { x: 1, y: 2, z: 3 }; delete o.y; return o }
const f1 = makeXYZ()
const f2 = makeXYZ()
const same = { x: 1, z: 3 }
assert.ok(%HaveSameMap(f1, f2), '同样的 delete 序列产出同构对象')
assert.ok(!%HaveSameMap(f1, same), 'delete 后与同形状字面量隐藏类不同')
```

`{ x, z }` 字面量与「三属性对象删掉 y」即便长得一模一样，隐藏类也不同——后者走哈希查找。热路径对象**用 `undefined` 赋值代替 delete**。

## 三、分层编译：实测 tier-up

用 `%GetOptimizationStatus` 追踪一个函数的状态位（16 = optimized，64 = TurboFan，128 = interpreted）：

> 摘自 `./code/v8-lab/opt.cjs`

```js
// ── 1. 分层编译：冷 → 预热 → 优化 ───────────────────────────────
function add(a, b) { return a + b }
const cold = %GetOptimizationStatus(add)
assert.equal(cold & 16, 0) // 冷启动：未优化
for (let i = 0; i < 1e5; i++) add(i, i)
const warm = %GetOptimizationStatus(add)
assert.ok(warm & 16, '预热足够多次后应进入优化状态')
assert.ok(warm & 64, 'add 足够简单，应被 TurboFan 编译')
console.log(`分层编译: cold=${cold}(未优化) → warm=${warm}(optimized+TurboFan)`)
```

实测：`cold=262145（未优化）→ warm=81（optimized + TurboFan）`——**调用 10 万次后，add 已从解释执行变成优化机器码**。所谓 JIT「先慢后快」，就是这个迁移过程。

## 四、优化与反优化

优化代码基于类型反馈押注。喂进不同类型，押注失败：

> 摘自 `./code/v8-lab/opt.cjs`

```js
// ── 2. 反优化：类型反馈被打脸 → 退出优化代码 ────────────────────
function concat(a, b) { return a + b }
for (let i = 0; i < 1e5; i++) concat(i, i)
assert.ok(%GetOptimizationStatus(concat) & 16)
concat('a', 'b') // 喂进字符串：与优化代码假设的类型不符
concat(1, 2)
assert.equal(%GetOptimizationStatus(concat) & 16, 0, '类型变化应触发反优化')
console.log(`反优化  : 喂入字符串后 optimized 位清零(status=${%GetOptimizationStatus(concat)})`)
```

实测：`optimized 位清零`——**一个字符串参数就把十万次预热攒下的优化代码作废了**。函数会重新走解释 → 收集反馈 → 再优化，热路径上反复 deopt 是隐形性能杀手。

## 五、工程含义清单

| 军规 | 原理（对应实测） |
| --- | --- |
| 构造函数里初始化所有字段 | 事后加属性派生新隐藏类（§二） |
| 同一操作保持同一种类型 | 类型打脸触发 deopt（§四） |
| 别在热对象上 delete | 推入字典模式（§二） |
| 对象字段顺序保持一致 | 顺序不同隐藏类不同（§二） |
| 高频函数参数避免多形态 | IC 从单态退化到多态/超态 |
| 热路径避免 `arguments` / `try-catch` 包裹 | 历史上的优化禁区（现代 V8 已大幅缓解） |

> 提示：这些军规只在**热路径**上有意义。V8 对冷代码无所谓——为冷函数扭曲可读性是负优化。先用性能面板找到热点，再谈形状。

## 小结

- V8 执行与优化
  - 分层执行：AST → Ignition 字节码（收集类型反馈）→ Sparkplug → Maglev → TurboFan
  - 隐藏类（map）+ 内联缓存：属性访问按形状偏移直取；`%HaveSameMap` 可实测
  - 实测：同构 true · 乱序 false · 事后加属性 false · delete 推入字典模式
  - tier-up 实测：冷（未优化）→ 预热 10 万次（optimized + TurboFan）
  - 反优化实测：一个字符串参数让 optimized 位清零
  - 军规只在热路径有意义：先找热点，再保形状
