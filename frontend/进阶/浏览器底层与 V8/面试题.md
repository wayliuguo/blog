# 浏览器底层与 V8：面试题

> 格式：结论 → 原理 → 边界/坑 → 追问。标注「见第 X 篇」的题目按阅读顺序出题。

### Q1: Chrome 为什么用多进程？站点隔离是什么？（第 1 篇）

- **结论**：多进程让崩溃隔离、沙箱安全；站点隔离进一步做到「每个站点一个渲染进程」，防跨站点信息泄露。
- **原理**：浏览器主进程管 UI 与调度，GPU 进程统一出画面，渲染进程跑页面（JS/布局/绘制），网络进程独立。进程是操作系统级隔离，恶意站点即使攻破自己进程的沙箱也读不到别的站点——这是 Meltdown/Spectre 后的安全补课。
- **边界**：同站点 iframe 共享渲染进程，跨站 iframe 拆出去——一个复杂页面可能十几个渲染进程，内存占用随之上升。
- **追问**：为什么主线程卡死时页面还能滚动？→ 滚动由渲染进程的合成器线程接管，不需要主线程；只有当滚动监听器可能 `preventDefault` 时合成器才需要等主线程（所以有 `passive: true`）。

### Q2: transform 动画为什么比 left 动画流畅？（第 1 篇）

- **结论**：left 变化走「布局 → 绘制记录 → 光栅 → 合成」全链且在主线程；transform 只影响合成阶段，可以完全绕开主线程。
- **原理**：渲染管线里 Paint 只产出「怎么画」的指令列表，位图由光栅线程池异步生成，合成器线程用已光栅化的图层改变换矩阵出帧。transform/opacity 是合成器可直接处理的属性。
- **边界**：合成层占显存，滥用 `will-change` 会层爆炸；属性变化的元素要真正提升为独立图层才有收益。
- **追问**：长任务为什么让点击变卡但滚动不卡？→ click 事件必须转发到主线程 JS 处理（排队），滚动由合成器独立完成——这也是 INP 只关注交互延迟的原因。

### Q3: 什么是隐藏类（map）？写代码时怎么配合它？（第 2 篇）

- **结论**：V8 给每个对象挂一个描述「属性布局」的隐藏类，属性访问按偏移直取；代码要保持对象形状稳定才能让内联缓存走最快路径。
- **原理**：同构造函数、同字段顺序 → 共享隐藏类；乱序、事后加属性、delete 都会产生不同 map 或推入字典模式。实测（`%HaveSameMap`）：`new Point(1,2)` 与 `new Point(3,4)` 同构；`{y:2,x:1}` 与构造产物异构；delete 后的对象与同形状字面量异构。
- **边界**：军规只对热路径有意义——冷函数形状怎么写都无所谓，为可读性让路；先用性能面板找热点再优化。
- **追问**：怎么用 Node 验证这些结论？→ `node --allow-natives-syntax` 下用 `%HaveSameMap(a,b)` 看隐藏类、`%GetOptimizationStatus(fn)` 看优化状态位（16=optimized、64=TurboFan、128=interpreted），v8-lab 实测 cold=262145 → warm=81。

### Q4: 什么是反优化（deopt），怎么触发的？（第 2 篇）

- **结论**：优化代码基于类型反馈押注；押错（喂进与假设不符的类型）就退出优化代码，退回解释器重新收集反馈。
- **原理**：实测——函数用数字预热 10 万次进入 optimized+TurboFan，随后一个字符串参数让 optimized 位清零（status 129）。JIT「先慢后快」与「反复 deopt 是隐形杀手」都是这个机制的两面。
- **边界**：deopt 不是错误，是设计的回退路径；热路径上反复触发才要修——修法是保持调用形态一致（同类型、同参数个数、同形状对象）。
- **追问**：为什么「同一函数传不同类型」比「两个函数各传一种类型」慢？→ 前者让类型反馈膨胀、IC 从单态退化到多态/超态，优化假设变弱甚至放弃优化。

### Q5: GC 怎么工作的？什么样的代码会泄漏？（第 3 篇）

- **结论**：GC 按「从根出发是否可触达」回收；泄漏的唯一原因是代码仍持有引用，而不是 V8 忘了回收。
- **原理**：新生代 Scavenge 复制存活对象（快），老生代 Mark-Compact（慢），增量 + 并发标记消停顿。实测（`--expose-gc`）：200 万个作用域垃圾 GC 后堆从峰值回到 4MB 基线；同样的对象被全局数组持有则 GC 后仍占 88MB，放开引用即回落。
- **边界**：四大持有模式——全局缓存只进不出（用 LRU/WeakMap）、定时器没清、监听器没退订、分离 DOM；闭包是隐性持有的主通道（回调捕获整个外层作用域）。
- **追问**：怎么定位线上「越用越卡」？→ DevTools 快照对比法：操作前拍 A、操作 N 次拍 B，Comparison 按 Delta 找净增长的构造函数，Retainers 链看谁攥着；判断标准是堆「楼梯形」阶梯增长不回落，而非单次内存高。

### Q6: WebAssembly 快在哪？什么时候不该用？（第 4 篇）

- **结论**：快在静态确定的指令与真正的 32 位整数（无类型反馈、无 deopt 风险），实测循环密集计算约 3.7 倍于 JS；不该用在「调用频繁但每次极轻」的任务和一切依赖 DOM/JS 生态的场景。
- **原理**：wasm 是沙箱化的可移植字节码，模块由类型/函数/导出/代码四节构成，`Instance.exports` 直接得到可调用的 JS 函数。手写字节码实测：77 字节即可组装一个 `sum` 模块。
- **边界**：数字语义是第一条分界线——i32 超 2³¹ 回绕（实测 sum(1e6)=1784293664），JS double 精确；跨调用边界有参数转换与线性内存复制成本，**一次调用要干足够多的活**才划算。
- **追问**：工程上怎么获得 wasm 模块？→ 几乎没人手写字节码：Rust/C++ 源码经 wasm-pack / Emscripten 编译为 npm 包；典型案例 Figma、Photoshop Web、SQLite wasm。
