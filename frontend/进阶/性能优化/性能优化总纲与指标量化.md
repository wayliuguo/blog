# 性能优化总纲与指标量化

这一篇是整个模块的总纲与起点：先把「优化性能到底在优化什么」定下来，再把量化这一步走完——指标、辅助指标、两种口径、采集代码、测量工具。

后面三篇各自服务一个核心目标（LCP / INP / CLS），不再重复这些内容。所有读数都来自 `code/perf-lab`（零依赖，用本机无头 Chrome 真跑真测）。

## 一、整体思路：四步主线与三个核心目标

性能优化最容易陷入的困境不是「没有手段」，而是「手段太多、不知道该用哪个」。这个模块按一条主线组织，你随时能定位自己走到哪一步：

```
先量化指标  ──►  定位瓶颈  ──►  分层优化  ──►  持续监控
   本篇            各篇第1节       各篇主体        性能优化闭环
```

**核心目标只有三个**，它们就是 Core Web Vitals——Google 挑出来「直接对应用户感受」的三个指标，各自对应一类体验：

| 核心目标 | 指标（看 p75） | 用户的话 |
| --- | --- | --- |
| 加载性能 | LCP ≤ 2.5s | 什么时候能看到内容 |
| 交互响应 | INP ≤ 200ms | 点了多久有反应 |
| 视觉稳定 | CLS ≤ 0.1 | 页面会不会自己乱跳 |

**其余指标都不是目标，是诊断用的辅助指标。** TTFB、FCP、TBT、TTI、SI 的价值在于**定位**：核心指标是一个结果，辅助指标把这个结果拆到时间轴上，告诉你卡在哪一段。LCP 差，光看 LCP 只能说「不太行」，把 TTFB 和资源瀑布摆在一起才能说出「是服务端慢还是资源太大」。第三节专门讲这层从属关系。

因为核心目标正好三个，本模块后面三篇**每篇服务且只服务一个核心目标**，结构统一：

```
先定位：把这个核心指标拆成几段，逐段排查（回答「差在哪一段」）
  ↓
分层手段：网络 / 构建 / JS 执行 / 渲染 / 资源 / 框架 / 感知，各层给可落地的做法
```

**分层是手段的归属维度，不是篇章骨架**，它和「指标」这个维度正交：一条手段常同时服务多个指标（代码分割既改善 LCP 也改善 INP），而有些手段不归属任何单一指标（感知性能、内存、框架层）。两者在「优化手段速查」篇用一张矩阵对上，一个都不丢。

## 二、核心指标：LCP / INP / CLS

这三个之所以是核心，是因为它们各自**等于一个核心目标**，而且都是结果型指标——用户能直接感受到。下面逐个拆开，每个都配本仓实验台的实测。

| 维度 | 指标 | 回答的问题 |
| --- | --- | --- |
| 加载 | LCP | 主要内容什么时候看到 |
| 交互 | INP（取代 FID） | 点下去多久有反应 |
| 稳定 | CLS | 页面会不会自己乱跳 |

### LCP（Largest Contentful Paint，最大内容绘制）

LCP 是**视口内最大的那块内容**渲染完成的时刻。候选元素按优先级包括：

- `<img>`、`<svg>` 内嵌 `<image>`、`<video>` 的封面图
- 用 `url()` 加载背景图**的元素**（背景图本身不算，元素算）
- 包含文本节点的块级元素（纯文字页面里，一整块标题就是候选）

**目标值**：≤ 2.5s（看第 75 百分位，不是平均值）。

LCP 由四段构成，优化时按这个顺序找瓶颈：

```
LCP = TTFB（服务器 + 网络）
    + 资源加载延迟（发现资源够不够早、优先级对不对）
    + 资源加载时长（体积、带宽）
    + 元素渲染延迟（主线程忙不忙、要不要等 JS）
```

> 摘自 `./code/perf-lab/scenarios/metrics.mjs`（运行：`npm run metrics`）

```js
    const rows = await sweep('/metrics.html', [
        { name: '轻量首屏', query: { mode: 'light' }, rounds: 3 },
        { name: '未治理首屏', query: { mode: 'heavy' }, rounds: 3 }
    ])
```

两台页面的差别只有两处：重版本多了一个 500KB 的 parser 阻塞脚本，以及一张 300KB 的首屏大图。实测结果（3 轮中位数）：

```
| 页面       | TTFB   | FCP     | LCP     | 位移  | DOMContentLoaded | load    | 长任务 | 最长任务 |
|------------|--------|---------|---------|-------|------------------|---------|--------|----------|
| 轻量首屏   | 159 ms | 396 ms  | 396 ms  | 0.000 | 381 ms           | 382 ms  | 0      | 0 ms     |
| 未治理首屏 | 160 ms | 2600 ms | 4024 ms | 0.000 | 2589 ms          | 4010 ms | 0      | 0 ms     |
```

TTFB 基本一致（160 ms vs 159 ms）——服务端没问题；LCP 差了 10 倍，全部来自资源侧。这一条就否掉了「先去优化服务器」的方向。

### INP（Interaction to Next Paint，交互到下次绘制）

INP 量的是**整个页面生命周期内所有交互**里最有代表性的那一次：从用户点击开始，到浏览器把这次交互的结果绘制到屏幕上为止。它比 FID 合理的地方在于——FID 只看第一次输入（且只算「等待响应」的那段队列时间，不含处理耗时），而 INP 看全程、含处理与绘制。

**目标值**：≤ 200ms。

INP 差的根因几乎总是同一个：**主线程被长任务占住了**。浏览器只有在一个任务结束后才能处理输入，所以一个 300ms 的长任务会把期间所有点击都推迟到 300ms 之后。

> 摘自 `./code/perf-lab/scenarios/longtask.mjs`（运行：`npm run longtask`）

```js
    const rows = await sweep('/longtask.html', [
        { name: '一次做完', query: { mode: 'sync' }, rounds: 3 },
        { name: '分片切片', query: { mode: 'chunked' }, rounds: 3 }
    ])
```

实测 60000 行列表的两种渲染写法：

```
| 做法     | 总耗时  | 分片数 | 最长同步块 | 首屏可见耗时 | 超过 50ms 的块 |
|----------|---------|--------|------------|--------------|----------------|
| 一次做完 | 737 ms  | 1      | 737 ms     | 737 ms       | 1              |
| 分片切片 | 1152 ms | 10     | 144 ms     | 162 ms       | 10             |
```

一次做完的那一版有一个 737ms 的同步块——这 737ms 里用户点任何东西都不会有反应。切片版总耗时反而更长（多 415ms，每次结算布局都有固定开销），但最长块降到 144ms、首屏可见从 737ms 降到 162ms。**这就是「总耗时」和「INP」不是一回事的地方**。INP 的详细优化手段见「交互性能与 INP」篇。

### CLS（Cumulative Layout Shift，累积布局偏移）

CLS 量的是「内容自己动了多少」。一次位移的分数是：

```
单次位移分数 = 影响比例（impact fraction）× 位移距离比例（distance fraction）
```

- **影响比例**：不稳定元素在位移前后占据的视口区域并集，占整个视口面积的比例
- **位移距离比例**：元素移动的最大距离，除以视口高度

CLS 是所有单次分数之和。**目标值：≤ 0.1。**

两个最常见的来源，实测一下就很清楚：

> 摘自 `./code/perf-lab/scenarios/cls.mjs`（运行：`npm run cls`）

```js
    const rows = await sweep('/cls.html', [
        { name: '无预留', query: { mode: 'bad' }, rounds: 3 },
        { name: '有预留', query: { mode: 'good' }, rounds: 3 }
    ])
```

```
| 版本   | 位移合计 | 位移次数 | 评级 | FCP    | LCP    |
|--------|----------|----------|------|--------|--------|
| 无预留 | 0.300    | 2        | 差   | 336 ms | 740 ms |
| 有预留 | 0.000    | 0        | 良好 | 324 ms | 720 ms |
```

两次位移各自是什么，脚本会打出来：

```
---- 两次位移分别是什么 ----
[无预留] +0.0901 @730ms  +0.1922 @785ms
[有预留] 没有位移
```

`@730ms` 那次是图片：不给 `width` / `height`，浏览器先按 0 高排，图回来才知道要占 240px，下面的卡片整体下移。`@785ms` 那次是横幅：240px 高的元素插到了 `body` 最前面，整页内容被顶下去一次。

修法就两条，对应两个坑：**给图片写死尺寸**（或 `aspect-ratio`）、**给晚到的动态内容预留空间**（`min-height` 占位容器）。

> 注意 `transform` 与 `top` / `left` 的区别：位移分数的判定只看元素的**起始位置**是否变化。用 `transform: translate()` 做动画，元素在布局里的位置没变，不产生 CLS；改 `top` / `margin` 会。

## 三、辅助指标：把核心指标的差定位到阶段

辅助指标不单独作为目标。核心指标告诉你「差」，辅助指标告诉你「差在哪一段」，两者是从属关系而非并列关系。

一个页面从被请求到用户能顺畅操作，中间隔着一串阶段。每个指标负责定位其中一个阶段：

```
请求发出 ──► 首字节到达 ──► 首次绘制 ──► 首次有意义内容 ──► 最大内容元素 ──► 可交互 ──► 交互响应
   TTFB ────────┘              FCP ────────┘        LCP ─────────┘       TTI ────┘   INP
                                                                             ▲
                              整个过程里「主线程被长任务占住的时间」= TBT ──────┘
                              整个过程里「内容意外跳动」的累积 = CLS
```

这张图有三个用法：

1. **上游决定下游**。TTFB 是 3 秒，后面的 FCP / LCP 不可能好到哪去——先修上游。实测里「未治理首屏」TTFB 只有 160 ms，问题全在后面（阻塞脚本），这时去优化服务端毫无收益。
2. **指标之间要互相印证**。FCP 与 DCL 的差距说明「首屏画出来后还剩多少解析/执行工作」；TBT 大而 LCP 小说明「看得见但点不动」。
3. **一个数不构成结论**。单看 LCP = 2.6s 只能说「不太行」，把 TTFB / FCP / 资源瀑布摆在一起才能说出「是资源下得慢还是被脚本挡住了」。

### FP 与 FCP

- **FP（First Paint）**：第一个像素被绘制。不关心画了什么，白底也算。
- **FCP（First Contentful Paint）**：第一次画出**有意义内容**——文字、图片、非白底 canvas。

**目标值：FCP ≤ 1.8s。** FCP 与 FP 之间如果差得远，通常说明「先铺了背景色，内容还没来」，用户看到的是空壳。

### TTFB（Time to First Byte）

从请求发出到**响应头第一个字节**到达，串起了 DNS、TCP/TLS 握手、服务端处理、首字节传输。它是所有加载指标的上限。

**目标值：≤ 800ms**（纯服务端处理时长在 200ms 以内算健康）。静态资源走 CDN 时 TTFB 通常 20~80ms，如果看到 500ms 以上，先怀疑回源和缓存没命中。

### TBT、TTI 与 SI

- **TBT（Total Blocking Time）**：FCP 到 TTI 之间，所有长任务**超出 50ms 的部分**之和。一个 80ms 的长任务贡献 30ms。目标值 ≤ 200ms。
- **TTI（Time to Interactive）**：页面「可靠响应输入」的时刻。判定是「已有 FCP + 主线程连续 5s 没有超过 50ms 的长任务」。
- **SI（Speed Index）**：可视内容填充速度，靠逐帧截图算像素变化速率。越低表示内容呈现得越连贯，Lighthouse 参考值 ≤ 3.4s。

TBT 是 INP 的**实验室代理指标**——真实用户的 INP 要等交互才有，而 TBT 在加载阶段就能量出来。

```
TTFB → FP → FCP → (TBT 在这段累积) → TTI ─────► LCP 可能还在等图片
 └── 加载起点 ──┘└──── 内容呈现 ────┘└─ 可交互 ─┘
```

留意一个容易搞反的点：**LCP 不保证早于 TTI**。首屏图片很大时，页面已经能点了（TTI 到了），最大内容元素还在下载，LCP 反而更晚。上面那张实测表里，「未治理首屏」的 LCP（4024ms）就晚于 DOMContentLoaded（2589ms）。

## 四、怎么判断好坏：两种口径、分位数与评级区间

量出数字之后，还差一步才算「评估」：这个数到底算好还是差。

同一套指标，从两个地方拿，含义不一样：

| | 实验室（Lab） | 现场（Field / RUM） |
| --- | --- | --- |
| 数据来源 | 固定设备 + 模拟网络跑一次 | 真实用户的浏览器 |
| 典型工具 | Lighthouse、本仓 perf-lab | Web Vitals 采集 SDK + 上报 |
| 优势 | 可复现、可对比、能看火焰图定位 | 反映真实分布，不受单一环境误导 |
| 劣势 | 只代表这一次，不代表用户分布 | 噪声大，看不出根因 |

**正确的分工**：现场数据发现问题（「75 分位 LCP 4.2s，主要集中在移动端 4G」），实验室数据定位根因（「同一页面本地开 4G 节流能复现，阻塞脚本占了 2.2s」），改完再回现场看分布有没有真的变好。

还要注意**分位数 vs 平均值**：性能数据是长尾分布，平均值会被少数极快或极慢的样本带偏。Core Web Vitals 统一看 75 分位（p75），含义是「75% 的用户体验不差于这个值」。

有了数字，下一步是判断好坏。评级区间是硬标准，写成代码最省事：

> 摘自 `./code/perf-lab/scenarios/score.mjs`（运行：`npm run score`）

```js
/** 各指标的 [良好上限, 待改进上限]，超过第二个值即为「差」 */
const THRESHOLDS = {
    ttfb: [800, 1800],
    fcp: [1800, 3000],
    lcp: [2500, 4000]
}

function rate(name, value) {
    const [good, ok] = THRESHOLDS[name] || [Infinity, Infinity]
    if (value == null) return '—'
    if (value <= good) return '良好'
    if (value <= ok) return '待改进'
    return '差'
}
```

CLS 的区间不是线性的，单独写一个：

> 摘自 `./code/perf-lab/scenarios/score.mjs`

```js
function rateCls(value) {
    if (value == null) return '—'
    if (value <= 0.1) return '良好'
    if (value <= 0.25) return '待改进'
    return '差'
}
```

一张页面的整体结论由四个单项汇总，取最差的一档：

> 摘自 `./code/perf-lab/scenarios/score.mjs`

```js
                const rs = [rate('ttfb', m.ttfb), rate('fcp', m.fcp), rate('lcp', m.lcp), rateCls(m.clsRaw)]
                const bad = rs.filter(r => r === '差').length
                const warn = rs.filter(r => r === '待改进').length
                const overall = bad ? '差' : warn ? '待改进' : '良好'
```

把四个页面一起跑出来的体检表：

```
| 页面       | TTFB          | FCP              | LCP           | CLS（全量位移） | 整体 |
|------------|---------------|------------------|---------------|-----------------|------|
| 轻量首屏   | 194 ms ✓ 良好 | 400 ms ✓ 良好    | 400 ms ✓ 良好 | 0.000 ✓ 良好    | 良好 |
| 未治理首屏 | 111 ms ✓ 良好 | 2612 ms ! 待改进 | 4028 ms ✗ 差  | 0.000 ✓ 良好    | 差   |
| CLS 无预留 | 115 ms ✓ 良好 | 384 ms ✓ 良好    | 768 ms ✓ 良好 | 0.300 ✗ 差      | 差   |
| CLS 有预留 | 104 ms ✓ 良好 | 368 ms ✓ 良好    | 752 ms ✓ 良好 | 0.000 ✓ 良好    | 良好 |

| 指标  | 良好     | 待改进     | 差      |
|-------|----------|------------|---------|
| TTFB  | ≤800ms   | ≤1800ms    | >1800ms |
| FCP   | ≤1800ms  | ≤3000ms    | >3000ms |
| LCP   | ≤2500ms  | ≤4000ms    | >4000ms |
| CLS   | ≤0.1     | ≤0.25      | >0.25   |
| INP   | ≤200ms   | ≤500ms     | >500ms  |
```

「未治理首屏」和「CLS 无预留」两张表挂了同一个结论——**差**，但原因是两个完全不同的东西：前者是加载慢，后者是内容跳。所以体检表的价值不是排名，是**把「哪里差」定位到具体指标**。

区间用起来还有两个容易踩的坑：

- **评级是门槛不是排名**。LCP 从 8000ms 优化到 3000ms，评级仍是「待改进」，但用户体感已经是两个世界。
- **一次只盯一个**。四个指标一起抠，改动互相干扰、也看不出是哪个手段起的作用。把「差」先拉到「待改进」，再统一进「良好」。

## 五、怎么量：采集代码怎么写到页面里

指标的产生方式决定了采集代码的结构，这一节把链路从「产生」走到「上报」。

指标的产生方式分两类，这是采集代码的结构基础：

- **能从缓冲区直接读**：TTFB、FP、FCP、导航类时间。页面到达时它们已经在 `performance` 缓冲区里，`getEntriesByType()` 一次取完。
- **必须订阅**：LCP、CLS、长任务。它们是**累积**或**持续发生**的，只能在事件产生时收，收完还要等「不再变化」才能上报。

订阅统一走 `PerformanceObserver`，一次封装好能用很久：

> 摘自 `./code/perf-lab/pages/lab.js`

```js
    const observe = (type, cb) => {
        try {
            new PerformanceObserver(list => {
                for (const entry of list.getEntries()) cb(entry)
            }).observe({ type, buffered: true })
        } catch (err) {
            /* 浏览器不支持该条目类型时静默跳过 */
        }
    }
```

`buffered: true` 是关键——它让观察器能拿到**注册之前**已经产生的条目。否则你在页面底部注册 LCP 观察器，就会漏掉更早发生的那些。

有了 `observe`，四类指标各一行：

> 摘自 `./code/perf-lab/pages/lab.js`

```js
    observe('paint', e => (e.name === 'first-paint' ? (metrics.fp = e.startTime) : (metrics.fcp = e.startTime)))
    observe('largest-contentful-paint', e => (metrics.lcp = e.startTime))
    // …（layout-shift 的订阅见第六节）
    observe('longtask', e => longtasks.push({ start: e.startTime, duration: e.duration }))
```

缓冲区的那些在快照时一次取完：

> 摘自 `./code/perf-lab/pages/lab.js`

```js
    function snapshot() {
        const nav = performance.getEntriesByType('navigation')[0]
        if (nav) {
            metrics.ttfb = nav.responseStart
            metrics.domContentLoaded = nav.domContentLoadedEventEnd
            metrics.load = nav.loadEventEnd
        }
        const out = {}
        for (const [key, value] of Object.entries(metrics)) out[key] = round(value)
        return out
    }
```

**上报时机**是这条链路里最容易做错的一环。短时指标（TTFB / FCP）在 `load` 之后就是定值了；LCP 和 CLS 会一直变到用户离开页面为止，必须等页面进入隐藏态再报，否则报的是一个中途值。

> 摘自 `./code/perf-lab/harness/index.mjs`

```js
export async function measure(page, options = {}) {
    const { query = {}, rounds = 1, timeout = 30000, flags = [] } = options
    const srv = await startServer(options.server)
    try {
        const collected = []
        for (let round = 0; round < rounds; round++) {
            const qs = new URLSearchParams(Object.entries(query).map(([k, v]) => [k, String(v)])).toString()
            const wait = srv.nextReport(timeout)
            const chrome = openChrome(srv.origin + page + (qs ? `?${qs}` : ''), flags)
            try {
                collected.push(await wait)
            } finally {
                chrome.kill()
            }
        }
        return rounds === 1 ? collected[0] : medianDeep(collected)
    } finally {
        await srv.close()
    }
}
```

这段是实验台的编排（起服务 → 开无头 Chrome → 等页面回报），但它也说明了上报链路的形状：**页面侧只负责把数据送出去，聚合与判定放在外面**。真实项目里「外面」就是监控 SDK 的接收端，留给「性能与体验监控」篇展开。

顺带一个采样上的经验：**性能数据不必 100% 采集**。它是分布统计，1%~10% 的样本足够看趋势，而全量上报带来的带宽与服务端成本是实打实的。采样要按用户维度稳定（同一用户始终进/出样本），否则分位数会失真。

## 六、CLS 的双口径：无头环境里为什么恒为 0

采集 CLS 时会撞上一个规范细节，不搞清楚会得出完全错误的结论。

实验台一开始量不出位移——两个版本 CLS 都是 0。查下去发现是规范本身的一个细节：

> 摘自 `./code/perf-lab/pages/lab.js`

```js
    observe('layout-shift', e => {
        // 规范口径：位移发生在用户输入后 500ms 内属于「预期位移」，不计入 CLS
        // 无头环境里没有真实输入，hadRecentInput 却是 true，所以两个值都留着：
        // cls 是上报给监控的口径，clsRaw 是「所有位移之和」，对照实验读 clsRaw
        metrics.shifts += 1
        metrics.clsRaw += e.value
        if (!e.hadRecentInput) metrics.cls += e.value
    })
```

规范规定：位移如果发生在用户输入后 500ms 内，属于「用户预期内的变化」（比如点了「展开」），不计入 CLS，由 `hadRecentInput` 标记。而无头环境里没有任何输入事件，`hadRecentInput` 却依然是 `true`，于是规范口径的 CLS 恒为 0。

处理办法是**两个值都留着**：`cls` 是规范口径（上报给监控、真实用户环境用这个），`clsRaw` 是所有位移之和（无头对照实验读这个）。这不是实验台的权宜之计，生产环境里同样需要——有些团队会把 `hadRecentInput` 的判定窗口放宽到 1s，不同口径的数据混在一张报表里就没法比了。

## 七、怎么量：工具与「现象 → 工具」排查表

采集代码解决「持续地量」，工具解决「这一次为什么」。选工具的标准只有一条：它替你做了什么决定。

### 7.1 选工具的标准：它替你做了什么决定

DevTools 里能看性能的面板至少有六个，它们不是「同一个东西的不同视图」，而是各自做了不同的取舍：

| 工具 | 它替你做掉的事 | 代价 | 适合回答 |
| --- | --- | --- | --- |
| Network 面板 / 瀑布图 | 把请求按时间排好、标注优先级与阻塞关系 | 只看得到「搬运」，看不到计算 | 时间花在哪个资源的等待上 |
| Performance 面板 | 采样主线程调用栈、生成火焰图 | 录制有开销、数据量大 | 主线程那 500ms 到底在跑什么函数 |
| Coverage 面板 | 统计每个文件「已用字节 / 总字节」 | 只给静态结论，不给运行时上下文 | 有多少下了没用的代码 |
| Memory 面板 | 堆快照、对比、分配时间线 | 快照会暂停页面、体量大 | 为什么越用越卡、什么东西没被回收 |
| Lighthouse | 跑完一整套审计并打分 | 环境是模拟的，且只代表这一次 | 这个页面的整体水位、有没有明显短板 |
| Performance API / 本仓 perf-lab | 把读数变成可对比、可进 CI 的数字 | 需要自己写采集与聚合 | 优化前后差多少、要不要卡进流水线 |

顺序很重要：**先用粗粒度工具定位阶段，再用细粒度工具定位函数**。反过来做，你会在火焰图里翻十分钟，最后发现是首屏图片 3MB。

### 7.2 瀑布图：先回答「时间花在哪个等待上」

瀑布图（Network 面板，或本仓的 `npm run waterfall`）把每个资源的**开始请求时刻**与**耗时**画成横条，横轴是时间。读图只看三件事：

1. **谁在最后**。结束得最晚的那个资源，通常就是关键渲染路径上的瓶颈。
2. **谁被挡住了**。某根条明显靠右才开始，说明它前面有阻塞（脚本挡解析、依赖没就绪）。
3. **有没有并行度**。同类资源挤在一起起跑说明并行调度正常；一个接一个排成楼梯，说明被串行化了。

本仓用 ASCII 把同一套数据画出来，好处是可以把两次实验的输出 diff 起来看：

> 摘自 `./code/perf-lab/scenarios/waterfall.mjs`（运行：`npm run waterfall`）

```js
/** 把 /slow?ms=250&kb=200&name=hero.svg 压成一眼能认的名字 */
function label(url) {
    const name = url.split('name=').pop()
    const delay = url.match(/ms=(\d+)/)
    return (delay ? `slow ${delay[1]}ms · ` : '') + name
}
```

画条的逻辑在输出模块里，只是把「起点除以总时长」映射成列号：

> 摘自 `./code/perf-lab/harness/table.mjs`

```js
/** 主线程时间线的 ASCII 近似：把每段任务的起止按比例画成横条 */
export function timeline(items, total, cols = 56) {
    const head = pad('0 ms', 24) + '+' + '-'.repeat(cols) + '+ ' + ms(total)
    const rows = items.map(it => {
        const from = Math.round((it.start / total) * cols)
        const to = Math.max(from + 1, Math.round(((it.start + it.duration) / total) * cols))
        return (
            pad(it.label, 24) +
            '|' +
            ' '.repeat(from) +
            '#'.repeat(to - from) +
            ' '.repeat(Math.max(0, cols - to)) +
            '| ' +
            ms(it.duration)
        )
    })
    return [head, ...rows].join('\n')
}
```

跑出来的效果（对照页是「轻量首屏」和「未治理首屏」，只差一个阻塞脚本和一张首屏大图）：

```
================================================================
资源瀑布 · 未治理首屏（横轴 0 → 4016 ms）
================================================================
0 ms                    +--------------------------------------------------------+ 4016 ms
/lab.js                 |     #                                                  | 24 ms
slow 50ms · vendor.js   |      ###############################                   | 2222 ms
slow 0ms · hero.svg     |                                     ####################| 1417 ms
/favicon.ico            |                                                         #| 2 ms
```

一眼能看出的三件事：`vendor.js` 一个人占了 2.2 秒；`hero.svg` 直到 2647ms 才开始请求（被 `vendor.js` 挡住了）；`favicon.ico` 在 4.1 秒才来。后面还有一张明细表，标了每个资源的发起方和传输字节：

```
| 资源                  | 发起方 | 开始    | 耗时    | 传输字节 |
|-----------------------|--------|---------|---------|----------|
| /lab.js               | script | 388 ms  | 24 ms   | 3.6 KB   |
| slow 50ms · vendor.js | script | 418 ms  | 2222 ms | 482.5 KB |
| slow 0ms · hero.svg   | img    | 2647 ms | 1417 ms | 300.5 KB |
| /favicon.ico          | other  | 4101 ms | 2 ms    | 309 B    |
```

**「发起方」这一列是排障时的关键**。同一个 URL 由 `script` 还是 `img` 发起，决定了它走不走关键渲染路径、优先级高不高、能不能被 `preload` 提前。

### 7.3 同一个脚本换三个位置，瀑布图会变三次

「脚本该放哪」是老问题，但瀑布图能把它变成可对比的数字。本仓做了三份只差一行的页面：head 同步、head defer、body 末尾，脚本本身都是同一个 200ms 的慢资源。

> 摘自 `./code/perf-lab/scenarios/block.mjs`（运行：`npm run block`）

```js
    const rows = await sweep('/block-naive.html', [
        { name: 'head 同步', page: '/block-naive.html' },
        { name: 'head defer', page: '/block-defer.html' },
        { name: 'body 末尾', page: '/block-bottom.html' }
    ])
```

```
| 放法       | FCP    | LCP    | DOMContentLoaded | load   |
|------------|--------|--------|------------------|--------|
| head 同步  | 608 ms | 608 ms | 592 ms           | 593 ms |
| head defer | 416 ms | 416 ms | 498 ms           | 498 ms |
| body 末尾  | 444 ms | 444 ms | 528 ms           | 529 ms |

[head 同步] FCP=608 ms LCP=608 ms
0 ms                    +--------------------------------------------------------+ 593 ms
slow ms=60&kb=8&name=si |                                 #######                | 80 ms
slow ms=200&kb=80&name= |                                 ####################   | 218 ms
/lab.js                 |                                 #                      | 16 ms
```

head 同步那一版的横条全部挤在右侧——解析必须先停下来等脚本下载并执行完（218ms），页面才有机会画第一帧，于是 FCP 被推到 608ms。defer 之后脚本不再挡解析，FCP 掉到 416ms（剩下的是 CSS 这个真正的 render-blocking 资源）。挪到 body 末尾同样能先画（444ms），但 `DOMContentLoaded` 仍要等脚本跑完。

**这三行数字的用途不是「记住结论」，而是建立「改动 → 读数变化」的映射**。以后在真实项目里看到 FCP 与 DCL 差 300ms，你会先想到「有个阻塞脚本」。

### 7.4 Coverage：有多少代码下了没用上

Coverage 面板（DevTools → More tools → Coverage）给每个文件标出「已用字节 / 总字节」，红色部分是执行期间从未被用到、可以砍掉的代码。

本仓把它做成可对照的实验：10 个特性、每个 5KB，但页面只用到其中 3 个。

> 摘自 `./code/perf-lab/pages/coverage.html`

```js
    // 收集本次会话发出的 JS 资源字节数（transferSize 是压缩后的真实值）
    function scriptBytes() {
        return performance
            .getEntriesByType('resource')
            .filter(e => e.initiatorType === 'script' || e.name.includes('/bundle') || e.name.includes('/feature'))
            .reduce((sum, e) => sum + (e.transferSize || 0), 0)
    }
```

> 摘自 `./code/perf-lab/scenarios/coverage.mjs`（运行：`npm run coverage`）

```js
    const rows = await sweep('/coverage.html', [
        { name: '整包引入', query: { mode: 'full' }, rounds: 3 },
        { name: '按需引入', query: { mode: 'split' }, rounds: 3 }
    ])
```

```
| 引入方式 | 请求的 chunk 数 | 实际拿到的特性 | JS 传输字节 | 加载耗时 |
|----------|-----------------|----------------|-------------|----------|
| 整包引入 | 1               | 3 / 3          | 52.6 KB     | 1 ms     |
| 按需引入 | 3               | 3 / 3          | 19.1 KB      | 1 ms     |
```

整包版一次下发 52.6KB，页面只用 19.1KB——**33.5KB 是纯粹的无效下载**。这就是 Coverage 面板上那块红色的价值。

三个层级的「按需」对应三种做法，从粗到细：

1. **入口级**：路由懒加载，把首屏不需要的整块页面切走（对照见 `npm run lazy`）
2. **模块级**：`import()` 写进函数体，配合 tree-shaking 摇掉没被引用的导出
3. **依赖级**：第三方库按需引入（组件库只引 `Button`），或直接换更小的替代（moment → dayjs）

### 7.5 Memory：为什么越用越卡

内存问题的现象（页面用久了变卡、切换几次路由后卡死）和原因（有东西没被回收）之间隔得很远，必须靠工具。核心招式只有一个：**对比两次堆快照**。

本仓把「泄漏」压缩成一个最小对照：同样分配 60 轮、每轮 2000 个对象、每个带 512 字节字符串，唯一区别是每轮的数组有没有被挂到全局。

> 摘自 `./code/perf-lab/pages/memory.html`

```js
    /** 分配 n 个对象，每个带 512 字节字符串，模拟真实业务里的数据缓存 */
    function alloc(n) {
        const arr = []
        for (let i = 0; i < n; i++) arr.push({ id: i, payload: 'x'.repeat(512) })
        return arr
    }
```

> 摘自 `./code/perf-lab/pages/memory.html`

```js
            const chunk = alloc(2000)
            if (KEEP) window.__leakedBags.push(chunk) // 留引用 → GC 收不走
            // chunk 在 clean 模式下出了作用域就没人引用，下一次分配压力上来时会被回收
            samples.push(heap())
```

要量出逐轮趋势，必须开 `--enable-precise-memory-info`，否则 `performance.memory` 的粒度是 100KB 级：

> 摘自 `./code/perf-lab/scenarios/memory.mjs`（运行：`npm run memory`）

```js
const FLAGS = ['--enable-precise-memory-info']
```

```
| 模式           | 第 10% 处堆 | 末轮堆  | 峰值堆  | 净增长  | 留下的引用 |
|----------------|-------------|---------|---------|---------|------------|
| 留引用（泄漏） | 3.2 MB      | 21.5 MB | 21.5 MB | 18.3 MB | 60         |
| 可回收（正常） | 2.4 MB      | 3.2 MB  | 4.8 MB  | 0.8 MB  | 0          |
```

同样的分配次数、同样的数据量，唯一的差别是「还有没有引用指向它」——留引用的一版净涨 18.3MB 且从不回落，可回收的一版在 3MB 附近波动。

对应到 DevTools 里的三个操作：

- **Heap snapshot + Comparison**：先拍一次 → 反复做要排查的动作 → 再拍一次 → 选 Comparison，看哪些对象 **Delta 只增不减**。这是定位泄漏最直接的路径。
- **Detached DOM**：在快照里筛 `Detached` 关键字，能看到「已经不在文档里、但被 JS 变量引用着」的节点。Vue / React 组件卸载后 DOM 还被闭包引用，就藏在这里。
- **Allocation instrumentation on timeline**：录一段操作，蓝条是新增分配、灰条是已回收。**全蓝说明没有回收**。这个视图最适合「不知道该怀疑谁」时的第一轮扫描。

### 7.6 把浏览器打开这件事自动化

上面几个工具都要人点。要在 CI 里卡口，就得让程序自己开浏览器、自己取数。本仓用 `child_process` 拉起本机 Chrome，页面把采集结果 POST 回实验台服务器——不需要 puppeteer，也不需要 CDP。

> 摘自 `./code/perf-lab/harness/chrome.mjs`

```js
export function findChrome() {
    for (const file of CANDIDATES) {
        if (!file.includes('/') && !file.includes('\\')) return file
        if (fs.existsSync(file)) return file
    }
    throw new Error('没找到 Chrome，可用环境变量 CHROME_PATH 指定可执行文件路径')
}
```

这套做法的边界要清楚：**它能拿到页面自己量出来的东西（指标、资源、长任务、堆大小），拿不到需要 CDP 的能力**（强制 GC、CPU 降速、网络节流面板、逐帧截图）。所以合理分工是：

- 需要**跨环境反复对比、卡进 CI** 的读数 → 用脚本（本仓 perf-lab / Lighthouse CI）
- 需要**看懂「为什么」**的深挖 → 人开 DevTools

### 7.7 Lighthouse：知道它替你做了什么，就知道它什么时候不可信

Lighthouse 是一键审计：模拟移动端 4G + 4 倍 CPU 降速跑一遍，输出性能 / 无障碍 / 最佳实践 / SEO 的评分和一串优化建议。

它的模型是**固定权重汇总**——把 LCP、TBT、CLS、SI、FCP 按权重算成一个 0~100 的分。这带来两个必须知道的特性：

- **分数是相对的**：同样的页面在不同版本的 Lighthouse 里分数可能差 10 分，因为权重和曲线调整过。所以只看「分数有没有变差」，别把 90 分当硬目标。
- **它只是「一次」**：分数代表这一次模拟，不代表你的用户分布。真实用户 p75 才是最终依据。

正确用法：**当作趋势与短板扫描**——上线前跑一次存档，之后定期跑，看分数和具体指标有没有劣化；同时在 Opportunities 里找「立即可改」的项。**别把它当验收卡口**，卡口应该用真实指标 + 性能预算（见「性能优化闭环」篇）。

### 7.8 从现象到工具：一张排查表

| 现象 | 先看 | 再看 |
| --- | --- | --- |
| 首屏白很久 | 瀑布图：最后一个资源是谁 | Performance 面板：FCP 前主线程在干什么 |
| 页面能看见但点不动 | TBT / longtask 条目 | Performance 面板火焰图找那个长任务 |
| 内容突然跳动 | CLS 位移条目（含 `hadRecentInput` 与来源元素） | 有没有图片缺尺寸、有没有晚插的元素 |
| 滚动卡顿 | Performance 面板的 Frames 轨 | 是不是每帧都在强制布局（连续 layout 记录） |
| 越用越卡 | Memory 快照 Comparison | Detached DOM、不断增长的数组 / Map |
| 下载量偏大 | Coverage 面板 | 路由 chunk 切分、tree-shaking 配置 |

## 八、优先级：RAIL 与「先改哪个」

指标告诉你「哪里差」，RAIL 告诉你「先改哪个」。核心思想一句话：**优化的目标是响应用户，不是响应设备**。

| 缩写 | 含义 | 预算 | 对应指标 |
| --- | --- | --- | --- |
| R（Response） | 响应输入 | < 100ms | INP |
| A（Animation） | 动画流畅 | 每帧 < 16ms（渲染预算 10ms） | 帧率 |
| I（Idle） | 利用空闲 | 主线程空闲块 > 50ms | 长任务 |
| L（Load） | 加载内容 | < 5s（理想 < 2.5s） | LCP / FCP / TTFB |

用法是把指标超标的程度折算成「用户会有什么感受」：INP 从 150ms 涨到 600ms，是「点一下卡半秒」级别的问题，优先级高于 LCP 从 2.4s 涨到 2.8s——后者用户基本察觉不到。

四个预算里，**A 的 16ms 最容易被人忽略也最容易验证**：一帧 16.7ms，如果某段逻辑要跑 30ms，就一定会掉帧。把这段逻辑拆到两帧（或挪进 Worker）就能救回来，具体见「交互性能与 INP」篇。
