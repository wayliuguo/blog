# 视觉稳定与 CLS

这一篇服务一个核心目标：**把 CLS 打下来**（p75 ≤ 0.1）。

CLS 是三个核心目标里最「便宜」的一个。它通常不是性能问题，而是**写法问题**——图片少写一个 `height`、横幅插错了位置、字体换了一下，位移就产生了。也因此它的投入产出比最高：绝大多数 CLS 只来自四类写法，改完就能归零，不需要重构、不需要换架构。

判定规则先记住，后面四节都是它的推论：**CLS 只看元素的起始位置有没有变化**。元素在布局里的位置没变，怎么动都不算位移。

本篇同样先定位——位移是哪个元素、在哪个时刻产生的——再按来源分类给修法。

## 一、先定位：位移来自哪个元素、发生在哪个时刻

一次位移的分数是：

```
单次位移分数 = 影响比例（位移前后占据视口区域的并集 / 视口面积）
            × 位移距离比例（移动的最大距离 / 视口高度）
```

CLS 是页面生命周期内所有单次分数之和。**目标值 ≤ 0.1。**

只盯着总分修是修不掉的，必须拿到**每一次**位移的时刻与来源元素。实验台把两个版本跑在一起，并把每次位移单独打出来：

> 摘自 `./code/perf-lab/scenarios/cls.mjs`（运行：`npm run cls`）

```js
    const rows = await sweep('/cls.html', [
        { name: '无预留', query: { mode: 'bad' }, rounds: 3 },
        { name: '有预留', query: { mode: 'good' }, rounds: 3 }
    ])
```

```
| 版本   | 位移合计 | 位移次数 | 评级 | FCP    | LCP    |
|--------|----------|----------|------|--------|--------|
| 无预留 | 0.300    | 2        | 差   | 336 ms | 740 ms |
| 有预留 | 0.000    | 0        | 良好 | 324 ms | 720 ms |
```

两次位移各自是什么，脚本会打出来：

```
---- 两次位移分别是什么 ----
[无预留] +0.0901 @730ms  +0.1922 @785ms
[有预留] 没有位移
```

`@730ms` 是图片：不给 `width` / `height`，浏览器先按 0 高排，图回来才知道要占 240px，下面的卡片整体下移。`@785ms` 是横幅：240px 高的元素插到了 `body` 最前面，整页内容被顶下去一次。

**「时刻」就是归因的钥匙**，按它就能定位到来源：

| 位移发生在 | 通常的来源 | 去哪一节 |
| --- | --- | --- |
| 首屏绘制后不久，时刻接近 LCP | 图片 / 媒体没写尺寸、字体换掉导致文字重排 | 二、三 |
| 某个接口返回之后 | 动态插入的横幅、公告、推荐位、广告 | 四 |
| 用户交互后 500ms 内 | 属于「预期位移」（`hadRecentInput`），**不计入 CLS** | 不用修 |
| 用户交互后 500ms 之外 | 骨架屏结构与真实内容不一致、懒加载填充时没尺寸 | 四 |
| 滚动或动画过程中持续累积 | 用会触发布局的属性做动画（改 `top` / `height`） | 五 |

> 上报口径上有个坑：`hadRecentInput` 的判定在无头/自动化环境里可能恒为 `true`，导致规范口径的 CLS 恒为 0。所以实验台同时留了 `cls`（规范口径，上报用）和 `clsRaw`（所有位移之和，对照实验读它）。详见「性能优化总纲与指标量化」篇。

## 二、尺寸与预留：图片、媒体与广告位

**这是 CLS 最大的单一来源**，也是最好修的：给媒体元素写死尺寸。

- **写 `width` / `height` 属性**（不是 CSS）。现代浏览器会用这两个值自动算出 `aspect-ratio`，在图还没下下来之前就把位置占住。用 CSS 的 `width: 100%; height: auto` 配合也行，关键是**属性要在 HTML 里**，不能等 JS 或等 CSS 加载。
- **响应式图片要保证各档比例一致**。`srcset` 换的是分辨率不是比例，如果不同 `src` 的宽高比不同，预留的位置仍然会错。
- **`iframe`、广告位、embed 同样要留位**。用 `min-height` 给一个保守的占位高度，内容来了再撑开——撑开是在容器内部发生，不会顶走下面的内容。
- **别指望 `loading="lazy"` 顺带解决位移**。它只管什么时候下，不管占不占位；尺寸没写，图一落地照样跳。

判断标准很简单：**在图片还没开始下载的时候，那个位置的高度就已经是对的了**。用 DevTools 把网络限速到 Slow 3G 刷新一次，看布局是不是从一开始就是最终形态。

## 三、字体：不可见期与换字重排

字体是第二个大来源，而且它有两个独立的坑：**不可见期**（文字不显示）和**换字重排**（文字位置变）。

默认行为 `font-display: auto` 在字体没到时会有最长 3 秒的不可见期——文字位置留着、但不显示，用户盯着空白看。四个取值：

| 取值 | 行为 | 适用 |
| --- | --- | --- |
| `block` | 最长 3s 不可见期，然后换字体 | 几乎不用 |
| `swap` | 立刻用回退字体显示，字体到了再换 | 正文首选（会有一次跳变） |
| `fallback` | 极短不可见期（~100ms），之后用回退字体直到字体到达 | 平衡选择 |
| `optional` | 视为可选，网络不好就不用了 | 首屏体验优先、CLS 优先 |

选了 `swap` 就必然面临第二个坑：**换字体的那一下，文字会重排**。回退字体和正式字体的度量（字宽、行高）差得越远，重排越厉害；如果这段文字上面还有别的内容，就变成一次实实在在的 CLS。

两条解法：

1. **让回退字体的度量接近正式字体**。用 `size-adjust`、`ascent-override`、`descent-override` 调整回退字体，让它和目标字体占差不多的空间。
2. **把字体 `preload` 掉**。字体是「关键路径上、但浏览器发现得晚」的典型资源，preload 能让它赶在首次绘制前到位，从根上避免换字。注意 `as="font"` 必须带 `crossorigin`，否则会因为证书模式不匹配被下载两次。

## 四、动态内容：晚到的横幅、列表与骨架屏

第三类来源不是「元素变了」，而是**新元素插到了已有内容的前面或中间**，把后面所有东西顶走。

- **给动态内容预留容器**。公告条、推荐位、广告、评论区，先渲染一个带 `min-height` 的占位容器，内容到了填进去。填充发生在容器内部，不产生位移。
- **绝不在已有内容「上方」插入元素**。上面实测里 `@785ms` 那次 0.1922 的位移，就是把 240px 的横幅插到了 `body` 最前面——整页被顶下去，影响比例接近 1，一次就超过了 0.1 的及格线。
- **骨架屏必须和真实内容结构一致**。骨架屏改善的是主观等待感，但它把一次「白屏→内容」变成两次「白屏→骨架→内容」。如果骨架的高度、行数、间距和真实内容对不上，填充时就是一次大位移。
- **懒加载的填充同样要有尺寸**。滚动到视口才加载的图片、无限滚动追加的列表项，规则和第二节一样：位置先占好。

一个反直觉的点：**这类问题在开发环境通常看不见**。本地接口几十毫秒就返回，内容几乎是同步出现的；上了生产网络一慢，位移就暴露了。所以排查时一定要限速复现。

## 五、动画与交互：transform 与 top 的区别

回到开头那条判定规则：**CLS 只看元素在布局里的起始位置有没有变化**。这一条直接决定了动画怎么写。

- **用 `transform: translate()` 做动画**：元素只是在视觉上被挪动，它在布局里的位置没变，**不产生 CLS**，而且只走合成、不触发布局与重绘。
- **改 `top` / `left` / `margin` / `height`**：元素在布局里的位置真的变了，会算进位移，同时触发整条渲染流水线。

所以动画要尽量只用 `transform` 和 `opacity`——这一条同时服务三个目标：不产生 CLS、不掉帧、不触发布局。

两个配套注意点：

- **别滥用 `will-change`**。它会为元素单独提升一个合成层，层数一多，内存和合成开销反而上升。只在确实要开始动画前加、动画结束就撤。
- **「展开 / 收起」这类真的要改变布局的动画做不到纯合成**。这时退而求其次：让变化发生在容器内部（容器高度固定、内容滚动），或者接受这次位移但确保它发生在用户交互后 500ms 内（`hadRecentInput` 会把它排除掉）。
