# 优化手段速查

这一篇是清单，不是教程。前面六篇讲「为什么」，这里只讲「做什么、值多少、什么时候别做」。每条手段后面挂的数字都是本仓实验台实测出来的（`code/perf-lab`），不是经验值。

## 一、怎么用这篇

三个用法：

1. **排障时反查**：手上有一个指标很差（比如 LCP 4s），先跳到对应章节看「哪几条手段管这个指标」。
2. **评审时对账**：方案里写了「做代码分割优化首屏」，来这里确认——代码分割改善的是「首屏可用时间」，总字节不变，如果目标是减小总体积，这条手段对不上。
3. **写报告时取数**：每个数字都标了跑哪条命令能复现，可以直接引。

对照实验的工具很轻——两套参数跑同一份逻辑，结果并排出表：

> 摘自 `./code/perf-lab/harness/index.mjs`

```js
export async function sweep(page, variants, options = {}) {
    const out = []
    for (const variant of variants) {
        const report = await measure(variant.page || page, { ...options, ...variant })
        out.push({ name: variant.name, report })
    }
    return out
}
```

## 二、加载与首屏

| 手段 | 改哪个指标 | 实测效果 | 什么时候别做 |
| --- | --- | --- | --- |
| 同步脚本加 `defer` | FCP / LCP | 608ms → 416ms（`npm run block`） | 有依赖顺序要求的脚本要用 `defer` 保序，别用 `async` |
| 首屏外图片 `loading="lazy"` | 传输字节 | 2.35MB → 1.57MB（`npm run images`） | 首屏那张图绝不能加；LCP 不会因此变好 |
| 路由级代码分割 | 首屏可用时间 | 2069ms → 767ms（`npm run lazy`） | 首屏路由与高频路由别拆；必须配 loading 兜底 |
| 关键 CSS 内联 | FCP | 省掉一次 render-blocking 请求 | 首屏样式清单要维护，页面一改就漏 |
| 首屏图 `fetchpriority="high"` | LCP | 比默认优先级更早开始下载 | 页面有多张大图时反而互相抢带宽 |
| `preconnect` 到 CDN 域 | TTFB | 省掉 DNS + TCP + TLS 往返 | 该域只用一两次请求时不划算 |
| 字体 `font-display: swap` + 度量接近的回退字体 | 首屏可见 / CLS | 消除最长 3s 的不可见期 | 回退字体度量差很远时，换字体那一下会变成 CLS |
| SSR / 流式渲染 | LCP / FCP | 把 LCP 元素从 JS 渲染改为 HTML 内容 | 页面强交互、首屏没内容可预渲染时收益低 |
| 骨架屏 | 主观等待感 | 指标不变，感知变好 | 骨架结构必须与真实内容一致，否则填充时又是一次大位移 |
| 并发请求调优 / HTTP/2 多路复用 | 瀑布图并行度 | 消除串行楼梯 | HTTP/1.1 下才需要域名分片，HTTP/2 下反而是倒退 |

## 三、资源与体积

| 手段 | 改哪个指标 | 实测效果 | 什么时候别做 |
| --- | --- | --- | --- |
| 按需引入（只 import 用到的） | JS 传输字节 | 52.6KB → 19.1KB（`npm run coverage`） | 需要组件库支持子路径导出，否则要配按需插件 |
| tree-shaking | 打包产物体积 | 摇掉未被引用的导出 | CJS 模块摇不动；有顶层副作用的库要标 `sideEffects` |
| 依赖替换（moment → dayjs 等） | 产物体积 | 常见 10 倍级差距 | 项目已大量使用原库 API 时，迁移成本可能超过收益 |
| gzip / brotli | 传输字节 | gzip 约 -70%，brotli 再 -15%~20% | 只对文本有效，图片/字体/视频压不动 |
| 图片格式（WebP / AVIF） | 图片字节 / LCP | 同画质比 JPEG 小 25%~50% | 需要确认目标浏览器支持，配 `<picture>` 兜底 |
| `srcset` + `sizes` | 移动端图片字节 | 避免给手机发桌面大图 | 图片尺寸种类过多时维护成本上升 |
| vendor 拆分 + 内容哈希 | 缓存命中率 | 只更新变动的那部分 | 拆得太碎会让请求数暴涨（HTTP/1.1 下很致命） |
| sourcemap 不上线 | 安全（不是性能） | 避免源码泄露 | 必须上传到监控平台供错误反解，否则线上报错还原不了 |
| 去掉 `console` / 调试代码 | 体积（小） | 通常几十 KB | 别把 `console.error` 删了，监控上报依赖它 |

## 四、运行时与渲染

| 手段 | 改哪个指标 | 实测效果 | 什么时候别做 |
| --- | --- | --- | --- |
| 读写分离（先集中读、再集中写） | 交互延迟 / 帧率 | 4794ms → 4ms（`npm run thrash`） | 读的值必须是最新布局时才不能缓存，这种情况本来就该重构 |
| 长任务切片（`MessageChannel` / `scheduler.postTask`） | INP / 最长阻塞 | 最长块 737ms → 144ms（`npm run longtask`） | 单个工作单元超长时切不动；`Promise.then` 做切片无效 |
| 虚拟滚动 | DOM 数 / 滚动帧率 / 内存 | DOM 10012 → 39，滚动 288ms → 13ms（`npm run virtual`） | 列表只有几十上百行时纯属自找复杂度 |
| 把重计算挪进 Worker | 交互延迟 / 帧率 | 最长帧间隔 200ms → 17ms（`npm run worker`） | 与 DOM 相关或单次不到 50ms 的计算不值得 |
| 动画只用 `transform` / `opacity` | 帧率 / CLS | 只走合成，不触发布局 | 需要真正改变布局尺寸的动画（如折叠展开）做不到 |
| 事件委托 / 减少监听器数量 | 内存 / 交互延迟 | 避免成千上万个监听器 | 需要精细 `stopPropagation` 控制的场景 |
| 滚动与 resize 用 `rAF` 合帧 / 节流 | 帧率 | 避免一帧触发多次重算 | 需要每一帧都精确响应的场景 |
| `IntersectionObserver` 替代 `scroll` 回调 | 帧率 | 浏览器批量派发，不在滚动回调里算 | 需要「滚动距离」这类连续量的场景 |
| CSS `contain` / `content-visibility` | 布局与绘制耗时 | 缩小重排重绘范围 | 兼容性要确认；`contain` 用错会导致布局异常 |
| 防抖 / 节流 + 竞态取消 | 交互延迟 / 正确性 | 避免重复请求与过期响应覆盖 | 需要实时搜索建议的场景要配 `AbortController` 取消 |

## 五、内存

| 手段 | 改哪个指标 | 实测效果 | 什么时候别做 |
| --- | --- | --- | --- |
| 组件卸载时摘事件监听 | 内存 | 留引用净涨 18.3MB vs 可回收 0.8MB（`npm run memory`） | 挂在 `window` / `document` 上的必须显式摘，框架不会自动帮你 |
| 清理定时器与定时任务 | 内存 | 同上 | `setInterval` 永远要配清理逻辑 |
| 全局缓存加上限（LRU） | 内存 | 避免长会话页面持续膨胀 | 缓存本身就要求「命中率优先」时要单独评估 |
| 避免闭包绑住大对象 | 内存 | 用不到的字段不要留在闭包里 | 语言层面没有强制手段，靠 code review |
| 大数据量用分页 / 流式处理 | 内存 + 交互延迟 | 避免一次性把几十万条塞进数组 | 需要全局统计（排序、聚合）时绕不开 |

## 六、闭环与监控

| 手段 | 作用 | 说明 |
| --- | --- | --- |
| 性能预算写进仓库 | 定义水位线 | 从现状出发 + 留余量 + 逐步收紧 |
| 卡口进 CI（非零退出码） | 拦住劣化 | 确定性指标卡死，统计性指标用多轮中位数 + 宽松阈值（`npm run budget`） |
| 看板带基线 | 一眼看出变差 | 每个指标画一条上个稳定版本的值 |
| 分位数而非平均值 | 看到真实分布 | Core Web Vitals 统一看 p75 |
| 劣化归因到提交 | 知道「哪次改的」 | 发布记录对时间点，缺这一环就只能停留在「变差了」 |
| 灰度放量对比 | 验证真的变好 | 5% → 20% → 50% → 100%，对比新旧版本分位数 |
| 上报自身也有预算 | 控制监控成本 | SDK 体积与上报频率都要设上限 |

## 七、反面清单：这些「优化」经常没用

比「该做什么」更容易踩的是「做了但没用」。下面是实测能证伪的几条：

- **用 Promise 做长任务切片**。微任务队列会在当前宏任务结束前全部跑完，浏览器一帧都插不进来。切片必须用宏任务（`MessageChannel` / `postTask`）。
- **给首屏图片加 `loading="lazy"`**。它把图片降到 Low 优先级，LCP 直接变差。
- **无脑 `preload`**。给不在关键路径上的资源加高优先级，会抢走真正首屏资源的带宽，LCP 反而更差。
- **动态 `appendChild` 一个 script 来演示「阻塞」**。动态插入的 script 默认 `async`，不阻塞解析——想演示阻塞必须写进 HTML。
- **把 `preconnect` 加给所有第三方域**。每个 `preconnect` 都要建立并维持一条连接，加多了反而挤占首屏连接数。
- **只看 Lighthouse 总分**。它是固定权重汇总，权重随版本变；分数没动不代表指标没动。
- **在无头/本地环境直接比「谁更快」**。localhost 传 500KB 只要几毫秒，两个版本读数完全一样——必须限速。本仓的 `kbps` 参数就是干这个的。
- **拿单次测量下结论**。宿主机负载、冷启动都会影响读数，至少 3 轮取中位数。
- **虚拟滚动了却没优化单行渲染**。虚拟滚动减少的是 DOM 数量，不是计算量；每行的格式化逻辑照样在跑。
- **用平均值汇报性能**。长尾分布下平均值会被少数极快样本带偏，p75 / p95 才是用户真实体感。

## 小结

- 优化手段速查
  - 用法
    - 排障反查（哪个指标差 → 对应手段）
    - 评审对账（手段改善的指标是否等于目标指标）
    - 报告取数（每条都有可复现的命令）
  - 加载与首屏
    - `defer`（608→416ms FCP）、图片懒加载（2.35→1.57MB，LCP 不变）、路由分割（2069→767ms）
    - 关键 CSS 内联、`fetchpriority`、`preconnect`、字体 `swap`
    - SSR / 流式 / 骨架屏：改变的是「内容什么时候出现」，不是总时间
  - 资源与体积
    - 按需引入（52.6→19.1KB）、tree-shaking、依赖替换、gzip/brotli
    - 图片格式与 `srcset`、vendor 拆分与内容哈希、sourcemap 不上线
  - 运行时与渲染
    - 读写分离（4794→4ms）、长任务切片（737→144ms 最长块）、虚拟滚动（DOM 10012→39）
    - Worker（帧间隔 200→17ms）、合成层动画、事件委托、`IntersectionObserver`
  - 内存
    - 摘监听、清定时器、缓存加上限、避免闭包绑大对象
    - 实测：留引用净涨 18.3MB vs 可回收 0.8MB
  - 闭环
    - 预算进仓库、卡口进 CI、看板带基线、分位数而非平均值、归因到提交、灰度对比
  - 反面清单
    - Promise 切片无效、首屏图别 lazy、无脑 preload 有害、动态 appendChild 不阻塞
    - 空 localhost 不限速比不出差别、单次测量不可信、别只看 Lighthouse 总分
    - 虚拟滚动不减少计算量、别用平均值汇报
