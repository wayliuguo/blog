# 模块面试题 · 性能优化

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../面试方法论.md)的四步答题法——结论/原理/边界/追问。
> 题目来源：由本模块各篇正文整理，每题在标题后标注出处（第 N 篇）。本模块所有数字都可在 `code/perf-lab` 里用对应命令复现。

## 一、基础概念

### Q1: 前端性能指标有哪些？分别衡量什么？（第 1 篇）

- **结论**：Core Web Vitals 三个——LCP（加载）、INP（交互）、CLS（视觉稳定）；辅助指标沿时间轴排布——TTFB → FP → FCP → LCP → TTI，另有 TBT 与 SI。
- **原理**：LCP 是视口内最大内容元素的渲染完成时刻，由 TTFB + 资源加载延迟 + 加载时长 + 元素渲染延迟四段构成；INP 是全程代表性交互到下次绘制；CLS = 影响比例 × 位移距离比例的累积。
- **边界**：TTFB 是加载指标的上限，上游差时优化下游无效；LCP 不保证早于 TTI（首屏大图会拖后 LCP）。
- **追问**：FCP 和 LCP 什么时候会差很多？→ 首屏有大量文本先画出来（FCP 早），但最大内容是一张大图（LCP 晚）。

### Q2: LCP 由哪几段构成？优化时按什么顺序找瓶颈？（第 1 篇）

- **结论**：TTFB → 资源加载延迟 → 资源加载时长 → 元素渲染延迟，四段依次排查。
- **原理**：先看 TTFB 是否健康（>500ms 先修服务端与缓存）；再看资源发现得够不够早（优先级、preload）；再看体积；最后看主线程是否忙到没法渲染。
- **边界**：实测里"未治理首屏"TTFB 只有 160ms、LCP 却 4024ms，问题全在资源侧——先优化服务端毫无收益。
- **追问**：怎么快速判断卡在哪一段？→ 瀑布图看最后一个资源什么时候结束；若资源早已到而 LCP 仍晚，去火焰图看主线程。

### Q3: CLS 的计算方式是什么？怎么优化？（第 1 篇）

- **结论**：单次位移分数 = 影响比例 × 位移距离比例，CLS 是累积值；目标 ≤0.1。优化两条：给图片写死尺寸、给晚到的动态内容预留空间。
- **原理**：影响比例是不稳定元素位移前后占据的视口区域并集占视口面积的比例；位移距离比例是移动距离除以视口高度。判定看元素的**起始位置**是否变化。
- **边界**：`transform` 做动画不产生 CLS（布局位置没变），改 `top`/`margin` 会；规范口径会剔除用户输入后 500ms 内的位移（`hadRecentInput`）。
- **追问**：无头环境里 CLS 恒为 0 是怎么回事？→ 没有真实输入事件，`hadRecentInput` 却仍为 true，规范口径把全部位移都剔掉了；对照实验要另记"所有位移之和"。

### Q4: `performance.now()` 与 `Date.now()` 的区别？（第 1 篇）

- **结论**：`performance.now()` 是相对导航开始的高精度单调时间戳（微秒级），`Date.now()` 是系统时钟（毫秒、可被系统时间调整影响）。
- **原理**：前者由浏览器单调时钟提供，不受系统时间校准、时区变化影响，适合测耗时；后者适合取"真实世界时间"。
- **边界**：跨页面/跨会话比较耗时不能用 `performance.now()`（各页面的零点是各自的导航开始）。
- **追问**：`performance.timeOrigin` 是什么？→ 导航开始的绝对时间戳，`timeOrigin + now()` 可还原绝对时刻。

### Q5: 实验室数据（Lab）与现场数据（Field/RUM）怎么分工？（第 1 篇）

- **结论**：现场发现问题，实验室定位根因，改完回现场验证。
- **原理**：Lab 在受控环境跑一次，可复现、能看火焰图，但不代表用户分布；RUM 采集真实用户，反映真实网络与设备，但噪声大、看不出根因。
- **边界**：看 RUM 必须看**分位数**（Core Web Vitals 统一 p75），平均值会被长尾带偏；样本要按用户维度稳定采样，否则分位数失真。
- **追问**：线上 p75 LCP 4.2s，实验室跑出来只有 1.2s，怎么解释？→ 真实用户里有低端机与弱网，实验室环境太优；应在实验室开 CPU 降速 + 网络节流复现，或按机型/网络维度切分现场数据。

### Q6: RAIL 模型的四个预算是什么？用它做什么？（第 1 篇）

- **结论**：Response <100ms、Animation <16ms/帧、Idle 空闲块 >50ms、Load <5s；用它把"指标超标"折算成"用户感受"，决定先改哪个。
- **原理**：它以用户为中心，认为优化的目标是响应用户而不是响应设备。把 INP 从 150ms 涨到 600ms（"点一下卡半秒"）的优先级排在 LCP 从 2.4s 涨到 2.8s 之前。
- **边界**：A 的 16ms 最容易被忽略也最容易验证——一帧 16.7ms，某段逻辑跑 30ms 就必然掉帧。
- **追问**：怎么把 30ms 的逻辑塞进一帧？→ 拆到两帧、或挪进 Web Worker（见第 5 篇）。

## 二、机制与原理

### Q7: 为什么长任务会让 INP 变差？（第 5 篇）

- **结论**：浏览器只有在一个任务结束后才能处理输入，所以一个 300ms 的长任务会把期间所有点击推迟到 300ms 之后。
- **原理**：主线程要同时负责 JS 执行、样式计算、布局、绘制与输入响应，任务之间是串行的；超过 50ms 的任务被标记为长任务，是被观测与卡口的主要对象。
- **边界**：实验室里用 TBT 代理 INP（TBT = 长任务超出 50ms 的部分之和），但 TBT 无法覆盖交互时才暴露的问题。
- **追问**：实测 60000 行列表一次渲染，最长同步块 737ms，怎么改？→ 切成 10 片用 `MessageChannel` 让出，最长块降到 144ms、首屏可见从 737ms 降到 162ms。

### Q8: 为什么用 Promise 做长任务切片是无效的？（第 5 篇）

- **结论**：微任务队列会在当前宏任务结束前全部跑完，浏览器一帧都插不进来。
- **原理**：渲染机会出现在宏任务与宏任务之间。`Promise.then` 的回调是微任务，会在当前任务收尾时被连续执行完；`MessageChannel`、`setTimeout`、`scheduler.postTask` 的回调是宏任务，能让浏览器在中间插入样式计算与绘制。
- **边界**：`setTimeout(fn, 0)` 有约 4ms 节流，时间粒度差；`requestIdleCallback` 可能长时间不被调用，不适合"尽快出首屏"。
- **追问**：切片会让总耗时变长吗？→ 会。实测 737ms → 1152ms，多出来的 415ms 是每次结算布局的固定开销；换的是"最长卡顿"和"首屏可见"。

### Q9: 什么是强制同步布局？为什么能慢一千倍？（第 5 篇）

- **结论**：写样式后立刻读依赖布局的属性（`offsetWidth`、`getBoundingClientRect`、`getComputedStyle`），逼浏览器当场重算布局。
- **原理**：浏览器默认攒批——样式改动记下来，等这轮 JS 跑完统一算一次布局。但读操作要求"读值是正确的"，所以必须先把刚才的改动算进去，攒批机制被打破。
- **边界**：实测 2000 个盒子：交错读写 4794ms / 2000 次布局，集中读写 4ms / 1 次（1115 倍）。解法：读提前写后置、用缓存代替读、批量写延到下一帧。
- **追问**：滚动事件里最容易踩哪个坑？→ `scroll` 回调里既读 `scrollTop` 又改样式，每个回调都制造一对读写。要用 `rAF` 合帧或 `IntersectionObserver`。

### Q10: 哪些属性能避免重排？合成层是什么？（第 5 篇）

- **结论**：改 `transform` / `opacity` / `filter` 只触发合成，不触发布局与重绘；几何属性（`width`/`margin`/`font-size`）触发布局最贵。
- **原理**：渲染分几步——布局（算位置尺寸）→ 绘制（填像素）→ 合成（合成层叠加到屏幕）。只改合成属性时，前两步的产物可以复用，工作在 GPU 上完成。
- **边界**：`will-change` 会为元素单独提升合成层，滥用反而让内存与合成开销上升；只在动画前加、动画结束撤掉。
- **追问**：为什么 `transform` 动画不产生 CLS？→ 位移判定看元素在布局中的起始位置，`transform` 不改变布局位置。

### Q11: 虚拟滚动的原理与代价是什么？（第 5 篇）

- **结论**：只渲染可视窗口 + 缓冲区，用一根撑高的占位元素模拟完整滚动高度；实测 DOM 从 10012 降到 39 个节点，大跨度滚动从 288ms 降到 13ms。
- **原理**：`scrollTop / 行高` 算出窗口起始行，渲染 `[start - buffer, start + window + buffer)` 区间的行，用 `top` 偏移把它们放到正确位置。
- **边界**：代价有三——每次滚动都要重算窗口并重建那几十行（要做合帧）、不定高列表的滚动锚定问题（需要锚点或双套高度数据）、**它不减少计算量**（每行的格式化照样跑）。
- **追问**：列表只有 100 行还需要虚拟滚动吗？→ 不需要。DOM 节点数本身不是瓶颈，引入的复杂度反而是负担。

### Q12: Web Worker 能解决什么问题？边界在哪？（第 5 篇）

- **结论**：把与 DOM 无关的重计算挪出主线程；实测同一段 1200 万次循环，主线程版最长帧间隔 200ms、期间 19 帧，Worker 版 17ms、32 帧。
- **原理**：计算本身没有变快（189ms vs 191ms），变的是"谁被占用"——主线程空出来后可以照常响应输入与出帧。
- **边界**：`postMessage` 走结构化克隆（拷贝有成本，适合传输入参数与结果，不适合高频传大块数据）；Worker 里没有 DOM；创建与首次加载有开销，适合"一次重活"。
- **追问**：什么计算值得挪？→ 与 DOM 无关且单次超过 50ms：数据处理聚合、加解密、图片像素运算、压缩解压、文本解析、diff 计算。

### Q13: tree-shaking 的前提是什么？为什么有时摇不掉？（第 4 篇）

- **结论**：三个前提——ESM 静态结构、模块无副作用（`sideEffects: false`）、访问方式静态。
- **原理**：打包器要在不执行代码的前提下判断某个导出有没有被引用。CJS 的 `require` 是运行时求值，无法静态判断，只能整块保留；有顶层副作用的模块不敢删；`import * as pkg` 后动态取值也摇不掉。
- **边界**：**tree-shaking 只作用在"没被引用的导出"，不作用在"没执行到的分支"**——`if (false) { heavy() }` 里的代码照样打进去。
- **追问**：怎么确认按需引入真的生效了？→ 逐 chunk 的 gzip 体积 diff，加 DevTools Coverage 复核红色区域有没有变小。

### Q14: 代码分割优化的是什么？为什么说它不是体积优化？（第 4 篇）

- **结论**：它优化的是**下载时序**不是总量。实测 3 个路由 ×120KB（1.5 Mbps 限速）：首屏全量 2069ms、总字节 347.6KB；按需加载 767ms、总字节 348.2KB。
- **原理**：动态 `import()` 把非首屏的代码切成独立 chunk，首屏只带当前路由的，其余等真正访问时再下。最终都访问了三个路由，总量自然一样。
- **边界**：首屏路由与高频路由不该懒加载（等于给用户加一次等待）；懒加载必须配 loading 兜底；拆得太碎会让请求数暴涨。
- **追问**：如果目标是"减小总体积"，该做什么？→ tree-shaking、按需引入、依赖替换、压缩（见第 4 篇）。

### Q15: 图片 `loading="lazy"` 到底省了多少？它改善 LCP 吗？（第 3 篇）

- **结论**：省的是首屏之外的传输量——实测 12 张 200KB 的图，全 eager 2.35MB vs 首屏外 lazy 1.57MB（省 33%）；**LCP 完全不变**。
- **原理**：`loading="lazy"` 有约 1250px 的预加载距离，视口附近的图仍会请求，所以不是"一张都不多下"；真正的收益是远离首屏的图不来抢带宽。LCP 元素是第一屏那张，两种策略都要下它。
- **边界**：给 LCP 图片加 lazy 会把它降到 Low 优先级，LCP 直接变差；首屏大图应该配 `fetchpriority="high"`。
- **追问**：那首屏要怎么优化？→ 关键渲染路径（脚本 defer、关键 CSS 内联）、资源优先级（preconnect / preload）、压缩与格式（WebP/AVIF、srcset）。

## 三、排障与选型

### Q16: 首屏 LCP 很差，怎么一步步定位？（第 2、3 篇）

- **结论**：按 TTFB → 资源瀑布 → 主线程三段排查，工具依次是瀑布图、Performance 面板、Coverage。
- **原理**：① 看 TTFB 是否 >500ms（服务端/CDN/缓存）；② 瀑布图看最后一个资源是谁、哪个资源被挡住了（阻塞脚本、CSS）；③ 资源都到位但 LCP 仍晚，用火焰图看主线程那段在跑什么。
- **边界**：本机 localhost 不限速时两个版本读数一样，结论不可信——必须限速（实验台的 `kbps` 参数）或多轮取中位数。
- **追问**：实测「未治理首屏」FCP 2600ms / LCP 4024ms / TTFB 160ms，你判断瓶颈在哪？→ TTFB 正常，问题在资源：一个 500KB 的 parser 阻塞脚本占 2.2s，首屏大图被它挡到 2647ms 才开始请求。

### Q17: 页面"能看见但点不动"，从哪查？（第 1、5 篇）

- **结论**：查长任务与 TBT，再用火焰图定位那个长任务。
- **原理**：TBT 大而 LCP 小就是典型信号——内容已经渲染出来（LCP 早），但主线程被长任务占住，输入排在队列后面（INP 差）。
- **边界**：TBT 只覆盖 FCP→TTI 这段，交互时才暴露的长任务要靠现场 INP 数据。
- **追问**：定位到长任务后怎么改？→ 切片（`MessageChannel`/`postTask`）、挪进 Worker、读写分离消除强制布局、减少不必要的计算。

### Q18: 页面滚动卡顿，怎么区分是"布局问题"还是"计算问题"？（第 5 篇）

- **结论**：看 Performance 面板里连续出现的 Layout / Recalculate Style 记录——频繁强制布局就是读写交错；如果是一段长 JS，就是计算太重。
- **原理**：布局问题的特征是"每帧都有 Layout 且耗时随 DOM 规模增长"；计算问题的特征是火焰图里同一个函数反复占满帧。
- **边界**：长列表两者常常同时存在——即便虚拟滚动了，每行的复杂格式化仍然要算。
- **追问**：可以怎么改？→ 布局问题做读写分离 + 缓存读值；计算问题做切片、Worker、或降级渲染（分页/骨架）。

### Q19: 页面越用越卡，怎么排查内存泄漏？（第 2、5 篇）

- **结论**：对比两次堆快照，看哪些对象 Delta 只增不减；用 Detached DOM 筛"不在文档里但被引用"的节点。
- **原理**：实测同样分配 60 轮 × 2000 个对象，留引用（挂在全局）净涨 18.3MB、从不回落；可回收版只在 3MB 附近波动（净涨 0.8MB）——差别只在"还有没有引用指向它"。
- **边界**：`performance.memory` 需要 `--enable-precise-memory-info` 才有足够精度；堆快照本身会暂停页面，别在快照期间做操作。
- **追问**：前端最常见哪几类泄漏？→ 事件监听没摘、定时器没清、只增不减的全局缓存、闭包把大对象绑在长生命周期上。

## 四、场景设计题

### Q20: 场景：你要给一个已有项目上线性能预算卡口，怎么设计？（第 6 篇）

- **结论**：预算从现状出发、分级、只卡用户能感知的指标；CI 里确定性指标卡死、统计性指标留余量；劣化要能归因到提交。
- **原理**：① 先量现状作基线（哪怕很烂），预算定"现状 + 一点余量"；② 分级——首屏路由严（LCP ≤2.5s、JS ≤200KB），次要页面松；③ 只卡 LCP/FCP/TTFB/TBT、CLS、首屏 JS 体积、请求数、长任务数；④ 卡口用退出码（超线 `exit 1`），确定性指标（体积/chunk 数）卡死，统计性指标用多轮中位数 + 约 20% 余量；⑤ 看板画基线、发布记录对时间点做归因。
- **边界**：别把 Lighthouse 总分当卡口（固定权重随版本变）；一上来就定理想值会让所有人超线、卡口被关掉，然后不了了之。
- **追问**：实测里 JS 字节 467.9KB 超 300KB 预算怎么处理？→ 要么优化到预算内（按需引入、tree-shaking、依赖替换），要么确认基线不合理、把预算调到一个"当前不许更差"的值，然后逐步收紧。

### Q21: 场景：一个长列表页面滚动卡顿、首屏也慢，你按什么顺序优化？（第 3、5、6 篇）

- **结论**：先量（瀑布图 + 火焰图）定出主瓶颈，再按"加载 → 运行时 → 构建"的顺序改，每改一步都要有前后对比。
- **原理**：① 先用 `npm run metrics` 类的方式量 FCP/LCP/TBT；② 若首屏慢在资源，先做关键渲染路径（脚本 defer、关键 CSS 内联、图片尺寸与格式）；③ 若滚动卡顿在 DOM 规模，做虚拟滚动（实测 DOM 10012→39、滚动 288→13ms）；④ 若卡在单行计算，做切片或 Worker；⑤ 最后收紧预算并接进 CI。
- **边界**：虚拟滚动会引入滚动锚定与窗口重算复杂度，列表只有上百行时得不偿失；切片会让总耗时变长，但能救回交互。
- **追问**：优化完怎么证明有效？→ 前后对比表写清"手段 / 指标变化 / 代价 / 边界"，并在灰度里对比新旧版本 p75 与 p95。
