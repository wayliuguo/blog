> 精简核心版：按篇分组、抽出高频/重要的知识点——成员丰富的主题展开明细，要点型知识点列清单、点到为止。选点按「面试命中度 / 日常复用度」等维度（见[文档组织规范](../../../文档组织规范.md)）。详细知识树见[《模块总结 · 性能优化》](./总结.md)。

## 知识主线（一句话）

主轴是**「指标驱动的优化闭环」**：01 定下标尺（LCP / INP / CLS 与 TTFB / FCP / TBT），02 把标尺变成可复现的读数，03~05 分别沿加载、构建、运行时三条线做优化（每个手段锚在一个实测数字上），06 把「变好」升级为「不再变差」（预算 + CI 卡口 + 灰度回归），07 / 08 把全部手段收成可检索清单并落到真实 SPA。

## 高频核心点

### 01 性能指标与评估

**Core Web Vitals**

- **LCP**：视口内最大内容元素渲染完成，≤2.5s，由 TTFB + 资源加载延迟 + 加载时长 + 渲染延迟构成
- **INP**：代表性交互到下次绘制，≤200ms（取代 FID），根因几乎总是长任务
- **CLS**：影响比例 × 位移距离比例累积，≤0.1；`transform` 不产生位移
- **TI**：交互到下一帧——时间轴 TTFB → FP → FCP → LCP → TTI/INP，上游决定下游

**辅助指标与口径**

- **TTFB** ≤800ms 是所有加载指标的上限；FP/FCP 差距大说明先铺了背景色
- **Lab vs Field**：现场发现问题、实验室定位根因；统一看 p75，平均值被长尾带偏
- **`buffered: true`** 才能拿到注册前的条目；累积指标等 `visibilitychange` 进隐藏态再报
- **RAIL**：响应 <100ms · 动画 <16ms/帧 · 空闲块 >50ms · 加载 <5s

### 02 性能测量工具实操

- **瀑布图**：只看三件事——谁最后结束、谁被挡住、有无并行度；"发起方"列决定资源走不走关键路径
- **火焰图**：采样主线程调用栈，定位"那 500ms 在跑什么函数"；录制有开销，别边录边改
- **Coverage**：已用 / 总字节，红色是不可用部分（实测整包 52.6KB vs 按需 19.1KB）
- **内存**：对比两次堆快照的 Delta，只增不减即泄漏；Detached DOM 找被 JS 引用但不在文档的节点
- **Lighthouse 是固定权重汇总**，版本间不可直接比；跨环境与 CI 卡口交给脚本、深挖"为什么"交给人

### 03 加载与首屏优化

- **三段定位**：等（TTFB：CDN / 缓存 / 服务端时间）、下（资源：减量降体积调优先级）、画（解析渲染：关键 CSS、避免长任务与同步布局）
- **三类阻塞**：同步 `<script>` 阻塞解析、`<link rel=stylesheet>` 阻塞渲染、`<img>`/字体推迟 LCP；动态 `appendChild` 的 script 默认 async 不阻塞
- **四个提前指令**：`preconnect` 建连接 · `dns-prefetch` 只解析 · `preload` 单个高优先级 · `prefetch` 空闲预取；`as="font"` 必须配 `crossorigin`
- **图片**：写死尺寸 / `aspect-ratio` 免位移；首屏外 `loading="lazy"`（实测 12 张全 eager 2.35MB vs lazy 1.57MB）；**LCP 元素不能加 lazy**
- **改变感受非时间**：SSR/SSG 内容提前但 TTFB 升、骨架屏结构先出、流式渲染首字节极早、预取只对高概率小体积目标

### 04 构建侧优化

- **代码分割**：优化的是时序不是体积（1.5Mbps 下全量 2069ms vs 按需 767ms，总字节几乎相同）；首屏与高频路由不该懒加载
- **tree-shaking**：三前提——ESM 静态结构、无副作用、静态访问；CJS 无法静态分析只能整块保留；只摇"没被引用的导出"
- **按需引入**三个层级：入口级（路由懒加载）、模块级（动态 import + sideEffects）、依赖级（子路径 / moment→dayjs）
- **压缩与产物**：gzip 必开（约 -70%），brotli 再小 15%~20%；生产不部署 sourcemap（传监控平台）；vendor 拆分 + 内容哈希提升缓存命中

### 05 运行时性能

- **两个标尺**：单帧 16ms、长任务 50ms（期间用户输入无法处理，INP 恶化的直接原因）
- **强制同步布局**：写后立刻读 `offsetWidth` 逼浏览器重算（实测交错读写 4794ms vs 集中 4ms，**1115 倍**）；解法是读提前写后置、用缓存、批量写延下帧
- **长任务切片**：让出机制 `MessageChannel` 首选、`scheduler.postTask` 现代最佳、**`Promise.then` 无效**；只能切独立工作单元
- **重排/重绘/合成**：几何→布局、绘制→重绘、`transform`/`opacity`→只合成；动画只用后两者，`will-change` 别滥用
- **虚拟滚动**：解决"DOM 太多"不解决"计算太重"；用 `IntersectionObserver` 而非 scroll 回调；代价是不定高滚动锚定
- **Worker**：计算没变快、变的是谁被占用；判断标准 = 与 DOM 无关 + 单次超 50ms
- **四类泄漏**：事件监听没摘、定时器没清、只增不减的全局缓存、闭包绑大对象

### 06 性能优化闭环

- **闭环四环节**：定基线 → 定预算 → 卡卡口 → 回归验证；最容易跳过的是定基线与回归验证
- **性能预算**：从现状出发、留余量、每轮收紧；别把 Lighthouse 总分当卡口（固定权重随版本变）
- **CI 卡口与预算的差别是"退出码"**：确定性指标（体积/请求数）卡死；统计性指标（LCP/FCP/TBT）用多轮中位数 + 宽松阈值，只拦断崖式劣化
- **四案例**：脚本 defer（FCP 608→416ms）· 图片 lazy（2.35→1.57MB，LCP 不变）· 虚拟滚动（DOM 10012→39）· 路由按需加载（首屏 2069→767ms）
- **回归验证**：灰度放量 + 对比分位数（p75/p95）而非平均值；看 p95 而非均值、把劣化归因到提交

### 07 优化手段速查

- **加载与首屏**：defer（608→416ms）· 图片 lazy · 路由分割 · 关键 CSS 内联 · `fetchpriority` · `preconnect` · 字体 swap · SSR/流式/骨架
- **资源体积**：按需引入 · tree-shaking · gzip/brotli · 图片格式与 srcset · vendor 拆分与内容哈希 · sourcemap 不上线
- **运行时渲染**：读写分离（4794→4ms）· 长任务切片（737→144ms）· 虚拟滚动（DOM 10012→39）· Worker · 合成层动画 · 事件委托 · IntersectionObserver
- **内存**：摘监听 · 清定时器 · 缓存加上限 · 避免闭包绑大对象
- **反面清单**：Promise 切片无效 · 首屏图别 lazy · 无脑 preload 有害 · 动态 appendChild 不阻塞 · 别只看 Lighthouse 总分 · 别用平均值汇报性能

### 08 Vue SPA 性能实战

- **每手段独立开关**，否则无法归因；先补关键 CSS 内联 + 骨架屏（FCP 508→224ms）
- **陷阱**：LCP 落在骨架屏上——指标变绿但用户没看到内容，须配「内容就绪」自定义指标；路由分割省业务代码不省体积
- **切路由**：全量 69ms / 分割不预取 245ms / 分割+空闲预取 80ms——预取必须成对做
- **滚动**：逐行读写 3985ms → rAF 读写分离 1007ms；改法是读写分离不是"少滚几次"
- **ROI 顺序**：长期缓存 > 虚拟滚动 > 关键 CSS 内联 > 分割+预取 > 计算分片 > SW
