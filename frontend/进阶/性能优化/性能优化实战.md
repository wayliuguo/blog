# 性能优化实战

## 一、两个完全独立的项目

**`code/perf-lab` 下是两个互不共享源码的 vite + vue 生产工程：`apps/before` 优化前，`apps/after` 优化后。** 两个都是真实项目的形态：单入口 `index.html`、`vue-router`（hash 模式）管路由、样式走依赖图、`vite build` 出产物、`vite preview` 看打包后的页面。每一层（加载层 LCP / 运行层 INP / 视觉层 CLS）的优化都落在**源码写法与构建配置**上——before 用未优化的写法，after 用优化后的写法；没有共享源码、没有别名、没有总开关、没有 `?act=` 实验驱动。想看某一层的差异：**把两个项目都构建出来，打开对应页面对照**。

```
perf-lab/
├─ package.json        根：npm workspaces（apps/*）+ 全部 scripts
├─ apps/
│  ├─ before/          优化前项目（自包含）：index.html + memory.html* + src/ + public/
│  └─ after/           优化后项目（自包含）：index.html + memory.html* + src/ + public/
├─ dist-before/        构建产物（gitignore）
└─ dist-after/         构建产物（gitignore）

* `memory.html` 是 4.4 的内存对照实验页（第二个构建入口），不属于生产形态，见 3.2 产物清单下的说明。
```

「优化后」项目的构建配置长这样——与标准工程唯一的区别就是那个构建插件（把注入产物的 CSS `<link>` 改写成异步）：

> 摘自 `./code/perf-lab/apps/after/vite.config.mjs`（运行：`npm run build`）

```js
/**
 * 构建期优化插件：把 vite 注入产物 html 的 <link rel="stylesheet"> 改写成异步加载。
 * 原理：media="print" 的样式表匹配媒体查询失败，浏览器只下载不应用、不阻塞渲染；
 * onload 里改回 media="all" 生效；preload 提高下载优先级，noscript 兜底无 JS 场景。
 * 首屏要的样式已经内联在 index.html 的 <style> 里（关键 CSS），所以异步期间骨架屏不是裸的。
 * 对应 before 项目：那边没有这个插件，构建出的 <link rel="stylesheet"> 原样阻塞首屏。
 */
function htmlAsyncCss() {
    return {
        name: 'lab-html-async-css',
        enforce: 'post',
        apply: 'build',
        generateBundle(_, bundle) {
            for (const file of Object.values(bundle)) {
                if (file.type === 'asset' && file.fileName.endsWith('.html')) {
                    file.source = String(file.source).replace(
                        /<link rel="stylesheet"([^>]*href="[^"]+"[^>]*)>/g,
                        (m, attrs) =>
                            `<link rel="preload" as="style"${attrs}>` +
                            `<link rel="stylesheet"${attrs} media="print" onload="this.media='all'">` +
                            `<noscript><link rel="stylesheet"${attrs}></noscript>`
                    )
                }
            }
        }
    }
}

export default defineConfig({
    root: here,
    base: './',
    publicDir: resolve(here, 'public'),
    plugins: [vue(), htmlAsyncCss()],
    server: { port: 5193 },
    build: {
        outDir: resolve(here, '../../dist-after'),
        emptyOutDir: true,
        rollupOptions: {
            input: {
                index: resolve(here, 'index.html'),
                memory: resolve(here, 'memory.html')
            }
        }
    }
})
```

`apps/before` 那一份结构完全一样，差别只有三处：没有 `htmlAsyncCss` 插件、产物输出到 `dist-before`、注释里的说明换成优化前的写法。

**源码里没有一行「为了凑差异」的假代码。** `report-engine.js` 是 36 个指标定义 + 6 个维度 + 透视 / 异常检测 / 导出的真实现，它是报表路由的依赖，构建后自己就是 8.46 kB 的一块；`chart.js` 是仪表盘走势卡的真实渲染模块。之所以专门写这些重页面，是因为**路由级分割的收益本来就等于「被拆出去那部分有多大 × 它上首屏的概率有多低」**——拆几个十几行的组件，什么都量不出来。

## 二、怎么跑起来

```bash
cd code/perf-lab
npm install            # 一次装好两个项目（npm workspaces）；唯一的运行时依赖是 vue

npm run build          # 先构建：dist-before/ 与 dist-after/（看实验用这两个产物）
npm run preview:before # 优化前产物：http://localhost:5187/
npm run preview:after  # 优化后产物：http://localhost:5193/

npm run dev:before     # 源码模式（改代码随手看效果）：http://localhost:5177/
npm run dev:after      # 同上：http://localhost:5197/
```

四件事要记住：

- **看实验用 `build` + `preview`，不用 `dev`**。这个实验台比的就是「构建产物的形态」——chunk 怎么切、HTML 里注入了什么、CSS 链接是不是阻塞，这些只在产物里成立；`dev` 按模块分发、每个文件带 HMR 开销，字节数与关键路径都失真。dev 与 preview 端口故意错开（5177/5197 vs 5187/5193），可以同时开着改代码。
- **每个实验读数自己打自己**。页面加载结束会把一份 `[perf-lab] 本次实测` 的 payload 打到 Console（`metrics` 是 CLS / LCP 这类标准指标，`resources` 是每个文件的 `transferSize`）；聚合、重渲染、公告位、字体、动画、仪表盘这些实验被触发时，另打一条 `[perf-lab] ×× 对照`。
- **看差值，不看绝对值**。下文标注「示例读数」的数字来自 headless Chrome + `preview` 产物的一次实测，你机器上的绝对值会不同，结论落在「before → after 哪个数变了、变了多少」的方向上。
- **限速靠 DevTools，不靠本地服务**。本机传 500 KB 只要几毫秒，不放大网络差异；想让「少一次往返」「图没预留尺寸」肉眼可见，在 DevTools → Network 开 **Slow 3G** 即可。

## 三、加载层 LCP：HTML 入口、chunk 切割、渲染节奏、图片与缓存

加载层回答「第一屏的东西是不是下得又少又早又快」。下面五个对照，按「HTML → 构建产物 → 渲染节奏 → 图片 → 缓存」的顺序覆盖这一层。

### 3.1 HTML 入口：全量 CSS 阻塞 + 空壳 → 关键 CSS 内联 + 骨架屏 + CSS 异步

**定位**：优化前项目的首帧要等两件事——构建注入的全量 CSS 下完、JS 把 `#app` 填上，屏幕长时间空白。`npm run build` 之后把两个 `dist-*/index.html` 摆在一起，差异一目了然。优化前的入口就是真实项目里最常见的「不设防」写法：

> 摘自 `./code/perf-lab/apps/before/index.html`

```html
    <body>
        <!-- 真实项目最常见、也最「不设防」的入口：一个空壳，等 JS 来画。
             样式由 src/main.js import 进依赖图，构建时 vite 自动抽成 assets/index-*.css
             并把 <link rel="stylesheet"> 注入到这里 —— 下载解析完之前浏览器一个字都不画（阻塞首屏）。 -->
        <div id="app"></div>
        <script src="/lab.js"></script>
        <script type="module" src="./src/main.js"></script>
    </body>
```

构建后 vite 在 `<head>` 里注入的那行 `<link rel="stylesheet" href="./assets/index-*.css">`，就是首屏的阻塞源——**源码里没写它，是构建管线替你加的**，所以这类优化要落在构建配置上，不是手改 HTML。

优化后项目做了三件事：**关键 CSS 内联**（骨架屏的尺寸和布局直接写进源码的 `<style>`）、**骨架屏直接写在 HTML 里**（JS 还没到位就有东西可画）、**全量 CSS 异步加载**——最后一件由 `htmlAsyncCss` 构建插件完成（配置见「一」），构建出的 `<head>` 是这样：

```
构建产物（dist-after/index.html，htmlAsyncCss 插件的输出）：

<link rel="modulepreload" crossorigin src="...">
<link rel="preload" as="style" href="./assets/index-*.css">
<link rel="stylesheet" href="./assets/index-*.css" media="print" onload="this.media='all'">
<noscript><link rel="stylesheet" href="./assets/index-*.css"></noscript>
```

`media="print"` 匹配媒体查询失败，浏览器**只下载不应用、不阻塞渲染**，`onload` 里改回 `all` 生效；骨架屏的样子靠内联的关键 CSS 顶着。

> 摘自 `./code/perf-lab/apps/after/index.html`

```html
    <body>
        <!-- 骨架屏直接写在 HTML 里：JS 还没到位就有东西可画 -->
        <div id="app">
            <div class="app">
                <header class="top">
                    <nav><span class="sk sk-nav"></span></nav>
                </header>
                <main>
                    <p class="sk-text">订单数据加载中…</p>
                    <div class="sk sk-bar"></div>
                    <div class="sk sk-row"></div>
                    <div class="sk sk-row"></div>
                    <div class="sk sk-row"></div>
                </main>
            </div>
        </div>
        <!-- 全量样式走 src/main.js 进依赖图：构建时 vite 注入 <link>，
             再由 vite.config.mjs 里的 htmlAsyncCss 插件把它改写成异步加载（不挡首屏） -->
        <script src="/lab.js"></script>
        <script type="module" src="./src/main.js"></script>
    </body>
```

**怎么看**：`npm run build` 后 `preview` 起两边产物，开 Slow 3G 刷新两边首页——before 白屏到 CSS + JS 全部就位，after 先画出骨架屏。Console 里 `firstViewMs` 是「首个路由视图挂载」的耗时；示例读数（落地列表页）：FCP 296ms → 40ms、LCP 296ms → 148ms（骨架屏让首帧提前，不是「更少的工作」）。

### 3.2 构建层：五个视图全量打包 → 动态 import 切 chunk + 空闲预取

**定位**：优化前项目在构建层没有做任何 chunk 切割——路由表里的 `component` 直接写静态 import 的组件，rollup 只能打出一个全量 bundle：落在哪个路由，都得先把五个页面全部下完。这层的全部实现就是两张路由表的写法差别。

> 摘自 `./code/perf-lab/apps/before/src/main.js`

```js
/**
 * 优化前入口：一个标准 vite 项目的写法 —— 样式与五个视图全部在编译期打进同一个依赖图。
 * 路由用 vue-router 的静态路由表：component 直接写 import 进来的组件，
 * 路由库与五个视图都在编译期进入主 bundle，跑 `npm run build` 后看 dist-before/assets：
 * 五个视图没有独立 chunk，全在主 bundle 里。
 */
import { createApp } from 'vue'
import { createRouter, createWebHashHistory } from 'vue-router'
import './assets/main.css'
import App from './App.vue'
import DashboardView from './views/DashboardView.vue'
import ListView from './views/ListView.vue'
import DetailView from './views/DetailView.vue'
import ReportView from './views/ReportView.vue'
import AboutView from './views/AboutView.vue'

const router = createRouter({
    history: createWebHashHistory(),
    routes: [
        { path: '/', redirect: '/dashboard' },
        { path: '/dashboard', component: DashboardView },
        { path: '/list', component: ListView },
        { path: '/detail/:id', component: DetailView },
        { path: '/report', component: ReportView },
        { path: '/about', component: AboutView }
    ]
})

createApp(App).use(router).mount('#app')
```

> 摘自 `./code/perf-lab/apps/after/src/main.js`

```js
/**
 * 优化后入口：两处优化写法 ——
 *   1. 路由表里 component 写 () => import(...)（vue-router 的路由懒加载）：
 *      切到哪个路由才下哪个 chunk，rollup 把每个路由的模块图切成独立 chunk
 *   2. 全量样式从依赖图进（构建时抽出 <link>，由 htmlAsyncCss 插件改写成异步）
 * 对照 before/src/main.js 的静态路由，产物里会多出五个视图 chunk（见实战篇构建层一节）
 */
import { createApp } from 'vue'
import { createRouter, createWebHashHistory } from 'vue-router'
import './assets/main.css'
import App from './App.vue'

const router = createRouter({
    history: createWebHashHistory(),
    routes: [
        { path: '/', redirect: '/dashboard' },
        { path: '/dashboard', component: () => import('./views/DashboardView.vue') },
        { path: '/list', component: () => import('./views/ListView.vue') },
        { path: '/detail/:id', component: () => import('./views/DetailView.vue') },
        { path: '/report', component: () => import('./views/ReportView.vue') },
        { path: '/about', component: () => import('./views/AboutView.vue') }
    ]
})

createApp(App).use(router).mount('#app')
```

`npm run build` 的产物一眼能看出差别：

```
npm run build 的输出（vite 构建日志，kB 按 1000 进制报数）：

dist-before/   一个主 bundle 装着全部页面（含 vue + vue-router）
  assets/index-....js            111.53 kB │ gzip: 44.47 kB  ← 五个视图全在里面
  assets/index-....css             2.92 kB
  assets/memory-....js             1.03 kB
  index.html                       0.76 kB

dist-after/    主包瘦下来，五个视图各成一块
  assets/index-....js              97.05 kB │ gzip: 37.97 kB
  assets/ReportView-....js         8.46 kB  ← 透视 / 异常检测 / 导出算法，只有真点进报表页才下
  assets/ListView-....js           3.12 kB
  assets/DetailView-....js         2.78 kB
  assets/DashboardView-....js      2.71 kB  ← 含 chart.js（走势卡渲染模块）
  assets/AboutView-....js          0.42 kB
  assets/store-....js              0.93 kB
  assets/agg-worker-....js         0.44 kB
  assets/index-....css             3.34 kB
  index.html                       3.07 kB  ← 比 before 大，多出来的是内联的关键 CSS + 骨架屏
```

注意这张表证明的是**时序优化**，不是体积优化：优化后落地「关于页」和「报表页」的首屏字节并不一样——报表页那 8.46 kB 的重算法真被用到时才下；落在低频路由时，8.46 kB 留在网上。主包从 111.53 → 97.05 kB，差额不是「优化掉的代码」，而是被挪去五个视图 chunk 的那部分；路由库两边都在主包里，对比因此公平。`agg-worker` 在 before 产物里根本不存在（它压根不用 Worker），在 after 产物里是一个独立 chunk——`new Worker(new URL(...), { type: 'module' })` 是 vite 认得的写法，worker 永远不会被塞进主包。

清单里还有一个不属于 SPA 的 `memory-....js`：它对应第二个构建入口 `memory.html`（写进了 `vite.config.mjs` 的 `rollupOptions.input`），是 4.4 的内存对照实验页——内存对照要 `performance.memory` 的精确粒度，且不能被路由切换打断堆采样，所以做成了独立页面而不是 SPA 里的一张路由。**真实项目不会有这个入口，它是实验台的例外**，比对构建产物时跳过它即可。顺带一提，这种「`input` 里传多个 html」的写法就是 vite 官方的 **MPA（多页应用）配置形态**——真实 MPA 项目每个页面一张 html、各自独立产物（常用 glob 一次列出全部 html）；本项目借的只是这个形态本身，SPA 本体仍是单页应用，第二个入口只是给实验页搭便车。

**但分割本身是有代价的**：切路由多了一次 chunk 下载。所以 after 项目把预取跟它配成一对——首屏稳定后，在空闲时段把没去过的路由全部拉下来，切过去时不用再等：

> 摘自 `./code/perf-lab/apps/after/src/App.vue`

```js
    // 空闲时把没去过的路由预取下来：切过去时不用再等 chunk
    // 预取抢的是空闲带宽，所以必须等首屏稳定后再开始，不能跟首屏关键路径抢；
    // 懒加载路由的 components.default 就是那个 () => import 函数，调用它即触发下载进缓存
    const idle = window.requestIdleCallback || (fn => setTimeout(fn, 200))
    idle(async () => {
        for (const record of router.getRoutes()) {
            const comp = record.components && record.components.default
            if (typeof comp === 'function') await comp()
        }
    })
```

**怎么看**：`preview` 起两边产物，落地首页看 Console payload——示例读数：首载关键路径字节 46937 → 43590（数字接近，因为落地页本来就要下它自己的 chunk），`timings` 字段里能直接看到差别：before 的 `/dashboard` 是 1ms（组件在主包里，没有下载窗口），after 是 13ms（含 DashboardView chunk 的下载与执行）。真正的差别在切路由：before 落「关于页」「报表页」一个新请求都没有（全在主包里），after 首次切路由会拉对应 chunk（`timings` 里 14~17ms），空闲预取跑完后再切就零请求——Network 面板里能看到五个视图 chunk 的 `startTime` 落在首屏之后。**分割与预取必须成对做，只做分割是亏的。**

### 3.3 渲染节奏：一次铺满 22 张卡 → 首屏一批 + 空闲补齐

**定位**：仪表盘页有 4 张 KPI 卡 + 18 张分区走势卡 + 一个畅销榜。before 进页面就把全部 22 张卡一次性同步渲染——这些工作全落在首帧之前的那个任务里，「可交互时间」被整页推进；after 先渲染用户视线最先落到的 4 张 KPI + 6 张走势卡，剩下的在 `requestIdleCallback` 里分批补齐——折叠区下面的卡晚几百毫秒上屏，用户根本感觉不到：

> 摘自 `./code/perf-lab/apps/before/src/views/DashboardView.vue`


> 摘自 `./code/perf-lab/apps/after/src/views/DashboardView.vue`


**怎么看**：打开两边仪表盘页，Console 的 `[perf-lab] 仪表盘对照`——示例读数：before `impl: sync, syncMs: 15`（一次性任务），after `impl: idle-batch, firstBatchMs: 13, allMs: 59`（总时长反而更长——idle 等待有开销、分批有拆分成本，但首屏任务更短、主线程在卡片之间是让出来的）。还有一层要如实看：**分批插入的卡片没有预留高度，CLS 从 0 变成 0.1316**——分批消的是长任务，不解决位移，要消位移得给每张卡先占位。**这层的收益和 Worker 那层同构：不是算得更快，是「主线程什么时候让出来」。**

### 3.4 资源层：图集全部立即加载 → 首屏外懒加载

**定位**：详情页有 12 张约 21KB 的图集，只有第 0 张在首屏内。before 把 12 张全部立即加载——首屏之外的 11 张也在首屏抢带宽。

### 3.5 缓存：两版相同，也是其余对照的前提

**定位**：缓存这一层两个项目做的是同一件事，它不是对照项，而是前提——vite 默认给每个产物文件名加内容 hash，内容变了文件名就变，所以可以放心把缓存时间设到一年。二次访问时 `transferSize` 为 0 就是「没走网络」。

**怎么看**：`preview` 起任意一边，加载一次再刷新，Network 面板看「from cache」，或 Console payload 的 `resources` 里第二次的 `size` ≈ 0。**强缓存只解决「同一个文件再下一次」，首屏第一次访问它一点忙都帮不上。**

## 四、运行层 INP：聚合、滚动、重渲染与内存

运行层回答「交互之后主线程是不是很快还给你」。列表页是主战场，四个对照都在这一页。

### 4.1 聚合：同步一次干完 → Worker（分片是中间档）

**定位**：列表页的「跑一次全量聚合」按钮对 10000 条数据做三趟遍历 + 一次排序（列表本身 2000 条，聚合的数据量故意更大——2000 条同步算只有几毫秒，量不出长任务）。before 在主线程上同步一次干完：

> 摘自 `./code/perf-lab/apps/before/src/views/ListView.vue`

```js
/** 同步聚合：对 10000 条数据三趟遍历 + 一次排序，一段长任务把主线程占满，
 *  「点了之后卡多久」就是它的时长。列表本身 2000 条，聚合的数据量故意更大——
 *  2000 条同步算只有几毫秒，量不出长任务 */
function onAgg() {
    const t0 = performance.now()
    heavyAggregate(makeItems(10000))
    aggMs.value = Math.round(performance.now() - t0)
    console.info('[perf-lab] 聚合对照', { impl: 'sync', mainThreadMs: aggMs.value })
}
```

after 把整段计算搬进 Worker——主线程只发一条消息、收一条结果：

> 摘自 `./code/perf-lab/apps/after/src/views/ListView.vue`

```js

    // 聚合对 10000 条数据跑（列表本身 2000 条，数据量故意更大，2000 条量不出长任务）
```

Worker 是懒创建的——第一次点击才把 agg-worker chunk 拉下来，不用 Worker 的用户永远不付这份成本：


> 摘自 `./code/perf-lab/apps/after/src/lib/agg-worker.js`

```js
/**
 * 聚合搬进 Worker：主线程只负责发一条消息、收一条结果
 * `new Worker(new URL(...), { type: 'module' })` 是 vite 认得的写法，
 * 构建时会把这个文件单独打成一个 chunk，不会被塞进主包
```

两版共用的 `store.js` 里还留着一档 **MessageChannel 分片版**——每片 200 条、片与片之间让出主线程，数据量再小一档、不值得开 Worker 时用它：

> 摘自 `./code/perf-lab/apps/before/src/lib/store.js`（两版同文）

```js
/**
 * 分片版：每片 200 条，片与片之间用 MessageChannel 让出主线程
 * 为什么不用 setTimeout(0)：它有 4ms clamping，片数一多（2000/200=10 片）就白等 40ms
 */
export function sliceAggregate(items, chunk = 200) {
    return new Promise(resolve => {
        let i = 0
        let sum = 0
        let max = 0
        const buckets = {}
        const channel = new MessageChannel()
        const step = () => {
            const end = Math.min(i + chunk, items.length)
            for (; i < end; i++) {
                const price = Number(items[i].price)
                sum += price
                if (price > max) max = price
                buckets[items[i].tag] = (buckets[items[i].tag] || 0) + price
            }
            if (i < items.length) return channel.port2.postMessage(0)
            channel.port2.close()
            const sorted = [...items].sort((a, b) => b.score - a.score)
            resolve({ sum: Math.round(sum), max, buckets, top: sorted.slice(0, 5).map(it => it.name) })
        }
        channel.port1.onmessage = step
        step()
    })
}
```

**怎么看**：两边列表页各点一次「跑一次全量聚合」，Console 的 `[perf-lab] 聚合对照`——示例读数：before `impl: sync, mainThreadMs: 10`（这 10ms 里主线程被整块占住，数据更大或机器更慢时轻松越过 50ms 长任务线，Performance 面板看得到）；after `impl: worker, mainThreadMs: 35, workerMs: 13`——**别拿 `mainThreadMs` 当结论**：它包含 Worker 首次创建（懒创建，chunk 现拉）与消息往返，真正的计算时长在 `workerMs` 里，这层的收益是「交互期间主线程还响不响应」，不是「算得更快」。

### 4.2 滚动：无节流逐行读写 → rAF 合帧 + 虚拟滚动

**定位**：列表页 2000 行。before 全量渲染，滚动监听里对每一行「读 `offsetTop` 再写 `transform`」——读写交错，每个 scroll 事件都强制同步布局：

> 摘自 `./code/perf-lab/apps/before/src/views/ListView.vue`

```js
/** 未节流：每个 scroll 事件都对全部行逐行「读 offsetTop 再写 transform」，
 *  读写交错强制同步布局，滚动期间主线程被占死 */
function onWindowScroll() {
    for (const el of document.querySelectorAll('.row')) {
        el.style.transform = `translateX(${el.offsetTop % 3}px)`
    }
}
```

after 拆成两个优化：**rAF 合帧**（一帧只读一次滚动位置，然后只写一次）和**虚拟滚动**（2000 行只渲染窗口内的 14 行，DOM 规模先降两个量级）：

> 摘自 `./code/perf-lab/apps/after/src/views/ListView.vue`

```js
/** rAF 合帧：一帧只读一次滚动位置，然后只写一次 —— 不逐行读写交错 */
let scheduled = false
function onScroll() {
    if (scheduled) return
    scheduled = true
    requestAnimationFrame(() => {
        scheduled = false
        start.value = Math.floor(vp.value.scrollTop / ROW_H)
        offset.value = start.value * ROW_H
    })
}
```

> 摘自 `./code/perf-lab/apps/after/src/views/ListView.vue`

```html
        <!-- 虚拟滚动：只渲染窗口内 14 行，key 用稳定 id -->
        <div class="viewport" ref="vp" @scroll.passive="onScroll">
            <div class="total" :style="{ height: items.length * ROW_H + 'px' }">
                <div class="rows" :style="{ transform: 'translateY(' + offset + 'px)' }">
                    <RowItem v-for="it in visible" :key="it.id" :it="it" />
                </div>
            </div>
        </div>
```

**这个顺序很重要**：先分清是「读写的锅」还是「节点数的锅」。同一份全量渲染，只把写法从「逐行读写」换成「rAF 合帧」就能消掉长任务；DOM 规模（2000 行 → 14 行）是第二级收益，代价是滚动锚定与窗口计算的复杂度，只有列表确实长时才划算。

**怎么看**：两边列表页连滚一屏，Performance 面板看滚动期间的 longtask 与每帧耗时；Console payload 的 `domNodes`——示例读数：10030 → 108（全量 2000 行每行 5 个元素，虚拟滚动只渲染窗口内 14 行）。

### 4.3 重渲染：key 用下标 + 状态穿透 → key 用 id + 状态下沉

**定位**：列表页工具条上有两个按钮——「在头部插入一条」和「改一次『与列表无关』的状态」。before 的两个写法问题叠加在同一份行组件上：行 key 用下标 `i`（头部插入后所有行的 key 全部错位，行内容全部重建）；`tick` 这个与列表无关的状态作为 prop 穿透进每一行（它一变，2000 行跟着重渲染）。

> 摘自 `./code/perf-lab/apps/before/src/views/ListView.vue`

```js

const rendersShown = ref(0)

/** 行组件手写 render：只有手写才能在「每次渲染」这个点上打计数 */

        tick: { type: Number, default: 0 }

        return () => {
            stats.renders += 1
            return h('div', { class: 'row' }, [
                h('b', props.it.name),
                h('span', '¥' + props.it.price),
                h('i', props.it.tag),
                h('em', `${props.it.score} · t${props.tick}`)
            ])
        }
    }
})
```

> 摘自 `./code/perf-lab/apps/before/src/views/ListView.vue`

```html

            <RowItem v-for="(it, i) in items" :key="i" :it="it" :tick="tick" />
```

after 的行组件不再接收 `tick`，key 换成稳定 `id`；与列表无关的状态下沉到一个独立小组件，它变一次只有它自己重渲染：

> 摘自 `./code/perf-lab/apps/after/src/views/ListView.vue`


**怎么看**：两边列表页各点一次「在头部插入一条」「改一次无关的状态」，Console 的 `[perf-lab] 重渲染对照`——示例读数：头部插一条 `renders 2001 → 1`（key 用下标时所有行 key 错位全部重建，key 用 id 时只有新行自己）；无关状态变一次 `renders 2001 → 0`（下沉后只有 TickBadge 自己重渲染）。工具条上的「行组件已渲染 N 次」是同一个计数器的实时读数。

### 4.4 内存：留引用 → 可回收

**定位**：这是唯一不在 SPA 里的实验——它要 `--enable-precise-memory-info` 单独开浏览器（不加这个 flag，`performance.memory` 的粒度是 100KB 级，量不出逐轮趋势）。两个项目各有一张 `memory.html`，实现上的差别只有一处：before 把每轮的数组挂在全局上留引用，after 让它出了作用域就被回收。

> 摘自 `./code/perf-lab/apps/before/memory.js`


**怎么看**：用带 `--enable-precise-memory-info` 的 Chrome 分别打开两个项目的 `memory.html`，页面正文直接打印每轮堆采样，Console payload 里有 `growth`（增长量）——before 一路增长（泄漏），after 涨上去又落回来（可回收）。

### 5.4 动画：写 top → 写 transform

**定位**：详情页有一块 320px 高的展开面板，点「展开面板」按钮用 20 帧把它从收起推到展开，两版的起止位置、时长、帧数完全一样，唯一变量是写哪个属性：before 写 `top`（布局属性，每帧都触发重新布局），after 写 `transform`（合成属性）。

> 摘自 `./code/perf-lab/apps/before/src/views/DetailView.vue`

```js
    for (let i = 0; i <= frames; i++) {
        el.style.top = `${Math.round(-SHEET_H * (1 - i / frames))}px`
        await raf()
    }
```

> 摘自 `./code/perf-lab/apps/after/src/views/DetailView.vue`

```js
    for (let i = 0; i <= frames; i++) {
        el.style.transform = `translateY(${Math.round(-SHEET_H * (1 - i / frames))}px)`
        await raf()
    }
```

**怎么看**：两边详情页各点一次「展开面板」，Performance 面板看动画期间的布局抖动（before 每帧都有 Layout，after 没有）；Console 的 `[perf-lab] 动画对照` 给出 `prop`（`top` / `transform`）与每帧耗时——本机 localhost 上帧耗两档可能看不出差别（示例读数 18ms vs 17ms/帧），**布局条目数是更稳的读数**。

## 六、读数口径与已知坑

这些是只有真跑过才会知道的事，写下来省得下次再踩。两个项目的 `lab.js` 同文，口径集中在这里：

> 摘自 `./code/perf-lab/apps/before/public/lab.js`

```js
    observe('layout-shift', e => {
        // 规范口径：位移发生在用户输入后 500ms 内属于「预期位移」，不计入 CLS
        // 手动对照时浏览器仍可能把无输入时的位移标成预期（hadRecentInput 为 true），所以两个值都留着：
        // cls 是上报给监控的口径，clsRaw 是「所有位移之和」，对照实验读 clsRaw
        metrics.shifts += 1
        metrics.clsRaw += e.value
        if (!e.hadRecentInput) metrics.cls += e.value
    })
```

- **CLS 有两个口径**。规范会剔掉 `hadRecentInput` 为 true 的位移，对照实验读 `clsRaw`（所有位移之和）更有意义；`cls` 是规范口径（真实用户环境用这个），两个都打出来对照。
- **CLS 要保留 4 位小数**。CLS 真值多落在 0.005~0.1 之间，一位小数会把 0.0633 显示成 0.1、把 0.0081 显示成 0，两组对照直接看成一个数。
- **INP 用「最长同步块」近似**。真实 INP 要用户实际输入才产生 `event` 条目；脚本派发的不可信事件量的是「计时块里强制结算布局后主线程被独占的时长」——比帧间隔稳定，也更贴近「用户点了多久没反应」，但它不等于浏览器上报的 INP。
- **观测窗口必须一致**。CLS / LCP 是累积条目，「等某件事完成再上报」的实验如果两版等的事件不同，差就成了测量假象（3.4 的懒加载、5.1 的主图都是这样踩过来的）。
- **数值因机器负载波动，关注差值方向**。没有自动化多轮取中位数，单次读数受本机负载影响；同一台机器连开两次也可能差一点。
- **骨架屏的连带指标**。after 的骨架屏能让 LCP 变绿，但用户还看不到真实内容——真实项目要另配一个「真实内容渲染完成」的指标（现场侧的 RUM 采集见监控与稳定性模块）。
