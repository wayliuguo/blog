# 性能优化实战

## 一、这个工程长什么样

**两个工程、一套源码。** `apps/before` 是「优化前」，`apps/after` 是「优化后」，各自是一个独立的 vite + vue 工程；业务源码只有一份，放在 `shared/`，两边都用 `@lab` 别名引入。于是两个工程的差异被压到最小——只剩各自目录里的 HTML 入口、`main.js` 与 `vite.config.mjs` 三个文件。

```
perf-lab/
├─ package.json        根：npm workspaces（apps/*）+ 全部 scripts（只有 dev/build/preview）
├─ shared/             业务源码唯一一份，两个工程共用
│  ├─ App.vue          SPA 外壳：hash 路由、实验驱动（?act=）、指标采集
│  ├─ lib/             options.js（开关）/ store.js（数据与聚合）/ agg-worker.js / report-engine.js
│  ├─ views/           ListView / DetailView / ReportView / AboutView（四个手动实验的面板挂在这里）
│  └─ public/          app.css（两版共用）、lab.js（页面侧指标采集）、lab-assets/（hero + 12 张图，替换原 /asset 端点）
├─ apps/
│  ├─ before/          优化前：raw.html（CSS 外链阻塞 + #app 空壳）+ main.js（静态 import）+ memory.html
│  └─ after/           优化后：index.html（关键 CSS 内联 + 骨架屏）+ main.js（动态 import）
```

> 没有 `harness/` 目录、没有 `lab` 命令、没有服务端。测量能力长在页面里：浏览器原生 `PerformanceObserver` 订阅 paint / LCP / layout-shift / longtask，`performance.getEntriesByType('resource')` 直接给每个文件的 `transferSize`，`lab.js` 把这些整理成一份 payload 打到 console——开页面、开 DevTools 就能读数。

「优化后」那一侧的配置是这样：

> 摘自 `./code/perf-lab/apps/after/vite.config.mjs`（运行：`npm run build`）

```js
import { defineConfig } from 'vite'
import vue from '@vitejs/plugin-vue'
import { fileURLToPath } from 'node:url'
import { dirname, resolve } from 'node:path'

const here = dirname(fileURLToPath(import.meta.url))
const LAB = resolve(here, '../..') // perf-lab 根：产物与 lab-assets 都在这里
const SHARED = resolve(LAB, 'shared')

/**
 * 「优化后」工程：一个独立的 vite + vue 项目
 *   入口 index.html：首屏关键 CSS 内联 + HTML 里的骨架屏 + 全量 CSS 异步
 *   入口 main.js：() => import('@lab/views/X.vue')，rollup 把四个视图拆成独立 chunk
 * 业务源码同样来自 ../../shared/（@lab 别名），与 before 工程是同一份文件。
 * 两个工程各自独立构建，绝不合在一次构建里 —— 多入口一起构建时 rollup 会把共用模块提到
 * 公共 chunk，before 那份就不再是「一个 bundle 全量包含」的干净基线。
 */
export default defineConfig({
    root: here,
    base: './',
    publicDir: resolve(SHARED, 'public'),
    resolve: { alias: { '@lab': SHARED } },
    plugins: [vue()],
    server: { port: 5193, fs: { allow: [LAB] } },
    build: {
        outDir: resolve(LAB, 'dist-after'),
        emptyOutDir: true,
        rollupOptions: {
            input: { optimized: resolve(here, 'index.html') }
        }
    }
})
```

`apps/before` 那一份结构完全一样，差别只有三处：入口换成 `raw.html` + `memory.html`、产物输出到 `dist-before`、`dev` 端口 5187（`after` 是 5193）。

两次构建的产物一眼能看出差别：

```

  assets/memory-....js              1.13 kB
  assets/agg-worker-....js          0.44 kB

  assets/ReportView-....js          8.41 kB  ← 透视 / 异常检测 / 导出算法，只有真点进报表页才下
  assets/ListView-....js            5.45 kB

```

`agg-worker` 在两套产物里都是一个独立 chunk——`new Worker(new URL(...), { type: 'module' })` 是 vite 认得的写法，worker 有它自己的入口，永远不会被塞进主包。

**源码里没有一行「为了凑差异」的假代码。** `report-engine.js` 是 36 个指标定义 + 6 个维度 + 透视 / 异常检测 / 导出的真实现，它是报表路由的依赖，构建后自己就是 8.41 kB 的一块。之所以专门写一个低频繁重页面，是因为**路由级分割的收益本来就等于「被拆出去那部分有多大 × 它上首屏的概率有多低」**——拆几个十几行的组件，什么都量不出来。

**开关机制**：入口总开关写在 HTML 里（`window.__PERF_OPT = true/false`），单项开关可以在 query 上覆盖，用来做「只改一项」的对照：

> 摘自 `./code/perf-lab/shared/lib/options.js`

```js
/**
 * 实验台开关
 * 总开关写在 HTML 入口里：index.html 设 window.__PERF_OPT = true（优化后），raw.html 设 false（优化前）
 * 单项开关可以单独覆盖总开关，用来做「只改一项」的对照：
 *   ?virtual=0      → 优化后入口里只关掉虚拟滚动
 *   ?split=1        → 优化前入口里单独打开路由级分割（看它一项能拿多少）
 */
export const q = new URLSearchParams(location.search)
export const OPTIMIZED = window.__PERF_OPT === true

/** 没显式写这个开关时，跟着入口的总开关走 */
export function flag(key, whenOptimized) {
    if (q.has(key)) return q.get(key) !== '0'
    return OPTIMIZED ? whenOptimized : false
}

/** 列表条数，默认 2000 条 */
export const N = Number(q.get('n') || 2000)

/** 行高，虚拟滚动按它算偏移 */
export const ROW_H = 36
```

## 二、怎么把它跑起来

```bash
cd code/perf-lab
npm install          # 一次装好两个工程（npm workspaces）；唯一的运行时依赖是 vue
npm run dev:before   # 优化前：http://localhost:5187/raw.html
npm run dev:after    # 优化后：http://localhost:5193/index.html
npm run build        # 分别构建：dist-before/ 与 dist-after/
npm run preview:before   # 用构建产物起服务（更接近线上，推荐做字节 / 缓存对比）
npm run preview:after    # 同上，优化后
```

三件事要记住：

- **`dev` 与 `build/preview` 读的不是同一个东西**。`dev` 起的是源码（每个文件都带 HMR 开销，字节数失真），`preview` 起的是构建产物。想看**首屏字节 / 二次访问缓存**最准，用 `preview`；想随手改源码看效果，用 `dev`。
- **不需要本机 Chrome 自动化、不需要服务端**。打开浏览器、开 DevTools（Console / Network / Performance）就够了。页面在加载结束会把一份 `[perf-lab] 本次实测` 的 payload 打到 Console——`extra` 是各实验自己的读数，`metrics` 是 CLS / LCP 这类标准指标，`resources` 是每个文件的 `transferSize`。
- **看差值，不看绝对值**。下面所有数字都是示例读数（某台机器、某次加载跑出来的），你机器上的绝对值会不同；结论落在「before → after 哪个数变了、变了多少」的方向上。

限速（让网络差异肉眼可见）靠 **DevTools → Network → 限速**（如 Slow 3G），不靠任何本地服务——这是标准的手动手法，`images` / `cls` 想看明显的 LCP 差时打开即可。

## 三、实验怎么读：八个基础 case 与四个页面内对照

十二个实验分两类，但读法同一条：**打开 `before`（dev:before / preview:before）与 `after`（dev:after / preview:after）两个版本，对照同一个开关在两边的行为**。八 个基础 case 是「同一个开关在 before / after 下行为不同」，四个页面内对照是「读数本身是同一次加载里的前后差值」。逐个说每个实验在读什么、哪里最容易读错。

八个基础 case：

- `spa` 优化前 vs 优化后：首屏关键路径、JS 字节、请求数
- `nav` 路由切换：空闲预取开 / 关
- `agg` 一次耗时聚合：同步 / 分片 / Worker
- `scroll` 滚动 30 帧：虚拟滚动 + rAF 节流
- `images` 图集 12 张：loading="lazy" 到底省了多少
- `cls` 详情页主图：有没有预留尺寸
- `cache` 二次访问：强缓存 + 内容 hash
- `memory` 内存：留引用 vs 可回收（独立页）

有一条纪律贯穿全部 case：**一次只留一个变量**。最典型的是 `spa` 那个对照——两个入口本身的差异不止一处，而是「整个入口」三处合起来：CSS 外链阻塞 / 内联、`#app` 空壳 / 骨架屏、静态 `import` 全部视图 / 动态 `import`。三处合起来才叫「优化前 vs 优化后」，不把功劳单算给其中任何一项。想最干净地只比打包，给 `after` 加 `?prefetch=0` 即可（不影响关键路径字节 `criticalBytes` 的读数）。

下面逐个说每个 case 在读什么、哪里最容易读错。

### `spa`：优化前 vs 优化后

**读什么**：首屏关键路径上的 JS 字节与请求数，以及落地不同路由时这几个数怎么变。**不读什么**：首屏时间——本机 localhost 没有网络延迟，冷启 Chrome 又要几十毫秒，这个数噪声很大，只能当参考。

**关键读法**：优化前落地「关于页」和「报表页」的首屏字节**一模一样**（都是 78.0 KB）——一个 bundle 里装着全部页面，落在哪个路由都得整块下完。优化后两行才分出差别（61.1 KB vs 69.4 KB），因为报表页那 8.41 kB 的重算法真被用到了。所以这张表证明的是**时序优化**，不是体积优化；请求数甚至从 2 变成了 3。

### `nav`：路由切换，预取开 / 关

**读什么**：切换耗时，以及切换时又新拉了几个 chunk。**关键读法**：拆路由本身让切换多了一次 chunk 的下载（本机 RTT 接近 0 时这个差距很小，想放大可在 DevTools 加网络延迟）；空闲预取把后续 chunk 提前到空闲时下完，所以切的时候不用等。示例读数 129ms → 74ms，且第二行的「切换时新拉的视图 chunk」是 0——**这组数字曾用一跳 50ms 延迟放大过，手动对比时差会变小，但「预取把切换补齐」的方向不变**。

**关键读法**：这条实验是给 `spa` 那个 case 补代价的。分割本身让切路由变慢，预取把它补回来——**两者必须成对做**，只做分割是亏的。

### `agg`：一次 10000 条聚合，同步 / 分片 / Worker

**读什么**：这段交互的**新增长任务**与**最长任务**，不是总耗时。总耗时反直觉（分片比同步还短），别拿它当结论。

**关键读法**：同步那一档有一个 61ms 的长任务——长度就是「用户点了之后卡多久」；分片与 Worker 都是 0。**并且要理解代码里刻意没做的事**：三种算法都不回写列表。如果让主线程顺手把结果排序再渲染，Worker 那一档就会额外背上一段主线程开销，测出来又是两个变量。

### `scroll`：连滚 30 帧，三种渲染策略

**读什么**：每帧平均耗时、DOM 节点数、最长任务。**关键读法**：前两行的 DOM 节点数完全一样（10029），差别只在读写的写法——不节流那版有一个 2528ms 的长任务；第三行才轮到 DOM 规模（10029 → 101）。**这个顺序很重要**：先分清是「读写的锅」还是「节点数的锅」，否则一上来就上虚拟滚动，卡顿依旧。

### `images`：12 张 200KB 的图集

**读什么**：发出的图片请求数与图片传输字节（只看图集本身，主图不算——两种策略都得下它）。**关键读法**：懒加载那版仍旧下了 6 张，不是 1 张——`loading="lazy"` 自带约 1250px 的预加载距离。所以它省的是「首屏之后的带宽竞争」，不是首屏。两行 LCP 几乎一样，正是这个结论的证据。

**这个 case 踩过一个观测窗口的坑**：第一版跑出来「全部立即加载」的 LCP 是 412ms、「首屏外懒加载」是 1676ms，看着像懒加载让 LCP 变差了 4 倍。真实原因跟懒加载无关——12 张图几十毫秒就下完，页面立刻上报，而首屏那张主图还在慢发，LCP 就被记成了图集里的某一张；另一版因为要等懒加载的图、上报得更晚，主图反而已经画完了。**两版的观测窗口不一样，LCP 的差就成了测量假象**。修法是让两版都等到主图落地再上报：

> 摘自 `./code/perf-lab/shared/App.vue`

```js
    } else if (act === 'images') {
        // 等这批图落地（能落的都落了）再回报：`loading="lazy"` 的那些可能永远不落，
        // 所以给一个上限，超时就按「此刻已加载多少」计数 —— 这本身就是这个 case 的读数
        const imgs = [...document.querySelectorAll('.shots img')]
        const loaded = i => i.complete && i.naturalWidth > 0
        const landed = img =>
            Promise.race([
                new Promise(resolve => {
                    if (loaded(img)) return resolve()
                    img.addEventListener('load', resolve, { once: true })
                    img.addEventListener('error', resolve, { once: true })
                }),
                settle(3000)
            ])
        await Promise.all(imgs.map(landed))
        // 主图（首屏那张，本地静态 SVG，开发机瞬间下完）也必须等：不等的话，
        // 「全部立即加载」那一版图集几十毫秒就下完、立刻上报，而主图还没画出来 ——
        // LCP 就记成了图集里那张，两版的观测窗口不一样，LCP 的差就成了测量假象
        const hero = document.querySelector('.hero')
        if (hero) await landed(hero)
        await nextFrame()
        await nextFrame()
        out.imgTotal = imgs.length
        out.imgDecoded = imgs.filter(loaded).length
```

**凡是「等某件事完成再上报」的实验，都要问一句：另外那一版等的是同一件事吗。**

### `cls`：详情页主图，有没有预留尺寸

**读什么**：`cls`（规范口径）与 `clsRaw`（所有位移之和）两个值，以及**主图已落地**这一列。**关键读法**：这个 case 必须等主图真的落地才回报——图没到就回报，两个口径都是 0，看起来「没问题」，实际什么都没测到。想放大「图没预留尺寸」造成的 LCP 差，在 DevTools 开 Slow 3G 即可。

### `cache`：同一地址访问两次

**读什么**：第二次访问的 JS 实际传输字节（`transferSize` 为 0 就是「没走网络」），以及逐文件的传输对照。**关键读法**：强缓存的前提是产物文件名带内容 hash（vite 默认给每个 chunk 加 hash）——内容变了文件名就变，所以可以放心把缓存时间设到一年。这张表的第二个作用是提醒**强缓存只解决「同一个文件再下一次」**，首屏第一次访问它一点忙都帮不上。

### `memory`：留引用 vs 可回收

**读什么**：净增长与峰值堆。**这个 case 是唯一不在 SPA 里的**——它需要 `--enable-precise-memory-info` 单独开一次浏览器（不加这个 flag，`performance.memory` 的粒度是 100KB 级，量不出逐轮趋势），所以留在 `apps/before` 里单建一张 `memory.html`，用带 flag 的 Chrome 打开 `?mode=clean` / `?mode=leak` 对照。页面正文会直接打印每轮堆采样，console 里也有 `growth`。

### 另外四个：页面内手动对照实验

4.3 框架层、5.2 字体、5.3 动态内容、5.4 动画这四块的读数**都是同一次加载里的前后差值**——「重渲染次数」「位移像素」「换字前后文字块的高度」都要在同一页里前后对照着看，套一层「开页面 → 读一个数」的模型反而把要观察的那段过程切没了。所以它们做成页面内面板：`npm run dev:after` 打开页面，`?act=` 指定演哪一出，页面自己把两个时刻的读数一起打到 console。跑法：

```bash
cd code/perf-lab
npm run dev:after        # 起在 5193，下面四个都在这个端口上开
```

| 实验 | 页面 | 打开这个地址 | 一次只改的变量 |
| --- | --- | --- | --- |
| 4.3 重渲染 | `#/list` | `http://localhost:5193/index.html?act=rerender&key=idx&sink=0#/list` | `key=idx` ↔ `key=id`；`sink=0` ↔ `sink=1` |
| 5.3 动态内容 | `#/list` | `http://localhost:5193/index.html?act=banner&reserve=0#/list` | `reserve=0` ↔ `reserve=1` |
| 5.2 字体 | `#/detail/1` | `http://localhost:5193/index.html?act=font&sz=0#/detail/1` | `sz=0` ↔ `sz=1` |
| 5.4 动画 | `#/detail/1` | `http://localhost:5193/index.html?act=anim&anim=top#/detail/1` | `anim=top` ↔ `anim=transform` |

**页面会把实测打到控制台**：加载结束会打印一条 `[perf-lab] 本次实测`，在 DevTools Console 里展开那个对象：**`extra` 是该实验自己的读数**（渲染次数 `rendersOnInsert` / 位移像素 `pushed` / 文本块高度 `textHBefore`、`deltaH` …），**`metrics` 是 CLS 这类标准指标**（`cls`、`clsRaw`、`shifts`）——上面各表两列合起来就是这两块。四条注意：

- **dev 与 preview 读的不是同一个东西**：`npm run dev:after` 起的是源码（带 HMR 开销，字节数失真），`npm run preview:after` 起的是 `dist-after/` 产物。想看准确字节用 preview。
- **一个页面只演一个 `act`**：`?act=` 在页面加载时读一次，换实验请重新开（或刷新）页面，别指望在地址栏里改 query 就切换。
- **面板之间不互相感染**：`act=font` / `act=anim` 时详情页不渲染主图与图集，`act=banner` 时列表固定 200 行——都是为了不让别的位移源混进来。
- **看差值，不看绝对值**：这几页本身带一点基线位移，`transform` 那一档和「预留」那一档都读 0.0081，减掉它再看。

## 四、按 ROI 排一遍

做完八个 case，顺序感比单条手段更值钱：

1. **长期缓存（文件名 hash + `max-age`）**——零代码成本，二次访问传输量直接归零（69.4 KB → 0 B），收益最大。
2. **读写分离 / rAF 合帧**——同一份全量渲染，只换写法，30 帧耗时从 3482ms 降到 989ms，而且消掉了一个 2528ms 的长任务。改动小、收益陡。
3. **虚拟滚动 / 列表裁剪**——DOM 从 10029 降到 101，滚动成本换量级；代价是滚动锚定与窗口计算的复杂度，只有列表确实长时才划算。
4. **关键 CSS 内联 + 全量 CSS 异步**——省一跳阻塞，但要配好布局尺寸，否则等于用 CLS 换 FCP。
5. **路由级分割 + 空闲预取**——必须成对做，只做分割是亏的；收益取决于被拆出去的页面有多重、上首屏的概率有多低。
6. **长任务分片 / Worker**——只有「算」本身明显超过 50ms 才值得，否则是纯亏；数据量大时优先分片，计算重且输入小时才挪 Worker。
7. **图片懒加载**——只对「首屏之外、离视口远」的图做；首屏那张别碰。

互相打架的地方也说清楚：给首屏做的预取会占带宽（所以放进 `requestIdleCallback`）、把路由拆太细会让切路由变卡（所以要配预取）、骨架屏能让 LCP 变绿但用户还看不到内容（所以要另配一个「真实内容渲染完成」的指标）。

## 五、口径与已知坑

这些是只有真跑过才会知道的事，写下来省得下次再踩：

- **INP 用「最长同步块」近似**。本实验台量的是「计时块里读一次 `offsetHeight` 强制结算布局后，主线程被独占的时长」——比帧间隔稳定，也更贴近「用户点了多久没反应」。手动点（真实用户输入）时浏览器其实能上报真正的 INP，但这套读数统一走「最长同步块」口径，便于对照；它不等于浏览器上报的 INP。
- **CLS 有两个口径**。规范会剔掉 `hadRecentInput` 为 true 的位移，对照实验读 `clsRaw`（所有位移之和）更有意义；`cls` 是规范口径（真实用户环境用这个），两个都打出来对照。
- **限速靠 DevTools，不靠本地服务**。本机 localhost 传 500 KB 只要几毫秒，不放大网络差异，「少一次往返」「图没预留尺寸」这些结论根本显示不出来。看 `images` / `cls` 的 LCP 差时，在 DevTools → Network 里开 **Slow 3G**（或自定义限速）再对比即可——标准手动手法，比自己写限速服务简单。
- **数值因机器负载波动，关注差值方向**。没有自动化多轮取中位数，单次读数受本机负载影响；同一台机器连开两次也可能差一点。所以下面所有数字都是示例读数，结论落在「before → after 哪个数变了」的方向上。
- **CLS 要保留 4 位小数**。`lab.js` 早期把所有指标统一压到 1 位小数，于是真实值 0.0633 被显示成 **0.1000**——看起来像「刚好卡在及格线上」，实际差得远。时间类指标在出表时各自取整（`ms()`），所以把精度放宽到 4 位只影响 CLS 这类小量级指标。
- **CLS 在「换字重排」里不看方向**。字体那个实验两种写法分别位移 84px 与 63px，CLS 却是 0.0253 与 0.0292（反过来了）：换字重排会被拆到若干帧结算，每帧的位移距离都变小、再各自乘一次影响比例，结果随「在几帧里切完」而波动。量字体造成的位移，看位移像素。
