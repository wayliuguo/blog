## 1. 性能优化体系与指标

### 1.1 核心指标与辅助指标

**结论：三个核心指标是「要守的目标」（统一看 p75），其余指标都是「定位刻度」，二者不可混用——核心指标告诉你去哪，辅助指标告诉你在哪。**

目标三件套（Core Web Vitals）：

| 指标 | 中文含义 | 目标（p75） | 用户的话 |
| --- | --- | --- | --- |
| LCP | 最大内容绘制 | ≤ 2.5s | 多久能看到内容 |
| INP | 交互到下一次绘制 | ≤ 200ms | 点了多久有反应 |
| CLS | 累积布局偏移 | ≤ 0.1 | 页面会不会自己乱跳 |

红线：**LCP 好不代表体验好**——同一详情页主图不写/写死尺寸，CLS 0.0633→0，两版 LCP 都在 1900ms 上下，三者谁也替代不了谁。

定位刻度（辅助指标）：**TTFB**（首字节 ↔ 所有加载指标的上限，≤800ms）· **FP** · **FCP**（≤1.8s）· **TBT**（FCP→TTI 间长任务超 50ms 部分之和，≤200ms，即 INP 的实验室代理）· **TTI** · **SI** · **Long Task**（>50ms）· **Layout Shift** · **DOM Size**（<1500）。

三个核心指标各自的「拆法」是后面分层的钥匙：

```
LCP = TTFB → 加载延迟 → 加载时长 → 元素渲染延迟  （四段 ⇄ 四层，见 1.4）
INP = 输入延迟 / 处理时间 / 呈现延迟           （三段根因 ≈ 主线程被长任务占住，见 1.5）
CLS = 影响比例 × 位移距离比例，只看起始位置     （transform 挪动不算、改 top 算，见 1.6）
```

### 1.2 排障主线：从核心指标查到要改哪一层

**结论：全篇索引就是一张「核心指标 → 辅助指标 → 归属层」的映射表；读法是顺着它定位，而不是从手段出发。**

读法：核心指标超标 → 顺着辅助指标找到异常的那一段 → 定位到层 → 在层里查具体项 → 照方案改。

| 核心指标 | 先看哪个辅助指标 | 异常信号 | 归属层 |
| --- | --- | --- | --- |
| LCP | TTFB | > 500ms | 网络层（DNS / TCP / TLS / 服务端） |
| LCP | 资源瀑布 / Coverage | 阻塞资源条又长又靠右 | 构建与产物层 |
| LCP | FCP | TTFB 正常但 FCP 明显晚 | 资源层（图片 / 字体 / 关键 CSS） |
| LCP | LCP 元素本身 | 骨架屏成了 LCP | 感知层 |
| INP | TBT / Long Task | 交互落在长任务里 | JS 执行层 |
| INP | Long Task 后紧跟的 Layout | 回调快但紧跟大范围重排 | 渲染层（强制同步布局） |
| INP | 重渲染次数 | 数据没变、组件重渲一片 | 框架层 |
| INP | 堆内存曲线 | 只涨不落、越用越卡 | 内存与长会话 |
| CLS | Layout Shift 条目 | 位移时刻接近 LCP | 资源层（图片尺寸 / 字体换字） |
| CLS | Layout Shift 条目 | 位移发生在接口返回之后 | 渲染层（动态内容） |
| CLS | Layout Shift 条目 | 位移持续累积 | 渲染层（用会触发布局的属性做动画） |

两条纪律（纠错用，最容易被忽略）：

1. **上游决定下游**：TTFB 3s 时优化下游无效；TTFB 只有 60ms 时优化服务端也没有收益——瓶颈一定在后面。
2. **指标要互相印证**：「传输量砍一半」和「LCP 一动没动」摆在一起才有结论。12 张 200KB 图集加 `loading="lazy"` 后传输 2.35 MB → 1.17 MB，LCP 却 1832→1796ms——说明改的那一段**不在 LCP 的构成里**。

### 1.3 口径与工具

**结论：先判断数字可不可信（口径），再决定开哪个面板（工具）；工具按「它替你做了什么决定」选、按「粗 → 细」用。**

- **实验室 vs 现场**：Lab（Lighthouse / 实验台）可复现、能看火焰图定位；Field / RUM 反映真实分布。分工：**现场发现问题、实验室定位根因**，改完回现场验证。性能是长尾分布，一律看 p75 而非平均值。
- **评级区间**（良好 / 待改进 / 差）：TTFB 800/1800ms · FCP 1800/3000ms · LCP 2500/4000ms · INP 200/500ms · CLS 0.1/0.25。
- 红线①：**评级是门槛不是排名**——8000ms 优化到 3000ms 仍是「待改进」，但体感是两个世界。
- 红线②：**一次只盯一个指标**，几个一起抠会互相干扰。
- **CLS 双口径**：规范口径 `cls`（剔掉交互后 500ms 内预期位移，现场报表读）+ 所有位移之和 `clsRaw`（手动对照必须读它）。二者必须分开上报——手动对照里浏览器对无输入位移的判定与真实用户不一致。

工具选型（标准只有一条：替你做什么决定）：

| 工具 | 替你做的决定 | 用在哪一步 |
| --- | --- | --- |
| Network 瀑布图 | 请求按时间排好、标阻塞 | 粗定位：时间花在哪个资源 |
| Performance 火焰图 | 主线程采样、定位函数 | 细定位：那 500ms 在跑什么 |
| Coverage | 已用 / 总字节 | 下了没执行的代码 |
| Memory | 堆快照对比 / Detached DOM / 分配时间线 | 越用越卡、什么没被回收 |
| Lighthouse | 整体水位与短板 | 趋势与短板扫描 |
| Performance API / 实验台 | 可对比、可复现的数字 | 优化前后差多少、有没有真变 |

红线：Lighthouse 是**固定权重汇总**（分数随版本变、只代表这一次），只能当趋势与短板扫描，**别当验收卡口**；要卡口就写确定性指标（LCP / INP / CLS 真实读数）进 CI。

### 1.4 加载层：把 LCP 打下来

**结论：LCP 的四段构成正好对应加载层的四层——哪一段长就改哪一层。**

```
LCP = TTFB(网络层) → 加载延迟(3.2/3.3) → 加载时长(构建层) → 元素渲染延迟(感知层)
```

- **网络层（TTFB）**：先把请求拆 `DNS → TCP → TLS → 服务端处理 → 首字节传输`，前两段前端能改（`dns-prefetch` / `preconnect`），服务端处理慢只能走后端与缓存。优化不改变资源本身，只改变「什么时候开始下」和「优先级」。

  优先级：Highest（HTML / head 同步 script / 首屏 CSS）→ High（CSS / `fetchpriority="high"` / 字体）→ Medium（图片 / defer script）→ Low（`async` script / 非首屏图 / `loading="lazy"`）→ Lowest（`prefetch`）。

  四个「提前」指令（常被混）：`preconnect`（提前 DNS+TCP+TLS）· `dns-prefetch`（只解析 DNS）· `preload`（现在以高优先级下，用于关键路径但发现得晚的）· `prefetch`（空闲下下一页）。后两个只解决「发现得晚」不解决「太大」。红线：`preload` 了几秒内用不到会抢带宽；`as="font"` 必须带 `crossorigin`。

- **构建与产物层（首屏体积）**：核心是**路由级代码分割**——同一个 bundle 装全部页面时，落在哪个路由首屏字节都一样（实测 78.0 KB）；拆分后落地关于页 61.1 KB、落地报表页 69.4 KB（它那 8.41 KB 的透视 / 异常检测 / 导出算法躲不掉）。收益 = **被拆出去那部分有多大 × 它上首屏的概率有多低**，是**时序优化不是体积优化**（首屏请求数反而从 2 变 3）。代价要成对付：切路由要等新 chunk（加 50ms 一跳延迟后 129ms），空闲预取补回来（74ms、新拉 chunk 0）。

  **tree-shaking 三条硬规则**：必须 ESM；不背顶层副作用（库标 `sideEffects: false`）；访问方式静态——只删「没被引用的导出」，删不掉「引用了但没执行到的分支」。**按需引入三层级**：入口级（路由懒加载）→ 模块级（`import()` 进函数体）→ 依赖级（组件库子路径、`moment`→`dayjs`、polyfill 交 `browserslist`、附属包按需注册）。再压三层：代码压缩（`drop_console` 别删 `console.error`）、传输压缩（gzip 约 70%、brotli 再小 15~20%）、产物形态（**内容 hash + 长缓存**→二次访问 JS 传输 69.4 KB → 0 B；sourcemap 绝不部署上线）。

- **资源层（FCP）**：先看关键渲染路径上谁在挡——无 `defer`/`async` 的 `<script>` 阻塞解析、样式表阻塞渲染、图片与字体不阻塞但推迟 LCP。红线：**动态插入的 `<script>` 默认 `async` 不阻塞解析**，想演示阻塞必须写进 HTML；`<script type="module">` 天然 defer。图片三层：尺寸与格式（写死 `width`/`height`、WebP/AVIF、SVG）→ 响应式（`srcset`+`sizes`，各档比例必须一致）→ 懒加载（`loading="lazy"` 有约 **1250px 预加载距离**，12 张图仍下 6 张，省的是「首屏后的带宽竞争」、**不改善首屏**）。红线：首屏内那张图别加 lazy，应配 `fetchpriority="high"`。**关键 CSS 内联 + 全量 CSS 异步**（`media="print"` + `onload` 改 `all`）省一次阻塞；内联部分必须含布局尺寸，否则等于用 CLS 换 FCP。**字体**默认 `font-display: auto` 有最长 3s 不可见期，四个取值 `block` / `swap` / `fallback` / `optional`。

- **感知层（时间减不到零时）**：**SSR / SSG**（内容提前，代价 TTFB 上升 + hydration 期「看得见点不动」）· **骨架屏**（白屏换有结构）· **流式渲染**（边生成边发，首字节极早）· **预取下一页**。这些不改变 LCP 的定义，但改变 LCP 元素**是什么**——从「JS 渲染的内容」变「HTML 里的内容」，LCP 可早到 TTFB 附近。红线：**骨架屏会成为 LCP 候选，LCP 变绿但用户还没看到内容**——必须另配「真实内容渲染完成」指标。

### 1.5 运行层：把 INP 打下来

**结论：INP 落后先看三件事——有没有长任务、长任务里是谁、是不是越用越卡；且「总耗时」不等于「INP」。**

两个标尺：**单帧 16ms**（超了掉帧）、**长任务 50ms**（期间不响应输入）。实操顺序：先看有没有长任务 → 看长任务里是谁（业务回调 or 样式重算）→ 看是否持续劣化（去查内存）。

红线：**「总耗时」≠「INP」**——切片让总耗时变长，但最长阻塞块降下来 INP 就变好。

```
INP = 输入延迟（主线程被占）→ 处理时间（回调本身慢）→ 呈现延迟（DOM 太大/强制布局）
```

- **JS 执行层（输入延迟 + 处理时间）**：实测三档对照（10000 条聚合）——同步 75ms / 最长任务 61ms；分片 8ms / 0；Worker 9ms / 0。分片用每片 200 条 + `MessageChannel` 让出主线程。对照纪律：三档都不能回写列表，否则 Worker 档额外背一段主线程开销。让出机制：`Promise.then` 是微任务**做切片无效**；`setTimeout(fn,0)` 有 4ms 节流；`MessageChannel` / `scheduler.postTask` 是首选。切片只能切开「多个独立工作单元」。**Worker 边界**：`postMessage` 结构化克隆**在主线程同步执行**、成本随数据量线性增长——数据本身大时先分片；真正适合「输入小、算得久」（加解密 / 压缩 / 像素运算 / 文本解析 / diff）。

- **渲染层（呈现延迟）**：**强制同步布局** = 写样式后立刻读依赖布局的属性（`offsetWidth` / `getBoundingClientRect` / `getComputedStyle`）。实测（连滚 30 帧）：全量 + 不节流 3482ms / 最长任务 2528ms；同一份渲染只在 rAF 里读一次 → 989ms / 0；虚拟滚动 → 978ms / 0。关键判据：**前两行 DOM 节点数完全一样（10029）——先分清是「读写的锅」还是「节点数的锅」**，第三行才把 DOM 降到 101。三种解法：读提前写后置（或 fastdom）· 用缓存代替读 · 把写延到下一帧。属性触发深度三级：几何（布局→绘制→合成，最贵）· 绘制 · 合成（`transform` / `opacity` / `filter` 只合成）。`will-change` 别滥用。虚拟滚动代价：每次滚动重算窗口（要合帧）、不定高列表的滚动锚定、行高必须固定；**它解决「DOM 太多」，不解决「计算太重」**。

- **框架层（处理时间被重复消耗）**：问题通常不是「某个函数慢」而是「同一段渲染跑了很多次」。判据：一次交互后多少组件重渲了、数据其实没变。React 侧 `memo` / `useMemo` / `useCallback` 切断传播链、状态下沉；Vue 侧 `shallowRef` / `markRaw` 跳过深层代理、复杂表达式抽 `computed`、长列表 `v-memo`。两侧通用：`key` 要稳定、重渲染代价由子树大小决定、重组件按需引入。它是框架项目 INP 差时最常被忽略的一层（前两层没长任务也没强制布局，多半就是它）。

- **内存与长会话（持续劣化）**：现象「越用越卡」，原因「有东西没被回收」。实测 60 轮 × 2000 个对象——留引用净涨 18.4 MB、峰值 21.6 MB 且从不回落；可回收净涨 0.5 MB、峰值 4.8 MB。**四类泄漏**：事件监听没摘、定时器没清、全局缓存只增不减（配 LRU 或上限）、闭包把大对象绑在长生命周期上。跑内存对照要开 `--enable-precise-memory-info`。

### 1.6 视觉层：把 CLS 打下来

**结论：CLS 不是性能问题而是写法问题——只看元素在布局里的起始位置有没有变化，四节全是它的推论；改完黄金四类就能归零。**

- **尺寸与预留**（最大也最好修）：**在 HTML 里写 `width` / `height`**（不是 CSS），浏览器自动算 `aspect-ratio`。实测主图：不写尺寸 CLS 0.0633、写死 0.0000。`srcset` 各档比例必须一致；`iframe` / 广告位用 `min-height` 占位；主图别加 `loading="lazy"`。判据：**图片还没开始下载时，位置高度就已经是对的**。

- **字体**：两个独立坑——**不可见期**（取值见 1.4）与**换字重排**（选 `swap` 就必然有）。解法：`size-adjust` / `ascent-override` / `descent-override` 让回退字体度量接近正式字体；把字体 `preload`（`as="font"` 带 `crossorigin`）。红线：量字体位移**看「位移像素」**，CLS 只当佐证（重排被拆到几帧结算、每帧距离变小再乘影响比例，CLS 数值会反转）。

- **动态内容**：第三类来源不是「元素变了」而是**新元素插到了已有内容前面**。给动态内容预留带 `min-height` 的容器；**绝不在已有内容上方插入**（240px 横幅插 `body` 最前，影响比例接近 1，一次就超 0.1）；骨架屏必须与真实内容结构一致。红线：**这类问题开发环境看不见**，必须限速复现。

- **动画与交互**：**用 `transform: translate()` 不产生 CLS** 且只走合成；**改 `top` / `left` / `margin` / `height`** 既算位移又触发整条流水线。所以动画只用 `transform` 与 `opacity`——同时服务三个核心目标。「展开 / 收起」这类真要改布局的做不到纯合成，让变化发生在内部容器，或确保落在用户交互后 500ms 内（规范当「预期位移」排除）。

### 1.7 优先级与持续监控

**结论：先用 RAIL 把超标折算成「用户感受」排优先级，最后必须由现场数据闭环——实验室只对这一次、这一台机器成立。**

RAIL 折算「用户会有什么感受」：Response < 100ms · Animation 每帧 < 16ms（渲染预算 10ms）· Idle 空闲块 > 50ms · Load < 5s。INP 从 150ms 涨到 600ms 优先于 LCP 从 2.4s 涨到 2.8s（后者用户察觉不到）。其中 **A 的 16ms 最容易忽略也最容易验证**：一帧 16.7ms，某段逻辑跑 30ms 就必然掉帧。

总矩阵（行=核心目标、列=分层，格子里是手段，`—` 表示该层基本不服务该指标）：

| 分层 \ 目标 | LCP 加载 | INP 交互 | CLS 视觉 |
| --- | --- | --- | --- |
| 网络层 | preconnect/CDN/HTTP2/优先级 | — | — |
| 构建与产物 | 分包、按需、tree-shaking、gzip/brotli、hash+长缓存 | 少下载=少解析 | — |
| 资源层 | 图片格式/srcset、字体 preload | — | 写死尺寸、回退字体对齐、动态预留 |
| 感知层 | SSR/流式、骨架屏、预取 | 交互后给反馈态 | 骨架屏结构一致 |
| JS 执行 | 阻塞脚本 defer/async | 切片、Worker、换算法 | — |
| 渲染层 | 关键 CSS 内联 | 读写分离、虚拟滚动、rAF 合帧 | transform/opacity |
| 框架层 | 重组件按需引入 | memo、稳定 key、状态下沉 | — |
| 内存长会话 | — | 摘监听、清定时器、缓存设限 | — |

两个读法：**按行**从指标扫全场不漏层；**按列**从手段查归属——一条手段可多格（代码分割同时缩短 LCP 和 INP 两段不同时间），不是重复。

持续监控：Web Vitals 采集上报（CLS 两个口径分开）、看 p75 分布、上线后回看板确认分布真移动了。主体见「监控与稳定性 · 性能与体验监控」。

## 2. 性能优化实战

### 2.1 工程与源码组织

**结论：实验台是两个独立 vite+vue 工程 + 一份共享源码，用「两个工程」保证基线干净、用「共享源码」避免维护腐烂。**

`code/perf-lab`：`apps/before`（优化前：CSS 外链阻塞 + `#app` 空壳 + 四视图静态 import，入口 `raw.html`）与 `apps/after`（优化后：关键 CSS 内联 + 骨架屏 + 动态 import，入口 `index.html`），业务组件与逻辑只有一份在 `shared/`，两边用 `@lab` 别名引入——两工程差异只剩各自的 HTML 入口、`main.js` 与 `vite.config.mjs`。

两个设计决策（照抄时要知道为什么）：

- **为什么拆两个工程**：多入口一起构建时 rollup 把共用模块提到公共 chunk，优化前那份就不再是「一个 bundle 全量包含」的干净基线。
- **为什么源码不复制两份**：两份代码同步维护必然腐烂，比出来的不是「工程决策的差异」而是「两份代码的差异」。

红线（实验台信度根源）：源码里没有一行「为凑差异」的假代码——`report-engine.js` 是 36 指标 + 6 维度 + 透视 / 异常检测 / 导出的真实现（构建后 8.41 kB），它是报表路由的依赖；路由级分割的收益本来就等于「被拆出去多大 × 上首屏概率多低」，拆几个十几行的组件什么都量不出来。开关机制：入口总开关写在 HTML（`window.__PERF_OPT`），单项开关在 query 覆盖，用来做「只改一项」的对照。

### 2.2 实验台怎么跑

**结论：`npm install` 一次装好，`dev:before` / `dev:after` 打开两版对照，读数直接打在控制台，全链路无命令行测量、无服务端。**

`cd code/perf-lab` → `npm install`（workspaces 一次装两个工程）→ `npm run dev:before`（5187/raw.html，优化前）与 `npm run dev:after`（5193/index.html，优化后）对照。

页面自己订阅真实性能条目（paint / LCP / layout-shift / longtask + 每个资源的 `transferSize`），实测打控制台（`[perf-lab] 本次实测`），开 DevTools 看 Console / Network / Performance。要看准确首屏字节 / 二次访问缓存，用 `npm run build` + `preview:before` / `preview:after`。CLS / LCP 想看明显差异 → DevTools → Network 开 Slow 3G。

### 2.3 十二个实验（8 个基础 case + 4 个页面内对照）

**结论：8 个基础 case 覆盖三级指标的定位与手段，4 个页面内对照专攻「要在同一页前后比着看」的框架/字体/动态/动画。**

8 个基础 case：`spa`（首屏关键路径、JS 字节、请求数）· `nav`（切路由：预取开/关）· `agg`（10000 条聚合：同步/分片/Worker）· `scroll`（连滚 30 帧：全量不节流/rAF 节流/虚拟滚动）· `images`（12 张 200KB：立即加载 vs 首屏外懒加载）· `cls`（主图：有无尺寸）· `cache`（同地址访问两次）· `memory`（留引用 vs 可回收，独立页）。

**一次只留一个变量的纪律**：`spa` 两个入口的差异是「整个入口」三处合起来（CSS 外链/内联、`#app` 空壳/骨架屏、静态/动态 import），不把功劳单算给任何一项。**每个 case 的读法**：`spa` 只读首屏 JS 字节与请求数（时间噪声大）；`nav` 本机 RTT 近 0 时差距小，可在 DevTools 加网络延迟放大；`agg` 读「新增长任务 / 最长任务」而不是总耗时；`scroll` 先看前两行（DOM 一样）分清读写的锅；`images` 只算图集本身（主图两版都要下）；`cls` 必须等主图落地才上报；`memory` 唯一不在 SPA 里，需 `--enable-precise-memory-info` 起 Chrome。

**4 个页面内手动对照**（4.3 框架层 / 5.2 字体 / 5.3 动态内容 / 5.4 动画）**不做成命令行 case**——读数要一页里前后对照，自动汇总反而多一层壳。跑法：`dev:after` 后按 `?act=` 打开，读数打控制台：`rerender`（key 稳定 vs 状态下沉：头部插一条行组件渲染 201→1 次；无关状态变一次 201→0）· `banner`（动态预留：位移 240→0px、clsRaw 0.1174→0.0081）· `font`（`size-adjust` 对齐宽度到 0.4% 误差后位移 84→63px——**减不消**，因为位移由离散行数决定）· `anim`（`top` vs `transform`：clsRaw 0.0530→0.0081，帧耗两档无差别）。

### 2.4 按 ROI 排序

**结论：先做零成本/纯写法改动，再做重构件；ROI 从「二次访问归零」一路到「只对首屏外懒加载」。**

长期缓存（零代码成本，二次访问传输归零）→ 读写分离 / rAF 合帧（同一份渲染只换写法，30 帧 3482→989ms，消掉 2528ms 长任务）→ 虚拟滚动（DOM 10029→101）→ 关键 CSS 内联 + CSS 异步 → 路由分割 + 空闲预取（必须成对）→ 长任务分片 / Worker（只有算本身明显超 50ms 才值得）→ 图片懒加载（只对首屏之外、离视口远的图做）。

红线（互相打架处，改一个要连坐）：预取占带宽（放进 `requestIdleCallback`）· 路由拆太细让切路由变卡（配预取）· 骨架屏让 LCP 变绿但用户看不到内容（另配「真实内容渲染完成」指标）。

### 2.5 口径与已知坑

**结论：对照结论要读「差值方向」而不是绝对值；六条已知坑都有明确解，量之前先对口径。**

- **INP 用「最长同步块」近似**：手动点其实能报真正的 INP，但本实验台统一走「最长同步块」口径（计时块里读一次 `offsetHeight` 强制结算布局）便于对照——它**不等于**浏览器上报的 INP。
- **CLS 两个口径**都要打出来（见 1.3）。
- **限速靠 DevTools**：localhost 传 500 KB 只要几毫秒，不放大网络差异，「少一次往返」「图没预留尺寸」这类结论根本显示不出。
- **观测窗口要对齐**：`images` 第一版曾现「懒加载让 LCP 差 4 倍」假象——急加载那版图集秒到就上报、主图（本地静态 SVG）还没画完，两版等到的是不同一件事。
- **数值因机器负载波动，关注差值方向**：无自动化多轮取中位数，结论落在「before → after 哪个数变了」的方向上。
- **CLS 保留 4 位小数**：早期统一压到 1 位，真实值 0.0633 被显示成 0.1000——看起来「刚好卡及格线」实际差得远；时间类各自取整，放宽精度只影响 CLS 这类小量级。
- **CLS 在「换字重排」里不看方向**：字体两版分别位移 84px 与 63px，CLS 却 0.0253 与 0.0292（反了）——重排被拆到几帧结算。量字体位移看像素。
