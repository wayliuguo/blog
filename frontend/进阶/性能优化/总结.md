# 模块总结 · 性能优化

## 知识主线

七篇不是并列的知识点，而是一条闭环：**先定标尺 → 再学会量 → 然后按「加载 / 构建 / 运行时」三条线改 → 最后守住它**。每一篇都在回答上一篇留下的问题：

```
01 性能指标与评估（衡量什么：Core Web Vitals / 辅助指标 / 两种口径 / RAIL） ★主轴
        │  先定下"多快才算快"的标尺，后面所有优化才都有判据
        ▼
02 性能测量工具实操（怎么量：瀑布图 / 火焰图 / Coverage / Memory / 自动化）
        │  它在回答上一篇的什么问题：指标差了，怎么定位到具体是哪一段、哪个函数
        ▼
03 加载与首屏优化（加载线：关键渲染路径 / 资源优先级 / 图片 / 字体 / SSR）
        │  它在回答上一篇的什么问题：瀑布图指出资源在下得慢，具体怎么让首屏更快
        ▼
04 构建侧优化（体积线：代码分割 / tree-shaking / 按需引入 / 压缩）
        │  它在回答上一篇的什么问题：首屏资源砍不动了，怎么让产物本身更少更小
        ▼
05 运行时性能（运行时线：布局抖动 / 长任务 / 重排重绘 / 虚拟滚动 / Worker / 内存）
        │  它在回答上一篇的什么问题：首屏已经够快，但用户点下去卡、滚起来掉帧
        ▼
06 性能优化闭环（守住：预算 / CI 卡口 / 前后对比 / 灰度回归）
        │  它在回答上一篇的什么问题：改完变好了，怎么保证它不再变差
        ▼
07 优化手段速查（取用：逐条手段 + 实测数字 + 什么时候别做）
```

本模块的主轴是**「指标驱动的优化闭环」**：01 定下标尺（LCP / INP / CLS 与 TTFB / FCP / TBT），02 把标尺变成可复现的读数（本仓 `perf-lab`：起无头 Chrome、页面回报、多轮取中位数），03~05 分别沿加载、构建、运行时三条线做优化，每条手段都锚在一个实测数字上，06 把「变好」升级为「不再变差」（预算 + CI 卡口 + 灰度回归），07 把全部手段收成可检索的清单。

这也是本模块与其它模块最大的不同：**每个结论后面都跟着一条能复现的命令**。所有数字来自 `code/perf-lab`（零依赖，用本机无头 Chrome 真跑真测）。

## 分篇知识点

### 01-性能指标与评估

- **指标是一条诊断链路**
  - **时间轴**：TTFB → FP → FCP → LCP → TTI/INP，上游决定下游；FCP 与 DCL 之差看"首屏后还剩多少活"
  - **互相印证**：TBT 大而 LCP 小 = 看得见点不动；LCP 不保证早于 TTI（首屏大图会拖后 LCP）
- **Core Web Vitals**
  - **LCP（最大内容绘制）**：视口内最大内容元素渲染完成，目标 ≤2.5s；由 TTFB + 资源加载延迟 + 加载时长 + 元素渲染延迟四段构成
  - **INP（交互到下次绘制）**：全生命周期代表性交互到下次绘制，目标 ≤200ms，取代只看首次输入的 FID（≤100ms）；根因几乎总是长任务
  - **CLS（累积布局偏移）**：单次分数 = 影响比例 × 位移距离比例，累积目标 ≤0.1；`transform` 不产生位移，改 `top`/`margin` 会
  - **实测**：禁用尺寸预留 + 顶部插横幅 → 0.300（差）；两处都预留 → 0.000（良好）
- **辅助指标按时间轴定位**
  - **FP / FCP**：首次绘制任意像素 / 首次绘制有意义内容，FCP 目标 ≤1.8s；两者差距大说明先铺了背景色
  - **TTFB（首字节）**：串起 DNS/TCP/TLS/服务端处理，目标 ≤800ms，是所有加载指标的上限
  - **TBT（总阻塞时间）**：长任务超出 50ms 的部分之和，目标 ≤200ms，是 INP 的实验室代理
  - **TTI / SI**：可交互时刻与可见内容填充速度（Lighthouse 参考 ≤3.4s）
- **两种口径不能混**
  - **Lab（实验室）**：固定环境、可复现、能看根因，但不代表用户分布
  - **Field / RUM（现场）**：真实用户，噪声大；分工是现场发现问题、实验室定位根因
  - **统一看 p75**，平均值会被长尾带偏
- **评估要套区间**
  - **区间表**：TTFB 800/1800 · FCP 1800/3000 · LCP 2500/4000 · CLS 0.1/0.25 · INP 200/500
  - **评级是门槛不是排名**：LCP 从 8000ms 改到 3000ms 仍是"待改进"，但体感已完全不同；一次只盯一个指标
- **采集的工程细节**
  - **两类来源**：缓冲区直读（TTFB/FP/FCP）与 `PerformanceObserver` 订阅（LCP/CLS/longtask）
  - **`buffered: true`** 才能拿到注册之前已产生的条目
  - **上报时机**：短时指标 `load` 后可报，累积指标等 `visibilitychange` 进隐藏态
  - **采样按用户维度稳定**，比例不必高（性能是分布统计）
  - **`hadRecentInput` 陷阱**：规范口径会剔掉输入后 500ms 内的位移，无头环境里没有输入却仍为 true → 同时留 `cls`（规范）与 `clsRaw`（全量位移）两个口径
- **RAIL 排优先级**
  - **R 响应 <100ms · A 动画 <16ms/帧 · I 空闲块 >50ms · L 加载 <5s**
  - 用法是把"指标超标"折算成"用户会有什么感受"，再决定先改哪个

### 02-性能测量工具实操

- **选工具的标准**
  - **每个工具替你做了不同的决定**：排序（瀑布图）/ 采样（火焰图）/ 统计（Coverage）/ 快照（Memory）/ 打分（Lighthouse）/ 聚合（脚本）
  - **顺序**：先粗粒度定位阶段，再细粒度定位函数
- **瀑布图**
  - **只看三件事**：谁最后结束、谁被挡住、有没有并行度
  - **"发起方"这一列决定资源走不走关键渲染路径**
  - **实测阻塞脚本三种放法**：head 同步 FCP 608ms · head defer 416ms · body 末尾 444ms
- **火焰图（Performance 面板）**
  - **采样主线程调用栈**，用于定位"那 500ms 在跑什么函数"
  - **录制本身有开销**，不要边录边改代码
- **Coverage**
  - **已用字节 / 总字节**，红色部分是能砍掉的代码
  - **实测**：10 个特性只用 3 个，整包 52.6KB vs 按需 19.1KB
- **内存**
  - **核心招式是对比两次堆快照**，看 Delta 只增不减的对象
  - **Detached DOM** 找"不在文档里但被 JS 引用"的节点；**Allocation timeline 全蓝 = 没回收**
  - **实测**：留引用净涨 18.3MB vs 可回收 0.8MB；`performance.memory` 需 `--enable-precise-memory-info`
- **自动化与 Lighthouse**
  - **`child_process` 拉起本机 Chrome + 页面上报**，零依赖拿到可比读数；边界是拿不到 CDP 能力（强制 GC / CPU 降速 / 逐帧截图）
  - **分工**：跨环境对比与 CI 卡口交给脚本，深挖"为什么"交给人开 DevTools
  - **Lighthouse 是固定权重汇总**，版本间分数不可直接比；定位是趋势与短板扫描，不是验收卡口

### 03-加载与首屏优化

- **三段定位**
  - **等（TTFB）**：CDN、缓存命中、服务端渲染时间、连接复用
  - **下（资源）**：减少首屏资源、降体积、调优先级
  - **画（解析渲染）**：关键 CSS、避免长任务与同步布局
- **关键渲染路径**
  - **三类阻塞**：同步 `<script>` 阻塞解析、`<link rel=stylesheet>` 阻塞渲染、`<img>`/字体推迟 LCP
  - **动态 `appendChild` 的 script 默认 `async`**，不阻塞解析——想演示阻塞必须写进 HTML
  - **实测同一慢脚本**：head 同步 FCP 608ms · head defer 416ms · body 末尾 444ms
  - **`async` 不保序**，只适合独立的统计类脚本
- **资源优先级**
  - **四个提前指令**：`preconnect` 建连接 · `dns-prefetch` 只解析 · `preload` 单个高优先级 · `prefetch` 空闲预取
  - **`preload` 只给"关键路径 + 发现得晚"的资源**，否则抢带宽反而更差
  - **`as="font"` 必须配 `crossorigin`**，否则下载两次
  - **首屏图片用 `fetchpriority="high"`** 往往比整链 preload 更好维护
- **图片**
  - **写死尺寸（或 `aspect-ratio`）避免位移**；格式选 WebP/AVIF/SVG；响应式用 `srcset` + `sizes`
  - **实测 12 张 200KB**：全 eager 2.35MB vs 首屏外 lazy 1.57MB（省 33%）
  - **`loading="lazy"` 有约 1250px 预加载距离**，所以视口附近的图仍会请求；**LCP 元素不能加 lazy**
- **字体与关键 CSS**
  - **关键 CSS 内联 + 其余异步**，第一帧不必等外部样式
  - **`font-display: swap` 要配度量接近的回退字体**，否则换字体那一下会变成 CLS
- **改变感受而非时间**
  - **SSR / SSG**：内容提前，代价是 TTFB 上升与 hydration"点不动"
  - **骨架屏**：结构先出，须与真实内容结构一致
  - **流式渲染**：边生成边发，首字节极早；**预取下一页**：只对高概率、小体积目标做

### 04-构建侧优化

- **三个方向**：更少（分割 / 按需）、更小（tree-shaking / 压缩 / 依赖替换）、更合适（传输压缩 / sourcemap / chunk 哈希）
- **代码分割**
  - **实测（1.5 Mbps 限速）**：首屏全量 2069ms vs 按需 767ms，**总字节几乎相同**（347.6KB vs 348.2KB）
  - **它优化的是时序不是体积**：把下载时刻从首屏挪到真正需要时
  - **首屏路由与高频路由不该懒加载**；低频页面适合，且必须配 loading 兜底
- **tree-shaking**
  - **三个前提**：ESM 静态结构、无副作用（`sideEffects: false`）、静态访问
  - **CJS 的 `require` 无法静态分析**，只能整块保留
  - **只摇"没被引用的导出"**，不摇"没执行到的分支"（`if (false)` 里的代码照样打进去）
- **按需引入**
  - **实测**：10 个特性只用 3 个，整包 52.6KB vs 按需 19.1KB（砍 63%）
  - **三个层级**：入口级（路由懒加载）、模块级（动态 `import` + `sideEffects`）、依赖级（组件库子路径、moment→dayjs、polyfill 按需）
- **压缩与产物**
  - **gzip 必开（约 -70%），brotli 再小 15%~20%**，只对文本有效
  - **生产环境不部署 sourcemap**，改为上传监控平台供错误反解
  - **vendor 拆分 + 内容哈希**提升缓存命中，但别拆太碎
  - **确认改对了**：逐 chunk 的 gzip 体积 diff + Coverage 复核，能抓出"插件没生效"

### 05-运行时性能

- **两个标尺**
  - **单帧 16ms**：脚本 + 样式 + 布局 + 绘制必须挤进 16.7ms
  - **长任务 50ms**：超过就是长任务，期间用户输入无法被处理（INP 恶化的直接原因）
- **强制同步布局**
  - **写样式后立刻读 `offsetWidth` 等依赖布局的属性**，逼浏览器当场重算
  - **实测 2000 个盒子**：交错读写 4794ms / 2000 次布局 vs 集中读写 4ms / 1 次（**1115 倍**）
  - **三种解法**：读提前写后置、用缓存代替读、批量写延到下一帧
- **长任务与切片**
  - **实测 60000 行**：一次做完 737ms 单块 / 首屏 737ms；切片 10 片 / 最长块 144ms / 首屏 162ms
  - **切片让总耗时变长**（1152ms），换的是最长块与首屏可见
  - **让出机制**：`MessageChannel` 首选、`scheduler.postTask` 现代最佳、**`Promise.then` 无效**（微任务不让出渲染）
  - **只能切独立工作单元**，单个超长任务切不动
- **重排、重绘与合成**
  - **几何属性 → 布局**；**绘制属性 → 重绘**；**`transform`/`opacity` → 只合成**
  - 动画只用 `transform`/`opacity`；`will-change` 别滥用（层多了显存与合成开销上升）
- **长列表**
  - **实测 10000 行**：DOM 10012 → 39 节点（-99.6%）、首屏 14ms → 1ms、大跨度滚动 288ms → 13ms、堆 1421KB → 615KB
  - **代价**：每次滚动重算窗口、不定高列表的滚动锚定问题
  - **用 `IntersectionObserver` 而不是 `scroll` 回调**
  - **虚拟滚动解决"DOM 太多"，不解决"计算太重"**
- **Worker**
  - **实测 1200 万次循环**：主线程最长帧间隔 200ms / 19 帧 vs Worker 17ms / 32 帧
  - **计算本身没变快**，变的是"谁被占用"
  - **边界**：结构化克隆有成本、Worker 里没有 DOM、启动成本适合一次重活
  - **判断标准**：与 DOM 无关 + 单次超过 50ms
- **内存**
  - **实测**：留引用净涨 18.3MB vs 可回收 0.8MB
  - **四类常见泄漏**：事件监听没摘、定时器没清、只增不减的全局缓存、闭包绑住大对象

### 06-性能优化闭环

- **闭环四环节**
  - **定基线 → 定预算 → 卡卡口 → 回归验证**；最容易跳过的是定基线与回归验证
  - **性能是水位线不是一次性任务**：劣化通常来自非性能需求的累积（多引一个库、多埋一段逻辑）
- **性能预算**
  - **从现状出发**（基线的作用是"不许更差"而非"合格"）、留一点余量、每轮优化后逐步收紧
  - **覆盖用户能感知的指标**：LCP/FCP/TTFB/TBT、CLS、首屏 JS 体积、请求数与长任务数
  - **预算必须分级**（首屏严、次要页面松）；**别把 Lighthouse 总分当卡口**（固定权重会随版本变）
- **CI 卡口**
  - **卡口与预算的差别是"退出码"**：超线 `exit 1`，PR 不允许合并
  - **确定性指标（体积 / chunk 数 / 请求数）可以卡死**
  - **统计性指标（LCP/FCP/TBT）有抖动**，用多轮中位数 + 宽松阈值（约 +20%），只拦断崖式劣化
  - **实测**：TTFB 142ms / FCP 524ms / LCP 524ms 全 PASS，JS 字节 467.9KB 超 300KB 预算 → 退出码 1
- **前后对比的四个案例**
  - **脚本改 defer**：FCP / LCP 608ms → 416ms（-32%）
  - **图片 lazy**：2.35MB → 1.57MB（-33%），**LCP 不变**——懒加载不改善首屏
  - **长列表虚拟滚动**：DOM 10012 → 39、滚动 288ms → 13ms、堆 -57%，代价是窗口计算与滚动锚定复杂度
  - **路由按需加载**：首屏 2069ms → 767ms，总字节不变——时序优化不是体积优化
  - **报告必须写清"手段 / 指标变化 / 代价 / 边界"**
- **回归验证**
  - **灰度放量**（5% → 20% → 50% → 100%），对比新旧版本**分位数**（p75 / p95）而非平均值
  - **两类信号**：没变好（还有别的瓶颈）与变差了（如 preload 抢带宽）
  - **看分布形状**：平均值相同但 p95 变差 = 少数人明显更差
  - **上报自身也有体积与开销成本**
- **固化**
  - **预算进仓库 · 卡口进 CI · 看板带基线 · 劣化归因到提交**（缺最后一环就只能停留在"变差了"）

### 07-优化手段速查

- **用法**：排障反查（指标差 → 对应手段）· 评审对账（手段改善的指标是否等于目标指标）· 报告取数（每条都有可复现命令）
- **加载与首屏**：`defer`（608→416ms）· 图片 lazy（2.35→1.57MB，LCP 不变）· 路由分割（2069→767ms）· 关键 CSS 内联 · `fetchpriority` · `preconnect` · 字体 `swap` · SSR/流式/骨架
- **资源与体积**：按需引入（52.6→19.1KB）· tree-shaking · 依赖替换 · gzip/brotli · 图片格式与 `srcset` · vendor 拆分与内容哈希 · sourcemap 不上线
- **运行时与渲染**：读写分离（4794→4ms）· 长任务切片（737→144ms 最长块）· 虚拟滚动（DOM 10012→39）· Worker（帧间隔 200→17ms）· 合成层动画 · 事件委托 · `IntersectionObserver`
- **内存**：摘监听 · 清定时器 · 缓存加上限 · 避免闭包绑大对象（实测 18.3MB vs 0.8MB）
- **闭环**：预算进仓库 · 卡口进 CI · 看板带基线 · 分位数而非平均值 · 归因到提交 · 灰度对比
- **反面清单**
  - **Promise 切片无效**（微任务不让出渲染）· **首屏图别 lazy** · **无脑 preload 有害** · **动态 `appendChild` 不阻塞**
  - **空 localhost 不限速比不出差别** · 单次测量不可信 · 别只看 Lighthouse 总分
  - **虚拟滚动不减少计算量** · 别用平均值汇报性能
