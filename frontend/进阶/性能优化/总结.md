## 1. 性能指标与测量

### 1.1 指标时间轴与诊断链路

性能指标不是一堆孤立数字，而是一条**诊断链路**：

```
时间轴      TTFB → FP → FCP → LCP → TTI / INP
              │      │     │     │
              上游决定下游，越靠前越可能是瓶颈的家
互相印证    TBT 大而 LCP 小 = 看得见点不动
            LCP 不保证早于 TTI（首屏大图会拖后 LCP）
```

- **上游决定下游**：TTFB 差，后面所有加载指标的上限都被拉高，先优化下游无效。
- **FCP 与 DCL 之差**：看"首屏渲染完还剩多少活"。

### 1.2 Core Web Vitals：LCP / INP / CLS

**LCP（最大内容绘制）**：视口内最大内容元素渲染完成的时刻，目标 **≤2.5s**。由四段构成：

```
LCP = TTFB + 资源加载延迟 + 加载时长 + 元素渲染延迟
```

**INP（交互到下次绘制）**：全生命周期**代表性**交互到下次绘制，目标 **≤200ms**；取代只测首次输入的 FID（≤100ms）。根因几乎总是长任务。

**CLS（累积布局偏移）**：

```
单次位移分数 = 影响比例 × 位移距离比例  目标累积 ≤0.1
影响比例   位移前后占据的视口区域并集 / 视口面积
位移距离    移动距离 / 视口高度；判定看元素起始位置是否变化
```

| 要点 | 说明 |
| ---- | ---- |
| `transform` | 不产生位移，动画不产生 CLS |
| 改 `top` / `margin` | 改变布局位置，会积累 CLS |
| 实测 | 禁用尺寸预留 + 顶部插横幅 → 0.300（差）；两处都预留 → 0.000（良好） |

### 1.3 辅助指标与 RAIL

辅助指标沿**时间轴**定位瓶颈段：

| 指标 | 含义 | 目标 |
| ---- | ---- | ---- |
| FP / FCP | 首次绘制任意像素 / 首次绘制有意义内容 | FCP ≤1.8s |
| TTFB | 首字节，串起 DNS/TCP/TLS/服务端处理 | ≤800ms，是加载上限 |
| TBT | 长任务超出 50ms 的部分之和 | ≤200ms，INP 的实验室代理 |
| TTI / SI | 可交互时刻 / 内容填充速度 | Lighthouse 参考 ≤3.4s |

> FP 与 FCP 差距大，说明先铺了背景色。

**RAIL 以用户感受为中心**，把"指标超标"折算成"用户会有什么感受"，再决定先改哪个：

```
R 响应    <100ms       点一下要有反馈
A 动画    <16ms/帧    一帧 16.7ms，跑 30ms 必然掉帧
I 空闲    >50ms 块    空闲分块给后台活
L 加载    <5s         冷启动尽快可用
```

### 1.4 Lab 与 Field 两种口径

两种数据不是二选一，是**分工**：

```
Lab / 实验室    固定环境、可复现、能看根因（火焰图），但不代表用户分布
Field / RUM    真实用户，反映真实网络与设备，但噪声大、看不出根因
分工            现场发现问题 → 实验室定位根因 → 改完回现场验证
```

**统一看分位数（p75）**，平均值会被长尾带偏——少数极差用户拖高均值，掩盖多数人的真实体验。

**评估要套区间、按门槛理解**：

```
区间表   TTFB 800/1800 · FCP 1800/3000 · LCP 2500/4000 · CLS 0.1/0.25 · INP 200/500
评级是门槛不是排名   LCP 从 8000ms 改到 3000ms 仍是"待改进"，但体感已完全不同
一次只盯一个指标
```

### 1.5 采集与上报的工程细节

**两类来源**：

```
缓冲区直读            TTFB / FP / FCP（加载后直接读）
PerformanceObserver  LCP / CLS / longtask（订阅式）
```

- **`buffered: true`** 才能拿到注册之前已产生的条目。
- **上报时机**：短时指标 `load` 后可报；累积指标（CLS）等 `visibilitychange` 进隐藏态再报。
- **采样按用户维度稳定**，比例不必高——性能是分布统计。
- **`hadRecentInput` 陷阱**：规范口径会剔掉输入后 500ms 内的位移；无头环境里没有输入，`hadRecentInput` 却仍为 `true` → 同时留 `cls`（规范口径）与 `clsRaw`（全量位移）两个字段。

### 1.6 测量工具实操

**选工具的标准**：每个工具替你做了**不同的决定**——排序（瀑布图）/ 采样（火焰图）/ 统计（Coverage）/ 快照（Memory）/ 打分（Lighthouse）/ 聚合（脚本）。顺序是**先粗粒度定位阶段，再细粒度定位函数**。

**瀑布图**：只看三件事——谁最后结束、谁被挡住、有没有并行度；"发起方"这一列决定资源走不走关键渲染路径。

**火焰图（Performance 面板）**：采样主线程调用栈，定位"那 500ms 在跑什么函数"；**录制本身有开销，不要边录边改代码**。

**Coverage**：`已用字节 / 总字节`，红色部分就是能砍掉的代码；实测 10 个特性只用 3 个，整包 52.6KB vs 按需 19.1KB。

**内存**：核心招式是**对比两次堆快照**看 Delta，只增不减的对象就是泄漏；Detached DOM 找"不在文档里但被 JS 引用"的节点；实测留引用净涨 18.3MB vs 可回收 0.8MB；`performance.memory` 需 `--enable-precise-memory-info`。

**自动化与 Lighthouse**：

```
child_process 拉起本机 Chrome + 页面上报   零依赖拿到可比读数
边界           拿不到 CDP 能力（强制 GC / CPU 降速 / 逐帧截图）
分工           跨环境对比与 CI 卡口交脚本；深挖"为什么"人开 DevTools
Lighthouse     固定权重汇总，版本间分数不可直接比；定位是趋势与短板扫描，不是验收卡口
```

## 2. 加载与首屏优化

### 2.1 三段定位

把首屏慢拆成三段，先定位再动手：

```
等（TTFB）    CDN、缓存命中、服务端渲染时间、连接复用
下（资源）    减少首屏资源、降体积、调优先级
画（解析渲染） 关键 CSS、避免长任务与同步布局
```

### 2.2 关键渲染路径

**三类阻塞**：

```
同步 <script>          阻塞解析
<link rel=stylesheet>  阻塞渲染
<img> / 字体           推迟 LCP（元素渲染延迟）
```

- **动态 `appendChild` 的 script 默认 `async`**，不阻塞解析——想演示阻塞必须写进 HTML。
- **实测同一慢脚本**：head 同步 FCP 608ms · head defer 416ms · body 末尾 444ms。
- **`async` 不保序**，只适合独立的统计类脚本。

### 2.3 资源优先级

**四个提前指令**：

| 指令 | 作用 |
| ---- | ---- |
| `preconnect` | 提前建连接 |
| `dns-prefetch` | 只做 DNS 解析 |
| `preload` | 单个高优先级资源提前下 |
| `prefetch` | 空闲时预取下一页 |

- **`preload` 只给"关键路径 + 发现得晚"的资源**，否则抢带宽反而更差。
- **`as="font"` 必须配 `crossorigin`**，否则下载两次。
- 首屏图片用 `fetchpriority="high"` 往往比整链 preload 更好维护。

### 2.4 图片优化

- **写死尺寸（或 `aspect-ratio`）避免位移**；格式选 WebP/AVIF/SVG；响应式用 `srcset` + `sizes`。
- **实测 12 张 200KB**：全 eager 2.35MB vs 首屏外 lazy 1.57MB（省 33%）。
- **`loading="lazy"` 有约 1250px 预加载距离**，视口附近的图仍会请求——LCP **完全不变**。
- **LCP 元素不能加 lazy**（会被降到 Low 优先级，LCP 直接变差）；首屏大图配 `fetchpriority="high"`。

### 2.5 字体与关键 CSS

- **关键 CSS 内联 + 其余异步**，第一帧不必等外部样式表。
- **`font-display: swap` 要配度量接近的回退字体**，否则换字体那一下变成 CLS。

### 2.6 改变感受而非时间

优化目标是**体验**，有时不缩短真实时间、只改变感受：

```
SSR / SSG       内容提前，代价是 TTFB 上升与 hydration"点不动"
骨架屏          结构先出，须与真实内容结构一致
流式渲染        边生成边发，首字节极早
预取下一页      只对高概率、小体积目标做
```

## 3. 构建侧优化

### 3.1 三个方向与代码分割

构建侧三个方向：**更少**（分割 / 按需）、**更小**（tree-shaking / 压缩 / 依赖替换）、**更合适**（传输压缩 / sourcemap / chunk 哈希）。

**代码分割**：

```
实测（1.5 Mbps 限速）  首屏全量 2069ms vs 按需 767ms
总字节几乎相同          347.6KB vs 348.2KB
它优化的是时序不是体积  把下载时刻从首屏挪到真正需要时
```

- 首屏路由与高频路由**不该懒加载**；低频页面适合，且必须配 loading 兜底。

### 3.2 tree-shaking

**三个前提**：

```
ESM 静态结构       import/export 可静态分析
无副作用           sideEffects: false 允许删除
静态访问           不用 import * as 后动态取值
```

- **CJS 的 `require` 无法静态分析**，只能整块保留。
- **只摇"没被引用的导出"，不摇"没执行到的分支"**——`if (false) { heavy() }` 里的代码照样打进去。

### 3.3 按需引入

- **实测**：10 个特性只用 3 个，整包 52.6KB vs 按需 19.1KB（砍 63%）。
- 三个层级：

```
入口级    路由懒加载
模块级    动态 import + sideEffects
依赖级    组件库子路径、moment→dayjs、polyfill 按需
```

### 3.4 压缩与产物

- **gzip 必开（约 -70%），brotli 再小 15%~20%**，只对文本有效。
- 生产环境**不部署 sourcemap**，改为上传监控平台供错误反解。
- **vendor 拆分 + 内容哈希**提升缓存命中，但别拆太碎。
- **确认改对了**：逐 chunk 的 gzip 体积 diff + Coverage 复核，能抓出"插件没生效"。

## 4. 运行时性能

### 4.1 两个标尺：单帧 16ms 与长任务 50ms

```
单帧 16ms   脚本 + 样式 + 布局 + 绘制必须挤进 16.7ms
长任务 50ms 超过即长任务，期间用户输入无法被处理（INP 恶化的直接原因）
```

### 4.2 强制同步布局

**定义**：写样式后**立刻读**依赖布局的属性（`offsetWidth` / `getBoundingClientRect` / `getComputedStyle`），逼浏览器当场重算。

- **原理**：浏览器默认攒批——样式改动记下、等这轮 JS 跑完统一算一次布局；读操作要求"读值正确"，必须先把刚才的改动算进去，攒批被打破。
- **实测 2000 个盒子**：交错读写 4794ms / 2000 次布局 vs 集中读写 4ms / 1 次（**1115 倍**）。
- **三种解法**：

```
读提前写后置      先把要读的值都读了，再统一改样式
用缓存代替读      记录上次值，避免每回调都读
批量写延到下一帧   rAF 合帧，一轮只算一次布局
```

### 4.3 长任务与切片

- **实测 60000 行**：一次做完 737ms 单块 / 首屏 737ms；切片 10 片 / 最长块 144ms / 首屏 162ms。
- **切片让总耗时变长**（737→1152ms），换的是"最长卡顿"与"首屏可见"。
- **让出机制**：

```
MessageChannel     首选（稳定的宏任务让出）
scheduler.postTask 现代最佳
Promise.then       无效——微任务在当前宏任务结束前全跑完，不插渲染帧
```

- **只能切独立工作单元**，单个超长任务切不动。

### 4.4 重排、重绘与合成

```
几何属性（width/margin/font-size） → 布局（最贵）
绘制属性（color/background）        → 重绘
transform / opacity               → 只合成（性能最好）
```

- 动画只用 `transform` / `opacity`。
- **`will-change` 别滥用**：会为元素提升合成层，层多了显存与合成开销上升；动画前加、结束后撤掉。

### 4.5 长列表与虚拟滚动

**原理**：只渲染可视窗口 + 缓冲区，用一根撑高的占位元素模拟完整滚动高度：

```
scrollTop / 行高 → 算起始行
渲染 [start - buffer, start + window + buffer) 区间
用 top 偏移放到正确位置
```

- **实测 10000 行**：DOM 10012 → 39 节点（-99.6%）、首屏 14ms → 1ms、大跨度滚动 288ms → 13ms、堆 1421KB → 615KB。
- **代价**：每次滚动重算窗口、不定高列表的滚动锚定问题。
- 用 `IntersectionObserver` 而不是 `scroll` 回调。
- **虚拟滚动解决"DOM 太多"，不解决"计算太重"**。

### 4.6 Web Worker

- **实测 1200 万次循环**：主线程最长帧间隔 200ms / 19 帧 vs Worker 17ms / 32 帧。
- **计算本身没变快**（189 vs 191ms），变的是"谁被占用"——主线程空出来照常响应输入与出帧。
- **边界**：`postMessage` 结构化克隆有成本、Worker 里没有 DOM、启动成本适合一次重活。
- **判断标准**：与 DOM 无关 + 单次超过 50ms。

### 4.7 内存与泄漏

- **实测**：留引用净涨 18.3MB vs 可回收 0.8MB——差别只在"还有没有引用指向它"。
- **四类常见泄漏**：

```
事件监听没摘
定时器没清
只增不减的全局缓存
闭包绑住大对象（把对象挂在长生命周期上）
```

## 5. 性能优化闭环

### 5.1 闭环四环节

```
定基线 → 定预算 → 卡卡口 → 回归验证
```

- 最容易跳过的是**定基线**与**回归验证**。
- **性能是水位线不是一次性任务**：劣化通常来自非性能需求的累积（多引一个库、多埋一段逻辑）。

### 5.2 性能预算

- **从现状出发**：基线的作用是"不许更差"而非"合格"；留一点余量，每轮优化后逐步收紧。
- **覆盖用户能感知的指标**：LCP / FCP / TTFB / TBT、CLS、首屏 JS 体积、请求数、长任务数。
- **预算必须分级**（首屏严、次要页面松）。
- **别把 Lighthouse 总分当卡口**：固定权重会随版本变。

### 5.3 CI 卡口

- **卡口与预算的差别是"退出码"**：超线 `exit 1`，PR 不允许合并。

```
确定性指标（体积 / chunk 数 / 请求数）  可以卡死
统计性指标（LCP / FCP / TBT）有抖动    多轮中位数 + 宽松阈值（约 +20%），只拦断崖式劣化
```

- **实测**：TTFB 142ms / FCP 524ms / LCP 524ms 全 PASS，JS 字节 467.9KB 超 300KB 预算 → 退出码 1。

### 5.4 前后对比与灰度回归

**前后对比的四个案例**：

| 手段 | 指标变化 |
| ---- | ---- |
| 脚本改 defer | FCP / LCP 608ms → 416ms（-32%） |
| 图片 lazy | 2.35MB → 1.57MB（-33%），**LCP 不变**——懒加载不改善首屏 |
| 长列表虚拟滚动 | DOM 10012 → 39、滚动 288ms → 13ms、堆 -57% |
| 路由按需加载 | 首屏 2069ms → 767ms，总字节不变——时序优化不是体积优化 |

- **报告必须写清"手段 / 指标变化 / 代价 / 边界"**。

**回归验证**：

```
灰度放量          5% → 20% → 50% → 100%
对比分位数         新旧版本 p75 / p95，而非平均值
两类信号           没变好（还有别的瓶颈）与变差了（如 preload 抢带宽）
看分布形状         平均值相同但 p95 变差 = 少数人明显更差
上报成本           上报自身也有体积与开销
```

### 5.5 固化

```
预算进仓库
卡口进 CI
看板带基线
劣化归因到提交   缺这一环就只能停留在"变差了"
```

## 6. 优化手段速查

### 6.1 手段速查清单

**用法**：排障反查（指标差 → 对应手段）· 评审对账（手段改善的指标是否等于目标指标）· 报告取数（每条都有可复现命令）。

```
加载与首屏   defer（608→416ms）· 图片 lazy（2.35→1.57MB，LCP 不变）· 路由分割（2069→767ms）
             关键 CSS 内联 · fetchpriority · preconnect · 字体 swap · SSR/流式/骨架
资源与体积   按需引入（52.6→19.1KB）· tree-shaking · 依赖替换 · gzip/brotli
             图片格式与 srcset · vendor 拆分与内容哈希 · sourcemap 不上线
运行时与渲染  读写分离（4794→4ms）· 长任务切片（737→144ms 最长块）· 虚拟滚动（DOM 10012→39）
             Worker（帧间隔 200→17ms）· 合成层动画 · 事件委托 · IntersectionObserver
内存         摘监听 · 清定时器 · 缓存加上限 · 避免闭包绑大对象（实测 18.3MB vs 0.8MB）
闭环         预算进仓库 · 卡口进 CI · 看板带基线 · 分位数而非平均值 · 归因到提交 · 灰度对比
```


### 6.3 Vue SPA 性能实战

**形态**：一个真的 Vue 3 SPA（hash 路由 + 3 个路由模块 + 2000 条订单），每个手段是独立开关——否则无法归因。

**加载**：关键 CSS 内联 + 全量 CSS 异步（`media="print"`）· `modulepreload` · 骨架屏（FCP 508→224ms、首屏有内容 247→94ms、关键路径 JS 10→7 个）。

**陷阱**：LCP 落在骨架屏上（336ms）——指标变绿但用户还没看到内容，必须配「内容就绪」自定义指标；路由分割省的是**业务代码不是体积**（152.2→149.1KB，Vue 运行时占 131.5KB）。

**切路由**：

```
全量打包 69ms / 分割不预取 245ms / 分割+空闲预取 80ms（150ms RTT 下）
只做分割是拿 176ms 切换等待换 3KB 首屏，预取必须成对做
```

**运行时与滚动**：排序交互到下一帧 134ms（全量渲染）→ 31ms（虚拟滚动）→ 28ms（+分片）；逐行读写 3985ms / 最长任务 3035ms → rAF 读写分离 1007ms / 0 个——改法是**读写分离**不是"少滚几次"。

**缓存**：无缓存 289→278ms · HTTP 强缓存 266→122ms（传输 0B）· SW 276→205ms（传输 0B）；SW 比 HTTP 缓存慢 ~80ms（冷启动 + 每请求过 fetch），价值在**离线**与按资源分策略。

**实验坑**：HTTP 缓存按 origin 存，端口随机会造成"缓存没生效"假象 → 缓存场景必须固定端口；无头环境没有真实输入，INP 只能近似。

**ROI 顺序**：长期缓存 > 虚拟滚动 > 关键 CSS 内联 > 分割 + 预取 > 计算分片 > SW。
