## 1. 性能优化总纲与指标量化

模块主线：**先量化指标 → 定位瓶颈 → 分层优化 → 持续监控**。核心目标只有三个，就是 Core Web Vitals；其余指标是诊断用的辅助指标。

### 1.1 整体思路与三个核心目标

三个核心目标与指标一一对应：加载性能 → LCP ≤ 2.5s、交互响应 → INP ≤ 200ms、视觉稳定 → CLS ≤ 0.1，统一看 p75。后面三篇每篇服务一个核心目标，结构统一为「先定位 → 分层手段」。

### 1.2 核心指标：LCP / INP / CLS

LCP 是视口内最大内容元素渲染完成的时刻，由 TTFB + 资源加载延迟 + 资源加载时长 + 元素渲染延迟四段构成。INP 是全程代表性交互到下次绘制，取代只看首次输入的 FID。CLS 是所有单次位移分数之和，单次分数 = 影响比例 × 位移距离比例。

### 1.3 辅助指标与诊断链路

TTFB → FP → FCP → LCP → TTI 构成时间轴，TBT 在 FCP 与 TTI 之间累积。辅助指标的价值是**定位**：把核心指标的差拆到具体阶段。要点是「上游决定下游」——TTFB 差时优化下游无效；「一个数不构成结论」——要几个指标互相印证。

### 1.4 两种口径、分位数与评级区间

实验室（Lab）可复现、能看火焰图定位；现场（Field / RUM）反映真实分布。分工是现场发现问题、实验室定位根因。性能是长尾分布，一律看 p75 而非平均值。评级是门槛不是排名。

### 1.5 采集代码与上报

指标分两类：能从缓冲区直接读的（TTFB / FP / FCP）与必须订阅的（LCP / CLS / 长任务）。订阅统一走 `PerformanceObserver` 并开 `buffered: true`。**上报时机最容易做错**：LCP 与 CLS 会变到用户离开为止，必须等页面隐藏再报。

### 1.6 CLS 的双口径

`hadRecentInput` 会把交互后 500ms 内的位移排除，而无头环境里它恒为 `true`，导致规范口径 CLS 恒为 0。所以留两个值：`cls` 用于上报，`clsRaw` 用于对照实验。

### 1.7 测量工具与排查表

选工具的标准只有一条：它替你做了什么决定。顺序是**先用粗粒度工具定位阶段，再用细粒度工具定位函数**。Lighthouse 是固定权重汇总，只能当趋势与短板扫描，不能当验收卡口。

### 1.8 RAIL：先改哪个

Response < 100ms、Animation 每帧 < 16ms、Idle 空闲块 > 50ms、Load < 5s。用法是把指标超标程度折算成「用户会有什么感受」，按感受排优先级。

## 2. 加载性能与 LCP

### 2.1 先定位：LCP 卡在哪一段

「等、下、画」三段对应不同判断依据：TTFB 高去查服务端与 CDN；瀑布图里资源条又长又靠右去查资源；资源都到了 FCP 仍晚去查阻塞渲染的 CSS 与长任务。关键渲染路径上只有三类资源会卡住第一帧：无 `defer`/`async` 的 script、样式表、以及动态插入的 script（默认 `async`，不阻塞）。

### 2.2 网络层

不改变资源本身，只改变「什么时候开始下」和「浏览器有多重视它」。`preconnect` / `dns-prefetch` / `preload` / `prefetch` 分工不同；`preload` 只解决「发现得晚」不解决「太大」，用错会抢首屏带宽。首屏图可直接标 `fetchpriority="high"`。

### 2.3 构建与产物层

改善 LCP 里「资源加载时长」那一段。路由级代码分割把「什么时候下」从首屏挪到真正需要时（首屏 2069ms → 767ms，总字节不变）。tree-shaking 的三条硬规则：必须 ESM、不能被副作用绑住、访问方式要静态。按需引入分入口级 / 模块级 / 依赖级三层。压缩用 gzip（~70%）或 brotli（再小 15%~20%）。

### 2.4 资源层

图片是首屏最大的单块。三层手段：尺寸与格式（写死 `width`/`height`、WebP/AVIF）、响应式（`srcset` + `sizes`）、懒加载（`loading="lazy"` 有约 1250px 预加载距离，收益是「远离首屏的不抢带宽」，**不改善 LCP**）。字体默认有最长 3s 不可见期。

### 2.5 感知层

时间减不到零就改变感受：SSR / SSG、骨架屏、流式渲染、预取下一页。它们改变的是 LCP 元素**是什么**（从 JS 渲染的内容变成 HTML 里的内容），可以让 LCP 早到 TTFB 附近。骨架屏必须结构与真实内容一致。

## 3. 交互性能与 INP

### 3.1 先定位：INP 差在哪一段

INP = 输入延迟 + 处理时间 + 呈现延迟。有长任务 → 输入延迟，去 JS 执行层；火焰图里回调自身是宽条 → 处理时间，去 JS 执行层或框架层；回调很快返回但紧跟大范围 Layout → 呈现延迟，去渲染层。

### 3.2 JS 执行层

长任务切片的机制有讲究：`Promise.then` 是微任务，**做切片无效**；首选 `MessageChannel` 或 `scheduler.postTask`。切片让总耗时变长（737ms → 1152ms）但最长同步块 737ms → 144ms、首屏可见 737ms → 162ms。判断挪 Worker 的标准：与 DOM 无关且单次超 50ms。

### 3.3 渲染层

强制同步布局：读写交错 2000 次耗时 4794ms，集中读写 4ms，差 1115 倍。属性按触发深度分三级，动画只用 `transform` / `opacity`。虚拟滚动把 DOM 从 10012 降到 39，但它**解决 DOM 太多，不解决计算太重**。

### 3.4 框架层

问题通常不是「某个函数慢」，而是「同一段渲染被执行了很多次」。React 用 `memo` / `useMemo` / `useCallback` 切断传播链；Vue 用 `shallowRef` / `markRaw` / `v-memo`，并把复杂表达式抽成 computed。两侧通用：稳定的 `key`、状态下沉、重组件按需引入。

### 3.5 内存与长会话

四类泄漏全是「还留着引用」：监听没摘、定时器没清、全局缓存只增不减、闭包绑住大对象。留引用的一版净涨 18.3MB 且从不回落，可回收的一版在 3MB 附近波动。

## 4. 视觉稳定与 CLS

### 4.1 先定位：位移归因

判定规则：**CLS 只看元素的起始位置有没有变化**。归因靠「时刻」——接近 LCP 的是图片/字体；接口返回后的是动态插入；交互后 500ms 内属于预期位移不计入。

### 4.2 尺寸与预留

给媒体元素在 HTML 里写 `width` / `height`（不是 CSS），浏览器会自动算 `aspect-ratio`。`iframe` 与广告位用 `min-height` 占位。判据：图片还没开始下载时，那个位置的高度就已经是对的。

### 4.3 字体

`font-display` 四个取值里 `swap` 是正文首选，但换字那一下会重排。两条解法：用 `size-adjust` / `ascent-override` 让回退字体度量接近；把字体 `preload`（`as="font"` 必须带 `crossorigin`）。

### 4.4 动态内容

绝不在已有内容「上方」插入元素——一次 240px 横幅插到 `body` 最前面就贡献 0.1922。骨架屏必须与真实内容结构一致。这类问题在开发环境通常看不见，必须限速复现。

### 4.5 动画与交互

`transform` 不改变布局位置，不产生 CLS 且只走合成；改 `top` / `margin` / `height` 会算进位移并触发整条渲染流水线。`will-change` 别滥用。

## 5. 性能优化闭环

### 5.1 闭环四环节

定基线 → 定预算 → 卡卡口 → 回归验证。性能不是一次性任务，是一条需要守住的水位线。

### 5.2 性能预算

从现状出发，不是从理想出发；留余量，逐步收紧。

### 5.3 CI 卡口

确定性指标卡死，统计性指标用多轮中位数 + 宽松阈值。预算脚本超线时退出码为 1，可直接接进流水线。

### 5.4 前后对比与灰度回归

实验室变好 ≠ 用户变好。灰度 5% → 20% → 50% → 100%，对比新旧版本分位数。

### 5.5 固化

把预算写进仓库、看板带基线、劣化归因到提交。缺了「归因到提交」这一环，就只能停留在「变差了」。

### 6.3 按层的手段清单

每条手段给出「改哪个指标 / 实测效果 / 什么时候别做」。所有数字来自 `code/perf-lab`。

### 6.4 反面清单

用 Promise 做切片、给首屏图加 `lazy`、无脑 `preload`、只看 Lighthouse 总分、不限速比快慢、拿单次测量下结论、用平均值汇报——这些都是实测能证伪的。
