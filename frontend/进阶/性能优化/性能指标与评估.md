# 性能指标与评估

优化性能时最容易犯的错，是把「指标」当名词背下来就以为学会了——LCP ≤ 2.5s、CLS ≤ 0.1、INP ≤ 200ms，背得很熟，但线上 LCP 是 1.2s 还是 5.8s 却说不上来，更不知道这个数是怎么量出来的。

这一篇换一条路：指标、区间、采集代码三层一起走一遍，每一层都能在本仓的实验台上跑出真实数字。所有读数都来自 `code/perf-lab`（零依赖，用本机无头 Chrome 真跑真测）。

## 一、指标不是一串数字，是一条诊断链路

一个页面从被请求到用户能顺畅操作，中间隔着一串阶段。每个指标负责定位其中一个阶段：

```
请求发出 ──► 首字节到达 ──► 首次绘制 ──► 首次有意义内容 ──► 最大内容元素 ──► 可交互 ──► 交互响应
   TTFB ────────┘              FCP ────────┘        LCP ─────────┘       TTI ────┘   INP
                                                                             ▲
                              整个过程里「主线程被长任务占住的时间」= TBT ──────┘
                              整个过程里「内容意外跳动」的累积 = CLS
```

这张图有三个用法：

1. **上游决定下游**。TTFB 是 3 秒，后面的 FCP / LCP 不可能好到哪去——先修上游。实测里「未治理首屏」TTFB 只有 160 ms，问题全在后面（阻塞脚本），这时去优化服务端毫无收益。
2. **指标之间要互相印证**。FCP 与 DCL 的差距说明「首屏画出来后还剩多少解析/执行工作」；TBT 大而 LCP 小说明「看得见但点不动」。
3. **一个数不构成结论**。单看 LCP = 2.6s 只能说「不太行」，把 TTFB / FCP / 资源瀑布摆在一起才能说出「是资源下得慢还是被脚本挡住了」。

## 二、Core Web Vitals：三个维度各管什么

Core Web Vitals 是 Google 挑出来的三个「直接对应用户感受」的指标，覆盖加载、交互、视觉稳定三个维度，也是搜索排名里页面体验的参考。

| 维度 | 指标 | 回答的问题 |
| --- | --- | --- |
| 加载 | LCP | 主要内容什么时候看到 |
| 交互 | INP（取代 FID） | 点下去多久有反应 |
| 稳定 | CLS | 页面会不会自己乱跳 |

### LCP（Largest Contentful Paint，最大内容绘制）

LCP 是**视口内最大的那块内容**渲染完成的时刻。候选元素按优先级包括：

- `<img>`、`<svg>` 内嵌 `<image>`、`<video>` 的封面图
- 用 `url()` 加载背景图**的元素**（背景图本身不算，元素算）
- 包含文本节点的块级元素（纯文字页面里，一整块标题就是候选）

**目标值**：≤ 2.5s（看第 75 百分位，不是平均值）。

LCP 由四段构成，优化时按这个顺序找瓶颈：

```
LCP = TTFB（服务器 + 网络）
    + 资源加载延迟（发现资源够不够早、优先级对不对）
    + 资源加载时长（体积、带宽）
    + 元素渲染延迟（主线程忙不忙、要不要等 JS）
```

> 摘自 `./code/perf-lab/scenarios/metrics.mjs`（运行：`npm run metrics`）

```js
    const rows = await sweep('/metrics.html', [
        { name: '轻量首屏', query: { mode: 'light' }, rounds: 3 },
        { name: '未治理首屏', query: { mode: 'heavy' }, rounds: 3 }
    ])
```

两台页面的差别只有两处：重版本多了一个 500KB 的 parser 阻塞脚本，以及一张 300KB 的首屏大图。实测结果（3 轮中位数）：

```
| 页面       | TTFB   | FCP     | LCP     | 位移  | DOMContentLoaded | load    | 长任务 | 最长任务 |
|------------|--------|---------|---------|-------|------------------|---------|--------|----------|
| 轻量首屏   | 159 ms | 396 ms  | 396 ms  | 0.000 | 381 ms           | 382 ms  | 0      | 0 ms     |
| 未治理首屏 | 160 ms | 2600 ms | 4024 ms | 0.000 | 2589 ms          | 4010 ms | 0      | 0 ms     |
```

TTFB 基本一致（160 ms vs 159 ms）——服务端没问题；LCP 差了 10 倍，全部来自资源侧。这一条就否掉了「先去优化服务器」的方向。

### INP（Interaction to Next Paint，交互到下次绘制）

INP 量的是**整个页面生命周期内所有交互**里最有代表性的那一次：从用户点击开始，到浏览器把这次交互的结果绘制到屏幕上为止。它比 FID 合理的地方在于——FID 只看第一次输入（且只算「等待响应」的那段队列时间，不含处理耗时），而 INP 看全程、含处理与绘制。

**目标值**：≤ 200ms。

INP 差的根因几乎总是同一个：**主线程被长任务占住了**。浏览器只有在一个任务结束后才能处理输入，所以一个 300ms 的长任务会把期间所有点击都推迟到 300ms 之后。

> 摘自 `./code/perf-lab/scenarios/longtask.mjs`（运行：`npm run longtask`）

```js
    const rows = await sweep('/longtask.html', [
        { name: '一次做完', query: { mode: 'sync' }, rounds: 3 },
        { name: '分片切片', query: { mode: 'chunked' }, rounds: 3 }
    ])
```

实测 60000 行列表的两种渲染写法：

```
| 做法     | 总耗时  | 分片数 | 最长同步块 | 首屏可见耗时 | 超过 50ms 的块 |
|----------|---------|--------|------------|--------------|----------------|
| 一次做完 | 737 ms  | 1      | 737 ms     | 737 ms       | 1              |
| 分片切片 | 1152 ms | 10     | 144 ms     | 162 ms       | 10             |
```

一次做完的那一版有一个 737ms 的同步块——这 737ms 里用户点任何东西都不会有反应。切片版总耗时反而更长（多 415ms，每次结算布局都有固定开销），但最长块降到 144ms、首屏可见从 737ms 降到 162ms。**这就是「总耗时」和「INP」不是一回事的地方**。INP 的详细优化手段见「运行时性能」篇。

### CLS（Cumulative Layout Shift，累积布局偏移）

CLS 量的是「内容自己动了多少」。一次位移的分数是：

```
单次位移分数 = 影响比例（impact fraction）× 位移距离比例（distance fraction）
```

- **影响比例**：不稳定元素在位移前后占据的视口区域并集，占整个视口面积的比例
- **位移距离比例**：元素移动的最大距离，除以视口高度

CLS 是所有单次分数之和。**目标值：≤ 0.1。**

两个最常见的来源，实测一下就很清楚：

> 摘自 `./code/perf-lab/scenarios/cls.mjs`（运行：`npm run cls`）

```js
    const rows = await sweep('/cls.html', [
        { name: '无预留', query: { mode: 'bad' }, rounds: 3 },
        { name: '有预留', query: { mode: 'good' }, rounds: 3 }
    ])
```

```
| 版本   | 位移合计 | 位移次数 | 评级 | FCP    | LCP    |
|--------|----------|----------|------|--------|--------|
| 无预留 | 0.300    | 2        | 差   | 336 ms | 740 ms |
| 有预留 | 0.000    | 0        | 良好 | 324 ms | 720 ms |
```

两次位移各自是什么，脚本会打出来：

```
---- 两次位移分别是什么 ----
[无预留] +0.0901 @730ms  +0.1922 @785ms
[有预留] 没有位移
```

`@730ms` 那次是图片：不给 `width` / `height`，浏览器先按 0 高排，图回来才知道要占 240px，下面的卡片整体下移。`@785ms` 那次是横幅：240px 高的元素插到了 `body` 最前面，整页内容被顶下去一次。

修法就两条，对应两个坑：**给图片写死尺寸**（或 `aspect-ratio`）、**给晚到的动态内容预留空间**（`min-height` 占位容器）。

> 注意 `transform` 与 `top` / `left` 的区别：位移分数的判定只看元素的**起始位置**是否变化。用 `transform: translate()` 做动画，元素在布局里的位置没变，不产生 CLS；改 `top` / `margin` 会。

## 三、辅助指标：时间轴上的位置决定它的用途

### FP 与 FCP

- **FP（First Paint）**：第一个像素被绘制。不关心画了什么，白底也算。
- **FCP（First Contentful Paint）**：第一次画出**有意义内容**——文字、图片、非白底 canvas。

**目标值：FCP ≤ 1.8s。** FCP 与 FP 之间如果差得远，通常说明「先铺了背景色，内容还没来」，用户看到的是空壳。

### TTFB（Time to First Byte）

从请求发出到**响应头第一个字节**到达，串起了 DNS、TCP/TLS 握手、服务端处理、首字节传输。它是所有加载指标的上限。

**目标值：≤ 800ms**（纯服务端处理时长在 200ms 以内算健康）。静态资源走 CDN 时 TTFB 通常 20~80ms，如果看到 500ms 以上，先怀疑回源和缓存没命中。

### TBT、TTI 与 SI

- **TBT（Total Blocking Time）**：FCP 到 TTI 之间，所有长任务**超出 50ms 的部分**之和。一个 80ms 的长任务贡献 30ms。目标值 ≤ 200ms。
- **TTI（Time to Interactive）**：页面「可靠响应输入」的时刻。判定是「已有 FCP + 主线程连续 5s 没有超过 50ms 的长任务」。
- **SI（Speed Index）**：可视内容填充速度，靠逐帧截图算像素变化速率。越低表示内容呈现得越连贯，Lighthouse 参考值 ≤ 3.4s。

TBT 是 INP 的**实验室代理指标**——真实用户的 INP 要等交互才有，而 TBT 在加载阶段就能量出来。

```
TTFB → FP → FCP → (TBT 在这段累积) → TTI ─────► LCP 可能还在等图片
 └── 加载起点 ──┘└──── 内容呈现 ────┘└─ 可交互 ─┘
```

留意一个容易搞反的点：**LCP 不保证早于 TTI**。首屏图片很大时，页面已经能点了（TTI 到了），最大内容元素还在下载，LCP 反而更晚。上面那张实测表里，「未治理首屏」的 LCP（4024ms）就晚于 DOMContentLoaded（2589ms）。

## 四、实验室口径 vs 现场口径

同一套指标，从两个地方拿，含义不一样：

| | 实验室（Lab） | 现场（Field / RUM） |
| --- | --- | --- |
| 数据来源 | 固定设备 + 模拟网络跑一次 | 真实用户的浏览器 |
| 典型工具 | Lighthouse、本仓 perf-lab | Web Vitals 采集 SDK + 上报 |
| 优势 | 可复现、可对比、能看火焰图定位 | 反映真实分布，不受单一环境误导 |
| 劣势 | 只代表这一次，不代表用户分布 | 噪声大，看不出根因 |

**正确的分工**：现场数据发现问题（「75 分位 LCP 4.2s，主要集中在移动端 4G」），实验室数据定位根因（「同一页面本地开 4G 节流能复现，阻塞脚本占了 2.2s」），改完再回现场看分布有没有真的变好。

还要注意**分位数 vs 平均值**：性能数据是长尾分布，平均值会被少数极快或极慢的样本带偏。Core Web Vitals 统一看 75 分位（p75），含义是「75% 的用户体验不差于这个值」。

## 五、实测：套上区间才叫「评估」

有了数字，下一步是判断好坏。评级区间是硬标准，写成代码最省事：

> 摘自 `./code/perf-lab/scenarios/score.mjs`（运行：`npm run score`）

```js
/** 各指标的 [良好上限, 待改进上限]，超过第二个值即为「差」 */
const THRESHOLDS = {
    ttfb: [800, 1800],
    fcp: [1800, 3000],
    lcp: [2500, 4000]
}

function rate(name, value) {
    const [good, ok] = THRESHOLDS[name] || [Infinity, Infinity]
    if (value == null) return '—'
    if (value <= good) return '良好'
    if (value <= ok) return '待改进'
    return '差'
}
```

CLS 的区间不是线性的，单独写一个：

> 摘自 `./code/perf-lab/scenarios/score.mjs`

```js
function rateCls(value) {
    if (value == null) return '—'
    if (value <= 0.1) return '良好'
    if (value <= 0.25) return '待改进'
    return '差'
}
```

一张页面的整体结论由四个单项汇总，取最差的一档：

> 摘自 `./code/perf-lab/scenarios/score.mjs`

```js
                const rs = [rate('ttfb', m.ttfb), rate('fcp', m.fcp), rate('lcp', m.lcp), rateCls(m.clsRaw)]
                const bad = rs.filter(r => r === '差').length
                const warn = rs.filter(r => r === '待改进').length
                const overall = bad ? '差' : warn ? '待改进' : '良好'
```

把四个页面一起跑出来的体检表：

```
| 页面       | TTFB          | FCP              | LCP           | CLS（全量位移） | 整体 |
|------------|---------------|------------------|---------------|-----------------|------|
| 轻量首屏   | 194 ms ✓ 良好 | 400 ms ✓ 良好    | 400 ms ✓ 良好 | 0.000 ✓ 良好    | 良好 |
| 未治理首屏 | 111 ms ✓ 良好 | 2612 ms ! 待改进 | 4028 ms ✗ 差  | 0.000 ✓ 良好    | 差   |
| CLS 无预留 | 115 ms ✓ 良好 | 384 ms ✓ 良好    | 768 ms ✓ 良好 | 0.300 ✗ 差      | 差   |
| CLS 有预留 | 104 ms ✓ 良好 | 368 ms ✓ 良好    | 752 ms ✓ 良好 | 0.000 ✓ 良好    | 良好 |

| 指标  | 良好     | 待改进     | 差      |
|-------|----------|------------|---------|
| TTFB  | ≤800ms   | ≤1800ms    | >1800ms |
| FCP   | ≤1800ms  | ≤3000ms    | >3000ms |
| LCP   | ≤2500ms  | ≤4000ms    | >4000ms |
| CLS   | ≤0.1     | ≤0.25      | >0.25   |
| INP   | ≤200ms   | ≤500ms     | >500ms  |
```

「未治理首屏」和「CLS 无预留」两张表挂了同一个结论——**差**，但原因是两个完全不同的东西：前者是加载慢，后者是内容跳。所以体检表的价值不是排名，是**把「哪里差」定位到具体指标**。

区间用起来还有两个容易踩的坑：

- **评级是门槛不是排名**。LCP 从 8000ms 优化到 3000ms，评级仍是「待改进」，但用户体感已经是两个世界。
- **一次只盯一个**。四个指标一起抠，改动互相干扰、也看不出是哪个手段起的作用。把「差」先拉到「待改进」，再统一进「良好」。

## 六、实测：CLS 在无头环境里为什么恒为 0

实验台一开始量不出位移——两个版本 CLS 都是 0。查下去发现是规范本身的一个细节：

> 摘自 `./code/perf-lab/pages/lab.js`

```js
    observe('layout-shift', e => {
        // 规范口径：位移发生在用户输入后 500ms 内属于「预期位移」，不计入 CLS
        // 无头环境里没有真实输入，hadRecentInput 却是 true，所以两个值都留着：
        // cls 是上报给监控的口径，clsRaw 是「所有位移之和」，对照实验读 clsRaw
        metrics.shifts += 1
        metrics.clsRaw += e.value
        if (!e.hadRecentInput) metrics.cls += e.value
    })
```

规范规定：位移如果发生在用户输入后 500ms 内，属于「用户预期内的变化」（比如点了「展开」），不计入 CLS，由 `hadRecentInput` 标记。而无头环境里没有任何输入事件，`hadRecentInput` 却依然是 `true`，于是规范口径的 CLS 恒为 0。

处理办法是**两个值都留着**：`cls` 是规范口径（上报给监控、真实用户环境用这个），`clsRaw` 是所有位移之和（无头对照实验读这个）。这不是实验台的权宜之计，生产环境里同样需要——有些团队会把 `hadRecentInput` 的判定窗口放宽到 1s，不同口径的数据混在一张报表里就没法比了。

## 七、采集代码怎么写：一条指标从产生到上报

指标的产生方式分两类，这是采集代码的结构基础：

- **能从缓冲区直接读**：TTFB、FP、FCP、导航类时间。页面到达时它们已经在 `performance` 缓冲区里，`getEntriesByType()` 一次取完。
- **必须订阅**：LCP、CLS、长任务。它们是**累积**或**持续发生**的，只能在事件产生时收，收完还要等「不再变化」才能上报。

订阅统一走 `PerformanceObserver`，一次封装好能用很久：

> 摘自 `./code/perf-lab/pages/lab.js`

```js
    const observe = (type, cb) => {
        try {
            new PerformanceObserver(list => {
                for (const entry of list.getEntries()) cb(entry)
            }).observe({ type, buffered: true })
        } catch (err) {
            /* 浏览器不支持该条目类型时静默跳过 */
        }
    }
```

`buffered: true` 是关键——它让观察器能拿到**注册之前**已经产生的条目。否则你在页面底部注册 LCP 观察器，就会漏掉更早发生的那些。

有了 `observe`，四类指标各一行：

> 摘自 `./code/perf-lab/pages/lab.js`

```js
    observe('paint', e => (e.name === 'first-paint' ? (metrics.fp = e.startTime) : (metrics.fcp = e.startTime)))
    observe('largest-contentful-paint', e => (metrics.lcp = e.startTime))
    // …（layout-shift 的订阅见第六节）
    observe('longtask', e => longtasks.push({ start: e.startTime, duration: e.duration }))
```

缓冲区的那些在快照时一次取完：

> 摘自 `./code/perf-lab/pages/lab.js`

```js
    function snapshot() {
        const nav = performance.getEntriesByType('navigation')[0]
        if (nav) {
            metrics.ttfb = nav.responseStart
            metrics.domContentLoaded = nav.domContentLoadedEventEnd
            metrics.load = nav.loadEventEnd
        }
        const out = {}
        for (const [key, value] of Object.entries(metrics)) out[key] = round(value)
        return out
    }
```

**上报时机**是这条链路里最容易做错的一环。短时指标（TTFB / FCP）在 `load` 之后就是定值了；LCP 和 CLS 会一直变到用户离开页面为止，必须等页面进入隐藏态再报，否则报的是一个中途值。

> 摘自 `./code/perf-lab/harness/index.mjs`

```js
export async function measure(page, options = {}) {
    const { query = {}, rounds = 1, timeout = 30000, flags = [] } = options
    const srv = await startServer(options.server)
    try {
        const collected = []
        for (let round = 0; round < rounds; round++) {
            const qs = new URLSearchParams(Object.entries(query).map(([k, v]) => [k, String(v)])).toString()
            const wait = srv.nextReport(timeout)
            const chrome = openChrome(srv.origin + page + (qs ? `?${qs}` : ''), flags)
            try {
                collected.push(await wait)
            } finally {
                chrome.kill()
            }
        }
        return rounds === 1 ? collected[0] : medianDeep(collected)
    } finally {
        await srv.close()
    }
}
```

这段是实验台的编排（起服务 → 开无头 Chrome → 等页面回报），但它也说明了上报链路的形状：**页面侧只负责把数据送出去，聚合与判定放在外面**。真实项目里「外面」就是监控 SDK 的接收端，留给「性能与体验监控」篇展开。

顺带一个采样上的经验：**性能数据不必 100% 采集**。它是分布统计，1%~10% 的样本足够看趋势，而全量上报带来的带宽与服务端成本是实打实的。采样要按用户维度稳定（同一用户始终进/出样本），否则分位数会失真。

## 八、RAIL：把指标换算成优化优先级

指标告诉你「哪里差」，RAIL 告诉你「先改哪个」。核心思想一句话：**优化的目标是响应用户，不是响应设备**。

| 缩写 | 含义 | 预算 | 对应指标 |
| --- | --- | --- | --- |
| R（Response） | 响应输入 | < 100ms | INP |
| A（Animation） | 动画流畅 | 每帧 < 16ms（渲染预算 10ms） | 帧率 |
| I（Idle） | 利用空闲 | 主线程空闲块 > 50ms | 长任务 |
| L（Load） | 加载内容 | < 5s（理想 < 2.5s） | LCP / FCP / TTFB |

用法是把指标超标的程度折算成「用户会有什么感受」：INP 从 150ms 涨到 600ms，是「点一下卡半秒」级别的问题，优先级高于 LCP 从 2.4s 涨到 2.8s——后者用户基本察觉不到。

四个预算里，**A 的 16ms 最容易被人忽略也最容易验证**：一帧 16.7ms，如果某段逻辑要跑 30ms，就一定会掉帧。把这段逻辑拆到两帧（或挪进 Worker）就能救回来，具体见「运行时性能」篇。
