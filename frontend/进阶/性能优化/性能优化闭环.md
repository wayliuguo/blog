# 性能优化闭环

前面三篇分别解决了三个核心目标：把 LCP、INP、CLS 打下来。加上开篇的量化，模块主线已经走完三步——**先量化指标 → 定位瓶颈 → 分层优化**。

剩下的是第四步，也是工程上真正难的那一件：**变好之后，怎么保证它不再变差**。

一个常见场景：花两周把 LCP 从 4s 优化到 1.6s，三个月后回头看，又是 3.4s。中间没有哪一次改动是「性能改动」，全是业务需求顺手带上来的——多引了一个图表库、多埋了一段首屏不需要的逻辑、多插了一个同步脚本。**性能不是一次性任务，是一条需要守住的水位线。**

这一篇讲怎么把「测量 → 优化 → 守住」变成流程，也就是主线里的**持续监控**。

## 一、闭环的四个环节

```
① 定基线  ──►  ② 定预算  ──►  ③ 卡卡口  ──►  ④ 回归验证
现有指标是多少      每项不许超过多少     超了就 fail 流水线    线上真实分布有没有变好
（现场 + 实验室）                         （实验室指标）        （现场指标）
   ▲                                                              │
   └───────────────── 劣化时回到 ② 收紧预算 ◄────────────────────┘
```

四个环节里最容易被跳过的是 ① 和 ④：直接拍一个「LCP 要小于 2.5s」的口号开始改，改完也不回头看线上数据。结果就是「优化过一轮，但没人知道有没有用」。

## 二、定预算：从现状出发，不是从理想出发

性能预算（performance budget）是一组上限值，超出就算失败。**新手最常犯的错是把预算定成「理想值」**——一上来就要求 LCP ≤ 1.5s、首屏 JS ≤ 100KB，于是所有人都超线，卡口立刻被关掉，然后不了了之。

正确的做法是三步：

1. **先量现状**。把现有指标测一遍，作为基线。哪怕现状很烂（LCP 5.8s）也没关系，基线的作用是「不许更差」，不是「合格」。
2. **定一条「不许更差 + 一点余量」的线**。比如现状 LCP 2.4s，预算先定 2.6s。
3. **逐步收紧**。每完成一轮优化，把预算降到新的现状附近。这样预算是「压力」，不是「天花板」。

预算该覆盖哪些指标，只挑**用户能感觉到**的：

| 类型 | 指标 | 说明 |
| --- | --- | --- |
| 加载 | LCP / FCP / TTFB | 用户能感知的「多久看到」 |
| 交互 | TBT（或线上 INP） | 实验室里用 TBT 代理 INP |
| 稳定 | CLS | 内容乱跳 |
| 体积 | 首屏 JS / CSS 的 gzip 后字节 | 最直接可控、最该按路由分级 |
| 数量 | 首屏请求数、长任务个数 | 辅助判断，别当主要卡口 |

**别拿 Lighthouse 总分当卡口**——它是固定权重汇总出来的，权重会随版本变，卡一个会飘的数字没有意义。

预算还必须**分级**：首屏路由严（LCP ≤ 2.5s、JS ≤ 200KB），次要页面松；把所有路由塞进一个数字，等于逼着大家要么全放宽、要么全放弃。

## 三、卡卡口：让劣化过不去

预算是文档，卡口是代码。两者差一个**退出码**——超线就 `exit 1`，CI 直接红，PR 不允许合并。

卡口的标准写在代码里：

> 摘自 `./code/perf-lab/scenarios/budget.mjs`（运行：`npm run budget`）

```js
/** 预算：每个页面的上限。改这里就等于改卡口标准 */
const BUDGET = {
    ttfb: 900,
    fcp: 1500,
    lcp: 2500,
    clsRaw: 0.1,
    jsBytes: 300 * 1024,
    longtasks: 2
}
```

实测结果里，有一项超线：

```
---- 未治理首屏 ----
| 指标            | 实测     | 预算     | 结论 |
|-----------------|----------|----------|------|
| TTFB            | 142 ms   | 900 ms   | PASS |
| FCP             | 524 ms   | 1500 ms  | PASS |
| LCP             | 524 ms   | 2500 ms  | PASS |
| CLS（全量位移） | 0.000    | 0.100    | PASS |
| JS 字节         | 467.9 KB | 300.0 KB | FAIL |
| 长任务数        | 0        | 2        | PASS |

---- 汇总 ----
11 / 12 项在预算内，1 项超线。
  FAIL  未治理首屏 · JS 字节：实测 479140 > 预算 307200

退出码 1 —— 在 CI 里这一步会让流水线失败，PR 不允许合并。
```

注意这里暴露了卡口的一个真实问题：**超线的那一项（JS 字节）在实验室里是稳定可控的，而 LCP 之类的指标在 CI 机器上抖动很大**（宿主机负载、冷启动、网络）。所以预算要分两类对待：

| 类型 | 特点 | 适合当卡口吗 |
| --- | --- | --- |
| **确定性指标**：产物体积、chunk 数、请求数 | 完全可复现 | 适合，可以卡得很严 |
| **统计性指标**：LCP / FCP / TBT | 有抖动，需要多轮取中位 | 适合卡「明显劣化」，阈值要留余量 |

实践建议：**CI 卡口以确定性指标为主**（体积、请求数、长任务数），统计性指标用「多轮中位数 + 宽松阈值（比如 +20%）」，只拦断崖式劣化。真正精细的指标判断放到线上监控去做。

## 四、优化前后对比：四个案例

没有前后对比的优化报告是没有说服力的。下面四个案例都来自本仓实验台的对照页——每个都是「同一段业务，两种写法」，等价于一次优化前后的测量。

**案例 1：把阻塞脚本改成 defer。** 手段只有一处改动（`<script>` 加一个属性）。

```
| 放法       | FCP    | LCP    | DOMContentLoaded | load   |
|------------|--------|--------|------------------|--------|
| head 同步  | 608 ms | 608 ms | 592 ms           | 593 ms |
| head defer | 416 ms | 416 ms | 498 ms           | 498 ms |
```

FCP / LCP 下降 192ms（32%），DOMContentLoaded 只降 94ms——因为脚本该执行还是要执行，只是不再挡解析。

**案例 2：首屏之外的图片加 `loading="lazy"`。**

```
| 策略        | 发出图片请求 | 图片字节 | LCP    |
|-------------|--------------|----------|--------|
| 全部 eager  | 12 / 12      | 2.35 MB  | 540 ms |
| 首屏外 lazy | 8 / 12       | 1.57 MB  | 540 ms |
```

字节下降 33%，**LCP 完全不变**。这条对比的价值不只是「省了 0.78MB」，更是明确了一个边界：**懒加载不改善首屏**，它改善的是首屏之后的带宽竞争。如果目标是 LCP，改这个没用。

**案例 3：10000 行长列表改成虚拟滚动。**

```
| 做法     | DOM 节点数 | 实际渲染行数  | 首屏渲染 | 一次大跨度滚动 | JS 堆   |
|----------|------------|---------------|----------|----------------|---------|
| 全量渲染 | 10012      | 10000 / 10000 | 14 ms    | 288 ms         | 1421 KB |
| 虚拟滚动 | 39         | 25 / 10000    | 1 ms     | 13 ms          | 615 KB  |
```

DOM 节点 -99.6%，滚动 288ms → 13ms，堆 -57%。代价是引入了一份「窗口计算 + 滚动锚定」的复杂度，以及每次滚动都要重建那 25 行——**这是拿复杂度换体验**，只有列表确实长（上千行）时才划算。

**案例 4：路由改成按需加载（1.5 Mbps 限速）。**

```
| 策略     | 首屏加载到可用 | 发出的 chunk 数 | JS 传输总量 |
|----------|----------------|-----------------|-------------|
| 首屏全量 | 2069 ms        | 1               | 347.6 KB    |
| 按需加载 | 767 ms         | 3               | 348.2 KB    |
```

首屏 -63%，总字节几乎不变。这个案例最容易被误读——**它不是「体积优化」，是「时序优化」**：总量没变，只是把 2/3 的下载挪到了用户真正要去那些路由的时候。

四个案例连着看，能得到一条写报告的方法论：**每个优化点都要写清「手段 / 指标变化 / 代价 / 边界」**。只写「优化了 LCP」的报告，评审时一定会被问「怎么优化的、有没有副作用」，答不上来就等于没做。

## 五、回归验证：实验室变好 ≠ 用户变好

实验室测的是「这一次、这台机器、这个网络」。所以改完必须回到现场：

**第一步：灰度放量。** 别一次全量。5% → 20% → 50% → 100%，每一档对比新旧版本的指标分布。看的是**分位数**（p75 / p95），不是平均值。

**第二步：盯住「没变好」和「变差了」两类信号。**

- **指标没变好**：最常见的原因是「还有另一个瓶颈」。比如 LCP 优化了图片，但 TTFB 就 2s，LCP 自然不动。这时回到实验室看瀑布图找下一段。
- **指标变差了**：性能改动经常有反直觉的副作用。最典型的是**预加载 / preload 抢带宽**——给 A 资源加了高优先级，B 资源（真正的 LCP 元素）反而更慢。

**第三步：看分布形状的变化。** 平均值一样但 p95 变差，说明「多数人略好、少数人明显更差」。这种变化在平均值上是看不出来的，要画两版的分位曲线对比。

**第四步：确认观测本身没被影响。** 上报本身也有成本（尤其是 `sendBeacon` 频繁上报），监控 SDK 的体积与开销本身就该有预算。

## 六、把闭环固化下来

流程层面四件事，做完这套闭环才算立住：

1. **预算写进代码仓库**，和业务代码一起评审、一起改。写在文档里的预算一定会过期。
2. **卡口进 CI**，而且只对确定性指标卡死。统计性指标用宽松阈值 + 多轮中位数。
3. **看板带基线**。监控看板上每个指标都画一条基线（上个稳定版本的值），一眼能看出「今天是不是变差了」。
4. **劣化归因到提交**。把指标劣化与代码提交关联起来（发布记录对时间点），否则只能知道「变差了」而不知道「哪次改的」。这一步是很多团队缺失的最后一环。
