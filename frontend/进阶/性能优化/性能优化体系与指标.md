# 性能优化体系与指标

> 本篇把性能优化体系压成「决策与判断」：指标定位 → 分层手段 → 验证闭环。完整代码与全量读数见〔性能优化实战〕。

## 一、指标体系：核心指标是目标，辅助指标是刻度

三个核心指标（LCP / INP / CLS）是**要守的目标**，其余指标都不是目标，而是用来定位的刻度。

| 核心指标 | 中文含义 | 目标（p75） | 用户的话 |
| --- | --- | --- | --- |
| LCP | 最大内容绘制 | ≤ 2.5s | 多久能看到内容 |
| INP | 交互到下一次绘制 | ≤ 200ms | 点了多久有反应 |
| CLS | 累积布局偏移 | ≤ 0.1 | 页面会不会自己乱跳 |

三个谁也替代不了谁：同一张详情页，主图不写尺寸 CLS 0.0633、写死归零，而两版 LCP 都在 1900ms 上下——**LCP 好不代表体验好**。

辅助指标只有一种用途：把核心指标的「差」**定位到时间轴上的哪一段**。

```
请求发出   首字节   首次绘制  首次内容  最大内容  可交互    一次交互
  │          │          │        │        │       │        │
  ◄─TTFB──►   FP        FCP      LCP      TTI      INP
```

读图一句话：核心指标告诉你要去哪，辅助指标告诉你在哪。

全部辅助指标（TTFB / FP / FCP / TBT / TTI / SI / Long Task / Layout Shift / DOM Size）的量程与目标见原版 1.2，此处不重复。

### 排障主线：核心指标 → 辅助指标 → 层级 → 定位 → 优化

这张表是全篇索引。核心指标超标 → 顺着辅助指标找异常段 → 落到层 → 在层里查具体项 → 照方案改。

| 核心指标 | 先看哪个辅助指标 | 异常信号 | 归属层 | 层内定位什么 | 优化方案 |
| --- | --- | --- | --- | --- | --- |
| LCP | TTFB | >500ms | 网络层 | DNS / TCP / TLS / 服务端 / 首字节传输 | `preconnect` / `dns-prefetch`、CDN、HTTP/2、服务端缓存 → 3.1 |
| LCP | 资源瀑布 / Coverage | 阻塞资源条长且靠右；Coverage 大面积红 | 构建与产物层 | 首屏 JS 字节、下了没执行 | 路由分包、按需引入、tree-shaking、gzip/brotli、hash+长缓存 → 3.2 |
| LCP | FCP | TTFB 正常、FCP 明显晚 | 资源层 | 首屏图体积/格式、字体、阻塞 CSS | `srcset`/`sizes`、WebP/AVIF、字体 `preload`、关键 CSS 内联 → 3.3 |
| LCP | LCP 元素本身 | 骨架屏成了 LCP 元素 | 感知层 | 时间减不到零时的观感 | SSR/流式、骨架屏；必须同埋「真实内容渲染完成」指标 → 3.4 |
| INP | TBT / Long Task | 交互正落在长任务里 | JS 执行层 | 火焰图那个宽条是谁 | 切片（`MessageChannel`/`postTask`）、重计算搬 Worker、换算法 → 4.1 |
| INP | Long Task 后紧跟 Layout | 回调快返回、紧跟大范围重排 | 渲染层 | 强制同步布局 / DOM 节点数 | 读写分离、`rAF` 合帧、`IntersectionObserver`、虚拟滚动 → 4.2 |
| INP | 重渲染次数 | 数据没变、一片组件重渲 | 框架层 | `memo` / 依赖 / `key` 是否稳定 | `React.memo`/`useMemo`、`shallowRef`/`markRaw`、状态下沉 → 4.3 |
| INP | 堆内存曲线 | 只涨不落、越用越卡 | 内存与长会话 | Detached DOM、膨胀数组/Map | 摘监听、清定时器、全局缓存设上限 → 4.4 |
| CLS | Layout Shift 条目 | 位移接近 LCP | 资源层 | 图/媒体没尺寸、字体换字 | `width`/`height`、`aspect-ratio`、回退字体度量匹配、字体 `preload` → 5.1 / 5.2 |
| CLS | Layout Shift 条目 | 位移发生在接口返回后 | 渲染层 | 新元素插到已有内容上方/中间 | 容器 `min-height` 预留、不在上方插入、骨架屏结构一致 → 5.3 |
| CLS | Layout Shift 条目 | 位移持续累积 | 渲染层 | 用会触发布局的属性做动画 | 只用 `transform` / `opacity` → 5.4 |

两条纪律：

1. **上游决定下游**：TTFB 3 秒，后面 FCP / LCP 不可能好，先修上游；TTFB 只有 60ms 时去优化服务端没收益，瓶颈一定在后面。
2. **指标要互相印证**：「传输量砍一半」和「LCP 一点没动」摆在一起才有结论——说明改的那一段不在 LCP 构成里（见 3.3 的 `images` 实验）。

## 二、口径与工具：先判断数可不可信，再选面板

- **实验室管定位、现场管发现**：现场看分布（p75 偏高、集中在移动端 4G）→ 实验室复现根因 → 改完回现场看 p75。本篇全程实验室侧。
- **统一看 p75**：性能是长尾分布，平均值被极少数样本带偏。
- **评级是门槛不是排名**：LCP 8000→3000ms 评级仍是「待改进」，但体感已是两世界；**一次只盯一个指标**。
- **CLS 双口径**：`cls`（规范口径，现场报表读）+ `clsRaw`（所有位移之和，对照实验读），采集端分开上报。规范只把交互后 500ms 内位移当「预期位移」剔掉，手动对照里该记的位移可能被误剔，所以两个值都必须留。

工具选用标准只有一条：**它替你做了什么决定**。用序是先用粗粒度定位阶段（瀑布图 / TBT），再用细粒度定位函数（火焰图）——反过来做会在火焰图里翻十分钟、最后发现是首屏图 3MB。

| 工具 | 替你做掉的事 | 代价 | 适合回答 |
| --- | --- | --- | --- |
| Network / 瀑布图 | 请求按时间排好、标优先级阻塞 | 只看搬运、不看计算 | 时间花在哪个资源等待上 |
| Performance | 主线程采样、生成火焰图 | 录制有开销、体量大 | 那 500ms 在跑什么函数 |
| Coverage | 每文件已用/总字节 | 只给静态结论 | 有多少下了没用代码 |
| Memory | 堆快照/对比/分配时间线 | 快照暂停页面、体量大 | 越用越卡、什么没被回收 |
| Lighthouse | 全套审计打分 | 环境是模拟的、只代表这一次 | 整体水位、短板扫描 |
| Performance API / 实验台 | 读数变可复现数字 | 需自写采集聚合 | 优化前后差多少、有没有真变 |

Lighthouse 最容易用错：分数是**固定权重汇总**、相对且只看这一次，正确用法是**当趋势与短板扫描，别当验收卡口**；要卡口就把确定性指标（LCP / INP / CLS 真实读数）写进 CI。

## 三、加载层：把 LCP 打下来

LCP 由四段构成，正好对应加载层的四层——哪一段长改哪一层：

```
LCP = TTFB（网络 + 服务端）→3.1 ＋ 加载延迟（发现得够不够早）→3.2/3.3
    ＋ 加载时长（体积 / 带宽）→3.2 ＋ 元素渲染延迟（主线程忙不忙）→3.3
```

| 子层 | 服务 LCP 哪一段 | 手段清单 |
| --- | --- | --- |
| 3.1 网络层 | TTFB | `preconnect`/`dns-prefetch`、CDN、HTTP/2、`fetchpriority`、服务端缓存压缩、减小首屏 HTML |
| 3.2 构建与产物层 | 加载时长（体积） | 路由分包、按需引入、tree-shaking、依赖替换、gzip/brotli、hash+长缓存、vendor 拆分 |
| 3.3 资源层 | 加载延迟（关键渲染路径） | 图片尺寸+格式、`srcset`/`sizes`、懒加载、关键 CSS 内联、字体 `preload`/`font-display` |
| 3.4 感知层 | 元素渲染延迟 / 观感 | SSR/SSG、骨架屏、流式渲染、预取下一页 |

### 3.1 网络层：TTFB 慢在哪一段

先把这次请求拆成五段，定位到底慢在哪，再动手。

| 哪一段慢 | 判断依据 | 前端能不能改 |
| --- | --- | --- |
| DNS 查询 | 首次访问第三方域最明显 | 能：`dns-prefetch` |
| TCP 建连 + TLS | 同域多请求、连接复用后消失 | 能：`preconnect`、HTTP/2、CDN |
| 服务端处理 | 纯服务端 >200ms 不健康 | 不能（后端/缓存/CDN 回源） |
| 首字节传输 | 大响应体、弱网 | 能：压缩、减小 HTML |

四个「提前」指令常被混：

| 指令 | 做的事 | 用在哪 |
| --- | --- | --- |
| `preconnect` | DNS + TCP + TLS | 同域后面还要发多个请求（CDN），开销最大 |
| `dns-prefetch` | 只解析 DNS | 第三方域，收益小开销也小 |
| `preload` | 高优先级现在就下 | 关键路径但浏览器发现得晚的（字体、首屏大图） |
| `prefetch` | 空闲下下一页资源 | 高概率、小体积的下一页 |

注意三条：`preload`/`prefetch` 只改变开始下载时刻、不改变体积，解决「发现得晚」不解决「太大」；`as="font"` 必须带 `crossorigin` 否则被下载两次；给首屏图片直接标 `fetchpriority="high"` 比给整条链加 preload 更容易维护。

### 3.2 构建与产物层：首屏体积（按序 1→4）

1. **路由级分包**：路由改动态 `import()`，首屏只带当前路由。真假是要配空闲预取（只给大概率去的一两个路由），否则切路由时连本带利还回去。本质是**时序优化不是体积优化**——省的是「被拆出去的代码 × 上首屏概率」。
2. **tree-shaking**：删「没引用的导出」。前提是 ESM、库标 `sideEffects: false`、静态访问；`if(false){heavy()}` 打不掉，**体积对比是唯一能发现的证据**。
3. **代码/传输压缩**：`drop_console`/`pure_funcs` 别把 `console.error` 删了（监控上报靠它）；属性名混淆会让上报字段名一起变。gzip 约 70% 必开、brotli 再小 15~20%（只对文本）。
4. **内容 hash + 长缓存**：二次访问传输量压到 0。纪律：sourcemap 绝不部署线上；chunk 拆太碎请求数暴涨。

复核纪律：构建侧改动最容易「看着有道理但没效果」——产物体积逐 chunk diff → Coverage 复核红色区 → 首屏实际请求数与字节 → 真实指标回归。

### 3.3 资源层：谁在挡第一帧

TTFB 正常但 FCP 明显晚，看关键渲染路径上谁挡第一帧。

- **图片**：写死 `width`/`height`（自动 `aspect-ratio`）；照片用 WebP/AVIF（比 JPEG 小 25~50%）、图标用 SVG。
- **响应式**：`srcset`+`sizes` 按视口挑尺寸，**各档比例必须一致**（`srcset` 换分辨率不换比例）。
- **懒加载** `loading="lazy"`：只改善首屏之后的带宽竞争、**不改善首屏**（有约 1250px 预加载距离）；**首屏主图千万别加**，应配 `fetchpriority="high"`。
- **关键 CSS 内联**：内联进 `<head>` 其余异步；代价是异步 CSS 一到会位移，内联部分必须含布局尺寸。`media="print"`+`onload` 改 `all` 是最稳的异步 CSS 写法。
- **字体** `font-display`：正文首选 `swap`（有换字重排）、CLS 优先 `optional`；默认 `auto` 有最长 3s 不可见期。

一个现代工程事实：`<script type="module">` 天然 defer，vite/webpack 入口脚本不阻塞解析；动态 `appendChild` 的 script 默认 `async` 也不阻塞——真正要操心的是写死在 HTML 里的第三方统计脚本。

### 3.4 感知层：时间减不到零，就改变感受

前三层在减时间，这一层反过来。手段：SSR/SSG（LCP 元素由 JS 渲染变成 HTML 内含，可提前到 TTFB 附近）、骨架屏（不减少时间但把白屏换成有结构）、流式渲染（首字节早、上半屏提前）、预取下一页。

必须警惕一个指标假象：**骨架屏本身会成为 LCP 候选，LCP 变绿但用户还看不到内容**——用骨架屏的项目必须同时盯一个「真实内容渲染完成」的自定义指标。

## 四、运行层：把 INP 打下来

INP 拆三段，先记两个标尺：单帧 16.7ms（超了掉帧）、长任务 50ms（期间不响应输入）。

```
用户操作 ──► 回调开始 ──► 回调完 ──► 下一帧绘制
   └输入延迟┘└──处理时间──┘└─呈现延迟─┘
```

实操三步：**先看有没有长任务** → **再看长任务里是谁**（业务回调还是样式重算）→ **最后看是否持续劣化**（刚打开好、用久变卡就去查内存）。

一个容易反的点：**「总耗时」≠「INP」**——切片让总耗时变长（每片有结算开销），但最长阻塞块降下来 INP 就变好。

| 子层 | 动 INP 哪一段 | 手段清单 |
| --- | --- | --- |
| 4.1 JS 执行层 | 输入延迟 + 处理时间 | 长任务切片、重计算搬 Worker、换算法 |
| 4.2 渲染层 | 呈现延迟 | 读写分离、虚拟滚动、动画只用 transform/opacity |
| 4.3 框架层 | 处理时间（重复渲染） | 稳定 key、状态下沉、memo/useMemo/shallowRef/markRaw |
| 4.4 内存与长会话 | 持续劣化 | 摘监听、清定时器、缓存设上限、解除闭包大引用 |

### 4.1 JS 执行层：谁占住了主线程

- **长任务切片**：用 `MessageChannel` 或 `scheduler.postTask` 切开多片、片间让出主线程。**不能用 `Promise.then`**（微任务在宏任务结束前全跑完，一帧插不进）；`setTimeout(0)` 有 4ms clamping，片多白等。
- **重计算搬 Worker**：适合「输入小、算得久、与 DOM 无关」的活；**不是万能**——`postMessage` 结构化克隆在主线程同步执行、数据大时开销盖过收益，且 Worker 无 DOM、启动几十毫秒级，适合一次重活、不适合每 10ms 一次的小任务。
- **换更优算法**：单个工作单元本身就超 50ms 时，切片和 Worker 都救不了，只能改复杂度。

对照的判据是结果而非总耗时：同步计算那档有 61ms 长任务直接反映在 INP 上；分片和 Worker 两档最长阻塞块归零、没有长任务。**分片时不要让主线程回头重排渲染**——那会让 Worker 档额外背一段主线程开销，测的是两个变量混在一起。

### 4.2 渲染层：每帧要做多少事

- **读写分离（避免强制同步布局）**：浏览器渲染是攒批的，但 JS 改完立刻读布局属性（`offsetWidth`/`offsetTop`/`getBoundingClientRect`/`getComputedStyle`）就逼迫它马上重算 = 强制同步布局。解法：读集中最前、写放最后；写延到 `rAF` 批量。
- **虚拟滚动**：只解决「DOM 太多」、**不解决「计算太重」**，先分清哪口锅。代价：重算窗口要节流/rAF 合帧，否则重算成新卡顿源；不定高列表有滚动锚定问题；**行高必须固定**；别用 `scroll`+逐行判断，优先 `IntersectionObserver`。
- **动画只用 transform/opacity**：只走合成、可上 GPU，既不掉帧也不产生 CLS。别滥用 `will-change`（图层多耗内存显存）。

判断这两口锅：同 DOM 节点数只换滚动写法（全量渲染下 rAF 合帧、一帧只读一次），长任务直接消掉；虚拟滚动再把 DOM 节点数从全量 10030（2000 行 × 每行 5 个元素）降到 108（窗口内 14 行）。不先区分「读写的锅」和「节点数的锅」，一上来就上虚拟滚动会卡顿依旧。

### 4.3 框架层：避免不必要的重渲染

判据只有一条：**一次交互后有多少组件被重渲染了、而数据其实没变**。

- **稳定 key**：数组下标当 key，插入/排序时框架以为大量节点都变了，把「移动几个」变「重建一片」。key 用 id 后插入一条只渲染新来的那条。但稳定 key 管「谁是同一节点」，状态下沉管「谁需要知道」，不可替代。
- **状态下沉**：和列表无关的状态一变、201 行全重渲，key 稳定救不了——把状态下沉到真正需要的组件，别把大对象塞进一个 state/ref 里。
- **memo 收敛**：React 用 `React.memo`/`useMemo`/`useCallback` 切断父更新带子树的传播链；Vue 用 `shallowRef`/`markRaw` 跳过深层代理、复杂表达式抽 `computed`、长列表 `v-memo`。
- **重组件按需引入**：编辑器/图表/地图这类重但非首屏必需的组件，同时减首屏体积与初始化长任务（也入构建层总矩阵）。

这一层没有瀑布图可看，但**可以数出来**：给行组件手写 render 打计数，只做两个动作（头部插一条、改一次无关状态）。key 用 index 插入一条重渲 2001 个，换 id 只渲 1 个，再下沉状态后为 0。数的是渲染次数不是时间——200 行本地就几毫秒，真实页面是「点一下卡半秒」和「点了立刻有反应」的差别。前两层没长任务也没强制布局，多半就是它。

### 4.4 内存与长会话：为什么越用越卡

「越用越卡」几乎都来自引用没释放。审查前先开 `--enable-precise-memory-info`（否则 `performance.memory` 粒度 100KB 级、量不出逐轮趋势）。

四类泄漏，对策都是「断开那条引用」：

1. **事件监听没摘**：卸载时 `removeEventListener`。
2. **定时器没清**：及时 `clearInterval`/`clearTimeout`。
3. **全局缓存只增不减**：配 LRU 或大小上限。
4. **闭包绑死大对象**：只保留真正用到的字段。

定位靠 Heap snapshot Comparison（看哪类对象只增不减）、Detached DOM（被闭包吊住的游离节点）、Allocation timeline（哪一帧突然涨上去）。

## 五、视觉层：把 CLS 打下来

CLS 是最「便宜」的核心目标，通常不是性能问题而是**写法问题**——绝大多数来自四类写法，改完归零，不需要重构。判定规则只有两条：**只看元素起始位置变没变**；每次位移 = 影响比例 × 位移距离比例。

| 子层 | 防哪类位移 | 手段清单 |
| --- | --- | --- |
| 5.1 尺寸与预留 | 媒体/广告位晚到、占位缺失 | 写死 `width`/`height`、各档比例一致、iframe 占位、主图不 lazy |
| 5.2 字体 | 换字重排 | `size-adjust` 对齐、`preload`(带 crossorigin)、`font-display: swap`/`optional` |
| 5.3 动态内容 | 晚插元素顶走下方内容 | 预留容器 `min-height`、不在上方插入、骨架屏结构一致 |
| 5.4 动画 | 改会触发布局的属性 | 只用 transform/opacity、真改布局放容器内或交互后 500ms 内 |

### 5.1 尺寸与预留

给媒体写死尺寸，浏览器在图没到时已占位；**属性要在 HTML 里**，不能等 JS/CSS（占位时机太晚）。验证：DevTools 限速 Slow 3G 刷新，看布局是否一开始就是最终形态。首屏主图别加 `loading="lazy"`（降级为 Low 优先级、LCP 变差）。

### 5.2 字体：不可见期与换字重排是两个坑

`size-adjust` 把回退字体度量对齐正式字体，但**只能减小不能消掉**位移——位移由**行数**决定、行数是离散量，平均占位一样了折行点未必一致，多折一行就是 21px。**彻底的一条是 `preload` 字体**：赶在首次绘制前到位、根本不给回退字体上屏机会。

量字体造成的位移**看「位移像素」**，CLS 只当佐证——换字会被拆到几帧结算、每帧距离变小再乘影响比例，CLS 数值反而会反转。

### 5.3 动态内容

新元素插到已有内容上方/中间，会把后面所有东西顶走。这类问题**开发环境通常看不见**（本地接口几十毫秒返回、内容几乎同步出现）——**必须限速复现**。解法：给公告条、推荐位、评论区先渲染一个带 `min-height` 的占位容器，内容到了在里面填充（发生在容器内部、不产生位移）。要在**容器**上解，别去催接口。

### 5.4 动画：transform 与 top 的区别

`transform`/`opacity` 只改渲染位置、布局位置没变 → 不产生 CLS、只走合成；改 `top`/`left`/`margin`/`height` 布局真变了 → 位移 + 整条渲染流水线。真正要改布局的动画（展开/收起）退而求其次：变化放容器内部，或接受位移但确保发生在交互后 500ms 内（规范当「预期位移」排除）。

需要知道这个实验台的能量边界：本机 Chrome 帧被 vsync 对齐到 16.7ms，改 `top` 那点布局开销被吃掉，所以「改 top 会掉帧」在该实验里**没被证实**，被证实的是 CLS 那一列。

## 六、收口：优先级、反查表与持续监控

### 6.1 优先级：用 RAIL 折算「用户什么感受」

RAIL 核心一句：**优化的目标是响应用户，不是响应设备**。

| 缩写 | 含义 | 预算 | 对应指标 |
| --- | --- | --- | --- |
| R | 响应输入 | <100ms | INP |
| A | 动画流畅 | 每帧 <16ms（渲染预算 10ms） | 帧率 |
| I | 利用空闲 | 主线程空闲块 >50ms | 长任务 |
| L | 加载内容 | <5s（理想 <2.5s） | LCP/FCP/TTFB |

用法是把它折算成感受：INP 从 150→600ms 是「点一下卡半秒」级，优先级高于 LCP 从 2.4→2.8s（后者用户察觉不到）。

### 6.2 指标 × 分层总矩阵

行是核心目标、列是分层，格子里是手段，`—` 表示该层基本不服务该指标（本身是有用信息，如网络层对 CLS 几乎没用）。

| 分层 \ 目标 | LCP 加载 | INP 交互 | CLS 视觉 |
| --- | --- | --- | --- |
| 网络层 | preconnect/CDN/HTTP2/`fetchpriority` | — | — |
| 构建与产物 | 分包、按需引入、tree-shaking、gzip/brotli、hash+长缓存 | 少下载=少解析、减降级语法 | — |
| 资源层 | 图片格式/srcset、字体 preload | — | 写死尺寸、回退字体对齐、动态预留 |
| 感知层 | SSR/流式、骨架屏、预取 | 交互后给反馈态 | 骨架屏结构一致 |
| JS 执行 | 阻塞脚本 defer/async | 切片、Worker、换算法 | — |
| 渲染层 | 关键 CSS 内联 | 读写分离、虚拟滚动、rAF 合帧 | transform/opacity |
| 框架层 | 重组件按需引入 | memo、稳定 key、状态下沉 | — |
| 内存长会话 | — | 摘监听、清定时器、缓存设限 | — |

两个读法：按行从指标扫全场不漏层；按列从手段查归属——一条手段可多格（代码分割同时缩短 LCP 和 INP 两段不同时间），不是重复。矩阵只回答「属于哪层、服务谁」，效果与何时不做在三到五章各层里。

### 6.3 持续监控：实验室结论由现场侧闭环

实验室优化有天然漏洞：只对这一次、这一台机器成立。最后一步必须由现场数据闭环：**采集**（Web Vitals SDK + 上报，两个 CLS 口径分开）、**看板/告警**（看 p75 分布不看均值，按页面/设备/网络分层）、**回归验证**（上线后回看板确认分布真移动了，不只看实验室那一次）。

本篇负责「改什么、为什么这样改」的实验室结论；现场侧见「性能与体验监控」，负责「真实用户有没有变好」的现场结论。两侧用同一套指标口径对话，缺一侧就是半套体系。
