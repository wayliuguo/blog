## 知识主线（一句话）

交付与质量的主轴是**交付流水线**：01/02 是交付前的个人能力与约定——代码规范与门禁把风格与低级错误拦在提交前、排障方法论负责定位问题；03 把流程串成 lint→test→build→deploy 的自动化流水线；04 用测试分层与覆盖率门禁给流水线设硬约束；05 是流水线末端的发布策略、灰度熔断与回滚兜底，最终反哺规范。Git 协作约定见「基础 · 工程协作」，测试写法见「测试体系」，监控实现见「监控与稳定性」。

## 高频核心点

### 01 代码规范与质量门禁

**ESLint / Prettier 分工**

- **ESLint**：`.eslintrc` 关键字段 `env`（声明环境避免误报 process/window）/ `extends`（继承规则集）/ `plugins` / `rules`；与 Prettier 用 `eslint-config-prettier` 解风格冲突
- **Prettier**：统一引号/缩进/分号/换行；`.prettierignore` 忽略 node_modules、dist；vsCode 保存即格式化 + 配 git hooks

**提交前强校验**

- **husky + lint-staged**：`pre-commit` 检查/格式化/测试、`commit-msg` 校验提交消息、`pre-push` 推送前检查；lint-staged **只查暂存区**，避免全库无谓检查
- **commitlint + Commitizen**：commit-msg 钩子校验类型含 `feat`/`fix`/`docs`/`perf`/`test` 等；Commitizen 交互式产出 `type(scope): subject`

**从工具到门禁**

- **门禁本质**：工具结论接进流程判定，非 0 退出即阻断合入/上线
- **分层**：编辑器 / 提交（pre-commit 只增量）/ 合并（CI）/ 发布，便宜检查往前放
- **数据（真 ESLint 8，1000 文件）**：全量 3035ms/3000 问题 vs 只查改动 36ms/36 问题→ 增量覆盖率优于全量
- **增量的代价**：历史问题隐形→配套上基线；跨文件契约 ESLint 一律报 0，要靠 TS/构建/测试

### 02 排障方法论

- **通用链路**：现象 → 复现 → 定位 → 假设验证 → 沉淀
- **复现三要素**：稳定复现 / 最小路径 / 环境对齐（"本地是好的"是还没找到差异，不是结论）
- **DevTools 链路由易到难**：Console（报错）→ 断点（值变）→ Network（数据）→ Performance（慢）→ Application（状态/缓存）
- **断点统一模型**：调试客户端经调试协议连可中断运行环境；`launch`（起新进程）vs `attach`（附已运行进程）
- **线上定位**：现象先转数据（错误率/受影响分组/发布时间对照）；source map 还原压缩栈不公开托管；复现不出就补埋点，别盲改代码

### 03 CI/CD 自动化

**术语厘清**

- **CI 持续集成**：频繁合并小改动并自动验证，到构建+测试
- **CD 交付**：随时可发布到生产，到构建+测试+可部署产物
- **CD 部署**：验证通过自动上线；生产往往保留「一键/审批」

**GitHub Actions**

- **workflow → job → step** 三件套；`push`/`pull_request` 按分支过滤 + `workflow_dispatch` 手动触发
- **job 依赖与产物**：`needs` 声明依赖；`actions/upload-artifact` 上传产物、`download-artifact` 供下游使用；密钥走 `secrets.*` 仅运行时注入
- **尽早失败**：lint/test 便宜放最前；PR 只跑 quality、合并后跑完整发布
- **环境管理**：多环境分层（dev/test/staging/pre/production）；`environment` 为生产配独立 secrets 与 approvers 实现审批

**凭据安全**

- 密钥永不写进代码，放 secrets 仅运行时注入；`permissions` 收窄最小权限；OIDC 替代长期 token；fork 提交不获 secrets；日志回显前 mask

### 04 质量体系与测试

- **分层工具链**：ESLint（质量/潜在问题）、Prettier（格式）、lint-staged（只查改动）、husky（git hook）、commitlint（提交信息）各管一档、时机清晰
- **自定义 ESLint 规则**：本质是返回 `meta` + `create` 的对象；create 里监听 AST 节点（CallExpression）命中即 `context.report`，可带 `fix` 自动修复
- **覆盖率指标**：行 / 分支 / 函数；`coverage.thresholds` 配 vitest.config；CI 里 `pnpm lint && pnpm test:coverage` 任一非 0 即 pipeline 红
- **阈值卡在哪有效（模型）**：卡**全项目**是二值的（被存量稀释）；卡**改动文件**才有分辨力（60→90%，误杀 22.3% 触发到 88.9%）
- **测试失败才是主力**：召回 66.3% / 误杀 2.0% / 精确率 85.7%——它是行为信号，覆盖率只是存在性信号
- **覆盖率之外**：SonarQube/CodeQL 查同质重复、`npm audit`/Dependabot 查依赖漏洞、ESLint `complexity` 限复杂度、SLO 监控性能/错误率回归

### 05 发布、灰度与回滚

**四种发布策略**

- **蓝绿**：两套环境轮流上、一次性切换、回滚极快（切回蓝），适合后端服务
- **滚动**：逐台分批替换、回滚速度中，适合后端多实例
- **金丝雀**：先小流量试运行、逐渐引流，适合后端/功能
- **灰度**：按用户/区域/渠道分桶按比例放量；前端资源是静态文件，最常用灰度 + 即时可控的 CDN 发布

**不可变部署与 CDN**

- **内容 hash 产物**：产物文件名带 hash，每版本是 CDN 上独立永不修改的对象；切换版本=发布新 index.html 指向新 hash，回滚只需指回旧入口
- **缓存 TTL 分层**：带 hash 静态资源长缓存（`immutable`），index.html 短缓存/`no-cache` 每次回源
- **前端灰度三种手段**：入口级（CDN 按 cookie/header 分流到不同版本 index.html）、脚本级（模板按策略渲染资源标签）、路由级（服务端下发 featureFlag）

**灰度预案与回滚**

- **灰度决策流**：1% → 指标健康逐步 5%/20%/50%，不健康则熔断自动缩量/回滚
- **三种回滚**：资源回滚（入口指回旧 hash，极快无需重建）、重建回滚（重建上一 commit，可能引入差异）、功能回滚（关 featureFlag 无需发布）
- **分批参数（模型）**：跑满再判 → 100% 用户受影响；每批都判 → 第 1 批发现、受影响 5%；但最小样本量别定太大否则早停形同虚设
- **误回滚必然存在**：盯 N 个指标就多 N 次机会（多重比较）；只给核心指标设自动回滚，其余只告警
