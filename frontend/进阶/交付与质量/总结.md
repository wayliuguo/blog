# 模块总结 · 交付与质量

## 知识主线

六篇不是并列的知识点，而是一条有依赖关系的链，每一篇都在回答上一篇留下的问题：

```
01 代码规范（代码怎么写才一致）
        │  约定有了，改了代码怎么提交、多人怎么协作？
        ▼
02 Git 与协作（历史与协作怎么管）
        │  协作中出了问题，怎么高效定位？
        ▼
03 调试技巧（问题怎么定位）
        │  个人能力齐了，重复的检查/构建/部署怎么变成机器流程？
        ▼
04 CI/CD 自动化（流程怎么自动化）  ★主轴
        │  流水线有了，怎么让「质量不达标就不让合入」成为硬约束？
        ▼
05 质量体系与测试（门禁怎么设）
        │  质量通过了，新版本怎么安全送到用户面前、上线后怎么兜底？
        ▼
06 发布、灰度与监控（怎么安全上线与兜底）
```

本模块的主轴是**交付流水线**：01/02/03 篇是交付前的个人能力与约定——代码规范把风格与低级错误拦在提交前，Git 管好版本与协作，调试负责定位问题；04 篇把流程串成 lint→test→build→deploy 的自动化流水线；05 篇用测试分层与覆盖率门禁给流水线设硬约束；06 篇是流水线末端的发布策略、灰度熔断与可观测性兜底，最终反哺规范。

## 分篇知识点

### 01-代码规范

- **ESLint 静态检查**
  - **安装与初始化**：`npm install eslint` 安装，`npm init @eslint/config` 交互式生成 `.eslintrc.*` 配置文件
  - **`.eslintrc` 关键字段**：`env` 声明运行环境避免误报 `process` / `window`，`extends` 继承规则集、`plugins` 注册插件、`rules` 做细粒度开关
  - **与 Prettier 解冲突**：装 `eslint-config-prettier` + `eslint-plugin-prettier`，消除引号 / 缩进等风格冲突
- **Prettier 格式化**
  - **作用与两种使用方式**：统一引号 / 缩进 / 分号 / 换行等风格；vsCode 插件保存即格式化，npm 安装则命令行使用（配 git hooks 提交前强制格式化）
  - **`.prettierrc` 配置项**：`semi` / `singleQuote` / `printWidth` / `tabWidth` / `endOfLine` 等控制输出风格
  - **`.prettierignore` 忽略清单**：忽略 `node_modules`、`dist`、`package.json` 等无需格式化的文件
- **husky + lint-staged 提交前强制校验**
  - **Git 钩子**：`pre-commit`（提交前检查 / 格式化 / 测试）、`commit-msg`（校验提交消息格式）、`pre-push`（推送前额外检查）
  - **husky V6 目录式配置**：`npm pkg set scripts.prepare="husky install"` 让 `npm install` 自动建 `.husky/` 目录，`npx husky add .husky/pre-commit 'npx lint-staged'` 创建钩子文件
  - **lint-staged 只查暂存区**：配置 `"lint-staged": { "src/**/*.{js,jsx,ts,tsx}": ["prettier --write", "eslint --fix"] }`，只对暂存区文件跑格式化与检查，避免全库无谓检查
- **commitlint + Commitizen**
  - **commitlint 校验提交信息**：commit-msg 钩子里 `npx commitlint --edit ${1}` 按 `@commitlint/config-conventional` 校验，类型含 `feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` 等
  - **Commitizen 引导式提交**：配 `cz-conventional-changelog` 适配器 + `git-cz` 脚本，交互式问答填写 type / scope / description，产出 `type(scope): subject` 规范提交信息，便于回溯与自动生成 changelog
- **BEM 命名规范**
  - **三段式命名**：Block（块）__Element（元素，双下划线 `__` 连接）--Modifier（修饰符，双连字符 `--` 连接），如 `.header__logo--hidden`
  - **CSS 属性书写顺序**：定位属性 → 自身属性 → 文字样式 → 文本属性 → CSS3 新增属性
  - **JS 实现（createBEM）**：`_bem` 做字符串拼接，`createBEM` 导出 `b` / `e` / `m` / `be` / `bm` / `em` / `bem` 便捷函数，`createNamespace` 生成 `van-button__icon--small` 这类带前缀类名
- **常见坑与 VS Code 落地**
  - **换行符 CRLF / LF 冲突**：Windows 默认 CRLF 与项目 LF 冲突会提示 `Delete '␍'`；三种解法——VS Code 状态栏转 LF、Prettier 配 `endOfLine: "crlf"`、ESLint 规则忽略换行符检查（推荐）
  - **其他排查思路**：ESLint / Prettier 规则互报冲突确认 `extends` / `plugins` 已引入 prettier；钩子未触发确认 `husky install` 与 `.husky/` 目录存在；macOS / Linux 用 `chmod +x` 补执行权限
  - **`.vscode/settings.json`**：`editor.formatOnSave: true` 保存即格式化（默认格式化器设 Prettier），`editor.codeActionsOnSave: { "source.fixAll.eslint": true }` 保存即修复

### 02-Git 与协作

- **reset 三种模式**
  - **`--soft`**：只移动 HEAD 指针，工作区与暂存区不变，撤销最近一次提交、改动留在暂存区
  - **`--mixed`（默认）**：移动 HEAD 并更新暂存区与指定提交一致，工作区不动
  - **`--hard`**：工作区与暂存区都重置到指定提交，未提交改动全丢（慎用）；reset 会改写历史，已推远程共享分支不要 `--force`
- **revert 安全反做**
  - **作用与用法**：`git revert commitId` 新建一个相反提交抵消目标提交、不改写原有历史，适合已推送远程的场景；生成默认提交文案可改，不想要可 `git reset HEAD^` 去掉
  - **vim 编辑器小抄**：`:wq` / `:x` 保存并退出、`:q!` 不保存退出；普通 / 插入（`i` 进入）/ 命令（`:` 进入）三模式切换
- **分支协作工作流**
  - **功能分支流程**：从主分支 `git checkout -b feature/xxx` 拉功能分支 → 开发提交 → 推远程发起 PR / MR → 评审合入，其他成员 `git pull` 同步
  - **分支管理命令**：`git branch -vv` 看与远程关联、`git merge` 合并、`git pull --rebase` 变基合并让历史更线性
  - **合并冲突解决**：冲突文件标记 `both modified`，在 `<<<<<<<` / `=======` / `>>>>>>>` 区域手动选择保留代码，解决后 `git add` + `git commit`；提前 pull 保持最新、提交粒度单一可减少冲突
- **镜像同步**
  - **配置方法**：Gitee「管理 → 仓库镜像管理 → 添加镜像」，选 Push 方向、填目标仓库与个人令牌（令牌需含 `repo` 权限，否则镜像不可用）
  - **触发与限制**：提交到 Gitee 自动触发同步，也可手动更新；最短触发间隔 5 分钟；Push 方向自动同步分支、标签、提交记录
- **Monorepo 与 pnpm**
  - **Monorepo 是什么**：单仓库管理多个项目 / 模块；相比 MultiRepo，相同版本依赖提升到顶层只装一次省磁盘、工程配置一致、一次命令完成部署，代价是无项目级权限管控、仓库体积可达数 G
  - **pnpm 的优势**：相同文件只存一次省磁盘、安装更快；扁平结构避免嵌套冗余，但会带来「幽灵依赖」（未声明的包也能被访问），建议 `.npmrc` 配 `shamefully-hoist = true`
  - **pnpm 基本使用**：`pnpm -w add -D <dep>` 装到 workspace 根、`pnpm --filter <pkg> add <dep>` 装到子包；workspace 内用 `workspace:` 协议互链，避免手写 `npm link`
- **最小实现**
  - **`mini-dev-hmr.html`**：轮询「变更信号」决定取用哪一版，体会协作中「现在该拿哪一版」的通病

### 03-调试技巧

- **launch.json 核心字段**
  - **启动与目标字段**：`type`（node / google-chrome 等调试器类型）、`request`（launch 启动新进程 vs attach 附加已运行进程）、`program` 入口文件、`runtimeExecutable` 运行可执行文件（如 `"npm"`）
  - **环境与输出字段**：`cwd` 工作目录、`args` 命令行参数、`env` 环境变量、`console` / `externalConsole` 输出位置
  - **调试控制字段**：`skipFiles` 跳过无需调试的文件（如 `<node_internals>/**`）、`sourceMaps` 是否启用 source map、`preLaunchTask` 启动前编译任务、`outFiles` 映射源码与编译产物
- **三种入口调试**
  - **普通入口文件**：`program` 指向入口（如 `${workspaceFolder}\bin\index.js`）配 `args` 传参，F5 即可断点调试
  - **npm 脚本入口**：`runtimeExecutable: "npm"` + `args: ["run", "start:dev"]`，适合 Nest / Express 等需经过构建脚本的框架项目
  - **scripts 快捷 Debug 入口**：package.json 的 scripts 旁直接点 Debug 按钮，自动生成配置，不用手写 `runtimeExecutable`
- **断点类型**
  - **普通断点（Breakpoint）**：执行到该行停住，用于定位到某行就中断
  - **条件断点（Conditional Breakpoint）**：表达式成立才停住，适合循环中带条件过滤
  - **Logpoint 日志点**：不停顿只打日志，表达式处用 `{}` 包裹变量，避免写 `console.log`
  - **Triggered 触发断点**：与条件断点功能接近
- **浏览器调试**
  - **Sources 断点调试**：Chrome DevTools 源码行号点断点，调试控制栏暂停 / 单步 / 进入跳出函数
  - **Console 与 watch**：断点暂停时 Console 可实时求值（Evaluate in console）、watch 面板监视表达式值变化
  - **Performance 性能分析**：录制后看主线程时间线（Main）定位长任务 / 脚本执行 / 布局重排，结合 Network 面板定位慢请求与大资源
- **Node 浏览器调试**
  - **`node --inspect-brk index.js`**：停在入口等待调试器连接，并起 ws（WebSocket）调试服务
  - **`chrome://inspect/` 连接**：看到可调试目标点击进 DevTools；没有时「Configure…」添加 `localhost:9229`（默认调试端口）
  - **框架项目**：Nest 等提供 `start:debug` 脚本，以调试端口启动后在 `chrome://inspect/` 连接对应进程
- **统一认识**
  - **断点调试的本质**：调试客户端（VS Code / DevTools）通过调试协议连接可中断执行的运行环境，在命中断点处暂停查看调用栈与变量、单步执行；掌握 `launch` 与 `attach` 两种请求即可套用到任意运行时

### 04-CI/CD 自动化

- **术语厘清**
  - **CI 持续集成**：频繁合并小改动并自动验证，到构建 + 测试
  - **CD 交付（Continuous Delivery）**：随时可发布到生产，到构建 + 测试 + 可部署产物
  - **CD 部署（Continuous Deployment）**：验证通过自动上线；生产环境往往保留「一键 / 审批」而非全自动部署
- **GitHub Actions 三件套**
  - **workflow → job → step**：workflow 是由事件触发的一组自动化流程，声明在 `.github/workflows/*.yml`；job 是执行单元、可并行可依赖；step 是 job 内一步（一个命令或一个 action）
  - **事件触发**：`push` / `pull_request` 按分支过滤 + `workflow_dispatch` 手动触发
  - **job 依赖与产物传递**：`needs` 声明依赖（quality → build → deploy）；`actions/upload-artifact` 上传产物、`actions/download-artifact` 供下游发布 job 使用，密钥经 `secrets.*` 仅运行时注入
- **流水线设计**
  - **尽早失败**：lint / test 便宜且快放最前，避免在昂贵构建后才报低级错误；PR 阶段只跑 quality，合并后才跑完整发布
  - **各阶段 gate**：lint（ESLint / Prettier / commitlint，error 拒绝合入）→ test（单测 / 覆盖率，低于阈值 reject）→ build（多环境构建、产物 hash、版本标记）→ deploy（上传 CDN、灰度，冒烟通过 + 监控无异常才上线）
  - **产物与缓存**：`actions/setup-node` 配 `cache: "pnpm"` 自动缓存依赖，构建产物也开启缓存，CI 提速显著
- **环境管理**
  - **多环境分层**：dev（每次 push 自动）、test / staging（合并主干自动）、pre-production（上线前验证）、production（审批 / 灰度）
  - **environment 审批**：GitHub Actions 的 `environment` 为生产配置独立 secrets 与 approvers，实现「生产部署需人工审批」
  - **环境变量分层注入**：构建期 `NODE_ENV` / `VITE_API_BASE` / 版本编译进产物，部署期目标环境 / baseURL / 域名运行时注入
- **凭据安全**
  - **核心原则**：密钥永不写进代码或 yml 明文，放 secrets 仅运行时注入；`permissions` 收窄最小权限（如发布 job 只 `contents: read`）
  - **OIDC 与审计清单**：OIDC 替代长期 token 避免静态凭据；检查密钥都在 secrets、每 job 最小权限、生产部署有审批层、fork 提交不获 secrets、日志不回显敏感值（mask）
- **最小实现**
  - **`pipeline-demo.html`**：浏览器里跑 build → test → deploy 最小流水线，每步设门禁、任一步失败即终止，含灰度放量与一键回滚

### 05-质量体系与测试

- **规范治理工具链**
  - **分层工具链**：ESLint（质量与潜在问题）、Prettier（格式）、lint-staged（只查本次改动文件）、husky（注入 git hook）、commitlint（提交信息规范）各管一档、时机清晰
  - **接入方式**：`npx husky init` 生成 `.husky/pre-commit` 跑 `npx lint-staged`；lint-staged 按 `*.{ts,tsx,js,vue}` 等模式对暂存文件执行 `eslint --fix` + `prettier --write`
  - **commitlint 规范**：`type(scope): subject` 约定式提交，`@commitlint/config-conventional` 提供 `feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `chore` / `ci` / `revert` 等 type
- **自定义 ESLint 规则**
  - **规则结构**：规则本质是返回 `meta`（type / docs / messages / fixable）与 `create` 的对象
  - **AST 监听与报告**：在 `create` 里监听 AST 节点（如 `CallExpression`），命中即 `context.report` 报错，可带 `fix` 实现自动修复
- **测试在体系中的位置（详见测试体系模块）**
  - **分层角色**：静态检查提交前拦截；单测与组件测试合并前必过；E2E 在发布前把关键路径；覆盖率只卡增量
  - **写法不在本篇**：单测（替身与假定时器）、组件测试（契约与查询）、E2E（稳定性）、覆盖率真相见[测试体系](../测试体系/总结.md)模块
- **覆盖率与质量门禁**
  - **覆盖率指标**：行覆盖率（被执行代码行占比）、分支覆盖率（if / switch 分支）、函数覆盖率（被调用函数占比）
  - **thresholds 配置**：vitest.config.ts 配 `coverage.thresholds`（如 lines 80 / functions 80 / branches 70 / statements 80）
  - **CI 门禁落地**：`pnpm lint && pnpm test:coverage` 任一失败退出码非 0、pipeline 变红，让「质量不达标就不让合入」成为硬约束
- **覆盖率之外的信号**
  - **同质重复代码**：SonarQube / CodeQL 扫描
  - **依赖漏洞**：`npm audit` / Dependabot 检查
  - **复杂度与 SLO 回归**：ESLint `complexity` 规则限制复杂度，性能 / 错误率监控看 SLO 回归
- **最小实现**
  - **`lint-demo.html`**：用「规则数组 + 正则」逐条扫描代码，命中则报错 / 扣分并给出门禁结论，看清规范工具的本质

### 06-发布、灰度与监控

- **四种发布策略**
  - **蓝绿（Blue / Green）**：两套环境轮流上、切换点共存、一次性切换、回滚极快（切回蓝），适合后端服务
  - **滚动（Rolling）**：逐台分批替换、短暂共存、回滚速度中，适合后端多实例
  - **金丝雀（Canary）**：先小流量试运行再放量、长期共存逐渐引流（1% 逐步增大），适合后端 / 功能
  - **灰度（Gray）**：按用户 / 区域 / 渠道分桶、按比例 / 条件放量；前端资源是静态文件，最常用灰度 + 即时可控的 CDN 发布
- **不可变部署**
  - **内容 hash 产物**：产物文件名带内容 hash（`main.8f3c12b1.js`），每个版本是 CDN 上独立、永不修改的对象，旧资源不被覆盖
  - **构建期自动注入**：Vite 的 `build.rollupOptions.output` 配 `entryFileNames: 'assets/[name]-[hash].js'` 等即可生成
  - **版本切换**：切换版本 = 发布新的 index.html 指向新 hash 资源 + 新资源缓存失效；不覆盖旧对象，因此回滚只需指回旧入口
- **CDN 缓存策略**
  - **缓存 TTL 分层**：带 hash 静态资源长缓存（max-age 一年 + `immutable`），index.html 短缓存 / `no-cache` 每次回源拉到最新入口
  - **发布流程**：构建带 hash 产物 → 批量上传 CDN（按版本目录）→ 预热 / 刷新缓存 → 冒烟验证 → 交给发布系统更新入口 / 灰度
  - **前端灰度三种手段**：入口级（网关 / CDN 按 cookie / header 分流到不同版本 index.html）、脚本级（index.html 模板按策略渲染资源标签）、路由级（服务端下发 featureFlag）
- **灰度预案与回滚**
  - **灰度前清单**：明确比例与分桶口径（uid / ip / 设备 / 地域）、定义健康 / 失败指标（错误率 / 首屏 / 崩溃率）、设定自动熔断、准备回滚
  - **灰度决策流**：开始放量 1% → 观察指标，健康则逐步 5% → 20% → 50%，不健康则熔断自动缩量 / 回滚到上一版本
  - **三种回滚方式**：资源回滚（入口指回旧 hash，极快无需重建）、重建回滚（重新构建上一版本 commit，耗时可能引入差异）、功能回滚（关闭 featureFlag，无需发布）；基石是不可变产物 + 版本与入口映射
- **可观测性三大支柱**
  - **Logs（日志）**：Sentry 错误日志 / 用户行为日志 / 接口错误堆栈
  - **Metrics（指标）**：FP / FCP / LCP、JS Error 率、API 错误率、崩溃率，埋点 SDK / RUM 采集；Core Web Vitals 良好线为 LCP < 2.5s、INP < 200ms、CLS < 0.1
  - **Traces（链路）**：与后端 OpenTelemetry 打通 traceId，前后端串联定位慢接口
- **稳定性保障体系**
  - **预防**：lint、测试门禁、发布前置校验
  - **抑制**：错误边界（Vue `errorCaptured` / React `ErrorBoundary`）
