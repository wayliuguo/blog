# cd-lab · 交付与质量配套实验台

Node 内置模块 + 仓库根已有的 ESLint 8（`lint` 场景用真 ESLint，其余零依赖）。三个场景分别是**增量 lint 的代价、覆盖率阈值的分辨力、灰度早停的参数**。

```bash
npm run lint        # 全量 lint vs 只 lint 改动文件（真 ESLint 8 实测耗时）
npm run coverage    # 覆盖率阈值：拦截率 / 召回 / 误杀（蒙特卡洛模型）
npm run release     # 灰度分批：什么时候该喊停（蒙特卡洛模型）
npm run list        # 列出全部场景
```

> `lint` 场景依赖 ESLint 8。它默认从仓库根 `node_modules` 解析；如果你的实验台是被单独拷出去的，用 `ESLINT_DIR=/path/to/project npm run lint` 指向一个装了 eslint 的目录，或者 `npm i -D eslint@8`。

## 一、场景对照表

| npm script | 对照的是什么 | 读哪个数 |
|---|---|---|
| `lint` | 1000 个文件的样品工程：全量 lint vs 只 lint 改动的 12 个 | 耗时、被检查文件数、报出的问题数 |
| `coverage` | 卡「全项目覆盖率」vs 卡「改动文件覆盖率」，阈值 60/70/80/90 | 召回（抓到真缺陷）与误杀（拦掉好改动） |
| `release` | 跑满再判 vs 每批都判 vs 最小样本量定太大 | 坏版本平均受影响用户比例、误回滚率 |

## 二、哪些是实测，哪些是模型

这一点必须分清，否则数字会被误用：

- **`lint` 是实测**。真 ESLint 8、真文件、真计时。结论（总耗时对文件数线性、单文件耗时恒定）可以直接外推。
- **`coverage` 和 `release` 是模型**。真实项目里没有「这次改动有没有缺陷」「这个版本是不是坏的」这种现成标签，召回率不可能拿真数据算出来。模型做的是**把抽样误差和权衡关系量化**，价值在形状（阈值提高 → 召回和误杀同时上升；最小样本量太大 → 早停失效），不在绝对数值。所有假设都写成脚本顶部的常数，改常数就能复现你自己的场景。

## 三、结构

```
cd-lab/
├─ cli.mjs                 命令行入口：node cli.mjs <场景名>
├─ harness/table.mjs       中英混排对齐的表格与单位换算
├─ scenarios/
│  ├─ lint.mjs             真 ESLint 8：全量 vs 增量，外加跨文件盲区演示
│  ├─ coverage.mjs         覆盖率阈值的拦截率 / 召回 / 误杀
│  └─ release.mjs          灰度分批与回滚决策
└─ fixtures/               运行时生成的样品工程（已 gitignore，不入库）
```

## 四、已知取舍

- **不重复造随机**。三个场景都用固定种子的 mulberry32，同一个种子每次跑出同一张表，方便复现与前后对比。
- **`lint` 的样品工程每次运行都会重新生成**。1000 个文件写完约 1 秒，换来的是不往仓库里塞一堆样例代码。
- **ESLint 用仓库根的那一份**，不在实验台里 `npm install eslint`——否则会多出一份几千行的 lock 文件，而它对这个仓库的内容没有价值。
- **`lint` 取的是 3 轮中位数**。ESLint 首次调用要加载规则和解析器，第一轮明显偏慢，取首轮会高估全量 lint 的代价。
