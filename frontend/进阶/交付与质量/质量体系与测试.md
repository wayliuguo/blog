# 质量体系与测试

代码写得对不止靠"细心"，更要靠一套从"写代码之前"到"合并之前"的治理体系。它由静态治理（ESLint 自定义规则 / Prettier / husky / commitlint）、分层测试与质量门禁交织而成，把"质量不达标就不让合入"变成硬约束。本篇聚焦**治理与门禁**；分层测试的写法（单测、组件测试、E2E、覆盖率真相）见[测试体系](../测试体系/总结.md)模块。

## 一、分层治理工具链

| 工具 | 治理对象 | 时机 |
| ---- | ---- | ---- |
| ESLint | 代码质量与潜在问题 | 编辑器 + 提交前 |
| Prettier | 代码格式 | 编辑器 + 提交前 |
| lint-staged | 只检查本次改动的文件 | git 提交前 |
| husky | 注入 git hook | git 事件触发 |
| commitlint | commit message 规范 | git commit 前 |

这一层的价值在于**零维护成本**：规则写一次，所有人、所有分支、每一次提交都在跑，不需要任何人维护用例。

## 二、husky + lint-staged 接入示例

在较新的 husky 中，用 `husky init` 初始化并创建 hook 文件：

> 示意片段（无配套脚本）

```bash
npx husky init
```

生成 `.husky/pre-commit`：

> 示意片段（无配套脚本）

```sh
npx lint-staged
```

`package.json` 中声明：

> 示意片段（无配套脚本）

```json
{
  "lint-staged": {
    "*.{ts,tsx,js,vue}": ["eslint --fix", "prettier --write"],
    "*.{css,json,md}": ["prettier --write"]
  }
}
```

关键取舍：**pre-commit 只做增量检查**。全量测试放进 pre-commit，提交一次要等几分钟，团队很快就会养成 `--no-verify` 的习惯 —— 门禁也就名存实亡。重活交给 CI。

## 三、ESLint 自定义规则

内置规则不足以表达团队约束时，写自定义规则。规则本质是一个返回 `meta` 与 `create` 的对象：

> 示意片段（无配套脚本）

```js
// rules/no-console-errors.js
module.exports = {
  meta: {
    type: 'problem',
    docs: { description: 'Disallow console.error in production code' },
    messages: { avoid: '避免在业务代码中使用 console.error' },
    fixable: 'code',
  },
  create(context) {
    return {
      CallExpression(node) {
        if (isConsoleErrorCall(node)) {
          context.report({
            node,
            messageId: 'avoid',
            fix(fixer) {
              return fixer.remove(node);
            },
          });
        }
      },
    };
  },
};
```

> 示意片段（无配套脚本）

```js
function isConsoleErrorCall(node) {
  return (
    node.callee &&
    node.callee.type === 'MemberExpression' &&
    node.callee.object &&
    node.callee.object.type === 'Identifier' &&
    node.callee.object.name === 'console' &&
    node.callee.property &&
    node.callee.property.name === 'error'
  );
}
```

自定义规则适合表达这类"通用规则表达不了"的团队约束：禁止直接调用某个危险 API、强制埋点、禁止跨层引用。但要注意，**规则能自动修复（fixable）才有生命力**，否则会变成人人嫌的噪音。

## 四、commitlint 规范提交

使用 Conventional Commits 风格约定：`type(scope): subject`。

配置 `.commitlintrc.json`：

> 示意片段（无配套脚本）

```json
{
  "extends": ["@commitlint/config-conventional"]
}
```

常用 type：`feat` `fix` `docs` `style` `refactor` `perf` `test` `chore` `ci` `revert`。

规范提交不只是好看：它让 changelog 可以自动生成，也让"这次发布包含哪些改动"可以被机器回答 —— 出事故时这是最快的定位线索。

## 五、测试在质量体系中的位置

测试的**分层与写法**是独立的一块能力，这里只说明它在质量体系里承担的角色：

| 层 | 在门禁里的角色 | 详见 |
| ---- | ---- | ---- |
| 静态检查 | 提交前拦截，最便宜的一层 | 本篇第一至四节 |
| 单元测试 | 合并前必过，定位最准 | [单元测试深入](../测试体系/单元测试深入.md) |
| 组件测试 | 合并前必过，覆盖渲染与交互 | [组件测试](../测试体系/组件测试.md) |
| E2E | 发布前把关关键路径 | [E2E 与稳定性](../测试体系/E2E%20与稳定性.md) |
| 覆盖率 | 只卡增量，不做 KPI | [测试基建与门禁](../测试体系/测试基建与门禁.md) |

先测什么、测到什么程度由**测试点分级**（P0/P1/P2）决定，不按覆盖率数字决定 —— 详见[测试策略与分层](../测试体系/测试策略与分层.md)。

## 六、覆盖率与质量门禁

### 1. 覆盖率指标

| 指标 | 含义 |
| ---- | ---- |
| 行覆盖率(Statements) | 被执行过的代码行占比 |
| 分支覆盖率(Branches) | 被覆盖的 if/switch 分支占比 |
| 函数覆盖率(Functions) | 被调用过的函数占比 |

分支覆盖通常比行覆盖更难达标，也更有信息量。

### 2. 覆盖率配置与门槛

> 示意片段（无配套脚本）

```ts
// vitest.config.ts
export default defineConfig({
  test: {
    coverage: {
      provider: 'v8',
      include: ['src/**/*.{ts,vue}'],
      thresholds: {
        lines: 80,
        functions: 80,
        branches: 70,
        statements: 80,
      },
    },
  },
});
```

阈值不达标时命令以非 0 退出码结束 —— 这就是门禁的技术基础。但阈值策略要谨慎：**存量代码只卡增量覆盖率**，否则老项目等于禁止合并；核心目录可以设高阈值，配置与脚本不设。这部分的完整讨论见[测试基建与门禁](../测试体系/测试基建与门禁.md)。

### 2.1 阈值到底拦住了什么：量化一次

"覆盖率卡 80%" 是一句没有信息量的话——它没说清拦住了多少真缺陷、又误杀了多少正常改动。真实项目里没有「这次改动有没有缺陷」这种现成标签，召回率算不出来，所以用蒙特卡洛给它打上上帝视角的标签再看：

> 摘自 `./code/cd-lab/scenarios/coverage.mjs`（运行：`npm run coverage`）

```js
/** 算一组指标：拦截率 / 召回（抓到多少真缺陷）/ 误杀（拦了多少好改动）/ 精确率 */
function evaluate(changes, blocked) {
    let hit = 0
    let goodHit = 0
    const badTotal = changes.filter(c => c.bad).length
    const goodTotal = N - badTotal
    let caught = 0
    for (const c of changes) {
        if (!blocked(c)) continue
        hit++
        if (c.bad) caught++
        else goodHit++
    }
    const recall = caught / badTotal
    const fpr = goodHit / goodTotal
    return {
        blockedRate: hit / N,
        recall,
        fpr,
        precision: hit ? caught / hit : 0
    }
}
```

**卡「全项目覆盖率」**（项目基线 72%、存量 20 万行）：

| 阈值 | 拦截率 | 召回（抓到真缺陷） | 误杀（拦掉好改动） | 精确率 |
| ---- | ---- | ---- | ---- | ---- |
| 60% | 0.0% | 0.0% | 0.0% | 0.0% |
| 70% | 0.0% | 0.0% | 0.0% | 0.0% |
| 80% | 100.0% | 100.0% | 100.0% | 15.3% |
| 90% | 100.0% | 100.0% | 100.0% | 15.3% |

它的行为是**二值的**：70% 时几乎不拦，80% 时几乎全拦。因为一次改动只有几十行，被 20 万行存量稀释后，全项目覆盖率的变化落在小数点后第三位。**它要么永远不响、要么永远在响，中间没有可用的分辨力。**

**卡「改动文件的覆盖率」**：

| 阈值 | 拦截率 | 召回 | 误杀 | 精确率 |
| ---- | ---- | ---- | ---- | ---- |
| 60% | 34.2% | 100.0% | 22.3% | 44.7% |
| 70% | 53.4% | 100.0% | 44.9% | 28.7% |
| 80% | 72.5% | 100.0% | 67.5% | 21.1% |
| 90% | 90.6% | 100.0% | 88.9% | 16.9% |

这次阈值才有分辨力：召回随阈值升高，误杀也随阈值升高。**没有"正确的阈值"，只有"你愿意用多少误杀换多少召回"。**

**对照：靠测试失败来拦**

| 信号 | 拦截率 | 召回 | 误杀 | 精确率 |
| ---- | ---- | ---- | ---- | ---- |
| 测试失败 | 11.8% | 66.3% | 2.0% | 85.7% |

它比任何覆盖率阈值都准，因为它是**行为信号**（代码跑起来不对），覆盖率只是**存在性信号**（有没有测试碰过这行）。覆盖率拦不住最危险的一类：测试跑过这行、断言写得太弱（只测了不抛错），覆盖率是绿的，缺陷照样上线——这类只能靠评审和变异测试。

> ⚠️ 上面这些是**模型**不是实测（真实数据里没有"有没有缺陷"这个标签）。价值在形状：阈值提高会同时抬高召回与误杀；卡全项目等于没卡。假设都写成脚本顶部的常数，改常数就能复现你自己的场景。

### 3. 质量门禁在 CI 中的落地

> 示意片段（无配套脚本）

```
<push / pull_request>
      │
      ▼
  lint(ESLint+Prettier+commitlint) ──失败→ 拒绝
      │成功
      ▼
  单测 + 覆盖率阈值           ──失败/不达标→ 拒绝
      │成功
      ▼
  组件测试 + E2E            ──失败→ 拒绝
      │成功
      ▼
  gate 全绿 → 允许合并 / 进入需要审批的部署流程
```

在 CI 中直接失败退出码即"门禁"：

> 示意片段（无配套脚本）

```bash
pnpm lint && pnpm test:coverage   # 任一失败，命令退出码非 0，pipeline 红
```

### 4. 覆盖率之外的"质量信号"

质量门禁不止覆盖率：

| 信号 | 工具 |
| ---- | ---- |
| 同质重复代码 | SonarQube / kodethon / CodeQL |
| 依赖漏洞 | `npm audit` / Dependabot |
| SLO 回归 | 性能/错误率监控(见[发布、灰度与回滚](./发布、灰度与回滚.md)) |
| 复杂度 | ESLint `complexity` 规则 |

## 七、质量闭环

治理不是一串孤立的检查，而是一条从本地到线上的闭环：

```
写代码（编辑器提示）→ 提交（husky + lint-staged + commitlint）
    → CI（类型/规范/测试/覆盖率/构建）→ 灰度发布
    → 线上监控（错误率/性能指标）→ 反哺规范与用例
```

最后一环最常被忽略：线上发现的问题，应该沉淀成一条规则或一个用例，否则同一个坑会踩第二次。
