# 发布、灰度与监控

把新版本安全地送到用户面前，是一门"既要快又要稳"的玄学。一旦发布有误，影响的是成百上千万用户。本文深入发布策略（蓝绿 / 金丝雀 / 灰度 / 滚动）、前端资源版本与不可变部署、CDN 发布、灰度预案与回滚，并落到"可观测性"（日志 / 监控 / 链路）与前端的稳定性保障。

## 一、发布策略总览

### 1. 四种主流策略对比

| 策略 | 原理 | 新旧共存 | 影响范围 | 回滚速度 | 典型场景 |
| ---- | ---- | ---- | ---- | ---- | ---- |
| 蓝绿(Blue/Green) | 两套环境轮流上 | 双环境在切换点共存 | 一次性切换 | 极快(切回蓝) | 后端服务 |
| 滚动(Rolling) | 逐台分批替换 | 短暂共存 | 逐台 | 中 | 后端多实例 |
| 金丝雀(Canary) | 先小流量试运行再放量 | 长期共存、逐渐引流 | 从 1% 逐步增大 | 快 | 后端/功能 |
| 灰度(Gray) | 按用户/区域/渠道分桶 | 长期共存 | 按比例/条件 | 快 | 前端/移动端 |

> **对前端而言**：前端资源是静态文件，往往没有"多实例逐步替换"的滚动，最常用的是**灰度 + 即时可控的 CDN 发布与回滚**。

### 2. 发布策略如何选择

| 决策维度 | 倾向 |
| ---- | ---- |
| 变更风险低 | 快速全量即可 |
| 变更风险高/用户量大 | 灰度 + 金丝雀逐步放量 |
| 需要 AB / 分地区验证 | 按环境或分桶灰度 |
| 追求极致回滚效率 | 蓝绿 + 不可变产物 |

## 二、前端资源版本与不可变部署

### 1. 为什么"不可变"很重要

**可变部署**：同一个文件名 `app.js` 被覆盖，用户可能拿到"新旧混合"的资源，且缓存失效困难。

**不可变部署**：产物文件名带内容 hash（`main.8f3c12b1.js`），每个版本在 CDN 上是一个**独立的、永不修改的对象**。旧的资源不会被覆盖，直到自然过期或主动清理。

> 示意片段（无配套脚本）

```
旧: app.js           ← 覆盖式，无法精确切版本
新: app.8f3c12b1.js   ← 内容 hash，唯一且不可变
    app.4aa209f7.js
```

### 2. 构建期自动注入 hash

以 Vite 为例，`build.rollupOptions.output` 或默认配置即生成带 hash 的文件：

> 示意片段（无配套脚本）

```ts
// vite.config.ts
export default defineConfig({
  build: {
    rollupOptions: {
      output: {
        entryFileNames: 'assets/[name]-[hash].js',
        chunkFileNames: 'assets/[name]-[hash].js',
        assetFileNames: 'assets/[name]-[hash].[ext]',
      },
    },
  },
});
```

产物示例：

> 示意片段（无配套脚本）

```
dist/
├── index.html
└── assets/
    ├── main-8f3c12b1.js
    ├── vendor-d38fe002.js
    └── index-abc123.css
```

### 3. 不可变部署的版本切换

> 示意片段（无配套脚本）

```
版本 V1: index.html 引用 main-a.js
版本 V2: index.html 引用 main-b.js(新的确)
切换 = 发布新的 index.html(指向新 hash 资源) + CDN 缓存失效新资源
```

`index.html` 是"入口"，通过更新入口指向新 hash 资源实现切版本。由于 V2 的静态资源是全新对象，不会与 V1 混用，这正是"不可变"带来的回滚便利。

## 三、CDN 发布

### 1. CDN 为什么必须配合前端发布

- 前端资源经过 CDN 加速，`index.html` 和静态资源缓存在边缘节点。
- 缓存 TTL：静态资源带 hash 可长缓存（如 `max-age=31536000`、`immutable`）；`index.html` 应短缓存或 `no-cache`（需回源校验）。

> 示意片段（无配套脚本）

```
静态资源(app.*.js/css/img)   → max-age 一年, immutable  → 复用 CDN 缓存
index.html                   → no-cache / 短 TTL       → 每次回源拉到最新入口
```

### 2. 一条 CDN 发布流程

> 示意片段（无配套脚本）

```
构建出带 hash 的产物(如 dist/)
   │
   ▼ 批量上传到 CDN(对象存储/OSS/S3)，版本目录如 /2026/09/10/v2.3.0/
   │
   ▼ 预热/刷新 CDN 缓存(尤其 index.html 与部分大资源)
   │
   ▼ 验证线上可用(target 一套资源 URL 冒烟)
   │
   ▼ 交给发布系统更新入口/灰度
```

### 3. 前端灰度常用手段

| 手段 | 原理 | 实现 |
| ---- | ---- | ---- |
| 入口级灰度 | 让不同用户拿到不同的 `index.html` | 网关/CDN 根据 cookie/header 分流到不同版本入口 |
| 脚本级灰度 | 不同命名的资源，用户拉新 or 旧 | 通过 `index.html` 模板按策略渲染资源标签 |
| 路由级灰度 | 同一页面不同功能开关 | 服务端下发 featureFlag |

### 4. 入口级灰度示意

> 示意片段（无配套脚本）

```
用户请求 /  → 网关判断分流
   ├─ 灰度量(如 5%)   → index_v2.html (指向 v2 资源)
   └─ 其余 95%        → index.html (v1 资源)
当灰度指标健康 → 逐步调大百分比 → 全量切换到 v2 入口
```

## 四、灰度预案与回滚

### 1. 灰度前的核心清单

- [ ] 明确灰度比例、分桶口径（uid/ip/设备/地域）。
- [ ] 定义"健康/失败"判定指标（错误率、首屏、崩溃率）。
- [ ] 设定自动熔断：指标越界即暂停放量并告警。
- [ ] 准备回滚：可秒级切换到上一个版本入口。
- [ ] 通知与值班：发布期间有人盯监控。

### 2. 灰度的决策流

> 示意片段（无配套脚本）

```
开始放量(1%)
   ▼ 观察 N 分钟
指标健康? ──否──▶ 熔断:自动缩量/回滚到上一版本
   │是
   ▼
增加放量(逐步 5%→20%→50%)
   ▼ 每步观察
最终全量 or 保留下沉放量(部分用户)      ← 若发现回归，从 全量回滚 用上一版本入口
```

### 3. 分批的三个参数：量化一次

"5% → 20% → 50% → 100%"这句话里藏着三个没有默认值的参数：批次梯度、**最小样本量**、判据阈值。最小样本量尤其容易定错。用蒙特卡洛把它量化出来（坏版本错误率 1.6%，基线 0.4%，同时盯 3 个指标）：

> 摘自 `./code/cd-lab/scenarios/release.mjs`（运行：`npm run release`）

```js
function release(rand, isBad, { minSample, lastOnly }) {
    const p = isBad ? BAD_ERR : BASE_ERR
    for (let i = 0; i < BATCHES.length; i++) {
        const b = BATCHES[i]
        // lastOnly：只在最后一批判一次（"跑满再看"的做法）
        if (lastOnly ? i !== BATCHES.length - 1 : b.samples < minSample) continue
        // 三个指标各抽一次：任一超过基线的 2 倍就回滚
        let triggered = false
        for (let m = 0; m < METRICS; m++) {
            const se = Math.sqrt((p * (1 - p)) / b.samples)
            const observed = p + gauss(rand) * se
            if (observed > BASE_ERR * 2) triggered = true
        }
        if (triggered) return { stopBatch: i + 1, exposedRatio: b.ratio, caught: true }
    }
    return { stopBatch: BATCHES.length, exposedRatio: 1, caught: false }
}
```

| 策略 | 坏版本：平均受影响用户 | 坏版本：漏放率 | 坏版本：第几批发现 | 正常版本：误回滚率 |
| ---- | ---- | ---- | ---- | ---- |
| A 跑满 100% 再判 | 100.0% | 0.0% | 4.00 | 0.0% |
| B 每批都判（样本 ≥500） | 5.0% | 0.0% | 1.00 | 0.2% |
| C 样本 ≥3000 才判 | 20.0% | 0.0% | 2.00 | 0.0% |

- **A（跑满再判）**：坏版本一个都跑不掉（漏放率 0%），但要等到第 4 批——100% 的用户都吃到了这个坏版本。分批的意义本来就是把最坏情况限制在第一批，跑满再判等于把这个意义取消了。
- **B（每批都判）**：5% 那一批的 2500 个样本已经足够把 1.6% 和 0.4% 分开，绝大多数坏版本第一批就被拦下，代价是正常版本有 0.2% 的误回滚。
- **C（最小样本量 3000）**：第一批只有 2500 个样本"不够"，只能等到第二批——**最小样本量定得比第一批的样本量还大，等于放弃早停**。它把受影响用户从 5% 抬到了 20%，却没有换来任何额外收益（漏放率和误回滚率都是 0）。

误回滚为什么必然存在：正常版本的错误率本身就是 0.4%，抽样有波动，样本越少波动越大；这里同时盯 3 个指标，任一超线就回滚——**每多盯一个指标，误回滚就多一次机会**。这是多重比较问题：盯 10 个指标，就算版本完全正常，也总有某个指标"看起来变差了"。

应对不是"少盯几个"，而是：① 只对核心指标设自动回滚，其余只告警 ② 用置信区间而不是点估计判断 ③ 自动回滚要能一键改回，别让人不敢用。

> ⚠️ 同样是**模型**不是实测。真线上不可能反复发布同一个坏版本去统计"平均第几批发现"。价值在形状：**最小样本量要小于第一批能拿到的样本，否则早停形同虚设。**

### 4. 前端回滚的两种方式

| 方式 | 做法 | 优点 | 缺点 |
| ---- | ---- | ---- | ---- |
| 资源回滚 | 直接把入口 `index.html` 指回上一版本的 hash 资源 | 极快、无需重新构建 | 依赖上一版本产物仍可用 |
| 重建回滚 | 重新构建并发布上一版本 commit | 产物确定、干净 | 耗时、可能引入新差异 |
| 功能回滚(开关) | 关闭出问题的新 featureFlag | 无需发布 | 只适用于可回退的功能 |

> 前端回滚的基石是**不可变产物 + 版本与入口映射**：只要旧的 hash 资源还在 CDN 上、入口映射可控，就能秒切。因此**不要物理删除最近的 N 个版本**。

## 五、发布视角的可观测信号

可观测性的**完整实现**（Logs / Metrics / Traces 的采集、大盘、告警分级）属于[监控模块](../监控与稳定性/总结.md)的范畴。本篇只讲一件事：**发布与灰度期间，盯哪几个信号来决定"放量还是熔断"**。

### 1. 灰度期间的核心判定指标

| 信号 | 为什么盯它 | 越界意味着 |
| ---- | ---- | ---- |
| JS Error 率 / 捕获率 | 新版本最直观的"有没有炸" | 新代码抛错，立即熔断 |
| 首屏 / LCP | 资源加载或渲染是否劣化 | 可能引入了大依赖或阻塞脚本 |
| API 错误率 / 慢接口 | 前端调用链是否受影响 | 后端或网关侧回归 |
| 灰度版本崩溃率 | 仅灰度组的对比信号 | 新功能自身问题，与全量无关 |

判定逻辑：**灰度组的这些指标，相对全量基线（上一版本）有无显著恶化**。没有恶化才逐步放量，恶化就自动熔断回滚。

### 2. 把"现象"翻译成"可决策的数据"

> 示意片段（无配套脚本）

```
放量 1% ──▶ 看 5 分钟：错误率 / LCP / 崩溃率 vs 全量基线
   ├ 无显著恶化  → 5% → 20% → 50% → 全量
   └ 显著恶化    → 熔断（缩量/回滚到上一版本入口）→ 拉监控定位根因
```

这里"定位根因"要回到[排障方法论](./排障方法论.md)与[监控模块](../监控与稳定性/总结.md)：用 source map 还原压缩栈、借监控平台的真实用户上下文，而不是本地猜。本篇的回滚（资源回滚 / 功能开关）只是"止血"，根因要靠监控 + 排障闭环。
