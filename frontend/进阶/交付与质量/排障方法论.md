# 排障方法论

## 一、排障的通用链路

无论问题多复杂，排障都遵循同一条链路，缺一步就容易原地打转：

```
现象（用户/监控报了什么）
   │  先问清楚：必现还是偶发？什么环境？什么操作路径？
   ▼
复现（能稳定复现 = 成功了一半）
   │  找不到复现路径，就先补日志/埋点，别盲改代码
   ▼
定位（缩小到具体模块/函数/数据）
   │  二分、对照、最小化，用工具而不是靠猜
   ▼
假设 → 验证（改一处，验证是否解决，是否引入新问题）
   │
   ▼
沉淀（复现步骤 + 根因 + 防御手段，反哺用例/监控）
```

### 复现三要素

很多排障卡在第一步，是因为没把复现条件说清：

- **稳定复现**：是 100% 触发，还是只有特定数据/特定时序才触发？偶发问题先别急着改，先想清楚触发条件。
- **最小路径**：从首页点进来的 17 步里，哪几步是必需的？能用一个 URL / 一个脚本直达的，绝不靠手点。
- **环境对齐**：本地能复现吗？如果不能，差异在哪（数据 / 构建产物 / 浏览器版本 / 灰度分组）？"我本地是好的"不是结论，是还没找到差异。

## 二、DevTools 定位链路（按什么顺序看）

遇到一个"页面不对劲"，不要一上来就打断点。按代价从低到高的顺序看，往往几分钟就能定位：

### 1. Console：先看报错与警告

- 红色 error 直接给出文件与行号，是最高优先级的线索。
- 黄色 warning（如 React key、antd 废弃 API）常被忽略，但很多"显示异常"根因在这里。
- 断点暂停时可在 Console 用 **Evaluate** 实时计算表达式，比 `console.log` 快得多。

### 2. 断点：定位"值在哪里变了"

在行号左侧点击加普通断点；循环中用**条件断点**（表达式成立才停）；不想打断流程看变量用**日志点（Logpoint）**，用 `{}` 包裹变量，不停顿只输出。命中断点后看调用栈（Call Stack）往上追是谁调进来的。

### 3. Network：定位"数据对不对"

- 看请求是否发出、状态码、响应体、耗时。
- 对比"前端发的"和"后端返的"：是前端拼错了参数，还是后端返了错数据？这是前后端扯皮的高频现场。
- 用 `curl` / 接口工具复现一次请求，排除浏览器环境干扰。

### 4. Performance：定位"为什么慢"

页面卡顿、加载慢时录制 Performance，看**主线程时间线（Main）**找长任务、大量重排重绘、长脚本执行；结合 Network 面板定位慢请求与大资源。性能的测量与口径在[性能模块](../性能优化/总结.md)展开，本文只讲"排障入口"。

### 5. Application / Sources：定位"状态与缓存"

- `localStorage` / `sessionStorage` / `IndexedDB` 里是否有脏数据。
- 是否被旧 Service Worker / 强缓存的 JS 缠住——清缓存或开 DevTools 的 "Disable cache" 验证。

> 顺序的本质：报错（Console）→ 值错（断点）→ 数据错（Network）→ 慢（Performance）→ 状态错（Application）。先易后难，别跳步。

## 三、断点调试的统一模型

无论浏览器还是 Node，"断点调试"的本质都是：**调试客户端（VS Code / DevTools）通过调试协议连接到一个可中断执行的运行环境，在命中断点处暂停，供你查看调用栈与变量、单步执行**。掌握两类请求就能套用到任意运行时：

- **`launch`**：调试器启动一个新进程（如 `node index.js`、`vite`）。
- **`attach`**：调试器附加到一个已经在跑的进程（如已启动的 Chrome 页面、已运行的 Node 服务）。

前端代码既可以在浏览器 DevTools 中直接断点（Sources 面板），也可以通过 VS Code 的 `attach` 连接已启动的页面；Node 服务则用 `--inspect-brk` 暴露调试端口后由 DevTools 连接。

### Node.js 调试（浏览器连调试）

> 示意片段（无配套脚本）

```js
// index.js
const os = require('os');
console.log(os.homedir());
```

以调试模式启动：

> 示意片段（无配套脚本）

```bash
node --inspect-brk index.js
```

`--inspect-brk` 启动后会**停在入口等待调试器连接**，并起一个 ws（WebSocket）调试服务。打开 `chrome://inspect/`，点击可调试目标进入 DevTools；若列表为空，点「Configure…」添加 `localhost:9229`（默认调试端口）。

> 框架项目（如 Nest）通常提供 `start:debug` 脚本，以调试端口启动后同样在 `chrome://inspect/` 连接。

## 四、线上问题怎么复现与定位

本地能复现的问题都好办，**难的是只在线上出现、本地复现不了**的问题。这类问题的排障靠的是"可观测性 + 对照"两条腿。

### 1. 先把现象变成数据

线上不会有人给你贴控制台报错，所以第一步是把"白屏了""偶发崩"翻译成可查的数据：

- 错误率、受影响用户/设备/灰度分组、首次出现时间（对照发布时间点）。
- 有没有特征：只在某个浏览器版本？某个接口超时？某个灰度组？

### 2. 用 source map 把压缩栈还原

线上跑的是带 hash 的压缩产物（`main.8f3c12b1.js`），报错栈是一串 `a.b.c` 和偏移。要定位到源码：

- 构建时生成并上传 **source map**（`.map` 文件）到错误监控平台（如 Sentry），监控平台会用 map 把栈还原成 `src/utils/request.ts:42`。
- source map **不要公开托管在 CDN**——它等于把源码送给任何人；放在监控平台私有存储或带鉴权的地址。

> 示意片段（无配套脚本）

```ts
// vite.config.ts —— 仅生成 map，由上传步骤送到监控平台，不在站点公开
export default defineConfig({
  build: {
    sourcemap: true,          // 生成 .map
    // 生产不把 map 随 dist 上传到公开 CDN
  },
})
```

### 3. 用监控平台定位，而不是靠猜

错误监控平台（Sentry 类）能告诉你：错误发生时的 **URL、浏览器、user、自定义上下文、前几步 breadcrumb**。比本地瞎猜强在——它带着真实用户的真实环境。定位到可疑提交后，对照[发布、灰度与回滚](./发布、灰度与回滚.md)做回滚或开关降级。

### 4. 复现不出的处理：补埋点，别盲改

如果监控数据也看不出根因，**不要凭直觉改代码**——你改的可能根本不是原因。正确做法：

- 在可疑路径加临时日志 / 埋点（上报到监控而非 console）。
- 等下一次真实触发，拿到真实上下文。
- 定位后删埋点、修根因、补一个能拦住回归的用例。

## 五、常见排障场景速查

| 现象 | 优先看 | 典型根因 |
| ---- | ---- | ---- |
| 白屏 | Console error + Network | 入口 JS 加载失败 / 运行时抛错未捕获 |
| 数据不对 | Network 响应体 | 前端拼参错 / 后端返错 / 字段映射错 |
| 偶发崩溃 | 监控 breadcrumb + 灰度分组 | 特定数据时序 / 未覆盖分支 |
| 卡顿 | Performance Main 时间线 | 长任务 / 频繁重排 / 大列表未虚拟滚 |
| 样式错乱 | Elements + 缓存 | 旧 CSS 缓存 / 特异性冲突 |
| 本地好线上坏 | source map + 构建产物 | 构建差异 / 环境变量 / 数据差异 |
