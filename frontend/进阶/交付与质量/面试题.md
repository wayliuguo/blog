## 1. 代码规范与质量门禁

### Q1（1.1）｜ ESLint 与 Prettier 的分工？

- **判断**：ESLint 管"代码质量与规范"，Prettier 管"格式化"——两者各司其职、互不重叠。
- **展开**：ESLint 是规则引擎，能发现逻辑级问题（未定义/未使用变量、危险 API、复杂度）；Prettier 是纯格式化器，输出唯一风格（缩进/引号/换行）。ESLint 的 stylistic 规则与 Prettier 冲突时关闭交给 Prettier，用 `eslint-config-prettier` 消除打架。
- **边界**：格式规则放 Prettier、逻辑规则放 ESLint；为什么不能只用 Prettier？→ 它不检查逻辑错误，只改排版。

### Q2（1.1）｜ ESLint 9 flat config 相比 `.eslintrc` 的变化？

- **判断**：配置从"级联继承"变为"显式数组组合"，配置即数据。
- **展开**：`extends` 的隐式解析与 `overrides` 嵌套被取消；插件要显式 `plugins: { vue }` 声明；`ignores` 替代 `.eslintignore`；可被程序化组合是最大收益。
- **边界**：升级成本是旧配置改造；flat config 怎么忽略文件？→ `ignores: ['dist/**']` 数组项。

### Q3（1.2）｜ lint-staged + pre-commit 怎么落地门禁？

- **判断**：husky 挂 pre-commit 钩子，lint-staged 只对暂存文件跑格式化与 lint——检查快、门禁在合入前生效。
- **展开**：husky 生成 git 钩子调用 `lint-staged`；lint-staged 拿暂存文件列表按配置执行（`prettier --write`、`eslint --fix`、`git add`）；只查改动文件避免全库检查拖慢提交。
- **边界**：门禁是"提交前"而非"推送前"；pre-commit 太慢怎么办？→ 只做增量检查，重活（完整测试）放 CI。

### Q4（1.4）｜ 质量门禁分几层？各层拦什么？

- **判断**：按"发现成本从低到高"排：静态检查（提交前）→ 单元/组件测试（合并前）→ E2E（发布前）→ 灰度监控（发布后）。
- **展开**：越靠前的层越便宜、定位越准——静态检查零维护成本、单测定位到函数、E2E 只能告诉你"某条路径挂了"、线上监控是最后兜底。
- **边界**：门禁不是越多越好，pre-commit 只做增量检查，否则团队会养成 `--no-verify` 的习惯、门禁名存实亡；各层怎么写？→ 分层测试的写法见[测试体系](../../进阶/测试体系/总结.md)模块。

### Q5（1.3）｜ commit message 规范的意义？

- **判断**：提交信息是"变更的说明书"——让历史可检索、可追溯，可自动生成 changelog 与触发语义化发布。
- **展开**：约定式提交（`feat:`/`fix:`/`refactor:` 等）让 commit 分类可机器识别；配合 commitlint 门禁与 changelog 生成；关联 issue/PR 提供上下文。
- **边界**：规范的价值在可检索与自动化，不是形式主义；描述应说"为什么改"，而不是复述代码；commitlint 怎么落地？→ husky 的 commit-msg 钩子校验消息格式。

### Q6（1.4）｜ 代码评审（CR）应该关注什么？

- **判断**：CR 重点看契约与风险，不是抠代码风格——接口契约（入参/返回/兜底）→ 状态与副作用 → 兼容与降级 → 埋点覆盖新增分支。
- **展开**：契约错是运行期才暴露的错；状态与副作用决定可测性与内存安全；兼容与降级决定存量用户是否受损；埋点保证新增逻辑可观测。
- **边界**：CR 不替代自动化检查——格式、lint 交给机器，人只审逻辑与取舍；CR 过慢怎么办？→ 小步提交 + 关注点清单（契约/副作用/兼容/埋点），PR 控制在可审规模。

### Q7（1.4）｜ `merge` 与 `rebase` 的区别与取舍？

- **判断**：merge 保留历史分叉（记录真实协作），rebase 线性化历史（整洁但改写提交）。
- **展开**：merge 生成一个合并提交、保留两分支历史；rebase 把当前分支提交"重放"到目标分支顶部，历史线性；rebase 的冲突在逐个提交时解决。
- **边界**：rebase 改写已推送提交会破坏他人工作（需 force push）；公共分支禁用 rebase、私有/特性分支可 rebase；rebase 冲突怎么处理？→ 逐提交解决，解决后 `git rebase --continue`。

### Q8（1.4）｜ Git 分支模型？

- **判断**：分支模型不是越多越好，是按团队节奏选型——主干开发（Trunk-based）追求持续集成，Git Flow 适合固定版本节奏。
- **展开**：主干开发：所有人短分支快速合并回主干、分支存活短、冲突少、随时可发布；Git Flow：develop/feature/release/hotfix 多线并行、按版本发版；两者的本质区别是"发布节奏"与"分支存活时长"。
- **边界**：Git Flow 在小团队/快节奏迭代里流程重；主干开发要求测试与门禁强，否则主干不稳；前端项目适合哪种？→ 通常 Trunk-based + 发布分支，配合按页发布。

## 2. 排障方法论

### Q9（2.4）｜ 真机调试链怎么搭？

- **判断**：真实域名 + whistle 域名代理 + 扫码入口 + vConsole。
- **展开**：导航页链接不能写 `127.0.0.1`（手机上指向手机自己），必须真实域名；whistle 把线上域名代理到本地 dev server；Vite `allowedHosts` 放行（默认拒绝未知 Host 防 DNS Rebinding）。
- **边界**：只配了 dev 没配 preview，构建产物真机预览时找不到页面；为什么 Vite 默认拒绝未知 Host？→ 防 DNS Rebinding 攻击。

## 3. CI/CD 自动化

### Q10（3.3）｜ CI/CD 流水线里前端能做什么？

- **判断**：代码检查 → 单元/组件测试 → 构建 → E2E → 产物上传 → 按页/按包发布 → 灰度放量 → 监控与回滚。
- **展开**：门禁前置（pre-commit lint-staged / pre-push 测试）、构建产物可追溯（版本/哈希）、发布可灰度可回滚。
- **边界**：E2E 慢且脆，放发布前关键路径即可；别让测试成为发布瓶颈；测试在 CI 里失败会怎样？→ 阻断合并与发布，质量门禁兜底。

## 4. 质量体系与测试

### Q11（4.3）｜ 静态检查能替代测试吗？

- **判断**：不能——静态检查只能证明"代码形状对"（类型、引用、规则），测试才能证明"行为对"（输入输出的契约）。
- **展开**：类型系统与 ESLint 是编译期/静态分析，无法覆盖运行时的分支组合、异步时序与真实浏览器行为；反过来，测试也不能替代类型——类型一次声明全局生效，测试只能覆盖被写到的用例。
- **边界**：两者是互补的"成本结构"不同——类型零维护、测试要维护；什么时候该写测试而不是加类型？→ 涉及分支组合与边界值（金额、时间、权限）时。

### Q12（4.3）｜ 测试范围怎么随页面配置自动派生？

- **判断**：页面注册的唯一来源是页面配置，测试范围由配置自动派生——新增页面自动纳入，不用人补配置。
- **展开**：`pages.config.ts` 是单一数据源，测试盘点按配置遍历页面生成测试点清单；新页面加一条配置即进入测试范围与回归清单。
- **边界**：配置派生的是"范围"不是"断言"——具体断言仍需人工或生成；页面形态差异大时派生规则要兜底；派生出来的测试点谁写？→ 先 P0 主流程人工或 AI 生成，P1/P2 按优先级补齐。

### Q13（4.4）｜ 覆盖率当 KPI 会出什么问题？

- **判断**：会出现"为凑数字写无断言测试"——覆盖率上去了，质量没变，还多了一批要维护的脆用例。
- **展开**：覆盖率统计的是"代码被执行到"，不是"行为被验证过"；只调用不断言的用例照样能刷高数字。
- **边界**：正确用法是**存量只卡增量**、核心模块设高阈值、配置与脚本不设；覆盖率当信号、不当目标；分支覆盖为什么比行覆盖更有信息量？→ 详见[测试体系面试题](../../进阶/测试体系/面试题.md)。

### Q14（4.3）｜ `start-server-and-test` 解决什么（flaky）？

- **判断**：解决 E2E 的 flaky——先起服务、等端口就绪、再跑测试，把"启动时序竞争"从用例里消除。
- **展开**：`start-server-and-test` 一条命令串起"启动 server → 轮询端口/URL 就绪 → 执行 test → 结束进程"，避免用例因服务未就绪随机失败。
- **边界**：它解决启动时序、不解决用例本身的脆弱（选择器依赖、异步竞态）——后者要靠稳定选择器与等待策略；还有哪些 flaky 来源？→ 网络延迟、动画时序、测试数据污染。

## 5. 发布、灰度与回滚

### Q15（5.1）｜ 发布策略：按页发布 / 按包发布 / 灰度放量 / 回滚？

- **判断**：发布粒度决定回归成本——MPA 按页构建、按页发布，灰度放量 + 监控指标 + 自动/手动回滚。
- **展开**：按页构建产物独立，单页改动只发布该页；灰度按比例/条件放量观察错误率与成功率；回滚是"回到上一版本产物"。
- **边界**：灰度必须配监控口径（同一套埋点基准），否则放量风险不可观测；灰度观察哪些指标？→ 接口成功率、JS 错误率、白屏率、转化漏斗（产品视角）。

### Q16（5.5）｜ 线上问题怎么从监控定位到发布？

- **判断**：靠"监控 → 定位 → 回滚"三步——先有错误/白屏/接口监控兜住，再按版本与时间线缩小范围，最后回滚上一版本。
- **展开**：监控埋点（JS 错误、白屏、接口成功率）在发布后对比基线；按"版本号 + 时间窗口 + 影响面"定位是哪个发布引入；回滚是发布系统的标准动作（上一版本产物原地切换）。
- **边界**：监控口径与发布前一致才有可比性；回滚要快，前提是"发布产物可追溯、可一键回退"；怎么确认是新版本引入的？→ 对比新旧版本的错误率基线，灰度组 vs 对照组。

### Q17（5.4）｜ 场景：一个新页面要上线，质量保障怎么做全？

- **判断**：从规范到监控形成闭环——生成即合规、分层测试、CR、按页发布 + 灰度、监控与回滚预案。
- **展开**：规范（脚手架/规则文件让代码生成即合规）→ 单测 + 组件测试 + E2E（P0 主流程）→ CR（契约/兜底/埋点）→ 构建产物（单版本 ESM + 按需 polyfill）→ 按页发布 + 灰度 → 监控（错误/白屏/接口）→ 回滚预案。
- **边界**：体系的关键是"自动派生"而非人工清单——新增页面自动纳入测试与回归，否则必然遗漏；测试具体怎么写、怎么防 flaky？→ 见[测试体系](../../进阶/测试体系/总结.md)模块（策略分层 / 单测 / 组件 / E2E 与稳定性 / 基建门禁）。
