# 前端工程化 · 基建实战总串联

前面四篇各自打透了一个切片：全景（工程化解决什么）、模块化（代码怎么组织）、脚手架（结构怎么生成）、Monorepo（多包怎么协作）。但真实项目里它们不是并列的四个开关，而是一条咬合的链——模块化选型决定了包怎么被引用，包管理把多包捏进一个仓库，构建把源码变成可发布的产物，脚手架把"正确结构"固化成一条命令，CI 再把这四步串成门禁。本章用一个目标把四篇串起来：**从 0 搭一个"组件库 + 业务应用"的 Monorepo**，并在每一步指出它对应前面哪一篇。

## 一、目标与边界

我们要建的东西长这样：一个仓库里有两个包——`@demo/ui`（组件库，对外发布）和 `app`（业务应用，消费组件库）。这个最小形态已经逼出了工程化的全部核心决策：

- 组件库用什么模块规范、怎么被应用引用？→ **模块化与包管理**
- 两个包怎么在一个仓库里共存、依赖怎么不重复装？→ **Monorepo 工程化**
- 组件库怎么同时出 ESM/CJS/类型、应用怎么本地起、怎么打生产包？→ **构建体系**
- 新同事怎么一键拿到这个正确结构？→ **脚手架的诞生**
- 上面四步怎么在每次提交时自动跑、不靠人记？→ **CI/CD 自动化**

先定模块规范，因为后面所有环节都建立在"源码长什么样"之上。

## 二、起点：模块化选型决定一切

组件库对外发布，最稳妥的选型是 **ESM + `package.json` 的 `exports` 字段**，而不是把 CJS 当默认。原因在前面的《模块化与包管理》里展开过：ESM 是活绑定、Tree-shaking 友好、`exports` 能精确控制子路径与双格式入口。一个最小 `exports` 配置：

> 示意片段（无配套脚本）

```json
{
  "name": "@demo/ui",
  "type": "module",
  "exports": {
    ".": {
      "import": "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "types": "./dist/index.d.ts"
    },
    "./button": "./dist/button.mjs"
  }
}
```

`exports` 的命中顺序由书写顺序决定（前面匹配到就短路），所以"具体子路径"要写在通配之前。组件库源码用 ESM 写，引用语义上的坑——活绑定 vs 快照、循环依赖的 TDZ——可以用 `esm-probe` 实验台逐条实测确认，而不是凭记忆。这一步落定后，应用侧 `import { Button } from '@demo/ui'` 拿到的就是规范保证的 ESM 引用。

## 三、包管理：pnpm workspace 把多包捏进一个仓库

两个包放在一个仓库里，靠 workspace 协议共享，而不是各自 `npm publish` 再互相装：

> 示意片段（无配套脚本）

```yaml
# pnpm-workspace.yaml
packages:
  - 'packages/*'
```

> 示意片段（无配套脚本）

```json
// app/package.json
{
  "dependencies": {
    "@demo/ui": "workspace:*"
  }
}
```

`workspace:*` 让应用直接引用本地源码，改完组件库无需发布即可在应用里见效。pnpm 的硬链接 + 全局 store 同时解决了"幽灵依赖"（没声明却能用）和"依赖重复安装"两类痛点——这是《Monorepo 工程化》的核心收益。注意 `node_modules` 里 `@demo/ui` 是链接到 `packages/ui` 的符号链接，所以"应用看到的组件库"和"你正在改的组件库"是同一份。

## 四、构建：库构建与业务构建分流

同一种源码，两种产物目标，必须分开处理：

- **组件库（库构建）**：出 ESM + CJS + `.d.ts` 三件套，供外部消费。一个 `build` 脚本把 `src/` 编译到 `dist/`，类型用 `tsc --emitDeclarationOnly` 单独生成。
- **业务应用（应用构建）**：本地用 dev server 起、生产用 bundler 打。重点不在"出什么格式"，而在"打得小、打得对"。

> 示意片段（无配套脚本）

```json
// packages/ui/package.json
{
  "scripts": {
    "build": "tsc -p tsconfig.build.json && vite build",
    "types": "tsc -p tsconfig.build.json --emitDeclarationOnly"
  }
}
```

库构建的"出三件套"和"体积/拆包"手段在《构建体系》的 build-lab 有可运行实测（esbuild 0.13ms / SWC 0.13ms / Babel 20ms 的转换对比、按需引入 15× 体积差等），本章不重复，只把选型结论拿来用：库用 esbuild 出快、用 tsc 出类型；应用用 Vite 打开发体验。

## 五、脚手架：把"正确结构"变成一条命令

结构对了，团队才不会各写各的。把上面的 workspace + 双包结构沉淀成一个生成器，新包一条命令出来：

> 示意片段（无配套脚本）

```bash
# 生成一个新的组件包，自动带 exports / tsconfig / build script 骨架
demo-cli add-package button
# → packages/button/{package.json, src/index.ts, tsconfig.build.json}
```

真正的生成器怎么写（commander 做 CLI、模板引擎填充、版本管理）在《脚手架的诞生》里完整展开，本章只取它的产物：**结构即约束**。当"正确结构"由命令生成而非人手维护，模块化规范和构建脚本就不再是写在文档里、靠人遵守的东西，而是新包天生自带的东西。

## 六、CI：把四步串成门禁

前面五步里，"能跑起来"靠人本地跑，"不返工"靠脚手架，"规模化不崩"则只能靠 CI——每次提交自动 install → typecheck → test → build → publish，任何一步红就卡住合并。

> 示意片段（无配套脚本）

```yaml
# .github/workflows/release.yml
jobs:
  release:
    steps:
      - run: pnpm install --frozen-lockfile
      - run: pnpm -r typecheck      # 每个包 tsc --noEmit
      - run: pnpm -r test
      - run: pnpm -r build
      - run: pnpm -r publish        # 仅改了版本的包才发
```

`--frozen-lockfile` 保证 CI 装的依赖和本地锁文件一致（这是 Monorepo 规模化的命门）；`pnpm -r` 按依赖拓扑顺序跑各包脚本，避免"应用先 build、组件库还没 build"的竞态。

## 七、全景收口：四个切片映射到一条链

把《前端工程化全景》那张体系图，落回我们这个最小仓库上：

- **模块化** → `exports` 字段 + ESM 源码（决定"代码怎么被引用"）
- **包管理** → pnpm workspace（决定"多包怎么共存"）
- **构建** → 库出三件套 / 应用用 Vite（决定"源码怎么变产物"）
- **脚手架** → `add-package` 生成器（决定"正确结构怎么来"）
- **CI** → release 工作流（决定"四步怎么自动跑"）

五件事，前四件是"能力"，最后一件是"把这些能力焊死成默认"。缺少任何一件，工程化都会在某一刻漏水：没有模块化规范，引用就乱；没有 workspace，依赖就重；没有分流的构建，库和应用互相将就；没有脚手架，结构靠人守；没有 CI，前面四件都靠自觉。

## 八、方法论：工程化建设的优先级

如果团队要一步步补齐，顺序是固定的，因为后面一步依赖前面一步的结论：

1. **先能跑起来**：定模块规范 + 把源码打出来（模块化 + 构建）。这一步不解决，后面都是空中楼阁。
2. **再不返工**：用脚手架固化结构、用规范约束写法。这一步让"正确"成为默认，而非纪律。
3. **最后规模化**：上 Monorepo 把多包管好、上 CI 把质量门禁自动跑。这两件在团队/包数量变大时才真正划算，过早引入反而拖慢。

一句话收口：**工程化不是堆工具，而是把"已经想清楚的正确做法"固化成默认路径**——模块化定规范、构建产产物、脚手架生成结构、Monorepo 管多包、CI 守门禁，五者咬合，缺一环就漏。
