## 1. 前端工程化全景

### 1.1 工程化的本质与核心矛盾

工程化 = **用管理手段和工具能力，把「人的不确定性」转化为「流程的确定性」**。核心矛盾是规模越大、协作与稳定的成本越高。

传统痛点，逐条对应一个工程化答案：

| 传统痛点 | 各环节的答案 |
| ---- | ---- |
| 开发模块划分混乱、协作冲突 | 模块化、规范化 |
| 测试手动点页面 | 测试体系自动化 |
| 构建无缓存无 hash | 构建体系 |
| 部署覆盖式无法回滚 | 发布体系（产物不可变 + 版本映射一键回滚） |
| 监控靠用户截图反馈 | 监控体系 |

一句话：**靠体系兜底**，而不是「靠个人水平负责」。

### 1.2 五大阶段体系

五大阶段 = 一条完整的能力清单（是清单不是建设顺序）：

- **开发体系**：脚手架、代码规范（ESLint + Prettier + husky + commitlint）、Monorepo、本地开发体验（热更新 / Mock / 环境变量）。
- **测试体系**：单元测试（Vitest / Jest）、组件测试、E2E 测试（Playwright / Cypress）、覆盖率与门禁。
- **构建体系**：入口分析 → 依赖收集 → Tree Shaking → 分包 → 产出带 hash 的静态资源；多环境构建与产物策略。
- **发布体系**：CI/CD 自动化、蓝绿 / 金丝雀 / 灰度 / 滚动发布策略、产物不可变 + 版本映射一键回滚。
- **监控体系**：日志、性能指标（FP / FCP / LCP、JS Error、API 错误率）、与后端 trace 打通定位慢接口。

各阶段不是孤岛——**环环相扣**：规范影响测试通过率、测试门禁决定能否进构建发布、发布可控性决定线上稳定性与监控信号量。

> 最小实现：到 `../交付与质量/code` 运行 `pipeline-demo.html`，看 build→test→deploy 最小流水线如何把「人肉接力」变成「机器编排」。

### 1.3 依赖链与瓶颈定位

五大阶段不是并列的，而是一条**依赖链**：

```
规范/脚手架 → 质量门禁/CI-CD → 灰度/发布 → 监控/复盘 → 反哺规范
```

**链条最短的薄弱环节才是真正的瓶颈**——规范再严、没有监控兜底，稳定性依然悬空。找短环要靠可量化指标（构建耗时、发布失败率、回归缺陷率、上线至问题感知时长），让工程化迭代由度量驱动而非人拍脑袋。

### 1.4 基建工程师成长路径

演进路径是一条「对象不断变抽象」的阶梯：

```
写页面 → 写组件库 → 写团队脚手架 → 设计整套研发基础设施
```

- **角色差异**：服务对象从用户变为团队工程师，核心能力转向工程架构、自动化、抽象能力与复杂系统稳定性。
- **抽象能力是分水岭**：能否从 10 个项目的重复代码里提炼出通用基建；还需掌握封装抽象、工具链调度、稳定性、成本与长期维护等元知识。

### 1.5 成熟度模型 L1–L5

五级递进，顺序不可跳：

```
原始(靠人工) → 逐步(有部分工具) → 规范(有统一规范) → 自动(流水线化) → 平台(平台化、度量驱动迭代)
```

- **推进顺序**：遵循「先规范、再自动化、后平台化」——规范阶段的产出（统一 lint / 目录 / 发布流程）是自动化阶段的输入。没有规范就自动化，等于把混乱加速。
- **推进策略**：不要求全公司同步，从高频痛点、见效快的小项目切入、见效快再扩散。
- **度量为先**：用构建耗时、发布失败率、回归缺陷率、上线至问题感知时长等指标驱动迭代，避免工程化沦为形式。

## 2. 模块化与包管理

### 2.1 模块系统的作用

模块系统做**三件事**：

```
作用域隔离      每个模块一套作用域，不污染全局
依赖显式化      依赖关系可静态分析
加载时机可预测  拿到引用还是快照，规则明确
```

「把代码分文件」只解决可读性，**不构成模块系统**。

- **分水岭唯一**：CJS / AMD / CMD / UMD 都在**运行时**确定依赖，ESM 在**实例化阶段**确定——tree-shaking 与循环依赖行为均由此派生。
- **被淘汰者只记结论**：AMD 依赖前置、CMD 就近书写、UMD 是按环境自适应的兼容壳。

### 2.2 ESM / CJS 绑定语义

绑定语义是二者的根本差别：

| 形态 | 机制 | 表现 |
| ---- | ---- | ---- |
| ESM 导出绑定 | 导入方读到的始终是导出方变量的**当前值** | 导出方一改就可见（活引用） |
| CJS 导出值 | 基本类型在**导出那一刻拷贝** | 此后模块内变化传不出去；`exports` 对象本身按引用共享 |

- **实测对照**：ESM 侧 `count` 变 1，CJS 侧 `snapshot` 停在 0；CJS 只有通过闭包函数重读才拿得到新值（`exports.read = () => count`）。

### 2.3 循环依赖

- **ESM 不返回半成品**：实例化阶段一次性建好全部绑定，不存在 CJS 那种「先 undefined 后又有值」。
- **撞的是 TDZ**：未求值模块的 `const` / `let` 抛 `ReferenceError`，连 `Object.keys(命名空间)` 也一并抛。
- **函数声明是唯一例外**：`export function` 在实例化阶段就绪；换成 `export const fn = () => {}` 同样落入 TDZ。
- **正解是消除环**，函数声明只能绕不应依赖。

### 2.4 ESM 引 CJS 的互操作

- **`default` 是确定的**：就是 `module.exports` 本身。
- **具名导出靠静态扫描**：`cjs-module-lexer` 在求值前扫源码猜名字，逐个 `exports.x =` 或对象字面量可识别，动态拼装对象则只剩 `default`（运行时无任何补救）。
- **两条推论**：① 库作者把导出写成静态形式是兼容性义务；② `__esModule` 在原生 ESM 下不参与判定。
- **互操作在收敛**：Node 22 已支持无顶层 await 时用 `require()` 直接加载 ESM。

### 2.5 条件导出与导入

- **顺序即优先级**：按 `exports` 键的**书写顺序**逐个匹配，不是「最具体优先」——`browser` 写在 `import` 前会把两条路径都抢走。
- **`default` 必须最后**：写在前面会吃掉后面所有条件。
- **默认封闭**：声明 `exports` 后，未映射路径（含深链接）一律拒绝，把「哪些是公开 API」变成解析规则。
- **`imports` 是对内版本**：键以 `#` 开头、只能被本包引用，条件判定逻辑与 `exports` 一致。

### 2.6 双包危险

- **成因**：同一包被 `import` 与 `require` 解析到**两份入口**，各自持有独立的模块级状态。
- **实测**：`index.mjs` 引用 `state.mjs`、`index.cjs` 引用 `state.cjs`——两侧各自 `+1`，两份计数始终不相等。
- **危害**：单例对象（配置、连接池、缓存、事件总线）**静默分裂且不报错**，是最难查的一类。
- **规避（排序）**：① 两份入口共享同一份状态文件（最彻底）→ ② 只发一种格式 → ③ 把有状态部分拆成独立包。

### 2.7 依赖分类与语义化版本

**依赖三分类**：

| 分类 | 放什么 | 特性 |
| ---- | ---- | ---- |
| `dependencies` | 运行时必需 | 会进生产安装 |
| `devDependencies` | 仅开发 / 构建期用 | 只在本项目安装 |
| `peerDependencies` | 声明「宿主必须提供」 | 不重复安装、由宿主提供，避免同一库多实例 |

**版本即承诺**：`major` / `minor` / `patch` 对应破坏 / 新增 / 修复。

```
^1.2.3  覆盖 >=1.2.3 <2.0.0
~1.2.3  覆盖 >=1.2.3 <1.3.0
^0.2.3  只覆盖 <0.3.0 —— 0.x 次版本变化视为破坏性
```

用提交信息自动推导版本（fix→patch、feat→minor、BREAKING→major）让「版本号」与「变更内容」强制对齐。

### 2.8 包管理实践

- **依赖树形状**：npm/yarn 的扁平提升会造出**幽灵依赖**（能 `require` 未声明的包），依赖必须显式声明；workspace 与内容寻址存储见第 4 章。
- **应用锁死、库放开**：应用靠 lockfile 锁实际版本并走 `npm ci`；库则用 `^` 让出兼容范围。
- **排障方向**：「重装依赖后本地跑不起来 / 线上行为不一致」这类**无报错的不一致**，先怀疑依赖树形状，再怀疑双包危险；lockfile 不一致、registry 缓存、peer 依赖告警也都可能是诱因，从「能复现的最小环境」开始查。
- **快速确认双包**：打印两个入口文件路径（`import.meta.resolve` 与 `require.resolve`），若不相同基本可判定状态会分裂。

## 3. 脚手架的诞生

### 3.1 脚手架的本质与四件事

脚手架的核心职责 = **把「创建项目的知识」沉淀为可复用代码**，解决初始化、依赖版本漂移、规范不一致、升级困难。

四件事是一条流水线：

```
收集信息(交互式提问) → 选择模板 → 渲染生成 → 收尾(装依赖/初始化 git/输出指引)
```

本质是把团队约定固化成模板。注意它**只对新项目生效**，存量项目的规范漂移要靠 codemod / upgrade 补。

> 最小实现：`scaffold-cli.html` 用 JS 把 `my-create app -t vue --force` 解析成结构化选项、按参数决定模板，看清 CLI 的本质。

### 3.2 CLI 设计与健壮性

- **入口与参数解析**：`#!/usr/bin/env node` shebang 让系统用 Node 执行；`commander` / `yargs` 负责命令与参数解析（`program.command('create <projectName>').option('-t, --template')`）。
- **健壮性校验**：参数校验与错误处理，如目标目录已存在且未加 `--force` 时**报错退出**——这是脚手架最基本的健壮性要求。

### 3.3 模板引擎

- **占位符注入**：EJS / Handlebars 用占位符 + 条件 + 循环把配置注入模板文件；EJS 支持 JS 逻辑、Handlebars 偏纯文本。
- **构建坑**：插值语法可能与 Vue / 框架语法冲突（EJS 的 `<% %>` 撞 Vue 模板），应「**生成时渲染**」而非运行时渲染，否则把插值原样写进产物。

### 3.4 生成器三层架构

任何 create-app 类工具都能抽象成通用三层架构：

```
CLI 入口 → Generator 核心控制器(getTemplateDir/模板解析/文件渲染) → Template 仓库层
```

- **模板组织**：create-vite 按「框架 × 变体」组织模板（`FRAMEWORKS` 元信息数组），`getTemplateDir` 逐文件写入、`package.json` 单独改写以保留用户信息。

### 3.5 私有脚手架平台

- **平台构成**：npm 私服模板包 + 模板中心后台 + 版本化发布（`--template enterprise@1.2.0`），把团队约定与企业级能力沉淀进模板。
- **建设要点**：模板迭代与灰度、埋点统计、可升级性（upgrade / codemod）、文档与示例、权限与审计。
- **大忌**：模板越厚越难升级——业务逻辑进模板后，模板演进就变成「给所有存量项目做迁移」。

## 4. Monorepo 工程化

### 4.1 Monorepo vs Multi-repo

- **两种组织方式**：Multi-repo 每包一个 git 仓库、版本靠 semver 同步；Monorepo 单仓库多包，以「**统一版本 + 统一依赖 + 统一任务编排**」换一致性。
- **收益**：原子提交（一次 commit 完成跨包改动）、依赖统一、增量构建、基建复用（lint / test / CI 只在根目录写一次）。

### 4.2 pnpm 依赖管理

- **内容寻址存储（CAS）**：全局 `.pnpm-store` 按内容 hash 组织、一份内容多处链接，硬链接省磁盘、安装快。
- **非扁平结构防幽灵依赖**：pnpm 的 `node_modules` 只暴露**直接依赖**，与 npm/yarn 的扁平 hoist 不同，代码无法 `require` 未声明的包。

```
扁平 hoist(npm/yarn)  依赖提升到顶层 → 幽灵依赖
隔离结构(pnpm)       只暴露直接依赖   → require 未声明即报错
```

- **workspace 内部依赖**：`pnpm-workspace.yaml` 声明包范围，`workspace:*` 用工作区最新版本，软链 / 硬链即时生效、无需发布。
- 硬链接跨盘符 / 跨文件系统受限；少数工具链对扁平 `node_modules` 有隐式假设。

> 最小实现：`deps-demo.html` 可视化「内容寻址存储、硬链接/软链、扁平 hoist vs 隔离结构」，看懂幽灵依赖为何产生又为何被防住。

### 4.3 pnpm 配置与命令

- **三步起步**：`pnpm-workspace.yaml` 声明包范围 → 根 `package.json` 设 `private` + `packageManager` → 子包间用 `workspace:*` 链接。
- **`workspace:*` 协议**：用工作区该包最新版本，软链/硬链即时生效、无需发布（`workspace:^` 允许更高、`workspace:~` 同 minor）。
- **常用命令**：`pnpm --filter @scope/ui build` 定向、`pnpm -r run build` 按拓扑序递归、`pnpm install --frozen-lockfile` 锁定安装（CI 必用）。
- **配套代码**：`./code/pnpm-workspace-demo`（shared→sdk→ui 三包依赖链）可运行，演示 `workspace:*` / `--filter` / 拓扑序 / 幽灵依赖隔离。

### 4.4 版本发布与落地误区

- **发版用 changesets**：`changeset add` 声明变更类型（fix/feat/BREAKING），`changeset version` 统一联动受影响包版本并生成 CHANGELOG，`pnpm publish -r` 按依赖顺序发布——避免逐个改 `version` 的版本错位。
- **落地误区**：包太厚、循环依赖、权限全开放、跨包耦合无规约；应保持包粒度清晰、加 lint 规则与评审制度。

## 5. 基建实战总串联

### 5.1 总串联：不是并列开关而是链

模块化 / 脚手架 / Monorepo / 构建**不是四个并列开关，而是一条咬合的链**——后一步依赖前一步的结论，缺一环就漏。

### 5.2 各环落位

按顺序把各环落进一个真实 Monorepo 工作流：

1. **起点是模块规范**：组件库用 ESM + `package.json` 的 `exports`（命中顺序由书写顺序决定），应用侧 `import` 拿到规范保证的引用；ESM 活绑定 / 循环依赖 TDZ 用 `esm-probe` 实测而非记忆。
2. **包管理把多包捏进一仓**：pnpm `workspace:*` 让应用直接软链本地组件库，改完即见效；内容寻址 + 隔离 `node_modules` 同时解决幽灵依赖与重复安装。
3. **构建要分流**：库出 ESM + CJS + `.d.ts` 三件套（`tsc --emitDeclarationOnly` 出类型），应用用 Vite；转换 / 体积结论复用构建体系 build-lab。
4. **脚手架固化结构**：`add-package` 生成器让「正确结构」天生自带，规范不再靠人守。
5. **CI 焊死门禁**：install → typecheck → test → build → publish；`--frozen-lockfile` 保依赖一致、`pnpm -r` 按拓扑序跑各包脚本避免竞态。

### 5.3 建设优先级

```
先能跑(模块化+构建) → 再不返工(脚手架+规范) → 最后规模化(Monorepo+CI)
```

后面一步依赖前面一步的结论，缺一环就漏。
