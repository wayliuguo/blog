# 模块面试题 · 前端工程化

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../../进阶/面试方法论.md)的四步答题法——结论/原理/边界/追问。
> 题目来源：由本模块各篇正文的知识点整理，每题在标题后标注出处（第 N 篇 / 场景综合）。

## 一、基础概念

### Q1: 前端工程化到底解决什么问题？（第 1 篇）

- **结论**：用管理手段和工具能力把「人的不确定性」转化为「流程的确定性」，核心矛盾是规模越大、协作与稳定的成本越高。
- **原理**：模块化、组件化、构建、规范化、监控共同构成骨架；每个环节都有对应方案与工具，本质是「靠体系兜底」而不是「靠个人水平负责」。
- **边界**：工程化解决的是"人一多、页面一多"的协作问题，不是业务正确性；小项目上复杂配置与多余抽象反而拖慢节奏。
- **追问**：没有工程化会怎样？→ 依赖手动管理、全局命名冲突、无统一构建与回归，页面上量后只能全量发布、全量回归。

### Q2: 工程化的五大阶段与依赖链是什么？瓶颈怎么定位？（第 1 篇）

- **结论**：开发 → 测试 → 构建 → 发布 → 监控五个体系环环相扣，**链条上最短的那一环才是真正的瓶颈**。
- **原理**：规范影响测试通过率，测试门禁决定能否进构建发布，发布可控性决定线上稳定性与监控信号量；任何一环薄弱都会把上游投入吃掉——规范再严，没有监控兜底稳定性依然悬空。
- **边界**：五阶段是能力清单不是建设顺序清单；先补哪一环取决于当前痛点，不该按图索骥全都上。
- **追问**：怎么判断该补哪一环？→ 用可量化指标找最短环，例如构建耗时、发布失败率、回归缺陷率、上线至问题感知时长。

### Q3: 成熟度模型 L1–L5 的推进顺序为什么是"先规范、再自动化、后平台化"？（第 1 篇）

- **结论**：原始 → 逐步 → 规范 → 自动 → 平台，顺序不可跳；没有规范就自动化，等于把混乱加速。
- **原理**：规范阶段的产出（统一 lint、统一目录、统一发布流程）是自动化阶段的输入——自动化只是在执行规范；到了平台阶段才谈度量驱动迭代。
- **边界**：不要求全公司同步推进，从高频痛点、见效快的小项目切入扩散更现实。
- **追问**：平台化的标志是什么？→ 工程能力被平台承载、且迭代由度量数据驱动，而不是靠人推动。

### Q4: 模块系统解决的是哪三件事？（第 2 篇）

- **结论**：作用域隔离、依赖显式化、加载时机可预测；「把代码分文件」只解决可读性，不构成模块系统。
- **原理**：没有模块系统时多个 `<script>` 共享全局对象，变量互相覆盖；依赖靠书写顺序隐式约定，无法静态分析；"拿到的是引用还是快照"没有明确规则时，同一变量在不同文件里值不一样会变成玄学。
- **边界**：前两件是工程问题，第三件是语义问题；只做到"分文件"的项目在规模上来后仍会集中暴雷。
- **追问**：哪一件最容易被记错？→ 第三件。它错了不会立刻报错，而是以"偶发 bug"的形式出现。

### Q5: CJS 与 ESM 的分水岭是什么？（第 2 篇）

- **结论**：依赖是在**运行时**确定（CJS/AMD/CMD/UMD），还是在**实例化阶段**确定（ESM）。
- **原理**：`import` / `export` 是语法声明而非函数调用，所以引擎在求值之前就能读出完整依赖图并完成绑定；tree-shaking、循环依赖行为、具名导出的可行性全部由此派生。
- **边界**：AMD 与 CMD 的差异（依赖前置 vs 就近书写）只在维护老项目时有意义；UMD 不是规范而是按环境自适应的兼容壳，ESM 时代已无必要。
- **追问**：为什么只有 ESM 能做 tree-shaking？→ 静态声明让"哪些导出被用到"在构建期可判定，而 `require` 是运行时调用。

### Q6: 语义化版本规则与 `^` / `~` 的边界？（第 2 篇）


- **结论**：major 破坏性、minor 新增、patch 修复；`^1.2.3` 覆盖 `>=1.2.3 <2.0.0`，`~1.2.3` 只覆盖 `>=1.2.3 <1.3.0`。
- **原理**：版本号是**对使用方的承诺**，`^` 的自动化红利建立在"遵守承诺"之上；契约被破坏时 `^` 就从红利变成随机故障源。
- **边界**：`^0.2.3` 只覆盖 `<0.3.0`——主版本为 0 时次版本变化视为破坏性，"明明写的 `^0.2.0` 却升级坏了"就是踩这条。
- **追问**：怎么保证版本与变更内容对齐？→ 用提交信息自动推导版本（fix→patch、feat→minor、BREAKING CHANGE→major），而不是靠发版人的记忆。

### Q7: 脚手架的职责与四件事？（第 3 篇）

- **结论**：把「创建项目的知识」沉淀为可复用代码，解决初始化、依赖版本漂移、规范不一致、升级困难。
- **原理**：四件事——收集信息（交互式提问）→ 选择模板 → 渲染生成 → 收尾（装依赖/初始化 git/输出指引）；本质是把团队约定固化成模板。
- **边界**：脚手架只对新项目生效；存量项目的规范漂移要靠 codemod / upgrade 能力补，不是脚手架能解决的。
- **追问**：为什么不用"复制一个标准项目"替代脚手架？→ 复制会立刻产生版本漂移与规范分叉，且无法携带升级能力。

### Q8: Monorepo 与 Multi-repo 怎么选？（第 4 篇）

- **结论**：核心是"共享多还是隔离多"——共享多选 Monorepo，边界清晰、版本独立演进、故障隔离要求高时选 Multi-repo。
- **原理**：Monorepo 用「统一版本 + 统一依赖 + 统一任务编排」换一致性：原子提交、依赖统一、增量构建、lint/test/CI 只在根目录写一次。
- **边界**：仓库变大后 git 与 CI 变慢、权限粒度变粗、需要工具链（pnpm workspace / turborepo / lerna）编排；小团队强行 Monorepo 反成负担。
- **追问**：什么时候该拆回多仓库？→ 团队边界清晰、各产品版本独立演进、故障隔离要求高时。

## 二、机制与原理

### Q9: ESM 的导入是引用还是快照？CJS 呢？（第 2 篇）

- **结论**：**ESM 导出绑定（活引用），CJS 导出值（快照）**；实测 ESM 侧计数变 1，CJS 侧快照停在 0。
- **原理**：`export let count` 建立的是绑定，导出方 `count += 1` 后导入方立刻读到新值；`exports.snapshot = count` 在导出那一刻把基本类型拷走，此后模块内再变也传不出去。
- **边界**：CJS 的 `exports` 对象本身按引用共享，"改对象属性"两边能看见；传不出去的只是"导出时还是基本类型的值"。
- **追问**：CJS 模块怎么让外部看到内部最新值？→ 通过函数（闭包）重读原变量，如 `exports.read = () => count`。

### Q10: ESM 循环依赖为什么不是 `undefined`，而是 `ReferenceError`？（第 2 篇）

- **结论**：绑定关系在实例化阶段就全部建好，只是未求值模块的 `const` / `let` 仍在 TDZ，读它抛 `ReferenceError`。
- **原理**：ESM 分两阶段——先实例化（建绑定、分配内存），再求值（执行模块体）。循环时 `a → b → a` 里的 b 会先求值，此时 a 的模块体还没跑。
- **边界**：连 `Object.keys(命名空间)` 都会抛——命名空间对象的 `[[GetOwnProperty]]` 要读每个导出的值，碰到 TDZ 绑定一起抛；**唯一例外是函数声明**，`export function` 在实例化阶段就绪。
- **追问**：那是不是可以靠函数声明绕过循环依赖？→ 可以但不该依赖，正解是消除环；换成 `export const fn = () => {}` 就同样落入 TDZ。

### Q11: ESM 引 CJS 时，具名导出是怎么来的？（第 2 篇）

- **结论**：`default` 是确定的（就是 `module.exports`），具名导出是 Node 在求值前用 `cjs-module-lexer` **静态扫描**猜出来的。
- **原理**：CJS 的 `module.exports` 在求值前不存在，而 ESM 要求具名导入在实例化阶段就确定，所以只能靠源码静态分析。逐个 `exports.x =` 或对象字面量能被识别；`const bag = {}; bag.name = ...; module.exports = bag` 这类拼装则扫不出来。
- **边界**：扫不出名字时，命名空间里只剩 `default`，运行时没有任何补救；`__esModule: true` 在原生 Node ESM 下不参与判定。
- **追问**：这对库作者意味着什么？→ 把导出写成静态形式是一项兼容性义务，否则 ESM 使用方只能用 `default.xxx`。另外 Node 22 已支持无顶层 await 时用 `require()` 直接加载 ESM，互操作在收敛。

### Q12: 条件导出的命中顺序由什么决定？`default` 为什么必须最后？（第 2 篇）

- **结论**：由 **`exports` 对象里键的书写顺序**决定，取第一个命中的条件；顺序即优先级，不是"最具体优先"。
- **原理**：实测把 `browser` 写在 `import` 之前，激活 `browser` 条件后连 `require` 都被抢到 `.mjs`（`require.resolve` 也命中 `index.browser.mjs`）。
- **边界**：`default` 是兜底，写在前面会把后面所有条件全部吃掉；另外**一旦声明 `exports`，未映射路径（含深链接）一律拒绝**，要开放 `package.json` 必须显式补一条映射。
- **追问**：`imports` 与 `exports` 什么关系？→ `imports` 是对内版本，键必须以 `#` 开头、只能被本包引用，条件判定逻辑与 `exports` 一致。

### Q13: 什么是双包危险（dual package hazard）？怎么规避？（第 2 篇）

- **结论**：同一个包被 `import` 与 `require` 解析到两份入口文件，产生**两份模块级状态**；实测两侧各自 `+1`，两份计数始终不相等。
- **原理**：`index.mjs` 引用 `state.mjs`、`index.cjs` 引用 `state.cjs`，两套状态互不相干；同一个进程里既 import 又 require，等于存在两个包实例。
- **边界**：无状态包（纯函数库）受影响很小；有单例的包（全局配置、连接池、缓存、事件总线）会静默分裂且不报错，是最难查的一类。
- **追问**：三种规避方式怎么排序？→ ① 两份入口共享同一份状态文件（最彻底）；② 只发一种格式，CJS 使用方走 `require(esm)` 或动态 `import()`；③ 把有状态部分拆成独立包、只发一种格式。

### Q14: pnpm 的硬链接/软链与依赖隔离原理？（第 4 篇）

- **结论**：全局内容寻址存储 + 硬链接 + `.pnpm` 虚拟 store 的软链，实现"磁盘最省 + 依赖严格隔离"。
- **原理**：所有包版本按内容 hash 存全局 store，项目 `node_modules/.pnpm/<name>@<version>/` 用硬链接指向 store；包的真实依赖装在包自己的 `node_modules` 里（软链），因此不扁平提升。
- **边界**：硬链接跨盘符/跨文件系统受限；少数工具链对扁平 `node_modules` 有隐式假设，会踩坑。
- **追问**：为什么能防幽灵依赖？→ 依赖不提升到顶层，`require` 解析不到未声明的包，未声明即报错。

### Q15: turborepo 的任务编排与增量缓存怎么工作？（第 4 篇）

- **结论**：`turbo.json` 的 pipeline 声明任务依赖（如 build 依赖 `^build`），并行跑无依赖任务、有依赖的按拓扑序执行；缓存按输入文件 hash 判定。
- **原理**：命中缓存即复用产物，不重复执行；远程缓存让整个团队共享同一份缓存，CI 提速最明显。
- **边界**：缓存命中率取决于输入声明是否完整——漏声明环境变量或外部文件会导致"该重建却没重建"，比不缓存更危险。
- **追问**：只改了 A 包，怎么只跑受影响的构建？→ 用 `--filter` 定向，配合 `--parallel` 并行启动多个 dev。

### Q16: 脚手架的生成器三层架构是什么？（第 3 篇）

- **结论**：任何 create-app 类工具都能抽象为「CLI 入口 → Generator 核心控制器 → Template 仓库层」。
- **原理**：CLI 层负责 shebang 与参数解析（commander/yargs），核心控制器负责取模板目录、解析模板、渲染文件，模板层按「框架 × 变体」组织（如 create-vite 的 FRAMEWORKS 元信息数组）。
- **边界**：模板插值语法可能与框架语法冲突（EJS 的 `<% %>` 撞 Vue 模板），必须"生成时渲染"而不是把插值原样写进产物；`package.json` 往往需要单独改写以保留用户信息。
- **追问**：目标目录已存在怎么处理？→ 校验并报错退出，除非显式传 `--force`；这是脚手架最基本的健壮性要求。

### Q17: lerna 的版本联动与自动推导？（第 4 篇）

- **结论**：`lerna version/publish` 联动多包发版，按依赖顺序发布已变更的包。
- **原理**：`--conventional-commits` 基于提交信息自动推导版本——fix→patch、feat→minor、BREAKING→major，让版本号与变更内容强制对齐。
- **边界**：新版 lerna（≥7）不再自带任务编排，把编排交给 turborepo；版本推导的准确性依赖提交信息规范，规范不落地则推导就是摆设。
- **追问**：为什么不手动改版本号？→ 手动改依赖记忆，跨包依赖链上极易漏改或改错顺序。

## 三、排障与选型

### Q18: 依赖该放 `dependencies` / `devDependencies` / `peerDependencies`？（第 2 篇）

- **结论**：运行时必需放 `dependencies`，仅开发/构建期用放 `devDependencies`，声明"宿主必须提供"放 `peerDependencies`。
- **原理**：`dependencies` 会进生产安装；`devDependencies` 只在本项目安装；`peerDependencies` 不重复安装、由宿主提供，避免同一库出现多实例（如插件要求宿主已有 React）。
- **边界**：dev 依赖混进 `dependencies` 会让生产包变大；`peerDependencies` 版本不满足时 npm 通常只告警不报错，容易埋雷；`optionalDependencies` 安装失败不阻塞整体安装，常用于平台相关的二进制包。
- **追问**：应用该锁死还是放开范围？→ 应用靠 lockfile 锁实际版本并走 `npm ci`，库则用 `^` 让出兼容范围。

### Q19: "重装依赖后本地跑不起来 / 线上行为不一致"怎么排？（第 2 篇）

- **结论**：先怀疑依赖树形状，再怀疑双包危险——这两类是"无报错的不一致"的主要来源。
- **原理**：扁平提升让代码可以 `require` 未声明的包（幽灵依赖），换用 pnpm 或升级依赖后立刻炸；条件导出让同一包出现两份入口，产生两份模块级状态。
- **边界**：lockfile 不一致、registry 缓存、peer 依赖告警都可能是诱因，排查顺序应从"我能复现的最小环境"开始。
- **追问**：怎么快速确认是双包危险？→ 打印两个入口文件路径（`import.meta.resolve` 与 `require.resolve`），若不相同基本可判定状态会分裂。

### Q20: 私有脚手架平台该沉淀什么、避免什么？（第 3 篇）

- **结论**：沉淀团队约定与企业级能力（规范、目录、CI 模板、埋点），避免把业务代码塞进模板。
- **原理**：平台由 npm 私服模板包 + 模板中心后台 + 版本化发布（`--template enterprise@1.2.0`）构成；建设重点在模板迭代与灰度、埋点统计、可升级性（upgrade/codemod）、文档示例、权限审计。
- **边界**：模板越厚越难升级——业务逻辑进模板后，模板演进就变成"给所有存量项目做迁移"，成本会被无限放大。
- **追问**：模板升级怎么做才安全？→ 提供 upgrade/codemod 通道 + 灰度，而不是让项目重跑脚手架。

### Q21: 什么时候该拆多仓库？（第 4 篇）

- **结论**：团队边界清晰、版本各自演进、故障隔离要求高时拆；否则留在 Monorepo 里更省事。
- **原理**：Monorepo 的收益是原子提交与基建复用，代价是仓库变大后的 git/CI 成本与权限粒度变粗；收益小于代价时就该拆。
- **边界**：不该用"仓库数量"当作架构水平的指标；也不该把毫无共享的多个产品硬塞进一个仓库。
- **追问**：Monorepo 里包划分的常见误区？→ 包太厚、循环依赖、权限全开放、跨包耦合无规约；应保持包粒度清晰，加 lint 规则与评审制度。

## 四、场景设计题

### Q22: 场景：团队要统一"新项目初始化"，怎么设计脚手架？（第 3 篇）

- **结论**：把"新增项目/新增页面"的模板步骤固化成配置 + 模板，让新增 = 加一条配置，而不是复制粘贴。
- **原理**：CLI 收集信息 → 生成器按「框架 × 变体」选模板 → 渲染 → 收尾（装依赖、初始化 git、输出指引）；模板与版本强绑定，保证新项目从第一天起就符合规范。
- **边界**：页面形态同构才可能"零模板代码"，差异过大的场景仍需自定义；配置是收敛口，字段缺失必须有默认值兜底。
- **追问**：怎么保证模板演进不反向伤害存量项目？→ 模板只对新建生效，存量走 upgrade/codemod 通道，并做灰度。

### Q23: 场景：单仓多包之后 CI 越来越慢，怎么优化？（第 4 篇）

- **结论**：先做**定向**（只跑受影响的包），再做**缓存**（命中即复用），最后才考虑加机器。
- **原理**：turborepo 按输入文件 hash 判断任务是否过期，命中直接复用产物；远程缓存让整个团队共享；`--filter` 把构建范围收敛到受影响包。
- **边界**：缓存声明不完整会"该重建没重建"，比慢更危险；因此输入声明要覆盖环境变量与外部文件。
- **追问**：怎么衡量优化有效？→ 看 CI 的平均耗时与缓存命中率，而不是看单次构建快了多少。

### Q24: 场景：要发布一个同时支持 `import` 与 `require` 的库，怎么设计？（第 2 篇）

- **结论**：**先定状态归属，再定条件映射**——有状态的部分只发一种格式，无状态的按条件导出。
- **原理**：`exports` 里按 `import` / `require` 分别指向 `.mjs` / `.cjs`，`default` 放最后兜底；条件顺序决定优先级，`browser` 等平台条件要按需要排在前面。
- **边界**：两份入口若各自持有状态，就会触发双包危险（单例分裂且不报错）；`exports` 声明后未映射路径一律拒绝，历史深链接的兼容要显式补映射。
- **追问**：怎么验证发出去没问题？→ 在同一进程里分别 `import` 与 `require`，打印两个入口路径与各自读到的状态，确认要么同一份、要么明确无关。
