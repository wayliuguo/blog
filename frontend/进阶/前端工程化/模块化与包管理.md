# 模块化与包管理

## 模块系统解决的是三件事，不是"把代码分文件"

把代码拆成多个文件只解决可读性。真正需要模块系统兜住的是另外三件事：

1. **作用域隔离**。没有模块系统时，多个 `<script>` 共享同一个全局对象，任何变量都可能被同名变量覆盖，也随时可能污染 `window`。模块给每个文件一个独立作用域。
2. **依赖显式化**。谁依赖谁写在文件头部，而不是靠 HTML 里 `<script>` 的书写顺序隐式约定——后者一改顺序就炸，而且无法静态分析。
3. **加载时机可预测**。依赖在什么时候确定、拿到的是引用还是快照，必须有一套明确规则，否则"为什么这个变量在不同文件里值不一样"会变成玄学。

前两件是工程问题，第三件是语义问题。后文篇幅主要花在第三件上——因为它最容易被记错，而错了就会以"偶发 bug"的形式出现。

## 五种规范的分水岭只有一条：依赖什么时候确定

历史上出现过 CommonJS、AMD、CMD、UMD、ESM 五套写法，但真正的分水岭只有一条：**依赖是在运行时确定，还是在实例化阶段确定。**

| 规范 | 依赖确定时机 | 加载方式 | 现状 |
| --- | --- | --- | --- |
| CommonJS | 运行时（`require` 是函数调用） | 同步 | Node 服务端默认 |
| AMD | 运行时（在回调内） | 异步 | 已被淘汰 |
| CMD | 运行时（在回调内） | 同步/异步兼有 | 已被淘汰 |
| UMD | 运行时（按环境分支） | 视环境 | 只用于兼容老环境 |
| ESM | 实例化阶段（`import` 是声明） | 异步 | 浏览器与 Node 的共同方向 |

AMD 与 CMD 的差异（依赖前置 vs 就近书写）当年是热点，今天只在维护老项目时才有意义：**AMD 要求依赖列在工厂函数之前，CMD 提倡用到才 `require`，因此 CMD 的书写更接近 CommonJS。** 记住这一条即可，不必复现历史争论。

UMD 不是独立规范，而是一个**兼容壳**：它按环境自适应，先判断 Node 的 `exports`、再判断 AMD 的 `define`，最后兜底挂到全局。它存在的理由只有一个——把同一份产物同时投喂给三种加载器，这在 ESM 时代已无必要。

真正的分水岭落在 CJS 与 ESM 之间。ESM 的 `import` / `export` 是**语法声明**而非函数调用，所以引擎在**求值之前**就能把依赖图完整读出来并完成绑定。这一步叫实例化，它派生出后面所有差异——tree-shaking、循环依赖行为、具名导出的可行性，全部来源于此。

## 导入拿到的是引用还是快照

这是最容易记错的一点，跑一遍就清楚：

> 摘自 `./code/esm-probe/probe/counter.mjs`（运行：`npm run probe`，在 `code/esm-probe` 下）

```js
// ESM 的导出是「活绑定」：导入方每次读到的都是导出方当前的变量值
export let count = 0

export const bump = () => {
    count += 1
}
```

> 摘自 `./code/esm-probe/probe/counter.cjs`（运行：`npm run probe`，在 `code/esm-probe` 下）

```js
// CJS 导出的是「值」：导出那一刻拷一份，之后导出方再变也传不出去
let count = 0

exports.bump = () => {
    count += 1
}
exports.snapshot = count // 导出这一刻的值
exports.read = () => count // 每次调用重新读原变量
```

两个模块做同一件事：内部有个 `count`，提供 `bump()` 让它加一，区别只在导出方式。让两边各 `bump()` 一次再读：

> 摘自 `./code/esm-probe/probe/live-binding.mjs`（运行：`npm run probe`，在 `code/esm-probe` 下）

```js
console.log('初始         esm count =', count, '| cjs snapshot =', cjs.snapshot)

bump()
cjs.bump()

console.log('各自 +1 之后 esm count =', count, '| cjs snapshot =', cjs.snapshot)
console.log('cjs 用函数重读 =', cjs.read(), '（快照停在 0，只有重新读变量才看得到 1）')
```

```
初始         esm count = 0 | cjs snapshot = 0
各自 +1 之后 esm count = 1 | cjs snapshot = 0
cjs 用函数重读 = 1 （快照停在 0，只有重新读变量才看得到 1）
```

结论有两条，缺一不可：

- **ESM 导出的是绑定，不是值。** `import { count }` 拿到的是指向 `counter.mjs` 内变量的活绑定，`bump()` 一执行，导入方的 `count` 立刻变成 1。
- **CJS 导出的是值的拷贝。** `exports.snapshot = count` 把 0 拷进 `snapshot`，此后模块内部的 `count` 怎么变都传不出来；只有通过函数（闭包）重新读原变量才拿得到新值。

有一个常见误解要澄清：CJS 的 `exports` 对象本身按引用传递，`exports.bump` 这个函数属性两边共享，所以"改对象属性"能互相看见；传不出去的是**导出那一刻还是基本类型的值**。严格说，CJS 是"导出值、对象按引用共享"，ESM 是"导出绑定"。

## 循环依赖：ESM 不会给你 undefined，但会撞 TDZ

CJS 循环依赖的经典症状是"拿到 `undefined`，过一会儿又有了"——因为 `require` 在模块体执行到一半时就返回了半成品 `module.exports`。

ESM 的行为完全不同。它分两个阶段：先实例化（建立绑定、分配内存），再求值（执行模块体）。循环依赖时绑定关系**已经全部建好**，只是某个模块的模块体还没跑，它的 `const` / `let` 还停在 TDZ（暂时性死区）。

构造一个 `a → b → a` 的环：

> 摘自 `./code/esm-probe/probe/circular-a.mjs`（运行：`npm run probe`，在 `code/esm-probe` 下）

```js
import * as b from './circular-b.mjs'

export const valueFromA = 'A'

// 函数声明在实例化阶段就被初始化，所以循环依赖下它也是可用的
export function fnA() {
    return 'fnA'
}

console.log('[a] 依赖先求值完，这里能读到 b.valueFromB =', b.valueFromB)
```

> 摘自 `./code/esm-probe/probe/circular-b.mjs`（运行：`npm run probe`，在 `code/esm-probe` 下）

```js
import * as a from './circular-a.mjs'

// a 的模块体还没执行，它的 const 还在 TDZ，连读键都会抛
try {
    console.log('[b] 读 a.valueFromA =', a.valueFromA)
} catch (err) {
    console.log('[b] 读 a.valueFromA ->', `${err.name}: ${err.message}`)
}
try {
    console.log('[b] Object.keys(a) =', Object.keys(a))
} catch (err) {
    console.log('[b] Object.keys(a) ->', `${err.name}: ${err.message}`)
}
console.log('[b] typeof a.fnA =', typeof a.fnA, '（函数声明在实例化阶段就已就绪）')

export const valueFromB = 'B'
```

```
[b] 读 a.valueFromA -> ReferenceError: Cannot access 'valueFromA' before initialization
[b] Object.keys(a) -> ReferenceError: Cannot access 'valueFromA' before initialization
[b] typeof a.fnA = function （函数声明在实例化阶段就已就绪）
[a] 依赖先求值完，这里能读到 b.valueFromB = B
[entry] 两个模块求值完毕后： A B fnA
```

三个可以拿去面试的细节：

1. **不是 `undefined`，是 `ReferenceError`。** 绑定存在但处于未初始化状态，读它就抛错。这比 CJS 更好排查——报错位置直接指向问题，而不是让你在几百行之后发现某个值是 `undefined`。
2. **连 `Object.keys(a)` 都会抛。** 命名空间对象的 `[[GetOwnProperty]]` 需要读取每个导出的值，碰到 TDZ 绑定就一起抛。所以"先打印一下看里面有什么"这个调试手段在循环依赖里也不管用。
3. **函数声明是例外。** `export function fnA()` 在实例化阶段就完成初始化，所以在环里也能安全调用；换成 `export const fnA = () => {}` 就同样落入 TDZ。这是唯一可靠的"循环依赖逃生舱"，但正确做法是**消除环**，而不是依赖它。

## ESM 引 CJS：具名导出是"猜"出来的

一个 ESM 文件 `import` 一个 CJS 包时，`default` 的含义是确定的：**就是 `module.exports` 本身**。但具名导入是怎么来的？CJS 的 `module.exports` 在求值前根本不存在，ESM 却要求具名导入在实例化阶段就能确定。

Node 的解法是：在求值前用 `cjs-module-lexer` **静态扫描**一遍源码，猜出它导出了哪些名字。

> 摘自 `./code/esm-probe/probe/interop.mjs`（运行：`npm run probe`，在 `code/esm-probe` 下）

```js
console.log('default       =', legacy)
console.log('具名 name     =', name, '| version =', version)
console.log('命名空间 keys  =', Object.keys(ns))

// 扫不出名字时，具名导入不存在，只能走 default
const opaque = await import('./legacy-opaque.cjs')
console.log('opaque keys   =', Object.keys(opaque))
console.log('opaque.default =', opaque.default)
```

```
default       = { name: 'legacy', version: '1.0.0', describe: [Function (anonymous)] }
具名 name     = legacy | version = 1.0.0
命名空间 keys  = [ 'default', 'describe', 'name', 'version' ]
opaque keys   = [ 'default' ]
opaque.default = { name: 'opaque', version: '0.0.1' }
```

对照的两个 CJS 文件差别只在导出写法：一个逐个挂在 `exports` 上（`exports.name = ...`），另一个是先拼一个对象再 `module.exports = bag`（见 `probe/legacy-opaque.cjs`）。结果：

- 静态可分析的写法，具名导入全部可用，命名空间里能列出 `name` / `version` / `describe`；
- 拼出来的对象，命名空间里**只剩 `default`**——扫不出名字就是扫不出，运行时没有任何补救。

这条规则有两个现实推论：

1. **写 CJS 库时，`module.exports = { ... }` 对象字面量或逐个 `exports.xxx =` 都是安全的，但动态拼装对象会让 ESM 使用方只能用 `default.xxx`。** 如果你的库要被 ESM 项目引入，把导出写成静态形式是一项兼容性义务。
2. **不要依赖"检测到具名再回退到 default"的兜底行为。** 有一种广泛流传的写法是给 `module.exports` 加 `__esModule: true` 来配合转译器的互操作约定，但在原生 Node ESM 下它不参与判定——原生 ESM 只认 `cjs-module-lexer` 的静态结果。

这次运行还暴露了一个新事实：`--conditions=browser` 那一轮里 `require('twin')` 成功加载了一个 `.mjs` 文件。**Node 22 已支持在无顶层 await 时用 `require()` 直接加载 ESM**，这也是 ESM 与 CJS 互操作正在收敛的信号。

## 条件导出：命中顺序由书写顺序决定

同一个包要同时给 `import` 和 `require` 提供入口，靠的是 `package.json` 的 `exports` 字段——一张**条件到文件**的映射表。

> 摘自 `./code/esm-probe/pkgs/twin/package.json`（运行：`npm run probe`，在 `code/esm-probe` 下）

```json
"exports": {
  ".": {
    "browser": "./index.browser.mjs",
    "import": "./index.mjs",
    "require": "./index.cjs",
    "default": "./index.mjs"
  },
  "./package.json": "./package.json"
}
```

解析时引擎按**对象里键的书写顺序**逐条匹配，取第一个命中的条件。三条规则必须同时记住：

- **顺序敏感，不是"最具体优先"。** 把 `browser` 写在 `import` 前面，那么在同时激活 `browser` 与 `import` 条件的环境（打包器，或 `node --conditions=browser`）里，命中的就是浏览器版本。反过来写，`browser` 永远轮不到。
- **`default` 必须放最后**，它是兜底，写在前面会把后面全部吃掉。
- **一旦声明了 `exports`，包内其它文件默认不再对外开放。** 没被映射的路径连 `pkg/internal/xxx.js` 这种深链接都会被拒绝——这正是它的价值：把"哪些是公开 API"从口头约定变成解析规则。要显式开放 `package.json`，就得像上面那样补一条映射。

> 摘自 `./code/esm-probe/probe/conditions.mjs`（运行：`npm run probe`，在 `code/esm-probe` 下）

```js
const short = (p) => p.replace(/\\/g, '/').replace(/^.*node_modules\//, 'node_modules/')

console.log('import  命中文件 =', short(import.meta.resolve('twin')))
console.log('import  看到     =', viaImport)
console.log('require 命中文件 =', short(require.resolve('twin')))
console.log('require 看到     =', viaRequire.source)
console.log('imports(#internal-esm) =', internalEsm, '| require(#internal-cjs) =', internalCjs.tag)
```

```
import  命中文件 = node_modules/twin/index.mjs
import  看到     = index.mjs（import 条件命中）
require 命中文件 = node_modules/twin/index.cjs
require 看到     = index.cjs（require 条件命中）
imports(#internal-esm) = internal-esm | require(#internal-cjs) = internal-cjs
```

同一份代码换一组激活条件再跑一次（`node --conditions=browser probe/conditions.mjs`）：

```
import  命中文件 = node_modules/twin/index.browser.mjs
import  看到     = index.browser.mjs（browser 条件命中）
require 命中文件 = node_modules/twin/index.browser.mjs
require 看到     = index.browser.mjs（browser 条件命中）
```

因为 `browser` 被写在 `import` 之前，激活 `browser` 后它把两条路径**都**抢走了——`require` 也拿到了 `.mjs`。这就是"顺序即优先级"的直接证据。

解析顺序可以画成一条流水线：

```
import 'twin'
   │
   ├─ 找到 node_modules/twin/package.json
   │
   └─ 读 exports["."] 的键，按书写顺序逐个比对当前激活的条件集合
        browser  ──命中──▶ ./index.browser.mjs
        import   ──命中──▶ ./index.mjs
        require  ──命中──▶ ./index.cjs
        default  ──兜底──▶ ./index.mjs
```

与 `exports`（对外）对应的是 `imports`（对内）：键必须以 `#` 开头，只能被本包自己的文件引用。它解决的是"包内部相对路径过长、且改动会波及所有引用点"的问题——上面输出里的 `#internal-esm` / `#internal-cjs` 走的就是这套机制，条件判定逻辑与 `exports` 完全一致。

## 双包危险：同一个包的两份状态

条件导出解决了兼容性，同时引入一个新问题：**同一个包可能被解析到两份不同的入口文件，于是产生两份模块级状态。**

> 摘自 `./code/esm-probe/pkgs/twin/index.cjs`（运行：`npm run probe`，在 `code/esm-probe` 下）

```js
const { box } = require('./state.cjs')

exports.source = 'index.cjs（require 条件命中）'
exports.read = () => box.count
exports.bump = () => (box.count += 1)
```

ESM 入口 `index.mjs` 引用 `state.mjs`，CJS 入口 `index.cjs` 引用 `state.cjs`——两套状态互不相干。在同一个进程里既 `import` 又 `require` 这个包：

> 摘自 `./code/esm-probe/probe/dual-hazard.mjs`（运行：`npm run probe`，在 `code/esm-probe` 下）

```js
console.log('import  侧入口 =', esmSource)
console.log('require 侧入口 =', cjs.source)

esmBump()
console.log('ESM 侧 +1 后  -> esm.count =', esmRead(), '| cjs.count =', cjs.read())

cjs.bump()
console.log('CJS 侧 再 +1  -> esm.count =', esmRead(), '| cjs.count =', cjs.read())
```

```
import  侧入口 = index.mjs（import 条件命中）
require 侧入口 = index.cjs（require 条件命中）
ESM 侧 +1 后  -> esm.count = 1 | cjs.count = 0
CJS 侧 再 +1  -> esm.count = 1 | cjs.count = 1
```

两边各自加一，两份 `count` 始终不相等。如果这个 `box` 装的是**单例**（全局配置、连接池、缓存、事件总线），灾难就成立了：一处改了配置，另一处读到的还是旧值，而且不报错。

三种可行的规避方式，按推荐度排序：

1. **让两份入口共享同一份状态文件。** 最彻底。CJS 侧用 `.cjs` 状态文件、ESM 侧用 `.mjs` 就会分裂；把状态收敛到一种格式（例如状态写成 CJS，ESM 侧通过 `default` 互操作读取）就不会分裂。
2. **只保留一种格式的入口。** 纯 ESM 发布（`"type": "module"` + 只给 `import` 条件），CJS 使用方通过 `require(esm)`（Node 22+）或动态 `import()` 接入。这是新库的主流选择。
3. **把有状态的部分与无状态的部分拆成两个包**，有状态的那个只发一种格式。

## 包管理：版本号是一份契约

`package.json` 里有两个字段决定"这个包怎么被接进来"：一个是前面讲的 `exports`，另一个是版本范围。

| 写法 | 允许的范围 | 语义 |
| --- | --- | --- |
| `1.2.3` | 只有 `1.2.3` | 精确锁定，用于需要可重现的环境 |
| `~1.2.3` | `>=1.2.3 <1.3.0` | 只接受补丁更新 |
| `^1.2.3` | `>=1.2.3 <2.0.0` | 接受兼容更新（默认写法） |
| `^0.2.3` | `>=0.2.3 <0.3.0` | 主版本为 0 时**次版本变化视为破坏性**，范围被收紧 |

最后一行最常被忽略：`^` 在 `0.x` 下不遵循"次版本平滑"的假设。这也是"依赖自己写的库时，明明写的是 `^0.2.0` 却升级坏了"的原因。

版本号的意义是**对使用方的承诺**：`major` 变动代表破坏性变更、`minor` 代表新增能力、`patch` 代表修复。契约一旦被破坏，`^` 范围就从"自动化红利"变成"随机故障源"。对应的工程手段是把版本推导自动化——用提交信息决定版本号（`fix` → patch、`feat` → minor、`BREAKING CHANGE` → major），让版本号与变更内容强制对齐，而不是靠发版人的记忆。

依赖树的形状是另一半问题：npm / yarn 的扁平提升会把间接依赖提到顶层 `node_modules`，于是代码可以 `require` 一个自己没声明过的包（幽灵依赖），在依赖升级或换用 pnpm 时立刻炸掉。**这部分连同 workspace、内容寻址存储，见第 4 篇《Monorepo 工程化》。** 本篇只给结论：依赖必须显式声明，不要依赖提升带来的便利。

## 小结

- **模块系统的作用**
  - **三件事**：作用域隔离、依赖显式化、加载时机可预测；"把代码分文件"只解决可读性，不构成模块系统
  - **分水岭唯一**：CJS/AMD/CMD/UMD 都在运行时确定依赖，ESM 在实例化阶段确定，tree-shaking 与循环依赖行为均由此派生
  - **被淘汰者只记结论**：AMD 依赖前置、CMD 就近书写、UMD 是按环境自适应的兼容壳
- **绑定语义**
  - **ESM 导出绑定**：导入方读到的始终是导出方变量的当前值，导出方一改就可见
  - **CJS 导出值**：基本类型在导出那一刻拷贝，此后模块内变化传不出去；`exports` 对象本身按引用共享
  - **实测对照**：ESM 侧 `count` 变 1，CJS 侧 `snapshot` 停在 0，只有通过闭包函数重读才拿得到新值
- **循环依赖**
  - **ESM 不返回半成品**：实例化阶段一次性建好全部绑定，不存在 CJS 那种"先 undefined 后又有值"
  - **撞的是 TDZ**：未求值模块的 `const` / `let` 抛 `ReferenceError`，连 `Object.keys(命名空间)` 也一并抛
  - **函数声明是唯一例外**：`export function` 在实例化阶段就绪，换成 `export const fn = () => {}` 同样落入 TDZ；正解是消除环
- **ESM 引 CJS**
  - **default 是确定的**：就是 `module.exports` 本身
  - **具名导出靠静态扫描**：`cjs-module-lexer` 在求值前扫源码猜名字，逐个 `exports.x =` 或对象字面量可识别，动态拼装对象则只剩 `default`
  - **两条推论**：库作者把导出写成静态形式是兼容性义务；`__esModule` 在原生 ESM 下不参与判定
  - **互操作在收敛**：Node 22 已支持无顶层 await 时用 `require()` 直接加载 ESM
- **条件导出**
  - **顺序即优先级**：按 `exports` 键的书写顺序逐个匹配，`browser` 写在 `import` 前会把两条路径都抢走
  - **`default` 必须最后**：写在前面会吃掉后面所有条件
  - **默认封闭**：声明 `exports` 后未映射路径（含深链接）一律拒绝，把"哪些是公开 API"变成解析规则
  - **`imports` 是对内版本**：键以 `#` 开头、只能被本包引用，条件判定逻辑与 `exports` 一致
- **双包危险**
  - **成因**：同一包被 `import` 与 `require` 解析到两份入口，各自持有独立的模块级状态
  - **实测**：两侧各自 `+1`，两份计数始终不相等
  - **危害**：单例对象（配置、连接池、缓存、事件总线）静默分裂且不报错
  - **规避**：两份入口共享同一份状态文件 > 只发一种格式 > 把有状态部分拆成独立包
- **包管理**
  - **范围语义**：`^1.2.3` 覆盖 `>=1.2.3 <2.0.0`，但 `^0.2.3` 只覆盖 `<0.3.0`——`0.x` 下次版本变化视为破坏性
  - **版本即承诺**：major / minor / patch 对应破坏 / 新增 / 修复，用提交信息自动推导版本让二者强制对齐
  - **依赖树形状**：扁平提升造出幽灵依赖，依赖必须显式声明；workspace 与内容寻址存储见第 4 篇

cd code/esm-probe
