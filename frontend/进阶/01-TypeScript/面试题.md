# 模块面试题 · TypeScript

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../../进阶/面试方法论.md)的五步答题法——结论/原理/边界/追问/场景。

## 一、TS 基础

### Q1: TS 相比 JS 解决了什么问题？（第 01 篇）

- **结论**：TS 是 JS 的超集，用静态类型在编译期拦住类型错误，把"运行时爆炸"提前到"写代码时发现"。
- **原理**：类型系统 + 控制流分析在编译期推导与校验；编辑器基于类型做智能补全、跳转、重构；类型即文档，协作成本下降。
- **边界**：TS 不改变运行时语义（类型被擦除）；类型正确不等于逻辑正确，也不是性能保障。
- **追问**：为什么不是"编译更快"？→ TS 付出的是构建期成本，换的是运行期类型事故减少。
- **场景**：30+ 人协作的项目，接口入参出参类型化后，改字段名编译期全局报错，不再等线上才炸。

### Q2: `interface` 与 `type` 的区别？（第 01 篇）

- **结论**：多数场景可互换；interface 支持声明合并与面向对象语义，type 能表达更复杂的类型运算。
- **原理**：interface 可 `extends`、可重复声明合并；type 是类型别名，可组合联合/交叉/映射/条件类型。
- **边界**：interface 合并是特性也是风险（无意中被扩展）；type 不能声明合并。
- **追问**：能互相继承吗？→ type 可用交叉实现类似继承，interface `extends` type（对象类型）也允许。
- **场景**：公共 API 契约用 interface（可扩展、语义清晰）；联合类型、工具类型推导用 type。

### Q3: 联合类型、交叉类型、字面量类型？（第 01 篇）

- **结论**：联合是"或"（`A | B`），交叉是"与"（`A & B`），字面量把值收窄成类型（`'GET'`）。
- **原理**：联合类型的值属于任一成员；交叉合并成员的结构；`as const` / 字面量类型让魔法字符串变成可检查的常量集合。
- **边界**：交叉两个对象类型得到"两者属性都有"；联合后访问公共属性才安全，访问独有属性要收窄。
- **追问**：`string | number` 与 `string & number` 分别是什么？→ 前者任意其一，后者是 never（没有值同时是两者）。
- **场景**：请求方法 `type Method = 'GET' | 'POST' | 'PUT'`；响应 `{ code: 0; data: T } | { code: 1; msg: string }`。

### Q4: 泛型是什么？`<T>` 怎么用？（第 01 篇）

- **结论**：泛型是"类型的参数"，让函数/组件在保持类型安全的同时复用多种类型。
- **原理**：`function id<T>(x: T): T` 调用时由实参推导 T；约束 `extends` 限定 T 的范围；泛型让"输入与输出类型关联"成立。
- **边界**：泛型不是 any——any 丢失类型关系，泛型保留"同一类型"的约束；过早抽象会引入不必要的复杂度。
- **追问**：泛型组件 `FC<T>` 与普通组件区别？→ 调用时按 props 推导 T，保持 props/事件/返回值类型联动。
- **场景**：`useState<T>(init)`、`getProp<T, K extends keyof T>(obj, key)`、泛型表格列配置。

### Q5: `any` / `unknown` / `never` / `void` 的区别？（第 01 篇）

- **结论**：any 关闭类型检查，unknown 是"未知但需收窄"的安全版，never 是"不可能的类型"，void 是"无返回值"。
- **原理**：any 可赋值给任何类型也可被任何类型赋值（检查关闭）；unknown 只能赋值给 unknown/any，用前必须收窄；never 是底部类型，可赋值给一切、不能被赋值；void 表示函数不返回有用值。
- **边界**：any 是逃生舱也是隐患，团队规范应禁用（`no-explicit-any`）；never 常用于穷尽检查（switch 默认分支）。
- **追问**：函数抛异常返回什么？→ never——它永远不返回。
- **场景**：第三方无类型数据的过渡用 unknown + 收窄；分支穷尽检查 `const _exhaustive: never = x`。

## 二、类型进阶

### Q6: 类型收窄有哪些手段？（第 01 篇）

- **结论**：`typeof`、`in`、`instanceof`、`Array.isArray`、自定义类型守卫、可辨识联合，按场景组合。
- **原理**：控制流分析（CFA）在分支内收紧类型；可辨识联合靠共享判别字段（`type`/`code`）区分分支。
- **边界**：`typeof` 对 `null` 返回 `'object'`，需 `=== null` 判空；自定义守卫 `x is T` 写错会骗过类型系统、错误逃过检查。
- **追问**：为什么 `typeof` 对数组是 `'object'`？→ 需要 `Array.isArray` 收窄。
- **场景**：接口响应 `{ code: 0; data } | { code: 1; msg }` 用 `code` 判别；表单校验错误对象用 `in` 收窄。

### Q7: 工具类型 `Partial` / `Pick` / `Omit` / `Record` / `ReturnType` 的实现？（第 01 篇）

- **结论**：全部基于映射类型、`keyof`、条件类型与 `infer` 组合实现。
- **原理**：
  ```ts
  type Partial<T> = { [P in keyof T]?: T[P] }
  type Pick<T, K extends keyof T> = { [P in K]: T[P] }
  type Omit<T, K extends keyof any> = Pick<T, Exclude<keyof T, K>>
  type Record<K extends keyof any, V> = { [P in K]: V }
  type ReturnType<T> = T extends (...args: any) => infer R ? R : never
  ```
- **边界**：`Exclude` 基于可分配性，联合中的 never 被忽略；`keyof any` 是 `string | number | symbol`。
- **追问**：`infer` 是什么？→ 条件类型里"声明待推导类型变量"，`ReturnType` 就是从函数类型里抽返回值。
- **场景**：表单提交参数 `Pick<LoanParams, 'amount' | 'period'>`；事件回调返回值用 `ReturnType<typeof handler>` 推导。

### Q8: 泛型约束 `extends keyof`？（第 01 篇）

- **结论**：`K extends keyof T` 把泛型参数限制为 T 的键集合，保证索引访问 `T[K]` 安全。
- **原理**：`keyof T` 返回 T 的键联合；约束后 `T[K]` 索引访问类型合法且类型精确。
- **边界**：对象字面量传参时 TS 做多余属性检查，动态拼接 key 会绕开检查；约束要贴住真实场景，别过度。
- **追问**：`T[K]` 是什么？→ 索引访问类型，对应键的值类型。
- **场景**：`function getProp<T, K extends keyof T>(obj: T, key: K): T[K]`——取值类型与键联动，改字段名编译期报错。

### Q9: 枚举与 `as const` 联合类型怎么选？（第 01 篇）

- **结论**：默认用 `as const` + 联合类型——零运行时成本、类型更精确；需要反向映射（值→名）才用枚举。
- **原理**：枚举编译为运行时对象（数字枚举还有反向映射）；`const` 断言让字面量类型窄化，配合 `typeof` 生成联合。
- **边界**：数字枚举运行时能拿到不存在的值；`const enum` 完全内联但调试与 Babel 处理有坑。
- **追问**：`as const` 后怎么变成联合？→ `type Method = typeof METHODS[number]`。
- **场景**：请求方法、状态机、错误码用 `as const` + 联合；需要展示"值对应的名称"才用枚举。

### Q10: 函数重载与 `this` 类型？（第 01 篇）

- **结论**：重载让"同函数按参数形态返回不同类型"，`this` 参数显式声明函数体内 this 的类型。
- **原理**：重载签名列表在前、实现签名在后（实现签名对调用者不可见）；`this: SomeType` 是首个参数，编译后擦除。
- **边界**：重载过多会让实现签名难维护；`this` 类型错误通常源于回调里 this 丢失（箭头函数/解构）。
- **追问**：为什么重载实现签名必须兼容所有重载？→ 实现是唯一运行体，编译器按此检查。
- **场景**：`createElement(tag: 'div'): HTMLDivElement` + `createElement(tag: 'span'): HTMLSpanElement` 的重载；类方法里显式 `this` 防止误用。

## 三、类型体操

### Q11: 条件类型与 `infer` 的用法？（第 01 篇）

- **结论**：条件类型 `T extends U ? X : Y` 按类型关系选分支，`infer` 在分支里声明待推导变量；对裸类型参数会"分配式"逐个判断联合成员。
- **原理**：`T extends U ? X : Y` 中若 T 是泛型参数且是裸类型，会对联合每个成员分发；`infer` 用于从函数/元组/模板串里抽结构。
- **边界**：非分配时（T 被 `[]` 包住或用非裸参数）直接整体判断；递归条件类型要小心栈深。
- **追问**：`ReturnType` 为什么能抽返回值？→ `T extends (...args: any) => infer R ? R : never`，infer 声明 R。
- **场景**：`ElementType<T>` 从数组/元组抽元素类型；`Awaited<T>` 递归解包 Promise。

### Q12: 逆变与协变？（第 01 篇）

- **结论**：函数参数是逆变（更严格者可接受），返回值是协变（更宽泛者可接受）；strictFunctionTypes 下参数逆变检查开启。
- **原理**：类型兼容看"可赋值性"方向——返回值要求宽（协变），参数要求严（逆变）；对象属性默认协变。
- **边界**：方法语法（method shorthand）不强制参数逆变（为兼容老代码），用函数属性语法 `(x: T) => void` 才严格。
- **追问**：怎么记？→ "参数要敢收（超类型），返回要能给（子类型）"。
- **场景**：事件处理器签名、类继承里方法参数放宽会导致运行时类型错误，逆变检查兜住。

### Q13: 类型体操：实现一个 `DeepReadonly` / `MyOmit`？（第 01 篇）

- **结论**：`MyOmit` 用映射 + Exclude，`DeepReadonly` 用递归映射让所有层级只读。
- **原理**：
  ```ts
  type MyOmit<T, K extends keyof any> = { [P in Exclude<keyof T, K>]: T[P] }
  type DeepReadonly<T> = {
    readonly [P in keyof T]: T[P] extends object ? DeepReadonly<T[P]> : T[P]
  }
  ```
- **边界**：递归要处理函数/Date 等特殊类型（`extends object` 会误伤函数）；深度递归对超大类型有栈深压力。
- **追问**：`DeepReadonly` 对函数类型会怎样？→ 函数是 object，会被递归映射，需要额外排除。
- **场景**：配置对象只读化、API 响应只读化，防止业务代码误改。

## 四、工程实践

### Q14: 项目里怎么保证类型检查不拖慢构建？（第 02 篇）

- **结论**：多套 tsconfig 分治 + 类型检查与构建并行 + `skipLibCheck` + lint-staged 门禁。
- **原理**：`tsconfig.app.json` 管业务、`tsconfig.node.json` 管构建脚本，互不污染；`vue-tsc --noEmit` 与 `vite build` 并行跑，类型检查不再串行阻塞；lint-staged 只对暂存文件检查，改动小检查快。
- **边界**：`skipLibCheck` 跳过 .d.ts 检查省时，但会掩盖三方库类型问题，按需取舍。
- **追问**：改动范围怎么缩小？→ lint-staged 门禁只查本次提交文件。
- **场景**：CI 里 `vue-tsc --noEmit && vite build` 改成并行编排，构建时长明显下降。

### Q15: 声明文件 `.d.ts` 怎么写？第三方库类型缺失怎么处理？（第 02 篇）

- **结论**：`.d.ts` 只声明类型不实现；三方库缺类型按"查 @types → declare module → 自建声明 → 类型断言"的顺序兜底。
- **原理**：`declare module 'lib'` 为无类型库声明模块形状；`declare global` 扩展全局；`@types/*` 是社区类型包。
- **边界**：`declare module` 写得越粗，类型越废——尽量按实际 API 声明；类型断言（`as any`）是最后手段，要注释理由。
- **追问**：全局类型放哪？→ `env.d.ts` / `global.d.ts`，并在 tsconfig `include` 里覆盖。
- **场景**：`@types/weixin-js-sdk` 缺失 → 自建 `types/weixin.d.ts` 声明 `wx` 全局，业务代码获得补全与检查。

### Q16: 怎么用类型表达"接口契约"（类型即文档）？（第 02 篇）

- **结论**：在 api 层把接口入参出参收口成类型，页面只消费 api 层导出的类型——改契约编译期全局报错。
- **原理**：api 层导出 `LoanParams`/`LoanResult` 等类型，请求函数返回推导类型；页面不直接写 URL 与解析，类型成为唯一契约。
- **边界**：后端返回用可辨识联合 / 兜底类型表达成功失败；契约要跟后端同步维护，配代码生成（openapi）更稳。
- **追问**：类型即文档的前提？→ api 层是唯一出口，禁止页面直接 `fetch`。
- **场景**：借款页 `useLoanFlow` 只消费 api 层类型，后端改字段名 → 前端编译期一片红，而不是线上悄悄错。

### Q17: 30+ 人协作的 Vue3 + TS 项目，怎么用类型控制质量？（第 02 篇）

- **结论**：api 层类型收口（契约）→ 响应可辨识联合 → 状态用 `as const` + 联合 → tsconfig 分治 + 检查并行 → 提交前类型门禁。
- **原理**：类型把"接口协议"固化成可检查约束，页面不关心 URL/参数/返回解析；`as const` 消除魔法字符串；门禁让类型错误不流入主分支。
- **边界**：质量靠规范 + 门禁双轮——光有类型不设门禁，逃逸的 any 会腐蚀；全员禁用 any 要有替代路径（unknown + 收窄）。
- **追问**：渐进引入？→ 老代码先 `strict` 开启 + `noImplicitAny`，新代码强制类型，存量 any 列账逐步清。
- **场景**：接口分层（页面 → api 层 → 请求）后，新增接口只需在 api 层写一次类型，全项目消费。
