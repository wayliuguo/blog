# 模块总结 · 前端工程化与构建

## 知识主线

五篇不是并列的知识点，而是一条有依赖关系的链，每一篇都在回答上一篇留下的问题：

```
01 前端工程化全景（工程化解决什么问题）
        │  全景清楚了，但"代码怎么组织"还没着落——模块化是工程化的地基
        ▼
02 模块化规范（代码怎么组织）
        │  模块组织好了，怎么变成浏览器能跑的产物？
        ▼
03 构建工具（模块怎么打包成产物）  ★主轴
        │  项目能构建了，新项目怎么按统一规范一键初始化？
        ▼
04 脚手架的诞生（新项目怎么一键生成）
        │  单项目搞定了，多包大工程怎么统一依赖与任务编排？
        ▼
05 Monorepo 工程化（多包怎么统一管理）
```

本模块的主轴是**构建**：01 篇说明工程化为什么存在、给出「开发→测试→构建→发布→监控」全景，02 篇讲构建的对象——模块怎么组织、各规范如何取舍，03 篇讲打包本身（Webpack/Vite/Rollup 的机制与选型），04 篇讲脚手架如何把规范固化进新项目，05 篇讲多包工程如何统一依赖、版本与任务编排。

## 分篇知识点

### 01-前端工程化全景

- **工程化解决什么**
  - **本质与核心矛盾**：用管理手段和工具能力把「人的不确定性」转化为「流程的确定性」；核心矛盾是规模越大、协作与稳定的成本越高
  - **传统痛点**：开发模块划分混乱、协作冲突、测试手动点页面、构建无缓存无 hash、部署覆盖式无法回滚、监控靠用户截图反馈
  - **各环节的答案**：模块化/规范化/组件化/自动化/质量度量/部署回滚各有工程化方案与代表工具，一句话是「靠体系兜底」而非「靠个人水平负责」
- **五大阶段**
  - **开发体系**：脚手架、代码规范（ESLint+Prettier+husky+commitlint）、Monorepo、本地开发体验（热更新/Mock/环境变量）
  - **测试体系**：单元测试（Vitest/Jest）、组件测试、E2E 测试（Playwright/Cypress）、覆盖率与门禁
  - **构建体系**：入口分析 → 依赖收集 → Tree Shaking → 分包 → 产出带 hash 的静态资源；多环境构建与产物策略
  - **发布体系**：CI/CD 自动化、蓝绿/金丝雀/灰度/滚动发布策略、产物不可变 + 版本映射一键回滚
  - **监控体系**：日志、性能指标（FP/FCP/LCP、JS Error、API 错误率）、与后端 trace 打通定位慢接口
  - **环环相扣**：规范影响测试通过率、测试门禁决定能否进构建发布、发布可控性决定线上稳定性与监控信号量
- **依赖链**
  - **链条与瓶颈**：「规范/脚手架 → 质量门禁/CI-CD → 灰度/发布 → 监控/复盘 → 反哺规范」；链条最短的薄弱环节才是真正的瓶颈，规范再严没有监控兜底稳定性依然悬空
- **基建工程师成长路径**
  - **演进路径**：写页面 → 写组件库 → 写团队脚手架 → 设计整套研发基础设施
  - **角色差异**：服务对象从用户变为团队工程师，核心能力转向工程架构、自动化、抽象能力与复杂系统稳定性
  - **抽象能力是分水岭**：能否从 10 个项目的重复代码里提炼出通用基建，还需掌握封装抽象、工具链调度、稳定性、成本与长期维护等元知识
- **成熟度模型 L1–L5**
  - **五级递进**：原始（靠人工）→ 逐步（有部分工具）→ 规范（有统一规范）→ 自动（流水线化）→ 平台（平台化、度量驱动迭代）
  - **推进顺序**：遵循「先规范、再自动化、后平台化」，从高频痛点小的项目切入、见效快再扩散
  - **度量为先**：用构建耗时、发布失败率、回归缺陷率、上线至问题感知时长等指标驱动迭代，避免工程化沦为形式
- **最小实现**
  - **pipeline-demo 最小流水线**：到 `../03-交付与质量/code` 运行 `pipeline-demo.html`，看 build→test→deploy 最小流水线如何把「人肉接力」变成「机器编排」

### 02-模块化规范

- **为什么模块化**
  - **三大动机**：避免全局变量污染与命名冲突、解决依赖关系混乱与加载顺序难控、提升可维护性与协作效率
- **五种规范**
  - **CommonJS**：同步加载、运行时确定依赖、文件即模块有独立作用域，主要服务 Node 服务端
  - **AMD**：异步加载、贴合浏览器场景，`define(id?, dependencies?, factory)`，所有依赖加载完才执行回调，代表 require.js
  - **CMD**：sea.js 实现，整合 CommonJS 与 AMD，同步/异步兼有，`define(function (require, exports, module) {})`
  - **ES6 Modules**：编译时静态确定依赖、加载都是引用，可做静态分析与 tree-shaking
  - **UMD**：带前后端同构思想的封装工具而非规范，按环境自适应——先判断 Node `exports`、再判断 AMD `define`、最后挂到全局
- **CJS vs ESM 的本质差异**
  - **依赖确定时机**：CJS 运行时确认依赖，ESM 编译时确认依赖
  - **静态分析红利**：ESM 的编译时依赖让 tree-shaking 与类型检查成为可能
- **加载与输出细节**
  - **CommonJS 缓存与值拷贝**：首次加载后缓存、之后用缓存结果；`module.exports` 输出值的拷贝，模块内再变化不影响已输出值
  - **AMD 回调时机**：等所有依赖模块加载完成才执行当前模块的回调函数
  - **ESM 加载即引用**：所有加载都是引用，导入方与导出方共享同一份
- **package.json 入口字段**
  - **main**：JS 通用入口，`require` 导入返回该文件的 `module.exports`，不指定默认 `index.js`
  - **browser**：npm 包在浏览器环境下的入口文件
  - **module**：ES Modules 规范入口，browser 和 node 环境均可使用；为包体与引用方选对正确入口
- **最小实现**
  - **mini-bundler.html**：把依赖模块「拼装」成一份可运行产物，直观看见加载顺序如何被固定

### 03-构建工具

- **Webpack 是模块打包器**
  - **核心机制**：从入口递归构建依赖图，把 JS/CSS/图片/字体统一打包成浏览器可识别的静态资源
  - **核心配置**：entry/output/mode/module/plugins/optimization/devServer/resolve；`[name]`/`[hash]` 等占位符让产物文件名带内容指纹
  - **开发模式三件套**：mode、devServer（热更新/端口/代理）、source-map
- **loader 与 plugin 分工**
  - **loader 加工文件**：接收文件内容、加工后返回，在 `module.rules` 的 `use` 数组中声明、从右到左执行，负责非 JS 资源（babel-loader/css-loader/less-loader、Webpack 5 `type: 'asset'` 资源模块）
  - **plugin 监听生命周期**：与 loader 的单文件处理不同，plugin 监听整个构建生命周期，如 html-webpack-plugin 自动生成 HTML 并引入产物
- **代码分割与优化**
  - **splitChunks**：权衡「文件体积 vs 请求数」，按 chunks/minChunks/minSize/maxSize 与 cacheGroups（如单独打包第三方库）拆分，runtimeChunk 提取运行时代码
  - **tree-shaking**：开启 `usedExports` 配合 production 模式剔除未使用代码
  - **内容指纹与预加载**：`[contenthash]` 让文件名带内容指纹避免缓存失效；preload 立即获取关键资源、prefetch 空闲时获取非关键资源
  - **打包提速**：Dll 预构建把不变的第三方库提前打包并生成 manifest 清单；webpack-bundle-analyzer 可视化分析产物
- **Vite 基于原生 ESM**
  - **开发机制**：让浏览器通过 `<script type="module">` 自己分析模块、省去大量编译，esbuild 快速转译、类型检查交给 tsc，dev server 开箱即用
  - **生产构建**：底层仍用 Rollup 完成生产打包，自动分割异步代码，特殊拆分需求用 manualChunks
- **Rollup 专注库打包**
  - **产物干净**：不生成过多运行时代码，支持 ESM/CommonJS/UMD 多模块规范输出，tree-shaking 是强项
  - **核心配置**：input/output（dir/file、format）、external 忽略打进 bundle 的依赖；常用插件 @rollup/plugin-node-resolve 与 @rollup/plugin-terser
- **选型对比**
  - **Webpack**：生态庞大、可深度定制，适合大型应用与复杂配置
  - **Vite**：开发体验优先、约定优于配置，适合新一代应用脚手架
  - **Rollup**：产物干净、体积小，适合 npm 库/组件/工具发布

### 04-脚手架的诞生

- **脚手架的本质**
  - **核心职责**：把「创建项目的知识」沉淀为可复用代码，解决初始化、依赖版本漂移、规范不一致、升级困难
  - **四件事**：收集信息（交互式提问）→ 选择模板 → 渲染生成 → 收尾（安装依赖/初始化 git/输出指引）
- **CLI 设计**
  - **入口与参数解析**：`#!/usr/bin/env node` shebang 让系统用 Node 执行；commander/yargs 负责命令与参数解析（`program.command('create <projectName>').option('-t, --template')`）
  - **健壮性校验**：参数校验与错误处理，如目标目录已存在且未加 `--force` 时报错退出
- **模板引擎**
  - **占位符注入**：EJS/Handlebars 用占位符 + 条件 + 循环把配置注入模板文件；EJS 支持 JS 逻辑、Handlebars 偏纯文本
  - **构建坑**：插值语法可能与 Vue/框架语法冲突，应「生成时渲染」而非运行时渲染
- **生成器架构**
  - **通用三层架构**：任何 create-app 类工具都可抽象为「CLI 入口 → Generator 核心控制器（getTemplateDir/模板解析/文件渲染）→ Template 仓库层」
  - **模板组织**：create-vite 按「框架 × 变体」组织模板（FRAMEWORKS 元信息数组），getTemplateDir 逐文件写入、package.json 单独改写保留用户信息
- **私有脚手架平台**
  - **平台构成**：npm 私服模板包 + 模板中心后台 + 版本化发布（`--template enterprise@1.2.0`），把团队约定与企业级能力沉淀进模板
  - **建设要点**：模板迭代与灰度、埋点统计、可升级性（upgrade/codemod）、文档与示例、权限与审计
- **最小实现**
  - **scaffold-cli.html**：用 JS 把 `my-create app -t vue --force` 解析成结构化选项、按参数决定模板，看清 CLI 的本质

### 05-Monorepo 工程化

- **Monorepo vs Multi-repo**
  - **两种组织方式**：Multi-repo 每包一个 git 仓库、版本靠 semver 同步；Monorepo 单仓库多包以「统一版本 + 统一依赖 + 统一任务编排」换一致性
  - **收益**：原子提交（一次 commit 完成跨包改动）、依赖统一、增量构建、基建复用（lint/test/CI 只在根目录写一次）
- **pnpm 依赖管理**
  - **内容寻址存储（CAS）**：全局 `.pnpm-store` 按内容 hash 组织、一份内容多处链接，硬链接省磁盘、安装快
  - **非扁平结构防幽灵依赖**：pnpm 的 node_modules 只暴露直接依赖，与 npm/yarn 的扁平 hoist 不同，代码无法 require 未声明的包
  - **workspace 内部依赖**：`pnpm-workspace.yaml` 声明包范围，`workspace:*` 用工作区最新版本、软链/硬链即时生效无需发布
- **lerna 管版本**
  - **版本联动**：`lerna version/publish` 联动多包发版，按依赖顺序发布已变更包
  - **自动推导版本**：`--conventional-commits` 基于提交信息自动推导——fix→patch、feat→minor、BREAKING→major；新版 lerna(≥7) 把任务编排交给 turborepo
- **turborepo 管编排**
  - **任务依赖图**：turbo.json 的 pipeline 声明任务依赖（如 build 依赖 `^build`），并行执行无依赖任务、有依赖的按拓扑序先后执行
  - **增量缓存**：按「输入文件 hash」判断任务是否过期，命中即复用缓存产物；远程缓存让整个团队共享、CI 大幅提速
  - **定向操作**：`--filter` 定向构建受影响包、`--parallel` 并行启动所有 dev
- **大型案例与误区**
  - **Babel**：多版本共生 + 单元包模式，重度解耦、一个仓库内原子跨包改语法特性
  - **Vue 3**：按需拆包 + pnpm workspace 共建，dev 时改动 reactivity 即时反映到 compiler
  - **Turbo**：用自己构建自己（dogfooding 自举），天然验证工具质量与性能
  - **落地误区**：包太厚、循环依赖、权限全开放、跨包耦合无规约；应保持包粒度清晰、加 lint 规则与评审制度
- **最小实现**
  - **deps-demo.html**：可视化「内容寻址存储、硬链接/软链、扁平 hoist vs 隔离结构」，看懂幽灵依赖为何产生又为何被防住
