# 模块化规范

> 模块化是前端工程化的基石。理解各模块化规范的区别与取舍，是写出可维护、可复用代码的前提。

## 为什么需要模块化

- 避免全局变量污染、命名冲突
- 解决依赖关系混乱、加载顺序难控
- 提升代码的可维护性、可复用性与团队协作效率

## 主流模块化规范

- CommonJS
- AMD
- CMD
- UMD
- ES6（ES Modules）

## CommonJS（同步加载）

- 规定每个文件就是一个模块，有独立的作用域
- 每个模块内部都有一个 `module` 对象代表当前模块，其主要属性：
  - `id`：模块标识符，通常是绝对路径的模块文件名
  - `filename`：模块文件名，带有绝对路径
  - `loaded`：布尔值，是否已加载
  - `parent`：一个对象，调用该模块的模块
  - `children`：一个数组，该模块用到的其他模块
  - `exports`：对外输出的值
- 特点
  - 文件即模块，文件内代码运行在独立作用域
  - 模块可以被多次引用，第一次加载会被缓存，之后使用缓存结果
  - 加载某个模块，就是拿到该模块的 `module.exports` 属性
  - `module.exports` 输出的是值的**拷贝**，一旦输出，模块内发生变化不影响已输出的值
  - 加载顺序按照代码引入的顺序（同步加载，主要服务于 Node 服务端场景）

## AMD（异步加载）

- 模块化加载是异步的，完全贴合浏览器场景
- 异步加载：同时并发加载所依赖的模块，当所有依赖模块都加载完成之后，再执行当前模块的回调函数

> 示意片段（无配套脚本）

```js
define(id?, dependencies?, factory)
```

- `id`：模块名称
- `dependencies`：一个数组，定义依赖的模块
- `factory`：模块初始化时要执行的函数或对象

## CMD

- 整合了 CommonJS 和 AMD 的特点，其规范实现为 `sea.js`
- 同时支持同步和异步加载

> 示意片段（无配套脚本）

```js
define(factory)
define(function (require, exports, module) {})
```

- 参数说明
  1. `require`：一个函数，通过它可引用其他模块，也可通过 `require.async` 异步调用模块
  2. `exports`：一个对象，定义模块时通过向它添加属性来导出模块 API
  3. `module`：一个对象，包含 `uri`（模块完整 URI 路径）、`dependencies`（模块依赖）、`exports`（需导出的 API，作用同第二个参数 exports）

> 示意片段（无配套脚本）

```js
define(function (require, exports, module) {
    var add = require('math').add
    exports.increment = function (val) {
        return add(val, 1)
    }
    module.id = 'increment'
})
```

## UMD

- 并不是一个模块管理规范，而是带有**前后端同构思想**的模块封装工具
- 通过 UMD 可以在合适的运行环境选择对应的模块规范
- 实现原理
  1. 先判断是否支持 Node.js 模块格式（`exports` 是否存在）
  2. 再判断是否支持 AMD（`define` 是否存在），存在则使用 AMD 方式加载
  3. 若两者都不存在，则将模块公开到全局（`window` 或 `global`）

## ES6 Modules

- CommonJS 和 AMD 是在**运行时**确认依赖关系（运行时加载）
- ES6 module 在**编译时**就确认依赖关系，所有的加载其实都是**引用**，好处是可以做静态分析和类型检查

### 导出

> 示意片段（无配套脚本）

```js
export const first = 1

// 第二种方式
const first = 1
export { first }
```

### as 关键字（重命名导出）

> 示意片段（无配套脚本）

```js
const first = 1
export { first as second }
```

### export default（默认导出）

> 示意片段（无配套脚本）

```js
export default function () {}
```

- 导出默认输出，导入时不需要知道模块中的名字，可为它指定任意名字

### 导入

> 示意片段（无配套脚本）

```js
import { first } from './profile.js'
import { lastName as surname } from './profile.js'
import * as circle from './circle'
```

### 浏览器中使用 ES 模块

> 示意片段（无配套脚本）

```html
<script type="module">
    import module from './module'
</script>

<script nomodule>
    alert('您的浏览器不支持 ES 模块，请先升级！')
</script>
```

## package.json 与模块化入口

### main

- 指定 JS 的入口文件，在 `browser` 和 `Node` 环境中都可以使用
- 将项目发布为 npm 包后，`require` 导入时返回的就是 `main` 字段所列文件的 `module.exports`
- 如果不指定，默认是根目录下的 `index.js`

> 示意片段（无配套脚本）

```json
"main": "lib/index.js"
```

### browser

- 定义 npm 包在 browser 环境下的入口文件

> 示意片段（无配套脚本）

```json
"browser": "lib/index.js"
```

### module

- 定义 npm 包 ES Modules 规范的入口文件
- browser 和 node 环境均可使用

> 示意片段（无配套脚本）

```json
"module": "es/index.js"
```

## 小结

- 模块化规范
  - 为什么需要模块化
    - 避免全局污染与命名冲突
    - 解决依赖关系与加载顺序混乱
    - 提升可维护性、可复用性与协作效率
  - 主流规范
    - CommonJS / AMD / CMD / UMD / ES6 Modules
  - CommonJS（同步加载）
    - 文件即模块，独立作用域
    - `module` 对象与 `exports` 值拷贝
    - 模块缓存
    - Node 服务端场景
  - AMD（异步加载）
    - `define(id?, dependencies?, factory)`
    - 浏览器并发加载
  - CMD
    - sea.js 实现
    - 同步 / 异步混合加载
  - UMD
    - 前后端同构封装
    - 环境自适应：Node → AMD → 全局
  - ES6 Modules
    - 编译时静态依赖
    - `export` / `export default` / `as` 重命名
    - `import` 与浏览器 `<script type="module">`
  - package.json 与模块化入口
    - `main` / `browser` / `module` 字段
  - 规范对比小结
    - 加载方式 / 适用环境 / 依赖确定时机 / 代表实现
