# 网络可靠性与弱网

线上网络不是「通或不通」的二值状态，而是一段连续的质量区间：地铁里丢包 30%、运营商切换、CDN 节点抖动、后端偶发 5xx。前端在这件事上能做的有四件——**定超时、判断能不能重试、退避多久、以及让重试不会产生副作用**。这一篇把四件事分别实测一遍。

## 一、先定超时，再谈重试

没有超时的请求不是「更耐心」，而是把失败变成「一直转圈」。同一个后端（200ms 才返回），客户端两种设置：

```
| 客户端设置 | 限定等待 | 结果         | 实际耗时 |
|------------|----------|--------------|----------|
| 不设超时   | ∞        | 完成 200     | 214 ms   |
| 80ms 超时  | 80 ms    | TimeoutError | 110 ms   |
```

设置很短，靠 `AbortSignal.timeout` 一行就够：

> 摘自 `./code/net-lab/scenarios/retry.mjs`

```js
        for (const [name, limit] of [['不设超时', null], ['80ms 超时', 80]]) {
            const started = performance.now()
            let outcome
            try {
                const res = await fetch(`${base}/api/slow?ms=200`, limit ? { signal: AbortSignal.timeout(limit) } : {})
                await res.text()
                outcome = '完成 ' + res.status
            } catch (err) {
                outcome = err.name
            }
            timeoutRows.push([name, limit ? limit + ' ms' : '∞', outcome, ms(performance.now() - started)])
        }
```

三个必须知道的细节：

1. **超时不是一种错误，而是一次主动放弃。**`AbortSignal.timeout` 抛出的 `TimeoutError` 与网络错误（`TypeError: fetch failed`）要分开处理：前者值得重试（服务端可能只是慢），后者要看错误类型。
2. **取消只发生在客户端这一侧。**请求已经发出，服务端该算完还是算完——「前端超时了」绝不等于「服务端没执行」。这一点直接决定了下一篇的结论：**写操作必须靠幂等键兜底，不能靠超时**。
3. **超时要分层。**生产上一般至少三层：连接超时（几秒）、首字节超时（TTFB，十秒级）、整体超时（几十秒，配合上传下载进度）。只设一个「总超时」，会把「服务器在源源不断返回数据」的慢下载误杀。

还有一条容易忽略的：**超时值要按接口类型定**，不要全局一个数。列表页 3 秒没返回用户就跑了；报表导出 30 秒很正常。

## 二、哪些请求能自动重试

判断标准只有一条：**这个请求重发一次，结果会不会不一样**。按 HTTP 方法的幂等语义：

| 方法 | 自动重试 | 原因 |
| --- | --- | --- |
| `GET` / `HEAD` | 可以 | 只读，重试没有副作用 |
| `PUT` | 可以 | 幂等：同样的内容覆盖一次与两次结果相同 |
| `DELETE` | 可以 | 幂等：删两次与删一次结果相同 |
| `POST`（普通） | **不可以** | 每次调用都可能新建一条记录 |
| `POST` + 幂等键 | 可以 | 由服务端保证「同一个键只落库一次」 |

第三条是重试最常踩的坑：**服务端已经落库、但回包在网络上丢了**，客户端看到的是错误，重试一次就多下一单。脚本用一个「落库后断连」的端点把这件事做成可复现的实验：

```
| 客户端             | 两次请求的结果               | 服务端最终订单数 |
|--------------------|------------------------------|------------------|
| 不带幂等键         | 连接断开（结果未知） → ORD-2 | 2                |
| 带 Idempotency-Key | 连接断开（结果未知） → ORD-1 | 1                |
```

同样是「第一次连接断开、客户端重试」，不带幂等键最终落了 2 单，带幂等键是 1 单（第二次命中了同一个键，服务端把上次的结果回放）。

幂等键要注意三点：**由客户端生成**（UUID），**语义是「这一次业务意图」**而不是「这一个 HTTP 请求」——用户点击两次提交应该是两个意图，网络层重试同一个请求才是同一个意图；**有效期要明确**（通常 24 小时），过期后同一个键会被当成新请求。

## 三、退避与抖动

前两次必失败、之后成功的接口，四种策略的实测：

```
| 策略              | 尝试次数 | 各次等待       | 总耗时 | 结果 |
|-------------------|----------|----------------|--------|------|
| 不重试            | 1        | —              | 36 ms  | 放弃 |
| 固定间隔 200ms    | 3        | 200 / 200 ms   | 469 ms | 成功 |
| 指数退避 100ms×2ⁿ | 3        | 100 / 200 ms   | 375 ms | 成功 |
| 指数退避 + 抖动   | 3        | 55 / 265 ms    | 404 ms | 成功 |
```

> 摘自 `./code/net-lab/scenarios/retry.mjs`

```js
/** 重试策略：attempt 返回 true 表示成功 */
const STRATEGIES = [
    {
        name: '不重试',
        max: 1,
        backoff: () => 0
    },
    {
        name: '固定间隔 200ms',
        max: 4,
        backoff: () => 200
    },
    {
        name: '指数退避 100ms×2ⁿ',
        max: 4,
        backoff: (n) => 100 * 2 ** n
    },
    {
        name: '指数退避 + 抖动',
        max: 4,
        backoff: (n) => 100 * 2 ** n * (0.5 + Math.random())
    }
]
```

四个数字背后是四条判断：

- **不重试**：偶发 5xx 对用户就是一次可见的错误。这类错误里很大一部分再试一次就好了。
- **固定间隔**最快，但所有客户端会同时醒来。服务端每次 503 都带了 `Retry-After: 1`（秒），上面四种策略一个都没采纳它——**忽略 `Retry-After` 是自研重试最常见的毛病**：客户端比服务端更着急，只会把故障拖长。
- **指数退避**把压力往后摊，代价是总耗时变长；它解决的是「服务端刚崩，别立刻继续打」。
- **抖动（jitter）**不是为了显得随机，而是把同一批客户端错开。20 个客户端各重试 3 轮，按 50ms 分桶看重试时刻的分布：

```
| 重试方式           | 样本数 | 最拥挤窗口内的重试数 | 不同时间窗口数 |
|--------------------|--------|----------------------|----------------|
| 固定间隔（无抖动） | 60     | 20                   | 5              |
| 退避 + 抖动        | 60     | 10                   | 17             |
```

无抖动时 60 次重试只落在 5 个时间窗口里，最拥挤的一刻 20 个客户端同时打过来；加了抖动之后分散到 17 个窗口，最拥挤的那一刻减半。**服务端刚恢复的一瞬间，所有客户端同时回来，等于给自己补了一次流量洪峰**——这就是「重试风暴」。

所以一套完整的重试策略至少要有四个参数：**可重试的错误类型**（只重试网络错误与 5xx、429，4xx 不重试）、**上限次数**（3~5 次，超过就该报错）、**退避 + 抖动**、**尊重 `Retry-After`**。再往上一层要有熔断：连续失败到阈值就直接失败返回，不再打后端。

## 四、弱网下还能做什么

超时与重试是兜底，弱网体验的上限取决于这些手段：

- **请求去重与合并**：同一时刻对同一 URL 的重复请求合成一个（表格页连续点两次排序）；批量接口代替 N+1 请求。
- **并发限制与排队**：同时最多 4~6 个请求（HTTP/2 下单连接虽然能开很多 stream，但服务端处理能力有限），其余排队。首屏关键请求要能插队。
- **离线队列 + 后台同步**：写操作先落 IndexedDB 并立刻给用户反馈，联网后按顺序重放——重放必须带幂等键，否则离线期间的重试会制造重复数据。
- **乐观更新 + 回滚**：先改 UI，请求回来后确认或回滚。回滚要有明确的提示，静默回滚比失败更让人困惑。
- **降级策略**：超时后用上一次的缓存数据先把页面渲染出来并标注「数据可能不是最新」，比一直空白好。
- **按网络条件调整资源**：`navigator.connection.effectiveType`（`slow-2g` / `4g`）与 `navigator.connection.saveData` 可以决定要不要加载高清图、要不要自动播放视频。注意这个 API 只在部分浏览器可用，只能当「优化信号」，不能当「唯一依据」。
- **上传下载的可靠性**：分片 + 断点续传 + 秒传（见工程实践模块的大文件上传篇）。

## 五、怎么发现问题

**本地复现**：DevTools Network 面板的 Throttling 里有 `Slow 3G` / `Fast 3G` 预设，也可以自定义带宽与延迟（带宽用 kbps、延迟用 ms）。想验证超时与重试逻辑，把延迟拉到超过超时阈值即可；想验证离线队列，直接切 `Offline`。断言要落在行为上：超时后是否走了重试、重试是否有界、离线期间的操作联网后是否正确重放。

**线上观测**：光看平均耗时没有意义，要看这几个指标——**请求成功率、超时率、重试率、重试后的最终成功率、p95 与 p99 耗时**（见监控模块的性能与体验监控篇）。重试率高而最终成功率也高，说明退避策略在正常工作；重试率高但最终成功率低，说明后端确实扛不住，此时应降低重试次数或熔断，避免自己变成放大器。
