# CDN 与缓存体系

一遍网络请求最理想的状态是**不发这次请求**。缓存就是围绕这个目标做的分层决策：从浏览器内存、磁盘，到 CDN 边缘节点，每一层都可能替你把请求拦下来。这一篇讲清三层（强缓存 / 协商缓存 / 过期可用）的判定规则、CDN 那一层额外引入什么，以及落到工程上每类资源该配什么头。

## 一、缓存是一条决策链

一个请求从发出到拿到数据，路上有这些层可以「截胡」：

| 层 | 命中时 | 判据 |
| --- | --- | --- |
| 浏览器内存缓存（memory cache） | 不发请求，不落盘 | 同一次导航内的重复请求，配合 `Cache-Control` |
| 浏览器磁盘缓存（disk cache） | 不发请求，落盘 | 强缓存仍新鲜 |
| Service Worker | 不发请求（由你写逻辑） | 你自己实现的策略 |
| CDN 边缘节点 | 不发到源站 | 边缘自己那份副本还新鲜 |
| 源站 / 应用层缓存 | 不查数据库 | Redis 等 |

对前端来说，可控的是前两层与 CDN 的响应头配置。三者的判定规则是同一套：**看 `Cache-Control`、`Age`、`ETag` / `Last-Modified`**。所以先把这套规则吃透，CDN 的行为就只是「同一个规则在别人的机器上再跑一遍」。

## 二、四种响应头的实测对照

同一套服务端，三份资源配三种头。脚本先请求一次拿到 `ETag`，第二次带上 `If-None-Match` 再请求（`npm run cache`）：

```
| 资源          | Cache-Control                       | 首次状态/字节 | 二次状态/字节 | 二次是否传正文 |
|---------------|-------------------------------------|---------------|---------------|----------------|
| 内容哈希的 JS | public, max-age=31536000, immutable | 200 / 334 B   | 200 / 334 B   | 是             |
| 接口 JSON     | no-cache                            | 200 / 2.5 KB  | 304 / 0 B     | 否             |
| HTML 文档     | no-store                            | 200 / 54 B    | 200 / 54 B    | 是             |
```

**先说明「二次状态」这一列的口径**：脚本里的 `fetch` 是普通 HTTP 客户端，它不带缓存，永远照发不误。所以这一列只反映服务端行为，**不能**说明浏览器会不会发这次请求——那要看下面这张按 RFC 9111 判定出来的表：

```
| 资源          | 按 RFC 9111 判定的客户端行为              |
|---------------|-------------------------------------------|
| 内容哈希的 JS | 新鲜期内不发请求，且跳过刷新（immutable） |
| 接口 JSON     | 过期，带校验字段发请求（协商缓存）        |
| HTML 文档     | 每次都重新请求（no-store）                |
```

把两张表合起来读，就是三种缓存策略的本质差别：

- **强缓存（`max-age` + `immutable`）**：命中时**请求根本不出浏览器**。省下的是一整个往返，收益最大。代价是内容更新只能靠改 URL（所以配内容哈希文件名），`immutable` 是明确告诉浏览器「在我新鲜期内别做任何刷新动作，连 F5 都别重新验证」。
- **协商缓存（`no-cache` + `ETag`）**：请求照发，服务端内容没变就回 **304 且不带正文**。省的是正文，省不掉那一次 RTT。注意 `no-cache` 不是「不缓存」，是「每次用之前必须校验」——它和 `no-store` 完全是两回事。
- **`no-store`**：压根不落盘，每次都是完整的请求与正文。只该留给登录态、支付结果这类绝不允许留在磁盘上的响应。

判定规则本身很短，脚本里直接实现了一遍：

> 摘自 `./code/net-lab/scenarios/cache.mjs`

```js
/** 按 RFC 9111 判新鲜度：年龄 < max-age 就是新鲜的，直接可用，不发请求 */
function decide(headers, ageSeconds) {
    const cc = headers.get('cache-control') || ''
    const maxAge = Number((cc.match(/max-age=(\d+)/) || [])[1] ?? NaN)
    const swr = Number((cc.match(/stale-while-revalidate=(\d+)/) || [])[1] ?? NaN)
    if (/no-store/.test(cc)) return '每次都重新请求（no-store）'
    if (/immutable/.test(cc)) return '新鲜期内不发请求，且跳过刷新（immutable）'
    if (!Number.isNaN(maxAge) && ageSeconds < maxAge) return '新鲜，不发请求'
    if (!Number.isNaN(swr) && ageSeconds - maxAge < swr) return '先用旧数据渲染，后台悄悄刷新（swr 窗口内）'
    if (/no-cache/.test(cc)) return '过期，带校验字段发请求（协商缓存）'
    return '过期，重新请求'
}
```

顺序很重要：`no-store` 最先、`immutable` 与 `max-age` 判新鲜、然后才是 `swr` 窗口、最后落到协商缓存。

## 三、协商缓存的收益完全取决于校验字段稳不稳

给一个对不上的 `ETag` 再请求一次：

> 摘自 `./code/net-lab/scenarios/cache.mjs`

```js
        // 缓存失效：ETag 变了才会回 200 全量
        const changed = await fetch(base + '/api/cache/etag/doc.json', {
            headers: { 'If-None-Match': '"0000000000000000"' }
        })
```

实测结果：服务端状态码 `200`，正文 `2.5 KB`——说了「内容变了」，就得整份重传。这条推理有两个实用推论：

1. **`ETag` 不能带随机数或时间戳**。有些框架默认给 `ETag` 拼一段随机值，效果是每次请求都 200，协商缓存等于没配。`ETag` 必须是内容指纹（哈希）。
2. **`Last-Modified` 的精度只到秒**，同一秒内改两次就检测不到；能用 `ETag` 就别只靠时间。

再看 `Vary`：CDN 与浏览器缓存命中时，缓存的键是「URL + `Vary` 里声明的请求头」。`Vary: Accept-Encoding` 是正常且必要的（gzip / br 各存一份）；但 `Vary: User-Agent` 会让每个 UA 一份副本，边缘命中率直接崩掉。要按设备给不同内容，用 URL 区分（`/m/` 前缀）或 `Vary` 到粒度可控的头。

## 四、stale-while-revalidate：过期了也还能用

`max-age=60, stale-while-revalidate=600` 的意思：60 秒内新鲜；60 秒到 660 秒之间**已经过期但允许先用旧的**，同时后台发起刷新；超过 660 秒必须同步请求。脚本按 `Age` 的三个区间实测：

```
| 响应的 Age | 状态                | 客户端行为                                 |
|------------|---------------------|--------------------------------------------|
| Age=30s    | 新鲜                | 新鲜，不发请求                             |
| Age=300s   | 过期但在 swr 窗口内 | 先用旧数据渲染，后台悄悄刷新（swr 窗口内） |
| Age=1200s  | 过期且超出 swr 窗口 | 过期，重新请求                             |
```

它解决的是一个很具体的矛盾：列表页 / 详情页这类数据，**稍微旧一点用户根本感知不到**，但每次都同步等后端就是白白增加 TTFB。配上 swr 之后，用户立刻看到内容（可能是几秒前的），同时缓存被后台更新。配合 `stale-if-error` 还能在源站 5xx 时继续用旧内容兜底。

代价要写清楚：**用户可能看到旧数据**，所以只适合「可容忍轻微延迟」的资源，库存、余额、权限这类不行。

## 五、CDN 那一层额外引入什么

CDN 就是把「同一套缓存规则」放到离用户更近的机器上执行，但有三件事是必须知道的：

**1. 缓存键的决定权在 CDN 配置里。**大多数 CDN 默认按「完整 URL（含 query）」缓存，也允许忽略部分 query 参数（如把 `?t=timestamp` 忽略掉）。忽略错参数会造成**串号**——把带用户身份的参数忽略掉，就是一次安全事故。忽略参数只对「纯缓存击穿用途」的查询串做。

**2. 缓存分层与回源。**CDN 边缘节点之上还有中间的父层（也有厂商叫中心层），未命中时它先问父层，父层再回源。所以「源站 QPS 没涨」不等于「缓存真的命中了边缘」。判断命中层级看响应头：各家会加 `X-Cache: HIT/MISS`、`X-Cache-Lookup`、`Age`（`Age` 是这份副本已存活秒数，`Age` 很大说明命中的是很早的副本）。

**3. 刷新（purge）的粒度与代价。**发布新版本时，带内容哈希的静态资源不需要刷新（URL 变了就是新资源）；需要刷新的只有**不带哈希的入口文件**（HTML、Service Worker 文件、配置 JSON）。刷 CDN 是异步且可能延迟生效的操作，所以要紧的入口文件宁可配短 `max-age`（如 `no-cache` + ETag），也别指望「发布后我一定刷得掉」。

**预热（prefetch）**是反向操作：新版本发布前主动把热门资源推到边缘，避免发布瞬间所有边缘都回源造成雪崩。

## 六、按资源类型配头

这是一份可以直接照着用的表：

| 资源 | 推荐响应头 | 理由 |
| --- | --- | --- |
| 带内容哈希的 JS / CSS / 字体 / 图片 | `public, max-age=31536000, immutable` | URL 变了内容才变，可以放心长缓存 |
| HTML 入口 | `no-cache`（+ 弱验证 `ETag`）或 `max-age=0, must-revalidate` | 必须能及时拿到新版本的资源引用 |
| Service Worker 文件 | `no-cache` | 它决定后续所有资源的缓存策略，必须最先更新 |
| 接口数据（可容忍轻微延迟） | `max-age=60, stale-while-revalidate=600` | 秒开 + 最终一致 |
| 接口数据（必须实时） | `no-cache` + `ETag` | 至少省掉正文与带宽 |
| 登录态 / 支付结果 | `no-store` | 不允许留在任何一层磁盘上 |

**怎么确认真配对了**：

1. DevTools Network 面板看 **Size 列**——`(memory cache)` / `(disk cache)` 表示强缓存命中，`304` 表示协商缓存走了校验。
2. 看响应头里的 `Age` 与 CDN 的 `X-Cache`，确认命中的是边缘而不是回源。
3. 用 `curl` 手动验证协商缓存：`curl -I -H 'If-None-Match: "xxx"' <url>`，看是否真的回 304。
4. 发布流程里加一条检查：**新版本的 HTML 引用的资源名是否都带上了新的哈希**——哈希没更新，说明构建缓存或 CDN 缓存在捣乱。

## 小结

- 缓存是分层决策
  - 一次请求可能被浏览器内存、磁盘、Service Worker、CDN 边缘、源站缓存依次拦下
  - 每层的判定规则是同一套：`Cache-Control` + `Age` + `ETag` / `Last-Modified`
  - CDN 只是「同一套规则在离用户更近的机器上再跑一遍」
- 三种策略的取舍（实测）
  - 强缓存 `public, max-age=31536000, immutable`：不发请求，收益最大；代价是更新只能靠改 URL
  - 协商缓存 `no-cache` + ETag：实测 200 / 2.5 KB → 304 / 0 B，省正文不省 RTT
  - `no-store`：两次都是 200 / 54 B，只给登录态、支付结果这类用
  - `no-cache` ≠ 不缓存，它只是要求「每次用前校验」
- 协商缓存的成立条件
  - `ETag` 必须是内容指纹，带随机数或时间戳就等于没配（实测：对不上就回 200 全量 2.5 KB）
  - `Last-Modified` 精度只到秒，同秒内两次改动检测不到
  - `Vary` 会进缓存键：`Accept-Encoding` 正常，`User-Agent` 会让边缘命中率崩掉
- stale-while-revalidate
  - `max-age=60, stale-while-revalidate=600` 的三个区间：新鲜（不发请求）/ 过期可用（先用旧的 + 后台刷新）/ 必须同步
  - 适合可容忍轻微延迟的列表与详情数据；库存、余额、权限不行
  - 配合 `stale-if-error` 能在源站故障时继续兜底
- CDN 的三件额外事
  - 缓存键由 CDN 配置决定，忽略 query 参数要极其谨慎（忽略掉身份参数就是安全事故）
  - 有父层与回源分层：`X-Cache` / `Age` 才能看出命中的是哪一层，源站 QPS 不涨不等于边缘命中
  - 刷新是异步的：只刷新不带哈希的入口文件，其余靠内容哈希自然失效；发布前可预热热门资源
- 落地清单
  - 带哈希的资源长缓存 + HTML / SW 用 `no-cache` + 接口按「能否容忍旧数据」二选一
  - 验收看 DevTools 的 Size 列、响应头的 `Age` / `X-Cache`，以及「新 HTML 是否引用了新哈希」
