# 模块总结 · 网络与协议进阶

## 知识主线

四篇沿「一次请求的一生」排布：**先讲请求怎么上路（HTTP/2 与 HTTP/3）→ 再讲怎么让它不用上路（缓存与 CDN）→ 上路之后出问题怎么办（可靠性）→ 最后讲这条链路上哪里会被攻击（安全）**。每一篇都在回答上一篇留下的问题：

```
01 HTTP2 与 HTTP3（协议：多路复用 / 两种队头阻塞 / QUIC）
        │  它在回答的什么问题：HTTP/1.1 的并发靠多开连接堆出来，能不能只用一个连接
        ▼
02 CDN 与缓存体系（缓存：强缓存 / 协商缓存 / swr / 边缘节点）
        │  它在回答上一篇留下的问题：协议再快也要往返，能不能干脆别发这次请求
        ▼
03 网络可靠性与弱网（可靠性：超时 / 重试 / 退避抖动 / 幂等）
        │  它在回答上一篇留下的问题：缓存没命中、请求真的发出去了，然后失败了怎么办
        ▼
04 前端安全进阶（安全：CSP / SRI / Trusted Types / 供应链与泄露面）
        │  它在回答的什么问题：这条链路上每一步都可能被篡改或注入，工程上怎么设防
```

本模块的主轴是**「一次请求的成本可以从三个地方减掉：协议层少往返、缓存层不发请求、失败时正确地重试」**。四篇不是四个孤立话题，而是同一个问题的四层：01 把「同一连接上只能排队」变成「多路复用」，02 把「大部分请求」变成「不发」，03 把「失败」变成「有界重试且不产生副作用」，04 把「可信」变成「即使被注入也执行不了」。

本模块与其它模块最大的不同：**每个结论都配一条能复现的命令**，全部数字来自 `code/net-lab`（零依赖，只用 Node 22 的 `http` / `http2` / `crypto`，起临时服务器真跑真测）。唯一不能实测的是 HTTP/3，本机没有 QUIC 服务端——正文里明确标注了哪一段属于规范与公开资料，不编数字。

## 分篇知识点

### 01-HTTP2 与 HTTP3

- **HTTP/2 的并发模型**
  - **一句话**：把「请求」从「连接」里解耦，一条连接上开任意多 stream
  - **实测 6 个 200ms 请求**：HTTP/1.1 单连接 1332ms · 六连接 231ms · HTTP/2 单连接 245ms（连接数 6 → 1）
  - **连带结论**：域名分片、CSS 雪碧图、base64 内联这些「绕开 6 连接」的手段价值随之下降
- **两种队头阻塞**
  - **应用层**：HTTP/1.1 一个连接一次只处理一个请求，实测快请求被前面 500ms 的慢请求压到 617ms（平均）、678ms（最晚）
  - **HTTP/2 消除应用层队头阻塞**：同样场景快请求 33ms 完成，慢请求自己在 500ms 后返回
  - **TCP 层**：HTTP/2 全跑在一条 TCP 上，丢包波及所有 stream；HTTP/1.1 多连接时反而只影响其中一条
- **HTTP/2 的其它变化**
  - **二进制分帧**是基础：HEADERS / DATA 帧按 stream 编号交错
  - **HPACK 头部压缩**省掉大量重复头部，但压缩上下文是**连接级**的，带来 CRIME / BREACH 类攻击面
  - **`priority` 帧实现不一致**，控制首屏顺序还是靠 `preload` 与 `fetchpriority`
  - **服务端推送已被浏览器移除**，替代方案是 `103 Early Hints`
- **HTTP/3 与 QUIC**
  - **stream 级重传**：一条流丢包不影响其它流，这是 HTTP/2 解决不了的那一层
  - **握手更快**：TLS 1.3 内建；**0-RTT 恢复**的数据可被重放，只用于幂等请求
  - **连接迁移**：靠 Connection ID 而非四元组标识连接，Wi-Fi 切 4G 不用重新握手
  - **必须保留 HTTP/2 回退**：用 `Alt-Svc` 告知而不是强制，因为中间设备可能拦 UDP
  - ⚠️ **本机没有 QUIC 服务端，这一节不来自仓库实测**
- **工程落地**
  - **HTTP/2 实际使用必须 TLS + ALPN**；明文 h2c 只用于调试
  - **判断协议版本**：DevTools Network 的 Protocol 列（`h2` / `h3` / `http/1.1`），或 `curl -I --http2`
  - **打包策略**：请求数不再是核心指标，分包依据回到缓存命中率与首屏必需；正文压缩（gzip / brotli）仍必开

### 02-CDN 与缓存体系

- **缓存是分层决策**
  - **可能拦下请求的五层**：浏览器内存、磁盘、Service Worker、CDN 边缘、源站缓存
  - **判定规则同一套**：`Cache-Control` + `Age` + `ETag` / `Last-Modified`
  - **CDN 只是把同一套规则在离用户更近的机器上再跑一遍**
- **三种策略的取舍（实测）**
  - **强缓存 `public, max-age=31536000, immutable`**：新鲜期内不发请求，收益最大；代价是更新只能靠改 URL
  - **协商缓存 `no-cache` + ETag**：实测 200 / 2.5 KB → 304 / 0 B，**省正文不省 RTT**
  - **`no-store`**：两次都是 200 / 54 B，只给登录态、支付结果这类
  - **`no-cache` ≠ 不缓存**：它只是要求每次使用前必须校验
- **协商缓存的成立条件**
  - **`ETag` 必须是内容指纹**：带随机数或时间戳就等于没配（实测对不上就回 200 全量 2.5 KB）
  - **`Last-Modified` 精度只到秒**，同秒内两次改动检测不到
  - **`Vary` 会进缓存键**：`Accept-Encoding` 正常，`Vary: User-Agent` 会让边缘命中率崩掉
- **stale-while-revalidate**
  - **三个区间（`max-age=60, stale-while-revalidate=600`）**：Age=30s 新鲜不发请求 · Age=300s 先用旧的 + 后台刷新 · Age=1200s 必须同步请求
  - **适合**可容忍轻微延迟的列表与详情数据；**库存、余额、权限不行**
  - **配 `stale-if-error`** 可在源站故障时继续兜底
- **CDN 的三件额外事**
  - **缓存键由 CDN 配置决定**：忽略 query 参数要极谨慎，忽略掉身份参数就是安全事故
  - **有父层与回源分层**：源站 QPS 不涨不等于边缘命中，要看 `X-Cache` 与 `Age`
  - **刷新是异步的**：只刷新不带哈希的入口文件，其余靠内容哈希自然失效；发布前可预热热门资源
- **落地清单**
  - **带哈希的资源长缓存 + HTML / Service Worker 用 `no-cache` + 接口按「能否容忍旧数据」二选一**
  - **验收**：DevTools 的 Size 列（`memory cache` / `disk cache` / 304）、响应头 `Age` 与 `X-Cache`、「新 HTML 是否引用了新哈希」

### 03-网络可靠性与弱网

- **超时是前提**
  - **实测**：同一个 200ms 后端，不设超时 214ms 完成；80ms 超时 → `TimeoutError`，110ms 就放弃
  - **超时要分层**：连接超时、首字节（TTFB）超时、整体超时；只设总超时会误杀「服务端在持续返回数据」的慢下载
  - **超时值按接口类型定制**，不搞全局一个数（列表页 3s，报表导出 30s）
  - **取消只发生在客户端**：前端超时了不等于服务端没执行 → 写操作必须靠幂等兜底
- **能不能重试看幂等**
  - **可自动重试**：`GET` / `HEAD` / `PUT` / `DELETE`；**普通 `POST` 不可**；带幂等键的 `POST` 可以
  - **实测「服务端已落库但回包失败」**：不带幂等键重试后落了 2 单，带 `Idempotency-Key` 是 1 单
  - **幂等键三要求**：客户端生成、语义是「一次业务意图」而非「一个 HTTP 请求」、有明确有效期
- **退避、抖动与上限**
  - **四种策略实测**：不重试直接失败 · 固定 200ms 总耗时 469ms · 指数退避 100×2ⁿ 375ms · 加抖动 404ms
  - **必须尊重 `Retry-After`**：服务端每次 503 都带了它，四种策略一个都没采纳——不采纳只会把故障拖长
  - **重试风暴实测**：20 客户端 × 3 轮，无抖动的 60 次重试只落在 5 个时间窗口、最拥挤一刻 20 次；加抖动后减半、分散到 17 个窗口
  - **完整策略四要素**：可重试错误类型（网络错误 / 5xx / 429，4xx 不重试）、上限次数、退避 + 抖动、`Retry-After`；再上一层是熔断
- **弱网体验的其它手段**
  - **请求去重与合并**、**并发限制与关键请求插队**
  - **离线队列 + 后台同步**：重放必须带幂等键，否则离线期间的重试会造重复数据
  - **乐观更新要能回滚**，且回滚要有提示；超时先用缓存数据渲染并标注「可能不是最新」
  - **`navigator.connection`** 的 `effectiveType` / `saveData` 只能当优化信号，不能当唯一依据
- **观测**
  - **本地复现**：Network 面板的 Slow 3G / Offline 预设；断言落在「重试是否有界」这类行为上
  - **线上看**：成功率、超时率、重试率、重试后的最终成功率、p95 / p99
  - **重试率高但最终成功率低** = 重试在放大故障，此时该降低次数或熔断

### 04-前端安全进阶

- **CSP 防的是能力，不是输入**
  - **实测策略**：`script-src 'self' 'nonce-…'` 下，无 nonce 的内联脚本被拦、`onclick` 被拦、第三方 CDN 脚本被拦、同源脚本放行
  - **nonce 必须逐请求生成**：攻击者猜不到，注入的代码就执行不了
  - **默认禁止 `eval`**，顺手关掉「字符串变代码」一整类注入路径
  - **来源清单是白名单**：`img-src` 放了具体域名、`script-src` 仍拦第三方，按资源类型分别收紧
  - **上线顺序**：`Content-Security-Policy-Report-Only` 收集违规 → 修内联 → 切强制 → 保留上报端点
- **SRI 校验内容一致性**
  - **实测**：`vendor.js` 追加一段代码后 sha384 完全改变（`wrYiCf9b…` → `riDGD4fn…`），浏览器整块丢弃不执行
  - **`integrity` 必须配 `crossorigin`**，否则跨域脚本拿不到可校验的响应体
  - **只保证「与声明一致」，不保证「内容可信」**：哈希被一起改掉就失效
  - **哈希由构建期生成写进 HTML**；最适合第三方 CDN 的固定版本脚本，动态 `import()` 靠 CSP 兜底
- **Trusted Types 的价值是收口**
  - **`require-trusted-types-for 'script'`** 之后 `innerHTML = 字符串` 直接抛错，唯一通路是显式策略 + 净化
  - **全项目只有一处能把字符串变成 HTML**，审计才做得完
- **响应头与 Cookie**
  - **体检五项**：CSP · HSTS · `nosniff` · `Referrer-Policy` · `frame-ancestors`（旧写法 `X-Frame-Options`）
  - **HSTS 的 `includeSubDomains` 要谨慎**：先把整个域锁死在 HTTPS，子域有 HTTP 服务就直接不可用
  - **Cookie 四件套**：`HttpOnly` / `Secure` / `SameSite` / `__Host-` 前缀；`SameSite=None` 必须配 `Secure`
- **泄露面与供应链**
  - **`.map` 不上线**：只上传监控平台供反解（`hidden-source-map`）；线上留 `sourceMappingURL` 等于公开源码
  - **上报数据要白名单过滤**：手机号、token、密码字段一律不落地
  - **供应链**：锁文件进仓库 + `npm ci` + 私服代理 + 依赖审计进 CI；**减少依赖数量本身最有效**
  - **其它最先被翻的**：`.git` / `.env` / 备份文件被部署到静态目录、接口原样返回内部堆栈
