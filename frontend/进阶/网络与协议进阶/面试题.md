# 模块面试题 · 网络与协议进阶

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../面试方法论/面试方法论.md)的题型驱动答题法——先判断题型，再按该题型的骨架展开，不写满五步。
> 题目来源：由本模块四篇正文整理，每题在标题后标注出处（第 N 篇）。本模块所有数字都可在 `code/net-lab` 里用对应命令复现（`npm run http2 / cache / retry / security`）。

## 一、基础概念

### Q1: HTTP/2 相比 HTTP/1.1 最大的变化是什么？（第 1 篇）

- **结论**：多路复用——把「请求」从「连接」里解耦，一条连接上开任意多 stream。
- **原理**：HTTP/1.1 一个连接同一时刻只能处理一个请求，浏览器靠同域名 6 个连接凑并发；HTTP/2 引入二进制分帧，按 stream 编号交错发送多组 HEADERS / DATA 帧。
- **边界**：实测 6 个 200ms 请求——HTTP/1.1 单连接 1332ms、六连接 231ms、HTTP/2 单连接 245ms，即并发度相当而连接数 6 → 1。
- **追问**：那域名分片还有用吗？→ 在 HTTP/2 下是净损失（多付 DNS 与握手），只在 HTTP/1.1 客户端占比仍高时才保留。

### Q2: 什么是队头阻塞？HTTP/2 解决了哪一种？（第 1 篇）

- **结论**：HTTP/2 解决了**应用层**队头阻塞，没有解决 **TCP 层**队头阻塞。
- **原理**：应用层指的是同一连接上后发的请求必须等前一个响应回来；TCP 层指的是字节流有序，一个报文丢了它后面的字节都要等重传。
- **边界**：实测 1 个 500ms 慢请求压 5 个 20ms 快请求：HTTP/1.1 单连接上快请求平均拖到 617ms，HTTP/2 上 33ms 完成。
- **追问**：为什么 HTTP/2 的 TCP 层问题反而更严重？→ 所有请求挤在一条 TCP 连接上，丢包会波及全部 stream；HTTP/1.1 多连接时只影响其中一条。

### Q3: QUIC 与 HTTP/3 解决了什么？（第 1 篇）

- **结论**：把传输层从 TCP 换成基于 UDP 的 QUIC，实现 stream 级重传、更快的握手与连接迁移。
- **原理**：QUIC 在用户态实现流，某条流的报文丢了只重传那一段；TLS 1.3 内建，恢复连接可 0-RTT；用 Connection ID 而非四元组标识连接，网络切换不用重新握手。
- **边界**：0-RTT 的数据**可被重放**，所以只能用于幂等请求；必须保留 HTTP/2 回退（`Alt-Svc` 告知而不强制），因为中间设备可能拦 UDP。
- **追问**：本仓库能实测 HTTP/3 吗？→ 不能，本机没有 QUIC 服务端；`net-lab` 只实测 HTTP/1.1 与 HTTP/2（h2c），HTTP/3 部分只有原理。

### Q4: 强缓存和协商缓存分别省什么？（第 2 篇）

- **结论**：强缓存省掉整个请求；协商缓存只省正文，省不掉那一次往返。
- **原理**：`max-age` 未过期时浏览器直接用本地副本、不发请求；`no-cache` + `ETag` 时浏览器仍发请求，服务端内容未变回 304（无正文）。
- **边界**：实测接口 JSON 第二次请求 `200 / 2.5 KB` → `304 / 0 B`；`immutable` 下连 F5 都不做重新验证。
- **追问**：`no-cache` 和 `no-store` 有什么区别？→ `no-cache` 会缓存但每次使用前必须校验；`no-store` 完全不落盘，实测两次都是 200 / 54 B。

### Q5: stale-while-revalidate 解决什么问题？（第 2 篇）

- **结论**：过期后允许「先用旧内容、同时后台刷新」，用一点数据新鲜度换掉一次同步等待。
- **原理**：`max-age=60, stale-while-revalidate=600` 的三个区间——Age<60 新鲜不发请求；60~660 先用旧的并后台刷新；>660 必须同步请求。
- **边界**：实测 Age=30s / 300s / 1200s 分别落在「新鲜」「过期但窗口内」「超出窗口」；只适合可容忍轻微延迟的数据，库存、余额、权限不行。
- **追问**：源站挂了怎么办？→ 配 `stale-if-error`，在错误期间继续用旧内容兜底。

### Q6: 一个请求在客户端超时了，服务端会不会继续执行？（第 3 篇）

- **结论**：会。取消只发生在客户端这一侧。
- **原理**：`AbortSignal.timeout(ms)` 到期只是客户端停止等待并抛 `TimeoutError`，请求报文早已发出，服务端按自己的节奏处理完。
- **边界**：实测 200ms 的后端在 80ms 超时下客户端 110ms 就放弃，但服务端仍然算完。
- **追问**：这对写操作意味着什么？→ 「前端超时了」不能当作「没执行」的依据，写操作必须靠幂等键兜底。

### Q7: 哪些 HTTP 方法可以安全地自动重试？（第 3 篇）

- **结论**：`GET` / `HEAD` / `PUT` / `DELETE` 可以；普通 `POST` 不可以，带幂等键的 `POST` 可以。
- **原理**：判断标准是幂等语义——重发一次结果是否相同。`PUT` 是覆盖、`DELETE` 是删除，重复执行结果一致；`POST` 每次都建一条新记录。
- **边界**：实测「服务端已落库但回包失败」时重试一次：不带幂等键最终 2 单，带 `Idempotency-Key` 是 1 单。
- **追问**：幂等键该由谁生成、粒度多大？→ 客户端生成；语义是「一次业务意图」而非「一个 HTTP 请求」，用户点两次提交是两个意图，网络层重试同一个请求才是一个意图。

### Q8: CSP 的 nonce 机制为什么能挡住注入的脚本？（第 4 篇）

- **结论**：因为 nonce 逐请求随机、攻击者猜不到，注入的内联脚本带不上合法 nonce。
- **原理**：`script-src 'self' 'nonce-xxx'` 下，内联脚本必须带匹配的 nonce 才执行；`onclick` 这类内联事件处理器同样按内联脚本处理。
- **边界**：实测判定表中，无 nonce 的内联脚本、`onclick`、第三方 CDN 脚本全被拦，同源脚本与带 nonce 的内联脚本放行。
- **追问**：上线 CSP 第一步做什么？→ 先上 `Content-Security-Policy-Report-Only` 只上报不拦截，收集到真实违规后再切强制模式。

## 二、机制与原理

### Q9: HTTP/2 的 HPACK 头部压缩有什么代价？（第 1 篇）

- **结论**：压缩上下文是**连接级**的，这带来了 CRIME / BREACH 类的攻击面。
- **原理**：静态表 + 动态表 + 哈夫曼编码，同一连接上重复的头部（Cookie、UA）用索引引用，省掉大量字节；动态表在连接内跨请求共享。
- **边界**：攻击者若能观测到响应长度，就可能通过构造请求、观察压缩后的长度变化来推断压缩字典里的秘密内容。
- **追问**：怎么缓解？→ 对敏感数据禁用压缩、把秘密与用户输入分开响应、开启 `SameSite` 与 CSRF token 的双重校验。

### Q10: 为什么 HTTP/2 的服务端推送被废弃了？（第 1 篇）

- **结论**：服务端无法判断客户端是否已缓存，容易推重复，反而浪费带宽。
- **原理**：推送的资源不经过客户端缓存判断（除非用 `cache-digest` 之类的辅助），推过去的可能白推；且推送与客户端自己的请求竞争带宽。
- **边界**：想要「响应还没生成就先让浏览器去准备资源」，用 `103 Early Hints` ——它只是提前给出 `Link` 头，是否加载由客户端决定。
- **追问**：那首屏资源怎么提前？→ `preload` + `fetchpriority`（见性能模块的加载与首屏优化篇）。

### Q11: `ETag` 为什么不能带随机数或时间戳？（第 2 篇）

- **结论**：协商缓存的收益完全取决于校验字段是否稳定，带随机值等于每次都 200 全量。
- **原理**：`ETag` 是内容指纹，只有内容未变时它才相同；如果每次生成都不同，客户端永远无法命中 304。
- **边界**：实测对不上的 `ETag` → 服务端返回 200 与完整 2.5 KB 正文；`Last-Modified` 精度只到秒，同秒内两次改动检测不到。
- **追问**：`ETag` 与 `Last-Modified` 同时存在时谁优先？→ `ETag` 优先，`If-None-Match` 会让服务端忽略 `If-Modified-Since`。

### Q12: 指数退避为什么必须加抖动？（第 3 篇）

- **结论**：不加抖动时，同一批客户端会同时重试，把故障变成流量洪峰。
- **原理**：退避只把重试往后推，但所有客户端的时钟与策略一致，重试时刻仍然对齐；抖动（随机系数）把它们的时刻摊开。
- **边界**：实测 20 客户端 × 3 轮重试，按 50ms 分桶：无抖动时 60 次重试只落在 5 个窗口、最拥挤一刻 20 次；加抖动后最拥挤一刻 10 次、分散到 17 个窗口。
- **追问**：还有哪些参数不能少？→ 可重试的错误类型、上限次数、尊重 `Retry-After`；再上一层要有熔断。

### Q13: SRI 能防住什么，防不住什么？（第 4 篇）

- **结论**：能防「内容与声明不一致」（CDN 被篡改、中间人被换内容）；防不住「内容本身就是恶意的」。
- **原理**：哈希不需要密钥，浏览器下载完自己算一遍比对；攻击者若能同时改 HTML 里的 `integrity`，校验照样通过。
- **边界**：实测 `vendor.js` 追加一段代码后 sha384 由 `wrYiCf9b…` 变成 `riDGD4fn…`；`integrity` 必须配 `crossorigin`，否则跨域脚本拿不到可校验的响应体。
- **追问**：为什么自己构建的产物很少用 SRI？→ 产物文件名已带内容哈希，改内容就是改 URL；SRI 最适合第三方 CDN 的固定版本脚本。

### Q14: Trusted Types 相比「写个净化函数」强在哪？（第 4 篇）

- **结论**：强在**收口**——全项目只有一处能把字符串变成 HTML，审计才做得完。
- **原理**：开 `require-trusted-types-for 'script'` 后，`element.innerHTML = 字符串` 直接抛 `TypeError`，必须通过显式创建的策略对象赋值，策略里做净化。
- **边界**：它的前提是项目已经清掉内联脚本与老库（不少老库依赖 `eval` 或直接 `innerHTML`），否则迁移成本会很高。
- **追问**：它和 CSP 是什么关系？→ 用 CSP 声明 `require-trusted-types-for 'script'` 与 `trusted-types` 白名单来启用与限定策略名。

### Q15: `Vary` 为什么会打掉 CDN 命中率？（第 2 篇）

- **结论**：因为 `Vary` 声明的内容会进入缓存键，粒度一粗，同一份内容会被拆成很多份副本。
- **原理**：缓存的键是「URL + `Vary` 里列出的请求头」。`Vary: Accept-Encoding` 只会多出 gzip / br 两份；`Vary: User-Agent` 会按 UA 字符串各存一份，副本数直接爆炸。
- **边界**：要按设备给不同内容，应该用 URL 区分（如 `/m/` 前缀）或 `Vary` 到粒度可控的头（如 `Vary: Accept`）。
- **追问**：CDN 侧还有哪些键的坑？→ 「忽略 query 参数」很危险：把带用户身份的参数忽略掉，就是一次串号事故。

## 三、排障与选型

### Q16: 怎么确认线上到底跑的是 HTTP/1.1 还是 HTTP/2、HTTP/3？（第 1 篇）

- **结论**：看 DevTools Network 面板的 Protocol 列（`http/1.1` / `h2` / `h3`），或用 `curl -I --http2` 看响应首行。
- **原理**：HTTP/2 实际使用必须经过 TLS + ALPN 协商（`h2`）；HTTP/3 靠 `Alt-Svc` 响应头告知，浏览器下次才走 `h3`。
- **边界**：明文 h2c 只在内部调试用，线上不会出现；首次访问一定不是 HTTP/3，因为要等 `Alt-Svc` 缓存下来。
- **追问**：为什么本地起了 HTTP/2 服务但浏览器还是走 1.1？→ 没有 TLS/ALPN，浏览器不会对普通 http 协商 h2（除 `--http2` 实验或 h2c 直连）。

### Q17: 页面首屏慢，怎么判断是网络问题还是缓存没配好？（第 2 篇）

- **结论**：先看 DevTools 的 Size 列与响应头 `Age` / `X-Cache`，再决定改哪一层。
- **原理**：Size 显示 `(disk cache)` / `(memory cache)` 说明强缓存命中；显示 304 说明走了协商缓存；显示实际字节且 `Age` 很小说明每次都回源。
- **边界**：脚本里的 `fetch` 不带缓存，所以用脚本连发两次请求「看不到」强缓存的效果——那是**服务端行为**，浏览器是否发请求要看 RFC 9111 的判定。
- **追问**：新版本发布了但用户还是旧资源怎么办？→ 查 HTML 是否被缓存（应配 `no-cache`）、新 HTML 里的资源名是否带上了新哈希。

### Q18: 重试策略怎么配才安全？（第 3 篇）

- **结论**：四个参数齐备——可重试错误类型、上限次数、退避 + 抖动、尊重 `Retry-After`，再配熔断。
- **原理**：只对网络错误、5xx、429 重试；4xx 重试毫无意义（参数错了重试还是错）。上限 3~5 次，超了就报错；退避摊开压力，抖动打散同批客户端。
- **边界**：实测四种策略的总耗时 36ms / 469ms / 375ms / 404ms 说明「越快不一定越好」——固定间隔最快，但制造了同步重试风暴（最拥挤一刻 20 次）。
- **追问**：服务端让你等 1 秒（`Retry-After`），客户端等 200ms 就重试有什么问题？→ 你在用它承受不了的速度打它，只会延长故障。

### Q19: 怎么在本地复现弱网问题？（第 3 篇）

- **结论**：用 DevTools Network 面板的 Throttling（`Slow 3G` / `Fast 3G` / 自定义）与 `Offline`，断言落在行为上。
- **原理**：Throttling 直接控制带宽（kbps）与延迟（ms）；把延迟拉到超过超时阈值就能触发超时分支，切 `Offline` 就能验证离线队列与重放。
- **边界**：「请求发出去了但响应丢了」这类故障本地面板模拟不出来，要让服务端配合（`net-lab` 用 `/api/flaky-order` 的「落库后断连」模拟）。
- **追问**：要断言什么？→ 超时后是否进入重试、重试是否有界、离线期间的操作联网后是否只落一次库。

### Q20: CSP 上线后有用例被拦了，怎么定位与收敛？（第 4 篇）

- **结论**：看违规上报（`report-uri` / `report-to`），按指令逐条收敛，不要图省事加 `unsafe-inline`。
- **原理**：CSP 违规报告里带 `violated-directive` 与 `blocked-uri`，能直接定位是哪个来源的哪类资源被拦。
- **边界**：加 `'unsafe-inline'` 会让整条内联防线失效——**注意 CSP 2/3 里存在 nonce 或 hash 时 `unsafe-inline` 会被忽略**，所以「加了也没用」；正确做法是把内联脚本改成 nonce 或 hash。
- **追问**：`strict-dynamic` 什么时候用？→ 现代前端需要在运行时动态插脚本（如加载第三方 SDK）时，用它可以放行「被合法脚本插入的脚本」，同时忽略来源清单。

### Q21: 怎么判断一个接口该用强缓存、协商缓存还是不缓存？（第 2 篇）

- **结论**：按「内容能不能容忍旧」与「更新频率」两问决定：静态资源带哈希 → 强缓存；接口实时但内容常不变 → 协商缓存；可容忍几秒旧数据 → swr；敏感且必须最新 → `no-store`。
- **原理**：强缓存省掉往返但只能靠改 URL 更新；协商缓存实时但每次一个 RTT；swr 先用旧的后台刷新；`no-store` 完全不落盘。
- **边界**：登录态、支付结果绝不能进强缓存或 swr，也不该进协商缓存的磁盘副本——它们是 `no-store` 的典型对象。
- **追问**：为什么带内容哈希的资源可以放心用 `immutable`？→ 内容变了文件名就变了，URL 与内容一一对应，不存在「同一个 URL 内容变了却拿不到新版本」的情况。

## 四、场景设计题

### Q22: 设计一套前端请求层，要求「弱网可用、重试不产生脏数据」（第 3 篇）

- **结论**：分层做——统一超时与重试策略、幂等键、请求去重与并发控制、离线队列、可观测。
- **原理**：超时分层（连接 / 首字节 / 整体）；重试只覆盖网络错误与 5xx/429，退避 + 抖动 + 尊重 `Retry-After`，上限 3~5 次；写操作由客户端生成幂等键，服务端按键去重并对重复请求回放上次结果。
- **边界**：用 `net-lab` 的实测数据说明必要性——同样「服务器已落库但回包失败」，不带幂等键落 2 单、带幂等键落 1 单；重试风暴里无抖动时 60 次重试挤在 5 个窗口。
- **追问**：并发控制怎么和 HTTP/2 配合？→ HTTP/2 下单连接能开很多 stream，但服务端处理能力有限，所以要自己在客户端限并发（4~6），并让首屏关键请求能插队。

### Q23: 一个页面既用了自研脚本，又用了 CDN 上的 jQuery、统计 SDK 和地图 JS，CSP 该怎么写？（第 4 篇）

- **结论**：来源清单写死具体域名（不用 `*`），内联脚本全部改 nonce，地图 SDK 若要动态插脚本则评估 `strict-dynamic`。
- **原理**：`default-src 'self'` 打底，`script-src 'self' 'nonce-…' https://cdn.example.com https://map.example.com`；`img-src` 单独放行图片 CDN 与 `data:`；`object-src 'none'`、`base-uri 'self'`、`frame-ancestors 'none'`。
- **边界**：先上 Report-Only 收违规，因为清单一定会漏；`unsafe-inline` 在存在 nonce 时会被忽略，加它只会让人误以为放行了。
- **追问**：统计 SDK 需要一个内联的初始化片段怎么办？→ 把它改成带 nonce 的内联脚本，或改成外部文件并把初始化参数放到 `data-*` 属性上。

### Q24: 首屏有 30 个静态资源，怎么让「第二次访问几乎零等待」？（第 2 篇）

- **结论**：带内容哈希的资源配 `immutable` 长缓存，HTML 配 `no-cache` + ETag，CDN 边缘命中并预热。
- **原理**：资源名带哈希 → URL 与内容一一对应 → 可以设一年且 `immutable`；HTML 不带哈希 → 必须能及时更新，用 `no-cache` 保证每次校验；CDN 边缘命中后连源站都不用回。
- **边界**：要注意 CDN 的刷新粒度（只刷新不带哈希的入口文件）与 `Vary` 配置；`Age` 与 `X-Cache` 是判断命中层级的关键响应头。
- **追问**：为什么不能用「HTML 也长缓存 + 发布时刷 CDN」？→ 刷新是异步且可能延迟，发布瞬间会有用户拿到新旧不匹配的 HTML，加载到已删除的旧哈希资源就是 404。

### Q25: 一个内部管理后台要做「离线可填表、联网自动提交」，怎么保证不重复提交？（第 3 篇）

- **结论**：本地队列 + 幂等键 + 服务端按键去重，配合 `IndexedDB` 持久化与后台同步。
- **原理**：每条待提交记录在本地生成唯一幂等键并持久化，重放时带上同一个键；服务端第一次落库、后续同键直接回放结果。
- **边界**：重放顺序要保序（同一表单的多次编辑不能乱序提交）；超时与取消都只发生客户端，所以「提交失败」不等于「没下单」——用 `net-lab` 的实测（2 单 vs 1 单）说明差别。
- **追问**：离线期间用户改了同一份表三次怎么办？→ 合并成一次提交（同一个业务意图），或按版本号顺序提交并由服务端做冲突检测。

### Q26: 团队里有人提「为了省请求，把首屏需要的小图都内联成 base64、再把 JS 拆到多个域名」，怎么评估？（第 1 篇）

- **结论**：这两条都是 HTTP/1.1 时代的绕路手段，在 HTTP/2 下是净损失。
- **原理**：HTTP/2 一个连接就能承载并发，域名分片反而要多付 DNS 与握手（实测六连接 231ms vs 单连接 245ms，而连接数 6 → 1 说明多连接并没有更快）；base64 内联会让图片随 CSS / JS 一起失效，牺牲缓存粒度。
- **边界**：如果站点仍有大量 HTTP/1.1 客户端（比如某些内嵌 WebView），可以保留部分策略，但要有数据支撑，而不是默认沿用。
- **追问**：那首屏到底怎么提速？→ 回到「关键路径 + 缓存」：关键 CSS 内联、首屏图 `fetchpriority`、带哈希长缓存（见性能模块的加载与首屏优化篇与第 2 篇）。
