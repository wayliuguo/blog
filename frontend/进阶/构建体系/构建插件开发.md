# 构建插件开发

会写构建插件，是"会用构建工具"和"能改造构建流程"的分界线。难点不在语法——三套工具的对象形状都很简单——而在于**同一件事在三个工具里的抽象层级完全不同**：Rollup/Vite 给你"回答 id 和内容"的声明式钩子，webpack 把你放进它的内部工厂。

本篇用**同一个需求在三套工具里各写一遍**的方式讲清楚差异，再用 unplugin 展示"写一次跑三处"，最后列出实测踩到的坑。

## 一、插件能扩展什么

不管哪个工具，插件的扩展点只有三类：

```
1. 解析（这个 import 指向谁？内容从哪来？）  → resolveId / load / resolver 钩子
2. 转换（内容要不要改？）                    → transform / loader
3. 产物（最后再加工一下）                    → generateBundle / processAssets / emit
```

绝大多数插件只用到其中一类。判断"该挂哪个钩子"的方法很简单：**先问这个能力发生在构建的哪一步**。

## 二、三套钩子对照

| 能力 | Rollup | Vite | webpack |
| ---- | ---- | ---- | ---- |
| 解析 id | `resolveId` | `resolveId`（可加 `enforce`） | `normalModuleFactory.beforeResolve` / `resolve.plugins` |
| 提供内容 | `load` | `load` | loader（且要求文件真实存在） |
| 转换代码 | `transform` | `transform` | loader |
| 产出文件 | `generateBundle` + `emitFile` | 同 Rollup | `compilation.emitAsset` |
| 仅 dev | 无 | `configureServer` / `handleHotUpdate` | `compiler.hooks.watchRun` / devMiddleware |
| 收尾 | `buildEnd` / `writeBundle` | 同 Rollup | `compiler.hooks.done` |

差异的根源：**Rollup/Vite 是"我告诉你 id，你给我内容"的契约；webpack 是"模块必须真实存在，内容由 loader 加工"的模型**。所以 webpack 的虚拟模块要绕一层。

## 三、同一个需求，三套实现

需求：让源码能 `import { BUILD_INFO } from 'virtual-build-info'`，拿到构建时注入的信息。

### Rollup 版

> 摘自 `./code/build-lab/plugin-lab/three-ways.mjs`（运行：`npm run plugin`）

```js
function rollupPlugin() {
    return {
        name: 'build-info-rollup',
        resolveId(source) {
            if (source === VIRTUAL) return RESOLVED
            return null
        },
        load(id) {
            if (id === RESOLVED) return `export const BUILD_INFO = ${INFO};`
            return null
        }
    }
}
```

### webpack 版

> 摘自 `./code/build-lab/plugin-lab/three-ways.mjs`（运行：`npm run plugin`）

```js
// webpack 没有 resolveId/load，得自己接进 resolver + 造一个模块
function webpackPlugin() {
    return {
        apply(compiler) {
            // 拦截解析：把虚拟 id 指向一个"不存在的绝对路径"，再由 loader 提供内容
            compiler.hooks.normalModuleFactory.tap('build-info-webpack', (nmf) => {
                nmf.hooks.beforeResolve.tap('build-info-webpack', (resolveData) => {
                    if (resolveData.request === VIRTUAL) {
                        resolveData.request = path.join(ROOT, 'virtual-build-info.js')
                    }
                })
            })
            // 用 loader 把内容喂进去
            compiler.options.module.rules.push({
                test: /virtual-build-info\.js$/,
                use: [
                    {
                        loader: path.join(ROOT, 'virtual-loader.cjs'),
                        options: { info: INFO }
                    }
                ]
            })
        }
    }
}
```

注意那句"不存在的绝对路径"其实要打个引号——**webpack 要求模块文件真实存在**，所以仓库里放了一个占位文件：

> 摘自 `./code/build-lab/plugin-lab/virtual-build-info.js`（运行：`npm run plugin`）

```js
// 占位文件：webpack 的 resolve 要求模块真实存在（内容由 loader 覆盖）
// 对比：Rollup / Vite 的虚拟模块不需要这个文件
export const BUILD_INFO = {}
```

### Vite 版

> 摘自 `./code/build-lab/plugin-lab/three-ways.mjs`（运行：`npm run plugin`）

```js
function vitePlugin() {
    return {
        name: 'build-info-vite',
        // enforce: 'pre' —— 抢在 Vite 内置解析之前处理，否则虚拟 id 会被当成普通依赖
        enforce: 'pre',
        resolveId(source) {
            if (source === VIRTUAL) return RESOLVED
            return null
        },
        load(id) {
            if (id === RESOLVED) return `export const BUILD_INFO = ${INFO};`
            return null
        }
    }
}
```

三套都跑通了：

```
---- 1. Rollup ----
  产物含 BUILD_INFO: true
  产物片段: const BUILD_INFO = {"builtAt":"2026-09-19T03:41:19.938Z","env":"plugin-lab"}; fu

---- 2. webpack ----
  [virtual-loader] options.info = {"builtAt":"2026-09-19T03:41:19.938Z","env":"plugin-lab"}
  [virtual-loader] options.info = {"builtAt":"2026-09-19T03:41:19.938Z","env":"plugin-lab"}
  产物含 BUILD_INFO: true
  产物片段: tual-build-info.js const BUILD_INFO = {"builtAt":"2026-09-19T03:41:19.938Z","env":"plugin-lab"}; ;//

---- 3. Vite（build 侧）----
  产物含 BUILD_INFO: true
  产物片段: virtual-build-info var BUILD_INFO = { "builtAt": "2026-09-19T03:41:19.938Z", "env": "plugin-lab" }
```

顺带观察：三个产物的格式略有差异（Vite 那行是格式化后的 JSON），但内容一致——这正是"同一件事不同实现"的直观体现。

## 四、unplugin：写一次，跑三处

如果插件不依赖某个工具的独有钩子，可以用 unplugin 只写一份：

> 摘自 `./code/build-lab/plugin-lab/unplugin-demo.mjs`（运行：`npm run plugin:unplugin`）

```js
// 只写一次：resolveId + load，unplugin 负责翻译成各打包器的钩子
// 注意：createUnplugin 返回的不是工厂函数，适配器才是入口 —— unplugin.rollup(options)
const unplugin = createUnplugin((options = {}) => {
    const info = JSON.stringify({ builtAt: new Date().toISOString(), env: options.env || 'dev' })
    return {
        name: 'build-info-unplugin',
        resolveId(id) {
            if (id === VIRTUAL) return RESOLVED
            return null
        },
        load(id) {
            if (id === RESOLVED) return `export const BUILD_INFO = ${info};`
            return null
        },
        transform(code) {
            if (!code.includes('__PLUGIN_MARK__')) return null
            return code.replace(/__PLUGIN_MARK__/g, 'marked by unplugin')
        }
    }
})
```

调用时取对应适配器：

```
---- 1. 同一份实现 → Rollup ----
  含 BUILD_INFO: true | const BUILD_INFO = {"builtAt":"2026-09-19T03:41:28.106Z","env":"unplugin-demo"};

---- 2. 同一份实现 → Vite ----
  含 BUILD_INFO: true | ild-info var BUILD_INFO = { "builtAt": "2026-09-19T03:41:28.151Z", "env": "unplugin-demo

---- 3. 同一份实现 → webpack ----
  含 BUILD_INFO: true | t */ }); const BUILD_INFO = {"builtAt":"2026-09-19T03:41:31.543Z","env":"unplugin-demo"};

---- 结论 ----
unplugin 把 resolveId / load / transform 翻译成各打包器的原生钩子
代价：只能用它抽象的那一层，deep 定制（webpack 内部工厂钩子、Vite 的 configureServer）仍要写原生插件
```

一个容易踩的 API 细节：**`createUnplugin(...)` 返回的不是工厂函数**，正确用法是 `unplugin.rollup(options)` / `unplugin.vite(options)` / `unplugin.webpack(options)`。写成 `unplugin(options).rollup()` 会报 `is not a function`。

## 五、六个实测踩到的坑

### 坑 1：虚拟模块 id 别用冒号

最初写成 `virtual:build-info`，Rollup 和 Vite 都正常，webpack 直接报错：

```
UnhandledSchemeError: Reading from "virtual:build-info" is not handled by plugins (Unhandled scheme).
Webpack supports "data:" and "file:" URIs by default.
```

webpack 把 `xxx:` 当成 URI scheme。改用 `virtual-build-info` 或 `~build-info` 即可。

### 坑 2：未被引用的导出，内容会被摇掉

第一版验证时三套里两套"失败"——不是插件没生效，是**入口只 export 了函数、没人调用**，打包器把整个导出连同它引用的常量一起删了。给入口加一处真实使用（`console.log`）后立刻恢复正常。

判断插件是否生效时，别用"产物里有没有这段内容"做唯一依据，先确认这段内容没有被优化掉。

### 坑 3：Vite 插件要抢在内置解析之前

虚拟 id 必须加 `enforce: 'pre'`，否则 Vite 自己的解析插件先把它当成普通依赖处理。

### 坑 4：改了代码就要还 sourcemap

`transform` 返回字符串等于声明"没有 sourcemap"，调试时行号会错位。正确做法是返回 `{ code, map }`，并让改动保持行号不变（用 magic-string 而不是字符串拼接）。

### 坑 5：分清楚 dev 和 build

Vite 的 `configureServer`、`handleHotUpdate` 只在 dev 跑；`generateBundle` 只在 build 跑。写在通用钩子里的 dev 逻辑会在 build 时执行（反之亦然），这是"本地好好的、构建报错"的常见来源。

用 `configResolved` 里的 `config.command` 判断阶段：

> 摘自 `./code/build-lab/vite-lab/counter-plugin.mjs`（运行：`npm run vite`）

```js
        configResolved(config) {
            command = config.command // serve | build
        },
```

### 坑 6：webpack 插件改配置要趁早

在 `apply` 里 `compiler.options.module.rules.push(...)` 这种改配置的写法，依赖 webpack 尚未固化 ruleSet。更稳的做法是让规则出现在配置文件里，插件只负责改写请求（本仓脚本就是这么做的）。

## 六、四类高频插件与写法要点

| 类型 | 核心钩子 | 要点 |
| ---- | ---- | ---- |
| 虚拟模块 | `resolveId` + `load` | id 加 `\0`（webpack 侧要占位文件 + loader） |
| 注入常量 | `transform` 或 `define` | 优先用工具自带的 `define` / `DefinePlugin`，别自己拼字符串 |
| 产物处理 | `generateBundle` / `processAssets` | 用 `emitFile` / `emitAsset` 产出，不要直接 `fs.writeFileSync` |
| dev 增强 | `configureServer` | 加中间件、自定义 HMR；注意只在 dev 生效 |

一句话经验：**能配置解决的不要写插件，能用 `transform` 解决的不要碰 `resolveId`**。插件越靠近底层，越容易在工具升级时碎掉。

## 小结

- 构建插件开发
  - 扩展点只有三类
    - 解析（resolveId/load）· 转换（transform/loader）· 产物（generateBundle/emitAsset）
  - 三套钩子的差异根源
    - Rollup/Vite：声明式"回答 id 与内容"
    - webpack：模块必须真实存在，内容由 loader 加工
  - 同一需求三套实现
    - 实测三套产物都含 BUILD_INFO
    - webpack 需要占位文件 + loader；Vite 需要 `enforce: 'pre'`
  - unplugin
    - 一份实现跑 Rollup / Vite / webpack（实测三者均成功）
    - API 细节：`unplugin.rollup(options)`，不是 `unplugin(options).rollup()`
    - 代价：只能用它抽象的那层，deep 定制仍要原生插件
  - 六个坑
    - 虚拟 id 别用冒号（webpack 报 Unhandled scheme）
    - 未被引用的导出会被摇掉，误判插件失效
    - Vite 虚拟模块要 `enforce: 'pre'`
    - transform 要还 sourcemap，用 magic-string 保行号
    - 分清 dev / build 阶段，用 `config.command` 判断
    - webpack 插件改配置要趁早，规则放配置文件更稳
  - 经验
    - 能配置不写插件；能用 transform 不碰 resolveId
