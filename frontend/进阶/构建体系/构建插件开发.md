# 构建插件开发

会写构建插件，是"会用构建工具"和"能改造构建流程"的分界线。难点不在语法——三套工具的对象形状都很简单——而在于**同一件事在三个工具里的抽象层级完全不同**：Rollup/Vite 给你"回答 id 和内容"的声明式钩子，webpack 把你放进它的内部工厂。

本篇不拿"虚拟模块"当主案例（它是手段不是需求），而是用**两个生产里真会写的插件**讲差异：组件库按需引入（一次编写、三处运行）与禁用 API 门禁（把团队约定变成构建期报错）。最后列出实测踩到的坑。

## 一、插件能扩展什么

不管哪个工具，插件的扩展点只有三类：

```
1. 解析（这个 import 指向谁？内容从哪来？）  → resolveId / load / resolver 钩子
2. 转换（内容要不要改？）                    → transform / loader
3. 产物（最后再加工一下）                    → generateBundle / processAssets / emit
```

绝大多数插件只用到其中一类。判断"该挂哪个钩子"的方法很简单：**先问这个能力发生在构建的哪一步**。

## 二、三套钩子对照

| 能力 | Rollup | Vite | webpack |
| ---- | ---- | ---- | ---- |
| 解析 id | `resolveId` | `resolveId`（可加 `enforce`） | `normalModuleFactory.beforeResolve` / `resolve.plugins` |
| 提供内容 | `load` | `load` | loader（且要求文件真实存在） |
| 转换代码 | `transform` | `transform` | loader |
| 产出文件 | `generateBundle` + `emitFile` | 同 Rollup | `compilation.emitAsset` |
| 仅 dev | 无 | `configureServer` / `handleHotUpdate` | `compiler.hooks.watchRun` / devMiddleware |
| 收尾 | `buildEnd` / `writeBundle` | 同 Rollup | `compiler.hooks.done` |

差异的根源：**Rollup/Vite 是"我告诉你 id，你给我内容"的契约；webpack 是"模块必须真实存在，内容由 loader 加工"的模型**。所以 webpack 的虚拟模块要绕一层。

## 三、真实场景一：组件库按需引入

需求来自一个真实的浪费：业务只用了组件库里的一个 `Button`，产物里却躺着整包。先看样本——组件库每个模块顶层都有一句注册副作用（真实组件库的全局注册就是这样），所以只要进了图就摇不掉：

> 摘自 `./code/build-lab/plugin-lab/ui-lib/es/button.js`（运行：`npm run plugin:ondemand`）

```js
// 顶层副作用：模块一进图就会执行（真实组件库的全局注册就是这样）
console.log('button 被注册')

export default function Button(props) {
    return { tag: 'button', ...props }
}
```

> 摘自 `./code/build-lab/plugin-lab/ui-lib/index.js`（运行：`npm run plugin:ondemand`）

```js
// 组件库的"总入口"：一次 re-export 所有组件
// 每个组件模块顶层都有一句注册副作用 —— 所以只要进了图就摇不掉
export { default as Button } from './es/button.js'
export { default as Table } from './es/table.js'
export { default as Form } from './es/form.js'
```

业务代码只 import 了一个组件：

> 摘自 `./code/build-lab/plugin-lab/src-ondemand/main.js`（运行：`npm run plugin:ondemand`）

```js
// 业务只用了 Button 一个组件
import { Button } from 'ui-lib'

console.log(Button({ text: '提交' }))
```

插件要做的，是把具名导入改写成深路径导入，并补上样式文件的副作用导入。用 unplugin 写一次，三个打包器各取适配器：

> 摘自 `./code/build-lab/plugin-lab/import-on-demand.mjs`（运行：`npm run plugin:ondemand`）

```js
const unplugin = createUnplugin(({ libraryName = 'ui-lib', style = true } = {}) => {
    return {
        name: 'import-on-demand',
        transform(code, id) {
            if (!id.endsWith('.js') || !code.includes(libraryName)) return null
            const ast = parse(code, { sourceType: 'module' })
            const s = new MagicString(code)
            let changed = false

            for (const node of ast.program.body) {
                if (node.type !== 'ImportDeclaration') continue
                if (node.source.value !== libraryName) continue
                const specs = node.specifiers.filter((sp) => sp.type === 'ImportSpecifier')
                if (!specs.length) continue

                const lines = []
                for (const sp of specs) {
                    const name = sp.imported.name // Button
                    const dir = name.toLowerCase() // button
                    lines.push(`import ${sp.local.name} from '${libraryName}/es/${dir}.js'`)
                    if (style) lines.push(`import '${libraryName}/es/${dir}/style.css'`)
                }
                s.overwrite(node.start, node.end, lines.join('\n'))
                changed = true
            }

            if (!changed) return null
            // 用 magic-string 而不是字符串 replace：它顺带把 sourcemap 算好了
            return { code: s.toString(), map: s.generateMap({ hires: true }) }
        }
    }
})
```

裸导入与样式的解析交给一个辅助插件（真实项目里这是 node-resolve 与 css 插件的活）：

> 摘自 `./code/build-lab/plugin-lab/import-on-demand.mjs`（运行：`npm run plugin:ondemand`）

```js
const resolver = {
    name: 'ui-lib-resolver',
    resolveId(source) {
        if (source === 'ui-lib') return path.join(LIB, 'index.js')
        if (source.startsWith('ui-lib/')) return path.join(LIB, source.slice('ui-lib/'.length))
        return null
    },
    load(id) {
        // 本实验不关心样式内容：真实项目由 css 插件接管，这里给个空模块
        if (id.endsWith('.css')) return 'export default ""'
        return null
    }
}
```

同一份源码，加不加插件的差别：

```
---- ① 不用插件：import { Button } from "ui-lib" ----
  Rollup（无插件）        button:true  table:true  form:true    242 字符

---- ② 加了按需插件（同一份源码）----
  Rollup             button:true  table:false form:false   222 字符 · sourcemap mappings 194 字符
  Vite               button:true  table:false form:false   242 字符
  webpack            button:true  table:false form:false   463 字符

---- 结论 ----
  组件库每个模块顶层都有注册副作用，所以"整包引入"会把三个组件全打进来
  按需插件把具名导入改写成深路径 + 样式副作用导入，只引真正用到的那个
  改写必须用 magic-string：字符串 replace 会让 sourcemap 错位，报错定位到行号就不可信了
  同一份实现跑三个打包器：差异只在 unplugin.rollup / .vite / .webpack 这一行
```

四个要点：

1. **需求决定钩子**：这是"改代码"，所以只用 `transform`，不碰 `resolveId`。**能用 `transform` 解决的不要碰 `resolveId`**——越靠近底层越容易在工具升级时碎掉。
2. **必须补样式副作用导入**：按需引入组件却不引样式，是最常见的事故（组件能跑但没样式）。这也是为什么改写后是"深路径 + `style.css`"两条。
3. **magic-string 不是可选优化**：改写了代码却不给 `map`，产物行号与源码对不上，线上报错定位直接失效。
4. **unplugin 的 API 细节**：`createUnplugin(...)` 返回的不是工厂函数，正确用法是 `unplugin.rollup(options)`；写成 `unplugin(options).rollup()` 会报 `is not a function`。代价是只能用它抽象的那一层，webpack 内部工厂钩子、Vite 的 `configureServer` 这类深层定制仍要写原生插件。

### 三·一、顺带：虚拟模块在三家的差异

"虚拟模块"（`resolveId` 返回一个磁盘上不存在的 id，再由 `load` 提供内容）是**手段**，不是需求；它服务的真实需求是"构建期注入版本信息、git 分支、特性开关"。

| 工具 | 怎么做 | 注意 |
| ---- | ---- | ---- |
| Rollup | `resolveId` + `load`，id 用 `\0` 前缀 | 不处理就返回 `null` |
| Vite | 同 Rollup，但要 `enforce: 'pre'` | 否则虚拟 id 会被内置解析当成普通依赖 |
| webpack | 模块必须真实存在：用 `normalModuleFactory.beforeResolve` 改写请求，再配 loader 喂内容 | id 别用冒号，见坑 1 |

对应脚本 `plugin-lab/three-ways.mjs`（三套各写一遍）与 `plugin-lab/unplugin-demo.mjs`（unplugin 写一次）。

## 四、真实场景二：禁用 API 门禁

第二个需求同样常见：团队约定"不许直连 `localStorage`"、"`console.log` 不许进生产"，靠 CR 人肉盯必漏。把它做成构建期检查：命中就报文件行列，`fail` 一开就直接中断。

规则写成数据，遍历逻辑不动：

> 摘自 `./code/build-lab/plugin-lab/ban-api.mjs`（运行：`npm run plugin:ban`）

```js
const RULES = [
    {
        id: 'no-direct-storage',
        test: (callee) => callee.object?.name === 'localStorage',
        msg: '禁止直连 localStorage：请用统一的 storage 封装（它有容量兜底与隐私模式降级）'
    },
    {
        id: 'no-console',
        test: (callee) => callee.object?.name === 'console' && callee.property?.name === 'log',
        msg: '生产构建不允许 console.log：请用 logger（线上可关）'
    }
]
```

用 AST 而不是正则——正则扫得到关键字，扫不到"这是调用还是字符串字面量"：

> 摘自 `./code/build-lab/plugin-lab/ban-api.mjs`（运行：`npm run plugin:ban`）

```js
            traverse(ast, {
                CallExpression(p) {
                    const callee = p.node.callee
                    if (callee.type !== 'MemberExpression') return
                    for (const rule of rules) {
                        if (!rule.test(callee)) continue
                        hits.push({
                            rule: rule.id,
                            line: p.node.loc.start.line,
                            column: p.node.loc.start.column,
                            msg: rule.msg
                        })
                    }
                }
            })

            // 先记账再报错：this.error 会直接抛出，写在它后面的代码不会执行
            sink.push(...hits.map((h) => ({ ...h, file: rel(id) })))
            for (const h of hits) {
                const at = `${rel(id)}:${h.line}:${h.column}`
                // this.warn 只提示、this.error 直接中断：同一个插件换个开关就是"报告"或"门禁"
                if (fail) this.error(`[${h.rule}] ${at} ${h.msg}`)
                this.warn(`[${h.rule}] ${at} ${h.msg}`)
            }
            return null
```

样本里两处违规（一处直连存储、一处 console）：

> 摘自 `./code/build-lab/plugin-lab/src-ban/cart.js`（运行：`npm run plugin:ban`）

```js
export function saveCart(items) {
    localStorage.setItem('cart', JSON.stringify(items))
    return items
}
```

> 摘自 `./code/build-lab/plugin-lab/src-ban/order.js`（运行：`npm run plugin:ban`）

```js
export function submit(order) {
    console.log('submit', order)
    return fetch('/api/order', { method: 'POST', body: JSON.stringify(order) })
}
```

同一个插件，开关不同：

```
---- ① 只警告（fail: false） ----
  构建通过
  命中 2 处（警告 2 条）：
    src-ban/cart.js:2:4  [no-direct-storage] 禁止直连 localStorage：请用统一的 storage 封装（它有容量兜底与隐私模式降级）
    src-ban/order.js:2:4  [no-console] 生产构建不允许 console.log：请用 logger（线上可关）

---- ② 当门禁（fail: true） ----
  构建被中断： [plugin ban-api] plugin-lab/src-ban/order.js: [no-console] src-ban/order.js:2:4 生产构建不允许 console.log：请用 logger（线上可关）
  命中 1 处（警告 0 条）：
    src-ban/order.js:2:4  [no-console] 生产构建不允许 console.log：请用 logger（线上可关）

---- 结论 ----
  正则能扫到关键字，但扫不到"这是调用还是字符串" —— 所以要用 AST 判 CallExpression
  this.error 中断的是构建，报错里带 [plugin] 前缀与文件行列，直接贴到工单里就能定位
  规则写成数据后，新增一条禁用项只加一个对象，不用改遍历逻辑
  这份实现是 Rollup 原生写法；要走 Vite / webpack，用 unplugin 包一层即可（见 import-on-demand.mjs）
  error 会立刻中断：门禁模式只报出第一处（order.js），后面的 cart.js 根本没被处理
  想一次报全，就把命中攒到数组里，等 buildEnd 再 this.error 一次
```

"门禁模式只报 1 处"不是 bug 而是 `this.error` 的语义：它抛出的那一刻构建就停了，后面的模块不会被处理。想一次报全所有违规，正确做法是 transform 里只收集、`buildEnd` 里统一 `this.error`。

## 五、七个实测踩到的坑

### 坑 1：虚拟模块 id 别用冒号

最初写成 `virtual:build-info`，Rollup 和 Vite 都正常，webpack 直接报错：

```
UnhandledSchemeError: Reading from "virtual:build-info" is not handled by plugins (Unhandled scheme).
Webpack supports "data:" and "file:" URIs by default.
```

webpack 把 `xxx:` 当成 URI scheme。改用 `virtual-build-info` 或 `~build-info` 即可。

### 坑 2：未被引用的导出，内容会被摇掉

第一版验证时三套里两套"失败"——不是插件没生效，是**入口只 export 了函数、没人调用**，打包器把整个导出连同它引用的常量一起删了。给入口加一处真实使用（`console.log`）后立刻恢复正常。

判断插件是否生效时，别用"产物里有没有这段内容"做唯一依据，先确认这段内容没有被优化掉。

### 坑 3：Vite 插件要抢在内置解析之前

虚拟 id 必须加 `enforce: 'pre'`，否则 Vite 自己的解析插件先把它当成普通依赖处理。

### 坑 4：改了代码就要还 sourcemap

`transform` 返回字符串等于声明"没有 sourcemap"，调试时行号会错位。正确做法是返回 `{ code, map }`，并让改动保持行号不变（用 magic-string 而不是字符串拼接）。

### 坑 5：分清楚 dev 和 build

Vite 的 `configureServer`、`handleHotUpdate` 只在 dev 跑；`generateBundle` 只在 build 跑。写在通用钩子里的 dev 逻辑会在 build 时执行（反之亦然），这是"本地好好的、构建报错"的常见来源。

用 `configResolved` 里的 `config.command` 判断阶段：

> 摘自 `./code/build-lab/vite-lab/counter-plugin.mjs`（运行：`npm run vite`）

```js
        configResolved(config) {
            command = config.command // serve | build
        },
```

### 坑 6：webpack 插件改配置要趁早

在 `apply` 里 `compiler.options.module.rules.push(...)` 这种改配置的写法，依赖 webpack 尚未固化 ruleSet。更稳的做法是让规则出现在配置文件里，插件只负责改写请求（本仓脚本就是这么做的）。

### 坑 7：`.mjs` 里 require CJS 包要绕一层

插件脚本常用 `.mjs`（跟着 Vite 生态），但像 `@babel/traverse` 这种老包是 CJS：直接 `require` 会报 `require is not defined in ES module scope`，直接 `import` 拿到的又不是函数（`traverse is not a function`）。

> 摘自 `./code/build-lab/plugin-lab/ban-api.mjs`（运行：`npm run plugin:ban`）

```js
// @babel/traverse 是 CJS，ESM 里拿 default 要走 createRequire
const traverse = createRequire(import.meta.url)('@babel/traverse').default
```

## 六、五类高频插件与写法要点

| 类型 | 核心钩子 | 要点 |
| ---- | ---- | ---- |
| 虚拟模块 | `resolveId` + `load` | id 加 `\0`（webpack 侧要占位文件 + loader） |
| 注入常量 | `transform` 或 `define` | 优先用工具自带的 `define` / `DefinePlugin`，别自己拼字符串 |
| 按需改写 | `transform` + magic-string | 改写同时补上副作用导入（如样式）；必须给 `map` |
| 规范门禁 | `transform` + AST | 用 AST 而不是正则；`warn` 报告、`error` 门禁；想报全就攒到 `buildEnd` |
| 产物处理 | `generateBundle` / `processAssets` | 用 `emitFile` / `emitAsset` 产出，不要直接 `fs.writeFileSync` |

一句话经验：**能配置解决的不要写插件，能用 `transform` 解决的不要碰 `resolveId`**。插件越靠近底层，越容易在工具升级时碎掉。

## 小结

- 构建插件开发
  - 扩展点只有三类
    - 解析（resolveId/load）· 转换（transform/loader）· 产物（generateBundle/emitAsset）
  - 三套钩子的差异根源
    - Rollup/Vite：声明式"回答 id 与内容"
    - webpack：模块必须真实存在，内容由 loader 加工
  - 真实场景一：组件库按需引入
    - 实测：无插件三个组件全进产物；插件后只剩 button（222/242/463 字符）
    - 具名导入 → 深路径 + 样式副作用导入；用 magic-string 保 sourcemap
    - unplugin 一次编写三处运行：差异只在 `unplugin.rollup/.vite/.webpack`
  - 真实场景二：禁用 API 门禁
    - 规则写成数据；用 AST 判 CallExpression 而不是正则
    - 实测：warn 模式命中 2 处并构建通过；error 模式中断且只报第一处
    - 想一次报全就攒到 `buildEnd` 再 `this.error`
  - 七个坑
    - 虚拟 id 别用冒号 · 未被引用的导出会被摇掉 · Vite 要 `enforce:'pre'`
    - 改代码要还 sourcemap · 分清 dev/build · webpack 改配置要趁早 · `.mjs` 里 require CJS 要 createRequire
  - 五类高频插件
    - 虚拟模块 / 注入常量 / 按需改写 / 规范门禁 / 产物处理
