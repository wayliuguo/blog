# 产物分析与体积优化

## 一、先看清产物里有什么，再谈优化

体积优化最容易犯的错是"凭感觉删依赖"。`lodash` 看着大就换 `lodash-es`，`moment` 看着大就换 `dayjs`——但你可能根本没把整个 `moment` 打进产物。

正确的顺序是三步：**看清产物 → 定位大头 → 选手段**。第一步的产物数据有三个来源：

| 来源 | 拿到什么 | 适用 |
| ---- | ---- | ---- |
| 构建器的元数据（esbuild `metafile`、webpack `stats`、Rollup `output`） | 每个输入模块在产物里占多少字节 | 命令行、CI 里做门槛 |
| 可视化工具（`webpack-bundle-analyzer`、`rollup-plugin-visualizer`） | treemap 图，一眼看到谁最大 | 人工排查 |
| 产物本身的文本 | 某个函数/字符串到底在不在里面 | 验证 tree-shaking 是否真的生效 |

第三项常被忽略，但它最直接：想知道 `util19` 有没有被打进去，读产物搜一下就知道。

> 摘自 `./code/build-lab/analyze-lab/optimize.cjs`（运行：`npm run analyze`）

```js
console.log('\n---- 关键判断 ----')
console.log('  A 全量引入是否把 20 个函数都打进去了：', rows[0].code.includes('util19'))
console.log('  B 按需引入后 util19 还在吗：', rows[1].code.includes('util19'))
console.log('  C 带副作用模块的 window 赋值还在吗：', rows[2].code.includes('__ANALYZE_MARK__'))
console.log('  D 首屏产物里含 util 吗（应该在点击后才加载）：', splitFirstScreen.includes('function util0'))
```

实测输出：

```
---- 关键判断 ----
  A 全量引入是否把 20 个函数都打进去了： true
  B 按需引入后 util19 还在吗： false
  C 带副作用模块的 window 赋值还在吗： true
  D 首屏产物里含 util 吗（应该在点击后才加载）： false
```

这四行是本篇的主线：A/B 说明引用方式决定 tree-shaking，C 说明副作用会保住整块代码，D 说明加载时机能把代码挪出首屏。

## 二、体积的四类来源

拿到产物清单后，大头通常落在四类之一。它们的优化手段完全不同，先分清是哪种：

1. **业务代码**：自己写的。靠 tree-shaking 与代码分割，改引用方式与加载时机。
2. **第三方依赖**：`node_modules` 里的。靠换更轻的依赖、按需引入、去重（同一包的多个版本）。
3. **重复打包**：同一个包被两个入口或两份依赖引入，产出了两份副本。靠 `dedupe`、分包、external。
4. **没被压缩的"形态"**：未压缩、把 ES5 语法和 polyfill 一起打进去。靠压缩与现代语法产物。

判断方法：看产物清单里 `node_modules` 路径的占比。占比高就先查依赖，占比低就别在依赖上浪费时间。

## 三、四条手段的实测对照

实验设计：一个 20 个函数的工具模块，四种打包姿势，其余条件完全一致（未压缩、`format: 'esm'`、`target: 'es2020'`）。

> 摘自 `./code/build-lab/analyze-lab/optimize.cjs`（运行：`npm run analyze`）

```js
const cases = [
    {
        // 把 namespace 整体再导出：打包器无法判断外部会用到哪个成员，只能全留
        name: 'A. 全量引入（namespace 再导出）',
        entry: 'case-a.js',
        code: "import * as utils from './utils.js'\nexport { utils }\nconsole.log(utils.util0(1))\n"
    },
    {
        name: 'B. 按需引入（具名 import）',
        entry: 'case-b.js',
        code: "import { util0 } from './utils.js'\nconsole.log(util0(1))\n"
    },
    {
        name: 'C. 用了带副作用的模块',
        entry: 'case-c.js',
        code: "import { util0 } from './utils.js'\nimport { flag } from './side-effect.js'\nconsole.log(util0(1), flag)\n"
    },
    {
        name: 'D. 动态 import 拆分（首屏只留入口）',
        entry: 'case-d.js',
        code: "console.log('first screen')\ndocument.addEventListener('click', () => {\n  import('./utils.js').then((m) => console.log(m.util0(1)))\n})\n"
    }
]
```

实测输出：

```
---- 未压缩产物体积（字节）----
  A. 全量引入（namespace 再导出）               2509  ██████████████████████████████
  B. 按需引入（具名 import）                    165  ██
  C. 用了带副作用的模块                          269  ███
  D. 动态 import 拆分（首屏只留入口）              2946  ███████████████████████████████████
```

**A vs B：2509 → 165 字节，差 15 倍**，改的只是一行 import 的写法。这不是 esbuild 特有能力，webpack 与 Rollup 同样如此。

关键在于 `* as utils` 之后又 `export { utils }`——打包器无法证明外部不会访问 `utils.util19`，只能全留。如果这个 namespace 只在模块内部用、不被再导出，多数打包器仍能摇掉未用成员；**被再导出是 tree-shaking 的失效点**。

**C：269 字节**。看上去只比 B 多 100 字节，但那是因为它引入的 `side-effect.js` 本身就小。重点不是体积，是关键判断那一行——`window.__ANALYZE_MARK__` 被保留了。带顶层副作用的模块，打包器不敢删它的任何顶层语句。

> 摘自 `./code/build-lab/analyze-lab/optimize.cjs`（运行：`npm run analyze`）

```js
require('node:fs').writeFileSync(
    path.join(ROOT, 'src', 'side-effect.js'),
    "// 顶层副作用：有没有 sideEffects 声明，决定它会不会被整块保留\nwindow.__ANALYZE_MARK__ = true\nexport const flag = 'with-side-effect'\n"
)
```

实验里给它加了一份 `sideEffects` 声明做对照：

> 摘自 `./code/build-lab/analyze-lab/optimize.cjs`（运行：`npm run analyze`）

```js
// 给 C 场景加一份 sideEffects 声明，做组内对照
require('node:fs').writeFileSync(
    path.join(ROOT, 'src', 'package.json'),
    JSON.stringify({ sideEffects: ['./side-effect.js'] }, null, 2)
)
```

`sideEffects` 是**给打包器的承诺**：数组外的文件可以视为无副作用、整块删除。注意方向——这里是把它列进数组（声明"它有副作用，别删"），所以 `window` 赋值被保留；反过来写 `sideEffects: false` 才是"整个包都无副作用"。

## 四、代码分割：改的是加载时机

D 场景在 `splitting: false` 下是 2946 字节（因为打包器把 `utils.js` 内联进来了）。开启分割后：

> 摘自 `./code/build-lab/analyze-lab/optimize.cjs`（运行：`npm run analyze`）

```js
const splitOut = path.join(OUT, 'split')
esbuild.buildSync({
    entryPoints: [path.join(ROOT, 'src', 'case-d.js')],
    bundle: true,
    outdir: splitOut,
    format: 'esm',
    target: 'es2020',
    splitting: true
})
```

实测输出：

```
---- D 场景：开启代码分割后的产物清单 ----
  utils-L57ZOEVP.js                1939 字节
  case-d.js                         175 字节
  首屏只需要加载入口那个文件，其余按需下载
```

总字节没变少（反而多了 chunk 的胶水代码），但**首屏从 2946 降到 175 字节**。这就是代码分割的真实收益：它不是"减小体积"，是"改变体积的分布"。

分割粒度怎么定：

- **按路由拆**：最稳。每个路由一个 chunk，命中率高、缓存友好。
- **按交互拆**：如弹窗、编辑器、图表这类点击后才用的重型组件，用 `import()` 包住。
- **按依赖拆**（SplitChunks / `manualChunks`）：把 `node_modules` 抽成 `vendor`。收益来自缓存——业务代码频繁改动时 `vendor` 的 hash 不变。

别过度拆：HTTP/2 下并发不再是瓶颈，但每个 chunk 仍有独立的请求开销与胶水代码。几十字节的 chunk 是负收益。

## 五、压缩与现代语法产物

前三条手段都只影响部分代码，压缩是唯一对所有代码生效的一条。

> 摘自 `./code/build-lab/analyze-lab/optimize.cjs`（运行：`npm run analyze`）

```js
console.log('\n---- 压缩后的效果（取 A 与 B）----')
for (const idx of [0, 1]) {
    const res = build(cases[idx].entry, { minify: true })
    const meta = Object.values(res.metafile.outputs)[0]
    console.log(`  ${cases[idx].name}: ${rows[idx].bytes} → ${meta.bytes} 字节（${(meta.bytes / rows[idx].bytes).toFixed(2)}）`)
}
```

实测输出：

```
---- 压缩后的效果（取 A 与 B）----
  A. 全量引入（namespace 再导出）: 2509 → 1714 字节（0.68）
  B. 按需引入（具名 import）: 165 → 84 字节（0.51）
```

两点值得注意：

1. **压缩不能替代 tree-shaking**。A 压缩后 1714 字节，仍是 B 压缩后 84 字节的 20 倍。压缩只是把已经在那里的代码写得更短。
2. **压缩后的数字才接近传输体积**，但还不等于——真实传输还要过 gzip/brotli。做体积门槛时看压缩后（或压缩 + gzip 后）的值，不要看未压缩产物。

现代语法产物的收益来自"少做降级"：箭头函数、`async/await`、可选链不用转成 ES5 的等价实现，polyfill 也不用打进去。做法是为现代浏览器与旧浏览器各出一份（如 Vite 的 `build.target` 配合 `<script type="module">` / `nomodule`），而不是统一降级到最低版本。

## 六、容易踩的四个误区

- **"我把库换成按需引入了，为什么体积没变"**：先确认那个库本身支持 tree-shaking（是 ESM 产物、且没声明 `sideEffects: false` 却仍有副作用）。CommonJS 产物无法被静态分析，换了写法也没用。
- **"拆了包怎么反而变大了"**：正常。分割加的是胶水代码与 chunk 边界；看首屏体积，不看总体积。
- **"压缩后体积达标了"**：压缩后还要过 gzip/brotli。CI 门槛用哪一口径，全团队要统一。
- **"vendor 抽出来就一定快"**：只有当 vendor 的文件名 hash 长期不变时才赚到缓存收益。依赖一升级就整体重打，抽 vendor 只是把缓存失效集中化了。
