## 1. 构建全景与选型

### 1.1 构建在做什么与为什么非构建不可

构建 = 把「开发者写的模块」翻译成「浏览器能高效加载的产物」，四步：

```
解析建图 → 转换 → 拼装 → 优化输出
  递归依赖图    语法降级/资源编译  合成少数文件  摇树/压缩/hash 命名
```

**为什么非构建不可**：

```
模块数量   上千个模块 → 上千个请求，必须合并成几个文件
语法降级   新语法（TS/JSX/新特性）浏览器跑不起来
非 JS 资源 TS / CSS / 图片不能被浏览器直接执行
体积优化   没有压缩与 tree-shaking，首屏慢
```

- **开发环境可以少做，生产必须全做**——开发态能跳过拼装与压缩（Vite 就是这么做的）。

### 1.2 三代工具与开发态 / 生产态

```
第一代  任务流（Grunt/Gulp）    不解析依赖，只做文件级加工
第二代  打包器（webpack/Rollup） 建完整依赖图，开发时也要全量拼装
第三代  原生 ESM + 原生语言（Vite/esbuild）  把打包从开发态挪走
```

- 第三代不是「打包被淘汰」——生产依然要打包，只是**开发时不再为它付费**：浏览器原生 ESM 自己加载模块，开发时不拼装，加上 Go/Rust 写的转译器把单文件转换压到毫秒级。
- Vite 生产构建 8.x 起走 **Rolldown**（兼容 rollupOptions），不是 Rollup。

### 1.3 tree-shaking 的真相与实测对比

**tree-shaking 分两步：标记 + 删除**：

```
webpack   标记（usedExports）→ 删除交给压缩器（minimize）
Rollup    一步完成（解析期就能删）
```

- 只声明 `sideEffects: false` **不删代码**，必须同时开 `minimize`。
- 评估体积**必须开压缩看**；检测未使用代码要**搜字符串常量**。

**实测对比（200 模块）**：

```
esbuild 557ms / rollup 1303ms / webpack 3698ms
进程总耗时比构建耗时多约 400ms（Node 启动固定成本）
```

- 两个贯穿全模块的判断：**构建速度的差距，主要来自「开发态要不要拼装」；产物体积的差距，主要来自「引用方式与副作用」，而不是压缩**——03~06 篇的每一组数字都指向这两句。

### 1.4 选型与构建 / 架构接口

```
应用     → Vite / webpack（需 Module Federation 用 webpack）
库       → Rollup（或基于它的 Vite 库模式，不要用 webpack）
工具链   → esbuild / SWC / Rspack 等原生语言工具
```

- Vite 快的是**开发态**；生产构建 8.x 起走 Rolldown。
- **构建与架构的接口**：代码分割 / hash 策略 / 输出格式 / 多入口 / 运行时注入——这些决定产物能不能被浏览器与 CDN 高效利用。

## 2. 编译与 AST

### 2.1 编译器三件事与 AST 结构

编译器本质就三件事：

```
parse（文本→树）→ transform（改树）→ generate（树→文本）
```

- **AST 与源码是两份数据**，改树必须走 `generate`。
- AST 结构：顶层是 `Program`，语句在 `program.body`；节点 `type` 决定有哪些字段；**靠 astexplorer 查，不靠猜**。
- 朴素遍历只能「看」，增删改需要**路径（Path）**。

### 2.2 transform：visitor 与路径

- visitor 模式：按节点类型注册回调。
- 类型判断用 `t.isXxx`、构造用 `t.xxx()`、**容器操作传的是父节点字段名**（不是数组本身）。

### 2.3 写 Babel 插件

插件 = 返回 `{ name, visitor }` 的函数，`state.opts` 收参数。

两个坑：

```
坑一  替换后的节点会被重新遍历，可能递归
坑二  plugins 先于 presets 执行；plugins 按顺序、presets 逆序
```

### 2.4 codemod、工具选择与 AST 应用面

```
codemod   正则会误伤字符串与注释，AST 不会；generate 会重写格式
          → 先统一格式化基线再跑
工具选择  自定义转换用 Babel（插件需求）；只求快用 SWC / esbuild
类型检查  永远交给 tsc --noEmit——转译器不做类型检查
```

AST 的应用面：ESLint 规则 / 按需引入（改 import） / 埋点注入 / 死代码检测 / i18n 提取 / 依赖分析。

### 2.5 Babel API 全景：函数与产物对照

```
入口 A   @babel/core.transformSync(code, opts)    一步到位，内部依次跑完三步
           → { code, map, ast, metadata, sourceType, options }
入口 B   parser.parse → traverse → generate       想逐步控制就走这条
工具层   types（t.isXxx / t.xxx）· template       被 traverse 调用，不占主链
```

- **`transformSync` 不是第四个阶段**，它内部就是把 parse → traverse → generate 串起来跑一遍；两条入口是并行关系，不是上下游。
- **parse 的产物是 `File` 而不是 Program**，语句在 `File.program.body`；`tokens` 与 `range` 默认不存在，必须显式传 opts。
- **只读分析用 `types.traverseFast`**（不建 Path/Scope），要改树才用 `traverse`；改完必须 `generate` 才会变回文本。

## 3. Webpack 深入

### 3.1 五个对象与配置全览

五个对象的从属关系：

```
Compiler（进程级）→ Compilation（一次编译）→ Module → Chunk → Asset
```

- **模块数 ≠ 文件数**，中间隔着 Chunk 分组：一次 `compiler.run()` 产出一个 Compilation；Compilation 里装着所有 Module；Module 按规则分组成 Chunk；Chunk 渲染成 Asset 落盘。
- 配置只有五类：**入口 / 出口 / 转换 / 扩展 / 优化**；`mode` 是一组默认配置的开关，不是环境名。

### 3.2 loader 与 plugin

- **loader**：本质是「源码字符串 → 代码字符串」的函数；在 `module.rules` 声明、链式从右往左执行、结果会被缓存。
- **plugin**：有 `apply(compiler)` 的对象，靠钩子插手编译流程；产出文件用 `compilation.emitAsset`，不要 `fs.writeFileSync`（否则产物不进资产清单）；`processAssets` 带 `stage` 控制多个插件处理同一资产的顺序。

### 3.3 SplitChunks 与持久化缓存

**SplitChunks** 三个条件**同时满足**才抽：

```
minChunks  被引用次数
minSize    默认 20KB（最常见的"抽不出来"原因）
cacheGroups 匹配规则
```

- 实测同样代码：`minSize` 20KB 不抽，改成 0 就抽出 common chunk。
- 抽出来不一定更快：vendor 与路由级值得切，**小共享模块不值得**；抽 common 需多入口共享同一模块。

**持久化缓存**：

```
实测  小样本 1.11x、大样本 2.21x（按 webpack 自报时间）
坑    require('webpack') 本身要 2.8~3.3s，墙钟时间会淹没优化效果
    缓存目录要进 CI 缓存；遇到诡异问题先删缓存目录
```

- 持久化缓存**不是默认就该开**——先量再决定。

### 3.4 运行时代价与不该用 webpack 的场景

- 实测：业务 981 bytes / 运行时 6.37 KiB——`runtimeChunk: 'single'` 值得开，把运行时代码单独抽出，业务 chunk 的 hash 不再被运行时变动带崩。
- **库不该用 webpack 打包**（运行时对库是纯浪费）。
- 不该用 webpack 的场景：库用 Rollup、新应用用 Vite、纯转译用 esbuild、提速用 Rspack。

### 3.5 钩子全景与断点调试

一次构建实测 **237 次钩子触发 / 96 个不同钩子**（webpack 5.111.1），主干 11 段：

```
① 初始化 → ② 启动 → ③ 编译前 → ④ 建模块 → ⑤ 封装 → ⑥ 优化
→ ⑦ 编号 → ⑧ 代码生成 → ⑨ 哈希 → ⑩ 产物 → ⑪ 收尾
```

- **③ 之前**是注册 compilation 级钩子的最后时机；**⑤ 之后**不能再加模块；**⑩ 产物**是改 assets 的唯一安全窗口（早则产物未生成，晚则已写盘）。
- 能拿到什么随阶段变：`make` 0/0/0 → `finishMake` modules 6 → `afterChunks` chunks 3 → `runtimeModule` modules 7→14（运行时并入）→ `chunkAsset` assets 1→3 → `emit` assets 4。
- 谁在哪个钩子干活（实测 tap 名单）：`SplitChunksPlugin`→optimizeChunks、`mini-css-extract`→renderManifest/contentHash、`TerserPlugin`→processAssets(400)、`HtmlWebpackPlugin`→processAssets(700)、`CopyPlugin`→processAssets(-2000)、`CleanPlugin`→emit、`SizeLimitsPlugin`→afterEmit。
- **5.x 已废弃**：`additionalChunkAssets` / `optimizeChunkAssets` / `afterOptimizeChunkAssets` / `normalModuleLoader` → 统一改用 `processAssets` + `stage`。

**断点调试**：入口换成 Node API 脚本（本篇 `debug-entry.cjs`），别用 `npm run webpack`——Windows 下隔了一层 `npm.cmd`，`--inspect-brk` 传不到 node；`node --inspect-brk=9229` + `chrome://inspect` 可完全脱离 IDE。

```
坑  持久化缓存命中时 buildModule 系列直接不触发（实测首次 6 次 → 第二次 0 次）
    → 调试必须 cache: false，否则会误判成「这个钩子根本没执行」
    watch 模式进程不退出，调试一律用单次 run
    loader 按 cwd 解析，launch.json 的 cwd 指错会报找不到 loader
```

## 4. Vite

### 4.1 双引擎：dev 与 build

```
dev   esbuild 预构建 + 单文件转换，浏览器原生 ESM 加载，不打包
build 8.x 起默认 Rolldown（兼容 rollupOptions），全量打包
```

- 快在「不打包」——请求到哪个模块才转哪个模块，与项目规模无关；实测 dev 只转 1 个模块、build 转 3 个。
- HMR 同理：只重转变更模块 + WebSocket 通知，与项目规模无关；没有 `accept` 边界会向上冒泡，冒泡不到就整页刷新；`hotUpdate` 可接管（8.x 起，老的 `handleHotUpdate` 已不再触发）。

### 4.2 依赖预构建

解决两件事：**CJS → ESM** 与**碎片合并**（避免请求瀑布）；实测 magic-string → 单个 37.3 KB 文件。

```
optimizeDeps.include  提前声明，避免运行期新发现依赖触发重新预构建并刷新页面
optimizeDeps.exclude  给本地 workspace 包留活路（被预构建后改动不生效）
缓存目录              node_modules/.vite；遇到诡异问题先删缓存
```

### 4.3 环境变量、静态资源与产物形态

**环境变量**：

```
编译期静态替换，实测产物里 import.meta.env 已消失
只有 VITE_ 前缀暴露；不能动态拼接 key
define 替换的是代码文本，值必须 JSON.stringify
```

**静态资源与产物形态**：

```
assetsInlineLimit  0.6KB 内联 / 10.8KB 发文件；内联的图不进 HTTP 缓存（跟着 JS 走）
build.target       只管语法不管 API；es2015 下 ?? 与 ?. 都被改写；API polyfill 不补
import.meta.glob   默认懒加载（4 chunk），eager 合并（1 chunk）
```

### 4.4 配置、插件与 HMR

- 配置按阶段分：通用 / 仅 dev / 仅 build / SSR；`server.proxy` 只在 dev 生效；SSR 的 external 与浏览器产物的 external 是两件事；Rolldown 下 `manualChunks` 只接受函数形式。
- 插件：`enforce` 排**同一钩子**内的顺序（实测 pre → normal → post，跨钩子无效）；`apply` 决定加载与否（`'build'` / `'serve'`）。
- `transformIndexHtml` 的 `ctx.bundle` 仅 build；dev 侧走 `configureServer` 挂中间件。
- 真实插件：注入 modulepreload **必须查重**，Vite 默认已注入过。

### 4.5 钩子全景与断点调试

实测 Vite 8.3.0：一次 build 触发 **21 个钩子**，一次 dev + 请求触发 **13 个**。主干分四段：

```
① 配置期（两侧，只跑一次）  config → configResolved → options
② 构建期（按模块放大）      buildStart → resolveId → load → transform
                            → resolveDynamicImport → moduleParsed → buildEnd
③ 输出期（按 chunk 放大）   renderStart → banner / intro / outro / footer
                            → renderChunk → augmentChunkHash
                            → generateBundle → transformIndexHtml → writeBundle
④ 收尾                      closeBundle
```

- **dev 也走打包器管线**（Vite 6 起 Environment API）：`buildStart` / `buildEnd` / `options` 在 dev 侧一样触发，"dev 只是裸 ESM 服务、没有插件管线"已经不成立。
- **`transformIndexHtml` 两侧位置不同**：build 在 `generateBundle` 之后（先有全部产物再生成 HTML，`ctx` 带 `bundle`）；dev 在 `load` 之前，`ctx` 是 `{ path, filename, server, originalUrl }`。
- **`handleHotUpdate` 已失效**：8.x 改名 `hotUpdate`（`ctx` = `{ type, file, timestamp, read, server, modules }`），老名字注册了也一次都不触发。
- **注册了不等于会被调用**：实测 3 个钩子全程未触发——`handleHotUpdate`、`configurePreviewServer`（只在 `vite preview` 下）、`renderDynamicImport`（本次 Rolldown 管线没有调它）。
- **`enforce` 不是"排到最前 / 最后"**：它决定的是用户插件彼此的先后、以及落在内置链的哪一段。实测 `enforce: 'pre'` 的用户插件落在索引 4（前面还有 4 个内置插件），`'post'` 之后仍压着 3 个；插件链长度 29（serve）/ 38（build）。
- 内置插件是现成的钩子教材：解析 `vite:pre-alias` / `vite:resolve-dev` / `vite:optimized-deps`、加载 `vite:asset` / `vite:css` / `builtin:vite-json`、转换 `vite:oxc` / `vite:define` / `vite:import-analysis`、产物 `vite:css-post` / `vite:build-html`、变更 `vite:watch-package-data` / `vite:import-glob`。

**断点调试**：入口换成 JS API 脚本（本篇 `debug-entry.mjs`），别用 `.bin/vite`——Windows 下 `vite.cmd` 多包了一层批处理，`--inspect-brk` 传不到真正的 node 进程；`node --inspect-brk=9229` + `chrome://inspect` 可完全脱离 IDE。

```
坑  dev server 不自己退出 → 调试入口留 --once，请求一次就关
    dev 下不请求就什么都不发生（实测 transform 0 次）→ 必须自己 fetch 页面与模块
    `.bin/vite.cmd` 吞 --inspect-brk → 直指 node_modules/vite/bin/vite.js，或用 JS API 入口
```

- `timingPlugin` 打印里程碑耗时（实测 `buildStart` 201ms → `buildEnd` 285ms → `generateBundle` 314ms → `writeBundle` 360ms），能把"慢在模块构建"与"慢在产物生成"分开。

### 4.6 边界

```
老浏览器、webpack 专有 loader、Module Federation、多格式库产物
```

这几个场景 Vite 并不占优，需权衡迁移成本。

## 5. Rollup

### 5.1 ESM 优先

静态 `import` 让构建期就拿到完整依赖图。

```
收益  精确 tree-shaking、作用域提升、无运行时注入
代价  CJS 要靠插件、动态 require 不支持
```

### 5.2 tree-shaking 与副作用

- 实测：未被引用的导出被删（false），顶层副作用保留（true）。
- 两档控制：`/*#__PURE__*/` 管**单个表达式**、`treeshake.moduleSideEffects` 管**整个模块**。
- **`moduleSideEffects: false` ≠ 模块内副作用语句可删**——实测 `lib.js` 顶层 `console.log` 照样保留，Rollup 证明不了 `console` 的方法是纯的。
- 对比 webpack：Rollup 一步完成，webpack 要「标记 + 压缩器」两步。

### 5.3 五种输出格式

```
esm 0.45 KB（最小）→ cjs 0.50 → iife 0.64 → system 0.86 → umd 0.91 KB
差异只在包裹层；只有 es 能被二次 tree-shaking
```

- 发库至少给两份：`main` → cjs、`module` → esm；`exports` 条件导出可更精细（按 import/require 分别给入口）。

### 5.4 四个产物开关

```
external        打不打进来（实测 10170 → 23 字符）
output.globals   UMD/IIFE 下外部依赖取全局变量，不配就是 undefined
manualChunks    拆成几个文件（长缓存）
preserveModules  不合并、一比一还原源目录（组件库）
```

- 判断标准：**使用方也可能用到的东西就该 external**。

### 5.5 插件钩子与 PluginContext

钩子分两类：

```
build 钩子  options → buildEnd   一次构建只跑一次
output 钩子  renderStart → closeBundle  每个 output 各跑一次
resolveId/load/transform/moduleParsed 按模块数放大
```

- `closeBundle` 只在 bundle 被关闭时触发——只用 `generate()` 且忘了 `bundle.close()` 就等不到它。
- PluginContext：`getModuleIds` / `getModuleInfo` 拿模块图；`emitFile` 出 asset；`warn` 只提示、`error` 直接中断——同一插件换开关就是「报告」或「门禁」。
- 真实插件（体积门禁）：`generateBundle` 里算 **gzip**、卡阈值、`emitFile` 出 manifest；量 gzip 而非 raw；按 chunk 定阈值而非总量。

### 5.6 CJS 互操作与不适合场景

- Rollup 眼里 `module.exports` 只是一行赋值；commonjs 插件的本质是把赋值改写成导出 + interop 包装（产物里的 `_interopDefault` / `__toESM`）。
- CJS 的 `module.exports` 对应 ESM 的 `default` 还是命名空间，取决于使用方怎么导入，只能生成包装函数在运行时判断。
- 不适合：应用开发（无 dev server / HMR）、MF、复杂非 JS 资源、大量 CJS 依赖（每个都要过转换 + interop 陷阱）。

## 6. esbuild 与 Rust 工具链

### 6.1 esbuild：transform 与 build

```
transform  只转换单个字符串、不解析依赖（适合"改一段代码"，如 TS 剥离）
build      建依赖图出产物（完整打包）
```

- 实测 transform 第二次 3 ms；首次调用约 700 ms（加载 Go 编译的原生二进制），之后常驻内存。

### 6.2 target 与 metafile

- **target**：降级要注入运行时辅助代码（实测 es2015 产物 685 字符 vs esnext 82）；target 由浏览器基线决定，**不是越新越好**。只管语法不管 API。
- **metafile**：看占比要读 `outputs[*].inputs` 的 **`bytesInOutput`**，不是顶层 `inputs`（后者是源文件大小，不代表进产物的量）；tree-shaking 默认生效；压缩比实测 0.58。

### 6.3 三工具对比与 Rust 工具链全景

**三工具对比（50 次转换）**：

```
SWC 0.13ms / esbuild 1.50ms / Babel 20.10ms（167x）
单文件转换 SWC 赢（跨进程开销小）；整包构建 esbuild 赢（一个进程做完）
批量转换用 SWC，整包构建用 esbuild，需要自定义插件用 Babel
```

- 类型检查永远交给 `tsc --noEmit`——三者都是转译器，不做类型检查。
- **Rust 工具链全景**：SWC 替 Babel、Rspack 替 webpack、Rolldown 替 Rollup、Biome/Oxlint 替 ESLint/Prettier。
- **选型关键不是"谁快"，是替换成本**：配置兼容 / 行为一致 / 插件生态。
- 不该换的情况：构建只要几秒、重度自定义 Babel 插件、瓶颈不在构建、无人能排查。

## 7. 构建插件开发

### 7.1 扩展点与三套钩子的差异

**扩展点只有三类**：

```
解析    resolveId / load
转换    transform / loader
产物    generateBundle / emitAsset
```

三套钩子的差异根源：

```
Rollup/Vite   声明式"回答 id 与内容"
webpack       模块必须真实存在，内容由 loader 加工
```

### 7.2 同一需求三套实现与 unplugin

- 实测同一需求三套产物都含 BUILD_INFO；webpack 需要**占位文件 + loader**，Vite 需要 `enforce: 'pre'`。
- **unplugin**：一份实现跑 Rollup / Vite / webpack（实测三者均成功）；API 是 `unplugin.rollup(options)`，不是 `unplugin(options).rollup()`。
- 代价：只能用 unplugin 抽象的那层，**deep 定制仍要写原生插件**。

### 7.3 六个坑与经验

```
坑一  虚拟 id 别用冒号（webpack 报 Unhandled scheme）
坑二  未被引用的导出会被摇掉，误判插件失效——先确认有没有真实使用
坑三  Vite 虚拟模块要 enforce: 'pre'
坑四  transform 要还 sourcemap，用 magic-string 保行号
坑五  分清 dev / build 阶段，用 config.command 判断
坑六  webpack 插件改配置要趁早，规则放配置文件更稳
```

**经验**：能配置不写插件；能用 transform 不碰 resolveId。

## 8. 产物分析与体积优化

### 8.1 分析顺序与体积来源

**顺序**：先看清产物，再选手段——构建器元数据（`metafile` / `stats`）看每个输入模块占多少字节、可视化工具看 treemap、读产物文本验证某函数是否真的被打进去。

**体积的四类来源**：

```
业务代码   靠 tree-shaking 与分割
第三方依赖 靠换轻依赖、按需引入
重复打包   靠 dedupe / external（产物清单里同一包两条 node_modules 路径）
产物形态   靠压缩与现代语法
```

### 8.2 引用方式与 tree-shaking

- 实测 A 全量 2509 vs B 按需 165 字节，差 **15 倍**。
- **`import * as ns` 再 `export` 出去是失效点**——打包器无法证明外部不会访问 `ns.utilN`，只能全留。
- 「按需引入了体积还没变」的三个可能：库本身是 CJS 产物、引入了带副作用的模块、把 namespace 又 export 了出去。
- `sideEffects` 是给打包器的承诺：数组外的文件可整块删；写错方向会删掉必须保留的代码（如样式）。

### 8.3 副作用、分割、压缩与误区

**副作用**：顶层有副作用的模块整块保留（实测 `window` 赋值仍在）。

**代码分割**：

```
改的是"体积分布"不是"体积总量"
实测首屏 2946 → 入口 175 / utils chunk 1939
分割引入 chunk 边界胶水，总字节可能反而变大；粒度：按路由 > 按交互 > 按依赖
```

**压缩**：

```
实测 A 0.68 / B 0.51——不能替代 tree-shaking（压缩后仍差 20 倍）
传输体积还要过 gzip/brotli；做体积门槛要统一口径、量压缩后字节
```

**误区**：

```
CJS 产物无法被静态分析，改引用方式无效
拆包可能总体积变大
vendor 的收益来自 hash 稳定（缓存命中），不在抽取动作本身；依赖一升级就整体重打
```

## 9. 手写 mini-bundler

### 9.1 四步骨架与依赖解析

**四步骨架**：

```
解析依赖 → 建模块图 → ESM→CJS 转换 → 生成运行时 + 模块表
```

- 真实打包器产物结构相同，差别只在运行时功能多寡。
- **依赖解析**：相对路径以「引用者所在目录」为基准，所以要带 `importer`；补后缀（`.js` / `index.js`）；裸模块在本实现里直接抛错。
- 用 AST 而非正则，因为 import 写法太多。

### 9.2 建图、转换与运行时

**建图**：

```
modules.has 兼做去重与防环
「先登记再递归」是循环依赖不爆栈的前提
id = 发现顺序，DFS 前序（deps: [1, 3, 2, 4]）
```

**转换**：

```
四种 import → __require(id) + 解构；别名方向是 { imported: local }
default 约定放在 exports.default
export 用「删关键字 + 末尾统一赋值」，代价是快照而非活绑定
```

**运行时**：

```
cache 让模块只执行一次
cache[id] = module 必须早于执行，否则循环依赖死循环
函数包装 = 模块作用域
```

### 9.3 循环依赖实测与边界

**循环依赖（实测）**：

```
函数导出  原生 ESM 读到 function，产物读到 undefined（函数声明有提升，掩盖问题）
const 导出 原生 ESM 抛 ReferenceError 并中止，产物静默 undefined 且继续跑
结论      打包把加载期错误推迟成运行期 undefined，是 CJS 语义的固有代价
```

- ESM 的绑定是活绑定 + TDZ，读未初始化的绑定直接抛错；打包成 CJS 后，运行时把「正在构建的模块」提前放进缓存，循环引用拿到的是**半成品 exports**。
- 「本地能跑通」不能当作没有循环依赖的证据，要查模块图而不是查现象。
- 补充第三句贯穿判断：**打包成 CJS 会改变模块语义**——ESM 的活绑定与 TDZ 报错，在 CJS 运行时里会退化成静默的 `undefined`。

**边界**：无 tree-shaking / 作用域提升 / 代码分割 / sourcemap / 非 JS 资源；真实工具的每一项能力，都是在这个骨架上加一层。
