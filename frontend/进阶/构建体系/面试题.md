# 模块面试题 · 构建体系

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。
> 答题节奏遵循[「面试方法论」](../../进阶/面试方法论.md)的四步答题法——结论/原理/边界/追问。
> 题目来源：由本模块各篇正文的知识点整理，每题在标题后标注出处（第 N 篇 / 场景综合）。

## 一、基础概念

### Q1: 构建到底在做什么？为什么不能直接用源码上线？（第 1 篇）

- **结论**：构建就是把「开发者写的模块」翻译成「浏览器能高效加载的产物」——四步：解析建图 → 转换 → 拼装 → 优化输出。
- **原理**：解析阶段从入口递归出依赖图；转换阶段做语法降级与资源编译；拼装把成百上千个模块合成少数几个文件；优化输出做 tree-shaking、压缩、hash 命名。
- **边界**：不构建的代价是模块数量（上千个请求）、语法降级（新语法跑不起来）、非 JS 资源（TS/CSS/图片不能被直接执行）、体积（没有压缩与摇树）。
- **追问**：开发环境能不能少做？→ 能。开发环境可以跳过拼装与压缩（Vite 就是这么做的），生产必须全做。

### Q2: 三代构建工具的分界线是什么？（第 1 篇）

- **结论**：任务流（Grunt/Gulp，不解析依赖）→ 打包器（webpack/Rollup，建依赖图）→ 原生 ESM + 原生语言（Vite/esbuild）。第三代的本质是**把打包从开发态挪走**。
- **原理**：第一代只做「文件级加工」，不知道谁依赖谁；第二代建完整依赖图，代价是开发时也要全量拼装；第三代让浏览器原生 ESM 自己加载模块，开发时不拼装，加上 Go/Rust 写的转译器把单文件转换压到毫秒级。
- **边界**：第三代不是「打包被淘汰」——生产依然要打包，只是开发时不再为它付费。
- **追问**：Vite 生产构建用什么？→ 8.x 起默认 Rolldown（兼容 rollupOptions），不是 Rollup。

### Q3: loader 和 plugin 的区别？（第 3 篇）

- **结论**：loader 是「文件翻译器」，plugin 是「流程参与者」——前者加工单个文件的内容，后者监听整个构建生命周期。
- **原理**：loader 本质是「源码字符串 → 代码字符串」的函数，在 `module.rules` 里声明、链式从右往左执行；plugin 是有 `apply(compiler)` 的对象，靠钩子（如 `processAssets`）插手编译流程。
- **边界**：能用现有 loader 解决的别写 plugin；产出文件要用 `compilation.emitAsset`，不要自己 `fs.writeFileSync`（那样产物不进 webpack 的资产清单）。
- **追问**：产出文件的钩子为什么带 stage？→ `processAssets` 用 stage 控制多个插件处理同一资产的先后顺序。

### Q4: Vite 开发环境为什么快？快在哪一步？（第 4 篇）

- **结论**：快在「不打包」——dev 时 esbuild 只做依赖预构建与单文件转换，模块加载交给浏览器原生 ESM。
- **原理**：请求到哪个模块才转哪个模块，与项目规模无关；依赖预构建把 CommonJS 转成 ESM、把碎片依赖合并成单文件（实测 magic-string → 一个 37.3 KB 文件）。
- **边界**：HMR 同理——只重转变更模块 + WebSocket 通知，与项目规模无关；没有 `accept` 边界会向上冒泡，冒泡不到就整页刷新。
- **追问**：生产构建也快吗？→ 不。生产是全量打包，走 Rolldown，速度与产物与 Rollup 同量级。

### Q5: `import.meta.env` 和 `process.env` 有什么本质区别？（第 4 篇）

- **结论**：前者是**编译期静态替换**，后者在 webpack 下也是替换、但在 Node 里是运行时读取；构建工具里的环境变量本质都是文本替换。
- **原理**：构建时把 `import.meta.env.VITE_API` 直接替换成字面量，实测产物里 `import.meta.env` 已消失；所以不能动态拼接 key。Vite 只暴露 `VITE_` 前缀的变量。`define` 替换的是代码文本，值必须 `JSON.stringify`。
- **边界**：替换是「文本级」的，写错就是语法错或字符串没引号；密钥不能靠前缀机制保护——产物里是明文的。
- **追问**：改了 `.env` 为什么不生效？→ 环境变量在启动时读入，改了要重启 dev server。

### Q6: Rollup 的五种输出格式怎么选？（第 5 篇）

- **结论**：发库至少给两份——`main` 指向 cjs、`module` 指向 esm；iife/umd 只给需要 `<script>` 直接引入的场景。
- **原理**：实测同一份源码：esm 0.45 KB → cjs 0.50 → iife 0.64 → system 0.86 → umd 0.91 KB，差异只在包裹层；**只有 esm 能被二次 tree-shaking**，所以 `module` 字段是消费方能否摇树的关键。
- **边界**：`exports` 条件导出可以比 `main`/`module` 更精细（按 import/require 分别给入口），但要小心条件解析顺序。
- **追问**：umd 为什么最大？→ 它要同时适配 AMD、CommonJS 与全局变量，包裹层最厚。

### Q7: esbuild 的 `transform` 和 `build` 有什么区别？（第 6 篇）

- **结论**：`transform` 只转换单个字符串、不解析依赖；`build` 建依赖图并出产物。
- **原理**：`transform` 适合「改一段代码」（如插件里的 TS 剥离）；`build` 才是完整打包。实测 `transform` 第二次调用 3 ms，首次调用约 700 ms（含加载原生二进制）。
- **边界**：`transform` 不解析 import，所以不会帮你摇树、不会合并模块。
- **追问**：为什么第一次调用慢这么多？→ 首次要把 Go 编译的原生二进制加载进进程，之后常驻内存。

## 二、机制与原理

### Q8: tree-shaking 到底是怎么删代码的？（第 1 / 5 篇）

- **结论**：两步——**标记**哪些导出没被用到，再**删除**它们；webpack 的第二步由压缩器完成，Rollup 一步完成。
- **原理**：ESM 的依赖在编译期静态确定，打包器能建出「谁导出、谁引用」的图；未被引用的导出被标记为可删。webpack 用 `usedExports` 标记，删的动作交给 minimizer。
- **边界**：实测只声明 `sideEffects: false` 不删代码，必须同时开 `minimize`；所以评估体积必须开压缩看，检测未使用代码要搜字符串常量。
- **追问**：为什么 CommonJS 不能摇树？→ 依赖在运行时才确定，无法静态分析。

### Q9: 为什么我按需引入了，体积还是没变？（第 8 篇）

- **结论**：三种可能——库本身是 CommonJS 产物、引入了带副作用的模块、或者把 namespace 又 `export` 了出去。
- **原理**：实测同一份 20 函数的工具模块，全量引入 2509 字节 vs 具名引入 165 字节（差 15 倍）；但 `import * as utils` 再 `export { utils }` 会让打包器无法证明外部不会访问 `utils.utilN`，只能全留。顶层有副作用的模块（如 `window.x = true`）整块保留。
- **边界**：`sideEffects` 是给打包器的承诺——数组外的文件可视为无副作用、整块删除；写错方向会删掉必须保留的代码。
- **追问**：怎么验证到底摇掉了没有？→ 直接读产物搜那个函数名或字符串常量。

### Q10: 代码分割减小体积了吗？收益到底在哪？（第 8 篇）

- **结论**：**不减小总量，改的是体积的分布**——把非首屏代码挪出首屏。
- **原理**：实测同一场景，不分割时首屏 2946 字节；开启分割后入口 chunk 175 字节、utils chunk 1939 字节，首屏从 2946 降到 175。
- **边界**：分割会引入 chunk 边界的胶水代码，总字节可能反而变大；几十字节的 chunk 是负收益。
- **追问**：vendor 抽出来就一定快吗？→ 不一定，收益来自 vendor 的 hash 长期不变（缓存命中），依赖一升级就整体重打。

### Q11: webpack 的五个核心对象是什么关系？（第 3 篇）

- **结论**：Compiler（进程级）→ Compilation（一次编译）→ Module → Chunk → Asset；**模块数 ≠ 文件数**，中间隔着 Chunk 分组。
- **原理**：Compiler 是全局唯一的编译器实例；一次 `compiler.run()` 产出一个 Compilation；Compilation 里装着所有 Module；Module 按规则分组成 Chunk；Chunk 最终渲染成 Asset 落盘。
- **边界**：写插件时改 Module 不等于改 Asset——要在 `processAssets` 阶段拿到的才是最终文本。
- **追问**：`runtimeChunk: 'single'` 为什么值得开？→ 把运行时代码单独抽出，业务 chunk 的 hash 不再被运行时变动带崩（实测运行时 6.37 KiB）。

### Q12: SplitChunks 为什么没抽出来？（第 3 篇）

- **结论**：三个条件要同时满足——`minChunks`（被引用次数）、`minSize`（默认 20 KB）、cacheGroups 匹配规则。**默认 20 KB 下限是最常见的"抽不出来"原因**。
- **原理**：webpack 认为小于 20 KB 的共享模块单独发请求不划算。实测同样代码：`minSize` 20 KB 不抽，改成 0 就抽出 common chunk。
- **边界**：抽出来不一定更快——vendor 与路由级值得切，小共享模块不值得。
- **追问**：抽 common 需要什么前提？→ 多入口共享同一个模块（单入口的公共代码不算共享）。

### Q13: webpack 持久化缓存为什么小项目反而没收益？（第 3 篇）

- **结论**：缓存有序列化（读写磁盘）成本，模块少时这个成本可能盖过省下的转换时间。
- **原理**：实测小样本 1.11x、大样本 2.21x（按 webpack 自报时间）。另外 `require('webpack')` 本身要 2.8~3.3 s，用墙钟时间测量会被淹没。
- **边界**：持久化缓存不是默认就该开——先量，再决定；真要用，缓存目录要进 CI 缓存。
- **追问**：遇到诡异的构建问题第一步做什么？→ 删缓存目录。

### Q14: Babel 插件怎么写？最容易踩的坑是什么？（第 2 篇）

- **结论**：插件是返回 `{ name, visitor }` 的函数，visitor 按节点类型回调；两个坑是**替换后会被重新遍历**（可能递归）和 **plugins/presets 的执行顺序**（plugins 先于 presets，plugins 顺序、presets 逆序）。
- **原理**：`parse` 把文本变成 AST，`transform` 遍历改树，`generate` 变回文本；**AST 与源码是两份数据**，改树必须走 generate。类型判断用 `t.isXxx`、构造用 `t.xxx()`。
- **边界**：容器操作传的是父节点的字段名（不是数组本身）；增删节点需要路径（Path），朴素遍历只能「看」。
- **追问**：什么场景别用 AST？→ 纯文本替换且确定不涉及字符串/注释的，用正则更省；但 codemod 一定要用 AST（正则会误伤字符串与注释）。

### Q15: esbuild、SWC、Babel 怎么选？（第 6 篇）

- **结论**：**批量单文件转换用 SWC，整包构建用 esbuild，需要自定义插件用 Babel**。
- **原理**：实测同一份 TS 转换 50 次：SWC 0.13 ms / esbuild 1.50 ms / Babel 20.10 ms（167x）。SWC 赢在单文件转换（跨进程开销小），esbuild 赢在整包构建（一个进程做完所有事）。
- **边界**：类型检查永远交给 `tsc --noEmit`——这三个都是转译器，不做类型检查。
- **追问**：Rust 工具链该不该整体替换？→ 关键不是「谁快」，是替换成本：配置兼容性、行为一致性、插件生态。构建只要几秒的项目不值得换。

### Q16: Vite 的依赖预构建解决了什么问题？（第 4 篇）

- **结论**：两个——把 CommonJS 依赖转成 ESM，以及把大量碎片文件合并成少数几个文件（避免请求瀑布）。
- **原理**：扫描入口发现的裸模块依赖，用 esbuild 打包成单文件放进 `node_modules/.vite`；实测 magic-string → 一个 37.3 KB 文件。
- **边界**：运行期新发现的依赖会触发重新预构建并刷新页面——用 `optimizeDeps.include` 提前声明可以避免。
- **追问**：遇到诡异的依赖问题第一步做什么？→ 删 `node_modules/.vite`。

## 三、排障与选型

### Q17: 新项目该选 webpack 还是 Vite？（第 1 篇）

- **结论**：现代浏览器的业务应用默认选 Vite；需要 Module Federation、重度自定义 loader 的老项目留在 webpack。
- **原理**：Vite 的优势在开发态（不打包 + 原生 ESM），生产构建走 Rolldown，产物质量与 Rollup 同量级；webpack 的优势在生态深度（MF、复杂 loader 链）。
- **边界**：迁移成本不在配置，在**自定义 loader 与插件的替换成本**——先把这块列清楚再决定。
- **追问**：「Vite 比 webpack 快所以迁移」这个说法错在哪？→ Vite 快的是开发态，生产构建不比 Rollup/Rolldown 快。

### Q18: 发 npm 库该用哪个打包器？（第 1 / 5 篇）

- **结论**：用 Rollup（或基于它的 Vite 库模式），**不要用 webpack**。
- **原理**：Rollup 是 ESM 优先，产物干净——作用域提升、无运行时注入；webpack 会塞进自己的运行时（实测 6.37 KiB），对库是纯浪费。
- **边界**：库打包清单——依赖 external、双格式（cjs + esm）、类型声明、`sideEffects`、sourcemap、体积检查。
- **追问**：库为什么不适合 webpack 的 `runtimeChunk` 补救？→ 即便抽出来，消费方仍要多加载一个文件，不如 Rollup 根本不生成。

### Q19: 构建产物体积突然涨了，怎么排查？（第 8 篇）

- **结论**：按「看清产物 → 定位大头 → 选手段」三步走，别凭感觉删依赖。
- **原理**：三个数据来源——构建器元数据（esbuild `metafile`、webpack `stats`）看每个输入模块占多少字节；可视化工具看 treemap；直接读产物文本验证某个函数是否真的被打进去。先分清是业务代码、第三方依赖、重复打包（同一包多版本）还是产物形态（未压缩 / ES5 + polyfill）中的哪一类。
- **边界**：看 metafile 要读 `outputs[*].inputs` 里的 `bytesInOutput`，不是顶层 `inputs`（后者是源文件大小，不代表进产物的量）。
- **追问**：怎么判断是不是重复打包？→ 产物清单里同一个包出现两条 `node_modules` 路径（不同版本）。

### Q20: 编译产物太大，压缩能救吗？（第 8 篇）

- **结论**：**压缩不能替代 tree-shaking**——它只把已经在那里的代码写得更短。
- **原理**：实测 A（全量）2509 → 1714 字节，B（按需）165 → 84 字节；压缩后 A 仍是 B 的 20 倍。
- **边界**：压缩后的数字才接近传输体积，但还不等于——还要过 gzip/brotli。做体积门槛时全团队要统一口径。
- **追问**：现代语法产物能省多少？→ 省的是降级代码与 polyfill：实测同一段 `??`，target esnext 82 字符 vs es2015 685 字符（要注入运行时辅助）。

### Q21: 写构建插件，怎么一份代码同时支持 webpack / Vite / Rollup？（第 7 篇）

- **结论**：用 unplugin——一份实现（resolveId + load）翻译成三套钩子。
- **原理**：三者的扩展点本质只有三类：解析（resolveId/load）、转换（transform/loader）、产物（generateBundle/emitAsset）；unplugin 负责把同一份定义映射到各打包器的钩子。注意 API 是 `unplugin.rollup(options)`，不是 `unplugin(options).rollup()`。
- **边界**：只能用 unplugin 抽象的那层，deep 定制仍要写原生插件；webpack 侧模块必须真实存在，所以要配占位文件 + loader。
- **追问**：虚拟模块 id 为什么要避免冒号？→ webpack 会把 `virtual:xxx` 当 URI scheme，报 Unhandled scheme。

### Q22: 构建速度慢，第一步该做什么？（第 1 / 3 篇）

- **结论**：先**量清楚慢在哪**——是转换、依赖图还是压缩；别急着换工具。
- **原理**：实测 200 模块构建：esbuild 557 ms / rollup 1303 ms / webpack 3698 ms，差距的根因是「开发态要不要拼装」与「转译器是不是原生语言」。另外一个常被忽略的事实：进程总耗时比构建耗时多约 400 ms（Node 启动固定成本），用墙钟时间测小项目会得出错误结论。
- **边界**：构建只要几秒的项目，换 Rust 工具链的收益不如先开持久化缓存、缩小 loader 作用范围（include/exclude）。
- **追问**：怎么量？→ 用 Node API 直接调构建器并计时，或读 `stats` 自报时间，不要测 `npm run build` 的墙钟。

## 四、场景设计题

### Q23: 场景：要给团队做一个「构建产物体积门禁」，怎么设计？（场景综合）

- **结论**：三件事——定口径、定基线、定动作；口径不统一的门禁一定会误杀。
- **原理**：① 口径统一为「压缩后（或压缩 + gzip 后）的产物字节数」，并写死在脚本里；② 基线取「最近 N 次构建的中位数」而非固定值，避免单次波动；③ 超阈值时在 CI 输出「哪个模块涨了多少」（读 metafile / stats），而不是只报一个总数；④ 分级——小幅增长只警告，大幅增长才阻断。
- **边界**：不要对「未压缩产物」设门槛（压缩率会掩盖真实变化）；不要把 vendor chunk 和业务 chunk 混在一起判定（前者涨是依赖升级，后者涨是代码问题）。
- **追问**：为什么建议用中位数而不是平均值？→ 中位数不受单次异常构建影响，且能体现趋势漂移。

### Q24: 场景：老 webpack 项目要迁 Vite，怎么评估与落地？（场景综合）

- **结论**：先盘「不可替换项」，再按路由灰度迁移，最后才动配置。
- **原理**：① 列出所有自定义 loader 和 plugin，逐个判断 Vite 侧有无等价物（多数 loader 可由插件替代，webpack 专有的要重写）；② 检查是否用了 Module Federation、CommonJS 动态 require、非标准资源处理——这几项是硬阻塞；③ 用 `vite build` 单独跑通产物，与 webpack 产物做体积与功能对比；④ 开发态先切（收益最直接），生产构建保留 webpack 一段时间双跑。
- **边界**：环境变量要迁移（`process.env` → `import.meta.env`，且只有 `VITE_` 前缀暴露）；依赖预构建可能掩盖 CJS 依赖问题，上线前要清缓存重跑一次。
- **追问**：为什么说迁移成本不在配置？→ 配置文件通常几百行能翻译完，真正的成本是自定义 loader 与插件的重写和验证。

### Q25: 场景：要做一个「按需引入」的组件库（类似 babel-plugin-import），怎么实现？（场景综合）

- **结论**：两种路线——编译期改写 import（Babel/SWC 插件），或纯 ESM + `sideEffects: false` 让打包器自己摇。
- **原理**：① 插件路线：在 visitor 里拦截 `ImportDeclaration`，把 `import { Button } from 'ui'` 改写成 `import Button from 'ui/es/button'` 并补上样式 import，靠 `t.isImportDeclaration` 判断、`path.replaceWithMultiple` 替换；② 摇树路线：库以 ESM 发布、每个组件独立文件、声明 `sideEffects` 只保留样式文件，消费方具名引入即可。
- **边界**：插件路线要防重复遍历（替换后的节点会再次进入 visitor）；样式文件的副作用必须保留，否则样式会被摇掉。
- **追问**：现在更推荐哪种？→ 摇树路线。现代打包器对 ESM 的支持已经足够好，少一层编译插件就少一处出错点。

### Q26: 场景：要给内部框架写一个「构建期注入版本信息」的能力，怎么设计？（场景综合）

- **结论**：用虚拟模块 + 构建钩子，不要运行时读接口——构建期注入的值才能被常量折叠与摇树。
- **原理**：插件 `resolveId` 拦截约定的模块 id（如 `virtual-build-info`），`load` 返回 `export const BUILD_INFO = {...}` 的源码；构建时把 git 分支、commit、构建时间写进去。Vite 侧要 `enforce: 'pre'`，webpack 侧模块必须真实存在（配占位文件 + loader）。
- **边界**：虚拟 id 别用冒号（webpack 报 Unhandled scheme）；未被引用的导出会被摇掉——调试时若发现「插件没生效」，先确认有没有真实使用。
- **追问**：为什么不用 `define` 直接替换一个全局变量？→ 可以用，但虚拟模块能导出结构化对象、有类型，且能被摇树。

### Q27: 场景：线上偶发一个字段是 `undefined`，怀疑是循环依赖，怎么定位与处理？（场景综合）

- **结论**：循环依赖是「构建期本该暴露的错误被推迟成运行期 `undefined`」的典型来源；先确认链路，再改设计，兜底放最后。
- **原理**：ESM 的绑定是活绑定，`const` 导出还有 TDZ，读未初始化的绑定会**直接抛错**；打包成 CJS 后，运行时把「正在构建的模块」提前放进缓存，循环引用拿到的是**半成品 exports**，读不到就是 `undefined`。实测对照：同一份源码，原生 ESM 抛 `ReferenceError: Cannot access 'A_NAME' before initialization` 并中止，打包产物静默打印 `undefined` 并一路跑完。
- **边界**：函数声明有提升，循环里读函数**看起来是正常的**（实测原生读到 `function`），最容易掩盖问题；所以「本地能跑通」不能当作没有循环依赖的证据，要查模块图而不是查现象。
- **追问**：确认了循环依赖但一时改不动怎么办？→ 把顶层的读取改成函数内部的延迟求值（或改成依赖注入传参），让引用发生在两个模块都初始化之后。
