# 模块面试题 · 构建体系

> 用法：先遮住答案自测，再对照参考；每题以一句能背下来的判断句打头，可直接当复习清单用。

## 1. 构建全景与选型

### Q1（1.1）｜ 构建到底在做什么？为什么不能直接用源码上线？

- **判断**：构建就是把「开发者写的模块」翻译成「浏览器能高效加载的产物」——四步：解析建图 → 转换 → 拼装 → 优化输出。
- **展开**：解析阶段从入口递归出依赖图；转换阶段做语法降级与资源编译；拼装把成百上千个模块合成少数几个文件；优化输出做 tree-shaking、压缩、hash 命名。不构建的代价是模块数量（上千个请求）、语法降级（新语法跑不起来）、非 JS 资源（TS/CSS/图片不能被直接执行）、体积（没有压缩与摇树）。
- **边界**：开发环境能少做——可以跳过拼装与压缩（Vite 就是这么做的），生产必须全做。追问：为什么不能直接上线？→ 等价于探究四类代价各自会引发什么问题，按模块数量 / 语法 / 非 JS 资源 / 体积逐条答。

### Q2（1.2）｜ 三代构建工具的分界线是什么？

- **判断**：任务流（Grunt/Gulp，不解析依赖）→ 打包器（webpack/Rollup，建依赖图）→ 原生 ESM + 原生语言（Vite/esbuild）。第三代的本质是**把打包从开发态挪走**。
- **展开**：第一代只做「文件级加工」，不知道谁依赖谁；第二代建完整依赖图，代价是开发时也要全量拼装；第三代让浏览器原生 ESM 自己加载模块，开发时不拼装，加上 Go/Rust 写的转译器把单文件转换压到毫秒级。
- **边界**：第三代不是「打包被淘汰」——生产依然要打包，只是开发时不再为它付费。追问：Vite 生产构建用什么？→ 8.x 起默认 Rolldown（兼容 rollupOptions），不是 Rollup。

### Q3（1.3）｜ tree-shaking 到底是怎么删代码的？

- **判断**：两步——**标记**哪些导出没被用到，再**删除**它们；webpack 的第二步由压缩器完成，Rollup 一步完成。
- **展开**：ESM 的依赖在编译期静态确定，打包器能建出「谁导出、谁引用」的图；未被引用的导出被标记为可删。webpack 用 `usedExports` 标记，删的动作交给 minimizer；Rollup 在解析期直接删掉。
- **边界**：实测只声明 `sideEffects: false` 不删代码，必须同时开 `minimize`；所以评估体积必须开压缩看，检测未使用代码要搜字符串常量。追问：为什么 CommonJS 不能摇树？→ 依赖在运行时才确定，无法静态分析。

### Q4（1.3）｜ 构建速度慢，第一步该做什么？

- **判断**：先**量清楚慢在哪**——是转换、依赖图还是压缩；别急着换工具。
- **展开**：实测 200 模块构建 esbuild 557 ms / rollup 1303 ms / webpack 3698 ms，差距的根因是「开发态要不要拼装」与「转译器是不是原生语言」。另一个常被忽略的事实：进程总耗时比构建耗时多约 400 ms（Node 启动固定成本），用墙钟时间测小项目会得出错误结论。
- **边界**：构建只要几秒的项目，换 Rust 工具链的收益不如先开持久化缓存、缩小 loader 作用范围（include/exclude）。追问：怎么量？→ 用 Node API 直接调构建器并计时，或读 `stats` 自报时间，不要测 `npm run build` 的墙钟。

### Q5（1.4）｜ 新项目该选 webpack 还是 Vite？

- **判断**：现代浏览器的业务应用默认选 Vite；需要 Module Federation、重度自定义 loader 的老项目留在 webpack。
- **展开**：Vite 的优势在开发态（不打包 + 原生 ESM），生产构建走 Rolldown，产物质量与 Rollup 同量级；webpack 的优势在生态深度（MF、复杂 loader 链）。
- **边界**：迁移成本不在配置，在**自定义 loader 与插件的替换成本**——先把这块列清楚再决定。追问：「Vite 比 webpack 快所以迁移」这个说法错在哪？→ Vite 快的是开发态，生产构建不比 Rollup/Rolldown 快。

### Q6（1.4）｜ 发 npm 库该用哪个打包器？

- **判断**：用 Rollup（或基于它的 Vite 库模式），**不要用 webpack**。
- **展开**：Rollup 是 ESM 优先，产物干净——作用域提升、无运行时注入；webpack 会塞进自己的运行时（实测 6.37 KiB），对库是纯浪费。
- **边界**：库打包清单——依赖 external、双格式（cjs + esm）、类型声明、`sideEffects`、sourcemap、体积检查。追问：库为什么不适合 webpack 的 `runtimeChunk` 补救？→ 即便抽出来，消费方仍要多加载一个文件，不如 Rollup 根本不生成。

### Q7（1.4）｜ 场景：老 webpack 项目要迁 Vite，怎么评估与落地？

- **判断**：先盘「不可替换项」，再按路由灰度迁移，最后才动配置。
- **展开**：①列出所有自定义 loader 和 plugin，逐个判断 Vite 侧有无等价物（多数 loader 可由插件替代，webpack 专有的要重写）；②检查是否用了 Module Federation、CommonJS 动态 require、非标准资源处理——这几项是硬阻塞；③用 `vite build` 单独跑通产物，与 webpack 产物做体积与功能对比；④开发态先切（收益最直接），生产构建保留 webpack 一段时间双跑。
- **边界**：环境变量要迁移（`process.env` → `import.meta.env`，且只有 `VITE_` 前缀暴露）；依赖预构建可能掩盖 CJS 依赖问题，上线前要清缓存重跑一次。追问：为什么说迁移成本不在配置？→ 配置文件通常几百行能翻译完，真正的成本是自定义 loader 与插件的重写和验证。

## 2. 编译与 AST

### Q8（2.3）｜ Babel 插件怎么写？最容易踩的坑是什么？

- **判断**：插件是返回 `{ name, visitor }` 的函数，visitor 按节点类型回调；两个坑是**替换后会被重新遍历**（可能递归）和 **plugins/presets 的执行顺序**（plugins 先于 presets，plugins 顺序、presets 逆序）。
- **展开**：`parse` 把文本变成 AST，`transform` 遍历改树，`generate` 变回文本；**AST 与源码是两份数据**，改树必须走 generate。类型判断用 `t.isXxx`、构造用 `t.xxx()`。
- **边界**：容器操作传的是父节点的字段名（不是数组本身）；增删节点需要路径（Path），朴素遍历只能「看」。追问：什么场景别用 AST？→ 纯文本替换且确定不涉及字符串/注释的，用正则更省；但 codemod 一定要用 AST（正则会误伤字符串与注释）。

## 3. Webpack 深入

### Q9（3.1）｜ webpack 的五个核心对象是什么关系？

- **判断**：Compiler（进程级）→ Compilation（一次编译）→ Module → Chunk → Asset；**模块数 ≠ 文件数**，中间隔着 Chunk 分组。
- **展开**：Compiler 是全局唯一的编译器实例；一次 `compiler.run()` 产出一个 Compilation；Compilation 里装着所有 Module；Module 按规则分组成 Chunk；Chunk 最终渲染成 Asset 落盘。
- **边界**：写插件时改 Module 不等于改 Asset——要在 `processAssets` 阶段拿到的才是最终文本。追问：`runtimeChunk: 'single'` 为什么值得开？→ 把运行时代码单独抽出，业务 chunk 的 hash 不再被运行时变动带崩（实测运行时 6.37 KiB）。

### Q10（3.2）｜ loader 和 plugin 的区别？

- **判断**：loader 是「文件翻译器」，plugin 是「流程参与者」——前者加工单个文件的内容，后者监听整个构建生命周期。
- **展开**：loader 本质是「源码字符串 → 代码字符串」的函数，在 `module.rules` 里声明、链式从右往左执行；plugin 是有 `apply(compiler)` 的对象，靠钩子（如 `processAssets`）插手编译流程。
- **边界**：能用现有 loader 解决的别写 plugin；产出文件要用 `compilation.emitAsset`，不要自己 `fs.writeFileSync`（那样产物不进 webpack 的资产清单）。追问：产出文件的钩子为什么带 stage？→ `processAssets` 用 stage 控制多个插件处理同一资产的先后顺序。

### Q11（3.3）｜ SplitChunks 为什么没抽出来？

- **判断**：三个条件要同时满足——`minChunks`（被引用次数）、`minSize`（默认 20 KB）、cacheGroups 匹配规则。**默认 20 KB 下限是最常见的"抽不出来"原因**。
- **展开**：webpack 认为小于 20 KB 的共享模块单独发请求不划算。实测同样代码：`minSize` 20 KB 不抽，改成 0 就抽出 common chunk。
- **边界**：抽出来不一定更快——vendor 与路由级值得切，小共享模块不值得。追问：抽 common 需要什么前提？→ 多入口共享同一个模块（单入口的公共代码不算共享）。

### Q12（3.4）｜ webpack 持久化缓存为什么小项目反而没收益？

- **判断**：缓存有序列化（读写磁盘）成本，模块少时这个成本可能盖过省下的转换时间。
- **展开**：实测小样本 1.11x、大样本 2.21x（按 webpack 自报时间）。另外 `require('webpack')` 本身要 2.8~3.3 s，用墙钟时间测量会被淹没。
- **边界**：持久化缓存不是默认就该开——先量，再决定；真要用，缓存目录要进 CI 缓存。追问：遇到诡异的构建问题第一步做什么？→ 删缓存目录。

## 4. Vite

### Q13（4.1）｜ Vite 开发环境为什么快？快在哪一步？

- **判断**：快在「不打包」——dev 时 esbuild 只做依赖预构建与单文件转换，模块加载交给浏览器原生 ESM。
- **展开**：请求到哪个模块才转哪个模块，与项目规模无关；依赖预构建把 CommonJS 转成 ESM、把碎片依赖合并成单文件（实测 magic-string → 一个 37.3 KB 文件）。
- **边界**：HMR 同理——只重转变更模块 + WebSocket 通知，与项目规模无关；没有 `accept` 边界会向上冒泡，冒泡不到就整页刷新。追问：生产构建也快吗？→ 不。生产是全量打包，走 Rolldown，速度与产物与 Rollup 同量级。

### Q14（4.2）｜ Vite 的依赖预构建解决了什么问题？

- **判断**：两个——把 CommonJS 依赖转成 ESM，以及把大量碎片文件合并成少数几个文件（避免请求瀑布）。
- **展开**：扫描入口发现的裸模块依赖，用 esbuild 打包成单文件放进 `node_modules/.vite`；实测 magic-string → 一个 37.3 KB 文件。
- **边界**：运行期新发现的依赖会触发重新预构建并刷新页面——用 `optimizeDeps.include` 提前声明可以避免；`exclude` 给本地 workspace 包留活路。追问：遇到诡异的依赖问题第一步做什么？→ 删 `node_modules/.vite`。

### Q15（4.3）｜ `import.meta.env` 和 `process.env` 有什么本质区别？

- **判断**：前者是**编译期静态替换**，后者在 webpack 下也是替换、但在 Node 里是运行时读取；构建工具里的环境变量本质都是文本替换。
- **展开**：构建时把 `import.meta.env.VITE_API` 直接替换成字面量，实测产物里 `import.meta.env` 已消失；所以不能动态拼接 key。Vite 只暴露 `VITE_` 前缀的变量。`define` 替换的是代码文本，值必须 `JSON.stringify`。
- **边界**：替换是「文本级」的，写错就是语法错或字符串没引号；密钥不能靠前缀机制保护——产物里是明文的。追问：改了 `.env` 为什么不生效？→ 环境变量在启动时读入，改了要重启 dev server。

### Q16（4.3）｜ 小图标是内联成 data URI 好，还是单独发文件好？

- **判断**：看 `build.assetsInlineLimit`（默认 4096 字节）——阈值以下的转 base64 内联，以上的发独立文件。
- **展开**：实测两个 svg：0.6KB 的在默认阈值下内联（`data:image/svg+xml`），10.8KB 的始终是独立文件；把阈值收到 512 后，0.6KB 那个也变成文件了。
- **边界**：内联的资源**不会**进 HTTP 缓存——它跟着 JS 走，JS 一变它就要重新下载。所以"频繁变动的 JS 里内联一堆图片"是反模式；长期不变的小图标才适合内联。字体、大图永远不要内联。追问：为什么会有这个阈值而不是全部内联？→ base64 会让体积膨胀约 1/3，且无法被浏览器单独缓存，省下的请求数换来的可能是更大的传输量与更差的缓存命中。

### Q17（4.3）｜ 把 `build.target` 设成 `es2015` 是不是就兼容老浏览器了？

- **判断**：不是。`target` 只管**语法降级**，不管 **API polyfill**。
- **展开**：实测 `target: 'esnext'` 的产物里 `??` 与 `?.` 原样保留，`target: 'es2015'` 时两者都被改写成等价的 `if`/三元形式（主 chunk 从 4863 字符涨到 5135 字符）。但 `Object.fromEntries`、`Array.prototype.at`、`Promise.any` 这类新增 API 一个都不会被补上。
- **边界**：`target` 也不处理 CSS 特性与浏览器私有前缀；真要兼容老浏览器还得配 `@babel/preset-env` + `core-js`。追问：默认 `baseline-widely-available` 是什么档？→ 按浏览器基线数据选的一档，比 `esnext` 保守。降得越低产物越大、执行越慢，只按真实用户的最低版本来定。

### Q18（4.3）｜ `import.meta.glob` 默认会怎么打包？什么时候该用 `eager`？

- **判断**：默认**懒加载**——每个匹配到的模块单独出一个 chunk；`eager: true` 会把它们全部并进主 chunk。
- **展开**：实测 `import.meta.glob('./features/*.js')` 匹配 3 个模块时产物 4 个 chunk（入口 1 + 特性 3），改成 `eager: true` 后只剩 1 个 chunk。glob 在构建期展开成真实的 import 列表，所以它是静态可分析的，能被摇树也能被切 chunk。
- **边界**：模块很多时默认行为会产生一堆小文件（HTTP2 下影响有限，但在弱网与老协议下是负担）；反过来把首屏必需的东西设成懒加载，会多一轮"下载入口 → 发现依赖 → 再下载"的串行等待。追问：它是 Vite 独有的吗？→ 是的，webpack 里对应的是 `require.context`（能力更受限）。

### Q19（4.4）｜ 插件的 `enforce` 和 `apply` 分别管什么？为什么我的插件在 dev 下没生效？

- **判断**：`enforce` 管**同一钩子内部的执行顺序**（`pre` → `normal` → `post`），`apply` 管**插件是否被加载**（`'build'` / `'serve'`）。
- **展开**：实测把三个插件按 post / normal / pre 的乱序写进配置，同一个模块上的 `transform` 顺序仍是 `pre → normal → post`。`apply: 'build'` 的插件在 dev 阶段完全不会被调用。
- **边界**：`enforce` 跨钩子无效——`resolveId` 一定早于 `transform`，跟 enforce 无关。另外 `transformIndexHtml` 的 `ctx.bundle` **只有构建期才有**，dev 阶段想做类似的事必须走 `configureServer` 挂中间件。追问：想在 Vite 内置转换之前处理源码怎么办？→ `enforce: 'pre'`（TS 语法剥离、宏展开都靠它）；想看到最终 HTML 用 `order: 'post'`。

### Q20（4.4）｜ 场景：要给产物 HTML 自动加 `modulepreload` 和 CSP nonce，怎么做？有什么坑？

- **判断**：写一个 `apply: 'build'` 的插件，在 `transformIndexHtml`（`order: 'post'`）里读 `ctx.bundle` 找入口 chunk 的 `imports`，生成 `<link rel="modulepreload">`，再给 `<script>` 加 `nonce`。
- **展开**：实测入口 chunk 依赖 `assets/vendor-*.js` 时，注入后 HTML 里出现对应的 modulepreload，且 `<script nonce="lab-nonce">` 生效。这解决的是"入口 JS 下载完才知道还要下依赖"的串行等待。
- **边界**：**Vite 默认已经注入过 modulepreload**（`build.modulePreload`），自定义注入不查重就会变成 2 条、同一个 chunk 被请求两次——实测不查重 2 条、查重后 1 条。这是"以为是补能力、实际是重复"的典型。追问：dev 阶段也能这么改 HTML 吗？→ 可以调 `transformIndexHtml`，但拿不到 `ctx.bundle`（没有产物）；要暴露构建信息就走 `configureServer` 挂一个中间件。

## 5. Rollup

### Q21（5.3）｜ Rollup 的五种输出格式怎么选？

- **判断**：发库至少给两份——`main` 指向 cjs、`module` 指向 esm；iife/umd 只给需要 `<script>` 直接引入的场景。
- **展开**：实测同一份源码：esm 0.45 KB → cjs 0.50 → iife 0.64 → system 0.86 → umd 0.91 KB，差异只在包裹层；**只有 esm 能被二次 tree-shaking**，所以 `module` 字段是消费方能否摇树的关键。
- **边界**：`exports` 条件导出可以比 `main`/`module` 更精细（按 import/require 分别给入口），但要小心条件解析顺序。追问：umd 为什么最大？→ 它要同时适配 AMD、CommonJS 与全局变量，包裹层最厚。

### Q22（5.2）｜ `/*#__PURE__*/` 注解和 `treeshake.moduleSideEffects` 有什么区别，该用哪个？

- **判断**：两者粒度不同——注解管**单个表达式**，配置管**整个模块**；互补而不是替代。
- **展开**：实测同一份源码，默认配置下带 `/*#__PURE__*/` 的 `make('pure')` 被删、紧邻不带注解的 `make('nopure')` 保留（产物 404 字符）；改成 `moduleSideEffects: false` 后，整个 `pure.js` 连同它的顶层语句一起消失（151 字符）。
- **边界**：`moduleSideEffects: false` **不等于**"模块内部的副作用语句也能删"——实测 `lib.js` 顶层的 `console.log` 照样保留，Rollup 证明不了 `console` 的方法是纯的。真实库的正确姿势是给确定的模块开白名单（`moduleSideEffects: (id) => !id.includes('pure.js')`），而不是全局 `false`。追问：注解该谁写？→ 注解写在源码里（库作者负责），声明写在配置或 `package.json` 的 `sideEffects` 字段里（库使用者负责）。

### Q23（5.4）｜ 打包库时忘了配 `external` 会怎样？UMD 为什么还要配 `output.globals`？

- **判断**：忘记 external 会把依赖源码整个打进产物；UMD/IIFE 下 external 之后不配 `globals`，运行时取到的是 `undefined`。
- **展开**：实测入口整体 re-export 一个 200 导出的依赖——不 external 产物 10170 字符，external 后 23 字符（**440 倍**）；UMD 格式下 external 的依赖只能从全局变量取，"模块名 → 全局变量名"的映射就是 `output.globals: { react: 'React' }`。
- **边界**：`manualChunks` / `preserveModules` 管的是"拆成几个文件"，和 external 不是一回事；判断标准只有一条——**使用方也可能用到的东西就该 external**。追问：怎么避免手漏？→ 在 `options` 钩子里读 `package.json` 的 `dependencies` + `peerDependencies` 自动生成 external 列表，很多库的打包脚本就是这么干的。

### Q24（5.5）｜ Rollup 插件的 build 钩子和 output 钩子怎么分，放错了会怎样？

- **判断**：build 钩子（`options` → `buildEnd`）一次构建只跑一次；output 钩子（`renderStart` → `closeBundle`）每个 output 各跑一次。
- **展开**：实测 3 模块入口：`options`/`buildStart`/`buildEnd` 各 1 次，`resolveId`/`load`/`transform`/`moduleParsed` 各 3 次（按模块数放大）；同一个 bundle 第二次 `generate()` 后，build 钩子 +0、output 钩子 +1。
- **边界**：`closeBundle` 只在 bundle 被关闭时触发——只用 `generate()` 且忘了 `bundle.close()` 就等不到它。把重活放在按模块数放大的钩子里，模块一多就是构建变慢的主因。追问：插件要读一个自己的配置文件，放哪个钩子？→ `buildStart`，并且调 `this.addWatchFile(配置文件)` 声明监听，否则 watch 模式下改配置不会触发重构建。

### Q25（5.5）｜ 场景：产物体积总是悄悄涨上去，怎么做一个体积门禁？

- **判断**：在 `generateBundle` 里按 chunk 算 **gzip** 字节，超阈值就 `this.error` 中断，同时 `this.emitFile` 产出一份 manifest 供前后对拍。
- **展开**：实测 `index.js` raw 465B / gzip 358B；预算设成 0.15KB 时构建被中断，报错带 `[plugin bundle-guard]` 前缀。`generateBundle` 是最后一个能改产物的钩子，此刻的 `code` 就是即将落盘的内容。
- **边界**：必须量 gzip——浏览器拿到的是压缩后的字节，raw 与 gzip 常差 3 倍，拿 raw 定阈值等于自欺欺人；阈值要按 chunk 定而不是按总量，否则"新增了一个懒加载 chunk"会被总量掩盖。追问：只打印一行日志不行吗？→ 日志会丢、没法 diff；manifest 作为 asset 进 CI 产物，下次涨了才能定位到"哪天、哪个 chunk、涨了多少"。

### Q26（5.6）｜ Rollup 为什么离不开 `@rollup/plugin-commonjs`？CJS 依赖能不能不打插件用？

- **判断**：Rollup 只认 ESM，CJS 必须过插件；能不能直接用，看依赖的 `package.json` 有没有 `module` 或 `exports.import` 字段。
- **展开**：实测 `module.exports = { greet }` 不加插件时报 `"default" is not exported by "dep.cjs"`——在 Rollup 眼里那只是一行普通赋值语句。手写 20 行插件（把 `module.exports =` 替换成 `export default`）就能让它通过，这就是 commonjs 插件的最小形态。
- **边界**：真实插件还要处理动态 `require`、混合导出、条件导出，以及最麻烦的 interop——CJS 的 `module.exports` 到底对应 ESM 的 `default` 还是命名空间，取决于使用方怎么导入，只能生成包装函数在运行时判断（产物里的 `_interopDefault` / `__toESM` 就是这么来的）。追问：老项目全是 CJS 依赖，还适合用 Rollup 吗？→ 每个依赖都要过转换，转换结果还可能有 interop 陷阱，这类项目用 webpack / Vite 的成本明显更低。

## 6. esbuild 与 Rust 工具链

### Q27（6.1）｜ esbuild 的 `transform` 和 `build` 有什么区别？

- **判断**：`transform` 只转换单个字符串、不解析依赖；`build` 建依赖图并出产物。
- **展开**：`transform` 适合「改一段代码」（如插件里的 TS 剥离）；`build` 才是完整打包。实测 `transform` 第二次调用 3 ms，首次调用约 700 ms（含加载原生二进制）。
- **边界**：`transform` 不解析 import，所以不会帮你摇树、不会合并模块。追问：为什么第一次调用慢这么多？→ 首次要把 Go 编译的原生二进制加载进进程，之后常驻内存。

### Q28（6.3）｜ esbuild、SWC、Babel 怎么选？

- **判断**：**批量单文件转换用 SWC，整包构建用 esbuild，需要自定义插件用 Babel**。
- **展开**：实测同一份 TS 转换 50 次：SWC 0.13 ms / esbuild 1.50 ms / Babel 20.10 ms（167x）。SWC 赢在单文件转换（跨进程开销小），esbuild 赢在整包构建（一个进程做完所有事）。
- **边界**：类型检查永远交给 `tsc --noEmit`——这三个都是转译器，不做类型检查。追问：Rust 工具链该不该整体替换？→ 关键不是「谁快」，是替换成本：配置兼容性、行为一致性、插件生态。构建只要几秒的项目不值得换。

## 7. 构建插件开发

### Q29（7.2）｜ 写构建插件，怎么一份代码同时支持 webpack / Vite / Rollup？

- **判断**：用 unplugin——一份实现（resolveId + load）翻译成三套钩子。
- **展开**：三者的扩展点本质只有三类：解析（resolveId/load）、转换（transform/loader）、产物（generateBundle/emitAsset）；unplugin 负责把同一份定义映射到各打包器的钩子。注意 API 是 `unplugin.rollup(options)`，不是 `unplugin(options).rollup()`。
- **边界**：只能用 unplugin 抽象的那层，deep 定制仍要写原生插件；webpack 侧模块必须真实存在，所以要配占位文件 + loader。追问：虚拟模块 id 为什么要避免冒号？→ webpack 会把 `virtual:xxx` 当 URI scheme，报 Unhandled scheme。

### Q30（7.2）｜ 场景：要给内部框架写一个「构建期注入版本信息」的能力，怎么设计？

- **判断**：用虚拟模块 + 构建钩子，不要运行时读接口——构建期注入的值才能被常量折叠与摇树。
- **展开**：插件 `resolveId` 拦截约定的模块 id（如 `virtual-build-info`），`load` 返回 `export const BUILD_INFO = {...}` 的源码；构建时把 git 分支、commit、构建时间写进去。Vite 侧要 `enforce: 'pre'`，webpack 侧模块必须真实存在（配占位文件 + loader）。
- **边界**：虚拟 id 别用冒号（webpack 报 Unhandled scheme）；未被引用的导出会被摇掉——调试时若发现「插件没生效」，先确认有没有真实使用。追问：为什么不用 `define` 直接替换一个全局变量？→ 可以用，但虚拟模块能导出结构化对象、有类型，且能被摇树。

## 8. 产物分析与体积优化

### Q31（8.1）｜ 构建产物体积突然涨了，怎么排查？

- **判断**：按「看清产物 → 定位大头 → 选手段」三步走，别凭感觉删依赖。
- **展开**：三个数据来源——构建器元数据（esbuild `metafile`、webpack `stats`）看每个输入模块占多少字节；可视化工具看 treemap；直接读产物文本验证某个函数是否真的被打进去。先分清是业务代码、第三方依赖、重复打包（同一包多版本）还是产物形态（未压缩 / ES5 + polyfill）中的哪一类。
- **边界**：看 metafile 要读 `outputs[*].inputs` 里的 `bytesInOutput`，不是顶层 `inputs`（后者是源文件大小，不代表进产物的量）。追问：怎么判断是不是重复打包？→ 产物清单里同一个包出现两条 `node_modules` 路径（不同版本）。

### Q32（8.2）｜ 为什么我按需引入了，体积还是没变？

- **判断**：三种可能——库本身是 CommonJS 产物、引入了带副作用的模块、或者把 namespace 又 `export` 了出去。
- **展开**：实测同一份 20 函数的工具模块，全量引入 2509 字节 vs 具名引入 165 字节（差 15 倍）；但 `import * as utils` 再 `export { utils }` 会让打包器无法证明外部不会访问 `utils.utilN`，只能全留。顶层有副作用的模块（如 `window.x = true`）整块保留。
- **边界**：`sideEffects` 是给打包器的承诺——数组外的文件可视为无副作用、整块删除；写错方向会删掉必须保留的代码。追问：怎么验证到底摇掉了没有？→ 直接读产物搜那个函数名或字符串常量。

### Q33（8.2）｜ 场景：要做一个「按需引入」的组件库（类似 babel-plugin-import），怎么实现？

- **判断**：两种路线——编译期改写 import（Babel/SWC 插件），或纯 ESM + `sideEffects: false` 让打包器自己摇。
- **展开**：①插件路线：在 visitor 里拦截 `ImportDeclaration`，把 `import { Button } from 'ui'` 改写成 `import Button from 'ui/es/button'` 并补上样式 import，靠 `t.isImportDeclaration` 判断、`path.replaceWithMultiple` 替换；②摇树路线：库以 ESM 发布、每个组件独立文件、声明 `sideEffects` 只保留样式文件，消费方具名引入即可。
- **边界**：插件路线要防重复遍历（替换后的节点会再次进入 visitor）；样式文件的副作用必须保留，否则样式会被摇掉。追问：现在更推荐哪种？→ 摇树路线。现代打包器对 ESM 的支持已经足够好，少一层编译插件就少一处出错点。

### Q34（8.3）｜ 代码分割减小体积了吗？收益到底在哪？

- **判断**：**不减小总量，改的是体积的分布**——把非首屏代码挪出首屏。
- **展开**：实测同一场景，不分割时首屏 2946 字节；开启分割后入口 chunk 175 字节、utils chunk 1939 字节，首屏从 2946 降到 175。
- **边界**：分割会引入 chunk 边界的胶水代码，总字节可能反而变大；几十字节的 chunk 是负收益。追问：vendor 抽出来就一定快吗？→ 不一定，收益来自 vendor 的 hash 长期不变（缓存命中），依赖一升级就整体重打。

### Q35（8.3）｜ 编译产物太大，压缩能救吗？

- **判断**：**压缩不能替代 tree-shaking**——它只把已经在那里的代码写得更短。
- **展开**：实测 A（全量）2509 → 1714 字节，B（按需）165 → 84 字节；压缩后 A 仍是 B 的 20 倍。
- **边界**：压缩后的数字才接近传输体积，但还不等于——还要过 gzip/brotli。做体积门槛时全团队要统一口径。追问：现代语法产物能省多少？→ 省的是降级代码与 polyfill：实测同一段 `??`，target esnext 82 字符 vs es2015 685 字符（要注入运行时辅助）。

### Q36（8.3）｜ 场景：要给团队做一个「构建产物体积门禁」，怎么设计？

- **判断**：三件事——定口径、定基线、定动作；口径不统一的门禁一定会误杀。
- **展开**：①口径统一为「压缩后（或压缩 + gzip 后）的产物字节数」，并写死在脚本里；②基线取「最近 N 次构建的中位数」而非固定值，避免单次波动；③超阈值时在 CI 输出「哪个模块涨了多少」（读 metafile / stats），而不是只报一个总数；④分级——小幅增长只警告，大幅增长才阻断。
- **边界**：不要对「未压缩产物」设门槛（压缩率会掩盖真实变化）；不要把 vendor chunk 和业务 chunk 混在一起判定（前者涨是依赖升级，后者涨是代码问题）。追问：为什么建议用中位数而不是平均值？→ 中位数不受单次异常构建影响，且能体现趋势漂移。

## 9. 手写 mini-bundler

### Q37（9.3）｜ 场景：线上偶发一个字段是 `undefined`，怀疑是循环依赖，怎么定位与处理？

- **判断**：循环依赖是「构建期本该暴露的错误被推迟成运行期 `undefined`」的典型来源；先确认链路，再改设计，兜底放最后。
- **展开**：ESM 的绑定是活绑定，`const` 导出还有 TDZ，读未初始化的绑定会**直接抛错**；打包成 CJS 后，运行时把「正在构建的模块」提前放进缓存，循环引用拿到的是**半成品 exports**，读不到就是 `undefined`。实测对照：同一份源码，原生 ESM 抛 `ReferenceError: Cannot access 'A_NAME' before initialization` 并中止，打包产物静默打印 `undefined` 并一路跑完。
- **边界**：函数声明有提升，循环里读函数**看起来是正常的**（实测原生读到 `function`），最容易掩盖问题；所以「本地能跑通」不能当作没有循环依赖的证据，要查模块图而不是查现象。追问：确认了循环依赖但一时改不动怎么办？→ 把顶层的读取改成函数内部的延迟求值（或改成依赖注入传参），让引用发生在两个模块都初始化之后。
