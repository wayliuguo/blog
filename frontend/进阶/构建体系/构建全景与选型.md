# 构建全景与选型

构建工具这几年换了三轮：从"任务流"到"打包器"再到"原生 ESM 开发服务器"。工具越换越快，但要解决的问题从来没变——把**人写的源码**变成**浏览器能高效加载的产物**。本篇先把这条链路拆开，看清每个阶段到底做了什么，再谈选型：只有知道"慢在哪一步"，才能在 webpack / Vite / Rollup / esbuild 之间做出有理由的选择，而不是跟着流行走。

## 一、构建到底在做什么

不管用哪个工具，一次构建都是这四步：

```
源码（多文件、ESM/CJS/TS/JSX/Vue）
   │
   ├─ 1. 解析与建图：从入口出发，找到所有依赖，得到模块图（Module Graph）
   │
   ├─ 2. 转换：TS→JS、JSX→JS、新语法→旧语法、CSS 预处理 → 每个模块变成目标形态
   │
   ├─ 3. 拼装：把模块图按规则合并成一个或多个 chunk（产物文件）
   │
   └─ 4. 优化输出：tree-shaking、压缩、hash 命名、sourcemap、产物清单
```

四步里**真正耗时的分布**决定了工具的速度差距：

| 阶段 | 传统打包器（webpack） | 原生 ESM 开发服务器（Vite） |
| ---- | ---- | ---- |
| 解析与建图 | 启动时全量做一遍 | 开发时按需做（浏览器请求到谁才转谁） |
| 转换 | 全量 | 按需 + 依赖预构建（esbuild） |
| 拼装 | 启动时全量 | 开发时不做（浏览器原生加载 ESM） |
| 优化输出 | 每次构建都做 | 只在 `build` 时做 |

这就是"开发启动慢 vs 开发启动快"的根因：**开发态要不要拼装**。webpack 在 `dev` 时也要先把整个应用拼出来才能服务；Vite 直接把源文件当 ESM 交给浏览器，一个模块一个请求。

## 二、为什么非构建不可

如果浏览器已经原生支持 ESM，能不能不构建？对**生产环境**来说不行，四个理由：

1. **模块数量**：一个中型应用 1500+ 个模块，不合并就是 1500 个 HTTP 请求，HTTP/2 也扛不住（仍有头部开销、连接复用上限、服务端渲染水合成本）。
2. **语法与运行时**：TS、JSX、装饰器、新语法需要转换；旧浏览器需要降级与 polyfill。
3. **非 JS 资源**：CSS、图片、字体、WASM 要变成可引用的产物。
4. **体积**：tree-shaking、压缩、常量折叠这些只有构建期能做。

反过来说，**开发环境**可以少做：少做就快，快就反馈及时。这是 Vite 一类工具的全部出发点。

## 三、三代工具的演进逻辑

| 代际 | 代表 | 核心思路 | 被取代的原因 |
| ---- | ---- | ---- | ---- |
| 任务流 | Grunt / Gulp | 把"编译、拼接、压缩"串成任务 | 不解析依赖关系，模块的加载顺序要人肉维护 |
| 打包器 | webpack / Rollup / Parcel | 从入口解析依赖图，产出 bundle | 应用规模变大后，冷启动与热更新越来越慢 |
| 原生 ESM + 原生语言 | Vite / esbuild / Rspack | 开发态不打包；转换阶段用 Go/Rust/原生编译 | — |

第三代不是"打包器被淘汰"，而是**把打包从开发态挪走**：生产构建依然要打包，只是开发时不再为它付费。

> 版本事实（本仓实测）：Vite 8.3.0 起，生产构建的默认打包器已换成 **Rolldown**（Rust 实现的 Rollup 兼容版），配置项仍写作 `build.rollupOptions`。所以"Vite 生产走 Rollup"这句话在 8.x 上已经不准确，详见[Vite](./Vite.md)篇。

## 四、实测：同一份源码，三个工具的差距

先造一份有代表性的样本：200 个模块组成的链式依赖，每个模块导出一个被用到的函数、一个没被用到的函数和一个数组——用来同时观察耗时与 tree-shaking。

> 摘自 `./code/build-lab/bench/gen.cjs`（运行：`npm run bench`）

```js
// m${i}.js
export function used(x) {
    return x + ${i}
}

export function unused${i}() {
    return '这段应该被 tree-shaking 摇掉 ${i}'
}

export const big${i} = [${Array.from({ length: 20 }, (_, k) => k + i).join(', ')}]
${next}
```

每个工具跑在独立子进程里（避免模块缓存与堆内存互相影响），跑两次取第二次：

> 摘自 `./code/build-lab/bench/one.cjs`（运行：`npm run bench`）

```js
if (tool === 'esbuild') {
    const esbuild = require('esbuild')
    esbuild.buildSync({
        entryPoints: [entry],
        bundle: true,
        format: 'esm',
        minify: false,
        outfile: outFile,
        logLevel: 'silent'
    })
    done()
}
```

实测输出（Node 22.22.2 / i7-7700HQ / 8 核）：

```
---- 同一份源码（200 个模块）构建对比（第二次运行）----
工具                                构建耗时       进程总耗时        产物含 unused
esbuild                         557 ms      958 ms    0.2 KB  false
rollup                         1303 ms     1695 ms    0.2 KB  false
webpack + sideEffects:false    2783 ms     3210 ms    0.7 KB  true
webpack                        3698 ms     4104 ms    0.7 KB  true
webpack + minimize             4431 ms     4790 ms    0.0 KB  false

---- 结论（由上面的实测数据推导）----
最快/最慢倍数： 8.0x
摇掉了未使用代码： esbuild / rollup / webpack + minimize
仍保留未使用代码： webpack / webpack + sideEffects:false
webpack 的 tree-shaking 是"标记 + 压缩器删除"两步：关掉 minimize 就只剩标记
```

这组数据有三个值得记住的点：

1. **8 倍差距**来自"谁做的活少"：esbuild 用 Go 写的原生代码，转换与拼装都在进程内一次完成；webpack 要走一遍完整的插件流水线。
2. **"构建耗时"和"进程总耗时"差了 400ms 左右**——这是 Node 启动 + 加载工具自身模块的固定成本。CI 上对比工具时只看构建耗时会低估这个成本。
3. **webpack 那两行 `true` 是最容易被误解的地方**，见下一节。

## 五、tree-shaking 的真相：标记与删除是两步

很多人以为 webpack 不做 tree-shaking，或者以为加 `sideEffects: false` 就够了。实测给出了否定答案：**光声明 `sideEffects: false` 并没有摇掉，只有开启压缩（minimize）之后才摇掉**。

原因是 webpack 的 tree-shaking 分成两步：

```
1. usedExports 分析（构建期）：标记"这个导出没人用"  ← 只标记，不删
2. 压缩器删除（Terser / SWC）：把标记为未使用的代码真正删掉  ← 真正瘦身的那一步
```

关掉 `minimize` 时只做了第一步，产物里当然还留着。而 esbuild / Rollup 把这两步合在自己的流水线里，所以 `minify: false` 也能删。

由此得到一条实践规则：**评估打包体积必须开压缩看**，用未压缩产物判断"有没有摇掉"会得出完全错误的结论。

> 摘自 `./code/build-lab/bench/one.cjs`（运行：`npm run bench`）

```js
const hasUnused = fs.existsSync(outFile)
    ? fs.readFileSync(outFile, 'utf8').includes('这段应该被 tree-shaking 摇掉')
    : null
```

注意这里检测的是**字符串常量**而不是函数名：压缩会重命名标识符，但不会动字符串。用 `unused` 去搜压缩产物会得到"摇掉了"的假阳性。

## 六、怎么选：先回答三个问题

选型不是比谁快，是比谁能满足你的产物形态：

| 问题 | 答案指向 |
| ---- | ---- |
| 产出的是**应用**还是**库**？ | 应用 → Vite / webpack；库 → Rollup / tsdown |
| 需要**兼容到多老的浏览器**？ | 需要 IE11 或很老的 WebView → webpack（生态最全）；只需现代浏览器 → Vite |
| 团队能否接受**双引擎**（开发 esbuild、生产 Rollup）？ | 不能接受"开发和生产行为可能不一致" → webpack 单引擎 |

具体判断：

- **业务应用，现代浏览器**：Vite。开发体验优势是数量级的，生产构建走 Rolldown/Rollup，产物质量不打折。
- **业务应用，需要复杂资源处理 / 微前端 Module Federation**：webpack。MF 的运行时共享能力目前仍是 webpack 最成熟。
- **组件库 / SDK / npm 包**：Rollup（或基于它的 tsup / tsdown）。输出格式齐全（esm/cjs/umd/iife），tree-shaking 最干净，产物里没有 webpack 运行时。
- **内部工具链、批量转换、CI 里的语法降级**：esbuild 直接调用，别拿它当完整构建器。
- **超大型已有 webpack 项目，想提速又不敢重写**：Rspack（webpack 配置的 Rust 实现，兼容大部分 loader/plugin）。

一个常见误区是"Vite 比 webpack 快所以全量迁移"。Vite 快的是**开发态**（按需转换）；生产构建的耗时与产物形态取决于它背后的打包器（8.x 是 Rolldown）。迁移真正要评估的是插件生态与自定义 loader 的替换成本。

## 七、Rust 工具链全景

上一节的方法论落到"用原生语言重写工具链"这个既定事实上，就是这张全景。"Rust/Go 工具链"不是单一工具，而是**按职责替换 JS 工具**的一套组合：

| 工具 | 语言 | 替换谁 | 成熟度 | 落地建议 |
| ---- | ---- | ---- | ---- | ---- |
| SWC | Rust | Babel | 高（Next.js 默认） | 新项目直接用；老项目先做产物对比 |
| esbuild | Go | 转换 + 打包 | 高（Vite 预构建） | 工具链、预构建、内部工具 |
| Rspack | Rust | webpack | 中高 | webpack 项目提速，配置基本兼容 |
| Rolldown | Rust | Rollup | 中（Vite 8 起默认生产打包器） | 跟着 Vite 走即可 |
| Turbopack | Rust | webpack（Next.js 场景） | 中 | Next.js 项目可用，独立使用慎重 |
| Biome | Rust | ESLint + Prettier | 中 | 新项目可试；存量规则迁移成本高 |
| Oxlint | Rust | ESLint | 中 | 作为 CI 的"快速第一道检查"很好用 |

选型时最该问的不是"谁更快"，而是**替换成本**：

- **配置兼容性**：Rspack 兼容大部分 webpack 配置，但专有 loader/plugin 要逐个验证。
- **行为一致性**：Rust 版工具与 JS 版在边界行为上可能有差异（比如对某些提案语法的处理）。迁移前必须做产物对比（同一份源码两边产物 diff + 跑测试）。
- **生态插件**：Babel 插件生态是十年积累，SWC 的插件需要用 Rust 写或走 `swc-plugin`——这是最大的迁移阻力。

一个务实的中间路线：**让快工具做它最擅长的那一环**。Vite 就是典型——esbuild 负责预构建与单文件转换，Rolldown/Rollup 负责生产打包。不是每家公司都要全套替换。

> 关于速度差距更细的实测：单文件转换 SWC 是 esbuild 的约 12 倍（Node 原生插件 vs 跨进程 Go 二进制），但整包构建 esbuild 反而更快——详见[esbuild](./esbuild%20与%20Rust%20工具链.md)篇的实测。

## 八、构建与架构的接口

构建产物形态会反过来约束部署与架构，这层关系常被忽略：

| 构建决策 | 被约束的下游 |
| ---- | ---- |
| 是否代码分割 | 路由级懒加载能否生效、首屏体积 |
| hash 策略（contenthash / chunkhash） | CDN 缓存命中率与回滚方式 |
| 输出 ESM 还是 CJS | 能否用 `<script type="module">`、能否被 Node 直接 require |
| 是否多入口（MPA） | 按页发布、按页回滚的粒度 |
| 是否注入运行时（webpack runtime） | 微前端共享、长缓存策略 |

所以"选构建工具"从来不是单点决策，它决定了后面缓存、发布、监控三件事的做法。
