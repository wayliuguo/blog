# 直播技术方案

> 级别：中级→高级

按本书四层推进：

- **入门使用**：看懂直播"推流 → 转码 → 分发 → 拉流"整体链路，以及各推送 / 拉取协议的关系；
- **进阶**：理解 HLS 分片与 HTTP-FLV 边下边播为何延迟不同，掌握低延迟直播方案（LL-HLS、WebRTC）的原理；
- **实战**：掌握流生命周期状态机，以及秒开、卡顿排查、追帧这三大直播实战问题的解法；
- **最小实现掌握原理**：到 `code/frontend/16-media` 打开 `mse-hls.html`，用 `appendBuffer` 模拟"分片边下边播"，体会 hls.js / flv.js 在浏览器里替代原生支持的底层来源。

直播与点播最大的差异是"实时性"与"一次性消费"：数据不能提前全部缓冲，延迟每分每秒都敏感。本章从直播整体链路、各协议对比、低延迟方案、流生命周期，到秒开/卡顿/追帧等常见问题，梳理一条从推流到播放的完整技术路线。

## 一、直播链路总览

一条标准直播链路由"推、转、分、拉"四段组成：

```text
采集(摄像头/采集卡) ──推流──▶ 源站 RTMP/RTP
                                │ 转码(转码+多码率+GOP)
                                ▼
拉流(Safari原生HLS / hls.js / flv.js / WebRTC) ◀──分发CDN(边缘节点)◀── 源站切片/封装
```

| 环节 | 职责 | 常用协议/组件 |
| --- | --- | --- |
| 推流 | 把采集到的 A/V 推到服务器 | RTMP / SRT / WebRTC |
| 转码 | 多码率、低延迟、加字幕广告 | FFmpeg / 云转码 |
| 分发 | CDN 边缘缓存、就近拉流 | 阿里云/腾讯云直播 CDN |
| 拉流 | 播放端拉取并渲染 | HLS / HTTP-FLV / WebRTC |

关键概念：**推流地址**（含 streamKey）用于鉴权，**播放地址**（含 hls/flv 不同后缀）面向观众。CDN 负责把"一份推流"复制到全球多处缓存。

## 二、协议对比

### 1. 推流协议

| 协议 | 传输 | 延迟 | 特点 |
| --- | --- | --- | --- |
| RTMP | TCP | 1-3s | 最老牌推流，Adobe 相关已废弃但生态仍在 |
| SRT | UDP | 0.5-1s | 抗弱网、开源、适合公网推流 |
| RTSP | TCP/UDP | 亚秒 | 安防/IPC 摄像头天然支持 |
| WebRTC | UDP | <500ms | Web 端通用，但推流方多为 H5 |

### 2. 拉流协议对比（重点）

| 协议 | 传输 | 端到端延迟 | 浏览器支持 | 适用 |
| --- | --- | --- | --- | --- |
| HLS | HTTP(TS/fMP4) | 5-30s | iOS 原生 | 兼容大王、超大规模 |
| FLV (HTTP-FLV) | HTTP | 2-5s | 需 MSE+flv.js/mpegts.js | Web 低延迟主流 |
| MPEG-DASH | HTTP | 2-8s | 需 MSE+dash.js | 标准自适应 |
| WebRTC | UDP | 0.3-1s | 原生 | 极低延迟互动 |

**选型口诀**：

- 要**兼容 + 大规模点播式直播**（如营销投放）→ HLS。
- 要**Web 端低延迟**（如购物、秀场）→ HTTP-FLV（mpegts.js）。
- 要**互动级别低延迟**（如连麦、实时答题）→ WebRTC。

### 3. 为什么 HTTP-FLV 延迟低于 HLS

HLS 以 `m3u8` 里的分片为单位配置，会额外缓冲 1~2 个分片（每个分片通常 2-6s），延迟 = 分片时长 × (1~2) + CDN 缓存。HTTP-FLV 是**边下边播的流式**，小分片并开启 `low latency` 可以显著压到 2s 内。

## 三、低延迟直播方案

### 1. 延迟构成

```text
总延迟 ≈ 采集编码延迟 + 推送网络延迟 + 服务端转码/切片延迟 + CDN缓存 + 播放器缓冲
```

每一步都在加延迟，逐项优化才能降到 1s 内。

### 2. 降低延迟的常见手段

| 手段 | 消减的延迟 | 实施 |
| --- | --- | --- |
| 切小分片 | 播放器缓冲 | HLS 分片缩到 1-2s |
| GHLS（分组 HLS） | 推送队列 | 分组并行分片 |
| Low-Latency HLS (LL-HLS) | 分段即出 + 长会话 | 部分支持 |
| HTTP-FLV + 立即启动 | 播放器缓冲 | fetch 拉起首片即播 |
| WebRTC | 全链路 | P2P/SFU 亚秒级 |
| CDN 边缘缓存抖动 | 缓存 | 开低延迟缓存策略 |

### 3. WebRTC 低延迟拉流

对**连麦/互动**，拉流端可直接用 WebRTC 接 SFU，媒起到"播放即 P2P/SFU"的亚秒级效果：

```js
const pc = new RTCPeerConnection({ iceServers });
const video = document.getElementById('live');
pc.ontrack = ev => video.srcObject = ev.streams[0];
// 通过信令交换 offer/answer 拿到远端直播流
// 配合 Simulcast，可动态在 360p/720p 间降码率保证流畅
```

## 四、直播流生命周期

直播流进入与退出都要有明确的状态管理，防止"流失效但仍显示 loading"。

### 1. 状态机

```text
loading(检测中) ──▶ playing(可播)
    │                  │
    ├──▶ stalled(卡顿)  └──▶ ended(主播结束)
    │                  │
    └──▶ error(拉不到) └──▶ retrying(超时重试N次后转 error)
```

### 2. 见流检测（首帧）

用 `onWaiting`/`stalled` 判断视频卡在哪个阶段不合理。直播见流通常以 `playing` 事件 + `currentTime` 增长为准：

```js
video.addEventListener('playing', () => setState(State.PLAYING));
video.addEventListener('stalled', () => setState(State.STALL));
video.addEventListener('error', () => {
  if (state === State.LOADING) retry(nextAttempt()); // 拉流的可重试
  else showError();
});
```

### 3. 生命周期事件

- **预推流**：直播开播前推流端需先连上行，才能降低开播等待。
- **直播中**：播放器持续 append，需防内存无限增长（见 Buffer 一章）。
- **主播结束**：服务器回一段 `END/` 空流或 `m3u8` 结尾标记，播放器进入 `ended`。
- **录制与回放**：同一路可同时出点播（录制成 MP4/HLS）。

## 五、直播常见问题

### 1. 秒开（首帧快）

秒开 = 从点击到出画面的时间。优化点：

- 优先取最近 I 帧：网络层让**分片边界对齐关键帧**，播放器从距离最近的 I 帧开始（别从 GOP 中间硬解出糊帧）。
- 首片预热：拉流前提前请求第 0 片。
- 封面图 `poster`：见流前先展示海报而非黑屏。
- CDN 就近与边缘缓存策略。

### 2. 卡顿（Buffer starvation）

原因：网络带宽 < 码率，或 Buffer 空、FPS 掉。排查序列：

```text
1) 看带宽 vs 当前档位码率
2) 看 buffered 是否持续为空 → 网络跟不上则降码率
3) 看 framesDropped / framesDecoded → 是解码卡还是传输卡
4) 看 CPU/内存 → 软解超高导致渲染掉帧
```

多档位 ABR 是兜底：网络差时切低档位，保持"能看但不卡"。

### 3. 追帧（追上实时进度）

直播时观众点一下，会从缓存的靠后位置跳到**尽可能接近边缘的位置**，尽可能减少积压延迟，这份动作叫"同步对齐/追帧"。常见"直播秒追"按钮即此逻辑：

```js
function catchUp(video) {
  const edge = video.buffered.length ? video.buffered.end(video.buffered.length - 1) : 0;
  const target = Math.max(edge - 0.5, video.currentTime); // 追到缓冲边缘前 500ms
  video.currentTime = target;
}
```

### 4. 直播 vs 点播体验差异表

| 维度 | 直播 | 点播 |
| --- | --- | --- |
| 延迟目标 | 越低越好 | 无所谓 |
| 重试 | 可无限重试（随时可能在播） | 简单重试 |
| 缓冲策略 | 不宜过大（追真实时） | 越大越好 |
| ABR | 强依赖（主播主播动态） | 可按位率档切 |
| 推流 | 需上行设备 | 无 |

## 最小实现：分片边下边播的最小原理

到 `code/frontend/16-media` 打开 `mse-hls.html`，它模拟了直播拉流端在浏览器里最核心的机制：从"网络分片"逐段取数据、`appendBuffer` 进 `SourceBuffer`，让 `<video>` 随到随播——这正是 HTTP-FLV（flv.js / mpegts.js）和 HLS（hls.js）拉流端做的事。

- HLS 延迟高，是因为它按"整段分片 + 额外缓冲 1~2 片"交付；HTTP-FLV 采用更细粒度、边下边播，所以延迟更低。demo 演示的正是"JS 控制喂数据节奏"这一层。
- 理解"分片边界对齐关键帧""buffer 不能无限增长"，就容易看懂直播的秒开与卡顿优化。

原理一句话：直播拉流端 = 网络分片 + `appendBuffer` 喂给 MSE；谁能更快、更准地喂到 `<video>`，谁的延迟就更低——这是把 HLS / HTTP-FLV / WebRTC 拉流串起来的统一底座。若浏览器不支持 MSE，demo 会显示友好提示。
