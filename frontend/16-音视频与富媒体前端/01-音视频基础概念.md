# 音视频基础概念

> 级别：中级

按本书四层推进：

- **入门使用**：看懂视频编码为何存在、I/P/B 帧与 GOP、封装格式，理解"编码 vs 封装"的分工；
- **进阶**：掌握码率 / 分辨率 / 帧率三者的联动关系，能读懂时间戳（PTS/DTS）与软硬解取舍；
- **实战**：用 `canPlayType` / MediaCapabilities 在当前浏览器做真实编解码能力检测与降级选型，理解 MSE 的定位；
- **最小实现掌握原理**：到 `code/frontend/16-media` 打开 `mse-hls.html`，用 MediaSource 把分片数据喂给 `<video>`，亲手体会"浏览器只负责解封装 + 解码 + 渲染"这一本章最核心的边界。

音视频是富媒体前端的地基。不理解"视频是怎么压缩和封装的"，就谈不上做播放器、直播和性能优化。本章从编码原理、封装格式、码率/分辨率、浏览器编解码能力四个维度，把音视频最核心的概念一次讲透，并不涉及具体浏览器 API 的深度使用。

## 一、视频编码原理

### 1. 为什么需要视频编码

一段原始视频体积巨大。以 1080p、30fps、24bit 色彩为例，一帧图像的裸数据量为：

```text
1920 × 1080 × 3（RGB 三通道）≈ 6.2 MB
每秒：6.2 MB × 30 = 186 MB/s
一分钟：186 MB × 60 ≈ 11 GB/min
```

一小时就是 660 GB 左右，完全不可传输。**视频编码的本质是牺牲一部分人眼不可感知的细节，换取几十到几百倍的压缩率。**

### 2. 空间冗余与时间冗余

视频压缩主要利用两类冗余：

| 冗余类型 | 来源 | 压缩手段 |
| --- | --- | --- |
| 空间冗余 | 单帧内相邻像素相似 | 帧内压缩（Intra） |
| 时间冗余 | 相邻帧内容高度相似 | 帧间压缩（Inter） |
| 视觉冗余 | 人眼对高频、色彩不敏感 | 量化、色彩二次采样 |
| 熵冗余 | 编码符号非等概率 | 熵编码（Huffman / CABAC） |

### 3. H.264 / H.265 / AV1 对比

| 编码器 | 发布日期 | 压缩效率（相对 H.264） | 硬件支持 | 授权费用 | 适用场景 |
| --- | --- | --- | --- | --- | --- |
| H.264 (AVC) | 2003 | 基准 | 全平台 | 有专利费 | 直播/点播兼容之王 |
| H.265 (HEVC) | 2013 | 提升约 50% | 移动端较全 | 授权复杂、贵 | 4K/8K |
| VP9 | 2013 | 与 HEVC 相仿 | Chrome 系强 | 免费 | YouTube 主力 |
| AV1 | 2018 | 比 HEVC 再提升 20-30% | 逐步普及 | 免费（ROI 有个别收费） | 下一代 Web 主力 |

> 选型速记：**兼容性选 H.264，免费+Chrome 系选 VP9/AV1，追求 4K 极致体积选 HEVC。** 前端实际做法是"多重编码 + 能力检测降级"。

### 4. 帧类型：I / P / B 帧

- **I 帧（关键帧/IDR）**：完整编码一帧图像，不含任何帧间参考，体积最大，是随机访问（seek）的入口。
- **P 帧（预测帧）**：只编码与前一参考帧的差异，体积小。
- **B 帧（双向预测帧）**：参考前后两个方向，压缩率最高，但**引入延迟**（显示顺序和编码顺序不一致），低延迟场景常禁用 B 帧。

```text
编码传输顺序（B 帧导致重排）：
显示顺序：   I1  B2  B3  P4  B5  B6  P7
编码顺序：   I1  P4  B2  B3  P7  B5  B6
```

**GOP（Group of Pictures，图像组）** 指从 I 帧开始到下一个 I 帧前的全部帧序列，例如 `GOP = 250` 即每 250 帧出现一个 I 帧。GOP 越大压缩率越高，但 seek 到中间帧需要回溯到最近的 I 帧解码，**随机访问延迟越大**；GOP 越小越利于秒开与直播追帧。

### 5. 一个 H.264 NAL 单元的结构

```text
[start_code 0x00000001]  NAL header(1字节)  RBSP(原始字节序列负载)
                        [forbidden_zero_bit|nal_ref_idc(2bit)|nal_unit_type(5bit)]
```

常用 `nal_unit_type`：`7 = SPS`（序列参数集）、`8 = PPS`（图像参数集）、`5`=IDR 帧、`1`=非 IDR 切片、`6`=SEI。SPS/PPS 描述分辨率、帧率、profile 等关键信息，**解码器必须先拿到 SPS/PPS 才能解 I 帧**，这在 FLV/TS 流的头字段解析中非常关键。

## 二、音频编码

### 1. 采样率、位深与声道

- **采样率**：每秒采样的次数，常见 44100Hz（CD）、48000Hz（视频标准）、96000Hz（HiFi）。
- **位深**：每个采样的量化比特数，常见 16bit、24bit。
- **声道**：单声道(1)、双声道立体声(2)、5.1(6)、7.1(8)。

```text
码率 = 采样率 × 位深 × 声道数
例：48000 × 16 × 2 = 1,536,000 bps ≈ 1.5 Mbps（PCM 无压缩）
```

### 2. 常见音频编码对比

| 编码 | 是否无损 | 典型码率 | 特点 |
| --- | --- | --- | --- |
| PCM | 无损 | 1.4 Mbps+ | 裸采样，无压缩 |
| MP3 | 有损 | 128-320 kbps | 最普及 |
| AAC | 有损 | 128-256 kbps | 效率高于 MP3，HLS 常用 |
| OPUS | 有损 | 6-510 kbps | 实时性极佳，WebRTC 首选 |
| FLAC | 无损 | 800-1000 kbps | 无损压缩 |

> 前端重点掌握 **AAC（点播/直播音频轨）** 与 **OPUS（WebRTC 通话）**，其余了解即可。

## 三、封装格式

### 1. 封装 vs 编码

**编码格式（Codec）**解决"画面/声音怎么压缩"，**封装格式（Container）**解决"压缩后的数据怎么组织和描述"。一个容器里要有：

- 视频轨 + 音频轨（可能有多路字幕、元数据）
- 各轨的 Codec 类型、采样信息
- 同步用的时间戳 PTS/DTS
- 分片索引（便于定位和 seek）

### 2. 主流容器对比

| 容器 | 扩展名 | 微软/HLS 场景 | 优点 | 缺点 |
| --- | --- | --- | --- | --- |
| MP4 | .mp4 | 点播/最通用 | 兼容性最好 | 需完整 moov 才能播放 |
| WebM | .webm | 网页 | 开源免授权 | 主要支持 VP8/VP9/AV1 |
| FLV | .flv | 直播 | HTTP-FLV 低延迟利器 | 结构老旧 |
| TS | .ts | HLS 分片 | 抗丢包、HLS 标准 | 冗余高 |
| Matroska | .mkv | 非 Web | 功能强大 | 浏览器不支持 |

### 3. MP4 的 moov/ftyp/mdat

MP4 是 box 结构，关键 box 有：

- **ftyp**：文件类型与兼容性声明
- **moov**：元数据（含 mvhd、trak、stbl），**包含全部帧的位置和时长索引**
- **mdat**：真正的音视频数据

```text
[ftyp] [moov] [mdat ...]     ← moov 在前：可流式播放、秒开快
[ftyp] [mdat ....] [moov]    ← moov 在后：需下载完整文件才能播放（糟糕）

优化：转码时把 moov 前置（-movflags faststart），是 HTML5 秒开的关键优化之一。
```

## 四、码率、分辨率与帧率

### 1. 码率（Bitrate）

单位是 `bps`（bit per second），描述单位时间的数据量。码率越大画质越好、体积越大。需要区分：

- **恒定码率 CBR**：码率稳定，网络友好但浪费码率。
- **可变码率 VBR**：按场景复杂度分配码率，同体积下画质更好。
- **限制码率 CRF/VBV**：折中方案，兼顾码率上下限。

### 2. 自适应码率（ABR / 多码率）

同一内容生成多档分辨率与码率（如 240p~1080p），播放器根据网络动态切换，是 HLS 秒级核心机制：

| 档位 | 分辨率 | 推荐码率 | 场景 |
| --- | --- | --- | --- |
| 低 | 480p | 0.6-1 Mbps | 弱网 |
| 中 | 720p | 1.5-2.5 Mbps | 标清 |
| 高 | 1080p | 4-6 Mbps | 高清 |
| 4K | 2160p | 15-25 Mbps | 超高清 |

### 3. 分辨率与帧率

- **分辨率**：画面的像素尺寸，如 1920×1080。画质的关键是**码率是否匹配分辨率**，分辨率高但码率不足反而更糊。
- **帧率（fps）**：每秒画面帧数。电影 24fps、网页默认 30fps/60fps。帧率影响流畅度，也直接影响编码码率。
- **像素密度**：移动端要看 DPR 与 Viewport，避免 2x 屏拉大低分辨率视频造成模糊。

## 五、浏览器支持的编解码与 MSE

### 1. 编解码器支持表（概要）

| 容器 | 视频编码 | 音频编码 | Chrome/Safari/Firefox |
| --- | --- | --- | --- |
| MP4 | H.264 | AAC | 全部支持 |
| MP4 | HEVC | AAC | Safari ✅ / Chrome 视平台 |
| WebM | VP9 | Opus | Chrome/FF ✅ / Safari 部分 |
| WebM | AV1 | Opus | Chrome/FF 支持，Safari 较新才支持 |
| TS | H.264 | AAC | HLS（Safari 原生） |

### 2. 使用 `canPlayType` 与 Media Capabilities 做能力检测

```js
const v = document.createElement('video');

// 传统方式：返回“probably”“maybe”“”三种
console.log(v.canPlayType('video/mp4; codecs="avc1.42E01E"'));
console.log(v.canPlayType('video/webm; codecs="vp9"'));
console.log(v.canPlayType('video/mp4; codecs="hev1.1.6.L120.90"'));

// 现代方式：Media Capabilities 能给出真实解码能力与性能档位
if (navigator.mediaCapabilities) {
  const res = await navigator.mediaCapabilities.decodingInfo({
    type: 'file',
    video: { contentType: 'video/mp4; codecs="avc1.42E01E"', width: 1920, height: 1080, bitrate: 5000000, framerate: 30 },
    audio: { contentType: 'audio/mp4; codecs="mp4a.40.2"' },
  });
  console.log('支持:', res.supported, '流畅:', res.smooth, '省电:', res.powerEfficient);
}
```

### 3. MSE（Media Source Extensions）

**MSE 是前端播放协议流（HLS/FLV/MPEG-DASH）的关键前提**：浏览器原生不支持 HLS/FLV 分片，但 MSE 允许 JS 把分片数据 `appendBuffer` 进一个 `SourceBuffer`，浏览器再次完成"解封装+解码+渲染"。它使普通 `<video>` 摇身一变成为可编程播放器内核。

```html
<video id="mse"></video>
<script>
  const video = document.querySelector('#mse');
  if (window.MediaSource && MediaSource.isTypeSupported('video/mp4; codecs="avc1.42E01E"')) {
    const ms = new MediaSource();
    video.src = URL.createObjectURL(ms);
    ms.addEventListener('sourceopen', () => {
      const sb = ms.addSourceBuffer('video/mp4; codecs="avc1.42E01E"');
      // 之后不断 fetch 分片并 fetch(data).then(buf=>sb.appendBuffer(buf))
    });
  }
</script>
```

MSE 的 `appendBuffer`、`removeBuffer` 与 Buffer 水位管理，是后面"播放器架构"一章的核心内存机制。

## 六、时间戳：PTS 与 DTS

- **DTS（Decode Time Stamp）**：解码顺序的时间戳。
- **PTS（Presentation Time Stamp）**：显示顺序的时间戳。
- B 帧会导致 PTS 与 DTS 不同；无 B 帧时二者一致。同步用 PTS，解封装传输按 DTS 排序。

```text
HLS/MP4 里时间基（timescale）常见 90000（TS）或 1000/15360（MP4）。
播放器需把时间基统一换算成毫秒，才能正确 seek 与音画同步。
// 换算：contractionMs = timestamp / timescale * 1000
```

## 七、软解与硬解

| 维度 | 软解（软件解码） | 硬解（硬件解码） |
| --- | --- | --- |
| 原理 | CPU 用解码库（ffmpeg wasm） | GPU/专用解码单元 |
| 性能 | 耗电、发热、卡顿高发 | 流畅省电 |
| 兼容 | 对编码格式宽容（如 HEVC 全解） | 依赖平台能力 |
| 典型场景 | 不支持的编码兜底 | 主流 H.264/HEVC/VP9/AV1 |

浏览器内无法直接指定"必须硬解"，但 `powerEfficient == true` 通常表示硬解可用，可作为决策参考。

## 最小实现：分片如何被喂给播放器

到 `code/frontend/16-media` 打开 `mse-hls.html`，它演示了本章"浏览器不支持 HLS/FLV 却能播放"的最小原理：先探测 `MediaSource` 是否可用，再 `appendBuffer` 把一段 `video/mp4` 分片数据推入 `SourceBuffer`，浏览器收到数据后自行完成"解封装 → 解码 → 渲染"。

- 网络上是 TS 分片的 HLS，浏览器原生不认；MSE 让 JS 把分片喂给 `<video>`，才把"能播哪种流"的主动权交给前端。
- 这正是 `canPlayType` 能力检测（原生能不能播）与 MSE（JS 硬灌数据）这两条路线的本质区别。

原理一句话：浏览器只负责解封装、解码、渲染，分片从哪来、以什么格式来，由 JS 用 MSE 决定——这就是"能力检测 + 封装控制"的最小闭环。若浏览器不支持 MSE，demo 会显示友好提示，页面文字始终可见。
