## 1. HTTP 与 HTTPS

### 1.1 HTTP 基础：无状态、报文与请求-响应模型

**HTTP 是无状态的应用层协议**，这是理解整个网络模块的起点：

- **无状态与身份模拟**：每个请求独立、服务器不记忆客户端；靠 Cookie / Session / Token **显式携带身份**来模拟"有状态"。
- **请求-响应模型**：客户端发起请求、服务端返回响应；明文传输是早期版本被窃听、篡改的根源（HTTPS 的由来）。

报文结构分三块：

```
请求报文   请求行 + 头 + 空行 + 体
             请求行 = METHOD + 路径 + HTTP版本
响应报文   响应行 + 头 + 空行 + 体
             响应行 = HTTP版本 + 状态码 + 描述
```

### 1.2 方法语义与幂等性

| 方法 | 语义 | 请求体 | 幂等 |
| ---- | ---- | ---- | ---- |
| `GET` | 取数据 | 无 | 是 |
| `POST` | 提交 / 创建资源 | 有 | 否 |
| `PUT` | 整体替换资源 | 有 | 是 |
| `PATCH` | 局部更新资源 | 有 | 通常否 |
| `DELETE` | 删除资源 | — | 是 |

- **幂等性的价值**：网络超时重试、用户重复点击时，靠幂等性做正确决策（重复 GET/PUT 不产生副作用）。
- **GET 与 POST 唯一本质差异是语义**，二者的传输安全性都由 HTTPS 提供。

### 1.3 状态码五类

| 大类 | 含义 | 常见状态码 |
| ---- | ---- | ---- |
| 2xx | 成功 | `200` 正常、`201` 已创建（POST 常用）、`204` 成功无内容（DELETE 成功） |
| 3xx | 重定向 | `301` 永久、`302` 临时、`304` 协商缓存命中（资源未变用缓存） |
| 4xx | 客户端错误 | `401` 未认证 `vs` `403` 无权限、`404` 不存在、`405` 方法不允许、`429` 限流 |
| 5xx | 服务端错误 | `500` 内部错误、`502` 网关收到无效响应、`503` 暂时不可用、`504` 网关超时 |

> 最容易混的一对：`401` 是"没认证"（未登录），`403` 是"没权限"（已登录但无授权）。

### 1.4 强缓存与协商缓存

两种缓存都要先分清"发不发请求"：

| 类型 | 判定头 | 命中表现 |
| ---- | ---- | ---- |
| 强缓存 | `Cache-Control`（相对时间，优先）`vs` `Expires`（绝对时间、依赖客户端时钟） | 命中不发请求，直接用本地副本 |
| 协商缓存 | `If-None-Match`（对应 `ETag`，内容指纹，优先）`vs` `If-Modified-Since`（对应 `Last-Modified`，秒级时间） | 一次条件请求，服务端回 `304` 后复用 |

**开发实践**：

```
静态资源  内容指纹文件名(app-5f8c2a.js) + 长 max-age → 内容变则文件名变、缓存自动失效
HTML      用 no-cache 保证每次拿到最新
```

### 1.5 HTTP 版本演进：消除队头阻塞

```
HTTP/1.1  Keep-Alive 持久连接 + 管线化；一个连接同时只处理一个请求
           队头阻塞 → 靠并发多连接(约6个)缓解
HTTP/2    二进制分帧 + 多路复用：一个 TCP 连接多个流交错传输，解决 HTTP 层队头阻塞
           配 HPACK 头部压缩 + 服务端推送
HTTP/3    传输层换 QUIC(基于 UDP)：内置 TLS 1.3、0-RTT 握手、连接迁移
           一个流丢包不影响其他流，彻底解决 TCP 层队头阻塞
```

### 1.6 HTTPS 与 DNS

- **混合加密**：非对称加密仅协商会话密钥，大量数据用对称加密（如 AES）传输，兼顾安全与性能。
- **CA 证书体系**：服务器向 CA 申请证书，客户端用内置根证书验证签名，防中间人冒充。
- **DNS 解析**：走"浏览器/系统缓存 → 本地 DNS 递归 → 根/顶级/权威迭代查询"把域名换成 IP；可用 `dns-prefetch` / `preconnect` 预解析预热。

### 1.7 TCP 与 UDP

| 维度 | TCP | UDP |
| ---- | ---- | ---- |
| 连接 | 面向连接（三次握手） | 无连接 |
| 可靠性 | 可靠（确认应答 / 超时重传 / 乱序重排） | 不可靠，丢包不重传 |
| 控制 | 有流量与拥塞控制 | 无 |
| 速度 | 较慢 | 快 |

- **粘包问题**：TCP 面向字节流、多条消息黏连要封包/拆包；UDP 面向报文、自带消息边界不会粘包。
- **选型**：HTTP / HTTPS / WebSocket / 文件传输走 TCP；实时音视频 / 直播 / DNS / 游戏走 UDP；QUIC 是"在 UDP 上自建可靠性"的折中。

### 1.8 WebSocket

- **定位**：复用 HTTP 握手（`Upgrade 101`）的全双工持久连接，服务器可主动推送；**无同源限制**但服务端要校验 `Origin`。

**四种即时通信方式对比**：

```
性能       WebSocket > SSE > 长轮询 > 短轮询
兼容性     反之；SSE 是单向流式 HTTP、实现简单且自动重连，但客户端不能推
```

- **工程要点**：断线重连（退避策略）、心跳保活防代理掐连接、`wss://` 加密、`Origin` 白名单。

## 2. HTTP/2 与 HTTP/3

### 2.1 HTTP/2 并发模型：多路复用

把「请求」从「连接」里解耦，一条连接上开任意多 stream。

| 场景 | HTTP/1.1 | HTTP/2 |
| ---- | ---- | ---- |
| 并发模型 | 一个连接同时只能处理一个请求，靠同域名 6 连接凑并发 | 多路复用，一条连接开任意多 stream |
| 实测 6 个 200ms 请求 | 单连接 1332ms · 六连接 231ms | 单连接 245ms（连接数 6 → 1） |

**连带结论**：域名分片、CSS 雪碧图、base64 内联这些「绕开 6 连接」的手段价值随之下降。

### 2.2 两种队头阻塞

队头阻塞分两层，HTTP/2 只解决其中一层：

| 层级 | 现象 | HTTP/2 的效果 |
| ---- | ---- | ---- |
| 应用层 | HTTP/1.1 一个连接一次只处理一个请求 | **消除** |
| TCP 层 | 字节流有序，一个报文丢了后面都要等重传 | **没有解决** |

- **应用层**：实测快请求被前面 500ms 的慢请求压到平均 617ms、最晚 678ms；HTTP/2 快请求 33ms 完成，慢请求自己在 500ms 后返回。
- **TCP 层**：HTTP/2 全跑在一条 TCP 上，丢包波及所有 stream；HTTP/1.1 多连接时反而只影响其中一条。

### 2.3 HTTP/2 的其它变化

- **二进制分帧**是基础：HEADERS / DATA 帧按 stream 编号交错。
- **HPACK 头部压缩**省掉大量重复头部，但压缩上下文是**连接级**的，带来 CRIME / BREACH 类攻击面。
- **`priority` 帧实现不一致**，控制首屏顺序还是靠 `preload` 与 `fetchpriority`。
- **服务端推送已被浏览器移除**，替代方案是 `103 Early Hints`。

### 2.4 HTTP/3 与 QUIC

把传输层从 TCP 换成基于 UDP 的 QUIC：

- **stream 级重传**：一条流丢包不影响其它流，这是 HTTP/2 解决不了的那一层。
- **握手更快**：TLS 1.3 内建；**0-RTT 恢复**的数据可被重放，只用于幂等请求。
- **连接迁移**：靠 Connection ID 而非四元组标识连接，Wi-Fi 切 4G 不用重新握手。
- **必须保留 HTTP/2 回退**：用 `Alt-Svc` 告知而不是强制，因为中间设备可能拦 UDP。

> ⚠️ **本机没有 QUIC 服务端，这一节不来自仓库实测**，属于规范与公开资料，不编数字。

### 2.5 工程落地

- **HTTP/2 实际使用必须 TLS + ALPN**；明文 h2c 只用于调试。
- **判断协议版本**：DevTools Network 的 Protocol 列（`h2` / `h3` / `http/1.1`），或 `curl -I --http2`。
- **打包策略**：请求数不再是核心指标，分包依据回到缓存命中率与首屏必需；正文压缩（gzip / brotli）仍必开。

## 3. CDN 与缓存体系

### 3.1 缓存的分层与判定规则

- **可能拦下请求的五层**：浏览器内存、磁盘、Service Worker、CDN 边缘、源站缓存。
- **判定规则同一套**：`Cache-Control` + `Age` + `ETag` / `Last-Modified`。
- **CDN 只是把同一套规则在离用户更近的机器上再跑一遍**。

### 3.2 三种缓存策略的取舍

| 策略 | 写法 | 行为（实测） | 收益 / 代价 |
| ---- | ---- | ---- | ---- |
| 强缓存 | `public, max-age=31536000, immutable` | 新鲜期内不发请求 | 收益最大；更新只能靠改 URL |
| 协商缓存 | `no-cache` + `ETag` | 200 / 2.5 KB → 304 / 0 B | **省正文不省 RTT** |
| 禁用 | `no-store` | 两次都是 200 / 54 B | 只给登录态、支付结果这类 |

**`no-cache` ≠ 不缓存**：它只是要求每次使用前必须校验。

### 3.3 协商缓存的成立条件

- **`ETag` 必须是内容指纹**：带随机数或时间戳就等于没配（实测对不上就回 200 全量 2.5 KB）。
- **`Last-Modified` 精度只到秒**，同秒内两次改动检测不到。
- **`ETag` 优先于 `Last-Modified`**：`If-None-Match` 会让服务端忽略 `If-Modified-Since`。
- **`Vary` 会进缓存键**：`Accept-Encoding` 正常，`Vary: User-Agent` 会让边缘命中率崩掉。

### 3.4 stale-while-revalidate

顶格写法 `max-age=60, stale-while-revalidate=600`，三个区间：

| Age | 区间语义 | 行为 |
| ---- | ---- | ---- |
| Age=30s | 新鲜期 | 不发请求 |
| Age=300s | 过期但在窗口内 | 先用旧的 + 后台刷新 |
| Age=1200s | 超出窗口 | 必须同步请求 |

- **适合**可容忍轻微延迟的列表与详情数据；**库存、余额、权限不行**。
- 配 `stale-if-error` 可在源站故障时继续兜底。

### 3.5 CDN 的三件额外事

- **缓存键由 CDN 配置决定**：忽略 query 参数要极谨慎，忽略掉身份参数就是安全事故。
- **有父层与回源分层**：源站 QPS 不涨不等于边缘命中，要看 `X-Cache` 与 `Age`。
- **刷新是异步的**：只刷新不带哈希的入口文件，其余靠内容哈希自然失效；发布前可预热热门资源。

### 3.6 落地清单与验收

- **带哈希的资源长缓存 + HTML / Service Worker 用 `no-cache` + 接口按「能否容忍旧数据」二选一**。
- **验收**：DevTools 的 Size 列（`memory cache` / `disk cache` / 304）、响应头 `Age` 与 `X-Cache`、「新 HTML 是否引用了新哈希」。

## 4. 网络可靠性与弱网

### 4.1 超时是前提

- **实测**：同一个 200ms 后端，不设超时 214ms 完成；80ms 超时 → `TimeoutError`，110ms 就放弃。
- **超时要分层**：连接超时、首字节（TTFB）超时、整体超时；只设总超时会误杀「服务端在持续返回数据」的慢下载。
- **超时值按接口类型定制**，不搞全局一个数（列表页 3s，报表导出 30s）。
- **取消只发生在客户端**：前端超时了不等于服务端没执行 → 写操作必须靠幂等兜底。

### 4.2 能不能重试看幂等

- **可自动重试**：`GET` / `HEAD` / `PUT` / `DELETE`；**普通 `POST` 不可**；带幂等键的 `POST` 可以。
- **实测「服务端已落库但回包失败」**：不带幂等键重试后落了 2 单，带 `Idempotency-Key` 是 1 单。
- **幂等键三要求**：客户端生成、语义是「一次业务意图」而非「一个 HTTP 请求」、有明确有效期。

### 4.3 退避、抖动与上限

- **四种策略实测**：不重试直接失败 · 固定 200ms 总耗时 469ms · 指数退避 `100×2ⁿ` 375ms · 加抖动 404ms。
- **必须尊重 `Retry-After`**：服务端每次 503 都带了它，四种策略一个都没采纳——不采纳只会把故障拖长。
- **重试风暴实测**：20 客户端 × 3 轮，无抖动的 60 次重试只落在 5 个时间窗口、最拥挤一刻 20 次；加抖动后减半、分散到 17 个窗口。
- **完整策略四要素**：可重试错误类型（网络错误 / 5xx / 429，4xx 不重试）、上限次数、退避 + 抖动、`Retry-After`；再上一层是熔断。

### 4.4 弱网体验的其它手段

- **请求去重与合并**、**并发限制与关键请求插队**。
- **离线队列 + 后台同步**：重放必须带幂等键，否则离线期间的重试会造重复数据。
- **乐观更新要能回滚**，且回滚要有提示；超时先用缓存数据渲染并标注「可能不是最新」。
- **`navigator.connection`** 的 `effectiveType` / `saveData` 只能当优化信号，不能当唯一依据。

### 4.5 观测

- **本地复现**：Network 面板的 Slow 3G / Offline 预设；断言落在「重试是否有界」这类行为上。
- **线上看**：成功率、超时率、重试率、重试后的最终成功率、p95 / p99。
- **重试率高但最终成功率低** = 重试在放大故障，此时该降低次数或熔断。

## 5. 同源策略与跨域

### 5.1 同源策略

- **同源三要素**：协议 + 域名 + 端口三者全同；`localhost` 与 `127.0.0.1`、`5177` 与 `5178` 都不同源。
- **管的是"读"不是"发"**：跨源的 `<script>` / `<img>` 可以正常加载执行，跨源 `fetch` 的请求也会真的发出去、服务端照常处理，被拦的只是"把响应交给 JS"。
- **保护对象**：另一源的响应内容、跨源 iframe 的 DOM、按源隔离的存储与 Cookie。

### 5.2 CORS 跨域资源共享

- **简单请求**：方法限 `GET` / `HEAD` / `POST`、请求头限安全列表、`Content-Type` 只能是表单三类之一；直接发真实请求，靠响应头决定 JS 能否读。
- **预检请求**：非简单请求（自定义头、`PUT` / `DELETE`、`application/json`）先自动发 `OPTIONS`，通过后才发真实请求；页面只写一次 `fetch` 却产生两次请求。
- **六个响应头**：`Allow-Origin`（必填）/ `Allow-Methods` / `Allow-Headers` / `Allow-Credentials` / `Max-Age` / `Expose-Headers`。
- **两条硬规则**：`Allow-Credentials: true` 与 `Allow-Origin: *` 互斥；自定义响应头默认对 JS 不可见，必须 `Expose-Headers` 放行。
- **失败表现**：JS 只拿到 `TypeError: Failed to fetch`（无状态码、无原因），定位靠 Network 面板与 Console；服务端其实收到了那次请求，所以 **CORS 不能当鉴权**。
- **工程首选**：同域部署或 dev server 代理，从架构上消灭跨源；必须跨源时按"是否带凭据"选 `*` 还是回显白名单 Origin。

## 6. 前端安全

### 6.1 XSS 三类与防御

| 类型 | 注入路径 | 特点 |
| ---- | ---- | ---- |
| 反射型（非持久） | 恶意脚本在请求 URL 中、服务器渲染后立即反射回页面 | 典型触发点：搜索框、错误提示、URL 参数回显 |
| 存储型（持久） | 恶意脚本入库持久化 | 所有访问该页面的用户都中招，评论区 / 留言 / 昵称是重灾区，危害最大、可横向传播 |
| DOM 型 | 前端 JS 操作 DOM 时注入、不经过服务端 | `innerHTML` / `document.write` / `eval` / `location.hash` 是危险入口 |

**防御手段**：输入白名单校验 + 输出上下文编码；用 `textContent` / DOMPurify 安全渲染富文本；Cookie 加 `HttpOnly`；配合 CSP 纵深防御。

### 6.2 CSRF

- **攻击原理**：用户已登录 A 站时访问恶意站 B，浏览器自动带上 A 的 Cookie 发请求，服务端无法辨别是否用户本意，从而执行转账、改密等危险操作。
- **SameSite 首选防御**：现代浏览器默认 `SameSite=Lax` 使跨站 POST 不再自动带 Cookie，从根上阻断大部分 CSRF；`None` 最危险、必须配合 Token 等额外校验。
- **辅助防御**：CSRF Token（请求头 / 体携带一次性随机凭证）、校验 Origin / Referer、敏感操作二次验证（验证码 / 二次确认）。

### 6.3 CSP 与点击劫持

- **指令白名单**：通过响应头或 `<meta>` 声明允许的资源来源，核心指令 `default-src` / `script-src` / `style-src` / `img-src` / `connect-src`。
- **内联放行**：内联脚本用 `nonce`（随机数）或 `hash` 方式放行，避免完全禁止导致功能可用性问题；配 `report-uri` 上报可及时发现真实攻击。
- **防点击劫持**：`frame-ancestors` 限定哪些站点能以 iframe 嵌入本页（现代首选），老方案 `X-Frame-Options: DENY / SAMEORIGIN` 兼容旧浏览器。

### 6.4 SQL 注入与上传安全

- **SQL 注入**：根治在服务端参数化查询 / 预编译语句、禁止拼接 SQL 字符串；前端校验可被绕过不能作安全边界，只能预校验明显恶意输入并做错误脱敏与异常上报。
- **上传安全**：类型白名单 + 魔数校验（不信任扩展名）、限制大小，重命名后存到非 web 可执行目录，不允许上传文件被当作脚本执行。
- **SVG 风险**：SVG 可能内嵌脚本，非必要时禁止上传 SVG，若需支持必须做内容净化。

### 6.5 纵深防御模型

```
传输层     HTTPS + HSTS 保证机密性、完整性与身份认证，也是 Secure Cookie、CSP、SW 的前提
输入输出层  白名单优先的输入校验 + 按上下文(HTML/属性/JS/URL)输出编码；敏感信息最小化返回、存储脱敏
会话层     Cookie 三件套 HttpOnly / Secure / SameSite，防 XSS 盗取与 CSRF 自动携带
策略层     CSP 白名单约束资源来源；frame-ancestors / X-Frame-Options 防点击劫持
服务端层   参数化查询根治 SQL 注入、上传文件非可执行目录存储、接口鉴权
兜底层     监控风控(CSP report-uri、异常上报)，前端校验被绕过时仍有最后防线
```

## 7. 前端安全进阶

### 7.1 CSP 防的是能力，不是输入

- **实测策略**：`script-src 'self' 'nonce-…'` 下，无 nonce 的内联脚本被拦、`onclick` 被拦、第三方 CDN 脚本被拦、同源脚本放行。
- **nonce 必须逐请求生成**：攻击者猜不到，注入的代码就执行不了。
- **默认禁止 `eval`**，顺手关掉「字符串变代码」一整类注入路径。
- **来源清单是白名单**：`img-src` 放了具体域名、`script-src` 仍拦第三方，按资源类型分别收紧。
- **上线顺序**：`Content-Security-Policy-Report-Only` 收集违规 → 修内联 → 切强制 → 保留上报端点。

### 7.2 SRI 校验内容一致性

- **实测**：`vendor.js` 追加一段代码后 sha384 完全改变（`wrYiCf9b…` → `riDGD4fn…`），浏览器整块丢弃不执行。
- **`integrity` 必须配 `crossorigin`**，否则跨域脚本拿不到可校验的响应体。
- **只保证「与声明一致」，不保证「内容可信」**：哈希被一起改掉就失效。
- **哈希由构建期生成写进 HTML**；最适合第三方 CDN 的固定版本脚本，动态 `import()` 靠 CSP 兜底。

### 7.3 Trusted Types 的价值是收口

- **`require-trusted-types-for 'script'`** 之后 `innerHTML = 字符串` 直接抛错，唯一通路是显式策略 + 净化。
- **全项目只有一处能把字符串变成 HTML**，审计才做得完。

### 7.4 响应头与 Cookie

- **体检五项**：CSP · HSTS · `nosniff` · `Referrer-Policy` · `frame-ancestors`（旧写法 `X-Frame-Options`）。
- **HSTS 的 `includeSubDomains` 要谨慎**：先把整个域锁死在 HTTPS，子域有 HTTP 服务就直接不可用。
- **Cookie 四件套**：`HttpOnly` / `Secure` / `SameSite` / `__Host-` 前缀；`SameSite=None` 必须配 `Secure`。

### 7.5 泄露面与供应链

- **`.map` 不上线**：只上传监控平台供反解（`hidden-source-map`）；线上留 `sourceMappingURL` 等于公开源码。
- **上报数据要白名单过滤**：手机号、token、密码字段一律不落地。
- **供应链**：锁文件进仓库 + `npm ci` + 私服代理 + 依赖审计进 CI；**减少依赖数量本身最有效**。
- **其它最先被翻的**：`.git` / `.env` / 备份文件被部署到静态目录、接口原样返回内部堆栈。
