## 1. HTTP 协议与缓存体系

全篇一条渐进主线：数据怎么送到对方（分层与传输层）→ 说什么（HTTP 语义）→ 怎么传得安全（HTTPS）→ 怎么传得快（HTTP/2 与 HTTP/3）→ 怎么不重复传（缓存与 CDN）。

### 1.1 网络分层与传输层

- **五层模型**：应用层（HTTP / DNS / TLS）→ 传输层（TCP / UDP）→ 网络层（IP）→ 数据链路层 → 物理层；发送端从上到下打包、接收端从下到上解包。
- **TCP vs UDP**：TCP 面向连接、可靠（确认应答 / 超时重传 / 乱序重排）、有流量与拥塞控制；UDP 无连接、不可靠但快、面向报文。
- **粘包问题**：TCP 面向字节流、多条消息黏连要封包/拆包；UDP 面向报文、自带消息边界不会粘包。
- **选型**：HTTP / HTTPS / WebSocket / 文件传输走 TCP；实时音视频 / 直播 / DNS / 游戏走 UDP；QUIC 是"在 UDP 上自建可靠性"的折中。

### 1.2 HTTP 基础：无状态、报文、方法幂等与状态码

**HTTP 是无状态的应用层协议**，这是理解整个网络模块的起点：

- **无状态与身份模拟**：每个请求独立、服务器不记忆客户端；靠 Cookie / Session / Token **显式携带身份**来模拟"有状态"。
- **请求-响应模型**：客户端发起请求、服务端返回响应；明文传输是早期版本被窃听、篡改的根源（HTTPS 的由来）。

报文结构分三块：

```
请求报文   请求行 + 头 + 空行 + 体
             请求行 = METHOD + 路径 + HTTP版本
响应报文   响应行 + 头 + 空行 + 体
             响应行 = HTTP版本 + 状态码 + 描述
```

**方法语义与幂等性**：

| 方法 | 语义 | 请求体 | 幂等 |
| ---- | ---- | ---- | ---- |
| `GET` | 取数据 | 无 | 是 |
| `POST` | 提交 / 创建资源 | 有 | 否 |
| `PUT` | 整体替换资源 | 有 | 是 |
| `PATCH` | 局部更新资源 | 有 | 通常否 |
| `DELETE` | 删除资源 | — | 是 |

- **幂等性的价值**：网络超时重试、用户重复点击时，靠幂等性做正确决策（重复 GET/PUT 不产生副作用）。
- **GET 与 POST 唯一本质差异是语义**，二者的传输安全性都由 HTTPS 提供。

**状态码五类**：

| 大类 | 含义 | 常见状态码 |
| ---- | ---- | ---- |
| 2xx | 成功 | `200` 正常、`201` 已创建（POST 常用）、`204` 成功无内容（DELETE 成功） |
| 3xx | 重定向 | `301` 永久、`302` 临时、`304` 协商缓存命中（资源未变用缓存） |
| 4xx | 客户端错误 | `401` 未认证 `vs` `403` 无权限、`404` 不存在、`405` 方法不允许、`429` 限流 |
| 5xx | 服务端错误 | `500` 内部错误、`502` 网关收到无效响应、`503` 暂时不可用、`504` 网关超时 |

> 最容易混的一对：`401` 是"没认证"（未登录），`403` 是"没权限"（已登录但无授权）。

### 1.3 HTTPS：加密基础、证书与 TLS 握手

- **三个要解决的问题**：窃听（防窃听→加密）、篡改（防篡改→完整性校验）、冒充（防冒充→身份认证）。
- **加密基础**：对称加密快但密钥分发难，非对称加密能分发但慢——混合加密用非对称协商会话密钥、正文对称传输；防篡改由 AEAD（如 AES-GCM）顺带完成，改一个字节校验即失败。
- **证书内容**：主体域名、公钥、有效期、签发者与 CA 数字签名；浏览器内置根 CA 公钥沿链验签——CA 像公安局，证书是服务器身份证，解决"这份公钥到底是谁的"。
- **TLS 握手五步**：①ClientHello / ②ServerHello+证书（明文，谈条件+验身份）→ ③预主密钥用公钥加密传输（中间人无私钥解不开）→ ④双端各自合成相同的会话密钥（从未明文上网）→ ⑤Finished 对暗号。
- **RSA vs ECDHE（面试高频）**：RSA 是"传"密钥材料（私钥泄露历史流量可解，无前向保密），ECDHE 是交换临时公钥各自"算"出来（前向保密）；TLS 1.3 已禁用 RSA 交换。
- **TLS 1.3**：1-RTT 握手（恢复可 0-RTT）、移除弱算法；配合会话复用与 CDN 边缘 TLS 终止，性能开销基本可忽略。

### 1.4 HTTP 版本演进：消除队头阻塞

队头阻塞分两层，演进就是逐层消灭它：

| 层级 | 现象 | 谁解决 |
| ---- | ---- | ---- |
| 应用层（HTTP 层） | 一个连接同时只能处理一个请求 | HTTP/2 多路复用 |
| 传输层（TCP 层） | 字节流有序，一个报文丢了后面都要等重传 | HTTP/3 QUIC |

- **HTTP/1.1**：升级特性是持久连接（一次 TCP 连接传多个请求）与 `Host` 头；缺点是队头阻塞——一个连接同时只能处理一个请求，并发靠 6 个连接硬扛。
- **HTTP/2**：多路复用（一条 TCP 连接上多个 stream 的二进制帧交错传输，请求不再排队）、二进制分帧（多路复用的前提）、HPACK 头部压缩；遗留 TCP 层队头阻塞（丢一个包全体 stream 等重传）。
- **HTTP/3**：传输层换 QUIC（基于 UDP）——stream 级重传彻底无队头阻塞、1-RTT/0-RTT 握手、连接迁移。
- **工程两句话**：协议版本看 DevTools Protocol 列；HTTP/2 下请求数量不再是最重要指标，分包回到缓存命中率与首屏必需，**gzip / brotli 仍必开**。

### 1.5 缓存决策链与三种策略

- **可能拦下请求的五层**：浏览器内存、磁盘、Service Worker、CDN 边缘、源站缓存；判定规则同一套：`Cache-Control` + `Age` + `ETag` / `Last-Modified`。

| 类型 | 判定头 | 命中表现 | 收益 / 代价 |
| ---- | ---- | ---- | ---- |
| 强缓存 | `Cache-Control`（相对时间，优先）`vs` `Expires`（绝对时间、依赖客户端时钟） | 命中不发请求，直接用本地副本 | 省一整个往返；更新只能靠改 URL |
| 协商缓存 | `If-None-Match`（对应 `ETag`，内容指纹，优先）`vs` `If-Modified-Since`（对应 `Last-Modified`，秒级时间） | 条件请求，服务端回 `304` 后复用 | **省正文不省 RTT** |
| 禁用 | `no-store` | 每次完整请求 | 只给登录态、支付结果这类 |

**`no-cache` ≠ 不缓存**：它只是要求每次使用前必须校验。

- **协商缓存的成立条件**：`ETag` 必须是内容指纹（带随机数/时间戳等于没配）；`Last-Modified` 精度只到秒；**`Vary` 会进缓存键**——`Vary: User-Agent` 会让命中率崩掉。
- **stale-while-revalidate**：`max-age=60, swr=600` 三个区间——新鲜期不发请求 / 过期在窗口内先用旧的 + 后台刷新 / 超出窗口同步请求；适合可容忍轻微延迟的数据，库存、余额、权限不行；配 `stale-if-error` 可在源站故障时兜底。
- **开发实践**：静态资源内容指纹文件名（`app-5f8c2a.js`）+ 长 `max-age` + `immutable`；HTML 与 Service Worker 文件用 `no-cache`；接口按「能否容忍旧数据」二选一。
- **验收**：DevTools 的 Size 列（`memory cache` / `disk cache` / 304）、响应头 `Age` 与 `X-Cache`、「新 HTML 是否引用了新哈希」。

### 1.6 CDN：三件额外事与配置落地

- **缓存键由 CDN 配置决定**：忽略 query 参数要极谨慎，忽略掉身份参数就是安全事故。
- **有父层与回源分层**：源站 QPS 不涨不等于边缘命中，要看 `X-Cache` 与 `Age`。
- **刷新是异步的**：只刷新不带哈希的入口文件，其余靠内容哈希自然失效；发布前可预热热门资源，防回源雪崩。

### 1.7 DNS 与 WebSocket

- **DNS 解析**：走"浏览器/系统缓存 → 本地 DNS 递归 → 根/顶级/权威迭代查询"把域名换成 IP；可用 `dns-prefetch` / `preconnect` 预解析预热。
- **WebSocket 定位**：复用 HTTP 握手（`Upgrade 101`）的全双工持久连接，服务器可主动推送；**无同源限制**但服务端要校验 `Origin`。

**四种即时通信方式对比**：

```
性能       WebSocket > SSE > 长轮询 > 短轮询
兼容性     反之；SSE 是单向流式 HTTP、实现简单且自动重连，但客户端不能推
```

- **工程要点**：断线重连（退避策略）、心跳保活防代理掐连接、`wss://` 加密、`Origin` 白名单。

## 2. 同源策略与跨域

### 2.1 同源策略

- **同源三要素**：协议 + 域名 + 端口三者全同；`localhost` 与 `127.0.0.1`、`5177` 与 `5178` 都不同源。
- **管的是"读"不是"发"**：跨源的 `<script>` / `<img>` 可以正常加载执行，跨源 `fetch` 的请求也会真的发出去、服务端照常处理，被拦的只是"把响应交给 JS"。
- **保护对象**：另一源的响应内容、跨源 iframe 的 DOM、按源隔离的存储与 Cookie。

### 2.2 CORS 跨域资源共享

- **简单请求**：方法限 `GET` / `HEAD` / `POST`、请求头限安全列表、`Content-Type` 只能是表单三类之一；直接发真实请求，靠响应头决定 JS 能否读。
- **预检请求**：非简单请求（自定义头、`PUT` / `DELETE`、`application/json`）先自动发 `OPTIONS`，通过后才发真实请求；页面只写一次 `fetch` 却产生两次请求。
- **六个响应头**：`Allow-Origin`（必填）/ `Allow-Methods` / `Allow-Headers` / `Allow-Credentials` / `Max-Age` / `Expose-Headers`。
- **两条硬规则**：`Allow-Credentials: true` 与 `Allow-Origin: *` 互斥；自定义响应头默认对 JS 不可见，必须 `Expose-Headers` 放行。
- **失败表现**：JS 只拿到 `TypeError: Failed to fetch`（无状态码、无原因），定位靠 Network 面板与 Console；服务端其实收到了那次请求，所以 **CORS 不能当鉴权**。
- **工程首选**：同域部署或 dev server 代理，从架构上消灭跨源；必须跨源时按"是否带凭据"选 `*` 还是回显白名单 Origin。

## 3. 前端安全

安全的共同根源是信任边界的错置：页面信任了不该信任的输入（XSS）、浏览器信任了不该信任的请求（CSRF）、用户信任了不该信任的界面（点击劫持）。

### 3.1 XSS 三类与防御

| 类型 | 注入路径 | 特点 |
| ---- | ---- | ---- |
| 反射型（非持久） | 恶意脚本在请求 URL 中、服务器渲染后立即反射回页面 | 典型触发点：搜索框、错误提示、URL 参数回显 |
| 存储型（持久） | 恶意脚本入库持久化 | 所有访问该页面的用户都中招，评论区 / 留言 / 昵称是重灾区，危害最大、可横向传播 |
| DOM 型 | 前端 JS 操作 DOM 时注入、不经过服务端 | `innerHTML` / `document.write` / `eval` / `location.hash` 是危险入口 |

**防御手段**：输入白名单校验 + 输出上下文编码；用 `textContent` / DOMPurify 安全渲染富文本；Cookie 加 `HttpOnly`；CSP 纵深防御（见 3.4）；Trusted Types 把 `innerHTML` 等危险赋值点收口——全项目只有一处能把字符串变成 HTML，审计才做得完。

### 3.2 CSRF

- **攻击原理**：用户已登录 A 站时访问恶意站 B，浏览器自动带上 A 的 Cookie 发请求，服务端无法辨别是否用户本意，从而执行转账、改密等危险操作。
- **SameSite 首选防御**：现代浏览器默认 `SameSite=Lax` 使跨站 POST 不再自动带 Cookie，从根上阻断大部分 CSRF；`None` 最危险、必须配合 Token 等额外校验。
- **辅助防御**：CSRF Token（请求头 / 体携带一次性随机凭证）、校验 Origin / Referer、敏感操作二次验证（验证码 / 二次确认）。

### 3.3 CSP 与点击劫持

- **指令白名单**：通过响应头或 `<meta>` 声明允许的资源来源，核心指令 `default-src` / `script-src` / `style-src` / `img-src` / `connect-src`。
- **内联放行**：内联脚本用 `nonce`（随机数）或 `hash` 方式放行，避免完全禁止导致功能可用性问题；配 `report-uri` 上报可及时发现真实攻击。
- **防点击劫持**：`frame-ancestors` 限定哪些站点能以 iframe 嵌入本页（现代首选），老方案 `X-Frame-Options: DENY / SAMEORIGIN` 兼容旧浏览器。

### 3.4 CSP：XSS 的纵深防线

- **思路**：转义漏了就功亏一篑，CSP 声明页面允许加载与执行哪些资源，清单外一律拦下。
- **核心指令**：`default-src` / `script-src` / `style-src` / `img-src` / `connect-src`；防点击劫持用 `frame-ancestors`（见 3.3）。
- **内联放行三种方式**：来源清单（静态站点）/ nonce（逐请求随机，服务端渲染）/ hash（内容固定）；`strict-dynamic` 放行合法脚本动态插入的脚本。
- **判定口径**：`script-src 'self' 'nonce-…'` 下，无 nonce 的内联脚本被拦、`onclick` 被拦、`eval` 被拦、第三方 CDN 脚本被拦、同源脚本放行——来源清单是白名单，按资源类型分别收紧。
- **上线顺序**：`Content-Security-Policy-Report-Only` 只上报不拦截收集违规 → 修内联 → 切强制 → 保留上报端点。

### 3.5 SRI 与依赖供应链

- **SRI 机制**：`integrity="sha384-<哈希>"`，浏览器下载完先算哈希，对不上整块丢弃；文件追加一个字节摘要就面目全非，篡改立即暴露。
- **`integrity` 必须配 `crossorigin`**，否则跨域脚本拿不到可校验的响应体。
- **只保证「与声明一致」，不保证「内容可信」**：哈希被一起改掉就失效；最适合第三方 CDN 固定版本脚本，动态 `import()` 靠 CSP 兜底。
- **供应链**：锁文件进仓库 + CI 用 `npm ci` + 私服代理统一入口 + 依赖审计进 CI；**减少依赖数量本身最有效**。

### 3.6 安全响应头与 Cookie 属性

- **底线四项**：HSTS（强制 HTTPS，`includeSubDomains` 先短 `max-age` 试）· `nosniff`（禁猜类型）· `Referrer-Policy`（显式声明才可控）· `X-Frame-Options`（旧写法，`frame-ancestors` 优先）。
- **Cookie 四件套**：`HttpOnly` / `Secure` / `SameSite` / `__Host-` 前缀；`SameSite=None` 必须配 `Secure`。
- **HTTPS 是基石**：CSP、SW、`Secure` Cookie 都要求 HTTPS；原理见 HTTP 篇第三节。

### 3.7 SQL 注入与上传安全

- **SQL 注入**：根治在服务端参数化查询 / 预编译语句、禁止拼接 SQL 字符串；前端校验可被绕过不能作安全边界，只能预校验明显恶意输入并做错误脱敏与异常上报。
- **上传安全**：类型白名单 + 魔数校验（不信任扩展名）、限制大小，重命名后存到非 web 可执行目录，不允许上传文件被当作脚本执行。
- **SVG 风险**：SVG 可能内嵌脚本，非必要时禁止上传 SVG，若需支持必须做内容净化。

### 3.8 数据脱敏与输入校验

- **`.map` 不上线**：只上传监控平台供反解（`hidden-source-map`）；线上留 `sourceMappingURL` 等于公开源码。
- **上报数据要白名单过滤**：手机号、token、密码字段一律不落地；展示与日志做打码/部分脱敏（手机号中间四位）。
- **输入校验**：白名单优先，复杂校验用 zod / joi；目标是体验不是安全边界。

### 3.9 落地顺序

先盘点资源来源 → `Report-Only` 收违规 → 修内联（改动量最大）→ 切强制 + 监控违规 → 补响应头与 Cookie 属性 → `.map` 摘出产物、依赖审计进 CI。
