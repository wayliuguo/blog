# HTTP 协议与缓存体系

本篇按一条渐进主线展开：**数据怎么送到对方**（分层与传输层）→ **说什么**（HTTP 语义）→ **怎么传得安全**（HTTPS）→ **怎么传得快**（HTTP/2 与 HTTP/3）→ **怎么不重复传**（缓存与 CDN）。每一步都建立在前一步之上。

## 一、网络分层与传输层

互联网通信极其复杂，没人能一次性把整个流程描述清楚。**分层**就是化繁为简的手段：把网络按不同职责切成多层，每层只关心自己的事，并向上层/下层提供稳定的接口。真实数据在发送时**从上到下逐层打包**，接收方**从下到上逐层解包**，各层互不感知对方细节。

最常用的是**五层模型**（综合 OSI 与 TCP/IP 两套经典划分，前端视角最直观）：应用层、传输层、网络层、数据链路层、物理层。

> 示意片段（无配套脚本）

```
| 层级         | 代表协议     | 职责                        |
|--------------|--------------|-----------------------------|
| 应用层       | HTTP  DNS    | 浏览器发起的请求/响应        |
| (安全)       | TLS          | 给 HTTP 加一层加密          |
| 传输层       | TCP  UDP     | 保证数据可靠/快速地送达     |
| 网络层       | IP           | 在网络上找路、寻址          |
| 数据链路层   | 以太网/WiFi  | 相邻节点间传输              |
| 物理层       | 网卡/光缆    | 比特流的物理传输            |

注意："网络分层"是逻辑划分，真实数据是"从上到下打包、对端从下到上解包"。
```

HTTP 只是应用层协议，真正把数据搬过去的，是下层 TCP——所以我们先讲传输层。

### 1. TCP 与 UDP

TCP 与 UDP 是传输层的两大协议，HTTP/HTTPS、WebSocket 都跑在 TCP 上，QUIC 跑在 UDP 上。区别一句话概括：**TCP 面向连接、可靠，UDP 无连接、不可靠但快**。

| 对比项 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接，三次握手建立、四次挥手断开 | 无连接，直接发数据报 |
| 可靠性 | 可靠：确认应答、超时重传、乱序重排 | 不可靠：发出去不管，丢包不重传 |
| 有序性 | 保证字节流按序到达 | 不保证顺序 |
| 传输方式 | 面向字节流 | 面向报文（有消息边界，天然不会粘包） |
| 流量控制 | 有（滑动窗口，避免发送方淹没接收方） | 无 |
| 拥塞控制 | 有（慢启动、拥塞避免、快重传、快恢复） | 无 |
| 速度 | 慢（握手 + 确认开销大） | 快（无握手、无确认） |
| 应用场景 | HTTP/HTTPS、WebSocket、文件传输、邮件 | 视频会议、直播、语音、DNS 查询、游戏实时对战 |

**为什么 UDP 不粘包**：TCP 是**面向字节流**的协议，应用层多次 send 的数据在接收方看来是一条连续的字节流，接收方无法天然区分"这条消息到哪结束"，于是出现**粘包**。常用解法：封包/拆包（包头加长度字段）、关闭 Nagle 算法、消息间加分隔符。UDP 是**面向报文**的，每个数据报自带消息边界，接收端一次只能收到一个完整的报文，天然不会粘包。

**选择依据**：要**可靠**（数据不能丢、顺序不能乱）→ TCP；要**实时低延迟**（丢几帧可以接受）→ UDP。前端日常：HTTP 系全部走 TCP；需要极低延迟的实时音视频才考虑 UDP/WebRTC；HTTP/3 的 QUIC 是在 UDP 上自己实现了可靠性——"既要快又要可靠"的折中方案。

## 二、HTTP 基础

### 1. HTTP 是什么

**HTTP（HyperText Transfer Protocol）** 是建立在 TCP/IP 之上的**应用层**协议，定义了客户端（浏览器）与服务器之间如何"请求"和"响应"。它由 Tim Berners-Lee 在 1989 年发明，最初只用于传输超文本（HTML），如今几乎承载了全网的业务数据。

四个特点：

- **无状态（Stateless）**：每个请求都是独立的，服务器不记忆客户端之前的请求。缓解方案是通过 **Cookie / Session / Token** 在请求中显式携带身份信息，人为地模拟"有状态"。
- **基于请求-响应模型**：客户端发起请求，服务端返回响应，一次完整的交互由此完成。
- **明文传输**：数据以明文传输，可被窃听、篡改——这正是 HTTPS 要解决的问题（见第三节）。

### 2. 报文结构

一次 HTTP 交互由**请求报文**和**响应报文**组成。两者结构高度对称，都包含三个部分：

> 示意片段（无配套脚本）

```
请求报文：
   请求行     METHOD 路径(URL) 协议版本\r\n
   请求头     Header: Value\r\n
   （空行）   \r\n
   请求体     Body（请求方法如 POST/PUT 才可能携带）

响应报文：
   状态行     协议版本 状态码 状态描述\r\n
   响应头     Header: Value\r\n
   （空行）   \r\n
   响应体     Body（HTML、JSON、图片流等）
```

一个真实的请求报文示例：

> 示意片段（无配套脚本）

```http
POST /api/login HTTP/1.1
Host: example.com
Content-Type: application/json
Content-Length: 31
User-Agent: Mozilla/5.0 ...
Cookie: session=abc123

{"username":"jack","password":"***"}
```

常见的请求头与响应头：

| 方向 | 头部 | 含义 |
| --- | --- | --- |
| 请求 | `Host` | 目标主机名与端口 |
| 请求 | `User-Agent` | 客户端浏览器/环境标识 |
| 请求 | `Cookie` | 携带的身份凭证 |
| 请求 | `Content-Type` | 请求体的媒体类型（`application/json` 等） |
| 请求 | `Accept` | 期望返回的内容类型 |
| 响应 | `Content-Type` | 响应体的媒体类型 |
| 响应 | `Content-Length` | 响应体的字节长度 |
| 响应 | `Cache-Control` | 缓存策略 |
| 响应 | `Set-Cookie` | 让浏览器写入一个 Cookie |
| 响应 | `Location` | 配合 3xx 重定向使用 |

### 3. 请求方法与幂等性

| 方法 | 用途 | 是否有请求体 | 幂等性 |
| --- | --- | --- | --- |
| `GET` | 获取资源 | 无 | 幂等 |
| `POST` | 提交/创建资源 | 有 | 非幂等 |
| `PUT` | 整体替换资源 | 有 | 幂等 |
| `PATCH` | 局部更新资源 | 有 | 非幂等 |
| `DELETE` | 删除资源 | 通常无 | 幂等 |
| `HEAD` | 只获取响应头，不返回响应体 | 无 | 幂等 |
| `OPTIONS` | 询问服务器支持的请求方法（常用于跨域预检） | 无 | 幂等 |

**幂等**指无论执行一次还是执行多次，产生的结果都是相同的，且不会产生副作用叠加。为什么关注它？因为网络可能超时重试、用户可能重复点击——诚实地区分方法语义，能帮助网关重试、缓存系统与接口设计做出正确决策。

**GET 与 POST 的区别**：

| 对比项 | GET | POST |
| --- | --- | --- |
| 语义 | 取数据，无副作用 | 提交数据，有副作用 |
| 参数位置 | URL 查询串 | 请求体 |
| 数据可见性 | 可见于地址栏、日志 | 不在 URL 中 |
| 缓存 | 默认可缓存 | 默认不可缓存 |
| 长度限制 | 受 URL 长度限制 | 理论上只受服务器配置限制 |
| 安全 | 参数易被浏览器历史/代理记录 | 相对不易泄露（但都是明文，除非走 HTTPS） |

> 注意：GET 和 POST 都不"安全"（机密性由 HTTPS 提供）。它们唯一的本质差异是**语义**，其余都是浏览器/框架的默认行为约定。

### 4. 状态码

服务器通过**状态码**告诉客户端请求的结果。状态码为三位数字，按首位数字分为五类：

| 分类 | 首位 | 含义 |
| --- | --- | --- |
| 信息响应 | 1xx | 请求已收到，继续处理（例如 `101` 切换协议） |
| 成功 | 2xx | 请求成功处理 |
| 重定向 | 3xx | 需要进一步操作才能完成请求 |
| 客户端错误 | 4xx | 请求有误，责任在客户端 |
| 服务端错误 | 5xx | 服务器处理出错，责任在服务端 |

常见状态码速查：

| 状态码 | 说明 |
| --- | --- |
| `200 OK` | 请求成功，正常返回 |
| `201 Created` | 已创建新资源（常用于 POST） |
| `204 No Content` | 成功但无内容返回（如 DELETE 成功） |
| `301 Moved Permanently` | 永久重定向，搜索引擎会更新链接 |
| `302 Found` | 临时重定向 |
| `304 Not Modified` | 协商缓存命中，服务端告知"资源未变，用缓存" |
| `400 Bad Request` | 请求语法或参数错误 |
| `401 Unauthorized` | 未认证，需要登录 |
| `403 Forbidden` | 已认证但无权限，拒绝访问 |
| `404 Not Found` | 资源不存在 |
| `405 Method Not Allowed` | 方法不被允许 |
| `429 Too Many Requests` | 请求过于频繁，触发限流 |
| `500 Internal Server Error` | 服务器内部错误 |
| `502 Bad Gateway` | 网关/代理收到上游无效响应 |
| `503 Service Unavailable` | 服务暂时不可用（如过载、维护） |
| `504 Gateway Timeout` | 网关/代理请求上游超时 |

要点：`301` 与 `302` 的区别在于**是否永久**；`401` 与 `403` 的区别在于**有没有登录（认证）** 与 **有没有权限（授权）**。

## 三、HTTPS：把明文通道变成加密通道

HTTPS = HTTP + TLS 加密层：在 TCP 之上、HTTP 之下插入一层 **TLS**（前身 SSL），提供**机密性、完整性、身份认证**三大保障。理解它的最短路径是三个递进的问题：**怎么不被偷看（加密）→ 怎么确认对方是谁（证书）→ 两者怎么落地（TLS 握手）**。

### 1. 先看要解决什么

明文 HTTP 有三个致命问题：**窃听**（数据被中间人截获读走）、**篡改**（数据中途被改，双方不知情）、**冒充**（连上的"服务器"其实是攻击者）。后面的设计逐一对应：加密解决窃听、完整性校验解决篡改、数字证书解决冒充。

### 2. 加密：混合方案

- **对称加密**：加解密用**同一把密钥**，速度快、适合大流量——但密钥怎么安全地发给对方是死结。
- **非对称加密**：一对密钥，公钥加密只有私钥能解，天然解决密钥分发——但计算慢，不适合加密大块数据。

HTTPS 取两者之长的**混合加密**：先用非对称加密安全地协商出一把「**会话密钥**」，之后的所有正文都改用对称加密（AES）——分发安全与加解密性能兼得。

### 3. 证书：公钥不能裸奔

混合加密有个缺口：客户端第一次拿到的"服务器公钥"可能来自中间人。解法是**数字证书**——服务器把「公钥 + 域名 + 有效期」交给 **CA（证书颁发机构）**，CA 用自己的私钥对内容签名；客户端内置各大 CA 的**根证书（公钥）**，据此验签。证书可信、域名匹配、在有效期内，公钥才可信。

一句话：**证书解决的是"这份公钥到底是谁的"**。

### 4. TLS 握手：三件事串起来

> 示意片段（无配套脚本）

```
客户端                                服务器
  │ ① ClientHello：支持的 TLS 版本/算法套件/随机数A
  ├───────────────────────────────────────►
  │ ② ServerHello：选定算法/随机数B + 数字证书
  ◄───────────────────────────────────────┤
  │ ③ 验证证书 → 生成"预主密钥"，用服务器公钥加密发出
  ├───────────────────────────────────────►
  │ ④ 双方用 预主密钥+随机数A/B 各自算出相同的"会话密钥"
  │ ⑤ 互发用会话密钥加密的 Finished 确认 → 握手完成
  │ ◄═══ 之后所有 HTTP 数据用会话密钥对称加密 ═══►
```

渐进地看：

1. **①② 谈参数**：互报 TLS 版本、算法套件与两个随机数——确定双方都能用的加密参数；
2. **③ 传密钥材料**：客户端验过证书后，用证书里的公钥加密"预主密钥"发出——中间人没有私钥，拿不到；
3. **④⑤ 合成会话密钥**：两端各自用预主密钥 + 随机数 A/B 推导出同一把对称密钥并互相确认——它从未在网络上明文出现过；
4. **闭环**：此后正文对称加密，窃听读不懂、篡改校不过、冒充过不了验签——第 1 小节的三个问题全部解决。

补充：TLS 1.3 把握手压缩到 1-RTT（会话恢复可 0-RTT）并移除了静态 RSA 交换等弱算法；配合会话复用、HTTP/2 减少连接数、CDN 边缘 TLS 终止，HTTPS 的性能开销在工程上已基本可忽略。

## 四、HTTP 版本演进：把传输变快

### 1. HTTP/1.1：队头阻塞与 6 连接的补救

HTTP/1.1 引入**持久连接（Keep-Alive）**：一次 TCP 连接可传多个请求，避免每次握手；新增 `Host` 头、更多方法与分块传输。

但一个连接同一时刻仍只能处理一个请求——**队头阻塞（Head-of-Line Blocking）**：前面的响应慢了，后面的只能排队。想并行只能多开 TCP 连接，**并发度直接等于连接数**（浏览器同域名通常限 6 个）。同一台机器、同一个后端、6 个耗时 200ms 的请求，三种发法的量级对照（本机测量）：

```
| 发法                            | TCP 连接数 | 批次总耗时 | 相对串行 |
|---------------------------------|------------|------------|----------|
| HTTP/1.1 单连接                 | 1          | 1332 ms    | 1.00×    |
| HTTP/1.1 六连接                 | 6          | 231 ms     | 5.77×    |
| HTTP/2 单连接（6 个 stream）    | 1          | 245 ms     | 5.45×    |
```

6 个连接的代价：6 次 DNS、6 次 TCP 握手、6 次 TLS 握手、6 份拥塞窗口各自从慢启动开始爬。这也是为什么「域名分片」「CSS 雪碧图」「小图标内联 base64」这类手段流行了那么久——它们都是在绕开 6 连接的限制，而这些手段本身有代价：分片增加 DNS 与握手开销，雪碧图与 base64 牺牲缓存粒度（改一个图标，整张贴图与整份 CSS 都失效）。

### 2. HTTP/2：多路复用

HTTP/2 在**一个** TCP 连接上用二进制**帧**同时交错传输多个请求/响应**流（stream）**——「有多少请求要发」不再受「能开多少连接」限制，上表的第三行就是它的效果：单连接拿到与 6 连接同量级的并发。

但要先分清两个层次的队头阻塞，很多讨论把两者混在一起：

| 层级 | 现象 | HTTP/2 的效果 |
| --- | --- | --- |
| 应用层（HTTP 层） | 一个连接上，前一个响应没回来，后面的请求不能上路 | **消除** |
| 传输层（TCP 层） | TCP 保证字节流有序，一个报文丢了，后面收到的也要等重传 | **没有解决** |

一个 500ms 的请求排在最前、后面跟 5 个 20ms 的请求，两种协议的对照（本机测量）：

```
| 发法            | 快请求平均完成于 | 快请求最晚完成于 | 说明                                     |
|-----------------|------------------|------------------|------------------------------------------|
| HTTP/1.1 单连接 | 617 ms           | 678 ms           | 同一连接上只能一个一个来，全被慢请求挡住 |
| HTTP/2 单连接   | 33 ms            | 33 ms            | 各 stream 独立，慢的不拖累快的           |
```

HTTP/2 里每个请求是连接上的一个独立 stream，慢请求自己在 500ms 后返回，互不影响。但这也埋下伏笔：**所有请求都挤在一条 TCP 连接里**，一旦丢包，TCP 层队头阻塞从「只影响一条连接」变成「波及全部 stream」。

除多路复用外，协议层还有几处必须知道的变化：

| 变化 | 内容 | 为什么重要 |
| --- | --- | --- |
| 二进制分帧 | 请求/响应被切成 HEADERS 帧与 DATA 帧，按 stream 编号交错发送 | 文本协议没法做优先级与交错，二进制帧才能 |
| 头部压缩 HPACK | 静态表 + 动态表 + 哈夫曼编码，同一连接上的重复头部用索引引用 | 省掉大量重复 Cookie / UA；但压缩上下文是**连接级**的，带来 CRIME/BREACH 类攻击面 |
| 流优先级 | 声明依赖树与权重（`priority` 帧） | 实践里服务器实现不一致；控制首屏关键资源顺序还是靠 `preload` 与 `fetchpriority` |
| 连接级流控 | 按 stream 与连接两个维度做窗口控制 | 一个慢客户端不会拖垮整个连接 |
| 服务端推送 | 服务端主动推资源，**浏览器已废弃** | 推送的资源无法确定客户端是否已缓存；想要更可控的替代用 `103 Early Hints` |

**工程落地**：HTTP/2 实际使用必须走 TLS + ALPN 协商（`h2`），明文 h2c 只用于内部调试。判断线上协议看 DevTools Network 面板的 Protocol 列（`h2` / `h3` / `http/1.1`），或 `curl -I --http2 https://example.com` 看响应首行。打包策略跟着改：**请求数量不再是最重要的指标**（但小文件过多仍有头部与调度成本，分包依据回到「缓存命中率」与「首屏必需」）；雪碧图、base64 内联、域名分片的收益下降甚至转为净损失；**gzip/brotli 仍必开**——HPACK 只管头部，正文压缩还得靠内容编码。

### 3. HTTP/3：QUIC

HTTP/3 把传输层从 TCP 换成 **QUIC（基于 UDP）**，专治 HTTP/2 留下的 TCP 层队头阻塞：

- **stream 级重传**：QUIC 在用户态实现了流的概念，某个 stream 的报文丢了只重传那一段，其它 stream 不受影响——真正无队头阻塞。
- **握手更快**：TLS 1.3 内建在 QUIC 里，首次连接 1-RTT；**0-RTT 恢复**时客户端用上次会话的票据，第一个报文就能带上请求数据（代价是 0-RTT 数据可被重放，只允许用在幂等请求上）。
- **连接迁移**：QUIC 用 Connection ID 而不是四元组标识连接，Wi-Fi 切 4G 不需要重新握手。

**要不要上 HTTP/3**：CDN 厂商基本都支持，开启通常只是控制台一个开关；收益集中在弱网与移动端（连接迁移、抗丢包）。风险点是中间设备对 UDP 的拦截，所以服务端都要同时保留 HTTP/2 作为回退——这也是为什么 HTTP/3 用 `Alt-Svc` 头来「告知」而不是强制。

### 4. 演进总结

一条主线：**逐层消灭队头阻塞与冗余开销**。

| 版本 | 关键改动 | 解决了什么 | 遗留问题 |
| --- | --- | --- | --- |
| HTTP/1.1 | 持久连接、Host 头 | 反复握手的开销 | HTTP 层队头阻塞 |
| HTTP/2 | 二进制帧、多路复用、HPACK | HTTP 层队头阻塞、头部冗余 | TCP 层队头阻塞 |
| HTTP/3 | QUIC（UDP）+ TLS 1.3 | TCP 层队头阻塞、握手慢 | 生态较新，部署依赖 UDP 放行 |

## 五、缓存：让数据不必重复传输

缓存是提升性能、减少带宽最有效的手段之一。先看全景：一个请求从发出到拿到数据，路上有这些层可以「截胡」：

| 层 | 命中时 | 判据 |
| --- | --- | --- |
| 浏览器内存缓存（memory cache） | 不发请求，不落盘 | 同一次导航内的重复请求，配合 `Cache-Control` |
| 浏览器磁盘缓存（disk cache） | 不发请求，落盘 | 强缓存仍新鲜 |
| Service Worker | 不发请求（由你写逻辑） | 你自己实现的策略 |
| CDN 边缘节点 | 不发到源站 | 边缘自己那份副本还新鲜 |
| 源站 / 应用层缓存 | 不查数据库 | Redis 等 |

对前端来说，可控的是前两层与 CDN 的响应头配置。所有层的判定规则是同一套：**看 `Cache-Control`、`Age`、`ETag` / `Last-Modified`**。所以先把这套规则吃透——CDN 的行为只是「同一个规则在离用户更近的机器上再跑一遍」（见第六节）。

### 1. 强缓存（Cache-Control / Expires）

命中强缓存时，浏览器**不发任何网络请求**，直接使用本地副本，状态码通常显示为 `200 (from disk cache)` 或 `200 (from memory cache)`。

- **Expires**（HTTP/1.0）：使用**绝对时间**，如 `Expires: Wed, 21 Oct 2026 07:28:00 GMT`。缺点是依赖客户端时钟，客户端调时间就会失准。
- **Cache-Control**（HTTP/1.1，推荐）：使用**相对时间**或其他指令，如 `Cache-Control: max-age=3600`。两者同时存在时以 `Cache-Control` 为准。

常用指令：

> 示意片段（无配套脚本）

```http
Cache-Control: no-cache    # 协商缓存：每次使用前都去服务器确认
Cache-Control: no-store    # 完全禁止缓存（敏感数据）
Cache-Control: max-age=3600  # 强缓存 3600 秒
Cache-Control: public      # 可被任何缓存（含代理）缓存
Cache-Control: private     # 只能被浏览器私有缓存
```

### 2. 协商缓存（Last-Modified / ETag）

命中协商缓存时，浏览器会**携带上次的验证信息**发起一个带条件请求，服务器返回 `304 Not Modified`（不带正文），浏览器再使用缓存副本；若资源已变化，服务器返回 `200` 和完整的新资源。

有两对字段：

- **Last-Modified / If-Modified-Since**（基于时间）：
  - 首次响应带 `Last-Modified: 2026-06-01T10:00:00Z`（资源最后修改时间）。
  - 后续请求带 `If-Modified-Since: 上次的时间`，服务器比较时间决定 304 或新资源。
  - 局限：时间精度只有秒级，同一秒内改两次就检测不到。

- **ETag / If-None-Match**（基于内容指纹，更精确）：
  - 首次响应带 `ETag: "5f8c2a-19d4"`（内容的哈希/版本指纹）。
  - 后续请求带 `If-None-Match: "5f8c2a-19d4"`，服务器比较指纹决定 304 或新资源。

优先级：**ETag 优先于 Last-Modified**——`If-None-Match` 会让服务端忽略 `If-Modified-Since`，因为指纹比时间精确。

**协商缓存的成立条件**——校验字段必须稳定：

- **`ETag` 必须是内容指纹**：有些框架默认给 `ETag` 拼随机值或时间戳，效果是每次校验都对不上、回 200 全量，协商缓存等于没配。
- **`Vary` 会进缓存键**：CDN 与浏览器缓存命中时，缓存的键是「URL + `Vary` 里声明的请求头」。`Vary: Accept-Encoding` 正常且必要（gzip / br 各存一份）；但 `Vary: User-Agent` 会让每个 UA 一份副本，命中率直接崩掉。要按设备给不同内容，用 URL 区分（`/m/` 前缀）。

### 3. stale-while-revalidate：过期了也还能用

`max-age=60, stale-while-revalidate=600` 的意思：60 秒内新鲜；60 秒到 660 秒之间**已过期但允许先用旧的**，同时后台发起刷新；超过 660 秒必须同步请求。按 `Age`（副本已存活秒数）分三个区间：

| 响应的 Age | 状态 | 客户端行为 |
| --- | --- | --- |
| Age=30s | 新鲜 | 不发请求 |
| Age=300s | 过期但在 swr 窗口内 | 先用旧数据渲染，后台悄悄刷新 |
| Age=1200s | 过期且超出窗口 | 同步重新请求 |

它解决的是一个很具体的矛盾：列表页 / 详情页这类数据，**稍微旧一点用户根本感知不到**，但每次都同步等后端就是白白增加 TTFB。配上 swr 之后，用户立刻看到内容，同时缓存被后台更新。配合 `stale-if-error` 还能在源站 5xx 时继续用旧内容兜底。

代价要写清楚：**用户可能看到旧数据**，所以只适合「可容忍轻微延迟」的资源，库存、余额、权限这类不行。

### 4. 缓存决策流程

> 示意片段（无配套脚本）

```
① 发起请求
   │
   ▼
② 检查强缓存（Cache-Control/Expires）
   ├── 命中 ──► 直接使用本地副本，不发请求 ✓
   └── 未命中
         ▼
③ 携带条件（If-None-Match / If-Modified-Since）发起协商请求
   ├── 服务器返回 304 ──► 使用本地副本，只是重新确认 ✓
   └── 服务器返回 200 + 新资源 ──► 更新本地缓存
```

### 5. 按资源类型配头与验收

这是一份可以直接照着用的表：

| 资源 | 推荐响应头 | 理由 |
| --- | --- | --- |
| 带内容哈希的 JS / CSS / 字体 / 图片 | `public, max-age=31536000, immutable` | URL 变了内容才变，可以放心长缓存；`immutable` 明确告诉浏览器新鲜期内连 F5 都别重新验证 |
| HTML 入口 | `no-cache`（+ 弱验证 `ETag`）或 `max-age=0, must-revalidate` | 必须能及时拿到新版本的资源引用 |
| Service Worker 文件 | `no-cache` | 它决定后续所有资源的缓存策略，必须最先更新 |
| 接口数据（可容忍轻微延迟） | `max-age=60, stale-while-revalidate=600` | 秒开 + 最终一致 |
| 接口数据（必须实时） | `no-cache` + `ETag` | 至少省掉正文与带宽 |
| 登录态 / 支付结果 | `no-store` | 不允许留在任何一层磁盘上 |

**怎么确认真配对了**：

1. DevTools Network 面板看 **Size 列**——`(memory cache)` / `(disk cache)` 表示强缓存命中，`304` 表示协商缓存走了校验。
2. 看响应头里的 `Age` 与 CDN 的 `X-Cache`，确认命中的是边缘而不是回源。
3. 用 `curl` 手动验证协商缓存：`curl -I -H 'If-None-Match: "xxx"' <url>`，看是否真的回 304。
4. 发布流程里加一条检查：**新版本的 HTML 引用的资源名是否都带上了新的哈希**——哈希没更新，说明构建缓存或 CDN 缓存在捣乱。

## 六、CDN：把缓存搬到离用户更近的地方

CDN 就是把「同一套缓存规则」放到离用户更近的机器上执行，规则本身上面已经吃透，但有**三件事是 CDN 层额外引入的**：

**1. 缓存键的决定权在 CDN 配置里。** 大多数 CDN 默认按「完整 URL（含 query）」缓存，也允许忽略部分 query 参数（如把 `?t=timestamp` 忽略掉）。忽略错参数会造成**串号**——把带用户身份的参数忽略掉，就是一次安全事故。忽略参数只对「纯缓存击穿用途」的查询串做。

**2. 缓存分层与回源。** CDN 边缘节点之上还有中间的父层（也有厂商叫中心层），未命中时它先问父层，父层再回源。所以「源站 QPS 没涨」不等于「缓存真的命中了边缘」。判断命中层级看响应头：各家会加 `X-Cache: HIT/MISS`、`X-Cache-Lookup`、`Age`（`Age` 很大说明命中的是很早的副本）。

**3. 刷新（purge）的粒度与代价。** 发布新版本时，带内容哈希的静态资源不需要刷新（URL 变了就是新资源）；需要刷新的只有**不带哈希的入口文件**（HTML、Service Worker 文件、配置 JSON）。刷 CDN 是异步且可能延迟生效的操作，所以要紧的入口文件宁可配短 `max-age`（如 `no-cache` + ETag），也别指望「发布后我一定刷得掉」。

**预热（prefetch）**是反向操作：新版本发布前主动把热门资源推到边缘，避免发布瞬间所有边缘都回源造成雪崩。

## 七、DNS 解析流程

**DNS（Domain Name System，域名系统）** 负责把人类友好的**域名**（`example.com`）解析成机器可读的 **IP 地址**（`93.184.215.14`）。

### 1. 解析流程（递归 + 迭代）

当浏览器请求 `https://www.example.com` 时，大致步骤：

> 示意片段（无配套脚本）

```
① 浏览器本地缓存 + Hosts 文件 —— 有则直接用
      │ 未命中
② 系统/操作系统 DNS 缓存 —— 有则返回
      │ 未命中
③ 向"本地 DNS 服务器"(通常是运营商/LAN提供的, 如 8.8.8.8 或 114.114.114.114)发起递归查询
      │
      ▼
④ 本地 DNS 若没有，则开始"迭代查询":
   a. 查询根域名服务器(. 根) → 得到 .com 顶级域服务器地址
   b. 查询 .com 顶级域服务器 → 得到 example.com 权威服务器地址
   c. 查询 example.com 权威服务器 → 得到 www.example.com 的 IP
      │
      ▼
⑤ 本地 DNS 拿到 IP → 逐级缓存 → 返回给浏览器
```

### 2. 关键概念

- **递归查询**：客户端→本地 DNS，由本地 DNS 负责"跑完整流程"并回结果。
- **迭代查询**：本地 DNS→根/顶级/权威服务器，逐层"指路"，每次只给出下一级地址。
- **权威服务器（Authoritative）**：对特定域名拥有最终答案的服务器。
- **缓存**：浏览器、OS、本地 DNS 都有缓存，`TTL` 决定缓存时长；合理设置 TTL 可以平衡变更速度与解析性能。

### 3. 常见的优化手段

> 示意片段（无配套脚本）

```html
<!-- DNS 预解析 -->
<link rel="dns-prefetch" href="//api.example.com" />

<!-- 预连接（预解析 + TCP/TLS 握手预热） -->
<link rel="preconnect" href="https://cdn.example.com" />
```

## 八、WebSocket

WebSocket 是 HTML5 提供的**全双工**通信协议：基于 TCP，**复用 HTTP 的握手通道**，握手完成后建立持久连接，服务器与客户端**双向主动推送**。协议标识符是 `ws://`（加密 `wss://`）。

### 1. 为什么需要它

HTTP 是"请求-响应"模型，**服务器无法主动推送**。实时场景（聊天、行情、协作编辑）只能靠轮询模拟：

| 方案 | 原理 | 实时性 | 资源消耗 |
| --- | --- | --- | --- |
| 短轮询 | 客户端定时发 HTTP 请求 | 取决于间隔 | 大量无效请求，最浪费 |
| 长轮询 | 请求挂起，服务器有数据才响应，客户端再发起 | 较好 | 连接挂起也占资源 |
| SSE | 服务器声明返回流信息，单向持续推送（基于 HTTP） | 好 | 单向，客户端不能推 |
| WebSocket | 全双工持久连接 | 最好 | 连接开销在握手，之后极省 |

**兼容性顺序与性能顺序正好相反**：性能上 WebSocket > SSE > 长轮询 > 短轮询；兼容性（支持广度）上则相反。所以老项目用轮询兜底，新项目实时通信首选 WebSocket。

### 2. 与 HTTP 的区别

- **连接方式**：HTTP 短连接（一次请求一次响应，靠 Keep-Alive 复用）；WebSocket 一次握手、长驻连接。
- **通信方向**：HTTP 半双工（客户端发起）；WebSocket 全双工（双方随时互发）。
- **数据格式**：HTTP 头部冗长；WebSocket 数据帧轻量（二进制/文本）。
- **同源限制**：HTTP 有同源策略与 CORS；WebSocket **没有同源限制**，但服务端要校验 `Origin` 防跨站连接攻击。

### 3. 基本用法

> 示意片段（无配套脚本）

```js
const ws = new WebSocket("wss://example.com/ws");
ws.onopen = () => ws.send("hello");   // 连接建立后发送
ws.onmessage = (e) => console.log(e.data); // 收消息（MessageEvent.data）
ws.onclose = () => console.log("closed");
```

工程要点：断线自动重连（`close` 后按退避策略重连）、心跳保活（定时发 ping 防代理掐断空闲连接）、`wss://` 加密传输、`Origin` 白名单校验。

## 九、同源策略与 CORS

前面讲的是协议本身。这一节讲的是**浏览器额外加的一道门**：同源策略（Same-Origin Policy）决定了一个页面的脚本能读哪些响应、能操作哪个 iframe 的 DOM，而 CORS（Cross-Origin Resource Sharing）是这道门上唯一的官方"放行条"。

### 1. 同源：三要素

**源（Origin）= 协议 + 域名 + 端口**，三者完全一致才同源。假设页面来自 `http://localhost:5177/page.html`：

| 目标地址 | 同源？ | 原因 |
| --- | --- | --- |
| `http://localhost:5177/other.html` | ✅ | 三要素全同 |
| `https://localhost:5177/` | ❌ | 协议不同（`http` → `https`） |
| `http://api.localhost:5177/` | ❌ | 域名不同 |
| `http://localhost:5178/` | ❌ | **端口不同** |
| `http://127.0.0.1:5177/` | ❌ | 域名不同（`localhost` 与 `127.0.0.1` 是两个 host） |

同源策略管的是**"读"**，不是**"发"**：

- 跨源的 `<script>` / `<img>` / `<link>` 标签**可以加载并执行/展示**——这正是 XSS 与 CSRF 能成立的前提。
- 跨源的 `fetch` / `XHR` **请求会正常发出去**，服务端也会正常处理；被拦的只是"把响应交给 JS 读取"这一步。
- 同源策略还保护 DOM 与存储：跨源 iframe 的 DOM 读不到、`localStorage` 按源隔离、Cookie 另有自己的域规则。

### 2. 两种跨源请求：简单请求与预检

浏览器把跨源请求分成两类，走完全不同的流程：

| | 简单请求 | 非简单请求 |
| --- | --- | --- |
| 方法 | 仅 `GET` / `HEAD` / `POST` | 其它方法（`PUT` / `DELETE` / `PATCH`…） |
| 请求头 | 仅 CORS 安全列表（`Accept` / `Accept-Language` / `Content-Language` / `Range` 等），`Content-Type` 的值只能是 `application/x-www-form-urlencoded`、`multipart/form-data`、`text/plain` | 带任何自定义头，或 `Content-Type` 用其它值 |
| 流程 | 直接发真实请求，浏览器检查响应里的 `Access-Control-Allow-Origin` 决定 JS 能否读 | **先自动发一个 `OPTIONS` 预检**，通过后才发真实请求 |
| 页面代码感知 | 只看到一次请求 | 只写了一次 `fetch`，实际产生两次请求 |

最容易踩的一条：**`Content-Type: application/json` 不在安全值列表里**，所以"用 JSON 提交一个 POST"几乎必然触发预检。这不是 bug，而是规范故意留的"先问一句"。

### 3. 服务端要回的响应头

| 响应头 | 作用 | 出现时机 |
| --- | --- | --- |
| `Access-Control-Allow-Origin` | 允许哪个源读取响应：`*` 或一个具体源 | 每次跨源响应 |
| `Access-Control-Allow-Methods` | 预检时告知允许的方法 | 仅预检 |
| `Access-Control-Allow-Headers` | 预检时告知允许的请求头 | 仅预检 |
| `Access-Control-Allow-Credentials` | 是否允许带凭据（Cookie / 客户端证书） | 需要凭据时 |
| `Access-Control-Max-Age` | 预检结果缓存多久（少一次往返） | 仅预检 |
| `Access-Control-Expose-Headers` | 额外放行哪些响应头给 JS 读 | 需要读自定义响应头时 |

两条硬规则：**`Allow-Credentials: true` 与 `Allow-Origin: *` 不能同时出现**（回显具体源才行）；**自定义响应头默认对 JS 不可见**，必须在 `Expose-Headers` 里列出来。

### 4. 跨源失败时为什么查不到原因

被 CORS 拦下时，JS 侧拿到的只有 `TypeError: Failed to fetch`——**没有状态码、没有响应头、也没有失败原因**。这是浏览器故意的：如果给出细节，就等于让脚本能探测别的源。所以定位跨源问题必须靠两个地方：

- **Network 面板**：请求是红色的（(blocked: cors) 之类），但 `/api/data` 的响应体其实是服务端真返回的内容——因为请求确实到了服务端。
- **Console**：浏览器会在这里给出具体原因，例如"缺少 `Access-Control-Allow-Origin`"、"credentials mode 为 include 时 `Allow-Origin` 不能用通配符"。

推论有两条：**排查时不要以为"请求没发出去"**；反过来，**CORS 不能当鉴权**——它只在浏览器里生效，绕过浏览器（curl / 服务端转发）就完全没有约束，服务端该做的鉴权一个都不能省。

还有一个常见误解：`fetch(url, { mode: 'no-cors' })` 不是"绕过 CORS"，它只是允许发出一个**不透明响应**（`type: 'opaque'`，`status` 恒为 0、内容读不到）——适合给 CDN 预热、上报这类不关心结果的请求。

### 5. 工程实践

- **首选不跨源**：接口与页面收敛到同一个域（网关 / BFF 统一前缀），开发期用 dev server 代理（Vite 的 `server.proxy`、webpack 的 `devServer.proxy`）把 `/api` 转出去。跨域问题在架构上消灭掉，比在响应头上调参可靠得多。
- **必须跨源时**：
  - 不涉及凭据 → `Allow-Origin: *` 最省事，但**不能再加 `Allow-Credentials`**。
  - 涉及 Cookie / 双向 TLS → 白名单校验 `Origin` 后**回显具体源** + `Allow-Credentials: true`，前端同时要写 `credentials: 'include'`。
  - 自定义响应头要在 `Expose-Headers` 里列出，否则前端读不到。
  - 减少预检：能落在简单请求里就落（方法、`Content-Type`、请求头三项都受约束）；否则给 `Max-Age` 把预检结果缓存起来——但改了允许的方法或头之后，要确认客户端没在用旧缓存。
- **别配成"回显任意 Origin + `Allow-Credentials: true`"**：那等于让任何站点都能带着用户 Cookie 读你的接口，同源策略被彻底关掉。这是配置层面的常见事故，与[「前端安全」](./前端安全.md)里的 CSRF 直接相关。
- 顺带区分一个容易混的概念：**"跨源"与"跨站"不是一回事**。Cookie 的 `SameSite` 判的是**站点**（协议 + 可注册域，不看端口），所以 `5177` → `5178` 这种"跨源但同站"的请求，`SameSite` 限制并不生效；真正决定它能不能被读的是 CORS。
