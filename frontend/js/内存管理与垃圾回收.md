# 内存管理与垃圾回收

## 一、值类型与引用类型

JavaScript 的数据可分为两大类，它们在内存中的存储和传递方式完全不同。

- **值类型（原始类型）**：`number`、`string`、`boolean`、`null`、`undefined`、`symbol`、`bigint`。它们直接保存"值本身"。
- **引用类型（对象类型）**：`Object`、`Array`、`Function` 以及各种类实例。变量里保存的是"指向内存中对象的地址"。

> 示意片段（无配套脚本）

```js
// 值类型：赋值即拷贝，互不影响
let a = 10;
let b = a;
b = 20;
console.log(a); // 10

// 引用类型：赋值拷贝的是"引用地址"，指向同一个对象
const obj1 = { count: 1 };
const obj2 = obj1;
obj2.count = 99;
console.log(obj1.count); // 99
```

> 示意片段（无配套脚本）

```js
// 比较同样不同：值类型按值比较，引用类型按"引用地址"比较
console.log(1 === 1);            // true
console.log({a:1} === {a:1});    // false（两个不同对象，地址不同）
```

## 二、栈（Stack）与堆（Heap）

运行时内存大致分为两大区域：

- **栈（Stack）**：结构紧凑、固定容量、先进后出。存放**值类型的值**、函数调用时的**作用域/局部变量/上下文**以及**引用地址**。分配和释放极快（函数结束自动出栈）。
- **堆（Heap）**：灵活、容量大、无固定顺序。存放**对象本体**。对象何时释放不再由栈决定，而交给 GC。

> 示意片段（无配套脚本）

```js
function foo() {
  let local = "我是局部变量";   // 存栈上
  const obj = { name: "hi" }; // 引用地址存栈，对象本体存堆
  return obj;
}
const ret = foo(); // foo 结束后 local 随栈弹出而释放，但 obj 对象仍在堆上
```

一个核心结论：**对象生命周期比函数作用域更长**——函数返回后局部变量销毁了，但它返回的对象只要还被引用，就仍然存活。这正是"引用计数"要解决的问题。

## 三、垃圾回收的基础策略

GC 要回答一个问题：**怎么判断一块内存"没用了"，可以回收？** "没用了"不是看"还变不变量名"，而是看**能否从根出发被访问到**。根（Roots）包括全局对象、当前执行栈中的变量与函数上下文；从根出发能遍历到的对象叫**可达（live）**，不可达的就是可回收的垃圾。历史上先后出现过两条判定思路，演化出一条清晰的演进链，最终胜出者成为现代引擎的基石。

### 1. 引用计数（Reference Counting）：最早的朴素思路

为每个对象记录"被引用的次数"，次数归零即回收——这是最直觉的思路：没被任何人引用了，就说明没用了。

> 示意片段（无配套脚本）

```js
const a = {};
const b = a; // a 指向的对象引用计数 +1（两次：a、b）
a = null;
b = null;    // 归零，回收
```

致命缺陷：**无法处理循环引用**。两个对象互相引用，外部无人引用时计数永远不为零，导致泄漏。

> 示意片段（无配套脚本）

```js
function cycle() {
  const o1 = { next: null };
  const o2 = { next: null };
  o1.next = o2; // 互相引用
  o2.next = o1;
  // 函数结束后，o1、o2 从外部不可达，但彼此引用导致计数不清零
}
cycle(); // 引用计数法下，这两个对象成为"不可回收的孤岛"
```

> **落点**：正因为无法处理循环引用，现代 V8 已不在主路径上单独使用纯引用计数（它只可能作为启发式辅助）。它在演进链中的意义是**铺垫**——引出为何需要一种"以根为准、能穿透循环引用"的判定方式（即下一种策略），也帮你理解"对象生命周期比函数作用域更长"（见「二」）为何需要 GC 而非靠栈弹出。

### 2. 标记清除（Mark-and-Sweep）：击败引用计数成为主流

从 JS 的**根对象**（全局对象、当前执行栈中的变量、调用栈等）出发，递归遍历所有可达的引用，把能到达的对象打上"存活"标记；遍历结束后，**没有被标记的对象就是垃圾**，统一清除。

> 示意片段（无配套脚本）

```js
let x = {};
x = null; // 原来的 {} 不再被任何根可达引用，标记清除时被回收
```

优雅地绕过了引用计数的死穴：它以根为起点判断可达性，两个互指但外部不可达的对象，都不会被标记为存活，能一起回收。

但它也有代价：**内存地址不连续，容易产生碎片**。标记存活后留下的空洞散布在堆里，后续分配大对象时可能因找不到连续块而失败。

> **落点**：标记清除的"碎片问题"正是引出「标记整理」的原因——老生代在碎片率高时切换到标记整理（Mark-Compact）消除碎片，详见「五、避免主线程停顿」。

### 3. 分代收集（Generational GC）：策略如何落地

经验规律：**绝大多数对象的生命周期都很短**。于是 GC 将堆分成不同"代"，对不同代用不同频率、不同策略回收，这一思想叫**分代收集**。年轻对象高频回收，长命对象低频回收（老生代）。

> **落点**：分代收集决定了"标记清除"在现代引擎里落在哪个阶段、以什么形态出现——这正是「四、V8 的堆结构」的整体框架。

## 四、V8 的堆结构与新生代/老生代

V8 是现代浏览器与 Node 采用的 JS 引擎。它的堆从逻辑上分成多个区域，核心是**新生代（Young Generation）**与**老生代（Old Generation）**。

### 1. 新生代（Young Generation）

- 存放**生命周期短**的刚创建对象。
- 采用 **Scavenge（半空间复制）**算法：把新生代分成 **From 空间**和 **To 空间**两块同大小的半区。
- 回收时：遍历 From 中的存活对象，**复制**到 To 空间，然后整体清空 From、并交换两块空间的角色（From↔To）。
- 代价是牺牲一半空间换极高吞吐，因为新生代对象绝大多数很快死亡，存活复制的很少。

> 示意片段（无配套脚本）

```js
// 直观示意（伪代码，非真实 API）
// 对象在 From 中被创建；发生 GC 时存活对象复制到 To，清空 From，切换角色
function scavenge(from, to) {
  for (const alive of from.aliveObjects()) {
    to.push(alive); // 复制存活对象
  }
  from.clear();
  [from, to] = [to, from]; // 交换
}
```

- **晋升（Promotion）**：当对象经历了多次 GC 仍存活（如一次 Scavenge 后仍有引用），或 To 空间放不下时，会被**晋升**到老生代。

### 2. 老生代（Old Generation）

- 存放**长命对象**：晋升来的对象、全局对象、大对象等。
- 空间大、对象存活率高，不适合复制，回收形态有两种：
  - **标记清除（Mark-Sweep）**：默认形态。先从根标记存活对象，再清除未标记的。速度快、代价是留碎片。
  - **标记整理（Mark-Compact）**：**按需触发**。当碎片率高、分配不出连续大块时才切换：把存活对象搬移到一端连成片，再清掉边界外所有内存。搬移要改写所有指向这些对象的指针，比清除慢得多。
- 两者的关系是**互补而不是先后**：平时标记清除够用；碎片积累到影响分配时，那一次回收才升级成标记整理。

### 3. 完整链路

把「三」的判定策略和上面的分代框架串起来，就是一次完整的对象一生：

> 示意片段（无配套脚本）

```
创建对象
   │
   ▼
新生代（Scavenge 高频回收，复制存活对象，天然无碎片）
   │  多次存活 / 空间不足 → 晋升
   ▼
老生代
   ├─ 标记段：从根出发标记存活（增量 + 并发，避免长时间停顿）
   ├─ 清除段：清掉未标记对象（惰性/并发，分批做）
   └─ 整理段：仅当碎片率高时，本次回收升级为标记整理（搬移存活对象消除碎片）
```

一句话串起来：**先分代；新生代用复制；老生代默认"标记 → 清除"，标记段靠增量/并发压停顿，清除段惰性做，碎片高了才把这一次升级为标记整理。**

## 五、避免主线程停顿：优化压在老生代的标记与清除上

老生代空间大、对象图复杂，扫描与清除耗时会长；这段时间若主线程完全暂停（Stop-The-World），页面就卡顿。V8 的优化思路是**把耗时的阶段拆小、挪到后台**——注意这些手段只作用于老生代（新生代 Scavenge 本来就快，不需要）：

- **标记段——增量标记（Incremental Marking）**：把一次全量标记拆成许多小步骤，穿插在 JS 执行间隙完成，避免一口气卡住主线程。
- **标记段——并发标记（Concurrent Marking）**：标记工作放到**后台线程**做，主线程继续跑 JS；主线程期间改了引用关系，再由短暂的重新扫描兜底。
- **清除段——惰性清理 / 并发清理**：垃圾不必一次清完，可以边执行边分批清，或交给后台线程。

一个常见误解要纠正：**「标记 → 清除 → 整理」不是每次回收必走的三段**。整理是**按需升级项**——只有碎片率高到影响分配时，那一次回收才从标记清除切换成标记整理（搬移存活对象、重写指针，代价远高于清除），所以它的停顿优化手段也是独立的：整理本身也可以增量、并发地搬移，且 V8 通过空闲内存分列表（Free List）优先复用碎片块，尽量降低触发整理的频次。

一句话：**分代定框架，新生代复制，老生代标记清除为主；标记靠增量 + 并发压停顿，清除靠惰性分批，碎片高了才升级整理。**

> 示意片段（无配套脚本）

```js
// 没有可直接调用的"手动 GC" API（开发时不建议）
// 但调试时可在 Chrome DevTools 的 Memory 面板点击垃圾桶图标触发一次 GC
```

补充：V8 给了少量相关参数，但决定引擎行为，**生产代码不应依赖它们**，仅作了解：

> 示意片段（无配套脚本）

```js
// Node 启动参数（演示，非推荐使用）
// node --max-old-space-size=4096 app.js   // 限制老生代最大堆
// node --max-semi-space-size=64   app.js   // 调整新生代半区大小
```

## 六、常见内存泄漏（Memory Leak）

内存泄漏指"本应被回收的内存，因残留引用而无法释放"，长期累积会导致页面卡顿、崩溃。以下是五个头号元凶。

### 1. 意外的全局变量

未声明的变量会被挂到全局，且全局对象常被根可达，永远不回收。

> 示意片段（无配套脚本）

```js
function leak() {
  data = "我不小心变成全局变量了"; // 忘记用 let/const/var 声明
}
leak(); // data 被放到全局，无法回收
```

规避：开启严格模式 `"use strict"`，它在赋值给未声明变量时直接抛错。

### 2. 闭包导致的对象固化

闭包会长期持有其外部作用域，若外部变量引用大对象，即使闭包"用完了"该对象也不释放。

> 示意片段（无配套脚本）

```js
function create() {
  const bigData = new Array(1000000).fill(0);  // 大对象
  return function () {
    console.log("hello");
    // 虽然函数没用 bigData，但闭包仍持有它
  };
}
const fn = create(); // bigData 因被 fn 闭包持有而无法回收
```

规避：让闭包**只捕获所需的最小变量**，用完即置空，或在函数体内快速释放不再引用的大对象。

### 3. 事件监听未移除

向 DOM 或全局对象添加的监听器会形成引用链。如果监听器引用了大对象，而监听器未被移除，泄漏就产生了。

> 示意片段（无配套脚本）

```js
const handler = () => { /* 内部可能引用了大对象 */ };
window.addEventListener("scroll", handler);
// 换肤/卸载时忘记 removeEventListener("scroll", handler)
```

规避：成对使用 `removeEventListener(同名同函数)`；或使用 `AbortController` 批量取消：

> 示意片段（无配套脚本）

```js
const ac = new AbortController();
window.addEventListener("scroll", handler, { signal: ac.signal });
ac.abort(); // 一次性移除该信号下的所有监听
```

### 4. 定时器未清理

`setInterval` 的回调会持续执行并持有其引用，忘记 `clearInterval` 会一直占用。

> 示意片段（无配套脚本）

```js
setInterval(() => {
  // 每 200ms 累积数据，又不清理 interval
  cache.push(fetchBigPayload());
}, 200);
```

规避：页面卸载（`beforeunload` / Vue `onBeforeUnmount` / React effect cleanup）时 `clearInterval` / `clearTimeout`，并把回调里临时大引用置空。

### 5. 分离的 DOM 节点（Detached DOM）

用 JS 变量把 DOM 节点从文档中"摘除"后仍持有引用，节点虽不可见却无法回收。

> 示意片段（无配套脚本）

```js
let detached;
function create() {
  const div = document.createElement("div");
  div.textContent = "我会被分离";
  document.body.appendChild(div);
  detached = div;      // 之后即使 remove 出文档，detached 仍引用它
  document.body.removeChild(div); // 分离却仍被 detached 持有
}
create();
```

规避：分离 DOM 后务必清空对它的引用（`detached = null`），或重建节点。

### 完整清单自查表

| 泄漏类型 | 典型例子 | 规避手段 |
| --- | --- | --- |
| 全局变量 | 忘记声明、挂到 window | "use strict"、尽量局部化 |
| 闭包固化 | 闭包持有大对象 | 最小捕获、及时置空 |
| 事件监听 | scroll/click 未移除 | removeEventListener / AbortController |
| 定时器 | setInterval 未清理 | 生命周期结束 clear |
| 分离 DOM | 摘除后仍引用节点 | 置空引用 |
| 全局缓存/Map | 缓存无限增长 | 限制容量、定期清理、WeakMap |

## 七、如何检测内存

### 1. Performance API 初步诊断

浏览器提供了内存信息，可粗略观测：

> 示意片段（无配套脚本）

```js
// Chrome 等浏览器支持 performance.memory（非标准，仅作观测）
const mem = performance.memory;
console.log(mem.usedJSHeapSize / 1024 / 1024, "MB 已用"); // 已用堆
console.log(mem.totalJSHeapSize / 1024 / 1024, "MB 总量"); // 总堆
```

Node 端可用 `process.memoryUsage()`：

> 示意片段（无配套脚本）

```js
const mem = process.memoryUsage();
console.log(mem.heapUsed / 1024 / 1024, "MB heapUsed");     // 堆已用
console.log(mem.external / 1024 / 1024, "MB external");     // 底层（Buffer 等）
console.log(mem.rss / 1024 / 1024, "MB RSS");               // 常驻内存
```

### 2. Chrome DevTools —— Memory 面板

这是定位前端泄漏的主力工具，常用三招：

1. **Performance（性能）记录**：录制交互过程，观察内存曲线是否"只升不降"或阶梯式抬升（齐步向上 = 泄漏信号）。
2. **Memory → Heap Snapshot（堆快照）**：抓取某一时刻的堆，对照分析。可操作"垃圾桶"强制 GC 后再抓，对比 `Detached DOM`、超大数组等对象是否仍存在。
3. **Allocation instrumentation（分配采样）**：记录分配来源，回放交互找出"谁在持续分配却不释放"。

### 3. 排查泄漏的标准姿势

> 示意片段（无配套脚本）

```js
// 思路（伪流程）
// 1. 打开 DevTools Performance，录制一段"重复操作 + 复位"的流程
// 2. 观察内存曲线：泄漏表现为台阶式/一直上升，不复位
// 3. Memory 抓 Heap Snapshot，按 Retained Size 排序找大对象
// 4. 查看对象的引用路径（Retainers），定位是谁还握着它
// 5. 修复后再次录制，确认曲线回落
```

## 八、WeakMap 与 WeakSet：为弱引用而生

普通 `Map`/`Set` 持有的是**强引用**，会阻止 GC 回收其键/值；而 **Weak** 版持有**弱引用**，不阻止回收，是预防缓存类泄漏的利器。

### 1. 为什么用它们

> 示意片段（无配套脚本）

```js
// 强引用：Map 的键一直保存对象，即使外部不再使用也不回收 → 缓存泄漏
const cache = new Map();
function process(obj) {
  cache.set(obj, { data: ... }); // obj 永远被 cache 强引用
}
```

用 `WeakMap`，当对象的其他强引用消失后，条目会被 GC 自动清掉，从而**不会阻止回收**：

> 示意片段（无配套脚本）

```js
const wcache = new WeakMap();
function process(obj) {
  wcache.set(obj, { data: /* ... */ });
}
// obj 不再被外部引用时，WeakMap 里的条目可被 GC 回收
```

### 2. 关键限制（设计如此）

- 键必须是**对象**（不能是原始类型）。
- 没有 `size` 属性，不支持 `keys()` / `values()` / `entries()` 迭代，也（对 WeakMap）没有 `.clear()`。
- WeakSet 元素也必须是对象，且不能迭代。

这些限制恰恰是"弱引用、可回收"承诺的代价——引擎无法在对象还被迭代时安全回收。

### 3. 典型应用：对象私有数据 / 缓存

> 示意片段（无配套脚本）

```js
// 给对象附加私有元数据，不污染原型，不阻止回收
const meta = new WeakMap();
function setSize(el, size) {
  meta.set(el, size);
}
function getSize(el) {
  return meta.get(el);
}
```

> 示意片段（无配套脚本）

```js
// DOM 用完即丢的临时缓存
const cache = new WeakMap();
function memo(el) {
  if (cache.has(el)) return cache.get(el);
  const res = expensiveWork(el);
  cache.set(el, res);
  return res;
}
```

> **Why WeakMap 是内存安全的**：当元素本身被移除/不再可达时，对应条目会被 GC 自动清理，无需手动 `delete`，也天然规避了"缓存无限增长"的泄漏。
