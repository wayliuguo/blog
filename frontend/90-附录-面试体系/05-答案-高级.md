## 第一阶段：框架原理与架构（96-105）

### Q96: React 的 Fiber 架构是什么？它解决了什么问题？

① **一句话结论**：Fiber 是 React 16 重新设计的"可中断的协调（reconciliation）"架构，用链表结构的 Fiber 节点 + 双缓冲工作循环，实现了渲染的可中断、可调度。

② **解决的问题**：

- 旧版递归无法中断，更新量大时阻塞主线程，导致掉帧/卡顿。
- 需要按优先级调度更新（同步 vs 低优先级），支持并发渲染。

③ **核心机制**：

- **构建工作树**：渲染时创建 Fiber 节点组成的树（含 `return/child/sibling` 指针）。
- **双缓冲**：在内存中构建新的 Fiber 树（workInProgress），更新完成后切换（commit）到当前树，最后与真实 DOM 对齐。
- **可中断**：工作循环每执行一个"单元工作"就检查是否要让出（`shouldYield`），让给浏览器渲染，通过时间片切分。
- **调度器（Scheduler）**：用优先级队列安排工作，可低优先级的更新被高优先级打断/推迟。

④ **阶段划分**：`render phase`（可中断，计算 diff）→ `commit phase`（不可中断，提交 DOM + 副作用）。

⑤ **追问**：Fiber 的 `workLoop` 与 `shouldYield` 如何工作？`Concurrent Mode` / `React 18 useTransition` 与 Fiber 的关系？

### Q97: React 的 Diff 算法原理是什么？

① **一句话结论**：React 的 diff 是"对同层级进行比较 + 用 key 优化"的同向 O(n) 经典算法，尽可能复用已有节点。

② **三大前提策略**：

1. **只比较同层级**：不做跨层跨级深度 diff，复杂度降到 O(n)。
2. **类型不同直接重建**：若两个节点的元素类型不同（`div` vs `span`），直接销毁重建。
3. **Set（key）**：同级数组用 key 判断移动与复用。

③ **比较流程**：

- 同级单节点：类型一致则复用（更新 props/子节点），否则重建。
- 多节点（列表）：根据顺序 + key 做"新增 / 删除 / 移动"处理。

④ **与 Vue 的对齐**：Vue 3 的 diff 用"头尾指针双端 + patchFlags"做更细粒度的静态/动态分离，而 React 依赖整棵组件树级协调 + `memo`。

⑤ **追问**：为什么不要用 index 当 key？diff 中"移动"怎么识别（最长递增子序列）？

### Q98: React 有哪些渲染优化手段（memo / PureComponent / SCU / 并发特性）？

① **一句话结论**：优化核心是"减少不必要的子组件重新渲染"与"让更新可中断"，手段包括 `React.memo`、`PureComponent`、`useMemo/useCallback`、并发特性。

② **手段**：

- **React.memo**：对函数组件的 props 做浅比较，props 没变则不重渲染。
- **PureComponent**：类组件的浅比较版 SCU。
- **shouldComponentUpdate**：手动控制类组件是否重渲染。
- **useMemo / useCallback**：缓存计算结果 / 稳定函数引用，避免子组件因 props 引用变化而重渲染。
- **拆分组件粒度**：让数据订阅在最内层（state 局部化），避免大范围重渲染。
- **并发特性**：`startTransition`、`useDeferredValue` 把低优先级更新做延后展示，`<Suspense>` + `lazy` 拆包。

③ **另外**：列表用 `key` 稳定、避免内联 `onClick={() => ...}`（每次新引用）、`useLayoutEffect` 减少可见闪屏。

④ **边界**：`memo` 不一定带来收益，浅比较本身也有开销；性能优化应从"真卡"为出发点。

⑤ **追问**：`memo` 的浅比较有什么局限？`startTransition` 如何降低输入卡顿？

### Q99: Vue 3 的响应式原理（Proxy）相比 Vue 2（Object.defineProperty）有什么优势？

① **一句话结论**：Vue 3 用 `ES6 Proxy` 对对象整体代理，弥补了 Vue 2 `Object.defineProperty` 劫持属性的先天局限。

② **Vue 2 局限（有所为何被替换）**：

- 只能劫持"已存在属性"，新增属性需 `Vue.set`。
- 数组下标修改 / 直接 `length` 变化侦测不到。
- 深度响应式需递归 `defineProperty`，开销与初始化成本高。

③ **Vue 3（Proxy）优势**：

```js
function reactive(target) {
  return new Proxy(target, {
    get: (t, k) => { track(t, k); return Reflect.get(t, k); },
    set: (t, k, v) => { const r = Reflect.set(t, k, v); trigger(t, k); return r; },
  });
}
```

- **整对象代理**：新增/删除属性、数组下标都能被拦截。
- **惰性收集**：getter 触发时收集依赖，比递归一上来劫持更高效。
- **可嵌套**：访问到未代理的嵌套对象时才去代理。

④ **兼容性**：Proxy 无法被完整 polyfill（ES5 无法模拟），因此 Vue 3 要求现代浏览器/环境支持 ES2015。

⑤ **追问**：`Reflect.get/set` 为什么配 Proxy 用？`ref` vs `reactive` 的取舍？

### Q100: Vue 3 的虚拟 DOM / 编译优化（patchFlags、静态提升）原理是什么？

① **一句话结论**：Vue 3 通过"编译时标记 + 运行时按标记 diff"，把静态内容提升、动态内容精确锁定，大幅减少不必要 diff。

② **编译优化**：

- **静态提升（hoisting）**：把不会改变的静态节点提升到渲染函数外，只创建一次，更新时整体复用。
- **patchFlags（补丁标记）**：编译时给动态节点打标记（如 `TEXT`、`PROPS`、`CLASS` 或 `condition`），运行时仅对标记的维度做 diff，跳过无关比较。
- **动态节点收集**：组件渲染时把动态子节点收集进 `dynamicChildren` 数组，diff 时只遍历这个"动态子数组"，跳过静态子树。

③ **对比**：Vue 2 是"整棵虚拟 DOM 全量 diff"（除非有 key / 静态文档）；Vue 3 借助编译信息做到"只比较动态部分"。

④ **vnode 结构贡献**：结合 `proxy` 响应式，Vue 3 更新粒度更细、更快。

⑤ **追问**：`v-once`、`v-memo` 与编译优化的关系？SSR 阶段的静态提升如何收益？

### Q101: 虚拟 DOM 的原理和优缺点是什么？

① **一句话结论**：虚拟 DOM（VDOM）是用 JS 对象描述"真实 DOM 的树状结构"，框架通过对比新旧 VDOM 差异（diff）最终批量更新真实 DOM。

② **原理**：

```js
const vnode = { type: 'div', props: { id: 'app' }, children: [...] };
```

render（VDOM → DOM）→ diff（新旧 VNode）→ patch（最小化更新真实 DOM）。

③ **优点**：

- **跨平台**：抽象自 DOM，可渲染到 DOM / Native / Canvas（React Native、Vue Native）。
- **批量/最小化更新**：比对后只改变化部分，避免频繁直接操作 DOM 的性能丢失。
- **声明式、可预测**：开发者只管描述 UI，更新交给框架。

④ **缺点 / 边界**：

- **有额外开销**：创建 VNode + diff 本身也有成本，超大数据额场景吞吐量未必优于手写 DOM。
- **首次渲染**：需先建 VDOM 再渲染，首屏相比直接操作 DOM 略慢。

⑤ **结论**：虚拟 DOM 的价值更多在"开发体验 + 跨平台 + 性能可控"，而非绝对性能最优。

⑥ **追问**：虚拟 DOM 与 Incremental DOM 对比？为什么虚拟 DOM 产生"torch"语义而惰性绑定（框架间对比）？

### Q102: React 和 Vue 你更倾向哪个？二者的设计哲学区别？

① **一句话结论**：React 强调"单向数据流 + 函数式 + 用 JS 表达一切（All in JS）"；Vue 强调"渐进式 + 模板友好 + 响应式自动优化"，均为优秀的社区级框架，倾向取决于团队与场景。

② **设计哲学对比**：

| 维度 | React | Vue |
|------|-------|-----|
| 理念 | JS 驱动一切（JSX），函数式，一切皆函数 | 渐进式，模板 + options/setup，模板驱动 |
| 学习曲线 | 需理解 hooks 心智 | 模板/响应式上手快，进阶需懂响应式 |
| 响应式 | 显式（状态 + 触发重渲染），手动 memo 优化 | 响应式依赖追踪，自动细粒度更新 |
| 状态与写法 | JSX 灵活、搭配 TSX | `<script setup>` 简洁、模板指令丰富 |
| 生态 | 路由/状态需选择库 | 官方整合度高（Router/Pinia） |

③ **倾向判断**：

- 喜欢 JS 函数式、大前端跨端（RN）用 React。
- 喜欢模板声明式、快速上手中后台、追求内置优化用 Vue。

④ **客观表述**：两者本质思想趋同（组件化 + 数据驱动 + 虚拟 DOM），都能应对大型项目；面试应展示"深度理解 + 有自己的判断依据"。

⑤ **追问**：两者的 diff、优化策略具体差别？在某个业务场景里你怎么选型？

### Q103: 微前端是什么？qiankun 和 Module Federation 的原理是什么？

① **一句话结论**：微前端是把一个大前端应用拆成多个可独立开发/部署的"子应用"，运行时聚合到主应用；主流方案有 qiankun（基于 JS 沙箱 + 单例框架）和 Webpack Module Federation（模块共享联邦）。

② **要解决的问题**：大型中后台工程体积大、各团队协作慢、发型批次耦合、技术栈异构。

③ **qiankun 原理**：

- **加载子应用**：借助 `single-spa` 的 `import-html-entry` 拉取子应用 HTML，解析并执行其 JS。
- **JS 沙箱**：用 Proxy 生成 `window` 代理，隔离子应用的全局变量污染，支持 `legacySandbox` / `proxySandbox`。
- **样式隔离**：给子应用 DOM 加上限定前缀（shadow DOM / scope attr）。
- **应用生命周期**：子应用暴露 `bootstrap/mount/unmount`。

④ **Module Federation 原理**：

- 打包出"共享模块谱（remote）"，运行时通过 `import('remote/xxx')` 动态加载并共享依赖 / 组件。
- 用 `exposes`/`remotes`/`shared` 配置，构建期生成 manifest，运行期 webpack 运行时加载远程模块，**可实现组件级共享而非整页面级**。

⑤ **差异**：qiankun 面向"应用级聚合 + 沙箱",MF 面向"模块级共享"，可结合使用。

⑥ **追问**：微前端的聚合适配 / 依赖共享 / 乾坤沙箱失效场景？子应用路由如何通信？

### Q104: 如何设计一个复杂中后台项目的整体架构？

① **一句话结论**：中后台架构遵循"分层、模块化、可扩展"，从目录、请求、状态、权限、路由、组件、异常处理几个维度设计。

② **分层/目录设计**：

```
src/
  api/        接口层（统一封装请求）
  components/ 通用组件 + 业务组件
  hooks/      复用逻辑
  stores/     状态（Pinia/Zustand）
  router/     路由 + 守卫
  directives/ 指令（权限、水印）
  utils/      工具
  layouts/    布局
  views/      页面
```

③ **关键能力设计**：

- **请求层**：封装 axios，统一 token 注入、错误码处理（401 刷新 / 跳登录）、超时重试、取消请求。
- **权限**：路由级（beforeEach 校验）+ 按钮/指令级（`v-permission`）；角色 + 权限点。
- **状态管理**：用户信息、权限、企业配置集中在 store。
- **组件库沉淀**：表格 / 表单 / 弹窗封装，配合 Schema 驱动（见低代码方向）。
- **路由懒加载 + 菜单动态注册**。
- **异常兜底与埋点**：全局错误边界，统一错误提示。

④ **工程保障**：TypeScript、ESLint、CI 校验、环境多套、规范化提交。

⑤ **追问**：如何拆分"可复用的业务组件"与"页面级组件"？微前端 vs 模块化如何选择？

### Q105: 如何从 0 设计并维护一个组件库？

① **一句话结论**：组件库设计关键是"API 稳定、类型齐全、可复用可扩展、配套工程化（构建/文档/测试/发布）"。

### Q106: 如何从 0 搭建一套完整的前端工程化体系？

① **一句话结论**：前端工程化包含"规范、构建、质量、部署、监控"五大支柱，在技术选型基础上把流程与工具串联起来。

② **五大支柱**：

1. **规范**：ESLint + Prettier + EditorConfig + husky（pre-commit）+ commitlint + git 工作流。

5. **监控**：错误上报（Sentry/自建）、性能监控（Core Web Vitals）、sourcemap 管理（脱敏上传）。

③ **落地顺序**：先进规范 → 再构建优化 → 加质量/CI → 最后监控。

④ **关键**：一切配置都通过"脚手架/模板"沉淀并团队共享，用 Monorepo 统一多个包。

⑤ **追问**：工程化如何衡量收益（构建时间、错误率、代码标准 ENFALL）？前端基建与后端基建的配合（发布/灰度）？

### Q107: Monorepo（pnpm workspace / turborepo）有什么优势？实现原理是什么？

① **一句话结论**：Monorepo 把多个相关包放在一个仓库统一管理，配合 workspace 依赖提升和构建缓存，提升协作与复用、节省磁盘与构建。

② **优势**：

- 代码共享与复用（跨包直接引用与统一改动）。
- 依赖统一管理，减少重复安装与版本漂移。
- 原子提交（一次变更跨包联动）、便于统一 CI 与规范。
- 增量构建与远程缓存加速。

③ **pnpm workspace 原理**：

- 用硬链接 + 符号链接实现"内容寻址存储（Stores）"，多项目共享同一份依赖，节省磁盘。
- 包通过 workspace 协议引用 `workspace:*`。

④ **turborepo 原理**：

- 基于任务依赖图 DAG 并行调度构建、测试。
- 任务缓存（`cache`）——输入 hash 不变则跳过（本地 + 远程缓存）。

⑤ **对比**：pnpm 侧重"依赖安装与管理",turborepo 侧重"任务编排与缓存加速"，常搭配使用。

⑥ **追问**：Monorepo 相比 Multirepo 的缺点（权限/大小/工具复杂度）？单仓库多项目的依赖如何隔离？

### Q108: 什么是 CI/CD？如何设计前端自动化构建与部署？

① **一句话结论**：CI（持续集成）是把代码变更自动拉取、构建、测试；CD（持续部署/交付）是把构建产物自动发布到环境；前端用它保证每次提交都是"可验证、可发布"的。

② **典型流程（Pipeline）**：

```text
push / PR
 → lint + type-check + unit test
 → build（打包 + 代码分割，产出静态资源）
 → 上传产物（CDN/对象存储 / 构建镜像）
 → 部署到环境（dev/staging/prod） + 健康检查
 → 通知（Slack/飞书）
```

③ **实现**：GitHub Actions / GitLab CI，`on` 定义触发，`jobs` 串并任务。

④ **前端要点**：

- 静态资源指纹缓存 + CDN 发布，file 资源时间戳/版本管理。
- 环境变量按目标注入（.env.dev / .env.prod）。
- 产物与 sourcemap 分离上传（sourcemap 不进生产公开）。
- 回滚：保留上一版本，失败可快速切换。

⑤ **追问**：蓝绿 / 金丝雀发布在前端怎么落地？构建产物如何做 CDN 版本回退？

### Q109: 如何设计一套前端监控体系（错误上报 / 性能监控 / 埋点）？

① **一句话结论**：前端监控体系涵盖"错误采集、性能上报、用户行为/埋点、告警与可视化排查"四层，核心是"采集 — 上报 — 聚合 — 告警 — 复盘"。

② **分层设计**：

- **错误采集**：
  - JS 异常：`window.onerror` / `unhandledrejection`。
  - 资源加载失败：`window.addEventListener('error', ..., true)` 捕获非 JS 资源。
  - 框架级：React `ErrorBoundary`、Vue `errorCaptured`。
  - 接口异常：封装请求层拦截（4xx/5xx/超时）。
- **性能上报**：`performance.getEntriesByType('navigation')` 计算 TTFB/FCP/LCP，`Long Tasks` 检测主线程阻塞；用 `web-vitals`。
- **埋点**：SPA 路由变化 + 关键事件（点击等），携带 `requestId`/`userId`/`sessionId`，采样率控制。
- **上报策略**：`navigator.sendBeacon`（页面关闭也能发）、图片打点、批量合并、避免影响主流程。

③ **聚合与可视化**：后端聚合按类型/版本/页面，结合 sourcemap 反推源码位置，看板（错误率、版本分布、上线回归）。

### Q110: 前端灰度发布和 A/B 测试如何实现？

## 第三阶段：SSR 与同构渲染（111-117）

### Q111: 什么是 SSR？和 CSR 有什么区别？SSR 的优缺点是什么？

① **一句话结论**：SSR（服务端渲染）是在服务端把组件渲染成完整 HTML 后发给浏览器；CSR（客户端渲染）是浏览器下载 JS 再渲染。

② **对比**：

| 维度 | CSR | SSR |
|------|-----|-----|
| 渲染位置 | 客户端 | 服务端 |
| 首屏 | 白屏到 JS 加载渲染后显示，慢 | 直接返回完整 HTML，快 |
| SEO | 差（爬虫难等 JS） | 好 |
| 服务端压力 | 无渲染 | 服务端渲染 CPU 负载 |
| 交互/二次渲染 | 流畅 | 需 Hydration 完成后才可交互 |

③ **SSR 优点**：首屏快、SEO 好；**缺点**：服务端成本高、Hydration 期交互阻塞、需要连接状态/数据请求的方式（同构）。

④ **SSR 本质**：同一套组件代码既能在服务端 produce HTML（node），也能在客户端水合（hydrate），即同构渲染。

⑤ **追问**：SSR 首帧 vs 交互可用哪个优先？数据请求在服务端如何避免重复请求？

### Q112: Next.js 中 SSR、SSG、ISR 的区别与各自使用场景？

① **一句话结论**：三者是 Next.js 的三种渲染策略——SSR 服务端按请求渲染、SSG 构建时生成静态页、ISR 静态页 + 按需重新生成，从"实时性"到"性能"光谱分布。

② **对比**：

- **SSR**：`getServerSideProps`，每个请求都服务端渲染。适合数据实时、个性化（用户态）页面。性能最差、缓存依赖配置。
- **SSG**：`getStaticProps` 构建时生成静态 HTML。适合内容稳定（博客、文档、落地页），CDN 缓存，性能最佳。
- **ISR**：`getStaticProps` + `revalidate` 设置，构建生成静态页，请求时若超过 revalidate 时间则后台重新生成。适合内容更新不频繁但需要定时刷新（新闻列表）。

③ **选择判断**：

- 内容很少变 → SSG。
- 相对静态但要定时更新 → ISR。
- 强实时 / 强个性化 → SSR（或将个性化部分移到客户端）。

④ **注意**：SSG 页面的"用户相关"数据不能服务端返回，需在客户端请求或 cookie 判断。

⑤ **追问**：ISR 的 `revalidate` 与 CDN 缓存页签关系？`getStaticPaths` 预渲染的动态路由怎么做？

### Q113: 什么是 Hydration（水合）？如何避免水合错位（hydration mismatch）？

① **一句话结论**：Hydration 是 SSR 把服务端生成的静态 HTML"附上交互能力（事件与状态）"的过程——浏览器用客户端 VDOM 匹配服务端生成的 DOM 并挂接事件。

② **原理**：

1. 服务端渲染出 HTML（无交互）。
2. 浏览器下载 JS 后执行，框架"水合"：尽快复用已有 DOM 节点并绑定事件、恢复状态，而不是重建 DOM。

③ **水合错位（mismatch）**：客户端渲染结果与服务端 HTML 不一致（因数据、随机数、时区、浏览器 API、key 顺序等导致），React/Vue 会警告并可能重渲染，影响性能与正确性。

④ **规避**：

- 保证首屏在服务端与客户端一致（数据来源统一、禁用随机/时区/浏览器唯一下发）。
- 用 `useEffect` 只在客户端做会变化的事（如 window.matchMedia、Date.now、随机 id），或用框架的 hydration 后 fallback。
- 不把非确定性的动态内容放进首屏 HTML。

⑤ **进阶**：部分水合（partial hydration）、`streaming`（React Suspense，渐进式注入）。

⑥ **追问**：如何用 sentinel 检测水合是否成功？水合失败对性能影响及降级？

### Q114: 如何设计 SSR 的降级方案（CSR fallback）？

① **一句话结论**：SSR 降级是当"服务端渲染或预取失败/过载/超时"时，回退到客户端渲染，保证页面仍可用。

② **降级场景**：

- SSR 服务过载/挂掉 → 返回静态壳页，客户端自行渲染。
- 服务端数据请求失败/超时 → 服务端渲染兜底空壳或直出错误，浏览器再客户端重拉。

③ **分层降级方案**：

1. **服务端渲染失败**：网关/CDN 返回预渲染的静态 fallback HTML + 只引入 CSR bundle。
2. **数据预取失败**：出错时可能输出 `<div id="root">` + 空数据，客户端重新请求；或用 SPA 页面兜底。
3. **给出标记**：`<meta name="ssr" content="failed">` 或 cookie 标记用于诊断。
4. **网关级开关**：feature flag 或健康检查在 SSR 不可用时统一切换到 CSR 入口。

④ **实现要点**（以 React 为例）：

```jsx
// 服务端渲染 try/catch，失败则渲染最小外壳
res.status(500).send(prepareFallbackHtml()); // 只有 id=root 的 CSR 壳
// 前端根据环境 flag 决定是否走客户端渲染逻辑
if (window.__SSR_FAILED__) mountSpaApp();
```

⑤ **注意事项**：降级后需保障基本可用（长列表/路由可达），同时监控降级触发率用于告警。

⑥ **追问**：SSR 与 CDN 缓存如何配合处理降级？降级期间并发突发怎么保护？

### Q115: 跨端开发有哪些主流方案？Taro / uni-app / RN / Flutter 如何选型？

① **一句话结论**：跨端方案按"写一次、运到多端"的理念分三种技术路线——Web 套壳 / 动态化 / 自编译渲染，主流的 Taro、uni-app、RN、Flutter 各走其路。

② **方案梳理**：

- **Taro / uni-app**：用 React/Vue 写，编译到小程序（WXML）+ H5 + RN。基于"编译为多端代码"，一次编写多端运行，生态对小程序友好。
- **React Native**：React 语法，用运行时桥接原生组件渲染（JS 层 -> 原生 bridge/Fabric），真原生体验，生态大。
- **Flutter**：Dart 编写，用自绘引擎（Skia/Impeller）直接绘制 UI 到 Canvas，跨 iOS/Android/web/桌面，性能高、UI 一致，但依赖 Dart 生态。

③ **选型矩阵**：

| 需求 | 推荐 |
|------|------|
| 主要目标是小程序，兼顾 H5 | Taro / uni-app |
| 想用前端技术栈 + 真原生体验 | RN（需原生基础） |
| 要极致一致 UI / 动画 / 跨平台一致性能 | Flutter |
| 只想快速 H5 | 直接 Web / SSR |

④ **权衡**：Web 套壳（如 Capacitor）开发快但性能/体验打折；跨端方案都需老练团队与配套基建（热更、发布、监控）。

⑤ **追问**：动态化（发烫方案如 JSPatch/Alpha）与静态编译的区别？WebView 与原生混合方案（hybrid）的适用？

### Q116: React Native 和 Flutter 的渲染原理有什么区别？

① **一句话结论**：RN 通过"JS 驱动、桥接调用原生组件渲染（宿主绑定）"；Flutter 用 Skia/Impeller"自绘引擎把所有 UI 画在 Canvas"，两套路径决定了性能与一致性差异。

② **RN 渲染**：

- 业务逻辑跑在 JS 线程，通过 Bridge / Fabric 与原生通信。
- 最终由**宿主平台的原生组件**渲染（iOS 的 UIKit / Android 的 View）。
- 好处：与原生交互顺滑、可用原生组件；代价：跨端一致性依赖各自平台组件，JS 与原生通信有开销与异步延迟。

③ **Flutter 渲染**：

- Dart 代码直接编译运行，UI 由**自绘引擎（Skia/Impeller）on Canvas** 绘制，不依赖平台控件。
- 好处：跨平台 UI 像素级一致、可高度自定义、性能好（无需桥接每帧）；代价：与原生能力集成需 channel（MethodChannel），包体积较大。

④ **对比要点**：

| 维度 | RN | Flutter |
|------|----|---------|
| 渲染 | 原生组件 + 桥（JS↔原生） | 自绘引擎（Skia） |
| 一致性 | 依赖平台 | 强一致 |
| 性能 | 依赖通信开销 | 高、平滑 |
| 语言 | JS/TS | Dart |

⑤ **追问**：RN 的 New Architecture（Fabric + TurboModule + 同步 JSI）解决了什么？Flutter 的 Impeller 为何替代 Skia？

### Q117: 小程序的双线程架构原理是什么？

① **一句话结论**：小程序采用"双线程"——逻辑层（JS）与渲染层（WXML 转虚拟树/WebView）分离，两线程通过原生桥（JSCore + 消息协议）异步通信保证安全与性能。

② **为什么要双线程**：如果直接操作 DOM，恶意代码可能绕开限制访问原生能力，安全性差。将逻辑与渲染隔离（类似受限沙箱），同时让小程序的抽象 UI 编译到自定义渲染。

③ **架构**：

- **逻辑线程**：运行 JS（页面逻辑、状态、API 调用），没有 DOM。
- **渲染线程**：渲染由 WXML 编译成的虚拟节点树（在小程序运行时的 WebView 或自渲染层绘制）。
- **通信**：逻辑线程的数据变化通过"数据快照（setData）"发送到渲染线程，渲染线程据此更新树并重绘；采用"数据驱动的 DOM 绑定"，并非传统 DOM 操作。

④ **setData 性能影响**：`setData` 数据量大、频繁调用会成为性能瓶颈（每一次都跨线程异步同步），应精简 setData 数据、合并更新。

⑤ **与 RN/Flutter 对比**：RN 也是"JS 逻辑 + 原生渲染"的双线程思路，小程序类似但其渲染常基于 WebView/自定义渲染，且交互受"数据快照"约束。

⑥ **追问**：`setData` 为什么慢、怎么优化？小程序分包 / 预下载如何降低包体与启动成本？

## 第四阶段：可视化（118-121）

### Q118: Canvas、SVG、WebGL 的区别？如何按场景选择？

① **一句话结论**：三者按渲染能力分档——SVG 基于 DOM 声明式（量小/交互方便），Canvas 用像素级即时绘制的位图（中等数据量/动态效果），WebGL 基于 GPU 的高性能图形（大数据量/3D）。

② **对比**：

| 维度 | SVG | Canvas 2D | WebGL |
|------|-----|-----------|-------|
| 本质 | 矢量、DOM 节点 | 位图、JS 绘制 | GPU 着色器渲染 |
| 元素 | 可事件、可 CSS 交互 | 无独立节点，需自行命中 | 底层，需着色器 |
| 数据量 | 较小（节点多则 DOM 重） | 中等，性能取决于绘制 | 极大（几十万点） |
| 缩放 | 无损 | 会失真（可重绘） | 精确控制 |
| 学习成本 | 低 | 中 | 高 |

③ **选择建议**：

- 图表交互多、节点少（如简单流程图/图标）用 SVG。
- 动态图表、大量图形、需要局部重绘（如实时监控曲线）用 Canvas。
- 大数据可视化（几十万节点）、3D、碎片粒子用 WebGL（Three.js）。

④ **补充**：Canvas 与 SVG 可混用（外层 SVG 交互，内部 Canvas 绘制海量）。

⑤ **追问**：Canvas 如何做静态图形增删而不全量重绘？WebGL 与 GPU 的坐标系？

### Q119: 如何用 Canvas 实现一个高性能的可视化图表？

① **一句话结论**：高性能 Canvas 图表核心是"减少重绘、按需局部更新、合理坐标与离屏离屏缓存、避免不必要的测量"。

② **关键手段**：

- **分层画布**：把"静态层（轴/网格）与动态层（数据/交互）"拆到不同 canvas，静态层只画一次（drawImage 复用），动态层单独刷新。
- **离屏 Canvas 缓存**：把复杂静态元素先画到离屏 canvas，主画布直接 `drawImage`，省去重复计算。
- **避免全量重绘**：交互（hover/缩放）时只重绘受影响区域或用双缓冲。
- **数据分片 / LOD**：大数据量时按可视窗口抽稀（下采样），画计数轴而非逐点。
- **requestAnimationFrame 批量**：多帧绘制统一在 rAF 回调内，避免 setInterval 浪费。
- **设备像素比 DPR 处理**：`canvas.width = cssWidth * dpr` 保持清晰。

③ **周边**：用 `<canvas>` 尺寸固定、关闭混合/阴影可提性能；复杂带动画的曲线可用增量绘制。

④ **追问**：Canvas 如何做"命中检测"（判断点击了哪个图形）？LOD 抽稀算法有哪些（如经度抽稀）？

### Q120: 大数据量可视化的性能优化（分层渲染 / 虚拟化 / 增量渲染）？

① **一句话结论**：大数据可视化优化核心是"按需渲染"，用分层、虚拟化（可见区渲染）、增量/采样降低实际绘制量。

② **方案**：

- **分层渲染（Layer）**：将不同类型图形分到多层 canvas 分别更新，避免一锅粥全量重绘。
- **虚拟化 / 视口裁剪（Viewport clipping）**：只渲染可视区内的数据点，通过剔除不可见点减少绘制调用（如大数据散点图按屏幕范围过滤）。
- **降解采样（LOD / 抽稀）**：按当前缩放级别把数据抽稀，缩得越远点越少；或对线图做 min/max 抽稀保持视觉。
- **增量 / 流式渲染**：数据实时到达时用增量追加（drawImage 缓存已画部分），而非整图重绘。
- **合并绘制**：把相同样式图形合并为一次批量 draw（减少状态切换）。
- **空间索引 / 聚集**：用网格聚合（grid aggregation）、octree/kd 树加速定位。

③ **WebGL 进阶**：几十万/百万级用 WebGL + instancing，或 WebGPU compute 在 GPU 上做聚合。

④ **追问**：散点图的"可视区剔除"如何搭配缩放做？聚合与原始点如何切换（交互钻取）？

### Q121: Three.js 的核心概念（场景 / 相机 / 渲染器 / 网格）是什么？

① **一句话结论**：Three.js 用"场景（Scene）+ 相机（Camera）+ 渲染器（Renderer）"构成 3D 渲染基本面，物体由"几何体 + 材质"组成"网格（Mesh）"加入场景。

② **核心概念**：

```js
// 场景：容纳所有对象的容器
const scene = new THREE.Scene();
// 相机：决定从哪看（透视/正交）
const camera = new THREE.PerspectiveCamera(75, w/h, 0.1, 1000);
camera.position.z = 5;
// 渲染器：把场景+相机绘制到 canvas
const renderer = new THREE.WebGLRenderer();
renderer.setSize(w, h);
document.body.appendChild(renderer.domElement);

// 网格 = 几何体 + 材质
const geo = new THREE.BoxGeometry(1, 1, 1);
const mat = new THREE.MeshStandardMaterial({ color: 0xff5533 });
const cube = new THREE.Mesh(geo, mat);
scene.add(cube);

// 动画循环
function animate() {
  requestAnimationFrame(animate);
  cube.rotation.x += 0.01;
  renderer.render(scene, camera);
}
animate();
```

- **光源**：`AmbientLight`、`DirectionalLight`、`PointLight` 等决定光照模型。
- **坐标系/组**：`Group` 组织层级，便于整体变换。

③ **追踪**：物体变换用 `position/rotation/scale`；都需要 `requestAnimationFrame` 循环调用 `renderer.render`。

⑤ **追问**：透视 vs 正交相机适用场景？`BufferGeometry` 与 CPU/GPU 内存的关系？

## 第五阶段：低代码（122-124）

### Q122: 什么是低代码/无代码？低代码平台的整体架构是什么？

① **一句话结论**：低代码是"通过少量或零编码，用可视化/配置方式开发应用"；其平台核心是把"页面 = 字段/组件/数据 + 配置（Schema）"抽象出来，用一个运行时按配置渲染并驱动交互。

② **整体架构（分层）**：

```
设计态（可视化编辑器）
   ↓ 产出 JSON Schema（页面结构 / 组件配置 / 数据绑定 / 事件逻辑）
存储层（Schema 持久化 + 发布版本）
   ↓
运行时（Runtime）
   渲染引擎（按 Schema 渲染组件）
   表单引擎（校验/联动/动态渲染）
   业务逻辑引擎（数据请求 / 事件编排）
   权限 / 多租户隔离
   ↓
集成（后端 API、数据源、第三方）
```

③ **核心价值**：把"重复的 CRUD 页面"抽成配置，降低开发门槛、加快交付、统一规范。

④ **能力分层**：无代码（拖拽全配置）≈ 面向业务；低代码（可写少量 JS 扩展）面向开发者。

### Q123: 低代码渲染引擎的设计思路是什么？

① **一句话结论**：低代码渲染引擎"接收 JSON Schema，递归渲染为组件树并执行数据绑定与交互"，核心是"Schema → Component 的映射 + 组件协议 + 渲染上下文"。

② **核心设计**：

1. **组件注册表（Registry）**：把"组件名 → 组件实现"映射登记，Schema 里 `type: 'input'` 对应注册的 Input 组件。
2. **Schema 结构**：描述节点类型、props、children、事件、数据绑定；渲染器按 name 查注册表拿到组件渲染。

```jsonc
// Schema 示例
{
  "type": "form",
  "props": { "labelCol": 6 },
  "children": [
    { "type": "input", "props": { "field": "name", "label": "姓名" } },
    { "type": "select", "props": { "field": "city", "options": [...] } }
  ]
}
```

3. **渲染上下文（context）**：向下传递 value、onChange、校验状态、数据源。
4. **递归渲染**：遍历 schema.children 递归产出 `React.createElement(registry[name], {...props, context})`，Vue 则 `resolveComponent`。
5. **事件与联动**：Schema 里声明按钮 onClick / 字段联动，运行时绑定并触发更新。

③ **关键能力**：type 解析、props 校验、动态注册（插件化）、版本与兼容（Schema 升级）、性能（大量字段避免全量渲染）。

⑤ **追问**：如何用 React `createElement` / Vue `resolveDynamicComponent` 实现注册表渲染？运行时与设计器如何共享同一套渲染？

### Q124: 表单引擎 / Schema（协议）驱动的原理是什么？

① **一句话结论**：Schema 驱动的表单引擎把"表单的定义（字段、布局、校验、联动）描述成 JSON/JS 配置"，由引擎统一解析、渲染、校验、收集数据，实现"配置即表单"。

② **核心结构**：

```json
{
  "fields": [
    { "name": "username", "label": "用户名", "type": "input",
      "rules": [{ "type": "required", "message": "必填" }, { "type": "min", "value": 3 }] },
    { "name": "email", "label": "邮箱", "type": "input",
      "rules": [{ "type": "email" }],
      "dependents": [{ "when": { "field": "needMail", "eq": true }, "visible": true }] }
  ]
}
```

③ **引擎职责**：

- **渲染**：根据字段 type 选择对应组件，layout 由 schema 描述（栅格/分组）。
- **状态收集**：统一 `formData`（fields 名 -> value），避免逐字段 setState。
- **校验**：按 `rules` 调用校验器，展示错误，拦截 submit。
- **联动**：`watch` 字段变化更新相关字段（显示/禁用/赋值/校验规则）。
- **数据传输**：提交时产出标准化 `formData`，可单字段校验/全表校验。

④ **实现选择**：可直接基于成熟库二次封装（antd Form 的 schema、Fusion/Formily、Vue FormKit），或自研轻量引擎（核心是"字段 registry + 状态收集 + 校验 + 联动"）。

⑤ **收益**：CRUD 表单可由后端返回 Schema 动态渲染，同一套表单在桌面/移动/H5 复用，大大减少样板代码。

⑥ **追问**：如何保证复杂表单性能（大量字段避免每次输入全量渲染）？联动规则循环依赖怎么防？

### Q125: HTML5 播放器如何实现？MSE（Media Source Extensions）是什么？

① **一句话结论**：HTML5 播放器围绕 `<video>` 标签 + 播放控制逻辑实现；要在浏览器里播放"分片流/自定义源"，需要 MSE 把二进制流喂给媒体元素。

② **HTML5 播放器实现**：

- 播放：`video.play()`/`video.pause()`；监听 `timeupdate` / `canplay` / `ended`。

- **SourceBuffer**：往缓冲队列 append 数据，管理 bytes。
- **作用**：实现自适应码流、seek、直播拼接等浏览器本身不原生覆盖的分片能力。

④ **常用做法**：HLS（m3u8）等方案在 web 常用 `hls.js`/`video.js` 封装 MSE + XHR 拉分片实现。

### Q126: HLS 和 DASH 流媒体协议的区别？

① **一句话结论**：HLS 和 DASH 都是"基于 HTTP 的自适应码流分片协议"，把视频切成若干 .ts/.mp4 分片 + 一个描述清单，客户端按网络带宽动态选码率；区别在格式、标准化与生态。

② **HLS（Apple 提出，m3u8）**：

- 清单：`*.m3u8`，分片常用 `TS`（也可 fMP4）流,可通过 `#EXT-X-STREAM-INF` 列出多码率。
- 成熟、生态广（iOS/Android 原生支持，Web 常用 hls.js）。

③ **DASH（MPEG-DASH，.mpd）**：

- 清单：`*.mpd`（XML），分片用 `fMP4`（CMAF）。
- 标准化程度高、更灵活（多编解码、多个period），Web 用 `dash.js`。

④ **技术对比**：

| 项 | HLS | DASH |
|----|-----|------|
| 标准 | Apple 私有（后被广泛采纳） | 公共 MPEG 标准 |
| 清单 | m3u8（M3U 文本） | mpd（XML） |
| 分片封装 | TS / fMP4 | fMP4（CMAF） |
| 原生支持 | iOS/Android/Edge 较好 | 需 JS 库 |
| 码率自适应 | 支持 | 支持（更细粒度） |

⑤ **选型**：H5 与 iOS 生态 HLS 覆盖好；跨端/标准化要求高选 DASH + 封装 SDK；实际常由播放器库透明适配。

⑥ **追问**：m3u8 的 `#EXT-X-KEY`（加密 DRM）如何实现播放加密流？码率自适应 switch 的策略（平滑 vs 激进）？

### Q127: 直播技术方案（WebRTC / 低延迟直播）如何设计？

① **一句话结论**：直播涉及"采集 → 推流 → 分发 → 拉流播放"，实时/低延迟方案围绕 WebRTC（真实时双向）与"低延迟 HLS/HTTP-FLV"（低延迟单流）两条路线。

② **链路**：

```
采集（摄像头/屏幕/麦克风）
 → 编码（H.264/VP8/AV1）
 → 推流（上传到媒体服务器/转推 CDN）
 → 分发（CDN + 协议：RTMP/HTTP-FLV/DASH/HLS/WebRTC-SFU）
 → 播放（hls.js / flv.js / WebRTC 原生播放）
```

③ **方案分类**：

- **WebRTC**：端到端实时、P2P + 回退 SFU（Selective Forwarding Unit，如 M79/如 Plug 方案）；延迟几百 ms，适合连麦/1v1/低延迟直播。需信令服务器（交换 SDP/ICE）+ 媒体服务器。
- **低延迟直播（LL-HLS / HTTP-FLV + fMP4）**：秒级内延迟，适合大众直播；LL-HLS 用 CMSF 用 segment 目标 1-2s，HTTP-FLV 适合 WebRTC 不可达场景。
- **标准 HLS**：延迟较高（十几 s），场景简单。

④ **关键设计**：

- **信令**：管理会议/房间（WebSocket/HTTP）。
- **媒体协商**：WebRTC 用 `createOffer/answer` + ICE（STUN/TURN）。
- **吞并/CDN**：大规模观看用 CDN 分发（WebRTC izebox / 直播转推 CDN）。

### Q128: 音视频播放的缓冲策略与首帧优化怎么做？

① **一句话结论**：缓冲策略目标是"快起播 + 平滑播放"，通过分级缓冲水位、码率自适应、预取与释放优化；首帧优化核心是"尽早拿到底片 + 快速解码首帧"。

② **缓冲策略**：

- **缓冲水位（Buffering policy）**：设起播阈值（如缓冲达到 3s 才播）与满载阈值（暂停拉取），低阈值快起播，高阈值防卡顿；播放前缓冲不足则等待 `waiting` 事件。
- **分支 fetch/预取**：渐进拉取后续分片，视网速决定预取量。
- **码率自适应（ABR）**：根据下载速度动态选高/低码率分片，避免缓冲耗尽。
- **释放控制**：播放稳定后控制缓冲大小防内存膨胀。

③ **首帧优化**：

- **缩短 TTFB**：CDN 就近分发、把首片放首页/预拉取、请求合并。
- **分辨率/首片编码**：首片用小 size/低码率快速起播。
- **预热解码器**：提前 `decode()`（WebCodecs）预热。
- **缩略图/占位**：首帧前放秒级封面占位，减少白屏感知。

④ **API 辅助**：监听 `timeupdate`、用 `readyState`/`buffered` 判断缓冲；`readystatechange`、`canplay` 触发起播。

⑤ **追问**：`buffered`/`seekable` 时间范围怎么算？ABR 是否每次切码率都造成重新缓冲（衔接成本）？

### Q130: 游戏循环（requestAnimationFrame）与游戏性能优化是怎么做的？

① **一句话结论**：游戏循环是"帧循环"——每帧读取输入 → 更新逻辑（基于 deltaTime）→ 渲染，用 `requestAnimationFrame` 与浏览器刷新率同步；性能优化围绕"降渲染成本与稳定帧率"。

② **游戏循环**：

```js
let last = performance.now();
function loop(now) {
  const dt = (now - last) / 1000; // 秒
  last = now;
  update(dt);   // 逻辑更新（乘 dt 统一节奏）
  render(dt);   // 渲染
  requestAnimationFrame(loop);
}
requestAnimationFrame(loop);
```

- 用 deltaTime 让不同帧率下移动速度一致（避免 device 帧率差异）。

③ **性能优化**：

- **离屏缓存/精灵批处理**：合并绘制调用（Pixi 自动批处理），减少 draw call。
- **对象池**：子弹/粒子等反复创建销毁的对象用对象池复用，避免 GC。
- **LOD / 剔除**：屏幕外的对象不渲染。
- **控制粒子/纹理数**：限制 draw call 上限，纹理合图（atlas）。
- **固定/裁剪帧**：静态场景缓存到离屏 canvas，只重绘动态层。
- **降低 vsync/分辨率**、使用 WebGL instancing。

④ **追问**：`requestAnimationFrame` 与 `setInterval` 的差异（节流/丢帧/后台暂停）？帧率统计 FPS 怎么算？

### Q131: WebAssembly 是什么？和 JavaScript 是什么关系？

① **一句话结论**：WebAssembly（WASM）是一种可在浏览器运行的**底层字节码**，接近原生性能（C/C++/Rust 编译而来），JS 与 WASM 互补并行，各自擅长的任务互相配合。

WebAssembly.instantiateStreaming(fetch('app.wasm'), importObj)

### Q132: PWA 是什么？Service Worker 如何实现离线缓存？

① **一句话结论**：PWA（渐进式 Web 应用）让 Web 应用具备"可安装、离线可用、可推送"等接近原生体验的能力，核心是 Service Worker + Web App Manifest + 推送 API。

② **三大支柱**：

- **Service Worker**：运行在独立线程的代理，拦截网络请求实现离线缓存、后台同步、推送。
- **Manifest（manifest.json）**：定义应用名/图标/启动方式，配合"添加到主屏"。
- **Push API / Notification**：消息推送。

③ **Service Worker 生命周期**：注册 → 安装（`install`，预缓存核心资源）→ 激活（`activate`，清理旧缓存）→ 空闲拦截 `fetch` 事件。

```js
// sw.js
self.addEventListener('install', (e) => {
  e.waitUntil(caches.open('v1').then(c => c.addAll(['/', '/app.js'])));
});
self.addEventListener('fetch', (e) => {
  e.respondWith(
    caches.match(e.request).then(cached =>
      cached || fetch(e.request).then(res => {
        const clone = res.clone();
        caches.open('v1').then(c => c.put(e.request, clone));
        return res;
      }))
  );
});
// 注册
navigator.serviceWorker.register('/sw.js');
```

④ **缓存策略**：cache-first（静态资源）、network-first（需更新数据）、stale-while-revalidate、network-only（表单）。

④b **限制**：Service Worker 仅 HTTPS（或 localhost）；需处理缓存版本与旧版本。

### Q133: WebGPU 相比 WebGL 有哪些优势？

① **一句话结论**：WebGPU 是现代浏览器新的底层图形/计算 API，相比 WebGL 紧随 GPU 现代架构、复用 Vulkan/Metal/DX12 抽象，提供了更高性能、更细控制与通用计算（GPGPU）。

② **相比 WebGL 的优势**：

- **更贴近现代 GPU**：基于队列/命令缓冲/渲染管线模型，减少状态跳跃与 CPU-GPU 开销。
- **性能**：底层更高效（显式命令提交、绑定组、持续更新数据），少驱动翻译开销。
- **通用计算**：内置 compute shader（并行的数据并行计算），明显强于 WebGL 的 fragment 计算。
- **可移植/一致**：跨 Vulkan/Metal/DX12 统一抽象，行为更一致。
- **开发体验**：`navigator.gpu`、`WGSL` 着色语言、更清晰的资源管理（无全局状态）。

③ **现状**：现代浏览器逐步支持（Chrome/Edge 已启用）；处理大数据、GPU 计算（如 AI 推理/图像/科学计算）前景广阔。

④ **同 WebGL** 的区别概括：WebGL 2 ≈ 传统固定管线（较老）；WebGPU 更贴近原生级并行做 GPU 计算的"新范式"。

- **框架与渲染**：React/Vue 持续 + 编译优化（Signal、compiler）；框架的"信号/细粒度响应式"（Vue Signal、Solid、preact signals）。
- **服务端渲染演进**：`React Server Components`、流式/并行渲染，前后端同构深化。
- **WASM / WebGPU**：让 Web 承担更重计算与原生级图形（AI 推理、3D、大数据）。
- **AI 原生**：AI 辅助编码、LLM 交互、Agent 自动化、RAG 应用成为标配。
- **跨端与微前端**：Taro/RN/Flutter 多端、微前端治理复杂。
- **可观测性/工程化**：性能、错误、成本的全链路可观测。
- **Web 标准演进**：`View Transitions API`、`Document Picture-in-Picture`、`CSS @layer`、`Web Animations`。

③ **我关注的**：Signal/编译器优化、WASM/WebGPU 与 Web 平台增强、AI Agent/缓存与流渲染、以及 Web 组件/新 CSS 能力。

④ **回答由头**：趋势观察要有依据（framework/官方/社区）并落到业务价值（性能/人效/体验）。
