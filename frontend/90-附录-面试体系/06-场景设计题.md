## 场景 A：实现一个高性能的虚拟滚动列表

### 题目背景
后台有个订单列表，数据量可达数十万条。直接渲染会导致首屏卡顿、内存飙升。请设计一套虚拟滚动列表方案，让长列表任意滚动都保持流畅。

### 考察点
- 只渲染可视区思想、滚动位置换算、总高度撑起、`key` 复用、动态行高
- 与浏览器 整段滚动 / IntersectionObserver 的区别
- 性能细节：避免重复渲染、滑动平滑、滚动去抖节流

### 参考答案思路

**核心思路**：容器固定高度（可视视口），根据 `scrollTop` + 行高反推要渲染的 `[start, end]` 区间，用"上下占位（padding / translateY）保持滚动条总高度"，只渲染可视区内少量 DOM。

**关键步骤**：

1. **数据与参数**：`total = items.length`、`itemHeight`、`viewHeight = 容器.clientHeight`、`scrollTop`。
2. **计算可视区间**：

```js
function computeRange(scrollTop, itemHeight, viewHeight, buffer = 5) {
  const start = Math.max(0, Math.floor(scrollTop / itemHeight) - buffer);
  const end = Math.min(total, Math.ceil((scrollTop + viewHeight) / itemHeight) + buffer);
  return { start, end };
}
```

- `buffer`（预渲染额外行）用于快速滚动/边缘时减少白屏。

3. **渲染结构**：

```jsx
<div className="list" onScroll={handleScroll} style={{ height: viewHeight, overflow: 'auto' }}>
  {/* 外层占位高度撑起滚动条 */}
  <div style={{ height: total * itemHeight, position: 'relative' }}>
    <div style={{ transform: `translateY(${start * itemHeight}px)` }}>
      {items.slice(start, end).map(item => <Row key={item.id} data={item} />)}
    </div>
  </div>
</div>
```

4. **滚动处理**：`onScroll` 里读 `scrollTop`，`rAF` 节流更新 `start/end`，尽量用 `useState` 一次性更新减少重渲染。
5. **`key` 复用**：用稳定 `item.id`，复用已有 DOM（避免错位状态）。
6. **动态行高**：若行高不固定，引入测量（`useLayoutEffect` 量取实际高度缓存到 map，未测量时用预估高度，滚动后校准），或用 `estimatedItemSize`。

**边界与进阶**：

- 快速拖动时可用 `useDeferredValue` 或视觉空号避免闪烁。
- 考虑 `overscan`（可视外多渲染几行）与虚拟化交互（点击/选中的命中）。
- 生产可直接用成熟库（`react-window`、`@tanstack/virtual`、扩展列表）。

## 场景 B：设计一个可视化大屏架构

### 题目背景
要给数据团队做一个监控大屏，展示订单量、营收、实时在线等多项图表，数据量大且需要定时刷新 / 实时推送，要求高性能与可扩展。

### 考察点
- 可视化选型（ECharts / Canvas / WebGL）、图表布局、数据流
- 大数据渲染优化（分层、按需渲染、LOD）
- 数据实时性（轮询 / WebSocket / SSE）与更新策略
- 工程化：配置化、主题、分辨率适配、监控告警

### 参考答案思路

**核心思路**：采用"配置驱动 + 分层渲染 + 独立图表 + 统一数据源"的大屏架构。

**关键步骤**：

1. **选型与分层**：
   - 图表用 ECharts（自带 Canvas/SVG 切换），大数据/复杂动效用 WebGL。
   - 布局用 CSS Grid 把大屏拆成多卡片，每卡片挂载一个图表实例。

2. **数据流**：

```
数据源（轮询/WebSocket/SSE）
 → 数据层（统一 Store，内存缓存 + 去抖）
 → 图表层（各图表只订阅自己需要的那部分切片 → setOption）
 → 渲染（ZoomableCanvas，按需 update）
```

3. **实时更新策略**：
   - 低频指标定时轮询合并；高频监控走 WebSocket 推送。
   - 图表用 `setOption(option)` 增量更新（避免整图重绘）。

4. **性能优化**：
   - **配置化 DataMap**：每图表声明 `{ dataKey, transform, draw }`，统一数据转换。
   - **LOD / 抽稀**：时间线长时按窗口聚合（min/max 下采样）。
   - **离屏缓存**：静态报表/背景画布一次绘制复用。
   - 避免大屏一更新整屏全刷，仅刷新受影响图表。

5. **工程化**：大屏尺寸用 `vw/vh` 或 rem 适配不同分辨率；提供主题/换肤；监控数据错误与图表渲染异常上报。

**边界**：

- 上线前压测上报峰值；后端支持"按需聚合"接口应对大时间窗。
- 实时推送失败自动降级为轮询。

## 场景 C：给一个复杂表单做性能优化

### 题目背景
一个包含上百个字段、多个联动、动态增删行、频繁校验的后台表单，用户在输入时页面卡顿、每次击键都整体重渲染。请设计方案优化。

### 考察点
- 细粒度更新（避免全表重渲）、字段拆分、受控组件重渲染
- 校验的性能控制（防抖、局部校验、规则拆分）
- 联动与动态表单的正确性
- 大规模数据管理与不可变更新

### 参考答案思路

**核心思路**：把"全局状态集中在单一 store"改为"字段级订阅",让每个字段/区块独立更新；校验去抖 + 增量计算；必要时虚拟化。

**关键步骤**：

1. **状态模型拆分**：
   - 把 `formData` 存到"字段级 store"（如 `useField` 各自 `value` + 一个 `touchedMap`），或用表单库的 `Field` 细粒度订阅。
   - 避免"任何输入都 setState 整个表单 JSON"——React 中可把每字段拆成独立受控组件（`<FormField name>`），只让该字段重渲染。

2. **减少全量重渲染**：
   - React：`memo` + 稳定 `onChange`（useCallback）。
   - Vue：`defineModel` / `v-model` 局部化，组合式 API 里字段独立 `computed`。
   - 用不可变更新（`{[...prev, index]: v}`）保证引用变化精确。

3. **校验优化**：
   - **防抖**：输入校验延迟，非必要不做实时强校验。
   - **局部 / 增量校验**：只校验变更的字段与联动字段，不整表校验。
   - **规则外置函数表**：把校验器组织成 `{ field: rules[] }`，避免每次手写内联。
   - 大表单远处 open/close 的校验缓存。

4. **动态表单项（增删行）**：
   - 每行用独立组件 + 自己的 `key`，行内数据离散，避免整表重渲。
   - 数组字段的插入/删除用不可变数组替换 + 仅受影响行更新。

5. **极端大数据**：字段数极多时考虑虚拟渲染可视字段区块，或分步骤/分区块表单（Step）。

**边界**：

- 优先"真卡才优化"，先在 Performance 面板确认主因（多余重渲染 vs 校验复杂度）。
- 注意表单库本身开销；自定义实现时维护 field mask（脏检查）复杂度上升。

## 场景 D：设计 SSR 降级方案

### 题目背景
用 Next.js（或同构 SSR）做电商详情页，首屏依赖 SSR。某次上游返回超时 / SSR 服务过载，页面白屏。请设计一套降级方案，保证任何时刻页面可用。

### 考察点
- SSR 与 CSR 双路径、降级触发条件
- 服务端与客户端的渲染兜底、数据预取失败处理
- 网关 / CDN / feature flag 的配合
- 降级期间的性能、监控与恢复

### 参考答案思路

**核心思路**：建立"SSR 正常 → SSR 失败 → 兜底 CSR"的多级降级，结合"页面壳 + 客户端注水"，做到服务端挂了仍能渲染基础页面。

**关键步骤**：

1. **正常路径（SSR）**：`getServerSideProps` 服务端取数据并渲染完整 HTML。

2. **诱发降级的条件**：
   - 服务端 `getServerSideProps` 的数据请求超时 / 抛错。
   - SSR 服务健康检查失败 / 负载过高 / 错误率超阈值。
   - 上游接口 5xx。

3. **降级乒乓设计（分层）**：

```
Level 0  正常 SSR（完整 HTML + Hydration）
Level 1  数据失败 SSR：服务端渲染"空壳 + 骨架屏"，标记 ssr:meta=failed
         （浏览器再独立请求数据 CSample 渲染）
Level 2  SSR 服务不可用：网关/CDN 直接返回预渲染的 fallback HTML（含 CSR 入口），
         浏览器下载 bundle 后以 CSR 模式重新挂载
```

4. **实现抓手**：

- **标记传播**：SSR 里把降级状态写到 `<meta>` / `window.__SSR_STATE__`。
- **客户端二段渲染**：CSR bundle 检测到"我是降级壳"就跳过水合 `hydrate` 改为 `createRoot().render()`，并自行拉数据。
- **网关兜底**：`try_files` / 反向代理在 SSR 503 时返回静态壳页（可预先生成 `fallback.html`）。
- **全局开关**：配置中心下发 feature flag，运维可一键切换全局 CSR。

5. **恢复与监控**：
   - 记录降级触发原因（接口超时 / 服务不可用）到监控系统。
   - 恢复条件：SSR 健康检查连续通过后自动恢复。
   - 对降级率 / 降级时长设置告警。

**边界**：

- 降级后 SEO 会受影响（可接受：可用性优先）。
- 注意与 CDN 缓存的相互作用——降级响应别被长期缓存导致无法恢复。

## 场景 E：搭建一个低代码渲染引擎

### 题目背景
公司想做一个内部表单搭建 / 页面搭建平台，让业务同学拖拽生成表单与页面，前端要负责"把配置 Schema 渲染成真实可交互页面"的运行时（渲染引擎）。请设计这个引擎。

### 考察点
- Schema → 组件映射（注册表）、递归渲染
- 组件协议（props、数据绑定、事件）、表单收集与校验
- 与设计器共享渲染、性能（不整页重渲）
- 扩展性（插件化、自定义组件）与 Schema 版本兼容

### 参考答案思路

**核心思路**：建立"Schema（协议）+ 组件注册表 + 递归渲染器 + 渲染上下文"四层，同一套渲染 runtime 在设计器预览与线上共用。

**关键步骤**：

1. **Schema 协议**：

```jsonc
{
  "root": "form",
  "props": { "labelWidth": 100 },
  "fields": [
    { "type": "input", "name": "name", "label": "姓名",
      "rules": [{ "type": "required" }] },
    { "type": "select", "name": "baidu", "label": "城市",
      "props": { "options": [{ "label": "北京", "value": "bj" }] },
      "dependents": [{ "when": { "field": "name", "ne": "" }, "visible": true }] }
  ],
  "actions": [{ "type": "button", "text": "提交", "onClick": { "action": "submit" } }]
}
```

2. **组件注册表（Registry）**：

```tsx
const registry = {
  input: ({ name, value, onChange }) => <Input value={value} onChange={onChange} />,
  select: SelectComponent,
  // ...
};
```

3. **递归渲染器**：遍历 `fields`，`createElement(registry[type], { ...props, name, value, onChange })`，Vue 用 `resolveDynamicComponent`。数据/提交/校验封装成 `FormContext` 全局下发。

4. **表单引擎**：统一 `values` 状态 + `rules` 校验器 + 联动 `watch`，提交时 `onValidate` 后吐 `values`。

5. **性能**：
   - 大量字段时那个字段独立订阅（细粒度），避免每次输入全量重渲染。
   - 组件用 `memo` 缓存。

6. **扩展与兼容**：
   - 组件可动态注册（插件化）：`registry.register('my-comp', Comp)`。
   - Schema 带 `version` 字段，渲染器做版本迁移。

**边界**：

- 与设计器统一用同一份 render 便于"所见即所得"。
- 校验 / 联动规则需防循环依赖，限制规则图无环。

## 场景 F：设计音视频播放器的缓冲策略

### 题目背景
做一个视频/直播播放器，要求"首屏秒开"，同时播放过程中尽量少卡顿（缓冲耗尽）。直播与点播各有不同。请设计一套缓冲管理策略。

### 考察点
- HTTP 分片 / MSE 缓冲水位、ABR（自适应码率）
- 分片预取、缓冲释放与内存控制
- 首帧优化（尽早拿到 / 首片小 / 预热解码）
- 直播低延迟 vs 稳定性的权衡
- 事件驱动（waiting/canplay/buffered）联动 UI

### 参考答案思路

**核心思路**：分区管理"起播 + 稳播 + 释放"三段缓冲水位，结合 ABR 选码率与预取策略，用事件驱动更新 UI 状态。

**关键步骤**：

1. **统一缓冲水位模型**：

```js
const BUFFER = {
  start: { min: 3000, max: 8000 }, // ms：起播阈值 / 满载
  steady: { min: 5000, max: 20000 },
};
```

- `buffered`（`video.buffered`）低于 `min` 时持续拉取分片；达到 `max` 暂停拉取（省带宽，防内存膨胀）。

2. **分片拉取器**：
   - 用 MSE `SourceBuffer.appendBuffer(segment)` 追加；维护拉取队列、去重（防重复请求同一 segment）。
   - 监听 `updateend` 后追加下一片；`bufferered` 空洞处理。

3. **ABR（自适应码率）**：
   - 记录最近 N 个分片的下载速度，选能满足"下载 ≤ 阈值可追上几个 segment"的最高码率。
   - 平滑 vs 激进策略：切换码率会引入新缓冲，需在"清晰度"与"缓冲"间平衡。

4. **起播（首帧）优化**：
   - 预测请求第一个小 size/低码率片（先起播再升码率）。
   - 预先拉取 manifest + 首分片；用 CDN 就近。
   - 播放前 `decode`（WebCodecs）预热解码器；封面占位减少白屏感知。

5. **事件驱动 UI**：

```js
video.addEventListener('waiting', showLoading);   // 缓冲不足
video.addEventListener('canplay', hideLoading);
video.addEventListener('timeupdate', updateProgress);
```

6. **直播低延迟权衡**：
   - 追求低延迟：缩小延迟窗口 + 跳段（丢弃落后 segment 强制追上）。
   - 追求稳定：维持更大缓冲。
   - 用 LL-HLS / HTTP-FLV 或 WebRTC 分场景权衡。

**边界**：

- 移动端带宽/流量关心：设低水位上限。
- 内存：限制 `SourceBuffer` 内数据量，播放进度推进时移除过期 segment。
- 提供手动码率切换入口并正确处理切换衔接。
