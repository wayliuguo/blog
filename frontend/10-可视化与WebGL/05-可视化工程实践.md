## 一、可视化大屏架构

### 1. 大屏的本质

大屏（数据可视化大屏 / 数字孪生）本质是一个**信息密度高、长期运行、强更新**的展示页。它的架构关键词：**数据流清晰、渲染可控、资源可回收、视觉统一**。

### 2. 分层架构

```
数据层(Data) → 状态层(Store) → 图表组件层(Chart) → 渲染层(Render/Canvas|SVG|WebGL)
```

- **数据层**：接口、WebSocket、轮询，统一产出"业务语义数据"。
- **状态层**：`Pinia / Vuex` 保存原始数据与布局状态，组件只读状态。
- **组件层**：把"某个图表"封装成独立组件，只接收数据属性。
- **渲染层**：由组件决定用 Canvas/SVG/WebGL 哪个引擎画出来。

好处：**换渲染引擎不碰业务数据；加图表不改数据流**。

### 3. 数据更新策略

| 场景 | 方案 | 说明 |
| --- | --- | --- |
| 实时监控 | **WebSocket 推送** | 低延迟，双向 |
| 常规看板 | 定时轮询 | `setInterval` + 幂等 `setOption` |
| 一次性大盘 | 首屏拉取后静态 | 无需轮询，最省 |
| 联动下钻 | 按需请求 + 缓存 | 命中缓存避免重复请求 |

```js
// 轮询封装示例（要点）
function startPolling(fn, interval) {
  const run = () => Promise.resolve(fn()).finally(() => setTimeout(run, interval));
  run();
}
```

## 二、图表库的工程化封装

### 1. 为什么必须封装

项目里如果每个页面都 `echarts.init + setOption` 手写，会带来重复 init、忘 dispose、resize 不同步、主题不统一等一堆坑。封装成**统一组件**是管理复杂度、控制性能内存的关键。

### 2. 一个 ECharts Vue3（组合式）封装要点

```vue
<template>
  <div ref="chartEl" class="chart"></div>
</template>
```

```js
// 封装思路：单实例 + 生命周期对齐 + resize 同步
import * as echarts from "echarts";
import { onMounted, onBeforeUnmount, watch, ref } from "vue";

const chartEl = ref(null);
let chart = null;

function render(option) {
  if (!chart) chart = echarts.init(chartEl.value);
  chart.setOption(option);
}

function resize() { chart && chart.resize(); }

let ro;
onMounted(() => {
  render(props.option);
  ro = new ResizeObserver(resize);
  ro.observe(chartEl.value);
});
watch(() => props.option, render, { deep: true });

onBeforeUnmount(() => {
  ro && ro.disconnect();
  chart && chart.dispose();   // 关键：销毁实例，防内存泄漏
  chart = null;
});
```

要点：
- **只 init 一次**，数据变化走 `setOption`（增量合并减少重绘）。
- **`ResizeObserver`** 比 `window.resize` 更精确地跟随容器变化。
- **`dispose` 必做**，尤其当页面有大量图表实例时。

### 3. 主题与通用能力抽离

公共主题（色板、字体、渐变）、tooltip 统一配置、loading/空态、点击下钻，都可沉淀为封装组件的统一 props/`provide-inject`。

## 三、Canvas / SVG / WebGL 选型

### 1. 一张决策表

| 技术 | 最佳场景 | 上限与短板 | 代表 |
| --- | --- | --- | --- |
| **SVG** | 图标、少节点图表、强交互、缩放清晰 | 节点几千+ DOM 爆炸 | 图表库 SVG 渲染器 |
| **Canvas 2D** | 中等大量节点、逐帧动画、自定义绘制 | 无图形对象可寻址、hit 测试要手写 | ECharts 默认、游戏 2D |
| **WebGL** | 海量点/3D/粒子/物理 | 学习成本高、编写复杂 | Three.js、ECharts GL |

### 2. 选型流程（决策树思路）

```
图形是不是 3D 或需要海量并发粒子？ → 是：WebGL(Three.js)
否则，节点是否成千上万且频繁更新？ → 是：Canvas
否则，是否需要矢量缩放/强事件/易维护？ → 是：SVG
（否则 Canvas/SVG 皆可，按团队认知与生态定）
```

### 3. 混合使用策略

- 图标用 SVG（清晰可缩放），大数据图表用 Canvas，3D 交 WebGL。**同一系统分层混用**是常态。
- ECharts 支持 canvas 渲染器 + 自定义系列；必要时在图表中叠加 WebGL 场景。
- 关键原则：**别为炫技选重引擎**，够用即最优，避免过度工程。

## 四、性能与内存管理

### 1. 性能优化的分层视角

| 层面 | 手段 |
| --- | --- |
| 数据层 | 降采样（`sampling: "lttb"`）、聚合、只传渲染所需字段 |
| 渲染层 | 选对引擎、合批/`InstancedMesh`、关闭动画、分批绘制 |
| 资源层 | 缓存静态部分、复用纹理/渐变对象、`progressive` 分批 |
| 调度层 | 不可见即停止 `rAF`、`IntersectionObserver` 懒渲染 |

### 2. 常见内存泄漏根因

- **没 `dispose`** 图表/Three 场景/WebGL context → 最常见。
- **事件/ResizeObserver/Observer 未移除**：组件卸载时要 `removeEventListener` / `disconnect`。
- **闭包持有的 DOM 引用**：定时器/回调里引用了已被移除的 DOM。
- **离屏 Canvas / 纹理未复用**：频繁 new 又没释放。

### 3. 统一的心法

```
进组件即注册，出组件即清理；实例化少而复用多；
可见才渲染，隐藏即暂停；大数据先降维再上屏。
```

### 4. 帧率与流畅度判断

- 用 `rAF` 时间戳计算 FPS，远超 30 逐劣化处理时及时优化。
- 埋点观测 FPS / dropped frames，形成衡量而非"感觉卡"。

## 五、跨端可视化

### 1. 分辨率适配三件套

- **rem / vw 方案**：大屏按设计稿等比，用 `rem` 或整体 scale 缩放容器。
- **DPR 适配**：Canvas 按 `devicePixelRatio` 放大分辨率再缩小显示（见 Canvas 篇）。
- **`Flex`/栅格 + 断点**：PC/平板/移动用响应式布局。

```js
// 大屏整体等比缩放的经典做法（要点）
function fit(el, w, h) {
  const scale = Math.min(window.innerWidth / w, window.innerHeight / h);
  el.style.transform = `scale(${scale})`;
  el.style.transformOrigin = "left top";
}
window.addEventListener("resize", () => fit(root, 1920, 1080));
```

### 2. 按设备降级

- **移动端减密度**：大屏 10 个图表降为 3~5 个核心指标。
- **不支持 WebGL 时降级**：`getContext("webgl")` 为空则回退 Canvas 2D。
- **图形过重时切换渲染器**：ECharts 可运行中 `renderer: "svg"` ⇄ `"canvas"`。

### 3. 触摸 / 手势

触屏补充 `touchstart/move/end`、`OrbitControls` 增加 `enablePan/touches` 支持；缩小点击热区避免误触。

## 六、可视化工程质量清单

### 1. 可维护性

- 组件只收"业务语义数据"，渲染与引擎细节内置。
- 主题、色板、tooltip 抽成统一配置文件（`theme.js`）。
- 命名统一：`xxxChart.vue`、数据字段语义化。

### 2. 稳定性与监控

- 兜底空态/loading，避免接口异常白屏。
- WebGL 失败捕获并给出降级提示。
- 关键指标埋点（渲染耗时、FPS、错误率）。

### 3. 复用沉淀

把通用能力沉淀成**内部 components 库或 npm 包**，跨项目复用：`BaseChart`、`DataTicker`（数字滚动）、`LegendPanel` 等。

## 小结

- **大屏 = 数据流 + 渲染 + 资源回收**，分层设计让换引擎不动业务。
- **图表组件封装**：单实例、生命周期对齐、ResizeObserver + dispose 是铁律。
- **选型决策**：3D/海量→WebGL；海量 2D→Canvas；矢量强交互→SVG；可分层混用。
- **性能与内存**：可见才渲染、合批降 draw call、及时 dispose/移除监听。
- **跨端**：rem/scale 适配分辨率、DPR 修正、按设备降级与触摸支持。

## 最小实现：把整章四个 demo 串成一条"可视化链路"

到 `code/frontend/10-visualize` 按序打开四个 demo，一遍走完本章的决策与工程链路：

- `canvas-chart.html` + `svg-chart.html` —— 同一份数据同时用 Canvas 与 SVG 实现，亲测"多而高频用 Canvas、少而强交互用 SVG"的选型手感；
- `raf-particles.html` —— 一条 `requestAnimationFrame` 主循环 + 数据更新即重绘，是可视化"数据流 + 渲染"的最小形态；
- `webgl-triangle.html` —— 顶点/片元着色器，看"数据涨到海量、效果升级 3D"时为什么该上 WebGL。

原理一句话：可视化工程的核心不是某个绘制 API 本身，而是"数据 → 选型 → 渲染 → 资源回收"这套决策链——四个 demo 把它们的最小版本压缩在一屏之内。
