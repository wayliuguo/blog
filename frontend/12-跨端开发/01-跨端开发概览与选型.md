# 跨端开发概览与选型
> 级别：中级

跨端开发的目标是"一套代码，多端运行"，从而降低多平台重复开发的成本。本章从跨端的本质出发，梳理主流技术方案的原理与取舍，并给出面向不同业务场景的选型建议，帮助你建立一套可迁移的技术决策框架。

按本书四层推进：

- **入门使用**：跨端的本质、四类"端"、主流方案全景（响应式 H5 / 小程序 / React Native / Flutter / 编译型）；
- **进阶**：架构层次（逻辑层 / UI 层 / 能力层）与各渲染路径差异、选型决策树；
- **实战**：后续各篇分别深入 Taro/uni-app、React Native、Flutter 与渲染原理；
- **最小实现掌握原理**：到 `code/frontend/12-cross-platform` 运行 `adapt-layer.html`（一套 DSL → 多平台适配层）与 `render-models.html`（渲染模型对比与桥接），亲眼看清"一次编写、多端落地"的最小骨架。

## 一、什么是跨端

### 1. 跨端的本质

跨端（Cross-Platform）指的是同一份业务逻辑（或尽量少的重复代码）能够运行在多个目标平台上。这里的"端"通常指：

- **移动原生**：iOS、Android
- **Web 语义**：桌面浏览器、移动浏览器（H5）
- **小程序生态**：微信、支付宝、抖音、京东等
- **桌面端**：Windows、macOS、Linux（可选诉求）

跨端要解决的问题按难度可分为三层：

| 层次 | 内容 | 典型手段 |
|------|------|----------|
| 逻辑层 | 业务数据处理、状态管理、接口调用 | JS/TS 共享逻辑 |
| UI 层 | 界面渲染、组件、样式 | 统一组件库 + 各端渲染器 |
| 能力层 | 摄像头、定位、支付、推送 | 各端原生 API 的封装桥 |

```js
// 跨端共享的业务逻辑示例：一次编写，多端复用
export function formatPrice(cents, currency = 'CNY') {
  const amount = (cents / 100).toFixed(2);
  return currency === 'CNY' ? `¥${amount}` : `${currency} ${amount}`;
}
```

跨端的核心矛盾始终是：**开发效率**与**性能/能力上限**之间的平衡。越贴近底层原生，性能越强但成本越高；越抽象，效率越高但受限越多。

### 2. 为什么需要跨端

| 动机 | 说明 |
|------|------|
| 降成本 | 一套团队维护多端，人力复用 |
| 提效率 | 一次发布多端同步，灰度更一致 |
| 统一体验 | UI 与交互风格可保持一致 |
| 应对生态碎片化 | 小程序平台众多，逐一开发不现实 |

## 二、主流跨端方案全景

### 1. 响应式 Web（H5）

一套标准 Web 技术栈（HTML/CSS/JS），通过响应式布局适配不同屏幕。优点是成本最低、SEO 友好、可随时发布；缺点是无法直接调用原生能力，性能受浏览器宿主限制，且无法进入应用商店分发。

```css
/* 响应式 H5 典型案例：媒体查询 */
.container {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(280px, 1fr));
  gap: 16px;
}
@media (max-width: 480px) {
  .container { gap: 8px; }
}
```

### 2. 小程序

依托微信/支付宝等宿主框架，包体小、体验接近原生、具备独立生态。缺点是平台锁死、不同平台 API 差异大、宿主规则限制多，因此催生了 Taro、uni-app 这类**编译型跨端框架**。

### 3. React Native（RN）

Facebook 出品，以 React 描述 UI，通过 **JSI** 桥把 JS 虚拟节点映射为 iOS/Android 原生控件。体验接近原生，复用前端技术栈；但依赖桥通信，首屏与复杂列表存在开销，且原生依赖版本常需逐平台维护。

```jsx
// RN 示例：JS 声明式 UI，映射到原生控件
import { Text, View, StyleSheet } from 'react-native';
export default function App() {
  return (
    <View style={styles.card}>
      <Text style={styles.title}>Hello Cross-Platform</Text>
    </View>
  );
}
const styles = StyleSheet.create({
  card: { padding: 16, backgroundColor: '#fff', borderRadius: 8 },
  title: { fontSize: 18, fontWeight: '600' },
});
```

### 4. Flutter

Dart 语言 + 自绘引擎（Skia/Impeller）。UI 由 GPU 直接绘制，不依赖宿主原生控件，因此各端渲染一致性极高、性能稳定。缺点是 Dart 语言学习成本 + 包体积较大，且 Web/桌面支持相对移动端较弱。

### 5. Taro 与 uni-app（编译型）

一类"用前端框架写，编译成各端目标产物"的方案：

- **Taro**：京东开源，以 React 为内核，编译到微信/支付宝小程序、H5、RN。
- **uni-app**：DCloud 出品，Vue 语法，编译到小程序、H5、App（内置引擎）等多端。

二者都走"一次编写，多端编译"，适合小程序 + H5 组合场景。

## 三、选型维度对比

### 1. 横向对比表

| 维度 | H5/响应式 | 小程序 | RN | Taro/uni-app | Flutter |
|------|-----------|--------|-----|--------------|---------|
| 语言 | JS/TS | JS + WXML/WXSS | JS/TS + JSX | React/Vue | Dart |
| 渲染路径 | 浏览器 | 宿主 WebView+原生组件 | 原生控件 | 宿主渲染 | GPU 自绘 |
| 性能 | 中 | 中 | 较高（New Arch 更高） | 依赖宿主 | 高 |
| 一致性 | 依赖浏览器 | 平台差异大 | 平台差异中 | 据端而异 | 极高 |
| 包体/引擎 | 无引擎体积 | 小 | 偏大 | 据端而异 | 偏大 |
| 原生能力 | 弱 | 中（宿主能力） | 强 | 中（差量原生） | 中，需插件 |
| 学习成本 | 低 | 低 | 中 | 中 | 中高 |
| 生态 | 极丰富 | 宿主生态 | React 生态 | 中文生态好 | 增长中 |
| 典型场景 | 营销页、后台 | 电商服务、工具 | 中大型 App | 小程序+后台聚合 | 高质量 UI App |

### 2. 决策逻辑

一个实用的决策树：

```
需要进入应用市场发布?  ——否→ 优先 H5/响应式
是 ↓
团队更熟悉 Dart?      ——是→ 选 Flutter
否 ↓
需要重度原生能力+高性能? ——是→ 选 RN（或 Flutter）
否 ↓
以小程序为主导、兼顾 H5/App? ——是→ 选 Taro / uni-app
```

选型不追求"最好的框架"，而是"当前团队技能栈 + 业务形态 + 长期演进"三者交集的最大化。常见误区是唯性能论或唯社区热度论，忽略了可维护性与团队可投入度。

## 四、适用场景与典型案例

| 场景 | 推荐方案 | 理由 |
|------|----------|------|
| 活动营销/H5 | 响应式 Web | 快、可随时上线、无需商店审核 |
| 公众号/微信生态 | 微信小程序 + Taro | 借力宿主流量，编译降成本 |
| 工具型 App | RN | 兼顾性能与前端复用 |
| 视觉要求高的 App | Flutter | 渲染一致、动画能力强 |
| 一鱼多吃（小程序+H5+App） | uni-app | 一次编写多端编译 |

## 五、最小实现：一套 DSL → 多平台适配层

到 `code/frontend/12-cross-platform` 运行 `adapt-layer.html`：输入一条 setData 这类 DSL，切换 Web DOM / 小程序 / RN / Flutter 四个"平台"，观察适配层如何把同一条业务翻译成各端产物；再到 `render-models.html` 看四种渲染模型的快照对比与桥接分发。

> 原理一句话：跨端的骨架就是"统一 DSL + 按平台适配器"。业务只写一次，差异被收口到适配层，新增平台只加一个适配器。
