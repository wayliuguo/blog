# 异步编程与事件循环

> 级别：初级→中级

按本书四层推进：

- **入门使用**：同步/异步、回调地狱、Promise 三种状态与链式调用、async/await（常用必会）；
- **进阶**：Promise 静态方法组合、Generator 与 async 的关系、事件循环宏任务/微任务调度、浏览器与 Node 差异；

JavaScript 是"单线程"语言，却能够处理网络请求、定时器、动画等并发任务，这依赖的正是它独特的**异步编程模型**与**事件循环（Event Loop）**机制。理解这套机制，是掌握 JS 进阶能力的分水岭——它决定了代码的执行顺序，也决定了你是否能写出无泄漏、无竞态的生产级代码。

这篇文章我们从"为什么需要异步"讲起，逐步深入 Promise、async/await、Generator，再揭开事件循环的底层真相，最后给出事件循环的经典输出题练习。

## 一、同步与异步

### 1. 什么是同步

**同步（Synchronous）**：代码按照书写顺序，一行一行、自上而下地执行，前一行没有执行完，后一行就不会开始。

```js
console.log("开始");
const result = 1 + 2; // 这行没执行完，下面不会执行
console.log(result);
console.log("结束");
```

同步代码符合人类直觉，但它有一个致命问题：**如果某一行耗时很长，就会"阻塞"后续所有代码的运行**。浏览器会因此卡顿，甚至失去响应用户点击的能力。

```js
// 假设这是一个耗时 3 秒的假同步函数
function block() {
  const end = Date.now() + 3000;
  while (Date.now() < end) {}
}

block(); // 阻塞 3 秒
console.log("3 秒后才打印"); // 页面在此期间会"假死"
```

### 2. 什么是异步

**异步（Asynchronous）**：发起一个任务后，不等待它的结果，而是立刻继续执行后面的代码；当任务完成时，再通过"回调"等手段通知你。

```js
console.log("1. 发起请求");
setTimeout(() => {
  console.log("2. 请求完成（异步回调）");
}, 1000);
console.log("3. 继续往下走");
// 输出：1 -> 3 -> 2
```

注意输出顺序是 `1`、`3`、`2`，说明 `setTimeout` 没有阻塞后续代码，其回调在 1 秒后才执行。

### 3. 异步的本质：单线程 + 回调

JavaScript 之所以要用异步，是因为它是**单线程**的。为避免"一个慢任务卡死整个应用"，它把"耗时操作"交给**宿主环境**（浏览器的 Web API、Node 的 libuv）去处理，等结果就绪后再把回调压回主线程执行。主线程永远只做一件事情，从而避免了多线程操作 DOM 带来的数据竞争。

## 二、回调地狱

异步最早的实现方式是**回调函数（Callback）**。但多层嵌套的异步逻辑会产生著名的**回调地狱（Callback Hell）**：

```js
// 模拟多层依赖的异步操作
getUser(userId, (user) => {
  getOrders(user.id, (orders) => {
    getOrderDetail(orders[0].id, (detail) => {
      getPayments(detail.id, (payments) => {
        // 层层嵌套，缩进越来越深……
      });
    });
  });
});
```

回调地狱带来的问题：

- **可读性差**：嵌套缩进越来越深，难以阅读。
- **难以维护**：修改一处逻辑往往牵动整个链路。
- **错误处理棘手**：每一层都要单独写错误回调，容易遗漏。
- **执行顺序不直观**：回调的实际调用时机难以一眼判断。

为解决这些问题，ES6 引入了 **Promise**。

## 三、Promise

### 1. 基本概念

`Promise`（承诺）是一个表示"异步操作最终结果"的对象。它有三种状态，且状态**一经变更就不可逆**：

- **pending（进行中）**：初始状态。
- **fulfilled（已成功）**：操作成功，对应 `resolve`。
- **rejected（已失败）**：操作失败，对应 `reject`。

```js
const p = new Promise((resolve, reject) => {
  // 异步任务
  setTimeout(() => {
    const ok = Math.random() > 0.5;
    if (ok) {
      resolve("成功数据");
    } else {
      reject(new Error("失败了"));
    }
  }, 1000);
});

p.then((data) => console.log("成功：", data))
 .catch((err) => console.log("失败：", err));
```

关键点：**状态只能从 `pending` 变为 `fulfilled` 或 `rejected`，且一旦转变就无法再改**。`resolve` 和 `reject` 谁先调用谁生效，重复调用无效。

### 2. 链式调用

聪明之处在于 `then` 会返回一个**新的 Promise**，因此可以无限链式书写，把"嵌套地狱"摊平成"串行链"：

```js
getUser(userId)
  .then((user) => getOrders(user.id))
  .then((orders) => getOrderDetail(orders[0].id))
  .then((detail) => getPayments(detail.id))
  .then((payments) => console.log(payments))
  .catch((err) => console.error("任一步出错都会到这里", err));
```

在链中：

- `then` 的回调返回**普通值**时，会传入下一个 `then`。
- `then` 的回调返回**新的 Promise** 时，下一个 `then` 会等待它完成。
- 任一环抛出异常或 reject，都会**跳过其后所有 `then`**，直达最近的 `catch`。

```js
Promise.resolve(1)
  .then((n) => n + 1)
  .then((n) => {
    throw new Error("中途出错");
  })
  .then(() => console.log("不会执行"))
  .catch((err) => console.log("捕获到：", err.message)); // 捕获到：中途出错
```

### 3. 静态方法与组合

`Promise` 提供了几个常用的静态方法，用于组合多个异步任务，是面试重点：

#### Promise.all —— 全部成功才成功

```js
const p1 = Promise.resolve(1);
const p2 = new Promise((r) => setTimeout(() => r(2), 1000));
const p3 = Promise.reject(new Error("boom"));

// 全部 fulfilled 时，返回所有结果的数组
Promise.all([p1, p2]).then((res) => console.log(res)); // [1, 2]

// 只要有一个 rejected，整体立即 rejected，且只返回最先失败者
Promise.all([p1, p2, p3]).catch((err) => console.log(err.message)); // boom
```

适用场景：**需要并行发起且全部成功才继续**，例如同时请求多个独立接口再合并渲染。

#### Promise.allSettled —— 等全部结束，无论成败

```js
const results = await Promise.allSettled([p1, p2, p3]);
console.log(results);
// [
//   { status: "fulfilled", value: 1 },
//   { status: "fulfilled", value: 2 },
//   { status: "rejected", reason: Error: boom }
// ]
```

它**永不 reject**，总是返回每个任务的状态明细，适合"部分成功也要收集结果"的场景（如批量上传、批量下载）。

#### Promise.race —— 谁先完成听谁的

```js
Promise.race([p1, p2]).then((res) => console.log(res));
```

`race` 只看**最先落定**的那个（无论成功还是失败）。常用来实现"超时控制"：

```js
function withTimeout(promise, ms) {
  const timeout = new Promise((_, reject) =>
    setTimeout(() => reject(new Error("请求超时")), ms)
  );
  return Promise.race([promise, timeout]);
}
```

#### Promise.any —— 有一个成功即可（ES2021）

```js
Promise.any([p3, p1]).then((res) => console.log(res)); // 1
// 若全部 rejected，则整体 rejected，且 reason 是 AggregateError
```

`any` 与 `race` 的区别：`any` 只关心"成功"，只要有一个 fulfilled 就立即返回该结果；如果全部失败，才 rejected。它适合"多个兜底接口，谁成功用谁"的场景（如切 CDN）。

### 4. 巨坑提醒

- **Promise 里的异常不会自动抛出到外层**，必须显式 `.catch`，否则会出现"未处理的 Promise rejection"。
- `.finally` 在成功或失败后都会执行，适合做清理（关闭 loading、释放资源），但它不改变结果值。

```js
p.finally(() => console.log("无论成败，必定执行"));
```

## 四、async/await

`async` / `await` 是 ES2017 提供的语法糖，让异步代码**看起来像同步**，彻底消除链式回调的视觉噪音。

```js
async function getData() {
  try {
    const user = await getUser(userId);
    const orders = await getOrders(user.id);
    return orders; // async 函数总是返回一个 Promise
  } catch (err) {
    console.error(err);
  }
}

getData().then((res) => console.log(res));
```

关键规则：

- 声明为 `async` 的函数，**总返回一个 Promise**（即使内部直接 `return 2`，外层拿到的也是 `Promise.resolve(2)`）。
- `await` 只能出现在 `async` 函数中（顶层 `await` 属模块增强特性，需特定环境支持）。
- `await` 会**暂停**当前 `async` 函数的执行，直到右侧 Promise 落定；右侧是非 Promise 值时会自动包装。
- 用 `try/catch/finally` 捕获错误，替代 `.catch`。

```js
async function main() {
  const value = await Promise.resolve(42);
  console.log(value); // 42
}
main();
```

`await` 让"并行"变得容易——如果你想让多个互不依赖的任务**并行**，应先并发发起再用 await 汇总，而不是一个个顺序 await：

```js
// 错误：串行，总共耗时 2s
const a = await fetchA();
const b = await fetchB();

// 正确：并行，耗时约 1s
const [a2, b2] = await Promise.all([fetchA(), fetchB()]);
```

## 五、Generator 与 async 的关系

`Generator`（生成器）函数用 `function*` 声明，配合 `yield` 可以**暂停和恢复**执行，这是它和 async/await 的渊源所在：

```js
function* gen() {
  const a = yield 1;   // 暂停，交出控制权
  const b = yield a + 1;
  return b;
}

const it = gen();
console.log(it.next());        // { value: 1, done: false }
console.log(it.next(10));      // { value: 11, done: false }
console.log(it.next());        // { value: 11, done: true }
```

`next(value)` 可以把**值回传**给上一次的 `yield` 位置，这正是"挂起-恢复"的核心。

### 1. async/await 本质上是对 Generator 的封装

历史上来讲，最早"用同步写法写异步"的方案之一，是通过 **co 库**驱动 Generator 自动执行：遇到 `yield promise` 就等待其落定再 `next` 继续。后来 ES2017 把这一模式"内置"成了 `async/await`。

可以把 `async/await` 理解为：**async ≈ `function*` + 自动执行器**，await ≈ yield。

```js
// 用 Generator 模拟 async/await 的雏形（co 库的核心思想）
function co(genFn) {
  const it = genFn();
  function step(args) {
    const { value, done } = it.next(args);
    if (done) return value;
    return Promise.resolve(value).then(step); // await 后的结果回传给 yield
  }
  return Promise.resolve(step());
}
```

### 2. 二者的联系与差异

| 维度 | async/await | Generator |
| --- | --- | --- |
| 语法本质 | 语言内置的语法糖 | 生成器，可挂起/恢复 |
| 是否需要手动驱动 | 否，自动管理 | 是，需手动调用 `.next()` |
| 错误处理 | `try/catch` 直观 | 需配合自动执行器或手动处理 |
| 是否返回 Promise | 总是 | 返回迭代器对象 |
| 实际用途 | 异步流程控制 | 惰性求值、无限序列、迭代器本质 |

```js
// Generator 的另一个经典用途：惰性生成无限序列
function* infinite() {
  let i = 0;
  while (true) yield i++;
}
const it = infinite();
console.log(it.next().value); // 0
console.log(it.next().value); // 1
```

## 六、事件循环（Event Loop）

### 1. 为什么需要它

虽然 async/await 写起来像同步，但底层依然是**单线程 + 事件循环**。事件循环是"调度器"：当主线程空闲时，不断地从"任务队列"里取出任务执行。

### 2. 宏任务（MacroTask）与微任务（MicroTask）

任务分为两大类：

- **宏任务（MacroTask）**：`setTimeout`、`setInterval`、`setImmediate`（Node）、I/O、UI 渲染、`requestAnimationFrame` 等。
- **微任务（MicroTask）**：`Promise.then`、`queueMicrotask`、`process.nextTick`（Node）、`MutationObserver` 等。

核心规则是：**每执行完一个宏任务，都会清空当前所有微任务；微任务之间在执行宏任务之前一次性按序处理完毕。**

```js
console.log("A");            // 同步
setTimeout(() => console.log("B"), 0); // 宏任务 B
Promise.resolve().then(() => console.log("C")); // 微任务 C
console.log("D");            // 同步
// 输出顺序：A D C B
```

为什么 `C` 在 `B` 前面？因为微任务在整个宏任务（这里是整个同步脚本）执行结束后、等待下一个宏任务之前，会被一次全部清空。

### 3. 浏览器中的事件循环流程

```
宏任务队列
  │
  ▼
执行一个宏任务
  │
  ▼
执行所有微任务（若期间产生新的微任务，继续执行到底）
  │
  ▼
需要渲染则渲染（UI 更新、requestAnimationFrame）
  │
  ▼
回到宏任务队列，取下一个
```

要注意：**微任务可以"饿死"渲染**。如果一个微任务里不断创建新的微任务，那么渲染和下一个宏任务会被无限推迟，页面就可能卡死。

```js
// 危险的例子：微任务无限循环，阻塞渲染与后续宏任务
function loop() {
  queueMicrotask(loop);
}
loop(); // 慎用，会卡死页面
```

### 4. Node.js 与浏览器的区别

Node 的事件循环（基于 libuv）有**六个阶段**，比浏览器更复杂：

```
   ┌───────────┐
 ┌─┤  timers   │ setTimeout / setInterval 到期回调
 └─▶  ┌───────────┐
  │   │  pending   │ 系统 I/O 回调（如 TCP 错误）
  ├─▶  ┌───────────┐
  │   │  poll       │ 主要的 I/O 事件（等待/处理回调）
  ├─▶  ┌───────────┐
  │   │  check      │ setImmediate 回调
  └────┤  close     │ close 事件回调（如 socket 关闭）
```

几个重要的 Node 特性差异：

- `process.nextTick` 是 Node 特有，其优先级比 Promise（微任务）还高，会在**当前阶段结束、下一阶段之前**立即执行。
- `setImmediate` 与 `setTimeout(..., 0)` 在**主模块**中的执行顺序不固定（取决于 I/O 阶段进入时机）；但在 **I/O 回调内部**，`setImmediate` 一定先于 `setTimeout`。
- Node 11 之后，微任务阶段的处理行为与浏览器趋于一致（每处理一个宏任务就清一次微任务）。

```js
// Node 环境
process.nextTick(() => console.log("nextTick"));
Promise.resolve().then(() => console.log("promise"));
console.log("sync");
// 输出：sync → nextTick → promise（Node 中 nextTick 优先于 Promise 微任务）
```

### 5. 定时器相关 API

#### setTimeout / setInterval

- `setTimeout(fn, delay)`：`delay` 毫秒后执行**一次**。注意最小延迟约为 4ms（嵌套嵌套时可能缩为 1ms），且会被挂起/后台标签页的 `throttling` 影响，**并非精确计时器**。
- `setInterval(fn, interval)`：每隔 `interval` 毫秒执行**一次**。若每次回调执行时间超过间隔，会排队等待（不会并发执行）。

```js
const timer = setTimeout(() => console.log("延迟执行"), 1000);
clearTimeout(timer); // 取消

const interval = setInterval(() => console.log("每秒一次"), 1000);
clearInterval(interval); // 清除
```

**真实计时建议**：无论是 `setTimeout` 还是 `setInterval`，都受事件循环、渲染、节流影响，精度有限。需要精确计时（如倒计时、动画）时，应基于系统时钟计算差值，而不是靠计时器"凑次数"。

```js
// 用 setTimeout 实现更稳妥的"每秒"，避免 setInterval 漂移
let expected = Date.now() + 1000;
function tick() {
  console.log("tick");
  const drift = Date.now() - expected;
  expected += 1000;
  setTimeout(tick, 1000 - drift); // 每次根据偏差修正
}
setTimeout(tick, 1000);
```

#### requestAnimationFrame（rAF）

- 专用于**动画**，浏览器会在**下一次重绘之前**调用回调（通常 60fps）。
- 页面切到后台/不可见时**自动暂停**，节省资源，天然适配节流。
- 回调中通常再调用一次 `requestAnimationFrame` 形成循环。

```js
let start = null;
function step(timestamp) {
  if (!start) start = timestamp;
  const progress = (timestamp - start) / 1000;
  element.style.transform = `translateX(${progress * 100}px)`;
  if (progress < 2) requestAnimationFrame(step); // 持续 2 秒
}
requestAnimationFrame(step);
```

相比 `setInterval`，rAF 的帧率与屏幕刷新率同步、后台暂停、能拿到精确时间戳，**动画首选 rAF**。

#### requestIdleCallback（rIC）

- 在浏览器**空闲时期**执行低优先级任务，优先保证用户交互与渲染不被阻塞。
- 回调收到 `IdleDeadline`，通过 `timeRemaining()` 判断还剩多少空闲时间。
- 不支持的环境需降级（用 rAF 或 `setTimeout` 兜底）。

```js
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 0 && queue.length) {
    doTask(queue.shift()); // 在空闲时间内分片处理
  }
});
```

典型用途：上报日志、preload 非关键资源、处理大数据分批渲染。

## 七、事件循环经典输出题

综合以上规则，来做几道经典题，先自己思考再对照答案。

### 题目一：基础混合

```js
setTimeout(() => console.log("t1"), 0);
Promise.resolve().then(() => console.log("p1"));
console.log("sync");
```

```js
// 输出：
// sync → p1 → t1
```

分析：同步 `sync` 先输出；随后微任务 `p1` 在宏任务 `t1` 之前被清空。

### 题目二：嵌套微任务

```js
Promise.resolve().then(() => {
  console.log("a");
  Promise.resolve().then(() => console.log("b"));
});
setTimeout(() => console.log("c"), 0);
```

```js
// 输出：
// a → b → c
```

分析：清空微任务时，`then` 里新产生的微任务 `nested b` 会**继续**在本次微任务队列中执行完毕，因此 `a`、`b` 都在 `c` 之前。

### 题目三：async 内部细节

```js
async function foo() {
  console.log("start");
  await bar();
  console.log("after");
}
function bar() {
  console.log("bar");
}
foo();
console.log("outer");
```

```js
// 输出：
// start → bar → outer → after
```

分析：`async` 函数体在调用时**同步**执行到第一个 `await`；`bar()` 本身是同步的，所以 `bar` 立即输出。`await` 后的 `after` 被当作微任务挂起，因而在 `outer` 之后输出。这是一个高频考点——**await 会将其右侧后面的代码延后到微任务中执行**。

### 题目四：定时器与渲染调度

```js
setTimeout(() => console.log("task"), 0);
requestAnimationFrame(() => console.log("raf"));
console.log("sync");
```

```js
// 输出（大致）：
// sync → （一帧内）raf → task
```

分析：当前同步任务结束、微任务清空后，浏览器先触发下一次重绘（`rAF` 回调），之后才继续取宏任务 `task`；因此 `raf` 通常早于 `task`。（帧率与节流会影响精确顺序。）

### 小结万能口诀

> 同步代码立即执行 → 微任务（当前宏任务结束时一次性清空，含新增）→ UI 渲染/rAF → 下一个宏任务。nextTick（Node）优先于普通微任务。

## 八、本章回顾

| 主题 | 核心要点 |
| --- | --- |
| 同步/异步 | 单线程决定必须异步，异步靠宿主 + 回调 |
| 回调地狱 | 多层嵌套难读难维护，催生 Promise |
| Promise | 三态不可逆，链式与组合（all/allSettled/race/any）|
| async/await | 语法糖，让异步像同步，自动并行可用 Promise.all |
| Generator | 可挂起恢复，是 async/await 的底层鼻祖，亦用于惰性序列 |
| 事件循环 | 宏任务/微任务调度，浏览器与 Node 阶段差异 |
| 定时器 | setTimeout/setInterval 精度有限；rAF 做动画；rIC 做闲时任务 |

掌握异步与事件循环，不只是为了应付面试，更是编写高性能、无泄漏前端应用的基础。下一章我们继续深入**内存管理与垃圾回收**，看看上层的"异步"如何在底层资源层面被真正管理。
