# 性能优化手段与落地

## 一、排障主线：核心指标超标后，先定位到层再动手

这张表是全篇索引。核心指标超标 → 顺着辅助指标找异常段 → 落到层 → 在层里查手段，**不要从手段出发乱改**。

| 核心指标 | 先看哪个辅助指标 | 异常信号 | 归属层 | 优化手段 |
| --- | --- | --- | --- | --- |
| LCP | TTFB | > 500ms | 网络层 | `preconnect` / `dns-prefetch`、CDN、HTTP/2 → 二 |
| LCP | 资源瀑布 / Coverage | 阻塞资源条又长又靠右 | 构建与产物层 | 路由分包、tree-shaking、压缩、hash + 长缓存 → 四 |
| LCP | FCP | TTFB 正常、FCP 明显晚 | 资源层 | 图片格式与尺寸、关键 CSS 内联、字体 preload → 三 |
| LCP | LCP 元素本身 | 骨架屏成了 LCP 元素 | 感知层 | SSR/SSG、骨架屏必须配「真实内容渲染完成」指标 → 七 |
| INP | TBT / Long Task | 交互正落在长任务里 | JS 执行层 | 切片、Worker、换算法 → 六 |
| INP | Long Task 后紧跟的 Layout | 回调快返回、紧跟大范围重排 | 渲染层 | 读写分离、虚拟滚动 → 五 |
| INP | 重渲染次数 | 数据没变、一片组件重渲 | 框架层 | 稳定 key、状态下沉、memo → 六 |
| INP | 堆内存曲线 | 只涨不落、越用越卡 | 内存与长会话 | 摘监听、清定时器、缓存设上限 → 六 |
| CLS | Layout Shift 条目 | 位移时刻接近 LCP | 资源层 | 图片宽高、`aspect-ratio`、字体度量对齐 → 三 / 五 |
| CLS | Layout Shift 条目 | 位移发生在接口返回后 | 渲染层 | 容器 `min-height` 预留、不在上方插入 → 五 |
| CLS | Layout Shift 条目 | 位移持续累积 | 渲染层 | 动画只用 `transform` / `opacity` → 五 |

三个核心指标的「拆法」是定位的钥匙——哪一段长，就去改服务那一段的层：

```
LCP = TTFB(网络) ＋ 加载延迟(发现得早不早) ＋ 加载时长(体积) ＋ 元素渲染延迟(主线程忙不忙)
INP = 输入延迟(主线程被占) ＋ 处理时间(回调本身慢) ＋ 呈现延迟(DOM 大 / 强制布局)
CLS = 影响比例 × 位移距离比例，只看元素起始位置变没变
```

两条纪律：

1. **上游决定下游**：TTFB 3s 时后面 FCP / LCP 不可能好，先修上游；TTFB 只有 60ms 时去优化服务端没收益——瓶颈一定在后面。
2. **指标要互相印证**：「传输量砍一半」和「LCP 一点没动」摆在一起才有结论——说明改的那一段不在 LCP 的构成里，换下一段。

## 二、网络层：减少请求、缩小体积、缩短 RTT、提高缓存命中

网络层通常收益最大，优先做。目标四个：减少请求、减少包体积、缩短 RTT、提升缓存命中率。

### 1. 传输协议与连接

- **HTTP/2 / HTTP/3（QUIC）**：多路复用，解决 HTTP/1.1 的队头阻塞；HTTP/3 基于 UDP，弱网下建连更快。
- **静态资源全部走 CDN**：缩短物理距离，回源压力也小。
- **预连接第三方域名**：`dns-prefetch` 提前解析 DNS、`preconnect` 提前建连（见本章第 4 节）。

### 2. 缓存策略：二次访问传输归零

- **强缓存**（不发请求）：`Cache-Control: max-age` 优先，`Expires` 是旧写法。
- **协商缓存**（304）：`ETag` / `Last-Modified`，资源变了才重新下载。
- **命名纪律**：静态资源用内容 hash 文件名（`main.xxxx.js`）配长期 `max-age`——内容变文件名就变，缓存永远新鲜；入口 HTML 不缓存或短缓存，保证用户拿到最新引用。

### 3. 传输压缩

- 文本资源必开 gzip / **Brotli**（压缩率更高，优先）：JS、CSS、HTML、SVG。gzip 约压掉 70%，Brotli 再小 15~20%；只对文本有效，图片视频本身已压缩。

### 4. 四个「提前」指令（高频混淆）

| 指令 | 做的事 | 用在哪 |
| --- | --- | --- |
| `preconnect` | 提前 DNS + TCP + TLS | 同域后面还要发多个请求（CDN），开销最大收益也最大 |
| `dns-prefetch` | 只解析 DNS | 第三方域名，收益小开销也小 |
| `preload` | 高优先级现在就下 | 关键路径但浏览器发现得晚的（LCP 图、关键字体） |
| `prefetch` | 空闲时下 | 高概率、小体积的下一页资源 |

三条注意：`preload` / `prefetch` 只改变**开始下载的时刻**、不改变体积——解决「发现得晚」，不解决「太大」；`as="font"` 必须带 `crossorigin`，否则字体会被下载两次；preload 加太多会抢关键资源的带宽。

## 三、资源层：图片、字体与关键渲染路径

TTFB 正常但 FCP / LCP 明显晚，看关键渲染路径上谁在挡第一帧。

### 1. 图片（LCP 与 CLS 的双重重灾区）

- **格式**：照片用 WebP / AVIF（比 JPEG 小 25~50%），图标用 SVG。
- **写死 `width` / `height`**：浏览器在图片到位前就预留出位置，自动算 `aspect-ratio`——根治图片类 CLS；属生要写在 HTML 属性里，不能等 JS/CSS。
- **响应式**：`srcset` + `sizes` 按视口挑尺寸，**各档比例必须一致**（`srcset` 换分辨率不换比例）。
- **懒加载 `loading="lazy"`**：只改善**首屏之后**的带宽竞争，**不改善首屏**（自带约 1250px 预加载距离）；**首屏主图千万别加**——会被降到低优先级，LCP 直接变差，应配 `fetchpriority="high"`。
- **LCP 图预加载**：`<link rel="preload" as="image" href="...">`，让它早于 CSS/JS 被发现。
- 图片走 CDN、按需裁剪尺寸、控制质量梯度。

### 2. 字体

- **体裁剪（子集化）+ WOFF2**：只打包实际用到的字符。
- **`font-display: swap`**：先用回退字体渲染（FOUT），避免默认 `auto` 最长 3s 的不可见期（FOIT）；CLS 敏感场景用 `optional`。
- **preload 关键字体**（`as="font"` 带 `crossorigin`），赶在首次绘制前到位；非必要字体异步加载。
- 回退字体用 `size-adjust` 校准度量，减小换字重排。

### 3. 关键 CSS

- **关键 CSS 内联**进 `<head>`（首屏布局所需的那部分），全量 CSS 异步加载（`media="print"` + `onload` 改 `all` 是最稳的写法）。
- 内联部分**必须含布局尺寸**，否则异步 CSS 一到就位移——用 CLS 换 FCP。

一个现代工程事实：`<script type="module">` 天然 defer，vite / webpack 入口脚本不阻塞解析；动态 `appendChild` 的 script 默认 `async` 也不阻塞——真正要操心的是写死在 HTML 里的第三方统计脚本。

## 四、构建与产物层：把首屏字节砍下来

JS 解析是昂贵操作，产物瘦身的本质是**少下载、少解析、多复用缓存**。

### 1. 代码分割

- **路由懒加载**：路由组件改动态 `import()`（React.lazy + Suspense / Vue defineAsyncComponent），首屏只带当前路由。本质是**时序优化不是体积优化**——收益 = 拆出去的体积 × 上首屏的概率；**必须配空闲预取**（只预取大概率去的一两个路由），否则切路由时连本带利还回去。
- **第三方包单独分包**（vendor / chunk）：框架代码变动少，单独成块吃满长缓存。

### 2. tree-shaking

- 删「没被引用的导出」。前提三条：ESM 模块（不能是 CommonJS）、库标 `sideEffects: false`、访问方式静态。
- `if (false) { heavy() }` 这种引用了但没执行到的分支**打不掉**；体积对比是唯一能发现它没生效的证据。

### 3. 第三方依赖治理（很多项目包体积的最大元凶）

- 替换重型库：moment → dayjs；lodash 全量 → lodash-es 按需导入。
- 剔除无用依赖、版本瘦身。
- **externals**：大库走 CDN 引入，不打进 bundle。

### 4. CSS 与产物清理

- **CSS tree-shaking**（PurgeCSS）：移除未使用样式。
- **移除 console**：但别把 `console.error` 删了（监控上报靠它）；属性名混淆会让上报字段名一起变。
- **sourcemap 绝不部署线上**：生产关闭或上传监控平台，不下发给用户。

## 五、渲染层：少重排重绘，稳住 CLS

### 1. 避免强制同步布局（Layout Thrashing）

浏览器渲染是攒批的，但 JS 改完样式立刻读布局属性（`offsetWidth` / `offsetTop` / `getBoundingClientRect` / `getComputedStyle`）就逼迫它马上重算。解法：**先批量读，再批量写**；写延到 `requestAnimationFrame` 批量。

> 示意片段（无配套脚本）

```js
// 坏：循环内读写交错，每次读都强制浏览器马上重排
for (const el of list) {
    const h = el.offsetHeight           // 读
    el.style.height = h + 10 + 'px'     // 写
}
// 好：先全部读取，再全部写入
const heights = list.map(el => el.offsetHeight)
list.forEach((el, i) => { el.style.height = heights[i] + 10 + 'px' })
```

### 2. 动画走合成层

- 只用 `transform` / `opacity`：不触发重排重绘、可上 GPU、也不产生 CLS——同时服务三个核心指标。
- `will-change` 谨慎使用：提前分配图层与 GPU 内存，滥用反而耗资源。

### 3. 稳住 CLS 的四类写法

| 位移来源 | 解法 |
| --- | --- |
| 媒体 / 广告位晚到 | 写死 `width` / `height`，iframe 用占位容器 |
| 字体换字重排 | `size-adjust` 对齐度量 + 字体 `preload` |
| 动态内容晚插 | 容器 `min-height` 预留、**绝不在已有内容上方插入**；骨架屏与真实内容结构一致 |
| 用布局属性做动画 | 只用 `transform` / `opacity`；真要改布局放容器内部，或确保发生在交互后 500ms 内（规范当「预期位移」排除） |

动态内容这类问题**开发环境通常看不见**（本地接口几十毫秒返回），必须限速复现。

### 4. DOM 与长列表

- **减少 DOM 节点数**：上千节点会拖慢样式计算与布局。
- **虚拟滚动**：只渲染视口内的 DOM（vue-virtual-scroller / react-window）。它解决「DOM 太多」、**不解决「计算太重」**——先分清哪口锅；窗口重算要 rAF 合帧，否则重算成新卡顿源；行高必须固定。
- **批量插入**：文档碎片 DocumentFragment 收集后一次插入，避免循环 `innerHTML` / `append`。

## 六、JS 主线程层：拆长任务、降 INP

INP 上线后，主线程长任务是第一大痛点。两个标尺：**单帧 16.7ms**（超了掉帧）、**长任务 50ms**（期间不响应输入）。

### 1. 长任务拆分（核心方案）

- **切片**：用 `MessageChannel` 或 `scheduler.postTask` 把超大循环、复杂计算切成多片，片间让出主线程。**不能用 `Promise.then`**（微任务在当前宏任务结束前全跑完，一帧插不进）；`setTimeout(0)` 有 4ms clamping，片多白等。
- **`requestIdleCallback`**：低优先级任务（埋点上报、统计、弹窗预加载）在浏览器空闲时执行。
- **Web Worker**：**纯计算逻辑移出主线程**（排序、解析、加密、大数据处理）。边界要清楚：`postMessage` 结构化克隆**在主线程同步执行**、成本随数据量线性增长；Worker 无 DOM、启动几十毫秒级——适合「输入小、算得久」的一次重活，不适合每 10ms 一次的小任务。
- **换算法**：单个工作单元本身就超 50ms 时，切片和 Worker 都救不了，只能降复杂度。
- 一个容易反的点：**「总耗时」≠「INP」**——切片让总耗时变长（每片有结算开销），但最长阻塞块降下来 INP 就变好。

### 2. 懒执行与事件优化

- 非首屏逻辑（埋点、弹窗、评论、推荐模块）等页面空闲再加载执行。
- **防抖 debounce**（输入搜索）、**节流 throttle**（scroll / resize / mousemove）。
- **事件委托**：减少事件绑定数量。
- 避免在主线程做大量 `JSON.parse`、大文件解析。

### 3. 框架层：避免无效重渲染

判据只有一条：**一次交互后有多少组件被重渲染了、而数据其实没变**。

- **稳定 key**：不要用数组下标当 key——插入 / 排序时框架把「移动几个」误判成「重建一片」。
- **状态下沉**：与列表无关的状态别穿透进每一行；别把大对象塞进一个 state / ref。
- **React**：`memo` / `useMemo` / `useCallback` 合理使用——缓存本身有开销，滥用反而增加内存与耗时。
- **Vue**：`shallowRef` / `shallowReactive` / `markRaw` 跳过深层代理，复杂表达式抽 `computed`，长列表 `v-memo`。
- **重组件按需引入**：编辑器 / 图表 / 地图这类重但非首屏必需的组件，同时减首屏体积与初始化长任务。

### 4. 内存与长会话：为什么越用越卡

「越用越卡」几乎都来自引用没释放，四类泄漏、对策都是断开那条引用：

1. **事件监听没摘**：卸载时 `removeEventListener`。
2. **定时器没清**：及时 `clearInterval` / `clearTimeout`。
3. **全局缓存只增不减**：配 LRU 或大小上限。
4. **闭包绑死大对象**：只保留真正用到的字段。

定位靠 Memory 面板：Heap snapshot 对比（哪类对象只增不减）、Detached DOM（被闭包吊住的游离节点）、Allocation timeline（哪一帧突然涨上去）。

## 七、渲染模式选型：CSR / SSR / SSG / ISR 是顶层性能决策

不同渲染模式天然性能基线不同，选型本身就是性能优化：

| 模式 | TTFB | LCP | SEO | 代价 | 适合 |
| --- | --- | --- | --- | --- | --- |
| CSR（SPA） | 取决于静态资源 | 差（等 JS 渲染） | 差 | — | 后台管理 |
| SSG（静态生成） | 极低 | 优秀 | 好 | 构建期生成，更新要重建 | 内容页、文档（VitePress、Next 静态页） |
| SSR（服务端渲染） | 取决于后端 | 好 | 好 | 服务器压力大；**水合抢占主线程，是 SSR 页面常见的 INP 杀手** | 动态首屏 |
| ISR（增量静态再生） | 低 | 优秀 | 好 | 增量更新有延迟 | 高频更新的内容页 |

水合（hydration）优化策略：

1. 延迟非关键组件水合；
2. 按需水合（交互后再水合）；
3. **选择性水合 / 岛屿架构（Islands）**：只水合有交互的组件，大幅减少水合 JS（Astro、Marko）。
4. 兜底手段是减少 SSR 页面的 JS 体积。

## 八、落地闭环：从基线到门禁，防止性能回退

1. **定基线**：先采集线上 RUM，统计 P50 / P90 / P95——**不看平均值，看分位数**；P95 代表最差那批用户，是优化重点。
2. **定位瓶颈**：LCP 差查 Network（TTFB？图片太大？JS 阻塞？）；INP 差用 Performance 看长任务、找到耗时代码；CLS 高找没有固定尺寸的动态资源。
3. **小流量灰度**：不要全量上线。
4. **验证收益**：优化后对比 P95 指标；实验室结论必须由现场数据闭环——上线后回看板确认分布真的移动了。
5. **CI 性能门禁**：打包体积阈值（如单包 JS 超 500KB 阻断 MR）、Lighthouse CWV 不达标禁止发布——防止后续迭代退化。
6. **持续看板告警**：指标恶化自动告警。

## 九、高频坑与误区

1. **「Lighthouse 分高 = 用户体验好」**：Lighthouse 是受控实验室环境，弱网、低端机、真实网络波动模拟不了；体验以 RUM 为准。
2. **「useMemo / memo 越多越好」**：缓存本身有开销，滥用反而增加内存和耗时。
3. **「will-change 大量加」**：提前分配 GPU 内存，反而耗资源。
4. **「preload 所有资源」**：preload 过多抢占带宽，拖慢关键资源。
5. **「图片懒加载加在 LCP 图上」**：LCP 图懒加载会被降优先级，LCP 直接变差。
6. **「平均值看性能」**：性能指标看 P90 / P95，长尾用户才是优化重点。
