## 1. 性能优化体系与指标

### 1.1 指标体系：核心指标是目标，辅助指标是刻度

**结论：CWV 三核心（LCP / INP / CLS）是要守的目标，其余指标都是定位刻度；核心指标告诉你去哪，辅助指标告诉你在哪，二者不可混用。**

| 核心指标 | 中文含义 | 目标（p75） | 用户的话 |
| --- | --- | --- | --- |
| LCP | 最大内容绘制 | ≤ 2.5s 良好；2.5~4s 待改进；> 4s 差 | 多久能看到内容 |
| INP | 交互到下一次绘制 | ≤ 200ms 良好；200~500ms 待改进；> 500ms 差 | 点了多久有反应 |
| CLS | 累积布局偏移 | ≤ 0.1 良好；0.1~0.25 待改进；> 0.25 差 | 页面会不会自己乱跳 |

一句话记忆：**LCP 看加载快不快，INP 看点击卡不卡，CLS 看页面跳不跳**。三个谁也替代不了谁——LCP 好不代表体验好（主图不写尺寸时 CLS 差而 LCP 不动）。

- **LCP**：视口内最大可见元素完成渲染的时间；只记录初始加载、多次渲染取最后一次；元凶是大图未优化、服务端慢、阻塞 JS/CSS、字体。
- **INP**（替换旧 FID）：任意交互到下一次绘制的时间，取全页**最差交互**；衡量点击卡顿，长任务是 INP 杀手。
- **CLS**：无用户操作的意外位移总分；每次位移 = 影响比例 × 位移距离比例；元凶是图片无宽高、动态广告、字体 FOIT、异步插 DOM。

定位刻度：

```
请求发出      首字节     首次绘制   首次内容    最大内容    可交互     一次交互
  │            │           │          │          │          │          │
  ◄──TTFB──►   FP         FCP        LCP        TTI        INP
```

| 指标 | 定位用途 |
| --- | --- |
| TTFB | 首字节时间，所有加载指标的上游；高 = DNS / CDN / 服务端 / 数据库慢，服务端那段前端救不了 |
| FP | 首次绘制，白屏结束的起点，不区分内容是否有效 |
| FCP | 首次内容绘制（文本 / 图片 / SVG），用户开始看到内容 |
| FMP | 首次有意义绘制——**标准已废弃** |
| TTI | 可交互时间——**Core Web Vitals 已移除**，长任务会拉高它 |
| TBT | FCP→TTI 间长任务超 50ms 部分之和，主线程卡顿度量，**INP 的实验室代理** |
| Long Task | 主线程任务 > 50ms，直接拉高 INP / TBT / TTI |
| Layout Shift | 单次布局偏移，CLS 的组成单元 |
| 资源指标 | JS / 图片总大小、请求数、缓存命中率 |

三个核心指标的「拆法」是分层的钥匙：

```
LCP = TTFB ＋ 加载延迟 ＋ 加载时长 ＋ 元素渲染延迟
INP = 输入延迟 ＋ 处理时间 ＋ 呈现延迟
CLS = 影响比例 × 位移距离比例，只看起始位置变没变
```

### 1.2 渲染流水线：重排、重绘与合成三级开销

**结论：优化就是挑开销最低的那条路——优先合成、其次重绘、避免重排。**

```
请求资源 → 解析HTML生成DOM树 → 解析CSS生成CSSOM树 → 合并生成Render树
        → Layout(布局/重排) → Paint(绘制) → Composite(合成)
```

| 环节 | 触发 | 开销 |
| --- | --- | --- |
| 重排 Reflow | 几何属性（宽高 / margin / top）变化、DOM 增删、读 offset 系列 | 最大 |
| 重绘 Repaint | 颜色、背景色、visibility 等不改布局的样式 | 中等 |
| 合成 Composite | transform、opacity | 最低，可走 GPU |

主线程模型：主线程**单线程**负责 JS 解析执行、DOM、样式计算、Layout、Paint；JS 执行抢占主线程，期间不响应输入、不渲染——这是前端卡顿的核心根源。合成线程、GPU 线程、网络线程是绕开瓶颈的资源。

### 1.3 口径：先判断数可不可信

**结论：实验室管定位、现场管发现，线上以 RUM 为准；一律看分位数，一次只盯一个指标。**

- **实验室 vs 现场**：Lighthouse / DevTools = Lab（受控、可复现）；RUM = 真实用户分布。分工：现场看分布发现问题 → 实验室复现根因 → 改完回现场验证。
- **看 p75 / p95**：性能是长尾分布，均值被极少数样本带偏；P95 代表最差那批用户，是优化重点。
- **评级是门槛不是排名**：LCP 8000→3000ms 仍是「待改进」，但体感是两个世界；一次只盯一个指标。
- **CLS 双口径**：`cls`（规范口径，剔掉交互后 500ms 内的预期位移，现场报表读）+ `clsRaw`（所有位移之和，对照实验读）；两个值必须分开上报。

### 1.4 采集与工具：读数从哪来

**结论：线上采集用浏览器原生 API（web-vitals 库封装），调试工具按「它替你做了什么决定」选、按「先粗后细」用。**

- **PerformanceObserver**：订阅 LCP / INP / CLS；LCP、INP 动态更新，**页面卸载时取最终值上报**。
- **Long Task API / LayoutShift 条目**：捕获长任务与逐次位移（`hadRecentInput` 区分预期位移）。
- **resource entries**：`transferSize` 为 0 即缓存命中。
- **web-vitals + `navigator.sendBeacon`** 上报（页面卸载也能发出、不阻塞）。

| 工具 | 替你做掉的事 | 适合回答 |
| --- | --- | --- |
| Network / 瀑布图 | 请求按时间排好、标优先级与阻塞 | 时间花在哪个资源等待上 |
| Performance | 主线程采样、火焰图 | 那 500ms 在跑什么函数 |
| Coverage | 每文件已用 / 总字节 | 有多少代码下了没用 |
| Memory | 堆快照 / Detached DOM / 分配时间线 | 越用越卡、什么没被回收 |
| Lighthouse | 全套审计打分 | 整体水位、短板扫描 |

用序先粗后细：先瀑布图 / TBT 定位阶段，再火焰图定位函数。红线：Lighthouse 分数是固定权重汇总、只代表这一次，**当趋势与短板扫描用，别当验收卡口**；要卡口就把 LCP / INP / CLS 真实读数写进 CI。上报、看板、告警的主体见前端监控模块《监控SDK》篇。

## 2. 性能优化手段与落地

### 2.1 排障主线：先定位到层再动手

**结论：核心指标超标 → 顺着辅助指标找异常段 → 落到层 → 在层里查手段，不从手段出发乱改。**

| 核心指标 | 先看哪个辅助指标 | 异常信号 | 归属层 | 手段所在 |
| --- | --- | --- | --- | --- |
| LCP | TTFB | > 500ms | 网络层 | 2.2 |
| LCP | 资源瀑布 / Coverage | 阻塞资源条又长又靠右 | 构建与产物层 | 2.4 |
| LCP | FCP | TTFB 正常、FCP 明显晚 | 资源层 | 2.3 |
| LCP | LCP 元素本身 | 骨架屏成了 LCP | 感知层 | 2.7 |
| INP | TBT / Long Task | 交互落在长任务里 | JS 执行层 | 2.6 |
| INP | Long Task 后紧跟 Layout | 回调快、紧跟大范围重排 | 渲染层 | 2.5 |
| INP | 重渲染次数 | 数据没变、组件重渲一片 | 框架层 | 2.6 |
| INP | 堆内存曲线 | 只涨不落、越用越卡 | 内存与长会话 | 2.6 |
| CLS | Layout Shift 条目 | 位移接近 LCP | 资源层 | 2.3 / 2.5 |
| CLS | Layout Shift 条目 | 位移发生在接口返回后 | 渲染层 | 2.5 |
| CLS | Layout Shift 条目 | 位移持续累积 | 渲染层 | 2.5 |

两条纪律：**上游决定下游**（TTFB 3s 时优化下游无效；TTFB 60ms 时优化服务端没收益）；**指标要互相印证**（「传输量砍一半」+「LCP 没动」摆在一起才有结论——改的那段不在 LCP 构成里）。

### 2.2 网络层：协议、缓存、压缩与预连接

**结论：收益通常最大、优先做；目标四个——减少请求、缩小体积、缩短 RTT、提高缓存命中。**

- **协议与连接**：HTTP/2 / HTTP/3（QUIC）多路复用解决 HTTP/1.1 队头阻塞；静态资源全走 CDN；`dns-prefetch` / `preconnect` 预连接第三方域名。
- **缓存策略**：强缓存 `Cache-Control: max-age`（不发请求）+ 协商缓存 `ETag` / `Last-Modified`（304）；静态资源内容 hash 文件名配长缓存，入口 HTML 不缓存或短缓存——二次访问传输归零。
- **传输压缩**：文本必开 gzip / Brotli（压缩率更高，优先），只对文本有效。
- **四个「提前」指令**：

| 指令 | 做的事 | 用在哪 |
| --- | --- | --- |
| `preconnect` | DNS + TCP + TLS | 同域后面还要发多个请求（CDN） |
| `dns-prefetch` | 只解析 DNS | 第三方域名 |
| `preload` | 高优先级现在就下 | 关键路径但发现得晚的（LCP 图、关键字体） |
| `prefetch` | 空闲时下 | 高概率、小体积的下一页资源 |

`preload` / `prefetch` 只改变开始下载时刻、不改变体积；`as="font"` 必须带 `crossorigin` 否则下载两次；preload 滥用抢关键资源带宽。

### 2.3 资源层：图片、字体与关键 CSS

**结论：TTFB 正常但 FCP / LCP 晚，看关键渲染路径上谁在挡第一帧；图片是 LCP 与 CLS 的双重重灾区。**

- **图片**：WebP / AVIF 格式；写死 `width` / `height`（自动 `aspect-ratio`，根治图片类 CLS）；`srcset` + `sizes` 响应式（各档比例必须一致）；`loading="lazy"` 只改善首屏之后、**首屏主图千万别加**（应配 `fetchpriority="high"`）；LCP 图 `<link rel="preload" as="image">`；图片 CDN 与裁剪。
- **字体**：子集化 + WOFF2；`font-display: swap`（避免默认 `auto` 最长 3s 的 FOIT，CLS 敏感用 `optional`）；关键字体 `preload`（带 `crossorigin`）；回退字体 `size-adjust` 校准度量。
- **关键 CSS**：首屏所需内联进 `<head>`，全量 CSS 异步（`media="print"` + `onload` 改 `all`）；内联部分必须含布局尺寸，否则用 CLS 换 FCP。
- 现代工程事实：`<script type="module">` 天然 defer，动态插入的 script 默认 `async`；要操心的是写死在 HTML 里的第三方统计脚本。

### 2.4 构建与产物层：分割、tree-shaking 与依赖治理

**结论：产物瘦身 = 少下载、少解析、多复用缓存；第三方依赖是很多项目包体积的最大元凶。**

- **代码分割**：路由懒加载（动态 `import()`）——**时序优化不是体积优化**，收益 = 拆出去的体积 × 上首屏概率，**必须配空闲预取**否则切路由连本带利还回去；第三方包单独分包（vendor）吃长缓存。
- **tree-shaking**：删「没被引用的导出」；前提 ESM、库标 `sideEffects: false`、静态访问；`if (false) { heavy() }` 打不掉，体积对比是唯一证据。
- **依赖治理**：moment → dayjs、lodash → lodash-es 按需；剔除无用依赖；externals + CDN 引入大库。
- **产物清理**：PurgeCSS 移除未用样式；移除 console 但保留 `console.error`（监控上报靠它）；sourcemap 绝不部署线上。

### 2.5 渲染层：读写分离、合成层与 CLS 四类写法

**结论：渲染层优化三条线——避免强制同步布局、动画走合成、用写法纪律把 CLS 压到零。**

- **读写分离（避免 Layout Thrashing）**：写样式后立刻读布局属性（`offsetWidth` / `getBoundingClientRect` 等）= 强制同步布局；先批量读、再批量写，写延到 rAF。
- **动画走合成**：只用 `transform` / `opacity`（不重排不重绘、不产生 CLS）；`will-change` 谨慎使用。
- **CLS 四类写法**：媒体写死尺寸；字体度量对齐 + preload；动态内容 `min-height` 预留、绝不在已有内容上方插入（开发环境看不见，必须限速复现）；动画只用 transform / opacity，真改布局放容器内或交互后 500ms 内。
- **DOM 与长列表**：减少节点数（上千节点拖慢样式计算）；虚拟滚动只渲染视口内 DOM——解决「DOM 太多」不解决「计算太重」，窗口重算要 rAF 合帧、行高必须固定；DocumentFragment 批量插入。

### 2.6 JS 主线程层：长任务拆分与框架渲染治理

**结论：INP 上线后主线程长任务是第一大痛点；两个标尺——单帧 16.7ms、长任务 50ms；「总耗时」≠「INP」。**

- **长任务拆分**：`MessageChannel` / `scheduler.postTask` 切片让出主线程（`Promise.then` 微任务插不进一帧、`setTimeout(0)` 有 4ms clamping，都不行）；`requestIdleCallback` 跑低优先级任务（埋点、统计）；Web Worker 移出纯计算——边界是 `postMessage` 结构化克隆在主线程同步执行、Worker 无 DOM 启动几十 ms，适合「输入小、算得久」；单个工作单元超 50ms 只能换算法。
- **懒执行与事件**：非首屏逻辑空闲再执行；防抖（输入搜索）、节流（scroll / resize / mousemove）；事件委托；避免主线程大 `JSON.parse`。
- **框架层**（判据：一次交互后多少组件重渲了、数据其实没变）：稳定 key（不用下标）；状态下沉；React `memo` / `useMemo` / `useCallback` 合理用（滥用反伤）；Vue `shallowRef` / `markRaw` / `v-memo` / 复杂表达式抽 `computed`；重组件按需引入。
- **内存与长会话**（越用越卡 = 引用没释放）：监听没摘、定时器没清、全局缓存不设上限（配 LRU）、闭包绑死大对象；用 Heap snapshot 对比、Detached DOM、Allocation timeline 定位。

### 2.7 渲染模式选型：CSR / SSR / SSG / ISR 与水合

**结论：渲染模式天然决定性能基线，选型是顶层性能决策。**

| 模式 | TTFB | LCP | SEO | 代价 | 适合 |
| --- | --- | --- | --- | --- | --- |
| CSR（SPA） | 取决于静态资源 | 差 | 差 | — | 后台管理 |
| SSG | 极低 | 优秀 | 好 | 更新要重建 | 内容页、文档 |
| SSR | 取决于后端 | 好 | 好 | 服务器压力；**水合抢占主线程（INP 杀手）** | 动态首屏 |
| ISR | 低 | 优秀 | 好 | 增量更新延迟 | 高频更新内容页 |

水合优化：延迟非关键组件水合 → 按需水合（交互后再水合）→ 选择性水合 / 岛屿架构（Astro，只水合交互组件）→ 兜底减少 SSR 页面 JS 体积。

### 2.8 落地闭环：基线、灰度、验证与 CI 门禁

**结论：优化不是改完就完——定基线、灰度、验证、门禁、告警构成防止回退的闭环。**

1. 定基线：RUM 采 P50 / P90 / P95，不看均值。
2. 定位瓶颈：LCP 查 TTFB / 图 / 阻塞资源；INP 查长任务；CLS 查无尺寸动态资源。
3. 小流量灰度，不全量上线。
4. 对比 P95 验证收益，实验室结论由现场数据闭环。
5. CI 门禁：单包 JS 超阈值阻断 MR、CWV 不达标禁止发布。
6. 看板告警：指标恶化自动告警。

### 2.9 高频坑与误区

**结论：六条坑都是「手段用错位置」——工具当真理、优化当万金油、均值当结论。**

1. Lighthouse 分高 = 体验好？实验室受控环境，模拟不了弱网与低端机，以 RUM 为准。
2. useMemo / memo 越多越好？缓存有开销，滥用反伤内存与耗时。
3. will-change 大量加？提前分配 GPU 内存，反而耗资源。
4. preload 所有资源？抢占带宽，拖慢关键资源。
5. LCP 图加懒加载？降优先级，LCP 直接变差。
6. 平均值看性能？看 P90 / P95，长尾用户才是优化重点。

## 3. 复习工具

### 3.1 快速自查清单

- CWV 三大指标阈值是否记住？LCP ≤ 2.5s、INP ≤ 200ms、CLS ≤ 0.1（p75）。
- LCP 慢：TTFB / 图片 / 阻塞 JS/CSS 哪个是瓶颈？
- INP 高：有没有大量长任务？能不能分片、Worker、懒执行？
- CLS 高：图片宽高、aspect-ratio、font-display、动态内容预留？
- 静态资源缓存策略、hash 文件名、Brotli 压缩？
- 代码分割、路由懒加载、大依赖替换？
- 关键资源 preload，非关键 prefetch？
- 动画是否走 transform + opacity 合成层？
- 有没有强制同步布局、超大 DOM、长列表无虚拟滚动？
- 线上 RUM 上报、P95 监控、CI 性能门禁？

### 3.2 面试口述框架

> 我把前端性能优化分成指标、底层原理、五大优化方向、采集监控、闭环落地：

1. **指标**：核心是 CWV——LCP 加载、INP 交互卡顿、CLS 稳定性，辅以 TTFB、TBT、长任务；区分实验室 Lighthouse 和真实 RUM，看 P95 长尾。
2. **底层**：基于浏览器渲染流水线和主线程单线程模型，优化本质是**减少网络耗时、减少 JS 解析执行、减少 Layout / Paint、避免主线程阻塞**。
3. **优化方向**：网络缓存 & CDN & 图片字体 → 打包体积分包 tree-shaking → 渲染层面减少重排重绘、虚拟滚动 → JS 长任务分片、Web Worker、防抖节流、框架减少无效渲染 → 顶层渲染模式选型（CSR / SSR / 岛屿架构，解决水合问题）。
4. **闭环**：web-vitals 采集指标，Performance 面板定位火焰图瓶颈；建立 CI 门禁 + 线上看板，持续监控防止性能回退。
