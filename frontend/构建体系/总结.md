## 1. Vite

### 1.1 双引擎：dev 不打包，build 才打包

```
dev   按 URL 返回源码，import 原样保留 → 浏览器原生 ESM 自己加载（不打包）
build 从入口全量解析依赖图 → 打包、分割、压缩
```

- 一句话概括：**dev 处理的是"被请求到的模块"，build 处理的是"整个依赖图"**。dev 引擎是 esbuild（预构建 + 单文件转换），build 引擎是 Rolldown（8.x 起，兼容 Rollup 配置）。
- dev 侧维护的是**模块图**（module graph）：一个 URL ↔ 一个模块节点，节点挂 `importers`（谁 import 我）与 `importedModules`（我 import 谁）。它解释了冷启动快、HMR 快、`optimizeDeps.exclude` 的坑、以及"源码必须是 ESM"。
- **依赖预构建**（`optimizeDeps`）：把 `node_modules` 里 CJS 的、或碎片化的包预转成单个 ESM 文件放进 `node_modules/.vite`；`include` 提前声明可避免运行期新发现依赖触发重新预构建并刷新页面。
- **环境变量**：`import.meta.env` 是**编译期静态替换**，不是运行时读取；只有 `VITE_` 前缀会暴露给客户端（`envPrefix` 可改）；不能动态拼接 key（构建期不知道 key 是什么）。
- **HMR**：服务端只重转变更模块，再通过 WebSocket 通知浏览器重新请求，更新耗时与项目规模无关；模块没有 `import.meta.hot.accept` 边界时会向上冒泡，冒泡不到就整页刷新。

### 1.2 生产配置全览（单入口）

五类配置：

| 类别 | Vite 配置 |
| --- | --- |
| 入口 | `root` + `index.html` 里的 `<script type="module">` |
| 出口 | `build.outDir` / `rollupOptions.output.*FileNames` |
| 转换 | 内置 + `@vitejs/plugin-vue`（SFC） |
| 扩展 | `plugins` |
| 优化 | `manualChunks` / `minify` |

- 一个独特的点：**Vite 的入口写在 HTML 里**——`index.html` 是构建的起点（不是产物模板），那句 `<script type="module" src="/src/main.js">` 就是 entry。
- `define` 替换的是代码文本，值必须 `JSON.stringify`；`[hash:8]` 对应产物长缓存；`minify: false` 是有意的——关掉内置压缩，交给手写的 `mini-terser`。
- **`.vue` 的编译只能靠官方插件**：Vite 内置转换不认 SFC，需 `@vitejs/plugin-vue`。所谓"生产配置全手写"针对的是**产物收尾**（HTML / 压缩 / 门禁），不是语言编译。
- 配置按阶段分四类：通用 / 仅 dev（`server.*`、`optimizeDeps.*`）/ 仅 build（`build.*`）/ SSR。最易想错两条：`server.proxy` 只在 dev 生效；`assetsInlineLimit` 属于 build。

### 1.3 钩子全貌速查

- Vite 的钩子有**两条正交的轴**：**归属**（通用即 Rollup / Rolldown 兼容，还是 Vite 专有）与**生效端**（dev / build / 两者 / preview）。判"能不能换个工具复用"看归属，判"什么时候触发"看生效端——通用钩子里 `transform` 两端都跑、`renderChunk` 只在 build 跑；专有钩子里 `transformIndexHtml` 两端都跑。主干按生效端分三类：**dev 专属**（`configureServer` / `hotUpdate`）、**build 专属**（`renderChunk` / `generateBundle` / `closeBundle`）、**两端都跑但含义不同**（`resolveId` / `load` / `transform`——dev 只处理"被请求到的模块"，build 处理整张依赖图）。
- 排序分三层且**只有中间一层跨插件**：跨钩子天然有序（`resolveId → load → transform`）；`enforce: 'pre' | 'normal' | 'post'` 跨插件排同一个钩子；`order` 排同插件同一钩子的多个 handler。官方顺序链：`alias → pre → vite core → normal → vite build → post → vite build post`。
- **钩子不触发先查 `apply`**：`apply: 'serve'` 的插件在 build 里根本不加载，断点当然打不中；表里的空行（如 `configurePreviewServer` 未被使用）也是信息。
- build 侧分工纪律：改 chunk 代码用 `renderChunk`（代码已生成、hash 未算、未写盘）；增删产物 / 改文件名 / 出清单用 `generateBundle`；改 HTML 用 `transformIndexHtml`（只有它拿得到 `ctx.bundle`）。一句话——**改代码在 `renderChunk`，动产物结构在 `generateBundle`**。

### 1.4 dev 期插件：mock API 与 HMR 观测

- 两个插件都声明 `apply: 'serve'`，build 时根本不加载——这是"Vite 的插件不止 build 侧"最直接的证据。
- **mini-mock**（`configureServer`）：直接 `server.middlewares.use()` 是立刻挂（抢在内置中间件之前）；`return () => {...}` 是交给 Vite 等内置中间件装完再调用。这个差别有后果——`/api/*` 的 404 必须放在靠前那个中间件里，否则带 `Accept: text/html` 的请求会被 Vite 的 HTML 回退先吞掉（实测 `/api/nope` 曾返回 `index.html` 200）。
- **mini-hmr**（`hotUpdate`）：`hotUpdate` 是新名，`handleHotUpdate` 仍可用。返回值决定这次更新发给谁——不返回 → Vite 自己算 HMR 边界；返回 `[]` → 吞掉这次更新、改用 `server.ws.send()` 自己通知前端；返回模块数组 → 把更新限定在这几个模块。`ctx.modules` 是"已被更早的插件过滤过"的结果：`@vitejs/plugin-vue`（走旧 `handleHotUpdate`）排在前面，会按"改了哪个块"收窄——改 `<template>` 得 1 个模块，只改块外注释得 0 个。这正是"同钩子内排在前面的人先改数据"的现实版本。

### 1.5 手写插件：虚拟模块与剔除

- **mini-virtual**：`resolveId` 认领 `virtual:build-info`、`load` 提供内容。三个关键点——虚拟 id 用 `\0` 打头（表示"不是真实路径"）；`resolveId` 返回 `null` 表示"我不处理"，交还插件链；`load` 返回的字符串就是模块源码，会像真实文件一样被后续 `transform`、被 tree-shaking。`configResolved` 里缓存 `mode`，是为了在 `load` 时内联成字面量。
- **mini-drop**：`enforce: 'pre'` 抢在内置转换之前看源码。(a) 测试 / mock 文件返回空模块 `export {}`——让文件照常进依赖图，再由 tree-shaking 把整块摇掉，而不是"删文件"（否则 import 它的那条边会变孤儿）；(b) 只对本项目 `src/` 下的文件判断，`node_modules` 一律不碰。实测清空 `main.spec.js`、`mock.js`。

### 1.6 手写插件：HTML 收尾 / 压缩 / 体积门禁

- **mini-html**：`apply: 'build'` 只在构建期加载；`transformIndexHtml` 用 `order: 'post'` 保证看到最终 HTML；`ctx.bundle` 只有构建期才有（"文件名 → 产物"的映射），所以能现读带 hash 的入口文件名与依赖。补 `modulepreload` **必须查重**——Vite 默认已注入，实测"补 0 条"；给 `<script>` 加 `nonce`。
- **mini-terser**：挂在 `renderChunk`（代码已生成、hash 未算、未写盘，正是改代码的时机）。8.x 细节：`renderChunk` 阶段拿到的是占位文件名，日志用 `chunk.name` 做标签。
- **mini-size-gate**：`generateBundle` 里按 **gzip** 称重、`emitFile` 出 `build-manifest.json`、`this.error` 超预算中断。三个设计点——量 gzip 而非 raw；产出清单而非只打印（清单进 CI 产物，可 diff）；`this.error` 让插件从"报告"变"门禁"。
- **钩子分工纪律**：改 chunk 代码用 `renderChunk`；增删产物 / 改文件名 / 出清单用 `generateBundle`；改 HTML 用 `transformIndexHtml`。一句话——**改代码在 `renderChunk`，动产物结构在 `generateBundle`**。

### 1.7 代码分割与压缩

- 走 `build.rollupOptions.output.manualChunks`。**8.x 的坑：Rolldown 下 `manualChunks` 只接受函数形式**，写成对象会报 `Invalid type: Expected Function but received Object`。
- 单入口下最自然的分割是**路由级懒加载**：路由表里写 `component: () => import('./views/Home.vue')`，`() => import()` 就是动态 `import()`，每个视图一个独立 chunk、按需加载。实测产物：`vendor.*.chunk.js`（node_modules，含 vue / vue-router）/ `index.*.js`（入口）/ `Home.*.chunk.js`、`About.*.chunk.js`（两个路由视图）/ 抽出的 CSS（含 SFC 的 `<style scoped>`）。
- CSS 由 `cssCodeSplit: true` 单独成文件——拿独立 hash、单独命中缓存，随 HTML 并行加载无 FOUC。
- 压缩由手写 `mini-terser` 完成（配置里 `minify: false`），读数完全来自我们的插件。

### 1.8 三个命令与预览

- 三个命令共用同一份配置：`npm run dev`（dev server，端口 5182）、`npm run build`（写盘 `dist/`）、`npm run preview`（先 build 再 `vite preview`，端口 5181）。不需要第二份配置文件——`build.*` 只在构建期生效，dev 插件用 `apply: 'serve'` 把自己挡在 build 之外，`mini-html` / `mini-drop` 用 `apply: 'build'` 反向挡住 dev。第十节的 `mini-vite` 是**独立项目**（`code/mini-vite/`），命令不在 vite-lab 里。
- **`vite preview` 不是 dev server**：没有 HMR、不做任何转换，是纯静态服务，服务的正是 `build` 写盘的 `dist/`——"预览到的"与"要上线的"是同一批文件。

### 1.9 断点调试

- 断点直接打在 `plugins/*.mjs`、`vite.config.mjs` 里就能命中——它们是我们自己的源码，不在 `node_modules`。
- 入口问题靠 `launch.json`：`runtimeExecutable: "npm"` + `runtimeArgs: ["run", "build"]`，改脚本不用改 `launch.json`。
- 别用 `node_modules/.bin/vite` 启动调试（Windows 下 `vite.cmd` 多包一层批处理，`--inspect-brk` 传不到 node）；要命令行调试就直指 `node_modules/vite/bin/vite.js`。若以仓库根为工作区打开 VS Code，嵌套的 `.vscode/launch.json` 不生效。

### 1.10 手写 mini-vite

- `mini-vite`（**独立项目**，唯一依赖 `acorn`）收敛成**单 build 引擎**：从入口全量建图、拓扑排序后拼成一个文件——定位是「一次构建、一个产物」的最小可跑模型。文件按概念拆进 `lib/`：`hook.mjs`（三种调用约定 `call` / `first` / `pipe`）、`plugin-container.mjs`（`config` → `apply` 过滤 → `enforce`/`order` 排序 → 注册 → 分发）、`resolve.mjs` / `module-graph.mjs` / `transform.mjs` / `build.mjs` / `emit.mjs`。
- 排序只在容器一处：主键 `enforce`（跨插件）、次键 `order`（同钩子内）、末键注册顺序；`apply: 'serve' | 'build'` 决定插件进哪一端的插件表。
- 实测：从入口全量建图，6 个模块（4 个磁盘文件 + 裸导入占位 `\0deps:tiny-lib` + 虚拟模块 `\0virtual:build-info`）按拓扑序拼成一个文件；钩子触发次数表为 build 单列——`resolveId` 5 次、`load` / `transform` 各 6 次，`renderChunk` / `generateBundle` / `closeBundle` / `transformIndexHtml` 各 1 次。
- Vite 真身叠加的是内置插件链、HMR 的 accept 边界、依赖预构建的缓存、以及 Rolldown 生产引擎——**机制没变，只是把每一步做重、做对、做成可插拔**。

## 2. Rollup

### 2.1 ESM 优先

```
CJS：  const a = require(condition ? 'x' : 'y')   ← 构建期不知道依赖谁
ESM：  import a from 'x'                          ← 构建期静态可见
```

- CJS 的 `require` 是运行时函数调用，依赖关系只有执行到那一行才知道；ESM 的 `import` 是静态声明，**不执行代码就能得到完整依赖图**。三点收益：精确 tree-shaking、作用域提升（把模块展平到同一作用域，产物无模块加载运行时）、按引用关系重命名。
- 打包器对比：为兼容 CJS 与动态依赖，有的产物里必须带一套模块运行时；Rollup 打同样的代码，产物就是"模块体拼在一起"（本 lab 的 `dist/index.mjs` 里没有模块运行时注入）。
- 代价：**CJS 要靠插件**（`@rollup/plugin-commonjs`），遇到动态 `require` 就无能为力。

### 2.2 生产配置全览（库打包）

| | 应用打包（Vite） | 库打包（Rollup） |
| --- | --- | --- |
| 依赖怎么处理 | 全打进来 | 使用方一定也有的依赖 `external` 掉 |
| 产物格式 | 一种（给浏览器） | 多份（esm 给打包器、cjs 给 Node） |
| 产物体积 | 压缩 + 分割 + hash 长缓存 | 越小越好，且要能被打包器二次 tree-shaking |
| 门禁 | 首屏体积 | 库体积 + 禁用 API + 依赖图 |

- 五类配置：`input` / `output`（**数组**：多格式）/ `plugins`（Rollup 没有内置转换，全靠插件）/ `external` + `treeshake`。
- 三个要点：**`output` 是数组**（一次构建出多份格式）；**`external` 是库打包第一原则**（忘了它 `react` 会被打进产物）；**`treeshake.moduleSideEffects` 是"给使用方的承诺"**，等价于 `package.json` 的 `"sideEffects": false`。
- 两个命令：`npm run build` / `npm run mini:cjs`；**没有 preview**——库产物不是给人打开看的页面，验收方式是读产物、跑单测、使用方试装。

### 2.3 tree-shaking：摇掉了什么，留下了什么

- 未被引用的导出被删（`unusedHelper` 消失）；顶层副作用被保留（`globalThis.__metaLoaded = true` 还在）——Rollup 不敢删，因为它不知道你是不是故意的。
- **tree-shaking 细到对象字面量的属性级**：虚拟模块注入的 `BUILD_INFO` 里没人访问的 `name` 属性被删。
- 一条必须记住的区分：**`moduleSideEffects: false` ≠ 模块内副作用语句可删**。它说的是"模块没被引用时可以整块删掉"，不是"模块内部有副作用的语句可以删"；已在依赖图里的模块，里面的副作用语句照样保留。精确控制要用函数给确定的模块开白名单，而不是全局 `false`。
- 与「标记 + 删除」两步的工具对比：Rollup 一步完成（解析期就删）；两步式的工具要「`sideEffects` 声明 + 开启压缩」才删得掉——只声明 `sideEffects: false` 不删代码。

### 2.4 手写插件：虚拟模块与禁用 API 门禁

- **mini-virtual**：`resolveId` 认领说明符、`load` 提供内容；虚拟 id 用 `\0` 打头；`resolveId` 返回 `null` 表示"我不处理"；`load` 返回的字符串就是模块源码，会被后续 `transform`、会被 tree-shaking。真实用途：构建期注入版本号 / git commit / 特性开关。
- **ban-api**：把团队约定（禁直连 `localStorage` / 禁 `console.log`）做成构建期报错——**规则数据化 + AST 判定**（正则扫得到关键字，扫不到"是调用还是字符串字面量"）；`warn` / `error` 双档（`fail: false` 是"报告"，`fail: true` 是"门禁"，CI 非零退出码靠它）。注意 `this.error` 抛出即停，想一次报全要在 `transform` 里只收集、到 `buildEnd` 再统一 `this.error`。

### 2.5 手写插件：CJS 替身与体积门禁

- **mini-commonjs**：Rollup 只认 ESM，一个 CJS 文件在它眼里就是"给一个叫 `module` 的变量赋值"。插件在 `transform` 阶段把 `module.exports =` 改写成 `export default`（或把 `exports.x =` 改写成 `export const x =`）。真实插件还要处理动态 `require`、混合导出、条件导出与 interop 包装。
- **size-gate**：`generateBundle` 里按 **gzip** 称重、`emitFile` 出 `bundle-manifest.json`、`this.error` 超预算中断。四个设计点——量 gzip 而非 raw；产出清单而非只打印；阈值按 chunk 而非总量（总量会被"新增一个文件"骗过去）；**只挂在一个 output 上**（output 钩子每个 output 各跑一次，挂顶层会让 esm 与 cjs 各出一份清单互相覆盖）。

### 2.6 external 与多格式产物

- `external: ['react']` 一行决定"打不打进来"：esm 产物第一行直接透传 `export { useState } from 'react'`；cjs 产物换成 `require`。**忘记 external 的代价是双份依赖**——体积翻倍只是最小的损失，更严重的是使用方的 `react` 与库里的 `react` 是两个实例，hooks 直接报错、`instanceof` 静默失效。判断标准：**使用方也可能用到的东西就该 external**。
- `output` 传数组，一次构建出多份，差异只在"包裹层"：`es`（最小，**只有它能被使用方二次 tree-shaking**）/ `cjs` / `umd`（最大）/ `iife` / `system`。**UMD / IIFE 必须配 `output.globals`**，否则产物里 `React` 是未定义变量，用户一打开就是白屏。
- `package.json` 入口字段：`main` → cjs、`module` → esm、`exports` 条件导出（推荐）。`exports: 'named'` 让 cjs 产物用 `Object.defineProperty(exports, ...)` 而非覆盖整个对象，这样 Node 的 `cjs-module-lexer` 才能静态识别命名导出。
- 与 Vite 的关系：Vite 的生产构建走的就是 Rollup 这一套（8.x 起是 Rolldown，配置兼容），所以 `external` / `output` / `manualChunks` 在 `build.rollupOptions` 里直接通用；反过来 `config` / `configResolved` / `configureServer` / `transformIndexHtml` / `optimizeDeps` 是 Vite 独有。跨工具复用的统一外壳是 unplugin。

### 2.7 CJS 互操作

- Rollup 眼里 CJS 的 `module.exports` 就是一行普通赋值语句——不加插件时，入口 `import pkg from './dep.cjs'` 会报 `"default" is not exported by dep.cjs`。
- `mini-commonjs` 二十行替身做的事就是"把赋值改写成导出"（`module.exports =` → `export default`），使用方这才 import 得到。
- 真实插件（`@rollup/plugin-commonjs`）还要处理动态 `require`、混合导出、条件导出，以及最麻烦的 **interop**——CJS 的 `module.exports` 对应到 ESM 到底是 `default` 还是命名空间，取决于使用方怎么导入，只能生成包装函数在运行时判断（产物里的 `_interopDefault` / `__toESM` 就是这么来的）。
- 判断一个依赖"能不能不打插件直接用"：看它的 `package.json`——有 `module` 或 `exports.import` 字段的走 ESM 分支；只有 `main` 且是 CJS 的必须过插件。

### 2.8 断点调试

- 断点直接打在 `plugins/*.mjs`、`rollup.config.mjs` 里就能命中——它们是我们自己的源码，不在 `node_modules`。
- 入口问题靠 `launch.json`：`runtimeExecutable: "npm"` + `runtimeArgs: ["run", "build"]`，改脚本不用改 `launch.json`。
- 一个 Rollup 特有的注意点：`generateBundle` 里的断点**会因 `output` 数组被执行两次**（esm 一次、cjs 一次）——这正是 `sizeGate` 只挂在一个 output 上的原因。
- 别用 `node_modules/.bin/rollup` 启动调试（Windows 下 `rollup.cmd` 吞 `--inspect-brk`）；若以仓库根为工作区打开 VS Code，嵌套的 `.vscode/launch.json` 不生效。
