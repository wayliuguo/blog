# 性能优化实践

web 性能是网站或应用程序的**客观度量**与**可感知的用户体验**的统一。优化实践的最终目标不是单纯地把某个数字压下去，而是让用户在"加载更快、交互更顺、视觉更稳"的体验中获得价值。本文从加载性能、运行时性能、代码分割、缓存、布局与渲染、长列表、资源提示等维度，系统梳理一套可落地的前端性能优化实践。

> 级别：中级→高级

按本书四层推进：

- **入门使用**：把性能优化按载荷、加载、渲染、交互、缓存等维度做一次系统梳理；
- **进阶**：理解懒加载、虚拟滚动、代码分割、资源提示等方案背后的浏览器渲染原理（诸如"为什么少回流重绘、少占用主线程能更流畅"）；
- **实战**：结合 `01-性能指标与评估` 用指标驱动优化，让每次改动都有数据判据；
- **最小实现掌握原理**：到 `code/frontend/09-performance` 运行懒加载与 FPS/主线程卡顿对比 demo，直观印证"按需加载、别阻塞主线程"。

## 性能优化的基本流程

性能优化不是靠直觉拍脑袋，而应遵循一套可量化、可迭代的流程：

1. **明确指标**：先搞清楚"多快才算快"，用统一的核心指标（如 Web Vitals、RAIL）作为优化目标。
2. **量化评估**：使用 Lighthouse、Performance、WebPageTest 等专业工具，将网站性能数字化。
3. **定位原因**：立足页面响应的生命周期（从输入 URL 到渲染完成），分析造成性能瓶颈的具体环节。
4. **实施优化**：开展技术改造、可行性分析，针对瓶颈做定向优化。
5. **迭代优化**：线上持续监控，回归验证优化效果，并不断迭代。

所谓"性能"通常包含几个层面：

- **减少整体加载时间**：减小文件体积、减少 HTTP 请求、使用预加载。
- **使网站尽快可用**：仅加载首屏内容，其余按需懒加载。
- **平滑与交互性**：用 CSS 替代 JS 动画、减少 UI 重绘。
- **感知表现**：用户可能无法体验得更快，但可以让他们"感觉"更快——耗时操作用加载动画、进度条、骨架屏等提示信息给出反馈。
- **性能测定**：通过指标、测试、监控持续优化。

## 加载性能

### 懒加载（Lazy Loading）

懒加载的核心思想是**按需加载**：首屏内容立即渲染，滚动进入可视区的内容才去加载真实资源。最典型的场景是图片懒加载。

常见实现有两种方式：

- **基于滚动事件 + getBoundingClientRect**：兼容性好，滚动时检测元素是否进入可视区。
- **IntersectionObserver**：性能更优，无需监听滚动，但兼容性较差。

以 Vue 中手动实现一个图片懒加载插件为例，整体思路是封装一个 `lazy` 指令，元素绑定指令时注册一个监听器，滚动时检测该元素是否位于可视区，若在可视区则替换 `src` 加载真实图片。

```js
// 入口：注册 lazy 指令，真正的能力由 LazyClass 提供
const VueLazyLoad = {
    install(Vue, options) {
        const LazyClass = lazy(Vue)
        const instance = new LazyClass(options)
        Vue.directive('lazy', {
            bind: instance.add.bind(instance),
            unbind: instance.remove.bind(instance)
        })
    }
}
```

```js
// LazyClass：收集元素监听器、绑定滚动事件、分发加载逻辑
const lazy = Vue => {
    return class LazyClass {
        constructor(options) {
            this.options = options
            this.bindHandler = false
            this.listeners = []
        }
        add(el, bindings) {
            Vue.nextTick(() => {
                // 寻找可滚动的父元素
                let ele = scrollParent(el)
                // 1. 记录需要监听的元素
                let listener = new ReactiveListener({
                    el,
                    src: bindings.value,
                    options: this.options
                })
                this.listeners.push(listener)
                // 2. 绑定滚动事件（只需绑定一次）
                // 也可使用 IntersectionObserver（兼容性不好）
                if (!this.bindHandler) {
                    // 节流降低触发频率
                    let lazyHandler = throttle(this.lazyLoadHandler.bind(this), 500)
                    ele.addEventListener('scroll', lazyHandler, { passive: true })
                    this.bindHandler = true
                }
                // 默认不滚动也需检测一次当前可视内容
                this.lazyLoadHandler()
            })
        }
        lazyLoadHandler() {
            // 找出在可视区内且尚未加载的元素，触发加载
            this.listeners.forEach(listener => {
                if (listener.state.loading) return
                listener.checkInView() && listener.load()
            })
        }
        remove() {}
    }
}
```

监听器 `ReactiveListener` 负责两个动作：

- `checkInView`：通过 `getBoundingClientRect` 判断元素到视口顶部的距离是否小于视口高度（乘以 `preload` 预加载系数），从而判断是否已在可视区。
- `load`：先显示 loading 占位图，再异步加载真实图片，成功显示加载结果，失败显示错误占位。

```js
// 监听器：检测是否进入可视区并执行加载
class ReactiveListener {
    constructor({ el, src, options }) {
        this.el = el
        this.src = src
        this.options = options
        this.state = { loading: false }
    }
    checkInView() {
        let { top } = this.el.getBoundingClientRect()
        return top < window.innerHeight * this.options.preload
    }
    load() {
        render(this, 'loading')          // 先展示 loading
        loadImg(
            this.src,
            () => { this.state.loading = true; render(this, 'loaded') },
            () => { render(this, 'error') }
        )
    }
}
```

配套的辅助函数：

```js
// 找到可滚动的父级元素
const scrollParent = el => {
    let parent = el.parentNode
    while (parent) {
        if (/scroll/.test(getComputedStyle(parent)['overflow'])) return parent
        parent = parent.parentNode
    }
}

// 根据状态切换 src
const render = (listener, status) => {
    const srcMap = {
        loading: listener.options.loading,
        loaded: listener.src,
        error: listener.options.error
    }
    listener.el.setAttribute('src', srcMap[status])
}

// 加载图片
const loadImg = (src, resolve, reject) => {
    const img = new Image()
    img.src = src
    img.onload = resolve
    img.onerror = reject
}
```

使用时只需注册插件并在 `img` 标签上写 `v-lazy` 指令即可：

```js
import VueLazyLoad from './plugins/vue-lazyload'
Vue.use(VueLazyLoad, {
    loading: logo,   // 加载占位图
    preload: 1.2      // 预加载系数，提前加载
})
```

```html
<div class="box">
  <li v-for="(item, index) in list" :key="index">
    <img v-lazy="item" alt="">
  </li>
</div>
```

### 图片优化

图片通常是页面体积的大头，优化手段包括：

- **减少不必要的图片**：能用 CSS 样式实现的（如纯色背景、渐变、圆角图标）就不要用图片。
- **选择合适的格式**：小图标用 SVG 字体图标或雪碧图；照片类用 JPEG/WebP。接入 WebP 时可根据请求头 `Accept` 判断浏览器是否支持，主流 CDN 厂商（如阿里云图像处理）都支持 WebP 格式转换。
- **压缩与规格控制**：压缩项目静态图片、限制上传图片大小、按需引入不同尺寸的图片。
- **雪碧图（CSS Sprites）**：合并多个小图标减少请求数；但在 HTTP/2 及以上协议下建议不再使用（多路复用已降低请求开销）。
- **Base64 内联**：小图片可转 Base64 减少请求，但体积过大的图片转 Base64 后体积反而更大，且会增大 JS 体积，需谨慎权衡。

### 文件上传性能

上传本身也会影响用户体验（尤其大文件），可从单文件上传、进度管控、切片合并三个方向优化。

**单文件上传**：通过 `<input type="file">` 的 `change` 事件拿到文件对象，用 `FormData` + `append` 组织表单数据传递给服务器。

```js
let formData = new FormData()
formData.append('file', _file)
formData.append('filename', _file.name)
instance.post('/upload_single', formData).then(data => {
    if (+data.code === 0) {
        alert(`文件上传成功，可基于 ${data.servicePath} 访问`)
    }
})
```

**进度管控**：利用 axios 的 `onUploadProgress` 回调（底层是 `xhr.upload.onprogress`）获取已上传的 `loaded` 与总量 `total`，动态更新进度条宽度，给用户及时的进度反馈。

```js
data = await instance.post('/upload_single', formData, {
    onUploadProgress(ev) {
        let { loaded, total } = ev
        upload_progress_value.style.width = `${loaded / total * 100}%`
    }
})
```

**大文件切片上传 + 合并切片**：将大文件切成多个分片，逐个上传，全部上传完成后通知服务器合并。这里配套了三个接口：上传切片 `/upload_chunk`、合并切片 `/upload_merge`、获取已上传切片 `/upload_already`（用于断点续传，已上传的切片直接跳过）。

```js
// 通过 FileReader + SparkMD5 生成文件 HASH，实现断点续传与合并依据
const changeBuffer = file => new Promise(resolve => {
    const fileReader = new FileReader()
    fileReader.readAsArrayBuffer(file)
    fileReader.onload = ev => {
        const buffer = ev.target.result
        const spark = new SparkMD5.ArrayBuffer()
        spark.append(buffer)
        const HASH = spark.end()
        const suffix = /\.([a-zA-Z0-9]+)$/.exec(file.name)[1]
        resolve({ buffer, HASH, suffix, filename: `${HASH}.${suffix}` })
    }
})

// 文件切片：固定大小，最多 100 片
const max = 1024 * 100
let count = Math.ceil(file.size / max)
if (count > 100) {
    count = 100
}
const chunks = []
for (let index = 0; index < count; index++) {
    chunks.push({
        file: file.slice(index * max, (index + 1) * max),
        filename: `${HASH}_${index + 1}.${suffix}`
    })
}

// 逐片上传，全部成功后合并
let uploaded = 0
const complate = async () => {
    uploaded++
    upload_progress_value.style.width = `${uploaded / count * 100}%`
    if (uploaded < count) return
    // 所有切片上传成功，通知服务器合并
    data = await instance.post('/upload_merge', { HASH, count }, {
        headers: { 'Content-Type': 'application/x-www-form-urlencoded' }
    })
}
chunks.forEach(chunk => {
    // 已上传的切片跳过，实现断点续传
    if (already.length > 0 && already.includes(chunk.filename)) { complate(); return }
    const fm = new FormData()
    fm.append('file', chunk.file)
    fm.append('filename', chunk.filename)
    instance.post('/upload_chunk', fm).then(data1 => {
        if (+data1.code === 0) complate()
    })
})
```

> 切片上传把一个大请求拆成多个小并发请求，可通过控制并发数避免阻塞主网络层，也天然支持"失败重传单个分片"的可靠性优化。

## 运行时性能

运行时性能主要关注**操作响应速度**与**页面流畅度**，常见瓶颈是主线程被长任务长期占用（超过 50ms 即视为长任务），导致用户交互无响应、页面掉帧。

### 操作响应速度

影响操作响应速度的因素主要有两点：

- **操作后执行时间过长**：用户等待时间长，此时应给加载/进度反馈（符合 RAIL 模型的响应原则，感知延迟 100ms 内给出反馈）。
- **主线程被占用**：有任务正在执行，需等待主线程空闲。可通过"把任务拆分成 < 50ms 的片段"来释放线程响应交互，也符合 **RAIL 空闲（Idle）** 原则。

优化手段：

- 首次加载只执行首屏所需代码，其余按需加载。
- 优化代码执行时间，降低单次操作的复杂度。

### 页面流畅度

掉帧通常由以下原因引起：

- **JS 执行时间过长**：阻塞渲染线程。
- **回流（Reflow）与重绘（Repaint）过多**：频繁触发布局重排。
- **资源加载阻塞**：阻塞主文档渲染。

可用 **rAF（requestAnimationFrame）** 配合 **IntersectionObserver/scroll 监听** 将高耗时逻辑错峰到空闲帧执行；复杂任务用 **Web Worker** 移出主线程。动画尽量用 CSS `transform`/`opacity`（走合成器，不触发重排重绘）代替 JS 操作 `width`/`left` 等布局属性。

### 内存管理与泄漏

内存占用过高会导致运行卡顿甚至浏览器崩溃，常见的内存泄漏源：

- 全局变量占用的内存持续增长。
- 闭包持有外部的引用未被释放。
- 定时器未清除。
- 循环引用。
- DOM 删除时未解绑事件。
- 未清理的 DOM 元素引用。

优化原则：**及时销毁不再使用的对象**，防止旧对象不被销毁、新对象又不断生成导致内存持续增长。

### 感知性能与交互体验

用户对"快"的感知不仅来自真实耗时，也来自体验设计：

- **及时反馈**：耗时操作用 loading、进度条、骨架屏提示。
- **符合用户习惯**：操作路径符合直觉，减少等待焦虑。
- **预判加载**：鼠标 hover 或即将进入视区前，提前预加载目标资源。

## 代码分割

代码分割的核心思想是**避免把所有代码打包进一个文件**，从而减小首屏响应体积。

- **Code Splitting**：将代码按路由、按组件、按功能拆分成多个 chunk，按需加载。
- **Tree Shaking**：删除未引用的代码（副作用纯净的 ES Module 模块可被摇树优化）。
- **组件按需加载 / 路由懒加载**：进入某个路由或渲染某个组件时才加载对应代码。
- **第三方库按需引入**：如 lodash、UI 库等，仅引入用到的部分。

在 Webpack 中落地主要依赖：

```js
// 路由级别的懒加载（借助动态 import）
const router = [
  {
    path: '/detail',
    // 访问该路由时才加载对应模块，减少首屏体积
    component: () => import('@/views/Detail.vue')
  }
]
```

### Vue 中的优化实践

在 Vue 项目中，除代码分割外还有丰富的运行时优化手段：

- 合理使用 `watch` 与 `computed`（`computed` 有缓存）。
- 使用**异步组件**，避免一次性加载过多组件。
- 使用 `keep-alive` 缓存组件，避免重复渲染与加载。
- 路由懒加载。
- 利用状态管理（Vuex/Pinia）缓存数据。
- 合理使用 `mixins` 抽离公共代码。
- `v-for` 不要和 `v-if` 同时使用；`v-for` 不要用 `index` 做 `key`（配合数据变更会导致错误复用与性能浪费）。
- 避免使用 `v-html`（有安全风险且性能较差），用 `v-pre`/`v-once` 减少不必要的更新。

## 缓存策略

缓存是减少重复请求、提升加载速度最有效的手段之一。

### 强缓存与协商缓存

浏览器加载资源时优先命中缓存：

- **强缓存**：`Expires`、`Cache-Control`——命中后不发请求直接使用本地副本。
- **协商缓存**：`Last-Modified` / `If-Modified-Since`、`ETag` / `If-None-Match`——需与服务器验证，命中则返回 304，不重新下载。

相关细节可参考 HTTP 缓存的专项使用方式（强缓存与协商缓存的字段、优先级、更新策略等）。

### 服务端代理缓存与 CDN

- **浏览器缓存 + Nginx 代理层缓存**：缓存静态资源文件。
- **CDN 加速**：内容分发网络（CDN）是一组分布在多个物理位置的 Web 服务器。服务器离用户越远延迟越高，CDN 通过在多个位置部署服务器缩短物理距离，从而缩短响应时间。同时利用 CDN 增加并发连接与长缓存优势加速下载。
- **合理设置资源缓存有效期**：对于带 hash 的静态资源可使用长缓存；对易变资源使用较短的缓存。

## 资源响应速度优化

- **使用 CDN 加速**：增加并发连接与长缓存优势，加速静态资源下载。
- **开启 gzip 压缩**：减小资源体积。可在打包层（Webpack）预生成 `.gz`，也可在服务器（Nginx）开启 `gzip`。

```js
// 打包时用 CompressionWebpackPlugin 生成 gzip 文件
if (process.env.NODE_ENV === 'production') {
    plugins.push(new CompressionWebpackPlugin({
        filename: '[path].gz[query]',
        algorithm: 'gzip',
        test: new RegExp(`\\.(${productionGzipExtensions.join('|')})$`),
        threshold: 10240,     // 超过 10KB 才压缩
        minRatio: 0.8,
        deleteOriginalAssets: false
    }))
}
```

```nginx
# Nginx 开启 gzip
gzip on;
gzip_static on;
gzip_min_length 1k;
gzip_buffers 4 16k;
gzip_comp_level 2;
gzip_types text/plain application/javascript application/x-javascript text/css application/xml text/javascript application/x-httpd-php application/vnd.ms-fontobject font/ttf font/opentype font/x-woff image/png image/jpeg image/svg+xml image/gif;
gzip_vary off;
gzip_disable "MSIE [1-6].";
```

- **减少网络请求次数与体积**：压缩文件、合并小文件，但需与拆分（首屏体积）找到合理平衡点；清理多余 JS/CSS 代码；合理使用 Webpack 打包策略拆包。
- **升级 HTTP 协议**：HTTP/2 多路复用、头部压缩等特性可显著提升加载效率（升级后不建议继续使用雪碧图）。

## 资源体积优化

- **文本资源（HTML/CSS/JS）**
  - 代码压缩（minify）。
  - 内容级压缩（gzip/brotli）。
  - 代码精简与无效代码清理。
  - **JS 体积**：Tree Shaking、Code Split、组件按需加载、代码按需打包。
  - **CSS 体积**：第三方库样式按需引入、减少不必要的 CSS 前缀补全。
- **图片资源**
  - 去掉不必要的图片，能用样式实现的不用图片。
  - 雪碧图（HTTP/2 及以上不需要）。
  - 上传图片大小限制与压缩。
  - 接入 WebP 格式处理。

### 代码质量

良好的代码质量本身也是性能优化的组成部分：

- **代码量**：用简洁清晰的代码（善用 lodash、正则、位运算、ES6 语法）、去除无效代码；抽离并封装公共函数与公共组件；CSS 近似原子化，让每行样式物尽其用。
- **代码复杂度**
  - 时间复杂度（增加 JS 解析时间）：减少嵌套循环，用空间换时间，使用高性能算法。
  - 空间复杂度（内存占用过大可能引起浏览器崩溃）：减少全局变量，注意销毁无用对象防止内存溢出。
- **代码结构设计**：组件懒加载、虚拟列表（virtual-list）、图片懒加载。

## 布局与渲染性能

### 关键渲染路径

浏览器处理资源到最终像素遵循关键渲染路径，优化它的每一环都能带来收益：

1. 解析文档，构建 **DOM 树**。
2. 下载资源，构建 **CSSOM 树**。
3. 将 DOM 与 CSSOM 合并为 **渲染树**（只包含可见节点）。
4. **布局（Layout）**：计算节点在视口中的位置与大小，输出"盒模型"。
5. **绘制（Paint）**：将节点绘制方式转换为屏幕上的实际像素。

渲染优化的要点：

- **CSS 放 `<head>`**：页面渲染出时 CSS 已就绪，样式按预期展示，避免 FOUC。
- **JS 放 DOM 底部**：JS 会阻塞 DOM 构建；若脚本无需操作 DOM，可用 `async` / `defer` 异步加载，避免阻塞首屏渲染。
- **减少回流与重绘**：合并 DOM 操作、用 CSS 类切换代替频繁改样式、离线修改再上屏、动画使用 `transform`/`opacity`。
- **为高构图预留空间，降低 CLS**：布局位移常由异步加载资源或动态插入 DOM 导致，可用固定尺寸占位符（骨架屏）保持布局稳定。

### 资源加载顺序

图片、音频、视频不会阻塞首次渲染，而 JavaScript、首次请求的 HTML、CSS 会阻塞首次渲染（构建 DOM/CSSOM 必需）。因此：

- 将 `async`/`defer` 的脚本延后或异步执行。
- 让首屏必需资源优先下载，非必需资源根据情况懒加载或异步加载。

## 长列表与虚拟滚动

面对几千上万条数据的列表，一次性渲染全部 DOM 会导致初始化白屏、滚动卡顿、内存暴涨。**虚拟滚动（Virtual Scrolling）** 只渲染可视区附近的少量元素，用"占位撑高 + 定位偏移"模拟完整滚动条，是长列表渲染的事实标准方案。

### 实现思路

虚拟滚动主要有两种实现思路：

1. **定位 + translate3d**：固定展示个数，用一个 `scroll-list` 渲染区用 `translate3d` 偏移标识滚动位置，外层用总高度撑出滚动条。
2. **上下 padding 占位**：用上下 `padding` 撑起完整数据高度，真正渲染的只有可视区附近的 DOM。

### 定位 + translate3d 实现（固定高度）

核心依赖三个值：`items`（数据）、`size`（元素高度）、`remain`（可视展示个数）。`scroll-bar` 高度 = 数据总数 × 高度，用于撑出滚动条；`scroll-list` 通过 `translate3d` 跟随滚动偏移。

```html
<div class="vl">
  <div class="scroll-bar"></div>
  <div class="scroll-list">
    <div v-for="..."></div>
  </div>
</div>
```

```js
// 展示区域范围、偏移量、前后缓冲
const state = reactive({ start: 0, end: props.remain })
const offset = ref(0)

// 前置/后置缓冲数量：保证快速滚动时不白屏（多渲染上下两屏）
const prev = computed(() => Math.min(state.start, props.remain))
const next = computed(() => Math.min(props.remain, props.items.length - state.end))
const visibleData = computed(() =>
    props.items.slice(state.start - prev.value, state.end + next.value)
)

const handleScroll = throttle(() => {
    const scrollTop = wrapperRef.value.scrollTop
    state.start = Math.floor(scrollTop / props.size)        // 滚动过的数据个数
    state.end = state.start + props.remain                  // 当前结束下标
    offset.value = state.start * props.size - props.size * prev.value
}, 17)

const initWrapper = () => {
    wrapperRef.value.style.height = `${props.remain * props.size}px`
    barRef.value.style.height = `${props.items.length * props.size}px`
}
```

### padding 实现（固定高度）

通过 `getPadFront`（预估高度 × 开始下标）与 `getPadBehind`（剩余数据长度 × 预估高度）设置上下 padding 撑起总高度，配合滚动偏移计算可视范围。滚动时根据 `overs = Math.floor(scrollTop / estimateSize)` 判断向上（FRONT）/向下（BEHIND）滚动，结合缓冲区内逻辑复用或重建可视区。

```js
function getPadFront()  { return param.estimateSize * range.start }
function getPadBehind() {
    const lastIndex = param.uniqueIds.length - 1
    return (lastIndex - range.end) * param.estimateSize
}

function checkRange(start, end) {
    // 数据不足则取全部数据；否则保证可视个数完整
    if (total < keeps) { start = 0; end = total - 1 }
    else if (end - start < keeps - 1) start = end - keeps + 1
    updateRange(start, end)
}

function handleScroll(offset) {
    // 通过滚动偏移差值判断方向
    const direction = offset < offsetValue ? 'FRONT' : 'BEHIND'
    offsetValue = offset
    direction === 'FRONT' ? handleFront() : handleBehind()
}
```

### 动态高度

当元素高度不固定时，固定高度估算会导致滚动位置漂移。优化方法是**在元素渲染完成后收集其高度**，记录 `id → height` 映射：

- 初始记录第一个元素高度为固定高度，若后续发现有高度变化则切换为**动态高度模式**。
- 动态模式下，用已渲染元素高度计算**平均高度**来撑开滚动条，上 padding 用已收集的高度累加（`getIndexOffSet`）。
- 计算滑动个数时，动态高度用**二分查找**在排序好的高度累计区间中定位最近下标。

```js
// 元素渲染后回调独有高度，用于动态高度模式
const saveSize = (id, size) => {
    sizes.set(id, size)
    if (calcType === CALC_TYPE.INIT) {
        fixedSizeVal = size
        calcType = CALC_TYPE.FIXED
    } else if (calcType === CALC_TYPE.FIXED && fixedSizeVal !== size) {
        calcType = CALC_TYPE.DYNAMIC   // 高度发生变化，进入动态模式
        fixedSizeVal = 0
    }
    // 动态模式：根据已加载数据计算平均高度撑开滚动条
    if (calcType === CALC_TYPE.DYNAMIC && sizes.size < Math.min(param.keeps, param.uniqueIds.length)) {
        firstRangeAvg = Math.round([...sizes.values()].reduce((a, v) => a + v, 0) / sizes.size)
    }
}
```

```js
// 上 padding：固定高度直接相乘；动态高度累加已收集高度
function getPadFront() {
    if (isFixed()) return getEstimateSize() * range.start
    return getIndexOffSet(range.start)   // 动态模式精确累加
}
```

虚拟滚动总结：核心是"**用占位模拟总量，只渲染可视区**"，优劣权衡在于固定高度实现简单高效、动态高度更精准但需收集高度映射，实际项目按数据特征选择。

## 资源提示（Resource Hints）

通过资源提示可以提前告知浏览器"接下来可能需要什么资源"，让它更早地发起请求或建立连接，从而缩短关键路径：

- **`preload`**：提前加载本页即将使用的关键资源（字体、图片、脚本）。
- **`prefetch`**：提前获取后续导航可能需要的资源（低优先级，闲时加载）。
- **`preconnect`** / **`dns-prefetch`**：提前建立与第三方域名的连接 / 解析 DNS，缩短跨域请求耗时。

```html
<link rel="preload" href="/fonts/icon.woff2" as="font" type="font/woff2" crossorigin>
<link rel="preconnect" href="https://fonts.googleapis.com">
```

## 性能指标速查

### 核心指标

| 指标 | 含义 | 阈值（绿/中/红） |
| --- | --- | --- |
| FCP | 首次内容绘制 | 0-2s / 2-4s / >4s |
| LCP | 最大内容绘制 | 0-2s / 2-4s / >4s |
| FID | 首次输入延迟 | 0-100ms（目标 <100ms） |
| TTI | 完全可交互 | 0-3.8s / 3.8-7.3s / >7.3s |
| TBT | 总阻塞时间 | 0-300ms / 300-600ms / >600ms |
| CLS | 累计布局偏移 | 0-0.1 / 0.1-0.25 / >0.25 |

## 总结

性能优化是一个"指标驱动 → 定位瓶颈 → 定向优化 → 监控回归"的持续过程。把本文的实践按载荷（体积/请求）、加载（懒加载/虚拟滚动/资源提示）、渲染（关键路径/回流重绘）、交互（长任务/感知反馈）、缓存（强缓存/协商缓存/CDN）等维度组合使用，并始终以 LCP、FID、CLS 等用户体验指标作为判据，才能让优化既"看得见数字提升"也"感受得到体验变好"。
