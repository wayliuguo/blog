> 级别：中级→高级

按本书四层推进：

- **实战**：结合 `02-性能优化实践` 把"测得慢"落到具体优化手段，形成"先测量、再优化、后回归"的闭环；

前端性能是用户体验的核心组成部分。要优化性能，首先必须学会"测量"——用统一的指标衡量页面在加载、交互、渲染等各个阶段的表现。本文系统梳理 Web 性能的核心指标、常见辅助指标、评估工具，以及如何将这些指标落地到测量与上报流程中。

## 核心 Web 指标（Core Web Vitals）

Core Web Vitals 是 Google 推出的、直接关系到用户体验的一组核心指标，它们覆盖了加载体验、交互体验和视觉稳定性三个维度。Google 将其作为搜索排名中页面体验方面的重要参考。

| 维度 | 指标 | 全称 |
| --- | --- | --- |
| 加载 | LCP | 最大内容绘制 |
| 交互 | INP（原 FID） | 首次输入延迟 / 交互到下一次绘制 |
| 稳定 | CLS | 累积布局偏移 |

下面是三大核心指标详解。

### LCP（Largest Contentful Paint，最大内容绘制）

LCP 衡量的是**最大内容元素**从开始加载到渲染完成所花费的时间，代表用户感知到的"页面主要内容是否加载完成"。

LCP 关注的最大内容元素通常包括：

- `<img>` 图片元素
- `<svg>` 内的 `<image>` 元素
- `<video>` 视频封面图
- 通过 `url()` 加载背景图片的元素
- 包含文本节点或其他行内级文本元素的块级元素

**目标值（Good 区间）**：≤ 2.5 秒（在首屏加载开始的 75 分位数）。

```js
// 示例：最大内容元素会是哪一项？
// 这里标题文本或大图会成为 LCP 的候选
<div class="post">
  <img src="hero.jpg" alt="hero" />   <!-- 可能是 LCP 元素 -->
  <h1>这是一篇长篇标题文字，块级文本</h1>
</div>
```

**优化方向**：减少服务器响应时间（TTFB）、优化图片体积与格式、预加载关键资源（`<link rel="preload">`）、提升渲染路径。

### FID 与 INP（交互响应性）

**FID（First Input Delay，首次输入延迟）**衡量用户**第一次**与页面交互（点击、点击按键）到浏览器能够响应该交互之间的时间。它反映的是主线程的繁忙程度，而非事件处理耗时。

FID 只能反映"第一次输入"，无法覆盖页面生命周期内的所有交互，因此 Google 正在用 **INP（Interaction to Next Paint，交互到下次绘制）** 取代 FID。INP 衡量的是页面**整个生命周期内**所有用户交互中最差/具有代表性的一次交互延迟，即从用户交互到下一帧被绘制的时间。

**目标值（Good 区间）**：

- FID：≤ 100ms
- INP：≤ 200ms

**优化方向**：减少主线程阻塞（拆分长任务）、减少不必要的 JavaScript、使用 Web Worker 处理重逻辑、控制事件监听频率。

### CLS（Cumulative Layout Shift，累积布局偏移）

CLS 衡量页面在加载过程中**意外**发生的布局偏移程度。它由两部分决定：

- **位移距离（distance）**：不稳定元素移动的距离
- **影响比例（impact fraction）**：元素在视口中的影响范围

偏移分数 = 位移距离 × 影响比例。CLS 是这些分数的总和。

**目标值（Good 区间）**：≤ 0.1。

**优化方向**：

- 为图片/视频等设置固定 `width`、`height` 或 `aspect-ratio`
- 避免在内容上方动态插入元素
- 使用 `transform` 动画替代触发布局的属性
- 预留广告位、弹窗等动态元素的空间

## 其他性能指标

除了三大核心指标，还有一组辅助指标帮助更细粒度地诊断性能问题。它们与"时间"相关的指标统称为 **Time-based Metrics**。

### FP 与 FCP

- **FP（First Paint，首次绘制）**：浏览器第一次将任何像素绘制到屏幕的时刻。它不关心绘制内容是否有意义。
- **FCP（First Contentful Paint，首次内容绘制）**：第一次绘制出**有意义内容**（文本、图片、非白背景的 canvas 等）的时刻。

**目标值**：FCP ≤ 1.8 秒。

### TTFB（Time to First Byte，首字节时间）

TTFB 衡量从请求发出到浏览器接收到**响应头的第一个字节**的时间。它受 DNS 查询、TLS 握手、服务器处理、网络传输等影响，是加载体验的起点。

**目标值**（推荐）：≤ 800ms（服务器响应为主导时 < 200ms）。

```text
TTFB = 请求发出 → 首字节到达
      ├─ DNS 解析
      ├─ TCP/TLS 握手
      ├─ 服务器处理（最大变数）
      └─ 响应首字节传输
```

### TBT（Total Blocking Time，总阻塞时间）

TBT 衡量页面从 FCP 到 TTI 之间，主线程**被长任务阻塞的总时间**。所谓"长任务"是持续时间超过 50ms 的任务，TBT 只统计长任务**超过 50ms 的部分**之和。

示例：一个 80ms 的长任务贡献 `80 - 50 = 30ms` 到 TBT。

**目标值**（Lighthouse 评分参考）：≤ 200ms 为优（移动端）。

### SI（Speed Index，速度指数）

SI 衡量页面**可见内容的填充速度**，通过计算可视区域内容呈现过程中像素变化的速率得出。SI 越低，表示页面内容越快完整呈现。

**目标值**：≤ 3.4 秒为优（Lighthouse 参考）。

### TTI（Time to Interactive，可交互时间）

TTI 衡量页面"可可靠响应用户输入"的时间点。判定条件通常是：

- 页面已完成首个内容绘制（FCP）
- 页面处于可响应状态（主线程空闲）
- 没有超过 50ms 的长任务阻塞

**示例指标关系**（按时间轴）：

```text
TTFB → FP → FCP → (TBT 发生在期间) → TTI → LCP → 稳定(CLS)
 ----加载起点---- ----内容呈现---- ----可交互---- ----完成----
```

## 性能评估工具

### Lighthouse

Lighthouse 是 Google 提供的开源自动化审计工具，对页面进行"开箱即用"的性能打分。它在模拟移动端（4G 节流）环境下运行，输出性能、无障碍、最佳实践、SEO、PWA 等多项评分。

- 使用方式：Chrome DevTools → Lighthouse 面板 / 命令行 `npx lighthouse <url>`
- 输出：性能报告 + 各项指标评分 + 优化建议（Opportunities / Diagnostics）
- 定位：**基准审计与趋势监控**，而非精确的实验室数据

```bash
# 命令行方式
npx lighthouse https://example.com --only-categories=performance --output=html --output-path=./report.html
```

### Chrome Performance 面板

Chrome DevTools 的 Performance 面板提供**详细的运行时性能剖析**，用于定位具体瓶颈：

- **Record**：录制交互过程，回放主线程时间线
- **火焰图（Flame Chart）**：查看函数调用堆栈、耗时占比、长任务（红色标记）
- **Frames / Rendering**：查看渲染、绘制、布局耗时
- **Bottom-Up / Call Tree**：按耗时聚合自下而上分析热点函数

```text
Performance 面板使用步骤
1. 打开 DevTools → Performance
2. 点击 Record 开始录制
3. 与页面交互（或刷新页面复现问题）
4. 停止录制，分析火焰图与指标
5. 结合 Network 面板定位资源加载瓶颈
```

### Performance API

`performance` 全局对象提供浏览器自动收集的高精度时间数据，是编程式测量的基础：

- `performance.timing`（已废弃）/ `performance.getEntriesByType()`：获取各类性能条目
- `performance.now()`：相对导航开始的高精度时间戳（微秒级）
- `performance.mark()` / `performance.measure()`：手动标记与测量

```js
// 记录自定义耗时
performance.mark('moduleA-start');
// ... 执行业务逻辑
performance.mark('moduleA-end');
performance.measure('moduleA-duration', 'moduleA-start', 'moduleA-end');

// 读取测量结果
const entries = performance.getEntriesByType('measure');
console.log(entries);
```

### PerformanceObserver

`PerformanceObserver` 是**监听**性能条目的推荐方式，它以异步回调的方式持续接收新的性能事件，无需轮询。相比之下，直接调用 `getEntries()` 只能获取历史数据。

```js
// 监听 LCP
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('LCP:', entry.startTime);
  }
}).observe({ type: 'largest-contentful-paint', buffered: true });

// 监听布局偏移（CLS）
new PerformanceObserver((list) => {
  let cls = 0;
  for (const entry of list.getEntries()) {
    if (!entry.hadRecentInput) {
      cls += entry.value;
    }
  }
  console.log('CLS:', cls);
}).observe({ type: 'layout-shift', buffered: true });

// 监听长任务（TBT 数据来源）
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log('长任务时长:', entry.duration, 'ms');
  }
}).observe({ type: 'longtask', buffered: true });
```

### RAIL 模型

RAIL 是 Google 提出的一套以"用户为中心"的性能模型，指导性能优化的优先级。其核心思想是：**性能优化的目标是响应用户，而非响应设备**。

| 缩写 | 含义 | 目标 | 提倡操作 |
| --- | --- | --- | --- |
| R (Response) | 响应 | 输入响应 < 100ms | 交互即时反馈 |
| A (Animation) | 动画 | 每帧 < 16ms (10ms 渲染预算) | 帧率 60fps |
| I (Idle) | 空闲 | 主线程空闲 > 50ms | 用空闲时间处理非用户请求 |
| L (Load) | 加载 | 内容加载 < 5s | 首屏快速呈现 |

RAIL 的响应预算示例：输入 100ms → 分给处理 5ms、其余给渲染。它帮助开发者权衡"优先优化哪一项"。

## 如何测量与上报指标

性能指标本质上分为三类，度量与采集方式各不相同：

1. **实验室数据（Lab）**：在受控环境（如 Lighthouse）下测得，可复现、可对比，但不反映真实用户。
2. **真实用户监控（RUM，Field）**：在用户浏览器中采集，反映真实网络与设备，但样本噪声大。
3. **综合测量**：二者结合，用 RUM 发现问题、用 Lab 定位根因。

### 核心指标采集示例

结合 `performance.getEntriesByType()` 与各类专项观察器，可以采集完整指标集合：

```js
function collectMetrics() {
  const metrics = {};

  // FCP / FP
  const navEntry = performance.getEntriesByType('navigation')[0];
  const paint = performance.getEntriesByType('paint');
  paint.forEach((p) => (metrics[p.name] = p.startTime));

  // TTFB
  if (navEntry) {
    metrics.ttfb = navEntry.responseStart;
  }

  // LCP
  try {
    const lcpEntries = performance.getEntriesByType('largest-contentful-paint');
    if (lcpEntries.length) {
      metrics.lcp = lcpEntries[lcpEntries.length - 1].startTime;
    }
  } catch (e) {
    /* 旧浏览器不支持时忽略 */
  }

  return metrics;
}

// 建议在页面隐藏或卸载前上报，避免上报请求自身影响数据
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    reportMetrics(collectMetrics());
  }
});
```

### 上报示例

上报策略建议：

- **批处理**：合并多条指标为一次请求，使用 `navigator.sendBeacon()` 或 `fetch` + `keepalive`。
- **去重**：按 `sessionId + 页面路径 + 设备类型` 维度去重，控制采样率。
- **附带上下文**：上报网络类型（EffectiveConnectionType）、设备、浏览器版本。

```js
function reportMetrics(metrics, extra) {
  const body = { metrics, ...extra };
  const blob = JSON.stringify(body);

  if (navigator.sendBeacon) {
    // sendBeacon 保证在页面卸载时也能送达
    navigator.sendBeacon('/api/perf', blob);
  } else {
    // fetch keepalive 作为兜底
    fetch('/api/perf', {
      method: 'POST',
      body: blob,
      keepalive: true,
      headers: { 'Content-Type': 'application/json' },
    });
  }
}

// 采样率控制示例
const SAMPLE_RATE = 0.1; // 10% 用户上报
if (Math.random() < SAMPLE_RATE) {
  reportMetrics(collectMetrics(), {
    version: '1.0.0',
    route: location.pathname,
  });
}
```

### 上报时序建议

不同指标的"稳定判定"时机不同，建议分层上报：

```js
// 短时指标（FCP/TTFB）在 load 后即可上报
window.addEventListener('load', () => {
  reportMetrics(pickShortMetrics());
});

// 长时指标（LCP/CLS/INP）在页面隐藏前上报，确保拿到最终值
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    reportMetrics(pickLongMetrics());
  }
});
```

## 指标快照表

下表汇总本文涉及的所有指标，方便查阅对照。

| 指标 | 含义 | 衡量内容 | 目标值（Good） | 产生的时机 |
| --- | --- | --- | --- | --- |
| LCP | 最大内容绘制 | 最大内容元素渲染完成时间 | ≤ 2.5s | 加载完/加载中某个时刻 |
| FID | 首次输入延迟 | 首次交互到响应的时间 | ≤ 100ms | 首次输入时（将被 INP 取代） |
| INP | 交互到下一次绘制 | 生命周期内代表性交互延迟 | ≤ 200ms | 交互事件时 |
| CLS | 累积布局偏移 | 意外布局位移的总分 | ≤ 0.1 | 整个生命周期累积 |
| FP | 首次绘制 | 首次绘制任意像素 | 越快越好 | 首个像素绘制时 |
| FCP | 首次内容绘制 | 首次绘制有意义内容 | ≤ 1.8s | 首个内容绘制时 |
| TTFB | 首字节时间 | 请求到首字节到达 | ≤ 800ms | 响应首字节时 |
| TBT | 总阻塞时间 | FCP→TTI 期间长任务阻塞总时长 | ≤ 200ms | 主线程长任务期间 |
| SI | 速度指数 | 可见内容填充速度 | ≤ 3.4s | 加载全程 |
| TTI | 可交互时间 | 页面可靠响应输入的时间 | 越快越好 | 主线程空闲后 |

### 选择策略

- **面向用户体感**：优先关注 Core Web Vitals（LCP / INP / CLS）
- **面向诊断**：TTFB、FCP、TBT、SI 帮助定位加载链路哪一步拖沓
- **面向维护**：以 RAIL 模型判断优化优先级，用 Field 数据（RUM）发现真实问题、用 Lab 数据（Lighthouse）验证修复

## 小结

性能评估是一个"先测量、再优化、后回归"的闭环过程。本文确立了三大 Core Web Vitals 作为用户体验的基线目标，补充了 TTFB、FCP、TBT 等内容与交互维度的辅助指标，并通过 Lighthouse、Chrome Performance 面板、Performance API 与 PerformanceObserver 提供了从"基准审计"到"运行分析"再到"编程上报"的完整工具链。掌握这套指标与评估体系，是把性能优化从"玄学"变为"工程"的第一步。

## 最小实现：用 Demo 读一次真实指标

到 `code/frontend/09-performance` 运行 `perf-reader.html`：页面先显示"waiting…"，随后通过 `performance.getEntriesByType('paint')` 打印 FCP、通过 `PerformanceObserver` 监听 `largest-contentful-paint` 拿到 LCP、再读 `navigation` 条目算 DOMContentLoaded 与 TTFB。原理一句话：浏览器在渲染过程中把各阶段耗时写进 `performance` 只读缓冲区，测量就是对这份数据进行读取与订阅，而非靠猜。
