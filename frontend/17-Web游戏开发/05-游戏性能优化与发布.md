# 游戏性能优化与发布

> 级别：高级

按本书四层推进——属实战收尾：入门渲染 / 内存 / 加载三大性能维度与监控指标；进阶到 draw call、图集、对象池、Worker 与掉帧自适应；实战用 `code/frontend/17-game` 的 demo 观察帧率，最小实现即"用 FPS 统计代码量化每次改动的收益"，让"优化要靠数据说话"落到可运行的代码上。

Web 游戏"卡不卡"直接决定口碑，而性能问题从来不是某一处的问题，而是**渲染、内存、资源加载、GC 卡顿、发布适配**一串链条。一个优化到位的 Web 小游戏，能把庞大场景在普通手机上跑出稳定 60fps；一个疏于优化的，同样的代码在高端机上也掉帧。

这一章我们从渲染性能（draw call、合批、帧率）讲起，依次覆盖内存与资源管理、加载优化（分包/预加载/懒加载）、防卡顿与掉帧策略、Web 性能监控，最后到发布与多端适配（PC / 移动 / 小程序）。每一点都给可执行的度量标准与手段。

## 一、渲染性能：draw call / 合批 / 帧率

### 1. 三大核心指标

| 指标 | 含义 | 参考达标 |
| --- | --- | --- |
| FPS | 每秒帧数 | 稳定 ≥ 55（移动端 ≥ 30~45） |
| draw call | 每帧调用 GPU 绘制命令的次数 | 桌面 < 数百，移动端 < 100 |
| 帧耗时 | 每帧 CPU+GPU 总耗时 | < 16.7ms 才能跑 60fps |

> **一句口诀**：draw call 是按"一次提交"算的，**越少越好**；GPU 忙于光栅化"过度绘制（overdraw）"和纹理带宽，内存层面的纹理也要惦记。

### 2. 什么是 draw call 与合批（Batching）

**draw call** 是 CPU 一次"把一堆顶点提交给 GPU 去画"的系统调用。每个 draw call 都有 CPU 开销，动辄成百上千个就会拖垮主线程。引擎会用**合批**把"能用同一纹理、同一 shader 的多个物体"合并成一次 draw call 提交：

- **Texture Atlas / Spritesheet**：把零散小图合成一张大图 → 同纹理 → 可合批。
- **Instance（实例化）**：同一模型大量复制（子弹、弹幕、森林）用 `InstancedMesh`，一次提交画 1000 颗子弹。
- **合批限制**：纹理、透明度、混合模式、滤镜不同时会打断合批。

```js
// Three.js：InstancedMesh 一次画大量相同模型
import { InstancedMesh, BoxGeometry, MeshBasicMaterial } from "three";
const geo = new BoxGeometry(0.1, 0.1, 0.1);
const mat = new MeshBasicMaterial({ color: 0x44dd88 });
const instanced = new InstancedMesh(geo, mat, 5000); // 5000 个实例
scene.add(instanced);
// 逐实例设置变换矩阵
instanced.setMatrixAt(i, new Matrix4().makeTranslation(x, y, z));
instanced.instanceMatrix.needsUpdate = true;
```

### 3. 帧率与垂直同步

- `renderer.setPixelRatio(Math.min(devicePixelRatio, 2))` 避免高分屏过度采样。
- 设置 `devicePixelRatio` 与阴影分辨率上限，防止移动端直接崩帧。
- 掉帧严重时可**动态降分辨率**（自适应渲染），并把 60fps 降到 30fps 作为兜底策略。

## 二、内存与资源管理

### 1. 纹理是内存大头

- **纹理会占用显存**：一张 2048×2048 RGBA 纹理 = 2048×2048×4 ≈ 16MB 显存。堆十几张大图立刻告急。
- **尽量用图集**：相同面积下，图集纹理比零散图省 CPU 纹理绑定与显存。
- **控制 mipmap**：不需要缩放远距离细节时关掉或用较少级数。

```js
// 加载器设置内存谨慎的选项
renderer.dispose()              // 显存释放
material.dispose(); geometry.dispose(); texture.dispose();
```

### 2. 手动释放不再用的资源

Three.js / PixiJS 里的几何体、材质、纹理不会自动 GC，需显式 `dispose()`，否则**显存悄悄增长**，最终 WebGL context lost。

```js
// 切换场景/删除对象时
scene.traverse(obj => {
  if (obj.isMesh) {
    obj.geometry.dispose();
    if (Array.isArray(obj.material)) obj.material.forEach(m => m.dispose());
    else obj.material.dispose();
  }
});
// 清理 PIXI：sprite.destroy({ children: true, texture: true });
```

### 3. 内存泄漏排查

- 用 Chrome **Memory / Performance** 面板录几帧看堆与显存曲线是否只增不减。
- 注意**闭包、全局数组、AudioContext、事件监听**的泄漏。
- 善用**对象池**（第 2 章）避免高频对象反复 new 带来的 GC 抖动。

## 三、加载优化：分包 / 预加载 / 懒加载

### 1. 首屏包体控制是游戏速度关键

Web 游戏最大的门槛是"加载慢"。核心手段是**分包 + 懒加载**，把首关所需资源和后续内容分开。

```js
// CSS/JSDelivr 或构建工具里按需加载（伪代码示意）
import { loadGLTF } from "./loader.js";

// 进入第 2 关时才异步加载该关资源
level2Button.onclick = () => {
  renderer.loading.show();
  const assets = await Promise.all([
    loadGLTF("levels/level2.glb"),
    loadTexture("levels/level2.png"),
  ]);
  renderer.loading.hide();
  startLevel2(assets);
};
```

### 2. 预加载 vs 懒加载

| 策略 | 时机 | 适用 |
| --- | --- | --- |
| 预加载 | 进场/加载页内一次性拉完核心资源 | 体量小、必须的关卡、用户可等待 |
| 懒加载 | 用到时再加载 | 后几关、可选皮肤、不常用的模型 |
| 分包 | 物理上把资源拆成多份文件 | 严格控制首包体量 |

### 3. 缓存与复用

- 静态资源加 `Cache-Control`，让浏览器 `localStorage`/HTTP Cache 命中第二次访问秒开。
- 大模型资源压缩（Draco/meshopt）；图片用 WebP/AVIF。
- 配置 CDN 就近分发、开启 gzip/brotli。

## 四、防卡顿与掉帧策略

### 1. 卡顿分类

| 类型 | 成因 | 对策 |
| --- | --- | --- |
| 长任务（jank） | 一次 JS 干太多阻塞主线程 | 拆帧、分片、用 Worker |
| GC 停顿 | 大量临时对象触发回收 | 对象池、避免每帧 new |
| 渲染突发 | 一帧突然提交大量资源 | 预加载、图片流式解码 |
| 网络卡顿 | 资源中途加载导致暂停 | 分包 + 预加载 + 占位 |

### 2. 让加载不影响游戏流

- **图片/纹理异步解码**：用 `createImageBitmap` 或离图流式，避免解码阻塞主线程。
- **Loading 画面**：加载资源时显示进度，不让用户看到冻结画面。
- **延迟创建**：非关键对象放到空闲时再创建（`requestIdleCallback`）。

### 3. 用 Worker 把重活丢出主线程

把物理、路径查找、AI、二进制解码放到 **Web Worker**，主线程只做渲染与轻逻辑。渲染仍在主线程，但 CPU-bound 大头被移走，主线程就稳了。

```js
const worker = new Worker(new URL("./physics.worker.js", import.meta.url));
worker.postMessage({ type: "step", dt });
worker.onmessage = ({ data }) => syncBodies(data);
```

### 4. 掉帧自适应

```js
const target = 60, LOW = 30;
let frameAcc = 0;
function measure() { /* 统计最近帧耗时 */ }

if (avgFrameTime > 1000 / LOW) {
  renderer.setPixelRatio(1.5);      // 降分辨率
  shadowEnabled = false;            // 关阴影/后处理
}
```

## 五、Web 性能监控

### 1. 监控指标

- **FPS / 长帧**：统计每帧耗时，标记 > 50ms 的长帧为卡顿。
- **加载耗时**：从 navigationStart 到首帧渲染。
- **内存 / GPU**：监听 `performance.memory`（堆）、`webglcontextlost`。

```js
let frames = 0, sum = 0, max = 0;
function tick(now) {
  const dt = now - last; last = now;
  sum += dt; frames++;
  max = Math.max(max, dt);
  if (frames >= 120) {
    console.log("平均帧耗时", sum / frames, "最大", max);
    frames = 0; sum = 0; max = 0;
  }
  requestAnimationFrame(tick);
}
```

### 2. 打点上报

把关键指标上报到监控平台（如 WebVitals 外的自定义埋点），聚合出"哪些机型/哪些关卡掉帧最严重"，据此针对性优化。

```js
navigator.sendBeacon("/telemetry", JSON.stringify({
  fps, longFrameCount, level, device,
})); // sendBeacon 在页面离开也能可靠发出
```

## 六、发布与多端适配

### 1. PC / 移动 Web

| 端 | 注意点 |
| --- | --- |
| PC（Web） | 键盘鼠标体验优先、宽屏布局、F 全屏、Gamepad 支持 |
| 移动（WebView/H5） | 触摸 / 防止滚动、`devicePixelRatio` 限制、`touch-action`、软键盘避让 |

```css
/* H5 游戏禁用页面滚动与双击缩放 */
html, body { overflow: hidden; touch-action: none; user-select: none; }
```

### 2. 小程序小游戏

- **无 DOM**：只用宿主 Canvas/WebGL 渲染，登录、支付、分享走宿主 API。
- **包体限制**：严格限制首包大小（微信主包很小），**大资源分包 + 远程 CDN**。
- 平台差异 API 用适配层隔离（PIXI/Cocos 有现成 adapter）。

### 3. 发布流程建议

1. 打包优化（压缩 JS、图片、模型，Tree-shaking 去掉无用引擎模块）。
2. CDN 部署 + 分域 + Cache 头。
3. 多端出包：Web / 移动 H5 / 微信小游戏 / 抖音小游戏，各用其适配构建。
4. 灰度发布 + 线上监控 + 快速回滚预案。

## 小结

- 渲染性能关注 **draw call / 合批 / 帧率**，用图集与实例化压 draw call。
- 内存大头是**纹理**，记得 `dispose()` 显式释放，防显存泄漏与 GC 抖动。
- 加载优化 = **分包 + 预加载 + 懒加载 + 缓存压缩**，首屏体积是速度关键。
- 防卡顿要靠**拆帧、对象池、Worker 移重活、掉帧自适应**。
- 用 **FPS/长帧/内存/contextlost** 做监控并上报，指导后续优化。
- 发布要应对 **PC / 移动 H5 / 小程序** 三种适配，各管一套构建与规范。

## 最小实现：跑起来数帧率

性能优化的最佳量具是帧率。到 `code/frontend/17-game` 打开 demo，观察主循环里统计每帧耗时、标记长帧，再通过调整方块 / 精灵数量体会掉帧的直观影响。原理一句话：优化前先量化——用"每帧耗时 / FPS"说话，找到瓶颈再动手，才符合"用数据驱动优化"的工程习惯。
