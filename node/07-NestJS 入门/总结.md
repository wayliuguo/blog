## 分篇知识点

### NestJS 入门 00-NestJS 学习地图与边界

- **为什么 NestJS 要排在后面学**
  - **价值在"组织"而不是"能力"**：它能做的事裸 Node.js 都能做，只是把"怎么组织一个能长期维护的后端项目"变成了一套有约束的约定
  - **先学语法就只会写不会答**：`private readonly userService` 为什么不用 `new`、`@Get(':id')` 怎么变成路由、请求进来先经过谁，答案都藏在底层 HTTP 与 Web 框架知识里
- **NestJS 封装的四层（每层对应一个认知）**
  - **分层链**：Controller → NestJS（DI / 装饰器 / 生命周期）→ Express / Fastify → Node HTTP → TCP / epoll，你只写最上面的 Controller
  - **DI 容器**：对象谁来创建、依赖怎么传
  - **装饰器 + Metadata**：路由、参数、权限怎么"声明"出来
  - **请求生命周期**：请求依次经过哪些环节
  - **底层 HTTP**：报文怎么解析、响应怎么写出
- **框架是一组"你已经认可了的约定"**
  - **学的是约定解决的问题**：重点不是记住有多少个装饰器，而是理解每一层约定解决了什么问题——这样当约定不适用时，你知道该在哪里打破它
- **学习边界与节奏**
  - **必须掌握**：Module / Controller / Provider 三件套、依赖注入（`@Injectable` + 构造函数注入）、请求处理链顺序、DTO + ValidationPipe、数据库集成、配置与日志
  - **知道怎么用即可**：微服务架构、切换 Fastify、动态模块与自定义 Provider Token，业务代码很少碰
  - **可以暂时跳过**：源码级最小实现、`forwardRef` 循环依赖、高级装饰器元编程，踩到再回来
  - **节奏上的优先级**：先跑通快速上手与依赖注入摸清概念，再写模块与控制器，接着啃请求处理链（最关键、不能跳），最后接上数据库集成——到这里算入门
- **三个常见误区**
  1. **把 NestJS 当成"更高级的 Express"**：它不是多几个中间件，而是多出 Guard（能不能进）、Pipe（数据对不对）、Interceptor（包裹执行）、Filter（出错怎么办）各司其职的一整套生命周期
  2. **觉得装饰器是"魔法"**：装饰器只负责往类或方法上贴标签，真正干活的是运行时读标签的框架代码，`@Roles('admin')` 必须配一个 Guard 才会生效
  3. **一上来就拆微服务**：单体配合良好的模块划分能撑到相当大的规模，提前拆只会把分布式事务、链路追踪、服务发现的复杂度塞给自己


### NestJS 入门 01-快速上手

- **NestJS 的四个核心特点**
  1. **内置 TypeScript**：类型安全，开发体验好
  2. **借鉴 Angular 架构**：模块化、依赖注入、装饰器
  3. **底层可切换**：默认 Express，可切换为 Fastify
  4. **开箱即用**：内置验证、序列化、ORM 集成等
- **项目初始化与启动**
  - **两条命令**：`npm install -g @nestjs/cli` 装 CLI，`nest new my-project` 建项目，默认监听 3000
  - **src/ 五个文件的职责**：`app.controller.ts` 处理请求、`app.module.ts` 组织代码、`app.service.ts` 承载业务、`main.ts` 是入口
  - **两个启动脚本**：`npm run start` 单次启动，`npm run start:dev` 带热重载，开发期用后者
- **第一个 Controller**
  - **路由由装饰器拼出**：`@Controller('users')` 给出路由前缀，`@Get()` 与 `@Get(':id')` 决定具体路径
- **CLI 常用命令**
  - **`nest g` 系列**：`nest g resource users` 一次生成 module / controller / service / dto / entities 全套骨架，也可单独 `nest g module|controller|service|class`


### NestJS 入门 02-IOC 与依赖注入

- **为什么需要 DI**
  - **手动 `new` 的三个代价**：与实现紧耦合、没法替换 Mock 做单测、改构造方式要改所有调用点
  - **DI 的做法**：构造函数里声明 `private readonly userService: UserService`，实例由容器创建并注入
- **两个装饰器与一行声明**
  - **`@Injectable()` 真正的作用**：把类登记进 DI 容器的"可被注入"名单，没有它容器根本不认识这个类
  - **构造函数注入一行三用**：`private readonly userService: UserService` 同时声明了字段、类型和依赖
  - **按 Token 注入**：非类依赖（如配置对象）用 `@Inject('CONFIG')` 取值
- **DI 容器怎么装配依赖**
  1. **发现**：扫描 `@Injectable` 标记的类
  2. **分析**：读取构造函数的参数类型
  3. **递归**：先把依赖的实例创建出来
  4. **注入并返回**：塞进构造函数，交回创建好的实例
- **三种自定义 Provider**
  1. **useClass**：`{ provide: UserService, useClass: UserService }`，Token 就是类本身，最常用的一种
  2. **useValue**：`{ provide: 'CONFIG', useValue: { port: 3000 } }` 注入常量或配置对象，取值要配 `@Inject('CONFIG')`
  3. **useFactory**：`{ provide: 'DB_CONNECTION', useFactory: cfg => ..., inject: [ConfigService] }`，用于需要运行时逻辑或异步的实例


### NestJS 入门 03-模块与提供器

- **@Module：组织代码的基本单元**
  - **四个字段**：`imports` 导入别的模块、`controllers` 挂控制器、`providers` 注册服务、`exports` 导出给别处用
  - **根模块有且只有一个**：其余模块从根模块的 `imports` 开始被递归挂载，这条递归链决定了模块可见性
- **模块共享的完整链条**
  - **注册 → 导出 → 导入**：提供方先 `providers` 注册再 `exports` 导出，使用方在 `imports` 里引入，三步缺一就报 DI 错
- **@Global() 全局模块**
  - **免导入即可用**：Provider 在所有模块里都能注入，只留给配置、日志这类真正全局的东西，不要滥用
- **动态模块**
  - **forRoot**：`static forRoot(options): DynamicModule` 让库在被导入时接收一份配置参数
  - **forRoot 与 forRootAsync**：同步直接传对象，异步用 `imports + inject + useFactory` 从 ConfigService 读配置


### NestJS 入门 04-控制器与路由

- **@Controller 与路由前缀**
  - **前缀机制**：`@Controller('users')` 之后该控制器所有路由都以 `/users` 开头
  - **方法装饰器定动作**：`@Get()` / `@Post()` / `@Put(':id')` / `@Delete(':id')` 分别对应查、建、改、删
- **参数装饰器大全**
  1. **`@Param`**：取路由参数，如 `:id`
  2. **`@Query`**：取查询串，如 `?page=1`
  3. **`@Body`**：取请求体（POST / PUT 的 JSON）
  4. **`@Headers`**：取请求头，如 `Authorization`
  5. **`@Ip`**：取请求 IP
  6. **`@Req`**：拿原始 Request 对象
- **响应处理**
  - **返回值自动序列化**：控制器返回对象会被自动转成 JSON，默认状态码 200，不用手动写响应
  - **@HttpCode 与 @Redirect**：`@HttpCode(201)` 自定义状态码，`@Redirect('/users', 301)` 做重定向
- **RESTful 设计规范**
  - **方法语义**：GET 查询、POST 创建、PUT 全量替换、PATCH 部分更新、DELETE 删除
  - **资源命名反例**：动词式路径 `/getUsers`、命名不一致 `/userList`、用 POST 做查询、把资源 ID 塞进查询参数


### NestJS 入门 05-请求处理链

- **请求处理链的精确顺序**
  1. **固定顺序**：Middleware → Guard → Interceptor(前置) → Pipe → Controller → Service → Interceptor(后置) → HTTP Response，异常统一进 Exception Filter
  2. **Service 不是生命周期阶段**：Controller → Service → Repository 是业务调用链，框架不会为它单开处理节点
- **两个心智模型：IoC/DI 与 装饰器/元数据**
  - **IoC 与 DI 的分工**：IoC 是把对象创建与依赖装配的控制权交给容器的思想，DI 是它的落地方式；Controller 只声明 `userService: UserService`，实例由容器造好注入
  - **装饰器与元数据的分工**：Decorator 负责写标签、`Reflect.defineMetadata` 负责存标签、`Reflector` 负责读标签
  - **`@Roles` 本身不拦请求**：它只是声明，必须成对写一个 Guard 去读这个标签，权限校验才真正生效
- **两套生命周期别混**
  - **应用生命周期**：`onModuleInit` / `onApplicationShutdown` 这类钩子只在整个进程启动与关闭时跑，每个请求不会触发
  - **请求生命周期**：Middleware → … → Response 这条处理链，每个 HTTP 请求都跑一遍
- **Middleware 与 Guard 的本质差别**
  - **能力差异**：Middleware 只拿到 `req/res/next`，Guard 能从 `ExecutionContext` 拿到 `switchToHttp().getRequest()`、`getHandler()` 与 `getClass()`
  - **鉴权为什么放 Guard**：只有 Guard 能拿到"即将执行的 Handler"，配合 `Reflector` 才能读方法上的 `@Roles` 元数据，实现按路由粒度的权限
- **五组件职责口诀**
  - **Middleware**：预处理——进来之前先做什么（日志、CORS、cookie 解析、安全头）
  - **Guard**：能不能进——这个请求有权限吗（身份认证、角色校验）
  - **Pipe**：数据对不对——参数合法、类型对吗（DTO 校验、类型转换、分页范围）
  - **Interceptor**：包裹执行——进出前后还要做点什么（统一响应格式、耗时统计、缓存）
  - **Exception Filter**：处理异常——出错了怎么返回（统一错误响应）
- **各组件的落地写法**
  - **Middleware 的三种写法**：类式实现 `NestMiddleware` 可注入依赖、函数式更轻量，都用 `consumer.apply().forRoutes()` 绑定；`app.use()` 挂 Express 原生中间件全局生效
  - **全局注册优先用 Provider**：`app.useGlobalGuards(new X())` 无法注入依赖，`{ provide: APP_GUARD, useClass: X }` 可以
  - **Interceptor 的包裹模型**：前置逻辑写在 `intercept()` 里，再 `return next.handle().pipe(...)`——`tap` 统计耗时、`map` 统一响应格式，响应改写发生在 pipe 内
  - **ValidationPipe 三个关键选项**：`whitelist` 剔除 DTO 未定义字段、`forbidNonWhitelisted` 遇到多余字段直接 400、`transform` 自动转类型
  - **Exception Filter 的两种粒度**：`@Catch(HttpException)` 只兜指定类型、`@Catch()` 兜全部，用 `host.switchToHttp()` 取 res 手动返回，全局注册用 `APP_FILTER` 才可注入依赖


### NestJS 入门 06-数据库集成

- **TypeORM 集成三步**
  1. **建连接**：`TypeOrmModule.forRoot({ type: 'mysql', ... })` 在根模块里配好连接参数
  2. **定义 Entity**：`@Entity('users')` 配 `@PrimaryGeneratedColumn` / `@Column` 描述表结构
  3. **注册 Repository**：`TypeOrmModule.forFeature([User])` 在业务模块里注册 `User` 的 Repository
- **实体关系装饰器**
  - **一对多 / 多对一**：`@OneToMany` / `@ManyToOne` 配 `@JoinColumn({ name: 'user_id' })` 指定外键列名
  - **多对多的维护方**：`@ManyToMany` 需要一方加 `@JoinTable()`，只有这一侧会在库里建中间表，另一方只声明反向关系
- **事务用 QueryRunner**
  - **完整流程**：`createQueryRunner()` → `connect()` → `startTransaction()` → manager 操作 → `commitTransaction()`，出错 `rollbackTransaction()`，finally 里 `release()`
- **synchronize 与迁移**
  - **synchronize 只在开发开**：`synchronize: true` 会按实体自动改表结构，生产必须关掉并改用 Migration，否则可能丢数据
  - **迁移三条命令**：`migration:generate` 生成、`migration:run` 执行、`migration:revert` 回滚，生产表结构变更全靠它
- **@InjectDataSource**
  - **注入 DataSource**：事务、原生 SQL 这类 Repository 覆盖不到的场景直接用它


### NestJS 进阶 01-自定义装饰器

- **参数装饰器：从执行上下文里取数据**
  - **`createParamDecorator` 的签名**：回调是 `(data, ctx)`，用 `ctx.switchToHttp().getRequest()` 拿到请求对象再取需要的数据
  - **`@CurrentUser()` 的两种用法**：`@CurrentUser()` 返回整个 `user` 对象，`@CurrentUser('id')` 按字段名只返回指定字段
- **方法装饰器：打标签与读标签**
  - **`SetMetadata` 只写标签不干任何活**：`const Roles = (...roles) => SetMetadata('roles', roles)`，权限判断留给 Guard
  - **`Reflector.getAllAndOverride` 的优先级**：写在方法上的元数据覆盖类上的，参数顺序固定为 `[context.getHandler(), context.getClass()]`
- **装饰器组合：一处声明多处生效**
  - **`applyDecorators` 合并多个装饰器**：把 `SetMetadata` + `UseGuards` + Swagger 装饰器合成一个 `@Auth('admin', 'editor')`
- **`ExecutionContext` 的四种能力**
  1. **`getType()`**：判断上下文是 `http`、`rpc` 还是 `ws`
  2. **`switchToHttp()`**：取 `getRequest()` 与 `getResponse()`
  3. **`getClass()`**：拿到控制器类
  4. **`getHandler()`**：拿到被调用的具体方法


### NestJS 进阶 02-作用域与循环依赖

- **三种 Provider 作用域**
  1. **`DEFAULT`（单例）**：整个应用共享一个实例，大部分 Service 用它
  2. **`REQUEST`（请求级）**：每个请求创建一个新实例，用于获取请求上下文
  3. **`TRANSIENT`（瞬态）**：每次注入都创建一个新实例，适合无状态工具类
- **REQUEST 作用域怎么用**
  - **怎么拿到请求对象**：构造函数里 `@Inject(REQUEST) private request: Request` 直接注入当前请求
  - **作用域会沿依赖链向上传染**：单例 A 注入了请求作用域的 B，A 也会退化成请求作用域，每请求重建
  - **性能代价**：每请求新建实例，增加构造耗时与 GC 压力，高频接口上代价明显
- **循环依赖用 `forwardRef` 打破**
  - **服务间循环依赖**：互相依赖的两侧都要写 `@Inject(forwardRef(() => OtherService))`
  - **模块间循环依赖**：`imports: [forwardRef(() => OrdersModule)]`，两个模块里都要写
- **作用域选型**：默认优先单例，只有确实需要"每请求一份状态"时才上 `Scope.REQUEST`


### NestJS 进阶 03-登录注册实战

- **注册链路：防重 + 加密 + 校验**
  - **密码加密用 `bcrypt`**：`genSalt(10)` 生成盐再 `hash` 存库，登录用 `compare` 比对，明文密码永不落库
  - **注册要防重与强度校验**：先查 email 是否已存在并抛 `ConflictException`，DTO 上用 `@IsEmail`/`@MinLength`/`@Matches` 限制格式
- **JWT 的结构与信任模型**
  1. **三段结构**：Header（算法与类型）+ Payload（用户数据与过期时间）+ Signature（HMAC-SHA256 签名），中间用 `.` 分隔
  2. **Payload 只是 Base64 不是加密**：任何人都能解开，绝不能放密码等敏感信息；`secret` 泄露即可伪造任意 Token
  3. **JWT 与 Session 的取舍**：JWT 天然支持分布式、无需共享存储，代价是主动注销要额外机制（Redis 黑名单或极短过期）
  4. **JWT 与 Cookie 不是竞争关系**：JWT 是凭证内容、Cookie 是保存方式，把 JWT 放进 HttpOnly Cookie 能兼得两者
- **登录凭证的签发与放行**
  - **签发与校验**：`JwtService.sign(payload)` 默认 HS256，`JwtModule.register({ secret, signOptions: { expiresIn } })` 配置密钥与过期时间；`PassportStrategy` 用 `ExtractJwt.fromAuthHeaderAsBearerToken()` 取令牌，`validate` 的返回值挂到 `request.user`
  - **`@Public()` 跳过全局鉴权**：用 `SetMetadata(IS_PUBLIC_KEY, true)` 打标签，全局 Guard 里用 `Reflector` 读到就放行
- **双 Token：单 Token 矛盾的解法**
  - **矛盾是什么**：有效期长则泄露危害大、短则体验差，且 JWT 天然无法主动吊销
  - **职责拆分**：Access Token 短（如 15m）只用于访问业务接口，Refresh Token 长（如 7d）只用于换发新的 Access Token
  - **刷新流程**：用 `jwtService.verify` 校验旧 Refresh Token，失败抛 `UnauthorizedException('Refresh Token 已过期，请重新登录')`
- **HttpOnly Cookie 保存 Refresh Token**
  1. **`httpOnly`**：JS 读不到，挡掉大多数 XSS 窃取，但不解决 XSS 本身
  2. **`secure`**：仅 HTTPS 传输，防明文链路被抓包
  3. **`sameSite: 'strict'`**：阻止跨站请求携带 Cookie，缓解 CSRF
  4. **`path: '/auth/refresh'`**：只在刷新接口携带，缩小暴露面
  5. **`maxAge`**：设为 7 天，与 Refresh Token 的有效期对齐
  - **Access Token 不进 Cookie**：它要前端手动塞进 `Authorization` 头，通常仍放在内存或状态管理里
- **微信小程序登录只换身份来源**：用 `code` 向微信换 `openid` 作唯一标识，之后的 JWT 签发流程与账号密码登录完全一致


### NestJS 进阶 04-文件上传实战

- **单文件上传：拦截器、落盘与两道校验闸**
  - **`FileInterceptor` 接单文件**：`@UseInterceptors(FileInterceptor('file', {...}))`，第一个参数必须与前端表单字段名一致，取参用 `@UploadedFile()`
  - **`diskStorage` 自定义落盘**：`destination` 定目录，`filename` 回调里用时间戳加随机数再加 `extname`，避免重名与中文乱码
  - **`limits` 与 `fileFilter` 两道闸**：`limits.fileSize` 限大小（如 `2 * 1024 * 1024`），`fileFilter` 用 mimetype 正则挡掉非图片，拒绝时回调传 `false` 并抛 `BadRequestException`
- **多文件上传**：`FilesInterceptor('files', 10)` 第二个参数是最大数量，取参用 `@UploadedFiles()` 拿数组
- **文件也能被管道校验**：写一个 `PipeTransform` 实现类，在 `@UploadedFile(new FileValidationPipe(10 * 1024 * 1024))` 处传入，内部校验大小与 mimetype 白名单
- **静态资源要显式开**：Express 下 `app.useStaticAssets(join(...), { prefix: '/uploads/' })`，否则文件存了也访问不到
- **头像上传的完整链路**
  1. **前端选择图片**：客户端先限制格式和大小
  2. **服务端验证**：类型、大小、是否恶意文件
  3. **重命名存储**：避免文件名冲突和中文乱码
  4. **生成缩略图**：可选，用 `sharp` 压缩
  5. **返回 URL**：保存到用户表
  6. **静态资源访问**：配置 nginx 或 Nest 静态服务


### NestJS 进阶 05-WebSocket 实时通信

- **Gateway 的声明与注册**
  - **Gateway 就是 WebSocket 层的 Controller**：`@WebSocketGateway({ cors, namespace })` 声明，并且要作为 provider 写进模块
  - **两个连接钩子**：实现 `OnGatewayConnection` 的 `handleConnection` 与 `OnGatewayDisconnect` 的 `handleDisconnect`
- **消息收发与房间模型**
  - **`@WebSocketServer()` 拿到服务端实例**：`server.emit` 全局广播，`client.to(room).emit` 定向推送给房间
  - **`@SubscribeMessage` 处理客户端消息**：回调签名 `(client, payload)`，房间用 `client.join(room)` 加入
- **连接时就要完成身份校验**
  - **取令牌**：从 `client.handshake.auth.token` 取，验证失败直接 `client.disconnect()` 断开
  - **用户信息挂在 `client.data` 上**：验证通过后 `client.data.user = user`，后续的消息处理器里随取随用
- **HTTP 与 WS 共享同一个 Service**：把 `server` 注入 `NotificationService`，HTTP 控制器也能触发 WebSocket 广播


### NestJS 进阶 06-定时任务与队列

- **定时任务的注册与三类装饰器**
  - **`ScheduleModule.forRoot()` 是前提**：不导入这个模块，`@Cron` 装饰器不会注册任何任务，只是死标签
  - **`@Cron` 两种写法**：用 `CronExpression.EVERY_DAY_AT_2AM` 这类常量，或直接写 `'*/10 * * * *'` 表达式
  - **`@Timeout` 与 `@Interval` 的区别**：`@Timeout(5000)` 是只跑一次的延迟任务，`@Interval(10000)` 是按固定间隔重复执行
  - **`SchedulerRegistry` 动态管理任务**：`addCronJob` 加、`getCronJob(name).stop()` 停、`getCronJobs()` 列出全部
- **Bull 队列：生产者与消费者**
  - **注册**：`BullModule.forRoot({ redis: { host, port: 6379 } })` 配 Redis，再 `BullModule.registerQueue({ name: 'email' })` 建队列
  - **生产者**：`@InjectQueue('email')` 注入 `Queue`，用 `queue.add('verification', data, opts)` 投递任务
  - **消费者**：`@Processor('email')` 标类、`@Process('verification')` 标方法，回调参数是 `job`，任务载荷在 `job.data`
  - **重试与延迟选项**：`attempts: 3` 重试次数、`backoff: 5000` 重试间隔、`delay` 延迟执行、`removeOnComplete: true` 完成后清理记录
- **选型：定时任务还是队列**
  1. **固定时间点执行**：每日报表生成用 `@Cron`
  2. **固定间隔的轻量任务**：健康检查用 `@Interval`
  3. **异步且要失败重试**：发送验证码邮件、用户注册欢迎邮件用 Bull 队列，主流程不阻塞
  4. **延迟触发的业务动作**：订单 30 分钟不支付则取消，用 Bull 的延迟任务


### NestJS 进阶 07-微服务架构

- **微服务两侧的角色与写法**
  - **子服务怎么起**：`NestFactory.createMicroservice<MicroserviceOptions>(Module, { transport, options })`，`options` 里给 `host` 与 `port`，网关仍用 `NestFactory.create()` 起 HTTP
  - **子服务怎么收消息**：`@MessagePattern({ cmd: 'get_user' })` 配 `@Payload()` 读参数，取代 HTTP 路由
  - **网关怎么发起调用**：`@Inject('USER_SERVICE')` 注入 `ClientProxy` 后 `client.send({ cmd }, data)` 走传输层调下游
  - **下游服务在哪声明**：`ClientsModule.register` 每个服务一项 `name + transport + options`，`name` 就是注入时用的 Token
- **四种传输方式的权衡**
  1. **TCP**：点对点、简单、低延迟，适合内部服务间通信与中小规模
  2. **Redis**：基于 Pub/Sub，无需额外中间件，适合已有 Redis 的场景
  3. **RabbitMQ**：消息持久化、路由灵活、有 ACK 机制，适合需要可靠投递的场景
  4. **Kafka**：高吞吐、分区、持久化，适合大数据量与日志收集
- **同步与异步要在同一条链路上混用**：注册流程里创建用户走 TCP 等结果，发验证邮件、赠送注册积分走 RMQ 异步不阻塞主流程，记录操作日志再走 TCP


### NestJS 进阶 08-切换Fastify平台

- **换 Fastify 的收益**
  - **性能约 2~3 倍**：压测约 40000 req/s 对比 Express 的 15000 req/s
  - **快在哪**：内置 JSON Schema 序列化替代 `JSON.stringify`
- **切换要改的三处**
  1. **入口**：装 `@nestjs/platform-fastify` 后换成 `NestFactory.create<NestFastifyApplication>(AppModule, new FastifyAdapter())`
  2. **静态资源写法不同**：Express 是 `useStaticAssets(path, { prefix })`，Fastify 是 `useStaticAssets({ root, prefix })`；视图引擎也从 `setViewEngine('hbs')` 换成 `setViewEngine({ engine, templates })`
  3. **文件上传要额外注册解析器**：Fastify 下需要 `app.register(contentParser)`（来自 `fastify-multer`）才能接收 multipart 请求
- **Express 中间件不能直接搬**：Fastify 不兼容 Express 的 `req`/`res`，`cookie-parser`/`helmet` 要换成 `@fastify/cookie`、`@fastify/helmet`，用 `app.register()` 注册


### NestJS 进阶 09-NestJS 源码分析

- **前置知识三件套**：TypeScript 装饰器、`reflect-metadata`、`design:paramtypes`，缺一个就读不懂依赖注入
  - **四类装饰器的签名**：类 `(target)`、方法 `(target, key, descriptor)`、属性 `(target, key)`、参数 `(target, key, parameterIndex)`
  - **`reflect-metadata` 的意义**：用 `Reflect.defineMetadata`/`getMetadata` 隔离存储元数据，不像 `target._x = x` 那样污染类原型
  - **`design:paramtypes` 怎么被读到**：开启 `emitDecoratorMetadata` 后编译产物带上构造参数类型，容器靠它知道该注入什么
  - **元数据生成有前提**：`emitDecoratorMetadata` 只对**至少有一个装饰器**的类生效，没装饰器就没有 `paramtypes`
- **启动调用链**
  - **顺序**：`new Container` → 递归收集模块的 controller/provider → `resolve()` 读 `design:paramtypes` 递归注入 → 扫路由 → `http.createServer`
  - **装饰器写元数据的时机**：类定义时立即执行，`@Module` 存配置、`@Controller` 存 `prefix`、`@Get` 往路由数组 push、`@Param` 按参数位置记 `{ type, key }`，方法装饰器的元数据挂在 `target.constructor` 上而不是原型
- **请求调用链**
  - **顺序**：路由正则匹配 `:param` → Guard → 解析参数装饰器 → Pipe → Interceptor → Handler → 统一 `res.json`
  - **每个环节都是可选的**：按实例上有没有 `canActivate`/`transform`/`intercept` 方法决定是否执行
  - **三个出口**：Guard 返回 `false` 出 403，路由匹配不上出 404，Handler 抛错被捕获出 500
- **与真实源码的差距**：最小实现手动遍历 `paramtypes`，NestJS 用 `InstanceLoader`/`ModuleScanner`/`RoutesResolver`，并额外支持作用域与循环依赖

### NestJS 进阶 11-认证进阶-双Token与多设备会话

- **双 Token 的分工**
  - **单 Token 的死穴**：有效期长则泄露危害大、短则体验差，且客户端存不住、服务端管不了（无法主动吊销）
  - **职责拆分**：Access Token 短（如 15m）、放前端内存或 `Authorization` 头，只管访问业务接口；Refresh Token 长（如 7d）、放 HttpOnly Cookie，只管换发新的 Access Token
  - **决策模型**：Refresh Token 必须有"服务端能主动作废"的能力，否则就退化成无法吊销的长效 JWT
- **HttpOnly Cookie 的四个选项与边界**
  1. **`httpOnly`**：JS 无法读取，降低 XSS 窃取 Token 明文的风险，但**不解决 XSS 本身**
  2. **`secure`**：仅 HTTPS 下发与传输，防明文抓包
  3. **`sameSite`**：跨站不自动携带，缓解 CSRF；需要跨站携带时权衡用 `lax`
  4. **`path`**：限定携带路径（如 `/auth/refresh`），缩小 Token 暴露面
- **Refresh Token 的存储：SHA-256 而非 bcrypt**
  - **必须哈希入库**：用 `createHash('sha256').update(token).digest('hex')` 单向哈希存库，明文只在响应里给客户端一次，拖库也拿不到可用 Token
  - **别用 bcrypt 存长 Token**：bcrypt 只处理输入的前 72 字节，超长 Token 会被截断，导致不同 Token 哈希相同、校验误判
- **AuthSession 表：支持多设备会话**
  - **User 1:N AuthSession**：每个设备一条记录，新设备登录不会顶掉旧设备
  - **关键字段**：`userId`、`refreshTokenHash`（校验刷新请求）、`deviceId`（区分设备）、`userAgent`（展示活跃设备）、`expiresAt`（服务端侧过期闸门）、`revoked`（软删除标记）
- **轮换与登出**
  - **轮换做到"重放即失效"**：每次刷新先把旧记录 `revoked = true`，再签新的一对 `15m`/`7d` Token 并写入新会话，偷来的旧 Token 一用就 401
  - **登出就是会话作废**：单设备按 `refreshTokenHash` 更新，全设备按 `userId` 批量置 `revoked`，都是软删除
  - **登出后 Access Token 的 15m 窗口**：要么每次请求都查库校验（失去无状态优势），要么接受这个窗口，高敏接口可再加版本号/黑名单校验
- **常见坑**
  1. **`verifyAsync` 忘记 `await`**：异常被吞，错误变成 500 而非 401
  2. **Cookie 跨域带不上**：后端 `sameSite` 放宽到 `lax`/`none` + `secure`，前端 `fetch` 带 `credentials: 'include'`
  3. **过期时间校验缺失**：刷新时同时判断 `expiresAt > now()` 与 `revoked`
  4. **Refresh Token 明文入库**：拖库即失陷，永远只存 SHA-256 哈希
  5. **轮换后旧 Token 还能用**：每次刷新先把旧记录 `revoked = true`
- **Prisma 与 TypeORM 同层**：只是图类型推导完整才用 Prisma，哈希入库、轮换、多设备登出的设计思路完全一致，`findUnique({ where: { tokenHash } })` 对应 `sessionRepo.findOne({ where: { tokenHash } })`


### NestJS 进阶 12-IoC 与依赖注入原理

- **从手动 new 到 IoC**
  - **没有 IoC 的代价**：手动 new 出整条依赖网，改一个构造参数上层全要跟着改，越写越乱
  - **IoC 与 DI 是两个层面**：IoC 是"为什么把控制权交给容器"的思想，DI 是"怎么交出去"的具体实现方式
- **容器怎么"看得见"依赖**
  - **注入链路的完整路径**：装饰器在编译期 emit `design:paramtypes` → `reflect-metadata` 挂到类上 → 启动扫描 → 容器解析并实例化 → 注入使用方
  - **`@Injectable()` 与 `emitDecoratorMetadata` 缺一不可**：前者让零件进"可注入"名单，后者让容器看得见零件类型，否则运行时报 `Nest can't resolve dependencies`
- **Provider Token 与四种声明方式**
  1. **`useClass`**：`{ provide: UserService, useClass: UserService }`，最常用，Token 即类
  2. **`useValue`**：`{ provide: 'CONFIG', useValue: { secret: 'x' } }`，注入常量或配置对象
  3. **`useFactory`**：`{ provide: Repo, useFactory: () => new Repo(...) }`，需要运行时逻辑、异步或依赖其他 Provider
  4. **`useExisting`**：`{ provide: 'Alias', useExisting: RealService }`，给同一个实例起别名
  - **非类 Token 必须 `@Inject` 指名**：Token 是字符串或 `Symbol` 时，使用方要写 `@Inject(CONFIG)` 才能对上，否则容器无从匹配
- **Provider 作用域（Scope）**
  1. **`Scope.DEFAULT`（Singleton）**：整个应用一个实例、所有请求共享，绝大多数无状态服务用它
  2. **`Scope.REQUEST`**：每个请求新建一个实例，适合绑定请求上下文（如按租户隔离）
  3. **`Scope.TRANSIENT`**：每次注入都新建实例，适合有状态、不可共享的工具类
  - **代价**：Request/Transient 绕过 Singleton 的复用，高频接口上增加创建开销，且无法被 Singleton 依赖（作用域语义冲突）
- **启动流程与循环依赖**
  - **`NestFactory.create` 的顺序**：扫描 Module 树（imports/providers/controllers）→ 收集元数据 → 建依赖关系图 → 建 IoC 容器 → 按依赖顺序实例化 → 注入 Controller 与其他 Provider → 绑路由与 Guard/Pipe → 启动 HTTP Server
  - **循环依赖会让启动直接失败**：依赖图里出现环，容器无法确定先实例化谁，要用 `forwardRef()` 打破
- **DI 报错排查三步法**（口诀：要被用先注册、要跨模块先导出、要用别人先导入）
  1. **该 Provider 是否在 `providers` 里注册**：没注册就补上
  2. **它来自别的 Module 吗、是否通过 `exports` 导出**：提供方 Module 要写 `exports: [XxxService]`
  3. **使用方 Module 是否 `imports` 了提供方 Module**：没导入就补上
  - 三步走完还报错，再检查 `emitDecoratorMetadata` 是否开启、构造参数类型是否可解析（比如用了接口而非具体类却没给 Token）

## 见 X 想 Y

现象是表相，先定位到哪一层（模块 / 容器 / 处理链 / 数据），再动手。

| 见到什么 | 该想到什么 | 一句话理由 |
| --- | --- | --- |
| 写了 `@Roles('admin')` 却没拦住请求 | 缺一个 Guard + Reflector | 装饰器只写标签，读标签的代码没写 |
| 在 Middleware 里读 `req.user.roles` 做权限 | 挪到 Guard 里去 | Middleware 拿不到 `getHandler()`，做不到路由粒度鉴权 |
| 报 `Nest can't resolve dependencies of the XxxService` | DI 排查三步法 | 没注册 / 没导出 / 没导入，三者之一 |
| `@Injectable()` 改成 `Scope.REQUEST` 后接口变慢 | 检查依赖链传染 | 上游单例会被一起拖成请求作用域，每请求重建 |
| 启动时报循环依赖，容器起不来 | `forwardRef()` | 依赖图里出现环，容器无法确定先实例化谁 |
| 库里存的 Refresh Token 能还原出明文 | 改存 SHA-256 哈希 | 拖库即失陷，Refresh Token 本来不需要可还原 |
| 一台设备登录把另一台踢下线 | 缺 AuthSession 会话表 | 单条记录覆盖式存储，无法区分设备 |
| `res.cookie` 少了 `httpOnly` | 补上，并确认 secure/sameSite | 脚本可读的 Cookie 等于把令牌交给前端 |
| Fastify 下 `app.use(cookieParser())` 报错 | 换 `@fastify/cookie` 插件 | Fastify 不兼容 Express 的 req/res |
| 定时任务注册了却从不执行 | 检查 `ScheduleModule.forRoot()` | 没导入这个模块，`@Cron` 只是死标签 |
| 生产环境配置里写着 `synchronize: true` | 立刻关掉并上迁移 | 自动同步会改甚至删表，数据丢失不可逆 |
| 文件存到了 uploads 却访问不到 URL | 配置 `useStaticAssets` | 静态目录没被注册成静态服务 |

## 易错点汇总

- **"NestJS 是更高级的 Express"**：多出来的 Guard / Pipe / Interceptor / Filter 不是装饰，各自解决一类明确的问题。搞混它们，就会出现"把权限逻辑写在中间件里"这类能跑但难维护的代码。
- **"加了 @Roles 权限就生效了"**：装饰器只往元数据里写标签，必须有一个 Guard 用 Reflector 读出来才真正拦截。标签和 Guard 要成对出现，缺一个就是玄学。
- **"Service 也是生命周期的一个阶段"**：Controller → Service → Repository 是业务调用链，框架不为它单开处理节点。框架只在 Middleware/Guard/Interceptor/Pipe/Filter 这几处插手。
- **把两套生命周期混为一谈**：`onModuleInit`/`onApplicationShutdown` 每个进程只跑几次，请求生命周期每请求跑一遍。把请求级逻辑写进应用级钩子，它只会执行一次。
- **"单例注入请求作用域的类没影响"**：作用域会沿依赖链向上传染，单例 A 注入 REQUEST 的 B 之后，A 每次请求都会重建，高频接口上代价很明显。
- **用 forwardRef 却只写了一侧**：无论服务之间还是模块之间，互相依赖的两侧都要写 `forwardRef`，只写一边不解决问题。
- **DI 报错只盯着报错那一行**：`can't resolve dependencies` 的根因常在模块边界——没注册、没导出、没导入三选一，先在模块层面查。
- **"JWT 是加密的"**：Payload 只是 Base64URL 编码，任何人都能解开。往里放密码等敏感信息等于公开，secret 泄露即可伪造任意 Token。
- **把 Refresh Token 当长一点的 JWT 存明文**：应当只存 SHA-256 哈希；另外别用 bcrypt，它只处理输入的前 72 字节，超长 Token 会被截断导致校验误判。
- **登出后以为 Access Token 立刻失效**：这是双 Token 的固有取舍——已签发的短效 Access Token 在 15m 内仍然可用。要更严就每请求查库或加用户版本号。
- **定时任务只看 @Cron 不看模块**：没导入 `ScheduleModule.forRoot()`，装饰器不会注册任何任务。排障时先确认模块导了没，再看表达式对不对。
- **生产环境留着 synchronize: true**：它会按实体自动改表结构，字段改名甚至删列都可能发生。生产一律关闭，表结构变更全走 Migration。
