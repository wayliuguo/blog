主轴只有一句：**NestJS 的价值在"组织"而不是"能力"**——它把"怎么组织一个能长期维护的后端项目"变成一套有约束的约定，本模块就是把这套约定从怎么用一直拆到为什么这样设计。

## 分篇知识点

### NestJS 入门 00-NestJS 学习地图与边界

- **排在模块五的原因**
  - 价值在"组织"而非"能力"：裸 Node.js 都能做，NestJS 只是把"如何组织可维护后端项目"变成有约束的约定
  - 先学语法只会写不会答：为什么不用 new、路由怎么来的、请求先经谁，答案都在底层 HTTP 与 Web 框架知识里
- **封装的四层**
  - 分层链：Controller → NestJS（DI / 装饰器 / 生命周期）→ Express / Fastify → Node HTTP → TCP / epoll，业务只写最上层 Controller
  - 四层各对应一个认知：DI 容器管对象创建与依赖、装饰器 + Metadata 管路由/参数/权限声明、请求生命周期管环节顺序、底层 HTTP 管报文解析与写出
- **框架的本质**：框架是一组"已认可的约定"，重点是理解每层约定解决了什么问题，而非记住多少装饰器；约定不适用时知道在哪打破
- **学习边界**：必须掌握 Module/Controller/Provider 三件套、DI、请求处理链顺序、DTO+ValidationPipe、数据库、配置日志；微服务/Fastify/动态模块知道即可；源码级/forwardRef/高级元编程踩到再学
- **学习节奏**：快速上手+DI → 模块+控制器 → 请求处理链（最关键、不能跳）→ 数据库集成算入门，再进阶实战、源码、模板
- **三个常见误区**
  1. 把 NestJS 当"更高级的 Express"：多出的 Guard/Pipe/Interceptor/Filter 各司其职，不是多几个中间件
  2. 觉得装饰器是"魔法"：只贴标签，真正干活的是运行时读标签的框架代码，`@Roles('admin')` 必须配 Guard 才生效
  3. 一上来就拆微服务：单体+清晰模块划分能撑很大规模，提前拆只引入分布式复杂度


### NestJS 入门 01-快速上手

- **四个核心特点**：内置 TypeScript（类型安全）、借鉴 Angular 架构（模块化/DI/装饰器）、底层可切换（默认 Express、可换 Fastify）、开箱即用（验证/序列化/ORM 集成）
- **项目初始化与启动**
  - 两条命令：`npm install -g @nestjs/cli` 装 CLI，`nest new my-project` 建项目，默认监听 3000
  - src/ 四个文件职责：`app.controller.ts` 处理请求、`app.module.ts` 组织代码、`app.service.ts` 承载业务、`main.ts` 是入口
  - 启动脚本：`npm run start` 单次启动，`npm run start:dev` 带热重载（开发期用后者）
- **第一个 Controller**：`@Controller('users')` 给路由前缀，`@Get()` 与 `@Get(':id')` 决定具体路径，完整路由由装饰器拼出


### NestJS 入门 02-IOC 与依赖注入

- **为什么需要 DI**：手动 `new` 紧耦合、难替换 Mock 做单测、改构造方式要改所有调用点；DI 改为在构造函数声明 `private readonly userService: UserService`，实例由容器创建并注入
- **两个装饰器与一行声明**
  - `@Injectable()` 的作用：把类登记进 DI 容器的"可注入"名单，没有它容器不认识这个类
  - 构造函数注入一行三用：`private readonly userService: UserService` 同时声明字段、类型和依赖
  - 按 Token 注入：非类依赖（如配置对象）用 `@Inject('CONFIG')` 取值
- **DI 容器装配依赖**：发现（`@Injectable` 标记）→ 分析（读构造函数参数类型）→ 递归（先创建依赖实例）→ 注入并返回（塞进构造函数）
- **三种自定义 Provider**
  1. `useClass`：`{ provide: UserService, useClass: UserService }`，Token 即类，最常用
  2. `useValue`：`{ provide: 'CONFIG', useValue: { port: 3000 } }` 注入常量或配置对象，取值配 `@Inject('CONFIG')`
  3. `useFactory`：`{ provide: 'DB_CONNECTION', useFactory: cfg => ..., inject: [ConfigService] }` 用于运行时逻辑或异步实例


### NestJS 入门 03-模块与提供器

- **@Module 基本单元**：四个字段 `imports`（导入模块）/ `controllers`（挂控制器）/ `providers`（注册服务）/ `exports`（导出给别处用）；根模块唯一，其余从它的 `imports` 递归挂载，这条链决定模块可见性
- **模块共享链条**：注册 → 导出 → 导入，提供方先 `providers` 注册再 `exports`，使用方 `imports` 引入，三步缺一就报 DI 错
- **@Global() 全局模块**：Provider 在所有模块可注入、免导入，只留给配置/日志这类真正全局的东西，不要滥用
- **动态模块**
  - `forRoot`：`static forRoot(options): DynamicModule` 让库在被导入时接收配置参数
  - `forRoot` 与 `forRootAsync`：同步直接传对象，异步用 `imports + inject + useFactory` 从 ConfigService 读配置


### NestJS 入门 04-控制器与路由

- **@Controller 与路由前缀**：`@Controller('users')` 后该控制器所有路由以 `/users` 开头；`@Get()`/`@Post()`/`@Put(':id')`/`@Delete(':id')` 分别对应查/建/改/删
- **参数装饰器**：`@Param` 取路由参数（`:id`）、`@Query` 取查询串（`?page=1`）、`@Body` 取请求体、`@Headers` 取请求头、`@Ip` 取请求 IP、`@Req` 拿原始 Request 对象
- **响应处理**：返回值自动序列化成 JSON（默认 200，不用手写响应）；`@HttpCode(201)` 自定义状态码、`@Redirect('/users', 301)` 做重定向
- **RESTful 规范**
  - 方法语义：GET 查询、POST 创建、PUT 全量替换、PATCH 部分更新、DELETE 删除
  - 命名反例：动词式路径 `/getUsers`、命名不一致 `/userList`、用 POST 做查询、把 ID 塞进查询参数


### NestJS 入门 05-请求处理链

- **请求处理链精确顺序**：Middleware → Guard → Interceptor(前) → Pipe → Controller → Service → Interceptor(后) → Response，异常统一进 Exception Filter；Service 不是生命周期阶段，Controller→Service→Repository 是业务调用链
- **两个心智模型**
  - IoC/DI 分工：IoC 是把对象创建与依赖装配控制权交给容器的思想，DI 是落地方式；Controller 只声明 `userService: UserService`，实例由容器注入
  - 装饰器与元数据分工：Decorator 写标签、`Reflect.defineMetadata` 存标签、`Reflector` 读标签；`@Roles` 本身不拦请求，须配对 Guard 读标签才生效
- **两套生命周期**：应用生命周期（`onModuleInit`/`onApplicationShutdown` 等钩子，仅进程启停时跑）与请求生命周期（Middleware→…→Response，每请求跑一遍），不要混
- **Middleware 与 Guard 差别**：Middleware 只拿 `req/res/next`，Guard 能从 `ExecutionContext` 拿 `getHandler()`/`getClass()`；只有 Guard 能按路由粒度读 `@Roles` 元数据做鉴权，所以鉴权放 Guard
- **五组件职责**：Middleware 预处理（日志/CORS/cookie/安全头）、Guard 能不能进（认证/角色）、Pipe 数据对不对（DTO 校验/类型转换）、Interceptor 包裹执行（统一响应/耗时/缓存）、Exception Filter 处理异常（统一错误响应）
- **落地写法**
  - Middleware 三种写法：类式 `NestMiddleware` 可注入、函数式更轻量，都用 `consumer.apply().forRoutes()` 绑定；`app.use()` 挂 Express 原生中间件全局生效
  - 全局注册优先用 Provider：`app.useGlobalGuards(new X())` 无法注入依赖，`{ provide: APP_GUARD, useClass: X }` 可以
  - Interceptor 包裹模型：前置逻辑在 `intercept()`，再 `return next.handle().pipe(...)`，`tap` 统计耗时、`map` 统一响应格式
  - ValidationPipe 三选项：`whitelist` 剔除 DTO 未定义字段、`forbidNonWhitelisted` 遇多余字段直接 400、`transform` 自动转类型
  - Exception Filter 两粒度：`@Catch(HttpException)` 兜指定类型、`@Catch()` 兜全部，全局注册用 `APP_FILTER` 才可注入依赖


### NestJS 入门 06-数据库集成

- **TypeORM 集成三步**：`TypeOrmModule.forRoot({ type: 'mysql', ... })` 在根模块配连接；`@Entity('users')` + `@PrimaryGeneratedColumn`/`@Column` 定义表结构；`TypeOrmModule.forFeature([User])` 在业务模块注册 Repository
- **实体关系装饰器**：一对多/多对一用 `@OneToMany`/`@ManyToOne` + `@JoinColumn({ name: 'user_id' })` 指定外键列名；多对多需一方加 `@JoinTable()`，只有这一侧在库里建中间表
- **事务用 QueryRunner**：`createQueryRunner()` → `connect()` → `startTransaction()` → manager 操作 → `commitTransaction()`，出错 `rollbackTransaction()`，finally 里 `release()`
- **synchronize 与迁移**：开发开 `synchronize: true`（按实体自动改表），生产必须关掉改用 Migration 防丢数据；`migration:generate`/`migration:run`/`migration:revert` 三条命令管生产表结构变更
- **@InjectDataSource**：事务、原生 SQL 等 Repository 覆盖不到的场景直接注入 DataSource


### NestJS 进阶 01-自定义装饰器

- **参数装饰器**：`createParamDecorator` 回调是 `(data, ctx)`，用 `ctx.switchToHttp().getRequest()` 取数据；`@CurrentUser()` 返回整个 `user`，`@CurrentUser('id')` 按字段名只返回指定字段
- **方法装饰器：打标签与读标签**：`SetMetadata` 只写标签不干活的（如 `const Roles = (...roles) => SetMetadata('roles', roles)`），权限判断留给 Guard；`Reflector.getAllAndOverride` 方法上的元数据覆盖类上的，参数顺序固定 `[getHandler(), getClass()]`
- **装饰器组合**：`applyDecorators` 把 `SetMetadata` + `UseGuards` + Swagger 装饰器合成一个 `@Auth('admin', 'editor')`，一处声明多处生效
- **ExecutionContext 四种能力**：`getType()` 判断 `http`/`rpc`/`ws`；`switchToHttp()` 取 `getRequest()`/`getResponse()`；`getClass()` 拿控制器类；`getHandler()` 拿被调用方法


### NestJS 进阶 02-作用域与循环依赖

- **三种 Provider 作用域**：`DEFAULT` 单例（整个应用一个实例，多数 Service 用它）、`REQUEST` 请求级（每请求新建，用于请求上下文）、`TRANSIENT` 瞬态（每次注入都新建，适合无状态工具类）
- **REQUEST 作用域**
  - 取请求对象：构造函数 `@Inject(REQUEST) private request: Request` 直接注入当前请求
  - 沿依赖链向上传染：单例 A 注入请求作用域的 B，A 也退化成请求作用域、每请求重建
  - 性能代价：每请求新建实例，增加构造耗时与 GC 压力，高频接口上明显
- **循环依赖用 `forwardRef` 打破**：服务间两侧都写 `@Inject(forwardRef(() => OtherService))`；模块间 `imports: [forwardRef(() => OrdersModule)]`，两处都要写
- **作用域选型**：默认优先单例，只有确实需要"每请求一份状态"时才上 `Scope.REQUEST`


### NestJS 进阶 03-登录注册实战

- **注册链路**：密码用 `bcrypt` 加盐哈希（`genSalt(10)`+`hash`）存库、登录 `compare` 比对，明文永不落库；先查 email 是否已存在抛 `ConflictException`，DTO 上 `@IsEmail`/`@MinLength`/`@Matches` 做格式校验
- **JWT 结构与信任模型**
  - 三段结构：Header（算法/类型）+ Payload（用户数据/过期）+ Signature（HMAC-SHA256 签名），用 `.` 分隔
  - Payload 仅 Base64 不是加密：任何人能解开，绝不放密码；`secret` 泄露即可伪造任意 Token
  - 与 Session 取舍：JWT 天然支持分布式、无需共享存储，代价是主动注销要额外机制（Redis 黑名单/极短过期）
  - 与 Cookie 不竞争：JWT 是凭证内容、Cookie 是保存方式，放进 HttpOnly Cookie 兼得两者
- **登录签发与放行**：`JwtService.sign(payload)` 默认 HS256，`JwtModule.register({ secret, signOptions: { expiresIn } })` 配密钥与过期；`PassportStrategy` 用 `ExtractJwt.fromAuthHeaderAsBearerToken()` 取令牌，`validate` 返回值挂 `request.user`；`@Public()` 用 `SetMetadata` 打标签、全局 Guard 用 `Reflector` 读到即放行
- **双 Token 方案**：单 Token 长则泄露危害大、短则体验差且无法主动吊销；Access Token 短（15m）只管访问业务接口，Refresh Token 长（7d）只管换发新 Access Token；刷新用 `jwtService.verify` 校验旧 Token，失败抛 401
- **HttpOnly Cookie 存 Refresh Token**：`httpOnly`（JS 读不到、不解决 XSS 本身）、`secure`（仅 HTTPS）、`sameSite: 'strict'`（缓解 CSRF）、`path: '/auth/refresh'`（缩小暴露面）、`maxAge` 7 天对齐有效期；Access Token 不进 Cookie，前端塞 `Authorization` 头
- **微信登录只换身份来源**：用 `code` 向微信换 `openid` 作唯一标识，之后 JWT 签发流程与账号密码登录完全一致


### NestJS 进阶 04-文件上传实战

- **单文件上传**：`FileInterceptor('file', {...})` 首个参数须与表单字段名一致，取参 `@UploadedFile()`；`diskStorage` 用 timestamp+随机数+`extname` 防重名与中文乱码
- **两道校验闸**
  - `limits.fileSize` 限大小（如 `2*1024*1024`），`fileFilter` 用 mimetype 正则挡非图片，拒绝传 `false` 并抛 `BadRequestException`
  - 也可写 `PipeTransform`，在 `@UploadedFile(new FileValidationPipe(10*1024*1024))` 处校验大小与 mimetype 白名单
- **多文件上传**：`FilesInterceptor('files', 10)` 第二个参数为上限数量，取参 `@UploadedFiles()` 拿数组
- **静态资源要显式开**：`app.useStaticAssets(join(...), { prefix: '/uploads/' })`，否则文件存了也访问不到
- **头像上传链路**：前端限格式大小 → 服务端验类型/大小/恶意文件 → 重命名存储 → `sharp` 缩略图(可选) → 返回 URL 存用户表 → 配静态访问


### NestJS 进阶 05-WebSocket 实时通信

- **Gateway 即 WS 层的 Controller**：`@WebSocketGateway({ cors, namespace })` 声明并注册为 provider；`handleConnection`/`handleDisconnect` 处理上下线
- **消息收发与房间**：`@WebSocketServer()` 取实例，`server.emit` 全局广播、`client.to(room).emit` 定向推；`@SubscribeMessage` 收消息，回调 `(client, payload)`，`client.join(room)` 入房
- **连接即校验身份**：令牌取自 `client.handshake.auth.token`，失败 `client.disconnect()`；通过后置 `client.data.user`，后续随取随用
- **HTTP 与 WS 共享 Service**：把 `server` 注入 `NotificationService`，HTTP 控制器也能触发 WS 广播


### NestJS 进阶 06-定时任务与队列

- **定时任务前置**：`ScheduleModule.forRoot()` 是前提，否则 `@Cron` 等只是死标签
- **三类装饰器**
  - `@Cron`：`CronExpression` 常量或 `'*/10 * * * *'` 表达式，到点执行
  - `@Timeout(n)` 只跑一次、`@Interval(n)` 按固定间隔重复
  - `SchedulerRegistry` 动态管理：`addCronJob` 加、`getCronJob(name).stop()` 停、`getCronJobs()` 列全部
- **Bull 队列**
  - 注册：`BullModule.forRoot({ redis })` + `registerQueue({ name })`；生产者 `@InjectQueue('email')` 注入 `Queue` 后 `queue.add` 投递
  - 消费者：`@Processor('email')` 标类、`@Process('verification')` 标方法，载荷在 `job.data`
  - 选项：`attempts` 重试、`backoff` 间隔、`delay` 延迟、`removeOnComplete` 完成后清理
- **选型**：固定时点/轻量间隔用 `@Cron`/`@Interval`；异步且需失败重试或延迟动作（发邮件、订单 30 分钟取消）用 Bull 队列，不阻塞主流程


### NestJS 进阶 07-微服务架构

- **两侧角色与写法**
  - 子服务：`NestFactory.createMicroservice(Module, { transport, options })` 起，`@MessagePattern({ cmd })` + `@Payload()` 收消息取代 HTTP 路由；网关用 `NestFactory.create()` 起 HTTP
  - 网关调用：`@Inject('USER_SERVICE')` 注入 `ClientProxy` 后 `client.send({ cmd }, data)` 走传输层；`ClientsModule.register` 每项 `name+transport+options`，`name` 即注入 Token
- **四种传输方式**
  1. **TCP**：点对点、简单、低延迟，内部通信与中小规模
  2. **Redis**：Pub/Sub，无需额外中间件，已有 Redis 场景
  3. **RabbitMQ**：持久化+路由灵活+ACK，需可靠投递
  4. **Kafka**：高吞吐+分区+持久化，大数据量与日志收集
- **同步异步混用**：注册创建用户走 TCP 等结果，发邮件/送积分走 RMQ 异步不阻塞，记日志再走 TCP


### NestJS 进阶 08-切换Fastify平台

- **收益**：性能约 2~3 倍（压测 ~40000 vs Express 15000 req/s），快在 JSON Schema 序列化替代 `JSON.stringify`
- **切换三处改动**
  1. **入口**：装 `@nestjs/platform-fastify` 后换 `NestFactory.create<NestFastifyApplication>(AppModule, new FastifyAdapter())`
  2. **静态/视图**：`useStaticAssets({ root, prefix })`、`setViewEngine({ engine, templates })`（写法与 Express 不同）
  3. **文件上传**：需 `app.register(contentParser)`（来自 `fastify-multer`）才能收 multipart 请求
- **中间件不兼容**：Fastify 不兼容 Express 的 `req`/`res`，`cookie-parser`/`helmet` 换 `@fastify/cookie`/`@fastify/helmet`，用 `app.register()` 注册


### NestJS 进阶 09-NestJS 源码分析

- **前置三件套**：TS 装饰器、`reflect-metadata`、`design:paramtypes`——缺一个读不懂 DI；`reflect-metadata` 隔离存元数据不污染原型；`emitDecoratorMetadata` 只对至少带一个装饰器的类生成 `paramtypes`
- **四类装饰器签名**：类 `(target)`、方法 `(target, key, descriptor)`、属性 `(target, key)`、参数 `(target, key, parameterIndex)`
- **启动链**：`new Container` → 收集 controller/provider → 读 `design:paramtypes` 递归注入 → 扫路由 → `http.createServer`；装饰器在类定义时即写元数据（`@Module`/`@Controller`/`@Get`/`@Param` 各存各自信息）
- **请求链**：路由匹配 `:param` → Guard → 参数装饰器 → Pipe → Interceptor → Handler → `res.json`；各环节按有无 `canActivate`/`transform`/`intercept` 可选执行；出口为 403/404/500
- **与真实源码差距**：最小实现手动遍历 `paramtypes`，NestJS 用 `InstanceLoader`/`ModuleScanner`/`RoutesResolver` 并额外支持作用域与循环依赖


### NestJS 进阶 10-NestJS 项目模板

- **目录结构**：src 五大块 `common`/`config`/`constants`/`modules`/`shared`；业务模块自带 `dto`/`entities`/`guards`/`services`/`strategies` + 三件套
- **配置管理**：`config/` 集中读 `.env` 给默认值，`database.config.ts` 派生 `TypeOrmModuleOptions`（`synchronize`/`logging` 仅 development 开）；`.env` 按 DB/Redis/JWT 三组给变量（`JWT_EXPIRES` 默认 2h）
- **根模块与入口**：`APP_FILTER`/`APP_INTERCEPTOR` 以 Provider 注册（可注入依赖），`main.ts` 挂 `ValidationPipe`(`whitelist`/`transform`/`forbidNonWhitelisted`)+`enableCors`+`setGlobalPrefix('api')`+Swagger
- **数据层与公共设施**
  - 实体演示主键/唯一列/`select:false` 隐藏密码/`ManyToOne` 级联删除；业务模块组合 dto/module/controller/service
  - 统一响应 `ResponseModel`+`TransformInterceptor`、统一异常 `@Catch()` 过滤器（堆栈仅 development）；`@Global()` `RedisModule` 用 `useFactory`+Token `'REDIS_CLIENT'` 全局可用
  - 健康检查查两头：`dataSource.query('SELECT 1')` 与 `redis.ping()`，任一失败置 degraded
- **上手与最佳实践**：CLI 建项目 → 装依赖 → `cp .env.example .env` → 起 MySQL/Redis → `start:dev`/`build`+`start:prod`；按功能划模块、共享下沉、基础设施进 common、全局校验/响应/异常、依赖注入


### NestJS 进阶 11-认证进阶-双Token与多设备会话

- **双 Token 分工**：单 Token 长则泄露危害大、短则体验差且无法主动吊销；Access 短(15m)放内存/`Authorization` 头管接口，Refresh 长(7d)放 HttpOnly Cookie 只管换发；Refresh 必须可服务端作废否则退化成长效 JWT
- **HttpOnly Cookie 四选项**：`httpOnly` 降 XSS 窃取(不解决 XSS)、`secure` 仅 HTTPS、`sameSite` 缓解 CSRF(跨站权衡 `lax`)、`path` 缩暴露面
- **Refresh 存储用 SHA-256 而非 bcrypt**：单向哈希入库、明文只给一次、拖库也拿不到可用 Token；bcrypt 只处理前 72 字节会截断长 Token 致哈希误判
- **AuthSession 表支持多设备**：User 1:N，每设备一条记录互不顶号；字段 `userId`/`refreshTokenHash`/`deviceId`/`userAgent`/`expiresAt`/`revoked`(软删)
- **轮换与登出**：刷新先 `revoked=true` 旧记录再签新对（偷来的旧 Token 一用即 401）；登出按 `refreshTokenHash`(单设备)或 `userId`(全设备)批量软删；Access 的 15m 窗口要么查库失无状态、要么接受高敏加黑名单
- **常见坑**
  - `verifyAsync` 记得 `await`：否则异常被吞变 500 而非 401
  - 跨域 Cookie 带不上：后端 `sameSite=lax/none`+`secure`、前端 `fetch` 带 `credentials:'include'`
  - 刷新缺过期校验：同时判断 `expiresAt>now()` 与 `revoked`
- **ORM 同层**：Prisma 仅图类型推导，`findUnique({ where: { tokenHash } })` 对应 `sessionRepo.findOne({ where: { tokenHash } })`，设计思路一致


### NestJS 进阶 12-IoC 与依赖注入原理

- **IoC 与 DI 的两层**：手动 new 整条依赖网，改动牵一发动全身；IoC 是"为何交控制权给容器"的思想，DI 是"怎么交出去"的实现
- **容器看得见依赖的前提**：装饰器 emit `design:paramtypes` → `reflect-metadata` 挂类 → 启动扫描 → 容器解析注入；`@Injectable()` 与 `emitDecoratorMetadata` 缺一不可，否则 `Nest can't resolve dependencies`
- **Provider 四种声明**
  1. **`useClass`**：Token 即类，最常用
  2. **`useValue`**：注入常量/配置对象
  3. **`useFactory`**：需运行时逻辑/异步/依赖其他 Provider
  4. **`useExisting`**：给同一实例起别名
  - 非类 Token(字符串/`Symbol`)须 `@Inject` 指名才能对上
- **作用域 Scope**
  1. **`DEFAULT`(Singleton)**：全应用一实例，无状态服务默认
  2. **`REQUEST`**：每请求新建，绑请求上下文(如租户隔离)
  3. **`TRANSIENT`**：每次注入新建，有状态不可共享工具类
  - 代价：绕过复用增创建开销，且不可被 Singleton 依赖
- **启动流程与循环依赖**：`NestFactory.create` 扫 Module 树→建依赖图→建容器→按序实例化注入→绑路由/Guard/Pipe→起 HTTP Server；依赖图成环启动直接失败，用 `forwardRef()` 打破
- **DI 报错三步法**：①该 Provider 是否注册 ②跨模块是否 `exports` 导出 ③使用方是否 `imports`；仍报错查 `emitDecoratorMetadata` 与构造参数类型是否可解析(接口没给 Token)

## 易错点汇总

- **"NestJS 是更高级的 Express"**：多出来的 Guard / Pipe / Interceptor / Filter 不是装饰，各自解决一类明确的问题。搞混它们，就会出现"把权限逻辑写在中间件里"这类能跑但难维护的代码。
- **"加了 @Roles 权限就生效了"**：装饰器只往元数据里写标签，必须有一个 Guard 用 Reflector 读出来才真正拦截。标签和 Guard 要成对出现，缺一个就是玄学。
- **"Service 也是生命周期的一个阶段"**：Controller → Service → Repository 是业务调用链，框架不为它单开处理节点。框架只在 Middleware/Guard/Interceptor/Pipe/Filter 这几处插手。
- **把两套生命周期混为一谈**：`onModuleInit`/`onApplicationShutdown` 每个进程只跑几次，请求生命周期每请求跑一遍。把请求级逻辑写进应用级钩子，它只会执行一次。
- **"单例注入请求作用域的类没影响"**：作用域会沿依赖链向上传染，单例 A 注入 REQUEST 的 B 之后，A 每次请求都会重建，高频接口上代价很明显。
- **用 forwardRef 却只写了一侧**：无论服务之间还是模块之间，互相依赖的两侧都要写 `forwardRef`，只写一边不解决问题。
- **DI 报错只盯着报错那一行**：`can't resolve dependencies` 的根因常在模块边界——没注册、没导出、没导入三选一，先在模块层面查。
- **"JWT 是加密的"**：Payload 只是 Base64URL 编码，任何人都能解开。往里放密码等敏感信息等于公开，secret 泄露即可伪造任意 Token。
- **把 Refresh Token 当长一点的 JWT 存明文**：应当只存 SHA-256 哈希；另外别用 bcrypt，它只处理输入的前 72 字节，超长 Token 会被截断导致校验误判。
- **登出后以为 Access Token 立刻失效**：这是双 Token 的固有取舍——已签发的短效 Access Token 在 15m 内仍然可用。要更严就每请求查库或加用户版本号。
- **定时任务只看 @Cron 不看模块**：没导入 `ScheduleModule.forRoot()`，装饰器不会注册任何任务。排障时先确认模块导了没，再看表达式对不对。
- **生产环境留着 synchronize: true**：它会按实体自动改表结构，字段改名甚至删列都可能发生。生产一律关闭，表结构变更全走 Migration。
