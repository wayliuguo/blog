主轴只有一句：**NestJS 的价值在"组织"而不是"能力"**——它把"怎么组织一个能长期维护的后端项目"变成一套有约束的约定，本模块就是把这套约定从怎么用一直拆到为什么这样设计。

## 分篇知识点

### NestJS 入门 00-NestJS 学习地图与边界

- **NestJS 的排位逻辑**：放在模块五（后端架构）是刻意的，它能做的事裸 Node.js 都能做，价值在"组织"而非"能力"
- **四层封装图**：Controller → NestJS（DI/装饰器/生命周期）→ Express/Fastify → Node HTTP → TCP/epoll，每层对应一个认知
- **必须掌握的清单**：Module/Controller/Provider 三件套、依赖注入、请求处理链顺序、DTO+ValidationPipe、数据库集成
- **知道怎么用即可的清单**：微服务架构、切换 Fastify、动态模块与自定义 Provider Token，业务代码很少碰
- **可以暂时跳过的清单**：源码级最小实现、`forwardRef` 循环依赖、高级装饰器元编程，踩到再回来
- **框架是一组约定**：学 NestJS 的重点不是记住有多少个装饰器，而是理解每层约定解决了什么问题、什么时候该打破它
- **三个常见误区**：把 NestJS 当"更高级的 Express"、觉得装饰器是魔法、一上来就拆微服务

### NestJS 入门 01-快速上手

- **NestJS 四个核心特点**：内置 TypeScript、借鉴 Angular（模块化/依赖注入/装饰器）、底层可切 Fastify、开箱即用
- **项目初始化两条命令**：`npm install -g @nestjs/cli` 装 CLI，`nest new my-project` 建项目，默认监听 3000
- **src/ 五个文件的职责**：`app.controller.ts` 处理请求、`app.module.ts` 组织代码、`app.service.ts` 承载业务、`main.ts` 是入口
- **第一个 Controller**：`@Controller('users')` 给出路由前缀，`@Get()` 与 `@Get(':id')` 决定具体路径
- **CLI 常用命令**：`nest g resource users` 一次生成 module/controller/service/dto/entities 全套骨架
- **两个启动脚本**：`npm run start` 单次启动，`npm run start:dev` 带热重载，开发期用后者

### NestJS 入门 02-IOC 与依赖注入

- **手动 new 的三个代价**：与实现紧耦合、没法替换 Mock 做单测、改构造方式要改所有调用点
- **@Injectable() 真正的作用**：把类登记进 DI 容器的"可被注入"名单，没有它容器根本不认识这个类
- **构造函数注入一行三用**：`private readonly userService: UserService` 同时声明了字段、类型和依赖
- **容器解析的四步流程**：发现 `@Injectable` → 分析构造参数类型 → 递归创建依赖实例 → 注入并返回
- **useClass**：`{ provide: UserService, useClass: UserService }`，Token 就是类本身，最常用的一种
- **useValue**：`{ provide: 'CONFIG', useValue: { port: 3000 } }` 注入常量或配置对象，取值要配 `@Inject('CONFIG')`
- **useFactory**：`{ provide: 'DB_CONNECTION', useFactory: cfg => ..., inject: [ConfigService] }`，用于需要运行时逻辑或异步的实例

### NestJS 入门 03-模块与提供器

- **@Module 的四个字段**：`imports` 导入别的模块、`controllers` 挂控制器、`providers` 注册服务、`exports` 导出给别处用
- **模块共享的完整链条**：提供方先 `providers` 注册再 `exports` 导出，使用方 `imports` 引入，三步缺一就报 DI 错
- **@Global() 全局模块**：Provider 在所有模块里免导入可用，只留给配置、日志这类真正全局的东西，不要滥用
- **动态模块 forRoot**：`static forRoot(options): DynamicModule` 让库在被导入时接收一份配置参数
- **forRoot 与 forRootAsync**：同步直接传对象，异步用 `imports + inject + useFactory` 从 ConfigService 读配置
- **根模块有且只有一个**：其余模块从根模块的 `imports` 开始被递归挂载，这条递归链决定了模块可见性

### NestJS 入门 04-控制器与路由

- **@Controller 是路由前缀**：`@Controller('users')` 之后该控制器所有路由都以 `/users` 开头
- **参数装饰器大全**：`@Param` 取路由参数、`@Query` 取查询串、`@Body` 取请求体、`@Headers` 取头、`@Ip` 取 IP、`@Req` 拿原始请求对象
- **返回值自动序列化**：控制器返回对象会被自动转成 JSON，默认状态码 200，不用手动写响应
- **@HttpCode 与 @Redirect**：`@HttpCode(201)` 自定义状态码，`@Redirect('/users', 301)` 做重定向
- **RESTful 方法语义**：GET 查询、POST 创建、PUT 全量替换、PATCH 部分更新、DELETE 删除
- **资源命名反例**：动词式路径 `/getUsers`、命名不一致 `/userList`、用 POST 做查询、把资源 ID 塞进查询参数

### NestJS 入门 05-请求处理链

- **请求处理链的精确顺序**：Middleware → Guard → Interceptor(前) → Pipe → Handler → Interceptor(后) → 异常统一进 Exception Filter
- **Middleware 与 Guard 的本质差别**：Middleware 只拿到 `req/res/next`，Guard 能从 ExecutionContext 拿到 `getHandler()` 与 `getClass()`
- **鉴权为什么放 Guard**：只有 Guard 能拿到"即将执行的 Handler"，配合 Reflector 才能读方法上的 `@Roles` 元数据
- **装饰器与元数据的分工**：Decorator 负责写标签、`Reflect.defineMetadata` 负责存标签、Reflector 负责读标签
- **@Roles 本身不拦请求**：它只是声明，必须成对写一个 Guard 去读这个标签，权限校验才真正生效
- **两套生命周期别混**：应用生命周期（`onModuleInit`/`onApplicationShutdown`）每进程只跑几次，请求生命周期每请求跑一遍
- **Service 不是生命周期阶段**：Controller → Service → Repository 是业务调用链，框架不会为它单开处理节点
- **五组件职责口诀**：Middleware 预处理、Guard 能不能进、Pipe 数据对不对、Interceptor 包裹执行、Filter 出错怎么办
- **全局注册优先用 Provider**：`app.useGlobalGuards(new X())` 无法注入依赖，`{ provide: APP_GUARD, useClass: X }` 可以
- **ValidationPipe 三个关键选项**：`whitelist` 剔除 DTO 未定义字段、`forbidNonWhitelisted` 遇到多余字段直接 400、`transform` 自动转类型

### NestJS 入门 06-数据库集成

- **TypeORM 集成三步**：`TypeOrmModule.forRoot()` 建连接、`@Entity` 定义表、`forFeature([User])` 为该模块注册 Repository
- **synchronize 只在开发开**：`synchronize: true` 会按实体自动改表结构，生产必须关掉并改用 Migration
- **实体关系装饰器**：`@OneToMany`/`@ManyToOne` 配 `@JoinColumn({ name: 'user_id' })` 指定外键列名，`@ManyToMany` 需要一方加 `@JoinTable()`
- **多对多的维护方**：只有加了 `@JoinTable()` 的那一侧会在库里建中间表，另一方只声明反向关系
- **事务用 QueryRunner**：`createQueryRunner()` → `connect()` → `startTransaction()` → manager 操作 → `commitTransaction()`，出错 `rollbackTransaction()`，finally 里 `release()`
- **迁移三条命令**：`migration:generate` 生成、`migration:run` 执行、`migration:revert` 回滚，生产表结构变更全靠它
- **@InjectDataSource 注入 DataSource**：事务、原生 SQL 这类 Repository 覆盖不到的场景直接用它

### NestJS 进阶 01-自定义装饰器

- **createParamDecorator 造参数装饰器**：回调签名 `(data, ctx)`，从 `ctx.switchToHttp().getRequest()` 里取需要的数据
- **@CurrentUser() 的两种用法**：`@CurrentUser()` 返回整个 user 对象，`@CurrentUser('id')` 只返回指定字段
- **SetMetadata 造方法装饰器**：`const Roles = (...roles) => SetMetadata('roles', roles)`，只写标签不干任何活
- **Reflector.getAllAndOverride 的优先级**：方法上的元数据覆盖类上的，参数顺序写成 `[context.getHandler(), context.getClass()]`
- **applyDecorators 做装饰器组合**：把 `SetMetadata` + `UseGuards` + Swagger 装饰器合成一个 `@Auth('admin')`，一处声明多处生效
- **ExecutionContext 的四种能力**：`getType()` 判 http/rpc/ws、`switchToHttp()` 取 req/res、`getClass()` 拿控制器类、`getHandler()` 拿具体方法

### NestJS 进阶 02-作用域与循环依赖

- **三种 Provider 作用域**：`DEFAULT` 单例全局共享、`REQUEST` 每请求一个新实例、`TRANSIENT` 每次注入都新建
- **REQUEST 作用域怎么拿到请求对象**：构造函数里 `@Inject(REQUEST) private request: Request` 直接注入当前请求
- **作用域会沿依赖链向上传染**：单例 A 注入了请求作用域的 B，A 也会退化成请求作用域，每请求重建
- **请求作用域的性能代价**：每请求新建实例，增加构造耗时与 GC 压力，高频接口上代价明显
- **服务间循环依赖用 forwardRef**：互相依赖的两侧都要写 `@Inject(forwardRef(() => OtherService))`
- **模块间循环依赖同样要 forwardRef**：`imports: [forwardRef(() => OrdersModule)]`，两个模块里都要写
- **默认优先单例**：只有确实需要"每请求一份状态"时才上 REQUEST，其余一律保持默认

### NestJS 进阶 03-登录注册实战

- **密码加密用 bcrypt**：`genSalt(10)` 生成盐再 `hash` 存库，登录用 `compare` 比对，明文密码永不落库
- **注册要防重与强度校验**：先查 email 是否已存在并抛 `ConflictException`，DTO 上用 `@IsEmail`/`@Matches` 限制格式
- **JWT 三段结构**：Header（算法与类型）+ Payload（用户数据与过期时间）+ Signature（HMAC-SHA256 签名），中间用点分隔
- **Payload 只是 Base64 不是加密**：任何人都能解开，绝不能放密码等敏感信息；secret 泄露即可伪造任意 Token
- **JWT 与 Session 的取舍**：JWT 天然支持分布式、无需共享存储，代价是主动注销要额外机制（黑名单或极短过期）
- **JWT 与 Cookie 不是竞争关系**：JWT 是凭证内容、Cookie 是保存方式，把 JWT 放进 HttpOnly Cookie 能兼得两者
- **@Public() 跳过全局鉴权**：用 `SetMetadata(IS_PUBLIC_KEY, true)` 打标签，全局 Guard 里用 Reflector 读到就放行
- **微信小程序登录只换身份来源**：用 code 向微信换 openid 作唯一标识，之后的 JWT 签发流程与账号密码登录完全一致

### NestJS 进阶 04-文件上传实战

- **FileInterceptor 接单文件**：`@UseInterceptors(FileInterceptor('file', {...}))`，第一个参数必须与前端表单字段名一致
- **diskStorage 自定义落盘**：`destination` 定目录，`filename` 回调里用时间戳加随机数再加 `extname`，避免重名与中文乱码
- **limits 与 fileFilter 两道闸**：`limits.fileSize` 限大小，`fileFilter` 用 mimetype 正则挡掉非图片，拒绝时回调传 `false`
- **FilesInterceptor 接多文件**：`FilesInterceptor('files', 10)` 第二个参数是最大数量，取参用 `@UploadedFiles()` 拿数组
- **文件也能被管道校验**：写一个 `PipeTransform` 实现类，在 `@UploadedFile(new FileValidationPipe(10 * 1024 * 1024))` 处传入
- **静态资源要显式开**：Express 下 `app.useStaticAssets(join(...), { prefix: '/uploads/' })`，否则文件存了也访问不到
- **头像上传的完整流程**：前端限格式 → 服务端验类型大小 → 重命名存储 → 可选生成缩略图 → 返回 URL 存入用户表

### NestJS 进阶 05-WebSocket 实时通信

- **Gateway 就是 WebSocket 层的 Controller**：`@WebSocketGateway({ cors, namespace })` 声明，并且要作为 provider 写进模块
- **两个连接钩子**：实现 `OnGatewayConnection` 的 `handleConnection` 与 `OnGatewayDisconnect` 的 `handleDisconnect`
- **@WebSocketServer() 拿到服务端实例**：`server.emit` 全局广播，`client.to(room).emit` 定向推送给房间
- **@SubscribeMessage 处理客户端消息**：回调签名 `(client, payload)`，房间用 `client.join(room)` 加入
- **连接时就要校验 token**：从 `client.handshake.auth.token` 取令牌，验证失败直接 `client.disconnect()` 断开
- **用户信息挂在 client.data 上**：验证通过后 `client.data.user = user`，后续的消息处理器里随取随用
- **HTTP 与 WS 共享同一个 Service**：把 server 注入 NotificationService，HTTP 控制器也能触发 WebSocket 广播

### NestJS 进阶 06-定时任务与队列

- **ScheduleModule.forRoot() 是前提**：不导入这个模块，`@Cron` 装饰器不会注册任何任务，只是死标签
- **@Cron 两种写法**：用 `CronExpression.EVERY_DAY_AT_2AM` 这类常量，或直接写 `'*/10 * * * *'` 表达式
- **@Timeout 与 @Interval 的区别**：Timeout 是只跑一次的延迟任务，Interval 是按固定间隔重复执行
- **SchedulerRegistry 动态管理任务**：`addCronJob` 加、`getCronJob(name).stop()` 停、`getCronJobs()` 列出全部
- **Bull 队列由生产者与消费者构成**：`@InjectQueue('email')` 往队列加任务，`@Processor('email')` + `@Process('verification')` 处理任务
- **队列的重试与延迟选项**：`attempts` 重试次数、`backoff` 重试间隔、`delay` 延迟执行、`removeOnComplete` 完成后清理记录
- **选型口诀**：固定时间点执行用 `@Cron`，异步且要失败重试用队列，订单超时取消用 Bull 的延迟任务

### NestJS 进阶 07-微服务架构

- **微服务有两种启动方式**：`NestFactory.createMicroservice()` 起子服务，`NestFactory.create()` 起 HTTP 网关
- **@MessagePattern 定义消息处理器**：`@MessagePattern({ cmd: 'get_user' })` 配 `@Payload()` 读参数，取代 HTTP 路由
- **网关用 ClientProxy 发起调用**：`@Inject('USER_SERVICE')` 注入后 `client.send({ cmd }, data)` 走传输层调下游
- **ClientsModule.register 声明下游服务**：每个服务一项 `name + transport + options`，`name` 就是注入时用的 Token
- **四种传输方式的权衡**：TCP 点对点低延迟、Redis 基于 Pub/Sub 免额外中间件、RabbitMQ 支持可靠投递与路由、Kafka 高吞吐
- **同步与异步要混用**：注册流程里创建用户走 TCP 等结果，发邮件、加积分走 RMQ 异步，不阻塞主流程

### NestJS 进阶 08-切换Fastify平台

- **Fastify 快 2~3 倍**：内置 JSON Schema 序列化替代 `JSON.stringify`，压测约 40000 req/s 对比 Express 的 15000 req/s
- **切换只改入口**：装 `@nestjs/platform-fastify` 后换成 `NestFactory.create<NestFastifyApplication>(AppModule, new FastifyAdapter())`
- **静态资源写法不同**：Express 是 `useStaticAssets(path, { prefix })`，Fastify 是 `useStaticAssets({ root, prefix })`
- **文件上传要额外注册解析器**：Fastify 下需要 `app.register(contentParser)` 才能接收 multipart 请求
- **Express 中间件不能直接搬**：Fastify 不兼容 Express 的 req/res，`cookie-parser`/`helmet` 要换成 `@fastify/cookie`、`@fastify/helmet`

### NestJS 进阶 09-NestJS 源码分析

- **前置知识三件套**：TypeScript 装饰器、reflect-metadata、`design:paramtypes`，缺一个就读不懂依赖注入
- **四类装饰器的签名**：类 `(target)`、方法 `(target, key, descriptor)`、属性 `(target, key)`、参数 `(target, key, parameterIndex)`
- **reflect-metadata 的意义**：用 `Reflect.defineMetadata`/`getMetadata` 隔离存储元数据，不像 `target._x = x` 那样污染类原型
- **design:paramtypes 怎么被读到**：开启 `emitDecoratorMetadata` 后编译产物带上构造参数类型，容器靠它知道该注入什么
- **元数据生成有前提**：`emitDecoratorMetadata` 只对**至少有一个装饰器**的类生效，没装饰器就没有 paramtypes
- **启动调用链**：`new Container` → 递归收集模块的 controller/provider → `resolve()` 读 paramtypes 递归注入 → 扫路由 → `createServer`
- **请求调用链**：路由正则匹配 `:param` → Guard → 解析参数装饰器 → Pipe → Interceptor → Handler → 统一 `res.json`
- **与真实源码的差距**：最小实现手动遍历 paramtypes，NestJS 用 `InstanceLoader`/`ModuleScanner`/`RoutesResolver`，并额外支持作用域与循环依赖

### NestJS 进阶 10-NestJS 项目模板

- **src 五大块划分**：`common` 公共基础设施、`config` 配置、`constants` 常量、`modules` 按业务分模块、`shared` 共享第三方服务
- **模块内部自成一体**：每个业务模块自带 `dto`/`entities`/`guards`/`services`/`strategies` 加 controller、module、service 三件套
- **配置集中在 config/**：`index.ts` 读 `.env` 并给每项默认值，`database.config.ts` 由它派生出 `TypeOrmModuleOptions`
- **全局装配写在根模块**：`APP_FILTER`/`APP_INTERCEPTOR`/`APP_PIPE` 用 Provider 方式注册，这样才能注入依赖
- **统一响应与统一异常**：`ResponseModel` + `TransformInterceptor` 包装返回值，`@Catch()` 过滤器兜住所有异常并记录日志
- **@Global() 的 RedisModule**：用 `useFactory` 加自定义 Token `'REDIS_CLIENT'` 提供客户端，`exports` 后全局可用
- **健康检查查两头**：`/health` 里分别跑 `dataSource.query('SELECT 1')` 与 `redis.ping()`，任一失败就把状态改成 degraded
- **最佳实践七条**：按功能划分模块、共享模块下沉、基础设施进 common、全局校验、统一响应、统一异常、依赖注入

### NestJS 进阶 11-认证进阶-双Token与多设备会话

- **单 Token 的死穴**：有效期长则泄露危害大、短则体验差，且客户端存不住、服务端管不了（无法主动吊销），所以要拆成双 Token
- **Cookie 四个选项的边界**：`httpOnly` 挡 XSS 窃取但不解决 XSS 本身，`secure` 防明文抓包，`sameSite` 缓解 CSRF，`path` 缩小暴露面
- **Refresh Token 必须哈希入库**：用 SHA-256 单向哈希存库，明文只在响应里给客户端一次，拖库也拿不到可用 Token
- **别用 bcrypt 存长 Token**：bcrypt 只处理输入的前 72 字节，超长 Token 会被截断，导致不同 Token 哈希相同、校验误判
- **AuthSession 表支持多设备**：User 1:N AuthSession，关键字段是 `userId`、`refreshTokenHash`、`deviceId`、`expiresAt`、`revoked`
- **轮换做到"重放即失效"**：每次刷新先把旧记录 `revoked = true` 再签新的一对，偷来的旧 Token 一用就 401
- **登出就是会话作废**：单设备按 `refreshTokenHash` 更新，全设备按 `userId` 批量置 `revoked`，都是软删除
- **Prisma 与 TypeORM 同层**：本篇用 Prisma 只是图类型推导完整，哈希入库、轮换、多设备登出的设计思路完全一致

### NestJS 进阶 12-IoC 与依赖注入原理

- **没有 IoC 的代价**：手动 new 出整条依赖网，改一个构造参数上层全要跟着改，越写越乱
- **IoC 与 DI 是两个层面**：IoC 是"为什么把控制权交给容器"的思想，DI 是"怎么交出去"的具体实现方式
- **注入链路的完整路径**：装饰器编译期 emit `design:paramtypes` → reflect-metadata 挂到类上 → 启动扫描 → 容器解析实例化 → 注入使用方
- **@Injectable 与 emitDecoratorMetadata 缺一不可**：前者让零件进"可注入"名单，后者让容器看得见零件类型，否则报 can't resolve dependencies
- **四种 Provider 声明方式**：`useClass` 类作 Token、`useValue` 注入常量、`useFactory` 需要运行时逻辑、`useExisting` 给同一实例起别名
- **非类 Token 必须 @Inject 指名**：Token 是字符串或 Symbol 时，使用方要写 `@Inject(CONFIG)` 才能对上，否则容器无从匹配
- **启动流程的文字图**：扫描 Module 树 → 收集元数据 → 建依赖关系图 → 建 IoC 容器 → 按依赖顺序实例化 → 注入 → 绑路由与 Guard → 监听端口
- **DI 报错排查三步法**：该 Provider 在 providers 里注册了吗 → 跨模块时导出/导入了吗 → 提供方 `exports` 与使用方 `imports` 是否配对

## 易错点汇总

- **"NestJS 是更高级的 Express"**：多出来的 Guard / Pipe / Interceptor / Filter 不是装饰，各自解决一类明确的问题。搞混它们，就会出现"把权限逻辑写在中间件里"这类能跑但难维护的代码。
- **"加了 @Roles 权限就生效了"**：装饰器只往元数据里写标签，必须有一个 Guard 用 Reflector 读出来才真正拦截。标签和 Guard 要成对出现，缺一个就是玄学。
- **"Service 也是生命周期的一个阶段"**：Controller → Service → Repository 是业务调用链，框架不为它单开处理节点。框架只在 Middleware/Guard/Interceptor/Pipe/Filter 这几处插手。
- **把两套生命周期混为一谈**：`onModuleInit`/`onApplicationShutdown` 每个进程只跑几次，请求生命周期每请求跑一遍。把请求级逻辑写进应用级钩子，它只会执行一次。
- **"单例注入请求作用域的类没影响"**：作用域会沿依赖链向上传染，单例 A 注入 REQUEST 的 B 之后，A 每次请求都会重建，高频接口上代价很明显。
- **用 forwardRef 却只写了一侧**：无论服务之间还是模块之间，互相依赖的两侧都要写 `forwardRef`，只写一边不解决问题。
- **DI 报错只盯着报错那一行**：`can't resolve dependencies` 的根因常在模块边界——没注册、没导出、没导入三选一，先在模块层面查。
- **"JWT 是加密的"**：Payload 只是 Base64URL 编码，任何人都能解开。往里放密码等敏感信息等于公开，secret 泄露即可伪造任意 Token。
- **把 Refresh Token 当长一点的 JWT 存明文**：应当只存 SHA-256 哈希；另外别用 bcrypt，它只处理输入的前 72 字节，超长 Token 会被截断导致校验误判。
- **登出后以为 Access Token 立刻失效**：这是双 Token 的固有取舍——已签发的短效 Access Token 在 15m 内仍然可用。要更严就每请求查库或加用户版本号。
- **定时任务只看 @Cron 不看模块**：没导入 `ScheduleModule.forRoot()`，装饰器不会注册任何任务。排障时先确认模块导了没，再看表达式对不对。
- **生产环境留着 synchronize: true**：它会按实体自动改表结构，字段改名甚至删列都可能发生。生产一律关闭，表结构变更全走 Migration。
