# 请求处理链

> 一个请求从进入到返回，会经过 NestJS 的请求处理链。理解这条链，关键是先建立两个心智模型：依赖是从哪来的（IoC/DI），以及"标签"是如何被写下来又被读走的（Decorator/Metadata）。
> 承上：[控制器与路由](./04-控制器与路由) —— 先会写路由，才有"一个请求进来后依次经过哪些环节"的参照；以及 [HTTP 与 HTTPS 深入](../03-网络编程与实时通信/02-HTTP%20与%20HTTPS%20深入) —— req/res 本质是流，不懂报文解析就看不透中间件/守卫插手的时机
> 启下：[数据库集成](./06-数据库集成) —— 用 TypeOrmModule 连上 MySQL、定义 Entity 与 Repository，并在 Service 里完成一次真实的 CRUD

## 请求处理流程总览

```
请求到达
    ↓
Middleware（中间件）→ 日志、CORS
    ↓
Guard（守卫）→ 是否允许访问（身份验证）
    ↓
Interceptor（拦截器）→ 请求前处理
    ↓
Pipe（管道）→ 参数校验与转换
    ↓
Handler（控制器方法）→ 执行业务逻辑
    ↓
Interceptor（拦截器）→ 响应后处理
    ↓
Exception Filter（异常过滤器）→ 统一错误处理
    ↓
返回响应
```

## 核心心智模型：IoC 与 DI —— 为什么 Controller 里不需要 new

刚从前端转过来的同学最常见的困惑是：在 Controller 里写 `private readonly userService: UserService`，从来没有 `new UserService()`，为什么它就能直接用？

这是因为 NestJS 帮你完成了对象的创建与装配。这套机制要拆成两层理解：

> **IoC（Inversion of Control，控制反转）是一种思想**：把"对象创建"和"依赖管理"的控制权，从写业务代码的人手里，交还给框架容器。你不再主动 `new`，而是声明"我需要什么"，由容器决定何时创建、如何组装。
>
> **DI（Dependency Injection，依赖注入）是这种思想的实现方式**：容器先把依赖（UserService）创建好，再通过构造函数"注入"给使用者（Controller）。

对照一下就清楚了：

```typescript
// 没有 IoC：自己 new，自己管依赖，依赖越多关系越乱
const repo = new UserRepository()
const service = new UserService(repo)   // 你手动组装整条依赖链
const controller = new UserController(service)

// 有 NestJS：只声明类型，容器负责创建和注入
@Controller('users')
export class UserController {
    // 声明"我需要一个 UserService"，容器会造好并塞进来
    constructor(private readonly userService: UserService) {}
}
```

`private readonly userService: UserService` 这一行同时做了三件事：声明字段、声明类型、声明依赖。NestJS 在启动时扫描到这个类型，就去容器里找 `UserService` 的实例注入进来。所以**你写的不是"创建"，而是"声明需要"**。关于这套机制如何运作，进阶阅读见 [IoC 与依赖注入原理](../08-NestJS%20进阶/12-IoC%20与依赖注入原理)。

## 装饰器与元数据：标签的"写"与"读"

NestJS 大量使用装饰器（`@Get()`、`@Roles('admin')`、`@UseGuards()`），要把它们和"业务数据"区分开。这里有一套清晰的分工：

> **Decorator（装饰器）负责"写标签"**：给类 / 方法 / 参数贴上一个标记，比如"这个路由需要 admin 角色"。
> **Metadata（元数据）负责"存标签"**：装饰器内部调用 `Reflect.defineMetadata`，把标签存进一个与该类/方法绑定的元数据表里。
> **NestJS / Guard 负责"读标签"**：运行时用 `Reflector` 把标签读出来，决定该怎么处理。

关键区分：**业务数据是请求里携带的（req.body、req.user），元数据是框架层面预先定义好的（角色、是否需要鉴权等）**，两者互不直接耦合。

```typescript
// 写标签：定义一个装饰器，仅做声明，本身不校验任何东西
import { SetMetadata } from '@nestjs/common'

export const ROLES_KEY = 'roles'
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles)

// 贴标签：只声明"需要 admin"，但此刻什么都不发生
@Roles('admin')
@Get('admin/dashboard')
getDashboard() {}

// 读标签：Guard 里用 Reflector 读出来，真正做校验
@Injectable()
export class RolesGuard implements CanActivate {
    constructor(private reflector: Reflector) {}

    canActivate(context: ExecutionContext): boolean {
        const requiredRoles = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
            context.getHandler(),
            context.getClass(),
        ])
        if (!requiredRoles) return true
        const { user } = context.switchToHttp().getRequest()
        return requiredRoles.some(role => user.roles?.includes(role))
    }
}
```

注意：`@Roles('admin')` 只是"声明"，它自己不会拦请求。**必须有一个 Guard 配合 Reflector 去读这个标签，权限校验才真正生效**。这也是为什么写框架代码时，装饰器和 Guard 要成对出现。

## 请求生命周期的精确顺序

"中间件先执行还是守卫先执行？"——这是面试高频题。精确顺序是固定的：

```
Middleware
  → Guard            （能不能进）
    → Interceptor(before)   （进入前包裹逻辑）
      → Pipe       （参数校验/转换）
        → Controller        （控制器方法）
          → Service → Repository  （业务调用链，非框架阶段）
        → Interceptor(after)    （返回后包裹逻辑）
  → HTTP Response
异常：任意环节抛出 → Exception Filter 统一兜底
```

> 一个常被混淆的点：**Service 不是框架生命周期的一个"阶段"，而是业务调用链（Controller → Service → Repository）的一部分**。请求链路描述的是"框架在什么时候插手"，而 Service 是你业务逻辑内部的方法调用，框架不会为它单独开一个处理节点。

## 两套"生命周期"不要混为一谈

NestJS 里其实有两套完全不同的生命周期，名字都带"生命周期"，但描述的是不同维度：

| 维度 | 名称 | 触发时机 | 典型钩子 |
|------|------|----------|----------|
| 应用级 | 应用生命周期 | 整个进程启动 / 关闭时，每个请求**不会**触发 | `onModuleInit` / `onApplicationBootstrap` / `onModuleDestroy` / `beforeApplicationShutdown` / `onApplicationShutdown` |
| 请求级 | 请求生命周期 | 每一个 HTTP 请求到达时 | 上节的 Middleware → Guard → … → Response |

```typescript
@Injectable()
export class UserService implements OnModuleInit, OnApplicationShutdown {
    async onModuleInit() {
        // 应用启动时执行一次：建立连接池、预热缓存等
        console.log('UserService 初始化')
    }

    async onApplicationShutdown(signal: string) {
        // 进程关闭时执行一次：释放连接、落盘等
        console.log('收到关闭信号', signal)
    }
}
```

> 应用生命周期钩子适合做"启动/关闭时的一次性资源操作"；请求生命周期是一条请求的处理管道。前者每个进程只跑几次，后者每次请求都跑一遍。

## ExecutionContext：为什么 Guard 比 Middleware 更强

同样是"进门前的检查"，Guard 通常比 Middleware 更受推荐，根子在于 `ExecutionContext`。

Middleware 拿到的只有 `req / res / next`，它**不知道当前请求会落到哪个 Controller、哪个方法**。而 Guard 的 `canActivate(context: ExecutionContext)` 能拿到：

```typescript
@Injectable()
export class AuthGuard implements CanActivate {
    canActivate(context: ExecutionContext): boolean {
        // 拿到当前 HTTP 请求对象
        const request = context.switchToHttp().getRequest()

        // 关键能力：拿到"即将执行的 Handler"和"所属 Controller 类"
        const handler = context.getHandler()   // 具体的方法（如 getDashboard）
        const controllerClass = context.getClass()  // 所属的 Controller 类

        // 因为能拿到 handler，才能配合 Reflector 读取方法上的元数据
        // 例如 @Roles('admin') 的标签 → 实现"按路由粒度"的权限判断
        return this.checkPermission(request, handler)
    }
}
```

| 能力 | Middleware | Guard |
|------|-----------|-------|
| 读取请求/响应 | 能 | 能（`switchToHttp().getRequest()`） |
| 知道当前是哪个 Handler | 不能 | 能（`getHandler()`） |
| 读取 Handler 上的元数据（如 `@Roles`） | 不能 | 能（`Reflector` + `getHandler()`） |
| 按路由粒度做权限 | 难 | 易 |

> 一句话：**Middleware 站在"门外"，只看见进来的流量；Guard 站在"门口"，还知道你要进哪扇门、门上贴了什么标签**。所以基于装饰器元数据的鉴权，几乎总是放在 Guard 里。

## 各组件职责口诀

记不住谁干什么时，用下面这张表当速查：

| 组件 | 职责口诀 | 回答的核心问题 | 典型场景 |
|------|----------|----------------|----------|
| Middleware | 预处理 | 进来之前先做什么？ | 日志、CORS、cookie 解析、安全头 |
| Guard | 能不能进 | 这个请求有权限吗？ | 身份认证、角色校验 |
| Pipe | 数据对不对 | 参数合法、类型对吗？ | DTO 校验、类型转换、分页范围 |
| Interceptor | 包裹执行 | 进出前后还要做点什么？ | 统一响应格式、耗时统计、缓存 |
| Exception Filter | 处理异常 | 出错了怎么返回？ | 统一错误响应 |

## 中间件（Middleware）

中间件函数在请求到达路由之前执行，与 Express 中间件一致。

### 方式一：类式中间件（可注入依赖）

```typescript
import { Injectable, NestMiddleware, MiddlewareConsumer, Module, NestModule } from '@nestjs/common'
import { Request, Response, NextFunction } from 'express'

@Injectable()
export class LoggerMiddleware implements NestMiddleware {
    use(req: Request, res: Response, next: NextFunction) {
        console.log(`${req.method} ${req.url}`)
        next()
    }
}

// 在模块中配置
@Module({
    providers: [LoggerMiddleware]
})
export class AppModule implements NestModule {
    configure(consumer: MiddlewareConsumer) {
        consumer
            .apply(LoggerMiddleware)
            .forRoutes('*')  // 对所有路由生效
    }
}
```

### 方式二：函数式中间件（无依赖注入，更轻量）

```typescript
import { Request, Response, NextFunction } from 'express'

// 纯函数，不需要 @Injectable()
export function logger(req: Request, res: Response, next: NextFunction) {
    console.log(`${req.method} ${req.url}`)
    next()
}

// 在模块中直接应用（无需注册 provider）
@Module({})
export class AppModule implements NestModule {
    configure(consumer: MiddlewareConsumer) {
        consumer
            .apply(logger)  // 直接传函数引用
            .forRoutes('*')
    }
}
```

### 方式三：Express 原生中间件（在 main.ts 中全局使用）

```typescript
// main.ts
import { NestFactory } from '@nestjs/core'
import { AppModule } from './app.module'
import * as cookieParser from 'cookie-parser'
import * as helmet from 'helmet'

async function bootstrap() {
    const app = await NestFactory.create(AppModule)

    // Express 原生中间件（绕过 Nest 管道，全局生效）
    app.use(cookieParser())
    app.use(helmet())

    await app.listen(3000)
}
```

**使用场景**：请求日志、CORS、静态文件处理、cookie 解析、安全头设置。

## 守卫（Guard）

守卫决定请求是否放行，返回 `true` 放行，`false` 拒绝。

```typescript
import { Injectable, CanActivate, ExecutionContext } from '@nestjs/common'
import { Observable } from 'rxjs'

@Injectable()
export class AuthGuard implements CanActivate {
    canActivate(context: ExecutionContext): boolean | Promise<boolean> | Observable<boolean> {
        const request = context.switchToHttp().getRequest()
        const token = request.headers.authorization

        if (!token) return false

        // 验证 token...
        return true
    }
}
```

### 使用方式

```typescript
// 方式一：路由级别（@UseGuards）
@Controller('users')
@UseGuards(AuthGuard)          // 整个控制器需要登录
export class UserController {
    @Get()
    @UseGuards(AuthGuard)      // 或只对某个路由生效
    findAll() {}
}

// 方式二：全局注册（main.ts）
async function bootstrap() {
    const app = await NestFactory.create(AppModule)
    app.useGlobalGuards(new AuthGuard())  // 全局生效，但无法注入依赖
    await app.listen(3000)
}

// 方式三：全局注册（Provider 推荐）
import { APP_GUARD } from '@nestjs/core'

@Module({
    providers: [
        {
            provide: APP_GUARD,
            useClass: AuthGuard,
        }
    ]
})
export class AppModule {}
```

**使用场景**：身份验证、权限检查。

## 拦截器（Interceptor）

拦截器可以在请求处理**前后**执行逻辑，实现 `NestInterceptor` 接口。

### 基础示例

```typescript
import { Injectable, NestInterceptor, ExecutionContext, CallHandler } from '@nestjs/common'
import { Observable } from 'rxjs'
import { tap } from 'rxjs/operators'

@Injectable()
export class LoggingInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        console.log('请求前...')

        return next.handle().pipe(
            tap(data => console.log('请求后...', data))
        )
    }
}
```

### 统一响应格式

```typescript
import { Injectable, NestInterceptor, ExecutionContext, CallHandler } from '@nestjs/common'
import { Observable } from 'rxjs'
import { map } from 'rxjs/operators'

export interface ApiResponse<T> {
    code: number
    data: T
    message: string
}

@Injectable()
export class TransformInterceptor<T> implements NestInterceptor<T, ApiResponse<T>> {
    intercept(context: ExecutionContext, next: CallHandler): Observable<ApiResponse<T>> {
        return next.handle().pipe(
            map(data => ({
                code: 0,
                data,
                message: 'success'
            }))
        )
    }
}
```

### 请求耗时统计

```typescript
@Injectable()
export class TimingInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        const start = Date.now()

        return next.handle().pipe(
            tap(() => {
                const duration = Date.now() - start
                console.log(`请求耗时: ${duration}ms`)
            })
        )
    }
}
```

### 使用方式

```typescript
// 方式一：路由级别（@UseInterceptors）
@Controller('users')
@UseInterceptors(TransformInterceptor)
export class UserController {
    @Get()
    @UseInterceptors(TimingInterceptor)  // 可叠加多个
    findAll() {}
}

// 方式二：全局注册（main.ts）
async function bootstrap() {
    const app = await NestFactory.create(AppModule)
    app.useGlobalInterceptors(new TransformInterceptor())
    // 缺点：无法注入依赖
    await app.listen(3000)
}

// 方式三：全局注册（Provider 推荐）
import { APP_INTERCEPTOR } from '@nestjs/core'

@Module({
    providers: [
        {
            provide: APP_INTERCEPTOR,
            useClass: TransformInterceptor,
        },
        {
            provide: APP_INTERCEPTOR,
            useClass: TimingInterceptor,
        }
    ]
})
export class AppModule {}
```

**使用场景**：统一响应格式、请求耗时统计、缓存。

## 管道（Pipe）

管道对传入的参数进行转换或校验。

### 内置管道

```typescript
@Get(':id')
findOne(
    @Param('id', ParseIntPipe) id: number,  // 将字符串 "1" 转为数字 1
) {}

@Get()
findAll(
    @Query('page', DefaultValuePipe(1), ParseIntPipe) page: number,  // 默认值 + 类型转换
) {}
```

**常用内置管道**：

| 管道 | 作用 |
|------|------|
| `ValidationPipe` | 基于 DTO 的声明式校验 |
| `ParseIntPipe` | 字符串转整数 |
| `ParseFloatPipe` | 字符串转浮点数 |
| `ParseBoolPipe` | 字符串转布尔值 |
| `DefaultValuePipe` | 设置默认值 |

### DTO 与 class-validator

DTO（Data Transfer Object）用于定义请求体的结构，配合 `class-validator` 实现声明式校验。

```bash
npm install class-validator class-transformer
```

```typescript
import { IsString, IsInt, IsOptional, Min, Max, IsEmail } from 'class-validator'

export class CreateUserDto {
    @IsString({ message: '姓名必须是字符串' })
    @MinLength(2, { message: '姓名至少 2 个字符' })
    @MaxLength(50)
    name: string

    @IsInt()
    @Min(0)
    @Max(150)
    age: number

    @IsEmail({}, { message: '邮箱格式不正确' })
    email: string

    @IsOptional()
    @IsString()
    phone?: string
}
```

### 自定义管道

```typescript
import { PipeTransform, Injectable, BadRequestException } from '@nestjs/common'

@Injectable()
export class ParseIdPipe implements PipeTransform {
    transform(value: string) {
        const id = parseInt(value, 10)
        if (isNaN(id) || id <= 0) {
            throw new BadRequestException('ID 必须是正整数')
        }
        return id
    }
}
```

### 使用方式

```typescript
// 方式一：路由级别（在 @Param/@Body/@Query 中直接使用）
@Get(':id')
findOne(@Param('id', ParseIdPipe) id: number) {
    return this.userService.findById(id)
}

@Post()
create(@Body(new ValidationPipe()) body: CreateUserDto) {
    // 如果校验失败，NestJS 会自动返回 400 错误
    return this.userService.create(body)
}

// 方式二：全局注册（main.ts）
async function bootstrap() {
    const app = await NestFactory.create(AppModule)

    app.useGlobalPipes(new ValidationPipe({
        whitelist: true,               // 自动剔除 DTO 中未定义的字段
        forbidNonWhitelisted: true,    // 发现未定义字段则拒绝请求
        transform: true,               // 自动类型转换（"1" → 1）
        disableErrorMessages: false,   // 生产环境设为 true 隐藏错误详情
    }))

    await app.listen(3000)
}

// 方式三：全局注册（Provider）
import { APP_PIPE } from '@nestjs/core'

@Module({
    providers: [
        {
            provide: APP_PIPE,
            useClass: ParseIdPipe,
        }
    ]
})
export class AppModule {}
```

**whitelist 的作用**：
```typescript
// DTO 只定义了 name 和 age
export class CreateUserDto {
    name: string
    age: number
}

// 请求体包含额外字段
{
    "name": "张三",
    "age": 25,
    "role": "admin"  // 未定义字段
}

// whitelist: true → role 会被自动剔除
// forbidNonWhitelisted: true → 直接返回 400 错误
```

**使用场景**：参数类型转换、数据校验、ObjectId 格式校验、分页参数范围校验。

## 异常过滤器（Exception Filter）

异常过滤器捕获未处理的异常并返回统一格式的错误响应。

### 内置 HTTP 异常

```typescript
// NestJS 内置了常用的 HTTP 异常类
throw new BadRequestException('参数错误')       // 400
throw new UnauthorizedException('未登录')      // 401
throw new ForbiddenException('无权限')          // 403
throw new NotFoundException('资源不存在')        // 404
throw new ConflictException('资源冲突')          // 409
throw new InternalServerErrorException('服务器错误') // 500
```

### 自定义异常过滤器

```typescript
import { ExceptionFilter, Catch, ArgumentsHost, HttpException } from '@nestjs/common'
import { Response } from 'express'

@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
    catch(exception: HttpException, host: ArgumentsHost) {
        const ctx = host.switchToHttp()
        const response = ctx.getResponse<Response>()
        const status = exception.getStatus()
        const exceptionResponse = exception.getResponse()

        response.status(status).json({
            code: status,
            message: typeof exceptionResponse === 'string'
                ? exceptionResponse
                : (exceptionResponse as any).message || exception.message,
            timestamp: new Date().toISOString(),
            path: ctx.getRequest().url
        })
    }
}
```

### 捕获所有异常

```typescript
@Catch()  // 不指定类型，捕获所有异常
export class AllExceptionsFilter implements ExceptionFilter {
    catch(exception: unknown, host: ArgumentsHost) {
        const ctx = host.switchToHttp()
        const response = ctx.getResponse<Response>()

        let status = 500
        let message = '服务器内部错误'

        if (exception instanceof HttpException) {
            status = exception.getStatus()
            message = exception.message
        }

        response.status(status).json({
            code: status,
            message,
            timestamp: new Date().toISOString()
        })
    }
}
```

### 使用方式

```typescript
// 方式一：路由级别（@UseFilters）
@Controller('users')
@UseFilters(HttpExceptionFilter)
export class UserController {
    @Get()
    @UseFilters(HttpExceptionFilter)
    findAll() {}
}

// 方式二：全局注册（main.ts）
async function bootstrap() {
    const app = await NestFactory.create(AppModule)
    app.useGlobalFilters(new HttpExceptionFilter())
    // 缺点：无法注入依赖
    await app.listen(3000)
}

// 方式三：全局注册（Provider 推荐）
import { APP_FILTER } from '@nestjs/core'

@Module({
    providers: [
        {
            provide: APP_FILTER,
            useClass: HttpExceptionFilter,
        }
    ]
})
export class AppModule {}
```

## 面试题

### Q1: 拦截器和过滤器的区别？

拦截器（Interceptor）在请求处理前后执行，可以修改请求和响应，适合统一响应格式、日志、缓存等。过滤器（Exception Filter）在异常发生时执行，捕获异常并返回统一格式的错误响应。

### Q2: 全局绑定拦截器有哪两种方式？有什么区别？

`app.useGlobalInterceptors`（无法注入依赖）和 `APP_INTERCEPTOR` 提供者（可以注入依赖）。推荐使用 `APP_INTERCEPTOR` 方式，因为拦截器通常需要依赖其他服务。

### Q3: `ValidationPipe` 的 `whitelist` 和 `forbidNonWhitelisted` 有什么区别？

`whitelist: true` 会自动剔除 DTO 中未定义的字段；`forbidNonWhitelisted: true` 更严格，发现未定义字段直接返回 400 错误。两者结合使用可以获得最佳安全性。

### Q4: 为什么说 DTO 比直接在控制器中写校验更好？

DTO 将校验逻辑从控制器中分离出来，职责单一、可复用（同一个 DTO 可以在多个地方使用）、可测试（可以单独测试 DTO 的校验逻辑）。

### Q5: 一次请求里，Middleware、Guard、Pipe、Interceptor 的精确执行顺序是什么？

`Middleware → Guard → Interceptor(before) → Pipe → Controller → Interceptor(after) → Response`；任意环节抛异常都会进入 Exception Filter。注意 Service 属于业务调用链，不是框架生命周期的独立阶段。

### Q6: 为什么基于装饰器（如 `@Roles('admin')`）的鉴权要放在 Guard 里，而不是 Middleware 里？

因为 Guard 拿到的 `ExecutionContext` 能访问 `getHandler()` 和 `getClass()`，从而配合 `Reflector` 读取 Handler 上的元数据标签；Middleware 只拿到 `req/res/next`，无法感知当前路由方法，也就读不到这些标签。

### Q7: IoC 和 DI 是什么关系？为什么 Controller 里不用 `new` 就能用 `UserService`？

IoC（控制反转）是思想：把对象创建与依赖管理的控制权交给容器。DI（依赖注入）是实现：容器创建好 `UserService` 后通过构造函数注入给 Controller。所以 Controller 只需声明依赖类型，由容器负责实例化与装配，自然不需要手动 `new`。
