> 在动手写第一行 NestJS 代码之前，先想清楚两件事：它到底替你做了什么，以及你打算学到什么程度。

## 为什么 NestJS 排在模块五

如果你翻过前面的模块，会发现 NestJS 的位置有点"靠后"：

```
模块一 运行环境   →  Node.js 怎么跑
模块二 网络底层   →  请求怎么进来
模块三 Web 框架   →  Express/Koa 封了什么
模块四 数据与缓存 →  数据存在哪、怎么取
模块五 后端架构   →  NestJS 在以上全部之上又封了什么   ← 你在这里
```

这是刻意的。原因很简单：**NestJS 的价值在于"组织"，而不是"能力"。**

- 它能做的事，裸 Node.js 都能做
- 它只是把"怎么组织一个能长期维护的后端项目"这件事，变成了一套有约束的约定

所以如果先学 NestJS，你学到的是一堆语法：

```ts
@Controller('user')
export class UserController {
  constructor(private readonly userService: UserService) {}

  @Get(':id')
  findOne(@Param('id') id: string) {
    return this.userService.findOne(id)
  }
}
```

你会写它，但答不上来：`private readonly userService` 为什么不用 `new`？`@Get(':id')` 是怎么变成路由的？请求进来之后，先经过谁、后经过谁？

这些问题的答案，全都藏在前面四个模块里。

## NestJS 到底封装了哪几层

把模块二的链路图接上 NestJS，是这样的：

```
你的 Controller          ← 你只写这一层
  ↑
NestJS（DI 容器 / 装饰器 / 生命周期）   ← 本篇及后续要讲的
  ↑
Express / Fastify（路由、中间件）        ← 模块三
  ↑
Node.js HTTP（报文解析）                 ← 模块二
  ↑
TCP / Socket / epoll                    ← 模块二
```

四层封装，对应四个认知：

| 层 | NestJS 替你决定了什么 | 想搞懂要看 |
|----|---------------------|-----------|
| DI 容器 | 对象谁来创建、依赖怎么传 | [IOC 与依赖注入](./02-IOC%20与依赖注入) |
| 装饰器 + Metadata | 路由、参数、权限怎么"声明"出来 | [控制器与路由](./04-控制器与路由) |
| 请求生命周期 | 请求依次经过哪些环节 | [请求处理链](./05-请求处理链) |
| 底层 HTTP | 报文怎么解析、响应怎么写出 | [HTTP 与 HTTPS 深入](../03-网络编程与实时通信/02-HTTP%20与%20HTTPS%20深入) |

> 心智模型：**框架是一组"你已经认可了的约定"。** 学 NestJS 的重点不是记住有多少个装饰器，而是理解每一层约定解决了什么问题 —— 这样当约定不适用时，你知道该在哪里打破它。

## 学习边界：什么必须掌握，什么点到为止

NestJS 非常大，全学完没有必要。按目标划分：

### 必须掌握（不会就没法干活）

| 主题 | 为什么必须 |
|------|-----------|
| Module / Controller / Provider 三件套 | 所有代码都长在这三者上 |
| 依赖注入（`@Injectable` + 构造函数注入） | 不理解为啥不用 `new`，调试 DI 报错会毫无头绪 |
| 请求处理链的顺序 | 中间件/守卫/管道/拦截器/过滤器放错位置 = 功能不生效 |
| DTO + ValidationPipe | 参数校验是接口安全的第一道闸 |
| TypeORM / 数据库集成 | 真实项目绕不开 |
| 配置与日志（模块六） | 上线必需 |

### 知道怎么用即可（用到再深挖）

| 主题 | 建议 |
|------|------|
| 微服务架构 | 知道 `@MessagePattern` 与传输层选项，单体够用就不拆 |
| 切换 Fastify | 知道有这条路、知道中间件兼容性差异即可 |
| 动态模块 / 自定义 Provider Token | 写公共库时才需要，业务代码很少碰 |

### 可以暂时跳过

| 主题 | 什么时候再回来 |
|------|--------------|
| 源码级实现（最小实现 NestJS） | 想彻底搞懂启动流程时 |
| 循环依赖 `forwardRef` | 真的踩到时 |
| 高级装饰器元编程 | 要写通用能力（如统一权限、多租户）时 |

## 建议的学习节奏

模块五一共 18 篇，建议这样分配：

```
第 1 步  快速上手 + IOC 与依赖注入          摸清概念，跑起项目
第 2 步  模块与提供器 + 控制器与路由         能写出第一个 CRUD
第 3 步  请求处理链                          理解请求的一生（最重要的一篇）
第 4 步  数据库集成                          接上模块四
        ──────────── 到这里算「入门」 ────────────
第 5 步  自定义装饰器 + 作用域与循环依赖      进阶特性
第 6 步  登录注册实战 → 认证进阶              把前面所有串成一个真实系统
第 7 步  文件上传 / WebSocket / 定时任务      补齐常见业务场景
第 8 步  NestJS 源码分析 + IoC 与依赖注入原理  理解框架本身
第 9 步  项目模板                            照着搭一个完整项目
第 10 步 微服务 / Fastify                     按需
```

**一个建议**：第 3 步「请求处理链」不要跳。它决定了你后面是在"配置框架"还是在"猜框架"。而这一篇能不能读得顺，又取决于模块二是否扎实 —— 这也是为什么网络层要排在前面。

## 三个常见误区

### 误区一：把 NestJS 当成"更高级的 Express"

不是。Express 是"请求 → 中间件 → 响应"，NestJS 是"请求 → 一整套生命周期 → 响应"。多出来的 Guard / Pipe / Interceptor / Filter 不是装饰，它们各自解决一类明确的问题：

- Guard：**能不能进**（认证、权限）
- Pipe：**数据对不对**（校验、转换）
- Interceptor：**包裹执行**（统一响应、耗时统计、缓存）
- Filter：**出错怎么办**（异常 → 标准错误响应）

搞混它们，就会出现"把权限逻辑写在中间件里"这种能跑但难维护的代码。

### 误区二：觉得装饰器是"魔法"

装饰器只做一件事：**往类或方法上贴标签**。真正干活的是运行时读取标签的框架代码。

```ts
@Roles('admin')            // 只是贴了个标签
@Get('users')
findAll() {}
```

`@Roles('admin')` 本身不会拦截任何请求。需要一个 Guard 通过 `Reflector` 把它读出来，才会生效。理解这一点，"为什么我加了 `@Roles` 却不生效"就不再是玄学。

### 误区三：一上来就拆微服务

单体 NestJS 项目配合良好的模块划分，能撑到相当大的规模。模块划分清晰的前提下，未来拆分是水到渠成的事；一上来就拆，只会把"分布式事务、链路追踪、服务发现"这些复杂度提前塞给自己。
