## 一、基础概念

### Q1: 在浏览器输入 URL 到页面渲染完成，中间经历了哪些步骤？（第 02 篇）

- **结论**：`DNS 解析 → TCP 三次握手 → [HTTPS] TLS 握手 → 发 HTTP 请求 → 服务端处理并返回 → 浏览器解析渲染`。前几段就是"浏览器到 Controller"这条链路的客户端侧。
- **原理**：域名先经本地缓存 → 系统 hosts → 递归 DNS 换成 IP；再与目标 IP:端口（默认 80 / 443）建立 TCP；HTTPS 还要多一轮 TLS 握手与证书校验；之后组装请求报文写入 socket，数据经内核协议栈、网卡、路由抵达服务器。
- **边界**：真实场景还要算上强缓存（命中则不发请求）、CDN 按地域返回不同 IP、HTTP/2 多路复用省掉多次握手；拿到 HTML 之后浏览器再构建 DOM / CSSOM、合并渲染树并绘制。
- **场景**：排查"接口慢"时先分清是浏览器侧慢（DNS、TLS、多次重定向、资源并发数）还是服务端侧慢，两侧用的工具完全不同。
- **追问**：解析失败的现象是 `ENOTFOUND`（域名解析不到）或 `EAI_AGAIN`（临时失败、可重试），对应链路第 1–2 步。

### Q2: TCP 在不可靠的 IP 网络之上提供了哪三种保证？它和 UDP 的区别是什么？（第 01 篇）

- **结论**：面向连接、可靠、有序。
- **原理**：面向连接 = 通信前先三次握手；可靠 = 丢包重传 + 校验和 + 确认应答；有序 = 序号保证到达顺序。缺掉任何一条，就会出现"文件下载残缺""后发的包先到、消息乱序"。
- **边界**：UDP 无连接、不保证可靠与顺序，换来更低的延迟与开销；HTTP/3 的 QUIC 正是基于 UDP，在用户态自己重建可靠传输与拥塞控制。
- **场景**：音视频、实时游戏状态同步这类"低延迟优先、可容忍少量丢包"的场景才值得选 UDP；业务接口默认要的是可靠有序，所以都是 TCP。
- **追问**：TCP 只保证"字节可靠有序"，不保证"你发几次我收几次"——这正是粘包拆包的根源（见 Q13）。

### Q3: TCP 为什么是"字节流"而不是"消息流"？（第 01 篇）

- **结论**：TCP 只保证一串字节可靠、有序地到达，不保留你调用 `write` 的次数与边界。
- **原理**：`write('hello')` 和 `write('world')` 在 TCP 眼里就是连续的字节，可能被合并成一个包，也可能被拆成 `hel` + `loworld` 两次送达；`socket.on('data')` 拿到的 `data` 是 Buffer，不是字符串。

```
发送方：write('hello')          write('world')
                  └──────┬──────┘
                         ▼
   TCP 眼里只有一串连续字节（没有"两条消息"这回事）
接收方：可能一次 data = 'helloworld'，也可能两次 = 'hel' + 'loworld'
```

- **边界**：所以"一次发送 = 一次接收"不成立，基于 TCP 的应用协议必须自己定义消息边界。
- **追问**：`Buffer.from('你好').length` 是 6 而不是 2——字符长度 ≠ 字节长度，算 `Content-Length` 时踩的就是这个坑。

### Q4: Socket 和 Stream 是什么关系？为什么说 `net.Socket` 是 Duplex Stream？（第 01 篇）

- **结论**：Socket 是"应用程序使用操作系统网络能力的接口抽象"，在 Node 里它以双工流（Duplex Stream）的形态暴露出来。
- **原理**：`net.Socket` 同时实现 Readable 与 Writable——可读对应 `socket.on('data')` 收数据，可写对应 `socket.write()` 发数据，这正是 TCP 全双工的体现。
- **边界**：所以"Stream 不只用于文件"：`req` 是可读流、`res` 是可写流，根源是它们背后就是同一个 Socket 的两端；`pipe` 能直接把文件推给客户端，也沾了这个设计的光。
- **场景**：中间件之所以能在同一对 `req` / `res` 上层层叠加，是因为它们共享同一个 Socket 的两端——换 Socket 等于换连接，不可能只换中间件。
- **追问**：一条 TCP 连接由四元组（源 IP:源 Port → 目标 IP:目标 Port）唯一区分，源端口不同就是不同连接，这就是单机支撑上万连接的由来。

### Q5: 什么是 HTTP？TCP 之上为什么还要一层应用协议？状态码怎么分类？（第 02 篇）

- **结论**：HTTP 是定义"字节流如何被翻译成一次请求与响应"的应用层协议，约定 Method / URL / Header / Body / Status Code。
- **原理**：TCP 只懂字节流，不懂"我要 GET /users"；HTTP 用请求行 + 头 + 空行 + 体的格式给出报文边界，服务端据此解析出结构化请求。你写框架时能直接拿到 `@Body()`，就是因为框架已按 HTTP 规则把字节解析好了。
- **状态码**：1xx 信息（101 协议切换）、2xx 成功（200 / 201）、3xx 重定向（301 永久 / 302 临时）、4xx 客户端错误（400 报文畸形 / 401 未认证 / 403 无权限 / 404 未命中 / 431 请求头过大）、5xx 服务端错误（500 / 502 / 503 / 504）。
- **边界**：状态码由服务端主动决定、客户端只做解释，所以"返回 200 但 body 里塞业务错误码"是设计选择而非协议要求，代价是破坏了对 HTTP 语义的统一理解。
- **追问**：`res.statusCode = 404; res.end()` 就是最原始的状态码用法，框架只是把它包装得更顺手。

### Q6: 一段 HTTP 报文长什么样？它在字节流里靠什么划出"头"和"体"的边界？（第 02 篇）

- **结论**：请求行 / 状态行 + 若干头 + **一个空行** + 体；那个空行就是头与体的分界。

```http
GET /users HTTP/1.1
Host: example.com
Accept: application/json
                        ← 空行：头到此结束
```

- **请求侧**：首行是 `方法 路径 版本`，空行之后是 Body（GET 通常为空）；响应侧首行是 `版本 状态码 原因短语`，空行之后是正文。
- **边界**：头部结束位置靠空行确定，**体的结束位置**靠 `Content-Length` 或 `Transfer-Encoding: chunked` 确定——这就是 HTTP 在 TCP 字节流之上自己定义的消息边界，也是它"看起来没有粘包"的原因。
- **追问**：`Content-Length` 必须写字节长度，写成字符长度会让客户端截断或报错。

### Q7: HTTPS 比 HTTP 多了什么？TLS 到底解决了哪三件事？（第 02 篇）

- **结论**：HTTPS = HTTP over TLS，在 HTTP 与 TCP 之间多垫了一层 TLS；TLS 解决加密、身份认证、数据完整性。
- **原理**：加密——内容只有通信双方能读，防窃听；身份认证——证书证明"你真的是 example.com"，防中间人冒充；数据完整性——防响应被注入篡改。
- **流程**：ClientHello（版本 / 密码套件 / 随机数）→ ServerHello + 证书链 → 客户端校验证书链与域名有效期 → 协商会话密钥（如 ECDHE）→ Finished 后进入加密传输。
- **边界**：生产上 TLS 通常在网关（Nginx / 负载均衡）终结，Node 服务跑在内网明文 HTTP 上，证书续期与多实例统一入口都更省心。
- **追问**：HTTPS 只保证"传输过程"安全，不保证服务端本身可信。证书校验失败时不要用"忽略证书校验"绕过，那等于把中间人风险永久留在链路上。

### Q8: WebSocket 和 TCP 到底是什么关系？它能替代 TCP 吗？（第 03 篇）

- **结论**：不能。分层是 `WebSocket → TCP → IP`，WebSocket 是建立在 TCP 之上的应用层协议。
- **原理**：它把"如何可靠地双向传消息"标准化了：握手（HTTP Upgrade）、Frame（切分单位）、Message（若干帧组成）、Ping / Pong、Close、Text / Binary。
- **边界**：若绕过它直接用 `net.createServer()` 写 TCP，消息格式、粘包分包、心跳、断线重连全要自己造；WebSocket 复用 TCP，而不是替代 TCP。
- **追问**：协议只解决"怎么传消息"，不解决"握手后怎么鉴权、多久心跳、如何优雅关闭"——这些仍然是工程问题。

### Q9: SSE 是什么？它靠什么做到"断线重连不重复推送"？（第 03 篇）

- **结论**：SSE（Server-Sent Events）用一条普通 HTTP 长连接做服务端 → 客户端的单向推送，方向固定为 `Client ← Server`。
- **原理**：响应头设 `Content-Type: text/event-stream`、`Cache-Control: no-cache`，然后往 `res` 这条可写流持续 `write` 事件文本；事件按行组织（`event:` / `data:` / `id:` / `retry:`），事件之间用空行分隔。
- **断线续传**：服务端给每条事件带 `id:`；浏览器 `EventSource` 自动重连时会在请求头带上 `Last-Event-ID`，服务端据此从断点之后继续推，跳过已发过的部分。
- **边界**：必须监听 `req.on('close')` 清理定时器，否则客户端断开后推送逻辑还在跑，会造成内存与 fd 泄漏。
- **场景**：任务进度、日志回放、行情推送这类"服务端单向、低频回传"的需求，用 SSE 能省掉 WebSocket 一半的协议负担。

### Q10: `ECONNREFUSED`、`ECONNRESET`、`ETIMEDOUT`、`socket hang up` 分别说明链路哪一段出错？（第 00 篇）

- **结论**：`ECONNREFUSED` = 连接根本没建立；`ETIMEDOUT` = 握手或读写一直等不到回应；`ECONNRESET` = 连接建立过、中途被对端强行重置；`socket hang up` = 响应还没回来，连接就先被对方关了。
- **原理**：`ECONNREFUSED` 发生在三次握手之前——目标 IP:端口没有进程监听，或防火墙直接拒绝；`ECONNRESET` 发生在连接生命周期中——对端崩溃、空闲连接被 NAT / 代理掐断、或收到数据后回 RST；`ETIMEDOUT` 是"包发出去了但始终没有回应"，多为防火墙静默丢包或网络不可达。
- **边界**：判断依据是"报错发生在建连前还是建连后"。前者查"服务起没起、端口绑没绑"，后者查"谁先关的连接、有没有超时或心跳缺失"。
- **追问**：`EADDRINUSE` 属于"服务根本起不来"那一类——端口已被占用，说明旧进程没退干净或端口配错，和上面四个报错不是一回事。

## 二、机制与原理

### Q11: 服务端收到请求后，从网卡到你的 Controller 内部经历了哪些层？（第 04 篇）

- **结论**：网卡 → 内核 TCP/IP 协议栈 → Socket Receive Buffer → fd 变 readable → epoll 通知 → libuv → Event Loop poll 阶段 → `node:http` 解析报文 → 触发 `'request'` → 框架适配层 → 中间件 / Guard / Interceptor / Pipe → Controller。

```
网卡 → 内核 TCP/IP 栈 → Socket Receive Buffer → fd 变 readable
  → epoll 通知 → libuv 取事件 → Event Loop 的 poll 阶段
  → node:http 解析报文、触发 'request' → req(Readable) / res(Writable)
  → Express/Fastify 适配层 → Middleware → Guard → Interceptor → Pipe
  → Controller（res.end() 之后沿原路反向再走一遍）
```

- **原理**：内核只负责把字节可靠送到 socket 并标记它可读；libuv 把 epoll / kqueue / IOCP 的差异屏蔽掉；`node:http` 把字节流按 HTTP 规则切成 `req`（可读）与 `res`（可写）；框架再把这对流交给你的方法。
- **边界**：真正耗时的"等待"发生在内核与网卡，主线程只在就绪时被唤醒——所以"单线程扛万连接"不是一万条线程，而是"一个线程 + 一万次就绪通知"。
- **追问**：链路是**对称的**："请求怎么进来"和"响应怎么出去"是同一张图的两次遍历，理解其一就理解了另一半。

### Q12: 三次握手为什么不能简化成两次？（第 01 篇）

- **结论**：因为双方都要确认"我发得出去、也收得到"，两次握手只能让客户端确认自己的收发，服务端确认不了。
- **原理**：两次握手时服务端收到 SYN 就分配资源（缓冲区、端口）。若这个 SYN 是网络里滞留的旧报文或重复报文，服务端会空等直到超时，白白占着资源——SYN Flood 利用的正是这一点。
- **边界**：第三次 ACK 让服务端确认"客户端确实收到了我的回应"，此时双方都验证过收发能力，才敢放心投入资源。
- **场景**：排查"连接数异常高但业务量不大"时，可以往半连接堆积（客户端只发 SYN 不回 ACK）的方向看，而不是先怀疑业务代码。

### Q13: 粘包 / 拆包是怎么产生的？有哪些解法？（第 01 篇）

- **结论**：因为 TCP 是字节流、不保留消息边界，所以两次 `write` 可能被读成一次，也可能被拆成多段。

```
发送方：write('hello') + write('world')
接收方：① 一次 data = 'helloworld'          （粘包）
        ② 两次 data = 'hel' + 'loworld'     （拆包）
        ③ 三次 data = 'hello' + 'wor' + 'ld'（混合）
```

- **解法**：长度前缀（4 字节 N + N 字节 Body，最通用，二进制也适用）、分隔符（`\n` / `\r\n`，适合文本日志与 Redis 协议）、定长（简单但浪费补齐字节）。接收方按规则从字节流里切出完整消息，半包先缓存等下一段。
- **边界**：HTTP "看起来"没有粘包，是因为它用 `Content-Length` 或 `Transfer-Encoding: chunked` 自己定义了边界，不是 TCP 帮你分的。

### Q14: `epoll` 解决了什么问题？libuv 又解决了什么？（第 01 篇）

- **结论**：epoll 解决"大量连接由谁来盯"，libuv 解决"各 OS 机制不一样、写一份代码怎么跨平台"。
- **原理**：没有 epoll 时，1 万个 Socket 只能逐个轮询"有数据吗"，效率极低；epoll 让内核关注大量文件描述符，有数据时主动通知，进程只处理就绪的那几个。
- **边界**：Linux 是 epoll、macOS 是 kqueue、Windows 是 IOCP，libuv 把它们统一抽象成一套异步接口，所以我们写 `socket.on('data')` 时完全不用关心当前平台。
- **追问**：两者不是替代关系——epoll 是内核能力，libuv 是跨平台封装；Node 的网络 I/O 路径是"libuv 调 epoll，拿到就绪事件后回调回 JS"。

### Q15: 网络 I/O 到底走不走 libuv 线程池？单线程凭什么扛万连接？（第 01 篇）

- **结论**：网络 I/O **不走**线程池，走的是操作系统提供的 I/O 多路复用（epoll / kqueue / IOCP）。
- **原理**：会进线程池的是那些"没有同类异步机制可用"的工作——`fs` 文件操作、`dns.lookup`、`crypto`、`zlib`。成千上万的 Socket 由内核盯着，就绪了才通知 libuv，主线程只处理已经就绪的事件，等待全程不占主线程。
- **边界**：所以不要记成"异步 = 线程池"；单线程能扛并发的前提是主线程不被阻塞，一旦有同步重计算占住它，所有连接的处理会一起卡住。
- **场景**：`fs` 与 `crypto` 抢的是同一组线程，重 CPU 的加密任务会顺带拖慢文件读写——这是排查"文件操作莫名变慢"时容易忽略的一条。

### Q16: `socket.write()` 返回 `false` 意味着什么？该怎么处理？（第 01 篇）

- **结论**：意味着 Writable 内部缓冲已积压到压力阈值，此时应停止写入，等 `'drain'` 事件后再恢复生产。
- **原理**：磁盘读 500 MB/s、网络只能发 10 MB/s 时，不做任何控制数据就一路堆在内存里，最终 OOM。`write()` 的返回值就是背压信号：`false` 让你暂停，`'drain'` 表示缓冲已排空、可以继续。
- **边界**：生产代码别自己写 `on('data')` 加无脑 `write`，那样会丢掉背压；用 `pipe()` 让流内部协调速率，或用 `pipeline()` 在任一环出错时统一销毁整条链路。
- **追问**：`pipe` 帮你做了背压，但出错时不会自动销毁链路；要"任一环出错就整体清理"，就用 `pipeline`。

### Q17: 为什么 `req` 和 `res` 在 Node 里是流，而不是一个现成的字符串？（第 02 篇）

- **结论**：因为 HTTP 数据经 TCP 到达时本就是分块字节流，可能很大、不会一次到齐。
- **原理**：`req` 是可读流，用 `data` 事件逐块给 Buffer，你在 `end` 里 `Buffer.concat(chunks).toString()` 拼成完整报文；`res` 是可写流，支持多次 `write()`，用 `end()` 收尾。本质上是把 TCP 字节流按 HTTP 语义向上封装。
- **边界**：这个设计让大文件可以直接 `readableStream.pipe(res)` 边读边发，不必先全量进内存；`req` / `res` 之所以是流，根源在 `net.Socket` 是 Duplex Stream。
- **场景**：所以读请求体不要指望"等一个字符串"，而是按 chunk 累积；写响应也尽量别先 `JSON.stringify` 一个超大对象再一次性 `end`。

### Q18: 流式响应为什么不能先算 `Content-Length`？那用什么替代？（第 02 篇）

- **结论**：流式响应是"边产生边发送"，总长度要等数据全部产生完才知道，所以改用 `Transfer-Encoding: chunked`。
- **原理**：chunked 把响应体切成若干块，每块自带长度前缀，最后以一个长度为 0 的块表示结束，服务端因此无需预先知道总字节数。流式推送、大文件下载、实时进度都靠这套分块传输支撑。
- **边界**：还有一层坑——`Content-Length` 取的是**字节长度**，`'你好'.length` 是 2 而 `Buffer.byteLength('你好')` 是 6，算错会直接让客户端截断或报错。
- **追问**：这是两条互不相干的线——`Content-Length` / chunked 管的是响应体边界，`maxHeaderSize` 与 `431` 管的是请求头体积，别混在一起调。

### Q19: HTTP Keep-Alive 有什么用？`keepAliveTimeout`、`headersTimeout`、`requestTimeout` 三者什么关系？（第 02 篇）

- **结论**：Keep-Alive 让多个 HTTP 请求复用同一条 TCP 连接，省掉每次建连断连的握手与挥手成本；三者为连接生命周期的三把尺子。

```
无 Keep-Alive：建 TCP → 请求1 → 响应1 → 关 TCP（每个请求都付一次连接成本）
有 Keep-Alive：一条 TCP 连接上 请求1/响应1 → 请求2/响应2 → 请求3/响应3
               空闲超过 keepAliveTimeout 才关闭
```

- **原理**：`keepAliveTimeout` 是空闲连接保持多久后服务端主动关闭；`headersTimeout` 是建连后多久内必须收齐请求头（防慢速攻击）；`requestTimeout` 是单个请求从开始到结束的总时限。
- **关键约束**：`headersTimeout` 必须**大于** `keepAliveTimeout`。否则会出现竞态——连接按 keepAlive 超时被关掉，而"已关闭"状态还没和请求头超时逻辑对齐，后续进来的请求被直接丢弃，客户端就表现为 `ECONNRESET` / `socket hang up`。
- **边界**：一句话原则是**反向代理的超时 ≥ 服务端超时**，否则代理还以为连接活着，拿去发请求时服务端已经关了。

### Q20: HTTP/1.1 的队头阻塞是什么？HTTP/2 多路复用怎么解决？（第 02 篇）

- **结论**：H1.1 即使复用了 TCP 连接，同一条连接上的请求 / 响应仍是串行的——前一个响应没回来，后一个请求只能排队，这是应用层队头阻塞。

```
HTTP/1.1：  Request1 → Response1 → Request2 → Response2   （同一条连接上串行排队）
HTTP/2：    一条 TCP 连接上 Stream1 / Stream3 / Stream5 的帧交错传输，互不排队
```

- **原理**：浏览器只能靠多开 TCP 连接（约 6 条）来缓解，又额外付出握手与 TLS 握手成本。HTTP/2 把报文拆成 Frame，在单条 TCP 连接上划分多个 Stream 交错传输，一个连接即可并发多个请求。
- **边界**：HTTP/2 顺带做了二进制分帧与 HPACK 头部压缩省带宽，但"消除队头阻塞"只到应用层为止，TCP 层那一份还没解决（见 Q21）。

### Q21: HTTP/3 为什么要把传输层从 TCP 换成 QUIC（UDP）？（第 02 篇）

- **结论**：因为 HTTP/2 的多个 Stream 仍共享同一条 TCP 连接，而 TCP 要求字节流可靠且有序——丢一个包，后面已到达的数据也得等缺失段重传补齐才能上交应用，这就是 TCP 层队头阻塞。
- **原理**：HTTP/3 改用基于 UDP 的 QUIC，在用户态自己实现可靠传输、多路复用、拥塞控制与 TLS 安全能力，让不同 Stream 相互独立：某个 Stream 丢包只影响它自己，其余照常前进。
- **边界**：业务代码通常无感，由运行时或网关决定；本质是把"可靠、有序、加密"从内核态的 TCP 挪到应用可控的一层。
- **追问**：正因如此，HTTP/3 不是业务代码里"打个开关"就能生效的优化——需要客户端、CDN、网关三段都支持。

### Q22: WebSocket 的握手过程是怎样的？101 状态码是什么意思？（第 03 篇）

- **结论**：客户端先发一个带 `Upgrade: websocket`、`Connection: Upgrade`、`Sec-WebSocket-Key`、`Sec-WebSocket-Version: 13` 的普通 HTTP 请求；服务端同意就返回 `101 Switching Protocols` 与 `Sec-WebSocket-Accept`。101 表示"协议切换"。
- **原理**：握手本身仍是标准 HTTP，成功之后这条 TCP 连接脱离请求-响应语义，改用 WebSocket 帧协议，双方进入长连接双向通信。
- **边界**：`Sec-WebSocket-Accept` 不是加密用的，而是服务端把客户端发来的 Key 拼上固定字符串、做一次 SHA-1 + Base64 回传，用来证明"对方确实懂 WebSocket 握手"，防止缓存代理把升级请求误当普通 HTTP 处理而返回脏数据。
- **追问**：如果服务端返回的是 400 / 426 而不是 101，通常意味着代理没有正确转发 `Upgrade` 头，或服务端压根没挂上 WebSocket 处理器。

### Q23: 为什么长连接一定要有心跳（Ping / Pong）？（第 03 篇）

- **结论**：因为客户端断网、切换网络、进程被杀、NAT 映射超时或设备关机后，服务端往往长期不知情，连接会"假死"。
- **原理**：假死连接的 Socket 对象还在，却再也收不到数据，白白占着内存和文件描述符。定期 Ping / Pong 探测，连续多次无 Pong 就判定失效并释放 Socket，避免死连接悄悄拖垮服务端。
- **边界**：一个能上生产的长连接服务，至少还要同时考虑断线感知、客户端自动重连、空闲与读写超时、连接健康度、关键消息确认，以及多实例下的连接分布。
- **场景**：心跳间隔要结合 NAT 与代理的空闲超时来定——必须比中间设备的空闲超时更短，否则连接会在你探测之前就被静默回收。

### Q24: NestJS 帮我们封装了哪些层？它"不知道"底下什么？（第 04 篇）

- **结论**：NestJS 封装了 `node:http` 之上的一切——Routing、Controller、Provider / DI、Middleware、Guard、Interceptor、Pipe、Exception Filter，以及 WebSocket Gateway。
- **原理**：它**不知道**自己底下有 epoll 和事件循环——Guard、Pipe 再怎么写，最终都落到一次 `res.end()` 把字节交给内核，从不在意 socket 是怎么被标记为 readable、poll 阶段怎么消费的。
- **边界**：这层"不知道"正是学网络层的意义：框架把底层错误翻译成一句含糊的 `ECONNRESET` 或 `504` 甩给你，能不能秒定位，取决于你是否懂下面那几层。
- **追问**：`@Body()` 并不会自动校验，没挂 Pipe 时脏数据能直接打穿到业务层——这属于框架层盲区，不是网络层问题，排查时要分清。

## 三、排障与选型

### Q25: 线上频繁出现 `ECONNRESET`，你的判断链是什么？（第 04 篇）

- **第一步 定性**：`ECONNRESET` 说明连接建立过、中途被对端重置，所以先排除"服务没起"这类问题（那是 `ECONNREFUSED`）。
- **第二步 查超时**：第一嫌疑是 Keep-Alive 两侧不匹配——Node 的 `server.keepAliveTimeout` 与 Nginx 的 `keepalive_timeout` 谁先关，另一端还在读写就会收到 RST。正确做法是让服务端 keepAlive 超时略小于网关超时。
- **第三步 查资源与进程**：fd 耗尽（`Too many open files`）会导致连接被强制关闭；某一端进程崩溃退出也会造成重置。
- **第四步 查中间设备**：NAT、负载均衡、代理在空闲一段时间后掐断连接，典型特征是"空闲一段时间后的第一个请求失败，重试又好"。
- **收口**：先看是哪一端先关的连接，再比对两侧超时与连接数，以及是否有心跳缺失——不要一上来就翻业务代码。

### Q26: 网关层报 `502` 和 `504`，分别往哪查？（第 04 篇）

- **结论**：502 查"上游在不在"，504 查"上游为什么慢"。
- **502 Bad Gateway**：网关连上了上游但拿到非法 / 不完整响应，或压根没连上——查上游进程是否存活、端口是否监听（`EADDRINUSE` 会让新进程起不来）、协议与证书是否正确、健康检查是否误摘流。
- **504 Gateway Timeout**：网关连上了，但上游在超时内没响应完——查上游处理耗时（慢查询、下游依赖拖慢）、Event Loop 是否被同步任务占住、代理 `proxy_read_timeout` 是否过短。
- **共同的坑**：网关超时与服务端 `keepAliveTimeout` 打架，也会表现成 502 / 连接被提前重置。先确认"断在哪一跳"，再往下钻到事件循环与业务层。
- **追问**：502 也可能是上游正在重启，去看日志里有没有进程退出或 `EADDRINUSE` 记录；504 则先看上游自己的耗时分布，别急着调大代理超时来掩盖慢查询。

### Q27: 服务端出现 `Too many open files`，怎么定位？（第 04 篇）

- **结论**：这是文件描述符耗尽（`EMFILE` / `ENFILE`）——每个 TCP 连接、文件、socket 都占一个 fd。
- **判断链**：先 `lsof -p <pid>` 数连接数与打开文件数，区分是"连接泄漏"还是"真高并发"；再 `ulimit -n` 看进程 fd 上限是否过低；然后追连接来源——是下游连接没关，还是 Keep-Alive 配错导致连接堆积，或是长连接只增不减。
- **常见根因**：连接没正常释放（忘了 `close()`）、没用连接池、超时配置过长而回收不及时。
- **场景**：长连接服务最容易踩这条——每个用户一条 SSE / WebSocket，fd 数随在线人数线性增长，必须同时准备 fd 上限与连接数上限两道闸。
- **边界**：这属于链路第 18 步与全局资源层的问题，靠改业务逻辑改不掉，要看连接生命周期、fd 上限与回收策略。

### Q28: 服务端"CPU 高但 QPS 低"，怎么定位？（第 04 篇）

- **结论**：这是典型的**事件循环被占住**——主线程忙于同步计算，已经就绪的连接排不上队。
- **判断链**：先看 CPU 是不是只热一个核（多核只打满一核，更像主线程阻塞而非横向压力）；再用 `clinic.js` 或火焰图找热点函数；最后回到代码里找同步重活——大循环、`readFileSync`、`JSON.stringify` 超大对象、复杂正则回溯。
- **反向排错**：如果 CPU 不高但延迟陡增，方向就反了，那是"等待"而不是"计算"——查下游与数据库慢调用、连接池是否耗尽。两者现象相似、根因相反，先用 CPU 曲线区分。
- **追问**：还有一种"CPU 高、QPS 低"来自频繁 GC 或大对象序列化开销，火焰图能区分是 JS 热点还是序列化 / 内存分配。

### Q29: `ETIMEDOUT` 和 `socket hang up` 该怎么区分、分别往哪查？（第 00 篇）

- **`ETIMEDOUT`**：连接或读写一直等不到回应而超时——常见于防火墙静默丢包、安全组未放行、目标主机不可达。先 `telnet` / `nc` 探端口，再核对安全组与网络策略。
- **`socket hang up`**：响应还没回来，连接就被对方提前关闭——常见于上游崩了、上游主动断开、或代理 / 客户端超时掐连接。先看上游进程是否存活、有没有异常退出，再比对两侧超时。
- **区分口径**：`ETIMEDOUT` 是"没有回应"，`socket hang up` 是"回应没来、连接先没了"——前者查网络可达性，后者查谁先断的连接。
- **追问**：两者都可能由代理超时配置不当引起，所以查完网络后，回头再对一遍网关与服务的超时配置。

### Q30: 报了 `UNABLE_TO_VERIFY_LEAF_SIGNATURE` 或证书错误，怎么查？（第 00 篇）

- **结论**：这类报错落在链路的 TLS 握手（第 7–11 步），几乎都是证书链、域名或系统时间的问题，不是业务代码问题。
- **判断链**：先看证书有效期是否过期；再查证书链是否完整（服务端有没有把中间证书一起下发）；然后核对证书域名与实际访问域名是否匹配；最后确认服务器系统时间是否正确——时间不对会让"未生效 / 已过期"的判断全错。
- **自签场景**：自签证书未加入信任链会报 `DEPTH_ZERO_SELF_SIGNED_CERT`；测试环境可以显式信任，生产环境应换成正式证书，或由网关统一终结 TLS。
- **追问**：证书链不完整是自建证书最常见的坑——很多服务只配了站点证书，忘了把中间证书一起下发。
- **边界**：如果只有 curl 报错而浏览器正常，多半是本机 CA 库或代理拦截，先换一台机器复现再定性。

### Q31: SSE 和 WebSocket 应该怎么选？（第 03 篇）

- **结论**：判断"谁是主要说话方、要不要双向"，不要默认"实时 = WebSocket"。
- **选 SSE**：只有服务端单向持续推送时——实时通知、站内信、行情、日志回放、任务进度。它基于纯 HTTP 长连接、浏览器 `EventSource` 自动重连、网关兼容好，运维最轻。
- **选 WebSocket**：需要客户端高频双向收发时——聊天、多人协作编辑、双人实时游戏。它握手后升级为独立协议，原生支持 Text / Binary，但心跳、重连、鉴权都要自己实现。
- **边界**：SSE 只支持文本（二进制需自行编码），且受浏览器同源连接数限制；反向代理上要记得关缓冲，否则推送会被代理攒住不下发。
- **追问**：两种需求并存时（既要服务端广播、又要客户端上报状态），可以"SSE 收推送 + 普通 HTTP 发指令"，不必为了少数双向场景整体换成 WebSocket。

### Q32: 长连接在多实例部署下会遇到什么问题？（第 03 篇）

- **结论**：单机时所有连接在同一进程，广播直接遍历即可；多实例后连接散落在不同进程，A 实例无法把消息发给 B 实例持有的连接，广播必然漏发。
- **解法**：引入共享的订阅关系或消息总线（如 Redis 发布订阅）——任一实例产生消息后广播出去，每个实例再把消息投递给自己持有的那部分连接。
- **边界**：还要处理同一用户多端、多标签页造成的重复连接（推送要幂等），以及实例扩缩容时的连接迁移与集中重连，所以成熟项目通常直接用带房间与集群能力的库，而不是从裸 `net` 起步。
- **追问**：所以选型时先问"要不要横向扩多个实例"——如果需要，从第一天就得把订阅总线设计进去，而不是等扩容时再补。

### Q33: 框架都封装好了，为什么还要学网络层？只学框架会踩什么坑？（第 00 篇）

- **结论**：写业务时代码永远待在最上面一层，而线上出问题时，问题往往在最下面几层。
- **典型坑**：误以为网络 I/O 走线程池（其实是操作系统就绪通知）、不了解粘包拆包导致自定义协议解析错位、同步阻塞调用拖垮整个事件循环、以为 Keep-Alive 与代理超时随便配都行。
- **判断依据**：学底层不是为绕过框架裸写 TCP，而是拿到"框架之下的坐标系"——看到 `ECONNRESET` 知道去 TCP 层查连接生命周期，看到 `504` 先确认上游是不是慢，而不是重启了事。
- **场景**：把报错翻译成"该去哪一层看"最省时间——DNS 层、TCP 层、TLS 层、网关层、运行时层、业务层各有各的入口，先定位层再决定查什么。
- **边界**：本模块的边界是"Node 进程这一侧"，不追求徒手写一套生产级 HTTP 服务器，也不背 TCP 状态机的每一次转移。

## 四、场景设计题

### Q34: 设计一个 WebSocket 实时通知方案（第 03 篇）

- **需求**：系统产生新事件（新订单、新消息、任务状态变化）时，主动推送给对应前端用户；要扛得住多实例部署与频繁断线重连。
- **方案要点**
  - **建连**：用 Socket.IO / `@nestjs/websockets` 起网关，握手仍是一次 HTTP Upgrade（收到 101 后切换协议）；可用 namespace 区分业务域，如 `/orders`、`/notifications`。
  - **鉴权**：客户端在 `handshake.auth.token` 里带 JWT，网关在 `handleConnection` 或守卫中校验，非法连接直接断开——不要把鉴权留到连上之后。
  - **房间管理**：连接成功后 `socket.join(userId)`，把用户 ID 当房间名；断开时自动离开。推送统一走 `server.to(userId).emit('notification', data)`，点对点与广播共用一套 API。
  - **心跳与清理**：服务端开启 Ping / Pong 并设超时，连续无 Pong 判定假死；`handleDisconnect` 里清理房间、订阅与定时器。
  - **消息可靠性**：关键通知先落库再推送，并带上递增 id；客户端按 id 去重，规避重连后的重复事件。
  - **可观测**：记录在线连接数、房间数、心跳超时数与推送失败数——出问题时先看这四条曲线，而不是先读业务日志。
- **断线重连怎么处理**
  - 客户端开 `reconnection` 并做退避（如 1s 起步、指数增长），避免网络恢复瞬间的雪崩式重连。
  - 服务端要容忍同一用户的多条连接（多标签页、多设备），推送只保证"投递给该用户的所有连接"。
  - 重连后客户端按 id 或时间戳补拉断线期间的消息，而不是指望服务端全量重推。
- **多实例怎么广播**
  - 单机时遍历本地连接即可；多实例后本实例拿不到别的实例上的连接，直接广播会漏。
  - 引入共享订阅或消息总线（如 Redis 发布订阅）：任一实例产生消息后广播，各实例再投给自己持有的连接。
- **为什么这么设计**：房间把"连接"抽象成"用户"，业务代码不必知道连接落在哪个实例；鉴权前移到建立连接那一刻，能挡住绝大多数无效长连接；心跳与清理决定这套方案能不能长期稳定地跑下去。
- **边界与代价**：长连接会持续占用 fd 与内存，扩缩容还涉及连接迁移与集中重连；网关层必须放行 `Upgrade` 头并延长空闲超时，否则连接会被代理提前掐断、表现为客户端反复重连。
- **替代方案**：若只是服务端单向推送（通知、进度、行情），SSE 更轻——纯 HTTP、浏览器自动重连、网关免配 Upgrade，不必为了长连接上整套 WebSocket 运维。
