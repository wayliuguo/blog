## 分篇知识点

一篇一份清单，每条的知识点名都能直接当搜索关键词；忘记细节时，按知识点名回到对应篇目即可。

### 00 导读与全景图

- **网络层排在运行环境之后是依赖不是难易**：模块一讲的 Event Loop / libuv / Buffer / Stream，正好在网络层各自找到"真实来源"。
- **全景图**：Browser → HTTP → TLS → TCP → IP → 网卡 → 内核 → Socket → epoll → libuv → Event Loop → node:http → 框架 → Controller。
- **链路是对称的**：响应沿原路反向再走一遍，"请求怎么进来"和"响应怎么出去"是同一张图的两次遍历。
- **用户态与内核态的分界**：libuv 往上是你写代码能控制的范围，内核及其以下（Socket 缓冲区、TCP、epoll）改 JS 改不动。
- **框架替你做的三件事**：把字节流切成请求、把写响应封成 `res.json()`、把连接生命周期管起来——这三件一出问题，盲区就变成故障点。
- **五篇路线图**：00 立坐标 → 01 字节流 → 02 请求语义 → 03 长连接 → 04 纵向收束；建议前四篇边读边跑，04 篇不引入新实验。
- **每层出问题的典型现象表**：DNS 层 `ENOTFOUND` / `EAI_AGAIN`，TCP 层 `ECONNREFUSED` / `ECONNRESET` / `ETIMEDOUT` / `EADDRINUSE`，TLS 层证书校验失败，HTTP 层 400 / 404 / 431，网关层 502 / 504，运行时层 `Too many open files`。
- **报错越靠上越像配置与路由问题，越靠下越像连接生命周期与资源问题**：先定位层，再决定查什么，不要一上来全局搜代码。
- **这一层最易被跳过，回报却最高**：框架把它包得太好，你几乎感觉不到它存在；但读 Express 最小实现或 NestJS 请求处理链时"有没有感觉"，全看这一层。
- **边界声明**：不深入内核协议栈源码、不手写 epoll、不背 TCP 状态机；目标只是出问题时知道往哪看、读框架时知道底下是什么。

### 01 TCP 与 Socket 编程

- **TCP/IP 分层模型**：应用层（HTTP）定义要什么 → 传输层（TCP）保证可靠有序送达 → 网络层（IP）寻址路由 → 网络接口层把比特变成电信号。
- **TCP 的三重保证**：面向连接（三次握手）、可靠（丢包重传 + 校验和 + 确认应答）、有序（序号）；缺一条就是下载残缺或消息乱序。
- **三次握手为什么不能省成两次**：两次时服务端收到 SYN 就分配缓冲区与端口，遇上网络里滞留的旧 SYN 会空等超时，SYN Flood 打的正是这一点。
- **TCP 提供的是可靠字节流，不是消息流**：`write('hello')` + `write('world')` 可能并成一次 `data`，也可能拆成 `hel` + `loworld`；`data` 拿到的是 Buffer。
- **粘包 / 拆包与长度前缀**：`4 字节长度 + N 字节 Body` 最通用，另有分隔符（`\n` / `\r\n`）与定长；半包要缓存等下一段，凑齐一条才交给业务。
- **Socket 与四元组**：源 IP:Port → 目标 IP:Port 唯一区分一条连接，所以同一台机器上目标都是 `:3000`，源端口不同就是不同连接。
- **`node:net` 与 Duplex Stream**：`net.createServer` / `createConnection` 是最底层的出入口；`net.Socket` 可读对应 `on('data')`、可写对应 `write()`，这是 TCP 全双工的形态，也是"Stream 不只用于文件"的由来。
- **epoll 与 libuv 各解决一件事**：epoll 让内核替你盯上万个 fd、就绪时主动通知；libuv 把 epoll / kqueue / IOCP 的差异抽象成一套异步接口。
- **网络 I/O 不走 libuv 线程池**：走的是操作系统就绪通知，主线程只在就绪时被唤醒；进线程池的是 `fs`、`dns.lookup`、`crypto`、`zlib` 这类没有同类异步机制的工作。
- **网络侧背压与 `pipe` / `pipeline`**：`write()` 返回 `false` 表示内部缓冲到阈值，应停下等 `'drain'`；`pipe` 自带速率协调，`pipeline` 还能在任一环出错时统一销毁整条链路。

### 02 HTTP 与 HTTPS 深入

- **HTTP 是 TCP 之上的应用层协议**：约定 Method / URL / Header / Body / Status Code；头部与体靠一个空行分界，体的结束靠 `Content-Length` 或 `Transfer-Encoding: chunked`。
- **用 `node:http` 手写 Server 会撞上的工程问题**：路由表、查询参数、Body 解析、异常兜底、鉴权横切、代码分层——Express / Fastify 就是来收这些的。
- **`req` 是可读流、`res` 是可写流**：请求体要 `chunks[] + Buffer.concat` 累积，响应可多次 `write()` 后用 `end()` 收尾；这个设计的根源在 `net.Socket` 是 Duplex Stream。
- **流式响应与 `Content-Length` 的取舍**：流式响应算不出总长度，改用 `Transfer-Encoding: chunked`；`Content-Length` 取的是字节长度（`'你好'` 是 6 不是 2），算错会截断。
- **Keep-Alive 复用同一条 TCP 连接**：省掉每个请求都建连断连的握手与挥手成本，空闲超过阈值才关闭。
- **三个超时的分工与硬约束**：`keepAliveTimeout` 管空闲关闭、`headersTimeout` 管收齐请求头、`requestTimeout` 管单请求总时限；`headersTimeout` 必须大于 `keepAliveTimeout`，否则竞态丢请求。
- **HTTPS = HTTP over TLS**：TLS 解决加密、身份认证、数据完整性三件事；生产上 TLS 通常在网关终结，Node 服务跑在内网明文 HTTP 上。
- **HTTP/1.1 队头阻塞与 HTTP/2 多路复用**：H1.1 同连接上请求响应串行，浏览器只能多开约 6 条连接绕过；H2 用二进制分帧 + HPACK + 单连接多 Stream 消除应用层队头阻塞。
- **HTTP/3 换成 QUIC（基于 UDP）**：H2 的多个 Stream 仍共享一条 TCP，丢包会带来 TCP 层队头阻塞；QUIC 让各 Stream 相互独立，业务代码通常无感。
- **错误码对上成因**：`502` 是网关没连上上游或拿到非法响应，`504` 是连上了但上游迟迟不回；`431` 是请求头过大，`ECONNRESET` 常来自 Keep-Alive 超时不匹配。

### 03 WebSocket 与 SSE 实时通信

- **HTTP 的一问一答不匹配服务端主动推送**：聊天、行情、通知、协作需要一条 `Client ⇄ Server` 的常开连接，WebSocket 就是为此设计的应用层协议。
- **WebSocket 先复用一次 HTTP 完成协议升级**：客户端发 `Upgrade: websocket` + `Sec-WebSocket-Key`，服务端同意就回 `101 Switching Protocols` + `Sec-WebSocket-Accept`。
- **`Sec-WebSocket-Accept` 不是加密**：把 Key 拼上固定字符串做一次 SHA-1 + Base64 回传，只用来证明"对方确实懂握手"，防缓存代理误当普通 HTTP 返回脏数据。
- **WebSocket 不替代 TCP**：分层是 `WebSocket → TCP → IP`；它把 Frame、Message、Ping / Pong、Close、Text / Binary 标准化，省掉自己造协议。
- **长连接为什么需要心跳**：客户端断网、切网、进程被杀、NAT 映射超时后连接会"假死"——Socket 还在却收不到数据，白白占内存与 fd。
- **能上生产的长连接还要考虑**：断线感知、客户端自动重连、读写与空闲超时、连接健康度、关键消息确认，以及多实例下的连接分布。
- **SSE 是纯 HTTP 长连接的单向推送**：方向固定 `Client ← Server`；响应头设 `Content-Type: text/event-stream` + `Cache-Control: no-cache`，然后往 `res` 这条可写流持续 `write`。
- **SSE 的报文格式、断线续传与清理**：事件按 `event:` / `data:` / `id:` / `retry:` 分行、空行分隔；重连带 `Last-Event-ID` 从断点续推；必须监听 `req.on('close')` 清掉定时器，否则泄漏。
- **流式输出场景为什么适合 SSE**：需求本质是"服务端单向、低频回传、高频推送"（日志、进度、大文件生成、监控），SSE 无需握手升级、浏览器原生支持、网关无缝兼容。
- **SSE 与 WebSocket 的选型准则**：只需服务端单向推送（通知、行情、日志、进度）用 SSE 最轻；需要高频双向（聊天、协作、游戏）才上 WebSocket。

### 04 一次请求完整经历了什么

- **31 步链路**：DNS → 三次握手 → [TLS] → 组报文 → 内核协议栈 → 网卡 → 路由 → 服务端 Receive Buffer → fd 变 readable → epoll → libuv → poll → `node:http` 解析 → `req` / `res` → 框架 → Controller。
- **你那行 `return []` 只是第 30 步**：前面 29 步都在"把请求安全送到这一行"，最后 1 步是"把结果安全送回去"。
- **第 18–22 步是 Node 网络能力的真正底座**：Receive Buffer → fd 就绪 → epoll 通知 → libuv 取事件 → poll 阶段消费，这才是"单线程扛万连接"的落点。
- **排障坐标系**：DNS 1–2 步看 `ENOTFOUND` / `EAI_AGAIN`；TCP 4–6 步看 `ECONNREFUSED` / `ETIMEDOUT`；TLS 7–11 步看证书链与系统时间；网关 16 步看 502 / 504；Keep-Alive 影响第 31 步的 `ECONNRESET`。
- **资源层与运行时层的两类现象**：`EMFILE` / `Too many open files` 是 fd 耗尽（连接泄漏或真高并发）；"CPU 高但 QPS 低"是事件循环被同步任务占住。
- **响应序列化也是故障点**：一次性 `JSON.stringify` 超大对象会卡住主线程并涨内存，应改流式、分页或压缩。
- **NestJS 封装了 `node:http` 之上的一切**：Routing、Controller、Provider / DI、Middleware、Guard、Interceptor、Pipe、Exception Filter、WebSocket Gateway。
- **框架的"两层不知道"**：框架不知道自己底下有 epoll 与事件循环，最后都落到一次 `res.end()`；只学框架的你也不知道请求先在 Receive Buffer 排队、被标记可读才触发。
- **为什么还要学这一层**：写业务时代码永远待在最上面一层，出问题时问题往往在最下面几层——学底层是把"报错"翻译成"该去哪一层看"。
- **一条可验证的是否判断链**：DNS 正常吗 → TCP 能建连吗 → TLS 握手成功吗 → 网关正常吗 → Keep-Alive 有问题吗 → Node 服务正常吗 → 事件循环被阻塞吗 → 框架报错吗 → 业务异常吗。

## 见 X 想 Y

现象是表相，先定位到层，再动手。

| 见到什么 | 该想到什么 | 一句话理由 |
| --- | --- | --- |
| `ECONNREFUSED` | 连接根本没建立，目标 IP:端口没有进程监听 | 报错发生在三次握手之前，先查服务起没起、端口绑没绑 |
| `ECONNRESET` | 连接建立过、中途被对端重置 | 大半是 Keep-Alive 两侧超时打架，先看谁先关的连接 |
| `ETIMEDOUT` | 包发出去了但始终没有回应 | 多是防火墙静默丢包或地址不可达，用 `telnet` / `nc` 探端口 |
| `socket hang up` | 响应还没回来，连接就被对方提前关了 | 查上游进程是否存活、有没有异常退出 |
| `EADDRINUSE` | 服务根本起不来 | 端口已被占用，多半是旧进程没退干净 |
| `Too many open files` | 文件描述符耗尽，多半是连接泄漏 | 每个连接占一个 fd，长连接服务要同时设 fd 上限与连接数上限 |
| `502 Bad Gateway` | 网关没连上上游，或拿到非法 / 不完整响应 | 查上游进程、端口监听、健康检查是否误摘流 |
| `504 Gateway Timeout` | 网关连上了，但上游在超时内没响应完 | 查慢查询与下游依赖，别用调大代理超时掩盖慢查询 |
| 证书校验失败 | 落在 TLS 握手那一段，不是业务代码 | 查有效期、证书链是否完整、域名是否匹配、系统时间对不对 |
| `431 Request Header Fields Too Large` | 请求头体积超限 | 典型是 Cookie / 鉴权头累积过多，和响应体的 chunked 是两条线 |
| 两次 `write` 只收到一次 `data` | TCP 是字节流，不保留消息边界 | 要自己定长度前缀或分隔符，HTTP 靠 `Content-Length` 自己定了边界 |
| `write()` 返回 `false` | 下游消费跟不上，内部缓冲到阈值了 | 停下等 `'drain'`，或直接用 `pipe` / `pipeline` 让流自己协调速率 |
| CPU 高但 QPS 低 | 事件循环被同步任务占住了 | 就绪的连接排不上队，去找大循环、`readFileSync`、超大 `JSON.stringify` |
| 客户端频繁重连长连接 | 心跳间隔没盖住中间设备的空闲超时 | NAT 与代理会静默回收空闲连接，心跳必须比它们更短 |

## 易错点汇总

下面这些是把各篇的误区合并去重后的版本，每条都对应一个线上真会踩的坑。

- **"异步 = 线程池"**：网络 I/O（`net` / `http` / `https`）走操作系统就绪通知，全程不占线程池。只有 `fs`、`dns.lookup`、`crypto`、`zlib` 这类没有同类异步机制的工作才会进池。
- **"TCP 保证你发几次我收几次"**：TCP 只保证字节可靠有序，不保留 `write` 的次数与边界，还可能出现半包。要消息边界就自己加长度前缀或分隔符，并把不够一条的字节留在缓冲区。
- **"`headersTimeout` 与 `keepAliveTimeout` 随便配"**：`headersTimeout` 必须大于 `keepAliveTimeout`。否则连接按 Keep-Alive 超时被关、状态还没和请求头超时逻辑对齐，后续请求被直接丢弃，客户端只看到 `ECONNRESET`。
- **"`Content-Length` 用字符长度"**：它取的是字节长度，`'你好'.length` 是 2 而 `Buffer.byteLength('你好')` 是 6。算错会让客户端截断或报错。
- **"流式响应也先算 `Content-Length`"**：流式的意义就是不等数据产完先发，总长度根本算不出来，应该改用 `Transfer-Encoding: chunked`。能算的只有一次性生成好的小响应。
- **"`Sec-WebSocket-Accept` 是加密"**：它是客户端 Key 拼固定串后 SHA-1 + Base64 的结果，不含任何加密语义，只用来证明对方懂握手、防缓存代理误判升级请求。
- **"WebSocket 能替代 TCP"**：分层是 `WebSocket → TCP → IP`，它是应用层协议，只是把消息格式、帧切分、心跳标准化了。绕开它直接用 `net`，这些规则全要自己造。
- **"实时通信就等于 WebSocket"**：只需服务端单向推送时，SSE 是纯 HTTP 长连接、浏览器自带重连、网关免配 `Upgrade`，比 WebSocket 轻得多；为了单向广播上双向电台是白付运维成本。
- **"SSE 推完就不管了"**：必须监听 `req.on('close')` 清理定时器与引用。否则客户端断开后推送逻辑还在跑，定时器、连接对象与 fd 都留着，形成泄漏。
- **"长连接建好就行"**：客户端断网、切网、NAT 超时后连接会"假死"，没有心跳就会一直背着死连接，慢慢吃光内存与 fd。
- **"单机广播能直接扩到多实例"**：多实例后连接散落在不同进程，A 实例发不到 B 实例持有的连接，广播必然漏发。需要共享订阅关系或消息总线。
- **"学底层是为了以后裸写 TCP"**：目的是拿到框架之下的坐标系——知道 `req` 是可读流、`res.end()` 触发的是一次 Socket 写、`ECONNRESET` 该去查连接生命周期。

## 与相邻模块的接口

上一模块给的是机制，本模块把机制落到具体链路上；本模块产出的坐标系，正是下一模块读框架源码的起点。

**进入本模块前必须已经掌握**

模块一「运行环境」给了四样东西，本模块正是它们的"真实来源"：

- **Event Loop**：模块一讲它分几个阶段，本模块说清 poll 阶段收的是内核的 I/O 就绪事件——"轮询"是问内核"谁就绪了"，不是"谁有数据了"。
- **libuv**：模块一讲它是异步 I/O 的调度层，本模块说清它底下屏蔽的是 epoll / kqueue / IOCP 的差异。
- **Buffer**：网络字节流进出的第一手形态就是 Buffer，HTTP 报文与 TCP 字节流落到 JS 里都是一段段 Buffer，而不是现成的字符串或对象。
- **Stream**：`net.Socket` 本身就是 Duplex Stream，所以 `req` 是可读流、`res` 是可写流——这个"流"来自 Socket，不是来自文件。

**本模块交给下一模块什么**

- 交给模块三「Web 框架基础」的是**「框架底部到底发生了什么」**：`node:http` 解析出的 `req` / `res` 是一对可读 / 可写流，路由匹配发生在 `'request'` 事件之后。
- 有了这个坐标，读 Express 的最小实现才能看懂"为什么只能这么写"：中间件之所以能用 `next()` 串起来，是因为它们叠加在同一对 `req` / `res` 上；`res.end()` 之所以能结束响应，是因为它最终触发一次 Socket 写。
- 同时要分清层次：`@Body()` 不会自动校验、异常要靠 `ExceptionFilter` 统一兜底，这些是框架层的问题，与网络层无关——排障时才不会串层。
