# 导读与全景图：网络层为什么在这里

## 网络层为什么排在运行环境之后：是依赖，不是难易

很多人学 Node.js 的顺序是「基础语法 → 框架 → 数据库 → 部署」。这条路线顺手，但会在同一个地方卡住：面试问 `req` 为什么是可读流，只能背结论；线上出现 `ECONNRESET`、连接假死、并发上不去，只能重启了事。

根源是同一个：**跳过了网络这一层，直接学了框架**。框架是对网络的封装，不懂被封装的东西，就只能记住封装的结果。

把顺序反过来会怎样？先学框架、后学网络，你同样能把接口写出来、把服务跑起来。但一旦往下追问「`req` 为什么是流」「`res.end()` 为什么能结束响应」「单线程为什么扛得住万连接」，框架给的答案都是「Node 就是这么设计的」——这句话没错，可它没告诉你设计背后的链路。于是你记住的是结论，不是机制；能抄写法，却读不懂源码。模块一先讲机制、模块二再给机制配真实来源，正是为了让你在第一次追问时就接得住。

所以模块二排在模块一「运行环境」之后，依据的是**依赖关系**，而不是由易到难：

- 模块一讲了 Event Loop、libuv、Buffer、Stream、进程线程；
- 如果不知道这些机制在「等什么、搬什么、扛什么」，它们就只是孤立概念；
- 网络层恰好给它们配上了「真实来源」——下一次请求进来，这些机制才有具体的事可做。

### 把模块一的五个机制对上「真实来源」

下面五条自问自答，是整篇模块二的暗线。先在这里立起来，最后一篇（04）会逐条结账：

```
Q1. Event Loop 到底在等什么？
A.  等内核通知的 I/O 就绪事件——某个 socket 可读了、可写了、有连接进来了。
    「轮询」是 poll 阶段去问内核「谁就绪了」，而不是去问「谁收到数据了」。

Q2. libuv 到底负责什么？
A.  把 epoll（Linux）/ kqueue（macOS）/ IOCP（Windows）的差异屏蔽掉，
    对外只暴露一套统一的异步 I/O 接口。你写的 net/tcp 代码因此能跨平台。

Q3. Buffer 为什么在 Node.js 里如此重要？
A.  网络字节流进出的第一手形态就是 Buffer。HTTP 报文、TCP 字节流，
    落到 JS 里都是一段段 Buffer，而不是现成的字符串或对象。

Q4. Stream 为什么不仅用于文件，也大量出现在网络编程中？
A.  net.Socket 本身就是 Duplex Stream（可读可写的两端流）。
    req 是可读流、res 是可写流，这个「流」来自 Socket，不是来自文件。

Q5. Node.js 单线程为什么还能支撑大量网络连接？
A.  连接本身由内核盯着（维护 TCP 状态、收发包），主线程只在事件就绪时
    被唤醒去处理。一万条连接不等于一万条线程，而是「一个线程 + 一万次就绪通知」。
```

这五条现在不必全懂，只要先记住「它们有出处」。模块二读完，再回来对照，每条都能落地。

## 全景图：一次请求从浏览器到 Controller

访问一个接口时，数据要穿过多层抽象才到你写的 Controller。下图是模块二乃至整个后端链路的地图——先把它记在脑子里，后面每一篇都是在放大其中一段：

```
Browser / App
  │  HTTP 请求（GET /api/users）
  ▼
HTTP（应用层：方法 / 路径 / 头部 / 正文）        ← 模块二 · 02 HTTP 与 HTTPS 深入
  ▼
TLS（传输层安全，仅 HTTPS；握手 + 证书校验）      ← 模块二 · 02（HTTPS 部分）
  ▼
TCP（传输层：面向连接、可靠、字节流管道）         ← 模块二 · 01 TCP 与 Socket 编程
  ▼
IP（网络层：寻址与路由，找到目标服务器）
  ▼
网卡（链路层：比特流 ↔ 电信号 / 光信号）
  ▼
操作系统内核（Socket 缓冲区、TCP/IP 协议栈）      ← 模块一 · 03 运行机制 + 模块二 · 01
  ▼
Socket（内核给应用层的 I/O 句柄，fd）             ← 模块二 · 01
  ▼
epoll / kqueue / IOCP（内核通知「这个 socket 就绪了」）← 模块一 · 03 + 模块二 · 01
  ▼
libuv（跨平台异步 I/O 抽象，屏蔽上述差异）         ← 模块一 · 03 运行机制
  ▼
Event Loop（poll 阶段收齐就绪事件，回调入队）      ← 模块一 · 03 运行机制
  ▼
node:http（解析 HTTP 报文 → req / res 对象）       ← 模块二 · 02
  ▼
Express / Fastify（路由 + 中间件，洋葱模型）        ← 模块三 · Web 框架基础
  ▼
NestJS（Controller / Service / IoC 容器）           ← 模块五 · 后端架构
  ▼
你的 Controller（业务代码，@Get() 在这里）
```

图例：**左侧是链路，右侧 `←` 标注该层在本模块哪一篇讲、或属于后续哪个模块**。越往下越「像机器」（字节流、epoll、Socket），越往上越「像人话」（`@Get()`、`@Body()`）。NestJS 把下面几层全部替你包好，你只写业务逻辑；但线上一旦出问题，问题往往在最下面几层。

注意链路是**对称的**：响应（你的 `return` / `res.end()`）会沿原路反向走一遍——Controller 返回值 → 框架序列化 → `node:http` 组报文 → Event Loop 派发写事件 → libuv → epoll 可写通知 → 内核 Socket → TCP 分包 → 网卡 → 回到浏览器。所以「请求怎么进来」和「响应怎么出去」是同一张图的两次遍历，理解其一就理解了另一半。后面 02 篇讲 `res` 为什么是「可写流」、为什么 `pipe` 能直接把文件推给客户端，根基都在这一段。

把模块一那几个反复出现的术语，直接钉到这张图上，后面读起来就不会飘：

- **Event Loop**：图里「Event Loop」那一行，特指 poll 阶段去收内核的就绪通知，再把回调推入任务队列；
- **libuv**：图里「libuv」那一行，是用户态这半边的总调度，网络 I/O 走 OS 异步接口、少数操作（如 `fs`、DNS 在某些平台）才借线程池；
- **Buffer**：字节流进出 Node 时的第一手容器，落在「TCP → Socket」这一段，报文每帧都是 Buffer；
- **Stream**：`net.Socket` 是 Duplex Stream，所以「HTTP → req/res」这对流的本质，是 Socket 的两端正反向被框架借走；
- **就绪通知**：图里 `epoll / kqueue / IOCP` 那一行，是「连接由内核盯着、主线程只在就绪时被唤醒」这句话的落点。

记住这五个落点，本篇开头的五条暗线就已经在图上有位置了。

## 这张图为什么值得先记住：业务代码只有一行，链路却有一整条

日常写业务，你停留在最上面一层。一个查询用户列表的接口，在框架层往往只有这么几行：

> 示意片段（无配套脚本）

```ts
@Controller('users')
export class UserController {
  @Get()
  findAll() {
    return this.userService.list();   // 业务代码，只关心「返回什么」
  }
}
```

但这一行 `@Get()` 背后，实际穿过了上一节整条链路：浏览器组 HTTP 报文 → 走 TCP → 过内核 Socket → epoll 通知 → libuv 收事件 → Event Loop 派发 → `node:http` 解析成 `req` → 框架路由命中 → 中间件穿过 → 才进到你的 `findAll()`。

所以学网络层的目的**不是以后绕开框架去裸写 TCP**，而是：当框架把链路藏起来时，你仍知道底下发生了什么。知道 `req` 是可读流，才理解为什么大请求体要「攒 Buffer」而不是「等字符串」；知道 `net.Socket` 是 Duplex Stream，才理解为什么 `res.end()` 能结束响应、为什么 `res` 能 `pipe` 给文件。

这一层给你的是「框架之下的坐标系」，不是另一套要天天手敲的 API。

顺着这条链路，可以明确数出框架替你做的三件最关键的事，反过来也就是网络层帮你补上的三块盲区：

1. **把字节流切成「请求」**：`node:http` + 框架解析器把 TCP 字节流按 HTTP 报文规则切成方法、路径、头部、正文，让你拿到结构化的 `req`，而不是一段裸 Buffer；
2. **把「写响应」封装成一句调用**：`res.json()` / `return` 背后是一次 `res.end()` 触发 TCP 写，你不必手动组报文、算 `Content-Length`；
3. **把连接生命周期管起来**：建立、保活（Keep-Alive）、超时、关闭都由框架与运行时接手，你不必自己盯着每个 socket 的状态。

这三件一旦出问题（报文畸形、响应提前断、连接泄漏），盲区就变成了故障点——这正是后面几篇要逐个拆开看的地方。

顺着图再划一条更根本的分界：**用户态 vs 内核态**。从「操作系统内核」那一行往下（网卡、IP、TCP、Socket 缓冲区、epoll 通知）都发生在内核里，你的 Node 进程碰不到、也改不了；从「libuv」那一行往上（`node:http`、框架、你的 Controller）才是你写代码能控制的范围。这条界线的意义在于：模块一讲的 Event Loop / libuv 是「用户态这半边的发动机」，模块二讲的 TCP / HTTP 是「数据怎么穿过界线进来」。大量线上问题（丢包、端口占用、fd 耗尽）其实卡在界线之下，靠改 JS 是改不掉的——你得去看配置、看内核参数、看连接生命周期。先认准这条线，后面定位故障才不会「在用户态里瞎找内核态的锅」。

## 每一层出问题时的典型现象表

链路里任意一层出毛病，都会以某种「现象 / 错误码」暴露出来。下面这张表是模块二的故障坐标系——后面遇到对应报错，先回这里定位「往哪看」，再去对应篇章深究：

| 层次 | 典型现象 / 错误码 | 先看哪里 |
| --- | --- | --- |
| DNS 层 | `ENOTFOUND`（域名解析不到）/ `EAI_AGAIN`（解析临时失败，可重试） | 域名拼写、DNS 配置、解析服务是否可用 |
| TCP 层 | `ECONNREFUSED`（目标端口无监听）/ `ECONNRESET`（对端突然断连）/ `ETIMEDOUT`（握手或读写超时）/ `EADDRINUSE`（端口已被占用） | 目标进程是否起来、防火墙、绑定端口、连接是否被中间设备掐断 |
| TLS 层 | 证书过期 / `UNABLE_TO_VERIFY_LEAF_SIGNATURE`（证书链校验失败） | 证书有效期、CA 链是否完整、是否自签未信任 |
| HTTP 层 | `400`（请求畸形）/ `404`（路由未命中）/ `431`（请求头过大）/ `socket hang up`（对端在响应前关连接） | 报文格式、路由表、请求头体积、上游是否提前断开 |
| 网关层 | `502 Bad Gateway`（上游返回非法响应）/ `504 Gateway Timeout`（上游超时） | 反向代理（Nginx 等）与健康检查、上游超时与 Keep-Alive 配置是否打架 |
| 运行时层 | `Too many open files`（文件描述符耗尽 / 连接泄漏） | 连接是否正常关闭、是否泄漏 Socket、ulimit 与 fd 上限 |
| 业务层 | 响应慢但 CPU 不高（事件循环被占住 / 下游慢） | 是否有同步重计算占住 Event Loop、下游服务与数据库是否拖慢 |

记住一个规律：报错码越靠上（HTTP / 网关），越可能是「配置或路由」问题；越靠下（TCP / 运行时），越可能是「连接生命周期或资源」问题。模块二重点帮你把下半部分的直觉补上。

给一个具体用法示范，避免这张表沦为摆设：假设服务偶发 `ECONNRESET`，按表先落入「TCP 层 → 对端突然断连」，再看右侧「连接是否被中间设备掐断」——大概率不是你的代码写错，而是客户端/代理在空闲一段时间后发起了 RST（NAT 超时、负载均衡摘流、浏览器标签页关闭）。这时该查的是连接保活与心跳（03 篇），而不是去改业务路由。再比如 `Too many open files`，表指向「运行时层 → 连接泄漏」，该查的是每条连接有没有正常 `close()`、有没有把 socket 当成长生命周期对象存起来忘了释放，而不是去翻 HTTP 报文。表的用法就是「先定位层，再决定查什么」，别一上来就全局搜代码。

读完这 5 篇，你能回答三件事：TCP 是字节流，应用层怎么知道一条消息在哪结束；网络 I/O 不占 libuv 线程池，Node 凭什么用单线程管上万个连接；一个服务端持续推送接口，为什么用 SSE 而不是 WebSocket。答得上来，模块二就算过关。

建议的阅读方式：**前四篇边读边跑**。实验台 `./code/net-lab` 里每个脚本都对应一个「框架之前的世界」——用 `node:net` 起 Server、故意连发两次看 `data` 收到几段、用 `node:http` 手写路由、用 SSE 推一个每秒计时器。亲手复现过粘包、亲手 `res.end()` 过一次，再回头看 `app.use()` 和 `@Get()`，那种「它替我做了什么」的感觉会非常具体。04 篇是收束，不引入新实验，只把前几篇串成端到端链路，并回到本篇开头的五条暗线逐条结账。

## 这一层与后续模块的关系：最易被跳过，回报却最高

网络层是整条链路里最容易被跳过的一环——因为框架把它包得太好了，你几乎感觉不到它的存在。但恰恰是这一层，决定了你后面读源码时「有没有感觉」。

- 读模块三「Web 框架基础」里 Express 的**最小实现**（路由匹配、中间件、`res.end()` 封装）时，只有懂了 `node:http` 解析出的 `req`/`res` 是什么，才看得懂框架在「封装什么」；
- 读模块五 NestJS 的**请求处理链**（Guard / Interceptor / Pipe 如何在 `req` 上叠层）时，只有懂了 `req` 是可读流、`res` 是可写流，才理解这些装饰器到底作用在链路的哪一段。

换句话说，本模块从 `node:net` 的裸 TCP 开始，再往上到 `node:http`，最后到框架，是为了让你带着「底层坐标」去读上层封装。先有地基，再盖楼，读框架源码才不会变成「对着一堆回调猜意思」。

举一个具体的对照：模块三会带你写一个 Express 的**最小实现**——几十行代码完成「路径匹配 → 中间件遍历 → `res.end()`」。不懂网络层时，你只能看懂「代码在做什么」；懂了 `req` 是可读流、`res` 是可写流、`net.Socket` 是 Duplex 之后，你会突然看懂「为什么只能这么写」：中间件之所以能 `next()` 串起来，是因为它在同一个 `req`/`res` 上叠加处理；`res.end()` 之所以能结束响应，是因为它最终触发的是一次 Socket 写。这一个「为什么」，就是网络层给的回报。

## 边界声明：本模块不追求成为网络协议专家

最后划清边界，免得用力过猛：

- **不深入** Linux 网络协议栈源码，不手写 `epoll`，不背 TCP 状态机每一个细枝末节；
- **重点是**「Node.js 后端开发必须理解的几件事」：字节流与消息边界、Socket 与就绪通知、HTTP 报文结构、`req`/`res` 为何是流、长连接与推送的取舍、常见报错往哪查；
- 目标是让你**出问题时知道往哪看、读框架时知道底下是什么**，而不是让你去写一套网络库。

把上面这张全景图和故障表留着，它们会贯穿模块二全部 5 篇。

补充一句「学完本模块你能做什么、不能做什么」，作为心理预期：学完你应当能**定位**绝大多数线上网络类故障到具体层（连接泄漏在运行时层、报文错在 HTTP 层、`502/504` 在网关层），能**读懂**框架对网络的封装而不是死记 API，能**判断**长连接场景该选 SSE 还是 WebSocket。你不需要能徒手写一个生产级 HTTP 服务器，也不需要能画出 TCP 状态机的每个转移——那是协议专家与内核工程师的事，不是 Node.js 后端开发的日常。

一个判断边界的实用标准：当你的问题开始变成「内核的 `net.ipv4.tcp_*` 该调哪个」「conntrack 表为什么被打满」「epoll 的就绪列表为什么这么长」，你已经跨过了本模块的边界，该去翻操作系统与网络栈的资料了。本模块负责把「Node 进程这一侧」讲透，让你在那一侧出问题时不至于一无所知、能跟运维或基础架构同事对齐语言；但深挖内核不是这里的目标。带着这个边界去读后面 5 篇，既不焦虑、也不飘。

把本篇记住两样东西就够了：一张「请求从浏览器到 Controller」的全景图，一张「每层出事往哪看」的故障表。它们会在 01 到 04 篇里被反复放大、反复引用。下一站是 `node:net` 的裸 TCP——你会亲手起一个 Server，亲眼看到字节流怎么一段段进来、为什么需要「长度前缀」来界定一条消息的边界。那是全景图最底下、也最该先摸透的一段。

读到这里，可以用三句话自测是否拿到了本篇的地图：能不翻图说出「请求从网卡到 Controller」经过哪几层；看到 `ECONNRESET` 能立刻反应「去 TCP 层查连接生命周期」而不是去翻业务代码；知道 `req`/`res` 是流这件事，根源在 `net.Socket` 是 Duplex Stream。三句都答得出，模块二的后 4 篇就是顺着这张图往下钻，不会迷路。
