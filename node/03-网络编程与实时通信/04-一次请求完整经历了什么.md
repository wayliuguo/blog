# 一次请求完整经历了什么

> 承上：本模块前 4 篇 —— 这一篇不讲新知识，用来把前 4 篇接成一条链
> 启下：[Express 快速入门](../04-Express 与 Koa/01-Express 快速入门) —— 用 Express 写出带路由与中间件的 HTTP 接口，并说清 `next()` 不调用时请求为何一直挂起

---

前面四篇是**分层**的：TCP、HTTP、HTTPS、WebSocket，每一篇横切一块知识。这一篇是**纵向**的——把那些一层层的概念穿进一次真实请求里，从"用户在浏览器点下按钮"到"响应渲染完毕"，让概念落地成时间线。

> **心智模型**：前四篇给你的是"零件图"，这一篇给你的是"装配图"。零件都认识，但只有装起来跑一遍，才知道哪里会松、哪里会断。

## 31 步完整链路

把一次 HTTPS 接口请求（浏览器 → 服务端 → 返回渲染）拆成下面 31 步，返回路径反向走：

1. **DNS 解析** —— 浏览器把域名换成 IP；本地缓存 → 系统 hosts → 递归 DNS。
2. **拿到 IP** —— 解析结果带 TTL 缓存，过期前不再查；CDN 常按地域返回不同 IP。
3. **选端口** —— 默认 443（HTTPS）/ 80（HTTP）；HTTP/2、HTTP/3 也跑在对应端口上。
4. **建立 TCP 连接（第一次握手 SYN）** —— 客户端发 SYN，携带初始序列号，进入 SYN_SENT。
5. **服务端回 SYN+ACK** —— 服务端确认客户端序列号并发送自己的序列号，进入 SYN_RCVD。
6. **客户端发 ACK** —— 三次握手完成，连接进入 ESTABLISHED，内核为该连接建立 socket。
7. **HTTPS：TLS 握手之 ClientHello** —— 客户端发支持的 TLS 版本、密码套件、随机数。
8. **HTTPS：TLS 握手之 ServerHello + 证书** —— 服务端选定套件、发证书链（含公钥）。
9. **HTTPS：验证证书** —— 客户端校验证书链、域名、有效期，并核对本地系统时间是否可信。
10. **HTTPS：协商密钥** —— 通过 ECDHE 之类交换得到对称密钥，后续报文用该密钥加密。
11. **HTTPS：Finished** —— 双方交换校验摘要，握手完成，进入加密应用数据传输。
12. **浏览器组装 HTTP 请求报文** —— 方法、路径、Host、Cookie、Content-Type 等头部就绪。
13. **浏览器把请求报文写入 socket** —— 数据交给内核，变成待发送的字节流。
14. **内核 TCP/IP 协议栈处理** —— TCP 分段、加上 TCP 头与 IP 头，必要时在 IP 层分片。
15. **网卡发出** —— 字节流经网卡变成电信号/光信号，按 MTU 成帧送上网络。
16. **网络路由转发** —— 经交换机、路由器、可能过 CDN / 负载均衡，逐跳逼近服务器。
17. **抵达服务器网卡** —— 服务端网卡收包，触发中断，数据送入内核网络栈。
18. **内核协议栈重组** —— 去 IP/TCP 头、按序列号重组字节流，放入该 socket 的接收缓冲区。
19. **内核通过 epoll 感知可读** —— 该 fd 就绪，epoll_wait 返回"可读"事件（kqueue/IOCP 同理）。
20. **libuv 取到就绪事件** —— 事件循环从 epoll 把就绪 fd 取出，封装成上层回调。
21. **事件循环 poll 阶段执行回调** —— Node 在 poll 阶段消费 I/O 事件，驱动后续 JS 执行。
22. **Node HTTP 模块解析报文** —— 从字节流中解析出方法、路径、头部，触发内部逻辑。
23. **触发 'request' 事件** —— http.Server 发出 request，把 req（Readable）/ res（Writable）交给框架。
24. **Express/Koa 中间件链执行** —— 请求沿中间件栈层层穿过，可改写 req/res、可短路返回。
25. **NestJS Middleware → Guard** —— 先走中间件，再走守卫做身份认证与权限判断。
26. **Interceptor（前） → Pipe** —— 拦截器在调用前做日志/超时，Pipe 做 DTO 校验与类型转换。
27. **Controller 方法执行** —— 路由匹配到具体方法，调用 Service 处理业务逻辑。
28. **Service 业务逻辑** —— 可能查 MySQL、读 Redis、调第三方；其间网络 I/O 异步进行。
29. **Interceptor（后）序列化响应** —— 返回数据在拦截器里被序列化、包装为标准结构。
30. **Filter 是否介入** —— 无异常则 ExceptionFilter 不触发；有异常则统一包装成错误响应。
31. **写响应 → 浏览器渲染** —— 经 res 可写流写状态行/头/体（大响应触发背压与 drain）；Keep-Alive 决定连接保留或四次挥手关闭；浏览器解析并渲染。

> **心智模型**：你写的那行 `await service.getData()` 只是第 28 步；前面 27 步全是"为了把请求安全送到这一行"做的铺垫，后面 3 步是"把结果安全送回去"。

## 每一步出问题时是什么现象

| 出问题的环节 | 线上现象 | 通常往哪里查 |
|------|------|------|
| DNS 解析（步骤 1-2） | 域名解析失败、解析到旧 IP、部分地区打不开 | DNS 配置、TTL 是否过长、CDN 解析策略 |
| TCP 握手（4-6） | 连接超时、`connection refused`、端口不通 | 防火墙、安全组、服务是否监听、端口占用 |
| TLS 证书（7-10） | 证书过期、握手失败、浏览器红锁 | 证书有效期、系统时间、证书链是否完整 |
| 内核接收缓冲区（18） | 连接数一高就丢包、吞吐上不去 | 内核 `net.core.rmem`、backlog、fd 上限 |
| epoll / 事件循环（19-21） | 并发上不去、请求堆积、延迟陡增 | 是否有同步阻塞调用占住事件循环 |
| 中间件链（24） | 请求被莫名改写/短路、跨域失败 | 中间件顺序、CORS、鉴权中间件 |
| Guard / Pipe / Filter（25-30） | 401/403、DTO 校验 400、异常格式不统一 | 守卫逻辑、DTO 装饰器、ExceptionFilter |
| Keep-Alive 超时不匹配（31） | `ECONNRESET`、`502`、`504` | Node `server.keepAliveTimeout` vs Nginx `keepalive_timeout` |
| 上游未关连接 / 超时（31） | 客户端等到 `504`、网关超时 | 上游超时配置、代理 `proxy_read_timeout` |
| 响应体过大 / 背压（31） | 内存涨、响应慢、客户端收不全 | res 背压、是否忘了监听 `drain`、流处理 |
| 服务进程假死（整体） | 进程在但完全不响应、健康检查失败 | 死循环、未处理的 Promise、事件循环饥饿 |

> **心智模型**：同一症状常常对应不同层。看到 `ECONNRESET`，别先怀疑代码——先看是连接哪一端先关的，多半是 Keep-Alive 超时不匹配。

## NestJS 到底封装了什么

NestJS 不是重新发明网络栈，而是在 Node 已有的能力上叠了一层"结构化外壳"。纵向分层：

```
业务代码（@Controller / @Get / @Body）
     ↓
NestJS（路由注册、依赖注入、Guard、Interceptor、Pipe、Filter）
     ↓
Express / Koa Adapter（中间件链、req/res 增强）
     ↓
Node.js HTTP 模块（报文解析、事件触发）
     ↓
TCP Socket（net.Socket，本质是 Duplex Stream）
     ↓
libuv + 内核（epoll / kqueue / IOCP）
```

逐层看它替你做了什么、不知道会踩什么坑：

| 分层 | 这一层替你做了什么 | 不知道它会踩的坑 |
|------|------|------|
| 业务代码 | 用装饰器声明路由与参数，专注逻辑 | 以为 `@Body()` 自动校验，其实没挂 Pipe 就被脏数据打穿 |
| NestJS | DI 容器、Guard 鉴权、Interceptor 横切、Pipe 校验、Filter 统一异常 | 中间件顺序、拦截器执行时机错，导致日志/超时逻辑失效 |
| Express/Koa Adapter | 把 Node 原生 req/res 包成更易用的对象，串起中间件链 | 忘记 `next()` 导致请求挂起；res 写了两次报 `ERR_HTTP_HEADERS_SENT` |
| Node HTTP 模块 | 解析原始报文、触发 `'request'`，省去手撕字节流 | 读请求体要 `chunks + Buffer.concat`，否则中文被截断 |
| TCP Socket | 把字节流抽象成 Duplex Stream，读写像操作流 | 不了解粘包拆包，自定义协议就解析错位 |
| libuv + 内核 | 用 epoll 感知就绪事件，异步处理海量连接 | 误以为所有 I/O 都走线程池；同步阻塞调用拖垮整个事件循环 |

## 既然都封装了，为什么还要学这一层

核心论点：**写业务代码时你永远待在最上面一层；出问题时，问题往往在最下面几层。**

封装让你"写得快"，但封装挡不住"底层病"——它只会把底层的错误翻译成一句含糊的 `ECONNRESET` 或 `504` 甩给你。你能不能秒定位，取决于你是否懂下面那几层。

排障思路链（从现象往里钻）：

```
请求失败
  ├─ 域名能解析吗？          → DNS
  ├─ 端口通吗？TCP 能连上吗？  → TCP / 防火墙 / 安全组
  ├─ HTTPS 握手成功吗？       → TLS / 证书
  ├─ 经过 Nginx 了吗？        → 反向代理 / 负载均衡配置
  ├─ 连接被谁断的？          → Keep-Alive 超时打架
  ├─ Node 收到请求了吗？      → 事件循环是否被阻塞 / 进程是否活着
  ├─ 框架层拦下了吗？         → Guard / Interceptor / Filter / DTO
  └─ 业务逻辑错了吗？         → 日志与链路追踪
```

> **心智模型**：框架是电梯，让你直达 30 层写业务；但电梯坏了，你得会走楼梯——楼梯就是 TCP、HTTP、内核、libuv 这几层。

这就是为什么模块二放在模块三（Express/Koa）和模块五（NestJS）**之前**：先懂被封装的东西，再看封装才有落点。否则框架对你只是"黑盒咒语"，出问题就只会 `重启一下`。

## 面试题

### Q1: 浏览器输入 URL 到页面渲染，经历了哪些主要阶段？

答：DNS 解析拿到 IP → TCP 三次握手建连 →（HTTPS）TLS 握手协商密钥 → 组装并发送 HTTP 请求 → 经网络路由抵达服务端 → 内核重组、epoll 通知 → Node 解析报文并触发 request → 框架与业务处理 → 原路返回响应 → 浏览器解析渲染。本质是"纵向穿过各网络层"的过程。

### Q2: 为什么 Keep-Alive 配置不一致会导致 ECONNRESET 或 502？

答：Node 用 `server.keepAliveTimeout` 决定服务端多久后主动关连接，Nginx 用 `keepalive_timeout` 决定自己侧多久关。若 Nginx 先关而 Node 还以为连接活着、继续写，或对端已关而本端仍在读，就会收到 `ECONNRESET`；网关侧则表现为 `502`。正确做法是让网关的 keepalive 超时**略小于**后端的 `keepAliveTimeout`。

### Q3: NestJS 的 Guard、Interceptor、Pipe、Filter 各自在哪一步、干什么？

答：请求进入后 Middleware 先走（同 Express 中间件）→ Guard 做认证鉴权 → Interceptor 调用前可做日志/超时 → Pipe 做 DTO 校验与转换 → Controller 执行业务 → 返回时 Interceptor 后处理（序列化）→ 若无异常 Filter 不介入，有异常则 ExceptionFilter 统一包装错误响应。

### Q4: 收到 504 和 ECONNRESET，分别该往哪一层查？

答：`504` 通常是**上游超时**——网关等不到后端响应，查上游处理耗时与代理 `proxy_read_timeout`。`ECONNRESET` 通常是**连接被对端异常重置**——优先查 Keep-Alive 超时不匹配、fd 耗尽、或某一端进程崩溃退出。两者一虚一实：504 是"等太久"，ECONNRESET 是"被强行断开"。

### Q5: 为什么说"网络 I/O 不走 libuv 线程池"？

答：TCP/HTTP 的收发由内核完成，libuv 只是用 epoll/kqueue/IOCP 监听 fd 是否就绪，就绪后在事件循环里回调，全程在主线程。线程池只用于文件 I/O、DNS（`dns.lookup` 走线程池，而 `dns.resolve` 走 epoll）、压缩等少数阻塞操作。若在回调里写同步阻塞代码，反而会卡住整个事件循环。
