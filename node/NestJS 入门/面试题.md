# 模块面试题 · 后端架构

## 1. 入门认知与工程骨架

### Q1（1.1）｜ 框架定位：NestJS 的价值为什么在"组织"而非"能力"？
- **判断**：NestJS 能做的事裸 Node.js 都能做，它把"如何组织可维护后端项目"变成一套有约束的约定。
- **展开**：它是"约定"而非"能力"——提供的是模块化、DI、装饰器、请求生命周期这些组织手段，让"能手写的工程"变成"可长期维护的工程"。
- **边界**：业务一旦涉及多业务域、多人协作，模块化与 DI 的收益才开始显现；写一次性脚本或纯静态服务完全没必要上它。
- **佐证**：写 CRUD、发消息、管定时任务这些"能力"在 Express 也能做，NestJS 强在把它们按统一结构组织起来。

### Q2（1.2）｜ 框架定位（认知入口）：NestJS 相比 Express/Koa 多封装了哪几层？
- **判断**：Express/Koa 管"请求→中间件→响应"，NestJS 之上又封四层：DI 容器、装饰器+Metadata、请求生命周期、底层 HTTP。
- **展开**：Express 是"请求 → 中间件 → 响应"；NestJS 是"请求 → 一整套生命周期 → 响应"，多出的 Guard/Pipe/Interceptor/Filter 不是装饰、各司其职。
- **边界**：四层各对应一个认知入口——DI 容器→IoC 与依赖注入、装饰器→控制器与路由、生命周期→请求处理链、底层 HTTP→网络模块。
- **佐证**：分层链 `Controller → NestJS → Express/Fastify → Node HTTP → TCP/epoll`，业务只写最上层 Controller。

### Q3（1.1）｜ 框架定位（误区）：为什么"@Roles('admin') 是魔法"这个理解是错的？
- **判断**：装饰器只往类/方法上贴标签，真正干活的是运行时读标签的框架代码。
- **展开**：`@Roles('admin')` 内部只是 `SetMetadata` 写一条元数据，自己不会拦任何请求；必须有一个 Guard 用 `Reflector` 读出来才生效。
- **边界**：三个常见误区——把 NestJS 当"更高级 Express"（多出的组件各司其职）、觉得装饰器是魔法（只贴标签）、一上来拆微服务（提前塞分布式复杂度）。
- **追问**：所以调试"加了 @Roles 不生效"要查的不是装饰器本身，而是有没有配套 Guard。

### Q4（1.4）｜ 项目骨架：src/ 下四个文件各管什么、怎么启动？
- **判断**：`app.controller.ts` 处理请求、`app.module.ts` 组织代码、`app.service.ts` 承载业务、`main.ts` 是入口。
- **展开**：`main.ts` 里 `NestFactory.create(AppModule)` → 全局装配 → `app.listen(3000)`；业务代码长在 module/controller/service 三件套上。
- **边界**：启动用 `npm run start` 单次、`npm run start:dev` 热重载；`nest g resource` 能连 DTO/实体/模块/控制器/服务一体生成。
- **追问**：`app.module.ts` 是唯一根模块，其余模块从它的 `imports` 递归挂载。

## 2. IoC 与依赖注入

### Q1（2.1）｜ 原理：IoC 和 DI 的区别是什么？
- **判断**：IoC 是思想（把对象创建与依赖管理控制权交给容器），DI 是实现方式（容器创建依赖后通过构造注入）。
- **展开**：IoC 回答"为什么交出去"，DI 回答"怎么交出去"；NestJS 用 DI 来实现 IoC——你只声明依赖，框架启动时扫描、实例化、注入。
- **边界**：两者常被混用当同义词，面试里分清"思想 vs 实现"是加分点。
- **追问**：DI 不是 IoC 的全部——事件驱动、模板方法同样属于控制反转，只是 DI 在框架里最常见。

### Q2（2.1）｜ 原理：为什么 Controller 里不 new 就能用 UserService？
- **判断**：因为容器在启动时已把 UserService 建好塞进构造参数，你写的是"声明需要"不是"创建"。
- **展开**：`private readonly userService: UserService` 一行同时声明字段、类型、依赖；容器读 `design:paramtypes` 后去容器找对应实例注入。
- **佐证**：容器的解析是递归的——先造 UserRepository、再造 UserService、再造 UserController，自底向上装配。
- **边界**：Service 不是框架生命周期的独立阶段，而是业务调用链（Controller→Service→Repository）的一部分。

### Q3（2.1）｜ 设计决策：依赖注入具体好在哪三点？代价是什么？
- **判断**：解耦（类只声明需要什么）、可测（能塞 Mock）、可维护（换实现不影响使用方）。
- **展开**：把"new 谁、何时 new、共享哪个实例"从业务代码收到容器；单测里直接注入假 UserRepository 不必起数据库。
- **边界**：代价是启动期多了"扫描+依赖图解析"复杂度，报错 `Nest can't resolve dependencies` 对新手不友好，但长期收益远大于成本。
- **追问**：加分点在能举出"单测把真实依赖换成 Mock 的具体写法"。

### Q4（2.2）｜ 原理：`@Injectable()` 和 `@Controller()` 的区别？
- **判断**：`@Injectable()` 标记可被容器管理的普通 Provider，`@Controller()` 标记路由入口。
- **展开**：`@Controller()` 本质是经过特殊处理的 `@Injectable()`——被装饰类同时具备 DI 能力和路由处理能力；Nest 扫模块时把 Controller 注册进路由系统、把 Injectable 注册进 DI 容器。
- **边界**：Service/Repository 用 `@Injectable()`，对外入口用 `@Controller()`；`@Injectable({ scope })` 能指定作用域，`@Controller()` 不提供。
- **追问**：两者最终都由同一容器管理实例，区别只在是否参与路由注册。

### Q5（2.2）｜ 原理：为什么必须开启 `emitDecoratorMetadata`？`@Injectable()` 不加会怎样？
- **判断**：开启后 TS 才会在编译产物生成 `design:paramtypes`（记录构造参数类型），Nest 靠它才知道注入谁；没有 `@Injectable()` 容器不认识这个类。
- **展开**：`reflect-metadata` 提供运行时存取元数据能力，`emitDecoratorMetadata` 负责把类型信息写进去，`experimentalDecorators` 与 `emitDecoratorMetadata` 缺一不可。
- **边界**：`emitDecoratorMetadata` 只对**至少有一个装饰器**的类生效——裸类不生成 paramtypes，容器无从解析；装饰器在类定义时（非实例化时）就执行。
- **追问**：Nest CLI 生成的 tsconfig 默认已开，最易出事的是手改编译配置误关。

### Q6（2.3）｜ 原理：Provider 的四种声明方式分别适合什么场景？
- **判断**：`useClass`（Token 即类，最常用）、`useValue`（常量/配置/Mock）、`useFactory`（需运行时逻辑/异步/依赖其他 Provider）、`useExisting`（同实例起别名）。
- **展开**：Provider 在容器里以 Token 为键登记，默认 Token 即类本身；Token 是字符串或 Symbol 时使用方必须 `@Inject(TOKEN)` 指名。
- **边界**：`useValue` 是同一对象引用、注入方改了会影响所有使用方；`useClass` 可配接口抽象做"换实现"，前提是给了 Token。
- **追问**：测试 `overrideProvider().useValue(mock)` 本质就是往同 Token 塞替代项。

### Q7（2.4）｜ 原理：Provider 有哪几种作用域？REQUEST 为什么有性能代价？
- **判断**：`DEFAULT`（单例，默认）、`REQUEST`（每请求一个实例）、`TRANSIENT`（每次注入都新建）。
- **展开**：REQUEST/TRANSIENT 绕过单例复用，每次创建有实例化开销；REQUEST 取当前请求用 `@Inject(REQUEST)`，TRANSIENT 适合无状态工具类。
- **边界**：作用是级联向上污染——单例注入了 REQUEST 作用域 Provider，自己就降级为请求作用域、整条依赖链每请求重建；REQUEST 不能被单例依赖。
- **追问**：要请求上下文又不想降级作用域时，`AsyncLocalStorage` 是更现代的解，不用改作用域就把上下文贯穿调用链。

### Q8（2.5）｜ 原理：NestJS 启动时 DI 容器做了哪几件事？
- **判断**：扫模块树→收集元数据→建依赖图→建容器→先依赖后使用方实例化→注射→绑路由/全局组件→起 HTTP Server。
- **展开**：容器核心是"读 design:paramtypes → 递归 resolve 每个参数 → new Token(...args) → 结果进单例缓存"，缓存命中直接返回就是单例来源。
- **边界**：正因为要确定"先实例化谁"，依赖图有环直接启动失败——这是循环依赖报错的根本原因。
- **追问**：真实实现对应 `InstanceLoader + ModuleRef`，比最小实现多出作用域、循环依赖、`@Optional()` 等能力。

### Q9（2.5）｜ 原理：循环依赖为什么让启动失败？`forwardRef` 做了什么？
- **判断**：容器必须按依赖顺序自底向上实例化，A↔B 时"谁先建"无法确定导致启动失败；`forwardRef(() => Xxx)` 把类型求值推迟到实例化阶段，先建占位后回填。
- **用法**：Provider 层 `@Inject(forwardRef(() => OrderService))`、模块层 `imports: [forwardRef(() => OrdersModule)]`，两层都要写，只加一层仍报错。
- **边界**：循环依赖通常是设计问题的信号，更优解是重构抽第三个服务或把依赖单向化，`forwardRef` 只是止血。
- **追问**：`ModuleRef.run` 运行时按 Token 取实例解决"运行时才知道要谁"，与打破启动期环不是同一件事。

### Q10（2.6）｜ 排障：启动报 `Nest can't resolve dependencies of the XxxService (?)` 怎么三步排查？
- **判断**：九成是模块可见性问题，按"注册→导出→导入"三步自查。
- **展开**：① 该 Provider 是否在某个模块 providers 注册？② 来自别的模块吗？提供方要 `exports`？③ 使用方模块 import 了吗？
- **边界**：三步都对还报错，再检查 `emitDecoratorMetadata` 是否被关、构造参数是否用了接口（接口运行时不存在须 `@Inject(TOKEN)` 或换具体类）。
- **追问**：测试常见坑是 `Test.createTestingModule` 忘了把被依赖 Provider 一起放进去；口诀"要被用先注册、要跨模块先导出、要用别人先导入"。

## 3. 模块系统

### Q1（3.1）｜ 原理：`@Module` 的配置项有哪些？空模块合法吗？
- **判断**：`imports` / `controllers` / `providers` / `exports` 四常用配置，外加 `@Global()` 表达全局可见。
- **展开**：`providers` 注册可注入服务、`controllers` 注册路由入口、`imports` 引入别的模块能力、`exports` 把 Provider 暴露给导入者。
- **边界**：所有项可选，`@Module({})` 空模块完全合法，常被动态模块当"壳"；模块还能 re-export 别的模块 exports 做能力中转。
- **追问**：模块默认是封装的——没写进 exports 的 Provider 别人 import 也拿不到。

### Q2（3.2）｜ 原理：`imports` 和 `exports` 分别管什么？
- **判断**：`imports` 决定"我能用谁"，`exports` 决定"谁能用我"，共同构成模块依赖图。
- **展开**：只有被 exports 导出的 Provider 才能被导入该模块的其他模块注入；模块内部 Provider 对自己模块自动可见、无需导出。
- **边界**：`exports` 只影响"可注入性"不影响"是否实例化"——被 import 的模块 Provider 仍单例一份，多处 import 不会重复创建。
- **追问**：`exports` 里可直接写模块对象（re-export），常用于把一组能力包装成公共包整体转出。

### Q3（3.3）｜ 设计决策：`@Global()` 全局模块解决什么问题？什么时候不该用？
- **判断**：让模块 exports 注册到全局容器，任何模块无需 import 就能注入，省掉大量样板 imports。
- **展开**：NestJS 模块默认隔离，`@Global()` 跳过显式 import 手续；全局限定在 exports 上，没导出的 Provider 依然私有。
- **边界**：滥用会让依赖关系隐式化——看 Service 构造函数猜不出它依赖了哪些基础设施；只对配置/日志/Redis/数据库等真正全局的开。
- **追问**：`ConfigModule` / `LoggerModule` / `RedisModule` 是典型全局模块，`UserModule` 这类业务模块不该开。

### Q4（3.4）｜ 原理：什么是动态模块？`forRoot` 与 `forRootAsync` 的区别？
- **判断**：动态模块是"能在 import 时传参"的模块，用静态方法返回 `DynamicModule` 把配置在导入阶段注入。
- **展开**：`forRoot(options)` 同步接收配置；`forRootAsync({ imports, inject, useFactory })` 把获取推迟到运行时、工厂可 async，适合读 ConfigService 或异步建连接。
- **边界**：`forRoot` 一个模块只应被调一次，`forFeature` 才是按需多次调用，混淆会重复创建连接。
- **追问**：`TypeOrmModule.forRoot({...})` 写死、`forRootAsync` 从 `ConfigService.get('DB_HOST')` 取。

## 4. 控制器与请求链路

### Q1（4.1）｜ 原理：`@Controller('users')` 的参数是什么？一个方法怎么变成一条路由？
- **判断**：字符串参数是路由前缀，最终路径 = 前缀 + 方法装饰器路径（`@Get(':id')` → `GET /users/:id`）。
- **展开**：`@Get` / `@Post` / `@Put` / `@Patch` / `@Delete` 是方法装饰器，运行时把 `{ method, path, handlerName }` 写进类元数据，启动时读元数据绑路由并实例化控制器。
- **边界**：控制器只负责"收请求还响应"，业务逻辑应在 Service 层，否则难测难复用。
- **追问**：`@HttpCode(201)` 改状态码、`@Redirect('/users', 301)` 重定向；不加装饰器时返回值自动序列化 JSON、状态码 200。

### Q2（4.2）｜ 原理：`@Param` / `@Query` / `@Body` / `@Headers` / `@Ip` 各取什么数据？
- **判断**：`@Param` 取路径参数、`@Query` 取查询串、`@Body` 取请求体、`@Headers` 取请求头、`@Ip` 取客户端 IP。
- **展开**：都是参数装饰器，运行时按参数位置从 req 不同部位取值填进 Handler 实参表；数据来源不同，可同时出现在一个方法签名。
- **边界**：`@Param()` 不传参数名返回整个 params 对象；`@Req()` 直接给原始 Request 对象，是逃生舱。
- **追问**：`@Body()` 依赖请求体解析（Nest 默认已接好）。

### Q3（4.3）｜ 规范：PUT 和 PATCH 有什么区别？RESTful 命名上最容易犯什么错？
- **判断**：PUT 是全量替换（没传的字段视为重置），PATCH 是部分更新（只改传了的字段）。
- **展开**：`PUT /users/1` 提交完整用户对象、`PATCH /users/1` 只提交 `{ phone }`；对应 `@Put(':id')` 与 `@Patch(':id')`。
- **边界**：这是语义约定而非框架强制——用 PUT 做部分更新代码照样跑，但会让接口契约与缓存策略混乱。
- **追问**：命名最常见错误是用动词（`/getUsers`、`/deleteUser?id=1`）或在 POST 里做查询；规范做法是资源用复数名词、动作交给 HTTP 方法。

### Q4（4.4）｜ 原理：一次请求里 Middleware、Guard、Interceptor、Pipe、Filter 的精确执行顺序？
- **判断**：`Middleware → Guard → Interceptor(before) → Pipe → Controller → Service → Repository → Interceptor(after) → Response`，任意环节异常进 Exception Filter。
- **展开**：Nest 底层按元数据把各组件组合进一条处理管道，Middleware 在路由匹配前执行、Guard 决定是否继续、Interceptor 包裹整体、Pipe 在 Handler 前处理参数。
- **边界**：Service 不是框架生命周期独立阶段，而是业务调用链的一部分；全局与局部绑定组件会一起参与，同类多个按注册顺序。
- **追问**：Middleware 需在模块 `configure(consumer)` 里用 `forRoutes` 声明生效范围，Guard 及其后组件按控制器/方法就近绑定。

### Q5（4.5）｜ 原理：Middleware、Guard、Pipe、Interceptor、Exception Filter 各自职责？
- **判断**：Middleware「进来之前先做什么」、Guard「能不能进」、Pipe「数据对不对」、Interceptor「进出前后还做点什么」、Filter「出错了怎么返回」。
- **展开**：Middleware 预处理（日志/CORS/cookie/安全头），Guard 认证与角色，Pipe DTO 校验与类型转换，Interceptor 统一响应/耗时统计/缓存，Filter 统一错误响应。
- **边界**：搞混职责就会出现"把权限逻辑写在中间件里"这种能跑但难维护的代码。
- **追问**：五类组件都能全局/控制器/方法级注册，粒度越细优先级越高，就近覆盖全局。

### Q6（4.5）｜ 原理：为什么基于装饰器（如 `@Roles('admin')`）的鉴权要放 Guard 而不是 Middleware？
- **判断**：因为 Guard 的 `ExecutionContext` 能拿到 `getHandler()` 和 `getClass()`，从而配 `Reflector` 读方法级元数据；Middleware 只有 `req/res/next`，不知道请求落到哪个方法。
- **展开**：装饰器负责写标签、运行时框架读标签；能不能读取决于组件拿不拿得到"当前是哪个 Handler"。
- **边界**：`@Roles('admin')` 本身不拦任何请求，必须有个 Guard 读它权限才生效。
- **追问**：Middleware 适合放日志、CORS、cookie 解析等"与路由无关"的横切逻辑。

### Q7（4.5）｜ 原理：拦截器和异常过滤器的分工？
- **判断**：拦截器是包裹执行（Handler 前后都能插逻辑、能改写返回数据），过滤器是异常兜底（只在有异常抛出时触发，翻译成统一错误响应）。
- **展开**：拦截器实现 `intercept(context, next)`，必须 `return next.handle().pipe(...)`，`map` 改响应、`tap` 打点；过滤器实现 `catch(exception, host)`，用 `host.switchToHttp().getResponse()` 写出错误体。
- **边界**：拦截器技术上能用 `catchError`，但最佳实践是把异常交给过滤器，各司其职响应格式才一致。
- **追问**：成功路径格式拦截器管、失败路径格式过滤器管，两边共用同一响应模型。

### Q8（4.5）｜ 原理：`ValidationPipe` 的 `whitelist` 与 `forbidNonWhitelisted` 有什么区别？
- **判断**：`whitelist: true` 剔除 DTO 未定义字段，`forbidNonWhitelisted: true` 更严格——发现未定义字段直接抛 400。
- **展开**：只有 DTO 类里用装饰器声明过的属性才属白名单；请求体多带的 `role: 'admin'` 前者被静默丢掉、后者直接报错。
- **边界**：要容错用 `whitelist`，要严格契约两个都开；`transform: true` 让 `"1"` 自动转 `1`。
- **追问**：项目模板通常直接开 `whitelist + transform`，`forbidNonWhitelisted` 视前后端契约严格程度定。

### Q9（4.5）｜ 原理：自定义 Pipe 怎么实现？`transform` 能拿到哪些信息？
- **判断**：实现 `PipeTransform.transform(value, metadata)`，`value` 是原始参数值、`metadata` 里有 `type`（body/param/query）、`data`（参数名）、`metatype`（目标类型）。
- **展开**：返回处理后的值或抛 `BadRequestException`；`transform` 可返回 Promise 做异步校验（如查库判唯一）。
- **边界**：内置管道（`ParseIntPipe` / `ParseBoolPipe` / `DefaultValuePipe` 等）覆盖大多场景，只在满足不了时自定义。
- **追问**：`@Param('id', ParseIdPipe)` 参数级用法，`app.useGlobalPipes()` 全局用法。

### Q10（4.5）｜ 原理：自定义 Exception Filter 怎么实现？`@Catch()` 不传参表示什么？
- **判断**：实现 `ExceptionFilter.catch(exception, host)` 用 `host.switchToHttp().getResponse()` 写统一错误体；`@Catch()` 不传类型表示捕获所有异常。
- **展开**：先判断 `instanceof HttpException` 决定用 `getStatus()` 还是兜底 500；未知错误记完整堆栈、对外返回模糊提示避免泄露内部细节。
- **边界**：`exception.getResponse()` 可能是字符串或对象，写统一格式要兼容；开发环境可带 `stack`，生产去掉。
- **追问**：全局注册用 `APP_FILTER`（可注入 Logger），就近注册用 `@UseFilters()`。

### Q11（4.7）｜ 原理：`createParamDecorator` 如何拿到请求对象？
- **判断**：工厂函数第二参就是 `ExecutionContext`，调 `ctx.switchToHttp().getRequest()` 拿原生请求对象，返回值成为 Handler 实参。
- **展开**：`export const CurrentUser = createParamDecorator((data, ctx) => { const user = ctx.switchToHttp().getRequest().user; return data ? user?.[data] : user })`，于是 `@CurrentUser('id')` 直接取 ID。
- **边界**：依赖上游（通常是 Guard）已把 `req.user` 挂好，否则读到 undefined；`data` 用于让调用方定制返回。
- **追问**：参数装饰器可和 Pipe 叠加，`@Param('id', ParseIdPipe)` 先取值再转换，职责不冲突。

### Q12（4.7）｜ 原理：`SetMetadata` 和 `Reflector` 在权限控制中如何配合？
- **判断**：`SetMetadata(key, value)` 在类/方法上写元数据，`Reflector` 在 Guard 里读出来与当前用户角色比对后返回布尔值。
- **展开**：`const Roles = (...roles) => SetMetadata('roles', roles)`，Guard 用 `this.reflector.getAllAndOverride<string[]>('roles', [getHandler(), getClass()])` 读、`requiredRoles.some(r => user.roles?.includes(r))` 判权限。
- **边界**：元数据存在类或方法上，读时必须指定正确目标；`getAllAndOverride` 方法覆盖类、`getAllAndMerge` 类方法合并。
- **追问**：`@Public()` 就是同一机制——贴 isPublic 标签，全局 JwtAuthGuard 读到就跳过。

### Q13（4.7）｜ 原理：`ExecutionContext` 的 `switchToHttp` / `switchToRpc` / `switchToWs` 有什么区别？
- **判断**：三者分别用于取 HTTP、微服务 RPC、WebSocket 上下文，是同一套 Guard/Interceptor/Filter 跨传输层复用的关键抽象。
- **展开**：`switchToHttp()` 返回提供 `getRequest()`/`getResponse()` 的 `HttpArgumentsHost`；`switchToRpc()` 用 `getData()` 取消息体；`switchToWs()` 用 `getClient()` 取 socket 客户端。
- **边界**：三者不能混用——WS 连接调 `switchToHttp()` 会抛异常，跨协议组件先 `getType()` 再分支。
- **追问**：`getClass()` 和 `getHandler()` 任何协议都可用，是路由粒度元数据读取入口。

### Q14（4.7）｜ 原理：装饰器本身为什么不能是 async？异步校验逻辑该放哪？
- **判断**：装饰器在类定义阶段同步执行，返回 Promise 没任何人 await，等于白写；异步逻辑应放 Guard 或 Interceptor。
- **展开**：`canActivate` 返回类型允许 `boolean | Promise<boolean> | Observable<boolean>`，异步判断是框架原生支持的；`transform` 也可返回 Promise。
- **边界**：参数装饰器里做异步取值同样不可行，返回值就是参数值没有 await 机会，需异步取值放 Pipe。
- **追问**："自定义装饰器里能不能查库判权限"的答案是——装饰器不能，但"装饰器 + Guard"可以。

### Q15（4.7）｜ 场景设计 · 设计一个 RBAC 权限管理系统
**题目要求**：用户→角色→权限三层模型，支持接口级权限校验，说明还能做到哪些粒度。
- **判断**：用"装饰器声明 + Guard 校验"而不是在服务层逐个 if，规则和路由定义放在一起不会漏配。
- **展开**：数据模型 `users/roles/permissions` 三张主表加 `user_roles/role_permissions` 两中间表，权限项用"资源:动作"命名；`@RequirePermissions('user:create')` 内部 `SetMetadata`，`PermissionsGuard.canActivate` 用 `getAllAndOverride` 读出要求、从 `req.user` 取 userId、查（并缓存）权限集合用 `every` 判断。
- **边界**：数据级权限（"只看自己订单"）Guard 解决不了，要在 Service 查询拼接属主条件；字段级权限（脱敏）适合序列化层处理；权限缓存有"改权限到生效"延迟。
- **佐证**：`{ provide: APP_GUARD, useClass: PermissionsGuard }` 全局注册才能注入 UserService，`JwtAuthGuard` 排前面先备好 `req.user`。

### Q16（4.8）｜ 原理：`app.useGlobalXxx()` 和 `APP_XXX` 提供者两种全局注册有什么区别？
- **判断**：`app.useGlobalInterceptors(new X())` 手工塞实例无法注入依赖；模块 providers 注册 `{ provide: APP_INTERCEPTOR, useClass: X }` 由容器创建、可注入依赖。
- **展开**：全局组件几乎总要依赖别的服务（日志/权限/配置），推荐统一用 `APP_*` provider 方式；`APP_GUARD` / `APP_PIPE` / `APP_FILTER` 同理。
- **边界**：在根模块注册的 `APP_*` 才是全局，子模块注册只对该模块生效；多个同类全局组件按注册顺序执行。
- **追问**：即使组件无依赖（如纯 ValidationPipe）也建议统一 `APP_PIPE` 保持风格一致、日后加依赖不用改结构。

### Q17（4.5）｜ 排障：全局拦截器里 `@Inject()` 的服务是 `undefined`，为什么？
- **判断**：几乎肯定是用了 `app.useGlobalInterceptors(new LoggingInterceptor())`——手工 new 的实例不在 DI 容器内，构造参数不被注入。
- **正解**：在模块 providers 注册 `{ provide: APP_INTERCEPTOR, useClass: LoggingInterceptor }`，让容器创建实例依赖才被解析。
- **边界**：`APP_GUARD` / `APP_PIPE` / `APP_FILTER` 同理；根模块注册才是全局。
- **追问**：全局组件需要读 req 时 `APP_*` 也可指向 `Scope.REQUEST` 的类。

### Q18（4.5）｜ 排障：一个接口突然变慢，在 NestJS 里怎么快速定位到环节？
- **判断**：先拦截器打点拿"框架侧耗时"，再用日志分业务耗时，比盲猜是参数校验还是 SQL 快得多。
- **展开**：`TimingInterceptor` 在 `intercept` 记 `Date.now()`、`next.handle().pipe(tap(...))` 算差值；要量全链路把起点挪到 Middleware。
- **边界**：拦截器量到的是"进入 Handler 到返回"不含 Guard/Pipe 开销；异步操作要在正确时机打点否则把排队当业务耗时。
- **追问**：耗时集中 Pipe→查 DTO 有无同步重活/远程调用；集中 Handler→开 SQL 日志看缺索引或 N+1。

### Q19（4.5）｜ 场景设计 · 设计一个统一错误处理方案
**题目要求**：让所有接口返回格式一致错误响应，能区分"参数错、业务错、系统错"。
- **判断**：过滤器是异常的唯一出口，做成"分派中心"，业务代码只 `throw` 语义化异常不必关心响应拼装。
- **展开**：统一响应体 `{ code, message, details? }`；业务异常类继承 `HttpException` 携带业务码；全局 `@Catch()` 过滤器按类型分派（BusinessException→用自己 code/status、HttpException→用 getStatus()、未知→500+固定文案并写日志）；ValidationPipe 的字段信息抽出拼进 `details`。
- **边界**：就近 `@UseFilters()` 会覆盖全局过滤器，排查格式不一致先看有无局部注册；业务码是对外契约新增容易改难，前期留分段。
- **佐证**：用 `{ provide: APP_FILTER, useClass: GlobalExceptionFilter }` 注册可注入日志，成功响应交给 TransformInterceptor。

## 5. 数据库集成

### Q1（5.1）｜ 原理：TypeORM 集成要哪三步？
- **判断**：`forRoot` 配连接 → `@Entity` + 列装饰器定义表结构 → `forFeature([Model])` 在业务模块注册 Repository。
- **展开**：`TypeOrmModule.forRoot({ type, host, entities, synchronize })` 根模块配连接；`TypeOrmModule.forFeature([User])` 业务模块注册；关系装饰器配 `@JoinColumn` / `@JoinTable`。
- **边界**：连接配在根模块，Repository 按业务模块 `forFeature` 注册，两者各司其职。
- **追问**：实体主键用 `@PrimaryGeneratedColumn()`，字段大小/唯一/默认值/时间戳用 `@Column` 各参数声明。

### Q2（5.2）｜ 原理：实体一对一/一对多/多对多关系怎么声明？
- **判断**：一对多用 `@OneToMany` + 对方 `@ManyToOne` 并在外键一侧 `@JoinColumn({ name })` 指列名；多对多需一方加 `@JoinTable()` 建中间表。
- **展开**：只有 `@JoinTable()` 那一侧在库里建中间表，另一侧写对应关系即可；`@JoinColumn` 指定外键列名。
- **边界**：关系两边装饰器要对应写，名称与反向关系指对，否则 ORM 无法建关联。
- **追问**：级联删除用 `@ManyToOne(..., { onDelete: 'CASCADE' })` 决定删除时的行为。

### Q3（5.3）｜ 原理：事务用 QueryRunner 怎么保证原子性？
- **判断**：`createQueryRunner() → connect() → startTransaction() → manager 操作 → commit`，出错 `rollback`，finally 里 `release()`。
- **展开**：先扣余额再建订单两写必须同一个 QueryRunner 的 manager 才在一个事务内；`@InjectDataSource()` 注入 DataSource 拿 `createQueryRunner()`。
- **边界**：一定要 `finally` 里 `release()` 释放连接，否则连接池泄漏。
- **追问**：事务、原生 SQL 等 Repository 覆盖不到的场景直接注入 DataSource。

### Q4（5.4）｜ 场景设计：`synchronize: true` 能上生产吗？
- **判断**：不能。它是开发期便利开关，生产环境必须关。
- **展开**：`synchronize` 比对实体与真实表结构自动改表，改法由 ORM 决定，可能直接 DROP 列/表导致数据不可逆；多实例并发启动还会互相打架。
- **做法**：开发开 `synchronize: true` 图方便；生产 `synchronize: false` + TypeORM Migration（`migration:generate` / `migration:run` / `migration:revert`）管理结构变更，可评审、可回滚。
- **追问**：临时救火也别直接改库，先补迁移保证"代码版本→表结构"可追溯；`logging` 同理长期全量开拖慢服务。

## 6. 认证与安全

### Q1（6.1）｜ 原理：密码应该怎么存？为什么用 bcrypt 而不是直接存密文/MD5？
- **判断**：密码要加盐哈希后再入库，用 bcrypt 这类慢哈希抗彩虹表，明文与简单哈希都不可接受。
- **展开**：注册 `bcrypt.hash(password, salt)` 存库，登录 `bcrypt.compare` 比对；bcrypt 是慢哈希让暴力破解成本陡增。
- **边界**：别把密码放 JWT Payload（Base64 可解）；掉库不等于明文泄露是有盐慢哈希的价值所在。
- **追问**：先查 email 是否已存在抛 `ConflictException`，DTO 用 `@IsEmail` / `@MinLength` / `@Matches` 做格式校验。

### Q2（6.2）｜ 原理：JWT 由哪三部分组成？为什么服务端可以不存 Session？
- **判断**：`Header.Payload.Signature` 三段用 `.` 分隔，各段 Base64URL 编码；服务端用同一密钥重算签名比对就能信 Payload 未被篡改，所以不必存 Session。
- **展开**：Header 声明算法与类型，Payload 放声明（`sub`/`exp`/`iat` 及自定义 userId/role），Signature = HMAC-SHA256(header + "." + payload, secret)。
- **边界**：Payload 只是 Base64 编码不是加密，绝不能放密码等敏感数据；Signature 只防篡改不提供保密性。
- **追问**：JWT 的无状态代价是"无法主动吊销"，这正是引入会话表的原因。

### Q3（6.2）｜ 原理：JWT 和 Cookie 是竞争关系吗？
- **判断**：不是。JWT 是凭证内容、Cookie 是保存方式，两者可以组合。
- **展开**：把 JWT 放进 HttpOnly Cookie 既保留无状态校验便利又降低 XSS 窃取 Token 明文的风险。
- **边界**：放 Cookie 要防 CSRF 配 `sameSite`，放 Authorization 头免疫 CSRF但前端要自己保管好 Token——两种存法各有一处要防。
- **追问**："用 JWT 还是用 Cookie"是伪问题，真问题是"凭证放哪、防哪类攻击"。

### Q4（6.4）｜ 原理：双 Token 方案为什么把 Access 和 Refresh 拆开？各自的存放与职责？
- **判断**：单 Token 长则泄露危害大、短则体验差且无法主动吊销；Access 短(15m)只管访问、Refresh 长(7d)只管换发，Refresh 必须有服务端能主动作废的能力。
- **展开**：Access 放前端内存 / `Authorization` 头，Refresh 放 HttpOnly Cookie；短凭证每次请求都传输所以越短越安全，长凭证只用于换发所以越长越省心。
- **边界**：Access 越短越安全，Refresh 越长越省心，但 Refresh 若无法服务端作废就退化成无法吊销的长效 JWT。
- **追问**："客户端存不住、服务端管不了"是单 Token 的死穴，双 Token + 服务端会话表正是解药。

### Q5（6.4）｜ 原理：Refresh Token 应该存 localStorage 还是 HttpOnly Cookie？
- **判断**：Refresh 放 HttpOnly Cookie，Access 放前端内存。
- **展开**：`localStorage` 任何 JS 都能读、页面有 XSS 就被发走；HttpOnly Cookie 禁止 JS 访问挡掉大部分窃取路径；Access 要前端塞 Authorization 头所以留内存。
- **配置**：`httpOnly` + `secure` + `sameSite` + `path: '/auth/refresh'`（只在刷新接口携带缩小暴露面）+ `maxAge`。
- **追问**：跨域要放宽 `sameSite` 到 `lax`/`none` 并让前端 `fetch` 带 `credentials: 'include'`，否则 Cookie 带不上来（最常见刷新 401 原因）。

### Q6（6.4）｜ 安全：HttpOnly Cookie 能防住 XSS 吗？
- **判断**：不能。它只让 JS 读不到 Token 明文，不能让 XSS 发不出请求。
- **展开**：被注入脚本虽拿不到 Cookie 内容，但可借浏览器带 Cookie 发请求（凭证由浏览器自动附加），仍能冒充用户操作。
- **边界**：`secure` 防明文、`sameSite` 缓解 CSRF、`path` 缩小暴露面，三者都是"降低风险"而非"消灭风险"。
- **追问**：真正 XSS 治理是输出转义 + CSP + 依赖审计；Cookie 加固只是纵深防御一层，根本对策修掉漏洞本身。

### Q7（6.5）｜ 原理：为什么 Refresh Token 不能像密码一样用 bcrypt 存库？
- **判断**：bcrypt 只处理输入前 72 字节，Refresh Token 往往更长，超出被截断会导致"内容不同但前 72 字节相同"两 Token 校验都被判真。
- **展开**：Refresh 只需单向校验（确认是否当初发的那个）、不怕暴力枚举（本身随机长串），用 `sha256(token)` 存哈希即可，还比 bcrypt 快。
- **边界**：Token 明文只在签发响应给客户端一次，服务端永远只留哈希——拖库也拿不到可用 Token。
- **追问**：坚持用 bcrypt 得先摘要到 72 字节内，比直接 SHA-256 更绕没理由；签发时 payload 带随机 jti 避免同一秒两台设备签出相同 Token。

### Q8（6.5）｜ 设计决策：为什么需要 AuthSession 表而不是只发 JWT？
- **判断**：JWT 本身无法被服务端主动吊销，AuthSession 表（User 1:N）把"能作废某个 Token"的能力补回来，同时支持多设备会话。
- **字段**：`refreshTokenHash`（校验是否真实签发）、`deviceId`（区分设备避免一台刷新踢另一台下线）、`userAgent/clientInfo`（活跃设备列表）、`expiresAt`（服务端过期闸门）、`revoked`（软删除标记）。
- **边界**：单设备登出只吊销该条，全设备登出 `updateMany({ where: { userId, revoked: false } })` 一次作废全部——纯 JWT 做不到。
- **追问**：它把无状态 JWT 的便利和会话可控性重新缝合，代价是刷新环节查一次库（访问环节仍无状态）。

### Q9（6.6）｜ 原理：什么是 Refresh Token Rotation？它解决了什么问题？
- **判断**：每次用 Refresh 换 Access 都签一对全新 Token 并让旧记录 `revoked=true` 立即失效，实现"重放即失效"。
- **流程**：校验 JWT 签名与过期 → 算哈希查库比对且 `revoked=false` → 旧记录置 revoked → 签新 Access + 新 Refresh → 写新会话记录（沿用 deviceId）。
- **边界**：轮换引入"并发刷新"问题——同一客户端并发两个刷新，第二个用已吊销旧 Token 失败，前端要做"刷新串行化/单飞"。
- **追问**：写新会话时 deviceId 要沿用旧记录，否则活跃设备列表凭空多出一台；若攻击者先重放旧 Token，合法用户刷新也会失败（被迫重登的异常信号）。

### Q10（6.6）｜ 安全/场景：用户点了"退出登录"，为什么手里的 Access Token 还可能短期有效？
- **判断**：登出只吊销服务端会话记录，而 Access Token 是无状态的不查库就认它。
- **展开**：Access 校验只看签名和 exp 不看 DB；登出把 `AuthSession.revoked` 置 true 只影响刷新环节——Refresh 再也换不到新 Access，但手里这张在剩余短生命周期（典型 15m）内仍可用。
- **应对**：接受短窗口最常见；安全要求高时给 Access 加版本号/签发时间戳，只对高敏接口额外校验或查黑名单。
- **追问**：想"登出即失效"就得每请求查库/缓存，等于放弃 JWT 无状态优势——这是明确取舍，不是设计缺陷。

### Q11（6.6）｜ 排障：双 Token 场景有哪些高发坑？
- **判断**：`verifyAsync` 忘 await、跨域 Cookie 带不上、刷新缺过期校验、Refresh 明文入库、轮换后旧 Token 还能用。
- **展开**：`await jwtService.verifyAsync(token)`，校验错误显式转 `UnauthorizedException`；刷新同时判断 `expiresAt > now()` 与 `revoked`；永远只存 SHA-256 哈希；每次刷新先把旧记录 `revoked = true`。
- **边界**：跨域 Cookie 需要后端 `sameSite=lax/none`+`secure`、前端 `fetch` 带 `credentials: 'include'`。
- **追问**：这些坑都来自"无状态 JWT 与可控会话"两部分缝合处的细节，逐一对应到会话表字段与刷新流程。

### Q12（6.6）｜ 场景设计 · 设计一个用户注册登录系统
**题目要求**：支持邮箱注册、密码登录、令牌认证，并说明如何做到"登录态可控"。
- **判断**：密码 bcrypt 加盐存库、双 Token 认证、Refresh 哈希入会话表轮换，把"无状态访问"与"可控登录态"缝合。
- **展开**：注册 `RegisterDto`（`@IsEmail`+`@Matches`）先查邮箱存在返回 409、`bcrypt.hash` 入库返回 201；登录查不到或 compare 失败返回**同一文案** 401（避免枚举已注册邮箱），成功后签发 Access(15m)+Refresh(7d)；Access 走响应体、Refresh 用 Set-Cookie HttpOnly；JwtStrategy 解析 Bearer、`validate` 返回值挂 `req.user`，全局 JwtAuthGuard 用 `@Public()` 放行登录注册。
- **边界**：登出后 Access 短窗口仍有效，接受或对高敏接口校验版本号；轮换并发刷新要串行化。
- **佐证**：密码/Token 选型不同——密码 bcrypt（慢哈希防彩虹表）、Refresh SHA-256（长随机串只需单向校验且 bcrypt 有 72 字节截断）。

## 7. 实时通信（WebSocket）

### Q1（7.1/7.2）｜ 原理：WebSocket 与 HTTP 轮询各有什么优缺点？NestJS 怎么收发消息？
- **判断**：WebSocket 全双工长连接实时性高、头部开销小，适合聊天与主动推送；HTTP 轮询实现简单纯无状态，但延迟受间隔限制、空轮询浪费带宽。
- **展开**：`@WebSocketGateway({ cors, namespace })` 声明网关，`handleConnection`/`handleDisconnect` 管生命周期，`@WebSocketServer()` 注入 Server、`server.emit` 全局广播、`client.to(room).emit` 定向推，`@SubscribeMessage` 收消息、`client.join(room)` 入房。
- **边界**：长连接要处理心跳与断线重连；服务多实例需额外消息总线（适配器接 Redis）才能跨实例广播。
- **追问**：SSE 是第三种选择——服务端单向推、走普通 HTTP、浏览器自带重连，只推不收比 WebSocket 省事。

### Q2（7.3）｜ 场景设计：Gateway 如何在 HTTP 控制器里推送消息？
- **判断**：Gateway 用 `@WebSocketServer()` 注入 Server，但控制器不该直接依赖 Gateway——把 Server 交给一个共享服务持有，控制器注入该服务再调 emit。
- **展开**：`NotificationService` 存 `private server: Server` 并暴露 `setServer` / `notifyAll` / `notifyRoom`；Gateway 初始化时把 `this.server` 交给它，控制器只管调 `notifyAll`。
- **边界**：HTTP 控制器和 Gateway 分属不同传输层，直接互相关注会耦合；中间隔一个服务两边只依赖服务，便于单测替换。
- **追问**：连接时鉴权取 `client.handshake.auth.token` 失败 `client.disconnect()`，通过后置 `client.data.user` 随取随用；多实例需适配器接 Redis 打通广播。

## 8. 文件上传

### Q1（8.1）｜ 原理：`diskStorage` 和 `memoryStorage` 的区别？
- **判断**：`diskStorage` 边收边写磁盘适合大文件低内存，`memoryStorage` 读成 Buffer 放内存适合小文件或要立刻转存/压缩。
- **展开**：头像直存磁盘用 `diskStorage` + 唯一文件名（`Date.now()`+随机数+extname）避免重名与中文乱码；要转对象存储或压缩生成的用 `memoryStorage` 拿 `file.buffer`。
- **边界**：`memoryStorage` 并发上传大文件内存陡增必须配 `limits.fileSize` 兜底，否则被大文件打爆。
- **追问**：两种模式业务拿到的字段不同——`memoryStorage` 用 `file.buffer`、`diskStorage` 用 `file.path`。

### Q2（8.2）｜ 设计决策：文件类型校验放 `fileFilter` 还是自定义 Pipe？
- **判断**：两者都做、职责不同——`fileFilter` 负责"早拒绝"，Pipe 负责"可复用的业务规则"。
- **展开**：`fileFilter` 在 Multer 写入磁盘**之前**执行，`cb(new BadRequestException(), false)` 直接拦掉不产生落盘开销；Pipe 在参数进 Handler 前执行，能拿到 `size`/`mimetype`/`originalname` 做上限/白名单/命名等规则。
- **选择**：只做 MIME 白名单 + `limits.fileSize` 用 fileFilter；多接口复用一套规则封成 `FileValidationPipe`。
- **追问**：mimetype 由客户端提供可伪造，安全要求高读文件头二次确认或上传后异步扫描；`limits.fileSize` 超限的异常要确认全局过滤器正确映射 4xx。

### Q3（8.3）｜ 场景设计 · 设计一个文件上传服务
**题目要求**：支持单/多文件上传，做类型与大小校验，上传后可访问。
- **判断**：校验前置到 Multer 层最早拒绝非法请求，可复用规则抽成 Pipe，重命名存储消除路径穿越与重名覆盖。
- **展开**：单文件 `FileInterceptor('file')`+`@UploadedFile()`、多文件 `FilesInterceptor('files', 10)`+`@UploadedFiles()`；`limits.fileSize` 设上限、`fileFilter` 做 MIME 白名单不合法抛 `BadRequestException`；`diskStorage` 用 `Date.now()+随机数+extname` 重命名；`app.useStaticAssets(join(...), { prefix: '/uploads/' })` 暴露静态目录。
- **边界**：上传接口必须挂鉴权 Guard；`mimetype` 可伪造；单机磁盘横向扩展成瓶颈，多实例前规划对象存储，生产静态资源交 Nginx/CDN。
- **佐证**：头像链路：前端限格式大小 → 服务端验类型/大小/恶意文件 → 重命名存储 → `sharp` 缩略图(可选) → 返回 URL 存用户表 → 配静态访问。

## 9. 定时任务与队列

### Q1（9.1）｜ 原理：`@Cron` / `@Timeout` / `@Interval` 各自语义？怎么动态管理？
- **判断**：`@Cron` 到点执行、`@Timeout` 只跑一次、`@Interval` 固定间隔重复，前提都要 `ScheduleModule.forRoot()`。
- **展开**：`@Cron` 用 `CronExpression` 常量或 `'*/10 * * * *'` 表达式；`SchedulerRegistry` 可 `addCronJob` 加、`getCronJob(name).stop()` 停、`getCronJobs()` 列全部。
- **边界**：`@Cron` 在多实例部署下每个实例各跑一次，需分布式锁或独立调度进程；不带重试语义，失败就等下一周期。
- **追问**：`SchedulerRegistry` 动态增删适合"运营后台配置定时报表"这类需求。

### Q2（9.2）｜ 原理：Bull 队列如何保证任务不丢失？
- **判断**：Bull 基于 Redis 持久化，任务先写 Redis 再被消费；消费者崩溃时未确认任务重新入队，语义是"至少一次投递"。
- **配置**：`attempts: 3` 控制最大重试、`backoff: 5000` 控制重试间隔避免风暴、`removeOnComplete: true` 防 Redis 无限增长、延迟任务用 `delay`。
- **边界**："至少一次"意味着可能重复消费，所以消费端必须做幂等（业务唯一键+唯一索引兜底），只配 attempts 不配幂等重试就变重复扣款。
- **追问**：下游服务支持幂等键重试天然安全；超最大重试次数进失败队列告警靠人工或定时补偿。

### Q3（9.3）｜ 选型：`@Cron` 和 Bull 队列分别适合什么场景？
- **判断**：`@Cron` 定时触发、到点就跑不管上次结果；Bull 异步解耦带重试/延迟/并发控制。
- **场景**：每日报表、健康检查用 `@Cron`/`@Interval`；验证码邮件、订单 30 分钟未支付自动取消、注册欢迎邮件用 Bull（延迟+重试）。
- **原理**：队列是生产者消费者模式能削峰填谷——高峰期只管写进队列消费者按自己节奏处理。
- **追问**：固定时点/轻量间隔用 `@Cron`，异步且需失败重试或延迟动作用 Bull 不阻塞主流程。

### Q4（9.2）｜ 场景设计：队列任务失败怎么重试才不重复扣款？
- **判断**：重试必须与幂等一起设计，只配 `attempts` 不够。
- **展开**：Bull 默认"至少一次投递"同一任务可能被处理两次；① attempts+backoff 控制重试与退避避免风暴；② 消费端按业务唯一键幂等或数据库唯一索引兜底；③ 超最大次数进失败队列告警。
- **边界**：长时间阻塞任务要设合理并发与超时否则队列堆积；`removeOnComplete: true` 防 Redis 无限增长。
- **追问**：队列积压先看消费 vs 生产速度，再决定加消费者、拆细任务或搬出耗时操作。

## 10. 微服务架构

### Q1（10.1）｜ 原理：微服务间通信有哪两类？NestJS 分别用什么 API？
- **判断**：同步（请求—响应）用 `ClientProxy.send()` 配 `@MessagePattern()`；异步（事件广播、发完不管）用 `ClientProxy.emit()` 配 `@EventPattern()`。
- **展开**：`send()` 返回 Observable 等对端返回结果；`emit()` 是发布事件不等待响应；两者都走 `ClientsModule.register()` 配好的传输通道。
- **边界**：`emit()` 没有回执，可靠性取决于传输层（RabbitMQ 有 ACK/持久化，Redis Pub/Sub 和裸 TCP 没有），"必须送达"别只靠 emit。
- **追问**：网关用 `ClientsModule.register([{ name: 'USER_SERVICE', transport, options }])` 声明通道、`@Inject('USER_SERVICE')` 注入 ClientProxy。

### Q2（10.2）｜ 选型：微服务传输方式怎么选（TCP / Redis / RabbitMQ / Kafka）？
- **判断**：按"要不要可靠投递、要不要回放、吞吐多大"选，而不是按流行度选。
- **对照**：TCP 点对点延迟最低适合内部同步 RPC但服务重启丢消息；Redis Pub/Sub 已有 Redis 零新增中间件同样"发出去就没了"；RabbitMQ 队列持久化+路由灵活+ACK 适合必须送达并需重试；Kafka 高吞吐+分区+可回放适合日志/埋点海量数据。
- **边界**：NestJS 侧切换只改 transport 与 options，业务里 `@MessagePattern`/`@EventPattern` 不用动——这是最大便利。
- **追问**：混合常见——读多写少查询走 TCP 同步，跨服务状态变更走 RabbitMQ 事件，各取所长。

### Q3（10.3）｜ 设计决策：微服务下如何保证数据一致性？
- **判断**：单机事务解决不了跨服务一致性，生产用"本地事务+消息+补偿"实现最终一致。
- **原理**：主流是 Saga（编排式或协同式）与 TCC（Try-Confirm-Cancel）；NestJS 常见落地是"先写本地库、再投事件、下游消费失败靠重试与补偿兜底"。
- **边界**：最终一致意味着中间态对用户可见（"订单已创建、积分待发放"），前端要能表达；想要强一致得引入分布式事务框架，代价是吞吐和复杂度。
- **追问**：本地事务提交与消息投递之间有"库写了但消息没发出"的窗口，严格场景用本地消息表/发件箱补齐。

### Q4（10.3）｜ 设计决策：单体做得好好的，什么时候才该拆微服务？
- **判断**：出现"拆开才能解决的问题"时才拆，而不是"因为微服务先进"。
- **触发**：子系统间伸缩需求差异极大（一个吃 CPU 一个吃内存）、团队规模大到模块边界冲突频繁、需要独立发布节奏或故障隔离。
- **判断依据**：模块划分清晰是拆的前提——NestJS 模块本就对应未来服务边界，先把模块切干净，未来拆分水到渠成。
- **追问**：拆前想清楚分布式事务、链路追踪、服务发现、配置中心由谁承担；可量化判断——"改一个模块要等另一个团队排期"频繁出现时该切。

## 11. 平台切换与源码原理

### Q1（11.1）｜ 选型：什么时候该从 Express 切到 Fastify？切完哪些会坏？
- **判断**：高并发、I/O 密集且不重度依赖 Express 中间件生态时切，否则不值得。
- **收益**：压测下 Fastify 吞吐显著高于 Express（~40000 vs 15000 req/s），内置 JSON Schema 序列化替代 `JSON.stringify` 是主因之一。
- **代价**：Fastify 不兼容 Express `req/res`，`cookie-parser`/`helmet`/`multer` 不能直接用要换 `@fastify/cookie`/`@fastify/helmet`；`useStaticAssets` 参数形态变 `({ root, prefix })`；文件上传要额外注册 `contentParser`。
- **边界**：Guard/Interceptor/Pipe/Filter 与平台无关、切换后照常可用（挂在 Nest 抽象层）；重度依赖 passport/multer 建议留 Express；切换后重跑压测与回归。

### Q2（11.2）｜ 原理：读 NestJS 源码前置三件套是什么？
- **判断**：TS 装饰器、`reflect-metadata`、`design:paramtypes`——缺一个读不懂 DI。
- **展开**：`reflect-metadata` 隔离存元数据不污染原型；`emitDecoratorMetadata` 只对至少带一个装饰器的类生成 paramtypes。
- **边界**：四类装饰器签名——类 `(target)`、方法 `(target, key, descriptor)`、属性 `(target, key)`、参数 `(target, key, parameterIndex)`。
- **追问**：装饰器在类定义时即写元数据，`@Module`/`@Controller`/`@Get`/`@Param` 各存各自信息。

### Q3（11.3）｜ 原理：NestJS 启动链与请求链的最小实现是什么？
- **判断**：启动 `new Container → 收集 controller/provider → 读 design:paramtypes 递归注入 → 扫路由 → http.createServer`；请求 `路由匹配 :param → Guard → 参数装饰器 → Pipe → Interceptor → Handler → res.json`。
- **展开**：请求链各环节按有无 `canActivate` / `transform` / `intercept` 可选执行，出口为 403/404/500。
- **边界**：与真实源码差距——最小实现手动遍历 paramtypes，NestJS 用 `InstanceLoader`/`ModuleScanner`/`RoutesResolver` 并额外支持作用域与循环依赖。
- **追问**：真实实现对应 `InstanceLoader + ModuleRef`，比最小实现多出作用域、循环依赖、`@Optional()` 等能力。

## 12. 工程落地与项目模板

### Q1（12.1/12.2）｜ 场景设计：一个可上线的 NestJS 项目目录与配置该怎么组织？
- **判断**：src 分 `common`/`config`/`constants`/`modules`/`shared` 五大块，业务模块自带 dto/entities/guards/services/strategies + 三件套。
- **展开**：配置集中 `config/` 读 `.env` 给默认值，`database.config.ts` 派生 `TypeOrmModuleOptions`（synchronize/logging 仅 development 开）；`.env` 按 DB/Redis/JWT 三组给变量。
- **边界**：根模块用 Provider 注册 `APP_FILTER`/`APP_INTERCEPTOR`（可注入依赖）；`main.ts` 挂 ValidationPipe(whitelist/transform/forbidNonWhitelisted)+enableCors+setGlobalPrefix('api')+Swagger。
- **追问**：数据层实体演示主键/唯一列/`select:false` 隐藏密码/`ManyToOne` 级联删除。

### Q2（12.3）｜ 场景设计：统一响应、统一异常、全局 Redis、健康检查怎么落地？
- **判断**：`ResponseModel`+`TransformInterceptor` 管成功、`@Catch()` 过滤器管失败（堆栈仅 development 显示）、`@Global()` `RedisModule` 全局可用、健康检查查两端。
- **展开**：统一异常过滤器按类型分派把 stack 只在开发环境带出；`@Global()` 的 `RedisModule` 用 `useFactory` + Token `'REDIS_CLIENT'` 全局注入；健康检查 `dataSource.query('SELECT 1')` 与 `redis.ping()` 任一失败置 degraded。
- **边界**：全局组件要可注入依赖就用 `APP_*` Provider 而非 `app.useGlobalXxx()`。
- **追问**：成功与失败共用同一响应模型，对外格式才真正一致。

### Q3（12.4）｜ 场景设计：从零把项目搭起来并按最佳实践组织的关键步骤？
- **判断**：CLI 建项目 → 装依赖 → `cp .env.example .env` → 起 MySQL/Redis → start:dev / build + start:prod。
- **展开**：按功能划模块、共享逻辑下沉、基础设施进 common、全局校验/响应/异常统一、坚持依赖注入。
- **边界**：生产 `.env` 走环境注入、密钥不进库不进 git；`synchronize` 生产关 + Migration。
- **追问**：这套模板把认证收口成结构（AuthSession/轮换/双 Token），走完一圈回到最初"容器怎么知道注入谁"的原理闭环。
