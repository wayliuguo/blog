## 一、基础概念

### Q1: NestJS 相比 Express/Koa 多封装了哪几层？（07-入门/00 篇）

- **结论**：Express/Koa 管的是「请求 → 中间件 → 响应」；NestJS 在其上又封了三层：**DI 容器**（对象谁创建、依赖怎么传）、**装饰器 + Metadata**（路由/参数/权限怎么"声明"出来）、**请求生命周期**（请求依次经过哪些环节）。
- **判断依据**：NestJS 的价值在"组织"而非"能力"——它能做的事裸 Node.js 都能做，只是把"怎么组织一个能长期维护的后端项目"变成了一套有约束的约定。
- **边界**：单体 NestJS 配合清晰的模块划分能撑到相当大的规模。一上来就拆微服务，等于把分布式事务、链路追踪、服务发现提前塞给自己。
- **场景**：写个一次性脚本或纯静态服务，完全不需要这套；一旦有多个业务域、多人协作，模块化与 DI 的收益才开始显现。
- **追问**：这四层各自的认知入口是：DI 容器 → IOC 与依赖注入、装饰器 → 控制器与路由、生命周期 → 请求处理链、底层 HTTP → 网络模块。

### Q2: `@Module` 的配置项有哪些？空模块合法吗？（07-入门/03 篇）

- **结论**：四个常用配置项 `imports` / `controllers` / `providers` / `exports`，外加 `@Global()` 装饰器表达"全局可见"。
- **原理**：`providers` 注册可被注入的服务，`controllers` 注册路由入口（Nest 会自动实例化并绑定路由），`imports` 引入其他模块导出的能力，`exports` 把本模块的 Provider 暴露给导入者。
- **边界**：所有项都是可选的，`@Module({})` 空模块完全合法，常被动态模块用来当"壳"。模块还能 re-export 别的模块的 exports，实现"能力中转"。
- **追问**：模块默认是**封装**的——没有写进 `exports` 的 Provider，即便别的模块 `imports` 了本模块也拿不到。

### Q3: 模块的 `imports` 和 `exports` 分别管什么？（07-入门/03 篇）

- **结论**：`imports` 决定"我能用谁"，`exports` 决定"谁能用我"。两者共同构成 NestJS 的模块依赖图。
- **原理**：只有被 `exports` 导出的 Provider，才能被导入了该模块的其他模块注入使用；模块内部的 Provider 对自己模块是自动可见的，不需要导出。
- **场景**：`DatabaseModule` 里 `exports: [DatabaseService]`，`UsersModule` 里 `imports: [DatabaseModule]` 后即可在 `UserService` 构造函数里注入 `DatabaseService`。
- **边界**：`exports` 只影响"可注入性"，不影响"是否实例化"——被 import 的模块里的 Provider 仍以单例形式存在一份，不会因为多处 import 而重复创建。
- **追问**：`exports` 里也可以直接写模块对象（re-export），常用于把一组能力包装成"公共包"再整体转出去。

### Q4: `@Global()` 全局模块解决什么问题？什么时候不该用？（07-入门/03 篇）

- **结论**：让模块的 exports 注册到全局容器，任何模块无需 `imports` 就能注入，省掉大量样板 imports。
- **原理**：NestJS 模块默认隔离，A 要用 B 的 Provider 必须显式导入；`@Global()` 把 B 标记为全局，跳过这道手续。
- **边界**：滥用会让依赖关系隐式化——看一个 Service 的构造函数完全猜不出它依赖了哪些基础设施，可维护性下降。只对真正通用的模块开（配置、日志、Redis 客户端、数据库连接），业务模块一律显式 import。
- **场景**：`ConfigModule`、`LoggerModule`、`RedisModule` 是典型的全局模块；`UserModule` 这类业务模块不该开这个口子。
- **追问**：全局限定在 exports 上，没导出的 Provider 依然是模块私有的。

### Q5: 什么是动态模块？`forRoot` 与 `forRootAsync` 的区别？（07-入门/03 篇）

- **结论**：动态模块是"能在 import 时传参"的模块——用一个静态方法返回 `DynamicModule` 对象，把配置在导入阶段注入进去。
- **原理**：`forRoot(options)` 同步接收配置对象，适合配置值已知或直接来自环境变量的场景；`forRootAsync({ imports, inject, useFactory })` 把配置的获取推迟到运行时，工厂函数可以是 async，适合要读 ConfigService、远程配置中心、或需要异步建连接的场景。
- **场景**：`TypeOrmModule.forRoot({...})` 写死连接参数；`TypeOrmModule.forRootAsync({ imports: [ConfigModule], inject: [ConfigService], useFactory: (c) => ({ host: c.get('DB_HOST') }) })` 从配置里取。
- **边界**：`forRoot` 一个模块只应被调用一次，`forFeature` 才是按需多次调用；两者混淆会导致连接重复创建。
- **追问**：`forRoot` 返回的对象里通常还要 `imports` 自己的 `forFeature`，或者把需要复用的 Provider 直接拼进 `providers`。

### Q6: IoC 和 DI 的区别是什么？（08-进阶/12 篇）

- **结论**：IoC 是**设计思想**——把"对象创建 + 依赖管理"的控制权从业务代码反转给容器；DI 是**实现方式**——容器创建好依赖后通过构造函数注入给使用者。IoC 回答"为什么交出去"，DI 回答"怎么交出去"。
- **原理**：NestJS 用 DI 来实现 IoC：你只声明依赖类型，框架在启动时扫描、实例化、注入。
- **对比**：没有 IoC 时依赖网是手动 new 出来的，改一个构造参数要改一整条链；有 IoC 时只写 `constructor(private readonly userService: UserService) {}`。
- **边界**：两者常被混用当同义词，但面试里能把"思想 vs 实现"分清是加分点。
- **追问**：DI 也不是 IoC 的全部——事件驱动、模板方法等同样属于"控制反转"，只是 DI 在框架里最常见。

### Q7: `@Injectable()` 和 `@Controller()` 的区别？（07-入门/02 篇）

- **结论**：`@Injectable()` 标记"这是一个可被 DI 容器管理的普通 Provider"；`@Controller()` 标记"这是一个路由入口"。
- **原理**：`@Controller()` 本质上是经过特殊处理的 `@Injectable()`——被它装饰的类同时具备依赖注入能力和路由处理能力；Nest 扫描模块时把 `@Controller()` 类注册进路由系统，`@Injectable()` 类注册进 DI 容器。
- **边界**：两者最终都由同一个容器管理实例，区别只在"是否参与路由注册"和语义。Service / Repository 用 `@Injectable()`，对外入口用 `@Controller()`。
- **追问**：`@Injectable({ scope })` 还能指定作用域，`@Controller()` 不提供这个选项。

### Q8: 依赖注入具体好在哪三点？代价是什么？（07-入门/02 篇）

- **结论**：解耦（类不依赖具体实现，只声明需要什么）、可测（能塞 Mock 对象）、可维护（换实现的构造方式不影响使用方）。
- **原理**：把"new 谁、什么时候 new、共享哪个实例"从业务代码收到容器里，业务代码只描述关系。
- **场景**：单测 `UserService` 时直接注入一个假 `UserRepository`，不必起数据库；生产环境把 `useClass` 换成真实实现即可。
- **边界**：代价是启动期多了一层"扫描 + 依赖图解析"的复杂度，出错信息（`Nest can't resolve dependencies`）对新手不友好；但长期维护收益远大于这点成本。
- **追问**：三条好处容易被答成口号，加分点在于能举出"单测里把真实依赖换成 Mock 的具体写法"。

### Q9: `@Controller('users')` 的参数是什么？一个方法怎么变成一条路由？（07-入门/04 篇）

- **结论**：字符串参数是**路由前缀**，最终路径 = 前缀 + 方法上的装饰器路径（如 `@Get(':id')` → `GET /users/:id`）。
- **原理**：`@Get()` / `@Post()` / `@Put()` / `@Patch()` / `@Delete()` 是方法装饰器，运行时把 `{ method, path, handlerName }` 写进类的元数据；Nest 在启动时读取这份元数据，为每个方法绑定路由并实例化控制器。
- **边界**：控制器只负责"收请求、还响应"，业务逻辑应在 Service 层——否则控制器既难测又难复用。
- **追问**：`@HttpCode(201)` 改状态码，`@Redirect('/users', 301)` 做重定向；不加装饰器时返回值自动序列化为 JSON、状态码 200。

### Q10: `@Param()`、`@Query()`、`@Body()`、`@Headers()`、`@Ip()` 各取什么数据？（07-入门/04 篇）

- **结论**：`@Param()` 取路径参数（`/users/:id` 里的 `id`）、`@Query()` 取问号后的查询串、`@Body()` 取请求体（通常配合 DTO + ValidationPipe）、`@Headers()` 取请求头、`@Ip()` 取客户端 IP。
- **原理**：这些都是参数装饰器，运行时按参数位置从 `req` 的不同部位取值，填进 Handler 的实参表。
- **边界**：三者数据来源不同，可以同时出现在一个方法签名里；`@Body()` 依赖请求体解析（Nest 默认已接好 body 解析），`@Req()` 则直接给出原始请求对象，是"逃生舱"。
- **追问**：`@Param()` 不传参数名会返回整个 params 对象。

### Q11: PUT 和 PATCH 有什么区别？RESTful 命名上最容易犯什么错？（07-入门/04 篇）

- **结论**：PUT 是**全量替换**（没传的字段视为置空/重置），PATCH 是**部分更新**（只改传了的字段）。
- **场景**：`PUT /users/1` 提交完整用户对象；`PATCH /users/1` 只提交 `{ phone }`。对应到 NestJS 就是 `@Put(':id')` 与 `@Patch(':id')`。
- **边界**：这是语义约定而非框架强制——用 PUT 做部分更新代码照样跑，但会让接口契约和缓存策略混乱。
- **追问**：命名上最常见的错是用动词（`/getUsers`、`/deleteUser?id=1`）或在 POST 里做查询；规范做法是资源用复数名词，动作交给 HTTP 方法表达。

### Q12: Provider 的四种声明方式分别适合什么场景？（08-进阶/12 篇）

- **结论**：`useClass`（Token 即类，最常用）、`useValue`（注入常量/配置对象/Mock）、`useFactory`（需要运行时逻辑、异步或依赖其他 Provider）、`useExisting`（给同一个实例起别名）。
- **原理**：Provider 在容器里以 **Token** 为键登记。默认 Token 就是类本身；当 Token 是字符串或 `Symbol` 时，使用方必须用 `@Inject(TOKEN)` 显式指名。
- **场景**：`{ provide: 'CONFIG', useValue: { port: 3000 } }` 注入配置；`{ provide: 'DB', useFactory: async (c) => createConn(c.get('URL')), inject: [ConfigService] }` 异步建连接；`{ provide: 'Alias', useExisting: RealService }` 让两个 Token 指向同一实例。
- **边界**：`useValue` 是同一个对象引用，注入方拿到后修改会影响所有使用方；`useClass` 可以配合接口抽象做"换实现"，前提是给了 Token。
- **追问**：测试里"覆盖 Provider"（`overrideProvider(...).useValue(mock)`）本质就是往同 Token 的位置塞一个替代项。

### Q13: Middleware、Guard、Pipe、Interceptor、Exception Filter 各自的职责是什么？（07-入门/05 篇）

- **结论**：记住口诀——Middleware「进来之前先做什么」、Guard「能不能进」、Pipe「数据对不对」、Interceptor「进出前后还要做点什么」、Filter「出错了怎么返回」。
- **对应问题**：Middleware 回答预处理，Guard 回答有没有权限，Pipe 回答参数合法吗，Interceptor 回答要包裹执行什么，Filter 回答异常怎么统一成响应。
- **典型场景**：Middleware → 日志、CORS、cookie 解析、安全头；Guard → 认证、角色校验；Pipe → DTO 校验、类型转换、分页范围；Interceptor → 统一响应格式、耗时统计、缓存；Filter → 统一错误响应。
- **边界**：搞混职责就会出现"把权限逻辑写在中间件里"这种能跑但难维护的代码。
- **追问**：这五类组件都能全局注册、控制器级注册、方法级注册；粒度越细优先级越高，就近原则覆盖全局。

### Q14: 拦截器（Interceptor）和异常过滤器（Exception Filter）的分工？（07-入门/05 篇）

- **结论**：拦截器是**包裹执行**——它在 Handler 前后都能插入逻辑，还能改写返回的数据；过滤器是**异常兜底**——只在有异常抛出时被触发，负责把异常翻译成统一的错误响应。
- **原理**：拦截器实现 `intercept(context, next)`，用 `next.handle()` 拿到 RxJS Observable 流，配 `map` 改响应、配 `tap` 打点；过滤器实现 `catch(exception, host)`，用 `host.switchToHttp().getResponse()` 写出错误体。
- **边界**：拦截器技术上能用 `catchError` 处理异常，但最佳实践是交给过滤器——两者职责不同，各司其职才不至于让响应格式分散在多处。
- **场景**：成功路径的格式由拦截器统一，失败路径的格式由过滤器统一，两边共用同一个响应模型，对外才是真正"格式一致"。
- **追问**：过滤器在 Controller 方法里标记 `@UseFilters()` 是就近生效，改全局要注册 `APP_FILTER`。

### Q15: `diskStorage` 和 `memoryStorage` 的区别？（08-进阶/04 篇）

- **结论**：`diskStorage` 边收边写磁盘，适合大文件、低内存占用；`memoryStorage` 把整个文件读成 Buffer 放在内存里，适合小文件或"拿到 Buffer 后要进一步处理/转存"的场景。
- **场景**：用户头像直存本地磁盘用 `diskStorage` + 唯一文件名（`Date.now()` + 随机数 + 原扩展名）避免重名和中文乱码；要转存对象存储、或上传后要立刻压缩/生成缩略图的，用 `memoryStorage` 拿 Buffer 更方便。
- **边界**：`memoryStorage` 的代价是并发上传大文件时内存陡增，必须配 `limits.fileSize` 兜底，否则容易被大文件打爆。
- **追问**：两种模式下业务代码拿到的字段不同——`memoryStorage` 用 `file.buffer`，`diskStorage` 用 `file.path`，写处理逻辑时要注意区分。

### Q16: WebSocket 与 HTTP 轮询各有什么优缺点？（08-进阶/05 篇）

- **结论**：WebSocket 是全双工长连接，实时性高、头部开销小，适合聊天和主动推送；HTTP 轮询实现简单、纯无状态，但延迟受轮询间隔限制、空轮询浪费带宽。
- **原理**：NestJS 用 Gateway 封装了连接管理——`@WebSocketGateway()` 声明网关，`handleConnection` / `handleDisconnect` 管连接生命周期，`@SubscribeMessage('event')` 收消息，`@WebSocketServer()` 注入 `Server` 实例做广播或按房间推送。
- **边界**：长连接要处理心跳与断线重连，且服务多实例时需要额外的消息总线（如适配器接到 Redis）才能跨实例广播；轮询在这些方面反而省心。
- **追问**：SSE 是第三种选择——服务端单向推送、走普通 HTTP、浏览器自带重连，只推不收的场景比 WebSocket 更省事。

### Q17: `@Cron` 和 Bull 队列分别适合什么场景？（08-进阶/06 篇）

- **结论**：`@Cron` 是**定时触发**——到点就跑，不管上一次结果；Bull 是**异步解耦**——把任务投进队列由消费者处理，天然带重试、延迟、并发控制。
- **场景**：每日报表生成、健康检查用 `@Cron` / `@Interval`；发验证码邮件、下单 30 分钟未支付自动取消、用户注册欢迎邮件用 Bull（延迟任务 + 失败重试）。
- **原理**：队列本质是生产者—消费者模式，能削峰填谷——请求高峰期只管把任务写进队列，消费者按自己的节奏处理。
- **边界**：`@Cron` 在多实例部署下会**每个实例各跑一次**，需要分布式锁或独立调度进程；`@Cron` 也不带重试语义，跑失败就等下一个周期。
- **追问**：`SchedulerRegistry` 能在运行时动态增删任务，适合"运营后台配置定时报表"这类需求。

### Q18: 微服务间通信有哪两类？NestJS 分别用什么 API？（08-进阶/07 篇）

- **结论**：同步（请求—响应）用 `ClientProxy.send()`，配 `@MessagePattern()`；异步（事件广播、发完不管）用 `ClientProxy.emit()`，配 `@EventPattern()`。
- **原理**：`send()` 返回 Observable，会等对端返回结果；`emit()` 是"发布事件"，不等待响应。两者走的都是 `ClientsModule.register()` 配好的传输通道。
- **场景**：API 网关查用户详情要结果 → `send({ cmd: 'get_user' }, { id })`；用户创建成功后通知邮件服务、积分服务 → `emit('user.created', payload)`。
- **边界**：`emit()` 没有回执，可靠性取决于传输层（RabbitMQ 有 ACK/持久化，Redis Pub/Sub 和裸 TCP 没有），"必须送达"的业务别只靠 `emit()`。
- **追问**：网关侧用 `ClientsModule.register([{ name: 'USER_SERVICE', transport, options }])` 声明通道，再用 `@Inject('USER_SERVICE')` 注入 `ClientProxy`。

### Q19: JWT 由哪三部分组成？为什么服务端可以不存 Session？（08-进阶/03 篇）

- **结论**：`Header.Payload.Signature` 三段，用 `.` 分隔，各段都是 Base64URL 编码。服务端只需用同一密钥重算签名并比对，就能信任 Payload 未被篡改，所以不必存 Session。
- **原理**：Header 声明算法与类型（`{"alg":"HS256","typ":"JWT"}`），Payload 放声明（标准声明 `sub`/`exp`/`iat`，以及自定义的 `userId`/`role`），Signature = HMAC-SHA256(base64url(header) + "." + base64url(payload), secret)。
- **边界**：Payload 只是 Base64 **编码**不是加密，任何人都能解出内容，绝不能放密码等敏感数据；Signature 只防篡改，不提供保密性。
- **追问**：单 Token 有个绕不开的矛盾——有效期长则泄露危害大，有效期短则用户频繁重登。这正是要拆成 Access Token（短，如 15m）+ Refresh Token（长，如 7d）的原因：短凭证每次请求都传输所以越短越安全，长凭证只用于换发所以越长越省心。
- **追问**：JWT 的无状态带来的代价是"无法主动吊销"，这正是要引入会话表的原因。

### Q20: JWT 和 Cookie 是竞争关系吗？（08-进阶/03 篇）

- **结论**：不是。JWT 是**凭证内容**（令牌本身是什么），Cookie 是**保存方式**（令牌放在哪里），两者可以组合。
- **原理**：把 JWT 放进 HttpOnly Cookie，既保留服务端无状态校验的便利，又降低 XSS 直接窃取 Token 明文的风险。
- **边界**：放进 Cookie 就要面对 CSRF，需要配 `sameSite`；而放进 `Authorization` 头则天然免疫 CSRF，但前端必须自己保管好 Token——两种存法各有一处要防。
- **追问**：所以"用 JWT 还是用 Cookie"是个伪问题，真问题是"这个凭证放在哪、要防哪一类攻击"。

## 二、机制与原理

### Q21: 为什么 Controller 里不 `new` 就能用 `UserService`？（07-入门/05 篇）

- **结论**：因为容器在启动时已经把 `UserService` 建好并"塞"进了构造参数，你写的不是"创建"，而是"声明需要"。
- **原理**：`private readonly userService: UserService` 这一行同时做了三件事——声明字段、声明类型、声明依赖。Nest 扫描到类型后去容器里找对应实例完成注入。
- **边界**：`Service` 本身不是框架生命周期的一个阶段，而是业务调用链（Controller → Service → Repository）的一部分。请求链路描述的是"框架什么时候插手"，Service 是你业务内部的方法调用。
- **场景**：`readonly` 只是 TS 的编译期约束，运行时容器照样会赋值——它是"声明依赖"的语法糖，不是不可变保证。
- **追问**：容器的解析是递归的——要造 `UserController` 先造 `UserService`，要造 `UserService` 先造 `UserRepository`，自底向上装配。

### Q22: 为什么 NestJS 必须开启 `emitDecoratorMetadata`？（08-进阶/12 篇）

- **结论**：只有开启它，TypeScript 才会在编译产物里生成 `design:paramtypes` 元数据，记录构造函数每个位置需要的类型；Nest 靠这份元数据才知道"该注入哪个类的实例"。
- **原理**：`reflect-metadata` 提供 `Reflect.defineMetadata` / `getMetadata` 的运行时存储能力，`emitDecoratorMetadata` 负责把类型信息写进去。`experimentalDecorators` 与 `emitDecoratorMetadata` 两个开关缺一不可。
- **边界**：`emitDecoratorMetadata` 只对**至少有一个装饰器**的类生效——裸类不会被生成 `design:paramtypes`，容器自然无从解析。
- **追问**：Nest CLI 生成的 `tsconfig.json` 默认已开这两个开关，最容易出事的是手改编译配置时误关。
- **心智模型**：`@Injectable()` 告诉容器"我能当零件"，`emitDecoratorMetadata` 让容器"看得见零件的长相"。

### Q23: 为什么类上要加 `@Injectable()`？不加会怎样？（08-进阶/12 篇）

- **结论**：`@Injectable()` 把类登记为"可被容器管理的 Provider"，同时触发 `design:paramtypes` 的生成。没有它，容器不认识这个类，注入时会报"无法解析依赖"。
- **原理**：装饰器在**类定义时**就执行（不是实例化时），因此元数据在应用启动扫描前已经写好。
- **边界**：`@Injectable()` 是语义标记，运行时容器真正依赖的是"这个 Token 有没有对应的 Provider 注册"以及"参数类型能不能被解析"。
- **追问**：所以只要这个类有构造参数且没装饰器，`design:paramtypes` 缺失就会导致注入失败——规则是"只要可注入，就加 `@Injectable()`"。

### Q24: Provider 有哪几种作用域？REQUEST 作用域为什么有性能代价？（08-进阶/02 篇）

- **结论**：`DEFAULT`（单例，默认，全应用一个实例）、`REQUEST`（每个请求一个实例）、`TRANSIENT`（每次注入都新建）。
- **原理与代价**：REQUEST / TRANSIENT 绕过了单例复用，每次创建都有实例化开销；高频接口上频繁创建会明显加重 GC 压力。
- **关键陷阱**：作用域会**级联向上污染**——一个单例 Provider 只要注入了 REQUEST 作用域的 Provider，它自己也会被降级为请求作用域，整条依赖链都变成每个请求重建。
- **边界**：REQUEST 作用域的 Provider 不能被单例依赖（语义冲突）；默认一律单例，只在确实需要"每请求一份状态"时才上 REQUEST。
- **追问**：需要请求上下文又不想降级作用域时，`AsyncLocalStorage` 是更现代的解法——不用改作用域就能把上下文贯穿整条调用链。

### Q25: 一次请求里 Middleware、Guard、Interceptor、Pipe、Filter 的精确执行顺序是什么？（07-入门/05 篇）

- **结论**：`Middleware → Guard → Interceptor(before) → Pipe → Controller → Service → Repository → Interceptor(after) → HTTP Response`；任意环节抛异常都进入 Exception Filter。
- **原理**：这个顺序是固定的，Nest 底层按元数据把各组件组合进一条处理管道，Middleware 在路由匹配前执行，Guard 决定是否继续，Interceptor 包裹整体，Pipe 在 Handler 前处理参数。
- **易错点**：Service 不是框架生命周期的独立阶段，而是业务调用链的一部分——"框架什么时候插手"和"你业务里调了谁"是两个维度。
- **边界**：Middleware 需要在模块的 `configure(consumer)` 里用 `forRoutes` 声明生效范围；Guard 及其之后的组件则按控制器/方法就近绑定。
- **追问**：全局绑定与局部绑定的组件会一起参与，顺序上全局的通常在前；同类多个组件的执行顺序按注册顺序。

### Q26: 为什么基于装饰器（如 `@Roles('admin')`）的鉴权要放 Guard，而不是 Middleware？（07-入门/05 篇）

- **结论**：因为 Guard 的 `ExecutionContext` 能拿到 `getHandler()` 和 `getClass()`，从而配合 `Reflector` 读到挂在具体方法上的元数据；Middleware 只有 `req / res / next`，根本不知道请求会落到哪个方法。
- **原理**：装饰器负责"写标签"（内部走 `Reflect.defineMetadata`），运行时由框架"读标签"。能不能读，取决于组件拿不拿得到"当前是哪个 Handler"。
- **一句话**：Middleware 站在门外，只看见进来的流量；Guard 站在门口，还知道你要进哪扇门、门上贴了什么标签。
- **边界**：所以 `@Roles('admin')` 本身不拦任何请求——它只是声明，必须有一个 Guard 去读它，权限校验才真正生效。
- **追问**：Middleware 也有它的位置——日志、CORS、cookie 解析、安全头这些"与路由无关"的横切逻辑放它是正确的。

### Q27: `SetMetadata` 和 `Reflector` 在权限控制中如何配合？（08-进阶/01 篇）

- **结论**：`SetMetadata(key, value)` 在类/方法上写元数据，`Reflector` 在 Guard 里读出来，与当前用户的角色比对后返回布尔值决定放行。
- **写法**：先封一个语义化装饰器 `export const Roles = (...roles: string[]) => SetMetadata('roles', roles)`，Guard 里用 `this.reflector.getAllAndOverride<string[]>('roles', [context.getHandler(), context.getClass()])` 读，`requiredRoles.some(r => user.roles?.includes(r))` 判权限。
- **边界**：元数据存在类或方法上，读的时候必须指定正确的目标；`getAllAndOverride` 是"方法覆盖类"，`getAllAndMerge` 是"类与方法合并"，多级权限场景按需选。
- **场景**：`@Public()` 就是同一套机制的另一个用法——贴 `isPublic: true` 标签，全局 `JwtAuthGuard` 读到就跳过校验。
- **追问**：读不到元数据（`undefined`）时应当直接 `return true` 放行，否则所有没贴标签的路由都会被拦。

### Q28: `createParamDecorator` 如何拿到请求对象？（08-进阶/01 篇）

- **结论**：工厂函数的第二个参数就是 `ExecutionContext`，调 `ctx.switchToHttp().getRequest()` 拿到原生请求对象，再从中取需要的数据；工厂函数的返回值会成为 Handler 的实参。
- **写法**：`export const CurrentUser = createParamDecorator((data: string | undefined, ctx: ExecutionContext) => { const user = ctx.switchToHttp().getRequest().user; return data ? user?.[data] : user })`，于是 `@CurrentUser('id')` 能直接拿到当前用户 ID。
- **边界**：它依赖上游（通常是 Guard）已经把 `req.user` 挂好，否则读到 `undefined`；`data` 参数用于让调用方定制返回内容。
- **追问**：参数装饰器可以和 Pipe 叠加，`@Param('id', ParseIdPipe)` 会先取值、再交给 Pipe 转换，两者职责不冲突。

### Q29: `ExecutionContext` 的 `switchToHttp` / `switchToRpc` / `switchToWs` 有什么区别？（08-进阶/01 篇）

- **结论**：三者分别用于取 HTTP、微服务（RPC）、WebSocket 协议的上下文对象，是同一套 Guard/Interceptor/Filter 能跨传输层复用的关键抽象。
- **差异**：`switchToHttp()` 返回 `HttpArgumentsHost`，提供 `getRequest()` / `getResponse()`；`switchToRpc()` 返回 `RpcArgumentsHost`，用 `getData()` 取消息体；`switchToWs()` 返回 `WsArgumentsHost`，用 `getClient()` 取 socket 客户端。
- **边界**：三者不能混用——当前是 WebSocket 连接时调 `switchToHttp()` 会抛异常。跨协议组件应先判断 `context.getType()`（`'http' | 'rpc' | 'ws'`）再分支。
- **场景**：同一个鉴权 Guard 要同时服务 HTTP 接口和 WebSocket 网关时，先按 `getType()` 分流，再各自用 `switchToXxx()` 取凭证，业务逻辑可以复用。
- **追问**：`getClass()` 和 `getHandler()` 在任何协议下都可用，是路由粒度的元数据读取入口。

### Q30: NestJS 启动时 DI 容器做了哪几件事？（08-进阶/09 篇）

- **结论**：`NestFactory.create(AppModule)` 依次做：递归扫描模块树 → 收集所有 Provider/Controller 元数据 → 建立依赖关系图 → 创建容器 → 按"先依赖后使用者"的顺序实例化 → 注入 → 绑路由与全局组件 → 启动 HTTP Server。
- **原理**：容器的核心是"读 `design:paramtypes` → 递归 `resolve` 每个参数 → `new Token(...args)` → 结果进单例缓存"；缓存命中就直接返回，这就是单例的来源。
- **边界**：正因为要确定"先实例化谁"，依赖图里出现环就直接启动失败——这是循环依赖报错的根本原因。
- **追问**：解析失败时抛的是 `UnknownDependenciesException`，错误信息会指出是哪个 Token 的哪个参数位置解析不出来，按这个线索定位最快。
- **追问**：真实实现里对应 `InstanceLoader` + `ModuleRef`，比最小实现多出作用域、循环依赖、`@Optional()` 等能力。

### Q31: 循环依赖为什么会让启动失败？`forwardRef` 做了什么？（08-进阶/02 篇）

- **结论**：容器必须按依赖顺序自底向上实例化，A 依赖 B、B 又依赖 A 时"谁先建"无法确定，于是启动直接失败。`forwardRef(() => Xxx)` 把类型求值推迟到实例化阶段，让容器先建占位、后回填，从而打破这个环。
- **用法**：Provider 层用 `constructor(@Inject(forwardRef(() => OrderService)) private readonly orderService: OrderService)`；模块层用 `imports: [forwardRef(() => OrdersModule)]`。**两层都要加**，只加一层仍旧报错。
- **边界**：循环依赖通常是设计问题的信号。更优解是重构——抽出第三个服务承载共享逻辑，或把依赖单向化；`forwardRef` 只是临时解法。
- **追问**：`ModuleRef` 也能在运行时按 Token 取实例，但那是解决"运行时才知道要谁"，与打破启动期的环不是同一件事。

### Q32: `app.useGlobalXxx()` 和 `APP_XXX` 提供者两种全局注册有什么区别？（07-入门/05 篇）

- **结论**：`app.useGlobalInterceptors(new X())` 在 `main.ts` 里手工塞实例，**无法注入依赖**；在模块 `providers` 里注册 `{ provide: APP_INTERCEPTOR, useClass: X }` 由容器创建实例，**可以正常注入依赖**。
- **判断依据**：全局组件几乎总是要依赖别的服务（写日志、查权限、读配置），所以推荐统一用 `APP_*` 提供者方式。`APP_GUARD` / `APP_PIPE` / `APP_FILTER` 同理。
- **边界**：在**根模块**注册的 `APP_*` 才是全局；在子模块注册则只对该模块生效。多个同类全局组件的执行顺序按注册顺序。
- **追问**：即使某个组件本身没有依赖（如纯净的 `ValidationPipe`），也建议统一用 `APP_PIPE` 注册，保持风格一致、日后加依赖时不用改结构。

### Q33: 拦截器是怎么在 Handler 前后"包裹"逻辑的？（07-入门/05 篇）

- **结论**：实现 `intercept(context, next)`，**必须返回 `next.handle()`**——它是一根 RxJS 流；在 `next.handle()` 之前写的是前置逻辑，用 `.pipe(map(...))` 改响应、`.pipe(tap(...))` 做后置统计。忘了返回这根流，请求就会挂住不响应。
- **典型实现**：统一响应格式用 `next.handle().pipe(map(data => ({ code: 0, data, message: 'success' })))`；耗时统计在 `intercept` 里记 `Date.now()`，在 `tap` 里算差值。
- **边界**：拦截器可以层层叠加（`@UseInterceptors(A, B)`），执行顺序是"外层先进入、外层后退出"，这与它的"包裹"语义一致。
- **追问**：`next.handle()` 是冷 Observable，只有被订阅（框架会自动订阅）才会真正触发 Handler——这是"忘了 return 就没响应"的底层原因。
- **追问**：拦截器不适合做参数校验（那是 Pipe）或业务鉴权（那是 Guard），它的定位是 AOP 切面。

### Q34: `ValidationPipe` 的 `whitelist` 与 `forbidNonWhitelisted` 有什么区别？（07-入门/05 篇）

- **结论**：`whitelist: true` 把 DTO 中未定义的字段**剔除**；`forbidNonWhitelisted: true` 更严格——发现未定义字段直接抛 400 拒绝请求。
- **原理**：两者配合 class-validator 使用。只有 DTO 类里用装饰器声明过的属性才算"白名单内"；请求体里多带的 `role: 'admin'` 这类字段，前者被静默丢掉，后者直接报错。
- **选择依据**：要容错（前端可能多传字段）用 `whitelist`；要严格契约、希望客户端尽早发现自己传错了，两个都开。
- **场景**：项目模板的 `main.ts` 里通常直接开 `whitelist: true` + `transform: true`，`forbidNonWhitelisted` 视前后端契约严格程度决定。
- **追问**：`transform: true` 让 `"1"` 自动转成 `1`，缺了它 DTO 上的数字类型校验会误判；`disableErrorMessages: true` 可在生产隐藏详细报错。

### Q35: 自定义 Pipe 怎么实现？`transform` 能拿到哪些信息？（07-入门/05 篇）

- **结论**：实现 `PipeTransform` 接口的 `transform(value, metadata)`——`value` 是原始参数值，`metadata` 里有 `type`（`body`/`param`/`query`）、`data`（参数名）、`metatype`（目标类型）。返回处理后的值，或直接抛 `BadRequestException`。
- **场景**：`ParseIdPipe` 把字符串 ID 转正整数、非法就抛 400；`FileValidationPipe` 校验上传文件的大小与类型；DTO 校验失败的异常会被自动交给 Exception Filter。
- **边界**：内置管道（`ParseIntPipe` / `ParseBoolPipe` / `DefaultValuePipe` 等）已覆盖大多数场景，只在"内置的满足不了"时才自定义；`transform` 可以返回 Promise，做异步校验（如查库判唯一）。
- **追问**：Pipe 里只管抛语义化异常，不用自己拼响应——所有异常最终都会汇到 Exception Filter，格式统一由它保证。
- **追问**：`@Param('id', ParseIdPipe)` 是参数级用法，`app.useGlobalPipes()` 或 `APP_PIPE` 是全局用法。

### Q36: 自定义 Exception Filter 怎么实现？`@Catch()` 不传参表示什么？（07-入门/05 篇）

- **结论**：实现 `ExceptionFilter` 接口的 `catch(exception, host)`，用 `host.switchToHttp().getResponse()` 拿响应对象写出统一错误体；`@Catch()` 不传类型表示**捕获所有异常**，传类型则精确匹配该异常及其子类。
- **写法要点**：先判断 `exception instanceof HttpException` 决定用 `getStatus()` 还是兜底 500；非 HTTP 异常（未知错误）必须记完整堆栈再对外返回模糊提示，避免泄露内部细节。
- **边界**：`exception.getResponse()` 的返回值可能是字符串也可能是对象，写统一格式时要兼容两种形态；开发环境可附带 `stack`，生产环境务必去掉。
- **场景**：项目里的全局过滤器还会注入日志服务——5xx 记完整堆栈，4xx 只记简要信息，避免日志被正常业务错误淹没。
- **追问**：全局注册用 `APP_FILTER` 提供者（可注入 Logger），就近注册用 `@UseFilters()`。

### Q37: 装饰器本身为什么不能是 async？异步校验逻辑该放哪？（08-进阶/01 篇）

- **结论**：装饰器在**类定义阶段同步执行**，返回 Promise 没有任何人 await，等于白写。所以"异步装饰器"的正确做法是：装饰器只负责用 `SetMetadata` **贴标签**，真正的异步逻辑放在 Guard 或 Interceptor 里执行。
- **写法**：`export const Permission = (perm: string) => SetMetadata('permission', perm)`，`PermissionGuard.canActivate` 声明成 `async`，在里面读元数据、查用户权限（可 await 远程/DB 调用）、返回布尔值。
- **原理**：`canActivate` 的返回值类型允许 `boolean | Promise<boolean> | Observable<boolean>`，所以异步判断是被框架原生支持的。
- **边界**：在参数装饰器里做异步取值同样不可行——参数装饰器的返回值就是参数值，没有 await 的机会；需要异步取值应放到 Pipe 里。
- **追问**：所以"自定义装饰器里能不能查库判断权限"的答案是——装饰器不能，但"装饰器 + Guard"可以。

### Q38: 为什么 Refresh Token 不能像密码一样用 bcrypt 存库？（08-进阶/11 篇）

- **结论**：bcrypt 只处理输入的**前 72 字节**，而 Refresh Token 往往更长，超出部分被截断，会导致"内容不同但前 72 字节相同的两个 Token 校验都被判为真"。
- **原理与做法**：Refresh Token 只需**单向校验**（确认"这次带来的 Token 是不是当初发的那个"），不需要还原，也不怕被暴力枚举（本身是随机长串），因此用 `createHash('sha256').update(token).digest('hex')` 存哈希就够，还比 bcrypt 快得多。
- **边界**：Token 明文只在签发响应里给客户端一次，服务端永远只留哈希——即使被拖库，攻击者拿到的哈希也无法直接拿去刷新。
- **追问**：如果坚持用 bcrypt，得先把 Token 做一次摘要压到 72 字节以内，但这比直接用 SHA-256 更绕，没有理由这么做。

### Q39: 什么是 Refresh Token Rotation？它解决了什么问题？（08-进阶/11 篇）

- **结论**：每次用 Refresh Token 换 Access Token，都**签发一对全新的 Token 并让旧的立即失效**（把库里那条记录的 `revoked` 置为 `true`）。
- **原理**：被窃取的旧 Token 一旦被攻击者重放，库里对应记录已 `revoked`，哈希比对失败直接返回 401——这就是"重放即失效"。反过来，如果攻击者先用了旧 Token，合法用户再刷新时也会失败，等于给了"被迫重新登录"这个异常信号。
- **流程**：校验 JWT 签名与过期 → 算哈希查库比对且 `revoked = false` → 把旧记录置 `revoked` → 签发新 Access + 新 Refresh → 写入新会话记录。
- **边界**：轮换引入了"并发刷新"问题——同一客户端并发发起两个刷新请求时，第二个会用已被吊销的 Token 失败，前端要做"刷新请求串行化/单飞"。
- **追问**：写入新会话记录时 `deviceId` / 客户端标识要沿用旧记录，否则用户的"活跃设备列表"里会凭空多出一台。

### Q40: 为什么需要 AuthSession 表，而不是只发 JWT？（08-进阶/11 篇）

- **结论**：JWT 本身**无法被服务端主动吊销**。AuthSession 表（User 1:N）把"服务端能作废某个 Token"这个能力补回来，同时支持多设备会话。
- **字段设计**：`refreshTokenHash`（校验是否是真实签发的那一个）、`deviceId`（区分设备，避免一台设备刷新把另一台踢下线）、`clientInfo`（登录时的客户端标识，给用户展示活跃设备列表）、`expiresAt`（服务端侧过期闸门）、`revoked`（软删除标记，登出/轮换置位）。
- **场景**：单设备登出只吊销当前那条记录；全设备登出 `updateMany({ where: { userId, revoked: false } })` 一次作废该用户全部会话——这是纯 JWT 做不到的。
- **追问**：这张表还能直接支撑"我登录了哪些设备""踢掉某一台设备"这类产品能力，纯 JWT 方案一样做不了。
- **边界**：它把无状态 JWT 的便利和会话可控性重新缝合，代价是刷新环节要查一次库（访问环节仍然无状态）。

### Q41: Bull 队列如何保证任务不丢失？（08-进阶/06 篇）

- **结论**：Bull 基于 Redis 持久化，任务**先写入 Redis 再被消费**；消费者崩溃时未确认（未 ACK）的任务会重新入队，语义上是"至少一次投递"。
- **配置**：`attempts: 3` 控制最大重试次数，`backoff: 5000` 控制重试间隔避免瞬间风暴，`removeOnComplete: true` 防止 Redis 无限增长；延迟任务用 `delay` 而不是自己写定时器。
- **边界**："至少一次"意味着**可能重复消费**，所以消费端必须做幂等（业务唯一键 + 唯一索引兜底），只配 `attempts` 不配幂等，重试就会变成重复扣款。
- **追问**：如果下游服务本身支持幂等键（如支付单号），重试天然安全；没有幂等键时才需要自己做去重表。
- **追问**：超过最大重试次数的任务应进失败队列并告警，靠人工或定时补偿，而不是无限重试。

### Q42: Gateway 如何在 HTTP 控制器里推送消息？（08-进阶/05 篇）

- **结论**：Gateway 用 `@WebSocketServer()` 注入 `Server` 实例，但控制器不该直接依赖 Gateway——把 `Server` 交给一个**共享服务**持有，控制器注入这个服务再调 `emit`。
- **写法**：`NotificationService` 里存 `private server: Server` 并暴露 `setServer(server)` / `notifyAll(event, data)` / `notifyRoom(room, event, data)`；Gateway 在初始化时把 `this.server` 交给它，控制器只管调 `notifyAll`。
- **为什么这么设计**：HTTP 控制器和 Gateway 分属不同传输层，直接互相关注会形成耦合；中间隔一个服务，两边都只依赖这个服务，也便于单测时替换。
- **边界**：多实例部署时，A 实例推的消息到不了连在 B 实例上的客户端，需要 socket.io 的适配器（如接 Redis）把广播跨实例打通。
- **追问**：同一个共享服务也可以反向给 Gateway 提供"查在线用户列表"的能力，两边共用是这条路线的核心。

## 三、排障与选型

### Q43: 启动报 `Nest can't resolve dependencies of the XxxService (?)`，怎么三步排查？（08-进阶/12 篇）

- **结论**：这不是注入语法写错，九成是**模块可见性**问题。按"注册 → 导出 → 导入"三步自查。
- **三步**：① 该 Provider 是否在某个模块的 `providers` 里注册？没注册就加。② 它来自别的模块吗？提供方模块要 `exports: [XxxService]`。③ 使用方模块是否 `imports: [XxxModule]`？
- **补充**：三步都对还报错，再检查 `tsconfig.json` 的 `emitDecoratorMetadata` 是否被关掉，以及构造参数是否用了**接口**——接口在运行时不存在，必须配 `@Inject(TOKEN)` 显式指明，或者把类型换成具体类。
- **场景**：测试环境最常见的坑是 `Test.createTestingModule({ providers: [XxxService] })` 里忘了把被依赖的 Provider 一起放进去。
- **口诀**：要被用，先注册；要跨模块，先导出；要用别人，先导入。

### Q44: 接口加了 `@Roles('admin')` 却不生效，问题出在哪？（07-入门/05 篇）

- **结论**：`@Roles()` 只是贴标签，它自己不拦任何请求；必须有一个 Guard 用 `Reflector` 把标签读出来并返回布尔值，鉴权才真正发生。
- **排查清单**：① 该控制器/方法上有没有 `@UseGuards(RolesGuard)`（或全局注册 `APP_GUARD`）？② Guard 里读元数据用的是 `getHandler()` 还是 `getClass()`——标签贴在哪一级就读哪一级，要跨级就用 `getAllAndOverride([getHandler(), getClass()])`；③ 写入与读取的 key 字符串是否一致（统一用 `ROLES_KEY` 常量最稳）；④ 用户的角色字段挂上了吗（`req.user` 是否为 `undefined`）。
- **边界**：Guard 返回 `false` 时抛 403 Forbidden；"未登录"应该是 401 Unauthorized，两者要分开，否则前端无法区分"重新登录"和"无权限"。
- **追问**：确实需要"某类场景跳过校验"时，正确做法是在 Guard 里再读一个 `@Public()` 标签后 `return true`，而不是把 `@Roles` 删掉。

### Q45: 全局拦截器里 `@Inject()` 的服务是 `undefined`，为什么？（07-入门/05 篇）

- **结论**：几乎可以肯定是用了 `app.useGlobalInterceptors(new LoggingInterceptor())`——这种方式在 `main.ts` 里手工 new 出实例，实例不在 DI 容器内，构造参数不会被注入。
- **正解**：在模块 `providers` 里注册 `{ provide: APP_INTERCEPTOR, useClass: LoggingInterceptor }`，让容器创建实例，依赖才会被解析。
- **边界**：`APP_GUARD` / `APP_PIPE` / `APP_FILTER` 同理；在根模块注册才是全局，在子模块注册只对该模块生效。
- **场景**：全局组件确实需要读 `req` 时，`APP_*` 方式同样能指向 `Scope.REQUEST` 的类，用法不受限制。

### Q46: 循环依赖报错，该重构还是用 `forwardRef`？（08-进阶/02 篇）

- **结论**：默认假设是设计问题，`forwardRef` 是止血手段而不是首选解法。
- **判断依据**：如果互相调用是因为**职责交叉**（UserService 要查订单、OrderService 要查用户），优先抽第三个服务承载共享逻辑，或把共用查询下沉到 Repository；只有确实是双向强关联（如互相订阅事件、双向门面）才值得用 `forwardRef`。
- **用法**：Provider 层 `@Inject(forwardRef(() => Xxx))` + 模块层 `imports: [forwardRef(() => XxxModule)]`，两层都要加，否则仍报错。
- **边界**：`forwardRef` 会让依赖关系的静态可读性变差、启动顺序更难推理，能消除就尽早消除。
- **追问**：加了 `forwardRef` 还报错，先确认是不是只加了一层——Provider 层和模块层是两个独立的环，各需各自处理。

### Q47: 线上内存/延迟升高，怀疑是 `Scope.REQUEST` 引起的，怎么定位与规避？（08-进阶/02 篇）

- **结论**：先查"谁把请求作用域的 Provider 注入进了单例"，再看实例创建次数。
- **原理**：REQUEST 作用域会**向上污染**——单例 Provider 只要注入了请求作用域的 Provider，自身就被降级为请求作用域，整条依赖链每次请求都重建，于是创建开销和 GC 压力一起上来。
- **定位**：沿注入链往上找第一个 `@Injectable({ scope: Scope.REQUEST })`，检查它的使用方是不是单例；用拦截器/构造函数的打点统计实例创建次数最直观。
- **规避**：默认一律单例；确需请求上下文时只在"叶子节点"（如 RequestLogger）上开 REQUEST；更稳的做法是用 `AsyncLocalStorage` 承载请求级上下文，避免作用域级联。
- **追问**：真要在 Service 里用请求信息，把值当参数从 Controller/Guard 传下去，比开 REQUEST 作用域便宜得多。

### Q48: 文件类型校验放 `fileFilter` 还是自定义 Pipe？（08-进阶/04 篇）

- **结论**：两者都做，职责不同——`fileFilter` 负责"早拒绝"，Pipe 负责"可复用的业务规则"。
- **原理**：`fileFilter` 在 Multer 写入磁盘/内存**之前**执行，`cb(new BadRequestException(), false)` 直接拦掉，不产生落盘开销；自定义 Pipe 在参数进入 Handler 前执行，能拿到 `size`/`mimetype`/`originalname`，适合大小上限、白名单、命名规范等更复杂的规则。
- **选择依据**：只做 MIME 白名单 + `limits.fileSize`，`fileFilter` 就够；需要在多个接口复用同一套规则（图片 5MB、文档 10MB），封成 `FileValidationPipe` 更合适。
- **边界**：`mimetype` 由客户端提供、可被伪造，安全要求高时还要读文件头做二次判断，或上传后异步扫描。
- **追问**：`limits.fileSize` 超限时 Multer 抛的是"负载过大"类异常，要确认全局过滤器能正确映射成 4xx，而不是被兜底成 500。

### Q49: 什么时候该从 Express 切到 Fastify？切完哪些会坏？（08-进阶/08 篇）

- **结论**：高并发、I/O 密集且不重度依赖 Express 中间件生态时切；否则不值得。
- **收益**：压测下 Fastify 吞吐通常显著高于 Express，内置 JSON Schema 序列化是主因之一，适合商品详情页、秒杀这类读多写多的接口。
- **代价**：Fastify 不兼容 Express 的 `req/res` API，`cookie-parser`、`helmet`、`multer` 这类中间件不能直接用，要替换为 `@fastify/cookie`、`@fastify/helmet` 等插件；`useStaticAssets` 的参数形态也从 `(path, { prefix })` 变成 `({ root, prefix })`；文件上传要额外注册 `contentParser`。
- **边界**：Guard / Interceptor / Pipe / Filter **与平台无关**，切换后照常可用——它们挂在 Nest 抽象层上，不直接操作原生 `req/res`。项目重度依赖 `passport`、`multer` 时建议留在 Express。
- **追问**：切换后要重跑压测与回归——吞吐提升往往伴随错误处理与序列化行为的细微变化。

### Q50: 微服务的传输方式怎么选（TCP / Redis / RabbitMQ / Kafka）？（08-进阶/07 篇）

- **结论**：按"要不要可靠投递、要不要回放、吞吐多大"选，而不是按流行度选。
- **对照**：TCP 点对点、延迟最低，适合内部同步 RPC，但服务重启期间消息会丢；Redis 基于 Pub/Sub，已有 Redis 时零新增中间件，同样是"发出去就没了"；RabbitMQ 有队列持久化、路由灵活、ACK 机制，适合必须送达并需要重试的业务消息；Kafka 高吞吐、分区、可回放，适合日志与埋点这类海量且要管理消费位点的场景。
- **边界**：NestJS 侧切换只改 `transport` 与 `options`，业务代码里的 `@MessagePattern` / `@EventPattern` 不用动——这是选择它做微服务的最大便利。
- **追问**：混合使用很常见——读多写少的查询走 TCP 同步调用，跨服务的状态变更走 RabbitMQ 事件，各取所长。

### Q51: 微服务下如何保证数据一致性？（08-进阶/07 篇）

- **结论**：单机事务解决不了跨服务一致性，生产上用"本地事务 + 消息 + 补偿"实现最终一致。
- **原理**：主流方案是 Saga（编排式或协同式）与 TCC（Try-Confirm-Cancel）；NestJS 侧最常见的落地是"先写本地库，再把事件投给队列，下游消费失败靠重试与补偿兜底"。
- **场景**：下单要扣库存、送积分。先在订单库落单并发出 `order.created` 事件，库存服务和积分服务各自消费；任一步失败走重试，超过次数进死信人工介入。
- **边界**：最终一致意味着中间态对用户可见（如"订单已创建、积分待发放"），前端要能表达这种状态；想要强一致只能引入分布式事务框架，代价是吞吐和复杂度。
- **追问**：本地事务提交与消息投递之间存在"库写了但消息没发出去"的窗口，严格场景要用本地消息表/发件箱模式补上这一环。

### Q52: 单体做得好好的，什么时候才该拆微服务？（07-入门/00 篇）

- **结论**：出现"拆开才能解决的问题"时才拆，而不是"因为微服务先进"。
- **触发条件**：子系统间伸缩需求差异极大（一个吃 CPU、一个吃内存）；团队规模大到模块边界冲突频繁；需要独立发布节奏或故障隔离。
- **判断依据**：模块划分清晰是拆的前提——NestJS 的模块本就对应未来服务的边界，先把模块切干净，未来拆分是水到渠成的事。
- **边界**：拆之前先想清楚分布式事务、链路追踪、服务发现、配置中心这四件事由谁承担，否则复杂度会立刻淹没收益。
- **追问**：可以量化判断——当"改一个模块要等另一个团队排期"频繁出现时，这条边界就该切了。

### Q53: 用户点了"退出登录"，为什么手里的 Access Token 还可能短期有效？（08-进阶/11 篇）

- **结论**：登出只吊销了服务端的会话记录，而 Access Token 是无状态的——服务端不查库就认它。
- **原理**：Access Token 的校验只看签名和 `exp`，不看数据库。登出把 `AuthSession.revoked` 置为 `true` 只影响刷新环节：Refresh Token 再也换不到新 Access Token，但手里这张在剩余有效期内（典型 15 分钟）仍然可用。
- **应对**：接受这个短窗口是最常见的做法；安全要求高时给用户加"版本号/签发时间戳"，实例内缓存并定期拉取，只对高敏接口额外校验，或对高敏接口查一次黑名单。
- **边界**：想做到"登出即失效"就得每次请求查库或查缓存，等于放弃 JWT 的无状态优势——这是明确的取舍，不是设计缺陷。
- **追问**：折中方案是在 Access Token 里放一个 `jti` 或版本号，配一张很小的吊销表，只对高敏接口查一次，用可控成本换更小的窗口。

### Q54: HttpOnly Cookie 能防住 XSS 吗？（08-进阶/11 篇）

- **结论**：不能。它只让 JS **读不到** Token 明文，不能让 XSS **发不出请求**。
- **原理**：被注入的脚本虽然拿不到 Cookie 内容，但可以借用用户浏览器带着 Cookie 发起请求（凭证由浏览器自动附加），效果上仍能冒充用户操作。
- **边界**：`secure` 防明文抓包、`sameSite` 缓解 CSRF、`path` 缩小暴露面——三者都是"降低风险"而非"消灭风险"。
- **场景**：真正的 XSS 治理是输出转义 + CSP + 依赖审计；Cookie 加固只是"万一中招，损失小一点"的兜底。
- **追问**：根本对策是修掉 XSS/CSRF 漏洞本身，把 Cookie 方案当成纵深防御的一层，而不是安全前提。

### Q55: Refresh Token 应该存 localStorage 还是 HttpOnly Cookie？（08-进阶/03 篇）

- **结论**：Refresh Token 放 HttpOnly Cookie，Access Token 放前端内存。
- **原理**：`localStorage` 里的值任何 JS 都能读，页面一旦有 XSS，Token 会被脚本直接发走；HttpOnly Cookie 禁止 JS 访问，能挡掉大部分窃取路径。Access Token 需要前端手动塞进 `Authorization` 头，因此留在内存/状态管理里更自然。
- **配置**：`httpOnly: true` + `secure: true` + `sameSite: 'strict'` + `path: '/auth/refresh'`（只在刷新接口携带，缩小暴露面）+ `maxAge`。
- **边界**：跨域场景要把 `sameSite` 放宽到 `lax`/`none` 并让前端 `fetch` 带 `credentials: 'include'`，否则 Cookie 带不上来——这是最常见的"刷新接口 401"原因。
- **追问**：开发环境用 http 时 `secure: true` 会让 Cookie 带不上来，本地调试要么起 https，要么临时关掉这个开关。

### Q56: 队列任务失败了怎么重试才不重复扣款？（08-进阶/06 篇）

- **结论**：重试必须与幂等一起设计，只配 `attempts` 是不够的。
- **原理**：Bull 基于 Redis，任务先写入 Redis 再消费，消费者崩溃时未确认的任务会重新入队，所以默认语义是"至少一次投递"——同一任务可能被处理两次。
- **做法**：① `attempts` + `backoff` 控制重试次数与退避间隔，避免瞬间重试风暴；② 消费端按业务唯一键（订单号 + 动作类型）做幂等判断，或用数据库唯一索引兜底；③ 超过最大重试次数的任务进失败队列并告警，靠人工或定时补偿。
- **边界**：长时间阻塞的任务要设合理的并发与超时，否则队列会堆积；`removeOnComplete: true` 可避免 Redis 无限增长。
- **追问**：队列积压时先看"消费速度 vs 生产速度"，再决定加消费者、拆细任务粒度，还是把耗时操作搬出队列。

### Q57: 一个接口突然变慢，在 NestJS 里怎么快速定位到环节？（07-入门/05 篇）

- **结论**：先用拦截器打点拿"框架侧耗时"，再用日志分业务耗时，比盲猜是参数校验还是 SQL 快得多。
- **做法**：`TimingInterceptor` 在 `intercept` 里记 `Date.now()`，`next.handle().pipe(tap(...))` 里算差值。注意这样量到的是"进入 Handler 到返回"的时间，不含 Guard/Pipe 的开销；要量全链路就把起点挪到 Middleware（`req` 上挂开始时间，响应结束时相减）。
- **判断依据**：耗时集中在 Pipe → 查 DTO 校验里有没有同步重活或远程调用；集中在 Handler → 打开 SQL 日志看是否缺索引或 N+1；两者都正常但响应慢 → 看拦截器链和序列化体积。
- **边界**：异步操作要在正确的时机打点，否则会把"排队等待"算成业务耗时。
- **追问**：全局拦截器链本身也有开销，排查时把拦截器数量与它们做的事一起算进去。

### Q58: `synchronize: true` 能上生产吗？（07-入门/06 篇）

- **结论**：不能。这是开发期的便利开关，生产环境必须关闭。
- **原理**：`synchronize` 会比对实体定义与真实表结构并自动改表，改法由 ORM 决定，可能直接 DROP 列/表导致数据不可逆丢失；多实例并发启动时还会互相打架。
- **做法**：开发环境 `synchronize: true` 图方便；生产环境 `synchronize: false` + TypeORM Migration 管理结构变更，脚本入库评审、可回滚。
- **边界**：临时救火也别直接改库——先补一条迁移，保证"代码版本 → 表结构"可追溯。
- **追问**：`logging` 同理——开发环境打开看 SQL、临时排查时打开，长期全量打开会明显拖慢服务并淹没日志。

## 四、场景设计题

### Q59: 场景设计 · 设计一个用户注册登录系统（08-进阶/03 篇 · 08-进阶/11 篇）

**题目要求**：支持邮箱注册、密码登录、令牌认证，并说明如何做到"登录态可控"。

**要点式方案**

- **注册**：`POST /auth/register` 接 `RegisterDto`（`@IsEmail` + 密码强度 `@Matches`），先查邮箱是否已存在，存在返回 409；用 `bcrypt.hash(password, 10)` 加盐哈希后入库，返回 201。
- **登录**：`POST /auth/login` 按邮箱查用户，查不到或 `bcrypt.compare` 失败都返回**同一个** 401 文案（避免被枚举出哪些邮箱已注册）；成功后签发 Access Token（15m）+ Refresh Token（7d）。
- **令牌投递**：Access Token 走响应体由前端放内存；Refresh Token 用 `Set-Cookie` 写入 HttpOnly + secure + sameSite Cookie，`path` 限定在刷新接口。
- **鉴权**：JwtStrategy 解析 `Authorization: Bearer`，`validate` 返回的对象挂到 `req.user`；全局 `JwtAuthGuard` 默认拦截，用 `@Public()` 装饰器 + `Reflector` 给登录、注册开白名单。
- **登录态可控**：Refresh Token 以 SHA-256 哈希入库到 AuthSession 表（带 `deviceId`/`expiresAt`/`revoked`），刷新时轮换并吊销旧记录；登出吊销当前会话，另提供"全设备登出"。

**为什么这么设计**

- 密码哈希用 bcrypt（慢哈希、防彩虹表），Token 哈希用 SHA-256（长随机串、只需单向校验且 bcrypt 有 72 字节截断问题）——两者目标不同，选型也不同。
- 双 Token 把"频繁传输的短凭证"和"低频传输的长凭证"分开，泄露危害与用户体验各自可控；会话表补上 JWT 缺失的"主动吊销"能力。

**边界与代价**

- 登出后 Access Token 在剩余有效期内仍可用（典型 15 分钟），要么接受窗口，要么对高敏接口额外校验版本号。
- 轮换会带来并发刷新问题，前端需要把刷新请求串行化（单飞），否则第二个请求会拿到 401。

### Q60: 场景设计 · 设计一个统一错误处理方案（07-入门/05 篇）

**题目要求**：让所有接口返回格式一致的错误响应，且能区分"参数错、业务错、系统错"。

**要点式方案**

- **统一响应体**：约定 `{ code, message, details? }`——`code` 是业务码（不是 HTTP 状态码），`message` 面向用户，`details` 放字段级错误。
- **业务异常类**：继承 `HttpException`，携带业务码与消息，例如 `BusinessException.notFound('用户不存在')`、`BusinessException.forbidden('无权操作')`。
- **全局过滤器**：`@Catch()` + `ExceptionFilter` 实现 `catch(exception, host)`，按类型分派：`BusinessException` → 用它自己的 code/status；`HttpException` → 用 `getStatus()` 映射；其余未知错误 → 500 + 固定文案，并把完整堆栈写日志。
- **校验错误处理**：`ValidationPipe` 抛出的 `BadRequestException` 里带着 class-validator 的字段信息，在过滤器里抽出来拼进 `details`，让前端能逐字段高亮。
- **注册与配合**：用 `{ provide: APP_FILTER, useClass: GlobalExceptionFilter }` 注册（可注入日志服务）；成功响应交给 `TransformInterceptor`，两边共用同一套响应模型。

**为什么这么设计**

- 过滤器是异常的唯一出口，把它做成"分派中心"，业务代码就只需要 `throw` 语义化异常，不必关心响应拼装。
- 未知错误对外模糊、对内详细，是安全与可排查性的平衡点。

**边界与代价**

- 就近注册的 `@UseFilters()` 会覆盖全局过滤器，排查"格式不一致"时要先看有没有局部注册。
- 业务码体系一旦上线就是对外契约，新增容易、改难，前期要留好分段（如 4xxxx 参数、5xxxx 业务）。

### Q61: 场景设计 · 设计一个文件上传服务（08-进阶/04 篇）

**题目要求**：支持单文件与多文件上传，做类型与大小校验，上传后可访问。

**要点式方案**

- **接收**：单文件用 `@UseInterceptors(FileInterceptor('file'))` + `@UploadedFile()`；多文件用 `FilesInterceptor('files', 10)` 限制个数 + `@UploadedFiles()`。
- **校验**：`limits.fileSize` 设上限（如头像 2MB）；`fileFilter` 做 MIME 白名单（`image/jpeg|png|webp`），不合法就 `cb(new BadRequestException(...), false)`；跨接口复用的规则再封一个 `FileValidationPipe`。
- **存储**：本地盘用 `diskStorage`，`filename` 用 `Date.now() + 随机数 + extname(originalname)` 重命名，避免重名与中文乱码；要转存对象存储的走高内存路径，或直接 `memoryStorage` 拿 Buffer。
- **可访问**：`app.useStaticAssets(join(__dirname, '..', 'uploads'), { prefix: '/uploads/' })` 暴露静态目录，接口返回相对 URL 存进用户表。
- **工程加固**：上传接口必须挂鉴权 Guard；生产环境静态资源交给 Nginx/CDN，应用只负责落盘与返回 key。

**为什么这么设计**

- 校验前置到 Multer 层能最早拒绝非法请求，省掉落盘与后续处理的开销；把可复用规则抽成 Pipe 则避免了在各控制器里复制白名单。
- 重命名而非使用原始文件名，是为了消除路径穿越与重名覆盖两个风险。

**边界与代价**

- `mimetype` 来自客户端、可伪造，安全要求高的场景要读文件头二次确认。
- 单机磁盘存储横向扩展后会成为瓶颈，多实例部署前就要规划对象存储。

### Q62: 场景设计 · 设计一个 RBAC 权限管理系统（08-进阶/01 篇 · 08-进阶/12 篇）

**题目要求**：用户 → 角色 → 权限三层模型，支持接口级权限校验，并说明还能做到哪些粒度。

**要点式方案**

- **数据模型**：`users` / `roles` / `permissions` 三张主表，加 `user_roles`、`role_permissions` 两张多对多中间表。权限项用"资源:动作"命名（`user:create`、`article:delete`），便于扩展和做通配。
- **元数据声明**：自定义 `@RequirePermissions('user:create')`，内部就是 `SetMetadata('permissions', perms)`——它只贴标签，不做任何校验。
- **校验守卫**：`PermissionsGuard` 实现 `CanActivate`，`reflector.getAllAndOverride<string[]>('permissions', [context.getHandler(), context.getClass()])` 读出要求，从 `req.user` 取 `userId`，查（并缓存）该用户的权限集合，用 `every` 判断是否全部满足；未声明权限的路由直接放行。
- **注册方式**：`{ provide: APP_GUARD, useClass: PermissionsGuard }` 全局注册以便注入 UserService 或缓存服务；`JwtAuthGuard` 排在它前面，先把 `req.user` 准备好。
- **动态菜单**：登录接口顺带返回按角色算出的菜单树，前端据此渲染（注意这只是体验优化，真正的拦截仍在服务端）。

**为什么这么设计**

- 用"装饰器声明 + Guard 校验"而不是在服务层里逐个 if，权限规则就和路由定义放在一起，改接口时不会漏配。
- 用户权限集合缓存到 Redis 并按角色变更失效，避免每个请求都连表查询。

**边界与代价**

- 数据级权限（"只能看自己的订单"）没法靠 Guard 解决，要在 Service 查询里拼接租户/属主条件；字段级权限（手机号、身份证脱敏）适合放在序列化层统一处理。
- 权限集合缓存会带来"改权限到生效"的延迟，敏感操作要么缩短 TTL，要么在授予/回收时主动失效。
