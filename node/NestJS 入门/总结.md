## 1. 入门认知与工程骨架

### 1.1 框架定位：价值在"组织"

NestJS 的价值不在"能力"而在"组织"——它能做的事，裸 Node.js 都能做（能写 CRUD、能发消息、能管定时任务），它只是把"如何组织一个能长期维护的后端项目"变成了一套有约束的约定。给业务定义一个"怎么组织"的框架，是它区别于 Express/Koa 的本质：Express 是"请求 → 中间件 → 响应"，NestJS 是"请求 → 一整套生命周期 → 响应"。

### 1.2 四个认知入口与封装分层

把网络层链路接上 NestJS，得到四层封装，每层对应一个认知：

```
你的 Controller                     ← 业务只写这一层
  ↑
NestJS（DI 容器 / 装饰器 / 生命周期）  ← 本模块
  ↑
Express / Fastify（路由、中间件）      ← 模块三 Web 框架
  ↑
Node.js HTTP（报文解析与写出）         ← 模块二 网络底层
  ↑
TCP / Socket / epoll
```

| 层 | NestJS 替你决定了什么 | 认知入口 |
|----|---------------------|----------|
| DI 容器 | 对象谁创建、依赖怎么传 | IoC 与依赖注入 |
| 装饰器 + Metadata | 路由、参数、权限怎么"声明"出来 | 控制器与路由 |
| 请求生命周期 | 请求依次经过哪些环节 | 请求处理链 |
| 底层 HTTP | 报文怎么解析、响应怎么写出 | 网络模块 |

心智模型：**框架是一组"你已经认可的约定"**。学 NestJS 的重点不是记住有多少装饰器，而是理解每层约定解决什么问题——这样约定不适用时，你知道在哪打破。

### 1.3 学习边界与三个常见误区

**必须掌握**：Module / Controller / Provider 三件套、依赖注入（`@Injectable` + 构造函数注入）、请求处理链顺序、DTO + ValidationPipe、数据库集成、配置与日志。

**知道即可（用到再深挖）**：微服务、切换 Fastify、动态模块 / 自定义 Provider Token。

**可先跳过（踩到再学）**：源码级实现、循环依赖 `forwardRef`、高级装饰器元编程。

三个常见误区：

1. 把 NestJS 当"更高级的 Express"——Guard / Pipe / Interceptor / Filter 不是装饰，各自解决"能不能进 / 数据对不对 / 包裹执行 / 出错怎么办"一类明确问题，职责不可混。
2. 觉得装饰器是"魔法"——装饰器只往类/方法上贴标签，真正干活的是运行时读标签的框架代码；`@Roles('admin')` 必须配 Guard 读它才生效。
3. 一上来就拆微服务——单体 + 清晰模块划分能撑很大规模，提前拆只把分布式事务、链路追踪、服务发现提前塞给自己。

### 1.4 项目初始化与工程骨架

- 两个核心特点清单：内置 TypeScript（类型安全）、借鉴 Angular 架构（模块化 / DI / 装饰器）、底层可切换（默认 Express、可换 Fastify）、开箱即用（验证 / 序列化 / ORM 集成）。
- 初始化：`npm install -g @nestjs/cli` 装 CLI，`nest new my-project` 建项目（默认监听 3000）。
- 启动脚本：`npm run start` 单次启动，`npm run start:dev` 开发热重载。
- `src/` 四文件职责：`app.controller.ts` 处理请求、`app.module.ts` 组织代码、`app.service.ts` 承载业务、`main.ts` 为入口。
- 常用生成命令：`nest g resource users`（连带 DTO/实体/模块/控制器/服务一体生成）、`nest g module/controller/service` 单生成。
- 第一个 Controller：`@Controller('users')` 给路由前缀，`@Get()` 与 `@Get(':id')` 决定具体路径，完整路由由装饰器拼出。

## 2. IoC 与依赖注入

### 2.1 IoC 与 DI：思想与实现

- **IoC（控制反转）是思想**：把"对象创建 + 依赖管理"的控制权从业务代码反转交给框架容器。你不再主动 `new`，只声明"我需要什么"。
- **DI（依赖注入）是实现**：容器先创建好依赖，再通过构造函数注入给使用者。IoC 回答"为什么交出去"，DI 回答"怎么交出去"。
- 没有 IoC 时的痛点：手动 `new` 出整条依赖网，紧耦合、难替换 Mock 做单测、改一个构造参数要改所有调用点、共享实例全靠人肉传参。

```
没有 IoC：                      有 IoC：
const repo = new Repository()   @Controller('users')
const svc = new Service(repo)   export class Ctl {
const ctl = new Controller(svc)     constructor(
改一个参数，上面全要改                private readonly svc: Service
                                  ) {}  // 只声明，容器注入
```

- 构造函数注入一行三用：`private readonly userService: UserService` 同时声明字段、类型、依赖，运行时不赋 `new` 也直接用。

### 2.2 注入前提：@Injectable 与 design:paramtypes

- `@Injectable()` 的两个作用：把类登记进 DI 容器"可注入"名单（没有它容器不认识这个类）；配合 `emitDecoratorMetadata` 触发 `design:paramtypes` 元数据生成。
- 整条链路：TS 装饰器 → 编译时生成 `design:paramtypes`（记录构造参数类型）→ `reflect-metadata` 把元数据挂到类上 → 启动扫描 → 容器按类型解析实例化 → 注入到使用方。
- `tsconfig.json` 必须开 `experimentalDecorators` 与 `emitDecoratorMetadata` 两个开关（Nest CLI 默认开，手改配置最易误关）；只对**至少带一个装饰器的类**生成 paramtypes。
- 按 Token 注入：非类依赖（配置对象、第三方实例）用 `@Inject('CONFIG')` 显式指名。
- 心智模型：`@Injectable()` 告诉容器"我能当零件"，`emitDecoratorMetadata` 让容器"看得见零件的长相"。

### 2.3 Provider 四种声明方式

Provider 在容器里以 **Token** 为键登记，默认 Token 即类本身；非类 Token 使用方须 `@Inject()` 指名。

| 声明 | 写法 | 适用场景 |
|------|------|----------|
| `useClass` | `{ provide: UserService, useClass: UserService }` | 最常用，Token 即类 |
| `useValue` | `{ provide: 'CONFIG', useValue: { port: 3000 } }` | 注入常量 / 配置对象 / Mock，同对象引用 |
| `useFactory` | `{ provide: 'DB', useFactory: (c) => ..., inject: [ConfigService] }` | 需运行时逻辑 / 异步建连接 / 依赖其他 Provider |
| `useExisting` | `{ provide: 'Alias', useExisting: RealService }` | 给同一实例起别名 |

`useValue` 注入的是同一对象引用，`useFactory` 可声明 `inject` 依赖其他 Provider。

### 2.4 Provider 作用域 Scope

| 作用域 | 值 | 生命周期 | 场景 |
|--------|----|----------|------|
| Singleton（单例） | `Scope.DEFAULT` | 全应用一实例，所有请求共享 | 绝大多数无状态 Service |
| Request（请求级） | `Scope.REQUEST` | 每请求新建 | 绑定请求上下文（如租户隔离） |
| Transient（瞬态） | `Scope.TRANSIENT` | 每次注入新建 | 有状态、不可共享的工具类 |

- REQUEST 取当前请求：构造函数 `@Inject(REQUEST)` 注入 `Request`。
- **级联污染**：单例 A 注入了请求作用域的 B，A 也退化成请求作用域、每请求重建，整条依赖链跟着重建。
- 性能代价：REQUEST / TRANSIENT 绕过单例复用，每次创建有实例化开销，高频接口上加重 GC 压力；且请求作用域不能被单例依赖。
- 默认一律单例，只在确实需要"每请求一份状态"时才上 REQUEST；现代替代是 `AsyncLocalStorage`。

### 2.5 容器原理与循环依赖

`NestFactory.create(AppModule)` 内部流程：扫 Module 树（分析 imports/providers/controllers）→ 收集元数据 → 建依赖关系图 → 建容器 → 按依赖顺序实例化（先依赖后使用方）→ 注入 → 绑路由/Guard/Pipe → 起 HTTP Server。

```
main.ts → NestFactory.create
  ①扫描 Module 树 → ②收集元数据 → ③建依赖图 → ④建容器
  → ⑤按序实例化（先依赖后使用方） → ⑥注入
  → ⑦绑路由 / Guard / Pipe → ⑧起 HTTP Server
```

容器的核心是"读 `design:paramtypes` → 递归 resolve 每个参数 → `new Token(...args)` → 结果进单例缓存"。

**循环依赖**：依赖图出现环，容器无法确定"先实例化谁"，启动直接失败（`Nest can't resolve dependencies`）。`forwardRef(() => Xxx)` 把类型求值推迟到实例化阶段，让容器先建占位、后回填打破环。**两层都要写**：Provider 层 `@Inject(forwardRef(() => OtherService))`，模块层 `imports: [forwardRef(() => XxxModule)]`，只加一层仍报错。循环依赖通常是设计问题的信号，优先重构抽第三个服务，`forwardRef` 只是止血手段。

### 2.6 DI 报错排查三步法

```
① 该 Provider 是否在某个模块的 providers 里注册？
② 它来自别的模块？提供方要 exports: [XxxService]？
③ 使用方所在模块是否 imports: [XxxModule]？
```

口诀：**要被用，先注册；要跨模块，先导出；要用别人，先导入**。三步走完还报错，再检查 `emitDecoratorMetadata` 是否被关、构造参数是否用了接口（接口运行时不存在，须 `@Inject(TOKEN)` 指名或换成具体类）。

## 3. 模块系统

### 3.1 @Module 与模块可见性

`@Module` 是组织代码的基本单元，每个应用至少一个根模块，其余从它的 `imports` 递归挂载，这条链决定模块可见性。四字段各管一摊：

| 字段 | 作用 |
|------|------|
| `imports` | 导入其他模块 |
| `controllers` | 挂控制器（路由入口） |
| `providers` | 注册服务 / 提供器 |
| `exports` | 导出给别处用 |

`@Module({})` 空模块合法，常被动态模块当"壳"；模块可 re-export 别的模块的 exports，做能力中转。根模块唯一，负责把业务模块拼起来。

### 3.2 模块共享链：注册→导出→导入

共享关系三步缺一就报 DI 错误：提供方先 `providers` 注册、再 `exports` 导出；使用方 `imports` 引入后即可注入对方导出的 Provider。`exports` 只影响"可注入性"，不影响"是否实例化"——被 import 的模块的 Provider 仍是单例一份，不会因多处 import 重复创建。

### 3.3 @Global 全局模块

`@Global()` 让模块的 exports 注册到全局容器，任何模块无需 `imports` 就能注入，省掉大量样板 imports。**滥用会让依赖关系隐式化**——看 Service 构造函数猜不出它依赖了哪些基础设施。只给真正全局通用的模块开（配置 / 日志 / Redis 客户端 / 数据库连接），业务模块一律显式 import。

### 3.4 动态模块 forRoot / forRootAsync

动态模块是"能在 import 时传参"的模块——用静态方法返回 `DynamicModule` 对象把配置在导入阶段注入。

- `forRoot(options)`：同步直接传对象，适合配置值已知或来自环境变量的场景。
- `forRootAsync({ imports, inject, useFactory })`：把配置获取推迟到运行时，工厂可为 async，适合读 ConfigService、远程配置中心、需异步建连接的场景。
- `forRoot` 一个模块只应被调一次，`forFeature` 才是按需多次调用，两者混淆会重复创建连接。

## 4. 控制器与请求链路

### 4.1 控制器与路由装饰器

- `@Controller('users')` 字符串是**路由前缀**，最终路径 = 前缀 + 方法装饰器路径（`@Get(':id')` → `GET /users/:id`）。
- 方法装饰器：`@Get()` / `@Post()` / `@Put(':id')` / `@Patch()` / `@Delete(':id')` 运行时把 `{ method, path, handlerName }` 写进类元数据，启动时读元数据绑路由。
- 控制器只负责"收请求、还响应"，业务逻辑放 Service 层，否则难测又难复用。

### 4.2 参数装饰器与数据来源

| 装饰器 | 取什么 |
|--------|--------|
| `@Param('id')` | 路由参数 `/users/:id` |
| `@Query('page')` | 查询串 `?page=1` |
| `@Body()` | 请求体（配合 DTO + ValidationPipe） |
| `@Headers('authorization')` | 请求头 |
| `@Ip()` | 客户端 IP |
| `@Req()` | 原始 Request 对象（逃生舱） |

数据来源不同，可同现于一个方法签名；`@Param()` 不传参数名返回整个 params 对象。

### 4.3 响应处理与 RESTful

- 返回值自动序列化 JSON（默认 200）；`@HttpCode(201)` 改状态码，`@Redirect('/users', 301)` 做重定向。
- 内置 HTTP 异常语法糖：`BadRequestException`(400) / `UnauthorizedException`(401) / `ForbiddenException`(403) / `NotFoundException`(404) / `ConflictException`(409) / `InternalServerErrorException`(500)，直接 `throw` 即可。
- RESTful 方法语义：GET 查、POST 建、PUT 全量替换、PATCH 部分更新、DELETE 删。
- 命名反例：`/getUsers` 动词式、`/userList` 命名不一致、POST 做查询、把 ID 塞查询参数；规范做法是资源用复数名词、动作交给 HTTP 方法。

### 4.4 请求生命周期精确顺序

```
Middleware
  → Guard（能不能进）
    → Interceptor(before)（进入前包裹）
      → Pipe（参数校验/转换）
        → Controller
          → Service → Repository   ← 业务调用链，非框架阶段
        → Interceptor(after)（返回后包裹）
  → HTTP Response
异常：任意环节抛出 → Exception Filter 统一兜底
```

`Service` 不是框架生命周期的独立阶段，而是业务调用链（Controller → Service → Repository）的一部分——"框架何时插手"与"你业务里调了谁"是两个维度。

### 4.5 五类组件职责

| 组件 | 口诀 | 回答的问题 | 典型场景 |
|------|------|-----------|----------|
| Middleware | 预处理 | 进来之前先做什么 | 日志、CORS、cookie 解析、安全头 |
| Guard | 能不能进 | 有权限吗 | 身份认证、角色校验（403） |
| Pipe | 数据对不对 | 参数合法吗 | DTO 校验、类型转换、分页范围 |
| Interceptor | 包裹执行 | 进出前后再做什么 | 统一响应格式、耗时统计、缓存 |
| Exception Filter | 处理异常 | 出错了怎么返回 | 统一错误响应 |

- Middleware 只拿 `req/res/next`，不知道请求落到哪个 Handler；Guard 的 `ExecutionContext` 能拿 `getHandler()` / `getClass()`，只有它能按路由粒度读 `@Roles` 元数据做鉴权——所以基于装饰器元数据的鉴权放 Guard。
- Interceptor 包裹模型：`intercept()` 里必须 `return next.handle().pipe(...)`，前置逻辑在 `next.handle()` 前，`tap` 统计耗时、`map` 统一响应；漏 return 请求会挂住不响应。
- ValidationPipe 三选项：`whitelist` 剔除 DTO 未定义字段、`forbidNonWhitelisted` 遇多余字段直接 400、`transform` 自动转类型（`"1"` → `1`）。内置管道 `ParseIntPipe` / `ParseBoolPipe` / `DefaultValuePipe` 等覆盖大多数场景。
- Exception Filter 两粒度：`@Catch(HttpException)` 兜指定类型（含子类）、`@Catch()` 兜全部；`exception.getResponse()` 可能返回字符串或对象，写统一格式要兼容。
- DTO 配 class-validator：`@IsEmail` / `@MinLength` / `@MaxLength` / `@IsInt` 等声明式校验，失败自动 400、消息用 DTO 上的自定义 `message`。

### 4.6 两套生命周期

| 维度 | 名称 | 触发时机 | 典型钩子 |
|------|------|----------|----------|
| 应用级 | 应用生命周期 | 进程启动/关闭时，每请求**不**触发 | `onModuleInit` / `onApplicationBootstrap` / `onModuleDestroy` / `onApplicationShutdown` |
| 请求级 | 请求生命周期 | 每个 HTTP 请求 | Middleware → Guard → … → Response |

应用钩子适合一次性资源操作（建连接池、预热缓存、关连接、落盘）；请求生命周期是每请求跑一遍的处理管道。

### 4.7 自定义装饰器与元数据读写

Decorator 负责"写标签"、`Reflect.defineMetadata` 负责"存标签"、`Reflector` 负责"读标签"：

```
Decorrelation 分工：Decorator 写标签 → Metadata 存标签 → Reflector 读标签（运行时）
```

- **方法/类装饰器**：`SetMetadata('roles', roles)` 只写标签不干活；Guard 用 `this.reflector.getAllAndOverride('roles', [getHandler(), getClass()])` 读，参数顺序固定 `[getHandler(), getClass()]`；方法级覆盖类级，读不到（`undefined`）直接 `return true` 放行。
- **参数装饰器**：`createParamDecorator((data, ctx) => ...)`，回调第二参是 `ExecutionContext`，`ctx.switchToHttp().getRequest()` 取数据，返回值为 Handler 实参；`data` 用于让调用方定制，`@CurrentUser('id')` 返回指定字段。
- **装饰器组合**：`applyDecorators(SetMetadata, UseGuards, Swagger)` 合成一个 `@Auth('admin', 'editor')`，一处声明多处生效。
- **ExecutionContext 四能力**：`getType()` 判断 `http`/`rpc`/`ws`；`switchToHttp()` 取 `getRequest()`/`getResponse()`；`switchToRpc()` 用 `getData()`；`switchToWs()` 用 `getClient()`；`getClass()`/`getHandler()` 取控制器类与被调方法。三者不能混用，跨协议组件先 `getType()` 分流。
- 装饰器在**类定义阶段同步执行**，不能 async；异步鉴权/校验放 Guard（`canActivate` 允许 Promise/Observable）或 Pipe（`transform` 可返回 Promise）。
- `@Public()` 是同一套机制的另一用法：`SetMetadata('isPublic', true)` 贴标签，全局 `JwtAuthGuard` 读到即跳过。

### 4.8 全局注册方式：useGlobalXxx 与 APP_XXX

`app.useGlobalInterceptors(new X())` 在 `main.ts` 手工 new 出实例，**无法注入依赖**（服务会是 `undefined`）；在模块 `providers` 注册 `{ provide: APP_INTERCEPTOR, useClass: X }` 由容器创建，**可注入依赖**。`APP_GUARD` / `APP_PIPE` / `APP_FILTER` 同理。注意：在根模块注册的 `APP_*` 才是全局，子模块注册只对本模块生效；多个同类全局组件按注册顺序执行。

## 5. 数据库集成

### 5.1 TypeORM 集成三步

```
① TypeOrmModule.forRoot({ type:'mysql', host, entities, synchronize })  在根模块配连接
② @Entity('users') + @PrimaryGeneratedColumn / @Column(长度/默认/唯一/时间戳)  定义表结构
③ TypeOrmModule.forFeature([User])  在业务模块注册 Repository
```

### 5.2 实体关系装饰器

- 一对多 / 多对一：`@OneToMany(() => Order, o => o.user)` + `@ManyToOne(() => User, u => u.orders)`，外键一侧用 `@JoinColumn({ name: 'user_id' })` 指定列名。
- 多对多：一方加 `@JoinTable()` 指定维护侧，只有这一侧在库里建中间表，另一侧写对应 `@ManyToMany(() => X, x => x.students)`。
- 外键级联：`@ManyToOne(..., { onDelete: 'CASCADE' })` 等配置决定删除时的行为。

### 5.3 事务与 QueryRunner

```
createQueryRunner() → connect() → startTransaction()
   → queryRunner.manager 操作（扣余额、建订单）
   → commitTransaction()
出错 → rollbackTransaction()
finally → release()
```

事务、原生 SQL 等 Repository 覆盖不到的场景可注入 `@InjectDataSource()` 拿 `DataSource`。

### 5.4 synchronize 与迁移

- 开发开 `synchronize: true` 按实体自动改表；生产**必须关**——`synchronize` 会比对实体与真实表结构自动改表，可能直接 DROP 列/表导致数据不可逆，多实例并发启动互打架。
- 生产用 Migration 管理结构变更：`typeorm migration:generate` / `migration:run` / `migration:revert` 三条命令，脚本入库评审、可回滚。临时救火也别直接改库，先补一条迁移保证"代码版本 → 表结构"可追溯。
- `logging` 同理：开发开看 SQL，长期全量开启会拖慢服务并淹没日志。

## 6. 认证与安全

### 6.1 密码存储与注册校验

- 密码用 `bcrypt` 加盐哈希：`genSalt(10)` + `hash` 存库、登录 `compare` 比对，明文永不落库。bcrypt 是慢哈希、抗彩虹表。
- 注册链路：先查 email 是否已存在抛 `ConflictException`(409)；DTO 用 `@IsEmail` / `@MinLength` / `@Matches` 做格式校验。

### 6.2 JWT 结构与信任模型

```
JWT = Header . Payload . Signature
Header    → { alg: 'HS256', typ: 'JWT' }  算法与类型
Payload   → { sub, exp, iat, userId, role }
Signature → HMAC-SHA256(base64url(header) + '.' + base64url(payload), secret)
```

- 三段用 `.` 分隔，各段 Base64URL 编码。服务端只需用同一密钥重算签名比对，就能信 Payload 未被篡改，所以不必存 Session。
- **Payload 是 Base64 编码不是加密**：任何人能解开，绝不放密码等敏感数据；`secret` 泄露即可伪造任意 Token。Signature 只防篡改、不提供保密性。
- 与 Session 取舍：JWT 天然支持分布式、无需共享存储，代价是无法主动吊销（正是会话表存在的原因）。
- 与 Cookie 不竞争：JWT 是凭证内容、Cookie 是保存方式，放进 HttpOnly Cookie 兼得两者（但要防 CSRF）。

### 6.3 登录签发与放行机制

- `JwtModule.register({ secret, signOptions: { expiresIn } })` 配密钥与过期；`JwtService.sign(payload)` 默认 HS256 签发。
- `PassportStrategy` 用 `ExtractJwt.fromAuthHeaderAsBearerToken()` 取 `Authorization` 头令牌，`validate` 返回值挂 `request.user`。
- `@Public()` 用 `SetMetadata` 打 isPublic 标签、全局 `JwtAuthGuard` 用 `Reflector` 读到即放行——默认全局拦、白名单放行。

### 6.4 双 Token 与 HttpOnly Cookie

单 Token 的绕不开矛盾：有效期长则泄露危害大、短则频繁重登、且无法主动吊销。拆双 Token：

| Token | 有效期 | 存放 | 职责 |
|-------|--------|------|------|
| Access Token | 短（15m） | 前端内存 / `Authorization` 头 | 访问业务接口（短凭证越短越安全） |
| Refresh Token | 长（7d） | HttpOnly Cookie | 只管换发新 Access Token（长凭证只用于换发） |

Decision 模型：Access 越短越安全、Refresh 越长越省心，但**Refresh 必须有服务端能主动作废的能力**，否则退化为无法吊销的长效 JWT。

HttpOnly Cookie 选项：`httpOnly`（JS 读不到，降 XSS 窃取，**不解决 XSS 本身**）、`secure`（仅 HTTPS）、`sameSite: 'strict'`（缓解 CSRF，跨站取 `lax`/`none`）、`path: '/auth/refresh'`（缩小暴露面）、`maxAge` 对齐有效期。XSS 与 CSRF 是两条攻击线：HttpOnly 治 XSS 偷明文、sameSite 治 CSRF 借 Cookie 发力，根本对策还是修掉漏洞本身。

### 6.5 Refresh Token 哈希与 AuthSession 会话表

**Refresh Token 不能像密码用 bcrypt 存库**：bcrypt 只处理输入**前 72 字节**，Refresh Token 往往更长，超出被截断，会导致"内容不同但前 72 字节相同的两 Token 校验都被判真"。Refresh 只需**单向校验**（确认是不是当初那个）、不怕暴力枚举（随机长串），用 `sha256(token)` 存哈希即可，还比 bcrypt 快。Token 明文只在签发响应给客户端一次，服务端永远只存哈希——拖库也拿不到可用 Token。

签发时 payload 带随机 `jti`：JWT 时间戳精度到秒，只有 `{ sub }` 时同一秒两设备会签出逐字节相同 Token，哈希自然相同，会话表会查错行。

**AuthSession 表支持多设备**（User 1:N，每设备一条记录互不顶号）：

| 字段 | 用途 |
|------|------|
| `refreshTokenHash` | 校验刷新是否来自真实签发的 Token |
| `deviceId` | 区分设备，避免一台刷新把另一台踢下线 |
| `userAgent` / `clientInfo` | 给用户展示活跃设备列表 |
| `expiresAt` | 服务端侧过期闸门 |
| `revoked` | 软删除标记，登出 / 轮换置位 |

它补回 JWT 缺失的"主动吊销"能力，为无状态访问保留便利、刷新环节查一次库。

### 6.6 刷新轮换与登出

- **轮换（Refresh Token Rotation）**：每次用 Refresh Token 换新 Access，都签一对全新 Token 并让旧记录立刻失效。窃取的旧 Token 一旦重放就撞上 `revoked`，直接 401——"重放即失效"。
- 刷新流程：校验 JWT 签名与过期 → 算哈希查库比对且 `revoked = false` → 旧记录置 `revoked` → 签新 Access + 新 Refresh → 写新会话记录（沿用 `deviceId`）。
- 轮换引入"并发刷新"问题：同一客户端并发两个刷新，第二个会撞上已被吊销的旧 Token，前端需做刷新请求串行化 / 单飞。
- 登出：单设备按 `refreshTokenHash` 软删该行；全设备按 `userId` `updateMany` 一次作废全部会话——纯 JWT 做不到。
- 常见坑：`verifyAsync` 记得 `await`（否则异常被吞变 500 而非 401）；跨域 Cookie 带不上（后端 `sameSite` 放宽 + 前端 `credentials: 'include'`）；刷新缺过期校验（同时判断 `expiresAt > now()` 与 `revoked`）。
- 权衡：登出后手里那张 Access Token 在剩余短生命周期（如 15m）内仍可能有效——要么接受窗口，要么对高敏接口加版本号/黑名单。
- 微信登录只换身份来源：用 `code` 向微信换 `openid` 作唯一标识，之后 JWT 签发流程与账号密码登录一致。
- ORM 同层：Prisma 仅图类型推导，`findUnique({ where: { tokenHash } })` 对应 `sessionRepo.findOne({ where: { tokenHash } })`，设计思路一致。

## 7. 实时通信（WebSocket）

### 7.1 Gateway 角色与注册

Gateway 是 WS 层的 Controller（同样注册为 provider）。`@WebSocketGateway({ cors, namespace })` 声明，`handleConnection` / `handleDisconnect` 处理上下线。

### 7.2 消息收发与房间

- `@WebSocketServer()` 注入 `Server` 实例；`server.emit` 全局广播、`client.to(room).emit` 定向推。
- `@SubscribeMessage('event')` 收消息，回调 `(client, payload)`，`client.join(room)` 入房。
- WebSocket 与 HTTP 轮询对比：WebSocket 全双工长连接、实时性高、头部开销小；轮询实现简单、纯无状态，但延迟受间隔限制、空轮询浪费带宽。

### 7.3 连接鉴权与 HTTP 共享 Service

- 连接即校验身份：令牌取 `client.handshake.auth.token`，失败 `client.disconnect()`；通过后置 `client.data.user` 后续随取随用。
- HTTP 与 WS 共享 Service：把 `server` 注入 `NotificationService`（暴露 `setServer` / `notifyAll` / `notifyRoom`），Gateway 初始化时把 server 交给它，HTTP 控制器只管调 `notifyAll`——避免控制器直接依赖 Gateway 形成跨传输层耦合，也便于单测替换。
- 多实例部署时，A 实例推的消息到不了连在 B 实例的客户端，需 socket.io 适配器（如接 Redis）跨实例打通广播。

## 8. 文件上传

### 8.1 单文件与多文件上传

- 单文件：`FileInterceptor('file', {...})` 首个参数须与表单字段名一致，取参 `@UploadedFile()`。
- 多文件：`FilesInterceptor('files', 10)` 第二参为上限数量，取参 `@UploadedFiles()` 拿数组。
- 存储：`diskStorage` 边收边写磁盘、适合大文件低内存，`filename` 用 `Date.now()` + 随机数 + `extname(originalname)` 防重名与中文乱码；`memoryStorage` 把文件读成 Buffer、适合小文件或要立刻转存/压缩（拿 `file.buffer`），但并发大文件内存陡增，必须配 `limits.fileSize` 兜底。

### 8.2 两道校验闸

- `limits.fileSize` 限大小（`2*1024*1024`），`fileFilter` 用 mimetype 正则挡非图片，拒绝传 `false` 并抛 `BadRequestException`——它在 Multer 写入磁盘**之前**执行，是"早拒绝"、不产生落盘开销。
- 也可写 `PipeTransform` 在 `@UploadedFile(new FileValidationPipe(...))` 处校验大小与 mimetype 白名单，适合跨接口复用的可复用业务规则。
- 提示：`mimetype` 由客户端提供、可伪造，安全要求高时读文件头二次确认或上传后异步扫描。

### 8.3 静态资源暴露与上传链路

静态资源要显式开：`app.useStaticAssets(join(...), { prefix: '/uploads/' })`，否则文件存了也访问不到。完整头像链路：前端限格式大小 → 服务端验类型/大小/恶意文件 → 重命名存储 → `sharp` 缩略图（可选）→ 返回 URL 存用户表 → 配静态访问。生产静态资源交给 Nginx/CDN，应用只负责落盘与返回 key。

## 9. 定时任务与队列

### 9.1 定时任务装饰器

- 前提：`ScheduleModule.forRoot()`，否则 `@Cron` 等只是死标签。
- 三类装饰器：`@Cron`（`CronExpression` 常量或 `'*/10 * * * *'` 到点执行）、`@Timeout(n)` 只跑一次、`@Interval(n)` 固定间隔重复。
- `SchedulerRegistry` 动态管理：`addCronJob` 加、`getCronJob(name).stop()` 停、`getCronJobs()` 列全部，适合运营后台配置定时报表。

### 9.2 Bull 队列

- 注册：`BullModule.forRoot({ redis })` + `registerQueue({ name })`；生产者 `@InjectQueue('email')` 注入 `Queue` 后 `queue.add` 投递。
- 消费者：`@Processor('email')` 标类、`@Process('verification')` 标方法，载荷在 `job.data`。
- 常用选项：`attempts` 重试次数、`backoff` 重试间隔、`delay` 延迟、`removeOnComplete` 完成后清理。
- 可靠性：Bull 基于 Redis 持久化，任务先写 Redis 再消费，消费者崩溃时未 ACK 任务重新入队，语义是"至少一次投递"——所以**可能重复消费，消费端必须做幂等**（业务唯一键 + 唯一索引兜底），只配 `attempts` 不配幂等，重试就会变成重复扣款。超最大次数的任务进失败队列并告警。

### 9.3 选型：定时 vs 队列

- 固定时点 / 轻量间隔用 `@Cron` / `@Interval`（但多实例下**每个实例各跑一次**，需分布式锁或独立调度；`@Cron` 不带重试语义）。
- 异步且需失败重试或延迟动作（发验证码邮件、订单 30 分钟未支付取消、注册欢迎）用 Bull 队列，削峰填谷、不阻塞主流程。

## 10. 微服务架构

### 10.1 网关与子服务的两侧角色

- 子服务：`NestFactory.createMicroservice(Module, { transport, options })` 起，`@MessagePattern({ cmd })` + `@Payload()` 收消息取代 HTTP 路由；网关用 `NestFactory.create()` 起 HTTP。
- 网关调用：`@Inject('USER_SERVICE')` 注入 `ClientProxy` 后 `client.send({ cmd }, data)` 走传输层；`ClientsModule.register` 每项 `name+transport+options`，`name` 即注入 Token。
- 同步用 `send()`（配 `@MessagePattern`，返回 Observable 等对端结果），异步用 `emit()`（配 `@EventPattern`，发完不管，无回执）。

### 10.2 四种传输方式

| 方式 | 特点 | 适用 |
|------|------|------|
| TCP | 点对点、简单、低延迟 | 内部同步 RPC、中小规模（重启期间消息会丢） |
| Redis | Pub/Sub | 已有 Redis 场景、零新增中间件（发出去就没了） |
| RabbitMQ | 持久化 + 路由灵活 + ACK | 需可靠投递并重试的业务消息 |
| Kafka | 高吞吐 + 分区 + 可回放 | 日志 / 埋点海量数据、要管理消费位点 |

NestJS 侧切换只改 `transport` 与 `options`，业务里的 `@MessagePattern` / `@EventPattern` 不用动。

### 10.3 同步异步混用与数据一致性

- 混用示例：注册创建用户走 TCP 等结果，发邮件/送积分走 RabbitMQ 异步不阻塞，记日志再走 TCP。
- 数据一致性：单机事务解决不了跨服务一致性，生产用"本地事务 + 消息 + 补偿"实现最终一致（Saga 编排式或协同式 / TCC）；NestJS 常见落地是"先写本地库、再投事件、下游消费失败靠重试与补偿兜底"。最终一致意味着中间态对用户可见（"订单已创建、积分待发放"），前端要能表达；本地事务提交与消息投递之间要补"本地消息表 / 发件箱"。
- 什么时候拆微服务：出现"拆开才能解决的问题"才拆，不是因为它先进；触发条件是伸缩差异极大、团队边界冲突频繁、需要独立发布/故障隔离。拆前想清楚分布式事务、链路追踪、服务发现、配置中心由谁承担。模块划分清晰是拆的前提——模块本就对应未来服务边界，先把模块切干净，拆分是水到渠成。

## 11. 平台切换与源码原理

### 11.1 切换 Fastify 平台

- 收益：性能约 2~3 倍（压测 ~40000 vs Express 15000 req/s），主要快在 JSON Schema 序列化替代 `JSON.stringify`。适合高并发、I/O 密集且不重度依赖 Express 中间件生态时。
- 三处改动：① 入口装 `@nestjs/platform-fastify` 后换 `NestFactory.create<NestFastifyApplication>(AppModule, new FastifyAdapter())`；② 静态/视图 `useStaticAssets({ root, prefix })`、`setViewEngine({ engine, templates })`（写法与 Express 不同）；③ 文件上传需 `app.register(contentParser)`（来自 `fastify-multer`）才能收 multipart。
- 中间件不兼容：Fastify 不兼容 Express 的 `req/res`，`cookie-parser` / `helmet` 换 `@fastify/cookie` / `@fastify/helmet`，用 `app.register()` 注册。
- 边界：Guard / Interceptor / Pipe / Filter **与平台无关**，挂在 Nest 抽象层不直接操作原生 `req/res`，切换后照常可用；重度依赖 `passport` / `multer` 时留在 Express。

### 11.2 源码前置：装饰器与元数据

- 前置三件套：TS 装饰器、`reflect-metadata`、`design:paramtypes`——缺一个读不懂 DI。`reflect-metadata` 隔离存元数据不污染原型；`emitDecoratorMetadata` 只对至少带一个装饰器的类生成 paramtypes。
- 四类装饰器签名：类 `(target)`、方法 `(target, key, descriptor)`、属性 `(target, key)`、参数 `(target, key, parameterIndex)`。

### 11.3 启动链与请求链的最小实现

```
启动链：new Container → 收集 controller/provider
  → 读 design:paramtypes 递归注入 → 扫路由 → http.createServer
请求链：路由匹配 :param → Guard → 参数装饰器 → Pipe
  → Interceptor → Handler → res.json（出口 403 / 404 / 500）
```

- 装饰器在类定义时即写元数据（`@Module` / `@Controller` / `@Get` / `@Param` 各存各自信息）。
- 请求链各环节按有无 `canActivate` / `transform` / `intercept` 可选执行。
- 与真实源码差距：最小实现手动遍历 paramtypes，NestJS 用 `InstanceLoader` / `ModuleScanner` / `RoutesResolver` 并额外支持作用域与循环依赖（真实实现里对应 `InstanceLoader` + `ModuleRef`）。

## 12. 工程落地与项目模板

### 12.1 目录结构

- src 五大块：`common` / `config` / `constants` / `modules` / `shared`。
- 业务模块自带 `dto` / `entities` / `guards` / `services` / `strategies` + 三件套（module/controller/service）。

### 12.2 配置管理

- `config/` 集中读 `.env` 给默认值，`database.config.ts` 派生 `TypeOrmModuleOptions`（`synchronize` / `logging` 仅 development 开）。
- `.env` 按 DB / Redis / JWT 三组给变量（`JWT_EXPIRES` 默认 2h）。

### 12.3 根模块与公共设施

- 根模块用 Provider 注册 `APP_FILTER` / `APP_INTERCEPTOR`（可注入依赖）；`main.ts` 挂 `ValidationPipe`（`whitelist` / `transform` / `forbidNonWhitelisted`）+ `enableCors` + `setGlobalPrefix('api')` + Swagger。
- 数据层：实体演示主键 / 唯一列 / `select:false` 隐藏密码 / `ManyToOne` 级联删除；业务模块组合 dto/module/controller/service。
- 公共设施：统一响应 `ResponseModel` + `TransformInterceptor`、统一异常 `@Catch()` 过滤器（堆栈仅 development 显示）；`@Global()` `RedisModule` 用 `useFactory` + Token `'REDIS_CLIENT'` 全局可用。
- 健康检查查两头：`dataSource.query('SELECT 1')` 与 `redis.ping()`，任一失败置 degraded。

### 12.4 上手步骤与最佳实践

- 上手：CLI 建项目 → 装依赖 → `cp .env.example .env` → 起 MySQL / Redis → `start:dev` / `build` + `start:prod`。
- 最佳实践：按功能划模块、共享逻辑下沉、基础设施进 common、全局校验 / 响应 / 异常统一、坚持依赖注入。
