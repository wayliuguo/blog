# 请求处理链

> 一个请求从进入到返回，会经过 NestJS 的请求处理链。理解这条链，关键是先建立两个心智模型：依赖是从哪来的（IoC/DI），以及"标签"是如何被写下来又被读走的（Decorator/Metadata）。

---

## 请求处理流程总览

```
请求到达
    ↓
Middleware（中间件）→ 日志、CORS
    ↓
Guard（守卫）→ 是否允许访问（身份验证）
    ↓
Interceptor（拦截器）→ 请求前处理
    ↓
Pipe（管道）→ 参数校验与转换
    ↓
Handler（控制器方法）→ 执行业务逻辑
    ↓
Interceptor（拦截器）→ 响应后处理
    ↓
Exception Filter（异常过滤器）→ 统一错误处理
    ↓
返回响应
```

## 核心心智模型：IoC 与 DI —— 为什么 Controller 里不需要 new

刚从前端转过来的同学最常见的困惑是：在 Controller 里写 `private readonly userService: UserService`，从来没有 `new UserService()`，为什么它就能直接用？

这是因为 NestJS 帮你完成了对象的创建与装配。这套机制要拆成两层理解：

> **IoC（Inversion of Control，控制反转）是一种思想**：把"对象创建"和"依赖管理"的控制权，从写业务代码的人手里，交还给框架容器。你不再主动 `new`，而是声明"我需要什么"，由容器决定何时创建、如何组装。
>
> **DI（Dependency Injection，依赖注入）是这种思想的实现方式**：容器先把依赖（UserService）创建好，再通过构造函数"注入"给使用者（Controller）。

对照一下就清楚了。**没有 IoC** 时，依赖链要自己一层层 `new` 出来：

> 摘自 `./code/nestjs-basics/src/di/manual-wiring.ts`（反面示例，随项目一起 `npm run build` 编译）

```typescript
class UserController {
    private userService = new UserService()  // 手动创建

    getUsers() {
        return this.userService.findAll()
    }
}
```

**有 NestJS** 时，只声明类型，容器负责创建和注入：

> 摘自 `./code/nestjs-basics/src/users/users.controller.ts`（运行：`npm start`）

```typescript
@Controller('users')  // 路由前缀：所有路由都以 /users 开头
// …
export class UsersController {
    constructor(private readonly usersService: UsersService) {}
```

`private readonly userService: UserService` 这一行同时做了三件事：声明字段、声明类型、声明依赖。NestJS 在启动时扫描到这个类型，就去容器里找 `UserService` 的实例注入进来。所以**你写的不是"创建"，而是"声明需要"**。关于这套机制如何运作，进阶阅读见 [IoC 与依赖注入原理](../NestJS%20进阶/IoC%20与依赖注入原理)。

## 装饰器与元数据：标签的"写"与"读"

NestJS 大量使用装饰器（`@Get()`、`@Roles('admin')`、`@UseGuards()`），要把它们和"业务数据"区分开。这里有一套清晰的分工：

> **Decorator（装饰器）负责"写标签"**：给类 / 方法 / 参数贴上一个标记，比如"这个路由需要 admin 角色"。
> **Metadata（元数据）负责"存标签"**：装饰器内部调用 `Reflect.defineMetadata`，把标签存进一个与该类/方法绑定的元数据表里。
> **NestJS / Guard 负责"读标签"**：运行时用 `Reflector` 把标签读出来，决定该怎么处理。

关键区分：**业务数据是请求里携带的（req.body、req.user），元数据是框架层面预先定义好的（角色、是否需要鉴权等）**，两者互不直接耦合。

**写标签**：定义一个装饰器，仅做声明，本身不校验任何东西。

> 摘自 `./code/nestjs-basics/src/common/roles.decorator.ts`（运行：`npm start`）

```typescript
import { SetMetadata } from '@nestjs/common'

export const ROLES_KEY = 'roles'
export const Roles = (...roles: string[]) => SetMetadata(ROLES_KEY, roles)
```

**贴标签**：只声明"需要 admin"，但此刻什么都不发生。

> 摘自 `./code/nestjs-basics/src/users/admin.controller.ts`（运行：`npm start`）

```typescript
@Roles('admin')
@Get('users')
findAll(): User[] {
    return this.usersService.findAll()
}
```

**读标签**：Guard 里用 `Reflector` 读出来，真正做校验。

> 摘自 `./code/nestjs-basics/src/common/roles.guard.ts`（运行：`npm start`）

```typescript
@Injectable()
export class RolesGuard implements CanActivate {
    constructor(private reflector: Reflector) {}

    canActivate(context: ExecutionContext): boolean {
        const requiredRoles = this.reflector.getAllAndOverride<string[]>(ROLES_KEY, [
            context.getHandler(),
            context.getClass()
        ])
        if (!requiredRoles) return true

        const { user } = context.switchToHttp().getRequest()
        return requiredRoles.some(role => user?.roles?.includes(role))
    }
}
```

实测输出（`curl -H "Authorization: Bearer demo-token" http://localhost:3000/admin/users`，`@Roles('admin')` 配 `RolesGuard` 才真的生效——`AuthGuard` 往 `request.user` 里放了 `roles: ['admin']`）：

```
{"code":0,"data":[{"id":1,"name":"张三","age":28,"email":"zhangsan@test.com","createdAt":"2024-01-01T00:00:00.000Z","balance":100},{"id":2,"name":"李四","age":32,"email":"lisi@test.com","createdAt":"2024-01-02T00:00:00.000Z","balance":200}],"message":"success"}
```

注意：`@Roles('admin')` 只是"声明"，它自己不会拦请求。**必须有一个 Guard 配合 Reflector 去读这个标签，权限校验才真正生效**。这也是为什么写框架代码时，装饰器和 Guard 要成对出现。

## 请求生命周期的精确顺序

"中间件先执行还是守卫先执行？"——这是面试高频题。精确顺序是固定的：

```
Middleware
  → Guard            （能不能进）
    → Interceptor(before)   （进入前包裹逻辑）
      → Pipe       （参数校验/转换）
        → Controller        （控制器方法）
          → Service → Repository  （业务调用链，非框架阶段）
        → Interceptor(after)    （返回后包裹逻辑）
  → HTTP Response
异常：任意环节抛出 → Exception Filter 统一兜底
```

> 一个常被混淆的点：**Service 不是框架生命周期的一个"阶段"，而是业务调用链（Controller → Service → Repository）的一部分**。请求链路描述的是"框架在什么时候插手"，而 Service 是你业务逻辑内部的方法调用，框架不会为它单独开一个处理节点。

## 两套"生命周期"不要混为一谈

NestJS 里其实有两套完全不同的生命周期，名字都带"生命周期"，但描述的是不同维度：

| 维度 | 名称 | 触发时机 | 典型钩子 |
|------|------|----------|----------|
| 应用级 | 应用生命周期 | 整个进程启动 / 关闭时，每个请求**不会**触发 | `onModuleInit` / `onApplicationBootstrap` / `onModuleDestroy` / `beforeApplicationShutdown` / `onApplicationShutdown` |
| 请求级 | 请求生命周期 | 每一个 HTTP 请求到达时 | 上节的 Middleware → Guard → … → Response |

> 摘自 `./code/nestjs-basics/src/users/users.service.ts`（运行：`npm start`）

```typescript
@Injectable()
export class UsersService implements OnModuleInit, OnApplicationShutdown {
// …
    async onModuleInit() {
        // 应用启动时执行一次：建立连接池、预热缓存等
        console.log('UsersService 初始化')
    }

    async onApplicationShutdown(signal: string) {
        // 进程关闭时执行一次：释放连接、落盘等
        console.log('收到关闭信号', signal)
    }
// …
}
```

实测输出（`npm start` 启动日志节选）：

```
UsersService 初始化
```

> 应用生命周期钩子适合做"启动/关闭时的一次性资源操作"；请求生命周期是一条请求的处理管道。前者每个进程只跑几次，后者每次请求都跑一遍。

## ExecutionContext：为什么 Guard 比 Middleware 更强

同样是"进门前的检查"，Guard 通常比 Middleware 更受推荐，根子在于 `ExecutionContext`。

Middleware 拿到的只有 `req / res / next`，它**不知道当前请求会落到哪个 Controller、哪个方法**。而 Guard 的 `canActivate(context: ExecutionContext)` 能拿到：

> 摘自 `./code/nestjs-basics/src/common/auth.guard.ts`（运行：`npm start`）

```typescript
@Injectable()
export class AuthGuard implements CanActivate {
    canActivate(context: ExecutionContext): boolean | Promise<boolean> | Observable<boolean> {
        // 拿到当前 HTTP 请求对象
        const request = context.switchToHttp().getRequest()

        // 关键能力：拿到"即将执行的 Handler"和"所属 Controller 类"
        const handler = context.getHandler()        // 具体的方法（如 findAll）
        const controllerClass = context.getClass()  // 所属的 Controller 类
// …
        // 因为能拿到 handler / controllerClass，这里可以按路由粒度做审计与鉴权
        console.log(`[AuthGuard] ${controllerClass.name}.${handler.name} ← ${request.method} ${request.url}`)
// …
        return true
    }
}
```

实测输出（`npm start` 服务端日志节选，把"当前落到哪个 Controller 的哪个方法"直接打了出来）：

```
[AuthGuard] UsersController.findAll ← GET /users
[AuthGuard] AdminController.findAll ← GET /admin/users
```

| 能力 | Middleware | Guard |
|------|-----------|-------|
| 读取请求/响应 | 能 | 能（`switchToHttp().getRequest()`） |
| 知道当前是哪个 Handler | 不能 | 能（`getHandler()`） |
| 读取 Handler 上的元数据（如 `@Roles`） | 不能 | 能（`Reflector` + `getHandler()`） |
| 按路由粒度做权限 | 难 | 易 |

> 一句话：**Middleware 站在"门外"，只看见进来的流量；Guard 站在"门口"，还知道你要进哪扇门、门上贴了什么标签**。所以基于装饰器元数据的鉴权，几乎总是放在 Guard 里。

## 各组件职责口诀

记不住谁干什么时，用下面这张表当速查：

| 组件 | 职责口诀 | 回答的核心问题 | 典型场景 |
|------|----------|----------------|----------|
| Middleware | 预处理 | 进来之前先做什么？ | 日志、CORS、cookie 解析、安全头 |
| Guard | 能不能进 | 这个请求有权限吗？ | 身份认证、角色校验 |
| Pipe | 数据对不对 | 参数合法、类型对吗？ | DTO 校验、类型转换、分页范围 |
| Interceptor | 包裹执行 | 进出前后还要做点什么？ | 统一响应格式、耗时统计、缓存 |
| Exception Filter | 处理异常 | 出错了怎么返回？ | 统一错误响应 |

## 中间件（Middleware）

中间件函数在请求到达路由之前执行，与 Express 中间件一致。

### 方式一：类式中间件（可注入依赖）

> 摘自 `./code/nestjs-basics/src/common/logger.middleware.ts`（运行：`npm start`）

```typescript
@Injectable()
export class LoggerMiddleware implements NestMiddleware {
    use(req: Request, res: Response, next: NextFunction) {
// …
        // 用 originalUrl 而不是 url：Express 挂载中间件时会把 url 重写成相对路径
        console.log(`[LoggerMiddleware] ${req.method} ${req.originalUrl}`)
        next()
    }
}
```

在模块里用 `configure()` 把它绑到路由上：

> 摘自 `./code/nestjs-basics/src/app.module.ts`（运行：`npm start`）

```typescript
export class AppModule implements NestModule {
    configure(consumer: MiddlewareConsumer) {
        consumer
            .apply(LoggerMiddleware)
            .forRoutes('*')  // 对所有路由生效
    }
}
```

实测输出（`npm start` 服务端日志节选，每个请求进来都会先打一行）：

```
[LoggerMiddleware] GET /users
```

### 方式二：函数式中间件（无依赖注入，更轻量）

> 摘自 `./code/nestjs-basics/src/common/logger.middleware.ts`（运行：`npm start`）

```typescript
// 纯函数，不需要 @Injectable()；不依赖注入时用这种写法更轻量
export function logger(req: Request, res: Response, next: NextFunction) {
    console.log(`[functional] ${req.method} ${req.originalUrl}`)
    next()
}
```

它同样用 `configure()` 绑定，只是 `apply()` 里直接传函数引用、也不用注册 provider：

> 摘自 `./code/nestjs-basics/src/orders/orders.module.ts`（运行：`npm start`）

```typescript
@Module({
    imports: [UsersModule, CacheModule],  // 导入其他模块
    controllers: [OrdersController],      // 该模块下的控制器
    providers: [OrdersService],           // 该模块下的服务/提供器
    exports: [OrdersService]              // 导出给其他模块使用的提供器
})
export class OrdersModule implements NestModule {
    configure(consumer: MiddlewareConsumer) {
        consumer
            .apply(logger)  // 直接传函数引用，不需要注册 provider
            .forRoutes('orders')
    }
}
```

实测输出（`npm start` 服务端日志节选，只有 `/orders` 下的请求会多出 `[functional]` 这一行）：

```
[LoggerMiddleware] GET /orders/stats
[functional] GET /orders/stats
```

### 方式三：Express 原生中间件（在 main.ts 中全局使用）

> 摘自 `./code/nestjs-basics/src/main.ts`（运行：`npm start`）

```typescript
async function bootstrap() {
    const app = await NestFactory.create(AppModule)
// …
    // 方式三：Express 原生中间件（绕过 Nest 的组件体系，全局生效）
    app.use((req: any, res: any, next: any) => {
        res.setHeader('X-Powered-By', 'nestjs-basics')
        next()
    })
// …
}
```

实测输出（任意请求的响应头里都会多出这一行）：

```
[x-powered-by: nestjs-basics]
```

**使用场景**：请求日志、CORS、静态文件处理、cookie 解析、安全头设置。

## 守卫（Guard）

守卫决定请求是否放行，返回 `true` 放行，`false` 拒绝。

> 摘自 `./code/nestjs-basics/src/common/auth.guard.ts`（运行：`npm start`）

```typescript
@Injectable()
export class AuthGuard implements CanActivate {
    canActivate(context: ExecutionContext): boolean | Promise<boolean> | Observable<boolean> {
        // 拿到当前 HTTP 请求对象
        const request = context.switchToHttp().getRequest()
// …
        const token = request.headers.authorization
        if (!token) return false
// …
        // 验证 token...（演示用：真实项目里换成 jwt.verify(token, secret)）
        request.user = { id: 1, name: 'demo', roles: ['admin'] }
// …
    }
}
```

实测输出（不带 `Authorization` 头 → 403；带上 → 200）：

```
=== GET /  无 token -> 403
{"code":403,"message":"Forbidden resource","timestamp":"2026-09-17T06:15:33.301Z","path":"/"}

=== GET /  带 token -> 200
{"code":0,"data":"Hello, NestJS!","message":"success"}
```

### 使用方式

**方式一：路由级别（`@UseGuards`）**，写在 Controller 类或方法上。

> 摘自 `./code/nestjs-basics/src/users/users.controller.ts`（运行：`npm start`）

```typescript
@Controller('users')  // 路由前缀：所有路由都以 /users 开头
@UseGuards(RolesGuard)  // 整个控制器需要 admin 角色（全局那套在 main.ts / app.module.ts）
```

**方式二：全局注册（main.ts）**，写法简单，但 `new` 出来的实例拿不到依赖注入。

> 摘自 `./code/nestjs-basics/src/main.ts`（运行：`npm start`）

```typescript
    // 方式二：全局注册——写法简单，但 new 出来的实例拿不到依赖注入
    app.useGlobalGuards(new AuthGuard())
```

**方式三：全局注册（Provider 推荐）**，写成 `APP_GUARD` Provider，可以注入依赖，数组顺序就是执行顺序。

> 摘自 `./code/nestjs-basics/src/app.module.ts`（运行：`npm start`）

```typescript
import { APP_FILTER, APP_GUARD, APP_INTERCEPTOR, APP_PIPE } from '@nestjs/core'
// …
        // 全局组件推荐用 Provider 形式注册：可以注入依赖；数组顺序就是执行顺序
        { provide: APP_GUARD, useClass: AuthGuard },
        { provide: APP_GUARD, useClass: RolesGuard },
```

**使用场景**：身份验证、权限检查。

## 拦截器（Interceptor）

拦截器可以在请求处理**前后**执行逻辑，实现 `NestInterceptor` 接口。

### 基础示例

> 摘自 `./code/nestjs-basics/src/common/logging.interceptor.ts`（运行：`npm start`）

```typescript
import { CallHandler, ExecutionContext, Injectable, NestInterceptor } from '@nestjs/common'
import { Observable } from 'rxjs'
import { tap } from 'rxjs/operators'

@Injectable()
export class LoggingInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        console.log('请求前...')

        return next.handle().pipe(
            tap(data => console.log('请求后...', data))
        )
    }
}
```

实测输出（`npm start` 服务端日志节选，`请求前` 与 `请求后` 把 Handler 夹在了中间）：

```
请求前...
请求后... {
  id: 1,
  name: '张三',
  age: 28,
  email: 'zhangsan@test.com',
  createdAt: 2024-01-01T00:00:00.000Z,
  balance: 100
}
```

### 统一响应格式

> 摘自 `./code/nestjs-basics/src/common/transform.interceptor.ts`（运行：`npm start`）

```typescript
import { CallHandler, ExecutionContext, Injectable, NestInterceptor } from '@nestjs/common'
import { Observable } from 'rxjs'
import { map } from 'rxjs/operators'

export interface ApiResponse<T> {
    code: number
    data: T
    message: string
}

@Injectable()
export class TransformInterceptor<T> implements NestInterceptor<T, ApiResponse<T>> {
    intercept(context: ExecutionContext, next: CallHandler): Observable<ApiResponse<T>> {
        return next.handle().pipe(
            map(data => ({
                code: 0,
                data,
                message: 'success'
            }))
        )
    }
}
```

它在这个项目里是通过 `APP_INTERCEPTOR` 全局挂上的，所以每个成功响应都长这样：

```
{"code":0,"data":"Hello, NestJS!","message":"success"}
```

### 请求耗时统计

> 摘自 `./code/nestjs-basics/src/common/timing.interceptor.ts`（运行：`npm start`）

```typescript
import { CallHandler, ExecutionContext, Injectable, NestInterceptor } from '@nestjs/common'
import { Observable } from 'rxjs'
import { tap } from 'rxjs/operators'

@Injectable()
export class TimingInterceptor implements NestInterceptor {
    intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
        const start = Date.now()

        return next.handle().pipe(
            tap(() => {
                const duration = Date.now() - start
                console.log(`请求耗时: ${duration}ms`)
            })
        )
    }
}
```

实测输出（`npm start` 服务端日志节选）：

```
请求耗时: 1ms
```

### 使用方式

**方式一：路由级别（`@UseInterceptors`）**，可叠加多个，`@UseInterceptors` 写在类上时对该控制器所有方法生效。

> 摘自 `./code/nestjs-basics/src/users/users.controller.ts`（运行：`npm start`）

```typescript
@Controller('users')  // 路由前缀：所有路由都以 /users 开头
// …
@UseInterceptors(LoggingInterceptor)
export class UsersController {
```

**方式二：全局注册（main.ts）**，同样拿不到依赖注入。

> 摘自 `./code/nestjs-basics/src/main.ts`（运行：`npm start`）

```typescript
    app.useGlobalInterceptors(new TimingInterceptor())
```

**方式三：全局注册（Provider 推荐）**。

> 摘自 `./code/nestjs-basics/src/app.module.ts`（运行：`npm start`）

```typescript
        { provide: APP_INTERCEPTOR, useClass: TransformInterceptor },
```

**使用场景**：统一响应格式、请求耗时统计、缓存。

## 管道（Pipe）

管道对传入的参数进行转换或校验。

### 内置管道

`@Param('id', ParseIntPipe)` 会把字符串 `"1"` 转成数字 `1`；查询参数上还能先补默认值再转类型：

> 摘自 `./code/nestjs-basics/src/orders/orders.controller.ts`（运行：`npm start`）

```typescript
    @Get()
    findAll(@Query('page', new DefaultValuePipe(1), ParseIntPipe) page: number) {
        return { page, orders: this.ordersService.findAll() }
    }
```

实测输出（`curl -H "Authorization: Bearer demo-token" "http://localhost:3000/orders?page=3"`——`page` 是**数字** `3` 而不是字符串 `"3"`）：

```
{"code":0,"data":{"page":3,"orders":[]},"message":"success"}
```

**常用内置管道**：

| 管道 | 作用 |
|------|------|
| `ValidationPipe` | 基于 DTO 的声明式校验 |
| `ParseIntPipe` | 字符串转整数 |
| `ParseFloatPipe` | 字符串转浮点数 |
| `ParseBoolPipe` | 字符串转布尔值 |
| `DefaultValuePipe` | 设置默认值 |

### DTO 与 class-validator

DTO（Data Transfer Object）用于定义请求体的结构，配合 `class-validator` 实现声明式校验。

```bash
npm install class-validator class-transformer
```

> 摘自 `./code/nestjs-basics/src/users/dto/create-user.dto.ts`（运行：`npm start`）

```typescript
import { IsEmail, IsInt, IsOptional, IsString, Max, MaxLength, Min, MinLength } from 'class-validator'

export class CreateUserDto {
    @IsString({ message: '姓名必须是字符串' })
    @MinLength(2, { message: '姓名至少 2 个字符' })
    @MaxLength(50)
    name: string

    @IsInt()
    @Min(0)
    @Max(150)
    @IsOptional()
    age: number

    @IsEmail({}, { message: '邮箱格式不正确' })
    email: string

    @IsOptional()
    @IsString()
    phone?: string
}
```

### 自定义管道

> 摘自 `./code/nestjs-basics/src/common/parse-id.pipe.ts`（运行：`npm start`）

```typescript
import { ArgumentMetadata, BadRequestException, Injectable, PipeTransform } from '@nestjs/common'

@Injectable()
export class ParseIdPipe implements PipeTransform {
    transform(value: any, metadata: ArgumentMetadata) {
        // 只处理 :id 这个路径参数，其余参数原样放行 —— 这样它也能安全地全局注册
        if (metadata.type !== 'param' || metadata.data !== 'id') return value

        const id = parseInt(value, 10)
        if (isNaN(id) || id <= 0) {
            throw new BadRequestException('ID 必须是正整数')
        }
        return id
    }
}
```

实测输出（`curl -H "Authorization: Bearer demo-token" http://localhost:3000/users/abc`）：

```
{"code":400,"message":"ID 必须是正整数","timestamp":"2026-09-17T06:15:33.331Z","path":"/users/abc"}
```

> 摘自 `./code/nestjs-basics/src/users/dto/create-user.dto.ts`（运行：`npm start`）

```

```

## 异常过滤器（Exception Filter）

异常过滤器捕获未处理的异常并返回统一格式的错误响应。

### 内置 HTTP 异常

NestJS 内置了一整套 HTTP 异常类，业务代码里直接 `throw` 即可，状态码由异常类型决定：

> 摘自 `./code/nestjs-basics/src/orders/orders.controller.ts`（运行：`npm start`）

```typescript
    @Get('errors/:type')
    throwOne(@Param('type') type: string): never {
        switch (type) {
            case 'bad-request':
                throw new BadRequestException('参数错误')            // 400
            case 'unauthorized':
                throw new UnauthorizedException('未登录')           // 401
            case 'forbidden':
                throw new ForbiddenException('无权限')               // 403
            case 'not-found':
                throw new NotFoundException('资源不存在')             // 404
            case 'conflict':
                throw new ConflictException('资源冲突')               // 409
            default:
                throw new InternalServerErrorException('服务器错误')  // 500
        }
    }
```

实测输出（顺带能看到 `@Catch(HttpException)` 的过滤器把状态码与消息统一成了标准错误体）：

```
=== GET /orders/errors/bad-request -> 400
{"code":400,"message":"参数错误","timestamp":"2026-09-17T06:15:33.357Z","path":"/orders/errors/bad-request"}

=== GET /orders/errors/not-found -> 404
{"code":404,"message":"资源不存在","timestamp":"2026-09-17T06:15:33.362Z","path":"/orders/errors/not-found"}
```

### 自定义异常过滤器

> 摘自 `./code/nestjs-basics/src/common/http-exception.filter.ts`（运行：`npm start`）

```typescript
import { ArgumentsHost, Catch, ExceptionFilter, HttpException } from '@nestjs/common'
import { Response } from 'express'

@Catch(HttpException)
export class HttpExceptionFilter implements ExceptionFilter {
    catch(exception: HttpException, host: ArgumentsHost) {
        const ctx = host.switchToHttp()
        const response = ctx.getResponse<Response>()
        const status = exception.getStatus()
        const exceptionResponse = exception.getResponse()

        response.status(status).json({
            code: status,
            message: typeof exceptionResponse === 'string'
                ? exceptionResponse
                : (exceptionResponse as any).message || exception.message,
            timestamp: new Date().toISOString(),
            path: ctx.getRequest().url
        })
    }
}
```

上面两条 `errors/*` 的实测输出就是这个过滤器的产物（`code` / `message` / `timestamp` / `path` 四件套）。

### 捕获所有异常

> 摘自 `./code/nestjs-basics/src/common/all-exceptions.filter.ts`（运行：`npm start`）

```typescript
import { ArgumentsHost, Catch, ExceptionFilter, HttpException } from '@nestjs/common'
import { Response } from 'express'

@Catch()  // 不指定类型，捕获所有异常
export class AllExceptionsFilter implements ExceptionFilter {
    catch(exception: unknown, host: ArgumentsHost) {
        const ctx = host.switchToHttp()
        const response = ctx.getResponse<Response>()

        let status = 500
        let message = '服务器内部错误'

        if (exception instanceof HttpException) {
            status = exception.getStatus()
            message = exception.message
        }

        response.status(status).json({
            code: status,
            message,
            timestamp: new Date().toISOString()
        })
    }
}
```
