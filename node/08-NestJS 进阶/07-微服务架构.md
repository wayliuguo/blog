# 微服务架构

> NestJS 原生支持微服务架构，通过不同的传输层（TCP、Redis、RabbitMQ、Kafka 等）实现服务间通信。
> 承上：[模块与提供器](../07-NestJS%20入门/03-模块与提供器) —— 微服务本质是多模块拆分，先会组织 Module 才分得清 API 网关与各子服务
> 启下：[切换 Fastify 平台](./08-切换Fastify平台) —— 把底层平台从 Express 换成 Fastify，并处理 CORS、静态资源与文件上传的适配器差异

## 微服务架构概览

```
                    ┌──────────────┐
                    │  API 网关     │
                    │  (HTTP)       │
                    └──────┬───────┘
                           │
           ┌───────────────┼───────────────┐
           ▼               ▼               ▼
    ┌────────────┐  ┌────────────┐  ┌────────────┐
    │ 用户服务    │  │ 订单服务   │  │ 商品服务   │
    │ (TCP:3001)  │  │(TCP:3002)  │  │(TCP:3003)  │
    └────────────┘  └────────────┘  └────────────┘
```

## 创建微服务

本篇的配套示例在 `code/microservice-demo/`：三个进程（API 网关 + 用户微服务 + 订单微服务）全部走 TCP，不依赖 MySQL / Redis，装完依赖就能在本机跑起来。先看用户微服务的入口——把 `NestFactory.create` 换成 `NestFactory.createMicroservice`，普通应用就变成了微服务。

> 摘自 `./code/microservice-demo/user-service/src/main.ts`（运行：`npm run start:user`）

```typescript
import { NestFactory } from '@nestjs/core'
import { Transport, MicroserviceOptions } from '@nestjs/microservices'
import { UserModule } from './user.module'

async function bootstrap() {
    // 创建基于 TCP 的微服务实例
    const app = await NestFactory.createMicroservice<MicroserviceOptions>(UserModule, {
        transport: Transport.TCP,
        options: {
            host: '127.0.0.1',
            port: 3001
        }
    })

    // 启动微服务，开始监听 TCP 连接
    await app.listen()
}
bootstrap()
```

微服务启动的日志和普通 HTTP 应用有两点不同：多了 `ClientsModule dependencies initialized`（如果它注册了下游客户端），最后一行是 `NestMicroservice successfully started` 而不是 `NestApplication successfully started`。

实测输出（`npm run start:user`，为便于阅读去掉了终端颜色码，其余原样）：

```
[Nest] 6592  - 2026/09/17 15:33:53     LOG [NestFactory] Starting Nest application...
[Nest] 6592  - 2026/09/17 15:33:53     LOG [InstanceLoader] UserModule dependencies initialized +40ms
[Nest] 6592  - 2026/09/17 15:33:53     LOG [NestMicroservice] Nest microservice successfully started +26ms
```

### 定义微服务控制器

微服务不收 HTTP 请求，而是收「消息」：`@MessagePattern` 声明匹配的消息模式，`@Payload()`（或直接写参数）拿数据。下面的用户微服务控制器把两个 `cmd` 分别交给 `UserService` 处理。

> 摘自 `./code/microservice-demo/user-service/src/user.controller.ts`（运行：`npm run start:user`）

```typescript
import { Controller } from '@nestjs/common'
import { MessagePattern } from '@nestjs/microservices'
import { UserService } from './user.service'

@Controller()
export class UserController {
    constructor(private readonly userService: UserService) {}

    /**
     * 获取用户信息
     * 匹配 cmd: 'get_user'，入参为 { id }
     */
    @MessagePattern({ cmd: 'get_user' })
    getUser(data: { id: number }) {
        return this.userService.getUser(data.id)
    }

    /**
     * 创建用户
     * 匹配 cmd: 'create_user'，入参为 { name, email }
     */
    @MessagePattern({ cmd: 'create_user' })
    createUser(data: { name: string; email: string }) {
        return this.userService.createUser(data.name, data.email)
    }
}
```

注意 `@Controller()` 这里不写路由前缀——微服务没有 URL，只有消息模式。数据存在 `UserService` 的内存数组里（`./code/microservice-demo/user-service/src/user.service.ts`），所以进程重启数据就回到初始的两条。

## API 网关（TCP 客户端）

网关这边还是普通的 HTTP 控制器，只是方法体不再查库，而是把请求转给下游微服务。`ClientProxy.send()` 返回的是 **Observable**，所以要用 `firstValueFrom` 包一层才能 `await`。

> 摘自 `./code/microservice-demo/api-gateway/src/user/user.controller.ts`（运行：`npm run start:gateway`）

```typescript
import { Body, Controller, Get, Inject, Param, Post } from '@nestjs/common'
import { ClientProxy } from '@nestjs/microservices'
import { firstValueFrom } from 'rxjs'

@Controller('users')
export class UserController {
    // 注入 user-service 的客户端代理（注入名 USER_SERVICE）
    constructor(@Inject('USER_SERVICE') private readonly userClient: ClientProxy) {}

    /**
     * GET /users/:id
     * 获取用户信息，转发 cmd: 'get_user'
     */
    @Get(':id')
    async getUser(@Param('id') id: string) {
        const result = await firstValueFrom(this.userClient.send({ cmd: 'get_user' }, { id: Number(id) }))
        return result
    }

    /**
     * POST /users
     * 创建用户，转发 cmd: 'create_user'
     */
    @Post()
    async createUser(@Body() body: { name: string; email: string }) {
        const result = await firstValueFrom(this.userClient.send({ cmd: 'create_user' }, body))
        return result
    }
}
```

### 客户端连接配置

下游服务在网关的 `AppModule` 里用 `ClientsModule.register()` 声明：每项一个 `name`（注入用的 Token）+ `transport` + `options`（地址端口）。

> 摘自 `./code/microservice-demo/api-gateway/src/app.module.ts`（运行：`npm run start:gateway`）

```typescript
import { Module } from '@nestjs/common'
import { ClientsModule, Transport } from '@nestjs/microservices'
import { UserController } from './user/user.controller'
import { OrderController } from './order/order.controller'

@Module({
    imports: [
        ClientsModule.register([
            // 用户微服务客户端（注入名 USER_SERVICE，端口 3001）
            {
                name: 'USER_SERVICE',
                transport: Transport.TCP,
                options: {
                    host: '127.0.0.1',
                    port: 3001
                }
            },
            // 订单微服务客户端（注入名 ORDER_SERVICE，端口 3002）
            {
                name: 'ORDER_SERVICE',
                transport: Transport.TCP,
                options: {
                    host: '127.0.0.1',
                    port: 3002
                }
            }
        ])
    ],
    controllers: [UserController, OrderController]
})
export class AppModule {}
```

三个进程按 **user-service(3001) → order-service(3002) → api-gateway(3000)** 的顺序启动后，链路才通：网关收到 HTTP 请求 → 转成 TCP 消息发给下游 → 下游返回消息 → 网关再包成 HTTP 响应。下面这次请求里的第 4 行最能说明问题——创建订单时 `order-service` 又回头用 TCP 调了一次 `user-service` 校验用户（见 `./code/microservice-demo/order-service/src/order.service.ts`）。

实测输出（先起三个服务，再用 node 的 `http` 请求网关；`curl` 等价）：

```
GET /users/1 -> 200 {"success":true,"data":{"id":1,"name":"张三","email":"zhangsan@example.com"}}
POST /users -> 201 {"success":true,"data":{"id":3,"name":"王五","email":"wangwu@example.com"}}
GET /orders/1 -> 200 {"success":true,"data":{"id":1,"userId":1,"product":"商品A","amount":100}}
POST /orders -> 201 {"success":true,"data":{"id":3,"userId":1,"product":"商品C","amount":50}}
POST /orders -> 201 {"success":false,"message":"用户不存在，无法创建订单"}
```

最后一行是 `userId: 999` 的请求：`order-service` 通过 TCP 查 `user-service` 拿不到用户，于是拒绝创建订单——跨服务校验就是这么落到代码里的。

## RabbitMQ 传输

TCP 只适合点对点。换成 **RabbitMQ** 只要改 `transport` 与 `options`：微服务端多一个 `queue`（消费队列）与 `queueOptions`，客户端指向同一个队列。

> 摘自 `./code/advanced-lab2/src/07-transports.ts`（运行：`npm run 07transports`）

```typescript
// 微服务端：NestFactory.createMicroservice(Module, rmqServerOptions)
export const rmqServerOptions = {
    transport: Transport.RMQ,
    options: {
        urls: ['amqp://localhost:5672'],
        queue: 'user_queue',
        queueOptions: { durable: false }
    }
}

// …

// 客户端：ClientsModule.register([rmqClientOptions])
export const rmqClientOptions = {
    name: 'USER_SERVICE',
    transport: Transport.RMQ,
    options: {
        urls: ['amqp://localhost:5672'],
        queue: 'user_queue'
    }
}
```

`queueOptions.durable: false` 表示队列不持久化——broker 重启后队列会消失，适合演示；要可靠投递就给它配上持久化与 ACK。

## Redis 传输

**Redis** 传输基于 Pub/Sub，项目里已经有 Redis 时最省事：不需要新增中间件，只要一个能连上的地址。

> 摘自 `./code/advanced-lab2/src/07-transports.ts`（运行：`npm run 07transports`）

```typescript
// 微服务端：NestFactory.createMicroservice(Module, redisServerOptions)
export const redisServerOptions = {
    transport: Transport.REDIS,
    options: {
        host: 'localhost',
        port: 6379
    }
}

// …

// 客户端：ClientsModule.register([redisClientOptions])
export const redisClientOptions = {
    name: 'USER_SERVICE',
    transport: Transport.REDIS,
    options: { host: 'localhost', port: 6379 }
}
```

四种传输的差别只在 `transport` 与 `options` 这两个字段上，业务代码（`@MessagePattern` / `client.send`）完全不用改：

## 传输方式对比

| 传输 | 特点 | 适用场景 |
|------|------|---------|
| **TCP** | 点对点、简单、低延迟 | 内部服务间通信，中小规模 |
| **Redis** | 基于 Pub/Sub，无需额外中间件 | 已有 Redis 的场景 |
| **RabbitMQ** | 消息持久化、路由灵活、ACK 机制 | 需要可靠投递的场景 |
| **Kafka** | 高吞吐、分区、持久化 | 大数据量、日志收集 |

## 生产场景：用户注册流程

```
API 网关 (HTTP)
    │
    ├── TCP ──→ 用户微服务：创建用户
    │
    ├── RMQ ──→ 邮件微服务：发送验证邮件（异步）
    │
    ├── RMQ ──→ 积分微服务：赠送注册积分（异步）
    │
    └── TCP ──→ 日志微服务：记录操作日志
```

## 小结

- **微服务两侧的角色与写法**
  - **子服务怎么起**：`NestFactory.createMicroservice<MicroserviceOptions>(Module, { transport, options })`，`options` 里给 `host` 与 `port`，网关仍用 `NestFactory.create()` 起 HTTP
  - **子服务怎么收消息**：`@MessagePattern({ cmd: 'get_user' })` 配 `@Payload()` 读参数，取代 HTTP 路由
  - **网关怎么发起调用**：`@Inject('USER_SERVICE')` 注入 `ClientProxy` 后 `client.send({ cmd }, data)` 走传输层调下游
  - **下游服务在哪声明**：`ClientsModule.register` 每个服务一项 `name + transport + options`，`name` 就是注入时用的 Token
- **四种传输方式的权衡**
  1. **TCP**：点对点、简单、低延迟，适合内部服务间通信与中小规模
  2. **Redis**：基于 Pub/Sub，无需额外中间件，适合已有 Redis 的场景
  3. **RabbitMQ**：消息持久化、路由灵活、有 ACK 机制，适合需要可靠投递的场景
  4. **Kafka**：高吞吐、分区、持久化，适合大数据量与日志收集
- **同步与异步要在同一条链路上混用**：注册流程里创建用户走 TCP 等结果，发验证邮件、赠送注册积分走 RMQ 异步不阻塞主流程，记录操作日志再走 TCP
