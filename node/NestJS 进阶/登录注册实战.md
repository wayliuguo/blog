> 摘自 `./code/nestjs-template/src/modules/auth/auth.service.ts`

```typescript
import * as bcrypt from 'bcrypt'

// …

/** bcrypt 加盐轮数（10 轮约 100ms，兼顾安全与性能） */
const BCRYPT_ROUNDS = 10

// …

@Injectable()
export class AuthService {
    // …

    /**
     * 用户注册：邮箱唯一校验 → bcrypt 哈希密码 → 入库。
     * @returns 不含密码的用户基本信息
     */
    async register(dto: RegisterDto) {
        const exists = await this.userRepo.findOne({
            where: { email: dto.email }
        })
        if (exists) throw new ConflictException('该邮箱已注册')

        const password = await bcrypt.hash(dto.password, BCRYPT_ROUNDS)
        const user = this.userRepo.create({
            email: dto.email,
            username: dto.username,
            password,
            role: 'user'
        })
        await this.userRepo.save(user)

        this.logger.log(`用户注册成功: ${user.email}`)
        return {
            id: user.id,
            email: user.email,
            username: user.username,
            role: user.role
        }
    }
    // …（本类里还有 login / refresh / logout，下文逐段引用）
}
```

（`nestjs-template` 依赖 MySQL 与 Redis，本机没有起这两个服务、也未安装依赖，以上代码未实跑，只做了逐字摘录。）

对照 Demo 里常见的写法，这里有三处差别值得记一下：轮数用常量 `BCRYPT_ROUNDS = 10` 而不是硬编码；`bcrypt.hash` 一次性完成「生成盐 + 哈希」两步，不用先 `genSalt` 再 `hash`；返回值刻意剔掉了 `password`，避免哈希值回给前端。

```typescript
import { ApiProperty } from '@nestjs/swagger'
import { IsEmail, IsNotEmpty, IsString, MaxLength, MinLength } from 'class-validator'

export class RegisterDto {

    email: string

    @ApiProperty({ description: '用户名', example: '张三' })
    @IsString({ message: '用户名必须为字符串' })
    @IsNotEmpty({ message: '用户名不能为空' })
    @MaxLength(64, { message: '用户名最长 64 个字符' })
    username: string

    @ApiProperty({ description: '密码', example: '123456' })
    @IsString({ message: '密码必须为字符串' })
    @IsNotEmpty({ message: '密码不能为空' })

    @MaxLength(32, { message: '密码最长 32 个字符' })

```

三个字段的校验都写在装饰器上，由全局 `ValidationPipe` 统一执行，业务代码里不必再手写 `if`。想看「密码必须包含大小写字母和数字」这类更严的规则，加一个 `@Matches(/.../)` 即可，本项目的取舍是最短 6 位 + 最长 32 位；`@ApiProperty` 只影响 Swagger 文档，不参与校验。

### JWT 原理

JWT（JSON Web Token）是一种开放标准（RFC 7519），用于在双方之间安全传递信息。

#### JWT 结构

一个 JWT 由三部分组成，用 `.` 分隔：

```
eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOiIxIiwiZW1haWwiOiJ0ZXN0QGV4LmNvbSJ9.SflKxwRJSMeKKF2QT4f
└────────────── Header ─────────────┘└────────────── Payload ─────────────┘└──────── Signature ────────┘
```

| 部分 | 内容 | 说明 |
|------|------|------|
| Header | `{"alg": "HS256", "typ": "JWT"}` | 签名算法和令牌类型 |
| Payload | `{"sub": 1, "email": "test@ex.com", "exp": 1696000000}` | 实际数据（用户 ID、邮箱、过期时间等） |
| Signature | HMAC-SHA256(Header + Payload, secret) | 防篡改签名 |

#### 签发与验证流程

```
签发（服务端登录）：
    Header  → Base64URL 编码
    Payload → Base64URL 编码
    两者拼接后用 secret 做 HMAC-SHA256 签名
    → 返回 Base64(Header).Base64(Payload).Signature

验证（服务端中间件）：
    1. 取出 Header 和 Payload
    2. 用同样的 secret 重新计算签名
    3. 对比签名是否一致（不一致说明被篡改）
    4. 检查 exp 是否过期
```

#### JWT vs Session 对比

| 对比项 | Session | JWT |
|--------|---------|-----|
| 存储位置 | 服务端内存/Redis | 客户端（localStorage/Cookie） |
| 扩展性 | 多服务器需共享 Session | 天然支持分布式，无需共享 |
| 主动注销 | 删 Session 即可 | 需额外机制（黑名单/短过期） |
| 大小 | Cookie 中存 Session ID | JWT 本身携带数据，体积较大 |

#### 安全注意事项

- Payload 只是 Base64 编码，**不是加密**，不要放敏感信息（密码等）
- secret 必须足够复杂，泄露后所有 Token 都可被伪造
- Access Token 建议短过期（如 15m）+ Refresh Token 长过期（如 7d）；下文会解释为什么要这样设计
- 主动注销场景需配合 Redis 黑名单或版本号机制
- **JWT 与 Cookie 不是竞争关系**：JWT 是"凭证内容"（令牌本身），Cookie 是"保存方式"（令牌放在哪）。两者可以结合——把 JWT 放进 HttpOnly Cookie，既享受无状态校验，又降低 XSS 窃取风险

### 签发 JWT

> 摘自 `./code/nestjs-template/src/modules/auth/auth.service.ts`

```typescript
import { JwtService } from '@nestjs/jwt'

// …

@Injectable()
export class AuthService {
    // …

    /**
     * 用户登录：按邮箱查找用户并校验密码，校验通过签发令牌对。
     * 密码比对使用 bcrypt.compare（常量时间比较，防时序攻击）。
     */
    async login(dto: LoginDto) {
        const user = await this.userRepo.findOne({ where: { email: dto.email } })
        if (!user) throw new UnauthorizedException('邮箱或密码错误')

        const ok = await bcrypt.compare(dto.password, user.password)
        if (!ok) throw new UnauthorizedException('邮箱或密码错误')

        return this.generateTokens(user)
    }

    // …

    /**
     * 生成 access + refresh 令牌对。
     * - accessToken：JWT，payload 为 { sub, email, role }，不存储。
     * - refreshToken：随机 32 字节 hex，以 SHA-256 哈希为 key 存入 Redis，
     *   携带用户信息，TTL = refreshExpires。
     */
    private async generateTokens(user: User) {
        const { jwtExpires, refreshExpires } = this.configService.get<ISecurityConfig>('security')!

        const payload = { sub: user.id, email: user.email, role: user.role }
        const accessToken = this.jwtService.sign(payload)

        const refreshToken = randomBytes(32).toString('hex')
        const hash = this.sha256(refreshToken)

        const stored: RefreshTokenPayload = {
            userId: user.id,
            email: user.email,
            role: user.role
        }
        await this.redisService.set(`${REFRESH_TOKEN_PREFIX}${hash}`, stored, refreshExpires)

        return {
            accessToken,
            refreshToken,
            expiresIn: jwtExpires,
            user: {
                id: user.id,
                email: user.email,
                username: user.username,
                role: user.role
            }
        }
    }
    // …（本类里还有 refresh / logout / sha256 等方法）
}
```

（`nestjs-template` 依赖 MySQL 与 Redis，本机未起这两个服务、也未安装依赖，以上代码未实跑。)

登录这段只做两件事：查人 + 比密码，**失败时两种情况返回同一句错误文案**（`邮箱或密码错误`），免得攻击者靠文案差异探测某个邮箱是否注册过。真正签 Token 的是 `generateTokens`：

- `this.jwtService.sign(payload)` 不传 `expiresIn`，用的是 `JwtModule.registerAsync` 里的模块级默认值；
- Access Token 是 JWT，**服务端不存储**；Refresh Token 反过来——它是随机 32 字节，存进 Redis 的是它的 SHA-256 哈希（`token:refresh:{hash}`），TTL 就是 `refreshExpires`。这样即使 Redis 数据泄露，攻击者也拿不到可用的 Refresh Token 原文。

```typescript
import { ConfigModule, ConfigService } from '@nestjs/config'
import { JwtModule } from '@nestjs/jwt'
import { PassportModule } from '@nestjs/passport'

import { ISecurityConfig } from '~/config/configuration'
import { UsersModule } from '~/modules/users/users.module'
import { AuthController } from './auth.controller'
import { AuthService } from './auth.service'
import { JwtStrategy } from './strategies/jwt.strategy'

@Module({
    imports: [
        PassportModule,
        // UsersModule 内部 TypeOrmModule.forFeature([User]) 并 re-export，
        // 导入后即可在本模块注入 User Repository（AuthService 使用）
        UsersModule,

            inject: [ConfigService],

                return {
                    secret: jwtSecret,
                    // expiresIn 接受字符串（如 '2h'）或数字（秒）
                    signOptions: { expiresIn: jwtExpires } as any
                }
            }
        })
    ],
    controllers: [AuthController],
    providers: [AuthService, JwtStrategy],
    exports: [AuthService, JwtModule]
})
export class AuthModule {}
```

### JWT 验证 Guard

> 摘自 `./code/nestjs-template/src/modules/auth/strategies/jwt.strategy.ts`

```typescript
import { Injectable, UnauthorizedException } from '@nestjs/common'
import { ConfigService } from '@nestjs/config'
import { PassportStrategy } from '@nestjs/passport'
import { ExtractJwt, Strategy } from 'passport-jwt'
import type { Request } from 'express'

import { ISecurityConfig } from '~/config/configuration'
import { RedisService } from '~/shared/redis/redis.service'

/** Token 黑名单 Redis 键前缀，格式 token:blacklist:{accessToken} */
const TOKEN_BLACKLIST_PREFIX = 'token:blacklist:'

/** JWT payload 类型定义，与 AuthService.generateTokens 中 jwtService.sign 的参数一致 */
interface JwtPayload {
    /** 用户 ID（对应数据库自增主键） */
    sub: number
    /** 用户邮箱 */
    email: string
    /** 角色，默认 'user' */
    role: string
}

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {
    constructor(
        private readonly configService: ConfigService,
        private readonly redisService: RedisService
    ) {
        super({
            // 从 Authorization: Bearer <token> 提取 JWT
            jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
            // 不忽略过期时间，过期 token 直接拒绝
            ignoreExpiration: false,
            secretOrKey: configService.get<ISecurityConfig>('security')!.jwtSecret,
            // 将原始 Request 传入 validate，便于提取原始 token 做黑名单检查
            passReqToCallback: true
        })
    }

    /**
     * 验证通过签名后的二次校验。
     * 解析出原始 token，检查其是否已登出（加入 Redis 黑名单），
     * 返回的用户对象会被注入到 request.user 上，供后续 Guard / Controller 使用。
     */
    async validate(request: Request, payload: JwtPayload) {
        const token = ExtractJwt.fromAuthHeaderAsBearerToken()(request)
        if (!token) {
            throw new UnauthorizedException('未提供认证令牌')
        }

        // 黑名单检查：登出的 token 即使未过期也拒绝
        const blacklisted = await this.redisService.exists(`${TOKEN_BLACKLIST_PREFIX}${token}`)
        if (blacklisted) {
            throw new UnauthorizedException('令牌已失效')
        }

        return {
            id: payload.sub,
            email: payload.email,
            role: payload.role || 'user'
        }
    }
}
```

（`nestjs-template` 依赖 MySQL 与 Redis，本机未起这两个服务、也未安装依赖，以上代码未实跑。)

签名校验由 Passport 完成，`validate` 里做的是**签名之后的二次校验**：`passReqToCallback: true` 把原始 `Request` 传进来，再取出原始 token 去 Redis 查黑名单——登出过的 token 即便签名有效、也没过期，照样 401。`validate` 的返回值挂到 `request.user` 上。

这个策略不是手动 `@UseGuards(AuthGuard('jwt'))` 挂上去的，而是由下面的全局守卫统一接管。

### @Public() 跳过验证

> 摘自 `./code/nestjs-template/src/modules/auth/decorators/public.decorator.ts`

```typescript

/** 元数据键名，JwtAuthGuard 通过此键读取是否为公开路由 */
export const PUBLIC_KEY = 'public'

/** 标记接口为公开访问（跳过 JWT 认证守卫） */

```

> 摘自 `./code/nestjs-template/src/modules/auth/guards/jwt-auth.guard.ts`

```typescript
import { ExecutionContext, Injectable, UnauthorizedException } from '@nestjs/common'
import { Reflector } from '@nestjs/core'
import { AuthGuard } from '@nestjs/passport'

import { PUBLIC_KEY } from '../decorators/public.decorator'

@Injectable()
export class JwtAuthGuard extends AuthGuard('jwt') {
    constructor(private readonly reflector: Reflector) {
        super()
    }

    /**
     * 判断当前请求是否需要认证。
     * 先读取 @Public() 元数据，标记为公开则直接放行；
     * 否则调用父类 AuthGuard('jwt') 的 canActivate 执行 JWT 验证。
     */
    canActivate(context: ExecutionContext) {
        const isPublic = this.reflector.getAllAndOverride<boolean>(PUBLIC_KEY, [
            context.getHandler(),
            context.getClass()
        ])

        if (isPublic) return true

        return super.canActivate(context)
    }
    // …（本类还重写了 handleRequest，把 Passport 的错误统一成 401）
}
```

`@Public()` 只干一件事：往方法上写一条 `public = true` 的元数据。判断发生在全局守卫 `JwtAuthGuard` 的 `canActivate` 里——`getAllAndOverride` 按「方法 → 类」的顺序找这条元数据，找到就直接 `return true`（登录、注册、刷新、健康检查都靠它放行），否则交给父类 `AuthGuard('jwt')` 走完整的 JWT 校验。这个守卫在 `AppModule` 里用 `APP_GUARD` 全局注册，所以控制器上一个 `@UseGuards` 都不用写。

## 生产级认证视角：单 Token 的矛盾与双 Token 方案

上面把 JWT 直接当登录凭证发出去，在 Demo 里没问题，但生产环境会撞上一个绕不开的矛盾：

> **单 Token 的矛盾**
> - 有效期设长（比如 7 天）：用户体验好，但一旦 Token 泄露，攻击者能在 7 天内一直冒充用户，且 JWT 天然无法主动吊销。
> - 有效期设短（比如 15 分钟）：泄露损失有限，但用户每 15 分钟就要重新登录一次，体验崩塌。

解法不是二选一，而是**拆成两个 Token**，各自承担不同职责：

| Token | 有效期 | 职责 | 泄露后果 |
|-------|--------|------|----------|
| Access Token | 短，如 15m | 访问业务接口的凭证，每次请求携带 | 短期有效，危害有限 |
| Refresh Token | 长，如 7d | 仅用于换发新的 Access Token | 可配合吊销/轮换机制兜底 |

这样用户只在首次登录时输密码，之后靠 Access Token 干活，过期了用 Refresh Token 无感换新。关于 Refresh Token 怎么安全存储、如何支持多设备、如何轮换与登出，进阶阅读见 [认证进阶：双 Token 与多设备会话](./认证进阶-双Token与多设备会话)。

## Refresh Token 机制

### 双 Token 策略

> 摘自 `./code/advanced-lab/src/03-tokens.ts`（运行：`npm run 03tokens`）

```typescript
// Access Token：短期有效（2小时），用于访问资源
// Refresh Token：长期有效（7天），用于获取新的 Access Token

@Injectable()
export class AuthService {
    constructor(private readonly jwtService: JwtService) {}

    login(user: { id: number; email: string }) {
        const payload = { sub: user.id, email: user.email }

        return {
            access_token: this.jwtService.sign(payload, { expiresIn: '2h' }),
            refresh_token: this.jwtService.sign(payload, { expiresIn: '7d' })
        }
    }

    refreshToken(refreshToken: string) {
        try {
            const payload = this.jwtService.verify(refreshToken)
            const newPayload = { sub: payload.sub, email: payload.email }

            return {
                access_token: this.jwtService.sign(newPayload, { expiresIn: '2h' })
            }
        } catch {
            throw new UnauthorizedException('Refresh Token 已过期，请重新登录')
        }
    }
}
```

实测输出（`npm run 03tokens`）：

```
=== 1) 用户登录：同一个账号签出两份 Token ===
  access_token  = eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ...
  refresh_token = eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ...

  access_token   alg=HS256 sub=1 email=test@ex.com iat=1789629102 exp=1789636302 有效期=7200s（2 小时）
  refresh_token  alg=HS256 sub=1 email=test@ex.com iat=1789629102 exp=1790233902 有效期=604800s（7 天）

=== 2) 用 Refresh Token 换新的 Access Token ===
  换到的 access_token = eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJ...
  new access     alg=HS256 sub=1 email=test@ex.com iat=1789629102 exp=1789636302 有效期=7200s（2 小时）
  和刚登录时那份 access_token 内容相同：true（同一秒里签发、payload 和 exp 都一样，所以字符串一致）

=== 3) 拿 Access Token 去验证：签名对了就通过 ===
  verify 通过，payload = {"sub":1,"email":"test@ex.com","iat":1789629102,"exp":1789636302}

=== 4) Refresh Token 过期后会怎样（签一个 1 秒就过期的）===
  1s token       alg=HS256 sub=1 email=test@ex.com iat=1789629102 exp=1789629103 有效期=1s（1 秒）
  等待 1.2 秒...
  抛出：UnauthorizedException: Refresh Token 已过期，请重新登录
```

两份 Token 的 payload 完全一样，**只有 `exp` 不同**：7200 秒 vs 604800 秒。第 4 段特意签了一个 1 秒过期的 token 再等 1.2 秒，`jwtService.verify` 抛出 `TokenExpiredError`，被 `catch` 兜住转成了那句 401 文案——这正是前端触发「无感刷新」失败、跳回登录页的时刻。

## 用 HttpOnly Cookie 保存 Refresh Token

把 Refresh Token 直接返回给前端、由前端存 `localStorage`，是最常见的 XSS 重灾区——一段被注入的脚本就能把 Token 读走发到攻击者服务器。更稳妥的做法是让服务端通过 `Set-Cookie` 把它写进 **HttpOnly Cookie**：

> 摘自 `./code/advanced-lab/src/03-cookie.ts`（运行：`npm run 03cookie`）

```typescript
// 登录成功后，把 refresh_token 写入 HttpOnly Cookie
@Post('login')
async login(@Body() dto: LoginDto, @Res({ passthrough: true }) res: Response) {
    const { access_token, refresh_token } = await this.authService.login(dto)

    res.cookie('refresh_token', refresh_token, {
        httpOnly: true,   // JS 读不到，挡掉大多数 XSS 窃取
        secure: true,     // 仅 HTTPS 传输
        sameSite: 'strict', // 阻止跨站请求携带，缓解 CSRF
        path: '/auth/refresh', // 只在刷新接口带上，缩小暴露面
        maxAge: 7 * 24 * 60 * 60 * 1000
    })

    // Access Token 仍走响应体，由前端带在 Authorization 头
    return { access_token }
}
```

几个边界要讲清楚：

| 选项 | 作用 | 能解决什么 | 不能解决什么 |
|------|------|------------|--------------|
| `httpOnly` | JS 无法读 Cookie | 降低 XSS 直接窃取 Token 的风险 | 不解决 XSS 本身（XSS 仍能以用户身份发请求） |
| `secure` | 仅 HTTPS 传输 | 防止明文链路被抓包 | 不防同源内的其他风险 |
| `sameSite` | 跨站不自动带 Cookie | 缓解 CSRF | 宽松场景需权衡兼容性 |
| `path` | 限定携带路径 | 缩小 Token 暴露面 | —— |

> HttpOnly Cookie 是"降低风险"而非"消灭风险"。它让 XSS 拿不到 Token 明文，但如果页面已被 XSS 控制，攻击者仍可以"借用户的浏览器"带着 Cookie 发请求。**真正的对策是同时修掉 XSS 漏洞本身**，Cookie 方案只是兜底的一道防线。另外 Access Token 因为要前端手动塞进 `Authorization` 头，通常仍放在内存/状态管理里，不进 Cookie。

## 微信小程序登录

> 摘自 `./code/advanced-lab/src/03-wechat.ts`（运行：`npm run 03wechat`）

```typescript
@Injectable()
export class WechatAuthService {
    constructor(
        private userRepository: UserRepository,
        private jwtService: JwtService
    ) {}

    async wechatLogin(code: string) {
        // 1. 用 code 向微信服务器换取 session_key 和 openid
        const response = await axios.get(wechatEndpoint, {
            params: {
                appid: 'your-app-id',
                secret: 'your-app-secret',
                js_code: code,
                grant_type: 'authorization_code'
            }
        })

        // 微信出错时返回的是 HTTP 200 + errcode，必须自己判
        if (response.data.errcode) {
            throw new UnauthorizedException(`微信登录失败：${response.data.errmsg}`)
        }

        const { openid, session_key } = response.data

        // 2. 查找或创建用户
        let user = await this.userRepository.findOneBy({ wechatOpenId: openid })
        if (!user) {
            user = this.userRepository.create({ wechatOpenId: openid })
            user = await this.userRepository.save(user)
        }

        // 3. 签发 JWT
        const payload = { sub: user.id, openid: openid }
        return {
            access_token: this.jwtService.sign(payload),
            session_key // 演示用：真实项目里 session_key 绝不能返回给前端
        }
    }
}
```

实测输出（`npm run 03wechat`；脚本在本地起了一个假的微信服务器顶替 `api.weixin.qq.com`，所以不用真的 appid/secret 也能跑通）：

```
本地 stub 已启动：http://127.0.0.1:52161/sns/jscode2session

=== 1) 第一次用 code 登录：openid 没见过的用户会被创建 ===
  [stub] 收到请求 /sns/jscode2session?appid=your-app-id&js_code=good-code&grant_type=authorization_code
  access_token 的 payload = {"sub":1,"openid":"oX9kZ5fakeOpenId","iat":1789629111}

=== 2) 同一个 openid 再登一次：复用已有用户，不重复建号 ===
  [stub] 收到请求 /sns/jscode2session?appid=your-app-id&js_code=good-code&grant_type=authorization_code
  access_token 的 payload = {"sub":1,"openid":"oX9kZ5fakeOpenId","iat":1789629111}
  两次的 sub 都是 1 —— 说明第二次走的是「查到已有用户」而不是新建（新建会变成 2）

=== 3) code 无效时：微信返回 errcode，服务端要自己判并转成 401 ===
  [stub] 收到请求 /sns/jscode2session?appid=your-app-id&js_code=bad-code&grant_type=authorization_code
  抛出：UnauthorizedException: 微信登录失败：invalid code, rid: 65f0a1b2-3c4d5e6f
```

第 2 段是关键：同一个 `openid` 进来两次，`sub` 都是 1，说明走的是「查到已有用户」而不是新建。第 3 段则是微信接口的经典坑——**code 无效时它返回的是 HTTP 200，错误码藏在响应体的 `errcode` 里**，不自己判就会把一次失败当成登录成功。

> 微信登录的核心是用 `code` 换取 `openid` 作为用户唯一标识，再走和账号密码登录一样的 JWT 签发流程。区别只是"身份证明"来自微信而非密码。

## 配套代码

本篇有两个项目：

- `node/NestJS 进阶/code/nestjs-template` —— 一个结构完整的 Nest 应用（MySQL + TypeORM + Redis），登录注册跑的就是它；依赖 MySQL 与 Redis，本机没起这两个服务，所以只做了逐字摘录、**未实跑**。
