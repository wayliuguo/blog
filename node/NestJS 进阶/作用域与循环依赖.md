# 作用域与循环依赖

## Provider 作用域

Provider 的作用域决定了实例的生命周期。

> 摘自 `./code/advanced-lab/src/02-scope-and-circular.ts`（运行：`npm run 02scope`）

```typescript
import { Injectable, Scope } from '@nestjs/common'

// …

// ====== 1) 三种 Provider 作用域 ======
// DEFAULT（默认）：单例模式，整个应用共享一个实例
@Injectable()
export class SingletonService {}

// REQUEST：每个请求创建一个新实例
@Injectable({ scope: Scope.REQUEST })
export class RequestScopedService {
    constructor(@Inject(REQUEST) private request: Request) {}
}

// TRANSIENT：每次注入都创建一个新实例
@Injectable({ scope: Scope.TRANSIENT })
export class TransientService {}
```

实测输出（`npm run 02scope` 第 1 段；`controller` / `singleton` / `transient` 是脚本给每个实例打的编号，同一个实例永远是同一个号）：

```
=== 1) 只注入单例 + 瞬态：控制器自己也是单例，两次请求实例完全相同 ===
  GET /singleton  → {"controller":1,"singleton":2,"transient":3}
  GET /singleton  → {"controller":1,"singleton":2,"transient":3}
```

两次请求三个编号一个没变：控制器只注入了单例和瞬态，自己也就还是个单例。

### 作用域对比

| 作用域 | 说明 | 使用场景 |
|--------|------|---------|
| `DEFAULT`（单例） | 所有请求共享一个实例 | 大部分 Service |
| `REQUEST`（请求级） | 每个请求创建新实例 | 获取请求上下文 |
| `TRANSIENT`（瞬态） | 每次注入创建新实例 | 无状态工具类 |

### 请求作用域的使用

> 摘自 `./code/advanced-lab/src/02-scope-and-circular.ts`（运行：`npm run 02scope`）

```typescript
// ====== 2) 请求作用域里怎么拿到当前请求 ======
@Injectable({ scope: Scope.REQUEST })
export class RequestLogger {
    constructor(@Inject(REQUEST) private request: Request) {
        console.log('新请求:', request.url)
    }

    log(message: string) {
        console.log(`[${this.request.url}] ${message}`)
    }
}
```

实测输出（`npm run 02scope` 第 2 段；`/scope` 请求两次，注意 `requestScoped` / `requestLogger` 两组编号每次都换，而 `singleton` 始终是 2）：

```
=== 2) 注入请求作用域：控制器被传染成请求作用域，每次请求都是新实例 ===
新请求: /scope
[/scope] ScopeController 处理了一次请求
  GET /scope      → {"controller":4,"singleton":2,"transient":5,"transientInProbe":6,"requestScoped":7,"requestLogger":8}
新请求: /scope
[/scope] ScopeController 处理了一次请求
  GET /scope      → {"controller":9,"singleton":2,"transient":10,"transientInProbe":6,"requestScoped":11,"requestLogger":12}
```

`RequestScopedService` 和 `RequestLogger` 都在请求作用域里，所以每个请求都重新构造一次——那两行 `新请求: /scope` 就是 `RequestLogger` 的构造函数打的。顺带看两组瞬态：`transient`（控制器直接注入的）两次请求换了号，`transientInProbe`（`TransientProbe` 里那份）两次都是 6，但每个请求内它和 `transient` 又不是同一个实例——这正是 `TRANSIENT`「每次注入新建」的含义。

## 循环依赖

### 什么是循环依赖

> 示意片段（无配套脚本）

```typescript
// user.service.ts
@Injectable()
export class UserService {
    constructor(private readonly orderService: OrderService) {}
}

// order.service.ts
@Injectable()
export class OrderService {
    constructor(private readonly userService: UserService) {}
}
```

`UserService` 依赖 `OrderService`，`OrderService` 又依赖 `UserService`，形成循环。真实项目里两个类分处两个文件、各自 `import` 对方，就是上面这个样子；下面是配套脚本里同一件事的可运行版本（两个类挤在一个文件里，所以参数类型换成了接口，原因见块内注释）。

### 使用 forwardRef 解决

> 摘自 `./code/advanced-lab/src/02-scope-and-circular.ts`（运行：`npm run 02scope`）

```typescript
// ====== 3) 循环依赖：用 forwardRef 打破 ======
//
// 注意这里的参数类型写成了接口（IUser / IOrder）而不是类本身。
// 原因：这一对类在同一个文件里互相引用，而 @Injectable() 会生成 design:paramtypes 元数据，
// 元数据在类定义时就要**求值**——后声明的那个类此时还在 TDZ 里，会直接报
// ReferenceError: Cannot access 'OrderService' before initialization。
// 真实项目里两个类分处两个文件（各自 import 对方），不会踩到这个问题，直接写
// `private readonly orderService: OrderService` 即可；@Inject(forwardRef(...)) 提供的
// token 才是真正决定注入谁的东西。
export interface IUser {
    readonly peer: IOrder
}

export interface IOrder {
    readonly peer: IUser
}

@Injectable()
export class UserService implements IUser {
    constructor(
        @Inject(forwardRef(() => OrderService))
        private readonly orderService: IOrder
    ) {}

    get peer(): IOrder {
        return this.orderService
    }
}

@Injectable()
export class OrderService implements IOrder {
    constructor(
        @Inject(forwardRef(() => UserService))
        private readonly userService: IUser
    ) {}

    get peer(): IUser {
        return this.userService
    }
}
```

`forwardRef` 用回调把类的求值推迟到注入那一刻，两侧都写，环就破了；`peer` 只是把注入进来的对方暴露出去，好让脚本能互相验证。

### 模块间循环依赖

> 摘自 `./code/advanced-lab/src/02-scope-and-circular.ts`（运行：`npm run 02scope`）

```typescript
// ====== 4) 模块间循环依赖：同样用 forwardRef ======
@Module({
    imports: [forwardRef(() => OrdersModule)],
    providers: [UserService],
    exports: [UserService]
})
export class UsersModule {}

@Module({
    imports: [forwardRef(() => UsersModule)],
    providers: [OrderService],
    exports: [OrderService]
})
export class OrdersModule {}
```

实测输出（`npm run 02scope` 第 4 段；服务间那对 `forwardRef` 与模块间这对同时生效，`CycleController` 直接从容器里取两个 Service 来对号）：

```
=== 4) 服务间循环依赖（forwardRef）：两边互相拿到对方，环是闭的 ===
  GET /cycle      → {"userService":19,"userServiceSees":20,"orderService":20,"orderServiceSees":19,"cycleClosed":true}
```

`userService` 是 19、`orderService` 是 20，而 `userServiceSees` = 20、`orderServiceSees` = 19——各自注入进来的正好是对方那个实例，`cycleClosed` 为 `true`，环确实闭着。模块间的 `forwardRef` 不产生新实例，它只负责让两个模块的导入关系能解析下去。

## 请求作用域的性能影响

使用 `Scope.REQUEST` 需要注意：

> 摘自 `./code/advanced-lab/src/02-scope-and-circular.ts`（运行：`npm run 02scope`）

```typescript
// ====== 5) 请求作用域会沿依赖链向上传染 ======
// 如果 A 是单例，但注入了 B（请求作用域）
// 那么 A 实际上也会变成请求作用域
// 这会级联影响所有依赖链上的 Provider
@Injectable() // 原本是单例
export class ReportService {
    constructor(
        private readonly requestLogger: RequestLogger // 请求作用域
    ) {}

    get logger(): RequestLogger {
        return this.requestLogger
    }
}
```

实测输出（`npm run 02scope` 第 3 段；`ReportService` 声明上没有任何 `scope`，但两次请求的编号全在换）：

```
=== 3) 单例 ReportService 注入了请求作用域的 RequestLogger ===
新请求: /cascade
  GET /cascade    → {"controller":13,"reportService":14,"requestLogger":15}
新请求: /cascade
  GET /cascade    → {"controller":16,"reportService":17,"requestLogger":18}
```

`ReportService` 一个字没改，只因为构造函数的参数是请求作用域的 `RequestLogger`，它自己就跟着每次请求重建了——这就是「传染」。

**性能影响**：

- 请求作用域 = 每次请求创建新实例
- 创建实例需要时间，影响响应速度
- 频繁创建实例增加 GC 压力

**建议**：尽量使用单例，只在必要时使用请求作用域。
