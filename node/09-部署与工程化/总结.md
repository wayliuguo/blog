### 部署与工程化 01-环境管理与配置

- **部署的本质**：同一份代码跑出不同行为——本地连本地库、生产连云库，差异全靠一组可替换的环境变量。
- **process.env 的四个问题**：类型全是 string、默认值要手写、访问散落各处、Node 不会自动读 .env（得靠 dotenv）。
- **泛型不转型**：`get<number>('DB_PORT')` 的 `<T>` 只是告诉 TypeScript 你期望什么类型，运行时不做转换。
- **多环境加载链**：`envFilePath` 数组越靠前优先级越高；顺序是 `process.env` > `.env.local` > `.env.<环境>` > `.env.example` > `.env`。
- **容器/CI 兜底**：环境变量已由容器或 CI 注入时应当跳过 dotenv 加载，否则 `.env` 的旧值会覆盖真实注入值。
- **registerAs 命名空间**：`ConfigType<typeof AppConfig>` 从工厂返回值推断类型，配合 `{ infer: true }` 才拿到真 number。
- **env / envNumber / envBoolean**：约 30 行的读取工具，自带转换与默认值；envNumber 遇非法值立刻 throw。
- **启动校验**：密钥缺失或等于占位符默认值就直接抛错——宁可启动失败，不可带病运行。
- **敏感信息兜底**：扫 `.env.example` 生成 `types/env.d.ts` 让 `process.env` 有补全；`.env*` 全进 `.gitignore`。

### 部署与工程化 02-日志体系

- **console.log 的四个硬伤**：没有级别、没有时间戳、不落文件（重启即丢）、同步写 stdout 拖慢高并发请求。
- **Winston 三概念**：level（级别）、format（格式）、transport（输出目的地），缺一个都构不成生产日志。
- **日志级别数值**：error 0 / warn 1 / info 2 / debug 3 / verbose 4，数字越小越严重，生产默认停在 info。
- **结构化 JSON**：`format.json()` 让日志能被采集工具解析，也才能配合 `jq` 做二次分析。
- **双写架构**：`LoggerService` 继承 `ConsoleLogger` 保留框架原生输出，同时由 Winston 写文件，业务代码零改动。
- **按日轮转**：`DailyRotateFile` + `datePattern: 'YYYY-MM-DD'` + `maxFiles`（默认 31 天），单文件不会无限膨胀。
- **错误日志独立文件**：`app-error.%DATE%.log` 只收 error，排障时不必在全量日志里 grep。
- **auditFile**：记录轮转状态，容器重启后不会重复处理旧文件。
- **trace ID 串联**：借异步上下文给每个请求分配 ID 并附到每条日志，按 ID 一搜就还原完整调用链。
- **三层查看方式**：`docker logs -f`（实时）、容器内 `logs/app.*.log`（历史、可过滤）、`pm2 logs`（进程问题），各有场景。

### 部署与工程化 03-PM2 进程管理

- **裸跑四宗罪**：终端绑定（SSH 断开即死）、崩溃即停、默认只吃一核、日志无管理。
- **常用命令**：`pm2 list` / `logs` / `restart` / `reload` / `stop` / `delete` / `monit` / `describe` / `flush`。
- **开机自启组合拳**：`pm2 startup` 生成自启脚本 + `pm2 save` 保存进程列表，系统重启后自动拉起全部应用。
- **max_memory_restart**：内存超限自动重启，防止内存泄漏把整台机器拖垮。
- **ecosystem.config.js**：把命令行参数变成可版本化、可复用的声明式配置，`env_production` 还能区分环境。
- **fork vs cluster**：fork 单进程（Windows / Docker / 不需要负载均衡），cluster 多进程（Linux 裸机多核、无编排平台）。
- **Docker 里用 fork**：水平扩展交给编排平台多副本，容器内再 cluster 只会造成资源浪费与信号混乱。
- **reload 只对 cluster 有意义**：它靠逐个重启 worker 实现零停机，fork 单进程无 worker 可换。
- **架构演进主线**：裸机自己管进程 → 容器编排管副本 → 平台管一切；PM2 从"负载均衡器"退化为"容器内进程管家"。

### 部署与工程化 04-Docker 容器化

- **要解决的问题**："在我机器上是好的"——把应用和它的运行环境一起打包，一次构建到处运行。
- **镜像 vs 容器 vs 仓库**：镜像是只读模板（类），容器是运行实例（对象），仓库负责存储分发；镜像按指令分层，层不变就复用缓存。
- **单阶段 Dockerfile 的三个问题**：带源码和 devDependencies（约 1GB、攻击面大）、装全量依赖慢、没有健康检查。
- **多阶段构建**：构建用的环境不进运行镜像，最终只 `COPY` dist 与 node_modules，体积从约 1GB 降到约 200MB。
- **层缓存顺序与锁文件**：先 `COPY package*.json` 再装依赖，描述文件不变就命中缓存；`--frozen-lockfile` 保证各环境依赖一致。
- **deps → build → prod-deps → runtime**：四阶段分工，runtime 从 deps 继承系统工具、从 prod-deps 取依赖、从 build 取产物。
- **固定版本与 cache mount**：基础镜像写死 `node:20.16.0-alpine` 保证构建可复现；`--mount=type=cache` 让依赖缓存不进镜像层却能复用。
- **非 root 与最小权限**：`USER node` 运行，`chown` 只授权 logs 与 dist，不遍历 node_modules 以免拖慢构建。
- **端点级 HEALTHCHECK 与 ENTRYPOINT**：探 `/api/health` 而不是探端口；entrypoint 用 exec 形式才能成为 PID 1、收到 SIGTERM 优雅关闭。
- **特殊依赖独立阶段**：Playwright 浏览器拆成独立阶段 + cache mount，锁文件不变就跳过整个下载。

### 部署与工程化 05-Docker Compose 编排

- **docker run 的混乱**：参数记不住、网络手动 link、重启要重新组织命令、无法版本化。
- **一个文件声明全栈**：app + mysql + redis 用一份 YAML 描述，`up -d` 一条命令全部拉起。
- **服务名互访**：Compose 自动建网络并做 DNS 解析，容器间直接用服务名当主机名，这是与 docker run 的本质区别。
- **命名卷持久化**：`volumes: mysql_data:/var/lib/mysql`，容器删了数据还在。
- **生产堆栈分离**：`infra.prod.yml` 管 MySQL/Redis（一次性启动）、`prod.yml` 管迁移与应用（日常更新）。
- **为什么要拆**：数据库几年不动、应用天天更新，生命周期不同；拆开后切换自建/云 RDS 只需改 env，不动编排文件。
- **depends_on 的 condition**：`service_completed_successfully` 等迁移 Job 成功完成才启动应用，比默认"只等容器启动"严格。
- **同镜像不同入口**：迁移 Job 与业务容器共用镜像，只靠 `entrypoint` 覆盖区分，`restart: 'no'` 让一次性任务失败就失败。
- **端口只绑 127.0.0.1 与跨宿主机访问**：应用端口不暴露公网、对外只留 Nginx；容器访问宿主机靠 `host.docker.internal` + `extra_hosts`。
- **三种部署场景**：全 Docker（先 infra 再应用）、混合（infra 注释掉 mysql，DB_HOST 填云地址）、全云（只用 prod）。

### 部署与工程化 06-Nginx 反向代理与网关

- **正向 vs 反向代理**：正向代理代理客户端去访问外部，反向代理代理服务端接收请求，后端说的"加一层"基本都是后者。
- **不设入口的四个问题**：没有域名路由、无法多服务共享 80/443、没有 SSL、没有负载均衡。
- **基本转发三件套**：`proxy_pass` 指向后端，配合 `Host` / `X-Real-IP` / `X-Forwarded-For` 三个头。
- **真实 IP 的坑**：装了代理后应用日志与限流看到的是代理 IP，必须在应用层解析 `X-Forwarded-For`。
- **WebSocket 代理**：`Upgrade` + `Connection: upgrade` + `proxy_http_version 1.1` + 300s 读写超时，缺一条就握手失败。
- **静态资源处理**：`try_files $uri $uri/ /index.html` 支撑前端 History 模式回退，Gzip 压 `gzip_types` 指定的文本类 MIME。
- **负载均衡策略**：默认轮询、`least_conn` 分给连接最少的实例、`ip_hash` 把同一 IP 固定到同一实例（需要 Session 时）。
- **各组件职责**：Nginx 负责入口与 SSL 终结，PM2 负责进程，Docker 负责隔离与编排，MySQL/Redis 负责数据。
- **三种部署架构**：纯 Docker、PM2 + Nginx 传统部署、Docker 容器内 PM2；演进主线是 Nginx 始终是唯一入口。

### 部署与工程化 07-数据库迁移与发布

- **为什么改表要成体系**：开发时改 Entity 重启即同步很爽，生产表里全是真数据，任何结构变更都可能丢数据、锁表、不可回滚。
- **synchronize 是定时炸弹**：不可审计、不可回滚、删字段即永久丢数据、无法 Code Review、还让 `migration:generate` 比对不出差异。
- **migrations 表与执行流程**：建表 → 读 `dist/migrations/*.js` → 对比已执行记录 → 按时间戳顺序跑 up() → 逐个记录，表里存 id / timestamp / name。
- **幂等性**：已执行的迁移不会重复运行，没有新迁移时输出 `"No migrations are pending"` 直接退出。
- **事务保护**：up() / down() 默认包在事务里，失败整体回滚；但已成功的迁移不会自动回滚，撤销要显式 `migration:revert`。
- **三个 DataSource**：Local（.env.development + TS 源码）、CLI（注入变量 + dist 产物）、Runtime（走 DI 容器）分工不同。
- **迁移 CLI 不依赖 NestJS**：直接 `node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`，应用有 bug 也能迁移。
- **开发新流程**：改 Entity → `migration:dev:generate` → `migration:dev:run` → 启动 dev 应用连已迁移的库。
- **迁移做成独立 Job**：多实例若各自跑迁移会并发锁冲突、产生脏数据，且新迁移出问题会阻塞在服务的容器。
- **首次与后续部署**：空库时 migrations 表自动创建并全量执行；已有数据时只跑新增迁移，已有数据不受触碰。安全迁移可进 CI 自动跑，删除/重命名的破坏性迁移必须人工确认。
### 部署与工程化 08-生产部署实战

- **统一部署模式**：MySQL 与 Redis 永远是外部服务，compose 堆栈只管理 migration + app。
- **三条设计原则**：数据库独立于应用栈、迁移与业务分离、端口只绑 `127.0.0.1`。
- **首次部署四步**：准备 `.env.production` → 启动 infra → `up -d --build` 起应用 → 接入 Nginx。
- **一条命令背后发生的事**：构建镜像 → 迁移容器等 MySQL 并跑迁移 → 应用等迁移成功再启动 → HEALTHCHECK 探测 → curl 验证。
- **日常迭代**：`git pull` + `up -d --build`，Compose 先起新容器、健康检查通过再停旧容器，单机下近似滚动更新。
- **数据持久化位置**：MySQL、Redis 落宿主机目录，应用日志落命名卷，容器重建都不丢。
- **备份与恢复**：`mysqldump` 导出、`mysql < backup.sql` 导入；自建库靠宿主机目录 + 定时全量备份，云库由云方提供。
- **排障五问**：容器活着吗 → 健康吗 → 应用日志说什么 → 是不是数据库问题 → 是不是被重启过。
- **容器反复重启的常见原因**：数据库未就绪、环境变量缺失导致启动校验抛错、端口冲突。
- **部署检查清单**：镜像构建成功、迁移无 ERROR、`State.Health.Status` 健康、本地接口可访问、日志正常写入、外部入口可达。

### 部署与工程化 09-CI/CD 自动化部署

- **手动部署的四个问题**：易漏步骤、构建吃服务器资源、无法快速回滚、多人发版不可控。
- **核心区别**：构建从服务器挪到云端 CI，服务器只做拉新镜像、重启容器这一件事。
- **workflow 三概念**：触发条件（on）、任务（jobs）、步骤（steps）。
- **推荐双流水线**：build 负责构建推送，deploy 等 build 成功后再 SSH 部署；构建失败就不会触发部署，deploy 还能多机复用。
- **流水线一**：`on: push: tags: ['v*']` 触发，登录仓库后构建并推 `stable` 与 `v1.0.0` 两个 tag。
- **流水线二**：`workflow_run` 监听构建完成，且 `conclusion == 'success'` 才执行 SSH 部署。
- **pull 替代 --build**：服务器只 `docker compose pull` + `up -d`，不本地构建，压力大幅下降。
- **Secrets 管理**：镜像账号、镜像名、服务器地址与 SSH 私钥全放仓库 Secrets，并为流水线单独生成密钥对。
- **迁移进流水线**：安全迁移（新增表/字段/索引）自动执行，破坏性迁移（删除/重命名）必须人工确认后手动跑。
- **回滚就是再发一次旧 tag**：拉旧版本镜像重新部署，秒级完成。

### 脚手架开发 01-脚手架开发入门

- **脚手架是什么**：自动化创建项目的工具，用户命令行交互选配置后自动生成模板，如 `create-react-app`、`nest new`。
- **核心流程**：用户输入命令 → 交互式问答 → 按选择复制模板文件 → 替换模板中的变量 → 输出项目。
- **入口文件约定**：`bin/index.js` 首行 `#!/usr/bin/env node`，在 package.json 的 `bin` 字段里映射成全局命令名。
- **两个依赖分工**：inquirer 负责交互问答，fs-extra 负责目录复制（比原生 fs 多了目录递归与覆盖便利）。
- **变量替换**：复制完模板后读文件，用 `replace(/{{projectName}}/g, ...)` 把占位符换成真实项目名。
- **yargs 参数解析**：用 `command('create <name>')` 定义子命令与 positional，`option` 定义 `--template` 之类的可选参数，`.help()` 自动生成帮助。

### 进阶主题 01-消息队列

- **什么是消息队列**：生产者发消息到队列、消费者从队列取消息的异步通信机制。
- **同步 vs 异步**：同步是下单后等扣库存、发短信、发邮件、算积分全部完成；异步只让用户等下单，其余由队列驱动。
- **三大作用**：异步处理（非核心操作异步执行）、削峰填谷（高峰缓冲）、解耦（生产者与消费者互不直接依赖）。
- **Kafka 角色**：Producer 发、Consumer 收、Topic 是消息分类（类似表）、Partition 是分区（实现并行）。
- **选型对比**：Kafka 吞吐百万级/秒、学习成本高，适合日志与流处理；RabbitMQ 万级、适合业务系统与任务分发；Redis Stream 轻量、适合简单消息。

### 进阶主题 02-性能优化

- **缓存穿透**：查不存在的数据每次都打到库；对策是缓存空值或上布隆过滤器。
- **缓存击穿**：热点 key 过期瞬间大量请求涌向数据库；对策是互斥锁或热点数据永不过期。
- **缓存雪崩**：大量 key 同时过期把数据库压垮；对策是过期时间加随机值、多级缓存。
- **限流四算法**：计数器（简单但有突刺）、滑动窗口（平滑）、令牌桶（允许突发）、漏桶（平滑且不允许突发）。
- **NestJS 限流落地**：`ThrottlerModule.forRoot({ ttl, limit })` 定全局窗口，`@Throttle(5, 60000)` 按接口覆盖。
- **数据库优化五手段**：索引优化、慢查询日志 + EXPLAIN、连接池复用、读写分离、分库分表。

### 进阶主题 03-安全

- **XSS**：往页面注入恶意脚本，靠模板引擎与前端框架的默认 HTML 转义防御。
- **CSRF**：诱导用户在不知情下执行操作，靠 CSRF Token 防御。
- **SQL 注入**：字符串拼接 SQL 就是注入入口，必须用参数化查询（`?` 占位）让驱动做转义。
- **Helmet**：一个 `app.use(helmet())` 批量设置安全响应头，成本极低收益高。
- **CORS**：开发可放开，生产必须用 `origin` 白名单；带 Cookie 时 `credentials` 与前端 `withCredentials` 要成对配。
- **参数校验**：永远不信任用户输入，`ValidationPipe` 开 `whitelist + forbidNonWhitelisted` 只放行 DTO 声明过的字段。

### 进阶主题 04-测试

- **测试金字塔**：单元测试最多最快、覆盖单个函数；集成测试居中；E2E 最少最慢、覆盖完整请求链路。
- **NestJS 单元测试**：`Test.createTestingModule({ providers: [...] })` 编译后 `module.get()` 取出待测服务。
- **集成测试**：`imports: [AppModule]` 编译出完整应用，`createNestApplication()` + `app.init()` 后用 supertest 打真实 HTTP。
- **三种替身**：Mock 模拟整个对象、Stub 替换方法返回值、Spy 只监控调用情况（`jest.spyOn` 后断言 `toHaveBeenCalledWith`）。

### 进阶主题 05-设计模式

- **单例模式**：NestJS 的 Provider 默认就是单例，注入到多少个类里都是同一个实例。
- **策略模式**：把算法抽成可互换的接口实现（如多种登录校验），用 `@Inject('AUTH_STRATEGY')` 在运行时选择。
- **观察者模式**：`EventEmitter2` 的 `emit` 发布、`@OnEvent` 监听就是框架内置的观察者模式，用来做下单后发短信这类副作用。
- **工厂模式**：自定义 Provider 的 `useFactory` 按环境返回不同的数据库连接，就是工厂模式的落点。

### 进阶主题 06-系统设计

- **NestJS 微服务**：`ClientsModule.register` 声明传输方式（TCP / Redis / Kafka / RabbitMQ），`client.send({ cmd }, payload)` 发消息。
- **拆分原则**：按业务拆（用户/订单/商品）、每个服务独立数据库、独立部署扩展；同步用 HTTP/gRPC，异步用消息队列。
- **WebSocket 网关**：`@WebSocketGateway` + `@SubscribeMessage` 处理消息，`server.emit` 广播给所有客户端。
- **高可用五策略**：负载均衡、冗余部署、健康检查自动剔除异常节点、熔断降级、限流。

### 进阶主题 07-Git 与协作

- **三种工作流**：GitHub Flow（main + feature + PR，小团队持续部署）、Git Flow（多出 develop/release，中大型版本发布）、Trunk-Based（短命分支，CI/CD 成熟时用）。
- **合并策略取舍**：merge 保留完整历史但多一个合并提交，rebase 得到线性历史但改写提交，squash 把多个提交压成一个。
- **提交信息规范**：Conventional Commits 的 `<type>(<scope>): <subject>`，用 feat / fix / docs / refactor / test / chore 分类。
- **Code Review**：单次 PR 控制在 200~300 行以内，先看整体逻辑再看细节，指出问题的同时给建议，并检查规范、复杂度、异常处理、安全与测试覆盖。

| --- | --- | --- |
| 本地跑得好、线上就不对 | 配置加载链与启动校验 | 同一份代码行为不同，九成是环境变量没对齐或密钥还是占位符 |
| 排障时找不到一次请求的完整路径 | trace ID | 日志散在多个服务与容器里，只有请求级 ID 能把它们串起来 |

## 易错点汇总

- **"`get<number>()` 会帮我转型"、"容器里也照读 `.env`"**：泛型只是给 TypeScript 看的期望类型，运行时 `'3306'` 仍是字符串；而环境变量已由容器或 CI 注入时再加载 `.env`，文件里的旧值会覆盖真实注入值。
- **"配置类型安全就等于值正确"**：`JWT_SECRET` 被配成 `your-jwt-secret-change-me` 也是合法字符串，类型检查拦不住。必须在配置工厂里做启动校验。
- **"console.log 够用了"**：没有级别、没有时间戳、不落文件，重启即丢，而且同步写 stdout 在高并发下会拖慢请求。生产必须交给日志库并落文件。
- **"PM2 的日志能当历史日志查"**：PM2 日志是内存缓冲，容器一重启就没了。历史排障要看 `logs/app.*.log` 文件日志。
- **"fork 和 cluster 随便选，`pm2 reload` 通用"**：Docker 容器内该用 fork 单实例，水平扩展交给编排平台；reload 靠逐个重启 worker 实现零停机，fork 模式没有意义。
- **"单阶段 Dockerfile 够用"**：它会把源码和 devDependencies 一起打进镜像，体积约 1GB 且攻击面大。多阶段构建后只留产物，降到约 200MB。
- **"写了 `depends_on` 就保证启动顺序"**：默认的 depends_on 只等容器启动、不等服务就绪。要"迁移跑完再起应用"必须配 `condition: service_completed_successfully`。
- **"容器起来了就算部署成功"**：健康检查要打到应用端点而不是端口；一次部署还要确认镜像 tag、迁移无 ERROR、日志正常写入、外部入口可达。
- **"`synchronize: true` 方便，生产也留着"**：Entity 删一个字段重启就真删列，数据永久丢失，变更还无法审查、无法回滚。
- **"迁移和业务容器一起跑没关系"、"破坏性迁移也让 CI 自动执行"**：多实例各跑迁移会并发锁冲突、产生脏数据，迁移应做成独立一次性 Job；而 `DROP` / 重命名不可逆，必须人工确认后再执行。
- **"缓存和限流对策可以随便选"、"SQL 拼接只是风格问题"**：穿透、击穿、雪崩要分别用布隆过滤器、互斥锁、随机过期时间；令牌桶允许突发而漏桶不允许；字符串拼 SQL 就是注入入口，必须参数化查询并配 `ValidationPipe` 白名单。
