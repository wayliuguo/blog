## 分篇知识点

### 部署与工程化 01-环境管理与配置

- **为什么部署从配置开始**
  - **部署的本质**：同一份代码跑出不同行为——本地连本地库、生产连云库，差异全靠一组可替换的环境变量
  - **渐进四步**：`.env` + `@nestjs/config` 先跑起来 → 按环境拆文件 → `registerAs` 类型安全 → 启动校验与敏感信息兜底
- **`process.env` 裸用的四个问题**
  1. **类型全是 `string`**：端口、数字配置无法自动转型，得手动 `Number()`
  2. **默认值全靠手写**：每次都要 `process.env.X || 'default'`
  3. **访问散落各处**：改个变量名要全局搜索替换
  4. **`.env` 文件不生效**：Node 不会自动读 `.env` 文件，得装 `dotenv` 手动加载
- **`ConfigService.get()` 的类型只是"声明"**
  - **泛型不转型**：`get<number>('DB_PORT')` 的 `<T>` 只告诉 TypeScript 你期望什么类型，运行时不做任何转换
  - **`infer: true` 才有精确推导**：`get('app.port')` 拿到 `any`，`get('app.port', { infer: true })` 才拿到 `number`
- **多环境加载链与优先级**
  - **`envFilePath` 数组越靠前优先级越高**：`process.env` > `.env.local` > `.env.<环境>` > `.env.example` > `.env`，符合 12-Factor App 的"配置与代码严格分离"
  - **容器/CI 兜底**：环境变量已由容器或 CI 注入时（以 `DB_HOST` 判断）应跳过 dotenv 加载，否则 `.env` 的旧值会覆盖真实注入值
- **`registerAs` 命名空间与类型推断**
  - **`ConfigType<typeof AppConfig>`**：从工厂返回值推断配置类型，无需手写 `interface`
  - **聚合与批量加载**：`src/config/index.ts` 汇总所有命名空间，`load: [...Object.values(configs)]` 一次注册
  - **`ConfigKeyPaths`**：把嵌套配置展平成点号路径联合，`app.logger.level` 这类深层 key 也有精确类型
- **类型安全的读取工具 `env` / `envNumber` / `envBoolean`**
  - 约 30 行的全局工具，让读取自带转换与默认值；`envNumber` 遇非法值立刻 `throw`，避免带病启动
- **启动校验：宁可启动失败，不可带病运行**
  - 密钥缺失或等于占位符默认值（如 `'your-jwt-secret-change-me'`）就直接抛错；`ADMIN_USERNAME` / `ADMIN_PASSWORD` 同理必填
- **敏感信息与构建产物兜底**
  - **构建产物带类型**：扫 `.env.example` 生成 `types/env.d.ts`，让 `process.env.XXX` 编辑期有补全、拼错变量名编译期报错
  - **`.gitignore` 兜底**：`.env*` 全进忽略清单、只放行 `*.env.example`——密钥一旦进 git 历史就永久留存


### 部署与工程化 02-日志体系

- **日志为什么是生产刚需**
  - 线上出问题时**代码无法重新执行，但日志可以复盘**；日志体系的差距，决定排障是"半小时"还是"一下午"
- **`console.log` 的四个硬伤**
  1. **没有日志级别**：无法区分 debug / info / error，排查时被海量日志淹没
  2. **没有时间戳**：无法定位"什么时候发生"
  3. **不支持输出到文件**：容器/服务器重启日志即丢，无法复盘
  4. **性能差**：同步写 stdout，高并发下拖慢请求
- **Winston 的三个核心概念**
  - **`level` / `format` / `transport`**：级别、格式、输出目的地，缺一个都构不成生产日志
  - **数字越小越严重**：`error` 0 / `warn` 1 / `info` 2 / `debug` 3 / `verbose` 4；生产默认停在 `info`，把 `debug` 留给开发——不是不记，而是分轻重
  - **结构化 JSON**：`format.json()` 让日志能被采集工具解析，也才能配合 `jq` 做二次分析
- **双写架构：控制台给开发、文件给生产**
  - `LoggerService` **继承 `ConsoleLogger`** 保留框架原生输出，同时由 Winston 写文件；调用方仍是 `this.logger.log('xxx')`，业务代码零改动
  - 链路是控制台 → stdout → PM2 捕获 → `docker logs`
  - **全局注册**：`LoggerModule.forRoot()` 声明 `global: true`；`main.ts` 里配合 `bufferLogs: true` 与 `app.useLogger()`，NestJS 内部日志才会一并走自定义 Logger
- **按日轮转与错误分离**
  - **`DailyRotateFile` + `datePattern: 'YYYY-MM-DD'` + `maxFiles`（默认 31 天）**：单文件不会无限膨胀，按日期归档好查询
  - **`app-error.%DATE%.log` 独立错误文件**：只收 `error`，排障时不必在全量日志里 `grep`
  - **`auditFile`**：记录轮转状态，容器重启后不会重复处理旧文件
  - **磁盘预算**：JSON 日志正常请求量每天约 10-50MB，保留 31 天建议预留 2GB 以上；日志量异常增长优先检查 `LOGGER_LEVEL`
- **日志级别与保留天数走配置中心**
  - 不硬编码：`LOGGER_LEVEL=info` / `LOGGER_MAX_FILES=31` 经 `app.logger.level`、`app.logger.maxFiles` 读取
- **trace ID 串联整条调用链**
  - 借 `nestjs-cls` 异步上下文给每个请求分配 ID，并以 `[${traceId}] ${message}` 附到每条日志；按 ID 一搜，一次请求从入口到数据库的完整路径都在
- **三层日志查看方式**
  1. **`docker logs -f <container>`**：快速排查、启动日志、实时监控
  2. **容器内文件 `logs/app.*.log`**：历史日志、按级别过滤、重启后仍可查
  3. **`pm2 logs`**：PM2 进程管理问题（重启、内存告警）


### 部署与工程化 03-PM2 进程管理

- **裸跑的四个致命问题（PM2 的守护进程化、自动重启、集群模式、日志收集正对应它们）**
  1. **终端绑定**：关闭终端或 SSH 断开，进程即死
  2. **崩溃即停**：未捕获异常直接退出，无人拉起
  3. **单线程浪费**：现代 CPU 多核，Node 默认只用一核
  4. **无日志管理**：输出散落在终端，重启即丢
- **常用命令与开机自启**
  - **日常操作**：`pm2 start` / `list` / `logs` / `restart` / `stop` / `delete` / `monit` / `describe` / `flush`
  - **开机自启组合拳**：`pm2 startup` 生成自启脚本 + `pm2 save` 保存进程列表，系统重启后自动拉起全部应用
- **`ecosystem.config.js`：把命令行参数变成声明式配置**
  - 让配置**可版本化、可复用**；`env` 注入环境变量，`env_production` 还能区分环境
  - **`autorestart`**：进程崩溃自动重启
  - **`max_memory_restart`**：内存超限自动重启（命令行写法 `--max-memory-restart 500M`，配置里写 `'1G'`），防止内存泄漏拖垮整台机器
  - **`watch`**：文件变化自动重启，仅开发用
- **fork 与 cluster 的取舍**
  1. **fork**：单进程、父子进程模式，适合 Windows、Docker 容器、不需要负载均衡的场景
  2. **cluster**：多进程，Node 原生 cluster + 轮询负载均衡，适合 Linux/macOS 裸机、无容器编排平台；`-i max`（或 `instances: 'max'`）让进程数等于 CPU 核数
- **`pm2 reload` 为什么只在 cluster 下有意义**
  - 它靠**逐个重启 worker** 实现零停机；fork 是单进程，没有 worker 可换，也就没有 reload 的必要
- **Docker 里为什么用 fork 而不是 cluster**
  - 水平扩展交给编排平台（Docker Compose 多副本 / K8s），容器内再开 N 个进程只会造成**资源浪费与信号混乱**
  - PM2 在容器里保留 fork，只为三件事：日志管理、进程监控、内存限制重启
- **三层部署架构的演进**
  1. **裸机**：用户 → Nginx(80/443) → PM2 cluster（多个 worker）→ DB
  2. **Docker**：用户 → Nginx → Docker 容器（PM2 fork 单进程）× N 副本 → DB
  3. **K8s**：用户 → Ingress → Pod（容器内 fork）→ DB
  - 主线：**裸机自己管进程 → 容器编排管副本 → 平台管一切**；PM2 从"负载均衡器"逐步退化为"容器内的进程管家"
- **与日志体系的衔接**
  - PM2 捕获应用 stdout，正是"控制台 → PM2 捕获 → `docker logs`"这条链路的中段（`pm2 logs my-app --lines 100 --nostream`、`pm2 flush`）
  - **PM2 日志是内存缓冲、不持久化**，容器重启即丢；要查历史日志必须看文件日志 `logs/app.*.log`


### 部署与工程化 04-Docker 容器化

- **Docker 要解决的问题**
  - "在我机器上是好的"：把应用和它的运行环境一起打包，实现**一次构建，到处运行**
- **镜像 / 容器 / 仓库的心智模型**
  - **镜像**是只读模板（类比类 / 光盘），**容器**是镜像的运行实例（类比实例 / 光驱），**仓库**负责存储分发（如 Docker Hub）
  - **分层缓存**：每条指令生成一个只读层，层不变就复用缓存——所以指令顺序直接影响构建速度
- **单阶段 Dockerfile 的三个问题**
  - 镜像里带着源码和 devDependencies（约 1GB、攻击面大）、`npm install` 装全量依赖导致构建慢、没有健康检查（容器"起来了"但应用没就绪）
- **多阶段构建为什么能瘦身**
  - 核心思想：**构建用的环境不进运行镜像**；runtime 只用 `COPY --from=builder` 拿 `dist` 与 `node_modules`，体积从约 1GB 降到约 200MB，攻击面同步减小
  - 其他手段：选 Alpine 基础镜像（约 120MB vs Ubuntu 约 1GB）、`.dockerignore` 给构建上下文瘦身、合并 `RUN` 减少层数（`npm ci --only=production && npm cache clean --force`）
- **层缓存顺序与锁文件**
  - 先 `COPY package*.json` 再装依赖：**依赖描述文件不变 → 缓存命中 → 跳过整段安装**
  - **`--frozen-lockfile`**：严格按 lockfile 安装，所有环境依赖版本一致
  - **`--prod`**：只装 `dependencies`，跳过 TypeScript / ESLint / Jest 等 devDependencies
- **四阶段分工：deps → build → prod-deps → runtime**
  - **deps**：装好 pnpm、pm2、时区工具等系统依赖，供后续阶段继承
  - **build**：装全量依赖并 `nest build` 出 `dist`
  - **prod-deps**：只装生产依赖，不含 devDependencies
  - **runtime**：从 deps 继承系统工具、从 prod-deps 取依赖、从 build 取产物
- **可复现构建与 cache mount**
  - 基础镜像写死 `node:20.16.0-alpine` 而非 `node:20-alpine`，保证今天构建和半年后构建结果一致
  - **`--mount=type=cache`**：依赖缓存挂载为构建缓存，不落入镜像层却能被后续构建复用
  - **`ARG TZ=Asia/Shanghai`** 设置时区，日志时间戳与定时任务才正确
- **安全、健康检查与元数据**
  - **非 root 与最小权限**：`USER node` 运行，`chown` 只授权 `logs` 与 `dist`（不遍历 `node_modules`，构建不拖慢）
  - **端点级 HEALTHCHECK**：`wget --spider http://localhost:$APP_PORT/api/health`，验证应用真正就绪，而非仅仅端口在监听
  - **`ARG` + `LABEL`**：版本号与构建时间写入镜像元数据，`docker inspect` 可溯源
  - **`ENTRYPOINT` 用 exec 形式**：entrypoint 成为 PID 1，才能正确接收 SIGTERM 实现优雅关闭
- **特殊依赖独立阶段**
  - Playwright 浏览器下载 184MB：装进 build 阶段白装、装进 runtime 每次重下
  - 拆成独立阶段 + `cache mount`（`PLAYWRIGHT_DOWNLOAD_HOST` 走 npmmirror 加速）：浏览器缓存可复用、runtime 只复制一次、锁文件不变就跳过整个下载


### 部署与工程化 05-Docker Compose 编排

- **Compose 要解决的痛点**
  - `docker run` 一个个起容器要敲几十个参数：**参数记不住、网络手动 `--link`、重启要重新组织命令、无法版本化**
  - Compose 用一份 YAML 声明"这一组服务长什么样"，`docker compose up -d` 一条命令全部拉起
- **一个文件声明全栈**
  - app + mysql + redis 写进同一份 YAML，用 `up -d` / `ps` / `logs -f` / `down` 管理整套服务
  - **服务名互访**：Compose 自动创建网络并做 DNS 解析，容器间直接用服务名（`mysql` / `redis`）当主机名——这是与 `docker run` 的本质区别
- **数据怎么不丢**
  - **命名卷持久化**：`volumes: mysql_data:/var/lib/mysql`，容器删了数据还在
  - **Redis 持久化**：`--appendonly yes --appendfsync everysec` 每秒刷盘，崩溃最多丢 1 秒数据
  - **日志命名卷**：`show-track-logs:/app/logs/` 让日志跨容器生命周期持久化
- **生产堆栈分离**
  - `docker-compose.infra.prod.yml` 管 MySQL + Redis（**一次性启动，之后不管**）；`docker-compose.prod.yml` 管 migration + 应用（日常部署更新）
  - **为什么要拆**：数据库几年不动、应用天天更新，生命周期不同；拆开后数据库可自建 Docker、可上云 RDS、可混合，切换只改 env 不动编排文件
  - **基础设施细节**：`restart: always` 让数据库挂掉自动拉起；`./__data/redis/` 挂到宿主机，容器重建不丢；数据库上云时直接注释掉 mysql 服务
- **迁移 Job：把启动顺序变成硬依赖**
  - **`depends_on: condition: service_completed_successfully`**：应用等迁移 Job **成功完成**才启动，比默认"只等容器启动"严格得多
  - **同镜像不同入口**：迁移与业务共用同一镜像，只靠 `entrypoint` 覆盖区分；`restart: 'no'` 让一次性任务失败就失败，不留死循环重试
- **入口收敛与跨宿主机访问**
  - **`ports: '127.0.0.1:${APP_PORT}:${APP_PORT}'`**：只绑宿主机回环地址、不暴露公网，对外只开 Nginx 一个口
  - **`env_file: .env.production`**：环境变量从文件注入，密钥不进镜像、不进代码
  - **显式命名网络**：`networks: name: show_track_net` 让多个 compose 文件共享同一网络
  - **跨宿主机访问**：`extra_hosts` 配 `host.docker.internal:host-gateway`，`DB_HOST` 填 `host.docker.internal`（自建库）或云 RDS 地址
- **三种部署场景**
  1. **全部 Docker（自建 MySQL + Redis）**：先 `infra.prod.yml` 启动基础设施，再 `prod.yml` 部署应用
  2. **混合（MySQL 上云 + Redis 本地）**：infra 文件注释掉 mysql，`.env` 里 `DB_HOST` 填云地址
  3. **全部云服务**：跳过 infra 文件，`.env` 里全填云地址，只用 `prod.yml`


### 部署与工程化 06-Nginx 反向代理与网关

- **为什么必须有入口网关**
  - 直接把 `3000` 暴露给公网有四个问题：**没有域名路由、无法多服务共享 80/443、没有 SSL、没有负载均衡**
  - 用户只跟 Nginx 打交道，Nginx 把请求分发给背后的服务，并隐藏内部网络结构
- **正向代理 vs 反向代理**
  - **正向代理代理客户端**去访问外部资源（翻墙、公司内网出口）；**反向代理代理服务端**接收请求（网关、负载均衡）——后端语境说的"加一层"基本都是后者
- **基本转发与真实 IP**
  - **转发三件套**：`proxy_pass` 指向后端，配合 `Host $host`（保留原始域名，后端才能正确生成链接）、`X-Real-IP`（客户端真实 IP）、`X-Forwarded-For`（转发链上所有 IP，供日志/风控分析）
  - **真实 IP 的坑**：装了代理后应用日志与限流看到的是代理 IP，必须在应用层解析 `X-Forwarded-For`
- **WebSocket 代理**
  - `proxy_set_header Upgrade $http_upgrade` + `Connection "upgrade"` + `proxy_http_version 1.1` + `proxy_read_timeout 300s`（连同 `proxy_send_timeout 300s`），缺一条前端就握手失败
- **静态资源与 Gzip**
  - **History 模式回退**：`try_files $uri $uri/ /index.html` 让前端路由刷新时也能命中 `index.html`
  - **Gzip**：`gzip on` 配合 `gzip_http_version 1.1`、`gzip_types` 指定的文本类 MIME、`gzip_min_length 1000`、`gzip_comp_level 9`，减小传输体积
- **负载均衡策略（`upstream` 组 + `proxy_pass http://backend/` 转发给整组）**
  1. **默认轮询**：依次分发，权重相同
  2. **`least_conn`**：分给当前连接最少的实例
  3. **`ip_hash`**：同一 IP 固定到同一实例（需要 Session 的场景）
- **各组件职责**
  - **Nginx**：接收请求、SSL 终结、静态文件、反向代理、负载均衡
  - **PM2**：Node 进程管理、故障恢复、内存管理
  - **Docker**：环境隔离、一致性部署、服务编排
  - **MySQL / Redis**：数据持久化 / 缓存
- **三种部署架构**
  1. **纯 Docker 部署**（现代默认）：Nginx、Server、Redis、MySQL 都在同一套 Compose 网络里
  2. **PM2 + Nginx 传统部署**：Nginx(80/443) 反代与负载均衡 → 多个 PM2 cluster 实例 → MySQL / Redis
  3. **Docker + 容器内 PM2**：Nginx 在宿主机做唯一公网入口 → Docker 容器（PM2 fork 管理单进程）× N 副本 → 宿主机 Docker 或云上的 MySQL / Redis
  - 演进主线：**Nginx 始终保持"唯一入口"**；变化的只是背后的 Node 进程由谁管理（裸机 PM2 → 容器 → 编排平台）


### 部署与工程化 07-数据库迁移与发布

- **为什么"改表"要成体系**
  - 开发时改 Entity 重启即同步很爽，但**生产表里全是真数据**，任何结构变更都可能丢数据、锁表、不可回滚——"改表"从开发技能变成发布流程
- **`synchronize` 是定时炸弹（只适合早期原型，进入协作开发就要关掉）**
  1. **不可审计**：谁改了表、什么时候改、改了什么，无从追溯
  2. **不可回滚**：出问题无法撤销，只能手动修
  3. **数据丢失**：Entity 删字段 → 重启 → 列被删 → 数据永久丢失
  4. **不可审查**：变更无法通过 Code Review 检查
  5. **迁移失效**：数据库已和实体同步，`migration:generate` 对比不出差异
- **迁移的执行机制：记录、幂等、事务**
  - **`migrations` 表**：记录已执行的迁移，字段为 `id` / `timestamp` / `name`，不存在时自动创建
  - **`migration:run` 流程**：连接数据库 → 检查 `migrations` 表 → 读 `dist/migrations/*.js` → 对比已执行记录 → 按时间戳顺序执行未跑过的 `up()` → 每个执行完插一条记录
  - **幂等**：已执行的迁移不会重复运行；没有新迁移时输出 `"No migrations are pending"` 直接退出
  - **事务保护**：`up()` / `down()` 默认包在事务里，失败整体回滚，不留半完成的表结构
  - **已成功的迁移不会自动回滚**：要撤销必须显式 `migration:revert`
- **三个 DataSource 的分工**
  - **Local**（`data-source.dev.ts`）：本地开发迁移命令，`dotenv` 读 `.env.development`，吃 `src/**/*.ts` 源码（免 build）
  - **CLI**（`data-source.ts`）：生产迁移命令（Docker / CI），读注入的环境变量，吃 `dist/**/*.js` 编译产物（免 ts-node）
  - **Runtime**（`database.config.ts`）：应用运行时连接，走 `@nestjs/config` 与 DI 容器
  - 三者的 `synchronize` 都建议硬编码或配置为 `false`
- **迁移 CLI 为什么独立于 NestJS**
  - 直接 `node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`，不启动应用
  - **收益**：应用有 bug 也能迁移、不经过 DI 容器所以轻量可独立运行、开发用 TS 源码而生产用编译产物
  - **环境加载沿用同一套思想**：本地读 `.env.<环境>` 文件，容器/CI 已注入（以 `DB_HOST` 判断）则跳过
- **开发期的迁移流程**
  - 改 Entity → `pnpm migration:dev:generate`（对比生成迁移文件）→ `pnpm migration:dev:run`（执行迁移）→ 启动 dev，应用连已迁移的库；生产对应 `migration:prod:run`
- **迁移做成独立 Job**
  - 多实例若各自在启动时跑迁移，会**并发锁冲突、产生脏数据**；新迁移有问题时也不该阻塞已运行的容器继续服务
  - 做法：迁移是**独立的一次性 Job 容器，跑在业务容器之前**——两者各自用 `wait-for-it.sh` 等 MySQL，迁移容器 `restart: 'no'` 执行完退出，业务容器用 `depends_on: condition: service_completed_successfully` 等它成功
- **首次部署与后续部署**
  - **首次（空库）**：`migrations` 表自动创建 → 全部迁移按时间戳执行
  - **后续（已有数据）**：对比发现只有新增迁移 → 只执行新的，已有数据不受影响
  - **无新迁移**：输出 `"No migrations are pending"` 直接跳过
  - **安全保障**：已有数据不会被迁移框架触碰，除非某个 `up()` 显式写了 `DROP` / `DELETE` / `TRUNCATE`
- **安全迁移与破坏性迁移的差别**
  - **安全迁移**（新增表 / 字段 / 索引）可进 CI/CD 流水线自动执行：`docker compose -f docker-compose.prod.yml run --rm --entrypoint "" show-track-server node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`
  - **破坏性迁移**（删除 / 重命名）不可逆，必须人工确认后手动执行


### 部署与工程化 08-生产部署实战

- **统一部署模式与三条设计原则**
  - 核心原则：**MySQL 和 Redis 永远是外部服务，compose 堆栈只管理 migration + app**
  - **数据库独立于应用栈**：生命周期不同；可随时切换自建 / 云 RDS 而不动应用编排
  - **迁移与业务分离**：迁移失败不阻塞已有服务；多实例不并发迁移
  - **端口只绑 `127.0.0.1`**：对外只有 Nginx 一个入口，安全面最小
- **首次部署四步**
  1. **准备环境变量**：`cp .env.example .env.production`，填入数据库密码、JWT 密钥、域名等真实值（`.env.production` 不提交，密钥必须强随机）
  2. **启动基础设施**：`docker compose -f docker-compose.infra.prod.yml --env-file .env.production up -d`，之后靠 `restart: always` 与宿主机卷自管
  3. **构建并启动应用**：`docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build`
  4. **接入 Nginx**：写 `/etc/nginx/conf.d/my-app.conf`，`proxy_pass http://127.0.0.1:3000/` 指向容器映射的宿主机端口，公网请求全部走 Nginx
- **一条 `up -d --build` 背后发生的事**
  1. `build`：五阶段 Dockerfile 构建镜像（缓存复用）
  2. `migration` 容器启动：`wait-for-it` 等 MySQL → `migration:run`
  3. `app` 容器启动（等迁移成功）→ 容器内 PM2 fork 拉起 NestJS
  4. `HEALTHCHECK` 周期探测 `/api/health`
  5. 验证：`curl http://your-server:3000/api/health`
- **日常迭代与近似滚动更新**
  - `git pull` + `docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build`
  - Compose 先启动新容器，**健康检查通过后再停旧容器**——单机环境下的"滚动更新"，服务基本不中断
- **数据持久化位置**
  - MySQL 落 `./__data/mysql/`、Redis 落 `./__data/redis/`（宿主机目录），应用日志落命名卷 `show-track-logs`，**容器重建都不丢**
- **备份与恢复**
  - 备份：`docker exec <mysql-container> mysqldump -uroot -p <db> > backup.sql`；恢复：`docker exec -i <mysql-container> mysql -uroot -p <db> < backup.sql`
  - 云数据库的备份由云服务方提供，自建 Docker 库靠宿主机目录 + 定时 `mysqldump`；**生产建议至少每日全量备份**
- **故障排障：五问定位**
  1. **容器活着吗**：`docker ps | grep <app>`，没起来先看反复重启的常见原因
  2. **健康吗**：`docker inspect <container>` 看 Health 状态与 ExitCode
  3. **应用日志说什么**：`docker logs <container> --tail 50`；查当天错误用 `docker exec <container> cat logs/app-error.$(date +%Y-%m-%d).log`，按 trace ID `grep` 还原整条调用链
  4. **是不是数据库问题**：`docker logs <mysql-container>`
  5. **是不是被重启过**：`pm2 logs <app> --lines 50 --nostream`
- **重启与迁移失败的定位**
  - **容器反复重启的三个常见原因**：数据库未就绪（等 migration）、环境变量缺失导致启动校验抛错、端口冲突
  - **迁移失败**：`docker compose -f docker-compose.prod.yml logs migration` 看退出码与日志，用 `SELECT * FROM migrations ORDER BY id DESC LIMIT 5` 看表状态
  - **迁移失败不破坏已有数据**（事务回滚 + 幂等），修好迁移文件重跑即可
- **部署检查清单**
  - 镜像构建成功（`docker images` 有最新 tag）、迁移执行成功（`docker compose logs migration` 无 ERROR）、容器健康（`docker inspect <app>` 看 `State.Health.Status`）、本地接口可访问（`curl http://127.0.0.1:3000/api/health`）、日志正常写入（`docker exec <app> ls /app/logs/`）、外部入口通（`curl https://api.example.com/api/health`）


### 部署与工程化 09-CI/CD 自动化部署

- **手动部署的问题与 CI/CD 的核心区别**
  - **四个问题**：易漏步骤、构建消耗服务器资源、无法快速回滚、多人发版不可控
  - **核心区别**：**构建从服务器挪到云端 CI**，服务器只做一件事——拉新镜像、重启容器
  - **对应关系**：触发方式从 SSH 敲命令变成 `git tag v1.0.0` 推送；构建位置从服务器本地变成 GitHub Actions 云端；镜像从本地构建变成从仓库拉取；回滚从 `git checkout` 重新构建变成切回旧 tag 镜像（秒级）
- **workflow 的三个概念（`.github/workflows/*.yml`）**
  1. **触发条件（`on`）**：什么时候跑——`push`、`tag`、手动
  2. **任务（`jobs`）**：一个流水线的步骤集合，可并行
  3. **步骤（`steps`）**：具体动作——`checkout`、`build`、`deploy`
- **为什么推荐双流水线**
  - **build 负责构建推送，deploy 等 build 成功后再 SSH 部署**
  - 构建失败就不会触发部署；deploy 还能在多台服务器上复用
- **流水线一：构建镜像并推送（build-stable.yml）**
  - `on: push: tags: ['v*']` 触发，`docker/login-action@v3` 登录 Docker Hub 后由 `docker/build-push-action@v5` 构建并 `push: true`
  - 同时打两个 tag：`stable` 表示"最新稳定版"，`v1.0.0`（`github.ref_name`）表示"此版本"；**回滚时直接拉旧 tag 的镜像**
- **流水线二：SSH 部署（deploy.yml）**
  - `on: workflow_run` 监听 `Build Stable Image` 工作流的 `completed`，且 `if: conclusion == 'success'` 才执行，连接由 `appleboy/ssh-action@v1` 完成
  - 服务器上只跑 `docker compose -f docker-compose.prod.yml --env-file .env --env-file .env.production pull` + `up -d`
  - **`pull`（从仓库拉取）替代 `--build`（服务器本地构建）**，这就是"构建挪到云端"的关键，服务器压力大幅下降
- **Secrets：密钥不进代码**
  - 在仓库 **Settings → Secrets and variables → Actions** 配置 `DOCKER_USERNAME` / `DOCKER_PASSWORD`、`DOCKER_IMAGE`、`SERVER_HOST` / `SERVER_USER`、`SERVER_SSH_KEY`
  - 建议为 CI/CD 单独生成密钥对（`ssh-keygen -t ed25519 -C "github-actions-deploy"` + `ssh-copy-id`），不要用日常账号
- **迁移进流水线**
  - **安全迁移**（新增表 / 字段 / 索引）在 deploy 中自动执行，且用隔离容器：`docker compose -f docker-compose.prod.yml run --rm --entrypoint "" my-app node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`
  - **破坏性迁移**（删除 / 重命名）不可逆，自动化执行没有"看一眼"的机会，必须人工确认后手动执行——安全的变更全自动，危险的变更留人工
- **触发、回滚与验证**
  - **发版 / 删 tag**：`git tag v1.0.0 && git push origin master && git push origin v1.0.0`；`git tag -d v1.0.0 && git push origin --delete v1.0.0`
  - **回滚 = 用旧 tag 再部署一次**：CI 重新构建旧代码镜像并部署，秒级完成
  - **验证**：GitHub Actions 页面看运行日志；服务器上 `docker ps | grep my-app`、`docker logs -f my-app-server`、`curl https://api.example.com/api/health`


### 脚手架开发 01-脚手架开发入门

- **脚手架的定位与核心流程**
  - **脚手架是什么**：自动化创建项目的工具，用户命令行交互选配置后自动生成模板，如 `create-react-app`、`nest new`。
  - **核心流程**：用户输入命令 → 交互式问答（项目名称、模板类型等）→ 根据用户选择复制模板文件 → 替换模板中的变量 → 输出生成的项目。
- **CLI 工程的三个落点**
  1. **入口约定**：`bin/index.js` 首行 `#!/usr/bin/env node`，在 `package.json` 的 `bin` 字段里映射成全局命令名。
  2. **依赖分工**：inquirer 负责交互问答，fs-extra 负责目录复制（比原生 fs 多了目录递归与覆盖便利）。
  3. **变量替换**：复制完模板后读文件，用 `replace(/{{projectName}}/g, ...)` 把占位符换成真实项目名。
- **yargs 的参数解析**
  - 用 `command('create <name>')` 定义子命令与 positional，`option` 定义 `--template` 之类的可选参数，`.help()` 自动生成帮助。


### 进阶主题 01-消息队列

- **消息队列的本质：把同步调用拆成异步通信**
  - **什么是消息队列**：生产者发消息到队列、消费者从队列取消息的异步通信机制
  - **同步 vs 异步**：同步是下单后等扣库存、发短信、发邮件、算积分全部完成；异步只让用户等下单，其余由队列驱动
- **队列带来的三大作用**
  1. **异步处理**：非核心操作异步执行，用户不必等全部完成
  2. **削峰填谷**：请求高峰时缓冲，像水库蓄水一样防止下游被冲垮
  3. **解耦**：生产者和消费者不直接依赖，彼此不需要知道对方
- **Kafka 的六个核心概念**
  1. **Producer**：发送消息的应用程序
  2. **Consumer**：消费消息的应用程序
  3. **Topic**：消息的分类，类似数据库的表
  4. **Partition**：Topic 的分区，实现并行处理
  5. **Broker**：Kafka 集群中的服务器
  6. **Consumer Group**：消费者组，组内消费者负载均衡消费
- **选型对比：Kafka / RabbitMQ / Redis Stream**
  1. **Kafka**：吞吐极高（百万级/秒），落磁盘、分区内有序，适合日志、大数据与流处理；学习成本高
  2. **RabbitMQ**：吞吐高（万级/秒），落磁盘、单队列有序，适合业务系统与任务分发；学习成本中
  3. **Redis Stream**：吞吐高（万级/秒），内存+磁盘、有序，轻量，适合简单消息与缓存场景；学习成本低


### 进阶主题 02-性能优化

- **缓存的三种失效场景与对策**
  1. **缓存穿透**：查不存在的数据每次都打到库；对策是缓存空值或上布隆过滤器
  2. **缓存击穿**：热点 key 过期瞬间大量请求涌向数据库；对策是互斥锁或热点数据永不过期
  3. **缓存雪崩**：大量 key 同时过期把数据库压垮；对策是过期时间加随机值、多级缓存
- **限流的四种算法**
  1. **计数器**：固定时间窗口内计数，实现简单但有突刺问题
  2. **滑动窗口**：细粒度时间窗口，解决突刺、更平滑
  3. **令牌桶**：匀速放入令牌、请求消耗令牌，允许突发流量
  4. **漏桶**：匀速处理请求，平滑流量但不允许突发
- **NestJS 限流落地**
  - **全局配置**：`ThrottlerModule.forRoot({ ttl: 60000, limit: 10 })` 定 60 秒窗口、窗口内最多 10 次
  - **按接口覆盖**：`@Throttle(5, 60000)` 让单个路由在 60 秒内最多 5 次
- **数据库优化的五个手段**
  1. **索引优化**：合理建索引，避免全表扫描
  2. **慢查询日志**：定位慢 SQL，用 EXPLAIN 分析
  3. **连接池**：复用数据库连接，避免频繁创建
  4. **读写分离**：主库写，从库读
  5. **分库分表**：数据量大时水平拆分


### 进阶主题 03-安全

- **三类常见攻击与对应防线**
  1. **XSS（跨站脚本攻击）**：往页面注入恶意脚本，靠模板引擎（Pug）与前端框架（React/Vue）默认的 HTML 转义防御
  2. **CSRF（跨站请求伪造）**：诱导用户在不知情下执行操作，靠 CSRF Token 防御，NestJS 里可用 `csurf` 中间件
  3. **SQL 注入**：字符串拼接 SQL 就是注入入口，必须用参数化查询（`?` 占位）让驱动做转义
- **框架层的三道通用防护**
  1. **Helmet**：一个 `app.use(helmet())` 批量设置安全响应头，成本极低收益高
  2. **CORS**：开发可放开（`app.enableCors()`），生产必须用 `origin` 白名单；带 Cookie 时 `credentials` 与前端 `withCredentials` 要成对配
  3. **参数校验**：永远不信任用户输入，`ValidationPipe` 开 `whitelist + forbidNonWhitelisted` 只放行 DTO 声明过的字段


### 进阶主题 04-测试

- **测试金字塔：按性价比分层**
  1. **单元测试**：极快、数量最多，覆盖单个函数/方法
  2. **集成测试**：速度与数量居中，覆盖模块间交互
  3. **E2E 测试**：最慢、数量最少，覆盖完整请求链路
- **NestJS 里两类测试怎么写**
  - **单元测试**：`Test.createTestingModule({ providers: [...] })` 编译后 `module.get()` 取出待测服务
  - **集成测试**：`imports: [AppModule]` 编译出完整应用，`createNestApplication()` + `app.init()` 后用 supertest 打真实 HTTP
- **三种测试替身**
  1. **Mock**：模拟整个对象，如 `jest.fn().mockResolvedValue(...)`
  2. **Stub**：替换方法返回值，如 `jest.spyOn(...).mockResolvedValue(...)`
  3. **Spy**：只监控调用情况，`jest.spyOn` 后断言 `toHaveBeenCalledWith`


### 进阶主题 05-设计模式

- **实例的创建与复用：单例与工厂**
  1. **单例模式**：NestJS 的 Provider 默认就是单例，注入到多少个类里都是同一个实例
  2. **工厂模式**：自定义 Provider 的 `useFactory` 按环境返回不同的数据库连接，就是工厂模式的落点
- **行为的替换与通知：策略与观察者**
  1. **策略模式**：把算法抽成可互换的接口实现（如多种登录校验），用 `@Inject('AUTH_STRATEGY')` 在运行时选择
  2. **观察者模式**：`EventEmitter2` 的 `emit` 发布、`@OnEvent` 监听就是框架内置的观察者模式，用来做下单后发短信这类副作用


### 进阶主题 06-系统设计

- **微服务：先拆得开，再连得上**
  1. **连通方式**：`ClientsModule.register` 声明传输方式（TCP / Redis / Kafka / RabbitMQ），`client.send({ cmd }, payload)` 发消息
  2. **拆分原则**：按业务拆（用户/订单/商品）、每个服务独立数据库、独立部署扩展；同步用 HTTP/gRPC，异步用消息队列
- **WebSocket 网关：连接与广播**
  - **网关声明**：`@WebSocketGateway({ namespace, cors })` 声明命名空间与跨域；`handleConnection(client)` 处理连接建立
  - **消息与广播**：`@SubscribeMessage` 处理消息，`server.emit` 广播给所有客户端
- **高可用的五个策略**
  1. **负载均衡**：多台服务器分担请求
  2. **冗余部署**：多实例部署，单点故障不影响
  3. **健康检查**：定期检查服务状态，自动剔除异常节点
  4. **熔断降级**：服务不可用时返回降级响应而非崩溃
  5. **限流**：保护后端不被突发流量打垮


### 进阶主题 07-Git 与协作

- **三种工作流怎么选**
  1. **GitHub Flow**：main + feature 分支，PR 合并；适合小型团队、持续部署
  2. **Git Flow**：main + develop + feature + release 分支；适合中大型项目、版本发布
  3. **Trunk-Based**：所有人在 main 上开发、用短命分支；适合高频发布、CI/CD 成熟
- **合并策略的取舍**
  1. **Merge**：`git merge feature` 保留完整历史，但多一个合并提交
  2. **Rebase**：`git rebase main` 得到线性历史、无合并提交，但会改写提交
  3. **Squash**：合并时把多个提交压缩为一个
- **提交信息规范（Conventional Commits）**
  - **格式**：`<type>(<scope>): <subject>`
  - **type 分类**：`feat` / `fix` / `docs` / `refactor` / `test` / `chore`
- **Code Review 实践**
  - **PR 粒度**：单次 PR 不要太大，控制在 200~300 行以内
  - **审查顺序**：先理解整体逻辑，再看细节
  - **沟通方式**：指出问题的同时给出建议，尊重作者，用"建议"代替"要求"
  - **审查清单**：代码规范、是否有不必要的复杂性、异常处理是否完善、是否有安全漏洞、测试是否覆盖

| 见到什么 | 该想到什么 | 一句话理由 |
| --- | --- | --- |
| 本地跑得好、线上就不对 | 配置加载链与启动校验 | 同一份代码行为不同，九成是环境变量没对齐或密钥还是占位符 |
| 排障时找不到一次请求的完整路径 | trace ID | 日志散在多个服务与容器里，只有请求级 ID 能把它们串起来 |
| 容器"起来了"但请求全 502 | 端点级 HEALTHCHECK | 端口在监听不代表应用就绪，探针要打到 `/api/health` |

| 应用日志里的 IP 全是同一个 | X-Forwarded-For | 反向代理后看到的是代理地址，要在应用层解析原始头 |
| 前端 WebSocket 一直握手失败 | Nginx 的 Upgrade / Connection 头 | 不升级协议、不放开长超时，长连接过不了代理层 |
| Entity 一改库就跟着变 | synchronize 必须关 | 生产表里是真数据，删字段等于永久丢数据 |
| 多副本部署时报迁移锁冲突 | 迁移做成独立一次性 Job | 每个业务容器都跑迁移必然并发打架 |
| 发版还要 SSH 上去敲命令 | 双流水线 + 镜像 tag | 构建挪到云端、服务器只 pull，回滚就是再发一次旧 tag |
| 新项目每次从零配环境 | 脚手架 | 交互问答 + 模板变量替换，项目起点也变成一次命令 |
| 下单接口要等发短信发邮件 | 消息队列 | 非核心动作异步化，只让用户等核心链路 |
| 热点 key 一过期数据库就炸 | 互斥锁或过期时间加随机值 | 击穿与雪崩成因不同，对策也不同 |

## 易错点汇总

- **"`get<number>()` 会帮我转型"、"容器里也照读 `.env`"**：泛型只是给 TypeScript 看的期望类型，运行时 `'3306'` 仍是字符串；而环境变量已由容器或 CI 注入时再加载 `.env`，文件里的旧值会覆盖真实注入值。
- **"配置类型安全就等于值正确"**：`JWT_SECRET` 被配成 `your-jwt-secret-change-me` 也是合法字符串，类型检查拦不住。必须在配置工厂里做启动校验。
- **"console.log 够用了"**：没有级别、没有时间戳、不落文件，重启即丢，而且同步写 stdout 在高并发下会拖慢请求。生产必须交给日志库并落文件。
- **"PM2 的日志能当历史日志查"**：PM2 日志是内存缓冲，容器一重启就没了。历史排障要看 `logs/app.*.log` 文件日志。
- **"fork 和 cluster 随便选，`pm2 reload` 通用"**：Docker 容器内该用 fork 单实例，水平扩展交给编排平台；reload 靠逐个重启 worker 实现零停机，fork 模式没有意义。
- **"单阶段 Dockerfile 够用"**：它会把源码和 devDependencies 一起打进镜像，体积约 1GB 且攻击面大。多阶段构建后只留产物，降到约 200MB。
- **"写了 `depends_on` 就保证启动顺序"**：默认的 depends_on 只等容器启动、不等服务就绪。要"迁移跑完再起应用"必须配 `condition: service_completed_successfully`。
- **"容器起来了就算部署成功"**：健康检查要打到应用端点而不是端口；一次部署还要确认镜像 tag、迁移无 ERROR、日志正常写入、外部入口可达。
- **"`synchronize: true` 方便，生产也留着"**：Entity 删一个字段重启就真删列，数据永久丢失，变更还无法审查、无法回滚。
- **"迁移和业务容器一起跑没关系"、"破坏性迁移也让 CI 自动执行"**：多实例各跑迁移会并发锁冲突、产生脏数据，迁移应做成独立一次性 Job；而 `DROP` / 重命名不可逆，必须人工确认后再执行。
- **"缓存和限流对策可以随便选"、"SQL 拼接只是风格问题"**：穿透、击穿、雪崩要分别用布隆过滤器、互斥锁、随机过期时间；令牌桶允许突发而漏桶不允许；字符串拼 SQL 就是注入入口，必须参数化查询并配 `ValidationPipe` 白名单。
