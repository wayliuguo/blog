## ① 部署全景：统一部署模式

生产部署的核心设计原则（来自前几篇的合流）：

> **MySQL 和 Redis 永远是外部服务，compose 堆栈只管理 migration + app。**

```
┌─────────────────────────────────────────────────┐
│  docker-compose.infra.prod.yml（一次性启动，之后不管）│
│  ├── mysql    restart: always  数据卷持久化        │
│  └── redis    restart: always                     │
└─────────────────────────────────────────────────┘
                        │
                        │ host.docker.internal:3306/6379
                        ▼
┌─────────────────────────────────────────────────┐
│  docker-compose.prod.yml（日常部署更新）           │
│  ├── migration    一次性 Job，迁移完退出           │
│  └── app-server   restart: always               │
└─────────────────────────────────────────────────┘
```

为什么这样分层：

| 原则 | 理由 |
|------|------|
| 数据库独立于应用栈 | 生命周期不同；可随时切换自建/云 RDS 而不动应用编排 |
| 迁移与业务分离 | 迁移失败不阻塞已有服务；多实例不并发迁移 |
| 端口只绑 `127.0.0.1` | 对外只有 Nginx 一个入口，安全面最小 |

## ② 首次部署：从空服务器到线上

### 2.1 准备环境变量

```bash
git clone <your-repo> /opt/my-app && cd /opt/my-app
cp .env.example .env.production
# 编辑 .env.production：填入数据库密码、JWT 密钥、域名等真实值
```

> 环境变量的组织见 [环境管理与配置](./01-环境管理与配置)：`.env.example` 提交、`.env.production` 不提交、密钥必须强随机。

### 2.2 启动基础设施（一次性）

```bash
docker compose -f docker-compose.infra.prod.yml --env-file .env.production up -d
```

启动后不用再管它：`restart: always` 保证挂了自动拉起，数据落在宿主机卷里。

### 2.3 构建并启动应用（日常命令）

```bash
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
```

这条命令背后发生的事（前几篇的合流）：

```
1. build → 五阶段 Dockerfile 构建镜像（缓存复用，见 Docker 容器化）
2. migration 容器启动 → wait-for-it 等 MySQL → migration:run（见数据库迁移与发布）
3. app 容器启动（等迁移成功）→ 容器内 PM2 fork 拉起 NestJS（见 PM2）
4. HEALTHCHECK 周期探测 /api/health（见 Docker 容器化）
5. 验证：curl http://your-server:3000/api/health
```

### 2.4 接入 Nginx

```bash
# /etc/nginx/conf.d/my-app.conf
server {
    listen 80;
    server_name api.example.com;

    location / {
        proxy_pass http://127.0.0.1:3000/;   # 指向容器映射的宿主机端口
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    }
}
```

> 为什么 Nginx 转发到 `127.0.0.1:3000` 而不是直接暴露？因为 compose 里端口绑定在回环地址上——**公网请求全部走 Nginx**，细节见 [Nginx 反向代理与网关](./06-Nginx%20反向代理与网关)。

## ③ 日常迭代：更新、持久化、备份

### 3.1 更新版本

```bash
git pull
docker compose -f docker-compose.prod.yml --env-file .env.production up -d --build
```

Compose 会先启动新容器，**健康检查通过后再停旧容器**——单机环境下的"滚动更新"，服务基本不中断。

### 3.2 数据持久化

| 数据 | 存储位置 | 容器重建是否丢失 |
|------|---------|----------------|
| MySQL | `./__data/mysql/`（宿主机目录） | 否 |
| Redis | `./__data/redis/` | 否 |
| 应用日志 | named volume `show-track-logs` | 否 |

### 3.3 备份与恢复

```bash
# 备份 MySQL
docker exec <mysql-container> mysqldump -uroot -p <db> > backup.sql

# 恢复 MySQL
docker exec -i <mysql-container> mysql -uroot -p <db> < backup.sql
```

> 云数据库的备份由云服务方提供，自建 Docker 数据库则靠宿主机目录 + 定时 mysqldump。生产建议至少每日全量备份。

## ④ 故障排障：从现象到定位

### 4.1 排障路径

```
服务不可用
   │
   ├─ 1. 容器活着吗？        docker ps | grep <app>          → 没起来看 4.2
   ├─ 2. 健康吗？            docker inspect <container>      → 不健康看日志
   ├─ 3. 应用日志说什么？     docker logs <container> --tail 50 → 看 4.3
   ├─ 4. 是不是数据库问题？   docker logs <mysql-container>    → 看 4.4
   └─ 5. 是不是被重启过？     pm2 logs <app> --lines 50 --nostream
```

### 4.2 容器反复重启

```bash
docker logs <container> --tail 50   # 看启动报错
docker inspect <container>          # 看 Health 状态和 ExitCode
```

常见原因：数据库未就绪（等 migration）、环境变量缺失（启动校验抛错，见[环境管理与配置](./01-环境管理与配置)）、端口冲突。

### 4.3 应用报错

```bash
# 今天的错误日志（独立错误文件，见日志体系）
docker exec <container> cat logs/app-error.$(date +%Y-%m-%d).log

# 按 trace ID 串联整条调用链（日志体系 3.4 节）
docker exec <container> grep "<trace-id>" logs/app.$(date +%Y-%m-%d).log
```

### 4.4 数据库迁移失败

```bash
# 迁移 Job 退出码与日志
docker compose -f docker-compose.prod.yml logs migration

# 查看 migrations 表当前状态
docker exec <mysql-container> mysql -uroot -p <db> -e "SELECT * FROM migrations ORDER BY id DESC LIMIT 5"
```

> 迁移失败不会破坏已有数据（事务回滚 + 幂等），修好迁移文件重跑即可，见 [数据库迁移与发布](./07-数据库迁移与发布)。

## 实战清单：一次部署要检查什么

| 检查项 | 命令 |
|--------|------|
| 镜像构建成功 | `docker images`（有最新 tag） |
| 迁移执行成功 | `docker compose logs migration`（无 ERROR） |
| 容器健康 | `docker inspect <app>` 查看 `State.Health.Status` 字段 |
| 接口可访问 | `curl http://127.0.0.1:3000/api/health` |
| 日志正常写入 | `docker exec <app> ls /app/logs/` |
| 外部入口通 | `curl https://api.example.com/api/health` |
