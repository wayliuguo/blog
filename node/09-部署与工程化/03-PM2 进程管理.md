## 为什么需要进程管理

`node dist/main.js` 能跑，但那是"前台裸跑"：终端一关进程就死、崩溃没人管、日志无处可查。生产环境需要的是一个"管家"——**PM2**。

渐进四步：

| 阶段 | 目标 | 你能获得 |
|------|------|---------|
| ① 认清问题 | 裸跑的四个致命问题 | 知道为什么需要 PM2 |
| ② 常用命令 | 启动/查看/日志/重启 | 能把应用管起来 |
| ③ ecosystem 配置 | 声明式配置 + 环境区分 | 配置可版本化、可复用 |
| ④ 部署决策 | fork vs cluster、与 Docker 的分工 | 生产选型能力 |

---

## ① 认清问题：`node app.js` 裸跑的四宗罪

| 问题 | 表现 |
|------|------|
| 终端绑定 | 关闭终端进程即死（Ctrl+C / SSH 断开） |
| 崩溃即停 | 未捕获异常直接退出，无人拉起 |
| 单线程浪费 | 现代 CPU 多核，Node 默认只用一核 |
| 无日志管理 | 输出散落在终端，重启即丢 |

PM2 解决全部四个：**守护进程化、自动重启、集群模式、日志收集**。

## ② 常用命令：把应用管起来

```bash
npm install -g pm2
```

```bash
pm2 start dist/main.js --name my-app   # 启动
pm2 list                               # 查看所有进程（状态、CPU、内存）
pm2 logs my-app --lines 100            # 查看最近 100 行日志
pm2 restart my-app                     # 重启
pm2 reload my-app                      # 重新加载（零停机，仅 cluster 模式）
pm2 stop my-app                        # 停止
pm2 delete my-app                      # 删除进程
pm2 monit                              # 实时监控面板
pm2 describe my-app                    # 进程详情
```

守护与自动重启：

```bash
pm2 start app.js --name my-app --max-memory-restart 500M  # 内存超限自动重启
pm2 save                                # 保存当前进程列表
pm2 startup                             # 生成开机自启脚本
```

> `pm2 startup` + `pm2 save` 组合拳：系统重启后 PM2 自动拉起全部应用。

## ③ ecosystem.config.js：把配置写进代码

命令行参数每次都要敲，且无法版本化。生产项目用 `ecosystem.config.js` 声明式配置：

```javascript
// ecosystem.config.js（show-track-server 生产配置）
module.exports = {
  apps: [
    {
      name: 'show-track-server',      // 应用名称
      script: './dist/main.js',       // 入口脚本
      autorestart: true,              // 异常退出自动重启
      exec_mode: 'fork',              // Docker 中使用 fork 模式
      instances: 1,                   // 单实例，编排平台负责水平扩展
      watch: false,                   // 是否监听文件变化
      max_memory_restart: '1G',       // 内存超 1G 自动重启
      env: {
        NODE_ENV: 'production',
        PORT: process.env.APP_PORT,   // 从环境变量读取端口
      },
    },
  ],
};
```

启动：

```bash
pm2 start ecosystem.config.js
```

字段速查：

| 字段 | 作用 |
|------|------|
| `autorestart` | 进程崩溃自动重启 |
| `max_memory_restart` | 内存超限自动重启（防内存泄漏拖垮机器） |
| `exec_mode` / `instances` | 进程模式与数量（见 ④） |
| `env` | 注入环境变量，可用 `env_production` 区分环境 |
| `watch` | 文件变化自动重启（仅开发用） |

## ④ 部署决策：fork vs cluster，以及和 Docker 的分工

### 4.1 两种执行模式

| 模式 | 说明 | 适用场景 |
|------|------|----------|
| **fork** | 单进程，父子进程模式 | Windows、Docker 容器、不需要负载均衡 |
| **cluster** | 多进程，Node 原生 cluster + 轮询负载均衡 | Linux/macOS 裸机部署、无容器编排平台 |

裸机多核部署（cluster 模式）：

```bash
# 利用全部 CPU 核心
pm2 start dist/main.js -i max --name my-app
pm2 list  # 会看到 N 个进程，名称都是 my-app
```

```javascript
// 裸机 cluster 配置
{
  name: 'my-app',
  script: 'dist/main.js',
  exec_mode: 'cluster',  // 集群模式
  instances: 'max',      // 进程数 = CPU 核数
}
```

### 4.2 关键决策：Docker 里用 fork 而不是 cluster

这是最容易踩的坑。show-track 在 Docker 里明确用 **fork 单实例**，为什么？

```
Docker 容器（fork 单进程）
   │
   ├─ 水平扩展交给编排平台（Docker Compose 多副本 / K8s）
   ├─ 容器内不做 cluster（避免一层容器内再开 N 个进程）
   └─ PM2 保留 fork 模式用于：日志管理、进程监控、内存限制重启
```

| 场景 | 用哪种 | 为什么 |
|------|--------|--------|
| Docker 容器内 | **fork** | 水平扩展由编排平台负责；容器内再 cluster 反而造成资源浪费和信号混乱 |
| Linux 裸机 | **cluster** | 没有编排平台，需要 PM2 自己利用多核 |
| Windows / 单机小项目 | **fork** | cluster 在 Windows 上行为异常，单实例足够 |

> 这也回答了 ② 里的坑：**`pm2 reload` 只对 cluster 模式有意义**（逐个重启 worker 实现零停机），fork 模式下没有 reload 的必要。

### 4.3 三层部署架构的演进

```
裸机部署（传统）：  用户 → Nginx(80/443) → PM2 cluster（多个 worker）→ DB
Docker 部署（现代）：用户 → Nginx → Docker 容器（PM2 fork 单进程）× N 副本 → DB
K8s 部署（云原生）：用户 → Ingress → Pod（容器内 fork）→ DB
```

> 演进主线：**裸机自己管进程 → 容器编排管副本 → 平台管一切**。PM2 的角色从"负载均衡器"逐步退化为"容器内的进程管家"。

## 与日志体系的衔接

PM2 会捕获应用的控制台输出（stdout），这就是上一篇双写架构里"控制台 → PM2 捕获 → docker logs"这条链路：

```bash
# 查看 PM2 捕获的进程输出
pm2 logs my-app --lines 100 --nostream
# 清除 PM2 日志缓存
pm2 flush
```

> 注意：PM2 日志是内存缓冲、不持久化，容器重启后丢失。**要查历史日志请看文件日志**（`logs/app.*.log`），见 [日志体系](./02-日志体系)。
