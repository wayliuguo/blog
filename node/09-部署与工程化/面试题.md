## 一、基础概念

### Q1: 镜像、容器、仓库分别是什么？镜像和容器是什么关系？（09-部署/04 篇）

- **结论**：镜像是只读模板（类 / 光盘），容器是镜像的运行实例（对象 / 光驱），仓库负责存储与分发镜像。一个镜像可以起多个容器。
- **原理**：Dockerfile 每条指令产出一个只读层，容器在镜像层之上再加一层**可写层**——运行时所有改动都落在可写层，删掉容器即丢，镜像本身不变。
- **边界**：可写层不是持久化方案。数据库数据、应用日志这类要留住的东西必须挂数据卷或绑宿主机目录，否则容器一重建就没了。
- **追问**：`docker build` 造镜像、`docker run` 起容器；`docker commit` 能把容器改动固化回镜像，但生产应改 Dockerfile 重建，不用 commit。

### Q2: Dockerfile 里 COPY 和 ADD 怎么选？（09-部署/04 篇）

- **结论**：默认用 `COPY`。`ADD` 多出「从 URL 下载」和「自动解压本地 tar」两个隐式行为，只在确实需要解压时用。
- **原理**：`COPY` 只做一件事——把构建上下文里的文件复制到镜像路径；`ADD` 的隐式解压 / 下载会让构建结果依赖网络和压缩包内容，构建不再可复现。
- **边界**：多阶段构建里几乎只用 `COPY`，跨阶段复制靠 `COPY --from=<stage>`，这与 `ADD` 无关。
- **追问**：构建上下文瘦身靠 `.dockerignore`（`node_modules`、`.git`、`.env`、`*.md`）——上下文越小，`docker build` 要传给守护进程的字节越少。

### Q3: Compose 与 `docker run` 的关系是什么？（09-部署/05 篇）

- **结论**：`docker run` 是「一条命令起一个容器」，Compose 是「一份 YAML 声明一组服务」。Compose 不替代 Docker，而是把 `docker run` 的参数、网络、卷、启动顺序变成可版本化的文件。
- **原理**：起 app + MySQL + Redis 三个容器，`docker run` 要敲三串参数、手动 `--link`、重启还得重新组织命令；Compose 一条 `up -d` 全部拉起，并自动为这组服务建网络做 DNS 解析，容器之间**直接用服务名互访**。
- **场景**：`docker run` 适合临时调试单个容器；只要涉及"应用 + 数据库 + 缓存"的组合，就该上 Compose。
- **边界**：Compose 是单机编排，跨宿主机要 K8s / Swarm；而且 `depends_on` 默认**只等容器启动、不等服务就绪**，要真就绪必须配 `condition` + `healthcheck`。

### Q4: PM2 是什么？常用命令有哪些？（09-部署/03 篇）

- **结论**：PM2 是 Node 的进程管家，一次解决裸跑 `node dist/main.js` 的四宗罪——终端绑定、崩溃即停、只吃一核、日志无处可查。
- **原理**：`pm2 start` 把进程 daemon 化并接住崩溃自动拉起；`pm2 save` + `pm2 startup` 组合保证系统重启后自动恢复全部应用。
- **命令**：`pm2 list`（状态 / CPU / 内存）、`pm2 logs <app> --lines 100`（日志）、`pm2 restart` / `pm2 reload`（重启 / 零停机重载）、`pm2 monit`（面板）、`pm2 describe`（详情）、`pm2 flush`（清日志缓存）。
- **边界**：PM2 的日志是**内存缓冲、不持久化**，容器重启即丢——要查历史日志看文件日志 `logs/app.*.log`。
- **追问**：`pm2 reload` 只对 cluster 模式有意义（逐个重启 worker）；fork 模式下没有 worker 可换，直接 `restart` 即可。

### Q5: 正向代理和反向代理的区别？（09-部署/06 篇）

- **结论**：正向代理代理**客户端**去访问外部（公司内网出口），反向代理代理**服务端**接收请求（Nginx 网关）。区别在"替谁出面"。
- **原理**：正向代理时客户端知道自己在用代理，服务端只看到代理；反向代理时客户端以为在直接访问服务，背后的实例与网络拓扑被完全隐藏。
- **场景**：后端说的"加一层代理"几乎都是反向代理——统一入口、SSL 终结、负载均衡、动静分离、Gzip 都在这一层做。
- **边界**：反向代理会改写请求来源，应用拿到的地址是 Nginx 的 IP；要真实 IP 必须让 Nginx 传 `X-Real-IP` / `X-Forwarded-For`，并在应用层解析。

### Q6: `.env` 有什么作用？多环境配置怎么组织？（09-部署/01 篇）

- **结论**：`.env` 把配置从代码里剥出来，换来"同一份代码跑出不同行为"。多环境靠**按环境拆文件**：`.env`（默认值，提交）、`.env.development` / `.env.production`（不提交）、`.env.example`（模板，提交）。
- **原理**：`@nestjs/config` 封装了 dotenv，`envFilePath: [`.env.${NODE_ENV}`, '.env']` 数组**越靠前优先级越高**；完整加载链是 `process.env`（OS / 容器注入，最高）> `.env.local` > `.env.<环境>` > `.env.example` > `.env`。
- **边界**：`.env*` 必须进 `.gitignore`，只留 `.env.example`——密钥进了 Git 历史就永久留存，删掉也能从旧 commit 里翻出来。
- **追问**：容器 / CI 已注入环境变量时应**跳过 dotenv 加载**（判 `process.env.DB_HOST` 存在即 return），否则 `.env` 文件会把真实注入值覆盖掉。

### Q7: 为什么 `console.log` 不能上生产？（09-部署/02 篇）

- **结论**：它是一条**没有级别、没有时间戳、不落文件、高并发下拖慢请求**的 stdout 输出——生产日志该有的能力它一项都没有。
- **原理**：四个硬伤——无法区分 debug / info / error，排查时被海量日志淹没；无法定位"什么时候发生"；容器 / 服务器一重启就丢，无法复盘；同步写 stdout 在高并发下影响吞吐。
- **边界**：隐藏坑是 stdout 只适合"实时看"、不适合"事后查"，`docker logs` 能看到不等于留得住。所以生产日志必须落到文件。
- **追问**：旧资料常把"同步阻塞事件循环"当成第一原因；新版正文的口径是**能力缺失 + stdout 不持久**才是主要问题，阻塞只是高并发下的一条副作用。

### Q8: 什么是日志分级？Winston 有哪些级别？（09-部署/02 篇）

- **结论**：分级是按严重程度给日志贴标签，用"输出线"控制噪音。Winston 沿用 npm 级别体系，**数字越小越严重**：`error`(0) / `warn`(1) / `info`(2) / `debug`(3) / `verbose`(4)。
- **原理**：`level` 是"最低输出线"——设成 `info` 时 `debug` / `verbose` 直接被丢弃，连格式化都不走，省磁盘 I/O 也省 CPU。生产一般设 `info`，把 debug 留给开发。
- **场景**：级别不硬编码，走配置中心（`LOGGER_LEVEL`），这样线上临时排查可以调级别，不必改代码重新发版。
- **边界**：级别只在**你记了**的前提下有用——关键路径没打日志，级别再细也查不出东西。所以入口、外部调用、异常兜底三处必须留错误日志。

### Q9: 消息队列解决了什么问题？（11-进阶/01 篇）

- **结论**：三件事——**异步处理、削峰填谷、解耦**。把"下单要等扣库存 + 发短信 + 发邮件 + 加积分"变成"用户只等下单"。
- **原理**：生产者发完消息立刻返回，消费者各自异步处理；突发流量先在队列里缓冲，消费者按自身能力取，下游不会被瞬间打垮；生产者不需要知道谁在消费，新增消费者不用改生产者。
- **边界**：代价是复杂度——消息可能丢失、重复、乱序，还要多运维一套中间件。需要立刻拿到结果的强实时调用不适合走队列。
- **追问**：引入队列后必须配套三件事：可靠投递（确认 / 重试）、消费幂等（去重）、可观测（积压量告警）。

### Q10: Kafka 的核心概念有哪些？（11-进阶/01 篇）

- **结论**：Producer、Consumer、Topic、Partition、Broker、Consumer Group 六个。
- **原理**：Topic 是消息的逻辑分类（类似表）；Partition 是存储与并行消费的最小单位，**分区内有序、跨分区无序**；Broker 是集群节点，一个 Topic 的分区分散在不同 Broker 上；Consumer Group 内每个分区只被组内一个消费者消费——组内负载均衡、组间独立消费。
- **边界**：分区数决定消费的最大并行度——消费者多于分区数时多出来的会空转；分区太多又推高文件句柄与选举开销。
- **追问**：要让同一订单的事件有序，就用 `orderId` 作分区键，让同一订单的消息永远落进同一分区。

### Q11: 单元测试和集成测试的区别？（11-进阶/04 篇）

- **结论**：单元测试测**单个函数 / 类**、隔离外部依赖、极快；集成测试测**模块间协作**、要起应用上下文（甚至真数据库与 HTTP 请求）、慢。
- **原理**：单元测试用 Mock 把数据库、网络、外部服务全替换掉，只验证被测类的逻辑分支；集成测试用 `Test.createTestingModule({ imports: [AppModule] })` + `createNestApplication()` 起真应用，再用 Supertest 打 HTTP，验证"Controller → Service → 数据库"整条链。
- **场景**：测试金字塔建议单元 : 集成 : E2E ≈ 7 : 2 : 1——底层多、顶层少。
- **边界**：单元测试定位精确、跑得快，但 Mock 过头就变成"实现细节的快照"，重构一行就红一片；关键链路的真实性得由集成测试兜底。

### Q12: Mock、Stub、Spy 的区别？（11-进阶/04 篇）

- **结论**：Stub 管**返回值**（状态验证），Mock 管**交互行为**（是否被调、调了几次、参数是什么），Spy 在真实对象上**旁听**调用、不改变实现。
- **原理**：Stub 给依赖一个预设返回值，让被测代码能独立跑完；Mock 在返回值之外还记录调用轨迹，用来断言行为；Spy 包一层真实方法，可顺便断言 `toHaveBeenCalledWith`。
- **场景**：Jest 里 `jest.fn().mockResolvedValue(...)` 既是 Stub 也是 Mock；`jest.spyOn(obj, 'method')` 是 Spy，加上 `.mockResolvedValue` 就变 Stub。
- **边界**：只在需要验证"确实调了"时才用 Mock。把每个依赖都 Mock 一遍，测试就绑死在实现细节上——测的是"代码怎么写"，不是"代码对不对"。

### Q13: 什么是脚手架？核心流程是什么？（10-脚手架/01 篇）

- **结论**：脚手架是把"建项目骨架"自动化的 CLI：敲一条命令、交互式问答，然后生成一套填好变量的项目模板。
- **原理**：`bin/index.js` 里用 `inquirer` 收集参数（项目名、模板类型），用 `fs-extra` 的 `copy` 把 `templates/<类型>` 复制到目标目录，再把文件里的 `{{projectName}}` 占位符替换成真实值，最后打印 `cd xxx && npm install` 提示下一步。
- **边界**：模板可以来自本地目录，也可以从远程仓库下载；**装依赖通常不自己做**，而是交给用户——脚手架里跑安装会拉长等待、失败率还高。
- **追问**：`package.json` 里写 `"bin": { "create-my-app": "./bin/index.js" }`，文件顶部加 `#!/usr/bin/env node`，`npm link` 或全局安装后就能当命令用。

### Q14: `git merge` 和 `git rebase` 的区别？（11-进阶/07 篇）

- **结论**：`merge` 保留分支历史并生成一个合并提交；`rebase` 把你的提交**重放到**目标分支顶端，历史是线性的，但提交被改写了。
- **原理**：rebase 会为每个被搬运的提交算新的 hash——所以**已推送的公共分支绝对不能 rebase**，别人手里的旧提交还在，一推就分叉成两份历史。
- **场景**：个人 feature 分支想保持整洁、跟进 main 用 `git rebase main`；合并进 main 用 merge，或干脆在 PR 界面上 squash 成一个提交。
- **边界**：rebase 要逐提交解冲突（可能解多次），merge 只解一次。团队若用 squash merge，feature 分支上 rebase 的收益基本只剩"跟主线"。
- **追问**：`git cherry-pick` 是另一种"搬提交"——只挑单个提交到当前分支，常用于把热修复回移到发布分支。

### Q15: 缓存穿透、缓存击穿、缓存雪崩分别是什么？（11-进阶/02 篇）

- **结论**：穿透 = 查**不存在**的数据，每次都打到库；击穿 = **单个热点 key** 刚过期，大量请求同时打到库；雪崩 = **大批 key 同时过期**，库里压力暴增。
- **原理**：三者现象都是"数据库被打"，区分靠三点——key 存不存在、同时过期多少个、是不是同一个 key。
- **对策**：穿透用缓存空值（短 TTL）+ 布隆过滤器前置拦截；击穿用互斥锁重建或热点 key 逻辑过期（异步续期）；雪崩用过期时间加随机抖动 + 多级缓存 + 缓存集群。
- **边界**：任何一层缓存都要配降级——缓存整体不可用时是"放请求去数据库"还是"直接返回兜底值"，必须事先定好，不能等出事现场决定。

## 二、机制与原理

### Q16: Docker 多阶段构建为什么能给镜像瘦身？（09-部署/04 篇）

- **结论**：因为"构建用的环境不必进运行镜像"。多个 `FROM` 各自是独立阶段，最终镜像只 `COPY --from=<stage>` 拿产物，源码、devDependencies、编译工具链全留在前面的阶段。
- **原理**：单阶段 Dockerfile 会把源码、全量依赖、TypeScript / ESLint 全打进镜像（约 1GB）。多阶段拆成 `deps → build → prod-deps → runtime`：build 装全量依赖并编译出 `dist`，prod-deps 用 `--prod` 只装生产依赖，runtime 只复制 `dist` + 生产 `node_modules`，体积降到 200MB 上下。

```dockerfile
build      → 装全量依赖 + 编译，dist 留在第一阶段，不进最终镜像
prod-deps  → pnpm install --prod，去掉 TypeScript / ESLint / Jest
runtime    → COPY --from 只拿 dist + node_modules，无源码无工具链
```
- **收益**：瘦身直接换来部署传输更快、攻击面更小（镜像里没有编译器和源码）；还有一条间接收益是构建更快——`COPY package*.json` 在前、源码在后，依赖没变时那层缓存命中，直接跳过安装。
- **边界**：瘦身不等于安全。还要配 `USER node`（非 root 运行）、固定基础镜像版本（`node:20.16.0-alpine` 而非 `node:20-alpine`）保证可复现、`--frozen-lockfile` 保证各环境依赖版本一致。

### Q17: 生产环境为什么把基础设施和应用拆成两个 compose 文件？（09-部署/05 篇）

- **结论**：因为两者**生命周期不同**——数据库几年不动，应用天天更新。绑在一个文件里，每次发版都得担心数据库被顺带重启。
- **原理**：拆成 `docker-compose.infra.prod.yml`（MySQL + Redis，一次性 `up -d` 之后不管，配 `restart: always`、数据挂宿主机目录、Redis 开 `--appendonly yes --appendfsync everysec`）与 `docker-compose.prod.yml`（migration + 应用，日常部署）。
- **收益**：部署模式可切换——数据库可以自建 Docker、可以上云 RDS、可以混合，切换时只改 `.env`（`DB_HOST` 换成 `host.docker.internal` 或云地址），编排文件一行不动。
- **边界**：拆开后两个 compose 文件要靠**显式命名的网络**（`name: show_track_net`）才能互通；另外应用端口只绑 `127.0.0.1:${APP_PORT}`，对外只留 Nginx 一个入口，安全面才最小。

### Q18: `depends_on` 的 `service_completed_successfully` 解决什么问题？（09-部署/05 篇）

- **结论**：默认 `depends_on` 只保证依赖容器**启动了**，不保证服务**就绪**；`condition: service_completed_successfully` 保证依赖**成功跑完并退出**，专门用来串一次性的迁移 Job。
- **原理**：迁移 Job 与业务容器**共用同一个镜像**，只把 `entrypoint` 换成迁移脚本、`restart: 'no'`（一次性，失败不重试）。应用侧声明 `depends_on: migration: condition: service_completed_successfully`，迁移失败应用根本不会启动。
- **边界**：长驻服务要用 `condition: service_healthy`（配 `healthcheck`），而不是 `service_completed_successfully`；`depends_on` 也只管单机 Compose 内的顺序，跨服务 / 跨宿主机要靠健康检查或重试逻辑。
- **追问**：为什么不让应用启动时自己跑迁移？多实例并发跑会锁冲突、写脏数据；而且应用有 bug 时迁移也跑不了，表结构该修却修不了。

### Q19: PM2 的 cluster 模式和 Node 自身的 cluster 是什么关系？（09-部署/03 篇）

- **结论**：是**同一套东西**。PM2 的 cluster 模式底层就是 Node 原生 `cluster` 模块——主进程按 `instances` 起多个 worker，worker 监听同一端口，由主进程做轮询（Round-Robin）分发。
- **原理**：所以 `instances: 'max'` 等于"按 CPU 核数起进程"，`pm2 start app.js -i max` 会让 `pm2 list` 出现 N 个同名进程；PM2 在原生 cluster 之上加了崩溃自动重启、日志收集、内存超限重启。
- **代价**：进程之间内存**不共享**——Session、内存缓存、单机限流计数器都不能放在进程内，必须外置到 Redis。
- **边界**：cluster 只在 Linux / macOS 裸机上合适；Windows 上行为异常，容器里也不该用（见下一题）。

### Q20: Docker 容器里为什么用 fork 而不是 cluster？（09-部署/03 篇）

- **结论**：容器内 cluster 等于"在编排平台之上再自己做一层负载均衡"，既重复又有害。
- **原理**：容器编排（Compose 多副本 / K8s）本就是水平扩展那一层，容器里再开 N 个进程只会让资源计量、健康检查、信号（`SIGTERM` 该发给谁）全部变复杂。所以生产 `ecosystem.config.js` 写 `exec_mode: 'fork'` + `instances: 1`，PM2 只保留进程监控、日志管理、`max_memory_restart` 三项职责。
- **边界**：反过来，**没有编排平台的 Linux 裸机**才该用 cluster 吃满多核；Windows 或单机小项目 fork 单实例就够。
- **追问**：这也是 `pm2 reload` 在容器内没意义的原因——单进程 fork 没有"逐个重启 worker"的余地，滚动更新交给编排平台。

### Q21: PM2、Docker、Nginx 三者在生产里各管什么？（09-部署/03 篇）

- **结论**：Nginx 管**入口**（收请求、SSL 终结、静态资源、反向代理、负载均衡），Docker 管**环境与隔离**（一次构建到处运行、服务编排），PM2 管**容器内的 Node 进程**（故障恢复、内存限制、日志收集）。
- **原理**：三者不重叠也不互相替代。典型链路是：用户 → 宿主机 Nginx（唯一公网入口）→ Docker 容器（内跑 PM2 fork 单进程）× N 副本 → MySQL / Redis。
- **边界**：职责会随架构演进漂移——裸机时代 PM2 是"负载均衡器 + 进程管家"，有了容器编排后它退化成"容器内的进程管家"。判断"某件事该谁做"的口径就是一句：**看这一层是否已经有人做了**。
- **追问**：那"多核利用"归谁？裸机交给 PM2 cluster，容器里交给副本数，别两边都做。

### Q22: `synchronize: true` 为什么是生产环境的定时炸弹？（09-部署/07 篇）

- **结论**：因为它让"改 Entity"直接等于"改生产表结构"，而生产的表里全是真数据。
- **原理**：四个后果——**不可审计**（谁改的、何时改的无从追溯）、**不可回滚**（出问题只能手工修）、**数据丢失**（Entity 删字段 → 重启 → 列被删，数据永久没了）、**不可审查**（变更进不了 Code Review）。
- **附加伤害**：它还会让迁移机制失效——库已经和实体同步，`migration:generate` 对比不出任何差异，等于这条路被自己堵死。
- **边界**：`synchronize: true` 只适合早期原型。进入协作开发就得关掉，表结构变更全部由迁移文件控制；本地开发改成"改 Entity → `migration:generate` → `migration:run` → 起应用"。

### Q23: 迁移为什么"天生幂等"？跑多少遍都安全吗？（09-部署/07 篇）

- **结论**：安全。因为 TypeORM 在库里维护一张 `migrations` 表记录已执行过的迁移，`migration:run` 每次都先对比，只跑没执行过的。
- **原理**：执行流程是——连库 → 检查（不存在则创建）`migrations` 表 → 读 `dist/migrations/*.js` → 对比已执行记录 → 按时间戳顺序执行未跑过的 `up()` → 每执行完插一条记录。没有待执行迁移时直接输出 `"No migrations are pending"` 退出。
- **保证**：每个 `up()` / `down()` 默认包在事务里，某个迁移失败会整体回滚，不会留下半完成的表结构。但**已成功的迁移不会自动回滚**（`migrations` 表已有记录），要撤销必须显式 `migration:revert`。
- **边界**：已有数据不会被框架触碰——除非某个 `up()` 里显式写了 `DROP` / `DELETE` / `TRUNCATE`。所以破坏性变更必须人工确认，不能进自动流水线。

### Q24: 迁移为什么必须独立于应用启动、并与业务容器分离？（09-部署/07 篇）

- **结论**：因为"迁移该在应用之前、且只跑一次"，而"应用可能多副本、可能起不来"。
- **原理**：两个理由——① 多实例部署时每个业务容器都跑迁移会**并发锁冲突、产生脏数据**；② 应用有 bug 起不来时，表结构该修还是得能修，所以迁移 CLI **不经过 NestJS DI 容器**，只依赖编译产物 + 环境变量：`node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`。
- **落地**：拆成一个一次性 Job 容器，与业务共用镜像、只换 entrypoint，`restart: 'no'`，业务容器 `depends_on` 它 `service_completed_successfully`。
- **边界**：三个 DataSource 的分工要分清——本地迁移用 TS 源码（免 build）、生产迁移用 `dist/**/*.js`（免 ts-node）、应用运行时由 `@nestjs/config` 加载；三者的 `synchronize` 都应为 `false`。

### Q25: 装了 Nginx 之后，应用为什么拿不到真实客户端 IP？（09-部署/06 篇）

- **结论**：因为请求是 Nginx 转发过来的，应用看到的来源地址就是 Nginx 的地址。真实 IP 只能靠代理头带过来。
- **原理**：Nginx 侧要显式 `proxy_set_header X-Real-IP $remote_addr` 和 `X-Forwarded-For $proxy_add_x_forwarded_for`（后者会在已有值后追加，形成完整转发链）；应用侧再从这两个头里取。
- **影响面**：不解析代理头会让**日志、限流、风控、黑名单全部失真**——所有请求看起来来自同一个 IP，按 IP 限流会直接限死全站。
- **边界**：`X-Forwarded-For` 客户端可伪造，只应信任你自己那层代理追加的值；多级代理下按固定跳数取。Nest / Express 里要配 `trust proxy`，`req.ip` 才会是真实客户端 IP。

### Q26: `acks` 0 / 1 / -1 分别意味着什么？怎么选？（11-进阶/01 篇）

- **结论**：`acks` 控制生产者等几层确认——`0` 不等（最快、可能丢）、`1` 等 Leader 写入（默认、折中）、`-1`（`all`）等所有 ISR 副本写入（最安全、最慢）。
- **原理**：`acks=1` 的漏洞在于 Leader 刚写完、还没同步给 Follower 就宕机；`acks=-1` 要求所有同步副本都落盘才返回，持久性最强。
- **场景**：日志 / 埋点这类容忍少量丢失用 `0`；核心交易用 `-1`，但必须同时设 `min.insync.replicas >= 2`、`replication.factor >= 3`，否则"所有 ISR"可能只剩 Leader 一个副本，等于白设。

```ini
acks=0      # 日志、埋点、指标：可容忍少量丢失，吞吐最高
acks=-1     # 订单、支付：等所有 ISR 副本确认，最安全
min.insync.replicas=2                 # 至少 2 个同步副本确认才算成功
replication.factor=3                  # 每个分区 3 个副本
unclean.leader.election.enable=false  # 不让非 ISR 副本选成 Leader
```
- **边界**：`acks=-1` 不等于绝对不丢（所有 ISR 都宕机时仍可能丢），而且明显降低吞吐；`min.insync.replicas` 设过高时副本不足会**直接拒绝写入**。

### Q27: 消息不丢失要在哪三端做保障？（11-进阶/01 篇）

- **结论**：生产端、Broker 端、消费端各做一段，缺一段链路就断——没有"某一端开了就万无一失"的开关。
- **原理**：**生产端**设 `acks=-1`、开启重试（`retries > 0`）、确认发送结果（同步或回调），不要 fire-and-forget；**Broker 端**设 `replication.factor >= 3`、`min.insync.replicas >= 2`、`unclean.leader.election.enable=false`（不让非 ISR 副本选成 Leader）；**消费端**关掉 `enable.auto.commit`，业务处理**成功之后**再手动提交 offset。
- **代价**：严格不丢必然降吞吐，而且生产端重试会带来**重复消息**——所以"不丢"的另一半是幂等，通常用业务唯一键 + 去重表处理。
- **边界**：消费端的正解是"至少一次 + 幂等"，不要指望中间件给你"恰好一次"；offset 提交与业务写库不在同一事务里，崩溃点就只能靠幂等兜住。

### Q28: 单例和工厂模式在 NestJS 里怎么体现？（11-进阶/05 篇）

- **结论**：单例是 **DI 容器的默认作用域**（`@Injectable()` 不写 scope 就是单例），工厂是**自定义 Provider 的 `useFactory`**。
- **原理**：容器首次解析某 Provider 时创建实例并缓存，之后所有模块注进来的都是同一个（构造函数只执行一次）；`useFactory` 把"怎么造这个对象"交给一个函数，函数可声明 `inject` 依赖、可 async，适合"要读配置才能造""要异步建连接"的对象。
- **场景**：`{ provide: 'CACHE_OPTIONS', useFactory: (cfg: ConfigService) => ({ host: cfg.get('REDIS_HOST'), port: cfg.get('REDIS_PORT') }), inject: [ConfigService] }`。
- **边界**：`useFactory` 造出来的实例默认也是单例（除非显式配 scope）；有状态的服务（请求级缓存、请求上下文）不能挂单例，否则一个请求写的数据会被下一个请求看到——该用 `Scope.REQUEST` 或显式传参。

### Q29: 策略、观察者、装饰器模式在 NestJS 里怎么体现？（11-进阶/05 篇）

- **结论**：**策略** = 统一接口 + 多个实现 + 运行时按条件选（Guard 与自定义 Provider 常用于此）；**观察者** = `@nestjs/event-emitter` 的 `emit` / `@OnEvent`；**装饰器** = 整个框架的骨架（`@Controller()` / `@Module()` / `@Injectable()` / `@Get()` / `@UseGuards()`）。
- **原理**：策略模式常见两种落地——注入单个策略（`@Inject('AUTH_STRATEGY')`），或把所有策略收进 `Map` 按 `type` 取，直接消掉一长串 `if/else`；观察者模式里发布方 `this.eventEmitter.emit('order.created', order)`，监听方 `@OnEvent('order.created')`，发布方完全不知道谁在听。
- **边界**：观察者模式解耦的代价是调用链变隐式——"谁处理了这个事件"要全局搜事件名，事件一多就难调试；监听器里抛异常还可能影响主流程，要单独兜住。
- **追问**：装饰器本质是给类和属性附加元数据，Nest 启动时用 `Reflector` 读元数据决定行为；多个装饰器的执行顺序是从下到上、从右到左。

### Q30: 一次请求的全链路日志是怎么串起来的？（09-部署/02 篇）

- **结论**：靠一个贯穿请求生命周期的 trace ID——入口分配、异步上下文里随处可取、每条日志自动带上。
- **原理**：用 `nestjs-cls`（基于 `AsyncLocalStorage`）给每个请求分配 ID，`LoggerService` 在写日志前把它拼进消息并放进结构化字段（`{ context, traceId }`），排查时 `grep "<trace-id>" logs/app.<date>.log` 就能拉出这次请求从入口到数据库的完整路径。
- **边界**：trace ID 只在**异步上下文能传下去**的前提下有效——手动 `new` 的任务或未传上下文的地方可能取不到；跨进程要把它放进消息头传下去。
- **追问**：日志落盘要按日轮转（`DailyRotateFile`）+ 错误日志独立文件（`app-error.%DATE%.log`），再加 `auditFile` 记录轮转状态——否则容器重启会重复处理旧文件。

### Q31: CI/CD 为什么拆成 build 和 deploy 两条流水线？（09-部署/09 篇）

- **结论**：因为"构建"和"部署"是两件事，触发条件和失败后果都不同。拆开后构建失败不会触发部署，deploy 还能在**多台服务器上复用**。
- **原理**：build 由 `push: tags: ['v*']` 触发，在云端构建镜像并推两个 tag——`stable`（最新稳定版）和 `v1.0.0`（此版本）；deploy 由 `workflow_run: types: [completed]` + `if: conclusion == 'success'` 触发，SSH 到服务器执行 `docker compose pull` + `up -d`。
- **收益**：**构建从服务器挪到云端 CI**——服务器只拉镜像、重启容器，不再装依赖、不再编译，压力大幅下降；回滚变成"用旧 tag 再部署一次"，秒级完成。
- **边界**：镜像 tag 必须唯一可追溯（版本号与构建时间通过 `ARG` / `LABEL` 写进元数据），否则回滚时不知道回到的是哪份代码；Secrets 要建专用部署密钥对，不要复用日常账号。

## 三、排障与选型

### Q32: 生产环境的日志怎么查？三种方式分别什么时候用？（09-部署/02 篇）

- **结论**：三层——`docker logs` 看实时与启动、容器内**文件日志**查历史与按级别过滤、`pm2 logs` 查进程管理问题。
- **原理**：三者数据源不同。`docker logs` 读容器 stdout（PM2 捕获的控制台输出）；文件日志是 Winston 写进 `/app/logs` 的 JSON（已持久化到命名卷）；`pm2 logs` 读 PM2 的内存缓冲区。
- **速查**：容器是否正常启动 → `docker logs <c> --tail 20`；实时跟随 → `docker logs -f <c>`；最近一小时 → `--since 1h`；今天的所有错误 → `cat logs/app-error.$(date +%Y-%m-%d).log`；找某接口 → `grep "POST /api/xxx" logs/app.$(date +%Y-%m-%d).log`；带上下文搜错误 → `grep -C 2 '"level":"error"'`。
- **判断依据**：**实时用 stdout，历史用文件**——`docker logs` 与 `pm2 logs` 都会随容器重启丢失，只有文件日志留得住。

### Q33: Nginx 报 502 和 504，分别往哪查？（09-部署/06 篇）

- **结论**：502 是"连不上 / 上游给的不是合法响应"，504 是"连上了但**超时**没等到响应"。
- **原理**：502（Bad Gateway）常见于后端进程没起、端口写错、容器挂了——Nginx 压根没拿到响应；504（Gateway Timeout）说明连接建立了，但处理时间超过 `proxy_read_timeout`。
- **排查顺序**：先确认后端活着（`docker ps`、`curl 127.0.0.1:3000/api/health`），再看 Nginx `error.log` 区分是 connect refused（→ 502，进程 / 端口问题）还是 upstream timed out（→ 504，慢查询 / 死循环 / 外部依赖卡住）。
- **边界**：应用只绑 `127.0.0.1` 时 Nginx 必须转发到宿主机回环地址，写成容器 IP 就会 502；有长连接（WebSocket）或慢接口时要调 `proxy_read_timeout` / `proxy_send_timeout`，否则正常的慢请求也会被当 504。

### Q34: 容器起来就反复重启，你怎么定位？（09-部署/08 篇）

- **结论**：按"容器活着吗 → 健康吗 → 应用说什么 → 是不是依赖的问题 → 是不是被重启过"五步走，不要一上来改代码。
- **原理**：`docker logs <c> --tail 50` 看启动报错；`docker inspect <c>` 看 `State.Health.Status` 和 `ExitCode`；再到 MySQL 容器日志、`pm2 logs <app> --lines 50 --nostream` 看是否被内存超限重启。
- **常见根因**：数据库未就绪（迁移 Job 没跑完 / `wait-for-it` 没配）、环境变量缺失（启动校验直接抛错，比如 `JWT_SECRET` 没配）、端口冲突、健康检查失败（应用起来了但 `/api/health` 依赖的 Redis 不通）。
- **边界**：健康检查必须做**端点级**而不是端口级——端口通只说明进程活着，接口能返回 200 才说明它依赖的库与缓存都就绪了。

### Q35: Kafka 和 RabbitMQ 怎么选？（11-进阶/01 篇）

- **结论**：看两个维度——**吞吐量 vs 路由灵活性**。要百万级吞吐、流式处理选 Kafka；要灵活路由、低延迟、完善确认机制选 RabbitMQ。
- **原理**：Kafka 是拉模型 + 顺序写盘 + 批量压缩，吞吐极高，靠分区并行消费；RabbitMQ 是推模型，支持 direct / topic / fanout / headers 多种交换机，路由灵活，ACK/NACK 与死信、延迟队列成熟，但吞吐通常在万级。
- **场景**：日志收集、埋点、指标、流计算 → Kafka；订单处理、任务分发、通知推送、异步 RPC → RabbitMQ；只是解耦一个简单异步任务、又已经有 Redis → Redis Stream 最省事。
- **边界**：别只看吞吐。还要看团队运维能力（Kafka 高可用集群有成本）、顺序要求（Kafka 只保证分区内有序）、是否需要延迟消息（RabbitMQ 有现成方案）。

### Q36: 限流算法怎么选？（11-进阶/02 篇）

- **结论**：要**允许突发**用令牌桶；要**绝对平滑**用漏桶；要**统计精确**用滑动窗口；只图快用固定窗口计数器（有边界突刺）。
- **原理**：计数器在固定窗口内计数，简单但窗口交界处能放过两倍流量；滑动窗口把小时间片加起来，精度高、内存与计算开销大；令牌桶按固定速率放令牌、桶满丢弃，桶容量决定允许多大突发；漏桶无论进来多少都匀速流出，是"整流"而非"限流"。
- **场景**：普通 API 首选令牌桶（能吸收秒杀峰值）；登录 / 短信这类敏感接口用固定窗口计数器配极低阈值就够；需要严格保护下游时用漏桶。
- **边界**：单机限流用进程内计数器即可，**多实例必须走 Redis**，并且要用 Lua 脚本把"取数 + 判断 + 写回"做原子，否则每个副本各限一份，总量是 N 倍。

### Q37: SQL 注入、XSS、CORS 各在哪一层防？（11-进阶/03 篇）

- **结论**：SQL 注入防在**数据访问层**（参数化查询），XSS 防在**输出层**（编码），CORS 配在**响应头层**（服务端声明允许的来源）。
- **SQL 注入**：`pool.query('SELECT * FROM users WHERE id = ?', [id])`——参数化让输入永远只是数据、不参与 SQL 语法解析，ORM 默认这么做；拼接字符串（`` `... id = ${id}` ``）才是漏洞源头。
- **XSS**：根源是**输出未编码**，不是输入没校验。HTML 输出时把 `<` `>` 等转义（模板引擎与 React 的插值默认转义），再用 `Content-Security-Policy` 和 `HttpOnly` Cookie 兜底；`dangerouslySetInnerHTML` / `v-html` 是破坏默认转义的入口。
- **CORS**：浏览器同源策略的例外机制，服务端用 `Access-Control-Allow-Origin` 声明允许的来源，复杂请求（PUT / DELETE / 自定义头）会先发 `OPTIONS` 预检。
- **边界**：CORS 是**浏览器侧**限制，服务端到服务端的请求不受它管，别把它当 API 鉴权；`credentials: true` 时不能用 `*`，生产要写具体域名。输入校验（`ValidationPipe` 的 `whitelist`）是必需的基础防线，但它替代不了输出编码。

### Q38: 缓存预热和缓存降级怎么做？（11-进阶/02 篇）

- **结论**：预热 = 系统启动 / 上线时**主动**把热数据灌进缓存，避免冷启动时请求全打库；降级 = 压力超阈值时**主动关掉非核心功能**，把资源让给核心链路。
- **原理**：预热在 `onApplicationBootstrap` 里查热点数据写 Redis，配合理过期时间与异步刷新；降级靠开关（配置中心或本地配置）在 CPU / QPS 超阈值时直接返回缓存值或默认值。
- **边界**：预热的数据量要控住——全量预热会拖慢启动，接口半天不 ready；降级必须**可自动恢复**，只做"关"不做"开"的开关，流量回落后还得人工兜。
- **追问**：降级开关放配置中心还是本地？配置中心改起来快但有网络依赖（拿不到配置时按"降级"还是"不降级"兜底要先定），本地配置可靠但改一次要重启。

### Q39: 热点 Key 怎么解决？（11-进阶/02 篇）

- **结论**：核心是"别让所有请求挤在同一个 key / 同一个节点上"。四种手段：本地缓存、key 复制分散、读写分离、分片集群。
- **原理**：热点 key（大促爆款、热搜）在 Redis 单线程模型下会串行处理，把这个节点打满，还容易触发击穿。**本地缓存**挡掉绝大部分读；**key 复制**把 `hot:item` 拆成 `hot:item:0..N`，请求随机打一个副本；**读写分离**把读流量分到从节点；**Cluster** 从 key 层面先散开。
- **边界**：本地缓存带来**多实例数据不一致**（各机副本过期时间不同），只适合"能容忍几秒延迟"的热点；key 复制抬高写入成本与内存占用，写一次要写 N 份。
- **追问**：怎么自动发现热点 key？服务端用采样统计，客户端统计 key 访问频次上报——不要靠人工猜。

### Q40: 什么时候该拆微服务？拆分原则是什么？（11-进阶/06 篇）

- **结论**：按**业务边界**拆，不按技术分层拆。四条原则：高内聚低耦合、单一职责、**数据独立**（各自一个库）、独立部署与扩展。
- **原理**：每个服务对应一个业务域（用户 / 订单 / 商品 / 支付 / 通知），服务间只通过 API 或消息队列通信，**不允许跨服务直连数据库**——一旦共享库，拆开就形同虚设。
- **判断依据**：该拆的信号是"某个模块的变更频率、扩缩容需求或团队归属明显和其他部分不同"；这些都没出现时，单体 + 清晰模块划分的收益更大。
- **边界**：拆早了代价很重——分布式事务、服务发现、链路追踪、跨服务调试全都要提前付；拆太细会变成"微服务地狱"，一个业务动作要串五六个服务。

### Q41: 高可用要靠哪几类机制组合？（11-进阶/06 篇）

- **结论**：五类——**冗余部署、负载均衡、健康检查、熔断降级、限流**；再配上**进程守护**与**优雅退出**，才形成闭环。
- **原理**：多副本 + 负载均衡解决"单点"；健康检查负责把故障实例自动摘除；熔断降级让下游故障不拖垮自己；限流防止突发流量打穿。进程守护（PM2 `autorestart` / 容器 `restart: always`）保证崩溃能自愈；优雅退出（接住 `SIGTERM` → 停收新连接 → 等在途请求归零 → 关依赖 → 退出）保证发布不丢请求。
- **边界**：**别忘了依赖也是单点**——数据库、Redis、消息队列的高可用要单独设计；应用层做得再好，一个单机 MySQL 挂掉照样全站不可用。
- **追问**：容器 / K8s 滚动发布默认发 `SIGTERM`，应用没接住就会出现"发布期间零星 502"。

### Q42: 线上发版出问题怎么回滚？破坏性迁移为什么不自动跑？（09-部署/09 篇）

- **结论**：回滚 = **用旧版本的 tag 再走一次部署**（拉旧镜像 + 重启容器），秒级完成。破坏性迁移（`DROP` / 重命名）因为**不可逆**，必须人工确认后手动执行。
- **原理**：镜像打了 `stable` 和 `v1.0.0` 两个 tag，回滚时把旧版本 tag 推上去触发同一套流水线，`docker compose pull` + `up -d` 用旧镜像重建容器。
- **边界**：回滚不是万能的——**已经执行的迁移不会跟着回滚**。"代码回滚 + 列已经删了"这种组合是灾难，所以破坏性变更要和代码发布**分开发**，顺序是"先做兼容（新代码同时兼容新旧表结构）→ 再清理旧字段"。
- **判断依据**：安全迁移（新增表 / 字段 / 索引）可以进自动流水线；删除 / 重命名这类必须人工看一眼再执行。

### Q43: 从零到线上，一次完整的部署要做哪些事、怎么验证？（09-部署/08 篇）

- **结论**：主线是"配置 → 起基础设施 → 跑迁移 → 起应用 → 接 Nginx → 验证"。动手前先记住核心原则——**数据库与缓存是外部服务，compose 堆栈只管 migration + 应用**。
- **首次部署**：`cp .env.example .env.production` 填真实值 → `docker compose -f docker-compose.infra.prod.yml up -d`（一次性，之后不管）→ `docker compose -f docker-compose.prod.yml up -d --build`（日常命令）→ 配 Nginx 反代到 `127.0.0.1:3000`。
- **那条 `up -d --build` 背后发生的事**：五阶段 Dockerfile 构建镜像 → migration 容器 `wait-for-it` 等 MySQL 就绪后 `migration:run` → 应用容器等迁移成功才启动 → 容器内 PM2 fork 拉起 NestJS → `HEALTHCHECK` 周期探 `/api/health`。
- **日常迭代**：`git pull` + 同一条 `up -d --build`；Compose 会先起新容器、**健康检查通过后再停旧容器**，单机环境下相当于一次滚动更新。
- **验证清单**：镜像有新 tag → `docker images`；迁移无 ERROR → `docker compose logs migration`；容器健康 → `docker inspect` 看 `State.Health.Status`；接口通 → `curl 127.0.0.1:3000/api/health`；日志在写 → `docker exec <app> ls /app/logs/`；外部入口通 → `curl https://<域名>/api/health`。
- **边界**：备份必须独立于部署单独验证——自建 MySQL 靠宿主机目录 + 定时 `mysqldump`，云库靠云服务方；生产至少每日全量，"部署成功"和"有备份"是两件事。
- **追问**：回滚虽然能秒级切回旧镜像，但**数据层回不去**——所以破坏性迁移要先做兼容（新代码同时兼容新旧表结构），确认稳定后再清理旧字段。

### Q44: 脚手架为什么用 yargs / commander 而不是自己解析 `process.argv`？（10-脚手架/01 篇）

- **结论**：因为参数解析的"脏活"全在边界情形上，而不在 `argv` 取值本身；专业库已经把这些情形处理完了。
- **原理**：`process.argv` 拿到的是原始字符串数组，位置参数、`--option value` 与 `--option=value`、短别名（`-t api`）、布尔开关、默认值、类型转换、非法值报错、`--help` 生成——每一条都得自己写；yargs 用 `command` + `positional` + `option` 声明式描述，自带 `choices` 校验与 `help()` 输出。
- **场景**：`yargs(hideBin(process.argv)).command('create <name>', '创建新项目', b => b.positional('name', { type: 'string' }).option('template', { alias: 't', choices: ['basic', 'api'], default: 'basic' }), argv => {...}).help()`。
- **边界**：参数十几个、子命令三四个以上时，声明式的收益才明显；参数极少的内部脚本直接读 `process.argv[2]` 反而更清楚，不必为了"规范"引入依赖。
- **追问**：交互式问答（inquirer）和参数式（yargs）是两条并列入口——CI 里没有 TTY，脚手架必须支持全参数化执行，否则在流水线里直接用不了。

## 四、场景设计题

### Q45: 场景题：为生产环境的 Node 应用设计一套健康检查与监控方案（09-部署/02·04·08 篇）

- **题目要求**：服务要能自证"活着且有依赖可用"；异常要能被外部探针发现并自动摘除 / 重启；关键指标超阈值要告警。
- **健康检查端点**：`GET /api/health` 返回 `{ status, uptime, timestamp }`，并顺带探依赖——数据库连接池状态、Redis 连通性；任一依赖不可用返回 **503**，同时在 JSON 里标出具体哪个组件 `status: 'down'`。
- **容器层**：Dockerfile 里写**端点级** `HEALTHCHECK`（不是端口探测），`--start-period` 留给迁移与缓存预热：

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=40s --retries=3 \
  CMD wget --no-verbose --tries=1 --spider http://localhost:$APP_PORT/api/health || exit 1
```

- **编排层**：Compose 中依赖它的服务用 `depends_on: condition: service_healthy`；探针失败由编排平台负责重启或摘掉流量。
- **进程层**：PM2 侧配 `max_memory_restart: '1G'`，内存超限自动重启，防内存泄漏把机器拖垮；`autorestart: true` 再兜一层未捕获异常导致的退出。
- **指标采集**：用 `process.memoryUsage()` 看 `heapUsed` 是否持续上涨不回落（内存泄漏信号），用事件循环延迟与 `process.hrtime` 判断主线程是否被占住，用 `os` 模块采 CPU 与内存使用率定期上报。
- **告警阈值**：CPU > 80%、内存 > 80%、事件循环延迟 > 200ms、5xx 错误率 > 1%，超阈值走 Webhook 推给值班人。
- **为什么这么设计**：健康检查必须是**端点级**而不是端口级——端口通只说明进程还在，接口能返回 200 才说明依赖的库与缓存都就绪；一个端点同时服务探针、编排平台和值班人，避免"三个地方三种健康定义"。
- **边界与代价**：健康检查**不能查重依赖或做慢操作**，否则探针自己成了压力源（比如每次都 `SELECT` 大表）；`start-period` 要留给迁移和缓存预热；告警阈值先宽松再收紧，否则上线第一周全在响，很快就会被屏蔽。
- **追问**：健康检查还分用途——给编排平台判断"要不要重启容器"的，和给负载均衡判断"要不要摘掉这个实例"的，后者可以更严格（含依赖探测），前者只该反映进程自身状态。

### Q46: 场景题：下单成功后异步通知商家、扣库存、发短信，怎么设计？（11-进阶/01 篇）

- **题目要求**：下单接口不能被短信、库存、商家通知拖慢；这些动作要可靠——丢了能重试，重试了不能重复执行。
- **选型**：要可靠投递 + 灵活路由 → RabbitMQ；已有 Redis 且只想解耦一个轻量任务 → Redis Stream；要极高吞吐或事件流回放才上 Kafka。
- **消息结构**：`{ eventType: 'order.created', orderId, timestamp, traceId }`——带上 `traceId` 才能和下单请求的日志串起来。
- **生产者**：订单**写库成功后**再发消息到 `exchange: order`，路由键 `order.created`；"写库"与"发消息"不在同一个事务里，要用本地消息表（事务性发件箱）保证最终一致，否则会出现"订单建了、消息没发"。
- **消费者**：拆成多个队列各自消费——`sms` 队列发短信、`merchant` 队列推站内信或长连接推送、`inventory` 队列扣库存；彼此独立，一个挂了不影响其他。
- **确认与重试**：手动 ACK——成功 `channel.ack(msg)`，失败 `channel.nack(msg, false, true)` 重新入队；重试超过 3 次进死信队列（DLQ）转人工处理。
- **幂等**：用 `orderId + eventType` 做唯一键（Redis `SETNX` + 过期时间，或数据库唯一索引），命中即 ACK 跳过：

```js
const key = `processed:order:${orderId}`;
if (await redis.get(key)) return channel.ack(msg);  // 已处理过，直接确认
await handle(orderId);                              // 业务处理
await redis.setex(key, 86400, '1');                 // 记下"已处理"
channel.ack(msg);
```

- **为什么这么设计**：
  - 让"用户等待"缩到只剩下单本身，其余全部异步——下单接口的耗时不再受下游 SDK 抖动影响。
  - 可靠性与幂等分开处理：中间件只负责"至少一次送到"，"重复了也不出错"是业务自己的责任；把这两件事分开，才能各自选最合适的方案。
- **边界与代价**：至少一次投递必然带来重复，所以幂等不是可选项；死信队列必须有人看，只积压不处理等于消息丢了。
- **边界与代价**：要监控队列积压量——积压是"消费者已经跟不上"的第一信号；扩容要按分区 / 队列数来，盲目加实例会得到一堆空闲消费者。
- **追问**：要保证同一订单的事件按序处理，就用 `orderId` 做分区键 / 队列路由，让同一订单的消息走同一条通道。

### Q47: 场景题：用 Docker Compose 部署 Node + MySQL + Redis，怎么落地？（09-部署/04·05 篇）

- **题目要求**：一条命令拉起三个服务；服务间能互相访问；数据不能因容器重建而丢；敏感配置不能进镜像。
- **应用镜像**：多阶段构建——build 阶段装全量依赖并编译，prod-deps 阶段 `pnpm install --prod --frozen-lockfile`，runtime 只 `COPY --from` 拿 `dist` 与生产依赖；基础镜像固定版本（`node:20.16.0-alpine`），并 `USER node` 非 root 运行。
- **服务划分**：基础设施与应用分开编排——`infra.prod.yml` 管 MySQL / Redis（`restart: always`），`prod.yml` 管 migration + 应用（日常部署）。
- **网络**：所有服务加入同一个**显式命名**的自定义网络（`name: show_track_net`），容器之间直接用服务名互访；应用端口只绑 `127.0.0.1:${APP_PORT}`，对外只留 Nginx。
- **启动顺序**：`depends_on` + `condition` 双保险——等 MySQL 用 `service_healthy`，等迁移用 `service_completed_successfully`。

```yaml
depends_on:
  mysql:
    condition: service_healthy        # 等健康检查通过，而不是等容器启动
  migration:
    condition: service_completed_successfully  # 迁移成功跑完才启动应用
```

- **数据持久化**：MySQL 挂宿主机目录（`./__data/mysql:/var/lib/mysql`）；Redis 开 `--appendonly yes --appendfsync everysec`（每秒刷盘，崩溃最多丢 1 秒）并挂 `./__data/redis:/data`；应用日志挂 named volume。
- **配置注入**：走 `env_file: .env.production`，`.env*` 进 `.gitignore`，只提交 `.env.example`——镜像里不含任何密钥。
- **为什么这么设计**：
  - Compose 的价值是把"网络、卷、启动顺序、环境变量"变成可版本化的声明，`docker run` 时代这些全靠人记；写进文件之后，一份编排能在开发、测试、生产之间复用。
  - 基础设施单独一份，是为了让"切到云 RDS"只需改 `.env` 而不动编排文件——**把变化点收敛到配置里**。
  - 迁移用"共用镜像、只换 entrypoint"的方式做成 Job，而不是另写一个脚本镜像，才能保证"迁移用的代码"和"跑起来的代码"始终是同一个版本。
- **边界与代价**：`depends_on` 只解决单机内的顺序问题，多副本 / 跨宿主机要靠健康检查 + 重试逻辑兜。
- **边界与代价**：Compose 是单机编排，要跨机器、要自动扩缩容就得换 K8s；迁移 Job 的 `restart: 'no'` 意味着失败就是失败，必须有告警或人工介入，不能指望它自愈。
- **边界与代价**：数据库放进容器等于把备份、扩容、升级、主从的运维责任全拿回来；自建只适合小规模或学习环境，生产更推荐云 RDS + 定期 `mysqldump` 双保险。
- **追问**：容器之间用服务名互访靠的是 Compose 自动建的 DNS，所以**服务名不能随便改**——改一次要同步改所有引用它的环境变量。

### Q48: 场景题：多个 Node 实例的日志怎么统一收集、存储、查询？（09-部署/02 篇）

- **题目要求**：实例横向扩到 N 个后，日志不能再"一台台登上去看"；要能按服务、按时间、按请求 ID 查；还要控制磁盘增长。
- **应用侧输出**：用 Winston（或 Pino）输出**结构化 JSON**，字段固定为 `timestamp / level / serviceName / requestId / message / stack`；请求日志由中间件统一记（方法、URL、状态码、耗时），业务代码不再手拼字符串。
- **分级与轮转**：生产 `LOGGER_LEVEL=info`（debug / verbose 直接丢），用 `winston-daily-rotate-file` 按天切文件、保留 30 天；错误单独落 `app-error.%DATE%.log`，配 `auditFile` 记录轮转状态。
- **采集**：每个容器跑 Filebeat sidecar（或 DaemonSet）监听日志文件，把新内容送到 Elasticsearch / Logstash——应用只管写文件，不关心谁在采集，这是解耦的关键。
- **存储与索引**：ES 按天建索引（`app-logs-2026.09.06`），配 ILM 生命周期策略，30 天后归档或删除，避免磁盘被日志吃满。
- **查询与可视化**：看板展示错误率趋势、接口响应时间分布、Top 慢接口；按 `requestId` 能拉出单次请求的全链路。
- **成本控制**：采样与分级并存——高频只读接口的请求日志按比例采样，错误日志一律全量；这样总量可控，排查时又不缺关键证据。
- **为什么这么设计**：
  - 应用只做"写好结构化日志"这一件事，采集、传输、存储、检索全部外置——换存储（ES → 其他）不用改一行业务代码。
  - 采集用 sidecar 而不是让应用直接写 ES，是为了让"日志系统故障不拖垮业务"——ES 挂了只丢日志，请求照常返回。
  - 用 JSON 而不是纯文本，采集端才能做字段级解析、聚合和索引；纯文本日志到了平台侧只能全文检索，做不出错误率趋势这类看板。
  - 轮转放在**应用侧**（`DailyRotateFile` + `maxFiles`），而不是靠外部工具删文件，是因为应用最清楚自己写了多少；外部清理常常滞后到磁盘已经满了。
- **边界与代价**：引入 ELK 就多一套要运维的中间件（ES 集群也是要人管的），小团队先用"文件日志 + 轮转 + 集中 grep"完全够，别为了日志把运维复杂度翻倍。
- **边界与代价**：日志脱敏必须在**写入前**做（手机号、密码、Token 不能进日志），落盘之后再删没有意义——日志文件本身就是扩散面。
- **追问**：磁盘阈值按日志量算——JSON 日志正常请求量每天约 10-50MB，保留 31 天建议预留 2GB 以上；日志量突然暴涨先查 `LOGGER_LEVEL` 是否被调成了 debug。

### Q49: 场景题：为 API 设计一套限流方案（11-进阶/02 篇）

- **题目要求**：既要挡住恶意刷接口，又不能误伤正常用户；要能按不同维度（全局 / 接口 / 用户 / IP）分别设阈值；超限要给客户端明确反馈。
- **算法选择**：主用**滑动窗口**（Redis Sorted Set：`ZREMRANGEBYSCORE` 挪掉窗口外记录、`ZCARD` 统计、`EXPIRE` 兜底过期），或令牌桶（Lua 脚本保证"补令牌 + 扣令牌"原子）；固定窗口计数器最简单，但窗口交界处能放过两倍流量，只在阈值极低的敏感接口上用。
- **限流维度**：全局总 QPS ≤ 1000；敏感接口（登录、短信）每分钟 ≤ 10 次；单用户每秒 ≤ 5 次；单 IP 每分钟 ≤ 100 次——细粒度阈值比全局阈值更能挡住单点刷。
- **实现位置**：NestJS 里用 `@nestjs/throttler` 的 `ThrottlerGuard` + 自定义 `@Throttle({ limit, ttl })` 装饰器，在进入业务前判断；存储换成 Redis 就天然支持多实例。
- **单机 vs 分布式**：单实例用进程内计数器即可；多副本**必须落到 Redis**，而且要把"读计数 + 判断 + 写回"打包成 Lua 脚本——拆成两条命令做，并发下必然漏判。
- **限流响应**：返回 `429 Too Many Requests`，响应头带 `Retry-After: <seconds>` 告诉客户端多久后重试，响应体给友好提示；不要返回 500 或直接断连接。
- **真实 IP**：按 IP 限流要用对客户端 IP——有 Nginx 时从 `X-Forwarded-For` / `X-Real-IP` 取并配 `trust proxy`，否则所有请求算同一个 IP，一限就限死全站。
- **兜底与联动**：网关层（Nginx `limit_req`）先做一道粗粒度限流，应用层再做细粒度限流——前者挡住明显的洪水且开销极低，后者处理业务维度；只有应用层限流时，洪水会先把连接和进程资源耗掉。
- **为什么这么设计**：
  - 限流的目标不是"拒绝"而是"保护下游"——按维度分层是为了让恶意流量在触及昂贵资源（数据库、外部接口）之前就被挡住，而不是等打穿了再救。
  - 用 Redis 是为了让阈值在集群维度上是**一个数**，而不是"每个副本各限 1/N"；否则扩容之后总放行量会随副本数一起放大。
  - 限流必须配明确的响应语义（429 + `Retry-After`），客户端才知道是"被限了、稍后重试"，而不是"服务坏了"——否则客户端会立刻重试，反而放大流量。
- **边界与代价**：滑动窗口要存窗口内每个请求的时间戳，**内存开销随 QPS 线性增长**，超高频接口更适合令牌桶（只存令牌数与上次补充时间）。
- **边界与代价**：阈值设太严会伤正常用户——NAT 后的公司出口、运营商网关后的用户会共用一个 IP，按 IP 限流前要先看真实 IP 分布，上线前用真实流量打点定阈值。
- **边界与代价**：限流之外还要有熔断与降级——限流挡的是"量"，熔断处理的是"下游已经坏了"；只有限流、没有熔断，下游挂了照样会把请求全赔进去。
