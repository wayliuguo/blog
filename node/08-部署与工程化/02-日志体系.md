# 日志体系

> 从 console.log 到双写架构：日志的渐进式演进
> 实战参考：show-track-server 的 `src/shared/logger/`

---

## 日志为什么值得单独一篇

日志是生产环境的"黑匣子"。线上出问题时，**代码无法重新执行，但日志可以复盘**。日志体系的差距，决定了排障是"半小时"还是"一下午"。

和上一篇配置一样，日志也是四步渐进：

| 阶段 | 目标 | 你能获得 |
|------|------|---------|
| ① 认清问题 | 明白 console.log 在生产中的局限 | 知道为什么要上日志库 |
| ② Winston 基础 | 分级 + 时间戳 + 输出到文件 | 可查的历史日志 |
| ③ 双写架构 | 控制台与文件双通道、按日轮转、追踪 ID | 生产级日志体系 |
| ④ 日志查看 | 三层日志查看方式与排障速查 | 故障排查能力 |

---

## ① 认清问题：console.log 为什么不能上生产

```javascript
console.log('用户创建成功', user)
console.error('创建用户失败', err)
```

生产环境用 console.log 有四个硬伤：

| 问题 | 说明 |
|------|------|
| 没有日志级别 | 无法区分 debug/info/error，排查时被海量日志淹没 |
| 没有时间戳 | 无法定位"什么时候发生" |
| 不支持输出到文件 | 容器/服务器重启日志即丢，无法复盘 |
| 性能差 | 同步写 stdout，高并发下拖慢请求 |

> 控制台日志还有个隐藏坑：它走的是 **stdout**，只适合"实时看"，不适合"事后查"。生产日志必须落到文件。

---

## ② Winston 基础：分级 + 时间戳 + 文件输出

Winston 是 Node.js 生态最主流的日志库，核心概念三个：**level（级别）、format（格式）、transport（输出目的地）**。

```bash
npm install winston
```

```typescript
import { createLogger, format, transports } from 'winston';

export const logger = createLogger({
  level: 'info', // 低于该级别的日志不输出
  format: format.combine(
    format.timestamp(),
    format.json(), // 结构化 JSON，便于采集工具解析
  ),
  transports: [
    new transports.Console(), // 输出到控制台
    new transports.File({ filename: 'logs/combined.log' }),
    new transports.File({ filename: 'logs/error.log', level: 'error' }),
  ],
});
```

### 日志级别

Winston 沿用 npm 的级别体系，**数字越小越严重**：

| 级别 | 数值 | 说明 | 生产是否输出 |
|------|------|------|------------|
| `error` | 0 | 错误，需要立即关注 | 是 |
| `warn` | 1 | 警告，不影响功能 | 是 |
| `info` | 2 | 一般信息 | 是 |
| `debug` | 3 | 调试信息 | 否（默认） |
| `verbose` | 4 | 详细信息 | 否（默认） |

> 生产环境日志级别一般设为 `info`，把 debug 留给开发。这是"日志分级"的价值——**不是不记，而是分轻重**。

### 使用

```typescript
logger.debug('创建用户参数:', dto)             // 开发调试
logger.info(`用户创建成功: ${user.id}`)         // 一般信息
logger.error(`用户创建失败: ${err.message}`, { stack: err.stack }) // 错误
```

> **小结**：② 解决了"分级 + 落文件 + 时间戳"。但还有三个生产问题没解决：控制台输出没有统一、单文件无限膨胀、错误日志和普通日志混在一起。继续看 ③。

## ③ 双写架构：show-track 的生产级日志

show-track 的日志设计解决了上面三个问题。核心思想是**双写**：控制台保留 NestJS 原生输出（开发可读），Winston 负责写文件（生产可查）。

```
应用代码
   │
   ▼
LoggerService（继承 ConsoleLogger，双写）
   ├── ConsoleLogger ──▶ 控制台 stdout ──▶ PM2 捕获 ──▶ docker logs
   └── Winston ────────▶ logs/app.%DATE%.log（全量，JSON，按日轮转）
                         logs/app-error.%DATE%.log（仅 ERROR）
```

### 3.1 继承 ConsoleLogger：不破坏 NestJS 原生体验

```typescript
// src/shared/logger/logger.service.ts
import { ConsoleLogger, Injectable } from '@nestjs/common';
import { createLogger, format, transports } from 'winston';
import 'winston-daily-rotate-file';

@Injectable()
export class LoggerService extends ConsoleLogger {
  private winstonLogger: WinstonLogger;

  constructor(context: string, options: ConsoleLoggerOptions,
              private configService: ConfigService<ConfigKeyPaths>) {
    super(context, options);
    this.initWinston();
  }
  // ...
}
```

> 继承 `ConsoleLogger` 而不是另起炉灶：**调用方仍然用 `this.logger.log('xxx')`，但内部同时写了控制台和文件**。业务代码零改动。

### 3.2 按日轮转：解决单文件无限膨胀

```typescript
protected initWinston(): void {
  this.winstonLogger = createLogger({
    levels: config.npm.levels,
    format: format.combine(format.errors({ stack: true }), format.timestamp(), format.json()),
    transports: [
      // 全量日志：按日切文件，保留 maxFiles 天
      new transports.DailyRotateFile({
        level: this.level,                              // 由配置中心控制
        filename: 'logs/app.%DATE%.log',               // app.2026-09-09.log
        datePattern: 'YYYY-MM-DD',
        maxFiles: this.maxFiles,                        // 默认保留 31 天
        format: format.combine(format.timestamp(), format.json()),
        auditFile: 'logs/.audit/app.json',
      }),
      // 错误日志：独立文件，快速定位故障
      new transports.DailyRotateFile({
        level: 'error',
        filename: 'logs/app-error.%DATE%.log',
        // ... 同上
      }),
    ],
  });
}
```

三个生产细节：

| 细节 | 为什么 |
|------|--------|
| `DailyRotateFile` 按日切文件 | 单文件不会无限膨胀，按日期归档好查询 |
| `app-error.%DATE%.log` 独立错误文件 | 排障时直接看错误文件，不用在大日志里 grep |
| `auditFile` | 记录轮转状态，重启容器后不会重复处理旧文件 |

### 3.3 配置中心控制级别与保留天数

日志级别和保留天数不硬编码，走第一篇的配置系统：

```typescript
// 从配置中心读取（.env 里 LOGGER_LEVEL / LOGGER_MAX_FILES）
protected get level(): LogLevel {
  return this.configService.get('app.logger.level', { infer: true })!;
}
protected get maxFiles(): number {
  return this.configService.get('app.logger.maxFiles', { infer: true })!;
}
```

```ini
LOGGER_LEVEL=info        # 生产只输出 info 及以上
LOGGER_MAX_FILES=31      # 保留 31 天
```

### 3.4 请求追踪 ID：串联整条调用链

分布式/微服务环境下，一次请求会横跨多个服务，散落的日志无法串联。show-track 用 `nestjs-cls`（异步上下文）给每个请求分配 trace ID，自动附加到每条日志：

```typescript
private getTraceId(): string | undefined {
  return this.clsService?.getId();
}

private formatWithTrace(message: unknown): string {
  const traceId = this.getTraceId();
  return traceId ? `[${traceId}] ${message}` : String(message);
}

log(message: unknown, context?: string): void {
  const msg = this.formatWithTrace(message);
  super.log.apply(this, [msg, context]);
  this.winstonLogger.log('info', msg, { context, traceId: this.getTraceId() });
}
```

> 排查时按 trace ID 一搜，一次请求从入口到数据库的完整路径都在。

> **小结**：③ 实现了生产级双写。但"写得好"还要"查得到"——最后一步是日志查看方法论。

## ④ 日志查看：三层方式与排障速查

日志写好了，怎么查？生产环境（Docker 部署）下有**三层查看方式**，各有适用场景：

| 查看方式 | 命令入口 | 适用场景 |
|---------|---------|---------|
| ① docker logs | `docker logs -f <container>` | 快速排查、启动日志、实时监控 |
| ② 容器内文件 | `docker exec ... cat logs/app.xxx.log` | 历史日志、按级别过滤、重启后仍可查 |
| ③ pm2 logs | `docker exec ... pm2 logs` | PM2 进程管理问题（重启、内存告警） |

### 场景速查表

| 想看什么 | 用什么命令 |
|----------|-----------|
| 容器是否正常启动 | `docker logs <container> --tail 20` |
| 实时监控应用日志 | `docker logs -f <container>` |
| 今天的所有错误 | `docker exec <container> cat logs/app-error.$(date +%Y-%m-%d).log` |
| 某个接口的请求日志 | `docker exec <container> grep "POST /api/xxx" logs/app.$(date +%Y-%m-%d).log` |
| 最近 1 小时发生了什么 | `docker logs <container> --since 1h` |
| 应用是否被 PM2 重启过 | `docker exec <container> pm2 logs <app> --lines 50 --nostream` |
| 搜索错误及其上下文 | `docker exec <container> grep -C 2 '"level":"error"' logs/app.$(date +%Y-%m-%d).log` |

> 文件日志是 JSON 格式，配合 `jq` 可以做进一步结构化分析。

### 日志文件管理

| 配置项 | 值 | 说明 |
|--------|-----|------|
| 轮转周期 | 每天 | 每天生成新文件 |
| 文件命名 | `app.2026-09-09.log` | 按日期命名 |
| 保留天数 | 31 天 | 超过自动删除 |
| 错误日志 | 独立文件 | `app-error.%DATE%.log` |

磁盘注意：JSON 日志正常请求量每天约 10-50MB，保留 31 天建议预留 2GB 以上；如果日志量异常增长（如 debug 级别被启用），优先检查 `LOGGER_LEVEL` 配置。

## 完整示例：NestJS 全局注册

```typescript
// src/shared/logger/logger.module.ts
@Module({})
export class LoggerModule {
  static forRoot() {
    return {
      global: true,          // 全局可用
      module: LoggerModule,
      imports: [ConfigModule],
      providers: [LoggerService],
      exports: [LoggerService],
    };
  }
}
```

```typescript
// main.ts
const app = await NestFactory.create(AppModule, {
  bufferLogs: true, // 让 NestJS 内部日志也走自定义 Logger
});
app.useLogger(app.get(LoggerService)); // 替换默认 Logger
```
