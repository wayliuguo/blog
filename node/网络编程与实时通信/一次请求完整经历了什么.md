# 一次请求完整经历了什么

## 一条 GET /users 请求是怎么逐层穿过的？

以浏览器请求为例：

```http
GET /users HTTP/1.1
Host: localhost:3000
```

把从浏览器到 Controller、再原路返回的整条链路画成一张图（下文每一步都标了它"在第几篇讲过"，方便回头查）：

```
Browser
  │ ① DNS 解析 host → IP                          （见 02 篇 / 00 篇）
  │ ② TCP 三次握手 SYN → SYN+ACK → ACK            （见 01 篇）
  │ ③ [HTTPS] TLS 握手：ClientHello → 证书 → 密钥  （见 02 篇）
  │ ④ 组装 HTTP 请求报文：方法 / 路径 / Host / 头
  ▼
Socket（浏览器侧）
  │ ⑤ 请求字节流写入内核 TCP/IP 协议栈
  ▼
IP 网络：路由、CDN、负载均衡                       （见 00 篇）
  ▼
Server NIC → Linux Kernel → TCP/IP 协议栈
  │ ⑥ 重组字节流，落入 Socket Receive Buffer      （见 01 篇）
  │ ⑦ fd 变为 readable（就绪）
  ▼
epoll 通知 → libuv 取事件 → Event Loop poll 阶段    （见 模块一03 篇）
  ▼
node:http 解析报文 → 触发 'request'
  │ ⑧ 构造 req（Readable）/ res（Writable）        （见 02 篇 / 模块一06 篇）
  ▼
Express / Fastify（Adapter + 中间件链）
  ▼
NestJS：Middleware → Guard → Interceptor → Pipe
  ▼
Controller（@Get findAll）→ Service → 返回 []
  │
  ▼ （原路返回）
res 写出 → Socket Send Buffer → 内核 → TCP → 网络 → 浏览器渲染
```

把上面这张图拆成带编号的步骤，去到 Controller 再原路回来，共 31 步：

1. **DNS 解析** —— 浏览器把 `localhost`/域名换成 IP；本地缓存 → 系统 hosts → 递归 DNS。（见 02 篇 / 00 篇）
2. **拿到 IP** —— 解析结果带 TTL 缓存，过期前不再查；生产里 CDN 常按地域返回不同 IP。（见 02 篇）
3. **选端口** —— 默认 443（HTTPS）/ 80（HTTP）；HTTP/2、HTTP/3 也跑在对应端口上。（见 02 篇）
4. **TCP 第一次握手 SYN** —— 客户端发 SYN，携带初始序列号，进入 SYN_SENT。（见 01 篇）
5. **服务端回 SYN+ACK** —— 确认客户端序列号并发送自己的序列号，进入 SYN_RCVD。（见 01 篇）
6. **客户端发 ACK** —— 三次握手完成，连接进入 ESTABLISHED，内核为该连接建立 socket。（见 01 篇）
7. **HTTPS：TLS ClientHello** —— 客户端发支持的 TLS 版本、密码套件、随机数。（见 02 篇）
8. **HTTPS：ServerHello + 证书** —— 服务端选定套件、发证书链（含公钥）。（见 02 篇）
9. **HTTPS：验证证书** —— 客户端校验证书链、域名、有效期，并核对系统时间是否可信。（见 02 篇）
10. **HTTPS：协商密钥** —— 通过 ECDHE 之类交换得到对称密钥，后续报文用该密钥加密。（见 02 篇）
11. **HTTPS：Finished** —— 双方交换校验摘要，握手完成，进入加密应用数据传输。（见 02 篇）
12. **浏览器组装 HTTP 请求报文** —— 方法、路径、Host、Cookie、Content-Type 等头部就绪。（见 02 篇）
13. **浏览器把请求报文写入 socket** —— 数据交给内核，变成待发送的字节流。（见 02 篇）
14. **内核 TCP/IP 协议栈处理** —— TCP 分段、加 TCP 头与 IP 头，必要时在 IP 层分片。（见 01 篇 / 00 篇）
15. **网卡发出** —— 字节流经网卡变成电信号/光信号，按 MTU 成帧送上网络。（见 00 篇）
16. **网络路由转发** —— 经交换机、路由器、可能过 CDN / 负载均衡，逐跳逼近服务器。（见 00 篇）
17. **抵达服务器网卡** —— 服务端网卡收包，触发中断，数据送入内核网络栈。（见 00 篇）
18. **内核协议栈重组** —— 去 IP/TCP 头、按序列号重组字节流，放入该 socket 的 **Receive Buffer**。（见 01 篇）
19. **socket 变为 readable（就绪）** —— fd 可读，内核标记就绪。（见 01 篇）
20. **`epoll` 通知** —— 该 fd 就绪，`epoll_wait` 返回"可读"事件（macOS 为 kqueue、Windows 为 IOCP，机制同理）。（见 模块一03 篇）
21. **`libuv` 取出事件** —— 事件循环从 epoll 把就绪 fd 取出，封装成上层回调。（见 模块一03 篇）
22. **Event Loop 的 poll 阶段** —— Node 在 poll 阶段消费 I/O 事件，驱动后续 JS 执行。（见 模块一03 篇）
23. **`node:http` 解析报文** —— 从字节流中解析出方法、路径、头部（状态行 / 头 / body），触发内部逻辑。（见 02 篇）
24. **构造 `req` 与 `res`** —— `req` 是 Readable、`res` 是 Writable，二者都是流。（见 02 篇 / 模块一06 篇）
25. **触发 `'request'` 事件** —— `http.Server` 发出 request，把 `req`/`res` 交给上层框架。（见 02 篇）
26. **Express / Fastify 适配层** —— 把原生 `req`/`res` 包成更易用的对象，串起中间件链。（见下一篇 04-Express）
27. **NestJS Middleware → Guard** —— 先走中间件，再走守卫做身份认证与权限判断。（见 07 篇）
28. **Interceptor（前） → Pipe** —— 拦截器在调用前做日志/超时，Pipe 做 DTO 校验与类型转换。（见 07 篇）
29. **Controller 方法执行** —— 路由匹配到 `@Get() findAll()`，调用 Service 处理业务。（见 07 篇）
30. **Service 业务逻辑** —— 返回 `[]`，其间查数据库、调下游的网络 I/O 异步进行。（见 07 篇）
31. **Interceptor（后）序列化 → 写回** —— 返回数据在拦截器里被序列化、包装；经 `res` 可写流写出（大响应触发背压与 `drain`）；Keep-Alive 决定连接保留或四次挥手；浏览器解析渲染。（见 07 篇 / 模块一06 篇）

心智模型：你写的那行 `return []` 只是第 30 步；前面 29 步全是"为了把请求安全送到这一行"做的铺垫，后面 1 步是"把结果安全送回去"。其中第 18–22 步（Receive Buffer → epoll → libuv → poll）是 Node 网络能力的真正底座，前几篇分别在 01 篇（TCP）、模块一03 篇（事件循环）展开过。

## 每一步出问题时是什么现象？（排障坐标系）

同一症状常常对应不同层。看到报错先别怀疑业务代码，按"链路环节"定位：

| 链路环节 | 典型现象 / 错误码 | 该往哪查 / 怎么验证 |
|------|------|------|
| DNS 解析（步骤 1–2） | `ENOTFOUND`、`EAI_AGAIN`、部分地区打不开、解析到旧 IP | `nslookup`/`dig` 验证解析；查 DNS 配置、TTL 是否过长、CDN 解析策略 |
| TCP 建连（4–6） | `ECONNREFUSED`、连接超时 `ETIMEDOUT`、端口不通 | `telnet`/`nc` 探端口；查服务是否监听、防火墙、安全组、端口占用 |
| TLS 握手（7–11） | 证书过期、握手失败、浏览器红锁、`DEPTH_ZERO_SELF_SIGNED_CERT` | 查证书有效期、系统时间、证书链是否完整、域名是否匹配 |
| 网关（16 / 反向代理） | `502 Bad Gateway`、`504 Gateway Timeout` | 查 Nginx 等代理配置、`proxy_read_timeout`、上游是否存活 |
| 连接复用（Keep-Alive，31） | `ECONNRESET`、`socket hang up`、`502` | 比对 `server.keepAliveTimeout` 与 Nginx `keepalive_timeout` 谁先关 |
| 文件描述符（18 / 全局） | `EMFILE` / `ENFILE`、`Too many open files` | `lsof -p <pid>` 数连接；查 `ulimit -n`、连接泄漏、未释放的 socket |
| 事件循环（20–22） | CPU 高但 QPS 低、请求堆积、延迟陡增 | 查是否有同步阻塞调用占住主线程；用 `clinic.js`/火焰图看热点 |
| 响应序列化（31） | 大 JSON 卡住、内存涨、客户端收不全 | 是否一次性 `JSON.stringify` 大对象；改用流 / 分页 / 压缩 |
| 框架层（27–28） | Guard 拦截返回 401/403、DTO 校验失败 400、异常格式不统一 | 查守卫逻辑、Pipe/DTO 装饰器、`ExceptionFilter` 是否覆盖 |
| 业务层（30） | 下游慢、超时、依赖抖动、偶发 5xx | 查 Service 日志、链路追踪、下游数据库 / 第三方耗时与限流 |

心智模型：看到 `ECONNRESET`，别先怀疑代码——先看是连接哪一端先关的，大半是 Keep-Alive 超时不匹配；看到 `504`，先确认是不是上游等太久而不是本服务崩了。

## NestJS 到底帮我们封装了哪几层？

进入 NestJS 后，你通常不会再写：

> 摘自 `./code/net-lab/src/05-http-server.js`（运行：`npm run 05`）

```js
const http = require('node:http')

const server = http.createServer((req, res) => {
    // req.method / req.url 是解析出来的首行信息
    console.log(`收到请求: ${req.method} ${req.url}`)
// …
    // 其他路径返回 404
    res.writeHead(404, { 'Content-Type': 'text/plain; charset=utf-8' })
    res.end('404 Not Found')
})
```

这一层就是第 23–25 步：报文的解析、`req`/`res` 的构造、`'request'` 事件的触发。跑起来看，它只会把每次请求原样打出来：

实测输出（`npm run 05`）：

```
最小 HTTP 服务已启动: http://localhost:3000
收到请求: GET /
收到请求: GET /api/users
收到请求: POST /api/echo
收到请求: GET /unknown
```

更不会直接写 `net.createServer()` 去处理裸 TCP。你写的是装饰器 + 类：

> 示意片段（无配套脚本）

```ts
@Controller('users')
export class UserController {
  @Get()
  findAll() {
    return []; // 一个请求走到这里，前面 29 步都已被框架和运行时消化完
  }
}
```

整个抽象层级栈是自顶向下的：

```
业务代码（@Controller / @Get / @Injectable）
     ↓
Controller（路由匹配、参数绑定）
     ↓
NestJS（DI、Guard、Interceptor、Pipe、Filter）
     ↓
Express / Fastify Adapter（中间件链、req/res 增强）
     ↓
node:http（报文解析、触发 'request'）
     ↓
TCP Socket（net.Socket，本质是 Duplex Stream）
     ↓
libuv + OS（epoll / kqueue / IOCP、内核协议栈）
```

NestJS 解决的工程问题基本覆盖了 Web 服务需要的全部横切能力：

- **Routing**：用装饰器声明路由，不必手写 `if (req.url === '/users')`。
- **Controller**：把请求处理方法组织成类，结构清晰。
- **Provider / Dependency Injection**：用 `@Injectable()` 声明依赖，容器自动装配，测试可替换。
- **Middleware**：在请求进入路由前统一做日志、CORS、压缩。
- **Guard**：集中做认证与鉴权（401/403）。
- **Interceptor**：做日志、超时、响应统一包装、缓存。
- **Pipe**：做 DTO 校验与类型转换（校验失败直接 400）。
- **Exception Filter**：把异常统一翻译成标准错误响应。
- **WebSocket Gateway / Microservices**：在统一范式下写实时通信与微服务，不必换一套心智模型。

但是这里有**两层"不知道"**，是学这一层真正的意义：

1. **框架不知道它底下有 `epoll` 与事件循环。** NestJS 的 `next()`、Guard、Pipe 再怎么写，最后都落到 `res.end()` 把字节交给内核；它从不关心"这个 socket 是怎么被 epoll 通知可读的""事件循环在 poll 阶段怎么消费的"。
2. **你如果只学框架，也不知道它底下发生了什么。** 你知道 `@Get()` 能收到请求，却不一定知道这个请求是先在 Receive Buffer 里排队、被 epoll 标记为 readable、再由 libuv 送进 poll 阶段才触发的。

纵向分层越深，"出问题时该看哪一层"就越容易迷路：框架把底层错误翻译成一句含糊的 `ECONNRESET` 或 `504` 甩给你，而你能不能秒定位，取决于你是否懂下面那几层。

## 既然框架都封装了，为什么还要学这一层？

核心论点：**写业务代码时你永远待在最上面一层；出问题时，问题往往在最下面几层。**

平时业务正常时，`@Get()` / `@Post()` / `@Injectable()` 确实够用。但一旦线上出现：

```
ECONNRESET        ECONNREFUSED       ETIMEDOUT
EADDRINUSE        socket hang up    Too many open files
502 Bad Gateway   504 Gateway Timeout
```

如果只会框架，很容易不知道从哪开始排查。理解网络分层后，可以建立一条"是 / 否"分叉的排查思路链，从现象往里钻：

```
请求失败
  ├─ DNS 正常吗？              否 → ENOTFOUND / EAI_AGAIN，查 DNS 与 CDN
  ├─ TCP 能建立连接吗？        否 → ECONNREFUSED（端口不通）/ ETIMEDOUT（防火墙、网络），探端口
  ├─ TLS 握手成功吗？          否 → 证书过期 / 校验失败，查证书链与系统时间
  ├─ 网关正常吗？              否 → 502（上游挂）/ 504（上游超时），查代理与上游存活
  ├─ Keep-Alive 有问题吗？     是 → ECONNRESET / socket hang up，比对两侧超时
  ├─ Node 服务正常吗？         否 → 进程死 / EADDRINUSE（端口被占），看进程与端口
  ├─ Event Loop 是否被阻塞？   是 → CPU 高但 QPS 低，查同步阻塞调用
  ├─ 框架是否报错？            是 → Guard 拦截 / DTO 校验 400，查守卫与 Pipe
  └─ 业务逻辑是否异常？        是 → 下游慢 / 异常，查 Service 日志与链路追踪
```

每一步都是一个可验证的"是 / 否"判断：先确认 DNS、再确认 TCP、再确认 TLS……一层层往下排除，比"重启一下试试"高效得多。

收束一句：**学底层最大的意义，是把"报错"翻译成"该去哪一层看"。** 框架是电梯，让你直达顶层写业务；电梯坏了，你得会走楼梯——楼梯就是 TCP、HTTP、内核、libuv 这几层。这也就是为什么模块二放在模块三（Express/Koa）和模块七（NestJS）之前：先懂被封装的东西，再看封装才有落点，否则框架对你只是"黑盒咒语"。

## 模块二小结：把五篇串成一张网络全景图

- **00 导读与全景图**：建立"应用层 → 传输层 → 网络层 → 内核 → libuv"的整体坐标，知道每层各管什么。
- **01 TCP 与 Socket 编程**：链路第 4–6 步（三次握手）、第 18 步（Receive Buffer）、第 19 步（readable 就绪）的底座，理解字节流为什么需要自己定消息边界。
- **02 HTTP 与 HTTPS 深入**：链路第 1–3 步（DNS / 端口）、第 7–13 步（TLS 握手、报文组装）、第 23–25 步（`node:http` 解析、`req`/`res` 即流）。
- **03 WebSocket 与 SSE**：长连接与升级后的双向通道，是这条链路的"常驻变体"——握手仍走 HTTP，之后才脱离请求-响应模型。
- **04 一次请求完整经历了什么（本篇）**：把上面四篇纵向串成一条 31 步链路 + 一张排障坐标系，并回答"框架都封装了为什么还要学"。

模块二到此结束。下一个模块是**模块三（Web 框架基础）**：把这里的网络能力包装成好用的框架——先讲 Express 与 Koa（站在 `node:http` 之上，替你管好中间件、路由和响应），再讲它们的源码，你此时已经知道"中间件底下是 `req`/`res` 这两个流、路由匹配发生在 `'request'` 事件之后"，读源码才有落点。
