# 模块面试题 · 网络底层

> 用法：先盖住答案自测，答得磕巴的再回去读对应章节；题目标注的"（N.N）"是该题所属知识域编号，也是回查入口；排障题尽量按判断链复述而不是背结论。

## 1. 分层模型与链路坐标

### Q1（1.1）｜网络分哪四层，一次 `GET /users` 是怎么逐层下降的？（结论先行）

- **判断**：网络按职责分成应用 / 传输 / 网络 / 接口四层，`GET /users` 逐层下降最终变成电信号。
- **展开**：所谓"逐层下降"= 应用层定义语义 → 传输层可靠有序送达 → 网络层寻址路由 → 接口层把字节变成电信号，每层只解决一件事。HTTP 只定义报文不管送达，TCP 保证可靠有序送达，IP 找路，网卡变电信号。
- **边界**：排障时先定位故障落在哪一层——越靠下越像连接与资源问题，越靠上越像配置与路由问题。

### Q2（1.2）｜每层出问题各表现为哪些典型报错？为什么先定位层而不是全局搜代码？（结论先行）

- **判断**：同一症状常常对应不同层，看到报错先把故障钉在某一层，再决定查什么。
- **展开**：DNS 层看 `ENOTFOUND` / `EAI_AGAIN`，TCP 建连层看 `ECONNREFUSED` / `ETIMEDOUT` / `EADDRINUSE`，连接生命周期看 `ECONNRESET` / `socket hang up`，TLS 看证书错误，HTTP 层看 400 / 404 / 431，网关看 502 / 504，运行时资源看 `Too many open files`。
- **边界**：报错越靠上越像配置与路由问题、越靠下越像连接生命周期与资源问题；顺序反过来查容易在错误的一层白忙。

### Q3（1.2）｜请求链路是对称的吗？"请求怎么进来"和"响应怎么出去"是同一件事吗？（结论先行）

- **判断**：是同一张图的两次遍历——响应沿请求进来的原路反向走回去。
- **展开**：请求字节流从网卡经内核、`node:http`、框架到达业务函数；业务函数 `res.end()` 之后，字节再沿 socket → 内核 → 网络 → 浏览器渲染反向走一遍。
- **佐证**

```
Browser ──请求──▶ HTTP ──▶ TLS ──▶ TCP ──▶ ip ──▶ 网卡
        ◀──响应── HTTP ◀── TLS ◀── TCP ◀── ip ◀── 网卡
```

- **边界**：理解其一即理解其二；一次连接的生命周期里，请求与响应始终在同一条 socket 上完成。

## 2. TCP 与 Socket 编程

### Q1（2.1）｜TCP 在不可靠的 IP 网络之上提供了哪三种保证？它和 UDP 的区别是什么？（结论先行）

- **判断**：TCP 提供面向连接、可靠、有序三种保证；UDP 都没有。
- **展开**（表格）：

| 特性 | TCP | 缺了会怎样 |
| --- | --- | --- |
| 面向连接 | 三次握手后通信 | 对方可能没准备好 |
| 可靠 | 丢包重传 + 校验和 + 确认应答 | 文件残缺 |
| 有序 | 序号保证到达顺序 | 消息乱序 |

- **边界**：UDP 换来更低延迟与开销；HTTP/3 的 QUIC 正是基于 UDP 在用户态自己重建可靠传输与拥塞控制。业务接口默认要可靠有序，所以都是 TCP；音视频、游戏状态同步这类"容忍少量丢包、低延迟优先"才选 UDP。
- **追问**：TCP 只保证"字节可靠有序"，不保证"你发几次我收几次"——这正是粘包拆包的根源。

### Q2（2.1）｜三次握手为什么不能简化成两次？（结论先行）

- **判断**：因为双方都要确认"我发得出去、也收得到"，两次握手服务端确认不了。
- **展开**：两次握手时服务端收到 `SYN` 就分配资源（缓冲区、端口）；若这个 `SYN` 是网络里滞留的旧报文，服务端会空等超时、白白占资源。
- **佐证**

```
客户端                            服务端
SYN（seq=x）      ──────────────▶  收到 SYN，分配资源
SYN+ACK（seq=y）  ◀──────────────  
ACK              ──────────────▶  确认客户端已收到，才放心投资源
```

- **边界**：第三次 `ACK` 让服务端确认"客户端确实收到了回应"，双方才验证过收发能力；恰恰是这一步挡住了 SYN Flood 的空等策略。

### Q3（2.2）｜TCP 为什么是"字节流"而不是"消息流"？（结论先行）

- **判断**：TCP 只保证一串字节可靠、有序地到达，不保留你调用 `write` 的次数与边界。
- **展开**：`write('hello')` 与 `write('world')` 在 TCP 眼里只是连续字节，可能被合成一次，也可能被拆成多段；`socket.on('data')` 拿到的 `data` 是 Buffer 不是字符串。
- **边界**："一次发送 = 一次接收"不成立，基于 TCP 的应用协议必须自己定义消息边界。

### Q4（2.2）｜粘包 / 拆包是怎么产生的？有哪些解法？（结论先行）

- **判断**：因为 TCP 是字节流、不保留消息边界，所以两次 `write` 可能被读成一次，也可能被拆成多段。
- **展开**：解法有长度前缀、分隔符、定长三种，其中**长度前缀（4 字节 N + N 字节 Body）最通用**——
- **佐证**

```
发送方：write('hello') + write('world')
接收方：① 一次 = 'helloworld'（粘包）
       ② 'hel' + 'loworld'（拆包）
       ③ 'hello' + 'wor' + 'ld'（混合）
```

- **展开（续）**：长度前缀不依赖内容里是否恰好出现分隔符、不浪费补齐字节、对二进制同样适用；半包先缓存等下一段。HTTP 看起来没粘包，是因为它用 `Content-Length` 自己定义了边界。

### Q5（2.3）｜Socket 和 Stream 是什么关系？为什么说 `net.Socket` 是 Duplex Stream？（结论先行）

- **判断**：Socket 是"应用程序使用操作系统网络能力的接口抽象"，在 Node 里以双工流形态暴露。
- **展开**：`net.Socket` 同时实现 Readable 与 Writable——可读对应 `socket.on('data')` 收数据，可写对应 `socket.write()` 发数据，正是 TCP 全双工的体现。一条连接由四元组（源 IP:源 Port → 目标 IP:目标 Port）唯一区分，源端口不同就是不同连接，这是单机撑上万连接的由来。
- **佐证**

```
             net.Socket
           Readable      Writable
             │             │
       on('data') 收     socket.write() 发
```

- **边界**：`req` / `res` 是流、`pipe` 能直接把文件推给客户端，根源都是它们背后是同一个 Socket 的两端。

### Q6（2.4）｜`epoll` 解决了什么问题？libuv 又解决了什么？（结论先行）

- **判断**：epoll 解决"大量连接由谁来盯"，libuv 解决"不同 OS 机制不一样、写一份代码怎么跨平台"。
- **展开**：没有 epoll 时 1 万个 Socket 只能逐个轮询"有数据吗"；epoll 让内核关注大量描述符、有数据时主动通知，进程只处理就绪的那几个。
- **佐证**

```
10000 个 Socket → epoll（内核关注）→ 内核通知：Socket 583 有数据了
        ↑                ↑
    Linux epoll      macOS kqueue    Windows IOCP  → 都由 libuv 统一抽象
```

- **边界**：两者不是替代关系——epoll 是内核能力，libuv 是跨平台封装；Node 网络路径是"libuv 调 epoll，拿到就绪事件后回调回 JS"。

### Q7（2.4）｜网络 I/O 到底走不走 libuv 线程池？单线程凭什么扛万连接？（结论先行）

- **判断**：网络 I/O **不走**线程池，靠操作系统 I/O 多路复用（epoll / kqueue / IOCP）。
- **展开**：进线程池的是"没有同类型异步机制"的工作——`fs`、`dns.lookup`、`crypto`、`zlib`。等待交给内核与 libuv，主线程只处理已就绪事件，所以单线程能扛海量连接。
- **佐证**

```
一万个 Client → OS 盯 Socket → 就绪才通知 libuv → Event Loop → 只处理就绪 → 完成
```

- **边界**：不要记成"异步 = 线程池"；单线程能扛的前提是主线程不被阻塞，一旦有同步重计算占住它，所有连接一起卡住。`fs` 与 `crypto` 抢同一组线程，重 CPU 加密会顺带拖慢文件读写。

### Q8（2.5）｜`socket.write()` 返回 `false` 意味着什么？该怎么处理？（结论先行）

- **判断**：意味着 Writable 内部缓冲已积压到压力阈值，此时应停止写，等 `'drain'` 事件后再恢复生产。
- **展开**：磁盘读 500 MB/s、网络只能发 10 MB/s 时不做控制，数据一路堆内存最终 OOM。`write()` 的返回值就是背压信号：`false` 让暂停，`drain` 表示缓冲排空可继续。
- **佐证**

```
Producer ─▶ Writable Buffer ─▶ Consumer
    ▲          │ 
    │     消费慢 → 缓冲到阈值 → write 返 false（暂停）
    └── drain（可继续）◀── Consumer 慢慢消费
```

- **边界**：生产代码别自己写 `on('data')` 加无脑 `write`，那会丢掉背压；用 `pipe()` 或 `pipeline()` 让流内部协调速率。

### Q9（2.5）｜为什么更推荐 `pipeline()` 而不是手写 `pipe`？（结论先行）

- **判断**：`pipeline()` 和 `pipe()` 都能托管背压，但 `pipeline()` 出错时统一销毁整条链路，生产更稳。
- **展开**：`pipe()` 内部协调快慢（下游跟不上自动暂停上游）；但 `pipe` 出错时不会自动销毁链路，需手动处理。反例 `on('data') + write` 连背压都丢，返回 `false` 也照写，积压随发送总量一路涨。
- **佐证**：实测同一份 4MB 数据、同一个慢速客户端，手写写法发送缓冲峰值积压 1280KB、`pipe` 只有 64KB。
- **边界**：需"任一环出错就整体清理"时用 `pipeline`；只转发不需额外清理的简单场景 `pipe` 够用。

## 3. HTTP 与 HTTPS

### Q1（3.1）｜什么是 HTTP？TCP 之上为什么还要一层应用协议？状态码怎么分类？（结论先行）

- **判断**：HTTP 是定义"字节流如何被翻译成一次请求与响应"的应用层协议，约定 Method / URL / Header / Body / Status Code。
- **展开**：TCP 只懂字节流，HTTP 用"首行 + 头 + 空行 + 体"给出报文边界，框架已按此规则把字节解析好，所以你能直接拿 `@Body()`。状态码 1xx 信息（101 协议切换）、2xx 成功、3xx 重定向、4xx 客户端错误（400 / 401 / 403 / 404 / 431）、5xx 服务端错误（500 / 502 / 503 / 504）。
- **边界**：状态码由服务端决定、客户端只解释，所以"返回 200 但 body 里塞业务错误码"是设计选择而非协议要求，代价是破坏统一理解。

### Q2（3.1）｜一段 HTTP 报文在字节流里靠什么划出"头"和"体"的边界？（结论先行）

- **判断**：请求行 / 状态行 + 若干头 + **一个空行** + 体，空行就是头与体的分界。
- **展开**：头部结束位置靠空行确定；**体的结束位置**靠 `Content-Length` 或 `Transfer-Encoding: chunked` 确定——这就是 HTTP 在 TCP 之上自己定义消息边界、看着像没粘包的真正原因。
- **佐证**

```

GET /users HTTP/1.1
Host: example.com
Accept: application/json
                        ← 空行：头到此结束，之后是 body
```

- **边界**：`Content-Length` 必须写**字节长度**，写成字符长度会让客户端截断或报错。

### Q3（3.2）｜为什么 `req` 和 `res` 在 Node 里是流，而不是一个现成字符串？（结论先行）

- **判断**：因为 HTTP 数据经 TCP 到达时本就是分块字节流、可能很大、不会一次到齐。
- **展开**：`req` 是可读流，用 `data` 逐块给 Buffer，`end` 里 `Buffer.concat(chunks).toString()` 拼回；`res` 是可写流，可多次 `write()`、`end()` 收尾。这本质是把 TCP 字节流按 HTTP 语义向上封装。
- **边界**：这个设计让大文件能 `readableStream.pipe(res)` 边读边发不必全量进内存；`req` / `res` 是流的根源在 `net.Socket` 是 Duplex Stream。

### Q4（3.2）｜流式响应为什么不能先算 `Content-Length`？那用什么替代？（结论先行）

- **判断**：流式响应是"边产生边发送"，总长度要等全部产生完才知道，所以改用 `Transfer-Encoding: chunked`。
- **展开**：chunked 把响应体切成若干块、每块自带长度前缀、以长度 0 的块结束，服务端无需预先知道总字节数。
- **边界**：还有个死坑——`Content-Length` 取的是**字节长度**，`'你好'.length` 是 2 而 `Buffer.byteLength('你好')` 是 6，算错会直接截断。且 `Content-Length`/chunked 管响应体边界，`maxHeaderSize` 与 `431` 管请求头体积，别混在一起调。

### Q5（3.3）｜HTTP Keep-Alive 有什么用？三个超时什么关系？（结论先行）

- **判断**：Keep-Alive 让多个请求复用同一条 TCP 连接，省掉建连断连成本；三个超时是连接生命周期的三把尺子。
- **展开**：`keepAliveTimeout` 管空闲多久关；`headersTimeout` 管收齐请求头时限（防慢速攻击）；`requestTimeout` 管单请求总时限。
- **边界（关键坑）**：`headersTimeout` 必须 > `keepAliveTimeout`，否则空闲连接被关时"已关闭"状态未对齐、后续请求被丢弃，表现为 `ECONNRESET` / `socket hang up`。一句话原则：**反向代理的超时 ≥ 服务端超时**。
- **佐证**

```

无 Keep-Alive：建 TCP → 请求1 → 响应1 → 关 TCP（每个请求付一次连接成本）
有 Keep-Alive：一条 TCP 上 请求1/响应1 → 请求2/响应2 → …（空闲超时才关）
```

### Q6（3.4）｜HTTPS 比 HTTP 多了什么？TLS 到底解决了哪三件事？（结论先行）

- **判断**：HTTPS = HTTP over TLS，在 HTTP 与 TCP 间多垫一层 TLS；TLS 解决加密、身份认证、数据完整性。
- **展开**：加密防窃听、身份认证防中间人冒充、完整性防响应被篡改注入。握手：ClientHello → ServerHello + 证书链 → 校验证书 → 协商会话密钥 → Finished。
- **边界**：生产上 TLS 通常在网关卸载、Node 跑内部明文 HTTP。HTTPS 只保证运输过程安全，不保证服务端本身可信；证书报错不要用"忽略证书校验"绕过，那等于永久留下中间人风险。

### Q7（3.5）｜HTTP/1.1 的队头阻塞是什么？HTTP/2 多路复用怎么解决？（结论先行）

- **判断**：H1.1 同一条连接上的请求 / 响应仍是串行，前一个响应没回、后一个只能排队，即应用层队头阻塞；HTTP/2 用单条 TCP 上的多 Stream 交错传输解决。
- **佐证**

```
HTTP/1.1：Request1 → Response1 → Request2 → Response2（串行排队）
HTTP/2：   一条 TCP 上 Stream1 / Stream3 / Stream5 帧交错，互不排队
```

- **展开（续）**：HTTP/2 顺带做二进制分帧与 HPACK 头压缩省带宽；但多 Stream 仍共享同一条 TCP，"消除队头阻塞"只到应用层为止，TCP 层那份还没解决。

### Q8（3.5）｜HTTP/3 为什么要把传输层从 TCP 换成 QUIC（UDP）？（结论先行）

- **判断**：因为 HTTP/2 的多 Stream 仍共享一条 TCP，而 TCP 要求字节流可靠有序，丢一个包就让后续数据等重传补齐——即 TCP 层队头阻塞；HTTP/3 用基于 UDP 的 QUIC 绕开。
- **展开**：QUIC 在用户态自己实现可靠传输、多路复用、拥塞控制与 TLS，让各 Stream 相互独立，某个 Stream 丢包只影响自己。
- **边界**：业务代码通常无感，由运行时或网关决定；HTTP/3 不是业务里打个开关就生效，需要客户端、CDN、网关三段都支持。

## 4. 实时通信：WebSocket 与 SSE

### Q1（4.1）｜WebSocket 和 TCP 到底是什么关系？它能替代 TCP 吗？（结论先行）

- **判断**：不能。分层是 `WebSocket → TCP → IP`，WebSocket 是建立在 TCP 之上的应用层协议。
- **展开**：它把"如何可靠双向传消息"标准化为 Handshake / Frame / Message / Ping-Pong / Close / Text-Binary。
- **边界**：若绕过它直接写裸 TCP，消息格式、粘包分包、心跳、断线重连全要自己造；WebSocket 复用 TCP，而不是替代 TCP。
- **边界（追问）**：协议只解决"怎么传消息"，不解决"握手后怎么鉴权、多久心跳、如何优雅关闭"，这些仍是工程问题。

### Q2（4.2）｜WebSocket 的握手过程是怎样的？101 是什么意思？（结论先行）

- **判断**：客户端先发带 `Upgrade: websocket`、`Sec-WebSocket-Key`、`Version: 13` 的普通 HTTP 请求，服务端同意回 `101 Switching Protocols` 与 `Sec-WebSocket-Accept`，101 表示"协议切换"。
- **展开**：握手本身仍是标准 HTTP，成功之后这条 TCP 脱离请求-响应语义，改用 WebSocket 帧协议双方进入长连接。
- **边界**：`Sec-WebSocket-Accept` **不是加密**，是把 Key 拼固定串做 SHA-1 + Base64 回传，只用于证明对方真懂握手、防缓存代理误判返回脏数据。
- **边界（追问）**：返回 400 / 426 而非 101，通常意味着代理没正确转发 `Upgrade` 头，或服务端没挂 WebSocket 处理器。

### Q3（4.3）｜为什么长连接一定要有心跳（Ping / Pong）？（结论先行）

- **判断**：因为客户端断网、切网络、进程被杀、NAT 超时后服务端往往长期不知情，连接会"假死"。
- **展开**：假死连接的 Socket 还在却再也收不到数据，白白占着内存与 fd；定期 Ping / Pong 探测、连续多次无 Pong 判定失效并释放 Socket。
- **边界**：心跳间隔要结合 NAT 与代理的空闲超时，必须比中间设备超时更短，否则连接在你探测前就被静默回收。能上生产的长连接服务至少还要断线感知、自动重连、读写超时、健康度、消息确认、扩容分布。

### Q4（4.3）｜长连接在多实例部署下会遇到什么问题？（结论先行）

- **判断**：单机时所有连接在同一进程、广播可遍历；多实例后连接散落不同进程，A 实例发不到 B 实例持有的连接，广播必然漏发。
- **展开**：解法是共享订阅关系或消息总线（如 Redis 发布订阅）——任一实例产生消息后广播，各实例再投给自己持有的连接。
- **边界**：还要处理同一用户多端 / 多标签页的重复连接（推送要幂等），以及扩缩容时的连接迁移与集中重连；成熟项目直接用带房间与集群能力的库，而非从裸 `net` 起步。
- **边界（追问）**：选型先问"要不要横向扩多实例"——需要的话从第一天就把订阅总线设计进去。

### Q5（4.4）｜SSE 是什么？它靠什么做到"断线重连不重复推送"？（结论先行）

- **判断**：SSE 用一条普通 HTTP 长连接做服务端 → 客户端单向推送，方向固定 `Client ← Server`。
- **展开**：响应头设 `Content-Type: text/event-stream`、`Cache-Control: no-cache`，然后往 `res` 持续 `write` 事件文本；事件按行组织（`event:` / `data:` / `id:` / `retry:`）、空行分隔。
- **断线续传**：服务端给每条事件带 `id:`，浏览器 `EventSource` 自动重连时带 `Last-Event-ID` 头，服务端据此从断点续推。
- **边界**：必须监听 `req.on('close')` 清定时器，否则客户端断开后推送还在跑，造成内存与 fd 泄漏。

### Q6（4.4）｜在 Node 里实现 SSE，到底哪三步？（结论先行）

- **判断**：设对响应头 → 关掉默认缓冲 → 往 `res` 流持续 `write` 事件文本，并监听客户端断开清理。
- **展开**：① `Content-Type: text/event-stream`；② `Cache-Control: no-cache`、`Connection: keep-alive`；③ `res.write(\`data: ${payload}\n\n\`)` 持续推送、`req.on('close')` 里清定时器。
- **佐证**

```

res.writeHead(200, { 'Content-Type': 'text/event-stream',
                     'Cache-Control': 'no-cache',
                     Connection: 'keep-alive' })
const timer = setInterval(() => res.write(`data: ${...}\n\n`), 500)
req.on('close', () => clearInterval(timer))
```

- **边界**：因为 `res` 本身就是可写流，SSE 才能直接复用这套流式输出机制。

### Q7（4.5）｜SSE 和 WebSocket 应该怎么选？（结论先行）

- **判断**：判断"谁是主要说话方、要不要双向"，别默认"实时 = WebSocket"。
- **展开**：单向 `Server → Client` 持续推送（通知 / 站内信 / 行情 / 日志 / 进度）→ SSE，纯 HTTP、浏览器自动重连、网关易配、运维最轻；双向高频（聊天 / 协作 / 游戏）→ WebSocket，原生 Text / Binary 但心跳重连鉴权都要自己实现。
- **边界**：SSE 只支持文本（二进制需自行编码）、受浏览器同源连接数限制、代理要关缓冲否则被攒住；两种需求并存时可"SSE 收推送 + 普通 HTTP 发指令"。

### Q8（4.3 / 4.5）｜设计一个多实例可用的 WebSocket 实时通知方案（结论先行）

- **判断**：核心是"连接散落 → 用消息总线广播 + 房间把连接抽象成用户 + 鉴权前移到建连瞬间 + 心跳清理假死"。
- **展开**：握手仍是一次 HTTP Upgrade；`handshake.auth.token` 里带 JWT 在建连时鉴权，非法直接断开；`socket.join(userId)` 把用户 ID 当房间名，推送统一 `server.to(userId).emit(...)`；服务端 Ping / Pong 判假死、`handleDisconnect` 里清理房间 / 订阅 / 定时器；关键通知先落库再推并带递增 id，客户端按 id 去重；多实例用 Redis 发布订阅做总线，各实例投给自己持有的连接。
- **边界**：长连接持续占 fd 与内存、扩缩容涉及连接迁移；网关必须放行 `Upgrade` 头并延长空闲超时，否则连接被代理提前掐断、表现为客户端反复重连。若只是服务端单向推送，SSE 更轻。

## 5. 端到端链路与排障

### Q1（5.1）｜服务端收到请求后，从网卡到你的 Controller 内部经历了哪些层？（结论先行）

- **判断**：网卡 → 内核协议栈 → Socket Receive Buffer → fd 变 readable → epoll → libuv → poll → `node:http` 解析 → 构造 req / res → 框架 → Controller。
- **佐证**

```

网卡 → 内核 TCP/IP 栈 → Receive Buffer → fd 变 readable
  → epoll 通知 → libuv 取事件 → Event Loop poll 阶段
  → node:http 解析、触发 'request' → req(Readable) / res(Writable)
  → Express/Fastify → Middleware → Guard → Interceptor → Pipe
  → Controller（res.end() 之后沿原路反向再走一遍）
```

- **展开**：真正耗时的等待发生在内核与网卡，主线程只在就绪时被唤醒——"一个线程 + 一万次就绪通知"，不是一万条线程。
- **边界**：链路是**对称**的，"请求进来"和"响应出去"是同一张图的两次遍历。

### Q2（5.1）｜在浏览器输入 URL 到页面渲染完成，中间经历了哪些步骤？（结论先行）

- **判断**：`DNS 解析 → TCP 三次握手 → [TLS 握手] → 组装 HTTP 请求 → 服务端处理返回 → 浏览器解析渲染`。
- **展开**：域名经本地缓存 → 系统 hosts → 递归 DNS 换 IP；与目标 IP:端口建 TCP；HTTPS 多一轮 TLS 握手与证书校验；组装报文写入 socket，经内核栈、网卡、路由到服务器。
- **边界**：真实场景还要算强缓存命中、CDN 按地域返回不同 IP、HTTP/2 多路复用省握手；拿到 HTML 后再构建 DOM / CSSOM、合并渲染树绘制。查"接口慢"先分浏览器侧慢还是服务端侧慢，两侧工具完全不同。

### Q3（5.2）｜`ECONNREFUSED`、`ECONNRESET`、`ETIMEDOUT`、`socket hang up` 各说明链路哪一段出错？（结论先行）

- **判断**：`ECONNREFUSED` = 连接根本没建立；`ETIMEDOUT` = 握手或读写一直等不到回应；`ECONNRESET` = 连接建立过、中途被对方强行重置；`socket hang up` = 响应还没回来连接先被关了。
- **展开**：建连前查"服务起没起、端口绑没绑"；建连后查"谁先关的连接、有没有超时或心跳缺失"。
- **边界**：`ETIMEDOUT` 是"没有回应"（防火墙静默丢包 / 不可达，查网络可达性）；`socket hang up` 是"回应没来、连接先没了"（查谁先断）。`EADDRINUSE` 属"服务根本起不来"，端口被占，和这四个不是一回事。

### Q4（5.2）｜线上频繁出现 `ECONNRESET`，你的判断链是什么？（结论先行）

- **判断**：先定性在建连后，再查超时不匹配，再查资源与中间设备——不先翻业务代码。
- **展开**：① 定性：`ECONNRESET` 说明连接建立过、中途被对端重置（排除"服务没起"那是 `ECONNREFUSED`）；② 查超时：第一嫌疑是 Keep-Alive 两侧不匹配，正确做法是服务端 keepAlive 超时略小于网关超时；③ 查资源：`Too many open files` 会强制关连接、进程崩溃也可致重置；④ 查中间设备：NAT / 负载均衡空闲后掐连接，特征是"空闲后的第一个请求失败，重试又好"。
- **边界**：核对"哪一端先关 + 两侧超时 + 连接数 + 是否缺心跳",不要一上来就翻业务代码。

### Q5（5.2）｜网关报 `502` 和 `504`，分别往哪查？（结论先行）

- **判断**：502 查"上游在不在"，504 查"上游为什么慢"。
- **展开**：502 是网关连不上或被拒 / 拿到非法响应——查上游进程、端口（`EADDRINUSE` 让新进程起不来）、健康检查；504 是连上了但超时内没响应完——查上游耗时（慢查询、下游依赖）、Event Loop 是否被同步任务占住、`proxy_read_timeout` 是否过短。
- **边界**：共同的坑是网关超时与服务端 `keepAliveTimeout` 打架也表现成 502 / 提前重置；先确认"断在哪一跳"再往下钻。504 先看上游耗时分布，别急着调大代理超时掩盖慢查询。

### Q6（5.2）｜`Too many open files` 怎么定位？（结论先行）

- **判断**：这是文件描述符耗尽（`EMFILE` / `ENFILE`）——每个连接、文件、socket 都占一个 fd。
- **展开**：先 `lsof -p <pid>` 数连接与文件数，区分"连接泄漏"还是"真高并发"；再 `ulimit -n` 看进程 fd 上限；然后追连接来源——下游没关、Keep-Alive 配错堆积、长连接只增不减。
- **边界**：长连接服务最容易踩——每个用户一条 SSE / WebSocket，fd 随在线人数线性增长，必须同时备 fd 上限与连接数上限两道闸。这属于资源层问题，改业务逻辑改不掉，要看生命周期与回收策略。

### Q7（5.2）｜服务端"CPU 高但 QPS 低"怎么定位？（结论先行）

- **判断**：这是典型的**事件循环被占住**——主线程忙于同步计算，就绪的连接排不上队。
- **展开**：先看 CPU 是否只热一个核（更贴主线程阻塞而非横向压力）；用 `clinic.js` / 火焰图找热点；回代码里找大循环、`readFileSync`、`JSON.stringify` 超大对象、正则回溯。
- **边界**：若 CPU 不高但延迟陡增，方向反过来——那是"等待"而非"计算"，查下游慢调用与连接池。现象相似、根因相反，先用 CPU 曲线区分。

### Q8（5.2）｜`ETIMEDOUT` 和 `socket hang up` 该怎么区分、分别往哪查？（结论先行）

- **判断**：`ETIMEDOUT` 是"没有回应"，`socket hang up` 是"回应没来、连接先没了"。
- **展开**：`ETIMEDOUT` 常见防火墙静默丢包、安全组未放行、目标不可达——`telnet` / `nc` 探端口再核对安全组；`socket hang up` 常见上游崩了、上游主动断开、代理或客户端超时掐连接——看上游进程与两侧超时。
- **边界**：两者都可能由代理超时配置不当引起，查完网络回头再对一遍网关与服务的超时配置。

### Q9（5.2）｜报了证书错误（如 `UNABLE_TO_VERIFY_LEAF_SIGNATURE`），怎么查？（结论先行）

- **判断**：这类报错落在 TLS 握手环节，几乎都是证书链、域名或系统时间的问题，不是业务代码问题。
- **展开**：先后看证书有效期 → 证书链是否完整（中间证书有没有一起下发）→ 证书域名与实际访问域名是否匹配 → 服务器系统时间是否正确。
- **边界**：自签证书未入信任链报 `DEPTH_ZERO_SELF_SIGNED_CERT`，测试可显式信任、生产换正式证书或由网关统一终结 TLS；只有 curl 报错而浏览器正常时，多半是本机 CA 库或代理拦截，先换台机器复现再定性。

### Q10（5.3）｜NestJS 帮我们封装了哪些层？它"不知道"底下什么？（结论先行）

- **判断**：NestJS 封装了 `node:http` 之上的一切——Routing、Controller、Provider / DI、Middleware、Guard、Interceptor、Pipe、Exception Filter、WebSocket Gateway。
- **展开**：它**不知道**自己底下有 epoll 与事件循环——Guard / Pipe 再怎么写，最后都落到一次 `res.end()` 把字节交给内核，从不关心 socket 怎么被标记 readable、poll 阶段怎么消费。
- **边界**：这层"不知道"正是学网络层的意义——框架把底层错误翻译成一句含糊的 `ECONNRESET` / `504`，能不能秒定位取决于懂不懂下面几层。`@Body()` 并不自动校验，没挂 Pipe 时脏数据能打穿到业务层，那是框架层盲区不是网络层问题。

### Q11（5.4）｜框架都封装好了，为什么还要学网络层？只学框架会踩什么坑？（结论先行）

- **判断**：写业务时代码永远待在最上面一层，而线上出问题时，问题往往在最下面几层。
- **展开**：典型坑有误以为网络 I/O 走线程池（其实是就绪通知）、不了解粘包导致自定义协议解析错位、同步阻塞拖垮事件循环、以为 Keep-Alive 与代理超时随便配都行。学底层不是为绕过框架裸写 TCP，而是拿到"框架之下的坐标系"——看到 `ECONNRESET` 去 TCP 层查连接生命周期，看到 `504` 先确认上游是不是慢。
- **佐证**

```

请求失败 → DNS 正常吗？→ TCP 能建连吗？→ TLS 成功吗？→ 网关正常吗？
  → Keep-Alive 有问题吗？→ Node 正常吗？→ Event Loop 阻塞吗？→ 框架报错吗？→ 业务异常吗？
（每一步都是可验证的是/否判断，逐层排除）
```

- **边界**：本模块边界是"Node 进程这一侧"，不追求徒手写生产级 HTTP 服务器、不背 TCP 状态机每一次转移。
