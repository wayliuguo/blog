## 1. 分层模型与链路坐标

### 1.1 网络分层模型

把一次网络通信从下往上切成四层，每层只解决一件事，排障时先定位故障落在哪一层：

```
┌ 应用层                  HTTP / HTTPS / WebSocket / 业务协议（定义"要什么"）
├ 传输层                  TCP（可靠、有序）   /   UDP（快、不可靠）
├ 网络层                  IP（主机寻址 + 路由）
└ 网络接口层              Ethernet / Wi-Fi（网卡把 0/1 变电信号）
```

- 你写的那句 `GET /users` 属**应用层**，但 HTTP 不管送达；送达交给 TCP（可靠有序），找路交给 IP，最终网卡把字节变成电信号。
- 请求下降链路：应用层定义语义 → 传输层可靠有序送达 → 网络层寻址路由 → 接口层变电信号，每一跳都只负责自己那一层。

### 1.2 端到端链路与排障坐标

一张从浏览器到业务函数的全景链路，是"都别扁平"的坐标系：

```
Browser → HTTP → TLS → TCP → IP → 网卡 → 内核 → Socket → epoll → libuv
        → Event Loop → node:http → 框架 → Controller
```

- **链路是对称的**：响应沿原路反向再走一遍，"请求怎么进来"和"响应怎么出去"是同一张图的两次遍历，理解其一即理解其二。
- **用户态与内核态分界**：libuv 往上是你写代码能控制的范围；内核及其以下（Socket 缓冲区、TCP、epoll）改 JS 改不动。
- **框架替你做的三件事**：把字节流切成请求、把写响应封成 `res.json()`、把连接生命周期管起来——这三件一出问题，盲区就变成故障点。
- **每层出问题的典型现象表**：先定位层，再决定查什么，不要一上来全局搜代码。

| 层 | 典型现象 / 错误码 |
| --- | --- |
| DNS | `ENOTFOUND` / `EAI_AGAIN` |
| TCP 建连 | `ECONNREFUSED` / `ETIMEDOUT` / `EADDRINUSE` |
| 连接生命周期 | `ECONNRESET` / `socket hang up` |
| TLS | 证书校验失败、`DEPTH_ZERO_SELF_SIGNED_CERT` |
| HTTP | 400 / 404 / 431 |
| 网关 | 502 / 504 |
| 运行时资源 | `EMFILE` / `Too many open files` |

## 2. TCP 与 Socket 编程

### 2.1 TCP 的三重保证与三次握手

TCP 在不可靠的 IP 网络之上提供三种保证：

| 特性 | 含义 | 没有它会怎样 |
| --- | --- | --- |
| 面向连接 | 通信前先三次握手 | 对方可能根本没准备好 |
| 可靠 | 丢包重传、校验和、确认应答 | 文件下载残缺 |
| 有序 | 序号保证到达顺序 | 消息乱序 |

**三次握手为什么不能是两次**：核心是"双方都必须确认我发得出去、也收得到"这两个方向都通。

```
客户端                                服务端
 SYN（seq=x）      ────────────────▶   收到 SYN，分配资源（缓冲区/端口）
 SYN+ACK（seq=y）  ◀────────────────   （两次握手在此就跳过下一步）
 ACK（确认）       ────────────────▶   确认客户端收到，放心投入资源
```

- 若省成两次：服务端收到 `SYN` 就分配资源，滞留的旧/重复报文会让它空等超时，白白占资源——SYN Flood 利用的正是这一点。
- 第三次 `ACK` 让服务端确认"客户端确实收到了回应"，双方才验证过收发能力。

### 2.2 字节流、粘包与消息边界

**`data` 是 `Buffer` 不是字符串**：网络上流动的是字节，`socket.on('data')` 拿到的是 Buffer，需手动 `.toString('utf8')` 才是字符串。

```
socket.write('Hello Node.js')
   → 线缆里流动的是字节 H e l l o ...
   → 一串没有"消息边界"的 0/1
   → Node 收进 Buffer
   → JS 手动 .toString() 才是字符串
```

**TCP 只保证"可靠、有序"，不保证"你发几次、我收几次"**——它不认业务消息边界：

```
发送方：write('hello') + write('world')
接收方：① 一次 data = 'helloworld'            （粘包）
       ② 第一次 = 'hel'  第二次 = 'loworld'   （拆包）
       ③ 混合 = 'hello' + 'wor' + 'ld'
```

**边界方案**：

- **长度前缀**（`Length(4B) + Body(NB)`）最通用——不依赖内容里是否恰好出现分隔符、不浪费补齐字节、对二进制同样适用；接收方先读 4 字节得到 N，再精确读 N 字节，多余的留缓冲等下一条。
- 定长（每条固定长度、不足补位，简单但低效）、分隔符（`\r\n` / `\n` 结尾，常见于文本日志、Redis 协议）次之。
- HTTP 之所以"看起来"没粘包，是因为它用 `Content-Length` 或 chunked 自己定义了边界——你写的 TCP 协议也要自己定义。

### 2.3 Socket 与 node:net

**Socket 是"应用程序使用操作系统网络能力的接口抽象"**，JS 通过它收发网络字节。

- **四元组唯一区分连接**：`源IP:源Port → 目标IP:目标Port`；服务端固定端口，客户端端口由操作系统随机分配、用完回收复用，故即使目标同是 `:3000`、只要源 IP:源 Port 不同就是不同连接——单机可撑上万连接。
- **`node:net` 是最底层入口**：处理 `data`（收字节）/ `end`（对端停止发送）/ `error`（异常）三类事件。
- **`net.Socket` 本质是 Duplex Stream**（同时 Readable + Writable），收发可并行互不阻塞，正是 TCP 全双工的体现：

```
             net.Socket（Duplex Stream）
            ╱                      ╲
      Readable                    Writable
      socket.on('data')          socket.write()
        收数据                      发数据
```

### 2.4 内核、epoll 与 libuv 的分工

**盯着 Socket 的是内核，不是 Node**：10,000 个 Socket 若逐个轮询"你有数据吗"效率极低，Linux `epoll` 让内核主动通知就绪。

```
10000 个 Socket → 全部交给内核关注 → epoll → 内核通知：Socket 583 有数据了
```

**libuv 抹平平台差异**：Linux `epoll` / macOS `kqueue` / Windows `IOCP` 被抽象成统一异步接口，写 `socket.on('data')` 时无需关心当前平台。

**单线程扛万连接**：等待交给内核与 libuv，主线程只处理已就绪的事件——"等待不占线程"：

```
一万个 Client → OS（内核盯所有 Socket）→ epoll/kqueue/IOCP（就绪才通知）
  → libuv（跨平台 + 事件派发）→ Event Loop → JS 回调（只处理就绪）→ 完成
```

**网络 I/O 不走线程池**：`net` / `http` / `https` 走 OS 事件通知、主线程回调；只有文件 I/O、部分 DNS、`crypto`、`zlib` 等进线程池。不要记成"异步 = 线程池"。

### 2.5 传输层的背压与 pipe / pipeline

**背压来自"生产快于消费"**：磁盘读 500 MB/s、网络只能发 10 MB/s 时，不做控制数据会一路积压内存直到 OOM。

**`write()` 返回值就是背压信号**：`socket.write()` 返回 `false` 表示内部缓冲已到压力阈值，应暂停生产，等 `drain` 事件（缓冲已排空）再继续：

```
Producer ─▶ Writable Buffer ─▶ Consumer
      ▲          │
      │     消费慢 → 缓冲到阈值
      │          │
      │     write 返回 false（暂停）
      │          │
      └─ drain（可继续）◀───── Consumer 慢慢消费
```

- **别手写 `on('data') + write` 接背压**：反例会丢掉背压，返回 `false` 也照写，积压随发送总量一路涨（实测峰值差 20 倍）。
- **`pipe()` 内部自动协调**：下游跟不上就暂停上游、`drain` 后继续，只积压当前写的那一块。
- **`pipeline()` 更进一步**：任一环出错时统一销毁整条链路，避免资源泄漏，生产更推荐；`pipe` 出错不会自动销毁，需手动处理。

## 3. HTTP 与 HTTPS

### 3.1 HTTP 应用层协议与报文边界

TCP 只懂字节流、不懂"我要 `GET /users`"，所以要在其上再定义一层应用层协议，约定 `Method / URL / Header / Body / Status Code`。

- 报文用首行 + 若干头 + **一个空行** + 体；头与体靠空行分界，体的结束靠 `Content-Length` 或 `Transfer-Encoding: chunked`。
- 用框架能直接拿 `@Body()`，是因为框架已按 HTTP 规则把字节流解析好。
- 手写 `node:http` 会撞上一串工程问题，正是框架要去收的事：

```
路由怎么管理？   参数怎么解析？   Body 怎么解析？
异常怎么兜底？  权限怎么横切？  代码怎么分层？
  → Express / Fastify（路由+中间件）→ NestJS（装饰器+DI）逐层抽象
```

### 3.2 req 与 res 本质上也是流

不是因为 HTTP 数据是一个拼好的字符串，而是它经 TCP 到达时本就是分块字节流、可能很大、不会一次到齐。

- `req` 是 **Readable**：请求体分多次到达，`chunk` 是 Buffer，靠 `data` 累积 + `end` + `Buffer.concat(chunks).toString()` 拼回字符串。
- `res` 是 **Writable**：可多次 `write`，最后 `end()` 收尾。
- 收益：大文件下载可直接 `readableStream.pipe(res)` 边读边发，不必先全部读进内存。

**流式响应 vs 预知长度的边界——Content-Length 与 chunked**：

- 一次性算出的响应体可以在 `writeHead` 带 `Content-Length`，但必须用 `Buffer.byteLength()`（字节长度）；`'你好'` 字符长 2、字节长 6，写成字符长度会让客户端截断或报错。
- 流式响应算不出总长度，改用 `Transfer-Encoding: chunked`：响应体切成若干块、每块自带长度前缀、以长度 0 的块结束，实现"边产生边发送边结束"。

### 3.3 Keep-Alive 与三个超时

Keep-Alive 让**多个 HTTP 请求复用同一条 TCP 连接**，省掉每次建连/断连的握手与挥手成本。

- `keepAliveTimeout`：keep-alive 连接空闲多久后服务端主动关闭。
- `headersTimeout`：建连后多久内必须收齐请求头（防慢速攻击）。
- `requestTimeout`：单请求从开始到结束的总时限。

**关键坑**：`headersTimeout` 必须 **>** `keepAliveTimeout`，否则空闲连接被服务端按时关掉时，"已关闭"状态未与请求头超时逻辑对齐，后续请求被丢弃，客户端表现为 `ECONNRESET` / `socket hang up`。一句话原则：**反向代理的超时 ≥ 服务端超时**。

### 3.4 HTTPS 与 TLS

HTTPS 不是新协议，而是 **HTTP over TLS**——在 HTTP 与 TCP 之间多垫一层 TLS。TLS 解决三件事：

| 能力 | 作用 | 没有它会怎样 |
| --- | --- | --- |
| 加密 | 内容只有双方能读 | 中间人窃听明文 |
| 身份认证 | 证书证明"你真的是 example.com" | 中间人伪造钓鱼 |
| 数据完整性 | 防响应被篡改 | 注入广告/恶意脚本 |

握手分步：ClientHello（版本/套件/随机数）→ ServerHello + 证书链 → 校验证书链与域名有效期 → 协商会话密钥 → Finished 后进入加密传输。生产上 TLS 通常在网关（Nginx / 负载均衡）卸载，Node 服务跑内部明文 HTTP，证书续期与多实例统一入口都更省心。

### 3.5 HTTP 版本演进：队头阻塞与多路复用

- **HTTP/1.1**：即使复用了 TCP 连接，同一条连接上的请求/响应仍是**串行**的——前一个响应没回来，后一个排队，即**应用层队头阻塞**；浏览器只能靠开多条 TCP 连接（约 6 条）绕过，额外付出握手成本。
- **HTTP/2**：单条 TCP 连接上划分多个 **Stream** 交错传输（多路复用），加二进制分帧与 HPACK 头压缩；但多 Stream 仍共享同一条 TCP，丢包会触发 TCP 层队头阻塞。
- **HTTP/3**：传输层换成基于 UDP 的 **QUIC**，在用户态自己实现可靠传输、多路复用、拥塞控制与 TLS，各 Stream 更独立：某个 Stream 丢包只影响它自己。

### 3.6 常见报错码与排障方向

| 现象 | 成因 | 排查方向 |
| --- | --- | --- |
| `ECONNRESET` | 对端突然重置（keep-alive 被服务端先关，或读写时对方已断） | 核对两侧超时、是否有心跳缺失 |
| `socket hang up` | 客户端视角连接被对方提前关闭 | 看上游是否崩、是否超时断连 |
| `ECONNREFUSED` | 目标地址/端口无进程监听 | 确认进程在跑、端口正确、网络可达 |
| `431` | 请求头过大（Cookie / 鉴权头累积） | 精简头；必要时调大 `maxHeaderSize` |
| `502` vs `504` | 前者网关根本没连上上游；后者连上了但上游迟迟不回 | 502 查上游存活；504 查上游处理耗时 |

方法论：遇网络报错先定位"断在哪一跳"，再看对应超时与配置，别一上来翻业务代码。

## 4. 实时通信：WebSocket 与 SSE

### 4.1 WebSocket 的定位与分层

普通 HTTP 是"一问一答，立刻结束"；聊天、游戏、行情、通知这类业务需要服务端**随时主动推**，于是要一条 `Client ⇄ Server` 常开的长连接。

- 分层是 **WebSocket → TCP → IP**，WebSocket 是 TCP 之上的应用层协议，**不替代 TCP**。
- 它把"可靠双向传消息"标准化了：Handshake、Frame、Message、Ping / Pong、Close、Text / Binary。
- 若绕过它直接用 `net.createServer()` 写裸 TCP，消息格式、粘包分包、心跳、断线重连全要自己造。

### 4.2 建立连接：HTTP 升级握手

WebSocket 并**不新建一条 TCP 连接**，而是先复用一次 HTTP 完成协议升级：

```
HTTP 普通请求（Upgrade: websocket + Sec-WebSocket-Key + Version: 13）
   → 服务端返回 101 Switching Protocols（Sec-WebSocket-Accept）
   → WebSocket 帧协议接管同一条 TCP 连接 → Client ⇄ Server 长连接
```

- `Sec-WebSocket-Accept` **不是加密**：把 Key 拼固定串做 SHA-1 + Base64 回传，只用于证明"对方真懂握手"、防缓存代理把升级请求误判成普通 HTTP 返回脏数据。

### 4.3 长连接的心跳与生产必备件

**为什么必须心跳**：客户端断网、切网络、进程被杀、NAT 超时后服务端不能立刻感知，连接"假死"还占着内存与 fd。定期 `Ping / Pong` 探测，连续多次无 Pong 则判定失效并释放 Socket。

```
Server ─Ping（你还活着吗？）─▶ Client ─Pong（活着）─▶ Server（健康）
      连续多次无 Pong → 判定连接失效 → 释放 Socket
```

能上生产的 WebSocket 服务，绝不只是"建连 + 收发"两步，至少同时考虑：**心跳、断线感知、客户端重连、空闲/读写超时、连接健康度、关键消息确认、扩容分布**。

- **多实例**：连接散落不同进程，A 实例无法把消息发给 B 实例持有的连接，广播必然漏发——需共享订阅关系（Redis 发布订阅 / 消息总线）或集中式连接管理；成熟项目直接用带房间/集群能力的库，而非从裸 `net` 起步。

### 4.4 SSE：单向推送

SSE（Server-Sent Events）用一条普通 HTTP 长连接做 `Client ← Server` 的单向推送。

- 报文纯文本、按行组织、空行分隔事件，常见字段 `event:` / `data:` / `id:` / `retry:`。
- **断线续传**：服务端给每条事件带 `id:`，浏览器 `EventSource` 自动重连并带 `Last-Event-ID`，服务端从断点续推。
- **Node 三步实现**：`Content-Type: text/event-stream` → 关默认缓冲（`Cache-Control: no-cache`、`Connection: keep-alive`）→ 往 `res` 持续 `write` 事件文本，并监听 `req.on('close')` 清定时器（否则泄漏）。
- **流式输出场景正合适**：20 秒任务若等算完再返回像卡死，边产生边推则立即显示；典型场景是日志回放、任务进度、大文件生成、实时监控——共同点是数据分段来且不需客户端高频回传。

### 4.5 SSE 与 WebSocket 的选型

| 维度 | SSE | WebSocket |
| --- | --- | --- |
| 方向 | 单向（Server → Client） | 双向全双工 |
| 基于纯 HTTP | 是 | 握手后升级为独立协议 |
| 自动重连 | 浏览器内置 `EventSource` | 需自己实现 |
| 二进制 | 仅文本（需自行编码） | 原生 Text / Binary |
| 网关 | 易配 | 需配 `Upgrade` 头 |

判断准则：业务本质是 `Server → Client` 持续推送（通知 / 行情 / 日志 / 进度）→ SSE 足够；需 `Client ⇄ Server` 高频双向（聊天 / 协作 / 游戏）→ WebSocket。

## 5. 端到端链路与排障

### 5.1 31 步链路

一次 `GET /users` 从浏览器到 Controller、再原路返回，共 31 步。压缩成关键节点：

```
DNS 解析 → 拿 IP → 选端口 → SYN → SYN+ACK → ACK（三次握手）
  → [TLS] ClientHello → ServerHello+证书 → 验证证书 → 协商密钥 → Finished
  → 组装报文 → 写入 socket → 内核协议栈 → 网卡发出 → 路由转发
  → 服务端网卡 → 内核重组进 Socket Receive Buffer → fd 变 readable
  → epoll 通知 → libuv 取事件 → poll 阶段
  → node:http 解析 → 构造 req/res → 触发 'request'
  → Express/Fastify 适配层 → 中间件链 → Guard → Interceptor → Pipe → Controller
  → 序列化写回 → 原路返回 → 浏览器渲染
```

- **你那行 `return []` 只是第 30 步**：前面 29 步都在"把请求安全送到这一行"，最后 1 步是"把结果安全送回去"。
- **第 18–22 步是 Node 网络能力的真正底座**：Receive Buffer → fd 就绪 → epoll 通知 → libuv 取事件 → poll 阶段消费，这才是"单线程扛万连接"的落点。

### 5.2 排障坐标系

| 链路环节 | 典型现象 | 往哪查 |
| --- | --- | --- |
| DNS（1–2） | `ENOTFOUND` / `EAI_AGAIN` | `nslookup`/`dig` 验证解析 |
| TCP 建连（4–6） | `ECONNREFUSED` / `ETIMEDOUT` | 探端口，服务/防火墙/安全组 |
| TLS（7–11） | 证书错误、红锁 | 证书有效期、系统时间、证书链 |
| 网关（16） | 502 / 504 | 代理配置、`proxy_read_timeout`、上游存活 |
| Keep-Alive（31） | `ECONNRESET` / `socket hang up` | 比对两侧超时谁先关 |
| 文件描述符（18） | `EMFILE` / `Too many open files` | `lsof` 数连接、`ulimit -n`、连接泄漏 |
| 事件循环（20–22） | CPU 高但 QPS 低 | 同步阻塞调用、火焰图 |
| 响应序列化（31） | 大 JSON 卡住、内存涨 | 改流式 / 分页 / 压缩 |
| 框架层（27–28） | 401 / 403 / 400 | 守卫、DTO、ExceptionFilter |
| 业务层（30） | 下游慢、偶发 5xx | Service 日志、链路追踪 |

**可验证的是/否判断链**：DNS 正常吗 → TCP 能建连吗 → TLS 握手成功吗 → 网关正常吗 → Keep-Alive 有问题吗 → Node 服务正常吗 → 事件循环被阻塞吗 → 框架报错吗 → 业务异常吗。每一步都是可验证的是/否判断，逐层排除，比"重启试试"高效。

### 5.3 框架的封装与"两层不知道"

NestJS 封装了 `node:http` 之上的一切：Routing、Controller、Provider / DI、Middleware、Guard、Interceptor、Pipe、Exception Filter、WebSocket Gateway / Microservices。

```
业务代码（@Controller / @Get / @Injectable）
  → Controller（路由匹配、参数绑定）
  → NestJS（DI、Guard、Interceptor、Pipe、Filter）
  → Express / Fastify Adapter（中间件链、req/res 增强）
  → node:http（报文解析、触发 'request'）
  → TCP Socket（net.Socket，Duplex Stream）
  → libuv + OS（epoll / kqueue / IOCP、内核协议栈）
```

**两层"不知道"**：

1. 框架不知道自己底下有 epoll 与事件循环——Guard / Pipe 再怎么写，最后都落到一次 `res.end()` 把字节交给内核。
2. 只学框架的你也不知道请求先在 Receive Buffer 排队、被标记可读才触发——框架把底层错误翻译成一句含糊的 `ECONNRESET` 或 `504`。

### 5.4 为什么还要学这一层

**写业务时代码永远待在最上面一层，出问题时问题往往在最下面几层**。学底层不是为裸写 TCP，而是拿到"框架之下的坐标系"——把"报错"翻译成"该去哪一层看"。

- 框架像电梯，让你直达顶层写业务；电梯坏了你得会走楼梯——楼梯就是 TCP、HTTP、内核、libuv 这几层。
- `@Body()` 并不自动校验，没挂 Pipe 时脏数据能打穿到业务层——这属于框架层盲区，排查时要分清不是网络层问题。
