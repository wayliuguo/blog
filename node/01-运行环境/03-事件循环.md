## 事件循环（Event Loop）

事件循环是 Node.js 的核心机制，它让 JavaScript 可以"非阻塞"地处理异步操作。

### 简化版执行顺序

```
执行同步代码
    ↓
处理微任务队列（process.nextTick、Promise.then）
    ↓
处理宏任务队列（setTimeout、setInterval、I/O 回调）
    ↓
重复以上步骤
```

### 代码示例

```javascript
console.log('1')  // 同步，先执行

setTimeout(() => {
    console.log('2')  // 宏任务
}, 0)

Promise.resolve().then(() => {
    console.log('3')  // 微任务
})

console.log('4')  // 同步，后执行

// 输出顺序：1 → 4 → 3 → 2
```

## 宏任务与微任务

| 类型 | 包含 | 优先级 |
|------|------|--------|
| 微任务 | `process.nextTick`、`Promise.then/catch/finally` | 高（先执行） |
| 宏任务 | `setTimeout`、`setInterval`、I/O 回调、`setImmediate` | 低（后执行） |

**关键规律**：
1. 同步代码执行完
2. 清空微任务队列
3. 执行一个宏任务
4. 再清空微任务队列
5. 再执行下一个宏任务

```javascript
console.log('1')

setTimeout(() => {
    console.log('2')
    Promise.resolve().then(() => console.log('3'))
}, 0)

setTimeout(() => {
    console.log('4')
}, 0)

Promise.resolve().then(() => console.log('5'))

console.log('6')

// 输出：1 → 6 → 5 → 2 → 3 → 4
```

## Node.js 真的"单线程"吗：四层结构

面试里常听到"Node.js 是单线程的"，这句话**不准确**。准确的表述是：

> **默认情况下，Node.js 用一个主线程执行你的 JavaScript，但 Node.js 进程本身不止一个线程。**

真正干活的不只是你写的那段 JS。把一次 `fs.readFile` 拆开看，它要穿过四层：

```txt
┌───────────────────────────────────────────────┐
│  你的 Node.js 应用（你写的 JS 代码）             │
├───────────────────────────────────────────────┤
│  V8 引擎：解析 / JIT 编译 / 执行 JS / 垃圾回收   │
├───────────────────────────────────────────────┤
│  Node.js Bindings：把 JS 调用桥接到底层 C/C++    │
├───────────────────────────────────────────────┤
│  libuv：Event Loop（事件循环）+ Thread Pool      │
│        （线程池负责 fs / dns / crypto / zlib）    │
├───────────────────────────────────────────────┤
│  OS：epoll / kqueue / IOCP 等 I/O 事件通知       │
└───────────────────────────────────────────────┘
```

- **单线程的部分**：只有"执行 JS"这一步是单线程的——同一时刻只有一个 JS 调用栈在跑，所以不存在多线程同时改同一个变量的竞态。
- **多线程的部分**：libuv 内部有一个**线程池（Thread Pool）**，默认 4 个线程，专门替你去干那些 OS 没法异步通知的活（见下文"哪些 I/O 会进 libuv 线程池"）。

> 心智模型：说 Node"单线程"指的是 JS 执行模型，不是说整个进程只有一个线程。这解释了为什么"CPU 密集计算"会卡死整个服务（占住唯一的 JS 线程），而"异步 I/O"不会（活儿被甩给了别的线程 / OS）。

## 事件循环的六个阶段

很多人把事件循环理解成"宏任务队列 + 微任务队列"两个队列轮转，这是浏览器视角。Node.js 的事件循环是一串**有固定顺序的阶段（Phase）**，每个阶段是一个回调队列：

| 阶段 | 主要处理什么 |
|------|--------------|
| `timers` | `setTimeout` / `setInterval` 中**到期**的回调 |
| `pending callbacks` | 上一轮推迟的系统回调（如 TCP 连接错误的少数回调） |
| `idle, prepare` | 内部使用，开发者一般碰不到 |
| `poll`（轮询） | **I/O 的核心**：检索新的 I/O 事件，执行 I/O 回调（文件、网络等） |
| `check` | `setImmediate` 的回调 |
| `close callbacks` | 关闭类事件的回调，如 `socket.on('close')` |

每进入一个阶段，Node 会**把该阶段队列里的回调一次性执行完**（或执行到系统上限），然后离开，进入下一阶段，转完一圈再从 `timers` 开始。

> `poll` 是整台机器的心脏：当没有任何定时器待触发、也没有 `setImmediate` 时，事件循环就停在 `poll` 阶段**阻塞等待**新的 I/O 事件到来——这也是 Node 能"看起来一直在线却不占 CPU"的原因。

## 精确的微任务模型：nextTick 与 Promise

前面"宏任务 / 微任务"是简化模型。要真正答对输出题，得精确到**两个独立的微任务队列**：

1. **`process.nextTick` 队列**（不属于 Event Loop 的任何一个阶段，属于"当前操作结束后立刻执行"）
2. **Promise 微任务队列**（`Promise.then/catch/finally` 注册的回调）

它们的优先级是：**`nextTick` 队列整体先于 Promise 微任务队列执行**，且两者都会被"清空到空"才罢休。

### 关键易错点：微任务检查点

> **微任务并不是"整轮 Event Loop 结束后才执行一次"，而是每次从 JS 回调返回到调度层（C++ 侧）时，都会触发一次 microtask checkpoint 来清空微任务队列。** 也就是说，每跑完一个回调，就会先把这个回调新产生的所有微任务（含 nextTick 和 Promise）处理干净，再继续下一个回调。

用经典输出题证明：

```javascript
setTimeout(() => {
    console.log('timer1')
    Promise.resolve().then(() => console.log('promise1')) // timer1 的回调里再挂一个 Promise
}, 0)

setTimeout(() => {
    console.log('timer2')
}, 0)

// 输出：timer1 → promise1 → timer2
```

为什么不是 `timer1 → timer2 → promise1`？因为两个 `setTimeout` 都在同一轮 `timers` 阶段。执行 `timer1` 回调时打印 `timer1`，并往 Promise 微任务队列挂了 `promise1`。`timer1` 回调一返回调度层，**立刻触发 microtask checkpoint**，把 `promise1` 清空（打印 `promise1`），然后才轮到 `timer2` 回调（打印 `timer2`）。

> 反直觉但很重要：微任务穿插在"每个宏任务回调之间"，而不是"整轮事件循环之后"。记不住这个，遇到复杂输出题就会算错。

## setImmediate 与 setTimeout(0) 的不确定性

```javascript
setTimeout(() => console.log('timeout'), 0)
setImmediate(() => console.log('immediate'))
// 在文件顶层直接跑：顺序不确定
```

- **在文件顶层**运行：`setTimeout(..., 0)` 实际至少需要 1ms 才到期，而 `setImmediate` 在下一轮 `check` 阶段就触发。两者都被排到"下一轮循环"，谁先谁后取决于定时器何时真正到期，所以**顺序不确定**。
- **在一个 I/O 回调里**运行：情况相反且**稳定**——当前处于 `poll` 阶段，紧接着就是 `check` 阶段（`setImmediate` 立即执行），而 `setTimeout(0)` 要等下一轮循环的 `timers` 阶段，所以此时 `setImmediate` 恒早于 `setTimeout(0)`。

> 现代 Node（v20+）对 `timers` 阶段的触发时机做过调整，"timers 在 poll 之后被推迟触发"的情形更常见。所以**不要死记"定时器一定先跑"**，而是用"阶段顺序 + 微任务检查点"的心智模型去推演，才是最稳的。

## 事件循环饥饿：递归 process.nextTick

`process.nextTick` 的回调会在"任何阶段切换之前"被无脑清空。如果递归地往 `nextTick` 队列塞自己，队列永远清不空，事件循环就**永远进不了下一个阶段**：

```javascript
function starve() {
    process.nextTick(starve) // 每次都往 nextTick 队列头里加自己
}
starve()

setTimeout(() => console.log('我永远没机会执行'), 0)
console.log('这一行能跑') // 先打印
// setTimeout 的回调永远不会执行：事件循环卡在清空 nextTick 上
```

> 决策模型：用 `process.nextTick` 做"延迟到当前操作之后、但尽量早"的回调（比如错误先抛给用户再继续）；但**绝不要**在 `nextTick` 里递归调度无限任务——那会饿死整个事件循环。需要"让出执行权且不饿死循环"时，用 `setImmediate` 更合适（它排进下一轮 `check` 阶段，不会阻塞阶段推进）。

## 内核多路复用：epoll / kqueue / IOCP 为什么存在

假设服务端有 1 万个 TCP 连接，如何知道"哪些 socket 现在有数据可读"？

**错误做法（忙轮询）**：每毫秒遍历 1 万个 socket 调用 `recv`，没数据的也调一次。CPU 100% 空转，连接越多越慢。

**正确做法（I/O 多路复用）**：告诉内核"我关心这 1 万个 socket 的读事件"，内核在网卡收到数据、把字节放入该 socket 的缓冲区后，**主动通知**你"第 1024 号和第 8833 号现在有数据了"。你只需处理真正就绪的那几个。

不同操作系统的实现：

| 机制 | 操作系统 | 工作方式 |
|------|---------|---------|
| epoll | Linux | 内核维护就绪列表，返回就绪事件 |
| kqueue | macOS / BSD | 类似 epoll，事件更通用 |
| IOCP | Windows | 完成端口，异步完成通知 |

```txt
忙轮询（差）：  for each socket: recv()  →  CPU 爆满
epoll（好）：   epoll_wait() 睡到内核叫醒 → 只处理就绪的少量 socket
```

> 心智模型：忙轮询像你每分钟挨个打电话问"到货没"；epoll 像你告诉仓库"到货了 call 我"，然后去喝咖啡。

## 哪些 I/O 会进 libuv 线程池

一个高频误解："Node 异步 I/O 都是多线程并发处理的"。其实要分两类：

| 类型 | 是否用 libuv 线程池 | 机制 |
|------|---------------------|------|
| 网络 I/O（HTTP、TCP、Socket） | **否** | 走 OS 的 `epoll` / `kqueue` / `IOCP` 事件通知，主线程在 `poll` 阶段等通知 |
| `fs`（文件读写） | **是** | 交给 libuv Thread Pool |
| `dns`（如 `dns.lookup`） | **是** | 交给 libuv Thread Pool |
| `crypto`（加解密） | **是** | 交给 libuv Thread Pool |
| `zlib`（压缩） | **是** | 交给 libuv Thread Pool |

> 为什么网络 I/O 不进线程池？因为操作系统内核本身就提供"当这个 socket 有数据时通知我"的机制（epoll 等），Node 只需要**等通知**即可，不需要开线程去阻塞轮询。而文件操作、DNS 解析、加解密这些要么 OS 不提供事件接口、要么本身就是 CPU/阻塞型工作，才需要 libuv 真正开线程去干。

## 彻底理解 Event Loop：一张调度模型图

把前面所有概念串起来，一次"任务"的完整生命周期是：

```txt
┌─────────────────────────────────────────────────────────────┐
│ 1. 同步代码执行                                               │
│    └─ 全部进入 Call Stack 顺序执行，遇到异步 API 就注册回调     │
└───────────────────────────┬─────────────────────────────────┘
                            │ Call Stack 清空
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 2. 微任务检查点（每次回调返回调度层都会触发）                    │
│    ├─ 清空 process.nextTick 队列（优先）                       │
│    └─ 清空 Promise 微任务队列                                  │
└───────────────────────────┬─────────────────────────────────┘
                            │ 微任务清空
                            ▼
┌─────────────────────────────────────────────────────────────┐
│ 3. 进入 Event Loop，按阶段轮转一圈                             │
│    timers → pending → idle/prepare → poll → check → close     │
│    └─ 每跑完一个阶段里的某个回调，回到第 2 步清空微任务          │
└───────────────────────────┬─────────────────────────────────┘
                            │ 一轮结束
                            ▼
                    回到第 3 步继续轮转，直到所有队列清空、无定时器
```

> 一句话心智模型：**同步代码 → Call Stack 清空 → nextTick 队列 → Promise 微任务 → Event Loop 各阶段轮转（每个回调间再插一轮微任务清空）**。记住这张图，绝大多数"输出顺序"面试题都能手推出来。

## 面试题

### Q1: 事件循环中微任务和宏任务的执行顺序？

同步代码 → 清空微任务队列 → 执行一个宏任务 → 清空微任务队列 → 下一个宏任务。微任务包括 `process.nextTick` 和 `Promise.then`，宏任务包括 `setTimeout`、`setInterval`、I/O 回调。

### Q2: `process.nextTick` 和 `Promise.then` 谁先执行？

`process.nextTick` 的优先级高于 `Promise.then`。`nextTick` 是微任务队列中最先被执行的。但要注意：微任务不是在整轮事件循环结束后才跑一次，而是**每个 JS 回调返回调度层时都会触发一次 microtask checkpoint** 去清空它们。

### Q3: Node.js 事件循环有哪六个阶段？哪个是 I/O 核心？

`timers` → `pending callbacks` → `idle/prepare` → `poll` → `check`（`setImmediate`）→ `close callbacks`。`poll` 阶段是 I/O 核心，负责检索新的 I/O 事件并执行 I/O 回调；当没有定时器、没有 `setImmediate` 时，循环会停在 `poll` 阶段阻塞等待新事件。

### Q4: 网络 I/O 会进入 libuv 线程池吗？哪些会？

不会。网络 I/O（HTTP/TCP/Socket）走 OS 的 `epoll`/`kqueue`/`IOCP` 事件通知，主线程在 `poll` 阶段等通知即可。真正进 libuv Thread Pool 的是 `fs`（文件）、`dns.lookup`、`crypto`（加解密）、`zlib`（压缩）这类 OS 不提供事件接口或本身偏阻塞/CPU 的工作。

### Q5: `setImmediate` 和 `setTimeout(0)` 谁先执行？

没有固定答案，取决于运行位置。在文件顶层直接跑时顺序不确定；在 I/O 回调里跑时，`setImmediate` 恒先执行（当前 `poll` 阶段之后立刻是 `check` 阶段，而 `setTimeout(0)` 要等下一轮 `timers` 阶段）。现代 Node 对 timers 触发时机有调整，建议用"阶段 + 微任务检查点"模型推导而非死记。
