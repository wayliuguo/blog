# 模块系统：CommonJS 与 ES Module

## 为什么不能把所有代码写在一个文件里？

Node.js 项目里你不可能把所有逻辑都堆进一个 `index.js`。一个真实的后端服务通常会按职责把代码拆到不同目录，每个文件只负责一块功能，再用模块系统把它们拼起来：

```
src/
├── controllers/   处理 HTTP 请求入口，解析参数、返回响应
├── services/      业务逻辑，编排多个下游调用
├── models/        数据访问层，封装数据库读写
├── utils/         通用工具函数，如日期、校验、加密
├── config/        读取配置（端口、密钥、环境变量）
├── db/            建立并导出数据库连接
└── index.js       程序入口，启动服务、挂载路由
```

不同文件之间如何互相调用？靠的就是模块系统。它至少要解决三件事：怎么把一个文件里的东西"导出"、怎么在另一个文件里"导入"、以及导入时到底拿到的是值本身还是值的引用。Node.js 目前有两套并存的模块系统。

```
CommonJS   —— Node.js 早期自带的方案，后缀 .js / .cjs
ES Module  —— 语言标准的方案，后缀 .mjs / 配 type 的 .js
```

## CommonJS：用 require 和 module.exports 拼装程序

CommonJS 是 Node.js 的"出厂默认"。一个最朴素的导出长这样：

```js
// math.js
function add(a, b) {
  return a + b;
}

function subtract(a, b) {
  return a - b;
}

module.exports = { add, subtract };
```

导入时使用 `require`，拿到的是 `module.exports` 的值：

```js
// index.js
const math = require('./math');
console.log(math.add(1, 2));   // 3
console.log(math.subtract(5, 2)); // 3

// 也可以直接解构
const { add, subtract } = require('./math');
```

`require` 接收的是模块标识符：以 `./` 或 `../` 开头是相对路径（Node 会去补 `.js` / `.json` / `.node` 扩展名并解析目录）；不以 `.` 开头则当作包名，去 `node_modules` 里找。

### 模块缓存：同一个文件只执行一次

`require` 不是每次都重新读文件、重新执行。Node 会把每个已加载模块的结果缓存在 `require.cache` 里，第二次 `require` 同一个路径时，直接返回缓存的 `module.exports`，模块顶层代码不会再跑一遍。

下面是一个直观的例子，演示缓存带来的"只执行一次"：

```js
// counter.cjs
let count = 0;
count += 1;
console.log('counter 模块被执行了，count =', count);
module.exports = { get: () => count };
```

```js
// index.cjs
const a = require('./counter'); // 打印一次
const b = require('./counter'); // 不再打印，直接命中缓存
console.log(a === b); // true，两次拿到的是同一个对象
```

预期输出：

```
counter 模块被执行了，count = 1
true
```

这意味着：如果模块顶层有副作用（连数据库、起定时器、打印日志），它只会在第一次 `require` 时触发；这也是为什么循环依赖里可能拿到"还没初始化完"的半成品对象——模块执行到一半就把当前 `module.exports` 交出去缓存了。

### exports 与 module.exports 的陷阱

每个 CommonJS 文件里，`exports` 其实是 `module.exports` 的一个引用（`exports === module.exports` 初始为 `true`）。给 `exports.xxx` 赋值能生效，是因为你在给同一个对象挂属性；但一旦你**重新给 `module.exports` 赋值**，两者就分道扬镳了。

```js
// 正确：给共享对象挂属性
exports.add = (a, b) => a + b;   // 等价于 module.exports.add = ...

// 陷阱：重新赋值 module.exports 后，exports 上的挂件全失效
module.exports = { add: (a, b) => a + b };
exports.subtract = (a, b) => a - b; // 写在 module.exports 赋值之后，外界拿不到！
```

更隐蔽的坑是直接给 `exports` 赋值：

```js
exports = { add: (a, b) => a + b }; // 只是把局部变量 exports 指到新对象
// module.exports 没变，外界 require 到的还是原来的空对象 {}
```

记住一条铁律：最终被导出的是 `module.exports`，`exports` 只是它的快捷引用。要整体替换导出对象，用 `module.exports = ...`；要增量挂属性，用 `exports.xxx = ...`，且别在之后重赋值 `module.exports`。

## ES Module：用 import 和 export 描述依赖关系

ES Module（ESM）是 JavaScript 语言标准里的模块方案，语法和前端打包工具完全一致。导出用 `export`，导入用 `import`：

```js
// math.mjs
export function add(a, b) {
  return a + b;
}

export const PI = 3.14;

export default { add, PI }; // 默认导出
```

```js
// index.mjs
import { add, PI } from './math.mjs'; // 命名导入
import myMath from './math.mjs';      // 默认导入

console.log(add(1, 2));    // 3
console.log(PI);           // 3.14
console.log(myMath.add(1, 2)); // 3
```

ESM 里导入路径通常要带扩展名（`./math.mjs` 而不是 `./math`）。它不会像 CommonJS 那样帮你猜测扩展名和补全路径——这正是"静态可分析"要付出的代价，也是它能做 Tree Shaking 的前提。

### 静态结构：import 会被提升到文件顶部

ESM 的 `import` 是静态的：在模块**求值之前**，引擎先扫描整个文件，把所有 `import` 收集起来建好依赖图，再按依赖顺序实例化。这带来两个直接结果：

- `import` 必须写在顶层作用域，不能写在 `if`、函数里根据条件动态决定，也不能用变量拼路径。
- 即便你把 `import` 写在文件最下面，它也会"提升"到模块体执行之前完成求值，所以不存在"在 import 之前用到导出"的时序问题。

```
文件被加载
   ↓
① 静态扫描所有 import，建立依赖图（编译期）
   ↓
② 按依赖顺序实例化绑定（live binding 就位）
   ↓
③ 才真正执行模块体里的普通语句
```

对比 CommonJS：它的 `require` 是普通函数调用，执行到那一行才去读文件、编译、运行，因此可以写进 `if`、可以动态拼路径。这正是两者"死板 vs 灵活"的分水岭。

## Node.js 怎么判断用哪套：type 字段与文件后缀

同一份 `.js` 文件，Node 到底按 CommonJS 还是 ESM 解析？决定权在两个地方，优先级如下：

1. **文件后缀强制指定**：`.cjs` 永远按 CommonJS，`.mjs` 永远按 ESM，后缀说了算，不受 `package.json` 影响。
2. **`package.json` 的 `type` 字段**：没有显式后缀时，看最近的 `package.json`。

`"type": "module"` 是一个"整包开关"——一旦声明，该目录及其子目录下所有 `.js` 文件都被当作 ESM；不写或写 `"type": "commonjs"`，则默认 CommonJS。

```json
{
  "type": "module"
}
```

这就是为什么很多项目要么全用 ESM 要么全用 CommonJS：一个 `.js` 到底是哪套，取决于它处于哪个 `package.json` 的作用域内。想在一个 ESM 包里保留个别 CommonJS 文件，就把它改名成 `.cjs`；反过来，在 CommonJS 包里写 ESM，就改成 `.mjs`。

```
my-app/
├── package.json        ("type": "module")
├── index.js            → 当作 ESM
├── legacy.cjs          → 强制 CommonJS（后缀优先）
└── lib/
    └── helper.js       → 当作 ESM（继承上层 type）
```

## require 与 import 的本质区别是什么？

这是面试里出现频率最高的问题，不能只答"一个是 CommonJS、一个是 ES Module"。真正要讲透的是背后的模块机制差异。

### 解析时机：运行时 vs 编译期

`require` 是运行时解析——代码执行到那一行，Node 才去定位、读文件、编译、执行模块，所以它可以写在条件分支里、可以动态拼接路径。

`import` 是编译期静态分析——进入文件后引擎先扫出全部依赖关系，在代码运行前就确定了完整的依赖图。代价是不能写进 `if`、不能动态拼路径，收益是依赖关系在加载前就一清二楚。

### 加载语义：值的拷贝 vs 值的引用

CommonJS 导出的是 `module.exports` 对象的**拷贝式引用**：导入方拿到的是当时那个对象的引用，模块内部后续对原始局部变量的重新赋值，导入方看不到。

ESM 是**活绑定（live binding）**：导出的变量和模块内部的变量是同一个绑定，模块内部改了值，所有导入方实时同步。

```js
// esm-counter.mjs
export let count = 0;
export function inc() { count += 1; }
```

```js
// esm-main.mjs
import { count, inc } from './esm-counter.mjs';
console.log(count); // 0
inc();
console.log(count); // 1，live binding 实时同步，CommonJS 做不到
```

### 同步 vs 异步加载

`require` 是同步的：调用时必须"立刻拿到返回值"，因此无法等待一个 Promise，CommonJS 里也没有顶层 `await`。

`import` 是异步加载的：底层返回的是模块命名空间对象，ESM 还支持顶层 `await`——文件顶层直接 `await`，整个模块及其导入方会等它完成，适合在启动时连数据库、读配置。

### 互操作：两套系统能不能混用？

```
ESM → 引入 CommonJS   通常可直接 default import，Node 帮你把 module.exports 包成默认导出
CJS → 引入 ESM        Node 22 起可以直接 require 同步求值的 ESM（旧版本抛 ERR_REQUIRE_ESM）
CJS → 引入 ESM(顶层 await)  不能 require（同步等不了异步求值，抛 ERR_REQUIRE_ASYNC_MODULE），必须改用动态 import()
```

ESM 里用 CommonJS 包，一般直接 `import pkg from 'some-cjs-pkg'` 即可，`pkg` 就是对方的 `module.exports`。反向则要看 Node 版本：**Node 22 起 `require()` 已能同步加载 ESM**（前提是该 ESM 的求值过程不含顶层 `await`，`require` 返回带 `__esModule` 标记的命名空间对象），旧版本会抛 `ERR_REQUIRE_ESM`；而**含顶层 `await` 的 ESM 在任何版本都不能 `require`**——同步的 `require` 等不了异步求值，会抛 `ERR_REQUIRE_ASYNC_MODULE`，只能用动态 `import()`：

```js
// CommonJS 里桥接 ESM
async function main() {
  const { something } = await import('some-esm-pkg'); // 动态 import 返回 Promise
  something();
}
main();
```

动态 `import()` 是两套系统的"桥"：它返回 Promise，无论在 CommonJS 还是 ESM 里都能调用，也是渐进迁移老项目的推荐手段。

### 为什么 ESM 能做 Tree Shaking 而 CommonJS 不能？

Tree Shaking 指打包时把没被用到的导出代码删掉。它依赖于"编译期就能确定哪些导出被引用、且导出是静态可分析的"。

ESM 的 `import` / `export` 是静态语法，依赖图在解析阶段就固定了，打包器可以精确知道 `add` 被用了而 `subtract` 没被用，于是把后者整段丢掉。

CommonJS 的 `require` 是运行时函数调用，路径可以是变量、可以写在条件里，导出对象还能被整体替换，打包器在静态阶段根本无法证明"某个属性一定没被用到"，只能保守地全部保留。这就是为什么新项目更倾向 ESM——不仅语法统一，还能让打包产物更小。

```
ESM：  静态依赖图 → 精确知道用到哪些导出 → 删掉 dead code（Tree Shaking）
CJS：  运行时才知依赖 → 无法静态证明某导出无用 → 全部保留
```

## 依赖从哪来：npm 包管理

模块解决了"自己代码怎么拆分"，依赖解决了"别人的代码怎么引入"。Node 生态的包管理器是 npm，核心就是把包名和版本写进 `package.json`，再把实体下载到 `node_modules`。

### 从零开始：npm init 与 npm install

```bash
npm init        # 交互式生成 package.json
npm init -y     # 跳过交互，用默认值快速生成
npm install express     # 安装生产依赖（简写 npm i express）
npm install -D typescript  # 安装开发依赖（-D = --save-dev）
npm uninstall express      # 卸载
npm update                 # 按 package.json 的版本范围更新
```

`package.json` 里几个关键字段：

```json
{
  "name": "my-project",
  "version": "1.0.0",
  "main": "index.js",
  "scripts": {
    "start": "node index.js",
    "dev": "nodemon index.js"
  },
  "dependencies": {
    "express": "^4.18.0"
  },
  "devDependencies": {
    "typescript": "^5.0.0"
  }
}
```

### dependencies 与 devDependencies 的区别

`dependencies` 是**运行时真正需要的包**：服务跑起来、代码执行时要用（框架、数据库驱动、工具库）。`devDependencies` 是**只在开发期需要的包**：构建、测试、类型检查、代码格式化（TypeScript、Jest、ESLint）。

这个区分很关键：部署到生产环境时，`npm install --production` 只会装 `dependencies`，跳过 `devDependencies`，能显著减小镜像体积、缩短安装时间。

### scripts：把常用命令固化下来

`scripts` 把"启动、构建、测试"这类长命令固化成短名字，用 `npm run <名>` 调用（`start` / `test` 可省略 `run`）。它本质是在 `node_modules/.bin` 里找可执行文件，所以本地装的 CLI 不用写全局路径：

```bash
npm run dev     # 等价于执行 scripts.dev
npm start       # 等价于 node index.js
```

## 版本号怎么读：语义化版本

依赖版本写成 `主版本.次版本.补丁`（如 `4.18.2`），含义是：主版本变 = 不兼容的 API 改动；次版本变 = 向后兼容的新功能；补丁变 = 向后兼容的 bug 修复。版本范围符号决定 `npm install` 能装到多新：

```
^4.18.0  → 允许 4.x.x（不改变主版本），可升到 4.19.0
~4.18.0  → 允许 4.18.x（不改变前两位），只能升到 4.18.9
4.18.0   → 精确锁定，只装这一个版本
4.18.0-beta.1 → 预发布版本，默认不会被 ^ / ~ 自动选中
```

`^` 敢跨次版本（新功能通常不破坏旧调用），但不敢跨主版本（可能是破坏性升级）；`~` 更保守，连次版本都不变。`-beta` / `-rc` 这类预发布标签默认被 `^` `~` 排除，除非你显式写进去——避免生产环境无意间引入不稳定的预览版。

## 为什么必须提交锁文件：package-lock.json 的作用

`package.json` 里写的 `^4.18.0` 是个**范围**，不是精确值。今天装到 `4.18.2`，下周同事装可能变成 `4.19.0`，哪怕代码没变，依赖树也可能不同——这就是"在我机器上能跑"的根源。

`package-lock.json` 记录的是**实际装上的每一层依赖的精确版本与内容哈希**，把整棵依赖树钉死。它的作用有三点：

- 保证团队每个人、CI 机器装到的依赖树**完全一致**，可复现构建。
- 加快后续安装：npm 能直接按锁文件比对，少做版本求解。
- 配合 `npm ci`：它严格按锁文件安装、不写锁文件、更快，是 CI 和生产部署的推荐命令。

```
package.json   → "express": "^4.18.0"   （范围，会漂移）
package-lock.json → "express": "4.18.2"  （精确，钉死）
```

结论：**提交 `package.json` 时一定也要提交锁文件**。只改 `package.json` 不更新锁文件，或把它加进 `.gitignore`，都会让"可复现"形同虚设。

## node_modules 的扁平化与查找算法

`npm install` 后依赖落到 `node_modules`。从 npm v3 起它做了**扁平化（hoisting）**：不再把每个包的依赖层层嵌套，而是尽量把二级、三级依赖提升到顶层 `node_modules`，只有当版本冲突无法共存时才降级放进各自的子目录。这样既能复用同一份包、减小体积，又避免路径过深。

```
node_modules/
├── express/          （你的直接依赖，也在顶层）
├── body-parser/      （express 的依赖，被提升到顶层复用）
└── lodash/           （某包依赖，无冲突 → 提升到顶层）
```

而 `require('lodash')` 找文件时，走的是**从当前文件所在目录逐级向上**的查找算法：

```
/app/src/controllers/user.js
  require('lodash')
    → 查 /app/src/controllers/node_modules/lodash
    → 没有 → 查 /app/src/node_modules/lodash
    → 没有 → 查 /app/node_modules/lodash   ✓ 命中
    → 仍没有 → 继续向上，直到文件系统根 /node_modules
    → 全没有 → 抛 MODULE_NOT_FOUND
```

这个"就近优先、逐级向上"的规则，解释了为什么顶层 `node_modules` 里的包，能被任意子目录的代码 `require` 到，也解释了为什么装错层级会找不到包。`node_modules` 通常很大，应写进 `.gitignore` 不提交，靠 `package.json` + 锁文件重建。

代码文件之间已经能互相引用、依赖也能从 npm 装进来，但"这些文件怎么在同一进程里同时跑起来、I/O 怎么不互相阻塞"，靠的是另一套机制。下一篇就讲 Node.js 的发动机：事件循环。

## 小结

- **模块系统要解决三件事**：怎么导出、怎么导入、拿到的到底是值还是引用；项目按 controllers/services/models/utils/config 拆分
- **模块缓存与循环依赖**：`require.cache` 命中后不再读文件、不再执行顶层代码，两次 require 是同一个对象；模块执行到一半就把 `module.exports` 交出去缓存，所以循环依赖可能拿到半成品
- **exports 与 module.exports 的陷阱**：`exports` 只是 `module.exports` 的初始引用，整体重新赋值 `module.exports` 后，挂在 `exports` 上的属性外界都拿不到
- **import 是静态的**：求值前先扫描全部 import 建依赖图，必须写顶层、不能条件化、不能拼路径；代价是路径要带扩展名，收益是能做 Tree Shaking
- **解析器判定两条规则**：`.cjs` 永远是 CommonJS、`.mjs` 永远是 ESM（后缀优先）；其余 `.js` 看最近的 `package.json` 的 `type` 字段
- **require 与 import 的本质差异**：require 是运行时同步加载、拿到值的拷贝；import 是编译期静态分析、活绑定（live binding）、支持顶层 await
- **两套系统的互操作**：ESM 里 `import pkg from 'cjs-pkg'` 直接用；CJS 引 ESM 在 Node 22 起可直接 `require()`（限同步求值的 ESM，旧版本抛 `ERR_REQUIRE_ESM`），含顶层 `await` 的仍只能走动态 `import()`，它返回 Promise，是渐进迁移的桥
- **npm 依赖分类与 scripts**：dependencies 是运行时必需、devDependencies 只在开发期，`npm install --production` 只装前者；脚本去 `node_modules/.bin` 找可执行文件
- **语义化版本与锁文件**：`^4.18.0` 允许 4.x.x 会漂移，`~4.18.0` 只允许 4.18.x；`package-lock.json` 钉死实际版本与哈希，CI 用 `npm ci`
- **node_modules 扁平化与查找算法**：npm v3 起把二三级依赖提升到顶层；require 从当前目录逐级向上找 node_modules，全没有抛 MODULE_NOT_FOUND
