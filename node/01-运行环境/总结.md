# 模块总结 · 运行环境

## 知识主线

七篇不是并列的知识点，而是一条有依赖关系的链，每一篇都在回答上一篇留下的问题：

```
01 Node.js 是什么（跑的是什么、为什么适合）
        │  先算清"耗时绝大部分是等待"，才知道后面所有机制在优化什么
        ▼
02 模块系统与包管理（代码怎么组织）
        │  文件不能互相引用、依赖装不进来，后面任何机制都跑不起来
        ▼
03 事件循环：六个阶段与微任务  ★主轴
        │  先知道"机器怎么转"（六个阶段、内核就绪通知），
        │  再知道"顺序怎么定"（两条微任务队列、检查点）——两半合起来才是一台完整的机器；
        │  机器转明白了，下一个问题是：代码怎么写才既并发又不卡？
        ▼
04 异步编程与事件驱动
        │  异步搬运的到底是什么？——不是变量，而是字节流
        ▼
05 Buffer 与 Stream
        │  I/O 模型讲到头，单线程算力到顶、还要故障隔离，怎么办？
        ▼
06 进程、线程与优雅退出
        │  单点机制都通了，最后要放回同一张架构图与决策模型里收口
        ▼
07 运行机制收束（收口、误区清单与自测）
```

本模块的主轴是**事件循环**：01 说明它为什么值得存在，02 决定代码怎么进 V8，03 把它的六个阶段与微任务机制一次讲完，04 讲在它之上怎么写代码，05 讲它搬运的字节长什么样，06 讲它不够用时怎么往外扩，07 把它放回架构图收口。

## 分篇知识点

### 01-Node.js 是什么

- **一笔请求的耗时账**：一次聚合请求两三秒，MySQL 30ms、下游 100ms、第三方 2000ms、Redis 5ms，绝大部分是等待
- **I/O 密集型服务的定义**：真正执行 JS 往往只有几毫秒，其余全花在等磁盘、网络、外部服务
- **高并发靠"不让主线程等"**：等待无法消除，只是从主线程挪给内核与线程池，主线程在等的时候去处理别的请求
- **阻塞 vs 非阻塞模型**：阻塞模型下 B、C 被 A 的 2000ms 堵死；非阻塞模型发起后立刻转去处理下一个请求
- **Node.js 的定位**：是 JavaScript 运行环境，既不是语言也不是后端框架；V8 只负责执行 JS，服务端能力是 Node 在 V8 之外补的
- **四层结构**：你的代码 → V8（解析/JIT/GC）→ Node.js Bindings → libuv（Event Loop + Thread Pool）→ 操作系统（epoll/kqueue/IOCP）
- **适合与不适合**：适合 Web/API、BFF 聚合、CLI、实时推送；不适合大数运算、图像视频编解码、复杂加密压缩、超大 JSON.parse
- **版本基准**：用 LTS，`node -v` 验证；本系列结论以 Node 20+ 为准，Node 20（libuv 1.45）调整过 timers 阶段时机
- **三条代价**：CPU 密集任务会拖垮服务、同步 API 破坏"不闲着"、异步心智成本（写出看着像并发其实是串行的代码）

### 02-模块系统与包管理

- **模块系统要解决三件事**：怎么导出、怎么导入、拿到的到底是值还是引用；项目按 controllers/services/models/utils/config 拆分
- **模块缓存与循环依赖**：`require.cache` 命中后不再读文件、不再执行顶层代码，两次 require 是同一个对象；模块执行到一半就把 `module.exports` 交出去缓存，所以循环依赖可能拿到半成品
- **exports 与 module.exports 的陷阱**：`exports` 只是 `module.exports` 的初始引用，整体重新赋值 `module.exports` 后，挂在 `exports` 上的属性外界都拿不到
- **import 是静态的**：求值前先扫描全部 import 建依赖图，必须写顶层、不能条件化、不能拼路径；代价是路径要带扩展名，收益是能做 Tree Shaking
- **解析器判定两条规则**：`.cjs` 永远是 CommonJS、`.mjs` 永远是 ESM（后缀优先）；其余 `.js` 看最近的 `package.json` 的 `type` 字段
- **require 与 import 的本质差异**：require 是运行时同步加载、拿到值的拷贝；import 是编译期静态分析、活绑定（live binding）、支持顶层 await
- **两套系统的互操作**：ESM 里 `import pkg from 'cjs-pkg'` 直接用；CJS 引 ESM 在 Node 22 起可直接 `require()`（限同步求值的 ESM，旧版本抛 `ERR_REQUIRE_ESM`），含顶层 `await` 的仍只能走动态 `import()`，它返回 Promise，是渐进迁移的桥
- **npm 依赖分类与 scripts**：dependencies 是运行时必需、devDependencies 只在开发期，`npm install --production` 只装前者；脚本去 `node_modules/.bin` 找可执行文件
- **语义化版本与锁文件**：`^4.18.0` 允许 4.x.x 会漂移，`~4.18.0` 只允许 4.18.x；`package-lock.json` 钉死实际版本与哈希，CI 用 `npm ci`
- **node_modules 扁平化与查找算法**：npm v3 起把二三级依赖提升到顶层；require 从当前目录逐级向上找 node_modules，全没有抛 MODULE_NOT_FOUND

### 03-事件循环：六个阶段与微任务

- **单线程的准确表述**：只有执行 JS 的那条主线程是单线程，进程内还有 libuv 线程池与操作系统的网络 I/O
- **事件循环解决的问题**：发起 I/O 后不等待、转去处理下一个请求，结果回来再执行它的回调；所以一个慢查询不会卡住后面的请求
- **六个阶段**：timers → pending callbacks → idle/prepare → poll → check → close callbacks，每阶段把回调队列执行完再进下一阶段
- **timers 阶段**：只处理已到期的 setTimeout/setInterval；`setTimeout(fn, 1000)` 是最小等待时间，主线程被 while 阻塞 3 秒就 3 秒后才打印
- **pending callbacks 与 idle/prepare**：前者处理少数推迟到下一轮的系统级 I/O 回调，后者是 libuv 与 Node 内部用的阶段，日常开发基本碰不到
- **poll 是 I/O 核心**：向内核询问哪些 socket/文件就绪并执行就绪回调；没有定时器和 setImmediate 时可阻塞在此等新事件
- **check 阶段与 setImmediate**：setImmediate 的回调在 poll 阶段完成后的 check 阶段执行，属于本轮之内，而 setTimeout 要等下一轮 timers
- **setImmediate 与 setTimeout(fn, 0) 的顺序**：主模块里不确定；写在 I/O 回调里稳定为 setImmediate 先（当前在 poll，紧接着就是 check）
- **close callbacks 的入口很窄**：只有真正经历 `uv_close` 的 handle 才落在这个阶段；无连接 server 的 `close` 由 `process.nextTick` 派发，不进这一阶段
- **网络 I/O 不走线程池**：TCP/HTTP/Socket 注册给 epoll/kqueue/IOCP，由内核通知就绪，一个主线程能管成千上万连接
- **只有 fs/dns/crypto/zlib 进 libuv 线程池**：这些平台没有统一异步接口，或本身就是偏阻塞、CPU 型工作
- **libuv 线程池默认 4 线程**：`UV_THREADPOOL_SIZE` 可调、最大 1024；10 个 pbkdf2 会呈 4/4/2 分批完成
- **UV_THREADPOOL_SIZE 的三个坑**：必须在进程启动前设置（运行时改无效）、不是越大越好、fs/dns/crypto/zlib 共用同一组线程
- **Node 20 / libuv 1.45 改了 timer 时机**：timer 主要挪到 poll 之后处理，看事件循环文章要先确认写于哪一年、对应哪个 Node 版本
- **两条微任务队列**：`process.nextTick` 队列与 Promise 微任务队列；宏任务走六个阶段，微任务走更靠前的检查机制
- **同步代码永远先跑完**：异步 API 在这一步只是"注册"；`start → end → nextTick → promise → timeout`
- **nextTick 不属于任何 phase**：官方六阶段图里没有它，触发时机是 Call Stack 清空后立刻把队列清空到空，再继续 Event Loop
- **同一检查点内 nextTick 先于 Promise**：两条独立队列，顺序固定为先清空 nextTickQueue、再清空 Promise 队列
- **微任务检查点在每个 JS 回调返回调度层时**：不是一整轮才清一次，所以同轮两个 setTimeout 的输出是 `timer1 → promise → timer2`
- **递归 nextTick 会饿死事件循环**：队列要"清空到空"，边清边注册就永远清不完，poll/timers/check 进不去（I/O starvation）；要让出执行权用 setImmediate
- **输出顺序推演四步法**：①划出同步代码 ②标出每个回调返回处的检查点 ③同检查点 nextTick 优先 ④最后才轮到下一阶段宏任务
- **为什么适合 I/O 密集型**：万级连接只用一个 JS 线程，Event Loop 在 poll 阻塞等内核通知，避免"一请求一线程"的上下文切换与内存爆炸
- **CPU 密集为什么卡死全服务**：它占住唯一的 JS 线程，Event Loop 转不动，所有 I/O 回调一起排队

### 04-异步编程与事件驱动

- **三次写法变革**：Callback → Promise → async/await 是层层包裹不是替代，每一层都在解上一层的痛点
- **error-first 与回调地狱**：回调第一个参数永远是 error；多步依赖时代码右移成金字塔，且每层都要手写 `if (err)`，漏一层错误就被吞掉
- **Promise 三态且不可逆**：pending → fulfilled / rejected，落定即锁死；`.then` 回传 Promise 自动展开，`.catch` 捕获整条链，`.finally` 做清理
- **await 不阻塞事件循环**：它只把当前 async 函数的后半段挂成微任务，主线程立刻去处理别的回调与请求
- **await 用不对会把并发写成串行**：三个 100/100/500ms 任务串行 700ms，`Promise.all` 并行 500ms；无数据依赖就该并发
- **Promise.all 是快速失败**：任一 reject 整体立刻 reject，其余已发起任务的结果被整体丢弃（任务本身不会被取消）
- **allSettled / race / any 的分工**：allSettled 永不整体失败、拿 `{status, value|reason}`；race 第一个落定者决定；any 第一个成功者决定、全失败才 reject
- **EventEmitter 是内置对象的基类**：`net.Server`、`http.Server`、`fs.ReadStream`、`process` 都是它的实例，四步是注册→等待→触发→执行
- **EventEmitter 的两个坑**：`emit('error')` 无监听器会抛 uncaughtException 让进程退出；on 了不 off 会触发 MaxListenersExceededWarning（默认上限 10）且内存只增不减
- **事件驱动解耦执行与观测**：业务主流程只负责 emit，日志/监控/通知各自 on，新增埋点主流程一行都不用改

### 06-Buffer 与 Stream

- **Buffer 是固定长度的字节序列**：容量创建时定死，是 `Uint8Array` 的子类；字节本身没有编码，同一段字节用 utf8 / hex / base64 解读得到不同结果
- **Buffer.alloc 与 Buffer.from 的区别**：alloc(n) 分配并清零、适合待填充缓冲，from(x) 从已有数据编码；不要用未清零的 `Buffer(size)` 旧构造，会残留堆上旧数据
- **字符长度 ≠ 字节长度**：`'你好'.length` 是 2，`Buffer.from('你好').length` 是 6（UTF-8 每汉字 3 字节），算 Content-Length 必须用字节数
- **Buffer 的五个应用场景**：fs.readFile 不指定编码、TCP socket 的 data chunk、图片音视频、AES/RSA 加解密、Base64 编解码
- **Stream 是一块一块地搬**：10GB 文件用 readFile 会撑爆内存，Stream 一次搬一块（通常 64KB），内存恒定在几十 KB 到几 MB；Buffer 是水桶、Stream 是水管
- **四种 Stream**：Readable（只读）、Writable（只写）、Duplex（双向，典型是 TCP Socket）、Transform（Duplex + 转换，如 gzip、加解密）
- **背压**：`writable.write()` 返回 false 表示内部缓冲到顶、上游应暂停，缓冲降下来触发 `'drain'` 再恢复；`highWaterMark`（默认 64KB）决定触发点
- **pipe 与 pipeline 的取舍**：pipe 自动协调背压但下游出错不会销毁上游；pipeline 任一环出错统一销毁所有流，链路长或要错误兜底时用它
- **流式推送必须用 Stream**：日志/进度/大文件做成 Readable 边产生边推，客户端立刻开始消费，`res` 本身就是 Writable
- **fs 的三种风格与 path**：回调版、`fs/promises`、`*Sync`；同步版本阻塞事件循环，只适合启动初始化与 CLI。拼路径永远用 `path.join`，要基于 cwd 的绝对路径才用 `path.resolve`

### 07-进程线程与优雅退出

- **`node app.js` 起的是一个进程**：独立内存空间 + 一个 V8 实例 + 一个堆 + 一个事件循环；用 `process.pid/argv/uptime/memoryUsage` 观测，rss 含 Buffer 与线程栈所以常远大于 heapUsed
- **child_process 四把刀**：`spawn` 不走 shell 且流式输出、`exec` 走 shell 且全缓冲（maxBuffer 默认 1MB）、`execFile` 无 shell 更安全、`fork` 额外建 IPC 通道
- **多核与 cluster**：JS 默认只用一个主线程，8 核也只忙 1 核；cluster 让 Primary fork 出共享同一端口的多个 Worker（数量取 `os.availableParallelism()`），崩一个补一个，价值在进程级故障隔离
- **进程内存默认不共享**：只能借 IPC / Socket / Redis / 消息队列 / HTTP 这类进程外通道通信；线程共享部分内存但带来竞态条件
- **Worker Thread 不等于 libuv 线程池**：前者是你主动 `new`、有独立 V8 跑你的 JS 的线程；后者由 Node 内部维护、跑 fs/dns/crypto/zlib，你感知不到
- **worker_threads 只适合 CPU 密集**：把大计算挪出主线程，配 `terminate()` 释放、`on('error')` 兜异常、`isMainThread` 判上下文；普通 I/O 交给事件循环更快
- **不要每请求 new Worker**：1 万并发就是 1 万个 Worker，创建与调度本身成了新瓶颈；正确做法是 Worker Pool（≈ 核数）+ Task Queue，对外用 Promise 包装
- **共享内存的代价是并发安全**：`SharedArrayBuffer` 能让主线程与 Worker 共享同一块内存，但 `shared[0]++` 非原子会丢更新，必须用 `Atomics.add`
- **四种并发方式怎么选**：I/O 用异步、CPU 用 Worker（走池）、要隔离或跑外部程序用 child_process、要铺多核 + 故障隔离用多进程
- **优雅关闭与错误分层兜底**：SIGTERM 先停收新连接 → 等在途请求结束（带超时兜底）→ 关 DB/Redis/MQ → 退出；别滥用 `process.exit()`，错误按同步/回调/Promise/进程级分层接住

### 07-运行机制收束

- **完整架构的三条主线**：网络 I/O 走内核 epoll/kqueue/IOCP 不进线程池；fs/crypto/dns/zlib 走 libuv 线程池；你写的 JS 只在主线程的 V8 里跑
- **主动创建的两类并发结构**：同进程内的 Worker Thread（可共享 SharedArrayBuffer）与独立 Child Process（内存不共享，靠 IPC/Socket）
- **七篇在架构图上的位置**：模块系统决定代码怎么进 V8，事件循环与微任务决定主线程怎么转，Buffer/Stream 决定数据怎么流，进程线程是主动扩出的并发
- **抽象栈定位**：模块一讲的全是"进程内"的事，业务代码与框架在上、Event Loop + libuv + 内核在下，排障时从现象所在层往相邻层递推
- **决策模型的第一反应**：见"卡 / 慢 / 顺序乱 / 内存涨"先问"事件循环是不是被占住了、数据流有没有背压"，再决定换异步、上 Stream，还是丢给线程/进程
- **六条误区清单**：单线程、所有异步都在线程池、await 阻塞事件循环、worker_threads 就是线程池、nextTick 越多越快、多开进程就能变快
- **自测 6 问**：覆盖 01~08，能答上（一次请求 CPU 真算多久、require 与 import、六个阶段、nextTick 与 Promise、await 写成串行、进程不退出漏了什么）说明模块一过关
- **交接模块二**：进程内 I/O 模型收口，接下来要回答"这些 I/O 从哪来"——HTTP/TCP/WebSocket 的本质是跨机器交换字节

| 不要每请求 new Worker | 应使用 Worker Pool（≈ 核数）+ Task Queue | 06 篇 |
| 优雅关闭 | SIGTERM 后停收新连接 → 等在途请求（带超时兜底）→ 关依赖 → 退出 | 06 篇 |
| 决策模型第一反应 | 先问"事件循环是不是被占住了、数据流有没有背压" | 07 篇 |

## 见 X 想 Y

现象是表相，先定位到层，再动手。

| 见到什么 | 该想到什么 | 一句话理由 |
| --- | --- | --- |
| 接口慢、一次请求两三秒 | I/O 密集型，等的是别人 | CPU 真正执行只有几毫秒，别急着加机器 |
| 响应顺序不符合预期 | 微任务检查点（nextTick vs Promise） | 每个回调返回调度层都清一次，同检查点内 nextTick 先于 Promise |
| CPU 打满但 QPS 很低 | 主线程被同步长任务占住 | 事件循环转不动，I/O 回调全在排队 |
| 代码里出现 readFileSync / execSync | 同步 API 阻塞事件循环 | 同步版本只适合启动初始化与 CLI，别放请求热路径 |
| 大文件读写、上传下载、日志推送 | Stream + 背压 | 一次读进内存会撑爆堆，createReadStream + pipe 内存恒定 |
| 内存一路涨最后 OOM | 背压没做 / 事件监听器泄漏 | write() 返回 false 没暂停，或 on 了不 off |
| 压缩、加密、大 JSON 解析 | Worker Thread（走线程池） | CPU 密集会占住唯一的 JS 线程，丢到 Worker 才不卡 |
| 调 ffmpeg / python 脚本 / 系统命令 | child_process（spawn / execFile） | 这是别的程序，得起独立进程去跑 |
| 用不满多核、要故障隔离 | 多进程（cluster / 进程管理） | 一个 Node 进程只用一个核，崩一个不影响其他 |
| 服务重启丢请求 | SIGTERM 优雅关闭 | 先停收新请求、等存量请求跑完再退出，别硬切连接 |
| 进程不退出 | 未清理的句柄 + 优雅关闭 | server / timer / 长连接没 close，句柄清空进程才自然退出 |
| 同样并发换多核机器没变快 | 先确认瓶颈是"算"还是"等" | I/O 密集等的是别人，加核帮不上忙 |
| "在我机器上能跑" | 锁文件没提交或版本范围漂移 | package.json 写的是 `^` 范围，靠 package-lock.json 钉死 |

## 易错点汇总

- **"Node.js 是单线程的"／"所有异步操作都在线程池里跑"**：只有执行 JS 的主线程是单线程。网络 I/O 走内核 epoll/kqueue/IOCP 通知，不进线程池；只有 fs、部分 DNS、crypto、zlib 才进 libuv 线程池，而且它们共用同一组默认 4 个线程。
- **"setTimeout(fn, 1000) 就是 1000ms 后执行"**：它是"至少 1000ms 后才有资格执行"，还要等主线程空闲。主线程被 while 阻塞 3 秒，这个回调就 3 秒后才跑。它是最小等待时间，不是精确执行时间。
- **"微任务是一整轮 Event Loop 之后才清一次"**：每个 JS 回调返回调度层都是一次微任务检查点。所以同一轮 timers 里的两个 setTimeout 输出是 `timer1 → promise → timer2`，而不是 `timer1 → timer2 → promise`。
- **"process.nextTick 用得越多越快"**：nextTick 队列要一直清空到空，在回调里递归注册会让它永远清不完，事件循环进不了 poll/timers/check，造成 I/O 饥饿。需要让出执行权又不想饿死循环时，用 setImmediate。
- **"await 会阻塞事件循环"**：await 只暂停当前 async 函数的后半段并挂成微任务，主线程立刻去处理别的回调。真正的坑是"两个互不依赖的 await 写成串行"，本该 500ms 的活儿变成 700ms。
- **"重新赋值 module.exports 后，再挂 exports.xxx 也生效"**：`exports` 只是 `module.exports` 的初始引用，一旦整体替换 `module.exports`，挂在旧 `exports` 上的属性外界全拿不到。整体替换用 `module.exports`，增量挂属性用 `exports.xxx`。
- **"UV_THREADPOOL_SIZE 可以运行时改、每个模块各有一个池"**：libuv 在进程启动时一次性读取并创建线程，运行时改 `process.env.UV_THREADPOOL_SIZE` 无效。而且 fs、DNS、crypto、zlib 抢的是同一组线程，给 crypto 开满会挤占 fs。
- **"字符串长度等于字节长度"**：`'你好'.length` 是 2，`Buffer.from('你好').length` 是 6。算 Content-Length 或切分二进制协议帧时用字符数会让长度算小，下游按错误长度截断，数据全乱。
- **"有 pipe 就够了，不需要 pipeline"**：pipe 只协调背压，下游出错时不会销毁上游，容易留下没释放的文件描述符与 Socket。链路长、要错误兜底、要串多个 Transform 时用 pipeline，它出错统一销毁整条链路。
- **"worker_threads 就是 libuv 线程池"／"每请求 new 一个 Worker"**：前者是你主动 `new`、有独立 V8 跑你的 JS，后者是 Node 内部跑 fs/dns/crypto/zlib 的系统线程。生产环境每请求 new 一个 Worker，1 万并发就是 1 万个线程，应该用 Worker Pool + Task Queue。
- **"emit('error') 没监听器顶多报个错"**：EventEmitter 对 error 事件有特殊处理，没有监听器会直接抛 uncaughtException 让进程退出。同理 on 了不 off 会触发 MaxListenersExceededWarning（默认上限 10），且闭包引用的对象无法回收、内存缓慢上涨。
- **"多开进程就能变快"／"process.exit(1) 很干脆"**：多开进程只对 CPU 密集或要故障隔离的场景成立，I/O 密集的瓶颈是等待，多开只是多占内存。`process.exit()` 会立即终止，stdout 没写完、日志没发出、事务没提交、响应没结束都可能发生。

## 与相邻模块的接口

**进入本模块前必须已经掌握**：这是整套体系的起点，没有前置依赖。只要会写 JavaScript（变量、函数、对象、class、Promise）、能在终端敲命令就够了。Node 的 fs / http / crypto 这些服务端能力从哪来，本模块会从头讲起。

**本模块交给下一模块什么**：本模块产出的是"进程内"的完整 I/O 模型——事件循环为什么能扛并发、异步怎么写、字节流怎么搬、单线程不够时怎么用进程与线程分流。下一模块要靠它回答一个一直悬着的问题：**这些 I/O 到底是从哪来的**。HTTP 请求、TCP 连接、WebSocket 推送本质都是"通过网卡与另一台机器交换字节"，而 Socket 就是一条 Duplex Stream、HTTP body 就是 Stream 在搬运 Buffer。
