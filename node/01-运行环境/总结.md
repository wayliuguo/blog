## 知识主线

七篇不是并列的知识点，而是一条有依赖关系的链，每一篇都在回答上一篇留下的问题：

```
01 Node.js 是什么（跑的是什么、为什么适合）
        │  先算清"耗时绝大部分是等待"，才知道后面所有机制在优化什么
        ▼
02 模块系统与包管理（代码怎么组织）
        │  文件不能互相引用、依赖装不进来，后面任何机制都跑不起来

03 事件循环：六个阶段与微任务  ★主轴
        │  先知道"机器怎么转"（六个阶段、内核就绪通知），
        │  再知道"顺序怎么定"（两条微任务队列、检查点）——两半合起来才是一台完整的机器；
        │  机器转明白了，下一个问题是：代码怎么写才既并发又不卡？
        ▼
04 异步编程与事件驱动
        │  异步搬运的到底是什么？——不是变量，而是字节流
        ▼
05 Buffer 与 Stream
        │  I/O 模型讲到头，单线程算力到顶、还要故障隔离，怎么办？
        ▼
06 进程、线程与优雅退出
        │  单点机制都通了，最后要放回同一张架构图与决策模型里收口
        ▼
07 运行机制收束（收口、误区清单与自测）
```

本模块的主轴是**事件循环**：01 说明它为什么值得存在，02 决定代码怎么进 V8，03 把它的六个阶段与微任务机制一次讲完，04 讲在它之上怎么写代码，05 讲它搬运的字节长什么样，06 讲它不够用时怎么往外扩，07 把它放回架构图收口。

## 分篇知识点

### 01-Node.js 是什么

- **一笔请求的耗时账：时间是"等"出来的**
  - **典型链路**：MySQL 30ms → 下游聚合服务 100ms → 第三方 API 2000ms → Redis 5ms → 保存访问记录 30ms，串行相加就是两三秒
  - **CPU 实际只算了几毫秒**：绝大部分耗时花在等数据库、等网络往返、等文件读写、等下游聚合
  - **I/O 密集型（I/O Bound）服务的定义**：一次请求中真正消耗 CPU 的时间极短，绝大部分耗时来自磁盘、网络、外部服务的输入/输出等待
- **阻塞模型与非阻塞模型**
  - **阻塞模型**：主线程"等完才走"，A 等下游服务的 2000ms 里 CPU 几乎空转，B、C 明明只要几十毫秒却被堵在后面
  - **非阻塞模型**：发起 I/O 后不等待、立刻转去处理下一个请求，I/O 完成时由内核发出就绪通知，事件循环回过头执行对应回调
  - **锚点结论**：Node.js 擅长的不是"计算得快"，而是"等待的时候不闲着"；高并发不是消除了等待，而是不让主线程等待——等待被挪给内核和线程池
- **Node.js 的定位与四层结构**
  - **定位**：是 JavaScript 的**运行环境**，不是一门新语言、也不是后端框架；V8 只负责把 JS 跑起来，服务端能力是 Node 在 V8 之外补的一整层
  - **V8 之外的补充**：`fs`、`http` / `net`、`crypto`、`stream`、`child_process`、`worker_threads`
  - **四层结构**：你的代码 → V8（解析 / JIT / 执行 / 内存管理与 GC）→ Node.js Bindings（把 `fs.readFile()` 翻译成底层能力调用）→ libuv（Event Loop + Thread Pool + 异步 I/O）→ 操作系统（Linux `epoll`、macOS / BSD `kqueue`、Windows `IOCP`）
- **适用与不适用的边界**
  - **适合**：Web / API 服务、接口聚合 / BFF、命令行工具、实时推送——共同点是等待占比极高
  - **不适合**：CPU 密集型的大数运算、图像 / 视频编解码、复杂加密压缩、超大对象 `JSON.parse`，它们会让主线程长时间被占住、事件循环转不动
- **三个常见误区**
  1. **"Node.js 是单线程的"**：单线程只指执行 JS 的那条主线程；libuv 另有线程池（默认 4 个线程）处理文件 I/O、DNS 解析、`crypto` 加密计算，定时器与网络 I/O 由事件循环和内核协作——准确表述是"单线程执行 JS + 多线程处理底层 I/O"
  2. **"Node.js 什么都适合"**：强项是"等 I/O 时不闲着"，弱项是"算得重"；CPU 密集任务应交给 Worker Thread 或子进程
  3. **"Node.js 就是后端框架"**：它是运行环境，只提供 JS 运行时、事件循环与系统级 API；路由、中间件、依赖注入这些后端架构由 Express、Koa、NestJS 定义
- **代价清单**
  1. **CPU 密集任务会拖垮服务**：只有一个 JS 主线程，一段重计算占住它，所有请求都得等
  2. **同步 API 会破坏"不闲着"**：`readFileSync`、超大对象 `JSON.parse` 这类操作把异步模型打回阻塞原形
  3. **异步心智成本**：写惯同步代码的人容易写出"看着像并发、其实是串行"的 `await`
- **版本基准**
  - **安装与验证**：装 **LTS（长期支持）** 版本，用 `node -v` 确认版本，用 `node -e` 直接执行一段内联 JS 验证环境正常
  - **结论基线**：以 **Node 20 及以上**为准——Node 20（libuv 1.45）对事件循环的 timers 阶段时机做过调整，更早教程里的结论可能已经不准


### 02-模块系统与包管理

- **模块系统要解决三件事**：怎么导出、怎么导入、拿到的到底是值还是引用
- **模块系统的本质区别（CJS 与 ESM）**
  1. **解析时机**：`import` 在求值前先扫描全部 import 建出依赖图（静态）；`require` 是运行时同步加载
  2. **值的语义**：`require` 拿到的是值的拷贝（快照），导出方之后再改也看不见；`import` 是活绑定（live binding），导出方改变量、导入方立刻可见
  3. **加载方式**：`require` 同步阻塞；`import()` 立刻返回 Promise，只把求值挂到后续调度
  4. **写法约束**：`import` 必须写顶层、不能条件化、不能拼路径，路径要带扩展名；代价换来 Tree Shaking
  5. **互操作**：ESM 引 CJS 直接 `import pkg from 'cjs-pkg'`；CJS 引 ESM 在 Node 22 起可直接 `require()`（限同步求值的 ESM，旧版本抛 `ERR_REQUIRE_ESM`），含顶层 `await` 的仍只能走动态 `import()`
- **模块类型怎么判定**
  - **两条规则**：`.cjs` 永远是 CommonJS、`.mjs` 永远是 ESM（后缀优先）；其余 `.js` 看最近的 `package.json` 的 `type` 字段
- **模块缓存与循环依赖**
  - **缓存**：`require.cache` 命中后不再读文件、不再执行顶层代码，两次 require 是同一个对象
  - **循环依赖**：模块执行到一半就把 `module.exports` 交出去缓存，所以可能拿到半成品
- **`exports` 与 `module.exports` 的陷阱**
  - `exports` 只是 `module.exports` 的初始引用，整体重新赋值 `module.exports` 后，挂在 `exports` 上的属性外界都拿不到
- **工程组织**
  - **目录拆分**：按 controllers / services / models / utils / config 分层
  - **npm 依赖分类与 scripts**：dependencies 是运行时必需、devDependencies 只在开发期，`npm install --production` 只装前者；脚本去 `node_modules/.bin` 找可执行文件
  - **语义化版本与锁文件**：`^4.18.0` 允许 4.x.x 会漂移，`~4.18.0` 只允许 4.18.x；`package-lock.json` 钉死实际版本与哈希，CI 用 `npm ci`
  - **`node_modules` 扁平化与查找算法**：npm v3 起把二三级依赖提升到顶层；require 从当前目录逐级向上找 node_modules，全没有抛 `MODULE_NOT_FOUND`


### 03-事件循环：六个阶段与微任务

- **单线程的准确表述与事件循环带来的收益**
  - **"单线程"的准确含义**：只有执行 JS 的那条主线程是单线程，进程内还有 libuv 线程池与操作系统的网络 I/O
  - **事件循环解决的问题**：发起 I/O 后不等待、转去处理下一个请求，结果回来再执行它的回调；所以一个慢查询不会卡住后面的请求
  - **为什么适合 I/O 密集型**：万级连接只用一个 JS 线程，Event Loop 在 `poll` 阻塞等内核通知，避免"一请求一线程"的上下文切换与内存爆炸
  - **CPU 密集为什么卡死全服务**：它占住唯一的 JS 线程，Event Loop 转不动，所有 I/O 回调一起排队
- **六个阶段的固定轮转顺序**
  1. **timers**：`setTimeout` / `setInterval` 中已到期的回调
  2. **pending callbacks**：少数被推迟到下一轮执行的系统级 I/O 回调（如部分 TCP 连接错误）
  3. **idle / prepare**：libuv 与 Node 内部使用，日常开发基本碰不到
  4. **poll**：I/O 事件处理核心
  5. **check**：`setImmediate` 的回调
  6. **close callbacks**：资源关闭回调
  - **轮转规则**：每进入一个阶段就把该阶段的回调队列一次性执行完（或执行到系统上限），再离开进入下一阶段
- **timers 阶段：`setTimeout` 是"最小等待时间"，且时机随版本变**
  - **资格而非保证**：`setTimeout(fn, 1000)` 只表示至少 1000ms 后这个 callback 才"有资格"执行，能否真执行还要等主线程空闲；主线程被 `while` 阻塞 3 秒，它就 3 秒后才打印
  - **Node 20 / libuv 1.45 改了 timer 时机**：timer 的调度重点从"本轮结束前再处理一次"改成主要放到 `poll` 之后处理（仅在首次进入事件循环前仍处理一次 Timer 以向后兼容），旧的"定时器先跑"推论不再成立
  - **看文章的纪律**：先确认文章写于哪一年、对应哪个 Node 版本，用阶段顺序去推演，而不是死记某条旧结论
- **poll 与 check：I/O 回调内的时序才稳定**
  - **`poll` 是 I/O 核心**：一是向内核询问哪些 socket / 文件就绪，二是执行已准备好的 I/O callback；没有定时器待触发也没有 `setImmediate` 时，会停在这里阻塞等待新 I/O 事件
  - **`check` 阶段与 `setImmediate`**：官方定义为"在 `poll` 阶段完成之后、进入 `check` 阶段调用"，属于本轮之内
  - **顺序不确定 vs 稳定**：直接写在主模块里 `setTimeout(fn, 0)` 与 `setImmediate` 谁先谁后不确定（`setTimeout` 至少 1ms 才到期，两者都排到下一轮）；写在 I/O 回调里则稳定为 `setImmediate` 先——当前在 `poll`，紧接着就是 `check`，而 `setTimeout(0)` 要等下一轮 `timers`
- **close callbacks 的入口很窄**
  - **判定依据是 handle 而非事件名**：只有真正经历 `uv_close` 的 handle，回调才落在 `close callbacks` 阶段——`client.destroy()` 销毁的是真实 socket 连接，所以排在整段输出的最后
  - **反例**：`net.Server.close()` 在没有任何活跃连接时只是关掉服务端 handle，Node 内部改用 `process.nextTick` 派发 `'close'`，于是它夹在 nextTick 队列被清空的位置，根本没进这个阶段
- **网络 I/O 与 libuv 线程池：谁进池、谁不进池**
  - **网络 I/O 不走线程池**：TCP / HTTP / Socket 注册给 `epoll` / `kqueue` / `IOCP`，由内核在数据到达时通知就绪，一个主线程就能管成千上万连接
  - **只有 fs / dns / crypto / zlib 进池**：文件 I/O（`fs.readFile`）、`dns.lookup`、`crypto.pbkdf2` / `scrypt`、zlib 压缩解压，这些平台没有像 socket 那样统一高效的异步接口，或本身就是偏阻塞、CPU 型工作
  - **线程池默认 4 个线程**：`UV_THREADPOOL_SIZE` 可调、允许的最大值是 1024；10 个 `pbkdf2` 任务会呈现 4 / 4 / 2 分批完成的节奏
  - **`UV_THREADPOOL_SIZE` 的三个坑**：必须在进程启动前设置（运行时改 `process.env` 无效，libuv 只在启动时读一次）、不是越大越好（上下文切换开销）、`fs` / DNS / `crypto` / zlib 共用同一组线程池，给 `crypto` 开满会挤占 `fs.readFile` 的并发
- **两条微任务队列与微任务检查点**
  - **两条队列**：`process.nextTick()` 队列（nextTickQueue）与 Promise 微任务队列（`Promise.then` / `catch` / `finally`）；宏任务走六个阶段，微任务走更靠前的检查机制
  - **同步代码永远先跑完**：异步 API 在这一步只是"注册"，例如 `start → end → nextTick → promise → timeout`
  - **nextTick 不属于任何 phase**：官方六阶段图里没有它，触发时机是 Call Stack 清空后立刻把 nextTickQueue 清空到空，再继续 Event Loop，因此优先级高于 Promise 微任务与所有宏任务
  - **同一检查点内 nextTick 先于 Promise**：两条独立队列，顺序固定为先清空 nextTickQueue、再清空 Promise 队列
  - **检查点在每个 JS 回调返回调度层时**：不是一整轮才清一次，所以同轮两个 `setTimeout` 的输出是 `timer1 → promise → timer2` 而不是 `timer1 → timer2 → promise`
  - **递归 nextTick 会饿死事件循环**：队列要"清空到空"，边清边注册就永远清不完，`poll` / `timers` / `check` 都进不去（I/O starvation）；需要"让出执行权但不饿死循环"时应改用 `setImmediate`
- **输出顺序推演四步法**
  1. **先划出同步代码**：不在任何回调里的 `console.log` 一定按书写顺序最先打印，异步 API 此刻只是注册
  2. **标出每个回调返回处的微任务检查点**：每执行完一个宏任务回调就在返回点记一个检查点
  3. **同一检查点内 nextTick 优先于 Promise**：先清空 `process.nextTick` 队列，再清空 Promise 队列，都清空到空
  4. **最后才轮到下一阶段的宏任务**：微任务全部清空后 Event Loop 才推进到下一个 phase，然后回到第 2 步


### 04-异步编程与事件驱动

- **异步写法的三次变革（Callback → Promise → async/await）**
  - **演进链**：`Callback` 解决嵌套地狱 → `Promise` 链式 `.then` → `async/await` 同步式书写
  - **层层包裹而非替代**：`async/await` 建立在 `Promise` 之上，`Promise` 又把 `Callback` 的嵌套结构拍平；理解这条链才知道每层解掉了上一层的什么痛点
- **Callback：error-first 约定与回调地狱**
  - **error-first 约定**：回调的第一个参数永远是 `error` 对象、第二个起才是真正的返回值，调用方必须先判断 `err` 才能继续；贯穿 `fs`、`net`、`http` 等几乎所有回调式 API
  - **回调地狱的两个真问题**（不只是"缩进深"）：可读性差，代码呈金字塔状右移、主流程被埋在最深的括号里；错误处理分散，每层都要手写一遍 `if (err)`，漏掉一层错误就被悄悄吞掉，编排"并行 / 超时 / 任一失败即中止"几乎不可读
- **Promise：三态不可逆与链式语义**
  - **三种状态且不可逆**：`pending` → `fulfilled`（`resolve` 进入）/ `rejected`（`reject` 或链中抛错进入）；一旦落到终态就锁死，不能再变
  - **链式语义把嵌套拍平**：`.then` 回传 Promise 时会被自动展开，嵌套变成纵向的链；`.catch` 捕获整条链上任意位置的拒绝，是统一错误处理点；`.finally` 不论成败都执行，适合清理；在 `.then` 里直接 `throw` 会被自动转成 `rejected`，`catch` 一定接得住
- **async/await 只是"看起来"同步**
  - **并没有把异步 I/O 变成阻塞 I/O**：`await` 只把当前 `async` 函数"后面的部分"挂起为一个微任务，等 `Promise` 就绪后再回来继续；挂起期间主线程立刻腾出来处理别的回调、别的请求
  - **心智模型**：`await` 是"在这里插一个书签，结果好了再回来接着跑"，而不是"让整个程序停在这行"，底层非阻塞 I/O 的本质完全没有改变
- **并发编排：什么时候该并行**
  - **`await` 的默认语义是串行**：三个互不依赖的 100ms / 100ms / 500ms 任务逐个 `await`，总耗时 ≈ 700ms
  - **判断准则**：两个 `await` 之间没有数据依赖时就该用 `Promise.all` 并发，总耗时 ≈ 最慢的 500ms；服务端把"取用户信息 + 读会话状态 + 查配置中心 + 调第三方 API"这类独立调用写成串行会让端到端时延线性累加
  - **四种组合器的分工**
    1. **`Promise.all`**：快速失败——任一 reject 整体立刻 reject，其余已发起的任务不会被取消、只是结果被整体丢弃
    2. **`Promise.allSettled`**：永不因失败而整体失败，拿到每项形如 `{ status: 'fulfilled', value }` 或 `{ status: 'rejected', reason }`
    3. **`Promise.race`**：谁先"落定"（成功或失败都算）就以谁为准，常用于加超时
    4. **`Promise.any`**：谁先成功就以谁为准，只有全部失败才整体 reject，适合多镜像源取最快可用
- **EventEmitter：事件驱动的骨架**
  - **解决的场景**：`Promise` / `async` 解决"等一个结果"，而 `EventEmitter` 解决"一个源头不断吐出多个事件"
  - **核心四步**：注册 → 等待 → 触发 → 执行监听器；常用 API 为 `on` / `emit`（同步调用所有监听器）/ `once` / `off` / `listenerCount`
  - **是大量内置对象的基类**：`net.Server`、`http.Server`、`fs.ReadStream`、`process` 本质上都是它的实例，所以才有 `server.on('connection', ...)`、`req.on('data', ...)`、`process.on('exit', ...)`
  - **两个必须知道的实战坑**
    1. **`'error'` 事件没有监听器会直接让进程崩溃**：会抛出 `uncaughtException` 导致进程退出，凡是要 `emit('error', ...)` 的对象务必先挂监听器
    2. **监听器泄漏**：默认同一事件最多挂 10 个监听器，超过就告警 `MaxListenersExceededWarning`；`on` 了不 `off`、或在循环里反复 `on`，监听器数量只增不减、闭包引用的对象无法回收——用 `once`、显式 `off` 或具名函数，靠 `listenerCount` 排查
- **事件驱动解耦"执行"与"观测"**
  - **本质**：业务主流程只在关键节点 `emit`，完全不需要知道外面挂了多少监听器、它们怎么实现；日志 / 监控 / 通知 / 状态更新各自 `on` 监听，互不影响
  - **收益**：新增"埋点 / 审计 / 告警"时只要在外部再加一个 `task.on(...)`，业务主流程一行都不用改，执行逻辑与观测逻辑靠事件总线连接


### 05-Buffer 与 Stream

- **Buffer 的内存模型与"编码只是视角"**
  - **固定长度的字节序列**：容量在创建时就定死，不能无限追加；Node 4+ 的 `Buffer` 是 `Uint8Array` 的子类，能与整个 TypedArray 体系互操作（`buf instanceof Uint8Array` 为 `true`）
  - **字节本身没有编码**：`Buffer.from('hello')` 打印成 `<Buffer 68 65 6c 6c 6f>`，正好是 ASCII 的 `h e l l o`、每个字母一字节；同一段字节用 `'utf8'` / `'hex'` / `'base64'` 解读分别得到 `hello` / `68656c6c6f` / `aGVsbG8=`，这正是 `Buffer.from(str)` 与 `buf.toString()` 成对出现的原因
  - **`Buffer.alloc(n)` 与 `Buffer.from(x)` 的区别**：`alloc(n)` 分配 n 个字节并清零，适合作为待填充的缓冲区；`from(x)` 从已有数据（字符串、数组、`ArrayBuffer`）编码而来，不清零；不要用未清零的 `Buffer(size)` 旧构造，它残留堆上的随机旧数据、可能泄漏敏感信息
- **字符长度 ≠ 字节长度（`Content-Length` 的坑）**
  - **基本差异**：`'你好'.length` 是 2（字符数），`Buffer.from('你好').length` 是 6（UTF-8 下每个汉字 3 字节）
  - **中英混合**：`'中文abc'.length` 是 5，对应字节数是 9（中 3×2 + 英 1×3）
  - **结论**：算 HTTP 响应头的 `Content-Length`、切分二进制协议帧、限制上传体积时，必须用 `Buffer.length`（字节数）而不是 `string.length`（字符数），否则长度会被算小、下游按错误长度截断导致数据错乱
- **Buffer 的五个应用场景**
  1. **文件读取**：`fs.readFile` 不指定 encoding 时，回调拿到的 `data` 就是 `Buffer`
  2. **TCP Socket 的 `data` 事件**：网络收到的原始字节，`chunk` 通常就是 `Buffer`
  3. **图片 / 音频 / 视频**：JPEG、PNG、MP3、MP4 本质都是二进制字节流
  4. **加密**：明文先变成 `Buffer`，交给 `AES` / `RSA` 处理，产出的密文也是 `Buffer`
  5. **Base64 编解码**：把任意二进制安全地塞进只认文本的协议（邮件、JSON、Data URL）
- **Stream 的本质，以及它与 Buffer 的关系**
  - **一块一块地搬**：`fs.readFile` 读 10GB 视频意味着整个文件进内存、进程直接被撑爆；Stream 一次只搬一小块（通常 64KB），内存占用始终维持在几十 KB 到几 MB
  - **水桶与水管**：`Buffer` 是一块数据（水桶里装的那桶水），`Stream` 是数据的运输方式（水管）；Stream 不断输送一个又一个 Buffer chunk——没有 Buffer 就没东西可运，没有 Stream 就只能整块整块堆在内存里
- **四种 Stream**
  1. **`Readable`（只读）**：只生产数据，如 `fs.createReadStream('./a.txt')`、HTTP 请求体
  2. **`Writable`（只写）**：只消费数据，如 `fs.createWriteStream('./b.txt')`、HTTP 响应
  3. **`Duplex`（双向）**：同时可读可写，**典型是 TCP Socket**
  4. **`Transform`（双向 + 转换）**：`Duplex` 的一种，输入经过"转换"再输出，如 `gzip` 压缩、加解密、数据格式转换
- **Stream 的工程实践：复制、背压与 `pipe` / `pipeline`**
  - **复制大文件必须用 Stream**：`fs.readFile` + `fs.writeFile` 会把整个文件读进内存、大文件直接 OOM；`createReadStream` 配 `pipe` 到 `createWriteStream` 后数据沿 `Disk → Buffer → Readable Stream → Writable Stream → Disk` 流动，内存恒定在几 KB 到几 MB
  - **背压是 Stream 真正高级的地方**：速度不匹配时（磁盘 500MB/s、网络 10MB/s），`writable.write(chunk)` 返回 `true` 表示内部缓冲未到阈值可继续写、返回 `false` 表示**缓冲已达上限、调用方应暂停读取**，否则内存照样涨到 OOM；缓冲降下来后触发 `'drain'` 事件再恢复写入，闭环是 `write() 返回 false → pause → 缓冲下降 → 'drain' → resume`
  - **`highWaterMark` 决定背压触发点**：`createReadStream` 的 `highWaterMark` 默认 64KB，阈值越小内存越省但搬运次数越多；手写 `pause` / `resume` 容易出错，直接用 `pipe` / `pipeline`，它们内部已自动协调背压
  - **`pipe` 与 `pipeline` 的取舍**：`pipe` 会自动协调读取速度、写入速度、缓存与背压，但**下游出错时不会自动销毁上游**，可能留下悬挂的流与未释放的文件描述符、Socket；`pipeline`（`node:stream/promises`）在任意一环出错时统一销毁所有流并抛出错误，还能顺序串联多个 Transform（读 → 压缩 → 加密 → 写）——简单搬运用 `pipe`，链路更长、需要错误兜底或串联多个转换时用 `pipeline`
- **流式推送为什么必须用 Stream**
  - **问题**：日志流、进度百分比、大文件传输、实时监控数据这类**持续产生**的数据，用 `readFile` 或先拼成大字符串再一次性返回，会让客户端干等到全部生成完、服务端内存还被撑着
  - **做法**：把数据源做成 Readable Stream 边产生边推，客户端每收到一段就消费一段；`res` 本身就是 `Writable` Stream，`stream.pipe(res)` 即可
- **落地 `fs` 与 `path`：读写、目录遍历与拼路径**
  - **`fs` 的三种风格**：老式回调版（深层嵌套易成回调地狱）、`fs/promises`（配 `async/await` 与 `try/catch` 统一兜底，现在的主流）、`*Sync` 同步版——同步版会**阻塞事件循环**直到 I/O 完成，只适合启动初始化、CLI 这类不在请求热路径上的场景
  - **常用 API**：`readFile` / `writeFile` / `mkdir({ recursive: true })` / `readdir`（配 `withFileTypes` 拿 `Dirent` 判断类型，避免反复 `stat`）/ `stat`（`isFile()` / `isDirectory()` 与 `size`）/ `rm({ recursive: true })`
  - **拼路径永远用 `path.join`**：手写 `'/'` 或 `'\\'` 在跨平台（Linux `/`、Windows `\`）时必翻车；`basename` / `dirname` / `extname` / `parse` 能把路径拆成结构化字段，`path.sep` 给出当前系统分隔符
  - **`path.resolve` 与 `path.join` 的区别**：`join` 只按顺序拼接并规范化，不引入当前工作目录；`resolve` 从右往左拼、**遇到绝对路径就停下来**，并把结果解析成基于 cwd 的绝对路径（相当于对每段依次 `cd`）——只是拼路径用 `join`，要"从项目根出发的绝对路径"才用 `resolve`


### 06-进程线程与优雅退出

- **进程的本质与观测**
  - **`node app.js` 起的是一个进程**：拥有独立的内存空间、一个 V8 实例、一块堆（Heap）、一个事件循环、一组文件描述符与若干系统资源
  - **用全局 `process` 观测**：`pid`（操作系统唯一标识）、`uptime()`、`argv`（`argv[0]=node`、`argv[1]=脚本`）、`exitCode`（设码但非立即退出）、`memoryUsage()`（`rss` 物理内存总量、`heapTotal` V8 已申请堆、`heapUsed` JS 堆已用、`external` 堆外内存如 Buffer）
  - **`rss` 常远大于 `heapUsed`**：一个 Node 进程"JS 对象不多、内存却很大"是常态，因为 Buffer、线程栈等都算进 `rss`
- **`child_process` 四把刀**
  1. **`spawn(command, args)`**：不走 shell、输出走**流**（边产边吐），适合长时间运行、大量输出；`stdio: 'inherit'` 让子进程共用父进程标准输入输出，`detached: true` 配 `child.unref()` 可让子进程脱离父进程独立运行
  2. **`exec(command, cb)`**：走 shell、把输出**全缓冲**在内存后回调，适合 `git status` 这类短命令；输出特别大会撑爆 `maxBuffer`（默认 1MB）
  3. **`execFile(file, args, cb)`**：不经 shell 直接执行已知可执行文件，无 shell 注入面、更安全
  4. **`fork(modulePath)`**：专门创建 Node 子进程并额外建立 **IPC 通道**，用 `child.send()` / `process.on('message')` 通信
  - **口诀**：流式大输出用 `spawn`；短命令拼 shell 用 `exec`；跑文件不要 shell 用 `execFile`；跑 Node 并通信用 `fork`
- **单进程吃不满多核，以及 `cluster` 的正确定位**
  - **多进程并行的由来**：8 核 CPU 上 Node 执行 JS 默认只用一条主线程，事件循环再快也只持续占满一个核；要让多核都忙起来就得开多个进程各占一核，而进程之间互相隔离、还得专门手段协作
  - **`cluster` 的做法**：Primary 进程 fork 出多个 Worker，它们**共享同一监听端口**，由 OS / Primary 做负载分发；Worker 数量取 `os.availableParallelism()`（不写死核数），`cluster.on('exit')` 里崩一个补一个
  - **关键提醒**：Node 官方明确——不需要进程级隔离时应优先 `worker_threads`（同实例内可共享内存、成本更低）；`cluster` 的真正价值是**进程级故障隔离 + 多核部署**，而不是单纯并行算点东西
- **进程与线程的内存模型**
  - **进程内存默认不共享**：进程 A 的 `const count = 100` 进程 B 无法直接访问，通信只能借"进程外通道"：IPC（含 `fork` / `cluster` 通道、pipe）、Socket（TCP / Unix Domain）、Redis、消息队列、HTTP
  - **线程是进程内的执行路径**：一个进程可并发多条线程，它们**共享进程的一部分内存**、通信成本低于进程，代价是并发控制、内存可见性与**竞态条件**——多线程同时改同一块数据，结果取决于执行时序
  - **进程 vs Worker Thread**：进程内存独立、V8 与 Event Loop 各自独立、隔离性强（崩一个不影响其他）、创建成本较高、只能走 IPC、能运行外部程序；Worker 可用 `SharedArrayBuffer` 共享内存、创建成本较低、隔离较弱、并发安全要自己管
- **`worker_threads`：适用边界与池化实践**
  - **同进程内开 JS 线程**：主线程 `postMessage` 派活、Worker 用 `parentPort` 回结果；Worker 有自己的 V8 与执行环境，却与主线程同属一个进程
  - **三个必备件**：`worker.terminate()` 主动销毁线程释放 V8 资源、`worker.on('error')` 兜住未捕获异常、`isMainThread` 确认运行上下文
  - **适合 CPU 密集型 JavaScript**：图片处理、视频数据处理、巨大 JSON 解析 / 计算、复杂数学、压缩、哈希、大数组、复杂文本解析；反例是请求处理函数里跑十亿次循环——主线程被占死，请求 A/B/C、WebSocket、Timer 全部受影响
  - **判别标准**：I/O 密集（网络、文件、DB / Redis 调用）交给 Event Loop / 异步 I/O；CPU 密集（大计算、加解密、压缩）用 Worker Threads
  - **I/O 不要丢给 Worker**：每个请求都 `new Worker` 要额外付"创建 Thread → 初始化 V8 环境 → 跨线程传输数据 → 销毁 Thread"四份成本，反而更慢
  - **不等于 libuv 线程池**：libuv Thread Pool 由 Node **内部**维护、替你跑 `fs` / `dns` / `crypto` / `zlib` 的底层阻塞操作，你一般不直接创建、也感知不到；`worker_threads` 是你 `new Worker()` **主动创建**、有独立 V8 跑你写的 JS
  - **不要每请求 `new Worker`**：1 万并发就是 1 万个 Worker，创建与调度本身成了新瓶颈，比主线程直接算还惨
  - **正确做法是 Worker Pool + Task Queue**：预先创建固定数量（≈ CPU 核数）的 Worker，要点为①空闲标记（只派给空闲的）②任务队列（超额排队而非新建线程）③轮询派发④`Promise` 包装（对外暴露 `runTask(input): Promise<result>`）
  - **共享内存的代价是并发安全**：`SharedArrayBuffer` 能让主线程与 Worker 共享同一块内存，但两个 Worker 并发 `shared[0]++` 会因"读→改→写"非原子而丢失更新，必须用 `Atomics.add`——没有同步原语，共享内存几乎必然写出并发 Bug
- **四种并发方式的选型**
  1. **普通 HTTP / DB / Redis / 外部 API** → Event Loop（异步 I/O）
  2. **CPU 密集型 JavaScript** → `worker_threads`（配 Worker Pool）
  3. **要强隔离 / 独立崩溃 / 运行外部程序 / 执行 shell** → `child_process`
  4. **要多实例铺满多核 + 进程级故障隔离** → 多进程（`cluster` / 进程管理器 / 容器编排 + 负载均衡）
- **优雅关闭与错误分层兜底**
  - **优雅关闭（Graceful Shutdown）**：收到 `SIGTERM` **不应立刻退出**，而应停收新连接（`server.close()` + `closeIdleConnections()` 关空闲 keep-alive）→ 等在途请求结束（带 10 秒超时兜底防卡死）→ 关数据库 / Redis / MQ → `process.exit(0)`
  - **两个信号都要接**：`SIGTERM` 是容器编排的标准信号（`docker stop` 默认发它、K8s 滚动发布也发），`SIGINT` 是终端 `Ctrl+C` 发的、本地调试必碰
  - **不要滥用 `process.exit()`**：它会**立即**终止进程，可能丢掉没写完的 `stdout`、没发出的日志、没提交的数据库事务、没结束的 HTTP 响应；官方建议若因错误必须结束进程，让未捕获错误自然终止更安全——自然终止前 Node 会先跑完已排队的 I/O 与回调。生产要掌握的是 `process.exitCode`、Graceful Shutdown、Signal Handling 三件事
  - **错误按发生位置分层接住**：同步代码（如 `JSON.parse`）用 `try / catch`；回调式 API 判断第一个 `err` 参数；Promise / async 用 `.catch` 或 `await try/catch`；路由 / 定时任务 / 消息消费入口外层包 try/catch 转成可观测响应；漏到进程级用 `uncaughtException` / `unhandledRejection` 做最后清理（前者是同步代码抛出却没人 catch，后者是 Promise reject 了却没接住）
  - **`uncaughtException` 之后不推荐继续运行**：异常能漏到这一层说明进程内部状态已不可信（模块半初始化、状态写坏），强行续命会引入更难查的 Bug；正确姿势是记录日志 + 优雅退出，交给 PM2 / K8s 拉起干净新进程
  - **判断错误种类**：用 `error.code`（如 `ENOENT` 文件不存在、`EADDRINUSE` 端口被占用、`ECONNRESET` 连接被重置）与 `error.name`（如 `TypeError` / `RangeError`）
- **环境变量与 `os` 模块**
  - **`process.env` 读环境变量**：区分环境、存放敏感配置；配 `.env` 文件由 `dotenv` 加载（`import 'dotenv/config'`）
  - **`.env` 不要提交 Git**：它常含数据库密码、API Key，提交等于公开密码；正确做法是 `.env.example` 进仓库、真实 `.env` 进 `.gitignore`
  - **`NODE_ENV` 的通行用法**：`development` 开调试、`production` 关调试走优化，很多库都读它决定行为
  - **`os` 提供机器信息**：`os.cpus()` 看核数、`os.totalmem()`、`os.availableParallelism()`（Node 推荐的并行 worker 数，`cluster` / `fork` 用它，比硬编码 `os.cpus().length` 更贴合 Node 调度建议）、`os.homedir()`、`os.tmpdir()`


### 07-运行机制收束

- **完整架构的三条主线**：网络 I/O 走内核 epoll/kqueue/IOCP 不进线程池；fs/crypto/dns/zlib 走 libuv 线程池；你写的 JS 只在主线程的 V8 里跑
- **主动创建的两类并发结构**：同进程内的 Worker Thread（可共享 SharedArrayBuffer）与独立 Child Process（内存不共享，靠 IPC/Socket）
- **七篇在架构图上的位置**：模块系统决定代码怎么进 V8，事件循环与微任务决定主线程怎么转，Buffer/Stream 决定数据怎么流，进程线程是主动扩出的并发
- **抽象栈定位**：模块一讲的全是"进程内"的事，业务代码与框架在上、Event Loop + libuv + 内核在下，排障时从现象所在层往相邻层递推
- **决策模型的第一反应**：见"卡 / 慢 / 顺序乱 / 内存涨"先问"事件循环是不是被占住了、数据流有没有背压"，再决定换异步、上 Stream，还是丢给线程/进程
- **六条误区清单**：单线程、所有异步都在线程池、await 阻塞事件循环、worker_threads 就是线程池、nextTick 越多越快、多开进程就能变快
- **自测 6 问**：覆盖 01~08，能答上（一次请求 CPU 真算多久、require 与 import、六个阶段、nextTick 与 Promise、await 写成串行、进程不退出漏了什么）说明模块一过关
- **交接模块二**：进程内 I/O 模型收口，接下来要回答"这些 I/O 从哪来"——HTTP/TCP/WebSocket 的本质是跨机器交换字节

| 锁文件 | package.json 写的是范围会漂移，package-lock.json 钉死实际版本，配 npm ci | 02 篇 |
| await 与并发 | 无数据依赖的两个 await 会写成串行，应改 Promise.all | 04 篇 |
| Promise.all 的失败语义 | 任一 reject 整体立刻 reject，其余成功结果被丢弃 | 04 篇 |
| EventEmitter 的 error | emit('error') 无监听器会抛 uncaughtException 让进程退出 | 04 篇 |
| 字符长度 ≠ 字节长度 | `'你好'.length` 是 2，Buffer 长度是 6（UTF-8 每汉字 3 字节） | 05 篇 |
| 背压 | write() 返回 false 表示缓冲到顶、上游应暂停，`'drain'` 后恢复 | 05 篇 |
| pipe 与 pipeline | pipe 不销毁上游；pipeline 任一环出错统一销毁整条链路 | 05 篇 |
| Worker Thread 与线程池 | 前者你主动创建跑你的 JS，后者 Node 内部跑 fs/dns/crypto/zlib | 06 篇 |
| 不要每请求 new Worker | 应使用 Worker Pool（≈ 核数）+ Task Queue | 06 篇 |
| 优雅关闭 | SIGTERM 后停收新连接 → 等在途请求（带超时兜底）→ 关依赖 → 退出 | 06 篇 |
| 决策模型第一反应 | 先问"事件循环是不是被占住了、数据流有没有背压" | 07 篇 |

## 见 X 想 Y

现象是表相，先定位到层，再动手。

| 见到什么 | 该想到什么 | 一句话理由 |
| --- | --- | --- |
| 接口慢、一次请求两三秒 | I/O 密集型，等的是别人 | CPU 真正执行只有几毫秒，别急着加机器 |
| 响应顺序不符合预期 | 微任务检查点（nextTick vs Promise） | 每个回调返回调度层都清一次，同检查点内 nextTick 先于 Promise |
| CPU 打满但 QPS 很低 | 主线程被同步长任务占住 | 事件循环转不动，I/O 回调全在排队 |
| 代码里出现 readFileSync / execSync | 同步 API 阻塞事件循环 | 同步版本只适合启动初始化与 CLI，别放请求热路径 |
| 大文件读写、上传下载、日志推送 | Stream + 背压 | 一次读进内存会撑爆堆，createReadStream + pipe 内存恒定 |
| 内存一路涨最后 OOM | 背压没做 / 事件监听器泄漏 | write() 返回 false 没暂停，或 on 了不 off |
| 压缩、加密、大 JSON 解析 | Worker Thread（走线程池） | CPU 密集会占住唯一的 JS 线程，丢到 Worker 才不卡 |
| 调 ffmpeg / python 脚本 / 系统命令 | child_process（spawn / execFile） | 这是别的程序，得起独立进程去跑 |
| 用不满多核、要故障隔离 | 多进程（cluster / 进程管理） | 一个 Node 进程只用一个核，崩一个不影响其他 |
| 服务重启丢请求 | SIGTERM 优雅关闭 | 先停收新请求、等存量请求跑完再退出，别硬切连接 |
| 进程不退出 | 未清理的句柄 + 优雅关闭 | server / timer / 长连接没 close，句柄清空进程才自然退出 |
| 同样并发换多核机器没变快 | 先确认瓶颈是"算"还是"等" | I/O 密集等的是别人，加核帮不上忙 |
| "在我机器上能跑" | 锁文件没提交或版本范围漂移 | package.json 写的是 `^` 范围，靠 package-lock.json 钉死 |

## 易错点汇总

- **"Node.js 是单线程的"／"所有异步操作都在线程池里跑"**：只有执行 JS 的主线程是单线程。网络 I/O 走内核 epoll/kqueue/IOCP 通知，不进线程池；只有 fs、部分 DNS、crypto、zlib 才进 libuv 线程池，而且它们共用同一组默认 4 个线程。
- **"setTimeout(fn, 1000) 就是 1000ms 后执行"**：它是"至少 1000ms 后才有资格执行"，还要等主线程空闲。主线程被 while 阻塞 3 秒，这个回调就 3 秒后才跑。它是最小等待时间，不是精确执行时间。
- **"微任务是一整轮 Event Loop 之后才清一次"**：每个 JS 回调返回调度层都是一次微任务检查点。所以同一轮 timers 里的两个 setTimeout 输出是 `timer1 → promise → timer2`，而不是 `timer1 → timer2 → promise`。
- **"process.nextTick 用得越多越快"**：nextTick 队列要一直清空到空，在回调里递归注册会让它永远清不完，事件循环进不了 poll/timers/check，造成 I/O 饥饿。需要让出执行权又不想饿死循环时，用 setImmediate。
- **"await 会阻塞事件循环"**：await 只暂停当前 async 函数的后半段并挂成微任务，主线程立刻去处理别的回调。真正的坑是"两个互不依赖的 await 写成串行"，本该 500ms 的活儿变成 700ms。
- **"重新赋值 module.exports 后，再挂 exports.xxx 也生效"**：`exports` 只是 `module.exports` 的初始引用，一旦整体替换 `module.exports`，挂在旧 `exports` 上的属性外界全拿不到。整体替换用 `module.exports`，增量挂属性用 `exports.xxx`。
- **"UV_THREADPOOL_SIZE 可以运行时改、每个模块各有一个池"**：libuv 在进程启动时一次性读取并创建线程，运行时改 `process.env.UV_THREADPOOL_SIZE` 无效。而且 fs、DNS、crypto、zlib 抢的是同一组线程，给 crypto 开满会挤占 fs。
- **"字符串长度等于字节长度"**：`'你好'.length` 是 2，`Buffer.from('你好').length` 是 6。算 Content-Length 或切分二进制协议帧时用字符数会让长度算小，下游按错误长度截断，数据全乱。
- **"有 pipe 就够了，不需要 pipeline"**：pipe 只协调背压，下游出错时不会销毁上游，容易留下没释放的文件描述符与 Socket。链路长、要错误兜底、要串多个 Transform 时用 pipeline，它出错统一销毁整条链路。
- **"worker_threads 就是 libuv 线程池"／"每请求 new 一个 Worker"**：前者是你主动 `new`、有独立 V8 跑你的 JS，后者是 Node 内部跑 fs/dns/crypto/zlib 的系统线程。生产环境每请求 new 一个 Worker，1 万并发就是 1 万个线程，应该用 Worker Pool + Task Queue。
- **"emit('error') 没监听器顶多报个错"**：EventEmitter 对 error 事件有特殊处理，没有监听器会直接抛 uncaughtException 让进程退出。同理 on 了不 off 会触发 MaxListenersExceededWarning（默认上限 10），且闭包引用的对象无法回收、内存缓慢上涨。
- **"多开进程就能变快"／"process.exit(1) 很干脆"**：多开进程只对 CPU 密集或要故障隔离的场景成立，I/O 密集的瓶颈是等待，多开只是多占内存。`process.exit()` 会立即终止，stdout 没写完、日志没发出、事务没提交、响应没结束都可能发生。

## 与相邻模块的接口

**进入本模块前必须已经掌握**：这是整套体系的起点，没有前置依赖。只要会写 JavaScript（变量、函数、对象、class、Promise）、能在终端敲命令就够了。Node 的 fs / http / crypto 这些服务端能力从哪来，本模块会从头讲起。

**本模块交给下一模块什么**：本模块产出的是"进程内"的完整 I/O 模型——事件循环为什么能扛并发、异步怎么写、字节流怎么搬、单线程不够时怎么用进程与线程分流。下一模块要靠它回答一个一直悬着的问题：**这些 I/O 到底是从哪来的**。HTTP 请求、TCP 连接、WebSocket 推送本质都是"通过网卡与另一台机器交换字节"，而 Socket 就是一条 Duplex Stream、HTTP body 就是 Stream 在搬运 Buffer。
