# 异步编程与事件驱动

## 异步编程为什么经历了三次写法变革？

Node.js 的异步写法，从早期到现在走过一条非常清晰的演进链：

```
Callback  ──(解决嵌套地狱)──▶  Promise  ──(语法糖)──▶  async / await
   回调                        链式 .then                 同步式书写
```

三者不是替代关系，而是层层包裹：`async/await` 建立在 `Promise` 之上，`Promise` 又把 `Callback` 的嵌套结构拍平。理解这条链，才知道每一层到底解决了上一层的什么痛点。

## Callback：error-first 约定与回调地狱

Node.js 最早的异步范式是回调函数——把"完成后要做什么"作为一个函数参数传进去。

```js
import fs from 'node:fs';

// error-first：回调第一个参数永远是 error
fs.readFile('./test.txt', 'utf8', (err, data) => {
  // 约定：err 为 null 表示成功，非 null 表示出错
  if (err) {
    console.error('读取失败：', err);
    return;
  }
  console.log(data);
});
```

这是 Node 的核心约定：**error-first callback**。回调的第一个参数永远是 `error` 对象，第二个参数起才是真正的返回值。调用方必须先判断 `err` 才能继续。这个约定贯穿了 `fs`、`net`、`http` 等几乎所有回调式 API。

当多个步骤前后依赖时，问题就出现了：

```js
// 每一步都依赖上一步的结果，层层向右嵌套
getUser((user) => {
  getOrders(user.id, (orders) => {
    getProducts(orders, (products) => {
      saveResult(products, () => {
        // 真正的业务逻辑被挤到最右列
      });
    });
  });
});
```

这就是经典的 **Callback Hell（回调地狱）**。它暴露两个真问题，而不只是"缩进深"：

- **可读性差**：代码呈金字塔状右移，主流程被埋在最深的括号里，想看清执行顺序要来回扫视。
- **错误处理分散**：每一层都要手动写一遍 `if (err)`，一旦漏掉某一层，错误就悄悄吞掉；要编排"并行 / 超时 / 任一失败即中止"这类逻辑，回调写法几乎不可读。

`Promise` 的出现正是为了把"嵌套的回调"拍平成"可组合的链式调用"。

## Promise 把嵌套拍平成了链

`Promise` 是一个"未来才会有结果"的容器，它有三种状态，且**状态不可逆**：

```
       resolve()          reject() / throw
  ┌──────────────┐   ┌──────────────────────┐
  │   pending    │──▶│       fulfilled       │  (已成功，终态)
  └──────────────┘   └──────────────────────┘
        │
        └────────────▶  rejected  (已失败，终态)
```

- `pending`：进行中，初始状态。
- `fulfilled`：已成功，调用 `resolve` 进入。
- `rejected`：已失败，调用 `reject` 或链中抛出错误进入。
- **一旦落到 `fulfilled` 或 `rejected`，状态就锁死，不能再变。**

链式调用让嵌套消失：

```js
getUser()
  .then((user) => getOrders(user.id))     // 返回新的 Promise，自动往下传
  .then((orders) => getProducts(orders))
  .then((products) => saveResult(products))
  .catch((error) => {
    console.error('任一环节出错都会落到这里：', error);
  })
  .finally(() => {
    console.log('无论成功失败都执行，如释放资源');
  });
```

几个关键语义：

- `.then` 回传 Promise 时会被自动"展开"，于是嵌套变成纵向的链，主流程一眼到底。
- `.catch` 捕获**整条链上任意位置**的拒绝，是统一错误处理点。
- `.finally` 不论成败都会执行，适合做清理（关连接、清临时状态）。
- 在 `.then` 里直接 `throw new Error(...)` 会被**自动转成 `rejected`**，等价于 `reject`，所以 `catch` 一定能接住。

## async/await 只是"看起来"同步

`async/await` 是 `Promise` 的语法糖，让代码读起来像同步：

```js
async function main() {
  try {
    const user = await getUser();
    const orders = await getOrders(user.id);
    const products = await getProducts(orders);
    await saveResult(products);
  } catch (error) {
    console.error(error);
  }
}
```

这里必须点明一个常见误解：**`async/await` 并没有把异步 I/O 变成阻塞 I/O。**

`await` 做的只是：把当前 `async` 函数"后面的部分"挂起为一个**微任务**，等 `Promise` 就绪后再回来继续。在挂起期间，主线程立刻腾出来去处理别的回调、别的请求——事件循环照常运转。如果你还不清楚微任务是什么，见第 03 篇《事件循环：六个阶段与微任务》。

心智模型：`await` 是"在这里插一个书签，结果好了再回来接着跑"，而不是"让整个程序停在这行"。底层非阻塞 I/O 的本质完全没有改变。

## await 用得不对，会把并发写成串行

这是本篇最值得记住的一点。`await` 的本质是"等这个 Promise 好了再往下走"，所以**两个互不相干的 `await` 之间其实是串行执行的**。

假设有三个互不依赖的任务，分别耗时 100ms / 100ms / 500ms：

```js
// 串行：每个 await 都死等上一个结束
const a = await taskA(); // 100ms
const b = await taskB(); // 100ms
const c = await taskC(); // 500ms
// 总耗时 ≈ 100 + 100 + 500 = 700ms
```

```js
// 并行：三者同时发起，一起 await
const [a, b, c] = await Promise.all([taskA(), taskB(), taskC()]);
// 总耗时 ≈ 最慢的 500ms
```

把时间轴画出来对照就一目了然：

```
串行：每个任务都要等前一个结束，耗时相加
时间 →
taskA  ███ 100ms
taskB       ███ 100ms
taskC            ███████████ 500ms
       └──────── 总耗时 ≈ 700ms ────────┘

并行：三个任务同一时刻出发，总耗时由最慢的决定
时间 →
taskA  ███ 100ms
taskB  ███ 100ms
taskC  ███████████ 500ms
       └── 总耗时 ≈ 500ms（取决于最慢的 taskC）──┘
```

关键判断准则：**两个 `await` 之间没有数据依赖时，就该用 `Promise.all` 并发；`await` 用得不合理，会把本来能并发的任务写成串行。** 在服务端尤其致命——一个请求往往要"取用户信息 + 读会话状态 + 查配置中心 + 调第三方 API"，前几步彼此独立，写成串行的 `await` 会让延迟线性累加，端到端时延直接翻倍。

## 并行时的错误处理：all 与 allSettled

并发时错误处理比串行微妙，因为多个任务同时跑，失败可能只发生在其中一个。

`Promise.all` 是**"快速失败"**语义：

```js
// 任意一个 reject，整体立刻 reject；其余已经发起的任务不会被取消，只是结果被丢弃
const [user, profile, config] = await Promise.all([
  getUser(id),
  getUserProfile(id),
  fetchRemoteConfig(id),
]);
```

也就是说，哪怕只有 1 个失败，你也拿不到另外 2 个的成功结果——它们被整体丢弃了。

如果你希望"各自的错误互相不影响，谁成谁败都要拿到"，用 `Promise.allSettled`：

```js
const results = await Promise.allSettled([getUser(id), getReport(id), queryInventory(id)]);
// results 是数组，每项形如：
//   { status: 'fulfilled', value: ... }   成功
//   { status: 'rejected',  reason: ... }  失败
const user = results[0].status === 'fulfilled' ? results[0].value : null;
```

另外两个并列工具，一句话定位：

- `Promise.race([...])`：谁先"落定"（成功或失败都算）就以谁为准，**第一个结果决定整体**。常用于加超时（`race([请求, 超时定时器])`）。
- `Promise.any([...])`：谁先**成功**就以谁为准，只有**全部失败**才整体 reject。适合"多个镜像源取最快可用"的场景。

怎么选，看下表：

| 方法 | 失败语义 | 拿到什么 | 典型场景 |
| --- | --- | --- | --- |
| `Promise.all` | 任一失败即整体失败 | 全成功的值数组，否则拿不到 | 步骤强依赖、要全有或全无 |
| `Promise.allSettled` | 永不因失败而整体失败 | 每项 `{status, value\|reason}` | 部分失败可容忍、需逐个处理 |
| `Promise.race` | 第一个落定者决定结果 | 第一个落定的结果 | 竞速、超时控制 |
| `Promise.any` | 全部失败才失败 | 第一个成功的结果 | 多源取最快可用 |

## EventEmitter：事件驱动的骨架

`Promise` / `async` 解决的是"**等一个结果**"。但有些场景是"**一个源头不断吐出多个事件**"——比如一个 HTTP 请求体上陆续到达的数据块、一个服务端任务从触发到分派再到汇总的全过程。`EventEmitter` 就是为此而生的事件中枢。

```js
import { EventEmitter } from 'node:events';

const emitter = new EventEmitter();

// 注册监听器
emitter.on('message', (msg) => {
  console.log('收到消息：', msg);
});

// 触发事件
emitter.emit('message', 'Hello Node');
// 输出：收到消息：Hello Node
```

常用 API：

- `emitter.on(event, listener)`：注册一个监听器（可多次触发）。
- `emitter.emit(event, ...args)`：触发事件，同步调用所有监听器。
- `emitter.once(event, listener)`：只触发一次，触发后自动移除。
- `emitter.off(event, listener)`：移除某个监听器。
- `emitter.listenerCount(event)`：查看某事件当前挂了多少监听器。

核心思想就四步：**注册 → 等待 → 触发 → 执行监听器**。

```
注册事件 (on)  ──▶  等待触发  ──▶  emit 触发  ──▶  遍历并执行监听器
```

`EventEmitter` 不是孤立的工具，它是 Node 里**大量内置对象的基类**。`net.Server`、`http.Server`、`fs.ReadStream`、`process` 本质上都是 `EventEmitter` 的实例——你会写 `server.on('connection', ...)`、`req.on('data', ...)`、`process.on('exit', ...)`，正是因为它们的原型链上就有 `EventEmitter`。理解它就理解了 Node 事件驱动的一半。

### 两个必须知道的实战坑

**坑一：`'error'` 事件没有监听器会直接让进程崩溃。**

`EventEmitter` 对 `error` 事件有特殊处理：如果触发了 `error` 却没有任何监听器，它会**直接抛出 `uncaughtException`，导致进程退出**。所以凡是你 `emit('error', ...)` 的对象，务必先挂一个error 监听器。

```js
emitter.on('error', (err) => {
  console.error('捕获到错误，进程不会崩：', err);
});
emitter.emit('error', new Error('出事了')); // 被上面的监听器接住
```

**坑二：监听器泄漏，会触发 `MaxListenersExceededWarning` 并持续吃内存。**

`EventEmitter` 默认同一事件最多挂 10 个监听器，超过就告警 `MaxListenersExceededWarning`。真正危险的是：`on` 了不 `off`，或者在循环里反复 `on` 同一个事件——监听器数量只增不减，闭包引用的对象也无法回收，内存缓慢上涨。

```js
// 危险：每次调用都新增一个监听器，永不移除
function bad(emitter, id) {
  emitter.on('data', (chunk) => handle(chunk, id));
}

// 正确：用 once 自动移除，或显式 off，或把监听器提取成具名函数后 off
function good(emitter, id) {
  const fn = (chunk) => handle(chunk, id);
  emitter.once('data', fn); // 触发一次后自动清理
  // 或 emitter.off('data', fn) 在合适时机移除
}
```

排查时可用 `emitter.listenerCount('data')` 观察某个事件的监听器数量是否异常增长。

## 事件驱动怎么解耦"执行"与"观测"

事件驱动最大的价值，是把"**业务主流程**"和"**日志 / 监控 / 通知 / 状态更新等观测逻辑**"彻底解耦。业务代码只负责在关键节点 `emit` 事件，完全不需要知道外面挂了多少监听器、它们怎么实现。

以一个"任务开始 → 调用外部服务 → 任务完成"的服务端流程为例：

```
业务主流程（只负责 emit）              观测层（各自 on 监听，互不影响）
─────────────────────────           ──────────────────────────────
emit('task:start')     ────────────▶  logger 记录开始时间
                                        metrics 计数 +1
emit('task:dispatch')  ────────────▶  监控统计标记"已调外部服务"
emit('task:progress')  ────────────▶  消息通知推送进度
emit('task:finish')    ────────────▶  状态更新写库
                                        推送最终结果给客户端
```

业务侧代码长这样，它根本不 import 任何日志或通知模块：

```js
const task = new EventEmitter();

task.on('task:start',    ({ jobId }) => log('任务开始', jobId));
task.on('task:dispatch', ({ name }) => metrics.mark(`call:${name}`));
task.on('task:finish',   ({ summary }) => updateStatus(summary));

async function runTask(input) {
  task.emit('task:start', { jobId: input.jobId });
  const result = await callPartnerApi(input);   // 调用外部服务
  task.emit('task:dispatch', { name: 'callPartnerApi' });
  task.emit('task:finish', { summary: result });
}
```

新增"埋点 / 审计 / 告警"时，只要在外部再加一个 `task.on(...)`，业务主流程一行都不用改。这就是事件驱动解耦的本质：**执行逻辑与观测逻辑各写各的，靠事件总线连接。**

---

异步"搬运"的到底是什么？——不是变量，而是**字节流**。一个文件、一段 TCP 报文、一份上传的附件，底层都是一串字节，而不是你写代码时习惯的 `string` / `object`。当数据大到内存装不下、或需要边产生边消费时，`Promise` 和 `EventEmitter` 都不再够用，你需要 `Buffer` 与 `Stream`。下一篇展开。

## 小结

- **异步写法的三次变革（Callback → Promise → async/await）**
  - **演进链**：`Callback` 解决嵌套地狱 → `Promise` 链式 `.then` → `async/await` 同步式书写
  - **层层包裹而非替代**：`async/await` 建立在 `Promise` 之上，`Promise` 又把 `Callback` 的嵌套结构拍平；理解这条链才知道每层解掉了上一层的什么痛点
- **Callback：error-first 约定与回调地狱**
  - **error-first 约定**：回调的第一个参数永远是 `error` 对象、第二个起才是真正的返回值，调用方必须先判断 `err` 才能继续；贯穿 `fs`、`net`、`http` 等几乎所有回调式 API
  - **回调地狱的两个真问题**（不只是"缩进深"）：可读性差，代码呈金字塔状右移、主流程被埋在最深的括号里；错误处理分散，每层都要手写一遍 `if (err)`，漏掉一层错误就被悄悄吞掉，编排"并行 / 超时 / 任一失败即中止"几乎不可读
- **Promise：三态不可逆与链式语义**
  - **三种状态且不可逆**：`pending` → `fulfilled`（`resolve` 进入）/ `rejected`（`reject` 或链中抛错进入）；一旦落到终态就锁死，不能再变
  - **链式语义把嵌套拍平**：`.then` 回传 Promise 时会被自动展开，嵌套变成纵向的链；`.catch` 捕获整条链上任意位置的拒绝，是统一错误处理点；`.finally` 不论成败都执行，适合清理；在 `.then` 里直接 `throw` 会被自动转成 `rejected`，`catch` 一定接得住
- **async/await 只是"看起来"同步**
  - **并没有把异步 I/O 变成阻塞 I/O**：`await` 只把当前 `async` 函数"后面的部分"挂起为一个微任务，等 `Promise` 就绪后再回来继续；挂起期间主线程立刻腾出来处理别的回调、别的请求
  - **心智模型**：`await` 是"在这里插一个书签，结果好了再回来接着跑"，而不是"让整个程序停在这行"，底层非阻塞 I/O 的本质完全没有改变
- **并发编排：什么时候该并行**
  - **`await` 的默认语义是串行**：三个互不依赖的 100ms / 100ms / 500ms 任务逐个 `await`，总耗时 ≈ 700ms
  - **判断准则**：两个 `await` 之间没有数据依赖时就该用 `Promise.all` 并发，总耗时 ≈ 最慢的 500ms；服务端把"取用户信息 + 读会话状态 + 查配置中心 + 调第三方 API"这类独立调用写成串行会让端到端时延线性累加
  - **四种组合器的分工**
    1. **`Promise.all`**：快速失败——任一 reject 整体立刻 reject，其余已发起的任务不会被取消、只是结果被整体丢弃
    2. **`Promise.allSettled`**：永不因失败而整体失败，拿到每项形如 `{ status: 'fulfilled', value }` 或 `{ status: 'rejected', reason }`
    3. **`Promise.race`**：谁先"落定"（成功或失败都算）就以谁为准，常用于加超时
    4. **`Promise.any`**：谁先成功就以谁为准，只有全部失败才整体 reject，适合多镜像源取最快可用
- **EventEmitter：事件驱动的骨架**
  - **解决的场景**：`Promise` / `async` 解决"等一个结果"，而 `EventEmitter` 解决"一个源头不断吐出多个事件"
  - **核心四步**：注册 → 等待 → 触发 → 执行监听器；常用 API 为 `on` / `emit`（同步调用所有监听器）/ `once` / `off` / `listenerCount`
  - **是大量内置对象的基类**：`net.Server`、`http.Server`、`fs.ReadStream`、`process` 本质上都是它的实例，所以才有 `server.on('connection', ...)`、`req.on('data', ...)`、`process.on('exit', ...)`
  - **两个必须知道的实战坑**
    1. **`'error'` 事件没有监听器会直接让进程崩溃**：会抛出 `uncaughtException` 导致进程退出，凡是要 `emit('error', ...)` 的对象务必先挂监听器
    2. **监听器泄漏**：默认同一事件最多挂 10 个监听器，超过就告警 `MaxListenersExceededWarning`；`on` 了不 `off`、或在循环里反复 `on`，监听器数量只增不减、闭包引用的对象无法回收——用 `once`、显式 `off` 或具名函数，靠 `listenerCount` 排查
- **事件驱动解耦"执行"与"观测"**
  - **本质**：业务主流程只在关键节点 `emit`，完全不需要知道外面挂了多少监听器、它们怎么实现；日志 / 监控 / 通知 / 状态更新各自 `on` 监听，互不影响
  - **收益**：新增"埋点 / 审计 / 告警"时只要在外部再加一个 `task.on(...)`，业务主流程一行都不用改，执行逻辑与观测逻辑靠事件总线连接
