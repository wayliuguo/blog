# 异步编程：从回调到 async/await 与事件驱动

> Node.js 的核心优势就是异步 I/O——不阻塞主线程。
> 承上：[事件循环](./03-事件循环) —— 先明白事件循环怎么调度，再看异步代码该怎么写
> 启下：[内置模块与文件操作](./05-内置模块与文件操作) —— 能用 Stream 边读边写大文件，并说清什么场景必须用流式而非一次性 readFile

---

本篇有两条线：一条是**异步写法**的演进（Callback → Promise → async/await → Promise.all），解决"单个异步操作怎么写得清楚、怎么并发得高效"；另一条是**事件驱动**（EventEmitter），解决"一个源头不断吐出多个事件时，怎么解耦生产者和消费者"。前者在前面逐节展开，EventEmitter 会在文末单独成节。

## 为什么需要异步

```javascript
// 同步代码：readFileSync 会阻塞，等文件读完才执行下一行
const data = fs.readFileSync('file.txt', 'utf8')
console.log('文件读取完成')
console.log('这行要等上面执行完')

// 异步代码：readFile 不会阻塞，先注册回调，继续执行后续代码
fs.readFile('file.txt', 'utf8', (err, data) => {
    console.log('文件读取完成')
})
console.log('这行先执行，不等文件读取')
```

异步的核心：**I/O 操作不阻塞主线程**，Node.js 可以继续处理其他请求。

## 回调函数（Callback）

回调是 Node.js 最早的异步模式。

```javascript
const fs = require('fs')

fs.readFile('file.txt', 'utf8', (err, data) => {
    if (err) {
        console.error('读取失败', err)
        return
    }
    console.log('文件内容:', data)
})
```

Node.js 早期约定：**回调的第一个参数是错误对象**（error-first callback）。

### 回调地狱

```javascript
// 多层嵌套，代码难以维护
fs.readFile('a.txt', 'utf8', (err, dataA) => {
    fs.readFile('b.txt', 'utf8', (err, dataB) => {
        fs.readFile('c.txt', 'utf8', (err, dataC) => {
            console.log(dataA, dataB, dataC)
        })
    })
})
```

> 回调地狱真正的问题不是"缩进深"，而是**错误处理的重复与流程控制的困难**：每一层都要写一遍 `if (err)`；想"并行读三个文件再汇总""任一个失败就中止""加超时"这类编排逻辑，用回调写出来几乎不可读。Promise 的价值正是把"嵌套的回调"拍平成"可组合的链式调用"，让异步流程能用同步代码的思维方式去组合。

## Promise

Promise 是 ES6 引入的异步解决方案，解决了回调地狱问题。

### 三种状态

- `pending`（进行中）
- `fulfilled`（已成功）
- `rejected`（已失败）

### 基本用法

```javascript
const readFilePromise = (filename) => {
    return new Promise((resolve, reject) => {
        fs.readFile(filename, 'utf8', (err, data) => {
            if (err) reject(err)
            else resolve(data)
        })
    })
}

// 使用
readFilePromise('a.txt')
    .then((data) => {
        console.log(data)
        return readFilePromise('b.txt')
    })
    .then((data) => {
        console.log(data)
    })
    .catch((err) => {
        console.error('读取失败', err)
    })
    .finally(() => {
        console.log('无论成功失败都执行')
    })
```

## async / await

async/await 是 Promise 的语法糖，让异步代码看起来像同步代码。

```javascript
const readFile = async () => {
    try {
        const dataA = await readFilePromise('a.txt')
        const dataB = await readFilePromise('b.txt')
        console.log(dataA, dataB)
    } catch (err) {
        console.error('读取失败', err)
    }
}

readFile()
```

### 关键点

- `await` 只能在 `async` 函数中使用
- 错误处理使用 `try / catch`
- `await` 会暂停当前函数执行，但不会阻塞主线程

### 串行与并行的决策模型

```javascript
// 串行：每个 await 都等上一个完成，总耗时是各步之和（慢）
const user = await getUser(userId)        // 假设 100ms
const profile = await getUserProfile(userId) // 假设 100ms
const config = await getConfig(q)         // 假设 500ms
// 总耗时 ≈ 100 + 100 + 500 = 700ms

// 并行：三者无依赖，同时发起，总耗时约等于最慢的那个
const [user, profile, config] = await Promise.all([
    getUser(userId),         // 100ms
    getUserProfile(userId),   // 100ms
    getConfig(q),             // 500ms
])
// 总耗时 ≈ 500ms
```

> 在服务端里这个差别很致命：一个请求往往要"取用户信息 + 读会话状态 + 查配置中心 + 调第三方 API"。前几步彼此独立，若写成串行 `await`，延迟会线性累加；用 `Promise.all` 并发，端到端延迟直接收敛到最慢那一步。

### 关键澄清：async/await 并没有把 I/O 变成阻塞

```javascript
async function handler() {
    const data = await fetchRemote() // 看起来像同步"等结果"
    return process(data)
}
```

`await` 只**暂停了当前 `async` 函数内部的执行**，让出主线程去处理别的请求。它**不会**阻塞事件循环，其他请求在此期间照常被处理。所以 async/await 只是"语法层面"让异步代码读起来像同步，底层的非阻塞 I/O 本质完全没有改变。

> 心智模型：把 `await` 理解为"在这里插了一个书签，等 Promise 好了再回来接着执行"，而不是"让整个程序停在这行"。如果只是为了让代码好看而无脑串行 `await` 一堆本可并发的任务，性能会比回调时代还差。

### 并行中的错误处理

`Promise.all` 是"一损俱损"：任何一个 reject，整体就 reject，其余已经发起的请求并不会被取消（只是结果被丢弃）。如果希望"各自的错误互相不影响"，用 `Promise.allSettled`：

```javascript
const results = await Promise.allSettled([getUser(id), getMemory(id)])
const user = results[0].status === 'fulfilled' ? results[0].value : null
```

## EventEmitter 与事件驱动

Promise/async 解决的是"一次异步操作得到结果"。但有些场景是"**一个源头不断吐出多个事件**"——比如一个 HTTP 请求体上陆续到达的数据块、一个服务端任务从"触发"到"分派子任务"再到"汇总"的全过程。这类一对多、持续性的事件流，用 `EventEmitter` 表达更自然。

```javascript
const EventEmitter = require('events')
const emitter = new EventEmitter()

// 监听事件
emitter.on('data', (chunk) => {
    console.log('收到数据块:', chunk)
})
emitter.on('end', () => {
    console.log('全部结束')
})

// 触发事件
emitter.emit('data', 'hello')
emitter.emit('data', 'world')
emitter.emit('end')
```

### 在服务端的应用思路

服务端里很多流程本身就是一条事件流：一次请求从"收到"到"转发到下游"再到"推送状态"的全过程、一个定时任务从"触发"到"分派子任务"再到"汇总"。用事件来解耦"执行逻辑"和"观测/日志/推送"非常合适：

```javascript
const task = new EventEmitter()

task.on('task:start',    ({ jobId }) => log('任务开始', jobId))
task.on('task:dispatch', ({ name, args }) => log('分派子任务', name, args))
task.on('task:progress', ({ name, result }) => log('子任务完成', name))
task.on('task:finish',   ({ summary }) => pushToClient(summary))

// 执行层只负责 emit，不关心谁在监听
async function runTask(input) {
    task.emit('task:start', { jobId: input.jobId })
    const sub = pickSubTask(input)
    task.emit('task:dispatch', { name: sub.name, args: input.args })
    const result = await sub.run(input.args)
    task.emit('task:progress', { name: sub.name, result })
    task.emit('task:finish', { summary: '...' })
}
```

> 心智模型：Promise 适合"**等一个结果**"，EventEmitter 适合"**订阅一串过程**"。Node.js 内部大量机制（HTTP 请求、Stream、进程通信）底层都是 EventEmitter，理解它就理解了 Node 事件驱动的一半。

## 面试题

### Q1: Promise 和 async/await 的关系？

async/await 是 Promise 的语法糖，底层仍然是 Promise。`async` 函数返回一个 Promise，`await` 相当于 `Promise.then()` 的简化写法。

### Q2: `Promise.all` 和 `Promise.allSettled` 的区别？

`Promise.all` 只要有一个 Promise 失败，整个就失败。`Promise.allSettled` 等所有 Promise 完成，无论成功失败，返回每个 Promise 的结果和状态。

### Q3: 写成 `await a(); await b(); await c();` 和 `await Promise.all([a(), b(), c()])` 性能差在哪？

前者是串行：每个 `await` 等上一个完成，总耗时约为三步之和；后者并发：三者同时发起，总耗时约为最慢那一步。当几步之间没有数据依赖时，应优先用 `Promise.all` 并发，这在 API 网关"取用户+读状态+调下游"这类场景里能显著压低端到端延迟。
