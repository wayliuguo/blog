## 一个完整的请求链路

当你在浏览器输入 `https://example.com` 并回车，发生了什么？

```
用户输入 URL
    ↓
DNS 解析（域名 → IP 地址）
    ↓
建立 TCP 连接（三次握手）
    ↓
请求到达服务器（后端）
    ↓
后端处理请求（读取数据库、计算等）
    ↓
返回响应（HTML / JSON / 图片等）
    ↓
浏览器渲染页面
```

后端就处在 **"服务器处理请求"** 这个环节。

上面这条链路里，数据库、网络、文件这些"等"的动作占了绝大部分时间。接下来我们把镜头拉近，专门看 Node.js 在这条链路里扮演什么角色——以及它为什么能用很少的线程，同时扛住大量这种"大部分时间在等"的请求。

## 为什么是 Node.js：一笔真实的账

在开始学之前，得先回答一个问题：**为什么这条主线选 Node.js，而不是 Java / Go / Python？**

答案不是"Node 算得快"，恰恰相反。先算一笔账。

### 一次 API 聚合请求，时间到底花在哪了

假设我们要做一个 API 聚合网关，用户请求一个"首页信息流"，后端要同时聚合多个下游服务。后端要经历这些步骤：

```
用户请求
    ↓
查询 MySQL             30ms
    ↓
调用商品推荐服务        100ms
    ↓
请求第三方支付 API     2000ms
    ↓
查询 Redis              5ms
    ↓
保存访问日志            30ms
    ↓
返回结果
```

整个请求差不多 **2.2 秒**。但关键问题是：

> **CPU 真正用来执行 JavaScript 的时间有多少？**

答案是 **只有几毫秒**。剩下 2 秒多全都在"等"：

```
等待数据库
等待网络
等待文件
等待第三方 API
等待下游服务返回
```

这就是典型的 **I/O 密集型（I/O Bound）** 服务。而 API 聚合/网关类应用天然就是这样：

```
第三方支付 API + MySQL + Redis + 商品推荐服务 + 消息队列 + 文件存储
```

这些操作绝大多数都涉及网络 I/O。**这类 API 聚合服务本质上是一个非常典型的 I/O 密集型应用。**

### 阻塞模型 vs 非阻塞模型

假设同时来了三个请求：

```
请求 A → 调用第三方 API → 等待 2000ms
请求 B → 查询 MySQL    → 等待 30ms
请求 C → 查询 Redis    → 等待 5ms
```

**如果采用阻塞模型**（来一个处理完再处理下一个）：

```
处理 A
    ↓ 等待第三方 API 2 秒（这段时间 CPU 什么都没干）
处理 B
    ↓ 等待 MySQL
处理 C
    ↓ 等待 Redis
```

等待第三方 API 的两秒里，CPU 大部分时间其实是在空转，后面的请求全被堵住。

**Node.js 的思路不是这样**：

```
处理 A
    ↓ 发起第三方 API 请求
    ↓ 不等待，立刻去处理 B
处理 B
    ↓ 发起 MySQL 查询
    ↓ 不等待，立刻去处理 C
处理 C
    ↓ 发起 Redis 查询
某个 I/O 完成 → 回来执行它的回调
```

画成图就是：

```
                ┌── 第三方 API ────────┐
                │                      ↓
                ├── MySQL ──────→ 完成 → 回调
Node.js 主线程 ──┤
（Event Loop）  ├── Redis ─→ 完成 → 回调
                │
                └── HTTP ──────→ 完成 → 回调
```

一句话概括：

> **Node.js 擅长的不是"计算得快"，而是"等待的时候不闲着"。**

一个线程就能同时照看成千上万个正在"等 I/O"的请求——因为它们大部分时间都不需要 CPU，只需要有人记得"等到了叫我一声"。而"等到了叫我一声"这件事，操作系统内核（epoll / kqueue / IOCP）就替我们做了。

### 那这条主线是怎么排出来的

既然主轴是"**非阻塞 I/O + 事件循环**"，整条运行环境主线就自然排出来了：

```
模块系统        → 代码怎么组织（CJS / ESM）
    ↓
事件循环  ★主轴 → 为什么"等的时候不闲着"能扛住高并发
    ↓
异步编程        → 怎么写代码才能"不闲着"（Callback → Promise → async/await）
    ↓
Buffer / Stream → 等到的数据长什么样、为什么大文件不能一次读完
    ↓
进程与线程      → 单线程不够用时，还有哪四种选择
```

这是本模块 7 篇的顺序依据。**每一篇都在回答上一篇留下的问题**，而不是并列的知识点。

> **心智模型**：如果你只从这条主线里带走一句话，就带走这句——**Node.js 的高并发不是靠"多线程算得快"，而是靠"单线程等得巧"**。后面所有内容（事件循环、异步、Stream、进程线程）都是这句话的展开。

### 代价是什么

任何设计都有取舍。Node.js 的代价也很明确：

| 代价 | 说明 | 后面哪一篇讲 |
|------|------|-------------|
| CPU 密集型任务会卡死整个服务 | 只有一个 JS 线程，一段复杂计算会占住它，所有请求都得等 | 进程与并发决策 |
| 同步 API 会破坏一切 | `readFileSync`、大对象 `JSON.parse` 这类操作会把"不闲着"直接打回原形 | 内置模块与文件操作 |
| 需要理解异步心智模型 | 写惯了同步代码的人容易写出"看着像并发、其实是串行"的 await | 异步编程入门 |

## Node.js 是什么

Node.js **不是**一门新的编程语言，而是 **JavaScript 的运行环境**。

```
JavaScript 原本只在浏览器中运行
       ↓
Node.js 基于 Chrome V8 引擎，让 JS 可以跑在服务器上
```

- 语言：JavaScript / TypeScript
- 运行环境：Node.js
- 底层引擎：V8（Chrome 浏览器用的那个）

## Node.js 能做什么

| 用途 | 说明 | 例子 |
|------|------|------|
| Web 服务器 | 处理 HTTP 请求，提供 API | Express、NestJS |
| 命令行工具 | 编写 CLI 工具 | Webpack、create-react-app |
| 桌面应用 | 用 JS 写桌面软件 | VS Code（基于 Electron） |
| 工具链 | 前端构建工具 | Vite、Webpack |

## 第一个 Node.js 程序

创建一个文件 `hello.js`：

```javascript
console.log('Hello, Node.js!')
```

在终端中运行：

```bash
node hello.js
# 输出：Hello, Node.js!
```

### 创建一个简单的 HTTP 服务器

```javascript
const http = require('http')

const server = http.createServer((req, res) => {
    res.end('Hello World')
})

server.listen(3000, () => {
    console.log('Server running at http://localhost:3000')
})
```

运行后，在浏览器打开 `http://localhost:3000`，你会看到 `Hello World`。

> 先不用管 `req`、`res` 是什么——这个五行的服务器背后藏着网络编程、事件循环、流式 I/O 三件大事。它们分别在模块一和模块二里展开。

## 常见误区

### 误区一："Node.js 是单线程的"

严格说，只有 **执行 JavaScript 的那条主线程**是单线程。进程内部，libuv 维护着一个**线程池**（默认 4 个线程），专门用来处理那些操作系统没有提供真正异步接口的操作：文件 I/O、DNS 解析、`crypto` 加密计算等；另外，定时器、网络 I/O 由事件循环和内核协作完成。所以更准确的说法是：Node.js 是"单线程执行 JS + 多线程处理底层 I/O"。

> **心智模型**：把 Node.js 想成"一个前台 + 一支后台团队"。前台（主线程）一次只接待一位客人，但所有耗时的跑腿活都交给后台团队（libuv 线程池与内核），前台永远不为某件事干等。

### 误区二："Node.js 什么都适合"

错。Node.js 的强项是"等 I/O 的时候不闲着"，弱项是"算得重"。如果业务逻辑里塞满 CPU 密集型计算——大数运算、图像/视频处理、复杂加密压缩、超大对象 `JSON.parse`——主线程会被占住，事件循环转不动，所有其他请求一起跟着卡。这类任务应该拆分到 Worker Thread 或子进程（见《进程线程与优雅退出》）。

> **心智模型**：Node.js 像一位高效的前台接待，擅长同时照看很多"在等"的客人；但如果你让他去搬一整天箱子（CPU 密集），前台就没人了，门口全挤住。

### 误区三："Node.js 就是后端"

Node.js 是**运行环境**，不是后端框架。它提供的是 JS 运行时、事件循环、系统级 API（文件、网络、进程）。真正定义"后端"的是框架——Express、Koa、NestJS 这些才负责路由、中间件、依赖注入、控制器等后端结构。没有框架也能写后端（用内置 `http` 模块），但那只是"裸 HTTP 服务"，谈不上一套后端架构。

> **心智模型**：Node.js 是厨房（运行环境），Express/NestJS 是菜谱和分工流程（后端框架）。有厨房不等于有餐厅，有运行环境也不等于有后端架构。

## 面试题

### Q1: Node.js 和 JavaScript 是什么关系？

Node.js 不是一门语言，而是 JavaScript 的运行环境。JavaScript 是语言本身，Node.js 基于 Chrome 的 V8 引擎，为 JS 提供了文件系统、网络、进程等系统级 API，让 JS 能脱离浏览器在服务端运行。

### Q2: 为什么 API 聚合/网关类服务适合用 Node.js？

因为这类服务是典型的 I/O 密集型服务：一次请求里 CPU 真正执行 JS 的时间可能只有几毫秒，其余 2 秒多都在等数据库、缓存、第三方 API、消息队列返回。Node.js 的非阻塞 I/O + 事件循环让单个线程能同时照看成千上万个"正在等 I/O"的请求，等待期间 CPU 不会空转在某个请求上。

### Q3: Node.js 不适合什么场景？

CPU 密集型场景。因为执行 JS 的只有一个主线程，一段复杂计算（大数运算、图像处理、加密压缩）会把事件循环占住，期间所有请求都被阻塞。这类任务应该交给 Worker Thread 或子进程（见《进程线程与优雅退出》）。
