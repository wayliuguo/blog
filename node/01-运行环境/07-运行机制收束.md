## 一张知识关系总图

模块一 6 篇不是并列的，而是一条有依赖关系的链——每一篇都是上一篇留下的问题的答案：

```
模块系统（代码怎么组织：CommonJS / ESM / npm）
        │
        │  先把"文件能被加载、被引用"解决掉，后面才能跑
        ▼
   Event Loop ★主轴（为什么单线程能扛并发）
   libuv 六阶段 · 宏任务/微任务 · nextTick
        │
        │  总线被占住就会卡，于是怎么写？
        ├────────► 异步编程与事件驱动（Callback → Promise → async/await）
        │                    │
        │                    │  异步"搬运"的到底是什么？
        │                    ▼
        └────────► Buffer / Stream（字节与背压，异步 I/O 的数据形态）
                             │
                             │  I/O 形态清楚了，但单线程算力到顶了
                             ▼
                     进程 / 线程（cluster / worker_threads / child_process / process）
                             │
                             │  扩了进程线程，出错了怎么安全收场？
                             ▼
                     错误兜底与优雅退出（错误类型 · 兜底 · SIGTERM 优雅关闭）
```

为什么是这个顺序：

- **模块系统**解决"代码怎么组织"——文件不能互相引用，后面什么都跑不起来。
- **事件循环**解决"为什么不会卡"——它是整条链的主轴，理解它才懂异步为什么有效。
- **异步编程**解决"怎么写不卡"——在事件循环之上，用 Callback / Promise / async-await 把代码写顺。
- **Buffer / Stream**解决"数据长什么样"——异步搬运的不是"变量"而是字节流；大文件、上传下载、实时推送、媒体处理都绕不开它。
- **进程 / 线程**解决"单线程不够用怎么办"——I/O 模型走到头，CPU 密集或要故障隔离时，从进程/线程层面再扩。
- **错误兜底与优雅退出**解决"出错了怎么安全收场"——只要起了多进程、开了连接，就必然要处理崩溃、未清理句柄与重启丢请求。

> **心智模型**：把模块一想象成"修一条高速公路"。模块系统是路基（路得先连起来），事件循环是红绿灯（车怎么不堵），异步编程是行车规则（车按规则跑），Buffer/Stream 是车里拉的货（字节流与背压），进程/线程是再开几条辅路（单条路堵了就分流），错误兜底与优雅退出是收费站和应急车道（出事能安全疏散）。

## 决策模型：见 X → 想 Y

拿到需求或遇到性能问题，先别急着写代码，用这张表做"条件反射"：

| 见到什么现象 / 需求 | 该想到什么 | 一句话理由 |
|------|------|------|
| HTTP 请求、查数据库、调外部 API | **Event Loop（异步 I/O）** | 别用同步 API（`fs.readFileSync`、`execSync`）阻塞事件循环 |
| 大文件读写、文件上传下载、流式输出 | **Stream + 背压** | 别用 `readFile` 一次性读进内存，用 `createReadStream` + `pipe` 边读边传 |
| 压缩、加密、大 JSON 解析、复杂计算 | **Worker Thread** | CPU 密集会占住事件循环，丢到 worker 才不卡 |
| 调 ffmpeg、python 脚本、系统命令 | **Child Process** | 这是别的程序，用 `spawn` / `execFile` 起进程去跑 |
| "用不满多核""要故障隔离" | **多进程（cluster / PM2）** | 一个 Node 进程只用一个核，cluster 才能铺满多核，且崩一个不影响其他 |
| "进程不退出" | **未清理的句柄 + 优雅关闭** | 还有 server / timer / 连接没关，`SIGTERM` 时要主动 `close` 并 `process.exit` |
| "响应顺序不符合预期" | **微任务检查点（nextTick vs Promise）** | `nextTick` 队列在每阶段之间清空，Promise 的 `then` 在每个阶段之后，顺序差在这 |
| "CPU 打满但 QPS 很低" | **同步阻塞操作占住事件循环** | 主线程被长同步任务卡死，I/O 回调全在排队，并发能力归零 |
| "服务重启丢请求" | **SIGTERM 优雅关闭** | 收到信号先停收新请求、等存量请求跑完再 `close`，否则连接被硬切断 |
| "内存一路涨最后 OOM" | **背压没做 / 事件监听器泄漏** | 上游猛灌下游慢没暂停，或 `on` 了不 `off`，内存只增不减 |

> **决策模型**：现象是表相，主轴是事件循环。任何"卡""慢""顺序乱""内存涨"的问题，先问一句"是不是事件循环被占住了 / 数据流有没有背压"，再决定是换异步、上 Stream、还是丢给线程/进程。

把这张表当成肌肉记忆：下次评审方案或线上排障，先翻它而不是先翻文档。

## 抽象栈：模块一在 Node 后端体系处在哪一层

模块一讲的都是"进程内"的事。把它放进一个真实的 Node 后端请求链路，你能看清每部分属于哪一篇：

```
你的业务代码
框架（Express / Koa / NestJS）      ← 模块三 / 模块五
node:http（报文解析）                ← 模块二
Event Loop + 微任务                  ← 03 / 04
libuv（线程池默认 4）                ← 03
内核（epoll / kqueue / IOCP）        ← 03（模块二从网络视角再用一次）
Socket（本质是 Duplex Stream）        ← 05 / 模块二
TCP（可靠字节流，会粘包）             ← 模块二
HTTP / HTTPS / WebSocket / SSE       ← 模块二
```

补充两条横向归属：

- **Buffer / Stream ← 05**：贯穿上图——Socket 是 Duplex Stream，HTTP body、文件、媒体流都是它在搬。
- **进程与线程 ← 06**：横切在最上层，决定一个 Node 实例是单进程还是多进程/多线程地跑上面这一整条栈。

记住这条栈，排障时就能"顺藤摸瓜"：用户说接口慢，先想是业务代码慢（模块三/五），还是报文解析/序列化慢（模块二/05 的 Buffer），还是事件循环被占住（03/04），还是网络层卡（模块二/TCP）。

## 常见误区清单

前 6 篇散落的坑，这里集中破除一次：

**1. "Node.js 是单线程的"**
只有 JS 执行是单线程的（主线程跑你的代码）。进程内部还有 libuv 线程池在后台跑 `fs` / `dns` / `crypto` / `zlib`，以及 OS 级别的网络 I/O 线程。说"单线程"是特指"JS 执行单线程"。

**2. "所有异步操作都在线程池里跑"**
错。网络 I/O（HTTP、TCP、数据库驱动大多走 libuv 的 `epoll` / `kqueue` / IOCP）由操作系统接管，不进线程池。只有 `fs`、`dns`（部分）、`crypto`、`zlib` 这类才进 libuv 线程池。

**3. "await 会阻塞事件循环"**
`await` 只暂停**当前 async 函数**的后续执行，把后面代码挂到微任务队列；主线程立刻去处理别的回调。它从不阻塞事件循环，阻塞的是"这个函数自己的后半段"。

**4. "worker_threads 就是 libuv 线程池"**
两者不是一回事。`worker_threads` 是你主动 `new Worker()` 创建、可共享 `SharedArrayBuffer` 的 JS 线程；libuv 线程池是 Node 内部自动维护、你无法直接控制的系统线程。前者给"你"用，后者给"Node 内部"用。

**5. "process.nextTick 用得越多越快"**
`nextTick` 队列在每个阶段之间被**清空**（直到为空），递归调用 `nextTick` 会饿死事件循环，导致 timers / I/O 回调永远得不到执行。需要"让出执行权、下一轮再继续"应该用 `setImmediate`。

**6. "多开进程就能变快"**
只对 CPU 密集型或要故障隔离的场景成立。I/O 密集型瓶颈在"等待"，事件循环本就能在等待时处理别的请求，多开进程只是多占内存，解决不了等待问题。

## 面试题

### Q1: 一个 Node 服务 CPU 打满但 QPS 很低，你怎么定位？

先确认瓶颈在"算"不在"等"：用 `perf_hooks` 的 `eventLoopUtilization` 或 `process.hrtime` 看事件循环是否被长任务占住；`top`/`htop` 看单核跑满还是多核均匀。定位到是同步阻塞（如 `readFileSync`、大 JSON 同步解析、死循环式计算）就搬到 `worker_threads`；定位到是单进程只用单核就上 `cluster`。关键判断：**CPU 高 + QPS 低 = 主线程被占住，不是 I/O 在等**。

### Q2: 什么时候用 cluster，什么时候用 worker_threads？

看"要不要共享内存、是不是同类 JS 任务"。`worker_threads` 适合在**同一个进程内**把 CPU 密集的 JS 任务（压缩、加密、大 JSON 解析） offload 出去，且可通过 `SharedArrayBuffer` 共享内存；`cluster` 适合**横向铺满多核 + 故障隔离**，每个进程是独立实例、内存不共享，一个崩了不影响其他。简单记：要"分流计算且共享状态"用线程，要"多实例扛量与隔离"用进程。

### Q3: 处理一个 2GB 的文件上传并转存，为什么不能用 `fs.readFile`？正确的做法是什么？

`readFile` 会把整个文件一次性读进内存，2GB 直接撑爆内存还可能 OOM。正确做法是用 `fs.createReadStream` 创建可读流，配合 `pipe` 流向 `fs.createWriteStream` 或可写目标；Stream 自带背压（backpressure），当下游处理慢于上游时自动暂停读取，避免内存堆积。

### Q4: `process.nextTick` 和 `setImmediate` 有什么区别？什么场景用哪个？

`nextTick` 的回调在**当前操作完成后、事件循环下一阶段前**立即执行，且会一直清空队列（可能饿死循环）；`setImmediate` 的回调在**当前 poll 阶段之后、check 阶段**执行，每轮事件循环最多跑一批。适合：`nextTick` 用于"在当前栈结束后立刻做收尾/错误抛出"；需要让出执行权、避免饿死循环时用 `setImmediate`。

### Q5: 多开进程就一定能提升性能吗？什么场景下多开进程没用？

不一定。I/O 密集型瓶颈在"等待"，单进程的事件循环本就能在等待时处理别的请求，多开进程只是多占内存、解决不了等待问题。只有 CPU 密集（单进程只用单核跑满）或需要故障隔离时，多进程（cluster / PM2）才有意义。选型前先分清瓶颈是"算"还是"等"。

## 交接：模块一结束，进入模块二

进程内的 I/O 模型到这就讲完了——事件循环为什么能扛并发、异步怎么写、字节流怎么搬、单线程不够时怎么用进程线程分流，全都串起来了。但有一个问题我们一直没回答：**这些 I/O 到底是从哪来的？**

答案是网络。HTTP 请求、数据库调用、WebSocket 推送、实时消息，本质都是"通过网卡和另一台机器交换字节"。I/O 模型是"怎么高效地等和搬"，而数据是怎么在机器之间流动、TCP 和 HTTP 是什么、WebSocket 怎么做到实时——这就是模块二要解决的。
