## 进程与线程的区别

理解 Node 的并发模型，先分清两个概念：

| 维度 | 进程（Process） | 线程（Thread） |
|------|----------------|----------------|
| 定义 | 一个**运行中的程序实例** | 进程内的一条**执行路径** |
| 内存 | 各自独立，默认不共享 | 同一进程内的线程**共享内存** |
| 开销 | 创建/切换重（要拷贝资源） | 创建/切换轻 |
| 崩溃影响 | 一个进程崩了不影响别的进程 | 一个线程崩了可能拖垮整个进程 |
| Node 里 | 每个 `node app.js` 是一个进程 | libuv 线程池、worker_threads 是线程 |

> 心智模型：进程像"一栋楼"，线程像"楼里的房间"。一栋楼（进程）倒了，别的楼没事；但楼里一个房间（线程）着火，整栋楼都可能受影响——所以多线程共享内存既快又有"互相踩踏"的风险。Node 主线程执行 JS 是单线程的，但一个 Node **进程**内部还藏着 libuv 的线程池等"房间"。

## process 对象

`process` 是一个全局对象，提供当前 Node.js 进程的信息和控制。

### 常用属性

```javascript
// 进程信息
console.log(process.pid)          // 进程 ID
console.log(process.title)        // 进程标题
console.log(process.arch)         // 架构: 'x64' | 'arm64'
console.log(process.platform)     // 平台: 'win32' | 'darwin' | 'linux'
console.log(process.version)      // Node.js 版本号

// 内存使用
console.log(process.memoryUsage())
// { rss: 30MB, heapTotal: 10MB, heapUsed: 5MB, external: 1MB }

// 运行时间
console.log(process.uptime())     // 进程运行了多少秒
```

### 命令行参数

```javascript
// 运行: node app.js --port=3000 --env=production
console.log(process.argv)
// [
//   'node.exe 路径',
//   'app.js 路径',
//   '--port=3000',
//   '--env=production'
// ]

// 推荐使用 yargs 或 commander 解析参数
```

### 工作目录

```javascript
console.log(process.cwd())    // 当前工作目录
process.chdir('/tmp')         // 切换工作目录
```

## exit 与信号

```javascript
// 正常退出
process.exit(0)   // 0 表示成功
process.exit(1)   // 非 0 表示失败

// 监听退出事件
process.on('exit', (code) => {
    console.log(`进程退出，退出码: ${code}`)
    // 注意：exit 事件中只能执行同步操作
})

// 监听 SIGINT 信号（Ctrl+C）
process.on('SIGINT', () => {
    console.log('收到 Ctrl+C')
    process.exit(0)
})

// 优雅关闭
process.on('SIGTERM', () => {
    console.log('收到关闭信号，开始清理...')
    // 关闭数据库连接、保存状态等
    server.close(() => {
        process.exit(0)
    })
})
```

## os 模块

`os` 模块提供操作系统相关的信息。

```javascript
const os = require('os')

// 系统信息
console.log(os.hostname())      // 主机名
console.log(os.type())          // 操作系统类型: 'Windows_NT' | 'Linux' | 'Darwin'
console.log(os.release())       // 操作系统版本号
console.log(os.uptime())        // 系统运行时间（秒）

// CPU 信息
console.log(os.cpus())          // CPU 核心信息数组
console.log(os.cpus().length)   // CPU 核心数（用于 PM2 设置进程数）

// 内存信息
console.log(os.totalmem())      // 总内存（字节）
console.log(os.freemem())       // 空闲内存（字节）

// 网络信息
console.log(os.networkInterfaces())  // 网络接口信息
```

## child_process：在 Node 里调用外部程序

Node 不是万能的——调用 `ffmpeg` 转码、`python` 脚本、系统命令时，需要 `child_process` 模块派生子进程。

| API | 特点 | 适用场景 |
|-----|------|----------|
| `spawn` | 返回 `ChildProcess`，`stdout/stderr` 是**流**；不开 shell | 输出量大、要流式处理、长时间运行的命令 |
| `exec` | 缓冲**整个**输出，回调里一次性拿到字符串；**开 shell** | 简单命令、要用管道/通配符等 shell 特性、输出较小 |
| `execFile` | 同 `exec` 但不开 shell，直接执行文件 | 执行一个已知二进制、不需要 shell、更省更安全 |
| `fork` | 专门跑另一个 Node 脚本，并建立 **IPC 通信通道** | 父子进程间用 `send`/`on('message')` 互传数据 |

```javascript
const { spawn, exec, execFile, fork } = require('child_process')

// spawn：流式读大输出
const ls = spawn('ls', ['-la', '/usr'])
ls.stdout.on('data', (chunk) => console.log(chunk.toString()))

// exec：简单拿结果（注意 shell 注入风险，别拼接用户输入）
exec('ls -la | grep node', (err, stdout) => console.log(stdout))

// fork：和子 Node 程序通信
const child = fork('./worker.js')
child.send({ task: 'compute', n: 1000 })
child.on('message', (msg) => console.log('子进程返回:', msg))
```

> 决策模型：要**流式 / 大数据 / 长运行** → `spawn`；要**顺手用 shell 拼命令且输出小** → `exec`；要**跑文件不想要 shell 开销** → `execFile`；要**跑 Node 子程序并通信** → `fork`。

## 多进程与多核：cluster

单进程的 Node 用不满多核 CPU。`cluster` 模块让一个 **Primary（主）进程** fork 出多个 **Worker（工作）进程**，它们共享同一个监听端口，由 OS / Primary 做负载均衡分发请求。

```javascript
const cluster = require('cluster')
const os = require('os')
const http = require('http')

if (cluster.isPrimary) {
    // 按 CPU 核数拉起 worker
    const cpus = os.cpus().length
    for (let i = 0; i < cpus; i++) cluster.fork()
    cluster.on('exit', (worker) => {
        console.log(`worker ${worker.process.pid} 挂了，重启一个`)
        cluster.fork() // 故障自愈：某个 worker 崩了自动补位
    })
} else {
    http.createServer((req, res) => res.end('hi')).listen(3000)
}
```

> 官方建议：cluster 的价值在于**进程级隔离**（一个 worker 崩了不影响其他）和**多核部署**。如果只是想并行做 CPU 计算（不需要独立进程、要共享内存），Node 官方更推荐下面要讲的 `worker_threads`——它比多进程更轻量。

## worker_threads：JS 层面的多线程

`worker_threads` 让你在**同一个进程内**开多条 JS 执行线程，适合把 CPU 密集型任务（加密、压缩、大量计算）从主线程挪走，避免卡死事件循环。

```javascript
const { Worker } = require('worker_threads')

const worker = new Worker(`
    const { parentPort } = require('worker_threads')
    let sum = 0
    for (let i = 0; i < 1e9; i++) sum += i
    parentPort.postMessage(sum) // 把结果回传主线程
`, { eval: true })

worker.on('message', (result) => console.log('计算结果:', result))
```

### 关键易混点：libuv 线程池 ≠ worker_threads

| 对比 | libuv Thread Pool | worker_threads |
|------|-------------------|----------------|
| 由谁创建 | Node **内部自动**维护（默认 4 个） | 你用 `new Worker()` **主动**创建 |
| 干什么 | 替你跑 `fs`/`dns`/`crypto`/`zlib` 等底层阻塞操作 | 跑你写的 JS 计算逻辑 |
| 能共享内存吗 | 不能，是 C++ 侧的工作线程 | 能，通过 `SharedArrayBuffer` |

> 一句话：libuv 线程池是"Node 帮你干底层脏活"的线程，你感知不到；worker_threads 是"你自己要开一条 JS 线程算东西"的线程。两者完全不同的东西，别混为一谈。

## 决策模型：该用哪种并发方式

遇到性能 / 架构问题，先判断属于哪一类，再选方案：

| 场景 | 推荐方案 | 理由 |
|------|----------|------|
| I/O Bound（网络请求、文件读写） | Event Loop / 异步 I/O | 单线程非阻塞就够，无需多线程 |
| CPU Bound（计算密集、加解密、压缩） | Worker Thread | 把重计算挪出主线程，不卡事件循环 |
| 执行外部程序（ffmpeg / python 脚本） | Child Process | 必须派生独立进程跑别的程序 |
| 多核部署 / 故障隔离 | 多进程（cluster / PM2）+ 负载均衡 | 吃满多核、单点崩溃不影响全局 |

### 运行时错误

// 代码能运行，但执行时出错

// 代码能运行，但结果不对

## 错误处理与兜底

### 同步代码：try/catch

```javascript
try {
    const data = JSON.parse(userInput)
    console.log(data.name)
} catch (err) {
    console.error('JSON 解析失败:', err.message)
}
```

### 异步代码：Promise.catch

```javascript
// 不好的做法
const data = await riskyFunction()  // 可能抛异常，没处理

// 好的做法
try {
    const data = await riskyFunction()
} catch (err) {
    console.error('操作失败:', err)
}
```

### 全局未捕获异常

```javascript
// 处理未捕获的 Promise 异常
process.on('unhandledRejection', (reason, promise) => {
    console.error('未处理的 Promise 拒绝:', reason)
})

// 处理未捕获的同步异常
process.on('uncaughtException', (err) => {
    console.error('未捕获的异常:', err)
    // 记录日志后优雅退出
    process.exit(1)
})
```

> 注意：`uncaughtException` 不推荐用于恢复程序运行，它只是让你在崩溃前做清理工作。

### 两个"兜底"钩子的区别

| 钩子 | 触发场景 | 典型动作 |
|------|----------|----------|
| `uncaughtException` | 同步代码里抛出的异常没人 catch | 记日志、上报监控，然后**尽快退出重启** |
| `unhandledRejection` | Promise reject 了但没有 `.catch` / `await try` 接住 | 同上；Node 15+ 之后未处理的 rejection 也会让进程退出 |

> 决策模型：**不要**在这两个钩子里"就地修复并继续跑"——状态可能已经损坏，强行续命会引入更难查的 bug。正确做法是在钩子里做"最后一程"：把错误、堆栈、上下文写进日志/告警，然后调用 `process.exit(1)`（配合进程管理器如 PM2 / K8s 自动拉起）。同时，更治本的方式是在**每个异步入口**（HTTP 路由、定时任务、消息消费）外层包一层 try/catch，把错误变成可观测、可返回的响应，而不是让它漏到进程级兜底。

## 优雅关闭（Graceful Shutdown）

收到 `SIGTERM`（容器编排如 K8s 发）或 `SIGINT`（Ctrl+C）时，**不要立刻 `process.exit()`**——那样会直接掐断正在处理的请求、来不及落库。正确顺序是：

1. **停止接收新请求**（`server.close()`，已有连接继续处理）
2. **等待在途请求结束**（跟踪活跃请求数，归零或超时后再走）
3. **关闭依赖**（数据库 / Redis / MQ 连接）
4. **退出**

```javascript
const http = require('http')
const server = http.createServer(app)
server.listen(3000)

let activeRequests = 0
server.on('request', (req, res) => {
    activeRequests++
    res.on('finish', () => { activeRequests-- })
})

async function shutdown(signal) {
    console.log(`收到 ${signal}，开始优雅关闭`)

    // 1. 不再接受新连接
    server.close()

    // 2. 等待在途请求结束（带超时兜底）
    const deadline = Date.now() + 10000
    while (activeRequests > 0 && Date.now() < deadline) {
        await new Promise((r) => setTimeout(r, 100))
    }

    // 3. 关闭外部依赖
    await db.end()        // 关闭数据库连接
    await redis.quit()    // 关闭 Redis
    // await mq.close()   // 关闭消息队列

    // 4. 干净退出
    process.exit(0)
}

process.on('SIGTERM', () => shutdown('SIGTERM'))
process.on('SIGINT', () => shutdown('SIGINT'))
```

> 心智模型：优雅关闭的本质是"**先拒绝新活、把手上的活干完、再收摊**"。生产环境缺少这一步，会导致滚动发布时一部分用户请求被硬生生断掉。结合上文 `uncaughtException` 的处理，二者共同构成服务的"体面退场"。

## 面试题

### Q1: `process.env` 的作用是什么？

`process.env` 是一个包含所有环境变量的对象，用于在 Node.js 应用中读取环境配置。常用于区分开发/生产环境、存储敏感信息（数据库密码、API Key 等）。

### Q2: 如何优雅地关闭 Node.js 应用？

收到 `SIGTERM`/`SIGINT` 后不要立刻 `process.exit()`。标准顺序是：先 `server.close()` 停止接收新请求 → 等待在途请求结束（跟踪活跃请求数或加超时）→ 关闭数据库 / Redis / MQ 等依赖 → 再退出。这样滚动发布时不会硬断开正在处理的请求。

### Q3: `worker_threads` 和 `cluster` 怎么选？libuv 线程池和它们有什么关系？

`cluster` 开**多个进程**（每进程一个主线程 + 自己的 libuv 池），适合多核部署和进程级故障隔离；`worker_threads` 在**一个进程内**开多条 JS 线程，适合进程内并行 CPU 计算、且能共享内存，比多进程轻量。二者都不是"Node 内部的 libuv 线程池"——libuv 线程池是 Node 自动维护、专门跑 `fs`/`dns`/`crypto`/`zlib` 底层操作的隐藏线程，开发者感知不到，也控制不了。
