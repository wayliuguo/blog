# 事件循环：六个阶段与微任务

## Node.js 真的是单线程吗？

"Node.js 是单线程的"这句话严格来说不准确。准确表述是：**默认情况下，Node.js 用一个主线程执行你的 JavaScript，但整个 Node.js 进程本身不止一个线程。**

一次 `fs.readFile` 调用，要穿过至少四层角色：

```
Application (你写的 JS 代码)
        │
        ▼
     ┌──────────────┐
     │   V8 引擎     │  解析 / JIT 编译 / 执行 JS / GC
     └──────┬───────┘
            │  Node.js Bindings（JS 调用桥接到底层 C/C++）
            ▼
     ┌──────────────┐
     │    libuv      │  Event Loop（事件循环）
     │              │  Thread Pool（线程池）
     └──────┬───────┘
            │
            ▼
     Operating System
     epoll / kqueue / IOCP（I/O 事件通知）
```

- **V8**：只负责执行 JavaScript，它不知道 `fs.readFile` 是什么。
- **Node.js**：在 V8 之外补齐服务器端能力（`fs` / `http` / `net` / `crypto` / `stream` / `child_process` / `worker_threads` …）。
- **libuv**：Node.js 异步能力的核心基础设施，负责事件循环、异步 I/O、网络 I/O、Timer、线程池，以及跨平台系统调用封装。
- **操作系统**：真正执行底层 I/O。Linux 用 `epoll`，macOS / BSD 用 `kqueue`，Windows 用 `IOCP`。

所以 Node.js 的高并发能力，不是因为 JavaScript 执行得特别快，而是因为它**尽量不让主线程去等 I/O**。

## 事件循环到底解决什么问题？

假设服务器收到一个请求，需要查询数据库（可能要等 100ms）：

> 示意片段（无配套脚本）

```js
app.get('/user', async (req, res) => {
  const user = await queryDatabase(); // 可能等 100ms
  res.json(user);
});
```

如果采用**同步（阻塞）模型**，一个请求在等数据库时，整个线程都在空转，后面的请求只能排队：

```
请求 A
 │
 ├── 发起数据库查询
 │
 │   等待 100ms ……
 │
 └── 返回结果

请求 B
     只能干等
```

Node.js 的做法是：发起请求后**不等待**，转去处理下一个请求，结果回来时再执行回调：

```
请求 A
 │
 ├── 发起数据库请求
 └── 不等待
          │
          ▼
      处理请求 B
          │
          ▼
      处理请求 C
          │
          ▼
数据库结果返回
          │
          ▼
执行请求 A 的回调
```

## 一个贯穿全章的例子：六个阶段与两条微任务队列

前面两节在回答"为什么需要事件循环"。这一节先不看原理，直接跑一段代码——它用四类来源不同的回调，把事件循环的几个主要阶段依次点亮，顺带把两条微任务队列也牵出来。本章后面每一节，都会回头解释下面输出里的某一行。下面这段**逐字摘自配套脚本**（它就是本篇所有"阶段观测"的唯一事实来源，复制出来即可直接 `npm run 03phases`）。

> 摘自 `./code/node-basics/src/03-eventloop-phases.js`（运行：`npm run 03phases`）

```js
const fs = require('node:fs')
const net = require('node:net')

console.log('==== 同步代码开始 ====')

// 观测点 1：timers 阶段的宏任务
setTimeout(() => {
    console.log('[timers] setTimeout callback')
    // 回调里注册的微任务，会在本回调返回时立刻被清空 —— 这就是微任务检查点
    Promise.resolve().then(() => {
        console.log('[微任务] setTimeout promise then')
    })
}, 0)

// 观测点 2：poll 阶段 —— fs.readFile 的 I/O 回调在 poll 阶段执行
fs.readFile(__filename, () => {
    console.log('[poll] fs.readFile I/O callback')

    // 此刻正处在 poll 阶段内部：
    //   setImmediate 会在本轮的 check 阶段执行（poll 的下一步就是 check，所以很近）
    //   setTimeout 虽然延时 0，但要等到下一轮的 timers 阶段
    setImmediate(() => {
        console.log('[check] readFile 里的 setImmediate')
    })
    setTimeout(() => {
        console.log('[timers] readFile 里的 setTimeout')
    }, 0)

    Promise.resolve().then(() => {
        console.log('[微任务] readFile promise then')
    })
})

// 观测点 3：check 阶段 —— setImmediate 的回调
setImmediate(() => {
    console.log('[check] 顶层 setImmediate')
})

// 观测点 4：close callbacks 阶段 —— 真实 socket 被销毁后的 'close' 事件
const server = net.createServer()
server.listen(0, () => {
    const client = net.createConnection(server.address().port, () => {
        // 连上之后主动销毁这条真实连接，让底层 handle 走一次 uv_close
        client.destroy()
    })
    client.on('close', () => {
        console.log('[close callbacks] client socket close')
        server.close()
    })
})

// 对照实验：无连接的服务端，close() 触发的 'close' 事件并不在 close callbacks 阶段
const idle = net.createServer().listen(0)
idle.on('listening', () => idle.close())
idle.on('close', () => {
    console.log('[对照] 无连接 server 的 close（由 nextTick 派发，不是 close callbacks 阶段）')
})

// 两条微任务队列：nextTick 优先级高于 Promise
process.nextTick(() => {
    console.log('[nextTick] 顶层 nextTick')
})
Promise.resolve().then(() => {
    console.log('[微任务] 顶层 promise then')
})

console.log('==== 同步代码结束 ====')
```

实测输出（`npm run 03phases`）：

```
==== 同步代码开始 ====
==== 同步代码结束 ====
[nextTick] 顶层 nextTick
[对照] 无连接 server 的 close（由 nextTick 派发，不是 close callbacks 阶段）
[微任务] 顶层 promise then
[timers] setTimeout callback
[微任务] setTimeout promise then
[check] 顶层 setImmediate
[close callbacks] client socket close
[poll] fs.readFile I/O callback
[微任务] readFile promise then
[check] readFile 里的 setImmediate
[timers] readFile 里的 setTimeout
```

> 注意：`[close callbacks] client socket close` 与 `[poll] fs.readFile I/O callback` 的相对顺序**并不固定**——前者依赖真实 socket 销毁的时机、后者依赖文件读取完成的时机，两者几乎同时就绪时谁先谁后随计时抖动（本机连跑 10 次约 9 次是 close 在前、1 次是 poll 在前）。其余 10 行顺序稳定。所以下面归位表按"它属于哪个阶段"归类，而非承诺绝对先后。

把每一行按"它属于哪里"重新归一次位，整章的骨架就出来了：

| 输出行 | 属于哪里 | 本章哪一节解释它 |
| --- | --- | --- |
| `==== 同步代码开始/结束 ====` | 同步代码，Call Stack | 两条微任务队列：nextTick 与 Promise |
| `[nextTick] 顶层 nextTick` | nextTickQueue（不属于任何阶段） | 两条微任务队列：nextTick 与 Promise |
| `[对照] 无连接 server 的 close` | 同样是 nextTickQueue | close callbacks：为什么对照里这一行不在这个阶段 |
| `[微任务] 顶层 promise then` | Promise 微任务队列 | 两条微任务队列：nextTick 与 Promise |
| `[timers] setTimeout callback` | timers 阶段 | timers 阶段：setTimeout 是"最小等待时间" |
| `[微任务] setTimeout promise then` | 回调返回处的微任务检查点 | 微任务检查点：不是一轮一次 |
| `[check] 顶层 setImmediate` | check 阶段 | check 阶段与 setImmediate |
| `[poll] fs.readFile I/O callback` | poll 阶段 | poll 阶段：事件循环的核心 |
| `[微任务] readFile promise then` | 回调返回处的微任务检查点 | 微任务检查点：不是一轮一次 |
| `[check] readFile 里的 setImmediate` | check 阶段（紧跟 poll） | check 阶段与 setImmediate |
| `[timers] readFile 里的 setTimeout` | 下一轮的 timers 阶段 | check 阶段与 setImmediate |
| `[close callbacks] client socket close` | close callbacks 阶段 | close callbacks：为什么对照里这一行不在这个阶段 |

记住这张表里的三处"反直觉"，本章就抓住了重点：

1. 同步代码全部跑完，才轮到任何异步回调；
2. 微任务（nextTick、Promise）不在六个阶段里，它们插在每个回调返回的那一刻；
3. 同样是 `close` 事件，真实 socket 销毁落在 close callbacks 阶段，无连接的服务端却由 `process.nextTick` 派发。

## libuv 的六个阶段

Node.js 的事件循环不是"一个宏任务队列 + 一个微任务队列"轮转那么简单（那是浏览器视角）。它是一串**有固定顺序的阶段（Phase）**，每个阶段是一个回调队列，按固定次序轮转：

```
┌─────────────────────────┐
│         timers          │  setTimeout / setInterval
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│    pending callbacks    │  推迟到下一轮的系统回调
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│      idle / prepare     │  Node 内部使用
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│          poll           │  I/O 事件处理核心
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│         check           │  setImmediate
└────────────┬────────────┘
             │
             ▼
┌─────────────────────────┐
│     close callbacks     │  资源关闭回调
└────────────┬────────────┘
             │
             └───────────► 下一轮
```

每进入一个阶段，libuv 会把这个阶段的回调队列一次性执行完（或执行到系统上限），然后离开、进入下一阶段。

## timers 阶段：setTimeout 是"最小等待时间"

`timers` 阶段处理 `setTimeout` 和 `setInterval` 中**已到期**的回调。

### 为什么 setTimeout 是"最小等待时间"？

很多人误以为 `setTimeout(fn, 1000)` 表示"1000ms 后一定执行"。实际上 1000ms 表示：**至少经过 1000ms 后，这个 callback 才"有资格"执行**——它能不能真的执行，还要等主线程空闲。

看一个反直觉的例子：

> 示意片段（无配套脚本）

```js
setTimeout(() => {
  console.log('timeout');
}, 1000);

const start = Date.now();

// 阻塞主线程 3 秒
while (Date.now() - start < 3000) {}
```

直觉上应该"1 秒后打印"，但运行结果是**大约 3 秒后**才打印 `timeout`。原因：

```
Timer 到期（1 秒时）
      ↓
只是 callback 获得了"执行资格"
      ↓
还必须等 JavaScript 主线程空闲
      ↓
主线程被 while 阻塞了 3 秒，所以 3 秒后才轮到它
```

所以 `setTimeout(fn, 1000)` 是**最小等待时间**，不是精确执行时间。

## pending callbacks 与 idle/prepare：理解存在即可

这两个阶段日常开发基本碰不到，知道它们存在就行：

- **pending callbacks**：处理被推迟到下一次循环执行的一部分系统级 I/O 回调，比如少数 TCP 连接错误的回调。
- **idle / prepare**：libuv 和 Node.js 内部使用的阶段，普通 JavaScript 开发几乎不会主动操作。

## poll 阶段：事件循环的核心

整台机器里最值得理解的是 `poll` 阶段，因为大量 I/O 都和它有关。它做两件事：

```
poll 阶段负责：
  1. 获取新的 I/O 事件（向内核询问哪些 socket / 文件就绪）
  2. 执行已经准备好的 I/O callback
```

比如文件读取：

> 示意片段（无配套脚本）

```js
fs.readFile('./data.txt', () => {
  console.log('file loaded');
});
```

`fs.readFile` 发起后，这个回调会被注册；等到文件数据真正从磁盘读完，`poll` 阶段会把它调度执行——这就是全章例子里 `[poll] fs.readFile I/O callback` 那一行的来历。

当没有任何定时器待触发、也没有 `setImmediate` 时，事件循环会停在 `poll` 阶段**阻塞等待**新 I/O 事件到来——这也是 Node 能"一直在线却不占 CPU"的原因。

## check 阶段与 setImmediate

`check` 阶段执行 `setImmediate()` 注册的回调：

> 示意片段（无配套脚本）

```js
setImmediate(() => {
  console.log('immediate');
});
```

Node.js 官方定义 `setImmediate()` 为"在 `poll` 阶段完成之后，进入 `check` 阶段调用"。

### 为什么写在 I/O 回调里，顺序就稳定了？

这是经典面试题，答案取决于**写在哪**。

如果在主模块里直接写：

> 示意片段（无配套脚本）

```js
setTimeout(() => {
  console.log('timeout');
}, 0);

setImmediate(() => {
  console.log('immediate');
});
```

**顺序不确定**。`setTimeout(..., 0)` 实际至少需要 1ms 才到期，`setImmediate` 在下一轮 `check` 阶段触发，两者都被排到"下一轮循环"，谁先谁后受进程启动耗时影响。

如果写在 I/O callback 里，情况就稳定了：

> 示意片段（无配套脚本）

```js
fs.readFile('./test.txt', () => {
  setTimeout(() => {
    console.log('timeout');
  }, 0);

  setImmediate(() => {
    console.log('immediate');
  });
});
```

```
immediate
timeout
```

因为当前正处在 `poll` 阶段，紧接着就是 `check` 阶段，所以 `setImmediate` 立即执行；而 `setTimeout(0)` 要等下一轮循环的 `timers` 阶段：

```
当前：poll 阶段（正在执行 I/O 回调）
   ↓
check 阶段（setImmediate 在这里）
   ↓
下一轮 timers 阶段（setTimeout 在这里）
```

全章例子里那三行就是这个结论的实证：`[check] readFile 里的 setImmediate` 紧跟在 `[poll] fs.readFile I/O callback` 之后，而 `[timers] readFile 里的 setTimeout` 被推到了更后面。

另外注意 `[check] 顶层 setImmediate` 出现在 `[poll] fs.readFile I/O callback` **之前**——因为第一轮的 poll 还没有就绪的 I/O，事件循环没在 poll 停留，直接进了 check。这也说明"poll 一定在 check 之前"讲的是同一轮内的顺序，不是绝对时间先后。

## close callbacks：为什么对照里这一行不在这个阶段

`close callbacks` 阶段处理资源关闭类回调。但它的入口很窄——**只有真正经历过 `uv_close` 的 handle，回调才会落在这里**。

全章例子里有两行 `close`，位置却相隔很远：

```
[对照] 无连接 server 的 close（由 nextTick 派发，不是 close callbacks 阶段）   ← 在第 4 行附近（nextTick 队列清空处）
...
[close callbacks] client socket close                                        ← 在 [check] 顶层 setImmediate 之后、[timers] readFile 里的 setTimeout 之前/附近（注意：它和 [poll] 的先后会随计时抖动，并非固定在最后）
```

区别在于：

- `client.destroy()` 销毁的是一条**真实的 socket 连接**，底层 handle 会走一次 `uv_close`，所以 `'close'` 事件落在 close callbacks 阶段（排在整段输出的最后）。
- `net.Server.close()` 在**没有任何活跃连接**时，只是把服务端 handle 关掉，Node 内部改用 `process.nextTick` 派发 `'close'` 事件。所以它出现在 nextTick 队列被清空的位置——夹在 `[nextTick] 顶层 nextTick` 和 `[微任务] 顶层 promise then` 之间，根本没进 close callbacks 阶段。

**结论**：想知道一个 `close` 回调"是不是在 close callbacks 阶段跑的"，要问的不是事件名，而是**这个 handle 有没有真的经历 `uv_close`**。这也说明：凡是对"某个回调落在哪个阶段"的断言，都值得自己实跑一遍，别替运行时想当然。

## 网络 I/O 与 libuv 线程池：谁进池、谁不进池

假设你写了一个 TCP 服务器监听连接：

> 示意片段（无配套脚本）

```js
const net = require('node:net');

const server = net.createServer(socket => {
  socket.on('data', data => {
    console.log(data);
  });
});

server.listen(3000);
```

Node.js **不会**"一个连接开一个线程去等 socket"，而是把 socket 注册给操作系统的 I/O 多路复用机制：

```
Node.js 应用
     │
     ▼
   libuv
     │
     ▼
   epoll（Linux）
     ├── socket A
     ├── socket B
     ├── socket C
     ├── socket D
     └── socket ...
```

```
Kernel（内核收到数据）
     │
     ▼
   epoll（通知就绪）
     │
     ▼
   libuv
     │
     ▼
Event Loop（poll 阶段）
     │
     ▼
JavaScript Callback（socket.on('data') 的回调）
```

靠这套机制，一个主线程就能管理成千上万个连接。

### 不是所有异步操作都在 libuv 线程池里跑

有人以为"Node 异步 I/O 都是多线程并发处理的"，其实要分情况：

```
Async Operation（异步操作）
                    │
        ┌───────────┴────────────┐
        │                        │
        ▼                        ▼
  OS Async I/O             libuv Thread Pool
  （内核通知，不开线程）       （真正开线程干）
        │                        │
  Network / Socket          File System（fs.readFile）
  TCP / HTTP                DNS（dns.lookup）
                           Crypto（pbkdf2 / scrypt）
                           zlib（压缩/解压）
```

- **网络 I/O（TCP / HTTP / Socket）**：依赖操作系统的异步 I/O / I/O 多路复用，交给 `epoll` 等机制，**不进线程池**。内核在数据到达时主动通知，Node 只要等通知，不需要开线程去阻塞轮询。
- **文件 I/O（`fs.readFile`）、一部分 DNS（`dns.lookup`）、一部分 crypto（`crypto.pbkdf2` / `scrypt`）、zlib**：很多平台没有像 socket 那样统一高效的异步接口，或本身就是偏阻塞 / CPU 型工作，libuv 才把它们交给 **Thread Pool**。

记住一句话：**网络 I/O 不进线程池，文件 / DNS / crypto / zlib 才会进。**

### libuv 线程池默认只有 4 个线程

libuv 自带的线程池，默认线程数是 **4**。可以用环境变量调整：

```bash
UV_THREADPOOL_SIZE=8 node src/03-uv-threadpool.js
```

允许的最大值是 **1024**。

用一个可验证的例子感受"默认 4 个线程"。下面这段**逐字摘自配套脚本**（脚本发起 10 个 `pbkdf2`，用完成时刻反推线程池批次）：

> 摘自 `./code/node-basics/src/03-uv-threadpool.js`（运行：`npm run 03pool`）

```js
const crypto = require('node:crypto')

const TASKS = 10
// 让单次 pbkdf2 约 100~300ms。本机实测 100000 次迭代 sha512 约 150ms；若跑太快可调大
const ITERATIONS = 100000
const poolSize = Number(process.env.UV_THREADPOOL_SIZE) || 4

const start = process.hrtime.bigint()
let done = 0
const rows = []

for (let i = 0; i < TASKS; i += 1) {
    // 这一段在演示：每个 pbkdf2 占用线程池里的一个线程，直到算完才释放
    crypto.pbkdf2('password', 'salt', ITERATIONS, 64, 'sha512', () => {
        const elapsedMs = Number(process.hrtime.bigint() - start) / 1e6
        rows.push({ i, elapsedMs, poolSize })
        done += 1
        if (done === TASKS) printSummary()
    })
}

function printSummary() {
    console.log(`UV_THREADPOOL_SIZE = ${poolSize}`)
    console.log('序号 | 距开始(ms) | 占用线程池')
    console.log('-'.repeat(44))
    for (const r of rows) {
        console.log(String(r.i).padEnd(6) + '| ' + r.elapsedMs.toFixed(0).padEnd(11) + '| ' + `1 / ${r.poolSize}`)
    }
    console.log('-'.repeat(44))

    // 按完成顺序分析批次（线程池一次只能并发 poolSize 个）
    const sorted = [...rows].sort((a, b) => a.elapsedMs - b.elapsedMs)
    const firstBatch = sorted.slice(0, poolSize)
    const last = sorted[sorted.length - 1]
    const firstAvg = firstBatch.reduce((s, r) => s + r.elapsedMs, 0) / firstBatch.length
    console.log(`前 ${poolSize} 个完成于约 ${firstAvg.toFixed(0)} ms（几乎同时开跑）；`)
    console.log(`第 ${poolSize + 1} 个起要等线程释放，最晚约 ${last.elapsedMs.toFixed(0)} ms。`)
    console.log('结论：libuv 线程池默认 4 线程，超出部分必须排队 —— 印证“线程池只有 4 个”。')
}
```

实测输出（`npm run 03pool`）：

```
UV_THREADPOOL_SIZE = 4
序号 | 距开始(ms) | 占用线程池
--------------------------------------------
1     | 142        | 1 / 4
3     | 142        | 1 / 4
2     | 180        | 1 / 4
0     | 180        | 1 / 4
4     | 287        | 1 / 4
5     | 295        | 1 / 4
6     | 320        | 1 / 4
7     | 335        | 1 / 4
9     | 396        | 1 / 4
8     | 399        | 1 / 4
--------------------------------------------
前 4 个完成于约 161 ms（几乎同时开跑）；
第 5 个起要等线程释放，最晚约 399 ms。
结论：libuv 线程池默认 4 线程，超出部分必须排队 —— 印证“线程池只有 4 个”。
```

`pbkdf2` 是 CPU 密集的哈希计算，会进线程池。线程池只有 4 个，执行节奏就近似这样：

```
Task 0 ─┐
Task 1 ─┼─ 第一批（4 个线程同时跑）
Task 2 ─┤
Task 3 ─┘

Task 4 ─┐
Task 5 ─┼─ 第二批（前 4 个完成才轮到）
Task 6 ─┤
...
```

你会观察到时间戳明显分成"4 个一批、后面的要排队"。

`UV_THREADPOOL_SIZE` 有三个坑：

1. **必须在进程启动前设置**：运行时用 `process.env.UV_THREADPOOL_SIZE = 8` 改无效。libuv 在进程启动时一次性读取并创建线程，启动后再改只是改了个字符串，线程数不会变。
2. **不是越大越好**：线程过多会增加上下文切换开销，得不偿失。4 是大多数场景的甜点值，需要调大时要基于压测数据，而不是凭感觉。
3. **它是全局共享的一组线程**：`fs`、DNS、`crypto`、zlib 抢的是**同一组**线程池。给 `crypto` 把线程开满，`fs.readFile` 的并发能力也会被挤占——它们不是各自独立的池。

## Node 20 / libuv 1.45 之后 timer 时机变化

从 **libuv 1.45.0 / Node.js 20** 开始，libuv 调整了 Timer 的运行时机：

- **旧版本**可以粗略理解为：

```
timers
  ↓
poll
  ↓
timers（本轮结束前再处理一次）
```

- **现在**每轮循环的 Timer 调度重点变成：

```
poll
  ↓
check
  ↓
close
  ↓
timers（Timer 主要放到 poll 之后处理）
```

libuv 仍会在**首次进入事件循环前**处理一次 Timer，以保持向后兼容。

这个变化会影响部分 `setImmediate()` 与 Timer 的时序关系——以前某些"定时器先跑"的推论，在新版本里不再成立。所以看任何事件循环文章时，请先确认：**文章写于哪一年？对应的 Node 版本是多少？** 用"阶段顺序"去推演，而不是死记某条旧结论。

## 两条微任务队列：nextTick 与 Promise

六个阶段讲完，只讲了宏任务的一半。JavaScript 还有一类任务叫**微任务（Microtask）**：如果只盯着六个阶段，你永远算不对那些带 `Promise.then` 和 `process.nextTick` 的输出题。

在 Node.js 里，需要重点理解的是**两条**微任务队列：

- `process.nextTick()` 队列（nextTickQueue）
- Promise 微任务队列（`Promise.then` / `catch` / `finally` 注册的回调）

宏任务（setTimeout、setInterval、I/O 回调、setImmediate）走六个阶段，而微任务走的是另一套更靠前的检查机制。

### 同步代码永远先执行

第一条铁律：**同步代码永远先跑完**，异步 API 在这一步只是"注册"，不会执行。

> 摘自 `./code/node-basics/src/03-eventloop-order.js`（运行：`npm run 03order`）

```js
console.log('start') // 同步代码，最先执行

setTimeout(() => {
    console.log('timeout') // 宏任务：进入 timer 阶段，排在最后
}, 0)

Promise.resolve().then(() => {
    console.log('promise') // 微任务：在同步代码之后、timer 之前执行
})

process.nextTick(() => {
    // nextTick 队列优先级高于微任务队列，所以先于 promise 打印
    console.log('nextTick')
})

console.log('end') // 同步代码
```

实测输出（`npm run 03order`）：

```
start
end
nextTick
promise
timeout
```

答案是：

```
start → end → nextTick → promise → timeout
```

把上面的代码过一遍 Call Stack：

1. `console.log('start')` —— 同步，立刻打印 `start`。
2. `setTimeout(...)` —— 把一个回调注册进 **timers 阶段**，不执行。
3. `Promise.resolve().then(...)` —— 把一个回调注册进 **Promise 微任务队列**，不执行。
4. `process.nextTick(...)` —— 把一个回调注册进 **nextTickQueue**，不执行。
5. `console.log('end')` —— 同步，立刻打印 `end`。

```
同步执行：  console.log('start')   → start
           setTimeout(注册)         （不打印）
           Promise.then(注册)       （不打印）
           nextTick(注册)           （不打印）
           console.log('end')     → end
───────────────────────────────────────
至此 Call Stack 清空，才轮到微任务与宏任务
```

全章例子里那两行 `==== 同步代码开始/结束 ====` 排在最前面，同一个道理。

再补一道小题，把"宏任务不立即执行"钉死：

> 示意片段（无配套脚本）

```js
console.log('1');
setTimeout(() => { console.log('2'); }, 0);
Promise.resolve().then(() => { console.log('3'); });
console.log('4');
```

顺序是：同步 `1`、`4` 先打印 → 微任务 Promise `3` 清空 → 再进入下一轮 Event Loop 的 timers 阶段打印 `2`：

```
输出：1 → 4 → 3 → 2
```

### process.nextTick 队列：它不属于任何一个 phase

`process.nextTick` 有一个非常特殊的位置——**它不属于 libuv Event Loop 的任何一个 phase**。官方的事件循环阶段图里根本没有它。

Node.js 官方特意强调：nextTick 不在六个阶段之内。它的触发时机是"当前 JavaScript 操作完成后、Call Stack 清空时立刻处理"，然后才继续 Event Loop。

```
当前 JavaScript 操作完成
        │
        ▼
   Call Stack 清空
        │
        ▼
   处理 nextTickQueue（清空到空）
        │
        ▼
   继续 Event Loop（进入下一个 phase）
```

正因为它排在"Call Stack 清空后、Event Loop 继续前"，所以它的优先级**比 Promise 微任务还高**，也比所有宏任务高。

### Promise 微任务队列：排在 nextTick 之后

`Promise.resolve().then(...)` 注册的回调进入 **Promise 微任务队列**。它与 nextTick 队列是两条独立的队列，处理顺序是固定的：

```
当前 JS Callback 执行完毕
        │
        ▼
   Call Stack 清空
        │
        ▼
   process.nextTick 队列（清空到空）
        │
        ▼
   Promise 微任务队列（清空到空）
        │
        ▼
   Event Loop 继续进入下一阶段
```

所以单独比较这两条队列时，nextTick 永远先于 Promise：

> 示意片段（无配套脚本）

```js
process.nextTick(() => { console.log('nextTick'); });
Promise.resolve().then(() => { console.log('promise'); });
```

```
输出：nextTick → promise
```

全章例子里，`[nextTick] 顶层 nextTick` 与 `[对照] 无连接 server 的 close` 都在 nextTick 队列，它们比 `[微任务] 顶层 promise then` 更早，就是这条次序的实证。

## 微任务检查点：不是一轮一次

这是理解复杂输出题最关键、也最容易被记错的一点。

很多人的错误模型是：整轮 Event Loop 跑完，最后才清空一次微任务队列。按这个错误模型，下面这道题会算错。

> 摘自 `./code/node-basics/src/03-microtask-checkpoint.js`（运行：`npm run 03check`）

```js
console.log('脚本开始（同步）')

setTimeout(() => {
    console.log('第一个 timer 回调开始')
    // 关键：在 timer 回调内部注册的微任务，会在“这个回调返回之前”被立刻清空
    Promise.resolve().then(() => console.log('第一个 timer 里的微任务'))
    console.log('第一个 timer 回调结束')
}, 0)

setTimeout(() => {
    console.log('第二个 timer 回调')
}, 0)

console.log('脚本结束（同步）')
```

实测输出（`npm run 03check`）：

```
脚本开始（同步）
脚本结束（同步）
第一个 timer 回调开始
第一个 timer 回调结束
第一个 timer 里的微任务
第二个 timer 回调
```

错误推断（把微任务当成整轮结束才执行）：

```
第一个 timer → 第二个 timer → 第一个 timer 里的微任务
```

正确输出（配套脚本实测）是：

```
脚本开始（同步） → 脚本结束（同步） → 第一个 timer 回调开始 → 第一个 timer 回调结束 → 第一个 timer 里的微任务 → 第二个 timer 回调
```

原因：两个 `setTimeout` 都在同一轮 `timers` 阶段。执行第一个 timer 回调时，先打印"第一个 timer 回调开始"，再往 Promise 微任务队列挂了"第一个 timer 里的微任务"，然后打印"第一个 timer 回调结束"。第一个 timer 回调一返回调度层，**立刻触发一次微任务检查点（microtask checkpoint）**，把"第一个 timer 里的微任务"清空（打印它），然后才轮到第二个 timer 回调（打印"第二个 timer 回调"）。

```
执行第一个 timer 回调 → 打印"第一个 timer 回调开始/结束"
        │
        ▼
第一个 timer 回调返回调度层 → 触发微任务检查点
        │
        ▼
清空 Promise 微任务队列 → 打印"第一个 timer 里的微任务"
        │
        ▼
执行下一个回调 → 打印"第二个 timer 回调"
```

结论：**每次从 JS 回调返回 Node.js 调度层时，都可能成为一个微任务检查点**。把它记成"每个回调之后都清空一次微任务队列"，复杂题就不会错。

全章例子里 `[timers] setTimeout callback` → `[微任务] setTimeout promise then` 紧挨在一起、`[poll] fs.readFile I/O callback` → `[微任务] readFile promise then` 同理，都是这个检查点在起作用。

## 递归 process.nextTick 会饿死事件循环

nextTick 队列的清空策略是"一直清空直到为空"。如果在 nextTick 回调里又注册 nextTick，队列就永远清不空，Event Loop 再也进不到 poll / timers / check 阶段——这就是官方文档提醒的 **I/O starvation（I/O 饥饿）**。

> 摘自 `./code/node-basics/src/03-nexttick-starve.js`（运行：`npm run 03starve`）

```js
let count = 0
const MAX = 10

function starve() {
    count += 1
    console.log(`nextTick 第 ${count} 次`)
    if (count < MAX) {
        process.nextTick(starve) // 递归塞入 nextTick 队列
    }
}
starve()

setTimeout(() => {
    console.log(`setTimeout 终于执行了（排在 ${MAX} 次 nextTick 之后）`)
    console.log('说明：如果上面是无限递归，这一行永远不会打印——这就是“饥饿”')
}, 0)
```

实测输出（`npm run 03starve`）：

```
nextTick 第 1 次
nextTick 第 2 次
nextTick 第 3 次
nextTick 第 4 次
nextTick 第 5 次
nextTick 第 6 次
nextTick 第 7 次
nextTick 第 8 次
nextTick 第 9 次
nextTick 第 10 次
setTimeout 终于执行了（排在 10 次 nextTick 之后）
说明：如果上面是无限递归，这一行永远不会打印——这就是“饥饿”
```

配套脚本里 `starve()` 第一次注册 nextTick，Call Stack 清空后开始清空 nextTickQueue：执行 `starve` → 又注册 `starve` → 再执行 `starve` → 又注册 `starve`……队列始终不为空，Event Loop 卡在清空 nextTick 上，`setTimeout` 那个回调几乎永远没机会执行。

```
nextTick → 注册 nextTick → nextTick → 注册 nextTick → ...
Event Loop 一直进不了：poll / timers / check
```

所以 `process.nextTick` **不是越多越好**。需要"让出执行权、但不饿死循环"时，应该用 `setImmediate`（它排进下一轮 check 阶段，不会阻塞阶段推进）。

## 一张图彻底理解 Event Loop

把同步代码、两条微任务队列、六个阶段，以及"每个回调返回处都是检查点"串成一张完整的调度模型图：

```
同步代码
  │
  ▼
Call Stack 清空
  │
  ▼
┌─────────────────────────────────────────────┐
│  微任务检查点（每次 JS 回调返回调度层都会触发） │
│   ① process.nextTick 队列 ── 清空到空         │
│   ② Promise 微任务队列   ── 清空到空          │
└──────────────────────┬──────────────────────┘
                       │
                       ▼
               ┌───────────────┐
               │  Event Loop   │
               └──────┬────────┘
                      │
                      ▼
                 pending callbacks
                      │
                      ▼
                   idle / prepare
                      │
                      ▼
                    poll（I/O 核心，阻塞等待就绪）
                      │
                      ▼
                    check（setImmediate）
                      │
                      ▼
                close callbacks
                      │
                      ▼
                 timers（setTimeout / setInterval）
                      │
                      └──────► 回到"微任务检查点"，进入下一轮
```

图里最该刻进脑子的一行标注是：**微任务检查点在每个 JS callback 之后**。也就是说，微任务不是"整轮 Event Loop 之后才处理一次"，而是穿插在"每个宏任务回调之间"。

## 输出顺序推演四步法

拿到任何一道输出顺序题，都按这四步走：

**① 先划出同步代码。** 从头扫一遍，把不在任何回调里的 `console.log` 标出来——它们一定按书写顺序最先打印，所有异步 API 此刻只是注册。

**② 再标出每次回调返回处的微任务检查点。** 每执行完一个宏任务回调（setTimeout / I/O / setImmediate 等），就在这个"返回点"记一个检查点；回调里新注册的 nextTick 和 Promise 都在这个检查点内清空。

**③ 同一检查点内 nextTick 优先于 Promise。** 检查点处理顺序固定：先清空 `process.nextTick` 队列，再清空 Promise 微任务队列，两者都清空到空才结束。

**④ 最后才轮到下一阶段的宏任务。** 微任务全部清空后，Event Loop 才继续推进到下一个 phase、执行下一个宏任务回调，然后再次回到第 ② 步。

用这套流程回头复盘本章那个 12 行的例子，逐行都能对上：

```
① 同步代码          → ==== 同步代码开始 ==== / ==== 同步代码结束 ====
② 第一个检查点      → [nextTick] 顶层 nextTick → [对照] server close → [微任务] 顶层 promise then
③ timers 宏任务     → [timers] setTimeout callback
② 它返回处的检查点  → [微任务] setTimeout promise then
④ 同一轮 check      → [check] 顶层 setImmediate
④ 下一轮 poll        → [poll] fs.readFile I/O callback
② 它返回处的检查点  → [微任务] readFile promise then
④ 同轮 check        → [check] readFile 里的 setImmediate
④ 再下一轮 timers    → [timers] readFile 里的 setTimeout
④ close callbacks   → [close callbacks] client socket close
```

不需要死记任何"玄学顺序"。

## 为什么 Node 特别适合 I/O 密集型服务

现在可以正面回答这个问题了。假设有 10,000 个请求同时打进来，它们的大量时间其实都花在等下游：数据库、Redis、HTTP API、Socket、磁盘。这些等待本身不消耗 CPU。

如果每个请求占一个线程（传统"一个请求一个线程"模型）：

```
10000 个请求
      ↓
大量线程被创建
      ↓
频繁的上下文切换（Context Switch）
      ↓
大量内存占用，CPU 被调度本身拖垮
```

而 Node.js 的模型是：

```
大量连接
      ↓
Event Loop 串行调度
      ↓
操作系统异步 I/O（epoll / kqueue / IOCP 就绪通知）
      ↓
就绪后执行对应回调
```

JS 主线程始终只有一个，CPU 真正执行 JS 的只有几毫秒；其余时间 Event Loop 在 `poll` 阶段阻塞等待内核的就绪通知，等哪个 socket / 文件就绪了，就回调哪个。线程不爆炸、切换不爆炸，所以 Node 特别适合 **I/O 密集型**场景：API Server、BFF、WebSocket、即时通讯、代理、爬虫、服务网关、以及服务端流式推送（日志、进度、大文件分片）。

反过来也解释了：为什么 CPU 密集计算会卡死整个服务——它占住了唯一的 JS 线程，Event Loop 转不动，所有 I/O 回调一起排队。

## 小结

- **单线程的准确表述与事件循环带来的收益**
  - **"单线程"的准确含义**：只有执行 JS 的那条主线程是单线程，进程内还有 libuv 线程池与操作系统的网络 I/O
  - **事件循环解决的问题**：发起 I/O 后不等待、转去处理下一个请求，结果回来再执行它的回调；所以一个慢查询不会卡住后面的请求
  - **为什么适合 I/O 密集型**：万级连接只用一个 JS 线程，Event Loop 在 `poll` 阻塞等内核通知，避免"一请求一线程"的上下文切换与内存爆炸
  - **CPU 密集为什么卡死全服务**：它占住唯一的 JS 线程，Event Loop 转不动，所有 I/O 回调一起排队
- **六个阶段的固定轮转顺序**
  1. **timers**：`setTimeout` / `setInterval` 中已到期的回调
  2. **pending callbacks**：少数被推迟到下一轮执行的系统级 I/O 回调（如部分 TCP 连接错误）
  3. **idle / prepare**：libuv 与 Node 内部使用，日常开发基本碰不到
  4. **poll**：I/O 事件处理核心
  5. **check**：`setImmediate` 的回调
  6. **close callbacks**：资源关闭回调
  - **轮转规则**：每进入一个阶段就把该阶段的回调队列一次性执行完（或执行到系统上限），再离开进入下一阶段
- **timers 阶段：`setTimeout` 是"最小等待时间"，且时机随版本变**
  - **资格而非保证**：`setTimeout(fn, 1000)` 只表示至少 1000ms 后这个 callback 才"有资格"执行，能否真执行还要等主线程空闲；主线程被 `while` 阻塞 3 秒，它就 3 秒后才打印
  - **Node 20 / libuv 1.45 改了 timer 时机**：timer 的调度重点从"本轮结束前再处理一次"改成主要放到 `poll` 之后处理（仅在首次进入事件循环前仍处理一次 Timer 以向后兼容），旧的"定时器先跑"推论不再成立
  - **看文章的纪律**：先确认文章写于哪一年、对应哪个 Node 版本，用阶段顺序去推演，而不是死记某条旧结论
- **poll 与 check：I/O 回调内的时序才稳定**
  - **`poll` 是 I/O 核心**：一是向内核询问哪些 socket / 文件就绪，二是执行已准备好的 I/O callback；没有定时器待触发也没有 `setImmediate` 时，会停在这里阻塞等待新 I/O 事件
  - **`check` 阶段与 `setImmediate`**：官方定义为"在 `poll` 阶段完成之后、进入 `check` 阶段调用"，属于本轮之内
  - **顺序不确定 vs 稳定**：直接写在主模块里 `setTimeout(fn, 0)` 与 `setImmediate` 谁先谁后不确定（`setTimeout` 至少 1ms 才到期，两者都排到下一轮）；写在 I/O 回调里则稳定为 `setImmediate` 先——当前在 `poll`，紧接着就是 `check`，而 `setTimeout(0)` 要等下一轮 `timers`
- **close callbacks 的入口很窄**
  - **判定依据是 handle 而非事件名**：只有真正经历 `uv_close` 的 handle，回调才落在 `close callbacks` 阶段——`client.destroy()` 销毁的是真实 socket 连接，所以排在整段输出的最后
  - **反例**：`net.Server.close()` 在没有任何活跃连接时只是关掉服务端 handle，Node 内部改用 `process.nextTick` 派发 `'close'`，于是它夹在 nextTick 队列被清空的位置，根本没进这个阶段
- **网络 I/O 与 libuv 线程池：谁进池、谁不进池**
  - **网络 I/O 不走线程池**：TCP / HTTP / Socket 注册给 `epoll` / `kqueue` / `IOCP`，由内核在数据到达时通知就绪，一个主线程就能管成千上万连接
  - **只有 fs / dns / crypto / zlib 进池**：文件 I/O（`fs.readFile`）、`dns.lookup`、`crypto.pbkdf2` / `scrypt`、zlib 压缩解压，这些平台没有像 socket 那样统一高效的异步接口，或本身就是偏阻塞、CPU 型工作
  - **线程池默认 4 个线程**：`UV_THREADPOOL_SIZE` 可调、允许的最大值是 1024；10 个 `pbkdf2` 任务会呈现 4 / 4 / 2 分批完成的节奏
  - **`UV_THREADPOOL_SIZE` 的三个坑**：必须在进程启动前设置（运行时改 `process.env` 无效，libuv 只在启动时读一次）、不是越大越好（上下文切换开销）、`fs` / DNS / `crypto` / zlib 共用同一组线程池，给 `crypto` 开满会挤占 `fs.readFile` 的并发
- **两条微任务队列与微任务检查点**
  - **两条队列**：`process.nextTick()` 队列（nextTickQueue）与 Promise 微任务队列（`Promise.then` / `catch` / `finally`）；宏任务走六个阶段，微任务走更靠前的检查机制
  - **同步代码永远先跑完**：异步 API 在这一步只是"注册"，例如 `start → end → nextTick → promise → timeout`
  - **nextTick 不属于任何 phase**：官方六阶段图里没有它，触发时机是 Call Stack 清空后立刻把 nextTickQueue 清空到空，再继续 Event Loop，因此优先级高于 Promise 微任务与所有宏任务
  - **同一检查点内 nextTick 先于 Promise**：两条独立队列，顺序固定为先清空 nextTickQueue、再清空 Promise 队列
  - **检查点在每个 JS 回调返回调度层时**：不是一整轮才清一次，所以同轮两个 `setTimeout` 的输出是 `timer1 → promise → timer2` 而不是 `timer1 → timer2 → promise`
  - **递归 nextTick 会饿死事件循环**：队列要"清空到空"，边清边注册就永远清不完，`poll` / `timers` / `check` 都进不去（I/O starvation）；需要"让出执行权但不饿死循环"时应改用 `setImmediate`
- **输出顺序推演四步法**
  1. **先划出同步代码**：不在任何回调里的 `console.log` 一定按书写顺序最先打印，异步 API 此刻只是注册
  2. **标出每个回调返回处的微任务检查点**：每执行完一个宏任务回调就在返回点记一个检查点
  3. **同一检查点内 nextTick 优先于 Promise**：先清空 `process.nextTick` 队列，再清空 Promise 队列，都清空到空
  4. **最后才轮到下一阶段的宏任务**：微任务全部清空后 Event Loop 才推进到下一个 phase，然后回到第 2 步
