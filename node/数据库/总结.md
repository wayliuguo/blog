## 1. MySQL 基础与 SQL

### 1.1 关系型模型与表设计

- 数据存进「表 Table」，行是记录、列是字段，表之间靠外键关联，可整体类比一张 Excel 工作表：`MySQL 表 = 行列网格 + 表间外键`。
- 常用列类型：`INT PRIMARY KEY AUTO_INCREMENT` 自增主键、`VARCHAR(n)` 变长字符串、`DATETIME` 时间、`DECIMAL(m,n)` 精确金额（绝不使用 `FLOAT`/`DOUBLE` 存金额，二进制浮点无法精确表示十进制小数）。
- 库层拦截是防脏数据的第一道门：`NOT NULL` 非空、`DEFAULT` 缺省值、`UNIQUE` 唯一约束，都落在数据库层而不是应用层。
- 主键优先自增 `BIGINT` 而非随机 UUID——有序插入顺序落盘，减少 B+ 树页分裂与碎片。

### 1.2 SQL 基础

- `SELECT`：`WHERE` 过滤 → `ORDER BY` 排序 → `LIMIT` 限制数量；`LIMIT 10 OFFSET 20` 取第 21-30 条，OFFSET 越大扫描越多。
- `INSERT` / `UPDATE` / `DELETE`：写操作漏写 `WHERE` 会作用于全表，务必带上；`DELETE` 是 DML 可回滚、`TRUNCATE` 是 DDL 清表重置自增且不可回滚、`DROP` 连表结构一起删。

```
写数据安全的优先级：WHERE 必带 > 约束兜底 > 备份
```

### 1.3 表关系与连接查询

- 三种关系形态：1:1 直接加外键字段；1:N 外键指向主表（`orders.user_id → users.id`）；N:N 必须建中间表（如学生-课程）。
- `INNER JOIN` 只保留两表都匹配的行（交集）；`LEFT JOIN` 保留左表全部、右表缺失补 `NULL`，查"所有用户含零订单"必须用 LEFT JOIN。

```
INNER JOIN：A ∩ B     LEFT JOIN：A 全集 + B 可空
```

- 陷阱：`LEFT JOIN ... WHERE 右表.列 = 'x'` 会把外连接退化回内连接，右表条件要写进 `ON`。

### 1.4 范式与反范式

- 三大范式：1NF 每列不可再分、2NF 非主键列完全依赖主键、3NF 非主键列不依赖其他非主键列。
- 实际取舍：严格范式减少冗余但查询要更多 JOIN；多数项目接受适度反范式，用数据冗余换查询性能，代价是冗余副本需自行维护一致性（订单项冻结下单时商品名与单价即典型）。

## 2. MySQL 索引与查询优化

### 2.1 索引原理

- 聚簇索引即 InnoDB 主键索引，叶子存整行、数据按主键顺序物理存放，一个表只一个；二级（非聚簇）索引叶子只存"索引列 + 主键值"，查非索引列要**回表**。
- 最左前缀：联合索引 `(name, age)` 相当于先按 name 排、name 相同再按 age 排，支持 `name` 与 `name+age`，单独查 `age` 用不上。
- 联合索引字段顺序决策：几乎每次必带的等值列放最左 → 区分度高的在前 → 范围列靠后 → `ORDER BY` 排序列放末尾以免 filesort。

### 2.2 EXPLAIN 与执行计划

- `type` 由优到劣：`ALL`（全表扫描）→ `range`（索引范围）→ `ref`（非唯一索引等值）→ `eq_ref`（唯一索引）→ `const`（主键/唯一等值）；日常目标至少 `range`、避免 `ALL`。
- `rows` 预估扫描行数越小越好；`Extra` 的 `Using index`=覆盖索引、`Using index condition`=索引下推、`Using filesort`=排序未走索引、`Using temporary`=用了临时表，后两者是要优化的信号。

```
读 EXPLAIN 三件套：type 是否 ALL → rows 偏离是否大 → Extra 有无 filesort/temporary
```

### 2.3 SQL 执行顺序与子查询

- 逻辑执行顺序：`FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`；所以 WHERE 分组前过滤行（不能用聚合）、HAVING 分组后过滤组（只能用聚合或 `GROUP BY` 列）。
- EXISTS vs IN：外层小 / 子结果集大用 EXISTS（逐行判断、命中即返回）；外层大 / 结果集小用 IN（结果集缓存、外层走索引）；关联子查询只能用 EXISTS。
- 现代写法：取"每个用户最新一笔/组内 Top"用窗口函数 `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC)` 替代关联子查询。

### 2.4 索引失效与索引设计

- 底层根因只有一条：**索引列在 WHERE 里被"改造"**了。五类典型失效：
  1. 隐式类型转换：`phone = 13800138000`（列是 VARCHAR）等价于对列套函数，改写成 `phone = '13800138000'`
  2. 函数或运算包住列：`DATE(created_at) = ...`、`amount * 1.1 > 100`，改范围条件或把运算挪到常量侧
  3. `%x` 前缀模糊：`LIKE '%张三'` 走不了 B-Tree，改 `LIKE '张三%'` 或 FULLTEXT / ES
  4. `OR` 中一列无索引：改 `UNION` 或给另一列建索引走 index_merge
  5. 低区分度列单独建索引：优化器认为扫全表更快，放进联合索引当补充列
- `!=` 与 `NOT IN` 通常不走索引（优化器认为全表更快）。
- 覆盖索引（查询列全在索引里、`Extra` 显示 `Using index`、不回表）是见效最快的优化，`SELECT *` 几乎必然破坏它。
- 索引下推 ICP：MySQL 5.6+ 把 WHERE 里能用索引字段的条件推到存储引擎层，遍历索引时就筛行、减少回表次数。
- 索引要按真实查询建：`SELECT *` 破坏覆盖 → 只查所需列；十条典型场景（email 唯一、订单号等值、`(user_id, created_at)` 联合、会话+时间游标分页等）都围绕"等值/范围高频查询列"展开。

### 2.5 COUNT 与分页优化

- `COUNT(*)` 与 `COUNT(1)` 等价（InnoDB 已优化）；`COUNT(列)` 只数非 NULL 行、结果可能不同。
- 大表 COUNT：选最小非空二级索引 `USE INDEX`、`SHOW TABLE STATUS` 取估算值、Redis 维护计数，或分页用 `EXISTS` 判"是否有下一页"。
- 深度分页：`LIMIT 10 OFFSET 100000` 越翻越慢，换游标 `WHERE id > 100000 ORDER BY id LIMIT 10`，翻第 N 页和翻第 1 页一样快。

### 2.6 慢查询排查流程

- 开启日志：`slow_query_log = ON`、`long_query_time = 1`、`log_queries_not_using_indexes = ON`，生产用 `pt-query-digest` 按总耗时 × 出现次数排优先级。
- 五步闭环：发现 → 定位 → `EXPLAIN` → 优化 → 验证；把"函数包裹列"改成范围查询后 `type` 从 ALL 变 range、扫描行数骤降，再复测确认没有让别的查询变差。

## 3. MySQL 事务、锁与并发控制

### 3.1 ACID 与隔离级别

- ACID：原子性（全成或全败）、一致性（约束不被破坏）、隔离性（并发事务互不干扰）、持久性（提交后不丢）。
- 四种隔离级别（脏读 / 不可重复读 / 幻读，从高到低）：读未提交（都可能，最快）、读已提交（防脏读）、可重复读（防脏读 + 不可重复读）、串行化（全防，最慢）。**InnoDB 默认可重复读（RR）**。

### 3.2 MVCC 与快照读/当前读

- MVCC：每行两个隐藏字段 `DB_TRX_ID` + `DB_ROLL_PTR` 串成 Undo Log 版本链，每事务一个 Read View，实现"读不阻塞写、写不阻塞读"。
- 快照读：普通 `SELECT` 读事务开始时的 MVCC 快照、不加锁；RR 下同一事务内两次普通 SELECT 结果一致。
- 当前读：`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` 读最新已提交版本并加锁；"我刚 UPDATE 了别人一定能看到"是误区——RR 下别人普通 SELECT 仍看旧版本，`FOR UPDATE` 把读升级成当前读才是写并发控制正确的读法。

```
SELECT 默认"看旧版本"；FOR UPDATE / UPDATE / DELETE 才"看最新并加锁"
```

### 3.3 锁粒度与防幻读

- 锁粒度：`WHERE` 走索引才是行锁（Record Lock）；不走索引则锁住所有行、等价表锁。
- RR 挡不住幻读，靠间隙锁（Gap Lock）与 Next-Key Lock（行锁+间隙锁）兜底；`WHERE id BETWEEN 10 AND 20 FOR UPDATE` 会锁住区间与间隙、阻止插入。
- 间隙锁只在 RR 生效，会显著压低保并发；可接收时降级到读已提交换吞吐。

### 3.4 防超卖的原子 UPDATE

- 把判断下推进 UPDATE 的 WHERE：`UPDATE quotas SET balance = balance - 1 WHERE user_id = ? AND balance >= 1`，用 affectedRows 判定成败（1 成功、0 余额不足），避免"先 SELECT 再 UPDATE"被并发插空扣成负数；UPDATE 本身是当前读 + 行锁，多个并发串行执行。
- 三种方案取舍：纯扣减且不能超用**原子 UPDATE**（最简单无锁等待）；扣减前需跨表校验再上**悲观锁 `FOR UPDATE`**；偶发并发多字段更新用 **version 乐观锁**、冲突重试。

### 3.5 死锁防范

- AB-BA 死锁：两个事务以相反顺序更新多行（A 锁 id=1 等 id=2，B 锁 id=2 等 id=1）。
- 排查：`SHOW ENGINE INNODB STATUS` 看 `LATEST DETECTED DEADLOCK` 段落、`INFORMATION_SCHEMA.INNODB_TRX` 看活动事务、`INNODB_LOCK_WAITS` 看等待。
- 预防：所有事务按相同顺序访问资源（如都按 id 升序）、保持事务简短、避免事务内用户交互、用 `SELECT ... FOR UPDATE NOWAIT`（8.0+）避免等锁。

## 4. MySQL 高可用、分布式与运维

### 4.1 主从复制与读写分离

- 四步复制流程：主库写 Binlog → dump 线程推给从库 → 从库 I/O 线程写 Relay Log → SQL 线程重放。
- Binlog 三种格式：`STATEMENT` 日志小但非确定性函数（`UUID()`/`NOW()`）会主从不一致；`ROW` 最精确、日志大，生产推荐；`MIXED` 自动切换。
- 主从延迟排查：看 `SHOW SLAVE STATUS` 的 `Seconds_Behind_Master`、`Slave_IO_Running`/`Slave_SQL_Running`；先分清 I/O 迟到还是 SQL 迟到（网络推送 vs 重放慢）；解法定向：拆大事务（每次删 1000 行）、并行复制（`slave_parallel_workers = 4` + `LOGICAL_CLOCK`）、延迟敏感业务强制读主。

```
写→主库 → Binlog → 从库 RelayLog → SQL 重放 → 读
```

### 4.2 分库分表

- 两类拆分：垂直按业务分库（用户/订单/商品库）；水平按分片键取模拆表（`user_id % 4` → `users_0..users_3`）。
- 分片键选型：按时间分片会造成写入热点（90% 写入集中当月末）；`user_id`/`order_id` 哈希取模更均匀且同用户数据同片；消息系统用"时间+用户"做冷热分离、地理位置按区域范围。
- SQL 限制与绕开：跨分片 JOIN/事务、无分片键的全分片扫描都不可用；用广播表（配置表每片都存）、ER 分片（父子表同键）、ES 索引表绕开。
- 全局唯一 ID 四方案：雪花算法（高性能、趋势递增、依赖时钟）、Redis INCR（简单但依赖 Redis）、数据库号段（`UPDATE id_generator SET max_id += 1000` 批量领号）、UUID（本地生成但无序过长伤索引）。

### 4.3 在线 DDL 与迁移

- Online DDL：加索引/加列/删列/改默认值可 `ALGORITHM=INPLACE, LOCK=NONE` 不阻塞读写；改列类型与改主键要重建表、不允许并发 DML。
- 大表用 gh-ost：建影子表 `_orders_gho` → 监听 Binlog 同步增量 → 分批拷贝原表数据 → 原子改名切换（毫秒级），千万级表首选。
- 零停机迁移五步：搭主从复制 → `pt-table-checksum` 校验 → 灰度切读（10%→50%→100%）→ 切写（窗口 1-5 分钟）→ 保留旧库 3-7 天观察回滚。

### 4.4 连接池调优与故障排查

- 核心参数：`connectionLimit`、`queueLimit: 0`、`waitForConnections: true`、`connectTimeout: 10000`、`idleTimeout`（mysql2 默认 60 秒）、`enableKeepAlive: true`；注意 `acquireTimeout` 是旧 `mysql` 库参数，mysql2 已失效。
- 连接数估算：`(CPU 核心数 × 2) + 有效磁盘数` 或 `QPS × 平均查询时间`；4 核 8G 建议 20-50、8 核 16G 建议 50-100；过多连接因上下文切换反而变慢。
- 三类故障：溢出（`ER_CON_COUNT_ERROR`）先查慢查询占连；泄漏（连接只涨不落）检查 `finally` 里 release 或用 `connection.execute` 自动归还；超时（`connect ETIMEDOUT`）源于 `wait_timeout` 默认 8 小时，开 `enableKeepAlive` 且 `idleTimeout` 小于它。
- 监控要从底层 `pool.pool` 的 `_allConnections`/`_freeConnections`/`_connectionQueue` 取真实计数，告警阈值：活跃占比 > 80%、等待队列 > 100。

### 4.5 备份与恢复

- 三方案：mysqldump 逻辑备份（恢复慢，<50GB）；XtraBackup 物理备份（1TB 约 30 分钟）；Binlog 增量用于时间点恢复 PITR。
- 策略与清单：周日全量 + 每日增量 + Binlog 保留 7 天以上；异地备份、每周恢复测试、每季度限时 4 小时完整演练、备份失败 5 分钟内告警。
- PITR 三步：`xtrabackup --prepare`/`--copy-back` 恢复全备 → `mysqlbinlog --stop-datetime` 回放至误操作前一刻 → 校验关键表行数与业务数据。

## 5. Node.js 访问 MySQL

### 5.1 mysql2 连接与参数化查询

- 连接池：`mysql.createPool` 复用连接省握手，`connectionLimit: 10` 控上限、`queueLimit: 0` 不限队列、`waitForConnections: true` 没空闲连接就排队。
- 参数化查询防注入：用 `?` 占位符传参（`pool.query('... WHERE id = ?', [userId])`），绝不把变量拼进 SQL 字符串——占位符值只当数据、不当 SQL。

### 5.2 TypeORM 建模与关系

- ORM 定位：把数据库表映射成带装饰器的 Entity 类，用 Repository 方法操作数据而不手写 SQL。
- 核心装饰器：`@Entity('users')` 对应表、`@PrimaryGeneratedColumn()` 自增主键、`@Column({ length: 50 })`/`{ default: 0 }`/`{ unique: true }` 定列约束。
- 实体关系：`@OneToMany` 与 `@ManyToOne` 配 `@JoinColumn({ name: 'user_id' })` 表达一对多；`@OneToMany` 侧是虚拟字段、库里无此列，外键由 `@JoinColumn` 指定。

### 5.3 N+1 问题

- N+1：先 1 次查主表拿 N 条，再循环各查 1 次关联表 = 总共 1+N 次，本质是懒加载把一次关联拆成 N 次网络往返。
- 解决：`relations: ['orders']` 一次带出，或用 QueryBuilder `.leftJoinAndSelect('user.orders', 'order').getMany()` 压成一次。

### 5.4 QueryRunner 事务

- 流程：`createQueryRunner()` → `connect()` → `startTransaction()` → 业务操作（`manager.decrement`/`manager.save`）→ `commitTransaction()`，出错 `rollbackTransaction()`，`finally` 必须 `release()`。

## 6. MongoDB 文档模型与基础操作

### 6.1 文档型模型与 BSON

- 概念映射：`数据库/集合/文档/字段` 对应 MySQL 的 `库/表/行/列`，主键是驱动自动生成的 `_id`。
- 文档以 BSON（Binary JSON）存储，字段值可嵌套数组与对象，无需预定义 Schema。
- ObjectId 共 12 字节 = 4 字节时间戳 + 5 字节机器标识 + 2 字节进程号 + 3 字节计数器，时间戳在最高位所以趋势递增、按 `_id` 排序 ≈ 按插入时间排序（游标分页可拿它当游标）；接口入参 `_id` 先按 `/^[0-9a-f]{24}$/` 校验，否则非法值直接抛 `BSONError`。

### 6.2 基本 CRUD

- 查询：`find({ age: { $gt: 18 } })` 比较操作符、`/张/` 正则、`$in: [18, 20]`；驱动返回游标，`.toArray()` 才取回文档。
- 插入：`insertOne` 返回 `insertedId`（`_id` 客户端生成）、`insertMany` 返回 `insertedCount` + `insertedIds`。
- 更新：`updateOne({ name }, { $set: { age: 26 } })`，只改指定字段；不带 `$set` 直接传文档会**整条替换**；`matchedCount` 与 `modifiedCount` 不等说明值本来就一致。
- 删除：`deleteOne`/`deleteMany` 的 `deletedCount` 为 0 可判断目标文档是否存在。

### 6.3 Mongoose 入门

- 用法：先定义 Schema（`required`/`default`/`unique` 等约束）再 `mongoose.model()` 生成 Model，之后走 `create`/`find`/`findById`/`updateOne`/`deleteOne`；与 TypeORM 类似但没有迁移概念。
- `required`/`default` 是客户端校验，`unique: true` 只是让 Mongoose 建唯一索引、真正拦截重复靠服务端索引（需 `await User.init()` 等索引建好）。

### 6.4 文档关系建模

- 嵌入：一次查询拿全数据，但有冗余、受单文档 16MB 限制；适合数据总是一起查、不单独变化、量小的场景。
- 引用：省空间、一致性由引用保证，`populate()` 补齐（本质是再发一次查询）；适合独立变化、量大、需单独查询的场景。

```
先问访问模式：能否一次查询满足页面需求？
  能 → 嵌入；不能 → 引用
```

- 嵌入 vs 引用对照：查询速度（快 vs 慢需 JOIN）、数据冗余（有 vs 无）、一致性（自维护 vs 引用保证）、文档限制（16MB vs 不受限）。

### 6.5 选型与生产场景

- MySQL vs MongoDB 选型：用户/订单/财务等结构化数据要强 ACID 与复杂关联报表 → MySQL；日志/评论/配置等结构灵活、写频繁、快速迭代 → MongoDB。
- 日志系统：TTL 索引自动过期（时间字段设 `expireAfterSeconds`，后台约每 60 秒扫一次删过期文档，有分钟级延迟，必须建在日期或带时间数组字段上）；日志按日期分集合 `logs_20240101`，历史数据整体 `drop()` 比 DELETE 快、不产生碎片，但跨天统计要在应用层汇总。
- 评论/回复系统：回复嵌在评论内用 `$push` 追加、`comments.$.replies` 定位更新（定位靠条件里的 `comments._id`，漏写则更新静默落空）；每条评论 < 1KB、一篇文档内评论不超 100 条才适合嵌入。

## 7. MongoDB 索引、聚合与高可用

### 7.1 索引与查询优化

- 创建索引：`createIndex({ name: 1 })` 单字段、`{ age: 1, name: 1 }` 复合、`{ unique: true }` 唯一索引，`1` 升序 `-1` 降序；`createIndex` 幂等，索引拖慢写入、按真实查询建。
- explain 关键指标：`totalDocsExamined` 扫描文档数、`nReturned` 返回数、`executionTimeMillis` 执行时间；`winningPlan.stage` 的 `IXSCAN`=走索引、`COLLSCAN`=全集合扫描；`explain('executionStats')` 会真跑查询、线上慎用。
- 慢查询：`db.setProfilingLevel(1, { slowms: 100 })` 记录超 100ms 查询，再查 `system.profile`（级别 0 会连 `system.profile` 集合一起删，要留档先导出）。

### 7.2 聚合管道

- 常用阶段：`$match` 过滤（类似 WHERE）→ `$group`（`$sum`/`$sum:1` 分组聚合，类似 GROUP BY）→ `$sort` → `$project`（选字段、`_id: 0` 排除）→ `$limit`。
- 阶段顺序决定性能：`$match`、`$sort` 越靠前越能用索引、越早缩小数据量；`$group`/`$sort` 单阶段内存默认 100MB，超限开 `allowDiskUse`。
- 关联与展开：`$lookup` 类似 LEFT JOIN、`$unwind` 把 `$lookup` 产生的数组摊平成对象；按月分组用 `_id: { $month: '$createdAt' }`。

### 7.3 事务与原子性

- 多文档事务：`startSession()` + `startTransaction()`，出错 `abortTransaction()`，`finally` 里 `endSession()`。
- MongoDB 4.0+ 支持但性能低于 MySQL 事务，只在必要时使用；**单机 mongod 起不了事务**，多文档事务要求副本集或分片集群。

### 7.4 副本集与高可用

- 三种角色：Primary 唯一可写、Secondary 异步复制 `opLog` 且可读、Arbiter 只参与选举不存数据。
- 选举与大多数原则：Primary 心跳超时（默认 10 秒）触发选举，需超半数节点同意，因此节点取奇数（3、5、7）；偶数可能票数对等选不出新主形成脑裂，可加 Arbiter 凑奇数。
- 读写分离：连接串带 `replicaSet=` 与 `readPreference`（合法值 primary/primaryPreferred/secondary/secondaryPreferred/nearest）；`secondaryPreferred` 优先读从、`primaryPreferred` 优先读主；一致性要求高读主、容忍延迟读从、报表读从；故障转移 10-30 秒完成。

### 7.5 分片集群与水平扩展

- 何时分片：数据超单机内存（300GB+）、写入超 1 万 QPS、垂直扩展到头，三选一才考虑；副本集解决高可用、分片解决水平扩展，可组合（每个分片本身是副本集）。
- 分片键坑点：时间戳分片写入热点、自增 ID 哈希分片让范围查询跨全部分片；`user_id` 哈希或"区域 + 时间"更稳。
- 跨分片分页：各分片返 N 条再客户端聚合排序、分片越多越慢；优化靠带分片键只查单分片、游标分页（`_id: { $gt: lastId }`）、统计结果缓存 Redis。

### 7.6 索引失效与覆盖索引

- 最左前缀：索引 `{ user_id: 1, created_at: -1 }` 下 `find({ user_id: 123 })` 与带 `created_at` 范围能用，只查 `created_at` 用不到。
- 失效场景：正则包含匹配 `/张三/` 不走索引（`/^张/` 前缀可以）、对索引列用函数（`$expr + $year`）不走索引；改 `$gte`/`$lt` 范围条件才走索引。
- 覆盖索引：查询只用索引里的字段（如 `count({ user_id: 123 })`）无需回表，`explain()` 只有 `IXSCAN`、无 `FETCH` 即命中。
- 优化判据：`totalDocsExamined >> nReturned` 说明扫描远多于返回、需要优化。

## 8. PostgreSQL 与 pgvector

### 8.1 PG 与 MySQL 定位差异

- 设计取向：MySQL 简单、快、稳，是 Web 业务与交易首选；PG 标准、严谨、可扩展，能力面更宽，适合分析、地理、JSON 文档、向量等混合负载。
- 心智模型：MySQL 管"钱和订单"，PostgreSQL 管"半结构化数据与向量"；不是替代关系，而是后端该同时掌握的两套武器。
- 选型：核心业务/交易/账户选 MySQL（生态成熟、运维简单）；半结构化 metadata、复杂分析/窗口函数、地理（PostGIS）、向量（pgvector）选 PG；常见组合是 MySQL 管账户订单 + PG 管运行数据与文档向量。

### 8.2 强数据类型

- `UUID`：分布式环境生成主键、避免自增 ID 被遍历，`DEFAULT gen_random_uuid()`。
- `TEXT[]` 数组：一个字段存多值、省掉关联表，用 `'io' = ANY(tags)` 做包含判断。
- `ENUM`：`CREATE TYPE task_status AS ENUM (...)` 限定取值集合，比 `VARCHAR` 更省空间更安全。
- `JSONB`：承载任意结构化/半结构化字段（详见下节）。

### 8.3 JSONB 与 GIN 索引

- JSON vs JSONB：JSON 文本原样存、每次解析慢、不能高效索引；JSONB 解析后二进制存、直接取字段快、可建 GIN 索引。
- 取值与过滤：`->` 返回 jsonb、`->>` 返回文本；`payload @> '{"tool": "sql_query"}'` 走 GIN 包含判断，也可只对某键建 `USING GIN ((payload -> 'tool'))` 更省空间。
- 决策模型：结构稳定、要联表用普通列；结构随业务演进、常整体读写、需灵活查询用 JSONB + GIN（工具调用日志、运行 metadata 几乎都该用 JSONB）。

### 8.4 窗口函数、CTE 与 UPSERT

- 窗口函数：`ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC)` 取组内最新一条、`RANK() OVER (...)` 算组内排名；行还在、只多一列，看到"每个 X 的 Top N / 最新一条 / 累计值"第一反应就应是窗口函数。
- CTE（`WITH`）：`WITH ranked AS (...)` 把子查询命名，多步逻辑比嵌套子查询清晰。
- UPSERT：`ON CONFLICT (run_id) DO UPDATE SET status = EXCLUDED.status` 一条语句完成幂等写入（重复运行更新而非报错）。

### 8.5 更丰富的索引类型

- B-Tree：等值、范围、排序（默认），如 `WHERE user_id = ?`、`ORDER BY created_at`。
- GIN：多值/JSONB/数组包含，如 `payload @> '{"tool":"x"}'`、数组 tags。
- GiST：几何、范围重叠、全文检索。
- 部分索引：只对部分行建索引（如 `WHERE status = 'running'`），体积小、写入快（PG 独有且实用）。
- 表达式索引：对函数结果建索引，如 `ON users (lower(email))` 做大小写无关查询；MySQL 无部分索引、对 `lower(email)` 要走生成列。

### 8.6 EXPLAIN ANALYZE

- PG 的 EXPLAIN ANALYZE 会真执行语句并给真实耗时，比 MySQL 的 EXPLAIN 信息更全。
- 三件事：`Seq Scan`（全表扫描）大表出现通常没走索引；`rows` 与 `actual rows` 偏差大说明统计信息过期需 `ANALYZE`；`Planning Time`/`Execution Time`（毫秒）是优化目标。

```
看到 Seq Scan + 大表 + 慢执行 → 先问为何没走索引，再想该建 GIN/部分索引，而不是加内存
```

### 8.7 MVCC 与 VACUUM

- 旧版本存放不同：MySQL 在 undo log（独立段）由 purge 线程清理；PG 在数据表本身（行有 `xmin`/`xmax` 版本号）。
- 回收方式：PG 的 UPDATE 是"标记旧行失效 + 插入新行"，旧行成 dead tuple 靠 `VACUUM`（或 autovacuum）回收，否则表持续膨胀、越查越慢。
- 长事务影响：MySQL 阻塞 purge；PG 阻塞 VACUUM、死元组堆积。手动 `VACUUM (ANALYZE, VERBOSE)` 回收并更新统计信息。

### 8.8 pgvector 向量检索

- 完整流程：原始文档 → 切块（200~1000 字一段）→ Embedding 转定长向量（如 1536 维）→ 存 `VECTOR(1536)` 列 → 用户查询向量化 → 余弦距离 `<=>` 取 TopK。
- 建表与索引：`CREATE EXTENSION IF NOT EXISTS vector;`；IVFFlat 适合百万级以内（`WITH (lists = 100)`）、HNSW 在 PG 0.5+ 召回更准、构建更快（新项目直接用）。
- 距离算子与索引 ops 对齐：`<->` 欧氏配 `vector_l2_ops`、`<#>` 内积配 `vector_ip_ops`、`<=>` 余弦配 `vector_cosine_ops`，ops 不对应索引不会被使用。
- 何时上专用库：数据到千万级、QPS 很高、需独立扩缩容时再考虑 Milvus / Qdrant；中小型业务用 PG + pgvector 已足够。

### 8.9 NestJS + Prisma 集成

- 类型旁路：Prisma 无 `VECTOR` 原生类型，schema 用 `Unsupported("vector(1536)")?` 透传。
- 读写走 raw query：`$executeRaw` 写向量（拼成 `'[1,2,...]'` 字符串）、`$queryRawUnsafe` 做 TopK——ORM 方法表达不了 `<=>`。
- 建表与索引：`DATABASE_URL` 用 `postgresql://`；migration 先 `CREATE EXTENSION vector;`，HNSW 索引手写 `CREATE INDEX`（Prisma 不支持声明式定义）。

## 9. Redis 基础与数据结构

### 9.1 Redis 定位与为什么快

- Redis 定位：基于内存的键值数据库，读写微秒级，常用于缓存、会话、排行榜、计数器、消息队列、分布式锁、限流；数据可丢可重建的放 Redis、必须落盘的进 MySQL。
- 与 MySQL 分工：MySQL 存磁盘、毫秒级、容量大、做持久存储；Redis 存内存、微秒级、受内存限制、做加速与临时数据。
- 为什么快四条：基于内存、单线程模型（命令串行免上下文切换与锁竞争）、IO 多路复用（epoll 扛大量并发连接）、高效数据结构（SDS、跳表、压缩列表）。
- 单线程的代价：一条慢命令（`KEYS *`、遍历大 key、复杂 Lua）会阻塞所有客户端，是 Redis 性能问题头号来源。

### 9.2 五种基本数据结构

- String：可存字符串、数字、二进制，`INCR`/`INCRBY` 做计数器、`SETEX`/`SET EX` 设值顺带设过期；底层 SDS（自带 `len`/`free`、取长 O(1)、预分配免重分配、二进制安全）。
- Hash：字段-值对，`HSET`/`HGET`/`HINCRBY` 单独读写某字段，比存整份 JSON 灵活；字段很多时会从紧凑编码退化成哈希表、内存上升（大 Hash 要拆）。
- List：双向链表实现的有序可重复列表，`LPUSH` 配 `RPOP` 即最简 FIFO 消息队列与时间线。
- Set：无序不重复集合，`SINTER`/`SUNION`/`SDIFF` 支撑标签、共同好友与去重统计；底层 intset 或 hashtable。
- ZSet：成员带分数按分数排序，`ZADD`/`ZREVRANGE`/`ZRANK` 实现排行榜、延时队列、滑动窗口限流；底层跳表 + 字典。

## 10. Redis 持久化与内存管理

### 10.1 持久化方式

- RDB 快照：靠 `save 900 1` 规则或 `BGSAVE` 定期落盘；文件紧凑、恢复快，但可能丢最后一次快照之后的数据。
- AOF 日志：每个写命令追加落盘，`appendfsync everysec` 是默认推荐折中（最多丢 1 秒），代价是文件更大、恢复更慢；`always` 最安全最慢、`no` 最快最不安全。
- AOF 重写：`auto-aof-rewrite-percentage 100` + `auto-aof-rewrite-min-size 64mb` 自动触发，或手动 `BGREWRITEAOF`，去掉冗余命令压小文件。
- 混合持久化：`aof-use-rdb-preamble yes` 让 RDB 快照充当 AOF 前缀，同时拿到 RDB 恢复速度与 AOF 高安全性。

### 10.2 过期策略与内存淘汰

- 惰性删除 + 定期删除组合：访问才判断过期并删除；另每 100ms 随机抽一批带 TTL 的 key 检查（`hz` 控制每秒检查次数、默认 10）。
- 八种淘汰策略：默认 `noeviction` 内存满写直接报错；纯缓存用 `allkeys-lru`、想只淘汰带 TTL 的 key 用 `volatile-*`；`maxmemory` 划定内存上限；淘汰只在达 `maxmemory` 后触发，`evicted_keys` 持续增长说明容量不足应扩容。
- 内存监控：`used_memory`/`maxmemory` 看水位、`mem_fragmentation_ratio` 碎片率超 1.5 告警。

### 10.3 Big Key 与 Hot Key

- Big Key 判定：String 超 10KB 或集合类超 5000 元素；危害是阻塞 Redis 单线程、集群数据倾斜、网络开销；拆子 Hash、压缩大 JSON、删除用 `UNLINK` 异步删（List 用 `LTRIM` 分批清）。
- Hot Key 判定：单 key QPS 过万或某节点 CPU 明显偏高；解法四种：本地缓存、读写分离、副本分片、限流；常与击穿耦合，配"逻辑过期 + 异步刷新"更好。
- 排查：`redis-cli --bigkeys`（扫全库有性能影响，生产低峰或从节点执行）、`redis-cli --hotkeys`（基于 LFU）。

### 10.4 Redis 事务

- `MULTI`/`EXEC` 打包执行但不回滚：语法错误整批不执行、运行时错误只影响出错那条；要"先检查再修改"的原子语义靠 `WATCH` 乐观锁或 Lua 脚本。
- 需要真正原子复合操作（扣库存、释放锁）一律用 Lua；`MULTI` 只适合"不关心中途出错、只想一次发完"的批量场景，那用 Pipeline 更合适。

## 11. Node.js 操作 Redis

### 11.1 连接与重连

- 连接配置：`new Redis({ host, port, retryStrategy })`，重连策略返回 `Math.min(times * 200, 2000)` 做指数退避。
- ioredis 内置连接池与自动重连；集群模式用 `new Redis.Cluster([...])` 传节点列表；密码为空时不要传 `password`，否则向无密码实例发起 AUTH 会报错。

### 11.2 各数据类型的 Node 写法

- String：`setex` 缓存 JSON、`incr`/`incrby` 做计数器（原子自增，无需先读再写）。
- Hash：`hset`/`hgetall`/`hget` 存对象，可只更新单字段。
- List：`lpush`/`rpop` 做 FIFO 消息队列。
- Set：`sadd`/`sismember` 做标签与去重集合。
- ZSet：`zadd`/`zrevrange 'WITHSCORES'` 做排行榜 Top N。

### 11.3 NestJS 集成与 RedisService 封装

- 全局 Redis 模块：用 `@Global()` 的 `useFactory` 提供 `'REDIS'` token 并 exports，Service 用 `@Inject('REDIS')` 注入。
- RedisService 封装：把 JSON 序列化反序列化、`set` 的 TTL 分支、`del`、`lock`/`unlock` 收进一个服务，业务侧不碰连接细节；安全释放锁必须用 Lua 比对 value 再删。

### 11.4 管道与 Lua 脚本

- 管道 Pipeline：`redis.pipeline()` 批量攒命令减少网络往返，`exec()` 返回 `[[err, result], ...]` 与命令顺序对应；只保证批量、不保证原子性。
- Lua 脚本原子性：`redis.eval(script, 1, key)` 在 Redis 内串行原子执行，适合"判断 + 扣减库存"这类跨多条命令的逻辑。

### 11.5 连接健康监控

- 定时 `ping()` 探活（连接异常抛错）+ `info()` 解析结构化字段，对连接数过千、内存超 1GB、`evicted_keys` 出现三类情况告警。

## 12. Redis 缓存实战

### 12.1 缓存读写与更新策略

- 热点缓存读写套路：查缓存 → 未命中查库 → `setex` 回写并设 TTL；热点列表设 5 分钟这类短 TTL，避免脏数据长期滞留。
- 缓存过期来源：定时与惰性过期由 Redis 负责；数据变更时由业务主动 `del` 缓存，是应用层责任。
- 三种更新策略：Cache Aside（读查缓存未中回写、写先落库再删缓存）最常用、简单但短暂不一致；Read/Write Through 由缓存层代理读写、一致性较好但复杂；Write Behind 异步批量写库、性能好但可能丢数据。
- 删缓存而非更新缓存：写路径"先写库再删缓存"；更新缓存可能被一串无效更新浪费资源，删缓存是懒加载、下次读时再回写；要更强一致用延迟双删或删动作进 MQ 重试。

### 12.2 缓存三大问题

- 穿透（查不存在的数据每次都打到库）：缓存空值并给短 TTL（如 60 秒，注意存的是 `'null'` 而非 `null`），或前置布隆过滤器（位数组 + 多个哈希函数，有假阳性无假阴性），并做参数合法性校验。
- 击穿（热点 key 过期瞬间大量请求同时回源）：`SET NX EX` 互斥锁只放一个请求查库重建、其余等待重试，锁 TTL 必须大于重建缓存最大耗时；超热 key 用"逻辑过期 + 后台异步刷新"。
- 雪崩（大量 key 同一时刻过期）：TTL 加随机抖动打散、提前缓存预热、本地 + Redis 多级缓存、对库请求限流降级。

```
穿透 = 不存在的数据  击穿 = 单热点瞬间失效  雪崩 = 大批同时失效
```

### 12.3 缓存预热与全局 ID

- 缓存预热：大促前 30 分钟用 Pipeline 批量灌入热点数据、TTL 带随机值、每 5 分钟刷新一次。
- Redis INCR 全局 ID：格式"前缀 + 日期 + 6 位自增"（如 `ORDER20240101000001`），首次 `incr` 返回 1 时设 2 天过期，防 key 无限堆积。

### 12.4 分布式锁

- 加锁与安全释放：`SET lock:key <value> NX EX 10` 加锁，value 用唯一标识标识持有者；解锁必须用 Lua 比对 value 再删，否则误删别人的锁（自己的锁已过期、别人已拿到）。
- `SETNX` 的缺陷：`SETNX` + `EXPIRE` 两步非原子、崩溃即死锁；不设 TTL 直接死锁；到期用 `DEL` 误删他锁；TTL 到期业务没跑完锁提前失效。
- Redlock：多节点场景需至少 3 个独立 Redis 节点、半数以上加锁成功且总耗时小于 TTL 才算成功；依赖各节点时钟基本一致、不提供强一致。最好"锁 + 幂等"双保险。

### 12.5 滑动窗口限流

- ZSet 滑动窗口（可靠）：`ZREMRANGEBYSCORE` 清窗口外记录 → `ZCARD` 判断是否超限 → `ZADD` 记录本次请求；成员用"时间戳 + 序号"保证同一毫秒唯一；生产给限流 key 设过期，防 key 一直留在 Redis。

## 13. Redis 高可用与集群

### 13.1 主从复制

- 五步复制流程：从节点发 `SYNC` → 主节点 `BGSAVE` 出 RDB → 传 RDB → 从节点加载 → 之后持续同步写命令（增量复制）。
- 作用：读写分离分担读压力、从节点作数据备份、高可用的基础（主崩溃后可提升）；默认异步，从节点可能读到旧数据，一致性敏感读走主节点。

### 13.2 哨兵与故障转移

- 哨兵解决高可用（监控、自动故障转移、通知客户端新主地址），不解决分片；`sentinel monitor mymaster host port 2` 的 `2` 是判定主主观下线所需哨兵票数。
- 故障转移流程：检测到主下线（主观下线）→ 多哨兵协商确认客观下线 → 选新主 → 从节点重指向新主 → 通知客户端。

```
主观下线 → 多哨兵确认客观下线 → 选新主 → 重指向 → 通知客户端
```

- 哨兵模式下客户端必须通过哨兵发现主节点地址，不能写死 IP。

### 13.3 Cluster 与哈希槽

- Cluster 同时解决分片与高可用：数据分到 16384 个哈希槽、`CRC16(key) % 16384` 定位节点，每分片有主从，节点间靠 Gossip 协议通信，支持水平扩展。
- 相比哨兵多了自动分片；槽太少单节点数据量大、扩缩容粒度粗，槽太多槽位同步开销大；多 key 原子操作用 `{tag}` 哈希标签强制同槽（牺牲分布均匀），扩容时按槽迁移、客户端收到 `MOVED` 应更新本地槽缓存。

### 13.4 高级数据类型

- Bitmap 做日活：`SETBIT user:日期 用户ID 1` 记录访问、`BITCOUNT` 统计当天人数，内存占用极小。
- HyperLogLog 做 UV：`PFADD`/`PFCOUNT` 统计独立用户数、固定只占 12KB、误差约 0.81%，`PFMERGE` 合并。
- GEO 做地理位置：`GEOADD` 存坐标、`GEODIST` 算两点距离、`GEORADIUS` 查半径内目标，底层复用 ZSet。
- Stream 做消息队列：Redis 5.0+ 提供，支持持久化、消费组与 ACK；`XADD` 生产、`XREADGROUP` 消费、`XGROUP CREATE` 建消费组；List 做队列消费者崩溃时会丢消息。

### 13.5 安全与性能调优

- 安全配置：`requirepass` 设强密码、`bind` 只留内网地址、用 `rename-command` 禁用 FLUSHALL/FLUSHDB/CONFIG、改掉默认 6379 端口。
- 慢查询日志：`slowlog-log-slower-than 10000` 记录超 10ms 命令，`SLOWLOG GET` 查看、`SLOWLOG LEN` 数量、`SLOWLOG RESET` 清空。
- 多线程 IO：Redis 6.0 的 `io-threads` 只把网络 IO 读写多线程化，命令执行仍是单线程；适合网络 IO 密集场景，多数场景单线程已足够。

### 13.6 关键监控指标

- 四组 `INFO`：`INFO clients` 看连接数（含 `blocked_clients`）、`INFO memory` 看内存与碎片率、`INFO stats` 算命中率 `keyspace_hits / (hits + misses)`、`INFO commandstats` 看单命令 `usec_per_call` 耗时、`INFO replication` 的 `master_last_io_seconds_ago` 看复制延迟（> 30 秒表示延迟严重）。
