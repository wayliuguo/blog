## 一、基础概念

### Q1: INNER JOIN 和 LEFT JOIN 有什么区别？（数据库/01 篇）

- **结论**：INNER JOIN 只返回两表都匹配的行；LEFT JOIN 以左表为基准全部返回，右表无匹配补 NULL。
- **原理**：INNER JOIN 取交集，任一侧不满足关联条件就不出现在结果里；LEFT JOIN 保留左表全集，相当于"以左表为主体的可选关联"。
- **场景**：查"订单对应的用户"用 INNER JOIN；查"所有用户及其订单（含零订单用户）"必须用 LEFT JOIN，否则零订单用户会被静默丢掉。
- **边界/追问**：`LEFT JOIN ... WHERE 右表.列 = 'x'` 会把外连接退化成内连接，右表条件要写进 `ON` 才是"先关联再筛选"的语义。

### Q2: 主键和外键有什么区别？为什么生产环境常不用物理外键？（数据库/01 篇）

- **结论**：主键唯一标识一行、不能为 NULL、一表只有一个；外键指向另一张表的主键、可以为 NULL、可以有多个。
- **原理**：主键保证实体完整性（InnoDB 里主键就是聚簇索引，决定数据物理顺序）；外键保证引用完整性，写入时会加锁校验父表记录。
- **边界/追问**：外键校验会带来额外锁、阻碍批量导入与分库分表，所以生产中常用应用层校验或异步对账替代。另外主键优先用自增 `BIGINT` 而不是 UUID，随机主键会让 B+ 树频繁页分裂。

### Q3: CHAR 和 VARCHAR 怎么选？金额字段为什么必须用 DECIMAL？（数据库/01 篇）

- **结论**：CHAR 定长、不足补空格、读写略快；VARCHAR 变长、按实际长度加 1~2 字节存储、更省空间。金额一律 `DECIMAL`。
- **原理**：`FLOAT`/`DOUBLE` 是二进制浮点，无法精确表示 0.1、0.2 这类十进制小数，多次累加会出现肉眼可见的误差；`DECIMAL(m,n)` 是十进制定点，精确且可控。
- **边界/追问**：长度稳定的字段（手机号、身份证、MD5）用 CHAR 更省开销；`VARCHAR` 本身上限 65535 字节，长文本应改用 TEXT。

### Q4: DELETE、TRUNCATE、DROP 有什么区别？（数据库/01 篇）

- **结论**：DELETE 删除行，是 DML，可带 WHERE、可回滚、会触发触发器；TRUNCATE 清空表，是 DDL，不可回滚、会重置自增计数器；DROP 连表结构一起删。
- **原理**：DELETE 逐行删除并写 undo/redo，所以慢但可回滚；TRUNCATE 直接释放数据页并重建表结构，几乎不写逐行日志，所以快。
- **边界/追问**：要删掉大表绝大部分数据时，`DELETE` 会长时间持锁并产生巨量 undo，更稳的做法是"建新表灌数据 + 原子改名"或分批删除。

### Q5: 范式与反范式怎么取舍？（数据库/01 篇）

- **结论**：严格三范式减少冗余、但查询要更多 JOIN；适当反范式用冗余换查询性能，但要自己维护一致性。
- **原理**：1NF 每列不可再分；2NF 非主键列完全依赖主键；3NF 非主键列不依赖其他非主键列。反范式就是主动违反它们，把"每次查询都要 JOIN 的字段"冗余到主表。
- **场景**：订单项里冗余商品名与下单时单价，就是典型且必要的反范式——历史订单必须冻结当时的价格快照。
- **边界/追问**：反范式只用在"读多写少且允许短暂不一致"的地方；被冗余的字段一旦需要更新，就要保证所有副本同步改。

### Q6: WHERE 和 HAVING 有什么区别？（数据库/02 篇）

- **结论**：WHERE 在分组**之前**过滤行、不能用聚合函数；HAVING 在分组**之后**过滤组、可以用聚合结果。
- **原理**：SQL 的逻辑执行顺序是 `FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`，所以 WHERE 阶段还不存在聚合值。
- **边界/追问**：能放 WHERE 的条件不要留到 HAVING——越早缩小数据量，GROUP BY 与排序的代价越小。

### Q7: 聚簇索引和二级索引（非聚簇索引）有什么区别？（数据库/02 篇）

- **结论**：InnoDB 主键索引即聚簇索引，叶子节点存整行数据，一张表只有一个；二级索引叶子节点只存"索引列 + 主键值"，查非索引列需要**回表**。
- **原理**：数据按主键顺序物理组织，所以主键等值查询定位到叶子即拿到整行；走二级索引只能拿到主键，还要再走一次聚簇索引取其余列。
- **边界/追问**：这正是"自增主键优于随机主键"的原因——有序插入顺序落盘，减少页分裂与碎片。

### Q8: 什么是数据库连接池？为什么用池而不是每次新建连接？（数据库/03 篇）

- **结论**：连接池维护一组已建立的连接，请求时借出、用完归还，避免反复创建销毁。
- **原理**：建立连接要走 TCP 握手、认证、权限加载，是重量级操作；池化后单次获取几乎无成本，并把并发连接数收敛在可预期范围内，防止把数据库连接数打满。
- **边界/追问**：连接数不是越多越好，`(CPU 核心数 × 2) + 有效磁盘数` 是常见起点；池太大反而让 MySQL 在线程调度上耗掉更多时间。核心参数是 `connectionLimit`、`queueLimit`、`acquireTimeout`、`idleTimeout`。

### Q9: MongoDB 和 MySQL 分别适合什么场景？（数据库/05 篇）

- **结论**：结构化、强事务、需复杂关联的业务（账户、订单、财务）选 MySQL；结构灵活、写入频繁、几乎不做多表关联的数据（日志、评论、配置、运行记录）选 MongoDB。
- **原理**：MySQL 有固定 Schema、成熟的 JOIN 优化器与事务；MongoDB 无 Schema、文档模型贴近对象、靠分片横向扩展。
- **边界/追问**：两者的强弱恰好互补，常见组合是 MySQL 存核心交易数据、MongoDB 存日志与衍生数据；MongoDB 4.0 之后虽有多文档事务，但性能开销明显高于 MySQL，不能因此认为它可以替代关系库。

### Q10: MongoDB 的文档（Document）和集合（Collection）是什么？（数据库/05 篇）

- **结论**：文档是基本数据单元（类比"行"），以 BSON 存储，可嵌套子文档与数组；集合是文档的容器（类比"表"），无需预定义结构。
- **原理**：BSON 是二进制 JSON，除 JSON 类型外还支持日期、ObjectId、二进制、长整型等，序列化/反序列化更快；集合在首次插入时自动创建。
- **边界/追问**：同一集合内的文档结构允许不同（Mongoose 的 Schema 只是应用层约束），但结构混用会让索引与聚合难以维护，工程上仍应统一。

### Q11: Mongoose 里 Schema 和 Model 是什么关系？（数据库/05 篇）

- **结论**：Schema 定义结构与规则（字段类型、必填、默认值、唯一约束、索引、钩子），Model 是 Schema 编译出来的构造函数，提供 `find` / `create` / `updateOne` / `deleteOne` 等 CRUD 接口。
- **原理**：一个 Model 对应一个集合，所有写入都会经过 Schema 的类型转换、校验与默认值填充。
- **边界/追问**：修改 Schema 不会改变已存在的数据，只影响之后的读写解释；`pre('save')` 这类钩子挂在 Schema 上、由 Model 触发，适合做密码哈希、时间戳维护。

### Q12: 嵌入文档和引用（reference）两种建模方式怎么选？（数据库/05 篇）

- **结论**："总是一起查、一起改、数量可控"的子数据用嵌入（一次查询拿全）；"独立变化、可能被单独查询、数量会膨胀"的用引用（存 ObjectId，查询时 `populate`）。
- **原理**：嵌入省掉关联查询但有数据冗余，且单文档上限 16MB；引用无冗余，但要么二次查询要么走 `$lookup`，读放大明显。
- **边界/追问**：经验法则是"一对少、读多写少 → 嵌入；一对多/多对多、写频繁 → 引用"。拿不准时按访问模式判断：能否一次查询满足页面需求。

### Q13: ObjectId 由哪些部分组成？有什么优势？（数据库/05 篇）

- **结论**：12 字节 = 4 字节时间戳 + 5 字节机器标识 + 2 字节进程号 + 3 字节计数器。
- **原理**：时间戳放在最高位，所以 ObjectId 整体**趋势递增**，可以近似当作创建时间用于排序；客户端可自行生成，不需要向数据库申请号，天然适配分布式写入。
- **边界/追问**：趋势递增意味着它适合做主键（不像随机 UUID 那样破坏索引局部性），但同一秒内的高并发仍靠最后 3 字节计数器区分。

### Q14: TTL 索引的原理和适用场景是什么？（数据库/05 篇）

- **结论**：给日期字段建 `expireAfterSeconds` 索引后，MongoDB 会定期删除超过该时长的文档，实现数据自动过期。
- **原理**：后台线程每约 60 秒扫描一次并删除过期文档，所以删除不是瞬时精确的，会有分钟级延迟。
- **场景**：会话数据、验证码、访问日志、临时缓存这类"有明确生命周期、过期即可丢弃"的数据。
- **边界/追问**：TTL 删除同样产生写入负载，日志量很大时更推荐"按日期分集合，过期整体 `drop()`"，成本远低于逐条删除。

### Q15: PostgreSQL 的 JSONB 和 MySQL 的 JSON 有什么区别？为什么业务常用 JSONB？（数据库/07 篇）

- **结论**：JSONB 解析后以二进制存，支持 GIN 索引做包含与键查询；JSON 原样存文本，每次取值都要解析，很难高效索引。
- **原理**：`payload @> '{"tool":"sql_query"}'` 这类包含判断可走 GIN 倒排索引；取值时 `->` 返回 JSON 类型，`->>` 返回文本。也可以只对某个键建索引（`USING GIN ((payload -> 'tool'))`）以省空间。
- **边界/追问**：结构稳定、需要联表的字段仍应建成普通列；只有随业务演进、需要灵活检索的元数据才用 JSONB，切忌把主键/外键塞进 JSONB。

### Q16: 什么时候该用 PostgreSQL 而不是 MySQL？（数据库/07 篇）

- **结论**：需要 JSONB 灵活建模、复杂窗口函数/CTE 分析、地理信息，或需要原生向量相似度检索时选 PG；纯交易型业务 MySQL 足够且运维更简单。
- **原理**：PG 类型系统更严格（UUID、ARRAY、ENUM、JSONB），扩展机制强（PostGIS、pgvector、fdw），索引家族更宽（B-Tree / GIN / GiST / 部分索引 / 表达式索引）。
- **边界/追问**：团队熟悉度与运维成本同样是选型项；常见组合是"MySQL 管账户与订单 + PG 管半结构化运行数据与相似度检索"，而不是二选一。

### Q17: Redis 的 String 和 Hash 分别适合什么场景？（Redis/01 篇）

- **结论**：String 适合整体读写的小对象、计数器、分布式锁；Hash 适合"对象"，可以只改一个字段而不动整份数据。
- **原理**：String 存对象需要整体序列化/反序列化；Hash 用 `HSET` / `HGET` 精确到字段，省带宽也省编解码开销，还能配合 `HINCRBY` 做字段级计数。
- **边界/追问**：Hash 字段很多时会从紧凑编码退化成哈希表、内存开销上升，这也是"大 Hash 要拆"的根因。分布式锁用 String（`SET ... NX EX`），不要用 Hash。

### Q18: Redis 的 List、Set、ZSet 分别适合什么场景？（Redis/01 篇）

- **结论**：List 有序可重复，做队列与时间线；Set 无序去重，做标签、共同好友、去重统计；ZSet 带分数排序，做排行榜、延时队列、滑动窗口限流。
- **原理**：List 底层是双向链表/quicklist，两端出入均 O(1)；Set 底层是 intset 或 hashtable，支持交并差运算；ZSet 用跳表 + 字典，按分数范围与排名查询都很高效。
- **边界/追问**：做消息队列要 ACK 和消费组就用 Stream——List 的 `LPOP` 在消费者崩溃时会直接丢消息。

### Q19: Redis 适用哪些场景？不适用哪些场景？（Redis/01 篇）

- **结论**：适用热点缓存、计数器、排行榜、分布式锁、限流、会话共享、轻量消息队列；不适用大容量持久化存储、强事务、复杂多表关联查询。
- **原理**：数据全内存，容量受内存成本限制；命令单线程串行执行，没有回滚、隔离级别与 JOIN 语义。
- **边界/追问**：判断标准是"这份数据能不能丢、能不能重建"——能重建的放 Redis，不能丢的必须落库，Redis 只作为加速层。

### Q20: RDB 和 AOF 有什么区别？生产怎么选？（Redis/02 篇）

- **结论**：RDB 是定时快照，文件紧凑、恢复快，但会丢最后一次快照之后的数据；AOF 追加写命令，`everysec` 下最多丢 1 秒，但文件更大、恢复更慢。生产建议同时开启，或用 Redis 4.0+ 的混合持久化。
- **原理**：RDB 靠 `BGSAVE` fork 子进程写 dump.rdb；AOF 的落盘频率由 `appendfsync` 决定（`always` 最安全最慢、`everysec` 默认、`no` 最快最不安全），文件膨胀后由 `BGREWRITEAOF` 重写压缩；混合持久化（`aof-use-rdb-preamble yes`）把 RDB 快照当作 AOF 文件前缀，兼顾恢复速度与数据安全。
- **边界/追问**：纯缓存场景可以只开 RDB 甚至不开持久化；数据量大时 `fork` 的瞬时内存与延迟抖动要提前评估。

### Q21: Redis 的过期键删除策略是什么？（Redis/02 篇）

- **结论**：惰性删除 + 定期删除的组合拳。
- **原理**：惰性删除是访问 key 时才检查是否过期、过期则删；定期删除是每 100ms（频率由 `hz` 控制）随机抽查一批设置了 TTL 的 key，删掉其中已过期的，避免全量扫描。
- **边界/追问**：抽查是随机的，因此过期 key 可能长期滞留占内存，最终靠内存淘汰策略兜底——这就解释了"明明设了 TTL，内存却没降下去"。

### Q22: Redis 的内存淘汰策略有哪些？缓存场景用哪个？（Redis/02 篇）

- **结论**：共 8 种。缓存场景最常用 `allkeys-lru`；只想淘汰带 TTL 的 key 用 `volatile-lru` / `volatile-lfu` / `volatile-ttl`；绝不允许丢数据的场景用默认 `noeviction`（内存满后写请求直接报错）。
- **原理**：LRU 看"最近有没有被访问"，LFU 看"被访问的频次"，热点相对稳定时 LFU 命中率更高但需要更多元数据。
- **边界/追问**：淘汰只在达到 `maxmemory` 后触发，务必给 `maxmemory` 留出 fork 与内存碎片的余量；`evicted_keys` 持续增长说明容量不足，应该扩容而不是继续调策略。

### Q23: 什么是 Big Key？判定标准和危害是什么？（Redis/02 篇）

- **结论**：单个 key 存储的数据过大。粗略判定：String 超过 10KB，或 Hash/List/Set/ZSet 超过 5000 个元素。
- **原理**：Redis 命令执行是单线程的，读写或删除大 key 会长时间占用主线程，导致其他请求排队；集群模式下还会造成内存倾斜与跨节点大包传输。
- **解决**：拆分成多个小 key（如 `user:1:orders:202401`）、对大 JSON 压缩后存储、删除用 `UNLINK` 异步回收而不是 `DEL`。
- **边界/追问**：排查用 `redis-cli --bigkeys`，但它要扫描全库、有明显性能影响，生产应低峰执行或在从节点执行。

### Q24: Redis 事务和 MySQL 事务有什么不同？（Redis/02 篇）

- **结论**：Redis 用 `MULTI` / `EXEC` 把命令打包，但**不支持回滚**——语法错误导致整批不执行，运行时错误只影响出错那一条，其余命令照常生效。
- **原理**：命令在 `EXEC` 前只是入队，没有隔离级别、没有 undo 机制；要"先检查再修改"的原子语义，得靠 `WATCH` 乐观锁或 Lua 脚本。
- **边界/追问**：需要真正原子的复合操作（扣库存、释放锁）一律用 Lua 脚本；`MULTI` 只适合"我不关心中途出错、只想一次发完"的批量场景，那其实用 Pipeline 更合适。

## 二、机制与原理

### Q25: 最左前缀原则是怎么回事？（数据库/02 篇）

- **结论**：联合索引 `(a, b, c)` 的排序是"先按 a 排，a 相同再按 b，b 相同再按 c"，所以查询条件必须从最左列开始且中间不能断，断掉的列及其右侧列都用不上索引。
- **原理**：B+ 树只能沿有序维度定位。`WHERE a = 1` 能用；`WHERE a = 1 AND b = 2` 能用；`WHERE a = 1 AND c = 3` 只有 a 生效；`WHERE b = 2` 完全用不上。
- **延伸**：最左前缀同样约束排序——`ORDER BY a, b` 能复用索引排序，`ORDER BY b` 不行。
- **边界/追问**：设计联合索引的顺序按"几乎每次都带的等值列在最左 → 区分度高的在前 → 范围列靠后 → 排序列放末尾"排；范围列后面的索引列会失效，别把范围条件夹在中间。

### Q26: MVCC 是什么？InnoDB 如何靠它实现可重复读？（数据库/02 篇）

- **结论**：MVCC（多版本并发控制）让"读不阻塞写、写不阻塞读"，可重复读就建立在它之上——同一事务内多次读取结果一致，且读取不需要加锁。
- **原理**：每行记录有两个隐藏字段，`DB_TRX_ID`（最近修改它的事务 ID）和 `DB_ROLL_PTR`（回滚指针，指向 undo log 里的上一版本），所有版本串成一条版本链；事务首次查询时生成 Read View（当前活跃事务 ID 的快照），之后只读"创建时间早于自己"的版本。
- **边界/追问**：可重复读只在**第一次查询**时创建 Read View 并复用；读已提交则每次查询都重建，所以同一事务内两次读可能不同。另外 MVCC 只解决快照读，写冲突仍要靠锁。
- **追问预判**：undo log 何时清理？——没有更早的 Read View 再需要它时，由 purge 线程回收。

### Q27: InnoDB 在可重复读隔离级别下怎么避免幻读？（数据库/02 篇）

- **结论**：两条腿走路——**快照读**用 MVCC 的 Read View 保证看不到新插入的行；**当前读**用 Next-Key Lock（行锁 + 间隙锁）锁住扫描范围内的记录与间隙，阻止别人插入。
- **原理**：普通 `SELECT` 走快照读，读的是事务开始时的版本，自然不会出现"两次查询行数不同"；`SELECT ... FOR UPDATE` / `UPDATE` / `DELETE` 走当前读，会在扫描到的索引区间上加 Next-Key Lock。
- **边界/追问**：间隙锁**只在可重复读生效**，读已提交只有行锁；间隙锁会显著降低并发（尤其范围查询密集时），若业务不需要防幻读可以降级到读已提交换取吞吐。

### Q28: 什么是覆盖索引？为什么能提升性能？（数据库/02 篇）

- **结论**：查询要用到的列全部包含在索引里，不需要回表，`EXPLAIN` 的 `Extra` 会显示 `Using index`。
- **原理**：二级索引叶子节点只存"索引列 + 主键值"，若 `SELECT` 的列都在其中，MySQL 直接从索引树返回数据，省掉逐行回聚簇索引的随机 I/O——这是最容易见效的优化之一。
- **边界/追问**：`SELECT *` 几乎必然破坏覆盖索引；也要注意覆盖索引会让索引变宽、写入变慢，只对高频查询建立。它与联合索引的关系是"联合索引恰好覆盖了所有需要的列"。

### Q29: 什么是索引下推（ICP）？（数据库/02 篇）

- **结论**：MySQL 5.6+ 把 WHERE 中能用上索引字段的过滤条件下推到存储引擎层，在遍历索引时就筛掉不满足的行，只对通过的行回表。
- **原理**：联合索引 `(name, age)` 下执行 `WHERE name LIKE 'A%' AND age = 18`——无 ICP 时按 name 范围找到所有命中的行、逐行回表再过滤 age；有 ICP 时在索引遍历阶段就直接判断 age，回表次数大幅下降。
- **边界/追问**：`EXPLAIN` 的 `Extra` 显示 `Using index condition`；ICP 对聚簇索引无意义（本来就不需要回表）。它和覆盖索引的区别是：ICP 减少**回表次数**，覆盖索引是**完全不回表**。

### Q30: 快照读和当前读有什么区别？（数据库/02 篇）

- **结论**：普通 `SELECT` 是快照读，读事务开始时的版本、不加锁；`SELECT ... FOR UPDATE`、`LOCK IN SHARE MODE`、`UPDATE`、`DELETE` 是当前读，读最新已提交版本并加锁。
- **原理**：这是"防超卖"的基石——只有当前读才能保证"读到的值"和"接下来要改的值"是同一份并被自己独占。
- **常见误区**：以为"我刚 UPDATE 了别人就一定看得到"——可重复读下别的事务的普通 `SELECT` 仍看旧版本；以为"`FOR UPDATE` 只是加锁"——它同时把读升级为当前读。
- **边界/追问**：写并发控制逻辑时一律用当前读（或者干脆把判断下推到 `UPDATE ... WHERE` 里用 `affectedRows` 判断），别依赖快照读。

### Q31: SQL 的逻辑执行顺序是怎样的？EXISTS 和 IN 怎么选？（数据库/02 篇）

- **结论**：执行顺序是 `FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`。
- **用途**：这条顺序解释了为什么 WHERE 里不能用 SELECT 中定义的别名（此时还没执行到 SELECT），但 ORDER BY 里可以用。
- **EXISTS vs IN**：外层表小、子查询结果集大 → 用 `EXISTS`（逐行判断，子查询找到第一条即返回）；外层表大、子查询结果集小 → 用 `IN`（子结果集可缓存，外层走索引匹配）；关联子查询（子查询依赖外层列）只能用 `EXISTS`。
- **边界/追问**：MySQL 8.0 优化器会把很多 `IN` 改写成半连接（semi-join），实测差异可能被抹平，最终仍以 `EXPLAIN` 为准。

### Q32: 主从复制的原理是什么？Binlog 有哪几种格式？（数据库/03 篇）

- **结论**：主库把变更写入 Binlog，dump 线程推送给从库；从库 I/O 线程写入 Relay Log，SQL 线程重放，完成同步。Binlog 三种格式：`STATEMENT`（记录 SQL）、`ROW`（记录行变更，生产推荐）、`MIXED`（混合）。
- **原理**：`ROW` 记录每行的前后镜像，因此 `NOW()`、`UUID()` 这类非确定性函数不会导致主从数据不一致，代价是批量更新时日志量显著变大；`STATEMENT` 日志小但存在不一致风险；`MIXED` 默认用 STATEMENT、遇到不确定语句自动切 ROW。
- **配置要点**：主从 `server_id` 必须不同；从库设 `read_only = 1` 防误写；主库建议 `sync_binlog = 1` 保证提交即落盘；级联复制要开 `log_slave_updates`。
- **边界/追问**：复制是异步的（默认），所以从库可能落后；要减少丢数据风险可用半同步复制，但要接受写延迟上升。

### Q33: 分库分表后，全局唯一 ID 怎么生成？（数据库/03 篇）

- **结论**：主流四方案——雪花算法（趋势递增、高性能，但依赖机器时钟）、Redis `INCR`（实现简单，但依赖外部组件）、数据库号段（批量取号本地分配，不依赖外部组件）、UUID（全局唯一但无序且过长，不适合做聚簇索引主键）。
- **原理**：雪花 ID 是 64 位长整型：1 位符号 + 41 位毫秒时间戳 + 10 位机器号 + 12 位序列号，本地生成、无网络开销，且整体趋势递增。号段模式靠 `UPDATE id_generator SET max_id = max_id + 1000` 批量领号，在应用层内存分配。
- **边界/追问**：UUID 做主键会让 B+ 树频繁分裂、页利用率低；雪花算法要处理**时钟回拨**（等待追平、改用备用机器号、或直接拒绝服务）；号段模式要接受"机器重启丢弃未用号段"造成的空洞。

### Q34: 什么是 N+1 查询？为什么会产生？（数据库/04 篇）

- **结论**：先查 1 次拿到 N 条主记录，再循环对每条发起 1 次关联查询，总共 1 + N 次——本质是 ORM 懒加载把"一次关联"拆成了 N 次网络往返。
- **原理**：每次查询都要付网络往返 + 解析 + 执行的开销，N 大时总耗时线性上涨。开发环境数据量小、本地延迟低，往往察觉不到，上线高并发后立刻成为瓶颈。
- **解决**：改成一次性关联查询——TypeORM 用 `find({ relations: ['orders'] })` 或 `createQueryBuilder().leftJoinAndSelect()`；Mongoose 用 `populate`；或者先批量查出所有关联记录，再在内存里按外键分组拼装。
- **边界/追问**：`populate` 本质仍是多次查询，只是把 N+1 降为 2 次；数据量特别大时手写 JOIN 或 `$lookup` 更稳。检测手段是在开发期开启 SQL 日志、统计同一请求内的查询条数。

### Q35: ORM 和直接写 SQL 各有什么取舍？（数据库/04 篇）

- **结论**：ORM 开发效率高、参数化查询天然防注入、类型安全、便于迁移；但复杂查询难以表达、性能是黑盒。直接写 SQL 性能可控、执行计划一目了然；但代码量大、需要自己保证参数化。
- **原理**：ORM 把对象操作翻译成 SQL，复杂统计常生成低效语句，且难以预料实际执行计划；原生 SQL 能精确控制 JOIN 顺序、索引使用与分页方式。
- **边界/追问**：工程上的默认答案是混合——简单 CRUD 走 ORM，报表/批量/复杂聚合走原生 SQL；主流 ORM 都提供 `query()` / `$queryRaw` 逃生口。用原生 SQL 时务必用占位符而不是字符串拼接。

### Q36: PostgreSQL 的 MVCC 和 MySQL 有什么不同？表膨胀从哪来？（数据库/07 篇）

- **结论**：MySQL 的旧版本放在 undo log（独立段），由后台 purge 线程自动回收；PG 的旧行**留在数据表本身**变成 dead tuple，必须靠 `VACUUM` 回收。频繁 UPDATE/DELETE 又不及时 VACUUM，死元组堆积就造成表膨胀、查询变慢。
- **原理**：PG 的 UPDATE 本质是"把旧行标记失效 + 插入新行"，行内用 `xmin`/`xmax` 记录可见性；MVCC 的读语义相似，回收方式完全不同。
- **边界/追问**：长事务会阻塞 VACUUM、让死元组持续堆积；用 `VACUUM (ANALYZE, VERBOSE)` 手动回收并更新统计信息。所以 PG 慢不一定是 SQL 写错，可能是没做 VACUUM。

### Q37: 部分索引和表达式索引解决什么问题？（数据库/07 篇）

- **结论**：部分索引只对满足条件的行建索引（如 `WHERE status = 'running'`），体积更小、写入更快；表达式索引对函数结果建索引（如 `lower(email)`），让函数条件也能走索引。
- **原理**：绝大部分运行记录都是 `finished`、只有 `running` 常被查，全列索引里大部分条目从未被使用，纯粹拖慢写入。
- **边界/追问**：MySQL 没有部分索引，只能用联合索引或前缀索引近似；MySQL 想对 `lower(email)` 建索引要走"生成列 + 索引"。两者都要求查询条件与索引定义**完全匹配**才会被使用。

### Q38: pgvector 的向量相似度检索是怎么跑的？（数据库/07 篇）

- **结论**：表里存一列定长向量 `VECTOR(1536)`，查询时用距离算子排序取 TopK。三个算子：`<=>` 余弦距离、`<->` 欧氏距离、`<#>` 内积，例如 `ORDER BY embedding <=> '[...]'::vector LIMIT 5`。
- **原理**：向量列上的索引决定检索速度——`IVFFlat` 需要先设候选列表数（`lists = 100`），适合百万级以内；`HNSW` 召回更准、构建更快，新项目直接用。索引的 ops 必须与距离算子对应（`vector_cosine_ops` 配 `<=>`），否则不会被使用。
- **工程要点**：向量维度必须与业务侧写入的定长浮点数组一致，改了维度就要重建表与索引；向量赋值与相似度查询都要走 raw query（ORM 表达不了 `<=>`），索引也需在迁移脚本里手写 `CREATE INDEX`。
- **边界/追问**：小数据量直接顺序扫描也够快，索引不是必须的；索引只做近似最近邻，追求精确结果时要用精确扫描。

### Q39: MongoDB 的 `$lookup` 和 MySQL 的 JOIN 有什么区别？（数据库/06 篇）

- **结论**：`$lookup` 功能上类似 LEFT JOIN，但它是聚合管道里**逐文档**去目标集合匹配，没有 JOIN 优化器，性能明显不如 MySQL 的 JOIN。
- **原理**：MySQL 的 JOIN 由优化器在 Nested Loop / Hash Join 之间选择执行计划，并可利用索引；`$lookup` 对每条输入文档都做一次查找，输入集合越大越吃亏。
- **边界/追问**：只支持左外连接语义，内连接/右连接要用 `$unwind` 等后续阶段模拟；频繁使用 `$lookup` 通常说明数据模型该改成嵌入。

### Q40: MongoDB 聚合管道的 `$match`、`$group`、`$sort` 怎么理解？（数据库/06 篇）

- **结论**：`$match` 过滤文档（类似 WHERE）、`$group` 按 `_id` 分组并用 `$sum`/`$avg`/`$max` 等累加器聚合、`$sort` 排序（1 升序、-1 降序）。
- **原理**：管道分阶段执行，每个阶段产出一个新的文档集合，所以**阶段顺序直接决定性能**：`$match`、`$sort` 越靠前越能利用索引、越早缩小数据量；`$project` 提前裁掉不需要的字段也能省内存。
- **边界/追问**：`$group`、`$sort` 会消耗内存，单阶段默认限额 100MB，超限要开 `allowDiskUse`；`$unwind` 把数组拆成多行，常与 `$lookup` 配合使用。

### Q41: Redis 为什么快？（Redis/01 篇）

- **结论**：四条原因——数据全在内存；命令单线程串行执行，没有锁竞争与线程上下文切换；用 IO 多路复用（epoll）扛住大量并发连接；底层数据结构为场景专门优化（SDS、跳表、压缩列表）。
- **原理**：单线程并不是瓶颈所在——真正的瓶颈是网络带宽与内存，省掉线程协调反而更快更简单。Redis 6.0 之后把网络读写也拆成多线程，但命令执行仍是单线程。
- **边界/追问**：正因为单线程，一条慢命令（`KEYS *`、遍历大 key、复杂 Lua）会阻塞所有客户端，这才是 Redis 性能问题的头号来源。

### Q42: Redis 为什么是 16384 个哈希槽？（Redis/01 篇）

- **结论**：16384 = 2^14，槽位号用 14 位就能表示，节点间交换槽位映射与心跳包更省带宽，同时节点规模（上千节点）也足够用。
- **原理**：`HASH_SLOT = CRC16(key) % 16384`。槽太少则单节点数据量过大、扩缩容粒度粗；槽太多则节点间同步槽位信息的开销变大。
- **边界/追问**：需要多 key 原子操作时可以用 `{tag}` 哈希标签把相关 key 强制落到同一个槽，但会牺牲分布均匀性；扩容时按槽迁移，客户端收到 `MOVED` 重定向后应更新本地槽位缓存。

### Q43: String 为什么用 SDS 而不是 C 字符串？（Redis/01 篇）

- **结论**：SDS（Simple Dynamic String）自带 `len` 与 `free` 字段——取长度 O(1)；按策略预分配、减少内存重分配次数；二进制安全，可存任意字节（包括 `\0`）；兼容部分 C 字符串函数。
- **原理**：C 字符串以 `\0` 结尾，取长度要遍历、也无法保存含 `\0` 的二进制内容；SDS 追加时按"小于 1MB 翻倍、大于 1MB 每次加 1MB"策略扩容，并用惰性释放避免频繁缩容。
- **边界/追问**：这些设计直接支撑了 Redis 把 String 当"二进制安全的字节容器"使用——缓存序列化对象、图片、协议数据都没有问题。

### Q44: Pipeline 和 Lua 脚本分别解决什么问题？（Redis/03 篇）

- **结论**：Pipeline 把多条命令一次性发出、一次性收回，减少网络往返，但**不保证原子性**；Lua 脚本在服务端原子执行，**保证整段逻辑不被打断**。
- **原理**：Pipeline 只是打包传输，命令之间仍可能插入其他客户端的命令（所以严格说它提供的是"批量"而不是"事务"）；Lua 由单线程一次性执行完整个脚本，中间不会切走。
- **边界/追问**：库存扣减、分布式锁的安全释放必须用 Lua（"先比较再删除"是复合判断）；批量灌数据、批量读用 Pipeline。Lua 脚本要尽量短，长脚本同样会阻塞主线程。真正的火山级批量可用 `redis-cli --pipe` 之类的离线方式。

### Q45: Redis 6.0 的多线程 IO 是怎么回事？（Redis/05 篇）

- **结论**：多线程**只用于网络读写**（解析请求、回写响应），命令执行仍然是单线程。
- **原理**：配置 `io-threads`（建议不超过 CPU 核心数）与 `io-threads-do-reads yes`；适合连接数极多、网络 IO 成为瓶颈的场景。
- **边界/追问**：如果是命令本身慢（大 key、`KEYS`）或 CPU 密集，多线程 IO 完全没帮助；多数场景单线程已经足够，不必开启。

### Q46: Redis 主从复制的流程是怎样的？（Redis/05 篇）

- **结论**：从节点发 `PSYNC` → 主节点 `BGSAVE` 生成 RDB 快照 → 发送给从节点加载 → 之后主节点持续把写命令同步给从节点（增量复制）。
- **原理**：复制的作用有三：读写分离分担读压力、从节点作为数据备份、作为高可用的基础（主节点故障后从节点可被提升为主）。
- **边界/追问**：复制默认是异步的，所以从节点可能读到旧数据（主从延迟），对一致性敏感的读要走主节点；配置项是 redis.conf 里的 `replicaof <host> <port>`。

## 三、排障与选型

### Q47: 索引失效的常见场景有哪些？（数据库/02 篇）

- **结论**：底层原因只有一个——**索引列在 WHERE 里被"改造"了**，导致无法按原有顺序走 B+ 树。
- **五种典型**：① 隐式类型转换，`phone` 是 VARCHAR 却写 `phone = 13800138000`（MySQL 把列转成数字，等价于在列上套函数）；② 函数作用在列上，`DATE(created_at) = '2024-01-01'` 应改成范围 `created_at >= ? AND created_at < ?`；③ 运算作用在列上，`amount * 1.1 > 100` 应改写成 `amount > 100 / 1.1`；④ 前缀模糊 `LIKE '%张三'`，只能用后缀模糊 `LIKE '张三%'`，或改上全文索引/搜索服务；⑤ OR 条件里有未索引列，可用 UNION 拆开或给另一列也建索引。
- **边界/追问**：`!=` 与 `NOT IN` 通常也不走索引，因为优化器认为全表扫描更划算；低区分度列（只有两三种取值的 `status`）单独建索引几乎不会被使用，应放进联合索引当补充列。
- **实测手段**：拿真实数据量跑 `EXPLAIN`，别在小表上验证——数据量不足时优化器一律选全表扫描。

### Q48: `EXPLAIN` 的 `type` 字段怎么排序？重点看什么？（数据库/02 篇）

- **结论**：性能从优到劣 `system > const > eq_ref > ref > range > index > ALL`，日常优化目标是至少达到 `range`，绝不出现 `ALL`。
- **含义**：`const` 主键或唯一索引等值命中至多一行；`eq_ref` 多表 JOIN 中被驱动表按主键/唯一索引匹配一行；`ref` 非唯一索引等值命中多行；`range` 索引范围扫描（`>`、`<`、`BETWEEN`、`IN`）；`index` 全索引扫描；`ALL` 全表扫描。
- **还要同时看**：`rows`（预估扫描行数，越小越好）、`key`（实际用了哪个索引）、`Extra`。
- **`Extra` 信号**：`Using index` 覆盖索引（好）；`Using index condition` 索引下推；`Using where` 需要在 Server 层再过滤；`Using filesort` 排序没走索引；`Using temporary` 用了临时表（常见于 GROUP BY）。后两者是需要优化的信号。

### Q49: 一条慢 SQL 的完整排查流程是什么？（数据库/02 篇）

- **结论**：发现 → 定位 → `EXPLAIN` → 优化 → 验证，五步闭环。
- **定位**：开启慢查询日志（`slow_query_log = ON`、`long_query_time = 1`、`log_queries_not_using_indexes = ON`），用 `pt-query-digest` 按总耗时排序，先处理最贵的那几条。
- **优化**：先在执行计划上判断属于哪一类——缺索引（按最左前缀建联合索引）、索引失效（改写条件）、写法问题（去掉 `SELECT *` 让覆盖索引生效、大偏移分页改游标分页、避免范围条件夹在联合索引中间）。
- **进阶手段**：大表 `COUNT(*)` 改走最小的二级索引或维护计数缓存；统计类查询加缓存；单表过大做冷热分离或归档；改表结构走 Online DDL 或 gh-ost。
- **边界/追问**：优化后必须复测 `rows` 与 `Extra` 是否变好，并确认没有让其它查询变差；只信真实数据量下的执行计划与耗时。

### Q50: 大表 DDL 怎么做才不影响线上？（数据库/03 篇）

- **结论**：MySQL 5.6+ 的 Online DDL 支持 `ALGORITHM=INPLACE, LOCK=NONE`，加索引、加列、删列、改默认值都不阻塞读写；千万级以上的表建议用 gh-ost 之类的外置工具做零停机改表。
- **原理**：gh-ost 建影子表 → 监听 Binlog 把增量同步到影子表 → 分批拷贝原表数据 → 原子改表名切换，全程原表可读写，且支持暂停与限速。
- **边界/追问**：改列类型、改主键仍需重建表（会锁表）；即便用 Online DDL，也要关注对磁盘 IO 与主从复制的冲击，安排在低峰并盯住延迟。

### Q51: 主从延迟怎么排查和解决？（数据库/03 篇）

- **结论**：在从库执行 `SHOW SLAVE STATUS`，重点看 `Seconds_Behind_Master`（延迟秒数）、`Slave_IO_Running` / `Slave_SQL_Running`（两个线程是否正常）、`Last_IO_Error` / `Last_SQL_Error`。
- **常见原因**：从库硬件（CPU/IOPS）弱于主库；主库存在大事务（一次删百万行）；从库自身有慢查询或锁等待；从库同时扛着读流量；跨机房部署的网络延迟。
- **解决**：升级从库硬件、把大事务拆成小批量、开启并行复制（`slave_parallel_workers` + `LOGICAL_CLOCK`）、延迟敏感的业务强制读主库。
- **边界/追问**：先区分是 I/O 线程落后还是 SQL 线程落后——前者是网络或主库推送压力，后者是从库重放慢，处理方向完全不同。

### Q52: 连接池溢出和连接泄漏怎么定位？（数据库/03 篇）

- **结论**：报 "Cannot get connection from pool" 或 `ER_CON_COUNT_ERROR` 时，先分清是"连接不够用"还是"连接被占着不放"。
- **区分方法**：看连接池的 `totalConnectionCount` / `activeConnectionCount` / `pendingRequestCount`——活跃数长期贴满且等待队列积压，多半是慢查询长期占用连接；空闲连接也持续增长不回收，才是真正的泄漏。
- **解决**：泄漏要检查"获取连接后是否在 `finally` 里 release"，或改用 `pool.query()` / `connection.execute()` 自动归还；被占满则先优化慢 SQL，再适度调大 `connectionLimit`。
- **边界/追问**：应用侧 `idleTimeout` 要小于 MySQL 的 `wait_timeout`（默认 8 小时），并开启 `enableKeepAlive`，否则空闲连接会被服务端单方面断开，下一次使用才报错。

### Q53: 分片键怎么选？时间戳分片为什么是坑？（数据库/03 篇）

- **结论**：分片键要同时满足三条——查询条件高频包含它、数据分布均匀、取值不可变。单调递增的时间戳是典型反面案例。
- **原理**：按时间分片会让所有新写入都落在最新分片（写热点），历史分片几乎无写入；按 `user_id` 哈希取模则写入天然分散，且同一用户的数据都在同一个分片，便于按用户维度查询。
- **常见选型**：用户系统按 `user_id`，订单系统按 `order_id` 或 `user_id`，消息系统用"时间 + user_id"（范围 + 哈希）实现冷热分离，地理位置按区域 ID 做范围分片。
- **边界/追问**：跨分片 JOIN、跨分片事务、无分片键的全分片扫描都要尽量避免；跨分片分页可用"每片取 N 条再汇总排序"，但数据量随分片数放大，更稳的是让查询带上分片键。MongoDB 侧同理，`sh.shardCollection` 一旦选定分片键几乎无法修改。

### Q54: 副本集和分片集群怎么选？副本集为什么建议奇数个节点？（数据库/06 篇）

- **结论**：副本集解决高可用与数据冗余（数据量单机能放下时用它）；分片集群解决水平扩展（数据量到 TB 级、单机放不下时用）。两者可组合——每个分片本身就是一个副本集。
- **为什么奇数**：主节点选举需要"大多数"节点同意。偶数节点（如 4 个）可能出现票数对等而选不出新主，形成脑裂；所以用 3、5 个，或者在 4 节点里加一个不存数据的仲裁节点凑成 5 个。
- **原理**：副本集由 Primary（唯一可写）、Secondary（异步复制、可读）、可选的 Arbiter（只参与选举）组成；分片集群由分片（存数据子集）、配置服务器（存元数据）、路由节点（客户端入口）组成，按分片键把数据分散到各分片。
- **边界与代价**：副本集写性能受限于单个主节点；分片集群运维复杂度明显更高，分片键选不好会数据倾斜或引发全分片扫描，属于"能不拆就不拆"的选项。

### Q55: 缓存穿透、缓存击穿、缓存雪崩的区别与各自解法？（Redis/04 篇）

- **结论**：三者后果都是数据库压力激增，但成因完全不同——穿透是"查一个根本不存在的数据"，击穿是"单个热点 key 过期瞬间"，雪崩是"大量 key 同时过期或 Redis 整体不可用"。
- **缓存穿透的解法**：缓存空值（带较短 TTL，如 60 秒）+ 布隆过滤器前置拦截，同时做参数合法性校验，拒绝明显非法的 ID。
- **缓存击穿的解法**：对回源加互斥锁（`SET NX`），只放一个请求去查库重建，其余等待后重试；超热 key 改为"逻辑过期 + 后台异步刷新"，避免硬 TTL 造成的瞬时回源。
- **缓存雪崩的解法**：TTL 加随机偏移（`基础值 + random * 300` 秒）打散失效时间；叠加本地内存缓存作为第一级；对数据库入口限流降级；Redis 侧用主从 + 哨兵或 Cluster 保证不整体崩。
- **边界/追问**：三类问题常同时出现，所以要组合防护而不是二选一；互斥锁本身必须带 TTL 并设置等待超时，否则持锁请求卡死会拖垮整条链路。

### Q56: 布隆过滤器的原理是什么？误判是怎么回事？（Redis/04 篇）

- **结论**：一个位数组加多个哈希函数。写入时把元素哈希出的多个位置置 1；查询时只要有任意一位是 0，就**一定不存在**；全是 1 则**可能存在**。
- **误判来源**：不同元素的哈希位互相覆盖，导致不存在的元素被误判为存在（假阳性）；但不会把存在的判成不存在（无假阴性）。
- **参数取舍**：位数组越大、哈希函数个数越合适，误判率越低，代价是内存与写入开销上升；元素只能加不能删，需要删除时得改用计数布隆过滤器。
- **边界/追问**：布隆过滤器只能挡住"明显不存在"的请求，误判仍会漏到数据库，所以它通常与"缓存空值"组合使用，而不是替代后者。数据批量变更后要注意重建过滤器。

### Q57: 缓存和数据库的一致性怎么保证？（Redis/04 篇）

- **结论**：主流方案是 Cache Aside——**读**：先查缓存，未命中查库并回写；**写**：先更新数据库，再删除缓存（删而不是改）。
- **为什么删而不是改**：更新缓存是一次真写操作，可能被一串无效更新白白消耗资源；删除是懒加载，等下次被读到时才回填，只有真正被读的数据才进缓存。
- **为什么先写库再删缓存**：反过来的"先删缓存再更新库"在并发读写下有窗口会留下旧值（读线程在库更新前把旧值回填）。
- **边界/追问**：要更强的一致性可用延迟双删（更新后延迟一小段时间再删一次），或把删除动作放进消息队列重试以保证"最终一定删掉"。强一致需要分布式锁或事务，代价是性能，多数业务取最终一致即可。

### Q58: Redis 分布式锁怎么实现？`SETNX` 有什么缺陷？（Redis/04 篇）

- **结论**：加锁用一条命令 `SET key value NX EX ttl`；释放锁必须用 Lua 脚本"先比较 value 再删除"，保证只释放自己的锁。
- **`SETNX` 的四个缺陷**：① `SETNX` 加 `EXPIRE` 是两步、非原子，中间进程崩溃就造成锁永不释放；② 不设 TTL 时持锁进程崩溃直接死锁；③ 到期后用 `DEL` 会误删别人的锁（自己的锁已过期、别人已拿到）；④ TTL 到期而业务还没跑完，锁会提前失效导致互斥失效。
- **原理**：`SET ... NX EX` 把"判断 key 不存在"与"设置过期时间"合并为一条原子命令；value 用唯一标识（请求号/UUID）标识持有者，释放时用 Lua 比对后再删。
- **边界/追问**：多节点场景用 Redlock（半数以上节点加锁成功且总耗时小于 TTL 才算成功），但它依赖各节点时钟基本一致、且不提供强一致性保证。业务执行时间不确定时可用看门狗续期；最好的实践是"锁 + 幂等"双保险，别把正确性全押在锁上。

### Q59: 什么是热点 Key？怎么解决？（Redis/02 篇）

- **结论**：某个 key 被极高并发访问，把承载它的那个节点 CPU 与带宽打满。判定参考：单 key QPS 上万，或集群中某节点 CPU 明显高于其他节点。
- **解决方案**：① 应用层加本地缓存、减少 Redis 访问；② 读写分离，把读请求分散到多个从节点；③ 把热点 key 复制成多份（`hot:key:1..N`）打散到不同分片；④ 对访问做限流，保护后端数据库。
- **边界/追问**：热点 key 常与"热点数据失效"耦合（即击穿），所以更适合配"逻辑过期 + 异步刷新"而不是硬 TTL。定位手段是 `redis-cli --hotkeys`（基于 LFU 统计）或代理层访问统计。

### Q60: 哨兵和 Cluster 有什么区别？分别适合什么数据量？（Redis/05 篇）

- **结论**：哨兵解决**高可用**（监控、自动故障转移、通知客户端新主地址），但不解决数据分片；Cluster 同时解决**分片与高可用**（16384 个槽 + 每片主从）。
- **原理**：哨兵是独立的一组进程，靠多数派判定主节点客观下线并选举新主（先主观下线，再多哨兵协商确认客观下线）；Cluster 用 Gossip 协议让节点互相通信、客户端按 `CRC16(key) % 16384` 路由，扩容时迁移槽位。
- **选型**：数据量小、只要高可用 → 主从 + 哨兵；数据量超过单机内存或需要水平扩展 → Cluster。两者的读写分离与自动故障转移都支持。
- **边界/追问**：Cluster 下跨槽的多 key 操作受限，要用 `{tag}` 保证相关 key 落在同一个槽，但会牺牲分布均匀；哨兵模式下客户端必须通过哨兵发现主节点地址，不能写死 IP。

### Q61: Redis 缓存命中率多少算正常？低了怎么提升？（Redis/05 篇）

- **结论**：一般应在 90% 以上，低于 80% 就该系统排查。计算方式是 `keyspace_hits / (keyspace_hits + keyspace_misses)`，从 `INFO stats` 取。
- **提升手段**：扩大缓存容量（减少被迫淘汰）、合理延长 TTL、上线或大促前做缓存预热、把淘汰策略从 LRU 换成 LFU。
- **诊断顺序**：先看是否有大量不存在的 key 在被空查（那是穿透问题），再看 TTL 是否太短导致反复回源，最后才考虑加内存。
- **边界/追问**：命中率高不等于没问题——命中率很高但单 key 极热，依然会打爆某个节点，所以要同时看单 key 的 QPS 分布。

## 四、场景设计题

### Q62: 设计一个基于 Redis 的缓存网关，支持失效策略与穿透防护（场景题）

- **题目要求**：为一批热点数据加上 Redis 缓存层，必须说清 Key 设计、数据结构选择、过期与失效策略、三类缓存故障的防护，以及回源一致性。
- **整体思路**：采用 Cache Aside 模式——读请求先查缓存，命中直接返回；未命中查库后回写缓存并设置 TTL；写请求先更新数据库，再删除对应缓存。
- **Key 设计**：
  - 冒号分层命名 `cache:{业务}:{实体}:{id}`，例如 `cache:user:profile:123`，便于按前缀排查与批量清理。
  - 冷热分离：热点数据用独立前缀（如 `hot:`），便于单独设置更长的 TTL 与预热策略。
  - 类型选择：整体读写的实体用 String 存 JSON；需要单独更新某几个字段的对象用 Hash，避免整体序列化。
  - 统一封装 `CacheService`，对外只暴露 `get<T>()` / `set()` / `del()`，序列化与异常吞并在内部收口。
  - 禁止业务代码直接拼 key，前缀与命名规范集中定义，避免同一份数据出现多个 key。
- **穿透防护**：
  - 布隆过滤器：启动或定时把所有存在的 ID 灌入，请求先过过滤器，判定不存在直接返回空，不查库。
  - 空值缓存：数据库查不到时也回写一个短 TTL（如 60 秒）的空值占位，避免同一个非法 ID 反复打库。
  - 入口参数校验：格式非法的 ID 在进业务逻辑之前就拒掉。
- **击穿防护**：
  - 回源前抢锁 `SET lock:{key} {reqId} NX EX 10`，抢到的负责查库并重建缓存，没抢到的短暂退避后重试读缓存。
  - 超热 key 改用"逻辑过期 + 后台异步刷新"，让失效发生在后台任务里，彻底避开硬 TTL 到期瞬间的回源尖峰。
- **雪崩防护**：
  - TTL 加随机偏移（`基础值 + random * 300` 秒）打散失效时间，避免同一时刻集体失效。
  - 叠加进程内本地缓存作为第一级，扛住 Redis 抖动的最初一跳。
  - 数据库入口限流降级；Redis 自身用主从 + 哨兵或 Cluster 保证不会整体不可用。
  - 对缓存层做健康探测，异常时整体切到"直连数据库 + 强限流"的降级模式，并保留人工开关。
- **为什么写路径是"删"而不是"改"**：删除是懒加载，只有真正被读到的数据才回填，避免一串无效更新白白消耗资源；而"先更新数据库、再删缓存"能规避并发读把旧值回填的窗口。要更强的一致性可延迟一小段时间再删一次（延迟双删），或把删除动作放进消息队列重试。
- **为什么这么设计**：三类故障的成因完全不同（查不存在的数据 / 单个热点失效 / 批量同时失效），防护手段必须一一对应，指望一种手段通吃会既浪费内存又挡不住真正的风险源。缓存网关的价值就在于把这三类防护、序列化与降级统一收口，业务代码只依赖一个稳定接口。
- **上线前自检**：热点数据是否已预热、布隆过滤器是否已加载全量 ID、互斥锁 TTL 是否覆盖最慢的业务耗时、降级开关是否能人工干预——四项确认完再放量。
- **边界与代价**：空值缓存会占用内存，还可能把"数据真的没了"与"暂时查不到"混为一谈，务必用短 TTL 并保留业务侧的存在性判断；互斥锁必须带 TTL 且有等待超时与降级为直接查库的兜底，否则一个卡住的请求会拖垮整条链路；布隆过滤器只能减少流量、不能做到 100% 拦截；本地缓存要额外考虑多实例之间的不一致与失效广播。

### Q63: 设计一个秒杀系统的库存扣减方案，防止超卖（场景题）

- **题目要求**：高并发下扣减商品库存，绝不能扣成负数，同时要扛住瞬时流量、保证最终账目准确。
- **分层思路**：Redis 做前置原子扣减，过滤掉绝大部分无效请求；消息队列削峰，把瞬时高峰摊平；数据库做最终一致性落账，真正决定库存盈亏。
- **库存预热**：
  - 活动开始前把库存写入 Redis（`SET goods:{id}:stock 100`），并给该 key 设置比活动时长更久的 TTL 作为兜底。
  - 预热要有校验：确认写入的库存值与数据库一致，避免超卖从源头就发生。
- **Redis 原子扣减**：
  - 用 Lua 脚本把"读库存 → 判断是否大于 0 → `DECR` → 返回结果"打包成一次原子执行，脚本在 Redis 端串行运行，天然不会超卖。
  - 库存不足直接返回失败，不进入任何后续流程，避免无效请求流向队列与数据库。
  - 不要把"先查再减"写成两条命令——两步之间其他请求会插进来，这正是扣成负数的经典原因。
  - 返回结果带上剩余库存，让前端能直接做售罄提示，减少无意义的重试流量。
- **异步削峰**：
  - 扣减成功的请求写入消息队列，接口立即返回"排队中"，前端轮询或推送查询结果。
  - 下游消费者按自己的消费能力拉取，把瞬间洪峰转换成平稳写入，避免数据库被直接打穿。
  - 排队结果要有明确的超时与取消语义，避免用户无限等待、也避免过期请求继续占用名额。
- **数据库落账**：
  - 消费者用条件更新保证最终一致：`UPDATE goods SET stock = stock - 1 WHERE id = ? AND stock > 0`。
  - 拿 `affectedRows` 做判断：为 1 表示成功；为 0 说明数据侧已无库存，需要回补 Redis 名额并触发告警。
  - 这与"把判断下推到 UPDATE 的 WHERE 里"是同一个套路，由数据库的行锁 + 当前读保证原子性。
  - 落账失败的消息进入重试队列，多次重试仍失败则人工介入，绝不能静默丢弃。
- **防重复扣减**：
  - 同一用户在同一活动内只允许扣一次，用 `SETNX seckill:user:{userId}:{activityId}` 去重（TTL 设为活动时长）。
  - 下单接口自身必须幂等，以订单号或请求号作为幂等键，避免消息重投造成重复下单。
- **为什么这么设计**：Redis 承担的是"过滤"而不是"记账"——它只决定谁有资格进入队列，真正的库存账目以数据库的原子条件更新为准。这样既有高并发吞吐，又不会出现"Redis 说成功、数据库扣不动"的数据漂移；MQ 的存在则把"瞬时并发"变成"可控速率"，让数据库始终工作在舒适区间。
- **边界与代价**：必须处理双向补偿（Redis 扣了但落库失败要回补名额，落库成功但回补遗漏要能通过对账发现）；消息队列要保证不丢（否则少卖）且下游必须幂等（否则超卖）；单个商品的库存 key 本身就是热点，QPS 极高时要考虑分桶或按库存分片；活动结束后要清理临时 key 并与数据库对账。

### Q64: 设计一套慢 SQL 排查与优化流程（场景题）

- **题目要求**：线上接口响应变慢、怀疑是数据库问题，要求给出可直接执行的排查与优化流程，而不是一句"加索引"。
- **整体流程**：确认范围 → 抓出慢语句 → 读执行计划 → 分类优化 → 验证与防回归，五步闭环，每一步都要有可观测的产出。
- **第一步 · 确认问题范围**：
  - 单个接口慢、某类查询慢，还是全局变慢？全局变慢要先怀疑连接池耗尽、锁等待或机器负载，而不是逐条看 SQL。
  - 对齐时间线：是不是发版、批量任务、数据量增长之后开始的，能大幅缩小排查面。
- **第二步 · 抓出慢语句**：
  - 开启慢查询日志：`slow_query_log = ON`、`long_query_time = 1~2`、`log_queries_not_using_indexes = ON`。
  - 用 `pt-query-digest` 按"总耗时 × 出现次数"排序，先处理性价比最高的那几条，而不是按单次耗时排。
  - 没有慢日志时，用 `SHOW FULL PROCESSLIST` 抓当下正在跑的长查询应急。
- **第三步 · 读执行计划**：对慢 SQL 跑 `EXPLAIN`，重点看三处——`type` 是否出现 `ALL`/`index`；`rows` 是否远大于返回行数；`Extra` 是否出现 `Using filesort`（排序没走索引）或 `Using temporary`（用了临时表）。
  - 同时看 `key` 与 `possible_keys`：前者为空说明确实没走索引，后者非空却没用说明优化器判断走索引更贵。
  - 数据量小的表全表扫描反而更快，别为了消掉 `ALL` 硬加索引。
- **第四步 · 分类优化**：
  - 缺索引：按"等值列在最左 → 区分度高的在前 → 范围列靠后 → 排序列放末尾"建联合索引。
  - 索引失效：改写条件——去函数、去隐式类型转换、去前缀模糊、用 UNION 拆 OR。
  - 写法问题：去掉 `SELECT *` 让覆盖索引生效；大偏移分页改游标分页（`WHERE id > lastId LIMIT 20`）；避免把范围条件夹在联合索引中间。
  - 排序与分组无法走索引时，优先考虑预计算与冗余列，而不是每次现算。
- **第五步 · 结构性优化**：
  - 单表过大就按时间或业务做冷热分离与归档，把查询圈定在小表上。
  - 高频统计改为维护计数缓存，或给大表 `COUNT(*)` 指定最小的二级索引。
  - 热点读加 Redis 缓存层；表结构改动走 Online DDL 或 gh-ost，避开线上锁表。
  - 连接池等待队列积压说明瓶颈在并发而非单条 SQL，这时调池比调 SQL 更直接。
- **第六步 · 验证与防回归**：
  - 对比优化前后的 `rows`、`Extra` 与真实响应时间，并与优化前的执行计划一起留档。
  - 把这类 SQL 的特征写进巡检项，并对 `Slow_queries`、`Innodb_row_lock_waits`、连接池等待队列长度设置告警。
  - 优化写法要沉淀成团队规范，否则同类问题会在下一个人手里重来一遍。
- **为什么这么设计**：先度量再优化能避免"凭感觉加索引"——加错索引不仅不生效，还会拖慢写入路径；按耗时总量排序能保证每一分精力都花在最贵的语句上，而不是均匀地优化一百条无关紧要的查询。把"验证"和"监控"写进流程，是为了让优化结果可复现、可回溯，而不是靠感觉宣称"快了"。
- **边界与代价**：加索引会增加存储并拖慢写路径，需要权衡读写比；`FORCE INDEX` 只在优化器选错时作为临时手段，不能长期依赖；改 SQL 前要确认没有其他业务依赖同一语句；大表归档与改表都要安排在低峰执行，并全程盯住主从延迟；优化上线后要留观察窗口，避免问题换个形式再出现。

### Q65: 设计一个数据库读写分离方案（场景题）

- **题目要求**：应用读多写少，需要通过读写分离提升整体吞吐，并说清架构、应用层路由、连接池配置、主从延迟处理与故障兜底。
- **整体架构**：
  - 一主多从：主库开启 Binlog 承担全部写请求；从库配置复制并设为只读（`read_only = 1`），承担读请求。
  - 从库同时兼作数据备份与报表分析的载体，把分析型查询从主库上彻底剥离。
  - 从库至少部署两个：既分摊读流量，也避免单个从库故障后读能力直接归零。
- **应用层路由**：
  - 首选框架内置能力：ORM 配 `replication` 选项（`master` + `slaves` 连接配置），自动把 `SELECT` 路由到从库、写操作路由到主库。
  - 也可以自建数据源路由，按方法注解或事务语义决定；关键是路由必须**显式可覆盖**，方便个别查询强制走主库。
  - 事务内的读要跟着主库走，避免同一个事务里读到不同数据源导致逻辑错乱。
  - 强制走主库的能力要以最小侵入的方式提供（如方法装饰器或请求上下文标记），否则业务会绕过它。
- **连接池配置**：
  - 主库写少，池可以小（如 10）；从库读多，池要大（如每节点 30），并在多个从库之间做负载均衡。
  - 连接池要带探活，从库故障时自动摘除，避免把请求投给已下线的节点。
  - 所有池的总连接数要控制在上游数据库 `max_connections` 之内，否则拆得越细越容易打满。
  - 为每个池设置获取连接的超时，避免请求在池里无限排队把上游拖垮。
- **主从延迟处理**：
  - 延迟敏感路径（如"下单后立刻查自己的订单"）强制读主库——用请求上下文标记（写操作后一小段时间内的读走主库）或显式指定 `useMaster`。
  - 历史查询、报表类、对时效不敏感的读正常走从库，把主库的读压力真正降下来。
  - 把"延迟多少算不可接受"写成明确的阈值配置，而不是靠个人感觉临时判断。
- **监控与兜底**：
  - 持续采集 `Seconds_Behind_Master` 与从库复制线程状态，超过阈值告警。
  - 延迟过大时自动把读流量切回主库或降级到缓存，宁可损失吞吐也不能把过期数据当最新数据返回。
  - 从库恢复后要能自动重新纳入流量，避免长期由单节点承载读请求。
- **为什么这么设计**：读写分离的收益来自"读可以水平扩展"，但最容易出事故的地方不是路由写错，而是**把主从延迟当成了一致性**——业务以为读到的是最新数据，实际是几百毫秒前的快照。所以路由策略必须按业务的时效性要求分级，而不是简单按 SQL 类型一刀切。
- **边界与代价**：只能缓解读压力，写压力与单表容量瓶颈依然存在（那要靠分库分表）；从库越多，主库 Binlog 推送与从库存储成本越高；"写后立刻读主库"会把一部分读流量拉回主库，收益打折，需要明确一致性与性能之间的取舍点；从库越多，故障面也越大，摘除与恢复流程必须自动化。

### Q66: 设计电商订单系统的数据库表结构（场景题）

- **题目要求**：设计用户、商品、订单、订单项等核心实体的表结构，说明实体关系、字段类型选择、索引设计与范式取舍。
- **表划分**：`users`（用户）、`products`（商品，含价格、库存、上下架状态）、`orders`（订单头，含订单号、用户 ID、总金额、状态、支付时间）、`order_items`（订单项，含商品快照、数量、小计），共四张核心表，遵循第三范式但对订单项做局部反范式。
  - 支付流水、物流单、退款单等按业务需要单独成表追加，核心四张表保持精简，避免一张宽表塞下所有字段。
- **关键字段选择**：
  - 主键统一 `BIGINT AUTO_INCREMENT`；订单号 `VARCHAR(32)` 加唯一索引，由发号器或雪花算法生成，对外展示用订单号而不是自增 ID。
  - 金额一律 `DECIMAL(12,2)`（单价 `DECIMAL(10,2)`），绝不用 `FLOAT`/`DOUBLE`，避免浮点精度问题。
  - 状态用 `TINYINT` 枚举并写清 `COMMENT`，比字符串更省空间也更快比较。
  - 时间字段用 `DATETIME`，`created_at` / `updated_at` 交给数据库默认值维护。
  - 所有表统一保留 `created_at` / `updated_at`，便于问题排查与增量同步。
- **快照冗余**：`order_items` 里冗余 `product_name` 与 `product_price`，即使商品之后改名、改价，历史订单的金额与展示内容也不会变。这是查询性能与业务正确性共同要求的一处反范式。
  - 快照字段一经写入就视为只读，任何后续流程都不应回改，否则"冻结"就失去意义。
- **索引设计**：
  - `orders` 建联合索引 `(user_id, status, created_at)`——等值列打底、排序列收尾，让"某用户的某状态订单按时间倒序"一次命中且免 filesort。
  - 按状态做的运营筛选可单独使用 `status` 前缀，或按需再建 `(status, created_at)`。
  - `order_items` 建 `order_id` 索引，保证按订单取明细高效；`users.email` 建唯一索引，兼作登录约束。
  - 索引只建在真正高频的查询维度上，每个新增索引都要说得出它对应哪条查询。
- **外键取舍**：开发阶段可用物理外键保证引用完整性；一旦要分库分表或做高频批量导入，就要去掉外键，改为应用层校验或异步对账，否则约束校验带来的锁与迁移成本无法接受。
- **为什么这么设计**：
  - 电商订单是"读历史、写当下"的典型负载：写入路径要求状态与金额绝对准确，读取路径要求列表页与详情页都能走索引快速返回。
  - 所以字段类型从严（`DECIMAL` 保金额精度、`TINYINT` 保状态紧凑、`BIGINT` 保主键空间），冗余只加在"必须冻结"的快照字段上。
  - 索引围绕最高频的两个查询维度（用户 + 时间）组织，而不是给每个字段都建一个索引。
- **边界与代价**：反范式意味着商品信息变更时不回改历史订单，这是预期行为但必须向业务明确；订单表增长极快，需要提前规划按时间分区或分库分表；一旦引入分片，订单查询必须带上分片键，否则会退化成全分片扫描；金额与状态的枚举含义要写进 `COMMENT` 并在代码里集中定义，避免各处硬编码。
