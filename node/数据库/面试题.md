# 模块面试题 · 数据与缓存

## 1. MySQL 基础与 SQL

### Q1（1.3）｜ INNER JOIN 和 LEFT JOIN 有什么区别？（左连接最怕把条件写进 WHERE）
- **判断**：INNER JOIN 只返回两表都匹配的行；LEFT JOIN 以左表为基准返回全部，右表无匹配补 `NULL`。
- **展开**：INNER JOIN 取交集，任一侧不满足关联就不出现；LEFT JOIN 保留左表全集，是"以左表为主体的可选关联"。查"订单的用户"用 INNER；查"所有用户及订单（含零订单用户）"必须 LEFT。
- **边界**：`LEFT JOIN ... WHERE 右表.列 = 'x'` 会把外连接退化回内连接，右表条件要写进 `ON` 才是"先关联再筛选"。

### Q2（1.1）｜ 主键和外键有什么区别？为什么生产常不用物理外键？
- **判断**：主键唯一标识一行、不能 NULL、一表一个；外键指向另一张表主键、可 NULL、可多个。
- **展开**：主键保证实体完整性（InnoDB 里主键即聚簇索引，决定数据物理顺序）；外键保证引用完整性，写入时加锁校验父表。
- **边界**：外键校验加锁、阻碍批量导入与分库分表，生产用应用层校验或异步对账替代；主键优先自增 `BIGINT` 而非随机 UUID，否则 B+ 树频繁页分裂。

### Q3（1.1）｜ CHAR 和 VARCHAR 怎么选？金额为什么必须 DECIMAL？
- **判断**：CHAR 定长、不足补空格；VARCHAR 变长、按实际长度加 1~2 字节、更省空间；金额一律 `DECIMAL`。
- **展开**：`FLOAT`/`DOUBLE` 是二进制浮点，无法精确表示 0.1、0.2，累加会有肉眼可见误差；`DECIMAL(m,n)` 十进制定点精确可控。
- **边界**：长度稳定字段（手机号、身份证、MD5）用 CHAR 更省开销；VARCHAR 上限 65535 字节，长文本用 TEXT。

### Q4（1.2）｜ DELETE、TRUNCATE、DROP 有什么区别？
- **判断**：DELETE 删行（DML）可带 WHERE、可回滚、触发触发器；TRUNCATE 清表（DDL）不可回滚、重置自增；DROP 连表结构一起删。
- **展开**：DELETE 逐行写 undo/redo 慢但可回滚；TRUNCATE 直接释放数据页并重建结构、几乎不写逐行日志所以快。
- **边界**：删大表绝大部分数据时 DELETE 会长时间持锁与巨量 undo，更稳的是"建新表灌数据 + 原子改名"或分批删除。

### Q5（1.4）｜ 范式与反范式怎么取舍？
- **判断**：严格三范式少冗余但查询多 JOIN；适当反范式用冗余换查询性能、但要自己维护一致性。
- **展开**：1NF 每列不可再分；2NF 非主键列完全依赖主键；3NF 非主键列不依赖其他非主键列。反范式=主动违反、把"每次查询都会 JOIN 的字段"冗余到主表。
- **佐证**：订单项冗余商品名与下单时单价，是典型且必要的反范式——历史订单必须冻结当时价格快照。
- **边界**：反范式只用在"读多写少且允许短暂不一致"处；冗余字段一旦要更新需所有副本同步改。

### Q6（1.3）｜ 设计一套电商订单系统核心表结构，说明关系、字段与索引。
- **判断**：四张核心表——`users`/`products`/`orders`/`order_items`，遵循第三范式并对订单项做局部反范式。
- **展开**：主键统一 `BIGINT AUTO_INCREMENT`、订单号 `VARCHAR(32)` 唯一索引（对外用订单号非自增 ID）；金额 `DECIMAL(12,2)`、状态 `TINYINT` 枚举写 COMMENT、时间 `DATETIME`；`order_items` 冗余 `product_name`/`product_price` 快照，写入后只读不回改。
- **索引**：`orders` 建 `(user_id, status, created_at)` 联合索引（等值打底、排序列收尾免 filesort）；`order_items` 建 `order_id` 索引；`users.email` 建唯一索引；索引只建在高频查询维度上。
- **边界**：金额绝不用浮点；订单表增长快要提前规划分区或分库；一旦分片查询必须带分片键否则退化成全分片扫描；发育期可用物理外键、要分库时去掉改应用层校验。

## 2. MySQL 索引与查询优化

### Q1（2.1）｜ 最左前缀原则是怎么回事？
- **判断**：联合索引 `(a, b, c)` 先按 a、a 同再按 b、b 同再按 c 排序，查询条件须从最左列开始且中间不能断。
- **展开**：`WHERE a=1` 能用；`a=1 AND b=2` 能用；`a=1 AND c=3` 只有 a 生效；`WHERE b=2` 完全用不上。最左前缀同样约束排序—`ORDER BY a, b` 复用索引、`ORDER BY b` 不行。
- **边界**：设计顺序按"几乎每次必带的等值列最左 → 区分度高的在前 → 范围列靠后 → 排序列末尾"；范围列后面的索引列会失效，别把范围条件夹中间。

### Q2（2.1）｜ 聚簇索引和二级索引（非聚簇索引）有什么区别？
- **判断**：InnoDB 主键索引即聚簇索引，叶子存整行、一表只有一个；二级索引叶子只存"索引列 + 主键值"，查非索引列需回表。
- **展开**：数据按主键顺序物理组织，主键等值定位到叶子即拿整行；走二级索引只拿主键、还要再走一次聚簇索引取其余列。
- **边界**：这正是"自增主键优于随机主键"的原因——有序插入顺序落盘、减少页分裂与碎片。

### Q3（2.4）｜ 覆盖索引为什么能提升性能？与索引下推有何区别？
- **判断**：查询列全在索引里、不需要回表，`EXPLAIN` 的 `Extra` 显示 `Using index`。
- **展开**：二级索引叶子只存"索引列 + 主键值"，若 `SELECT` 列都在其中，MySQL 直接从索引树返回，省掉逐行回聚簇的随机 I/O。
- **边界**：`SELECT *` 几乎必然破坏覆盖索引；覆盖索引会让索引变宽、写入变慢，只对高频查询建。ICP 是 MySQL 5.6+ 把能用索引字段的 WHERE 条件下推到存储引擎、遍历时筛行——它**减少回表次数**，覆盖索引是**完全不回表**（`Extra` 分别显示 `Using index condition` 与 `Using index`）。

### Q4（2.4）｜ 索引失效的常见场景有哪些？
- **判断**：底层原因只有一条——索引列在 WHERE 里被"改造"了，无法按原有序走 B+ 树。
- **展开**（五类）：① 隐式类型转换，`phone = 13800138000`（列是 VARCHAR）等价于对列套函数，改成 `phone = '13800138000'`；② 函数/运算包住列，`DATE(created_at)=...`、`amount*1.1>100`，改范围或把运算挪常量侧；③ 前缀模糊 `LIKE '%张三'`，只能用 `LIKE '张三%'` 或 FULLTEXT/ES；④ `OR` 有未索引列，用 UNION 拆或给另一列建索引；⑤ 低区分度列单独建索引，优化器认为扫全表更快。
- **边界**：`!=` 与 `NOT IN` 通常也不走索引（优化器认为全表更划算）；拿真实数据量跑 `EXPLAIN` 验证，小表时优化器一律选全表。

### Q5（2.2）｜ EXPLAIN 的 type 字段怎么排序？重点看什么？
- **判断**：性能从优到劣 `system > const > eq_ref > ref > range > index > ALL`，日常目标至少 range、绝不 ALL。
- **展开**：`const` 主键/唯一等值命中至多一行；`eq_ref` 被驱动表按主键/唯一匹配一行；`ref` 非唯一索引等值多行；`range` 索引范围（`>`/`<`/`BETWEEN`/`IN`）；`index` 全索引扫描；`ALL` 全表扫描。同时看 `rows`（越小越好）、`key`、`Extra`。
- **边界**：`Extra` 的 `Using filesort`/`Using temporary` 是要优化的信号（分别对应排序没走索引、用了临时表）。

### Q6（2.5）｜ COUNT(*) 和 COUNT(1)、COUNT(列) 有什么区别？大表 COUNT 怎么优化？
- **判断**：`COUNT(*)` 与 `COUNT(1)` 等价（InnoDB 已优化）；`COUNT(列)` 只数非 NULL 行、结果可能不同。
- **展开**：大表 COUNT 的四种优化——选最小非空二级索引 `USE INDEX`、`SHOW TABLE STATUS` 取估算值、Redis 维护计数、分页改 `EXISTS` 判"是否有下一页"。
- **边界**：`EXISTS(SELECT 1 FROM orders WHERE id > ?)` 比 COUNT 快得多；计数缓存要用在实时性要求不高的场景。

### Q7（2.5）｜ 深分页为什么慢？怎么优化？
- **判断**：`LIMIT 10 OFFSET 100000` 的 OFFSET 越大、要跳过的行越多，越翻越慢。
- **展开**：游标分页 `WHERE id > 100000 ORDER BY id LIMIT 10` 利用索引，翻第 N 页和翻第 1 页一样快；前提是排序字段可作游标。
- **边界**：游标分页不适合"页码可跳转"的需求（无法精确跳到第 N 页）；MongoDB 侧同理可用 `_id > lastId`。

### Q8（2.6）｜ 一条慢 SQL 的完整排查流程是什么？
- **判断**：发现 → 定位 → `EXPLAIN` → 优化 → 验证，五步闭环。
- **展开**：先确认问题范围（单接口慢还是全局慢），开启慢查询日志（`slow_query_log = ON`、`long_query_time = 1`、`log_queries_not_using_indexes = ON`），用 `pt-query-digest` 按耗时 × 次数排序；对慢 SQL 跑 `EXPLAIN` 看 type/rows/Extra；分类优化（缺索引、索引失效、写法问题），再去函数/去 `SELECT *`/大偏移改游标/范围条件不夹中间。
- **佐证**：把 `DATE(created_at) = '...'` 改范围 `created_at >= ? AND < ?` 后，`type` 从 `ALL` 变 `range`、扫描行数从 50 万降到 1200、耗时 3.2s→0.02s。
- **边界**：加索引会拖慢写路径，权衡读写比；`FORCE INDEX` 只作临时手段；优化后必须复测避免让其它查询变差。

### Q9（2.3）｜ SQL 逻辑执行顺序、WHERE/HAVING 区别、EXISTS 与 IN 怎么选？
- **判断**：执行顺序 `FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT`；WHERE 分组前过滤行（不能用聚合），HAVING 分组后过滤组（只能用聚合或 `GROUP BY` 列）。
- **展开**：这解释了 WHERE 里不能用 SELECT 别名、ORDER BY 可以用。EXISTS vs IN：外层小/子结果集大用 EXISTS（逐行判断、命中即返回）；外层大/子结果集小用 IN（结果集缓存、外层走索引）；关联子查询只能用 EXISTS。
- **佐证**：MySQL 8.0 可以 `ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC)` 窗口函数取"每个用户最新一条"，替代关联子查询。
- **边界**：MySQL 8.0 优化器会把很多 IN 改写成半连接，实测差异可能被抹平，最终以 `EXPLAIN` 为准。

## 3. MySQL 事务、锁与并发控制

### Q1（3.2）｜ MVCC 是什么？InnoDB 如何靠它实现可重复读？
- **判断**：MVCC 让"读不阻塞写、写不阻塞读"，可重复读建立在它之上——同一事务内多次读取一致、且读取不加锁。
- **展开**：每行两个隐藏字段 `DB_TRX_ID`（最近修改它的事务 ID）与 `DB_ROLL_PTR`（指向 undo log 上一版本）串成版本链；事务首次查询生成 Read View（活跃事务快照），之后只读"创建时间早于自己"的版本。
- **边界**：RR 只在第一次查询创建 Read View 并复用，读已提交每次查询都重建；MVCC 只解决快照读，写冲突仍靠锁。追问：undo 何时清理？—没有更早 Read View 需要它时由 purge 线程回收。

### Q2（3.2）｜ 快照读和当前读有什么区别？
- **判断**：普通 `SELECT` 是快照读（读事务开始时的版本、不加锁）；`SELECT ... FOR UPDATE`/`UPDATE`/`DELETE`/`LOCK IN SHARE MODE` 是当前读（读最新已提交版本并加锁）。
- **展开**：这是防超卖的基石——只有当前读保证"读到的值"和"要改的值"是同一份且被自己独占。误区：以为"我刚 UPDATE 了别人一定看得到"——RR 下别人的普通 SELECT 仍看旧版本；以为"FOR UPDATE 只是加锁"——它同时把读升级为当前读。
- **边界**：写并发控制一律用当前读，或把判断下推进 `UPDATE ... WHERE` 用 affectedRows，别依赖快照读。

### Q3（3.3）｜ InnoDB 在可重复读下怎么避免幻读？
- **判断**：两条腿——快照读用 MVCC 的 Read View 看不到新插入行；当前读用 Next-Key Lock（行锁 + 间隙锁）锁住扫描区间与间隙、阻止插入。
- **展开**：普通 SELECT 走快照读，自然不出现"两次查询行数不同"；`FOR UPDATE`/`UPDATE`/`DELETE` 走当前读，在扫描的索引区间上加 Next-Key Lock。
- **边界**：间隙锁只在 RR 生效，读已提交只有行锁；间隙锁会显著降并发（范围查询密集时尤其），可接收时可降级到读已提交换吞吐。

### Q4（3.4）｜ 高并发下怎么防止库存/额度扣成负数（超卖）？
- **判断**：把判断下推进 UPDATE 的 WHERE，用 affectedRows 判定成败：`UPDATE quotas SET balance = balance - 1 WHERE user_id = ? AND balance >= 1`，返回 1 成功、0 余额不足。
- **展开**：反面是先 `SELECT` 再判断再 `UPDATE`——两步之间别的请求插进来会双扣成负。UPDATE 是当前读 + 行锁，多个并发串行化执行，`balance >= 1` 在库内原子判断。
- **佐证**：`UPDATE ... SET stock = stock - 1 WHERE id = ? AND stock > 0` 是秒杀 DB 落账的标准写法。
- **边界**：三种方案取舍—纯扣减且不能超用原子 UPDATE；扣减前需跨表校验再上 `FOR UPDATE` 悲观锁；偶发并发多字段更新用 version 乐观锁、冲突重试。

### Q5（3.5）｜ 什么是 AB-BA 死锁？怎么排查和预防？
- **判断**：两个事务以相反顺序更新多行、各自持锁等对方释放，形成循环等待。
- **展开**（形态→分步）：事务 A 锁 id=1 等 id=2、事务 B 锁 id=2 等 id=1，互不相让即死锁；InnoDB 会自动回滚其中一个事务报 `LATEST DETECTED DEADLOCK`。
- **佐证**：排查用 `SHOW ENGINE INNODB STATUS`（看死锁段落）、`INFORMATION_SCHEMA.INNODB_TRX`（活动事务）、`INNODB_LOCK_WAITS`（锁等待）。
- **边界**：预防四招—所有事务按相同顺序访问资源、事务保持简短、避免事务内用户交互、用 `SELECT ... FOR UPDATE NOWAIT`（8.0+）避免等锁；一次删超大表数据要拆小批量避免长事务放大锁范围。

### Q6（3.4）｜ 结合 Redis 设计一个秒杀系统的库存扣减方案，如何防止超卖？
- **判断**：三层分工——Redis 原子扣减做前置过滤、消息队列削峰、数据库条件更新做最终落账，绝不以 Redis 为记账依据。
- **展开**：
  - 预热：活动前 `SET goods:{id}:stock` 写入库存，TTL 比活动久。
  - Redis 层：用 Lua 把"读库存 → 判断 >0 → DECR → 返回"打包原子执行，不足直接失败；不要把先查再减写成两条命令（这是扣成负数的经典原因）。
  - DB 层：消费者用 `UPDATE goods SET stock = stock - 1 WHERE id = ? AND stock > 0` 拿 affectedRows 判定，1 成功 0 则需回补 Redis 名额并告警。
  - 防重复：`SETNX seckill:user:{id}:{activityId}` 去重、下单接口以订单号幂等。
- **佐证**："判断下推进 UPDATE WHERE + affectedRows"与上面 Q4 是同一套路，由行锁 + 当前读保证原子性。
- **边界**：必须处理双向补偿（Redis 扣了但落库失败要回补名额、落库成功但回补遗漏靠对账发现）；MQ 不丢 + 下游幂等；单商品库存 key 本身是热点，QPS 极高时要分桶或按库分片；活动结束清理 key 并与库对账。

## 4. MySQL 高可用、分布式与运维

### Q1（4.1）｜ 主从复制的原理？Binlog 有哪几种格式？
- **判断**：主库写 Binlog → dump 线程推给从库 → 从库 I/O 线程写 Relay Log → SQL 线程重放。
- **展开**：Binlog 三格式—`STATEMENT`（记 SQL，日志小但 `NOW()`/`UUID()` 会主从不一致）、`ROW`（记行变更，最精确、日志大，生产推荐）、`MIXED`（混合自动切）。
- **佐证**：主从 `server_id` 必须不同、从库 `read_only = 1` 防误写、主库 `sync_binlog = 1` 保证提交即落盘、级联复制开 `log_slave_updates`。
- **边界**：复制默认异步、从库可能落后；要降丢数据风险用半同步复制，但接受写延迟上升。

### Q2（4.1）｜ 主从延迟怎么排查和解决？
- **判断**：在从库 `SHOW SLAVE STATUS` 看 `Seconds_Behind_Master`、`Slave_IO_Running`/`Slave_SQL_Running`、`Last_IO_Error`/`Last_SQL_Error`。
- **展开**：常见原因—从库硬件弱、主库大事务（一次删百万行）、从库慢查询/锁等待、从库扛读流量、跨机房网络延迟。
- **边界**：先区分 I/O 线程落后还是 SQL 线程落后—前者网络/主库推送、后者重放慢，处理方向完全不同；解决用拆大事务（每次删 1000 行）、并行复制（`slave_parallel_workers = 4` + `LOGICAL_CLOCK`）、延迟敏感业务强制读主。

### Q3（4.2）｜ 分库分表后，全局唯一 ID 怎么生成？
- **判断**：四方案—雪花算法（趋势递增、高性能、依赖时钟）、Redis `INCR`（简单但依赖外部组件）、数据库号段（批量领号本地分配、不依赖外部）、UUID（全局唯一但无序过长、不适合聚簇主键）。
- **展开**：雪花 64 位 = 1 符号 + 41 毫秒时间戳 + 10 机器号 + 12 序列号，本地生成、无网络开销、趋势递增；号段靠 `UPDATE id_generator SET max_id += 1000` 批量领号、应用层内存分配。
- **边界**：UUID 作主键让 B+ 树频繁分裂；雪花要处理时钟回拨（等待追平/换备机号/拒绝服务）；号段模式接受机器重启丢弃未用号段的空洞。

### Q4（4.2）｜ 分片键怎么选？时间戳分片为什么是坑？
- **判断**：分片键要同时满足三条—查询高频包含它、数据分布均匀、取值不可变；单调递增的时间戳是典型反面案例。
- **展开**：按时间分片让所有新写入落最新分片（写热点）、历史分片几乎无写入；按 `user_id` 哈希取模则写入分散且同用户同片；订单系统按 `order_id`、消息系统用"时间+用户"冷热分离、地理位置按区域范围分片。
- **佐证**：`user_id % 16 → 16 分片`，每次写入随机分布；MongoDB 侧 `sh.shardCollection` 同样 `user_id: 'hashed'` 优于时间戳。
- **边界**：跨分片 JOIN、跨分片事务、无分片键的全分片扫描都要避免；跨分片分页用"每片取 N 条再汇总"，更稳的是查询带上分片键。

### Q5（4.3）｜ 大表 DDL 怎么做才不影响线上？
- **判断**：MySQL 5.6+ 的 Online DDL 支持 `ALGORITHM=INPLACE, LOCK=NONE`，加索引/加列/删列/改默认值都不阻塞读写；千万级以上用 gh-ost。
- **展开**：gh-ost 建影子表 `_orders_gho` → 监听 Binlog 同步增量 → 分批拷贝原表数据 → 原子改名切换（毫秒级），原表全程可读写、支持暂停限速。
- **边界**：改列类型、改主键仍要重建表（会锁表）；即便 Online DDL 也要关注对磁盘 IO 与主从复制的冲击，安排低峰并盯延迟。

### Q6（4.4）｜ 什么是数据库连接池？连接池溢出与连接泄漏怎么定位？
- **判断**：连接池维护一组已建连接、借出归还，避免反复创建销毁（TCP 握手/认证/权限加载是重量级操作）。
- **展开**：报 `ER_CON_COUNT_ERROR` 或 "Cannot get connection" 时先分清"不够用"还是"被占着不放"—活跃数贴满且队列积压多半慢查询长期占连；空闲也持续增长不回收才是泄漏。
- **边界**：连接数不是越多越好，`(CPU核心数 × 2) + 有效磁盘数` 是起点，池太大反而上下文切换变慢；`idleTimeout` 要小于 MySQL `wait_timeout`（默认 8 小时）并开 `enableKeepAlive`，否则空闲连接被服务端单方断开；mysql2 里 `acquireTimeout` 已失效，真正控获取超时的是 `connectTimeout`。

### Q7（4.5）｜ 怎么制定生产环境的 MySQL 备份与 PITR 恢复方案？
- **判断**：周日全量（XtraBackup） + 每日增量 + Binlog 增量（用于时间点恢复），组成"周日全量 + 每日增量 + Binlog 保留 7 天"策略。
- **展开**（分步）：三方案对比—mysqldump 逻辑备份恢复慢（<50GB）；XtraBackup 物理备份（1TB 约 30 分钟）；Binlog 增量做 PITR。PITR 三步—`xtrabackup --prepare`/`--copy-back` 恢复全备 → `mysqlbinlog --stop-datetime` 回放至误操作前一刻 → 校验关键表行数与业务数据。
- **边界**：备份文件必须异地、不能和库同一台机器；每周恢复测试、每季度限时 4 小时完整演练、备份失败 5 分钟内告警。

### Q8（4.1）｜ 设计一个数据库读写分离方案（含应用层路由与主从延迟处理）。
- **判断**：一主多从，主库开 Binlog 承担写、从库 `read_only = 1` 承担读，从库兼作备份与报表载体。
- **展开**：应用层用 ORM `replication` 选项（master + slaves）自动把 SELECT 路由到从、写操作到主，路由要可显式覆盖；事务内读跟着主库走，避免同事务读到不同源；延迟敏感路径（写后立刻读）强制读主。
- **边界**：从库越多、主库 Binlog 推送与存储成本越高；"写后立刻读主"会把部分读拉回主库、收益打折；从库故障要能自动摘除与恢复；`max_connections` 上限内控制总连接数。

## 5. Node.js 访问 MySQL

### Q1（5.1）｜ mysql2 连接池怎么用？为什么用池而不是每次新建连接？怎么防 SQL 注入？
- **判断**：`createPool` 复用连接、`connectionLimit: 10` 控上限、`queueLimit: 0` 不限队列、`waitForConnections: true` 没空闲就排队；防注入用 `?` 占位符传参、绝不拼字符串。
- **展开**：建 TCP 连接 + 认证 + 权限加载是重量级操作，池化后单次获取几乎无成本，并把并发连接收敛在可预期范围；`pool.query('... WHERE id = ?', [userId])` 中值只当数据、不当 SQL。
- **佐证**：`SELECT * FROM users WHERE id = ' + userId` 一旦 userId 来自用户输入即注入通道。
- **边界**：连接数不是越多越好、多了上下文切换反而变慢；池参数过大会把 MySQL 连接数打满。

### Q2（5.2）｜ TypeORM 里 Entity 和 Repository 是什么？核心装饰器有哪些？
- **判断**：Entity 是带装饰器映射表的类，Repository 用方法操作数据而不手写 SQL。
- **展开**：`@Entity('users')` 对应表、`@PrimaryGeneratedColumn()` 自增主键、`@Column({ length: 50 })`/`{ default: 0 }`/`{ unique: true }` 定列约束；关系 `@OneToMany` 与 `@ManyToOne` 配 `@JoinColumn({ name: 'user_id' })`，`@OneToMany` 侧是虚拟字段、库里无此列。
- **边界**：`create()` 只造实体实例（不落库）、`save()` 才写库；`findOneBy` 找不到返回 `null` 需自己判空。

### Q3（5.3）｜ 什么是 N+1 查询？为什么产生？怎么解决？
- **判断**：先 1 次查主表拿 N 条、再循环各查 1 次关联 = 总共 1+N 次，本质是 ORM 懒加载把一次关联拆成 N 次网络往返。
- **展开**：每次查询都付网络往返 + 解析 + 执行开销，N 大时总耗时线性上涨；开发环境数据量小本地延迟低，上线高并发立刻成瓶颈。
- **佐证**：TypeORM `find({ relations: ['orders'] })` 或 `createQueryBuilder().leftJoinAndSelect('user.orders', 'order').getMany()` 都能压成一次；Mongoose 用 `populate`。
- **边界**：`populate` 本质仍是多次查询、只是把 N+1 降为 2 次；数据量特别大时手写 JOIN 或 `$lookup` 更稳；开发期开 SQL 日志统计同请求查询条数检测。

### Q4（5.2）｜ ORM 和直接写 SQL 各有什么取舍？什么时候用哪个？
- **判断**：ORM 开发效率高、参数化天然防注入、类型安全，但复杂查询难表达、性能是黑盒；原生 SQL 性能可控但代码量大、需自建参数化。
- **展开**：ORM 把对象翻译成 SQL，复杂统计常生成低效语句、难以预判执行计划；原生 SQL 能精确控制 JOIN 顺序、索引使用与分页。
- **边界**：工程默认答案混合——简单 CRUD 走 ORM、报表/批量/复杂聚合走原生 SQL，主流 ORM 提供 `query()`/`$queryRaw` 逃生口；原生 SQL 必须用占位符。

### Q5（5.4）｜ QueryRunner 事务怎么写？为什么 finally 必须 release？
- **判断**：手动挡流程—`createQueryRunner()` → `connect()` → `startTransaction()` → 业务操作 → `commitTransaction()`，出错 `rollbackTransaction()`，`finally` 里 `release()`。
- **展开**：同一事务内操作都走 queryRunner 的 manager（如 `manager.decrement` 扣余额 + `manager.save` 建订单），保证要么都提交要么都回滚。
- **佐证**：扣减用户余额 + 创建订单两笔操作绑成一事务，中途任一步抛错整体回滚。
- **边界**：不 `release()` 会把连接池连接长期占住，累积成连接泄漏。

## 6. MongoDB 文档模型与基础操作

### Q1（6.5）｜ MongoDB 和 MySQL 分别适合什么场景？
- **判断**：结构化、强事务、需复杂关联的业务（账户/订单/财务）选 MySQL；结构灵活、写频繁、几乎不做多表关联的数据（日志/评论/配置）选 MongoDB。
- **展开**：MySQL 有固定 Schema、成熟 JOIN 优化器与事务；MongoDB 无 Schema、文档贴近对象、靠分片横向扩展。
- **边界**：两者互补，常见组合是 MySQL 存核心交易 + MongoDB 存日志衍生数据；MongoDB 4.0 后虽有多文档事务但性能开销明显高于 MySQL，不能因此替代关系库。

### Q2（6.1）｜ 文档（Document）和集合（Collection）是什么？ObjectId 怎么组成？
- **判断**：文档是基本数据单元（类比行）、以 BSON 存储可嵌套子文档与数组；集合是文档容器（类比表）、无需预定义结构；`_id` 默认由驱动生成。
- **展开**：BSON 是二进制 JSON，还支持日期、ObjectId、二进制等；ObjectId 12 字节 = 4 时间戳 + 5 机器标识 + 2 进程号 + 3 计数器，时间戳在最高位所以趋势递增、按 `_id` 排序 ≈ 按插入时间排序。
- **边界**：同一集合内文档结构允许不同（Mongoose 的 Schema 只是应用层约束），但结构混用让索引聚合难维护、工程上应统一；接口入参 `_id` 先按 24 位十六进制校验，否则非法值直接抛 `BSONError`。

### Q3（6.4）｜ 嵌入文档和引用（reference）怎么选？
- **判断**：总是一起查、一起改、数量可控 → 嵌入（一次查询拿全）；独立变化、可能单独查询、数量膨胀 → 引用（存 ObjectId、查询时 `populate`）。
- **展开**：嵌入省关联查询但有冗余、受单文档 16MB 限制；引用无冗余，但要么二次查询要么 `$lookup`、读放大明显。
- **佐证**：`populate('userId')` 说到底是"再发一次查询"；`ref` 只是告诉 Mongoose 该 ObjectId 指向哪个 Model、库里存的仍是普通 ObjectId。
- **边界**：经验法—"一对少、读多写少 → 嵌入；一对多/多对多、写频繁 → 引用"；拿不准按访问模式判断能否一次查询满足页面需求。

### Q4（6.3）｜ Mongoose 里 Schema 和 Model 是什么关系？
- **判断**：Schema 定义结构与规则（字段类型、必填、默认值、唯一约束、索引、钩子），Model 是 Schema 编译出的构造函数、提供 CRUD 接口。
- **展开**：一个 Model 对应一个集合，所有写入经过 Schema 的类型转换、校验与默认值填充；`required`/`default` 是客户端校验，`unique: true` 只是让 Mongoose 建唯一索引，真正拦重复靠服务端索引（需 `User.init()`）。
- **边界**：改 Schema 不影响已存在的数据、只影响之后解释；`pre('save')` 钩子挂在 Schema、由 Model 触发，适合密码哈希、时间戳维护。

### Q5（6.3）｜ MongoDB 基本 CRUD 有哪些要点？`$set` 与整条替换怎么区分？
- **判断**：`find`/`insertOne`/`updateOne`/`deleteOne` 与 mongosh 的 collection 方法同名；更新必须用 `$set` 只改指定字段，否则直接传文档会整条替换。
- **展开**：`insertOne` 返回 `insertedId`（`_id` 客户端生成）、`insertMany` 返回 `insertedCount` + `insertedIds`；更新返回 `matchedCount`（匹配几条）与 `modifiedCount`（真正改几条），二者不等说明值本来就一致；`deleteOne` 的 `deletedCount` 为 0 可判断目标不存在。
- **边界**：驱动 find 返回的是游标，`.toArray()` 才取回文档；查询条件 `$gt`/正则/`$in` 对应比较/匹配/取其一。

### Q6（6.5）｜ TTL 索引的原理和适用场景？日志量很大怎么处理？
- **判断**：给日期字段建 `expireAfterSeconds` 索引后，MongoDB 定期删除超期文档，实现数据自动过期。
- **展开**：后台线程约每 60 秒扫描一次删除，不是瞬时精确、有分钟级延迟；`expireAfterSeconds` 必须建在日期或带时间的数组字段上，否则不生效。
- **边界**：TTL 删除也产生写负载，日志量很大时更推荐按日期分集合 `logs_20240101`、过期整体 `drop()`（比逐条删快、不产生碎片），但跨天统计要在应用层汇总。

### Q7（6.5）｜ 评论/回复系统适合用 MongoDB 怎么做？为什么适合嵌入？
- **判断**：回复嵌在评论内、用 `$push` 追加、`comments.$.replies` 定位更新，适合"每条评论 < 1KB、一篇文档内评论不超 100 条"的场景。
- **展开**：`$push` 只管追加，定位到"哪条评论"靠条件里的 `comments._id`，漏写则 `$` 无落点、更新静默落空；嵌套文档一次读全、省掉多次查询。
- **边界**：评论量或单条体积超限时就该改引用/分表，否则单文档 16MB 会爆。

## 7. MongoDB 索引、聚合与高可用

### Q1（7.2）｜ 聚合管道的 $match、$group、$sort 怎么理解？阶段顺序为什么重要？
- **判断**：`$match` 过滤（类似 WHERE）、`$group` 按 `_id` 分组用 `$sum`/`$avg` 累加（类似 GROUP BY）、`$sort` 排序（1 升 -1 降）。
- **展开**：管道分阶段执行、每阶段产出新文档集，所以阶段顺序直接决定性能—`$match`/`$sort` 越靠前越能用索引、越早缩小数据量，`$project` 提前裁字段省内存；`$lookup` 类似 LEFT JOIN、`$unwind` 把数组摊平（`$lookup` 后 user 是数组、`$unwind` 后才是对象）。
- **佐证**：按月统计 `_id: { $month: '$createdAt' }`；统计总消费用 `$group` + `$sum` 再 `$lookup` 关联用户。
- **边界**：`$group`/`$sort` 单阶段默认 100MB，超限开 `allowDiskUse`。

### Q2（7.2）｜ MongoDB 的 $lookup 和 MySQL 的 JOIN 有什么区别？
- **判断**：`$lookup` 功能类似 LEFT JOIN，但它是聚合管道里逐文档去目标集合匹配、没有 JOIN 优化器、性能明显不如 MySQL 的 JOIN。
- **展开**：MySQL JOIN 由优化器在 Nested Loop/Hash Join 间选计划并可走索引；`$lookup` 对每条输入文档做一次查找、输入集合越大越吃亏。
- **边界**：只支持左外连接语义，内/右连接要用 `$unwind` 等阶段模拟；频繁 `$lookup` 通常说明模型该改成嵌入。

### Q3（7.3）｜ MongoDB 的多文档事务是怎么做的？有什么限制？
- **判断**：`startSession()` + `startTransaction()`，出错 `abortTransaction()`，`finally` 里 `endSession()`；MongoDB 4.0+ 支持。
- **展开**（分步）：会话把"扣库存 + 建订单"绑成一笔事务，中间任一步抛错整体回滚。
- **边界**：性能低于 MySQL 事务、只在必要时使用；**单机 mongod 起不了事务**——多文档事务要求副本集或分片集群，脚本失败是环境限制不是写法错。

### Q4（7.4）｜ 什么是副本集？为什么建议奇数个节点？
- **判断**：副本集解决高可用与数据冗余，由 Primary（唯一可写）、Secondary（异步复制、可读）、可选的 Arbiter（只参与选举不存数据）组成。
- **展开**：选举需"大多数"节点同意，偶数节点（如 4 个）可能票数对等选不出新主形成脑裂，所以用 3、5 个或加 Arbiter 凑奇数；Primary 心跳超时（默认 10 秒）触发选举，故障转移 10-30 秒。
- **边界**：`$lookup` 连接串必须带 `replicaSet=` 与 `readPreference`（secondaryPreferred 优先读从、primaryPreferred 优先读主）；一致性要求高读主、容忍延迟读从、报表读从。

### Q5（7.5）｜ 副本集和分片集群怎么选？分片键怎么避坑？
- **判断**：副本集解决高可用（数据量单机能放下时用）；分片集群解决水平扩展（数据到 TB 级/单机放不下时用）；可组合——每个分片本身是副本集。
- **展开**：何时分片—数据超单机内存（300GB+）、写入超 1 万 QPS、垂直扩展到头三选一。分片键坑点—时间戳分片写入热点、自增 ID 哈希分片让范围查询跨全分片；`user_id` 哈希或"区域 + 时间"更稳。
- **边界与代价**：副本集写性能受限于单主；分片集群运维复杂度高、分片键选不好数据倾斜或全分片扫描，属于"能不拆就不拆"；`sh.shardCollection` 一旦选定分片键几乎无法修改。

### Q6（7.6）｜ MongoDB 的索引最左前缀、覆盖索引与失效场景？
- **判断**：最左前缀和 MySQL 一致；覆盖索引是查询只用了索引里的字段、无需回表（`explain` 只有 `IXSCAN` 无 `FETCH`）。
- **展开**：索引 `{ user_id: 1, created_at: -1 }` 下 `find({ user_id: 123 })` 与带 `created_at` 范围能用、只查 `created_at` 用不到；失效场景—正则包含 `/张三/` 不走索引（`/^张/` 前缀可以）、`$expr + $year` 对索引列用函数不走索引，改 `$gte`/`$lt` 范围才走。
- **佐证**：`countDocuments({ user_id: 123 })` 只需 `{ user_id: 1 }` 索引即可覆盖；`totalDocsExamined >> nReturned` 说明扫描远多于返回、需要优化。
- **边界**：`explain('executionStats')` 会真跑查询、线上别对大集合随手跑；慢查询用 `db.setProfilingLevel(1, { slowms: 100 })` 再查 `system.profile`（级别 0 会连带删 profile 集合，要留档先导出）。

## 8. PostgreSQL 与 pgvector

### Q1（8.3）｜ PostgreSQL 的 JSONB 和 MySQL 的 JSON 有什么区别？为什么业务常用 JSONB？
- **判断**：JSONB 解析后二进制存、支持 GIN 索引做包含与键查询；JSON 文本原样存、每次取值解析、很难高效索引。
- **展开**：取值为 `->` 返回 jsonb、`->>` 返回文本；`payload @> '{"tool":"sql_query"}'` 走 GIN 倒排；也可只对某键建 `USING GIN ((payload -> 'tool'))` 省空间。
- **边界**：结构稳定、要联表的字段仍建普通列；只有随业务演进、需灵活检索的元数据才用 JSONB，别把主键/外键塞进 JSONB。

### Q2（8.1）｜ 什么时候该用 PostgreSQL 而不是 MySQL？
- **判断**：需要 JSONB 灵活建模、复杂窗口函数/CTE 分析、地理（PostGIS）或原生向量相似度检索时选 PG；纯交易业务 MySQL 足够且运维简单。
- **展开**：PG 类型更严（UUID/ARRAY/ENUM/JSONB）、扩展机制强（pgvector/PostGIS/fdw）、索引家族更宽（B-Tree/GIN/GiST/部分/表达式）。
- **边界**：团队熟悉度与运维成本同样是选型项；常见组合是"MySQL 管账户订单 + PG 管半结构化运行数据与向量"，而不是二选一。

### Q3（8.1/8.2）｜ PG 有哪些 MySQL 没有的强类型？各解决什么问题？
- **判断**：UUID、TEXT[]、ENUM、JSONB 四类降低应用层拼接字符串的麻烦、更贴近业务对象。
- **展开**：UUID 分布式生成主键、避免自增被遍历（`DEFAULT gen_random_uuid()`）；`TEXT[]` 一字段存多值、省关联表（`'io' = ANY(tags)`）；ENUM 限定取值集合、比 VARCHAR 更省更安全；JSONB 承载任意半结构化字段。
- **边界**：MySQL 想对 `lower(email)` 建索引要走生成列、没有部分索引；PG 的 ENUM 加取值要 ALTER TYPE、不如 VARCHAR 灵活。

### Q4（8.4）｜ 窗口函数、CTE 和 UPSERT 分别解决什么？
- **判断**：窗口函数在不聚合行的同时算组内排名/最新/累计；CTE 把子查询命名提升可读性；UPSERT 用 `ON CONFLICT` 一条语句完成幂等写入。
- **展开**：`ROW_NUMBER() OVER (PARTITION BY user_id ORDER BY created_at DESC)` 取组内最新一条、`RANK()` 算排名（行还在、只多一列）；`WITH ranked AS (...)` 拆步骤；`ON CONFLICT (run_id) DO UPDATE SET status = EXCLUDED.status` 重复运行更新而非报错。
- **边界**：看到"每个 X 的 Top N / 最新一条 / 累计值"第一反应应是窗口函数，而不是 GROUP BY 或应用层循环。

### Q5（8.5）｜ 部分索引和表达式索引解决什么问题？
- **判断**：部分索引只对满足条件的行建索引（如 `WHERE status = 'running'`），体积小、写入快；表达式索引对函数结果建索引（如 `lower(email)`），让函数条件也能走索引。
- **展开**：90% 运行记录是 finished、只有 running 常被查，全列索引里大部分条目从未被用、纯粹拖慢写入。
- **边界**：MySQL 没有部分索引、只能用联合/前缀近似；两者都要求查询条件与索引定义完全匹配才会被使用。PG 索引家族对照—B-Tree 等值/范围/排序、GIN 多值/JSONB、GiST 几何/范围、部分/表达式函数。

### Q6（8.6）｜ PG 的 EXPLAIN ANALYZE 和 MySQL 的 EXPLAIN 有什么不同？怎么读？
- **判断**：PG 的 EXPLAIN ANALYZE 会真执行语句给真实耗时，信息比 MySQL 更全。
- **展开**：`Seq Scan` 大表出现通常没走索引；`rows` 与 `actual rows` 偏差大说明统计信息过期需 `ANALYZE`；`Planning Time`/`Execution Time`（毫秒）是优化目标。
- **边界**：看到 `Seq Scan + 大表 + 慢执行` 先问为何没走索引、再想建 GIN/部分索引，而不是加内存。

### Q7（8.7）｜ PostgreSQL 和 MySQL 的 MVCC 有什么不同？表膨胀从哪来？
- **判断**：MySQL 旧版本在 undo log（独立段）由 purge 线程自动回收；PG 旧行留在数据表本身变 dead tuple、必须靠 `VACUUM` 回收。频繁 UPDATE/DELETE 又不 VACUUM 就表膨胀、查询变慢。
- **展开**：PG 的 UPDATE 本质是"标记旧行失效 + 插入新行"，行内用 `xmin`/`xmax` 记录可见性；MVCC 读语义相似、回收方式完全不同。
- **边界**：长事务阻塞 VACUUM、死元组堆积；用 `VACUUM (ANALYZE, VERBOSE)` 手动回收并更新统计信息。所以 PG 慢不一定是 SQL 写错，可能是没做 VACUUM。

### Q8（8.8）｜ pgvector 的向量相似度检索怎么跑？索引怎么选？
- **判断**：表里存一列定长向量 `VECTOR(1536)`，查询用距离算子排序取 TopK；三个算子 `<=>` 余弦、`<->` 欧氏、`<#>` 内积，如 `ORDER BY embedding <=> '[...]'::vector LIMIT 5`。
- **展开**：完整流程—文档切块（200~1000 字）→ Embedding 转定长向量 → 存 `VECTOR` 列 → 查询向量化 → `<=>` 取 TopK。索引—IVFFlat 适合百万级以内（`lists = 100`）、HNSW 召回更准构建更快（新项目直接用）、ops 必须与算子对应（`vector_cosine_ops` 配 `<=>`）否则不生效。
- **边界**：向量维度必须与业务侧写入的定长数组一致、改维度要重建表与索引；向量赋值与相似度查询走 raw query、索引在迁移脚本手写 `CREATE INDEX`；小数据量顺序扫描也够快；索引做近似最近邻、要精确结果用精确扫描。

### Q9（8.9）｜ NestJS + Prisma 怎么集成 pgvector？
- **判断**：Prisma 无 `VECTOR` 原生类型，schema 用 `Unsupported("vector(1536)")?` 透传；向量读写走 raw query 表达不了 `<=>`。
- **展开**：`$executeRaw` 写向量（拼成 `'[1,2,...]'` 字符串）、`$queryRawUnsafe` 做 TopK；`DATABASE_URL` 用 `postgresql://`；migration 先 `CREATE EXTENSION vector;`，HNSW 索引手写 `CREATE INDEX`（Prisma 不支持声明式定义）。
- **边界**：Prisma 负责事务与 CRUD、pgvector 负责相似度检索，职责清晰，别试图把向量运算塞进 ORM。

## 9. Redis 基础与数据结构

### Q1（9.1）｜ Redis 为什么快？
- **判断**：四条—数据全在内存；单线程串行执行无锁竞争与上下文切换；IO 多路复用（epoll）扛大量连接；底层数据结构专门优化（SDS、跳表、压缩列表）。
- **展开**：单线程不是瓶颈——瓶颈是网络带宽与内存，省掉线程协调反而更快更简单；Redis 6.0 后把网络读写拆成多线程、命令执行仍单线程。
- **边界**：正因为单线程，一条慢命令（`KEYS *`、遍历大 key、复杂 Lua）会阻塞所有客户端，是 Redis 性能问题头号来源。

### Q2（9.1）｜ Redis 适用哪些场景？不适用哪些场景？
- **判断**：适用热点缓存、计数器、排行榜、分布式锁、限流、会话共享、轻量消息队列；不适用大容量持久化存储、强事务、复杂多表关联查询。
- **展开**：数据全内存、容量受内存成本限制；命令单线程、没有回滚/隔离级别/JOIN 语义。
- **边界**：判断标准是"这份数据能不能丢、能不能重建"—能重建的放 Redis、不能丢的必须落库，Redis 只作加速层。

### Q3（9.2）｜ Redis 的 String 和 Hash 分别适合什么场景？
- **判断**：String 适合整体读写的小对象、计数器、分布式锁；Hash 适合"对象"、可只改一个字段不动整份数据。
- **展开**：String 存对象需整体序列化/反序列化；Hash 用 `HSET`/`HGET` 精确到字段、省带宽与编解码开销、配合 `HINCRBY` 做字段级计数。
- **边界**：Hash 字段很多时会从紧凑编码退化成哈希表、内存上升（大 Hash 要拆的根因）；分布式锁用 String（`SET ... NX EX`）、不要用 Hash。

### Q4（9.2）｜ Redis 的 List、Set、ZSet 分别适合什么场景？
- **判断**：List 有序可重复做队列与时间线；Set 无序去重做标签、共同好友、去重统计；ZSet 带分数排序做排行榜、延时队列、滑动窗口限流。
- **展开**：List 底层双向链表/quicklist，两端出入 O(1)；Set 底层 intset 或 hashtable，支持交并差；ZSet 用跳表 + 字典，按分数范围与排名查询都高效。
- **边界**：做消息队列要 ACK 和消费组就用 Stream——List 的 `LPOP` 在消费者崩溃时会直接丢消息。

### Q5（9.2）｜ String 为什么用 SDS 而不是 C 字符串？
- **判断**：SDS 自带 `len`/`free` 字段——取长 O(1)、按策略预分配减少内存重分配、二进制安全（可存含 `\0` 的任意字节）。
- **展开**：C 字符串以 `\0` 结尾、取长要遍历、无法存含 `\0` 的二进制；SDS 追加按"小于 1MB 翻倍、大于 1MB 每次加 1MB"扩容、惰性释放避免频繁缩容。
- **边界**：这些设计支撑 Redis 把 String 当"二进制安全的字节容器"——缓存序列化对象、图片、协议数据都没问题。

## 10. Redis 持久化与内存管理

### Q1（10.1）｜ RDB 和 AOF 有什么区别？生产怎么选？
- **判断**：RDB 是定时快照、文件紧凑恢复快但丢最后一次快照后数据；AOF 追加写命令、`everysec` 下最多丢 1 秒但文件更大恢复更慢。生产建议同时开或用 Redis 4.0+ 混合持久化。
- **展开**：RDB 靠 `BGSAVE` fork 子进程写 dump.rdb；AOF 落盘频率由 `appendfsync` 决定（`always` 最安全最慢、`everysec` 默认、`no` 最快最不安全），文件膨胀后 `BGREWRITEAOF` 重写压缩；混合持久化（`aof-use-rdb-preamble yes`）把 RDB 快照当 AOF 前缀，兼顾恢复速度与数据安全。
- **边界**：纯缓存可只开 RDB 甚至不开持久化；数据量大时 fork 的瞬时内存与延迟抖动要提前评估。

### Q2（10.2）｜ Redis 的过期键删除策略是什么？
- **判断**：惰性删除 + 定期删除的组合拳。
- **展开**：惰性删除是访问 key 时才检查过期、过期则删；定期删除是每 100ms（频率由 `hz` 控制）随机抽查一批设置了 TTL 的 key、删掉已过期的，避免全量扫描。
- **边界**：抽查是随机的、过期 key 可能长期滞留在内存，最终靠内存淘汰策略兜底——这就解释了"明明设了 TTL 内存却没降下去"。

### Q3（10.2）｜ Redis 的内存淘汰策略有哪些？缓存场景用哪个？
- **判断**：共 8 种。缓存场景最常用 `allkeys-lru`；只想淘汰带 TTL 的 key 用 `volatile-lru`/`volatile-lfu`/`volatile-ttl`；绝不允许丢数据的用默认 `noeviction`（内存满后写请求直接报错）。
- **展开**：LRU 看"最近有没有被访问"、LFU 看"被访问频次"，热点相对稳定时 LFU 命中率更高但需更多元数据。
- **边界**：淘汰只在达 `maxmemory` 后触发，务必给 `maxmemory` 留 fork 与内存碎片余量；`evicted_keys` 持续增长说明容量不足、应扩容而不是继续调策略。

### Q4（10.3）｜ 什么是 Big Key？判定标准、危害和解决？
- **判断**：单个 key 存储的数据过大。粗略判定—String 超 10KB、或集合类超 5000 元素。
- **展开**：命令单线程执行，读写或删除大 key 长时间占主线程致其他请求排队；集群下还造成内存倾斜与跨节点大包传输。
- **佐证**：拆子 Hash（`user:10000:orders:202401`）、大 JSON 压缩后存、删除用 `UNLINK` 异步回收（List 用 `LTRIM` 分批清）。
- **边界**：排查用 `redis-cli --bigkeys`，但要扫描全库、有明显性能影响，生产低峰或从节点执行。

### Q5（10.3）｜ 什么是热点 Key？怎么解决？
- **判断**：某个 key 被极高并发访问、把承载它的节点 CPU 与带宽打满；判定参考单 key QPS 上万或某节点 CPU 明显偏高。
- **展开**（四种解法）：① 应用层本地缓存减少 Redis 访问；② 读写分离把读分散到多个从；③ 把热点 key 复制成多份（`hot:key:1..N`）打散到不同分片；④ 限流保护后端。
- **边界**：热点 key 常与击穿耦合，更适合配"逻辑过期 + 异步刷新"而非硬 TTL；定位用 `redis-cli --hotkeys`（基于 LFU）或代理层访问统计。

### Q6（10.4）｜ Redis 事务和 MySQL 事务有什么不同？
- **判断**：Redis 用 `MULTI`/`EXEC` 打包命令但**不支持回滚**——语法错误整批不执行、运行时错误只影响出错那条。
- **展开**：命令在 `EXEC` 前只是入队，没有隔离级别、没有 undo 机制；要"先检查再修改"的原子语义得靠 `WATCH` 乐观锁或 Lua 脚本。
- **边界**：需要真正原子的复合操作（扣库存、释放锁）一律用 Lua；`MULTI` 只适合"不关心中途出错、只想一次发完"的批量场景，那用 Pipeline 更合适。

### Q7（10.2）｜ Redis 缓存命中率多少算正常？低了怎么提升？
- **判断**：一般 90% 以上，低于 80% 就该系统排查；计算 `keyspace_hits / (hits + misses)`、从 `INFO stats` 取。
- **展开**（诊断顺序）：先看是否大量不存在的 key 被空查（穿透问题）、再看 TTL 是否太短反复回源、最后才考虑加内存；提升手段—扩大容量、合理延长 TTL、上线/大促前缓存预热、LRU 换 LFU。
- **边界**：命中率高不等于没问题——命中率很高但单 key 极热，依然会打爆某节点，要同时看单 key QPS 分布。

## 11. Node.js 操作 Redis

### Q1（11.1）｜ ioredis 怎么连接与重连？
- **判断**：`new Redis({ host, port, retryStrategy })`，重连策略返回 `Math.min(times * 200, 2000)` 做指数退避。
- **展开**：ioredis 内置连接池与自动重连；集群模式用 `new Redis.Cluster([...])` 传节点列表；`redis.on('error')` 挂连接错误日志。
- **边界**：密码为空时不要传 `password`，否则向无密码实例发起 AUTH 会报错；`SET key val EX 60` 与 `SETEX key 60 val` 等价、读回来要自己 `JSON.parse`。

### Q2（11.2）｜ 五种数据类型的 Node 写法分别是什么？
- **判断**：String `setex`/`incr` 存缓存与计数、Hash `hset`/`hgetall`/`hget` 存对象、List `lpush`/`rpop` 做队列、Set `sadd`/`sismember` 做标签、ZSet `zadd`/`zrevrange 'WITHSCORES'` 做排行榜。
- **展开**：`incr`/`incrBy` 原子自增、无需先读再写；`hget` 取单字段、`hgetall` 取整对象；`lpush` + `rpop` 是 FIFO 队列（入队 `JSON.stringify`、取出再 `JSON.parse`）；`zrevrange(key, 0, 9, 'WITHSCORES')` 取前 10 名带分数。
- **边界**：重复 `sadd` 同一 member 不会增加（去重集合）；Hash 字段很多会退化编码升内存。

### Q3（11.3）｜ NestJS 里怎么做 Redis 全局模块与 RedisService 封装？
- **判断**：用 `@Global()` 的 `useFactory` 提供 `'REDIS'` token 并 exports，Service 用 `@Inject('REDIS')` 注入；封装把 JSON 序列化、TTL 分支、`del`、`lock`/`unlock` 收进一个服务。
- **展开**：Cache-Aside 的最小实现 `getProduct`——先 `get` 命中返回、未中查库并 `set` 回写设 TTL；`set` 传了 ttl 用 `setex` 否则永久；`lock` 返回布尔、`unlock` 在生产必须用 Lua 比对 value 再删。
- **边界**：业务侧不该到处手写 `JSON.parse`/`JSON.stringify`；简单的 `unlock` 是简化版，多实例下必须 Lua 保证只释放自己的锁。

### Q4（11.4）｜ Pipeline 和 Lua 脚本分别解决什么问题？
- **判断**：Pipeline 把多条命令一次性发出/收回、减少网络往返但不保证原子；Lua 脚本在服务端原子执行、保证整段逻辑不被打断。
- **展开**：Pipeline 只是打包传输、命令间仍可能插入其他客户端命令，提供"批量"而非"事务"；Lua 由单线程一次性执行完、中间不切走。
- **佐证**：`redis.eval(stockScript, 1, key)` 里 `1` 是 KEYS 个数、`KEYS[1]` 指向库存 key；"判断库存 + DECR"打包原子，并发下不超卖。
- **边界**：Lua 只适合短脚本，长脚本同样阻塞主线程；`exec()` 返回 `[[err, result], ...]` 与命令顺序对应；库存扣减、锁安全释放必须 Lua。

### Q5（11.5）｜ 怎么监控 Redis 连接健康？
- **判断**：定时 `ping()` 探活（连接异常抛错）+ `info()` 把文本解析成结构化字段，对连接数过千、内存超 1GB、`evicted_keys` 出现三类情况告警。
- **展开**：`parseInfo` 按 `connected_clients`/`used_memory`/`evicted_keys` 键拆分；`eval` 挂 `setInterval`（30 秒一次）、进程退出 `clearInterval`，告警接通知通道。
- **边界**：命中率、碎片率、复制延迟等信息同样来自 `INFO` 的不同段，可按需并入同一个监控循环。

## 12. Redis 缓存实战

### Q1（12.1）｜ 缓存和数据库的一致性怎么保证？
- **判断**：主流是 Cache Aside——读：先查缓存、未中查库回写；写：先更新数据库、再删除缓存（删而不是改）。
- **展开**：为什么删不是改—更新缓存是一次真写、可能被一串无效更新白耗资源；删除是懒加载、只有真正被读的数据才回填。为什么先写库再删缓存—反过来"先删缓存再更新库"在并发读下有窗口让读线程把旧值回填。
- **边界**：要更强一致用延迟双删（更新后延迟一小段再删一次）或把删除动作放 MQ 重试；强一致要分布式锁或事务、代价是性能，多数业务取最终一致。

### Q2（12.2）｜ 缓存穿透、击穿、雪崩的区别与各自解法？
- **判断**：三者后果都是数据库压力激增但成因不同——穿透是"查不存在的数据"、击穿是"单热点 key 过期瞬间"、雪崩是"大量 key 同时过期或 Redis 整体不可用"。
- **展开**：
  - 穿透：缓存空值（短 TTL 如 60 秒）+ 布隆过滤器前置 + 参数合法性校验。
  - 击穿：回源互斥锁 `SET NX EX` 只放一个请求查库、其余等待重试；超热 key 改"逻辑过期 + 后台异步刷新"。
  - 雪崩：TTL 加随机偏移打散 + 本地缓存作第一级 + 数据库限流降级 + Redis 主从/哨兵/Cluster 保证不整体崩。
- **边界**：三类问题常同现、要组合防护不是二选一；互斥锁必须带 TTL 且有等待超时，否则持锁请求卡死拖垮整条链路。

### Q3（12.2）｜ 布隆过滤器的原理是什么？误判是怎么回事？
- **判断**：一个位数组 + 多个哈希函数；写入把元素哈希出的多个位置置 1；查询任一位置是 0 则**一定不存在**、全是 1 则**可能存在**。
- **展开**：不同元素哈希位互相覆盖导致不存在的元素被误判为存在（假阳性）；但不会把存在的判成不存在（无假阴性）。位数组越大、哈希函数个数合适则误判率越低、代价是内存与写入上升；元素只能加不能删。
- **边界**：布隆过滤器只能挡"明显不存在"的请求、误判仍漏到库，所以它与"缓存空值"组合而不是替代；数据批量变更后要重建过滤器。

### Q4（12.4）｜ Redis 分布式锁怎么实现？SETNX 有什么缺陷？
- **判断**：加锁用一条命令 `SET key value NX EX ttl`；释放锁必须用 Lua"先比较 value 再删除"，保证只释放自己的锁。
- **展开**（SETNX 四缺陷）：① `SETNX` + `EXPIRE` 两步非原子、中间崩溃锁永不释放；② 不设 TTL 持锁崩溃直接死锁；③ 到期后 `DEL` 误删别人的锁；④ TTL 到期业务没跑完锁提前失效、互斥失效。value 用唯一标识标记持有者。
- **边界**：多节点用 Redlock（半数以上节点加锁成功且总耗时 < TTL 才算成功），但它依赖各节点时钟一致、不提供强一致；业务时间不确定可用看门狗续期；最好"锁 + 幂等"双保险。

### Q5（12.3）｜ Redis 怎么做缓存预热和全局 ID 生成？
- **判断**：预热用 Pipeline 批量灌入热点数据并带 TTL 随机抖动；全局 ID 用 `INCR` 生成"前缀 + 日期 + 6 位自增"。
- **展开**：预热—大促前 30 分钟跑、每 5 分钟刷新热门数据、用 cron 调度，`setex(key, ttl, ...)` 的 ttl 加 `Math.random()*300` 打散避免集体失效；ID—key 带日期每天从 1 开始，首次 `incr` 返回 1 时 `expire` 2 天防 key 无限堆积。
- **佐证**：生成形态 `ORDER20240101000001`；Pipeline `exec()` 返回 `[[err,result],...]` 与命令顺序对应、一次网络往返替代 N 次。
- **边界**：预热前先校验缓存库存与库一致，否则超卖从源头发生；ID 生成依赖 Redis 可用，高可用场景要评估 Redis 故障兜底。

### Q6（12.5）｜ 滑动窗口限流怎么做？
- **判断**：用 ZSet 记录每次请求时间戳，先 `ZREMRANGEBYSCORE` 清窗口外记录，再 `ZCARD` 判断是否超限，超限 `ZREM` 该条，否则 `ZADD` 记录这次请求。
- **展开**：成员用"时间戳 + 序号"唯一串（`t + '-' + i`），同一毫秒内多次请求不互相覆盖；生产给限流 key 设过期（`expire(key, 窗口秒数)`）防 key 一直留在 Redis。
- **边界**：对比固定窗口—固定窗口在窗口边界会有突刺放量、滑动窗口更平滑，代价是每次请求都要两三条命令；阈值/窗口按业务吞吐定。

### Q7（12.1）｜ 设计一个基于 Redis 的缓存网关，支持失效策略与穿透防护（场景题）。
- **判断**：采用 Cache Aside——读查缓存未中回源回写设 TTL、写先更新库再删缓存；统一封装 `CacheService` 只暴露 `get<T>()`/`set()`/`del()`。
- **展开**：
  - Key：冒号分层 `cache:{业务}:{实体}:{id}`、冷热分离 `hot:` 前缀、类型选择（整体读写 String 存 JSON、需要单独改字段用 Hash）、禁止业务直接拼 key。
  - 穿透：布隆过滤器置全量 ID + 空值缓存（短 TTL）+ 入口参数校验。
  - 击穿：`SET lock:{key} {reqId} NX EX 10` 抢锁重建、没抢到退避重试；超热 key 用"逻辑过期 + 后台异步刷新"。
  - 雪崩：TTL 随机偏移 + 本地缓存第一级 + 数据库限流降级 + Redis 高可用。
- **佐证**：写路径"删"而非"改"是懒加载、规避并发读回填旧值；要更强一致用延迟双删或删动作进 MQ 重试。
- **边界**：三类故障成因不同、防护必须一一对应，一种手段通吃既浪费内存又挡不住真正风险；互斥锁 TTL 必须覆盖最慢业务耗时、空值缓存用短 TTL 并保留存在性判断；本地缓存要考虑多实例一致性。

## 13. Redis 高可用与集群

### Q1（13.1）｜ Redis 主从复制的流程是怎样的？
- **判断**：从节点发 `PSYNC` → 主节点 `BGSAVE` 生成 RDB → 传从节点加载 → 之后主节点持续把写命令增量同步给从节点。
- **展开**：复制三作用—读写分离分担读压力、从节点作数据备份、高可用基础（主故障时从可提升为主）。
- **边界**：复制默认异步、从节点可能读到旧数据（主从延迟），一致性敏感读走主节点；配置 `replicaof <host> <port>`。

### Q2（13.2）｜ 哨兵和 Cluster 有什么区别？分别适合什么数据量？
- **判断**：哨兵解决高可用（监控、自动故障转移、通知新主地址）但不解决分片；Cluster 同时解决分片与高可用（16384 槽 + 每片主从）。
- **展开**：哨兵是独立一组进程，靠多数派判定客观下线并选举新主（主观下线 → 多哨兵协商客观下线 → 选新主 → 重指向 → 通知客户端）；Cluster 用 Gossip 协议互通、客户端按 `CRC16(key) % 16384` 路由、扩容迁移槽位。
- **边界**：数据量小只要高可用 → 主从 + 哨兵；超单机内存或需水平扩展 → Cluster；Cluster 跨槽多 key 操作受限、用 `{tag}` 保证同槽（牺牲均匀）；哨兵模式客户端必须通过哨兵发现主节点、不能写死 IP。

### Q3（13.3）｜ Redis 为什么是 16384 个哈希槽？
- **判断**：16384 = 2^14，槽号 14 位可表示，节点间交换槽位映射与心跳包更省带宽，同时上千节点规模也够用。
- **展开**：`HASH_SLOT = CRC16(key) % 16384`。槽太少单节点数据量过大、扩缩容粒度粗；槽太多节点间槽位同步开销变大。
- **边界**：多 key 原子操作用 `{tag}` 哈希标签强制同槽、但牺牲分布均匀；扩容按槽迁移，客户端收到 `MOVED` 应更新本地槽缓存。

### Q4（13.2）｜ 哨兵故障转移的完整流程？
- **判断**：主观下线 → 多哨兵协商确认客观下线 → 选新主 → 从节点重指向新主 → 通知客户端。
- **展开**：`sentinel monitor mymaster host port 2` 的 `2` 是判定主主观下线所需票数；`down-after-milliseconds` 设超时、`failover-timeout` 设转移超时；哨兵周期性监控主从、自动触发转移。
- **边界**：哨兵不解决分片、数据量超过单机内存仍要 Cluster；客户端不能写死主 IP，必须经哨兵发现新主。

### Q5（13.4）｜ Redis 的 Bitmap、HyperLogLog、GEO、Stream 分别做什么？
- **判断**：Bitmap 做日活（位图极省内存）、HyperLogLog 做 UV（固定 12KB、误差约 0.81%）、GEO 做地理位置（底层复用 ZSet）、Stream 做消息队列（Redis 5.0+，支持持久化、消费组与 ACK）。
- **展开**：Bitmap `SETBIT user:日期 用户ID 1` + `BITCOUNT` 统计当天人数；HyperLogLog `PFADD`/`PFCOUNT` 统计独立用户、`PFMERGE` 合并；GEO `GEOADD` 存坐标、`GEODIST` 算距离、`GEORADIUS` 查半径内；Stream `XADD` 生产、`XREADGROUP` 消费、`XGROUP CREATE` 建消费组。
- **边界**：List 做队列消费者崩溃会丢消息、要可靠队列就 Stream；HyperLogLog 是近似基数、不能存具体成员。

### Q6（13.5）｜ Redis 生产怎么加固安全？慢查询和多线程 IO 怎么调？
- **判断**：安全四件套—`requirepass` 强密码、`bind` 只留内网、`rename-command` 禁用 FLUSHALL/FLUSHDB/CONFIG、改默认 6379 端口。
- **展开**：慢查询 记录超时命令（`slowlog-log-slower-than 10000` 记超 10ms）、`SLOWLOG GET/LEN/RESET` 查看与管理；多线程 IO 是 Redis 6.0 的 `io-threads` 只把网络读写多线程化、命令执行仍单线程。
- **边界**：多线程 IO 只对网络 IO 密集场景有用，如果是命令本身慢（大 key、KEYS）或 CPU 密集完全没帮助，多数场景单线程已足够；慢查询里 `KEYS *` 是典型元凶。

### Q7（13.6）｜ 监控 Redis 主要看哪些指标？
- **判断**：四组 `INFO`——clients（连接数/阻塞数）、memory（内存/碎片率）、stats（命中率）、replication（复制延迟）。
- **展开**：`INFO clients` 看 `connected_clients`/`blocked_clients`；`INFO memory` 看 `used_memory`/`mem_fragmentation_ratio`；`INFO stats` 算命中率 `keyspace_hits / (hits + misses)`；`INFO commandstats` 看单命令 `usec_per_call`；`INFO replication` 的 `master_last_io_seconds_ago` 看复制延迟（> 30 秒严重）。
- **边界**：命中率低要先诊断穿透/TTL 再考虑加内存；碎片率超 1.5 报警；`evicted_keys` 持续增长说明容量不足。
