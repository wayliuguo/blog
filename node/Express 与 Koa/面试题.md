## 一、基础概念

### Q1: Express 是什么？它在原生 `node:http` 之上把什么收敛成了约定？（第 01 篇）

- **结论**：Express 不提供新能力，它把 `node:http` 的常用写法标准化成三件事——路由注册、中间件链、响应封装。
- **对应关系**：手写 `if (req.url === ...)` 分发 → `app.get('/user', handler)`；手写 `Buffer.concat` 读请求体 → `express.json()`；每处手写日志 / 鉴权 / 跨域 → `app.use(fn)`；手动 `res.setHeader` + `res.end` → `res.json()` / `res.status()`；手动 404 分支 → 兜底中间件。
- **边界**：内置的只有路由、静态文件、模板引擎集成与 body 解析；鉴权、限流、ORM、日志都要靠第三方中间件组装。

### Q2: Koa 的核心设计理念是什么？（第 02 篇）

- **结论**：Koa 是 Express 原班人马打造的继任者，定位是**极简内核**——核心只给 `ctx` 封装，其余全部交给独立中间件。
- **原理**：原生支持 `async/await`；不内置路由、模板、静态文件与 body 解析，分别要装 `@koa/router`、`koa-body`、`koa-static`；中间件采用洋葱模型。
- **边界**：体积极小的代价是装配成本高、新手容易低估——「开箱即用度」明显低于 Express，换来的是每一层都可替换。

### Q3: Express 与 Koa 的核心区别是什么？（第 02 篇）

- **结论**：两条差异——**异步模型**（回调 `next()` vs `async/await` + `await next()`）与**内核定位**（Express 内置路由与静态文件，Koa 只给 `ctx`，其余全靠中间件组装）。
- **原理**：Express 的 `next()` 语义是「把控制权往下传」，不等下游做完；Koa 把中间件组合成嵌套 Promise 链，`await next()` 真正等待下游整条链 resolve，所以才会出现「进入 → 处理 → 返回」的洋葱形态。
- **边界**：Express 也能写 async 中间件，但 `next()` 本身不返回 Promise，异步错误要手动 `try/catch` + `next(err)`，否则错误会漏出框架的捕获范围。
- **追问**：为什么 Koa 的异步错误更容易捕获，见 Q15。

### Q4: Express 里 `req.params`、`req.query`、`req.body` 分别从哪里来？（第 01 篇）

- **结论**：`params` 来自路由路径里的 `:name` 占位符；`query` 来自 `?` 之后的查询串，Express 自动解析；`body` 必须由中间件解析后才存在。
- **原理**：`/users/:id` 匹配 `/users/123` 后得到 `req.params.id === '123'`，注意是**字符串**，当数字用必须先转换；`?page=1` 解析进 `req.query.page`；`req.body` 依赖 `express.json()` / `express.urlencoded()`，而 `multipart/form-data` 内置解析器不支持，要另上 `multer` 之类的中间件。

```js
app.get('/users/:id', (req, res) => {
  console.log(req.params.id)  // URL 参数，恒为字符串
  console.log(req.query.page) // 查询参数 ?page=1
})
```

- **边界**：三者都来自客户端，必须显式校验与类型转换；直接拿 `req.query.id` 拼 SQL 就是注入入口。

### Q5: Koa 的 `ctx` 对象常用属性有哪些？（第 06 篇）

- **结论**：`ctx` 是 Koa 对 `req` / `res` 的封装，记两组合就够——请求侧与响应侧。
- **请求侧**：`ctx.method`、`ctx.url`、`ctx.path`、`ctx.query`、`ctx.headers`、`ctx.request.body`（需 `koa-body`）、`ctx.params`（需路由中间件）。
- **响应侧**：`ctx.status`、`ctx.body`、`ctx.set(key, value)`。
- **跨界用法**：`ctx.req` / `ctx.res` 是原始 Node 对象，只有需要底层能力时才碰；`ctx.state` 用于在中间件之间传递数据（如 `ctx.state.user = decoded`），等价于 Express 挂在 `req` 上的自定义字段。

### Q6: `ctx.body` 可以赋值哪些类型？`Content-Type` 由谁决定？（第 06 篇）

- **结论**：字符串、对象、`Buffer`、`null` / `undefined` 都行，Koa 按类型自动决定响应方式，业务代码不用手写 `res.end`。
- **映射关系**：`string` → `text/html; charset=utf-8`；对象 → `application/json` 且自动 `JSON.stringify`；`Buffer` → 原样写入；`null` / `undefined` → 状态码被改成 **204** 且不发送 body。
- **边界**：给 `ctx.body` 赋值只是「标记需要发送响应」，真正发送发生在整条中间件链 resolve 之后——所以外层 `await next()` 之后还能改写 `ctx.body`，最终以最后一次赋值为准。

### Q7: `app.use` 与 `app.get` 的区别是什么？（第 01 篇）

- **结论**：`app.use` 匹配**所有 HTTP 方法**且路径是**前缀匹配**；`app.get` 只匹配 GET 且路径**精确匹配**。
- **原理**：`app.use('/user', fn)` 对 `/user`、`/user/123`、`/user/123/detail` 全部命中；`app.get('/user', fn)` 只命中 `GET /user` 这一个路径。

```js
app.use('/user', userRouter)       // 挂载路由模块，匹配所有方法
app.get('/user', (req, res) => {}) // 只匹配 GET /user
```

- **边界**：`app.all()` 虽然也匹配所有方法，但路径仍是精确匹配，这点常和 `app.use` 混淆；路由级中间件用 `router.use(fn)` 挂在子路由上。

### Q8: 一个接近生产的 Express 项目为什么要按 `routes / controllers / services / entities` 分层？（第 03 篇）

- **结论**：分层的目的不是整齐，而是让**路由只管接口形状、控制器只管解析请求、服务层只管业务规则**，三者能各自替换和测试。
- **具体分工**：`routes/users.js` 用 `Router` 声明路径与中间件顺序；controller 从 `req` 取值、调 service、`res.json` 输出，出错则 `next(err)` 转交；service 抛带 `statusCode` / `isOperational` 的业务错误，完全不碰 `req` 和 `res`。
- **边界**：service 不感知 HTTP 是这条线的价值所在——同一份 `userService` 可以被定时任务或命令行脚本复用；一旦在 service 里写 `res.json()`，这个复用点就没了，单测也得靠 mock 请求对象。

## 二、机制与原理

### Q9: Express 的错误处理中间件为什么必须是 4 个参数？（第 01 篇）

- **结论**：Express 通过**函数形参个数**（读取 `fn.length`）识别中间件类型，只有 `(err, req, res, next)` 的 `.length === 4` 才会被当成错误处理器。
- **原理**：普通中间件是 `(req, res, next)`，`.length === 3`。链上任意位置调用 `next(err)` 后，Express 会**跳过后面全部普通中间件**，只寻找下一个 4 参数函数。
- **边界**：4 个参数必须全部写出来，即便 `err` / `next` 用不到也不能省——省掉就退化成普通中间件，错误被静默放过，表现为请求挂起而不是报错。

### Q10: Express 中间件里 `next()` 不调用会发生什么？（第 01 篇）

- **结论**：请求会**挂在那里**——既不进入下一个中间件，也不返回响应，客户端一直等到超时。
- **原理**：中间件链靠 `next()` 递归推进，不调用就等于递归在这里断掉，`req` / `res` 都不会被释放。
- **边界**：**终止型中间件**（路由处理函数、鉴权失败分支）不调 `next()` 是正常的，前提是它已经用 `res.json()` / `res.send()` 结束了响应；「既不发响应也不调 `next`」才是 bug。
- **排障信号**：接口无响应、`res.on('finish')` 不触发、同一请求只有进入日志没有结束日志，先怀疑这里。

### Q11: 给出下面这段 Koa 中间件，请求时的控制台输出顺序是？（第 02 篇）

```js
app.use(async (ctx, next) => {
  console.log('A 进入'); await next(); console.log('A 返回')
})
app.use(async (ctx, next) => {
  console.log('B 进入'); await next(); console.log('B 返回')
})
app.use(async (ctx) => { console.log('处理请求'); ctx.body = 'ok' })
```

- **结论**：输出 `A 进入 → B 进入 → 处理请求 → B 返回 → A 返回`，即进入按注册顺序、返回按**逆序**。
- **原理**：`await next()` 等待的是**下游整条链**完成后的 Promise，所以 B、A 的「返回」段只能在最内层结束之后才开始执行。
- **判据**：决定形态的是代码里有没有 `await`。写 `next()` 而不 `await`，返回段就会提前执行，洋葱立刻被拉平成线性模型。
- **追问**：最内层没有 `next()`，它靠 `ctx.body` 收尾；真正的响应发送发生在整条链 resolve 之后。

### Q12: Express 里 `next('route')` 和 `next('router')` 有什么区别？（第 04 篇）

- **结论**：`next('route')` 跳过**当前路由**剩余的中间件，去尝试下一个匹配的路由；`next('router')` 直接**跳出当前 Router 实例**，把控制权交回外层的挂载点。
- **原理**：两者都是把控制权「短路」，而不是传给下一个普通中间件；`next('router')` 只在用 `express.Router()` 嵌套、且中间件挂在 Router 上时才有意义。
- **场景**：`next('route')` 适合「条件不满足就走另一条路由」的业务中间件；`next('router')` 适合整个子路由都不适用时把控制权还给外层。
- **边界**：两者都不是错误对象，不会被错误处理中间件接住；若后面没有其他匹配路由，最终仍落到 404 兜底。

### Q13: 手写一个最小 Express 的依据是什么？（第 04 篇）

- **结论**：核心 = **中间件数组 + 一次递归遍历 + 路由正则匹配 + 增强 `res`**，不到 100 行就能跑起来。
- **原理**：`app.use` 把 `{ path, handler }` 推进 `middlewares`；`app.get` 等方法把 `{ method, path, handler }` 推进 `routes`；`executeMiddlewareChain` 内用 `next()` 递归取下一个；`matchRoute` 把 `/users/:id` 转成正则 `^/users/([^/]+)$` 提取 `req.params`；`enhanceRes` 给 `res` 挂上 `status` / `json` / `send`。

```js
app.use = (path, handler) => {
  if (handler === undefined) { handler = path; path = '/' }
  middlewares.push({ path, handler })
}
```

- **边界**：最小实现是同步 `try/catch` 加线性遍历；真实 Express 具备 Layer 缓存与路由压缩，所以「100 行能跑通」不等于「100 行能上生产」。

### Q14: Koa 的 `compose` 是怎么把洋葱模型跑起来的？`index` 在防什么？（第 06 篇）

- **结论**：`compose` 把中间件数组组合成嵌套 Promise 链，`dispatch(i)` 执行第 `i` 个中间件，并把 `dispatch(i + 1)` 作为 `next` 传进去。
- **原理**：`Promise.resolve(fn(ctx, () => dispatch(i + 1)))` 让 `await next()` 真正等到 `dispatch(i + 1)` 完成；`dispatch(len)` 取到 `undefined` 后返回 `Promise.resolve()`，这是递归的自然终点。
- **`index` 防重入**：每次 `dispatch(i)` 先判断 `if (i <= index)` 则 `reject(new Error('next() 被多次调用'))`，再更新 `index = i`；同一中间件里 `await next()` 调两次时，第二次的 `i` 不大于已记录的 `index`，直接报错而不是把下游重跑一遍。
- **边界**：任意中间件 `reject` 都会被 `fn(ctx).catch()` 统一接住，返回 500。

### Q15: Koa 的错误处理为什么比 Express 更自然？（第 05 篇）

- **结论**：因为 `await next()` 把下游异常变成 Promise rejection **顺着 `await` 往回抛**，最外层一个 `try/catch` 就能包住整条链。
- **写法**：最外层中间件 `try { await next() } catch (err) { ... }`；配合 `ctx.throw(status, msg)` 主动抛 HTTP 错误，未被捕获的错误再 `ctx.app.emit('error', err, ctx)` 交给应用级日志。
- **与 Express 的对比**：Koa 的错误捕获像普通同步代码一样自然，Express 则要靠 4 参数中间件，且只能接住**同步**抛出的异常（见 Q16）。
- **边界**：如果内层忘记 `await next()`，下游的 rejection 就游离在链路之外，外层 `try/catch` 接不到——这是最常见的坑，表现为 500 有日志但错误处理器拿不到上下文。

### Q16: Express 中异步中间件抛错为什么不会被错误处理中间件捕获？怎么修？（第 03 篇）

- **结论**：Express 4 只在**同步调用栈**里 `try/catch` 中间件；`async` 函数返回的是 Promise，内部 reject 不会自动转成 `next(err)`。
- **现象**：`app.use(async (req, res, next) => { throw new Error('boom') })` 触发后，请求挂起或进程报未处理的 rejection，而错误处理中间件毫无动静。
- **三种修法**：① 在 async 中间件内部 `try/catch` 后 `next(err)`——项目模板里每个 controller 都是这么写的；② 包一层 `asyncHandler(fn)` 高阶函数自动 `.catch(next)`；③ 升级到 Express 5，它已支持把 Promise rejection 转成 `next(err)`。
- **对应 Koa**：Koa 天生没有这个问题（见 Q15），所以 Koa 的 controller 能直接 `await` 而不必逐个 try/catch——这是两端模板写法差异的根因。

### Q17: 为什么中间件的注册顺序这么讲究？错误处理为什么必须最后注册？（第 03 篇）

- **结论**：中间件链**按注册顺序**入队并按顺序执行，越早注册越靠外层；只有排在所有路由**之后**的 4 参数中间件，才能兜住前面全部的 `next(err)`。
- **模板中的顺序依据**：`cors()` → 请求日志 → `express.json()` / `urlencoded()` → 业务路由 → 404 兜底 → 错误处理。CORS 在最前是因为响应头必须在任何输出之前设好；body 解析必须在需要 `req.body` 的路由之前；404 兜底要能接住所有未被命中的请求。
- **边界**：错误处理器若写在路由之前，后面路由抛的错它一概看不见；404 兜底写成 `app.use((req, res) => ...)` 属于**普通中间件**，作用是拦截未命中请求，别指望它接错误。

## 三、排障与选型

### Q18: 跨域问题该怎么解决？CORS 应该加在哪一层？（第 01 篇）

- **结论**：跨域是**浏览器同源策略**的限制（协议、域名、端口任一不同即跨域），必须在**服务端响应头**上解决，前端改不了。
- **方案**：CORS 是标准做法，用 `cors()` 中间件或手写 `Access-Control-Allow-Origin` / `-Methods` / `-Headers` 统一放行；JSONP 只支持 GET 已基本淘汰；开发阶段用 dev server 代理，本质是把请求变回同源。
- **必须放在最前面**：CORS 中间件要在路由之前注册，保证任何响应（含错误响应）都带上跨域头，否则出错时浏览器只报「跨域」，真实错误被掩盖。
- **边界**：带 `Content-Type: application/json` 或自定义请求头会触发**预检 OPTIONS**，要正确响应；带 Cookie 时 `Allow-Origin` 必须是具体 Origin 而不能是 `*`，并需配合 `Access-Control-Allow-Credentials`。

### Q19: 什么是 CSRF？防御应该做在哪一层？（第 03 篇）

- **结论**：CSRF 是攻击者利用浏览器**自动携带 Cookie** 的特性，在用户已登录状态下伪造请求；防御要落在**服务端对请求来源的校验**上，而 CORS 管不了它（CORS 只限制读取响应，不阻止请求发出）。
- **三种手段**：① CSRF Token——服务端签发、随表单或请求头回传后校验；② Cookie 设 `SameSite=Lax/Strict`，从源头限制跨站携带；③ 校验 `Origin` / `Referer`，并让非简单请求（带自定义头）触发预检。
- **边界**：把 JWT 放在 `Authorization` 头而非 Cookie 的方案天然免疫 CSRF，因为不会被自动携带；但 Token 存 `localStorage` 又会引入 XSS 风险——CSRF 与 XSS 是两个方向，别混为一谈。

### Q20: Express 项目里 404、401、500 各怎么统一处理？（第 03 篇）

- **结论**：404 用兜底中间件 `res.status(404).json(...)`；业务错误与未捕获异常经 `next(err)` 进入 4 参数错误处理器返回 500；401 由鉴权中间件在进入路由前直接拦截。
- **原理**：错误处理器读取 `err.statusCode` 与 `err.isOperational` 决定状态码，以及要不要把内部信息暴露给客户端；`stack` 只在开发环境回传。
- **边界**：错误处理中间件必须最后注册，否则前面抛的错找不到它；404 兜底必须排在所有路由之后、错误处理器之前。

### Q21: Koa 里怎么做统一错误处理？404 和真错误怎么区分？（第 05 篇）

- **结论**：最外层中间件用 `try/catch` 包住 `await next()`，把 `err.statusCode || err.status || 500` 写进 `ctx.status`；而 **404 不是错误**，是「没有路由命中」，必须在路由之后单独兜底。
- **为什么不能靠 catch 处理 404**：没有路由命中的时候什么都没抛，`catch` 根本不会触发；想自定义 404 文案就得在路由之后补一层判断，或用 `allowedMethods()` 统一处理未匹配方法与路径。
- **可预期错误**：`ctx.throw(401, '未登录')` 抛出的是带 `status` 的 HttpError，会被同一套 catch 合理处理；裸 `throw new Error()` 没有 status，只能按 500 处理。
- **对应 Express**：两者思路一致，差别在于 Koa 用 try/catch 包链、Express 用 4 参数中间件；区分 404 与真错误的判据在两端都是「有没有错误对象」。

### Q22: 生产环境的错误响应里为什么不能直接回 `err.message`？（第 03 篇）

- **结论**：非预期错误的 `message` 可能夹带 SQL 片段、文件路径、内部字段名，原样返回给客户端就是**信息泄露**；只有**可预期的业务错误**才适合透传文案。
- **判据**：模板的约定是服务层抛错时标记 `err.isOperational = true` 并给出 `statusCode`（邮箱已注册 409、密码错误 401、用户不存在 404），错误处理器据此决定用原文还是统一改写成「服务器内部错误」。
- **开发辅助**：`stack` 只在 `NODE_ENV === 'development'` 时附加到响应；生产环境把完整堆栈写进日志（配合 `errors({ stack: true })`），用请求标识关联。
- **边界**：日志里要记 `req.method` 与 `req.url`，但**绝不能**记密码、Token、Cookie 原文。

### Q23: 什么时候选 Express、什么时候选 Koa、什么时候直接上 NestJS？（第 01、02 篇）

- **Express**：需要快速起步、生态里现成中间件最全、团队熟悉回调风格，或项目要嵌入已有 Express 体系。Express 5 已支持把 async 错误自动转交 `next`，异步这块的老痛点已缓解。
- **Koa**：看重洋葱模型带来的「请求前后都能介入」（耗时统计、统一包装、事务），或者想要一个只有内核、中间件全由自己挑的瘦身底座；代价是路由 / body / 静态文件都得自己装。
- **NestJS**：中大型、多人协作、长期维护的项目——需要强制的模块化（`@Module`）、依赖注入、装饰器与 TypeScript 强约束时选它；其底层默认就是 Express，所以前两者的心智模型依然适用。
- **判断依据**：先看**团队规模与项目生命周期**（短平快还是长周期多模块），再看**是否需要强规范**；选 NestJS 本质是选「架构约束」而非「性能」，「能不能用 async/await」「有没有内置路由」在新版本里都已不是决定性差异。
