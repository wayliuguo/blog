# 模块面试题 · Web 框架基础

## 1. 框架定位与心智模型

### Q1（1.1）｜ Express 是什么？它在 node:http 之上把什么收敛成了约定？

- **判断**：Express 不提供新能力，它把 `node:http` 的常用写法标准化成三件事——路由注册、中间件链、响应封装。
- **展开**：手写 `if (req.url === ...)` 分发 → `app.get('/user', handler)`；手写 `Buffer.concat` 读请求体 → `express.json()`；每处手写日志/鉴权/跨域 → `app.use(fn)`；手动 `res.setHeader`+`res.end` → `res.json()`/`res.status()`；手动 404 分支 → 兜底中间件。
- **边界**：内置的只有路由、静态文件、模板引擎集成与 body 解析；鉴权、限流、ORM、日志都靠第三方中间件组，选 Express 就要接受「一切都自己拼」。

### Q2（1.2）｜ Koa 的核心设计理念是什么？

- **判断**：Koa 是 Express 原班人马打造的继任者，定位是**极简内核**——核心只给 `ctx` 封装，其余全部外置可替换。
- **展开**：原生支持 `async/await`；不内置路由、模板、静态与 body 解析，要装 `@koa/router`、`koa-body`、`koa-static`；中间件采用洋葱模型。
- **边界**：体积极小的代价是装配成本高、开箱即用度明显低于 Express，新手容易低估——换来的是每一层都可替换。

### Q3（1.3）｜ 什么时候选 Express、什么时候选 Koa、什么时候直接上 NestJS？

- **判断**：先看**团队规模与项目生命周期**，再看**是否需要强规范**；选 NestJS 本质是选「架构约束」而非「性能」。
- **展开**：Express 生态最全、回调风格团队熟悉、要嵌入既有体系时用它（Express 5 已缓解 async 错误痛点）；Koa 看重「请求前后都能介入」（耗时、事务、统一包装）或要一个只有内核的瘦身底座；NestJS 面向中大型、多人协作、长期维护，靠 `@Module`/DI/装饰器强制规范，底层默认就是 Express，前两者心智依然适用。
- **边界**：「能不能用 async/await」「有没有内置路由」在新版本里都不是决定性差异，别拿这些当选型主因。

## 2. 中间件执行模型

### Q4（2.1）｜ Express 的中间件是怎么串起来的？`next()` 有哪几重语义？

- **判断**：Express 中间件是**线性数组 + 递归 `next()`**按注册顺序推进，`next` 既是推进开关也是错误通道。
- **展开**：签名 `(req, res, next)`；`executeMiddlewareChain` 维护 `index`，每次 `next()` 取 `middlewareList[index++]`；`next(err)` 带着 err 时跳过剩余普通中间件直奔 4 参数错误处理器，没注册则回落 500。
- **边界**：不调 `next()` 且没结束响应 → 请求挂起，客户端等到超时；终止型中间件（路由处理、鉴权失败）不调 `next` 但要 `res.json/send` 收尾。

### Q5（2.2）｜ 给出下面这段 Koa 中间件，请求时的控制台输出顺序是？

```
app.use(async (ctx, next) => { console.log('A 进入'); await next(); console.log('A 返回') })
app.use(async (ctx, next) => { console.log('B 进入'); await next(); console.log('B 返回') })
app.use(async (ctx) => { console.log('处理请求'); ctx.body = 'ok' })
```

- **判断**：输出 `A 进入 → B 进入 → 处理请求 → B 返回 → A 返回`，进入按注册顺序、返回按**逆序**。
- **展开**：`await next()` 等待的是**下游整条链** resolve 后的 Promise，所以 B、A 的返回段只能在内层结束后才执行；最内层没有 `next()`，靠 `ctx.body` 收尾，真正调节 `respond` 发生在整条链 resolve 之后。
- **佐证**：判据是代码里有没有 `await`——写 `next()` 不 `await`，返回段提前执行，洋葱立刻被拉平成线性。
- **边界**：同一中间件里写两个 `await next()` 会因 `index` 防重入直接 reject 报「next() 被多次调用」，而不是重跑下游。

### Q6（2.3）｜ 为什么 Koa 的洋葱模型适合做耗时统计、事务这类跨切面逻辑？

- **判断**：因为 `await next()` 让一个中间件能在请求「处理前」和「响应后」两个时段都插入代码，一次注册就包住整条链。
- **展开**：`responseTime` 写法——`start = Date.now()` → `await next()` → `ctx.set('X-Response-Time', ...)`；`logger` 进/出各打一条日志，夹出上下半场。
- **佐证**：这正是线性模型做不到的「响应上半场」——Express 想统计耗时只能退而用 `res.on('finish')` 监听结束事件，无法在响应发送前介入。
- **边界**：洋葱的价值依赖「每个中间件都 `await next()`」；一旦有人漏 `await`，下游 rejection 游离出链，外层就接不到了。

## 3. 路由与请求数据

### Q7（3.1）｜ Express 里 `req.params`、`req.query`、`req.body` 分别从哪里来？

- **判断**：`params` 来自路径 `:name` 占位符；`query` 来自 `?` 后查询串（自动解析）；`body` 必须由中间件解析后才存在。
- **展开**：`/users/:id` 命中 `/users/123` 得 `req.params.id === '123'`——**恒为字符串**，当数字用必须先 `Number()`；`?page=1` 进 `req.query.page`；`req.body` 依赖 `express.json()`/`express.urlencoded()`，`multipart/form-data` 内置不支持要另上 `multer`。
- **佐证**：`express.json()` 保留 JSON 原生类型，URL 编码无类型信息只能还原出字符串（`age` 是 `"18"`）。
- **边界**：三者都来自客户端，必须显式校验与类型转换；直接拿 `req.query.id` 拼 SQL 就是注入入口。

### Q8（3.1）｜ `app.use` 和 `app.get` 的区别是什么？

- **判断**：`app.use` 匹配**所有方法**且路径**前缀匹配**；`app.get` 只匹配 GET 且路径**精确匹配**。
- **展开**：`app.use('/user', fn)` 对 `/user`、`/user/123` 全部命中（常用于挂载子路由）；`app.get('/user', fn)` 只命中 `GET /user` 一个路径。
- **边界**：`app.all()` 也匹配所有方法但路径仍精确，别和 `app.use` 混淆；路由级中间件用 `router.use(fn)` 挂在子路由上。

### Q9（3.2）｜ Koa 的 `ctx` 常用属性要记哪两组？

- **判断**：记请求侧与响应侧两组就够，`ctx` 是对 `req`/`res` 的封装。
- **展开**：请求侧 `ctx.method`/`url`/`path`（`?` 前）/`query`/`headers`/`request.body`（需 koa-body）/`params`（需路由）；响应侧 `ctx.status`/`body`/`set(key, value)`。
- **边界**：`ctx.req`/`ctx.res` 是原始 Node 对象，只有要底层能力才碰；`ctx.state` 用于中间件间传数据（auth 写 `ctx.state.user`），等价于 Express 挂 `req` 的自定义字段。

### Q10（3.3）｜ `req.body` / `ctx.request.body` 为什么不是天生存在？要怎样才有？

- **判断**：请求体解析不是框架内核，必须显式挂解析中间件才存在——Express 内置，Koa 需自装。
- **展开**：Express 用 `express.json()`（解析 `application/json`）和 `express.urlencoded({ extended: true })`（解析表单）；Koa 用 `koaBody()`（v7 起具名导出 `const { koaBody } = require('koa-body')`）。
- **边界**：解析中间件必须放在依赖 body 的路由**之前**；multipart 文件上传两类都另配 `multer`/`koa-body` 的文件能力。

## 4. 源码原理

### Q11（4.1）｜ 手写一个最小 Express 的依据是什么？

- **判断**：核心 = **中间件数组 + 一次递归遍历 + 路由正则匹配 + 增强 `res`**，不到 100 行纯 `node:http` 就能跑起来。
- **展开**：`app.use` 把 `{ path, handler }` 推进 `middlewares`（`handler === undefined` 时补 `path = '/'` 实现重载）；`app.get` 等把 `{ method, path, handler }` 推进 `routes`；`executeMiddlewareChain` 内用 `next()` 递归取下一个，走到末尾做路由匹配；`matchRoute` 把 `/users/:id` 转正则 `^/users/([^/]+)$` 提取 `req.params`；`enhanceRes` 挂 `status`/`json`/`send`。
- **佐证**：
```
app.use = (path, handler) => {
  if (handler === undefined) { handler = path; path = '/' }
  middlewares.push({ path, handler })
}
```
- **边界**：最小实现是同步 `try/catch` 加线性遍历；真实 Express 有 Router 类、Layer 缓存与路由压缩，所以「100 行跑通」≠「100 行能上生产」。

### Q12（4.2）｜ Koa 的 `compose` 是怎么把洋葱模型跑起来的？`index` 在防什么？

- **判断**：`compose` 把中间件数组组合成嵌套 Promise 链，`dispatch(i)` 执行第 i 个中间件并把 `dispatch(i+1)` 作为 `next` 传入。
- **展开**：`Promise.resolve(fn(ctx, () => dispatch(i+1)))` 让 `await next()` 真正等下游完成；`dispatch(len)` 取到 `undefined` 返回 `Promise.resolve()` 是递归终点；`index` 每次先 `if (i <= index) reject` 再更新，阻止同一中间件重复 `await next()` 重跑下游。
- **边界**：任意中间件 reject 都会被 `fn(ctx).then(respond).catch(...)` 统一接住返回 500。

### Q13（4.3）｜ `ctx.body` 可以赋哪些类型？`Content-Type` 和状态码由谁决定？

- **判断**：字符串、对象、`Buffer`、`null`/`undefined` 都行，`respond` 按类型自动处理，业务代码不用手写 `res.end`。
- **展开**：`string → text/html; charset=utf-8`；对象/数组 → `application/json` + 自动 `JSON.stringify`；`Buffer → 原样 end`；`null/undefined → 状态码改 204 且不发 body`。
- **边界**：给 `ctx.body` 赋值只是「标记需要响应」，真正发送在整条链 resolve 之后——外层 `await next()` 之后还能改写，最终以最后一次赋值为准。

### Q14（4.4）｜ 最小实现和真实框架的差距在哪？为什么「能跑」不等于「能上生产」？

- **判断**：最小实现为讲原理砍掉了性能与完备性，真实框架在细节上远更复杂。
- **展开**：Express 真实源码有 Router 类、Layer 缓存、路由压缩（trie/radix tree）、完整 `req.accepts()`/`res.cookie()`/`res.redirect()`、多层错误传播，且中间件是同步 `try/catch` 只能接同步异常；Koa 真实源码用 `koa-compose`、ctx 双层委托、`ctx.onerror`/`app.on('error')`、支持 stream 作 `ctx.body`、文件上传与 `@koa/router` 路由。
- **边界**：面试追问常落在「那 100 行实现怎么改进到生产级」——按上面的差距逐条补充即可。

## 5. 工程模板

### Q15（5.1）｜ 一个接近生产的 Express / Koa 项目为什么按 routes / controllers / services / entities 分层？

- **判断**：分层的目的是让**路由只管接口形状、控制器只管解析请求、服务层只管业务规则**，三者能各自替换和测试。
- **展开**：`routes` 用 Router 声明路径与中间件顺序；`controller` 从请求取值、调 service、`res.json`/`ctx.body` 输出、出错交外层；`service` 抛带 `statusCode`/`isOperational` 的业务错误，**完全不碰 `req`/`res`**。
- **边界**：service 不感知 HTTP 是价值所在——同一份 `userService` 可被定时任务/命令行脚本复用；一旦在 service 里写 `res.json()`，这个复用点就没了，单测还得 mock 请求对象。

### Q16（5.3）｜ 为什么中间件的注册顺序这么讲究？错误处理为什么必须最后注册？

- **判断**：中间件链按注册顺序入队执行，越早越靠外；只有排在所有路由**之后**的 4 参数中间件才能兜住前面全部的 `next(err)`。
- **展开**：模板顺序 `cors()` → 请求日志 → body 解析 → 业务路由 → 404 兜底 → `errorHandler`；Koa 版 `cors()` → `errorHandler` → `responseTime` → `logger` → `koaBody()` → 路由。CORS 在最前保证响应头先设好，body 解析须在依赖它的路由前。
- **边界**：错误处理器写在路由之前，后面路由抛的错一概看不见；404 兜底是普通中间件，作用是拦未命中请求，别指望它接错误。

### Q17（5.4）｜ TypeORM 里怎么用代码声明实体？`synchronize` 能动吗？

- **判断**：用 `EntitySchema` 声明实体表结构，`synchronize` 只供开发、生产走迁移。
- **展开**：`new DataSource({ type:'mysql', entities:[...], migrations:[...], migrationsTableName:'_migrations_history' })`；实体用 `EntitySchema` 声明列，如 User.email 用 `unique:true`、Product.price 用 `decimal(10,2)`，时间戳用 `createDate`/`updateDate`。
- **边界**：`synchronize` 在开发自动同步表结构方便，但生产开 `synchronize:true` 有覆盖数据风险——所以生产必须走 migrations；`AppDataSource.initialize()` 是异步、启动必须先 await。

### Q18（5.5）｜ Express 与 Koa 模板的 controller 写法为什么不一样？

- **判断**：根因是两端错误传播模型不同——Express 异步错误不自动转 `next`，controller 要 `try/catch` + `next(err)`；Koa 用 `await next()` 让异常自然回流，controller 直接 await 不用逐个 try/catch。
- **展开**：Express controller：`try { const user = await service.createUser(req.body); res.status(201).json(...) } catch (err) { next(err) }`；Koa controller：`const user = await service.createUser(ctx.request.body); ctx.status = 201; ctx.body = {...}`。
- **佐证**：见本章节 6.2（Q22）的异步错误讲解，二者是同一问题的两端体现。
- **边界**：两端的 service 层约定完全一致（抛 `statusCode`+`isOperational`），可以无缝迁移，差别只在「response 拼装」这一层。

## 6. 错误处理与排障

### Q19（6.1）｜ Express 的错误处理中间件为什么必须是 4 个参数？

- **判断**：Express 通过读取 `fn.length` 识别中间件类型，只有 `(err, req, res, next)` 的 `.length === 4` 才被当成错误处理器。
- **展开**：普通中间件 `(req, res, next)` 的 `.length === 3`；链上任意位置 `next(err)` 后 Express 跳过后面全部普通中间件，只找 4 参函数。
- **佐证**：依赖形参个数是硬编码约定，而非类型检查。
- **边界**：4 个参数必须全写出来，即便 `err`/`next` 用不到也不能省——省掉就退化成普通中间件，错误被静默放过，表现为请求挂起而不是报错。

### Q20（6.1）｜ Express 里 `next()` 不调用会发生什么？

- **判断**：请求会挂在那里——既不进下一个中间件也不返回响应，客户端等到超时。
- **展开**：中间件链靠 `next()` 递归推进，不调用就等于递归在这里断掉，`req`/`res` 都不被释放。
- **边界**：终止型中间件（路由处理、鉴权失败分支）不调 `next()` 是正常的，前提是已用 `res.json()`/`res.send()` 结束响应；「既不发响应也不调 `next`」才是 bug。排障信号：接口无响应、`res.on('finish')` 不触发、只有进入日志没有结束日志。

### Q21（6.1）｜ `next('route')` 和 `next('router')` 有什么区别？

- **判断**：`next('route')` 跳过**当前路由**剩余中间件去试下一个匹配路由；`next('router')` 直接**跳出当前 Router 实例**把控制权交回外层挂载点。
- **展开**：两者都是「短路」而非传给下一个普通中间件；`next('router')` 只在用 `express.Router()` 嵌套、中间件挂在 Router 上时才有意义；场景上 `next('route')` 适合条件不满足走另一条路由，`next('router')` 适合子路由整体不适用时交还外层。
- **边界**：两者都不是错误对象，不会被错误处理中间件接住；若后面没有其他匹配路由，最终落到 404 兜底。

### Q22（6.2）｜ Express 异步中间件抛错为什么不会被错误处理中间件捕获？怎么修？

- **判断**：Express 4 只在**同步调用栈**里 `try/catch` 中间件，async 函数返回 Promise，内部 reject 不会自动转成 `next(err)`。
- **现象**：`app.use(async (req, res, next) => { throw new Error('boom') })` 触发后请求挂起或进程报未处理 rejection，错误处理中间件毫无动静。
- **三种修法**：① async 中间件内部 `try/catch` 后 `next(err)`（模板每个 controller 都这么写）；② 包 `asyncHandler(fn)` 高阶函数自动 `.catch(next)`；③ 升级 Express 5 已支持把 Promise rejection 转成 `next(err)`。
- **对位 Koa**：Koa 天生没有此问题，`await next()` 把异常变成 rejection 顺着往回收，最外层一个 `try/catch` 即可——这是两端模板写法差异的根因。

### Q23（6.3）｜ Koa 里怎么做统一错误处理？404 和真错误怎么区分？

- **判断**：最外层中间件用 `try/catch` 包住 `await next()`，把 `err.statusCode || err.status || 500` 写进 `ctx.status`；**404 不是错误**，是「没有路由命中」，必须单独兜底。
- **展开**：可预期错误用 `ctx.throw(401,'未登录')` 抛带 `status` 的 HttpError，同一套 catch 处理；裸 `throw new Error()` 无 status 只能按 500；写 404 文案在路由后补一层判断或用 `allowedMethods()`；未捕获错误再 `ctx.app.emit('error', err, ctx)` 交给应用级日志。
- **边界**：没有路由命中时什么都没抛，`catch` 根本不触发——这是新手以为「catch 能接 404」的常见误区；区分两者的判据是「有没有错误对象」，两端一致。

### Q24（6.4）｜ 生产环境的错误响应里为什么不能直接回 `err.message`？

- **判断**：非预期错误的 message 可能夹带 SQL 片段、文件路径、内部字段名，原样返回客户端就是**信息泄露**；只有可预期的业务错误才透传文案。
- **展开**：模板约定 service 抛错时标记 `err.isOperational = true` 并给 `statusCode`（邮箱已注册 409、密码错误 401、用户不存在 404），错误处理器据此决定用原文还是统一改「服务器内部错误」；`stack` 只在 `NODE_ENV === 'development'` 附加响应，生产写进日志（`errors({ stack: true })`）用请求标识关联。
- **边界**：日志要记 `req.method` 与 `req.url`，但**绝不能**记密码、Token、Cookie 原文。

## 7. 安全与跨切面

### Q25（7.1）｜ 跨域问题该怎么解决？CORS 应该加在哪一层？

- **判断**：跨域是**浏览器同源策略**的限制（协议、域名、端口任一不同即跨域），必须在**服务端响应头**解决，前端改不了。
- **展开**：用 `cors()` 中间件或手写 `Access-Control-Allow-Origin`/`-Methods`/`-Headers` 统一放行；JSONP 只支持 GET 基本淘汰；开发阶段可用 dev server 代理把请求变回同源。**必须注册在最前**，保证任何响应（含错误响应）都带跨域头，否则出错时浏览器只报「跨域」，真实错误被掩盖。
- **边界**：带 `Content-Type: application/json` 或自定义请求头会触发**预检 OPTIONS** 要正确响应；带 Cookie 时 `Allow-Origin` 必须是具体 Origin 而非 `*`，并配 `Access-Control-Allow-Credentials`。

### Q26（7.2）｜ 什么是 CSRF？防御应该做在哪一层？

- **判断**：CSRF 是攻击者利用浏览器**自动携带 Cookie** 的特性在用户已登录状态下伪造请求；防御落在**服务端对请求来源的校验**上，CORS 管不了它。
- **三种手段**：① CSRF Token——服务端签发、随表单或请求头回传后校验；② Cookie 设 `SameSite=Lax/Strict` 从源头限制跨站携带；③ 校验 `Origin`/`Referer`，让带自定义头的非简单请求触发预检。
- **边界**：把 JWT 放 `Authorization` 头而非 Cookie 的方案天然免疫 CSRF（不会被自动携带）；但 Token 存 `localStorage` 又引入 XSS 风险——CSRF 与 XSS 是两个方向，别混为一谈。

### Q27（7.3）｜ 洋葱模型除了执行顺序，在工程上还能带来什么能力？

- **判断**：它把「请求前后都能介入」固化成普通中间件能力，让跨切面逻辑（耗时、事务、统一包装、错误）独立成层而非散落各路由。
- **展开**：`responseTime`/`logger` 一次 `await next()` 就包住前后半场；`errorHandler` 放最外层用 `try/catch` 包整条链，作为统一兜底；这正是模块收口「一个能挂数据库与缓存的 Web 服务骨架」能成立的结构基础。
- **边界**：能力成立的前提是每个中间件都 `await next()` 且错误 handler 真在最外层——两条都满足才能享受洋葱的全部红利。
