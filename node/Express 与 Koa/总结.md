# 模块总结 · Web 框架基础

## 知识主线

```
01 Express 快速入门
     │  先有 app.use / app.get 这套"中间件流水线"的共同语言
     ▼
02 Koa 快速入门
     │  知道 Koa 只给内核、其余全靠自己装，才明白工程化缺的那层必须自己补
     ▼
03 Express 项目模板
     │  模板里的分层与装配顺序都是"约定"，所以下一步要拆开看底层怎么实现的
     ▼
04 Express 源码分析
     │  Express 底层 = 中间件数组 + 递归 next；把同一套骨架换成 Koa 的洋葱编排
     ▼
05 Koa 项目模板
     │  模板里 errorHandler / logger / responseTime 全靠 await next() 夹出上下半场
     ▼
06 Koa 源码分析
     │  compose + dispatch 说明"前后都能介入"为何成立，两条线在此闭环
     ▼
收口：一个能挂数据库与缓存的 Web 服务骨架
```

本模块的主轴只有一句话：**把 `node:http` 的请求处理抽象成一条中间件流水线**。Express 用"线性数组 + 递归 `next()`"，Koa 用"嵌套 Promise + 洋葱模型"，两条线各自走完「快速入门 → 工程模板 → 源码原理」。

## 分篇知识点

### 01-Express 快速入门

- **Express 的定位与心智模型**
  - 不提供 `node:http` 之外的新能力：把路由分发、请求体读取、响应封装收敛成约定（`if (req.url)` → `app.get(path, handler)`）
  - Hello World 五步：`require('express')` → `express()` → `app.get('/')` → `res.send()` → `app.listen(3000)`
- **路由匹配规则**
  - `app.get/post/put/delete(path, handler)` 按方法与路径分发，`:id` 是路径占位符
  - `use` 与 `get` 的差异：`use` 匹配所有方法且前缀匹配（`/user` 命中 `/user/123`），`get` 只匹配 GET 且精确匹配
- **请求数据的三个来源**
  1. `req.params`：路径占位符的值，恒为字符串，当数字用必须先 `Number()`
  2. `req.query`：查询串自动解析（`?page=1` 进 `req.query.page`）
  3. `req.body`：挂了 `express.json()`/`urlencoded()` 才存在，`multipart/form-data` 要另上 multer
- **中间件执行模型**
  - 签名 `(req, res, next)`，调 `next()` 才推进，否则请求挂起；每个请求都会经过
  - 错误处理中间件靠 4 参数（`fn.length === 4`）识别，`next(err)` 跳过后续普通中间件直奔错误处理器
- **中间件生态**：内置 `express.json()`/`urlencoded()`/`static('public')`；跨域、鉴权、限流等靠第三方包（如 `cors()`）
- **框架选型（Express vs NestJS）**：Express 无架构约束、TS 可选、无 DI，适合小型/学习；NestJS 强制 MVC/TS/DI/`@Module`，适合中大型长期项目


### 02-Koa 快速入门

- **Koa 的定位与最小写法**
  - 极简内核：Express 原班人马打造的继任者，只给 `ctx` 封装，路由/模板/静态/body 解析全外置
  - Hello World：`app.use(async ctx => { ctx.body = 'Hello World' })`，给 `ctx.body` 赋值即完成响应，不写 `res.end`
  - 原生 `async/await`：中间件都是 async 函数，`await` 到数组直接赋 `ctx.body`，自动序列化成 JSON
- **洋葱模型**
  - 顺序：进入按注册顺序、返回按逆序（「1 进入 → 2 进入 → 处理 → 2 返回 → 1 返回」）
  - 成立前提：`await next()` 等待下游整条链 resolve；写成 `next()` 不 await 则洋葱被拉平成线性
  - 价值：请求前后都能介入，天然适合耗时统计、事务管理、统一响应包装
- **Express 与 Koa 的对比**
  - 七项差异：中间件模型（线性/洋葱）、异步（回调/async）、体积、路由、body 解析、静态文件、社区生态
  - 需额外安装：`@koa/router`（路由）、`koa-body`（body）、`koa-static`（静态），用 `app.use(router.routes())` 挂载


### 03-Express 项目模板

- **工程骨架与依赖栈**
  - 分层目录：`src/` 下 config/controllers/entities/middleware/routes/services/utils 七目录 + `app.js`
  - 依赖栈：express/cors/dotenv/typeorm/mysql2/ioredis/jsonwebtoken/bcrypt/joi/winston；`"dev": "node --watch"` 免 nodemon 热重启
- **配置管理**：`config/index.js` 先 `dotenv.config()` 再聚合 port/database/redis/jwt，业务代码一律不直接读 `process.env`
- **应用装配与启动**
  - 中间件顺序：`cors()` → 请求日志 → `express.json()`/`urlencoded()` → 路由 → 健康检查 → 404 兜底 → `errorHandler`（必须最后）
  - 启动：先连库 `AppDataSource.initialize()`、再 `redisClient.ping()`、最后 `app.listen()`；任一步失败 `process.exit(1)`
  - 健康检查 `GET /health` 用 `SELECT 1` + `redisClient.ping()` 双探，失败返回 503
- **数据层**：TypeORM 用 `EntitySchema` 声明 User（email 唯一）/Product（price decimal(10,2)）；`synchronize` 仅开发开，生产走迁移
- **三层职责（routes/controllers/services）**
  - 划分：routes 声明路径与中间件顺序；controller 取请求调 service 再 `res.json`、出错 `next(err)`；service 只管业务规则、不碰 `req`/`res`
  - 错误约定：service 抛 `err.statusCode` + `isOperational`（409/401/404），错误处理器据此决定状态码与文案透传
- **中间件与工具**
  - 四个中间件：auth 解析 `Bearer` 写 `req.user`、validate 用 Joi 校验后 `req.body = value`、errorHandler 区分可预期/未知、logger 用 `res.on('finish')` 记耗时
  - 三个工具：Winston 日志、ioredis 客户端、Joi schemas


### 04-Express 源码分析

- **Express 的核心抽象**
  - 只有三件事：路由注册、中间件链、响应封装；不到 100 行即可写出能跑的最小版本
  - 两个核心数据结构：`middlewares = [{ path, handler }]`（app.use 填充）与 `routes = [{ method, path, handler }]`（app.get 等填充）
- **注册 API 的重载设计**：`app.use` 靠 `handler === undefined` 区分 `use(fn)` 与 `use(path, fn)`，前者补 `path = '/'`
- **路由匹配与参数提取**：`/users/:id` 把 `:id` 替换成 `([^/]+)` 拼成 `^/users/([^/]+)$`，`url.match` 后捕获组写回 `req.params`
- **中间件链（线性递归）**
  - `executeMiddlewareChain` 维护 `index`，每次 `next()` 取走 `middlewareList[index++]`，走到末尾执行回调（路由匹配）
  - 前缀匹配：`mw.path !== '/'` 且 `url` 不以它开头时直接 `next()` 跳过
  - `next` 双重语义：既是推进下一个中间件，也是错误通道——`next(err)` 有值时跳过剩余中间件直奔 `errorHandler`，未注册则回落 500
- **响应封装（`enhanceRes`）**：给原生 `res` 挂 `status(code)`（链式）、`json(data)`（设 JSON 头+end）、`send(body)`（对象走 json、其余走 text/html）
- **能力边界：最小实现 vs 真实源码**
  - 同步 `try/catch` 只能接住同步抛出的异常
  - 真实源码有 `Router` 类、Layer 缓存与路由压缩（trie/radix tree），非每次线性遍历；"100 行跑通"≠"100 行能上生产"


### 05-Koa 项目模板

- **工程骨架与依赖栈（相对 Express 模板）**
  - 目录同名同构，仅多 `middleware/responseTime.js`（洋葱模型让耗时统计顺手成独立中间件）
  - 依赖替换：koa/@koa/router/koa-body/@koa/cors 替掉 express/cors，其余 typeorm+mysql2+ioredis+jsonwebtoken+bcrypt+joi+winston 完全一致
- **路由挂载**：`@koa/router` 用 `new Router({ prefix: '/api' })` 统一前缀，`api.use(routes())` → `app.use(api.routes())` + `app.use(api.allowedMethods())`
- **洋葱堆叠顺序**：`cors()` → `errorHandler` → `responseTime` → `logger` → `koaBody()` → 路由 → 健康检查；越先注册越靠外层，错误处理包住整条链
- **洋葱模型的两个典型用法**：`logger` 与 `responseTime` 进入时记 `start`、`await next()` 后才算差值写响应头，这是线性模型做不到的"响应上半场"
- **错误处理约定**
  - `errorHandler` 靠最外层 `try { await next() } catch` 包链，按 `err.statusCode || err.status || 500` 写 `ctx.status`，再 `ctx.app.emit('error', err, ctx)`
  - 业务错误与 Express 模板一致：服务层仍抛 `statusCode` + `isOperational`
  - 控制器不用逐个 try/catch：异常顺 `await next()` 的 rejection 回到最外层统一处理
  - 404 与真错误分开：未命中路由什么都不抛，catch 不触发，需路由后兜底或用 `allowedMethods()`
- **中间件间数据传递**：auth 把解码结果写 `ctx.state.user`，控制器读 `ctx.state.user.userId`，等价于 Express 的 `req.user`


### 06-Koa 源码分析

- **Koa 的核心抽象**
  - 只有两件事：洋葱模型中间件链（`compose`）与 Context 封装（`createContext`），比 Express 更精简
  - `app.use` 链式：`middlewares.push(fn)` 后 `return app`，可连续 `app.use(...).use(...)`
- **洋葱模型：compose 与 dispatch**
  - `compose` 返回 `function(ctx)`，从 `dispatch(0)` 启动；`middlewareList[i]` 为空时 `Promise.resolve()` 是递归终点
  - `dispatch` 把下个自己当 `next`：`Promise.resolve(fn(ctx, () => dispatch(i+1)))`——`await next()` 能等下游完成全靠这句
  - `index` 防重入：同一中间件写两个 `await next()` 会因 `i <= index` 直接 reject，而非重跑下游
  - `await next()` 决定回程：A、B 的返回段只能在内层 C 结束后才开始
- **Context 封装（`createContext`）**：挂 method/url/path(`?`前)/query/headers/status/body 与 `ctx.set()`；`ctx.body` setter 赋值时标记 `_respond`
- **响应自动生成（`respond`）**：string→text/html；对象→application/json+JSON.stringify；Buffer→原样 end；null/undefined→状态码改 **204** 且不发 body
- **错误传播**：统一靠 `fn(ctx).then(respond).catch(...)`，任意中间件 reject 都落同一 catch 返回 500
- **能力边界 vs Koa 源码**：真源码用 `koa-compose`、ctx 双层属性委托、`ctx.onerror` 与 `app.on('error')`、支持 stream 作 `ctx.body` 与文件上传，路由交 `@koa/router`

## 见 X 想 Y

现象是表相，先定位到层，再动手。

| 见到什么 | 该想到什么 | 一句话理由 |
| --- | --- | --- |
| 接口一直无响应，日志只有进入没有结束 | 中间件既没调 `next()` 也没发响应 | 链靠 `next()` 递归推进，断掉就既不推进也不响应 |
| 控制台里「A 返回」排在「B 进入」之前 | Koa 中间件里漏了 `await` | 不 await 就等不到下游链 resolve，回程段提前执行 |
| async 中间件抛错，错误处理中间件毫无动静 | Express 4 只能接住同步异常 | async 返回的是 Promise，reject 不会自动转成 `next(err)` |
| 出错时浏览器只报跨域，看不到真实状态码 | CORS 中间件注册得太靠后 | 错误响应没带上跨域头，真实错误被掩盖 |
| 新加的路由仍返回 404 兜底文案 | 路由注册在 404 兜底之后 | 中间件按注册顺序执行，越早注册越靠外层 |
| 错误处理器写在路由前，后面抛的错它看不见 | 错误处理器必须最后注册 | 只有排在所有路由之后的 4 参数函数才能兜住全部 `next(err)` |
| `req.params.id + 1` 得到 `"11"` | 路径参数恒为字符串 | 提取自 URL 文本，参与运算前需显式转换 |
| 想在某接口打出「进入 + 耗时」两行日志 | 这是洋葱模型 / `res.on('finish')` 的用武之地 | Koa 用 `await next()` 前后夹，Express 靠响应结束事件 |
| 生产响应里出现了 SQL 片段或文件路径 | 非预期错误的 `message` 被直接回传 | 只有 `isOperational` 的业务错误才适合透传文案 |
| 想把同一份 service 给定时任务复用 | 先检查它有没有碰 `req` / `res` | 服务层不感知 HTTP 才有复用与单测的可能 |
| 路由改成 `/users/:id` 后 `req.params` 是空对象 | 路由没命中，或正则未匹配上 | `:id` 先转 `([^/]+)` 再 match，命不中就没有 params |
| `await next()` 之后还想改响应内容 | 最终以最后一次赋值为准 | `ctx.body` 赋值只标记待发送，真正 `respond` 在链尾 |
| `ctx.body = null` 却拿到 204 空响应 | 这是 Koa 的约定而非 bug | `null` / `undefined` 会被映射成 204 且不发送 body |
| 同一个中间件里写了两个 `await next()` | compose 会直接抛「next() 被多次调用」 | `index` 记录已执行的 dispatch 编号，用来防重入 |

## 易错点汇总

- **"Express 提供了原生 `http` 没有的能力"**：Express 不新增能力，只是把 `node:http` 的常用写法标准化。理解这一点才能看懂最小实现为何不到 100 行就能跑通，也才不会在源码里找"黑魔法"。
- **"Koa 的洋葱形态是注册时就形成的"**：形态取决于代码里有没有 `await`。写 `next()` 而不 await，返回段会提前执行，洋葱立刻被拉平成线性模型，日志与耗时统计的结果跟着全乱。
- **"Express 的 async 中间件抛错会被错误处理中间件接住"**：Express 4 只在同步调用栈里 `try/catch`，async 函数内部的 reject 不会自动转成 `next(err)`。三种修法：中间件内 `try/catch` 后 `next(err)`、包一层 `asyncHandler` 自动 `.catch(next)`、升级到 Express 5。
- **"中间件不调 `next()` 一定是 bug"**：终止型中间件（路由处理函数、鉴权失败分支）不调是正常的，前提是已经用 `res.json()` / `res.send()` 结束了响应；"既不响应也不推进"才是 bug，表现为请求挂起、`res.on('finish')` 不触发。
- **"错误处理中间件少写一个参数也行"**：Express 靠 `fn.length === 4` 识别，四个形参必须全部写出来。省掉任意一个就退化成普通中间件，错误被静默放过，表现为请求挂起而不是报错。
- **"`req.params` 拿到的是数字"**：路径参数提取自 URL 文本，恒为字符串。`req.params.id + 1` 得到的是 `"11"` 而不是 `2`，必须先 `Number()` 或 `parseInt()`。
- **"不挂 body 解析中间件也能读 `req.body`"**：`req.body` 依赖 `express.json()` / `urlencoded()`；`multipart/form-data` 内置解析器不支持，要另上 `multer` 之类的中间件。
- **"CORS 中间件放哪都行"**：必须放在路由之前，保证任何响应（含错误响应）都带上跨域头。否则出错时浏览器只报跨域，真实状态码与错误信息被完全掩盖。
- **"把 `req` / `res` 传进 service 层很方便"**：一旦在 service 里写 `res.json()`，这个复用点就没了，单测也得靠 mock 请求对象。service 不感知 HTTP 才是这条分层的价值所在。
- **"404 是错误，应该由错误处理器处理"**：没有路由命中时什么都没抛，`catch` 根本不触发。想自定义 404 文案就得在路由之后补一层判断，或用 `allowedMethods()` 统一处理。
- **"生产环境回 `err.message` 更利于排查"**：非预期错误的 `message` 可能夹带 SQL 片段、文件路径、内部字段名，原样返回就是信息泄露。只有可预期的业务错误才适合透传，`stack` 也只在开发环境附加。
- **"同一个中间件里可以多次 `await next()`"**：compose 的 `index` 就是防这个的，第二次调用会直接 reject，而不是把下游中间件重跑一遍——这是最容易写出"重复响应头"或"重复写库"的坑。

## 与相邻模块的接口

**进入本模块前必须已经掌握**

上一模块是**模块二 · 网络底层**，它给了 `node:http` 那一层：用 `http.createServer` 拿回调、路由靠 `if (req.url === ...)` 分发、请求体靠 `chunks.push` + `Buffer.concat` 读取、响应靠 `res.setHeader` + `res.end` 输出，以及两个前提——`req` 是可读流、`res` 是可写流。入口见 [模块二 · 网络底层总结](../网络编程与实时通信/总结.md)。

本模块所有的"抽象"都建立在这之上：Express 就是把上面这些重复劳动收敛成路由注册、中间件链、响应封装；Koa 再把它换成 `ctx` 封装加 Promise 化的洋葱链。没有模块二的 `http` 心智模型，读 04 / 06 两篇的最小实现只会觉得是在凭空空想。

**本模块交给下一模块什么**

本模块产出一个**能挂数据库与缓存的 Web 服务骨架**：`routes / controllers / services / entities` 四层分工 + `config` 统一聚合配置 + 五道中间件（cors / logger / auth / validate / errorHandler）+ `bootstrap` 的启动顺序（先连库、再验缓存、最后 listen），以及 404 / 401 / 500 的统一处理口径。

下一模块是**模块四 · 数据与缓存**，它要靠这套骨架做什么：把模板里的 `TypeORM DataSource` 与 `ioredis` 从"能连通"推进到"会用"——SQL 建表与 JOIN、索引与事务、缓存穿透 / 击穿 / 雪崩、缓存与数据库的一致性，全部挂在这套骨架的 service 层上。出口见 [模块四 · 数据与缓存总结](../数据库/总结.md)。

## 代码与自测入口

本模块配套代码共 4 个项目，都在本目录 `code/` 下，路径为纯文本：

- `node/Express 与 Koa/code/express-mini` —— 200 行还原 Express 核心（中间件链、路由匹配、`res` 封装）。无第三方依赖，`npm start` 或直接 `node index.js`，默认监听 3000；`curl http://localhost:3000/users/42` 可验证动态路由参数。
- `node/Express 与 Koa/code/koa-mini` —— 180 行还原 Koa 洋葱模型（`compose` / `dispatch` / `ctx`）。同样无依赖，`npm start` 后 `curl http://localhost:3000/health` 返回健康检查结果。
- `node/Express 与 Koa/code/express-template` —— Express + TypeORM + Redis + JWT 模板。需 MySQL 与 Redis 可达，依次 `npm install` → `npm run migration:run` 建表 → `npm run dev`。
- `node/Express 与 Koa/code/koa-template` —— 同栈的 Koa 版本。读 `src/app.js` 里中间件从上到下的堆叠顺序（cors → errorHandler → responseTime → logger → koaBody → 路由），最能体会洋葱模型。
