## 1. 框架定位与心智模型

### 1.1 Express：把 node:http 收敛成约定
- 本模块主轴的唯一一句话：**把 `node:http` 的请求处理抽象成一条中间件流水线**。
- Express **不提供 `node:http` 之外的新能力**，它把原生里要手写的重复劳动标准化成约定：
  - 手写 `if (req.url === ...)` 分发 → `app.get('/user', handler)`
  - 手写 `chunks`/`Buffer.concat` 读请求体 → `express.json()` 中间件
  - 每处手写日志 / 鉴权 / 跨域 → `app.use(fn)` 中间件链
  - 手动 `res.setHeader` + `res.end` → `res.json()` / `res.status()`
  - 手动 404 分支 → 兜底中间件
- Hello World 五步：`require('express')` → `express()` → `app.get('/', handler)` → `res.send()` → `app.listen(3000)`。
- 内置能力只有路由、静态文件、模板引擎集成与 body 解析；鉴权、限流、ORM、日志都要靠第三方中间件组装。

### 1.2 Koa：极简内核，其余自己装
- Koa 是 Express 原班人马打造的继任者，定位是**极简内核**：核心只给 `ctx` 封装，路由、模板、静态、body 解析全部外置。
- Hello World 最小写法：`app.use(async ctx => { ctx.body = 'Hello World' })`——给 `ctx.body` 赋值即完成响应，不写 `res.end`、不手动 `JSON.stringify`。
- 原生支持 `async/await`：中间件都是 async 函数，`await` 到的数组直接赋 `ctx.body` 会自动序列化成 JSON。
- 需额外自装：`@koa/router`（路由）、`koa-body`（body）、`koa-static`（静态），用 `app.use(router.routes())` 挂载。
- 体积极小的代价是装配成本高、开箱即用度低于 Express，换来的是每一层都可替换。

### 1.3 框架选型：Express / Koa / NestJS
- **Express**：生态最全、现成中间件最多、团队熟悉回调风格时优先；Express 5 已支持把 async 错误自动转交 `next`。
- **Koa**：看重洋葱模型带来的「请求前后都能介入」（耗时统计、统一包装、事务），或想要只有内核、中间件全由自己挑的瘦身底座。
- **NestJS**：中大型、多人协作、长期维护项目，需要强制模块化（`@Module`）、依赖注入、装饰器与 TS；其底层默认就是 Express，前两者的心智模型依然适用。
- 判断依据：先看团队规模与项目生命周期，再看是否需要强规范；选 NestJS 本质是选「架构约束」而非「性能」。

## 2. 中间件执行模型

### 2.1 Express 线性中间件链
- 中间件签名 `(req, res, next)`，每个请求按**注册顺序**依次经过；调 `next()` 才推进，不调用请求就挂起。
- `next` 是双重语义：既是推进下一个中间件，也是错误通道——`next(err)` 有值时跳过剩余普通中间件直奔 4 参数错误处理器。
- 应用级 `app.use(fn)` 每个请求都执行；路由级 `app.use('/api', fn)`（带路径）只在 URL 以 `/api` 开头时才执行。

```
Express: 中间件A → 中间件B → 处理请求
```

### 2.2 Koa 洋葱模型与 await next()
- 执行顺序**进入按注册顺序、返回按逆序**：「中间件A进入 → 中间件B进入 → 处理请求 → 中间件B返回 → 中间件A返回」。

```
Koa: 中间件A进入 → 中间件B进入 → 处理请求 → 中间件B返回 → 中间件A返回
```

- 成立前提是 `await next()`：await 等待的是**下游整条链** resolve；写成 `next()` 不 await，返回段提前执行，洋葱被拉平成线性。
- `index` 防重入：同一中间件里写两个 `await next()` 会因 `i <= index` 直接 reject，而不是重跑下游。
- A、B 的返回段只能在内层 C 结束后才开始——`await next()` 决定回程。

### 2.3 洋葱 vs 线性：前置后置介入
- 洋葱模型最大的优势：**可以在请求处理前后都执行逻辑**，天然适合请求耗时统计、事务管理、统一响应包装。
- 典型用法：`logger` 与 `responseTime` 进入时记 `start`、`await next()` 之后才算差值写响应头，这是线性模型做不到的「响应上半场」。
- Express 想实现同样效果要退而求其次：用 `res.on('finish')` 监听结束事件（如模板里的 `logger`）统计耗时，无法在响应发送前介入收尾。

## 3. 路由与请求数据

### 3.1 Express 路由匹配与请求数据三来源
- `app.get/post/put/delete(path, handler)` 按方法与路径分发，同一路径上挂不同方法互不干扰——**先按方法过滤，再比路径**；`:id` 是路径占位符。
- `app.use` 与 `app.get` 的差异：`use` 匹配**所有方法**且**前缀匹配**（`/user` 命中 `/user/123`）；`get` 只匹配 GET 且**精确匹配**；`app.all()` 匹配所有方法但路径仍精确。
- 请求数据的三个来源：
  1. `req.params`：路径占位符的值（`/users/:id` 命中 `/users/123` 得 `req.params.id === '123'`），**恒为字符串**，当数字用必须先 `Number()`。
  2. `req.query`：查询串自动解析（`?page=1` 进 `req.query.page`），同样只有字符串类型信息。
  3. `req.body`：挂了 `express.json()`/`urlencoded()` 才存在；`express.json()` 保留原生类型，URL 编码无类型信息只能还原出字符串；`multipart/form-data` 需另上 `multer`。
- 三者都来自客户端，必须显式校验与类型转换。

### 3.2 Koa 路由挂载与 ctx 封装
- `@koa/router` 支持 `new Router({ prefix: '/api' })` 统一前缀，用 `api.use(routes())` → `app.use(api.routes())` + `app.use(api.allowedMethods())` 挂载。
- `ctx` 是对 `req`/`res` 的封装，记两组就够：
  - **请求侧**：`ctx.method`、`ctx.url`、`ctx.path`（`?` 前）、`ctx.query`、`ctx.headers`、`ctx.request.body`（需 `koa-body`）、`ctx.params`（需路由）。
  - **响应侧**：`ctx.status`、`ctx.body`、`ctx.set(key, value)`。
- `ctx.state` 用于中间件间传数据（如 auth 写 `ctx.state.user`，控制器读 `ctx.state.user.userId`），等价于 Express 里挂 `req` 上的自定义字段；`ctx.req`/`ctx.res` 是原始 Node 对象，只在要底层能力时才碰。

### 3.3 请求体解析与静态文件托管
- Express 内置 `express.json()`、`express.urlencoded()`、`express.static('public')`；Koa 分别需 `koa-body('public')`、`koa-static`。
- `koa-body` 从 v7 起改具名导出：CommonJS 里写 `const { koaBody } = require('koa-body')`（v8 老写法报 `koaBody is not a function`）。
- multipart 文件上传两类框架都不内置，走 `multer`（Express）或 `koa-body` 的文件能力。
- 请求体中间件必须放在用到 `req.body` / `ctx.request.body` 的路由**之前**注册。

## 4. 源码原理

### 4.1 Express 最小实现
- Express 的核心只有三件事：**路由注册、中间件链、响应封装**，不到 100 行即可写出能跑的最小版本（纯 `node:http`，零第三方依赖）。
- 两个核心数据结构：`middlewares = [{ path, handler }]`（`app.use` 填充）与 `routes = [{ method, path, handler }]`（`app.get` 等填充）。
- 注册 API 重载：`app.use` 靠 `handler === undefined` 区分 `use(fn)` 与 `use(path, fn)`，前者补 `path = '/'`。
- 路由匹配：`/users/:id` 把 `:id` 替换成 `([^/]+)` 拼出 `^/users/([^/]+)$`，`url.match` 后把捕获组写回 `req.params`。
- 中间件链（线性递归）：`executeMiddlewareChain` 维护 `index`，每次 `next()` 取走 `middlewareList[index++]`；走到末尾执行回调（内层做路由匹配）；`mw.path !== '/'` 且 URL 不以它开头时直接 `next()` 跳过（前缀匹配）。
- `next(err)`：err 有值时跳过剩余中间件，直接调 `errorHandler`；未注册则回落 500。
- 响应封装（`enhanceRes`）：给原生 `res` 挂 `status(code)`（链式）、`json(data)`（设 JSON 头 + end）、`send(body)`（对象走 json、其余 text/html）。

```
请求 → app.handle → enhanceRes(res) → 中间件链（递归 next） → 路由匹配
                                                        ├─ 命中 → handler(req, res)
                                                        └─ 未命中 → notFound() = 404
        next(err) → 直接跳到 errorHandler(err, req, res, next)
```

### 4.2 Koa 的 compose 与 dispatch
- Koa 的核心比 Express 更精简，只有两件事：**洋葱中间件链（`compose`）与 Context 封装（`createContext`）**。
- `app.use` 链式：`middlewares.push(fn)` 后 `return app`，可连续 `.use(...).use(...)`。
- `compose` 返回 `function(ctx)`，从 `dispatch(0)` 启动；`dispatch` 把下个自己当 `next`：`Promise.resolve(fn(ctx, () => dispatch(i+1)))`——**`await next()` 能等下游完成全靠这句**。
- `middlewareList[i]` 为空时 `return Promise.resolve()` 是递归的自然终点。
- `index` 防重入：每次 `dispatch(i)` 先 `if (i <= index) reject` 再更新 `index = i`。
- 错误传播：任意中间件 reject 都会被 `fn(ctx).then(respond).catch(...)` 统一接住，返回 500。

```
dispatch(0) → A(ctx, ()=>dispatch(1))
                └─ await next() → dispatch(1) → B(ctx, ()=>dispatch(2))
                                                  └─ await next() → dispatch(2) → C
                                                                      └─ C return → B 后半 → A 后半 → respond(ctx)
```

### 4.3 Context 封装与响应自动生成
- `createContext` 挂 method/url/path(`?` 前)/query/headers/status/body 与 `ctx.set()`；`ctx.body` 用 defineProperty 的 setter，赋值时标记 `_respond`。
- 响应自动生成（`respond`）：`string → text/html; charset=utf-8`；对象 → `application/json` + `JSON.stringify`；Buffer → 原样 end；`null`/`undefined` → 状态码改 **204** 且不发 body。
- 给 `ctx.body` 赋值只是「标记需要响应」，真正发送发生在整条链 resolve 之后——所以外层 `await next()` 后还能改写 `ctx.body`，最终以最后一次赋值为准。

### 4.4 能力边界：最小实现 vs 真实源码
- Express 最小实现是同步 `try/catch` 加线性遍历，只能接住同步抛出的异常；真实源码有 `Router` 类、Layer 缓存与路由压缩（trie/radix tree）、完整的 `req.accepts()`/`res.cookie()`/`res.redirect()`。
- **「100 行跑通」≠「100 行能上生产」**。
- Koa 最小实现手写 `compose`/`ctx`；真源码用 `koa-compose`、ctx 双层属性委托（request/response 对象）、`ctx.onerror` 与 `app.on('error')`、支持 stream 作 `ctx.body` 与文件上传，路由交 `@koa/router`。

## 5. 工程模板

### 5.1 目录分层与依赖栈
- 分层目录：`src/` 下 config / controllers / entities / middleware / routes / services / utils 七目录 + `app.js` 入口。
- Express 依赖栈：express / cors / dotenv / typeorm / mysql2 / ioredis / jsonwebtoken / bcrypt / joi / winston。
- Koa 依赖替换：koa / @koa/router / koa-body / @koa/cors 替掉 express / cors，其余完全一致。
- 两模板均 `"dev": "node --watch src/app.js"` 免 nodemon 热重启；Koa 模板多一个 `middleware/responseTime.js`（洋葱让耗时统计成独立中间件）。

### 5.2 配置集中管理与环境变量
- `config/index.js` 先 `require('dotenv').config()` 再聚合 port / nodeEnv / database / redis / jwt；业务代码一律不直接读 `process.env`。
- `.env` 模板含 PORT、NODE_ENV、DB_*、REDIS_*、JWT_SECRET / JWT_EXPIRES；`.env.example` 作模板。
- 数据库配置用 TypeORM `DataSource`，`synchronize` 仅开发开、生产走迁移（`migrationsTableName: '_migrations_history'`）。

### 5.3 应用装配顺序与启动流程
- **Express 中间件顺序**：`cors()` → 请求日志 → `express.json()`/`urlencoded()` → 业务路由 → 健康检查 → 404 兜底 → `errorHandler`（必须最后）。CORS 在最前是把响应头在一切输出前设好；body 解析须在依赖 `req.body` 的路由前。
- **Koa 洋葱堆叠顺序**：`cors()` → `errorHandler` → `responseTime` → `logger` → `koaBody()` → 路由 → 健康检查；越先注册越靠外层，错误处理包住整条链。
- 启动流程：先 `AppDataSource.initialize()` 连库、再 `redisClient.ping()`、最后 `app.listen()`；任一步失败 `process.exit(1)`。
- 健康检查 `GET /health` 用 `SELECT 1` + `redisClient.ping()` 双探，失败返回 503。

### 5.4 数据层：TypeORM 实体声明
- 用 `EntitySchema` 声明用户与商品实体（无装饰器），如 User（email 唯一、createDate/updateDate 时间戳）、Product（price 用 `decimal(10,2)`、stock 默认 0）。
- 属性关键词：`primary` / `generated: 'increment'` / `unique` / `default` / `createDate` / `updateDate`。

```
AppDataSource.getRepository('User') → userRepo → create / save / findOneBy
```

### 5.5 三层职责：routes / controllers / services
- 划分：**routes 声明路径与中间件顺序**；**controller 取请求调 service 再 `res.json`（Koa 是 `ctx.body`）、出错 `next(err)`**；**service 只管业务规则，永远不碰 `req`/`res`**。
- routes 示例（Express）：`router.post('/register', validate(schema), controller.register)`；Koa 用 `router.post('/users/register', validate, controller.register)`。
- service 抛带标记的错误：`const err = new Error('邮箱已被注册'); err.statusCode = 409; err.isOperational = true; throw err`。
- service 不感知 HTTP 是这条线的价值：同一份 `userService` 可被定时任务 / 命令行脚本复用；一旦在 service 里写 `res.json()`，复用点就没了。
- 错误约定：409（已注册）/ 401（密码错误）/ 404（用户不存在）；错误处理器据此决定状态码与文案透传。
- 控制器写法差异的根因：Express 用 `try/catch` + `next(err)`（异步错误不会自动转交）；Koa 控制器直接 `await`，异常沿 `await next()` 的 rejection 回最外层统一处理。

### 5.6 工程中间件与工具链
- **auth**：解析 `Bearer` token → `jwt.verify` → 写 `req.user`（Koa 写 `ctx.state.user`）；TokenExpiredError 与无效 token 都回 401 但文案不同。
- **validate**：Joi `schema.validate(req.body, { abortEarly: false, stripUnknown: true })`，成功后 `req.body = value` 覆盖（Koa 写 `ctx.request.body`）。
- **errorHandler**：Express 4 参数 `(err, req, res, next)`，读 `err.statusCode || 500`、`err.isOperational` 决定状态码与文案，dev 环境附 `stack`；Koa 版最外层 `try/catch` 包 `await next()`，按 `err.statusCode || err.status || 500` 写 `ctx.status`，再 `ctx.app.emit('error', err, ctx)`。
- **logger**：Express 用 `res.on('finish')` 记 `method url statusCode duration`；Koa 用 `await next()` 前后夹（`-->`进入、`await next()` 后 `--> 返回`）。
- **utils/logger**：Winston，dev 用 debug 级 + colorize，生产写 `logs/error.log`，`format.errors({ stack: true })`；**utils/redis**：ioredis，`retryStrategy` 退避 + `maxRetriesPerRequest: 3`；**utils/schemas**：Joi 场景 schema（`abortEarly: false` 一次返回全部错误）。

## 6. 错误处理与排障

### 6.1 Express 4 参数错误中间件
- Express 通过**函数形参个数**（`fn.length`）识别中间件类型：只有 `(err, req, res, next)` 的 `.length === 4` 被当成错误处理器；普通中间件 `(req, res, next)` 的 `.length === 3`。
- 链上任意位置 `next(err)` 后，Express 跳过后面**全部普通中间件**，只找下一个 4 参数函数。
- 4 个参数必须全写，即便 `err`/`next` 用不到也不能省——省掉就退化成普通中间件，错误被静默放过。

### 6.2 Express 异步中间件抛错与修复
- Express 4 只在**同步调用栈**里 `try/catch` 中间件；async 函数返回 Promise，内部 reject 不会自动转成 `next(err)`。
- 现象：`app.use(async (req, res, next) => { throw new Error('boom') })` 触发后请求挂起或进程报未处理 rejection，错误处理中间件毫无动静。
- 三种修法：① async 中间件内部 `try/catch` 后 `next(err)`（模板每个 controller 都这么写）；② 包 `asyncHandler(fn)` 高阶函数自动 `.catch(next)`；③ 升 Express 5，已支持把 Promise rejection 转成 `next(err)`。
- 对位 Koa：Koa 天生无此问题，因为 `await next()` 把下游异常变成 rejection 顺着 await 往回抛，最外层一个 `try/catch` 就能包住整条链——这是两端模板写法差异的根因。

### 6.3 Koa 的错误处理与 404 区分
- 写法：最外层中间件 `try { await next() } catch (err) { ctx.status = err.statusCode || err.status || 500; ... }`。
- 可预期错误：`ctx.throw(401, '未登录')` 抛出带 `status` 的 HttpError，会被同一套 catch 合理处理；裸 `throw new Error()` 没有 status，只能按 500。
- **404 不是错误**：路径未命中时什么都没抛，`catch` 根本不触发；想自定义 404 文案要在路由之后补一层判断，或用 `allowedMethods()` 处理未匹配方法与路径。
- 区分 404 与真错误的判据在两端都是「有没有错误对象」。

### 6.4 状态码语义与生产环境错误响应
- 统一处理：404 兜底 `res.status(404).json(...)`；业务错误与未捕获异常经 `next(err)`（Koa 经 try/catch）返回对应状态码；401 由 auth 中间件在进路由前直接拦。
- 生产错误响应**不能直接回 `err.message`**：非预期错误的 message 可能夹带 SQL 片段、文件路径、内部字段名，原样返回是信息泄露；只有 `isOperational` 的可预期业务错误才透传文案，否则统一「服务器内部错误」。
- 开发辅助：`stack` 只在 `NODE_ENV === 'development'` 附加响应；生产把完整堆栈写进日志（`errors({ stack: true })`），用请求标识关联。
- 日志要记 `req.method` 与 `req.url`，但**绝不能**记密码、Token、Cookie 原文。

## 7. 安全与跨切面

### 7.1 CORS 跨域
- 跨域是**浏览器同源策略**的限制（协议、域名、端口任一不同即跨域），必须在**服务端响应头**解决，前端改不了。
- 方案：`cors()` 中间件（或手写 `Access-Control-Allow-Origin`/`-Methods`/`-Headers`）统一放行；JSONP 只支持 GET 已基本淘汰；开发阶段用 dev server 代理，本质是变回同源。
- **必须放最前面**：保证任何响应（含错误响应）都带跨域头，否则出错时浏览器只报「跨域」，真实错误被掩盖。
- 边界：带 `Content-Type: application/json` 或自定义头会触发**预检 OPTIONS**，要正确响应；带 Cookie 时 `Allow-Origin` 必须是具体 Origin（不能 `*`）+ `Access-Control-Allow-Credentials`。

### 7.2 CSRF 与安全手段
- CSRF 是攻击者利用浏览器**自动携带 Cookie** 的特性在用户已登录状态下伪造请求；CORS 管不了它（CORS 只限制读取响应，不阻止请求发出）。
- 三种手段：① CSRF Token——服务端签发、随表单或请求头回传后校验；② Cookie 设 `SameSite=Lax/Strict` 从源头限制跨站携带；③ 校验 `Origin`/`Referer`，让非简单请求（带自定义头）触发预检。
- JWT 放 `Authorization` 头而非 Cookie 的方案天然免疫 CSRF（不会被自动携带）；但 Token 存 `localStorage` 又引入 XSS 风险——CSRF 与 XSS 是两个方向，别混为一谈。

### 7.3 跨切面应用：耗时统计与事务
- 洋葱模型的杀手锏：请求**前后都能介入**，把「统计耗时、事务管理、统一响应包装、统一错误」做成独立中间件而非散落在每个 route。
- 例：`responseTime` 中间件 `start = Date.now()` → `await next()` → `ctx.set('X-Response-Time', ...)`；`logger` 用 `await next()` 夹出上下半场。
- 一个能挂数据库与缓存的 Web 服务骨架正是本模块的收口——Express 与 Koa 两条线各自走完「快速入门 → 工程模板 → 源码原理」后在中间件心智上闭环。
