## 第二阶段：Node.js 基础

### Q106: 事件循环的六个阶段分别做什么？

① 一句话结论：事件循环的六个阶段依次是 timers、pending callbacks、idle/prepare、poll、check、close callbacks，每个阶段维护一个回调队列，循环执行。

② 原理剖析：**timers** 阶段执行 setTimeout/setInterval 到期回调；**pending callbacks** 执行延迟到下一轮的 I/O 回调；**idle/prepare** 内部使用；**poll** 获取新 I/O 事件并执行回调，若无回调则检查是否有 setImmediate 或到期定时器；**check** 执行 setImmediate 回调；**close callbacks** 执行 close 事件回调（如 socket.on('close')）。每个阶段执行完毕后，会检查微任务队列（process.nextTick 优先于 Promise）。

③ 场景举例：
```js
const fs = require('fs');
fs.readFile(__filename, () => {
  setTimeout(() => console.log('timer'), 0);
  setImmediate(() => console.log('immediate'));
});
// 输出顺序：immediate → timer（readFile 回调在 poll 阶段执行，setImmediate 在 check 阶段先执行）
```

④ 优缺点与边界：理解事件循环是 Node.js 异步编程的核心，但面试易混淆的是微任务（nextTick/Promise）在每个阶段间隙执行，而非在阶段内部。

⑤ 追问预判：process.nextTick 与 Promise.then 的执行顺序？uv_run 一次迭代的完整流程？

### Q107: setImmediate 和 setTimeout 的执行顺序为什么不确定？

① 一句话结论：在主模块中执行时顺序不确定，因为 setTimeout(fn, 0) 的延迟时间受 event loop 启动开销影响；在 I/O 回调中执行时 setImmediate 永远先于 setTimeout。

② 原理剖析：setTimeout(fn, 0) 的延迟至少为 1ms（Node.js 对 0 做了 clamp）。主模块执行时，事件循环尚未进入 timers 阶段，若 1ms 已过则 timers 阶段先执行；若 1ms 未过则 poll 阶段先处理 I/O 事件，然后 check 阶段执行 setImmediate。在 I/O 回调中，当前处于 poll 阶段，setImmediate 在接下来的 check 阶段执行，而 setTimeout 需等到下一轮 timers 阶段，因此 setImmediate 始终先执行。

③ 场景举例：
```js
// 主模块中：顺序不确定
setTimeout(() => console.log('timeout'), 0);
setImmediate(() => console.log('immediate'));
// 可能 immediate 先，也可能 timeout 先

// I/O 回调中：immediate 始终先于 timeout
require('fs').readFile(__filename, () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
});
```

④ 优缺点与边界：这是 Node.js 事件循环的设计细节，实际开发中应避免依赖此不确定顺序，改用 process.nextTick 或明确逻辑控制。

⑤ 追问预判：setTimeout(fn, 0) 在浏览器中表现如何？最小延迟时间是多少？

### Q108: Node.js 中如何实现进程间通信（IPC）？

① 一句话结论：Node.js 通过 `child_process.fork()` 创建的进程自动建立 IPC 通道，使用 `send()` 和 `message` 事件实现双向通信。

② 原理剖析：fork() 在创建子进程时，Node.js 内部会建立一个 IPC 通道（Unix 域套接字或 Windows 命名管道），通过该通道传递序列化后的消息。父进程调用 `child.send()` 发送消息，子进程通过 `process.on('message')` 接收；子进程通过 `process.send()` 回复，父进程通过 `child.on('message')` 接收。消息传递采用 JSON 序列化，不支持函数或 Symbol。

③ 场景举例：
```js
// parent.js
const { fork } = require('child_process');
const child = fork('./child.js');
child.send({ cmd: 'compute', data: [1, 2, 3] });
child.on('message', (msg) => console.log('结果:', msg));

// child.js
process.on('message', (msg) => {
  if (msg.cmd === 'compute') {
    process.send(msg.data.reduce((a, b) => a + b, 0));
  }
});
```

④ 优缺点与边界：IPC 通信简单易用，但消息体积过大时性能下降；不支持共享内存，适合传递控制指令和小数据量任务。

⑤ 追问预判：如何实现进程间共享内存？IPC 和 HTTP 通信的区别？

### Q109: Cluster 模式下主进程和子进程如何通信？

① 一句话结论：Cluster 模式下主进程和子进程通过内置的 IPC 通道通信，主进程可向指定子进程发送消息，子进程向主进程发送消息，也可通过 `cluster.workers` 遍历所有子进程。

② 原理剖析：`cluster.fork()` 底层调用 `child_process.fork()`，每个子进程自动建立 IPC 通道。主进程通过 `worker.send()` 向特定子进程发消息，子进程通过 `process.send()` 回复主进程。主进程可在 `worker.on('message')` 中接收子进程消息。此外，主进程可通过 `cluster.on('message')` 统一监听所有子进程的消息。

③ 场景举例：
```js
const cluster = require('cluster');
if (cluster.isMaster) {
  const worker = cluster.fork();
  worker.send({ type: 'config', port: 3000 });
  worker.on('message', (msg) => console.log('来自子进程:', msg));
} else {
  process.on('message', (msg) => {
    if (msg.type === 'config') process.send({ ok: true });
  });
}
```

④ 优缺点与边界：Cluster IPC 无法直接广播到所有子进程（需手动遍历），子进程间也无法直接通信，需通过主进程转发。适合负载均衡场景下的消息下发。

⑤ 追问预判：如何实现主进程共享内存状态？子进程崩溃后如何保证消息不丢失？

## 第四阶段：数据库 - MySQL

### Q110: 什么是 MVCC？MVCC 如何实现可重复读？

① 一句话结论：MVCC（Multi-Version Concurrency Control）是多版本并发控制，通过每行数据的多个版本实现无锁读取，InnoDB 利用它实现可重复读隔离级别。

② 原理剖析：MVCC 在每行记录后隐藏两个字段：`DB_TRX_ID`（最近修改事务 ID）和 `DB_ROLL_PTR`（回滚指针，指向 undo log 中前一版本）。事务开始时生成一个 `read view`（活跃事务 ID 快照），可重复读隔离级别下，一个事务只在首次查询时创建 read view，后续复用。查询时只读取 `DB_TRX_ID` 小于 read view 中最小活跃事务 ID 的版本，确保事务内看到一致的数据快照。

③ 场景举例：
```
事务 A（trx_id=100）: BEGIN; SELECT * FROM user WHERE id=1; -- 读取 trx_id=99 的版本
事务 B（trx_id=101）: UPDATE user SET name='new' WHERE id=1; -- 产生新版本
事务 A: SELECT * FROM user WHERE id=1; -- 仍看到 trx_id=99 的旧版本（可重复读）
```

④ 优缺点与边界：MVCC 实现了读不阻塞写、写不阻塞读，但 `间隙锁`（Gap Lock）仍需配合 MVCC 才能完全避免幻读。可重复读下，MySQL 对当前读（SELECT FOR UPDATE）使用锁，快照读使用 MVCC。

⑤ 追问预判：MVCC 在 RC（读已提交）和 RR（可重复读）下的 read view 创建时机有何不同？undo log 何时清理？

### Q111: InnoDB 如何避免幻读？

① 一句话结论：InnoDB 在可重复读隔离级别下，通过 **MVCC 快照读** + **间隙锁（Gap Lock）** 组合避免幻读。

② 原理剖析：幻读指同一事务内两次查询返回不同行数。InnoDB 的解决方案分两种：快照读（普通 SELECT）利用 MVCC 的 read view 机制，始终返回事务开始时的快照，不会出现新行；当前读（SELECT FOR UPDATE/UPDATE/DELETE）使用 **Next-Key Lock**（行锁 + 间隙锁），锁定扫描范围内所有间隙，阻止其他事务插入新行。间隙锁仅在 RR 级别生效，RC 级别仅使用行锁。

③ 场景举例：
```sql
-- 事务 A
BEGIN;
SELECT * FROM user WHERE age > 20 FOR UPDATE;
-- 锁定 age > 20 的所有行 以及 (20, +∞) 的间隙

-- 事务 B（阻塞）
INSERT INTO user(age) VALUES(25); -- 被间隙锁阻塞，无法插入
```

④ 优缺点与边界：间隙锁有效避免了幻读，但会降低并发性能，尤其在范围查询频繁的场景下。若业务不需要防幻读，可降级到 RC 级别提升性能。

⑤ 追问预判：间隙锁何时会升级为表锁？如何排查间隙锁导致的死锁？

### Q112: 什么是覆盖索引？为什么覆盖索引能提升性能？

① 一句话结论：覆盖索引指查询所需的所有字段都包含在索引中，无需回表查询，从而大幅提升查询性能。

② 原理剖析：InnoDB 的聚簇索引叶子节点存储完整行数据，二级索引叶子节点存储主键值。当查询命中二级索引，且 SELECT 的字段全部在该索引中时，MySQL 直接从索引树中获取数据，无需通过主键回表查询完整行，减少了磁盘 I/O 次数。使用 `EXPLAIN` 查看执行计划时，Extra 列出现 `Using index` 即表示使用了覆盖索引。

③ 场景举例：
```sql
-- 创建联合索引
CREATE INDEX idx_name_age ON user(name, age);
-- 覆盖索引查询（Extra: Using index）
SELECT name, age FROM user WHERE name = 'Alice';
-- 非覆盖索引查询（需回表）
SELECT * FROM user WHERE name = 'Alice';
```

④ 优缺点与边界：覆盖索引减少了 I/O 但增加了索引体积，且更新索引字段时开销更大。不适合写多读少、索引字段频繁更新的场景。

⑤ 追问预判：如何通过 EXPLAIN 判断是否使用了覆盖索引？覆盖索引和联合索引的关系？

### Q113: 什么是索引下推（ICP）？

① 一句话结论：索引下推（Index Condition Pushdown）是 MySQL 5.6 引入的优化，将 WHERE 条件中部分过滤操作下推到存储引擎层，在索引遍历过程中提前过滤，减少回表次数。

② 原理剖析：没有 ICP 时，存储引擎通过索引定位到行后，将所有满足索引条件的行返回给 Server 层，Server 层再对 WHERE 条件中非索引列进行过滤。启用 ICP 后，存储引擎在遍历索引时，直接对索引中包含的字段执行 WHERE 过滤，仅把满足条件的行回表，减少回表 I/O。ICP 适用于 `二级索引` 且查询条件包含索引列和非索引列的场景。

③ 场景举例：
```sql
-- 联合索引 idx(name, age)
SELECT * FROM user WHERE name LIKE 'A%' AND age = 18;
-- 无 ICP：通过 name 范围找到所有以 A 开头的行，逐行回表再过滤 age
-- 有 ICP：在索引树遍历时，同时检查 age=18，仅满足条件的行才回表
```

④ 优缺点与边界：ICP 对范围查询（LIKE、BETWEEN）场景性能提升明显，但对聚簇索引不生效（因为聚簇索引本身包含完整行数据，无需回表）。

⑤ 追问预判：ICP 在 EXPLAIN 中如何体现？ICP 和覆盖索引的区别与联系？

### Q114: 分库分表后 ID 主键如何处理？

① 一句话结论：分库分表后不能使用数据库自增 ID，常用方案包括雪花算法（Snowflake）、UUID、号段模式（Segment）或 Redis 自增 ID。

② 原理剖析：自增 ID 在分库分表后各库独立生成，必然产生重复。雪花算法生成 64 位 Long 型 ID（1 位符号位 + 41 位时间戳 + 10 位工作机器 ID + 12 位序列号），全局唯一且趋势递增。号段模式通过集中分配器（如数据库）批量获取 ID 段，本地缓存分配，性能高。UUID 虽全局唯一，但无序且长度长，不适合作为聚簇索引主键（导致 B+ 树频繁分裂）。

③ 场景举例：
```js
// 雪花算法（Snowflake）ID 结构
// 0 | 0000000000 0000000000 0000000000 0000000000 0 | 00000 | 00000 | 000000000000
// 符号位 (1) | 时间戳 (41) | 机器 ID (10) | 序列号 (12)
```

④ 优缺点与边界：雪花算法 ID 趋势递增、性能好，但依赖机器时钟，时钟回拨会导致 ID 重复。号段模式性能最佳但需额外维护分配器。UUID 简单但性能差，不推荐作为主键。

⑤ 追问预判：雪花算法时钟回拨如何解决？美团 Leaf 和滴滴 TinyID 的方案对比？

## 第四阶段：数据库 - MongoDB

### Q115: MongoDB 聚合管道中的 $lookup 和 MySQL 的 JOIN 的区别？

① 一句话结论：$lookup 是 MongoDB 3.2 引入的左外连接操作，功能类似 MySQL 的 LEFT JOIN，但执行机制和性能表现差异较大。

② 原理剖析：$lookup 在聚合管道中对当前集合的每条文档，去目标集合中匹配符合条件的文档，合并为数组字段。与 MySQL JOIN 的最关键区别：MySQL 的 JOIN 在单次查询中由优化器选择执行计划（如 Nested Loop Join、Hash Join），而 $lookup 本质是逐文档查询，性能受限于集合大小和索引。$lookup 不支持内连接、右连接，需通过 $unwind 等后续阶段模拟。MySQL JOIN 支持更丰富的连接类型和优化策略。

③ 场景举例：
```js
// MongoDB $lookup
db.orders.aggregate([
  {
    $lookup: {
      from: "products",
      localField: "productId",
      foreignField: "_id",
      as: "product"
    }
  }
]);
```

④ 优缺点与边界：$lookup 适合简单关联查询，但复杂关联场景性能远不如 MySQL JOIN。MongoDB 设计哲学是尽量用嵌入文档避免关联，频繁使用 $lookup 可能意味着数据模型设计不合理。

⑤ 追问预判：$lookup 性能如何优化？$lookup 和 $unwind 配合使用有哪些注意事项？

### Q116: 什么是 MongoDB 的事务？从什么版本开始支持多文档事务？

① 一句话结论：MongoDB 从 4.0 版本开始支持副本集下的多文档事务，4.2 版本扩展到分片集群，提供 ACID 事务保证。

② 原理剖析：MongoDB 事务支持在多个集合或文档间执行原子操作，具备 ACID 特性（原子性、一致性、隔离性、持久性）。事务使用快照隔离级别，在事务开始时创建数据快照，事务内所有读取都基于该快照。事务通过 `session.startTransaction()` 启动，`session.commitTransaction()` 提交，`session.abortTransaction()` 回滚。MongoDB 事务的隔离级别是可重复读，但写操作使用乐观锁，冲突时通过 WiredTiger 存储引擎的并发控制处理。

③ 场景举例：
```js
const session = db.getMongo().startSession();
session.startTransaction();
try {
  db.collection1.updateOne({ _id: 1 }, { $set: { status: 'done' } }, { session });
  db.collection2.insertOne({ ref: 1, log: 'completed' }, { session });
  session.commitTransaction();
} catch (e) {
  session.abortTransaction();
} finally {
  session.endSession();
}
```

④ 优缺点与边界：MongoDB 事务提供强一致性，但性能开销比原生操作大（事务日志、锁管理），不适合高频小事务场景。建议仅在确实需要跨文档原子性时使用。

⑤ 追问预判：MongoDB 事务的隔离级别是什么？事务对性能的影响有多大？

### Q117: MongoDB 副本集和分片集群的区别？

① 一句话结论：副本集解决高可用和数据冗余，分片集群解决水平扩展和海量数据存储，两者可组合使用。

② 原理剖析：**副本集**（Replica Set）由 Primary（主节点）、Secondary（从节点）和 Arbiter（可选仲裁节点）组成，Primary 处理所有写操作，Secondary 异步同步数据并可在 Primary 宕机后选举为新主。**分片集群**（Sharded Cluster）由三个组件组成：分片（Shard，存储数据子集，一般是副本集）、配置服务器（Config Server，存储元数据）、路由节点（mongos，作为入口转发查询）。分片集群通过分片键（Shard Key）将数据分布到多个分片，解决单机存储和性能瓶颈。

③ 场景举例：
```
副本集适用场景：数据量 < 500GB，需要高可用
分片集群适用场景：数据量 TB 级，单机无法承载
组合使用：每个 Shard 是一个副本集，兼顾扩展性和高可用
```

④ 优缺点与边界：副本集最多支持 50 个节点，且写性能受限于 Primary 单机。分片集群增加了运维复杂度，分片键选择不当会导致数据倾斜或性能瓶颈。

⑤ 追问预判：分片键如何选择？如何为现有副本集扩展为分片集群？

## 第六阶段：NestJS 进阶

### Q118: ExecutionContext 的 switchToHttp、switchToRpc、switchToWs 的区别？

① 一句话结论：switchToHttp/Rpc/Ws 是 ExecutionContext 提供的三个切换方法，分别用于获取 HTTP、RPC（微服务）和 WebSocket 通信协议的上下文对象。

② 原理剖析：NestJS 支持多种传输层（HTTP、TCP/Redis/RabbitMQ 微服务、WebSocket），ExecutionContext 抽象了不同协议的请求处理。`switchToHttp()` 返回 `HttpArgumentsHost`，提供 `getRequest()` 和 `getResponse()` 方法；`switchToRpc()` 返回 `RpcArgumentsHost`，提供 `getData()` 获取消息数据；`switchToWs()` 返回 `WsArgumentsHost`，提供 `getClient()` 和 `getData()`。自定义 Guard/Interceptor/Filter 中通过该方法适配不同协议。

③ 场景举例：
```ts
@Injectable()
export class AuthGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    if (context.getType() === 'http') {
      const request = context.switchToHttp().getRequest();
      // 从 HTTP 请求头获取 token
    } else if (context.getType() === 'rpc') {
      const data = context.switchToRpc().getData();
      // 从 RPC 消息中获取 token
    }
    return true;
  }
}
```

④ 优缺点与边界：三种方法不能混用，如调用 switchToHttp() 但当前请求是 WebSocket 会抛出异常。建议先通过 `context.getType()` 判断协议类型。

⑤ 追问预判：如何开发一个同时支持 HTTP 和 WebSocket 的 Guard？getType() 返回值的类型有哪些？

### Q119: 如何实现一个支持依赖注入的全局拦截器？

① 一句话结论：在 NestJS 中，全局拦截器通过在模块中注册为 `APP_INTERCEPTOR` 提供者实现，或通过 `app.useGlobalInterceptors()` 注册，但后者无法注入依赖。

② 原理剖析：`app.useGlobalInterceptors()` 注册的拦截器不在 DI 容器内，无法使用 `&#64;Injectable()` 注入其他服务。正确做法在模块中注册：

```ts
import { APP_INTERCEPTOR } from '@nestjs/core';

@Module({
  providers: [
    { provide: APP_INTERCEPTOR, useClass: LoggingInterceptor }
  ]
})
```

这样 NestJS 会将拦截器注册为全局单例，且 LoggingInterceptor 可通过构造函数注入其他服务。

③ 场景举例：
```ts
@Injectable()
export class LoggingInterceptor implements NestInterceptor {
  constructor(private readonly logger: Logger) {} // 注入 Logger
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    return next.handle().pipe(tap(() => this.logger.log('Request completed')));
  }
}
```

④ 优缺点与边界：模块注册方式支持依赖注入，但拦截器在模块作用域内生效（除非在根模块注册）。注意多个全局拦截器的执行顺序是按注册顺序的。

### Q120: 自定义装饰器中如何结合 Reflector 实现元数据读取？

① 一句话结论：通过 `&#64;SetMetadata()` 或自定义装饰器设置元数据，然后在 Guard/Interceptor 中通过 `Reflector` 读取元数据，实现基于角色的权限控制等场景。

② 原理剖析：NestJS 的 `Reflector` 封装了 `Reflect.defineMetadata`，提供 `get()`、`getAll()`、`getAllAndOverride()` 等方法读取元数据。自定义装饰器通常使用 `&#64;SetMetadata()` 或 `Reflect.defineMetadata` 将数据附加到类/方法上。在 Guard 或 Interceptor 中注入 Reflector，通过 `reflector.get(key, context.getHandler())` 获取方法上的元数据，或 `reflector.get(key, context.getClass())` 获取类上的元数据。

③ 场景举例：
```ts
// 自定义装饰器
export const Roles = (...roles: string[]) => SetMetadata('roles', roles);

// 使用 Reflector 读取
@Injectable()
export class RolesGuard implements CanActivate {
  constructor(private reflector: Reflector) {}
  canActivate(context: ExecutionContext): boolean {
    const roles = this.reflector.getAllAndOverride<string[]>('roles', [
      context.getHandler(),
      context.getClass(),
    ]);
    if (!roles) return true;
    const { user } = context.switchToHttp().getRequest();
    return roles.includes(user.role);
  }
}
```

④ 优缺点与边界：Reflector 支持按 `getAllAndOverride` 和 `getAllAndMerge` 两种策略合并类级别和方法级别的元数据，前者方法覆盖类，后者合并。

### Q121: 什么是异步自定义装饰器？

① 一句话结论：异步自定义装饰器是指在装饰器工厂函数中执行异步操作（如数据库查询、HTTP 请求），通常通过 `SetMetadata` 存储元数据，在 Guard/Interceptor 中执行异步逻辑，而非在装饰器本身中 await。

② 原理剖析：装饰器本身是同步的，不能直接使用 async/await（会被 TypeScript 编译为返回 Promise 的函数，但装饰器期望的是同步函数）。实现异步装饰器有两条路径：一是在装饰器中使用 `SetMetadata` 标记元数据，在 Guard 或 Interceptor 中执行异步逻辑；二是在参数装饰器中使用 `async` 函数，但必须注意 TypeScript 实验性装饰器的限制。更常见的做法是依赖 NestJS 的 Guard/Interceptor 处理异步操作。

③ 场景举例：
```ts
// 推荐做法：装饰器仅设置元数据，Guard 中执行异步
export const Permission = (perm: string) => SetMetadata('permission', perm);

@Injectable()
export class PermissionGuard implements CanActivate {
  async canActivate(context: ExecutionContext): Promise<boolean> {
    const perm = this.reflector.get('permission', context.getHandler());
    const user = context.switchToHttp().getRequest().user;
    const hasPerm = await this.permService.checkPermission(user.id, perm);
    return hasPerm;
  }
}
```

④ 优缺点与边界：装饰器本身不能是 async 函数，这是一个常见误解。异步逻辑应放在 Guard/Interceptor 中，装饰器只做元数据标记，遵循职责分离原则。

⑤ 追问预判：TypeScript 装饰器为什么不能是 async 的？如何在参数装饰器中执行异步操作？

### Q122: 微信小程序登录的流程是怎样的？

① 一句话结论：微信小程序登录通过 `wx.login()` 获取临时 code，后端用 code 换取 openid 和 session_key，服务端生成自定义登录态（如 JWT token）返回给小程序。

② 原理剖析：流程分为三步：小程序调用 `wx.login()` 获取临时 code（有效期 5 分钟）；后端调用微信接口 `https://api.weixin.qq.com/sns/jscode2session` 传入 appid、secret、code，获取 `openid`（用户唯一标识）和 `session_key`（会话密钥，用于解密敏感数据）；后端生成自定义 token（如 JWT）返回给小程序，小程序后续请求携带该 token 完成身份认证。`session_key` 不应返回给客户端，也不应作为 token 使用。

③ 场景举例：
```ts
@Controller('auth')
export class AuthController {
  @Post('wx-login')
  async wxLogin(@Body('code') code: string) {
    const { openid, session_key } = await this.wxService.code2Session(code);
    const token = this.jwtService.sign({ openid });
    return { token };
  }
}
```

④ 优缺点与边界：code 只能使用一次，session_key 有效期内不会变。需注意 code 过期、微信服务器异常等边界情况。小程序端还应调用 `wx.checkSession()` 检查 session_key 是否过期。

### Q123: 如何实现微信登录的 Guard？

@Injectable()
export class JwtStrategy extends PassportStrategy(Strategy) {

### Q124: 缓存穿透场景下布隆过滤器的原理和实现？

① 一句话结论：布隆过滤器是一种概率型数据结构，用于判断一个元素是否在集合中，可以高效拦截缓存穿透中不存在的 Key 查询，但存在一定的误判率。

② 原理剖析：布隆过滤器由一个位数组和多个哈希函数组成。插入元素时，元素经过 k 个哈希函数得到 k 个位位置，将这些位设为 1。查询时同样计算 k 个位位置，若所有位均为 1 则认为存在（可能有误判），若任意一位为 0 则一定不存在（无漏判）。在缓存穿透场景中，先将所有可能查询的 Key 存入布隆过滤器，请求到达时先检查过滤器，若不存在则直接返回，不查询数据库和缓存。

③ 场景举例：
```ts
// 使用 redis 的布隆过滤器模块
@Injectable()
export class BloomFilterService {
  constructor(@InjectRedis() private redis: Redis) {}
  async add(key: string) {
    await this.redis.bfAdd('cache:bloom', key);
  }
  async exists(key: string): Promise<boolean> {
    return this.redis.bfExists('cache:bloom', key);
  }
}
```

④ 优缺点与边界：布隆过滤器无法删除元素（可用计数布隆过滤器或布谷鸟过滤器替代），且存在误判率（可通过调整位数组大小和哈希函数数量控制）。适合对误判不敏感的场景，如缓存穿透拦截。

⑤ 追问预判：布隆过滤器的误判率如何计算？布谷鸟过滤器相比布隆过滤器的优势？

### Q125: Redis 分布式锁的实现方式？SETNX 的缺陷？

① 一句话结论：Redis 分布式锁通过 `SET key value NX EX seconds` 命令实现，SETNX 的缺陷在于不可重入、无自动续期以及单点故障问题，Redlock 算法可提供更可靠的分布式锁方案。

② 原理剖析：正确的加锁命令是 `SET lock_key unique_id NX EX 30`（NX 表示不存在时才设置，EX 设置过期时间），使用唯一 ID（如 UUID）作为 value 确保锁只能被持有者释放。SETNX 的缺陷：**不可重入**（同一线程不能重复加锁，否则死锁）；**无自动续期**（业务执行超时锁自动释放，其他线程拿到锁导致并发问题）；**单点故障**（Redis 主节点宕机，从节点未同步导致锁丢失）。Redlock 算法在多个独立 Redis 节点上同时加锁，过半成功才算加锁成功，解决单点问题。

③ 场景举例：
```ts
// 加锁
const result = await redis.set(`lock:order:${orderId}`, uuid, 'NX', 'EX', 30);
if (result === 'OK') {
  try { await processOrder(orderId); }
  finally { await redis.eval(`if redis.call('get', KEYS[1]) == ARGV[1] then redis.call('del', KEYS[1]) end`, 1, lockKey, uuid); }
}
```

④ 优缺点与边界：Redis 分布式锁适合大多数场景，但对强一致性要求极高的场景（如金融交易）建议使用 ZooKeeper 或 etcd 的分布式锁，它们提供严格的线性一致性。

⑤ 追问预判：Redlock 算法是否真的安全（Martin Kleppmann 的争议）？如何实现可重入分布式锁？

### Q126: 消息队列的核心作用是什么？

① 一句话结论：消息队列的核心作用是**异步解耦、削峰填谷、可靠通信**，通过生产者-消费者模型将服务间直接调用改为间接通信。

② 原理剖析：**异步解耦**：生产者发送消息后立即返回，消费者异步处理，服务间不直接依赖，单个消费者故障不影响生产者。**削峰填谷**：突发流量时消息在队列中缓冲，消费者按自身处理能力消费，避免下游系统被瞬间流量打垮。**可靠通信**：消息持久化到磁盘，配合确认机制和重试，保证消息不丢失。此外消息队列还提供发布订阅、顺序消息、死信队列等高级特性。

③ 场景举例：
```
用户下单 → 订单服务 → 发送消息到队列 → 库存服务（扣库存）→ 通知服务（发短信）
                         ↓ 异步处理
                  用户立即收到"下单成功"响应
```

④ 优缺点与边界：引入消息队列增加了系统复杂度（消息丢失、重复消费、顺序问题），且需额外运维成本。适合需要异步处理、流量削峰的场景，不适合强实时同步调用。

⑤ 追问预判：消息队列如何保证消息不重复消费？消息队列的优缺点权衡？

### Q127: Kafka 和 RabbitMQ 的选型对比？

① 一句话结论：Kafka 适合高吞吐量日志收集和流式处理，RabbitMQ 适合低延迟、灵活路由和事务性消息场景。

② 原理剖析：**Kafka** 采用拉模型、顺序写入磁盘、批量压缩，吞吐量可达百万级/秒，消息持久化到磁盘，通过分区实现并行消费，但消息确认机制较简单，可能丢失少量消息（取决于 acks 配置）。**RabbitMQ** 采用推模型，支持多种交换机类型（direct、topic、fanout、headers），路由灵活，消息确认机制完善（ACK/NACK），支持延迟队列、死信队列等特性，但吞吐量通常为万级/秒。

③ 场景举例：
```
Kafka 适合：日志收集、用户行为追踪、Metrics 监控、流计算（Flink/Spark）
RabbitMQ 适合：订单处理、任务调度、通知推送、异步 RPC
```

④ 优缺点与边界：Kafka 的拉模型在高吞吐场景下表现优异，但消息延迟较高（毫秒级），不适合需要毫秒级响应的低延迟场景。RabbitMQ 延迟低（微秒级），但吞吐量有限。

⑤ 追问预判：Kafka 的推模型和拉模型各自优缺点？RabbitMQ 如何实现高可用？

### Q128: Kafka 的整体架构是怎样的？核心组件有哪些？

① 一句话结论：Kafka 架构由 Producer、Broker、Consumer、Topic、Partition、ZooKeeper（或 KRaft）组成，Producer 发布消息到 Topic 的不同 Partition，Consumer 从 Partition 拉取消费。

② 原理剖析：**Producer**：消息生产者，将消息发送到指定 Topic，可指定分区策略（轮询、key 哈希、自定义）。**Broker**：Kafka 集群节点，每个 Broker 可以托管多个 Partition，负责消息存储和读写。**Topic**：消息的逻辑分类，一个 Topic 包含多个 Partition。**Partition**：消息存储的最小单位，每个 Partition 是顺序写的有序日志文件，分区内消息有序。**Consumer Group**：消费者组，组内每个消费者负责消费不同 Partition，组间独立消费。**ZooKeeper/KRaft**：管理集群元数据、Broker 注册、Controller 选举（新版本已逐步移除 ZooKeeper 依赖）。

③ 场景举例：
```
Topic: user_events
  ├── Partition 0 (存储在 Broker 1)
  ├── Partition 1 (存储在 Broker 2)
  └── Partition 2 (存储在 Broker 3)
Consumer Group A: Consumer A1 消费 P0, Consumer A2 消费 P1, P2
```

④ 优缺点与边界：Kafka 的 Partition 是并行消费的单位，Partition 数量决定了消费的最大并行度，但过多 Partition 会带来文件句柄和选举开销。

⑤ 追问预判：Kafka 如何保证分区内消息有序？ISR 机制（In-Sync Replicas）的原理？

### Q129: 生产者发送消息的 acks 参数 0/1/-1 的含义与选择？

① 一句话结论：acks 参数控制生产者消息写入的确认级别，0 表示不等待确认（最快），1 表示等待 Leader 确认（默认），-1 表示等待所有 ISR 副本确认（最安全）。

② 原理剖析：**acks=0**：生产者发送消息后立即返回，不等待任何确认，可能丢失消息（Leader 写入失败时无感知），吞吐量最高。**acks=1**：生产者等待 Leader Partition 写入成功后返回，但 Leader 宕机且未同步给 Follower 时消息可能丢失，折中方案。**acks=-1（all）**：生产者等待所有 ISR（In-Sync Replicas）副本写入成功后返回，最强持久性保证，但延迟最高，且如果 min.insync.replicas 配置不当可能导致无法写入。

③ 场景举例：
```
日志收集（可容忍少量丢失）：acks=0
核心业务订单（必须保证不丢）：acks=-1 + min.insync.replicas=2
默认推荐：acks=1
```

④ 优缺点与边界：acks=-1 并不绝对保证不丢（如果所有 ISR 都宕机），还需配合 `min.insync.replicas` 和 `replication.factor` 共同保证。acks=0 在重试机制下也可能产生重复消息。

⑤ 追问预判：acks=-1 和 min.insync.replicas 的关系？如何设置保证消息不丢但性能可接受？

### Q130: 如何保证消息不丢失（生产者端、Broker 端、消费者端）？

① 一句话结论：消息不丢失需要在生产者、Broker、消费者三端各自配置确认机制，形成端到端的可靠链路。

② 原理剖析：**生产者端**：设置 `acks=-1`（所有 ISR 确认），开启重试 `retries > 0`，使用同步发送或回调确认发送结果，避免使用 fire-and-forget 模式。**Broker 端**：设置 `replication.factor >= 3`，`min.insync.replicas >= 2`，`unclean.leader.election.enable=false`（防止非 ISR 副本成为 Leader），启用日志持久化。**消费者端**：关闭自动提交 `enable.auto.commit=false`，在业务处理成功后再手动提交 offset，确保消息处理完成后再提交消费进度。

③ 场景举例：
```ts
// 消费者端手动提交
consumer.subscribe(['topic']);
await consumer.run({
  eachMessage: async ({ message, topic, partition }) => {
    await processMessage(message.value); // 先处理业务
    await consumer.commitOffsets([{ topic, partition, offset: (Number(message.offset) + 1).toString() }]); // 再提交
  }
});
```

④ 优缺点与边界：严格保证不丢失会降低吞吐量（acks=-1），且可能产生重复消息（生产者重试导致），需配合幂等性设计处理。消息丢失和消息重复通常是 trade-off 关系。

⑤ 追问预判：幂等性生产者如何实现？如何保证消息的恰好一次（Exactly Once）语义？

## 第九阶段：进阶主题 - 性能优化

### Q131: 什么是缓存预热？什么是缓存降级？

① 一句话结论：缓存预热是在系统上线或重启后主动将热点数据加载到缓存中，避免大量请求直接穿透到数据库；缓存降级是在系统压力过大时主动关闭非核心功能，释放资源保障核心功能。

② 原理剖析：**缓存预热**：系统启动后，通过定时任务或启动监听器，从数据库加载热数据到 Redis，设置合理的过期时间并配合异步刷新，避免冷启动时缓存穿透。**缓存降级**：当系统负载超过阈值（如 CPU 90%、QPS 超限），通过开关或自动检测，降级非核心功能（如商品详情页的推荐模块、评论展示），直接返回缓存或默认值，甚至返回错误提示，确保核心链路（如下单、支付）可用。

③ 场景举例：
```ts
// 缓存预热
@Injectable()
export class CacheWarmupService implements OnApplicationBootstrap {
  async onApplicationBootstrap() {
    const hotProducts = await this.db.query('SELECT * FROM products WHERE hot = 1');
    await this.redis.set('hot:products', JSON.stringify(hotProducts), 'EX', 3600);
  }
}
```

④ 优缺点与边界：缓存预热需考虑数据量，预热时间过长会延迟服务启动。缓存降级需设计合理的降级策略和恢复机制，避免降级后无法自动恢复。

⑤ 追问预判：缓存预热如何保证数据一致性？降级开关如何设计（配置中心 vs 本地配置）？

### Q132: 为什么 Redis 是单线程的却这么快？

① 一句话结论：Redis 单线程模型基于内存操作、非阻塞 I/O 多路复用和高效的数据结构，避免了多线程竞争和上下文切换开销，因此性能极高。

② 原理剖析：**内存操作**：Redis 数据全部存储在内存中，读写速度纳秒级，不受磁盘 I/O 瓶颈限制。**I/O 多路复用**：Redis 使用 epoll（Linux）/kqueue（macOS）实现单线程处理多个客户端连接，网络 I/O 采用非阻塞模式。**避免锁竞争**：单线程模型天然避免了多线程并发访问共享数据的锁开销和上下文切换。**高效数据结构**：Redis 内部使用 SDS（简单动态字符串）、跳表、压缩列表等优化数据结构，减少内存碎片。

③ 场景举例：
```
单线程处理模型：
主线程：accept → 读事件 → 解析命令 → 执行命令 → 写事件
（所有操作在主线程中串行执行，不存在并发问题）
```

④ 优缺点与边界：单线程的瓶颈在于单个命令不能耗时过长（如 KEYS、FLUSHALL），否则会阻塞其他命令。Redis 6.0 引入了多线程 I/O（仅用于网络读写，命令执行仍为单线程）。

⑤ 追问预判：Redis 6.0 的多线程 I/O 是如何实现的？为什么命令执行不改为多线程？

### Q133: Redis 的持久化机制 RDB 和 AOF 的区别？

① 一句话结论：RDB 是快照持久化（全量数据），AOF 是追加日志持久化（增量写命令），两者各有优劣，可同时开启以兼顾恢复速度和数据安全。

② 原理剖析：**RDB（Redis Database）**：按配置的触发条件（如 save 900 1），fork 子进程将内存数据写入临时 RDB 文件，然后替换旧文件。优点是文件紧凑、恢复快，缺点是可能丢失最后一次快照后的数据。**AOF（Append Only File）**：记录每次写命令到 AOF 缓冲区，按配置的 fsync 策略（每秒/每次写入/不主动同步）刷入磁盘。优点是数据丢失少（最多 1 秒数据），缺点是文件体积大、恢复慢。Redis 4.0 引入混合持久化（RDB + AOF 增量），兼顾快速恢复和数据安全。

③ 场景举例：
```
RDB 配置：save 900 1（900 秒内至少 1 次修改）| save 300 10 | save 60 10000
AOF 配置：appendfsync everysec（每秒同步，推荐）
混合持久化：aof-use-rdb-preamble yes
```

④ 优缺点与边界：RDB 适合备份和灾难恢复，AOF 适合数据高可靠性场景。同时开启时，Redis 重启优先加载 AOF（数据更完整）。AOF 文件过大时可执行 BGREWRITEAOF 重写压缩。

⑤ 追问预判：AOF 重写的原理？RDB 和 AOF 同时开启时重启加载顺序？

### Q134: 什么是热点 Key 问题？如何解决？

① 一句话结论：热点 Key 指某些 Key 被大量请求集中访问，导致 Redis 单节点负载过高，甚至打垮 Redis 或引发缓存雪崩。解决方案包括本地缓存、复制热点 Key、读写分离等。

② 原理剖析：热点 Key 通常出现在大促活动、热门新闻、明星动态等场景，如单一 Key 的 QPS 达到数十万。Redis 单线程模型下，热点 Key 的请求会串行处理，导致其他请求排队。**解决方案**：**本地缓存**（客户端缓存热点数据到内存，如 Caffeine），减少对 Redis 的请求；**Key 复制 + 分散访问**（将热点 Key 复制为多个带后缀的副本 key1/key2/.../keyN，请求随机访问不同副本）；**读写分离**（读请求分流到从节点）；**Redis Cluster** 天然分散 Key 到不同节点。

③ 场景举例：
```ts
// 热点 Key 分散策略
function getHotKey(key: string): string {
  const count = 10;
  const suffix = Math.floor(Math.random() * count);
  return `${key}:${suffix}`;
}
// 写入时：分别写入 key:0 ~ key:9
// 读取时：随机读取一个副本
```

④ 优缺点与边界：本地缓存解决了热点问题但引入了数据不一致性；Key 复制增加了写入复杂度和内存占用。需根据业务场景选择合适方案。

⑤ 追问预判：如何自动发现热点 Key？本地缓存和 Redis 缓存的数据一致性如何保证？

### Q135: 如何设计一个接口限流方案？

① 一句话结论：接口限流通过控制单位时间内的请求量来保护系统，常用算法有令牌桶、漏桶、滑动窗口，配合 Redis 或 Guava RateLimiter 实现分布式或单机限流。

② 原理剖析：**令牌桶算法**：以固定速率向桶中放入令牌，请求需获取令牌才能通过，桶满则丢弃令牌，允许一定程度的突发流量，最常用。**漏桶算法**：请求以固定速率流出，超出桶容量则丢弃，平滑流量但不支持突发。**滑动窗口**：将时间窗口划分为多个小格，统计每个小格的请求数，精确度高于固定窗口。**计数器**：固定时间窗口内计数，超过阈值则拒绝，缺点是在窗口边界会出现流量尖峰。

③ 场景举例：
```ts
// NestJS 中使用 @nestjs/throttler 实现限流
@Injectable()
export class ThrottlerGuard extends ThrottlerGuard {
  protected async handleRequest(context: ExecutionContext, limit: number, ttl: number): Promise<boolean> {
    const key = this.generateKey(context);
    const { totalHits } = await this.storageService.increment(key, ttl);
    if (totalHits > limit) throw new TooManyRequestsException();
    return true;
  }
}
```

④ 优缺点与边界：令牌桶适合大多数业务场景；漏桶适合流量整形需求；滑动窗口精度最高但内存开销大。分布式限流需 Redis 配合 Lua 脚本保证原子性。

⑤ 追问预判：分布式限流和单机限流的区别？如何实现基于用户 ID 的细粒度限流？

### Q136: HTTPS 的握手过程是怎样的？

① 一句话结论：HTTPS 握手通过 TLS 协议在 TCP 连接之上完成，包括客户端 Hello、服务器 Hello、证书验证、密钥交换和对称加密密钥生成四个核心步骤。

② 原理剖析：**① Client Hello**：客户端发送支持的 TLS 版本、加密套件列表、随机数 random_C。**② Server Hello**：服务端选择加密套件和 TLS 版本，发送证书（含公钥）和随机数 random_S。**③ 证书验证**：客户端验证证书链（CA 签名、域名、有效期、是否吊销），验证通过后生成预主密钥 Pre-Master Secret，用服务端公钥加密发送。**④ 密钥生成**：服务端用私钥解密得到 Pre-Master Secret，双方用 random_C + random_S + Pre-Master 计算会话密钥，之后发送 `Change Cipher Spec` 和 `Finished` 消息确认，后续通信使用对称加密。

③ 场景举例：
```
TCP 三次握手 → TLS 握手（1-2 RTT）→ 加密通信
TLS 1.3 优化：1-RTT 握手，支持 0-RTT 恢复
```

④ 优缺点与边界：TLS 握手增加 1-2 个 RTT 延迟，但显著提升安全性。TLS 1.3 相比 1.2 减少了握手往返次数，移除不安全加密套件。

⑤ 追问预判：TLS 1.3 相比 1.2 的主要改进？如何配置 HTTPS 证书（Nginx/Let's Encrypt）？

### Q137: 什么是 JWT 的无状态认证？JWT 如何防止篡改？

① 一句话结论：JWT 无状态认证指服务端不存储会话信息，所有用户身份信息编码在 Token 自身中，通过签名验证 Token 完整性防止篡改。

② 原理剖析：JWT 由三部分组成：Header（算法类型）、Payload（声明数据，如用户 ID、过期时间）、Signature（签名）。签名部分使用 Header 中指定的算法（如 HMAC SHA256）对 base64 编码的 Header + "." + Payload 进行加密，密钥仅服务端持有。服务端收到 JWT 后重新计算签名并与 Token 中的签名比对，若不一致则判定 Token 被篡改。由于 Payload 仅 base64 编码（非加密），不应存放敏感信息。签名验证确保完整性，而非机密性。

③ 场景举例：
```ts
// 生成 JWT
const token = jwt.sign({ userId: 1, role: 'admin' }, 'secret', { expiresIn: '7d' });
// 验证 JWT
try {
  const decoded = jwt.verify(token, 'secret');
  // 签名验证通过，payload 未被篡改
} catch (e) {
  // 签名无效或过期
}
```

④ 优缺点与边界：无状态的优点是不需要集中式 session 存储，易于水平扩展；缺点是无法主动吊销 Token（需等待过期），且 Payload 不宜过大（影响网络传输）。可通过黑名单机制实现即时吊销。

⑤ 追问预判：JWT 和 Session 认证的优缺点对比？如何实现 JWT 的黑名单撤销？

### Q138: 密码存储为什么要加盐？bcrypt 的原理？

① 一句话结论：加盐解决彩虹表攻击问题，即使相同密码在不同用户下存储的哈希值不同；bcrypt 是一种自适应哈希算法，通过内置盐值和可调节的工作因子抵御暴力破解。

② 原理剖析：**加盐**：在用户密码后附加随机字符串（盐值），再计算哈希，使得相同密码得到不同哈希值，攻击者无法使用预计算的彩虹表进行逆向。**bcrypt**：将盐值内嵌到算法中，输出为固定格式字符串（`$2b$10$salt$hash`），包含算法标识、工作因子（cost）、22 字符盐值和 31 字符哈希值。bcrypt 的慢速哈希设计（工作因子每增加 1，计算时间翻倍）使得暴力破解成本极高，即使 GPU 加速也难以快速破解。bcrypt 自动处理盐值生成和存储，开发者无需手动管理盐值。

③ 场景举例：
```ts
import * as bcrypt from 'bcrypt';
// 注册：哈希密码
const salt = await bcrypt.genSalt(10); // work factor = 10
const hash = await bcrypt.hash(password, salt);
// 登录：比对密码
const isValid = await bcrypt.compare(inputPassword, storedHash);
```

④ 优缺点与边界：bcrypt 的慢速哈希是安全与性能的权衡，work factor 建议 10-12，过高会导致用户登录体验差。bcrypt 对密码长度有限制（通常 72 字节），超长密码需先哈希再传入 bcrypt。

⑤ 追问预判：bcrypt 和 argon2、scrypt 的对比？如何选择 work factor？

### Q139: 如何在 NestJS 中编写单元测试？

① 一句话结论：NestJS 单元测试使用 Jest 作为默认测试框架，通过 `Test.createTestingModule()` 创建测试模块，模拟依赖并测试目标类。

② 原理剖析：`Test.createTestingModule()` 创建一个类似 NestJS 模块的测试容器，通过 `compile()` 编译后返回 `TestingModule`，调用 `get()` 获取目标类实例。测试中通过 `useValue` 或 `useFactory` 提供模拟依赖（Mock），避免依赖真实数据库或外部服务。每个测试用例通常由 Arrange（准备数据）、Act（执行方法）、Assert（验证结果）三部分组成。

③ 场景举例：
```ts
describe('UserService', () => {
  let service: UserService;

    }).compile();
    service = module.get(UserService);
  });

  it('should return user by id', async () => {
    mockUserRepo.findOne.mockResolvedValue({ id: 1, name: 'Alice' });
    const result = await service.findById(1);
    expect(result.name).toBe('Alice');
  });
});
```

④ 优缺点与边界：单元测试关注单类逻辑，需隔离外部依赖。过度 Mock 可能使测试偏离真实行为，应结合集成测试覆盖关键链路。

### Q140: 如何测试一个包含数据库操作的 Service？

② 原理剖析：创建测试模块时，配置 TypeORM 使用内存 SQLite 或独立测试数据库，设置 `synchronize: true` 自动创建表结构，`dropSchema: true` 在测试后清理数据。测试前在 `beforeEach` 中准备测试数据，测试后清理。这种方式比 Mock Repository 更接近真实行为，能发现 SQL 和 ORM 映射问题。

describe('UserService Integration', () => {

### Q141: E2E 测试的 beforeAll 和 afterAll 中通常做什么？

### Q142: 单例模式在 NestJS 中如何体现？

① 一句话结论：NestJS 默认所有 `&#64;Injectable()` 的类都是单例（Singleton Scope），每个提供者在整个应用生命周期内只实例化一次，共享同一个实例。

② 原理剖析：NestJS 的 DI 容器默认使用单例作用域，当模块首次解析提供者时，容器创建实例并缓存，后续其他模块注入同一提供者时返回缓存的同一实例。这是通过 `&#64;Injectable({ scope: Scope.DEFAULT })` 默认值实现的。单例模式保证了无状态服务的高效复用，避免了重复创建的开销，且天然线程安全（Node.js 单线程模型，但需注意异步上下文中的状态管理）。

③ 场景举例：
```ts
@Injectable() // 默认 scope: Scope.DEFAULT，即单例
export class UserService {
  constructor(private readonly userRepo: UserRepository) {} // 构造函数只执行一次
}
// 两个不同的 Controller 注入 UserService，得到的是同一个实例
```

④ 优缺点与边界：单例模式节省内存，但需注意有状态服务（如请求级别的缓存）不应使用单例，应改用 `Scope.REQUEST` 或 `Scope.TRANSIENT`。单例中的实例变量在多请求间共享，可能导致数据污染。

⑤ 追问预判：NestJS 的三种作用域（DEFAULT/REQUEST/TRANSIENT）的区别？如何在单例 Service 中处理请求级别的数据？

### Q143: 策略模式在 NestJS 中如何实现？

① 一句话结论：策略模式在 NestJS 中通过定义统一接口的具体策略类，利用 DI 容器按需注入或通过 `&#64;Inject()` 的 `token` 工厂按条件选择策略实现。

② 原理剖析：定义一个抽象策略接口（或抽象类），多个具体策略类实现该接口。在 NestJS 中，通过自定义 `Provider` 的 `useFactory` 或 `useClass` 动态选择策略，或将所有策略注入到 `Map` 中，根据条件（如支付方式、登录类型）动态调用。更优雅的方式是使用 `&#64;Injectable()` 注册所有策略，通过 `ModuleRef` 或 `&#64;Inject(STRATEGY_MAP)` 获取策略集合。

③ 场景举例：
```ts
// 策略接口
interface PaymentStrategy { pay(amount: number): Promise<void>; }

// 具体策略
@Injectable()
export class WechatPayStrategy implements PaymentStrategy { async pay(amount: number) { /* 微信支付 */ } }

@Injectable()
export class AliPayStrategy implements PaymentStrategy { async pay(amount: number) { /* 支付宝 */ } }

// 策略上下文
@Injectable()
export class PaymentService {
  private strategies: Map<string, PaymentStrategy> = new Map();
  constructor(wechat: WechatPayStrategy, ali: AliPayStrategy) {
    this.strategies.set('wechat', wechat);
    this.strategies.set('ali', ali);
  }
  pay(type: string, amount: number) {
    const strategy = this.strategies.get(type);
    if (!strategy) throw new Error('不支持的支付方式');
    return strategy.pay(amount);
  }
}
```

④ 优缺点与边界：策略模式消除了大量 if-else，扩展新策略只需添加新类，符合开闭原则。但策略类过多时需注意管理和注册。

### Q144: 观察者模式在 NestJS 中的体现（EventEmitter）？

① 一句话结论：观察者模式在 NestJS 中通过 `&#64;nestjs/event-emitter` 模块实现，允许解耦的事件发布与监听，适用于跨模块通信和异步任务编排。

② 原理剖析：`&#64;nestjs/event-emitter` 基于 Node.js 的 EventEmitter，提供装饰器 `&#64;OnEvent()` 和 `&#64;OnEventWithOptions()` 来注册事件监听器，通过 `EventEmitter2` 服务发布事件。事件发布者无需知道谁在监听，监听者只需关注特定事件名称。支持异步监听、通配符事件名、命名空间等高级特性。NestJS 内置的 `EventEmitterModule` 在应用启动时自动扫描并注册所有 `&#64;OnEvent` 装饰的方法。

③ 场景举例：
```ts
// 事件发布
@Injectable()
export class OrderService {
  constructor(private eventEmitter: EventEmitter2) {}
  async create(order: OrderDto) {
    const orderCreated = await this.orderRepo.save(order);
    this.eventEmitter.emit('order.created', orderCreated);
    return orderCreated;
  }
}

// 事件监听
@Injectable()
export class NotificationListener {
  @OnEvent('order.created')
  async handleOrderCreated(order: Order) {
    await this.sendEmail(order.userEmail, '订单创建成功');
  }
}
```

④ 优缺点与边界：观察者模式实现了解耦，但事件过多时调试困难（隐式调用链），且需注意事件监听器的异常处理，避免影响主流程。

⑤ 追问预判：&#64;nestjs/event-emitter 和 RxJS Subject 的观察者模式区别？如何实现事件的有序执行？

### Q145: 工厂模式在 NestJS 中的体现（useFactory）？

① 一句话结论：工厂模式在 NestJS 中通过 `useFactory` 提供者实现，允许在实例化时执行自定义逻辑，动态创建提供者，常用于配置动态值、条件注入或第三方库集成。

② 原理剖析：`useFactory` 是 NestJS 自定义提供者的一种，在模块的 `providers` 数组中注册，使用函数工厂返回提供者实例。`useFactory` 支持依赖注入，可通过 `inject` 数组声明依赖，框架在调用工厂函数时传入这些依赖。工厂模式适用于：需要根据运行时配置创建不同实例、需要初始化逻辑（如创建连接池）或需要封装第三方库的创建过程。

③ 场景举例：
```ts
@Module({
  providers: [
    {
      provide: 'CACHE_OPTIONS',
      useFactory: (configService: ConfigService) => {
        const host = configService.get('REDIS_HOST');
        const port = configService.get('REDIS_PORT');
        return { host, port, ttl: 60 };
      },
      inject: [ConfigService],
    },
  ],
})
export class CacheModule {}
```

④ 优缺点与边界：`useFactory` 提供灵活的实例化方式，但工厂函数复杂时建议抽取为单独的服务类。`useFactory` 创建的实例默认也是单例，除非配置了 `scope`。

⑤ 追问预判：useFactory、useClass、useValue 的区别和适用场景？如何在使用 useFactory 时实现异步初始化？

### Q146: 装饰器模式在 NestJS 中的体现？

① 一句话结论：装饰器模式是 NestJS 的核心设计理念，通过 `&#64;Controller()`、`&#64;Injectable()`、`&#64;Get()`、`&#64;UseGuards()` 等装饰器为类和方法附加元数据和行为，实现横切关注点的分离。

② 原理剖析：NestJS 大量使用 TypeScript 装饰器实现元数据编程。**类装饰器**（如 `&#64;Controller()`、`&#64;Module()`）在类上添加路由前缀、模块元数据等信息。**方法装饰器**（如 `&#64;Get()`、`&#64;Post()`）定义 HTTP 方法和路径。**参数装饰器**（如 `&#64;Body()`、`&#64;Param()`）描述参数如何从请求中提取。**组合装饰器**（如 `&#64;UseGuards()`、`&#64;UseInterceptors()`）将横切逻辑（权限、日志、缓存）附加到控制器上，通过 `&#64;nestjs/core` 的 `Reflector` 读取元数据并执行相应处理，本质上是装饰器模式在框架层面的实现。

③ 场景举例：
```ts
@Controller('users')       // 类装饰器：路由前缀
export class UserController {
  @Get(':id')              // 方法装饰器：HTTP 方法 + 路径
  @UseGuards(AuthGuard)    // 组合装饰器：附加守卫逻辑
  @Roles('admin')          // 自定义装饰器：附加角色元数据
  findOne(
    @Param('id') id: string,  // 参数装饰器：提取路由参数
    @Query('include') include?: string  // 参数装饰器：提取查询参数
  ) {
    return this.userService.findById(id);
  }
}
```

④ 优缺点与边界：装饰器模式使代码声明式、简洁，但过度使用装饰器可能导致隐式行为难以调试，且装饰器执行顺序需要理解（从下到上、从右到左）。

⑤ 追问预判：NestJS 中多个装饰器的执行顺序？自定义装饰器如何与 Passport 结合？

### Q147: 如何设计一个高可用的 Node.js 后端服务？

① 一句话结论：高可用 Node.js 后端服务通过多副本部署（Cluster/PM2）、负载均衡、进程守护、优雅退出、降级熔断和监控告警等机制组合实现。

② 原理剖析：**多副本部署**：利用 Cluster 模块或 PM2 的 fork 模式启动多个 Worker 进程，充分利用多核 CPU，单个 Worker 崩溃不影响整体服务。**进程守护**：PM2 或 Supervisor 自动重启崩溃进程，确保服务自愈。**负载均衡**：Nginx 反向代理分发请求到多个实例，支持健康检查和自动摘除故障节点。**优雅退出**：监听 SIGTERM 信号，关闭 Keep-Alive 连接，处理完当前请求后再退出，避免请求中断。**降级熔断**：使用断路器模式（如 &#64;nestjs/bull 的断路器）保护下游依赖，当依赖故障时快速失败。**监控告警**：Node.js 应用性能监控（APM）、日志聚合（ELK）、指标采集（Prometheus）+ 告警。

③ 场景举例：
```ts
// 优雅退出
async function gracefulShutdown(signal: string) {
  console.log(`收到 ${signal}，开始优雅退出`);
  server.close(() => {
    console.log('HTTP 服务器已关闭');
    process.exit(0);
  });
  setTimeout(() => process.exit(1), 30000); // 30 秒超时强制退出
}
process.on('SIGTERM', () => gracefulShutdown('SIGTERM'));
process.on('SIGINT', () => gracefulShutdown('SIGINT'));
```

④ 优缺点与边界：高可用设计增加了系统复杂度，需权衡可用性和成本。Node.js 单进程因无法利用多核，必须通过多进程部署实现高可用。此外需考虑数据库、缓存等中间件的单点故障问题。

⑤ 追问预判：如何实现零停机部署？PM2 的 Graceful Shutdown 如何配置？

### Q148: 微服务拆分的原则是什么？

① 一句话结论：微服务拆分遵循**高内聚、低耦合**原则，按业务边界（Bounded Context）拆分，确保每个服务独立部署、独立扩展、独立故障。

② 原理剖析：**按业务边界拆分**：每个微服务对应一个限界上下文（如订单服务、用户服务、库存服务），拥有自己的数据库，避免跨服务直接访问数据库。**单一职责**：每个服务只负责一个业务领域，变更不影响其他服务。**数据独立**：服务间通过 API 或消息队列通信，不共享数据库。**服务自治**：每个服务独立开发、测试、部署、扩缩容。**通信方式**：同步调用（REST/gRPC）适合实时查询，异步消息（Kafka/RabbitMQ）适合事件驱动。**避免拆分过早**：在业务不明确时先单体应用，待业务边界清晰后再拆分。

③ 场景举例：
```
电商系统拆分：
用户服务（User） → 认证、用户信息
订单服务（Order） → 订单创建、状态管理
商品服务（Product）→ 商品信息、库存
支付服务（Payment）→ 支付处理
通知服务（Notification）→ 短信、邮件推送
```

④ 优缺点与边界：微服务带来灵活性但也增加了分布式系统的复杂度（数据一致性、服务发现、调用链追踪、分布式事务），不适合简单业务。拆分粒度过细会导致"微服务地狱"。

⑤ 追问预判：如何解决微服务间的数据一致性问题？服务间通信失败如何处理？

### Q149: WebSocket 在 NestJS 中如何实现？

① 一句话结论：NestJS 通过 `&#64;nestjs/platform-socket.io` 或 `&#64;nestjs/platform-ws` 实现 WebSocket 网关，使用 `&#64;WebSocketGateway()` 装饰器定义网关，使用 `&#64;SubscribeMessage()` 处理消息。

② 原理剖析：`&#64;WebSocketGateway()` 标记一个类为 WebSocket 网关，支持配置命名空间和端口。`&#64;SubscribeMessage('eventName')` 装饰器订阅特定事件，方法接收 `&#64;MessageBody()` 消息体和 `&#64;ConnectedSocket()` 客户端引用。NestJS 的 WebSocket 集成支持依赖注入，可在网关中注入 Service 和 Guard。通过 `&#64;WebSocketServer()` 装饰器获取服务器实例，实现广播推送。支持 `&#64;UseGuards()` 对 WebSocket 连接进行鉴权。

③ 场景举例：
```ts
@WebSocketGateway({ namespace: '/chat' })
export class ChatGateway {
  @WebSocketServer() server: Server;

  @SubscribeMessage('message')
  handleMessage(@MessageBody() data: { room: string; content: string }, @ConnectedSocket() client: Socket) {
    this.server.to(data.room).emit('message', { content: data.content, sender: client.id });
  }

  @SubscribeMessage('join')
  handleJoin(@MessageBody() room: string, @ConnectedSocket() client: Socket) {
    client.join(room);
  }

  afterInit() { console.log('WebSocket 初始化完成'); }
  handleConnection(client: Socket) { console.log('客户端连接:', client.id); }
  handleDisconnect(client: Socket) { console.log('客户端断开:', client.id); }
}
```

④ 优缺点与边界：Socket.IO 兼容性好（支持降级为长轮询），但额外引入协议开销。原生 WebSocket 性能更好但兼容性差。生产环境需考虑 WebSocket 的横向扩展（Redis 适配器实现跨进程广播）。

⑤ 追问预判：WebSocket 如何实现横向扩展（Redis Adapter）？WebSocket 和 SSE（Server-Sent Events）的适用场景区别？

### Q150: 如何设计一个支持百万连接的系统架构？

① 一句话结论：百万连接系统架构需从网络层、应用层、服务层、数据层逐层设计，核心思路是水平扩展、无状态设计、异步 I/O 和连接复用。

② 原理剖析：**网络层**：使用 Nginx/HAProxy 做四层负载均衡（LVS + Keepalived），通过 DNS 轮询分散到多个入口。**应用层**：Node.js 利用事件驱动和非阻塞 I/O，单进程可支撑数万连接，结合 Cluster 模块利用多核，每台机器可支撑 10-20 万连接。**水平扩展**：通过 K8s 或 Docker Compose 部署多实例，配合自动扩缩容（HPA）。**连接管理**：使用长连接池（数据库连接池、Redis 连接池），避免频繁创建和销毁连接。**数据库层**：MySQL 分库分表 + Redis 缓存集群，读写分离，使用连接池限制连接数。**消息队列**：引入 Kafka 或 RabbitMQ 削峰填谷，缓冲瞬时流量。**无状态设计**：服务实例不存储会话状态，状态统一存储在 Redis 或数据库中，使任意实例可处理任意请求。

③ 场景举例：
```
百万连接架构示意：
DNS → LVS(四层负载均衡) → Nginx 集群(七层负载) → Node.js 应用集群(100台, 每台1万连接) → Redis 集群 → MySQL 分库分表
                                                              ↓
                                                     Kafka 消息队列 → 异步消费者
```

④ 优缺点与边界：百万连接架构需要充足的服务器资源和运维能力，小规模业务不建议超前设计。瓶颈通常不在应用层，而在数据库 IO 和网络带宽，需提前做好容量规划。

⑤ 追问预判：百万连接下如何优化 Node.js 的内存和 CPU 使用？C10K 和 C10M 问题的挑战分别是什么？
