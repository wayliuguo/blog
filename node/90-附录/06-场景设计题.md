## 场景 1：设计一个用户注册登录系统

### 题目描述
设计一个用户注册登录系统，支持邮箱注册、密码登录、JWT 无状态认证。

### 考察要点
- bcrypt 密码加密、JWT 签发与验证、AuthGuard 实现、DTO 校验

### 参考答案

**核心思路**：采用 NestJS 模块化架构，注册时 bcrypt 哈希密码，登录时比对密码后签发 JWT，AuthGuard 拦截受保护路由并解析 token。

**关键步骤**：

1. **注册流程**：
   - 前端提交邮箱 + 密码到 `POST /auth/register`
   - 后端使用 `class-validator` DTO 校验邮箱格式和密码强度
   - 查询数据库是否已存在该邮箱，存在则返回 409
   - 使用 `bcrypt.hash(password, 10)` 对密码加盐哈希
   - 将邮箱和哈希存入 `users` 表，返回 201

2. **登录流程**：
   - 前端提交邮箱 + 密码到 `POST /auth/login`
   - 根据邮箱查询用户，不存在则返回 401
   - 使用 `bcrypt.compare(password, user.password)` 比对密码
   - 密码正确则用 `jsonwebtoken.sign({ userId, email }, secret, { expiresIn: '7d' })` 签发 token
   - 返回 `{ accessToken }` 给前端

3. **认证中间件**：
   - 实现 `AuthGuard`，从 `Authorization: Bearer <token>` 提取 token
   - 使用 `jwt.verify(token, secret)` 解析 payload，失败则返回 401
   - 将解析出的用户信息挂载到 `req.user`，供后续处理器使用

```typescript
// 伪代码 - 核心逻辑
@Post('register')
async register(@Body() dto: RegisterDto) {
  const exists = await this.userRepo.findOneBy({ email: dto.email });
  if (exists) throw new ConflictException('邮箱已注册');
  const hash = await bcrypt.hash(dto.password, 10);
  return this.userRepo.save({ email: dto.email, password: hash });
}

@Post('login')
async login(@Body() dto: LoginDto) {
  const user = await this.userRepo.findOneBy({ email: dto.email });
  if (!user || !(await bcrypt.compare(dto.password, user.password)))
    throw new UnauthorizedException();
  const token = jwt.sign({ sub: user.id }, JWT_SECRET, { expiresIn: '7d' });
  return { accessToken: token };
}
```

## 场景 2：设计一个 RESTful API 的统一错误处理方案

### 题目描述
为 Node.js 应用设计一个全局错误处理机制，使 API 返回格式统一的错误响应。

### 考察要点
- 异常过滤器（Exception Filter）、错误码枚举、错误分类、日志记录

### 参考答案

**核心思路**：使用 NestJS 全局异常过滤器捕获所有异常，按类型分类处理后返回统一 JSON 结构。

**关键步骤**：

1. **定义统一响应格式**：
   ```json
   { "code": 40001, "message": "参数校验失败", "details": [...] }
   ```

2. **定义业务异常类**：
   - 继承 `HttpException`，携带 `code`（业务码）和 `message`
   - 例如：`BusinessException.forbidden('无权操作')`、`BusinessException.notFound('用户不存在')`

3. **实现全局异常过滤器**：
   - 实现 `ExceptionFilter` 接口，用 `@Catch()` 装饰器标记
   - 在 `catch` 方法中区分异常类型：`HttpException`、`BusinessException`、`ValidationError`、未知错误
   - 每种类型映射到统一格式，未知错误返回 500 并记录完整 error stack
   - 对 `ValidationError`（class-validator）提取字段名和约束信息拼接到 `details`

4. **注册为全局过滤器**：
   - 在 `main.ts` 中通过 `app.useGlobalFilters(new GlobalExceptionFilter())` 注册

```typescript
// 伪代码
@Catch()
export class GlobalExceptionFilter implements ExceptionFilter {
  catch(exception: unknown, host: ArgumentsHost) {
    const ctx = host.switchToHttp();
    const response = ctx.getResponse<Response>();
    let status = 500, body = { code: 50000, message: '服务器内部错误' };

    if (exception instanceof BusinessException) {
      status = exception.getStatus();
      body = { code: exception.code, message: exception.message };
    } else if (exception instanceof HttpException) {
      status = exception.getStatus();
      body = { code: status, message: exception.message };
    } else {
      Logger.error(exception); // 未知错误记录完整日志
    }
    response.status(status).json(body);
  }
}
```

## 场景 3：设计一个文件上传服务

### 题目描述
设计一个文件上传服务，支持单文件和多文件上传，需进行文件类型校验和大小限制。

### 考察要点
- Multer 中间件配置、文件类型白名单、大小限制、静态资源访问

### 参考答案

**核心思路**：使用 NestJS 内置的 FileInterceptor（单文件）和 FilesInterceptor（多文件），配置 Multer 选项进行校验和存储。

**关键步骤**：

1. **安装依赖**：`@nestjs/platform-express`（内置 Multer）

2. **配置 Multer 选项**：
   - `limits.fileSize` 限制最大文件大小（如 5MB）
   - `fileFilter` 回调中对文件类型做白名单校验，如 `['image/jpeg', 'image/png', 'application/pdf']`
   - 不合法文件调用 `cb(new Error('不支持的文件类型'), false)` 拒绝

3. **存储策略**：
   - 本地磁盘存储：`diskStorage` 配置 `destination` 和 `filename`（用 `uuid + 原始扩展名` 重命名）
   - 也可配置 `memoryStorage` 上传到云存储（OSS/S3）

4. **控制器实现**：
   - `POST /upload/single` 使用 `@UseInterceptors(FileInterceptor('file'))` 接收单文件
   - `POST /upload/multiple` 使用 `@UseInterceptors(FilesInterceptor('files', 10))` 接收最多 10 个文件
   - 处理成功后返回文件 URL 或路径

5. **静态资源访问**：在 `main.ts` 中配置 `app.useStaticAssets(join(__dirname, '..', 'uploads'), { prefix: '/uploads' })`

```typescript
// 伪代码
@Post('single')
@UseInterceptors(FileInterceptor('file', {
  limits: { fileSize: 5 * 1024 * 1024 },
  fileFilter: (req, file, cb) => {
    const allowed = ['image/jpeg', 'image/png'];
    allowed.includes(file.mimetype) ? cb(null, true) : cb(new BadRequestException('不支持的文件类型'), false);
  },
  storage: diskStorage({
    destination: './uploads',
    filename: (req, file, cb) => cb(null, `${uuid()}-${file.originalname}`),
  }),
}))
uploadSingle(@UploadedFile() file: Express.Multer.File) {
  return { url: `/uploads/${file.filename}` };
}
```

## 场景 4：设计一个基于 Redis 的缓存网关

### 题目描述
为热点数据设计一个 Redis 缓存层，支持缓存失效策略和穿透防护。

### 考察要点
- Redis 数据结构选择、缓存过期策略、缓存穿透/击穿/雪崩防护、Cache-Aside 模式

### 参考答案

**核心思路**：采用 Cache-Aside 模式，读请求先查缓存，命中直接返回；未命中查数据库，然后回写缓存并设置 TTL。

**关键步骤**：

1. **缓存 Key 设计**：
   - 统一前缀 + 业务标识 + ID，如 `cache:user:profile:123`
   - 使用 `:` 分层命名，便于批量管理

2. **缓存穿透防护**：
   - 布隆过滤器：启动时加载所有存在的 ID 到 BloomFilter，请求先过 BloomFilter，不存在则直接返回
   - 缓存空值：查询数据库结果为空时，也写一个 TTL 较短（如 60s）的空值到缓存

3. **缓存击穿防护**：
   - 使用互斥锁（SetNX）：当缓存失效且并发请求到达时，第一个请求获取锁回源查库，其余请求等待或重试
   - 热点数据设置较长的 TTL，配合异步更新

4. **缓存雪崩防护**：
   - 过期时间添加随机偏移量，避免大量 key 同时过期
   - 设置 TTL 为基础值 + `Math.random() * 300` 秒

5. **实现封装**：
   - 封装 `CacheService`，提供 `get<T>()`、`set()`、`del()` 方法
   - 内部处理序列化/反序列化（JSON）

```typescript
// 伪代码 - 带穿透防护的查询
async getUserProfile(userId: number) {
  const key = `cache:user:profile:${userId}`;
  // 1. 查缓存
  let data = await this.redis.get(key);
  if (data) return JSON.parse(data);
  // 2. 布隆过滤（可选）
  if (!this.bloomFilter.mightContain(userId)) throw new NotFoundException();
  // 3. 互斥锁防击穿
  const lockKey = `lock:user:profile:${userId}`;
  const locked = await this.redis.setnx(lockKey, '1', 10); // 10s 过期
  if (!locked) { await sleep(50); return this.getUserProfile(userId); } // 重试
  // 4. 查库
  data = await this.userRepo.findOneBy({ id: userId });
  // 5. 回写缓存（空值也缓存，防穿透）
  await this.redis.setex(key, 600 + Math.random() * 300, JSON.stringify(data ?? null));
  await this.redis.del(lockKey);
  return data;
}
```

## 场景 5：设计一个秒杀系统的库存扣减方案

### 题目描述
设计一个高并发秒杀场景下的库存扣减方案，防止超卖。

### 考察要点
- Redis 原子操作、乐观锁、Lua 脚本、库存预扣、MQ 异步削峰

### 参考答案

**核心思路**：Redis 原子扣减库存做前置过滤，数据库乐观锁最终扣减，MQ 异步处理后续流程，三管齐下防超卖。

**关键步骤**：

1. **库存预热**：秒杀开始前，将商品库存加载到 Redis 中 `SET goods:1001:stock 100`

2. **原子扣减（Redis Lua）**：
   - 用 Lua 脚本保证原子性：检查库存 > 0 → `DECR` → 返回成功
   - 脚本在 Redis 端串行执行，天然防超卖
   - 库存不足时直接返回失败

3. **异步削峰**：
   - 扣减成功的请求写入消息队列（RabbitMQ / Redis Stream），下游服务拉取消息同步更新数据库
   - 前端立即返回"排队中"，避免长时间阻塞

4. **数据库最终一致性**：
   - 消费者从队列取出消息，用乐观锁更新数据库：`UPDATE goods SET stock = stock - 1 WHERE id = ? AND stock > 0`
   - 影响行数为 0 则回滚并告警

5. **防重复扣减**：
   - 使用 Redis SetNX 或用户 ID 去重，确保同一用户在同一秒杀活动中只扣一次

```lua
-- Lua 伪代码
local key = KEYS[1]          -- 库存 key
local stock = redis.call('GET', key)
if not stock or tonumber(stock) <= 0 then
  return 0  -- 库存不足
end
redis.call('DECR', key)
return 1    -- 扣减成功
```

## 场景 6：设计一个慢 SQL 排查与优化流程

### 题目描述
系统上线后接口响应变慢，疑似数据库慢 SQL，请设计排查与优化流程。

### 考察要点
- 慢查询日志、EXPLAIN 执行计划、索引优化、分页优化、连接池调优

### 参考答案

**核心思路**：先定位慢 SQL，再分析执行计划，最后针对性优化。

**关键步骤**：

1. **开启慢查询日志**：
   - MySQL：`SET GLOBAL slow_query_log = ON; SET GLOBAL long_query_time = 1;`
   - 查看慢查询日志文件，找出执行时间超过阈值的 SQL

2. **获取执行计划**：
   - 对慢 SQL 执行 `EXPLAIN SELECT ...`，关注以下字段：
     - `type`：`ALL`（全表扫描）→ 需加索引；`index` / `ref` / `eq_ref` 较好
     - `rows`：扫描行数，越大越慢
     - `Extra`：`Using filesort`（需优化排序）、`Using temporary`（需优化分组）

3. **常见优化手段**：
   - **缺少索引**：为 `WHERE`、`JOIN`、`ORDER BY` 涉及的字段添加联合索引
   - **索引失效**：避免在索引列上使用函数、隐式类型转换、`LIKE '%xxx'`
   - **分页优化**：大偏移量分页用游标分页代替 `OFFSET`，如 `WHERE id > lastId LIMIT 20`
   - **避免 SELECT \***：只查需要的字段，减少回表和数据传输
   - **拆分大查询**：将大查询拆成多次小查询，或用覆盖索引

4. **连接池调优**：
   - 检查 `max_connections` 是否够用
   - 应用层连接池（如 `typeorm` 的 `poolSize`）根据并发量合理设置

5. **监控与告警**：
   - 使用 `performance_schema` 或第三方工具（如 PM2、Prometheus）持续监控

## 场景 7：设计一个 Node.js 应用的健康检查与监控方案

### 题目描述
为生产环境的 Node.js 应用设计健康检查和监控方案，确保服务稳定运行。

### 考察要点
- 健康检查端点、进程监控、内存/CPU 监控、日志告警、PM2 和 Docker 健康检查

### 参考答案

**核心思路**：暴露健康检查端点供外部探针检测，结合进程管理工具和监控平台实现全方位监控。

**关键步骤**：

1. **健康检查端点**：
   - `GET /health` 返回 `{ status: 'ok', uptime, timestamp }`
   - 扩展检查：数据库连接池状态、Redis 连通性、磁盘空间
   - 某个依赖不可用时返回 503，且 JSON 中标记对应组件的 `status: 'down'`

2. **进程管理（PM2）**：
   - 使用 PM2 管理进程，配置 `max_memory_restart` 内存超限自动重启
   - 开启 `--watch` 文件变更自动重启（开发环境）
   - 配置 `instances: max` 利用多核 CPU

3. **Docker 健康检查**：
   - Dockerfile 中配置 `HEALTHCHECK --interval=30s --timeout=3s CMD curl -f http://localhost:3000/health || exit 1`
   - 容器编排工具根据健康检查状态自动重启故障容器

4. **系统指标监控**：
   - 使用 `os` 模块采集 CPU 和内存使用率，定期上报
   - 使用 `event-loop-delay` 或 `process.hrtime` 监测事件循环延迟
   - 使用 `process.memoryUsage()` 监测内存泄漏（heapUsed 持续增长不回落）

5. **告警通知**：
   - 指标超过阈值时通过飞书/钉钉 Webhook 发送告警
   - 核心指标：CPU > 80%、内存 > 80%、事件循环延迟 > 200ms、5xx 错误率 > 1%

## 场景 8：设计一个消息队列场景：订单创建后异步通知

### 题目描述
用户下单成功后，需要异步通知商家、更新库存、发送短信等，请设计基于消息队列的实现方案。

### 考察要点
- 消息队列选型、生产者/消费者模式、消息确认、重试与死信、消息幂等性

### 参考答案

**核心思路**：订单服务作为生产者，将订单事件发布到消息队列，多个消费者独立处理各自业务。

**关键步骤**：

1. **选型**：RabbitMQ（可靠投递）或 Redis Stream（轻量级）

2. **消息结构**：
   ```json
   { "eventType": "order.created", "orderId": 12345, "timestamp": "2026-09-06T10:00:00Z" }
   ```

3. **生产者（订单服务）**：
   - 订单入库成功后，发布消息到 `exchange: order`，路由键 `order.created`
   - 使用事务或本地消息表保证订单与消息的最终一致性

4. **消费者**：
   - 短信通知消费者：订阅 `queue: sms`，调用短信 SDK
   - 商家通知消费者：订阅 `queue: merchant`，推送站内信或 WebSocket
   - 库存更新消费者：订阅 `queue: inventory`，扣减库存
   - 每个消费者独立消费，互不影响

5. **消息确认与重试**：
   - 开启手动 ACK：处理成功后 `channel.ack(msg)`，失败则 `channel.nack(msg, false, true)` 重新入队
   - 重试超过 3 次进入死信队列（DLQ），人工介入处理

6. **幂等性**：
   - 消费者使用 `orderId + eventType` 作为唯一键去重，防止重复消费导致重复扣库存或重复发短信

```typescript
// 伪代码 - 消费者
async consumeOrderCreated(msg: Message) {
  const { orderId } = JSON.parse(msg.content.toString());
  const key = `processed:order:${orderId}`;
  if (await this.redis.get(key)) return this.channel.ack(msg); // 幂等判断
  await this.sendSms(orderId); // 业务处理
  await this.redis.setex(key, 86400, '1');
  this.channel.ack(msg);
}
```

## 场景 9：设计一个数据库读写分离方案

### 题目描述
应用读多写少，需要做数据库读写分离来提升性能，请设计方案。

### 考察要点
- 主从复制原理、读写分离配置、连接池管理、主从延迟处理

### 参考答案

**核心思路**：配置一个主库（写）和多个从库（读），应用层使用 TypeORM 的读写分离功能自动路由。

**关键步骤**：

1. **主从复制架构**：
   - 主库开启 binlog，从库配置 `CHANGE MASTER TO` 开始同步
   - 主库负责 `INSERT/UPDATE/DELETE`，从库负责 `SELECT`

2. **TypeORM 配置**：
   - 配置 `replication` 选项，指定 `master` 和 `slaves` 连接配置
   - TypeORM 自动将查询路由到从库，写操作路由到主库

3. **连接池调优**：
   - 主库连接池可较小（如 `poolSize: 10`），从库连接池较大（如 `poolSize: 30`）
   - 从库多节点时建议配置负载均衡策略

4. **主从延迟处理**：
   - 延迟敏感场景（如下单后立即查询订单）：强制走主库，使用 `@Transactional({ readOnly: false })` 或查询时加 `{ useMaster: true }`
   - 非敏感场景（如历史数据查询）：正常走从库

5. **监控**：
   - 监控 `Seconds_Behind_Master` 指标，延迟超过阈值告警
   - 从库故障时自动摘除，避免影响整体可用性

```typescript
// 伪代码 - TypeORM 配置
{
  type: 'mysql',
  replication: {
    master: { host: 'master-host', port: 3306, username: 'root', password: 'xxx', database: 'db' },
    slaves: [
      { host: 'slave1-host', port: 3306, username: 'root', password: 'xxx', database: 'db' },
      { host: 'slave2-host', port: 3306, username: 'root', password: 'xxx', database: 'db' },
    ],
  },
  extra: { connectionLimit: 10 },
}
```

## 场景 10：设计一个 Docker 多服务部署方案

### 题目描述
设计一个使用 Docker Compose 部署 Node.js + MySQL + Redis 多服务应用的方案。

### 考察要点
- Dockerfile 编写、多阶段构建、Docker Compose 编排、网络配置、数据持久化、环境变量管理

### 参考答案

**核心思路**：使用 Docker Compose 编排三个服务，通过自定义网络互通，数据卷持久化 MySQL 和 Redis 数据。

**关键步骤**：

1. **Node.js Dockerfile**：
   - 多阶段构建：第一阶段安装依赖并编译，第二阶段只复制产物和 `node_modules` 以减小镜像体积
   - 基础镜像选择 `node:18-alpine`，安全且轻量
   - 使用非 root 用户运行应用

2. **docker-compose.yml**：
   - 定义三个服务：`app`（Node.js）、`mysql`、`redis`
   - 所有服务加入同一个自定义网络 `app-network`

## 场景 11：设计一个用户权限管理系统（RBAC）

### 题目描述
设计一个基于 RBAC（基于角色的访问控制）的用户权限管理系统，支持角色分配、权限校验。

### 考察要点
- RBAC 模型设计、数据表结构、权限中间件、动态菜单、权限粒度控制

### 参考答案

**核心思路**：用户 → 角色 → 权限 三层模型，通过自定义装饰器和守卫实现接口级别的权限控制。

**关键步骤**：

1. **数据表设计**：
   - `users`（用户表）
   - `roles`（角色表，如 admin / editor / viewer）
   - `permissions`（权限表，如 `user:create`、`article:delete`）
   - 中间表：`user_roles`（用户-角色多对多）、`role_permissions`（角色-权限多对多）

2. **权限校验守卫**：
   - 自定义 `@RequirePermissions('user:create')` 装饰器，将所需权限元数据附加到路由
   - `PermissionsGuard` 实现 `CanActivate`，从当前用户角色中查出所有权限，检查是否包含装饰器要求的权限
   - 不满足时返回 403 Forbidden

3. **动态菜单**：
   - 登录后根据用户角色返回对应的菜单树（前端根据权限动态渲染）

4. **粒度控制**：
   - 接口级：上述守卫方案
   - 数据级：在 Service 层根据用户角色和所属组织过滤数据，如"只能查看自己的订单"
   - 字段级：返回数据时根据权限过滤敏感字段（如手机号、身份证号）

```typescript
// 伪代码 - 权限守卫
@Injectable()
export class PermissionsGuard implements CanActivate {
  constructor(private reflector: Reflector, private userService: UserService) {}

  async canActivate(context: ExecutionContext): Promise<boolean> {
    const requiredPermissions = this.reflector.getAllAndOverride<string[]>('permissions', [
      context.getHandler(), context.getClass(),
    ]);
    if (!requiredPermissions) return true;
    const { userId } = context.switchToHttp().getRequest().user;
    const userPermissions = await this.userService.getUserPermissions(userId);
    return requiredPermissions.every(p => userPermissions.includes(p));
  }
}
```

## 场景 13：设计一个 WebSocket 实时通知方案

### 题目描述
设计一个 WebSocket 实时通知方案，当系统产生新事件（如新订单、新消息）时，主动推送给前端用户。

### 考察要点
- WebSocket 握手、Socket.IO 使用、房间管理、鉴权、断线重连

### 参考答案

**核心思路**：使用 Socket.IO 建立长连接，用户连接后加入个人房间，后端通过房间广播推送事件。

**关键步骤**：

1. **服务端初始化**：
   - 使用 `@nestjs/websockets` 创建 `EventsGateway`，配置 CORS
   - 启用 `namespace` 区分业务域，如 `/orders`、`/notifications`

2. **鉴权**：
   - 客户端连接时通过 `auth.token` 传递 JWT
   - 网关实现 `canActivate` 或 `OnGatewayConnection` 中验证 token，非法连接直接断开

3. **房间管理**：
   - 连接成功后，将用户加入以 `userId` 命名的房间 `socket.join(userId)`
   - 断开连接时自动离开房间

4. **事件推送**：
   - 业务服务中注入 `EventsGateway`，调用 `this.gateway.server.to(userId).emit('notification', data)` 推送给指定用户
   - 也可推送给所有连接用户（如系统公告）

5. **断线重连**：
   - 客户端配置 `reconnection: true`，退避策略 `reconnectionDelay: 1000`
   - 服务端需要幂等处理重复连接（同一个用户多个 tab 页）

```typescript
// 伪代码
@WebSocketGateway({ cors: { origin: '*' } })
export class EventsGateway implements OnGatewayConnection {
  @WebSocketServer() server: Server;

  async handleConnection(client: Socket) {
    const token = client.handshake.auth.token;
    const payload = jwt.verify(token, JWT_SECRET);
    client.join(payload.sub); // 加入用户房间
  }

  // 业务服务调用
  sendNotification(userId: string, data: any) {
    this.server.to(userId).emit('notification', data);
  }
}
```

## 场景 14：设计一个接口限流方案

### 题目描述
为 API 接口设计限流方案，防止恶意请求和流量突增导致服务不可用。

### 考察要点
- 限流算法（令牌桶 / 漏桶 / 滑动窗口）、Redis 实现、全局和细粒度限流、限流响应处理

### 参考答案

**核心思路**：使用 Redis 实现滑动窗口计数器或令牌桶算法，按 IP 和用户 ID 双重维度限流。

**关键步骤**：

1. **算法选择**：
   - 推荐滑动窗口：用 Redis Sorted Set 存储每个时间窗口内的请求时间戳，`ZREMRANGEBYSCORE` 移除过期记录，`ZCARD` 统计数量
   - 或令牌桶：`Lua` 脚本实现原子性补充令牌和消耗令牌

2. **限流维度**：
   - 全局限流：所有接口总 QPS 不超过 1000
   - 接口级限流：敏感接口（如登录、短信）每分钟不超过 10 次
   - 用户级限流：单个用户每秒不超过 5 次
   - IP 级限流：单个 IP 每分钟不超过 100 次

3. **实现方式**：
   - 自定义 `@Throttle({ limit: 10, ttl: 60 })` 装饰器
   - `ThrottlerGuard` 在请求到达时从 Redis 获取计数，超过阈值返回 429 状态码

4. **限流响应**：
   - 状态码 `429 Too Many Requests`
   - 响应头返回 `Retry-After: <seconds>` 告知客户端何时重试
   - 响应体友好提示"请求过于频繁，请稍后再试"

```typescript
// 伪代码 - Redis 滑动窗口限流
async isRateLimited(key: string, limit: number, windowMs: number): Promise<boolean> {
  const now = Date.now();
  const windowStart = now - windowMs;
  const multi = this.redis.multi();
  multi.zremrangebyscore(key, 0, windowStart); // 移除窗口外记录
  multi.zadd(key, now, `${now}-${Math.random()}`); // 添加当前请求
  multi.zcard(key); // 统计窗口内请求数
  multi.expire(key, Math.ceil(windowMs / 1000));
  const [, , count] = await multi.exec();
  return count > limit;
}
```

## 场景 15：设计一个数据库表结构：电商订单系统

### 题目描述
设计一个电商订单系统的数据库表结构，包含用户、商品、订单、订单项等核心实体。

### 考察要点
- 实体关系设计（ER）、字段类型选择、索引设计、范式与反范式、金额字段处理

### 参考答案

**核心思路**：采用 5 张核心表，遵循第三范式但适当反范式化（冗余订单快照信息）以提升查询性能。

**关键步骤**：

1. **表结构设计**：

```sql
-- 用户表
CREATE TABLE users (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  email       VARCHAR(255) NOT NULL UNIQUE,
  password    VARCHAR(255) NOT NULL,
  nickname    VARCHAR(50),
  phone       VARCHAR(20),
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,

);

-- 商品表
CREATE TABLE products (
  id          BIGINT PRIMARY KEY AUTO_INCREMENT,
  name        VARCHAR(200) NOT NULL,
  description TEXT,
  price       DECIMAL(10, 2) NOT NULL,  -- 金额用 DECIMAL，避免浮点精度问题
  stock       INT NOT NULL DEFAULT 0,
  status      TINYINT NOT NULL DEFAULT 1 COMMENT '1-上架 0-下架',
  created_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at  DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_status (status)
);

-- 订单表
CREATE TABLE orders (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_no      VARCHAR(32) NOT NULL UNIQUE COMMENT '订单号',
  user_id       BIGINT NOT NULL,
  total_amount  DECIMAL(12, 2) NOT NULL COMMENT '订单总金额',
  status        TINYINT NOT NULL DEFAULT 0 COMMENT '0-待支付 1-已支付 2-已发货 3-已完成 4-已取消',
  pay_time      DATETIME COMMENT '支付时间',
  created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  INDEX idx_user_id (user_id),
  INDEX idx_status (status),
  INDEX idx_created_at (created_at),
  FOREIGN KEY (user_id) REFERENCES users(id)
);

-- 订单项表
CREATE TABLE order_items (
  id            BIGINT PRIMARY KEY AUTO_INCREMENT,
  order_id      BIGINT NOT NULL,
  product_id    BIGINT NOT NULL,
  product_name  VARCHAR(200) NOT NULL COMMENT '快照-商品名',

  FOREIGN KEY (product_id) REFERENCES products(id),
  INDEX idx_order_id (order_id)
);
```

2. **设计要点说明**：

   - **索引设计**：`user_id`（用户查询订单）、`status`（按状态筛选）、`created_at`（按时间排序）分别建索引
   - **外键约束**：保证数据一致性，但在分库分表场景下需移除，改为应用层保证
