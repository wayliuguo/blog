## 第一阶段：认识后端（5 题）

### Q1: 后端开发的核心能力有哪些？

① 一句话结论：后端开发的核心能力包括接口设计、数据库操作、业务逻辑实现、服务器部署与性能优化。

② 原理剖析：后端负责处理客户端请求，与数据库交互，执行业务逻辑，返回响应数据。核心能力涵盖 RESTful API 设计、SQL/NoSQL 数据库操作、缓存策略、认证授权、日志与监控、性能调优等。

③ 场景举例：用户登录时，后端验证账号密码、生成 JWT Token、查询用户信息并返回给前端。

④ 优缺点与边界：后端开发需要关注安全性、并发处理和系统稳定性，不同业务场景侧重点不同。

⑤ 追问预判：如何设计一个高可用的后端系统？后端性能优化的常见手段有哪些？

### Q2: Node.js 和 JavaScript 有什么关系？

① 一句话结论：Node.js 是 JavaScript 的运行时环境，让 JS 可以脱离浏览器在服务端运行。

② 原理剖析：JavaScript 最初只在浏览器中运行，Node.js 基于 Chrome V8 引擎，封装了文件系统、网络、进程等系统级 API，使 JS 具备服务端开发能力。Node.js 实现了 CommonJS 模块规范，并逐步支持 ESM。

③ 场景举例：浏览器中的 JS 可以操作 DOM，Node.js 中的 JS 可以操作文件系统：`fs.readFileSync('file.txt')`。

④ 优缺点与边界：两者核心语法相同，但 API 能力不同——浏览器端有 DOM/BOM API，Node.js 有 fs/http/process 等模块。

⑤ 追问预判：Node.js 和浏览器的事件循环有什么区别？

### Q3: 用户在浏览器输入 URL 到页面加载完成，经历了哪些步骤？

① 一句话结论：步骤包括 DNS 解析、TCP 连接、HTTP 请求与响应、浏览器解析渲染。

② 原理剖析：① DNS 解析域名得到 IP 地址；② 建立 TCP 连接（三次握手）；③ 浏览器发送 HTTP 请求；④ 服务器处理请求返回 HTML；⑤ 浏览器解析 HTML，加载 CSS/JS/图片等资源，构建 DOM 树和 CSSOM 树，合并为渲染树后绘制页面。

③ 场景举例：简洁描述：`输入 URL → DNS 解析 → TCP 连接 → HTTP 请求 → 服务器响应 → 浏览器渲染`。

④ 优缺点与边界：现代浏览器还会考虑缓存、CDN、HTTPS（增加 TLS 握手）、HTTP/2 多路复用等优化因素。

⑤ 追问预判：HTTPS 的握手过程是怎样的？DNS 解析的完整流程是什么？

### Q4: 前端和后端的职责划分是怎样的？

① 一句话结论：前端负责用户界面和交互体验，后端负责数据处理和业务逻辑。

② 原理剖析：前端运行在浏览器中，管理 UI 渲染、用户交互、路由跳转、状态管理；后端运行在服务器上，处理数据存储、业务运算、认证授权、API 接口。两者通过 HTTP/WebSocket 等协议通信。

③ 场景举例：用户注册——前端展示表单并校验格式，后端接收数据后写入数据库并返回结果。

④ 优缺点与边界：边界逐渐模糊，Node.js 可以做 BFF（Backend For Frontend），前端也可以做 SSR（服务端渲染）。

⑤ 追问预判：什么是 BFF 模式？什么是 SSR，有哪些优缺点？

### Q5: 什么是 HTTP 协议？常见的状态码有哪些？

① 一句话结论：HTTP 是超文本传输协议，定义客户端和服务器之间的通信格式，是 Web 的基石。

② 原理剖析：HTTP 基于请求-响应模型，客户端发起请求（含方法、路径、头、体），服务器返回响应（含状态码、头、体）。常见状态码：200（成功）、201（已创建）、301（永久重定向）、302（临时重定向）、400（请求错误）、401（未认证）、403（无权限）、404（未找到）、500（服务器错误）、502（网关错误）、503（服务不可用）。

③ 场景举例：`res.status(200).json({ data: 'ok' })` 返回 200 状态码。

④ 优缺点与边界：状态码按类别分：1xx（信息）、2xx（成功）、3xx（重定向）、4xx（客户端错误）、5xx（服务器错误）。

⑤ 追问预判：301 和 302 的区别？HTTP 和 HTTPS 的区别？

## 第二阶段：Node.js 基础（12 题）

### Q6: CommonJS 和 ESM 的区别是什么？

① 一句话结论：CommonJS 使用 require/module.exports，ESM 使用 import/export，是 Node.js 中的两种模块规范。

② 原理剖析：CommonJS 同步加载模块，运行时执行，支持动态 require；ESM 异步加载，静态分析，支持 tree-shaking，import 必须在顶层。Node.js 中 .cjs 文件使用 CommonJS，.mjs 使用 ESM，.js 由 package.json 的 type 字段决定。

③ 场景举例：
```js
// CommonJS
const fs = require('fs');
module.exports = { foo };
// ESM
import fs from 'fs';
export const foo = 'bar';
```

④ 优缺点与边界：CommonJS 兼容性好但无法 tree-shaking，ESM 是现代标准但部分旧库不支持。

⑤ 追问预判：Node.js 中如何在 CommonJS 中导入 ESM 模块？ESM 的 import() 动态导入有什么用？

### Q7: require 的加载机制是怎样的？

① 一句话结论：require 会按路径查找文件，读取并执行模块代码，缓存模块导出对象后返回。

② 原理剖析：加载过程：① 检查缓存，有则直接返回；② 如果是内置模块（如 fs、http）直接返回；③ 根据路径解析文件（补全 .js/.json/.node 后缀）；④ 读取文件内容并包裹在函数中执行；⑤ 缓存模块的 exports 对象。

③ 场景举例：
```js
require('fs')       // 直接返回内置模块
require('./utils')  // 查找 ./utils.js 或 ./utils/index.js
```

④ 优缺点与边界：模块加载后会被缓存，多次 require 同一模块只会执行一次，有利于性能。

⑤ 追问预判：循环引用时 require 会怎样？模块缓存在哪里，如何清除？

### Q8: npm install 时 ^ 和 ~ 的区别？

① 一句话结论：^ 允许次要版本更新，~ 只允许补丁版本更新。

② 原理剖析：语义化版本格式为 `主版本.次版本.补丁`。`^1.2.3` 匹配 `>=1.2.3 <2.0.0`；`~1.2.3` 匹配 `>=1.2.3 <1.3.0`。^ 更宽松，~ 更保守。

③ 场景举例：`"express": "^4.18.0"` 允许安装 4.x.x 内最新版本；`"express": "~4.18.0"` 只允许 4.18.x 内更新。

④ 优缺点与边界：推荐使用 ^ 获取最新次要版本的修复，生产环境用 lock 文件锁定版本。

⑤ 追问预判：package-lock.json 的作用是什么？npm ci 和 npm install 的区别？

### Q9: package.json 中 dependencies 和 devDependencies 的区别？

① 一句话结论：dependencies 是生产环境依赖，devDependencies 是开发环境依赖。

② 原理剖析：dependencies 中的包在 `npm install --production` 时也会安装，而 devDependencies 不会。devDependencies 通常包含测试框架、构建工具、代码检查等开发阶段使用的工具。

③ 场景举例：
```json
{
  "dependencies": { "express": "^4.18.0" },
  "devDependencies": { "jest": "^29.0.0" }
}
```

④ 优缺点与边界：部署时可通过 `NODE_ENV=production` 跳过 devDependencies 安装，减少体积。但严格区分并不绝对，有些工具链也会混用。

⑤ 追问预判：peerDependencies 的作用是什么？为什么有些包需要放在 dependencies 中？

### Q10: 回调函数和 Promise 的区别？

① 一句话结论：回调函数是传统异步处理方式，Promise 是 ES6 引入的现代异步方案，更优雅地处理异步操作。

② 原理剖析：回调函数将结果处理逻辑作为参数传入异步函数，容易形成"回调地狱"；Promise 通过 `.then()` 链式调用，用 `.catch()` 统一处理错误，状态一经改变不可逆（Pending → Fulfilled/Rejected）。

③ 场景举例：
```js
// 回调
fs.readFile('a.txt', (err, data) => { if (err) throw err });
// Promise
fs.promises.readFile('a.txt').then(data => {}).catch(err => {});
```

④ 优缺点与边界：回调适合简单场景，Promise 适合复杂异步流程，配合 async/await 使用体验更佳。

⑤ 追问预判：Promise.all 和 Promise.allSettled 的区别？如何将回调函数转为 Promise？

### Q11: async/await 的本质是什么？

① 一句话结论：async/await 是 Promise 的语法糖，本质是基于 Promise 的异步流程控制。

② 原理剖析：async 函数返回一个 Promise 对象，await 关键字会暂停函数执行，等待 Promise 决议后恢复执行。编译层面，async/await 被转换为生成器（Generator）+ 自动执行器的模式。

③ 场景举例：
```js
async function getData() {
  const res = await fetch('/api');  // 暂停直到 Promise 完成
  return res.json();
}
```

④ 优缺点与边界：async/await 让异步代码看起来像同步，可读性更好，但需注意 await 只影响其所在函数，外层函数仍立即返回 Promise。

⑤ 追问预判：await 在 forEach 中能正常工作吗？如何处理多个并行的 await？

### Q12: try/catch 能捕获异步错误吗？

① 一句话结论：try/catch 只能捕获同步代码中的错误，不能直接捕获异步回调中的错误，但可以捕获 await 表达式的 Promise 拒绝。

② 原理剖析：同步代码中的 throw 可以直接被 try/catch 捕获；异步回调中的错误（如 setTimeout）在 try/catch 作用域之外抛出；但 await 一个 Promise 时，reject 状态可以被 try/catch 捕获。

③ 场景举例：
```js
try { setTimeout(() => { throw Error('err'); }, 100); } catch(e) { /* 捕获不到 */ }
try { const data = await asyncFunc(); } catch(e) { /* 可以捕获 */ }
```

④ 优缺点与边界：对于未使用 await 的 Promise，需通过 .catch() 处理错误。全局未捕获的 Promise 错误可通过 process.on('unhandledRejection') 监听。

⑤ 追问预判：unhandledRejection 和 uncaughtException 的区别？应该如何全局处理错误？

### Q13: fs.readFileSync 和 fs.readFile 的区别？

① 一句话结论：readFileSync 是同步读取，会阻塞进程；readFile 是异步读取，不会阻塞。

② 原理剖析：readFileSync 在读取完成前阻止后续代码执行，适合启动时加载配置文件；readFile 需要回调函数，文件读取完成后回调执行，不阻塞事件循环，适合运行时频繁的文件读取。

③ 场景举例：
```js
const data = fs.readFileSync('config.json');  // 阻塞
fs.readFile('config.json', (err, data) => {}); // 非阻塞
```

④ 优缺点与边界：同步方法代码更简洁但阻塞线程，异步方法性能更好但需处理回调。Node.js 还提供了 fs.promises.readFile 的 Promise 版本。

⑤ 追问预判：fs.promises API 是什么？Node.js 中还有哪些同步/异步对应的 API？

### Q14: path.join 和 path.resolve 的区别？

① 一句话结论：path.join 将多个路径片段拼接成一个路径，path.resolve 将路径解析为绝对路径。

② 原理剖析：join 只是用平台分隔符拼接路径，不会生成绝对路径；resolve 从右到左依次解析，遇到绝对路径则停止，最后生成绝对路径。如果 resolve 的参数都是相对路径，则基于当前工作目录生成绝对路径。

③ 场景举例：
```js
path.join('/a', '/b', 'c')  // 返回 \a\b\c（拼接）
path.resolve('a', 'b', 'c') // 返回 E:\working\a\b\c（绝对路径）
```

④ 优缺点与边界：join 适用于路径拼接，resolve 适用于获取绝对路径。两者都会规范化路径中的 `..` 和 `.`。

⑤ 追问预判：__dirname 和 __filename 的作用？如何获取当前工作目录？

### Q15: process.env 的作用是什么？

① 一句话结论：process.env 是一个包含用户环境变量的对象，用于读取系统环境变量和配置。

② 原理剖析：Node.js 运行时，process.env 会读取当前进程的环境变量。开发者常通过 process.env.NODE_ENV 判断运行环境（development/production），或使用 dotenv 库从 .env 文件加载配置。

③ 场景举例：
```js
const port = process.env.PORT || 3000;  // 默认端口 3000
if (process.env.NODE_ENV === 'production') { /* 生产环境逻辑 */ }
```

④ 优缺点与边界：环境变量适合存储敏感配置（如数据库密码），但不应提交到版本控制。dotenv 库在开发环境中常用。

⑤ 追问预判：如何设置环境变量？.env 文件的工作原理是什么？

### Q16: 如何创建一个简单的 HTTP 服务器？

① 一句话结论：使用 Node.js 内置的 http 模块调用 `http.createServer()` 创建服务器。

② 原理剖析：createServer 接收一个回调函数，每次有请求时回调被调用，回调接收 req（请求对象）和 res（响应对象）。调用 `res.end()` 或 `res.write()` 发送响应。最后调用 `server.listen()` 监听端口。

③ 场景举例：
```js
const http = require('http');
const server = http.createServer((req, res) => {
  res.writeHead(200, { 'Content-Type': 'text/plain' });
  res.end('Hello World');
});
server.listen(3000, () => console.log('Server running on 3000'));
```

④ 优缺点与边界：这是最基础的 HTTP 服务器，生产环境通常使用 Express/Koa 等框架简化开发。

⑤ 追问预判：req 和 res 对象有哪些常用属性和方法？如何解析请求体？

### Q17: console.log 是同步还是异步的？

① 一句话结论：在 Node.js 中，console.log 的底层实现是同步的（向 stdout 写入），但具体行为取决于输出目标。

② 原理剖析：当输出目标是终端（TTY）时，console.log 是同步的，确保日志在进程退出前完整输出；当输出目标是管道或文件时，console.log 是异步的，避免阻塞事件循环。

③ 场景举例：
```js
console.log('start');  // 通常同步输出
process.exit(0);
```

④ 优缺点与边界：在性能敏感场景中，大量 console.log 会影响性能，生产环境应使用日志库（如 Winston）替代。

⑤ 追问预判：console.log 和 console.error 的区别？为什么生产环境不应使用 console.log？

## 第三阶段：Express 与 Koa（8 题）

### Q18: Express 中间件中 next() 不调用会发生什么？

① 一句话结论：不调用 next() 会导致请求被挂起，客户端不会收到响应。

② 原理剖析：Express 中间件按注册顺序执行，每个中间件通过调用 next() 将控制权传递给下一个中间件。如果不调用 next() 且不主动结束响应（如 res.send()），请求会一直停留在该中间件中，直到超时。

③ 场景举例：
```js
app.use((req, res, next) => {
  // 没调用 next()，也没调用 res.send()
  // 请求会被挂起，客户端一直等待
});
```

④ 优缺点与边界：如果中间件是路由处理函数（如 app.get('/')），不调用 next() 但发送了响应是正常的。如果既没 next 也没响应，就是 bug。

⑤ 追问预判：如何判断 next() 是否已被调用？Express 中间件的错误处理机制是什么？

### Q19: Express 中如何获取 URL 参数和查询参数？

① 一句话结论：URL 参数通过 `req.params` 获取，查询参数通过 `req.query` 获取。

② 原理剖析：路由路径中使用 `:param` 定义参数，如 `/user/:id`，匹配后 `req.params.id` 可获取；查询参数即 URL 中 `?` 后的部分，Express 自动解析到 `req.query` 对象中。

③ 场景举例：
```js
app.get('/user/:id', (req, res) => {
  console.log(req.params.id);  // 获取 URL 参数
  console.log(req.query.page); // 获取查询参数 ?page=1
});
```

④ 优缺点与边界：req.params 是路由参数，req.query 是查询字符串参数，req.body 是请求体参数（需中间件解析）。

⑤ 追问预判：如何获取请求体中的 JSON 数据？如何使用 express.Router 组织路由？

### Q20: Express 错误处理中间件的参数有什么特殊之处？

① 一句话结论：错误处理中间件有 4 个参数：(err, req, res, next)，比普通中间件多一个 err 参数。

② 原理剖析：Express 通过中间件参数个数判断是否为错误处理中间件（检查 .length 属性）。当普通中间件中调用 next(err) 时，Express 会跳过后续普通中间件，直接进入错误处理中间件。

③ 场景举例：
```js
app.use((err, req, res, next) => {
  console.error(err.stack);
  res.status(500).send('Something broke!');
});
```

④ 优缺点与边界：错误处理中间件必须定义在所有路由和中间件之后，且必须声明 4 个参数，即使不用的参数也要保留占位。

⑤ 追问预判：如何在 Express 中统一处理 404 错误？生产环境如何避免暴露错误详情？

### Q21: Express 中 app.use 和 app.get 的区别？

① 一句话结论：app.use 匹配所有 HTTP 方法，app.get 只匹配 GET 请求。

② 原理剖析：app.use 的路径匹配是"前缀匹配"，`/user` 会匹配 `/user`、`/user/123` 等；app.get 是精确匹配，`/user` 只匹配 `/user`。app.use 常用于挂载中间件或路由模块，app.get 用于定义具体路由。

③ 场景举例：
```js
app.use('/user', userRouter);       // 挂载路由模块，匹配所有方法
app.get('/user', (req, res) => {}); // 只匹配 GET /user
```

④ 优缺点与边界：实践中 app.use 配合 express.Router() 做模块拆分，app.get/post/put/delete 做具体路由定义。

⑤ 追问预判：app.all 和 app.use 的区别？如何实现一个路由级别的中间件？

### Q22: Koa 的洋葱模型是什么？

① 一句话结论：洋葱模型是 Koa 中间件的执行机制，请求从外到内穿过各层中间件，响应从内到外反向穿出。

② 原理剖析：Koa 中间件通过 async/await 实现，每个中间件在 await next() 前的代码在请求阶段执行，await next() 后的代码在响应阶段执行。整体执行顺序像切洋葱：先进入最外层，再逐层进入，最后逐层返回。

③ 场景举例：
```js
app.use(async (ctx, next) => {
  console.log('1-进入');
  await next();
  console.log('1-返回');
});
// 请求过程：1-进入 → 2-进入 → 2-返回 → 1-返回
```

④ 优缺点与边界：洋葱模型让中间件可以在请求前后都执行逻辑，适合日志记录、请求计时、事务管理等场景。

⑤ 追问预判：Koa 的洋葱模型和 Express 的线性模型有什么区别？如何中止洋葱模型的执行？

### Q23: Koa 中 ctx 对象的常用属性有哪些？

① 一句话结论：ctx 是 Koa 的上下文对象，封装了 req 和 res，提供请求和响应的便捷访问。

② 原理剖析：常用属性：ctx.request / ctx.req（请求对象）、ctx.response / ctx.res（响应对象）、ctx.body（设置响应体）、ctx.status（设置状态码）、ctx.query（查询参数）、ctx.params（路由参数，需配合路由中间件）、ctx.headers（请求头）、ctx.method（请求方法）、ctx.url（请求路径）、ctx.state（共享数据，类似 Express 的 req）。

③ 场景举例：
```js
ctx.body = 'Hello';           // 设置响应体
ctx.status = 201;             // 设置状态码
console.log(ctx.query.name);  // 获取查询参数
```

④ 优缺点与边界：ctx.body 可以赋值为字符串、对象、Buffer、Stream 等，Koa 会自动设置 Content-Type。

⑤ 追问预判：ctx.throw 的用法？ctx.state 的作用是什么？

### Q24: Express 和 Koa 的核心区别是什么？

① 一句话结论：Express 功能更丰富内置，Koa 更轻量灵活，核心区别在于中间件模型和异步处理方式。

② 原理剖析：Express 采用线性中间件模型，回调风格，内置了路由、模板、静态文件等；Koa 采用洋葱模型，基于 async/await，不捆绑任何中间件，核心只提供 ctx 封装。Express 更成熟，生态系统更丰富；Koa 更现代，可定制性更强。

③ 场景举例：
```js
// Express: 回调风格
app.use((req, res, next) => { next(); });
// Koa: async/await 风格
app.use(async (ctx, next) => { await next(); });
```

④ 优缺点与边界：Express 社区更大、文档更多，适合快速开发；Koa 更优雅、灵活，适合需要精细控制的场景。

### Q25: 什么是跨域问题？如何解决？

① 一句话结论：跨域问题是浏览器同源策略限制，禁止不同源（协议、域名、端口任一不同）的页面请求资源。

② 原理剖析：浏览器出于安全考虑，限制脚本发起的跨域 HTTP 请求。常见解决方案：CORS（在后端设置响应头）、JSONP（仅 GET 请求）、代理服务器（开发环境用 webpack-dev-server 代理）。

③ 场景举例：
```js

app.use((req, res, next) => {
  res.setHeader('Access-Control-Allow-Origin', '*');
  res.setHeader('Access-Control-Allow-Methods', 'GET, POST, PUT, DELETE');
  next();
});
```

④ 优缺点与边界：CORS 是最标准最常用的方案，JSONP 只支持 GET 且不安全，生产环境推荐使用 CORS 或代理。

### Q26: 什么是关系型数据库？MySQL 有哪些存储引擎？

① 一句话结论：关系型数据库以表和关系（外键）组织数据，MySQL 的常用存储引擎有 InnoDB 和 MyISAM。

```sql
CREATE TABLE user (id INT PRIMARY KEY) ENGINE=InnoDB;
```

### Q27: INNER JOIN 和 LEFT JOIN 的区别？

① 一句话结论：INNER JOIN 只返回两表匹配的行，LEFT JOIN 返回左表所有行，右表无匹配则填充 NULL。

② 原理剖析：INNER JOIN 取两表交集，只有当关联条件在两边都满足时才返回；LEFT JOIN 以左表为基准，左表全部返回，右表没有匹配的字段为 NULL。

③ 场景举例：
```sql
-- INNER JOIN: 只返回有订单的用户
SELECT * FROM user INNER JOIN order ON user.id = order.user_id;
-- LEFT JOIN: 返回所有用户及其订单，无订单的用户订单字段为 NULL
SELECT * FROM user LEFT JOIN order ON user.id = order.user_id;
```

④ 优缺点与边界：INNER JOIN 效率更高但会丢失数据，LEFT JOIN 保证左表完整性。RIGHT JOIN 同理，但通常用 LEFT JOIN 替代。

⑤ 追问预判：JOIN 和子查询的性能对比？多表 JOIN 时如何优化性能？

### Q28: 什么是主键和外键？主键和外键有什么区别？

① 一句话结论：主键是表的唯一标识，外键是关联其他表的字段，保证数据完整性。

② 原理剖析：主键（PRIMARY KEY）唯一标识一行记录，不能为 NULL，一个表只有一个主键；外键（FOREIGN KEY）指向另一张表的主键，用于建立表间关联，可以为 NULL，可以有多个。主键保证实体完整性，外键保证引用完整性。

③ 场景举例：
```sql
CREATE TABLE user (id INT PRIMARY KEY);  -- 主键
CREATE TABLE order (id INT, user_id INT, FOREIGN KEY (user_id) REFERENCES user(id));  -- 外键
```

④ 优缺点与边界：主键通常用自增 ID 或 UUID，外键在分布式场景中因性能考虑有时会省略，改为在应用层维护。

⑤ 追问预判：什么是联合主键？什么是唯一约束？外键对性能有什么影响？

### Q29: CHAR 和 VARCHAR 的区别？

① 一句话结论：CHAR 是固定长度字符串，VARCHAR 是可变长度字符串。

② 原理剖析：CHAR(n) 占用固定 n 个字符空间，不足时用空格填充，存取速度快；VARCHAR(n) 根据实际长度加 1~2 字节存储，更省空间，但会有额外计算开销。CHAR 适合长度固定的数据（如手机号、身份证号），VARCHAR 适合长度不定的数据（如用户名、地址）。

③ 场景举例：
```sql
CREATE TABLE user (phone CHAR(11), name VARCHAR(50));
```

④ 优缺点与边界：CHAR 查询略快，但浪费空间；VARCHAR 节省空间但有少量额外开销。MySQL 中 VARCHAR 最大 65535 字节。

⑤ 追问预判：CHAR 和 VARCHAR 的最大长度？TEXT 和 VARCHAR 的区别？

### Q30: DELETE、TRUNCATE、DROP 的区别？

① 一句话结论：DELETE 删除行（可回滚），TRUNCATE 清空表（不可回滚，重置自增 ID），DROP 删除整个表结构。

② 原理剖析：DELETE 是 DML 操作，逐行删除，触发触发器，可加 WHERE 条件，支持事务回滚；TRUNCATE 是 DDL 操作，直接释放数据页，速度快，不能回滚，重置自增计数器；DROP 是 DDL 操作，删除整张表（结构和数据），不可恢复。

③ 场景举例：
```sql
DELETE FROM user WHERE id = 1;  -- 删除指定行
TRUNCATE TABLE user;            -- 清空表
DROP TABLE user;                -- 删除表
```

④ 优缺点与边界：删除少量数据用 DELETE，清空表用 TRUNCATE，删除整表用 DROP。生产环境 DELETE 需谨慎，TRUNCATE 和 DROP 操作前务必确认。

⑤ 追问预判：TRUNCATE 为什么不能回滚？DELETE 删除大量数据时性能问题如何优化？

### Q31: 什么是数据库连接池？为什么需要连接池？

① 一句话结论：数据库连接池是维护一组数据库连接的缓存池，复用连接避免频繁创建和销毁。

② 原理剖析：创建数据库连接是重量级操作（TCP 握手、认证等），每次请求都新建连接开销巨大。连接池预先创建一批连接，请求时从池中获取，使用后归还，控制并发连接数，提升性能。

③ 场景举例：
```js
const pool = mysql.createPool({ host: 'localhost', connectionLimit: 10 });
pool.query('SELECT * FROM user', (err, results) => {});  // 从池中取连接执行
```

④ 优缺点与边界：连接池能显著提升性能，但需合理设置最大连接数，过多会耗尽数据库资源，过少会导致请求排队。

⑤ 追问预判：连接池的常用参数有哪些？如何监控连接池状态？

### Q32: 什么是 NoSQL？MongoDB 和 MySQL 的区别？

① 一句话结论：NoSQL 是非关系型数据库，MongoDB 是文档型 NoSQL 数据库，与 MySQL 在数据模型和扩展性上不同。

④ 优缺点与边界：MongoDB 开发效率高、迭代快，但多表关联弱；MySQL 事务成熟、生态完善。选型取决于业务场景。

### Q33: MongoDB 的文档（Document）和集合（Collection）是什么？

③ 场景举例：

### Q34: Mongoose 中 Schema 和 Model 的关系？

① 一句话结论：Schema 定义文档结构，Model 基于 Schema 编译生成，用于操作数据库的构造函数。

② 原理剖析：Schema 定义字段名、类型、验证规则、默认值等结构信息；Model 通过 Schema 编译而成，提供了 CRUD 方法（find、create、update、delete 等），一个 Model 对应一个集合。

```js
const userSchema = new mongoose.Schema({ name: String, age: Number });  // 定义结构
```

④ 优缺点与边界：Schema 是"模板"，Model 是"操作接口"。修改 Schema 不影响已有数据，但 Model 的方法会基于 Schema 的验证规则检查数据。

### Q35: 依赖注入的好处是什么？

① 一句话结论：依赖注入降低代码耦合度，提高可测试性和可维护性。

② 原理剖析：依赖注入（DI）将对象的创建和依赖关系交由容器管理，类不需要自己创建依赖，而是通过构造函数声明依赖，由容器自动注入。好处：① 解耦，类不依赖具体实现；② 易测试，可轻松注入 Mock 对象；③ 单例管理，依赖默认单例，节省资源。

③ 场景举例：
```ts
@Injectable()
export class UserService {
  constructor(private readonly userRepo: UserRepository) {}  // DI 注入
}
```

④ 优缺点与边界：DI 增加了启动时的复杂度，但长期维护收益显著。NestJS 的 DI 容器基于 TypeScript 的装饰器实现。

### Q36: &#64;Controller() 装饰器的作用是什么？

① 一句话结论：&#64;Controller() 标记一个类为 NestJS 的控制器，用于定义路由和处理请求。

② 原理剖析：&#64;Controller() 接收一个可选的路由前缀参数，如 `&#64;Controller('users')`，该控制器内所有路由都会自动添加 /users 前缀。控制器中的方法通过 &#64;Get()、&#64;Post() 等装饰器定义具体路由和 HTTP 方法。

③ 场景举例：
```ts
@Controller('users')  // 前缀 /users
export class UserController {
  @Get(':id')         // GET /users/:id
  findOne(@Param('id') id: string) { return this.userService.findById(id); }
}
```

④ 优缺点与边界：控制器负责接收请求和返回响应，不应包含业务逻辑，业务逻辑应放在 Service 层。

### Q37: &#64;Get()、&#64;Post()、&#64;Put()、&#64;Delete() 分别对应什么 HTTP 方法？

① 一句话结论：&#64;Get() 对应 GET（查询），&#64;Post() 对应 POST（创建），&#64;Put() 对应 PUT（全量更新），&#64;Delete() 对应 DELETE（删除）。

② 原理剖析：这些装饰器是 NestJS 提供的 HTTP 方法装饰器，分别对应 RESTful API 中的 CRUD 操作：GET 获取资源、POST 创建资源、PUT 更新资源（全量替换）、DELETE 删除资源。PATCH（部分更新）使用 &#64;Patch()。

③ 场景举例：
```ts
@Get() findAll() {}       // GET /users
@Post() create() {}       // POST /users
@Put(':id') update() {}   // PUT /users/:id
@Delete(':id') remove() {} // DELETE /users/:id
```

④ 优缺点与边界：PUT 和 PATCH 的区别：PUT 替换整个资源，PATCH 只更新部分字段。RESTful 设计提倡使用复数名词作为路由名。

### Q38: &#64;Param()、&#64;Query()、&#64;Body() 分别获取什么数据？

① 一句话结论：&#64;Param() 获取路由参数，&#64;Query() 获取查询参数，&#64;Body() 获取请求体数据。

② 原理剖析：&#64;Param() 从 URL 路径中提取参数，如 /users/:id 中的 id；&#64;Query() 从 URL 问号后提取参数，如 ?page=1&size=10；&#64;Body() 从请求体中提取数据，通常用于 POST/PUT 请求，需配合 ValidationPipe 做校验。

③ 场景举例：
```ts
@Get(':id')
findOne(@Param('id') id: string, @Query('include') include: string) {}
@Post()
create(@Body() createUserDto: CreateUserDto) {}
```

④ 优缺点与边界：三者的数据来源不同，可同时使用。&#64;Body() 需要请求体解析中间件（NestJS 默认使用 body-parser）。

### Q39: 模块的 imports 和 exports 的作用？

① 一句话结论：imports 导入其他模块的功能，exports 导出本模块的功能供其他模块使用。

② 原理剖析：imports 数组中引入的模块，其导出的 Provider 可以在本模块中使用；exports 数组将本模块的部分 Provider（通常是 Service）暴露出去，导入该模块的其他模块可以使用这些 Provider。模块默认封装，不 exports 的 Provider 对外不可见。

③ 场景举例：
```ts
@Module({
  imports: [DatabaseModule],    // 导入 DatabaseModule 的功能
  exports: [UserService],       // 导出 UserService 供其他模块使用
})
export class UserModule {}
```

④ 优缺点与边界：imports 和 exports 构成了 NestJS 的模块依赖图，通过模块封装实现关注点分离。

⑤ 追问预判：&#64;Global() 装饰器的作用？模块的 providers 和 controllers 配置项的作用？

### Q40: &#64;Module 装饰器的完整配置项有哪些？

① 一句话结论：&#64;Module 的配置项包括：providers、controllers、imports、exports。

② 原理剖析：providers：注册该模块中可被注入的服务/提供者；controllers：注册该模块的控制器，NestJS 会自动实例化；imports：导入其他模块，引入其导出的功能；exports：导出本模块的 Provider，供其他模块使用。此外还有 global（设置为 true 使模块全局可见）。

③ 场景举例：
```ts
@Module({
  imports: [CommonModule],        // 导入模块
  controllers: [UserController],  // 注册控制器
  providers: [UserService],       // 注册服务
  exports: [UserService],         // 导出服务
})
export class UserModule {}
```

④ 优缺点与边界：所有配置项都是可选的，空模块也合法。模块可以重新导出（re-export）其他模块的 exports。

### Q41: Docker 镜像和容器的区别？

① 一句话结论：镜像是只读的模板，容器是镜像的运行实例，类似"类与对象"的关系。

② 原理剖析：镜像（Image）是一个静态的文件包，包含运行应用所需的代码、运行时、库、环境变量等；容器（Container）是镜像的运行实例，有独立的文件系统、网络、进程空间，可以被启动、停止、删除。一个镜像可以创建多个容器。


④ 优缺点与边界：镜像是分层的（Layer），容器在镜像层上添加可写层。镜像构建后不可变，容器的更改可以提交为新镜像。

### Q42: Dockerfile 中 COPY 和 ADD 的区别？

① 一句话结论：COPY 只能复制本地文件到镜像，ADD 额外支持 URL 下载和自动解压 tar 包。

② 原理剖析：COPY 是纯粹的文件复制指令，将构建上下文中的文件复制到镜像指定路径；ADD 在 COPY 的基础上增加了两个功能：支持从 URL 下载文件到镜像，支持自动解压本地 tar 压缩包。官方推荐优先使用 COPY，只有需要解压功能时才用 ADD。

③ 场景举例：
```dockerfile
COPY package.json /app/          # 复制 package.json
ADD app.tar.gz /app/             # 复制并自动解压
```

④ 优缺点与边界：COPY 更透明、更安全（无意外下载），ADD 的隐式行为可能导致意外。多阶段构建中通常只用 COPY。

### Q43: PM2 的常用命令有哪些？

① 一句话结论：PM2 是 Node.js 进程管理工具，常用命令包括启动、停止、重启、查看日志等。

② 原理剖析：PM2 核心命令：`pm2 start app.js`（启动进程）、`pm2 stop <name>`（停止）、`pm2 restart <name>`（重启）、`pm2 delete <name>`（删除进程）、`pm2 list`（查看进程列表）、`pm2 logs`（查看日志）、`pm2 monit`（监控面板）、`pm2 save`（保存进程列表）、`pm2 startup`（设置开机自启）。

③ 场景举例：
```bash
pm2 start app.js -i max --name my-app   # 启动，集群模式，最大实例数
pm2 list                                  # 查看所有进程
pm2 logs my-app                           # 查看 my-app 日志
```

④ 优缺点与边界：PM2 支持集群模式（利用多核 CPU）、自动重启、内存监控、日志管理等功能，适合生产环境部署。

### Q44: Git 中 git merge 和 git rebase 的区别？

① 一句话结论：merge 保留分支历史，rebase 重写提交历史使分支呈线性。

② 原理剖析：merge 将两个分支的末端合并，生成一个新的合并提交，保留完整的分支历史；rebase 将当前分支的提交"移植"到目标分支的顶端，重新生成提交，历史是线性的。merge 更安全但历史有分叉，rebase 历史更清晰但会改写提交。

③ 场景举例：
```bash
git merge feature    # 生成合并提交，保留分支结构
git rebase feature   # 将当前分支提交移到 feature 顶端，线性历史
```

④ 优缺点与边界：公共分支禁止 rebase（会改写已推送的历史），个人分支推荐 rebase 保持整洁。merge 适合多人协作，rebase 适合个人开发。

### Q45: .gitignore 文件的作用是什么？

① 一句话结论：.gitignore 用于指定 Git 应忽略的文件和目录，不被纳入版本控制。

② 原理剖析：在 .gitignore 中写入文件或目录模式，匹配的文件不会被 git add 跟踪，也不会出现在 git status 中。通常忽略 node_modules、.env、dist、.log 等不应提交的文件。

③ 场景举例：
```
node_modules/
.env
dist/
*.log
.DS_Store
```

④ 优缺点与边界：.gitignore 只对未被跟踪的文件生效，已被跟踪的文件需要先执行 `git rm --cached` 移除缓存。不同项目有不同的忽略规则，可参考 GitHub 的模板。

⑤ 追问预判：.gitignore 的匹配规则有哪些？如何忽略已经被跟踪的文件？
