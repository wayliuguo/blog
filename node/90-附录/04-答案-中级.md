## 第二阶段：Node.js 基础

### Q46: 事件循环中微任务和宏任务的执行顺序？

① **一句话结论**：每轮事件循环先执行一个宏任务，然后清空所有微任务队列，再执行下一个宏任务。

② **原理剖析**：事件循环的核心是循环执行宏任务队列。每次取出一个宏任务执行后，会检查微任务队列，将队列中所有微任务依次执行完毕，再进入下一轮宏任务。微任务包括 Promise.then、process.nextTick（实际优先级高于微任务）、queueMicrotask；宏任务包括 setTimeout、setInterval、I/O、setImmediate。

③ **场景举例**：
```js
console.log('1');
setTimeout(() => console.log('2'), 0);
Promise.resolve().then(() => console.log('3'));
console.log('4');
// 输出：1, 4, 3, 2
```

④ **优缺点与边界**：微任务优先级高于宏任务，但微任务中嵌套微任务会阻塞宏任务执行，需避免递归微任务导致死循环。

⑤ **追问预判**：process.nextTick 和 Promise.then 的执行顺序？setImmediate 和 setTimeout 的顺序？

### Q47: process.nextTick 和 Promise.then 谁先执行？

① **一句话结论**：process.nextTick 先于 Promise.then 执行。

② **原理剖析**：process.nextTick 不属于事件循环的正式阶段，而是在每个阶段切换时，优先于所有微任务执行。Promise.then 属于微任务，在微任务队列中执行。Node.js 在事件循环每个阶段完成后，会先执行完所有 process.nextTick 回调，再执行其他微任务。

③ **场景举例**：
```js
Promise.resolve().then(() => console.log('promise'));
process.nextTick(() => console.log('nextTick'));
// 输出：nextTick → promise
```

④ **优缺点与边界**：process.nextTick 优先级最高，但过度使用会阻塞事件循环，导致 I/O 饥饿。官方推荐优先使用 queueMicrotask 或 Promise。

⑤ **追问预判**：为什么要设计 process.nextTick 优先级高于 Promise？什么场景下需要使用 process.nextTick？

### Q48: setTimeout(() => {}, 0) 会在下一轮事件循环立即执行吗？

① **一句话结论**：不会立即执行，最快也要在当前事件循环的 timers 阶段执行，且受其他任务影响可能延迟。

② **原理剖析**：setTimeout(fn, 0) 并非真正的 0ms 延迟，浏览器和 Node.js 有最小延迟限制（通常 1-4ms）。它会被放入 timers 阶段对应的红黑树中，当前事件循环的所有同步任务和微任务执行完毕后，在 timers 阶段检查是否到时间，到时间才执行。

③ **场景举例**：
```js
setTimeout(() => console.log('timeout'), 0);
console.log('sync');
// 输出：sync → timeout
// 但实际执行可能延迟 1ms 以上
```

④ **优缺点与边界**：setTimeout(fn, 0) 不能保证精确的 0ms 延迟，计时器精度受系统调度影响。需要尽快异步执行时，setImmediate 或 process.nextTick 更合适。

⑤ **追问预判**：setTimeout(fn, 0) 和 setImmediate 的执行顺序？在 Node.js 和浏览器中表现是否一致？

### Q49: Node.js 的 Buffer 是什么？和普通数组有什么区别？

① **一句话结论**：Buffer 是 Node.js 用于处理二进制数据的类，类似数组但专门用于字节操作，与普通数组在存储类型、大小固定、性能方面有显著区别。

② **原理剖析**：Buffer 在堆外分配内存（通过 C++ 层面的 Node.js 内存管理），存储的是 0-255 的字节值；普通数组在 V8 堆内分配，可存储任意类型。Buffer 一旦创建大小固定，不能动态调整；普通数组可以 push/pop。Buffer 支持与字符串、Stream、文件读写等 Node.js 核心 API 无缝对接。

③ **场景举例**：
```js
const buf = Buffer.alloc(4); // 固定 4 字节
buf.writeUInt8(0x68, 0);    // 写入字节
const arr = [1, 2, 3];      // 可动态扩展
arr.push(4);
```

④ **优缺点与边界**：Buffer 性能更高（内存分配在堆外），但大小固定，超出范围会截断或报错。普通数组更灵活但不适合二进制数据操作。

⑤ **追问预判**：Buffer.alloc 和 Buffer.from 的区别？Buffer 和 ArrayBuffer 的关系？

### Q50: Stream 的四种类型是什么？

① **一句话结论**：Stream 的四种类型是：Readable（可读）、Writable（可写）、Duplex（双工）、Transform（转换）。

② **原理剖析**：Readable 用于读取数据（如 fs.createReadStream），Writable 用于写入数据（如 fs.createWriteStream），Duplex 既可读又可写（如 net.Socket），Transform 是 Duplex 的特例，在读写过程中可修改数据（如 zlib.createGzip）。它们都继承自 EventEmitter。

③ **场景举例**：
```js
const fs = require('fs');
const readStream = fs.createReadStream('input.txt');    // Readable
const writeStream = fs.createWriteStream('output.txt'); // Writable
const { Transform } = require('stream');
const upper = new Transform({
  transform(chunk, enc, cb) { cb(null, chunk.toString().toUpperCase()); }
}); // Transform
```

④ **优缺点与边界**：Stream 通过事件机制实现流式处理，避免内存溢出，适合大文件处理。但错误处理不当容易导致内存泄漏。

⑤ **追问预判**：什么是 Stream 的 highWaterMark？pipeline 和 pipe 的区别？

### Q51: Readable Stream 的两种模式（flowing 和 paused）的区别？

① **一句话结论**：Flowing 模式数据自动流动，需监听 data 事件消费；Paused 模式需手动调用 read() 拉取数据。

② **原理剖析**：Flowing 模式下，Stream 会尽可能快地将数据通过 data 事件推送，不消费会丢失；Paused 模式是默认模式，流不主动推送数据，调用 read() 时从内部缓冲区拉取数据。通过监听 data 事件、pipe() 或 resume() 可切换到 flowing 模式；调用 pause() 或取消 data 事件监听可切回 paused 模式。

③ **场景举例**：
```js
// Flowing 模式
readStream.on('data', chunk => console.log(chunk));
// Paused 模式
readStream.on('readable', () => {
  let chunk;
  while ((chunk = readStream.read()) !== null) {
    console.log(chunk);
  }
});
```

④ **优缺点与边界**：Flowing 模式方便但容易丢失数据；Paused 模式控制更精细，适合背压处理。pipe() 内部自动管理模式切换和背压。

⑤ **追问预判**：什么是背压（Backpressure）？如何手动实现背压控制？

### Q52: uncaughtException 和 unhandledRejection 的区别？

① **一句话结论**：uncaughtException 捕获未被 try/catch 包裹的同步异常，unhandledRejection 捕获未被 catch 处理的 Promise reject。

② **原理剖析**：uncaughtException 对应 process 对象的 'uncaughtException' 事件，触发时表示代码中有未处理的同步错误，Node.js 会打印堆栈并退出进程。unhandledRejection 对应 'unhandledRejection' 事件，Promise 的 reject 未被 .catch() 或 await 捕获时触发。

③ **场景举例**：
```js
process.on('uncaughtException', err => console.error('未捕获异常:', err));
process.on('unhandledRejection', (reason) => console.error('未处理拒绝:', reason));
throw new Error('sync error');  // 触发 uncaughtException
Promise.reject('async error');  // 触发 unhandledRejection
```

④ **优缺点与边界**：官方不推荐在生产环境用 uncaughtException 恢复程序，因为进程处于不稳定状态，应记录错误后优雅退出。unhandledRejection 在 Node.js 15+ 中默认会终止进程。

⑤ **追问预判**：uncaughtExceptionMonitor 事件的作用？如何全局捕获异步错误？

### Q53: 什么是 EventEmitter？如何自定义事件？

① **一句话结论**：EventEmitter 是 Node.js 的事件驱动核心模块，用于实现发布-订阅模式，通过 on/emit 自定义事件。

② **原理剖析**：EventEmitter 是 events 模块导出的类，核心方法包括 on(event, listener) 注册监听、emit(event, ...args) 触发事件、once() 单次监听、removeListener() 移除监听、removeAllListeners() 移除所有监听。自定义事件通过继承 EventEmitter 类实现。

③ **场景举例**：
```js
const EventEmitter = require('events');
class MyEmitter extends EventEmitter {}
const myEmitter = new MyEmitter();
myEmitter.on('customEvent', (data) => console.log('收到:', data));
myEmitter.emit('customEvent', 'hello');
```

④ **优缺点与边界**：EventEmitter 最大支持默认 10 个监听器（可通过 setMaxListeners 修改），超过会告警。事件名建议使用 Symbol 或字符串常量避免命名冲突。

⑤ **追问预判**：EventEmitter 的 newListener 和 removeListener 事件？on 和 addListener 的区别？

## 第三阶段：Express 与 Koa

### Q54: Express 错误处理中间件为什么有 4 个参数？

① **一句话结论**：Express 通过函数参数数量（4 个参数）来识别错误处理中间件，与其他中间件区分。

② **原理剖析**：Express 中间件栈执行时，遇到错误会跳过普通中间件，直接寻找下一个拥有 4 个参数 (err, req, res, next) 的中间件。Express 内部通过检查函数 .length 属性来判断参数个数，4 个参数即被识别为错误处理中间件。

③ **场景举例**：
```js
app.use((err, req, res, next) => {
  console.error(err.stack);
  res.status(500).send('Something broke!');
});
```

④ **优缺点与边界**：错误处理中间件必须放在所有路由和中间件之后，且必须保留 4 个参数，否则 Express 不会将其视为错误处理中间件。

⑤ **追问预判**：Express 中未捕获的错误如何传递到错误处理中间件？如何捕获异步错误？

### Q55: 如何实现一个自定义的 Express 中间件？

① **一句话结论**：自定义 Express 中间件是一个接收 (req, res, next) 的函数，在函数中执行逻辑后调用 next()。

② **原理剖析**：中间件函数可以修改 req 和 res 对象，执行日志、认证、解析等操作。调用 next() 将控制权传递给下一个中间件，不调用则请求挂起。通过 app.use() 注册全局中间件，或通过 app.get/post() 注册路由级中间件。

③ **场景举例**：
```js
// 自定义日志中间件
const logger = (req, res, next) => {
  console.log(`${req.method} ${req.url}`);
  next();
};
app.use(logger);
```

④ **优缺点与边界**：中间件按注册顺序执行。需注意：在中间件中修改 req/res 对象时，不要覆盖已有属性；异步中间件需确保错误被传递给 next(err)。

⑤ **追问预判**：中间件中如何实现错误处理？如何实现一个限流中间件？

### Q56: Express 中如何实现文件上传？

① **一句话结论**：Express 中常使用 multer 中间件实现文件上传，multer 解析 multipart/form-data 格式的请求体。

② **原理剖析**：multer 通过 `multer({ dest: 'uploads/' })` 配置上传目录，提供 .single()、.array()、.fields() 等方法处理不同数量的文件上传。上传的文件信息保存在 req.file 或 req.files 中，包含原始文件名、大小、MIME 类型等。

③ **场景举例**：
```js
const multer = require('multer');
const upload = multer({ dest: 'uploads/' });
app.post('/upload', upload.single('avatar'), (req, res) => {
  console.log(req.file); // 文件信息
  res.send('上传成功');
});
```

④ **优缺点与边界**：multer 基于 busboy 实现，支持文件大小限制、文件类型过滤等。Express 内置的 body-parser 不支持 multipart 格式，所以必须使用 multer 或 formidable 等第三方库。

⑤ **追问预判**：multer 的 diskStorage 和 memoryStorage 的区别？如何限制文件类型？

### Q57: Koa 中如何实现错误处理？

① **一句话结论**：Koa 通过 try/catch 包裹中间件组合，结合 ctx.throw 和 onerror 事件实现错误处理。

② **原理剖析**：Koa 的洋葱模型使得错误处理中间件可以包裹所有后续中间件。在最外层加上 try/catch，捕获所有下游中间件抛出的错误。Koa 通过 ctx.throw(status, msg) 主动抛出 HTTP 错误，未被捕获的错误会触发 app 的 error 事件。

③ **场景举例**：
```js
app.use(async (ctx, next) => {
  try {
    await next();
  } catch (err) {
    ctx.status = err.status || 500;
    ctx.body = { message: err.message };
  }
});
```

④ **优缺点与边界**：Koa 的错误处理比 Express 更优雅，因为 async/await 让错误捕获更自然。但需注意，如果忘记 await next()，错误将无法被外部捕获。

⑤ **追问预判**：Koa 中如何区分 404 和其他错误？ctx.throw 和 throw new Error 的区别？

### Q58: 什么是 CSRF？在 Express 中如何防御？

① **一句话结论**：CSRF（跨站请求伪造）是攻击者诱导用户点击链接，在用户已登录状态下执行非本意操作的攻击方式。Express 中常用 csurf 或 SameSite Cookie 防御。

② **原理剖析**：CSRF 利用浏览器自动携带 Cookie 的特性，用户在登录 A 网站后，未退出时访问恶意网站 B，B 站点伪造请求到 A 网站执行操作。防御方式包括：使用 CSRF Token（服务端生成 Token 嵌入表单，提交时校验）、SameSite Cookie 属性（限制跨站请求携带 Cookie）、验证 Referer 头。

③ **场景举例**：
```js
// 使用 csurf 中间件
const csrf = require('csurf');
app.use(csrf({ cookie: true }));
app.get('/form', (req, res) => {
  res.render('form', { csrfToken: req.csrfToken() });
});
```

④ **优缺点与边界**：CSRF Token 是主流防御方式，但需要前后端配合。SameSite 属性在现代浏览器中支持较好，但兼容性仍需考虑。

⑤ **追问预判**：CSRF 和 XSS 的区别？如何在没有 csurf 的情况下手动实现 CSRF 防御？

## 第四阶段：数据库 - MySQL

### Q59: 什么是索引？索引的本质是什么？

① **一句话结论**：索引是帮助 MySQL 高效获取数据的数据结构，本质上是排好序的快速查找数据结构（通常为 B+Tree）。

② **原理剖析**：索引存储了表中某列的值和对应行的物理地址指针，通过减少扫描的数据量来提升查询速度。MySQL InnoDB 引擎默认使用 B+Tree 索引，叶子节点存储完整行数据（聚簇索引），非叶子节点只存储索引键和子节点指针。索引的本质是空间换时间。

③ **场景举例**：
```sql
CREATE INDEX idx_name ON users(name); -- 在 name 列创建索引
SELECT * FROM users WHERE name = 'John'; -- 使用索引加速查找
```

④ **优缺点与边界**：索引能大幅提升查询速度，但会降低插入、更新、删除的性能，且占用额外磁盘空间。应在频繁查询的列上建索引，避免在频繁更新的列上建过多索引。

⑤ **追问预判**：聚簇索引和非聚簇索引的区别？联合索引的存储结构？

### Q60: 什么是最左前缀匹配原则？

① **一句话结论**：最左前缀匹配原则指联合索引查询时，从索引的最左列开始匹配，跳过的列会导致索引部分失效。

② **原理剖析**：MySQL 创建联合索引 (a, b, c) 时，会先按 a 排序，a 相同再按 b 排序，b 相同再按 c 排序。查询条件必须从最左列 a 开始，且中间的列不能跳过。如果查询条件是 b 和 c 而没有 a，则索引完全失效。如果查询条件是 a 和 c，则只有 a 能用到索引，c 无法用到。

③ **场景举例**：
```sql
-- 联合索引 (a, b, c)
WHERE a = 1           -- 用索引
WHERE a = 1 AND b = 2 -- 用索引
WHERE a = 1 AND c = 3 -- 只有 a 用到索引
WHERE b = 2           -- 索引失效
```

④ **优缺点与边界**：设计联合索引时，应将区分度高的列放在最左边，查询频率高的列放在最左边。最左前缀也适用于排序和分组。

⑤ **追问预判**：如何通过调整联合索引列顺序优化查询？最左前缀在排序中的表现？

### Q61: 索引失效的情况有哪些？

① **一句话结论**：索引失效的常见情况包括：对索引列使用函数或计算、使用 LIKE 前缀模糊查询、隐式类型转换、OR 条件包含非索引列等。

② **原理剖析**：当查询条件中对索引列进行函数操作（如 WHERE YEAR(date)=2024）、运算（如 WHERE age+1=20）、或使用 LIKE '%keyword'（前缀模糊）时，MySQL 无法使用索引，只能全表扫描。隐式类型转换（如字符串列不传引号）也会导致索引失效。OR 条件中只要有一个字段没有索引，整个查询就不会走索引。

③ **场景举例**：
```sql
SELECT * FROM users WHERE YEAR(create_time) = 2024; -- 函数导致索引失效
SELECT * FROM users WHERE name LIKE '%王';          -- 前缀模糊失效
SELECT * FROM users WHERE phone = 13800000000;      -- 隐式类型转换（phone 是 varchar）
```

④ **优缺点与边界**：避免索引失效的方法：不在索引列上使用函数、使用覆盖索引、使用 IN 代替 OR。MySQL 优化器不一定会选择最优索引，有时需要 FORCE INDEX 强制指定。

⑤ **追问预判**：什么是索引下推（ICP）？如何通过 EXPLAIN 分析索引使用情况？

### Q62: EXPLAIN 命令中 type 字段各值的性能排序？

① **一句话结论**：type 字段性能从优到劣排序：system > const > eq_ref > ref > range > index > ALL。

② **原理剖析**：system 表示表中只有一条数据（系统表），const 表示通过主键或唯一索引等值查询最多匹配一行，eq_ref 表示多表 JOIN 时每个表匹配一行（主键关联），ref 表示非唯一索引等值查询匹配多行，range 表示索引范围扫描（>、<、BETWEEN、IN），index 表示全索引扫描（遍历索引树），ALL 表示全表扫描（最差）。

③ **场景举例**：
```sql
EXPLAIN SELECT * FROM users WHERE id = 1;        -- const
EXPLAIN SELECT * FROM users WHERE name = 'John'; -- ref（非唯一索引）
EXPLAIN SELECT * FROM users WHERE age > 18;      -- range
EXPLAIN SELECT * FROM users;                      -- ALL
```

④ **优缺点与边界**：日常优化目标是至少达到 ref 或 range 级别，避免出现 ALL。system 和 const 是理想情况，实际业务中很少出现。

⑤ **追问预判**：Extra 字段中 Using index、Using where、Using filesort 分别表示什么？如何优化 filesort？

### Q63: 什么是 N+1 查询问题？如何解决？

① **一句话结论**：N+1 查询问题指查询主表数据后，对每条记录额外执行一次关联查询，导致总查询次数为 N+1 次，严重影响性能。

② **原理剖析**：常见于 ORM 懒加载场景。例如查出 100 个用户后，遍历每个用户查询其订单，产生 1 次用户查询 + 100 次订单查询。解决方案：使用 JOIN 一次性查询关联数据，或在 ORM 中使用预加载（eager loading）。

③ **场景举例**：
```js
// N+1 问题示例（Mongoose）
const users = await User.find();
for (const user of users) {
  const orders = await Order.find({ userId: user.id }); // 循环 N 次查询
}
// 解决：使用 JOIN 或 populate
const users = await User.find().populate('orders');
```

④ **优缺点与边界**：N+1 问题在开发环境中不易察觉，高并发下性能急剧下降。使用 JOIN 虽然增加单次查询复杂度，但避免多次网络往返，总体性能更好。

⑤ **追问预判**：ORM 中如何检测 N+1 问题？Sequelize 和 TypeORM 中如何预防？

### Q64: ORM 和直接写 SQL 的优缺点？

① **一句话结论**：ORM 通过对象映射操作数据库，开发效率高但灵活性差；直接写 SQL 性能可控但开发效率低。

② **原理剖析**：ORM 优点：自动生成参数化 SQL 防注入、数据库迁移方便、代码可读性好、易切换数据库。缺点：复杂查询性能差、学习成本（ORM 特有的 API 和概念）、难以优化执行计划。直接写 SQL 优点：完全掌握执行计划、可针对复杂查询精细优化、无额外抽象层开销。缺点：开发效率低、易出现 SQL 注入（需手动参数化）、代码维护性差。

③ **场景举例**：
```js
// ORM 方式
User.find({ where: { status: 'active' } });
// 直接 SQL
const [rows] = await db.query('SELECT * FROM users WHERE status = ?', ['active']);
```

④ **优缺点与边界**：团队开发建议 ORM + 原生 SQL 混合使用：简单 CRUD 用 ORM，复杂统计和报表用原生 SQL。小项目 ORM 足够，大并发系统需谨慎评估 ORM 性能损耗。

⑤ **追问预判**：TypeORM 和 Sequelize 的对比？如何在 ORM 中执行原生 SQL？

### Q65: 什么是事务的 ACID 特性？

① **一句话结论**：ACID 是事务的四个特性：原子性（Atomicity）、一致性（Consistency）、隔离性（Isolation）、持久性（Durability）。

② **原理剖析**：原子性：事务中的操作要么全部成功，要么全部回滚。一致性：事务前后数据完整性约束不被破坏。隔离性：并发事务之间互不干扰。持久性：事务提交后数据永久保存。InnoDB 通过 undo log 保证原子性，通过 redo log 保证持久性，通过锁和 MVCC 保证隔离性。

③ **场景举例**：
```sql
START TRANSACTION;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT; -- 原子性：两条更新要么都成功，要么都失败
```

④ **优缺点与边界**：ACID 是关系型数据库的核心特性，NoSQL 数据库通常牺牲 ACID 的某些特性换取性能和扩展性。隔离级别越高，并发性能越低。

⑤ **追问预判**：MySQL 如何通过 undo log 和 redo log 实现 ACID？分布式事务如何处理？

### Q66: MySQL 默认事务隔离级别是什么？解决了什么问题？

① **一句话结论**：MySQL InnoDB 默认事务隔离级别是 REPEATABLE READ（可重复读），解决了脏读和不可重复读问题。

② **原理剖析**：脏读指一个事务读到另一个未提交事务的数据；不可重复读指同一事务中两次读取同一数据结果不同。REPEATABLE READ 通过 MVCC（多版本并发控制）保证同一事务中多次读取同一数据结果一致。但无法完全解决幻读问题，InnoDB 通过间隙锁（Gap Lock）在 REPEATABLE READ 级别下部分解决了幻读。

③ **场景举例**：
```sql
SELECT @@transaction_isolation; -- 查看默认隔离级别：REPEATABLE-READ
```

④ **优缺点与边界**：脏读在 READ COMMITTED 及以上级别都不会出现，不可重复读在 REPEATABLE READ 及以上级别被解决。MySQL 的 REPEATABLE READ 通过间隙锁实现了接近 SERIALIZABLE 的幻读保护，但完全避免幻读需 SERIALIZABLE 级别。

⑤ **追问预判**：READ COMMITTED 和 REPEATABLE READ 的区别？MVCC 如何实现快照读？

### Q67: 嵌入（Embedding）和引用（Referencing）的区别？

① **一句话结论**：嵌入将子文档直接存储在父文档中，引用通过 ID 关联其他文档，两种方式在数据一致性、查询性能、文档大小限制上各有优劣。

② **原理剖析**：嵌入适合"包含"关系（如订单包含多个商品），数据一次性读取，无 JOIN 查询，但文档大小有限制（MongoDB 单文档 16MB），数据冗余导致更新不便。引用适合"关联"关系（如用户和文章），数据独立存储，通过引用 ID 关联，减少数据冗余，但需要多次查询或 $lookup 聚合。

③ **场景举例**：
```js
// 嵌入
{ user: 'Alice', orders: [{ product: 'book', price: 29 }] }
// 引用
{ user: 'Alice', orderIds: [ObjectId('...')] }
```

④ **优缺点与边界**：通常建议：一对少关系用嵌入，一对多/多对多关系用引用。数据频繁更新时用引用，读多写少时用嵌入。

⑤ **追问预判**：MongoDB 的 $lookup 和 MySQL 的 JOIN 性能差异？如何根据访问模式选择？

### Q68: MongoDB 和 MySQL 的适用场景对比？

① **一句话结论**：MongoDB 适合灵活 Schema、高并发读写、海量数据的场景；MySQL 适合强事务、复杂关联查询、数据一致性要求高的场景。

② **原理剖析**：MongoDB 优势：无 Schema 约束、横向扩展天然支持（分片）、读写性能高（内存映射）、文档模型接近对象。MySQL 优势：ACID 事务支持完善、JOIN 和复杂查询能力强、生态成熟、社区支持丰富。MongoDB 不适合需要多表关联的复杂业务场景，MySQL 不适合海量日志存储和高并发写入。

③ **场景举例**：
```
MongoDB 适用：日志系统、实时分析、物联网、内容管理
MySQL 适用：金融系统、电商订单、ERP、CRM
```

④ **优缺点与边界**：两者并非互斥，现代架构常采用混合方案：MySQL 存核心业务数据，MongoDB 存日志、评论、社交等非核心数据。

### Q69: MongoDB 的索引如何创建？有哪些类型？

① **一句话结论**：使用 createIndex 方法创建索引，类型包括单字段索引、复合索引、多键索引、文本索引、哈希索引、地理空间索引等。

② **原理剖析**：单字段索引是最基本的索引类型，复合索引支持多字段联合查询。多键索引自动对数组字段创建索引，文本索引支持全文搜索，哈希索引用于分片键，2dsphere 索引支持地理空间查询。创建索引时需指定索引类型和排序方式。

③ **场景举例**：
```js
db.users.createIndex({ name: 1 });           // 单字段升序索引
db.users.createIndex({ name: 1, age: -1 });  // 复合索引
db.articles.createIndex({ content: 'text' });// 文本索引
db.places.createIndex({ location: '2dsphere' }); // 地理空间索引
```

④ **优缺点与边界**：索引创建在后台默认不阻塞读写，但会消耗系统资源。MongoDB 索引使用 B-Tree 结构，与 MySQL 的 B+Tree 略有不同。

### Q70: 什么是 Mongoose 的 populate？如何解决多表关联查询？

① **一句话结论**：populate 是 Mongoose 中实现跨集合关联查询的方法，类似 SQL 的 JOIN，通过引用字段自动填充关联文档。

② **原理剖析**：在 Schema 中定义 ref 字段指向另一个 Model 的 ObjectId，调用 populate('fieldName') 时，Mongoose 自动执行额外查询获取关联文档并替换引用 ID。populate 支持链式调用、字段筛选、条件过滤等。

③ **场景举例**：
```js
const PostSchema = new Schema({
  user: { type: Schema.Types.ObjectId, ref: 'User' }
});
const posts = await Post.find().populate('user', 'name email');
// 输出：posts[0].user 不再是 ObjectId，而是 { _id: ..., name: 'Alice', email: '...' }
```

④ **优缺点与边界**：populate 本质上是多条查询，不会像 SQL JOIN 一样优化为单条查询。在大量关联数据场景下，populate 性能可能不如聚合管道的 $lookup。

⑤ **追问预判**：populate 和 $lookup 的性能对比？如何避免 populate 的 N+1 问题？

### Q71: MongoDB 的聚合管道中 $match、$group、$sort 的作用？

① **一句话结论**：$match 用于过滤文档，$group 用于分组聚合，$sort 用于排序，三者是聚合管道中最常用的阶段。

② **原理剖析**：$match 类似 SQL 的 WHERE，应尽早放在管道前端减少数据量。$group 通过 _id 指定分组字段，使用 $sum、$avg、$max、$min 等累加器进行聚合计算。$sort 按指定字段排序，1 升序 -1 降序，放在 $group 后对聚合结果排序。

③ **场景举例**：
```js
db.orders.aggregate([
  { $match: { status: 'completed' } },         // 过滤已完成订单
  { $group: { _id: '$category', total: { $sum: '$amount' } } }, // 按分类统计总金额
  { $sort: { total: -1 } }                      // 按总金额降序排序
]);
```

④ **优缺点与边界**：管道阶段顺序影响性能：$match 和 $sort 尽早使用可利用索引，$group 和 $project 会消耗更多内存。MongoDB 聚合管道内存限制为 100MB，大数据量需启用 allowDiskUse。

### Q72: &#64;Injectable() 和 &#64;Controller() 的区别？

① **一句话结论**：&#64;Injectable() 标记一个类为可被依赖注入的 Provider（服务/仓库等），&#64;Controller() 标记一个类为控制器，处理 HTTP 请求路由。

② **原理剖析**：&#64;Controller() 是 &#64;Injectable() 的子集扩展，被 &#64;Controller() 装饰的类同时具备依赖注入能力和路由处理能力。&#64;Injectable() 装饰的类可以注入到其他 Provider 或 Controller 中，但不处理路由。NestJS 在扫描模块时，&#64;Controller() 类会被注册到路由系统，&#64;Injectable() 类被注册到 DI 容器。

③ **场景举例**：
```ts
@Injectable()
export class UserService { /* 业务逻辑，可注入 */ }

@Controller('users')
export class UserController {
  constructor(private userService: UserService) {} // 注入 Service
  @Get() findAll() { return this.userService.findAll(); }
}
```

④ **优缺点与边界**：&#64;Controller() 本质上是经过特殊处理的 &#64;Injectable()，两者在使用场景上完全分离。Service 和 Repository 用 &#64;Injectable()，路由入口用 &#64;Controller()。

### Q73: 动态模块的 forRoot 和 forRootAsync 的区别？

① **一句话结论**：forRoot 同步配置动态模块，forRootAsync 异步配置动态模块，常用于需要在模块初始化时传递配置的场景。

② **原理剖析**：forRoot 接收静态配置对象，在模块导入时同步注册 Provider。forRootAsync 接收一个工厂函数或 useFactory 配置，支持异步获取配置（如从数据库读取配置、从远程配置中心拉取），并通过 imports 导入依赖模块。

```ts
// 静态配置
TypeOrmModule.forRoot({ type: 'mysql', host: 'localhost', ... });

TypeOrmModule.forRootAsync({
  imports: [ConfigModule],

    type: 'mysql',
    host: config.get('DB_HOST'),
  }),
  inject: [ConfigService],
});
```

④ **优缺点与边界**：forRoot 简单直接，适合配置固定或从环境变量读取的场景。forRootAsync 适合需要异步获取配置的场景，但增加了代码复杂度。

### Q74: NestJS 的请求处理链包含哪些组件？

① **一句话结论**：NestJS 请求处理链依次包含：Middleware → Guard → Interceptor（前）→ Pipe → Controller → Interceptor（后）→ Exception Filter。

② **原理剖析**：请求先经过全局/模块级的 Middleware（中间件），然后进入 Guard 进行权限验证，通过后进入 Interceptor 的前置处理，接着 Pipe 对参数进行验证和转换，然后到达 Controller 处理方法，返回结果后经过 Interceptor 的后置处理，最后 Exception Filter 捕获异常并格式化响应。

③ **场景举例**：
```
请求 → Middleware → Guard → Interceptor(before) → Pipe → Controller → Interceptor(after) → 响应
                                                                    ↓ 异常
                                                           Exception Filter
```

④ **优缺点与边界**：理解请求处理链对调试和性能优化至关重要。每个组件职责单一，按需组合使用。Interceptor 可以同时处理请求前和响应后的逻辑。

⑤ **追问预判**：为什么 Guard 在 Pipe 之前执行？Interceptor 和 Middleware 的适用场景区别？

### Q75: Middleware、Guard、Interceptor、Pipe 的执行顺序？

① **一句话结论**：执行顺序：Middleware → Guard → Interceptor（before）→ Pipe → Controller → Interceptor（after）→ Exception Filter。

② **原理剖析**：Middleware 在路由匹配前执行，是 Express 原生概念。Guard 在 Middleware 之后、Interceptor 之前执行，决定请求是否继续。Interceptor 包裹整个请求处理过程，可在方法执行前后追加逻辑。Pipe 在 Controller 方法执行前对参数进行转换和验证。Exception Filter 在最后捕获异常。

③ **场景举例**：
```ts
@UseGuards(AuthGuard)
@UseInterceptors(LoggingInterceptor)
@UsePipes(ValidationPipe)
@Get()
findAll() { return 'ok'; }
```

④ **优缺点与边界**：顺序不可改变，NestJS 在底层通过 Reflector 元数据按固定顺序组合这些组件。理解顺序有助于精确定位问题所在。

### Q76: 自定义 Provider 的 useClass、useValue、useFactory 的区别？

① **一句话结论**：useClass 提供一个类作为 Provider，useValue 提供一个具体值，useFactory 通过工厂函数动态创建 Provider。

② **原理剖析**：useClass 是最常用的方式，等价于标准 Provider 声明，NestJS 会自动实例化该类。useValue 用于提供常量、配置对象或 Mock 对象（测试场景）。useFactory 接收一个函数，可以注入其他 Provider 的实例，支持异步创建，适合需要复杂初始化逻辑的场景。

④ **优缺点与边界**：useValue 值不可变，useFactory 支持灵活初始化。三个模式都支持自定义 token（字符串或 Symbol），便于实现策略模式。

### Q77: 什么是全局模块？&#64;Global() 的作用？

① **一句话结论**：全局模块通过 &#64;Global() 装饰器标记，使该模块导出的 Provider 在整个应用中无需导入即可使用。

② **原理剖析**：默认情况下，NestJS 模块是隔离的，模块 A 要使用模块 B 的 Provider，必须将模块 B 导入模块 A 的 imports 中。&#64;Global() 装饰器将模块标记为全局，其 exports 中的 Provider 会被注册到全局 DI 容器，任何模块都可以直接注入使用。

### Q78: ValidationPipe 的 whitelist 和 forbidNonWhitelisted 的区别？

① **一句话结论**：whitelist 自动剔除 DTO 中未定义装饰器的属性，forbidNonWhitelisted 在检测到未定义属性时抛出异常。

② **原理剖析**：whitelist: true 时，ValidationPipe 会自动删除请求体中未在 DTO 类中通过装饰器定义的属性。forbidNonWhitelisted: true 时，不仅会删除，还会直接抛出 BadRequestException 拒绝请求，明确告知客户端传入了非法字段。两者常配合使用，先 whitelist 清理，再 forbidNonWhitelisted 严格校验。

③ **场景举例**：

```ts
// DTO
class CreateUserDto {

}
// whitelist: true → 自动删除多余字段
// forbidNonWhitelisted: true → 有多余字段直接报错
```

④ **优缺点与边界**：whitelist 适用于需要容错的场景（如前端传了额外字段），forbidNonWhitelisted 适用于严格安全的场景。两者常同时设为 true 实现严格校验。

### Q79: 拦截器和过滤器的区别？

① **一句话结论**：拦截器（Interceptor）在请求处理前后执行，可转换响应或扩展请求；过滤器（Exception Filter）专门处理异常，统一格式化错误响应。

② **原理剖析**：拦截器基于 NestJS 的拦截器接口，实现 intercept() 方法，通过调用 next.handle() 获取 Observable 流，可修改请求、响应、甚至完全替换响应。过滤器基于 ExceptionFilter 接口，实现 catch() 方法，捕获异常并返回自定义响应格式。拦截器适合：日志、缓存、响应映射；过滤器适合：统一错误格式、异常日志记录。

③ **场景举例**：
```ts
// 拦截器：转换响应
@Injectable()
export class TransformInterceptor implements NestInterceptor {
  intercept(context, next) {
    return next.handle().pipe(map(data => ({ code: 0, data })));
  }
}
// 过滤器：格式化异常
@Catch()
```

### Q82: SetMetadata 和 Reflector 如何配合实现权限控制？

### Q83: NestJS Provider 默认作用域是什么？REQUEST 作用域有什么影响？

① **一句话结论**：NestJS Provider 默认是单例作用域（SINGLETON），REQUEST 作用域为每个请求创建新实例，会带来性能和内存开销。

② **原理剖析**：默认 SINGLETON 作用域下，Provider 在应用启动时创建一次，所有请求共享同一个实例，性能最佳。REQUEST 作用域下，每个 HTTP 请求都会创建新的 Provider 实例，请求结束后实例被垃圾回收。DEFAULT 作用域也是单例。使用 REQUEST 作用域需要注入 REQUEST 对象，但会导致依赖链上的所有 Provider 都变为 REQUEST 作用域。

③ **场景举例**：
```ts
@Injectable({ scope: Scope.REQUEST })
export class RequestService {
  constructor(@Inject(REQUEST) private request: Request) {} // 可获取当前请求对象
}
```

④ **优缺点与边界**：REQUEST 作用域影响性能，每次请求创建新实例，不能缓存。应仅在确实需要请求级隔离时使用（如多租户场景），默认优选 SINGLETON。

### Q84: 循环依赖是什么？如何解决？

① **一句话结论**：循环依赖指两个或多个模块/Provider 相互依赖，导致依赖注入无法正常创建实例。可通过 forwardRef 和 forwardRef() 函数解决。

② **原理剖析**：在 NestJS 中，模块之间的循环依赖使用 forwardRef(() => ModuleB) 延迟求值。Provider 之间的循环依赖使用 &#64;Inject(forwardRef(() => ServiceB)) 延迟注入。forwardRef 创建一个延迟引用，等到实例化时再解析真正的依赖。

```ts
export class ServiceA {
  constructor(@Inject(forwardRef(() => ServiceB)) private serviceB: ServiceB) {}
}
```

④ **优缺点与边界**：循环依赖通常是设计问题的信号，应优先考虑重构代码结构（如提取公共模块）。forwardRef 只是临时解决方案，长期应消除循环依赖。

### Q85: JWT 的结构是什么？各部分的作用？

① **一句话结论**：JWT 由三部分组成：Header（头部）、Payload（载荷）、Signature（签名），格式为 header.payload.signature。

② **原理剖析**：Header 包含令牌类型（typ: 'JWT'）和签名算法（如 HS256、RS256）。Payload 包含标准声明（iss、sub、exp、iat 等）和自定义声明（如 userId、role）。Signature 是对 Header 和 Payload 的签名，使用 Header 中指定的算法和密钥生成，用于验证令牌未被篡改。三部分均经过 Base64URL 编码。

③ **场景举例**：
```
Header:  {"alg": "HS256", "typ": "JWT"}
Payload: {"sub": "123", "name": "Alice", "iat": 1516239022, "exp": 1516242622}
Signature: HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)
```

④ **优缺点与边界**：JWT 是无状态认证的核心，服务端无需存储会话信息。但 Payload 仅 Base64 编码未加密，不应存放敏感信息。Signature 仅防篡改，不加密数据。

⑤ **追问预判**：JWT 的 HS256 和 RS256 的区别？如何实现 JWT 的刷新和注销？

### Q86: 为什么要使用 Refresh Token？Access Token 为什么不设长过期时间？

① **一句话结论**：Access Token 设置短过期时间（如 15 分钟）降低泄露风险，Refresh Token 用于无感刷新令牌，提升用户体验。

② **原理剖析**：Access Token 在客户端（浏览器、App）中频繁传输，泄露风险高。短过期时间可限制泄露后的影响范围。Refresh Token 过期时间长（如 7 天），仅用于获取新的 Access Token，不用于业务请求，传输频率低，安全性更高。双 Token 机制在保障安全的同时，避免用户频繁登录。

③ **场景举例**：
```
登录 → 获取 Access Token(15min) + Refresh Token(7d)
Access Token 过期 → 使用 Refresh Token 请求新 Access Token → 继续业务
Refresh Token 过期 → 用户重新登录
```

④ **优缺点与边界**：双 Token 机制增加了实现复杂度（需存储 Refresh Token、处理并发刷新），但大幅提升了安全性和用户体验。Refresh Token 应在服务端存储并可撤销。

### Q90: 缓存穿透、缓存击穿、缓存雪崩的区别和解决方案？

① **一句话结论**：缓存穿透：查询不存在的数据，绕过缓存直击数据库。缓存击穿：热点 Key 过期，大量请求同时访问数据库。缓存雪崩：大量 Key 同时过期或 Redis 宕机，数据库被打垮。

② **原理剖析**：缓存穿透的解决方案：缓存空值（短过期）、布隆过滤器。缓存击穿的解决方案：互斥锁（只允许一个线程重建缓存）、热点 Key 永不过期（异步更新）。缓存雪崩的解决方案：过期时间加随机值、多级缓存、Redis 高可用集群。

③ **场景举例**：
```
穿透：查 id=-1 → 缓存无 → 数据库无 → 布隆过滤器拦截
击穿：热点商品 Key 过期 → 加锁重建缓存 → 其他请求等待
雪崩：Key 过期时间 + 随机值 → 避免同时过期
```

④ **优缺点与边界**：三种故障的后果都是数据库压力激增，但根本原因不同。穿透是无中生有，击穿是热点失效，雪崩是批量失效。实际中需组合多种方案。

⑤ **追问预判**：布隆过滤器的原理和误判率？如何实现热点 Key 的自动发现？

### Q91: Redis 的 String 和 Hash 分别适合什么场景？

① **一句话结论**：String 适合简单键值对、计数器、缓存；Hash 适合存储对象结构，如用户信息、商品详情。

② **原理剖析**：String 是 Redis 最基础的类型，值最大 512MB，支持 INCR/DECR 原子操作，适合缓存 JSON 字符串、计数器、分布式锁。Hash 是键值对集合，可独立操作单个字段，适合存储对象（如用户信息），修改一个字段无需读取整个对象，节省内存和带宽。

③ **场景举例**：
```bash
# String 场景：计数器
SET article:1001:views 0
INCR article:1001:views
# Hash 场景：用户信息
HSET user:1001 name "Alice" age 25 email "alice@example.com"
HGET user:1001 name
```

④ **优缺点与边界**：String 操作简单，但整体读写对象时需序列化/反序列化。Hash 可部分更新，但字段较多时内存开销较大。对象存储推荐 Hash，简单值推荐 String。

### Q92: Redis 的过期策略有哪些？

① **一句话结论**：Redis 的过期策略是定期删除 + 惰性删除的混合策略，同时使用内存淘汰机制作为兜底。

② **原理剖析**：定期删除：Redis 每隔 100ms 随机抽取一部分设置了过期时间的 Key 进行检查，删除已过期的 Key。惰性删除：当访问一个 Key 时，检查其是否过期，过期则删除。定期删除避免全量扫描性能问题，惰性删除兜底未被定期删除扫描到的过期 Key。当内存不足时，触发内存淘汰策略（如 LRU、LFU、TTL 等）。

③ **场景举例**：
```
定期删除（主动）：每 100ms 随机抽查，过期则删
惰性删除（被动）：访问时检查，过期则删
内存淘汰（兜底）：内存满时按策略淘汰
```

④ **优缺点与边界**：定期删除可能导致过期 Key 未被及时清理，占用内存。惰性删除确保过期 Key 在访问时被清理。混合策略在性能和内存占用间取得平衡。

⑤ **追问预判**：Redis 的 8 种内存淘汰策略？如何选择合适的淘汰策略？

### Q93: 如何保证缓存与数据库的数据一致性？

① **一句话结论**：缓存与数据库一致性的核心策略是 Cache Aside Pattern（旁路缓存），优先更新数据库再删除缓存。

② **原理剖析**：Cache Aside Pattern：读时先查缓存，缓存不命中查数据库并回写缓存；写时先更新数据库，再删除缓存（而非更新缓存）。延迟双删策略：先删除缓存，再更新数据库，延迟一小段时间后再次删除缓存，解决并发读写导致的脏数据。强一致性场景需使用分布式锁或同步双写。

③ **场景举例**：
```js
// 更新操作
async function updateData(id, newData) {
  await db.update(id, newData);       // 1. 更新数据库
  await cache.del(`key:${id}`);       // 2. 删除缓存（不是更新）
}
// 读操作
async function getData(id) {
  let data = await cache.get(`key:${id}`);
  if (!data) {
    data = await db.find(id);         // 缓存未命中，查数据库
    await cache.set(`key:${id}`, data);
  }
  return data;
}
```

④ **优缺点与边界**：先删缓存再更新数据库存在并发问题，优先选择先更新数据库再删缓存。缓存和数据库最终一致性是工程实践的主流选择，强一致性需牺牲性能。

⑤ **追问预判**：什么是延迟双删？如何实现缓存和数据库的最终一致性？

### Q95: 为什么生产环境不用 console.log？

① **一句话结论**：console.log 是同步操作（在特定条件下），会阻塞事件循环，且缺少日志级别、格式化、持久化等能力，不适用于生产环境。

② **原理剖析**：console.log 在 Node.js 中写入 stdout，默认情况下是同步的（当输出目标是终端或文件时），会在输出完成前阻塞事件循环，影响性能。生产环境需要日志分级（info/warn/error）、日志轮转、写入文件、集中式日志收集等能力，console.log 无法满足。应使用 Winston、Pino 等专业日志库。

③ **场景举例**：
```js
// 不推荐
console.log('User login:', userId);
// 推荐
logger.info('User login', { userId });
```

④ **优缺点与边界**：在性能敏感的场景下，console.log 的阻塞可能导致吞吐量下降。Winston、Pino 等日志库支持异步日志、日志分级、多传输目标等，是生产环境的标准选择。

⑤ **追问预判**：Pino 和 Winston 的对比？如何实现日志的集中式收集？

### Q96: .env 文件的作用？如何在不同环境管理配置？

① **一句话结论**：.env 文件用于存储环境变量，将配置与代码分离，不同环境通过不同的 .env 文件管理配置。

② **原理剖析**：.env 文件遵循 KEY=VALUE 格式，通过 dotenv 库加载到 process.env 中。不同环境使用不同文件：.env.development（开发）、.env.production（生产）、.env.test（测试）。加载优先级：实际环境变量 > .env.local > .env.[environment] > .env。.env 文件不应提交到 Git（在 .gitignore 中排除），而应提供 .env.example 作为模板。

③ **场景举例**：
```
# .env.development
DB_HOST=localhost
DB_PORT=3306
# .env.production
DB_HOST=prod-db.example.com
DB_PORT=3306
```

④ **优缺点与边界**：12-Factor App 原则建议将配置存储在环境变量中。NestJS 的 ConfigModule 内置了 .env 文件加载和验证功能。敏感信息（密钥、密码）应使用密钥管理服务，而非仅依赖 .env 文件。

### Q97: 什么是日志分级？Winston 的日志级别有哪些？

① **一句话结论**：日志分级是按严重程度将日志分为不同级别，便于过滤和定位问题。Winston 的日志级别从低到高：silly、debug、verbose、info、warn、error。

② **原理剖析**：日志分级允许在不同环境下输出不同级别的日志：开发环境输出 debug 级别，生产环境只输出 warn 及以上级别，减少磁盘 I/O 和日志噪音。Winston 默认级别对应数字优先级，error 最高（0），silly 最低（6）。可通过 npm 日志级别或自定义级别。

③ **场景举例**：
```js
const logger = winston.createLogger({
  level: process.env.NODE_ENV === 'production' ? 'warn' : 'debug',
  transports: [new winston.transports.File({ filename: 'combined.log' })],
});
logger.info('服务启动');     // 生产环境不输出
logger.error('数据库连接失败'); // 所有环境都输出
```

④ **优缺点与边界**：合理的日志分级是运维的基础。除 Winston 外，Pino 和 Bunyan 也是常用的日志库。日志分级应配合日志轮转和集中式收集使用。

### Q98: Docker 多阶段构建的作用？

① **一句话结论**：多阶段构建通过在一个 Dockerfile 中使用多个 FROM 语句，将构建环境和运行环境分离，大幅减小最终镜像体积。

② **原理剖析**：第一阶段（构建阶段）使用包含编译工具链的基础镜像（如 node:18），安装依赖、编译代码、运行测试。第二阶段（运行阶段）使用精简基础镜像（如 node:18-alpine），只复制构建产物和运行时依赖。多阶段构建确保最终镜像不包含源代码、编译工具、缓存等无关文件。

③ **场景举例**：
```dockerfile
# 构建阶段
FROM node:18 AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci --only=production
COPY . .
RUN npm run build

# 运行阶段
FROM node:18-alpine
WORKDIR /app
COPY --from=builder /app/dist ./dist
COPY --from=builder /app/node_modules ./node_modules
EXPOSE 3000
CMD ["node", "dist/main.js"]
```

④ **优缺点与边界**：多阶段构建可将镜像从 1GB+ 缩小到 100-200MB，减少部署时间和带宽消耗。同时降低了攻击面（无构建工具）。适合所有需要编译的 Node.js 项目。

⑤ **追问预判**：多阶段构建中如何缓存 npm 依赖层？Alpine 镜像和标准镜像的兼容性问题？

## 第九阶段：进阶主题 - 安全

### Q99: 什么是 SQL 注入？如何预防？

① **一句话结论**：SQL 注入是攻击者通过构造恶意输入，在 SQL 语句中插入非法 SQL 代码，窃取或破坏数据的攻击方式。预防核心是使用参数化查询。

② **原理剖析**：当用户输入直接拼接到 SQL 语句中时，攻击者可输入 `' OR '1'='1` 等 payload 改变 SQL 语义，如 `SELECT * FROM users WHERE name = 'admin' OR '1'='1'`，导致返回所有用户数据。预防方法：使用参数化查询（Prepared Statement）、ORM 内置的参数绑定、对输入进行严格校验和转义。

③ **场景举例**：
```js
// 不安全的写法（拼接 SQL）
const sql = `SELECT * FROM users WHERE name = '${req.body.name}'`; // SQL 注入！
// 安全的写法（参数化查询）
const sql = 'SELECT * FROM users WHERE name = ?';
db.query(sql, [req.body.name]); // 参数化，自动转义
```

④ **优缺点与边界**：参数化查询是预防 SQL 注入的最有效手段，ORM 默认使用参数化查询。此外应遵循最小权限原则（数据库账号只授予必要权限）、对敏感输入进行白名单校验。

⑤ **追问预判**：LIKE 模糊查询如何防止 SQL 注入？MyBatis 的 #{} 和 ${} 的区别？

### Q100: CORS 是什么？如何配置？

① **一句话结论**：CORS（跨域资源共享）是一种浏览器安全机制，允许服务器声明哪些跨域请求可以被接受。通过设置响应头来配置。

② **原理剖析**：浏览器同源策略默认阻止跨域请求。CORS 通过服务端设置 Access-Control-Allow-Origin 等响应头，告知浏览器允许指定来源的跨域请求。预检请求（OPTIONS）用于复杂请求（如 PUT、DELETE、自定义头）的权限确认。Express 中使用 cors 中间件，NestJS 中使用 app.enableCors() 配置。

③ **场景举例**：
```ts
// Express
const cors = require('cors');
app.use(cors({ origin: 'https://example.com', credentials: true }));
// NestJS
app.enableCors({ origin: ['https://example.com'], credentials: true });
```

④ **优缺点与边界**：CORS 是浏览器端的限制，不适用于服务器之间的请求。生产环境应将 origin 设置为具体域名而非 *，并开启 credentials 时不能用 * 通配符。

⑤ **追问预判**：简单请求和复杂请求的区别？如何配置多个允许的域名？

### Q101: XSS 攻击是什么？如何预防？

① **一句话结论**：XSS（跨站脚本攻击）是攻击者将恶意脚本注入到页面中，当其他用户访问时执行，窃取用户信息或篡改页面。预防核心是输出编码和内容安全策略。

② **原理剖析**：XSS 分为三类：反射型（恶意脚本在 URL 中，服务端未编码直接返回）、存储型（恶意脚本存入数据库，所有访问用户受影响）、DOM 型（客户端脚本动态修改 DOM 时执行恶意代码）。预防方法：对用户输入进行 HTML 实体编码（如 < 转义为 &lt;）、设置 Content-Security-Policy 头、使用 HttpOnly Cookie 防止脚本读取 Cookie。

③ **场景举例**：
```js
// 不安全：直接拼接用户输入
res.send(`<div>${userInput}</div>`); // XSS！
// 安全：转义后输出
const escapeHtml = (str) => str.replace(/</g, '&lt;').replace(/>/g, '&gt;');
res.send(`<div>${escapeHtml(userInput)}</div>`);
// 或使用模板引擎自动转义
```

④ **优缺点与边界**：XSS 的根源是未对输出进行编码。现代前端框架（React、Vue）默认对插值进行转义，但 dangerouslySetInnerHTML 和 v-html 需谨慎使用。后端对用户输入做输入校验，前端做输出编码，双重保险。

⑤ **追问预判**：CSP（Content Security Policy）如何配置？HttpOnly 和 Secure Cookie 能防御哪些攻击？

## 第九阶段：进阶主题 - 测试

### Q102: 单元测试和集成测试的区别？

① **一句话结论**：单元测试测试最小单元（函数/方法），隔离外部依赖；集成测试测试多个模块的协作，验证整体功能。

② **原理剖析**：单元测试关注单一模块的内部逻辑，不依赖数据库、文件系统、网络等外部资源，使用 Mock 隔离依赖。执行速度快，可频繁运行。集成测试验证模块间的交互是否正常，如 Controller + Service + Database 的完整链路，需要真实的或内存数据库。单元测试是白盒测试，集成测试偏灰盒测试。

③ **场景举例**：
```ts
// 单元测试：只测试 Service 逻辑
describe('UserService', () => {
  it('should create user', async () => {
    const user = await userService.create({ name: 'Alice' });
    expect(user.name).toBe('Alice');
  });
});
// 集成测试：测试完整链路
describe('POST /users', () => {
  it('should create user via API', async () => {
    const res = await request(app).post('/users').send({ name: 'Alice' });
    expect(res.status).toBe(201);
  });
});
```

④ **优缺点与边界**：测试金字塔建议：底层单元测试占比大（70%），集成测试次之（20%），E2E 测试最少（10%）。单元测试发现问题早、定位精确；集成测试更能发现接口交互问题。

⑤ **追问预判**：如何确定单元测试的覆盖范围？测试替身（Test Double）的几种类型？

### Q103: Mock 和 Stub 的区别？

① **一句话结论**：Mock 用于验证行为（是否被调用、调用次数、参数），Stub 用于提供预设返回值，隔离被测代码的外部依赖。

② **原理剖析**：Stub（桩）替换外部依赖，返回预设数据，使被测代码可以独立运行。关注的是"状态"——返回值是否正确。Mock（模拟对象）不仅替换依赖，还验证交互行为——方法是否被调用、调用次数、传入参数。测试框架（如 Jest）中，jest.fn() 可同时作为 Mock 和 Stub 使用。

③ **场景举例**：
```ts
// Stub：提供返回值
const userService = { findById: jest.fn().mockReturnValue({ id: 1, name: 'Alice' }) };
// Mock：验证行为
const callback = jest.fn();
someFunction(callback);
expect(callback).toHaveBeenCalledWith('success');
```

④ **优缺点与边界**：简单场景用 Stub 即可，只在需要验证交互行为时使用 Mock。过度使用 Mock 会导致测试脆弱（实现细节变化导致测试失败）。

⑤ **追问预判**：Jest 中 jest.spyOn 和 jest.fn 的区别？什么是 Partial Mock？

### Q104: Jest 中 describe、it、expect 的作用？

① **一句话结论**：describe 定义测试套件，it 定义单个测试用例，expect 创建断言来验证实际结果是否符合预期。

② **原理剖析**：describe(name, fn) 用于组织相关的测试用例，可嵌套使用，形成测试分组。it(name, fn) 或 test(name, fn) 定义一个测试用例，包含测试逻辑和断言。expect(value) 返回一个断言对象，配合匹配器（Matcher）如 toBe、toEqual、toContain、toThrow 等进行值比较。

③ **场景举例**：
```ts
describe('UserService', () => {        // 测试套件
  describe('create', () => {           // 嵌套分组
    it('should create a new user', () => { // 测试用例
      const result = createUser('Alice');
      expect(result).toHaveProperty('id');    // 断言
      expect(result.name).toBe('Alice');
    });
    it('should throw if name is empty', () => {
      expect(() => createUser('')).toThrow('Name required');
    });
  });
});
```

④ **优缺点与边界**：describe 可以嵌套，但过深嵌套降低可读性。it 支持异步测试（传入 async 函数或 done 回调）。expect 的 .not 修饰符取反断言。

⑤ **追问预判**：Jest 的钩子函数（beforeAll、beforeEach、afterAll、afterEach）的执行顺序？如何自定义匹配器？

## 第八阶段：脚手架开发

### Q105: 什么是脚手架？脚手架的核心流程是什么？

① **一句话结论**：脚手架是自动化创建项目初始结构的工具，核心流程是：输入配置 → 下载模板 → 渲染文件 → 安装依赖。

② **原理剖析**：脚手架将项目创建过程自动化，避免手动创建目录、配置文件、安装依赖等重复劳动。核心流程：用户交互（通过 CLI 询问项目名称、选择模板等）→ 获取模板（从本地或远程仓库下载）→ 模板渲染（使用 Handlebars、EJS 等模板引擎替换变量）→ 文件生成（写入目标目录）→ 依赖安装（自动执行 npm install）→ 完成提示。

③ **场景举例**：
```
用户输入项目名 → CLI 交互选择模板 → 下载模板文件
→ 模板引擎渲染（替换变量）→ 写入目标目录 → npm install → 完成提示
```

④ **优缺点与边界**：脚手架大幅提升团队开发效率，统一项目规范。常见脚手架工具包括 Yeoman、Plop、以及自定义的 CLI 工具（如 create-react-app、&#64;nestjs/cli）。

⑤ **追问预判**：如何设计一个企业级脚手架？模板引擎在脚手架中的应用（Handlebars vs EJS）？
