## 一、五步答题法

### 什么是五步答题法？

① **一句话结论** → 用最简练的语言给出核心答案，让面试官第一时间抓住要点。

② **原理剖析** → 深入底层原理，展现知识深度，不仅仅是"怎么用"，更要讲"为什么"。

③ **场景举例** → 结合真实项目场景，说明在什么情况下会用到、怎么用，体现实战能力。

④ **优缺点与边界** → 除了讲优点，也要主动指出局限性和适用边界，展现辩证思维。

⑤ **追问预判** → 预先思考面试官可能顺着往下问什么，主动铺垫，掌控节奏。

---

### 示例：什么是 JWT？

**① 一句话结论**：JWT（JSON Web Token）是一种自包含的、基于 JSON 的令牌格式，用于在客户端和服务端之间安全传输声明信息，常用于身份认证。

**② 原理剖析**：JWT 由三部分组成——Header（头部）、Payload（载荷）、Signature（签名），以 `.` 分隔。Header 指定算法和令牌类型，Payload 存放用户身份等声明信息，Signature 是对前两部分用密钥进行签名，防止篡改。服务端不存储会话信息，令牌自包含用户身份，是一种无状态认证方案。

**③ 场景举例**：在 NestJS 项目中，用户登录后服务端签发 JWT，客户端后续请求在 Authorization 头携带 `Bearer <token>`，服务端通过 `@nestjs/jwt` 的 `JwtModule` 验证签名后解析出用户信息，挂载到 `request.user` 上供后续 Guards 和 Interceptors 使用。

**④ 优缺点与边界**：
- 优点：无状态、跨域友好、适合分布式系统，无需集中存储会话。
- 缺点：一旦签发无法主动撤销（除非维护黑名单，但会破坏无状态性）；Payload 仅仅 Base64 编码，敏感信息不应放入；令牌体积较大，每次请求都携带，增加带宽开销。

**⑤ 追问预判**：面试官可能会追问——"Refresh Token 怎么实现？"、"JWT 和 Session 的区别是什么？"、"如何应对 JWT 泄露？"、"无状态认证的优缺点在什么场景下会被放大？"

### 示例：什么是事件循环？

**① 一句话结论**：事件循环是 Node.js 实现异步非阻塞 I/O 的核心机制，它允许 Node.js 在单线程下高效处理并发请求。

**② 原理剖析**：Node.js 启动后，主线程执行同步代码，遇到异步任务（如 `setTimeout`、`fs.readFile`、`Promise`）将其交给 libuv 的线程池或系统内核处理，回调函数被注册到对应的队列中。事件循环按阶段（timers → pending callbacks → idle/prepare → poll → check → close callbacks）不断轮询，依次执行各阶段队列中的回调。微任务（`process.nextTick` 和 `Promise.then`）在每个阶段切换时被清空，其中 `process.nextTick` 优先级高于 Promise。

**③ 场景举例**：在一个 NestJS 应用中，当请求处理涉及多个异步操作时，例如先查数据库再调用外部 API 最后写缓存，事件循环确保这些操作不会阻塞后续请求。即使 QPS 很高，单线程也能通过事件循环并发处理成千上万个连接（前提是每个回调不长时间占用 CPU）。

**④ 优缺点与边界**：
- 优点：高并发下内存开销低，没有多线程切换成本，适合 I/O 密集型场景。
- 缺点：CPU 密集型任务会阻塞事件循环，导致吞吐量骤降（此时需要用 Worker Threads 或子进程分离）。
- 边界：微任务队列可能无限递归导致事件循环"饿死"；`process.nextTick` 过度使用同样会阻塞后续阶段。

**⑤ 追问预判**：面试官可能会追问——"宏任务和微任务的执行顺序具体是怎样的？"、"`process.nextTick` 和 `Promise.then` 谁先执行？"、"事件循环的六个阶段分别做什么？"、"Node.js 和浏览器的事件循环有什么区别？"

## 二、追问链

### 追问链 1：事件循环

```
Q: 什么是宏任务和微任务？
  └── Q: 微任务在事件循环的哪个阶段执行？
        └── Q: process.nextTick 和 Promise.then 哪个先执行？
              └── Q: 事件循环的六个阶段分别是什么？
                    └── Q: poll 阶段具体做了什么？
                          └── Q: 如果 poll 阶段有定时器到期了怎么办？
                                └── Q: 写一段代码，预测 setTimeout(fn, 0) 和 Promise.resolve().then() 的输出顺序？
```

**关键知识点**：
- 宏任务：`setTimeout`、`setInterval`、`setImmediate`、I/O 回调
- 微任务：`process.nextTick`（优先级最高）、`Promise.then`/`catch`/`finally`
- 阶段切换时清空微任务队列，`process.nextTick` 队列优先于 Promise 队列
- 六个阶段：timers → pending callbacks → idle/prepare → poll → check → close callbacks

---

### 追问链 2：NestJS 请求处理链

```
Q: NestJS 的请求处理链有哪些组件？
  └── Q: Guards、Interceptors、Pipes、Filters 的执行顺序是怎样的？
        └── Q: Guard 的 canActivate 返回 false 会怎样？
              └── Q: Interceptor 和 Middleware 有什么区别？
                    └── Q: Pipe 的 transform 方法返回值会替换原始参数吗？
                          └── Q: ExceptionFilter 捕获到异常后怎么返回自定义响应？
                                └── Q: 如果我想在 Guard 中获取请求体数据，但 Guard 执行时请求体还没解析怎么办？
```

**关键知识点**：
- 执行顺序：Middleware → Guard → Interceptor（前置） → Pipe →  Controller Handler → Interceptor（后置） → ExceptionFilter（异常时）
- Guard 返回 `false` 抛出 `ForbiddenException`，不会继续执行后续组件
- Pipe 返回的值会替换原始参数传递给 Handler
- 自定义 ExceptionFilter 需实现 `ExceptionFilter` 接口，通过 `@Catch()` 指定捕获类型
- Guard 在请求体解析之前执行，无法直接获取 body；若需要，可将校验逻辑放在 Pipe 中

### 追问链 3：JWT 认证

```
Q: JWT 的结构是什么？
  └── Q: JWT 的 Signature 是怎么生成的？
        └── Q: 服务端怎么验证 JWT 是否有效？
              └── Q: JWT 泄露了怎么办？
                    └── Q: Refresh Token 机制是怎么实现的？
                          └── Q: Refresh Token 需要存数据库吗？
                                └── Q: 无状态认证和 Session 认证各自的优缺点是什么？
                                      └── Q: 在 NestJS 中如何实现 JWT 认证？
```

**关键知识点**：
- JWT 结构：Header（alg + typ）`.` Payload（claims）`.` Signature
- Signature = HMACSHA256(base64UrlEncode(header) + "." + base64UrlEncode(payload), secret)
- 验证：服务端用相同密钥重新计算签名，比对是否一致；同时校验 `exp`、`nbf`、`iss` 等声明
- 泄露应对：缩短 Access Token 有效期（如 15 分钟），配合 Refresh Token（有效期 7 天），Refresh Token 需存数据库支持撤销
- 无状态适合微服务，但无法主动踢人；Session 适合单体，可服务端注销，但需要共享存储

### 追问链 4：数据库索引

```
Q: 什么是索引？为什么用索引？
  └── Q: MySQL 的索引底层数据结构是什么？
        └── Q: 为什么是 B+Tree 而不是 B-Tree 或者红黑树？
              └── Q: 什么是联合索引？最左前缀原则是什么？
                    └── Q: 什么情况下索引会失效？
                          └── Q: 索引下推（Index Condition Pushdown）是什么？
                                └── Q: 如何通过 EXPLAIN 分析 SQL 性能？
                                      └── Q: 在 NestJS 中如何用 TypeORM 配合数据库索引？
```

**关键知识点**：
- B+Tree：所有数据存储在叶子节点，非叶子节点只存键值，叶子节点形成有序链表，范围查询高效
- 相比 B-Tree：B+Tree 非叶子节点不存数据，扇出更大，树高更低；叶子节点链表支持高效范围扫描
- 最左前缀：联合索引 `(a, b, c)` 可匹配 `(a)`、`(a, b)`、`(a, b, c)`，但跳过的列会导致后续列失效
- 索引失效场景：OR 条件、隐式类型转换、`LIKE '%xxx'`、函数包裹、`!=` / `<>`、联合索引未满足最左前缀
- NestJS + TypeORM 中用 `@Index()` 装饰器或 `@Entity` 的 `indices` 选项定义索引

### 追问链 5：缓存

```
Q: 什么是缓存穿透？怎么解决？
  └── Q: 布隆过滤器的工作原理是什么？
        └── Q: 缓存击穿和缓存雪崩的区别是什么？
              └── Q: 缓存和数据库的一致性怎么保证？
                    └── Q: 先更新数据库还是先删除缓存？
                          └── Q: 延迟双删策略是怎么实现的？
                                └── Q: 分布式环境下缓存一致性怎么处理？
                                      └── Q: Redis 分布式锁怎么实现？有什么坑？
```

**关键知识点**：
- 缓存穿透：查询不存在的数据，绕过缓存直接打 DB → 布隆过滤器或缓存空值
- 缓存击穿：热点 key 过期，大量请求打到 DB → 互斥锁或永不过期
- 缓存雪崩：大量 key 同时过期或 Redis 宕机 → 过期时间加随机值、集群部署、本地缓存兜底
- 一致性策略：Cache Aside 模式（读时先查缓存，miss 后查 DB 并回写缓存；写时先更新 DB，再删除缓存）
- 延迟双删：先删缓存 → 更新 DB → 延迟几百毫秒再删一次缓存，解决并发读写导致的不一致
- Redis 分布式锁：`SET key value NX EX 10`，注意设置超时防止死锁，使用 Redlock 或 Redisson 保证高可用

---

### 追问链 6：消息队列

```
Q: 为什么用消息队列？解决了什么问题？
  └── Q: 消息队列的常见使用场景有哪些？
        └── Q: Kafka、RabbitMQ、RocketMQ 的区别是什么？
              └── Q: Kafka 的架构是怎样的？Partition、Consumer Group 是什么？
                    └── Q: Kafka 怎么保证消息不丢失？
                          └── Q: 消息重复消费怎么处理？
                                └── Q: 如何保证消息的有序性？
                                      └── Q: 在 NestJS 中如何集成 Kafka 或 RabbitMQ？
```

**关键知识点**：
- 三大作用：解耦、异步、削峰填谷
- 常见场景：订单通知、日志收集、异步任务、流量削峰
- 选型对比：
  - Kafka：高吞吐、持久化、适合日志和流处理，但功能较简单
  - RabbitMQ：功能丰富、支持多种路由模式、适合业务消息，但吞吐量不如 Kafka
  - RocketMQ：阿里出品，介于两者之间，支持事务消息
- 不丢失：生产者 ACK 机制（`acks=all`）、Broker 副本同步、消费者手动提交 offset
- 重复消费：消费端幂等性（唯一 ID 去重 / 业务状态判断）
- 有序性：Kafka 同一 Partition 内有序，需将相关消息路由到同一 Partition；RabbitMQ 单个队列有序
- NestJS 集成：`@nestjs/microservices` 支持 `Kafka`、`RabbitMQ`、`Redis`、`TCP` 等多种传输层

## 三、项目包装

### STAR 法则

| 环节 | 说明 | 话术要点 |
|------|------|----------|
| **S**ituation | 项目的背景是什么？ | 业务规模、团队规模、你担任的角色 |
| **T**ask | 你面临的具体任务或挑战是什么？ | 量化指标：性能瓶颈、QPS、响应时间、数据量 |
| **A**ction | 你采取了什么具体行动？ | 技术选型、架构设计、具体实现、解决过程 |
| **R**esult | 最终取得了什么成果？ | 量化结果：性能提升百分比、故障率下降、效率提升 |

---

### 后端项目包装示例

**项目背景**：某电商平台的后端订单服务，日订单量 50 万+，大促期间峰值 QPS 3000+。

**S（Situation）**：我作为后端核心开发，负责订单系统的架构升级。原有系统采用单体架构，数据库压力大，订单状态更新延迟高，峰值期间经常出现超时和库存扣减不一致问题。

**T（Task）**：目标是将订单系统拆分为微服务，保证订单状态最终一致性，将下单接口 P99 延迟控制在 200ms 以内，库存扣减零误差。

**A（Action）**：
- 使用 NestJS 作为微服务框架，拆分出订单服务、库存服务、支付服务三个独立部署单元
- 引入 Kafka 作为异步消息通道，订单创建后发送消息触发库存预扣和支付流程
- 库存扣减采用"预扣 + 最终确认"的两阶段模式，超时未支付自动回滚，通过消息队列保证最终一致性
- 引入 Redis 缓存热点数据（商品信息、用户地址），缓存穿透使用布隆过滤器拦截
- 使用 TypeORM + MySQL 读写分离，热销商品订单表按月分表
- 使用 `@nestjs/bull` 处理异步任务（超时取消、发货通知）

**R（Result）**：
- 下单接口 P99 延迟从 850ms 降至 120ms，吞吐量提升 6 倍
- 大促期间成功支撑 QPS 5000+，无库存超卖故障
- 订单状态最终一致性在 95% 的情况下 3 秒内达成，剩余 5% 在 30 秒内通过补偿机制完成
- 系统可用性从 99.5% 提升至 99.99%

## 四、面试避坑清单

| 常见错误 | 表现 | 应对策略 |
|----------|------|----------|
| **答非所问** | 面试官问 A，你回答了 B | 停顿 2 秒组织思路，确认问题再回答；没听清可以礼貌请求重复 |
| **只背概念** | 纯背诵定义，不结合场景 | 每个知识点强行绑一个你实际用过的场景；实在没用过就说"虽然我没用过，但理论上..." |
| **不会说"不知道"** | 硬编答案，漏洞百出 | 诚实说"这块我了解不深，我目前的理解是..."，比瞎编好得多 |
| **基础规范不过关** | 代码题不写分号、空指针异常、变量命名随意 | 平时养成好习惯；面试前花 10 分钟复习 ESLint 常用规则 |
| **追问链准备不足** | 只准备了一层，被追问两轮就卡住 | 复习时每个知识点至少准备三层追问，画思维导图 |
| **项目讲得太浅** | 只说了"我做了 XX"，没有技术细节 | 用 STAR 法则组织项目描述，量化结果，提具体技术栈和方案 |
| **忽略边界条件** | 只讲正常流程，不考虑异常、并发、超时 | 讲方案时主动说"这里还要考虑 XX 边界情况" |
| **与面试官争辩** | 固执己见，不接受不同观点 | 先倾听，再理性讨论；可以说"您说得对，我之前的理解是...，您的角度让我学到了" |
| **简历夸大** | 被问到细节时暴露 | 写在简历上的每一条必须能展开讲 5 分钟；不要写"精通"改"熟悉" |
| **不主动引导** | 完全被动回答，一问一答 | 回答完主动说"这块我可以再展开讲一下 XX，您需要吗？" |

## 六、量级数据参考表

| 数据量 | 方案 |
|--------|------|
| 单表 < 500 万 | 普通索引即可 |
| 单表 500 万 - 5000 万 | 分表分库、读写分离 |
| 单表 > 5000 万 | 水平分片、分布式数据库（TiDB / ShardingSphere） |
| QPS < 1000 | 单机 Redis + MySQL |
| QPS 1000 - 10000 | 集群 Redis + 读写分离 |
| QPS 10000 - 50000 | 多级缓存（本地缓存 + Redis 集群）+ 消息队列削峰 |
| QPS > 50000 | CDN 静态化 + 多级缓存 + 消息队列削峰 + 弹性伸缩 |
| 日活 < 10 万 | 单机部署即可，做好容灾备份 |
| 日活 10 万 - 100 万 | 应用多节点部署 + 负载均衡 + 数据库读写分离 |
| 日活 100 万 - 1000 万 | 微服务化 + 容器化编排 + 全链路监控 |
| 日活 > 1000 万 | 单元化架构 + 多活部署 + 自研中间件 |
| 缓存数据 < 1 GB | 单机 Redis 足够 |
| 缓存数据 1 GB - 10 GB | Redis 集群（6 节点起） |
| 缓存数据 > 10 GB | Redis 集群 + 淘汰策略优化 + 本地缓存兜底 |
| 消息量 < 1 万/秒 | RabbitMQ 即可 |
| 消息量 1 万 - 10 万/秒 | Kafka 或 RocketMQ |
| 消息量 > 10 万/秒 | Kafka 分区优化 + 批量消费 + 压缩 |
| 接口响应 < 50ms | 全内存操作，看数据结构和算法是否高效 |
| 接口响应 50ms - 200ms | 合理，数据库查询 + 缓存配合 |
| 接口响应 200ms - 1000ms | 可接受但需优化，检查慢查询、缓存命中率、N+1 问题 |
| 接口响应 > 1000ms | 必须优化，考虑异步化、缓存预热、索引优化、架构调整 |
