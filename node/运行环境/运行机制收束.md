# 运行机制收束：一张图 + 决策模型

## 重新看 Node.js 完整架构

前七篇把每个机制单独拆开讲，现在把它们放回同一张架构图里。你写的 JavaScript 并不是直接碰硬件，中间隔着好几层：

```
┌───────────────────────────────────────────┐
│                  Node.js                  │
│                                           │
│                JavaScript                  │  你写的代码
│                   │                       │
│                   ▼                       │
│                    V8                      │  JS 引擎，编译执行你的代码
│                   │                       │
│                   ▼                       │
│             Node Bindings                 │  C++ 桥接层，把 JS 调用映射到 libuv
│                   │                       │
│                   ▼                       │
│                 libuv                     │
│        ┌──────────────┐                   │
│        │  Event Loop   │   Thread Pool    │  事件循环 + 线程池（默认 4 个线程）
│        └──────┬───────┘                   │
└───────────────┼───────────────────────────┘
                │
                ▼
      ┌─────────────────────┐
      │    OS Async I/O     │    File / Crypto / DNS / zlib
      │ (epoll/kqueue/IOCP) │    （后四类走 libuv 线程池）
      └─────────────────────┘
```

记住这张图的三条主线：

- **网络 I/O 不走线程池**：HTTP、TCP、数据库驱动大多通过 libuv 交给操作系统的 `epoll` / `kqueue` / `IOCP`，由内核异步通知就绪，不占线程池名额。
- **文件、加密、DNS、压缩走线程池**：`fs`、`crypto`、`dns`（部分）、`zlib` 这些阻塞式系统调用被 libuv 丢到后台线程池里跑，跑完回调回到事件循环。
- **你写的 JS 只在主线程的 V8 里执行**：所有"会不会卡"的问题，本质上都是"主线程被占住了没有"。

"只在主线程执行"不等于"一直在算"。下面这段摘自配套脚本，把一次真实请求的耗时拆开量——等待占了绝大多数，CPU 真正执行的只有几毫秒：

除了 Node 内部帮你维护的并发，你还可以**主动创建**两类并发结构：

```
Node Process
 ├── Main Thread          （V8，跑你的 JS + Event Loop）
 ├── Worker Thread        （同进程内的 JS 线程，可共享 SharedArrayBuffer）
 ├── Worker Thread
 └── Worker Thread
```

```
Primary Process
 ├── Child Process        （独立进程，内存不共享，靠 IPC / Socket 通信）
 ├── Child Process
 └── Child Process
```

一句话定位：**前七篇讲的机制，最终都落在这张架构图的不同层上**——模块系统决定代码怎么进 V8，事件循环与微任务决定主线程怎么转，Buffer/Stream 是数据在 libuv 与内核之间怎么流，进程/线程是你在这张图之上主动扩出来的并发结构。

把七篇逐一钉到图上，位置就不抽象了：

- **01 Node.js 是什么** → 整张图的"为什么是 I/O 密集型"视角，搞清楚 JS 与 libuv / 内核的关系。
- **02 模块系统** → 决定你的代码如何被打包、加载进 V8，是图最上层的入口。
- **03 / 04 事件循环** → 主线程里 V8 与 Event Loop 协作的那一条主轴，决定回调何时执行。
- **05 异步编程** → 你在主线程之上写出的 Callback / Promise / async，最终都回到 Event Loop。
- **06 Buffer 与 Stream** → 数据在 libuv、内核、Socket 之间流动的字节形态，是 I/O 真正的载体。
- **07 进程、线程** → 你在 Node Process / Primary Process 之上主动画出的 Worker / Child 分支。

光说"事件循环在转"不够直观，把四个观测点（timers / poll / check / close callbacks）和一个 nextTick / Promise 微任务对照分别挂上回调，就能亲眼看到回调究竟落在哪个阶段：

> 摘自 `./code/node-basics/src/03-eventloop-phases.js`（运行：`npm run 03phases`）

```js
const fs = require('node:fs')
const net = require('node:net')

console.log('==== 同步代码开始 ====')

// 观测点 1：timers 阶段的宏任务
setTimeout(() => {
    console.log('[timers] setTimeout callback')
    // 回调里注册的微任务，会在本回调返回时立刻被清空 —— 这就是微任务检查点
    Promise.resolve().then(() => {
        console.log('[微任务] setTimeout promise then')
    })
}, 0)

// …

// 观测点 2：poll 阶段 —— fs.readFile 的 I/O 回调在 poll 阶段执行
fs.readFile(__filename, () => {
    console.log('[poll] fs.readFile I/O callback')

    // 此刻正处在 poll 阶段内部：
    //   setImmediate 会在本轮的 check 阶段执行（poll 的下一步就是 check，所以很近）
    //   setTimeout 虽然延时 0，但要等到下一轮的 timers 阶段
    setImmediate(() => {
        console.log('[check] readFile 里的 setImmediate')
    })
    setTimeout(() => {
        console.log('[timers] readFile 里的 setTimeout')
    }, 0)

    Promise.resolve().then(() => {
        console.log('[微任务] readFile promise then')
    })
})

// …

// 两条微任务队列：nextTick 优先级高于 Promise
process.nextTick(() => {
    console.log('[nextTick] 顶层 nextTick')
})
Promise.resolve().then(() => {
    console.log('[微任务] 顶层 promise then')
})

console.log('==== 同步代码结束 ====')
```

实测输出（`npm run 03phases`）：

```
==== 同步代码开始 ====
==== 同步代码结束 ====
[nextTick] 顶层 nextTick
[对照] 无连接 server 的 close（由 nextTick 派发，不是 close callbacks 阶段）
[微任务] 顶层 promise then
[timers] setTimeout callback
[微任务] setTimeout promise then
[check] 顶层 setImmediate
[close callbacks] client socket close
[poll] fs.readFile I/O callback
[微任务] readFile promise then
[check] readFile 里的 setImmediate
[timers] readFile 里的 setTimeout
```

## 一张知识关系总图

模块一的六篇不是并列的知识点，而是一条有依赖关系的链——每一篇都是上一篇留下的问题的答案：

```
模块系统（代码怎么组织：CommonJS / ESM / npm）
        │
        │  文件不能互相引用，后面什么都跑不起来
        ▼
  事件循环：六个阶段与微任务 ★主轴
  六阶段 · 内核就绪通知 · 微任务 · nextTick vs Promise · 输出顺序
        │
        │  机器会转、顺序清楚，但代码怎么写才不卡？
        ▼
  异步编程与事件驱动
  Callback → Promise → async/await · EventEmitter
        │
        │  异步"搬运"的到底是什么样的字节？
        ▼
  Buffer 与 Stream
  字节数据 · 背压 · 大文件流式处理
        │
        │  I/O 模型讲到头，单线程算力到顶了怎么办？
        ▼
  进程、线程与优雅退出
  cluster · worker_threads · child_process · SIGTERM 优雅关闭
```

为什么是这个顺序——每一篇都卡在前一篇的尾巴上：

- **模块系统**解决"代码怎么组织"：文件不能互相引用、依赖装不进来，后面任何机制都没法跑。
- **事件循环**解决"为什么不卡、顺序怎么定"：它是整条链的主轴。六个阶段回答"机器怎么转"，两条微任务队列与检查点回答"回调按什么次序执行"——两半合起来才是一台完整的机器，也是异步为什么有效的根。
- **异步编程**解决"怎么写不卡"：在事件循环之上，用 Callback / Promise / async-await 把代码写顺，否则就掉进回调地狱或把并发写成串行。
- **Buffer / Stream**解决"数据长什么样"：异步搬运的不是"变量"而是字节流；大文件、上传下载、实时推送、媒体处理都绕不开它。
- **进程、线程**解决"单线程不够用怎么办"：I/O 模型走到头，CPU 密集或要故障隔离时，从进程/线程层面再扩。
- **优雅退出**解决"出错了怎么安全收场"：只要起了多进程、开了连接，就必然要处理崩溃、未清理句柄与重启丢请求。

这条链不是作者拍脑袋排的，而是"机制之间的赖账关系"：后一篇要解决的问题，正是前一篇跑通后自然暴露出的新瓶颈。读的时候顺着链走，比孤立背每一篇的 API 有用得多。

> **心智模型**：把模块一想象成"修一条高速公路"。模块系统是路基（路得先连起来），事件循环是红绿灯（车怎么不堵），异步编程是行车规则（车按规则跑），Buffer/Stream 是车里拉的货（字节流与背压），进程/线程是再开几条辅路（单条路堵了就分流），优雅退出是收费站和应急车道（出事能安全疏散）。

## 抽象栈：模块一在整个 Node 后端体系处在哪一层

模块一讲的都是"进程内"的事。把它放进一个真实的 Node 后端请求链路，你能看清每部分属于哪一篇：

```
你的业务代码                       ← 模块三 / 模块五
框架（Express / Koa / NestJS）     ← 模块二 / 模块三
node:http（报文解析）              ← 模块二
Event Loop + 微任务                ← 03 / 04
libuv（Event Loop + Thread Pool）  ← 03
内核（epoll / kqueue / IOCP）      ← 03（模块二从网络视角再用一次）
Socket（本质是 Duplex Stream）      ← 05 / 模块二
TCP（可靠字节流，会粘包）           ← 模块二
HTTP / WebSocket / SSE             ← 模块二
```

补充两条横向归属：

- **Buffer / Stream ← 05 / 06**：贯穿整条栈——Socket 是 Duplex Stream，HTTP body、文件、媒体流都是它在搬。
- **进程与线程 ← 07**：横切在最上层，决定一个 Node 实例是单进程还是多进程 / 多线程地跑上面这一整条栈。

记住这条栈，排障时就能"顺藤摸瓜"：用户说接口慢，先想是业务代码慢（模块三 / 五），还是报文解析 / 序列化慢（模块二 / 05 的 Buffer），还是事件循环被占住（03 / 04），还是网络层卡（模块二 / TCP）。层级越往下越接近硬件，越往上越接近你的业务逻辑——定位时从现象所在的层往相邻层递推，比全链路盲猜快得多。

## 决策模型：见 X → 想 Y

拿到需求或遇到性能问题，先别急着写代码，用这张表做"条件反射"。现象是表相，主轴是事件循环：

| 见到什么现象 / 需求 | 该想到什么 | 一句话理由 |
|------|------|------|
| HTTP 请求、查数据库、调外部 API | **Event Loop（异步 I/O）** | 别用同步 API（`fs.readFileSync`、`execSync`）阻塞事件循环 |
| 大文件读写、文件上传下载、流式推送 | **Stream + 背压** | 别用 `readFile` 一次性读进内存，用 `createReadStream` + `pipe` 边读边传 |
| 压缩、加密、大 JSON 解析、复杂计算 | **Worker Thread** | CPU 密集会占住事件循环，丢到 worker 才不卡 |
| 调 ffmpeg、python 脚本、系统命令 | **Child Process** | 这是别的程序，用 `spawn` / `execFile` 起进程去跑 |
| "用不满多核""要故障隔离" | **多进程（cluster / 进程管理）** | 一个 Node 进程只用一个核，cluster 才能铺满多核，且崩一个不影响其他 |
| "进程不退出" | **未清理的句柄 + 优雅关闭** | 还有 server / timer / 连接没关，`SIGTERM` 时要逐个 `close`，句柄清空后进程自然退出 |
| "响应顺序不符合预期" | **微任务检查点（nextTick vs Promise）** | 每个 JS 回调返回调度层都会触发一次检查点，同一检查点内 `nextTick` 先于 Promise，顺序差在这 |
| "CPU 打满但 QPS 很低" | **同步阻塞操作占住事件循环** | 主线程被长同步任务卡死，I/O 回调全在排队，并发能力归零 |
| "服务重启丢请求" | **SIGTERM 优雅关闭** | 收到信号先停收新请求、等存量请求跑完再 `close`，否则连接被硬切断 |
| "内存一路涨最后 OOM" | **背压没做 / 事件监听器泄漏** | 上游猛灌下游慢没暂停，或 `on` 了不 `off`，内存只增不减 |
| "WebSocket / SSE 推送越来越卡" | **单线程 + Stream 背压** | 长连接持续写、下游消费慢，没背压就会堆积，必要时分流到 worker |
| "同样是并发，换台多核机器没变快" | **确认瓶颈是算还是等** | I/O 密集等的是别人，多核帮不上；先测事件循环利用率再决定加进程 |

> **决策模型**：现象是表相，主轴是事件循环。任何"卡""慢""顺序乱""内存涨"的问题，先问一句"是不是事件循环被占住了 / 数据流有没有背压"，再决定是换异步、上 Stream，还是丢给线程 / 进程。

把这张表当成肌肉记忆：下次评审方案或线上排障，先翻它而不是先翻文档。

"响应顺序不符合预期"那一行的根因，是最经典的同步 / 微任务 / 宏任务顺序题。下面这段摘自配套脚本，跑一遍就知道回调为什么排在最后：

> 摘自 `./code/node-basics/src/03-eventloop-order.js`（运行：`npm run 03order`）

```js
// 03 经典事件循环输出顺序题
// 关键心智模型（阶段顺序）：同步代码 -> nextTick 队列 -> 微任务(Promise.then) -> timer
console.log('start') // 同步代码，最先执行

setTimeout(() => {
    console.log('timeout') // 宏任务：进入 timer 阶段，排在最后
}, 0)

Promise.resolve().then(() => {
    console.log('promise') // 微任务：在同步代码之后、timer 之前执行
})

process.nextTick(() => {
    // nextTick 队列优先级高于微任务队列，所以先于 promise 打印
    console.log('nextTick')
})

console.log('end') // 同步代码
```

实测输出（`npm run 03order`）：

```

end
nextTick
promise
timeout
```

"压缩、加密、大 JSON 解析、复杂计算"那一行，本质是 CPU 密集任务占住主线程、让事件循环转不动。下面这段把同一个重活分别跑在主线程和 Worker 里，看主线程心跳是否还在跳：

> 摘自 `./code/node-basics/src/06-worker-thread.js`（运行：`npm run 06worker`）

```js
// 06 对比：① 主线程直接跑 CPU 密集任务（阻塞心跳）② 放进 Worker（不阻塞）
const { Worker } = require('node:worker_threads')
const path = require('node:path')

// CPU 密集任务：大循环求和
function heavy() {
    let sum = 0
    for (let i = 0; i < 5e8; i += 1) sum += i
    return sum
}

// 心跳：每 100ms 打印一次。若主线程被阻塞，数字会"卡住"不跳
let beat = 0
const timer = setInterval(() => {
    beat += 1
    console.log(`心跳 #${beat}`)
}, 100)

// …

setTimeout(() => {
    console.log('\n=== 方案①：主线程直接算（观察心跳是否停滞）===')
    console.time('主线程计算耗时')
    const r1 = heavy()
    console.timeEnd('主线程计算耗时')
    console.log('主线程结果（尾 6 位）:', String(r1).slice(-6))
    console.log('注意：上面这段时间里，心跳是“没跳”的——主线程被算满了')

    // 让心跳再跳几拍，再跑 Worker 方案
    setTimeout(() => {
        console.log('\n=== 方案②：放进 Worker（心跳应持续跳动）===')
        const w = new Worker(path.join(__dirname, '06-worker-thread-child.js'))
        w.on('message', msg => {
            console.log('Worker 返回结果（尾 6 位）:', String(msg.result).slice(-6))
            console.log('可见：主线程心跳始终在跳，重活交给了另一条线程')
            w.terminate()
            clearInterval(timer)
            process.exit(0)
        })
        w.postMessage({ type: 'heavy' })
    }, 400)
}, 300)
```

## 常见误区清单

前七篇散落的坑，这里集中破除一次：

**1. "Node.js 是单线程的"**
只有 JS 执行是单线程的（主线程跑你的代码）。进程内部还有 libuv 线程池在后台跑 `fs` / `dns` / `crypto` / `zlib`，以及操作系统级别的网络 I/O 线程。说"单线程"是特指"JS 执行单线程"。

**2. "所有异步操作都在线程池里跑"**
错。网络 I/O（HTTP、TCP、数据库驱动大多走 libuv 的 `epoll` / `kqueue` / IOCP）由操作系统接管，不进线程池。只有 `fs`、`dns`（部分）、`crypto`、`zlib` 这类才进 libuv 线程池。

**3. "await 会阻塞事件循环"**
`await` 只暂停**当前 async 函数**的后续执行，把后面代码挂到微任务队列；主线程立刻去处理别的回调。它从不阻塞事件循环，阻塞的是"这个函数自己的后半段"。

**4. "worker_threads 就是 libuv 线程池"**
两者不是一回事。`worker_threads` 是你主动 `new Worker()` 创建、可共享 `SharedArrayBuffer` 的 JS 线程；libuv 线程池是 Node 内部自动维护、你无法直接控制的系统线程。前者给"你"用，后者给"Node 内部"用。

**5. "process.nextTick 用得越多越快"**
`nextTick` 队列在每个阶段之间被**清空**（直到为空），递归调用 `nextTick` 会饿死事件循环，导致 timers / I/O 回调永远得不到执行。需要"让出执行权、下一轮再继续"应该用 `setImmediate`。

**6. "多开进程就能变快"**
只对 CPU 密集型或要故障隔离的场景成立。I/O 密集型瓶颈在"等待"，事件循环本就能在等待时处理别的请求，多开进程只是多占内存，解决不了等待问题。

## 自测 6 问：不翻前面，凭记忆能答上来说明模块一过关

题目编号对应模块一的篇号（事件循环拆成上 / 下），覆盖 01 ~ 08：

**01｜一次请求里 CPU 真在算多久？为什么 Node 适合 I/O 密集型而不是 CPU 密集型？**（对应 01）
一次请求里数据库、下游服务、第三方 API、Redis 的等待占绝大多数，V8 真正执行你的 JS 往往只有几毫秒。Node 擅长的不是算得快，而是等待的时候不闲着——所以适合 I/O 密集，怕的是长同步计算。

**02｜`require` 和 `import` 有什么区别？CommonJS 与 ESM 能不能混用？**（对应 02）
`require` 是运行时同步加载、拿到的是值的拷贝（对象共享）；`import` 是静态分析、绑定引用。同一文件只能用一套，靠 `package.json` 的 `type` 字段或 `.cjs` / `.mjs` 后缀决定；跨系统引用要用 `module.exports` / `createRequire` 做桥。

**03｜libuv 有哪六个阶段？哪个是 I/O 核心？网络 I/O 到底走不走线程池？**（对应 03 事件循环上）
timers → pending callbacks → idle/prepare → poll → check → close callbacks。poll 是 I/O 核心，在这里等待文件 / 网络就绪。网络 I/O 走操作系统 `epoll` / `kqueue` / IOCP，不进线程池；只有 `fs` / `crypto` / `dns` / `zlib` 走 libuv 线程池。

**04｜`nextTick` 和 `Promise` 的回调谁先跑？为什么递归 `nextTick` 很危险？**（对应 04 事件循环下）
`nextTick` 队列在每阶段之间被清空、优先级高于 `Promise` 微任务；`Promise.then` 在阶段之后执行。递归 `nextTick` 会一直占住队列饿死事件循环，导致 timers / I/O 永远得不到执行。

**05｜`await` 用得不对会把并发写成串行吗？为什么 2GB 文件绝不能用 `readFile`？**（对应 05 异步 / 06 Buffer 与 Stream）
会。在 `for` 循环里 `await` 每个请求会把并行写成串行。2GB 文件用 `readFile` 会一次性读进内存，直接撑爆 V8 堆甚至 OOM；正确做法是用 `createReadStream` 边读边 `pipe`，Stream 自带背压。

**06｜进程不退出通常是漏了什么？面对"卡 / 慢"，决策模型第一反应是看哪一层？**（对应 07 进程线程 / 08 收束）
通常是 server / timer / 长连接 / 事件监听器没清理，或没监听 `SIGTERM` 主动 `close`。决策模型第一反应是："事件循环是不是被占住了？数据流有没有背压？"再决定换异步、上 Stream，还是丢给线程 / 进程。

"监听 SIGTERM 主动 close"落到代码上，就是下面这段：收到信号先 `server.close()` 停收新连接、等存量请求处理完，再关数据库连接，句柄都清空后进程才退出：

> 摘自 `./code/node-basics/src/06-graceful-shutdown.js`（运行：`npm run 06shutdown`）

```js
// 06 优雅关闭：收到 SIGTERM/SIGINT 时不立刻退出
// ① server.close() 停止接收新连接 ② 等待在途请求结束（这里有个 2 秒慢接口）
// ③ 关闭模拟的数据库连接 ④ 日志后 process.exit(0)
const http = require('node:http')

// 模拟一个数据库连接
const db = {
    close(cb) {
        console.log('[db] 正在关闭数据库连接...')
        setTimeout(cb, 200)
    }
}

// …

function gracefulShutdown(signal) {
    if (shuttingDown) return // 防止重复触发
    shuttingDown = true
    console.log(`\n收到信号 ${signal}，开始优雅关闭...`)

    // ① 停止接收新连接，但已建立的连接在途请求会继续处理完
    server.close(() => {
        console.log('[http] 已停止接收新连接，在途请求已处理完')
        serverClosed = true
        maybeExit()
    })

    // ③ 关闭数据库连接
    db.close(() => {
        console.log('[db] 数据库连接已关闭')
        dbClosed = true
        maybeExit()
    })
}
```

实测输出（`npm run 06shutdown` 启动后，在终端按 Ctrl+C / 发送 SIGTERM 触发优雅关闭）：

```
服务已启动: http://localhost:3000 （/slow 是 2 秒慢接口）
测试方式：另开终端执行  curl http://localhost:3000/slow  ，然后在本窗口按 Ctrl+C
```

> 收到信号后，会依次打印上面 `gracefulShutdown()` 里的三行日志（`收到信号 …`、`[http] 已停止接收新连接…`、`[db] 数据库连接已关闭`），最后 `优雅关闭完成，进程退出`——句柄清空前进程不会提前退出。

## 交接：模块一结束，进入模块二

进程内的 I/O 模型到这就讲完了——事件循环为什么能扛并发、异步怎么写、字节流怎么搬、单线程不够时怎么用进程线程分流，全都串起来了。但有一个问题我们一直没回答：**这些 I/O 到底是从哪来的？**

答案是网络。HTTP 请求、数据库调用、WebSocket 推送、实时消息，本质都是"通过网卡和另一台机器交换字节"。I/O 模型解决的是"怎么高效地等和搬"，而数据是怎么在机器之间流动、TCP 和 HTTP 是什么、WebSocket 怎么做到实时——这就是模块二要解决的。下一篇从网络底层建立整层的全景认知。
