# 进程、线程与优雅退出

## `node app.js` 启动的到底是一个什么？
敲下 `node app.js`，操作系统会创建一个 **Node.js 进程（Process）**，它拥有自己的一整套资源：

- 独立的内存空间、一个 V8 实例、一块堆（Heap）
- 一个事件循环（Event Loop）
- 一组文件描述符与若干系统资源

Node 用全局对象 `process` 让你观测和控制当前进程：

> 示意片段（无配套脚本）（说明：本篇配套脚本均为 CommonJS，下文代码块一律以 `require` 逐字摘录自 `./code/node-basics/src/`，不再使用 `import`。）

```js
console.log(process.pid)          // 进程 ID，操作系统中唯一标识
console.log(process.uptime())     // 进程已持续运行的秒数
console.log(process.argv)         // 启动参数，argv[0]=node，argv[1]=脚本
process.exitCode = 1              // 设置退出码，自然退出时带上（非立即退出）

// 内存占用：rss=物理内存总量；heapTotal=V8 已申请堆；heapUsed=JS 堆已用；external=堆外内存（如 Buffer）
console.log(process.memoryUsage())
```

注意 `rss` 与 `heapUsed` 的差异：一个 Node 进程「JS 对象不多、内存却很大」是常态，因为 Buffer、线程栈等都算进 `rss`。

## 怎么创建子进程：`child_process` 四把刀
调用 `ffmpeg`、`python` 脚本、系统命令时，要靠 `child_process` 派生子进程。四个 API 语义差别很大：

| API | 是否走 shell | 是否缓冲全部输出 | 是否走流 | 典型用途 |
|-----|:---:|:---:|:---:|---------|
| `spawn(command, args)` | 否 | 否（边产边吐） | 是 | 长时间运行、大量输出 |
| `exec(command, cb)` | 是 | 是（收完再回调） | 否 | 短命令、`git status` 等 |
| `execFile(file, args, cb)` | 否 | 是 | 否 | 执行已知可执行文件，更安全 |
| `fork(modulePath)` | 否（建 IPC） | 否 | 否（走 IPC） | 创建 Node 子进程并通信 |
`spawn` 最基础，输出走**流**，适合长时间/大输出程序：

> 摘自 `./code/node-basics/src/06-child-process.js`（运行：`npm run 06child`）

```js
// spawn 适合二进制/大输出，stdio 直接继承到当前终端
const sp = spawn('node', ['-e', 'console.log("spawn 子进程输出: hello")'], { stdio: 'inherit' })
sp.on('close', code => {
    console.log('--- spawn 退出码:', code)
    // …
```

实测输出（`npm run 06child`，仅截取 spawn 段）：

```
=== 1) spawn：以流的方式把子进程输出吐出来（不缓存）===
spawn 子进程输出: hello
--- spawn 退出码: 0
```

`exec` 走 shell，把输出**全缓冲**在内存后回调；输出特别大会撑爆 `maxBuffer`（默认 1MB）：

> 摘自 `./code/node-basics/src/06-child-process.js`（运行：`npm run 06child`）

```js
console.log('\n=== 2) exec：整段 shell 字符串，缓冲输出一次性回调 ===')
// exec 会把 stdout 缓存到回调里，适合小量文本输出
// 注意：这里用纯 ASCII 命令，避免 Windows 下 cmd 代码页导致中文乱码
exec('echo exec child process output: hello', (err, stdout) => {
    if (err) throw err
    console.log('exec 结果:', stdout.trim())
    // …
```

实测输出（`npm run 06child`，仅截取 exec 段）：

```
=== 2) exec：整段 shell 字符串，缓冲输出一次性回调 ===
exec 结果: exec child process output: hello
```

`execFile` 不经 shell 直接执行可执行文件，无 shell 注入面，更安全：

> 摘自 `./code/node-basics/src/06-child-process.js`（运行：`npm run 06child`）

```js
console.log('\n=== 3) execFile：直接执行可执行文件，不走 shell ===')
// execFile 更安全（无 shell 注入风险），这里直接跑 node 可执行文件
execFile(process.execPath, ['-e', 'console.log("execFile 运行 node 输出: hello")'], (err, stdout) => {
    if (err) throw err
    console.log('execFile 结果:', stdout.trim())
    // …
```

实测输出（`npm run 06child`，仅截取 execFile 段）：

```
=== 3) execFile：直接执行可执行文件，不走 shell ===
execFile 结果: execFile 运行 node 输出: hello
```

`fork` 专门创建 Node 子进程，额外建立 **IPC 通道**，用 `child.send()` / `process.on('message')` 通信：

> 摘自 `./code/node-basics/src/06-child-process.js`（运行：`npm run 06child`）

```js
console.log('\n=== 4) fork：专门跑 node 子模块，内置 IPC 通道 ===')
// fork 是 spawn('node', [子文件]) 的语法糖，且自动建立 IPC
const child = fork(path.join(__dirname, '06-worker-fork-child.js'))
child.on('message', msg => {
    console.log('父进程收到子进程消息:', msg)
    child.send({ from: 'parent', text: '收到你的问候' }) // 回一句让子进程退出
})
child.on('exit', code => {
    console.log('fork 子进程退出码:', code)
    console.log('\n四个 API 对照完成')
    process.exit(0)
})
child.send({ from: 'parent', text: '你好，子进程' })
```

上面父进程侧经 `fork` 建立了 IPC；子进程侧（被父进程 `fork` 起来的 `06-worker-fork-child.js`）通过 `process.on('message')` 收、`process.send` 回：

> 摘自 `./code/node-basics/src/06-worker-fork-child.js`（运行：`npm run 06child`）

```js
// fork 子进程（被 06-child-process.js 通过 fork 调用）
// 通过 process.on('message') 收父进程消息，用 process.send 回传，走 IPC 通道
console.log('[fork 子进程] 启动')

process.on('message', msg => {
    console.log('[fork 子进程] 收到:', msg)
    // 回传给父进程
    process.send({ echo: msg.text, time: Date.now() })
    // 双向通信完成（父进程发来“收到”后）主动退出
    if (msg.text && msg.text.includes('收到')) {
        process.exit(0)
    }
})
```

实测输出（`npm run 06child`，仅截取 fork 段）：

```
=== 4) fork：专门跑 node 子模块，内置 IPC 通道 ===
[fork 子进程] 启动
[fork 子进程] 收到: { from: 'parent', text: '你好，子进程' }
父进程收到子进程消息: { echo: '你好，子进程', time: 1789616243746 }
[fork 子进程] 收到: { from: 'parent', text: '收到你的问候' }
父进程收到子进程消息: { echo: '收到你的问候', time: 1789616243749 }
fork 子进程退出码: 0

四个 API 对照完成
```

补充：`spawn` 的 `stdio: 'inherit'` 让子进程共用父进程的标准输入输出；`detached: true` 配合 `child.unref()` 可让子进程脱离父进程独立运行（后台任务常用）。口诀：**流式大输出用 `spawn`；短命令拼 shell 用 `exec`；跑文件不要 shell 用 `execFile`；跑 Node 并通信用 `fork`。**

## 为什么一个 Node 进程吃不满多核？
8 核 CPU，但 Node 执行 JS 默认只用一个**主线程**。单个实例的事件循环再快，也只持续占满一个核；要让多核都忙起来，就开多个 Node 进程各占一核：

```
CPU  Core 1  →  Node Process A   (JS 主线程在跑)
CPU  Core 2  →  Node Process B   (空闲 → 被利用)
CPU  Core 3  →  Node Process C   ...
```

这即「多进程并行」的由来——但多个进程之间是隔离的，所以需要专门手段协作。

## 用 `cluster` 把多核铺满
`cluster` 让一个 **Primary（主）进程** fork 出多个 **Worker**，它们共享同一监听端口，由 OS / Primary 做负载分发：

> 示意片段（无配套脚本）

```js
const cluster = require('node:cluster')
const os = require('node:os')
const http = require('node:http')

if (cluster.isPrimary) {
  const cpuCount = os.availableParallelism()  // 按可用并行度，不写死核数
  for (let i = 0; i < cpuCount; i++) cluster.fork()
  cluster.on('exit', (w) => { console.log(`worker ${w.process.pid} 挂了`); cluster.fork() })
} else {
  http.createServer((req, res) => res.end(`PID: ${process.pid}`)).listen(3000)
}
```

```
                  Primary Process
                        │
            ┌───────────┼───────────┐
            │           │           │
            ▼           ▼           ▼
         Worker       Worker      Worker
        Process      Process     Process
            └───────────┼───────────┘
                        │
                     Port 3000（所有 worker 共享）
```

⚠️ **关键提醒**：Node 官方现已明确——如果不需要进程级隔离，应优先考虑 `worker_threads`，因为 Worker 能在同一 Node 实例内共享内存、成本更低。所以「见多核就无脑上 cluster」是错的：`cluster` 的真正价值是**进程级故障隔离**（一个崩了不影响其他）和**多核部署**，而不是单纯并行算点东西。

## 进程之间默认不能共享内存
进程 A 里 `const count = 100`，进程 B **无法直接访问**——因为两者内存空间由操作系统隔离：

```
Process A 的内存空间          Process B 的内存空间
┌──────────────┐            ┌──────────────┐
│ const count=100│   ←隔离→  │              │
└──────────────┘            └──────────────┘
```

所以进程间通信必须借助「进程外的公共通道」之一。几种方式适用场景：

| 方式 | 适用场景 |
|------|---------|
| IPC（含 `fork`/`cluster` 通道、pipe） | 同机父子/兄弟进程高频低延迟通信 |
| Socket（TCP/Unix Domain） | 同机或跨机、最通用的通信 |
| Redis | 跨进程共享状态/缓存/简单消息 |
| Message Queue | 异步解耦、削峰、可靠投递的后台任务 |
| HTTP | 跨服务跨语言，最易调试 |

## 什么是线程？
一个进程内可存在多个线程，是进程内的多条**执行路径**：

```
Process ──┬── Thread A
          ├── Thread B
          ├── Thread C
          └── Thread D
```

线程**共享进程的一部分内存空间**，通信成本低于进程；但共享也带来并发控制、内存可见性与 **竞态条件（Race Condition）**——多线程同时改同一块数据，结果取决于执行时序。Node 主线程跑 JS 是单线程的，但进程内还藏着 libuv 线程池等「房间」。

## 用 `worker_threads` 在同一个进程里开 JS 线程
`worker_threads` 让你在**同一进程内**开多条 JS 执行线程，把 CPU 密集任务从主线程挪走：

> 摘自 `./code/node-basics/src/06-worker-thread.js`（运行：`npm run 06worker`）

```js
console.log('\n=== 方案②：放进 Worker（心跳应持续跳动）===')
const w = new Worker(path.join(__dirname, '06-worker-thread-child.js'))
w.on('message', msg => {
    console.log('Worker 返回结果（尾 6 位）:', String(msg.result).slice(-6))
    console.log('可见：主线程心跳始终在跳，重活交给了另一条线程')
    w.terminate()
    clearInterval(timer)
    process.exit(0)
})
w.postMessage({ type: 'heavy' })
```

Worker 线程侧（`06-worker-thread-child.js`）在独立线程跑 CPU 密集任务，通过 `parentPort` 与主线程通信：

> 摘自 `./code/node-basics/src/06-worker-thread-child.js`（运行：`npm run 06worker`）

```js
// Worker 线程（被 06-worker-thread.js 通过 new Worker 调用）
// 在独立线程跑 CPU 密集任务，通过 parentPort 与主线程通信
const { parentPort } = require('node:worker_threads')

function heavy() {
    let sum = 0
    for (let i = 0; i < 5e8; i += 1) sum += i // 大循环求和，纯 CPU
    return sum
}

parentPort.on('message', msg => {
    if (msg && msg.type === 'heavy') {
        const r = heavy()
        parentPort.postMessage({ result: r })
    }
})
```

```
注意：上面这段时间里，心跳是“没跳”的——主线程被算满了

心跳 #6

=== 方案②：放进 Worker（心跳应持续跳动）===

心跳 #13

Worker 返回结果（尾 6 位）: 108900
```

```
        Node Process
            │
            ├── Main Thread  ⇄  postMessage / on('message')
```

`worker.terminate()` 释放线程、`worker.on('error')` 兜异常、`isMainThread` 确认运行上下文——三者是把 Worker 用稳的必备件。

## Worker Thread 真正适合什么？
官方指出 Worker Threads 主要执行 **CPU 密集型 JavaScript**：图片处理、视频数据处理、巨大 JSON 解析/计算、复杂数学、压缩、哈希、大数组、复杂文本解析。

反例最能说明问题：主线程一旦被大循环占满，事件循环就转不动。配套脚本用「心跳计时器」量化这一点——下面这段摘自 `06-worker-thread.js`，让主线程直接跑大循环（相当于在请求处理函数里跑重活）：

> 摘自 `./code/node-basics/src/06-worker-thread.js`（运行：`npm run 06worker`）

```js
console.log('\n=== 方案①：主线程直接算（观察心跳是否停滞）===')
console.time('主线程计算耗时')
const r1 = heavy()
console.timeEnd('主线程计算耗时')
console.log('主线程结果（尾 6 位）:', String(r1).slice(-6))
console.log('注意：上面这段时间里，心跳是“没跳”的——主线程被算满了')
```

实测输出（`npm run 06worker`，仅截取方案①主线程段，看「心跳 #2」后到「心跳 #3」之间的停顿）：

```
心跳 #1
心跳 #2

=== 方案①：主线程直接算（观察心跳是否停滞）===
主线程计算耗时: 954.147ms
主线程结果（尾 6 位）: 108900
注意：上面这段时间里，心跳是“没跳”的——主线程被算满了
心跳 #3
```

主线程被占死，事件循环转不动，于是请求 A/B/C、WebSocket、Timer **全部受影响**（CPU 打满但 QPS 极低）。正确做法是把 CPU 任务丢进 Worker，主线程等结果再响应：

```
Main Thread ──▶ Worker Thread ──▶ CPU 计算 ──▶ Result ──▶ 响应
   （继续处理        （后台算）
    别的请求）
```

## Worker Thread 为什么不用于普通 I/O？
`await fetch(...)` 这种事 Node 本来就极其擅长——事件循环 + 异步 I/O 已处理得很好。每个请求都 `new Worker` 去做 I/O，反而更慢，因为每次都要付出：

```
创建 Thread → 初始化 V8 环境 → 跨线程传输数据 → 销毁 Thread
```

判别标准：

| 你的任务 | 用什么 |
|----------|--------|
| I/O 密集（网络、文件、DB/Redis 调用） | Event Loop / 异步 I/O |
| CPU 密集（大计算、加解密、压缩） | Worker Threads |

## ⚠️ 误区四：`Worker Thread` ≠ `libuv` 线程池
Node 里有两个极易混淆的「线程」：

- **libuv Thread Pool**：Node **内部**自动维护，替你跑 `fs`/`dns`/`crypto`/`zlib` 底层阻塞操作。你**一般不直接创建**，也感知不到。
- **`worker_threads`**：你用 `new Worker()` **主动创建**的 JS Worker，有自己的 V8 环境与执行上下文，跑你写的 JS。

放到同一张图里边界才清楚：

```
                         Node Process
                              │
          ┌───────────────────┼───────────────────┐
          │                                       │
          ▼                                       ▼
     Main JS Thread                         Worker Thread
          │                              （你 new Worker() 创建，
          ▼                                有独立 V8 与执行上下文）
     Event Loop
          │
          ▼
        libuv
          │
          ├── Worker Pool Thread 1   （Node 内部维护，跑 fs/dns/
          ├── Worker Pool Thread 2     crypto/zlib，你不直接创建）
          ├── Worker Pool Thread 3
          └── Worker Pool Thread 4
```

一句话：libuv 线程池是「Node 帮你干底层脏活」的隐藏线程；worker_threads 是「你自己开一条 JS 线程算东西」的线程，两回事。

## Process 与 Worker Thread 全维度对比
| 维度 | 进程（Process） | Worker Thread |
|------|----------------|---------------|
| 内存 | 独立（默认不共享） | 可共享（SharedArrayBuffer） |
| V8 实例 | 独立（每进程一个） | Worker 自己跑 JS |
| Event Loop | 独立（每进程一个） | 有自己的执行环境 |
| 隔离性 | 强（崩一个不影响其他） | 较弱（同进程共享内存） |
| 创建成本 | 较高 | 相对较低 |
| 通信方式 | IPC | Message + Shared Memory |
| 能否运行外部程序 | 可以 | 不适合 |
| CPU 计算 | 可以 | 非常适合 |
| 故障隔离 | 好 | 不如独立进程 |

核心差异：**进程强隔离但不共享；线程轻量但共享、要自己管并发安全。**

## ⚠️ 误区五：生产环境为什么不能随便 `new Worker`？
常见错误写法「每请求一个线程」。配套脚本用「反例」演示每任务 `new Worker` 的开销——下面这段摘自 `06-worker-pool.js` 的 `antiPattern()`：

> 摘自 `./code/node-basics/src/06-worker-pool.js`（运行：`npm run 06pool`）

```js
// ---- 反例：每个任务都 new Worker ----
async function antiPattern() {
    const peak = samplePeak()
    const start = process.hrtime.bigint()
    const promises = []
    for (let i = 0; i < TASKS; i += 1) {
        // 这一段在演示：每个请求都创建一个 Worker，创建/调度开销随并发线性增加
        promises.push(
            new Promise(resolve => {
                const w = new Worker(childPath)
                w.once('message', m => {
                    w.terminate()
                    resolve(m.result)
                })
                // …
                w.postMessage({ n: N })
            })
        )
    }
    // …
```

实测输出（`npm run 06pool`，反例 vs 正例对比）：

```
=== 反例：每个任务 new Worker ===
总耗时 ≈ 840 ms，峰值 RSS ≈ 232.8 MB
说明：20 个 Worker 被同时创建，线程创建与调度本身成为瓶颈，内存随并发线性膨胀

=== 正例：Worker Pool（4 个复用）===
总耗时 ≈ 505 ms，峰值 RSS ≈ 110.2 MB
说明：Worker 复用，并发被限制在 4，内存平稳、可控

对比：
  耗时  反例 840 ms  vs  正例 505 ms
  内存  反例 232.8 MB  vs  正例 110.2 MB
```

10,000 并发 → 10,000 个 Worker，服务器照样炸——创建与调度线程本身成了新瓶颈，比主线程直接算还惨。

正确做法是 **Worker Pool + Task Queue**：预先创建固定数量（≈ CPU 核数）的 Worker，请求把任务投进队列，空闲 Worker 取任务执行：

```
         CPU = 8 Core
              │
   预先创建固定数量 Worker
              │
   Task Queue（任务队列）
      │   │   │   │
      ▼   ▼   ▼   ▼
   Worker1 Worker2 Worker3 Worker4 ...（≈ 核数）
```

最小实现要点：①**空闲标记**——每个 Worker 维护忙/闲，只派给空闲的；②**任务队列**——超额任务排队而非新建线程；③**轮询派发**——主线程 push、空闲 Worker 取；④**`Promise` 包装**——对外暴露 `runTask(input): Promise<result>`，调用方 `await` 即可，内部完成派发→取结果→回收。线程数恒定可控，既用多核又不让「建线程」成瓶颈。

## Worker Threads 能共享内存，但代价是并发安全
`worker_threads` 相对 `child_process`/`cluster` 的关键差异，是能用 `SharedArrayBuffer` 让主线程与 Worker 共享同一块内存：

```
      Main Thread
           │
           ├────────┐
           │ Shared │
           │ Memory │
           └────────┤
                    │
              Worker Thread
```

但共享内存意味着必须直面 **`Atomics`、竞态条件、同步与锁**。两个 Worker 并发 `shared[i]++` 会因「读→改→写」非原子而丢失更新：

> 示意片段（无配套脚本）

```js
shared[0]++ // ❌ 非原子：读旧值→+1→写回，中间会被插空，结果偏小
```

用 `Atomics.add` 保证一步到位：

> 示意片段（无配套脚本）

```js
const { Worker, isMainThread, parentPort } = require('node:worker_threads')
if (isMainThread) {
  const sab = new SharedArrayBuffer(4)
  const arr = new Int32Array(sab)
  for (let i = 0; i < 4; i++) new Worker(new URL(import.meta.url), { workerData: sab })
} else {
  const arr = new Int32Array(parentPort.workerData)
  for (let i = 0; i < 1000; i++) Atomics.add(arr, 0, 1) // ✅ 原子加法
  parentPort.postMessage('done')
}
```

没有 `Atomics` 这类同步原语，共享内存几乎必然写出并发 Bug。能共享是能力，会同步才是本事。

## 四种并发方式到底怎么选？
| 见到什么 | 用什么 |
|----------|--------|
| 普通 HTTP / DB / Redis / 外部 API | Event Loop（异步 I/O） |
| CPU 密集型 JavaScript | `worker_threads`（配 Worker Pool） |
| 要强隔离 / 独立崩溃 / 运行外部程序 / 执行 shell | `child_process` |
| 要多实例铺满多核 + 进程级故障隔离 | 多进程（`cluster` / 进程管理器 / 容器编排 + 负载均衡） |

浓缩一句：**I/O 用异步；CPU 用 Worker（走池）；要隔离或跑外部程序用子进程；要铺多核且要故障隔离用多进程。**

## 进程生命周期与优雅关闭
生产服务要经历启动、运行、异常、收到信号、优雅关闭、被重启。其中**优雅关闭（Graceful Shutdown）**是后端必修。收到 `SIGTERM` 时**不应立刻退出**，而应：停止收新请求 → 等在途请求结束 → 关数据库 → 关 Redis → 关 MQ → 退出。

> 摘自 `./code/node-basics/src/06-graceful-shutdown.js`（运行：`npm run 06shutdown`）

```js
function gracefulShutdown(signal) {
    if (shuttingDown) return // 防止重复触发
    shuttingDown = true
    console.log(`\n收到信号 ${signal}，开始优雅关闭...`)

    // ① 停止接收新连接，但已建立的连接在途请求会继续处理完
    server.close(() => {
        console.log('[http] 已停止接收新连接，在途请求已处理完')
        serverClosed = true
        maybeExit()
    })

    // ③ 关闭数据库连接
    db.close(() => {
        console.log('[db] 数据库连接已关闭')
        dbClosed = true
        maybeExit()
    })
}

process.on('SIGTERM', () => gracefulShutdown('SIGTERM'))
process.on('SIGINT', () => gracefulShutdown('SIGINT'))
```

实测输出（`npm run 06shutdown`，启动后按 `Ctrl+C` 触发 `SIGINT`）：

```
服务已启动: http://localhost:3000 （/slow 是 2 秒慢接口）
测试方式：另开终端执行  curl http://localhost:3000/slow  ，然后在本窗口按 Ctrl+C

（以下为脚本捕获到 SIGINT/SIGTERM 后实际会打印的关闭序列——本机无头环境无法自动注入信号，本地 `npm run 06shutdown` 后按 Ctrl+C 即可复现）
收到信号 SIGINT，开始优雅关闭...
[http] 已停止接收新连接，在途请求已处理完
[db] 数据库连接已关闭
优雅关闭完成，进程退出
```

为什么还要处理 `SIGINT`？它是终端 `Ctrl+C` 发的信号，本地调试必碰；而 `SIGTERM` 是容器编排（`docker stop` 默认就发它、K8s 滚动发布也发）通知「该走了」的标准信号。两个都接住，本地与线上才能一致体面退场。

## ⚠️ 误区六：不要滥用 `process.exit()`
`process.exit(1)` 会**立即**终止进程，来不及收尾，可能导致：`stdout` 没写完、日志没发出、数据库事务没提交、HTTP 响应没结束。

Node 官方甚至特别指出：**若因错误必须结束进程，让未捕获错误自然使进程终止，通常比随手 `process.exit()` 更安全**——自然终止前 Node 会先跑完已排队的 I/O 与回调。所以生产环境真正要掌握的是三件事，而非 `process.exit()`：`process.exitCode`（设码不立即杀）、Graceful Shutdown（先收摊再走）、Signal Handling（正确响应信号）。

## 错误类型与兜底：该在哪一层接住？
错误发生在不同位置，就该在不同层兜住：

| 错误发生的位置 | 该在哪一层兜住 |
|---------------|---------------|
| 同步代码（JSON.parse 等） | `try / catch` |
| 回调式 API（error-first） | 判断第一个 `err` 参数 |
| Promise / async | `.catch` 或 `await try/catch` |
| 路由 / 定时任务 / 消息消费入口 | 外层包 try/catch，转成可观测响应 |
| 漏到进程级 | `uncaughtException` / `unhandledRejection` 做最后清理 |

`uncaughtException` 与 `unhandledRejection` 的区别：前者是同步代码抛出却没人 catch，后者是 Promise reject 了却没接住。

> 摘自 `./code/node-basics/src/06-error-fallback.js`（运行：`npm run 06fallback`）

```js
process.on('uncaughtException', err => {
    console.error('[兜底·uncaughtException] 捕获到一个未处理异常：', err.message)
    console.error('[兜底·uncaughtException] 这只是最后一道防线，正确做法是记录日志后优雅退出，不要继续跑。')
    console.error('[兜底·uncaughtException] 这里为了演示直接退出（process.exit(1)）。')
    process.exit(1)
})

process.on('unhandledRejection', reason => {
    console.error('[兜底·unhandledRejection] 捕获到一个未处理的 Promise 拒绝：', reason)
    console.error('[兜底·unhandledRejection] 这只是最后一道防线，正确做法是记录日志后优雅退出，不要继续跑。')
    console.error('[兜底·unhandledRejection] 这里为了演示直接退出（process.exit(1)）。')
    process.exit(1)
})
```

实测输出（`npm run 06fallback uncaught` 触发进程级兜底）：

```
=== ③ 进程级兜底（无兜底时进程会直接崩）===
  下面触发一个「没有任何 try/catch 接住」的异常……
[兜底·uncaughtException] 捕获到一个未处理异常： 我没被任何 try/catch 接住，只能靠进程级兜底
[兜底·uncaughtException] 这只是最后一道防线，正确做法是记录日志后优雅退出，不要继续跑。
[兜底·uncaughtException] 这里为了演示直接退出（process.exit(1)）。
```

实测输出（`npm run 06fallback unhandled`）：

```
=== ③ 进程级兜底（unhandledRejection 分支）===
  下面创建一个「既没有 await 也没有 .catch」的 Promise 拒绝……
[兜底·unhandledRejection] 捕获到一个未处理的 Promise 拒绝： Error: 我既没 await 也没 .catch，只能靠进程级兜底
[兜底·unhandledRejection] 这只是最后一道防线，正确做法是记录日志后优雅退出，不要继续跑。
[兜底·unhandledRejection] 这里为了演示直接退出（process.exit(1)）。
```

⚠️ **为何 `uncaughtException` 之后不推荐继续运行？** 异常能漏到这一层，说明进程内部状态已不可信（模块半初始化、状态写坏）。强行续命会引入更难查的 Bug。正确姿势：记录日志 + 优雅退出，让 PM2/K8s 拉起干净新进程。判断错误种类常用 `error.code` 与 `error.name`：

> 示意片段（无配套脚本）

```js
// 判断错误种类：error.code 区分系统错误，error.name 区分异常类型
try { await fs.readFile('missing.txt') }
catch (err) {
  if (err.code === 'ENOENT') console.log('文件不存在')
  if (err.code === 'EADDRINUSE') console.log('端口被占用')
  if (err.code === 'ECONNRESET') console.log('连接被重置')
  // error.name 区分异常种类，如 'TypeError' / 'RangeError'
}
```

同步 / 异步两道前置防线，配套脚本用真实可跑的代码演示「在哪一层接住」：

> 摘自 `./code/node-basics/src/06-error-fallback.js`（运行：`npm run 06fallback`）

```js
// ── 第一道防线：同步 try/catch ──
function layer1Sync() {
    console.log('=== ① 同步 try/catch ===')
    try {
        // 故意访问不存在的属性，抛出同步异常
        const obj = null
        obj.foo.bar
    } catch (err) {
        console.log('  被 try/catch 接住，进程继续运行：', err.message)
    }
    console.log('  同步防线演示结束，进程依然健康。\n')
}

// ── 第二道防线：async 函数里的 try/catch 与 Promise.catch ──
async function layer2Async() {
    console.log('=== ② 异步 Promise.catch / async 里的 try-catch ===')

    // 2a) 显式 .catch 兜底
    Promise.reject(new Error('异步拒绝（用 .catch 接住）')).catch(err =>
        console.log('  被 .catch 接住，进程继续运行：', err.message)
    )

    // 2b) await 配合 try/catch
    try {
        await Promise.reject(new Error('await 抛出的拒绝（用 try/catch 接住）'))
    } catch (err) {
        console.log('  被 async/try-catch 接住，进程继续运行：', err.message)
    }
    // …
}
```

实测输出（`npm run 06fallback` 默认模式，只跑前两道防线）：

```
=== ① 同步 try/catch ===
  被 try/catch 接住，进程继续运行： Cannot read properties of null (reading 'foo')
  同步防线演示结束，进程依然健康。

=== ② 异步 Promise.catch / async 里的 try-catch ===
  被 .catch 接住，进程继续运行： 异步拒绝（用 .catch 接住）
  被 async/try-catch 接住，进程继续运行： await 抛出的拒绝（用 try/catch 接住）
  异步防线演示结束，进程依然健康。
```

## 环境变量与 `os` 模块
`process.env` 读取环境变量，常用于区分环境、存放敏感配置：

> 示意片段（无配套脚本）

```js
console.log(process.env.NODE_ENV) // 'development' / 'production'
console.log(process.env.PORT)     // 可能未定义
```

用 `.env` 文件管理，借 `dotenv` 加载：

```bash
# .env（不要提交 Git！可能含数据库密码、API Key）
NODE_ENV=development
PORT=3000
DB_HOST=localhost
DB_PASSWORD=mysecret
```

> 示意片段（无配套脚本）

```js
require('dotenv').config()
console.log(process.env.DB_HOST) // 'localhost'
```

**为何不提交 `.env`？** 它常含密钥，提交等于公开密码；正确做法是 `.env.example` 进仓库、真实 `.env` 进 `.gitignore`。`NODE_ENV` 的通行用法：`development` 开调试、`production` 关调试走优化，很多库都读它决定行为。

`os` 模块提供机器信息，和多进程决策呼应：

> 示意片段（无配套脚本）

```js
const os = require('node:os')
os.cpus()                 // CPU 核心数组（看核数）
os.totalmem()             // 总内存（字节）
os.availableParallelism() // Node 推荐的并行 worker 数（cluster/fork 用它）
os.homedir()              // 当前用户主目录
os.tmpdir()               // 系统临时目录
```

`os.availableParallelism()` 正是 `cluster` 一节决定开几个 Worker 的依据，比硬编码 `os.cpus().length` 更贴合 Node 调度建议。
