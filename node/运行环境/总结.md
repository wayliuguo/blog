# 模块总结 · 运行环境

## 知识主线

七篇不是并列的知识点，而是一条有依赖关系的链，每一篇都在回答上一篇留下的问题：

```
01 Node.js 是什么（跑的是什么、为什么适合）
        │  先算清"耗时绝大部分是等待"，才知道后面所有机制在优化什么
        ▼
02 模块系统与包管理（代码怎么组织）
        │  文件不能互相引用、依赖装不进来，后面任何机制都跑不起来
        ▼
03 事件循环：六个阶段与微任务  ★主轴
        │  先知道"机器怎么转"（六个阶段、内核就绪通知），
        │  再知道"顺序怎么定"（两条微任务队列、检查点）——两半合起来才是一台完整的机器；
        │  机器转明白了，下一个问题是：代码怎么写才既并发又不卡？
        ▼
04 异步编程与事件驱动
        │  异步搬运的到底是什么？——不是变量，而是字节流
        ▼
05 Buffer 与 Stream
        │  I/O 模型讲到头，单线程算力到顶、还要故障隔离，怎么办？
        ▼
06 进程、线程与优雅退出
        │  单点机制都通了，最后要放回同一张架构图与决策模型里收口
        ▼
07 运行机制收束（收口、误区清单与自测）
```

本模块的主轴是**事件循环**：01 说明它为什么值得存在，02 决定代码怎么进 V8，03 把它的六个阶段与微任务机制一次讲完，04 讲在它之上怎么写代码，05 讲它搬运的字节长什么样，06 讲它不够用时怎么往外扩，07 把它放回架构图收口。

## 分篇知识点

### 01-Node.js 是什么

- **Node 的定位与结构**
  - 定位：JavaScript 的运行环境，不是语言也不是后端框架；V8 只负责执行 JS，fs/http/crypto 等服务端能力是 Node 在 V8 之外补的
  - 四层：你的代码 → V8（执行 JS）→ Bindings（翻译为底层调用）→ libuv（事件循环 + 线程池）→ OS（epoll / kqueue / IOCP）
- **I/O 密集型**：一次请求两三秒，CPU 真正只算几毫秒，其余全是等数据库、网络、外部服务的等待——这是 Node 擅长它的根因
- **并发模型：阻塞 vs 非阻塞**
  1. 阻塞：主线程"等完才走"，A 在等待时 B/C 被堵在后面
  2. 非阻塞：发起 I/O 后转去处理别的请求，完成再由事件循环执行回调
  3. 锚点：Node 强在"等待时不闲着"，不是"算得快"；高并发是"不让主线程等"
- **适用边界**
  - 适合：Web/API、BFF 聚合、CLI、实时推送——共同点都是等待占比高
  - 不适合：CPU 密集（编解码、大 JSON.parse），会占住主线程让事件循环转不动
- **三个常见误区**
  1. "单线程"只指 JS 主线程，libuv 另有线程池（默认 4）处理文件 I/O、DNS、crypto
  2. "什么都适合"：弱项是算得重，CPU 密集应交给 Worker Thread 或子进程
  3. "就是后端框架"：运行环境只提供运行时/事件循环/系统 API，架构由 Express/Koa/NestJS 定义
- **版本基准**：装 LTS，结论以 Node 20+ 为准（libuv 1.45 改了 timers 时机，旧教程可能失准）


### 02-模块系统与包管理

- **模块系统要解决三件事**：怎么导出、怎么导入、拿到的到底是值还是引用
- **模块系统的本质区别（CJS 与 ESM）**
  1. **解析时机**：`import` 在求值前先扫描全部 import 建出依赖图（静态）；`require` 是运行时同步加载
  2. **值的语义**：`require` 拿到的是值的拷贝（快照），导出方之后再改也看不见；`import` 是活绑定（live binding），导出方改变量、导入方立刻可见
  3. **加载方式**：`require` 同步阻塞；`import()` 立刻返回 Promise，只把求值挂到后续调度
  4. **写法约束**：`import` 必须写顶层、不能条件化、不能拼路径，路径要带扩展名；代价换来 Tree Shaking
  5. **互操作**：ESM 引 CJS 直接 `import pkg from 'cjs-pkg'`；CJS 引 ESM 在 Node 22 起可直接 `require()`（限同步求值的 ESM，旧版本抛 `ERR_REQUIRE_ESM`），含顶层 `await` 的仍只能走动态 `import()`
- **模块类型怎么判定**
  - **两条规则**：`.cjs` 永远是 CommonJS、`.mjs` 永远是 ESM（后缀优先）；其余 `.js` 看最近的 `package.json` 的 `type` 字段
- **模块缓存与循环依赖**
  - **缓存**：`require.cache` 命中后不再读文件、不再执行顶层代码，两次 require 是同一个对象
  - **循环依赖**：模块执行到一半就把 `module.exports` 交出去缓存，所以可能拿到半成品
- **`exports` 与 `module.exports` 的陷阱**
  - `exports` 只是 `module.exports` 的初始引用，整体重新赋值 `module.exports` 后，挂在 `exports` 上的属性外界都拿不到
- **工程组织**
  - **目录拆分**：按 controllers / services / models / utils / config 分层
  - **npm 依赖分类与 scripts**：dependencies 是运行时必需、devDependencies 只在开发期，`npm install --production` 只装前者；脚本去 `node_modules/.bin` 找可执行文件
  - **语义化版本与锁文件**：`^4.18.0` 允许 4.x.x 会漂移，`~4.18.0` 只允许 4.18.x；`package-lock.json` 钉死实际版本与哈希，CI 用 `npm ci`
  - **`node_modules` 扁平化与查找算法**：npm v3 起把二三级依赖提升到顶层；require 从当前目录逐级向上找 node_modules，全没有抛 `MODULE_NOT_FOUND`


### 03-事件循环：六个阶段与微任务

- **单线程与事件循环的收益**
  - "单线程"只指执行 JS 的主线程，进程内还有 libuv 线程池与 OS 网络 I/O
  - 发起 I/O 后不等待、转去处理别的请求，结果回来再回调——慢查询不会卡住后面的请求
  - 适合 I/O 密集（万级连接只占一个 JS 线程，poll 阻塞等内核通知）；CPU 密集会占住主线程、事件循环转不动
- **六个阶段的固定轮转**
  1. timers：setTimeout / setInterval 到期回调
  2. pending callbacks：推迟到下一轮的系统级 I/O 回调
  3. idle / prepare：libuv 内部用，日常碰不到
  4. poll：I/O 事件处理核心
  5. check：setImmediate 回调
  6. close callbacks：资源关闭回调
  - 每进入一个阶段就把该队列一次性执行完，再进下一阶段
- **timers：setTimeout 是"资格"不是"保证"**
  - 只保证至少 N ms 后才"有资格"执行，能否真执行还要等主线程空闲
  - Node 20 / libuv 1.45 把 timer 主要挪到 poll 之后，旧"定时器先跑"推论失效；看文章先确认对应 Node 版本
- **poll 与 check：I/O 回调内时序才稳定**
  - poll 向内核问哪些 socket/文件就绪并执行其回调；无定时器、无 setImmediate 时阻塞等新 I/O
  - check 定义上紧跟 poll 之后；主模块里 setTimeout(0) 与 setImmediate 顺序不定，写在 I/O 回调里稳定为 setImmediate 先
- **close callbacks 入口很窄**
  - 判定看 handle 而非事件名：只有经历 uv_close 的真实 socket 销毁才落此阶段
  - 反例：无活跃连接时 net.Server.close() 改用 process.nextTick 派发 'close'，不进此阶段
- **网络 I/O 不进线程池，fs/dns/crypto/zlib 才进**
  - 网络 I/O 注册给 epoll/kqueue/IOCP，由内核通知就绪，一个线程管万级连接
  - 线程池默认 4 个（UV_THREADPOOL_SIZE 可调、上限 1024），且四类共用同一池——给 crypto 开满会挤占 fs 并发
- **两条微任务队列与检查点**
  - 队列：process.nextTick（不属于任何 phase）与 Promise 微任务队列
  - 同步代码永远先跑完；同一检查点内 nextTick 先于 Promise
  - 检查点在每个 JS 回调返回调度层时触发（非整轮一次）；递归 nextTick 饿死事件循环（I/O starvation），需让出执行权时用 setImmediate
- **输出顺序推演四步法**
  1. 划出同步代码：不在回调里的 console.log 按书写顺序最先打印
  2. 标出每个回调返回处的微任务检查点
  3. 同一检查点内 nextTick 优先于 Promise
  4. 微任务清空后才轮到下一阶段宏任务


### 04-异步编程与事件驱动

- **异步写法三次变革：Callback → Promise → async/await**
  - 层层包裹而非替代：async/await 建在 Promise 上，Promise 把 Callback 嵌套拍平；理解这条链才知道每层解掉什么痛点
- **Callback：error-first 与回调地狱**
  - 约定：回调第一个参数永远是 error，调用方必须先判 err 再继续
  - 真问题不是缩进深：错误分散（每层手写 if(err)，漏一层就被吞）、主流程被埋
- **Promise：三态不可逆 + 链式语义**
  - pending → fulfilled / rejected 一旦终态就锁死不可变
  - .then 回传 Promise 自动展开拍平嵌套；.catch 捕获整条链任意拒绝；.then 内 throw 自动转 rejected
- **async/await 只是"看起来"同步**
  - await 只把当前 async 函数"后面部分"挂成微任务，挂起期间主线程立刻腾出来处理别的回调/请求
  - 底层非阻塞 I/O 本质没变：它是在"这里插书签，好了再回来"，不是"程序停在这行"
- **并发编排：无依赖就并行**
  - await 默认串行：三个无依赖任务逐个 await 总耗时相加
  - 判断准则：两个 await 间无数据依赖就用 Promise.all；四组合器——all 快速失败 / allSettled 永不整体失败 / race 谁先落定（加超时）/ any 谁先成功（多镜像取最快）
- **EventEmitter：事件驱动骨架**
  - 解决"一个源头不断吐出多个事件"（Promise 只等一个结果）
  - 核心四步：注册 → 等待 → 触发 → 执行；on/emit 同步调用所有监听器
  - 是 net.Server / http.Server / fs.ReadStream / process 的基类
  - 两坑：'error' 无监听器会崩进程（uncaughtException）；监听器泄漏（默认超 10 告警，on 不 off 或循环反复 on）
- **事件驱动解耦"执行"与"观测"**
  - 主流程只在关键节点 emit，无需知道外面挂了多少监听器；日志/监控/告警各自 on，互不影响
  - 新增埋点/审计只在外部再加一个 on，业务主流程一行不改


### 05-Buffer 与 Stream

- **Buffer：固定长度的字节序列，字节本身无编码**
  - Node 4+ 的 Buffer 是 Uint8Array 子类（buf instanceof Uint8Array 为 true），能与整个 TypedArray 体系互操作
  - 同一段字节用 utf8/hex/base64 解读得到不同字符串——这正是 Buffer.from(str) 与 buf.toString() 成对出现的原因
  - alloc(n) 清零分配（待填充缓冲）；from(x) 从已有数据编码、不清零；别用未清零的旧 Buffer(size)，会泄漏堆上旧数据
- **字符长度 ≠ 字节长度（Content-Length 的坑）**
  - '你好'.length 是 2，Buffer.from('你好').length 是 6（UTF-8 每汉字 3 字节）
  - 算响应头 Content-Length、切二进制帧、限上传体积必须用 Buffer.length（字节），否则长度算小、下游截断错乱
- **Buffer 的五个典型场景**
  1. 文件读取（readFile 不指定 encoding 拿到 Buffer）
  2. TCP socket 的 data 事件（原始字节 chunk）
  3. 图片/音频/视频（本质二进制字节流）
  4. 加密（明文/密文都是 Buffer）
  5. Base64 编解码（把二进制塞进只认文本的协议）
- **Stream：一块一块搬，与 Buffer 是"水桶 vs 水管"**
  - readFile 读 10GB 整文件进内存会 OOM；Stream 一次只搬一小块（通常 64KB），内存恒定几十 KB~几 MB
  - Buffer 是"一桶水"，Stream 是"水管"——没有 Buffer 没东西运，没有 Stream 只能整块堆内存
- **四种 Stream**
  1. Readable：只生产（on('data')/read()/for await），pipe 返回目标流可链式
  2. Writable：只消费，write() 返 false 表示缓冲满须暂停上游，end() 后再 write 报 ERR_STREAM_WRITE_AFTER_END
  3. Duplex：双向（典型 TCP socket），allowHalfOpen 默认值不统一（new Duplex 是 true，net socket 是 false）
  4. Transform：Duplex+转换（gzip/加解密），实现 transform()+flush()，objectMode 时 chunk 可是任意 JS 值
- **工程实践：复制、背压、pipe / pipeline**
  - 复制大文件必须 Stream：readFile+writeFile 整文件进内存 OOM；pipe 数据 Disk→Buffer→Stream→Disk，内存恒定
  - 背压：write() 返 false 表示缓冲达上限应暂停读取，降下来触发 'drain' 再 resume（可观测 writableLength / writableNeedDrain / readableLength）
  - highWaterMark 两侧不同：createReadStream 64KB、createWriteStream 16KB；手写 pause/resume 易错，直接用 pipe/pipeline
  - pipe 出错不销毁上游（可能留悬挂流/FD）；pipeline 任意环出错统一销毁所有流并抛错，还能串联多个 Transform——简单搬运用 pipe，长链路/需错误兜底用 pipeline
- **流式推送为什么必须用 Stream**
  - 日志流/进度/大文件/实时数据这类持续产生的数据，先拼成大字符串再一次性返回会让客户端干等、服务端内存被撑
  - 把数据源做成 Readable 边产生边推，res 本身是 Writable，stream.pipe(res) 即可，别提前设 Content-Length（交给 chunked）
- **落地 fs 与 path**
  - fs 三风格：回调版（易嵌套）/ fs.promises（配 async/await，主流）/ *Sync（阻塞事件循环，只适合启动初始化、CLI）
  - 拼路径永远用 path.join（跨平台）；path.resolve 遇绝对路径停下并解析成基于 cwd 的绝对路径——只需拼路径用 join，要从项目根出发才用 resolve


### 06-进程线程与优雅退出

- **进程本质与观测**
  - node app.js 起一个进程：独立内存空间、一个 V8、一块堆、一个事件循环、一组 FD
  - 用全局 process 观测：pid / uptime / argv（argv[0]=node, argv[1]=脚本）/ memoryUsage（rss 物理内存、heapUsed JS 堆）
  - rss 常远大于 heapUsed：Buffer、线程栈等都算进 rss，"JS 对象不多内存却很大"是常态
- **child_process 四把刀**
  1. spawn：不走 shell、输出走流，适合长运行/大输出；stdio:'inherit' 共用父 IO，detached+unref 可脱离父进程独立跑
  2. exec：走 shell、输出全缓冲后回调，适合短命令；输出特大会撑爆 maxBuffer（默认 1MB）
  3. execFile：不经 shell 直接执行文件，无 shell 注入面、更安全
  4. fork：专门建 Node 子进程并建 IPC 通道，用 send()/on('message') 通信
  - 口诀：流式大输出 spawn；短命令拼 shell exec；跑文件不要 shell execFile；跑 Node 通信用 fork
- **单进程吃不满多核，cluster 的正确定位**
  - 多核要开多进程各占一核；cluster 让 Primary fork 多个共享同端口的 Worker，由 OS/Primary 分发，Worker 数取 os.availableParallelism()，exit 里崩一个补一个
  - 官方提醒：不需进程级隔离应优先 worker_threads（同实例共享内存、成本更低）；cluster 的真正价值是进程级故障隔离 + 多核部署
- **进程 vs 线程的内存模型**
  - 进程内存默认不共享，通信只能借 IPC/Socket/Redis/MQ/HTTP
  - 线程共享进程部分内存、通信成本低，代价是竞态条件
  - Worker 可用 SharedArrayBuffer 共享内存但并发安全自己管；进程隔离性强、创建成本高、只能 IPC、能跑外部程序
- **worker_threads：CPU 密集的归处，要池化**
  - 同进程内开 JS 线程：主线程 postMessage 派活、Worker 用 parentPort 回结果，各有独立 V8
  - 适合 CPU 密集 JS（图片/视频处理、大 JSON、压缩、哈希）；I/O 密集交给 Event Loop，别丢给 Worker
  - 不等于 libuv 线程池：后者是 Node 内部维护替你跑 fs/dns/crypto/zlib 的底层阻塞操作，前者是你 new Worker 主动建、跑你写的 JS
  - 不要每请求 new Worker（1 万并发=1 万 Worker，创建调度成新瓶颈）；正确做法 Worker Pool + Task Queue（固定≈核数、空闲才派、超额排队、Promise 包装）
  - SharedArrayBuffer 共享内存须用 Atomics.add，否则并发 ++ 非原子丢更新
- **四种并发方式选型**
  1. HTTP/DB/Redis/外部 API → Event Loop（异步 I/O）
  2. CPU 密集 JS → worker_threads（配 Pool）
  3. 强隔离/跑外部程序/执行 shell → child_process
  4. 多实例铺满多核 + 进程级故障隔离 → 多进程（cluster/容器编排 + 负载均衡）
- **优雅关闭与错误分层兜底**
  - 优雅关闭：收 SIGTERM 停收新连接（server.close + closeIdleConnections）→ 等在途请求（10s 超时兜底）→ 关 DB/Redis/MQ → exit(0)；SIGINT 是 Ctrl+C，本地必碰
  - 别滥用 process.exit()：立即终止会丢未写完的 stdout/日志/事务/响应；生产掌握 exitCode + Graceful Shutdown + Signal Handling 三件事
  - 错误分层接住：同步 try/catch、回调判首参 err、Promise .catch、入口外层包 try/catch；漏到进程级用 uncaughtException/unhandledRejection 做最后清理
  - uncaughtException 之后不推荐继续运行（内部状态已不可信），应记日志 + 优雅退出，交 PM2/K8s 拉起干净新进程
  - 判断错误种类用 error.code（ENOENT/EADDRINUSE/ECONNRESET）与 error.name（TypeError/RangeError）
- **环境变量与 os**
  - process.env 读环境变量、存敏感配置；.env 不提交 Git（含密码/Key），进仓库用 .env.example + .gitignore；NODE_ENV 控制调试/优化
  - os 看机器信息：cpus/totalmem/availableParallelism（Node 推荐并行 worker 数，比 os.cpus().length 更贴合调度）/homedir/tmpdir


### 07-运行机制收束

- **完整架构的三条主线**：网络 I/O 走内核 epoll/kqueue/IOCP 不进线程池；fs/crypto/dns/zlib 走 libuv 线程池；你写的 JS 只在主线程的 V8 里跑
- **主动创建的两类并发结构**：同进程内的 Worker Thread（可共享 SharedArrayBuffer）与独立 Child Process（内存不共享，靠 IPC/Socket）
- **七篇在架构图上的位置**：模块系统决定代码怎么进 V8，事件循环与微任务决定主线程怎么转，Buffer/Stream 决定数据怎么流，进程线程是主动扩出的并发
- **抽象栈定位**：模块一讲的全是"进程内"的事，业务代码与框架在上、Event Loop + libuv + 内核在下，排障时从现象所在层往相邻层递推
- **决策模型的第一反应**：见"卡 / 慢 / 顺序乱 / 内存涨"先问"事件循环是不是被占住了、数据流有没有背压"，再决定换异步、上 Stream，还是丢给线程/进程
- **六条误区清单**：单线程、所有异步都在线程池、await 阻塞事件循环、worker_threads 就是线程池、nextTick 越多越快、多开进程就能变快
- **自测 6 问**：覆盖 01~08，能答上（一次请求 CPU 真算多久、require 与 import、六个阶段、nextTick 与 Promise、await 写成串行、进程不退出漏了什么）说明模块一过关
- **交接模块二**：进程内 I/O 模型收口，接下来要回答"这些 I/O 从哪来"——HTTP/TCP/WebSocket 的本质是跨机器交换字节

## 见 X 想 Y

| --- | --- | --- |
| 接口慢、一次请求两三秒 | I/O 密集型，等的是别人 | CPU 真正执行只有几毫秒，别急着加机器 |
| 响应顺序不符合预期 | 微任务检查点（nextTick vs Promise） | 每个回调返回调度层都清一次，同检查点内 nextTick 先于 Promise |
| CPU 打满但 QPS 很低 | 主线程被同步长任务占住 | 事件循环转不动，I/O 回调全在排队 |

| 大文件读写、上传下载、日志推送 | Stream + 背压 | 一次读进内存会撑爆堆，createReadStream + pipe 内存恒定 |
| 内存一路涨最后 OOM | 背压没做 / 事件监听器泄漏 | write() 返回 false 没暂停，或 on 了不 off |
| 压缩、加密、大 JSON 解析 | Worker Thread（走线程池） | CPU 密集会占住唯一的 JS 线程，丢到 Worker 才不卡 |
| 调 ffmpeg / python 脚本 / 系统命令 | child_process（spawn / execFile） | 这是别的程序，得起独立进程去跑 |
| 用不满多核、要故障隔离 | 多进程（cluster / 进程管理） | 一个 Node 进程只用一个核，崩一个不影响其他 |
| 服务重启丢请求 | SIGTERM 优雅关闭 | 先停收新请求、等存量请求跑完再退出，别硬切连接 |
| 进程不退出 | 未清理的句柄 + 优雅关闭 | server / timer / 长连接没 close，句柄清空进程才自然退出 |

| "在我机器上能跑" | 锁文件没提交或版本范围漂移 | package.json 写的是 `^` 范围，靠 package-lock.json 钉死 |

## 易错点汇总

- **"Node.js 是单线程的"／"所有异步操作都在线程池里跑"**：只有执行 JS 的主线程是单线程。网络 I/O 走内核 epoll/kqueue/IOCP 通知，不进线程池；只有 fs、部分 DNS、crypto、zlib 才进 libuv 线程池，而且它们共用同一组默认 4 个线程。
- **"setTimeout(fn, 1000) 就是 1000ms 后执行"**：它是"至少 1000ms 后才有资格执行"，还要等主线程空闲。主线程被 while 阻塞 3 秒，这个回调就 3 秒后才跑。它是最小等待时间，不是精确执行时间。
- **"微任务是一整轮 Event Loop 之后才清一次"**：每个 JS 回调返回调度层都是一次微任务检查点。所以同一轮 timers 里的两个 setTimeout 输出是 `timer1 → promise → timer2`，而不是 `timer1 → timer2 → promise`。
- **"process.nextTick 用得越多越快"**：nextTick 队列要一直清空到空，在回调里递归注册会让它永远清不完，事件循环进不了 poll/timers/check，造成 I/O 饥饿。需要让出执行权又不想饿死循环时，用 setImmediate。
- **"await 会阻塞事件循环"**：await 只暂停当前 async 函数的后半段并挂成微任务，主线程立刻去处理别的回调。真正的坑是"两个互不依赖的 await 写成串行"，本该 500ms 的活儿变成 700ms。
- **"重新赋值 module.exports 后，再挂 exports.xxx 也生效"**：`exports` 只是 `module.exports` 的初始引用，一旦整体替换 `module.exports`，挂在旧 `exports` 上的属性外界全拿不到。整体替换用 `module.exports`，增量挂属性用 `exports.xxx`。
- **"UV_THREADPOOL_SIZE 可以运行时改、每个模块各有一个池"**：libuv 在进程启动时一次性读取并创建线程，运行时改 `process.env.UV_THREADPOOL_SIZE` 无效。而且 fs、DNS、crypto、zlib 抢的是同一组线程，给 crypto 开满会挤占 fs。
- **"字符串长度等于字节长度"**：`'你好'.length` 是 2，`Buffer.from('你好').length` 是 6。算 Content-Length 或切分二进制协议帧时用字符数会让长度算小，下游按错误长度截断，数据全乱。
- **"有 pipe 就够了，不需要 pipeline"**：pipe 只协调背压，下游出错时不会销毁上游，容易留下没释放的文件描述符与 Socket。链路长、要错误兜底、要串多个 Transform 时用 pipeline，它出错统一销毁整条链路。
- **"worker_threads 就是 libuv 线程池"／"每请求 new 一个 Worker"**：前者是你主动 `new`、有独立 V8 跑你的 JS，后者是 Node 内部跑 fs/dns/crypto/zlib 的系统线程。生产环境每请求 new 一个 Worker，1 万并发就是 1 万个线程，应该用 Worker Pool + Task Queue。
- **"emit('error') 没监听器顶多报个错"**：EventEmitter 对 error 事件有特殊处理，没有监听器会直接抛 uncaughtException 让进程退出。同理 on 了不 off 会触发 MaxListenersExceededWarning（默认上限 10），且闭包引用的对象无法回收、内存缓慢上涨。
- **"多开进程就能变快"／"process.exit(1) 很干脆"**：多开进程只对 CPU 密集或要故障隔离的场景成立，I/O 密集的瓶颈是等待，多开只是多占内存。`process.exit()` 会立即终止，stdout 没写完、日志没发出、事务没提交、响应没结束都可能发生。

## 与相邻模块的接口

**进入本模块前必须已经掌握**：这是整套体系的起点，没有前置依赖。只要会写 JavaScript（变量、函数、对象、class、Promise）、能在终端敲命令就够了。Node 的 fs / http / crypto 这些服务端能力从哪来，本模块会从头讲起。

**本模块交给下一模块什么**：本模块产出的是"进程内"的完整 I/O 模型——事件循环为什么能扛并发、异步怎么写、字节流怎么搬、单线程不够时怎么用进程与线程分流。下一模块要靠它回答一个一直悬着的问题：**这些 I/O 到底是从哪来的**。HTTP 请求、TCP 连接、WebSocket 推送本质都是"通过网卡与另一台机器交换字节"，而 Socket 就是一条 Duplex Stream、HTTP body 就是 Stream 在搬运 Buffer。
