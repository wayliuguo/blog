## 1. Node 运行时与适用边界

### 1.1 Node 的定位与四层结构

Node.js 是 JavaScript 的**运行环境**，不是一门新语言，也不是后端框架。它基于 Chrome 的 V8 引擎，把只能跑在浏览器里的 JS 带到服务端：V8 只负责执行 JS，`fs` / `http` / `net` / `crypto` 等服务端能力由 Node 在 V8 之外补齐。一个 Node 进程从代码到硬件至少穿过四层：

```
你的代码（JavaScript）
   │
   ▼
V8 引擎（解析 / JIT / 执行 JS / GC）
   │
   ▼
Node.js Bindings（把 JS 调用翻译成底层能力）
   │
   ▼
libuv（事件循环 + 线程池 + 定时器 + 跨平台异步 I/O）
   │
   ▼
操作系统（真正执行 I/O：epoll / kqueue / IOCP）
```

- **V8**：只负责把 JS 跑起来，并不知道 `fs.readFile` 是什么。
- **Node Bindings**：把 JS 调用桥接到 C/C++ 底层。
- **libuv**：Node 异步能力的底座，管事件循环、线程池、定时器、跨平台 I/O 封装。
- **操作系统**：Linux 用 `epoll`、macOS/BSD 用 `kqueue`、Windows 用 `IOCP`。

语言 / 运行环境 / 引擎三者区分：JavaScript/TypeScript 是语言，Node.js 是运行环境，V8 是底层引擎（与 Chrome 同款）。结论以 **Node 20+ 为准**：Node 20（libuv 1.45）调整了 timers 时机，老教程可能失准。

### 1.2 I/O 密集与耗时账

**I/O 密集型服务**指一次请求中 CPU 真实计算时间极短、绝大部分耗时来自磁盘 / 网络 / 外部服务等待的服务。聚合网关、BFF、接口编排、实时推送天然就是这种形态。

一次"获取首页信息流"请求约 2~3 秒，真正执行业务 JS 只有几毫秒，其余都在等：

```
查询 MySQL 30ms → 聚合下游 100ms → 请求第三方 API 2000ms → 查询 Redis 5ms → 写库 30ms
```

- 实测（`npm run 01`）：总墙上时间约 2500ms，CPU 实际占用仅 16ms（约 2.5%）。
- **这是 Node 适合后端服务、也是它高并发能力的根因**——等待占绝大多数。

### 1.3 并发模型：阻塞 vs 非阻塞

并发能力取决于如何组织"等待"，而不是如何算得快：

- **阻塞模型**：主线程"等完才走"，A 等待时 B/C 被堵在后面，CPU 在等待窗口空转。
- **非阻塞模型**：发起 I/O 后立刻转去处理别的请求，I/O 就绪由内核通知，事件循环再回来执行回调。

```
阻塞：  处理 A → 等 2000ms → 处理 B → 等 50ms → 处理 C → 等 5ms
非阻塞：处理 A → 发起后不等 → 处理 B → 处理 C → 某个 I/O 完成 → 执行对应回调
```

锚点是：**Node.js 擅长的不是"算得快"，而是"等待的时候不闲着"**。高并发靠"不让主线程等"，等待本身无法消除，只是被挪到了内核与线程池。

### 1.4 适用边界与常见误区

| 适合（等待占比高） | 不适合（CPU 密集） |
| --- | --- |
| Web / API、BFF 聚合、CLI、实时推送 | 大数运算、图像/视频编解码、复杂加密压缩、超大 `JSON.parse` |

CPU 密集任务会占住唯一的主线程、让事件循环转不动，应交给 Worker Thread 或子进程。

三个常见误区：

1. **"单线程"** 只指执行 JS 的**主线程**；进程内还有 libuv 线程池（默认 4）处理文件 I/O、DNS、crypto。准确说法是"单线程执行 JS + 多线程处理底层 I/O"。
2. **"什么都适合"**：弱项是算得重，浪费在 CPU 密集是不对的。
3. **"就是后端框架"**：运行环境只提供运行时 / 事件循环 / 系统 API，架构由 Express / Koa / NestJS 定义。

成本清单：CPU 密集拖垮服务、同步 API 破坏"不闲着"、异步心智成本（易写并发写成串行）。

## 2. 模块系统与包管理

模块系统解决三件事：怎么导出、怎么导入、拿到的到底是值还是引用。Node 有两套并存方案：CommonJS（`.js` / `.cjs`，早期自带）与 ES Module（`.mjs` / 配 `type` 的 `.js`，语言标准）。

### 2.1 CommonJS：导出与缓存

用 `require` 导入、`module.exports` 导出，拿到的是 **module.exports 对象本身**（同一路径多次 require 拿同一个引用）。

- **模块缓存**：同一文件在本进程内只求值一次，`require.cache` 命中后不再读文件、不再跑顶层代码；模块顶层的副作用（连库、起定时器）只在首次 require 触发。
- **循环依赖**：模块执行到一半就把当前 `module.exports` 交出去缓存，所以可能拿到"还没初始化完"的半成品。
- **`exports` 与 `module.exports`**：最终被导出的一定是 `module.exports`，`exports` 只是它的初始引用（`exports === module.exports` 初为 true）。

铁律：整体替换导出对象用 `module.exports = {...}`；增量挂属性用 `exports.xxx` 且之后不要再重赋值 `module.exports`。

```
exports === module.exports   （初为 true，挂属性=给同一对象挂）
module.exports = {...}       （整体替换后，之后挂的 exports.xxx 外界拿不到）
exports = {...}              （只改局部变量，module.exports 没动，外界拿到空对象）
```

### 2.2 ES Module：静态结构与活绑定

用 `import` / `export`（命名导出 + 默认导出）描述依赖，路径通常要带扩展名。ESM 是**静态结构**：求值前先扫描所有 import 建立依赖图，再按依赖顺序实例化、才执行模块体。

```
文件被加载 → ① 静态扫描 import 建依赖图（编译期）→ ② 按依赖顺序实例化绑定 → ③ 执行模块体
```

由此产生的约束与收益：

- **写法约束**：`import` 只能写顶层、不能条件化、不能拼路径、路径带扩展名（静态可分析的代价）。
- **活绑定（live binding）**：导出的绑定与模块内部同一个，导出方一改、所有导入方立刻同步（区别于 CJS 的值拷贝快照）。
- **Tree Shaking**：导出是静态语法，打包器能精确删掉没用到的导出；CJS 运行时才知依赖、无法静态证明某个导出没用，只能全保留。
- **顶层 `await`**：模块顶层可以直接 `await`，整个模块及其导入方都会等它完成，适合启动时连库、读配置。

### 2.3 模块判定、解析与互操作

同一份 `.js` 按哪套解析，决定权分两级，**后缀优先**：

1. `.cjs` 永远 CommonJS、`.mjs` 永远 ESM（后缀说了算）。
2. 其余 `.js` 看最近的 `package.json` 的 `"type"` 字段："module" 整包按 ESM，不写或 commonjs 则默认 CJS。

`require` 与 `import` 的四个本质区别：

| 维度 | `require`（CJS） | `import`（ESM） |
| --- | --- | --- |
| 解析时机 | 运行时同步解析，可进 `if`、可拼路径 | 编译期静态分析，建好依赖图 |
| 值的语义 | 值的拷贝（快照），导出方改后外部看不到 | 活绑定，外部实时同步 |
| 加载方式 | 同步阻塞，无顶层 await | 异步加载（`import()` 返回 Promise），支持顶层 await |
| Tree Shaking | 运行时才知道，全保留 | 静态可分析，能精确删除 |

互操作不对称：**ESM 引 CJS** 直接 `import pkg from 'cjs-pkg'`，Node 把 `module.exports` 包成默认导出；**CJS 引 ESM** 在 Node 22 起可直接 `require()`（限同步求值的 ESM，旧版本抛 `ERR_REQUIRE_ESM`），**含顶层 `await` 的 ESM 任何版本都不能 require**（同步等不了异步求值），只能走动态 `import()`——它是两套系统的"桥"，也是渐进迁移老项目的推荐手段。

### 2.4 npm 依赖管理与版本锁

- **依赖分类**：`dependencies` 是运行时必需，`devDependencies` 只在开发期；`npm install --production` 只装前者。scripts 去 `node_modules/.bin` 找可执行文件，本地 CLI 不用写全局路径。
- **语义化版本**：`^4.18.0` 允许 4.x.x 会跨次版本漂移，`~4.18.0` 只允许 4.18.x，精确写死最严；`-beta`/`-rc` 预发布标签默认被 `^` `~` 排除。
- **锁文件**：`package.json` 是范围、会漂移；`package-lock.json` 记录实际每一层依赖的精确版本与内容哈希，把整棵树钉死，可复现构建、加快安装，CI 用 `npm ci`。必须提交锁文件。
- **`node_modules` 查找与扁平化**：npm v3 起把二三级依赖提升到顶层复用（有版本冲突才降级）；`require('lodash')` 从当前目录**逐级向上**找 node_modules，全没有抛 `MODULE_NOT_FOUND`。`node_modules` 应写进 `.gitignore`。

## 3. 事件循环与微任务

### 3.1 单线程与事件循环的收益

"单线程"只指执行 JS 的主线程；进程内还有 libuv 线程池和内核层面的网络 I/O。事件循环的收益是：**发起 I/O 后不等待，转去处理别的请求，I/O 就绪由内核通知、再执行回调**——慢查询不会卡住后面的请求。适合 I/O 密集（万级连接只占一个 JS 线程，poll 阻塞等内核通知）；CPU 密集会占住主线程、事件循环转不动。

### 3.2 六个阶段轮转

事件循环是**一串有固定顺序的阶段**，每个阶段是一个回调队列；每进入一个阶段把该队列执行完、再进下一阶段：

```
┌──────────────┐
│    timers    │  setTimeout / setInterval 到期回调
└──────┬───────┘
       ▼
│ pending callbacks │  推迟到下一轮的系统级 I/O 回调
       ▼
│  idle / prepare   │  libuv 内部使用，日常碰不到
       ▼
│      poll         │  I/O 事件处理核心
       ▼
│      check        │  setImmediate 回调
       ▼
│  close callbacks  │  资源关闭回调
       └────── ► 下一轮
```

### 3.3 timers / poll / check / close

- **timers：`setTimeout(fn, 1000)` 是"最小等待时间"不是精确时间**——到期只代表回调"获得执行资格"，能否执行还要等主线程空闲；`setTimeout(0)` 同样不会立即执行（约 clamp 到 1ms）。
- **Node 20 / libuv 1.45 后 timer 时机变了**：旧"定时器先跑、本轮结束前再处理一次 Timer"的推论失效，现在 Timer 主要挪到 poll 之后。看事件循环文章先确认对应 Node 版本。
- **poll 是事件循环的核心**：向内核问哪些 socket/文件就绪并执行其 I/O 回调；无定时器也无 setImmediate 时阻塞等待新 I/O——这正是 Node"一直在线却几乎不占 CPU"的原因。
- **check 与 poll+check 时序**：check 定义上紧跟 poll 之后；主模块里 `setTimeout(0)` 与 `setImmediate` 顺序**不确定**（都排进下一轮、受启动耗时影响），写在 I/O 回调里则稳定为 `setImmediate` 先（当前在 poll → 紧接着 check → 下一轮才到 timers）。
- **close callbacks 入口很窄**：判定看 **handle 而非事件名**——只有真正经历 `uv_close` 的 socket 销毁才落此阶段；无活跃连接时 `net.Server.close()` 改用 `process.nextTick` 派发 `'close'`，不进此阶段。

### 3.4 网络 I/O 与 libuv 线程池

谁进池谁不进池，标准是"内核能否异步通知"：

```
OS 异步 I/O（内核通知，不开线程）        libuv Thread Pool（真正开线程）
  网络 / Socket / TCP / HTTP                File System（fs.readFile）
                                          DNS（dns.lookup）
                                          Crypto（pbkdf2 / scrypt）
                                          zlib（压缩/解压）
```

- **网络 I/O 不进线程池**：注册给 epoll / kqueue / IOCP，由内核在数据到达时通知，一个主线程管万级连接。
- **文件 / DNS / crypto / zlib 进线程池**：OS 无统一高效异步接口或本身偏阻塞/CPU 型。
- 线程池**默认 4 个**、`UV_THREADPOOL_SIZE` 可调、上限 1024；三坑：必须在**进程启动前**设置（运行时改 `process.env` 无效）、不是越大越好（上下文切换开销）、四类**共用同一池**（crypto 开满会挤占 fs 并发）。实测 10 个 pbkdf2 明显分"4 个一批"。

### 3.5 两条微任务队列与检查点

宏任务走六个阶段，微任务走另一套更靠前的机制，需要重点记两条独立队列：

- **`process.nextTick` 队列**：不属于任何阶段，在 Call Stack 清空后、事件循环继续前立刻处理，优先级比 Promise 微任务还高。
- **Promise 微任务队列**（`.then` / `.catch` / `.finally`）：排在 nextTick 之后，两条都清空到空才结束。

铁律：**同步代码永远先跑完**；同一检查点内 `nextTick` 先于 Promise。

微任务是**检查点（microtask checkpoint）触发，不是整轮一次**：每次 JS 回调返回 Node 调度层都可能触发一次，清空该回调新产生的微任务。最直观证据是 `timer1 → promise → timer2`——两个 setTimeout 同处 timers 阶段，timer1 回调返回时立刻清空它注册的 Promise，再执行 timer2。

```
当前 JS 回调完成 → Call Stack 清空 → 清空 nextTick 队列 → 清空 Promise 队列 → 进下一阶段
```

坑：递归调用 `process.nextTick` 会让队列永远清不空，**饿死事件循环（I/O starvation）**，timers/I/O 回调永远得不到执行；需要"让出执行权、下一轮再继续"时用 `setImmediate`。

### 3.6 输出顺序推演四步法

任何输出顺序题都按四步走：

1. **划同步代码**：不在回调里的 `console.log` 按书写顺序最先打印，异步 API 此刻只是注册。
2. **标检查点**：每执行完一个宏任务回调，在返回处记一个微任务检查点。
3. **先 nextTick 后 Promise**：同一检查点内清空 nextTick 队列，再清空 Promise 队列。
4. **再进下一阶段**：微任务清空后才轮到下一阶段的宏任务，循环到第 2 步。

经典：`console.log('start')` → `setTimeout`(注册) → `Promise.then`(注册) → `nextTick`(注册) → `console.log('end')` → Call Stack 清空 → `nextTick` → `promise` → `timeout`。

## 4. 异步编程与事件驱动

### 4.1 异步写法三次变革

```
Callback ──(解决嵌套地狱)──▶  Promise  ──(语法糖)──▶  async / await
```

三者**层层包裹而非替代**：async/await 建在 Promise 上、Promise 把 Callback 嵌套拍平。Callback 的真问题不是"缩进深"，而是**错误分散**（每层手写 `if (err)`，漏一层就被吞）与**主流程被埋**。

### 4.2 Promise 三态与链式语义

Promise 是"未来才有结果"的容器，**三态不可逆**：`pending`（初始）→ `fulfilled`（resolve）/ `rejected`（reject 或链中 throw），一旦落到终态就锁死。

链式语义：`.then` 回传 Promise 自动展开拍平嵌套；`.catch` 捕获整条链任意位置的拒绝；`.finally` 不论成败都执行（清理）；`.then` 里 `throw new Error` 自动转成 rejected。

### 4.3 async/await 与并发编排

**await 只是"看起来"同步，不阻塞事件循环**：它把当前 async 函数"后面部分"挂成微任务，挂起期间主线程立刻腾出来处理别的请求；底层非阻塞 I/O 本质没变。心智模型是"在这里插个书签、好了再回来"。

**await 的串行陷阱**：两个互不相干的 `await` 之间是串行的，延迟累加。

```
串行：taskA 100ms → taskB 100ms → taskC 500ms，总耗时 ≈ 700ms
并行（Promise.all）：三个同时出发，总耗时 ≈ 最慢的 500ms
```

判断准则：两个 await 间**无数据依赖就用 `Promise.all`**，否则会把能并发的任务写成串行（服务端端到端时延直接翻倍）。

并发四个工具：

| 方法 | 失败语义 | 典型场景 |
| --- | --- | --- |
| `Promise.all` | 任一失败即整体失败，其余结果被丢弃 | 步骤强依赖、全有或全无 |
| `Promise.allSettled` | 永不因失败而整体失败，逐项报 {status, value\|reason} | 部分失败可容忍、需逐个处理 |
| `Promise.race` | 第一个落定者（成功或失败）决定结果 | 竞速、加超时 |
| `Promise.any` | 全部失败才失败，返回第一个成功 | 多镜像取最快可用 |

### 4.4 EventEmitter 与事件驱动解耦

Promise 只"等一个结果"；**一个源头不断吐出多个事件**的场景用 EventEmitter。核心四步：**注册(on) → 等待 → 触发(emit) → 执行监听器**；`emit` 同步调用所有监听器。

它是大量内置对象的基类：`net.Server`、`http.Server`、`fs.ReadStream`、`process` 的原型链上都有它，所以你会写 `server.on('connection', ...)`、`req.on('data', ...)`。

两个实战坑：

- **`'error'` 无监听器会崩进程**：`emit('error')` 却没有监听器时直接 throw 成 `uncaughtException` 导致进程退出（有意为之的 fail-fast）。凡可能 `emit('error')` 的对象先挂 error 监听器。
- **监听器泄漏**：默认同一事件最多 10 个监听器，`on` 了不 `off` 或在循环里反复 `on` 会触发 `MaxListenersExceededWarning` 且内存缓慢上涨；一次性用 `once`，用 `listenerCount` 观测是否异常增长。

事件驱动解耦"执行"与"观测"：业务主流程只在关键节点 `emit`，日志 / 监控 / 告警各自 `on`，互不影响；新增埋点 / 审计只需外部再加一个 `on`，业务主流程一行不改。

## 5. 字节流与管道：Buffer 与 Stream

### 5.1 Buffer：固定长度字节序列

Buffer 是**固定长度的字节序列**，创建时容量定死；Node 4+ 的 Buffer 是 `Uint8Array` 子类，能与整个 TypedArray 体系互操作。

- **编码只是解读视角**：字节本身无编码，同一段字节用 `utf8` / `hex` / `base64` 解读得到不同字符串——这正是 `Buffer.from(str)` 与 `buf.toString()` 成对出现的原因。
- **`Buffer.alloc(n)` 清零分配**（待填充缓冲）；`Buffer.from(x)` 从已有数据编码、不清零；别用未清零的 `Buffer(size)` 旧写法（会残留堆上旧数据、泄漏敏感信息）。
- 五个典型场景：文件读取（不指定 encoding 即 Buffer）、TCP socket 的 data 事件（原始字节 chunk）、图片/音频/视频（二进制流）、加密（明文/密文都是 Buffer）、Base64 编解码（把二进制塞进只认文本的协议）。

### 5.2 字符长度 vs 字节长度

**字符长度 ≠ 字节长度**：`'你好'.length` 是 2，`Buffer.from('你好').length` 是 6（UTF-8 每汉字 3 字节）。

算 `Content-Length`、切二进制协议帧、限上传体积**必须用 `Buffer.length`（字节）**；用字符长度会把内容算小，下游按错误长度截断、数据错乱。

```
'中文abc'.length               → 5（字符数）
Buffer.from('中文abc').length  → 9（中 2×3 + 英 3×1 字节）
```

### 5.3 Stream：数据搬运与背压

**Buffer 是"一桶水"（一块数据），Stream 是"水管"（运输方式）**——没有 Buffer 没东西可运，没有 Stream 只能整块堆内存。`readFile` 读 10GB 会 OOM；Stream 一次只搬一小块（通常 64KB），内存恒定在几十 KB~几 MB。

```
10GB 文件 ──► 64KB ──► 网络 ──► 64KB ──► 网络 ──► …：内存恒定
```

四种 Stream：

| 能力\转换 | 不转换 | 转换 |
| --- | --- | --- |
| 单向 | `Readable`（只生产：on('data')/read()/for await，pipe 返回目标流可链式） | — |
| 双向 | `Duplex`（可读可写，典型 TCP socket；allowHalfOpen 默认值不统一：new Duplex 是 true、net socket 是 false） | `Transform`（Duplex+转换：gzip/加解密，实现 transform()+flush()） |

Writable 细节：`write()` 返回 `false` 表示缓冲满须暂停上游，`end()` 后再 write 报 `ERR_STREAM_WRITE_AFTER_END`；`objectMode: true` 时 chunk 可是任意 JS 值。

**背压（Backpressure）**：`write()` 返回 `false` 表示缓冲达 `highWaterMark` 上限、上游应暂停；消化完触发 `'drain'` 再恢复。可观测 `writableLength` / `writableNeedDrain` / `readableLength`。两侧 highWaterMark 不同：`createReadStream` 64KB、`createWriteStream` 16KB；阈值越小越省内存但系统调用更多。

```
Producer ── chunk ──► [Writable 缓冲] ──► Consumer
                        │ write() 返 false（缓冲顶到 highWaterMark）
                        ▼
                     Producer.pause() → 缓冲下降 → 'drain' → Producer.resume()
```

手写 pause/resume 易错，直接用 `pipe` / `pipeline`：

- **pipe**：内部自动协调背压与速度；短板是**下游出错不会自动销毁上游**（留悬挂流/FD）；返回目标流可 `.pipe()` 串链。
- **pipeline**（`node:stream/promises`）：任意一环出错统一销毁所有流并抛错，能串联多个 Transform（读→gzip→写）。
- 选型：**简单搬运用 pipe；长链路 / 需错误兜底 / 串多个转换用 pipeline**。

流式推送必须用 Stream：日志 / 进度 / 大文件 / 实时数据这类"持续产生"的数据，先拼成大字符串再返回会让客户端干等、服务端内存被撑；把数据源做成 Readable 边产生边推，`res` 本身是 Writable，`stream.pipe(res)` 即可，别提前设 Content-Length（交给 chunked）。实测 `/all`（拼完再发）首字节 814ms，`/stream`（边出边发）首字节 4ms。

### 5.4 fs 文件操作与 path 路径

- **fs 三风格**：回调版（易嵌套）/ `fs.promises`（配 async/await，主流，可 try/catch 兜底）/ `*Sync`（**阻塞事件循环**，只适合启动初始化、CLI，绝不上高并发请求热路径）。
- 目录遍历推荐 `fs.readdir` + `withFileTypes` 拿 `Dirent`，用 `isFile()` / `isDirectory()` 判断类型，避免反复 `stat`。
- **拼路径永远用 `path.join`**（跨平台，分隔符 `/` 与 `\` 差异）；`path.resolve` 遇绝对路径停下、解析成基于 cwd 的绝对路径。经验法则：只拼一段路径用 `join`，要从项目根出发才用 `resolve`。

## 6. 进程、线程与生命周期

### 6.1 进程本质与观测

`node app.js` 起一个 Node 进程：独立内存空间、一个 V8、一块堆、一个事件循环、一组文件描述符。

用 `process` 观测：`pid` / `uptime()` / `argv`（argv[0]=node、argv[1]=脚本）/ `memoryUsage()`（`rss` 物理内存、`heapUsed` JS 堆）。注意 **rss 常远大于 heapUsed**：Buffer、线程栈等都算进 rss，"JS 对象不多、内存却很大"是常态。

### 6.2 child_process 四把刀

| API | 是否走 shell | 输出 | 典型用途 |
| --- | --- | --- | --- |
| `spawn(command, args)` | 否 | 走流（边产边吐） | 长运行 / 大输出 |
| `exec(command, cb)` | 是 | 全缓冲后回调 | 短命令（git status） |
| `execFile(file, args, cb)` | 否 | 全缓冲 | 执行已知可执行文件，更安全（无 shell 注入面） |
| `fork(modulePath)` | 建 IPC | 走 IPC | 创建 Node 子进程并通信 |

`spawn` 的 `stdio: 'inherit'` 让子进程共用父 IO，`detached: true` + `child.unref()` 可脱离父进程独立跑。口诀：流式大输出 `spawn`；短命令拼 shell `exec`；跑文件不要 shell `execFile`；跑 Node 通信用 `fork`。`exec` 输出特大会撑爆 `maxBuffer`（默认 1MB）。

### 6.3 worker_threads 与 Worker Pool

`worker_threads` 在**同一进程内**开 JS 线程，把 CPU 密集任务从主线程挪走：主线程 `postMessage` 派活、Worker 用 `parentPort` 回结果，各自独立 V8 环境。主线程直接跑大循环会占死事件循环（心跳停滞），放进 Worker 心跳持续跳。

- **Worker 真正适合什么**：CPU 密集 JS——图片 / 视频处理、大 JSON 解析、复杂数学、压缩、哈希。I/O 密集交给 Event Loop，别丢给 Worker（每个 I/O 请求都 new Worker 要付"创建线程→初始化 V8→跨线程传数据→销毁"的固定成本，反而更慢）。
- **Worker ≠ libuv 线程池**：libuv 池是 Node 内部自动维护、替你跑 fs/dns/crypto/zlib 底层阻塞操作、你不直接创建；worker_threads 是 `new Worker()` 主动建、跑你写的 JS。判断标准：你写没写过 `new Worker()`。
- **不要每请求 new Worker**（1 万并发 = 1 万 Worker，创建调度成新瓶颈）；正确做法 **Worker Pool + Task Queue**：预建固定数量（≈ 核数）、空闲才派、超额排队、对外 `runTask(input): Promise` 包装。
- **`SharedArrayBuffer` 共享内存**：并发 `shared[i]++` 是"读→改→写"非原子会丢更新，须用 `Atomics.add` 等原子操作；能共享是能力、会同步才是本事。

### 6.4 cluster 与多进程选型

**单进程吃不满多核**：Node 默认一主线程只占一核，多核要开多进程各占一核。`cluster` 让 Primary fork 多个共享同端口的 Worker，由 OS/Primary 分发，Worker 数取 `os.availableParallelism()`，`exit` 里崩一个补一个。

进程 vs 线程：

| 维度 | 进程（Process） | Worker Thread |
| --- | --- | --- |
| 内存 | 独立（默认不共享） | 可共享（SharedArrayBuffer） |
| 隔离性 | 强（崩一个不影响其他） | 较弱（同进程共享内存） |
| 创建成本 | 高 | 低 |
| 通信 | IPC / Socket | Message + 共享内存 |
| 运行外部程序 | 可以 | 不适合 |

`cluster` 定位提醒：官方明确不需进程级隔离时应优先 `worker_threads`（同实例共享内存、成本低）；cluster 的真正价值是**进程级故障隔离 + 多核部署**。

四种并发选型：

| 见到什么 | 用什么 |
| --- | --- |
| HTTP / DB / Redis / 外部 API | Event Loop（异步 I/O） |
| CPU 密集 JS | worker_threads（走 Pool） |
| 强隔离 / 跑外部程序 / shell | child_process |
| 多实例铺满多核 + 故障隔离 | 多进程（cluster / 容器编排 + 负载均衡） |

浓缩一句：I/O 用异步；CPU 用 Worker（走池）；要隔离或跑外部程序用子进程；要铺多核且要故障隔离用多进程。

### 6.5 优雅关闭与错误兜底

- **优雅关闭**：收到 `SIGTERM` / `SIGINT` 先停收新连接（`server.close` + `closeIdleConnections`）→ 等在途请求（10s 超时兜底）→ 关 DB / Redis / MQ → `exit(0)`。SIGTERM 是容器编排（docker stop / K8s 滚动）的标准信号，SIGINT 是终端 Ctrl+C。
- **别滥用 `process.exit()`**：立即终止会丢未写完的 stdout / 日志 / 事务 / 响应；生产掌握 `process.exitCode`（设码不立即杀）+ Graceful Shutdown + Signal Handling 三件事。
- **错误分层接住**：同步 try/catch、回调判首参 err、Promise `.catch`/await try/catch、路由入口外层包裹；漏到进程级用 `uncaughtException` / `unhandledRejection` 做最后清理。**uncaughtException 之后不推荐继续运行**（内部状态已不可信），记日志 + 优雅退出，交 PM2/K8s 拉起干净新进程。
- 判断错误种类用 `error.code`（ENOENT / EADDRINUSE / ECONNRESET）与 `error.name`（TypeError / RangeError）。
- **环境变量与 os**：`process.env` 读环境变量、存敏感配置；`.env` 不提交 Git（含密码/Key），进仓库用 `.env.example` + `.gitignore`，`NODE_ENV` 切调试/优化；`os.cpus` / `totalmem` / `homedir` / `tmpdir`，多进程决策用 `os.availableParallelism()`（比 `os.cpus().length` 更贴合调度）。

### 6.6 运行机制收束与决策模型

完整架构三条主线：

- **网络 I/O 走内核**：epoll / kqueue / IOCP，不进线程池。
- **fs / crypto / dns / zlib 走 libuv 线程池**（默认 4）。
- **你写的 JS 只在主线程的 V8 里跑**——"所有卡不卡的问题，本质都是主线程被占住没有"。

主动创建的两类并发结构：同进程内 Worker Thread（可共享 SharedArrayBuffer）与独立 Child Process（内存不共享、靠 IPC/Socket）。

决策模型第一反应：见"卡 / 慢 / 顺序乱 / 内存涨"先问"事件循环是不是被占住了？数据流有没有背压？"，再决定换异步、上 Stream，还是丢给线程 / 进程。典型场景映射：一卡一慢→查事件循环利用率；文件上传/大文件→Stream+背压；压缩/加密/大 JSON→Worker；调 ffmpeg/python→child_process；用不满多核→cluster；进程不退出→未清理句柄+优雅关闭；响应顺序乱→微任务检查点（nextTick vs Promise）；CPU 打满 QPS 低→主线程被同步阻塞占住；内存涨 OOM→背压没做或监听器泄漏。

六条误区清单：

1. "单线程"只指 JS 执行，进程内还有 libuv 线程池。
2. "所有异步都在线程池"——网络 I/O 走内核，不进池。
3. "await 阻塞事件循环"——只暂停当前 async 函数后半段。
4. "worker_threads 就是线程池"——前者给你用、后者给 Node 内部用。
5. "nextTick 越多越快"——递归会饿死事件循环。
6. "多开进程就能变快"——I/O 密集瓶颈在等待，多开只多占内存。

交接模块二：进程内 I/O 模型已收口，接下来要回答"这些 I/O 从哪来"——HTTP / TCP / WebSocket 的本质是跨机器交换字节。
