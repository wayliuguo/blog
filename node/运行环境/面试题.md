# 模块面试题 · 运行环境

> 题目按知识体系章节分组，章号与 `总结.md` 大纲一一对应；每题 `（N.N）` 是所属知识域编号，作答走「判 · 展 · 证 · 界」四槽。题目口径已按新版知识与 Node 20+（libuv 1.45）校订。

## 1. Node 运行时与适用边界

### Q1（1.1）｜ Node.js 和 JavaScript 是什么关系？
- **判断**：Node.js 是 JavaScript 的运行环境，让 JS 脱离浏览器在服务端运行，它不是一门新语言。
- **展开**：基于 Chrome 的 V8 引擎做 JS 解析、JIT、执行与 GC；在 V8 之外补齐 `fs` / `http` / `net` / `crypto` / `process` 等服务端能力——V8 本身并不知道 `fs.readFile` 是什么。
- **佐证**：语言是 JS/TS，运行环境是 Node，底层引擎是 V8（与 Chrome 同款）。
- **边界**：语法核心一致但 API 能力不同——浏览器有 DOM/BOM，Node 有 fs/http/process；模块系统也不同，不能把浏览区写法直接照搬。

### Q2（1.1）｜ V8、libuv、操作系统在 Node 里各自负责什么？
- **判断**：三者分层协作——V8 跑 JS，libuv 是异步底座，操作系统真正执行底层 I/O。
- **展开**：V8 负责解析 / JIT / 内存管理 / GC；Node Bindings 把 JS 调用翻译成底层能力；libuv 管 Event Loop、线程池、定时器、跨平台异步 I/O 封装并调度回调；OS 是真正干活的一层。
- **佐证**：Linux 用 epoll、macOS/BSD 用 kqueue、Windows 用 IOCP。
- **边界**：Node 的高并发不是因为"没有等待"，而是因为"不让主线程去等"；等待本身无法消除。

### Q3（1.1）｜ "Node.js 是单线程的"这个说法准确吗？
- **判断**：不准确。准确表述是"执行 JavaScript 的主线程是单线程的，但 Node 进程本身不是单线程程序"。
- **展开**：libuv 维护一个默认 4 线程的线程池，专跑文件 I/O、DNS、crypto 等无原生异步接口的操作；定时器与网络 I/O 由事件循环和内核（epoll/kqueue/IOCP）协作完成。
- **边界**：标准说法是"单线程执行 JS + 多线程处理底层 I/O"。这条口径决定后面所有并发题的判断——"CPU 打满服务卡死"是主线程被占住，不是线程池被占满。

### Q4（1.2）｜ 为什么 Node.js 适合 I/O 密集型服务？
- **判断**：因为它的强项是"等待的时候不闲着"——把等待从主线程交给内核，而不是让 CPU 空转在某个请求上。
- **展开**：一次 API 请求里 CPU 真正执行 JS 往往只有几毫秒，其余两三秒全在等数据库、缓存、下游、第三方 API；非阻塞 I/O + 事件循环让主线程在等待窗口去处理别的请求，I/O 就绪再执行回调。
- **佐证**：实测总墙上约 2500ms，CPU 实际占用约 16ms（2.5%）。
- **边界**：瓶颈判断标准是"时间花在算还是在等"；等待占比极高的聚合网关、BFF、实时推送是主场，重计算不是。追问：等待无法消除，Node 只是把它挪出了主线程。

### Q5（1.3）｜ 阻塞模型和非阻塞模型有什么区别？为什么非阻塞能扛高并发？
- **判断**：阻塞是主线程"等完才走"，非阻塞是发起 I/O 后立刻转去处理别的请求——存量等待窗口被利用起来才有高并发。
- **展开**：阻塞模型下 A 等待时 B/C 被堵在后面、CPU 空转；非阻塞模型下主线程把请求都发出去，I/O 完成由内核就绪通知、事件循环再回调。
- **边界**：非阻塞不等于没有等待，等待挪到了内核与线程池。追问：一个主线程管理万级连接的底座正是内核的通知机制。

### Q6（1.4）｜ 什么场景不该选 Node.js？
- **判断**：CPU 密集型场景不该选——执行 JS 只有一个主线程，一段重计算占住事件循环，期间所有请求一起阻塞。
- **展开**：大数运算、图像/视频编解码、复杂加密压缩、超大 `JSON.parse` 都属此类，应交 Worker Thread 或子进程。
- **佐证**：主线程跑大循环时心跳计时器会"卡住"不跳，放进 Worker 才持续跳。
- **边界**：以重计算为主、I/O 等待占比很低的业务，Go/Java 的多线程或协程模型往往更顺手。追问：判断口径是"先用一笔耗时账分清算与等，再谈选型"。

### Q7（1.4）｜ 一次 API 请求两三秒，CPU 到底算了多久？
- **判断**：真正执行 JS 只有几毫秒，绝无两秒——其余全是等待。
- **展开**：链路是查 MySQL 30ms → 聚合下游 100ms → 请求第三方 2000ms → 查 Redis 5ms → 写库 30ms；等待占 99%，CPU 算的只有几毫秒。
- **边界**：这解释了 Node 的价值在"等待不闲着"；若某请求 CPU 真占了大多数，说明它不是 I/O 密集，就该换并发手段。

## 2. 模块系统与包管理

### Q8（2.1）｜ require 和 import 的本质区别是什么？
- **判断**：不能只答"一个是 CommonJS、一个是 ESM"，核心是解析时机、加载语义、同步异步、Tree Shaking 四点。
- **展开**：`require` 运行时才定位执行、可写进 if、可拼路径、拿到的是值的拷贝（对象共享）、同步无顶层 await；`import` 编译期静态建依赖图、必须顶层、路径静态、是活绑定、异步加载且支持顶层 await。
- **佐证**：ESM 静态可分析所以能摇树，CJS 运行期才知依赖所以全保留。
- **边界**：追问——CJS 导出方后续改内部变量导入方看不到；ESM 改了值所有导入方实时同步。

### Q9（2.1）｜ exports 和 module.exports 到底什么关系？为什么直接给 exports 赋值会失效？
- **判断**：`exports` 只是 `module.exports` 的初始引用，真正被导出的一定是 `module.exports`。
- **展开**：两者指向同一对象时 `exports.add=...` 能挂上属性；一旦 `module.exports={...}` 重赋值，两者分道扬镳，之后挂到 `exports` 上的外界拿不到；而直接 `exports={...}` 只是把局部变量指到新对象，`module.exports` 没动。
- **佐证**：铁律——整体替换用 `module.exports=`，增量挂属性用 `exports.xxx` 且之后不要再重赋值 `module.exports`。
- **边界**：最隐蔽的是 `exports = {...}`，外界 require 到的仍是原空对象。

### Q10（2.1）｜ require 的加载与缓存机制是怎样的？
- **判断**：`require` 按"查缓存 → 内置模块直返 → 路径解析 → 读取执行 → 缓存导出"走一遍，同一模块只执行一次。
- **展开**：相对路径补 `.js/.json/.node` 并解析目录；非 `.` 开头当包名从当前目录逐级向上找 node_modules，找不到抛 `MODULE_NOT_FOUND`；结果缓存在 `require.cache`，二次 require 直接返回缓存的 module.exports。
- **边界**：顶层副作用只在首次 require 触发；循环依赖时模块执行到一半就把当前 module.exports 交出去缓存，可能拿到半成品对象。

### Q11（2.1）｜ 同一个项目里 CommonJS 和 ESM 能混用吗？
- **判断**：能，但规则不对称——ESM 引 CJS 容易，CJS 引 ESM 受限。
- **展开**：ESM 里 `import pkg from 'cjs-pkg'` 通常直接可用，Node 把 module.exports 包成默认导出；反向不能直接 require 一个 ESM 包，因为 require 是同步的，等不了 ESM 异步求值。
- **佐证**：CJS 里桥接用 `await import('some-esm-pkg')`——动态 import 返回 Promise。
- **边界**：带顶层 await 的 ESM 在任何版本都不能 require（抛 ERR_REQUIRE_ASYNC_MODULE），只能动态 import()。追问：渐进迁移靠 `.cjs`/`.mjs` 后缀强制 + 动态 import()。

### Q12（2.2）｜ 为什么 ESM 能做 Tree Shaking 而 CommonJS 不能？
- **判断**：因为 ESM 的依赖关系在编译期就静态确定，打包器能精确知道哪些导出没被用而被删掉。
- **展开**：ESM 的 import/export 是静态语法，依赖图解析阶段就固定；CJS 的 require 是运行时函数调用、路径可变量、导出对象可整体替换，打包器无法静态证明某属性一定没用，只能全保留。
- **边界**：这是"新项目倾向 ESM"的工程理由之一——语法统一 + 打包产物更小。追问：建立在"导出必须静态可分析"这个前提上。

### Q13（2.2）｜ ESM 的"活绑定"（live binding）是什么意思？
- **判断**：导出的变量与模块内部的变量是同一个绑定，模块内部改了值、所有导入方立刻同步。
- **展开**：CJS 相反是"值的拷贝（快照）"——导出那一刻把值拷进对象，模块内部后续修改外部看不到。
- **佐证**：同样的 count 调一次 increase()，CJS 快照仍 0、ESM 活绑定变 1。
- **边界**：CJS 想同步得自己封装 getter。

### Q14（2.3）｜ Node 怎么判定一个 .js 文件走 CommonJS 还是 ESM？
- **判断**：后缀强制优先，其次看最近的 package.json 的 type 字段。
- **展开**：`.cjs` 永远 CJS、`.mjs` 永远 ESM（后缀说了算）；其余 `.js` 看 type：`"module"` 整包按 ESM，不写或 commonjs 默认 CJS。
- **佐证**：在一个 ESM 包中想保留个别 CJS 文件，就改名成 `.cjs`。
- **边界**：同一个 .js 到底哪套取决于它处于哪个 package.json 作用域内。

### Q15（2.3）｜ Node 22 以后 CJS 能直接 require 一个 ESM 包吗？
- **判断**：能，但有限制——只有"同步求值的 ESM"才能被 require。
- **展开**：Node 22 起 require() 可同步加载不含顶层 await 的 ESM，返回带 __esModule 标记的命名空间对象；含顶层 await 的任何版本都不能 require。
- **边界**：旧版本抛 ERR_REQUIRE_ESM；含顶层 await 的抛 ERR_REQUIRE_ASYNC_MODULE，必须改动态 import()。

### Q16（2.4）｜ 语义化版本里 ^ 和 ~ 的区别是什么？
- **判断**：`^` 允许次版本更新（不跨主版本），`~` 只允许补丁更新，`^` 更宽松。
- **展开**：版本号是"主版本.次版本.补丁"；`^4.18.0` 可升到 4.19.x，`~4.18.0` 只能到 4.18.x。
- **佐证**：`-beta`/`-rc` 预发布标签默认被 `^` `~` 排除，避免引入预览版。
- **边界**：符号只决定"允许升级到哪"，要真正钉死版本还得靠锁文件。

### Q17（2.4）｜ 为什么 package-lock.json 必须提交到 Git？
- **判断**：不提交锁文件等于放弃可复现构建，必然制造"在我机器上能跑"的漂移。
- **展开**：package.json 里的 `^4.18.0` 是范围不是精确值，不同时间/机器装到的版本会漂；锁文件记录实际每一层的精确版本与内容哈希，把整棵依赖树钉死。
- **边界**：它还能加快安装，配合 `npm ci` 严格按锁文件重建且更快，是 CI 与生产部署推荐命令。追问：只改 package.json 不更新锁文件，或把锁文件加进 .gitignore，都会让"可复现"形同虚设。

### Q18（2.4）｜ node_modules 为什么能扁平化？require 怎么找到顶层包？
- **判断**：npm v3 起把二三级依赖提升到顶层复用，require 按"就近优先、逐级向上"的算法在 node_modules 里找。
- **展开**：无版本冲突时提升到顶层、冲突才降级放子目录；`require('lodash')` 从当前目录逐级向上找，全没有抛 MODULE_NOT_FOUND。
- **佐证**：顶层包能被任意子目录引用到，就是这个规则解释的。
- **边界**：node_modules 很大应写进 .gitignore，靠 package.json + 锁文件重建。

## 3. 事件循环与微任务

### Q19（3.1）｜ 事件循环解决什么问题？单线程怎么扛万级并发？
- **判断**：先在线程"单线程"只指执行 JS 的主线程，事件循环通过"发起 I/O 不等待、I/O 就绪再回调"让一个线程照看大量等待中的连接。
- **展开**：慢查询不会卡住后面的请求；无定时器无 setImmediate 时事件循环停在 poll 阶段阻塞等内核就绪通知，几乎不占 CPU。CPU 密集会占住主线程、事件循环转不动。
- **边界**：万级连接只占一个 JS 线程的前提是这些连接都在"等 I/O"——靠 epoll/kqueue/IOCP 通知。

### Q20（3.2）｜ libuv 有哪六个阶段？哪个最重要？
- **判断**：六个阶段是 timers → pending callbacks → idle/prepare → poll → check → close callbacks，最重要的是 poll。
- **展开**：timers 管 setTimeout/setInterval；pending 处理推迟的系统回调；idle/prepare 是 Node 内部用；poll 是 I/O 核心，向内核取就绪事件并执行 I/O 回调；check 是 setImmediate；close 收尾资源关闭。
- **佐证**：每进入一个阶段就把该队列一次性执行完再进下一阶段。
- **边界**：拿不准顺序就用"阶段顺序"推导——poll 之后是 check，再往后才是下一轮的 timers。

### Q21（3.3）｜ 为什么说 setTimeout(fn, 1000) 不准？setTimeout(0) 会立即执行吗？
- **判断**：第二参数是最小等待时间而非精确时间，到期只代表回调"获得执行资格"；`setTimeout(0)` 同样不会立即执行。
- **展开**：Timer 到期只是把回调放进 timers 队列，还要等主线程空闲；若主线程被 3 秒同步循环占住，1 秒到期的回调也得 3 秒后才轮。
- **佐证**：`while(Date.now()-start<3000){}` 后约 3 秒才打印 timeout。
- **边界**：`0` 会被 clamp 到约 1ms。追问："定时任务不准时"通常是主线程被阻塞，不是定时器精度问题。

### Q22（3.3）｜ 主模块里和 I/O 回调里，setImmediate 与 setTimeout(0) 谁先执行？
- **判断**：主模块里顺序不确定；写在 I/O 回调里 setImmediate 恒定先执行。
- **展开**：主模块里两者都排到"下一轮循环"，setTimeout(0) 至少 1ms 到期，先后受启动耗时影响；写在 I/O 回调里当前正处 poll，紧接着就是 check，所以 setImmediate 先。
- **佐证**：`fs.readFile(... , () => { setTimeout(...); setImmediate(...); })` 稳定输出 immediate → timeout。
- **边界**：推演链路是"当前 poll → check（setImmediate）→ 下一轮 timers（setTimeout）"。追问：Node 20 后 timer 时机有调整，用阶段顺序推导而别背死亡结论。

### Q23（3.3）｜ close callbacks 阶段什么回调才会落进去？
- **判断**：只有真正经历 `uv_close` 的 handle（真实 socket 销毁）的回调才落在此阶段，看 handle 而非事件名。
- **展开**：`client.destroy()` 销毁真实连接会走一次 uv_close，`'close'` 落 close callbacks；无活跃连接时 `net.Server.close()` 改用 `process.nextTick` 派发 `'close'`，不进此阶段。
- **边界**：对"某个回调落在哪个阶段"的断言都应自己实跑验证，别替运行时想当然。

### Q24（3.4）｜ 网络 I/O 为什么不进 libuv 线程池？
- **判断**：因为内核本身能提供"socket 有数据时通知我"的机制，不需要开线程阻塞轮询。
- **展开**：Node 把 socket 注册给 epoll/kqueue/IOCP，内核数据到达时主动通知，libuv 在 poll 阶段取事件调度回调；文件 I/O（fs.readFile）、部分 DNS（dns.lookup）、部分 crypto（pbkdf2/scrypt）、zlib 才进线程池。
- **佐证**：区分标准就一条"内核能否异步通知"；能通知不进池。
- **边界**：记成"网络 I/O 不进池，文件/DNS/crypto/zlib 才进池"。

### Q25（3.4）｜ UV_THREADPOOL_SIZE 怎么调，有什么坑？
- **判断**：用环境变量在进程启动前设置，默认 4、上限 1024，且不是越大越好。
- **展开**：libuv 在进程启动时一次性读取并创建线程，`UV_THREADPOOL_SIZE=8 node app.js` 才有效；线程数决定同一时刻能并行跑几个 fs/crypto/dns/zlib 任务。
- **佐证**：并发 10 个 pbkdf2，时间戳明显分成"4 个一批、后面的排队"。
- **边界**：①运行时改 process.env 无效；②线程过多上下文切换开销大，4 是多数甜点值；③fs/DNS/crypto/zlib 抢同一个池，把 crypto 开满会挤占 fs.readFile 并发。

### Q26（3.4）｜ Node 20 / libuv 1.45 之后 timer 时机变了，哪些旧结论不能再背？
- **判断**：旧"timers→poll→timers 本轮结束前再处理一次 Timer"的说法过时，现在每轮循环的 Timer 调度重点是 poll→check→close→timers。
- **展开**：libuv 仍会在首次进入事件循环前处理一次 Timer 以保持向后兼容；这个变化影响部分 setImmediate 与 Timer 的时序关系。
- **佐证**：旧：timers→poll→timers；新：poll→check→close→timers。
- **边界**：看到任何事件循环文章，先问"写于哪年、对应哪个 Node 版本"，用阶段顺序重新推，别记结论。

### Q27（3.5）｜ process.nextTick 和 Promise.then 谁先执行？为什么？
- **判断**：process.nextTick 先于 Promise.then，同一检查点内永远是"先 nextTick、后 Promise"。
- **展开**：Node 把微任务拆成两条独立队列，处理顺序固定为"先清空 nextTickQueue，再清空 Promise 队列"，都清空到空才结束。
- **佐证**：`process.nextTick(...)` 与 `Promise.resolve().then(...)` 输出 nextTick → promise。
- **边界**：nextTick 不属于事件循环六个阶段，官方阶段图里根本没有它；优先级比所有宏任务和 Promise 微任务都高。

### Q28（3.5）｜ 微任务到底是什么时候被执行的？为什么说"不是一轮 Event Loop 才一次"？
- **判断**：不是整轮跑完集中清空一次，而是每次 JS 回调返回调度层都触发一次微任务检查点（microtask checkpoint）。
- **展开**：每执行完一个宏任务回调，就清空它新产生的 nextTick 和 Promise 微任务，再继续下一个回调。
- **佐证**：`timer1 → promise → timer2`——两个 setTimeout 同处 timers 阶段，timer1 返回时立刻清空它注册的 Promise，而不是等 timers 阶段结束。
- **边界**：心智模型记成"每个回调之后清空一次微任务"。追问：复杂输出题按"划同步→标检查点→先 nextTick 后 Promise→再下一阶段"四步推。

### Q29（3.5）｜ process.nextTick 和 setImmediate 有什么区别？怎么选？
- **判断**：nextTick 在当前操作结束后立即执行、优先级极高且不属于任何阶段；setImmediate 排进下一轮 check 阶段。
- **展开**：nextTick 在 Call Stack 清空时立刻触发，setImmediate 在 poll 之后的 check 阶段执行。
- **边界**：要"延迟到当前操作之后但尽量早"用 nextTick；要"让出执行权、不阻塞阶段推进"用 setImmediate。追问：绝不要在 nextTick 里递归调度无限任务。

### Q30（3.5）｜ 为什么递归调用 process.nextTick 会饿死 Event Loop？
- **判断**：因为 nextTick 队列的清空策略是"一直清空直到为空"，递归注册让队列永远不为空。
- **展开**：每次执行 loop 又往队列注册自己，Event Loop 一直卡在清空 nextTick 上，进不了 poll/timers/check 任何一个阶段。
- **佐证**：`function loop(){ process.nextTick(loop) }` 后 setTimeout 几乎永远执行不到。
- **边界**：这是官方文档明确警告的 I/O starvation。追问：排障时若发现 timers 一直不触发，优先怀疑递归 nextTick，无限调度改用 setImmediate。

### Q31（3.6）｜ 拿到一道异步输出顺序题，你怎么推？
- **判断**：按"划同步→标检查点→先 nextTick 后 Promise→再进下一阶段"四步走，不背玄学顺序。
- **展开**：同步代码按书写顺序最先打印；每执行完一个宏任务回调在返回处标检查点；同一检查点内先清空 nextTick 再清空 Promise；微任务清空后才轮到下一个宏任务。
- **佐证**：`start → setTimeout(注册) → Promise(注册) → nextTick(注册) → end` 输出 start→end→nextTick→promise→timeout。
- **边界**：两个阶段回调的相对先后可能随计时抖动，能归位到"属于哪个阶段"即可，别承诺绝对先后。

## 4. 异步编程与事件驱动

### Q32（4.1）｜ 异步写法为什么经历了 Callback → Promise → async/await 三次变革？
- **判断**：三者层层包裹而非替代——async/await 建在 Promise 上，Promise 把 Callback 嵌套拍平，每层解掉上一层的痛点。
- **展开**：Callback 的"回调地狱"真问题不是缩进深，而是错误分散（每层手写 if(err)，漏一层就被吞）与主流程被埋；Promise 用链式 .then/.catch 统一错误处理；async/await 让代码"看起来"同步。
- **佐证**：getUser→getOrders→getProducts→saveResult 从金字塔右移变纵向链。
- **边界**：底层非阻塞 I/O 本质始终没变。

### Q33（4.2）｜ Promise 的三种状态和链式语义是什么？
- **判断**：pending → fulfilled/rejected，三态不可逆，落到终态就锁死。
- **展开**：`.then` 回传 Promise 自动展开拍平嵌套；`.catch` 捕获整条链任意位置的拒绝；`.finally` 不论成败都执行；`.then` 里 throw 自动转 rejected。
- **佐证**：`getUser().then(u=>getOrders(u)).then(...).catch(err=>...)` 主流程一眼到底。
- **边界**：catch 是统一错误处理点，漏 catch 会变成 unhandledRejection。

### Q34（4.3）｜ await 会阻塞事件循环吗？为什么？
- **判断**：不会。await 只暂停当前 async 函数后半段的执行，主线程立刻腾出来处理别的请求。
- **展开**：await 把函数后半段挂成微任务，等 Promise 就绪再回来；底层 I/O 仍非阻塞，事件循环照常运转。
- **佐证**：`await later()` 之后还有同步代码会先跑完，不被 await 阻塞。
- **边界**：心智模型是"插书签、好了再回来"，不是"整个程序停在这一行"；await 阻塞的是"这个函数自己的后半段"。

### Q35（4.3）｜ await 用得不对，会把并发写成串行吗？
- **判断**：会。两个互不依赖的 await 之间是串行执行的，延迟线性累加。
- **展开**：await 的语义是"等这个 Promise 好了再往下走"，逐个 await 等于逐个死等；并发要用 Promise.all 一次性发起。
- **佐证**：串行 100+100+500≈700ms，Promise.all 并行≈500ms（取决于最慢的）。
- **边界**：服务端一个请求要"取用户信息+读会话+查配置+调外部"，前几步独立，写成串行端到端时延直接翻倍。追问：判断准则只有一条——两个 await 之间没有数据依赖就该并发。

### Q36（4.3）｜ Promise.all / allSettled / race / any 怎么选？
- **判断**：all 是"全有或全无"，allSettled 是"等全部结束、各自报状态"，race 取第一个落定者，any 取第一个成功的。
- **展开**：all 任一 reject 整体 reject、其余成功结果也被丢弃；allSettled 永不因失败而整体失败、逐项返回 {status, value|reason}；race 常用于加超时；any 适合多镜像取最快可用。
- **佐证**：事务性多步写库用 all；聚合下游接口的仪表盘用 allSettled。
- **边界**：race 成功或失败都算第一个；any 只有全部失败才整体 reject。

### Q37（4.4）｜ EventEmitter 是什么？为什么 'error' 事件特殊？
- **判断**：EventEmitter 是事件驱动的骨架（发布-订阅），而 error 事件是它唯一"没有监听器就崩进程"的特例。
- **展开**：核心 API 四步 on/emit/once/off；它是 net.Server、http.Server、fs.ReadStream、process 的基类。
- **佐证**：`emitter.on('error', ...); emitter.emit('error', err)` 被接住进程不崩。
- **边界**：普通事件没监听器只是没人响应，error 没监听器直接 throw 成 uncaughtException 导致进程退出——有意为之的 fail-fast，避免错误被静默吞掉。追问：凡可能 emit('error') 的对象都要先挂 error 监听器。

### Q38（4.4）｜ 监听器泄漏怎么发现和处理？
- **判断**：现象是 MaxListenersExceededWarning 反复出现 + 内存缓慢上涨，根因是 on 了不 off。
- **展开**：EventEmitter 默认同一事件最多挂 10 个监听器；在循环或高频函数里反复 on 同事件，监听器只增不减，闭包引用的对象也无法回收。
- **佐证**：用 `emitter.listenerCount('data')` 观察监听器数量是否异常增长。
- **边界**：一次性用 once 自动移除；把监听器提取成具名函数并在合适时机 off。追问："内存一路涨最后 OOM"两个典型方向——背压没做，或事件监听器泄漏。

### Q39（4.4）｜ 事件驱动怎么解耦"执行"与"观测"？
- **判断**：业务主流程只在关键节点 emit 事件，完全不知道外面挂了多少监听器，日志/监控/告警各自 on、互不影响。
- **展开**：task.on('task:start'/'task:dispatch'/'task:finish') 各挂观测；业务 runTask 只做 emit，不 import 任何日志/通知模块。
- **佐证**：新增埋点/审计只在外部再加一个 task.on(...)，业务主流程一行不改。
- **边界**：本质是"执行逻辑与观测逻辑各写各的，靠事件总线连接"。

## 5. 字节流与管道：Buffer 与 Stream

### Q40（5.1）｜ Buffer 是什么？和普通数组有什么区别？
- **判断**：Buffer 是固定长度的字节序列，Node 4+ 是 Uint8Array 的子类，能和整个 TypedArray 体系互操作。
- **展开**：创建时容量定死，元素只能是 0–255 的字节；`Buffer.alloc(n)` 分配并清零，`Buffer.from(x)` 从已有数据编码构造、不清零。
- **佐证**：`buf instanceof Uint8Array === true`。
- **边界**：旧资料说它是"堆外分配的类数组对象"是老口径，应答"TypedArray 体系的一员"；未清零的 `Buffer(size)` 是废弃写法，会残留堆上旧数据。追问：字符串是"给人读的字符"，Buffer 是"给机器搬的字节"。

### Q41（5.1）｜ Buffer.alloc 和 Buffer.from 有什么区别？
- **判断**：alloc 分配 n 字节并清零、适合待填充缓冲，from 从已有数据编码、不清零。
- **佐证**：`Buffer.alloc(5)` 全 0；`Buffer.from('hello')` 编码为 68 65 6c 6c 6f。
- **边界**：需要空白缓冲就用 alloc，别用未清零的 Buffer(size)（可能泄漏敏感信息）。

### Q42（5.2）｜ Buffer 与 String 的区别？用字节数举例。
- **判断**：String 是带编码的字符序列，Buffer 是原始字节序列，字符长度 ≠ 字节长度。
- **展开**：''你好''.length 是 2，Buffer.from('你好').length 是 6（UTF-8 每汉字 3 字节）——同一段字节用 utf8/hex/base64 解读得到不同字符串。
- **佐证**：'中文abc' 字符数 5、字节数 9（中 2×3 + 英 3×1）。
- **边界**：算 Content-Length、切二进制帧、限上传体积必须用 Buffer.length；用字符长度会把内容算小、下游截断错乱。

### Q43（5.3）｜ Stream 的四种类型是什么？
- **判断**：Readable / Writable / Duplex / Transform，按"单向还是双向 × 是否转换"划分。
- **展开**：Readable 只生产（on('data')/read()/for await）；Writable 只消费（write()/end()）；Duplex 同时可读可写（典型 TCP socket）；Transform 是 Duplex 的特例、输入经转换再输出（gzip、加解密）。
- **边界**：Stream 不是"文件相关"——net.Socket 就是 Duplex Stream，req/res 分别是可读/可写流，process.stdout 也是流。追问：Buffer 是水桶里的水，Stream 是水管，不断输送一个又一个 Buffer chunk。

### Q44（5.3）｜ Readable 的 flowing 和 paused 模式有什么区别？
- **判断**：flowing 靠 data 事件自动推数据，paused 靠 read() 主动拉数据。
- **展开**：监听 data、调用 pipe()/resume() 切到 flowing；调用 pause() 或移除 data 监听切回 paused；paused 下数据积在内部缓冲区由 read() 取走。
- **佐证**：`on('data',...)` 是 flowing（推）；`on('readable', ()=>{while(read()){}})` 是 paused（拉）。
- **边界**：flowing 方便但不消费就丢数据，paused 适合自己实现背压。追问：pipe/pipeline 内部自动管理模式切换与背压，绝大多数场景不必手写 pause/resume。

### Q45（5.3）｜ 什么是背压？它解决什么问题？
- **判断**：背压是 Stream 自动"踩刹车"的机制，解决"上游生产快、下游消费慢"导致缓冲堆积最终 OOM 的问题。
- **展开**：write() 返回 true 表示可继续写，返回 false 表示缓冲达上限、调用方应暂停读取；下游消化完触发 'drain' 再恢复写入。
- **佐证**：`if(!writable.write(chunk)) readable.pause();` 触发 'drain' 后 resume()。
- **边界**：磁盘读 500MB/s、网络只发 10MB/s 的速度失配是典型场景；pipe/pipeline 内部自动协调背压。追问："内存一路涨最后 OOM"的方向之一就是背压没做。

### Q46（5.3）｜ highWaterMark 的作用是什么？
- **判断**：它是可读/可写流内部缓冲区的高水位阈值，是背压机制里"何时该踩刹车"的开关。
- **展开**：它决定每次读取的块大小，也决定背压触发点——缓冲堆到该阈值时 write() 返 false、上游被要求暂停；两侧默认不同，createReadStream 64KB、createWriteStream 16KB。
- **佐证**：`createReadStream('./big.iso', { highWaterMark: 64*1024 })`。
- **边界**：阈值小更省内存但搬运次数多、阈值大反之，本质是内存占用与系统调用次数的权衡。

### Q47（5.3）｜ 为什么大文件必须用 Stream 而不是 readFile？
- **判断**：readFile 把整个文件读进内存、文件多大占多少，Stream 一次只搬一小块、内存恒定。
- **展开**：Stream 默认每次读 64KB，数据从磁盘流入可读流、再流入可写流落盘，内存始终维持在几十 KB 到几 MB；10GB 文件 readFile 会撑爆进程堆触发 OOM。
- **佐证**：64MB 文件 readFile 同时在手 64MB，pipe 只在手 128KB（读侧 64K + 写侧 16K）。
- **边界**：判断依据是"数据量可能超过内存"或"需要边产生边消费"。追问：流式推送也必须用流，否则客户端要等全部数据生成完才收到。

### Q48（5.3）｜ pipe 与 pipeline 怎么选？
- **判断**：简单搬运用 pipe；链路长、要错误兜底、或要串多个转换用 pipeline。
- **展开**：pipe 内部协调读写速度与背压，但短板是下游出错不会自动销毁上游、会留悬挂流与未释放的 FD；pipeline（node:stream/promises）任意一环出错统一销毁所有流并抛错，能顺序串联多个 Transform。
- **佐证**：`await pipeline(createReadStream, createGzip, createWriteStream)`。
- **边界**："流式搬运用了 on('data') 手写、还没处理错误"是 FD 泄漏的常见根因。

### Q49（5.3）｜ 为什么同步 API（如 readFileSync）不能上高并发路径？
- **判断**：同步 API 会阻塞事件循环直到 I/O 完成，期间整个进程什么异步任务都处理不了。
- **展开**：高并发接口里一次同步读盘就能让所有请求一起卡住，这是把异步模型打回阻塞原形的写法；fs/promises 配 await 与 try/catch 是主流。
- **边界**：同步版本只适合启动初始化、CLI 这些不在请求热路径上的场景。追问：同类要警惕 execSync、超大对象同步 JSON.parse。

### Q50（5.4）｜ fs 有哪三种风格？怎么取舍？
- **判断**：回调版、fs.promises（Promise 版）、*Sync 同步版，主流用 fs.promises 配合 async/await。
- **展开**：回调版深层嵌套易"回调地狱"；fs/promises 可读性好、能 try/catch 统一兜底；*Sync 阻塞事件循环、只适合启动初始化与 CLI。
- **佐证**：目录遍历推荐 fs.readdir + withFileTypes 拿 Dirent + isFile()/isDirectory()，避免反复 stat。
- **边界**：运行时频繁文件操作勿用 *Sync。

### Q51（5.4）｜ path.join 和 path.resolve 有什么区别？
- **判断**：join 只做拼接与规范化、不引入 cwd；resolve 会解析成基于当前工作目录的绝对路径。
- **展开**：join 按顺序拼接；resolve 从右往左拼、遇绝对路径停下并以此为基。
- **佐证**：`path.join('a','b','c')`→'a/b/c'；`path.resolve('a','b','c')`→'/cwd/a/b/c'；`path.resolve('/etc','x')`→'/etc/x'。
- **边界**：跨平台必须用 path 拼路径，手写 '/' 或 '\\' 会出问题。追问：只拼一段路径用 join，要项目根出发的绝对路径用 resolve。

## 6. 进程、线程与生命周期

### Q52（6.1）｜ node app.js 启动的是什么？process 能看到什么？
- **判断**：起一个 Node 进程——独立内存空间、一个 V8、一块堆、一个事件循环、一组 FD；用 process 观测。
- **展开**：pid / uptime() / argv（argv[0]=node、argv[1]=脚本）/ memoryUsage()（rss 物理内存、heapUsed JS 堆）。
- **佐证**：rss 常远大于 heapUsed：Buffer、线程栈都算进 rss，"JS 对象不多内存却很大"是常态。
- **边界**：argv 里 argv[0] 是 node、argv[1] 才是脚本路径。

### Q53（6.2）｜ child_process 的 spawn / exec / execFile / fork 差异在哪？
- **判断**：四把刀按"是否走 shell、是否缓冲全部输出、是否建 IPC"区分。
- **展开**：spawn 最基础、输出走流不缓冲、适合长运行/大输出；exec 走 shell、全缓冲后回调，大输出撑爆 maxBuffer（默认 1MB）；execFile 不经 shell、无 shell 注入面更安全；fork 专门创建 Node 子进程并建 IPC 通道。
- **佐证**：spawn 的 stdio:'inherit' 共用父子 IO，detached:true + unref() 可脱离父进程独立跑。
- **边界**：口诀——流式大输出 spawn；短命令拼 shell exec；跑文件不要 shell execFile；跑 Node 通信用 fork。

### Q54（6.2）｜ 进程之间默认能共享内存吗？怎么通信？
- **判断**：进程内存默认隔离，不能直接共享，通信必须借助"进程外的公共通道"。
- **展开**：进程 A 的 const count 进程 B 无法直接访问，因为 OS 隔离两块内存空间；通信可选 IPC（同机高频低延迟）、Socket（同机或跨机最通用）、Redis（共享状态）、MQ（异步解耦削峰）、HTTP（跨服务跨语言最易调试）。
- **佐证**：fork/cluster 的 IPC 走 Unix 域套接字或命名管道，消息经序列化传输，不支持函数与 Symbol。
- **边界**：cluster 的 IPC 不能直接广播到所有子进程（要手动遍历 cluster.workers），子进程间不能直连、必须经主进程转发。

### Q55（6.3）｜ worker_threads 和 libuv 线程池有什么关系，为何不能混为一谈？
- **判断**：两者完全不同——一个是 Node 内部自动维护的隐藏线程，一个是主动 new Worker() 创建的 JS 线程。
- **展开**：libuv 池默认 4 个、专跑 fs/dns/crypto/zlib 底层阻塞操作、你不直接创建也感知不到；worker_threads 有独立 V8 环境与执行上下文、跑你写的 JS、还能共享 SharedArrayBuffer。
- **佐证**：判断方法很直接——你写没写过 new Worker()？没写过却在跑文件/加密，那是 libuv 在干活。
- **边界**：官方定位是"libuv 线程池给 Node 内部用，worker_threads 给你用"。

### Q56（6.3）｜ Worker Thread 真正适合什么？为什么不用于普通 I/O？
- **判断**：Worker 适合 CPU 密集 JS；普通 I/O 交给事件循环，每个 I/O 请求都 new Worker 反而更慢。
- **展开**：图片/视频处理、大 JSON 解析、压缩、哈希、复杂数学属 CPU 密集；每请求 new Worker 要付"创建线程→初始化 V8→跨线程传数据→销毁"的固定成本。
- **佐证**：主线程直接跑大循环心跳停滞，丢进 Worker 心跳持续跳。
- **边界**：判别标准——I/O 密集（网络、文件、DB/缓存）走 Event Loop，CPU 密集才走 Worker。

### Q57（6.3）｜ 为什么生产环境不能每个请求都 new Worker？
- **判断**：每请求一个 Worker 会让"建线程"本身成为新瓶颈，比主线程直接算还糟。
- **展开**：1 万并发就造 1 万个线程，线程创建与调度成瓶颈、内存随并发线性膨胀。
- **佐证**：反例 20 个 Worker 耗时约 840ms、峰值 RSS 233MB；正例 4 个 Worker Pool 耗时约 505ms、110MB。
- **边界**：正确做法是 Worker Pool + Task Queue——按核数预建固定数量、空闲才派、超额排队、对外 runTask(input):Promise。

### Q58（6.3）｜ SharedArrayBuffer 的竞态与 Atomics 代价是什么？
- **判断**：共享内存让线程直接改同一块数据、省掉拷贝，但代价是失去隔离——"读→改→写"非原子就丢更新。
- **展开**：两个 Worker 并发 shared[i]++ 中间会被插空、结果偏小；Atomics.add 之类原子操作才能一步到位。
- **佐证**：`shared[0]++` 非原子（读→+1→写回可能被插空），`Atomics.add(arr,0,1)` 原子。
- **边界**：Atomics 带来同步开销与"锁与可见性"心智负担。"能共享是能力，会同步才是本事"——这也解释"要隔离用进程、要共享内存用线程"。

### Q59（6.4）｜ 为什么说"见多核就无脑上 cluster"是错的？
- **判断**：因为官方已明确——不需要进程级隔离时应优先 worker_threads（同实例共享内存、成本低）；cluster 的真正价值是进程级故障隔离与多核部署。
- **展开**：单进程只占一核；cluster 让 Primary fork 多个共享同端口的 Worker、由 OS/Primary 分发；Worker 数取 os.availableParallelism()，exit 里崩一个补一个。
- **佐证**：`on('exit', w => cluster.fork())` 实现自动拉起。
- **边界**：cluster 每个进程独立实例、内存不共享，一个崩了不影响其他。

### Q60（6.4）｜ 进程和 Worker Thread 该怎么选？
- **判断**：要强隔离、跑外部程序、崩溃互不影响→进程；单纯把重计算挪出主线程、还要共享内存→Worker（走 Pool）。
- **展开**：进程内存独立、隔离性强、能跑外部程序，但创建成本高、不共享内存；Worker 同进程内、可共享 SharedArrayBuffer、成本低、适合 CPU 密集，但隔离性弱、一个线程出错可能拖垮整进程。
- **佐证**：浓缩——I/O 用异步；CPU 用 Worker（走池）；要隔离或跑外部程序用子进程；要铺多核且要故障隔离用多进程。
- **边界**：cluster.fork() 数量按 os.availableParallelism() 取，比硬编码核数更贴合调度。

### Q61（6.4）｜ 四种并发方式到底怎么选？
- **判断**：按任务性质二分——I/O 异步、CPU 用 Worker、要隔离或跑外部程序用子进程、要铺多核且要故障隔离用多进程。
- **展开**：HTTP/DB/Redis/外部 API→Event Loop；CPU 密集 JS→worker_threads（配 Pool）；强隔离/独立崩溃/运行外部程序/shell→child_process；多实例铺满多核+故障隔离→cluster/容器编排+负载均衡。
- **边界**：放错位置（如用 Worker 跑 I/O）是"加了线程反而更慢"的常见根因。

### Q62（6.5）｜ 收到 SIGTERM 后怎么做优雅关闭，为何不能直接 process.exit()？
- **判断**：先停收新连接→等在途请求归零（带超时兜底）→关外部依赖→最后退出，绝不能直接杀。
- **展开**：直接退出会掐断在途请求、来不及落库、日志丢失；正确顺序是 server.close() 停收新连接（closeIdleConnections 关空闲 keep-alive）→ 等活跃请求归零 → 关 DB/Redis/MQ → exit(0)。SIGTERM 是 docker stop/K8s 滚动默认信号，SIGINT 是 Ctrl+C。
- **佐证**：`process.on('SIGTERM', () => shutdown('SIGTERM'))`。
- **边界**：若还有未清理的句柄或定时器进程不会自动退出，所以清理完成后要显式退出。

### Q63（6.5）｜ 为什么不该滥用 process.exit()？
- **判断**：process.exit() 会立即杀进程，跳过所有排队 I/O 与回调，导致日志没发、事务没提交、响应没结束。
- **展开**：它不经过收尾流程；因错误必须结束时让未捕获错误自然终止通常更安全（自然终止前 Node 会先跑完已排队的回调）；输出目标是管道/文件时 stdout 写入是异步的，process.exit() 可能让最后几行日志没落盘。
- **边界**：生产真正掌握三件事——process.exitCode（设码不立即杀）、Graceful Shutdown（先收摊再走）、Signal Handling（正确响应信号）。

### Q64（6.5）｜ uncaughtException 和 unhandledRejection 有什么区别？之后该怎么办？
- **判断**：前者是同步代码抛出却没人 catch，后者是 Promise reject 了却没接住；两者都是进程级最后兜底入口。
- **展开**：unhandledRejection 在 Node 15+ 默认也会终止进程；uncaughtException 之后进程内部状态已不可信（模块半初始化、状态写坏），不推荐继续运行。
- **佐证**：记日志 + 优雅退出，交 PM2/K8s 拉起干净新进程。
- **边界**：真正的错误处理应分层——同步 try/catch、回调判首参 err、Promise .catch、路由入口外层兜住，进程级监听只做最后清理。追问：判断错误种类用 error.code（ENOENT/EADDRINUSE/ECONNRESET）与 error.name（TypeError/RangeError）。

### Q65（6.5）｜ 错误该在哪一层接住？
- **判断**：错误发生在哪一层就在哪一层兜，漏到进程级的监听只做最后清理。
- **展开**：同步代码 try/catch；回调式 API 判第一个 err；Promise 用 .catch 或 await try/catch；路由/定时任务/消息消费入口外层包 try/catch 转成可观测响应。
- **佐证**：uncaughtException/unhandledRejection 是最后防线，官方不推荐继续运行。
- **边界**：回调式 API 必须判 err、Promise 必须有 .catch，二者不能靠一个外层 try/catch 一劳永逸。

### Q66（6.5）｜ process.env 的作用是什么？.env 为什么不能提交？
- **判断**：process.env 读取环境变量，用于区分环境与存放敏感配置。
- **展开**：NODE_ENV 切开发/生产行为，PORT 指定端口，密码/Key 走环境变量而非硬编码；dotenv 加载 .env。
- **边界**：真实 .env 进 .gitignore、只提交 .env.example；环境变量在进程启动时固化，运行中改它骗不过已读过配置的模块。

### Q67（6.6）｜ 一个 Node 服务 CPU 打满但 QPS 很低，你怎么定位？
- **判断**：CPU 高 + QPS 低 = 主线程被占住（算），而不是 I/O 在等。
- **展开**：用 perf_hooks 的 eventLoopUtilization 或 process.hrtime 看事件循环是否被长任务占住；用 top/htop 看是单核跑满还是多核均匀——单核跑满说明瓶颈在 JS 主线程。
- **边界**：定位到同步阻塞（readFileSync、大 JSON 同步解析）就搬 worker_threads；定位到"单进程只吃一个核"就 cluster 铺多核。追问：定位顺序是"先分清算还是等，再看单核还是多核"，别一上来就加机器。

### Q68（6.6）｜ 多开进程就一定能提升性能吗？什么场景下没用？
- **判断**：不一定。I/O 密集型瓶颈在等待，多开进程只是多占内存、解决不了等待问题。
- **展开**：单进程事件循环本就能在等待时处理别的请求，加进程不会让"等下游返回"变快；只有 CPU 密集（单进程单核跑满）或需要故障隔离时多进程才有意义。
- **佐证**：判断依据是"先测事件循环利用率，分清瓶颈是算还是等"。
- **边界**：同类的误区还有"服务重启丢请求"——那不是进程数量问题，而是没接住 SIGTERM 做优雅关闭。

### Q69（6.6）｜ 处理 2GB 文件上传并转存，为什么不能用 fs.readFile？正确做法是什么？
- **判断**：readFile 会把 2GB 一次性读进内存撑爆堆或 OOM；上传转存必须走流，且无需落地临时文件。
- **展开**：req 本身就是可读流，转存目标是 createWriteStream 或对象存储的可写流，`req.pipe(out)` 边收边写，内存恒定在几十 KB 级。
- **佐证**：`req.pipe(fs.createWriteStream('./big.bin'))`。
- **边界**：多环节（限速→校验→转存）用 pipeline 统一销毁链路；客户端中断要监听 req.aborted/'error' 清理半截文件。追问：这题本质考"数据是字节流、要边读边搬"，内存占用应恒定而非随文件增大。
