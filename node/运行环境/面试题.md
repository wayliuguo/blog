## 一、基础概念

### Q1: "Node.js 是单线程的"这个说法准确吗？（第 01 篇）

- **结论**：不准确。准确表述是"执行 JavaScript 的主线程是单线程的，但 Node.js 进程本身不是单线程程序"。
- **原理**：libuv 维护一个默认 4 线程的线程池，专门处理没有原生异步接口的操作（文件 I/O、DNS 解析、`crypto` 计算）；定时器和网络 I/O 由事件循环与内核（epoll / kqueue / IOCP）协作完成。
- **边界**：所以标准说法是"单线程执行 JS + 多线程处理底层 I/O"，说"单线程"时必须限定在"JS 执行"这个范围内。
- **追问**：这条口径决定了后面所有并发题的判断——"CPU 打满服务卡死"是主线程被占住，不是线程池被占满。

### Q2: Node.js 和 JavaScript 是什么关系？（第一阶段·认识后端）

- **结论**：Node.js 是 JavaScript 的运行时环境，让 JS 脱离浏览器在服务端运行——它不是一门新语言。
- **原理**：基于 Chrome 的 V8 引擎，在 V8 之外补齐 `fs` / `http` / `net` / `crypto` / `process` 等系统级能力；V8 只负责解析、JIT、执行 JS 与 GC，本身并不知道 `fs.readFile` 是什么。
- **边界**：核心语法一致，但 API 能力不同——浏览器有 DOM / BOM，Node 有 `fs` / `http` / `process`；模块系统也与浏览器不同，不能把浏览器写法直接照搬。
- **场景**：浏览器里 JS 操作 DOM，Node 里 JS 读文件 `fs.readFileSync('file.txt')`，同一门语言、两套能力面。

### Q3: V8、libuv、操作系统在 Node.js 里各自负责什么？（第 01 篇）

- **结论**：三者分层协作——V8 跑 JS，libuv 是异步底座，操作系统真正执行底层 I/O。
- **原理**：V8 负责解析 / JIT 编译 / 内存管理与 GC；Node Bindings 把 JS 调用翻译成底层能力；libuv 负责 Event Loop、线程池、定时器、跨平台异步 I/O 封装，并轮询 I/O 状态、调度回调。
- **边界**：操作系统才是真正干活的一层，Linux 用 epoll、macOS / BSD 用 kqueue、Windows 用 IOCP。

```
你的代码 → V8 → Node Bindings → libuv（Event Loop + Thread Pool）→ OS（epoll / kqueue / IOCP）
```

- **追问**：Node 的高并发不是因为"没有等待"，而是因为"不让主线程去等"。

### Q4: 后端开发的核心能力有哪些？（第一阶段·认识后端）

- **结论**：后端的核心是"接请求、存数据、算业务、稳服务"，远不止写接口。
- **原理**：涵盖 API 设计、数据库读写与建模、缓存策略、认证授权、日志与监控、性能调优、并发与错误处理这几层能力。
- **场景**：一次登录——校验账号密码、签发 Token、查用户信息、返回响应并记审计日志，背后是多层能力的叠加，而不是单个函数。
- **边界**：能力清单会随业务侧重变化，但"数据正确性 + 服务稳定性"是共同的底线。

### Q5: 前端和后端的职责划分是怎样的？（第一阶段·认识后端）

- **结论**：前端管界面与交互体验，后端管数据处理与业务逻辑，两者通过 HTTP / WebSocket 等协议通信。
- **原理**：前端跑在浏览器里，负责 UI 渲染、用户交互、路由跳转、状态管理；后端跑在服务器上，负责数据存储、业务运算、认证授权、对外接口。
- **边界**：边界在变模糊（BFF、SSR 让 Node 既做服务又出页面），但"谁出数据、谁出页面"这条主线不变。
- **追问**：Node 做 BFF 的价值在于"同语言 + 擅长聚合多个下游 I/O"，而不是替代后端的数据层。

### Q6: require 和 import 的本质区别是什么？（第 02 篇）

- **结论**：不能只答"一个是 CommonJS、一个是 ESM"，核心是解析时机、加载语义、同步异步、Tree Shaking 四点。
- **原理**：`require` 运行时才定位并执行模块，可写进 `if`、可拼路径，拿到的是 `module.exports` 的引用，同步且无顶层 `await`；`import` 在编译期静态建依赖图，必须顶层且路径静态，是 live binding，异步加载并支持顶层 `await`。
- **边界**：ESM 静态可分析所以能摇树，CJS 运行期才知依赖所以只能全部保留——这是"新项目倾向 ESM"的工程理由。
- **追问**：`require` 内部后续改局部变量，导入方看不到；ESM 改了值，所有导入方实时同步。

### Q7: 同一个 Node 项目里，CommonJS 和 ESM 能混用吗？（第 02 篇）

- **结论**：能，但规则不对称——ESM 引 CJS 容易，CJS 引 ESM 受限。
- **原理**：ESM 里 `import pkg from 'cjs-pkg'` 通常直接可用，Node 会把 `module.exports` 包成默认导出；反向不能直接 `require` 一个 ESM 包，因为 `require` 是同步的，等不了 ESM 的异步求值。
- **边界**：遇到带顶层 `await` 的 ESM 包必然失败，正确做法是用动态 `import()` 包一层 `async` 函数桥接。

```js
// CommonJS 里桥接 ESM
async function main() {
  const { something } = await import('some-esm-pkg'); // 动态 import 返回 Promise
  something();
}
main();
```

- **追问**：渐进迁移靠 `.cjs` / `.mjs` 后缀强制指定（后缀优先级高于 `package.json` 的 `type`），再配合动态 `import()` 过渡。

### Q8: exports 和 module.exports 到底什么关系？为什么直接给 exports 赋值会失效？（第 02 篇）

- **结论**：`exports` 只是 `module.exports` 的初始引用，真正被导出的是 `module.exports`。
- **原理**：两者指向同一对象时 `exports.add = ...` 能挂上属性；一旦 `module.exports = {...}` 重赋值，两者就分道扬镳，之后往 `exports` 上挂的东西外界拿不到。
- **边界**：更隐蔽的是直接 `exports = {...}`——这只是把局部变量指向新对象，`module.exports` 一动没动，外界 `require` 到的仍是原空对象。

```js
exports.add = (a, b) => a + b;        // 生效：给同一个对象挂属性
module.exports = { add };             // 整体替换后，exports 上的挂件全失效
exports.subtract = (a, b) => a - b;   // 写在后面 → 外界拿不到
```

- **追问**：铁律——整体替换用 `module.exports =`，增量挂属性用 `exports.xxx`，且不要在其后重赋值 `module.exports`。

### Q9: require 的加载与缓存机制是怎样的？（第 02 篇）

- **结论**：`require` 按"查缓存 → 内置模块直返 → 路径解析 → 读取并执行 → 缓存导出"走一遍，同一模块只执行一次。
- **原理**：相对路径会补 `.js` / `.json` / `.node` 后缀并解析目录；非 `.` 开头当包名，从当前文件目录逐级向上找 `node_modules`，找不到抛 `MODULE_NOT_FOUND`；加载结果缓存在 `require.cache`，第二次直接返回缓存的 `module.exports`。
- **边界**：模块顶层的副作用（连库、起定时器、打日志）只在首次 `require` 时触发；循环依赖时可能拿到"还没初始化完"的半成品对象——因为模块执行到一半就把当前 `module.exports` 交出去缓存了。
- **追问**：这也解释了为什么 `node_modules` 靠扁平化提升后，顶层包能被任意子目录引用到。

### Q10: 语义化版本里 ^ 和 ~ 的区别是什么？（第 02 篇）

- **结论**：`^` 允许次版本更新（不跨主版本），`~` 只允许补丁更新，`^` 更宽松。
- **原理**：版本号是 `主版本.次版本.补丁`；主版本变代表破坏性改动，次版本变是向后兼容的新功能，补丁变是向后兼容的修复。

```
^4.18.0  → 允许 4.x.x，可升到 4.19.0
~4.18.0  → 允许 4.18.x，只能升到 4.18.9
4.18.0   → 精确锁定，只装这一个版本
```

- **边界**：`-beta` / `-rc` 这类预发布标签默认被 `^` `~` 排除，避免生产无意引入预览版。
- **追问**：符号只决定"允许升级到哪"，要真正钉死版本还得靠锁文件。

### Q11: process.env 的作用是什么？（第 06 篇）

- **结论**：`process.env` 读取进程环境变量，用于区分运行环境与存放敏感配置。
- **原理**：常用 `NODE_ENV` 切开发 / 生产行为（很多库都读它决定是否走优化）、用 `PORT` 指定端口；密码、API Key 这类信息走环境变量而非硬编码。
- **边界**：真实 `.env` 进 `.gitignore`，只把 `.env.example` 提交进仓库；开发期用 `dotenv` 加载，生产由部署平台注入。
- **追问**：环境变量在进程启动时固化，运行中改它骗不过已经读过配置的模块。

### Q12: path.join 和 path.resolve 有什么区别？（第 05 篇）

- **结论**：`join` 只做拼接与规范化，`resolve` 会解析成基于当前工作目录的绝对路径。
- **原理**：`join` 按顺序拼接、不引入"当前工作目录"概念；`resolve` 从右往左拼，遇到绝对路径就停下并以此为基。
- **边界**：跨平台必须用 `path` 拼接，手写 `'/'` 或 `'\\'` 会在另一个系统上出问题。

```js
path.join('a', 'b', 'c');    // 'a/b/c'（相对路径，纯拼接）
path.resolve('a', 'b', 'c'); // '/当前工作目录/a/b/c'（绝对路径，以 cwd 为基）
path.resolve('/etc', 'x');   // '/etc/x'（遇到绝对路径即停止）
```

- **追问**：经验法则是"只是拼一段路径用 `join`，要项目根出发的绝对路径才用 `resolve`"。

### Q13: Buffer 是什么？和普通数组有什么区别？（第 05 篇）

- **结论**：Buffer 是**固定长度的字节序列**，现在它是 `Uint8Array` 的子类，能和整个 TypedArray 体系互操作。
- **原理**：创建时容量定死、元素只能是 0–255 的字节；`Buffer.alloc(n)` 分配 n 字节并清零，`Buffer.from(x)` 从已有数据（字符串 / 数组 / `ArrayBuffer`）编码构造。
- **边界**：旧资料说它是"堆外分配的类数组对象"，这是老口径——现在应按"TypedArray 体系的一员"来答；未清零的 `Buffer(size)` 是废弃写法，会残留堆上旧数据、可能泄漏敏感信息，需要空白缓冲就用 `Buffer.alloc`。
- **追问**：字符串是"给人读的字符"，Buffer 是"给机器搬的字节"。

### Q14: Buffer 与 String 的区别？用字节数举例。（第 05 篇）

- **结论**：String 是带编码的字符序列，Buffer 是原始字节序列，**字符长度 ≠ 字节长度**。
- **原理**：字符串的长度按"字符"算，Buffer 的长度按"字节"算，中文与 emoji 在 UTF-8 下占多字节。

```js
'你好'.length;                 // 2（2 个字符）
Buffer.from('你好').length;    // 6（UTF-8 下每个汉字 3 字节）
Buffer.from('中文abc').length; // 9（中 3×2 + 英 1×3）
```

- **边界**：算 `Content-Length`、切分二进制协议帧、限制上传体积时必须用 `Buffer.length`；用字符长度会把内容算小，下游按错误长度截断，数据就乱了。
- **追问**：字节本身没有编码，"编码只是解读视角"——同一段字节用 `utf8` / `hex` / `base64` 读出的东西不同。

### Q15: Stream 的四种类型是什么？（第 05 篇）

- **结论**：Readable / Writable / Duplex / Transform，按"单向还是双向 × 是否转换"划分。
- **原理**：Readable 只生产数据（`fs.createReadStream`、HTTP 请求体）；Writable 只消费数据（`createWriteStream`、HTTP 响应）；Duplex 同时可读可写；Transform 是 Duplex 的特例，输入经转换再输出（gzip、加解密、格式转换）。
- **边界**：Stream 不是"文件相关"的东西——`net.Socket` 本身就是 Duplex Stream，`req` / `res` 分别是可读 / 可写流，`process.stdout` 也是流。
- **追问**：Buffer 是一块数据（水桶里的水），Stream 是数据的运输方式（水管），Stream 不断输送一个又一个 Buffer chunk。

### Q16: Readable Stream 的 flowing 和 paused 两种模式有什么区别？（第 05 篇）

- **结论**：flowing 模式靠 `data` 事件自动推数据，paused 模式靠 `read()` 主动拉数据。
- **原理**：监听 `data`、调用 `pipe()` 或 `resume()` 会切到 flowing；调用 `pause()` 或移除 `data` 监听会切回 paused，paused 下数据积在内部缓冲区里，由 `read()` 取走。

```js
readStream.on('data', (chunk) => console.log(chunk));            // flowing：推
readStream.on('readable', () => { let c; while ((c = readStream.read()) !== null) {} }); // paused：拉
```

- **边界**：flowing 方便但不消费就会丢数据，paused 控制更精细、适合自己实现背压。
- **追问**：`pipe` / `pipeline` 内部会自动管理模式切换与背压，绝大多数场景不必手写 `pause` / `resume`。

### Q17: EventEmitter 是什么？为什么 'error' 事件特殊？（第 04 篇）

- **结论**：EventEmitter 是 Node 事件驱动的骨架（发布-订阅），而 `error` 事件是它唯一"没有监听器就崩进程"的特例。
- **原理**：核心 API 就四步——`on` 注册、`emit` 触发、`once` 只触发一次、`off` / `listenerCount` 管理与观测；它是大量内置对象的基类，`net.Server`、`http.Server`、`fs.ReadStream`、`process` 的原型链上都有它。

```js
const emitter = new EventEmitter();
emitter.on('error', (err) => console.error('进程不会崩：', err));
emitter.emit('error', new Error('出事了')); // 被监听器接住
```

- **边界**：普通事件没监听器只是"没人响应"，`error` 事件没监听器则直接 `throw`，变成 `uncaughtException` 导致进程退出——这是有意为之的 fail-fast，避免错误被静默吞掉。
- **追问**：所以凡是可能 `emit('error')` 的对象，都要先 `on('error', handler)`，或在进程级用兜底监听器接住。

### Q18: child_process 的 spawn / exec / execFile / fork 差异在哪？（第 06 篇）

- **结论**：四把刀按"是否走 shell、是否缓冲全部输出、是否建 IPC"区分。
- **原理**：`spawn` 最基础、输出走流不缓冲，适合长时间运行 / 大输出；`exec` 走 shell、把输出全缓冲后回调，大输出会撑爆 `maxBuffer`；`execFile` 不经 shell 直接执行可执行文件，没有 shell 注入面、更安全；`fork` 专门创建 Node 子进程并额外建立 IPC 通道。
- **边界**：`spawn` 的 `stdio: 'inherit'` 让子进程共用父子标准输入输出，`detached: true` 配合 `child.unref()` 可让子进程脱离父进程独立运行。
- **追问**：口诀——流式大输出用 `spawn`，短命令拼 shell 用 `exec`，跑文件不要 shell 用 `execFile`，跑 Node 并通信用 `fork`。

## 二、机制与原理

### Q19: 为什么 Node.js 适合 I/O 密集型服务？（第 01 篇）

- **结论**：因为它擅长"等待的时候不闲着"——把等待从主线程交给内核，而不是让 CPU 空转在某个请求上。
- **原理**：一次 API 请求里 CPU 真正执行 JS 往往只有几毫秒，其余两三秒都在等数据库、缓存、下游服务、第三方 API 返回；非阻塞 I/O + 事件循环让主线程在等待窗口去处理别的请求，I/O 就绪后再执行回调。
- **边界**：这意味着瓶颈的判断标准是"时间花在算还是等"；等待占比极高的聚合网关、BFF、实时推送是它的主场，重计算不是。
- **追问**：等待本身无法消除（下游该两秒还是两秒），Node 只是把等待挪出了主线程。

### Q20: 为什么说 setTimeout(fn, 1000) 不准？setTimeout(fn, 0) 会立即执行吗？（第 03 篇）

- **结论**：第二个参数是**最小等待时间**而非精确执行时间，到期只代表回调"获得执行资格"；`setTimeout(fn, 0)` 同样不会立即执行。
- **原理**：Timer 到期时只是把 callback 放进 timers 阶段的队列，它还必须等主线程空闲；若主线程被一段 3 秒的同步循环占住，1 秒到期的回调也得等到 3 秒后才轮到。

```js
setTimeout(() => console.log('timeout'), 1000);
const start = Date.now();
while (Date.now() - start < 3000) {} // 实际约 3 秒后才打印 timeout
```

- **边界**：`0` 会被 clamp 到约 1ms；写同步代码时它只是"尽快排进 timers 阶段"，剩下的同步语句先跑完，下一轮才轮到它。
- **追问**：所以"定时任务不准时"通常是主线程被阻塞，而不是定时器精度问题。

### Q21: libuv 有哪六个阶段？其中哪个最重要？（第 03 篇）

- **结论**：六个阶段是 `timers → pending callbacks → idle/prepare → poll → check → close callbacks`，最重要的是 **poll**。
- **原理**：poll 是 I/O 核心，负责向内核获取新的 I/O 事件、执行已就绪的 I/O 回调；当没有待触发定时器、也没有 `setImmediate` 时，循环会停在 poll 阶段阻塞等待——这正是 Node 能"一直在线却几乎不占 CPU"的原因。
- **边界**：pending callbacks 处理被推迟到下一轮的系统级 I/O 回调，idle/prepare 是 Node 内部使用，日常几乎碰不到；check 是 `setImmediate` 的归属地，close callbacks 收尾资源关闭。

```
timers → pending callbacks → idle/prepare → poll → check → close callbacks → 下一轮
```

- **追问**：拿不准顺序时就按"阶段顺序"推导——poll 之后是 check，再往后才是下一轮的 timers。

### Q22: 网络 I/O 为什么不进 libuv 线程池？（第 03 篇）

- **结论**：因为内核本身能提供"socket 有数据时通知我"的机制，不需要开线程去阻塞轮询。
- **原理**：Node 把 socket 注册给 epoll / kqueue / IOCP，内核在数据到达时主动通知，libuv 在 poll 阶段取事件、调度回调；一个主线程就能管理成千上万个连接。
- **边界**：文件 I/O（`fs.readFile`）、部分 DNS（`dns.lookup`）、部分 crypto（`pbkdf2` / `scrypt`）、zlib 才会进线程池——因为它们要么 OS 没有统一高效的异步接口，要么本身就是偏阻塞 / CPU 型工作。
- **追问**：区分标准就一条"内核能否异步通知"；能通知就不进池，记成"网络 I/O 不进池，文件 / DNS / crypto / zlib 才进池"。

### Q23: 主模块里和 I/O 回调里，setImmediate 与 setTimeout(0) 谁先执行？（第 03 篇）

- **结论**：主模块里顺序**不确定**；写在 I/O 回调里 `setImmediate` 恒定先执行。
- **原理**：主模块里两者都被排到"下一轮循环"，`setTimeout(0)` 至少需要 1ms 才到期，谁先谁后受进程启动耗时影响；写在 I/O 回调里当前正处在 poll 阶段，紧接着就是 check 阶段。

```js
fs.readFile('./test.txt', () => {
  setTimeout(() => console.log('timeout'), 0);
  setImmediate(() => console.log('immediate'));
}); // 稳定输出：immediate → timeout
```

- **边界**：推演链路是"当前 poll → check（setImmediate）→ 下一轮 timers（setTimeout）"。
- **追问**：Node 20 之后 timer 时机有调整，所以不要背死亡结论，用阶段顺序推导。

### Q24: UV_THREADPOOL_SIZE 怎么调，有什么坑？（第 03 篇）

- **结论**：用环境变量在**进程启动前**设置，默认 4、上限 1024，且不是越大越好。
- **原理**：libuv 在进程启动时一次性读取该变量并创建线程，`UV_THREADPOOL_SIZE=8 node app.js` 才有效；线程数决定"同一时刻能并行跑几个 fs / crypto / dns / zlib 任务"。

```bash
UV_THREADPOOL_SIZE=8 node app.js
```

- **边界**：三个坑——① 运行时改 `process.env` 无效，启动后再改只是个字符串；② 线程过多会增加上下文切换开销，4 是多数场景的甜点值，要依据压测调；③ 它是**全局共享的一组线程**，`fs` / DNS / crypto / zlib 抢同一个池，把 crypto 开满就会挤占 `fs.readFile` 的并发能力。
- **追问**：可验证手段是并发发 10 个 `crypto.pbkdf2`，观察时间戳是否明显分成"4 个一批、后面的排队"。

### Q25: Node 20 / libuv 1.45 之后 timer 时机变了，哪些旧结论不能再背？（第 03 篇）

- **结论**：旧资料里"`timers → poll → timers` 本轮结束前再处理一次 Timer"的说法已经过时，现在每轮循环的 Timer 调度重点是 `poll → check → close → timers`。
- **原理**：从 libuv 1.45.0 / Node.js 20 起，Timer 主要被放到 poll 之后处理；libuv 仍会在**首次进入事件循环前**处理一次 Timer，以保持向后兼容。
- **边界**：这个变化会影响部分 `setImmediate()` 与 Timer 的时序关系，以前"某些定时器先跑"的推论在新版本里不再成立。

```
旧：timers → poll → timers（本轮结束前再处理一次）
新：poll → check → close → timers（Timer 主要放到 poll 之后）
```

- **追问**：看到任何事件循环文章，先问"写于哪一年、对应哪个 Node 版本"，然后用阶段顺序重新推，而不是记结论。

### Q26: process.nextTick 和 Promise.then 谁先执行？为什么？（第 03 篇）

- **结论**：`process.nextTick` 先于 `Promise.then`，同一检查点内永远是"先 nextTick、后 Promise"。
- **原理**：Node 把微任务拆成两条独立队列——nextTickQueue 与 Promise 微任务队列，处理顺序固定为"先清空 nextTickQueue，再清空 Promise 队列"，两条都清空到空才结束。
- **边界**：`process.nextTick` 不属于 Event Loop 的六个阶段，官方阶段图里根本没有它；它在 Call Stack 清空后、事件循环继续前立刻触发，所以优先级比所有宏任务、也比 Promise 微任务都高。

```js
process.nextTick(() => console.log('nextTick'));
Promise.resolve().then(() => console.log('promise'));
// 输出：nextTick → promise
```

- **追问**：不要理解成"每个阶段切换时才处理一次 nextTick"——每个 JS 回调返回调度层也是一个检查点。

### Q27: 微任务到底是什么时候被执行的？为什么说"不是一轮 Event Loop 才一次"？（第 03 篇）

- **结论**：微任务不是整轮 Event Loop 跑完才集中清空一次，而是**每次从 JS 回调返回调度层时都触发一次微任务检查点（microtask checkpoint）**。
- **原理**：每执行完一个宏任务回调，就把它新产生的 nextTick 和 Promise 微任务清空到空，再继续下一个回调。
- **边界**：最直观的证据是 `timer1 → promise → timer2`——两个 `setTimeout` 同处 timers 阶段，timer1 回调里注册的 Promise 在 timer1 返回时立刻被清空，而不是等整个 timers 阶段结束。

```js
setTimeout(() => {
  console.log('timer1');
  Promise.resolve().then(() => console.log('promise'));
}, 0);
setTimeout(() => console.log('timer2'), 0);
// 正确输出：timer1 → promise → timer2（不是 timer1 → timer2 → promise）
```

- **追问**：心智模型记成"每个回调之后清空一次微任务"，复杂输出题按"划同步 → 标检查点 → 先 nextTick 后 Promise → 再下一阶段宏任务"四步推。

### Q28: process.nextTick 和 setImmediate 有什么区别？该怎么选？（第 03 篇）

- **结论**：`nextTick` 在当前操作结束后立即执行、优先级极高且不属于任何阶段；`setImmediate` 排进下一轮 Event Loop 的 check 阶段。
- **原理**：`nextTick` 在 Call Stack 清空时立刻触发，`setImmediate` 在 poll 之后的 check 阶段执行，属于六个阶段之一，时机更靠后。
- **选型**：需要"延迟到当前操作之后、但尽量早"用 `nextTick`（例如先抛错再继续）；需要让出执行权、又不阻塞阶段推进用 `setImmediate`。
- **追问**：绝不要在 `nextTick` 里递归调度无限任务，那会饿死整个 Event Loop。

### Q29: 为什么递归调用 process.nextTick 会饿死 Event Loop？（第 03 篇）

- **结论**：因为 nextTick 队列的清空策略是"一直清空直到为空"，递归注册让队列永远不为空。
- **原理**：每次执行 `loop` 又往队列头注册自己，Event Loop 一直卡在清空 nextTick 上，进不了 poll / timers / check 任何一个阶段。

```js
function loop() {
  process.nextTick(loop);
}
loop(); // nextTick → 注册 nextTick → …队列永不为空
setTimeout(() => console.log('几乎执行不到'), 1000);
```

- **边界**：结果就是 I/O 回调与定时器回调全都无法执行，服务彻底失去响应，这是官方文档明确警告的 I/O starvation。
- **追问**：排障时若发现 timers 一直不触发，优先怀疑递归 `nextTick`；无限调度请改用 `setImmediate` 让出控制权。

### Q30: await 会阻塞事件循环吗？为什么？（第 04 篇）

- **结论**：不会。`await` 只暂停**当前 `async` 函数**的后续执行，主线程立刻腾出来处理别的回调和请求。
- **原理**：`await` 把函数后半段作为一个微任务挂起，等 Promise 就绪再回来继续；底层 I/O 仍是非阻塞的，事件循环照常运转。
- **边界**：把它理解成"在这里插一个书签、结果好了再回来接着跑"，而不是"整个程序停在这一行"；误以为会卡住程序，就会错判 async/await 比回调更慢。
- **追问**：`await` 阻塞的是"这个函数自己的后半段"，这才是需要警惕的部分。

### Q31: await 用得不对，会把并发写成串行吗？（第 04 篇）

- **结论**：会。两个互不依赖的 `await` 之间是串行执行的，延迟会线性累加。
- **原理**：`await` 的语义就是"等这个 Promise 好了再往下走"，所以逐个 `await` 等于逐个死等；并发要用 `Promise.all` 一次性发起。

```js
const a = await taskA();                              // 100ms
const b = await taskB();                              // 100ms
const c = await taskC();                              // 500ms → 合计约 700ms

const [x, y, z] = await Promise.all([taskA(), taskB(), taskC()]); // 约 500ms
```

- **边界**：在服务端尤其致命——一个请求往往要"取用户信息 + 读会话状态 + 查配置 + 调外部服务"，前几步彼此独立，写成串行会让端到端时延直接翻倍。
- **追问**：判断准则只有一条——两个 `await` 之间没有数据依赖，就该并发。

### Q32: Promise.all 和 Promise.allSettled 有什么区别？实战怎么选？（第 04 篇）

- **结论**：`all` 是"全有或全无"，`allSettled` 是"等全部结束、各自报状态"。
- **原理**：`all` 任一 reject 就整体 reject，其余已发起任务的成功结果也被丢弃；`allSettled` 返回每项 `{status, value | reason}`，永不因失败而整体失败。
- **边界**：另外两个工具一句话定位——`race` 谁先落定（成功或失败都算）就以谁为准，常用于加超时；`any` 谁先成功就以谁为准，全部失败才整体 reject。
- **选型**：事务性多步写库、步骤强依赖用 `all`；聚合多个下游接口的仪表盘用 `allSettled`。

### Q33: 什么是背压（Backpressure）？它解决了什么问题？（第 05 篇）

- **结论**：背压是 Stream 自动"踩刹车"的机制，解决"上游生产快、下游消费慢"导致缓冲堆积最终 OOM 的问题。
- **原理**：`writable.write(chunk)` 返回 `true` 表示缓冲没到阈值可以继续写，返回 `false` 表示内部缓冲已达上限、调用方应暂停读取；等下游消化完触发 `'drain'`，再恢复写入。

```js
if (!writable.write(chunk)) readable.pause();      // 踩刹车
writable.on('drain', () => readable.resume());      // 恢复搬运
```

- **边界**：磁盘读 500MB/s、网络只发 10MB/s 这种速度失配是典型场景；`pipe` / `pipeline` 内部已自动协调背压，无需手写 `pause` / `resume`。
- **追问**：手写背压容易出错，所以"内存一路涨最后 OOM"的排查方向之一就是"背压没做"。

### Q34: highWaterMark 的作用是什么？（第 05 篇）

- **结论**：它是可读 / 可写流内部缓冲区的"高水位阈值"，默认 64KB，是背压机制里"何时该踩刹车"的开关。
- **原理**：它既决定每次读取的块大小，也决定背压触发点——缓冲堆积到该阈值时 `write()` 返回 `false`、上游被要求暂停。
- **边界**：阈值调小更省内存但搬运次数变多，调大反之，本质是"内存占用"与"系统调用次数"的权衡。

```js
const reader = fs.createReadStream('./big.iso', { highWaterMark: 64 * 1024 });
```

- **追问**：它只管"缓冲到多大算到顶"，真正的限速动作由 `write()` 返回值与 `'drain'` 事件驱动。

### Q35: worker_threads 和 libuv 线程池有什么关系，为何不能混为一谈？（第 06 篇）

- **结论**：两者完全不同——一个是 Node 内部自动维护的隐藏线程，一个是你要主动 `new Worker()` 创建的 JS 线程。
- **原理**：libuv 线程池默认 4 个线程，专门跑 `fs` / `dns` / `crypto` / `zlib` 底层阻塞操作，你不直接创建也感知不到；`worker_threads` 有独立 V8 环境与执行上下文，跑你写的 JS 计算，还能共享 `SharedArrayBuffer`。
- **边界**：判断方法很直接——你写没写过 `new Worker()`？没写过却在跑文件 / 加密，那是 libuv 在干活；写过了，才是 `worker_threads`。

```
Node Process
 ├── Main JS Thread（V8 + Event Loop）
 │      └── libuv Worker Pool × 4（Node 内部用）
 └── Worker Thread（你 new Worker() 创建，有独立 V8）
```

- **追问**：官方定位是"libuv 线程池给 Node 内部用，worker_threads 给你用"。

### Q36: 为什么 Worker Thread 不用于普通 I/O？（第 06 篇）

- **结论**：因为普通 I/O 本来就是事件循环最擅长的事，每个请求都开 Worker 反而更慢。
- **原理**：`await fetch(...)`、查数据库、读文件这类操作，事件循环 + 异步 I/O 已经把"等"处理得很好；而每个请求 `new Worker` 都要付出"创建线程 → 初始化 V8 环境 → 跨线程传数据 → 销毁线程"的固定成本。
- **边界**：判别标准是一句话——I/O 密集（网络、文件、数据库 / 缓存调用）走 Event Loop；CPU 密集（大计算、加解密、压缩、大 JSON 解析）才走 Worker Threads。
- **追问**：把这两类任务放错位置，是"加了线程反而更慢"的常见根因。

### Q37: SharedArrayBuffer 的竞态与 Atomics 代价是什么？（第 06 篇）

- **结论**：共享内存让线程能直接改同一块数据、省掉了拷贝，但代价是失去隔离——"读 → 改 → 写"非原子就会丢更新。
- **原理**：两个 Worker 并发执行 `shared[i]++`，中间会被插空，最终结果偏小；`Atomics.add` 之类原子操作才能保证一步到位。

```js
shared[0]++;                    // ❌ 非原子：读旧值 → +1 → 写回，中间可能被插空
Atomics.add(arr, 0, 1);         // ✅ 原子加法
```

- **边界**：`Atomics` 带来同步开销与"锁与可见性"的心智负担；没有同步原语，共享内存几乎必然写出并发 Bug——**能共享是能力，会同步才是本事**。
- **追问**：这也是"要隔离用进程、要共享内存用线程"这条选型法则的底层原因。

### Q38: uncaughtException 和 unhandledRejection 有什么区别？（第 06 篇）

- **结论**：前者是同步代码抛出却没人 `catch`，后者是 Promise reject 了却没接住。
- **原理**：两者都是进程级的最后兜底入口；`unhandledRejection` 在 Node 15+ 默认也会终止进程。

```js
process.on('unhandledRejection', (reason) => console.error('未处理的拒绝：', reason));
process.on('uncaughtException', (err) => {
  console.error('未捕获异常：', err);
  process.exit(1); // 记录日志后体面退出，交给进程管理器拉起
});
```

- **边界**：异常能漏到 `uncaughtException` 这一层，说明进程内部状态已不可信（模块半初始化、状态写坏），官方不推荐继续运行，正确姿势是记日志 + 优雅退出。
- **追问**：真正的错误处理应分层——同步代码 `try/catch`、回调式 API 判第一个 `err`、Promise 用 `.catch`、路由与任务入口外层兜住，进程级监听器只做最后清理。

### Q39: 进程之间怎么通信？cluster 下主从通信有什么限制？（第 06 篇）

- **结论**：进程内存默认隔离，通信必须借助"进程外的公共通道"；cluster 下主从靠内置 IPC 通道，但子进程之间不能直连。
- **原理**：`fork` / `cluster.fork()` 底层都是创建子进程并自动建立 IPC 通道（Unix 域套接字或命名管道），主进程用 `worker.send()` / `child.send()` 下发，子进程用 `process.on('message')` 收、`process.send()` 回；消息经序列化传递，不支持函数与 Symbol。
- **边界**：cluster 的 IPC 不能直接广播到所有子进程（要手动遍历 `cluster.workers`），子进程之间也无法直接通信，必须经主进程转发；消息体过大时性能明显下降，且不共享内存。
- **选型**：同机父子 / 兄弟进程高频低延迟用 IPC，同机或跨机通用用 Socket，跨进程共享状态用 Redis，异步解耦削峰用消息队列，跨服务跨语言用 HTTP。

## 三、排障与选型

### Q40: 什么场景不该选 Node.js？（第 01 篇）

- **结论**：CPU 密集型场景不该选——执行 JS 的只有一个主线程，一段重计算会占住事件循环，期间所有请求一起阻塞。
- **原理**：大数运算、图像 / 视频编解码、复杂加密压缩、超大对象 `JSON.parse` 都属于这类；它们应交 Worker Thread 或子进程处理。
- **边界**：若业务以重计算为主、I/O 等待占比很低，Go / Java 这类多线程或协程模型往往更顺手。
- **追问**：判断口径是"先用一笔耗时账分清算与等，再谈选型"。

### Q41: 为什么 package-lock.json 必须提交到 Git？（第 02 篇）

- **结论**：不提交锁文件等于放弃了可复现构建，必然制造"在我机器上能跑"的漂移。
- **原理**：`package.json` 里的 `^4.18.0` 是范围不是精确值，不同时间、不同机器 `npm install` 可能装到不同补丁或次版本，依赖树就漂了；锁文件记录实际装上的每一层依赖的精确版本与内容哈希，把整棵树钉死。
- **边界**：它还能加快后续安装（少做版本求解），配合 `npm ci` 可严格按锁文件重建且更快，是 CI 与生产部署的推荐命令。
- **追问**：只改 `package.json` 不更新锁文件，或把锁文件加进 `.gitignore`，都会让"可复现"形同虚设。

### Q42: 为什么同步 API（如 readFileSync）不能上高并发路径？（第 05 篇）

- **结论**：同步 API 会阻塞事件循环直到 I/O 完成，期间整个进程什么异步任务都处理不了。
- **原理**：在高并发接口里，一次同步读盘就能让所有请求一起卡住——这正是"把异步模型打回阻塞原形"的写法。
- **边界**：同步版本只适合启动初始化、CLI 工具这类不在请求热路径上的场景；运行时频繁的文件操作请用 `node:fs/promises` 配合 `await` 与 `try/catch`。
- **追问**：同类要警惕的还有 `execSync`、超大对象同步 `JSON.parse`——它们的共同点是"占住唯一的主线程"。

### Q43: 为什么大文件必须用 Stream 而不是 readFile？（第 05 篇）

- **结论**：`readFile` 把整个文件读进内存，文件多大就占多少；Stream 一次只搬一小块，内存占用恒定。
- **原理**：Stream 默认每次读 64KB，数据从磁盘流入可读流、再流入可写流落盘，内存始终维持在几 KB 到几 MB。

```js
const reader = fs.createReadStream('./big.mp4');
const writer = fs.createWriteStream('./copy.mp4');
reader.pipe(writer); // 一边读一边写，全程不把整文件搬进内存
```

- **边界**：判断依据是"数据量可能超过可用内存"或"需要边产生边消费"；10GB 文件用 `readFile` 会直接撑爆进程堆并触发 OOM。
- **追问**：流式推送（日志、进度、大文件下载）也必须用流，否则客户端要等全部数据生成完才开始收到。

### Q44: pipe 与 pipeline 怎么选？（第 05 篇）

- **结论**：简单搬运用 `pipe`；链路长、要错误兜底、或要串联多个转换用 `pipeline`。
- **原理**：`pipe` 会内部协调读写速度与背压，比手写 `on('data', chunk => socket.write(chunk))` 安全得多；但它的短板是**下游出错不会自动销毁上游**，会留下悬挂的流与未释放的文件描述符。
- **边界**：`pipeline`（`node:stream/promises`）在任意一环出错时统一销毁所有流并抛出错误，还能顺序串联多个 Transform，生产代码更推荐。

```js
await pipeline(
  fs.createReadStream('./input.mp4'),
  createGzip(),
  fs.createWriteStream('./output.mp4.gz'),
); // 任意一环出错都会统一销毁整条链路
```

- **追问**："流式搬运用了 `on('data')` 手写、还没处理错误"是文件描述符泄漏的常见根因。

### Q45: 监听器泄漏怎么发现和处理？（第 04 篇）

- **结论**：现象是 `MaxListenersExceededWarning` 反复出现 + 内存缓慢上涨，根因是 `on` 了不 `off`。
- **原理**：EventEmitter 默认同一事件最多挂 10 个监听器；在循环或高频函数里反复 `on` 同一事件，监听器数量只增不减，闭包引用的对象也无法回收。
- **处理**：一次性监听用 `once` 自动移除；把监听器提取成具名函数并在合适时机 `off`；用 `emitter.listenerCount(event)` 监控某事件监听器数量是否异常增长。
- **追问**："内存一路涨最后 OOM"有两个典型方向——背压没做，或事件监听器泄漏。

### Q46: try/catch 能捕获哪些异步错误？（第 04 篇）

- **结论**：只能捕获同步 `throw` 和 `await` 到的 Promise 拒绝，捕获不到回调内部的异步抛出。
- **原理**：`setTimeout` 回调里的 `throw` 发生在 try/catch 作用域之外（那时调用栈已经换了一轮），异常会一路漏到进程级；而 `await asyncFn()` 的 reject 是同步回到当前函数，能被接住。

```js
try { setTimeout(() => { throw new Error('err'); }, 100); } catch (e) { /* 捕获不到 */ }
try { await asyncFunc(); } catch (e) { /* 能捕获 */ }
```

- **边界**：没用 `await` 的 Promise 要靠 `.catch()`；全局兜底用 `process.on('unhandledRejection')`。
- **追问**：所以回调式 API 必须判 `err`、Promise 必须有 `.catch`，二者不能靠一个外层 `try/catch` 一劳永逸。

### Q47: 进程和 Worker Thread 该怎么选？（第 06 篇）

- **结论**：要强隔离 / 跑外部程序 / 崩溃互不影响 → 进程；单纯把重计算挪出主线程、还要共享内存 → Worker（且走 Pool）。
- **原理**：进程内存独立、隔离性强、能跑 shell 与别的程序，但创建成本高、不能共享内存；Worker 同进程内、可共享 `SharedArrayBuffer`、成本低、非常适合 CPU 密集 JS，但隔离性弱，一个线程出错可能拖垮整进程。
- **边界**：Node 官方已明确——不需要进程级隔离时应优先考虑 `worker_threads`，所以"见多核就无脑上 cluster"是错的；cluster 的真正价值是进程级故障隔离与多核部署。
- **追问**：浓缩一句——I/O 用异步；CPU 用 Worker（走池）；要隔离或跑外部程序用子进程；要铺多核且要故障隔离用多进程。

### Q48: 为什么生产环境不能每个请求都 new Worker？（第 06 篇）

- **结论**：每请求一个 Worker 会让"建线程"本身成为新瓶颈，比主线程直接算还糟。
- **原理**：创建线程要付出新建、初始化 V8、跨线程传数据、销毁四笔成本；1 万并发就造 1 万个线程，线程创建与调度反而成瓶颈。

```js
app.get('/calculate', (req, res) => {
  const worker = new Worker('./worker.js'); // ❌ 每个请求都建一个
});
```

- **边界**：正确做法是 **Worker Pool + Task Queue**——按 CPU 核数预建固定数量的 Worker，请求把任务投进队列，空闲 Worker 取任务执行，线程数恒定可控。
- **追问**：最小实现要点是空闲标记、任务队列、轮询派发，对外用 `Promise` 包装成 `runTask(input)`。

```
CPU 8 核 → 预建固定数量 Worker（≈ 核数）
                │
        Task Queue（超额任务排队，而非新建线程）
           │    │    │    │
        Worker1 Worker2 Worker3 Worker4 …
```

### Q49: 收到 SIGTERM 后怎么做优雅关闭，为何不能直接 process.exit()？（第 06 篇）

- **结论**：先停收新连接 → 等在途请求归零（带超时兜底）→ 关外部依赖 → 最后退出，绝不能直接杀。
- **原理**：直接退出会掐断在途请求、来不及落库、日志丢失；正确顺序是 `server.close()` 停收新连接（并 `closeIdleConnections()` 关掉空闲 keep-alive），等待活跃请求归零，再依次关数据库 / 缓存 / 消息队列。

```js
process.on('SIGTERM', () => shutdown('SIGTERM'));
process.on('SIGINT', () => shutdown('SIGINT'));
// shutdown：server.close() → closeIdleConnections() → 等 activeRequests 归零（10s 超时）→ 关 DB/Redis → process.exit(0)
```

- **边界**：`docker stop` 与 K8s 滚动发布默认发 `SIGTERM`，线上必须接住；本地 `Ctrl+C` 发 `SIGINT`，两者都处理才能本地与线上一致体面退场。
- **追问**：若还有未清理的句柄或定时器，进程不会自动退出——所以清理完成后要显式退出。

### Q50: 为什么不该滥用 process.exit()？（第 06 篇）

- **结论**：`process.exit()` 会**立即**杀进程，跳过所有排队 I/O 与回调，导致日志没发、事务没提交、响应没结束。
- **原理**：它不经过任何收尾流程；Node 官方甚至指出——因错误必须结束进程时，让未捕获错误自然终止通常比随手 `process.exit()` 更安全，因为自然终止前 Node 会先跑完已排队的回调。
- **边界**：另一个常被忽略的点是 stdout——输出目标是管道或文件时写入是异步的，`process.exit()` 可能让最后几行日志根本没落盘。
- **追问**：生产环境真正要掌握的是三件事——`process.exitCode`（设码不立即杀）、Graceful Shutdown（先收摊再走）、Signal Handling（正确响应信号）。

### Q51: 一个 Node 服务 CPU 打满但 QPS 很低，你怎么定位？（第 07 篇）

- **结论**：**CPU 高 + QPS 低 = 主线程被占住（算），而不是 I/O 在等**。
- **原理**：用 `perf_hooks` 的 `eventLoopUtilization` 或 `process.hrtime` 看事件循环是否被长任务占住；用 `top` / `htop` 看是单核跑满还是多核均匀——单核跑满说明瓶颈在 JS 主线程。
- **边界**：定位到同步阻塞（`readFileSync`、大 JSON 同步解析、死循环式计算）就搬到 `worker_threads`；定位到"单进程只吃一个核"就上 `cluster` 铺多核。
- **追问**：定位顺序是"先分清算还是等，再看是单核还是多核"，不要一上来就加机器。

### Q52: 什么时候用 cluster，什么时候用 worker_threads？（第 07 篇）

- **结论**：要"分流计算且共享状态"用线程，要"多实例扛量与故障隔离"用进程。
- **原理**：`worker_threads` 在同一进程内把 CPU 密集的 JS 任务（压缩、加密、大 JSON 解析）offload 出去，可通过 `SharedArrayBuffer` 共享内存；`cluster` 的每个进程是独立实例、内存不共享，一个崩了不影响其他。
- **边界**：`cluster.fork()` 的数量应按 `os.availableParallelism()` 取，而不是硬编码核数或凭感觉。
- **追问**：只对 CPU 密集或需要故障隔离的场景才值得上多进程。

### Q53: 处理一个 2GB 的文件上传并转存，为什么不能用 fs.readFile？正确做法是什么？（第 07 篇）

- **结论**：`readFile` 会把 2GB 一次性读进内存，直接撑爆堆或触发 OOM；上传转存场景必须走流，且不需要落地临时文件。
- **原理**：上传接口里 `req` 本身就是可读流（它继承自 Stream），转存目标是 `fs.createWriteStream` 或对象存储 SDK 的可写流，`req.pipe(writeStream)` 即可边收边写，内存占用恒定在几十 KB 级。

```js
app.post('/upload', (req, res) => {
  const out = fs.createWriteStream('./uploads/big.bin');
  req.pipe(out);                       // 边收边写，不落整份内存
  out.on('finish', () => res.end('ok'));
});
```

- **边界**：多环节（限速 → 校验 → 转存）时用 `pipeline`，任一环出错统一销毁链路；客户端中断要监听 `req.aborted` / `'error'` 清理半截文件，否则会留下脏数据。
- **追问**：这题本质考"数据是字节流、要边读边搬"这一认知——内存占用应恒定，而不是随文件增大。

### Q54: 多开进程就一定能提升性能吗？什么场景下多开进程没用？（第 07 篇）

- **结论**：不一定。I/O 密集型瓶颈在"等待"，多开进程只是多占内存、解决不了等待问题。
- **原理**：单进程的事件循环本就能在等待时处理别的请求，加进程并不会让"等下游返回"变快；只有 CPU 密集（单进程单核跑满）或需要故障隔离时，多进程（`cluster` / 进程管理器 / 容器编排 + 负载均衡）才有意义。
- **边界**：判断依据还是那句——先测"事件循环利用率"，分清瓶颈是"算"还是"等"，再决定加不加进程。
- **追问**：同类误区还有"服务重启丢请求"——那也不是进程数量问题，而是没接住 `SIGTERM` 做优雅关闭。
