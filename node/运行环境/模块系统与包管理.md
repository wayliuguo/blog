# 模块系统：CommonJS 与 ES Module

## 为什么不能把所有代码写在一个文件里？

Node.js 项目里你不可能把所有逻辑都堆进一个 `index.js`。一个真实的后端服务通常会按职责把代码拆到不同目录，每个文件只负责一块功能，再用模块系统把它们拼起来：

```
src/
├── controllers/   处理 HTTP 请求入口，解析参数、返回响应
├── services/      业务逻辑，编排多个下游调用
├── models/        数据访问层，封装数据库读写
├── utils/         通用工具函数，如日期、校验、加密
├── config/        读取配置（端口、密钥、环境变量）
├── db/            建立并导出数据库连接
└── index.js       程序入口，启动服务、挂载路由
```

不同文件之间如何互相调用？靠的就是模块系统。它至少要解决三件事：怎么把一个文件里的东西"导出"、怎么在另一个文件里"导入"、以及导入时到底拿到的是值本身还是值的引用。Node.js 目前有两套并存的模块系统。

```
CommonJS   —— Node.js 早期自带的方案，后缀 .js / .cjs
ES Module  —— 语言标准的方案，后缀 .mjs / 配 type 的 .js
```

## CommonJS：用 require 和 module.exports 拼装程序

CommonJS 是 Node.js 的"出厂默认"。一个最朴素的导出，就是给 `module.exports` 赋值——下面这段摘自配套脚本 `02-module-cjs.cjs` 的 CJS 一侧，导出一个对象字面量（`count` 在导出那一刻就被快照进了对象，这正是后面要讲的"值的拷贝"）：

> 摘自 `./code/node-basics/src/02-module-cjs.cjs`（运行：`npm run 02cjs`）

```js
let count = 0

// 导出的是一个「对象字面量」，count 在导出那一刻就被取值快照下来了
module.exports = {
    TAG: 'CommonJS',
    count, // 快照，永远是 0
    inc() {
        count += 1
        return count
    }, // 改的是模块内部的变量
    peek() {
        return count
    } // 开个口子，证明内部真的变了
}
```

实测输出（`npm run 02cjs`，与 `npm run 02esm` 逐行相同）：

```
[CJS 模块体] 执行完毕，导出 = TAG, count, inc, peek
[ESM 模块体] 开始执行
[互操作 ESM→CJS] 值的拷贝：调用前 count = 0
[互操作 ESM→CJS] 调 inc() 后 count = 0 但 cjs.peek() = 1 （内部变了，外部看不到）
[互操作 CJS→ESM] 活绑定：调用前 count = 0
[互操作 CJS→ESM] 调 inc() 后 count = 1 （立刻同步）
```

导入时使用 `require`，拿到的是 `module.exports` 对象本身（同一路径多次 `require` 拿到的是同一个对象引用）。下面这段摘自 `01-cache.cjs`，它连 `require` 三次同一个模块：

> 摘自 `./code/node-basics/src/02-module-realm/01-cache.cjs`（运行：`npm run mr01`）

```js
console.log('=== 1) 连续三次 require 同一个自建模块 ===')
const a = require('./lib/counter.cjs')
const b = require('./lib/counter.cjs')
const c = require('./lib/counter.cjs')

console.log('a === b ?', a === b) // true：拿到的是同一个对象
console.log('b === c ?', b === c) // true
console.log('a === c ?', a === c) // true
console.log('以上说明：三次 require 共享同一个 module.exports 对象引用')
```

实测输出（`npm run mr01`，节选）：

```
=== 1) 连续三次 require 同一个自建模块 ===
[counter.cjs] 模块体被执行（同一个进程里只会看到一次，除非手动清缓存）
a === b ? true
b === c ? true
a === c ? true
以上说明：三次 require 共享同一个 module.exports 对象引用
```

`require` 接收的是模块标识符：以 `./` 或 `../` 开头是相对路径（Node 会去补 `.js` / `.json` / `.node` 扩展名并解析目录）；不以 `.` 开头则当作包名，去 `node_modules` 里找。

### 模块缓存：同一个文件只执行一次

`require` 不是每次都重新读文件、重新执行。Node 会把每个已加载模块的结果缓存在 `require.cache` 里，第二次 `require` 同一个路径时，直接返回缓存的 `module.exports`，模块顶层代码不会再跑一遍。

下面这段摘自 `01-cache.cjs`，先看 `require.cache` 里长什么样，再手动删掉缓存让模块体重新执行一遍：

> 摘自 `./code/node-basics/src/02-module-realm/01-cache.cjs`（运行：`npm run mr01`）

```js
const key = require.resolve('./lib/counter.cjs')
console.log('\n=== 2) 缓存表（require.cache）里长什么样 ===')
console.log('缓存键（绝对路径）:', key)
console.log('该路径在 require.cache 中:', Object.prototype.hasOwnProperty.call(require.cache, key))
console.log('缓存记录里的 loaded 标记:', require.cache[key].loaded)
console.log('是第几层缓存命中的：缓存对象的 id 与上面 a 一致 ->', require.cache[key].exports === a)
// …
console.log('\n=== 3) 手动删掉缓存，模块体就会再执行一次 ===')
delete require.cache[key]
const d = require('./lib/counter.cjs')
console.log('删缓存后再 require，取到的是新对象吗（与 a 不同）:', d !== a) // true
console.log('注意上面又打印了一次「模块体被执行」，说明缓存被删后真的重新跑了一遍')
console.log('\n结论：同一路径在本进程内只求值一次；要拿到「干净」的模块状态，必须先清 require.cache。')
```

实测输出（`npm run mr01`）：

```
=== 1) 连续三次 require 同一个自建模块 ===
[counter.cjs] 模块体被执行（同一个进程里只会看到一次，除非手动清缓存）
a === b ? true
b === c ? true
a === c ? true
以上说明：三次 require 共享同一个 module.exports 对象引用

=== 2) 缓存表（require.cache）里长什么样 ===
缓存键（绝对路径）: E:\working\blog\node\运行环境\code\node-basics\src\02-module-realm\lib\counter.cjs
该路径在 require.cache 中: true
缓存记录里的 loaded 标记: true
是第几层缓存命中的：缓存对象的 id 与上面 a 一致 -> true
整个 require.cache 中 counter.cjs 的记录条数: 1

=== 3) 手动删掉缓存，模块体就会再执行一次 ===
[counter.cjs] 模块体被执行（同一个进程里只会看到一次，除非手动清缓存）
删缓存后再 require，取到的是新对象吗（与 a 不同）: true
注意上面又打印了一次「模块体被执行」，说明缓存被删后真的重新跑了一遍

结论：同一路径在本进程内只求值一次；要拿到「干净」的模块状态，必须先清 require.cache。
```

这意味着：如果模块顶层有副作用（连数据库、起定时器、打印日志），它只会在第一次 `require` 时触发；这也是为什么循环依赖里可能拿到"还没初始化完"的半成品对象——模块执行到一半就把当前 `module.exports` 交出去缓存了。

### exports 与 module.exports 的陷阱

每个 CommonJS 文件里，`exports` 其实是 `module.exports` 的一个引用（`exports === module.exports` 初始为 `true`）。给 `exports.xxx` 赋值能生效，是因为你在给同一个对象挂属性。下面这段摘自 `02-exports-trap.cjs`，先验证这层引用关系：

> 摘自 `./code/node-basics/src/02-module-realm/02-exports-trap.cjs`（运行：`npm run mr02`）

```js
// 02 exports 与 module.exports 的陷阱
// 这一段在演示：exports 只是 module.exports 的快捷引用，最终被导出的一定是 module.exports。
console.log('=== 0) 本文件里 exports 和 module.exports 是不是同一个对象 ===')
console.log('exports === module.exports ?', exports === module.exports) // true
console.log('所以一开始给 exports.xxx 挂属性，等于给 module.exports 挂属性')
```

但一旦你**重新给 `module.exports` 赋值**，两者就分道扬镳了——后面挂到 `exports` 上的属性，外界再也拿不到。下面两个陷阱模块的源码（都摘自 `traps/` 目录）直接演示这件事。

第一个：直接给 `exports` 整体赋值，只是把局部变量指到新对象，`module.exports` 没动，外界 `require` 到的还是原来的空对象：

> 摘自 `./code/node-basics/src/02-module-realm/traps/exports-reassign.cjs`（运行：`npm run mr02`）

```js
// traps/exports-reassign.cjs —— 「直接给 exports 赋值」的陷阱模块（给 02-exports-trap.cjs 用）
// 这一段在演示：exports 只是模块外层包裹函数收到的一个参数（局部变量）。
// 给它整体重新赋值，只是把局部变量指向了新对象，module.exports 一动不动。
const exported = { viaReassignedExports: true }

// 下面这行只是把局部变量指到新对象，外界 require 到的仍然是那个最初的空对象 {}
exports = exported
```

第二个：替换 `module.exports` 之后再挂 `exports.xxx`，`viaExportsAfterOverwrite` 挂在了已经没人引用的老对象上，外界拿不到：

> 摘自 `./code/node-basics/src/02-module-realm/traps/module-exports-overwrite.cjs`（运行：`npm run mr02`）

```js
// traps/module-exports-overwrite.cjs —— 「替换 module.exports 之后再挂 exports」的陷阱模块
// 这一段在演示：整体替换导出对象之后，exports 与 module.exports 就分道扬镳了，
// 后面的 exports.xxx 全挂在那个已经没人引用的旧对象上，外界看不到。
module.exports = {
    viaModuleExports: true
}

// 失效的一行：这是老对象上的属性，不会被导出
exports.viaExportsAfterOverwrite = true
```

`02-exports-trap.cjs` 把上面两个陷阱模块 `require` 进来，验证外界真正拿到的是什么：

> 摘自 `./code/node-basics/src/02-module-realm/02-exports-trap.cjs`（运行：`npm run mr02`）

```js

const reassigned = require('./traps/exports-reassign.cjs')
console.log('模块里写了 exports = { viaReassignedExports: true }')
console.log('外界 require 到的却是:', reassigned)
console.log('是个空对象吗:', Object.keys(reassigned).length === 0)
console.log('原因：exports 只是模块包裹函数的一个参数，重新赋值只改了局部变量，module.exports 没动')
// …
console.log('\n=== 3) 陷阱二：替换 module.exports 之后再挂 exports ===')
const overwritten = require('./traps/module-exports-overwrite.cjs')
console.log('模块里写了 module.exports = { viaModuleExports: true }，之后才写 exports.viaExportsAfterOverwrite = true')
console.log('外界 require 到的:', overwritten)
console.log('viaModuleExports =', overwritten.viaModuleExports)
console.log(
    'viaExportsAfterOverwrite =',
    overwritten.viaExportsAfterOverwrite,
    '（undefined，挂在没人引用的老对象上了）'
)
console.log('\n结论：')
console.log('  整体替换导出对象 -> 写 module.exports = { ... }')
console.log('  增量挂属性       -> 写 exports.xxx = ...，且不要在之后重新赋值 module.exports')
```

实测输出（`npm run mr02`）：

```

所以一开始给 exports.xxx 挂属性，等于给 module.exports 挂属性

=== 1) 正确姿势：给共享对象挂属性，外部看得见 ===
require 到的对象: {
  name: 'node-basics-store',

=== 3) 陷阱二：替换 module.exports 之后再挂 exports ===
模块里写了 module.exports = { viaModuleExports: true }，之后才写 exports.viaExportsAfterOverwrite = true
```

记住一条铁律：最终被导出的是 `module.exports`，`exports` 只是它的快捷引用。要整体替换导出对象，用 `module.exports = ...`；要增量挂属性，用 `exports.xxx = ...`，且别在之后重赋值 `module.exports`。

## ES Module：用 import 和 export 描述依赖关系

ES Module（ESM）是 JavaScript 语言标准里的模块方案，语法和前端打包工具完全一致。导出用 `export`（含命名导出 `export function` / `export const` 与默认导出 `export default`），导入用 `import`。下面这段摘自 `02-module-esm.mjs` 的 ESM 一侧——导出的 `count` 是「活绑定」，模块内部一改，外部立刻可见；`import` 也演示了 ESM 默认导入一个 CJS 模块（拿到对方的 `module.exports`，正是「值的拷贝」）：

> 摘自 `./code/node-basics/src/02-module-esm.mjs`（运行：`npm run 02esm`）

```js
export const TAG = 'ES Module'
export let count = 0 // 外部读到的 count 会跟着变，不是快照
export function inc() {
    count += 1
    return count
}
// …
// 互相导入：ESM 引 CJS —— 直接默认导入，拿到对方的 module.exports。
// import 声明会被提升，写在哪儿都先执行，放后面只是让对照读起来更顺。
import cjs from './02-module-cjs.cjs'

console.log('[ESM 模块体] 开始执行')
console.log('[互操作 ESM→CJS] 值的拷贝：调用前 count =', cjs.count)
cjs.inc()
console.log(
    '[互操作 ESM→CJS] 调 inc() 后 count =',
    cjs.count,
    '但 cjs.peek() =',
    cjs.peek(),
    '（内部变了，外部看不到）'
)
```

实测输出（`npm run 02esm`，与 `npm run 02cjs` 逐行相同）：

```
[CJS 模块体] 执行完毕，导出 = TAG, count, inc, peek
[ESM 模块体] 开始执行
[互操作 ESM→CJS] 值的拷贝：调用前 count = 0
[互操作 ESM→CJS] 调 inc() 后 count = 0 但 cjs.peek() = 1 （内部变了，外部看不到）
[互操作 CJS→ESM] 活绑定：调用前 count = 0
[互操作 CJS→ESM] 调 inc() 后 count = 1 （立刻同步）
```

ESM 里导入路径通常要带扩展名（`./math.mjs` 而不是 `./math`）。它不会像 CommonJS 那样帮你猜测扩展名和补全路径——这正是"静态可分析"要付出的代价，也是它能做 Tree Shaking 的前提。

### 静态结构：import 会被提升到文件顶部

ESM 的 `import` 是静态的：在模块**求值之前**，引擎先扫描整个文件，把所有 `import` 收集起来建好依赖图，再按依赖顺序实例化。这带来两个直接结果：

- `import` 必须写在顶层作用域，不能写在 `if`、函数里根据条件动态决定，也不能用变量拼路径。
- 即便你把 `import` 写在文件最下面，它也会"提升"到模块体执行之前完成求值，所以不存在"在 import 之前用到导出"的时序问题。

```
文件被加载
   ↓
① 静态扫描所有 import，建立依赖图（编译期）
   ↓
② 按依赖顺序实例化绑定（live binding 就位）
   ↓
③ 才真正执行模块体里的普通语句
```

对比 CommonJS：它的 `require` 是普通函数调用，执行到那一行才去读文件、编译、运行，因此可以写进 `if`、可以动态拼路径。这正是两者"死板 vs 灵活"的分水岭。

## Node.js 怎么判断用哪套：type 字段与文件后缀

同一份 `.js` 文件，Node 到底按 CommonJS 还是 ESM 解析？决定权在两个地方，优先级如下：

1. **文件后缀强制指定**：`.cjs` 永远按 CommonJS，`.mjs` 永远按 ESM，后缀说了算，不受 `package.json` 影响。
2. **`package.json` 的 `type` 字段**：没有显式后缀时，看最近的 `package.json`。

`"type": "module"` 是一个"整包开关"——一旦声明，该目录及其子目录下所有 `.js` 文件都被当作 ESM；不写或写 `"type": "commonjs"`，则默认 CommonJS。

```json
{
  "type": "module"
}
```

这就是为什么很多项目要么全用 ESM 要么全用 CommonJS：一个 `.js` 到底是哪套，取决于它处于哪个 `package.json` 的作用域内。想在一个 ESM 包里保留个别 CommonJS 文件，就把它改名成 `.cjs`；反过来，在 CommonJS 包里写 ESM，就改成 `.mjs`。

```
my-app/
├── package.json        ("type": "module")
├── index.js            → 当作 ESM
├── legacy.cjs          → 强制 CommonJS（后缀优先）
└── lib/
    └── helper.js       → 当作 ESM（继承上层 type）
```

## require 与 import 的本质区别是什么？

这是面试里出现频率最高的问题，不能只答"一个是 CommonJS、一个是 ES Module"。真正要讲透的是背后的模块机制差异。

### 解析时机：运行时 vs 编译期

`require` 是运行时解析——代码执行到那一行，Node 才去定位、读文件、编译、执行模块，所以它可以写在条件分支里、可以动态拼接路径。

`import` 是编译期静态分析——进入文件后引擎先扫出全部依赖关系，在代码运行前就确定了完整的依赖图。代价是不能写进 `if`、不能动态拼路径，收益是依赖关系在加载前就一清二楚。

### 加载语义：值的拷贝 vs 值的引用

CommonJS 导出的是 `module.exports` 对象的**拷贝式引用**：导入方拿到的是当时那个对象的引用（更准确说，是导出那一刻把 `count` 的值拷进了 `exports` 对象），模块内部后续对原始局部变量的重新赋值，导入方看不到。

ESM 是**活绑定（live binding）**：导出的变量和模块内部的变量是同一个绑定，模块内部改了值，所有导入方实时同步。

下面这段摘自 `03-cjs-value-vs-esm-binding.mjs`，同一个文件里同时导入 CJS 计数器与 ESM 计数器，各自调一次 `increase()`，再读 `count`——CJS 快照仍是 0，ESM 活绑定变成 1：

> 摘自 `./code/node-basics/src/02-module-realm/03-cjs-value-vs-esm-binding.mjs`（运行：`npm run mr03`）

```js
import cjsCounter from './lib/counter.cjs'
import { count as cjsNamedCount } from './lib/counter.cjs'
import { count as esmCount, increase as esmIncrease } from './lib/counter.mjs'

console.log('=== 调用 increase() 之前 ===')
console.log(`CJS 快照 count = ${cjsCounter.count}`)
console.log(`ESM 活绑定 count = ${esmCount}`)
// …
console.log('\n=== 各调一次 increase() ===')
const cjsInside = cjsCounter.increase() // 改的是 counter.cjs 内部的局部变量
const esmInside = esmIncrease() // 改的就是 counter.mjs 里被导出的那个绑定
console.log(`CJS increase() 内部返回 = ${cjsInside}`)
console.log(`ESM increase() 内部返回 = ${esmInside}`)
// …
console.log(`ESM 活绑定 count = ${esmCount}    <- 变成 1 了`)
console.log(`CJS 命名导入 count = ${cjsNamedCount}    <- 同样是 0，命名导入也救不了它`)
// …
console.log(`cjsCounter.peek()（模块内部实时值）= ${cjsCounter.peek()}`)
console.log('内部其实已经是 1 了，只是 require 那一刻把 count 拷进了 exports 对象，外面永远停在拷贝时的 0')
```

实测输出（`npm run mr03`）：

```
=== 调用 increase() 之前 ===
CJS 快照 count = 0
ESM 活绑定 count = 0
两者初始都是 0，看不出区别

=== 各调一次 increase() ===
CJS increase() 内部返回 = 1
ESM increase() 内部返回 = 1

=== 调用之后，从外部再读一次 count ===
CJS 快照 count = 0    <- 还是 0
ESM 活绑定 count = 1    <- 变成 1 了
CJS 命名导入 count = 0    <- 同样是 0，命名导入也救不了它

=== 为什么：看 CJS 模块内部真实的值 ===
cjsCounter.peek()（模块内部实时值）= 1
内部其实已经是 1 了，只是 require 那一刻把 count 拷进了 exports 对象，外面永远停在拷贝时的 0

结论：
  CommonJS -> 值的拷贝，模块内部后续赋值导入方看不到，要同步得自己封装 getter
  ES Module -> 活绑定（live binding），模块内部一改，所有导入方实时同步
```

### 同步 vs 异步加载

`require` 是同步的：调用时必须"立刻拿到返回值"，因此无法等待一个 Promise，CommonJS 里也没有顶层 `await`。

`import` 是异步加载的：底层返回的是模块命名空间对象，ESM 还支持顶层 `await`——文件顶层直接 `await`，整个模块及其导入方会等它完成，适合在启动时连数据库、读配置。

### 互操作：两套系统能不能混用？

```
ESM → 引入 CommonJS   通常可直接 default import，Node 帮你把 module.exports 包成默认导出
CJS → 引入 ESM        Node 22 起可以直接 require 同步求值的 ESM（旧版本抛 ERR_REQUIRE_ESM）
CJS → 引入 ESM(顶层 await)  不能 require（同步等不了异步求值，抛 ERR_REQUIRE_ASYNC_MODULE），必须改用动态 import()
```

ESM 里用 CommonJS 包，一般直接 `import pkg from 'some-cjs-pkg'` 即可，`pkg` 就是对方的 `module.exports`。反向则要看 Node 版本：**Node 22 起 `require()` 已能同步加载 ESM**（前提是该 ESM 的求值过程不含顶层 `await`，`require` 返回带 `__esModule` 标记的命名空间对象），旧版本会抛 `ERR_REQUIRE_ESM`；而**含顶层 `await` 的 ESM 在任何版本都不能 `require`**——同步的 `require` 等不了异步求值，会抛 `ERR_REQUIRE_ASYNC_MODULE`，只能用动态 `import()`：

> 摘自 `./code/node-basics/src/02-module-realm/06-dynamic-import.cjs`（运行：`npm run mr06`）

```js
// 06 CommonJS 里用 await import() 动态导入 ESM
// 这一段在演示：import() 是「保留字形式的函数」，返回 Promise，
// 是 CJS 早期加载 ESM 的唯一手段，也能在 ESM 里用来做按需加载。
// …
    console.log('\n=== 5) 动态路径：import() 可以用变量拼路径，静态 import 不行 ===')
    const which = 'only-esm'
    const picked = await import(`./lib/${which}.mjs`)
    console.log(`import(\`./lib/${which}.mjs\`) 的 flavor =`, picked.flavor)
// …
    console.log('\n结论：')
    console.log('  require()  -> 同步、返回导出值本身、只能读 CJS（新版可读同步求值的 ESM）')
    console.log('  import()   -> 异步、返回 Promise<模块命名空间>、ESM/CJS 都能读，路径可动态拼')
    console.log('  在只能同步加载的老版本 Node 里，import() 是 CJS 触达 ESM 的唯一桥梁')
```

实测输出（`npm run mr06`）：

```
=== 1) require 是同步的：立刻拿到值 ===
require 返回值的类型: object | name = node-basics-store

=== 2) import() 是异步的：拿到的是一个 Promise ===
import() 的返回值是 Promise 吗: true
同一行代码后面，模块还没加载完，只能等它 resolve

=== 3) await 之后拿到的模块命名空间对象 ===
命名导出 flavor = ESM
命名导出 features = [ '静态依赖图', '活绑定', '顶层 await', '可 Tree Shaking' ]
default 导出 = { flavor: 'ESM', hello: [Function: hello], kind: 'default export' }
对象上的键 = [ 'default', 'features', 'flavor', 'hello' ]

=== 4) import() 对 CJS 同样有效（会包一层 default）===
import CJS 得到的键 = [ 'default', 'describe', 'name', 'version' ]
cjsNs.default.name = node-basics-store
cjsNs.name（命名绑定） = node-basics-store

=== 5) 动态路径：import() 可以用变量拼路径，静态 import 不行 ===
import(`./lib/only-esm.mjs`) 的 flavor = ESM

结论：
  require()  -> 同步、返回导出值本身、只能读 CJS（新版可读同步求值的 ESM）
  import()   -> 异步、返回 Promise<模块命名空间>、ESM/CJS 都能读，路径可动态拼
  在只能同步加载的老版本 Node 里，import() 是 CJS 触达 ESM 的唯一桥梁
```

动态 `import()` 是两套系统的"桥"：它返回 Promise，无论在 CommonJS 还是 ESM 里都能调用，也是渐进迁移老项目的推荐手段。

### 为什么 ESM 能做 Tree Shaking 而 CommonJS 不能？

Tree Shaking 指打包时把没被用到的导出代码删掉。它依赖于"编译期就能确定哪些导出被引用、且导出是静态可分析的"。

ESM 的 `import` / `export` 是静态语法，依赖图在解析阶段就固定了，打包器可以精确知道 `add` 被用了而 `subtract` 没被用，于是把后者整段丢掉。

CommonJS 的 `require` 是运行时函数调用，路径可以是变量、可以写在条件里，导出对象还能被整体替换，打包器在静态阶段根本无法证明"某个属性一定没被用到"，只能保守地全部保留。这就是为什么新项目更倾向 ESM——不仅语法统一，还能让打包产物更小。

```
ESM：  静态依赖图 → 精确知道用到哪些导出 → 删掉 dead code（Tree Shaking）
CJS：  运行时才知依赖 → 无法静态证明某导出无用 → 全部保留
```

## 依赖从哪来：npm 包管理

模块解决了"自己代码怎么拆分"，依赖解决了"别人的代码怎么引入"。Node 生态的包管理器是 npm，核心就是把包名和版本写进 `package.json`，再把实体下载到 `node_modules`。

### 从零开始：npm init 与 npm install

```bash
npm init        # 交互式生成 package.json
npm init -y     # 跳过交互，用默认值快速生成
npm install express     # 安装生产依赖（简写 npm i express）
npm install -D typescript  # 安装开发依赖（-D = --save-dev）
npm uninstall express      # 卸载
npm update                 # 按 package.json 的版本范围更新
```

`package.json` 里几个关键字段：

```json
{
  "name": "my-project",
  "version": "1.0.0",
  "main": "index.js",
  "scripts": {
    "start": "node index.js",
    "dev": "nodemon index.js"
  },
  "dependencies": {
    "express": "^4.18.0"
  },
  "devDependencies": {
    "typescript": "^5.0.0"
  }
}
```

### dependencies 与 devDependencies 的区别

`dependencies` 是**运行时真正需要的包**：服务跑起来、代码执行时要用（框架、数据库驱动、工具库）。`devDependencies` 是**只在开发期需要的包**：构建、测试、类型检查、代码格式化（TypeScript、Jest、ESLint）。

这个区分很关键：部署到生产环境时，`npm install --production` 只会装 `dependencies`，跳过 `devDependencies`，能显著减小镜像体积、缩短安装时间。

### scripts：把常用命令固化下来

`scripts` 把"启动、构建、测试"这类长命令固化成短名字，用 `npm run <名>` 调用（`start` / `test` 可省略 `run`）。它本质是在 `node_modules/.bin` 里找可执行文件，所以本地装的 CLI 不用写全局路径：

```bash
npm run dev     # 等价于执行 scripts.dev
npm start       # 等价于 node index.js
```

## 版本号怎么读：语义化版本

依赖版本写成 `主版本.次版本.补丁`（如 `4.18.2`），含义是：主版本变 = 不兼容的 API 改动；次版本变 = 向后兼容的新功能；补丁变 = 向后兼容的 bug 修复。版本范围符号决定 `npm install` 能装到多新：

```
^4.18.0  → 允许 4.x.x（不改变主版本），可升到 4.19.0
~4.18.0  → 允许 4.18.x（不改变前两位），只能升到 4.18.9
4.18.0   → 精确锁定，只装这一个版本
4.18.0-beta.1 → 预发布版本，默认不会被 ^ / ~ 自动选中
```

`^` 敢跨次版本（新功能通常不破坏旧调用），但不敢跨主版本（可能是破坏性升级）；`~` 更保守，连次版本都不变。`-beta` / `-rc` 这类预发布标签默认被 `^` `~` 排除，除非你显式写进去——避免生产环境无意间引入不稳定的预览版。

## 为什么必须提交锁文件：package-lock.json 的作用

`package.json` 里写的 `^4.18.0` 是个**范围**，不是精确值。今天装到 `4.18.2`，下周同事装可能变成 `4.19.0`，哪怕代码没变，依赖树也可能不同——这就是"在我机器上能跑"的根源。

`package-lock.json` 记录的是**实际装上的每一层依赖的精确版本与内容哈希**，把整棵依赖树钉死。它的作用有三点：

- 保证团队每个人、CI 机器装到的依赖树**完全一致**，可复现构建。
- 加快后续安装：npm 能直接按锁文件比对，少做版本求解。
- 配合 `npm ci`：它严格按锁文件安装、不写锁文件、更快，是 CI 和生产部署的推荐命令。

```
package.json   → "express": "^4.18.0"   （范围，会漂移）
package-lock.json → "express": "4.18.2"  （精确，钉死）
```

结论：**提交 `package.json` 时一定也要提交锁文件**。只改 `package.json` 不更新锁文件，或把它加进 `.gitignore`，都会让"可复现"形同虚设。

## node_modules 的扁平化与查找算法

`npm install` 后依赖落到 `node_modules`。从 npm v3 起它做了**扁平化（hoisting）**：不再把每个包的依赖层层嵌套，而是尽量把二级、三级依赖提升到顶层 `node_modules`，只有当版本冲突无法共存时才降级放进各自的子目录。这样既能复用同一份包、减小体积，又避免路径过深。

```
node_modules/
├── express/          （你的直接依赖，也在顶层）
├── body-parser/      （express 的依赖，被提升到顶层复用）
└── lodash/           （某包依赖，无冲突 → 提升到顶层）
```

而 `require('lodash')` 找文件时，走的是**从当前文件所在目录逐级向上**的查找算法：

```
/app/src/controllers/user.js
  require('lodash')
    → 查 /app/src/controllers/node_modules/lodash
    → 没有 → 查 /app/src/node_modules/lodash
    → 没有 → 查 /app/node_modules/lodash   ✓ 命中
    → 仍没有 → 继续向上，直到文件系统根 /node_modules
    → 全没有 → 抛 MODULE_NOT_FOUND
```

这个"就近优先、逐级向上"的规则，解释了为什么顶层 `node_modules` 里的包，能被任意子目录的代码 `require` 到，也解释了为什么装错层级会找不到包。`node_modules` 通常很大，应写进 `.gitignore` 不提交，靠 `package.json` + 锁文件重建。

代码文件之间已经能互相引用、依赖也能从 npm 装进来，但"这些文件怎么在同一进程里同时跑起来、I/O 怎么不互相阻塞"，靠的是另一套机制。下一篇就讲 Node.js 的发动机：事件循环。

## 小结

- **模块系统要解决三件事**：怎么导出、怎么导入、拿到的到底是值还是引用
- **CommonJS 的特点**
  - **模块缓存**：同一路径在本进程内只求值一次，`require.cache` 命中就不再读文件、不再跑顶层代码
  - **循环依赖**：模块执行到一半就把当前 `module.exports` 交出去缓存，所以可能拿到半成品
  - **`exports` 与 `module.exports`**：最终被导出的一定是 `module.exports`，`exports` 只是它的初始引用；整体重赋值 `module.exports` 后，挂在 `exports` 上的属性外界拿不到
- **ES Module 的特点**
  - **静态结构**：`import` 会被提升到模块体执行之前，依赖图在求值前就固定下来
  - **写法约束**：`import` 必须写顶层、不能条件化、不能拼路径，路径还要带扩展名
  - **Tree Shaking**：导出是静态语法，打包器能精确删掉没用到的导出；CJS 运行时才知依赖，只能全保留
  - **顶层 `await`**：模块顶层可以直接 `await`，整个模块及其导入方都会等它完成
- **二者的本质区别**
  1. **解析时机**：`require` 是运行时同步解析；`import` 在求值前先静态扫描建出依赖图
  2. **值的语义**：CJS 是值的拷贝（快照），导出方之后再改也看不见；ESM 是活绑定（live binding），导出方一改、导入方立刻同步
  3. **加载方式**：CJS 同步阻塞、没有顶层 `await`；ESM 异步加载（`import()` 立刻返回 Promise），且支持顶层 `await`
  4. **互操作**：ESM 引 CJS 直接 `import pkg from 'cjs-pkg'`；CJS 引 ESM 在 Node 22 起可直接 `require()`（限同步求值的 ESM，旧版本抛 `ERR_REQUIRE_ESM`），含顶层 `await` 的仍只能走动态 `import()`
- **模块类型怎么判定**
  - **两条规则**：`.cjs` 永远是 CommonJS、`.mjs` 永远是 ESM（后缀优先）；其余 `.js` 看最近的 `package.json` 的 `type` 字段
- **工程组织**
  - **目录拆分**：按 controllers / services / models / utils / config 分层
  - **npm 依赖分类与 scripts**：dependencies 是运行时必需、devDependencies 只在开发期，`npm install --production` 只装前者；脚本去 `node_modules/.bin` 找可执行文件
  - **语义化版本与锁文件**：`^4.18.0` 允许 4.x.x 会漂移，`~4.18.0` 只允许 4.18.x；`package-lock.json` 钉死实际版本与哈希，CI 用 `npm ci`
  - **`node_modules` 扁平化与查找算法**：npm v3 起把二三级依赖提升到顶层；require 从当前目录逐级向上找 node_modules，全没有抛 `MODULE_NOT_FOUND`
