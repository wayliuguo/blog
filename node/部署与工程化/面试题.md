# 模块面试题 · 工程化与拓展

题目按**总结大纲**章节分组，章号与 [`总结`](./总结.md) 一一对应；每题标注所属知识域（`N.N`），用「判 · 展 · 证 · 界」四槽作答（佐证按题型取舍、不硬填）。

## 1. 配置与环境

### Q1（1.1）｜ `.env` 有什么作用？多环境配置怎么组织？
- **判断**：`.env` 把配置从代码里剥出来，换来“同一份代码跑出不同行为”，多环境靠按环境拆文件。
- **展开**：拆分规则——`.env`（默认值，提交）、`.env.<环境>`（不提交）、`.env.example`（模板，提交）、`.env.local`（个人覆盖，不提交）。
- **佐证**：`@nestjs/config` 封装 dotenv，`envFilePath: [`.env.${NODE_ENV}`, '.env']` 数组越靠前优先级越高；完整链是 `process.env`（OS/容器，最高）> `.env.local` > `.env.<环境>` > `.env.example` > `.env`，符合 12-Factor“配置与代码分离”。
- **边界**：`.env*` 必须进 `.gitignore`、只留 `*.env.example`——密钥进 git 历史就永久留存，删掉也能从旧 commit 找回。

### Q2（1.1）｜ 容器/CI 场景为什么可能不读 `.env` 文件？
- **判断**：因为环境变量已由 Compose / CI 注入，再读 `.env` 文件反而会用旧值覆盖真实注入值。
- **展开**：判断口径是“已注入”就用 `process.env.DB_HOST` 是否存在作为信号——存在则跳过 dotenv 加载，交给容器注入的上游。
- **佐证**：`loadEnv`：`if (process.env.DB_HOST) return;` 否则 `.env.<NODE_ENV>` 存在才 `dotenv.config`。
- **边界**：这也是“本地读文件、容器用注入”统一加载策略的一环，开发与生产共用同一份逻辑。

### Q3（1.2）｜ `ConfigService.get<T>()` 的 `<T>` 会做运行时类型转换吗？
- **判断**：不会，泛型只告诉 TS 期望类型，运行时不做任何转换。
- **展开**：`get('app.port')` 默认返回 `any`，加 `{ infer: true }` 才得到精确的 `number`；真正的类型安全要靠 `registerAs` + `ConfigType<typeof X>` 从工厂返回值推断，加上 `ConfigKeyPaths` 展平点号路径。
- **佐证**：类型安全读取工具 `env` / `envNumber` / `envBoolean` 约 30 行自带转换与默认值；`envNumber` 遇非法值立刻 `throw`，避免带病启动。
- **边界**：类型安全保证“读得对类型”，保证不了“配的是有效值”——类型正确不等于配置合法，这靠启动校验兜底。

### Q4（1.3）｜ 生产环境为什么要做启动校验？
- **判断**：宁可启动失败、不可带病运行——配置错误越早暴露代价越低。
- **展开**：在 `registerAs` 工厂里直接抛错：`JWT_SECRET` 缺失或用占位符默认值（`'your-jwt-secret-change-me'`）就 `throw`，`ADMIN_USERNAME` / `ADMIN_PASSWORD` 同样必填。
- **佐证**：另配套扫 `.env.example` 生成的 `types/env.d.ts`，让 `process.env.XXX` 编辑期补全、拼错名称编译期报错；`.gitignore` 兜底防误提交密钥。
- **边界**：启动校验是“值正确性”的最后防线，弥补了类型安全只管“类型”的空白；三者互补才构成生产级配置体系。

## 2. 日志体系

### Q1（2.1）｜ 为什么 `console.log` 不能上生产？
- **判断**：它是一条没有级别、没有时间戳、不落文件、高并发下拖慢请求的 stdout 输出——生产日志该有的能力一项都没有。
- **展开**：四个硬伤——无法区分 debug/info/error 被海量日志淹没；无法定位时间；容器/服务器一重启就丢无法复盘；同步写 stdout 高并发下拖慢吞吐。
- **边界**：stdout 只适合“实时看”不适合“事后查”，`docker logs` 能看到不等于留得住；阻塞只是高并发下的一条副作用，**能力缺失 + stdout 不持久**才是主因。

### Q2（2.1）｜ 什么是日志分级？Winston 有哪些级别？
- **判断**：分级是按严重程度给日志贴标签，用“输出线”控制噪音；Winston 沿用 npm 级别，数字越小越严重。
- **展开**：`error`(0) / `warn`(1) / `info`(2) / `debug`(3) / `verbose`(4)；`level` 是最低输出线，设成 `info` 时 `debug`/`verbose` 被直接丢弃，省磁盘与 CPU；生产一般 `info`，debug 留给开发。
- **佐证**：级别走配置中心 `LOGGER_LEVEL`，线上排障可调级别不必发版。
- **边界**：级别只在“你记了”的前提下有用——关键路径没打日志，级别再细也查不出；入口、外部调用、异常兜底三处必须留错误日志。

### Q3（2.2）｜ 双写架构怎么让 NestJS 原生日志自定义化？
- **判断**：继承 `ConsoleLogger` 保留框架输出、同时由 Winston 写文件，调用方仍是 `this.logger.log`，业务代码零改动。
- **展开**：`LoggerService extends ConsoleLogger`，内部再初始化一个 Winston logger；`LoggerModule.forRoot()` 设 `global: true`，`main.ts` 配 `bufferLogs: true` + `app.useLogger()`，让 NestJS 内部日志一并走自定义 Logger。
- **佐证**：链路——`控制台 stdout → PM2 捕获 → docker logs`，与 `Winston → logs/app.%DATE%.log` 并行。
- **边界**：双写不是“存两份”，而是“控制台写入实时通道、文件写入可复盘通道”，各司其职。

### Q4（2.2）｜ 日志文件为什么按日轮转？错误日志为什么要独立文件？
- **判断**：按日轮转防止单文件无限膨胀并按日期归档；错误独立文件让排障不必在全量日志里 grep。
- **展开**：`DailyRotateFile` + `datePattern: 'YYYY-MM-DD'` + `maxFiles`（默认 31 天）；`app-error.%DATE%.log` 只落 error；`auditFile` 记录轮转状态，容器重启不重复处理旧文件。
- **佐证**：磁盘预算——JSON 日志每天约 10-50MB，保留 31 天预留 2GB+；异常增长优先查 `LOGGER_LEVEL`。
- **边界**：若只靠 `docker logs` 而不把落到文件，容器重启即丢——文件日志才是“留得住”的历史。

### Q5（2.3）｜ 一次请求的全链路日志是怎么串起来的？
- **判断**：靠一个贯穿请求生命周期的 trace ID——入口分配、异步上下文随处可取、每条日志自动带上。
- **展开**：用 `nestjs-cls`（基于 AsyncLocalStorage）给每个请求分配 ID，`LoggerService` 写日志前拼成 `[traceId] msg` 并放进结构化字段，排查时 `grep "<trace-id>" logs/app.<date>.log` 拉出从入口到库的完整路径。
- **边界**：trace ID 只在异步上下文能传下去的前提下有效——手动 `new` 的任务或未传上下文的地方取不到；跨进程要把它放进消息头传下去。

### Q6（2.3）｜ 生产环境的日志怎么查？三种方式什么时候用？
- **判断**：实时用 `docker logs`、历史用容器内文件、进程问题用 `pm2 logs`——判定依据是“实时看 stdout、历史看文件”。
- **展开**：`docker logs` 读容器 stdout（PM2 捕获的控制台输出）；文件日志是 Winston 写进 `/app/logs` 的 JSON（命名卷持久化）；`pm2 logs` 读 PM2 内存缓冲区。
- **佐证**：今天错误 `cat logs/app-error.$(date +%Y-%m-%d).log`；某接口 `grep "POST /api/xxx" logs/app.$(date +%Y-%m-%d).log`；带上下文搜错 `grep -C 2 '"level":"error"'`。
- **边界**：`docker logs` 与 `pm2 logs` 都随容器重启丢失，只有文件日志留得住——历史定位必须落到文件。

## 3. 进程管理

### Q1（3.1）｜ PM2 是什么？常用命令有哪些？
- **判断**：PM2 是 Node 的进程管家，一次解决裸跑的四宗罪——终端绑定、崩溃即停、只吃一核、日志无处可查。
- **展开**：`pm2 start dist/main.js` 把进程 daemon 化并接住崩溃自动拉起；`pm2 save` + `pm2 startup` 组合保证系统重启后自动恢复全部应用。
- **佐证**：`list`（状态/CPU/内存）、`logs <app> --lines 100`、`restart` / `reload`、`monit`、`describe`、`flush`。
- **边界**：PM2 日志是内存缓冲、不持久化，容器重启即丢——要查历史日志看文件日志 `logs/app.*.log`。

### Q2（3.2）｜ `ecosystem.config.js` 有哪些关键字段？
- **判断**：它把命令行参数变成可版本化、可复用的声明式配置。
- **展开**：`autorestart`（崩溃自动重启）、`max_memory_restart`（内存超限自动重启，防内存泄漏拖垮机器）、`exec_mode` / `instances`（进程模式与数量）、`env`（注入变量，`env_production` 区分环境）、`watch`（文件变更重启，仅开发用）。
- **佐证**：生产配置常见 `autorestart: true` + `exec_mode: 'fork'` + `instances: 1` + `max_memory_restart: '1G'`。
- **边界**：`watch` 绝不能上生产（每次保存都重启服务就是事故）；Docker 内 fork 单实例，水平扩展交给编排平台。

### Q3（3.3）｜ PM2 的 cluster 模式和 Node 自身 cluster 是什么关系？
- **判断**：是同一套东西——PM2 cluster 底层就是 Node 原生 `cluster` 模块，主进程按 worker 数起多进程、由主进程做轮询（Round-Robin）分发。
- **展开**：`instances: 'max'` 等于“按 CPU 核数起进程”；PM2 在原生 cluster 之上加了崩溃自动重启、日志收集、内存超限重启。
- **边界**：进程间内存不共享——Session、内存缓存、单机限流计数不能放进程内，必须外置到 Redis；cluster 只适合 Linux/macOS 裸机，Windows 行为异常、容器里也不该用。

### Q4（3.3）｜ Docker 容器里为什么用 fork 而不是 cluster？
- **判断**：容器内 cluster 等于“在编排平台之上再自己做一层负载均衡”，既重复又有害。
- **展开**：编排（Compose 多副本 / K8s）本就是水平扩展那一层，容器里再开 N 个进程会让资源计量、健康检查、信号（`SIGTERM` 该发给谁）全变复杂；所以生产写 `exec_mode: 'fork'` + `instances: 1`，PM2 只留进程监控、日志管理、内存限制三项职责。
- **边界**：反过来，没有编排平台的 Linux 裸机才用 cluster 吃满多核；Windows 或单机小项目 fork 单实例就够；这也是容器内 `pm2 reload` 没意义的原因（单进程无 worker 可换）。

### Q5（3.3）｜ 裸机、Docker、K8s 三层部署架构怎么演进？
- **判断**：演进主线是“裸机自己管进程 → 容器编排管副本 → 平台管一切”，PM2 角色从“负载均衡器”退化为“容器内进程管家”。
- **展开**：裸机为 `用户 → Nginx → PM2 cluster（多 worker）→ DB`；Docker 为 `用户 → Nginx → 容器（PM2 fork）×N 副本 → DB`；K8s 为 `Ingress → Pod（容器内 fork）→ DB`。
- **边界**：判断“多核利用归谁”的口径——裸机交 PM2 cluster、容器交副本数，别两边都做。

## 4. 容器化与编排

### Q1（4.1）｜ 镜像、容器、仓库分别是什么？之间什么关系？
- **判断**：镜像是只读模板（类/光盘），容器是镜像的运行实例（对象/光驱），仓库存储分发镜像；一个镜像可起多个容器。
- **展开**：Dockerfile 每条指令产出一个**只读层**，容器在镜像之上再加一层**可写层**——运行时改动都落可写层，删容器即丢、镜像本身不变。
- **边界**：可写层不是持久化方案——数据库、日志要留住必须挂数据卷或绑宿主目录，否则容器重建即没。

### Q2（4.1）｜ Dockerfile 里 COPY 和 ADD 怎么选？
- **判断**：默认用 `COPY`；`ADD` 多出“从 URL 下载”和“自动解压本地 tar”两个隐式行为，只在确实要解压时用。
- **展开**：`COPY` 只做一件事——把构建上下文文件复制到镜像路径；`ADD` 的隐式解压/下载会令构建结果依赖网络和压缩包内容，破坏可复现性。
- **佐证**：多阶段里几乎只用 `COPY`，跨阶段复制靠 `COPY --from=<stage>`；构建上下文瘦身靠 `.dockerignore`（`node_modules`、`.git`、`.env`、`*.md`）。
- **边界**：上下文越小，`docker build` 传给守护进程的字节越少、构建越快。

### Q3（4.2）｜ Docker 多阶段构建为什么能给镜像瘦身？
- **判断**：因为“构建用的环境不必进运行镜像”——多个 `FROM` 各自独立阶段，最终镜像只 `COPY --from=<stage>` 拿产物。
- **展开**：单阶段把源码、全量依赖、TS/ESLint 全打进镜像（约 1GB）；多阶段拆 `deps → build → prod-deps → runtime`：build 装全量依赖编译出 dist、prod-deps 用 `--prod` 只装生产依赖、runtime 只复制 dist + 生产 node_modules，体积降到约 200MB。
- **佐证**：`COPY package*.json` 在前、源码在后，依赖没变时缓存命中跳过安装；`--frozen-lockfile` 保证各环境依赖版本一致。
- **边界**：瘦身不等于安全——还要 `USER node` 非 root、固定基础版本（`node:20.16.0-alpine`）保证可复现。

### Q4（4.2）｜ 生产级 Dockerfile 有哪些安全与就绪要素？
- **判断**：非 root 最小权限 + 端点级 HEALTHCHECK + ARG/LABEL 元数据 + exec 形式 ENTRYPOINT。
- **展开**：`USER node` 运行、`chown` 只授权 `logs`/`dist`（不遍历 node_modules）；`HEALTHCHECK` 用 `wget --spider http://localhost:$APP_PORT/api/health` 探接口真正就绪（非端口监听）；`ARG`+`LABEL` 写版本与构建时间供 `docker inspect` 溯源；`ENTRYPOINT` exec 形式成 PID 1 正确收 SIGTERM 优雅关闭。
- **佐证**：`--mount=type=cache` 把依赖缓存挂为构建缓存不进镜像层；`ARG TZ=Asia/Shanghai` 保证日志时间戳与定时任务正确。
- **边界**：健康检查必须**端点级**而非端口级——端口通只说明进程在，接口能返回 200 才说明依赖的库与缓存都就绪。

### Q5（4.3）｜ Compose 与 `docker run` 是什么关系？
- **判断**：`docker run` 是一条命令起一个容器，Compose 是一份 YAML 声明一组服务——Compose 不替代 Docker，而是把参数、网络、卷、启动顺序变成可版本化的文件。
- **展开**：起 app+MySQL+Redis 三个容器，`docker run` 要敲三串参数、手动 `--link`、重启要重组织命令；Compose 一条 `up -d` 全部拉起，并自动建网做 DNS 解析，容器间直接用**服务名互访**。
- **场景**：`docker run` 适合临时调试单个容器；涉及“应用+数据库+缓存”的组合就该上 Compose。
- **边界**：Compose 是单机编排，跨宿主机要 K8s/Swarm；`depends_on` 默认只等容器启动、不等服务就绪，要真就绪必须配 `condition` + `healthcheck`。

### Q6（4.4）｜ 生产为什么把基础设施和应用拆成两个 compose 文件？
- **判断**：因为两者生命周期不同——数据库几年不动、应用天天更新，绑一个文件每次发版都怕数据库被顺带重启。
- **展开**：拆成 `docker-compose.infra.prod.yml`（MySQL+Redis，一次性 `up -d` 不管，配 `restart: always`、数据挂宿主目录、Redis `--appendonly yes --appendfsync everysec`）与 `docker-compose.prod.yml`（migration+应用，日常部署）。
- **收益**：部署模式可切换——自建 Docker / 上云 RDS / 混合，切换只改 `.env`（`DB_HOST` 换成 `host.docker.internal` 或云地址），编排一行不动。
- **边界**：拆开后两文件靠**显式命名网络**（`name: show_track_net`）互通；端口只绑 `127.0.0.1:${APP_PORT}`、对外只留 Nginx 一个入口，安全面最小。

### Q7（4.4）｜ `depends_on` 的 `service_completed_successfully` 解决什么问题？
- **判断**：默认 `depends_on` 只保证依赖**启动了**、不保证服务**就绪**；`condition: service_completed_successfully` 保证依赖**成功跑完并退出**，专门串一次性迁移 Job。
- **展开**：迁移 Job 与业务容器共用同一镜像、只把 `entrypoint` 换成迁移脚本、`restart: 'no'`（一次性失败不重试）；应用侧 `depends_on: migration: condition: service_completed_successfully`，迁移失败应用根本不会启动。
- **边界**：长驻服务要用 `condition: service_healthy`（配 healthcheck），不是 `service_completed_successfully`；`depends_on` 只管单机 Compose 内的顺序，跨服务/宿主机靠健康检查或重试。
- **追问**：为什么不让应用启动时自己跑迁移？多实例并发跑会锁冲突写脏数据；应用有 bug 时迁移也跑不了，表结构该修却修不了。

## 5. 网关与反向代理

### Q1（5.1）｜ 正向代理和反向代理的区别？
- **判断**：正向代理代理**客户端**访问外部（公司内网出口），反向代理代理**服务端**接收请求（Nginx 网关）——区别在“替谁出面”。
- **展开**：正向代理时客户端知道在用代理、服务端只看到代理；反向代理时客户端以为直接访问服务、背后的实例与网络拓扑被完全隐藏。
- **佐证**：后端说的“加一层代理”几乎都是反向代理——统一入口、SSL 终结、负载均衡、动静分离、Gzip 都在这一层做。
- **边界**：反向代理会改写请求来源，应用拿到的地址是 Nginx 的 IP；要真实 IP 必须让 Nginx 传 `X-Real-IP` / `X-Forwarded-For`，并在应用层解析。

### Q2（5.2）｜ 装了 Nginx 之后应用为什么拿不到真实客户端 IP？
- **判断**：因为请求是 Nginx 转发过来的，应用看到的来源地址就是 Nginx 的地址，真实 IP 只能靠代理头带过来。
- **展开**：Nginx 侧要显式 `proxy_set_header X-Real-IP $remote_addr` 和 `X-Forwarded-For $proxy_add_x_forwarded_for`（后者在已有值后追加形成完整转发链）；应用侧再从这两个头里取。
- **影响面**：不解析会让**日志、限流、风控、黑名单全部失真**——所有请求看起来来自同一 IP，按 IP 限流会直接限死全站。
- **边界**：`X-Forwarded-For` 客户端可伪造，只应信任你自己那层代理追加的值；Nest/Express 要配 `trust proxy`，`req.ip` 才会是真实客户端 IP。

### Q3（5.2）｜ Nginx 代理 WebSocket 要配哪几项？
- **判断**：四件套——`Upgrade $http_upgrade`、`Connection "upgrade"`、`proxy_http_version 1.1`、`proxy_read_timeout`（及 `proxy_send_timeout`）调长，缺一条前端握手失败。
- **展开**：前两项让协议升级为 WebSocket，HTTP/1.1 才支持长连接，超时时间设 300s 让长连接不被打断。
- **佐证**：History 模式回退另需 `try_files $uri $uri/ /index.html`；Gzip 配 `gzip on` + `gzip_types` 指定文本 MIME + `gzip_comp_level 9` 减小传输体积。
- **边界**：静态资源与 WS 是不同 location，别混在同一个配置块里。

### Q4（5.3）｜ Nginx 报 502 和 504，分别往哪查？
- **判断**：502 是“连不上/上游给的不是合法响应”，504 是“连上了但超时没等到响应”。
- **展开**：502（Bad Gateway）常见于后端进程没起、端口写错、容器挂了；504（Gateway Timeout）说明连接建立但处理超过 `proxy_read_timeout`。
- **佐证**：排查顺序——先确认后端活着（`docker ps`、`curl 127.0.0.1:3000/api/health`），再看 Nginx `error.log` 区分 connect refused（→502）还是 upstream timed out（→504）。
- **边界**：应用只绑 `127.0.0.1` 时 Nginx 必须转发到宿主机回环地址，写成容器 IP 就 502；有 WebSocket 或慢接口要调 `proxy_read_timeout`，否则正常的慢请求也会被当 504。

### Q5（5.3）｜ PM2、Docker、Nginx 三者在生产里各管什么？
- **判断**：Nginx 管**入口**（收请求、SSL 终结、静态资源、反代、负载均衡），Docker 管**环境与隔离**，PM2 管**容器内的 Node 进程**（故障恢复、内存限制、日志收集）。
- **展开**：三者不重叠也不替代，典型链路 `用户 → 宿主机 Nginx（唯一公网入口）→ Docker 容器（PM2 fork 单进程）× N 副本 → MySQL/Redis`。
- **边界**：职责会随架构漂移——裸机时代 PM2 是“负载均衡器+进程管家”，有容器编排后退化为“容器内进程管家”；判断“某件事该谁做”的口径是**看这一层是否已有人做了**。

## 6. 发布与 CI/CD

### Q1（6.1）｜ `synchronize: true` 为什么是生产定时炸弹？
- **判断**：因为它让“改 Entity”直接等于“改生产表结构”，而生产表里全是真数据。
- **展开**：四个后果——不可审计（谁改/何时改/改了什么无从追溯）、不可回滚（出问题只能手工修）、数据丢失（Entity 删字段→重启→列被删）、不可审查（变更进不了 Code Review）。
- **佐证**：附加伤害——库已和实体同步，`migration:generate` 对比不出差异，迁移机制被自己堵死。
- **边界**：只适合早期原型；进入协作开发就要关掉，表结构变更全由迁移文件控制，本地改成“改 Entity→generate→run→起应用”。

### Q2（6.1）｜ 迁移为什么“天生幂等”？跑多少遍都安全吗？
- **判断**：安全——TypeORM 维护一张 `migrations` 表记录已执行迁移，`migration:run` 每次先对比、只跑没执行过的。
- **展开**：执行流程——连库 → 检查/创建 `migrations` 表 → 读 `dist/migrations/*.js` → 对比已执行 → 按时间戳执行未跑过的 `up()` → 每执行完插记录；无待执行时输出 `"No migrations are pending"` 退出。
- **佐证**：`up()`/`down()` 默认包事务，某个失败整体回滚，不留半完成表结构；但已成功的不会自动回滚，要撤销须显式 `migration:revert`。
- **边界**：已有数据不被框架触碰，除非某个 `up()` 显式写 `DROP`/`DELETE`/`TRUNCATE`——破坏性变更必须人工确认，不能进自动流水线。

### Q3（6.2）｜ 迁移为什么必须独立于应用启动、并与业务容器分离？
- **判断**：因为“迁移该在应用之前、且只跑一次”，而“应用可能多副本、可能起不来”。
- **展开**：两个理由——① 多实例每个业务容器都跑迁移会**并发锁冲突、产生脏数据**；② 应用有 bug 起不来时表结构该修还得修，所以迁移 CLI **不经过 NestJS DI 容器**，只依赖编译产物+环境变量。
- **佐证**：`node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`；落地成一次性 Job 容器，共用镜像、只换 entrypoint、`restart: 'no'`，业务用 `depends_on` 等它 `service_completed_successfully`。
- **边界**：三个 DataSource 分工要分清——本地迁移吃 TS 源码（免 build）、生产迁移吃 `dist/**/*.js`（免 ts-node）、应用运行时由 `@nestjs/config` 加载；三者 `synchronize` 都应为 false。

### Q4（6.3）｜ 容器起来就反复重启，你怎么定位？
- **判断**：按“容器活着吗→健康吗→应用说什么→是不是依赖问题→是不是被重启过”五步走，别一上来改代码。
- **展开**：`docker logs <c> --tail 50` 看启动报错；`docker inspect <c>` 看 `State.Health.Status` 与 `ExitCode`；再到 MySQL 容器日志、`pm2 logs <app> --lines 50 --nostream` 看是否被内存超限重启。
- **佐证**：常见根因——数据库未就绪（迁移没跑完 / wait-for-it 没配）、环境变量缺失（启动校验抛错，如 `JWT_SECRET` 没配）、端口冲突、健康检查失败（应用起来了但 `/api/health` 依赖的 Redis 不通）。
- **边界**：健康检查必须端点级而非端口级——口通只说明进程在，接口能返回 200 才说明依赖的库与缓存都就绪。

### Q5（6.3）｜ 从零到线上一次完整部署要做哪些事、怎么验证？
- **判断**：主线是“配置→起基础设施→跑迁移→起应用→接 Nginx→验证”；核心原则是**数据库与缓存是外部服务，compose 堆栈只管 migration + 应用**。
- **展开**：`cp .env.example .env.production` 填真实值 → `docker compose -f infra.prod.yml up -d`（一次性）→ `docker compose -f prod.yml up -d --build`（日常命令）→ 配 Nginx 反代到 `127.0.0.1:3000`。
- **佐证**：`up -d --build` 背后——五阶段构建 → migration 容器等 MySQL 跑迁移 → app 容器等迁移成功、PM2 fork 拉起 NestJS → HEALTHCHECK 探 `/api/health` → `curl 127.0.0.1:3000/api/health` 验证。
- **边界**：备份独立于部署验证——自建 MySQL 靠宿主目录+定时 `mysqldump`、云库靠云服务方，生产至少每日全量；“部署成功”与“有备份”是两件事。

### Q6（6.4）｜ CI/CD 为什么拆成 build 和 deploy 两条流水线？
- **判断**：因为“构建”和“部署”是两件事，触发条件和失败后果都不同——拆开后构建失败不触发部署，deploy 还能在多台服务器复用。
- **展开**：build 由 `push: tags: ['v*']` 触发，云端构建镜像并推 `stable`（最新稳定）+ `v1.0.0`（此版本）两 tag；deploy 由 `workflow_run: types: [completed]` + `if: success` 触发，SSH 到服务器执行 `docker compose pull` + `up -d`。
- **收益**：构建从服务器挪到云端 CI，服务器只拉镜像、重启容器；回滚变成“用旧 tag 再部署一次”，秒级。
- **边界**：镜像 tag 要唯一可追溯（版本与构建时间经 `ARG`/`LABEL` 写元数据）；Secrets 建专用部署密钥对，不复用日常账号。

### Q7（6.4）｜ 线上发版出问题怎么回滚？破坏性迁移为什么不自动跑？
- **判断**：回滚 = 用旧版本 tag 再走一次部署（拉旧镜像+重启容器），秒级完成；破坏性迁移（`DROP`/重命名）因**不可逆**必须人工确认后手动执行。
- **展开**：镜像打了 `stable` 与 `v1.0.0` 两 tag，回滚时把旧 tag 推上去触发同一套流水线 `pull`+`up -d`；破坏性迁移自动化没有“看一眼”的机会，安全的变更全自动、危险的留人工。
- **边界**：回滚不是万能的——**已执行的迁移不会跟着回滚**；“代码回滚 + 列已删”是灾难，破坏性变更要和代码发布分开，顺序是“先做兼容（新代码同时兼容新旧表结构）→ 再清理旧字段”。

### Q8（6.3）｜ 场景题：为生产 Node 应用设计健康检查与监控方案
- **判断**：服务要能自证“活着且有依赖可用”（端点级健康检查），异常能被探针发现并自动摘除/重启，超阈值要告警。
- **展开**：`GET /api/health` 返回 `{ status, uptime, timestamp }` 并探依赖（数据库连接池、Redis 连通性），任一不可用返回 503、标出哪个组件 `down`；容器层用端点级 `HEALTHCHECK --start-period` 留给迁移与预热；编排层靠 `condition: service_healthy` 重启/摘流量；进程层 PM2 `max_memory_restart: '1G'` + `autorestart`。
- **佐证**：指标采 `process.memoryUsage()` 看 heapUsed 是否持续上涨不回落（内存泄漏信号）、事件循环延迟 + `process.hrtime` 判主线程被占、`os` 模块采 CPU/内存；告警阈值 CPU>80%、内存>80%、事件循环延迟>200ms、5xx>1%。
- **边界**：健康检查**不能查重依赖或做慢操作**（否则探针自己成了压力源）；`start-period` 留给迁移与缓存预热；告警阈值先宽松再收紧，否则上线第一周全在响、很快被屏蔽。

## 7. 脚手架开发

### Q1（7.1）｜ 什么是脚手架？核心流程是什么？
- **判断**：脚手架是把“建项目骨架”自动化的 CLI——敲一条命令、交互式问答，然后生成一套填好变量的项目模板。
- **展开**：`bin/index.js` 用 `inquirer` 收集参数（项目名、模板类型），用 `fs-extra` 的 `copy` 把 `templates/<类型>` 复制到目标目录，再把 <code v-pre>{{projectName}}</code> 占位符替换成真实值，最后打印 `cd xxx && npm install` 提示下一步。
- **佐证**：流程——用户输入命令 → 交互问答 → 复制模板 → 替换变量 → 输出项目。
- **边界**：模板可来自本地目录或远程仓库；**装依赖通常不自己做**，交给用户——脚手架里跑安装会拉长等待、失败率还高。

### Q2（7.2）｜ 脚手架入口文件怎么让命令全局可用？
- **判断**：`bin/index.js` 首行 `#!/usr/bin/env node`，`package.json` 的 `bin` 字段映射成全局命令名，`npm link` 或全局安装后即可当命令用。
- **展开**：`bin` 写成 `"create-my-app": "./bin/index.js"`，文件顶部的 shebang 声明用 node 执行；依赖分工——inquirer 管交互问答、fs-extra 管目录复制（比原生 fs 多递归与覆盖便利）。
- **佐证**：`package.json` 的 `bin` 字段 + 首行 `#!/usr/bin/env node` 共同让命令可全局执行。
- **边界**：交互式问答（inquirer）和参数式（yargs）是两条并列入口——CI 里没有 TTY，脚手架必须支持全参数化执行，否则在流水线里直接用不了。

### Q3（7.2）｜ 为什么用 yargs / commander 而不是自己解析 `process.argv`？
- **判断**：因为参数解析的“脏活”全在边界情形上，而不在 `argv` 取值本身；专业库已把这些情形处理完。
- **展开**：`process.argv` 拿到的是原始字符串数组，位置参数、`--option value` 与 `--option=value`、短别名（`-t api`）、布尔开关、默认值、类型转换、非法值报错、`--help` 生成——每条都得自己写；yargs 用 `command` + `positional` + `option` 声明式描述，自带 `choices` 校验与 `help()` 输出。
- **佐证**：`yargs(hideBin(process.argv)).command('create <name>', b => b.positional('name', {type:'string'}).option('template', {alias:'t', choices:['basic','api'], default:'basic'}), argv => {...}).help()`。
- **边界**：参数十几个、子命令三四个以上时声明式收益才明显；参数极少的内部脚本直接读 `process.argv[2]` 反而更清楚，不必为了“规范”引入依赖。

## 8. 异步与消息队列

### Q1（8.1）｜ 消息队列解决了什么问题？
- **判断**：三件事——**异步处理、削峰填谷、解耦**，把“下单要等扣库存+发短信+发邮件+加积分”变成“用户只等下单”。
- **展开**：生产者发完消息立刻返回，消费者各自异步处理；突发流量先入队缓冲，消费者按自身能力取，下游不会被瞬间打垮；生产者不必知道谁在消费，新增消费者不改生产者。
- **边界**：代价是复杂度——消息可能丢失、重复、乱序，还要多运维一套中间件；需立刻拿结果的强实时调用不适合走队列。
- **追问**：引入队列后必须配套——可靠投递（确认/重试）、消费幂等（去重）、可观测（积压量告警）。

### Q2（8.2）｜ Kafka 的核心概念有哪些？
- **判断**：Producer、Consumer、Topic、Partition、Broker、Consumer Group 六个。
- **展开**：Topic 是逻辑分类（类似表）；Partition 是存储与并行消费的最小单位，**分区内有序、跨分区无序**；Broker 是集群节点，一个 Topic 分区分散在不同 Broker；Consumer Group 内每个分区只被组内一个消费者消费——组内负载均衡、组间独立消费。
- **佐证**：要让同一订单事件有序，用 `orderId` 作分区键，让同一订单消息永远落进同一分区。
- **边界**：分区数决定最大并行度——消费者多于分区时多出来的空转；分区太多又推高文件句柄与选举开销。

### Q3（8.2）｜ `acks` 0/1/-1 分别意味着什么？怎么选？
- **判断**：`acks` 控制生产者等几层确认——`0` 不等（最快、可能丢）、`1` 等 Leader 写入（默认、折中）、`-1`（`all`）等所有 ISR 副本写入（最安全、最慢）。
- **展开**：`acks=1` 的漏洞在 Leader 刚写完还没同步给 Follower 就宕机；`acks=-1` 要求所有同步副本都落盘才返回，持久性最强。
- **佐证**：日志/埋点容忍少量丢失用 `0`；核心交易用 `-1`，但必须同时设 `min.insync.replicas >= 2`、`replication.factor >= 3`，否则“所有 ISR”可能只剩 Leader 一个副本等于白设。
- **边界**：`acks=-1` 不等于绝对不丢（所有 ISR 都宕机时仍可能丢）且明显降吞吐；`min.insync.replicas` 设过高时副本不足会直接拒绝写入。

### Q4（8.2）｜ 消息不丢失要在哪三端做保障？
- **判断**：生产端、Broker 端、消费端各做一段，缺一段链路就断——没有“某一端开了就万无一失”的开关。
- **展开**：**生产端**设 `acks=-1`、开启重试（`retries > 0`）、确认发送结果；**Broker 端**设 `replication.factor >= 3`、`min.insync.replicas >= 2`、`unclean.leader.election.enable=false`（不让非 ISR 副本选成 Leader）；**消费端**关掉 `enable.auto.commit`，业务处理成功后再手动提交 offset。
- **边界**：严格不丢必然降吞吐，重试会带来**重复消息**——所以“不丢”的另一半是幂等（业务唯一键+去重表）；消费端正解是“至少一次+幂等”，别指望中间件给“恰好一次”。

### Q5（8.2）｜ Kafka 和 RabbitMQ 怎么选？
- **判断**：看两个维度——**吞吐量 vs 路由灵活性**：要百万级吞吐、流式处理选 Kafka；要灵活路由、低延迟、完善确认机制选 RabbitMQ。
- **展开**：Kafka 是拉模型+顺序写盘+批量压缩，吞吐极高，靠分区并行消费；RabbitMQ 是推模型，支持 direct/topic/fanout/headers 多种交换机、路由灵活，ACK/NACK 与死信、延迟队列成熟，但吞吐通常在万级。
- **佐证**：日志收集/埋点/指标/流计算 → Kafka；订单处理/任务分发/通知推送/异步 RPC → RabbitMQ；只解耦一个简单异步任务又已有 Redis → Redis Stream 最省事。
- **边界**：别只看吞吐——还要看运维能力（Kafka 高可用集群有成本）、顺序要求（Kafka 只保证分区内有序）、延迟消息（RabbitMQ 有现成方案）。

### Q6（8.1）｜ 场景题：下单成功后异步通知商家、扣库存、发短信，怎么设计？
- **判断**：把“用户等待”缩到只剩下单本身，其余全部异步；可靠性与幂等分开处理——中间件保证“至少一次送到”，“重复了也不出错”是业务自己的责任。
- **展开**：选型——可靠投递+灵活路由选 RabbitMQ，已有 Redis 只解耦轻量任务选 Redis Stream，极高吞吐/事件流回放才上 Kafka；消息结构带 `traceId` 才和下单请求日志串起来；订单**写库成功后**发消息（用事务性发件箱保证最终一致，否则会“订单建了、消息没发”）；消费者拆多个队列（sms/merchant/inventory）各自独立消费。
- **佐证**：手动 ACK——成功 `channel.ack(msg)`、失败 `channel.nack(msg, false, true)` 重新入队，重试超 3 次进死信队列；幂等用 `orderId + eventType` 做唯一键（Redis `SETNX` 或数据库唯一索引），命中即 ACK 跳过。
- **边界**：至少一次投递必然带来重复，幂等不是可选项；死信队列必须有人看，只积压不处理等于消息丢了；要监控积压量——积压是“消费者已经跟不上”的第一信号。

## 9. 性能优化

### Q1（9.1）｜ 缓存穿透、缓存击穿、缓存雪崩分别是什么？
- **判断**：穿透 = 查**不存在**的数据每次都打到库；击穿 = **单个热点 key** 刚过期大量请求同时打到库；雪崩 = **大批 key 同时过期**库里压力暴增。
- **展开**：三者现象都是“数据库被打”，区分靠三点——key 存不存在、同时过期多少个、是不是同一个 key。
- **佐证**：穿透用缓存空值（短 TTL）+布隆过滤器前置拦截；击穿用互斥锁重建或热点 key 逻辑过期（异步续期）；雪崩用过期时间加随机抖动+多级缓存。
- **边界**：任何一层缓存都要配降级——缓存整体不可用时是“放请求去数据库”还是“直接返回兜底值”必须事先定好，不能等出事现场决定。

### Q2（9.1）｜ 热点 Key 怎么解决？
- **判断**：核心是“别让所有请求挤在同一个 key / 同一个节点上”——本地缓存、key 复制分散、读写分离、分片集群四种手段。
- **展开**：热点 key 在 Redis 单线程模型下会串行处理，把节点打满还易触发击穿；**本地缓存**挡掉绝大部分读；**key 复制**把 `hot:item` 拆成 `hot:item:0..N` 随机打一个副本；**读写分离**把读流量分到从节点；**Cluster** 从 key 层面先散开。
- **边界**：本地缓存带来多实例数据不一致（各机副本过期时间不同），只适合“能容忍几秒延迟”的热点；key 复制抬高写入成本与内存占用，写一次写 N 份。
- **追问**：怎么自动发现热点 key？服务端采样统计、客户端统计访问频次上报，不要靠人工猜。

### Q3（9.2）｜ 限流算法怎么选？
- **判断**：要**允许突发**用令牌桶；要**绝对平滑**用漏桶；要**统计精确**用滑动窗口；只图快用固定窗口计数器（有边界突刺）。
- **展开**：计数器在固定窗口内计数，简单但窗口交界处能放过两倍流量；滑动窗口把小时间片加起来，精度高、内存与计算开销大；令牌桶按固定速率放令牌、桶满丢弃，桶容量决定允许多大突发；漏桶无论进来多少都匀速流出，是“整流”而非“限流”。
- **佐证**：普通 API 首选令牌桶（能吸收秒杀峰值）；登录/短信这类敏感接口用固定窗口计数器配极低阈值就够；需严格保护下游时用漏桶。
- **边界**：单机用进程内计数器即可，**多实例必须走 Redis**，且用 Lua 脚本把“取数+判断+写回”做原子，否则每个副本各限一份、总量是 N 倍。

### Q4（9.2）｜ 场景题：为 API 设计一套限流方案
- **判断**：限流的目标不是“拒绝”而是“保护下游”——分层按维度设阈值，让恶意流量在触达昂贵资源（数据库、外部接口）前就被挡住。
- **展开**：算法主用滑动窗口（Redis Sorted Set）或令牌桶（Lua 保证原子）；限流维度分层——全局总 QPS、敏感接口（登录/短信）每分钟、单用户每秒、单 IP 每分钟；实现用 NestJS `ThrottlerGuard` + 自定义 `@Throttle({limit, ttl})`，存储换 Redis 支持多实例。
- **佐证**：返回 `429 Too Many Requests` + `Retry-After` 头，客户端才知道是“被限了、稍后重试”而非“服务坏了”；网关层（Nginx `limit_req`）先做粗粒度、应用层做细粒度，两层联动。
- **边界**：按 IP 限流要用真实 IP（否则一限限死全站）；NAT 后公司出口/运营商网关用户共用一个 IP，按 IP 限流前先看真实 IP 分布；限流挡“量”、熔断处理“下游已坏”，只有限流没熔断下游挂了照样全赔进去。

### Q5（9.3）｜ 数据库优化有哪些手段？
- **判断**：五手段——索引优化、慢查询日志、连接池、读写分离、分库分表。
- **展开**：索引合理建避免全表扫描；慢查询日志定位慢 SQL + EXPLAIN 分析；连接池复用连接避免频繁创建；读写分离主库写从库读；分库分表在数据量大时水平拆分。
- **边界**：手段有适用位次——先建索引与查慢查询，再谈读写分离与分库分表，后者代价高，过早分库分表会引入巨大复杂度。

## 10. 安全防线

### Q1（10.1）｜ SQL 注入、XSS、CSRF 分别是什么？怎么防？
- **判断**：SQL 注入 = 恶意 SQL 片段拼进查询，防在**数据访问层**（参数化查询）；XSS = 注入恶意脚本，根源是输出未编码，防在**输出层**；CSRF = 诱导用户不知情操作，靠 CSRF Token 防。
- **展开**：`pool.query('SELECT * FROM users WHERE id = ?', [id])` 让输入永远只是数据、不参与 SQL 语法解析，ORM 默认这么做；拼接字符串才是漏洞源头。XSS 在 HTML 输出时转义 `<` `>`（模板引擎与 React/Vue 默认转义），`dangerouslySetInnerHTML`/`v-html` 是破坏默认转义的入口；CSRF 用 token 校验请求来源。
- **佐证**：NestJS 里 XSS 用模板转义 + `Content-Security-Policy` + `HttpOnly` Cookie 兜底；CSRF 用 `csurf` 中间件。
- **边界**：输入校验（`ValidationPipe` 的 `whitelist`）是必需基础防线，但它替代不了输出编码——XSS 的根在输出，不在输入校验。

### Q2（10.2）｜ Helmet、CORS、参数校验各解决什么？
- **判断**：Helmet 批量设安全响应头、CORS 显式声明跨域来源、参数校验只收 DTO 声明字段——三层互补、缺一不可。
- **展开**：`app.use(helmet())` 一个调用批量设 CSP、HttpOnly 等安全头，成本低收益高；CORS 开发可放开 `app.enableCors()`、生产必须 `origin` 白名单，带 Cookie 时 `credentials: true` 与前端 `withCredentials` 成对配；`ValidationPipe({ whitelist, forbidNonWhitelisted })` 永远不信任输入、只放行 DTO 声明字段。
- **佐证**：`credentials: true` 时不能用 `*`，生产要写具体域名；`maxAge` 缓存预检请求。
- **边界**：CORS 是浏览器侧限制、服务端到服务端的请求不受它管，别把它当 API 鉴权；参数校验兜“字段”，安全检查兜“头”，输出编码兜“内容”，各管一段。

## 11. 测试与设计模式

### Q1（11.1）｜ 单元测试和集成测试的区别？
- **判断**：单元测试测**单个函数/类**、隔离外部依赖、极快；集成测试测**模块间协作**、要起应用上下文（甚至真数据库与 HTTP）、慢。
- **展开**：单元测试用 Mock 把数据库、网络、外部服务全替换掉，只验逻辑分支；集成测试用 `Test.createTestingModule({ imports: [AppModule] })` + `createNestApplication()` 起真应用，再用 Supertest 打 HTTP，验证“Controller→Service→数据库”整条链。
- **佐证**：测试金字塔建议单元:集成:E2E ≈ 7:2:1——底层多、顶层少。
- **边界**：单元测试定位精确跑得快，但 Mock 过头就变成“实现细节快照”，重构一行就红一片；关键链路真实性得靠集成测试兜底。

### Q2（11.1）｜ Mock、Stub、Spy 的区别？
- **判断**：Stub 管**返回值**（状态验证），Mock 管**交互行为**（是否被调、调了几次、参数是什么），Spy 在真实对象上**旁听**调用、不改变实现。
- **展开**：Stub 给依赖预设返回值让被测代码能独立跑完；Mock 在返回值之外还记录调用轨迹用来断言行为；Spy 包一层真实方法、可顺便断言 `toHaveBeenCalledWith`。
- **佐证**：Jest 里 `jest.fn().mockResolvedValue(...)` 既是 Stub 也是 Mock；`jest.spyOn(obj, 'method')` 是 Spy，加 `.mockResolvedValue` 就变 Stub。
- **边界**：只在需要验证“确实调了”时才用 Mock；把每个依赖都 Mock 一遍，测试就绑死在实现细节上——测的是“代码怎么写”，不是“代码对不对”。

### Q3（11.2）｜ 单例和工厂模式在 NestJS 里怎么体现？
- **判断**：单例是 **DI 容器的默认作用域**（`@Injectable()` 不写 scope 就是单例），工厂是**自定义 Provider 的 `useFactory`**。
- **展开**：容器首次解析某 Provider 时创建实例并缓存，之后所有模块注进来都是同一个（构造只执行一次）；`useFactory` 把“怎么造这个对象”交给一个函数，可声明 `inject` 依赖、可 async，适合“要读配置才能造”“要异步建连接”的对象。
- **佐证**：`{ provide: 'DB_CONNECTION', useFactory: (cfg: ConfigService) => cfg.get('NODE_ENV')==='production' ? createProd(cfg) : createDev(cfg), inject: [ConfigService] }`。
- **边界**：`useFactory` 造的实例默认也是单例（除非显式配 scope）；有状态服务（请求级缓存、请求上下文）不能挂单例，否则一个请求写的数据下一个请求能看到——该用 `Scope.REQUEST` 或显式传参。

### Q4（11.2）｜ 策略、观察者、装饰器模式在 NestJS 里怎么体现？
- **判断**：**策略** = 统一接口+多个实现+运行时按条件选（Guard 与自定义 Provider 常用于此）；**观察者** = `@nestjs/event-emitter` 的 `emit` / `@OnEvent`；**装饰器** = 整个框架的骨架（`@Controller()`/`@Module()`/`@Injectable()`/`@Get()`/`@UseGuards()`）。
- **展开**：策略常见两种落地——注入单个策略（`@Inject('AUTH_STRATEGY')`）或把策略收进 `Map` 按 `type` 取，消掉一长串 `if/else`；观察者里发布方 `this.eventEmitter.emit('order.created', order)`、监听方 `@OnEvent('order.created')`，发布方完全不知道谁在听。
- **佐证**：装饰器本质是给类和属性附加元数据，Nest 启动时用 `Reflector` 读元数据决定行为；多个装饰器执行顺序从下到上、从右到左。
- **边界**：观察者解耦的代价是调用链变隐式——“谁处理了这个事件”要全局搜事件名，事件一多就难调试；监听器抛异常可能影响主流程，要单独兜住。

## 12. 系统设计与协作

### Q1（12.1）｜ 什么时候该拆微服务？拆分原则是什么？
- **判断**：按**业务边界**拆，不按技术分层拆——四条原则：高内聚低耦合、单一职责、**数据独立**（各自一个库）、独立部署与扩展。
- **展开**：每个服务对应一个业务域（用户/订单/商品/支付/通知），服务间只通过 API 或消息队列通信，**不允许跨服务直连数据库**——一旦共享库，拆开就形同虚设。
- **判断依据**：该拆的信号是“某个模块的变更频率、扩缩容需求或团队归属明显和其他部分不同”；这些都没出现时，单体+清晰模块划分的收益更大。
- **边界**：拆早了代价很重——分布式事务、服务发现、链路追踪、跨服务调试全要提前付；拆太细会变成“微服务地狱”，一个业务动作要串五六个服务。

### Q2（12.1）｜ NestJS 里微服务怎么连通？WebSocket 网关怎么用？
- **判断**：微服务用 `ClientsModule.register` 声明传输做客户端代理、WebSocket 用 `@WebSocketGateway` 声明网关；前者走消息通道、后者走长连接。
- **展开**：`ClientsModule.register([{ name, transport: Transport.TCP, options }])` 后 `client.send({ cmd }, payload)` 发消息；传输可选 TCP/Redis/Kafka/RabbitMQ。WebSocket 网关用 `@WebSocketGateway({ namespace, cors })` 声明命名空间与跨域，`handleConnection` 处理连接，`@SubscribeMessage` 处理消息、`server.emit` 广播给所有客户端。
- **边界**：微服务同步用 HTTP/gRPC、异步用消息队列是两套通信模型；系 broker 有重建连接负担、长连接要关注心跳与超时。

### Q3（12.2）｜ 高可用要靠哪几类机制组合？
- **判断**：五类——**冗余部署、负载均衡、健康检查、熔断降级、限流**；再配**进程守护**与**优雅退出**才闭环。
- **展开**：多副本+负载均衡解决“单点”；健康检查把故障实例自动摘除；熔断降级让下游故障不拖垮自己；限流防突发流量打穿。进程守护（PM2 `autorestart`/容器 `restart: always`）保证崩溃自愈；优雅退出（接 `SIGTERM` → 停收新连接 → 等在途请求归零 → 关依赖 → 退出）保证发布不丢请求。
- **边界**：**别忘了依赖也是单点**——数据库、Redis、消息队列的高可用要单独设计，应用层做得再好一个单机 MySQL 挂掉照样全站不可用；容器/K8s 滚动发布默认发 `SIGTERM`，应用没接住会出现发布期零星 502。

### Q4（12.3）｜ `git merge` 和 `git rebase` 的区别？
- **判断**：`merge` 保留分支历史并生成一个合并提交；`rebase` 把你的提交**重放到**目标分支顶端，历史线性、但提交被改写。
- **展开**：rebase 会为每个被搬运的提交算新的 hash——所以**已推送的公共分支绝不能 rebase**，别人手里的旧提交还在，一推就分叉成两份历史。
- **佐证**：个人 feature 分支保持整洁、跟进 main 用 `git rebase main`；合并进 main 用 merge，或干脆在 PR 上 squash 成一个提交。
- **边界**：rebase 要逐提交解冲突（可能解多次）、merge 只解一次；`git cherry-pick` 是另一种“搬提交”，只挑单个提交到当前分支，常用于把热修复回移到发布分支。

### Q5（12.3）｜ Git 工作流怎么选？Code Review 有哪些实践？
- **判断**：三种工作流各适其境——GitHub Flow 适小团队持续部署、Git Flow 适中大型版本发布、Trunk-Based 适高频发布且 CI/CD 成熟。
- **展开**：GitHub Flow = main + feature + PR 合并；Git Flow = main + develop + feature + release 四线；Trunk-Based = 人人 main 上开发 + 短命分支。Code Review 实践——PR 单次控制在 200~300 行以内、先理解整体逻辑再看细节、指出问题的同时给建议、用“建议”代替“要求”；审查清单覆盖代码规范、不必要复杂性、异常处理、安全漏洞、测试覆盖。
- **佐证**：提交信息规范 `Conventional Commits`：`<type>(<scope>): <subject>`，type 分 `feat`/`fix`/`docs`/`refactor`/`test`/`chore`。
- **边界**：工作流不是越多分支越好——小团队上 Git Flow 四线反而累赘；选型依据是团队规模、发布频率与 CI/CD 成熟度。
