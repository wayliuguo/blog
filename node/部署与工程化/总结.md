## 1. 配置与环境

部署的本质是"同一份代码，跑出不同行为"，差异全靠一组可替换的环境变量。

### 1.1 环境变量与多环境加载

- **`process.env` 裸用四个问题**：类型全是 `string`（数字得手动 `Number()`）、默认值全靠手写 `|| 'default'`、访问散落各处（改变量名要全局搜索）、Node 不自动读 `.env`（得装 `dotenv`）。
- **`.env` 多文件按环境拆分**：`.env`（默认值，提交）、`.env.<环境>`（不提交）、`.env.example`（模板，提交）、`.env.local`（个人覆盖，不提交）。
- **加载链与优先级**：`envFilePath` 数组越靠前优先级越高，完整链条为 `process.env`（OS/容器注入，最高）> `.env.local` > `.env.<环境>` > `.env.example` > `.env`，符合 12-Factor“配置与代码分离”。

```
process.env（容器/CI 注入，最高）
   ↑
.env.local
   ↑
.env.development / .env.production
   ↑
.env.example
   ↑
.env（最低）
```

- **容器/CI 兜底**：环境变量已注入（以 `DB_HOST` 存在判断）时跳过 dotenv，否则 `.env` 文件会用旧值覆盖真实注入值。
- **`ConfigService.get<T>()` 泛型不转型**：`<T>` 只告诉 TS 类型，运行时不做转换；`infer: true` 才做精确推导（`get('app.port')` 是 `any`，加 infer 才是 `number`）。

### 1.2 类型安全的配置体系

- **`registerAs` 命名空间 + `ConfigType<typeof X>` 类型推断**：从工厂返回类型推断，无需手写 `interface`。
- **`src/config/index.ts` 聚合注册**：`load: [...Object.values(configs)]` 一次批量注册所有命名空间；`AllConfigType` 汇总各命名空间类型。
- **`ConfigKeyPaths` 点号路径联合**：展平嵌套配置为 `'app.logger.level'` 这类点号路径，深层 key 也有精确类型补全。
- **类型安全读取工具**：`env` / `envNumber` / `envBoolean` 约 30 行全局工具自带转换与默认值；`envNumber` 遇非法值立刻 `throw`，避免带病启动。

### 1.3 启动校验与敏感信息兜底

- **启动校验**：宁可启动失败、不可带病运行——`JWT_SECRET` 缺失或用占位符默认值直接抛错，`ADMIN_USERNAME` / `ADMIN_PASSWORD` 同样必填。
- **构建产物带类型**：扫 `.env.example` 生成 `types/env.d.ts`，让 `process.env.XXX` 编辑期有补全、拼错变量名编译期报错。
- **`.gitignore` 兜底**：`.env*` 全进 git 忽略、只放行 `*.env.example`——密钥一旦进 git 历史就永久留存，删掉也能从 commit 找回。

## 2. 日志体系

日志是生产“黑匣子”：线上代码无法重跑，但日志可复盘；体系差距决定排障是“半小时”还是“一下午”。

### 2.1 生产日志的刚需与 Winston 基础

- **`console.log` 四个硬伤**：没有级别（排查被海量日志淹没）、没有时间戳（无法定位时间）、不支持落文件（容器重启即丢）、同步写 stdout（高并发拖慢请求）。
- **Winston 三核心**：`level`（级别）、`format`（格式）、`transport`（输出目的地），缺一个构不成生产日志。
- **级别语义**：数字越小越严重——`error` 0 / `warn` 1 / `info` 2 / `debug` 3 / `verbose` 4；生产停在 `info`，把 `debug` 留给开发。
- **结构化 JSON**：`format.json()` 让日志能被采集工具解析，配合 `jq` 做二次分析。

### 2.2 双写架构与按日轮转

- **双写架构**：继承 `ConsoleLogger` 保留框架输出、同时由 Winston 写文件，调用方仍是 `this.logger.log`，业务代码零改动。
- **全局注册**：`LoggerModule.forRoot()` 设 `global: true`，`main.ts` 配 `bufferLogs: true` + `app.useLogger()`，NestJS 内部日志一并走自定义 Logger。

```
LoggerService（双写）
   ├── ConsoleLogger ──▶ 控制台 stdout ──▶ PM2 捕获 ──▶ docker logs
   └── Winston ────────▶ logs/app.%DATE%.log（全量 JSON）+ app-error.%DATE%.log（仅 ERROR）
```

- **按日轮转**：`DailyRotateFile` + `datePattern: 'YYYY-MM-DD'` + `maxFiles`（默认 31 天），单文件不无限膨胀、按日期归档。
- **错误独立文件**：`app-error.%DATE%.log` 单独落，排障不必在全量日志里 grep。
- **`auditFile`**：记录轮转状态，容器重启不重复处理旧文件。
- **磁盘预算**：JSON 日志每天约 10-50MB，保留 31 天预留 2GB+；异常增长优先查 `LOGGER_LEVEL`。
- **级别与保留天数走配置中心**：`LOGGER_LEVEL` / `LOGGER_MAX_FILES` 经 `app.logger.level` / `app.logger.maxFiles` 读取，不硬编码。

### 2.3 链路追踪与日志查看

- **trace ID 串联调用链**：借 `nestjs-cls`（基于 AsyncLocalStorage）给每个请求分配 ID，以 `[${traceId}] ${message}` 附到每条日志；按 ID 一搜即还原请求从入口到库的全路径。
- **三层日志查看**：`docker logs -f`（快速排查/启动/实时）→ 容器内文件 `logs/app.*.log`（历史/按级过滤/重启仍可查）→ `pm2 logs`（进程管理问题）。
- **判定依据**：实时用 stdout、历史用文件——`docker logs` 与 `pm2 logs` 随容器重启丢失，只有文件日志留得住。

## 3. 进程管理

`node dist/main.js` 前台裸跑，需要一个“管家”PM2 来守护进程。

### 3.1 裸跑的四宗罪与 PM2 日常操作

- **四个致命问题**：终端绑定（关终端或 SSH 断开进程即死）、崩溃即停（未捕获异常直接退出无人拉起）、单线程浪费（多核 CPU 只用一核）、无日志管理（输出散落终端重启即丢）。
- **PM2 对应解决**：守护进程化、自动重启、集群模式、日志收集。
- **日常命令**：`pm2 start` / `list` / `logs` / `restart` / `reload` / `stop` / `delete` / `monit` / `describe` / `flush`。
- **开机自启**：`pm2 startup` 生成自启脚本 + `pm2 save` 保存进程列表，系统重启后自动拉起全部应用。

### 3.2 ecosystem 声明式配置

- **`ecosystem.config.js`**：把命令行参数变成可版本化、可复用的声明式配置。
- **`autorestart`**：进程崩溃自动重启；**`max_memory_restart`**：内存超限自动重启（命令行 `--max-memory-restart 500M`，配置 `'1G'`），防内存泄漏拖垮机器。
- **`watch`**：文件变化自动重启，仅开发用；**`env`** 注入变量，`env_production` 区分环境。

### 3.3 fork 与 cluster 及部署架构演进

- **fork 与 cluster 取舍**：fork 单进程、父子模式，适合 Windows、Docker 容器、不需要负载均衡；cluster 多进程 + Node 原生 cluster 轮询负载均衡，适合 Linux/macOS 裸机、无编排平台；`-i max` 让进程数 = CPU 核数。
- **`pm2 reload` 仅对 cluster 有意义**：靠逐个重启 worker 零停机；fork 单进程无 worker 可换，直接 `restart` 即可。
- **Docker 内用 fork**：水平扩展交给编排平台（Compose 多副本 / K8s），容器内再 cluster 只会资源浪费、信号混乱；PM2 在容器里保留 fork，只为日志管理、进程监控、内存限制重启。
- **三层部署架构演进**：

```
裸机：用户 → Nginx(80/443) → PM2 cluster（多 worker）→ DB
Docker：用户 → Nginx → Docker 容器（PM2 fork 单进程）× N 副本 → DB
K8s：用户 → Ingress → Pod（容器内 fork）→ DB
```

- **衔接日志体系**：PM2 捕获应用 stdout，是“控制台 → PM2 → `docker logs`”链路中段；PM2 日志是内存缓冲不持久化，历史日志必须看文件 `logs/app.*.log`。

## 4. 容器化与编排

Docker 打包“应用 + 运行环境”实现“一次构建、到处运行”，根治“在我机器上是好的”；Compose 用一份 YAML 声明整组服务。

### 4.1 镜像、容器与分层缓存

- **镜像 / 容器 / 仓库**：镜像只读模板（类/光盘），容器是运行实例（实例/光驱），仓库存储分发（Docker Hub）；一个镜像可起多个容器。
- **分层缓存**：每条指令生成只读层，层不变就复用缓存，容器运行时在镜像上再加一层可写层（删容器即丢）——指令顺序直接影响构建速度。
- **数据持久化认知**：可写层不是持久化，要留的数据必须挂数据卷或宿主目录。

### 4.2 多阶段构建与生产级 Dockerfile

- **单阶段三个问题**：镜像带源码和 devDependencies（约 1GB、攻击面大）、`npm install` 全量慢、无健康检查（容器起了但应用没就绪）。
- **多阶段瘦身**：构建环境不进运行镜像，runtime 用 `COPY --from=builder` 拿 `dist` 与生产 `node_modules`，体积约 1GB → 200MB。
- **其他瘦身**：Alpine 基础镜像、`.dockerignore` 给构建上下文瘦身、合并 `RUN` 减层（`npm ci --only=production && npm cache clean --force`）。
- **层缓存顺序**：先 `COPY package*.json` 再装依赖，依赖不变则缓存命中跳安装；`--frozen-lockfile` 按 lockfile 严格安装保证各环境一致；`--prod` 只装 `dependencies`。
- **四阶段分工 deps → build → prod-deps → runtime**：deps 装系统工具（pnpm、pm2、时区）、build 装全量依赖编译出 dist、prod-deps 只装生产依赖、runtime 继承系统工具 + 复制依赖与产物。
- **可复现构建与 cache**：写死基础版本 `node:20.16.0-alpine`（而非 `node:20-alpine`）；`--mount=type=cache` 把依赖缓存挂为构建缓存不进镜像层；`ARG TZ=Asia/Shanghai` 保证日志时间戳与定时任务正确。
- **安全、健康检查与元数据**：`USER node` 非 root + `chown` 只授权 logs/dist；端点级 `HEALTHCHECK` 用 `wget --spider http://localhost:$APP_PORT/api/health`；`ARG` + `LABEL` 写版本与构建时间供 `docker inspect` 溯源；`ENTRYPOINT` exec 形式成 PID 1 正确收 SIGTERM 优雅关闭。
- **特殊依赖独立阶段**：Playwright 浏览器 184MB 装进 build 白装、装 runtime 每次重下；拆独立阶段 + cache mount（`PLAYWRIGHT_DOWNLOAD_HOST` 走 npmmirror），锁文件不变就跳过下载。

### 4.3 Docker Compose 编排

- **Compose 解决的痛点**：`docker run` 一一起容器要敲几十参数（参数记不住、网络手动 `--link`、重启重组织命令、无法版本化）；Compose 一份 YAML 声明整组服务，`docker compose up -d` 一条命令拉起。
- **服务名互访**：Compose 自动建网并 DNS 解析，容器间直接用服务名（`mysql` / `redis`）当主机名——与 `docker run` 本质区别。
- **数据持久化**：命名卷 `mysql_data:/var/lib/mysql` 容器删了数据还在；Redis `--appendonly yes --appendfsync everysec` 每秒刷盘（崩溃最多丢 1 秒）；日志命名卷 `show-track-logs` 跨容器生命周期持久化。

### 4.4 生产堆栈分离与迁移 Job

- **生产拆分两个 compose 文件**：`docker-compose.infra.prod.yml` 管 MySQL + Redis（一次性启动后不管）；`docker-compose.prod.yml` 管 migration + 应用（日常部署）。
- **为什么拆**：生命周期不同（数据库几年不动、应用天天更新）；拆开便于自建 Docker / 上云 RDS / 混合切换（只改 `.env` 不动编排）；基础设施配 `restart: always`、数据挂宿主目录。
- **迁移 Job 硬依赖**：`depends_on: condition: service_completed_successfully` 让应用等迁移成功才启动（比只等容器启动严格）；同镜像只靠 `entrypoint` 覆盖区分，`restart: 'no'` 让一次性任务失败就失败。
- **入口收敛与跨宿主**：`ports: '127.0.0.1:${APP_PORT}:${APP_PORT}'` 只绑回环不暴露公网，对外只开 Nginx 一个口；`env_file: .env.production` 密钥不进镜像；显式命名网络 `name: show_track_net` 便于多 compose 共享；`extra_hosts` 配 `host.docker.internal:host-gateway` 访问宿主机/云库。
- **三种部署场景**：全部 Docker（先 infra 再 prod）→ 混合（infra 注释 mysql、`DB_HOST` 填云地址）→ 全部云服务（跳过 infra，只用 prod.yml）。

## 5. 网关与反向代理

直接把 `3000` 暴露公网有四个问题——无域名路由、无法共享 80/443、无 SSL、无负载均衡；Nginx 作为入口网关分发请求并隐藏内部网络。

### 5.1 正向代理与反向代理

- **区别在替谁出面**：正向代理代理客户端访问外部（翻墙、公司出口）；反向代理代理服务端收请求（网关、负载均衡）。
- **后端语境**：后端说的“加一层代理”几乎都是反向代理——Nginx 收下所有请求、按规则转发、并隐藏内部网络结构。

```
正向代理：客户端 → 代理 → 互联网（代理帮客户端访问）
反向代理：用户 → Nginx → 后端服务（代理帮后端收请求）
```

### 5.2 基本转发、真实 IP 与生产场景配置

- **转发三件套**：`proxy_pass` 指后端 + `Host $host`（保留域名，后端正确生成链接）+ `X-Real-IP`（真实客户端 IP）+ `X-Forwarded-For`（转发链全 IP，供日志/风控）。
- **真实 IP 的坑**：装代理后日志与限流看到的是代理 IP，必须在应用层解析 `X-Forwarded-For`（配 `trust proxy`）。
- **WebSocket 代理**：`Upgrade $http_upgrade` + `Connection "upgrade"` + `proxy_http_version 1.1` + `proxy_read_timeout 300s`（及 `proxy_send_timeout 300s`），缺一条前端握手失败。
- **History 回退**：`try_files $uri $uri/ /index.html` 让前端路由刷新命中 `index.html`。
- **Gzip**：`gzip on` + `gzip_http_version 1.1` + `gzip_types` 指定文本 MIME + `gzip_min_length 1000` + `gzip_comp_level 9`，减小传输体积。

### 5.3 负载均衡与部署架构协作

- **`upstream` 负载组**：`proxy_pass http://backend/` 转发给整组；策略三种——默认轮询（依次分发）、`least_conn`（分给连接最少实例）、`ip_hash`（同 IP 固定同实例，需 Session 场景）。
- **各组件职责**：Nginx 收请求/SSL 终结/静态文件/反代/负载均衡；PM2 进程管理/故障恢复/内存管理；Docker 环境隔离/一致性部署/服务编排；MySQL/Redis 数据持久化/缓存。
- **三种部署架构**：纯 Docker（Nginx、Server、Redis、MySQL 同网）→ PM2 + Nginx 传统（Nginx → 多 PM2 cluster → DB）→ Docker + 容器内 PM2（Nginx 宿主机唯一入口 → 容器 ×N 副本 → MySQL/Redis）。
- **演进主线**：Nginx 始终“唯一入口”，变化的只是背后 Node 进程由谁管（裸机 PM2 → 容器 → 编排平台）。

## 6. 发布与 CI/CD

“改表”与“发版”都要成体系，从开发技能变成受控、可回滚的发布流程。

### 6.1 数据库迁移机制

- **`synchronize` 是定时炸弹**：不可审计、不可回滚、数据丢失（Entity 删字段 → 重启 → 列被删）、不可审查、让迁移失效（库已同步，`migration:generate` 对比不出差异）；只适合早期原型。
- **`migrations` 表**：记录已执行迁移（`id` / `timestamp` / `name`），不存在自动创建。
- **`migration:run` 执行流程**：连库 → 查/建表 → 读 `dist/migrations/*.js` → 对比已执行 → 按时间戳跑未跑的 `up()` → 每跑完插记录。
- **幂等**：已执行不重跑，无新迁移输出 `"No migrations are pending"` 直接退出，跑多少遍都安全。
- **事务保护**：`up()` / `down()` 默认包事务，失败整体回滚；已成功的迁移不自动回滚，撤销须显式 `migration:revert`。

### 6.2 迁移架构设计与发布链路

- **三个 DataSource 分工**：Local（`data-source.dev.ts`，dotenv 读 `.env.development`，吃 `src/**/*.ts`）→ CLI（`data-source.ts`，读注入变量，吃 `dist/**/*.js`）→ Runtime（`database.config.ts`，走 `@nestjs/config` 与 DI）；三者 `synchronize` 都建议 false。
- **迁移 CLI 独立于 NestJS**：直接 `node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`——应用有 bug 也能迁移、不经 DI 容器故轻量、本地用 TS 源生产用编译产物。
- **开发期流程**：改 Entity → `migration:dev:generate`（对比生成）→ `migration:dev:run`（执行）→ 启动 dev；生产对应 `migration:prod:run`。
- **独立迁移 Job**：多实例各自跑迁移会并发锁冲突、产生脏数据；做法是独立一次性 Job 容器跑在业务前（各自 `wait-for-it.sh` 等 MySQL，迁移 `restart: 'no'` 执行完退出，业务用 `depends_on: condition: service_completed_successfully` 等它成功）。
- **首次与后续部署**：空库自动建表 + 全量迁移；有数据只执行新增迁移；无新增直接跳过；已有数据不被框架触碰，除非 `up()` 显式写 `DROP` / `DELETE` / `TRUNCATE`。
- **安全 vs 破坏性迁移**：安全迁移（新增表/字段/索引）可进 CI/CD 自动执行；破坏性迁移（删除/重命名）不可逆，必须人工确认后手动执行。

### 6.3 生产部署全流程

- **统一部署模式**：MySQL 和 Redis 永远是外部服务，compose 堆栈只管 migration + app；端口只绑 `127.0.0.1`、对外只有 Nginx 一个入口。
- **首次部署四步**：准备 `.env.production`（不提交，填真实值）→ 起基础设施 `infra.prod.yml up -d`（`restart: always` 自管）→ `prod.yml up -d --build` 构建启动应用 → 写 Nginx `conf.d` 反代 `127.0.0.1:3000`。
- **一条 `up -d --build` 背后**：五阶段构建 → migration 容器等 MySQL 跑迁移 → app 容器等迁移成功、PM2 fork 拉起 NestJS → HEALTHCHECK 探 `/api/health` → `curl http://your-server:3000/api/health` 验证。
- **日常迭代与滚动更新**：`git pull` + `up -d --build`，Compose 先启新容器、健康检查过再停旧容器，单机近似滚动更新、基本不中断。
- **数据持久化位置**：MySQL 落 `./__data/mysql/`、Redis 落 `./__data/redis/`、应用日志落命名卷 `show-track-logs`，容器重建都不丢。
- **备份与恢复**：`mysqldump` 备份、`mysql < backup.sql` 恢复；云库由云服务方提供，自建靠宿主目录 + 定时 `mysqldump`，生产建议每日全量。
- **故障排障五问**：容器活着吗（`docker ps`）→ 健康吗（`docker inspect`）→ 应用日志说什么（`docker logs --tail 50` / 按 trace ID grep）→ 是数据库问题吗（`docker logs <mysql>`）→ 被重启过吗（`pm2 logs`）。
- **重启常见原因**：库未就绪（等 migration）、环境变量缺失致启动校验抛错、端口冲突；迁移失败看退出码、查 `migrations` 表，事务回滚 + 幂等不破坏已有数据。
- **部署检查清单**：镜像有新 tag（`docker images`）、迁移无 ERROR、容器健康（`State.Health.Status`）、本地接口通（`curl 127.0.0.1:3000/api/health`）、日志在写（`ls /app/logs/`）、外部入口通（`curl https://api.example.com/api/health`）。

### 6.4 CI/CD 自动化部署

- **手动部署四问题**：易漏步骤、构建吃服务器资源、无法快速回滚、多人发版不可控；核心区别是**构建从服务器挪到云端 CI**，服务器只拉新镜像、重启容器。
- **workflow 三概念**（`.github/workflows/*.yml`）：触发（`on`：push / tag / 手动）、任务（`jobs`：步骤集合，可并行）、步骤（`steps`：checkout / build / deploy）。
- **双流水线**：build 构建推送，deploy 等 build 成功后再 SSH 部署——构建失败不触发部署、deploy 可在多机复用。
  - 流水线一（build-stable.yml）：`on: push: tags: ['v*']`，`docker/login-action` 登录后 `build-push-action` `push: true`，同时打 `stable` 与 `v1.0.0` 两 tag，回滚拉旧 tag。
  - 流水线二（deploy.yml）：`on: workflow_run: types: [completed]` + `if: success`，`appleboy/ssh-action` 连接，服务器只跑 `docker compose pull` + `up -d`。
- **Secrets**：Settings 配 `DOCKER_USERNAME/PASSWORD`、`DOCKER_IMAGE`、`SERVER_HOST/USER`、`SERVER_SSH_KEY`；建议为 CI/CD 单独生成密钥对（ed25519 + `ssh-copy-id`），不用日常账号。
- **迁移进流水线**：安全迁移用隔离容器自动执行 `docker compose run --rm --entrypoint "" my-app node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`；破坏性迁移必须人工确认后手动执行。
- **触发、回滚与验证**：发版 `git tag v1.0.0 && git push origin master && git push origin v1.0.0`；删 tag `git tag -d` + `git push --delete`；回滚 = 用旧 tag 再部署一次（秒级）；验证看 Actions 日志、`docker ps`、`docker logs -f`、`curl https://api.example.com/api/health`。

## 7. 脚手架开发

脚手架是自动化创建项目的 CLI 工具：用户命令行交互选配置后自动生成模板。

### 7.1 脚手架定位与核心流程

- **定位**：`create-react-app` / `nest new` / `vue create` 这类一键生成项目的工具。
- **核心流程**：用户输入命令 → 交互式问答（项目名、模板类型）→ 复制模板文件 → 替换模板变量 → 输出生成的带真实值的项目。
- **装依赖的取舍**：通常不自己装依赖，交给用户（`cd xxx && npm install`）——脚手架里跑安装会拉长等待、失败率还高。

```
用户输入命令
   → inquirer 交互问答（项目名、模板类型）
   → fs-extra 复制 templates/<类型> 到目标目录
   → replace(/{{projectName}}/g, ...) 替换占位符
   → 打印 cd xxx && npm install 提示下一步
```

### 7.2 CLI 工程落点与参数解析

- **入口约定**：`bin/index.js` 首行 `#!/usr/bin/env node`，在 `package.json` `bin` 字段映射成全局命令名。
- **依赖分工**：inquirer 负责交互问答，fs-extra 负责目录复制（比原生 fs 多递归与覆盖便利）。
- **变量替换**：复制完模板读文件，用 <code v-pre>replace(/{{projectName}}/g, ...)</code> 把占位符换成真实项目名。
- **yargs 参数解析**：`command('create <name>')` 定义子命令与 positional，`option` 定义 `--template` 等参数（`alias` / `choices` / `default`），`.help()` 自动生成帮助。
- **CI 无 TTY**：脚手架必须支持全参数化执行（不接交互问答），否则在流水线里直接用不了。

## 8. 异步与消息队列

消息队列是生产者发消息、消费者取消息的异步通信机制，解决同步等待与强耦合。

### 8.1 消息队列的本质与作用

- **同步 vs 异步**：同步是下单等扣库存/发短信/发邮件/加积分全完成；异步只让用户等下单，其余由队列驱动。

```
同步：下单 → 扣库存 → 发短信 → 发邮件 → 积分（用户等全部完成）
异步：下单 → 消息队列 → 扣库存、发短信、发邮件并行（用户只等下单）
```

- **三大作用**：异步处理（非核心操作异步执行，用户不必等全部完成）、削峰填谷（高峰缓冲，像水库蓄水防下游被冲垮）、解耦（生产者和消费者不直接依赖、无需知道对方）。
- **代价**：复杂度上升——消息可能丢失、重复、乱序；需要可靠投递、消费幂等、可观测（积压告警）；强实时调用不适合走队列。

### 8.2 Kafka 核心概念与选型

- **六核心**：Producer（发消息）、Consumer（消费）、Topic（消息分类，类似表）、Partition（分区，并行处理单位）、Broker（集群服务器）、Consumer Group（组内负载均衡、组间独立消费）。
- **分区语义**：分区内有序、跨分区无序；做同一订单有序用 `orderId` 作分区键。
- **选型对比**：Kafka（吞吐百万级/秒、落磁盘、分区内有序、学习成本高，适日志/大数据/流处理）；RabbitMQ（万级/秒、落磁盘、单队列有序、学习成本中，适业务系统/任务分发）；Redis Stream（万级/秒、内存+磁盘、轻量、学习成本低，适简单消息/缓存场景）。

## 9. 性能优化

缓存的三种失效、限流的四种算法与数据库的五种手段，是性能与稳定性的核心。

### 9.1 缓存穿透、击穿与雪崩

- **穿透**：查不存在的数据每次打到库；对策是缓存空值（短 TTL）或布隆过滤器前置拦截。
- **击穿**：单个热点 key 过期瞬间大量请求涌向库；对策是互斥锁重建或热点 key 逻辑过期（异步续期）。
- **雪崩**：大量 key 同时过期压垮库；对策是过期时间加随机值、多级缓存。
- **共同底线**：任何一层缓存都要配降级——缓存整体不可用时“放流量去数据库”还是“直接返回兜底值”，必须事先定好。

### 9.2 限流算法与 NestJS 落地

- **四种算法**：计数器（固定窗口计数、简单但窗口交界处有突刺）；滑动窗口（细粒度时间片、更平滑、内存开销大）；令牌桶（匀速放令牌、请求消耗、允许突发）；漏桶（匀速处理、平滑但不允许突发）。
- **算法选型**：允许突发用令牌桶；绝对平滑用漏桶；统计精确用滑动窗口；只图快用固定窗口计数器。
- **NestJS 落地**：全局 `ThrottlerModule.forRoot({ ttl: 60000, limit: 10 })` 定 60 秒窗口、窗口内最多 10 次；按接口 `@Throttle(5, 60000)` 让单路由 60 秒内最多 5 次。
- **多实例注意**：单机用进程内计数器即可，多副本**必须走 Redis**，并用 Lua 脚本把“取数 + 判断 + 写回”做原子，否则每个副本各限一份、总量是 N 倍。

### 9.3 数据库优化

- **五手段**：索引优化（避免全表扫描）、慢查询日志（定位慢 SQL + EXPLAIN 分析）、连接池（复用连接）、读写分离（主库写从库读）、分库分表（数据量大时水平拆分）。

## 10. 安全防线

安全编码分两层：防住常见攻击，再用好框架级通用防护。

### 10.1 三类常见攻击与防御

- **XSS（跨站脚本）**：往页面注入恶意脚本，根源是输出未编码而非输入未校验，靠模板引擎（Pug）与前端框架（React/Vue）默认 HTML 转义防御。
- **CSRF（跨站请求伪造）**：诱导用户不知情下操作，靠 CSRF Token 防御，NestJS 可用 `csurf` 中间件。
- **SQL 注入**：字符串拼接 SQL 就是注入入口（`` `... id = ${id}` ``），必须用参数化查询（`?` 占位）让驱动做转义，ORM 默认这么做。

### 10.2 框架级通用防护

- **Helmet**：一个 `app.use(helmet())` 批量设安全响应头（CSP、HttpOnly 等），成本低收益高。
- **CORS**：开发可放开（`app.enableCors()`），生产必须 `origin` 白名单；带 Cookie 时 `credentials: true` 与前端 `withCredentials` 成对配，且 `credentials` 时不能用 `*`。
- **参数校验**：永远不信任输入，`ValidationPipe` 开 `whitelist + forbidNonWhitelisted` 只放行 DTO 声明字段。
- **边界**：CORS 只是浏览器侧限制，服务端到服务端请求不受它管，别把它当 API 鉴权；输入校验替代不了输出编码。

## 11. 测试与设计模式

可测的模块边界加可替换的结构，是质量与设计在框架里的落点。

### 11.1 测试金字塔与 NestJS 测试

- **测试金字塔**：单元测试（极快、最多，覆盖单个函数/方法）> 集成测试（居中，覆盖模块间交互）> E2E 测试（最慢、最少，覆盖完整请求链路）；比例约 7:2:1。
- **单元测试**：`Test.createTestingModule({ providers: [...] })` 编译后 `module.get()` 取出待测服务。
- **集成测试**：`imports: [AppModule]` 编译出完整应用，`createNestApplication()` + `app.init()` 后用 supertest 打真实 HTTP。
- **三种测试替身**：Mock（模拟整个对象，如 `jest.fn().mockResolvedValue(...)`）；Stub（替换方法返回值，如 `jest.spyOn(...).mockResolvedValue(...)`）；Spy（只监控调用，断言 `toHaveBeenCalledWith`）。
- **Mock 过头的坑**：把每个依赖都 Mock 一遍，测试就绑死在实现细节上——测的是“代码怎么写”不是“代码对不对”。

### 11.2 单例、工厂、策略与观察者

- **单例**：NestJS Provider 默认就是单例，注入到多少类都是同一实例；有状态服务（请求级缓存/上下文）不能挂单例，该用 `Scope.REQUEST` 或显式传参。
- **工厂**：自定义 Provider 的 `useFactory` 按环境返回不同数据库连接（`inject` 声明依赖、可 async），就是工厂模式落点。
- **策略**：把算法抽成可互换接口（如多种登录校验），用 `@Inject('AUTH_STRATEGY')` 或 `type→Map` 运行时选择，消掉一长串 `if/else`。
- **观察者**：`EventEmitter2` 的 `emit` 发布、`@OnEvent` 监听，做下单后发短信这类副作用；代价是调用链变隐式（谁处理了事件要全局搜），监听器异常要单独兜住。

## 12. 系统设计与协作

- 单体到微服务、网关到高可用，最终落到分支策略与 Code Review。

### 12.1 微服务与 WebSocket 网关

- **微服务连通**：`ClientsModule.register` 声明传输（TCP/Redis/Kafka/RabbitMQ），`client.send({ cmd }, payload)` 发消息。
- **拆分原则**：按业务拆（用户/订单/商品）、每服务独立数据库、独立部署扩展；通信同步用 HTTP/gRPC、异步用消息队列；**不允许跨服务直连数据库**。
- **WebSocket 网关**：`@WebSocketGateway({ namespace, cors })` 声明命名空间与跨域，`handleConnection` 处理连接；`@SubscribeMessage` 处理消息、`server.emit` 广播给所有客户端。

### 12.2 高可用策略

- **五策略**：负载均衡（多台机器分担请求）、冗余部署（多实例避免单点）、健康检查（定期检查自动剔除异常节点）、熔断降级（下游故障返回降级响应而非崩溃）、限流（护后端不被突发流量打垮）。
- **闭环配套**：进程守护（PM2 `autorestart` / 容器 `restart: always`）保证崩溃自愈；优雅退出（接 `SIGTERM` → 停收新连接 → 等请求归零 → 关依赖 → 退出）保证发布不丢请求。
- **别忘依赖也是单点**：数据库、Redis、消息队列的高可用要单独设计，应用层做得再好一个单机 MySQL 挂掉照样全站不可用。

### 12.3 Git 工作流与协作规范

- **三种工作流**：GitHub Flow（main + feature，PR 合并，适小团队持续部署）；Git Flow（main + develop + feature + release，适中大型版本发布）；Trunk-Based（人人 main 上开发、短命分支，适高频发布、CI/CD 成熟）。
- **合并策略取舍**：Merge（`git merge feature` 保留完整历史但多一个合并提交）；Rebase（`git rebase main` 线性历史无合并提交但改写提交——已推送的公共分支绝不能 rebase）；Squash（把多个提交压成一个）。
- **提交信息规范（Conventional Commits）**：格式 `<type>(<scope>): <subject>`；type 分 `feat` / `fix` / `docs` / `refactor` / `test` / `chore`。
- **Code Review 实践**：PR 单次控制在 200~300 行以内；先理解整体逻辑再看细节；指出问题的同时给建议、用“建议”代替“要求”；清单覆盖代码规范、不必要复杂性、异常处理、安全漏洞、测试覆盖。
