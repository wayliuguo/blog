## 分篇知识点

### 部署与工程化 01-环境管理与配置

- **部署从配置开始**
  - 本质：同一份代码跑出不同行为，差异全靠一组可替换的环境变量
  - 渐进四步：`.env` + `@nestjs/config` 先跑起来 → 按环境拆文件 → `registerAs` 类型安全 → 启动校验与敏感信息兜底
- **`process.env` 裸用的四个问题**
  1. 类型全是 `string`，数字配置得手动 `Number()`
  2. 默认值全靠手写 `process.env.X || 'default'`
  3. 访问散落各处，改变量名要全局搜索
  4. Node 不自动读 `.env`，得装 `dotenv` 手动加载
- **`ConfigService.get()` 的类型**
  - 泛型不转型：`<T>` 只告诉 TS 期望类型，运行时不做任何转换
  - `infer: true` 才有精确推导：`get('app.port')` 拿到 `any`，加 `infer` 才拿到 `number`
- **多环境加载链与优先级**
  - `envFilePath` 数组越靠前优先级越高：`process.env` > `.env.local` > `.env.<环境>` > `.env.example` > `.env`，符合 12-Factor 的“配置与代码分离”
  - 容器/CI 兜底：环境变量已注入（以 `DB_HOST` 判断）时跳过 dotenv，否则 `.env` 旧值覆盖真实注入值
- **`registerAs` 命名空间与类型推断**
  - `ConfigType<typeof AppConfig>` 从工厂返回值推断类型，无需手写 `interface`
  - `src/config/index.ts` 汇总命名空间，`load: [...Object.values(configs)]` 一次注册；`ConfigKeyPaths` 展平嵌套配置为点号路径联合，深层 key 也有精确类型
- **类型安全的读取工具**：`env` / `envNumber` / `envBoolean` 约 30 行全局工具，让读取自带转换与默认值；`envNumber` 遇非法值立刻 `throw`，避免带病启动
- **启动校验**：宁可启动失败，不可带病运行——密钥缺失或用占位符默认值直接抛错，`ADMIN_USERNAME` / `ADMIN_PASSWORD` 同样必填
- **敏感信息与构建产物兜底**
  - 扫 `.env.example` 生成 `types/env.d.ts`，让 `process.env.XXX` 编辑期有补全、拼错变量名编译期报错
  - `.env*` 全进 gitignore、只放行 `*.env.example`——密钥一旦进 git 历史就永久留存


### 部署与工程化 02-日志体系

- **日志是生产刚需**：线上代码无法重跑，日志可复盘，体系差距决定排障是"半小时"还是"一下午"
- **`console.log` 的四个硬伤**
  1. 没有日志级别，排查时被海量日志淹没
  2. 没有时间戳，无法定位"什么时候发生"
  3. 不支持输出到文件，容器重启即丢
  4. 同步写 stdout，高并发拖慢请求
- **Winston 三核心**
  - `level` / `format` / `transport`：级别、格式、输出目的地，缺一个构不成生产日志
  - 数字越小越严重：`error` 0 / `warn` 1 / `info` 2 / `debug` 3 / `verbose` 4；生产停在 `info`，把 `debug` 留给开发
  - 结构化 JSON：`format.json()` 让日志能被采集工具解析，配合 `jq` 做二次分析
- **双写架构**：控制台给开发、文件给生产
  - `LoggerService` 继承 `ConsoleLogger` 保留框架输出，同时由 Winston 写文件；调用方仍是 `this.logger.log`，业务代码零改动
  - 链路：控制台 → stdout → PM2 捕获 → `docker logs`
  - 全局注册：`LoggerModule.forRoot()` 设 `global: true`，`main.ts` 配 `bufferLogs: true` + `app.useLogger()`，NestJS 内部日志一并走自定义 Logger
- **按日轮转与错误分离**
  - `DailyRotateFile` + `datePattern: 'YYYY-MM-DD'` + `maxFiles`（默认 31 天）：单文件不无限膨胀，按日期归档
  - `app-error.%DATE%.log` 独立错误文件：排障不必在全量日志里 `grep`
  - `auditFile`：记录轮转状态，容器重启不重复处理旧文件
  - 磁盘预算：JSON 日志每天约 10-50MB，保留 31 天预留 2GB+；异常增长优先查 `LOGGER_LEVEL`
- **日志级别与保留天数**：走配置中心，不硬编码——`LOGGER_LEVEL=info` / `LOGGER_MAX_FILES=31` 经 `app.logger.level`、`app.logger.maxFiles` 读取
- **trace ID 串联调用链**：借 `nestjs-cls` 异步上下文给每个请求分配 ID，以 `[${traceId}] ${message}` 附到每条日志；按 ID 一搜即还原一次请求从入口到库的全路径
- **三层日志查看方式**
  1. `docker logs -f <container>`：快速排查、启动日志、实时监控
  2. 容器内文件 `logs/app.*.log`：历史日志、按级别过滤、重启后仍可查
  3. `pm2 logs`：PM2 进程管理问题（重启、内存告警）


### 部署与工程化 03-PM2 进程管理

- **裸跑的四个致命问题**：终端绑定、崩溃即停、单线程浪费、无日志管理——PM2 的守护进程化、自动重启、集群模式、日志收集正对应解决
  1. 终端绑定：关闭终端或 SSH 断开，进程即死
  2. 崩溃即停：未捕获异常直接退出，无人拉起
  3. 单线程浪费：现代 CPU 多核，Node 默认只用一核
  4. 无日志管理：输出散落终端，重启即丢
- **常用命令与开机自启**
  - 日常操作：`pm2 start` / `list` / `logs` / `restart` / `stop` / `delete` / `monit` / `describe` / `flush`
  - 开机自启：`pm2 startup` 生成自启脚本 + `pm2 save` 保存进程列表，系统重启自动拉起全部应用
- **`ecosystem.config.js`**：把命令行参数变成可版本化、可复用的声明式配置
  - `autorestart`：进程崩溃自动重启
  - `max_memory_restart`：内存超限自动重启（命令行 `--max-memory-restart 500M`，配置 `'1G'`），防内存泄漏拖垮机器
  - `watch`：文件变化自动重启，仅开发用；`env` 注入变量，`env_production` 区分环境
- **fork 与 cluster 的取舍**
  1. fork：单进程、父子模式，适合 Windows、Docker 容器、不需要负载均衡
  2. cluster：多进程 + Node 原生 cluster 轮询负载均衡，适合 Linux/macOS 裸机、无编排平台；`-i max` 让进程数 = CPU 核数
- **`pm2 reload` 与 cluster**：靠逐个重启 worker 实现零停机；fork 是单进程无 worker 可换，故无 reload 必要
- **Docker 内用 fork**：水平扩展交给编排平台（Compose 多副本 / K8s），容器内再 cluster 只会造成资源浪费与信号混乱；PM2 在容器里保留 fork，只为日志管理、进程监控、内存限制重启
- **三层部署架构的演进**
  1. 裸机：用户 → Nginx(80/443) → PM2 cluster（多 worker）→ DB
  2. Docker：用户 → Nginx → Docker 容器（PM2 fork 单进程）× N 副本 → DB
  3. K8s：用户 → Ingress → Pod（容器内 fork）→ DB
  - 主线：裸机自己管进程 → 容器编排管副本 → 平台管一切；PM2 从"负载均衡器"退化为"容器内进程管家"
- **与日志体系的衔接**
  - PM2 捕获应用 stdout，正是"控制台 → PM2 → `docker logs`"链路中段（`pm2 logs --lines 100 --nostream`、`pm2 flush`）
  - PM2 日志是内存缓冲、不持久化，容器重启即丢；历史日志必须看文件 `logs/app.*.log`


### 部署与工程化 04-Docker 容器化

- **Docker 解决什么**：把应用和运行环境一起打包，实现"一次构建，到处运行"，根治"在我机器上是好的"
- **镜像 / 容器 / 仓库**
  - 镜像只读模板（类/光盘），容器是运行实例（实例/光驱），仓库存储分发（Docker Hub）
  - 分层缓存：每条指令生成只读层，层不变就复用缓存——指令顺序直接影响构建速度
- **单阶段 Dockerfile 的三个问题**：镜像带源码和 devDependencies（约 1GB、攻击面大）、`npm install` 装全量依赖慢、无健康检查（容器起了但应用没就绪）
- **多阶段构建瘦身**
  - 核心：构建环境不进运行镜像；runtime 用 `COPY --from=builder` 拿 `dist` 与 `node_modules`，体积从约 1GB 降到约 200MB
  - 其他手段：Alpine 基础镜像（约 120MB vs Ubuntu 约 1GB）、`.dockerignore` 给构建上下文瘦身、合并 `RUN` 减层（`npm ci --only=production && npm cache clean --force`）
- **层缓存顺序与锁文件**
  - 先 `COPY package*.json` 再装依赖：依赖描述不变 → 缓存命中 → 跳过整段安装
  - `--frozen-lockfile`：严格按 lockfile 安装，各环境依赖版本一致
  - `--prod`：只装 `dependencies`，跳过 TS/ESLint/Jest 等 devDependencies
- **四阶段分工：deps → build → prod-deps → runtime**
  - deps：装 pnpm、pm2、时区工具等系统依赖，供后续继承
  - build：装全量依赖并 `nest build` 出 `dist`
  - prod-deps：只装生产依赖，不含 devDependencies
  - runtime：从 deps 继承系统工具、从 prod-deps 取依赖、从 build 取产物
- **可复现构建与 cache mount**
  - 基础镜像写死 `node:20.16.0-alpine`（而非 `node:20-alpine`），保证今天与半年后构建一致
  - `--mount=type=cache`：依赖缓存挂载为构建缓存，不进镜像层却能被后续构建复用
  - `ARG TZ=Asia/Shanghai` 设时区，日志时间戳与定时任务才正确
- **安全、健康检查与元数据**
  - 非 root 与最小权限：`USER node` 运行，`chown` 只授权 `logs` 与 `dist`（不遍历 `node_modules`）
  - 端点级 HEALTHCHECK：`wget --spider http://localhost:$APP_PORT/api/health`，验证应用真正就绪而非仅端口监听
  - `ARG` + `LABEL`：版本号与构建时间写入镜像元数据，`docker inspect` 可溯源
  - `ENTRYPOINT` 用 exec 形式：entrypoint 成 PID 1，正确收 SIGTERM 实现优雅关闭
- **特殊依赖独立阶段**：Playwright 浏览器 184MB 装进 build 白装、装进 runtime 每次重下；拆独立阶段 + cache mount（`PLAYWRIGHT_DOWNLOAD_HOST` 走 npmmirror 加速），缓存可复用、runtime 只复制一次、锁文件不变就跳过下载


### 部署与工程化 05-Docker Compose 编排

- **Compose 解决的痛点**：`docker run` 一个个起容器要敲几十参数（参数记不住、网络手动 `--link`、重启重组织命令、无法版本化）；Compose 一份 YAML 声明整组服务，`docker compose up -d` 一条命令拉起
- **一个文件声明全栈**
  - app + mysql + redis 写进同一 YAML，用 `up -d` / `ps` / `logs -f` / `down` 管理整套服务
  - 服务名互访：Compose 自动建网并 DNS 解析，容器间直接用服务名（`mysql` / `redis`）当主机名——与 `docker run` 本质区别
- **数据持久化**
  - 命名卷：`volumes: mysql_data:/var/lib/mysql`，容器删了数据还在
  - Redis 持久化：`--appendonly yes --appendfsync everysec` 每秒刷盘，崩溃最多丢 1 秒
  - 日志命名卷：`show-track-logs:/app/logs/` 让日志跨容器生命周期持久化
- **生产堆栈分离**
  - `docker-compose.infra.prod.yml` 管 MySQL + Redis（一次性启动之后不管）；`docker-compose.prod.yml` 管 migration + 应用（日常部署）
  - 为什么拆：数据库几年不动、应用天天更新、生命周期不同；拆开可自建 Docker / 上云 RDS / 混合，切换只改 env 不动编排
  - 基础设施细节：`restart: always` 让库挂掉自动拉起；`./__data/redis/` 挂宿主机；上云时注释掉 mysql 服务
- **迁移 Job**：把启动顺序变硬依赖
  - `depends_on: condition: service_completed_successfully`：应用等迁移 Job 成功完成才启动，比默认“只等容器启动”严格
  - 同镜像不同入口：迁移与业务共用镜像，只靠 `entrypoint` 覆盖区分；`restart: 'no'` 让一次性任务失败就失败，不留死循环重试
- **入口收敛与跨宿主机访问**
  - `ports: '127.0.0.1:${APP_PORT}:${APP_PORT}'`：只绑回环、不暴露公网，对外只开 Nginx 一个口
  - `env_file: .env.production`：环境变量从文件注入，密钥不进镜像不进代码
  - 显式命名网络：`networks: name: show_track_net` 让多个 compose 文件共享同一网络
  - 跨宿主机访问：`extra_hosts` 配 `host.docker.internal:host-gateway`，`DB_HOST` 填 `host.docker.internal`（自建库）或云 RDS 地址
- **三种部署场景**
  1. 全部 Docker（自建 MySQL + Redis）：先 `infra.prod.yml` 起基础设施，再 `prod.yml` 部署应用
  2. 混合（MySQL 上云 + Redis 本地）：infra 注释掉 mysql，`.env` 里 `DB_HOST` 填云地址
  3. 全部云服务：跳过 infra 文件，`.env` 全填云地址，只用 `prod.yml`


### 部署与工程化 06-Nginx 反向代理与网关

- **入口网关的必要性**：直接暴露 `3000` 有四个问题——无域名路由、无法共享 80/443、无 SSL、无负载均衡；用户只跟 Nginx 打交道，Nginx 分发请求并隐藏内部网络
- **正向代理 vs 反向代理**
  - 正向代理代理客户端访问外部（翻墙、公司出口）；反向代理代理服务端收请求（网关、负载均衡）——后端语境的“加一层”基本是后者
- **基本转发与真实 IP**
  - 转发三件套：`proxy_pass` 指后端 + `Host $host`（保留域名，后端正确生成链接）+ `X-Real-IP`（真实客户端 IP）+ `X-Forwarded-For`（转发链全 IP，供日志/风控）
  - 真实 IP 的坑：装代理后应用日志与限流看到的是代理 IP，必须在应用层解析 `X-Forwarded-For`
- **WebSocket 代理**：`Upgrade $http_upgrade` + `Connection "upgrade"` + `proxy_http_version 1.1` + `proxy_read_timeout 300s`（及 `proxy_send_timeout 300s`），缺一条前端握手失败
- **静态资源与 Gzip**
  - History 模式回退：`try_files $uri $uri/ /index.html` 让前端路由刷新命中 `index.html`
  - Gzip：`gzip on` + `gzip_http_version 1.1` + `gzip_types` 指定文本 MIME + `gzip_min_length 1000` + `gzip_comp_level 9`，减小传输体积
- **负载均衡策略**：`upstream` 组 + `proxy_pass http://backend/` 转发给整组
  1. 默认轮询：依次分发，权重相同
  2. `least_conn`：分给当前连接最少的实例
  3. `ip_hash`：同 IP 固定到同实例（需 Session 的场景）
- **各组件职责**
  - Nginx：接收请求、SSL 终结、静态文件、反向代理、负载均衡
  - PM2：Node 进程管理、故障恢复、内存管理
  - Docker：环境隔离、一致性部署、服务编排
  - MySQL / Redis：数据持久化 / 缓存
- **三种部署架构**
  1. 纯 Docker（现代默认）：Nginx、Server、Redis、MySQL 同在一套 Compose 网络
  2. PM2 + Nginx 传统：Nginx(80/443) 反代与负载均衡 → 多个 PM2 cluster → MySQL/Redis
  3. Docker + 容器内 PM2：Nginx 在宿主机做唯一公网入口 → Docker 容器（PM2 fork 单进程）× N 副本 → 宿主机或云 MySQL/Redis
  - 演进主线：Nginx 始终“唯一入口”；变化的只是背后 Node 进程由谁管（裸机 PM2 → 容器 → 编排平台）


### 部署与工程化 07-数据库迁移与发布

- **“改表”要成体系**：生产表里全是真数据，任何结构变更都可能丢数据、锁表、不可回滚——从开发技能变发布流程
- **`synchronize` 是定时炸弹**：只适合早期原型，进入协作开发就关掉
  1. 不可审计：谁改、何时改、改了啥无从追溯
  2. 不可回滚：出问题只能手动修
  3. 数据丢失：删字段 → 重启 → 列被删 → 数据永久丢失
  4. 不可审查：变更无法 Code Review
  5. 迁移失效：库已和实体同步，`migration:generate` 对比不出差异
- **迁移执行机制：记录、幂等、事务**
  - `migrations` 表记录已执行（`id` / `timestamp` / `name`），不存在自动创建
  - `migration:run`：连库 → 查表 → 读 `dist/migrations/*.js` → 对比已执行 → 按时间戳跑未跑的 `up()` → 每跑完插记录
  - 幂等：已执行的不会重跑，无新迁移输出 `"No migrations are pending"` 直接退出
  - 事务保护：`up()` / `down()` 默认包事务，失败整体回滚；已成功的迁移不自动回滚，撤销须显式 `migration:revert`
- **三个 DataSource 的分工**
  - Local（`data-source.dev.ts`）：本地开发命令，`dotenv` 读 `.env.development`，吃 `src/**/*.ts` 源码（免 build）
  - CLI（`data-source.ts`）：生产命令（Docker/CI），读注入变量，吃 `dist/**/*.js`（免 ts-node）
  - Runtime（`database.config.ts`）：运行时连接，走 `@nestjs/config` 与 DI 容器；三者 `synchronize` 都建议 false
- **迁移 CLI 独立于 NestJS**：直接 `node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`，不启动应用——应用有 bug 也能迁移、不经 DI 容器故轻量、开发用 TS 源生产用编译产物；环境加载沿用“本地读文件、容器用注入”
- **开发期流程**：改 Entity → `pnpm migration:dev:generate`（对比生成）→ `pnpm migration:dev:run`（执行）→ 启动 dev；生产对应 `migration:prod:run`
- **迁移做成独立 Job**：多实例各自跑迁移会并发锁冲突、产生脏数据，且新迁移有问题时不应阻塞已运行容器——做法：独立一次性 Job 容器跑在业务容器前（各自 `wait-for-it.sh` 等 MySQL，迁移 `restart: 'no'` 执行完退出，业务用 `depends_on: condition: service_completed_successfully` 等它成功）
- **首次与后续部署**
  - 首次（空库）：`migrations` 表自动建 → 全部迁移按时间戳执行
  - 后续（已有数据）：只执行新增迁移，已有数据不受影响；无新迁移直接跳过
  - 安全保障：已有数据不被框架触碰，除非某 `up()` 显式写 `DROP` / `DELETE` / `TRUNCATE`
- **安全 vs 破坏性迁移**
  - 安全迁移（新增表/字段/索引）可进 CI/CD 自动执行：`docker compose -f docker-compose.prod.yml run --rm --entrypoint "" show-track-server node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`
  - 破坏性迁移（删除/重命名）不可逆，必须人工确认后手动执行


### 部署与工程化 08-生产部署实战

- **统一部署模式与三条原则**
  - 核心原则：MySQL 和 Redis 永远是外部服务，compose 堆栈只管 migration + app
  - 数据库独立于应用栈：生命周期不同，可随时切自建/云 RDS 不动编排
  - 迁移与业务分离：迁移失败不阻塞已有服务，多实例不并发迁移
  - 端口只绑 `127.0.0.1`：对外只有 Nginx 一个入口，安全面最小
- **首次部署四步**
  1. 准备环境变量：`.env.production` 不提交，密码/JWT 密钥/域名填真实值
  2. 起基础设施：`docker compose -f docker-compose.infra.prod.yml up -d`，靠 `restart: always` 与宿主机卷自管
  3. 构建启动应用：`docker compose -f docker-compose.prod.yml up -d --build`
  4. 接 Nginx：写 `conf.d` 配 `proxy_pass http://127.0.0.1:3000/`，公网全走 Nginx
- **一条 `up -d --build` 背后**：build（五阶段 Dockerfile）→ migration 容器等 MySQL 跑 `migration:run` → app 容器等迁移成功、PM2 fork 拉起 NestJS → HEALTHCHECK 探 `/api/health` → 验证 `curl http://your-server:3000/api/health`
- **日常迭代与滚动更新**：`git pull` + `up -d --build`，Compose 先启新容器、健康检查过再停旧容器，单机近似滚动更新、基本不中断
- **数据持久化位置**：MySQL 落 `./__data/mysql/`、Redis 落 `./__data/redis/`（宿主机目录），应用日志落命名卷 `show-track-logs`，容器重建都不丢
- **备份与恢复**：`mysqldump` 备份、`mysql < backup.sql` 恢复；云库由云服务方提供，自建靠宿主机目录 + 定时 `mysqldump`，生产建议每日全量
- **故障排障五问**
  1. 容器活着吗：`docker ps | grep <app>`，没起看重启原因
  2. 健康吗：`docker inspect` 看 Health 与 ExitCode
  3. 应用日志说什么：`docker logs --tail 50`；查当天错误用 `cat logs/app-error.<日期>.log`，按 trace ID `grep` 还原全链路
  4. 是数据库问题吗：`docker logs <mysql-container>`
  5. 被重启过吗：`pm2 logs <app> --lines 50 --nostream`
  - 重启常见原因：库未就绪（等 migration）、环境变量缺失致启动校验抛错、端口冲突；迁移失败用 `docker compose logs migration` 看退出码、查 `migrations` 表状态，事务回滚+幂等不破坏已有数据，修好重跑即可
- **部署检查清单**：镜像构建成功（`docker images` 有最新 tag）、迁移无 ERROR（`docker compose logs migration`）、容器健康（`docker inspect` 看 `State.Health.Status`）、本地接口通（`curl http://127.0.0.1:3000/api/health`）、日志正常写（`ls /app/logs/`）、外部入口通（`curl https://api.example.com/api/health`）


### 部署与工程化 09-CI/CD 自动化部署

- **手动部署的问题与核心区别**
  - 四个问题：易漏步骤、构建吃服务器资源、无法快速回滚、多人发版不可控
  - 核心区别：构建从服务器挪到云端 CI，服务器只拉新镜像、重启容器
  - 对应关系：触发从 SSH 敲命令变 `git tag`；镜像从本地构建变仓库拉取；回滚从重新构建变切旧 tag（秒级）
- **workflow 三概念（`.github/workflows/*.yml`）**
  1. 触发（`on`）：`push` / `tag` / 手动
  2. 任务（`jobs`）：步骤集合，可并行
  3. 步骤（`steps`）：`checkout` / `build` / `deploy`
- **双流水线**：build 负责构建推送，deploy 等 build 成功后再 SSH 部署——构建失败不触发部署，deploy 可在多机复用
  - 流水线一（build-stable.yml）：`on: push: tags: ['v*']`，`docker/login-action` 登录后 `build-push-action` `push: true`，同时打 `stable` 与 `v1.0.0` 两 tag，回滚拉旧 tag
  - 流水线二（deploy.yml）：`on: workflow_run` 监听构建 `completed` 且 `if: success`，`appleboy/ssh-action` 连接，服务器只跑 `pull` + `up -d`；`pull` 替代 `--build`，服务器压力大降
- **Secrets**：在仓库 Settings 配 `DOCKER_USERNAME/PASSWORD`、`DOCKER_IMAGE`、`SERVER_HOST/USER`、`SERVER_SSH_KEY`；建议为 CI/CD 单独生成密钥对（ed25519 + `ssh-copy-id`），不用日常账号
- **迁移进流水线**
  - 安全迁移（新增表/字段/索引）在 deploy 用隔离容器自动执行：`docker compose -f docker-compose.prod.yml run --rm --entrypoint "" my-app node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`
  - 破坏性迁移（删除/重命名）不可逆，自动化没“看一眼”机会，必须人工确认后手动执行
- **触发、回滚与验证**
  - 发版：`git tag v1.0.0 && git push origin master && git push origin v1.0.0`；删 tag：`git tag -d` + `git push --delete`
  - 回滚 = 用旧 tag 再部署一次：CI 重建旧代码镜像并部署，秒级
  - 验证：GitHub Actions 看日志；服务器 `docker ps | grep my-app`、`docker logs -f my-app-server`、`curl https://api.example.com/api/health`


### 脚手架开发 01-脚手架开发入门

- **脚手架的定位**：自动化创建项目的工具，用户命令行交互选配置后自动生成模板，如 `create-react-app`、`nest new`
- **核心流程**：用户输入命令 → 交互式问答（项目名、模板类型）→ 复制模板文件 → 替换模板变量 → 输出生成的项目
- **CLI 工程的三个落点**
  1. 入口约定：`bin/index.js` 首行 `#!/usr/bin/env node`，在 `package.json` 的 `bin` 字段映射成全局命令名
  2. 依赖分工：inquirer 负责交互问答，fs-extra 负责目录复制（比原生 fs 多递归与覆盖便利）
  3. 变量替换：复制完模板读文件，用 <code v-pre>replace(/{{projectName}}/g, ...)</code> 把占位符换成真实项目名
- **yargs 参数解析**：`command('create <name>')` 定义子命令与 positional，`option` 定义 `--template` 等可选参数，`.help()` 自动生成帮助


### 进阶主题 01-消息队列

- **消息队列的本质**：生产者发消息到队列、消费者从队列取消息的异步通信机制；同步是下单等扣库存/发短信/邮件/积分全完成，异步只让用户等下单，其余由队列驱动
- **三大作用**
  1. 异步处理：非核心操作异步执行，用户不必等全部完成
  2. 削峰填谷：高峰时缓冲，像水库蓄水防下游被冲垮
  3. 解耦：生产者和消费者不直接依赖，彼此无需知道对方
- **Kafka 六核心**
  1. Producer：发送消息的应用
  2. Consumer：消费消息的应用
  3. Topic：消息分类，类似数据库表
  4. Partition：Topic 的分区，实现并行处理
  5. Broker：Kafka 集群中的服务器
  6. Consumer Group：消费者组，组内负载均衡消费
- **选型对比：Kafka / RabbitMQ / Redis Stream**
  1. Kafka：吞吐极高（百万级/秒），落磁盘、分区内有序，适合日志/大数据/流处理；学习成本高
  2. RabbitMQ：吞吐高（万级/秒），落磁盘、单队列有序，适合业务系统/任务分发；学习成本中
  3. Redis Stream：吞吐高（万级/秒），内存+磁盘、有序，轻量，适合简单消息/缓存场景；学习成本低


### 进阶主题 02-性能优化

- **缓存三种失效与对策**
  1. 穿透：查不存在的数据每次打到库；对策是缓存空值或布隆过滤器
  2. 击穿：热点 key 过期瞬间大量请求涌向库；对策是互斥锁或热点数据永不过期
  3. 雪崩：大量 key 同时过期压垮库；对策是过期时间加随机值、多级缓存
- **限流四种算法**
  1. 计数器：固定窗口内计数，简单但有突刺
  2. 滑动窗口：细粒度窗口，解决突刺、更平滑
  3. 令牌桶：匀速放令牌、请求消耗，允许突发
  4. 漏桶：匀速处理请求，平滑但不允许突发
- **NestJS 限流落地**
  - 全局：`ThrottlerModule.forRoot({ ttl: 60000, limit: 10 })` 定 60 秒窗口、窗口内最多 10 次
  - 按接口：`@Throttle(5, 60000)` 让单路由 60 秒内最多 5 次
- **数据库优化五手段**
  1. 索引优化：合理建索引，避免全表扫描
  2. 慢查询日志：定位慢 SQL，用 EXPLAIN 分析
  3. 连接池：复用连接，避免频繁创建
  4. 读写分离：主库写、从库读
  5. 分库分表：数据量大时水平拆分


### 进阶主题 03-安全

- **三类常见攻击与防线**
  1. XSS（跨站脚本）：往页面注入恶意脚本，靠模板引擎（Pug）与前端框架（React/Vue）默认 HTML 转义防御
  2. CSRF（跨站请求伪造）：诱导用户在不知情下操作，靠 CSRF Token 防御，NestJS 可用 `csurf` 中间件
  3. SQL 注入：字符串拼接 SQL 就是注入入口，必须用参数化查询（`?` 占位）让驱动做转义
- **框架层三道通用防护**
  1. Helmet：一个 `app.use(helmet())` 批量设安全响应头，成本低收益高
  2. CORS：开发可放开（`app.enableCors()`），生产必须用 `origin` 白名单；带 Cookie 时 `credentials` 与前端 `withCredentials` 成对配
  3. 参数校验：永远不信任输入，`ValidationPipe` 开 `whitelist + forbidNonWhitelisted` 只放行 DTO 声明字段


### 进阶主题 04-测试

- **测试金字塔**
  1. 单元测试：极快、数量最多，覆盖单个函数/方法
  2. 集成测试：速度数量居中，覆盖模块间交互
  3. E2E 测试：最慢、数量最少，覆盖完整请求链路
- **NestJS 两类测试**
  - 单元测试：`Test.createTestingModule({ providers: [...] })` 编译后 `module.get()` 取出待测服务
  - 集成测试：`imports: [AppModule]` 编译出完整应用，`createNestApplication()` + `app.init()` 后用 supertest 打真实 HTTP
- **三种测试替身**
  1. Mock：模拟整个对象，如 `jest.fn().mockResolvedValue(...)`
  2. Stub：替换方法返回值，如 `jest.spyOn(...).mockResolvedValue(...)`
  3. Spy：只监控调用，断言 `toHaveBeenCalledWith`


### 进阶主题 05-设计模式

- **单例与工厂**
  1. 单例：NestJS 的 Provider 默认就是单例，注入到多少类都是同一实例
  2. 工厂：自定义 Provider 的 `useFactory` 按环境返回不同数据库连接，就是工厂模式的落点
- **策略与观察者**
  1. 策略：把算法抽成可互换接口（如多种登录校验），用 `@Inject('AUTH_STRATEGY')` 运行时选择
  2. 观察者：`EventEmitter2` 的 `emit` 发布、`@OnEvent` 监听是框架内置观察者模式，做下单后发短信这类副作用


### 进阶主题 06-系统设计

- **微服务**
  - 连通：`ClientsModule.register` 声明传输（TCP/Redis/Kafka/RabbitMQ），`client.send({ cmd }, payload)` 发消息
  - 拆分原则：按业务拆（用户/订单/商品）、每服务独立数据库、独立部署扩展；同步 HTTP/gRPC，异步消息队列
- **WebSocket 网关**
  - 网关声明：`@WebSocketGateway({ namespace, cors })` 声明命名空间与跨域；`handleConnection(client)` 处理连接
  - 消息与广播：`@SubscribeMessage` 处理消息，`server.emit` 广播给所有客户端
- **高可用五策略**
  1. 负载均衡：多台服务器分担请求
  2. 冗余部署：多实例部署，单点故障不影响
  3. 健康检查：定期检查状态，自动剔除异常节点
  4. 熔断降级：服务不可用返回降级响应而非崩溃
  5. 限流：保护后端不被突发流量打垮


### 进阶主题 07-Git 与协作

- **三种工作流怎么选**
  1. GitHub Flow：main + feature 分支、PR 合并；适合小团队、持续部署
  2. Git Flow：main + develop + feature + release 分支；适合中大型、版本发布
  3. Trunk-Based：所有人 main 上开发、短命分支；适合高频发布、CI/CD 成熟
- **合并策略的取舍**
  1. Merge：`git merge feature` 保留完整历史，但多一个合并提交
  2. Rebase：`git rebase main` 得线性历史、无合并提交，但改写提交
  3. Squash：合并时把多个提交压成一个
- **提交信息规范（Conventional Commits）**：格式 `<type>(<scope>): <subject>`；type 分 `feat` / `fix` / `docs` / `refactor` / `test` / `chore`
- **Code Review 实践**
  - PR 粒度：单次控制在 200~300 行以内
  - 审查顺序：先理解整体逻辑，再看细节
  - 沟通方式：指出问题的同时给建议，用“建议”代替“要求”，尊重作者
  - 审查清单：代码规范、是否有不必要复杂性、异常处理、安全漏洞、测试覆盖
