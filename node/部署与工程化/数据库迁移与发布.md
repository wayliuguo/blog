# 数据库迁移与发布

> 从 synchronize 到生产级迁移：表结构变更管理的渐进式演进
> 实战参考：show-track-server 的 `src/config/data-source*.ts` 与迁移 Job 容器

---

## 为什么"改表结构"需要一套体系

开发时改 Entity 就重启，TypeORM 自动同步表结构，很爽。但**生产环境的表里全是真数据**，任何一次结构变更都可能丢数据、锁表、不可回滚。"改表"从开发技能变成发布流程，就是这一篇的主题。

渐进四步：

| 阶段 | 目标 | 你能获得 |
|------|------|---------|
| ① 认清问题 | synchronize 在生产的危害 | 知道为什么必须迁移 |
| ② 机制原理 | migrations 表、幂等、事务 | 理解迁移如何工作 |
| ③ 架构设计 | 三个 DataSource 的分工 | 生产级配置能力 |
| ④ 发布链路 | 迁移 Job 与业务分离 | 完整发布能力 |

---

## ① 认清问题：synchronize 在生产是定时炸弹

> 示意片段（无配套脚本）
```typescript
// 开发期爽，生产期炸
TypeOrmModule.forRoot({
  synchronize: true, // Entity 一变，数据库自动同步
});
```

| 风险 | 说明 |
|------|------|
| 不可审计 | 谁改了表、什么时候改、改了什么——无从追溯 |
| 不可回滚 | 出问题无法撤销，只能手动修 |
| 数据丢失 | Entity 删字段 → 重启 → 列被删 → 数据永久丢失 |
| 不可审查 | 变更无法通过 Code Review 检查 |
| 迁移失效 | 数据库已和实体同步，`migration:generate` 对比不出差异 |

> **结论**：`synchronize` 只适合早期原型。进入协作开发就要关掉它，表结构变更全部由迁移文件控制。

## ② 机制原理：migrations 表、幂等、事务

### 2.1 migrations 表

TypeORM 在数据库里维护一张 `migrations` 表，记录已执行的迁移：

```sql
CREATE TABLE `migrations` (
  `id` int NOT NULL AUTO_INCREMENT,
  `timestamp` bigint NOT NULL,
  `name` varchar(255) NOT NULL,
  PRIMARY KEY (`id`)
);
```

### 2.2 migration:run 的执行流程

```
1. 连接数据库
2. 检查 migrations 表 → 不存在则自动创建
3. 读取 dist/migrations/*.js 所有迁移文件
4. 对比表中已执行的记录
5. 按时间戳顺序执行未执行过的 up() 方法
6. 每个执行完，在 migrations 表插入记录
```

### 2.3 幂等性：跑多少遍都安全

**已执行的迁移不会重复运行**。即使容器重启多次、`migration:run` 被反复调用，只有新增的迁移文件会被执行；没有新迁移时输出 `"No migrations are pending"` 直接退出。

### 2.4 事务：失败自动回滚

每个迁移的 `up()` / `down()` 默认包在事务里——某个迁移失败，它内部的所有操作整体回滚，不会留下半完成的表结构。

> **注意**：已成功的迁移不会回滚（`migrations` 表已有记录）。要撤销必须显式 `migration:revert`。

## ③ 架构设计：为什么有三个 DataSource

show-track 有三个独立的 TypeORM DataSource 配置，分工完全不同：

| | Local DataSource | CLI DataSource | Runtime DataSource |
|---|---|---|---|
| **文件** | `data-source.dev.ts` | `data-source.ts` | `database.config.ts` |
| **用途** | 本地开发迁移命令 | 生产迁移命令（Docker/CI） | 应用运行时连接 |
| **加载** | `dotenv` 读 `.env.development` | `dotenv` 读环境变量 | `@nestjs/config` |
| **依赖 NestJS** | 否 | 否 | 是（DI 容器） |
| **数据源** | `src/**/*.ts`（TS 源码） | `dist/**/*.js`（编译产物） | `dist/**/*.js` |
| **synchronize** | 硬编码 false | 硬编码 false | 环境变量控制，建议 false |

### 为什么迁移命令要独立于 NestJS？

最关键的设计决策。**`migration:run` 不能依赖 NestJS 启动**：

```bash
# 生产执行迁移（不启动应用，只依赖编译后的 data-source.js + 环境变量）
node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js
```

| 收益 | 说明 |
|------|------|
| 应用有 bug 也能迁移 | 应用启动失败不影响表结构修复 |
| 不经过 DI 容器 | 迁移命令轻量、可独立运行 |
| 开发/生产用不同的加载方式 | 本地用 TS 源码（免 build），生产用编译产物（免 ts-node） |

> 示意片段（无配套脚本）
```typescript
// src/config/load-env.helper.ts（迁移 CLI 的环境加载）
export function loadEnv(defaultEnv: string): void {
  if (process.env.DB_HOST) return;  // 容器/CI 已注入则跳过
  const envFile = `.env.${process.env.NODE_ENV || defaultEnv}`;
  if (fs.existsSync(envFile)) dotenv.config({ path: envFile });
}
```

> 这套"加载策略"和 [环境管理与配置](./01-环境管理与配置) 是同一套思想：**本地读文件、容器用注入**。

### 开发流程（synchronize=false 之后）

```
修改 Entity → pnpm migration:dev:generate（对比生成迁移文件）
           → pnpm migration:dev:run（执行迁移）
           → 启动 dev（应用连接已迁移的库）
```

> 生产对应：`migration:prod:run`（读 `dist/**/*.js`）。

## ④ 发布链路：迁移 Job 与业务容器分离

### 4.1 为什么要把迁移拆成独立容器

多实例部署时，如果每个业务容器启动都跑 migration，会**并发锁冲突、产生脏数据**；而且新迁移有问题时，不应阻止已运行的容器继续服务。

所以 show-track 的做法：**迁移是独立的一次性 Job 容器，在业务容器之前跑**（见 [Docker Compose 编排](./05-Docker%20Compose%20编排)）：

```
迁移 Job 容器（一次性）                    业务容器
   │                                        │
   ├─ wait-for-it.sh 等待 MySQL             ├─ wait-for-it.sh 等待 MySQL
   ├─ migration:run（连接→对比→执行）        ├─ PM2 fork 启动 NestJS
   ├─ 执行完退出（restart: no）              ├─ 等迁移 Job 成功才启动
   │                                        └─ 开始处理请求
   └─ 完成退出                               （depends_on: service_completed_successfully）
```

```yaml
# docker-compose.prod.yml（节选）
migration:
  entrypoint: /usr/local/bin/entrypoint-migration
  restart: 'no'                       # 一次性任务

show-track-server:
  depends_on:
    migration:
      condition: service_completed_successfully   # 迁移成功才启动
```

### 4.2 首次部署 vs 后续部署

| 场景 | 迁移行为 |
|------|---------|
| 首次部署（空库） | migrations 表自动创建 → 全部迁移按时间戳执行 |
| 后续部署（已有数据） | 对比发现只有新增迁移 → 只执行新的，已有数据不受影响 |
| 无新迁移 | 输出 `"No migrations are pending"` 直接跳过 |

> **关键安全保障**：已有数据不会被迁移框架触碰，除非某个迁移的 `up()` 方法显式写了 `DROP` / `DELETE` / `TRUNCATE` 等破坏性操作。

### 4.3 迁移与 CI/CD 的配合

安全迁移（新增表/字段/索引）可以在 CI/CD 流水线自动执行；破坏性迁移（删除/重命名）必须人工确认后手动执行（见 [CI/CD 自动化部署](./09-CI-CD%20自动化部署)）。

```bash
# CI 流水线中执行安全迁移
docker compose -f docker-compose.prod.yml run --rm --entrypoint "" show-track-server \
  node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js
```

## 小结

- **“改表”要成体系**：生产表里全是真数据，任何结构变更都可能丢数据、锁表、不可回滚——从开发技能变发布流程
- **`synchronize` 是定时炸弹**：只适合早期原型，进入协作开发就关掉
  1. 不可审计：谁改、何时改、改了啥无从追溯
  2. 不可回滚：出问题只能手动修
  3. 数据丢失：删字段 → 重启 → 列被删 → 数据永久丢失
  4. 不可审查：变更无法 Code Review
  5. 迁移失效：库已和实体同步，`migration:generate` 对比不出差异
- **迁移执行机制：记录、幂等、事务**
  - `migrations` 表记录已执行（`id` / `timestamp` / `name`），不存在自动创建
  - `migration:run`：连库 → 查表 → 读 `dist/migrations/*.js` → 对比已执行 → 按时间戳跑未跑的 `up()` → 每跑完插记录
  - 幂等：已执行的不会重跑，无新迁移输出 `"No migrations are pending"` 直接退出
  - 事务保护：`up()` / `down()` 默认包事务，失败整体回滚；已成功的迁移不自动回滚，撤销须显式 `migration:revert`
- **三个 DataSource 的分工**
  - Local（`data-source.dev.ts`）：本地开发命令，`dotenv` 读 `.env.development`，吃 `src/**/*.ts` 源码（免 build）
  - CLI（`data-source.ts`）：生产命令（Docker/CI），读注入变量，吃 `dist/**/*.js`（免 ts-node）
  - Runtime（`database.config.ts`）：运行时连接，走 `@nestjs/config` 与 DI 容器；三者 `synchronize` 都建议 false
- **迁移 CLI 独立于 NestJS**：直接 `node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`，不启动应用——应用有 bug 也能迁移、不经 DI 容器故轻量、开发用 TS 源生产用编译产物；环境加载沿用“本地读文件、容器用注入”
- **开发期流程**：改 Entity → `pnpm migration:dev:generate`（对比生成）→ `pnpm migration:dev:run`（执行）→ 启动 dev；生产对应 `migration:prod:run`
- **迁移做成独立 Job**：多实例各自跑迁移会并发锁冲突、产生脏数据，且新迁移有问题时不应阻塞已运行容器——做法：独立一次性 Job 容器跑在业务容器前（各自 `wait-for-it.sh` 等 MySQL，迁移 `restart: 'no'` 执行完退出，业务用 `depends_on: condition: service_completed_successfully` 等它成功）
- **首次与后续部署**
  - 首次（空库）：`migrations` 表自动建 → 全部迁移按时间戳执行
  - 后续（已有数据）：只执行新增迁移，已有数据不受影响；无新迁移直接跳过
  - 安全保障：已有数据不被框架触碰，除非某 `up()` 显式写 `DROP` / `DELETE` / `TRUNCATE`
- **安全 vs 破坏性迁移**
  - 安全迁移（新增表/字段/索引）可进 CI/CD 自动执行：`docker compose -f docker-compose.prod.yml run --rm --entrypoint "" show-track-server node ./node_modules/typeorm/cli.js migration:run -d ./dist/config/data-source.js`
  - 破坏性迁移（删除/重命名）不可逆，必须人工确认后手动执行
