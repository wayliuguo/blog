# 板块、模块与配套代码

博客基于 VitePress（`base: '/blog/'`），按内容领域分板块，板块下再分「模块」。

- 编号规则：**所有目录与文档文件名都不带数字前缀**（含章节文档）；真实阅读顺序以**侧边栏**为准，篇间引用写「见第 X 篇」（X 按侧边栏顺序）。
- 配套代码放在 `<板块>/<模块>/code/<项目名>/`，被 `srcExclude: ['**/code/**']` 排除出页面集合，不进导航、不进构建产物。

实例：

```
node/
  运行环境/                模块目录（不带编号）
    code/                    配套可运行代码
      node-basics/           code 下的项目
    Node.js 是什么.md      章节文档（文件名不带编号）
  总结.md                     模块元页面（见「模块总结与模块面试题」篇）
  面试题.md
```

## 测量型模块：配套代码做成「实验台」

当文章里的结论必须是**可复现的真实数字**（性能、监控、并发、内存这类模块）时，配套代码不写成"演示页"，而写成一个**实验台**：每个现象对应一个能跑出数字的场景脚本，文章里的实测输出块全部来自它的 stdout。本仓实例：`frontend/进阶/性能优化/code/perf-lab`、`frontend/进阶/监控与稳定性/code/monitor-lab`、`frontend/进阶/网络与协议进阶/code/net-lab`、`frontend/进阶/工程实践与架构/code/eng-lab`。

```
<模块>/code/<lab>/
  harness.*       脚手架：对齐表格、起服务、起无头浏览器、等结果
  scenarios/*     一个现象一个脚本，各自能单跑（runAsMain 判断主入口，或用 cli.mjs 分发）；
                  也可收敛成单一入口（如 harness/lab.mjs）按 case 名分发，两种形态都合规
  pages/ 或 site/ 浏览器侧的被测页面
  package.json    每个场景一条 script，名字与文章里的「运行：npm run xxx」逐字一致；
                  单入口形态则统一为 `npm run lab <case>`，case 名同样与正文逐字一致
```

上面是形态 ①② 的目录模板。形态 ③（perf-lab）的目录不同：用 `apps/before` + `apps/after` 两个独立工程 + `shared/` 共享源码 + `shared/public/` 静态资源，**没有 `harness.*` / `scenarios/*` / `pages/`**，也不产生 `npm run lab` 命令；正文数字直接来自浏览器控制台，README 用「实验 ↔ 篇目小节」对照表 + `?act=` 完整 URL 把读者引到数字出处。

几条固定做法：

- **零依赖优先**：只用语言内置能力起服务与浏览器（`PORT=0` 让系统分配端口，再从进程输出里回读真实端口）。
- **让差异可观测**：本机网络下什么都一样快，需要差异时在**服务端**按限速切片发送，把差别放大出来。
- **输出要可复现**：随机数据用固定种子，时间戳对齐到整秒，否则写进文章的数字每次都不一样。
- **依赖注入**：浏览器 API 从 `options.env || globalThis` 取，同一份实现既能进浏览器也能在 Node 里跑单测。
- **被测样本另放 `fixtures/`**：需要被扫描、分析、压测的对象（示例业务目录、待解析的源码）与实验台本身分开，并在 README 里写明「它是故意写坏的」以及坏在哪，读者可以自己先找答案再对答案。
- **口径差异要显式打印**：同一现象两套口径会给出不同的数（窗口 vs 秒桶、`cls` vs `clsRaw`），输出里就要把差异打出来并解释，否则读者会当成 bug。
- **入口形态三选一**：
  1. `scenarios/*` 一场景一文件 + `cli.mjs` 分发；
  2. 单一入口 `harness/lab.mjs` 按 case 分发（收敛成 `npm run lab <case>`）——monitor-lab / net-lab / eng-lab 用此形态；
  3. **纯手动对照**（perf-lab 现用此形态）：两个独立 vite 工程 + 一份共享源码，**无 harness、无 CLI 命令**，测量长在页面里（浏览器原生 `PerformanceObserver` 订阅 paint / LCP / layout-shift / longtask，`performance.getEntriesByType('resource')` 给每个文件 `transferSize`），对照靠打开 before / after 两版 + DevTools 限速 + 控制台读数。
  选 ①② 时 README 必须给「case ↔ 篇目小节」对照表；选 ③ 时 README 给「实验 ↔ 篇目小节」对照表（含 `?act=` 完整 URL），否则读者找不到正文数字的出处。
- **可以再挂一组「页面内手动对照实验」，但只在读数本身是差值时才这么做**。若某条结论的读数**是同一次加载里的前后差值**（换字前/后文本块多高、晚到的元素把下面推下去多少、一次脏更新触发几次子组件渲染），不要塞进 case：case 的模型是「开页面 → 跑一次 → 回报」，硬套就得在里面写「测两次再相减」的壳，还得两次加载各受一次噪声，反而不如让页面自己演一遍、把两个时刻一起打出来。形态是页面带 `?act=` 加载、读数挂 `window.__spa.exp[act]()`、跑完打 console（不带 `report=1` 时不回传）；跑法在 README 与手册篇里写成 `npm run dev:after` + 完整 URL，**不新增 npm 命令**。perf-lab 的 `rerender` / `banner` / `font` / `anim` 属这一类，与 8 个 case 同放一张「实验对照表」下分小表列出。
