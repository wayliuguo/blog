# 项目面试题（追问链版）


## 一、借钱核心页面改造（Weex → Vue3 H5）

### 1.1 背景与动机

**Q1：介绍一下这个项目的背景，为什么要做这次改造？**
- 先给业务定位：借钱核心页面（进件、要素联动、试算、提交），百万级 PV，金融链路
- 痛点分三类讲：① 技术栈——Weex 长期未迭代、社区停滞、与端容器强绑定；② 调试——链路经端容器转发，Chrome DevTools 不可用，效率低；CSS 是受限子集；③ 结构——主组件「视图+数据+请求+校验+埋点」多职责混写，级联试算与 UI 强耦合、多入口重复实现，回归靠手工
- 收口：改造目标 = 迁 Vue3 H5 + 重构 + 补测试监控，降低迭代成本、保障金融链路稳定

**Q2：问题是怎么发现的？还是拍脑袋要重构？**
- 承接日常需求时观察改动半径：小改动要动主组件多个分支，回归面不可预估
- 做了一次代码盘点：废弃业务分支、失效埋点、历史兼容判断、废弃配置
- 问题清单 → 立项，明确推进顺序：先架构骨架 → 冗余下线与数据流重构 → 补测试与监控

> F1：盘点怎么做的？花多久？
> - 逐分支读主组件，标注「还在被路由/入口引用吗 + 最近一次需求动过吗」，按引用关系判废
> - 产出物是问题清单文档，每条带证据（哪里引用、哪个埋点已失效），不是凭感觉列

### 1.2 方案选型

**Q3：为什么不继续用 Weex 重构，而要迁移 H5？为什么不是 RN / Flutter？**
- 拆前提：改造目的不是换更好的跨端方案，而是摆脱「绑定私有容器运行时」；再选 RN 等于换运行时继续绑定
- RN/Flutter 四个劣势：团队 3 人全 Vue 栈换栈成本；金融 App 动态化受合规限制热更新打折；公司容器能力（桥、监控）面向 H5 体系要重对接；缺双端原生兜底人力
- 补充：Weex 本身 Vue 语法 → 同栈迁移成本低；H5 发即生效 + 可灰度回滚匹配高频迭代

**Q4：H5 性能比原生差，怎么考量？**
- 框架：承认短板 → 论证不踩短板 → 补偿手段 → 测量收口
- 页面是表单流程页，瓶颈在首屏耗时不在帧率/手势；首屏用「1 前置 + 4 并行」编排压缩耗时；非关键接口异常不阻塞渲染
- 运行时：Vue3 编译优化 + 组件拆分收敛更新范围、Vant 按需、分包
- 兜底：真出现重交互场景可按页面粒度引入原生，混合架构不冲突

> F1：迁移期间新旧两版怎么共存？
> - 按页面/入口粒度灰度切流，旧版保持可回滚；新页面独立路由挂载，不是在同一组件里写兼容分支

> F2：灰度怎么决定放量节奏？
> - 监控先行：告警与看板先于放量就绪；每批看错误率/白屏/接口成功率与转化等业务指标，无异常再进下一批

### 1.3 实施细节

**Q5：架构迁移具体怎么推进的？怎么保证不出资损？**
- 先立骨架（分层 + ESLint / TS 规范），迁移与重构分开、分批推进、可回滚
- 金融页面安全重构三步：先锁定现有行为（对齐旧逻辑输出）→ 再换实现 → 用例逐项比对验证
- 级联试算（还款方式 → 计息方式 → 分期数）抽成纯函数模块，可逐项单测

> F1：级联试算怎么「锁定行为」的？
> - 先用旧实现跑出一批输入输出对（典型场景 + 边界：0 期、最大期数、非法还款方式），固化为期望值；新实现逐项对拍，不一致就先查口径再改

> F2：迁移中发现旧逻辑本身有 bug 怎么办？
> - 不静默「顺手修」：先和业务确认正确口径 → 区分「迁移内修」（改动小、口径明确）与「单独排期修」（影响面大）→ 无论哪种都记录差异，等价性比对以业务正确口径为准，而不是以旧实现为准

**Q6：重构前后逻辑组织上有什么变化？（Vue2 → Vue3）**
- Vue2 时代逻辑散在 data / methods / computed / mixin，按选项类型切，跨功能聚合困难
- Vue3 用组合式 API 按业务功能聚合逻辑，级联试算、要素联动各自成模块
- 编排与渲染分层：Vue2 时联动靠 watch 隐式触发——改 A 触发 B、B 再触发 C，链路藏在组件里看不见；重构后级联调度收拢到编排层显式调用，谁触发谁、按什么顺序，代码里一眼可见；渲染层只管展示与交互转发
- 沉淀组件迁移 Skill，指导原 Weex 组件按新架构规范批量迁移

> F1：组件迁移 Skill 具体指导什么？
> - 输入旧 Weex 组件 → 按新架构分层规范输出迁移模板：数据放哪、请求走 api 层、校验抽纯函数、埋点保留点位；批量迁移时人只处理 Skill 覆盖不到的差异

**Q7：接口治理做了什么？缓存和竞态具体怎么实现的？**
- 调用收敛到统一 api 层，集中维护缓存与竞态
- 缓存：逐接口传参配置，URL + 入参作为 key、响应作为 value，命中直接返回
- 竞态：请求标记位 + 最后生效——发起请求记标记，响应回来对标记，不是最新标记就丢弃（⚠️ 不说 AbortController / 请求令牌）
- 首屏编排：1 个前置接口（主信息）+ 4 个并行接口（Promise.all），缩短首屏等待
- 非关键接口异常：空值兜底 + 不阻塞渲染，主流程可用

> F1：缓存 key 什么场景会失效或出错？
> - key 含入参序列化：参数对象键序不同会生成不同 key（序列化前做稳定排序）；带时效的参数（时间戳/签名）不能进 key；缓存粒度按业务配置而不是全局一刀切

> F2：标记位方案和 AbortController 比优劣？
> - 标记位：实现简单、不依赖 abort 能力，代价是请求仍会发完（浪费带宽但不影响正确性）；AbortController 能真正取消请求，但要侵入请求链路、兼容 abort 语义
> - 选择依据：目标是「结果正确性」（旧的响应不许生效），标记位已满足且改动半径小

> F3：Promise.all 一个接口挂了怎么办？
> - 首屏的并行接口分关键/非关键：关键接口自身失败走页面级错误态；非关键接口在各自 catch 里空值兜底后再进 Promise.all，保证 all 不会被非关键失败拖挂

**Q8：自动化测试怎么建的？测试点哪来的？**
- 分层：单元（试算等纯函数，Vitest）→ 组件（@vue/test-utils，交互与状态）→ E2E（主流程）
- 测试点按页面功能与金融规则逐项拆解得出（人工梳理 + AI 辅助补全），再由 AI 批量生成用例与用例文档、人工评审
- 结果：页面自测与回归耗时从约 1 小时降到约 10 分钟

> F1：AI 生成的用例质量怎么保证？
> - AI 只提效生成环节：断言是否符合金融规则、边界场景漏不漏由人评审；生成依据是「测试点拆解文档」，不是让 AI 自由发挥

> F2：E2E 怎么保证不 flaky？
> - 等状态不 sleep、测试数据固定、用例独立可单跑、失败重试 + trace 定位（详见自动化测试篇）

**Q9：监控接入了哪些？指标口径怎么统一的？**
- 先说定位：在团队既有监控 SDK 上迭代补齐，不是从 0 自建
- 覆盖 JS 错误率、白屏、接口成功率与耗时；补全埋点，统一命名与口径
- 沉淀产品 / 研发指标口径文档（双视角），配置监控告警；上线后主动发现业务放量导致的问题 2 个

> F1：口径对不上的具体例子？
> - 「成功率」产品口径按转化漏斗（进入下一步算成功）、研发口径按接口 2xx 比例，分子分母都不同；口径文档先定义「谁在什么维度怎么算」，再配看数 SQL，看板按同一份 SQL 出数

### 1.4 结果与数字盘问（高级岗必戳）

**Q10：自测回归 1 小时降到 10 分钟，怎么测出来的？**
- 口径：同一个人按同一份自测清单（页面主流程 + 核心分支）手工走查计时，改造前后各计一次，取量级不精确到秒
- 构成差异：改造前逐项点检 + 手工对试算；改造后单测/组件测试批量跑 + E2E 覆盖主流程，人只看结果与处理失败项
- 答法：讲清「怎么算的」比数字本身更重要——被追问口径能对上，数字才可信

**Q11：「百万级 PV」怎么统计的？**
- 口径：监控埋点统计的页面级 PV 量级（日 PV 量级在百万档），来源是团队监控平台看板
- 主动说明是量级表述，不给精确值——精确值记不住就别硬编

**Q12：「主动发现业务放量导致的问题 2 个」是什么问题？**
- 框架答法：告警触发 → 影响面确认（版本/接口维度）→ 定位是业务放量导致（请求量上涨放大了既有薄弱点）→ 止血与修复 → 复盘补防线
- 面试前从真实经历里各挑一个能讲 2 分钟的案例填进这个框架（什么指标告了、根因、怎么修的）；答不出细节的案例不要往简历上写

### 1.5 压力与假设题

**Q13：迁移上线后出了资损问题，怎么办？**
- 止血优先：回滚到旧版（灰度架构保证旧版随时可回），先控制爆炸半径再定位
- 定位：监控下钻（版本/入口/接口维度）+ 等价性比对记录辅助归因
- 复盘：补用例（这次为什么没拦住）、补告警盲区；如实承认过程与改进，不甩锅

**Q14：如果业务方中途要求插紧急需求，迁移节奏被打断怎么办？**
- 骨架先行的好处在这兑现：新需求落在新架构上写，不回流旧结构
- 冲突时排优先级：线上故障 > 资损风险 > 紧急业务 > 迁移批次；迁移批次顺延但不中断，保住「旧版可回滚」的状态

**Q15：你在项目里的角色？最大的挑战是什么？**
- 核心开发：架构迁移方案设计与落地、核心链路重构、测试与监控接入
- 技术之外：前端 3 人分工、向团队讲清回归范围和回归重点、跨团队方案评审
- 挑战选一个真实展开（如：级联试算行为锁定 / 新旧并行期间的回归），讲「怎么做 + 怎么验证 + 结果」

## 二、监控配置脚手架（CLI 工具）

### 2.1 背景与做法

**Q1：为什么自己写脚手架，而不是手工配置或找现成工具？**
- 痛点：埋点指标注册与告警规则配置逐项手工操作，重复、易错
- 现成工具不贴合内部监控平台的接口与模板规范；自研可控、可演进
- 规模论证：单页面约 60 个指标 × 每项若干次界面操作，误差随指标数线性涨——工具化的收益可预估

**Q2：脚手架做了什么？怎么用的？**
- CLI 工具，发布 npm 包；拆解监控平台的配置接口参数，按配置文件批量发起请求，完成监控告警配置
- 与数据监控 Skill 串联：Skill 产出监控配置 → 人工审查 → 脚手架批量配置，替代逐项手动操作
- 量化：单页面（约 60 个指标）接入配置从约 5 小时降到约 30 分钟，推广两个前端小组 5 名同学使用

### 2.2 实施细节与追问

**Q3：技术上有什么要点？**
- Node.js + commander 命令行框架；axios 对接监控平台接口
- 拆解平台接口参数、配置化生成请求；配置失败的容错与结果反馈
- 收获：CLI 从设计到 npm 发布的完整流程；「Skill 产出配置 + 工具落地执行」的提效模式

> F1：批量配置某一条失败了怎么办？
> - 逐项执行、失败不中断：最后汇总成功/失败清单，失败的带原因（参数缺失/权限/重名），修配置后可重跑
> - 幂等设计：同配置重跑不产生重复告警项（按平台唯一标识判重）

> F2：调用内部接口的凭据和误操作风险怎么控？
> - 人工审查卡在 Skill 产出与脚手架执行之间——配置内容先过人眼；工具只做「照单执行」，不生成配置
> - 配置文件即变更记录：出问题可对照配置文件回溯

> F3：怎么推广的？有人不用吗？
> - 推广靠「替别人跑通第一个页面」：先帮两个小组各接入一个页面建立信任，再给使用文档
> - 诚实答法：没用起来的场景是「一次性配置几个指标的页面」，手工更快——工具的价值在批量，不掩盖边界

### 2.3 数字盘问

**Q4：5 小时降到 30 分钟怎么算的？**
- 口径：60 个指标，手工按每指标数分钟界面操作累计约 5 小时；工具化后 = 准备配置文件 + 人工审查 + 脚手架批量执行，合计约 30 分钟
- 瓶颈转移讲清楚：省的是「逐项界面操作」，花出去的是「写配置 + 审查」——审查环节刻意保留，不追求全自动

**Q5：为什么是你来做这件事？这个工具的非技术价值是什么？**
- 我同时在产出数据监控 Skill 与口径文档，是配置需求的「上游」，顺手把下游执行自动化，闭环最短
- 非技术价值：配置从「个人经验」变成「Skill 产出 → 人审查 → 工具执行」的标准化流程，新人也能接

## 三、赴演记（AI 辅助全栈个人项目）

### 3.1 背景与架构

**Q1：为什么做这个项目？**
- 真实需求：记录 / 检索 / 分享演出经历；同时验证「人定规格 → AI 实现 → 人工评审」的 AI 协作模式、系统性补齐服务端能力
- 口径：我定规格、架构与验收标准，AI 承担实现，我负责逐项评审——不是「AI 随便生成我照抄」

**Q2：三端分别怎么实现的？**
- 服务端：NestJS + TypeORM + MySQL + Redis；JWT 鉴权、日志轮转、统一异常与限流、接口文档；Docker 部署；Redis 支撑排行榜（zset）与热搜缓存
- 链接解析：抽象大麦 / 猫眼 / 秀动三家解析配置，Playwright 抓取，WebSocket 推送进度，替代手工录入
- 前端：管理后台 React 19 + Ant Design；小程序原生 + Vant Weapp + d3-geo 城市地图

> F1：为什么管理后台选 React 而不是 Vue？
> - 个人项目主动补 React 19 实战（主栈 Vue）；Ant Design 生态对中后台成熟；顺带验证自己跨栈的规格表达与评审能力——规格写得清楚，实现栈切换成本可控

### 3.2 关键细节与追问

**Q3：Redis 具体用在哪？为什么非用不可？**
- 排行榜：ZSet——ZINCRBY 更新分数、ZREVRANGE 取榜单，MySQL 排序在数据量与频次上都不划算
- 热搜缓存：热数据加 TTL 挡掉重复计算；缓存设过期与容量上限，避免无界增长
- 诚实边界：个人项目量级下 MySQL 也能扛，用 Redis 的目的之一是练对应场景的正确姿势（穿透/击穿/雪崩的对策）

**Q4：链接解析失败率怎么处理？反爬怎么办？**
- 三家平台解析配置抽象成统一结构，站点结构变化时只改对应配置
- 失败可重试 + 状态可见（WebSocket 推进度，前端不盲等）；解析是低频操作，限流防滥用（429）
- 不编造：没做验证码破解/账号池这类对抗性方案，碰到强对抗就降级为手动补录

**Q5：WebSocket 推进度的实现要点？**
- 解析任务异步执行，任务状态变化推给订阅的前端；连接级心跳保活、断线重连后按任务状态补拉
- 备选方案对比过：轮询实现简单但延迟与浪费都随任务数涨，解析时长不可预期所以选推送

**Q6：AI 协作开发具体怎么落地的？质量怎么保证？**
- 先写规格文档（接口约定 / 数据结构 / 边界条件）→ AI 按规格实现 → 人工逐项评审
- 沉淀两个 Skill：小程序代码审查、平台解析调试
- 强调：AI 提效的是实现环节，设计与验收标准始终由人把控

> F1：规格文档长什么样？举一个字段级的例子？
> - 例：排行榜接口——出参结构（榜单项 = 用户标识 + 分数 + 排名）、并列分数的排序规则、空榜单返回空数组而非 null、分页边界。规格写到「AI 不需要猜」的颗粒度

> F2：评审阶段发现过什么典型问题？
> - 典型三类：边界条件漏（空列表/并列分数）、AI 自作主张加需求外功能、错误处理与规格不符——评审清单对着规格逐项勾，发现即打回
> - 面试前从真实评审记录里备 1~2 个具体例子

> F3：AI 生成的代码出了线上事故谁负责？
> - 我负责。独立项目里没有其他人——这是「人定规格、人评审」模式的根本原因：责任与验收都在人，AI 不是免责对象

### 3.3 压力与假设题

**Q7：三端一个人做，怎么排优先级？烂尾了怎么办？**
- 服务端先行（契约稳定后前端两端并行推进）；每端先跑通主流程再加次要功能
- 已上线的底线：小程序端可用的核心功能优先保；管理后台与服务端功能按使用频率裁剪
- 这题考的是「独立项目的工程判断」，答「全都要」反而减分

**Q8：为什么不用现成 SaaS / 低代码平台搭？**
- 项目目的之一是系统性练服务端与部署能力，SaaS 恰好绕过了要练的部分
- 数据主权与定制性：解析配置、榜单逻辑这些核心环节需要完全控制

## 四、通用追问

**Q1：这三个项目里你个人贡献最大的？**
- 借钱核心页面改造（规模 + 深度，团队协作背景下的核心开发）；脚手架是独立完成度最高；赴演记体现广度与 AI 工作流
- 追问「为什么不是赴演记」：个人项目没有生产规模与多人协同的检验，分量上让位于真实业务项目——诚实且不贬低任何一个

**Q2：如果重来一次会怎么改进？**
- 建议真实复盘，备两条：① 更早补测试（不是迁移完才补，骨架期就给核心纯函数上单测）；② 迁移批次划分可以更细，单批回归面更小
- 反面教材：答「没什么要改进的」或「我会更早用 AI」都太空

**Q3：AI 在你工作流里的位置？**
- 规格与验收标准是人定的；AI 承担实现与初稿；评审与质量门禁是人负责；重复劳动沉淀为 Skill 与工具
- 用项目佐证：技术方案 Skill、自动化测试 Skill、数据监控 Skill + 脚手架、赴演记全流程——「AI 提效 + 人把质量关」不是口号，是一条完整的证据链

**Q4：三段经历里最有挫败感的一件事？**
- 行为题，选真实事件按「情境 → 我当时怎么做 → 结果 → 现在的反思」讲；忌讳编造「过于完美的失败」
- 方向参考：线上问题的第一次应急响应、迁移过程中的口径分歧——重点放在复盘后沉淀了什么机制
