## 一、借钱核心页面改造（Weex → Vue3 H5）

### 背景 / 动机类

**Q1：介绍一下这个项目的背景，为什么要做这次改造？**
- 先给业务定位：借钱核心页面（进件、要素联动、试算、提交），百万级 PV，金融链路
- 痛点分三类讲：① 技术栈——Weex 长期未迭代、社区停滞、与端容器强绑定；② 调试——链路经端容器转发，Chrome DevTools 不可用，效率低；CSS 是受限子集；③ 结构——主组件「视图+数据+请求+校验+埋点」多职责混写，级联试算与 UI 强耦合、多入口重复实现，回归靠手工
- 收口：改造目标 = 迁 Vue3 H5 + 重构 + 补测试监控，降低迭代成本、保障金融链路稳定

**Q2：问题是怎么发现的？还是拍脑袋要重构？**
- 承接日常需求时观察改动半径：小改动要动主组件多个分支，回归面不可预估
- 做了一次代码盘点：废弃业务分支、失效埋点、历史兼容判断、废弃配置
- 问题清单 → 立项，明确推进顺序：先架构骨架 → 冗余下线与数据流重构 → 补测试与监控

**Q3：为什么不继续用 Weex 重构，而要迁移 H5？为什么不是 RN / Flutter？**
- 拆前提：改造目的不是换更好的跨端方案，而是摆脱「绑定私有容器运行时」；再选 RN 等于换运行时继续绑定
- RN/Flutter 四个劣势：团队 3 人全 Vue 栈换栈成本；金融 App 动态化受合规限制热更新打折；公司容器能力（桥、监控）面向 H5 体系要重对接；缺双端原生兜底人力
- 补充：Weex 本身 Vue 语法 → 同栈迁移成本低；H5 发即生效 + 可灰度回滚匹配高频迭代

**Q4：H5 性能比原生差，怎么考量？**
- 框架：承认短板 → 论证不踩短板 → 补偿手段 → 测量收口
- 页面是表单流程页，瓶颈在首屏耗时不在帧率/手势；首屏用「1 前置 + 4 并行」编排压缩耗时；非关键接口异常不阻塞渲染
- 运行时：Vue3 编译优化 + 组件拆分收敛更新范围、Vant 按需、分包
- 兜底：真出现重交互场景可按页面粒度引入原生，混合架构不冲突

### 做法 / 细节类

**Q5：架构迁移具体怎么推进的？怎么保证不出资损？**
- 先立骨架（分层 + ESLint / TS 规范），迁移与重构分开、分批推进、可回滚
- 金融页面安全重构三步：先锁定现有行为（对齐旧逻辑输出）→ 再换实现 → 用例逐项比对验证
- 级联试算（还款方式 → 计息方式 → 分期数）抽成纯函数模块，可逐项单测

**Q6：重构前后逻辑组织上有什么变化？（Vue2 → Vue3）**
- Vue2 时代逻辑散在 data / methods / computed / mixin，按选项类型切，跨功能聚合困难
- Vue3 用组合式 API 按业务功能聚合逻辑，级联试算、要素联动各自成模块
- 编排与渲染分层：Vue2 时联动靠 watch 隐式触发——改 A 触发 B、B 再触发 C，链路藏在组件里看不见；重构后级联调度收拢到编排层显式调用，谁触发谁、按什么顺序，代码里一眼可见；渲染层只管展示与交互转发
- 沉淀组件迁移 Skill，指导原 Weex 组件按新架构规范批量迁移

**Q7：接口治理做了什么？缓存和竞态具体怎么实现的？**
- 调用收敛到统一 api 层，集中维护缓存与竞态
- 缓存：逐接口传参配置，URL + 入参作为 key、响应作为 value，命中直接返回
- 竞态：请求标记位 + 最后生效——发起请求记标记，响应回来对标记，不是最新标记就丢弃（⚠️ 不说 AbortController / 请求令牌）
- 首屏编排：1 个前置接口（主信息）+ 4 个并行接口（Promise.all），缩短首屏等待
- 非关键接口异常：空值兜底 + 不阻塞渲染，主流程可用

**Q8：自动化测试怎么建的？测试点哪来的？**
- 分层：单元（试算等纯函数，Vitest）→ 组件（@vue/test-utils，交互与状态）→ E2E（主流程）
- 测试点按页面功能与金融规则逐项拆解得出（人工梳理 + AI 辅助补全），再由 AI 批量生成用例与用例文档、人工评审
- 结果：页面自测与回归耗时从约 1 小时降到约 10 分钟

**Q9：监控接入了哪些？指标口径怎么统一的？**
- 先说定位：在团队既有监控 SDK 上迭代补齐，不是从 0 自建
- 覆盖 JS 错误率、白屏、接口成功率与耗时；补全埋点，统一命名与口径
- 沉淀产品 / 研发指标口径文档（双视角），配置监控告警；上线后主动发现业务放量导致的问题 2 个

**Q10：发布风险怎么控制？**
- 分批灰度放量，监控先行——告警与看板先于放量就绪
- 等价性验证：新旧页面跑同一批核心场景，比对输出一致后再切流
- 回滚预案：出问题先止血（回滚），再定位根因

### 角色 / 收获类

**Q11：你在项目里的日常职责和普通前端有什么区别？**
- 技术：方案设计、接口口径对齐、任务拆解与前置依赖对齐
- 质量：方案评审、代码把关
- 协调：前端 3 人分工，向团队讲清回归范围和回归重点

**Q12：你在项目里的角色？最大的挑战是什么？**
- 核心开发：架构迁移方案设计与落地、核心链路重构、测试与监控接入
- 挑战建议选一个真实展开（如：级联试算行为锁定 / 新旧并行期间的回归），讲「怎么做 + 怎么验证」

## 二、监控配置脚手架（CLI 工具）

**Q1：为什么自己写脚手架，而不是手工配置或找现成工具？**
- 痛点：埋点指标注册与告警规则配置逐项手工操作，重复、易错
- 现成工具不贴合内部监控平台的接口与模板规范；自研可控、可演进

**Q2：脚手架做了什么？怎么用的？**
- CLI 工具，发布 npm 包；拆解监控平台的配置接口参数，按配置文件批量发起请求，完成监控告警配置
- 与数据监控 Skill 串联：Skill 产出监控配置 → 人工审查 → 脚手架批量配置，替代逐项手动操作
- 量化：单页面（约 60 个指标）接入配置从约 5 小时降到约 30 分钟，推广两个前端小组 5 名同学使用

**Q3：技术上有什么要点？**
- Node.js + commander 命令行框架；axios 对接监控平台接口
- 拆解平台接口参数、配置化生成请求；配置失败的容错与结果反馈
- 收获：CLI 从设计到 npm 发布的完整流程；「Skill 产出配置 + 工具落地执行」的提效模式

## 三、赴演记（AI 辅助全栈个人项目）

**Q1：为什么做这个项目？**
- 真实需求：记录 / 检索 / 分享演出经历；同时验证「人定规格 → AI 实现 → 人工评审」的 AI 协作模式、系统性补齐服务端能力
- 口径：我定规格、架构与验收标准，AI 承担实现，我负责逐项评审——不是「AI 随便生成我照抄」

**Q2：三端分别怎么实现的？**
- 服务端：NestJS + TypeORM + MySQL + Redis；JWT 鉴权、日志轮转、统一异常与限流、接口文档；Docker 部署；Redis 支撑排行榜（zset）与热搜缓存
- 链接解析：抽象大麦 / 猫眼 / 秀动三家解析配置，Playwright 抓取，WebSocket 推送进度，替代手工录入
- 前端：管理后台 React 19 + Ant Design；小程序原生 + Vant Weapp + d3-geo 城市地图

**Q3：AI 协作开发具体怎么落地的？质量怎么保证？**
- 先写规格文档（接口约定 / 数据结构 / 边界条件）→ AI 按规格实现 → 人工逐项评审
- 沉淀两个 Skill：小程序代码审查、平台解析调试
- 强调：AI 提效的是实现环节，设计与验收标准始终由人把控

**Q：这三个项目里你个人贡献最大的？** → 借钱核心页面改造（规模 + 深度）；脚手架是独立完成度最高；赴演记体现广度与 AI 工作流
