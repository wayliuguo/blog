# 面试题 · 性能优化

> 定位：性能是高级岗「必考且必深挖」的模块——指标口径（Core Web Vitals + p75）、原理（渲染流水线 / 主线程 / GC）、分层手段（网络 / 构建 / 渲染 / 运行 / 框架）与场景排查缺一不可。全篇 10 组按「结论先行 + 表格 + 子层级」组织，答案自包含。

## 一、基础概念

### 1. 前端性能优化的目标是什么？核心指标有哪些？

**结论：目标是把「客观加载速度」和「主观体验」都做好；衡量标准是 Core Web Vitals 三件套——LCP（加载）、INP（交互）、CLS（视觉稳定），评级按真实用户 p75 看。**

| 指标 | 中文含义 | 良好阈值（p75） | 用户的话 |
| --- | --- | --- | --- |
| LCP | Largest Contentful Paint 最大内容绘制 | ≤ 2.5s | 多久能看到主要内容 |
| INP | Interaction to Next Paint 交互到下一次绘制 | ≤ 200ms | 点了多久有反应 |
| CLS | Cumulative Layout Shift 累积布局偏移 | ≤ 0.1 | 页面会不会自己乱跳 |

- 口径红线（2026 年现状）
  - **FID 已被 INP 取代**（2024-03 起剔除出 Core Web Vitals）——FID 只测首次交互，后半程体验测不到
  - FMP 已废弃（被 LCP 替代）；TTI 已淡出官方核心体系
  - 三者互不可替代：LCP 优秀但主图不预留尺寸的页面，CLS 照样爆表
- 优化目标的完整表述
  - 快：加载与响应快（LCP / INP）
  - 稳：视觉不跳（CLS）
  - 顺：交互流畅不掉帧（长任务 / 帧率）
  - 感知：减不到零时给反馈（骨架屏 / 进度条）——让用户「感觉」快也是优化
- 辅助指标是「定位刻度」不是「目标」：TTFB（≤800ms，所有加载指标的上限）、FCP（≤1.8s）、TBT（≤200ms，INP 的实验室代理）
- 为什么看 p75 不看平均：性能是右偏长尾分布，均值被少数极慢用户拉高，p75 才代表 75% 用户的真实体验
- 追问：FCP 和 LCP 什么区别？
  - FCP 是「有东西可见」（可能只是页头文本），LCP 是「主要内容可见」（hero 图 / 大标题）；两者差值是用户「白等」的时间

### 2. 浏览器从输入 URL 到页面完整渲染，流程是什么？

**结论：性能视角把全流程拆成「网络 → 解析 → 渲染 → 交互」四段，每段都有对应的优化切入点；DNS / TCP / 缓存的网络细节另有专篇，这里抓渲染链路。**

- 分阶段拆解（性能视角）

| 阶段 | 发生什么 | 可优化点 |
| --- | --- | --- |
| 1 网络请求 | 缓存判断 → DNS → TCP/TLS → 发请求 → 收响应 | 缓存策略、CDN、preconnect、压缩 |
| 2 解析 | HTML 解析建 DOM；遇 CSS 建 CSSOM；遇 JS 加载执行（可能阻塞） | defer/async、关键 CSS、压缩体积 |
| 3 渲染 | DOM + CSSOM → 渲染树 → 布局（Layout）→ 绘制（Paint）→ 合成（Composite） | 关键渲染路径、减少重排、合成属性动画 |
| 4 交互 | 事件循环处理输入，主线程响应用户 | 长任务切片、Worker、防抖节流 |

- 两个关键交叉点
  - **JS 与解析的关系**：同步 `<script>` 阻塞 DOM 解析（JS 可能改 DOM）；CSS 不阻塞 DOM 解析但阻塞渲染（渲染树需要完整 CSSOM）
  - **渲染树只含可见节点**：`display: none` 不进渲染树，`visibility: hidden` 进渲染树不绘制
- 追问：为什么 CSS 放 head、JS 放底部（或 defer）？
  - CSS 放 head 让渲染树尽早完整（不白屏后闪样式）；JS 不阻塞解析（defer / 底部）让 HTML 先解析出结构

### 3. 什么是关键渲染路径？如何缩短？

**结论：关键渲染路径 = 从收到 HTML 到首次渲染出像素，浏览器必须走完的最短链路：DOM → CSSOM → 渲染树 → 布局 → 绘制；缩短 = 减少关键资源数、降低关键资源体积、缩短关键链路长度。**

- 三个关键资源事实
  - HTML 一定关键（解析起点）；CSS 阻塞渲染（渲染树要等 CSSOM）；同步 JS 阻塞解析与渲染
- 缩短手段（对号入座）

| 手段 | 作用 |
| --- | --- |
| 关键 CSS 内联 | 消掉 CSS 的网络往返，首屏样式随 HTML 一起到 |
| 全量 CSS 异步（`media="print"` + onload 切回） | 非首屏样式不再阻塞渲染 |
| script 加 defer / async | JS 退出关键路径 |
| preload 字体 / 首屏图 | 关键资源早发现早下载 |
| 减少关键资源数 | 能合并的合并、能延后的延后 |

- 红线：内联的关键 CSS 必须含首屏布局尺寸——只内联了文字颜色这类非布局样式，等于用 CLS 换 FCP
- 追问：怎么找「关键资源」是哪些？
  - DevTools Coverage：加载页面后看「已用字节 / 总字节」——使用率低的资源就是不该进关键路径的

### 4. 什么是重排（Reflow）和重绘（Repaint）？开销对比？

**结论：重排 = 几何变化触发布局重算（贵），重绘 = 外观变化只重画像素（较便宜）；重排必然引发重绘，重绘不一定重排——优化就是少触发重排。**

| 维度 | 重排 Reflow | 重绘 Repaint |
| --- | --- | --- |
| 触发 | 几何属性变化（宽高 / 位置 / 结构） | 颜色 / 背景等外观变化 |
| 流程 | 布局 → 绘制 → 合成（整条流水线） | 绘制 → 合成（跳过布局） |
| 开销 | 高（可能传染到祖先与兄弟，影响整个渲染树范围） | 中 |
| 典型属性 | width / height / top / left / margin / font-size | color / background / visibility |

- 两者的关系
  - 几何变了 → 布局重算 → 重新绘制 → **重排必带重绘**
  - 只改颜色 → 不用重算布局 → **重绘不重排**
  - transform / opacity → 连重绘都不走 → 只合成（见下题）
- 触发重排的 JS 操作（代码层）
  - 读写几何属性（`offsetWidth` / `getBoundingClientRect` / `scrollTop`）、增删 DOM、改 class、窗口 resize、字体加载完成
- 追问：怎么批量 DOM 操作减少重排？
  - 读写分离（先全读后全写，见三.1）、`DocumentFragment` 攒一批再插入、离线修改（`display: none` 后改完再显示）、class 整体切换代替逐条样式

### 5. 什么是合成（Composite）？为什么 transform/opacity 不触发重排？

**结论：合成是把页面的各个「层」按正确顺序拼成最终画面的过程，由合成器线程独立完成——transform / opacity 只影响层内像素的变换与透明度，几何布局根本没变，所以跳过布局与绘制直达合成。**

- 渲染流水线三级触发

| 级别 | 代表属性 | 走的流程 |
| --- | --- | --- |
| 几何（最贵） | width / top / margin / font-size | 布局 → 绘制 → 合成 |
| 绘制 | color / background / visibility | 绘制 → 合成 |
| 合成（最便宜） | transform / opacity / filter | 只合成（主线程不参与） |

- 为什么 transform 不算布局偏移也不触发重排
  - 元素在布局中的「起始位置」没变——transform 是绘制后对层做矩阵变换；CLS 只统计起始位置变化，所以 transform 动画既流畅又不产生布局偏移
- 合成的前提：元素被提升为独立层（transform / opacity 动画自动提升，或 `will-change` 手动提）
- 隐患（顺带答，防追问）
  - 层不是免费的：每层占 GPU 内存，层爆炸（几千个提升的元素）反而更慢——`will-change` 别滥用，动画结束该移除就移除
- 追问：「展开 / 收起」面板必须改高度怎么办？
  - 高度动画走不了合成——折中：`transform: scaleY` 近似（内容会被压扁，适合图片 / 色块）；或动画只动内部容器让外部布局稳定；或确保变化落在用户交互后 500ms 内（CLS 规范当预期位移豁免）

### 6. 长任务是什么？造成什么问题？如何识别？

**结论：主线程上超过 50ms 的任务就是长任务；期间所有输入都排不上队（卡顿 / 掉帧 / INP 变差）；用 `PerformanceObserver` 监听 `longtask` 类型识别。**

- 为什么门槛是 50ms
  - 交互要 100ms 内反馈；100ms 里还要留出输入处理与渲染的时间，单个任务必须 ≤50ms
- 造成的问题

| 问题 | 机制 |
| --- | --- |
| 输入无响应 | 长任务期间事件排队，点了没反应 |
| 掉帧 | 动画帧间隔 16.7ms，被长任务合并丢帧 |
| INP / TBT 变差 | 阻塞时长直接进 TBT（超出 50ms 部分求和）与 INP |

- 识别方式

```js
const ob = new PerformanceObserver((list) => {
  for (const e of list.getEntries()) {
    // e.duration 总时长、e.attribution 归因（脚本来源）
    console.log('long task:', e.duration, e.name)
  }
})
ob.observe({ type: 'longtask', buffered: true })
```

  - DevTools Performance 火焰图上顶部长任务标记（红色三角）；TBT 在 Lighthouse 报告里直接给
- 治理方向：切片（`MessageChannel` 让出，微任务切片无效）、Web Worker、改算法（见四.4 / 四.5）
- 追问：切片时为什么 setTimeout 不理想？
  - 嵌套 4ms 节流且优先级低；`MessageChannel` 是无节流的宏任务，切片首选（详见四.4）

### 7. 主线程负责哪些工作？为什么阻塞主线程影响交互？

**结论：主线程跑 JS 解析执行、DOM 解析与修改、样式计算、布局、绘制编排、事件分发——所有这些串行排队共享一个线程；它被长任务占住时，用户的输入事件只能等。**

- 主线程的工作清单

| 工作 | 说明 |
| --- | --- |
| JS 执行 | 解析、编译、运行 |
| DOM / CSSOM | 解析 HTML / CSS、响应修改 |
| 样式 / 布局 | 样式计算、Layout |
| 事件分发 | 把输入事件派发给对应处理函数 |

- 为什么互斥
  - 单线程是 JS 的设计约束（避免 DOM 并发修改的锁问题）；渲染与脚本必须协调（JS 可改 DOM，渲染要看到最新 DOM）——所以同一条队列串行
- 不在主线程的部分
  - 合成、部分光栅化在合成器 / 光栅线程；Worker 在独立线程——这就是「动画用 transform 保流畅」「计算放 Worker」的底层原因
- 推论（面试加分表述）
  - 一切运行时优化本质都在回答同一个问题：「让主线程的队列短一点」——切片是拆长任务、Worker 是搬走任务、节流是减少任务、合成动画是绕开主线程
- 追问：主线程阻塞时页面完全不响应吗？
  - 合成器线程还活着——滚动 / 已启动的 transform 动画仍流畅；但新的事件处理（点击回调、输入响应）全部排队

## 二、加载阶段优化（网络层面）

### 1. 网络层面的性能优化有哪些手段？

**结论：围绕「少传输、快到达、不重复」三原则——压缩与精简（少传输）、CDN 与协议升级（快到达）、缓存与复用（不重复）。**

| 原则 | 手段 |
| --- | --- |
| 少传输 | gzip/brotli 压缩、tree-shaking、按需引入、图片格式（WebP/AVIF） |
| 快到达 | CDN 就近接入、preconnect/dns-prefetch、HTTP/2 多路复用、域名收敛、减少重定向 |
| 不重复 | 强缓存 + 内容 hash、协商缓存、Service Worker 离线缓存 |

- 总览之外的两个现代要点
  - 域名分片（H1 绕并发限制）在 H2 下**反效果**——破坏连接复用，应域名收敛；雪碧图同理不再必要
  - 升级 HTTP/3（QUIC）：传输层消灭队头阻塞、TLS 握手合并，首连更快（需服务端支持）
- 追问：这些手段怎么排优先级？
  - 按 ROI：缓存与压缩零成本收益最大 → CDN 次之 → 协议升级依赖基建 → 图片优化按页面占比

### 2. 强缓存与协商缓存的原理？Cache-Control、ETag、Last-Modified 区别？

**结论：强缓存浏览器自己决定（不发请求），协商缓存问服务器资源有没有变（发条件请求）；Cache-Control 是强缓存指令，ETag / Last-Modified 是协商缓存的两对验证字段。**

- 判断顺序

```
请求发起 → 有缓存副本？
  → Cache-Control 未过期（max-age 内）→ 直接用（强缓存，from disk/memory cache）
  → 过期了 → 带 If-None-Match(ETag) / If-Modified-Since 发条件请求
    → 资源没变 → 304（协商缓存，用本地副本）
    → 变了 → 200 新资源
```

| 字段对 | 类别 | 说明 |
| --- | --- | --- |
| `Cache-Control: max-age / no-cache / no-store` | 强缓存 | 相对时间优先于 Expires；`no-cache` 是「可存但必校验」，`no-store` 是彻底不存 |
| `ETag / If-None-Match` | 协商缓存 | 内容指纹（精确到内容），优先级高于 Last-Modified |
| `Last-Modified / If-Modified-Since` | 协商缓存 | 秒级时间戳（精度粗：1 秒内多次改动感知不到） |

- ETag 为什么优先
  - Last-Modified 无法表达「内容回滚」（时间变了内容没变）与秒内多次修改；ETag 按内容生成，语义准确——代价是服务端要算 hash，集群环境各机器生成要一致
- 落地组合（性能视角）
  - HTML：`no-cache`（每次协商，保证入口新鲜）；带 hash 的 JS/CSS/图片：`max-age=31536000, immutable`（一年强缓存）——发版换 hash，二次访问传输归零
- 追问：缓存判断的完整细节在哪？
  - 浏览器原理篇缓存题有完整版（含 disk / memory cache 分级与 Vary）；性能篇抓「怎么设计策略」这条线

### 3. gzip 和 brotli 的区别？适用场景？

**结论：brotli 压缩率比 gzip 高 15~20% 但高压缩档位慢——静态资源构建期预压缩用 brotli，动态响应用 gzip（实时压缩要快）；两者都需要 `Accept-Encoding` 协商。**

| 维度 | gzip | brotli |
| --- | --- | --- |
| 压缩率 | 基准（约 70%） | 再小 15~20% |
| 压缩速度 | 快（实时压得动） | 高质量档位慢 |
| 支持面 | 全量 | 现代浏览器全支持（IE 除外） |
| 适用 | 动态 API 响应、实时压缩 | 静态资源构建期预压缩 |

- 工程要点
  - 构建期预压缩出 `.gz` / `.br` 文件，Nginx `gzip_static` / `brotli_static` 直接发——比实时压缩省 CPU
  - 图片 / 视频 / 已压缩格式不再 gzip（白费 CPU 还可能变大）
- 追问：为什么 brotli 高质量档不能实时用？
  - 压缩耗时随质量档暴涨，动态响应等不起；brotli 的正确打开方式是「压一次用无数次」的静态场景

### 4. 图片优化有哪些方案？

**结论：四层体系——格式（WebP/AVIF）、响应式（srcset 按屏给对尺寸）、懒加载（首屏之外）、优先级（首屏图提权）；懒加载只省首屏后的带宽，不改善首屏。**

| 层 | 手段 | 要点 |
| --- | --- | --- |
| 格式 | WebP / AVIF / SVG / `<picture>` 回退 | AVIF 比 JPEG 小 25~35%；图标用 SVG；CDN 按请求头 `Accept` 自动转格式 |
| 响应式 | `srcset` + `sizes` | 各档图片**宽高比必须一致**（否则引入 CLS）；移动端别拉 PC 大图 |
| 懒加载 | `loading="lazy"` 或 IntersectionObserver | 有约 1250px 预加载距离；首屏外的图才懒 |
| 优先级 | 首屏图 `fetchpriority="high"` | **首屏内千万别加 lazy**，会推迟 LCP |

- 懒加载的真相（高频挖坑）
  - 实测 12 张图集加 lazy：传输 2.35MB → 1.17MB，**LCP 几乎没动**——它优化的是「滚动路径上的带宽竞争」；LCP 元素在首屏内时，lazy 反而害了 LCP
- 细节清单
  - 写死 `width` / `height`（防 CLS）；小图标可内联 base64（<2KB；大图 base64 膨胀约 1/3 且占主包）；雪碧图在 HTTP/2 下不再必要
- 追问：LQIP / 模糊占位是什么？
  - 先给一张极小低清图（几百字节）放大当占位，高清图到了再换——弱网下用户立刻「看见」内容，是感知层手段（不改变真实加载）

### 5. preload、preconnect、prefetch 三者区别和使用场景？

**结论：preconnect 提前建连接，preload 高优先级下当前页资源，prefetch 空闲时下下一页资源——前两个救「连接慢 / 发现晚」，prefetch 救「下一跳慢」。**

| 指令 | 做什么 | 优先级 | 场景 |
| --- | --- | --- | --- |
| `preconnect` | 提前 DNS + TCP + TLS | — | 关键第三方域（字体域 / API 域） |
| `preload` | 立即高优先级下载当前页资源 | High | 浏览器发现得晚的关键资源（字体 / 首屏大图） |
| `prefetch` | 空闲时下载下一页资源 | Lowest | 确定性动线（列表页预取详情页 chunk） |
| `dns-prefetch` | 只解析 DNS | — | preconnect 的兜底降级 |

- 四个高频坑
  - preload 了「几秒内用不到的」资源 → 抢首屏带宽，提速变挤占
  - preload 字体必须 `as="font"` + `crossorigin`（字体请求恒为匿名模式）——不带会**下载两次**
  - `fetchpriority="high"` 是更轻的提权（不重复下载、只提优先级）——LCP 图优先它而不是 preload
  - prefetch 只做确定性动线，乱 prefetch 等于替用户下载垃圾
- 追问：preload 和 fetchpriority 怎么选？
  - 资源在 CSS / JS 里浏览器发现得晚（字体、背景图）→ preload；资源在 HTML 里已早发现，只是优先级低（img 默认 Low）→ fetchpriority 提权

### 6. JS、CSS 文件放置位置为什么会影响首屏？

**结论：CSS 放 head 让渲染树尽早完整（避免白屏后样式闪变），同步 JS 放底部（或 defer）让 HTML 解析不被阻塞——两者都在缩短关键渲染路径。**

- CSS 放 head 的原理
  - 渲染树 = DOM + CSSOM，CSSOM 没齐就不绘制；CSS 放前面尽早开始下载构建 → 首次绘制提前
  - 反例：CSS 放 body 尾部 → 前面先按无样式渲染，CSS 到了再重画一次（FOUC 闪变 + 双倍绘制）
- JS 放底部 / defer 的原理
  - 同步 `<script>` 阻塞 DOM 解析（JS 可能改文档，浏览器必须停下等它下载执行完）
  - 底部：解析不被挡，脚本最后执行；`defer`：下载不阻塞、解析完按序执行——现代方案优先 defer，语义等价且更早开始下载
- 现代修正（老答案的更新）
  - `type="module"` 天然 defer 语义；`async` 用于完全独立的脚本（统计 / 埋点）
  - 「CSS 放 head」不等于「CSS 全放 head」——关键 CSS 内联 + 全量 CSS 异步化才是完整答案（呼应一.3）
- 追问：JS 放底部还有什么问题吗？
  - 底部脚本下载起步晚且仍阻塞 `DOMContentLoaded`——defer 在 head 里就能并行下载，比放底部更优

### 7. 大的 JS 包怎么分包？路由懒加载、动态 import 的原理？

**结论：路由级代码分割是主线——动态 `import()` 让打包器把模块切成独立 chunk，路由切换时才拉取；它是「时序优化」不是「体积优化」，必须配空闲预取成对使用。**

- 动态 import 的原理

```js
// 静态 import：编译期合并进主包
import Report from './views/Report.vue'
// 动态 import：打包器切出独立 chunk，运行时按需拉取执行
const routes = [{ path: '/report', component: () => import('./views/Report.vue') }]
```

- 收益公式与实测
  - 收益 = **被拆出去那部分有多大 × 它上首屏的概率有多低**——拆重组件（报表 / 图表）才值得，拆十几行的组件量不出效果
  - 实测：五视图全量打包单 bundle 78.0KB（哪页都一样）→ 分割后落地页 61.1KB；代价是切路由现拉 chunk（+50ms 一跳延迟后 129ms），空闲预取补回 74ms
- 成对原则（必答）

```js
const idle = window.requestIdleCallback || ((cb) => setTimeout(cb, 1))
idle(() => import('./views/Report.vue')) // 空闲预取下一跳
```

  - 只分割不预取：首次切路由变卡；只预取不分割：等于没分——两者成对
- 其他分包维度
  - 第三方库拆 vendor chunk（变动少、缓存友好，见六.5）；组件级懒加载（重组件 defineAsyncComponent / React.lazy）
- 追问：分割后首屏请求数变多，亏吗？
  - 不亏——HTTP/2 并发下多一个小请求的往返成本远小于少下载几十 KB；但要防拆太细把请求碎片化

### 8. Tree-Shaking 的原理、生效前提与失效坑？

**结论：基于 ESM 静态结构在编译期标记「没被引用的导出」并删除；三条硬前提——ESM、库声明无副作用、访问方式静态；最大的认知坑是它删不掉「引用了但没执行到的分支」。**

- 原理一句话
  - ESM 的 import/export 在编译期就能确定依赖图 → 打包器从入口做可达性分析 → 不可达的导出标记 → 压缩阶段删除
- 三条硬前提

| 前提 | 说明 | 失效反例 |
| --- | --- | --- |
| 必须 ESM | CommonJS 动态 require 无法静态分析 | `const _ = require('lodash')` |
| 副作用声明 | 库标 `sideEffects: false` 才敢删 | 带 polyfill / 样式副作用的包需豁免声明 |
| 访问静态 | 只删「没被引用的导出」 | `import * as utils`、`utils[name]` 动态访问断掉分析 |

- 常见失效坑清单
  - babel 配置残留 `modules: 'commonjs'`（ESM 被转成 CJS）
  - 全量默认导入 UI 库（`import Antd from 'antd'`）——按需子路径引入才能救
  - 类成员 / 原型挂载（打包器视为有副作用不敢删）
  - CSS 无静态依赖图可分析，要 purgeCSS / 原子化方案
- 能力边界（高频追问）
  - tree-shaking：删**没被引用的导出**；死代码消除（压缩器）：删**引用了但执行不到的分支**——两个阶段两个工具，别混

### 9. 第三方脚本（埋点、统计、广告）对页面性能的影响？怎么优化？

**结论：第三方脚本是首屏性能的隐形大头——同步加载阻塞、执行占主线程、体积不可控；优化按「延迟加载 → 隔离执行 → 自托管」三层。**

| 影响 | 机制 |
| --- | --- |
| 阻塞解析 | 文档中同步 `<script src>` |
| 占主线程 | 统计逻辑常做大量 DOM 扫描与同步请求 |
| 链式加载 | 一个第三方再拉五六个下游，瀑布拖长 |
| 隐私与安全 | 拿到页面上下文，可读可改 |

- 优化手段

| 手段 | 做法 |
| --- | --- |
| async / defer 加载 | 统计类脚本全部 async（不依赖执行顺序） |
| 延迟注入 | 交互后（首次点击 / 空闲时）才动态插入脚本 |
| facade 模式 | 嵌入物（视频 / 客服窗）先渲染假封面，点击才加载真实 iframe |
| 自托管 | 统计脚本下载后挂自己域——去掉第三方 RTT 依赖 + 版本可控 |
| Worker 隔离 | Partytown 类方案把第三方脚本挪进 Web Worker 执行 |

- 追问：为什么 facade 模式有效？
  - 嵌入物的真实脚本（视频播放器动辄几百 KB）绝大多数会话根本不会被点击——为「可能的一次点击」付全量首屏成本是错账，点击时再付（多等几百毫秒）是正确取舍

### 10. 什么是资源瀑布？如何减少资源瀑布？

**结论：瀑布 = 资源间因依赖与发现顺序形成的串行等待；减少 = 削减关键资源数、拉平串行链（preconnect/preload）、提高并发（HTTP/2）。**

- 瀑布的三种成因

| 成因 | 例子 | 解法 |
| --- | --- | --- |
| 依赖链 | HTML → CSS → 背景图 → 字体（层层发现） | preload 把深层资源提到最前 |
| 连接建立 | 每个新域都要 DNS+TCP+TLS | preconnect 提前握手、域名收敛 |
| 串行执行 | 同步脚本互相等待 | defer/async、H2 并发 |

- 减少瀑布清单
  - 关键资源数压到最少（内联关键 CSS、defer JS）
  - 深层关键资源 preload（字体是最典型的「第四层才发现」资源）
  - HTTP/2 让并发不再受 6 连接限制——合并文件从「必须」变「视情况」
  - 分析工具：Network 瀑布图看「priority 列 + 依赖链」；Lighthouse 的 render-blocking 审计
- 追问：怎么判断一条资源「该不该」在瀑布的早期？
  - 问它是不是首屏必需：是 → 提前（preload/内联）；否 → 延后（lazy/prefetch）——最怕的是「早发现的非关键资源」占着带宽

## 三、渲染阶段优化

### 1. 哪些 DOM 操作会触发重排？如何批量 DOM 操作减少重排？

**结论：读写几何信息、增删改节点都会触发重排；批量化的核心是读写分离——强制同步布局（写完立刻读）才是循环里的真正杀手。**

- 触发重排的操作

| 类别 | 例子 |
| --- | --- |
| 读布局 | `offsetWidth/Height`、`getBoundingClientRect`、`scrollTop/Left`、`getComputedStyle` |
| 写几何 | 改 width/height/position、增删节点、改含布局属性的 class |
| 全局性 | resize、字体加载完成、内容变化 |

- 强制同步布局（layout thrashing，高频下钻点）

```
// 错误：循环里「写完立刻读」——每次读都迫使浏览器同步重排
for (const row of rows) {
  row.style.height = x        // 写（布局失效）
  total += row.offsetHeight   // 读（此刻必须重排才能回答）
}
```

- 批量手段

| 手段 | 做法 |
| --- | --- |
| 读写分离 | 先循环读完所有布局值存数组，再循环写 |
| 缓存代替读 | 上次计算的尺寸缓存，不重复读 |
| 写延到下一帧 | 写放 `requestAnimationFrame`，rAF 里只读一次（fastdom 的原理） |
| 离线批量改 | `DocumentFragment` / `display:none` 后改完再显示 |

- 实测对照（连滚一屏）：全量 + 每行写完就读 → 长任务不断；同一渲染只在 rAF 读一次 → 长任务归零
- 纪律：先在 DOM 节点数不变的前提下只换读写写法——分清「读写的锅」还是「节点数的锅」，再决定上虚拟列表
- 追问：为什么读布局属性会触发重排？
  - 浏览器是惰性重排（攒到下一帧）；此刻读依赖布局的值，必须现在算准才能回答——同步重排被迫发生

### 2. 虚拟 DOM 为什么能提升渲染性能？一定更快吗？什么场景反而更慢？

**结论：虚拟 DOM 的价值是把「操作 DOM」抽象成「描述 UI + 最小化 diff」，用一次批量更新替代 N 次手动零散更新；但裸比操作次数，直接操作真实 DOM 更快——虚拟 DOM 买的是可维护性与确定性，不是绝对速度。**

- 为什么通常更快
  - 真实 DOM 操作贵在「每次都触发样式 / 布局管线」；虚拟 DOM 把 N 次操作合并成一次 diff，只 patch 真正变化的部分——省的是「无脑全量更新」
  - 附带收益：声明式 UI、跨平台（渲染器可换）
- 什么时候反而更慢

| 场景 | 原因 |
| --- | --- |
| 极简单的静态页 | diff + 框架运行时是纯开销，原生操作一步到位 |
| 大量高频细粒度更新 | diff 本身有成本；细粒度响应式（Vue）比全量 vdom diff 更省 |
| key 用错 | diff 退化成全量 patch（见 Vue 篇 key 题） |
| 超大列表全量渲染 | vdom diff 也要遍历全部——虚拟列表才是正解 |

- 框架技术选型差异（一句话级别）
  - React：全量 vdom diff + 可中断渲染（Fiber）；Vue：响应式依赖收集让更新只到组件级（组件内才 diff），粒度更细
- 追问：Svelte / Solid 这类无 vdom 方案快在哪？
  - 编译期直接生成「精确到具体 DOM 操作」的更新代码，跳过运行时 diff——证明 vdom 是「工程折中」不是「性能上限」

### 3. 减少 DOM 节点数量有哪些手段？

**结论：DOM 量级直接影响布局 / 重排 / 内存开销（官方参考 <1500 节点）——手段是虚拟列表、按需渲染、扁平化结构、内容懒挂载。**

| 手段 | 场景 |
| --- | --- |
| 虚拟列表 | 长列表（详见三.7） |
| 懒挂载 | 面板 / 弹层内容打开时才渲染（而非一开始全渲染藏起来） |
| 分页 / 分批渲染 | 首屏一批，`requestIdleCallback` 空闲补齐 |
| 结构扁平化 | 去掉纯装饰的包裹层 div（每个节点都参与样式计算与布局） |
| 组件复用 | 相似结构组件化，避免复制粘贴出重复子树 |

- 为什么节点数重要（原理级）
  - 布局计算范围与节点数相关——一个节点几何变了，重排可能传染到兄弟与祖先；全量 DOM 也是内存占用与 GC 压力的大头
- 追问：怎么量化当前页面的 DOM 健康度？
  - Lighthouse 的「Avoids an excessive DOM size」审计（给节点数与最大深度）；`document.getElementsByTagName('*').length` 快速看总量

### 4. CSS 优化：选择器性能、昂贵属性、哪些属性触发重排？

**结论：选择器性能在现代引擎里影响很小（别再背「从右往左匹配」当优化主手段），真正值钱的是：减少触发重排的属性、避免昂贵效果滥用、控制样式计算范围。**

- 选择器性能的真实地位
  - 引擎已高度优化（Bloom 过滤 + 从右往左匹配），常规选择器差异微秒级——除非极深层级链或通配符全量扫描
  - 值得做的：缩短选择器（同时省 CSS 体积）；用类代替深层后代链
- 昂贵 / 触发重排的属性分级

| 级别 | 属性 |
| --- | --- |
| 重排（最贵） | width / height / margin / padding / top / left / font-size / border |
| 重绘 | color / background / box-shadow / border-radius |
| 合成（便宜） | transform / opacity / filter |

- 昂贵效果的两个典型
  - 大模糊半径 `box-shadow` 大面积使用：重绘成本高（动画时更明显）
  - `position: fixed` 泛滥：每层 fixed 都可能提层，层爆炸占内存
- 样式计算范围优化
  - 避免频繁切换大 class（整树样式失效）；动画元素样式隔离（独立层）；`content-visibility: auto` 让屏幕外内容跳过渲染（现代利器，长页面分区渲染）
- 追问：`content-visibility: auto` 有什么坑？
  - 含锚点定位的长页面可能出现滚动条跳动——屏幕外内容未布局时高度未知，需要 `contain-intrinsic-size` 给预估尺寸

### 5. CLS 高怎么修？（黄金四类）

**结论：CLS 是写法问题不是性能问题——只看元素在布局里的起始位置有没有变；黄金四类修完即可归零：尺寸预留、字体度量、动态内容插入、动画写法。**

| 来源 | 根因 | 修法 |
| --- | --- | --- |
| 尺寸未预留 | 图片 / 广位 / iframe 加载后撑开 | **在 HTML 写 width/height**（不是 CSS），浏览器自动算 aspect-ratio；广告位 `min-height` 占位 |
| 字体换字 | 回退字体度量 ≠ 正式字体 | `size-adjust` 校准 + 字体 preload |
| 动态内容 | 新元素插到已有内容**上方** | 预留容器；绝不在已有内容上方插入 |
| 动画写法 | 用 top/left/margin/height 做动画 | 只用 transform / opacity |

- 关键实测
  - 主图不写尺寸 CLS 0.0633、写死 0.0000——**判据：图片还没开始下载时，位置高度就已经是对的**
  - 240px 横幅插 body 最前，影响比例接近 1，一次就超 0.1——「插上方」是重灾区
- 口径细节
  - 只累加「没有紧跟用户输入的位移」（交互后 500ms 内算预期豁免）；位移在 500ms 窗口内、影响面积 ≤5% 视口才合并为一次
  - 换字重排量「位移像素」别看 CLS——重排拆到几帧结算，CLS 数值会反转失真
- 追问：为什么开发环境看不见 CLS 问题？
  - 本地资源秒到没有位移窗口——必须 DevTools 限速（Slow 3G）复现

### 6. 开启 GPU 加速有什么好处与隐患？

**结论：GPU 加速 = 把元素提升为合成层，动画由合成器线程按 GPU 完成——主线程阻塞时动画依然流畅；隐患是每层占显存，层过多（层爆炸）反而变慢。**

| 维度 | 说明 |
| --- | --- |
| 好处 | 动画走合成：不重排不重绘不进主线程队列；transform/opacity 动画稳定 60fps |
| 提层方式 | 动画中自动提升；`will-change: transform` / `translateZ(0)` 手动提 |
| 隐患一 | 每层占 GPU 内存——层爆炸（大量 fixed / 提升元素）内存暴涨 |
| 隐患二 | 层管理有开销——层频繁创建销毁引发「层颠簸」，动画开始卡一下 |
| 隐患三 | 文本渲染可能模糊——提层后按层光栅化，非整数缩放发虚 |

- 使用纪律
  - `will-change` 只加给真正要动的元素、动画结束后移除；别全局撒
  - 先验证瓶颈在渲染（火焰图），再提层——不是「加了就快」
- 追问：怎么观察层的使用情况？
  - DevTools → Layers 面板：层数量、每层尺寸、内存占用与提升原因

### 7. 虚拟列表（虚拟滚动）原理、解决什么问题、有哪些边界问题？

**结论：只渲染可视区 + 上下缓冲的 DOM，滚动时按 scrollTop 换算窗口复用节点——解决「DOM 太多」的量级问题；不解决「计算太重」，且有不定高锚定等边界。**

- 原理（可手画的四步）

```
1. 容器总高度用占位元素撑起（保证滚动条长度正确）
2. 监听滚动（rAF 合帧），scrollTop → 起始索引 = floor(scrollTop / 行高)
3. 只渲染 [start - buffer, end + buffer] 的行，绝对定位偏移到正确位置
4. 视口外节点复用回收
```

- 实测效果：全量 10030 节点 → 虚拟化后 108 节点
- 边界问题（高级岗深挖区）

| 边界 | 说明与解法 |
| --- | --- |
| 不定高 | 行高未知 → 渲染后实测缓存、预估先顶实测后校正（react-window 内置） |
| 滚动抖动 | 快速滚动窗口重算 → 加大 buffer + rAF 合帧 |
| 全列表操作 | 搜索 / 全选 / 统计要全量数据 → 数据层全量、渲染层窗口化，两层分开 |
| 顶部插入 | 新数据插到头部要修正 scrollTop 防跳动 |

- 判据（先分锅再上）
  - 节点量级问题（几千上万行）→ 虚拟列表；计算重（滚动里聚合）→ 切片 / Worker；读写交替 → 读写分离——三者常并存，按序消
- 追问：虚拟列表的滚动条为什么会「跳」？
  - 不定高时总高度靠预估——实测后预估修正，总高变化带动滚动条位置跳；成熟库用「已渲染行高缓存 + 修正系数」平滑

## 四、JS 代码层面优化

### 1. 如何避免 JS 阻塞渲染？defer 和 async 的区别？

**结论：defer 与 async 都不阻塞解析，区别在执行时机——defer 按序在 DOMContentLoaded 前执行（有依赖的业务包），async 下载完立即执行（顺序不保证，独立脚本）。**

| 属性 | 下载 | 执行时机 | 顺序保证 | 适用 |
| --- | --- | --- | --- | --- |
| 无（同步） | 阻塞解析 | 下载完立即 | 有 | 极少数必须在解析中途跑的 |
| `defer` | 并行不阻塞 | DOM 解析完、DOMContentLoaded 前 | 按文档顺序 | 业务主包（依赖 DOM 与彼此） |
| `async` | 并行不阻塞 | 下载完立刻 | 无 | 统计 / 埋点等独立脚本 |
| `type="module"` | 并行不阻塞 | 同 defer 语义 | 有 | 现代模块入口 |

- 补充要点
  - 动态插入的 `<script>` 默认 `async`——想按序可设 `script.async = false`
  - module 脚本天然 defer，但模块内顶层 await 会延后执行
  - 「JS 放底部」是 defer 的老式等价物，defer 在 head 里即可并行下载，更优
- 追问：async 脚本为什么不能给业务代码用？
  - 执行顺序不保证——多文件有依赖时谁先到谁先执行会炸；且执行时 DOM 可能还没解析完，拿不到节点

### 2. 闭包、全局变量对内存的影响？内存泄漏常见场景？

**结论：闭包让被引用的外层变量无法回收、全局变量挂在 window 上生命周期等于页面——四类高频泄漏：监听没摘、定时器没清、全局缓存只增不减、闭包绑大对象。**

- 原理级
  - GC 按可达性回收：只要还有引用链到根（window），对象就不可回收——闭包 / 全局都是「制造持久引用链」的方式
- 四类泄漏与解法

| 类型 | 典型代码 | 解法 |
| --- | --- | --- |
| 事件监听没摘 | 组件卸载没 removeEventListener | 卸载钩子成对摘除；AbortController 一次解绑一组 |
| 定时器没清 | setInterval 持续跑 | 卸载时 clearInterval |
| 全局缓存只增 | 结果全塞 module 级 Map | LRU / 上限淘汰 |
| 闭包绑大对象 | 回调拖着大数组 | 用完置 null、缩小捕获范围 |

- 排查手段：Memory 面板堆快照对比、Detached DOM（详见场景八.3「越用越卡」路径）
- 追问：怎么区分「泄漏」和「缓存」？
  - 看增长是否有界——缓存有淘汰策略时峰值稳定，泄漏单调增长永不回落；固定操作序列压 50 轮看曲线形状

### 3. 防抖、节流的原理、适用场景与区别？（手写见九.1 / 九.2）

**结论：防抖是「停止触发 N ms 后只执行最后一次」（保结果），节流是「每 N ms 最多执行一次」（保频率）；rAF 合帧是渲染类任务的第三选择。**

| 手段 | 语义 | 典型场景 |
| --- | --- | --- |
| 防抖 debounce | 最后一次触发后延迟执行 | 搜索输入、resize 结束后重算 |
| 节流 throttle | 固定节奏执行 | scroll / mousemove / 拖拽 |
| rAF 合帧 | 每帧最多一次，与渲染对齐 | 滚动渲染、读布局 |

- 性能视角的关键区分
  - 防抖是**业务语义**优化（用户只想要最后那个词）；节流 / rAF 是**执行频率**优化（高频事件哪怕轻处理也会积少成多）
  - 滚动里读布局用 rAF 优于节流——与渲染帧对齐，不会在帧中间读出强制布局
- 细节
  - 防抖 leading 版（立即执行 + 冷却）用于按钮防重复提交
  - 节流 leading + trailing 结合：首次立刻执行、周期末补最后一次（不丢结尾状态）
  - scroll 监听加 `{ passive: true }`：声明不 preventDefault，浏览器不等 JS 就能滚
- 追问：搜索框场景防抖间隔怎么定？
  - 按用户输入节奏（常 300~500ms）+ 请求可取消（AbortController 取旧请求）组合，纯靠加大间隔会显得迟钝

### 4. 什么时候使用 Web Worker？有什么限制？适合处理哪些任务？

**结论：「输入小、算得久」的任务上 Worker——加解密 / 压缩 / 像素处理 / 大数组统计；边界是 postMessage 的结构化克隆在主线程同步执行，数据本身大时克隆先吃掉收益。**

| 维度 | 适合 | 不适合 |
| --- | --- | --- |
| 数据形态 | 输入几 KB、计算重 | 输入几十 MB——克隆成本线性增长 |
| 通信模式 | 一次消息换一次完整计算 | 高频小消息往返（每条都克隆） |
| 典型任务 | 加解密、压缩、图片像素、diff、大数组聚合 | 操作 DOM、需要 window / document |

- 实测对照（10000 条聚合）：同步 75ms / 最长任务 61ms；切片 0；Worker 主线程 9ms、最长任务 0
- 两个工程要点
  - 大数据用 `Transferable`（ArrayBuffer 转移所有权零拷贝）或先分片再传
  - 与切片的选择：切片共享主线程（简单、有残余开销），Worker 真并行（要起线程 + 通信成本）——计算明显超 50ms 才值得上 Worker
- 追问：Worker 里能用 fetch 吗？
  - 能——fetch / WebSocket / IndexedDB 都可用；DOM 操作与 window API 不可用（global 是 DedicatedWorkerGlobalScope）

### 5. 大数组、大数据渲染有哪些优化思路？

**结论：数据层全量、计算层离线（Worker / 分片）、渲染层窗口化（虚拟列表）——三层分开，各解决各的问题。**

| 层 | 问题 | 手段 |
| --- | --- | --- |
| 数据层 | 一次拉全量太大 | 分页 / 增量拉取；服务端 gzip |
| 计算层 | 过滤 / 聚合 / 排序阻塞主线程 | Web Worker（输入大先分片）；MessageChannel 切片 |
| 渲染层 | 几万节点 DOM 爆炸 | 虚拟列表只渲染可视区 |

- 组合拳（对应场景八.5）
  - 「后端一次返回几万条」：Worker 里建索引 → 虚拟表格渲染可视区几十行 → 本地搜索走索引
- 细节
  - 大 JSON 解析本身是长任务（`JSON.parse` 同步）——超大响应考虑流式解析或服务端拆块
  - 渲染批次：首屏渲染 20 条 + 空闲补齐，比一次性渲染 500 条的首帧快得多
- 追问：为什么不直接分页解决一切？
  - 有些业务要求全量浏览体验（报表 / 大盘）；分页是数据层方案之一，与计算 / 渲染层手段不互斥

### 6. 垃圾回收 GC 原理？V8 的垃圾回收机制？什么是内存碎片？

**结论：V8 分代回收——新生代 Scavenge（半空间复制，快但费空间），老生代标记清除 + 标记整理（三色标记、并发增量执行减少停顿）；内存碎片是标记清除留下的不连续空闲块，靠标记整理（紧凑搬移）解决。**

- 分代假设与两代策略

| 代 | 策略 | 原理 |
| --- | --- | --- |
| 新生代（存活短） | Scavenge（Cheney 半空间复制） | 存活对象复制到另一半空间，死亡即弃——快，空间利用率 50% |
| 老生代（存活久） | 标记 - 清除 / 标记 - 整理 | 从根做可达性标记，清除不可达；碎片多时整理搬移紧凑 |

- 关键机制（高级岗加分点）
  - 晋升：新生代对象经历两次 Scavenge 仍存活 → 晋升老生代
  - **停顿问题与 Orinoco 优化**：标记阶段全停顿太贵 → 三色标记（增量标记，与 JS 交替执行）+ 并发标记（辅助线程）+ 惰性清理——把大停顿拆碎
- 内存碎片
  - 标记清除只回收不搬移 → 空闲内存不连续（碎片）→ 大对象分配时「总空间够但连续块不够」
  - 标记整理把存活对象搬到一端 → 连续空间恢复（搬移有成本，只在碎片严重时触发）
- 与性能优化的关联
  - GC 停顿就是「不可控的长任务」——减少大对象频繁创建销毁、避免一次性巨量分配，直接减少 GC spike
- 追问：为什么新生代用复制而不用标记清除？
  - 新生代对象「朝生夕死」存活率极低——复制存活者（少量）比遍历清理死者（大量）更划算；空间换时间的典型取舍

## 五、框架层面（Vue / React）高频

### 1. React 中 memo、useMemo、useCallback 分别解决什么性能问题？各自误区？

**结论：三件套都是「引用稳定」工程——memo 拦组件级重渲染、useMemo 缓存计算结果、useCallback 稳定函数引用；最大误区是全员无脑包裹，比较与内存成本反而吃掉收益。**

| API | 拦截什么 | 生效前提 |
| --- | --- | --- |
| `memo(Comp)` | props 没变就不重渲染子组件 | props 的引用全稳定（对象 / 函数 props 也要稳定） |
| `useMemo(fn, deps)` | 依赖不变不重算（缓存**值**） | deps 数组正确完整 |
| `useCallback(fn, deps)` | 依赖不变不重建（缓存**函数**） | 下游组件被 memo 包裹才有意义 |

- 各自误区
  - **useMemo**：缓存占内存 + 比较依赖有成本——便宜的计算包它反而亏；依赖漏写直接产生陈旧值 bug
  - **useCallback 单独用没意义**：函数引用稳定了，但子组件没 memo 照样重渲染——它俩是配套的
  - **memo**：props 含每次新建的对象 / 函数字面量时完全失效——先修引用稳定再 memo，否则白比较
- 更根本的手段（优先于三件套）
  - **状态下沉**：把 state 放到最小的受影响组件，重渲染范围天然小——比到处 memo 更治本
  - `useTransition` / `useDeferredValue`：把非紧急更新标记为可中断，交互优先
- 追问：useMemo 的 deps 里放函数引用会怎样？
  - 函数每渲染都新建 → 依赖每次都变 → useMemo 永远重算——要么函数也 useCallback 稳定，要么依赖收敛到原始值

### 2. React 组件不必要重渲染的原因？如何排查？

**结论：三大来源——祖先状态变化沿树传播、引用类型 props 每次新建、Context 值变化全订阅者更新；用 React DevTools Profiler「Highlight updates + 火焰对比」定位。**

| 来源 | 机制 | 修法 |
| --- | --- | --- |
| 祖先重渲传播 | 父渲染 → 所有子默认跟着渲染 | memo + 稳定 props；状态下沉 |
| 引用不稳定 | props 传对象字面量 / 内联箭头函数 | useMemo / useCallback、对象构建下沉 |
| Context 滥用 | 一个值变 → 所有 useContext 的组件全更新 | Context 拆分（按消费粒度）、值 memo、状态下沉 |

- 排查工具链

| 工具 | 用法 |
| --- | --- |
| DevTools Highlight updates | 开「Highlight updates when components render」——交互后看谁闪 |
| Profiler 录制 | 录一次交互，看每组件「渲染次数 + 耗时」，直接给渲染原因 |
| 火焰图对比 | 优化前后同操作对比条宽（渲染耗时） |

- 判据（呼应一.4 排障主线）
  - 「数据没变但组件重渲一片」= 框架层问题——先查重渲染，再查执行耗时
- 追问：为什么 memo 了还是重渲染？
  - 顺着 props 摸引用链：某个对象 / 函数 props 每次新建（context 值、事件回调、map 出来的数组）——memo 是浅比较，任何一处引用变化就穿透

### 3. Vue2 和 Vue3 响应式差异带来哪些性能提升？

**结论：defineProperty → Proxy 的核心性能收益是「初始化不再递归全量劫持」——Vue3 访问到哪层才代理哪层，大对象初始化成本大幅下降；同时补齐数组与动态属性的响应式缺口。**

| 维度 | Vue2（defineProperty） | Vue3（Proxy） |
| --- | --- | --- |
| 初始化 | 递归遍历**全部**属性劫持 | 惰性——访问到哪层代理哪层 |
| 新增 / 删除属性 | 检测不到，要 `$set` / `$delete` | 原生拦截 set / delete |
| 数组 | 重写七个变异方法 | 原生拦截索引与 length |
| 运行时开销 | getter/setter 常驻每次访问 | 代理层拦截 |

- 性能视角的三个提升
  - **初始化快**：大数据对象不再全量递归——树形数据「用到哪层才转哪层」
  - **不用 $set**：数组直接 `arr[i] = x` 响应，少一层 API 心智与调用
  - **配合编译优化**：静态提升 + Patch Flag 让 diff 跳过静态内容只比动态标记——这是 Vue3 模板比手写 vdom 快的主因
- 追问：Proxy 代理为什么不能「完全无感」？
  - 仍需响应式系统在 get 收集、set 触发——只是拦截面更全（含新增 / 删除 / 数组）；深层大数组的高频操作仍有代理成本，可用 `shallowRef` 绕过

### 4. Vue 中 v-once、v-memo 的作用与使用场景？

**结论：都是「跳过更新」的编译优化——v-once 只渲染一次永不更新（纯静态），v-memo 按依赖数组缓存子树（依赖不变跳过整个 diff）。**

| 指令 | 语义 | 场景 |
| --- | --- | --- |
| `v-once` | 首次渲染后视为静态，后续永不更新 | 纯静态内容（版权 / 说明文案） |
| `v-memo="[dep1, dep2]"` | 依赖数组不变 → 复用缓存 vnode，**跳过整棵子树 diff** | 长列表中「大部分列不变的行」 |

- v-memo 的典型用法（长列表）

```html
<div v-for="item in list" :key="item.id" v-memo="[item.selected, item.text]">
  <!-- 只有 selected 或 text 变了这一行才 diff；其他列怎么变都跳过 -->
</div>
```

- 配套（Vue3 编译优化全家桶，体现体系）
  - 静态提升：静态节点提到 render 外只创建一次
  - Patch Flag：编译期给动态节点打标记，diff 只比标记部分
  - Cache Handler：事件处理缓存，避免每次渲染新建（React useCallback 问题的编译期解）
- 追问：v-memo 依赖漏了会怎样？
  - 该更新的子树不更新，显示陈旧值——v-memo 是拿「正确性风险」换性能，依赖数组要精确列全影响该子树的变量

### 5. keep-alive 的原理？使用 keep-alive 会带来哪些内存问题？

**结论：keep-alive 把组件实例（vnode + 状态 + DOM）缓存在 Map 里按 LRU 管理，切换时移出文档但实例常驻——代价是缓存实例的监听 / 定时器 / DOM 全部活着，缓存本身可能成为泄漏源。**

- 原理要点
  - 缓存 key = 组件名（或自定义 key）；命中缓存直接取实例挂回，不走 created / mounted
  - LRU 淘汰：`max` 超限时淘汰最久未使用的实例
  - 生命周期钩子 `activated` / `deactivated` 处理「回来 / 离开」
- 内存问题（必答）

| 问题 | 说明 | 解法 |
| --- | --- | --- |
| 实例常驻 | 缓存组件占内存且不参与 GC | `max` 设上限，防全量缓存 |
| 副作用活着 | 定时器 / 全局监听在缓存期间仍运行 | deactivated 里暂停、activated 恢复 |
| 缓存雪球 | 动态路由组件 key 不同各缓存一份 | 统一 key 策略、include 白名单 |

- 追问：keep-alive 和路由懒加载冲突吗？
  - 不冲突——懒加载管「首次加载拉不拉 chunk」，keep-alive 管「二次进入重不重渲」；被 keep 的实例常驻，更要配合 max 与 include 控制范围

### 6. 框架项目中如何避免大量 watch 侦听带来的性能损耗？

**结论：三个损耗源——deep 深遍历、监听大对象、回调里的重操作；方向是「能用 computed 不用 watch、精确监听、控制触发频率」。**

| 损耗 | 原因 | 解法 |
| --- | --- | --- |
| deep 遍历 | 深层对象每个属性都建依赖 | 监听具体字段 `() => obj.key`；shallowRef 承接大结构 |
| 触发过频 | 输入 / 滚动驱动的 watch 连发 | 防抖 / 节流 |
| 回调重操作 | watch 里做聚合 / 请求 | 抽 computed 缓存派生值；请求加 AbortController 取旧 |
| 多 watch 串联 | A 变改 B、B 变改 C 链式放大 | 收敛为单一数据源 + computed 派生 |

- 通用纪律
  - **watch 是副作用工具，computed 是派生值**——把「算」从 watch 挪到 computed，watch 里只剩「做」
  - 大列表场景优先 computed + v-memo 组合（见五.4），而不是每个字段一个 watch
- 追问：watchEffect 和 watch 的取舍？
  - watchEffect 自动收集依赖、立即执行——适合「依赖多但关系简单」；watch 显式依赖、能拿新旧值——适合条件触发；性能上 watchEffect 要注意回调里读了多少依赖（读越多触发面越广）

## 六、构建工程化优化（Vite / Webpack）

### 1. Webpack 构建层面有哪些性能优化（构建速度 + 产物体积）？

**结论：构建速度靠「缩小处理范围 + 缓存 + 并行」，产物体积靠「分割 + 摇树 + 压缩」——两条线的手段不同，答题要分开列。**

- 构建速度

| 手段 | 说明 |
| --- | --- |
| 持久化缓存 | `cache: { type: 'filesystem' }`——二次构建命中缓存跳过编译 |
| 缩小处理范围 | loader 的 `include/exclude`、`resolve.extensions` 精简、alias 减少解析 |
| 跳过解析 | `noParse` 对确定无依赖的大库不解析 |
| 并行 | thread-loader / esbuild-loader 替代 babel-loader（esbuild 转译快一个量级） |

- 产物体积

| 手段 | 说明 |
| --- | --- |
| 分割 | splitChunks（见六.5）+ 路由级动态 import |
| 摇树 | 见二.8 三硬规则 |
| 压缩 | terser / esbuild minify；`drop_console`（保留 console.error） |
| 传输压缩 | 构建期预压缩 gz / br（见二.3） |
| 按需 | 组件库子路径引入、polyfill 按 browserslist、moment→dayjs |

- 追问：DLL 还推荐吗？
  - 不推荐——filesystem cache 稳定后 DLL 收益被覆盖，且有依赖版本不同步的维护坑；老项目遗留可说明「用 cache 替代」

### 2. Vite 和 Webpack 原理差异？为什么 Vite 开发环境启动更快？生产打包还有差异吗？

**结论：dev 快的根源是「按需编译 vs 全量打包」——Webpack 必须先把整个依赖图打成 bundle 才能起服务，Vite 起静态服务器按请求即时编译单个模块（esbuild 预构建依赖）；生产两者都是全量构建（Vite 用 Rollup），启动快的优势在生产不存在。**

| 维度 | Webpack | Vite |
| --- | --- | --- |
| dev 原理 | 全量打包出 bundle 后才能访问 | 原生 ESM 按请求编译（项目多大启动都快） |
| 依赖预构建 | 无此概念 | esbuild 把 CJS 依赖预转 ESM + 合并小模块 |
| HMR | 重编译涉及的热更新块 | 精确到单模块失效重编，速度与项目大小解耦 |
| 生产构建 | 自己打包 | Rollup 打包 |

- 为什么 dev 快（三个层面）
  - 起服务不等打包：页面用到哪个模块才编译哪个
  - esbuild（Go 编写）预构建依赖比 JS 工具链快一个量级以上
  - HMR 粒度到单模块，改一个文件只重编一个
- 生产的真实差异
  - dev 快 ≠ prod 快——生产都是全量打包；Vite 生产走 Rollup，产物粒度与 tree-shaking 行为与 Webpack 有差异但量级相当
  - 选型本质：dev 体验（Vite 赢）vs 生态深度（Webpack 微前端 / 特殊 loader 更全）——编译原理与插件机制的深挖在 Vite 篇展开
- 追问：为什么依赖要预构建而不直接用？
  - node_modules 里大量 CJS 与零散小模块——浏览器 ESM 下几百个请求会把 dev 页面拖死；预构建把依赖转 ESM + 合并成一个文件

### 3. Bundle 分析工具如何使用？怎么定位大包？

**结论：可视化看「体积都花在哪」——bundle-analyzer / visualizer 出 treemap，按「最大块 / 重复依赖 / 没摇掉 / 该拆没拆」四问法逐项排查。**

- 工具与用法

| 工具 | 场景 |
| --- | --- |
| `webpack-bundle-analyzer` | Webpack 产物 treemap（方块面积 = 体积） |
| `rollup-plugin-visualizer` | Vite / Rollup 同类 |
| `source-map-explorer` | 基于 sourcemap 精确到源码行 |
| DevTools Coverage | 运行时视角——加载了多少、执行了多少 |

- 定位套路（四问法）

| 问题 | 信号 | 处理 |
| --- | --- | --- |
| 谁最大 | treemap 大方块 | 大库换轻库（moment→dayjs）、重组件懒加载 |
| 重复依赖 | 同一库多版本并存 | `npm ls` 找来源，resolutions 收敛 |
| 没摇掉 | 用了一个函数整包都在 | 查 ESM / 副作用声明 / 引入方式（见二.8） |
| 该拆没拆 | 多页面混一个 bundle | 路由分割 + splitChunks |

- 追问：Coverage 和 analyzer 的视角差在哪？
  - analyzer 看「打包了什么」（静态）；Coverage 看「执行了什么」（运行时）——打包进了但没执行的，正是懒加载 / 按需的候选

### 4. 按需引入的原理？如何避免全量引入大型 UI 库？

**结论：按需引入的本质是把「选择权交回静态分析」——子路径引入让打包器只见被引用的模块；三层级：入口级（路由懒加载）→ 模块级（import() 进函数体）→ 依赖级（子路径 / 换轻库）。**

| 层级 | 手段 | 例子 |
| --- | --- | --- |
| 入口级 | 路由懒加载 | `component: () => import(...)` |
| 模块级 | 动态 import 进函数体 | 点「导出」才拉导出库 |
| 依赖级 | 子路径引入 / 换轻库 / polyfill 按环境 | `import { Button } from 'ant-design-vue/es'`、moment→dayjs |

- 避免全量引入的清单
  - 禁止 `import Antd from 'antd'` 全量默认导入——全量导入 + 副作用声明缺失时 tree-shaking 救不回来
  - 选 ESM + `sideEffects` 声明良好的库（现代 UI 库直接子路径引入即可，无需 babel 插件）
  - 样式按需：unplugin 类工具自动按组件引样式
- 追问：为什么有的库需要 babel-plugin-import，有的不用？
  - 不用插件的库：包本身 ESM 且子路径可直达（`es/button`）；需要插件的：老库入口 CJS / 无子路径结构，靠插件编译期改写引入路径——本质都是「缩小打包器看到的范围」

### 5. 为什么要拆包（splitChunks）？拆包策略怎么设计？

**结论：拆包两个目的——利用长缓存（vendor 变动少，业务发版不失效）与公共依赖去重；策略按「变动频率分桶」：framework（几乎不变）/ vendor（低频）/ 业务公共（中频）/ 按路由（高频）。**

- 为什么拆（两句话答透）
  - 不拆：改一行业务代码整包 hash 变，用户重新下载全部
  - 拆后：业务 chunk 变，vendor 命中缓存——**二次访问传输归零的前提是「变动频率不同的代码不混在一个 chunk」**
- 策略设计（Webpack splitChunks 示意）

```js
splitChunks: {
  chunks: 'all',
  cacheGroups: {
    framework: { test: /[\\/]node_modules[\\/](vue|react|react-dom)[\\/]/, name: 'framework', priority: 20 },
    vendor:    { test: /[\\/]node_modules[\\/]/, name: 'vendor', priority: 10 },
    common:    { minChunks: 2, name: 'common', reuseExistingChunk: true }
  }
}
```

| 设计要点 | 说明 |
| --- | --- |
| 按变动频率分桶 | 变动越少缓存越久——framework 最高优先单独拆 |
| minChunks / minSize | 防拆太细：共用 2 次以上、体积达标才值得独立 chunk |
| maxAsyncRequests | 异步并发上限——拆太细导致请求碎片化 |
| 异步 chunk | 路由 chunk 天然独立，splitChunks 主要管「公共依赖去重」 |

- Vite 侧对应 `manualChunks` 同思路（按 node_modules 分桶）
- 追问：拆太细有什么坏处？
  - 请求碎片化（H2 下小 chunk 往返仍有成本）+ 每个文件独立 gzip 压缩率下降（字典上下文变小）——拆到「变动频率不同」的粒度即可，不是越细越好

## 七、性能采集、监控与排查

### 1. 如何采集页面性能指标？Performance、PerformanceObserver API

**结论：两范式——同步快照（`getEntriesByType` 拉）与异步订阅（`PerformanceObserver` 推）；快照管导航耗时，Observer 管动态指标（LCP/CLS/长任务），注册带 `buffered: true` 补收。**

| 范式 | API | 适用 |
| --- | --- | --- |
| 快照（拉） | `performance.getEntriesByType('navigation' / 'resource' / 'paint')` | DNS / TTFB / 资源耗时（加载时已写完） |
| 订阅（推） | `new PerformanceObserver(cb).observe({ type, buffered: true })` | LCP / CLS / longtask / event（异步产生、越晚越准） |
| 手动打点 | `performance.mark` + `measure` | 业务自定义区间（SPA 路由切换耗时） |

- 采集三原则（RUM 必然设计）
  - `buffered: true`：补收注册前的条目（SDK 晚加载否则 FCP 恒 0）
  - `visibilitychange → hidden` 定稿：LCP / CLS 越晚越准，hidden 才是上报时机
  - 不支持的 entry 类型 try/catch 静默跳过
- 上报与 SDK 设计（采样 / 攒批 / sendBeacon）属监控篇专题，此处不展开
- 追问：SPA 的路由切换耗时怎么测？
  - 原生 navigation 指标只管首屏——路由开始 `mark`、数据返回与渲染完成再 `mark`，`measure` 出区间；框架路由钩子是天然打点位

### 2. Chrome DevTools 性能面板怎么使用？如何定位页面卡顿、长任务？

**结论：Performance 录制看「主线程火焰图 + 瀑布图 + 帧率条」三联动——长任务看火焰图顶部长条、卡顿看掉帧、归因点开看色块与调用栈。**

- 面板三层结构（自上而下）

| 区域 | 看什么 |
| --- | --- |
| 帧率条 + 交互标记 | 掉帧段、点击 / 输入的 delay 标记 |
| 主线程火焰图 | 长任务（红色三角）、Task 内函数耗时、Layout / Paint 色块 |
| 瀑布图（Network） | 阻塞资源、优先级、依赖链 |

- 定位流程（可复述）

```
1. 录制：Record → 复现操作 → Stop
2. 找长任务：火焰图顶部 >50ms 的长条（红色三角标记）
3. 下钻归因：点开长任务看调用栈——业务函数？样式重算？GC？
4. 看瀑布：主线程被占的同时网络在干嘛（资源竞争）
5. Bottom-Up 视图：按「自身耗时」排序找热点函数
```

- 配套面板分工
  - Network：粗定位时间花在哪个资源；Coverage：下了没执行的代码
  - Memory：越用越卡类问题
  - Rendering：Layout Shift Regions 可视化 CLS 区域、Paint flashing 看重绘范围
- 追问：火焰图里怎么区分「JS 的锅」和「渲染的锅」？
  - 长任务内色块——黄色 Scripting / 紫色 Rendering（Layout）/ 绿色 Painting；Layout 密集 → 强制同步布局或节点太多；Scripting 密集 → 下钻函数

### 3. 线上环境怎么做性能监控？上报哪些指标？

**结论：RUM 采集核心三指标 + 辅助刻度 + 业务自定义指标，按 p75 看分布；上报走批量 + sendBeacon，采样按数据量分层。**

| 类别 | 指标 |
| --- | --- |
| 核心 | LCP、INP、CLS（带 p75 视角） |
| 辅助 | TTFB、FCP、TBT、长任务次数与明细（Top N） |
| 自定义 | SPA 路由切换耗时、关键模块渲染耗时（mark/measure） |
| 上下文 | 版本（release）、机型、网络类型、地域、路由 |

- 采集与上报要点（简版，SDK 细节见监控篇）
  - 性能指标全量或高比例（分位值要样本）；行为数据采样；hidden 时收口上报（LCP / CLS 定稿）；CLS 存双口径（规范 `cls` + 全量 `clsRaw`）
- 分析侧
  - 按 release / 机型 / 网络 / 路由分桶看 p75——全局均值掩盖分桶差异
- 追问：为什么上报要带 release 版本？
  - 没有版本维度的性能曲线没有意义——新版本发布后的劣化要能定位到版本，优化验证也挂版本

### 4. 如何区分开发环境性能问题和线上真实用户性能（RUM）？

**结论：Lab 可控可复现但代表不了真实用户（你的开发机不是用户），Field 反映真实分布但只有数字没有细节——现场发现问题、实验室定位根因，改完回现场验证。**

| 维度 | Lab（DevTools / Lighthouse） | Field / RUM |
| --- | --- | --- |
| 环境 | 固定机型 / 网络，可限速复现 | 真实机型 / 弱网 / 地域 |
| 输出 | 火焰图、瀑布、函数级根因 | 分布（p75）、分桶差异 |
| 局限 | 单次运行、不代表用户 | 无细节，只有聚合 |
| 分工 | 定位根因、回归对比 | 发现问题、验证效果 |

- 典型工作流

```
RUM 报警（某版本 LCP p75 从 2.1s 涨到 3.4s）
→ 按机型 / 路由分桶，锁定低端机 + 某页面
→ Lab 限速复现同一场景，火焰图定位根因
→ 修复 → Lab 验证 → 灰度发布 → RUM 确认 p75 回落
```

- 追问：为什么 Lighthouse 分数只能当趋势不能当验收？
  - 固定权重汇总、分数随版本变、单次运行波动大——验收卡口要用确定性指标（真实 LCP / TBT 读数 + 体积预算）进 CI

### 5. 性能预算（Performance Budget）是什么？如何落地？

**结论：给关键指标与资源设红线（LCP p75 ≤2.5s、单页 JS ≤300KB），两道闸落地——CI 阶段体积与指标卡口阻断发版、线上 RUM 持续对照告警。**

| 阶段 | 闸门 | 手段 |
| --- | --- | --- |
| 上线前 | CI 卡口 | bundle 体积超预算阻断（size-limit / analyzer 断言）；Lighthouse 抽取原始 LCP / TBT 断言 |
| 上线后 | RUM 告警 | 监控按 release 算 p75，连续 N 窗口超标告警 |

- 预算维度不止耗时
  - 资源体积（JS / CSS / 图片字节数）、请求数、第三方脚本数量——体积预算 CI 就能卡
- 落地节奏
  - 预算从「现状基线」逐步收紧（每次发版紧一点），一步到位的红线执行不动
  - 分级：核心指标超标阻断、辅助指标警告
- 追问：性能预算为什么必须「两头都要」？
  - 只有 CI：真实用户环境差异（机型 / 弱网）漏网；只有 RUM：劣化已发生才发现——CI 拦增量、RUM 验存量

## 八、场景大题（口述项目题）

### 1. 你如何从 0 到 1 落地性能优化？

**结论：从 0 到 1 的正确顺序是「先建度量 → 定基线找瓶颈 → 分层治理 → 防劣化固化」——不是拿到优化清单就开改；没有度量就没有优化，第一步永远是让性能可测量、可归因、可看板。**

- 第一步：建立度量（回答「现在有多慢、慢在哪」）
  - 定指标口径：Core Web Vitals 三件套（LCP / INP / CLS）为主，TTFB / FCP / TBT 为辅；看 **p75 不看均值**（长尾用户会拉高均值失真，p75 更贴近真实体验，也是 Search Console 的口径）
  - 双视角落地：
    - **Lab（Lighthouse / DevTools）**：可复现、可定位段，但受网络与机器影响，只作辅助不当验收卡口
    - **Field（RUM）**：PerformanceObserver + 监控 SDK 上报真实用户数据——优化效果的最终裁判
  - 产出物：一张性能看板（按页面、机型、网络分桶聚合），把「感觉慢」变成可见数字
- 第二步：定基线、找瓶颈、排优先级（回答「先修什么」）
  - 用 RUM 数据分桶归因（release / 机型 / 网络 / 页面路由）找共性瓶颈
  - 按排障主线把瓶颈映射到层：TTFB 高 → 网络层；加载时长长 → 资源体积；长任务多 / 强制布局 → 运行时
  - **按 ROI 排序**：影响用户量 × 修复收益 ÷ 改动成本——先做「大收益低成本」（缓存、压缩、CDN），再做工程量大的（SSR、重构）
- 第三步：分层治理（每项按「发现 X → 做 Y → 得到 Z」口述）

| 层 | 典型手段 | 特点 |
| --- | --- | --- |
| 网络层 | CDN、内容 hash 强缓存、brotli/gzip、HTTP/2 | 零/低代码成本，收益立竿见影 |
| 资源层 | 路由分割+空闲预取、tree-shaking、图片格式与懒加载、关键 CSS | 首屏字节直接决定加载段 |
| 运行时 | 长任务切片、读写分离、防抖节流、虚拟列表 | 治交互卡顿 |
| 感知层 | 骨架屏、SSR | 不改变真实就绪时间，改善主观感受 |

  - 分段归因纪律：分包降多少、缓存降多少分开说，不把功劳混进一个数字（与下一题的收益复盘衔接）
- 第四步：防劣化固化（从 0 到 1 最重要的收尾——否则优化完三个月又长回来）
  - CI 卡口：bundle 体积预算、构建产物体积 diff 超标即拦
  - 线上告警：RUM p75 环比劣化告警、白屏率 P0 告警
  - 规范固化：code review checklist（首屏图不许 lazy、新增依赖过体积预算）
- 成果量化：同口径 p75 前后对比 + 业务指标（跳出率 / 转化率）——落地汇报最终要用业务语言
- 追问：从 0 到 1 最难的是哪一步？
  - 不是技术是**推动**：性能没有业务需求背书，排不进迭代优先级。解法有三：用数据说话（慢页面的转化率对比）、借势（把性能目标挂到业务大促 / 核心页面上）、小步快跑（先做两周见效的快赢项建立信任，再要资源做大的）
- 追问：业务快速迭代和性能优化冲突怎么办？
  - 把优化做进**基建**而不是一次性运动——SDK、CI 卡口、脚手架默认配置，让后续业务「天然不慢」；新页面按性能预算验收

### 2. 项目里做过哪些前端性能优化？整体思路与指标收益？

**结论（按「背景定位 → 分层施策 → 数字收益 → 防回退」四段口述）：定位先行、分层下手，收益用同一口径的改前改后对比说话。**

- 参考叙事骨架（数字换成自己项目的量级）

```
定位：首页 FCP 3.2s / LCP 4.2s（RUM p75），Network 看到单 bundle 3MB、CSS 全阻塞、主图 800KB
施策：
  构建层——路由分割 + 空闲预取、tree-shaking 修复、vendor 按变动频率分桶
  资源层——关键 CSS 内联 + 全量异步、主图 WebP + fetchpriority + 写死尺寸
  缓存——内容 hash + 一年强缓存，HTML no-cache
  感知层——骨架屏（结构对齐真实内容）
收益（同口径 p75 对比）：
  首屏 JS 3MB → 800KB；FCP 3.2s → 1.5s；LCP 4.2s → 2.1s；二次访问 JS 传输归零
防回退：CI 体积预算 + RUM p75 告警
```

- 表述纪律
  - 每项手段对应一个「发现的问题」——不是清单轰炸，是「因为发现 X 所以做 Y 得到 Z」
  - 分段归因：分包降了多少、缓存降了多少，别把所有功劳混进一个数字
- 追问：哪项收益最大？
  - 一般是缓存（零代码成本、二次访问归零）与路由分割（首屏字节减半）——但要能说出自己项目里 ROI 的排序依据

### 2. 线上 LCP 指标很差，你排查的完整思路？

**结论：先分桶找共性，再按 LCP 四段构成下钻定位段，最后落到具体资源——「TTFB → 加载延迟 → 加载时长 → 元素渲染延迟」每段对应一层手段。**

- 第一步：分桶（RUM 数据）

| 分桶 | 能发现 |
| --- | --- |
| release | 某版本发版后劣化 → 回滚比对 |
| 机型 / 浏览器 | 低端机问题 → 渲染方向 |
| 地域 / 网络 | 弱网区域 → CDN / 体积方向 |
| 页面路由 | 单页问题 → 页面级排查 |

- 第二步：四段拆解

| 段长 | 归属 | 手段 |
| --- | --- | --- |
| TTFB 高 | 网络层 | CDN、缓存、preconnect |
| 加载延迟长 | 资源发现晚 | preload / fetchpriority、别 lazy 首屏图 |
| 加载时长长 | 体积 | WebP/AVIF、srcset、压缩 |
| 渲染延迟长 | 感知层 | 关键 CSS 内联、defer、SSR |

- 第三步：定位到资源
  - `entry.element` 找 LCP 元素（图还是文本——图走资源方向，文本走渲染方向）
  - 该资源的 `resource` entry 拆 DNS / TCP / 传输；看是否被 preload、是否被 lazy
  - LCP 时点前后的长任务 → 主线程阻塞推后渲染
- 验证：改后同口径 p75 环比 + Lighthouse 单次读数辅助
- 追问：骨架屏为什么可能让 LCP「假绿」？
  - 骨架屏本身是 LCP 候选且很早渲染——LCP 变好但用户还没看到真实内容；必须另配「真实内容渲染完成」自定义指标

### 4. 页面交互卡顿，怎么一步步定位是 JS、渲染还是网络问题？

**结论：卡顿以主线程问题为主（网络慢表现为「转圈」而非卡顿）——Performance 火焰图三步走：找长任务、看色块归因（Scripting / Rendering / Painting）、按归因下钻。**

- 定位决策树

```
卡顿发生时录 Performance：
1. 火焰图有没有长任务（>50ms）？
   有 → 看色块：Scripting 多 → JS 执行（下钻函数：算法？大循环？）
              Layout 多 → 强制同步布局 / DOM 太多（读写分离 / 虚拟列表）
   没有 → 看帧率条与 GC spike：GC 频繁 → 内存压力（大对象频繁创建）
2. 长任务出现在什么交互后？（点击回调里 → 事件处理太重）
3. 伴随网络瀑布拥堵吗？（弱网下「卡」可能是等响应——表现应是 loading 而非掉帧）
```

- 三类问题各自的解法方向

| 归因 | 解法 |
| --- | --- |
| JS 执行 | 切片（MessageChannel）/ Worker / 算法 |
| 渲染 | 读写分离、transform 动画、虚拟列表、content-visibility |
| 网络 | 缓存、压缩、预加载、请求合并（这是「慢」不是「卡」） |

- 追问：用户说「卡」但火焰图没长任务，还查什么？
  - 内存（越用越卡 → 泄漏，看 GC 频率与堆曲线）、合成失败的动画被拉回主线程、设备过热降频（低端机长时间高负载后整体变慢）

### 5. 首屏白屏有哪些原因？排查步骤？

**结论：白屏 = HTML 到达到有内容之间的真空——沿「网络（TTFB）→ 关键资源（CSS/JS 阻塞）→ 渲染入口（SPA 空壳等 JS）→ 运行时错误（JS 挂了）」四段排查。**

| 段 | 常见原因 | 排查 / 手段 |
| --- | --- | --- |
| 网络 | TTFB 高、重定向链长、CDN 缓存旧版 HTML | 看 Network 的 HTML 行；CDN 缓存策略 |
| 关键资源 | CSS / 同步 JS 阻塞 | 瀑布图看阻塞段；关键 CSS 内联、defer |
| 渲染入口 | SPA 空壳等 JS 拉接口后才渲染 | 骨架屏、SSR、首屏数据内联 |
| 运行时错误 | JS 报错导致渲染中断 | 错误监控（白屏率 P0 告警）；本地看 Console 复现 |

- SPA 特殊问题
  - 空壳 index.html + JS 渲染 = 白屏天然偏长——首屏数据内联（HTML 带初始数据）省「渲染 → 请求 → 响应 → 再渲染」一整轮
  - 白屏还要可观测：白屏检测（采样点 / DOM 节点数）+ 白屏率告警（见监控篇）
- 追问：白屏和骨架屏的关系？
  - 骨架屏把「白」变「有结构」，是感知层手段——不改变真实内容就绪时间；且骨架有坑（成为 LCP 候选、结构不一致引发 CLS）

### 6. 项目打包产物体积过大，你如何定位并优化？

**结论：analyzer treemap 定位「大在哪」+ Coverage 看执行率「用了多少」，按四问法逐项处理，最后 CI 体积预算防回退。**

- 定位

```
1. bundle-analyzer / visualizer 看 treemap：大方块是谁
2. npm ls 找重复依赖（同一库多版本）
3. Coverage：加载字节 vs 执行字节——使用率低的 = 懒加载 / 按需候选
4. 查引入方式：全量默认导入？CJS 混入？
```

- 优化对号入座

| 发现 | 手段 |
| --- | --- |
| 大库（moment / lodash 全量） | 换轻库 / 子路径按需 |
| 重组件（图表 / 编辑器） | 动态 import 懒加载 |
| 多页面混装 | 路由分割 + 空闲预取成对 |
| 没摇掉 | 修 ESM / 副作用声明 / 引入写法 |
| polyfill 全量 | browserslist 按目标环境 |

- 收尾：体积预算进 CI，防止「优化完三个月又长回来」
- 追问：优化后体积降了但 LCP 没动，为什么？
  - 印证纪律：改的那段不在 LCP 构成里（可能砍的是首屏后的 chunk）——回排障主线看 TTFB / 资源延迟哪段才是瓶颈

### 7. 移动端页面性能相比 PC 有哪些额外难点？针对性优化手段？

**结论：四个额外难点——算力弱（执行 / 渲染慢几倍）、内存小（易回收与崩溃）、网络不稳（弱网高延迟）、能耗敏感——核心思路是降级分档，不是照搬 PC 清单。**

| 难点 | 表现 | 针对手段 |
| --- | --- | --- |
| 算力弱 | JS 解析执行慢、长任务更常见 | 包更小、动画全合成属性、减少重渲染 |
| 内存小 | 页面被杀 / 频繁 GC | 缓存设上限、虚拟列表、避免大 JSON 驻留 |
| 网络不稳 | 高延迟 / 断续 | 激进懒加载、LQIP 占位、请求超时重试、首屏数据内联 |
| 能耗 | 持续动画 / 轮询耗电 | 页面不可见暂停动画与轮询（visibilitychange） |

- 分档降级
  - 按 `navigator.connection.effectiveType` + `deviceMemory` 分档：低端机给简化版（砍动画 / 降图质 / 少功能）
  - 分桶验证：低端机分桶的 LCP / INP p75 单独对比，别混进整体均值
- 移动端特有注意
  - 触屏无 hover 缓冲，100ms 交互反馈更要紧；软键盘弹起引发视口变化是 CLS 来源；bfcache 场景更多（pageshow 恢复状态）
- 追问：为什么移动端不能照搬 PC 的优化方案？
  - PC 优化的边际收益集中在网络，移动端瓶颈常在算力与内存——先测再改，移动端火焰图里 Layout / 长任务占比通常远高于 PC

## 九、手写代码题

### 1. 手写防抖函数

**结论：核心是「每次触发清掉上一个定时器」；加 leading 立即执行版本与取消能力是进阶点。**

```js
function debounce(fn, wait, { leading = false } = {}) {
  let timer = null
  function debounced(...args) {
    if (timer) clearTimeout(timer)
    const callNow = leading && !timer // leading：冷却期内首次立即执行
    timer = setTimeout(() => {
      timer = null
      if (!leading) fn.apply(this, args)
    }, wait)
    if (callNow) fn.apply(this, args)
  }
  debounced.cancel = () => { clearTimeout(timer); timer = null } // 取消
  return debounced
}
```

- 要点清单
  - `this` 与参数透传（`apply(this, args)`）
  - `timer` 挂闭包外（多次调用共享状态）
  - cancel 的用途：组件卸载时清理，防闭包拖住引用（呼应内存泄漏）
- 追问：leading 模式下「冷却期内再次触发」会怎样？
  - 只清定时器不执行——leading 语义是「一段时间内只认第一次」，按钮防重复提交靠这个

### 2. 手写节流函数

**结论：时间戳版保证「首触立即执行」，定时器版保证「收尾必补一次」；两者结合是完整版。**

```js
function throttle(fn, wait) {
  let last = 0, timer = null
  return function (...args) {
    const now = Date.now()
    const remain = wait - (now - last)
    if (remain <= 0) {
      // 时间戳版：周期起点立即执行
      if (timer) { clearTimeout(timer); timer = null }
      last = now
      fn.apply(this, args)
    } else if (!timer) {
      // 定时器版：周期末尾补执行最后一次
      timer = setTimeout(() => {
        timer = null
        last = Date.now()
        fn.apply(this, args)
      }, remain)
    }
  }
}
```

- 要点清单
  - 纯时间戳版：首次立即、结尾丢失；纯定时器版：首次延迟、结尾保真——组合版两者兼得
  - scroll 场景常配 `{ passive: true }` 监听
- 追问：节流和 rAF 合帧怎么选？
  - 处理里读布局 → rAF（与渲染对齐避免强制布局）；纯频率控制（上报 / 拖拽计算）→ throttle

### 3. 手写图片懒加载（IntersectionObserver 版本）

**结论：观察带 `data-src` 的图，进入视口换 `src` 并 `unobserve`（只报一次）；不支持时降级全量加载。**

```js
function lazyLoadImages() {
  const imgs = document.querySelectorAll('img[data-src]')
  if (!('IntersectionObserver' in window)) {
    imgs.forEach((img) => { img.src = img.dataset.src }) // 降级
    return
  }
  const io = new IntersectionObserver((entries) => {
    for (const entry of entries) {
      if (!entry.isIntersecting) continue
      const img = entry.target
      img.src = img.dataset.src          // 真实地址进 src 触发加载
      img.removeAttribute('data-src')
      io.unobserve(img)                  // 只加载一次
    }
  }, { rootMargin: '200px' })            // 提前 200px 预加载
  imgs.forEach((img) => io.observe(img))
}
```

- 要点清单
  - `data-src` 存真实地址（不写 src 防浏览器立即加载）
  - `unobserve` 防重复触发；`rootMargin` 控制提前量
  - `<img loading="lazy">` 是原生免 JS 版本（约 1250px 预加载距离）——两者择一，别叠加
- 追问：为什么不用 scroll + getBoundingClientRect？
  - 每次滚动同步读布局正是强制同步布局来源；IO 交给浏览器异步判定，且首屏内的图注册即回调（不漏）

### 4. 利用 PerformanceObserver 监听 LCP

**结论：订阅 `largest-contentful-paint` + `buffered: true` 补收，每次取 entries 最后一个为当前值，hidden 时定稿上报。**

```js
let lcp = 0
try {
  const ob = new PerformanceObserver((list) => {
    const entries = list.getEntries()
    const last = entries[entries.length - 1] // 持续报告新的最大元素，取最新
    if (last) lcp = last.startTime
  })
  ob.observe({ type: 'largest-contentful-paint', buffered: true })
} catch { /* 老浏览器不支持，静默跳过 */ }

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    report({ type: 'perf', name: 'lcp', value: Math.round(lcp) }) // hidden 定稿
  }
})
```

- 要点清单
  - 取 entries 最后一个（不是第一个）——LCP 候选持续更新
  - `buffered: true` 补收注册前条目（SDK 晚加载不丢早期值）
  - hidden 定稿：用户交互 / 转后台后浏览器不再报告，此时值即最终值
  - try/catch 包裹注册（老浏览器不支持该 entryType）
- 追问：LCP 候选什么时候停止更新？
  - 用户首次真实交互（点击 / 按键）或页面转后台——之后 DOM 变化不再产生新候选

## 十、SSR / SSG 性能相关拓展

### 1. SSR、SSG、CSR 三者在首屏性能上的差异？

**结论：CSR 首屏最慢（等 JS 全链路），SSG 首屏最快（静态 HTML 秒出），SSR 居中（实时渲染有 TTFB 开销）——选型按「内容变化频率 + 交互复杂度 + SEO 需求」。**

| 方案 | 首屏路径 | 首屏速度 | 适用 |
| --- | --- | --- | --- |
| CSR | HTML 空壳 → 拉 JS → 执行 → 渲染 | 最慢 | 重交互后台 / 工具 |
| SSG | 构建期生成静态 HTML 直出 | 最快（CDN 秒出） | 内容不常变（文档 / 博客 / 落地页） |
| SSR | 服务端实时渲染 HTML 直出 → hydration | 快（含服务端渲染的 TTFB 开销） | 内容个性化 / 实时（电商 / 社区） |

- 关键细节
  - SSG 的 HTML 是「死」的——有交互仍需 hydration
  - SSR 的 TTFB 含服务端渲染耗时——SSR 不是「免网络成本」，是把渲染成本从前端挪到服务端
  - LCP 元素不同：CSR 的 LCP 是 JS 渲染出来的内容；SSR / SSG 的 LCP 可早到 TTFB 附近（HTML 里就有内容）
- 追问：SSR 一定比 CSR 首屏快吗？
  - 不一定——SSR 的 TTFB 变长（服务端渲染 + 可能查库），高负载下服务端排队反而更慢；SSR 的快是「首屏可见早」，可交互还要看 hydration

### 2. SSR 的水合（hydration）是什么？水合的性能开销与优化？

**结论：水合 = 客户端 JS 把事件监听与状态「接」到 SSR 输出的静态 HTML 上让它变成可交互应用；开销在于整页 JS 都要下载并执行一遍才能交互——hydration 期「看得见点不动」（TTI 晚于 LCP）。**

- 开销拆解

| 开销 | 说明 |
| --- | --- |
| 下载 | 整页组件的 JS 都要拉（哪怕用户只看首屏） |
| 执行 | hydration 在主线程重建组件树 + 挂事件——CPU 密集的长任务 |
| 双重渲染 | 服务端渲染一次 + 客户端再「走一遍」对账 |

- 优化方向

| 手段 | 思路 |
| --- | --- |
| 代码分割 | 非首屏组件的 JS 不进首包，交互到才水合对应部分 |
| 渐进式水合 | 按优先级分批水合（首屏交互区先来） |
| 选择性水合 | React 18：按用户实际交互的区块优先水合 |
| 岛屿架构 | 静态部分根本不水合（见下题） |
| Resumability | Qwik：服务端序列化状态，客户端「恢复」而非「重放」执行 |

- 追问：为什么 SSR 页面「看得见但点不动」？
  - HTML 已直出（可见），但事件监听要等 hydration 完成——hydration 是主线程长任务，期间输入排队；这是 SSR 页面 INP 的常见坑

### 3. 什么是选择性水合、岛屿架构（Island）？

**结论：两者都在解决「水合太重」——选择性水合（React 18）按用户交互动态决定水合顺序（服务端流式发送 + 客户端按需接管）；岛屿架构（Astro）把页面拆成「静态 HTML 主体 + 交互小组件岛」，岛外零 JS。**

| 方案 | 思路 | 收益 |
| --- | --- | --- |
| 选择性水合 | 服务端流式推 HTML；hydration 不按顺序，谁被点击优先水合谁 | 交互响应不被「排队等水合」阻塞 |
| 岛屿架构 | 页面默认纯静态 HTML；每个交互区块（轮播 / 表单）是独立「岛」，各自独立水合 | 静态内容零 JS；岛之间互不拖累 |
| Resumability（Qwik，顺带） | 服务端把状态与监听关系序列化，客户端跳过重放直接恢复 | 几乎零水合成本 |

- 岛屿的适用边界
  - 内容为主 + 局部交互（新闻 / 博客 / 营销页）收益最大；全局高交互应用（编辑器 / 后台）岛屿切不干净，还是 CSR / SSR 合理
- 追问：岛屿之间需要共享状态怎么办？
  - 岛屿隔离是特点也是限制——跨岛状态要走全局存储（localStorage / URL / 全局事件）；状态重的应用选岛屿架构前先画交互边界
