# 面试题 · 性能优化

## 从0到1如何做性能优化？
- 完整步骤
  - 建立基线，确定指标：用真实用户数据，按大盘、网络、设配分组等维度确认现状核心指标，确定目标指标
  - 定位瓶颈：按照不达标的网络、设备等分组维度，通过实验室工具（性能面板、网络瀑布、Lighthouse ）等工具定位瓶颈，如网络瀑布显示首屏加载了全量js
  - 分层落地优化：根据定位到的瓶颈，按加载顺序逐层排查确定优化方案
  - 灰度验证上线
  - 常态化监控：接入性能告警、增加性能门禁、CR check list

- 排查链路：用lighthouse给初步方向，主要用performance 看网络、主线程、长任务、LCP等
- 分层落地手段
  - 网络层 ｜目标：降低往返延迟、提升传输效率
    - 静态资源接入 CDN
    - HTML no-cache 配置协商缓存；带hash长缓存
    - preconnect / dns-prefetch 预连接域名，提前加载关键资源：preload
    - 使用 HTTP2 / HTTP3
  - 资源层｜目标：调度资源优先级，让关键资源更快抵达
    - 减少产物体积：Tree Shaking、组件库按需加载
    - 只加载必要资源：路由懒加载、组件异步加载、图片懒加载
    - 第三方包单独分包
  - 渲染 / 运行时｜目标：降低渲染开销，稳定布局，控制 CLS
    - 框架-vue
      - 状态下沉：将状态放到使用它的最小组件，缩小变更影响范围，避免顶层状态连带大量无关组件重渲染
      - v-memo：缓存模板子树，依赖不变跳过 diff
      - v-once：静态内容只渲染一次
      - `shallowRef / shallowReactive`：大型数据关闭深层响应，降低代理开销
      - 收敛 watch：精确监听字段，避免不必要 deep，及时销毁 watch
      -  使用 `computed` 缓存昂贵派生计算
      -  Props 精简、保持引用稳定，不传递完整大对象
      -  动静组件拆分，隔离高频更新区域
    -  长列表使用虚拟列表
    -  稳定布局、低成本动画
       -  动画只用 `transform`、`opacity`，走合成层
       -  动态内容提前预留容器尺寸，防止 CLS
  - 交互层｜目标：保护主线程，保证 INP，响应及时
    -  优化长任务：长任务使用 MessageChannel 切片、密集计算使用 web worker
    -  防抖、节流
    -  `requestIdleCallback` 延迟挂载非关键组件
    -   及时清理定时器、请求订阅、事件监听，避免内存泄漏
  - 数据 / 页面请求层｜目标：避免数据阻塞关键渲染路径  
    - 消除/减少串行等待
    - 接口去除、缓存
    - 限制并发数量

## 性能指标有哪些？
- 核心指标
  - LCP 最大内容绘制，≤ 2.5s ≤ 4.0s > 4.0s
  - INP 交互到下一次绘制，200ms ≤ 500ms> 500ms
  - CLS 累积布局偏移，≤ 0.1 ≤ 0.25 > 0.25
- 辅助指标
  - TTFB: 首字节时间
  - FCP：首次内容绘制时间
  - 长任务：50ms

## 加载性能怎么优化？（LCP 为主）
- 定位瓶颈：按照 LCP = TTFB + 加载延迟 + 加载时长 + 渲染延迟 的四段归因，定位瓶颈段
- 进行分层优化手段：网络 → 资源 → 数据 → 感知
  - 网络层 
    - 静态资源接入 CDN
    - HTML no-cache 配置协商缓存；带hash长缓存
    - preconnect / dns-prefetch 预连接域名，提前加载关键资源：preload
    - 使用 HTTP2 / HTTP3
  - 资源层
    - 减少产物体积：Tree Shaking、组件库按需加载
    - 只加载必要资源：路由懒加载、组件异步加载、图片懒加载
    - 第三方包单独分包
  - 数据层
    - 消除/减少串行等待
    - 接口去除重复、缓存
    - 限制并发数量
  - 感知：接入骨架屏

## 交互性能怎么优化？（INP 为主）

- 定位瓶颈：INP 差 = 主线程被占住、输入排不上队，定位靠 Performance 火焰图找长任务。

- 原理：主线程跑 JS、DOM、样式布局、事件分发——串行共享一条队列，超过 50ms 的长任务期间所有输入只能等；一切运行时优化本质都是**让主线程的队列短一点**
- 分层优化
  - js 执行
    - 脚本加载：业务主包 defer（按序、DOMContentLoaded 前执行），统计 / 埋点 async（独立、下载完立刻执行）
    - 长任务切片
    - web worker 做密集计算
    - 防抖节流

  - 渲染层
    - 读写分离：先批量读完存变量，再批量写；或写放 rAF、下一帧只读一次
    - 合成动画：动画只用 transform / opacity（只走合成、不进主线程）;合理使用：`will-change` 
    - 虚拟列表

  - 框架层手段：v-momo、shallowRef绕过深层代理、computed、watch 治理


## 视觉稳定性怎么优化？（CLS）

**结论：CLS 是写法问题不是性能问题——浏览器只看元素在布局里的起始位置有没有变；黄金四类修完即可归零：尺寸预留、字体度量、动态内容插入、动画写法。**

| 来源         | 根因                             | 修法                                                                                         |
| ------------ | -------------------------------- | -------------------------------------------------------------------------------------------- |
| 尺寸未预留   | 图片 / 广位 / iframe 加载后撑开  | **在 HTML 写 width/height**（不是 CSS），浏览器自动算 aspect-ratio；广告位 `min-height` 占位 |
| 字体换字     | 回退字体度量 ≠ 正式字体          | `size-adjust` 校准回退字体 + 字体 preload                                                    |
| 动态内容插入 | 新元素插到已有内容**上方**       | 预留容器；绝不在已有内容上方插入（240px 横幅插 body 最前，一次就超 0.1）                     |
| 动画写法     | 用 top/left/margin/height 做动画 | 只用 transform / opacity——transform 是绘制后的矩阵变换，起始位置没变，CLS 不计               |

## 如何收集指标

```js
let lcp = 0
try {
  const ob = new PerformanceObserver((list) => {
    const entries = list.getEntries()
    const last = entries[entries.length - 1] // 候选持续更新，取最新
    if (last) lcp = last.startTime
  })
  ob.observe({ type: 'largest-contentful-paint', buffered: true }) // buffered 补收注册前条目
} catch { /* 老浏览器不支持，静默跳过 */ }

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    report({ type: 'perf', name: 'lcp', value: Math.round(lcp) }) // hidden 定稿上报
  }
})
```
