# 面试题 · 性能优化

> 定位：性能是高级岗「必考且必深挖」的模块。本篇只保留 7 道开放性大题——每道题串起一大块知识，适合面试口述展开，也方便自查闭环；细节用追问节点索引，顺着提纲自己扩充。
>
> 主线：**指标（题 1）→ 全链路（题 2）→ 分层治理（题 3~5，按核心指标驱动）→ 度量监控（题 6）→ 取舍保障（题 7）**。分层治理按 LCP / INP / CLS 三个核心指标组织（面试问法天然是指标形态），每个指标内部再按「层」排序给手段；手段的原理细节见「性能优化手段与落地」篇。

## 一、指标体系

### 1. 请说出现代前端核心性能指标（Web Vitals）：分别代表什么、怎么算、良好阈值、会受哪些因素影响？

**结论：核心三件套 LCP（加载）、INP（交互）、CLS（视觉稳定），评级按真实用户 p75 看；三者互不可替代——LCP 优秀但主图不预留尺寸的页面，CLS 照样爆表。**

| 指标 | 代表 | 怎么算 | 良好阈值（p75） | 受什么影响 |
| --- | --- | --- | --- | --- |
| LCP 最大内容绘制 | 加载性能——主要内容多久出来 | 最大内容元素绘制时刻；更大的元素出现就刷新候选，首次真实交互 / 转后台后定稿 | ≤ 2.5s | 大图、慢接口、大 JS、阻塞渲染的 CSS、服务端慢（TTFB） |
| INP 交互到下一次绘制 | 交互响应——点了多久有反应 | 单次交互 = 输入延迟 + 事件处理 + 下一帧绘制的总时长；页面取所有交互里最差的 | ≤ 200ms | 长任务、大量同步 JS、主线程阻塞、重渲染风暴 |
| CLS 累积布局偏移 | 视觉稳定——页面会不会自己乱跳 | 位移分数 = 影响比例 × 距离比例，会话式累加；只统计没有紧跟用户输入的意外位移 | ≤ 0.1 | 图片没宽高、动态插入 DOM、字体换字闪烁、非 transform 动画 |

- 辅助指标是「定位刻度」不是「目标」：TTFB（≤800ms，所有加载指标的上限）、FCP（≤1.8s，首次有内容可见）、TBT（≤200ms，INP 的实验室代理）
- 为什么看 p75 不看均值：性能是右偏长尾分布，均值被少数极慢用户拉高，p75 才代表 75% 用户的真实体验（也是 Search Console 的口径）
- 口径红线：**FID 已被 INP 取代**（2024-03 起剔除，FID 只测首次交互的输入延迟，后半程体验测不到）；FMP 已废弃；TTI 已淡出官方核心体系
- 追问：FCP 和 LCP 什么区别？
  - FCP 是「有东西可见」（可能只是页头文本），LCP 是「主要内容可见」（hero 图 / 大标题）；两者差值是用户「白等」的时间

## 二、全链路

### 2. 从输入 URL 到页面可交互，梳理整条链路，并说出每个阶段的优化思路

**结论：链路 = DNS → TCP/TLS → 请求资源 → HTML/CSS/JS 解析执行 → 渲染管线 → 可交互；每个阶段都能映射到一个主要指标和一组优化手段——这张表就是全篇的「链路 → 指标 → 手段」总索引。**

| # | 阶段 | 发生什么 | 主要指标 | 优化思路 |
| --- | --- | --- | --- | --- |
| 1 | DNS 解析 | 域名 → IP | TTFB | `dns-prefetch`、DNS 缓存 |
| 2 | TCP / TLS 建连 | 三次握手 + TLS 握手 | TTFB | HTTP/2 / 3、`preconnect` 预连接、会话复用 |
| 3 | 请求资源 | HTML + 子资源下载 | LCP / FCP | CDN、强缓存 / 协商缓存、brotli、preload / prefetch、资源拆分 |
| 4 | HTML 解析 | DOM 构建 | FCP | 精简 HTML、避免阻塞资源 |
| 5 | CSS 解析 | CSSOM（阻塞渲染） | FCP | 关键 CSS 内联、非首屏 CSS 异步加载 |
| 6 | JS 解析执行 | 阻塞 DOM 解析 | LCP / INP | defer / async、拆包减少首屏 JS、避免长任务 |
| 7 | 布局 → 绘制 → 合成 | 渲染管线 | INP / CLS | 减少重排重绘、动画只用 transform / opacity |
| 8 | 可交互 | 脚本执行完、事件就绪 | INP | hydration 优化、交互绑定提前 |

- 原理主线（关键渲染路径一句话）：DOM → CSSOM → 渲染树 → 布局 → 绘制 → 合成——**CSS 阻塞渲染**（CSSOM 没齐不绘制，所以 CSS 放 head、关键 CSS 内联）、**同步 JS 阻塞解析**（所以 defer / async）
- 追问：怎么找「关键资源」是哪些？
  - DevTools Coverage：看「已用字节 / 总字节」——使用率低的资源就是不该进关键路径的
- 追问：JS 放底部和 defer 的关系？
  - 「放底部」是 defer 的老式等价物；defer 在 head 里即可并行下载、解析完按序执行，更优；`type="module"` 天然 defer 语义，`async` 用于统计 / 埋点等完全独立的脚本

## 三、分层治理 · 按指标驱动

### 3. 加载性能怎么优化？（LCP 为主）

**结论：LCP 差先按「TTFB → 加载延迟 → 加载时长 → 渲染延迟」四段归因定位瓶颈段，再按「网络 → 构建 → 资源 → 感知」的层序给手段——先做零代码成本的（缓存、压缩、CDN），再做工程量大的（SSR、重构）。**

- 第一步：四段归因（RUM / Lighthouse 拆 LCP 构成）

| 瓶颈段 | 归属 | 手段 |
| --- | --- | --- |
| TTFB 高 | 网络层 | CDN、缓存、preconnect |
| 加载延迟长（资源发现晚） | 资源层 | preload / fetchpriority、首屏图别 lazy |
| 加载时长长（体积大） | 网络 + 资源层 | WebP/AVIF、srcset、brotli |
| 渲染延迟长（被阻塞） | 构建 + 感知层 | 关键 CSS 内联、defer、SSR |

- 网络层手段
  - 缓存策略：HTML `no-cache`（每次协商保证入口新鲜）+ 带 hash 的 JS/CSS/图片一年强缓存 `immutable`——发版换 hash，二次访问传输归零
  - 压缩：静态资源构建期预压缩 brotli（比 gzip 再小 15~20%），动态响应用 gzip
  - CDN：静态资源边缘分发；`preconnect` 提前对关键第三方域（字体域 / API 域）建连
- 构建层手段
  - 路由分割 + 空闲预取**成对**：动态 `import()` 切出独立 chunk（首屏字节减半），`requestIdleCallback` 空闲预取下一跳——只分割不预取，首次切路由变卡
  - Tree-Shaking 三前提：ESM、库声明 `sideEffects: false`、访问方式静态；全量默认导入 UI 库改子路径按需引入
  - vendor 按变动频率分桶（framework / vendor / common）——变动频率不同的代码不混一个 chunk，长缓存才有效
  - 第三方脚本（统计 / 埋点）：async 加载、交互后延迟注入、facade 模式（先假封面点击才加载真实 iframe）、自托管
- 资源层手段
  - 图片四件套：格式（WebP/AVIF）、响应式（srcset 各档宽高比必须一致）、懒加载（只对首屏外的图）、优先级（首屏图 `fetchpriority="high"`）
  - 关键 CSS 内联 + 全量 CSS 异步（`media="print"` + onload 切回）；字体 preload + `font-display`
  - 红线：内联的关键 CSS 必须含首屏**布局**尺寸——只内联文字颜色，等于用 CLS 换 FCP
- 感知层手段
  - 渲染模式选型：CSR 首屏最慢（等 JS 全链路）、SSG 最快（静态 HTML CDN 秒出）、SSR 居中（含服务端渲染的 TTFB 开销）——按「内容变化频率 + 交互复杂度 + SEO」选
  - 骨架屏：把「白」变「有结构」，不改变真实内容就绪时间；骨架本身是 LCP 候选，会让 LCP「假绿」，要配「真实内容渲染完成」自定义指标
- 追问：图片懒加载为什么几乎不动 LCP？
  - 它省的是滚动路径上的带宽（实测传输 2.35MB → 1.17MB，LCP 没动）；LCP 元素在首屏内时 lazy 反而**推迟** LCP——首屏内千万别 lazy
- 追问：体积降了但 LCP 没动，为什么？
  - 改的那段不在 LCP 构成里（可能砍的是首屏后的 chunk）——回到四段归因看 TTFB / 资源延迟哪段才是瓶颈

### 4. 交互性能怎么优化？（INP 为主）

**结论：INP 差 = 主线程被占住、输入排不上队（网络慢表现为「转圈」而不是卡顿）——按「JS 执行 → 渲染 → 框架」的层序消，定位靠 Performance 火焰图找长任务。**

- 原理一句话：主线程跑 JS、DOM、样式布局、事件分发——串行共享一条队列，超过 50ms 的长任务期间所有输入只能等；一切运行时优化本质都是「让主线程的队列短一点」
- JS 执行层手段
  - 脚本加载：业务主包 defer（按序、DOMContentLoaded 前执行），统计 / 埋点 async（独立、下载完立刻执行）
  - 长任务切片：首选 `MessageChannel`（无节流的宏任务）；`setTimeout` 嵌套有 4ms 节流且优先级低，不理想
  - Web Worker：适合「输入小、算得久」的任务（加解密、压缩、大数组聚合）——边界是 postMessage 结构化克隆在主线程同步执行，输入几十 MB 时克隆先吃掉收益（大 ArrayBuffer 用 Transferable）
  - 防抖节流：高频事件（输入 / 滚动 / resize）降频
- 渲染层手段
  - 读写分离：强制同步布局（循环里「写完立刻读」`offsetWidth`）才是真杀手——先批量读完存变量，再批量写；或写放 rAF、下一帧只读一次
  - 合成动画：动画只用 transform / opacity（只走合成、不进主线程）；隐患是每层占显存——层爆炸（大量 fixed / 提层）反而变慢，`will-change` 只加给真正要动的元素、用完移除
  - 虚拟列表：只渲染可视区 + 缓冲（原理：占位元素撑总高 → scrollTop 换算起始索引 → 窗口渲染 → 节点复用），实测 10030 节点 → 108 节点
  - `content-visibility: auto`：屏幕外内容跳过渲染（长页面利器，配 `contain-intrinsic-size` 防滚动条跳动）
- 框架层手段
  - React：memo 三件套都是「引用稳定」工程——先状态下沉（state 放最小受影响组件）再 memo；memo 了还重渲染 = 某个对象 / 函数 props 每次新建，用 Profiler 顺着 props 摸引用链
  - Vue：`v-memo` 依赖数组不变跳过整棵子树 diff（长列表「大部分列不变的行」）；大结构用 `shallowRef` 绕过深层代理；watch 治理——「算」挪 computed、watch 里只剩「做」
  - keep-alive：LRU 缓存实例常驻，`max` 设上限、deactivated 里暂停定时器 / 监听
- 定位（火焰图三步）：找长任务（>50ms 长条）→ 看色块归因（黄 Scripting = JS 执行；紫 Layout = 强制同步布局 / DOM 太多）→ 下钻调用栈
- 追问：用户说「卡」但火焰图没长任务，还查什么？
  - 内存（越用越卡 → 泄漏，看 GC 频率与堆曲线）、合成失败的动画被拉回主线程、低端机降频
- 追问：TBT 和 INP 什么关系？
  - TBT 是 INP 的实验室代理（Lighthouse 给）——统计所有长任务超出 50ms 部分的总和，线下用 TBT 定位、线上用 INP 验收

### 5. 视觉稳定性怎么优化？（CLS）

**结论：CLS 是写法问题不是性能问题——浏览器只看元素在布局里的起始位置有没有变；黄金四类修完即可归零：尺寸预留、字体度量、动态内容插入、动画写法。**

| 来源 | 根因 | 修法 |
| --- | --- | --- |
| 尺寸未预留 | 图片 / 广位 / iframe 加载后撑开 | **在 HTML 写 width/height**（不是 CSS），浏览器自动算 aspect-ratio；广告位 `min-height` 占位 |
| 字体换字 | 回退字体度量 ≠ 正式字体 | `size-adjust` 校准回退字体 + 字体 preload |
| 动态内容插入 | 新元素插到已有内容**上方** | 预留容器；绝不在已有内容上方插入（240px 横幅插 body 最前，一次就超 0.1） |
| 动画写法 | 用 top/left/margin/height 做动画 | 只用 transform / opacity——transform 是绘制后的矩阵变换，起始位置没变，CLS 不计 |

- 判据：图片**还没开始下载时，位置高度就已经是对的**——实测主图不写尺寸 CLS 0.0633、写死 0.0000
- 归因工具：DevTools Rendering 面板开 Layout Shift Regions 可视化偏移区域；本地资源秒到没有位移窗口，必须限速（Slow 3G）复现
- 口径细节：交互后 500ms 内的位移算预期豁免；500ms 窗口内、影响面积 ≤5% 视口才合并为一次
- 追问：展开 / 收起面板必须改高度怎么办？
  - 高度动画走不了合成——折中：`transform: scaleY` 近似（适合图片 / 色块）、或动画只动内部容器让外部布局稳定、或确保变化落在用户交互后 500ms 内（豁免窗口）

## 四、度量与监控

### 6. 前端性能怎么采集、上报、监控？怎么定位性能瓶颈？遇到性能劣化怎么排查？

**结论：Lab（Lighthouse / DevTools）现场定位根因、Field（RUM）现场发现问题——采集用 PerformanceObserver、上报带上下文埋点、监控按 p75 分桶告警、排查沿「分桶归因 → 实验室复现 → 修复验证」闭环。**

- Lab vs RUM 分工（重点：实验室不能代表线上用户，你的开发机不是用户）

| 维度 | Lab（DevTools / Lighthouse） | Field / RUM |
| --- | --- | --- |
| 环境 | 固定机型 / 网络，可限速复现 | 真实机型 / 弱网 / 地域 |
| 输出 | 火焰图、瀑布、函数级根因 | 分布（p75）、分桶差异 |
| 分工 | 定位根因、回归对比 | 发现问题、验证效果 |

- 采集：浏览器原生 API——`PerformanceObserver` 监听 Web Vitals（web-vitals 库封装）、`longtask` 长任务；`performance.timing` 已废弃，现代方案统一 PerformanceObserver（导航信息用 `navigation` entry）
- 手写 LCP 上报（高频手写题）

```js
let lcp = 0
try {
  const ob = new PerformanceObserver((list) => {
    const entries = list.getEntries()
    const last = entries[entries.length - 1] // 候选持续更新，取最新
    if (last) lcp = last.startTime
  })
  ob.observe({ type: 'largest-contentful-paint', buffered: true }) // buffered 补收注册前条目
} catch { /* 老浏览器不支持，静默跳过 */ }

document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    report({ type: 'perf', name: 'lcp', value: Math.round(lcp) }) // hidden 定稿上报
  }
})
```

- 上报：埋点到监控平台，带上下文（release 版本、机型、网络类型、地域、路由）——没有版本号的指标没法归因劣化
- 监控：RUM 按版本 / 页面分桶看 p75，环比劣化告警；白屏率 P0 告警兜底
- 瓶颈定位与劣化排查（可复述的工作流）

```
RUM 报警（某版本 LCP p75 从 2.1s 涨到 3.4s）
→ 分桶归因：按 release / 机型 / 网络 / 页面路由找共性（低端机？弱网？单页面？）
→ Lab 限速复现同一场景：Performance 火焰图找长任务、Network 看资源大小与加载时序
→ 逐项排查：图片过大？JS 包太大？接口慢？频繁 DOM 操作？
→ 修复 → Lab 验证 → 灰度发布 → RUM 确认 p75 回落
```

- 追问：为什么 Lighthouse 分数只能当趋势不能当验收？
  - 固定权重汇总、分数随版本变、单次运行波动大——验收卡口要用确定性指标（真实 LCP / TBT 读数 + 体积预算）进 CI
- 追问：LCP 候选什么时候停止更新？
  - 用户首次真实交互（点击 / 按键）或页面转后台——之后 DOM 变化不再产生新候选

## 五、取舍与保障

### 7. 性能优化不是无限做的：谈谈取舍、收益判断，以及怎么在团队建立性能保障机制（规范、门禁、预算）？

**结论：取舍看 ROI——影响用户量 × 修复收益 ÷ 改动成本，先做「大收益低成本」的快赢项；收益判断必须同口径 p75 前后对比 + 分段归因；保障靠「预算 + 门禁 + 告警 + 规范」四件套，让「快」成为默认状态而不是一次性运动。**

- 项目叙述框架（「项目里做过哪些优化」按四段口述，数字换成自己项目的量级）

```
定位：首页 FCP 3.2s / LCP 4.2s（RUM p75），Network 看到单 bundle 3MB、CSS 全阻塞、主图 800KB
施策：构建层（路由分割+空闲预取、tree-shaking、vendor 分桶）→ 资源层（关键 CSS、主图 WebP+fetchpriority+写死尺寸）→ 缓存（hash 强缓存、HTML no-cache）→ 感知层（骨架屏）
收益：同口径 p75 对比——首屏 JS 3MB→800KB；FCP 3.2s→1.5s；LCP 4.2s→2.1s
防回退：CI 体积预算 + RUM p75 告警
```

- 表述纪律：每项手段对应一个「发现的问题」（因为发现 X 所以做 Y 得到 Z）；**分段归因**——分包降多少、缓存降多少，别把所有功劳混进一个数字；最终汇报用业务语言（跳出率 / 转化率）
- 取舍权衡（优化都有成本，别盲目追求极致指标）

| 手段 | 收益 | 成本 / 代价 |
| --- | --- | --- |
| 预加载（preload / prefetch） | 关键资源早到 | 消耗额外带宽，乱预取 = 替用户下载垃圾 |
| SSR | LCP 早、SEO 好 | 服务端渲染成本 + TTFB 开销，高负载下排队反而更慢 |
| Web Worker | 主线程解放 | 起线程 + 结构化克隆的通信开销，输入大不划算 |
| 为几十 ms 优化 | 指标好看 | 维护成本可能远超收益——对齐用户真实体验，不为刷指标而优化 |

- ROI 排序：影响用户量 × 修复收益 ÷ 改动成本——缓存（零代码成本、二次访问归零）与路由分割（首屏字节减半）通常是收益最大的快赢项；先做快赢建立信任，再要资源做 SSR / 重构
- 团队保障四件套

| 层 | 手段 | 说明 |
| --- | --- | --- |
| 性能预算 | 总量预算（单包阈值）、指标预算（p75 LCP ≤ 2.5s）、增量预算（单次 MR 产物 diff 上限） | 从基线倒推、分层给——没有基线数字的预算都是拍脑袋 |
| CI 门禁（拦进不来） | bundle 体积预算超标阻断 MR；CWV 真实读数（LCP / TBT）进 CI | Lighthouse 分数只当趋势，门禁用确定性读数 |
| 线上告警（拦不被发现） | RUM p75 按版本 / 页面分桶环比告警；白屏率 P0 告警；劣化及时回滚 | 没有告警的优化做完就失明 |
| 规范与基建（天然不慢） | code review checklist（首屏图不许 lazy、图片写死尺寸、新增依赖过体积预算）；脚手架默认配置；新页面按预算验收；性能巡检周报；评审阶段提前评估性能风险 | 把优化做进基建而不是一次性运动 |

- 追问：从 0 到 1 最难的是哪一步？
  - 不是技术是**推动**：性能没有业务需求背书，排不进迭代优先级。解法有三：用数据说话（慢页面的转化率对比）、借势（把性能目标挂到业务大促 / 核心页面上）、小步快跑（快赢项建立信任再要资源）
- 追问：业务快速迭代和性能优化冲突怎么办？
  - 把优化做进基建——SDK、CI 卡口、脚手架默认配置，让后续业务「天然不慢」，而不是每次靠人力拦
