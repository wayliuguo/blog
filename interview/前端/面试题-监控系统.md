# 面试题 · 前端监控

> 定位：监控是「稳定性 + 性能 + 埋点」三合一的工程模块，高级岗爱考「体系设计 + 原理口径 + SDK 落地」三层。全篇 9 组按「结论先行 + 表格 + 子层级」组织，答案自包含；手写题按可复述伪代码粒度给出。

## 一、基础概念

### 1. 前端监控主要采集哪些类型的数据？

**结论：三类数据——稳定性（有没有坏）、体验（快不快）、业务（用户在做什么），三类量级与口径完全不同，必须分开采集、分开定采样。**

| 视角 | 回答的问题 | 采集对象 | 关键信号 |
| --- | --- | --- | --- |
| 稳定性 | 有没有坏 | JS 错误、Promise 异常、资源加载失败、接口异常、白屏 | 错误率、资源失败数、接口成功率 |
| 体验 | 快不快 | 加载与响应指标、长任务 | TTFB / FP / FCP / LCP / CLS / INP、>50ms 长任务 |
| 业务 | 用户在做什么 | 页面访问与行为 | PV / UV、停留时长、点击、转化漏斗 |

- 为什么必须分三类
  - 错误量小但必须**全量**（漏一条偶发崩溃可能就是线上事故）
  - 行为数据量最大，必须**采样**（全量上报监控自己就把带宽吃掉）
  - 性能指标要**足够样本才稳**（分位值 P75 在小样本上跳动很大）
- 监控闭环（不只"报个错"）
  - 目标设定与数据采集 → 传输与存储处理 → 分析与可视化 → 告警预警与定位优化
  - 前端 SDK 只负责「采集—上报」这一段，存储 / 看板 / 告警是服务端范畴

### 2. 前端可观测性一般包含哪几块？

**结论：三根支柱——Metrics（指标）、Logs（日志）、Traces（链路），前端监控是可观测性在浏览器侧的落地。**

| 支柱 | 回答的问题 | 前端对应物 |
| --- | --- | --- |
| Metrics 指标 | 系统状态怎么样 | 错误率、性能分位值（P75 LCP）、接口成功率 |
| Logs 日志 | 具体发生了什么 | 错误详情 + 用户行为轨迹 + 上下文（版本 / 设备） |
| Traces 链路 | 请求经历了什么 | 接口 TraceId、前后端链路串联（见七.6） |

- 追问：三者关系？
  - 指标发现异常（错误率突增）→ 日志还原现场（什么报错、哪个版本、什么行为触发）→ 链路定位根因（哪个接口、哪台服务）——层层下钻的关系，不是三选一

### 3. 前端监控的价值是什么？主要解决什么问题？

**结论：把「用户骂了才知道出事」变成「指标先于投诉发现、数据先于猜测定位」，同时给性能优化和业务决策提供量化依据。**

- 三个价值层次
  - **稳定性**：线上错误第一时间发现与定位，缩短故障恢复时间（MTTR）
  - **体验**：性能指标量化，优化效果可验证（改前改后对比，而不是「我感觉快了」）
  - **业务**：PV / UV / 转化漏斗，为产品决策和 A/B 实验提供数据
- 实验室数据 vs 真实用户监控（RUM）

| 维度 | Lab（Lighthouse 等） | RUM（真实用户监控） |
| --- | --- | --- |
| 环境 | 可控（固定设备 / 网络） | 不可控（真实机型 / 网络 / 地域） |
| 用途 | 回归对比、CI 卡口 | 发现真实差异（版本 / 机型 / 地域分化） |
| 局限 | 代表不了真实用户 | 样本噪声大，要靠分位值聚合 |

- 追问：为什么两者都要？
  - Lab 做**上线前卡口**（劣化直接挂 CI），RUM 做**上线后验证**（真实用户反馈）——只看 Lab 会漏掉低端机型问题，只看 RUM 缺少可控的回归基线

### 4. 什么是埋点？手动埋点、无埋点、可视化埋点各自优缺点？

**结论：埋点是把用户行为变成可分析事件的过程；三种方式按「口径准确度 vs 接入成本」取舍，实践是核心路径手动、长尾自动的组合。**

| 维度 | 手动（代码）埋点 | 无埋点（全埋点） | 可视化埋点 |
| --- | --- | --- | --- |
| 做法 | 业务代码里调 `track('事件', 参数)` | SDK 自动采集全部点击 / 曝光 | 运营后台圈选元素，配置下发 |
| 口径 | 最准、参数最全 | 覆盖全但噪声大 | 中间 |
| 成本 | 要发版才能加 / 改 | 零接入成本 | 不改代码但规则随改版失效 |
| 上报量 | 按需 | 巨大 | 按配置 |

- 组合策略（答这层是加分项）
  - 核心转化路径（下单 / 支付）用手动埋点——口径必须准、参数必须全
  - 长尾页面用无埋点兜底——看「还有哪些没覆盖」
  - 声明式埋点（`data-track` 属性 + 事件委托）是手动与无埋点的折中：业务只写属性，采集逻辑收进 SDK
- 追问：无埋点上报量巨大怎么治？
  - 只采「可交互元素」而非全部 DOM；采样率压到 10%~50%；文本截断、参数白名单

### 5. 前端监控 SDK 的设计思路，核心模块有哪些？

**结论：按「采集 / 传输 / 治理 / 生命周期」四层分工，一层只干一件事；单例 init 防重复上报，插件化让加一类采集不动其他层。**

| 层 | 职责 | 关键点 |
| --- | --- | --- |
| 采集层 | 拿原始事实：错误、性能条目、行为 | 各采集器互不感知，只认识 `emit(event)` 这个函数签名 |
| 传输层 | 采样 → 攒批 → 投递 → 重试 → 溢出丢弃 | 四个机制缺一不可（见四.4） |
| 治理层 | 采样率、脱敏、按指纹频控 | 与传输层各承担一半 |
| 生命周期 | 什么时候初始化、什么时候收口上报 | `visibilitychange → hidden` 定稿（见四.5） |

- 两个不是"设计癖"的必要设计
  - **单例**：多个团队各写一句 `init()`，每一类错误上报 N 遍，看板错误数直接乘 N——重复初始化 = 重复上报
  - **插件化**：错误采集不该知道埋点存在；加一类采集（如白屏检测）就是加一个插件，传输、重试、生命周期一行不改
- 追问：init 时机？
  - 尽早（错误监听越早挂越不漏），但重计算延迟（性能采集靠 `buffered: true` 补收注册前的条目，见三.5）

## 二、前端异常监控（高频）

### 1. 前端异常分为哪几大类？分别怎么捕获？

**结论：没有一个 API 能抓全错误，六类错误（外加 iframe 共七类）各挂各的监听，且每类各有"信息缺口"，采集器必须接受并各自兜底。**

| 类别 | 典型场景 | 捕获方式 | 信息缺口 |
| --- | --- | --- | --- |
| JS 运行时错误 | 读 `undefined` 的属性 | `window.onerror` 或 `error` 事件 | 有完整信息 |
| Promise 异常 | `await` 没 catch | `unhandledrejection` | 无 filename / lineno |
| 资源加载失败 | img / script / link 挂了 | `error` 事件 + **捕获阶段** | 不冒泡、无 message |
| 接口错误 | 后端 404 / 500 | 包裹 `fetch` / XHR，记 `!ok` | 无 message，靠 url / status |
| 网络错误 | DNS 失败、断网 | 同上，走 `catch` 分支 | 只有 `Failed to fetch` |
| 跨域脚本错误 | 第三方 CDN 脚本出错 | 同运行时，但只拿到 `Script error.` | 细节全无（见下题） |
| iframe 异常 | 嵌入页报错 | `window.onerror` **跨不了 iframe** | 需单独处理 |

- ErrorEvent 关键字段（不用背全，这五个够定位）

```
event.message    错误信息（已被浏览器加 "Uncaught TypeError: " 前缀，别自己再拼）
event.filename   出错文件 URL
event.lineno / colno  行号 / 列号
event.error      Error 对象，error.stack 才是完整调用栈
event.target     触发元素——有 tagName 就是资源错误（区分两类 error 的判据）
```

- iframe 异常的两个事实
  - 父页面的 `onerror` 收不到 iframe 内的报错（事件不跨文档边界）
  - 同源 iframe：拿到 `contentWindow` 注入同样的监听；跨域 iframe：注入不了，只能 iframe 内部自己接 SDK 后 `postMessage` 转发给父页统一上报
- 追问：为什么资源错误要捕获阶段监听？
  - `img` / `script` 的 `error` 事件**不冒泡**，默认（冒泡阶段）挂在 window 上收不到；`addEventListener('error', fn, true)` 第三个参数 `true` 让它在捕获阶段下传才能截住

### 2. Script error. 是什么错误？产生原因与解决方案？

**结论：`Script error.` 不是具体错误，是同源策略在保护——跨域脚本报错时浏览器故意不给 message / 行号 / 栈，防止把跨域页面的敏感信息漏给宿主页面。**

- 产生原因
  - 出错脚本的域与页面域不同（如 CDN 脚本），且没有满足跨域凭据条件
  - 浏览器在 `error` 事件里把细节抹成固定的 `Script error.`，信息全无
- 解决（两个条件**必须同时满足**）

| 条件 | 写在哪 | 作用 |
| --- | --- | --- |
| `<script crossorigin="anonymous">` | 引脚本的页面 | 声明"我愿意以匿名 CORS 方式加载" |
| `Access-Control-Allow-Origin` | CDN / 资源服务响应头 | 资源方同意暴露 |

- 兜底退路（CDN 加不了头时）
  - `Script error.` 连位置都没有，sourcemap 还原也用不上
  - 常见退路：关键第三方脚本自建同源（下载后挂自己域名）或服务端代理
- 追问：怎么快速验证是不是跨域问题？
  - 把脚本拉到本地同源环境跑一次——能拿到完整报错就是跨域抹除，复现不了才是错误本身偶发

### 3. window.onerror 和 window.addEventListener('error') 的区别？

**结论：能捕获的都差不多（JS 运行时错误），但 `addEventListener` 版本带捕获阶段参数——这是抓资源错误的唯一入口；`onerror` 是属性式只能挂一个，`addEventListener` 可挂多个。**

| 维度 | `window.onerror = fn` | `window.addEventListener('error', fn)` |
| --- | --- | --- |
| JS 运行时错误 | 能 | 能（默认冒泡阶段） |
| 资源加载错误 | **不能** | 能，但必须 `capture: true` |
| Promise 异常 | 不能 | 不能 |
| 挂载方式 | 属性赋值，后者覆盖前者 | 可多个监听器共存 |
| 参数形式 | `(msg, source, lineno, colno, error)` 五个散参 | `event` 对象（message / error / target 等字段） |

- `onerror` 五参的三个易错点
  - 顺序易记混：msg → source → lineno → colno → error
  - `msg` 已带浏览器前缀（`Uncaught TypeError: ...`），自己再拼前缀会重复
  - `lineno` 是整页行号（内联脚本含 HTML 部分），压缩产物上和源码对不上——最终还原靠 sourcemap
- 追问：同一个 error 事件怎么区分脚本错误和资源错误？
  - 看事件对象：有 `target.tagName`（元素）→ 资源错误；没有（target 是 window）→ 脚本错误。同一个监听里分流处理

### 4. unhandledrejection 的作用与捕获 Promise 报错的限制？

**结论：捕获「没人 catch 的 Promise 拒绝」——Promise 被拒且到下一个微任务周期仍无 catch 处理时触发；它不走 onerror，必须单独监听。**

- 基本用法

```js
window.addEventListener('unhandledrejection', (e) => {
  const reason = e.reason
  report({
    message: reason instanceof Error ? reason.message : String(reason),
    stack: reason instanceof Error ? reason.stack : '',
    type: 'promise'
  })
  // e.preventDefault() 可阻止控制台报错（一般不做，保留现场）
})
```

- 四个限制（面试考点）
  - **reason 不一定是 Error**：`Promise.reject('字符串')` / `reject(undefined)` 都合法，必须 `instanceof Error` 分支 + `String(reason)` 兜底
  - **没有 filename / lineno**：这类错误没有位置字段，`reason.stack` 是唯一线索，不能拿位置做唯一索引
  - **触发时机**：拒绝发生后、且该 Promise 到微任务周期结束仍无任何 catch 时才触发；之后有人补了 `.catch` 不会再撤回已上报的事件（部分浏览器会触发 `rejectionhandled` 可做撤销）
  - **兼容性**：老版 iOS Safari / 旧版浏览器不支持，需要 `try/catch` 包裹注册做静默降级
- 追问：`.then(onFulfilled)` 只传了成功回调，失败的 Promise 会触发吗？
  - 会——没有拒绝处理函数就算 unhandled；两个参数都传了且第二个是函数，就不触发

### 5. 如何捕获 Vue / React 框架内的组件渲染异常？

**结论：框架层各有自己的错误出口——Vue 用 `app.config.errorHandler`，React 用错误边界（Error Boundary）；但两者都只兜「框架内」错误，不能替代全局监听。**

- Vue

```js
app.config.errorHandler = (err, instance, info) => {
  report({ message: err.message, stack: err.stack, info, type: 'vue' })
}
// 组件级局部捕获：onErrorCaptured 钩子，可拦截并返回 false 阻止继续向上
```

- React

```jsx
class ErrorBoundary extends React.Component {
  state = { hasError: false }
  static getDerivedStateFromError() { return { hasError: true } }
  componentDidCatch(err, info) { report({ message: err.message, stack: err.stack, info, type: 'react' }) }
  render() { return this.state.hasError ? this.props.fallback : this.props.children }
}
```

- 错误边界的四个覆盖不了（必考准确性）
  - 事件处理器内的错误（渲染不到它）
  - 异步代码（setTimeout / Promise 回调）
  - 服务端渲染
  - Error Boundary 自身的 render 抛错
- 为什么不能只靠框架层
  - 框架出口只接得住「框架渲染过程」的错误；异步、裸 JS、第三方脚本的错误仍要 `onerror` / `unhandledrejection` 全局兜底——**分层拦截，全局打底**
- 追问：Vue3 的 errorHandler 能拿到什么？
  - 错误对象、触发组件实例、错误来源字符串（渲染函数 / 生命周期钩子 / watcher 等）——info 字段对定位「错在哪个阶段」很有用

### 6. SourceMap 的作用与原理？生产环境如何部署，有哪些安全风险？

**结论：sourcemap 把压缩后的位置映射回源码位置；生产环境的核心矛盾是「服务端还原要用它，浏览器不能公开它」——CI 上传 + 服务端还原 + 不随产物发布。**

- 作用
  - 生产栈是 `at n (app.a1b2c3.js:1:48213)` 这种压缩形式，人读不了；没有 sourcemap 等于拿到报错也定位不了
- 原理（一句话讲清即可）
  - map 文件里的 `mappings` 字段用 **VLQ 编码**记录「生成后位置 → 源文件 → 源码位置」的映射表；还原就是拿行列号查表 + 反解码
- 生产部署四条约定

| 约定 | 做法 | 防什么 |
| --- | --- | --- |
| CI 上传 | 构建后用 CLI 把 map 上传到监控平台，**上传后删本地** | map 留在构建机被顺手发布 |
| 不随产物发布 | Vite 用 `sourcemap: 'hidden'`（生成但不写 `//# sourceMappingURL` 注释） | 浏览器 DevTools 直接拉到 map 看源码 |
| release 绑定 | map 与代码用同一版本号（如 git sha）绑定上传 | 还原到错误版本的 map |
| 服务端还原 | 监控服务端收到压缩栈后查 map 还原 | 客户端还原体积大且要下发 map（等于公开） |

- 安全风险本质
  - map = 源码。公开部署等于把源码、注释、内部路径全部交出去；泄露渠道一般是「忘记关 sourcemap」「上传到公共 CDN 目录」
- 追问：为什么服务端还原优于客户端还原？
  - 客户端还原要把 map 下发到用户侧（体积大 + 泄露）；服务端还原只需上报压缩栈，map 永不出内网

### 7. 如何捕获接口请求错误？fetch 和 axios 的异常捕获有什么区别？

**结论：包裹请求层做两分法——`!res.ok` 记 HTTP 逻辑错误、`catch` 分支记网络错误；核心区别在 reject 语义：fetch 只有网络失败才 reject，axios 默认非 2xx 就 reject。**

- 包裹 fetch（两分法 + 必须重抛）

```js
async function request(url, options) {
  let res
  try {
    res = await fetch(url, options)
  } catch (err) {
    report({ type: 'network', url, message: err.message }) // 根本没到服务端：DNS/断网/CORS
    throw err                                              // 上报后必须 throw，否则吞掉业务异常
  }
  if (!res.ok) {
    report({ type: 'http', url, status: res.status })      // 到了服务端但 4xx/5xx
  }
  return res
}
```

- fetch vs axios 差异

| 维度 | fetch | axios（默认配置） |
| --- | --- | --- |
| 4xx / 5xx | **不 reject**，正常 resolve，要手动判 `res.ok` | reject，走 `catch` / 拦截器 onRejected |
| 网络失败 | reject（`Failed to fetch`） | reject |
| 超时 | 原生不内置（用 AbortController 手动） | 内置 `timeout` 配置，超时 reject |
| 统一处理点 | 自己包裹 | 响应拦截器统一接 |

- axios 侧的采集点
  - 响应拦截器 `onRejected`：拿到 `error.response`（有响应，逻辑错）/ 没有 `error.response`（网络错）——判断字段正好对应两分法
- 看板实践
  - `network-error` 找运维 / 网关（根本没到服务端），`http-error` 找对应服务端或前端（状态码说话）——两类分开，避免互相甩锅
- 追问：为什么 catch 上报后必须重新 throw？
  - 上报是副作用，吞掉异常会让业务 catch 以为成功，引发更深的 undefined 错误——监控不能改变业务语义

### 8. 如何区分用户侧报错和开发代码报错？

**结论：本质是「报错归属划分」——用 filename + sourcemap 定位到具体代码（业务包 / 第三方包），用版本号与环境维度区分用户环境问题还是代码缺陷，浏览器插件注入的报错要显式排除。**

- 三层归属判断

| 来源 | 识别方式 | 处理 |
| --- | --- | --- |
| 业务代码 | filename 命中自家域名 / bundle 命名 | 正常跟进 |
| 第三方脚本 | filename 是外域（CDN / 统计脚本） | 多为 `Script error.`，能还原才跟进 |
| 浏览器插件注入 | 报错脚本既不在自家产物清单、也不是已知第三方（如 `chrome-extension://`） | **直接丢弃**，这类"错误率"不是你的问题 |

- 用户侧 vs 代码侧的区分维度
  - **代码缺陷**：同一指纹集中在某版本（release 分桶）、跨设备跨地域稳定复现
  - **用户环境问题**：集中在特定机型 / 浏览器版本 / 网络类型（兼容性 / 弱网），换环境即消失
  - 所以错误上报必须带 release、UA、网络类型的上下文，没有维度就分不了
- 追问：怎么把插件报错挡在统计之外？
  - 维护「合法脚本清单」（构建产物清单 + 白名单），error 的 filename 不在清单内且前缀是扩展协议就丢弃；这也是为什么看板要按 filename 分组而不是只看总量

## 三、Web 性能指标（核心必考）

### 1. 解释 FP、FCP、LCP、CLS、INP 这几个核心指标

**结论：FCP / LCP 管「快不快」，CLS 管「稳不稳」，INP 管「跟不跟手」；FP 已少单独用，FMP 已废弃。**

| 指标 | 全称 | 含义 | 良好阈值 |
| --- | --- | --- | --- |
| FP | First Paint | 首次绘制（哪怕只是背景色） | — |
| FCP | First Contentful Paint | 首次内容绘制（文本 / 图片等真实内容） | ≤ 1.8s |
| LCP | Largest Contentful Paint | 最大内容元素渲染完成 | ≤ 2.5s |
| CLS | Cumulative Layout Shift | 累计布局偏移（无输入引起的位移之和） | ≤ 0.1 |
| INP | Interaction to Next Paint | 交互响应性（全交互取较差分位） | ≤ 200ms |

- 记忆锚点
  - FCP 是「有东西可见」，LCP 是「主要内容可见」——两者差值就是用户"白等"的时间
  - CLS 是**分值不是秒**：位移面积占比 × 移动距离占比，累加
- 口径红线（2026 年现状）
  - **FID 已被 INP 取代**（2024-03 起 Core Web Vitals 剔除 FID），答 FID 必须带这句
  - **FMP 已废弃**（Chrome 明确 deprecated），被 LCP 替代——老资料还在教 FMP，答出来要标注
- 追问：为什么 FMP 被废弃？
  - FMP 依赖浏览器猜"什么算有意义内容"，算法不稳定且易被小图干扰；LCP 用"最大元素"这个确定性规则替代

### 2. LCP 的定义？哪些元素算 LCP 元素？LCP 差怎么排查优化？

**结论：LCP 是视口内最大内容元素的渲染时间；候选是明确的四类元素，优化按「资源早到 → 提高优先级 → 少延迟渲染」三方向。**

- 四类候选元素
  - `<img>`（含 `<svg>` 内的 image）
  - `<video>` 的封面帧
  - 带 URL 的背景图（CSS `background-image`）
  - 块级元素内的文本节点（含行内子元素）
- 停止更新时机
  - 一次用户真实交互（点击 / 按键）或页面转后台后，浏览器不再报告新的 LCP 候选——**越晚越准，必须在页面隐藏时定稿**（见四.5）
- LCP 差的三方向排查

| 方向 | 常见原因 | 手段 |
| --- | --- | --- |
| 资源晚到 | LCP 图片 / 字体晚请求 | 预加载 `<link rel="preload">`、优先级提升、压缩 |
| 渲染被阻塞 | 阻塞 JS / CSS | 拆分关键 CSS、脚本 defer / async |
| 服务端慢 | TTFB 高 | 缓存、CDN、服务端渲染 |

- 追问：怎么找到当前页面的 LCP 元素？
  - `PerformanceObserver` 回调里 `entry.element` 直接给出 DOM 节点；排查工具用 Lighthouse 的诊断面板也能看

### 3. CLS 是什么？什么导致布局偏移？如何降低？

**结论：CLS 累计「没有紧跟用户输入的布局位移」；根因几乎都是「内容插入时没给占位」，优化就是给一切异步内容预留尺寸。**

- 会导致偏移的典型场景
  - 无尺寸的图片 / 广告位 / 嵌入 iframe 加载后撑开
  - 动态插入内容（横幅 / 推荐流）插到已有内容上方
  - web 字体加载后与回退字体度量不同（FOUT）
  - 骨架屏与真实内容尺寸不一致
- 优化清单

| 场景 | 手段 |
| --- | --- |
| 图片 / 视频 | 写死 `width` / `height` 或 `aspect-ratio` |
| 广告 / 嵌入位 | 预留固定占位容器 |
| 动态横幅 | 不插进文档流顶部，用覆盖层或预留槽位 |
| 字体 | `font-display: optional` 或度量兼容的回退字体 |
| 动画 | 用 `transform`（不触发重排）而不是 top / left |

- 口径细节（自研采集易错）
  - 规范只累加 `hadRecentInput === false` 的位移（用户点击导致的重排是预期内的）
  - 位移在 500ms 窗口内、影响面积不超过 5% 视口高度才合并为一次 shift
  - 工程上建议 **双口径**：`cls`（规范口径，对外可比）与 `clsRaw`（全量累加，排查用）都存
- 追问：为什么用户输入引起的偏移不计入？
  - 用户点了按钮内容跳走是「预期交互结果」，计入会把产品责任算到技术上——但排查时看 `clsRaw` 仍能发现"点击后横幅顶下去"这种体验问题

### 4. INP 是什么？和旧的 FID 有什么区别？

**结论：INP 衡量「所有交互」从输入到下一次渲染绘制的完整延迟，取页面生命周期内较差的分位；FID 只测「首次交互」的输入处理延迟。**

| 维度 | FID（已淘汰） | INP（现行） |
| --- | --- | --- |
| 统计范围 | 仅**首次**交互 | **所有**交互 |
| 测量终点 | 输入处理开始（事件处理函数开始跑） | 事件处理完成 + **渲染出下一帧** |
| 聚合方式 | 单次值 | 按交互分组取较差分位（P75） |
| 替代时间 | — | 2024-03 起正式取代 FID 进入 Core Web Vitals |

- 为什么 FID 不够用
  - FID 只回答"输入事件有没有被立即处理"，不包含事件处理函数执行时长和渲染——处理函数卡 2s 的页面 FID 照样好看
- 采集要点
  - **必须按交互分组**：不能对所有 `event` 条目的 `duration` 取平均——同一交互会派生多个事件（pointerdown / pointerup / click）
  - 真实生产建议直接接官方 `web-vitals` 库，自己算分位很容易算错
- 优化方向
  - 拆长任务（`scheduler.yield` / 分片）、减少事件处理中的同步布局（读写分离）、大列表虚拟化
- 追问：INP 怎么定「一次交互」？
  - 按交互 ID 分组：同一逻辑交互的多个事件归为一组，取该组最大 duration 与渲染时延——这也是为什么不能简单平均

### 5. 如何采集这些性能指标？用什么 API？

**结论：两范式——「同步快照拉」用 `getEntriesByType`，「异步订阅推」用 `PerformanceObserver`；注册必须带 `buffered: true`，否则 SDK 晚加载时 FCP 恒为 0。**

| 范式 | API | 适用指标 | 原因 |
| --- | --- | --- | --- |
| 快照（拉） | `performance.getEntriesByType('navigation' / 'resource' / 'paint')` | DNS / TTFB / 资源耗时 | 加载时就写完的记录，随时可读 |
| 订阅（推） | `PerformanceObserver` | LCP / CLS / 长任务 / event | 异步产生、越晚越准，轮询会采到半截值 |

- PerformanceObserver 标准四步

```js
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    report(entry) // 只累加、不上报（上报放 flush，见六.2）
  }
})
observer.observe({ type: 'largest-contentful-paint', buffered: true })
// buffered: true —— 把注册之前已经发生的条目补发回来（RUM 的三个必然设计之一）
```

- RUM 的三个必然设计

| 现实约束 | 对应设计 | 解决什么 |
| --- | --- | --- |
| SDK 可能跑了一半才加载 | `buffered: true` | 否则 FCP / LCP 早期值全丢 |
| LCP / CLS 越晚越准 | `visibilitychange → hidden` 定稿 | 否则报中途值、低估 |
| 老浏览器不支持某 entry 类型 | `try/catch` 注册、静默跳过 | 不把页面搞崩 |

- 追问：为什么 LCP / CLS 不能轮询 `getEntries()` 拿？
  - 轮询要么采到半截值（中途值被当最终值上报）、要么定时器空转浪费；Observer 是浏览器"有新值才通知"，语义正好匹配

### 6. 首屏加载完整流程，每个阶段可以采集哪些性能指标？

**结论：按 Navigation Timing 的阶段拆——redirect → DNS → TCP/SSL → TTFB → 响应 → DOM 解析 → 渲染，每段一个时间差公式；`performance.timing` 已废弃，用 `PerformanceNavigationTiming`。**

- 各阶段耗时公式（`n = performance.getEntriesByType('navigation')[0]`）

```
重定向   n.redirectEnd - n.redirectStart
DNS      n.domainLookupEnd - n.domainLookupStart
TCP      n.connectEnd - n.connectStart
SSL/TLS  n.connectEnd - n.secureConnectionStart   （https 时才有值）
TTFB     n.responseStart - n.startTime            （官方口径，含前面所有阶段）
内容传输 n.responseEnd - n.responseStart
DOM 就绪 n.domContentLoadedEventEnd - n.startTime
整页加载 n.loadEventEnd - n.startTime
```

- 公式易错点（高频挖坑）
  - **TCP 与 SSL 别记反**：SSL 是 TCP 的一部分，用 `connectEnd - secureConnectionStart`；全 TCP 就是 `connectEnd - connectStart`
  - TTFB 有两种口径：官方 `responseStart - startTime`（含重定向/DNS/TCP）；工程口径 `responseStart - requestStart`（纯请求段）——报数时说明用哪种
  - `loadEventEnd` 要在 load 之后才非 0，太早读是 0——导航类快照要延迟或监听 load 后取
- 废弃标注
  - `performance.timing` / `performance.navigation` 已废弃：精度只到毫秒整数、字段语义老化；一律用 `PerformanceNavigationTiming`（高精度浮点）
- SPA 的补充（加分项）
  - 首页能用原生 navigation 指标；**路由切换**要用自定义打点（路由开始 → 数据返回 → 关键内容渲染），否则只能评价首页
- 追问：TTFB 高说明什么？
  - 网络 + 服务端慢（含重定向、DNS、TCP）；配合 `redirect` / `dns` / `tcp` 分段值可以进一步定位是哪一段慢

### 7. 长任务（Long Task）是什么？如何采集？对页面有什么影响？

**结论：主线程上超过 50ms 的任务就是长任务，用 `PerformanceObserver` 监听 `longtask` 类型；长任务直接吃掉交互响应（INP 变差）和帧率（掉帧卡顿）。**

- 采集

```js
try {
  const ob = new PerformanceObserver((list) => {
    for (const e of list.getEntries()) {
      // e.duration 总时长；TBT 口径只累计超出 50ms 的部分
      tbt += Math.max(0, e.duration - 50)
    }
  })
  ob.observe({ type: 'longtask', buffered: true })
} catch { /* 老浏览器不支持，静默跳过 */ }
```

- 为什么门槛是 50ms
  - 交互要 100ms 内给出反馈；100ms 里还要留主线程给输入处理与渲染，任务必须 ≤50ms 才来得及
- 影响
  - INP / TBT 变差：任务阻塞期间所有输入排队
  - 掉帧：动画 / 滚动帧间隔 16.7ms，长任务让多帧合并
  - **TBT 只算超出部分**：`Σ max(0, duration - 50)`——写成"累加任务总时长"是自研采集最常见的错
- 治理
  - 拆任务（`setTimeout` 分片 / `scheduler.yield`）、重计算挪 Web Worker、大列表虚拟化、避免主线程同步大 JSON 解析
- 追问：长任务采集的采样策略？
  - 明细体积大，只报 Top N 长任务或 1%~5% 采样看趋势即可，错误与核心指标才值得全量

## 四、上报策略（SDK 工程重点）

### 1. 监控数据上报有哪些方案？各自优缺点？

**结论：三代演进——图片打点（GET、URL 受限）→ `fetch + keepalive`（兜底）→ `navigator.sendBeacon`（首选）；选择的核心变量是「页面卸载时能不能送达」和「能带多少数据」。**

| 手段 | 卸载时能否送达 | 是否阻塞 | 限制 | 定位 |
| --- | --- | --- | --- | --- |
| `new Image()` 打点 | 能（浏览器为它推迟卸载） | 否 | 只能 GET、URL 上限约 2~8KB、拿不到响应 | 上一代 |
| 同步 XHR | 能 | **阻塞卸载** | 浏览器已基本禁用 | 丢弃 |
| `fetch`（无 keepalive） | 不能，请求被取消 | 否 | — | 不适用 |
| `fetch + keepalive` | 能 | 否 | 请求体 64KB 上限 | 兜底 |
| `navigator.sendBeacon` | 能 | 否 | 无响应回调 | 首选 |

- 两个关键结论
  - **数据量的差别是代际性的**：图片打点只能把数据拼在 URL 上，数据一多就是死路；`sendBeacon` 用请求体承载
  - **`sendBeacon` 拿不到响应体**：只能回答"提交出去了没有"；确认服务端真收到要靠服务端入库计数
- 图片打点为什么当年流行
  - 无跨域限制（天然 img 免 CORS）、实现极简、体积小；但 cookie 随请求发往打点域（按目标域规则），且 URL 明文经过 access log / 浏览器历史，有泄露面
- 追问：为什么 sendBeacon 排第一、keepalive 兜底？
  - sendBeacon 语义专为"离开也要发"设计，浏览器保证不阻塞卸载；keepalive 行为接近但共享 64KB 配额且要自己处理错误——所以顺序是先 beacon、失败再 keepalive

### 2. sendBeacon 的特点、适用场景与限制？

**结论：为「页面要走了也要把数据发出去」设计的 API——异步不阻塞卸载、跨域不预检；限制是无响应回调、体积 64KB、跨域时 Content-Type 受限。**

- 特点
  - 调用立即返回 `true / false`（只代表"已交给浏览器排队"），不返回响应
  - 页面卸载 / 转后台时浏览器仍会尽力送达
  - 跨域请求**不触发预检**（设计初衷就是上报）
- 限制

| 限制 | 说明 |
| --- | --- |
| 无响应回调 | 拿不到 HTTP 状态码，重试只能靠返回 `false` 或上层机制 |
| 64KB 上限 | 单次请求体上限，超了返回 `false`——大批数据要自己分片 |
| Content-Type | 同源无限制；跨域只能用 CORS-safelisted 类型（`text/plain` 等），JSON 常以 `text/plain` 发送由服务端宽容解析 |
| 队列上限 | 浏览器对未完成的 beacon 总量有配额，超配额静默丢弃 |

- 适用场景
  - 页面卸载前的最后一批数据（性能定稿、停留时长、未上报队列）
  - 不适用：需要拿到响应确认入库的场景（改用 fetch 或依赖服务端对账）
- 追问：sendBeacon 返回 true 就一定发成功了吗？
  - 不一定——true 只表示进入队列；最终送达无回调可查，可靠性靠"服务端入库计数对账"来验收（见七.5）

### 3. 为什么监控数据不能实时逐条上报？会带来什么问题？

**结论：逐条上报把「请求数」乘出四倍以上——挤占业务请求的并发连接、浪费带宽与电量、高频序列化卡主线程，监控自己就成了性能问题。**

- 实测对照（同 12 条事件）

| 策略 | HTTP 请求数 |
| --- | --- |
| 逐条上报 | 12 |
| 攒批上报 | 3 |

- 逐条上报的四宗罪
  - **并发连接挤占**：浏览器对同域并发有上限，监控请求排队会把业务请求顶到等待
  - **带宽与电量**：每次请求的 HTTP 头开销远大于一条事件本身
  - **主线程开销**：每次 JSON.stringify + 网络初始化都在抢主线程
  - **服务端压力**：PV 十万的站点每次点击一条请求，接收端直接被打爆
- 追问：那错误也攒批吗？会不会延迟太久？
  - 分级：错误（尤其首见）可立即投递；行为 / 性能攒批 3~5 秒或攒满 N 条——延迟 3 秒对监控无感，请求数降一个量级

### 4. 合并上报、采样、节流、缓存队列分别怎么实现？

**结论：四个机制构成传输层——攒批（够 N 条或超时发）、采样（入队口丢）、节流（同指纹窗口内只报一次）、队列上限（溢出丢最旧）；采样必须在入队口做。**

| 机制 | 实现要点 | 关键参数示例 |
| --- | --- | --- |
| 合并（攒批） | 队列攒够 `batchSize` 或定时 `flushInterval` 触发一次请求 | 5 条 / 3 秒 |
| 采样 | `Math.random() >= rate` 直接拒收入队；**放入队口**而非投递口 | 错误 1、埋点 0.1~0.5 |
| 节流（频控） | 按指纹记时间戳，窗口内重复只累计 `count` 不重发 | 同一错误 3 秒一条 |
| 队列上限 | `maxQueue` 超限 `shift()` 丢最旧，记 `dropped` | 100 条 |

- 为什么采样放入口不放投递口
  - 被采样掉的数据早点消失，不在内存排队占空间；投递口才采样的话队列照样被撑爆
- 频控的键是「指纹」不是 message

```
指纹 = message + 出错位置（文件） + 行号
资源 / 接口错误没有 message —— 必须把 src / url 算进指纹
```

  - 同一函数循环调用时报错 message 一模一样，只按 message 去重会把不同出错点合并成一条；指纹才既压量又不丢信息
  - 必须带 `count` 累计（否则"每分钟 800 次"只看到一次）+ 指纹复位（如 5 分钟未再现清掉）
- 重试与溢出（配套必答）
  - 重试有上限（首投 + 2 次就放弃）——监控数据不值得无限重试，重试也耗用户带宽
  - 溢出丢最旧——留 40 条旧事件不会让看板更准，只会让页面更难跑
- 追问：攒批期间页面关了怎么办？
  - `visibilitychange → hidden` 时立即 flush 一次，投递走 sendBeacon / keepalive（见下题）

### 5. 页面卸载时如何保证监控日志成功上报？

**结论：不用 `unload`，监听 `visibilitychange → hidden`（移动端唯一可靠的"要走了"信号），在 hidden 时 flush 队列并用 sendBeacon / keepalive 投递。**

- 为什么不用 `unload`
  - 移动端浏览器为保住前进后退缓存（bfcache），**unload 经常不触发**；`pagehide` / `hidden` 才可靠
- 收口时序

```js
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    const metrics = perf.finalize()        // LCP / CLS 定稿
    emit({ type: 'perf', ...metrics })
    tracker.pageLeave()                    // 停留时长结算
    transport.flush('hidden')              // 队列 flush，内部走 sendBeacon
  }
})
```

- 指标越晚越准的原理
  - LCP / CLS 是整页生命周期内收敛的指标：滚动后的大图可能把 LCP 从 1.2s 改到 2.4s——**hidden 才是上报时机**，load 时报的是中途值
- 双保险
  - flush 内部投递顺序：先 `sendBeacon`，返回 `false` 或不可用时降级 `fetch + keepalive`
- 追问：hidden 之后用户又切回来，数据重复了吗？
  - flush 后队列已清空，不会重复；要防的是「flush 中途又入队」——flush 加个进行中标志位即可

### 6. 采样策略：全量、百分比、异常优先，适用场景？

**结论：按数据类型分层采样——错误全量、性能高比例、行为采样、长任务重度采样；「异常优先」是给出过错的会话临时提采样率的定向策略。**

| 数据类型 | 建议采样率 | 原因 |
| --- | --- | --- |
| 错误 | 100%（不采样） | 量不大，抽样会漏掉"偶发崩溃" |
| 性能指标 | 全量或高比例 | 分位值需要足够样本才稳 |
| 行为埋点 | 10%~50% | 量最大，统计口径不要求逐条准确 |
| 长任务 / 资源明细 | 1%~5% | 单条体积大，看趋势即可 |

- 异常优先采样（聪明的一层）
  - 常规会话按百分比采样；**一旦会话内出现错误 / 长任务 / 白屏，该会话打上标记并提升到 100% 采样**
  - 逻辑：异常会话的行为轨迹价值最高，正常会话的轨迹是同质化的——把配额花在刀刃上
- 采样的验证口径
  - 看板上要区分「真实现象」与「采样率变化」：改采样率必须和版本号一起标注，否则环比突降会被误判为错误率下降
- 追问：采样会不会漏掉大事故？
  - 会漏统计但能靠"结构"兜底：错误全量 + 白屏检测独立于采样 + 告警基于绝对计数（如首见指纹），不基于采样比例

### 7. 上报数据体积怎么控制？

**结论：单批体积要远小于一个业务接口响应（单条压到百字节级）——靠字段精简、栈截断、明细限流、批量压缩四板斧。**

| 手段 | 做法 |
| --- | --- |
| 字段精简 | 只上报看板真正消费的字段；UA 解析成设备类型后丢弃原始串 |
| 栈截断 | `error.stack` 只留前 N 帧（如 10 帧），重复帧去重 |
| 明细限流 | 资源 entry 全报会随资源数线性增长——只报 Top N 大文件或总量 |
| 文本截断 | 元素文本 40 字符封顶 |
| 批量压缩 | 攒批后整体 gzip（`Content-Encoding` 由网关处理）或 SDK 端 `CompressionStream` |
| 数值取整 | 耗时毫秒取整，CLS 保留 4 位小数即可 |

- 量级参考
  - 单条事件 100~150B、一批 5 条约 700B——比一张图片小两个数量级
  - 反例：一次上报带完整 DOM 快照 / 全量 UA / 所有资源列表，几十 KB 起步，监控成了新的性能瓶颈
- 追问：为什么错误对象只留栈不留引用？
  - `Error` 对象会拖着作用域链不释放（闭包引用），栈是纯字符串——留栈不留引用是内存治理的一部分

## 五、用户行为监控

### 1. 用户行为采集一般收集哪些信息？

**结论：四个层次——事件本体、身份标识、环境上下文、页面口径；重点是三个 ID 分工与会话切分，口径没定好报表一定对不上数。**

- 事件本体

| 字段 | 说明 |
| --- | --- |
| 事件类型 | 点击 / 曝光 / 路由切换 / 输入 |
| 事件元素 | 标识（如 `data-track` 值）+ 元素文本（截断） |
| 触发时间 | 时间戳 |
| 事件参数 | 额外参数（输入内容**永不采**，见五.3） |

- 身份三 ID（各管一段生命周期）

| ID | 生成与存储 | 回答的问题 |
| --- | --- | --- |
| 设备 ID | 首次访问生成，存 `localStorage` | "同一台设备" |
| 匿名 ID | 首次访问生成 | 未登录 PV / UV 去重 |
| 登录 ID | 登录后服务端下发 | 跨设备跨会话串联行为 |

- 会话与页面口径
  - **会话按 30 分钟不活跃切分**（行业惯例 25~30 分钟）：太短把"读一半吃饭"算两次，太长把"下午和晚上各来一次"算一次
  - 会话判定放**事件入口**：每次 `track` 都检查、任何事件都刷新活跃时间——"只滚动不点击"不会误判离开
  - PV 口径要先定：每次页面加载 vs 每次路由切换（SPA 里差数倍）；UV 去重键不同结果不同
  - 停留时长：离开时结算；直接关标签页会丢 `stay`，补救是 **enter / stay 双写**，接收端对"只有 enter 的会话"按超时估算
- 追问：为什么三个 ID 不合并成一个？
  - 合并后登录前的行为归不到人、登出后归不回设备；三 ID 是"设备 → 匿名 → 实名"三段连续性，登录事件把匿名 ID 与登录 ID 做关联即可串联

### 2. 如何做点击行为自动埋点（无埋点）？原理是什么？

**结论：事件委托 + 声明式属性——document 上挂一个 click 监听，从 `event.target` 向上找最近的 `data-track` 元素读取标识；一次监听覆盖全站，动态插入的 DOM 自动生效。**

- 核心实现

```js
document.addEventListener('click', (e) => {
  const el = e.target.closest('[data-track]')
  if (!el) return
  report({
    type: 'click',
    track: el.dataset.track,            // 埋点标识
    text: (el.textContent || '').trim().slice(0, 40), // 文本截断防泄露
    path: location.pathname
  })
}, { capture: true }) // capture 保证业务 stopPropagation 时也能采到
```

- 设计要点

| 要点 | 原因 |
| --- | --- |
| 事件委托挂 document | 不用给每个元素绑监听；动态 DOM 自动覆盖 |
| `closest('[data-track]')` | 点到子元素也能找到目标；找不到属性就静默返回 |
| capture 阶段监听 | 业务代码 `stopPropagation` 不会漏采 |
| 曝光与点击分开命名 | `data-track`（点击）与 `data-expose`（曝光）是两套独立标识，区分"看到了"和"点了" |

- 曝光的实现（配套考点）
  - 用 `IntersectionObserver` 而非监听 scroll：scroll 方案每次滚动同步读 `getBoundingClientRect`，正是布局抖动
  - `unobserve()` 让曝光只报一次（否则上下滚动报几十次）
  - 真实口径加**可见面积阈值（threshold）+ 持续时长阈值（≥1s）**，"一闪而过"不算曝光
- 追问：无埋点怎么区分按钮和整块卡片的点击？
  - `closest` 沿最近祖先找——点卡片内按钮命中按钮的标识，点空白区域命中卡片的标识；标识设计按「区域-元素-动作」命名即可自解释

### 3. 如何防止采集敏感信息？数据脱敏怎么做？

**结论：三条硬线全部放在采集口——URL 只留 path、元素文本截断、表单值一律不采；采集口不拦，数据出了浏览器再过滤只是心理安慰。**

- 三条硬线

| 硬线 | 做法 | 防什么 |
| --- | --- | --- |
| URL 只留 `pathname` | `url.split('?')[0]` | query 里的 token / 手机号 / 订单号 |
| 元素文本截断 | 40 字符封顶 | 长文本里夹带个人信息 |
| 表单值永不采 | `input.value` 在采集器里硬编码排除 | 密码 / 验证码 / 身份证 |

- 补充手段
  - 正则掩码：手机号（中间四位 `****`）、身份证（中间段星号）、邮箱（@ 前截断）——用于已经进参数的字段做二次兜底
  - 参数白名单：埋点参数只允许登记过的 key，未登记 key 开发环境直接告警（错在编码期发现成本几乎为零）
  - UA 只解析留必要字段，不上报完整串
- 埋点的长期事故：口径腐化
  - 两年后没人知道 `btn_v2_new` 是什么——治理四件套：埋点字典（登记标识/含义/负责人）、命名规范、上报校验、超期下线
- 追问：为什么"服务端再过滤一层"不可靠？
  - 数据一旦发出浏览器，经过网关 / 日志 / 第三方，泄露已发生；过滤只能防看板展示，防不了采集链路上的副本——所以必须源头（采集口）拦

### 4. 页面路由变化如何监听？hash 与 history 有什么区别？

**结论：hash 路由监听 `hashchange` 事件即可；history 路由的 `pushState / replaceState` **不触发任何事件**，必须重写这两个方法 + 监听 `popstate`，三件套缺一不可。**

| 路由模式 | 变化方式 | 监听手段 |
| --- | --- | --- |
| hash | 改 `location.hash` | `hashchange` 事件（原生支持） |
| history | `pushState` / `replaceState` / 浏览器前进后退 | 重写 `pushState` / `replaceState` 派发自定义事件 + `popstate` |

- history 三件套

```js
const wrap = (type) => {
  const raw = history[type]
  return function (...args) {
    const result = raw.apply(this, args)
    window.dispatchEvent(new Event(type.toLowerCase())) // 派发自定义事件
    return result
  }
}
history.pushState = wrap('pushState')
history.replaceState = wrap('replaceState')
window.addEventListener('popstate', onRouteChange) // 浏览器前进后退
window.addEventListener('pushstate', onRouteChange)
window.addEventListener('replacestate', onRouteChange)
```

- 对监控的意义
  - SPA 的 PV 靠路由监听统计——不监听路由，SPA 只有首页一条 PV
  - 路由切换也是 SPA 自定义性能打点的起点（路由开始 → 数据返回 → 渲染完成）
- 追问：框架路由（vue-router / react-router）自己有钩子，为什么 SDK 还要底层监听？
  - SDK 不应该绑框架——底层监听对所有框架通用；框架钩子留给业务侧补上下文，两层配合

## 六、SDK 架构与兼容性

### 1. 自研监控 SDK 整体分哪些模块？

**结论：四层——采集（错误/性能/埋点三个采集器）、传输（采样攒批投递重试溢出）、治理（脱敏/频控/采样率）、生命周期（init 单例 + hidden 收口）；对外只暴露 `init` + `use`（插件）+ `track`（手动上报）。**

- 模块与职责

| 模块 | 输入 | 输出 | 独立性 |
| --- | --- | --- | --- |
| errors 采集器 | `error` / `unhandledrejection` / 包裹 fetch | `emit({ type: 'error', ... })` | 不感知其他层 |
| perf 采集器 | PerformanceObserver / navigation | `emit({ type: 'perf', ... })` | 同上 |
| track 采集器 | 事件委托 / IntersectionObserver | `emit({ type: 'track', ... })` | 同上 |
| transport | 事件队列 | HTTP 请求 | 只管发 |
| index | 配置 | 单例实例 + 插件槽 | 组装与收口 |

- 关键接口约定
  - 所有采集器唯一交集是 `emit(event)` 函数签名——加一类采集就是加一个插件（`use(plugin)`），传输 / 重试 / 生命周期一行不改
  - 单例：`init` 二次调用直接返回已有实例，防重复绑监听、重复上报
- 追问：为什么治理（脱敏/频控）不单独成一层？
  - 实践中它天然分散：脱敏在采集口（事件生成时）、频控在传输入口（入队时）——强拧成一层反而要到处传上下文

### 2. SDK 如何做到低侵入、不影响主业务性能？

**结论：原则是「异步采集、热路径轻、总量受控」——用浏览器异步 API 而不是轮询，入队只做三件事，上报体积远小于业务响应。**

| 原则 | 具体做法 |
| --- | --- |
| 异步 API | `PerformanceObserver` 回调不占首屏；拒绝轮询 `getEntries()` |
| 热路径轻 | `enqueue` 只做「采样判断 + push + 判批」；序列化放 flush，不分散在采集回调里 |
| 指标只算一次 | `finalize()` 后不再重复计算，否则重复 flush 等于流量翻倍 |
| 延迟加载 | SDK 脚本 async / defer；性能采集靠 `buffered: true` 补收 |
| 体积自律 | 单条 100~150B、单批 <1KB（见四.7） |
| 错误只留栈 | 不留 Error 引用（拖着作用域链不释放） |

- 一个反例警示
  - 早期版本常见的"监控成了性能杀手"：序列化大对象太频繁、上报占满网络通道、采集回调里塞重逻辑——三条分别对应上面的热路径 / 连接 / 异步原则
- 追问：SDK 初始化时机怎么权衡？
  - 监听越早挂越不漏错（head 内同步挂监听）；重计算（UA 解析、会话初始化）延后到 idle；两者不冲突——挂监听是轻操作

### 3. SDK 本身报错怎么办？如何防止崩溃影响业务？

**结论：SDK 是寄生在业务里的代码，自己出事就是事故放大器——三层保命：全量 try/catch 静默丢弃、错误计数熔断自关、防上报死循环标志位。**

| 机制 | 做法 | 防什么 |
| --- | --- | --- |
| 全量包裹 | 所有采集回调、序列化、发送逻辑统一 try/catch，异常**静默丢弃** | SDK 异常逃逸到业务代码 |
| 熔断自关 | 内部错误计数器，连续失败超阈值自动关停整个 SDK | 无效重试反复拖累页面 |
| 防死循环标志位 | 上报期间标记"正在上报"，新错误只入队不触发新上报 | 上报失败触发异常、异常再触发上报的回环 |

- 死循环案例（能讲出来是加分项）
  - SDK 捕获错误 → 上报 → 上报请求本身出错 → 触发 error → 又上报……标志位 + 入队缓冲即可斩断
- 通道隔离（配套）
  - 上报走独立域名 / 子域（如 `monitor.example.com`），与业务主域分开——监控请求既不影响业务并发额度，也避免业务 cookie 带出
- 追问：SDK 关停后业务无感，但监控也瞎了，怎么发现？
  - 关停事件本身要上报一次（尽力而为）；服务端按应用维度监控"上报流是否断流"（见七.5）

### 4. 跨页面、多标签页场景，监控 SDK 如何处理？

**结论：核心是「会话归属」与「去重」——用 `sessionStorage`（标签页内）与 `localStorage`（跨页共享）分工存储，`BroadcastChannel` 做标签页间通信，页面级指标只由"当前可见页"上报。**

| 存储 | 生命周期 | 用途 |
| --- | --- | --- |
| 内存变量 | 页面 | 队列、频控表、指标中间值 |
| `sessionStorage` | 标签页会话 | 本标签页的会话 ID、路由计数 |
| `localStorage` | 持久 | 设备 ID、首次访问时间 |

- 多标签页的三个典型问题

| 问题 | 方案 |
| --- | --- |
| 同一会话被多个标签页重复切分 | 会话状态放 `sessionStorage`（每标签页独立但同源续接），活跃时间通过 `localStorage` 或 `BroadcastChannel` 同步刷新 |
| PV / 去重重复上报 | 页面级指标（PV、LCP）按「document 可见性」判定：`hidden` 时才算"这个页面结束了"，后台预开的新标签页不会重复 |
| 标签页间共享队列 | 队列不跨页共享（各自 flush 即可），避免共享带来的锁与竞态 |

- BroadcastChannel 的定位
  - 同源标签页间的轻量广播（如"会话 ID 刷新了""用户在别的页操作过"）；不支持的老浏览器用 `storage` 事件降级
- 追问：bfcache（前进后退缓存）恢复的页面，SDK 状态还是旧的怎么办？
  - 监听 `pageshow` 事件，`event.persisted === true` 时重置生命周期相关状态（重挂 hidden 监听、重新开批），避免恢复页面的数据流中断

### 5. 怎么采集浏览器、设备、系统、网络环境信息？

**结论：来源就三个——`navigator`（UA / 连接 / 内存）、`screen`（分辨率 / 像素比）、`performance`（网络时间）；原则是解析后只存结论，不上报原始串。**

| 信息 | 来源 | 存什么 |
| --- | --- | --- |
| 浏览器 / 系统 / 设备 | `navigator.userAgent` 解析 | 解析结果（如 `iOS 17 / Safari`），**不存原始 UA** |
| 网络类型 | `navigator.connection.effectiveType` | `4g / wifi` 等枚举 |
| 屏幕与像素比 | `screen.width/height`、`devicePixelRatio` | 分辨率分档 |
| 视口 | `innerWidth/Height` | 用于白屏检测 / LCP 归因 |
| 语言 / 时区 | `navigator.language`、时区 | 地域辅助分析 |

- 为什么不存原始 UA
  - 原始串几百字节且信息冗余；解析成结构化枚举后体积降一个量级，且看板维度聚合更直接
  - UA 逐步被冻结（ UA-CH 取代趋势），靠解析原始串的方案要有降级准备——加分点
- 追问：网络类型采集的坑？
  - `connection` 在 Safari 不支持（要 try/catch 静默）；`effectiveType` 是估算档位不是实测速率，只适合做分桶维度，别当精确值

### 6. 监控 SDK 的版本管理怎么做？

**结论：SDK 自身版本 + 业务接入的 release 版本两层都要——SDK 版本管「采集行为是否升级」，release 管「数据归属哪个业务版本」；两者都写进每条上报。**

| 层 | 标识 | 用途 |
| --- | --- | --- |
| SDK 版本 | `sdkVersion` 字段 | 采集口径变更后区分新旧数据；灰度升级出问题可定位 |
| 业务 release | 构建时注入（git sha / 包版本） | sourcemap 对齐、错误按版本分桶、性能按版本环比 |

- 实践要点
  - release 由构建工具注入（Vite `define` / 构建环境变量），运行时读取——保证和产物一一对应
  - sourcemap 上传必须与 release 匹配（见二.6），版本不匹配还原出来是错位源码
  - 数据看板所有"环比"都要以 release 为分桶前提，否则新旧版本混在一个曲线里没有意义
- 追问：SDK 升级怎么灰度？
  - 按业务方接入版本号分桶放量；SDK 的 schema 变更（字段增删）要带版本号在服务端兼容两种格式，避免升级瞬间数据断档

## 七、场景面试大题（口述项目题）

### 1. 项目中搭建前端监控体系遇到的最大难点是什么？

**结论（项目题按「难点 → 方案 → 结果」口述）：最大难点是「上报量与关键信息不丢的平衡」——全量上报监控自己就成性能与成本问题，粗暴采样又会漏掉致命异常；最终用分层采样 + 异常优先 + 绝对计数告警三层解决。**

- 难点的量化背景（先给规模感）
  - 行为事件量是错误的百倍量级；全量上报时监控请求占比肉眼可见，服务端存储成本也线性暴涨
- 三层方案

| 层 | 策略 | 保住什么 |
| --- | --- | --- |
| 分层采样 | 错误 100% / 性能全量 / 埋点 10%~50% / 长任务 1%~5% | 量大的降下来，量小的保住 |
| 异常优先 | 会话内出现错误即打标、该会话提升到 100% 采样 | 崩溃现场的完整行为轨迹 |
| 绝对计数告警 | 白屏检测、首见错误指纹不依赖采样比例 | 大事故不被采样稀释 |

- 关键代码形态（采样放入口 + 会话提标）

```js
function enqueue(event) {
  const rate = sessionFlagged ? 1 : cfg.sampleRate // 异常会话全量
  if (Math.random() >= rate) return false
  queue.push(event)
  if (queue.length > cfg.maxQueue) queue.shift()
  if (queue.length >= cfg.batchSize) flush('batch-full')
  return true
}
```

- 结果表述（带数字）
  - 上报量降约 70% 的同时，错误发现率不变（错误全量）；异常会话的排查信息反而更全了
- 追问预案：为什么白屏要独立于采样？
  - 白屏是"页面级灾难"，发生率低但影响 100% 用户；且白屏本身发生时其他采集可能也失效——独立轻量检测 + 不采样才能兜住

### 2. 线上大量 LCP 指标很差，如何通过监控定位问题？

**结论：按「先分桶定位面、再下钻定位点」两步——分桶找共性（版本/机型/地域/网络），下钻到具体资源与阶段（TTFB / 资源耗时 / 渲染阻塞）。**

- 第一步：分桶找共性

| 分桶维度 | 能发现什么 |
| --- | --- |
| release 版本 | 某版本发版后才劣化 → 回滚比对 |
| 机型 / 浏览器 | 低端机问题 → 渲染性能方向 |
| 地域 / 网络类型 | 弱网区域 → CDN / 资源体积方向 |
| 页面路由 | 单页面问题 → 页面级代码 |

- 第二步：下钻定位点
  - **LCP 元素**：`entry.element` 看是图还是文本——图走资源方向，文本走渲染方向
  - **TTFB 分段**：`responseStart - startTime` 高 → 服务端 / 网络慢；低但 LCP 仍高 → 前端资源与渲染慢
  - **资源明细**：LCP 图片的 `resource` entry 拆 DNS / TCP / 传输耗时；`initiatorType` 看有没有被 preload
  - **长任务**：LCP 时点前后的长任务 → 主线程被阻塞，渲染推后
- 与优化联动
  - 定位结论要落到可执行项：预加载 LCP 图片、defer 非关键脚本、CDN 覆盖弱网区域——优化后再用同一监控看 P75 环比验证
- 追问：为什么看 P75 而不是平均值？
  - 性能数据右偏分布（少数极慢拉高均值），P75 是官方推荐的体验线；均值会掩盖"多数人还行、少数人很惨"的分布

### 3. 线上偶发 JS 报错复现困难，监控体系如何帮助定位？

**结论：偶发错误的定位靠「上报时带全上下文 + sourcemap 还原 + 行为轨迹还原现场」三件套，把「复现」变成「读现场」。**

- 错误本身的完备性

| 字段 | 作用 |
| --- | --- |
| 指纹（message + 文件 + 行号） | 聚合同一错误、看发生频次与趋势 |
| `error.stack`（截断后） | 调用链；sourcemap 还原到源码位置 |
| release 版本 | 圈定引入版本，配合 git diff 直接看嫌疑改动 |
| 环境（机型 / 浏览器 / 网络） | 判断是兼容性问题还是逻辑问题 |

- 现场还原
  - **行为轨迹**：错误发生前 N 条用户行为（点击 / 路由 / 请求）随错误一起上报——"点了什么之后炸的"比栈更能指路
  - **异常优先采样**：出错的会话自动提为全量采集（见七.1），轨迹不缺
  - **复现步骤候选**：按轨迹里的操作序列在测试环境回放
- sourcemap 链路
  - 压缩栈 + release → 服务端查 map → 还原出文件名、行号、函数名——没有这条，偶发错误连"在哪"都不知道
- 追问：同一错误一千条上报怎么读？
  - 按指纹聚合成 issue（count + 首末次时间 + 版本分布 + 机型分布 Top3），人只看聚合后的 issue 卡片，不看原始流

### 4. 上报量太大、存储成本高，又不能丢关键异常，怎么优化？

**结论：成本与不丢是「分层」问题——按数据价值分层处理：源头分层采样、传输聚合预计算、存储冷热分离 + TTL；关键异常靠结构（全量 + 告警）保住而不是靠全量存储。**

| 层 | 手段 | 效果 |
| --- | --- | --- |
| 源头 | 分层采样 + 异常优先（见七.1） | 上报量降 70%+ |
| 传输 | 同指纹聚合上报（count + 首末次），不逐条存 | 错误存储从"次数"变"种类" |
| 处理 | 服务端预计算分位值 / 错误率，原始明细短 TTL | 看板查聚合表，明细只留 N 天 |
| 存储 | 热数据（30 天）明细库，冷数据转对象存储 / 按需回捞 | 存储单价降一个档 |

- 关键异常的"不丢"由结构保证
  - 错误 100% 采样进入聚合（种类不丢，频次有 count）
  - 白屏 / 首见错误独立告警，不依赖任何明细留存
  - 真需要原始现场时，按会话 ID 回捞（冷存储）
- 追问：聚合计数会不会丢"每次发生的细节"？
  - 会丢重复条目的独立上下文；补救是聚合时保留「首条完整 + 后续只累计」——首条现场保真，尾部只做量级统计

### 5. 如何衡量监控系统本身是否稳定可靠？

**结论：监控自己也要有 SLA——核心指标是「送达率」：服务端入库计数 vs 客户端发送计数对账；再配丢数兜底与断流检测。**

| 衡量项 | 方法 |
| --- | --- |
| 送达率 | 客户端每次 flush 带本地序号 / 批次 ID，服务端按序号统计缺口；缺口率即丢数率 |
| 采样准确性 | 上报带采样率字段，服务端按 1/rate 加权还原估算真实量 |
| 断流检测 | 按应用 + 版本监控"上报流心跳"——某版本流量归零可能不是没错误，而是 SDK 瞎了 |
| SDK 自身健康 | SDK 内部错误计数、熔断事件尽力上报一次 |

- 丢数的主要来源与对策

| 来源 | 对策 |
| --- | --- |
| 页面卸载时队列没发出去 | hidden 收口 + sendBeacon（见四.5） |
| 64KB / 配额超限 | 批次体积控制、sendBeacon 失败降级 keepalive |
| 服务端限流丢弃 | 限流要有度量，丢弃率进看板 |
| 浏览器 beacon 静默丢弃 | 对账才能发现——这也是"入库计数"存在的意义 |

- 追问：送达率多少算合格？
  - 行业常见目标 95%+（卸载场景天然有损耗）；低于阈值先查传输层再怀疑业务——先排除自己再报问题

### 6. 如何关联前端报错和后端链路 TraceId，打通前后端排查？

**结论：请求拦截器生成 / 透传 `X-Trace-Id`，前端把「最近一次请求的 traceId」附在错误上报里——从错误卡片能一键跳到后端链路。**

- 打通链路

```
用户操作 → 前端发起请求（header 带 X-Trace-Id）
        → 后端 APM 按 traceId 串联微服务调用链
        → 前端错误上报附带最近 traceId
        → 监控平台错误卡片 ↔ APM 链路页互跳
```

- 实现要点

| 点 | 做法 |
| --- | --- |
| 生成 | 前端生成 UUID 放请求头（后端未下发行时），或以后端响应头返回的为准 |
| 记录 | 包裹的请求层把 `{ url, traceId, ts }` 存入「最近请求」环形缓冲（如最近 20 条） |
| 附带 | 错误上报时把最近 3 条请求的 traceId + url 带上 |
| 后端 | APM（如 SkyWalking / OpenTelemetry）按 traceId 聚合调用链 |

- 这个关联解决的问题
  - 接口 500 导致的前端报错，从错误卡片直接看到后端哪台服务哪段代码抛的——前后端排障不再靠"你看看是不是你们的问题"互相甩锅
- 追问：接口成功但前端渲染报错，traceId 有用吗？
  - 仍有用——渲染错误前最后几条请求的数据形态（字段缺失 / 类型异常）常是根因；traceId 让你直接查到那次响应的链路日志

## 八、手写 / 实操题

### 1. 手写捕获全局 JS 错误

**结论：error 事件捕获阶段监听（同时兜住资源错误）+ onerror 分流处理。**

```js
window.addEventListener('error', (event) => {
  // 资源错误：target 是元素（不冒泡，靠捕获阶段截获）
  if (event.target && event.target.tagName) {
    const tag = event.target.tagName.toLowerCase()
    const src = event.target.src || event.target.href
    report({ type: 'resource', tag, src })
    return
  }
  // 脚本错误：ErrorEvent
  const err = event.error
  report({
    type: 'runtime',
    message: event.message,
    filename: event.filename,
    lineno: event.lineno,
    colno: event.colno,
    stack: err && err.stack
  })
}, true) // capture: true 是抓资源错误的关键
```

- 追问：为什么这里不区分 onerror 与 addEventListener？
  - addEventListener 版本是 onerror 的超集（多了资源错误 + 多监听），实际 SDK 只用它一个入口，内部按 target 分流

### 2. 手写捕获 Promise 异常

**结论：unhandledrejection 监听 + reason 类型兜底。**

```js
window.addEventListener('unhandledrejection', (event) => {
  const reason = event.reason
  report({
    type: 'promise',
    message: reason instanceof Error ? reason.message : String(reason),
    stack: reason instanceof Error ? reason.stack : '',
    // 注意：没有 filename / lineno，stack 是唯一位置线索
  })
})
```

- 追问：如何让用户补了 catch 之后撤销上报？
  - 监听 `rejectionhandled` 事件（补挂 catch 时触发），按记录的 reason 匹配到已上报条目做撤销标记

### 3. 基于 PerformanceObserver 采集 LCP

**结论：订阅 `largest-contentful-paint` + `buffered: true` 补收 + hidden 时定稿。**

```js
let lcp = 0
try {
  const ob = new PerformanceObserver((list) => {
    const entries = list.getEntries()
    // 每次回调的最后一个 entry 是当前最新的 LCP 候选
    const last = entries[entries.length - 1]
    if (last) lcp = last.startTime
  })
  ob.observe({ type: 'largest-contentful-paint', buffered: true })
} catch { /* 不支持的浏览器静默跳过 */ }

// hidden 定稿：LCP 越晚越准
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    report({ type: 'perf', name: 'lcp', value: Math.round(lcp) })
  }
})
```

- 追问：为什么取 entries 的最后一个而不是第一个？
  - 浏览器持续报告新的最大元素，每次覆盖——最后一个才是当前值；hidden 前最后一次报告即最终值

### 4. 实现批量上报队列（支持卸载补发）

**结论：队列 + 双触发条件（攒满 N 条或超时）+ hidden 收口 + sendBeacon 降级 keepalive。**

```js
function createTransport(url, { batchSize = 5, flushInterval = 3000, maxQueue = 100 } = {}) {
  let queue = []
  let timer = null

  function deliver() {
    if (!queue.length) return
    const body = JSON.stringify(queue)
    queue = [] // 先清队列再发送：失败场景靠重试机制兜底，避免重复堆积
    if (navigator.sendBeacon && navigator.sendBeacon(url, body)) return
    // 降级：keepalive 保证页面关闭后请求不被取消
    fetch(url, { method: 'POST', body, keepalive: true }).catch(() => {})
  }

  function schedule() {
    if (timer) return
    timer = setTimeout(() => { timer = null; deliver() }, flushInterval)
  }

  return {
    enqueue(event) {
      queue.push(event)
      if (queue.length > maxQueue) queue.shift() // 溢出丢最旧
      if (queue.length >= batchSize) { clearTimeout(timer); timer = null; deliver() }
      else schedule()
    },
    flush() { clearTimeout(timer); timer = null; deliver() }
  }
}

const transport = createTransport('/collect')
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') transport.flush() // 卸载补发
})
```

- 追问：flush 时 sendBeacon 和 fetch 同时挂会重复吗？
  - 不会——先 beacon 判返回值，false 才走 fetch；两个分支互斥

### 5. 实现 sendBeacon 降级方案

**结论：能力探测逐级降级——sendBeacon → fetch keepalive → 同步 img 打点（最后兜底）。**

```js
function send(url, data) {
  const body = JSON.stringify(data)
  // 1. 首选 sendBeacon
  if (typeof navigator.sendBeacon === 'function' && navigator.sendBeacon(url, body)) {
    return Promise.resolve(true)
  }
  // 2. 降级 fetch keepalive
  if (typeof fetch === 'function') {
    return fetch(url, {
      method: 'POST',
      body,
      keepalive: true,
      headers: { 'Content-Type': 'application/json' }
    }).then((res) => !!res && res.ok !== false).catch(() => false)
  }
  // 3. 最终兜底：img 打点（数据拼 URL，只适合小数据）
  return new Promise((resolve) => {
    const img = new Image()
    img.onload = img.onerror = () => resolve(true)
    img.src = url + '?d=' + encodeURIComponent(body.slice(0, 1800))
  })
}
```

- 追问：img 兜底为什么要截断到 1800 字符？
  - URL 上限约 2~8KB 且要留出 URL 本身与编码膨胀的空间；超大数据 img 兜不住，正确做法是提前分批

## 九、其他拓展

### 1. 什么是性能预算？如何通过监控落地性能预算告警？

**结论：性能预算是给关键指标设的"红线"（如 LCP P75 ≤ 2.5s、单页 JS ≤ 300KB），落地是两道闸——CI 阶段 Lab 检测阻断发版，线上 RUM 持续对照预算告警。**

| 阶段 | 闸门 | 手段 |
| --- | --- | --- |
| 上线前 | Lab 检测 | Lighthouse CI 对比预算，超标阻断合并 |
| 上线后 | RUM 告警 | 监控按 release 算 P75，连续 N 个窗口超标告警 |

- 预算的维度不止耗时
  - 资源体积（JS / CSS / 图片字节数）、请求数、第三方脚本数量——体积预算在 CI 用 bundle 分析就能卡
- 为什么两头都要
  - 只有 CI：真实用户环境差异漏网；只有 RUM：劣化已发生才发现——CI 拦增量、RUM 验存量
- 追问：预算定多少合理？
  - 从官方阈值（LCP 2.5s 等）倒推 + 现状基线逐步收紧——一步到位的预算执行不动，每次发版收紧一点是可持续的节奏

### 2. 前端告警怎么设计？哪些指标适合配置告警？如何避免告警风暴？

**结论：告警选「变化敏感 + 影响明确」的指标（白屏率、错误率、接口成功率、P75 性能），防风暴靠「指纹聚合 + 分级 + 静默 + 突变检测」。**

- 适合告警的指标

| 指标 | 告警条件示例 |
| --- | --- |
| 白屏率 | 超过基线 N 倍或绝对阈值 |
| JS 错误率 | 环比突增（如 10 分钟窗口 ×3） |
| 首见错误指纹 | 新指纹出现即告警（可能是新 bug） |
| 接口成功率 | 低于阈值（如 99%） |
| 性能 P75 | LCP / INP 连续窗口超标 |

- 告警风暴四防

| 手段 | 说明 |
| --- | --- |
| 指纹聚合 | 同一错误一千次只告一次（按 issue 不按原始条目） |
| 分级 | P0 电话 / 短信（白屏、错误率爆炸），P1 群消息，P2 日报 |
| 静默期 | 同一告警 N 分钟内不重复触发；正在处理中转"处理中"状态 |
| 突变检测 | 用环比 / 同比（避开日常波动）而不是绝对阈值拍脑袋 |

- 追问：为什么"绝对阈值"不如"突变检测"？
  - 不同页面 / 时段基线天然不同（大促流量翻倍错误数也会涨），突变检测自适应基线；绝对阈值只适合有天然上限的指标（成功率）

### 3. 页面白屏监控怎么实现？

**结论：核心是"判定页面是否白屏"——主流方案是采样点检测（取视口内若干点看是否命中有效内容）或 DOM 节点数阈值，onload 后延迟判定，按 PV 维度算白屏率。**

- 采样点方案（主流）

```js
function isWhiteScreen() {
  const points = []
  const { innerWidth: w, innerHeight: h } = window
  // 取中轴 + 四角内缩共 17 个采样点
  for (let x = 0.1; x <= 0.9; x += 0.4) {
    for (let y = 0.1; y <= 0.9; y += 0.4) points.push([w * x, h * y])
  }
  const empty = points.every(([x, y]) => {
    const el = document.elementFromPoint(x, y)
    // 命中容器根节点（#app / body 的直接骨架）≈ 没有内容
    return !el || isContainerOnly(el)
  })
  return empty
}
```

- 两种方案对比

| 方案 | 原理 | 优缺点 |
| --- | --- | --- |
| 采样点 | `elementsFromPoint` 看点位是否只有容器 | 准确（真的"看不见"）；依赖页面结构约定 |
| DOM 节点数 | 关键容器子节点数低于阈值判白屏 | 实现简单；有内容但样式丢失会误判 |

- 工程要点
  - 判定时机：load 后延迟 1~2s（等渲染），或首屏接口返回后再判一次
  - **独立于采样、独立上报**：白屏是页面级灾难且发生时其他采集可能也失效
  - 白屏比 = 白屏 PV / 总 PV，是 P0 级告警指标
- 追问：容器判定怎么和业务解耦？
  - 约定"有效内容选择器"白名单（如 `.page-content` 之外都不算内容），SDK 配置下发——白名单随页面结构维护

### 4. 页面卡顿监控怎么实现？

**结论：卡顿 = 主线程被长时间占用——用 `longtask` 观测长任务（>50ms）做基础，配合 event timing 看交互延迟（INP 原料），重度卡顿（>200ms）记明细。**

| 观测层 | API | 记什么 |
| --- | --- | --- |
| 长任务 | `longtask` | 次数、总阻塞时长（TBT 口径）、Top N 明细 |
| 交互延迟 | `event` timing | 各交互 `duration`，按交互分组算差值 |
| 掉帧（辅助） | `requestAnimationFrame` 差值 | 相邻帧间隔超阈值次数（低端机验证用） |

- 分级处理

```
50ms ~ 200ms  轻度卡顿：只累计次数与 TBT，看趋势
> 200ms       重度卡顿：记录明细（duration + attribution 归因容器类型）
```

- 归因信息
  - `longtask` entry 的 `attribution` 字段带 `containerType`（script / iframe 等）与 `containerSrc`——能定位"是哪个脚本卡的主线程"
  - 结合行为轨迹：卡顿前用户点了什么 → 复现路径
- 追问：为什么不用帧率（FPS）做主指标？
  - 页面静止时 rAF 不触发，FPS 采样本身不可靠且误导；官方口径（longtask / INP）语义明确、可跨页面比较——FPS 只做辅助验证
