# 面试题 · 前端监控

> 定位：监控是「稳定性 + 性能 + 埋点」三合一的工程模块，高级岗爱考「体系设计 + 原理口径 + SDK 落地」三层。全篇按「结论先行 + 表格 + 子层级」组织，答案自包含；手写题按可复述伪代码粒度给出。

## 一、整体架构：从 0 到 1 搭建监控体系

### 1. 从 0 到 1 怎样搭建前端监控体系？

**结论：按「采什么 → 怎么采 → 怎么送 → 怎么治理」四步搭——先分清三类数据定采集范围，再按四层架构实现 SDK，最后用闭环让数据产生决策价值；监控的价值是把「用户骂了才知道出事」变成「指标先于投诉发现、数据先于猜测定位」。**

- 第 1 步 定采集范围：三类数据、三类视角

| 视角 | 回答的问题 | 采集对象 | 关键信号 |
| --- | --- | --- | --- |
| 稳定性 | 有没有坏 | JS 错误、Promise 异常、资源加载失败、接口异常、白屏 | 错误率、资源失败数、接口成功率 |
| 体验 | 快不快 | 加载与响应指标、长任务 | TTFB / FP / FCP / LCP / CLS / INP、>50ms 长任务 |
| 业务 | 用户在做什么 | 页面访问与行为 | PV / UV、停留时长、点击、转化漏斗 |

  - 为什么必须分三类：错误量小但必须**全量**（漏一条偶发崩溃可能就是线上事故）；行为数据量最大必须**采样**；性能指标要**足够样本**分位值才稳——三类量级与口径完全不同，混在一个采集逻辑里必然顾此失彼
- 第 2 步 实现 SDK：四层架构，一层只干一件事
  - **采集层**：错误、性能、埋点各一个插件，互不感知、只共享 `emit(event)` 签名——加一类采集就是加一个插件
  - **传输层**：采样 → 攒批 → 投递（sendBeacon / fetch keepalive）→ 重试 → 溢出丢弃，缺一不可
  - **治理层**：采样率、脱敏、按指纹频控——脱敏在采集口、频控在传输入口
  - **生命周期**：单例 init 防重复上报；指标越晚越准，`visibilitychange → hidden` 时收口
- 第 3 步 落地闭环：目标设定与采集 → 传输与存储 → 分析可视化 → 告警与定位优化
  - 前端只负责「采集—上报」这一段，其余是服务端 / 数据分析的范畴
- 价值与可观测性
  - 三个价值层次：**稳定性**缩短 MTTR、**体验**让优化效果可验证（改前改后对比，而不是「我感觉快了」）、**业务**为产品决策和 A/B 实验提供数据
  - 可观测性三支柱的前端对应物：Metrics = 错误率 / 性能分位值；Logs = 错误详情 + 行为轨迹 + 上下文；Traces = 接口 TraceId、前后端链路串联（见六.1）
  - Lab 与 RUM 分工：Lab（Lighthouse）可控环境做回归卡口，RUM 看真实机型 / 网络 / 地域分化
- 答法建议：口述按四步走——采什么（本题）、异常怎么抓（二）、性能怎么采（三）、埋点怎么做（四）、上报怎么落地（五）；SDK 怎么设计就是本章 2、3 两题的展开

### 2. 自研监控 SDK 整体怎么设计？版本管理怎么做？

**结论：按「采集 / 传输 / 治理 / 生命周期」四层分工，对外只暴露 `init` + `use`（插件）+ `track`；单例 init 防重复上报，插件化让加一类采集不动其他层。版本两层都要——SDK 版本管采集行为、release 管数据归属，都写进每条上报。**

| 层 | 职责 | 关键点 |
| --- | --- | --- |
| 采集层 | 拿原始事实：错误、性能条目、行为 | 各采集器互不感知，只认识 `emit(event)` 这个函数签名 |
| 传输层 | 采样 → 攒批 → 投递 → 重试 → 溢出丢弃 | 四个机制缺一不可（见五.2） |
| 治理层 | 采样率、脱敏、按指纹频控 | 脱敏在采集口、频控在传输入口，天然分散 |
| 生命周期 | 什么时候初始化、什么时候收口上报 | `visibilitychange → hidden` 定稿（见五.1） |

- 两个不是"设计癖"的必要设计
  - **单例**：多个团队各写一句 `init()`，每一类错误上报 N 遍，看板错误数直接乘 N——重复初始化 = 重复上报
  - **插件化**：错误采集不该知道埋点存在；加一类采集（如白屏检测）就是加一个插件，传输、重试、生命周期一行不改
- init 时机：尽早（错误监听越早挂越不漏），但重计算延迟（性能采集靠 `buffered: true` 补收）
- 版本管理

| 层 | 标识 | 用途 |
| --- | --- | --- |
| SDK 版本 | `sdkVersion` 字段 | 采集口径变更后区分新旧数据；灰度升级出问题可定位 |
| 业务 release | 构建时注入（git sha / 包版本） | sourcemap 对齐、错误按版本分桶、性能按版本环比 |

  - release 由构建工具注入（Vite `define` / 环境变量），保证和产物一一对应；sourcemap 上传必须与 release 匹配（见二.3）；所有"环比"以 release 为分桶前提
- 追问：SDK 升级怎么灰度？
  - 按业务方接入版本号分桶放量；schema 变更（字段增删）要带版本号在服务端兼容两种格式，避免升级瞬间数据断档
- 追问：SDK 如何做到低侵入？自己报错怎么办？
  - 低侵入三原则：异步采集（PerformanceObserver 不占首屏）、热路径轻（enqueue 只做采样判断 + push + 判批，序列化放 flush）、总量受控（单条 100~150B、单批 <1KB）；上报走独立域名与业务隔离
  - 三层保命：所有回调/序列化/发送统一 try/catch 静默丢弃；连续失败熔断自关；「正在上报」标志位防上报失败→异常→再上报的死循环

## 二、异常监控：捕获哪些错误，用什么 API？

### 1. 前端异常分为哪几大类？分别怎么捕获？onerror、unhandledrejection 各扮演什么角色？

**结论：没有一个 API 能抓全错误，六类错误（外加 iframe 共七类）各挂各的监听——JS 运行时错误走 `error` 事件、Promise 走 `unhandledrejection`、资源错误靠捕获阶段；每类各有「信息缺口」，采集器必须接受并各自兜底。**

| 类别 | 典型场景 | 捕获方式 | 信息缺口 |
| --- | --- | --- | --- |
| JS 运行时错误 | 读 `undefined` 的属性 | `window.onerror` 或 `error` 事件 | 有完整信息 |
| Promise 异常 | `await` 没 catch | `unhandledrejection` | 无 filename / lineno |
| 资源加载失败 | img / script / link 挂了 | `error` 事件 + **捕获阶段** | 不冒泡、无 message |
| 接口错误 | 后端 404 / 500 | 包裹 `fetch` / XHR，记 `!ok` | 无 message，靠 url / status |
| 网络错误 | DNS 失败、断网 | 同上，走 `catch` 分支 | 只有 `Failed to fetch` |
| 跨域脚本错误 | 第三方 CDN 脚本出错 | 同运行时，但只拿到 `Script error.` | 细节全无（见下题） |
| iframe 异常 | 嵌入页报错 | `window.onerror` **跨不了 iframe** | 需单独处理 |

- ErrorEvent 关键字段（不用背全，这五个够定位）

```
event.message    错误信息（已被浏览器加 "Uncaught TypeError: " 前缀，别自己再拼）
event.filename   出错文件 URL
event.lineno / colno  行号 / 列号
event.error      Error 对象，error.stack 才是完整调用栈
event.target     触发元素——有 tagName 就是资源错误（区分两类 error 的判据）
```

- onerror 与 addEventListener('error') 的区别

| 维度 | `window.onerror = fn` | `window.addEventListener('error', fn)` |
| --- | --- | --- |
| JS 运行时错误 | 能 | 能（默认冒泡阶段） |
| 资源加载错误 | **不能** | 能，但必须 `capture: true` |
| Promise 异常 | 不能 | 不能 |
| 挂载方式 | 属性赋值，后者覆盖前者 | 可多个监听器共存 |

  - 实际 SDK 只用 addEventListener 一个入口，内部按 `target.tagName` 分流；onerror 五参顺序易记混（msg → source → lineno → colno → error），lineno 是压缩产物行号、最终还原靠 sourcemap
- unhandledrejection 的要点

```js
window.addEventListener('unhandledrejection', (e) => {
  const reason = e.reason
  report({
    message: reason instanceof Error ? reason.message : String(reason),
    stack: reason instanceof Error ? reason.stack : '',
    type: 'promise'
  })
})
```

  - **reason 不一定是 Error**：`Promise.reject('字符串')` 合法，必须 `instanceof Error` 分支 + `String(reason)` 兜底
  - **没有 filename / lineno**：`reason.stack` 是唯一线索，不能拿位置做唯一索引
  - **触发时机**：拒绝后到微任务周期结束仍无 catch 才触发；补了 `.catch` 不会撤回已上报（可听 `rejectionhandled` 做撤销标记）
  - 老浏览器不支持，`try/catch` 包裹注册静默降级
- iframe 异常的两个事实
  - 父页面的 `onerror` 收不到 iframe 内的报错（事件不跨文档边界）
  - 同源 iframe：拿到 `contentWindow` 注入同样的监听；跨域 iframe：注入不了，只能 iframe 内部自己接 SDK 后 `postMessage` 转发给父页统一上报
- 追问：为什么资源错误要捕获阶段监听？
  - `img` / `script` 的 `error` 事件**不冒泡**，默认挂在 window 上收不到；`addEventListener('error', fn, true)` 第三个参数 `true` 让它在捕获阶段下传才能截住
- 追问：Vue / React 组件渲染异常怎么抓？
  - Vue 用 errorCaptured / app.config.errorHandler，React 用 ErrorBoundary；框架钩子兜不住的（事件、异步）最终仍落 window.onerror——框架层是补充不是替代
- 追问：接口错误怎么捕获？fetch 和 axios 有什么区别？
  - fetch：网络失败 reject，HTTP 4xx/5xx 不 reject、要自己判 res.ok；axios 默认都 reject，可在拦截器统一上报；网络错误（找网关）与 HTTP 逻辑错误（找服务端）分开定口径

### 2. Script error. 是什么错误？产生原因与解决方案？

**结论：`Script error.` 不是具体错误，是同源策略在保护——跨域脚本报错时浏览器故意不给 message / 行号 / 栈，防止把跨域页面的敏感信息漏给宿主页面。**

- 产生原因
  - 出错脚本的域与页面域不同（如 CDN 脚本），且没有满足跨域凭据条件
  - 浏览器在 `error` 事件里把细节抹成固定的 `Script error.`，信息全无
- 解决（两个条件**必须同时满足**）

| 条件 | 写在哪 | 作用 |
| --- | --- | --- |
| `<script crossorigin="anonymous">` | 引脚本的页面 | 声明"我愿意以匿名 CORS 方式加载" |
| `Access-Control-Allow-Origin` | CDN / 资源服务响应头 | 资源方同意暴露 |

- 兜底退路（CDN 加不了头时）
  - `Script error.` 连位置都没有，sourcemap 还原也用不上
  - 常见退路：关键第三方脚本自建同源（下载后挂自己域名）或服务端代理
- 追问：怎么快速验证是不是跨域问题？
  - 把脚本拉到本地同源环境跑一次——能拿到完整报错就是跨域抹除，复现不了才是错误本身偶发

### 3. SourceMap 的作用与原理？生产环境如何部署，有哪些安全风险？

**结论：sourcemap 把压缩后的位置映射回源码位置；生产环境的核心矛盾是「服务端还原要用它，浏览器不能公开它」——CI 上传 + 服务端还原 + 不随产物发布。**

- 作用
  - 生产栈是 `at n (app.a1b2c3.js:1:48213)` 这种压缩形式，人读不了；没有 sourcemap 等于拿到报错也定位不了
- 原理（一句话讲清即可）
  - map 文件里的 `mappings` 字段用 **VLQ 编码**记录「生成后位置 → 源文件 → 源码位置」的映射表；还原就是拿行列号查表 + 反解码
- 生产部署四条约定

| 约定 | 做法 | 防什么 |
| --- | --- | --- |
| CI 上传 | 构建后用 CLI 把 map 上传到监控平台，**上传后删本地** | map 留在构建机被顺手发布 |
| 不随产物发布 | Vite 用 `sourcemap: 'hidden'`（生成但不写 `//# sourceMappingURL` 注释） | 浏览器 DevTools 直接拉到 map 看源码 |
| release 绑定 | map 与代码用同一版本号（如 git sha）绑定上传 | 还原到错误版本的 map |
| 服务端还原 | 监控服务端收到压缩栈后查 map 还原 | 客户端还原体积大且要下发 map（等于公开） |

- 安全风险本质
  - map = 源码。公开部署等于把源码、注释、内部路径全部交出去；泄露渠道一般是「忘记关 sourcemap」「上传到公共 CDN 目录」
- 追问：为什么服务端还原优于客户端还原？
  - 客户端还原要把 map 下发到用户侧（体积大 + 泄露）；服务端还原只需上报压缩栈，map 永不出内网

## 三、性能监控：指标有哪些，用什么 API？

### 1. 解释 FP、FCP、LCP、CLS、INP 这几个核心指标；INP 和 FID 有什么区别？

**结论：FCP / LCP 管「快不快」，CLS 管「稳不稳」，INP 管「跟不跟手」；FP 已少单独用，FMP 已废弃，FID 已被 INP 取代（2024-03）。**

| 指标 | 全称 | 含义 | 良好阈值 |
| --- | --- | --- | --- |
| FP | First Paint | 首次绘制（哪怕只是背景色） | — |
| FCP | First Contentful Paint | 首次内容绘制（文本 / 图片等真实内容） | ≤ 1.8s |
| LCP | Largest Contentful Paint | 最大内容元素渲染完成 | ≤ 2.5s |
| CLS | Cumulative Layout Shift | 累计布局偏移（无输入引起的位移之和） | ≤ 0.1 |
| INP | Interaction to Next Paint | 交互响应性（全交互取较差分位） | ≤ 200ms |

- 记忆锚点
  - FCP 是「有东西可见」，LCP 是「主要内容可见」——两者差值就是用户"白等"的时间
  - CLS 是**分值不是秒**：位移面积占比 × 移动距离占比，累加
- 口径红线（2026 年现状）
  - **FID 已被 INP 取代**（2024-03 起 Core Web Vitals 剔除 FID），答 FID 必须带这句
  - **FMP 已废弃**（Chrome 明确 deprecated），被 LCP 替代——老资料还在教 FMP，答出来要标注
- INP 与 FID 的区别

| 维度 | FID（已淘汰） | INP（现行） |
| --- | --- | --- |
| 统计范围 | 仅**首次**交互 | **所有**交互 |
| 测量终点 | 输入处理开始 | 事件处理完成 + **渲染出下一帧** |
| 聚合方式 | 单次值 | 按交互分组取较差分位（P75） |

  - FID 只回答"输入有没有被立即处理"——处理函数卡 2s 的页面 FID 照样好看；采集必须按交互 ID 分组（同一交互派生 pointerdown / click 等多事件），不能对所有 event 条目平均——生产直接接官方 `web-vitals` 库
- 追问：为什么 FMP 被废弃？
  - FMP 依赖浏览器猜"什么算有意义内容"，算法不稳定且易被小图干扰；LCP 用"最大元素"这个确定性规则替代
- 追问：CLS 是什么？怎么降布局偏移？
  - 视口内元素位移分数总和，0.1 内良好；成因：图片/广告无尺寸占位、动态内容插入已有内容上方、字体切换；降法：预留宽高、动画用 transform 而非 top/left、font-display: optional
- 追问：性能指标用什么 API 采集？长任务是什么？
  - 两范式：navigation/loading 同步快照（TTFB 等）+ PerformanceObserver 异步订阅（LCP/CLS/长任务，buffered: true 补收）；>50ms 即长任务，TBT 只算超出 50ms 的部分，别写成累加总时长

### 2. LCP 的定义？哪些元素算 LCP 元素？LCP 差怎么排查优化？

**结论：LCP 是视口内最大内容元素的渲染时间；候选是明确的四类元素，优化按「资源早到 → 提高优先级 → 少延迟渲染」三方向。**

- 四类候选元素
  - `<img>`（含 `<svg>` 内的 image）
  - `<video>` 的封面帧
  - 带 URL 的背景图（CSS `background-image`）
  - 块级元素内的文本节点（含行内子元素）
- 停止更新时机
  - 一次用户真实交互（点击 / 按键）或页面转后台后，浏览器不再报告新的 LCP 候选——**越晚越准，必须在页面隐藏时定稿**（见五.1）
- LCP 差的三方向排查

| 方向 | 常见原因 | 手段 |
| --- | --- | --- |
| 资源晚到 | LCP 图片 / 字体晚请求 | 预加载 `<link rel="preload">`、优先级提升、压缩 |
| 渲染被阻塞 | 阻塞 JS / CSS | 拆分关键 CSS、脚本 defer / async |
| 服务端慢 | TTFB 高 | 缓存、CDN、服务端渲染 |

- 追问：怎么找到当前页面的 LCP 元素？
  - `PerformanceObserver` 回调里 `entry.element` 直接给出 DOM 节点；排查工具用 Lighthouse 的诊断面板也能看

## 四、业务采集与埋点

### 1. 什么是埋点？手动埋点、无埋点、可视化埋点各自优缺点？

**结论：埋点是把用户行为变成可分析事件的过程；三种方式按「口径准确度 vs 接入成本」取舍，实践是核心路径手动、长尾自动的组合。**

| 维度 | 手动（代码）埋点 | 无埋点（全埋点） | 可视化埋点 |
| --- | --- | --- | --- |
| 做法 | 业务代码里调 `track('事件', 参数)` | SDK 自动采集全部点击 / 曝光 | 运营后台圈选元素，配置下发 |
| 口径 | 最准、参数最全 | 覆盖全但噪声大 | 中间 |
| 成本 | 要发版才能加 / 改 | 零接入成本 | 不改代码但规则随改版失效 |
| 上报量 | 按需 | 巨大 | 按配置 |

- 组合策略（答这层是加分项）
  - 核心转化路径（下单 / 支付）用手动埋点——口径必须准、参数必须全
  - 长尾页面用无埋点兜底——看「还有哪些没覆盖」
  - 声明式埋点（`data-track` 属性 + 事件委托）是手动与无埋点的折中：业务只写属性，采集逻辑收进 SDK
- 追问：无埋点上报量巨大怎么治？
  - 只采「可交互元素」而非全部 DOM；采样率压到 10%~50%；文本截断、参数白名单
- 追问：行为采集要收集哪些信息？怎么防采集敏感信息？
  - 事件本体 + 身份（设备/匿名/登录三 ID 分工）+ 环境上下文；脱敏三条硬线全在采集口拦：URL 只留 pathname、元素文本截断 40 字符、表单值永不采——数据出了浏览器泄露已发生，服务端过滤防不了采集链路

## 五、上报策略

### 1. 监控数据上报有哪些方案？页面卸载时如何保证送达？

**结论：三代演进——图片打点（GET、URL 受限）→ `fetch + keepalive`（兜底）→ `navigator.sendBeacon`（首选）；卸载收口不用 `unload` 而监听 `visibilitychange → hidden`，hidden 时 flush 队列并走 sendBeacon / keepalive。**

| 手段 | 卸载时能否送达 | 是否阻塞 | 限制 | 定位 |
| --- | --- | --- | --- | --- |
| `new Image()` 打点 | 能（浏览器为它推迟卸载） | 否 | 只能 GET、URL 上限约 2~8KB、拿不到响应 | 上一代 |
| 同步 XHR | 能 | **阻塞卸载** | 浏览器已基本禁用 | 丢弃 |
| `fetch`（无 keepalive） | 不能，请求被取消 | 否 | — | 不适用 |
| `fetch + keepalive` | 能 | 否 | 请求体 64KB 上限 | 兜底 |
| `navigator.sendBeacon` | 能 | 否 | 无响应回调 | 首选 |

- sendBeacon 的特点与限制
  - 调用立即返回 `true / false`（只代表"已交给浏览器排队"），不返回响应；跨域**不触发预检**
  - 限制：无响应回调（确认入库要靠服务端计数对账）；64KB 上限，超了返回 `false` 要自己分片；跨域 Content-Type 受限（JSON 常以 `text/plain` 发送由服务端宽容解析）
- 卸载收口时序

```js
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') {
    const metrics = perf.finalize()        // LCP / CLS 定稿
    emit({ type: 'perf', ...metrics })
    tracker.pageLeave()                    // 停留时长结算
    transport.flush('hidden')              // 队列 flush，内部先 sendBeacon、false 降级 keepalive
  }
})
```

- 为什么不用 `unload`
  - 移动端浏览器为保住前进后退缓存（bfcache），**unload 经常不触发**；`pagehide` / `hidden` 才可靠
- 指标越晚越准的原理
  - LCP / CLS 是整页生命周期内收敛的指标：滚动后的大图可能把 LCP 从 1.2s 改到 2.4s——**hidden 才是上报时机**，load 时报的是中途值
- 追问：hidden 之后用户又切回来，数据重复了吗？
  - flush 后队列已清空，不会重复；要防的是「flush 中途又入队」——flush 加个进行中标志位即可

### 2. 为什么不能逐条上报？合并、采样、频控、队列怎么实现？

**结论：逐条上报把「请求数」乘出几倍——挤占业务并发、浪费带宽电量、高频序列化卡主线程；传输层四机制——攒批（够 N 条或超时发）、采样（入队口丢）、频控（同指纹窗口内只报一次）、队列上限（溢出丢最旧）。**

- 逐条上报的代价（实测对照，同 12 条事件：逐条 12 个请求 vs 攒批 3 个）
  - **并发连接挤占**：浏览器同域并发有上限，监控请求排队把业务请求顶到等待
  - **带宽与电量**：每次请求的 HTTP 头开销远大于一条事件本身
  - **主线程开销**：每次 JSON.stringify + 网络初始化都在抢主线程
  - **服务端压力**：PV 十万的站点每次点击一条请求，接收端直接被打爆
- 四机制实现要点

| 机制 | 实现要点 | 关键参数示例 |
| --- | --- | --- |
| 合并（攒批） | 队列攒够 `batchSize` 或定时 `flushInterval` 触发一次请求 | 5 条 / 3 秒 |
| 采样 | `Math.random() >= rate` 直接拒收入队；**放入队口**而非投递口 | 错误 1、埋点 0.1~0.5 |
| 频控 | 按指纹记时间戳，窗口内重复只累计 `count` 不重发 | 同一错误 3 秒一条 |
| 队列上限 | `maxQueue` 超限 `shift()` 丢最旧，记 `dropped` | 100 条 |

- 采样分层

| 数据类型 | 建议采样率 | 原因 |
| --- | --- | --- |
| 错误 | 100%（不采样） | 量不大，抽样会漏掉"偶发崩溃" |
| 性能指标 | 全量或高比例 | 分位值需要足够样本才稳 |
| 行为埋点 | 10%~50% | 量最大，统计口径不要求逐条准确 |
| 长任务 / 资源明细 | 1%~5% | 单条体积大，看趋势即可 |

  - 异常优先采样：会话内出现错误 / 长任务 / 白屏即打标、该会话提升到 100% 采样——把配额花在刀刃上；改采样率必须和版本号一起标注，否则环比突降会被误判
- 频控的键是「指纹」不是 message

```
指纹 = message + 出错位置（文件） + 行号
资源 / 接口错误没有 message —— 必须把 src / url 算进指纹
```

  - 只按 message 去重会把不同出错点合并；必须带 `count` 累计 + 指纹复位（如 5 分钟未再现清掉）
- 体积控制四板斧：字段精简（UA 解析成枚举后丢弃原始串）、栈截断（`error.stack` 留前 N 帧且不留 Error 引用）、明细限流（资源 entry 只报 Top N）、批量压缩——单条 100~150B、一批约 700B，比一张图片小两个数量级
- 重试与溢出：重试有上限（首投 + 2 次就放弃）；溢出丢最旧
- 追问：那错误也攒批吗？攒批期间页面关了怎么办？
  - 分级：错误（尤其首见）可立即投递；行为 / 性能攒批 3~5 秒或攒满 N 条——延迟 3 秒对监控无感；`hidden` 时立即 flush 一次，投递走 sendBeacon / keepalive（见上题）

## 六、场景面试大题（口述项目题）

### 1. 项目中搭建前端监控体系遇到的最大难点是什么？（上报量太大、成本高又不丢关键异常怎么办）

**结论（项目题按「难点 → 方案 → 结果」口述）：最大难点是「上报量与关键信息不丢的平衡」——全量上报监控自己就成性能与成本问题，粗暴采样又会漏掉致命异常；最终用分层采样 + 异常优先 + 绝对计数告警三层解决，成本侧再配传输聚合与冷热存储。**

- 难点的量化背景（先给规模感）
  - 行为事件量是错误的百倍量级；全量上报时监控请求占比肉眼可见，服务端存储成本也线性暴涨
- 三层方案

| 层 | 策略 | 保住什么 |
| --- | --- | --- |
| 分层采样 | 错误 100% / 性能全量 / 埋点 10%~50% / 长任务 1%~5% | 量大的降下来，量小的保住 |
| 异常优先 | 会话内出现错误即打标、该会话提升到 100% 采样 | 崩溃现场的完整行为轨迹 |
| 绝对计数告警 | 白屏检测、首见错误指纹不依赖采样比例 | 大事故不被采样稀释 |

- 关键代码形态（采样放入口 + 会话提标）

```js
function enqueue(event) {
  const rate = sessionFlagged ? 1 : cfg.sampleRate // 异常会话全量
  if (Math.random() >= rate) return false
  queue.push(event)
  if (queue.length > cfg.maxQueue) queue.shift()
  if (queue.length >= cfg.batchSize) flush('batch-full')
  return true
}
```

- 成本侧配套（存储与传输）
  - 传输：同指纹聚合上报（count + 首末次），错误存储从"次数"变"种类"；聚合时保留「首条完整 + 后续只累计」保现场
  - 存储：服务端预计算分位值 / 错误率，原始明细短 TTL，冷数据转对象存储按需回捞
  - 关键异常的"不丢"由结构保证：错误 100% 采样进聚合 + 白屏 / 首见错误独立告警，不依赖明细留存
- 结果表述（带数字）
  - 上报量降约 70% 的同时，错误发现率不变（错误全量）；异常会话的排查信息反而更全了
- 追问预案：为什么白屏要独立于采样？
  - 白屏是"页面级灾难"，发生率低但影响 100% 用户；且白屏本身发生时其他采集可能也失效——独立轻量检测 + 不采样才能兜住
- 追问：怎么关联前端报错与后端链路 TraceId？
  - 前端生成/透传 traceId（请求头）→ 后端链路日志同 ID → 错误上报带上，报错卡片可直查后端哪台服务哪段代码；接口成功但渲染报错也有用——查报错前最后几条响应的数据形态

### 2. 线上大量 LCP 指标很差，如何通过监控定位问题？

**结论：按「先分桶定位面、再下钻定位点」两步——分桶找共性（版本/机型/地域/网络），下钻到具体资源与阶段（TTFB / 资源耗时 / 渲染阻塞）。**

- 第一步：分桶找共性

| 分桶维度 | 能发现什么 |
| --- | --- |
| release 版本 | 某版本发版后才劣化 → 回滚比对 |
| 机型 / 浏览器 | 低端机问题 → 渲染性能方向 |
| 地域 / 网络类型 | 弱网区域 → CDN / 资源体积方向 |
| 页面路由 | 单页面问题 → 页面级代码 |

- 第二步：下钻定位点
  - **LCP 元素**：`entry.element` 看是图还是文本——图走资源方向，文本走渲染方向
  - **TTFB 分段**：`responseStart - startTime` 高 → 服务端 / 网络慢；低但 LCP 仍高 → 前端资源与渲染慢
  - **资源明细**：LCP 图片的 `resource` entry 拆 DNS / TCP / 传输耗时；`initiatorType` 看有没有被 preload
  - **长任务**：LCP 时点前后的长任务 → 主线程被阻塞，渲染推后
- 与优化联动
  - 定位结论要落到可执行项：预加载 LCP 图片、defer 非关键脚本、CDN 覆盖弱网区域——优化后再用同一监控看 P75 环比验证
- 追问：为什么看 P75 而不是平均值？
  - 性能数据右偏分布（少数极慢拉高均值），P75 是官方推荐的体验线；均值会掩盖"多数人还行、少数人很惨"的分布

## 七、手写 / 实操题

### 1. 手写捕获全局 JS 错误与 Promise 异常

**结论：error 事件捕获阶段监听（同时兜住资源错误）+ unhandledrejection 兜 Promise，reason 类型要兜底。**

```js
window.addEventListener('error', (event) => {
  // 资源错误：target 是元素（不冒泡，靠捕获阶段截获）
  if (event.target && event.target.tagName) {
    const tag = event.target.tagName.toLowerCase()
    const src = event.target.src || event.target.href
    report({ type: 'resource', tag, src })
    return
  }
  // 脚本错误：ErrorEvent
  const err = event.error
  report({
    type: 'runtime',
    message: event.message,
    filename: event.filename,
    lineno: event.lineno,
    colno: event.colno,
    stack: err && err.stack
  })
}, true) // capture: true 是抓资源错误的关键

window.addEventListener('unhandledrejection', (event) => {
  const reason = event.reason
  report({
    type: 'promise',
    message: reason instanceof Error ? reason.message : String(reason),
    stack: reason instanceof Error ? reason.stack : ''
    // 注意：没有 filename / lineno，stack 是唯一位置线索
  })
})
```

- 追问：如何让用户补了 catch 之后撤销上报？
  - 监听 `rejectionhandled` 事件（补挂 catch 时触发），按记录的 reason 匹配到已上报条目做撤销标记

## 八、白屏监控

### 1. 页面白屏监控怎么实现？

**结论：核心是"判定页面是否白屏"——主流方案是采样点检测（取视口内若干点看是否命中有效内容）或 DOM 节点数阈值，onload 后延迟判定，按 PV 维度算白屏率。**

- 采样点方案（主流）

```js
function isWhiteScreen() {
  const points = []
  const { innerWidth: w, innerHeight: h } = window
  // 取中轴 + 四角内缩共 17 个采样点
  for (let x = 0.1; x <= 0.9; x += 0.4) {
    for (let y = 0.1; y <= 0.9; y += 0.4) points.push([w * x, h * y])
  }
  const empty = points.every(([x, y]) => {
    const el = document.elementFromPoint(x, y)
    // 命中容器根节点（#app / body 的直接骨架）≈ 没有内容
    return !el || isContainerOnly(el)
  })
  return empty
}
```

- 两种方案对比

| 方案 | 原理 | 优缺点 |
| --- | --- | --- |
| 采样点 | `elementsFromPoint` 看点位是否只有容器 | 准确（真的"看不见"）；依赖页面结构约定 |
| DOM 节点数 | 关键容器子节点数低于阈值判白屏 | 实现简单；有内容但样式丢失会误判 |

- 工程要点
  - 判定时机：load 后延迟 1~2s（等渲染），或首屏接口返回后再判一次
  - **独立于采样、独立上报**：白屏是页面级灾难且发生时其他采集可能也失效
  - 白屏比 = 白屏 PV / 总 PV，是 P0 级告警指标
- 追问：容器判定怎么和业务解耦？
  - 约定"有效内容选择器"白名单（如 `.page-content` 之外都不算内容），SDK 配置下发——白名单随页面结构维护
