## 一、包管理：npm 与 pnpm

### 1. npm 的两个核心痛点是什么？根源在哪？

**结论：npm v3 起把依赖拍平到顶层 node_modules 解决嵌套问题，代价是两个——同名包不同版本各留一份（重复安装），传递依赖全部暴露在顶层（幽灵依赖）。**

**① 重复安装**

- 根工程声明 `is-even@1.0.0`（依赖 `is-odd@0.1.2` → `is-number@3.0.0`）和 `is-odd@3.0.1`（依赖 `is-number@6.0.0`）
- `is-number@3.0.0` 与顶层要的 `@6.0.0` 冲突，只能嵌套在 `is-even` 下面——磁盘上出现多份副本
- `npm ls --all` 能直接看到这棵版本树

**② 幽灵依赖**

- 传递依赖被拍平到顶层后，源码可以 `require('is-number')`——一个自己从没声明的包
- 依赖了别人安装的结果：依赖方升级后不再依赖它、换包管理器、顶层版本变化，随时爆雷

**③ 根源**

- 扁平化是为了解决 v2 时代深层嵌套的路径长度问题，策略是「尽量提升、冲突才嵌套」
- 提升把「安装结构」变成了「隐式 API」——这是 npm 包管理模型的先天权衡

**⭐ 加分点**

- 幽灵依赖的三个爆雷时机能说全：依赖方升级后不再依赖、换包管理器（顶层结构规则不同）、顶层同包版本变化
- 排查工具：`npm ls --all` 看版本树、`npm why <pkg>` 查依赖来源

### 2. pnpm 的 store 硬链接 + 符号链接是怎么工作的？

**结论：所有包文件在全局 store 只存一份；项目 `node_modules/.pnpm` 里是硬链接（不复制数据），根 `node_modules` 的直接依赖是指向 `.pnpm` 的符号链接——磁盘省、安装快、结构严格三件事一次做到。**

**① 目录结构**

```
node_modules
├── react -> .pnpm/react@18.2.0/node_modules/react      # 直接依赖：符号链接
└── .pnpm
    ├── react@18.2.0
    │   └── node_modules
    │       └── react（文件是硬链接，指向全局 store）
    └── loose-envify@1.4.0
        └── node_modules
            └── loose-envify（硬链接）
```

**② 两个链接各管一件事**

- 硬链接：`node_modules/.pnpm` 里的包文件指向全局 store 的同一份磁盘文件——装包 ≈ 建链接，不复制数据
- 符号链接：项目根 `node_modules/xxx` 链到 `.pnpm` 里的真实位置——传递依赖全部隔离在 `.pnpm` 子目录里
- 全局 store 跨项目共享：`pnpm store path` 查看位置，第二个项目装同一个包几乎瞬时

**⭐ 加分点**

- 硬链接不能跨文件系统——store 与项目必须同盘，跨盘场景 pnpm 退化为复制
- 「省内存、安装快」的准确表述：省的是**同一份文件的多处副本**，快的是**避免网络下载后的全量复制**

### 3. 什么是幽灵依赖？pnpm 为什么能让它直接报错？

**结论：require 了没声明的传递依赖就是幽灵依赖；pnpm 把传递依赖全部隔离在 `.pnpm` 子目录、不提升到根 node_modules——未声明的包在解析路径上根本不存在，构建期直接报错。**

**① 危害**

- npm 扁平化下能 require，是因为传递依赖碰巧被提升到了顶层
- 爆雷时机：依赖方升级后不再依赖、换包管理器、顶层版本变化——错误延迟到运行时才出现

**② pnpm 的机制**

- 传递依赖全部待在 `.pnpm/<pkg>@<ver>/node_modules/` 里，根 node_modules 只链接 package.json 里声明的直接依赖
- 未声明 → Node 沿 node_modules 查找失败 → 报错——把运行时的隐性炸弹变成安装期的显式错误

**③ 修复姿势**

- 在 `package.json` 显式声明实际用到的包
- 迁移存量项目：这是 pnpm 化最常见的报错来源，逐个补声明即可

**⭐ 加分点**

- 严格模式不是「限制」而是「对齐语义」：Node 的解析规则本来就不该命中未声明的包——npm 是放宽了现实，pnpm 是恢复了契约
- ⚠️ 讲的时候别说「pnpm 禁止幽灵依赖是为了安全」这种空话，核心是**隔离了传递依赖的物理位置**

### 4. pnpm workspace 怎么组织 monorepo？

**结论：`pnpm-workspace.yaml` 声明成员目录，本地依赖用 `workspace:` 协议引用——版本与源码永远同步；根 package.json `private: true` 防误发布，编排靠 `-r`（递归）与 `--filter`（过滤）。**

**① 骨架**

- `pnpm-workspace.yaml`：声明哪些目录是工作区成员（`packages/*`、`apps/*`）
- 根 package.json：`private: true`（根工程不产出包，只做编排）+ 汇总脚本（`pnpm -r run build` 全量构建、`pnpm --filter @lab/web run start` 单包执行）
- 子包：对应成员目录各有 package.json，按是否发布设 `private`

**② 本地依赖声明**

- `workspace:*` 引用本地包：本地改完即生效，不会解析到线上 npm 版本
- 外部依赖用普通版本号，与单包工程无异

**③ 发布**

- `pnpm -r publish` 会把 `workspace:*` 替换成实际版本号——本地链接不会带进发布产物
- 发布前用 `pnpm -r version` 或 changesets 统一升版本、生成变更日志

**⭐ 加分点**

- `pnpm why <pkg> --filter <pkg>` 查某依赖是谁引入的；`pnpm list -r --depth -1` 列全部成员
- lockfile 按 importer 分组记录每个成员的依赖——monorepo 的可复现性是按包粒度锁的

### 5. 锁文件为什么必须提交？删了重新生成不行吗？

**结论：lockfile 锁住「解析后的确切版本与完整依赖树」，保证任何机器、任何时间 install 出同一棵树；删掉重新生成等于放弃可复现性——CI 和同事的机器可能装出完全不同的版本组合。**

**① 两个文件分工**

- `package.json` 是**意愿**：`^1.2.0` 是版本范围
- `pnpm-lock.yaml` / `package-lock.json` 是**事实**：解析出的精确版本 + integrity 哈希

**② 为什么必须锁**

- 不锁的话，两次 install 之间新发布的兼容版本会被自动采用——「我本地是好的」的经典来源
- CI 与本地解析结果分叉，问题在生产环境才暴露

**③ 正确的升级姿势**

- 升级走 `pnpm update` / `pnpm -r update --latest`，lockfile 随之更新并提交
- 「删 lockfile 重装」是排障手段（怀疑锁文件损坏），不是常规操作

**⭐ 加分点**

- lockfile 变化是 Vite 预构建缓存的失效条件之一——包管理层的纪律会传导到构建层
- 「锁文件冲突怎么解」：重装重新生成后 diff 检查，或用 `--fix-lockfile` 类选项——本质是保证树的一致性而非手工合并

## 二、Webpack：原理与心智模型

### 6. webpack 的构建流程是怎样的？Compiler 和 Compilation 有什么区别？

**结论：一条流水线——初始化 Compiler → make 阶段从入口递归建模块图（逐个跑 loader）→ seal 冻结模块图并分 chunk → processAssets 优化产物 → emit 写盘；Compiler 是进程级单例（持有配置与钩子），Compilation 是单次编译的容器（模块、chunk、assets 都挂在它上面）。**

**① 主流程五段**

- `beforeRun / run`：读取配置，创建 Compiler
- `make`：从 entry 出发 DFS 解析依赖，每个文件经 loader 链转成 Module，边解边建图
- `seal`：模块图冻结，按 splitChunks 等规则把 Module 分组成 Chunk
- `processAssets`：Chunk 渲染成 Asset（产物），压缩、抽 CSS、生成 HTML 都在这个窗口
- `emit / done`：写盘，产出 stats

**② 两个对象的分工**

- Compiler：一次进程只创建一个，持有 options 与 `compiler.hooks`；watch 模式下多次编译复用它
- Compilation：每触发一次编译就新建一个，`modules / chunks / assets` 全在上面——所以增量编译其实是「新 Compilation 复用旧模块缓存」
- 推论：plugin 想跨编译存数据挂 Compiler，想存本次产物挂 Compilation（如 CSS 登记表 `compilation.__miniCss`）

**③ 为什么是五个对象而不是两个**

- Module（一个源文件）→ Chunk（一组模块）→ Asset（一个产物文件）是三层映射：stats 里模块数与文件数对不上，就是因为中间隔着 chunk 分组规则
- 改一个文件会重渲染它所属的整个 Chunk——「增量」的粒度是模块缓存 + chunk 重渲染

**⭐ 加分点**

- `thisCompilation` 是注册 compilation 级钩子的**最后时机**；`seal` 之后不能再加模块；`processAssets` 是动产物内容的**唯一安全窗口**——三个边界能答出来说明真写过 plugin
- watch 模式「改一个文件为什么重建一堆」：模块缓存命中，但它所属 chunk 及引用了该 chunk 的产物都要重渲染
- 这套流程不用背——webpack-lab 里的手写插件（清目录、抽 CSS、产 HTML）就挂在对应钩子上，`DEBUG_WP=1` 起一次构建看钩子逐行打印就记住了

### 7. loader 和 plugin 的区别？各自解决什么问题？

**结论：loader 管「单个模块怎么转换」（输入源码字符串、输出代码字符串，在 make 阶段逐文件执行）；plugin 管「编译流程里插手」（有 `apply(compiler)`，挂在钩子事件流上，能跨模块、跨阶段操作模块图与产物）。**

**① loader：模块级转换器**

- 本质是纯函数：`source 进、代码文本出`，`use` 数组从右往左串行（pitch 阶段相反，从左往右）
- 典型：css-loader 内联 `@import`、改写 `url()` → `require()`；babel-loader 转译语法
- 边界：只能看到「当前这一个文件」，拿不到其他模块、拿不到产物

**② plugin：流程级扩展**

- 本质是「有 `apply(compiler)` 的对象」，在 `compiler.hooks` / `compilation.hooks` 上注册回调
- 能做的事远超 loader：新增产物（HtmlWebpackPlugin）、优化产物（TerserPlugin）、切 chunk（SplitChunksPlugin）、定义编译期常量（DefinePlugin）
- webpack 本体的大部分能力（splitChunks、runtimeChunk、侧效分析）就是内置 plugin

**③ 选型判断**

- 「把 X 文件变成 JS 能 import 的模块」→ loader；「在产物层面加东西/改东西/卡门禁」→ plugin
- 特殊资源两段式：loader 登记单个模块的内容（如 CSS 文本登记到 compilation），plugin 在 `processAssets` 汇总成独立产物——想加任何「特殊资源」都照这个拆法

**⭐ 加分点**

- loader 链的执行顺序是高频坑：普通阶段**从右往左**（`use: [a, b]` 先跑 b），pitch 阶段从左往右——mini-css-extract 的 loader 必须用 pitch，因为普通阶段拿到的已是 css-loader 产出的 JS 代码，取不到 CSS 文本
- loader 里 `this.addDependency(file)` 告诉 webpack「这也是依赖」——被 `@import` 的 CSS 改了能触发重新编译就靠它
- plugin 的产出纪律：`emitAsset` 新增、`updateAsset` 覆盖，不要 `fs.writeFileSync`——后者不进 stats、不参与 `output.clean`、不跟随 watch

### 8. 什么是 tapable？webpack 的插件机制建立在什么之上？

**结论：tapable 是 webpack 的「事件流」库——提供一组 Hook 类（SyncHook / AsyncSeriesHook / AsyncParallelHook 等），plugin 用 `tap/tapAsync/tapPromise` 注册，webpack 在固定时机 `call/callAsync` 触发；插件机制 = 钩子注册表 + 按约定触发。**

**① 极简模型**

- 一个 Hook 就是「先注册、后触发」：`tap(name, fn)` 存进数组，`call(...args)` 按序执行——原理版十几行就能写出来
- 真正的 tapable 还做了编译优化：hook 链会被 JIT 成一个连续执行的函数，比 EventEmitter 快

**② Hook 类型决定插件语义**

- Sync 系列：同步串行；`SyncBailHook` 有返回值就「熔断」跳过后面（resolve 类场景）
- Waterfall：上一个的返回值是下一个的入参
- AsyncSeries / AsyncParallel：异步串行（一个完再下一个）与异步并行（一起发、等齐）

**③ 这对写 plugin 意味着什么**

- 选错 Hook 类型 = 语义错误：要串行等待的用了 Parallel，可能读到中间态产物
- `tap` / `tapAsync(callback)` / `tapPromise(返回 Promise)` 三种注册方式对应 Hook 的异步能力
- 同一钩子上多个插件的先后：`processAssets` 按 **stage 数值**排（数字小先执行），不是注册顺序

**⭐ 加分点**

- `processAssets` 的 stage 表值得背几个：`ADDITIONS(-100)` 产新资源（如抽 CSS）→ `OPTIMIZE_SIZE(400)` 压缩 → `SUMMARIZE(1000)` 生成 HTML → `OPTIMIZE_HASH(2500)` 重算 contenthash
- stage 填错的真实后果：HTML 插件排在压缩之前，引用的就是压缩前的旧文件名；TerserPlugin 日志里的 hash 与最终产物对不上，正是因为 hash 在 2500 才重算
- 追问「tapable 与 EventEmitter 区别」：Hook 有类型语义（熔断/瀑布/并行），EventEmitter 只是无序通知

## 三、Webpack：loader 与 plugin

### 9. 手写一个 loader 需要注意什么？pitch loader 是什么？

**结论：loader 是「输入源码、输出代码字符串」的函数，三个要点——返回的是代码文本不是值、异步用 `this.async()`、依赖其他文件要 `this.addDependency`；pitch loader 是普通阶段之前从左往右先跑的「前置关卡」，能拿到剩余链的请求串，常用于「截胡」整条链。**

**① 基本形态与三个坑**

- 返回代码文本：想导出字符串要自己 `JSON.stringify` 拼进 `export default ...`，不能直接 return CSS
- 异步：拿 `const cb = this.async()`，完成后 `cb(err, content)`；同步 loader 直接 return
- 外部依赖：`this.addDependency(abs)` 登记，`@import` 的 CSS 改动才能触发重建

**② 链式执行顺序**

- `use: [a, b, c]`：pitch 阶段 a→b→c（从左往右），普通阶段 c→b→a（从右往左）
- 任一 pitch 有返回值，**跳过后续所有 loader 的普通阶段**，直接把它当最终结果——这就是「截胡」

**③ pitch 的典型用途**

- mini-css-extract 的 loader：普通阶段 source 已是 css-loader 的 JS 产物，取不到 CSS 文本；pitch 里用 `this.importModule('!!' + remainingRequest)` 在构建期跑完剩余链、拿回 CSS 导出，登记后返回占位模块
- `!!` 前缀含义：禁用配置里的所有 loader，只跑请求串里显式写的这条链

**⭐ 加分点**

- css-loader 改写 `url()` 的细节：保留 `url(...)` 包装本身，只把资源地址换成运行时插值——否则产物变成裸路径
- loader 不能访问 webpack 配置对象，但能通过 `this.getOptions()` 拿到自己的 options
- 追问「loader 能不能返回多个文件」：可以，`this.emitFile()`（如 file-loader 产图片），返回值仍是「当前模块」的代码

### 10. style-loader 和 mini-css-extract-plugin 的区别？生产为什么用后者？

**结论：style-loader 把 CSS 文本塞进 JS bundle、运行时创建 `<style>` 插入 head；mini-css-extract 把 CSS 抽成独立 `.css` 文件、HTML 用 `<link>` 引；生产默认选抽离——并行加载无 FOUC、独立 contenthash 单独命中缓存。**

**① 两条链路的原理**

- 注入：CSS → JS 字符串 → 打进 bundle → 运行时 `document.head.appendChild(<style>)`
- 抽离：loader 在 pitch 阶段登记 CSS 文本 → 返回占位模块 → plugin 在 `processAssets` 汇总成 `.css` 产物 → HTML 注入 `<link>`

**② 生产选抽离的三个理由**

- 生效时机：注入要等 JS 下载+执行完，首屏有 FOUC；`<link>` 与 JS 并行加载
- 缓存：注入的 CSS 没有独立 hash，CSS 一变 JS 文件名跟着变、缓存全失效；抽离后 CSS 单独 contenthash
- 能力：注入无法 `<link rel="preload">`，严格 CSP 下 `style-src` 要放行 inline

**③ 注入并没死**

- 微前端沙箱、Web Components / Shadow DOM、要求单文件产物的场景仍会用它
- 两条链互斥：同一个 `.css` 规则只能二选一

**⭐ 加分点**

- 抽离链是「loader+plugin 两段式」的最佳教学案例：loader 管单模块登记、plugin 管跨文件汇总
- Vue SFC 的 `<style>` 走抽离链的坑：style 块是带 `?vue&type=style` 查询串的请求，匹配不上 `test: /\.css$/`——`VueLoaderPlugin` 把规则克隆成带 `?vue` 的版本才接上
- 追问「CSS 抽离后怎么做按需加载」：路由懒加载 chunk 里的 CSS 会被拆到对应 chunk 的 css 文件，随 chunk 一起按需拉取（webpack 5 的 css chunk 跟随 js chunk）

### 11. 你写过哪些 webpack plugin？手写 plugin 的核心是什么？

**结论：plugin 是「有 `apply(compiler)` 的对象」，核心不是 API 而是「知道挂在哪个钩子、哪个 stage」——产物类插件几乎都挂在 `processAssets` 上按 stage 排队：先产 CSS（-100）→ 再压缩 JS（400）→ 最后生成 HTML（1000）。**

**① 骨架**

```js
class MyPlugin {
    apply(compiler) {
        compiler.hooks.thisCompilation.tap('MyPlugin', compilation => {
            compilation.hooks.processAssets.tap(
                { name: 'MyPlugin', stage: webpack.Compilation.PROCESS_ASSETS_STAGE_ADDITIONS },
                () => { /* 读/改 compilation.assets */ }
            )
        })
    }
}
```

**② 三个自测能用插件讲清楚的例子**

- MiniCssExtractPlugin：读 loader 登记的 CSS → `emitAsset` 产 `.css`（stage -100）
- MiniTerserPlugin：遍历 `.js` assets 过 terser → `updateAsset` 覆盖（stage 400）
- MiniHtmlPlugin：从 `compilation.assets` 与 `entrypoint.getFiles()` 现读带 hash 的文件名 → 拼模板产 `index.html`（stage 1000）

**③ 为什么 stage 比注册顺序重要**

- `processAssets` 上挤着几乎所有「动产物」的插件，彼此按 stage 数值排队
- 顺序即依赖：CSS 产物先存在，HTML 才引得到；压缩先完成，HTML 引用的才是最终文件名

**⭐ 加分点**

- JS 的 `<script>` 顺序要从 `entrypoint.getFiles()` 取（保证 runtime 在 main 之前），不是遍历 assets——这是 HtmlWebpackPlugin 级插件才知道的细节
- `compiler.hooks` 与 `compilation.hooks` 的选择：要拿配置/整次编译挂前者，要拿模块/chunk/产物挂后者；在 `thisCompilation` 里注册 compilation 级钩子是通用范式
- 高频追问「怎么让插件支持异步」：`tapPromise` 返回 Promise（如压缩要 await terser.minify），或 `tapAsync` 用 callback

### 12. 说几个你熟悉的 webpack 钩子，分别能拿到什么？

**结论：记「边界」比背清单有用——`thisCompilation`（注册 compilation 钩子的最后时机）、`make`（开始建图）、`seal`（模块图冻结）、`processAssets`（动产物的唯一安全窗口）、`emit`（写盘前）、`done`（stats 可用）。**

**① 编译建立期**

- `compiler.hooks.beforeRun`：还没开始解析，读外部配置、清理目录
- `compiler.hooks.thisCompilation`：拿到新建的 compilation（还是空的）——注册 compilation 级钩子的最后时机
- `compiler.hooks.make`：从这里开始递归解析依赖、跑 loader

**② 模块到产物期**

- `compilation.hooks.finishModules`：模块图完成、尚未分 chunk
- `compilation.hooks.seal`：模块图冻结，之后不能再加模块
- `compilation.hooks.optimizeChunks`：chunk 已切分——SplitChunksPlugin 在这干活

**③ 产物与收尾期**

- `compilation.hooks.processAssets`：全部产物就绪，压缩、生成 HTML、改 assets 的唯一安全窗口
- `compiler.hooks.emit`：产物即将写盘（CleanPlugin、统计校验）
- `compiler.hooks.done`：stats 可用，报告/通知类插件

**⭐ 加分点**

- 「想在产物里加 banner 该挂哪个钩子」：processAssets——早于它产物没生成，晚于它已写盘
- watch 模式下钩子按「次」触发：每次重编译都新建 compilation、重跑 compilation 级钩子，compiler 级钩子不重来
- 调试技巧：断点打在 `processAssets` 回调里能看到 `compilation.assets` 的最终形态；webpack-lab 的 debug-log-plugin 能把整条时间线逐行打出来

## 四、Webpack：产物优化

### 13. Tree-Shaking 的原理与前提？为什么有时摇不掉？

**结论：Tree-Shaking = 「标记 + 删除」两步——构建期基于 ESM 静态结构标记未引用的导出，压缩阶段由 Terser 删除死代码；前提三个：ESM 静态结构、`sideEffects` 标记、生产模式压缩，缺一不可。**

**① 为什么必须 ESM**

- `import/export` 是静态声明：不执行代码就能算出「谁导出了什么、谁引用了什么」
- CJS 的 `require` 是运行时函数调用（`require(condition ? 'x' : 'y')`），构建期无法确定依赖，摇不了

**② 两个前提条件**

- `sideEffects`：webpack 标记了「未引用」，但不敢删有副作用的模块（顶层执行代码、polyfill）；`package.json` 里 `"sideEffects": false` 是给打包器的承诺——「没引用的模块删掉不影响行为」
- 生产模式：`mode: 'production'` 才启用 Terser，标记的死代码真正被删；只标记不压缩，代码还在产物里

**③ 摇不掉的常见场景**

- 从「桶文件」（barrel，index.js 统一 re-export）导入：整个桶进了依赖图，sideEffects 未标记时全部保留
- babel 把 ESM 转成了 CJS（`@babel/preset-env` 默认 modules 转换）——要关：`modules: false`
- 类的方法、对象属性默认不摇（可能动态访问）；CommonJS 依赖整体不摇

**⭐ 加分点**

- 「`sideEffects: false` ≠ 模块内副作用语句可删」：它说的是「模块没被引用可整块删」，已在依赖图里的模块，顶层副作用语句照样保留
- 与 Rollup 的对比是加分项：Rollup 解析期一步完成删除；webpack 是「标记+压缩」两步——只配 `sideEffects` 不开生产压缩，一个字节都不会少
- 实测验证方法：构建产物里搜未引用函数名，或做「开 / 关 `sideEffects`」的体积对照实验

### 14. Code Splitting 怎么做？splitChunks 的 cacheGroups 怎么配？

**结论：两条路——动态 `import()` 切懒加载 chunk（路由级最自然），`splitChunks` 把 node_modules 与公共模块抽成独立 chunk；cacheGroups 里「按范围切」（vendor）与「按次数切」（common）是两种规则，别混成一句。**

**① 动态 import()**

- `() => import('./views/Home.vue')` 就是分割点：webpack 为它切独立 chunk，运行到才下载
- 路由级懒加载是单入口应用最自然的分割——首屏只带入口 chunk

**② splitChunks 的两种抽取规则**

- `vendor`（按范围）：`test: /node_modules/`，不设 `minChunks`——命中且过 `minSize` 就抽，与被引用几次无关
- `common`（按次数）：`minChunks: 2`——业务模块被两个以上 chunk 复用才抽
- `priority` 数值大优先：vendor=10 > common=5，node_modules 永远先归 vendors

**③ 生效的三个必要条件（同时满足）**

- `minChunks`：被引用次数够
- `minSize`：体积够大（默认 20KB）——「配了没生效」通常是被它挡住
- 命中 cacheGroup 的 test 规则

**⭐ 加分点**

- `runtimeChunk: 'single'` 的动机：webpack 运行时装着模块表与 chunk 映射，业务一变它跟着变；抽成独立文件后，业务 chunk 的 hash 不因运行时变化全部失效
- `chunks: 'all'` 的含义：初始 chunk 与异步 chunk 都参与拆分（默认只拆异步）
- 过度拆分的代价：chunk 过多抬高请求数，且每个 chunk 都有运行时开销——「能缓存」与「请求数」要平衡

### 15. contenthash / chunkhash / hash 的区别？长缓存怎么配？

**结论：`hash` 是整次构建一个值（任何文件变全变）、`chunkhash` 按 chunk 内容算（同 chunk 内文件互相牵连）、`contenthash` 按单个产物内容算（变谁换谁）——长缓存只认 `contenthash`。**

**① 三种 hash 的粒度**

- `[hash]`：一次编译一个值，改任何文件所有产物名全变——缓存全军覆没
- `[chunkhash]`：同一 chunk 的产物共享，CSS 变了同 chunk 的 JS 名也变
- `[contenthash]`：按产物自身内容算，CSS 变只换 CSS 的名——JS 缓存不受影响

**② 长缓存配置组合**

- `output.filename: '[name].[contenthash:8].js'` + `chunkFilename` 管懒加载 chunk + `assetModuleFilename` 管图片字体
- HTML 必须由插件生成（从 assets 现读最终文件名）——这就是不能手写 `<script src="app.js">` 的原因
- `output.clean: true` 每次先清 dist，不留旧 hash 残骸

**③ hash 稳定性的坑**

- 压缩会改内容：TerserPlugin 在 stage 400 改完，webpack 在 2500 用 RealContentHashPlugin 重算——插件日志里的文件名与最终产物对不上是正常的
- 模块 id 默认按发现顺序编号，新增模块会让后续 id 全位移 → 内容变 → hash 变；生产配 `optimization.moduleIds: 'deterministic'` 让 id 稳定

**⭐ 加分点**

- 「为什么 vendors 能长缓存」：第三方库不常变，contenthash 不变 → 文件名不变 → CDN/浏览器一直命中；业务代码频繁变，只换自己的小 chunk
- runtimeChunk 独立也是为 hash 稳定性服务（见上题）
- 追问「hash 冲突可能吗」：理论上 md5 截 8 位有碰撞概率，工程上不构成问题；内容寻址的意义是「变才换名」，不是全局唯一 id

### 16. webpack 构建速度怎么优化？

**结论：三个方向——少编译（缩小范围）、编译快（缓存与并行）、少重做（增量与持久化缓存）；先量后优，用 speed-measure-webpack-plugin 定位耗时大户。**

**① 少编译：缩小处理范围**

- loader 配 `include/exclude`：babel 别碰 `node_modules`
- `resolve.extensions` 别写太长（每个省略后缀的 import 都要逐个试）、`resolve.alias` 直连常用库
- `externals` 把大库排除在打包外（改走 CDN，前提全局变量可用）

**② 编译快：缓存与并行**

- `cache: { type: 'filesystem' }`（webpack 5 持久化缓存）——二次构建提速最明显的一项
- thread-loader 给重 loader（babel/ts）开 worker 池；esbuild-loader / swc 替换 babel（Go/Rust 实现快一个量级）
- `parallelism` 与 TerserPlugin 的 `parallel`（默认已开）

**③ 少重做：dev 与 watch**

- dev 用 webpack-dev-server / HMR 替代整包重建
- watch 模式的增量：模块级缓存命中，只重渲染受影响 chunk
- 大项目评估 rspack / turbopack（同 API 的 Rust 重写）是「换引擎」路线

**⭐ 加分点**

- 先量后优：`speed-measure-webpack-plugin` 打出每个 loader/plugin 耗时——优化没有数据的构建是猜
- 持久化缓存的安全：`cache.buildDependencies` 把配置文件声明进去，配置变了缓存自动失效
- thread-loader 不是免费的：worker 启动与通信有开销，小项目反而变慢——只放在耗时大的 loader 前

## 五、Vite：原理与心智模型

### 17. Vite 为什么快？dev server 启动的完整流程？

**结论：核心是「双引擎」结构——dev 不打包（原生 ESM 按需编译，请求到哪编译到哪），build 才打包（Rollup/Rolldown 深度优化）；再加 esbuild 预构建依赖，冷启动与项目体积解耦。**

- dev 引擎：浏览器原生 ESM 请求模块，dev server 只编译被请求的文件——启动快、HMR 粒度细
- 预构建引擎：依赖包用 esbuild（Go，比 JS 工具链快一个量级）提前处理
- build 引擎：生产用 Rollup（新版本可选 Rolldown）——成熟 tree-shaking 与产物优化
- 启动完整流程

```
1. 读取 vite.config，合并默认配置与 .env
2. 扫描源码 import，esbuild 预构建依赖（或命中缓存）
3. 启动 http server + WebSocket，注册中间件（模块转换、静态资源、HMR）
4. 浏览器请求 index.html → 解析 <script type="module"> → 逐个请求模块
5. 每个请求经过插件 transform 后返回——「请求到哪编译到哪」
```

- 本质一句话：「bundleless 开发 vs 全量 bundle」——快来自「dev 不做不需要的事」，不是「同样的活干得快」
- 追问：为什么 dev 可以不打包而生产必须打？
  - dev 只服务一个正在开发的浏览器会话，按需编译延迟可接受；生产要面对全部用户的网络瀑布与兼容性——必须全量 bundle + 优化（见第 19 题）

### 18. 依赖预构建是什么？什么时候触发？CJS/ESM 混用怎么处理？

**结论：esbuild 把 node_modules 里的第三方依赖提前转换——CJS/UMD 转 ESM + 把零散小模块合并成单文件防请求瀑布；结果缓存在 node_modules/.vite，命中缓存就跳过。CJS 依赖统一在预构建层转 ESM，扫描发现不了的用 optimizeDeps.include 显式声明。**

- 三个目的
  - 兼容：很多依赖是 CJS/UMD，浏览器 ESM 加载不了——统一转 ESM
  - 减请求：lodash 这类几百个子模块的包不合并，页面打开就是几百个请求瀑布
  - 快：esbuild 是 Go 写的，预构建秒级完成
- 触发时机：首次启动（无缓存）；lockfile 变化；vite.config 相关配置变化；手动 `--force`
- 配置：`optimizeDeps.include` 强制预构建（动态 import 的依赖、扫描发现不了的）、`exclude` 排除（保持源码形态）
- CJS/ESM 混用的分层处理
  - 依赖（node_modules）：预构建统一转 ESM——主流场景都在这层解决
  - 源码里的特殊依赖：`optimizeDeps.include: ['某cjs包']` 强制走预构建
  - `exclude` 的依赖：保持源码形态，需要该包自身提供 ESM 入口，否则报错
- 追问：二次启动为什么明显更快？缓存什么时候失效？
  - 二次快：命中 `.vite` 缓存跳过预构建 + 浏览器对依赖模块有强缓存——「冷启动慢、二次快」是设计行为
  - 失效：lockfile 变化、影响预构建的 config 变化、`--force`、缓存目录被清——保守但正确，因为 CJS 互操作结果与具体版本强相关

### 19. dev 快 ≠ 生产快：为什么生产还要打包？

**结论：dev 的按需服务只对「单会话开发」成立；生产要服务全部用户，必须解决请求瀑布、兼容性和产物体积——所以 build 走全量 bundle（Rollup/Rolldown），且「dev 正常 build 白屏」是经典差异坑。**

- 生产必须打包的三个理由
  - 请求瀑布：成百上千个 ESM 请求即使 HTTP/2 也有排队与解析开销
  - 兼容性：按 build.target 转译目标浏览器
  - 产物优化：tree-shaking、压缩、分包、内容 hash——dev 全没有
- dev / prod 行为差异的经典坑
  - 环境变量注入时机不同（`import.meta.env` 替换策略）
  - 动态 import 路径在 bundle 后的解析差异
  - 预构建源码形态差异（CJS 互操作）
- 规避：build 后 `preview` 起真实产物跑主流程——发布前必做
- 追问：为什么不干脆 dev 也全量 bundle？
  - 那就是回退到 Webpack 的启动模型——项目越大启动越慢，Vite 的核心价值就没了

## 六、Vite：HMR 与插件

### 20. HMR 热更新的完整原理？和 Webpack 的 HMR 区别？

**结论：server 监听文件变化，经 WebSocket 推送受影响模块，浏览器请求新版本并在运行时替换；替换沿 import 链向上冒泡找 accept 边界，找不到或替换失败就整页刷新兜底。与 Webpack 的差异根源是 bundleless vs bundle——Vite 推模块路径按需拉新，Webpack 推新 chunk。**

- 完整链路

```
文件变化 → server 编译该模块 → WebSocket 推送 { path, timestamp }
→ client 请求最新版本模块 → 执行模块自声明的 accept 回调完成替换
→ 该模块没 accept？沿 import 链向上找 accept 边界
→ 找不到边界 / 替换抛错 → full reload 兜底
```

- 不同资源的粒度：CSS 直接换 style 标签；Vue 单文件组件由插件精确到 template / script / style 分块替换
- 与 Webpack HMR 对比

| 维度 | Vite HMR | Webpack HMR |
| --- | --- | --- |
| 更新粒度 | 单模块（ESM 精确替换） | 重新编译该模块 + 受影响依赖链 |
| 速度与项目规模 | 无衰减（只处理改动文件） | 依赖链越长越慢 |
| 通信 | WebSocket 推模块路径 | WebSocket 推新 chunk hash |
| 极端兜底 | 替换失败整页刷新 | 同样可能整页刷新 |

- 追问：为什么改了 store 模块整页刷新了？
  - store 模块通常被多处引用且无 accept 边界；要保状态需自己写 accept + dispose + data 迁移（见下一题）。整页刷新不是 bug——HMR 的正确性优先于热度

### 21. import.meta.hot 能做什么？举例。

**结论：模块级的热替换控制接口——accept 声明可替换、dispose 清副作用、data 保状态；最典型应用是 store / 全局单例的热替换保状态。**

```js
if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    newModule.applyState(import.meta.hot.data.state)
  })
  import.meta.hot.dispose(() => { clearInterval(timer) })
  import.meta.hot.data.state = currentState
}
```

- 四个 API
  - `accept`：模块自声明「我能被热替换」
  - `dispose`：声明替换前要清理的副作用（定时器、事件监听）
  - `data`：跨更新保存状态（热替换时把旧状态带给新模块）
  - `decline`：声明「我无法热替换」→ 直接走刷新
- 三个典型场景
  - store 模块：替换后恢复旧状态，页面不重置
  - 定时器 / 事件监听：dispose 里清理，防重复注册
  - 不可热替换的模块：decline 明确拒绝，避免半替换状态
- 追问：`import.meta.hot` 判断存在有什么讲究？
  - 生产构建没有这个对象——包在 if 里，构建器可直接摇掉这块代码

### 22. Vite 插件的钩子体系？和 Rollup 插件什么关系？

**结论：两类钩子——通用钩子（与 Rollup 兼容，管模块内容：resolveId → load → transform → renderChunk）和 Vite 专有钩子（管开发服务：config、configureServer、hotUpdate 等）；`enforce: 'pre' / 'post'` 控制相对内置插件的顺序。Vite 兼容大部分 Rollup 插件，但 dev server 能力不通用。**

| 类别 | 代表钩子 | 管什么 |
| --- | --- | --- |
| 通用（Rollup 兼容） | resolveId / load / transform / renderChunk | 模块的定位、内容、转换、产物加工 |
| Vite 专有 | config / configureServer / hotUpdate / transformIndexHtml | 配置修改、dev 中间件、热更新、HTML 注入 |

- 三部曲分工纪律
  - resolveId：把 import 路径解析成真实或虚拟模块 id（别名、虚拟模块都在这）
  - load：按 id 返回内容（读盘、生成虚拟模块代码）
  - transform：对内容做转译（TS、Vue SFC、替换代码）
- enforce 顺序：pre → 核心（vite 内置）→ normal → post；Rollup 侧同义的 `order` 字段
- 通用性边界
  - 通用：只声明通用钩子的插件，两边都能跑（官方 `@rollup/plugin-*` 大多可直接用于 Vite）
  - 不通用：Vite 专有钩子在 Rollup 下被忽略；框架插件（@vitejs/plugin-vue）是 Vite 专属
- 追问：为什么改别人产出的内容用 transform 而不是 load？
  - load 在 transform 之前——load 阶段拿到的还是原始内容；要基于上游插件的产物做处理必须在 transform

### 23. 写一个 Vite 插件的真实套路？虚拟模块解决什么问题？

**结论：绝大多数需求落在三种形态——虚拟模块（resolveId + load 造出磁盘上不存在的模块）、内容替换（transform）、产物加工（renderChunk / generateBundle）；识别需求属于哪种，套模板即可。**

- 三种形态模板

```js
// 虚拟模块：resolveId 造 id + load 给代码
{
  name: 'virtual-env',
  resolveId(id) { if (id === 'virtual:env') return '\0virtual:env' },
  load(id) { if (id === '\0virtual:env') return `export const version = '1.0.0'` }
}
// 内容替换：transform 里改代码
{
  name: 'drop-console',
  transform(code, id) {
    if (!id.includes('src/')) return null
    return code.replace(/console\.log\([^)]*\);?/g, '')
  }
}
// 产物门禁：生成阶段比对预算
{
  name: 'size-gate',
  renderChunk(code, chunk) {
    if (chunk.fileName.includes('vendor') && code.length > 500 * 1024) {
      throw new Error('vendor 超过 500KB 预算')
    }
    return null
  }
}
```

- `\0` 前缀惯例：虚拟模块 id 加空字节前缀，防止与其他真实文件 / 插件冲突
- 虚拟模块 vs define：define 是文本替换（编译期常量），虚拟模块是完整模块（可导出函数、可 import 别的模块）——典型用途：注入版本号、聚合统一出口
- 追问：剔除 console 为什么要在 transform 而不是压缩阶段？
  - 可以在压缩阶段（esbuild drop 配置更彻底）——但插件形态可控（按目录、按规则），两者是「通用配置 vs 定制规则」的关系

## 七、Vite：配置与生态

### 24. 环境变量与模式怎么用？安全边界在哪？

**结论：.env 家族按模式加载（development / production / 自定义），只有 `VITE_` 前缀的变量注入客户端——这就是安全边界：服务端密钥绝不带 VITE_ 前缀。**

- 三层文件：`.env`（全模式）→ `.env.development` / `.env.production` → `.env.local`（本地覆盖，git 忽略）
- 取值：源码里 `import.meta.env.X`；非 `VITE_` 前缀不暴露（防密钥泄漏进 bundle）
- 运行时配置不走构建注入：发布后要改的配置（接口地址、开关）走后端接口拉取——构建期注入意味着改一个字要重新发版
- 追问：为什么运行时变更不走环境变量？
  - 构建注入是编译期写死进 bundle 的——改配置 = 重新构建发版；运行时配置的正确来源是接口或远程配置中心

### 25. 代码分割怎么设计？

**结论：路由级动态 import 是主刀（时序优化），manualChunks 按变动频率分桶是缓存优化——业务代码频繁变、第三方框架稳定，分开放才能让二次访问命中长缓存。**

- 两层分割
  - 路由级：动态 import 天然按页分 chunk——首屏只拉当前页
  - 依赖层：manualChunks（新版本 advancedChunks）把稳定依赖拆 vendor——业务改动不击穿 vendor 的内容 hash
- 长缓存的前提：内容 hash——vendor 不变则文件名不变，强缓存持续命中
- 注意点：分割解决「首屏拉太多」，但过度分割会请求碎片化——配合空闲预取
- 追问：把所有第三方拆进一个 vendor 一定好吗？
  - 不一定——一个 1MB 的 vendor 意味着任何依赖升级全体失效；按「变动频率一致」分桶更优

### 26. 怎么保证构建产物的质量？

**结论：三道关——类型检查拆出构建链（dev 不全量 tsc）、体积门禁插件卡预算、preview 预览验证真实产物；dev 能跑不等于产物能上线。**

- 类型检查：vite dev/esbuild 只转译不检查——IDE + 独立的 `tsc --noEmit` / vue-tsc 阶段兜住
- 体积门禁：插件在生成阶段比对预算超限报错（见 vite-lab 的 size-gate）——防「优化完三个月长回来」
- preview 验证：build 后起 preview 服务跑主流程——专治「dev 正常 build 白屏」（环境变量、动态导入路径、预构建差异）
- 追问：为什么 esbuild 转译 TS 不做类型检查？
  - 类型检查是全程序分析，慢；esbuild 追求转译吞吐——职责拆开：转译求快，检查单独跑

### 27. Rolldown 是什么？Vite 为什么要自研打包内核？

**结论：Rolldown 是 Rust 写的、API 兼容 Rollup 的打包器——Vite 团队用它统一双引擎（取代 esbuild + Rollup 两个依赖），目标是 dev / build 同一套内核、性能再上台阶。**

- 动机：dev 用 esbuild、build 用 Rollup 的双依赖结构有行为差异（转译能力、插件支持）——统一内核消灭差异
- 兼容策略：钩子 API 对齐 Rollup，存量插件与知识迁移成本低
- 版本口径：Vite 6+ 可选启用，逐步过渡；面试讲清「为什么统一」比背版本号重要
- 追问：统一内核后 esbuild 就被淘汰了吗？
  - esbuild 仍是压缩等环节的主力；淘汰的是「dev/build 用两套内核」的结构性不一致

### 28. Vite 的库模式（lib mode）和直接用 Rollup 什么关系？

**结论：Vite 库模式是 Rollup 的封装（预置入口、多格式、dts 协作）——简单库开箱即用；需要精细控制（多入口、复杂 external、插件流水线）时直接用 Rollup。**

- 库模式：`build.lib` 配置入口与格式名，底层还是 Rollup 打包——适合中小组件库
- 直接 Rollup：完整配置 external / 多格式 / exports / 自定义插件——组件库、工具库的精细方案（见 Rollup 篇）
- 选型经验：一个入口 + 双格式 → 库模式；多入口 + 类型产物 + CI 门禁 → Rollup
- 追问：库模式能加自定义 Rollup 插件吗？
  - 能——plugins 数组通吃，因为底层就是 Rollup

## 八、工程判断与场景题

### 29. Vite 和 Webpack 的核心差异？什么场景还选 Webpack？Vite 有哪些缺点？

**结论：本质差异是「bundleless 开发 vs 全量打包」——由此派生启动、HMR、配置复杂度的全面差异；生产两者都打包，Vite 用 Rollup/Rolldown。仍选 Webpack 的四类场景都源于 Vite 的现代浏览器前提与生态边界。**

| 维度 | Vite | Webpack |
| --- | --- | --- |
| dev 形态 | 原生 ESM 按需 serve | 全量构建成 bundle 再 serve |
| 冷启动 | 与项目体积基本无关 | 全量建依赖图，越大越慢 |
| HMR | 单模块替换，无衰减 | 依赖链重编译，越大越慢 |
| 配置 | 零配置起步，内置常用处理 | loader / plugin 需手动配 |
| 生产 | Rollup / Rolldown 打包 | 自研全功能打包 |
| 兼容性 | 面向现代浏览器（target 可调） | 可打 IE11（babel + polyfill） |
| 生态 | 快速成熟 | 最成熟（老项目 / 微前端沉淀深） |

- 生产端没那么大差异
  - 都要全量建图、分割、压缩；Vite 生产走 Rollup 体系（8.x 起 Rolldown），概念（chunk、contenthash、manualChunks）与 webpack 一一对应
  - 「Vite 生产也快」主要来自 Rolldown/esbuild 的实现语言优势，不是架构差异
- 仍选 Webpack 的四类场景
  - IE11：Vite 面向 ESM 浏览器，补到 IE 代价极高（官方已放弃）
  - 老 CJS 生态：大量依赖 Webpack 专属 loader / 插件的存量项目，迁移成本大于收益
  - 模块联邦：Webpack 5 的微前端方案，Vite 生态里是别的实现路径（已有成熟方案的项目不动）
  - Node 端 / 特殊环境打包：Webpack 的 target 与插件更全
- Vite 的缺点与规避

| 缺点 | 规避 |
| --- | --- |
| 首次预构建延迟、依赖变化触发重跑 | 锁定依赖版本、命中缓存、冷启动任务放 CI 预热 |
| dev 正常 build 白屏（行为差异） | build 后 preview 跑主流程，发布前必做 |
| 不支持旧浏览器 | build.target 明确目标；绕不开就换工具 |
| CJS 依赖报错 | optimizeDeps.include 强制预构建 |

- 追问：这些缺点里哪个最容易在生产翻车？
  - dev / prod 不一致——因为 dev 阶段完全无感；流程上强制 preview 验证是唯一可靠防线
- 追问：为什么生产不用原生 ESM？
  - 瀑布请求（几百个模块逐个请求）在真实网络下不可接受，兼容性与优化空间也依赖打包产物

### 30. Module Federation（模块联邦）是什么？解决什么问题？

**结论：webpack 5 的运行时模块共享机制——多个独立构建的应用（host/remote）在运行时互相加载对方暴露的模块，并共享依赖单例；解决微前端「独立开发部署 + 共享公共依赖」的问题。**

**① 角色与配置**

- remote（提供方）：`exposes` 声明暴露的模块（`./Button: './src/Button.vue'`）
- host（消费方）：`remotes` 声明远端地址，代码里 `import('app2/Button')` 像本地模块一样用
- `shared`：声明共享依赖（vue、react）——host 与 remote 协商出**同一个实例**，版本兼容就复用

**② 它解决了什么**

- 传统微前端（路由级拼接、iframe）共享依赖要各打一份：vue 打两份 = 体积翻倍 + 响应式系统两份实例直接出 bug
- 公共库升级不必所有子应用同时重新发布——remote 独立部署，host 运行时拉最新

**③ 代价与边界**

- 运行时拉取远端 entry：网络失败要有兜底（ErrorBoundary / 降级组件）
- 共享依赖版本协商有规则：大版本不一致会警告/各自加载，「共享」不等于「永远单例」
- 构建与部署复杂度上升：remoteEntry 的 hash、缓存策略、跨端类型同步都要工程化配套

**⭐ 加分点**

- 「为什么共享依赖必须单例」：vue/react 这类库有内部状态（响应式 effect 链、hooks 上下文），两个实例互相不认——这是 MF 的 `shared` 存在的根本原因，与库打包 external 的动机同源
- MF 是**运行时**集成，与普通 npm 依赖的**构建时**集成对比着讲
- 追问「和 vite 的 federation 插件关系」：社区有 vite-plugin-federation，但原生实现与生态以 webpack 为主——存量 webpack 微前端项目是 MF 的主要战场

### 31. 项目冷启动很慢、二次启动很快，什么原因？

**结论：这是 Vite 的设计行为——首次要预构建依赖（esbuild 全量处理）且浏览器无缓存；二次命中 `.vite` 缓存 + 浏览器强缓存，只剩源码按需编译。**

- 首次慢的组成：依赖预构建 + 首屏按需编译链 + 无缓存全量请求
- 二次快的组成：预构建缓存命中 + 浏览器对依赖模块强缓存（304 或直接内存）
- 优化方向：CI 预热缓存、收敛依赖版本减少失效、首屏模块合理分割减少首次编译链
- 追问：如果二次启动也变慢了，查什么？
  - 缓存被反复失效（lockfile/config 频繁变化）或缓存目录被清理工具误删——回到预构建失效排查链（题 18）

### 32. 改了一行代码，页面整页刷新了，为什么？

**结论：HMR 没找到 accept 边界或判定无法热替换——沿 import 链冒泡到根都没有模块自接受，就 full reload 兜底；常见于改了被多处引用的非组件模块、或改了导出结构。**

- 常见触发
  - 模块无 accept 且无人代接受（store、工具、配置模块）
  - 修改了模块的导出结构（新增/删除导出）——下游引用关系变了，热替换不可靠
  - 改了非模块文件（html、插件注入内容）
- 解决：模块内 `import.meta.hot.accept` 自接受 + dispose/data 处理状态；组件类交给框架插件边界
- 追问：整页刷新是 bug 吗？
  - 不是——HMR 的正确性优先于热度：替换不了就刷新，宁可慢也不给错状态

### 33. 场景：新装一个依赖是 CJS 格式，dev 报错「does not provide an export named 'default'」，怎么办？

**结论：该依赖没被预构建成 ESM——`optimizeDeps.include` 强制纳入预构建；仍不行检查 exclude 配置与该包是否有 ESM 入口。**

- 排查链
  - 是否被 `optimizeDeps.exclude` 排除了（exclude 的保持源码形态，CJS 直接报错）
  - 是否是动态 import（扫描发现不了）→ include 显式声明
  - 包自身提供 ESM 入口吗（package.json module/exports 字段）——都没有只能靠预构建互操作
- 顺带确认：lockfile 提交、`--force` 后复现一次再下结论（缓存脏数据会伪装成包的问题）
- 追问：为什么预构建能解决而浏览器原生不行？
  - 浏览器只认 ESM 语法；CJS 的 require 是运行时函数调用——必须构建期转成静态 import/export
