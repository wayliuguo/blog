# 面试题 · 计算机网络

## 一、总纲

### 1. 从输入 URL 到页面展示，发生了什么？

**结论：URL 解析 → DNS 解析 → TCP 连接（+TLS 握手）→ 发送 HTTP 请求 → 服务器处理并响应 → 浏览器解析渲染。本篇所有题目都挂在这条链上。**

- 第一步：URL 解析与缓存判断
  - 拆出协议/域名/端口/路径/查询参数；HSTS 列表命中则强制升级 HTTPS（HSTS = 服务端通过 `Strict-Transport-Security` 响应头下发「此域名必须走 HTTPS」策略，浏览器存入本地名单；命中后 http:// 在发出前就被改写为 https://，比 301 重定向安全）
  - 缓存判断
    - 强缓存：`Cache-Control`/`Expires` 未过期 → 直接用本地副本，**不发请求**，跳到第五步
    - 协商缓存：强缓存过期 → 带上 `If-None-Match`/`If-Modified-Since` 发请求问服务器，未变返回 **304** 只用本地副本（无响应体），变了返回 200 + 新资源
- 第二步：DNS 解析
  - 查询顺序：浏览器 DNS 缓存 → 系统缓存/hosts → 本地域名服务器
  - 本地域名服务器未命中：递归查询（替你问到底）→ 根/顶级/权威服务器逐级迭代查询
- 第三步：建立连接
  - TCP 三次握手：确认双方收发能力，携带初始序列号
  - HTTPS 再做 TLS 握手：非对称加密交换密钥、之后对称加密传输
  - HTTP/3 走 QUIC（基于 UDP）：握手与 TLS 合并，1-RTT 建连
- 第四步：发送 HTTP 请求与响应
  - 请求：报文 = 请求行 + 请求头 + 请求体
  - 响应：状态码判结果（2xx 成功 / 3xx 重定向 / 4xx 客户端错 / 5xx 服务端错）；CDN 场景先在边缘节点命中判断，未命中回源
- 第五步：浏览器渲染
  - 解析 HTML/CSS 构建 DOM/CSSOM → 合成渲染树 → 布局（计算几何位置）→ 绘制 → 合成上屏
- 答法建议
  - 高级岗按「每步一句话 + 挑一步深挖」作答，别平铺直叙背流水账
  - 前端岗重点展开：缓存、TLS、渲染；被追问哪步就深入哪步

### 2. OSI 七层与 TCP/IP 五层模型？

**结论：OSI 是理论分层（物/数/网/传/会/表/应），工程实际用 TCP/IP 四层或教学用五层；记住「层—设备—协议」对应即可。**

- 五层速记表

| 层 | 职责 | 设备 | 协议 |
| --- | --- | --- | --- |
| 应用层 | 为应用提供服务 | —— | HTTP/HTTPS/DNS/WebSocket/SSH |
| 传输层 | 端到端连接与可靠/不可靠传输 | —— | TCP/UDP |
| 网络层 | 主机到主机的路由寻址 | 路由器 | IP/ICMP |
| 数据链路层 | 相邻节点帧传输 | 交换机/网桥 | 以太网/ARP |
| 物理层 | 比特流传输 | 网卡/网线/集线器 | —— |

- 追问：OSI 的会话层/表示层去哪了？
  - 实际协议栈中合并进应用层（加密≈表示层、RPC 会话≈会话层），OSI 是教学模型
- 追问：数据封装顺序？
  - 发送方自上而下逐层加头（应用数据 → TCP 段 → IP 包 → 帧），接收方自下而上解

## 二、HTTP

### 3. HTTP 请求报文与响应报文的结构？常见头字段？

**结论：报文 = 起始行 + 头部 + 空行 + 体；头字段按通用/请求/响应/实体四类记。**

- 请求报文
  - 请求行：`方法 URL 版本`（如 `GET /index.html HTTP/1.1`）
  - 请求头 → 空行 → 请求体
- 响应报文
  - 状态行：`版本 状态码 短语`（如 `HTTP/1.1 200 OK`）
  - 响应头 → 空行 → 响应体
- 常见头速记

| 类别 | 字段 |
| --- | --- |
| 通用 | `Cache-Control`、`Connection`、`Date` |
| 请求 | `Host`（1.1 必带）、`Accept`/`Accept-Language`、`Authorization`、`If-None-Match`/`If-Modified-Since`、`Origin`、`Referer`、`User-Agent` |
| 响应 | `Set-Cookie`、`ETag`、`Last-Modified`、`Location`（重定向）、`Access-Control-*`（CORS） |
| 实体 | `Content-Type`、`Content-Length`、`Content-Encoding`（gzip/br） |

- 追问：HTTP 为什么「无状态」？怎么补状态？
  - 协议本身不记忆上下文；用 Cookie/Session/Token 在应用层补（详见浏览器原理篇存储章）
- 追问：`Content-Type` 常见取值？
  - `application/json`（接口主流）、`multipart/form-data`（文件上传）、`application/x-www-form-urlencoded`（表单默认）

### 4. HTTP/1.0 → 1.1 → 2 → 3 的演进与区别？

**结论：1.1 加长连接、2 解决应用层队头阻塞（二进制分帧+多路复用）、3 换 QUIC 解决传输层队头阻塞——每一步都在解决上一步的性能瓶颈。**

**HTTP/1.0**

- 存在的问题：
  - 短连接：每个请求都要新建一条 TCP 连接（三次握手），用完即断，开销大
  - 连接级队头阻塞：同一连接上请求串行，前一个响应没回来，后一个只能干等

**HTTP/1.1**

- 长连接：默认 keep-alive，一条 TCP 连接可复用多个请求，省去反复握手
- 存在的问题：
  - 响应必须按序返回（管道化实践中弃用），应用层队头阻塞仍在——慢的响应堵住后面的
  - 并发只能靠多开 6~8 条 TCP 连接缓解
  - 头部全量明文，重复传输、无压缩
- 顺带的改进：`Host` 头（支持虚拟主机）、Range 断点续传

**HTTP/2**

- 二进制分帧：报文拆成二进制帧传输，解析更高效
- 多路复用：一条 TCP 连接上多个 Stream 并发收发，互不阻塞——应用层队头阻塞解决
- HPACK 头部压缩（静态表 + 动态表 + Huffman）
- 存在的问题：
  - 传输层队头阻塞仍在：底层还是一条 TCP 按序交付，丢一个包，所有 Stream 都得等重传

**HTTP/3**

- 传输层换成 QUIC（基于 UDP）：在用户态自己实现序列号/确认/重传/流控，把 TCP 的可靠性搬了进来
- 每个 Stream 独立管理重传，丢包只堵自己——彻底解决队头阻塞
- 连接迁移（Connection ID，切网不断连）、0-RTT 快速建连

- 关键原理追问
  - **为什么 HTTP/2 没根治队头阻塞？**
    - 多路复用只在应用层分帧；底层仍是一条 TCP 按序交付——丢包时所有 Stream 等重传
    - HTTP/3 的 QUIC 在传输层为每个 Stream 独立管理重传，丢包只堵自己
  - QUIC 如何「在不可靠的 UDP 上实现可靠传输」？
    - 自己实现序列号/确认/重传/流控——把 TCP 的可靠性搬进用户态
  - HTTP/2 服务器推送现状？
    - 收益常为负（推的资源多半已有缓存），Chrome 已移除支持——知道即可，别当亮点
- 答法建议：按「1.1 解决连接复用 → 2 解决应用层队头阻塞 → 3 解决传输层队头阻塞」的因果链讲

### 5. GET 与 POST 的区别？

**结论：本质是语义区别——GET 幂等、可缓存、只读；POST 不幂等、用于写操作；参数位置只是实现约定，不是本质差异。**

| 维度 | GET | POST |
| --- | --- | --- |
| 语义 | 获取资源（安全：不改服务器状态） | 提交数据（可能改状态） |
| 幂等 | ✅ 多次结果一致 | ❌ 可能重复提交 |
| 可缓存/可收藏 | ✅ | ❌ |
| 参数位置 | URL 查询串 | 请求体（多种编码） |
| 浏览器行为 | 回退刷新直接重发 | 回退会提示重新提交 |

- 陷阱题（大厂高频）：**「用 POST 完全代替 GET 行不行？」**
  - 不行：GET 可被缓存/预取/收藏，POST 不行；替换会破坏语义约定、代理缓存与浏览器行为
- 纠偏（过时说法别背）
  - 「GET 只能传 2KB」——URL 长度是浏览器/服务器实现限制，协议无此规定
  - 「GET 参数不安全」——明文协议下 POST body 同样可见，安全性靠 HTTPS
- 追问：GET 幂等但为什么还有副作用？
  - 埋点上报、日志统计都是 GET 发生副作用，靠约定不靠协议强制

### 6. HTTP 状态码有哪些？重定向几兄弟的区别？

**结论：按 1xx~5xx 五类记代表码；重定向重点分清「永久/临时 × 是否改方法」两个维度。**

- 五大类

| 类 | 含义 | 代表 |
| --- | --- | --- |
| 1xx | 信息性 | 101（WebSocket 协议升级） |
| 2xx | 成功 | 200 / 201（已创建）/ **204（成功无体）** / **206（Partial Content，断点续传）** |
| 3xx | 重定向 | 301/302/303/307/308 / **304（协商缓存命中）** |
| 4xx | 客户端错误 | 400（参数错）/ **401（未认证）** / **403（已认证无权限）** / 404 / **429（限流）** |
| 5xx | 服务端错误 | 500 / **502（网关收到无效响应）** / **504（网关超时）** / 503（过载维护） |

- 重定向五兄弟（高频追问）

| 码 | 永久/临时 | 请求方法 | 场景 |
| --- | --- | --- | --- |
| 301 | 永久 | 可能改为 GET | 域名迁移（浏览器会缓存，慎用） |
| 302 | 临时 | 可能改为 GET | 短链跳转 |
| 303 | 临时 | **改 GET** | PRG 模式防表单重复提交 |
| 307 | 临时 | **保持原方法** | 要求 POST 重定向后仍是 POST |
| 308 | 永久 | 保持原方法 | 301 的「不改方法」版 |

- 高频追问
  - **304 怎么来的？**
    - 请求带 `If-None-Match`/`If-Modified-Since`，服务器校验资源未变返回 304 不带体（详见浏览器原理篇缓存章）
  - 401 vs 403？
    - 401「你是谁」（未登录/凭证无效，触发重新认证），403「我知道你是谁但你不行」（权限不足）
  - 502 vs 504？
    - 502 上游返回了无效响应（进程崩了），504 上游超时没响应

## 三、HTTPS 与实时通信

### 7. HTTP 与 HTTPS 的区别？

**结论：HTTPS = HTTP + TLS——加了加密（防窃听）、完整性校验（防篡改）、证书认证（防冒充），代价是握手延迟与计算开销。**

| 维度 | HTTP | HTTPS |
| --- | --- | --- |
| 传输 | 明文 | TLS 加密 |
| 默认端口 | 80 | 443 |
| 证书 | 不需要 | CA 证书 |
| 性能 | 无加密开销 | 握手多 1~2 RTT + 加解密 CPU |
| 生态 | —— | 搜索引擎加权、现代 Web 标配（HSTS 强制升级） |

- 追问：HTTPS 就完全安全了吗？
  - 证书信任链被破坏（用户装了恶意根证书）、TLS 版本过旧、业务逻辑漏洞（越权）都不归 TLS 管
- 追问：HTTPS 到底「混合」了什么？
  - 非对称加密只用来「安全交换对称密钥」，业务数据全用对称加密——下一题的过程中就能看到

### 8. HTTPS 建立连接的过程？

**结论：TLS 握手 = 证书验明服务器身份 + 非对称加密护送密钥材料 + 两端各自算出同一把对称会话密钥；之后业务数据全走对称加密。**（以 TLS 1.2 经典 RSA 交换为例，TLS 1.3 差异见文末追问）

- 第 1 步：ClientHello（明文，客户端 → 服务器）
  - 内容：支持的 TLS 版本、加密套件列表、客户端随机数 `Client Random`
- 第 2 步：ServerHello + 证书（明文，服务器 → 客户端）
  - 内容：服务器**选定**的 TLS 版本与加密套件、服务端随机数 `Server Random`、**服务器证书**
  - 证书里有什么（X.509）：服务器域名（SAN）、服务器**公钥**、有效期、签发 CA、**CA 数字签名**——证书公开传输，只有公钥没有私钥
  - 签名怎么来的：CA 对证书全部内容哈希出摘要，再用 **CA 自己的私钥**加密这份摘要 = 数字签名——等于 CA 担保「这个域名，公钥就是它」
- 第 3 步：客户端校验证书【身份校验核心，全部通过才继续】
  - 验签名：证书内容重算哈希得摘要 A；用**签发 CA 的公钥**解开数字签名得摘要 B；A = B → 内容未被篡改、确出自可信 CA
  - 验链条：根 CA 公钥（预装在操作系统/浏览器）验中间 CA 证书 → 中间 CA 公钥验服务器证书，逐级验到信任锚，一环失败即断开
  - 附加检查：证书域名（SAN）与当前访问一致、在有效期内、未被吊销（可选）
  - 为什么防住中间人：改证书里的公钥 → 签名对不上；自己伪造证书 → 拿不到可信 CA 的签名，浏览器不认
- 第 4 步：客户端发送预主密钥
  - 内容：本地随机生成的 `Pre-Master Secret`，用第 2 步证书里的**服务器公钥**加密后发出
  - 作用：只有持有对应私钥的真服务器能解开，中间人截获也读不到——密钥材料安全送达
- 第 5 步：两端各自算出会话密钥
  - 内容：`Client Random + Server Random + Pre-Master Secret` → 同一份对称会话密钥
  - 作用：两端本地计算、不经过网络；每次连接密钥都不同，防重放
- 第 6 步：Finished，切换对称加密
  - 内容：双方互发用会话密钥加密的「握手全程摘要」
  - 作用：校验握手数据未被篡改；此后所有 HTTP 报文都用会话密钥对称加密
- 闭环：这个过程怎么解决 HTTP 的问题
  - 防窃听（明文）：业务数据全走对称加密，抓包只能看到密文
  - 防篡改：报文带完整性校验（AEAD 认证标签），改一个 bit 就校验失败
  - 防冒充：第 3 步证书验签 + 证书链，假站拿不出可信签名
- 追问：TLS 1.3 变了什么？
  - 密钥交换改用 **ECDHE**（双方交换临时公钥、各自本地算出密钥，前向安全），不再用 RSA 加密传输预主密钥；握手压缩到 1-RTT——但**证书校验服务器身份的逻辑不变**
- 追问：证书的两个高频误区？
  - 证书**不加密通信内容**：只用来证明身份、分发服务器公钥；真正加密业务流量的是协商出的会话密钥
  - 证书里**没有私钥**：证书公开传输、只含公钥；私钥永远保存在服务器本地，绝不外传

### 9. WebSocket 是什么？和 SSE、轮询怎么选？

**结论：WebSocket 经 HTTP Upgrade 握手后升级为独立的全双工帧协议；SSE 是基于 HTTP 的单向服务器推送；按「单向/双向、消息频率」选型。**

- WebSocket 握手
  - 客户端发 `Upgrade: websocket` + `Sec-WebSocket-Key`，服务器回 **101 Switching Protocols**
  - 之后脱离 HTTP，改用 WebSocket 帧协议（`ws://` / `wss://`）
- 三种实时方案对比

| | 短轮询 | SSE | WebSocket |
| --- | --- | --- | --- |
| 方向 | 客户端拉 | 服务器 → 客户端**单向** | **全双工** |
| 协议 | HTTP | HTTP（`text/event-stream`） | 独立帧协议 |
| 开销 | 高（无消息也重复请求） | 一条长连接 | 一条长连接 |
| 自动重连 | 手写 | ✅ 内置 | 手写（心跳 + 重连） |
| 场景 | 低频状态检查 | 行情/通知/大模型流式输出 | 聊天/协作/游戏 |

- 追问：心跳为什么必须？
  - 中间设备（NAT/网关）会掐空闲长连接；双向 ping/pong 保活并探测断线
- 追问：SSE 为什么近两年又火了？
  - 大模型流式输出的标准载体——HTTP 可过网关/CDN、自带重连，实现成本远低于 WebSocket

## 四、传输层

### 10. TCP 与 UDP 的区别？

**结论：TCP 面向连接、可靠、字节流；UDP 无连接、不可靠、数据报。网页/接口走 TCP，直播/游戏/DNS/QUIC 走 UDP。**

| 维度 | TCP | UDP |
| --- | --- | --- |
| 连接 | 三次握手建立 | 无连接 |
| 可靠性 | 确认重传/排序/去重 | 尽力交付，可能丢/乱/重复 |
| 数据形态 | **字节流**（无消息边界） | **数据报**（一报一达，有边界） |
| 首部 | 20~60 字节 | 固定 8 字节 |
| 拥塞/流量控制 | 有 | 无 |
| 传输效率 | 低（机制换可靠） | 高 |
| 场景 | HTTP/SSH/文件传输 | DNS/视频直播/游戏/QUIC |

- 高频真题：**TCP 连发两个片段、UDP 连发两个数据报，接收端分别收到什么？**
  - TCP：拼成一条字节流，读多少、怎么分界由应用决定（引出粘包）
  - UDP：两个独立数据报，边界完好，但可能乱序/丢失
- 追问：UDP 怎么在应用层做「可靠」？
  - 自己实现确认重传/序号/滑动窗口——QUIC、KCP 就是这么干的

### 11. 三次握手与四次挥手？TIME_WAIT 是什么？

**结论：握手三次同步双方初始序列号并防历史连接；挥手四次因为被动方收到 FIN 后可能还有数据要发（半关闭）；TIME_WAIT 是主动关闭方停留 2MSL 的状态。**

- 三次握手

  ```text
  客户端 SYN(seq=x)              → SYN_SENT
  服务端 SYN+ACK(seq=y, ack=x+1) → SYN_RCVD
  客户端 ACK(ack=y+1)            → ESTABLISHED
  ```

- 为什么不是两次？
  - **防历史连接**（主因）：两次时服务端收到旧 SYN 就得建连；第三次 ACK 让服务端有机会识别并拒绝历史连接
  - **同步双方初始序列号**：双方都要确认「我的 seq 你收到了」
  - 资源角度：两次握手会让服务端为过期请求白建连接（SYN 洪泛温床）
- 四次挥手

  ```text
  主动方 FIN → FIN_WAIT_1
  被动方 ACK → CLOSE_WAIT   ← 此刻被动方仍可发数据（半关闭）
  被动方 FIN → LAST_ACK
  主动方 ACK → TIME_WAIT（2MSL）→ CLOSED
  ```

- 为什么挥手要四次？
  - FIN 只代表「我发完了」；被动方的 ACK 与它自己的 FIN 常不能合并（可能还有数据），所以拆开
- TIME_WAIT 为什么要等 2MSL？
  - 最后一个 ACK 若丢失，对方重发的 FIN 还能被应答
  - 让本连接旧报文在网络中自然消亡，不污染复用的新连接
- 真题追问：**服务器大量 TIME_WAIT 怎么办？**
  - 本质是短连接高频建断——改 HTTP 长连接复用、连接池；内核 `tcp_tw_reuse` 只能缓解
- 追问：SYN 洪泛与 SYN Cookie？
  - 半连接队列打满攻击；SYN Cookie 把状态编码进初始 seq，不占队列

### 12. TCP 如何保证可靠传输？

**结论：四件套——确认重传、序号排序、滑动窗口流量控制、拥塞控制；分别解决「丢、乱、快慢、堵」。**

- 校验与确认重传
  - 校验和查错；ACK 确认；超时重传（RTO 自适应）+ **快速重传**（3 个重复 ACK 立即重传，不等超时）
  - SACK 选择性确认：告诉发送方哪些段已收到，缩小重传范围
- 序号机制
  - 每字节编号 → 排序、去重、确认到哪一字节——字节流有序的基础
- 滑动窗口与流量控制
  - 接收方通告 `rwnd`（可用缓冲），发送方未确认数据不得超过它——**防接收端读不过来**
- 拥塞控制（四算法，防网络堵死）

| 算法 | 行为 |
| --- | --- |
| 慢启动 | cwnd 指数增长（每 RTT 翻倍）到阈值 |
| 拥塞避免 | 过阈值后线性增长 |
| 快速重传 | 3 个重复 ACK → 立即重传丢失段 |
| 快速恢复 | 阈值与 cwnd 减半后线性增长（不回慢启动） |

- 追问：流量控制与拥塞控制的区别？
  - 流量控制管**接收端**（rwnd），拥塞控制管**网络**（cwnd）；实际发送窗口取两者较小值
- 追问：TCP keepalive 与 HTTP keep-alive？
  - TCP keepalive 是空闲探测（默认 2 小时），HTTP keep-alive 是长连接复用——完全是两回事，高频混淆点

### 13. 粘包与拆包是怎么回事？UDP 为什么不粘包？

**结论：TCP 是字节流没有消息边界，两次发送可能被一次读完（粘）或被拆开（拆）；UDP 保留数据报边界所以不存在。**

- 成因
  - 发送端 Nagle 算法合并小包；接收端一次读取缓冲区拿到多包数据；MSS 分段
- 解决：应用层自定义消息边界

  - 固定长度（浪费带宽，少用）
  - 分隔符（如 `\r\n`，内容需转义）
  - **长度前缀**（头部存消息长度，最常用——HTTP 的 `Content-Length` 同理）

- UDP 为什么不粘包？
  - 数据报模式：每个 sendto 就是一个独立报文，一次 recvfrom 对应一条，边界天然保留
- 追问：Nagle 算法与延迟确认？
  - Nagle 攒小包提吞吐、延迟确认攒 ACK，两者叠加放大延迟——实时场景（游戏/协作）要关 Nagle（`TCP_NODELAY`）

## 五、DNS 与 CDN

### 14. DNS 的解析过程？

**结论：多级缓存就近查找，未命中后本地域名服务器递归查询，根/顶级/权威之间迭代查询；日常走 UDP 53。**

- 完整链路
  - 浏览器 DNS 缓存 → 系统缓存/hosts → 本地域名服务器
  - 本地域名服务器未命中 → **递归查询**：替客户端问到底
  - 本地域名服务器 → 根 → .com 顶级 → 权威——**迭代查询**：每级只告诉你「下一步问谁」
- 递归 vs 迭代一句话
  - 客户端 → 本地服务器是递归（帮我查到底）；本地服务器 → 各级是迭代（我自己挨个问）
- 追问：DNS 为什么同时用 TCP 和 UDP？
  - 常规查询/响应走 **UDP 53**（一问一答快）
  - 区域传送（主从同步）与超长响应走 TCP
- 优化关联
  - `dns-prefetch`/`preconnect` 预热（详见 HTML 篇资源提示题）
  - HTTPDNS：绕过运营商 LocalDNS 的劫持与调度不准，App 场景常用

### 15. CDN 的工作原理？

**结论：DNS 调度（CNAME 到全局负载均衡）把用户引到最近边缘节点，边缘命中直接返回、未命中回源并缓存——本质是「就近 + 缓存」。**

- 工作链路
  - 域名 CNAME 到 CDN 调度域名 → GSLB 按地理位置/负载返回最优边缘节点 IP
  - 边缘节点命中 → 直接返回；未命中 → 回源站取，按 Cache-Control 缓存
- 作用
  - 就近访问降延迟、分散源站压力、天然抗部分流量攻击
- 追问：怎么让 CDN 静态资源「更新即生效」？
  - 文件名带 contenthash + `Cache-Control: max-age=31536000, immutable`——URL 变了缓存自然失效（构建工具 hash 命名的由来）
- 追问：动态内容怎么加速？
  - 动态加速（路由优化/链路复用/协议优化），不是靠缓存——静态缓存、动态走优化链路
- 追问：缓存没更新怎么强制处理？
  - CDN 控制台 URL/目录刷新（purge）；上线前可用预热（preload 推边缘）
