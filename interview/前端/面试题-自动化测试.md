# 面试题 · 自动化测试（全覆盖版）

> 高频常考为主。红线：不提「19 个测试文件 / 覆盖率 80% / 已接入 CI 门禁」（未落地的方案目标值）；CI 概念可讲，别声称已落地。

## 一、策略与理念

**Q1：为什么要做自动化测试？投入产出怎么算？**
- 回归成本随项目变大线性涨，手工回归不可持续；金融场景错误代价高
- 权衡：优先覆盖「高频回归 + 资金相关 + 稳定逻辑」，不为覆盖率数字写测试

**Q2：测试金字塔？**
- 单元（多、快、稳）→ 集成/组件（中）→ E2E（少、慢、脆）
- 反模式：倒金字塔全靠 E2E——慢、flaky、定位难

**Q3：TDD / BDD 了解吗？**
- TDD：先写测试再实现（红→绿→重构），适合逻辑边界清晰的模块；BDD：行为驱动、用例即规格（Given/When/Then）
- 实践上不必教条：金融规则（试算）先对齐行为再写实现，思路接近 TDD

## 二、单元与组件测试

**Q4：Vitest 和 Jest 的区别？**
- Vitest：与 Vite 共用配置与转换管线（esbuild，快）、原生 ESM、API 与 Jest 高度兼容迁移成本低
- Jest：生态成熟、快照/覆盖率工具齐全；新 Vite 项目默认选 Vitest

**Q5：单测写什么？怎么写好断言？**
- 纯函数：边界值、等价类、非法输入（试算：0 期/最大期数/非法还款方式）
- 组件：契约测试——props in → 渲染结果，交互 → emit 出什么；不测内部实现细节
- AAA 结构：Arrange 准备 → Act 触发 → Assert 断言；一个用例一个关注点

**Q6：mock 有哪些层次？**
- 网络层：mock api 模块或用 MSW 拦截（更接近真实）
- 模块层：vi.mock/jest.mock 替换依赖模块；时间：useFakeTimers 控制定时器
- 原则：mock 边界放在「你控制不了的依赖」上，别 mock 被测对象内部

**Q7：异步逻辑怎么测？**
- await 断言（waitFor / findBy）；fake timer 推进 setTimeout；Promise 状态断言 rejects/toThrow
- 组件异步渲染用 findByXxx 等待出现，避免 sleep

**Q8：快照测试什么时候用？**
- 适合结构稳定、变化需显式审查的（组件渲染结构、配置生成结果）
- 坑：滥用后变成「无脑 update 快照」，失去断言意义——核心字段还是显式断言

**Q9：Vue 组件测试的工具与要点？**
- @vue/test-utils：mount/shallowMount、wrapper.find、emitted()
- 全局插件/指令/路由要挂桩；异步组件配合 flushPromises

## 三、E2E

**Q10：Cypress vs Playwright？**
- Cypress：浏览器内运行、时间旅行调试、开发体验好；跨域/多 tab 受限
- Playwright：Chromium/Firefox/WebKit 全覆盖、多 tab/iframe 强、自动等待、trace 截图录像
- 选型：内部 Web 主流程回归 Cypress 够用；跨浏览器与复杂场景 Playwright

**Q11：E2E 用例怎么设计？flaky 怎么治理？**
- 覆盖主流程与关键分支，不追求穷举（那是单测的活）
- 稳定性：等待状态不 sleep；测试数据固定与隔离；用例独立可单跑；失败重试 + trace 定位
- Page Object 模式：页面操作封装成类，用例只写业务动作，元素变更只改一处

## 四、度量与工程

**Q12：覆盖率指标怎么看？**
- 语句/分支/函数/行四指标；分支覆盖比行覆盖更能暴露漏测的 if 路径
- 正确用法：看「关键模块有没有漏」而不是追全局数字；为指标写测试是反模式

**Q13：CI 里怎么集成测试？**
- 阶段：lint → 单测 → 构建 → E2E（或 E2E 独立定时跑）；失败阻断合并
- 分层执行：单测每次提交跑，E2E 只在合并主分支跑（控制时长）
- 口径注意：可以讲方案与行业做法；别声称当前项目已接 CI 门禁

**Q14：AI 在测试流程里的角色？**
- 人负责：评审断言是否符合业务规则、补边界场景——AI 提效生成，不决定测试范围
