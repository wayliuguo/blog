# 面试题 · 自动化测试（高级前端）

> 口径红线：可讲方案与行业做法；不声称「覆盖率 80% / 已接 CI 门禁」等未落地的数字。

## 一、基础概念

### 1. 前端自动化测试有哪些分类？单元 / 集成 / E2E 的区别与适用场景？

**结论：按测试对象与成本分三层——单元测「逻辑」、集成测「组件协作」、E2E 测「完整用户旅程」；分派的判据是风险驱动：每一类 bug 指定一个主责层，同一条路径不三层重复维护。**

| 层 | 测什么 | 特点 | 适用场景 |
| --- | --- | --- | --- |
| 单元 | 纯函数、校验、计算、reducer | 快（毫秒）、稳、便宜 | 逻辑有分支、边界多的代码 |
| 集成（组件） | 组件树 + 请求 + store 的协作 | 中速，贴近用户视角 | 表单、交互状态、异步渲染 |
| E2E | 真浏览器里的完整旅程 | 慢、贵、易 flaky | 登录、下单、发布等关键路径 |

- 反模式：冰激凌筒（全靠 E2E，慢、flaky、定位难）、纯 shallow 单测高覆盖低信心
- 追问：一个 bug 三层都能拦，放哪层？
  - 放「最便宜且能诚实拦住它的那层」——价格算错单测拦（毫秒级）；按钮点了没反应集成拦；支付流程断掉 E2E 拦

### 2. 什么是 TDD、BDD？区别与落地？

**结论：TDD 是红→绿→重构的节奏（测试先行），适合逻辑边界清晰的模块；BDD 用 Given/When/Then 让用例即规格、业务方可读；实践不必教条，但测试先行有个隐藏价值——写不出测试往往说明接口还没想清楚。**

- TDD：先写测试再实现，迫使先定义行为契约；适合资金计算、校验规则
- BDD：面向行为描述（Given 某状态 / When 操作 / Then 结果），用例即需求文档
- 现实折中：核心规则 TDD 先行，UI 集成测试事后补——需求高频变动时严格 TDD 维护成本不划算
- 追问：TDD 落地最大阻力？
  - 需求本身在变，先写的测试跟着改；只对「稳定的规则」做测试先行

### 3. 自动化测试的价值是什么？什么时候引入，什么时候没必要？

**结论：价值是「改代码的底气」——回归拦截、重构安全网、活文档；真实度量是 escaped defects（漏到线上的 bug），不是用例数和覆盖率；长期演进的项目尽早引入，一次性活动页、高频变动原型不值得。**

- 价值三面
  - 回归拦截：改动破坏既有功能立刻红——手工回归成本随规模线性涨且不可重复
  - 重构安全网：不改行为的重构不担心
  - 活文档：用例即行为规格
- 优先覆盖：高频回归路径 + 资金权限逻辑 + 稳定核心逻辑
- 不值得的场景：一次性脚本、纯视觉调整、三天两头推翻重来的原型——维护成本超过收益
- 追问：怎么向团队证明价值？
  - 用数据：手点一次全量回归要多久、历史上漏测事故的代价——不是讲理念

### 4. 什么是测试金字塔？前端视角怎么理解？

**结论：金字塔（单元多、E2E 少）是成本模型；前端修正版是测试奖杯——组件不渲染子树、不打真实请求时「说了谎」，所以前端测试重心在集成层；静态检查（tsc / lint / a11y lint）是免费地基。**

| 形态 | 重心 | 前端适配问题 |
| --- | --- | --- |
| 金字塔 | 单元层最重 | 组件 shallow 单测跑过却断言不出真实问题——高覆盖低信心 |
| 奖杯 | 集成层最重 | 组件 + 真实子树 + MSW，更贴近用户视角 |

- 前端完整分层（从便宜到贵）：静态检查 → 单元（纯逻辑）→ 集成（组件 + MSW）→ E2E（关键旅程）
- 参考配比：集成 60~70%、单元 20~30%、E2E 5~10%——按自己项目的 bug 历史调整
- 追问：什么项目金字塔形态反而对？
  - 工具库、SDK——纯逻辑占大头，几乎没有 UI 集成可测

### 5. 什么是断言？断言失败代表什么？

**结论：断言是把「预期行为」写成可执行判断的语句——断言失败代表「代码的实际行为与预期不符」；它只能证伪不能证真，而没有断言的测试等于没测。**

- 本质：`expect(实际).toBe(预期)`——把「这里应该是什么」钉进代码
- 两个方向都要断言：正确路径的结果 + 错误路径（非法输入抛错、401 的提示）
- 覆盖率只记录「代码执行过」，不检查断言对不对——跑过但没 expect 的测试照样贡献覆盖率、照样漏 bug
- 追问：断言会不会写错？
  - 会，而且是最隐蔽的坑：把 bug 行为断言成「预期」（AI 生成测试的高发区）；验收土办法是改坏实现看测试红不红

### 6. 什么是 Mock？为什么测试里需要 mock？

**结论：mock 是用「受控的替身」替换真实依赖，让测试只关注被测对象本身——控制输入（返回固定数据）、隔离不确定性（网络、时间）、加速（不打真接口）。**

- 为什么需要
  - 依赖不可控：接口挂了 / 返回变化，测试不该跟着挂
  - 场景造不出来：401、500、超时——真实环境很难稳定复现
  - 速度：单测里打真实接口，套件从秒级变分钟级
- mock 该放的边界：「跨进程、你控制不了的依赖」——网络、时间、第三方 SDK；别 mock 被测对象内部
- 代价：mock 越多测试离真实越远——mock 的返回与真实行为漂移时，测试在保护一个不存在的世界
- 追问：所有依赖都 mock 掉行不行？
  - 不行，那就只剩「测试代码自己」——集成层的价值就在于少 mock，抓组合错误

## 二、单元测试（Jest + Vitest）

### 7. Jest 和 Vitest 怎么选型？

**结论：新 Vite 项目默认 Vitest（与 Vite 共用配置与转换管线、原生 ESM、API 与 Jest 高度兼容）；Jest 留给存量成熟套件和 React Native。**

| 维度 | Vitest | Jest |
| --- | --- | --- |
| 转换管线 | 复用 Vite（esbuild），dev 按需转换，快 | 自带转换（babel / ts-jest） |
| ESM | 原生 | 需要 transform 折腾 |
| 配置 | 与 vite.config 共享插件 | 独立配置 |
| 生态 | 快速成熟 | 最成熟 |

- 迁移成本低：describe / it / expect 基本同 API，主要替换 `jest.mock` → `vi.mock`
- 追问：Vitest 快在哪？
  - dev 模式只转换「当前要跑的文件」+ 与 Vite 共用插件管线

### 8. 单元测试适合测什么，不适合测什么？

**结论：适合测「逻辑确定、边界多、坏了能断言」的纯逻辑；不适合测 DOM 细节、样式、框架自身行为——那些交给集成层和 E2E。**

- 适合：解析器、格式化、校验规则、价格计算、reducer、工具函数（边界值 / 等价类 / 非法输入）
- 不适合
  - 测框架：`v-if` 会不会隐藏元素是 Vue 的事
  - 测样式与视觉：那是视觉回归的活
  - 重新实现 DOM 行为：shallow 单测里手写 DOM 假设，脆且无意义
- 追问：一段代码值不值得写单测的判据？
  - 坏了用户能感知吗？逻辑有分支吗？改它害怕吗？——三个都不是就不测

### 9. describe、it、expect 各自的作用？

**结论：describe 是分组（同一行为的用例集合 + 钩子作用域），it 是一条用例（一个行为断言），expect 是断言入口——三者构成「组织 → 描述 → 验证」的骨架。**

```js
describe('formatMoney', () => {
  it('千分位并保留两位小数', () => {
    expect(formatMoney(1234567.891)).toBe('1,234,567.89')
  })
})
```

- 组织纪律：一个 describe 对应一个行为域；测试名说行为（「满 100 才打折」），不是 `test1`
- 追问：describe 嵌套有实际用处吗？
  - 有——钩子作用域跟随嵌套（内层 beforeEach 先于外层执行），用于分层准备前置

### 10. 常用断言 API？toBe 和 toEqual 的区别？

**结论：toBe 用 `Object.is` 比较（引用相等，`{a:1} !== {a:1}`）；toEqual 深比较结构内容——对象数组断言用 toEqual，原始值用 toBe。**

| API | 用途 |
| --- | --- |
| `toBe` | 原始值 / 引用相等（Object.is） |
| `toEqual` | 深比较结构（不看引用） |
| `toStrictEqual` | 深比较 + 类型 + undefined 属性也查 |
| `toContain` | 数组含元素 / 字符串含子串 |
| `toThrow` | 抛错断言（可传消息匹配） |
| `toHaveBeenCalled*` | mock 调用次数 / 入参 |
| `rejects.toThrow` | Promise 拒绝路径 |

- 追问：`toEqual({a: 1, b: undefined})` 和 `toEqual({a: 1})` 相等吗？
  - toEqual 相等（忽略 undefined 属性），toStrictEqual 不相等——严格校验用后者

### 11. 测试钩子 beforeEach / afterEach / beforeAll / afterAll 的使用场景与区别？

**结论：beforeEach / afterEach 每条用例前后跑（保证用例隔离），beforeAll / afterAll 每个套件跑一次（放贵且只读的前置）；判断标准——「用例间必须重置的」放 Each，「建一次大家共用」的放 All。**

| 钩子 | 频率 | 典型用途 |
| --- | --- | --- |
| beforeAll | 每套件一次 | 建数据库连接、起 MSW server |
| beforeEach | 每用例前 | 重置 mock、清 localStorage、seed 数据 |
| afterEach | 每用例后 | `vi.restoreAllMocks`、cleanup 渲染 |
| afterAll | 每套件后 | 关连接、停 server |

- 隔离纪律：能放 beforeEach 的别偷懒放 beforeAll——共享可变状态是 flaky 第一根因
- 追问：beforeEach 里最常被漏掉的恢复是什么？
  - mock 与 fake timers 的恢复（`restoreAllMocks` / `useRealTimers`）——泄漏到后面的用例就是偶发失败

### 12. 什么是快照测试？原理、优缺点与坑？

**结论：快照把「输出序列化后存成基准文件」，下次对比——适合结构稳定、变化需显式审查的产物；核心坑是「无脑 update」让断言退化为「变了」而不是「对不对」。**

- 原理：首次运行把结果写入 `.snap` 文件，之后每次运行与基准 diff，不一致即红
- 适合：组件渲染结构、生成的配置 / 代码、序列化结果
- 坑
  - 大快照没人真看 → 全 approve → 只剩「变了」没有意义
  - 核心字段（价格、状态码）必须显式断言，不靠快照混过
- 追问：快照红了的标准处理？
  - 先判断 bug 还是预期变化：bug 修代码；预期变化人工看 diff 才 `--update`，且更新进 code review

### 13. 如何 mock 函数？如何校验调用次数与入参？

**结论：`vi.fn` 造替身函数，能定制返回并记录每次调用——`mockReturnValue / mockResolvedValue` 定制结果，`toHaveBeenCalledWith` 校验入参，`toHaveBeenCalledTimes` 校验次数；替身家族按「替什么」选：spy 包真实对象、fn 纯替身、mock 替换模块。**

```js
const onChange = vi.fn()
mount(Select, { props: { onChange } })
await wrapper.find('option').trigger('click')
expect(onChange).toHaveBeenCalledTimes(1)
expect(onChange).toHaveBeenCalledWith('beijing')
```

| 替身 | 行为 | API |
| --- | --- | --- |
| spy | 真实逻辑照跑，记录调用 | `vi.spyOn(obj, 'm')` |
| mock / stub | 替换实现，真实逻辑不跑 | `vi.fn().mockReturnValue(x)` |
| fake | 轻量真实现（内存库） | 自建 |

- 纪律：`beforeEach` 恢复（`vi.restoreAllMocks`）；mock 边界放依赖上，不 mock 被测对象内部
- 追问：spy 和 mock 什么时候混用？
  - `spyOn(obj, 'm').mockReturnValue(x)`——保留 afterEach 恢复能力，又能定制返回

### 14. 如何 mock 模块与第三方依赖？

**结论：`vi.mock('模块路径')` 在模块系统层整体替换——适合工具库、SDK 这类「被 import 进来的依赖」；但网络请求优先用 MSW 拦在网络层，比 mock 请求库更真实且一份 handlers 多处复用。**

- 模块层

```js
vi.mock('./analytics', () => ({ track: vi.fn() }))
import { track } from './analytics'
```

- 网络层（优先）：MSW 拦 fetch/XHR，组件代码原样跑，handlers 单一事实来源——单测、Storybook、E2E、dev 共用
- 两层的分工：非 HTTP 依赖（本地存储、埋点 SDK、路由）用 `vi.mock`；HTTP 交互用 MSW——mock 的是「HTTP 语义」而不是某个函数
- 追问：mock axios 和 MSW 的本质区别？
  - mock axios 锁死请求库（换 fetch 全重写）且组件网络栈没参与；MSW 与请求库无关，序列化、状态码全真实

### 15. 定时器怎么 mock？

**结论：用假定时器（`vi.useFakeTimers`）把「等时间」变成「跳时间」——防抖、节流、倒计时的标配；配套 `setSystemTime` 冻结日期，避免用例依赖「现在」。**

```js
vi.useFakeTimers()
it('防抖 300ms 只执行一次', async () => {
  const fn = vi.fn()
  const debounced = debounce(fn, 300)
  debounced(); debounced(); debounced()
  expect(fn).not.toHaveBeenCalled()
  vi.advanceTimersByTime(300)
  expect(fn).toHaveBeenCalledTimes(1)
})
```

- 推进方式：`advanceTimersByTime(ms)`（跨到指定时刻）、`advanceTimersToNextTimer()`（跳到下一个排队任务）
- 收尾恢复：`afterEach` 里 `vi.useRealTimers()`——假定时器泄漏是最常见的连环 flaky 源
- 追问：假定时器和 `await` 混用有什么坑？
  - 微任务不会被假定时器推进——交错场景用 `advanceTimersByTimeAsync` 或手动 flush

### 16. 异步代码怎么写单元测试？

**结论：等条件、不等时间——Promise 用 await 断言，组件异步渲染用 findBy 自动重试，定时器用假定时器推进；sleep 在异步测试里没有合法位置。**

- Promise：`await expect(p).rejects.toThrow()`；成功路径直接 `await` 后断言
- 组件异步渲染：`await screen.findByText(...)`（findBy = getBy + 轮询等待）；断言「消失」用 `queryBy`（找不到返回 null）
- 定时器型异步：见上一题假定时器
- 追问：`waitFor` 一直超时排查什么？
  - 断言条件写错（永远为真/假）、mock 没生效（真请求穿透）、事件没触发（userEvent 没 await）

### 17. 单元测试覆盖率是什么？四个指标的含义？

**结论：覆盖率只记录「哪些代码被执行过」，不检查断言对不对；四种口径里分支覆盖最有信息量。**

| 口径 | 统计什么 | 特点 |
| --- | --- | --- |
| 语句 | 每条语句是否执行过 | 最粗，`if` 只走一个分支也算覆盖 |
| 行 | 每行是否执行过 | 报表最常见 |
| 分支 | if / switch / 三元 / 短路每个分支 | 最有信息量，数字通常最低 |
| 函数 | 每个函数是否被调用过 | 只看调没调 |

- 为什么分支覆盖最有信息量：`if (a && b)` 执行过一次，行覆盖就 100%，但「a 假」「b 假」「a&&b 真」三条路径未必都走过
- 两种实现：v8（免插桩、快、分支粒度粗）vs istanbul（插桩、慢、细、可比性好）——选哪个都行，**不要中途换**，否则趋势图断了
- 追问：行覆盖 100% 意味着什么？
  - 几乎什么都不意味着——分支走全没走全、断言有没有意义才是关键

### 18. 覆盖率是不是越高越好？为什么不能盲目追 100%？

**结论：不是——覆盖率衡量「执行过」不衡量「断言对了」，跑过但没断言的代码照样贡献覆盖率、照样漏 bug；覆盖率是地图不是证明。**

- 例子：VIP 折扣本该「满 100 才生效」，实现漏了判断——测试把函数跑一遍没断言折扣值，覆盖率全绿，线上出错
- 盲目追 100% 的两个恶果
  - 逼出断言空转（跑一遍、不 expect）
  - 逼出为数字写的垃圾测试（getter/setter 全覆盖）
- 正确用法：看「关键模块有没有漏」（当地图用）+ 增量覆盖率防劣化（见 CI 组）
- 识别造假的土办法：看断言密度；进阶用变异测试——故意改坏一行，看测试红不红
- 追问：变异测试是什么？
  - 自动制造微小变异（`>` 改 `>=`），变异活下来 = 测试有洞——直接度量「能不能抓 bug」

## 三、组件测试（Testing Library / Vue Test Utils）

### 19. 组件测试和纯函数单元测试的区别？

**结论：纯函数「输入→输出」确定可纯断言；组件是有状态的协作单元——涉及渲染、DOM、生命周期、异步、事件，所以测法从「断言返回值」变成「断言契约：props in → 渲染 out，交互 in → emit out」。**

- 三个差异
  - 环境依赖：组件要挂载（DOM 环境、全局插件、路由）
  - 异步性：请求、nextTick、过渡——要等条件
  - 验证方式：不是函数返回值，而是「用户能看见什么、组件吐出什么事件」
- 契约三问：给什么渲染什么？操作后 emit 什么？边界（空数据、超长文本）显示什么？
- 追问：为什么不测组件内部 state？
  - 用户感知不到 state，只感知渲染结果与交互反馈——测 `isLoading` 没意义，测「按钮变 loading 且禁点」才是契约

### 20. Testing Library 核心思想「测行为不测实现」怎么理解？

**结论：像用户一样使用组件——通过「用户能找到、能操作」的入口（role、label、文本）查询和交互，断言用户能看见的结果；不用内部 state、实现类名、组件实例做断言依据。**

- 查询优先级 = 越接近「用户怎么找到它」越好

| 查询 | 适合 | 风险 |
| --- | --- | --- |
| `getByRole('button', { name })` | 首选——顺带 a11y 断言 | 无可访问名称会找不到（可能正是 bug） |
| `getByLabelText` | 表单控件首选 | — |
| `getByText` | 文本按钮 | 多处匹配歧义 |
| `getByTestId` | 兜底 | 与用户视角脱钩 |

- 三个前缀：`getBy` 找不到或多个都抛错（暴露歧义）；`queryBy` 返回 null（断言不存在）；`findBy` 自动等待（异步）
- `getByRole` 失败本身有价值：不是真 button、没有可访问名称、被 aria-hidden——都是真实可用性问题
- 判断标准：不改行为的重构让测试红了 = 测了实现
- 追问：为什么 class 选择器是反模式？
  - 实现细节：改样式就红，且不表达用户视角

### 21. Vue Test Utils 的 mount 和 shallowMount 区别与适用场景？

**结论：mount 渲染完整子树（集成优先、默认选它），shallowMount 把子组件替换为桩（只测当前组件自身逻辑）——shallow 只在「子树重且已有自己的测试」时用。**

- mount：能测父子契约（插槽渲染、子组件 emit 的传播）——更接近真实
- shallowMount：快，但子组件契约没测到，高覆盖低信心的主要来源
- 全局依赖挂桩：mount 的 `global.plugins` / `global.directives` / `global.provide` 配置最小真环境，而不是 mock 组件内部
- 追问：shallow 后想断言子组件被渲染了怎么办？
  - `findComponent` 断言存在性——但记住这只测了「挂没挂」，不测协作行为

### 22. 如何测试组件的 props 和 emit 事件？

**结论：props 从外注入断言渲染结果，事件用 emitted() 断言「交互后吐出了什么、带了什么参数」——两者合起来就是组件的输入输出契约。**

- props：改变 props 断言可见输出变化（`await wrapper.setProps({ loading: true })` → 按钮禁用）
- emit

```js
const wrapper = mount(Counter)
await wrapper.find('button').trigger('click')
expect(wrapper.emitted('change')?.[0]).toEqual([1])
```

- `emitted('change')` 是按次序的参数数组——断言参数内容而不只是「被调用过」
- 追问：为什么要断言 emit 的参数？
  - 父组件消费的是参数；只断言「有事件」测不住契约——参数错了父组件照样坏

### 23. 如何测试用户交互（点击、输入）？

**结论：用 userEvent（或 trigger 模拟真实事件序列）驱动交互，断言可见结果——点击用 click、输入用 type（逐键触发 input 事件），不直接改 DOM 值。**

```js
const user = userEvent.setup()
await user.type(screen.getByLabelText('手机号'), '13800000000')
await user.click(screen.getByRole('button', { name: '提交' }))
expect(await screen.findByText('提交成功')).toBeInTheDocument()
```

- Vue 侧：`wrapper.find('input').setValue(x)`、`trigger('click')`——trigger 返回 Promise，必须 await（等 nextTick）
- userEvent 模拟真实键鼠：会触发 focus、键盘事件链——fireEvent 直改事件测不出组合行为
- `userEvent.setup()` 放 beforeEach：每用例独立实例，防内部计时器泄漏
- 追问：为什么 fireEvent 不推荐？
  - 它只派发单个事件，跳过了真实输入的中间过程（composition、逐字符）——v-model 这类依赖 input 事件的机制测不全

### 24. 怎么测试异步渲染组件（接口请求后渲染）？

**结论：mock 网络层（MSW）+ 等条件断言——请求后出现的内容用 findBy 等「出现」，loading 消失用 queryBy 等「不存在」，绝不 sleep。**

```js
it('请求失败显示错误文案', async () => {
  server.use(http.get('/api/list', () => HttpResponse.json({ msg: '挂了' }, { status: 500 })))
  render(List)
  expect(await screen.findByText('挂了')).toBeInTheDocument()
})
```

- 中间态也值得断言：提交后 loading 出现（按钮禁用）→ 最终结果出现，两段都等条件
- Vue 侧配 `flushPromises` 清微任务队列
- 追问：`findByText` 和 `getByText` + `waitFor` 什么关系？
  - `findBy = getBy + waitFor`——等价语法糖，写哪个都行，关键是别写 sleep

### 25. 自定义 Hook（组合式函数）怎么单测？

**结论：Hook 依赖组件运行上下文（响应式、生命周期），不能当普通函数直接调用——必须挂在宿主环境里测：React 用 renderHook，Vue 用 @testing-library/vue 的 renderHook 或宿主组件包裹。**

- React：`renderHook(() => useCounter())` + `act` 驱动更新 + `result.current` 断言状态
- Vue：组合式函数用 `effectScope` / 宿主组件挂载后断言 ref 值变化；带生命周期（onMounted）的逻辑必须真实挂载
- 测什么：状态初值、动作后状态变化、边界（依赖外部参数时的分支）
- 追问：为什么不能直接调用 hook 函数测？
  - `setup` 外调用拿不到响应式上下文与生命周期——结果和运行时不一致，测了个寂寞

### 26. 组件测试中 ref 和 slot 怎么处理？

**结论：ref 优先通过 DOM 行为断言（直接戳 `wrapper.vm` 是测实现），必须摸实例时用 findComponent 限定范围；slot 测「注入的内容被正确渲染在正确位置」。**

- ref：能断言可见行为就别碰实例——`wrapper.find('input').element.value`；确需实例时 `wrapper.vm` 但知道这是实现耦合
- slot：mount 时传 `slots: { default: '<p>x</p>' }`，断言注入内容出现在预期容器里；具名插槽同理
- 共同原则：slot 是 props 的另一种契约（内容注入），测「渲染结果」不测「分发实现」
- 追问：直接断言 `wrapper.vm.count` 的问题是什么？
  - 改名或改成 computed 存储测试就红——行为没变测试挂了，就是实现耦合

### 27. 组件测试里 flaky 的常见原因？

**结论：与 E2E 同源——共享可变状态、不等条件、时间依赖、渲染未收口；治法也同源：每用例重置、等条件断言、冻结时间。**

- 高频清单
  - store / 单例在用例间共享可变状态 → beforeEach 重置
  - 断言跑在 nextTick / 微任务之前 → `await trigger()` / `flushPromises` / findBy
  - 假定时器没恢复 → afterEach `useRealTimers`
  - 全局插件（路由、i18n）状态残留 → 每用例 fresh mount
- 复现手段：随机顺序跑 + `--repeat-each`，把偶发变必现
- 追问：组件层比 E2E 层 flaky 更少，为什么？
  - 没有 网络 / 浏览器 / 环境三大不确定源——组件层 flaky 基本都是「自己写的时序假设」

## 四、E2E 端到端测试（Cypress / Playwright）

### 28. Cypress 和 Playwright 的对比与选型？

**结论：新项目默认 Playwright（跨浏览器、多 tab/iframe、并行分片、trace 生态全）；已有 Cypress 深度投入且场景简单的，不必为迁移而迁移。**

| 维度 | Cypress | Playwright |
| --- | --- | --- |
| 架构 | 测试代码跑在浏览器内 | 浏览器外协议驱动 |
| 跨浏览器 | 免费版受限 | Chromium / Firefox / WebKit 全覆盖 |
| 多 tab / iframe | 受限 | 原生支持 |
| 自动等待 | 有 | locator 级，更彻底 |
| 调试 | 时间旅行体验好 | trace viewer（截图 + 网络 + 控制台回放） |
| 并行分片 | 收费或外挂 | 内置 workers + sharding |

- 追问：Cypress 为什么多 tab 受限？
  - 测试代码和应用跑在同一个浏览器页面里，切 tab 就失去对应用的控制；Playwright 在浏览器外协议驱动，没有这个限制

### 29. E2E 测试的原理？运行在真实浏览器吗？

**结论：运行在真实浏览器——Playwright 用改造过的浏览器内核 + 协议（类 CDP）在浏览器外驱动，Cypress 把测试代码注入浏览器内运行；两者驱动真实渲染、真实网络、真实存储，这是 E2E 价值的来源。**

- Playwright：微软定制内核构建，协议直连浏览器——能开多 context、多 tab、拦截网络
- Cypress：测试代码与应用同页运行——因此同源、单 tab 受限
- 与 Selenium（WebDriver 协议）的差异：Playwright 走私有协议，速度快、等待内建
- 真实浏览器意味着：渲染、JS、cookie、storage 全真——也意味着慢和环境敏感
- 追问：E2E 为什么不能完全替代单测？
  - 最贵且最难定位——单测毫秒级定位到行，E2E 挂了只知道「旅程断了」

### 30. E2E 适合测什么场景？优缺点？

**结论：只守「花钱的路径」——登录、下单、发布、上线 smoke；优点是端到端真实性（唯一能证明「整个系统拼起来能用」的层），缺点是慢、贵、易 flaky、定位粗。**

- 用例设计：一条用例 = 一个完整用户旅程 = 一个失败原因
- 优点：全栈真实性（前端 + 后端 + 数据库）、用户视角
- 缺点：分钟级、维护贵、挂了不知道哪层坏了
- 反模式：几百条 E2E、没有单测的冰激凌筒；边界值塞进 E2E（单测的活）
- 追问：E2E 套件规模多少合适？
  - 全量在一杯咖啡时间内跑完——超了拆 smoke / 全量两级

### 31. Playwright 多浏览器、多页面、并发的原理？

**结论：内核级协议支持多浏览器矩阵（projects 配 chromium/firefox/webkit）；隔离单位是 context（类隐身会话，每用例一个）；并发靠 worker 进程 × context + CI 分片。**

| 层 | 是什么 | 隔离性 |
| --- | --- | --- |
| browser | 浏览器实例，最贵 | 全局复用 |
| context | 独立会话（cookie / storage / 权限） | 每用例一个，便宜 |
| page | 一个标签页 | context 内 |

- 并行：`fullyParallel` + `workers`（每 worker 独立进程独立 context）——天然隔离互不污染
- 分片：`--shard=1/3` 切套件多台 CI 并行，时长除以 N
- 多页面：一个 context 开多个 page（多 tab 场景）
- 追问：为什么隔离用 context 而不是新开 browser？
  - context 毫秒级创建，browser 秒级——隔离粒度和成本的平衡点

### 32. 什么是 flaky test？产生原因和解决办法？

**结论：同一代码时而绿时而红——flaky 不是玄学，绝大多数可归到可复现根因；治法是根因对号 + 隔离流程，重试只是诊断不是修复。**

| 根因 | 典型症状 | 修法 |
| --- | --- | --- |
| sleep 赌时间 | 慢机器 / CI 偶发失败 | 等条件（自动等待 / findBy） |
| 共享可变状态 | shuffle 顺序后时红时绿 | beforeEach 重置 / 独立构造 |
| 依赖「现在」 | 每天固定时段红 | 时间注入 + 固定系统时间 |
| 时区 | 本地好 CI 红 | 固定 `TZ` / 统一 UTC |
| 顺序依赖 | 单跑绿全量红 | 每用例全量前置 |
| 并行冲突 | 多 worker 才红 | worker 唯一账号 / 数据前缀 |
| 真实网络/环境 | 依赖外部服务时红 | MSW / route 拦截 / 挡板 |

- 治理流程：标记 → 隔离（quarantine，带 owner + 到期日）→ 修复根因 → 回归主套件；超期删除或重写
- 复现手段：`--repeat-each=20`、随机顺序——偶发变必现才能修
- 追问：「重试 3 次就绿」算修好吗？
  - 不算——根因还在只是被藏起来，而且重试烧 CI 且钝化信号

### 33. E2E 如何做网络 mock、拦截接口？

**结论：Playwright 用 `page.route` 拦截匹配 URL 的请求返回受控响应——造 401/500/慢响应不用改后端；与单元层的 MSW 分工：MSW 管「代码内」的单测/组件，route 管「真浏览器」的 E2E。**

```js
await page.route('**/api/list', route =>
  route.fulfill({ status: 500, body: JSON.stringify({ msg: '挂了' }) })
)
```

- 典型用途：错误态、空数据、慢响应（`delay`）、第三方依赖挡板（支付、地图）
- 也可反向用：`route.abort()` 模拟断网
- 追问：E2E 全拦截 mock 掉，还叫端到端吗？
  - 主流程走真实后端才是 E2E 的意义——拦截只用于「造不出来的异常分支」和外部依赖

### 34. E2E 的等待怎么做？为什么不推荐硬编码 sleep？

**结论：等状态不等时间——Playwright 的 locator 操作前自动等待（可见、可点、可编辑），断言 `expect(locator).toBeVisible()` 内建轮询；sleep 是赌固定时长，慢环境必炸、快环境白等。**

- 自动等待三处：操作（click/fill 前）、断言（toHaveText 轮询到超时）、显式等（`waitForURL`、`waitForSelector`）
- sleep 的双重伤害：CI 慢机器上不够长 → flaky；本地机器上太长 → 套件白白变慢
- `waitForLoadState('networkidle')` 的坑：长轮询 / SSE 页面永不 idle——等具体元素出现更可靠
- 追问：自动等待也失败了说明什么？
  - 元素真没出现——业务 bug、接口错误，或等待条件与业务不符（等一个被骨架屏替换的节点）

### 35. 元素定位方式：css 选择器、data-testid 怎么选？

**结论：优先级按「贴近用户视角」排——role / label 优先（顺带测 a11y）→ 文本 → data-testid 兜底；纯 css / class 是实现细节，禁止做主定位。**

| 方式 | 评价 |
| --- | --- |
| `getByRole` / `getByLabel` | 首选：语义强、顺带 a11y、抗样式重构 |
| 文本 | 可用但多语言 / 文案改动会挂 |
| `data-testid` | 兜底：无语义元素、文案多变时专用 |
| css / class | 实现细节，改样式就红，禁用 |

- data-testid 的正确用法：加在「稳定的测试契约点」上，配合规范（如 `data-testid="login-submit"`），不是到处撒
- 组件层与 E2E 层同一套优先级——定位器是测试的公共契约
- 追问：data-testid 会不会污染生产 DOM？
  - 会多一点属性，但代价远小于 flaky；介意可在构建时按环境剔除

### 36. E2E 如何处理弹窗、路由跳转、文件上传？

**结论：三类特殊交互各有专用 API——原生弹窗挂 dialog 事件、路由断 URL 并 waitForURL、上传用 setInputFiles；共同点：先挂监听再触发动作。**

- 弹窗：`page.on('dialog', d => d.accept())`——Playwright 对原生 confirm/alert 默认自动 dismiss，要 accept 必须先注册监听
- 路由跳转：`await page.click(...)` 后 `await page.waitForURL('**/home')` + `expect(page).toHaveURL(...)`——SPA 内部跳转断 URL 与渲染结果
- 文件上传：`await page.getByRole('button').setInputFiles('a.pdf')` 或 input 元素 `setInputFiles`；下载用 `page.waitForEvent('download')`
- 新 tab：`context.waitForEvent('page')` 先挂再点
- 追问：为什么「先挂监听再触发」是铁律？
  - dialog / download 是事件不是状态——动作触发后才挂监听就永远收不到了

### 37. E2E 能不能并行？如何提速？

**结论：能，且必须——Playwright 每 worker 独立进程 + 独立 context 天然可并行；提速三板斧：并行分片、套件分层（PR 跑 smoke、主干跑全量）、失败才留 trace。**

- 并行前提：用例间零共享（独立数据、独立 context）——并行冲突本身就是 flaky 源
- 分片：`--shard` 多机并行；`fullyParallel` 进程内并行
- 提速清单：依赖与浏览器缓存、按受影响文件过滤、video/trace 失败才留、禁不必要的动画
- 数据并行安全：每 worker 唯一账号 / 数据前缀，防互踩
- 追问：并行后出现「单跑绿、并行红」怎么办？
  - 按共享资源排查：同账号、同数据、同文件路径——给每个 worker 唯一命名空间

## 五、CI 集成与工程落地

### 38. 如何在 CI 流水线接入自动化测试？PR 卡点怎么做？

**结论：测试进 CI 的本质是「一条命令的非 0 退出码阻断合并」；卡点设计——单测 + 组件测试每次 PR 必跑并卡增量覆盖率，全量 E2E 主干跑，紧急修复留 override 通道。**

- 阶段顺序（fail fast）

```
typecheck（秒级）→ lint → 单测 + 组件测试 → E2E smoke → 合并后全量 E2E
```

- 覆盖率卡点三策略
  - 增量覆盖率：只要求本次 diff 改动的行被覆盖——存量项目卡全局阈值等于禁止合并
  - 分层阈值：核心目录 90%、通用 70%、脚本不设——一刀切逼人造假
  - 只升不降：阈值配置用 CODEOWNERS 保护，防「先改低让它绿」
- override：紧急修复可豁免 + 跟进工单——门禁防劣化趋势，不拦紧急修复
- 追问：E2E 全量太慢塞不进 PR 怎么办？
  - PR 只跑 smoke + 受影响模块；全量放主干或定时——反馈速度与覆盖的平衡

### 39. 单元测试和 E2E 放在 CI 的什么阶段？

**结论：单测放 PR 阶段（每提交必跑，分钟内），E2E 拆两级——smoke 进 PR、全量进主干合并后或定时；原则是「越贵的越往后放，便宜的放最前」。**

- 顺序理由：秒级反馈（typecheck/lint）在先，分钟级（单测）居中，十分钟级（E2E）殿后——类型错了不值得再花十分钟跑 E2E
- 失败即停：前置阶段红就不跑后面的，省算力
- 定时全量 E2E 的补充价值：抓「慢腐化」与环境漂移
- 追问：为什么不在 PR 阶段跑全量 E2E？
  - PR 要的是分钟级反馈；全量 E2E 十分钟级会把迭代速度拖死

### 40. 测试环境数据怎么准备？怎么清理？

**结论：隔离的单位是用例——每用例独立构造前置、专用测试库 + seed 重置；并行时 worker 唯一数据；绝不打真实库。**

- 数据准备：seed 脚本固定初始态；E2E 用专用测试环境 + 专用账号池
- 清理：`beforeEach` 清 localStorage / cookie、`server.resetHandlers()`、DB 重置；afterEach cleanup 渲染
- 并行安全：数据加 worker 前缀（同账号互踩是并行 flaky 第一来源）
- 重置和隔离的区别：重置是「清理脏了的环境」，隔离是「根本不共享」——隔离是根治
- 追问：E2E 要真实接口，怎么隔离第三方依赖？
  - 支付、短信等外部依赖用挡板 / route 拦截——被测系统真实、外部受控

### 41. 自动化脚本维护成本高，怎么降低？

**结论：维护成本主要花在「定位器失效、断言过紧、用例冗余」三处——解法是抗变定位、轻 POM、用例持续瘦身，把易变的 UI 断言下沉到更便宜的层。**

- 定位器抗变：role / label / 稳定 testId——样式类名、DOM 结构变了测试不挂
- 轻 POM：页面操作封装一处（元素变更只改一处）；断言留在用例里；拒绝层层继承的巨型 POM
- 用例瘦身：删低价值用例（三个月没拦过任何东西的 E2E）；同一路径只在一层主测
- 下沉：频改的 UI 细节断言从 E2E 下沉到集成层（改起来便宜）
- 契约化：接口字段靠 schema 契约测，不在 E2E 里逐字段断言
- 追问：怎么量化「该删哪些用例」？
  - 看拦截记录：长期零拦截 + 高维护频次的用例是负资产

### 42. 测试报告如何生成？CI 里怎么展示？

**结论：runner 自带报告 + CI 平台展示——单测出覆盖率 HTML 与 JUnit XML，E2E 出 HTML 报告（含失败截图 trace），产物存 artifact、摘要进 PR 评论。**

- Vitest：`--coverage.report` 出 HTML 覆盖率 + `--reporter=junit` 供 CI 解析
- Playwright：HTML reporter（用例列表 + 失败 trace / 截图 / 视频入口）
- CI 集成：报告存 artifact；失败摘要（哪条红、trace 链接）贴 PR；覆盖率趋势看板
- 趋势比单点重要：覆盖率（不换 provider）、flaky 率、套件时长三条曲线——时长持续变长就是治理信号
- 追问：报告没人看怎么办？
  - 把「失败摘要」推到人必经之路（PR 评论 / 群通知），而不是藏在 artifact 里等人翻

## 六、场景口述大题

### 43. 项目中引入自动化测试，从 0 到 1 怎么落地？

**结论：先基建、后用例、最后门禁——第一步不是定覆盖率指标，是把「跑一个测试」的成本降到零。**

- 落地顺序
  - ① 基建：Vitest 接入、公共 test-utils（render 封装、MSW server）、CI 能跑——扫清空白页
  - ② 结对示范：选真实功能和业务同学结对写第一个集成测试，定标准
  - ③ 数据说话：收集 escaped defects 与手点回归耗时
  - ④ 门禁最后上：且只上增量覆盖率阈值
- 反模式：上来定 80% 全局覆盖率——逼出断言空转和「改低阈值让它绿」
- 追问：为什么门禁放最后？
  - 没有基建和示范就上门禁，产出的是应付指标垃圾测试——门禁放大现状，不改善现状

### 44. 你写过哪些自动化用例？遇到的最大难点是什么，怎么解决？

**结论：按「背景 → 难点定位 → 解决 → 沉淀」口述；难点选 flaky 治理最有深度——它贯穿用例设计、基建、流程三层。**

- 参考叙事骨架（换自己的量级）

```
背景：给资金相关模块补单测与组件测试，CI 偶发红（10 次挂 2 次），团队开始无视红灯
定位：随机顺序复现 + 失败日志分类——三个根因：假定时器没恢复泄漏、
      store 单例跨用例共享、一个用例断言依赖「当天日期」
解决：afterEach 统一恢复（restoreAllMocks / useRealTimers）；
      beforeEach 重置 store；时间注入固定系统时间 + 固定 TZ
沉淀：test-utils 里封死「时间与时区冻结」，随机顺序进日常跑——
      之后新增用例想 flaky 都难
```

- 表述纪律：难点要说「为什么难」（偶发、难复现），解法要说「沉淀成什么」（基建 / 流程），不是只说「修好了」
- 追问：修完之后怎么保证不再发生？
  - 治理流程（隔离带到期日）+ 基建预防（冻结时间/时区）+ 随机顺序日常复现——三道防线

### 45. 用例不断增多，执行速度越来越慢，怎么优化？

**结论：按「慢在哪层」分层优化——单测靠按需执行与并行，E2E 靠分片与分层执行（smoke / 全量），再加持续瘦身删低价值用例。**

- 单测层：`related` 只跑改动相关文件、多线程并行、describe 分片
- E2E 层：`--shard` 多机分片、PR 只跑 smoke + 受影响模块、全量放主干 / 定时
- 通用：依赖与浏览器二进制缓存、video/trace 失败才留、禁动画
- 结构性：同一路径三层重复测的收敛到一层主责——用例数下降，覆盖不变
- 追问：删用例会不会有风险？
  - 删的是「零拦截 + 高维护」的负资产；删前看拦截记录，删后 escaped defects 是验收

### 46. E2E 容易出现 flaky，你遇到过哪些，怎么排查修复？

**结论：按根因表对号入座——sleep 赌时间、共享状态、依赖「现在」、时区、并行冲突；排查套路是「先取证再归因」：trace / 日志 → 复现（repeat + 随机顺序）→ 根因修复。**

- 排查流程
  - 取证：失败 trace（截图 + 网络 + 控制台）、判断是断言失败还是超时
  - 复现：`--repeat-each` + 随机顺序，把偶发变必现
  - 归因修复：等条件替换 sleep / worker 唯一数据 / 冻结时间与时区 / route 拦截真实网络
- 实例口径：本地好 CI 红 → 先查时区与时间；多 worker 才红 → 查共享账号与数据
- 追问：为什么先取证再改？
  - 直接重跑等于销毁证据；偶发问题的信息只在失败现场里

### 47. 业务迭代快、UI 频繁改，E2E 脚本频繁失效，怎么治理？

**结论：三个方向——定位器抗变（契约化）、断言下沉（频改细节从 E2E 挪到便宜的层）、E2E 收缩到稳定的关键路径；UI 快变区本来就不该用最贵的层去锁。**

- 定位器抗变：role / label / 稳定 testId——文案与样式改了测试不挂
- 断言下沉：颜色、间距、局部文案这类频改断言交给组件集成测试（改起来毫秒级）；E2E 只断旅程结果
- 轻粒度更新机制：POM 让元素变更只改一处；失败报告按「哪页坏了」聚合批量修
- 分层兜底：E2E 收缩到登录 / 下单等稳定主路径 + smoke
- 追问：怎么跟产品约定配合？
  - 关键路径元素（提交按钮、表单）纳入「改动需知会」契约——testId 就像接口字段一样有变更成本

### 48. 团队不愿意写测试，你怎么推动落地？

**结论：不靠理念靠机制——降低写测试的门槛（基建）、用快赢建立信任（数据说话）、把测试挂进流程（增量门禁）；推不动的根因通常是「收益感知不到、成本看得见」。**

- 四步推动
  - ① 基建降门槛：test-utils 封装好，写一个组件测试 20 分钟以内
  - ② 快赢：挑一个高频回归模块补测，第一次拦住回归立刻宣传
  - ③ 数据：手点回归耗时、线上漏测事故——用业务语言讲
  - ④ 流程固化：增量覆盖率门禁 + code review 里测试与代码同评
- 反模式：行政命令定指标——只会收获断言空转
- 追问：如果业务方始终不支持排期呢？
  - 把测试写进「改 bug 的成本」：修 bug 必须先补一个能复现它的测试——用事故倒逼，比宣传有效

### 49. 单元、组件、E2E，你的项目怎么分配比重？

**结论：按测试奖杯配比——集成（组件）60~70%、单元 20~30%、E2E 5~10%，且明确「比例服务于 bug 历史」不是教条；每个比例数字都能说出对应 rationale。**

- 分配逻辑
  - 单元：纯逻辑层吃满（校验、计算、工具）——边界多是它的主场
  - 集成：所有用户可交互组件的契约——覆盖面最广、性价比最高
  - E2E：登录、下单、发布等花钱路径 + smoke——数量少但每条都守命门
- 动态调整：线上哪类 bug 多就加重哪层——bug 历史决定投入
- 特例：工具库型项目单元层占比反超集成层
- 追问：怎么向面试官证明这个比重是「实践出来的」？
  - 说出一个调整案例：E2E 从几十条收敛到十几条主干、省下的维护投进组件层——有过程就有说服力

## 七、手写 / 实操题

### 50. 用 Vitest 写一个工具函数的单元测试

**结论：三段式——正常路径、边界、非法输入；用例名说行为，反例用 throws 断言。**

```js
// fmt.test.js
import { describe, it, expect } from 'vitest'
import { formatMoney } from './fmt'

describe('formatMoney 金额格式化', () => {
  it('千分位并保留两位小数', () => {
    expect(formatMoney(1234567.891)).toBe('1,234,567.89')
  })
  it('边界：0 与负数', () => {
    expect(formatMoney(0)).toBe('0.00')
    expect(formatMoney(-520.5)).toBe('-520.50')
  })
  it('非法输入抛错', () => {
    expect(() => formatMoney(NaN)).toThrow()
    expect(() => formatMoney('abc')).toThrow()
  })
})
```

- 要点：边界（0、负数）和非法输入是面试官真正在看的部分——只写 happy path 不加分
- 追问：还想补什么用例？
  - 极大值精度（浮点误差）、四舍五入边界（x.995）——主动暴露你知道的坑

### 51. 用测试库测一个按钮点击事件

**结论：交互三步——渲染、模拟点击、断言契约（emit 参数 + 可见结果）；等 trigger 的 Promise、断言 emit 参数而不是内部 state。**

```js
import { mount } from '@vue/test-utils'
import Counter from './Counter.vue'

it('点击后文案更新并向父组件 emit 次数', async () => {
  const wrapper = mount(Counter)
  await wrapper.find('button').trigger('click')
  expect(wrapper.text()).toContain('1')
  expect(wrapper.emitted('change')?.[0]).toEqual([1])
})
```

- 要点
  - `trigger` 返回 Promise，必须 await（等 DOM 更新收口）
  - 断言两层：可见文案（用户视角）+ emit 参数（父组件契约）——不戳 `wrapper.vm.count`
- 追问：如果点击后是异步请求再更新，怎么改？
  - mock 网络层 + `findBy` 等结果出现——断言从同步变等条件

### 52. 用 Playwright 写一个简单 E2E

**结论：访问 → 输入 → 点击 → 等待断言；全程 locator 自动等待，无 sleep。**

```js
import { test, expect } from '@playwright/test'

test('搜索关键词出现结果', async ({ page }) => {
  await page.goto('/search')
  await page.getByLabel('关键词').fill('手机')
  await page.getByRole('button', { name: '搜索' }).click()
  await expect(page.getByRole('listitem').first()).toBeVisible()
})
```

- 要点
  - 定位用 role / label（可访问性顺带测了）
  - `expect(...).toBeVisible()` 内建轮询——不需要 waitForSelector 也不需要 sleep
  - 断言「结果出现」而不是「等待 N 秒后截图看」
- 追问：怎么让这条用例不 flaky？
  - 测试数据独立（每次造唯一关键词）、断言等条件、失败留 trace 定位

## 八、补充拓展

### 53. 什么是可视化回归测试？原理与适用场景？

**结论：对渲染结果截图并与基准对比，机器盯样式回归——Storybook story 逐张截图（Chromatic / Percy）或 Playwright `toHaveScreenshot`；成败在阈值调教，调不好退化成「全点 accept」的信号失效。**

- 原理：基准截图入库 → 每次运行重截 → 像素 diff 超阈值标红 → 人工确认更新基准
- 适用边界：设计系统 / 组件库最值（组件少复用高）；业务页全站截图是噪声地狱
- 防误报：禁动画、固定字体回退、容忍度阈值、忽略动态区域（时间戳、头像）
- 追问：团队开始无脑 accept 怎么办？
  - 信号已失效——先降误报（阈值 / 忽略区域），再立规矩（accept 必须留言说明原因）

### 54. 性能测试能不能放进自动化？

**结论：能做「性能回归监测」，不能做「性能断言卡口」——实验室数字受环境波动大，做法是 Lighthouse CI / Playwright 采集指标 + 性能预算告警，而不是像功能断言那样非 0 即 1。**

- 自动化采集：CI 跑 Lighthouse（确定性环境下测 TBT / LCP 类实验室指标）、RUM 采集线上真实用户指标
- 落地形态：性能预算（体积、指标阈值）超标告警或 PR 评论——软卡口不是硬门禁
- 与功能测试的本质差异：功能结果确定（通过 / 失败），性能数字是分布——看 p75 环比趋势，不卡单次读数
- 追问：为什么性能不做成硬门禁？
  - 单次实验室读数波动能到两位数百分比——硬卡会被噪声误伤，最终被团队关掉

### 55. 自动化测试能不能替代人工测试？

**结论：不能——自动化擅长「已知预期的重复验证」，人工擅长「探索性测试、体验判断、未知场景」；AI 加持后边界略微移动，但断言评审与范围决策仍是人的职责。**

- 自动化的主场：回归、冒烟、数据驱动的大量组合、契约一致性
- 人工的主场：探索性测试（自动化只会测「写过的东西」）、UX 与视觉判断、新功能首次验收
- AI 的角色：生成用例提效（纯函数单测、E2E 初稿）——但 AI 会「跟着实现写断言」（把 bug 行为断言成正确），断言必须人评审
- 追问：AI 生成测试怎么验收？
  - 改坏 / 删掉实现看测试红不红；断言对照需求而不是对照实现——红不红的纪律一样适用
