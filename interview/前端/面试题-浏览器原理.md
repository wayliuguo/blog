# 面试题 · 浏览器原理

> 定位：高级岗浏览器原理考「讲得清机制」——安全、进程线程、缓存、渲染、存储、跨域、事件循环与 GC。全篇按「结论先行 + 表格 + 子层级」组织。

## 一、浏览器安全

### 1. 什么是同源策略？

**结论：协议 + 域名 + 端口三者相同才算同源；它是浏览器的安全基石，限制的是「脚本读取跨源资源」，不是「发出请求」。**

- 主要限制三个方面
  - 跨源的 Cookie、localStorage、IndexedDB 无法被当前域的脚本读取
  - 跨源的 DOM 无法被当前域的脚本操作（iframe 跨源后拿不到内部文档）
  - AJAX/fetch 的跨域请求默认被拦截（响应到了浏览器但脚本读不到，除非 CORS 放行）
- 不受限的部分（高频追问）
  - `img`/`script`/`link`/`iframe` 的**加载**不受同源限制——所以有 JSONP、图片打点
  - 原因：这些操作只「发出」，不「读取响应内容」，浏览器认为泄露风险可控
- 目的
  - 隔离不同源的文档，防止恶意网站窃取其他站点在浏览器里的数据（登录态、DOM 内容）
  - 它**只约束浏览器行为**——服务器之间互调不存在跨域，这也是「代理转发」能绕跨域的根本原因

### 2. XSS 攻击与防范？

**结论：XSS = 攻击者把恶意脚本注入页面执行，分存储型 / 反射型 / DOM 型三类；防范核心是「不信任任何用户输入」——输出转义 + CSP + HttpOnly 三层。**

- 三种类型

| 类型 | 注入位置 | 典型场景 | 特点 |
| --- | --- | --- | --- |
| 存储型 | 恶意代码存进数据库 | 评论里写 `<script>`，所有访问者中招 | 危害最大、持续触发 |
| 反射型 | 恶意代码在 URL 参数里 | 诱导用户点带脚本的链接，服务端把参数原样回显 | 一次性的，需诱导点击 |
| DOM 型 | 纯前端把不可信数据写进 DOM | `innerHTML = location.hash` 取出的内容 | 全程不经过服务器 |

- 防范手段
  - 输出转义：按上下文转义（HTML 实体 / 属性值 / JS 字符串），前端渲染少用 `innerHTML`，用 `textContent`
  - CSP（内容安全策略）：响应头 `Content-Security-Policy` 白名单化脚本来源，内联脚本不放行就直接不执行——即使注入成功也跑不起来
  - Cookie 加 `HttpOnly`：JS 读不到 Cookie，偷不到登录态
  - 输入校验是辅助不是主力：转义要按「输出位置」做，输入端永远防不全

### 3. CSRF 攻击与防范？

**结论：CSRF = 冒用用户已存的登录态发起伪造请求；它拿不到响应内容也偷不到 Cookie，只是「借浏览器自动带 Cookie 之手」，所以防范围绕「验证请求确实出自本站」展开。**

- 攻击原理
  - 用户已登录 A 站（Cookie 在浏览器里）
  - 访问恶意 B 站，B 站页面里藏一个自动提交的表单/img src 指向 A 站转账接口
  - 浏览器发请求时**自动携带 A 站 Cookie**，A 站以为是本人操作
- 与 XSS 的区别（高频追问）
  - XSS：注入脚本执行，能拿到页面内容，需要注入点
  - CSRF：不执行任何代码，只是借身份发请求，不需要注入点
- 防范手段
  - CSRF Token：表单/请求头带服务端签发的随机 Token，B 站拿不到（同源策略保护 Token 读取）
  - `SameSite` Cookie 属性：`Lax`（默认，跨站 GET 导航才带）/ `Strict`（全不带）/ `None`（显式声明才跨站带）——现代浏览器默认 Lax 已挡掉大部分 CSRF
  - 校验 `Referer`/`Origin` 头：非本站来源拒绝
  - 敏感操作二次确认（短信/验证码）

### 4. 中间人攻击与网络劫持？

**结论：中间人攻击 = 攻击者置身通信两端之间窃听/篡改；前端侧的典型表现是 DNS 劫持和 HTTP 劫持，根治手段是全站 HTTPS + HSTS。**

- 前端能感知的两种劫持
  - DNS 劫持：域名解析被指到假 IP，表现为整页变赌博/广告页
  - HTTP 劫持：运营商在明文 HTTP 响应里插脚本/弹窗广告（原内容还能正常打开）
- 防范
  - 全站 HTTPS：TLS 加密 + 证书校验，中间人篡改会被完整性校验发现
  - HSTS：服务端通过 `Strict-Transport-Security` 头下发「此域名必须走 HTTPS」策略，浏览器命中后 http:// 在发出前就被改写为 https://，堵住首请求被降级（SSL 剥离）的洞
  - 敏感接口固定证书（证书锁定，App 场景常用）
- 追问：HTTPS 就完全安全了吗？
  - 证书信任链被破坏（用户装了恶意根证书）、TLS 版本过旧、业务逻辑漏洞都不归 TLS 管

### 5. 什么是安全沙箱？

**结论：Chrome 把渲染进程放进 OS 级沙箱——渲染进程被视作不可信程序，大多数系统 API（文件、网络、窗口）都不可直接访问，需要通过 IPC 走浏览器主进程。**

- 为什么需要
  - 渲染进程直接解析不可信的网页内容（HTML/JS），是攻击面的最前沿
  - 沙箱保证即使渲染进程被攻破（远程代码执行），攻击者也困在沙箱里拿不到系统权限
- 沙箱内的限制
  - 渲染进程不能直接读写文件系统、不能发起任意网络请求（网络走网络进程统一代理）
  - 这解释了为什么 fetch/文件读写在架构上都由「浏览器主进程/网络进程」代劳
- 追问：沙箱与站点隔离的关系
  - 站点隔离（Site Isolation）= 不同站点强制放进不同渲染进程，是「进程级隔离」；沙箱是「进程内的 OS 级隔离」，两层叠加

### 6. 前端安全风险速览？

**结论：按「攻击面」记忆——内容注入、身份冒用、传输劫持、点击劫持、本地依赖。**

| 攻击面 | 代表攻击 | 一句防范 |
| --- | --- | --- |
| 内容注入 | XSS | 输出转义 + CSP |
| 身份冒用 | CSRF / 点击劫持 | Token + SameSite + `X-Frame-Options`/`frame-ancestors` |
| 传输劫持 | 中间人 / DNS·HTTP 劫持 | 全站 HTTPS + HSTS |
| 本地依赖 | 供应链投毒（恶意 npm 包、被篡改的第三方 script） | 锁版本 + SRI（`integrity` 属性校验） |
| 敏感数据 | localStorage 存 Token 被 XSS 偷 | 能 HttpOnly 的不放 JS 可读处 |

## 二、进程与线程

### 1. 进程与线程的区别？

**结论：进程是资源分配的最小单位，线程是 CPU 调度的最小单位；进程间内存隔离，线程共享进程内存。**

| 维度 | 进程 | 线程 |
| --- | --- | --- |
| 定位 | 资源分配的最小单位 | CPU 调度的最小单位 |
| 内存 | 独立地址空间 | 共享所属进程的地址空间 |
| 通信 | IPC（管道/消息队列/共享内存），开销大 | 直接读写共享变量，但要防竞态 |
| 崩溃影响 | 一个进程崩不影响其他进程 | 一个线程崩整个进程挂 |
| 切换开销 | 大（换地址空间） | 小 |

- 浏览器为什么用多进程（高频追问）
  - 隔离崩溃：一个标签页崩了不带崩整个浏览器
  - 隔离安全：配合沙箱 + 站点隔离，恶意页面困在低权限进程里

### 2. Chrome 的多进程架构？

**结论：浏览器进程 + GPU 进程 + 网络进程 + 渲染进程（多个）+ 插件进程；核心是「每个站点独立的渲染进程」。**

- 五类进程及职责
  - 浏览器主进程：地址栏 UI、书签、用户输入，协调其他进程
  - 网络进程：统一处理所有网络请求（渲染进程在沙箱里不能直接碰网络）
  - GPU 进程：合成层绘制、3D/CSS 加速
  - 渲染进程：页面解析渲染、JS 执行（在沙箱里，每标签页/每站点一个）
  - 插件进程：每个插件独立一个，防其崩溃波及
- 站点隔离（Site Isolation，追问加分点）
  - 同一标签页里的跨站 iframe 也分配到**独立的渲染进程**
  - 收紧了同源策略的进程边界：Spectre 类侧信道攻击难以跨进程读内存

### 3. 渲染进程里有哪些线程？

**结论：GUI 渲染线程与 JS 引擎线程互斥——这是「JS 执行会阻塞渲染」的根本原因。**

- 五个常考线程
  - GUI 渲染线程：解析 HTML/CSS、布局、绘制
  - JS 引擎线程（V8）：解析执行 JS
  - 事件触发线程：管理任务队列，栈空时把队首任务推给 JS 引擎
  - 定时器触发线程：setTimeout/setInterval 计时（不占 JS 线程），到期把回调放进任务队列
  - 异步 HTTP 请求线程：XHR 的网络等待
- 互斥的含义
  - JS 执行时 GUI 线程挂起 → 长任务掉帧、页面卡死
  - 反过来 DOM 渲染进行中改 DOM 也会竞态，所以必须互斥
- 追问：既然互斥，为什么 Worker 能并行？
  - 见下一题——Worker 是**独立线程**跑 JS，不碰 DOM，所以不互斥

### 4. Web Worker 是什么？为什么它不阻塞 UI？

**结论：Worker 是与主线程并行的独立 JS 线程，通过 postMessage 传递（结构化克隆的）数据；它不能访问 DOM/BOM，所以与 GUI 线程没有互斥关系。**

- 三种 Worker

| 类型 | 作用域 | 典型场景 |
| --- | --- | --- |
| Dedicated Worker | 只属于创建它的页面 | 大计算（图像处理、加密、数据解析） |
| Shared Worker | 多个同源页面共享 | 跨标签页共享连接/状态 |
| Service Worker | 浏览器级，独立生命周期 | 离线缓存、消息推送（见缓存组） |

- 使用要点
  - `new Worker('worker.js')` 加载独立脚本，与主线程只靠 `postMessage`/`onmessage` 通信，数据是**拷贝**（结构化克隆），不是共享内存
  - 能用：setTimeout/fetch/IndexedDB；不能用：DOM、`window`、`localStorage`
  - 通信开销考量：任务粒度太小会被序列化成本吃掉收益——适合「一次搬一大批、Worker 内算完再传回」

## 三、HTTP 缓存

### 1. 强缓存与协商缓存？

**结论：强缓存不发请求直接用本地副本（`Cache-Control`/`Expires`）；协商缓存发请求问服务器，未变返回 304 只用本地（`ETag`/`Last-Modified`）。流程是强缓存先行、协商缓存兜底。**

- 判断流程
  - 强缓存命中 → 200（from disk/memory cache），**不发请求**，直接用副本
  - 强缓存过期 → 发请求带校验字段 → 未变 **304**（无响应体，用本地）→ 变了 **200 + 新资源**
- 字段对照

| 机制 | 响应头（服务器下发） | 请求头（浏览器带回） | 优先级 |
| --- | --- | --- | --- |
| 强缓存 | `Cache-Control` / `Expires` | —— | Cache-Control > Expires |
| 协商缓存 | `ETag` / `Last-Modified` | `If-None-Match` / `If-Modified-Since` | ETag > Last-Modified |

- Cache-Control 关键值
  - `max-age`：相对秒数，优先于 Expires（绝对时间受客户端时钟影响，所以被取代）
  - `no-cache`：**能缓存但用前必须协商校验**；`no-store`：彻底不缓存（两者区别是必考追问）
  - `private`/`public`：中间代理（CDN）能否缓存
  - `Pragma: no-cache`：HTTP/1.0 遗物，行为近似 no-cache，一句话带过即可
- ETag 为什么优先于 Last-Modified（必考追问）
  - Last-Modified 只精确到**秒**，1 秒内多次修改检测不出
  - 内容没变但修改时间变了（重新发布），Last-Modified 会误判
  - ETag 基于内容指纹，但多机部署时各机器计算不一致会翻车——要保证集群生成规则一致

### 2. 浏览器的缓存位置有哪几层？

**结论：四个层级，命中优先级 Service Worker → Memory Cache → Disk Cache → Push Cache；四级之外才是真正发网络请求。**

| 位置 | 特点 |
| --- | --- |
| Service Worker | 可编程控制，能拦截请求自定义缓存策略，HTTPS 必须 |
| Memory Cache | 内存中，快但关标签页即清；当前页面加载过的资源优先在这 |
| Disk Cache | 磁盘，持久、容量大；强/协商缓存的正文存这里 |
| Push Cache | HTTP/2 推送的临时缓存，会话级，很少考细节 |

- 高频追问：from memory cache 和 from disk cache 什么区别？
  - 刷新页面时同一张图第一次 disk、第二次可能 memory；大文件即使重复加载也可能只走 disk

### 3. 实战：发版后用户还在用旧资源怎么办？

**结论：标准方案 = HTML 用 `no-cache` 每次协商校验，静态资源文件名带 hash + `max-age=31536000, immutable` 长强缓存——内容变了文件名就变，浏览器自然当新资源请求。**

- 配置示例

```
*.js/*.css/*.png   →  Cache-Control: max-age=31536000, immutable
index.html         →  Cache-Control: no-cache
```

- 每一层为什么这样配
  - HTML 不能长缓存：它是所有资源的入口，文件名写死了旧 hash 就永远引旧 JS
  - hash 长缓存：内容不变文件名不变，命中一年强缓存，零请求
  - `immutable`：告诉浏览器有效期内**即使刷新（F5）也不要发协商请求**（不写的话 F5 会绕过强缓存）
- 常见踩坑
  - 只给 JS 加 hash、HTML 却配了 max-age → 用户拿旧 HTML 引已删掉的旧 hash 文件，白屏
  - CDN 缓存没刷新（回源没更新），与浏览器缓存是两层，要分别处理

### 4. 刷新按钮 / F5 / Ctrl+F5 / 地址栏回车的区别？

**结论：地址栏回车正常走缓存；F5 跳过强缓存走协商；Ctrl+F5 连协商都跳过，全部重新拉取。**

| 行为 | 强缓存 | 协商缓存 | 说明 |
| --- | --- | --- | --- |
| 地址栏回车 / 普通跳转 | 正常判断 | 正常 | 完整缓存链 |
| F5 / 刷新按钮 | 跳过 | 走（请求带 `max-age=0`） | 必问服务器，变了才下载 |
| Ctrl+F5 | 跳过 | 跳过（请求带 `no-cache`） | 全量重新下载 |

- 追问：为什么 F5 要绕过强缓存？
  - 用户语义是「我要看有没有新内容」，跳过强缓存才能触发协商校验——这也是 `immutable` 字段要解决的反向需求

### 5. Service Worker 是什么？

**结论：运行在浏览器后台的独立线程脚本，能拦截所在作用域的所有网络请求并自定义缓存策略，是 PWA 离线能力的基础；必须 HTTPS（localhost 除外）。**

- 关键特性
  - 独立于页面生命周期：页面关了 SW 还活着，事件驱动被唤醒
  - 拦截式代理：fetch 事件里拿到请求，可返回缓存/转发网络/自造响应
  - 作用域：注册路径决定管辖范围（`/sw.js` 管全站，`/sub/sw.js` 只管 `/sub/`）
- 生命周期三步
  - install：预缓存核心资源（`caches.open().addAll()`）
  - waiting：旧 SW 还控制页面时，新 SW 等待（`skipWaiting` 可跳过）
  - activate：接管，清理旧版本缓存
- 常用缓存策略（面试说出名字和取舍即可）
  - Cache First（静态资源）/ Network First（HTML/API）/ Stale-While-Revalidate（先回缓存再后台更新）

## 四、渲染

### 1. 浏览器的渲染流程？

**结论：解析 HTML 构建 DOM 树，解析 CSS 构建 CSSOM，两者合成渲染树 → 布局计算几何 → 分层绘制 → GPU 合成上屏；CSSOM 不完整会阻塞渲染树构建。**

- 主流程分步
  - 解析 HTML → DOM 树（字节流 → Token → 节点 → 树，边下载边解析）
  - 解析 CSS → CSSOM 树（CSSOM 完整前渲染树不能开始合成——CSS 阻塞渲染的原因）
  - 合成渲染树（只含可见节点；`display:none` 不进渲染树）
  - 布局（Layout/Reflow）：计算每个节点的几何位置
  - 分层（Layer）：按层叠上下文等规则拆成合成层
  - 绘制（Paint）：生成绘制指令列表
  - 合成（Composite）：GPU 把各层位图合成最终画面
- 分层与合成（追问点）
  - `transform`/`opacity` 动画可提升为合成层：改动只发生在合成阶段，**跳过布局和绘制**，所以性能最好
  - 滥用 `will-change`/合成层过多反而涨内存（层爆炸）
- 追问：`display:none` 和 `visibility:hidden` 在渲染树上什么区别？
  - 前者不进渲染树；后者进渲染树占位、只跳过绘制

### 2. JS 和 CSS 如何影响渲染？

**结论：CSS 阻塞渲染不阻塞解析；JS 阻塞解析也阻塞渲染（脚本可能改 DOM）；预解析线程会提前下载资源缓解等待。**

- CSS 阻塞规则
  - CSSOM 构建完成前渲染树无法合成 → **CSS 阻塞首次渲染**（但不阻塞 HTML 解析）
  - 所以 CSS 放 `<head>` 尽早加载；媒体查询不匹配的样式表不阻塞（`media="print"`）
- JS 阻塞规则
  - 同步 script：**阻塞 HTML 解析**（脚本可能改 DOM，浏览器必须停等）+ 执行前要等前面 CSS 下载完（脚本可能查样式）
  - 缓解：defer（解析完按序执行）/ async（下载完立即执行）——defer/async 细节见 HTML 篇
- 文档预解析（Preload Scanner）
  - 主解析器被 JS 卡住时，预解析线程继续扫描后面的 HTML，**提前下载** CSS/JS/图片——只下载不解析
- 什么情况阻塞渲染
  - head 里的同步 CSS、同步 JS、字体（FOIT）——分别对应尽早加载/defer/`font-display: swap` 应对

### 3. 回流（重排）与重绘？

**结论：回流改几何必走布局（贵），重绘只改外观跳过布局（较便宜）；回流必然引发重绘，反之不成立；批量读写分离 + transform/opacity 是核心优化。优化手段细节见 CSS 篇回流重绘题。**

- 在渲染流水线中的位置
  - 改几何属性（宽高/位置/内容）→ Layout → Paint → Composite 全走
  - 改外观（颜色/背景/阴影）→ 跳过 Layout，走 Paint → Composite
  - 只改 `transform`/`opacity` → 只 Composite（合成器线程处理，不占主线程）
- 强制同步布局（Layout Thrashing，高频追问）
  - 交替「写样式 → 读 offsetTop 等几何属性」会逼浏览器每次**立即回流**，循环里尤其致命
  - 解法：读写分离——先批量读，再批量写
- 浏览器的批处理队列
  - 样式改动先进 flush 队列批量回流；一旦读了 `offsetWidth`/`getBoundingClientRect()` 这类几何敏感属性，队列被强制 flush

### 4. 哪些操作会触发回流？

**结论：一切「改变布局」的写和「读取几何」的读。按类记忆即可。**

- 写触发
  - 首次渲染；窗口 resize；增删可见 DOM；改几何（宽高/边距/位置/字号）；内容变化（文本/图片尺寸）
  - 激活 CSS 伪类、`offsetParent` 变化
- 读触发（强制 flush 队列）
  - `offsetTop/Left/Width/Height`、`scrollTop/Left`、`clientTop/Width`、`getBoundingClientRect()`、`getComputedStyle()`

## 五、本地存储

### 1. Cookie / LocalStorage / SessionStorage 区别？

**结论：Cookie 本职是随请求携带的「服务端状态」，4KB 且自动上传；Web Storage 是纯前端存储，5MB 左右不随请求发。**

| 维度 | Cookie | LocalStorage | SessionStorage |
| --- | --- | --- | --- |
| 生命周期 | 可设过期时间 | 永久（手动清） | 页面会话结束即清 |
| 容量 | ~4KB | ~5MB | ~5MB |
| 随请求发送 | 每次 | 否 | 否 |
| 服务端可写 | Set-Cookie 可写 | 否 | 否 |
| 作用域 | 域 + 路径 | 同源共享 | 同源 + **同标签页**（新开标签页不共享） |

- 使用建议
  - 登录态/服务端要读的 → Cookie（配 HttpOnly/Secure/SameSite，见下一题）
  - 前端偏好（主题/语言）→ LocalStorage
  - 一次性会话数据（表单草稿/验证码倒计时）→ SessionStorage
- 追问：localStorage 能存敏感信息吗？
  - 谨慎——XSS 可直接读；Token 放 localStorage 是业界常见但有争议的取舍（配合 CSP 降低 XSS 面）

### 2. Cookie 有哪些字段？

**结论：按「作用域、时效、安全」三组记；安全三件套 HttpOnly/Secure/SameSite 是 CSRF/XSS 防线的组成部分。**

- 作用域
  - `Domain`：可配父域实现子域共享（`Domain=a.com` 对 `x.a.com` 生效）
  - `Path`：路径前缀匹配
- 时效
  - `Expires`（绝对时间）/ `Max-Age`（相对秒，优先）；都不设则是会话 Cookie，关浏览器即失
- 安全
  - `HttpOnly`：JS 不可读——防 XSS 偷 Cookie
  - `Secure`：仅 HTTPS 传输
  - `SameSite`：`Strict`/`Lax`（浏览器默认）/`None`（需配 Secure）——防 CSRF 的核心字段
- 其他（加分点）
  - `Partitioned`（CHIPS）：第三方 Cookie 分区隔离——第三方 Cookie 逐步废弃背景下的新考点

### 3. IndexedDB 是什么？什么场景用？

**结论：浏览器内的非关系型（对象）数据库，容量可达数百 MB 且异步不阻塞主线程——Web Storage 存不下的结构化/大数据用它。**

| 维度 | IndexedDB | LocalStorage |
| --- | --- | --- |
| 容量 | 数百 MB 起 | ~5MB |
| API | 异步事务式 | 同步 |
| 数据类型 | 对象/二进制（Blob/File） | 仅字符串 |

- 典型场景
  - 离线应用数据缓存（配合 Service Worker）
  - 大量结构化数据本地查询（消息记录、离线包、编辑器草稿）
- 使用要点
  - 所有读写都在事务里；基于索引查询；事件式 API 冗长，实践中用 `idb` 类库封装

## 六、跨域

### 1. CORS 深挖：简单请求与预检请求？

**结论：简单请求直接发，浏览器只校验响应头；非简单请求先发 OPTIONS 预检问许可，通过才发真实请求。CORS 的控制权在服务端响应头。**

- 简单请求的判定（同时满足）
  - 方法为 GET / POST / HEAD 之一
  - 请求头只含安全字段（Accept、Accept-Language、Content-Language、Content-Type 限定值）
  - Content-Type 限于 `text/plain` / `multipart/form-data` / `application/x-www-form-urlencoded`
- 非简单请求
  - **会先触发 OPTIONS 预检**（自定义头、`Content-Type: application/json`、PUT/DELETE 都触发）——高频追问的准确性红线
  - 服务器返回允许的方法/头/源，浏览器校验通过才发真实请求；预检结果可被 `Access-Control-Max-Age` 缓存，期内不再预检
- 服务端核心响应头

| 响应头 | 作用 |
| --- | --- |
| `Access-Control-Allow-Origin` | 允许的源（`*` 或具体源） |
| `Access-Control-Allow-Methods` | 允许的方法 |
| `Access-Control-Allow-Headers` | 允许的自定义请求头 |
| `Access-Control-Allow-Credentials` | 允许携带 Cookie |
| `Access-Control-Max-Age` | 预检结果缓存秒数 |

- 带凭证的高频坑
  - 前端 `fetch(url, { credentials: 'include' })` 带上 Cookie
  - 服务端 `Allow-Credentials: true` 时 **`Allow-Origin` 不能是 `*`**，必须回显具体源——两边不改就报 CORS 错误

### 2. JSONP 与其他跨域方案？

**结论：JSONP 靠 script 标签不受同源限制，只支持 GET、有注入风险；现代项目首选 CORS + 代理，其余方案按场景选。**

- JSONP 原理（压缩版）
  - 前端定义全局回调函数，动态插 `<script src="http://api?callback=handleCallback">`
  - 服务端把数据包进回调返回：`handleCallback({"user":"admin"})`，script 加载即执行
  - 局限：只 GET、无法带凭证、依赖服务端配合、回调名不可信有 XSS 面——现代已少用
- 方案选型表

| 方案 | 原理 | 场景 |
| --- | --- | --- |
| CORS | 服务端响应头授权 | 生产环境标准解 |
| 开发代理（Vite proxy / webpack devServer） | dev server 同源转发 | 本地开发 |
| Nginx 反向代理 | 同源服务器转发到目标 | 生产同域部署 |
| postMessage | `window.postMessage` 跨窗口通信 | iframe 嵌套/跨窗口（如第三方登录弹窗） |
| WebSocket | 协议本身无同源限制 | 实时通信顺带解决跨域 |
| `document.domain` | 子域互设相同父域 | **已废弃**，面试答「知道但不用」 |

## 七、事件循环与 GC

### 1. 浏览器的事件循环机制？

**结论：JS 单线程，同步代码在执行栈跑；异步回调按宏/微任务排队——每轮宏任务跑完，清空全部微任务，再按需渲染（rAF 回调在渲染前）。**

- 为什么单线程（先答这个）
  - DOM 是共享的可变数据，多线程同时改 DOM 需要锁、复杂度高——索性单线程 + 异步
- 执行顺序（口诀：同步 → 微任务清空 → rAF/渲染 → 下一轮宏任务）
  - 执行同步代码（整体 script 属宏任务）
  - 清空全部微任务（Promise.then / MutationObserver / queueMicrotask）
  - 需要渲染时：执行 `requestAnimationFrame` 回调 → 样式计算/布局/绘制
  - 取下一个宏任务（setTimeout/setInterval/I/O/UI 事件），循环往复
- 经典输出题（必会）

```
console.log(1)
setTimeout(() => console.log(2))
Promise.resolve().then(() => console.log(3))
console.log(4)
// 1 4 3 2 —— 同步(1,4) → 微任务(3) → 宏任务(2)
```

- rAF 与渲染时机（追问点）
  - rAF 回调**不属于宏/微任务**，它在「微任务之后、本轮渲染之前」执行
  - 应用：想在下帧渲染前做样式调整放 rAF；微任务里改样式会在同一次渲染前生效
- 完整宏/微任务输出题集见 JS 篇事件循环题，此处不重复

### 2. V8 的垃圾回收机制？

**结论：分代回收——新生代用 Scavenge（复制算法，空间换时间），老生代用标记清除 + 标记整理；都是「标记可达对象，回收不可达」。**

- 新生代（1~8MB，存放存活短的对象）
  - Scavenge：两块半空间 From/To，存活对象从 From 复制到 To，然后互换
  - 两次 Scavenge 还存活 → 晋升老生代
  - 适合「朝生夕死」的对象（大多数局部变量），复制成本低
- 老生代
  - 标记清除（Mark-Sweep）：从根（全局对象、执行栈）出发标记可达，清除不可达——按**可达性**判断，所以循环引用也能回收（对比引用计数的死穴）
  - 标记整理（Mark-Compact）：清除后碎片多时，把存活对象移到一端
  - 全停顿问题：标记时 JS 暂停；V8 用**增量标记**（分小段穿插 JS 执行）+ 并发标记缓解

### 3. 哪些操作会造成内存泄漏？

**结论：本质都是「已经用不着的对象被无意间挂着引用，GC 收不走」；高频四类 + 一个定时器。**

- 四类高频场景
  - 意外的全局变量：未声明的赋值挂在 `window` 上
  - 被遗忘的定时器/回调：setInterval 不 clearInterval，回调里引用大对象
  - 闭包持有：长生命周期函数持有大对象引用（事件监听不 removeEventListener 同理）
  - 游离 DOM 引用：JS 变量存着已被移除的 DOM 节点，节点回收不掉
- 排查手段（体现工程化）
  - DevTools Memory 面板：操作前后各拍一次堆快照对比，看新增对象
  - Performance 面板录制：看内存锯齿是否持续爬升（GC 后不回落 = 泄漏）
  - `performance.memory`：可做页面内存监控指标
