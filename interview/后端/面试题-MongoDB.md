# 面试题 · MongoDB

> 对齐知识体系：node 模块四·数据与缓存（数据库）。
> 红线：定位全栈拓展；重点是「什么时候选 MongoDB、为什么」，运维级深挖不在范围。

## 一、数据模型与选型

### 1. MongoDB 是什么？和 MySQL 的核心区别与适用场景？

**结论：文档型 NoSQL——BSON 文档存储、无模式、嵌套结构天然聚合，适合内容/日志/画像/配置等半结构化与快速迭代场景；MySQL 强在关系、外键、复杂 JOIN 与强事务。选型看数据模型与访问模式，不看「谁更快」。**

- 对比表

| 维度 | MongoDB | MySQL |
| --- | --- | --- |
| 数据模型 | 文档（嵌套/数组） | 表（二维关系） |
| 模式 | 灵活（字段可动态增减） | 严格 schema |
| 关联 | `$lookup`（非强项）；优先内嵌 | 外键 + JOIN |
| 事务 | 4.0+ 多文档事务（有限制） | 完整 ACID |
| 扩展 | 原生分片，水平扩展强 | 分库分表成本高 |
| 适合 | 内容/日志/画像/IoT/配置 | 金融/交易/报表/强关系 |

- 一句话答法：**MongoDB 适合「对象天然是一个文档」的场景（一次读出整个聚合），MySQL 适合「数据之间关系复杂、要约束与一致性」的场景**
- 追问：MongoDB 支持事务吗？
  - 4.0+ 支持副本集内多文档事务（4.2+ 分片集群）；但设计哲学是**优先单文档原子性**——把需要原子的数据建模进一个文档，比开事务更「MongoDB」

### 2. BSON 和 JSON 的区别？ObjectId 的结构？

**结论：BSON 是二进制编码的 JSON——类型更丰富（日期/二进制/Decimal128/ObjectId 等）、可快速定位文档边界、机器解析更快；ObjectId 是默认主键，12 字节 = 4 时间戳 + 5 机器/进程随机 + 3 自增计数，天然趋势递增。**

- ObjectId 三段（记住功能不背字节）
  - 时间戳：可反推创建时间
  - 机器 + 进程标识：多机不冲突
  - 计数器：同进程同秒内唯一
- 趋势递增的意义（加分）：作为 `_id` 主键写入近似顺序追加，减少 B 树页分裂——与 MySQL「自增主键」同样的道理
- 追问：概念映射关系？
  - 文档↔行、集合↔表、数据库↔数据库；但集合内文档可不同构（无模式）

### 3. 内嵌（embedded）和引用（reference）怎么选？

**结论：「一起读写就内嵌、各自独立增长或被多方共享就引用」——内嵌一次读全拿无 JOIN，但文档上限 16MB 且会放大更新；引用避免冗余但要多次查询或 `$lookup`。**

- 判断标准
  - 内嵌：一对一、一对少量、整体生命周期一致（订单+订单项、用户+地址）
  - 引用：一对多且「多」无限增长（评论列表——只内嵌最近 N 条，其余单独集合）、多对多、被多个父文档共享
  - 反模式：无限增长的数组内嵌——文档膨胀导致频繁迁移与 16MB 上限风险
- 追问：MongoDB 文档最大多大？
  - 单文档 16MB 硬上限；大文件用 GridFS 或对象存储，库里只存引用

## 二、查询与索引

### 4. MongoDB 的索引机制？和 MySQL 有什么异同？

**结论：底层同为 B 树（WiredTiger 的 B+ 树变体），复合索引同样遵守最左前缀；差异在多键索引（数组字段建索引）、TTL 索引（自动过期删除）等特色类型，explain 验证同样是一切优化的起点。**

- 常用类型
  - 单字段 / 复合（顺序 = 等值→排序→范围，与 MySQL 同思路）
  - 多键索引（multikey）：数组字段自动展开，一个文档对应多个索引项
  - TTL 索引：按时间自动删文档——会话/日志保留期的标配
  - 文本索引 / 地理索引（2dsphere）
- 覆盖查询：查询与投影的列全在索引里，不回表——与 MySQL 覆盖索引同概念
- 追问：`explain()` 输出里看什么？
  - `winningPlan.stage`：COLLSCAN（全表扫）→ IXSCAN（走索引）；`totalDocsExamined` vs `nReturned` 的比值越小越好

### 5. 聚合管道（Aggregation Pipeline）是什么？怎么优化？

**结论：多阶段数据处理流水线——`$match` 过滤 → `$group` 聚合 → `$sort` 排序 → `$project` 裁剪等，数据像流水线一样逐阶段变换；优化核心是 `$match`/`$limit` 前置、排序用索引、控制 `$lookup` 次数。**

- 常用阶段

| 阶段 | 作用 |
| --- | --- |
| `$match` | 过滤（等价 WHERE） |
| `$group` | 分组聚合（等价 GROUP BY） |
| `$sort` / `$limit` / `$skip` | 排序分页 |
| `$project` | 字段裁剪与改名 |
| `$lookup` | 左连接（等价 LEFT JOIN） |
| `$unwind` | 数组拆行 |

- 优化清单
  1. `$match` 放最前——尽早缩小数据量（有索引时它在管道优化器里也会被前置）
  2. `$sort` 在 `$limit` 前、且让 `$sort` 走索引
  3. `$project` 早裁剪字段，减少后续阶段内存
  4. `$lookup` 是性能大头——能内嵌建模就少 lookup
- 追问：管道每个阶段的内存限制？
  - 默认单阶段 100MB，超了报错——`allowDiskUse: true` 落盘换容量，但慢；根子上靠裁剪数据量

### 6. MongoDB 分页怎么做？skip 有什么问题？

**结论：小数据量 `skip+limit`，大数据量必须「基于 _id/有序字段」的游标分页——skip 会扫描并丢弃前面所有文档，代价随页深线性涨，与 MySQL 深分页同一个病。**

- 两种写法

```js
// 小数据量：简单但要跳过前 N 条
db.user.find().skip(100000).limit(10)

// 大数据量：记住上页最后一个 _id
db.user.find({ _id: { $gt: lastId } }).sort({ _id: 1 }).limit(10)
```

- 排序字段必须有索引，否则 sort 触发全集合扫描（32MB 排序内存上限）
- 追问：游标分页不能跳页怎么办？
  - 产品要跳页就用「延迟关联」思路（先只查 `_id` 列表再回查），或直接限制跳页交互

## 三、可靠性与扩展

### 7. 副本集（Replica Set）的原理？

**结论：一主多从——写走 primary，secondary 拉 oplog（操作日志）重放保持同步；primary 挂了集群自动选举新主，实现高可用。**

- 要点
  - oplog：主节点的写操作环形日志，从节点异步拉取重放——**复制是异步的**，从节点读可能读到旧数据（复制延迟）
  - 选举：多数派投票选新主；建议至少 3 个数据节点（奇数），否则选不出主
  - 读写偏好：`primary`（默认强一致读）/ `secondaryPreferred`（分担读压，接受旧数据）——按一致性要求选
- 追问：write concern 怎么理解？
  - `w:1` 主节点确认即返回（快，宕机可能丢）；`w:"majority"` 多数节点确认（安全，慢）——按业务容忍度配

### 8. 分片（Sharding）解决什么问题？shard key 怎么选？

**结论：数据按 shard key 水平拆到多个分片，解决单机容量与吞吐上限；shard key 要高基数、查询常用、写入均匀——选错 key 会导致数据倾斜或查询广播所有分片。**

- 架构三件套：mongos（路由）→ config server（元数据）→ shard（数据）
- shard key 选择
  - 高基数（区分度高，不能用「国家」这种低基数字段）
  - 常用查询要带上 shard key（避免全分片广播）
  - 写入分布均匀（自增 _id 当 shard key 会写热点在最后一片——单调递增是反模式）
- 什么时候才分片（红线）：单机容量/吞吐真到瓶颈再分——分片带来运维与查询复杂度，能副本集解决就不分片
- 追问：MongoDB 和 Redis 怎么分工？
  - Redis 内存做热数据缓存/计数/锁，MongoDB 做持久化文档存储——Redis 挡读流量，Mongo 存全量，是常见的组合而非二选一
