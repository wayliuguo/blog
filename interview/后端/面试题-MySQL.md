# 面试题 · MySQL

> 对齐知识体系：node 模块四·数据与缓存（数据库）。
> 项目结合点：赴演记（MySQL + TypeORM）。红线：定位全栈拓展，不吹 DBA；原理讲到「能解释现象」即可，深挖源码层面不在范围内。

## 一、索引

### 1. 为什么 MySQL 索引用 B+ 树而不是 B 树、哈希表、二叉树？

**结论：B+ 树为磁盘而生——非叶子节点不存数据单页能装更多键（树更矮 IO 更少）、叶子节点有序链表天然支持范围查询、查询路径长度稳定；哈希不支持范围，二叉树太高，B 树范围查询要回溯。**

- 三层 B+ 树能存多少（面试加分账）：InnoDB 页 16KB，非叶子节点约存 1170 个键（键 8B + 指针 6B），三层 ≈ 1170 × 1170 × 16 行 ≈ 2000 万行——千万级数据也就 3~4 次 IO
- 对比

| 结构 | 等值查询 | 范围查询 | 结论 |
| --- | --- | --- | --- |
| 哈希表 | O(1) | 不支持 | 排除 |
| 二叉/红黑树 | O(logN) | 麻烦 | 树太高、IO 次数多 |
| B 树 | 快 | 要中序回溯 | 次优 |
| B+ 树 | 稳定（都到叶子） | 叶子链表顺序扫 | **最优** |

- 追问：什么情况哈希索引反而合适？
  - 只有等值、无范围无排序的场景（如 Memory 引擎/缓存映射）——InnoDB 有自适应哈希作内部加速，但不暴露给用户

### 2. 聚簇索引和非聚簇索引的区别？什么是回表？

**结论：聚簇索引的叶子节点就是数据行本身（一张表只有一个），二级索引的叶子存「索引列 + 主键」，查到主键后还要回聚簇索引再查一次——这就是回表。**

- 对比表

| 维度 | 聚簇索引（主键） | 二级索引 |
| --- | --- | --- |
| 叶子内容 | 完整数据行 | 索引列值 + 主键 ID |
| 数量 | 只能 1 个 | 可多个 |
| 查完整行 | 直接拿到 | 需回表 |

- 没定义主键怎么办（加分）：InnoDB 选第一个非空唯一索引，再没有就生成隐藏的 6 字节 ROW_ID
- 为什么建议用自增主键：写入时顺序追加不产生页分裂；UUID 主键随机写会导致频繁页分裂与碎片
- 追问：什么时候二级索引比回表更划算？
  - 覆盖索引时（见下题）——根本不回表

### 3. 什么是覆盖索引？怎么用它优化查询？

**结论：查询所需的所有列都包含在索引里，无需回表——EXPLAIN 的 Extra 出现 `Using index` 即命中；是少 IO 的第一优化手段。**

- 例：联合索引 `(name, age)`，`SELECT name, age FROM user WHERE name='张三'` 直接走索引不回表；改成 `SELECT name, age, phone` 就要回表
- 配套技巧：深分页优化里「先查 ID 再关联」就是利用覆盖索引只扫索引不扫行
- 追问：`SELECT *` 为什么被口诛笔伐？
  - 几乎必然回表 + 无法覆盖索引 + 拉多余字段占网络与内存——列裁剪是免费的优化

### 4. 最左前缀原则是什么？联合索引的列顺序怎么定？

**结论：联合索引 `(a,b,c)` 的 B+ 树按 a→b→c 排序，查询条件必须从最左列连续匹配才能用上索引；列顺序按「等值列在前、范围列在后，兼顾排序与区分度」。**

- 匹配速查

| 条件 | 是否用索引 |
| --- | --- |
| `a=1` | ✅ 用 a |
| `a=1 AND b=2` | ✅ 用 a,b |
| `b=2` | ❌ 跳过最左列 |
| `a=1 AND c=3` | ⚠️ 只用 a（b 断裂） |
| `a>1 AND b=2` | ⚠️ 只用 a（范围后失效） |

- 加分：优化器会自动重排 WHERE 顺序——`WHERE c=3 AND a=1` 一样走 `(a,b,c)` 的 a；范围列放最后是因为范围之后的列无法继续匹配
- 排序场景：`ORDER BY b` 在只有 `(a,b)` 索引且 `WHERE a=1` 时可免 filesort（索引内已有序）
- 追问：`(a, b)` 和两个单列索引 `(a)`、`(b)` 的区别？
  - 单查 a、b 各走各的；同时查 a+b 时联合索引一次定位，两个单列索引要做 index merge（效率差且不稳定）

### 5. 哪些场景索引会失效？至少说五条

**结论：对索引列做函数/运算、隐式类型转换、前模糊 `LIKE '%x'`、`OR` 两侧有非索引列、区分度过低被优化器放弃——失效的本质是「无法在有序结构上定位」。**

- 清单
  1. `WHERE YEAR(create_time)=2023` / `WHERE id+1=10`——列被函数或运算包裹
  2. 隐式类型转换：`WHERE phone=13800001111`（phone 是 varchar，字符串列被转数字）
  3. `LIKE '%abc'` 前缀不确定，无法走有序树（`'abc%'` 可以走）
  4. `OR` 连接了无索引列
  5. 联合索引不满足最左前缀
  6. 优化器判断全表更快（区分度低、回表代价高）——这不是「失效」而是「主动不用」，能说出这点是加分项
- 追问：怎么验证到底走没走索引？
  - EXPLAIN 看 key 列与 type——别靠猜

## 二、事务与 MVCC

### 6. ACID 分别靠什么实现？

**结论：原子性靠 undo log 回滚、持久性靠 redo log + 两阶段提交、隔离性靠 MVCC + 锁、一致性是前三者共同保证的结果——「一致性是目的，其余是手段」这句是加分总结。**

- 对应表

| 特性 | 实现机制 |
| --- | --- |
| 原子性 | undo log（回滚日志） |
| 持久性 | redo log（崩溃恢复）+ doublewrite |
| 隔离性 | MVCC + 锁 |
| 一致性 | 以上三者 + 约束共同保证 |

- 两阶段提交（redo 与 binlog 的一致性）：redo prepare → 写 binlog → redo commit——保证两份日志要么都成功要么都不算，否则主从与崩溃恢复会不一致
- 三大日志一句总结：**redo 保崩溃恢复、undo 保回滚与 MVCC 版本链、binlog 保复制与归档**
- 追问：为什么事务内不要做远程调用？
  - 长事务持锁时间拉长、undo 链堆积、连接占用——远程调用移到事务外，或用消息补偿

### 7. 四种隔离级别分别解决什么问题？MySQL 默认哪个？

**结论：读未提交 → 读已提交（解决脏读）→ 可重复读（再解决不可重复读，MySQL 默认）→ 串行化（再解决幻读）；MySQL 的 RR 通过 MVCC + 间隙锁基本解决幻读。**

- 三级并发问题：脏读（读到未提交）、不可重复读（两次读值不同）、幻读（两次读行数不同）
- 每级解决对应

| 级别 | 脏读 | 不可重复读 | 幻读 |
| --- | --- | --- | --- |
| 读未提交 | ❌ 有 | ❌ 有 | ❌ 有 |
| 读已提交 RC | ✅ 免 | ❌ 有 | ❌ 有 |
| 可重复读 RR（默认） | ✅ 免 | ✅ 免 | ✅ 基本免 |
| 串行化 | ✅ 免 | ✅ 免 | ✅ 免（加锁） |

- 加分：RC 与 RR 在 MVCC 上的唯一差别——RC 每次 SELECT 生成新 ReadView（能看到别人最新提交），RR 首次生成后全程复用
- 追问：RR 下幻读「基本」解决的含义？
  - 快照读靠 MVCC 避免幻读；当前读靠间隙锁阻止插入；混用快照读与当前读的特殊时序仍可能出现幻读——说「彻底解决」反而扣分

### 8. MVCC 的实现原理？

**结论：每行数据带隐藏字段（最近修改的事务 ID trx_id + 回滚指针 roll_ptr），同一行的多个版本沿 undo log 串成链；事务用 ReadView 判断哪个版本对自己可见——读不加锁，读写不阻塞。**

- ReadView 可见性判断（记住核心思想即可，规则不必背全）
  - 版本是自己的 → 可见；事务已提交 → 可见；事务还在进行/在活跃列表里 → 不可见，沿版本链往前找
  - RR：首次快照读生成 ReadView 复用；RC：每次生成新的
- 写并发：写写冲突仍靠锁；MVCC 只解决「读不阻塞写、写不阻塞读」
- 追问：undo log 版本链会不会无限长？
  - 不会被任何事务引用的版本由 purge 线程回收——**长事务**会拖住 purge，导致版本链堆积、磁盘暴涨，这也是长事务危害的根因

### 9. 快照读和当前读的区别？

**结论：快照读读 MVCC 可见版本不加锁（普通 SELECT），当前读读最新已提交版本并加锁（`FOR UPDATE`/`LOCK IN SHARE MODE` 及所有 DML）；幻读防护机制两者不同。**

- 对比

| 维度 | 快照读 | 当前读 |
| --- | --- | --- |
| 场景 | 普通 SELECT | SELECT...FOR UPDATE / UPDATE / DELETE / INSERT |
| 数据来源 | undo 链可见版本 | 最新已提交数据 |
| 加锁 | 不加 | 行锁/间隙锁/临键锁 |
| 防幻读 | ReadView 过滤 | 间隙锁阻止插入 |

- 追问：业务里什么时候必须当前读？
  - 「查出来再改」且要防并发覆盖的场景（扣库存、占座位）——`FOR UPDATE` 或直接原子 UPDATE

## 三、锁

### 10. 行锁、间隙锁、临键锁的区别？什么条件下退化？

**结论：行锁锁索引记录、间隙锁锁记录之间的空隙（防插入防幻读）、临键锁是行锁+间隙锁（左开右闭）且是默认加锁方式；唯一索引等值命中退化为行锁、未命中退化为间隙锁——退化是为了缩小锁范围提升并发。**

- 场景表（表中有 id=5, 10, 15）

| 查询 | 加锁 |
| --- | --- |
| `WHERE id=10 FOR UPDATE`（唯一索引命中） | 行锁：id=10 |
| `WHERE id=12 FOR UPDATE`（未命中） | 间隙锁：(10, 15) |
| `WHERE id>5`（范围） | 临键锁：(5,10] + (10,15] + (15,+∞) |

- 前提：**锁挂在索引上**——条件无索引时行锁直接升级为近似表锁，并发性能暴跌（高频追问）
- 追问：间隙锁只在哪个隔离级别生效？
  - RR（RC 没有间隙锁，所以 RC 吞吐更高但幻读风险回来）——RC 与 RR 的取舍本质是锁开销与隔离强度

### 11. 死锁是什么？怎么排查和避免？

**结论：两个事务互相等待对方持有的锁；InnoDB 自动检测并回滚代价小的事务；排查用 `SHOW ENGINE INNODB STATUS` 看 LATEST DETECTED DEADLOCK，避免靠「固定访问顺序 + 短事务 + 合理索引」。**

- 典型死锁

```text
事务A：锁 id=1 → 等 id=2
事务B：锁 id=2 → 等 id=1
```

- 避免三招
  1. 所有事务按相同顺序访问表和行
  2. 缩短事务（少持锁时间）
  3. 索引齐全——避免无索引更新把行锁放大成表锁后更容易互等
- 追问：`SHOW ENGINE INNODB STATUS` 里能看到什么？
  - 死锁双方的事务、各自持有的锁与等待的锁、SQL 语句——按这个还原时序改代码

### 12. 乐观锁和悲观锁怎么选？库存超卖怎么解决？

**结论：读多写少冲突低用乐观锁（版本号/CAS），写多冲突高用悲观锁（FOR UPDATE）；超卖的标准解法是「原子 SQL 扣减 / 版本号乐观锁 / 悲观锁」三选一，按并发量与容错要求定。**

- 三种写法

```sql
-- 原子 SQL：把判断塞进 WHERE，天然原子
UPDATE stock SET num = num - 1 WHERE id = 100 AND num > 0;

-- 乐观锁：版本号校验，affected rows = 0 则重试
UPDATE product SET num = num - 1, version = version + 1
WHERE id = 100 AND version = 5;

-- 悲观锁：锁住再改
SELECT num FROM stock WHERE id = 100 FOR UPDATE;
UPDATE stock SET num = num - 1 WHERE id = 100;
```

- 选型：普通业务优先原子 SQL；高并发低冲突用乐观锁；高冲突零容错（交易）用悲观锁
- 追问：Redis 扣减库存和数据库扣减怎么分工？
  - 热点流量 Redis 预扣（Lua 原子）+ 异步落库，数据库做最终扣减与对账——两层结合是电商标准答案（详见 Redis 篇）

## 四、优化与排查

### 13. EXPLAIN 怎么看？重点字段和信号？

**结论：第一步看 type（访问类型，从 system/const/eq_ref/ref/range/index 到 ALL——ALL 是全表扫描必须优化）、再看 key（实际用的索引）、rows（预估扫描行数）、Extra（`Using index` 好，`Using filesort`/`Using temporary` 要治）。**

- type 优先级：`system > const > eq_ref > ref > range > index > ALL`
- Extra 常见信号

| Extra | 含义 | 处理 |
| --- | --- | --- |
| Using index | 覆盖索引，好 | 保持 |
| Using filesort | 额外排序 | 让 ORDER BY 走索引 |
| Using temporary | 临时表（GROUP BY/DISTINCT） | 调整索引或 SQL |
| Using index condition | 索引下推 ICP 生效 | 好（加分概念：存储引擎层先用索引过滤再回表） |

- 追问：possible_keys 有值但 key 是 NULL 说明什么？
  - 优化器评估后认为不用更划算（回表代价高/区分度低）——配合 `FORCE INDEX` 实验对比，但生产慎用 hint

### 14. 慢 SQL 怎么排查？深分页为什么慢怎么优化？

**结论：三步法——开慢查询日志抓 SQL → EXPLAIN 看执行计划 → 按信号改写（加索引/覆盖索引/少扫行少回表少排序）；深分页 `LIMIT 100000,10` 慢在扫描并丢弃前 10 万行，解法是游标分页或延迟关联。**

- 慢 SQL 三步法
  1. `slow_query_log = ON` + `long_query_time = 1` 收集
  2. EXPLAIN 四字段：type / key / rows / Extra
  3. 改写三板斧：加对索引、避免 `SELECT *`、大事务拆小
- 深分页两解

```sql
-- ❌ 扫 100010 行丢 100000 行
SELECT * FROM `order` ORDER BY id LIMIT 100000, 10;

-- ✅ 游标分页：记住上页最后 ID（不支持跳页，适合无限滚动）
SELECT * FROM `order` WHERE id > 100000 ORDER BY id LIMIT 10;

-- ✅ 延迟关联：子查询只走覆盖索引拿 ID，再回表 10 行
SELECT o.* FROM `order` o
JOIN (SELECT id FROM `order` ORDER BY id LIMIT 100000, 10) t ON o.id = t.id;
```

- 追问：`count(*)`、`count(1)`、`count(col)` 的区别？
  - 前两者等价（InnoDB 会选最小的索引遍历，性能并不差）；`count(col)` 不统计 NULL 还要逐行判空，最慢
- 追问：连接池为什么必须配？
  - 建连+鉴权开销大，池化复用；上限防打爆数据库；**连接泄漏（只借不还）是常见线上事故**——TypeORM 里配连接数/队列/超时，用完必须释放
