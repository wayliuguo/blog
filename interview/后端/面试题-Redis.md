# 面试题 · Redis

> 对齐知识体系：node 模块四·数据与缓存。
> 项目结合点：赴演记（Redis 缓存 + 会话）。红线：定位全栈拓展，不吹缓存架构师；重点答「为什么这么设计 + 踩过什么坑」。

## 一、基础与数据结构

### 1. Redis 为什么快？单线程为什么够用？

**结论：纯内存操作 + 单线程命令执行（无锁无上下文切换）+ IO 多路复用（epoll）+ 高效数据结构；瓶颈通常在网络与内存，不在 CPU——所以单线程反而更快。**

- 四要素展开
  - 内存：所有数据在内存，没有磁盘 IO
  - 单线程：命令执行无锁竞争（6.0 起网络 IO 多线程化，**命令执行仍单线程**——这句是现役口径）
  - IO 多路复用：一个线程监听大量连接
  - 数据结构：SDS 动态字符串、跳表、压缩列表、quicklist 等都为内存与速度定制
- 追问：ZSet 底层为什么用跳表不用红黑树？
  - 实现简单、范围查询更顺（链表顺序扫）、支持按排名批量操作；跳表 + 哈希表组合，范围 O(logN)、按成员查分 O(1)

### 2. 五大基础数据结构及使用场景？

**结论：String 缓存/计数器/分布式锁，Hash 对象缓存，List 简单队列，Set 去重/共同关注，ZSet 排行榜/延时队列——答题时每个结构带一个真实场景。**

| 类型 | 底层 | 典型场景 |
| --- | --- | --- |
| String | SDS | 缓存、INCR 计数器、`SET NX` 锁 |
| Hash | ziplist → hashtable | 用户信息对象、购物车 |
| List | quicklist（双向链表） | 消息队列、最新列表 |
| Set | intset → hashtable | 去重、点赞、共同关注（SINTER） |
| ZSet | 跳表 + 哈希 | 排行榜、延时队列（score 存时间戳） |

- 加分扩展：Bitmap 签到/在线状态、HyperLogLog 基数统计（UV）、Geo 附近的人
- 追问：Hash 存对象和 String 存 JSON 序列化怎么选？
  - Hash 可单字段读写、省序列化开销；String 整存整取简单——字段常单独更新选 Hash

## 二、缓存三大问题（必问）

### 3. 缓存穿透、击穿、雪崩分别是什么？怎么解决？

**结论：穿透是「查不存在的数据」绕过缓存打 DB（解：布隆过滤器/空值缓存）；击穿是「热点 key 过期瞬间」并发打 DB（解：互斥锁/逻辑过期）；雪崩是「大量 key 同时失效或 Redis 宕机」（解：过期加随机/多级缓存/高可用）。**

- 三问题对照

| 问题 | 场景 | 解法 |
| --- | --- | --- |
| 穿透 | 恶意查 id=-1（库里也没有） | 布隆过滤器拦截；空值缓存（短 TTL）；参数校验 |
| 击穿 | 热点 key 到期瞬间 | 互斥锁（只放一个请求回源）；热点逻辑过期不设 TTL；预热 |
| 雪崩 | 大量 key 同时到期 / Redis 挂了 | TTL 加随机偏移；主从+哨兵高可用；多级缓存；限流熔断降级 |

- 区分记忆：穿透=数据不存在；击穿=单个热 key 失效；雪崩=大面积失效
- 追问：布隆过滤器原理与代价？
  - 多哈希位数组，说「可能存在」绝不说「不存在」——拦截穿透零误放；代价：误判率与不能删除（计数布隆可删）

### 4. 缓存与数据库一致性怎么保证？为什么是删缓存而不是更新缓存？

**结论：没有强一致，只有最终一致——标准做法「先更新 DB，再删缓存」，并发读写窗口用延迟双删兜底；不更新缓存是因为并发写会乱序覆盖，删除让下次读回源更安全。**

- 方案梯度
  - 基础：先更 DB → 删缓存（Cache Aside 旁路缓存）
  - 窗口问题：读旧写并发的瞬间，旧值可能被写回缓存 → **延迟双删**（删缓存 → 更 DB → 延迟几百 ms 再删一次）
  - 更进一步：订阅 binlog（Canal）异步删缓存，把删除从业务代码里解耦
- 为什么删除而非更新
  - 并发更新 DB 与更新缓存的顺序无法保证，后写的旧值会覆盖新值
  - 更新后若没人读，白写（写放大）
- 追问：延迟双删的「延迟」等多久？
  - 比一次读请求的耗时略长即可（几百 ms），本质是等旧读回源写缓存的动作发生完再补删

## 三、持久化与高可用

### 5. RDB 和 AOF 的区别？生产环境怎么选？

**结论：RDB 是定时 fork 子进程的全量快照（文件小恢复快、可能丢最后一次快照后的数据）；AOF 是追加写命令日志（丢数据少、文件大恢复慢）；4.0+ 混合持久化（RDB 做底 + AOF 增量）两者兼得，生产推荐。**

- 对比表

| 维度 | RDB | AOF |
| --- | --- | --- |
| 内容 | 全量二进制快照 | 写命令文本日志 |
| 数据安全 | 可能丢最后一段 | everysec 最多丢 1 秒 |
| 恢复速度 | 快 | 慢（逐条重放） |
| 文件 | 小 | 大（靠重写 AOF rewrite 瘦身） |
| 性能影响 | fork 瞬间可能卡（内存翻倍页表） | 每秒 fsync |

- AOF 三种刷盘策略：always（最安全最慢）/ everysec（推荐）/ no（交给 OS）
- 追问：RDB 的 fork 有什么风险？
  - fork 瞬间复制页表，大内存实例会卡顿；写时复制（COW）下写入高峰内存可能翻倍——大实例建议低峰期 bgsave

### 6. 主从复制、哨兵、Cluster 分别解决什么问题？

**结论：主从复制解决「数据冗余 + 读写分离」（异步复制可能丢数据）；哨兵解决「自动故障转移」（监控 + 选主 + 通知）；Cluster 解决「水平扩容」（16384 个哈希槽分片 + 自带高可用）——三者是叠加关系不是互斥关系。**

- 对比表

| 方案 | 解决 | 局限 |
| --- | --- | --- |
| 主从复制 | 冗余备份、读扩展 | 异步复制有延迟；主挂需手动切 |
| 哨兵 | 主挂自动选主切换 | 不解决容量上限 |
| Cluster | 16384 slot 分片 + 内置故障转移 | 不支持跨槽多 key 事务/ mget（要 hash tag） |

- 关键数字：Cluster `CRC16(key) % 16384` 定槽；哨兵至少 3 个节点（选举要过半）；MOVED（槽已迁走，永久重定向）与 ASK（迁移中，临时重定向）的区别
- 追问：主从延迟怎么应对？
  - 读不敏感场景容忍；强一致读走主；写后立即读的业务用「写后短时间读主」策略

## 四、实战应用

### 7. 分布式锁怎么实现？有哪些坑？

**结论：`SET key uniqueValue NX PX 30000` 一条命令原子加锁（NX 保证互斥、PX 防死锁、uniqueValue 防误删），解锁用 Lua 脚本校验 value 后删除保证原子；进阶用 Redisson 看门狗自动续期。**

- 三个坑与对策
  1. 忘设过期时间 → 客户端挂了锁永不释放（死锁）——`PX` 必带
  2. 删别人的锁 → 自己超时后锁已易主，直接 DEL 会误删——value 存唯一标识，Lua 里「比对一致才删」
  3. 业务没执行完锁先过期 → 看门狗自动续期（Redisson Watchdog）；或把过期时间设得远大于业务上限
- 追问：主从切换时锁会丢吗？
  - 会——主挂了锁还没同步到从，新主上锁不存在（RedLock 多节点过半加锁想解决这个，但争议大）；强一致锁诉求应考虑 ZooKeeper/etcd，说出这个权衡是加分项

### 8. 大 Key 和热 Key 的危害与处理？

**结论：大 Key（单 key 数据过大）阻塞单线程 + 网络慢 + 迁移卡；热 Key（单 key 访问过热）打爆单节点——大 Key 靠拆分与异步删除（UNLINK），热 Key 靠本地缓存与 key 分片。**

- 判定与处理

| 问题 | 判定 | 处理 |
| --- | --- | --- |
| 大 Key | String > 1MB；集合元素 > 5000 | 拆分（大 Hash → 多个小 Hash）；删除用 UNLINK（异步）不用 DEL（同步阻塞）；`--bigkeys` 定位 |
| 热 Key | 单 key QPS 异常突出 | 本地缓存（进程内 LRU 挡一层）；key 加随机后缀分片；读写分离 |

- 危害本质一句话：**Redis 命令执行单线程——一个大 Value 的读写会卡住所有请求**
- 追问：为什么禁用 `KEYS *`？
  - 全库遍历阻塞主线程，O(N) 卡死服务——线上用 `SCAN`（游标分批，不阻塞）

### 9. Redis 过期删除与内存淘汰策略？

**结论：过期删除 = 惰性删除（访问时检查）+ 定期删除（周期抽样清理）组合；内存满后按 maxmemory-policy 淘汰——生产推荐 volatile-lru（有过期时间的 LRU）或 allkeys-lru。**

- 过期删除
  - 惰性：key 被访问时才检查过期——省 CPU 但冷 key 占内存
  - 定期：周期性随机抽一批检查——两者互补
- 淘汰策略速记：noeviction（默认，写报错）/ allkeys-lru / volatile-lru / allkeys-lfu / volatile-ttl 等 8 种——LFU 适合访问频次差异大的场景（4.0+）
- 追问：Redis 事务和 Lua 怎么选？
  - MULTI/EXEC 只保证命令顺序执行不保证原子回滚；**Lua 脚本整体原子**（执行中不插入其他命令）——需要「判断+写」原子组合一律 Lua（扣库存/锁释放）

### 10. Redis 能做消息队列吗？

**结论：能但不专业——List（LPUSH/BRPOP）最简单但无 ACK 会丢消息，Stream 有持久化/消费组/ACK，是 Redis 内最接近 MQ 的方案；重可靠还是上 Kafka/RocketMQ。**

- 三档对比

| 方案 | 优点 | 缺点 |
| --- | --- | --- |
| List | 极简 | 无 ACK，消费者挂了消息丢 |
| Pub/Sub | 实时广播 | 不持久化，掉线即丢 |
| Stream | 持久化 + 消费组 + ACK | 吞吐与生态不及专业 MQ |

- 延时队列：ZSet score 存执行时间戳，轮询 `ZRANGEBYSCORE` 取到期任务
- 追问：什么规模以下用 Redis 队列就够了？
  - 量小、可容忍极端情况重放/丢失、不想引入新组件——内部通知、轻量任务分发；订单/支付类强可靠链路不要用

### 11. 场景题：秒杀的库存扣减怎么设计？

**结论：Redis 预扣挡住流量 + 数据库最终扣减——库存预热进 Redis，Lua 脚本原子「查-减-记」，扣成功的异步落库（MQ 削峰），扣失败直接返回售罄；DB 层再加原子 SQL/乐观锁兜底防超卖。**

- 链路分层
  1. 前置：库存预热进 Redis；按钮置灰/验证码削峰
  2. Redis 层：Lua 原子扣减（`DECR` 后判断，或先 GET 判断再 DECR 必须包 Lua 防竞态）
  3. MQ：扣成功发消息，消费端落库——DB 压力被削平
  4. DB 兜底：`UPDATE ... SET num=num-1 WHERE num>0` 原子扣，Redis 与 DB 对账
- 为什么不让 DB 直接扛：热点行锁让所有请求排队，DB 先崩
- 追问：Redis 扣成功但落库失败怎么办？
  - 补偿回滚 Redis 库存 + 记录异常对账；说「最终一致 + 对账兜底」比说「绝对不丢」更真实

### 12. 场景题：线上 Redis 变慢了怎么排查？

**结论：按「命令层面 → 内存层面 → 机器层面」三段排查——先看慢查询日志（SLOWLOG）抓慢命令，再查大 Key 与内存交换，最后看 CPU/网络/持久化时机。**

- 排查清单
  1. SLOWLOG GET：慢命令集中在哪（KEYS/大集合全量操作/误用 O(N) 命令）
  2. 大 Key：`--bigkeys`；删除是否用的 UNLINK
  3. 持久化：bgsave/AOF rewrite 是否撞上高峰（fork 卡顿）
  4. 内存：是否触发淘汰、是否 swap（内存交换是性能杀手）
  5. 网络：带宽打满（大 Value 批量拉取）、连接数暴涨
  6. 热点：单节点倾斜（Cluster 下热 key 集中一片）
- 答题框架比结论重要：先测量（SLOWLOG/监控）再下结论，与前端性能定位同一思想
