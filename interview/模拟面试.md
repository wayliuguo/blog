## 性能优化
### 借钱 H5 首屏优化：定位手段、落地措施、指标提升？

- 优化前我们通过 RUM 数据上报看真实用户的核心 Web Vitals，取 P75 口径：LCP 在 2.5 秒左右，超过了 Google 的"良好"阈值。

- 定位瓶颈时我分两步：先用线上 RUM 数据确定问题真实存在、锁定 P75 用户的画像（机型、网络、地域）；然后在相似条件下跑 Lighthouse 做实验室复现，缩小问题范围。具体排查时我按五层来做：网络层、资源层、渲染层、运行时层、接口层，逐层过。

- 定位下来存在的问题主要是：
  - 初始化接口耗时长：页面初始化要等 3 个接口串行返回才渲染核心内容，LCP 被接口链路拉长。我们把无依赖的接口改成 `Promise.all` 并行、有依赖的保持串行，同时把首屏关键接口做进 HTML 预请求。单点归因 LCP 降了约 400ms——是整个专项里归因最干净、收益最明确的一项。
  - LCP 元素是 CSS 背景图，浏览器要等 CSSOM 构建完才能发现它，发现时机天然偏晚。我们把图片 URL 提前注入 HTML 的 preload 并加 `fetchpriority="high"`，图片统一上 CDN；
  - 挽留弹窗拆包异步化：它原来和页面主 bundle 打在一起、首屏同步加载，传输 330KB。优化把它拆成独立 bundle，用 `defineAsyncComponent` 异步引入；预热在 onMounted 里注册，等 `load` 事件（网络空闲）之后的主线程空闲时段（requestIdleCallback）才真正发起——两层门槛保证不抢关键路径的带宽和主线程。首屏关键路径上不再有它，用户触发挽留时又因为预热过而秒开；
  - 基础建设
    - vue/vue-router/pinia 单独分包，业务迭代不影响 vendor chunk 的长缓存命中
    - Tree Shaking（lodash、内部库）、组件库按需加载
- 感知层面我们加了骨架屏：FCP 提前到 1 秒内，视觉上达到"秒开"，骨架屏按真实尺寸占位避免了布局跳动，CLS 控制在 0.1 以内。理论上骨架屏可能成为 LCP 元素、把 LCP 数字"做好看"，但我们在 Performance 面板实际观察过：有骨架屏的页面 LCP 元素并不是骨架屏——全屏背景图的面积比骨架占位块大，LCP 仍由背景图决定。
- 上线整体用灰度做了对照，确认指标变化确实是优化带来的，而不是流量结构变化。
- 最终 LCP 稳定在 1.5 秒，进入"良好"区间。

### LCP 元素有变怎么办？如何自定义 LCP 指标？

- 落地措施分三层：
  - 采集侧：上报 LCP 元素信息（tagName、class、图片 URL）；

export function useCoreBlockReport(selector = '.core-block') {

## 请求竞态：根因 + 至少两种方案及取舍？

- 根因：HTTP 对并发请求没有顺序保证，响应返回顺序不等于发出顺序。

- 方案一：双闸（发出时 cancel + 返回时拦截），我做在统一请求层：
  - 第一道闸在发出时：每个请求支持配置 key，新请求发出时如果同 key 的旧请求还在飞，用 AbortController 把它 abort 掉——省流量也减轻服务端压力；
  - 第二道闸在返回时：响应回来后请求层校验"是否还是当前最新 key"，不是就丢弃。这道闸是必须的，因为 cancel 并不可靠——abort 只保证客户端不再等待，服务端可能已处理完、响应可能已在缓冲区。cancel 管"尽量别来"，拦截管"来了也不认"，两道都设才算闭环；
  - 适用："结果已无意义"的场景（搜索输入、筛选切换）。代价是要业务配置 key，侵入性中等。

- 方案二：序号/generation 比对：请求层自动给每次请求递增 generation，响应回来比对是否当前代，不依赖业务配置 key、最通用。代价是所有"过期响应"一律丢弃，只保留最后一次，不适合需要其他合并语义的场景。

- 方案三：Vue 3 的 onCleanup：竞态很多时候不该藏在请求层，而该跟着副作用的生命周期走——`watch`/`watchEffect` 的 `onCleanup` 回调里取消上一次请求，依赖变化时自动清理。这是组合式 API 的设计本意，组件层最顺手；缺点是每个用到的组件都要写，不收敛在请求层。

- 相关代码

```ts
// ============ 1. 双闸：发出时 cancel + 返回时拦截（统一请求层） ============
const inflight = new Map<string, AbortController>()          // 同 key 在飞请求
const latest = new Map<string, number>()                     // 同 key 最新序号——必须按 key 隔离，
                                                             // 全局序号会误杀其他 key 的响应
async function request<T>(key: string, url: string): Promise<T> {
  // 闸一：同 key 旧请求还在飞 → abort 掉（省流量、减轻服务端压力）
  inflight.get(key)?.abort()
  const controller = new AbortController()
  inflight.set(key, controller)
  const seq = (latest.get(key) ?? 0) + 1
  latest.set(key, seq)

  try {
    const res = await fetch(url, { signal: controller.signal })
    const data = await res.json()
    // 闸二：abort 并不可靠（服务端可能已处理完、响应已在缓冲区），
    // 响应回来后校验——不是同 key 最新请求就丢弃。cancel 管"尽量别来"，拦截管"来了也不认"
    if (seq !== latest.get(key)) return Promise.race<never>([])   // 丢弃：返回永不 resolve 的占位
    return data
  } finally {
    if (inflight.get(key) === controller) inflight.delete(key)
  }
}

// ============ 1.5 双闸的 axios 版：闸一在请求拦截器、闸二在响应拦截器，业务零侵入 ============
import axios from 'axios'

const http = axios.create()
const inflightAx = new Map<string, AbortController>()
const latestAx = new Map<string, number>()

// TS：扩展 axios config，声明自定义字段
declare module 'axios' {
  export interface AxiosRequestConfig {
    raceKey?: string
    seq?: number
  }
}

// 闸一：请求拦截器——同 key 旧请求 abort，新请求编号
http.interceptors.request.use((config) => {
  const key = config.raceKey!
  inflightAx.get(key)?.abort()
  const controller = new AbortController()
  inflightAx.set(key, controller)
  config.signal = controller.signal                         // axios ≥0.22 原生支持 AbortController（CancelToken 已废弃）
  const seq = (latestAx.get(key) ?? 0) + 1
  latestAx.set(key, seq)
  config.seq = seq                                          // seq 随 config 带给响应拦截器
  return config
})

// 闸二：响应拦截器——不是同 key 最新请求就丢弃
http.interceptors.response.use(
  (res) => {
    const { raceKey: key, seq } = res.config
    // 只有"当前最新请求"的响应才清掉在飞记录——过期响应不清，避免误删新请求的 controller
    if (seq === latestAx.get(key)) inflightAx.delete(key)
    if (seq !== latestAx.get(key)) return new Promise(() => {})   // 丢弃：永不 resolve，业务侧无感
    return res
  },
  (err) => {
    if (axios.isCancel(err)) return new Promise(() => {})   // 被闸一取消的静默吞掉，业务层不用到处 catch
    return Promise.reject(err)
  }
)

// 业务侧：只声明 raceKey，双闸全程透明
// http.get('/api/search', { raceKey: 'search', params: { q: kw } })
```

## 请求缓存：key 怎么生成？如何按入参开关？

- key 的颗粒度：URL + 入参自动生成，不暴露给业务。
- 入参序列化必须稳定：`JSON.stringify` 直接序列化对象时，key 顺序由插入顺序决定——`{ a: 1, b: 2 }` 和 `{ b: 2, a: 1 }` 语义相同却会生成不同的 key。所以要先对 key 排序再序列化，嵌套对象递归处理。数组保持顺序（顺序本身是语义）。
- 开关由入参声明，默认不开启：`cache: true` 或 `cache: { ttl: 30000 }`。默认关闭是安全底线——缓存错一个写接口（提交订单被缓存，第二次点按钮直接返回上次结果）比少缓存十个读接口严重得多；金融类数据（额度、余额）宁可 TTL 短或不缓存。
- 缓存的是 Promise 而不是结果值：进行中的请求也能被第二个调用者共享，天然做**进行中去重**——同 key 并发调用只发一次请求，等的是同一个 Promise。
- 失效管理：TTL 过期自动失效；失败的 Promise 不缓存（下次重试）；写操作后主动按 URL 前缀批量失效（提交订单 → 失效订单列表 + 额度），主动失效比把 TTL 拉长更可靠。

- 相关代码

```ts
// ============ 1. key 生成：URL + 入参，序列化稳定 ============
function stableStringify(data: unknown): string {
  if (data === null || typeof data !== 'object') return JSON.stringify(data) ?? 'null'
  if (Array.isArray(data)) return '[' + data.map(stableStringify).join(',') + ']'
  // 对象：key 排序后递归——{ a:1, b:2 } 和 { b:2, a:1 } 生成同一个 key
  const entries = Object.entries(data as object)
    .sort(([a], [b]) => (a < b ? -1 : 1))
    .map(([k, v]) => `${JSON.stringify(k)}:${stableStringify(v)}`)
  return '{' + entries.join(',') + '}'
}

function buildCacheKey(config: AxiosRequestConfig): string {
  const params = config.params ? stableStringify(config.params) : ''
  const body = config.data ? stableStringify(config.data) : ''
  return `${config.method}:${config.url}?${params}#${body}`
}

// ============ 2. axios 拦截器实现：入参开关 + TTL + 进行中去重 ============
const cacheStore = new Map<string, { p: Promise<any>; time: number }>()

declare module 'axios' {
  export interface AxiosRequestConfig {
    cache?: boolean | { ttl?: number }                       // 入参开关：true 用默认 TTL，对象可指定
  }
}

http.interceptors.request.use((config) => {
  if (!config.cache) return config                           // 默认不开启：不缓存直接放行
  const key = buildCacheKey(config)
  const ttl = typeof config.cache === 'object' ? (config.cache.ttl ?? 30_000) : 30_000
  ;(config as any).__cacheKey = key                          // key 随 config 带给响应拦截器

  const hit = cacheStore.get(key)
  // 命中且未过期：直接复用同一个 Promise（进行中的请求也被共享 = 并发去重），请求根本不发
  if (hit && Date.now() - hit.time < ttl) {
    config.adapter = () => hit.p.then(res => ({              // 适配器短路：直接把缓存响应交回去
      data: res.data, status: res.status, statusText: '', headers: {}, config
    }))
  }
  return config
})

http.interceptors.response.use(
  (res) => {
    const key = (res.config as any).__cacheKey
    if (key) {
      // 存 Promise 而非结果值；p.catch 防失败缓存——失败的下一次重试
      const p: Promise<AxiosResponse> = Promise.resolve(res)
      p.catch(() => { if (cacheStore.get(key)?.p === p) cacheStore.delete(key) })
      cacheStore.set(key, { p, time: Date.now() })
    }
    return res
  },
  (err) => {
    const key = (err.config as any)?.__cacheKey
    if (key) cacheStore.delete(key)                          // 失败立即清，下次重试
    return Promise.reject(err)
  }
)

// ============ 3. 业务侧：声明开关即可，key 全程无感 ============
// http.get('/api/quota', { params: { uid }, cache: true })                  // 默认 TTL 30s
// http.get('/api/cardList', { params: { page }, cache: { ttl: 60000 } })    // 自定义 TTL
// http.post('/api/submit', form)                                            // 不声明 = 不缓存（安全底线）

// ============ 4. 写操作后主动失效：按 URL 前缀批量清 ============
function invalidateByPrefix(prefix: string) {
  for (const key of cacheStore.keys()) {
    if (key.includes(prefix)) cacheStore.delete(key)
  }
}
// 提交订单成功 → invalidateByPrefix('/api/order') + invalidateByPrefix('/api/quota')
```

## JWT 注销、续期、与 Session 的取舍？

注销怎么作废 token：JWT 无状态，签出去就收不回，所以必须在服务端补一个状态点。我的实现是 Redis 黑名单：用户调退出接口时，后端把这个 token 的 jti 写进 Redis，**TTL 设成这个 token 的剩余有效期**——过期后它自然失效，黑名单条目也自动清除，不会无限增长。全局鉴权中间件在验签之后、放行之前查一次黑名单，命中就返回登录过期。同时要把对应的 refresh token 一并拉黑——这步很关键，漏了的话被拉黑的 access token 换一个新 token 又活了。

续期方案：双 token。access token 短时效，我给到 **2 小时以内**——它的存在意义就是"泄露了影响窗口也极小"，长短由 refresh token 兜底；refresh token 长时效，7 到 30 天，而且做**一次性轮换**：每次用 refresh 换新 access 时，旧 refresh 作废、发一个新的，旧的再次被使用就视为泄露信号，直接吊销整个 token 家族。前端封装上，响应拦截器捕获 401 后自动刷新；这里有个关键细节是**并发单飞**：access 过期瞬间页面可能并行发了 5 个请求，全 401，如果不加锁会触发 5 次 refresh 调用，还可能互相把对方刚换的 refresh 作废。所以第一个 401 触发刷新并加锁，其余请求进队列等待，拿到新 token 后统一重放原请求。

无状态优势还剩多少、什么时候不如 Session：坦率说，做了黑名单之后 JWT 已经是"半有状态化"了——每个请求都要查一次 Redis，无状态的省去存储查询这个核心优势打了折扣。还剩的优势是：横向扩容不需要 session 亲和、跨服务共享鉴权只需共享密钥、payload 可以带基础用户信息减少查库。但我的判断标准是：如果业务需要**强即时撤销**——比如支付、风控、频繁踢人、权限高频变更——每次撤销都要靠黑名单实时生效，那这套复杂度不如直接上 Session，用集中式存储管理会话，撤销天然是 O(1) 的。我们项目是 C 端借钱业务，登录态变更频率低、对扩容有诉求，所以双 token + 黑名单是合适的平衡点。


## Q8. 线上故障 STAR + 防复发机制？

S(Situation 背景)/T(Task 任务|目标)：去年一次版本上线后约 10 分钟，后端监控平台报出某个接口的参数非法告警，5 分钟内累计 2000+ 次。我是这个页面的第一版开发者，对这个页面最熟，由我牵头处理。

**A(Action 行动)**：我先做了三件事：一是立刻在监控后台看告警的请求特征，确认是初始化试算接口收到了金额为 0 的非法参数；二是判断影响面——追踪这个请求的后续链路，确认它被下游校验拦住了、没有产生脏数据，业务无资损，所以不需要回滚，走热修；三是断点复现，定位到初始化逻辑在某个前置状态缺失时依然执行了试算。从告警到补丁上线大约 40 分钟。

**R(Result 结果)**：修复后告警归零。复盘会上我们沉淀了两个防复发机制：第一，**入口层加参数校验**，非法参数在源头拦截并上报，而不是等下游报错；第二，**把预发和灰度环境的告警纳入上线check list**——这次问题其实在预发就上报过，但当时没人看预发告警，所以新增了发布前检查预发告警清零的流程卡点。
