# 场景设计题

> 场景设计题是二面和三面的高频题型，考察的不是「记不记得 API」，而是「遇到一个真实需求，你怎么把它拆成可行方案」。每题按 **题目 → 分析思路 → 要点方案** 展开，代码给骨架与关键步骤。

## 1. 设计一个前端监控系统

- **题目**：请设计一个前端监控系统，要收集错误、性能、用户行为，并尽量减少对业务的影响。
- **分析思路**：先明确收集什么（错误/性能/行为）、怎么收集（无侵入）、怎么上报（不阻塞、去重、限流）、怎么存储与告警。
- **要点方案**：
  1. **错误监控**：`window.onerror` 捕获全局错误，`unhandledrejection` 捕获 Promise 异常，`error` 事件捕获资源加载失败。
  2. **性能监控**：用 Performance API 收集首屏、FP/FCP/LCP 等；用 `PerformanceObserver` 监听 LCP、长任务。
  3. **行为监控**：埋点收集 PV/UV、点击、路由（`hashchange`/`pushState`）。
  4. **无侵入**：封装 SDK，错误采集单例 + 全局监听，不侵入业务代码。
  5. **上报策略**：错误字符串化去重；超过阈值批量打包；Web Beacon / `sendBeacon` 或 `new Image()` 上报，页面卸载时用 `navigator.sendBeacon` 保证不丢失。
  6. **染色与采样**：按用户/场景染色全量，常规场景按比例采样控制成本。
  - 参考[监控](/interview/monitor)。

## 2. 实现一个无限滚动加载列表

- **题目**：一个可能上千条数据的列表，如何实现流畅的无限滚动，且内存不爆炸？
- **分析思路**：两种方向——「上拉加载」（增量 append）和「虚拟滚动」（只渲染可视区）；视频流列表常用分页 + 节流。
- **要点方案**：
  1. 分页加载 + 节流：滚动到底部附近触发加载，用 `throttle` 控制触发频率。
  2. 虚拟滚动：总高度用 `container 高 + item 高 × 总数` 撑开，`absolute` 定位可视项，仅渲染可视区。
  3. 关键参数：`scrollTop`、`viewportH`、`itemH`、`startIndex/endIndex`。
  - 骨架：
    ```
    onScroll: start = floor(scrollTop / itemH) - buffer
              end   = ceil((scrollTop + viewportH) / itemH) + buffer
              渲染 [start, end]，并把每个 item 的 top 设为 index * itemH
    ```
  4. 注意：固定高度计算简单，动态高度需预估 + 高度缓存。

## 3. 设计一个支持防抖/节流的 Markdown 编辑器

- **题目**：在线 Markdown 编辑器，内容变化时既要实时预览又要避免卡顿，你怎么设计？
- **分析思路**：编辑输入高频触发 → 需要防抖合并渲染；大文档解析耗时长 → 需要节流 / 分片 / 只更新变化区间。
- **要点方案**：
  1. **预览渲染**：输入后 `debounce(300ms)` 再渲染预览，避免每次按键都解析。
  2. **本地保存**：`debounce` 后再写 localStorage / 后端，防抖合并。
  3. **重型解析**：若解析很重，用 `throttle` 限制频率 + 走 `requestAnimationFrame` 或 Web Worker。
  4. **跳出编辑**：内容变化标记 dirty，切换文件/关闭前提示保存。
  - 参考对拍：需求要「实时但不卡」，就把「弹性」（防抖）和「限频」（节流）结合，先渲染高频编辑的自定义块。

## 4. 一套多端自适应（响应式）方案

- **题目**：同一套业务要跑在 PC 和移动端，且要适配不同分辨率 / 不同屏宽，你怎么做？
- **分析思路**：区分「适配方案」（rem/vw/fl - 布局单位）与「布局策略」（断点/移动端优先），并考虑页面差异是「自适应」还是「两套」。
- **要点方案**：
  1. **布局单位**：用 `vw`/`rem` 做字体与比例，`flex`/`grid` 做弹性布局；根字号随屏宽换算。
  2. **断点响应**：用媒体查询（如 768px / 1024px）切换排版，移动端优先（`min-width`）。
  3. **视口 meta**：`<meta name="viewport">` 设置，禁止误缩放。
  4. **复杂页面**：差异过大考虑 PC/H5 分流或用同前端不同路由。
  5. 选型权衡：`rem` 适合等比缩放，`vw` 更直接但注意最小宽度；业务富交互常两者结合。

## 5. 实现大文件上传（断点续传）

- **题目**：要上传一个 1GB 文件，网速一般、易中断，如何设计大文件上传？
- **分析思路**：核心是「切片 + 并行 + 秒传校验 + 断点续传 + 并发控制」。
- **要点方案**：
  1. **切片**：用 `Blob.prototype.slice` 把文件切成固定大小（如 2MB），逐个上传。
  2. **并行上传**：控制并发数（如 3~5 个），避免打爆连接。
  3. **断点续传**：已传的切片本地记录（localStorage/IndexedDB），刷新后跳过已传切片。
  4. **秒传**：前端计算整个文件 hash（`hash`、抽样 hash），服务端校验是否已存在。
  5. **合并**：全部上传成功后通知服务端按序合并，合并完成删临时切片。
  - 骨架：
    ```
    fileHash = await calcHash(file)          // 试大小，大文件用抽样 hash
    chunks   = cut(file, CHUNK_SIZE)
    并发上传每个 chunk（携带 index + fileHash）
    进度 = 已成功 chunk / 总数
    完成后 POST /merge
    ```

## 6. 设计前端权限系统

- **题目**：管理系统里有菜单可见性、按钮可用性、路由可访问性等多种权限，前端如何设计？
- **分析思路**：区分「路由权限」与「操作权限」，明确权限数据来源（登录后接口返回），落点在一个统一的鉴权工具。
- **要点方案**：
  1. **登录态**：token 存内存 + 刷新接口，路由守卫检查有没有 token，没有则跳登录。
  2. **动态路由**：登录后按用户角色/权限过滤出可见路由，动态注册（Vue Router `addRoute`）。
  3. **按钮权限**：抽 `v-permission` 指令或 `hasPermission(代码)` 封装，数据由接口返回。
  4. **服务端兜底**：前端只控制展示，真正的数据与接口权限必须在服务端校验，前端权限纯体验层。
  - 核心取舍：**前端权限是 UI 层，安全边界在服务端**。

## 7. 设计埋点统计系统

- **题目**：要统计全站的 PV/UV、点击、转化，上报量可能很大，前端怎么埋？
- **分析思路**：拆「埋点采集（通用/自动/命令式）→ 数据组织 → 上报（去重合并）→ 可视化」。
- **要点方案**：
  1. **手动埋点**：调用 `track(event, params)`，灵活但侵入。
  2. **自动埋点**：利用事件委托 / MutationObserver 自动采集点击、曝光。
  3. **PV/UV**：路由变化触发 pageView；UV 用设备标识（cookie/localStorage）去重。
  4. **上报**：批量合并 + `sendBeacon`（尤其卸载前），高频事件采样。
  5. **数据链路**：上报字段统一（event、uid、page、time、env），方便后端分析。
  - 参考[监控](/interview/monitor)。

## 8. 设计一个骨架屏

- **题目**：首屏内容靠异步加载，白屏期空白很难看，如何做骨架屏？
- **分析思路**：目标是「内容未到前先渲染一个与页面结构相近的占位」，重点是尽力匹配真实结构且不闪烁。
- **要点方案**：
  1. **粒度**：整页骨架 vs 局部骨架，SSR/SPA 都可应用。
  2. **实现方式**：
     - 静态骨架 HTML/CSS：手写或工具生成，随首屏直达。
     - 动态骨架：用真实 DOM 结构把文字/图片替换为占位色块（Sketch/插件生成），还原度高。
  3. **显示切换**：数据到达后隐藏骨架，注意用 `transition`/移除占位避免闪烁。
  4. 与 SSR 结合时骨架直接内联在 HTML，白屏期即展示。

## 9. 设计前端国际化（i18n）方案

- **题目**：产品要支持多语言，前端国际化方案怎么设计？
- **分析思路**：核心是「文案资源化 + 按 key 取值 + 语言切换 + 时区/数字/日期本地化」。
- **要点方案**：
  1. **文案抽取**：代码里不写死字符串，统一 `$t('key')`，语言资源放独立 JSON/按模块拆分。
  2. **语言切换**：依赖 `i18next`/`vue-i18n` 之类的库，运行时切换并持久化。
  3. **动态内容**：占位符插值、复数、变量；富文本用组件插槽。
  4. **非文案本地化**：日期、数字、货币用 `Intl`；`lang` 属性、方向（RTL）、字体。
  5. **构建期 vs 运行期**：大量页面可考虑分语言静态化（构建期），动态站点走运行期切换。

## 10. 设计一个前端请求库（带重试/取消/并发控制）

- **题目**：封装一个可靠的 http 请求库，要支持超时、重试、取消、防重、并发控制。
- **分析思路**：在 axios/fetch 之上组合若干**职责单一的功能**：拦截器、超时、取消、重试、池化。
- **要点方案**：
  1. **统一入口**：request 函数，封装 baseURL、超时、默认头，统一错误处理（统一弹提示/跳登录）。
  2. **超时 + 取消**：`AbortController` 实现取消；请求实例暴露 `cancelToken`/`signal`。
  3. **重试**：网络错误（非 4xx/业务错误）指数退避重试，顶层封装重试策略。
  4. **防重**：相同请求 key 并发去重，返回同一 Promise。
  5. **并发控制**：Promise 池限制最大并发，配合队列，超大并发不压垮服务。

## 11. 实现图片懒加载

- **题目**：长列表里很多图片，如何让图片真正滚动到才加载？
- **分析思路**：选 IntersectionObserver（推荐）或监听 scroll 计算位置；考虑失败重试与占位。
- **要点方案**：
  1. `data-src` 存真实地址，初渲染 src 置占位图。
  2. IntersectionObserver 观察图片进入可视区才赋真实 src，`unobserve` 移出观察。
  3. `rootMargin` 预留预加载距离，滚动更跟手。
  4. 兜底：低版本用 scroll + `getBoundingClientRect` 节流实现。

## 12. 设计一个全局错误上报 + 降级兜底

- **题目**：线上随时可能出错，怎么保证错误被看到，且用户体验不掉链子？
- **分析思路**：两个目标——「可观测」与「可降级」；监听错误 → 分类 → 上报 → 前端兜底渲染。
- **要点方案**：
  1. **监听**：`window.onerror` + `unhandledrejection` + 组件错误边界（Vue `errorHandler` / React ErrorBoundary）。
  2. **分类过滤**：ignore 掉白名单（如 script 加载静态资源 404 可降级处理）。
  3. **上报**：带堆栈 + 用户环境，`sourcemap` 定位源码。
  4. **降级兜底**：关键模块失败给「功能降级」或「重置按钮」，而不是白屏报错。

## 13. 设计一个权限隔离的多页面应用脚手架

- **题目**：企业要出多个子产品，但想共享基础能力（请求、鉴权、组件），怎么做多包/微前端？
- **分析思路**：权衡「Monorepo 共享」vs「微前端」；核心是抽公共包 + 独立部署 + 权限隔离。
- **要点方案**：
  1. **Monorepo（pnpm workspace）**：把公共请求封装、鉴权、UI 组件抽成 `packages/*`。
  2. **变更隔离**：版本管理与 break change 用 changeset，避免隐藏破坏。
  3. **微前端（如 qiankun/无界）**：子应用独立，基座做路由与沙箱隔离，主应用按需加载。
  4. **权限**：统一在基座鉴权，通过 props 注入 token 给子应用。

## 14. 设计一个关键词高亮 / 富文本搜索

- **题目**：页面有大量文本，搜索关键词高亮并快速定位，怎么做？
- **分析思路**：核心是「分词匹配 + 高亮节点渲染」；量大时走服务端检索，前端只管渲染命中的片段。
- **要点方案**：
  1. **匹配**：用正则（转义特殊字符）对文本匹配关键字，生成高亮区间。
  2. **渲染**：按区间把文本拆成「命中/未命中」片段，命中加 `<mark>`/高亮 class；注意 XSS 转义。
  3. **大量文本**：只在命中附近渲染可见片段（如前后各若干字），避免全量渲染。
  4. **滚动定位**：高亮后 `scrollIntoView` 定位到首条命中。

## 15. 实现一个拖拽 + 数据回传的看板编辑器

- **题目**：要做自由布局的看板，卡片可拖拽、缩放、保存布局，怎么设计？
- **分析思路**：拆「交互（拖拽/缩放）」与「数据（布局序列化规则）」；核心是统一的布局模型。
- **要点方案**：
  1. **布局模型**：每个卡片存 {id, x, y, w, h}，用网格布局（如 vuedraggable/grid-layout）。
  2. **交互**：拖拽实时更新坐标，给所有卡片传达避免重叠（视产品需求决定是否碰撞）。
  3. **持久化**：拖拽结束（拖/滚结束）节流保存布局 JSON 到后端，刷新恢复。
  4. **多用户**：避免并发覆盖，用版本号/最后写者策略，冲突时提示刷新。

## 16. 设计一个实时协作的多人表格

- **题目**：多人同时编辑同一张表格，前端如何做到低延迟且一致？
- **分析思路**：核心是「协同算法」——选 OT（操作转换）或 CRDT（无冲突复制数据类型）；前端关注 WebSocket 通道 + 本地缓冲。
- **要点方案**：
  1. **传输**：WebSocket 长连接，操作以「操作项」下发而非整表刷新。
  2. **本地先行**：输入先落到本地 + 乐观更新，立即反馈，后台同步。
  3. **一致性**：冲突用 OT/CRDT 解决，或简单场景悲观锁（单单元格编辑锁）。
  4. **重连**：断线期间的本地操作入队，重连后按序补发并对账。

## 17. Web 端实现实时图表/大屏（数据推送）

- **题目**：监控大屏要实时刷新数据，多次刷新怎么选型？
- **分析思路**：权衡轮询、SSE、WebSocket 三者的实时性、成本、复杂度。
- **要点方案**：
  1. **低实时**：轮询 + 节流，简单稳定。
  2. **单向推送**：SSE（`EventSource`）服务端单向推送，天然断线重连，适合推送场景。
  3. **双向交互**：WebSocket，适合高频双向（协同、聊天、游戏）。
  4. **渲染**：ECharts 数据增量更新，避免整表重绘；大数据量做降频渲染 / `requestAnimationFrame` 合并。

## 18. 设计一个前端打包/发布优化方案

- **题目**：项目打包越来越大、发布变慢，前端如何优化构建与发布？
- **分析思路**：拆「构建提速」与「产物瘦身」与「发布策略」。
- **要点方案**：
  1. **提速**：`esbuild`/`swc` 转译、cache 持久化、并行构建、跳过不必要的 lint。
  2. **瘦身**：按需引入、`splitChunks` 分包、压缩 + gzip/brotli、图片压缩。
  3. **发布**：CDN + 哈希指纹缓存、灰度发布、增量/差异发布（只更新变更模块）。
  4. **可回滚**：版本标记，异常快速回退上一版本。

## 综合答题套路

遇到**任何**场景设计题，都套这个框架回答，既结构化又显专业：

1. **澄清**：先问清规模、约束、实时性、成本（一句话即可）。
2. **目标/非目标**：说清楚这个方案要达到什么、不做什么。
3. **分层设计**：数据层 / 交互层 / 通信层 / 扩展点。
4. **关键取舍**：给出「为什么这么选」，证明你在权衡而不是背方案。
5. **演进空间**：补充异常处理、扩展性、性能边界。
