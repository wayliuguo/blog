- **服务端**：`/vendor/vue.js` → `node_modules/vue/dist/vue.esm-browser.prod.js`（浏览器直接跑 ESM，无构建步骤）；`startServer(options)` 新增 `port` / `spaCache` / `spaLatency`；`openChrome(url, flags, profileDir)` 新增第三个参数
- 四场景实测（3 轮中位数）：首屏 FCP 508→224 / 首屏有内容 247→94ms / 关键路径 JS 10→7 个 / DOM 10023→99；切路由 69（全量）/245（分割）/80ms（分割+预取，150ms RTT）；排序交互到下一帧 134→31→28ms；滚动 3985ms（最长任务 3035ms）→1007ms（0 个）；二次访问 289→278（无缓存）/266→122（HTTP 强缓存，0B）/276→205ms（SW，0B）
- **三个反直觉结论**：① 骨架屏让 LCP 落在「加载中…」上，指标变绿但用户没看到内容 → 必须配「内容就绪」自定义指标 ② 路由分割几乎不省体积（152.2→149.1KB，Vue 运行时占 131.5KB），省的是关键路径请求数 ③ **SW 比 HTTP 强缓存慢 ~80ms**（冷启动线程 + 每请求过 fetch），价值在离线与按资源分策略，不是「更快的缓存」
- **实验坑（重要）**：① HTTP 缓存按 origin 存，端口随机（listen 0）会导致「缓存没生效」的假象 → 缓存场景必须固定端口 5192 ② 本机 localhost 秒下，加载类对比必须人为加延迟（spaLatency）③ 无头环境无真实输入，脚本 click() 不产生 event 条目，INP 只能用「派发→第二个 rAF」近似 ④ 强制同步布局要「写完就读」才成立，只读不写测不出差异
