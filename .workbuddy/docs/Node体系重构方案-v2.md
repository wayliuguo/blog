## 1. 参考链接的知识链（已去 Agent）

三篇合起来是一条**主轴驱动的链**——所有内容都在回答同一个问题：
**「Node 为什么能用少量线程扛住大量 I/O？」**

### 第 1 篇 · 基础：先建立直觉

```
一次请求的真实耗时账
  MySQL 30ms + 向量库 100ms + 外部 API 2000ms + Redis 5ms + 落库 30ms
      ↓
疑问：Node 的 CPU 真的算了两三秒吗？—— 没有，真正跑 JS 只有几毫秒
      ↓
结论：这是 I/O 密集型（时间都花在"等"）
      ↓
阻塞模型的浪费：请求 A 等 2 秒时，CPU 空转，B/C 只能排队
      ↓
Node 的解法：非阻塞 I/O —— 发起后不等，去处理别的，完成后再回调
      ↓
── 于是问题变成：谁在调度这些回调？ ↓

模块系统（代码怎么组织）
  CommonJS require/module.exports → ESM import/export → package.json "type"
      ↓
Event Loop（为什么不会卡）
  单线程 ≠ 只有一个线程 → setTimeout(fn,0) 不是立即 → 132 / 1432 输出顺序
      ↓
异步编程（怎么写才不卡）
  Callback Hell → Promise → async/await → Promise.all（串行 700ms vs 并行 500ms）
  【澄清】await 只是写法像同步，并没有把 I/O 变成阻塞
      ↓
EventEmitter（事件驱动）
  on / emit → 注册 → 等待 → 触发 → 执行监听器
      ↓
Buffer（二进制数据是什么）
  Uint8Array 子类；'你好'.length = 2 而 Buffer.from('你好').length = 6
  应用：文件读取 / TCP chunk / 图片音视频 / 加密 / Base64
      ↓
Stream（大文件为什么不能一次读进内存）
  10GB 用 readFile 会炸；Stream 一块块处理（64KB），内存只占几十 KB~几 MB
  水桶（Buffer）vs 水管（Stream）
      ↓
fs（落地）
  readFile / writeFile / mkdir / readdir，扫描目录 → 读取文件
      ↓
串起来
```

### 第 2 篇 · 深入：同一个 Event Loop 再看一遍，这次到机械层

```
重新理解线程模型
  Node Application → V8 → Node bindings → libuv(Event Loop + Thread Pool) → OS(epoll/kqueue/IOCP)
      ↓
事件循环解决什么问题
  同步模型下数据库等 10/50/100/500ms，线程全在闲置
      ↓
libuv 的六阶段
  timers → pending callbacks → idle/prepare → poll → check → close callbacks
  （timers 是"最小等待时间"不是精确时间：while 阻塞 3000ms 后 timeout 才输出）
      ↓
网络 I/O 怎么异步
  net.createServer 不建线程；注册给 epoll；内核通知就绪 → 一个主线程管上万连接
      ↓
★【误区】所有异步操作都在线程池里跑吗？
  网络 I/O → 走 OS 异步机制，不占线程池
  fs / dns.lookup / crypto / zlib → 走 libuv 线程池
      ↓
libuv 线程池
  默认 4 个线程，UV_THREADPOOL_SIZE 可调（上限 1024）；pbkdf2 循环 10 次会分批
      ↓
setImmediate vs setTimeout(0)
  主模块里顺序不确定；在 I/O callback 里 setImmediate 先（poll → check → timer）
      ↓
Node 20 的变化
  libuv 1.45 起 timer 时机调整：旧 timers→poll→timers，新 poll→check→close→timers
  → 提醒读者注意文章年份与版本
      ↓
两者缺一不可：微任务
  nextTick Queue → Promise Microtask Queue → 每个回调结束后是 checkpoint
  【误区】微任务不是"一轮 Event Loop 才执行一次"
  【误区】递归 process.nextTick 会饿死事件循环（starvation）
      ↓
一张图彻底理解 Event Loop
      ↓
为什么特别适合 I/O 密集型
      ↓
Buffer（本质 / 例子 / 与 String 区别 / 5 个应用场景）
      ↓
Stream（核心思想 / 与 Buffer 关系 / 四种类型 / pipe / pipeline）
      ↓
背压（Backpressure）
  读 500MB/s 写 10MB/s → 不控制就 OOM → write() 返 false → 等 drain
      ↓
进程与线程（单线程不够用怎么办）
  Process 是什么 → child_process（spawn / exec / execFile / fork）
  → 为什么需要多进程 → Cluster → 进程间不能共享内存
  → Thread 是什么 → worker_threads → 什么场景用（CPU 密集）
  → 【误区】Worker Thread ≠ libuv 线程池
  → 【误区】生产环境不能每请求 new Worker（要 Worker Pool + Task Queue）
  → SharedArrayBuffer 共享内存
  → 生命周期：SIGTERM 优雅关闭 → 【误区】别滥用 process.exit()
      ↓
决策模型收尾（不是背 API，而是记判断表）
```

## 4. 连贯性机制（怎么做到"不分散"）

每篇开头 1 行引用，明说"上一篇留下的问题"；结尾 1 行"下一篇要回答什么"。

```
> 承上：03 结尾说「单线程不够用怎么办」—— 本篇就是答案。
```
