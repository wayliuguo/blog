# 文档组织规范

> 本文档是仓库文档的**单一规范出处**，覆盖 `frontend/` 与 `node/` 两大板块。所有文档组织、命名、结构与校验规则以本文为准；规则尽量可被脚本验证（见第 8 章）。

## 1. 总则与适用范围

- 适用范围：`frontend/`（基础 + 进阶两级）与 `node/`（模块目录）下的全部 Markdown 文档、VitePress 导航配置、配套代码项目。
- 文档是为「来仓库找知识的同行」和「想跑通示例的人」写的：标题即问题或判断句，正文给结论 + 原理 + 用法，代码给出处与真实输出。
- 单一出处：本规范是唯一的长期规范；`.workbuddy/scripts/` 里的校验脚本只是本规范第 8 章的可执行形式，`.workbuddy/docs/` 下其他方案文档是「某一次怎么改的」历史记录，不构成规范。

## 2. 目录组织

- `frontend/`：`基础/`（01-HTML 基础、02-CSS、03-JavaScript 核心、04-网络与浏览器、05-前端框架-React、06-前端框架-Vue）+ `进阶/`（01-TypeScript、02-前端工程化与构建、03-交付与质量、04-前端框架原理、05-性能优化与监控、06-工程实践与架构）+ 进阶根目录下的 `面试方法论.md`。
- `node/`：11 个模块目录（`运行环境` … `进阶主题`）+ `面试方法论/`。
- **目录名与文件名保留编号前缀**（如 `01-HTML 基础`、`03-事件循环：六个阶段与微任务.md`）。编号是目录与文件的稳定标识，用于排序与出处标注（`（第 03 篇）`），**不得删除**。
- 每个模块目录包含：正文文章、`总结.md`、`面试题.md`；配套代码放 `node/<模块>/code/<项目名>/`。
- 侧栏标题（导航 `text`）**不写编号前缀**（见第 3 章），与文件名的编号解耦。

## 3. 侧栏标题规范

- 导航配置（`.vitepress/config/*.js`）中的 `text` 一律**不写 `0X-` 编号前缀**。
  - ✅ `{ text: 'Node.js 是什么', link: '/node/运行环境/01-Node.js 是什么' }`
  - ❌ `{ text: '01-Node.js 是什么', link: '...' }`
- `text` 与文件名解耦：文件名保留编号（用于排序与出处），`text` 只写可读标题。
- 同一分组内 `text` 不得重名。
- 校验：对 `text: '0X-` 做全局 grep，应为 0 命中（含 `00-`）。

## 4. 单篇文章规范

单篇文章的标准解剖：

```
# <篇标题>

（正文：若干「知识小节」，小节标题即问题或判断句）

## 小结          ← 两级知识树，位置固定
## 配套代码       ← 表须含「对应小节」列；无独立 demo 时写「无独立 demo，见小节 XX」
## 参考          ← 首两行固定为本模块「总结 / 面试题」链接
```

- 结尾三段顺序**不可变**；正文不写 `> 承上：` / `> 启下：`，不写 `## 开篇`。
- 篇内引用别篇写「见第 X 篇」。
- `## 小结` 为两级知识树：第一层 = 有信息量的概念域，第二层 = `- **知识点**：一句话结论`；严格并列项用 `1. 2.` 编号；最多三级、每级缩进 2 空格、同层 ≤ 8 条。
- 部分篇目（收束 / 导读类）允许不加小结，具体以模块正文为准。

## 5. 模块总结规范（`<模块>/总结.md`）

统一结构：

```
# 模块总结 · <模块名>

## 知识主线      ← ASCII 依赖链图 + 一段「为什么这样排」的话
## 分篇知识点     ← 两级知识树（见下）
## 参考          ← 各篇链接 + 模块面试题链接
```

`## 分篇知识点` 规则（两级知识树，对齐 node 侧形态）：

- 每个正文篇对应一个 `### <篇名>` 节。
- 第一层 = `- **概念域**`，须有信息量（不能是「模块系统」这类空壳）；沿用已有条目标题，空壳时按正文提炼。
- 第二层 = `  - **知识点**：作用 + 用法概览一句话`，逐个覆盖该概念域下每个工具/子概念——**不是只列名字**。示例（内置工具类型必须逐条展开）：

```
- **内置工具类型**
  - **Partial<T>**：把 T 所有属性变为可选，常用于表单局部更新
  - **Pick<T, K>**：从 T 中挑出 K 指定属性组成新类型
  - **Record<K, V>**：以 K 为键名、V 为值类型构造对象类型
```

- 严格并列项用子弹逐条列，不使用 `1. 2.` 编号；每级缩进 2 空格；同一层 ≤ 8 条（超过则拆分概念域）。
- `## 知识主线` 与 `## 参考` 与正文保持一致；口径以正文为准。

## 6. 面试题规范（`<模块>/面试题.md`）

- 引言：用法说明 + 指向「面试方法论」的引用（`面试方法论.md`）。
- 每题格式：

```
### Q#: <题目>（第 XX 篇）

- **结论**：一句能背下来的判断句
- **原理**：机制讲解
- **边界**：局限/代价
- **追问**：预判下一句
- **场景**：实际场景
```

- 每题固定五条子弹，顺序为 结论/原理/边界/追问/场景；结论必须是判断句。
- 每题标出处 `（第 XX 篇）`；答案口径必须与正文一致，历史冲突一律按正文校订。

## 7. 配套代码规范

- 位置：`node/<模块目录>/code/<项目名>/`；`code/` 已通过 `srcExclude: ['**/code/**']` 排除出页面集合。
- 新增脚本必须同步三处：项目 `README.md`、`package.json` 的 `scripts`、对应篇正文的 `## 配套代码` 表。
- 脚本**先于文档**：先写出能跑通的脚本，再从它摘录进文档。
- 正文代码块标准形态：出处标注存在（`> 摘自 \`./code/xxx/src/05-buffer.js\``）+ 逐字摘录（省略处单独一行 `// …`）+ 实测输出（涉及数字、顺序、报错码时）。

## 8. 校验与维护

提交前必跑：

1. `grep` 检查：导航 `text: '0X-` 0 命中；总结 `## 分篇知识点` 无 `- **X**：...` 单层残留；面试题无 `## 0. 五步答题法` / `- [ ]` 残留。
2. `npm run prettier`（即 `prettier --write .`）：统一格式，使 pre-commit 钩子 no-op。
3. `npm run build`（即 `vitepress build`）：无 404 警告。
4. 提交用 conventional commits（husky + commitlint 强制）；提交前检查不触碰其他未提交改动。
