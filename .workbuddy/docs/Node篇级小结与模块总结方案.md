## 一、需求理解

### 1.1 关于「配套代码没覆盖到」

先澄清一个容易误判的点：我核查了 67 篇正文的 `## 配套代码` 小节，**引用的文件全部真实存在，没有死引用**。所以问题不是「链接坏了」，而是「**文档里讲到的知识点，代码里没有对应的验证脚本**」——`02` 篇两个脚本只演示了 CJS / ESM 各自最基础的写法，而正文里"两种系统的区别"和"互操作"这两大块（恰恰是这篇的核心）完全没有代码。

### 1.2 关于「总结」

我理解为**两级**：

| 级别 | 位置 | 定位 |
| --- | --- | --- |
| **篇级小结** | 每篇正文末尾，`## 配套代码` 之前 | 这一篇讲完，用 10~25 行把结论固化下来，并标出每条结论出自哪个小节 |
| **模块级总结** | 每个模块目录下新增一页 | 一屏之内扫完整个模块：知识主线 + 速查表 + 决策表 + 误区；**后续复习的入口** |

核心设计要求：**形态与位置完全可预期**（"总结在哪一页"不用想），且小结不是"把正文再抄一遍"，而是**结论化 + 可定位**（每条带出处小节，想细看能跳回去）。

```

  05-esm-imports-cjs.mjs          # ESM 导入 CJS：default = 整个 module.exports；命名导出靠静态分析
```

### 3.3 两个关键点已实测通过（方案可行性已验证）

在 Node 22.22.2 上实测：

```
① 活绑定 vs 值的拷贝
   ESM 导入后 counter = 0
   调用 bump() 后 counter = 1  ← 活绑定，看得到变化
   CJS 导入后 value = 0
   调用 bump() 后 value = 0    ← 值的拷贝，看不到变化

② CJS require ESM（Node 22 已支持）
   require(esm) OK
     named  greet = hello from esm
     default      = {"tag":"default-export"}
     keys         = __esModule, default, greet, name

③ ESM 导入 CJS
   default import of CJS → {"kind":"cjs-plain","value":42}
   named import  of CJS → named export from cjs   ← exports.x 形式可被静态分析识别
   namespace     of CJS → default, namedFromCjs, version
```

这三点是"区别与互操作"最有说服力的证据，都能变成可跑脚本 + 一段确定输出。

### 3.4 npm 包管理部分怎么做（两个选择）

| 选项 | 做法 | 代价 |
| --- | --- | --- |
| **甲（推荐）** | 只用 `10-resolution.cjs` + `11-semver-range.js` 两个零依赖脚本覆盖"能跑起来"的部分（查找算法、版本区间）；`npm init/install/scripts/锁文件` 属于**命令行操作**，在正文里用命令 + 输出示例讲清即可 | 不引入 `node_modules`，保持零依赖 |

## 四、篇级小结方案

### 4.1 形态：固定三元素

```md
## 小结

一句话：**<这一篇最该记住的判断句，能背下来>**

- <要点 1，一条一个判断句>（<小节名>）
- <要点 2>（<小节名>）
- ……（3~6 条）

| 维度 | A | B |     ← 有对照关系时用表格，比列表更清楚
| --- | --- | --- |

误区：<1~3 条，没有就不写>
```

三个设计要点：

1. **一句话结论打头** —— 用于"只记得住一句"的场景
2. **每条要点标注出自哪个小节** —— 这是"后续查看"的关键：小结里发现哪条不熟，直接定位回小节，不用重读全篇
3. **误区单列** —— 把这篇最容易被记反的点单独标出来

### 4.2 位置

固定在 `## 配套代码` **之前**：

```
正文各小节 …
## 小结          ← 新增
## 配套代码
## 参考
```

理由：`配套代码` 与 `参考` 是元信息，小结是**知识内容的收尾**；放在正文末尾、元信息之前，语义最顺，也让读者读完正文立刻看到收束。

### 4.3 示例（以 02 篇为例，实际落地时会写到这个程度）

```md
## 小结

一句话：**CommonJS 是运行时同步装载、导出的是值的快照；ES Module 是编译期静态分析、导出的是活绑定。**

| 维度 | CommonJS | ES Module |
| --- | --- | --- |
| 语法 | require / module.exports | import / export |
| 解析时机 | 运行时逐层同步解析 | 编译期静态分析，依赖图提前确定 |
| 加载方式 | 同步阻塞 | 异步（支持顶层 await） |
| 导出语义 | 值的拷贝（快照） | 值的引用（活绑定） |
| Tree Shaking | 不可能 | 可能 |
| 谁说了算 | .cjs，或 type 不是 module 的 .js | .mjs，或 type: module 的 .js |

- 判断用哪套：**新项目优先 ESM**；要兼容老代码 / 老工具链才用 CJS（Node.js 怎么判断用哪套）
- 一个文件只能是一套：`type` 是整包开关，`.cjs` / `.mjs` 是单文件强制（Node.js 怎么判断用哪套）
- 互操作三个方向：ESM `import` CJS（默认导出 = 整个 module.exports，命名导出靠静态分析）｜CJS `import()` 动态加载 ESM｜Node 22 起 CJS 也能直接 `require()` ESM（互操作）
- 依赖可复现 = `package.json` + 锁文件一起提交；`node_modules` 不进仓库（为什么必须提交锁文件）

误区：`exports = { ... }` 不会生效（断开了与 `module.exports` 的引用）；把 `.js` 混在 ESM 包里当 CJS 用会直接报错。
```

约 20 行。
